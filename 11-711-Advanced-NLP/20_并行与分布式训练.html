第二十讲：并行与规模化训练

单卡训练的计算量与 MFU，训练时的显存构成，批大小，激活重算与梯度累积，通信原语，数据并行及其重叠与分桶，张量并行，流水线并行与气泡，ZeRO 分片，怎样组合各种并行策略

主讲：Sean Welleck · 2026 年 3 月 31 日
资料来源：课程幻灯片（内容基于 Hugging Face 的 The Ultra-Scale Playbook） · 课堂录像（本文依据录像字幕整理课堂口述内容） · 课堂代码 · 主要阅读：The Ultra-Scale Playbook: Training LLMs on GPU Clusters（Hugging Face）

一、为什么要讲规模化

这部分课程以前叫"进阶话题"，Sean 今年发现这几讲有一个共同主题：效率与规模化。预训练、数据收集、微调、强化学习这些核心技术都讲过了，可靠地提升性能的一个办法就是把规模做大，而怎样做大很重要，也催生了不同的方法。上一讲是把模型缩小到能在电脑上跑；这一讲设想有人给你一万六千块 GPU，让你训练最好的模型，你该怎么做。下一讲的混合专家模型是一种新架构，同样是为了计算更高效、能用新的方式扩展。

这里主要考虑预训练，想法也适用于其他训练。缩放定律告诉我们，更多数据、更大的模型、更多计算，至少训练损失能可靠地变好。核心问题是怎样利用多个设备（GPU，在 Google 是 TPU）训练更大的模型，或者在给定时间内处理更多 token。要考虑三件事：

  • 显存使用：训练步骤必须放得进显存，模型太大时甚至要考虑怎样把它拆到多块 GPU 上。
  • 计算效率：希望硬件大部分时间都在计算，不浪费。
  • 通信开销：多个设备之间分配计算或模型就必然要通信，通信让 GPU 空闲，要尽量减少。这个主题会贯穿全讲。

本讲的大部分图和结构来自 Hugging Face 写的 The Ultra-Scale Playbook，想深入了解这个话题，它是最合适的资料。书里用比学术界多得多的算力训练了大量模型，每个点是一种并行配置。两个都是 3.5B 参数的模型，一个配置是 MBS 1、梯度累积 2、DP 128、PP 1、TP 2、ZeRO-1，另一个是 MBS 16、DP 2 等。不懂这些也能看出差别巨大：一个 MFU 17.4%，另一个 0.7%；一个每秒处理 170 万 token，另一个 6 万。你用后者而竞争对手用前者，你处理的 token 少得多，就会输。讲完这一讲应该能看懂这些配置的含义。

二、单卡训练的基础

先看一块 GPU 上发生什么：模型有若干层，做前向传播，再做反向传播计算梯度，用优化器（本讲只考虑 Adam，因为它带来大量显存开销）做一步更新，得到更新后的模型。要关心两样东西：计算和显存。

1. 计算

计算就是做浮点运算（加法、乘法）。缩放定律那一讲用过一个近似：前向加反向的计算量约为

$$6\times\text{model\_parameters}\times\text{token\_batch\_size}$$

对整个训练就是乘以总 token 数。学生说这是靠实验拟合出来的，Sean 说也可以这样，但有一个简单的论证：只考虑架构里的矩阵乘法，前向时每个参数参与一次乘法和一次加法，即 2 次浮点运算，所以前向是 2 倍参数量；反向要对权重求梯度，还要对激活求梯度传回去，这是两次矩阵乘法，又是 2 + 2。合计每参数 6 次。这只是粗略估计，Chinchilla 等论文用了更精确的近似。

术语区分：FLOP 指浮点运算次数（虽然是复数），FLOPS 指每秒浮点运算次数，是一个速率。衡量效率的指标是模型浮点利用率（Model FLOP Utilization，MFU）：

$$\text{MFU} = \frac{\text{Achieved FLOPS}}{\text{Theoretical Peak FLOPS}}$$

分母由设备厂商给出，即理论上每秒最多能做多少次浮点运算。NVIDIA 网页上 H100 的理论峰值随数据类型而不同，BF16 张量核心快得多，FP64、FP32 慢得多，这呼应了上一讲。分子是实测的。更好的 GPU 理论峰值更高。低效来自通信、显存带宽和空闲时间，后面会讲。

2. 显存

训练时要存：权重；反向传播时的梯度；优化器状态，Adam 为每个参数记录一阶矩和二阶矩两个标量，1000 亿参数的模型就要多存 2000 亿个数；激活，反向传播计算梯度时要用前向时保存的激活，后面会看到它们占用极大。每一样都是有形状和精度的张量。

一种常见的实现是：模型参数用 BF16 做前向；另存一份更高精度的模型副本和梯度，因为累加数值时高精度能避免下溢或上溢；优化器状态也用高精度。BF16 每个数 2 字节，FP32 每个数 4 字节，于是训练一步的峰值显存大致为：

$$\text{peak\_memory} = \text{model}_{\text{bf16}} + \text{model}_{\text{fp32}} + \text{grads}_{\text{fp32}} + \text{optim\_states} + \text{activations}$$

其中 BF16 模型 $2N$ 字节，FP32 模型和梯度各 $4N$ 字节，FP32 优化器状态 $(4+4)N$ 字节（Adam 的动量和方差），$N$ 为参数量。

实测的显存剖析图：一开始还没有优化器状态（粉色），橙色是反向传播时的梯度，紫色是激活，参数只占总显存的一小条，深绿是未知部分；优化步之后梯度缓冲被清空。要避免内存不足，就得看峰值。

学生问硬件（NVIDIA 之外各公司自研的芯片）怎样影响这些。Sean 说这些东西无论什么硬件都得存，所以这种图与硬件无关；硬件影响的是理论峰值，比如某种芯片做同样的矩阵乘法更高效；再细看显存分配到哪类存储，GPU 内部有存储层级，不同 GPU 的快速存储不同，两讲之后会讲。

按某个固定批大小和序列长度，看各种模型大小需要多少显存：H100 有 80 GB，而 70B 模型什么都不做的话需要约 1400 GB。看起来完蛋了，下面看几种减轻显存压力的技术。

3. 批大小

批太小，更新快但噪声大，梯度基于很少的样本；批大，梯度是更多样本的平均，近似更好，在给定数据集上需要的步数更少。如果能利用 GPU 的并行性，增大批大小就能每秒处理更多 token。批大小有几个部分：批内 token 数 $bs_t = bs\cdot seq$，即序列数乘序列长度，比如序列长 1000、批 8 个序列，就是 8000 个 token。预训练里 $bs_t$ 通常在数百万，大约 400 万到 6000 万 token。批太大会因为激活太多而内存不足。

4. 激活的显存

Transformer 激活的显存大致为：

$$m_{\text{act}} = L\cdot seq\cdot bs\cdot h\cdot\left(34 + \frac{5\cdot n_{\text{heads}}\cdot seq}{h}\right)$$

$L$ 是层数，$h$ 是隐藏维度（课上学生问 $h$ 是什么，Sean 一时也记不清，确认为常用的隐藏维度）。它与批大小呈线性关系，与序列长度呈平方关系，因为注意力要关注序列的各个部分。实测也是如此，序列一长，激活显存猛增。要降低它，可以从公式里任何一项入手，下面是两种策略。

5. 激活重算

也叫激活检查点（activation checkpointing）。前向时不保存所有激活，只保存部分层的激活，称为检查点；其余丢弃，反向时需要哪层的激活，就从最近的检查点开始重新做一遍前向算出来。这减少了显存，但增加了计算，因为真的要重做这些计算。这几乎是最基本的权衡：省显存就要在别处多花，比如计算。实际上可能明显变慢，但激活的显存大得离谱，有时不这样做模型根本放不进设备。用了重算之后，激活（紫色）大幅缩小，这么大的模型、这么长的序列也能在较小的 GPU 上训练。

6. 梯度累积

很容易实现，课上的演示笔记本里就常用。把一个批切成若干微批（micro-batch），比如批大小 8、微批大小 2，就是 4 个微批。依次对每个微批做前向和反向，把梯度累加到一个缓冲区，最后除以微批数取平均。于是有全局批大小：

$$bs = gbs = mbs\cdot\text{grad\_acc}$$

上例中 $mbs = 2$，$\text{grad\_acc} = 4$，全局批为 8。它相当于人为地增大批大小，得到的梯度和用一个大得多的批一样，显存却不变。权衡是什么？学生想到平均会受离群值影响，Sean 说他要的答案是计算：微批是顺序处理的，每个都要完整地前向反向一遍，又慢又费计算。后面的数据并行就是把它们并行做、最后再平均。

单卡小结：计算看 FLOPS 和 MFU；显存由参数、梯度、优化器状态和激活组成；激活重算和梯度累积都是用计算换显存；省下的显存可以用来增大批或增大模型。只有一块容量有限的 GPU 时，往往必须这样做才能训练。

三、数据并行

多卡时有一组策略可选。这一讲讲数据并行、张量并行、流水线并行和分片（ZeRO）；下一讲讲混合专家模型的专家并行，讲长上下文时还有序列并行或上下文并行。

数据并行的思路和梯度累积几乎一样，只是并行做：在每块 GPU 上复制一份模型，各自对不同的微批并行做前向和反向，再在 GPU 之间平均梯度，并确保每块 GPU 都更新自己的模型副本。比顺序的梯度累积快得多。

1. 朴素版本与通信原语

等所有反向传播都结束，再对所有 GPU 触发一次 all-reduce。实现要靠通信原语，也就是在多个进程间发送和汇总信息的基本操作。设备（GPU 或进程）通常称为 rank。

  • send / receive：一个设备把数据发给另一个，后者要实现接收。
  • reduce：对一列设备上的数据应用某个归约操作（比如加法），两两合并，最后得到一个值。
  • all-reduce：归约结果发给每个设备。数据并行正需要它：把各设备的梯度加起来除以设备数，并且每个设备都要拿到，好各自更新模型。
  • gather / all-gather：把各设备的数据拼在一起，all-gather 是每个设备都拿到拼接结果。
  • broadcast：把一个设备的数据发给所有设备。

可以自己从头实现，但通常用已经实现了这些原语的库，再写分布式训练代码；如今语言模型的分布式训练也已有现成的库。课堂代码参照 PyTorch 的文档，在笔记本上用多个进程当作 rank（原则上换成 CUDA 就能在多 GPU 服务器上跑，但没测过）。send 例子：rank 0 发给 rank 1，其余什么都不做；world size（rank 的数量）为 4 时，结果是 1、1、0、0。all-reduce 例子：每个设备持有 1，归约操作是求和，world size 为 4，每个设备最后都得到 4。PyTorch 文档里还有用 all-reduce 实现分布式 SGD 的例子，all-reduce 后除以 world size，就是平均。

2. 重叠与分桶

可以做得更好：反向传播是从后往前进行的，某一层的梯度一算完就立刻对它做 all-reduce，算第 2 层、all-reduce 第 2 层，算第 1 层、all-reduce 第 1 层……通信和计算重叠，省下时间。再推广一下，不按单层，而是把梯度分组成桶（bucket），一个桶可以是一层或几层，对同一个桶里的所有梯度发起一次 all-reduce。书里配套的分布式训练库就实现了这些。

3. 批大小的完整定义

$$\text{global batch size} = mbs\cdot\text{grad\_acc}\cdot dp$$

$dp$ 是并行实例数。比如 $mbs = 2$、$\text{grad\_acc} = 2$、$dp = 4$，全局批为 16。

一个更现实的例子，展示设备数和序列长度这些约束怎样决定参数：目标是每批 400 万 token（预训练范围的下限）；序列长 4000，于是需要约 1000 个序列，取 2 的幂 1024；假设一块 GPU 在显存限制下只放得下 2 个序列，那么 $mbs = 2$；只有 128 块 GPU，$dp = 128$，得到 $2\times 128 = 256$；剩下的用梯度累积补足，$\text{grad\_acc} = 4$，$256\times 4 = 1024$。课上留了个自测：如果有 512 块 GPU 呢？

4. 扩展性

GPU 越多，协调越多：all-reduce、网络通信、掉队的慢节点。随着数据并行度增加，每块 GPU 的吞吐（每秒 token 数）下降，扩展并不完美，主要原因是通信开销。但这只是单卡吞吐，乘以 256 后总吞吐仍远高于设备少的时候。只要微批大小不变，每块 GPU 的显存使用保持不变，其他策略不一定如此。

学生问有没有芯片能缓解 GPU 越多越难协调的问题。Sean 说没有很好的答案。一个办法是提高互联链路的质量：比如一台机器有 8 块 GPU，它们是独立设备，但可以加快它们之间的通信；机器之间也一样，高端集群在这方面好得多。另一个学生问软件和硬件哪个更重要：两者互补，分桶这样巧妙的算法能提速，给定算法也可以再加速运行它的硬件。还有学生提到有公司借鉴神经科学、试图用替代反向传播的方法并从硬件上实现。Sean 说在硬件上专门实现某个算法，以后就难改算法；如果确信算法不会变，确实能获得很大收益；替代反向传播是训练算法本身的巨大转变，要考虑会不会因此损失性能。

数据并行的局限：学生先说一个节点崩溃就浪费整个集群；Sean 提示考虑 6000 亿参数的模型，答案是模型仍然放不进单卡，因为数据并行在每个设备上都复制了整个模型。70B 模型在 80 GB 的 GPU 上连参数都放不下。所以接下来的策略是把模型切开、分到不同设备上：张量并行、流水线并行，以及分片（DeepSpeed ZeRO 或 PyTorch FSDP）。

四、张量并行

利用矩阵乘法的结构，把计算分布到多块 GPU 上。对 $XW = Y$ 有两种切法：

  • 按列：把 $W$ 竖着切成几列块，每块 GPU 负责一块，分别与 $X$ 相乘，再用 all-gather 拼起来，等价于原来的矩阵乘法。
  • 按行：把 $W$ 横着切成几行块，同时把输入 $X$ 按列切开，各自相乘得到两个部分结果，相加（all-reduce）得到最终矩阵。

实际中权重矩阵不止两列，可以设定切分的粒度。和数据并行不同，这里要深入模型内部，把矩阵乘法拆开送到不同 GPU，所以对具体架构要想好怎样切每一层的权重。NVIDIA 论文（Megatron）里的前馈层是先按列并行、再按行并行，好处是中间不需要 all-reduce 或 gather：按列并行的部分前向是恒等、反向做 all-reduce；按行并行的部分前向做 all-reduce、反向是恒等。根据使用的通信原语，某些原语序列比其他选择更高效。注意力层的做法不同：每块 GPU 负责一部分注意力头。

好处是任何一块 GPU 上都没有全部权重，每卡所需显存降低。张量并行度从 1 到 8 再到 16，原来毫无希望的 70B 模型现在能以 4000 的序列长度训练；再配合激活检查点，可以进一步降低显存，虽然会慢一些。代价是通信，每层都有 all-gather 或 all-reduce，串起来就是开销。通信分节点内和节点间，张量并行每层都要通信，跨节点的连接尤其慢，节点数一多就特别贵，所以通常在节点内做。

五、流水线并行

把层分到多块 GPU 上，比如第 1 到 4 层在 GPU 1，第 5 到 8 层在 GPU 2。计算是顺序的：GPU 1 做完前几层，把激活传给 GPU 2，期间 GPU 2 闲着；前向走完再反向，同样一段段往回传。图上大片灰色是 GPU 空闲的时间，叫气泡（bubble），是流水线并行带来的低效。关键挑战是减少气泡损失的时间。

巧妙的做法：把批切成微批（图中的数字现在是微批编号，不是层号），一前一后（one-forward-one-backward，1F1B），某个微批的前向一走完，就尽快开始它的反向，这样本来空闲的 GPU 可以去做这个微批的反向。Sean 第一次看到也很惊讶，竟然能把气泡缩小这么多；书里还提到在此之上更巧妙的算法。微批数少时因气泡而低效，微批数多时扩展得更好。

六、显存优化：ZeRO

各种微调库里都能见到。标准数据并行中，每块 GPU 都复制模型参数、梯度和优化器状态。零冗余优化器（Zero Redundancy Optimizer，ZeRO）把它们切分到各 GPU 上，有三级：

  • ZeRO-1：只分片优化器状态，每块 GPU 只存一部分参数的优化器状态，最后通过通信更新完整模型。
  • ZeRO-2：再分片梯度。
  • ZeRO-3：再分片参数。

不分片时显存很高、通信低；分片越多，显存越低，通信越高（all-gather）。核心是参数按需加载。例子：1B 参数的模型、4 块 GPU，每块存 250M 参数；到第 $\ell$ 层时，GPU 用 all-gather 取来第 $\ell$ 层的参数，算出激活，然后释放取来的参数，继续下一层。它与张量并行、流水线并行不同，只分片显存，不分片计算。ZeRO-3 通信开销极大、非常慢，但能在一块或少数几块 GPU 上放下极大的模型，是显存和通信之间的权衡。

七、选择与组合策略

策略核心思路权衡适用场景
数据并行（DP）在批维度上并行冗余；模型必须放得进单卡放得进单卡的标准模型
张量并行（TP）在隐藏维度上并行粒度细，通信开销高大的层（如 MLP），在节点内并行
流水线并行（PP）在模型层上并行流水线气泡很深的大模型，跨节点并行
ZeRO在 DP 中分片模型、优化器、梯度通信开销高（all-gather）单卡放不下的大模型

实际中通常组合使用：比如把设备分成若干组，组间做数据并行，组内做张量或流水线并行。开头那张图里每个点就是一种 DP、TP、PP 等的组合，其中某种是最优的。选择的顺序：先让模型放进显存，再满足目标全局批大小，最后优化训练吞吐。书里的实验（全局批 100 万 token，序列长 4096，1 到 64 个 8×H100 节点）显示，最佳配置随模型大小和节点数而变。要点是：手里有一组策略，针对给定的模型大小和节点数，找出最好地利用算力的那个。可以参考的库有 PyTorch 的 torchtitan 和 NVIDIA 的 Megatron-LM。

九、小结

规模化训练要在显存、计算效率和通信开销之间权衡，同样的模型换个并行配置，吞吐可以差几十倍。单卡上，计算量约为 6 倍参数量乘 token 数，用 MFU 衡量效率；显存由 BF16 与 FP32 两份权重、梯度、Adam 的两份状态和激活组成，激活随序列长度平方增长；激活重算和梯度累积用计算换显存。多卡上，数据并行在每卡复制模型、用 all-reduce 平均梯度，可以让通信与计算重叠并分桶，全局批大小等于微批乘累积步数乘并行度；模型放不下时，张量并行按行或列切开矩阵乘法（通信频繁，适合节点内），流水线并行按层切分（用微批和 1F1B 缩小气泡，适合跨节点），ZeRO 把优化器状态、梯度和参数分片、按需加载。实际训练把这些组合起来，按模型大小和节点数找最佳配置。
