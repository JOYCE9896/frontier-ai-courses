第一讲：课程概览，AI 系统与 Agent 系统

这门课学什么、怎么考核，AI 系统和传统计算机系统有哪些不同，Agent 是什么，为什么 Agent 是一个系统问题，以及这门课真正要优化的目标

主讲：Juncheng Yang（Harvard SEAS）
资料来源：课件（2026 年 9 月 2 日，Harvard 课程网站公开；课程不录像，本文依据课件整理，讲者口头补充的内容这里没有）

一、讲者和这门课的定位

Juncheng Yang 是 Harvard 工程与应用科学学院（SEAS）的助理教授，2024 年在 CMU 拿到博士学位，之前在 AWS、Snowflake、Cloudflare、Twitter 工作或实习过。他领导的组叫 MaDSys（Measurement and Design of Computer Systems），研究方向是存储系统、缓存，以及最近的 Agent 服务系统、上下文管理和 LLM 推理优化。组的口号是"别人找答案，我们找问题"：先测量真实系统，再设计和运营真实系统。

CS2680 是一门研究生层次的计算机系统课，2026 年秋季第一次开。课件对背景的期望是至少上过一门研究生系统课（操作系统、网络、数据库或体系结构中的一门），并有真实系统的经验。课程网站还写了先修 CS61（Harvard 的本科系统编程课），并默认会 Python 和 PyTorch。

课的名字里有两半："Agent" 和 "系统优化"。前几讲是基础：LLM 和 Agent 入门、怎样用 Claude Code、怎样设计和优化一个编程 Agent。占大部分课时的是后一半，即为 LLM 和 Agent 服务的系统：GPU 编程与内核、批处理和调度、显存管理、负载均衡与路由、KV 缓存与前缀缓存，以及 Agent 服务系统的其他优化。

二、五个作业和一个项目

五个作业是同一个系统一步一步拆开、一步一步接管的过程，课程把它们统称 Mads（Modern Agent Design and Systems 的缩写，也呼应 MaDSys 组名）。

  1. 给 Claude Code 做一个网页界面。目的是先当用户，体会编程 Agent 的效果，并看清一个 Agent 会话从开始到结束经历了什么。
  2. 自己写一个简单的编程 Agent。要解决一组简单问题，还要给作业 3 的排行榜出新题。
  3. 优化自己的编程 Agent。方向开放：上下文、记忆、测试时扩展、路由、子 Agent、工具调用；指标是准确率、成本和延迟。
  4. 服务自己的 Agent。从商业 API 换成自己部署的小模型，把 Agent 和推理引擎一起调。课件说这是最难的一个作业，任务也更难。
  5. 优化整个栈。方向同样开放：量化、路由、微调、引擎和 Agent 的协同设计，按排行榜计分。

期末项目是个人项目，可以用 AI 辅助，两个方向二选一：找一个缺口，做一个自己真的会用的工具；或者做一个研究项目，需要先和助教谈。期末有海报和现场演示，评分看代码、报告和同学互评。作业的具体内容见本站的 作业与项目 一页。

课件把话说得很直：在意 GPA 就别选这门课，每周预计要花 10 个小时以上；A 和 A- 都很难拿。课上时间有限，很多学习发生在课后，课程只给方向和指引，重点是教你"学会怎么学"。

分数构成在课件和网站上不完全一致。课件写的是作业 70%（1、2、4 各 10%，3、5 各 20%），项目 16%，展示 10%，参与 4%，另有最多 10% 的加分（课程反馈和"AI 解决不了的问题"）。课程网站后来的版本是作业 1、2、5 各 10%，作业 3、4 各 20%，项目 20%，课堂参与 10%，没有考试。以网站为准。

三、课程规则

鼓励使用 AI，但交作业时必须披露：哪些用法有效、哪些无效，并上传 AI 会话日志。AI 生成的代码要自己理解，交上去的每一行代码都由自己负责。

课程要求现场出勤，不录像。可以带笔记本电脑，但开着电脑的同学请坐后排。客座讲座前一周开放和嘉宾见面的报名。

计算资源有四类：Claude Code 许可；课程自己的模型 API（api.cs2680.com）；课程的 HPC 集群，用 SLURM 排队，显卡是 RTX 6000 PRO Blackwell，只能用于课程作业；AWS 账号，用完要关机。原计划容量 40 人，开课时已经扩到 80 人，但算力没有按比例增加，课件提醒作业截止那天可能抢不到 GPU。另外这是第一次开课，课表和评分方式都可能调整。

四、几个摸底问题

讲者先用几个问题了解学生背景：上过几门系统课（操作系统、分布式系统、数据库、网络、体系结构）；熟悉哪些话题，包括 Transformer 架构、TP/PP/DP/EP 几种并行方式、迭代级调度和 PagedAttention、线性注意力、GPU 编程、Linux 内核；以及平时怎样用 AI。用 AI 的方式分三档：聊天；用编程 Agent（含 MCP、Skills、插件、子 Agent、并行 Agent）；自己定制 Agent。

课件还给出了一个"Agent 编程等级"，从 0 到 5：

  • 0 级，不用 AI，代码全手写。
  • 1 级，辅助：AI 做自动补全。
  • 2 级，有监督：AI 写函数，人逐个审。
  • 3 级，限定范围：把一个任务整个交出去，人审代码。
  • 4 级，目标驱动：AI 写全部代码，靠测试来验证。
  • 5 级，并行 Agent：多个子 Agent 分工完成。

这个分级后面两讲会反复出现：第二讲讲怎样用好一个 Agent，第三讲讲怎样同时指挥多个 Agent。

五、什么是 AI 系统

"AI 系统"是个很宽的词，这门课只关心其中一类：大语言模型（LLM）系统。

做 AI 或机器学习的人问的问题是"该用哪个模型""模型该怎么设计"。他们会挑一个模型，写一段 Python 脚本把任务做出来，优化的是准确率和能力。做 AI 系统的人问的是"怎样大规模地训练和服务这个模型"。他们要优化四件事：GPU 利用率尽量高（性能），资源浪费尽量少（效率），停机时间尽量短（可靠性），碳排放尽量低（可持续性）。为此要处理一大堆部件：调度与编排、状态管理、通信、缓存、容错、安全、可观测性。

为什么要关心 AI 系统？课件的说法是，模型的能力要在系统这一层才变成产品，而这一层往往比模型本身更难做。它已经是关键的数字基础设施；懂系统能帮你理解模型为什么这样设计，也能帮你设计更好的产品；工作机会也多。

六、AI 系统和传统系统哪里不一样

计算：异构，分阶段，时间难预测

一次 LLM 推理里，CPU 和 GPU 分工不同。CPU 负责分词（把文字切成 token）、启动 GPU 内核、搬运数据、执行工具调用；GPU 负责矩阵乘法。一个集群里还常混着几代不同的 GPU，甚至别的加速器。

推理分两个阶段，瓶颈完全不同。第一阶段叫 prefill（预填充）：把用户输入的整段提示一次性送进模型，算出每个 token 的中间结果。这一步是大批量矩阵乘法，受限于算力，属于计算密集型。第二阶段叫 decode（解码）：模型一次只生成一个 token，每生成一个都要把整套模型权重从显存读一遍，计算量很小，读数据的时间占大头，所以受限于显存带宽。同一个部署，在不同时刻会撞上不同的瓶颈：算力、带宽，或者显存容量。

执行时间也很难预测。一个请求要跑多久取决于模型最后输出多少 token，这在开始时不知道。传统 Web 请求的处理时间大致可估，LLM 请求做不到，调度因此变难。

计算结果不确定

同样的输入跑两次，LLM 的输出可能不一样，哪怕温度设为 0。根源在浮点数。计算机里的浮点加法每做一次都要舍入，所以加法不满足结合律：$(a+b)+c$ 和 $a+(b+c)$ 的结果可能差在最后几位。乘法对加法的分配律 $a(b+c)=ab+ac$ 也不严格成立。甚至"相等"都不传递：在允许误差的比较下，$a$ 约等于 $b$、$b$ 约等于 $c$，推不出 $a$ 约等于 $c$。

这些微小差别会被放大。矩阵乘法里第七位小数的一点变化，可能让下一个 token 从 A 变成 B，之后整段输出都走上另一条路，课件称之为蝴蝶效应。差别的来源有三层：运行时（GPU 上线程束和线程块的调度顺序、内存访问顺序、异步流、批大小）；软件（是否用融合乘加指令、自动调优选了哪种内核、次正规数的处理）；硬件（普通 CUDA 核和张量核心算法不同，Hopper 的 FP8 和 Blackwell 的微缩放分块格式也不同）。批大小这一条最容易被忽略：同一个请求和不同数量的其他请求拼在一起算，内核的分块方式可能变，结果就可能变。

课件的结论是：在 AI 系统里，近似计算是可以接受的。

内存、存储和通信：状态巨大

模型权重从几 GB 到几 TB。推理时还要保存 KV 缓存：模型处理过的每个 token 都会在每一层留下一组"键"和"值"向量，后面生成新 token 时要反复用到，所以存起来不重算。每个 token 的 KV 缓存有几十到几百 KB，一段十万 token 的对话就是几 GB 到几十 GB。如果多个请求开头相同（比如同一段系统提示），它们的 KV 缓存可以共享，这叫前缀缓存。在这样大的状态面前，瓶颈往往是数据搬运而不是计算。

一张 GPU 放不下的模型要拆到多张 GPU 上，有流水线并行、张量并行、专家并行、上下文并行等方式（后面的课会讲）。拆开之后 GPU 之间要频繁通信，用 NCCL、UCCL 这类集合通信库；连接方式有机内的 NVLink 和机间的以太网或 InfiniBand；为了减少开销，还会用 RDMA 绕过 CPU 和操作系统内核直接读写对方内存。

模型和负载变化很快

注意力机制本身几年里换了好几代：标准多头注意力（MHA）、分组查询注意力（GQA）、多头潜在注意力（MLA）、原生稀疏注意力（NSA）、线性注意力。负载也在变：多轮聊天讲究交互和低延迟；解题类任务要长时间推理、输出很长；RAG 先检索文档再回答，上下文很长；Agent 上下文长，前缀缓存至关重要，还需要路由和负载均衡。模型要适配硬件，硬件也在反过来为模型架构设计。

可靠性、功耗和能源

课件给的数字是 GPU 年故障率约 9%，平均无故障时间约 5 万小时。在一个 1.6 万张 GPU 的集群里，大约每 3 小时就坏一张。功耗上，一颗 CPU 100 到 300 瓦，一张 GPU 700 到 1000 瓦，一台服务器装 4 到 8 张，整机功耗从过去的 800 瓦涨到 6000 瓦左右，大约 8 倍。大量 GPU 同时开始或停止计算时，电网负载会剧烈波动，怎样避免这种波动也是个问题。

七、什么是 AI Agent

课件的定义：AI Agent 是一个自主的软件系统，用 AI 模型围绕一个目标进行推理，使用外部工具，执行多步动作，直到任务完成。它通常经历五步：规划（把任务拆成子步骤）；行动（调用外部工具，比如 API、数据库）；观察（理解工具返回的结果）；调整（根据新信息修改计划）；交付（返回最终结果）。图上 Agent 由 LLM、推理与规划、记忆三部分组成，和环境之间是"行动出去、观察回来"的循环。

附加阅读里还对比了 Agent、助手和机器人（bot）。Agent 主动、以目标为导向，能独立决定并执行复杂的多步动作；助手是被动的，响应用户的请求，可以建议动作，但由用户决定；机器人按预先写好的规则响应触发或命令，几乎不学习。三者的区别集中在自主性、任务复杂度和学习能力上（这一页引自 Google Cloud 的介绍文章）。

为什么需要 Agent

课件引用了 Karpathy 在《Software is changing (again)》演讲里的说法：LLM 是一种奇怪的计算机，同时超人又无能。它在回忆海量事实、语言、模式匹配、写代码、跨领域工作上超过人类；却在持久记忆、可靠理解上下文、避免幻觉、知道自己不知道什么、抵御恶意输入上出奇地弱。Agent 的外围部件（记忆、工具、检查）就是用来补这些短板的。

Agent 是一种新的计算机

课件做了一组对应：LLM 对应 CPU，上下文窗口对应内存，工具对应外设，Agent Harness（包在模型外面、负责循环调用模型和工具的那层程序）对应操作系统，Agent 本身对应应用程序。它的意思是，LLM 不只是一颗更聪明的 CPU，而是一种新的可编程计算机，编程方式和出错方式都完全不同。

八、为什么 Agent 是一个系统问题

传统的 LLM 服务是一问一答：请求进来，推理一次，返回结果。Agent 的一次任务是一长串步骤：推理、调工具、再推理、再调工具、检索、再推理……关键路径横跨 GPU、CPU、存储、网络和外部服务。这带来一系列传统服务没有的麻烦：步骤之间有依赖，后一步要等前一步的结果；每一步耗时差别很大；经常要阻塞等待工具返回；状态（上下文）越滚越大；可以并发或投机执行；轨迹上任何一处都可能出错。

Agent 系统的分层

课件画了一张从上到下的栈：最上面是应用和用户；下面是 Agent/Harness 层，负责规划、上下文、记忆、工具、子 Agent；再下面是模型；然后是服务系统，负责批处理、调度、路由、缓存；再下面是运行时和内核（CUDA、Triton、集合通信）；最底层是硬件（GPU、CPU、内存、网络、存储）。旁边还有外部环境，即工具（网页、文件、API，甚至人）。这门课主张三层协同设计：Agent、服务系统、硬件。

到底在优化什么

课件的判断是：对 Agent 来说，吞吐量是错误的优化目标。TTFT（首 token 延迟，从请求发出到第一个 token 出来的时间）、TPOT（每个输出 token 的平均耗时）、工具调用延迟、GPU 利用率这些指标有用，但不够。每秒生成的 token 更多，Agent 仍可能更慢、更贵，比如它因为模型更快而多绕了很多步。

真正的目标写成一个约束优化：在延迟、成本、资源、可靠性、安全这些约束下，最大化任务成功率。要看的指标是任务成功率或准确率、端到端延迟、每个任务用多少 token、每个成功任务花多少钱、每个成功任务耗多少能量。

$$\max\ \text{任务成功率}\quad \text{约束：延迟、成本、资源、可靠性、安全}$$

Agent 负载带来的新问题

Agent 负载的每个特点都对应一个系统问题，这也是整门课的路线图：

  • 轨迹很长，所以要做状态和上下文管理。
  • 前缀反复出现，所以要做前缀缓存。
  • 工具调用之间有依赖，所以调度要感知依赖。
  • 工具延迟差别大，所以要异步执行。
  • 多个 Agent 同时工作，所以要编排和通信。
  • 上下文巨大，所以要有内存层级和检索。
  • 推理会分叉，所以可以做投机执行。
  • 用到不同的模型，所以要做路由。
  • 动作对外部有副作用，所以要考虑安全和隔离。
  • 任务运行时间长，所以要做检查点和容错。

可观测性是头等问题

分布式系统里常用"追踪"（trace）记录一个请求经过了哪些服务。到了 Agent，追踪变成嵌套的轨迹：一个会话（session）包含多轮（turn），每轮有多个 Agent 步骤，每一步里有模型请求、工具调用、工具结果，有的步骤还会派生子 Agent，子 Agent 里又是同样的结构。课件的原话是：看不见的东西没法优化。作业 1 让你给 Claude Code 做界面，看的就是这棵树。

九、这门课要你回答的问题

课件列了九个问题，并说上完课应该能定量地回答它们：

  1. 为什么批处理能提高吞吐量，却会伤害 Agent 的延迟？
  2. Agent 什么时候该用更大的模型？
  3. KV 状态和前缀状态应该放在哪里？
  4. 来自同一个 Agent 的多个请求应该怎样调度？
  5. 工具调用能不能和推理重叠进行？
  6. 什么时候该派生子 Agent？
  7. 怎样在不同型号的 GPU 和不同模型之间做路由？
  8. 一个跑了 30 分钟的 Agent 中途出错，怎样恢复？
  9. 怎样优化"每个成功任务的花费"，而不是"每秒 token 数"？

课程不讲的内容也列得很清楚：训练（因为算力需求的大头在推理），包括数据流水线、检查点、预训练、微调、后训练和强化学习采样；集群管理；模型架构设计；以及推理相关的通信、功耗与能源、新硬件设计。想补训练方面的内容，可以读本站的 CS336。
