第五讲：Agent 设计（二）：多 Agent 架构、协调与通信

什么时候该拆成多个 Agent，八种多 Agent 架构，任务分解的维度、粒度和常见失败，通信的介质、通道和消息格式，多 Agent 继承的分布式系统难题，A2A 协议与 MCP 的区别，以及四条设计原则

主讲：Juncheng Yang
资料来源：课件（2026 年 9 月 23 日；课程不录像，本文依据课件整理）
课程推荐阅读：Anthropic 的 multi-agent research system、scaling agent systems、Cognition 的 Don't build multi-agents

一、从一个 Agent 到多个

这一讲讲多 Agent 设计的三个方面：架构、协调（主要是任务怎样分解）、通信。多 Agent 系统不是新东西，有几十年的研究历史，课程不展开历史，只讲和 LLM Agent 相关的部分。推荐阅读里特意放了一正一反两篇：Anthropic 讲他们怎样用多 Agent 做研究系统，Cognition 的文章标题就是"别做多 Agent"。

什么时候、为什么要拆

课件给了四个理由：专业化，不同的 Agent 用不同的模型、提示和工具；隔离，给不同的 Agent 不同的权限；并行，互相独立的子任务同时执行；上下文管理，不必让每个 Agent 都看到整条轨迹。

每种架构背后的三张图

  • 控制图：谁来协调？一个主管、一层层的上下级，还是没有协调者？运行中会不会换人（交接）？
  • 通信图：它们怎样交流？直接发消息、广播，还是通过共享的工作区？
  • 任务图：工作怎样分解？由一个规划者事先拆好，通过竞标分配，还是从局部规则中自然形成？

二、八种多 Agent 架构

1. 主管和工人（Supervisor-worker）

一个 Agent 负责规划、委派和整合，工人只看到自己的子任务。例子是主管下面有研究员、程序员、审查员。任务由主管事先拆分，控制权在一个主管手里，通信是星形，都经过主管。适合子任务互相独立、可以并行的情况。弱点是主管成为瓶颈：它要重读每一个结果，它的上下文增长最快。

2. 层级式（Hierarchical）

把主管和工人的结构递归地用下去，主管管理下级主管。例子是开发一个功能：功能经理下面有后端负责人和前端负责人，后端负责人下面是 API 和数据库，前端负责人下面是 UI 和端到端测试。每一层都再拆一次，通信是树形，只在父子之间。适合本身就能层层分解的任务，比如存储系统、查询引擎、测试。难点是在哪一层分解，以及每条边界上要传递多少上下文。

3. 流水线或有向无环图（Pipeline / DAG）

阶段固定，每个阶段之间有类型明确的约定。例子是处理发票：OCR 识别、提取字段、和采购单匹配、审批、记账。阶段在设计时就定好，顺序本身就是控制，通信只在相邻阶段之间。这是最容易调试的结构，错误能定位到某个阶段。弱点是不能回头：第四阶段没法要求第一阶段给一个更好的来源。课件的建议是：加一条重试的回边，比多加一个 Agent 更管用。

4. 黑板和共享内存（Blackboard）

Agent 通过共享状态协调，而不是直接发消息。共享的工作区可以是数据库、向量库、文件系统、Git 仓库或任务图。例子是几个 Agent 共用一个 Git 仓库（任务列表、提交、历史），分别做功能、重构和测试，第三讲的 C 编译器项目就是这样。任务从共享状态中产生，没有中央控制，通信是间接的。好处是 Agent 可以随时加入或离开而不用重新连线，共享状态是持久的，也能检查。难点是一致性、并发控制、来源追溯、版本管理和垃圾回收。

5. 委员会或辩论（Committee / debate）

几个 Agent 各自提出答案并讨论，再由一个评委或投票来裁决分歧。例子是作文评分：评分员 A 和 B 各自打分，评委做最终决定。同一个任务并行做多遍，评委决定，通信先在同伴之间、再到评委。能提高需要判断的任务的准确率。失败模式是"一致但不独立"：如果用的是同一个模型、同样的上下文，它们有同样的盲点，意见一致也不说明对。

6. 市场和拍卖（Market / auction）

任务公布出来，各 Agent 根据自己的能力、成本和延迟来竞标。参与的 Agent 是异构的，模型、工具、机器、价格和专长都不同。例子是 GPU 任务路由："谁能跑这个训练任务？"A100 节点报价 0.20 美元、预计 3 秒；T4 节点 0.05 美元、10 秒；H100 节点 0.40 美元、1 秒。规则是 5 秒内最便宜的中标，所以给了 A100。工作会落到能胜任的最便宜的 Agent 上，不需要中央规划者。弱点是报价由 Agent 自己报，一个 Agent 可以靠夸大能力中标。

7. 群体（Swarm）

没有固定的协调者，Agent 之间直接协商、交换发现。需要一整套协议：发现、寻址、同步、终止和信任。例子是仓库里的拣货机器人互相商量谁去拣哪个订单。没有协调者会成为瓶颈或宕机，同伴进进出出工作也能继续。弱点是通信复杂度是 $O(n^2)$（$n$ 个 Agent 两两之间都可能通信），冲突也很难解决，产品里很少用。

8. 动态拓扑（Dynamic topology）

任务运行过程中增加、删除 Agent 或者重新连线。例子是客服机器人：普通工单它自己处理；工单升级后，才加入账单 Agent 和日志 Agent。任务在变难时重新拆分，控制权随加入的 Agent 变化。好处是能力随难度扩展，简单工单依然便宜。弱点是每次运行的结构都不一样，失败很难复现。

真实系统是混合的

课件的例子是：一个主管下面有规划 Agent，规划 Agent 生成一张动态任务图，图里有程序员、研究员、测试员，他们共用一个 Git 仓库，最后由审查员把关，需要时重新规划。这里同时用了层级、共享内存和流水线。

类别架构核心思路适合弱点
集中式主管和工人一个规划者，多个工人可分离的子任务规划者成为瓶颈
层级式主管的主管递归拆分错误被放大
流水线 / DAG每一阶段喂给下一阶段顺序清楚的阶段错误向下传播
市场 / 拍卖Agent 竞标任务动态分配虚报
去中心化黑板共享工作区围绕一个共同产出物状态过时
委员会 / 辩论先各自回答，再调和需要判断的问题群体思维
群体直接对话，没有控制者局部协商$O(n^2)$ 条消息
混合动态拓扑边做边重新连线结构事先未知难调试

三、协调：任务分解

多 Agent 的基本形态是：一个复杂任务拆成几个子任务，分别完成，再合并结果。

按什么维度拆

  • 数据：每个 Agent 处理一部分文档或记录。
  • 专长：安全、性能、正确性、法律分析。
  • 阶段：计划、实现、测试、审查。
  • 假设：几个 Agent 分别调查相互竞争的解释。
  • 工具：网页、数据库、代码执行、内部文档。
  • 权限：Agent 在不同的管理域里行动。

维度可以叠加。例子是审查一个改了 200 个文件的 PR：先按数据（文件）拆，再按专长（安全、性能）拆。

写子任务时要说清的八件事

目标；输入和相关上下文；边界和排除项；可用的工具和权限；期望的输出格式；完成的判定标准；预算和截止时间；依赖关系。课件对比了两个子任务。差的是"调研存储系统"。好的是"找出 2026 年发表的存储相关论文；返回标题、日期、系统贡献、评估规模和一手来源链接；不包括数据库查询优化"。

粒度的权衡

任务拆得太大，并行度很低，工作仍然是串行的；拆得太小，调度和通信的开销占了大头。多 Agent 完成任务的总时间大约是：

$$T_{\text{multi}} \approx T_{\text{规划}} + T_{\text{关键路径}} + T_{\text{通信}} + T_{\text{合并}}$$

关键路径指所有子任务里必须一个接一个完成的那条最长链。只有当并行省下的串行工作超过规划、通信和整合的成本时，并行化才划算。例子是 20 个一行就能查完的小任务，打包成 4 个子任务，让开销小于收益。

静态和动态分解

  • 静态：执行前就知道怎么拆，可预测，容易评估。例：分别总结上传的五个 PDF。
  • 动态：Agent 根据发现创建新任务。例：发现一个失效链接，就派生一个查找任务。
  • 递归：工人自己也可以再委派。例：一个综述 Agent 为每个子领域派一个子 Agent。
  • 机会式：空闲的 Agent 认领新出现的任务。例：空闲 Agent 去拿下一份未标注的文档。

分解必须有派生数量上限、预算、深度限制和终止条件，否则委派会递归地爆炸。

常见的分解失败

  1. 重叠：两个 Agent 总结了同一篇论文。
  2. 缺口：一个查 2020 到 2023 年，一个查 2025 到 2026 年，漏掉了 2024 年。
  3. 隐藏依赖：定价需要先知道规模，但这一点到运行时才发现。
  4. 输出无法合并：一个返回自由文本，一个返回 JSON，合并失败。
  5. 丢失全局上下文：每一节都没问题，整份报告却前后矛盾。
  6. 掉队者：六个 Agent 20 秒内完成，一个要 4 分钟，整体要等最慢的那个。

四、通信

多 Agent 通信有四个维度：拓扑，谁能和谁说话（主管和工人，或者点对点，由架构决定）；介质，信息通过什么交换（消息、共享内存、文件、数据库）；格式和语义，消息怎样组织、怎样表达意图（委派、汇报、询问、交接、取消）；通道，信息怎样传递（点对点、广播、发布订阅、共享状态、请求响应）。

介质

  • 消息传递：Agent 通过队列或总线发送显式消息，比如程序员把结果发到编排者的收件箱。
  • 共享内存：一个进程内的状态对象，所有 Agent 都读写它，比如一份随工作完成而更新的共享任务列表。
  • 文件和产出物（包括数据库）：工作成果通过文件存储交接，比如研究员写好 notes.md，写作者再打开它。

通道

  • 点对点：规划者把任务说明交给程序员 Agent。
  • 广播：编排者通知所有 Agent 构建失败了。
  • 发布订阅：Agent 订阅"新工单"主题，有新工单时响应。
  • 共享黑板：Agent 读写同一个"发现"草稿区。
  • 请求响应：Agent 向检索 Agent 查询，等待文档返回。
  • 产出物传递：一个 Agent 写 report.md，下一个读它。

消息格式

自然语言灵活但有歧义；结构化消息容易校验，但表达力弱。实用的设计两者都用。课件的例子是一条 JSON 结果消息，字段包括任务编号、消息类型（结果）、状态（完成）、结论（"回归问题始于提交 X 之后"）、置信度 0.82、证据（某条日志、某个提交）、产出物路径，以及是否需要回复。

关键是让消息带上语义，把控制和内容分开。差的做法是把一切都塞进一个字符串。好的做法是消息有编号、任务编号、发送者、接收者、类型和内容载荷，类型从运行时认识的一组操作里选：委派、查询、汇报、交接、更新、取消、确认、错误、完成。这样运行时自己就能路由、重试和停止，不用去问 LLM"这条消息是什么意思"。内容用自然语言，协调用结构化协议。

维度选项经验法则
拓扑主管和工人、点对点、网状照着任务的依赖关系来
介质消息、共享内存、文件每条连接只用一种介质
通道点对点、广播、发布订阅、请求响应只有所有人都必须知道时才广播
格式自然语言加控制字段按字段路由，不按文字路由

每个选择都在延迟、上下文和可靠性之间取舍。

五、通信是一个困难的分布式系统问题

课件举了一个例子：Agent A 让 Agent B "购买 8 台 GPU 实例"，网络超时，没有回复。B 到底执行了没有？该重试还是放弃？语义应该是"最多一次"还是"至少一次"？"恰好一次"在这里做得到吗？可以在任务编号上加幂等键（让同一个请求重复到达时只执行一次）；要准备补偿或回滚的路径；如果真的重复购买了，谁来付钱？

分布式系统的经典难题，多 Agent 系统全部继承：

  • 部分故障：分不清一个 Agent 是慢还是已经死了。
  • 并发和非确定性：很多机器同时修改状态。
  • 副本之间的一致性：一致性、可用性、分区容忍和延迟之间要取舍。
  • 没有全局时钟：不同机器上的时钟对不上。
  • 网络不可靠：包会延迟、丢失、乱序、重复。
  • 调试和可观测性：请求很多，日志分散，时间戳还有偏差。

多 Agent 还带来额外的系统问题：调度（下一个谁跑、跑多久）；状态管理（检查点、记忆、来源、版本）；资源分配（模型、CPU 等共享资源）。根本原因是没有预先确定的请求流：系统事先不知道谁需要运行、运行多久、每个 Agent 要消耗多少资源。

再加上 LLM 是黑盒，就更难了。上下文方面：信息丢失（摘要漏掉了工人知道的东西）；上下文污染（重要的东西被埋没）；信息过时（X 已经变成 5，B 还在按 X=3 行事）；信念冲突（A 说安全，B 说有漏洞）。协调和通信方面：责任丢失（每个 Agent 都以为别人负责）；通信循环（A 问 B，B 问 C，C 又问 A）。可观测性方面：到底为什么失败？

六、A2A 协议

A2A（Agent2Agent）是 Agent 之间通信的协议。基本流程是：Agent A 发现 Agent B 的能力，发送消息、创建任务，B 返回进度更新，最后返回产出物。例子是"分析 X 公司是否应该把推理栈迁到 Y 型号 GPU 上"：研究 Agent 通过各个 Agent 的"名片"找到同伴，让财务 Agent 估算 GPU 成本，让搜索 Agent 找基准数据，让编程 Agent 跑这些基准。

Agent 名片

每个 A2A 服务器在固定地址 /.well-known/agent-card.json 发布一张机器可读的名片，里面有名字、描述、技能列表、支持的接口、能力（比如是否支持流式输出）和安全方案。调用者从中得知：这个 Agent 是谁，声称能做什么，在哪里、怎样调用，支持流式还是推送，要满足哪种认证。

三个抽象

  • 消息（Message）：客户端和 Agent 之间的一轮对话，比如"订一张去波士顿的机票"。
  • 任务（Task）：有编号和生命周期的有状态工作单元，比如 task-42 从"进行中"变为"已完成"。
  • 产出物（Artifact）：任务的输出，比如行程单 PDF 和订票数据。

一条消息启动一个任务，任务以产出物的形式返回结果。后续的追问属于同一个任务，比如"哪天？""10 月 3 日"。

任务生命周期

状态包括：已提交、进行中、需要输入、需要认证、已完成、失败、被拒绝、已取消。A2A 是有状态的任务协议，工作可以停下来等输入或认证，再继续。例子：订机票，进入"需要输入"状态问"哪天"，收到"10 月 3 日"后回到"进行中"。

任务可能跑几秒，也可能跑几小时，调用方选择怎样跟进：轮询，客户端反复查询直到完成，适合短任务；流式，持续推送实时更新，适合交互式输出；推送通知，完成时触发 webhook，适合几小时的任务。A2A 只标准化通信，不管编排：怎样委派、怎样拆分、什么时候停，仍由 Harness 决定。

MCP 和 A2A 的区别

MCP 是 Agent 和服务之间的边界：一次工具调用，一个结果。它标准化工具（可调用的、带类型的能力）、资源（Host 可以附加的可读数据）和提示（可复用的交互模板）；一个客户端可以连很多服务器；暴露什么由 Host 决定，不由模型决定。

两者可以叠加：一个通过 A2A 调用的远程 Agent，自己可能又调用二十个 MCP 服务器。

七、四条设计原则

  1. 真的需要多 Agent 吗？单个 Agent 往往就够了，多个 Agent 常常只是增加开销和复杂度。
  2. 决定拓扑：反映任务的依赖关系，尽量减少通信。
  3. 找出信息丢失点：把汇总节点当作细节会丢失的地方来对待。
  4. 找出故障隔离的边界：确保一处出错时整个系统不会卡死。

稠密的网状结构很少是好的默认选择。通信越多，上下文压力越大，有用的信息却不一定增加。
