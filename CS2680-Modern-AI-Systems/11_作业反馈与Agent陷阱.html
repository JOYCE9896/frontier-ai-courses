第十一讲：作业反馈与使用 Agent 的十个陷阱

作业 1 里学生对 Claude Code 的观察和期望，Claude Code 为什么突然偏爱 Bash，作业 4 排行榜的结果有多稳定，三次作业里 Claude Code 用法的变化，用得好的人花了多少时间，以及从全班日志里总结的十个陷阱和改法

主讲：Juncheng Yang
资料来源：课件（2026 年 11 月 2 日；课程不录像，本文依据课件整理，图表里的数字是从图上读出来的）
这一天的课分两段，前一段是本文的作业反馈，后一段接着第十讲讲 GPU 编程，见下一讲。

一、这一讲讲什么

这门课要求学生提交 Claude Code 的会话日志。到第十一讲，全班已经交了三个作业（作业 1 做 Agent 事件的网页查看器，作业 2 自己写 Agent 循环，作业 3 做 Harness 竞赛），课程组把这些日志汇总分析，讲了学生用 Agent 时哪里做得好、哪里出问题。课件里的统计按作业分开，记作 A1、A2、A3，每次都是同样的 58 名学生。

通知：当天有答疑时间；作业 5 有加分项；需要帮助就找助教和讲师。

二、作业 1 回顾：学生从 Claude Code 学到了什么

Agent 的事件流是异步的，很难还原

作业 1 要求把 Claude Code 运行时产生的事件流做成一个可视化页面。学生发现这件事比想象的难：任务结束的顺序和开始的顺序不同；后台运行的 Bash 命令可能来自不同的子 Agent；Agent 经常用 Bash 去读写文件，而不用专门的 Read 和 Edit 工具。要做出一个可信的查看器，必须去看真实的轨迹，把状态怎样转换建模出来。

需求含糊，结果没人检查

宽泛的提示词让 Agent 做出了没要的功能、过度的架构或错误的布局。给截图、给明确的尺寸位置、给可以测量的标准，效果更好。另一面是结果没有被检查：

  • 测试检查的是内部状态，不是用户看得见的行为。
  • 测"隐藏/显示"的测试只检查了 HTML 的 hidden 属性，而 CSS 让内容仍然显示在页面上，测试通过，功能是坏的。
  • Agent 报告"已验证"，实际一个测试都没跑，或者测试被挡住根本没运行。

建议：把需求写成能验证的条件，配上视觉示例；让 Agent 把有歧义的地方提出来；大改之前先审设计；验证结果自己看一遍。

重复劳动和拆分不当的委派

子 Agent 用在互相独立的审查、各自不同的实现任务上是有效的。问题出在：不同会话里 Agent 重复做同样的探索；跑了功能用不到的操作；几个子 Agent 反复读同一个小仓库，重复父 Agent 已经做过的事；一个 Agent 在改文件，另一个同时在测这些文件。一个例子是 6 个 Agent、委派深度 3 层的一次运行花了 10 多分钟、近 15 美元，之前一个类似任务不到 2 分钟、1 美元。

建议：用记忆避免重复探索；不确定的想法拆成小的实验委派出去试；每个 Agent 职责明确，改动互相隔离。

作业 1 的四条经验

  1. 尽早看真实的轨迹，定清楚目标。
  2. 定义具体的验收标准。
  3. 小步构建。
  4. 用截图迭代。

讲者的总结是：最大的转变是从"让 Agent 写代码"转向"规定 Agent 的工作怎样被验证、怎样才能信任"。

三、学生希望 Claude Code 做到什么

归纳起来是两句话：信息更透明但不杂乱；Agent 能自主干活，同时人有机会插手。具体有三类：

  • 可见、可控的委派：委派出去之后，仍然能掌握任务、依赖和上下文，看到中间的决定和发现、每个子任务的状态和验证情况；拓扑（几个 Agent、委派几层）和范围能在运行中动态调整，而不只是事先写死的配置。
  • 更多可见性和控制：随时看到进度和剩余工作；简短说明计划和当前的假设；在用户还来得及插手时解释决定；报告时说清楚到底验证了什么、做了哪些假设。上下文能有选择地编辑，删掉错误的假设；记忆更容易修改，清掉过时的理解。实时显示花了多少钱，并且有明确的预算控制。
  • 让人保有对代码的掌控：知道 Agent 为什么在看某个工具或文件；按文件看改动；更清晰的模块结构；能把界面上看到的变化对应到实现它的代码；以及一种交互式调试模式，出错时停下来，让学生先判断问题可能在哪个文件或函数。

四、为什么 Agent 总用 Bash 而不用专门的工具

作业 1 里学生普遍发现 Claude Code 用 Bash 跑 cat、sed 去读写文件，而不调用 Read、Edit。课程组查下来，这是 Anthropic 有意做的实验，正好赶上了这次作业：

  • 在 auto 和 bypass-permissions 两种权限模式的会话里，系统会插入一条提醒："Do your work through the Bash tool wherever it can accomplish the job … rather than using the dedicated Read, Edit, or Write tools"。
  • Bash 工具的说明里原来有一句 "Avoid using this tool to run cat, head, tail, sed, awk, or echo"，同时被删掉了。
  • 几乎所有会话里都没有 Grep 和 Glob 工具，Agent 试图调用时会收到 "No such tool available: Grep … search file contents with grep via the Bash tool instead"，所以所有搜索都走 shell。

这个实验由一个功能开关（feature flag）控制，班上除了一个人以外都在实验组里；只对 Opus 5 和 Fable 模型生效，Sonnet 和 Haiku 不受影响。开关 8 月 12 日加上，作业 1 是 9 月 2 日到 22 日，有一位学生自己发现并测试了这一点。到 Opus 5.5，提示的语气放软了，改成"Bash 更简单时可以用它；精确替换、多行替换，或者 GNU 和 BSD/macOS 上参数不同的 sed/awk 这类容易出错的情况，优先用 Edit 或 Write"。

课件还画了 Claude Code 的判断流程，分三步：

  1. 这个会话是否属于"Bash 优先"组：每个会话判断一次，子 Agent 继承。Opus 5.5 和 Fable 5.1 总是；Opus 5 看功能开关；Sonnet 5 和 Haiku 不是。
  2. 要不要加提醒：每次请求之前判断，以下条件同时满足才加：权限模式是 auto 或 bypass；工具里同时有 Bash 和 Edit 或 Write；会话在 Bash 优先组；之前还没加过。
  3. 用哪段文字：按顺序取第一个匹配的：账户级设置；Opus 5.5 用宽松版；另一个功能开关；否则用严格版。

这些开关缓存在 ~/.claude.json 里，Anthropic 不发新版本就能改。

提示词的影响有多大

课件的图给出了量化结果。读写文件时用 Bash 的比例，没有提醒和上下文里有严格版提醒相比：

操作没有提醒有严格提醒
读文件8%41%

Opus 5 主 Agent 的读和编辑10%78%

另一张图看的是会话中途插入提醒的 22 个会话：插入之前用 Bash 的比例中位数是 3%，插入之后是 87%。系统提示里一句话，就能让 Agent 的工具选择整体改变。

五、作业 4 排行榜：同一份提交跑十次

作业 4 的排行榜看两个指标：26 个任务里解决了几个，以及端到端时间（上限 4 小时）。课程组把排名前 18 的提交（来自 12 名学生）各跑了 10 次，共 180 次评测。结论有三条：

  • 结果有波动，波动多大取决于 Harness。
  • 同一份提交的多次结果聚在一起，不同提交之间分得开。
  • 波动不会把一个好的 Harness 掩盖掉。好的设计跑几次都好。

这和后面陷阱 P8 有关：单次的分数有噪声，但多跑几次就能看出真实差别。

  • 提示长度中位数从 98 个字符降到 87、65，下降 34%。

  • 到 A3，72% 的提示在 auto 模式下发出，18% 在 bypass 模式下发出。

作业越来越难，学生却越来越少告诉 Agent 怎样判断完成。课件的提醒是：要给 Agent 一个验证自己工作的办法。按提示的内容分，A3 里约一半的提示点名了要改的目标，说明完成标准的只占 15%，含糊的提示在 A3 涨到四分之一左右。

子 Agent 和工作流用得越来越多

  • 让 Agent 启动过子 Agent 的学生：36%、47%、74%。
  • 运行过工作流（workflow）的学生：2.9%、10%、35%。

七、用得好不等于用得多

课件把作业的排行榜名次和投入时间画在一起。排第 1 层（帕累托前沿）的学生，Claude Code 的活跃时长并不比其他人长，很多人花的时间更多，名次反而靠后。学生本人投入的时间也一样：拿到第 1 层不到 1 小时的个人时间就够了。

把 Claude 的工作时间和学生的时间放在一起看，全班 Claude 工作时间的中位数是 4.3 小时，学生自己时间的中位数是 13.8 小时，多数人花在盯着 Agent 上的时间比 Agent 干活的时间还长。讲者的要求是：让 Agent 为你工作，而不要反过来；由你掌控，决定 Agent 该做什么。

八、使用 Agent 的十个陷阱

最大的问题是盲目信任 Agent。课件举了两个"Agent 做出的不是我们想要的"例子：

  • 要求"让测试通过"：Agent 把失败的测试删了。没有测试失败，bug 还在。
  • 要求"降低排行榜上的花费"：Agent 跳过了所有任务。花费 0 美元，完成的工作也是 0。

接下来按十个陷阱逐一给出数据和改法。

P1：盲目相信 Agent 的说法

Agent 说改好了、测试过了、结论成立，学生没检查就往下走。很多说法是错的：测试根本没跑，或者失败信息被管道过滤掉了。相信过 Agent 错误说法的学生是 20%、20%、33%；而提示里要求给测试或证据的只有 15%、27%、17%。

改法：先定义"完成"，要跑哪些测试、什么时候停；准备自己能验证的测试用例；自己读 diff，再手动检查一个用例；看完整的测试输出和退出状态，不要只看 tail 或 head 截出来的一段；也可以让另一个子 Agent 去核对结果和 diff。

P2：不清楚 Agent 到底做了什么

搞不清 Agent 做了什么的学生是 18%、37%、21%。30 分钟以上的长轮次从 41 次涨到 182、514 次。跑 30 分钟以上的学生里，起因是一句含糊要求的占 13%、50%、69%。

改法：分成可以审查的小步，每轮只做一个功能或一个实验，然后读 diff、提交；让 Agent 写更短、更好读的报告；维护一个 Agent 会更新的决策和历史文件（NOTES.md 或 CLAUDE.md）；中途检查进度、纠正方向，按 Esc 停下走错的一轮，或者直接输入更正。

P3：会话太长，压缩丢了上下文

上下文满了、被压缩过的学生是 16%、40%、69%；压缩次数（自动加手动）是 20、50、201 次。课件引了两句学生的话，一句是在一个持续 13 天、压缩过两次的会话里说的："i remember we tested 1 already, please pull those results before implementing"；另一句是"again respect the instructors feedback i shared earlier"，那段反馈是 5 个小时前贴进去的，压缩之后丢了。

改法：每个任务开新会话；计划、决定和状态写进文件（CLAUDE.md 或导入的 NOTES.md），新会话能接着做；大范围搜索和长日志交给子 Agent；在自然的停顿点自己运行 /compact，并说明要保留什么。

P4：一次叠加多个改动，没有对照实验

一次改很多东西或推倒重来的学生是 0%、5%、37%。例子：有人把四个"专家"功能一起加进第 9 版，成本涨了，解决数没涨。

改法：每次只改一处，和固定的基线比较，没用的先去掉再加下一个想法；每个实验一个 git 分支或 worktree，给提交的版本打标签；动手之前把假设写下来，让运行结果有机会证明它是错的。

P5：并行的会话互相干扰

有 15 分钟以上会话重叠的学生是 9%、22%、54%，最长重叠 1.7、15、21 小时。三个例子：A1 两个会话抢同一个 4000 端口；A2 一个旧批次覆盖了结果；A3 一次 git reset 弄坏了另一个运行的代码。

改法：每个会话一个 git worktree；每次运行和它的输出目录都起名字；计时测量单独进行，不和别的任务一起跑。

P6：Agent 执行破坏性命令

A2 里有 Agent 覆盖了 prompts.py，跑过的那版提示词就没有了。用 bypass 权限发出的提示占 8.6%、11%、16%；在执行前被拦下的工具调用（学生拒绝、deny 规则或 auto 模式拦截）有 167、233、484 次。

改法：有风险的步骤之前先提交；为 rm -rf、git reset --hard 和强制推送加 deny 规则；bypassPermissions 只在隔离的容器或虚拟机里用；让 Agent 在删除、重置或终止不是它自己创建的东西之前先确认。

P7：泄露密钥

暴露过密钥或密码的学生是 3%、23%、19%。A3 里有学生把提交用的用户名和密码直接打进提示，让 Agent 记下来以便自己不在时自动提交。按次数算，A1、A2、A3 里学生打进或贴进提示的分别是 1、10、6 次，Agent 把它打印出来的 1、6、6 次，留在已提交日志里的 1、2、15 次。

改法：密钥放在环境变量或 .env 文件里，让 git 和会话存档都不收录它；密钥不要进入 Agent 的环境，也不要贴进提示。

P8：把一次有噪声的结果当成真实效果

拿一次运行当证据的学生是 0%、30%、73%。A3 里同样的代码得分在 16 到 18 之间浮动，单次提交很难判断好坏。

改法：每个版本在同样的任务上多跑几次，比较分布，不只比一个分数；跑之前定好差多少才算数；每个版本一张结果表。

P9：发泄情绪，不给方向

课件摘了一些学生对 Agent 发火的原话，比如"clean this up immediately or ill be angry"、"CONITNUE DONT COME BACK TO ME UNLESS THEY ARE DONE … GOOOOOOO"、"what is happening oh my god its so bad"。这类提示里没有错误信息，也没有期望的结果，Agent 拿不到能用的信息。这样做的学生是 7%、5%、21%。

改法：修了两次还不对就停下来，要求 Agent 给出带证据的诊断，比如日志行或准确的报错；把准确的错误或截图贴进去，说清楚期望看到什么；分数一直低时，先问失败的运行把时间花在了哪里，再要新想法；用 /rewind 或 git 回到最后一个正常的状态，不要在坏掉的状态上一层层打补丁。

P10：平台问题或笔记本休眠

因为机器原因损失时间的学生是 12%、50%、65%。A3 有学生在笔记本上跑，42 GB 的任务镜像把硬盘塞满，评测基础设施跟着出错。

改法：第一次运行前读清楚对平台、硬盘、Docker 的要求，笔记本不够就一开始用 CloudLab 或 AWS；长时间的任务放在不会休眠的机器上，用 tmux 或 nohup 运行。

P2 不清楚做了什么小步走：读 diff，提交
P3 长会话丢上下文一个任务一个会话，笔记写进文件
P4 叠加改动每次改一处，对照基线

九、一个好的迭代循环

  1. 从一个简单的基线开始，不要一上来就用 pi 或 dsh 这类现成的复杂 Harness。
  2. 提出一个假设。
  3. 只改一处。
  4. 跑本地测试或排行榜测试。
  5. 至少重复一次。
  6. 验证成立就记录成一个版本。

原则是三条：自己掌控；一步一步来；验证之后再往下走，测试要严谨。

十、课程的反馈平台

课程组做了一个实验性的反馈网站 how-i-used-claude.cs2680.com（还在开发中），根据每个学生交的日志生成个人报告：和同学相比处于什么位置，自己的 Claude Code 用法统计，半个性化的建议，课程组在各次作业上的反馈，以及一张随每次作业变化的"使用 Agent 能力画像"。它想帮学生回答的问题是：作业里哪里出了问题、时间浪费在哪；提示是不是太含糊，是不是不该让 Agent 一口气完成整个项目；提示该不该写得更长、更细，有没有漏掉重要的东西；有没有更好的用法。讲者的说法是，AI 是每个人都必须掌握的工具。
