一、这一讲讲什么

第十讲讲的是 GPU 的硬件：为什么它是吞吐机器，算力、显存容量、带宽三个上限怎样决定性能。这一讲接着讲三件事：

  1. GPU 编程：代码怎样在 GPU 上跑，以及从高到低几种写 GPU 代码的方式。
  2. 效率和利用率：怎样判断一个推理服务有没有把 GPU 用好。
  3. 近年的内核优化：时间浪费在哪里，各种技术分别解决哪一种浪费。

讲者在开头说，这部分只为建立直觉，不深入细节。做作业 4（自己部署模型并优化推理）时会用到这里的很多概念。

二、GPU 编程

1. GPU 代码是异步执行的

一台 GPU 服务器分成两边。主机（host）是 CPU 加内存，运行 main()；设备（device）是 GPU 加 HBM 显存，运行内核（kernel，在 GPU 上执行的函数）。两边通过 PCIe Gen5 x16 连接，带宽约 64 GB/s，比 HBM 慢 75 倍左右，所以数据在两边来回搬很贵。

一个典型的流程是：CPU 用 cudaMalloc 在显存里分配空间，把输入从主机复制到设备，启动内核，然后把结果复制回来。要点有两个：

  • 启动是异步的：CPU 发出启动命令后不等内核跑完，继续做自己的事。直到要把结果复制回来时，CPU 才停下来等。
  • 错误出现得晚：内核里出了错（例如越界访问），要到下一次同步调用时才报出来。所以报错的那一行常常不是出错的那一行。

2. 内核是为一个线程写的

CUDA 内核的写法是：只写一个线程要做的事，启动时指定要多少个线程。下面是向量加法，每个线程算一个输出元素： 

// one thread computes one output element
__global__ void add(float* x, float* y,
                    float* out, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) out[i] = x[i] + y[i];
}

// launch: n = 1M elements
int threads = 256;
int blocks  = (n + threads - 1) / threads;
add<<<blocks, threads>>>(x, y, out, n);

线程被分成线程块（block）。这里每块 256 个线程，100 万个元素需要 $2^{20} / 256 = 4096$ 个块，GPU 把它们分到 132 个 SM（流式多处理器，GPU 上的计算单元）上执行。每个线程用"第几块 × 每块多少线程 + 块内第几个"算出自己负责的元素：第 2 块（从 0 数）的第 1 号线程，算出 $i = 2 \times 256 + 1 = 513$，就去处理 out[513]。if (i < n) 是为了最后一块里多出来的线程不越界。

块大小一般取 32 的倍数，常用 128 到 256，因为硬件按 32 个线程一组（线程束，warp）执行，线程束由块内线性编号连续的 32 个线程组成。函数前面的修饰符决定它在哪里运行、从哪里调用：

修饰符在哪里运行从哪里调用
__global__设备主机（这就是内核）
__device__设备设备
__host__ __device__两边都有任意一边

3. 软件概念和硬件的对应

软件含义对应的硬件
Grid（网格）一次内核启动的所有块整张 GPU，块分散在 132 个 SM 上
Block（线程块）最多 1024 个线程，共享一块 shared memory一个 SM，块分到某个 SM 后一直待到跑完
Warp（线程束）32 个线程步调一致地执行SM 的一个分区，调度器每个周期发射一次
Thread（线程）有自己的寄存器和编号一个核心（也叫 lane），线程束 32 条通道中的一条

线程束和 SIMT 的细节见 第十讲。

4. 不想管线程：图编译器

大多数人不直接写 CUDA。最省事的一层是图编译器，例如 PyTorch 的 torch.compile 和 JAX 的 jax.jit（后者生成 XLA）： 

import torch

def block(x, w, b):
    h = x @ w + b
    return gelu(h) * 0.5

# capture the graph, fuse, generate kernels
fast = torch.compile(block, mode="max-autotune")
y = fast(x, w, b)  # first call compiles

# JAX: jax.jit(block) lowers to XLA

分工是：你用普通的 PyTorch 或 JAX 写数学运算，不管线程、数据块和内存；编译器决定哪些算子融合在一起、块取多大，生成 Triton 或 XLA 内核。它在两种情况下帮不上忙：代码里的控制流（比如依赖数据的 if）把计算图打断；或者那个慢的算子没法和别的融合。

5. 再往下一层：tile 语言

CUDA C++ 让你写一个线程的工作；tile 语言让你写一个线程块处理一整块数据（tile）的工作。区别如下：

CUDA C++tile 语言
你写的是一个线程的工作一个数据块的工作
下标blockIdx × blockDim + threadIdxprogram_id 加上一段范围
搬数据到 shared memory、同步自己搬，自己调 __syncthreads()编译器负责
张量核心线程束级的 MMA 指令对整个数据块做一次点积

在用的 tile 语言有：Triton（Python，支持 NVIDIA 和 AMD GPU）、Pallas（JAX 的内核语言，支持 TPU 和 GPU）、TileLang（基于 TVM 的 Python DSL）、ThunderKittens（C++ 模板）、cuTile（NVIDIA 在 CUDA 13.1 里加的 tile 模型）。

6. 选读：三个例子

Triton：同样的向量加法，每个"程序"（对应一个 CUDA 线程块）处理 1024 个元素。 

# each program handles one BLOCK
@triton.jit
def add(x, y, out, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    a = tl.load(x + offs, mask=mask)
    b = tl.load(y + offs, mask=mask)
    tl.store(out + offs, a + b, mask=mask)

# launch: one program per tile
grid = (triton.cdiv(n, 1024),)
add[grid](x, y, out, n, BLOCK=1024)

mask 起的作用和 CUDA 版的 if (i < n) 一样。合并访存、shared memory 中转、用 tl.dot 调张量核心，都由编译器处理；@triton.autotune 可以针对每种输入形状试不同的块大小和线程束数量。

TileLang：你决定数据块的形状、放 shared memory 还是寄存器、提前加载几级（num_stages）；线程怎样分配、用哪种复制指令、MMA 调用由 TileLang 决定。适合需要显式控制数据搬运的矩阵乘和注意力变体。 

@T.prim_func
def mm(A, B, C):
  with T.Kernel(N // bn, M // bm, threads=128) as (bx, by):
    As = T.alloc_shared((bm, bk), "float16")
    Bs = T.alloc_shared((bk, bn), "float16")
    Cl = T.alloc_fragment((bm, bn), "float")
    T.clear(Cl)
    for k in T.Pipelined(K // bk, num_stages=3):
      T.copy(A[by * bm, k * bk], As)
      T.copy(B[k * bk, bx * bn], Bs)
      T.gemm(As, Bs, Cl)
    T.copy(Cl, C[by * bm, bx * bn])

CuTe、CUTLASS、ThunderKittens：再往下，你要自己决定数据布局（layout）、TMA 异步复制、哪些线程束负责加载、哪些负责计算。CuTe 的核心概念是 layout，一个把坐标映射成内存偏移的函数： 

# a layout maps a coordinate to an offset
row = cute.make_layout((8, 4), stride=(4, 1))   # (i, j) -> i*4 + j
col = cute.make_layout((8, 4), stride=(1, 8))   # (i, j) -> i + j*8

同一套写法可以描述线程束里线程到数据的映射、shared memory 里打乱（swizzle）过的数据块、TMA 的复制单元和 MMA 的片段。这些库提供经过测试的复制、MMA 和流水线组件，用于把矩阵乘和注意力压到接近峰值。

8. 选读：所有 GPU 程序最后都编译成 SASS

SASS 是 GPU 真正执行的机器码。不同来源的代码走不同的路：

  • CUDA C++（NVCC）：设备代码经 NVVM 生成 PTX（NVIDIA 的虚拟指令集），再由 ptxas 生成 SASS，两者一起打包进 fatbin；主机代码交给 GCC、Clang 或 MSVC，最后链接成可执行文件。
  • Triton：@triton.jit 函数依次变成 Triton IR、TritonGPU IR、LLVM IR，再经 LLVM 生成 PTX，由 ptxas 生成 SASS（cubin）。
  • cuTile（Python 或 C++）：生成 CUDA Tile IR，由 tileiras 直接生成 SASS。

程序加载时，驱动程序找和当前 GPU 匹配的 SASS；没有的话，就把 PTX 即时编译一遍并缓存起来。这就是为什么同一个程序能在新一代 GPU 上运行。

三、GPU 的效率和利用率

1. MFU：模型算力利用率

MFU（Model FLOPs Utilization）是实际达到的模型运算速度除以 GPU 的峰值：

$$\text{MFU} = \frac{\text{实际的模型 FLOP/s}}{\text{峰值 FLOP/s}}$$

推理时，生成一个 token 的模型运算量约为 $2N$ 次浮点运算（$N$ 是参数量，只算前向）。峰值取 GPU 张量核心的稠密运算速度。课件的例子是 8 张 H100 跑 Llama 2 70B：

  • 每个 token 的运算量：$2 \times 70\text{B} \approx 140$ GFLOP。
  • 每张卡每秒 3040 个 token，实际速度 $3040 \times 140\ \text{GFLOP} \approx 426$ TFLOP/s。
  • H100 的峰值是 1979 TFLOP/s，MFU $\approx 426 / 1979 \approx 22\%$。

经验值：训练 35% 到 45%；推理的预填充阶段 40% 到 60%，解码阶段 10% 到 40%。

2. MFU 为什么低

课件列了四个原因（引自 PaLM 论文和 Korthikanti 等关于激活重算的工作）：

  • 通信：张量并行、流水线并行、数据并行之间的数据传输没有被计算掩盖。
  • 流水线气泡：每批数据填满和排空流水线时，一些阶段空等。
  • 受内存限制的内核：归一化、softmax、优化器更新这些操作的速度取决于带宽，用不上张量核心的峰值。
  • 重算（训练时）：激活检查点会把前向计算再跑一遍，这部分运算不算进 MFU。

课件的总结是：MFU 把硬件能力和软件成熟度分开了。同一块硬件，MFU 低说明软件还有改进空间。

3. MBU：解码看的是带宽

第十讲讲过，解码阶段每生成一个 token 都要把全部权重读一遍，速度受带宽限制。所以解码应该看 MBU（Model Bandwidth Utilization）：

$$\text{MBU} = \frac{\text{实际每秒读写的字节数}}{\text{HBM 峰值带宽}}$$

每一步解码要读的字节数是全部权重加上 KV 缓存。例子：Llama 3 8B，BF16，批大小 1，H200。每个 token 读 16 GB，每秒 200 个 token 就是 3.2 TB/s，H200 的带宽是 4.8 TB/s，MBU $\approx 67\%$。经验规则：预填充和训练报 MFU，解码报 MBU。

衡量推理服务的其他指标：

  • 每张 GPU 每秒多少 token：要在给定的延迟目标下报，例如每个输出 token 的 p50 时间。
  • 每个 token 的能耗：焦耳 = 平均板卡功率 ÷ 每秒 token 数。
  • 每百万 token 的成本：每 GPU 小时的价格 ÷（每秒 token 数 × 3600）× $10^6$。

4. 先看时间线，再看单个内核

NVIDIA 有两个性能分析工具，用法是先粗后细：

工具命令看到什么用来找什么

四、近年的 GPU 内核优化

1. 时间浪费在三个地方

位置浪费在哪代表技术

2. 内核融合

融合是把几个操作合进一个内核，中间结果不写回 HBM。分两种：

  • 纵向融合：前一步的输出直接给下一步用。例如矩阵乘、加偏置、GELU 合成一个内核，每个结果留在寄存器里。省掉的是 HBM 往返。常见的有矩阵乘的收尾（epilogue）、LayerNorm、带掩码的 softmax。
  • 横向融合：几个读同一个输入的操作合成一个。例如 $x W_q$、$x W_k$、$x W_v$ 合成一个矩阵乘 $x [W_q\ W_k\ W_v]$，$x$ 只读一次，只启动一次。常见的有 QKV 投影、FFN 的 gate 和 up 投影。

课件的例子：在 1 GB 的 FP32 数据上依次做缩放、加偏置、ReLU。拆成三个内核时，每一步都要从 HBM 读一遍、写一遍，共 6 次，耗时 1.25 ms；融合成一个内核只读一次写一次，HBM 流量少 3 倍，耗时 0.42 ms。torch.compile 会自动把纵向的链融合成一个 Triton 内核；QKV 和 gate、up 的权重则常由模型代码手工拼接。

3. FlashAttention：分块算注意力，分数矩阵不进 HBM

标准注意力先算出 $n \times n$ 的分数矩阵 $S = QK^\top$，写到 HBM，再读回来算 softmax 得到 $P$，再写、再读，最后乘 $V$。序列长 8K 时，每个注意力头、每一层都有 $8192^2 \approx 6700$ 万个分数要在 HBM 里进出。

FlashAttention 的做法是：取一块 $Q$，依次和每一块 $K$、$V$ 计算，分数块只存在于一个线程块的 shared memory 和寄存器里。softmax 需要整行的最大值和总和，所以用在线 softmax（online softmax），边算边维护当前的最大值和总和，每来一块新数据就修正之前的结果。最后 HBM 只做三件事：读一遍 $K$、$V$，写一遍输出 $O$。

4. 选读：从 FlashAttention 到 FlashAttention-4

版本瓶颈做法效果
FlashAttention（2022，A100）HBM 流量：分数矩阵写出去再读回来在 shared memory 里分块；在线 softmax注意力快 2 到 4 倍；显存随长度线性增长
FlashAttention-2（2023，A100）占用率低：每个头一个块，非矩阵乘的运算多沿序列维度切分工作；减少重新缩放约为第一版的 2 倍；最高约 A100 峰值的 70%

FlashAttention-4（2025，B200）张量核心算力翻倍，算 exp 的单元没有，softmax 成了瓶颈累加结果放在 TMEM；一部分 exp 改用 FMA 单元算在 B200 上比 cuDNN 的注意力快

四代的思路一样：找到当前最慢的那个部件，把工作挪走或者和别的工作重叠。

5. 选读：持久化内核

一个矩阵乘被切成 160 个输出块，每块一个线程块。GPU 有 132 个 SM，所以要分两轮：第一轮 132 个块占满所有 SM，第二轮只剩 28 个块，104 个 SM 空等。而且每个块都要为它那一个输出块做一遍准备工作。

持久化内核（persistent kernel）只启动 132 个块，每个 SM 一个，各自循环领取输出块，算完一块写出去，接着算下一块。没有空闲的第二轮，准备工作只做一次。CUTLASS 和 DeepGEMM 都这样做。Stream-K（PPoPP 2023）更进一步，把输出块切得更小，让所有 SM 同时结束。

6. 选读：split-KV 平衡解码的负载

解码时每个请求只有一个查询 token，如果只按"批大小 × 注意力头数"分工，块数不够，SM 会闲着。而且不同请求的 KV 长度能差 100 倍，KV 缓存的页面在 HBM 里也是分散的。

split-KV（来自 Flash-Decoding）把每个请求的 KV 页面切开，分给多个 SM，例如每个 SM 处理 4 页。每个 SM 算出一个部分结果（当前最大值 $m$、总和 $\ell$、部分输出 $O$），最后按在线 softmax 的方法合并。FlashInfer（MLSys 2025 杰出论文）把分页的 KV 看作块稀疏的行，配合即时编译的专用内核和这种调度，网格大小固定，所以能和 CUDA Graphs 一起用。vLLM 和 SGLang 都用它。

7. 选读：CUDA Graphs

解码一个 token 要跑几十个小内核，每次启动在 CPU 和驱动上花几微秒，GPU 就在内核之间等着。CUDA Graphs 把一步解码里的所有启动录下来，之后每个 token 只用一次调用重放： 

cudaStreamBeginCapture(s, mode);   // record one step
  /* ...launch the kernels... */
cudaStreamEndCapture(s, &g);
cudaGraphInstantiate(&e, g, 0);
cudaGraphLaunch(e, s);              // replay every token

vLLM 和 SGLang 都这样做。

8. 选读：PDL，让下一个内核提前开始

在同一个 stream 里，内核 B 要等内核 A 完全结束、内存刷新之后才启动。解码每个 token 有很多微秒级的内核，启动延迟、每个内核开头的准备（prologue）和结尾的拖尾加起来不少。

Programmatic Dependent Launch（PDL）让 A 在合适的时候调用 cudaTriggerProgrammaticLaunchCompletion() 通知可以开始下一个；B 提前启动，先做不依赖 A 的准备工作，到 cudaGridDependencySynchronize() 处再等 A 的结果。PDL 需要 Hopper 或更新的 GPU（SM 9.0），可以在 CUDA Graphs 里用。

9. 选读：megakernel，整个模型一次启动

批大小为 1 时解码 Llama-3.2-1B，每层约 7 个内核，16 层，每个 token 就是约 112 次启动。每到内核边界，GPU 都要排空，下一个内核才开始加载权重。课件说 vLLM 和 SGLang 在这种情况下只用到 H100 带宽的约 50%。

Hazy Research 的 megakernel 把整个模型的前向放进一个内核：GPU 上有一个解释器，每个 SM 有自己的指令队列，shared memory 分页存放权重，用全局计数器管理操作之间的依赖。当前操作还在算时，下一个操作的权重已经在加载。批大小为 1 时达到 H100 带宽的 78%，单用户吞吐约为 SGLang 的 1.5 倍。Mirage MPK 能自动把模型编译成这样的任务图。

10. 选读：把张量并行的通信藏进矩阵乘

张量并行把每一层切到 8 张卡上，每个切分的矩阵乘前面要一次 AllGather，后面要一次 ReduceScatter。如果通信和计算是分开的内核，矩阵乘要等整个集合通信完成。

FLUX（Chang 等，2024）把通信融合进矩阵乘：每个输出块算完，收尾阶段直接通过 NVLink 或 NVSHMEM 写到它所属的 GPU；AllGather 加矩阵乘时，哪一行数据到了就先算哪一块。不需要额外的通信内核。在 8 张卡上最多掩盖 96% 的通信，预填充比 vLLM 快最多 1.66 倍，解码快最多 1.30 倍。

11. 选读：MoE 的 all-to-all 和计算重叠

混合专家模型的每一层要把每个 token 发给它选中的 8 个专家（在别的 GPU 上），再把输出收回来。串行执行时，发送（dispatch）和收回（combine）期间张量核心闲着，NCCL 的通信内核还会占用 SM。

DeepSeek 的 DeepEP 把一批数据分成两个微批次，A 在算注意力或专家时，B 在通信，交替进行。传输用基于 hook 的方式由网卡完成，不占 SM；发送用 FP8，收回用 BF16；跨节点时先走 NVLink 再转 RDMA。节点内发送约 153 GB/s，跨节点约 43 GB/s，接近链路上限。

12. 选读：让 Agent 写内核

每一代 GPU 都有新特性（TMA、TMEM、FP4），每种注意力变体都要新的手调内核，而会写的工程师很少。课件介绍的做法是一个循环：Agent 用 CUDA、Triton 或 CuTe DSL 写内核，编译（拿到 nvcc、ptxas 的报错），在很多种输入形状上和 PyTorch 参考实现比对结果，再测运行时间和 Nsight 计数器，把这些反馈给 Agent 继续改。

风险是生成的内核可能靠一个弱测试或者利用评测框架的漏洞显得很快。KernelBench 用 fastp 作指标：结果正确、并且比 PyTorch 快 $p$ 倍以上的任务占比；静态检查会拒绝有竞态的调度。这和 Agent 课程里反复讲的"奖励作弊"是同一类问题。

13. 内核优化的要点

  1. 内核内部：喂饱张量核心。融合收尾操作，FP8、FP4 按块缩放，把线程束分成生产者和消费者，把工作从最慢的单元上挪走。
  2. SM 之间和启动之间：消除空闲。持久化线程块和 split-KV 平衡各 SM 的负载；PDL 和 megakernel 消除内核之间的间隙。
  3. GPU 之间：掩盖通信。把张量并行的集合通信融合进矩阵乘的数据块，让 MoE 的 all-to-all 和专家计算重叠。
  4. 写内核：把搜索自动化。Agent 写出候选内核并测性能，在多种形状上的正确性检查决定哪些留下。

五、AI 硬件面临的问题

  • 网络：离开一台机器就慢 9 倍。把 Llama 3 70B 一个 32K token 提示的 KV 缓存交给另一台机器，走 400G 网卡要 215 ms，走 H100 的 NVLink 只要 24 ms。
  • 可靠性：Llama 3 训练期间平均每 3 小时出一次故障。419 次中断里，GPU 故障占 30%，HBM3 显存占 17%，网络占 8%。
  • 功耗：GB200 NVL72 一个机柜 120 kW，HGX B200 60 kW，普通机柜 15 kW，是普通机柜的 8 倍。
  • 散热和用水：GB200 NVL72 机柜必须液冷。训练 GPT-3 用了 70 万升淡水；预计 2027 年 AI 的取水量达 42 亿到 66 亿立方米。

六、选读：优化 GPU 代码的四个目标

课件最后附了一组选读，把常见的优化手段按目标归类。一个快的矩阵乘通常同时用到好几种：合并访存、双缓冲数据块、用张量核心。

目标技术做法例子
少搬数据合并访存相邻线程读连续地址线程 i 读 x[i]，不读 x[32·i]
shared memory 分块一块数据加载一次，块内线程共用矩阵块被很多输出复用
寄存器分块每个线程用寄存器里的数据算多个输出每个线程多个累加器

填充 / swizzle改 shared memory 布局，避免 bank 冲突转置时数据块从 32×32 改成 32×33
按缓存排序让相邻的块读同样的数据，复用缓存把读相同输入的输出块排在一起
掩盖等待、增加并行异步复制 + 双缓冲算当前数据块时加载下一块矩阵乘里两个 shared memory 缓冲区交替用
指令级并行前面的指令在等时，发射不相关的指令多个累加器，而不是一条依赖链

这些手段都有代价：split-K 多一步合并，流水线要多开缓冲区、多做同步；用张量核心要求形状合适，降精度要保证结果仍然准确，这是两个独立的选择。
