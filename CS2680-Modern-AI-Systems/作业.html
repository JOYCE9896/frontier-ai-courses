作业与期末项目

五个作业是同一个 Agent 系统一层层往下拆：先当用户看 Agent 怎样工作，再自己写循环，再在黑盒 API 上省 token，再换成自己部署的模型，最后优化整个栈。这一页整理每个作业要做什么、怎样评分、难在哪里，以及期末项目的要求

资料来源：Harvard CS2680 课程网站的 作业总览、作业 1、作业 2、作业 3、作业 4、期末项目（截至 2026 年 10 月 23 日；作业 5 尚未发布）。这里只做中文梳理，具体操作步骤、启动代码和提交格式以原网页为准。

一、总体安排

五个作业都叫 Mads 开头的名字（Modern Agent Design and Systems 的缩写），它们不是五道独立的题，而是同一个系统被一步步拆开、接管：

作业名字时间占比一句话
1Mads-Lens9/2 到 9/2010%给 Claude Code 做一个网页界面，看它怎样工作
2Mads-Loop9/21 到 10/410%自己写 Agent 循环，在 SWE-bench Pro 上测
3Mads-Opt10/5 到 10/2020%模型仍是黑盒 API，在成本和速度上竞赛
4Mads-Serve10/21 到 11/1020%自己在一张 GPU 上部署模型，让 Agent 跑得更快
5Mads-Stack11/11 到 11/2910%Agent、模型、服务系统全部可改，优化整个栈（未发布）

作业合计占总成绩 70%，期末项目 20%，没有考试。全部是个人作业，代码都提交到同一个私有 GitHub 仓库的 assignment1/ 到 assignment5/ 目录下，并把讲师和四位助教加为协作者。作业 1、2、4 的书面总结放进仓库，作业 3、5 原计划以博客文章形式发布。课程网站估计的工作量：作业 1 约 4 到 6 小时，作业 2 约 10 到 12 小时，作业 3 约 10 到 15 小时，作业 4 约 10 到 14 小时，作业 5 约 12 到 18 小时。整个学期有 4 个迟交天数，但排行榜提交不能用迟交天数。

课程鼓励用 AI，但要披露，并提交 Claude Code 等工具的会话日志作为证据（日志本身不计分）。多个作业明确要求书面总结由自己写，不得用 AI 生成；第七讲开头讲者专门说了作业 1 里有人删改日志的事。

算力：作业 1 用 Claude Code（课程提供 Harvard 账号登录的许可）；作业 2、3 用课程的模型 API（api.cs2680.com，兼容 OpenAI 接口）；作业 4、5 用课程的 HPC 集群（SLURM 排队）；AWS 账号第一周注册，使用可选。

二、作业 1：Mads-Lens，看 Agent 工作

任务是做一个网页，驱动 Claude Code：在页面上输入请求，Agent 在你选的目录里工作，页面实时显示它在做什么。这个作业故意做得很小，也是唯一一个后面不会再拿来比较的作业。学习目标有三个：用 Claude Code 写出能用的软件；用程序驱动 Agent，而不只是交互式地用；实时观看一条轨迹，看 Agent 读了什么、跑了什么、花了多少钱。作业建议连前端也用 Claude Code 来写，一边看它写，一边就知道页面该显示什么。

第一部分：在终端里驱动 Claude Code

Claude Code 有无头模式：加 -p 参数就非交互地运行，再加 --output-format stream-json --verbose，它会边运行边每行打印一个 JSON 事件。事件流的顺序是：一个初始化事件，然后是助手消息、工具调用和工具结果，最后一个结果事件，里面有总花费、耗时、轮数和会话编号。拿着会话编号用 --resume 再发一条提示，就能接着上一次的对话。作业要求先在终端里对一个临时目录跑一遍、读懂这些事件，再把一次完整的运行存成 events.jsonl 文件，因为第二部分的前端就是这个事件流的渲染器。

两个注意事项。无头模式下没人回答权限提示，需要权限的请求会被拒绝，所以要用跳过权限的参数（只对临时目录这样做），或者用 --allowedTools 只放行指定的工具。认证用 Harvard 登录，不要用 Agent SDK 或 API 密钥：一是使用条款规定 SDK 要用 API 密钥，而课程不提供；二是环境变量里的 API 密钥优先级更高，设了就会悄悄从你自己的账户扣钱。

第二部分：前端要有的七个功能

  1. 提交提示：在文本框里输入请求，对选定的工作目录运行，第一次结束后可以再开新的一次。
  2. 实时显示轨迹：助手的文字和每一个工具调用（名字和输入）在到达时立刻显示，而不是运行结束后才出来；助手的 Markdown 要渲染成格式。
  3. 显示工具结果：每个工具调用的结果跟着它显示，长输出要有意地截短或折叠。测试日志可能有几千行，怎样取舍是设计问题。
  4. 两级状态：每个工具调用从发出到对应结果到达之间显示"进行中"，结果报错时显示为错误（调用和结果靠同一个编号配对）；每次运行要区分进行中、已完成、失败，失败的运行（比如目录不存在）要显示错误，而不是让页面一直等着。
  5. 继续对话：后续提示接着同一个会话，Agent 保留上一轮的上下文。
  6. 显示运行的数字：每次运行结束后显示花费（美元）、耗时、轮数，这些在结果事件里都有。
  7. 树状轨迹：Claude Code 会把工作委派给子 Agent，子 Agent 发出的每个事件都带着派生它的那个工具调用的编号。要把子 Agent 的事件嵌套在那个调用下面，可以折叠；没有子 Agent 的运行仍是平的列表。另外在对话旁边显示一个只有调用名字的大纲，像目录一样可以跳转。

七个功能是最低要求，作业鼓励自己用这个页面、发现哪里不顺手就改，让它对人越来越友好。还给了几个实用建议：准备一个有几个文件和测试的小代码库给 Agent 干活，空目录演示不出东西；开发时给服务器加一个回放模式，读取存好的 events.jsonl 而不是每次真跑 Agent，真跑一次要一分钟以上还花钱，回放是瞬间且免费的。不能用 Agent 框架，也不能自己重写 Agent 循环（那是作业 2）。如果部署到公网机器上，必须在前面加随机访问令牌，因为这个页面等于是一个能读文件、跑命令的进程的遥控器。

第三部分：书面总结

三节：做了什么（一段话加一张截图，以及七个功能之外的改进）；学到了什么（三条观察，每条都要落到会话里的一个具体时刻：Agent 怎样工作，比如它在哪里花的时间比你预想的多；一个坑，以及你怎样发现的；一个教训，下次会怎样写提示、划范围或监督）；想改 Claude Code 的哪一点，以及看到了什么让你想改。

评分：七个功能各 10%，按演示视频判断完全实现、部分实现或没有；书面总结 20%，主要看第二节，落到具体会话时刻的观察得分，泛泛的称赞不得分；视觉设计 10%。另交一个 2 到 3 分钟的演示视频，必须展示全部七个功能，包括一次失败的运行和一次派生子 Agent 的运行。

三、作业 2：Mads-Loop，自己写 Agent 循环

任务是写一个最小的编程 Agent Harness，叫 madsLoop，用 SWE-bench Pro 的任务来测。模型固定用 qwen3.6-35b-a3b，通过课程的 API 调用。作业说明里特意用醒目的警告写着：第 0、1 部分描述的只是一种设计选择，不是答案，不要全信，要拿真实任务去检验，必要时修改；书面总结会问你和说明里有哪些不同、为什么。另一个警告是：给的 10 个任务里，有些即使 Harness 完美也解决不了。

要做的东西

接口：python madsLoop.py -p "问题描述" [--log] 工作目录。Agent 只能在工作目录里读、搜、改、跑命令；结束时修复以未暂存的修改留在目录里，之后用 git diff 生成补丁。加 --log 时要按规定的格式写运行日志，每行一个 JSON 事件，事件类型包括运行开始、API 请求（带 token 用量）、API 重试、工具调用、工具结果（按喂给模型时截断后的样子记录）、运行结束（带结束原因和迭代次数）。

Harness 的三块内容，正好对应第四讲：

  • 工具定义：每个工具有名字、自然语言描述和参数的 JSON Schema。参考的最小工具集是 bash、read_file（带行号）、edit_file（精确字符串替换）和 done，可以另行设计。
  • Agent 循环：把消息和工具发给模型；有工具调用就逐个执行，把助手消息和每个调用对应的一条结果消息追加进去，继续；没有工具调用就结束。修复时要处理自己引入的失败，和改动无关的原有失败可以不管。
  • 对话状态：模型没有状态，每次请求都要重发全部历史，由 Harness 维护。每个工具调用必须恰好配一条引用其编号的结果消息，否则 API 会报错。系统提示要说明角色和规则（比如改动最小、不要改测试）。工具输出会不断累积，至少要先截断大的输出再追加。

每个任务是一个预先构建好的 Docker 镜像，仓库检出在 /app，依赖都装好了。Agent 在容器里跑，官方评估在另一个容器里跑：把补丁应用到干净的检出上，恢复隐藏的测试文件，跑真正的测试，所以改测试文件没有用。

自己出四道题

除了给定的任务，还要自己做四个任务，不能取自 SWE-bench Pro 或任何其他 Agent 基准，来源只能是开源仓库里真实的 issue 及修复它的提交，或者自己以前项目里真修过的 bug、真加过的功能。每道题要有：一段话的问题描述（Agent 只看到这个）；能证明修好了的测试，包括至少一个"修复前失败、修复后通过"的测试，和若干"前后都通过"的测试（防止一个把仓库搞坏的补丁被当成修复）；一个 Dockerfile，构建出依赖齐全、不联网也能跑测试的镜像；以及真实修复的 gold.diff，用来证明测试可信。四道题分两组：两道是 Agent 一开始解决不了、改了 Agent 之后能解决的；两道是交作业时仍解决不了的。还要自己写一个 verify.sh 来判定是否解决。

评分

隐藏任务 40%：在给定任务加更多隐藏的 SWE-bench Pro 任务上运行，按可解任务中解决的比例计分；把不可解的任务"做通过了"反而扣分。书面总结 40%（一页，必须自己写）：哪些给定任务你认为不可解、为什么（20%），要给出运行中的证据，指出是任务本身的什么问题，而不是 Agent 的问题；和作业说明有哪些不同（10%）；自建的四道题（10%）。视频 20%：3 分钟讲解代码，以及哪一处改动让那两道题从不能解决变成能解决。

四、作业 3：Mads-Opt，Harness 竞赛

模型仍然是黑盒 API，要优化的是它周围的一切：减少不必要的 token 和调用，在够用的地方选便宜的模型，让工具执行重叠，压缩或重组上下文，重新设计控制流。在任务成功率不降的前提下压低成本和延迟。第八讲就是为这个作业准备的。讲者说它比前两个难得多，建议当期中考试对待。

框架

有两种容器。Agent 容器里跑你的主 Agent 循环，记忆、子 Agent 等功能也都在这里。每个任务有自己的任务容器，里面是检出到起始提交的仓库和测试依赖。两个容器都不能上网：Agent 容器唯一的出口是一个通往课程 API 的代理，任务容器完全没有网络。任务容器里跑着一个很小的 HTTP 服务，提供健康检查、执行命令、读文件、写文件四个接口，Agent 对仓库做的一切都通过它，不能在 Agent 容器里直接用本地文件操作（那里没有仓库）。可以给它加新接口。

Agent 通过一个调度器拿任务、交补丁、请求评分。评分时，设施把补丁应用到全新的任务镜像上，加上隐藏测试跑一遍，只告诉 Agent 测试总数和失败数。Agent 然后自己决定：继续修（容器和改动原样保留），还是宣布这个任务结束（以最后一次评分为准）。规则：同时最多开 5 个任务；每个任务同一时间只能有一次评分在进行；单次评分限时 35 分钟；整次运行限时 4 小时，从打开第一个任务开始计时，时间到了没打开的任务算失败。怎样安排任务顺序、是否并行、什么时候评分、失败了是再试还是放弃、从一个任务带什么经验到下一个，全部由你决定。启动代码里的示例 Agent 只演示了这些调用，什么都不修，跑出来是 0/5。

可以用三档模型，价格差别很大（每百万 token）：expert 输入 2.00 美元、缓存输入 0.10、输出 10.00；standard 输入 0.08、缓存 0.004、输出 0.28；starter 输入 0.01、缓存 0.0005、输出 0.04。同一次运行里可以混用。

排行榜

排行榜只取你的 src/ 目录，在 26 个评测任务上运行，看三个指标：解决的任务数；每个解决任务的花费；每个解决任务的时间（端到端时钟时间除以解决数）。每人每天 30 美元的评测预算，每次提交最多 10 美元，碰到上限就停，按已完成的部分记成绩。

排名用"天际线"：解决至少 7 个任务的提交，在三个指标上按帕累托支配分层，第 1 层是没有被任何提交支配的那些，拿掉后再算第 2 层，以此类推；少于 7 个的排在所有人后面，只按解决数排。每人以最好的一次提交排名。这就是第七讲最后讲的帕累托前沿。

评分

排行榜 80 分：名次为 $r$ 时得 $81-r$ 分；如果有任何一次提交达到基线（4 小时内、10 美元以内解决 16 个任务），至少得 50 分。书面总结 10 分（一页，自己写）：Harness 的主要部件（比如子 Agent、跨任务的记忆、哪一档模型做什么）；做了哪些优化和取舍（比如失败任务继续还是放弃的策略、同时开几个任务）；遇到了什么坑、什么对准确率、成本、时间有帮助。视频 10 分，要露脸、用自己的声音，在代码里指出每个部件的位置。另外，找到并报告安全漏洞最多可加 3 分总成绩，利用漏洞则提交作废。

五、作业 4：Mads-Serve，自己部署模型

这次没有前沿 API 了。要在一张 RTX PRO 4500（32 GB）上自己部署模型（Qwen3.6-35B-A3B 的 NVFP4 量化版），让作业 3 的 Agent 调用它，找出是什么限制了运行速度，再通过改推理引擎或改 Agent 让它更快，模型本身保持不变。讲者在第十讲说，这个作业要写的代码不多，重点是推理性能和瓶颈、迭代改进，并体会真实负载和合成基准有什么不同；书面总结很重要。课程 GPU 有限，全班共享，每人同时只能用一张，违反一次警告，之后每次扣本作业 10% 的分。

四个部分

  1. 跑起基础的 SGLang 配置：在集群的 GPU 节点上用课程提供的环境启动 SGLang 服务（课程环境里有依赖、CUDA 工具链和模型权重，SGLang 用自己克隆的一份以便修改），用课程的冒烟测试检查七项功能；Agent 和任务容器仍在作业 3 那台有 Docker 的机器上运行，通过 SSH 隧道连到 GPU 节点。三档模型变量都指向自己部署的这一个模型。
  2. 测量起点：用基础配置让作业 3 的 Agent 跑 25 个任务，一开始就把 25 个全部打开。记录解决数和端到端时间。运行期间定时（比如每 10 秒）读取服务器的指标接口并全部保存，结合服务器日志和 Agent 日志，弄清楚时间花在哪里，并画出整个运行过程。再用 SGLang 自带的服务基准测试，选尽量贴近 Agent 负载的参数，和真实运行的测量结果对比。
  3. 让服务更高效：按三步走，先用第二部分的测量找出限制速度的原因，再列出可能消除它的改动并预测每个的效果，然后实现最有希望的几个、逐个测量。一次只改一样，在同样的任务上测，每一次尝试都记录下来，没有效果的也要记。
  4. 提交：src/ 放 Agent，engine/ 放服务器配置（框架、启动参数、启动脚本，以及对 SGLang 源码的补丁，如果改了的话）。

能改什么，不能改什么

推理引擎可以用 SGLang 或 vLLM，源码和设置都可以改（但预编译的内核不能在课程节点上重新编译，只能改 Python 部分和运行时编译的内核），也可以自担风险用别的框架。Agent 怎样使用服务器也可以改。不能换模型，不能在加载时转换权重；KV 缓存的数据类型这类引擎设置可以改；投机解码可以用模型自带的多 token 预测头，但不能另外用草稿模型。不能改任务集、调度器、评测脚本，不能把模型调用发到别处。作业 3 的规则同样适用于引擎：不能识别具体任务或提示，不能内置从任务预先算好的回答或状态，不能在两次评测之间保留状态；在任务上测量来调一个通用的服务器参数是允许的。

排行榜和评分

排行榜在一个全新的 RTX PRO 4500 节点上、无网络的沙盒里按你的 engine/ 启动服务器（必须在 45 分钟内就绪，就绪之前的时间不计），再在 26 个评测任务上跑你的 Agent，这次同时打开的任务数没有上限。指标只有两个：解决数和端到端时间（从服务器就绪到最后一个任务结束，最多 4 小时）。每人每天最多评测 3 次。排名同样是天际线，但这次所有有效提交都参与，每一轮把前沿上出现过的学生整个拿掉再算下一轮。

排行榜 60 分：名次为 $r$ 时得 $61-r$ 分；达到基线（同一次提交里至少解决 7 个任务、端到端不超过 100 分钟）则至少 40 分。书面总结 30 分，自己写，按顺序包括四部分：起点运行受什么限制、怎样发现的；SGLang 基准测试和 Agent 真实运行对比的发现；一张优化表，每次尝试一行，写明改了什么、促使你改的观察（带数字）、为什么预期它有效以及预测的效果、实际测到的结果（和前一次运行对比，带日志里的数字）；学到的教训。视频 10 分，3 分钟，露脸，任何依赖日志或指标的说法都要把证据放在屏幕上。

六、作业 5：Mads-Stack，优化整个栈

截至 2026 年 10 月 23 日尚未发布，总览页上只有一段描述：这次 Agent 循环、模型和服务系统全部可以改。先剖析完整的执行路径，直到能说清时间、token 和算力花在哪里；改系统之前先写下性能假设；然后跨层优化，在同样的负载上重跑，判断哪些改动真正起了作用。原计划占 20%，第八讲时因为太难、且和期末项目以及其他课的项目重叠，改为 10%。发布后再补。

七、期末项目

作业里问题和评估都由课程规定，期末项目两者都由自己选：选一个问题，做一个系统或实验来解决它，并用测量数据支持一个论断。个人完成，占总成绩 20%：10 月 28 日交提案（2%）；12 月 7 日上午做海报和演示，包括同学互评（10%）；12 月 8 日在课程博客上发文章并公开代码仓库（8%）。

两条路线

产品路线：做一个 AI 系统，在一个真实问题上比现有最强的方案做得更好。差距可以来自缺少上下文、不可靠、太贵、太慢、隐私限制，或者现有工具不支持的工作流。方向举例：自动化科研流程（跑实验、复现结果、分析论文）、学习工具、改进自己日常的重复工作，或者把某个作业做得远远超出评分要求（要说明新在哪里）。

研究路线：要有一个原创的、可证伪的论断，关于 Agent 或运行它们的系统。必须得出最接近的已发表工作没有给出的结果，解释为什么，并说明在什么条件下成立。光是做得漂亮的实现、复现、基准或一组测量本身都不够。可以做 Agent 一侧（规划、工具使用、记忆、上下文管理、验证、多 Agent 协调、评估等，测的是 Agent 的行为、能力、可靠性或成本），也可以做系统一侧（推理、批处理、调度、缓存、路由、量化、压缩、内核等，测的是系统性能、效率、可扩展性或可靠性）。贡献形式有四种：测量（报告前人没报告过的行为、瓶颈或取舍，并解释原因和出现条件）；机制（提出方法并和已发表的最强方案对比，用消融实验隔离它的作用）；复现加边界（复现一个已发表结果，再找出它不再成立的条件）；工具（做一个让之前答不了的问题变得可答的基准或测量框架，验证它，再用它回答问题）。

提案的九个部分

标题和摘要；问题；现有工作和差距；论断；设计；评估计划；目标；计划和资源；参考文献。其中"现有工作和差距"要求最具体：产品路线要在自己的任务上实际试至少三个最接近的商业工具、开源系统或研究原型，再把同样的输入直接给一个前沿模型，描述每个怎样失败；研究路线要引用最接近的已发表工作，说明它没解决什么，并说明已经复现了什么或打算怎样复现。最后用一句可检验的话写出差距。"它读不了我集群的作业队列"是可检验的差距，"没有类似的东西"不是。目标要分三档：75% 是即使主要想法不成也能交出的最低结果；100% 是计划交出的结果；125% 是提前完成时尝试的扩展。

评估的要求

基线：产品路线要和"在你的任务上跑的现有最强系统"以及"现在手工做的流程（在你的工具介入之前先计时）"比；研究路线要和"未修改的 Agent 或系统"以及"在你的环境里复现出来的已发表最强方法"比。论文里报告的数字是在不同的模型、提示、任务、GPU、软件版本下测的，直接拿来比会把你的改动和这些差别混在一起，所以要先在自己的环境里复现。研究路线还要在主实验之前写下假设、固定流程，做重复试验并报告波动，隔离提出的原因，至少测一个边界条件。

指标要和论断对应，延迟结果必须说明是在什么请求速率下测的。要往下多测一层：只说"Agent 用了 60 秒"是报告结果，说"工具调用占了 40 秒，其中一次 30 秒的调用本可以并行"才指出了该改什么。五周的节奏是：第 1 周定问题、试现有系统或复现、记录基线；第 2 周跑通一个端到端原型或小规模的完整实验；第 3、4 周改进并做对照实验；第 5 周分析结果、准备海报、演示、博客和仓库。

博客文章面向一般技术读者，要包括问题和差距、设计、评估方法、结果（包括做得更差的对比）、局限和威胁效度的因素、达到了哪一档目标、仓库链接，以及按 AI 使用政策要求的说明：哪些交给了 AI、哪些自己做、AI 在哪里帮了忙、在哪里误导了你、你怎样发现的、花了多少。仓库要能让别人复现主要结果。评分看四个方面：问题和动机、技术实现、评估、报告。主要想法没成功也可能拿接近满分，只要博客解释清楚预期是什么、测到了什么、两者为什么不同；而测量不支持的论断，无论结果好坏都扣分。
