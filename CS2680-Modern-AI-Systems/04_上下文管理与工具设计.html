第四讲：Agent 设计（一）：上下文管理与工具设计

ReAct 循环与 Agent 循环的代码骨架，搜索、编辑、执行三类工具各有哪些做法和代价，工具设计原则，从提示工程到上下文工程，上下文窗口的四级管理手段，上下文失败的五种方式，以及"Agent = 模型 × Harness"

主讲：Juncheng Yang
资料来源：课件（2026 年 9 月 16 日；课程不录像，本文依据课件整理）
课程推荐阅读：ReAct、OpenAI 的 A practical guide to building agents、Lilian Weng 的 LLM Powered Autonomous Agents

一、从用户变成设计者

前两讲站在用户角度看 Claude Code。从这一讲开始换到设计者角度：如果自己写一个编程 Agent，要做哪些决定。作业 2 就是做这件事。这一讲讲三块：Agent 循环、工具设计、上下文管理。

二、ReAct 循环

ReAct 是 2022 年的一篇论文（Yao 等，《ReAct: Synergizing Reasoning and Acting in Language Models》），名字取自 Reason（推理）和 Act（行动）。它把两件事放进同一个循环，每一轮有三步：

  • 思考（Thought）：我知道什么，还缺什么，下一步做什么。
  • 行动（Action）：输出一个环境能执行的结构化调用。
  • 观察（Observation）：环境返回事实。

对比另外两种做法就能看出为什么要合在一起。只推理不行动，推理没有任何东西来检验，小错误层层累积，最后变成很有把握的幻觉。只行动不推理，工具调用背后没有计划，模型会重复自己。ReAct 里，思考引导下一个行动，观察纠正下一次思考。循环一直进行到观察结果回答了问题，或者触发了停止规则。

Agent 循环的代码骨架

课件给了一段十几行的 Python 伪代码，逻辑是这样的：先准备一个消息列表，里面放一条系统消息（"用这些工具解决任务"）和用户请求。然后进入一个最多跑 MAX_STEPS 步的循环。每一步把消息列表和工具定义发给模型，把模型的回复追加到消息列表。如果回复里有最终答案就返回；否则对回复里的每个工具调用，先校验参数，再执行工具，把结果序列化后作为一条 "tool" 角色的消息追加进去，并带上对应的调用编号。循环跑满还没有答案，就报错"超过步数上限"。

作为 Harness 设计者，要负责这个循环里的四处：组装上下文（发给模型之前放什么）；编写工具定义（名字、说明、参数格式）；校验请求、检查权限、执行工具；可选地处理工具结果、管理上下文（比如截断过长的输出）。

编程 Agent 的三个组成

  1. 模型加循环：LLM 提出动作，看结果，重复直到完成。一个 Agent 就是一个模型加一个循环。
  2. 工具和护栏：搜索、读、改、跑测试和 shell，外面套着权限、沙盒和审批。工具决定能力，护栏保证安全。
  3. 状态：此刻窗口里的内容，加上 Agent 在步骤之间带着走的东西。前者要组装，后者要保留。

三者共用一个上下文窗口，要一起设计。

三、工具设计：搜索和读取

Agent 该怎样找到相关代码？课件比较了四种方式。

glob 和 grep

Agent 反复调用 ls、glob、grep。好处是什么都不用建，也不用同步，永远反映仓库当前的真实状态。代价是要花很多轮次和上下文，而且按字面匹配，换个说法就找不到。例子是"修好登录超时"：grep -rn "timeout" src/ 在 12 个文件里找到 37 处；用 glob src/**/auth/*.ts 缩小到 auth/retry.ts；读这个文件，把 RETRY_MS 从 500 改掉。

语义搜索

一种是向量检索：把代码切成块，每块用嵌入模型变成一个向量，意思相近的文字向量也相近，查询时找最近的几块，所以"同样的意思、不同的说法"也能找到。另一种是结构化搜索，比如 Aider 的 repo map：给出文件树和按重要性排序的类与函数签名清单。查询时很快，代价是要建索引并随代码变化重新同步。例子："我们在哪里做限流？"第一次查询就返回 throttle.ts，即使代码里没出现"限流"这个词。

外部信号

源代码之外的证据：调用栈、失败的测试、git 历史。调试时这是精度最高的信号，但只有在这种信号存在时才有用。例子是结账时崩溃：调用栈指向 cart.ts 第 88 行，列出 3 个栈帧；打开这些位置，读 tax.ts 第 20 到 60 行，发现 applyTax 里的舍入问题；改完重跑 pytest tests/tax.py，通过，全程没用搜索。

语言服务器（LSP）

LSP（Language Server Protocol）是编辑器用来做"跳转到定义""查找引用"的那套服务。它查询的是编译器的符号索引：定义、引用、符号、类型，能正确处理 import、重载和重命名，而 grep 只能猜。代价是每种语言要常驻一个服务器，冷启动慢。例子是把 charge() 重命名为 capture()：查找引用，7 个文件里 42 处调用；执行重命名，连别名导入一起改；类型检查确认没有未解析的符号。

方式按什么找适合主要代价
glob / grep字面的名字和路径名字已知或能猜到每次搜索都花轮次和上下文
语义索引代码块的含义描述和代码用词对不上建索引和同步
外部信号调用栈、失败测试、git 历史已有报告指向代码只有部分任务有
语言服务器编译器的符号图修改必须跟着引用走每种语言一个常驻服务

实践中先用 grep，名字不够用时再上索引或 LSP。

四、工具设计：编辑代码

Agent 该怎样改代码？也有四种。

  • 整文件重写：模型重新生成整个文件，工具直接覆盖。没有补丁语法可以写错，每次都能应用成功。代价是输出量和文件大小成正比，没改的部分也可能被悄悄改动。例子：给 API 客户端加重试，读入 120 行的 client.ts，重新生成整个文件（实际只改了 4 行），第一次就能应用。
  • 统一 diff（补丁）：模型输出一个补丁，另一个工具负责应用。紧凑，便于审查，是人和 CI 本来就用的格式。代价是行号或上下文一旦对不上，补丁块就会失败。例子：在两个文件里提高重试上限，先读文件拿到行号，输出两个块共 6 行的补丁，用 git apply 应用。
  • 搜索替换：模型给出一段要精确匹配的原文和它的替换文本。输出量和改动大小成正比，与文件大小无关。代价是原文有歧义、已过时或空白不一致时会失败。例子：用 grep 确认 "retries = 3" 只出现一次，替换成 5，再读回来确认其余部分没动。Claude Code 的 Edit 工具用的就是这种方式。
  • 结构化（AST）编辑：AST 是抽象语法树，即编译器把代码解析成的树状结构。模型只说出要对某个符号做的操作，比如重命名、加参数，由工具在语法树上完成。和格式无关，不可能产生语法错误。代价是每种语言要有专门的工具，能表达的修改种类有限。例子：给 fetchUser() 加一个默认 5 秒的 timeout 参数，工具改写签名并更新全部 18 个调用处，解析和类型检查天然通过。

四种方式在 token 成本和稳健性（修改是否落在想改的地方）之间各有取舍：整文件重写在长文件上会漂移；统一 diff 遇到过时的行号会坏；搜索替换要求精确且唯一的匹配；AST 编辑覆盖的语言有限。

五、工具设计：执行

执行工具实际上就是一个 shell，是最强也最危险的工具。它的特点：可组合，一次调用就能串联、过滤、循环、重试；触及面广，文件系统、网络、包管理器、所有已装的程序；有持久性，文件和进程在调用结束后依然存在；破坏半径大，shell 能做的 Agent 都能做。

设计执行工具要考虑五点：失败信号，返回的错误要让 Agent 能据此行动；输出量，够用但不能太多；时长，长时间运行和后台进程怎样处理；预算，什么时候停止重试、把控制交还；隔离，代码在哪里跑、能接触到什么。

另外五种常用工具

  • 记忆和笔记：把发现写进文件，计划在压缩后依然存在。
  • 子 Agent 和委派：探索的结果是一个候选清单，而不是 40 次文件读取。
  • 网页搜索和抓取：先读本地已安装的源代码，再去网上找。
  • 浏览器和视觉反馈：截图渲染结果，再反馈给模型。
  • 询问用户：一个便宜的问题，好过一个自信但错误的补丁。

工具设计的最佳实践

  • 少而正交：工具功能重叠，模型会在它们之间犹豫。
  • 专用而非通用：search_orders(customer_id) 好过一个直接执行 SQL 的 run_sql 工具。
  • 输出省 token：截断、分页、摘要。工具设计就是上下文设计。
  • 错误信息要能教人：返回修复提示，而不只是"参数无效"。
  • 默认幂等：尽量让重试是安全的。幂等指同一个操作执行一次和执行多次效果相同。

只给一个 shell 行不行

课件引用了 SWE-agent 论文在 GPT-4 上的消融数据（解决率）：没有专门的编辑器 10.3%，只有 shell 11.0%，整文件查看 12.7%，保留完整交互历史 15.0%，专门设计的 SWE-agent 工具集 18.0%。也就是说，同一个模型，工具接口设计得好坏，结果能差出近一倍。讲者留了个悬念：在作业里自己去试。

六、从提示工程到上下文工程

课件列了一条术语演变线：2023 到 2024 年是提示工程，问的是"该怎样指示模型"，关注措辞、示例和输出格式；2025 到 2026 年是上下文工程，问的是"模型该看到什么"，关注检索、记忆、历史和压缩；2026 年出现了 Harness 工程，问的是"Agent 该怎样运作"，关注循环、工具、沙盒、重试和停止；再往后是目标工程，问的是"什么算成功"，关注目标、标准、约束和取舍。讲者补了一句：大家喜欢造新词，他用这些词是为了让学生遇到时知道是什么意思，不代表他赞同或喜欢它们。

提示工程的八种技术

  • 零样本：只给指令。例子是把客服工单分到 billing、bug、feature、other 四类，只回 JSON，不确定就选 other；"导出 PDF 时崩溃"得到 bug。适合常见任务、格式用文字说得清的情况；规则说不清时换成少样本。
  • 少样本：指令加几个做好的例子。比如先给"这个月被扣了两次钱"对应 billing、"能加个深色模式吗"对应 feature、乱码对应 other，再让模型分类新工单。适合输出形状特殊、规则演示比描述容易的情况；任务需要多步时换成思维链。
  • 角色设定：给模型一个身份来引导行为。比如"你是一位给高管审阅事故复盘的资深 SRE，指出证据缺口，不要猜测，最多五条"。适合语气或判断力重要、受众明确的情况。
  • 思维链：先列推理步骤，最后给答案。例子是"每周 3 个功能做 4 周，再每周 5 个做 2 周，一共多少"，分步算 12、10、22。适合任务确实有多步、错误来自跳步的情况。
  • 思维树：分支、打分、剪枝。比如提出 3 种降低结账延迟的方案，各按影响和工作量打 1 到 5 分，先展开最好的。适合有几条看似可行的路径、而且打分便宜的情况。
  • 自洽性：采样多次，多数投票。比如同一个"这张发票是否重复"的问题在温度 0.7 下问 5 次，得到 4 个 yes、1 个 no，一致率 0.8 达到阈值就采用；如果只有 3/5，就转人工。适合有唯一正确答案、而且答错代价高的情况。
  • 提示链：一次调用只做一件事，阶段之间的交接要校验。比如从邮件中抽取供应商、金额、日期；校验并补充供应商编号；起草回复。某一阶段的输出不符合格式，就只重试那一阶段。
  • 元提示：让模型来写提示。给它现有提示、10 个测试用例和其中失败的 3 个，让它在不破坏另外 7 个的前提下修复这 3 个，只返回新提示。课件的例子里新版加了一条明确的拒答规则，评估集从 8/10 变成 10/10。前提是有一个能打分的评估集。

选择顺序：先从简单的开始（零样本、少样本、角色设定），再加推理（思维链、思维树、自洽性），最后才是工程化的系统做法（提示链、元提示）。讲者也提醒，其中一些技术已经过时了，在作业里自己去发现是哪些。

写提示的四条做法：先简单再迭代，需要时才加上下文；分节，把背景、指令、工具、输出要求分开写，顺序是指令、分隔符、数据；具体而简洁，花哨的措辞没有用；把大任务拆成子任务，不要一开始就堆复杂度。另外，提示建议因模型而异，换模型就要重新调。

七、上下文工程

Karpathy 2025 年在 X 上的定义：上下文工程是一门精细的艺术和科学，要在上下文窗口里为下一步恰好放进正确的信息。

上下文是有限资源

三方面的成本：费用，每一步都要重新发送整个窗口，每一轮都要再付一次；延迟，提示越大，预填充和解码越慢，每一轮循环都变慢；注意力，窗口越满，模型越容易漏看信息，尤其是中间部分，所以上下文多不等于答案好。

课件给了两组数据。一组来自 Chroma 的 Context Rot 研究：随着输入 token 增加，简单查找任务的准确率从高位下降，加入干扰信息后降得更多，图上的终点分别是 73% 和 46% 左右。另一组来自 Liu 等的《Lost in the Middle》（TACL 2024）：把答案所在的文档放在 20 篇文档中的不同位置，放在第 1 篇时准确率 76%，第 5、10、15 篇时降到 61%、55%、59%，放在第 20 篇又回到 71%。答案在开头或结尾时模型找得到，在中间时最容易漏。

上下文窗口的组成

课件给了一个单轮 Agent 调用的示意预算：系统提示约 2K，工具定义约 6K，检索来的内容约 25K，项目环境约 8K，消息历史（用户、模型、工具结果）约 80K 并且还在增长。历史是最大、增长最快的部分。

四级管理手段

从预防性、无损的，到有损、不可逆的，依次是：准入、卸载、变换、压缩。越靠前越优先用。

准入：在门口把关，控制什么能进入窗口。做法包括定向检索（查询要窄，取字段而不是整篇文档）；整形工具输出（扔掉网页 DOM，只保留提取出的内容）；截断（整形做不到时才限制长度）；隔离（把原始的大块数据交给子 Agent 处理）。课件的例子：直接把原始网页 DOM 传进去要 48,000 token，在门口只提取价格和标题后是 900 token，小了 98%，答案一样。

卸载：不需要时不加载，内容保持"可取回"而不是"常驻"。做法包括渐进式工具定义（需要时才加载参数格式）；工具搜索（保留一个索引，按需取用）；工具输出卸载（返回一个句柄，需要时再加载内容）；任务清单外置（计划放在磁盘上）；持久记忆（笔记写到外面，只保留一个小索引）。例子：60 个工具的参数格式全部常驻要 42,000 token，换成索引加当前用到的 3 个后是 3,100 token，小了 93%，60 个工具仍然都能用。第二讲里 Skill 和 MCP 只先加载名字，就是这一招。

变换：有选择地丢弃历史，不做总结。做法包括去重（每个对象只保留最新状态，比如同一个文件读了三次，只留最后一次）；观察遮蔽（把 N 步之前的工具结果去掉）；滑动窗口（只保留开头和最近几轮）。例子：保留所有结果是 96,000 token，遮蔽和去重后只留最新状态是 24,000 token，小了 75%，而且没有经过任何总结。

压缩：最后的手段，让 LLM 来总结。滚动摘要是边走边把旧的工具结果总结掉；完整摘要是到上限时把整个历史重写一遍。三条注意事项：给输出留出余量；保住系统提示这个前缀不变（前缀一变，前缀缓存就失效）；压缩之后重新注入关键事实。再配合自动记忆，把关键事实存到窗口之外。

上下文失败的五种方式

课件引用 Drew Breunig 2025 年的文章《How Contexts Fail and How to Fix Them》：

  • 中毒：一个幻觉进入了窗口，后来被当作事实引用。
  • 分心：历史越来越长，Agent 开始模仿自己过去的动作，而不是思考新办法。
  • 混淆：无关的工具和文档把答案带偏。
  • 冲突：新信息和旧信息矛盾，两者都留在窗口里没有解决。
  • 漂移：真正的目标被埋没，被一个相近的子目标替换。

给失败命了名，修法就清楚了。

八、Agent = 模型 × Harness

模型能力决定上限，Harness 决定实际表现。课件引用了 2026 年的一篇论文（Lewis，《Same Model, Different Harness: Different Coding-Agent Results》）：同一个模型，只改进 Harness，SWE-bench Verified 的一个子集上从 43/169 提高到 72/169，SWE-bench Pro 的一个子集上从 31/316 提高到 72/316，后者是两倍多。改了的东西是：旧的工具输出被压缩；最近的观察保持可见；能检测到重复和停滞；卡住时进行干预。结论是，一些看起来是"模型失败"的情况，其实是上下文和控制循环的失败。

Agent 循环、提示、工具、上下文管理、失败处理都很重要，作业里会自己验证。下一讲讲多 Agent 设计、持久记忆、成本和安全。

九、选读：ReAct 之外的循环

  • ReAct：每一步都循环，思考、行动、观察。
  • Reflexion：失败之后才循环，尝试、评估、反思、重试。
  • 计划后执行（Plan-and-execute）：偏离计划时才循环，先计划，再执行各步，必要时重新计划。
  • 树搜索：不循环，一次展开很宽，从当前状态并行探索 A、B、C 几个分支，只保留最好的一个。
