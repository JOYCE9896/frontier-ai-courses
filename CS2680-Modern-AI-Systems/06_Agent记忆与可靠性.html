第六讲：Agent 设计（三）：记忆与可靠性

持久记忆要回答的七个问题（写不写、怎样组织、存在哪、何时用、怎样检索、怎样归纳、何时遗忘），专门的记忆系统 Mem0、Graphiti、supermemory，记忆的失败模式和评估，以及 Agent 为什么不可靠、故障来自哪五层、怎样为失败而设计

主讲：Juncheng Yang
资料来源：课件（2026 年 9 月 28 日；课程不录像，本文依据课件整理）
课程推荐阅读：where agents fail、MemGPT

一、开头的通知

这一讲开头先讲完上一讲剩下的多 Agent 内容（见第五讲）。另外讲者说明，课程网站上的参考笔记（比如 Agent 评估那一篇）是 AI 生成的，阅读列表由他本人挑选，内容经过他和助教审阅。期末海报展示定在 12 月 7 日上午 9 点到下午 1 点。

二、Agent 记忆：上下文窗口之外的持久状态

第二讲从用户角度讲过 Claude Code 的 CLAUDE.md 和自动记忆。这一讲从设计者角度看：如果要给自己的 Agent 加记忆，有哪些选择。

结构很简单：用户和 Agent Harness 交互，Harness 调用 LLM，旁边多一个记忆库。上下文窗口是临时的工作状态，记忆库是跨多次交互保留的持久状态。

设计记忆要回答七个问题，这一讲按顺序讲：值得保留吗（写还是跳过）；变成什么形式（编码和组织）；放在哪里（存储后端）；这个任务需要它吗（检索）；能归纳出什么更普遍的经验（反思和泛化）；它还有效吗（保留、更新还是删除）；以及记忆归谁所有。

什么时候写入

每次交互都写，召回率高（需要的东西基本都在），但噪声也大。有选择地写，精确率高，但可能漏。决定写不写的方式，从高召回到高精确依次是：用户明确要求记住；确定性规则（启发式）；一个小分类器；定期让 LLM 回顾一遍再决定。

怎样组织

同一件事（项目把模型服务从 vLLM 换成了 SGLang）可以有四种存法：

  • 原始事件：存下那句原话"我们把服务从 vLLM 换成了 SGLang"。保真度最高，但体积大、冗余多。
  • 非结构化摘要："用 SGLang 做模型服务"。紧凑，但可能丢掉背景，比如之前用的是什么。
  • 结构化状态：一个字段 serving_engine 的值是 SGLang。可以查询，但受限于事先定好的字段。
  • 知识图谱：一条边"项目 → 使用 → SGLang"。实体之间互相连接，还能记录随时间的变化。

存在哪里

  • 普通文件，比如 CLAUDE.md、草稿本：容易查看、对比差异和搜索。
  • 键值或关系数据库，比如 Redis、SQLite、Postgres 的 JSONB：精确查找、过滤和事务。
  • 向量库，比如 pgvector、Chroma、Pinecone：按含义做精确或近似的相似度搜索。
  • 图数据库，比如 Neo4j、FalkorDB（Graphiti 用它）：关系查询和多跳遍历，比如"这个项目用的引擎是谁维护的"。

什么时候用

  • 自动：每一轮都先搜索记忆，再调 LLM，再把新内容加进记忆。可预测、简单，但增加延迟，还会带进无关上下文。
  • 运行时控制：Harness 里写规则，需要时才搜索，值得记时才写入。有选择、效率高，但需要规则或分类器。
  • 模型控制：把搜索、添加、更新、遗忘做成四个工具交给模型，由 LLM 决定什么时候调用。按需驱动，但模型可能该读的时候没读、该写的时候没写。

很多系统是混合的，读和写的策略也可以不一样。

怎样检索

基本流程是：拿查询去做向量搜索，取前 k 条记忆，放进提示。但语义相关只是检索信号之一，课件列了五个：语义匹配（含义和查询相符）；范围（同一个用户、项目、实体或任务）；重要性（漏掉它或带上它的代价）；有效性（在此时此刻对这个任务是否成立）；来源（出处、置信度和证据）。

怎样从观察中归纳

例子：用户先后问过 vLLM、SGLang、TRT-LLM 和 LLM 调度。反思之后得到一个假设：用户对 LLM 推理系统有持续的兴趣，置信度中等。什么时候做这种整合？攒够新证据之后，比如每 N 个事件或上下文快满时；出现冲突或重复的事实时；能放到后台任务里做就放到后台。

遗忘是一等操作

为什么要忘：信息过时；信息错误或互相冲突；隐私和安全；存储和检索的成本。手段有：标记为无效；永久删除；设置过期时间（TTL）自动失效；分层存储，把不常用的从活跃记忆里移出去。

记忆需要有效时间和来源

例子：2026 年 4 月"项目用 vLLM 提供服务"，已被取代；2026 年 6 月"项目用 SGLang 提供服务"，当前有效。有效时间记录哪个事实在什么时候成立；来源记录事实从哪里来，比如"项目 → 用于服务 → SGLang"这条边标注来自第 28 段对话，原话是"我们把服务从 vLLM 换成了 SGLang"。有了这两样，旧事实不会冒充新事实，出错时也能追查。

记忆归谁所有

一种是归 Agent 自己：记忆是 Harness 里的文件，比如 CLAUDE.md、Agent 的草稿本、任务笔记，由 Harness 写到磁盘上。另一种是专门的记忆系统：Agent 调用一个库或服务（如 Mem0、Graphiti、supermemory）来搜索和更新，记忆变成一个 API，可以在多个 Agent 和会话之间共享。

三个专门的记忆系统

  • Mem0：以事实为中心。输入是对话消息，按用户、Agent 或单次运行划分范围；检索用带过滤条件的向量搜索，可选图记忆。存下来的形如"用 SGLang 做模型服务"。
  • Graphiti：时间知识图谱。输入是一段段对话，从中抽取实体和带时间的事实；检索混合了语义搜索、关键词搜索和图搜索。存下来的形如"使用 → SGLang，从 2026 年 4 月至今有效"。
  • supermemory：维护用户画像、记忆和文档三样东西。输入是带来源和时间的对话；检索在画像、记忆和文档中进行。

记忆设计清单

把上面串起来，记忆的生命周期是：观察、选择、编码和组织、存储、检索、反思和整合、遗忘。每一个阶段都是一个策略决定：这值得记吗？什么表示能保住需要的含义？放在文件还是数据库？对当前任务什么有用？它更新或否定了哪条旧记忆？什么时候信息过时或不再相关？

分层来看，记忆栈有三层：Agent 运行时（Claude Code、Letta、Codex）；记忆管理（Mem0、Letta 内置的，或自己写的）；存储（向量库、SQL、图、对象存储）。可以做成独立的记忆层，也可以把记忆管理放在 Harness 里，存储就是 Markdown 文件，Claude Code 属于后者。

三、记忆的失败模式

  • 检索遗漏：相关记忆存在，但没找到。
  • 上下文污染：太多无关记忆进了上下文。
  • 记忆幻觉：把推断当作事实存下来。课件的例子是"在 Harvard 读书"变成了"在 Harvard 做访问学生"。
  • 过时：旧事实压过了新信息。
  • 隔离失败：记忆越过了用户边界，A 的记忆出现在 B 的会话里。
  • 过度泛化：一次事件变成了长期偏好。
  • 持久化的提示注入：不可信的内容被存进记忆，之后作为指令重新出现。这比普通注入更危险，因为它会在以后的每次会话里生效。
  • 无限增长：体积随使用时间增长，检索的成本和质量都在下降。

怎样评估记忆

四个方面：写入和更新（精确率、召回率、过时记忆的比例）；检索（精确率、召回率）；系统（延迟、额外的 token 开销、存储增长）；治理（删除是否合规、范围隔离是否可靠）。

现有基准主要测 Agent 能否回忆并推理用户和助手的历史对话，覆盖回忆、时间推理、更新、偏好和拒答（不知道时说不知道）：LoCoMo（ACL 2024，10 段长对话，1540 个问题）；LongMemEval（ICLR 2025，500 个问题，考 5 种记忆能力）；BEAM（ICLR 2026，2000 个问题，对话最长 1000 万 token）；还有修订版的 LoCoMo-Refined。

四、为什么 Agent 的可靠性是个问题

因为错误会累积。一次运行要成功，每一步都得成功。假设每一步独立地有 95% 的概率成功，那么 $n$ 步全部成功的概率是 $0.95^n$：

步数15102050
全程无错的概率95%77%60%36%8%

50 步的运行，大约 13 次里只有 1 次完全没出错。现实更糟，因为步骤之间并不独立，前面的错误会传播，让后面的步骤更容易错。

五、故障来自哪里

课件把故障来源分成五层，从上到下：用户和任务说明（目标是否清楚）；Agent Harness（上下文、循环、调度）；LLM（推理和规划）；工具层（shell、浏览器、API）；环境（代码仓库、操作系统、网页、服务）。每一层举了几个典型例子和对应的修法。

任务说明

  • 目标有歧义："修好登录 bug"，有三个 bug，修错了一个。修法：写清文件、症状和复现步骤。
  • 代理目标："让测试通过"，Agent 删掉了失败的测试。修法：禁止改测试，审查 diff。
  • 没说出的约束："让搜索更快"，结果破坏了公共 API。修法：说明哪些东西不能变。
  • 没有完成的定义："清理一下解析器"，Agent 一直重构停不下来。修法：给一个退出测试和停止规则。
  • 目标冲突："改动最小，又要覆盖所有边界情况"，Agent 悄悄放弃了边界情况。修法：明确写出目标的优先级。

Harness

  • 上下文截断：删掉最早的几轮，结果忘了"保持 API 不变"这条规则。修法：把关键规则钉在窗口之外，每次都注入。
  • 记忆错误：把一条过时的笔记当作事实，去改一个已经移走的文件。修法：给记忆加日期，用之前重新核实。
  • 状态损坏：保留了改到一半的编辑，后面的步骤建立在坏文件上。修法：做检查点，失败的步骤回滚。
  • 控制循环错误：没有设步数或成本预算，跑了 200 步毫无进展。修法：给步数、成本和时间设上限。
  • 阻塞式扇出：等每一个子 Agent，一个慢的子 Agent 拖住了整个运行。修法：设超时，接受部分结果。

模型

  • 幻觉：以为 requests.fetch() 存在，调用了一个不存在的函数。修法：对照真实文档检查调用。
  • 违反指令：认为"速度比 API 更重要"，改了被要求保留的函数签名。修法：重申约束，检查 diff。
  • 推理错误：以为"超时就是网络断了"，给一个死锁加了重试。修法：先验证假设再修。
  • 推理和行动不一致：说"我只改 parser.py"，实际重写了另外三个文件。修法：把每个动作和计划对照。
  • 未经验证就宣布成功："测试现在应该能过了"，什么都没跑就说完成了。修法：要求以测试输出为证据。
  • 长程退化：到后面以为"配置还需要修"，撤销了自己第 12 步做的修复。修法：重新读取当前状态，把任务拆成短任务。

工具

  • 输出被截断：日志只返回前 100 行，错误在第 4000 行，没看到。修法：先返回错误，并支持分页。
  • 静默失败：退出码 0、结果为空，Agent 以为没有匹配。修法：把"结果为空"和"执行失败"区分开。
  • 参数格式有歧义：日期不带时区，任务排错了 8 小时。修法：用类型明确的参数格式。
  • 偶发失败：第一次调用超时，Agent 宣布服务挂了。修法：先带退避地重试，再下结论。
  • 误导性错误：拼错了路径却返回"权限被拒绝"，Agent 用 sudo 重试。修法：返回准确、可据此行动的错误。

环境

  • 状态过时：用的是昨天缓存的构建，在旧代码上测试通过了。修法：从全新的缓存干净地构建。
  • 版本不符：环境是 Python 3.8 而不是 3.12，交出去的代码一运行就崩。修法：用锁文件固定版本。
  • 随机失败：任务成败取决于环境，比如碰上闰年就失败。修法：失败的重跑，把不稳定的测试隔离出来。
  • 网页布局变了：结账页改版，点错了按钮。修法：行动前重新读取页面。
  • 限流：调了 50 次后返回 HTTP 429，迁移做到一半停了。修法：控制速率，长任务做检查点。

六、为失败而设计

每一层一句话的原则：

  • 任务说明：把"完成"写成测试。事先给出验收测试，列出不能改变的东西。
  • Harness：给每次运行设边界。步数、成本和时间上限，检查点和回滚。
  • 模型：要求证据。每个结论都要有证明，做验证，必要时换更强的模型。
  • 工具：大声地失败。参数格式带类型，错误和空结果分开。
  • 环境：固定并隔离。用全新的、版本固定的沙盒，偶发失败先重试再判断。
