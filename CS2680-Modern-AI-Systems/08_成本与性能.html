第八讲：进阶 Agent 设计（一）：成本与性能

把 Agent 的花费拆成一串乘积，逐项压缩：用户轮次、每轮步数、每步 token、每个 token 的单价；每种省钱办法的反作用；让 Agent 更快的五种办法与投机执行；三种 Harness 架构；以及八个开源和闭源 Harness 各自的独特设计

主讲：Juncheng Yang
资料来源：课件（2026 年 10 月 7 日；课程不录像，本文依据课件整理），以及课程网站的参考笔记 Cost-effective agents

10 月 5 日还有一场 Snowflake 的 Harsh Nilesh Pathak 讲企业场景下 Agent 开发与评估的客座讲座，没有公开课件，这里没有笔记。

二、钱花在哪里

这一讲只算 LLM 的费用，不算其他计算成本。先回忆一次会话的结构：一个会话有很多轮，每一轮从用户消息开始，中间是若干次"模型调用、工具调用"交替，最后回复用户。所以一轮用户对话里有多个 LLM 步骤和工具步骤。

照这个结构，总花费可以写成一串乘积：

$$\text{花费} = \text{用户数}\times\frac{\text{会话}}{\text{用户}}\times\frac{\text{轮}}{\text{会话}}\times\frac{\text{步}}{\text{轮}}\times\frac{\text{token}}{\text{步}}\times\frac{\text{价格}}{\text{token}}$$

前两项代表产品的普及和用户粘性，做产品的人希望它们增长。后面四项是工程师能压的：中间三项是 Agent 的轨迹长度，最后一项是单价。这一讲按"每个任务几轮、每轮几步、每步多少 token、每个 token 多少钱"的顺序逐项讲。

课件里用了一组很有意思的真实数据：全班同学在作业 1 和作业 2 里提交的 Claude Code 会话日志。下面每一节开头的数字都来自这份统计。

三、减少每个任务的用户轮次

同学们的数据：作业 1 有 68%、作业 2 有 75% 的会话只有一条提示，说明大多数人一个任务开一个新会话，这是好习惯；但也有少数"马拉松"会话超过 100 轮。

为什么轮次要紧？第 $k$ 轮要把前面 $k-1$ 轮的内容全部重新读一遍，所以总成本随轮数大致按平方增长。粗算一下：如果每轮新增的内容一样多，记为 1 个单位，第 $k$ 轮要读 $k$ 个单位，$n$ 轮总共读 $1+2+\cdots+n = n(n+1)/2$ 个单位。10 轮是 55，100 轮是 5050，轮数翻 10 倍，读的量翻近 100 倍。

用户之所以要回来再说一句，通常是三种原因：Agent 没有计划，做到一半停了，或者做完没有检查。对应的办法是：动手前先把目标和计划确认一次；把任务拆成子任务，每个子任务有自己的完成检查；交回之前先自己跑测试、检查输出。目标是让 Agent 自主做完，不需要用户中途再来。

四、减少每轮的步数

同学们的数据：每轮步数的中位数是 3（作业 1）和 4（作业 2），主要因为 effort（思考力度）设成了中或高；但有的轮次跑了将近 1000 步。

每次调用模型都要把完整上下文再读一遍，所以调用次数越少越便宜。三个办法：

  • 批量发出独立的调用。读五个文件，一步发五个读请求，而不是五步各读一个。课件的图里，"一步一个动作"要 4 次模型调用，"先计划，再并行调 3 个工具"只要 2 次。
  • 复用计划和 Skill。以前成功过的做法直接重放，不用重新推导一遍。
  • 一开始就加载需要的上下文。开头就把要用的文件读进来，而不是每一步读一个。

复用这条有一批研究：Voyager（2023）把可执行的技能存进技能库；ExpeL（2023）和 ReasoningBank（2025）从成功和失败的运行中提炼可复用的经验；Test-Time Plan Caching（2025）缓存并改写计划模板；Mem0、LightMem、SimpleMem 做持久的对话记忆。课件的提醒是：任务重复出现时复用才划算，维护记忆的开销和过时条目可能把省下的抵消掉。

五、减少每步的输入 token

同学们的数据：主 Agent 每步输入的中位数是 20 万到 30 万 token（作业 1 是 208K，作业 2 是 301K），第 90 百分位到 60 万到 70 万；子 Agent 的中位数约 8 万，第 90 百分位约 20 万。上下文累积得很快，到第 500 步左右已经有 65 万到 67 万 token。

还有一个数要单独拿出来看：作业 1 里 97.6% 的 token 是读缓存。模型输出比新写入缓存的输入（第一次预填充）少 5 倍左右，新写入的输入又比读缓存少 100 倍左右。典型的价格比例是读缓存 : 普通输入 : 输出 = 1 : 10 : 50。读缓存虽然单价最低，但量太大，依然是花费的大头。这也解释了第二讲那句"前缀缓存的读取占了大部分费用"。

核心原则是：留在上下文里的 token，以后每一步都要再付一次钱。办法分三类，和第四讲的上下文管理一一对应：

  • 扔掉过时的：截断过时的结果，遮蔽已经用过的工具输出，把旧轮次总结成状态。
  • 缩小进来的：压缩观察结果（保留错误，不要整份日志）；大的输出存成文件，只传路径。
  • 只加载需要的：有选择地检索，只放相关的工具和记忆；把探索交给子 Agent，只拿回摘要。

相关研究举几个有代表性的数字：ACON（2025）把峰值上下文降低 26% 到 54%；LLMLingua（2023）的提示压缩最多减少 20 倍 token，但 2026 年一篇实测文章指出只有在提示很长时才划算；Anthropic 的"用 MCP 执行代码"（2025）让 Agent 写代码在代码里过滤工具结果，一个例子从 15 万 token 降到 2 千；工具搜索（2025）减少 85% 的工具定义 token；程序化工具调用减少 37%。也有反面的发现：TRACE（2026）发现摘要会导致返工，因为丢掉的细节要重新找回来。

六、减少每步的输出 token

输出 token 单价最贵，办法是让模型少说：

  • 在提示里约束长度、格式和要省略的东西，比如"不超过 100 字""只返回 JSON""不要复述问题""不要解释推理"，或者在系统提示里写"简洁，除非被要求否则不讲背景"。
  • 在 API 调用里设硬上限，如 max_tokens=300。简单，但截断可能把答案切在半句话上，所以要和"简洁输出"的提示一起用。还有个坑：推理模型的思考过程也算输出，可能把上限用光。
  • 结构化输出：要求一个只含必要字段的格式，比如只有 action 和 argument 两个字段，并限制枚举值和可选字段，让模型没法多写。对用工具的 Agent 特别合适，因为工具调用周围的说明文字纯属成本。
  • 按步骤调整推理力度：查找和格式化用低力度，规划和调试用高力度，可以每次调用分别设置推理力度或思考 token 预算。

相关研究也有一个提醒：《Let Me Speak Freely?》（2024）发现过于严格的格式会损害推理。还有一类办法是只输出变化的部分，比如在 diff 和整文件之间自适应选择、在语法树层面编辑，以及让 Agent 自己造可复用的工具，有一篇 2026 年的工作报告输出 token 减少了 58%。

七、降低每个 token 的单价

缓存和批处理

以 Claude API 为例，以普通输入 token 的价格为 1：输出 token 是 5 倍；批处理输入（不要求马上返回，可以等几小时）是 0.5 倍；缓存命中的输入是 0.1 倍；批处理加缓存是 0.05 倍。所以两条做法：保持前缀稳定，即系统提示、工具定义和早期历史不要变，让缓存一直命中；能等的就批处理，比如评测、补数据、批量任务。

模型路由

让便宜的模型做它能做的事，有三种方式：事先选，每一轮生成之前选定一个模型，通常用在偏好数据上训练的路由器，还可以顺便选 Agent 角色（代表工作：RouteLLM、MasRouter）；失败才升级，先试便宜模型，检查不过再换更强的，检查可以是学出来的打分器、模型自查或执行反馈（FrugalGPT、AutoMix、EcoAssistant）；每一步重新选，随着轨迹变长，根据历史和预算重新选择模型，或者让一个小的编排模型把各个模型当工具来调（ToolOrchestra 等）。难点在于：便宜模型的一个规划错误，可能浪费后面很多步。

后面几讲的系统技术

模型层面有混合专家与稀疏化、量化、剪枝、蒸馏、针对负载的微调；推理引擎层面有投机解码、KV 缓存优化、更好的请求调度；硬件层面有更快的内核、更好的内核调度、专用加速器。前缀缓存的代表系统是 vLLM 的 PagedAttention 和 SGLang 的 RadixAttention，第九讲之后会讲。

八、每一笔节省都有反作用

  • 压缩和重建：被丢掉的文件会被重新读一遍，而且摘要会改写上下文，导致缓存失效重写。
  • 路由和更长的失败：便宜模型的一个坏计划，可能多出很多步或者一次失败的尝试。
  • 子 Agent 和重复上下文：每个子 Agent 都要重新读共享的文件和指令。
  • 投机和白做的工作：猜错的会浪费 token，还会和正常工作争抢同一批工具。

所以净节省等于毛节省减去反作用，两者都要在同一批任务上量。

给每个任务设预算，没进展就停

课件给的示例上限（只是示意）：每个任务 10 美元、80 次模型调用、15 分钟工具时间、每一步最多重试 2 次。上限应该从实际运行记录里定，比如取成功任务第 95 百分位的 2 倍。停止条件：验证通过；连续 N 步没有新的测试通过；同一个错误反复出现；碰到上限时，带着一份摘要把任务交出去。一个带摘要停下来的任务，比一个失控的任务便宜。

真的需要 LLM 吗

每次步骤都一样，就写脚本，让 LLM 写一次代码，之后直接运行；输入格式固定，就用正则、解析器、模板，每次调用零成本；只需要输出一个窄的标签或分数，就训练一个小分类器，比如梯度提升树；流程固定、推理很少，就把工作流写成脚本，只在需要的步骤调 LLM。只有某一步确实需要推理时才用 LLM。

九、让 Agent 更快

更快的 Agent 通常更便宜，但不总是。完成时间取决于关键路径，而不是所有步骤的时间之和。串行时，总时间约等于排队、准备、预填充、推理、工具、编排各段相加；并行时，总时间约等于最长那条链。两个反直觉的地方：便宜的小模型可能更慢，因为它要走更多步；并行花的钱更多，等待少了，总 token 却多了。

五个方向：

  • 加速 LLM 服务。前面所有省钱的技术也都降低延迟：更少的轮次、步数、token，缓存和更小的模型。
  • 改进编排。异步执行，工具在跑时就开始下一步；保持会话常驻，跨步骤一直开着同一个 shell 或浏览器；流式和流水线，模型回复还没结束就开始执行工具调用；服务同址部署，工具和模型跑在同一台机器上。
  • 加速工具调用。构建、测试、页面加载可能比模型调用还慢。缓存工具结果，让重复的读取和搜索命中缓存；重计算放到服务器而不是笔记本上；用更快更便宜的工具做同样的事；卡住的调用及时超时。调模型之前，先量清楚每一步工具花了多少时间。
  • 并行。独立的工具调用放在同一步发出，读三个文件的等待时间变成三分之一；独立的子任务交给并行的子 Agent，再合并摘要。只有互不依赖的工作能并行，共享状态需要合并步骤。
  • 投机执行，下面单独讲。

投机执行

思路借自 CPU 的分支预测：一个便宜的模型先猜下一个动作，在主模型还在思考时就提前执行；主模型给出决定后对比，猜对了结果已经就绪，等待时间省掉；猜错了就丢弃，代价是一次白做的调用。猜得准、动作能撤销时才划算。开放问题是：在 GPU、CPU 和 API 预算都有限的情况下，怎样调度这些投机调用，让关键路径上省下的时间多于浪费的工作。

投机的范围从小到大：只猜下一个是哪个工具（SPORK）；猜工具加参数（PASTE、Speculative Tool Calls）；猜任意动作或 API 响应（Speculative Actions，ICLR 2026）；同时走几条可能的分支（B-PASTE）；提前执行一整段多步轨迹（Speculative Macro Commit）。预测来源有三种：用一个小的草稿模型预测大模型的下一步；让同一个模型在推理早期分叉出一个探针，预测它自己之后会调用的工具；从历史轨迹里学，下一个工具由过去的模式预测，参数从上一步的结果里填。另外有无损和有损之分：无损的总是先验证再保留，有损的（如 SPAgent）会跳过部分检查。

两个例子。PASTE 从历史里发现，"搜索"之后通常是"访问第一条结果的网址"，再"提取页面"。所以搜索一开始，它就预测下一步是访问，网址从搜索结果里填，模型还在生成时访问就已经在跑了。SPORK 则利用了这样一个现象：模型在一段 2000 token 的思考里，往往很早就能看出它要调用什么工具，于是分叉出一个探针提前发起这个调用，等主模型真正输出调用时，结果已经在等着了。

循环地优化

运行并剖析，记录每一次调用、每一个 token、每一个工具和每一段等待；度量，搞清楚成本和延迟来自哪里；一次只改一样东西，比如压缩、路由、缓存或并行；在同样的任务上重新评估成功率、花费和第 95 百分位延迟；然后重复。讲者特别提醒作业 4 要用这个方法。

十、三种 Harness 架构

第三部分讲 Harness 本身怎样组织。三种架构的变化方向是：职责逐渐移出 Agent，从代码变成接口，再变成服务。

  • 单体式：记忆、工具、上下文、规划、执行全部在一个运行时里，Agent 拥有一切。好处是容易实现和调试，通信和执行开销都小，内部状态容易共享。坏处是很难单独替换一个部件，部件之间紧耦合，很难在多个 Agent 之间共享基础设施，也很难强制隔离。
  • 模块化：Agent 仍然控制循环，但通过接口访问各个部件，比如记忆接口背后接 Redis，工具接口背后接 MCP，上下文接口背后是滑动窗口，沙盒接口背后是 Docker。想把 Docker 换成 Firecracker，只换一个提供者就行。好处是部件容易替换，便于测试和扩展，职责清楚，第三方实现能插进来。坏处是控制器仍然掌握整个生命周期，协调逻辑越来越复杂，故障域仍可能共享，要联合调优还得改控制器。
  • 微内核：一个很小的运行时只管状态、协调、调度和安全，记忆、工具、执行都是外部服务，通过标准协议访问，可以跑在不同的容器或机器上。好处是各服务独立扩展，故障隔离更好，隔离可以更强（前提是真的强制执行），基础设施可以集中管理和共享。坏处是通信开销更高，要处理的失败模式更多，端到端调试更难，需要标准化的协议和生命周期。

以"运行一段 Python"为例：单体式直接在本地执行，跳数最少，但难以隔离；模块化调用沙盒提供者，换提供者不用改 Agent；微内核把执行请求发给执行服务，由它分配沙盒、执行、返回结果，沙盒的分配、隔离和生命周期都归执行服务管。适用场景上，单体式适合独立的 Agent，模块化适合 Agent 框架，微内核适合多 Agent 基础设施。

十一、八个 Harness 的独特之处

最后课件挑了八个 Harness，各讲一两个别人没有的设计：

  • Claude Code（Anthropic，TypeScript，闭源）：围绕 Claude 的策略层和带类型的 Hook。
  • Codex CLI（OpenAI，Rust）：沙盒优先、再问用户。命令默认在不能联网的沙盒里执行，只有要出沙盒时才请求批准。补丁格式由一套 Lark 语法规定，应用补丁时分四轮匹配。
  • DeepSeek Harness（TypeScript）：一切皆插件，连循环本身也是，可以用 YAML 分层替换任何插件。每个请求都是会话日志的一个冻结视图，Harness 只往日志里追加条目。编辑采用比较并交换：如果文件在模型上次读取后被改过，编辑就失败。
  • OpenCode（SST，TypeScript 加 Bun）：Harness 是一个服务器，终端界面、SDK 和网页应用都调用同一个 OpenAPI HTTP 服务。模糊编辑有九种替换器，从精确匹配逐级放宽到锚点匹配，但匹配范围过大的模糊编辑会被拒绝。每一步都在一个影子 git 仓库里拍快照，所以 /undo 能恢复文件，而不只是聊天记录。
  • Pi（TypeScript）：极简核心，只有四个工具，没有 MCP、子 Agent 和审批，其余功能都靠扩展。它会发保活请求让缓存不过期，但只在预计能省 0.05 美元以上时才发。它的 pi-ai 库支持 10 种接口协议上的 42 家服务商，被另外三个项目复用。
  • oh-my-pi（TypeScript 加 Rust，Pi 的分支）：hashline 编辑，每次编辑只给一个 4 位十六进制的文件标签和行号，模型不用再把旧文本敲一遍。一个 shell 在所有调用间常驻，原生工具提供搜索、语法树、LSP 和调试器。还有特别的上下文手段：snapcompact 把旧历史转成图片；TTSR 在输出匹配某个正则时停下重试。
  • OpenClaw（TypeScript）：一个面向聊天渠道的助手网关，27 个聊天渠道的消息按会话汇入各自的队列，运行期间新来的消息怎么处理由队列模式决定。压缩之前先跑一个静默轮次，把带日期的笔记写进记忆；回忆时全文搜索和向量搜索一起用。安全上用围栏隔离不可信文本，一旦读了网络内容，这一轮就被标记为"受污染"，并监控预先埋下的机密哨兵，看有没有被泄露。
  • Hermes Agent（Nous Research，Python）：一个会学习的分叉，在后台检查每个被提醒过的轮次，然后修改记忆和 Skill。它的压缩最早，上下文到 50% 就开始压缩，是八个里最早的。执行工具调用之前，先把调用记录写进会话数据库，再产生任何副作用。
