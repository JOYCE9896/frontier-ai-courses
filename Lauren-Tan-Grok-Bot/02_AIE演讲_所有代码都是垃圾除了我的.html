Lauren Tan：所有代码都是垃圾（除了我的）

Grok Bot 团队一个月合并 11,000 个 PR、回滚率约 0.5%，靠的是架构约束、lint 规则、运行时验证和形式化验证，先把这些地基打好，再去搭软件工厂

节目：AI Engineer · 主持：AI Engineer Code Summit 2026 演讲 · 嘉宾：Lauren Tan（网名 poteto，演讲里自称 Potato；SpaceXSI 的 Grok Bot 工程负责人）· 发布日期：2026 年 11 月 14 日 · 时长：17 分 31 秒 · 整理：Joyce（@JOYCE9896）
资料来源：All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI（本文依据节目英文字幕、章节和视频描述整理，是中文转述，不是逐字翻译；观点属于说话人，内容以发布当天为准）

这一期的内容

这是 Lauren Tan 在 2026 年 11 月 AI Engineer Code Summit 上的演讲单独上传版，17 分钟左右，没有主持人提问。她在 SpaceXSI（视频标题的写法）做 Grok Bot，这是一个 Electron 桌面应用，之前她在 Cursor 工作，演讲里有好几处拿 Cursor 代码库里的教训做对照。字幕里 Grok Bot 被拼成 Grokbot、Graph Bot、Grabot、Growth Bot、Gulp bot 等，下文统一写 Grok Bot。同一场演讲在 AI Engineer 代码峰会第一天直播笔记里有一段简版，这一页是按单独上传的视频整理的完整版。演讲没有广告插播。

演讲围绕一个问题：一个人一个月能往生产环境发几千个 PR 时，怎样保证代码不变成一堆 slop（AI 圈的说法，指大量产出、质量低的内容）。她的回答是一个“信任倒金字塔”：先用代码本身和 lint、类型、测试这类确定性手段约束 Agent，再叠加运行时验证和形式化验证，最后才是规则、Skill、AGENTS.md 这类文字。她给出了团队的数字（上个月 11,000 个 PR、227 名贡献者、回滚率稳定在约 0.5%、每天一个稳定版），最后讲了用 Grok Bot 搭“外循环”的一个例子：每次发版自动开一个 Cursor 项目对整个应用做模糊测试，找到 bug 就开修复 PR 并自动合并。

01. 把垃圾变成金子：一个月 3000 个 PR

节目位置 0:00:00–0:02:03 · Turning slop into gold

开场

她先让台下举手：有多少人看过别人写的代码，觉得全是 slop。她说她也一样，但今天要说服大家，slop 可以变成金子。接着她说上个月她做了件“疯狂的事”：自己一个人往生产环境发了 3000 个 PR（pull request，代码合并请求）。

人人都能当“编程机器”

她说有 Agent 之前，没人在意产量，只有少数特例。她在前一家公司把这类人叫作 coding machine（编程机器），举的例子是 Bret Taylor，据说他一个周末重写了整个 Google Maps。有了 Agent 以后，谁都可以是编程机器。

她的论点是：软件工程师这份工作的“meta”，变成了在产量大幅上升的同时，维持甚至提高代码质量。有人把这叫作软件工厂（software factory，指让大量 Agent 自动写代码、测试、合并的流水线），她更愿意简单地把它看成信任问题。她强调这里说的不是盲目信任，是投入精力建设 Agent 的工作环境，直到你能相信 Agent 会做对。

她说这要花不少功夫，她自己用了六个月，才做到能发出几千个 PR，其中很多是她睡觉时发出去的。她认为别人做到这一步会比她快得多。

02. 信任倒金字塔与代码库质量

节目位置 0:02:03–0:05:00 · The trust pyramid and codebase quality

从低信任到高信任：四层

她用一张倒金字塔图讲在 Agent 环境上该把时间花在哪里，从最宽的一层往下：

  • 前两层是确定性的，用代码本身来约束。第一层是好的 API 设计、架构、重构。第二层是 lint 规则（lint 是对源代码做静态检查的工具，按规则报出写法问题）、类型系统、编译器和各种测试。两层合起来限制 Agent 能做什么，让它默认就做对。
  • 第三层是验证，包括运行时验证和形式化验证。用来找 bug、检查系统里应该一直成立的性质和不变量，也用来检查 Agent 有没有理解你的目标和意图。
  • 最后一层才是少量文字：规则、Skill、AGENTS.md（放在代码仓库里、写给编程 Agent 看的说明文件），也就是需要判断力的东西。

代码库是 Agent 最大的输入

她说 Agent 的输出取决于输入，输入质量很重要，而代码库刚好是最大的输入之一。所以每次纠正 Agent 时，先想能不能把这次纠正变成一个确定性检查，别再往规则或 AGENTS.md 里加一行。写在代码里可以复现，也更值得信任。

代码库像花园

她用花园来打比方。以前代码一次来几个 PR，她记得 2024 年上班时要审同事写的 3 个 PR，现在这个数字更接近 300。每个工程师现在相当于几百甚至几千个 Agent 组成的团队，代码来得太快，几乎是连续的流，像有机体在生长。她放了一张图（画面演示，字幕未说明细节），说你给代码库设下的约束和护栏，是新代码围绕着生长的混凝土地基，就像图里那栋建筑。所以软件工程师的工作在很多方面越来越像园艺。

因为代码是 Agent 最大的输入，任何变通写法、反模式、废弃代码和技术债，都可能被下一个 Agent 照抄，因为在它看来这就是代码库里的既定模式。她说这就像花园里长了杂草和害虫，一不留神就到处都是。结论是让代码库尽量干净，Agent 抄到的都是好东西。

03. Dune 与可强制执行的架构

节目位置 0:05:00–0:06:56 · Dune and enforceable architecture

Dune 是什么

Dune 是团队为 Grok Bot 写的客户端框架，用来落实她说的“有机架构”。她说它在技术上没什么特别，可以理解成 Electron 应用版的 Next.js（Next.js 是一个流行的 React Web 框架；Electron 是用网页技术做桌面应用的框架）。它有意思的地方在于，里面写进了大量约束和 lint 规则，编码了团队做桌面应用学到的教训。

教训一：需要细腻判断才能用好的东西，往往出 slop

她举的经典例子是 React 的 useEffect（React 里处理副作用的 Hook）。它有适用场景，但经常被误用，有人开玩笑说用好 useEffect 得有个博士学位。Agent 也用不好。他们的做法是在产品代码里直接禁用，只允许在 Dune 内部 API 的少数地方出现。她说这类问题因此被“整类消除”，代码审查时再也不用去抓。

教训二：用目录结构传递上下文

在 Cursor（同样是 Electron 应用）里他们看到一个反模式：Agent 常把主线程（main）代码引入渲染线程（renderer），造成长任务和界面卡顿（jank）。在 Grok Bot 和用 Dune 做的应用里，他们把这件事做成死规矩：两个顶层目录直接叫 electron-renderer 和 electron-main（字幕写作 Electron renderer、Electron main），两者之间的互相引用被依赖图分析器和几条 lint 规则禁止。她说这些 lint 规则很容易写，但代码审查时就少了一件要想的事。

04. 用 lint 规则替代代码注释

节目位置 0:06:56–0:09:40 · Replacing comments with lint rules

Agent 拿 Markdown 给自己找理由

她说一件让她意外的事是 Agent 对 Markdown 的用法。文档、代码注释、规则、Skill，Agent 会在这些地方写下自己为什么不做正确的事。另一种情况是 Agent 对你的一次小纠正反应过度，把它当成永远不能破的硬规则。

Cursor 的定时器例子

在 Cursor 里，Agent 很爱用命令式定时器，比如 setTimeout、requestAnimationFrame、requestIdleCallback，拿来当快速补丁。她说这些补丁掩盖的是一个架构冲突：VS Code 的命令式风格和 React 的声明式风格合不来。所以当时的架构选择让客户端性能和 Agent 的表现都变差了。

她解释，做过 JavaScript 性能优化的人都知道，大量定时器被快速创建又销毁，会引起很多次 major GC（大规模垃圾回收），带来卡顿。更糟的是 Agent 写了很多代码注释（她的幻灯片上用红色标出，画面演示，字幕未说明细节），解释为什么这个快速补丁是合理的。结果定时器扩散到各处，应用性能明显下降。

Grok Bot 禁掉 99% 的注释

Grok Bot 吸取了这个教训，禁掉了 99% 的注释。她给的理由：

  • 注释很容易过时。
  • 人其实也不怎么读那些 slop 注释。
  • 注释给了 Agent 一个逃生口，让它可以为“因为难所以不做对”找理由。
  • 她说最糟的是注释没法强制执行。“我要告诉下一个 Agent 别做某件事”听起来是好意，但最后都变不成你能信任的东西。

现在 Grok Bot 和 Dune 里用 lint 规则代替，报错信息写得清楚、有用，告诉 Agent 去修根因，别绕着问题打补丁。

总原则

团队的通用原则是：每纠正 Agent 一次，就把它变成一个确定性检查，或者想办法通过更好的 API 设计、更好的架构，在代码层面整类消除这个问题。她说这样做的次数够多，代码审查要盯的东西就越来越少，到某个时候会发现已经没什么可审的了，可以让 Agent 自己合并大部分 PR。

05. 运行时验证与功能地图

节目位置 0:09:40–0:10:50 · Runtime verification and feature maps

代码审查缩成了看验证产物

她说验证是让 Agent 更自主、也让人更信任它的工作的一大块。他们的代码审查流程现在主要是看验证产物（verification artifacts）：视频、截图、图表、形式化验证结果。

运行时验证

最基础的是运行时验证。她说这只是个花哨的说法，意思是让 Agent 能自己把代码跑起来，并使用人类开发者也用的调试工具，比如 Chrome DevTools Protocol（Chrome 开发者工具的远程控制协议，程序可以通过它操作和检查浏览器或 Electron 页面）。

功能地图与自定义 CLI

  • 他们的运行时验证 Skill 里有一份 feature map（功能地图），类似站点地图，从用户视角列出应用里所有可用的功能。有了它，你说“左侧栏里那个东西”时 Agent 不用猜，人和 Agent 之间有了共同词汇。
  • 这些 Skill 里还带了自定义 CLI（命令行工具），Agent 每次复用同一个 CLI 和驱动程序，省 token，而且这些工具本身可以测试。

06. 形式化验证与 UI 测试

节目位置 0:10:50–0:11:51 · Formal verification and UI testing

TLA+ 和 Lean

形式化验证是用数学方法证明程序或设计满足某些性质，区别于跑测试抽查。她说他们最近开始用：

  • 用 TLA+（一种描述并发和分布式系统设计的规格语言，配有模型检查器，会穷举状态找违反规则的情况）对主要用户流程做模型检查，例子是跨多个设备、多个平台的通知。
  • 用 Lean（一种定理证明器和编程语言）证明某些算法。例子是团队自己写的虚拟化库（virtualization，长列表只渲染可见部分的技术），他们用 Lean 检查它不会出现闪烁或抖动。

她说整体还在试验阶段，看起来很有希望，已经靠形式化验证找到了不少 bug，但这不是银弹，他们把它当成 Agent 环境里又一种工具、又一层。

UI 的基于属性测试

她放了一段很快的视频（画面演示，字幕未说明细节），讲他们刚开始做的另一件事：对 UI 做基于属性的测试（property-based testing，随机生成大量输入，检查某条性质是否始终成立）。用的库叫 Bombadil，也已经抓到几个 UI bug。

07. 把 token 花在验证上

节目位置 0:11:51–0:13:32 · Spending tokens on verification

Cindy 的两条推文

她引用了一位字幕里叫 Cindy 的人的推文（具体身份字幕未说明）。6 个月前 Cindy 说自己没法信任 Agent，因为细微的 bug 一直被合并进去，Lauren 认为她当时缺的是验证流程。6 个月后 Cindy 说，她每天 70% 的 token 用在验证上。Lauren 说这和她自己看到的一致，她的大部分 token 也花在验证上。

方法都不新，只是变便宜了

她指出 Cindy 流程里（画面上列出，字幕未说明细节）的东西没有一样是新技术，都是好的软件工程工具。过去它们难理解、难写、难维护，成本高到用不起，Agent 把这个成本大幅降了下来。所以她说软件测试和验证正在进入黄金时代，因为 Agent 让测试的覆盖程度远超过去在经济上划算的程度。

形式化验证也帮人理解意图

她补充，形式化验证还能帮你想清楚产品应该怎样运作，以及 Agent 是否真的理解你的意图和目标。她在自己的插件 pstack（potato stack，Cursor 插件仓库里的一个目录）里做了一个新 Skill 叫 statechart（状态图），从用户视角把状态机可视化。她说和团队提供的视频、截图放在一起审，比看代码容易得多。说到这里她因为切回了前一张幻灯片道了歉。

08. 11,000 个 PR 与 0.5% 的回滚率

节目位置 0:13:32–0:15:11 · 11,000 PRs and a 0.5% revert rate

回报是什么

她把这一段叫作“应许之地”，讲这些投入换来了什么。Grok Bot 团队的数字：

  • 上个月团队往生产环境发了 11,000 个 PR，她自己说这是个离谱的数字。
  • 客户端发版节奏也加快了，大约每天切一个新的稳定版。
  • 核心团队的产出多了很多，还多了不少“顺手贡献者”（casual or drive-by contributors），他们不一定有多少上下文，但也在提交代码。
  • 10 月有大约 227 人至少提交过一个 PR。

没有变成一堆 slop

她预料台下会想：速度这么快，不会乱套吗，不会全是 slop 吗？她的回答是，被回滚（revert，撤销已合并的改动）的 PR 按比例算反而变少了，稳定在约 0.5%。

她觉得更有意思的是性能。在这样的发版节奏和 PR 数量下，Grok Bot 的性能不仅稳住了，和刚上线时相比在好几个维度上还变好了：启动、打字、开新对话、切换对话都更快了。她提醒 Grok Bot 目前还是 Electron 应用，性能有天花板，但已经比外面很多 Agent 界面快得多。她的评价是，对一个开发速度这么快、贡献者这么多的 Electron 应用来说，这个结果相当不错。

09. 先打地基，再搭软件工厂

节目位置 0:15:11–0:17:31 · Foundations before software factories

她的建议顺序

  1. 在动手搭软件工厂、把能自动化的都自动化之前，每次纠正 Agent，先试着通过改进代码库来纠正。
  2. 先加一条 lint 规则，防止反模式新增，然后再把老的写法清理掉。
  3. 把验证这一块做扎实。

她说这些工作本来就是自动化的前提。如果内循环（单个 Agent 写代码、自测的那一圈）产出 slop，把这个循环自动化只会产出更多 slop，然后就得往问题上砸越来越多的 token，大家都知道那很贵。等代码库、静态分析、运行时验证和形式化验证这些投入到位，很多事情会变得可行，在这些基础上搭自己的工厂会很容易。

用 Grok Bot 搭外循环

最后她介绍 Grok Bot 可以用来搭“外循环”（调度很多 Agent、决定什么时候跑什么的那一层）。她列了几样功能：

  • 大量连接器（connectors，接入外部服务）。
  • routines（定时或触发式任务），可以启动 Cursor 的云端 Agent。
  • projects，可以编排几百甚至上千个 Agent。

她举的例子：现在每次切新版本，Grok Bot 会自动为团队开一个新的 Cursor project，对整个应用、整个构建做模糊测试（fuzzing，用大量随机输入和操作去触发异常），像真实用户一样运行和使用应用来找 bug。然后为找到的每个 bug 开一个修复 PR，并且自动合并。她自己也说听上去很疯狂。

她说这之所以行得通，是因为代码库已经足够好，PR 默认就倾向于是好的，他们合进去的大部分产品代码已经不需要人深度审查。她的结尾是：有了扎实的地基和好的有机架构，就能把 slop 变成金子，在不牺牲质量的前提下高速发版。最后她再次自我介绍：网名 Potato，也叫 Lauren。
