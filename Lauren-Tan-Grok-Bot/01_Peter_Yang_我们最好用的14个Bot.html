Peng Zheng 与 Lauren Tan：Grok Bot 团队自己最好用的 14 个 Bot

Grok Bot 的设计负责人和工程负责人各自打开自己的账号，演示工作和生活里在用的 Bot：Peng 的幕僚长、设计师和写作 Bot，Lauren 的 Bot 设计师 Dr. Eggbot、私人助理和一整组工程 Bot，以及怎样一步步把更多工作交给 Bot

这一期的内容

01. 开场：Grok Bot 团队自己用的 Bot

节目位置 0:00:00–0:01:23 · The bots that the Grok Bot team actually uses

开头 40 秒是剪辑好的预告，取自后面的几句话：Peng 说他会把 PM、设计等三个 Bot 拉进一个群聊让它们讨论；他自己只做前 5%，画一个关键帧，然后让 Bot 扩展成完整流程；Lauren 说这套东西让她能编排很大的 Agent 群，有时 PR 已经合并了她才去看；以及她说“归根到底是信任”。

正片开始，Peter 介绍两位是 Grok Bot 团队的设计和技术人员，这期想看三件事：他们工作和生活中的 Grok Bot 配置，怎样用 Grok Bot 来设计和开发 Grok Bot 本身，以及社区里最让他们意外的 Bot。Peter 说 Grok Bot 是他见过的第一个“常驻的个人电脑”产品，然后请 Peng 先展示。

02. Peng 的幕僚长 Bot：买耗材、挂二手、管邮件和日历

节目位置 0:01:23–0:06:31 · Peng's chief of staff bot buys supplies and lists gear

按工作和生活分类，常用的置顶

Peng 说他在数字世界里的事几乎都交给 Grok Bot。他把 Bot 分成工作和生活两类，最常用的几个置顶。“Chief of staff”（幕僚长）是他的默认入口：不知道该交给哪个 Bot 的任务，就先发给它。

买 3D 打印耗材并更新库存表

几天前他让幕僚长买 3D 打印耗材（filament）。Bot 买完之后，还按他的要求更新了他在 Notion 里的库存数据库。那个数据库记录他手上各种颜色的耗材。

一句话挂卖 DJI 麦克风

他觉得把几个任务串在一起交出去最有用。例子是在 Facebook Marketplace 上卖掉一个 DJI 麦克风。他只发了一张照片，在一条 prompt 里交代了几件事：

  • 去官网查这个型号的最新价格；
  • 查他所在地区最低的挂售价，看看竞争对手；
  • 学习他过去写二手描述的方式；
  • 发布这条新的挂售；
  • 如果没人感兴趣，每周自动降价 5 美元。

他说有意思的是，到写描述那一步，幕僚长自己知道去问他的写作 Bot（writer bot），问 Peng 过去是怎么写 Marketplace 描述的；它也会去研究别人怎么卖同类东西，最后把挂售发出来。过去这五步都得自己手动做，现在不光能委派单个任务，还能让它把一串任务连起来做。

替代邮件和日历

他说 Bot 正在替代他的邮箱。他会问“今天收件箱里有哪些待办”，邮件本身还是他自己管，但其中他认定 Bot 能做的事就交出去。比如要给朋友转晚饭钱，他就让 Bot 去付。如果 Bot 没有对应账号的权限，会弹出一个登录页，他接管 Bot 的电脑登录一下，之后由 Bot 完成。

日历也一样。约人喝咖啡时，修改日程、新建活动、订会议室，他都是截一张图发过去，让 Bot 去加到日历里或者修改。

置顶的设计师 Bot 和写作 Bot

Peter 注意到他置顶了 designer 和 writer。Peng 说屏幕上是一个演示账号，配置和他自己的账号一样。最常用的就是这三个：幕僚长负责管理其他所有 Bot；他每天待在设计工具里，所以设计师 Bot 是他的主力，用来一起头脑风暴、让它出不同的设计方案，讨论之后还让它去执行。写作 Bot 则因为他英语不是母语，很多邮件和 Slack 消息发之前让它润色。Grok Bot 里有 Slack 和邮件的聊天组件（chat widget），草稿直接显示在对话里，他可以审阅、发送或决定怎么改。

03. 把 PM、设计、工程 Bot 拉进同一个群

节目位置 0:06:31–0:10:07 · Putting PM, design, and eng bots in the same room

群聊讨论“猫语翻译”App

Peter 问屏幕上那个好几个 Bot 互相聊天的频道是什么。Peng 说，任务大一些、需要不同角色从各自视角发表意见时，他会这样用。他举的例子是假设要做一个把猫叫翻译成英语的 App，想从不同角度审视这个点子，就把 PM、设计等三个独立的 Bot 拉进一个群聊，抛出这个 prompt，让它们讨论。他说看它们怎么想、怎么互相争论挺有意思。

群里的规则和人类群聊差不多：@ 某个 Bot，就只有它回复；不 @ 任何人直接发消息，每个 Bot 都会看，然后自己决定要不要回。

常驻的 Bot 与一次性的会话

Peter 说，他觉得在别的 AI 应用里很难做到这一点：既保持上下文干净，又让各有上下文的 Bot 互相交流。Peng 解释了背后的设计取舍。管理工作有两种思路：一种按单个会话、任务、项目来组织；Grok Bot 选的是把 Bot 做成常驻的、有名字的 Agent，每个有自己的身份、记忆系统和工具。可以复用的东西沉淀到“角色”里，再通过单聊和群聊让它们协作。同一个设计师 Bot 可以有好几个项目，每个项目开一个单独的聊天。

他说团队观察到，很多 AI Agent 产品里的聊天是很短命的，几乎用完即弃。人们可能只关心正在做的三到五个，两周前的聊天再也不会回去看。所以他们的平衡方式是：可复用的能力和记忆放在角色里，有起止和截止日期的具体项目开专门的会话。

Peter 追问：像人一样，如果他跟设计师 Bot 聊了邮件 App 和另一个 App（字幕作 bark app），它的上下文里两个都知道吗，还是分开的？Peng 说是同一个实体。Bot 在群聊里工作时，它在单聊（DM）里的工作状态也会跟着变化，是同一个 Bot 在做你的任务。

播客 Bot

Peng 说 Grok Bot 也替代了他的播客工具。他听很多播客，读到一篇文章想在开车或洗澡时听，就把链接发给他的播客 Bot，Bot 把它转成一期播客，他随时能听。他说 Bot 在这里成了各种文件格式之间的转换器。

04. 一张街拍变成个人网站上的微缩模型，以及设计师 Bot

节目位置 0:10:07–0:14:16 · Turning a street photo into a diorama on Peng's website

从一张照片到一个“打卡”网站

两周前，Peng 在旧金山唐人街等公交时，拍了一家蔬果店（字幕作 produced shop），然后用 AI 把它做成一个 3D 黏土微缩模型。他觉得好玩，就放到了自己很简约的个人网站上，配了一行字说最后一次出现在唐人街某家市场（店名字幕不清）。

接着他想到可以把个人网站做成一个“网络打卡”应用。他的理由是个人网站一般别人看一次就不会再来，他自己也很少看。于是他跟 Grok Bot 讨论这个想法，最后定下一条流水线：

  1. 他发给 Bot 一张去过地方的照片，加上同行者的社交账号；
  2. Bot 生成两张图，分别对应两种显示模式（字幕作 day and light mode，可能指浅色和深色模式）；
  3. 去掉背景；
  4. 发布到他的网站上。

他说这些步骤写在一个私有仓库的 playbook 里，Bot 每次先去拉最新的 playbook，再按步骤生成图片、清理、发布。这样 Grok Bot 成了托管内容的主界面，他不用另外做一个后台或 CMS 手动上传。Peter 笑说只有设计师才会想到两种模式都做一张。

Peng 的总结是，可以把 Grok Bot 当成你想做的东西里的一个构建模块，而且它能一步步带你走到目标。

设计师 Bot 与 Figma MCP

Peter 问他现在还在 Figma 里画框，还是都交给 Bot 只做审阅。Peng 说 xAI 的设计师用任何需要的工具：Figma、基于画布的工具、团队自己的原型环境，有时也自己提 PR。设计师 Bot 主要用来跟他来回讨论想法，也能做小改动，因为它通过 connector 接入了 Figma MCP（MCP 是让模型调用外部工具的一种标准协议），可以直接改 frame、更新设计、使用 design token。

他还给设计师 Bot 写了一个 skill，里面记录他的 Figma 文件怎么组织、设计系统是什么、什么时候用哪种颜色、字体和间距。

“我做前 5%”

Peter 猜 Bot 做前 80%，他手动微调。Peng 说有时他的流程已经变成：他只做前 5%，先把系统搭好，做一个关键帧，然后让 Bot 扩展成整套流程、做出端到端的所有页面。

Peter 建议他像 Lauren 开源她的插件集那样开源自己的设计 skill。Peng 说团队里的 skill 是按人名起的，Lauren 有 Lauren mode，他有 Peng mode。

05. Lauren 的 Bot 怎样在合并前测试自己的工作

节目位置 0:14:16–0:17:59 · How Lauren's bots test their own work before merging

让 Bot 操控 Mac 上的 Linux 虚拟机

Lauren 说她的配置和 Peng 很不一样，偏工程。她最近在做对 Omarchy 的更好支持。Omarchy 是 DHH 和几位开源开发者在做的一个 Linux 发行版（字幕作 Omachi，结合 DHH 可以确定）。她用的是一个特殊构建版本，在 Mac 上的虚拟机里运行，还很早期，但已经能用。

她说这很有用，因为她可以让 Agent 直接用脚本操控这台虚拟机。要给这个 Linux 发行版做支持，最好的办法就是让 Grok Bot 真的在她电脑上打开它，交互式地安装，比如在里面给她装上 Grok Bot。屏幕上 Bot 正在做这件事（画面演示，字幕未说明细节）。

Peter 确认：Grok Bot 在自己的电脑上，但通过虚拟机控制你的电脑？Lauren 说 Grok Bot 有自己的电脑，同时还有一个跑在你电脑上的本地执行守护进程（local execution daemon）。

清理硬盘的 Bot：Crumb

她另一个常用的场景是硬盘空间不够时，告诉一个叫 Crumb 的 Agent 去翻一遍硬盘，找出空间都花在哪里，然后去删。她说它对你的电脑有完全访问权，具体取决于你给它的权限。

验证自己的工作

回到 Omarchy，她想试用它，修一些 bug，改善 Linux 上的体验，所以让 Bot 直接控制她电脑上的 Linux 虚拟机很有用。她说自己常讲的一点是：Agent 要能验证自己的工作。这就是一个例子，Agent 可以在你的电脑上验证它的工作；此外它当然也有自己的电脑，你可以去看它在做什么。她说她的主要用途就是在 Grok Bot 上做大量工程工作。

用 eval 决定插件改动能不能合并

她还维护一个个人插件集（字幕作 Pstack，后文也出现 PP stack、PAC，名字字幕不清）。这个插件的开发几乎全在 Grok Bot 里进行。她会启动 Cursor 的云端 Agent（cloud agents）来跑 eval（评测，用一组测试任务检查改动是否真的变好）。流程是：

  1. 插件里有一个 eval playbook，教 Agent 怎么评测；
  2. Agent 派生几个使用不同模型的子 Agent（subagents），用它们试跑 prompt；
  3. 检查最初设定的意图和目标是否达成；
  4. 只有达成了，才合并那个 pull request。

她说这样她才能相信对 skill 的改动确实带来了更好的表现。

06. Dr. Eggbot：帮你设计和审查 Bot 的 Bot

节目位置 0:17:59–0:21:27 · Dr. Eggbot, Lauren's bot that designs and audits your bots

Bot 设计师，以及食物名字

Peter 说她的 Bot 名字比 Peng 的更有个性。Lauren 说她有一个叫 Dr. Eggbot 的 Bot，在社交媒体上分享过（视频描述附了它在 x.ai Bot 市场的链接，名为 dr-eggbot-v2）。它是一个“设计 Bot 的 Bot”，按她对 Bot 的工程严谨性要求来设计新 Bot。她还让它起食物主题的名字，她说可能是亚洲人的习惯，爱吃，所以 Bot 名字都很可爱（字幕里有几个名字听不清，像 daifuku、gyoza 一类）。

她的 Bot 阵容

  • 私人助理（字幕里时作 Suki 时作 Tuki）：管午饭、航班、订酒店。Lauren 说有时她不理它，它会变得有点“毒舌”。
  • 幕僚长：帮她处理各种杂事。
  • 侧边栏里一串工程 Bot。
  • 几个社交 Bot，管理她的社交媒体。

她的大部分工作经过其中两三个 Agent：要么跟幕僚长说，幕僚长再去找她的工程 Lead，一个叫 Matcha 的 Bot；要么是私人助理帮她订机票。她说还没给私人助理配一个团队，因为她没那么忙，目前一个助理做得很好。

什么时候该拆出新 Bot

当她发现自己在用一个 Agent 做很多不同的事，她会意识到这意味着往这个 Agent 里塞了大量很杂、互不相关的上下文，可能让它混乱。这时就让 Dr. Eggbot 给她设计新 Bot。

定期审查所有 Bot 的 routine

Dr. Eggbot 还会帮你设置一个 routine（Grok Bot 里的定时任务，到点唤醒 Bot 执行）。这个 routine 会翻看你所有的 Bot 以及你和它们的聊天记录，然后提出建议，例如“这个 Bot 老是做某件不太好的事”，再建议改进：可以是新 skill、新 Bot，或调整 routine。

它也会检查你已有的 routine 是否高效。Lauren 解释，routine 如果跑得太频繁，会很耗用量，因为每次都要唤醒 Agent；比如每 10 分钟一次，就是很多次唤醒。Dr. Eggbot 在这方面帮了很多。

07. 私人助理 Bot 订下了多城市行程

节目位置 0:21:27–0:25:22 · The assistant bot that booked Lauren's multi-city trip

最大的一笔：一整趟出差

Peter 问她最多给过私人助理多大的自主权，会不会让它做大额消费。Lauren 说她马上要去伦敦和阿姆斯特丹演讲，是一个巡回会议的一部分（字幕作 compile on the road conference），整趟行程都是助理订的。她说让她印象深刻，因为行程比简单的往返复杂得多：

Orange County → Denver → London → Amsterdam → 回家。

公司用的是差旅平台 Navan。Bot 做了全部工作：找最合适的航段、她能用的最好舱位、最好的时间，还找了离会场近的酒店。她给 Bot 的输入只是一条 Slack 消息的链接，里面有会议的一些细节，外加一句“帮我订酒店和机票，下单前先跟我确认”。Bot 给出了几个方案，她点了同意，它就全部订好了。她说这大概是她通过 Grok Bot 做过的最大一笔消费。

Peter 追问：所以还是要先让它说出计划再批准？Lauren 说对，还没到完全放手的程度。她不想被订到很离谱的红眼航班，或者坐到飞机最后面，所以要先审批。

Peter 的机票 Bot，买厕纸

Peter 说他也有一个类似的 Bot 在盯去日本的机票。Google Flights 也能设价格提醒，但 Bot 更聪明，会去找他没设置过的其他路线，最近帮他省了不少钱。Lauren 说她也用 Bot 买日用品，比如厕纸快用完了，就让它把 Amazon 上的订单再下一次。

给 Bot 一个手机号，提醒她吃午饭

她说在 Grok Bot 开发很早期、团队还在迭代时，讨论过 Bot 能不能给你发短信。她当时通过一个第三方服务给私人助理配了一个自己的手机号，这样助理可以直接给她发短信。原因是她总忘记吃午饭，而 Mac 开着勿扰模式时她看不到通知，短信会响。她还教会了助理用 DoorDash 给她点午饭。Peter 说午饭是他一天的高光，从不会忘；Lauren 说太投入的时候就是会忘。

08. 工程 Bot 团队，有时 PR 合并了她才看

节目位置 0:25:22–0:38:59 · Eng bots that sometimes land PRs before Lauren reads them

分层：幕僚长 → 工程 Lead → 工程 Bot

Peter 问她有一个 Lead 和几个工程 Bot，是每个负责一张工单吗？Lauren 说她有三个工程 Bot。她大多只跟幕僚长说话，幕僚长再去找工程 Lead。这些工程 Bot 都是用 Dr. Eggbot 设置的。她特别要求 Dr. Eggbot 确保工程 Lead 的职责是把任务拆小、委派和监督其他 Bot，自己不干活。

她给大家看工程 Lead 的描述（画面演示）：里面直接写着下属 Bot 的 ID，并告诉它“永远不要自己干活，总是委派给那四个 Bot”。她前面说有三个工程 Bot，这里说四个，字幕原样如此。她说它确实就是这么做的。

工程 Bot 只当“监工”，活交给云端 Agent

很多活是通过 cloud agents 完成的。工程 Bot 要做事时会创建一个云端 Agent，你可以在 Cursor 里或网页上打开它。这让她能按任务类型选用不同模型：简单的任务要速度；需要更多规划和推理的任务，就调高推理等级（reasoning level）。她说 Grok Bot 里的 cloud agents 给了她很细的控制。

她把每个工程 Bot 看成“主管”：Lead 管它们，它们自己也尽量不干活，总是去派生云端 Agent。它们负责传递消息，这让她能编排规模很大的 Agent 群（agent swarm）。碰到大项目，她就跟幕僚长说：我有个大项目，先在 Notion 文档里做个规划；幕僚长会想清楚工作分几个阶段，然后全部委派给工程 Lead，Lead 再拆得更细，交给各个 Bot 去做。

自动合并

Peter 问：每个 Bot 交回一个 PR，Bot 先审一遍？Lauren 说基本是这样，但她自己做得更多的一件事、也是她在 X 上常讲的，是把代码库做得对 Agent 友好。Grok Bot 的代码库和架构就是按这个思路做的，所以很多时候她直接让 PR 自动合并。她说听上去有点吓人，但有时她在 PR 合并之后才第一次看，看完觉得“嗯，没问题”。

“米其林厨房”，不叫软件工厂

Peter 问这是不是就是流行说的“软件工厂”。Lauren 说她更愿意叫它米其林厨房。她的理由是：说到米其林星级厨房，人们想到的是质量和手艺，做出来的产品是一道菜；同时它也有规模，一家餐厅可能有 50 个或 100 个座位，所以必须做到规模化的高质量。她说很多人听到“工厂”会联想到大批量、低质量的 slop（AI 批量产出的低质内容），而她想两者都要：怎样在规模上保证质量。她在插件集上的工作，以及把它和 Grok Bot 结合起来用，都是朝这个方向。

Peter 开玩笑说该做一个侍酒师式的 Bot，介绍“这个 PR 选自本地农场”。Lauren 接话说要来一个“手工 PR”。Peter 又打趣说 Peng 的工作就是把她开源的 skill 搬进产品里，随后说是开玩笑。

每个人的 mode skill，以及让所有人都能贡献代码

Lauren 说内部很多人都有自己的 mode skill。她的那个开源版叫 poteto mode，内部叫 Lauren mode；Peng 有 Peng mode；很多工程师、设计师和 PM 都有。她说这让团队能在代码库里已有的 skill 上不断叠加。重新设计和架构 Grok Bot 代码库的一大动机，就是让工程师以外的人也能在较高层面贡献，为此下了很多功夫。大家在 Grok Bot 里启动这些 Agent，有时也在 Cursor 里。

她说 Cursor 和 Grok Bot 的插件可以互通，比如她的插件集可以同时装在 Grok Bot 和 Cursor 上，复用同一套 skill。

skill、插件与市场

Peter 问 Bot 能不能调用不同的 skill，比如他有一个“像我一样写作”的 skill，是不是用斜杠触发。Lauren 说可以，输入 /poteto-mode 就能用那个 skill。也可以去插件市场看。她不确定市场里还有没有别的纯 skill 插件，她的是其中之一；但很多插件除了 MCP server 之外也附带 skill，例如她印象中 X 插件在工具之外还带了一个 skill。插件可以包含很多不同功能来扩展你的 Grok Bot。

社交 Bot Potato：外环喂给内环

Peter 问她的社交 Bot 怎样在 X 上把信号和 slop 分开。Lauren 说她的社交 Bot 接了 X 和 LinkedIn，她用 X 更多。有一个叫 Potato 的 Bot 专门看她在 X 上的所有提及。她在 X 上有个梗：说三遍 potato 她就会收到通知，靠的就是这个 Bot。它有一个 routine，她记得设的是大约每 30 分钟检查一次提及。她会进去回复，或者它会帮她汇总，比如“有五个用户报告了同一个 bug，你可能该看看”。

她把社交媒体看成她的“外环”（outer loop）。因为她的社交账号部分用于工作，这样能随时掌握用户反馈：有人报 bug、遇到问题、某个新功能让人困惑。她希望这些反馈能喂给“内环”，也就是她的工程 Bot。因为都是 Bot，她可以直接去找 Matcha 说“Potato 说了什么什么”，上下文就能从那边拿到，她不用复述 X 上的内容，也不用复制粘贴，只要说“去跟 Potato 聊，搞清楚，然后带一份修复方案回来”。

她说对她来说 Grok Bot 的威力在于把这些东西连起来，上下文可以从很多地方抓取、汇总，比她自己打字描述要丰富得多。Peter 说 AI 这件事上下文就是一切；所有 Bot 住在同一个房子里，可以互相传递上下文。

Potato 这个名字

Peter 问 potato 从哪来。Lauren 说很多年前玩 MMO 网游时起不出名字，她爱吃（看 Bot 名字就知道），就叫 potato。正常拼法被占了，她当时在学日语，就按日语片假名的感觉拼成 poteto，一直用到现在。

主持人追问：这还是“单人模式”吗

Peter 说 Grok Bot 的界面有点像 Slack：有私信、有队友、可以拉群。网上不少人说这类东西还很“单人”，一个人对着一群 Bot。他问 Lauren 和 Peng 能不能一起和一群 Bot 协作，团队对此有没有兴趣。

Peng 没有直接谈多人功能，而是讲了设计 Grok Bot 时的出发点：怎样让人从“自己手动管理任务”毕业。他把工作方式分成三层：

  1. 过去，人自己在工具里干活：在 Figma 里画矩形，在 Notion 里打字，在 Slack 里发消息；
  2. 现在，很多人已经在 prompt AI 替自己做这些；
  3. 他认为未来，人不再手动管理所有 Bot，而是去设计系统、设计护栏（guardrail），设计 Bot 之间、Bot 与其他人、Bot 与你怎样自主协作。

他说很多 AI Agent 产品以模型为中心，从 UI 就能看出来：先在模型外面搭 harness（模型外围的工具调用、上下文管理等运行框架），再在 harness 外面做产品，界面也是按这个做的，一路下来造出了很多术语和概念，他说他妈妈永远不会知道某个 .md 文件是什么（文件名字幕不清）。Grok Bot 是一个实验：怎样让系统模型和用户的心智模型对上。他们发现拟人化、有名字的 Agent 效果很好，能引起共鸣，因为现实世界里人就是这样办事的。他举的例子是你不需要懂车险公司怎么运作，但知道出事打给谁；有了医保，你不用懂医疗系统，有医生办公室作为联系人。让这样一个联系人成为你主要的输入输出界面，他说对他是一种范式转变。

他讲了团队内部的一个流程：他发现一堆 bug，就截图、标注，丢给一个 Bot，Bot 把它们整理发到一个 Notion 页面，他的工程 Bot 再从那里接手。他说大家开始用一种间接的、Agent 式的方式用这个产品，它却能把点连起来，自然长出新的、自主的、长时间运行的工作流。

Peter 说这也许是通用的最佳实践：人在环中（human in the loop）负责在 Bot 之间传递上下文和反馈。他坦言自己对“我去睡觉，让 Bot 把一切做完，醒来就完美”的说法一直有点怀疑，然后问两位：除了用 Lauren 的 skill，还有什么办法让 Bot 跑更久而不跑偏、真正做出想要的东西。

09. 一次一个 skill，慢慢把更多工作交给 Bot

节目位置 0:38:59–0:45:04 · How to trust your bots with more work, one skill at a time

Lauren：归根到底是信任

Lauren 说不一定要用她的插件集，但这和 skill 有关。她常讲的一点是，归根到底是信任：你愿意给 Agent 或 Bot 多少信任，让它替你做一件事。

她总是建议大家，不管用不用她的插件，先花时间观察 Bot 或 Agent 做事，过程中纠正它；在对话结束时，把它变成一个可复用的 skill。

报销单的例子

她举的例子是让 Bot 填报销单：翻一遍你这个月的所有开销，从邮箱里找出收据，全部录进报销工具。步骤是：

  1. 第一轮反复迭代，把 skill 打磨好；
  2. 直到你输入 /expense-report 它就能一次做对（one-shot）；
  3. 到这一步，你才有信心走开，让它设一个 routine：每当有带收据的新邮件进来，就自动填报销单。

她说这样就不用一直盯着。她认为这里没有秘诀，无论设计、工程还是生活杂务，都取决于你对 Bot 有多少信任。还不信任的时候，skill 和 prompt 能帮你建立信任，但必须是渐进的。一个从没用过 Bot、也没配好 skill 的人，你让他直接走开，他当然不会信任，因为他没见过 Bot 能做什么。和 Agent 一起做过一两次，知道它能重复做到，你才能把自己解放出来去做别的事。

Peter 的归纳与 Peng 的补充

Peter 归纳：下载 Grok Bot 后，先为手动工作流建几个 Bot，手动带着它们走一遍，顺手了就让它们写成 skill，最后设 routine 主动去做。Lauren 说这就是她的流程。

Peng 同意，说这是一个渐进的过程。他建议从简单开始，先给一个任务。他自己到今天还在测它的极限：凡是他要动键盘鼠标的事，都先试着交给 Bot，看效果如何。Peter 说那等于要故意让它超负荷，才能看到边界在哪。

Peng 把这形容为你和 Bot 之间建立关系。他说这是有意的设计：所有能力是共享的，包括工具、connector 和 skill；但记忆和偏好属于每个 Bot 自己。可复用的组件抽象到角色里方便管理，同时让人和 Bot 形成关系。他给的顺序是：先做一个简单任务，再做一个周期性任务，再设 routine 让它自动化；如果发现太烧 token 就调低一些；然后接入更多工具和 skill，做个性化。Bot 会逐渐成熟、越来越了解你，所以这很个人化，你的助理和他的助理肯定不一样，是一个双方共同进步的过程。

像招新员工

Peter 说这就像新员工入职，时间久了更信任。Lauren 说这个说法很好：像雇虚拟员工，你得像培训新员工那样先培训它，再让它自主。设置好之后可以进入很顺的状态，你像 CEO 一样委派、抽身，去做更高层的战略工作。Peter 说现在人人都能当产品的 CEO。

在哪找到他们

Lauren 在 X 上叫 poteto（她逐个字母拼了 p-o-t-e-t-o）。Peng 也活跃在 X 上，账号是 pengzheng_。Peter 说 Grok Bot 是很棒的产品，祝贺他们，期待后续。
