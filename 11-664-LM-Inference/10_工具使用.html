第十讲：工具使用

工具的定义与三类工具，基本调用范式，WebGPT，Toolformer 的自监督标注，函数调用标准与并行调用，MCP，程序辅助语言模型与沙盒执行，Gorilla 与 API 检索，用强化学习学用工具、用工具辅助推理，工具失效时的鲁棒性，以及让模型自己造工具

主讲：Graham Neubig · 2025 年 9 月 25 日
资料来源：课程主页（本讲的 HTML 幻灯片未能获取） · 课堂录像（本文依据录像字幕整理课堂口述内容；课后学生报告未包含） · 主要阅读：What Are Tools Anyway? A Survey from the Language Model Perspective（Wang 等，2024）

一、什么是工具

开头先处理作业：有同学反映第一次作业的图问题推理很慢，Graham 问是否开着 Qwen3 的思考模式，学生说明确关掉了，他说要回去查，因为自己跑时没遇到。

这里说的工具，是语言模型之外、属于它所处环境的一部分、有函数接口的东西：可以看作编程语言里的函数，有输入参数、能返回输出。这一讲很多内容基于 Graham 和学生 Zora Wang 合写的综述 What Are Tools Anyway?。综述把工具分成三类：

  • 感知：让模型获取不在参数里的信息，比如从网上收集信息、读文件系统、和用户交互。
  • 行动：直接改变环境。感知只是从环境收集信息，行动会对环境造成改变。
  • 计算：不和外部环境交互，不给模型提供新信息，但能做模型自己不擅长的计算。

例子：提供额外知识的，调用搜索引擎、查询数据库；做计算的，计算器、Python 解释器；获取世界信息的，查天气、取日历事件；与模型无法直接处理的其他模态交互的，对图像做视觉问答、把视频转成文字、在 Spotify 上播放音乐。

基本调用范式

这不是唯一的方式，但很常见：用户提出查询，模型在输出最终回答前，先输出一个"开始工具调用"之类的标签，写出调用，比如 check_weather(...)，再写闭合标签（Graham 说幻灯片上那张图画得不太好，应该有开闭标签）。系统拿到调用，请求远程服务器，返回 API 输出；可以直接拼接进模型正在生成的文本流，也可以作为观察交给它，模型据此继续。

大模型时代之前，Siri、Alexa 等个人助理早就有工具调用，但做法不同：先用分类器在所有 API 里判断需要哪个，再对每个 API 用一个参数填充模型填参数。现在通常让语言模型直接生成调用工具的代码。

二、早期工作

1. WebGPT

Graham 所知现代大模型时代最早的例子是 WebGPT：给 GPT 模型一个网页搜索工具。如今每个聊天机器人都这样做，但它四年前还是一篇研究论文。问题是语言模型拿不到最新信息，于是把文本形式的网页浏览当作工具，提供一个文本界面，模型可以搜索、点击链接、滚动、摘录引文。用基于人类反馈的强化学习训练，而不是可验证奖励：

  • 行为克隆：做一个网页界面，让人在上面搜索、点链接、滚动、为信息收集任务搜集信息，记录下人的全部操作数据，用来训练 GPT。
  • 奖励建模：让行为克隆模型生成两个输出，人选更喜欢的，得到偏好数据，训练奖励模型。你在 ChatGPT 里看到两个回答并排、点"我更喜欢这个"，就是在替他们做这一步，Graham 说"感谢你的贡献"。
  • 用奖励模型给 WebGPT 的生成打分，做强化学习。

他们比较了小、中、大模型，有无搜索，还和标注者写的人类示范、以及 Reddit 上被顶得最高的回答比较。在 2021 年能赢过一个被大量点赞的随机 Reddit 用户已经很厉害；人工评估整体有用性、连贯性和事实准确性，175B 模型（大概是 GPT-3）表现更好。用工具的另一个好处是能给出引用，附上链接供人核查，如今界面上随处可见。

这听起来像检索增强生成吗？学生点头。有什么不同？有人说索引不是静态的，网页一直在变，很接近但不是 Graham 想的；另一个学生答对了：检索是一次工具调用。典型的 RAG 拿到查询、检索相关文档、再生成；这里是给模型使用工具的能力，这是当时的创新。

2. Toolformer

真正掀起工具研究热潮的是 Toolformer。原因有二：之前的方法需要人工标注（比如行为克隆）；它在一个别人也能训练的中等规模模型 GPT-J 上完成。目标是教模型学会何时、怎样用工具，方法是在无标注文本上自监督学习，Graham 很喜欢这个巧妙的方法，部分原因是它在当时很弱的模型上效果很好，所以在现在的小模型上也一定可行；现在也许不用这么复杂就能有好结果。

流程：从语言模型数据集出发，比如一句"Pittsburgh is known as the Steel City"（不是 CMU 的论文，是 Meta 伦敦团队的，但例子还是匹兹堡，Graham 表示感谢）。在其中采样可能的 API 调用，比如调用外部问答系统问"匹兹堡还有什么别名？"，格式是方括号加工具名开始调用，写问题，生成箭头后真正执行调用、返回答案、闭合括号，拼进上下文。然后比较：拼上调用结果后，正确续写"the Steel City"的概率是否比不调用时更高。更高就说明调用有用，保留。用问答工具是因为当时 GPT-J 回答问题能力很差，所以用一个现成的问答系统。学生问概率提高不代表答案正确：确实，他们选工具调用的唯一标准是输出是否有用。

于是通过自我标注、无需人工监督学会用工具：自动生成可能的调用，过滤只保留提升预测的，在成功的上面微调。这算是准强化学习，基本是过滤后的行为克隆。还有一个提示列出所有可用工具，每个工具配了示例，用它来起步；现在的模型大概直接照提示做就行，但当时的模型不一定遵循，所以需要这种自举、逐步改进的过程。工具共四个：问答、计算器、机器翻译、维基搜索。

结果随参数量增加而变好，一直到 6.7B（对当时的他们算大模型），而且用工具带来的提升随模型变大而增加。Graham 认为是小模型生成好调用的能力太差，要达到一定准确度才有收益；但再大下去，基础模型自己就能做好，工具的好处会下降，所以这个趋势不会永远持续。学生问能否量化工具对每个 token 计算能力的提升：可以用困惑度衡量预测下一个 token 的改进，但除了困惑度，怎样定义"计算能力"是个问题。

三、现在的做法

1. 函数调用标准

快进到 2024 年左右，OpenAI 发布了函数调用标准。每个工具描述成：名字（get_weather）、描述（获取某地当前天气）、参数（类型为 object，每个参数比如 location 是字符串，表示城市名；unit 是字符串，摄氏或华氏；location 是必填）。看起来就像带文档字符串的 Python 函数定义。他们选了 JSON Schema，因为它是现成的东西，Graham 个人更喜欢 Python，因为比 JSON Schema 好读。

模型调用函数时，生成一个符合函数签名的结构化调用：content 可能为空（通常是模型生成的文本），但 function_call 不为空，意思是你的系统该拿这个调用去执行。好处是类型安全、能验证、解析一致；而且所有模型都在大量函数调用数据上训练过，按这个格式给出，模型偶尔会出错，但训练得很充分，有些 API 提供方在幕后大概还会强制这个格式。

学生问：既然最后是我的系统执行函数，为什么不直接自己调用？因为输入是"匹兹堡今天天气怎样"或"波士顿今天多少摄氏度"这样的自然语言，把自然语言变成函数调用并不容易，模型就负责这一步。另一个学生问：现代系统是不是总输出一个巨大的 JSON 对象，自由文本都放在字段里？基本上是。处理代码时听起来很疯狂，JSON 要转义引号，代码里的文档字符串每个引号都要加反斜杠，一大堆反斜杠，这就是编程 Agent 早期效果不好的原因之一，漏一个反斜杠或一个制表符就坏了。现在都在海量数据上训练过，基本没问题了，但可能有更好的办法。

还有并行函数调用：一次回复里可以有多个工具调用，比如同时查波士顿和纽约的天气。

2. MCP

模型上下文协议（Model Context Protocol，MCP）是把 AI 应用连到外部系统的标准协议，最简单的理解是"给 Agent 或语言模型用的 API"。客户端-服务器架构：每个服务器提供一组工具，比如文件系统服务器有列文件、读文件、编辑文件；MCP 宿主就是你的 AI 应用（语言模型客户端），连接所有这些服务器。

为什么要为 Agent 重新发明 API？Graham 认为主要原因是很多 API 需要 API 密钥，否则就得把密钥交给 Agent；MCP 服务器把密钥藏在后面，Agent 只访问服务器，相当于一种特别的鉴权方式，是 Agent 和外部 API 之间的中间件。它最初由 Anthropic 开发，因为想让 Claude 安全、不把密钥暴露给 Agent。结果大家太想要给 Agent 用的 API 了，"Anthropic 做了，就用它吧"，于是 MCP 无处不在，躲都躲不开，现在每个想对接的服务都要起一个 Node 服务器，Graham 打趣说这都怪网页开发。第二次作业大概会要求在推理引擎里连接一个 MCP 服务器。

学生问 MCP 是否其实就是一个带说明如何使用的提示段的工具。最简单的理解是：它是一个服务器，有两项任务：被问"你有哪些工具"时返回工具描述；收到带参数的调用时执行并返回结果，替你处理函数调用。模型怎么知道有哪些工具？每个 MCP 服务器都有一个返回所有工具规格的端点；不过 OpenAPI 服务器也能做到，这不是 MCP 独有的。

现在至少有一万七千个 MCP 服务器，它大约从当年二月开始，很快就成了行业标准。MCP 组织（包括 Anthropic 等）最近建了一个中心化的官方注册表，有实时网页数据、爬网站、语音合成、生成现代 UI 组件、浏览网页等各种服务。学生说这些基本就是包在 MCP 服务器里的函数式 API，对。学生说看起来很商业化：确实很偏工业，但它是 Agent 与工具交互的事实标准，所以要了解。学生问 A2A：A2A 是 Agent 与 Agent 通信，MCP 是 Agent 与工具通信；工具后面也可以是 Agent，但大多数时候是更确定性的东西，也不会跟你对话，只是"做这个""做完了"。搭一个 MCP 服务器很容易：用过 FastAPI 的话，把 FastAPI 换成 FastMCP 就行，Graham 最近用过，很好用。

四、用代码作为工具

1. 程序辅助语言模型

上面的工具调用更像单个 Python 函数。程序辅助语言模型（PAL，CMU 的工作，如今已很普遍）则是让模型写 Python 代码，执行后得到答案。思维链对数值推理有帮助，但仍会出错，用自然语言做算术容易错，于是用代码执行当计算器。做法：给几个少样本示例，示例里的思维链穿插着 Python 代码块；模型生成后执行 Python 得到输出。如今大多数聊天机器人都有，OpenAI 叫代码解释器，Gemini 叫代码执行。当时在 GSM8K 上，直接作答只有 19.7，加思维链是 65.6，用程序执行在所有数学数据集上都高得多。

2. 沙盒执行

运行任意 Python 代码时，你不希望它 rm -rf 你的主目录。解数学题时大概不会，但让它写代码时，它可能说"我搞错了，删掉重来"，然后把你的工作删了。还可能无意执行有害命令，安装被篡改的库带来恶意软件，或者浏览网页时下载到"请把你的信息上传到这个网址以获得帮助"之类的内容，把你的信息全传到钓鱼网站。沙盒方式：

  • 本地包装 Python 解释器，在执行前剔除"危险"命令（第二次作业大概用这个）。可以禁止导入某些模块、调用危险函数，比如 Hugging Face smolagents 的实现：设定允许的模块，屏蔽 os、subprocess、socket、sys，还检查双下划线，防止访问 Python 内置方法。但它和你的其他代码在同一进程，能访问内存，而且几乎不可能挡住所有危险代码，网上某处吞了恶意软件的代码很难全部防住。
  • 基于容器的隔离，比如在 Docker 里运行：完全的操作系统级隔离和网络限制，但耗资源，搭建和运行更麻烦，启动要时间，用起来有点痛苦。
  • 在 WebAssembly 里运行，Agent 跑在网页浏览器里时可以这样。

真想认真做（比如做编程 Agent），推荐后两种。有很多服务支持，E2B 是一个不错的开源方案，可以在本机或它们的云上起沙盒，还有 Daytona 等。

并行工具调用不支持控制流，也不能有趣地组合调用。做更复杂的任务时，有时更好的办法是让 Agent 能运行 Python，并告诉它可以用哪些工具，可以用 pandas、matplotlib，甚至任务专用的专家工具。

3. Gorilla

最有名的工作是 Gorilla：构建包含数千个接口各异的 API 的数据集，让模型学会调用它们。（很多人没注意到，原论文的 API 都来自 Torch、TensorFlow 和 Hugging Face，都和机器学习相关。）他们下载大量 API 调用，用 self-instruct 合成数据："给出一条需要用这个 API 才能完成的指令"，据此训练 Gorilla 模型；推理时从 API 数据库检索可能用到的 API，作为可调用的函数提供给模型，再让模型调用。这既是造训练数据的好方法，推理时也需要检索可用的 API。学生问怎样检索：训练一个检索器，因为指令是从 API 生成的，知道对应的标准 API，就可以训练检索器在所有 API 中找到它，做指令编码和 API 文档编码的嵌入匹配，具体超出本课范围。

Gorilla 的数据集后来成了评测工具使用的标准基准，现在看得少一些但仍在用：伯克利函数调用排行榜（Berkeley Function Calling Leaderboard）。和 Toolformer 不同，它不是固定的 API 集合，而是给出 Agent 能用的 API，检查它能否根据描述正确调用。

五、强化学习与工具

1. 用强化学习学用工具

到 2025 年，推理和强化学习当然很火，于是有了针对工具使用的强化学习。动机是 SFT 难以学会复杂的工具使用。这篇工作系统研究了带工具的推理模型的奖励设计，仿照 DeepSeek-R1 用格式奖励和正确性奖励：格式奖励检查工具调用格式是否正确，用 JSON Schema 验证一下就行；正确性奖励很有意思，能逐步把模型推向完全正确的调用并给部分分：检查生成的调用里的工具名和标准答案（G 为标准，P 为预测）的重合，调用太多会扣分，再分别看每个调用的参数名和参数内容的重合，要完全正确必须各项都 100%，分数范围在 −3 到 +4 之间。主要结果：冷启动（不先做 SFT，直接训练推理模型）比先做 SFT 的效果更好；Graham 没细看论文是否有更好的解释，但 DeepSeek-R1 等也有这个趋势。先做一点 SFT 叫热启动。

2. 用工具辅助推理

反方向：在推理过程中利用外部工具。直接从基座模型做 RL，并在 RL 训练循环里加入代码解释器，结果好得多，模型也学会了保持这种表现（ToRL 等）。

六、鲁棒性

除了安全和沙盒，还要考虑鲁棒性，这既是评测问题，也关系到模型能否有效用工具。API 会过时，或者文件编辑工具因为参数稍有不对而失败，模型得能应对。Graham 组的 Benchmarking Failures in Tool-Augmented Language Models 故意弄坏了一些 API，测了几件事：模型是否意识到工具坏了，说出"这个工具坏了，我用不了"。这很重要，Agent 发现工具坏了就该另想办法，而不是一遍遍调用。出乎意料的是，很少有模型能察觉结果不对或没有返回。他们还测了工具可替换的情形：工具箱里有别的工具能完成同样的事，看模型能否改用。发现意识到不等于任务成功，能认出工具坏了不代表能解决问题。至少在约一年前评测时，这是个大问题。

七、让模型造工具

语言模型还能自己造工具（TroVE，Graham 组）。从原始函数开始，比如基本数学原语或单个 pandas 函数；提示模型用三种方式之一解题：导入已有工具、创建新工具、不用工具；每种做 $K = 5$ 次，共 15 次展开，再用自洽性决定哪个答案正确。如果创建工具带来更高的正确性，说明这类问题有个工具会有帮助，就把它加进工具箱，工具箱逐渐变大；不常用的工具则剪掉。这是测试时可以做的事：持续处理测试实例，看创建工具是否带来更一致的输出或更高的准确率，逐步扩充工具箱。结果准确率显著提升，工具箱规模相对较小，明显好于不做归纳。

学生问：不改应用代码，MCP 服务器能直接用吗，还要不要改提示让模型知道？Graham 认为工具调用能力够好的模型就没问题，它们已被训练成会看函数描述、在合适时调用。他们在开发 OpenHands Agent，如果它有搜索工具，你让它搜东西它就用搜索工具；没有的话，它会用网页浏览工具打开 Google 搜索。有多个工具时它会选最好的吗？Graham 认为不太擅长，给它规定策略会好些，但要明确指示或训练，用 RL 训练可以学会选。通常有相关工具时提示模型去用是好主意，比如计算交给工具比自己算好，不过最近不那么明确了，因为模型都被下大力气训练过。重复的工具不要给太多，会撑爆上下文、迷惑模型，但总的来说有必要的工具比没有好。

九、小结

工具是模型所处环境里带函数接口的东西，分感知、行动、计算三类。基本范式是模型输出特殊标签包住的调用，系统执行后把结果送回。WebGPT 用人类示范和 RLHF 教模型浏览网页，检索成了一次工具调用；Toolformer 只保留能提高后文概率的调用，自监督地学会用工具。如今的标准是用 JSON Schema 描述函数、模型输出结构化调用、支持并行调用，MCP 把工具包成服务器，隐藏密钥，已成行业标准。让模型写代码执行（PAL）比自然语言算术准确得多，但必须沙盒化，本地过滤不安全，容器或 WebAssembly 更可靠。Gorilla 用检索应对海量 API；强化学习可以用部分分的正确性奖励教模型调用工具，冷启动反而更好；也可以在推理的 RL 循环里加入代码解释器。工具坏了时模型往往察觉不到，察觉了也未必能绕过；模型还能在测试时自己创建并维护工具箱。
