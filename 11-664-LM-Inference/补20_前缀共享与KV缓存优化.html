第二十讲（补充）：前缀共享与 KV 缓存优化

KV 缓存有多大，PagedAttention 怎样消除显存浪费，RadixAttention 与 Hydragen 怎样在请求之间共享前缀，以及从模型结构（MQA、GQA、MLA）、量化、淘汰三个方向压缩 KV 缓存

原课：Prefix Sharing and KV Cache Optimizations，Amanda Bertsch · 2025 年 11 月 11 日
本讲没有公开资料，以下根据其他公开资料整理，不是原课内容：PagedAttention / vLLM（Kwon 等，2023）；SGLang（Zheng 等，2023）；Hydragen（Juravsky 等，2024）；GQA（Ainslie 等，2023）；DeepSeek-V2（2024）；KIVI（Liu 等，2024）；H2O（Zhang 等，2023）；StreamingLLM（Xiao 等，2023）

问题：同一张 GPU，为什么用 vLLM 能同时服务的用户比早期系统多好几倍？

主要靠管好 KV 缓存。每个请求生成时都要存下前面所有 token 的键和值，这份缓存常常比模型参数还占显存。把显存切成小块按需分配、让相同的开头只存一份、再从模型结构上把每个 token 要存的东西压小，能放进同一个批次的请求就多了。

说明

课表上第 20 讲由 Amanda Bertsch 讲前缀共享与 KV 缓存优化，没有公开录像和幻灯片。这篇补充根据这个题目下最常被引用的系统论文和方法论文整理。

一、KV 缓存回顾

1. 是什么

Transformer 生成一个新 token 时，要用注意力每个位置用自己的查询向量和前文各位置的键向量做点积，按匹配程度加权取用前文的值向量。 AI 基础第 12 篇读取前面所有 token 的信息。每个 token 在每一层都会算出一个键向量（K）和一个值向量（V）。前面 token 的 K 和 V 一旦算出就不会再变，所以把它们存下来，生成下一个 token 时只给新 token 算 K、V，再追加进去。这份存储就是 KV 缓存，它让解码不必每一步都重算整段历史。

2. 有多大

每个 token 的 KV 缓存大小是：

$$2 \times \text{层数} \times \text{KV 头数} \times \text{每头维度} \times \text{每个数的字节数}$$

开头的 2 代表 K 和 V 各一份。以两个常见的 70 亿级模型为例，都用 16 位（2 字节）存储：

模型层数KV 头数每头维度每 token 的 KV 缓存
Llama-2-7B3232128512 KB
Llama-3-8B328128128 KB

以 Llama-2-7B 为例，一条 4000 token 的对话需要约 2 GB 的 KV 缓存。模型参数本身约 14 GB，如果一张 80 GB 的 GPU 要同时服务 30 个这样的对话，KV 缓存就要约 60 GB，比参数还大。上一讲（第 19 讲补充篇）算过，批同时处理的一组请求。批越大，读一次模型参数能服务的请求越多。越大，解码的瓶颈越会从读参数转移到读 KV 缓存。所以 KV 缓存同时卡住了两件事：显存容量决定能同时服务多少请求，显存带宽决定每一步解码要多久。

Llama-3-8B 的 KV 缓存只有 Llama-2-7B 的四分之一，原因是它用了分组查询注意力，第五节会讲。

二、PagedAttention：别浪费显存

1. 问题：碎片

一个请求最终会生成多少 token，事先不知道。早期的服务系统为每个请求预先分配一块连续的显存，大小按可能的最大长度来留。这造成三种浪费：预留了但最后没用上的部分；还没生成到的部分暂时空着；不同大小的请求之间留下无法利用的空隙。vLLM 的论文测量发现，在当时的系统里，KV 缓存占用的显存中只有约 20% 到 40% 真正存放了 token 的状态。显存浪费了，能同时放进批次的请求就少，吞吐量就上不去。

2. 借鉴操作系统的分页

操作系统管理内存时早就遇到过同样的问题，解决办法是虚拟内存和分页：程序看到的是连续的地址，实际的物理内存被切成固定大小的页，按需分配，可以散落在任何地方，由一张页表记录对应关系。

PagedAttention（Kwon 等，2023）把这个办法搬到 KV 缓存上。显存被切成固定大小的块，每块存若干个 token（默认 16 个）的 K 和 V。每个请求有一张块表，记录它的第 1 块、第 2 块……分别在显存的哪里。生成新 token 时，当前块满了才分配新块。注意力计算的核函数按块表去读取分散的块。这样浪费只发生在每个请求的最后一个块里，平均不到半块。

3. 顺带实现了共享

有了块表，多个请求可以指向同一个物理块。比如并行采样同一个提示词的 8 个回答，提示词部分的块只存一份，8 个请求的块表都指向它；每个块有引用计数，某个请求要修改一个被共享的块时才复制一份（写时复制）。束搜索的多个候选共享大部分历史，也能用同样的方式节省显存。

基于 PagedAttention 的 vLLM 在相同延迟水平下，比 FasterTransformer 和 Orca 等系统的吞吐量高 2 到 4 倍；序列越长、模型越大、解码算法越复杂（如并行采样、束搜索），提升越明显。

三、跨请求的前缀共享

1. 前缀到处都是

真实的推理负载里，大量请求的开头是相同的：

  • 同一个应用的所有用户共用一段系统提示词。
  • 少样本提示里的示例部分对每个问题都一样。
  • 多轮对话中，第 $n$ 轮的输入包含前 $n-1$ 轮的全部内容。
  • 本课程讲过的很多推理算法会对同一个提示词生成多个回答：Best-of-N、自洽性、MBR、树搜索。Agent 每一步的输入也是之前全部历史再加新的观察。

这些相同的前缀，KV 缓存完全一样，理论上只需算一次、存一份。

2. RadixAttention：自动发现可复用的前缀

SGLang（Zheng 等，2023）的 RadixAttention 在请求结束后不立刻丢掉它的 KV 缓存，而是保留在一棵前缀树（radix tree）里。树的每条边是一段 token 序列，从根到某个节点的路径就是一个前缀，节点上挂着对应的 KV 缓存块。新请求进来时，沿着树找到和它匹配的最长前缀，直接复用这部分 KV，只需对剩下的部分做预填充。显存不够时，按最近最少使用（LRU）的原则淘汰叶子节点。

SGLang 还把这个机制和它的前端语言结合：程序里显式写出的分叉（比如对同一段上下文并行问多个问题）会自然地共享前缀。论文报告，在 Agent 控制、逻辑推理、少样本学习、JSON 解码、检索增强生成、多轮对话等任务上，吞吐量最多比当时的其他推理系统高 6.4 倍。vLLM 后来也加入了自动前缀缓存（Automatic Prefix Caching），用哈希表按块匹配前缀，作用类似。

API 服务商对"缓存命中"的输入 token 收费更低，背后就是这种机制。这也给使用者一个实际的建议：把不变的内容（系统提示词、工具定义、长文档）放在提示词开头，变化的部分放在后面，才能命中缓存。

3. Hydragen：共享前缀时注意力也要算得快

前缀缓存解决的是"别重复存、别重复做预填充"。但解码时还有一个问题：一个批次里 64 个请求共享同一个很长的前缀，普通的注意力实现会让每个请求各自把这段前缀的 KV 从显存读一遍，同样的数据被读 64 次。而且每个请求的注意力是一个向量乘矩阵的运算，算术强度很低（第 19 讲补充篇）。

Hydragen（Juravsky 等，2024）把注意力拆成两部分分别计算：对共享前缀的注意力，和对各自独有后缀的注意力，最后用 softmax 的数学性质把两部分精确地合并。前缀部分的做法是：把批次里所有请求的查询向量拼在一起，和前缀的 KV 做一次矩阵乘矩阵，前缀的 KV 只读一次，而且矩阵乘法能充分利用 GPU 的算力。结果是精确的，不是近似。

在 CodeLlama-13B 上，端到端吞吐量最多提高 32 倍，批越大、共享前缀越长，提升越大。在大批量下，把共享前缀从 1K token 加长到 16K，Hydragen 的吞吐量下降不到 15%，基线系统则下降超过 90%。这个方法还能推广到树形的共享结构，在编程竞赛题上（每题采样很多解法）把推理时间又缩短了 55%。

四、压缩 KV 缓存的三个方向

共享能避免重复，但每个请求独有的部分仍然要存。要让 KV 缓存本身变小，有三类方法：改模型结构，让每个 token 存的东西更少；量化，用更少的比特存每个数；淘汰，只保留一部分 token 的 KV。

五、改模型结构：减少 KV 头

1. 多查询注意力（MQA）

标准的多头注意力里，每个头都有自己的 Q、K、V。Llama-2-7B 有 32 个头，就要存 32 份 K 和 V。Shazeer 在 2019 年提出多查询注意力（Multi-Query Attention，MQA）：保留 32 个查询头，但所有头共用一组 K 和 V。KV 缓存一下子缩小到三十二分之一，解码速度大幅提高。代价是模型质量可能下降。

2. 分组查询注意力（GQA）

GQA（Ainslie 等，2023）取了一个中间方案：把查询头分成若干组，每组共用一组 K 和 V。Llama-3-8B 有 32 个查询头、8 个 KV 头，每 4 个查询头共用一组，KV 缓存是多头注意力的四分之一。论文表明，GQA 的质量接近多头注意力，速度接近 MQA；还给出了一个办法，用原预训练计算量的 5% 把已有的多头注意力模型继续训练（uptrain）成 GQA 或 MQA。今天大多数开源模型都使用 GQA。

3. 多头潜在注意力（MLA）

DeepSeek-V2（2024）提出多头潜在注意力（Multi-head Latent Attention，MLA）。它不减少头数，而是把所有头的 K 和 V 一起压缩成一个低维的潜在向量，缓存里只存这个向量，计算注意力时再从它恢复出各个头需要的信息。和此前的 DeepSeek 67B 相比，DeepSeek-V2 的 KV 缓存减少了 93.3%，最大生成吞吐量提高到 5.76 倍（这一提升也来自它的 MoE 结构）。

这三种方法都需要在训练时就采用（或者继续训练），不能直接用在一个现成的模型上。

六、量化 KV 缓存

模型权重可以量化用更少的比特存每个数，比如把 16 位浮点数换成 4 位整数。模型变小、读得更快，精度略有损失。到 8 位或 4 位（CMU 11-711 第十九讲），KV 缓存也可以。难点在于 KV 缓存里的数值分布有特殊结构。KIVI（Liu 等，2024）分析了常见模型的 KV 缓存，发现键（K）缓存里有少数几个通道（向量的某几维）的数值始终特别大，所以 K 应该按通道分组量化；值（V）缓存没有这种通道上的异常，应该按 token 分组量化。按这个方案，KIVI 不需要任何微调就能把 KV 缓存压到 2 位，Llama、Falcon、Mistral 的质量几乎不变。峰值显存（包括模型权重）降低到原来的 1/2.6，批大小可以加大到 4 倍，实际推理吞吐量提高 2.35 到 3.47 倍。

七、淘汰：只保留重要的 token

1. 只留最近的窗口为什么不行

最直接的想法是只保留最近 $W$ 个 token 的 KV，更早的丢掉（滑动窗口）。StreamingLLM（Xiao 等，2023）发现，一旦文本长度超过窗口，模型表现会突然崩溃。

2. 注意力汇点

原因是论文观察到的一个现象：模型会把大量注意力分数放在最开头的几个 token 上，即使这些 token 在语义上并不重要。论文称之为注意力汇点（attention sink）。softmax 要求注意力分数加起来等于 1，当一个查询在前文里找不到特别相关的内容时，多余的注意力需要一个"去处"，开头的 token 对后面所有位置都可见，于是成了这个去处。滑动窗口把开头的 token 丢掉后，注意力分布被打乱，模型就崩溃了。

StreamingLLM 的做法因此很简单：保留开头几个 token 的 KV，再加上最近一个窗口的 KV。不需要任何微调，Llama-2、MPT、Falcon、Pythia 就能在多达 400 万 token 的流式输入上稳定地做语言建模，比每次滑动窗口都重新计算的基线最多快 22.2 倍。论文还发现，预训练时专门加一个占位 token 作为注意力汇点，流式部署的效果会更好。这种方法让模型能持续生成，但被丢掉的中间内容模型就再也看不到了，它不等于真正的长上下文理解。

3. 重点 token

H2O（Zhang 等，2023）观察到，计算注意力时，少数 token 贡献了大部分的注意力分数，称为重点 token（heavy hitter）。它们的出现和文本里词语的频繁共现密切相关，删掉它们会让表现明显下降。H2O 的淘汰策略是动态保留两类 token：最近的 token 和累计注意力分数最高的重点 token。保留 20% 的重点 token 时，在 OPT-6.7B 和 OPT-30B 上，吞吐量比 DeepSpeed Zero-Inference 和 Hugging Face Accelerate 最多高 29 倍，比 FlexGen 高 3 倍；同样批大小下延迟最多降低 1.9 倍。

淘汰类方法都是有损的：被丢掉的 token 如果后面突然变得重要（比如用户问到前文的某个细节），模型就无法找回。所以它们更适合流式对话这类不需要精确回忆全部历史的场景。

八、和本课程推理算法的关系

  • 第 4 讲的束搜索、第 12 讲的 Best-of-N、第 14 讲的 MBR、自洽性都会对同一个提示词生成多个序列，前缀共享直接降低了这些方法的成本。第 15 讲讨论推理计算是否划算时，用不用前缀共享会明显改变结论。
  • 第 5 讲的最佳优先搜索和第 11 讲的 Agent，每一步都在同一段历史后面追加，很适合 RadixAttention 这样的树形缓存。
  • 第 16 讲提到"能否复用缓存"会影响 token 的成本，这一讲讲的就是缓存怎样复用。

九、小结

KV 缓存每个 token 占几百 KB，大批量、长上下文时比模型参数还大，同时限制了能服务的请求数和每步解码的速度。PagedAttention 把 KV 缓存切成固定大小的块按需分配，几乎消除了碎片，也让同一请求的多个分支能共享块。RadixAttention 用前缀树在不同请求之间自动复用相同前缀的 KV；Hydragen 让共享前缀的注意力只读一次 KV 并改用矩阵乘法。要让 KV 缓存本身变小，可以从模型结构上减少 KV 头（MQA、GQA）或压缩成潜在向量（MLA），可以把 KV 量化到 2 位（KIVI 对 K 按通道、对 V 按 token 量化），也可以淘汰一部分 token（StreamingLLM 保留注意力汇点和最近窗口，H2O 保留最近 token 和重点 token），后者是有损的。
