第八讲：自我修正与迭代改进

自我修正循环与四个设计维度，推敲网络的两遍解码，把编辑过程建模为标注加生成，学习编辑的表示，Self-Refine，Self-Debug 的代码执行反馈，Reflexion 与 CRITIC，以及"大模型还不能自我修正推理"

主讲：Graham Neubig · 2025 年 9 月 18 日
资料来源：课程主页（本讲的 HTML 幻灯片未能获取） · 课堂录像（本文依据录像字幕整理课堂口述内容；课后三篇学生论文报告未包含） · 主要阅读：Self-Refine（Madaan 等，2023）；Teaching Large Language Models to Self-Debug（Chen 等，2023）

一、自我修正循环

上一讲讲思维链，下一讲讲推理模型，Graham 把推理模型看作把自我修正和思维链合在一起。今天讲的是更显式的自我修正方法，在很多场景里仍然很有用。

语言模型通常一遍从左到右生成，长的或复杂的输出容易出错。人写文章、写代码则会反复修改，先写出来，再回去打磨细节。这些方法就是帮模型做这件事。一般的流程（有细节差别）：设一个最大迭代次数和停止准则；生成初始输出；在最大迭代次数内循环（一般要有硬性上限，免得无限循环）：评估输出，按停止准则判断评价是否认为输出已令人满意，不满意就修改输出。不复杂，但细节很重要，今天讲的方法大多是在细节上让它管用。几个设计维度：

  • 评价是显式还是隐式：显式是明确提示或训练模型判断输出好不好；隐式是不单独判断，模型在修改步里不再做任何改动，就认为输出已经够好。
  • 是否专门训练模型擅长自我修正。
  • 修改步以什么为条件：输入、输出、评价本身，不同方法组合不同。
  • 是否用外部工具：有的评价只靠语言模型，有的借助外部工具判断输出好坏。

今天介绍七篇论文，六篇是自我修正方法，一篇相关但不完全一样，幻灯片上有一张表按这几个维度对它们分类。

二、早期的可训练方法

1. 推敲网络

Deliberation Networks（Xia 等 2017），那时神经语言生成刚兴起。想法很简单：不只生成一个输出，而是先生成再修改。两遍解码："推敲与修改"。第一遍生成初稿序列，第二遍在掌握全局上下文后修改。算法简单到连循环都没有，重要的是它表明可以训练模型擅长自我修正。训练目标是给定输入时最终输出的对数概率，对中间输出 $y'$ 求和：

$$\log P(y\mid x) = \log\sum_{y'} P(y\mid y', x;\theta_2)\,P(y'\mid x;\theta_1)$$

（当时用编码器-解码器模型，还有编码器参数 $\theta_e$，可以先忽略；那时是两个模型，现在大概会训练一个模型同时擅长两件事。）这有什么问题？学生先问离散的东西能否求梯度，好问题；但更大的问题是 $y'$ 的空间有多大？无穷大，它是所有序列的空间，就算长度限制在 100，也有 $|V|^{100}$ 种，没法求这个和。标准解法是什么？学生答：采样。采样若干个中间序列，再计算在每个中间序列条件下最终输出的对数概率；采样数大于 1 时，能看出哪个中间状态让最终输出概率更高或更低，据此调整。用 2025 年的话说这基本就是 GRPO：采样多个输出，按奖励给它们加权，这里的奖励就是那个对数概率。学生问输出序列是什么：是有监督的目标，他们做的是机器翻译，输入德语、输出英语；换成问答，目标就是答案。两遍共享解码器，在当时很强的基线上有很大提升（现在已经不算强了）。也可以多步训练，启发式地做，或者像扩散模型那样高效地反复做，那不在这一讲。

2. 把编辑过程建模出来

Learning to Model Editing Processes（Reid 和 Neubig），Graham 自己的论文，有两点有意思：数据，能从网上自然产生的编辑过程获取训练数据；表示，不是训练模型直接编辑文本，而是先找出哪里该改、怎样改，再去改。

算法和前面的自我修正循环相近，有两处主要不同。有输入和编辑历史，可以从空白开始，也可以从一段待编辑的文本开始。在没结束之前（比如预测出空编辑或用完迭代次数）：预测编辑操作（插入、删除、保留、替换）；根据编辑操作和到目前为止的编辑历史生成内容；按生成的内容应用编辑，这一步是确定性的；把这次编辑加入历史，供之后参考。

具体是这样分解的：先对输入的每个 token 做标注，比如在 the 后面要插入一个词，这几个 token 要替换，那几个要删除，这是对每个 token 的序列标注任务。删除是确定性的，直接去掉；插入和替换要生成新内容，而且是并行的：对每个插入或替换的位置，以该处的表示为条件生成，比如生成 domestic 或 domesticated descendant of。有了这些，就能确定性地得到"The domestic dog is a domesticated descendant of the wolf"。如果要反复编辑很长的文档，这很好：不用重新生成每个 token，一遍标注模型就能预测所有位置的操作，这只是编码，快得多，再生成较短的片段。学生问编辑操作是否已包含替换成什么：不包含，预测编辑时还不知道要填的词，所以需要第二步；生成的内容以句尾 token 结束，长度可变。

他们构建了两个数据集：WikiRevisions，Wikipedia 保留了所有修订历史；CodeRevisions，来自 GitHub 的代码修改历史。实验一是给定当前文本或代码和编辑意图（来自提交说明或 Wikipedia 的修改描述），预测编辑；实验二是参考之前的编辑预测之后的编辑，结果表明参考过去的编辑确实有助于预测未来的编辑：这里改过，接下来很可能再改。这很合理，Wikipedia 上常见编辑战、垃圾内容战，有人加了垃圾内容，之后会被删掉，所以能预测它会被删除。这说明编辑过程有别的建模方式，数据构建方法也许对大家的工作有启发。

3. 学习编辑的表示

Learning to Represent Edits（Yin 等，Graham 与 CMU 一位学生合作）：学习表示两段序列之间做了哪类修改。给定修改前和修改后，得到一个表示"这是哪种编辑"的向量；再给另一个相似的修改前文本和这个编辑表示，生成修改后的文本，可以端到端训练。编辑编码器的具体形式不重要，现在大概会直接把两段送进大模型微调。重要的是编辑表示限制在 512 维，这样学到的是"哪类编辑"的好表示，而不是把做了什么全记下来。训练目标像自编码器：从修改前后学到编辑表示，再以它和修改前文本为条件计算修改后文本的对数概率，所以要把尽可能多的信息塞进 512 维向量，告诉模型该做哪类编辑。编码器和解码器联合训练，因为两者都影响似然。

评估主要不是看它会不会编辑，而是看能否找出相似的编辑：比词袋模型准确得多。这是在微软代码分析团队实习时做的，他们想找出 GitHub 上人们做的相似修改，比如都是修复某个安全漏洞；为此用各种代码转换工具造了一个伪数据集，看它能否识别出同一种工具产生的相似变换。Graham 说如果对如今流行的推理策略感兴趣，这可以用来分析模型采用了哪些推理策略，比如编码每一步、预测下一步。

三、大模型上的自我修正

1. Self-Refine

最早在大模型上不训练、只靠提示做自我修正的论文之一（Madaan 等 2023）：大模型可以评价自己的输出，并据此生成更好的输出。算法就是前面的自我修正循环，没什么花哨的，全部靠提示：

  • 生成：标准的少样本提示，带几个任务相关的示例。
  • 反馈：提示模板类似"这个输出为什么不正确、不流畅（或你想要的任何品质）"，指出具体可改进之处。
  • 修改：把原始输入、当前输出和反馈合在一起，"根据反馈改进这个输出"。
  • 停止：用简单的启发式检查反馈是否正面，或者固定迭代次数。

结果有意思：在某些情形帮助很大，比如提高代码可读性、对话回复的友好程度、改变输出情感等；在大家如今很关心的数学推理上帮助不大。这些任务都是有点刁钻的小任务，算不上对语言模型很难的主要任务。Graham 认为原因是：模型没被专门训练擅长的那类非数值任务，就是不借助外部工具的自我改进最有效的地方。他们还发现越强的模型提升越大，GPT-4 从自我修正中得益更多；论文说"更大的模型更好"，Graham 认为实际上是"更强的模型更好"。

2. Self-Debug

Teaching Large Language Models to Self-Debug（Chen 等 2023）也符合这个模式，但和之前只靠语言模型改进输出的方法不同，它引入了外部工具：代码执行。生成代码后真的去执行，看是否通过单元测试；全部通过就结束，否则让语言模型解释错误，再根据解释修改。学生问为什么不直接把调用栈传回模型：好问题，也许是想压缩得短一些；这是 2023 年的论文，现在的模型训练数据里见过足够多的调用栈，大概不需要这样了。

结果在基线之上有从一点到很多不等的提升，如果你用过语言模型写代码，大概不意外，但这是最早的结果之一。去掉执行反馈，提升就小得多。另一个有意思的发现：这是 Graham 所知最早比较不同推理时算法的论文之一，他们和自洽性比较，自洽性要采 16 个样本，自我调试只需要一个样本。这说明引入外部信号或别的花推理计算的方式，可以和更暴力的方法竞争，很适合作为对比。

3. Reflexion 与 CRITIC

Reflexion（Shinn 等 2023）大致是 Self-Debug、Self-Refine 加上类似编辑过程论文里的做法：评估，获取外部反馈，自我反思，产生经验写进记忆，用来在之后的迭代里进一步改进。和编辑过程论文一样，把评价追加到记忆里，循环时考虑所有过去评价的记忆，而不只是最近一条。他们在很多领域上做了评估。

CRITIC（Gou 等）不像 Self-Debug 那样用固定的代码执行流程，而是让评价者自己使用工具：验证时可以查知识库、运行代码解释器、用 Perspective API 检查情感是否正面、用搜索引擎等，按任务类型配不同的工具。在评估的所有任务上都有显著提升。这给设计推理时算法提了一个问题：要在生成时加工具，还是在评价时加工具，或者别的方式？讲到工具使用时还会再谈。

学生问：这些流程之所以简单，是不是因为骨干模型很强，想用于小模型怎么办？前几篇不是这样，那些是更老的论文，骨干弱得多，但它们都涉及训练。Graham 认为 GPT-4 大概是第一个不经专门训练就自发具备自我修正能力的模型；下一讲会讲，现在专门训练推理模型具备这种能力，比 GPT-4 强得多。所以如果模型自发能力不够强，流程里某处就需要训练。

四、负面结果

写论文的人倾向于写正面结果，偶尔有人写负面结果，也要介绍。Large Language Models Cannot Self-Correct Reasoning Yet（Huang 等 2024）的主要发现：没有外部反馈的内在自我修正经常失败；只让模型自我修正，性能常常甚至下降；很多模型难以发现自己的错误，对模型难做的事，也难以检查；有确认偏差，倾向于强化最初的推理。

  • 成功的场景：语法、风格、格式；有外部反馈时，比如代码执行和事实核查，能显著提升；骨干模型越强效果越好。
  • 困难的场景：深层推理错误，比如数学证明和逻辑（这些实验用的模型没有专门训练过这些任务）；知识缺口，模型不知道某个事实，就没法自我修正；复杂的多步问题。

例子：很简单的数学题，它能改对；也能把本来对的改错。所以并没有"这种情况用、那种情况别用"的铁律。

回到前面的几个维度，在课程项目或作业里用自我修正时可以想：要显式评价还是隐式评价？要不要训练模型？以什么为条件，思维链、多步？要不要用工具来澄清输出？学生问：为什么不全都选"要"？Graham 说一是计算成本，这是推理课，要在大量数据上推理，期末排行榜的分数也取决于此，工具不必要时就别加；二是工业上的运维复杂度，启动一个代码沙盒比调一个语言模型 API 复杂得多，系统里多一个会坏的部件。他说这就是这门课该问的问题。

六、小结

自我修正就是生成、评价、修改的循环，设计上要决定评价是显式还是隐式、是否训练、修改以什么为条件、是否用外部工具。早期方法都靠训练：推敲网络用采样近似对中间稿的求和，训练两遍解码；编辑过程模型先给每个 token 标注插入、删除、替换，再并行生成要填的内容，并利用 Wikipedia 和 GitHub 的修订历史做数据；编辑表示用一个小向量刻画"哪类修改"。到了 GPT-4，模型不经训练就能靠提示自我修正，Self-Refine 在可读性、风格这类任务上有效，在数学上帮助不大；引入代码执行等外部反馈的 Self-Debug、能调用工具的 CRITIC、带记忆的 Reflexion 提升更稳。没有外部反馈时，模型常常发现不了自己的推理错误，甚至把对的改错，所以要不要加评价、训练和工具，得在效果、计算成本和系统复杂度之间权衡。
