第二十三讲（补充）：构建 MLC-LLM

用机器学习编译让同一个模型跑在服务器、手机、浏览器上：跨层级的中间表示、自定义量化格式、符号形状，云端的延迟与吞吐优化，以及 XGrammar 的高效结构化生成

原课：Building MLC-LLM，Tianqi Chen 客座讲座 · 2025 年 11 月 20 日
本讲没有公开资料，以下根据其他公开资料整理，不是原课内容：Tianqi Chen 的公开演讲 Enable Large Language Model Deployment across Cloud and Edge with ML Compilation（2025 年 2 月上传，依据录像字幕）；论文 TVM（Chen 等，2018）、Relax（Lai 等，2023）、WebLLM（Ruan 等，2024）、XGrammar（Dong 等，2024）

说明

课表上第 23 讲是 Tianqi Chen 的客座讲座，题目是构建 MLC-LLM，没有公开录像和幻灯片。Tianqi Chen 任教于 CMU，是 XGBoost、Apache TVM 和 MLC-LLM 的主要作者之一。这篇补充主要根据他 2025 年初一场内容相近的公开演讲整理，演讲分为三部分：跨平台部署、云端延迟优化、结构化生成，这里沿用这个结构，并用相关论文补充细节。

一、问题：模型要跑在很多不同的设备上

Tianqi Chen 在演讲开头提到生成式 AI 给系统带来的几个挑战：模型占用大量显存；需要很专门的计算；要和各种应用集成；模型结构还在不断变化。他特别关心一个方向：除了在云端运行，让模型也能在个人设备上运行，云端和边缘设备配合使用。

难点在于设备种类太多。服务器上是 NVIDIA 或 AMD 的 GPU，苹果电脑和 iPhone 用 Metal 编程，安卓手机用 Vulkan 或 OpenCL，浏览器里只能用 WebGPU。传统做法是为每个平台手工写一套计算核（kernel），工作量很大，新模型出来还要全部重写。

MLC（Machine Learning Compilation，机器学习编译）的思路是：把模型写成一种中间表示，由编译器针对每个平台自动生成代码。这和第 13 讲补充篇 Khattab 讲的"用高级语言加编译器代替手写底层代码"是同一个道理，只是这里的对象是计算核。这条路线的前身是 2018 年的 TVM：一个面向深度学习的编译器，在计算图层面和单个算子层面做优化，用学习出来的代价模型自动搜索代码优化方案，在手机 CPU、手机 GPU、服务器 GPU 上都达到了与手工优化库相当的性能。

二、编译流程的关键设计

1. 跨层级的表示

MLC-LLM 用一个叫 IRModule 的结构保存整个模型，里面是一组用类似 Python 的脚本写成的函数。关键是这个表示同时包含两个层级（Relax 论文称之为跨层级抽象）：

  • 高层的计算图：描述每一步计算哪个中间结果，写起来紧凑。
  • 低层的循环程序：直接描述一个算子怎样一层层循环计算，比如矩阵乘向量怎样遍历每个元素。它更灵活，能精细控制计算的细节。

同一个模块里还能直接调用外部的高性能库。编译器在这个表示上执行一系列可以自由组合的变换：节省显存、把某些算子交给高效的库、把参数切分到多张 GPU、尝试新的算子融合方式、换用新的注意力库等等。

2. 自定义量化格式

跨层级表示带来的一个直接好处是支持任意的量化格式。本地部署常常要把权重压到 4 位整数，读到芯片上时再即时解码成浮点数参与矩阵乘法。大多数计算图框架不原生支持 4 位整数类型。MLC 没有新增数据类型，它用一个低层函数直接写出解码过程，再由编译器的变换自动把这个解码过程融合进矩阵乘法，生成一个计算核。想换一种量化格式，只需要改解码函数，不用改整个编译流程。融合之后，4 位权重从显存读进来后直接在芯片上解码，读取量是 16 位的四分之一。第 19 讲补充篇说过，量化主要节省的是带宽。

3. 符号形状

语言模型里很多张量的形状是动态的：预填充时序列长度不固定，批处理时批大小不固定。很多编译器用"任意形状"处理，把动态的维度标成问号。这样实现简单，但编译器不知道不同问号之间的关系。

Relax 引入了一等公民的符号形状：把动态维度标成符号变量，比如 $n$，同一个符号在程序各处表示同一个值。演讲里举的例子是：一个形状为 $n \times 2 \times 2$ 的张量，变形成 $n \times 4$ 后，编译器能证明两者的元素总数相同，虽然编译时并不知道 $n$ 是多少。这些关系让编译器能做更多优化，比如提前规划显存。对实在无法确定的形状（比如结果取决于数据内容的算子），可以在运行时匹配到一个新的符号变量，继续参与后面的分析。这些符号关系在函数提取、内联等变换中都会被保留，并且在高层计算图和低层循环之间互相传递。

4. 一套引擎，到处运行

这些设计组合起来就是 MLC 引擎：同一条编译流水线为每个后端生成代码，可以在 Windows、Linux、Mac 的各种 GPU 上运行，并提供与 OpenAI 兼容的服务接口。它还支持 iOS（有一个叫 MLC Chat 的应用，能在手机上离线运行 30 亿参数级别的模型）、安卓、只有很小 GPU 的百元级开发板、Steam Deck 游戏机（用 Vulkan 后端）。

由于所有后端共用同一套引擎代码，推测解码、结构化生成这类新功能在服务器后端实现后，手机和浏览器等其他后端也能同时用上，从云端部署迁移到本地部署更容易。

5. 浏览器里的大模型：WebLLM

WebLLM 把同一条编译流程用到浏览器上：生成 WebGPU 计算核（WebGPU 是浏览器直接访问本机 GPU 的新标准）和 WebAssembly 代码。打开网页就能在本机运行模型，不用安装任何东西；第一次需要下载权重并缓存，之后可以完全离线运行，数据不离开本机。演讲中他在 M2 Max 笔记本上演示了在浏览器里运行 Llama 8B 模型。WebLLM 也是一个 npm 包，提供 OpenAI 风格的 API，开发者可以把本地模型嵌入自己的网页。论文报告，WebLLM 在同一设备上能达到原生运行性能的约 80%。

三、云端：同时兼顾延迟和吞吐

演讲的第二部分讲云端服务。用户希望每个 token 出得越快越好；服务商希望把很多请求放进一个批，降低成本。两者是矛盾的（第 18 讲补充篇）。过去很多服务系统只追求吞吐量，Tianqi Chen 团队则针对低延迟场景做了大量优化，目标是在给定的每 token 时间约束下，尽量提高吞吐量。以 Llama 3 为例，很多场景要求每秒 50 个 token 以上，有些要求每秒 100 个以上。

他提到两个观察。一是张量并行度的选择存在交叉点：如果要求每秒 60 到 70 个 token 以上，应该用更高的张量并行度（模型切分到更多 GPU）；如果能接受较长的延迟，用较低的并行度、提高并发数，每张 GPU 的产出更高。二是推测解码（第 21 讲补充篇）过去的研究多只考虑批大小为 1。要真正获益，需要把批处理和推测解码结合起来，为此需要专门的系统优化，比如能在一个批里同时验证所有请求草稿的 GPU 计算核，以及不需要每次重新分配显存的概率分布管理。这样在批大小为 1 时能达到每秒 100 个 token 以上，批大小到 30 左右时，延迟与吞吐的取舍也优于其他系统。

这些优化同样用于 MLC 引擎，所以在 H100 上做的改进，也能直接迁移到安卓和 WebGPU 后端。

四、结构化生成：XGrammar

1. 为什么需要

Agent 需要模型输出结构化的内容：一次函数调用要写清函数名和参数，比如打电话要给出号码和内容；或者输出符合某个 JSON Schema 的 JSON。第 6 讲讲过约束解码：每一步检查词表里哪些 token 接在当前输出后面仍然符合格式，把不符合的 token 屏蔽掉，只在合法的 token 里采样。这样能保证输出一定符合格式。

2. 上下文无关文法很灵活，也很慢

描述格式最灵活的方式是上下文无关文法（CFG）。正则表达式对应一个有限状态自动机，可以提前算好每个状态下哪些 token 合法。CFG 的规则可以递归，比如 JSON 对象里可以嵌套对象，需要一个栈来记录嵌套到了哪一层，状态无法预先穷举，只能在运行时检查。早期的实现（比如 llama.cpp 的语法功能）对词表里每一个 token 都在运行时跑一遍文法检查。Llama 3 的词表有 12 万多个 token，这样做很慢，批大小一大，生成掩码的时间甚至会超过模型计算本身。

3. 把 token 分成两类

XGrammar（Dong 等，2024）的关键观察是：大多数 token 是否合法，只取决于文法当前所在的位置，而不取决于栈里更深的内容。这类叫上下文无关 token，可以预先检查并缓存结果。只有少数 token 的合法性取决于整个栈的状态，叫上下文相关 token，必须在运行时解释执行。XGrammar 在此基础上做了几件事：

  • 通过文法变换扩展上下文，尽量把更多 token 变成可以预先检查的一类。
  • 用一种高效的持久化栈加速剩下的上下文相关 token 的检查。
  • 和推理引擎协同设计，让文法的计算在 CPU 上与 GPU 的模型计算重叠进行，掩码在 GPU 算完下一个 token 的分布时已经准备好了。

论文报告，XGrammar 比已有方案最多快 100 倍，结合推理引擎后，结构化生成几乎没有额外开销。演讲中提到，JSON Schema 场景下已有方案优化得较多，差距较小；通用的 CFG 场景差距更大。XGrammar 于 2024 年 11 月开源，之后被集成进 SGLang、vLLM、TensorRT-LLM 和 MLC-LLM 等主流推理框架。CMU 11-768 第二讲从 Agent 工具调用的角度也介绍了 XGrammar。

五、和本课程其他内容的联系

  • 第 6 讲的约束解码讲的是算法，XGrammar 讲的是怎样让它在真实系统里几乎没有开销。
  • 第 19 讲补充篇的硬件分析解释了为什么要做量化融合和为什么不同设备需要不同的计算核。
  • 第 21 讲补充篇的推测解码，在 MLC 引擎里和批处理结合，并通过统一的引擎带到各个平台。

六、小结

MLC-LLM 用机器学习编译解决"同一个模型要在很多种硬件上高效运行"的问题：模型写成同时包含计算图、底层循环和外部库调用的跨层级中间表示，编译器在上面执行可组合的变换，再为每个后端生成代码。跨层级表示让任意量化格式的解码可以融合进矩阵乘法；符号形状让编译器在动态形状下仍能推理张量之间的关系。同一套引擎覆盖服务器、电脑、手机、开发板和浏览器（WebLLM 能达到原生性能的约 80%），在一个平台上做的优化可以带到所有平台。在云端，团队在延迟约束下优化吞吐，并把推测解码和批处理结合起来。XGrammar 把词表分成可预检的上下文无关 token 和需要运行时检查的上下文相关 token，让基于上下文无关文法的约束解码几乎没有额外开销。
