自我改进的 Harness 工程

模型外面那层负责调度、记忆、工具和评估的系统（harness），怎样从人手写变成由模型自己去搜索和改进，以及它离“递归自我改进”还差什么

作者：Lilian Weng · 发表于 2026 年 7 月 4 日 · 整理：Joyce（@JOYCE9896）
资料来源：Harness Engineering for Self-Improvement（Lil'Log；本文依据原文英文网页整理，是中文转述和讲解，不是逐字翻译；图片引自原文，版权归原作者）

这篇文章讲什么

递归自我改进（recursive self-improvement，RSI）指 AI 用自己现有的能力去改进产生这份能力的系统，改进后的系统又能做出更好的改进。作者认为，近期最现实的 RSI 路线不会从“模型直接改自己的权重”开始，更可能从 harness 开始。harness 是包在基础模型外面的那层系统，负责编排执行流程，决定模型怎样思考和规划、怎样调用工具和行动、怎样感知和管理上下文、怎样存放产物、怎样评估结果。Claude Code 和 Codex 这类编程 agent 产品的成功说明，这一层和模型本身的智力差不多同样重要。

文章分三大块。第一块讲 harness 的常见设计模式（工作流循环、用文件系统当持久记忆、子 agent 与后台任务），并以编程 agent 为例列出它们的工具集。第二块是主体，按“被优化的对象”逐级往上讲：上下文工程（ACE、MCE、Meta-Harness）、工作流设计（AI Scientist、ScientistOne、Autodata、ADAS、AFlow）、自我改进的 harness（STOP、Self-Harness、AHE 等）、进化搜索（Promptbreeder、GEPA、AlphaEvolve、ShinkaEvolve、DGM 等），以及把 harness 和模型权重一起优化（SIA、Continual Harness）。第三块列出走向完整 RSI 还没解决的七个难题。附录整理了几个评测 AI 做科研和工程能力的 benchmark。

01. 引言：递归自我改进与 harness

原文小节：（开篇引言，无标题）

RSI 这个概念可以追溯到 I. J. Good (1965)。他把“超智能机器”（ultraintelligent machine）定义为一个在所有智力活动上都能超过人类、并且能设计出更好的机器来改进自身的系统。Yudkowsky (2008) 用 “recursive self-improvement” 这个词指一个具体的反馈回路：AI 用它当前的智力，去改进产生它智力的那套认知机制。

放到今天的 AI 里，这个反馈回路可以指模型直接重写自己的权重，也可以更宽泛地指模型去改进训练流水线和部署系统，从而训练出一个在有经济价值的任务上表现更好的后继模型。作者引用 Anthropic 和 OpenAI 的材料指出，前沿实验室的 AI 研发速度已经明显加快。

作者专门点出“部署系统”，因为原始模型和真实使用场景之间的那一层，看起来和模型的原始智力（也就是预训练刚结束时的评测成绩）同样重要。Harness 是 AI 部署里的重要组件，Claude Code 和 Codex 这些成功的编程 agent 产品就是证明。按作者的定义，harness 是包在基础模型外面的系统，它编排执行过程，决定模型如何思考和规划、如何调用工具并行动、如何感知和管理上下文、如何存放产物、如何评估结果。

这篇文章聚焦 harness 工程方面的研究，以及它怎样为 RSI 出力。近来关于自动科研（auto-research）、自我改进 agent、进化式程序搜索的很多工作，都可以围绕这个问题来组织。另有一些工作也符合 RSI 的设想，比如模型自我博弈（self-play）、合成数据、测试时训练（test-time training），以及更大的持续学习（continual learning）主题（例如 Yuan et al. 2024、Chen et al. 2024、Zhao et al. 2025、Choi et al. 2026），这篇文章不展开它们。

02. Harness 的设计模式

原文小节：Harness Design Patterns

作者 2023 年那篇 agent 综述里，早期 agent 框架的公式是“agent = LLM + 记忆 + 工具 + 规划 + 行动”。harness 工程在这之上又加了几样东西：工作流设计（例如循环怎么设计，loop engineering）、评估、权限控制、持久状态管理。它已经超出了 prompt 模板的范围，更接近运行时（runtime）和软件系统设计：模型怎样观察、行动、记忆、自查、改进。

作者认为设计应当刻意保持简单和通用，这样才能泛化；最好参照已有的软件工程实践，因为模型在预训练里已经见过大量这类知识，能直接用上。操作系统和 harness 之间有很强的相似性：harness 和 OS 一样，应该把复杂逻辑封装在里面，对外接口保持简单。同时，配置文件、工具接口和其他协议可能会逐渐在行业里标准化。

模式 1：工作流自动化

原文：Pattern 1: Workflow Automation

要让模型自动干活，一个核心设计是给它定义一个可以操作、测试、迭代的工作流。Karpathy 的 autoresearch 仓库（https://github.com/karpathy/autoresearch）是一个干净的例子，展示了这种工作流怎么搭。常见的工作流是一个以目标为导向的循环：计划、执行、观察/测试、改进、再执行，直到目标达成。过程中模型可以主动向用户提问，澄清任务要求或执行偏好。

工作流图还强调一点：模型要分析自己的轨迹（trajectory，即一次运行中模型的每一步输出和工具返回组成的完整记录）和失败案例，然后通过一个“agent 运行时”来迭代推进，而不是靠一个静态的 prompt 模板。

模式 2：用文件系统做持久记忆

原文：Pattern 2: File System as Persistent Memory

长程（long-horizon）agent 系统里反复出现的一个模式，是用简单的控制手段去管理丰富的状态和产物。harness 不应该把整个工作流和全部日志都塞进上下文，持久的状态应该放在文件里。在长程 agent 运行中，实验日志、代码 diff、论文摘要、错误栈、过去的运行轨迹这些产物，长度往往远超模型训练时用的上下文窗口。

学会读、写、改文件系统（通常靠 bash 命令）是 LLM 的一项基础技能。所以用文件这种简单形式来管理持久记忆，会随着模型核心能力的提升自然受益。

模式 3：子 agent 和后台任务

原文：Pattern 3: Sub-agent and Backend Jobs

harness 可以派生多个子 agent（subagent）并行执行，也可以监控后台任务。当主 agent 需要同时探索多个假设、并发跑实验、或者把一个独立子任务交出去又不想污染自己的上下文时，这很有用。这时父 agent 需要一个小型进程管理器：启动任务、查看日志、取消失败的运行、把结果合并回主线程。

这里的设计要点是让并行变得显式、可检查。如果子 agent 的输出只存在于临时的对话上下文里，它们很快就会过时、被埋掉。如果它们以文件、日志和状态记录的形式保存下来，模型在被中断后可以恢复，也能对自己的执行历史进行推理。

案例：编程 agent 的 harness

原文：Case study: Coding Agent Harness

主流编程 agent 的核心接口已经趋于稳定，Claude Code、Codex、OpenCode 和 Cursor 一类的 agent 普遍使用下面这样的循环：

有了一套工具，编程 agent 就能在给定仓库里开发和调试问题，就像人类开发者手里有 IDE 一样。下表列出常见工具分组。作者说明这不是完整清单，只是演示；感兴趣可以看这个仓库。

分组工具定义
File system（文件系统）文件发现：glob、grep、ls
文件读取：read、read_many
文件修改：write（写一个全新文件）；edit（按字符串精确匹配替换）；multi_edit；apply_patch（应用结构化的 patch/diff）
Shell execution（执行命令）运行命令：bash、PowerShell
IOlsp，git 工具如 git_status、git_diff、git_commit
External context（外部上下文）MCP 工具、Skills
Web search（网页搜索）web_search、web_fetch、浏览器工具
Artifacts（产物）读文档、图片；生成 HTML、图片

几个名词：lsp 指 Language Server Protocol，编辑器用来做跳转定义、查引用的那套接口。MCP（Model Context Protocol）是一种让模型接入外部工具和数据源的标准协议。Skills 是打包好的一组说明和脚本，模型在需要时加载。

Harness 层还是核心智力？

原文：Harness Layer vs Core Intelligence?

未来的 RSI 会在多大程度上依赖 harness 工程，很难预测。作者的判断是，RSI 的近期路径不太可能从模型直接重写自己的权重开始。她预测的现实近期路径有两点：

  • Harness 工程会朝“元方法论”（meta-methodology）方向演化，也就是除了改进答案，还要改进“得到更好答案的那套机制”。harness 系统自身变成优化目标，启发式规则变少，通用机制变多。
  • 反过来，成熟的 harness 让自动科研能够服务于模型的自我改进循环；更聪明的模型又能防止 harness 被过度工程化，让整个系统可持续。

最终，很多 harness 上的改进可能会被内化到模型的核心行为里，但模型和外部上下文、工具之间的接口应该会保留。作者举了一个温和一些的先例：prompt 工程。随着指令微调（instruction tuning，用“指令-回答”数据微调模型，让它更会听指令）和模型推理能力的提升，手工 prompt 技巧变得没那么重要了，但说明目标、约束、上下文和评估方式的需要并没有消失。

03. Harness 优化

原文小节：Harness Optimization

在 harness 系统里，被优化的对象大致经历了这样一个递进：指令 prompt → 结构化上下文 → 工作流 → harness 代码 → 优化器代码。模型越聪明、越强，我们就越往更复杂的优化对象和更通用的方法走。下面各小节大体按这个顺序展开。

上下文工程

原文：Context Engineering

agent 任务的时间跨度大幅变长以后，把所有工具返回和模型生成都直接追加进上下文，很快就会失控。上下文管理这一层的作用，是给 LLM 构造更有结构、更精简的上下文，并管理持久状态。长上下文研究肯定会继续进步，但目前长上下文能力和上下文工程有时是交织在一起的。

ACE：把上下文当成不断演化的手册

Agentic Context Engineering（ACE；Zhang et al. 2025）把上下文看作一本不断演化的“手册”（playbook），不让它变成一段越写越长的 prompt。它用三个组件维护一本由要点条目组成的上下文手册，每条要点有一个标识符和一段描述：

  • Generator（生成器）：参考手册里的要点，产生任务轨迹。
  • Reflector（反思器）：从成功和失败的轨迹中提炼经验。
  • Curator（整理器）：用增量的、逐条的方式更新结构化上下文。

反复重写上下文容易出两种毛病：上下文坍缩（context collapse，多轮重写后细节逐渐丢失）和简短偏置（brevity bias，重写倾向于越写越短、越写越笼统）。为了避免这两点，ACE 的一个设计是：curator 不重写整段 prompt，它只输出一组结构化的条目，形式是（标识符, 描述），再用确定性的逻辑把这些条目合并进一本结构化的上下文日志。这些条目会定期精炼和去重。

MCE：把“怎么管上下文”也交给优化

ACE 能从运行中学到经验，这让我们朝自我管理的记忆迈进了一步，但它的更新规则和整体工作流仍然是手工设计的。为了更接近自我改进的循环，Meta Context Engineering（MCE；Ye et al. 2026）把“机制”（如何管理上下文）和“内容”（上下文里放什么）分开：在元优化层做技能（skill）的演化，在基础层做上下文的优化。

MCE 里的一个技能 $s \in \mathcal{S}$ 定义了一个上下文函数 $c_s=(\rho_s,F_s)$，它把输入 $x$ 映射成上下文 $c = F_s(x;\rho_s)$，其中：

  • $\rho_s = \{\rho_1,\dots,\rho_m\}$ 是静态组件（prompt、知识库、代码库）。
  • $F_s = \{F_1,\dots,F_k\}$ 是动态算子（搜索、选择、过滤、格式化）。

这是一个双层优化（bi-level optimization）：内层在训练数据上，为给定技能 $s$ 找到最好的上下文 $c_s^*$；外层找到在验证集上表现最好的技能：

$$ \text{Inner: }c_s^*=\arg\max_{c_s}J_\text{train}(c_s;s)\quad \text{Outer: }s^*=\arg\max_{s\in\mathcal{S}}J_\text{val}(c_s^*) $$

技能库记录了之前所有技能、上下文函数和评估指标的历史 $\mathcal{H}_{k-1} = \{(s_i,c_i,J_i^\text{train}, J_i^\text{val})\}_{i=1}^{k-1}$。一个元层 agent 对已有技能做 agent 式的交叉（crossover，进化算法里把两个“父代”方案的部分组合成新方案的操作），针对任务 $\tau$ 产生新技能：$s_k=\text{crossover}(\tau,\mathcal{H}_{k-1})$。

然后，一个基础层的“上下文工程师”执行技能 $s_k$，在当前技能的指导下，从运行反馈 $\mathcal{R}_k$ 中学出上下文函数：$c_k=\text{engineer}(\tau,s_k;c_{k-1}^*,\mathcal{R}_k)$。

MCE 不像 ACE 那样强制规定上下文的结构。它用自由形式的技能来存放一个任务最重要的知识，并把技能和以技能为条件的上下文放在一起迭代演化。实现上，一个上下文函数 $c$ 就是某个专用目录下的一组文件，既有静态部分（skill.md），也有动态部分（上下文和数据的运行记录）。元层和基础层的优化都在 agent 式编程环境里跑，用一套标准工具：

$$ \mathcal{T}=\{\texttt{Read},\texttt{Write},\texttt{Edit},\texttt{Bash},\texttt{Glob},\texttt{Grep},\texttt{TodoWrite}\} $$

Meta-Harness：优化 harness 的 harness

Meta-Harness（Lee et al. 2026）又往下深了一层：被优化的对象是代码，这段代码决定并优化哪些信息该被存储、检索、呈现给模型。名字里的 “Meta-” 指它是一个用来优化 harness 的 harness。

负责提出新 harness 的 proposer 本身就是一个编程 agent，最终输出是一组位于 Pareto 前沿（Pareto frontier，在多个指标之间没有哪个候选能被另一个全面压过的那一批）上的 harness 候选。

  • 完整的执行历史都放在文件系统里，编程 agent 用 grep、cat 这类命令去翻，不需要把所有东西一股脑塞进一个 prompt。
  • 每个被提出的 harness 在文件系统里是一个目录，里面有它自己的源码、分数、运行轨迹和状态更新。
  • Meta-Harness 循环反复生成新 harness，只保留合格的。

作者认为从这里得到的教训很清楚：一旦 harness 设计变成一个可执行的搜索空间，一个强的编程 agent 就可以利用人类工程师所用的同一片设计空间。

工作流设计

原文：Workflow Design

人工设计的科研工作流

harness 里的工作流可以由领域专家手工设计。以自动科研为例，已经有不少框架被提出和测试过。AI Scientist 系统（Lu et al. 2026）搭了一条流水线：提出研究想法、写代码、跑实验、分析结果、写论文、做同行评审。Meng et al. (2026) 的 ScientistOne 把可验证性当作首要设计约束：每一条论断（引用、数值、方法、结论）都必须能追溯到一个证据来源，并接受 Chain-of-Evidence（证据链）检查的审计。

Autodata agent（Kulikov et al. 2026）被设计成一个数据科学家，负责生成训练和评估数据。主 agent 管理几个角色：一个出题的 challenger、一个弱求解器（weak solver）、一个强求解器（strong solver）和一个验证者/评判者（verifier/judge）。目标是合成难度“刚刚好”的数据，也就是强求解器能做对、弱求解器做不对的题。

在 Autodata 里，challenger 的 prompt 会根据求解器和验证者的反馈反复更新。作者指出它的局限：合成出来的题用来微调弱求解器，不用来微调强求解器。如果这个循环不能反复提升强模型，它更像是在一个生成出来的 prompt 分布上做间接蒸馏（distillation，用强模型的输出去训练弱模型），RSI 的味道就淡了。

ADAS：把 agent 设计当成搜索问题

工作流的设计空间极其庞大。很自然地，可以把工作流设计看作一个搜索问题，那么就应该能用算法找到好的方案，不必全靠手工。沿着这个方向，Automated Design of Agentic Systems（ADAS；Hu et al. 2025）把 agent 设计本身表述成一个优化问题，叫“元 agent 搜索”（meta-agent search）：由一个元 agent 提出新的 agent 工作流设计。步骤如下：

  1. 初始化一个 agent 工作流的存档（archive），放进一些简单的 agent，比如 CoT（chain-of-thought，让模型先写出逐步推理再给答案）和 self-refine。
  2. 让元 agent 受存档里已有方案的启发，编写新的 agent，全部用代码写。
    • 元 agent 先写出新工作流的高层描述，再用代码实现。
    • 草稿程序会经过元 agent 的两轮 self-refine 来检查它的新颖性。self-refine（Madaan et al. 2023）的做法是让模型先给出反馈，再让同一个模型根据反馈修改之前的输出。
  3. 评估每个新候选，把成功的加回存档。
  4. 重复第 2–3 步，直到达到最大迭代次数。

AFlow：用蒙特卡洛树搜索优化工作流图

AFlow（Zhang et al. 2025）把 agent 工作流表示成一张图：节点是调用 LLM 的动作，边是用代码实现的逻辑操作。工作流的优化靠 MCTS（Monte Carlo Tree Search，蒙特卡洛树搜索：在一棵候选树上反复“选一个节点、扩展、试跑、把结果回传”，逐步把搜索集中到有希望的分支上）：

  1. 用一个模板在树里初始化起始工作流 $W_0$。
  2. 选择一个工作流节点，选择方式是“按分数”和“均匀探索”的软混合。
  3. 扩展：让 LLM 以这个节点的评估表现为条件，产出一个修改后的工作流。
  4. 执行并评估新工作流。
  5. 如果新工作流在 $N$ 轮预算内有改进，就把它加回树里。
  6. 重复第 2–5 步，当 top-$k$ 的平均分不再上升或预算耗尽时停止。

AFlow 在问答、代码和数学任务上的实验显示，它相对手工设计的工作流和 ADAS 都有不错的提升。

自我改进的 harness

原文：Self-Improving Harness

上下文工程和工作流设计各自只是 harness 的一部分。我们需要在整个设计空间里搜索，把上下文管理逻辑、工作流、权限以及其他 harness 组件放在一起优化。从 Meta-Harness、ADAS、AFlow 这些工作里可以看到，代码是定义程序和系统的通用语言。说得直白一点，harness 就是一段代码，它规定 prompt、工具调用、子 agent、控制流、记忆和工作流逻辑如何配合。如果 LLM 能优化执行 agent 的那段代码，它能触及的设计空间要比手写 prompt 大得多。

STOP：改进“改进器”本身

Self-Taught Optimizer（STOP；Zelikman et al. 2023）是递归改进脚手架（scaffolding，模型外围那套调用模型的程序）的早期例子之一。在第 $t=0$ 步有一个种子改进器 $I_0$，它接收一个初始解 $s$、一个效用函数 $u$ 和一个黑盒语言模型 $M$，返回改进后的解 $s'$，即 $s' = I(u, s; M)$。STOP 的目标不在于直接改进 $s$，它要改进改进器 $I$ 本身。

先定义元效用（meta-utility）：一个改进器函数 $I$ 在一组下游任务 $\mathcal{D}$ 上的平均效用：

$$ \hat{u}(I) \triangleq \frac{1}{\vert\mathcal{D}\vert}\mathbb{E}_{(u,s)\sim \mathcal{D}}[u(I(u,s; M))] $$

“改进改进器”本身也是一个优化问题，所以可以递归地做：根据 $I_{t-1}$ 在元效用上的表现，用它自己来产生新版本 $I_t$：

$$ I_t=I_{t-1}(\hat{u},I_{t-1};M) $$

也就是说，把改进器自己当成“待改进的解”，把元效用 $\hat{u}$ 当成效用函数，交给改进器自己处理。

实验里，被改进过的改进器自己发现了多种策略，例如遗传算法、把问题分解再分别改进、多臂 prompt bandit（把不同 prompt 当成老虎机的不同拉杆，边试边分配尝试次数）、模拟退火、调节采样温度，以及 beam search / 树搜索。作者说这和“把 harness 工作流表示成一个可优化对象”的思路是类似的。

Zelikman et al. (2023) 还有一个需要警惕的发现：用 GPT-4 时，STOP 的下游平均表现随迭代提升；换成 GPT-3.5 和 Mixtral 这样较弱的模型，表现反而下降。光有递归结构不够，基础模型必须足够强，才能改进这套机制。作者由此认为，harness 的改进能让模型部署得更好，但智力仍然是核心。

改 harness 的能力和用好 harness 的能力是两回事

Lin et al. (2026) 更细地研究了 harness 演化对模型能力的依赖。他们拆开了两个维度：(1) harness-updating，产出有用的 harness 修改的能力；(2) harness-benefit，利用更新后的 harness、把任务解得更好的能力。有意思的是，从 Qwen3.5-9B 到 Claude Opus 4.6，一系列规模和核心智力不同的模型，在实验里表现出相近的 harness 更新能力；9B 的 harness 提议者/演化者写出的技能，在流程上和 Opus 写的是同构的。要用好一个 harness，模型需要正确、及时地调用技能和工具，并且擅长长程的指令遵循。

Self-Harness：提议、评估、接受

较新的 Self-Harness（Zhang et al. 2026）让 LLM agent 通过一个“提议-评估-接受”的循环来改进自己的 harness。

循环分三个阶段：

  1. 弱点挖掘（weakness mining）：把失败聚类成以验证器结果为依据的失败模式。
    • 用当前 harness $h_t$ 在任务上评估，收集执行轨迹做分析。
    • 两次运行在错误日志里可能有相同的表面验证结果，比如超时或缺少产物，但背后的因果机制不同。所以失败记录需要包含丰富信息：验证器层面的最终原因、相关 agent 行为的因果状态、轨迹暴露出来的抽象 agent 机制，这样才能找到根因。
  2. Harness 提议（harness proposal）：根据挖出的失败模式，提出有边界的 harness 修改。
    • 在 $h_t$ 下调用同一个模型来当提议者。
    • 给模型一个有边界的提议上下文：(1) 当前 harness 里可编辑的部分；(2) 评估系统给出的、以验证器为依据的失败模式；(3) 应当保留的通过行为的记录；(4) 以往尝试过的修改的摘要。
    • 修改应优先针对反复出现、能被处理的错误模式（例如排除任务本身就难的情况），并且能用小范围的改动解决。
    • 候选修改之间应当各不相同、足够多样。
  3. 提议验证（proposal validation）：验证并合并合格的修改，得到新 harness $h_{t+1}$。
    • 候选修改要在两个划分上跑回归测试：held-in 集 $D_\text{in}$（检查弱点是否被修好）和 held-out 集 $D_\text{out}$（检查有没有引入别的未知问题）。
    • 只有在 held-in 和 held-out 上都没有退步的候选才会被接受。
    • 被接受的候选合并进 harness，得到 $h_{t+1}$；被拒绝的候选记入日志，不改动当前在用的 harness。

在 Terminal-Bench-2 上用 MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5 运行时，Self-Harness 学到了针对不同基础模型不同弱点的、模型专属的 harness 指令，并提高了 held-out 通过率。

作者对这类工作有一个担心：如果一个程序被允许修改它所在的“操作系统”，抽象边界就被打破了。可编辑的范围需要仔细设计，权限控制和安全层要放在这个循环之外。奖励作弊（reward hacking，模型钻评估信号的空子拿高分，实际没完成任务）相关的所有挑战依然存在。

AHE：以可观测性为中心的 harness 演化

Agentic Harness Engineering（AHE；Lin et al. 2026）认为 harness 演化的瓶颈在于可观测性（observability）：一次运行失败了，要知道是哪个组件的责任，每一处修改都要有证据支撑。

这个框架用三根“可观测性支柱”组成一个闭环：

  1. 组件可观测性：每个可编辑的 harness 组件在文件系统里都有对应的表示，所以动作空间是显式、可追踪的。
    • 一个 harness 包含 7 个组件：系统 prompt、工具描述、工具实现、中间件（middleware）、技能（skill）、子 agent 配置、长期记忆。
    • 每个失败模式被映射到一个组件，让修改更有针对性。
  2. 经验可观测性：把大量原始轨迹分析、汇总成一个分层的证据和失败模式结构。
    • 每个 harness 产生 $k$ 条轨迹。
    • 用一个 agent（“Agent debugger”）分析这些轨迹，每条轨迹存在一个文件里，为每个任务生成一份分析报告，说明失败或成功的根因。
    • 所有单任务报告汇总成一份 benchmark 总览，供下一步使用；需要时也能访问原始轨迹。这种分层访问的结构更省 token。
  3. 决策可观测性：每一处修改都配一个对下一轮的预测，供下一轮验证。
    • 一个 agent（“Evolve agent”）读仓库，决定改哪个组件，然后产出修改和修改理由。
    • 每处修改都是一个文件级的、可证伪的论断，可以在下一轮被检验，并受两条约束：
      • (1) 修改只能作用于 harness 工作区。runs 目录、tracer、验证器和 LLM 配置都是只读的。这堵住了一批奖励作弊手段（例如关掉验证器、换模型、调高推理预算），也保证每一次记录下来的提升都能归因到 harness 的修改上。
      • (2) 修改由证据驱动，每处修改附一条清单记录（manifesto entry）：失败证据的名称、推断的根因、针对性的修复、预测的影响（包括预期修好的问题和可能退步的地方）。

在 Terminal-Bench-2 上，AHE 除了 Hard 档以外，都好于人类设计的 harness（OpenCode、Terminus-2、Codex），也好于另外几个自我演化的基线（ACE、TF-GRPO）。同一个冻结住、不再继续演化的 harness 可以迁移到 SWE-bench-verified 上。这说明演化出来的 harness 把工程经验编码进了 harness 组件里，没有在做针对某个 benchmark 的优化。

进化搜索

原文：Evolutionary Search

进化搜索是受自然选择启发的优化方法（作者早年写过一篇进化算法的文章）。它维护一个由多个解组成的种群，对它们做变异，只保留种群里“适应度”（fitness，即评估分数）高的那些。进化搜索在两种情况下好用：(1) 搜索空间很大或者形状很怪；(2) 很难直接用梯度优化，但评估一个解很容易。作者认为 harness 搜索看起来很适合这种方法。

用进化搜索优化 prompt

以前的研究已经把进化搜索用在 prompt 工程上。Promptbreeder（Fernando et al. 2023）用一套丰富的变异操作来优化任务专用的 prompt。有意思的是，变异 prompt（也就是指示 LLM 去变异某个任务 prompt 的那段指令）本身也通过进化来改进。GEPA（Agrawal et al. 2025）把基于反思（reflection）的 prompting 和进化搜索结合起来，对试错轨迹做自然语言反思，据此提出 prompt 的更新。

AlphaEvolve

Novikov et al. (2025) 提出了 AlphaEvolve，一个基于编程 agent 的进化搜索系统。它存着一个候选程序池，调用冻结的 LLM 生成改进用的 diff。系统反复评估子代程序、保留成功的那些，随着时间推移发现更好的解。

AlphaEvolve 设计里有几处细节很重要：

  • prompt 里包含父代程序、结果、指令，有时还有元信息。
  • 编程 agent 能访问整个仓库，但需要改进的代码区域会用 # EVOLVE-BLOCK-START 和 # EVOLVE-BLOCK-END 显式标出来。
  • 元 prompt（meta-prompt）按 LLM 的建议与指令、上下文一起共同演化，方式和演化解程序类似。

消融实验（ablation，逐个拿掉某个设计看效果掉多少）显示了以下几项的作用：进化过程本身、prompt 里的上下文、元 prompt、整文件演化，以及使用更强的 LLM。

近期变体

近期的变体里，ThetaEvolve（Wang et al. 2025）把进化搜索和强化学习（RL）、上下文学习（in-context learning）结合起来。DemoEvolve（Che et al. 2026）在模型自己的运行存档之外，加入人类专家的示范作为参考经验，用于 harness 层面的诊断和修改。ShinkaEvolve（Lange et al. 2025）则引入三个新组件来提高 LLM 采样效率：

  • 更省样本的探索：设计父代采样方式，在“表现排名”和“已有子代数量”之间取平衡。
  • 代码新颖性拒绝采样：用基于 embedding 的余弦相似度，丢掉和现有种群太像的候选。
  • 在一个元草稿本（meta-scratchpad）里记下成功解中的好模式，指导以后的变异。

Darwin Gödel Machine：agent 改自己的 harness 代码

上面这些方法关注的是改进解。Darwin Gödel Machine（DGM；Zhang et al. 2025）明确以“演化一个可编辑的 harness 代码仓库”为目标，由一个基于 LLM 的编程 agent 来做。准确地说，这个 agent 被允许修改它自己的 harness。后续工作 Hyperagents（Zhang et al. 2026）引入一个元 agent，由它控制如何修改已有的任务 agent 来产生新 agent。DGM 的流程：

  1. 池子里先放一个编程 agent。
  2. 每轮迭代选一个父代，选中概率和它的表现成正比、和它已有的子代数量成反比；对它做修改，分支出新的 agent。
  3. 被选中的父代 agent 查看自己的 benchmark 评估日志，然后对自己的 harness 代码库提出改进，生成新版本的编程 agent。代码编辑只用两个基础工具：(1) bash（参数：<bash_command>）；(2) editor（参数：view/create/edit <file_path>）。
  4. 评估新的编程 agent，只把表现足够好的加回池子。
  5. 重复第 2–4 步，直到满足停止条件。

DGM 是固定模型下的 harness 演化。实验中用 Claude 3.5 Sonnet 做基础 LLM、配简单的初始 harness，DGM 发现的 agent 和手工设计的 agent 相当或更好：SWE-bench Verified 从 20% 提到 50%，Polyglot 从 14.2% 提到 30.7%。

这一类方法在候选解能自动评估、适应度容易量化的场景里效果好，比如矩阵乘法、GPU kernel 优化、算法竞赛、数据中心调度。到了评估慢、含糊、主要靠启发式判断的领域就吃力了。进化的计算效率和有效性也是问题。

与模型权重联合优化

原文：Joint Optimization with Model Weights

harness 演化改的是模型周围那套非参数化的系统。要实现完整的自我改进，完全可以让模型同时更新自己的权重。权重更新可以通过改进模型训练流水线来做，也可以通过测试时的持续学习来做。作者说持续学习值得以后单独写一篇。

SIA（Hebbar et al. 2026）是把 harness 改进和模型参数更新放进同一个优化循环的早期尝试，设计里有三个组件：

  • Meta-Agent：提出初始 harness。
  • Task-Specific Agent：执行任务。
  • Feedback-Agent：根据最近的轨迹，决定这一轮更新 harness 还是更新模型权重。

作者指出 SIA 的实验里有几个混杂因素，让结果难以解读。例如任务 agent 比 Meta-Agent 和 Feedback-Agent 用的模型弱得多（gpt-oss-120b 对 Claude Sonnet 4.6），基线也太弱，没法和相关方法干净地对照。她认为方向有意思，但证据还是初步的。训练稳定性和 Goodhart 效应（一个指标一旦成为优化目标，就不再是好的指标）等许多挑战仍未解决。

Continual Harness（Karten et al. 2026）在长程游戏场景里做实验：一边更新 harness，一边共同训练一个策略模型，训练方式是在低奖励的轨迹上蒸馏一个强教师模型给出的标签。

04. 未来的挑战

原文小节：Future Challenges

AI Scientist 这一系列工作有力地证明，专家设计的 harness 可以协调自动科研循环的很大一部分，实验形式是写研究论文。但产出论文和做出科学发现并不等同。一个系统可以写出一篇看上去合理的论文，同时里面有编造的引用、实现偏离（implementation drift）或者很弱的实验结果。

从想法到论文：六种反复出现的失败

Trehan & Chopra (2026) 测试了 LLM 能否在最少的脚手架、只用基础工具（read_file、write_file、llm_search、list_files）的条件下，从一个研究想法走到一篇论文。每个想法有一个专用工作区，agent 可以在里面生成和读取文档，作为上下文的一部分。他们在三个领域做实验（world models、多智能体 RL、AI 安全与对齐），每个领域准备了 45–50 篇高质量的种子文档来启发新想法。最终只有四个想法被人类专家选中跑完整条流水线，其中只有一个被完整执行成论文。他们观察到六种反复出现的失败模式：

  • 偏向训练数据里的默认做法：用老旧的库、过时的命令、标准格式，或者做出与实际仓库、数据集不符的假设。
  • 执行压力下的实现偏离：实现在技术上变复杂时，模型可能滑向一个常见的、更简单的方案，偏离原本提出的方法。
  • 记忆和上下文退化：长程项目会丢掉关键细节，除非把日志写成持久的产物。
  • 过度乐观：实验噪声很大甚至失败了，模型仍然宣布成功。Bubeck et al. (2025) 也观察到类似的 “p-hacking and eureka-ing” 模式，模型会加上 “numerical duct tape”（数值上的胶带式修补），在信号仍是噪声时就宣布胜利。
  • 领域智慧不足：模型缺少默会的手艺知识，例如预估实现复杂度、判断一个实验结果是否合理、知道哪些基线才重要。
  • 科研品味弱：实验可能跑得通，却没有回答对的问题。

走向完整 RSI 的七个瓶颈

研究者已经取得了实际进展，但还剩几个瓶颈。

1. 评估器弱且模糊

很多研究论断没有快速而精确的验证器，许多现实任务也是这样。当前的自我改进循环在评估指标可测量、客观的任务上效果最好，这和强化学习的工作方式类似。科研品味、新颖性和长期科学价值要难测得多。比如科研品味往往混合了问题的提法、实验设计，以及判断哪些意外结果值得追、哪些失败值得重试。

2. 上下文与记忆的生命周期

AI agent 越自主、越独立，记忆就越多。一个有用的 harness 需要管理上下文和记忆，弥补长上下文生成目前的局限，同时尽量提高长程任务的成功率。作者说，人类能维持一生的记忆，她在这里看到一个类比：上下文工程将会、也应该成为智力的核心部分，不应一直停留在软件系统这一层。

3. 负面结果

研究者有动力发表成功的结果，所以文献偏向成功。LLM 在海量数据上训练（作者说这些数据大多是人写的，“at least for now, lol”），由于数据里成功和失败案例不平衡，模型可能不擅长判断何时放弃一个假设、报告负面结果，甚至承认失败。科研 harness 应当让失败的尝试容易被保存下来，因为从失败中学习是缩小任务搜索空间最好的办法。

4. 多样性坍缩

进化循环和 RL 循环倾向于利用已知的高奖励模式。我们需要一些探索机制，防止种群坍缩成同一个解的各种变体。这对开放式研究尤其要紧，因为在当前评估器下，最好的那条路一开始可能看起来更差。

5. 奖励作弊

自我改进循环会去优化你给它的任何信号（参见作者的奖励作弊一文）。如果奖励来自单元测试，agent 可能对测试过拟合；如果来自一个评判模型，它可能学会专门针对这个评判模型的作弊技巧；如果来自 benchmark 分数，它可能利用 benchmark 本身的瑕疵。

评估器和权限控制大概应该放在演化 harness 的那个循环之外，配合 held-out 测试、轨迹审计，以及在要紧的决策点上的人工审查。监督能扩展和自动化到什么程度，仍是一个开放的研究方向。

6. 长期的成功

外在的优化循环优化的是单次运行之外、能在训练沙盒里模拟出来的奖励。

以编程 agent 为例。编程 agent 已经提高了软件工程的日常生产力，但很多优化目标仍然太短期。它常常能把手头的任务做完，但一个由成百上千名工程师共同维护的仓库，它该怎样保护这个仓库的长期健康，就没那么清楚了。标准的、基于沙盒的 RLVR 式训练（reinforcement learning with verifiable rewards，用可自动验证对错的奖励做强化学习）很少能捕捉到可维护性、所有权边界、迁移成本、向后兼容性或未来的调试负担。

7. 人的角色

人应该往上走一层，不应被移出循环。也就是说，人要在对的时间、对的抽象层级上提供监督，系统设计要考虑在什么时候、以什么方式设置这些接触点。

上面列出的很多挑战都需要人的反馈和引导。作者在结尾写道：“After all, we are building the technology for better future of humanity, not other way around.”

05. 附录：几个有用的 benchmark

原文小节：Appendix: Some useful benchmarks

这些 benchmark 用来衡量 AI 做科研复现、机器学习工程和 GPU kernel 编写的能力。

PaperBench

PaperBench：从零复现 20 篇 ICML 2024 的 Spotlight 和 Oral 论文，包括理解论文贡献、搭建代码库、成功跑通实验。

  • 每个复现任务被拆成更小的、可以单独打分的子任务。
  • 一共 8,316 条评分细则（rubric），与论文作者共同制定。
  • 当时最好的模型（Claude 3.5 Sonnet，约 21%）没有超过机器学习博士。
  • 包含 PaperBench、PaperBench Code-Dev（轻量版）和 JudgeEval。

CORE-Bench

CORE-Bench：评估已发表研究的计算可复现性。

  • 270 个任务，基于计算机科学、社会科学和医学领域的 90 篇论文。
  • 任务是用给定的代码和数据复现结果。
  • 有多个难度级别，既有纯语言任务，也有视觉-语言任务。
  • 当时报告的最好 agent（GPT-4o 和 GPT-4o-mini）在最难的任务上准确率只有 21%。

ScienceAgentBench

ScienceAgentBench：评估 LLM agent 做数据驱动科学发现的能力。

  • 从四个学科（数学、化学、生物、地理）的 44 篇同行评审论文中提取了 102 个任务。
  • 覆盖这些领域的基础数据科学任务：数据处理、模型开发、数据分析、信息可视化。

RE-Bench

RE-Bench：在真实的机器学习研究工程环境里，拿前沿 AI agent 和人类专家对比。

  • 7 个有挑战性的、开放式的机器学习研究工程环境。
  • 每个环境 =（打分函数, 起始方案, 参考方案）；每个都能在 8 块或更少的 H100 GPU 上运行。
  • 例子：优化一个 kernel、跑一个 scaling law 实验、修一个 embedding、为问答任务微调 GPT-2 等。
  • 包含 61 位不同的人类专家进行的 71 次 8 小时尝试的数据。
  • 人类专家在 82% 的 8 小时尝试中拿到非零分；24% 达到或超过了强参考方案。
  • 在 2 小时预算下，最好的 AI agent 得分是人类的 4 倍；但人类从更长预算中获益更多，在 8 小时和 32 小时设定下超过了 agent。

MLE-bench

MLE-bench：用离线的 Kaggle 竞赛评估机器学习工程 agent。

  • 包含从 Kaggle 精选的 75 个机器学习工程竞赛。
  • 测试训练模型、准备数据集、跑实验、向打分脚本提交预测。
  • 用 Kaggle 公开排行榜作为人类基线。
  • 论文中最好的配置是 o1-preview 加 AIDE 脚手架，在 16.9% 的竞赛里至少达到 Kaggle 铜牌水平。
  • 包含资源扩展分析和数据污染分析。

KernelBench

KernelBench：评估生成的 GPU kernel 是否正确、是否够快。

  • 250 个 PyTorch 任务，评估 LLM 能否写出又快又正确的 kernel。
  • 评估指标 fast_p = 生成的 kernel 中既正确又比基线快的比例。
