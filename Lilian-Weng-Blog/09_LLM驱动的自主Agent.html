LLM 驱动的自主 Agent

把 LLM 当作 agent 的核心控制器，再配上规划、记忆和工具使用三个组件：每个组件有哪些代表方法，ChemCrow、Generative Agents、AutoGPT、GPT-Engineer 这些案例怎么搭，以及目前还有哪些限制

作者：Lilian Weng · 发表于 2023 年 6 月 23 日 · 整理：Joyce（@JOYCE9896）
资料来源：LLM Powered Autonomous Agents（Lil'Log；本文依据原文英文网页整理，是中文转述和讲解，不是逐字翻译；图片引自原文，版权归原作者）

这篇文章讲什么

Agent（智能体）在这里指能自己拆解任务、调用外部能力、根据结果继续行动的程序。这篇文章讨论的是一种具体搭法：让 LLM 充当 agent 的“大脑”，也就是核心控制器，外面再接上规划（Planning）、记忆（Memory）和工具使用（Tool Use）三类组件。作者以 2023 年上半年流行的 AutoGPT、GPT-Engineer、BabyAGI 等演示项目为起点，把相关论文按这三个组件归类整理。

文章顺序是：先给出整体框架图；然后讲规划，包括任务分解（CoT、Tree of Thoughts、LLM+P）和自我反思（ReAct、Reflexion、Chain of Hindsight、Algorithm Distillation）；接着讲记忆，从人脑的记忆分类对应到 LLM，再介绍向量检索常用的几种近似最近邻算法；然后讲工具使用（MRKL、TALM、Toolformer、HuggingGPT、API-Bank）；最后看几个案例（科学发现 agent、Generative Agents 小镇模拟、AutoGPT 和 GPT-Engineer 的系统提示），并列出三条共同的限制。读完你应该能说清一个 LLM agent 由哪些部分组成，每部分有哪些代表做法和已知结论。

01. 引言

原文小节：（开篇，无小标题）

作者开篇说，用 LLM（large language model，大语言模型）做核心控制器来搭 agent 是个很酷的想法。几个概念验证（proof-of-concept）演示项目，比如 AutoGPT、GPT-Engineer 和 BabyAGI，都给了人启发。

她的判断是：LLM 的潜力不止于写出漂亮的文案、故事、论文和程序，它可以被看作一个强大的通用问题求解器（general problem solver）。这篇文章就是在这个视角下，看怎样把 LLM 组织成能自己完成任务的系统。

02. Agent 系统总览

原文小节：Agent System Overview

在 LLM 驱动的自主 agent 系统里，LLM 承担 agent 大脑的角色，周围配几个关键组件。

规划（Planning）

  • 子目标与分解：agent 把大任务拆成更小、好处理的子目标，从而高效地处理复杂任务。
  • 反思与改进：agent 可以对过去的行动做自我批评和自我反思（self-criticism / self-reflection），从错误里学习，在后续步骤里修正，最终结果的质量因此提高。

记忆（Memory）

  • 短期记忆：作者把所有的 in-context learning（上下文内学习，指模型不更新权重，只靠 prompt 里给的信息和示例来完成任务，详见她的 Prompt Engineering 一文）都看作模型在用短期记忆学习。
  • 长期记忆：让 agent 能在很长时间里保存和回忆（可以是无限量的）信息，通常靠外部向量数据库（vector store）加快速检索实现。

工具使用（Tool use）

  • agent 学会调用外部 API，获取模型权重里缺少的信息（权重在预训练之后通常很难改），包括最新信息、代码执行能力、专有信息源等。

03. 组件一：规划

原文小节：Component One: Planning

一个复杂任务通常包含很多步。agent 需要知道这些步骤是什么，并提前做计划。

任务分解

原文小节：Task Decomposition

Chain of thought（CoT，思维链；Wei et al. 2022）已经是提升模型在复杂任务上表现的标准提示技巧。做法是让模型“think step by step”（一步一步想），用更多的测试时计算（test-time computation，即推理阶段多生成一些中间文字、多花一些算力）把难题拆成更小更简单的步骤。CoT 把大任务变成多个可管理的小任务，也让人能部分看到模型的思考过程。

Tree of Thoughts（思维树；Yao et al. 2023）在 CoT 的基础上，每一步都探索多种推理可能。它先把问题分成多个思考步骤，每步生成多个想法（thought），于是形成一棵树。搜索可以用 BFS（广度优先搜索）或 DFS（深度优先搜索），每个状态由一个分类器（通过 prompt 实现）或多数投票来评估。

任务分解有三种做法：

  1. 让 LLM 用简单提示来分解，比如 "Steps for XYZ.\n1."、"What are the subgoals for achieving XYZ?"；
  2. 用针对具体任务的指令，比如写小说时用 "Write a story outline."；
  3. 由人来输入。

另一种很不一样的路子是 LLM+P（Liu et al. 2023），它把长程规划（long-horizon planning）交给外部的经典规划器（classical planner）。中间接口是 PDDL（Planning Domain Definition Language，规划领域定义语言，一种在自动规划领域用来形式化描述“状态、动作、目标”的语言）。流程分三步：

  1. LLM 把问题翻译成“Problem PDDL”；
  2. 请经典规划器基于已有的“Domain PDDL”生成一份 PDDL 计划；
  3. LLM 再把 PDDL 计划翻译回自然语言。

换句话说，规划这一步外包给了外部工具。前提是要有特定领域的 PDDL 描述和合适的规划器。作者指出，这在某些机器人场景里很常见，但在很多其他领域并不具备。

自我反思

原文小节：Self-Reflection

自我反思让自主 agent 能通过修正过去的行动决策、纠正之前的错误来迭代改进。现实任务里免不了试错，所以它很重要。

ReAct

ReAct（Yao et al. 2023）把推理（reasoning）和行动（acting）合到 LLM 里。它扩展了动作空间，让它同时包含任务相关的离散动作和语言空间。前者让 LLM 能和环境交互（比如调用 Wikipedia 搜索 API），后者让 LLM 用自然语言生成推理过程（reasoning trace）。

ReAct 的 prompt 模板里有显式的思考步骤，大致格式是：

Thought: ...
Action: ...
Observation: ...
... (Repeated many times)

在知识密集型任务和决策类任务两类实验上，ReAct 都比去掉 Thought: … 这一步、只保留行动的 Act 基线更好。

Reflexion

Reflexion（Shinn & Labash 2023）是一个给 agent 配上动态记忆和自我反思能力、用来提升推理能力的框架。它采用标准的强化学习（RL，reinforcement learning：agent 在环境里行动、拿到奖励、据此改进策略）设置：奖励模型只给简单的二值奖励（成功或失败），动作空间沿用 ReAct 的设置，即在任务相关动作之外加上语言，以支持复杂的推理步骤。每做完一个动作 $a_t$，agent 会算一个启发式值 $h_t$，并根据自我反思的结果，可以选择重置环境，开始一次新的尝试（trial）。

启发式函数负责判断一条轨迹什么时候效率太低或者出现了幻觉，应该停下来。“低效规划”指轨迹花了太长时间仍没成功。“幻觉”在这里的定义是：遇到一串连续相同的动作，在环境里得到的都是同样的观察结果。

自我反思的内容是这样产生的：给 LLM 看两个示例（two-shot），每个示例是一对（失败的轨迹，用来指导后续计划修改的理想反思）。生成的反思被加进 agent 的工作记忆，最多保留三条，作为之后查询 LLM 时的上下文。

Chain of Hindsight

Chain of Hindsight（CoH；Liu et al. 2023）的思路是把一串过去的输出摆在模型面前，每个输出都附上反馈，让模型学会在自己的输出上改进。

人类反馈数据是一个集合 $D_h = \{(x, y_i , r_i , z_i)\}_{i=1}^n$，其中 $x$ 是 prompt，$y_i$ 是模型的一个补全，$r_i$ 是人对 $y_i$ 的打分，$z_i$ 是对应的人写的事后反馈（hindsight feedback）。假设这些反馈元组按奖励排好序，$r_n \geq r_{n-1} \geq \dots \geq r_1$。训练过程是监督微调（SFT，supervised fine-tuning：用现成的输入输出对直接训练模型），数据是这样一个序列：$\tau_h = (x, z_i, y_i, z_j, y_j, \dots, z_n, y_n)$，其中 $i \leq j \leq n$（原文这里的下界缺了一个符号）。模型被微调成只预测最后的 $y_n$，条件是前面的序列前缀。这样模型就能根据反馈序列做自我反思，产出更好的输出。测试时，模型还可以选择和人工标注者进行多轮指令交互。

为了防止过拟合，CoH 加了一个正则项，最大化预训练数据集的对数似然。为了防止走捷径和直接复制（反馈序列里有很多常见词），训练时会随机遮掉 0% 到 5% 的历史 token。

实验用的训练数据是三个数据集的组合：WebGPT comparisons、summarization from human feedback 和 human preference dataset。

Algorithm Distillation

CoH 的想法是：在上下文里展示一段逐步改进的输出历史，训练模型顺着这个趋势产出更好的输出。Algorithm Distillation（AD，算法蒸馏；Laskin et al. 2023）把同样的想法用到强化学习任务里跨 episode（一个 episode 指从开始到结束的一整局交互）的轨迹上，把一个算法封装进一个以长历史为条件的策略（policy）里。agent 和环境交互很多次，每个 episode 都会变好一点；AD 把这段学习历史拼接起来喂给模型，于是我们会期望模型预测的下一个动作比之前的尝试表现更好。目标是学会强化学习的过程，而不是训练一个只针对某个任务的策略。

论文的假设是：任何能产生一组学习历史的算法，都可以通过对动作做行为克隆（behavioral cloning，直接模仿数据里的动作，用监督学习来训练策略）蒸馏进一个神经网络。历史数据由一组源策略（source policy）生成，每个源策略针对一个具体任务训练。训练阶段，每次 RL 运行时随机抽一个任务，取多 episode 历史中的一段子序列来训练，这样学到的策略与具体任务无关（task-agnostic）。

实际上模型的上下文窗口长度有限，所以每个 episode 要足够短，才能拼出多 episode 的历史。要学到接近最优的上下文内强化学习（in-context RL）算法，需要 2 到 4 个 episode 的多 episode 上下文。in-context RL 的出现需要足够长的上下文。

论文和三个基线做了比较：ED（expert distillation，专家蒸馏，用专家轨迹而不是学习历史做行为克隆）；源策略（用 UCB 生成用于蒸馏的轨迹）；RL^2（Duan et al. 2017；因为它需要在线 RL，所以被当作上界）。结果是 AD 展示出了 in-context RL，虽然只用离线 RL，表现却接近 RL^2，而且学得比其他基线快得多。在以源策略的部分训练历史为条件时，AD 的改进速度也比 ED 基线快得多。

04. 组件二：记忆

原文小节：Component Two: Memory

作者在这一节开头写了一句说明：感谢 ChatGPT 帮她起草这一节，她在和 ChatGPT 的对话里学到了很多关于人脑和快速 MIPS 数据结构的知识。

记忆的类型

原文小节：Types of Memory

记忆可以定义为获取、存储、保持并在之后提取信息的一系列过程。人脑里有几种记忆。

  • 感觉记忆（Sensory Memory）：记忆的最早阶段，在原始刺激结束后还能保留感官信息（视觉、听觉等）的印象。感觉记忆一般最多持续几秒。子类包括图像记忆（iconic memory，视觉）、回声记忆（echoic memory，听觉）和触觉记忆（haptic memory）。
  • 短期记忆（Short-Term Memory，STM）或工作记忆（Working Memory）：存放我们当前意识到的、执行学习和推理等复杂认知任务所需的信息。一般认为短期记忆的容量大约是 7 项（Miller 1956），持续 20 到 30 秒。
  • 长期记忆（Long-Term Memory，LTM）：能把信息保存很久，从几天到几十年，存储容量基本没有上限。LTM 有两个子类：
    • 外显 / 陈述性记忆（explicit / declarative memory）：关于事实和事件的记忆，指那些能有意识地回想起来的记忆，包括情景记忆（episodic memory，事件和经历）和语义记忆（semantic memory，事实和概念）。
    • 内隐 / 程序性记忆（implicit / procedural memory）：无意识的，包括自动执行的技能和惯常动作，比如骑自行车、敲键盘。

作者给出一个大致的对应关系：

  • 感觉记忆，对应为原始输入（文本、图像或其他模态）学习 embedding 表示（embedding，把输入变成一个稠密向量）；
  • 短期记忆，对应 in-context learning。它短而有限，受 Transformer 有限的上下文窗口长度限制；
  • 长期记忆，对应 agent 在查询时可以访问的外部向量数据库，通过快速检索取用。

最大内积搜索（MIPS）

原文小节：Maximum Inner Product Search (MIPS)

外部记忆可以缓解注意力范围有限的问题。标准做法是把信息的 embedding 表示存进一个向量数据库，这个数据库要支持快速的最大内积搜索（MIPS，给定一个查询向量，找出和它内积最大的那些向量）。为了加快检索，常见选择是近似最近邻（approximate nearest neighbors，ANN）算法，它返回近似的 top k 个最近邻，牺牲一点点准确率换来大幅提速。

几种常用于快速 MIPS 的 ANN 算法：

  • LSH（Locality-Sensitive Hashing，局部敏感哈希）：引入一个哈希函数，让相似的输入以高概率被映射到同一个桶里，桶的数量远少于输入的数量。
  • ANNOY（Approximate Nearest Neighbors Oh Yeah）：核心数据结构是随机投影树（random projection trees），也就是一组二叉树，每个非叶节点代表一个把输入空间切成两半的超平面，每个叶子存一个数据点。这些树相互独立、随机构建，所以在某种程度上它模拟了一个哈希函数。搜索时在所有树里进行，每棵树都迭代地往离查询更近的那一半走，最后汇总结果。思路和 KD 树很接近，但可扩展性强得多。
  • HNSW（Hierarchical Navigable Small World，分层可导航小世界图）：灵感来自小世界网络，即大多数节点都能在很少几步内到达任何其他节点，比如社交网络的“六度分隔”。HNSW 把这种小世界图建成多层，最底层放真正的数据点，中间层建立捷径来加速搜索。搜索时从最顶层的一个随机节点出发，朝目标移动；走不动了就下到下一层，直到最底层。上层的每一步可以在数据空间里跨很远，下层的每一步负责把搜索结果修得更准。
  • FAISS（Facebook AI Similarity Search）：基于这样一个假设：在高维空间里，节点之间的距离服从高斯分布，因此数据点应该存在聚类。FAISS 用向量量化（vector quantization）把向量空间切成若干簇，再在簇内做更细的量化。搜索时先用粗量化找候选簇，再在每个簇里用细量化查找。
  • ScaNN（Scalable Nearest Neighbors）：主要创新是各向异性向量量化（anisotropic vector quantization）。它把数据点 $x_i$ 量化成 $\tilde{x}_i$ 时，目标是让量化后的内积尽量接近原来的内积 $\langle q, x_i \rangle$（原文写作“as similar to the original distance of $\angle q, \tilde{x}_i$”，按上下文指量化后的 $\langle q, \tilde{x}_i \rangle$），而不是简单地挑最近的量化中心点。

更多 MIPS 算法和性能比较可以看 ann-benchmarks.com。

05. 组件三：工具使用

原文小节：Component Three: Tool Use

使用工具是人类一个显著的、有区分度的特征。人会制造、改造和利用外部物体，去做超出自己身体和认知极限的事。给 LLM 配上外部工具，可以大幅扩展模型的能力。

MRKL

MRKL（Karpas et al. 2022）是“Modular Reasoning, Knowledge and Language”（模块化推理、知识与语言）的缩写，是一种用于自主 agent 的神经符号（neuro-symbolic）架构。一个 MRKL 系统包含一组“专家”模块，通用 LLM 充当路由器，把请求转给最合适的专家模块。这些模块可以是神经的（比如深度学习模型），也可以是符号的（比如数学计算器、汇率换算器、天气 API）。

他们以算术为测试场景，做了微调 LLM 调用计算器的实验。结果显示，文字描述的数学题比直接写出算式的题更难解，因为 LLM（7B 的 Jurassic1-large 模型）没法可靠地抽取出基本算术所需的正确参数。作者从中得出：在外部符号工具本身可靠的情况下，知道什么时候用、怎样用工具很重要，而这取决于 LLM 的能力。

TALM、Toolformer 与实际产品

TALM（Tool Augmented Language Models；Parisi et al. 2022）和 Toolformer（Schick et al. 2023）都是微调一个 LM，让它学会使用外部工具 API。数据集的扩充依据是：新加的 API 调用标注能不能提升模型输出的质量。更多细节见作者 Prompt Engineering 一文的 “External APIs” 一节。

ChatGPT Plugins 和 OpenAI API 的 function calling 是工具增强 LLM 在实际中落地的好例子。工具 API 的集合可以由其他开发者提供（Plugins 的方式），也可以自己定义（function call 的方式）。

HuggingGPT

HuggingGPT（Shen et al. 2023）是一个框架：用 ChatGPT 当任务规划器，根据模型描述在 HuggingFace 平台上挑选可用的模型，再根据执行结果汇总出回答。

系统分四个阶段。

（1）任务规划：LLM 作为大脑，把用户请求解析成多个任务。每个任务有四个属性：任务类型、ID、依赖关系和参数。他们用 few-shot 示例（在 prompt 里给几个示范）引导 LLM 做任务解析和规划。指令如下： 

The AI assistant can parse user input to several tasks: [{"task": task, "id", task_id, "dep": dependency_task_ids, "args": {"text": text, "image": URL, "audio": URL, "video": URL}}]. The "dep" field denotes the id of the previous task which generates a new resource that the current task relies on. A special tag "-task_id" refers to the generated text image, audio and video in the dependency task with id as task_id. The task MUST be selected from the following options: {{ Available Task List }}. There is a logical relationship between tasks, please note their order. If the user input can't be parsed, you need to reply empty JSON. Here are several cases for your reference: {{ Demonstrations }}. The chat history is recorded as {{ Chat History }}. From this chat history, you can find the path of the user-mentioned resources for your task planning.

（2）模型选择：LLM 把任务分配给专家模型，请求被组织成一道选择题，LLM 面前是一个可选模型列表。由于上下文长度有限，需要先按任务类型过滤。指令如下： 

Given the user request and the call command, the AI assistant helps the user to select a suitable model from a list of models to process the user request. The AI assistant merely outputs the model id of the most appropriate model. The output must be in a strict JSON format: "id": "id", "reason": "your detail reason for the choice". We have a list of models for you to choose from {{ Candidate Models }}. Please select one model from the list.

（3）任务执行：专家模型执行具体任务，记录结果。指令如下： 

With the input and the inference results, the AI assistant needs to describe the process and results. The previous stages can be formed as - User Input: {{ User Input }}, Task Planning: {{ Tasks }}, Model Selection: {{ Model Assignment }}, Task Execution: {{ Predictions }}. You must first answer the user's request in a straightforward manner. Then describe the task process and show your analysis and model inference results to the user in the first person. If inference results contain a file path, must tell the user the complete file path.

（4）回答生成：LLM 收到执行结果，给用户提供汇总后的结果。

要把 HuggingGPT 用到真实场景，还要解决几个问题：

  1. 效率需要提升，因为 LLM 的多轮推理和与其他模型的交互都会拖慢整个过程；
  2. 它依赖很长的上下文窗口，才能在复杂的任务内容上沟通；
  3. LLM 输出和外部模型服务的稳定性都需要提升。

API-Bank

API-Bank（Li et al. 2023）是一个评测工具增强 LLM 的基准。它包含 53 个常用 API 工具、一套完整的工具增强 LLM 工作流，以及 264 段标注好的对话，其中涉及 568 次 API 调用。API 种类很多样，包括搜索引擎、计算器、日历查询、智能家居控制、日程管理、健康数据管理、账户认证流程等。因为 API 数量多，LLM 先要通过一个 API 搜索引擎找到该调用的 API，再根据对应文档发起调用。

在 API-Bank 的工作流里，LLM 要做好几个决策，每一步都可以评估决策的准确度。这些决策包括：

  • 是否需要调用 API；
  • 找到正确的 API 来调用：如果结果不够好，LLM 需要反复修改 API 的输入（比如为搜索引擎 API 决定搜索关键词）；
  • 根据 API 返回的结果作答：如果结果不满意，模型可以选择改进后再调用一次。

这个基准从三个层级评估 agent 的工具使用能力：

  • Level-1 评估调用 API 的能力。给定一个 API 的描述，模型要判断是否调用它、正确地调用，并对 API 的返回做出恰当的回应。
  • Level-2 考察检索 API 的能力。模型要搜索可能满足用户需求的 API，并通过读文档学会怎么用。
  • Level-3 评估在检索和调用之外做 API 规划的能力。面对不明确的用户请求（比如安排小组会议、为一次旅行订机票、酒店和餐厅），模型可能要发起多次 API 调用才能解决。

06. 案例研究

原文小节：Case Studies

科学发现 Agent

原文小节：Scientific Discovery Agent

ChemCrow（Bran et al. 2023）是一个特定领域的例子：给 LLM 配上 13 个由专家设计的工具，完成有机合成、药物发现和材料设计方面的任务。它的工作流用 LangChain 实现，体现了前面讲过的 ReAct 和 MRKL 的思路，把 CoT 推理和任务相关的工具结合起来：

  • 给 LLM 一个工具列表，包括工具名、用途描述、预期输入输出的细节；
  • 然后指示它在必要时使用这些工具回答用户给出的 prompt。指令建议模型遵循 ReAct 格式：Thought, Action, Action Input, Observation。

一个有意思的现象：基于 LLM 的评估认为 GPT-4 和 ChemCrow 表现差不多，但由专家进行、侧重方案完成度和化学正确性的人工评估显示，ChemCrow 大幅胜过 GPT-4。这说明在需要深厚专业知识的领域，用 LLM 评估自己的表现可能有问题：缺乏专业知识会让 LLM 意识不到自身缺陷，也就没法很好地判断任务结果是否正确。

Boiko et al. (2023) 也研究了用于科学发现的 LLM agent，让它自主设计、规划和执行复杂的科学实验。这个 agent 能用工具浏览互联网、阅读文档、执行代码、调用机器人实验 API，还能调用其他 LLM。

例如，收到请求 "develop a novel anticancer drug"（开发一种新的抗癌药）时，模型给出的推理步骤是：

  1. 查询抗癌药物发现的当前趋势；
  2. 选定一个靶点；
  3. 请求一个针对这些化合物的骨架（scaffold）；
  4. 确定化合物之后，尝试合成它。

他们也讨论了风险，特别是非法药物和生物武器方面。他们做了一个测试集，里面是一批已知的化学武器制剂，让 agent 去合成。11 个请求里有 4 个（36%）被接受，agent 给出了合成方案，并试图查阅文档来执行流程。另外 7 个被拒绝；这 7 个里，5 个是在做了一次网页搜索之后拒绝的，2 个是只看 prompt 就拒绝了。

Generative Agents 模拟

原文小节：Generative Agents Simulation

Generative Agents（Park, et al. 2023）是作者口中“super fun”的实验：25 个虚拟角色，每个由一个 LLM 驱动的 agent 控制，在一个受《模拟人生》（The Sims）启发的沙盒环境里生活和互动。生成式 agent 为交互式应用创造可信的人类行为模拟。

它的设计把 LLM 和记忆、规划、反思机制结合起来，让 agent 的行为能以过去的经历为条件，并能和其他 agent 互动。

  • 记忆流（Memory stream）：一个长期记忆模块（外部数据库），用自然语言完整记录 agent 的经历。
    • 每个元素是一条观察（observation），即 agent 直接得到的一个事件。agent 之间的交流也会产生新的自然语言陈述。
  • 检索模型（Retrieval model）：根据相关性、时近性和重要性，把对 agent 行为有用的上下文找出来。
    • 时近性（Recency）：越近的事件得分越高；
    • 重要性（Importance）：区分平淡的记忆和核心记忆，直接问语言模型；
    • 相关性（Relevance）：根据它和当前情境或查询的关联程度。
  • 反思机制（Reflection）：随时间把记忆综合成更高层的推断，指导 agent 未来的行为。这些反思是对过去事件的高层总结（作者提醒，这和前面讲的自我反思有点不同）。
    • 用最近 100 条观察提示语言模型，让它根据这组观察或陈述提出 3 个最突出的高层问题，再让语言模型回答这些问题。
  • 规划与反应（Planning & Reacting）：把反思和环境信息转化成行动。
    • 规划的目的是在当下和一段时间里都优化行为的可信度（believability）；
    • Prompt 模板：{Intro of an agent X}. Here is X's plan today in broad strokes: 1)
    • agent 之间的关系、一个 agent 对另一个 agent 的观察，都会在规划和反应时被考虑进去；
    • 环境信息以树结构呈现。

这个模拟出现了涌现的社会行为，比如信息扩散、关系记忆（例如两个 agent 接着上次的话题聊下去），以及社交活动的协调（例如办一场派对并邀请很多人）。

07. 挑战

原文小节：Challenges

看完搭建以 LLM 为中心的 agent 的关键思路和演示之后，作者总结出几个共同的限制。

  • 有限的上下文长度：上下文容量有限，限制了能放进去的历史信息、详细指令、API 调用上下文和返回结果。系统设计只能在这条有限的通信带宽内工作，而像“从过去的错误中学习”这类自我反思机制，会从很长甚至无限的上下文窗口里获益很多。向量数据库和检索虽然能接入更大的知识库，但它们的表示能力不如完整的注意力（full attention）。
  • 长期规划和任务分解的困难：在很长的历史上做规划、有效地探索解空间，仍然很难。LLM 遇到意外错误时很难调整计划，所以和能从试错中学习的人相比，它们不够稳健。
  • 自然语言接口的可靠性：现在的 agent 系统用自然语言作为 LLM 和记忆、工具等外部组件之间的接口。但模型输出的可靠性存疑，LLM 可能犯格式错误，偶尔还会表现出“叛逆”行为（比如拒绝执行某条指令）。所以 agent 演示代码里有很大一部分都在解析模型输出。
