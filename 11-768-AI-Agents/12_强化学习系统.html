第十二讲：强化学习系统

RL 训练由推理和训练两种负载组成，怎样分别优化、怎样让两者配合，Agent 场景特有的麻烦，以及 RL 框架的系统设计

主讲：Apurva Gandhi · 2026 年 10 月 1 日
资料来源：课程幻灯片（课程网站尚未发布这一讲的录像，本文依据幻灯片和幻灯片中引用的资料整理）

一、本讲的位置

第九讲和第十一讲讲的是 RL 算法：让 Agent 尝试任务，按结果打分，再调整模型，让得高分的行为更可能出现。那两讲关心的是"更新公式长什么样"。这一讲换一个角度：这些公式在几百张 GPU 上真正跑起来时，系统要怎样搭。这一讲由客座讲者 Apurva Gandhi 主讲。

为什么需要单独一讲讲系统？Agent 的 RL 训练特别慢、特别贵。一次尝试（rollout）可能要和环境来回交互几十轮，生成几万个 token；每一步训练又要成百上千次这样的尝试。如果系统设计得不好，大部分 GPU 时间都花在等待上。这一讲讲的就是怎样把等待降下来。

先复习一个背景概念。语言模型生成文字分两个阶段。预填充（prefill）是把输入的提示词一次性读进去，所有位置可以并行计算，速度快。解码（decode）是一个 token 一个 token 地往后生成，每生成一个都要等前一个算完，只能顺序进行，GPU 的算力大部分闲着。第三讲讲长上下文时详细讲过这两个阶段，这一讲会反复用到。

二、RL 框架要支持哪些操作

1. 从策略梯度公式拆出操作

第九讲的策略梯度更新可以写成：

$$\theta \mathrel{+}= \sum_t \big(R(\tau) - b(h_t)\big)\, \nabla_\theta \log \pi_\theta(a_t \mid h_t)$$

符号的意思：$\theta$ 是模型参数；$\tau$ 是一次完整的尝试（一条轨迹）；$R(\tau)$ 是这次尝试的奖励；$h_t$ 是第 $t$ 步时 Agent 看到的历史；$a_t$ 是它在这一步做的动作；$\pi_\theta(a_t \mid h_t)$ 是模型在这个历史下选择这个动作的概率；$b(h_t)$ 是基线，用来判断这次结果比平均好还是差。

把这个公式变成可执行的程序，需要下面几种操作，从右往左看：

  • env.state / env.step 加上 Agent 的 Harness：让模型和环境交互，产生轨迹 $\tau$。
  • env.verify：检查结果，给出奖励 $R(\tau)$，比如跑测试看代码修对没有。
  • forward：前向计算，算出每个动作的 $\log \pi_\theta$。
  • backward：反向传播，算出梯度 $\nabla_\theta$。
  • optim_step：优化器用梯度更新参数。

2. 为什么不直接用 PyTorch 写

forward、backward、optim_step 在 PyTorch 里各有现成的函数。生成轨迹本质上也就是反复调用 forward。那为什么不用最普通的 PyTorch 自己写一个循环？

问题在于，RL 框架里其实有两种性质完全不同的计算负载，混在一起用同一套代码跑，两边都跑不快。

3. 两种负载

采样（sample）：用当前模型生成轨迹。这一步以解码为主，只能一个 token 一个 token 地顺序生成，不需要计算梯度。专门做这件事的软件叫推理引擎，常用的是 vLLM 和 SGLang。

训练（forward_backward）：拿生成好的完整轨迹，重新算一遍每个 token 的概率，同时记录计算图以便反向传播。因为整条轨迹已经有了，所有位置可以并行计算，形态和预填充一样。专门做这件事的软件叫训练引擎，常用的是 Megatron 和 PyTorch 的 FSDP2。

两边各有一套专门的优化：

推理引擎（vLLM、SGLang）训练引擎（Megatron、FSDP2）
KV 缓存激活检查点
跨请求的前缀缓存（Radix 缓存）前缀共享
连续批处理样本打包（batch sample packing）
推测解码、多 token 预测（MTP）
模型切分（PP、CP、TP、EP 等）模型切分（PP、CP、EP 等）

所以实际的 RL 框架是两个引擎配合工作：推理引擎负责生成轨迹，把轨迹数据交给训练引擎；训练引擎更新参数后，把新参数同步回推理引擎。下面分别讲两边的优化，再讲两边怎样配合。

4. 一个训练步骤的五个阶段

  1. sample（推理加环境）：用当前策略生成轨迹，过程中真正在环境里执行动作。
  2. verify（环境）：由验证器、测试或工具结果给出奖励。
  3. forward（训练引擎）：在训练引擎里重新算一遍每个 token 的对数概率，这次要记录梯度。
  4. backward（训练引擎）：反向传播算梯度。
  5. optim_step 与同步：更新训练引擎里的参数，发送给推理引擎，并按推理引擎的切分方式重新切分（reshard）。

然后用新参数重复。第 3 步为什么要"重新算一遍"概率？推理引擎生成时已经算过概率了，但推理引擎为了速度不记录计算图，没法反向传播；而且两个引擎的数值实现略有不同，算出的概率不完全一样。这一点后面讲 R3 时还会提到。

三、推理引擎的优化

1. KV 缓存

Transformer 生成第 $t$ 个 token 时，要用注意力机制读取前面所有 token 的信息。每个 token 在每一层都会算出一对向量，叫键（K）和值（V），注意力就是用新 token 的查询向量（Q）去和所有之前的 K 比较，再按比较结果加权平均对应的 V。

前面 token 的 K 和 V 一旦算出来就不会再变。所以生成第 7 个 token 时，没必要把前 6 个 token 的 K、V 重新算一遍，直接把它们存起来，只给新 token 算 Q、K、V，再把新的 K、V 加进存储。这份存储就是 KV 缓存。它用大量内存换掉了大量重复计算。

内存有多大？幻灯片以 Llama-3-8B 为例：用 bf16 精度（每个数 2 字节），每个 token 的 KV 缓存约 128 KB。这个数可以自己算：32 层 × 8 个 KV 头 × 每头 128 维 × K 和 V 两份 × 2 字节 = 131,072 字节。一条 32k token 的 Agent 轨迹就要约 4 GB，同时跑 64 条就是约 256 GB，超过三张 80 GB 的 H100 的显存总和。Agent 轨迹又长又多，KV 缓存往往是推理引擎最紧张的资源。

2. 前缀缓存

KV 缓存是在一条序列内部复用。前缀缓存更进一步：不同请求只要开头一样，开头那部分的 KV 就可以共用。Agent RL 特别适合这种优化，有两个原因：

  • GRPO 这类组内比较算法（第九讲）会对同一个任务生成一组轨迹，比如 8 条。它们的系统提示词、工具定义、任务描述完全一样，这部分只需计算一次。
  • 同一条轨迹里，第 2 轮交互的输入是第 1 轮的全部历史再加新观察，第 1 轮的 KV 可以直接复用。

SGLang 的 RadixAttention 和 vLLM 的自动前缀缓存（Automatic Prefix Caching）都实现了这个功能。RadixAttention 用一棵前缀树（radix tree）管理所有缓存的序列，新请求进来时沿树找到最长的公共前缀。

3. 连续批处理

GPU 一次处理一批请求比逐个处理效率高得多。最简单的做法是静态批处理：凑齐一批，一起开始，等全部生成完再换下一批。问题是同一批里的请求长度差别很大，短的早早结束，它占的位置就空着，整批都要等最长的那一个。Agent 轨迹长短差异尤其大，这种浪费很严重。

连续批处理按"每一个解码步"调度：某条序列一结束，立刻把它移出批次，队列里等着的请求马上补进这个空位。这个方法来自 Orca 系统（Yu 等，2022），论文里叫迭代级调度。

连续批处理通常配合分块预填充（chunked prefill）使用。新补进来的请求要先做预填充，如果它的提示词很长，这一步会占用很多时间，让同批其他正在解码的请求卡住。分块预填充把长提示词切成小块，每个解码步只处理一块。另一种做法是把预填充和解码分到不同的 GPU 上（disaggregation）。

4. 推测解码

解码慢是因为只能一个一个地生成。推测解码（Leviathan 等，2023）用一个便宜的"草稿模型"先猜后面 $k$ 个 token，比如 $k = 4$，再让真正的模型（策略）一次并行地检查这 4 个。检查是并行的，速度和预填充一样快。如果前 2 个猜对、第 3 个猜错，就接受前 2 个，第 3 个换成策略自己的选择。用拒绝采样决定接受还是拒绝，可以保证最终输出的分布和策略单独生成时完全一样，只是更快。草稿模型可以是一个小模型，也可以是挂在大模型上的多 token 预测（MTP）头。

RL 里有一个特有的麻烦：策略每一步训练都在变。草稿模型如果固定不动，它的猜测和策略越来越不像，接受率会逐渐下降，加速效果也就没了。解决办法是让草稿模型也在线训练，用一个辅助目标（比如对策略输出做 SFT 或蒸馏）让它跟上策略的变化。

四、训练引擎的优化

1. 激活检查点

反向传播需要用到前向计算时的中间结果（叫激活值），所以正常训练要把每一层的激活值都存下来，直到反向传播用完。序列越长，激活值越多，Agent 的长轨迹会让显存很快不够用。

激活检查点的做法是：前向计算时每一层只保存它的输入，内部的中间结果算完就丢；反向传播走到某一层时，用保存的输入把这一层重新算一遍，用完再释放。显存占用从"所有层的全部激活值"降到"每层一个输入，加上同一时刻一层的激活值"。代价是多做了大约一次前向计算，总计算量增加约 33%（原本前向加反向约等于三次前向的计算量，再加一次就是四次）。如果只重算注意力部分（选择性重算，Korthikanti 等，2022），额外代价要小得多。这个方法最早由 Chen 等（2016）提出，叫梯度检查点。

2. 前缀共享

前缀缓存是推理引擎里的优化，前缀共享是它在训练引擎里的对应物。一个 GRPO 组里的 4 条轨迹共用同一个提示词 P。普通做法是把每条轨迹都写成"P + 回答"，P 重复出现 4 次，前向和反向都要算 4 遍。

前缀共享把 P 只放一次，后面接 4 个分支 r1 到 r4。要让结果和分开算完全一样，需要处理三件事：

  • 树形注意力掩码：分支之间不能互相看到，r2 的 token 只能看到 P 和 r2 自己。
  • 位置编号按每条独立序列来编：r2 的第一个 token 的位置紧接在 P 之后，不能因为排在 r1 后面就往后挪。
  • 梯度累加：P 的梯度来自所有 4 个分支，要加在一起。

幻灯片给了两个实测结果。Snowflake 的 ZoRRo（Arctic RL，2026）发现，在长提示词的 GRPO 批次里，80% 到 95% 的 token 都是重复的提示词，去重后策略更新最多快 6 倍。AReaL-DTA（Zhang 等，2026，ICML）处理多轮交互：τ²-bench 上的多轮轨迹写成前缀树后能压缩 9.43 倍，用深度优先的方式一次走一条从根到叶的路径来训练，最多比普通训练快 8.31 倍。

3. 并行

大模型的参数和长序列的激活值都放不进一张 GPU，需要切分到多张上。表格里的缩写是几种切分方式：PP（流水线并行，按层切）、TP（张量并行，把一层内部的矩阵切开）、EP（专家并行，MoE 模型的不同专家放在不同 GPU）、CP（上下文并行，按序列长度切）。

幻灯片特别画了上下文并行，因为它对 Agent 的长轨迹最重要。把一条长序列按位置切成 4 段，分给 4 张 GPU。每张 GPU 保留自己那段的 Q，KV 分块在 GPU 之间轮流传递，每张 GPU 依次和每一块 KV 计算注意力，最后每段都得到了和完整序列做注意力的结果。CMU 11-711 第二十讲对各种并行方式有更完整的讲解。

五、两个引擎之间的配合

1. 权重同步

每次训练引擎更新完参数，都要把新参数送到推理引擎。最直接的做法是全量同步：把所有参数广播给每一个推理进程。一个一万亿参数的模型用 bf16 存储约 2 TB，每一步都传一遍代价很高。

增量同步利用了一个观察（PULSE，Mihai 和 Belilovsky，2026）：RL 每一步更新的幅度很小，在 bf16 精度下约 99% 的参数数值根本没有变化。所以只传送变了的那部分即可。

还要注意，训练引擎和推理引擎对模型的切分方式往往不同，比如训练用 FSDP 按参数切，推理用 TP 按矩阵切。所以同步时还要重新切分，这一步本身也有开销。

2. MoE 的路由重放（R3）

混合专家（MoE）模型里，每个 token 由一个路由器选择交给哪几个专家处理。路由是离散的选择，两个专家得分很接近时，极小的数值差异就可能导致选到不同的专家。推理引擎和训练引擎的计算实现不同，数值上总有微小差别，于是同一个 token 在生成时用的是专家 A，训练重新计算时却用了专家 B。这样算出的概率和生成时的概率对不上，RL 的更新就会出错。

R3（Rollout Routing Replay，Ma 等，2025）的办法是：推理引擎在生成时记下每个 token 选了哪些专家，训练引擎重新计算时直接沿用这些选择，不重新路由。这要求推理引擎能把路由决策导出给训练引擎。

六、Agent RL 特有的麻烦

1. 序列延展

Agent 一次任务会有很多轮：任务描述 T，第一个动作 A₁，环境返回观察 O₁，第二个动作 A₂，观察 O₂，依此类推。Harness 每一轮怎样把历史拼成模型的输入，会直接影响训练效率。幻灯片比较了两种 Harness：

  • Harness A：每一轮都在原有历史后面追加。第 4 轮的输入是 T A₁ O₁ A₂ O₂ A₃ O₃，后面接 A₄。
  • Harness B：每两轮观察后做一次压缩（第三讲讲过的上下文压缩）。O₂ 之后，保留 T，把 A₁ O₁ A₂ O₂ 总结成一段摘要 S。第 4 轮的输入变成 T S A₃ O₃。

哪个训练效率更高？Harness A 满足"序列延展"性质：每一轮的输入都是上一轮输入的严格延续。所以整条轨迹可以写成一条训练序列 T A₁ O₁ A₂ O₂ A₃ O₃ A₄ O₄，用一次前向和反向就能处理所有动作。损失掩码只在动作 token 上为 1（模型只对自己生成的部分负责，任务和观察是环境给的，掩码为 0），整条轨迹的优势值 Â 广播到每个动作 token 上。

Harness B 不满足这个性质。压缩之后，第 3 轮的输入不再是第 2 轮输入的延续，只能拆成两条训练数据：一条是 T A₁ O₁ A₂ O₂，另一条是 T S A₃ O₃ A₄ O₄。任务 T 在两条里都出现，虽然它的损失为 0，但作为上下文仍然要计算。轮数越多、压缩越频繁，拆出的数据越多，重复计算也越多。幻灯片的建议是：尽量保持精确的前缀，能拼接就一直拼接下去。

2. 聊天模板的坑

第一讲讲过，聊天模板决定了对话历史怎样被转换成 token 序列。一些常用模型的默认聊天模板并不满足序列延展性质。例子是 Qwen 3 和 Qwen 3.5：默认模板会把历史轮次里的推理内容（思考过程）删掉，只保留最终回答。这样第 2 轮输入里的第 1 轮，和第 1 轮生成时的样子不一样了，前缀对不上。

所以 Agent RL 框架常常自带聊天模板，或者叫"渲染器"（renderer），专门保证序列延展，比如 Tinker 和 PrimeRL。

3. token 进，token 出

推理引擎生成的轨迹要传给训练引擎。用什么格式传？字符串还是 token 编号？

答案是 token。原因有两个。字符串在传递过程中可能经过一些不起眼的变换，比如聊天模板多加了一个空格，再重新分词时得到的 token 就和生成时不一样了。更根本的是，分词和还原不是对称的：一段 token 序列还原成字符串是确定的，但同一个字符串可能对应多种 token 切法（还原是多对一的）。模型生成时可能选了一种不常见的切法，把字符串重新分词会得到常规切法，算出的概率就不是模型实际生成那个序列的概率。这种做法叫 token 进、token 出（Token-In-Token-Out，TITO），Miles 框架的文档《No Token Left Behind》详细讨论过。

4. 异步 RL

同步 RL 让训练引擎和推理引擎共用同一批 GPU，轮流使用：先全部用来生成，再全部用来训练。问题是 Agent 轨迹长短差别很大，生成阶段必须等最长的那条结束，其他 GPU 只能干等。

异步 RL 把 GPU 分成两组，一组专门推理，一组专门训练，两边同时工作。Agent RL 的瓶颈通常在生成轨迹（轨迹很长），所以可以给推理分更多 GPU，比如推理和训练按 3:1 分配。Pipeline RL 和 AReaL 是这种做法的代表。

代价是数据变得"陈旧"：训练引擎拿到的轨迹，可能是几个版本之前的参数生成的。第十一讲讲的重要性采样和裁剪就是用来修正这种偏离的。异步 RL 还要求推理引擎支持连续批处理，以及在生成进行中更新权重（in-flight weight update）：新参数到了，正在生成的序列不用中断，后面的 token 直接用新参数生成。SGLang 等推理框架已经为 RL 的需要加入了这个功能。

5. 复杂的 Harness

现实中的 Agent Harness 越来越复杂：主 Agent 调用子 Agent，定期压缩上下文，递归地分解任务。这种情况下，一次任务产生的不是一条线性序列，而是一棵调用树，每个节点有自己的上下文。怎样在这种结构上做 RL 训练，是一个正在研究的问题，幻灯片列出了 Recursive Agent Optimization（RAO，2026）和 Recursive Language Models（RLM，2025）作为参考。

七、系统设计的选择

1. 与 Harness 无关的设计

常用的 Agent Harness 很多：Codex、Claude Code、OpenHands、Pi、Hermes、Prime Agent 等。如果想用 RL 训练模型在这些 Harness 里表现更好，最笨的做法是为每个 Harness 写一套专门的轨迹生成和环境代码，换一个 Harness 就要重写一遍。

更好的做法是加一个中间代理服务。各种 Harness 本来就是通过标准的推理 API（OpenAI 的 Chat Completions、Responses，Anthropic 的 API 等）调用模型的。代理服务模仿这些 API，Harness 以为自己在调用普通的模型服务，实际请求被转给 RL 系统里的推理引擎，代理顺便记录下 token、对数概率、MoE 路由等训练需要的信息，存进轨迹库。这样接入一个新 Harness 不用改任何代码。Agent Lightning 就是这样设计的。

2. 单程序多数据（SPMD）

一种系统组织方式是：所有 GPU 上运行同一个 Python 程序，程序根据自己的编号（rank）决定做什么。比如 8 张 GPU，0 到 3 号做训练（FSDP 通信、优化器更新，然后异步发布新权重），4 到 7 号做推理（检查有没有新权重、取任务、生成轨迹、放进队列）。所有进程必须按相同的顺序创建通信组。

协调逻辑都写在这一个程序里，所有东西直接可控，比较直观，但灵活性差。AReaL 1.0 之前的版本采用这种设计。

3. 一切皆服务，加一个中央控制器

另一种方式是把每个组件做成独立的服务：推理服务（对外提供 SGLang 或 vLLM 的 API）、Agent 服务、训练服务（比如 Tinker 的训练 API）、权重同步服务、环境与奖励服务（比如 Open Reward Standard，ORS）。一个轻量的中央控制器负责编排，训练循环本身在 CPU 上运行。

这样做的好处是关注点分离。每个组件都很复杂、很专业，放在同一个代码库里会互相牵制。分开之后，研究人员只需改控制器里的训练循环就能试验新算法，不用处理复杂的依赖；各个组件的维护、升级和发布也不需要同步。同时还有模块化的好处：只要服务之间的通信协议不变，任何一个服务都可以替换成另一种实现，比如奖励服务可以用托管的 OpenReward，也可以自己部署。

4. 服务化带来的能力

  • 弹性扩展：推理服务下面可以再挂一个控制器，管理多个推理实例，需要更多算力时直接增加实例。
  • 多集群、异构算力：不同的推理实例可以在不同的集群上，用不同的硬件，比如一组 8×H100、一组 4×MI350。幻灯片举了 AstraFlow（Haizhong Zheng 等，2026）作为例子。
  • 多策略训练：微服务架构可以同时训练几个不同的模型，比如多 Agent 场景里每个 Agent 用不同的策略。
  • 在线 RL，即部署后继续训练：AReaL 2.0（2026）支持这种模式。幻灯片提到 Cursor 在生产环境中做在线 RL：Cursor Tab 补全功能，以及 Composer 模型每 5 小时就根据真实用户交互产出一个新检查点。
  • 多租户、多 LoRA 训练：LoRA 是只训练少量附加参数的微调方法。多个 LoRA 训练任务可以共用同一个基座模型同时进行，每个任务可以属于训练服务的不同用户。8 个并发任务的总吞吐量高于依次跑 8 个，但每个任务的完成时间会变长。这需要专门的 GPU 计算核（Grouped-GEMM、SGMV）。参考：SkyRL 与 Trajectory Labs 的多 LoRA 持续学习（2026），Punica 多租户 LoRA 服务（2023）。

Tinker 是这种设计的代表，它率先做了多租户、多 LoRA 的 RL 训练和解耦的训练服务。它的 API 很简洁：每个训练任务一个训练客户端，每个 LoRA 权重检查点一个采样客户端。

八、调试时值得盯的指标

幻灯片最后附了一张表，列出 RL 训练中常用的监控指标，以及出问题时的迹象：

指标说明什么警告信号
奖励 / pass@1策略在训练任务上有没有进步很多步都不动；或者训练奖励上升、留出集评估却下降（奖励作弊）
pass@k覆盖面：k 次采样里有没有一次能解决pass@1 上升而 pass@k 下降：多样性在崩塌
熵策略还在多大程度上探索突然掉到接近 0，或者突然跳高（生成乱码）
重要性权重最大值最极端的 token 概率比，如 π_train / π_rollout出现尖峰：两个引擎不一致或数据过旧，少数 token 主导了更新
梯度范数裁剪之前每次更新的大小发散前会出现尖峰；或者持续上升
平均陈旧度数据是几个权重版本之前生成的逐渐升高：生成轨迹跟不上训练速度
训练 MFU训练 GPU 的算力利用率因为填充、负载不均或微批次太小而下降
各阶段耗时：生成、更新、等待、总计每一步的时间花在哪里等待时间大于 0：训练引擎在等轨迹

MFU（Model FLOPs Utilization）是实际完成的有效计算量占 GPU 理论峰值的比例。pass@k 和熵这两行配合起来看很有用：如果模型越来越只会一种解法，pass@1 可能还在涨，但 k 次尝试的覆盖面在缩小，这就是第十一讲讲的探索崩溃。

九、参考资料导读

  • Orca（Yu 等，2022）：提出迭代级调度，也就是连续批处理，是今天 vLLM、SGLang 批处理方式的来源。
  • Fast Inference from Transformers via Speculative Decoding（Leviathan 等，2023）：推测解码的原始论文，证明了用拒绝采样可以让加速后的输出分布与原模型完全一致。
  • Training Deep Nets with Sublinear Memory Cost（Chen 等，2016）：梯度检查点。Reducing Activation Recomputation in Large Transformer Models（Korthikanti 等，2022）：只重算注意力等占显存多、计算少的部分。
  • Snowflake ZoRRo / Arctic RL（2026）与 AReaL-DTA（Zhang 等，2026）：训练端的前缀共享，前者针对 GRPO 组内重复的提示词，后者针对多轮交互的前缀树。
  • PULSE（Mihai 与 Belilovsky，2026）：RL 更新中绝大多数 bf16 参数不变，只同步增量。
  • R3（Ma 等，2025）：记录推理时 MoE 的专家选择，训练时重放，消除两个引擎路由不一致的问题。
  • Tinker 文档中的 Sequence Extension 一节，以及 Miles 的《No Token Left Behind: Demystifying Token-In-Token-Out》：序列延展和 TITO 的具体说明。
  • NVIDIA NeMo 框架用户指南中的并行章节：各种并行方式的图解。

十、小结

RL 训练由两种负载组成：以顺序解码为主的采样，和可以并行的前向反向计算，分别交给推理引擎和训练引擎。推理端靠 KV 缓存、前缀缓存、连续批处理和推测解码提速；训练端靠激活检查点、前缀共享和各种并行省显存、省计算。两个引擎之间要同步权重（可以只传增量），MoE 模型还要重放路由决策。Agent 场景有额外的麻烦：Harness 和聊天模板要保证序列延展，轨迹要以 token 形式传递，长短不一的轨迹适合用异步 RL。系统设计上，把各组件拆成服务、加一个代理层兼容各种 Harness，能换来模块化、弹性扩展和多租户训练。下一讲开始讲 Agent 安全：沙盒与凭证管理。
