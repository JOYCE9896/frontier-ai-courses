第五讲：规划、任务分解与多 Agent 协作

Agent 怎样决定要做什么：什么时候先规划，计划怎样表示，何时修改，人在哪里介入

主讲：Daniel Fried · 2026 年 9 月 8 日
资料来源：课程幻灯片 · 课堂录像（本文依据录像字幕整理课堂口述内容） · 指定阅读：Cursor Plan Mode 博客、Least-to-Most、Decomposed Prompting、Code as Policies、SayCan、Plan-and-Act、Thinking vs. Doing、Calibrate-Then-Act、RAO、MACU

一、一个只会"走一步看一步"的 Agent 会怎样失败

课程用一个采购任务开场：为实验室买一台新的 GPU 工作站，需要在多个供应商网站上比较配置和价格，对照内部 wiki 上集群的要求检查兼容性，然后提交采购申请。

一个纯反应式的 Agent（每一步只根据眼前的情况决定下一步）大概会这样做：第 1 步打开供应商 A 的网站看工作站规格；第 15 步配置了两块 RTX 6000、128 GB 内存、850 W 电源；第 31 步才在 wiki 上看到"机架只接受 4U 机箱，每个槽位 1600 W"；中间上下文被压缩过一次，从 128K 压到 14K；搜了四家供应商，只有 D 符合要求，但交货要等 20 周；第 201 步犹豫要不要选 D、找第五家、还是放宽某个要求；第 202 步直接去采购系统提交了申请。

问题出在三处：四个本来可以独立进行的搜索被塞进同一条线程、同一个上下文里；它选的四家都不理想；它还是随便挑了一家就提交了。

仔细看这个任务，它其实有结构：几家供应商的搜索可以并行；兼容性检查依赖 wiki 上的信息；有些信息要到任务后期才出现；提交申请是一个撤不回的步骤。而且当四家都不合适时，任务图本身要改变，需要加一个第五家的搜索。

Daniel Fried 说，这个采购例子来自他们几周前的真实经历：搜了四家，只有一家符合要求，但要等 20 周才能到货。这时 Agent 该直接买，还是去问人，还是再找几家？它需要根据在环境中看到的情况改变计划。他把这个任务画成一张依赖图：四家供应商的搜索互不依赖，可以并行；兼容性检查依赖这四家的结果；检查通过后才能提交申请。如果四家都不合适，就要往图里加新的节点。根据环境观测修改这张图，就叫重新规划（replanning）。

他也提到了这门课反复出现的一对矛盾：计划越固定，人越容易理解和监督 Agent 的行为；计划越灵活，Agent 越能应对途中出现的新情况。这一讲会看到设计空间里在两者之间取舍的不同做法。第三讲的上下文压缩是把"做过的事"总结成一个产物，计划也是一个 Agent 可以随时参考的产物，区别在于计划写的是"接下来要做什么"。

这一讲围绕四个问题展开：价值，规划什么时候有用，什么时候反而有害；表示，计划用什么形式写；承诺，计划什么时候制定，什么情况下可以改；监督，人应该怎样、在什么时候参与。

二、什么是计划

Cursor、Claude Code 和 Codex 都推出了"计划模式"（Plan Mode），流程是：只读调查、提出澄清问题、写出计划、人来审核、然后执行（可能用子 Agent 并行）。这可能从几个方面带来帮助：更多的计算、更好的上下文、一个外部的计划文件、任务分解，或者人的批准。

课上大部分学生都用过编程 Agent 的计划模式。Daniel 说这类功能大约一年前开始流行，Cursor 可能是最早的。计划模式在调查阶段只做不改变任何东西的动作，比如浏览代码库、收集信息，方便人判断计划好不好；人审核时可以直接改计划，也可以发消息让 Agent 改；确认后点"构建"，Agent 开始执行，这时还可以用子 Agent 并行执行计划里的各项。在 Claude Code 里，计划模式其实被设计成一种权限模式：先只执行收集信息的动作，批准之后再放开权限。

Daniel 请学生说说计划为什么有用，学生的回答有这几条。

  • 对于不太信任 Agent 的任务，看过计划能建立信任，知道它大概率会做对。
  • 先规划后执行的总成本可能比走一步看一步更低。Daniel 补充了几种情况：计划里的每一项比较简单，可以交给便宜的弱模型，只有写计划需要贵的强模型；子 Agent 可以并行，即使总计算量不少，时间也更短；好的计划还能避免 Agent 犯错陷入循环，少做很多无用的动作。
  • 计划可以当作人和 Agent 共享的草稿纸，把零散的想法理成结构。
  • 很长的任务拆成多个子任务后，有一个显式的产物记录做完了什么、还剩什么，帮助 Agent 跟踪进度。Daniel 说这和上下文管理的动机相似，只是计划是人能读、人能改的。

Cursor 的官方博客说，Cursor 现在大多数新功能都是从 Agent 先写一份计划开始的，他们观察到这明显提高了生成代码的质量。Agent 在规划时会调研代码库、查文档、提出澄清问题，最后生成一个带文件路径和代码引用的 Markdown 文件，用户可以在编辑器里直接修改这份计划。

课程给出的工作定义是：计划是对未来预期行为的显式表示，包括 Agent 将要尝试的动作或子目标，以及它们之间的顺序和依赖关系。它有三个特点：计划只针对当前任务，这是它和技能的区别，技能是跨任务可复用的，所以计划可以比技能更具体；计划组织未来的工作，可以写到动作层面，也可以只写子目标；计划是一个提议，不是保证，用户、另一个模型或环境交互都可以检查和修改它。

Daniel 引用了拳击手迈克·泰森的一句话："每个人都有计划，直到脸上挨了一拳。"有计划是好事，但也要能随时调整。同时他提醒，能重新规划也意味着 Agent 的行为更难预测、更难由人事先规定，这是后面要面对的取舍。

规划在课程里分散在好几讲：本讲讲提示出来的计划和 Harness 结构（分解、重新规划、计划文件）；编程 Agent 那讲讲一个固定的工作流 Agentless；多 Agent 交互那讲讲角色和通信；人机交互那讲讲澄清和人工批准；搜索那两讲讲对计划和预测结果的搜索。

三、行动前先分解

1. 思维链本身就是一种计划

Kojima 等（NeurIPS 2022）发现，在问题后面加一句"Let's think step by step"，模型的推理就会变好。Wang 等（ACL 2023）的 Plan-and-Solve 更进一步，提示词改成"先理解问题并制定一个解题计划，然后执行计划，一步步解题"。思维链给了模型额外的计算量和一块可以回头参考的草稿纸。但计划和解答是在一次生成中一起出来的，没有任何东西专门检查这个计划。思维链也可以被训练，以提高得出正确答案的概率，比如 STaR（Zelikman 等）和 DeepSeek-R1。

Daniel 补充了一点背景：在模型被专门训练去写思维链之前（也就是 o1、R1 这类推理模型出现之前），人们只能靠提示词让模型写思维链。Kojima 等人的论文里有一张很有意思的表，列出了各种提示词和对应的准确率，效果最好的就是"Let's think step by step"，一度被戏称为"一句话就够了"。后来的模型经过训练，对提示词的措辞不再那么敏感。思维链的作用有两个：让模型在给出答案前多做一些计算；提供一块草稿纸，把中间结果写下来，把解决复杂问题的过程外化。Agent 做规划的动机和这一样。他说，推理模型已经走到了"训练模型写出对答案有用的思维链"这一步，而 Agent 的规划现在正处在刚开始"训练模型写出对完成任务有用的计划"的阶段，本讲后面的 RAO 就是例子。

2. 把规划和求解分开

Least-to-Most（Zhou 等，ICLR 2023）分两个阶段：第一阶段写出子问题；第二阶段按顺序回答，每个答案传给后面的子问题。背后的观察是，模型回答复杂问题有困难，但回答子问题更好，而且回答子问题需要的上下文更少。问题越长，这种方法的提升越大。Recursive Language Models（Zhang 等，2025）延续了这个思路。

Daniel 用论文里的数学题解释了这个过程：先调用一次模型，把复杂问题拆成几个子问题，比如先问"每一趟要多长时间"，得到"五分钟"，再带着原问题和前面的答案去问下一个子问题。对当时的模型来说这帮助很大，因为它们还不擅长一口气完成需要多步推理的问题。这些动机对今天的 Agent 同样成立：搜某一家供应商的 GPU 时，不需要知道其他几家的情况，查完带回结果再汇总即可。按论文摘要，这个方法主要解决的是"由易到难的泛化"：普通思维链在题目比提示里的示例更难时往往表现不好。

3. 分解带来模块化

Decomposed Prompting（Khot 等，ICLR 2023）用一个分解器生成子任务，并把每个子任务交给专门的处理器。例如"1910 年出生的人制作的电影获得过什么奖"，拆成"哪些人出生于 1910 年"（交给简单问答处理器）、"#1 担任过哪些电影的制片人"（交给另一个处理器）等等。模块化的好处是每个处理器可以单独改进，用上下文示例或训练都可以。

Daniel 问学生：为什么要用不同的模型解决不同类型的子问题？学生答：可以找一个或训练一个专门擅长这类问题的模型。另一个原因是效率，简单的子问题不需要贵的模型。在 Decomposed Prompting 里，不同的处理器其实是同一个语言模型配上不同的提示和少样本示例，但你也可以设想每个处理器掌握不同的专门知识或工具。这篇论文还有一种简单的程序化控制：规定子任务的顺序，并允许把前一个子任务的答案作为参数传给下一个（上面例子里的 #1）。他指出，就像上一讲技能从模板走向代码一样，这种专用的结构化表示也可以换成通用的代码来编排子任务，本讲后面的 RAO 就是这样做的。

四、会作用于真实世界的计划

1. 推理和行动的区别

思维链里的一步推理只改变文字，写错了可以接着写来纠正，所有中间结果都能看到。计划有用，前提是模型基于它能做出更好的后续生成。

在真实世界里执行一个动作就不一样了：它改变了 Agent 接下来面对的状态；它可能揭示新的信息；它可能失败；它可能不可逆，比如提交、发送。所以一旦要行动，计划就必须考虑可行性、后果、信息和出错后的恢复。

Daniel 这样对比：思维链里的推理只是在写字，不会改变环境，也不会揭示新信息，因为所有内容都来自模型自己；写错了，写一句"算了，不对"再改就行。Agent 就不同了：它的动作会揭示信息，比如查到某家供应商有哪些 GPU；动作可能失败，计划再好，执行时发现需要的东西根本不存在；动作还可能不可逆地改变环境，比如删掉你所有的文件。这些都是推理模型不会遇到的问题。

2. 经典规划

传统 AI 里的规划（STRIPS，Fikes 与 Nilsson，1971）是这样定义的：状态是一组谓词，比如 on-table(x)、on(x, y)、clear(x)、holding(x)、hand-empty；动作有前提条件和效果，比如 pick-up(x) 要求 x 在桌上、x 上面没东西、手是空的，执行后变成手里拿着 x、x 不在桌上、手不空。一个合法的动作序列要求每一步的前提都满足。规划就是一个搜索问题：找到一串合法动作，从初始状态到达目标。

Daniel 提到，除了 STRIPS，PDDL 是另一种常用的规划语言，现在有研究把它作为评估 LLM 的目标，也有人在探索怎样结合两种方法的长处。经典规划的大部分工作是搜索：给定这种高度结构化的表示，用广度优先、深度优先、带启发函数的 A* 等算法找到一条从起点到终点的计划。

例子来自 PlanBench（Valmeekam 等，NeurIPS 2023）：蓝色积木压在橙色积木上，目标是橙色压在蓝色上。计划是：把蓝色从橙色上拿下来，放下蓝色，拿起橙色，放到蓝色上。

3. 难点变了

在 LLM 里，这些都是隐含的，没有明确的谓词和前提条件。对 LLM Agent 来说，写出一个看起来合理的计划变容易了，但判断它对世界的理解是否正确变难了。所以 Agent 的设计里深度搜索少了，更多是去检查真实世界：观察、验证、从错误中恢复。不过搜索和"动作是否适用"仍然是有用的概念。

Daniel 解释得更具体：经典规划里一切都是明确的，你确切知道一个动作什么时候能用、用了会怎样，对世界的了解也很多（也有表示不确定性的方法）。LLM 则相反，一个动作到底意味着什么、什么时候能用，大多存在于 Agent 之外，只能去环境里试。但 LLM 见过大量各种场景的信息，写一个合理的初步计划不需要做多少搜索，无论是移动积木还是调试代码库里的问题。所以对 LLM 来说，规划更多是检查计划是否可行、能否执行。课程末尾讲搜索时，会看到把搜索重新引入 LLM Agent 的方法。

4. 计划的表示形式

形式化的计划可以被检查，自然语言的计划更通用，程序介于两者之间。2023 年前后有一系列工作用代码 LLM 写程序，调用感知和控制 API：Code as Policies（Liang 等，ICRA 2023）、ProgPrompt（Singh 等，ICRA 2023）、Binder（Cheng 等，ICLR 2023）。程序可以运行、可以检查，但受限于 API 和程序结构能表达的范围。不过 API 本身也可以调用 LLM 或其他神经网络模型。

Daniel 用机器人例子说明这类方法：任务是"把积木叠到空碗上"，LLM 被提示写一段程序，调用领域专用的函数，这些函数由机器人的底层能力实现，比如对图像运行物体检测器，看有没有积木、有没有碗，再调用机械臂去操作。要让这行得通，需要有好的 API，而且任务本身要能被代码很好地表达。代码的好处之一是可以写"只要积木还没放上去就重试"这样的逻辑，相当于实现了简单的搜索和后置条件检查；缺点和上一讲讲过的一样，比较死板。他的理解是，在机器人领域，这类方法没有像端到端训练的多模态视觉语言动作模型（VLA）那样流行起来，但在编程 Agent 这类场景里仍然很有用，下一讲的 CodeAct 就是一个例子。

5. 为什么要边做边重新规划

决策可以在执行前做，也可以在执行中做，有三种程度：

  • 开发者定义的工作流：由开发者写死流程，比如检查一个固定的供应商列表。下一讲的 Agentless 就是这种。
  • 先规划后执行：模型决定查哪些供应商，然后在执行前就定下来。
  • 自适应：四家都不合适时，执行反馈让模型去找另一家。RAO 和 MACU 属于这种。
for v in VENDORS:               # 固定列表
    specs[v] = read_specs(v)    # 调用模型
ok = [v for v in specs if fits(v)]
requisition(cheapest(ok))

上面就是一个开发者定义的流程。事先定好计划更快、更便宜、更可预测；重新规划让模型能在执行中发现新信息时调整。课程引用 Anthropic 2024 年的文章 Building effective agents，建议只在反馈值得付出额外成本和复杂度时才用重新规划。

Daniel 对 Anthropic 那篇文章的解读是：先别急着做 Agent，从简单、容易推理、能事先规定的"工作流"开始。比如假设实验室经常买 GPU，每次都走同样的流程：固定的供应商列表，读规格，检查是否符合，挑最便宜的买。这样你清楚知道 Agent 大致会做什么，它仍有一定灵活性，比如供应商网站改版了，它大概还能找到信息。但缺点也很明显：如果这些供应商已经不是最好的选择了呢？可以放松一点，让 Agent 自己预测该查哪些供应商；或者完全放开，只告诉它你想要什么。

他还提到，Anthropic 后来在这篇文章上标注了"部分内容已过时"，并指向新的文章。他认为部分原因是现在的 Agent 更强了，不受工作流约束时也常常能做出合理的动作；编程领域也是这样，Agentless 这类固定流程已不再是解决 issue 最成功的方法。所以随着 Agent 在某个领域变强，一部分脚手架可以拿掉，但可靠性可能也跟着下降。如果你面对的是一个新问题，Agent 从没被训练过如何应对环境变化，从工作流开始更稳妥。

五、加入规划结构的四个理由

课程把理由归为四类，并对应到采购任务上：模块化，几家供应商的搜索分开进行；反馈，都不合适时修改计划，加一家供应商；长程，需求和进度要在整个任务中保持；控制，提交前由人批准。

1. 模块化：规划器和执行器分开

分开的模块可以用不同的模型和训练数据。UGround（Gou 等，ICLR 2025）和 Agent S（Agashe 等，ICLR 2025）里，GPT-4o 作为规划器，能看懂屏幕，但不擅长给出像素级的点击坐标，所以它只用语言描述下一步动作；再由一个单独训练的 7B 执行器把描述转换成屏幕坐标。

Daniel 补充说，这类方法在 2025 年的电脑操作 Agent 里用得很多，原因是当时最擅长写计划的模型不擅长处理网页上细粒度的视觉细节，尤其是要点到特定像素的时候。UGround 的做法是用合成数据训练这个 7B 模型：拿网页，为页面上的特定元素合成文字描述，训练模型根据描述找到元素。模型足够准之后，就可以执行规划模型给出的自然语言指令。模块化的好处是可以找出瓶颈在哪个组件，再单独把它做好。后来训练大模型的公司把这类细粒度的网页数据直接加进了大模型的训练，这种拆分对提升准确率已不那么必要，但对提高效率仍然有用。

Plan-and-Act（Erdogan 等，ICML 2025）用一个教师模型把成功的轨迹切分并标注出计划，然后在这些标注过的轨迹上分别微调规划器和执行器。

Daniel 解释了这里的难点：计划不像其他数据那样自然存在，没有现成的"计划"语料。所以 Plan-and-Act 先收集完整的执行轨迹，筛掉预测为错误的，再让教师 LLM 把每条轨迹切成几段，为每段写一句自然语言标签。有了这些，就可以"拆开"成两份训练数据：规划器学的是从任务描述到一串自然语言步骤；执行器学的是从一个步骤的描述到实际的动作。他指出这和上一讲的工作流归纳有相似之处，都是从轨迹出发做切分和标注，区别是这里用来生成训练数据。

但固定角色也有风险。Graham Neubig 2024 年的文章 Don't Sleep on Single-agent Systems 指出，编程任务中按角色拆分的多 Agent 系统（比如 CodeR）效果有限：角色是在任务到来之前定好的，验证者无法定位故障来检查自己的答案；交接靠摘要报告，可能丢掉下一个 Agent 需要的上下文。

Daniel 提到，编程领域曾有一系列论文让模型模拟一家软件公司或一个工程师团队，设有测试、编辑等专门角色，有的甚至设了产品经理。这些方法以及 Agentless 这类为解决 GitHub issue 量身定做的流程，在任务恰好符合这种结构时效果不错，但不够灵活，而且模块之间传递信息时，很难把下一个 Agent 需要的信息都传过去。如果是单个 Agent，只要上下文管理做得好，之前所有动作的信息都在，Agent 都能用上。

Graham 那篇文章的论证更完整。他指出多 Agent 系统的每个 Agent 其实就是"LLM 加提示词加动作空间"，而一个单 Agent 完全可以通过切换提示词和动作空间来扮演不同角色，同时保留全部上下文。

2. 反馈：考虑动作能否执行

回想经典规划里动作有前提条件。SayCan（Ahn 等，CoRL 2022）为机器人的每个技能学一个价值函数，预测当前状态下这个技能能成功完成的概率；再把它和 LLM 生成这一步计划的概率相乘，给子任务重新打分。这样 LLM 提出的计划不仅要"说得通"，还要"做得到"。

Daniel 讲了这项工作的背景：LLM 在 NLP 任务上大获成功之后，人们开始尝试用它来控制机器人，取代以往的规划系统。比如给出"把苹果放到桌上"，LLM 可以生成各种可能的下一步，每一步有一个模型给出的分数。问题是 LLM 不知道机器人在当前场景里能做什么：它可能提出"拿起苹果"，可如果视野里根本没有苹果，这就是一个糟糕的子任务。SayCan 用机器人领域的经典技术学习"可供性"（affordance）模型，也就是这个子任务在当前情况下能否被执行。附近没有苹果或可乐罐时，"拿起苹果"的概率就低，"去找苹果"的概率就高，"放下苹果"更低，因为手里根本没有。最后把两个概率相乘。

LLM-Planner（Song 等，ICCV 2023）、Inner Monologue（Huang 等，CoRL 2022）、SwiftSage（Lin 等，NeurIPS 2023）则根据环境反馈重新规划。

课上用 LLM-Planner 在 ALFRED 环境里的例子说明。ALFRED 是一个模拟的家居环境，机器人在房子里走动，任务是合成的，有些挺好笑，比如"把土豆煮熟然后放进回收桶"。模型先写出计划：走到土豆那里、拿起土豆、放进回收桶。执行时机器人报告"找不到土豆，但看到一个冰箱"，把这条反馈交给语言模型重新预测计划，新计划变成"打开冰箱"，希望土豆在里面。这是一种很简单的、类似 Reflexion 的重新规划方式，对那些一开始看不到全部环境信息的任务尤其有用。

3. 多想还是多做

Test-Time Interaction（Shen 等，NeurIPS 2025）在相同计算量下比较三种推理方式：生成更长的思维链、采样多个候选、与环境多交互几次。比如 Agent 宣布任务完成时，提示它"你刚才发出了完成信号，停一下再想想"。增加交互能从环境中获得更多信息，效果类似 Reflexion。

Daniel 描述了论文里的曲线：在花费相同 token 数的情况下，把 token 用在和环境多交互上的方法（绿线），通常好于把 token 用在每个动作前多想一会儿的方法（蓝线），也好于采样多条轨迹再让裁判挑一条的基线。他的总结是：只要不把自己带进糟糕的状态，从环境中多获取信息通常很有帮助。

Cuadron 等（2025）研究了"想太多"的问题，总结出三种模式：分析瘫痪、一连串失控的动作、过早放弃。在各类模型上，想得越多，解决的问题越少。

这篇论文 Graham 也参与了。Daniel 解释了方法：三种模式都不需要读取模型的推理内容，只需要知道它在推理上花了多少 token（很多 API 都提供这个数字），再结合它在环境中实际做了哪些动作。作者为三种模式训练了分类器，合成一个"想太多分数"，在 SWE-bench 上发现这个分数和解题表现有很强的负相关。更大、更强的模型在一定程度上能缓解这个问题，比如同一个 o1，推理强度调高反而想太多的程度更低、表现也更好；不是推理模型的模型也会在动作前写一些文字，同样有这种现象，只是没那么严重。按论文摘要，作者分析了 4018 条轨迹，这个分数和人类专家的评估相符。

Calibrate-then-Act（Ding、Tomlin、Durrett，2026）设计了一个需要"去看一看"的任务：每个文件都有一个隐藏格式，由三部分组成，分隔符（逗号、分号或制表符）、引号字符（双引号或单引号）、要跳过的表头行数（0 或 1），共 12 种组合，三项全对才能解析成功。唯一的线索是文件名，比如 sales_fr.tsv 暗示是制表符。该方法在提示里加入各种格式的估计概率，模型读到后会想："分隔符最可能是分号，概率约 0.85……但我不是百分之百确定，也许应该先跑几个单元测试确认。"也就是先校准自己的把握程度，再决定是直接做还是先查证。

课上 Daniel 用了一个更日常的例子：让编程 Agent 读一个 CSV 文件，找出价格最高的商品。大多数和价格有关的 CSV 都有一列叫 price，模型直接按这个假设去写代码，多数时候是对的，但不总是对。这篇论文研究的是：把"环境具有某种性质"的概率显式写出来，能否让 Agent 更可能做对，结论是可以。按论文摘要，它关注的是探索的成本和不确定性之间的权衡，比如写代码时，Agent 可以直接运行代码，也可以先写测试；写测试和跑测试都有成本，但通常低于运行有 bug 的代码的代价。

4. 长程：错误会一直带下去

Vending-Bench（Backlund 与 Petersson，2025）让 Agent 长时间经营一台自动售货机：定价、订货、补货，最长 2,000 条消息，约 2,500 万 token，最多模拟 222 天。课上的失败案例：Agent 在货物到期当天就去补货，但"今天到期"不等于"已经送达"，环境正确地报告"商品不可用"；Agent 错误地推断"现在不可用"等于"生意失败了"，从此不再等待到货邮件，也不再检查；错误一直延续，后来它把每天正常扣的费用当成欺诈，发邮件标题写着"紧急：业务终止后的未授权收费"。一个暂时的错误影响了后面所有决定。

Daniel 说，Vending-Bench 难在时间跨度长，而不是推理复杂：每件事都很简单，但要在最多 222 天、约 2500 万 token 里一直跟踪状态、反复做出好决定，还不能被自己过去的错误拖累。随着模型用长上下文训练、用强化学习学会从错误中恢复，这方面已经在进步。论文摘要提到，不同模型之间以及同一模型的不同运行之间，表现差异都很大。

Sinha 等（2025）分析了执行长度：单步准确率越高，能完成的任务越长；但模型会被自己之前的错误影响（自我条件化），后面的步骤准确率下降。更大的模型能执行更长的任务，但自我条件化也更严重。课程留下的问题是：强化学习能否解决这个问题。

Daniel 用概率解释了长程任务为什么难：每一步 90% 的正确率，连续做对所有步骤的概率是 0.9 × 0.9 × 0.9 ⋯ 一路乘下去，很快就很低了。反过来，单步准确率从 0.9 提高到 0.999，能完成的任务长度会大幅增加。这篇论文的标题 The Illusion of Diminishing Returns 就是这个意思：在短任务基准上看起来进步在放缓，但单步准确率的一点点提升，会复合成能完成的任务长度的指数级增长。

关于"自我条件化"，他给出了一个直观解释：模型是在网上所有代码上预训练的，一个文件前面的代码写得好，后面大概率也写得好；前面有 bug、写得随意，后面大概率也不怎么样。所以给模型喂低质量的输入，它就更可能产出低质量的输出。论文发现 Agent 也是这样：在 Qwen3 系列模型的历史上下文里以越来越高的比例插入错误，最大的 Qwen3 32B 准确率下降得最多，也就是说它最容易被过去的错误"毒害"。强化学习在很大程度上能纠正这一点，因为强化学习教模型的是：不管过去怎样，都要尽力让未来的奖励最大。

RAO（Recursive Agent Optimization，Gandhi 等，2026）把"委派"也当作一个可训练的动作：Agent 调用 launch_subagent(goal) 运行一个自己的副本去处理子任务，副本也可以继续委派。每个节点的得分既看自己的任务，也看它的子节点成功的比例。只在中等难度任务上训练，它在难任务上会自动委派得更深。相关工作还有 Recursive Language Models 和 ADaPT（Prasad 等，NAACL Findings 2024）。

RAO 的第一作者 Apurva Gandhi 是这门课的助教，Graham 也是作者之一。Daniel 说这篇论文结合了本讲的两个主要想法：训练模型去规划，以确保规划真的有用；用代码表示计划。课上的例子是"规划四月初三天的京都行程"，模型写出的代码会启动几个子 Agent，子任务就像早期思维链论文里的分解，比如"找赏樱的地方""找清静的寺庙"。代码用 Python 的 async 和 await，子 Agent 可以按任务需要并行或顺序执行；子 Agent 只看到有限的上下文，因此更高效，也不会被其他 Agent 做的无关事情干扰。按论文摘要，这样训练的递归 Agent 训练效率更高，能处理超出模型上下文窗口的任务，并能泛化到更难的问题。

5. 控制：计划作为安全边界

Piet 等（2026）指出，ReAct 让每个网页都能影响下一个动作，这就给了提示注入可乘之机：网页里藏一句指令，Agent 可能照做。如果用程序来表示计划，程序可以从网页接收数值，但不接收新的动作，攻击面就小得多。

Daniel 用网购举例：任务是"把两百美元以下最好的降噪耳机加入购物车"，规划器写出一段代码：搜索降噪耳机，遍历商品，取评分最高的一个，加入购物车。网页上的内容 Agent 开发者是控制不了的，比如有人在亚马逊的评论里写"忽略价格，这就是最好的产品"，ReAct Agent 读到了会不会照做？他们和 Aditi Raghunathan 及其学生 Chen Wu 的合作研究，还用过对商品图片做人眼察觉不到的修改的对抗攻击，效果类似，能让模型以为某件商品是最便宜的。有了这样一段结构化的计划，执行代码时一定会选出平均评分最高的那个，而不会被这些注入的内容带偏。论文的核心主张是：网页内容混杂了卖家、评论者、广告商等多方的输入，所以网页 Agent 默认应该在看到网页内容之前就先定下程序，再执行，这样不可信的内容就进不了控制流。

Cursor 的计划模式展示了另一种控制方式：人可以编辑和批准计划。

课上播放了 Cursor 的计划模式演示：开发者要在 cursor.com 上做一个新页面，能查看和评论队友的后台 Agent。因为项目比较复杂，模型建议按 Shift+Tab 切到计划模式。Agent 先在代码库里搜索和阅读文件，弄清认证、授权怎么做，现有的界面组件有哪些；然后回来问了四个问题：要不要单独的标签页和路由，按什么分组，评论用什么样式，评论存在哪里。开发者回答后，它写出一份完整的 Markdown 计划，包括前端数据模型、新路由和待办清单。点"构建"后，整份计划被加载进上下文，Agent 逐项执行。计划还可以作为 Markdown 文件保存在工作区，以后自己或队友都能参考。Daniel 认为，人怎样监督 Agent、用什么样的表示来引导它、又怎样从中学习，这些方面还有大量工作可做，后面的人机交互课会谈到。

还有一类约束跨越所有子任务。TravelPlanner（Xie 等，ICML 2024）里，航班、酒店、餐饮、景点可以干净地分解，但预算、交通方式和饮食要求是全局的，分开处理时经常被违反。

六、综合案例：多 Agent 电脑操作

最后一部分用 Daniel Fried 团队的工作把上面的内容串起来。Odysseys（Jang、Koh、Fried、Salakhutdinov，2026）是一个长程网页任务基准，课上的例子是"寻找做 ACL（前交叉韧带）手术的外科医生"，需要在多个网站之间查找、比对信息。

Odysseys 的任务来自真实的浏览记录：研究者请志愿者自愿捐出自己的 Google 浏览历史（可以自己选择捐哪些），据此构造网页 Agent 的基准任务。完成一个任务可能要几百步，相当于人在电脑上干半小时到一小时；评估时用评分细则逐项检查任务的各个部分是否完成。课上展示的一条轨迹用了 93 步，访问多个网站，把信息整理进一张表格，每一步都是底层的点击和输入。这种任务既长，又有结构，和开头的 GPU 采购例子很像。

MACU（Multi-Agent Computer Use，Koh、Salakhutdinov、Fried，2026）采用管理者加多个工作者的结构：管理者分解任务、分派子任务、根据结果修改任务图；工作者在各自的电脑环境中并行执行。幻灯片展示的实验结论有：更强的管理者能改善协调（在 OSWorld 的 36 个任务上，工作者固定为 Qwen3.5-4B）；较弱的工作者从中受益更多（管理者固定为 Opus 4.6）；在 Odysseys 简单子集的 45 个任务上考察了工作者并行数量的影响；管理者还能在执行中修改任务图。

Daniel 补充了 MACU 的运行方式：管理者用一个强模型（比如较新的 Claude 模型），把任务分解成有向无环图；按图中的依赖顺序，用并行的子 Agent 执行各个子任务；子 Agent 报告完成后，管理者检查结果，做得不对就让它重做，做对了也可能修改图，比如加一家新的供应商。如此反复，直到图全部处理完。课上的演示任务是"判断今天去旧金山吃早午餐合不合适"，需要查天气、查餐厅，可以看到管理者在执行中途发现需要新信息，往图里加了一个新节点。

这种模块化带来的一个好处是：管理者和工作者可以用不同的模型。工作者用一个便宜的模型，比如 Qwen3.5-4B，甚至可以在本地跑，不用调昂贵的 API；工作者固定时换更强的管理者，表现提升明显，而每个任务的成本增加不多，因为大部分动作是工作者做的。越弱的工作者，从管理者那里得到的提升越大。关于重新规划的价值，他们做了一个实验：限制管理者修改任务图的次数。完全不许修改时，在这个很难的长程基准上成功率约 25%；允许改一次，略有提升；允许的次数越多，成功率越高。

七、设计清单与开放问题

在加入规划结构之前，先问四个问题：

  1. 子任务能分开吗？规划器和执行器用不同的模型或训练会更好吗？
  2. 哪些失败或观测应该改变计划？
  3. 系统怎样阻止错误和上下文不断累积？
  4. 哪些信息或权限要分开？谁来批准不可逆的动作？

仍然没有解决的问题：检查，自然语言计划和子目标图没有通用的验证器；校准，Agent 经常判断不好什么时候该想、该看、该问、该改；全局状态，跨子任务的约束既难以分解，也难以靠更长的上下文解决；脚手架，经过训练的推理能力最终会不会把这些外部结构吸收进模型内部，目前还不清楚。

八、指定阅读与参考资料

指定阅读（十篇）

  • Cursor 博客 Introducing Plan Mode：见第二节。
  • Least-to-Most Prompting（Zhou 等，2022）：把复杂问题拆成一串更简单的子问题，按顺序求解，每个子问题都能用上前面的答案。在符号操作、组合泛化和数学推理任务上，能解出比提示示例更难的题目。
  • Decomposed Prompting（Khot 等，2022）：把复杂任务通过提示拆成子任务，交给一组专门处理各类子任务的提示化 LLM。每个提示可以针对自己的子任务单独优化，必要时继续拆分，也可以换成更好的提示、训练过的模型或符号函数。
  • Code as Policies（Liang 等，2022）：用会写代码的 LLM 写机器人策略代码。给几个"自然语言命令加对应代码"的示例，模型就能根据新命令重新组合 API 调用，写出新的策略代码，代码里可以处理感知结果（比如物体检测器的输出），并设定控制原语的参数。
  • SayCan（Ahn 等，2022）：见上文。论文标题 Do As I Can, Not As I Say 概括了核心思想：语言模型提供"该做什么"的语义知识，技能的价值函数提供"在这里能做什么"的现实约束。
  • Plan-and-Act（Erdogan 等，2025）：把高层规划和底层执行分开，并提出一种可扩展的方法合成规划器的训练数据，解决"LLM 本身没被训练过写计划"的问题。
  • Thinking vs. Doing（Shen 等，2025）：提出"扩展测试时交互"这个新维度。只在行动前多想，Agent 无法从环境获取新信息，也无法随时间调整行为；增加交互步数，才能在一次执行里做探索、回退和动态重新规划。
  • Calibrate-Then-Act（Ding 等，2026）：让 Agent 显式地权衡"继续探索的成本"和"不确定性"，比如何时停止探索、给出答案，从而在环境中做出更优的行动。
  • Recursive Agent Optimization（Gandhi 等，2026）：见上文。
  • Multi-Agent Computer Use（Koh 等，2026）：主张电脑操作 Agent 不应只是单个串行的 Agent，而应转向强调规划和并行执行的多 Agent 系统。论文提出管理者把任务分解成有向无环图、为子 Agent 编码依赖和目标的通用框架。

参考资料

  • Large Language Models are Zero-Shot Reasoners（Kojima 等，2022）：发现只要在每个答案前加上"Let's think step by step"，LLM 就是不错的零样本推理者，不需要手写逐步推理的示例。
  • Plan-and-Solve Prompting（Wang 等，2023）：指出零样本思维链有三类错误：计算错误、漏步骤、误解语义。为减少漏步骤，提示模型先制定计划把任务分成子任务，再按计划执行。
  • STaR（Zelikman 等，2022）：用少量带推理过程的示例，加上大量没有推理过程的数据，自举出推理能力。循环很简单：生成推理过程来回答问题；答错的，给出正确答案让模型重新生成推理过程；在最终答对的推理过程上微调；重复。
  • DeepSeek-R1（2025）：表明纯强化学习就能激发 LLM 的推理能力，不需要人工标注的推理轨迹，自我反思、验证等高级推理模式会自发出现。
  • Recursive Language Models（Zhang 等，2025）：把超长提示当作外部环境的一部分，让 LLM 用程序去查看、拆分它，并对其中的片段递归地调用自己。能处理比模型上下文窗口长两个数量级的输入。
  • PlanBench（Valmeekam 等，2022）：指出很多关于 LLM 规划能力的结论来自常识性任务，分不清模型是在规划还是在从海量知识里检索。于是基于国际规划竞赛的领域，构建了系统、可扩展的规划基准。
  • ProgPrompt（Singh 等，2022）：用程序形式的提示结构生成机器人任务计划，提示里列出可用的动作和环境中的物体，并给出示例程序，使生成的计划能适应不同的环境、机器人能力和任务。
  • Binder（Cheng 等，2022）：把任务输入映射成程序，把语言模型的功能作为 API 绑定到 SQL、Python 等语言里；LM 既负责解析出程序，也在执行时被 API 调用。
  • Anthropic：Building Effective Agents（2024 年 12 月）：和几十个团队合作后的总结：最成功的实现用的是简单、可组合的模式，而不是复杂的框架。
  • UGround（Gou 等，2024）：主张 GUI Agent 像人一样完全靠视觉感知环境、直接做像素级操作，不依赖 HTML 或无障碍树这类有噪声、不完整、开销大的文本表示。
  • Agent S（Agashe 等，2024）：见第四讲。
  • Language Models as Zero-Shot Planners（Huang 等，2022）：发现足够大的预训练语言模型，在合适的提示下能把"做早餐"这样的高层任务分解成中层计划，不需要额外训练；但直接生成的计划往往对不上环境允许的动作，论文提出一种把生成结果映射到合法动作的方法。
  • LLM-Planner（Song 等，2022）：用 LLM 为具身 Agent 做少样本规划，并用物理环境的信息生成和更新计划。
  • Inner Monologue（Huang 等，2022）：让 LLM 在具身环境里利用环境反馈（比如成功检测、场景描述、人的回答）形成一段"内心独白"，据此持续规划。
  • SwiftSage（Lin 等，2023）：借鉴人类认知的双过程理论：Swift 模块是一个在专家轨迹上微调的小模型，负责快速、直觉的动作；Sage 模块用 GPT-4 这样的大模型做子目标规划，负责慢速、深思的决策。
  • The Danger of Overthinking（Cuadron 等，2025）：见上文。
  • Training Proactive and Personalized LLM Agents（2025）：主张把 Agent 训练成会沟通、能适应人的合作者，提出三个维度：生产力、主动性和个性化；构建了带可配置用户模拟器的环境 UserVille，用多目标强化学习同时优化任务结果、提问的代价和对用户偏好的遵守。
  • Vending-Bench（Backlund 与 Petersson，2025）、The Illusion of Diminishing Returns（Sinha 等，2025）：见上文。
  • ADaPT（Prasad 等，2023）：只在 LLM 执行不了某个子任务时才进一步分解和规划，按需递归，从而适应任务的复杂度和模型的能力。
  • Web Agents Should Adopt the Plan-Then-Execute Paradigm（Piet 等，2026）、TravelPlanner（Xie 等，2024）、Odysseys（Jang 等，2026）：见上文。TravelPlanner 提供了一个包含大量数据的沙盒环境，任务需要同时满足多种约束。
  • Graham Neubig：Don't Sleep on Single-agent Systems（2024）：见上文。
  • Claude Code 的权限模式文档、OpenAI 的模型使用指南：计划模式相关的产品文档。

九、小结

计划是对未来行为的显式表示，是一个可以修改的提议。先分解再求解，能降低每个子问题的难度，并带来模块化。一旦计划要作用于真实世界，就要处理可行性、新信息、失败和不可逆操作。加入规划结构有四个理由：模块化、反馈、长程和控制，每一个都有对应的方法和代价。事先定死流程更便宜可控，重新规划更灵活，选择哪种要看反馈是否值得。
