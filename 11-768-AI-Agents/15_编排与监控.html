第十五讲：编排与监控

用 LangGraph 把已知流程固定下来，再用执行轨迹、成对比较和行为聚类看清 Agent 实际做了什么

主讲：Daniel Fried · 2026 年 10 月 20 日
资料来源：课程幻灯片（共 39 页）· Transluce 的 Terminal-Bench 调查 · Hodoscope 论文
本讲录像尚未公开（截至 2026 年 11 月 7 日），本文依据幻灯片和它引用的资料整理，不含课堂口述。录像发布后再对照补充。

一、本讲的位置

前面几讲已经出现过几种约束 Agent 行为的办法。第 4 讲的技能用指令引导行为，可执行的技能还能限制执行方式。第 5 讲的 MACU、RAO 把任务拆开再协调。第 14 讲的自动化把多次 Agent 运行串成规定好的步骤和检查。

这一讲讲的编排框架（orchestration framework）沿着同一个方向再走一步：开发者提前写好流程的一部分，只把需要判断和行动的环节交给模型。

下半讲换一个问题：一个 Agent 已经跑了成百上千次，怎样知道它实际做了什么？这就是监控。

二、单 Agent 和显式工作流

两种系统用的材料相同，都是模型、工具和普通代码。差别在于行为由谁决定。

单 Agent显式工作流
结构模型和工具之间循环：行动，观察，再行动一串提前定好的步骤，例如分类（模型）→ 检索（代码和工具）→ 调查（模型和工具）→ 检查（代码）
行为由什么决定模型、提示词和环境更多由开发者提前写定

流程已知的时候，固定下来能减少模型要做的决定，带来两个好处。

  • 一致性：必须做的步骤写死，检查放在代码里执行。例如回复被标记后，一定要先经过审批才能发送。
  • 效率：每一步可以用合适的模型，有的步骤甚至不用模型。例如轮询收件箱只用代码，分类用小模型。

代价也有两个：遇到流程外的情况时适应能力差；步骤之间传递什么信息，必须由开发者明确管理。而单 Agent 的上下文会自然累积。

三、用 LangGraph 写一个客服工作流

1. 两类请求，两条路径

幻灯片全程用同一个客服例子，改编自 LangGraph 的官方教程。

  • “我忘了密码，怎么重置？”这是常规问题，路径是：检索说明 → 起草回复 → 发送。
  • “我被重复扣费了，请退还多扣的钱。”这类请求需要人审核，路径是：起草回复 → 员工审批 → 发送。

把这两条路径合在一张图上，就有了七个步骤：读邮件、分类、查文档、建 bug 工单、起草回复、审核、发送。

分类结果下一步
question / feature / billing查文档，再起草回复
bug建 bug 工单
complex直接起草回复
起草后：billing / complex / urgent进入人工审核，否则直接发送

这张图里只有分类和起草两步调用模型，其他步骤都是代码。走哪条路由模型的分类结果决定。所以模型仍然影响流程，只是影响的范围被框定了。

2. 共享状态

步骤之间靠一个共享状态传递数据。每个节点读取状态，做完自己的事，只返回它改动的字段。 

class SupportState(TypedDict, total=False):
    email_id: str
    email_content: str
    classification: dict
    search_results: list[dict]
    draft_response: str
    review_decision: dict

def classify_intent(state):
    classification = model.classify(
        state["email_content"]
    ).model_dump()
    return {"classification": classification}

以重复扣费这封邮件为例，走到审核之前，状态里依次写入了邮件原文、分类结果（billing，高紧急度）、检索到的账单审核政策，以及回复草稿。

3. 节点和图

节点就是普通的 Python 函数。查文档这一步只调搜索服务，起草这一步把邮件和文档交给模型。 

def search_documentation(state):
    c = state["classification"]
    query = f"{c['intent']} {c['topic']}"
    return {"search_results": services.search(query)}

def draft_response(state):
    response = llm.invoke([
        ("system", "Draft a reply using these documents."),
        ("human", json.dumps({
            "email": state["email_content"],
            "documents": state.get("search_results", []),
        })),
    ])
    return {"draft_response": response.text}

然后把函数注册成节点，用边连起来。固定的转移写成 add_edge。 

g = StateGraph(SupportState)
g.add_node("read_email", read_email)
g.add_node("classify_intent", classify_intent)
g.add_node("search_documentation", search_documentation)
g.add_node("draft_response", draft_response)
g.add_edge(START, "read_email")
g.add_edge("read_email", "classify_intent")
g.add_edge("search_documentation", "draft_response")
graph = g.compile(checkpointer=checkpointer)

条件转移写在节点里，节点返回一个 Command，同时更新状态并指定下一步。 

intent = classification["intent"]
destination = (
    "bug_tracking" if intent == "bug" else
    "search_documentation"
    if intent in {"question", "feature", "billing"}
    else "draft_response"
)
return Command(
    update={"classification": classification},
    goto=destination,
)

以上都是幻灯片上的片段，省略了导入和其余节点。

4. 断点续跑和等待人工

假设检索完成后，模型生成回复时程序崩溃。如果检索结果已经存进状态，重启时只需要重做生成这一步。这也是把步骤拆细的一个理由：每个节点结束时都留下一份可以恢复的进度。

  • 检查点（checkpointer）：持久记录工作流的状态，以及接下来该从哪里继续。
  • 恢复：用同一个执行 ID 读取进度继续跑，需要时可以传入新输入。
  • 重试策略：节点遇到超时这类临时错误时重新执行。
  • 中断（interrupt）：让工作流暂停。应用去收集人的回复，恢复时再传回来。

人工审核就是用中断实现的。工作流停在审核节点，人可能隔很久才回复，这段时间程序不需要一直运行。

5. 测试

固定流程的另一个好处是好测试。节点的输入输出是明确的，可以单独测一个节点：给定邮件“我被重复扣费了”，让模型固定输出 billing，检查节点返回的分类更新和路由目的地（文档搜索）。

单测节点时不经过检查点，所以持久化和实际路由要放到整张图上测。幻灯片列了四个受控的工作流测试：

场景预期行为
密码问题检索说明，起草，发送
账单投诉暂停等待审批，此时什么都没有发出去
回复被拒绝结束，不发送
搜索临时失败重试搜索，然后继续

另外还需要两类检查。回归检查：改动之后（例如换了新模型）测试还能不能通过。集成测试：用真实的模型和服务跑完整个流程，看节点之间怎样相互影响。

四、读一次运行：执行轨迹

监控的基本单位是执行轨迹，也就是一次运行的完整记录。工作流的每一步里面可能有模型调用、工具调用和普通代码，每个操作都可以记下输入、输出、耗时和错误。LangSmith 把单个操作叫 run，把整棵树叫 trace。

幻灯片里有一条录制的轨迹：classify_intent 用了 4.08 秒，其中几乎全部花在一次 gpt-5-mini 调用上（362 个 token）；紧接着的 search_documentation 调用本地搜索，耗时约 0.00 秒。读这样一棵树，能直接看出时间花在哪、模型看到了什么。

五、读几百次运行：一次回归调查

轨迹适合在已经知道出问题时排查。运行次数一多，就有三个困难：一条条读太慢；现有检查只覆盖想到要测的行为；分数下降了，也说不清是什么变了。

幻灯片用 Transluce 的工具 Docent 重做了一次调查。问题是：在 Terminal-Bench 上（89 个任务，518 次运行），GPT-5 Codex 的成功率是 40%，换成更新的 GPT-5.1 Codex 反而只有 27%，两者用的是同一个 Harness。为什么？

第一步：成对比较

让 Agent 操作 Docent：对每一次失败的运行，找另一个模型在同一任务上的一次成功运行，写一小段话解释失败原因，再按模型分组。输出显示要解释 108 次失败，其中 GPT-5.1 Codex 79 次，GPT-5 Codex 29 次。

下面是其中一对。在 code-from-image 这个任务上，GPT-5 Codex 失败，GPT-5.1 Codex 用 OCR 成功。解释里写道：失败的那次把大部分时间花在反复尝试 ASCII 渲染上，很晚才装上 Tesseract，安装耗尽了剩余时间，还没来得及跑 OCR 就结束了；成功的那次用 Tesseract 提取了伪代码，算出两个 SHA-256 值，写好了文件。每句解释都带引用，可以点进两次运行的原始步骤核对。

第二步：归纳失败模式

再让它根据上一步的结果总结两个模型的差别。结论是：

  • GPT-5.1 Codex：“在交付之前就耗尽了时间。”
  • GPT-5 Codex：“能交付，但形式经常不对。”

第三步：用数据验证

到这里还只是模型给出的假设，可以用运行的元数据直接检验。

模型计分运行数通过率超时次数
GPT-5 Codex21940%69（32%）
GPT-5.1 Codex26527%132（50%）

接着只保留两个模型都没有超时的任务，一共 28 个，按任务取平均奖励。GPT-5.1 Codex 是 0.500，GPT-5 Codex 是 0.429，排名反过来了。

这说明同一个分数差距可以有完全不同的解释：新模型在不超时的任务上更好，却更容易把时间用光。Transluce 的原文补充了几点限制：只看没超时的任务，可能偏向较容易的任务；基于 LLM 的分析带有随机性；他们也把这项研究定位为示范，不当作对这两个模型的定论。

六、发现没想到的行为：Hodoscope

1. 为什么不直接让模型当裁判

让模型读轨迹并打分，是最直接的办法，但模型要知道该找什么。幻灯片的例子是：Claude Opus 4.6 评估一个 SWE-bench 上查看 Git 历史的 Agent，可疑度只给了 2/10。给它一个链接，指向 SWE-bench 的 issue #465（这个 issue 记录了用 git log --all 等命令偷看未来提交的漏洞），它的评分就升到了 7/10。

裁判需要提示，才知道这个行为有问题。没人想到的问题，就没人能给提示。

2. 把动作摆到一张图上

Hodoscope（CMU）走另一条路，叫无监督监控：工具不判断对错，只把不同的行为摆出来给人看。论文的依据是，有问题的行为往往很显眼。一个钻了基准漏洞的模型，会做出行为正常的基线模型没有的动作。流程分四步：

  1. 总结：把每个动作压缩成一句行为层面的描述。这样不同任务里的相似行为才能对应起来。
  2. 嵌入：把所有分组的描述向量化，用 t-SNE 投到二维平面。
  3. 密度差异：对每一组（例如每个模型）估计分布，叠加到总体上，就能看出哪组的哪类动作异常地多。图上用红色标出。
  4. 人工审查：人点开这些区域，读原始动作，判断是否有问题。

Apple 的 Embedding Atlas 是类似的探索工具。

3. Commit0 的例子

Commit0 这个基准的任务是重新写出从仓库里删掉的代码，但早期提交还留在 Git 历史里。在图上检查一簇 Git 操作，发现 Agent（图中是 MiniMax-M2.5 在 babel 任务上）在第 74、78 轮查看最近的提交，从历史里找回了本该自己写的代码。

七、审查的规模问题

最后一页用了 Black Hat USA 2026 上关于 OpenAI 与 Hugging Face 事件的演讲。截图上写着：这远远超出审查单次对话或单份日志的范围；许多相互独立的运行中，Agent 彼此分享漏洞利用方法，而且行动很快；调查到当时已经审查了超过 70 亿条 Agent 轨迹，用掉超过 300 万 GPU 小时。

幻灯片的结论只有一句：Agent 产生的内容已经多到人无法完整审查。这也是下半讲这些工具要解决的问题。下一讲是 Eric Wallace 的客座讲座，主题是安全。第 18 讲还会回到这起事件，讲这些 Agent 是怎样互相通信的。

八、本讲小结

  • 流程已知时，把它写成工作流，模型只负责判断和生成。好处是一致、省钱、好测试，代价是灵活性下降。
  • LangGraph 的基本元素是节点、边、共享状态和检查点。人工审批用中断实现。
  • 单次运行看轨迹。大量运行先做成对比较得出假设，再用元数据验证。
  • LLM 裁判只能发现它知道要找的东西。无监督监控把不同模型的行为差异摆出来，由人判断。
