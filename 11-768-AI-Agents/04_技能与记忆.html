第四讲：技能与记忆

Agent 怎样把做过的事变成下次能用的东西，而不必每次从零开始

主讲：Daniel Fried · 2026 年 9 月 3 日
资料来源：课程幻灯片 · 课堂录像（本文依据录像字幕整理课堂口述内容） · 指定阅读：OpenHands 技能博客、SkillsBench、MemGPT、AWM、ASI、ReasoningBank

一、问题：很多任务有共同的结构

看两个网店任务。任务一是"把索尼耳机加入心愿单"：打开网店，找到搜索框，输入"sony headphones"，点搜索，打开索尼的结果，点"加入心愿单"。任务二是"查无线键盘的价格区间"：打开网店，找到搜索框，输入"wireless keyboards"，点搜索，读出结果里的价格，报告最低价到最高价。

两个任务的前半段完全相同，只有搜索词不一样，后半段才是各自特有的部分。如果 Agent 每次都从头摸索，就是在重复劳动。这一讲讨论怎样把这类重复出现的结构保存下来。课程提出三个问题：表示，共同结构应该存成文字还是代码；归纳，Agent 怎样从经验中自己总结出它；生命周期，一个技能什么时候该被取出、检查、修改或遗忘。

Daniel Fried 在开场时说明了这一讲的两个视角。一个视角是让 Agent 从自己的经验里总结出技能，这建立在早先对 Agent 记忆系统的研究上。另一个视角是把技能看作人写给 Agent 的指令，用来传达最佳做法和你对"这件事该怎么做"的了解。这两者可以互补：可以让 Agent 根据经历提出候选的最佳做法，由人修改后再交还给它；也可以反过来，人先写一份技能，再由 Agent 根据实际经验不断改进。

二、更新 Agent 的三个位置

位置优点缺点
上下文窗口（上一讲）完全忠实于发生过的事贵、噪声多，不会自己判断什么重要
外部产物（本讲）可以查看、编辑、检索，能迁移到别处需要归纳、挑选和维护
模型权重（SFT 那一讲）推理更快，能大范围改变行为更新慢，不透明，绑定特定模型

本讲关心中间这一行：哪些经验值得变成一个外部产物。

Daniel 特别讲了外部产物的两个好处。第一，它能在不同模型之间通用：一段"如何在这个网站上搜索商品"的说明，换任何模型的 Agent 都能用；而改权重只对那一个模型有效。第二，人能看懂、能修改：Agent 提出一段做法，人检查后改掉不对的地方，人和系统之间有了一个交流的接口。即使上下文已经有一百万 token，Agent 连续做很多任务时仍然会超出，所以跨任务的经验必须存在上下文之外，比如一个数据库，或者一个 Agent 可以访问的文件系统。

他在课上做了一个调查：大部分学生都在编程 Agent 里用过技能，其中约一半自己写过，也有很多人让 Agent 替自己写过。有学生分享了失败经验：模型写技能时写得太多，把用户的意图过度推断了，另一个模型拿到后一字不差地执行，做了远超预期的事。也有学生分享了成功经验：处理生产环境的故障时，给 Agent 三四个过去的工单，让它"看看以前大家是怎么处理这类问题的，给自己写一个技能，让其他 Agent 也能照着做"，效果很好。Daniel 说他发现模型通常不太擅长揣摩另一个人或另一个 Agent 读到说明时会怎么理解，但只要在提示里明确要求它这样想，就会好很多。

经验有三种粒度。一是完整片段（episode）：一次任务的全部观测和动作。如果以后会再用到完全相同的商品、价格或操作顺序，就值得保存。二是事实（fact）：比如"这家店只在商品详情页显示价格"。如果这个事实以后还会用到，或者可以被更新，就值得保存。三是技能（skill）：比如"填搜索框、点搜索、打开一个结果"。如果以后的任务会重复同样的模式，就值得保存。

课程区分了记忆和技能。记忆是从 Agent 自己的交互中保存下来的内容，比如之前买过的某件商品。技能是关于"怎么做"的可复用知识，可以是代码、文字或两者都有，比如一个人写好的发布检查清单。两者有交叉：Agent 从自己成功的搜索中归纳出来的技能，既是技能，也来自它自己的经验。

技能有两种来源。作为指令的技能由人或组织编写，来自现有的专业知识、规章和文档，优点是意图和来历清楚，负担是专家要花时间编写和维护。作为学习成果的技能由 Agent 从自己的经历和结果中总结，优点是能处理那些必须靠探索才能发现的做法，负担是要判断结果好坏、验证和整理。

关于"事实"这一类记忆，Daniel 举了一个大家都见过的例子：早期的记忆系统主要就是保存事实，比如用户在对话里提到自己多大、住在哪里，助手记下来，之后的对话里用上。ChatGPT 和 Claude 的记忆功能基本就是这样做的，你可以在设置里看到它记了你哪些信息，那是一段由模型从你过去的对话中总结出来的文字。这在形式上有点像上下文压缩：由 LLM 生成，存在外部。

三、人写的技能

1. 什么是技能

设想你在每次代码评审对话里都要打同一段话："请检查这段 Python 代码：用 Black 格式化，行宽 88；用 Ruff 按我们的自定义规则检查；所有公开 API 都要有类型标注；用 Google 风格的文档字符串；所有新函数都要有 Pytest 测试。"当你需要反复按固定规范做一件事时（加测试、评审 PR、升级依赖），就适合把它写成技能。技能的实现是一组文件：文档、脚本和资源，提供指导和自动化。

2. 技能包的结构

以 OpenHands 的文章 How to Create Effective Agent Skills（Michelini 与 Neubig，2026）为例，一个技能是一个文件夹： 

python-review/
├── SKILL.md       # 必需：指令和元数据
├── scripts/       # 可选：可执行代码
├── references/    # 可选：参考文档
└── assets/        # 可选：模板和资源

SKILL.md 开头是 YAML 格式的元数据，写明名称、什么时候该用这个技能、触发关键词；后面是 Markdown 正文，写具体步骤。

3. 渐进式披露

如果把所有技能的全部内容都塞进上下文，上下文很快就会爆掉。所以技能按三层加载，这个设计叫渐进式披露（progressive disclosure）：

层级内容何时进入上下文
1SKILL.md 的元数据（名称和描述）始终加载
2SKILL.md 的正文Agent 触发这个技能时
3附带的文件（文本、脚本、数据）Agent 去读这些文件时

以开源项目 Hermes Agent 为例，系统提示里有一个技能索引，只列出名称和描述，并要求模型"回复前先扫一遍技能列表，只要有一个相关，就必须用 skill_view(name) 加载并照做"。这个索引在 Hermes 里大约 3K token。模型调用 skill_view('python-review') 后，技能正文作为工具结果进入上下文。接着模型在终端运行 python scripts/run_checks.py src/，进入上下文的只是脚本的输出（Black 和 Ruff 的检查结果），脚本代码本身不会进入。只有模型需要时，才会再调用 skill_view 读取 references/docstring-style.md 这样的参考文档。第一次作业里对应的函数叫 invoke_skill。

课堂上学生问了好几个实际问题。

  • 技能很多时，光是元数据就会不会影响表现？会。Daniel 说 Hermes Agent 里所有技能描述加起来大约三千 token，后面会看到论文证据：加入无关的技能会让表现下降，因为上下文变长，模型也容易被无关内容干扰。所以技能数量要控制，按需加载。一般不会多到上千个。
  • 技能的触发有多灵敏？触发就是模型发出的一次工具调用，调不调完全取决于模型，也取决于你写的描述，所以需要评估。
  • SKILL.md 这个名字是固定的吗？是。这个标准叫 Agent Skills，模型和 Agent 框架都按它训练和加载。其他格式也可以，只要在 SKILL.md 里说清楚，因为这些都是给语言模型看的指令。
  • 为什么用 Markdown？Daniel 认为这是机器可读和人可读之间的平衡：它是线性的，可以放超链接，可以嵌图片。不足是很难表达动态的内容，比如想演示数据的几种可视化方式，也许一个交互式的 JavaScript 页面更合适，这时可以把它作为代码文件放在技能里，在 Markdown 里引用。Graham 补充说，研究文献里技能大致分两类，文字技能放在 Markdown 里，程序技能放在脚本里，这个格式其实覆盖面很广。
  • 如果一家大银行在 AWS 上有海量资源，不可能为每个组件都准备一个工具，有没有办法不把所有东西都放进上下文？Daniel 说后面的研究论文里就有这样的做法：用文本向量从大量技能中检索，或者按领域加载，比如在某个网站上工作时只加载这个网站的技能。生产系统很可能也这样做，但他手头没有具体资料。

4. 技能能带来多大提升

SkillsBench（arXiv 2602.12670）包含 8 个领域的 87 个真实工作任务，每个任务配有人工挑选的技能包。主实验比较"没有技能"和"有人工挑选的技能"，覆盖 18 种模型与 Harness 组合。结果：

  • 技能把平均通过率从 33.9% 提高到 50.5%。
  • 聚焦的技能提升更大：配 1 到 3 个技能的任务比配 4 个以上的提升更多；SKILL.md 更短的组也提升更多。
  • 技能在 87 个任务中有 13 个反而降低了表现，因为技能可能取代了模型原本更好的默认策略。

Daniel 补充了 SkillsBench 的构建方法：作者从网上收集了大约两百万个技能，另外请人独立地编写了约四百个看起来能从技能中受益的任务，再由标注者为每个任务从技能池里挑出适用的几个。他们还做了一道筛选：先用少数几个模型确认给了技能后表现确实提升，再看这个结论能否推广到更多的框架和模型。他对结果的解读是：需要技能少的任务提升更大，一部分原因是难度，另一部分可能是技能多了模型被分散了注意力；技能在不少任务上仍然有害，说明模型可能用错了技能，做出的结果和人要求的不一样。所以写完技能一定要检查它是否真的让输出变好。

论文摘要里还有几个数字：按配置看，提升幅度从 4.1 到 25.7 个百分点不等；最多包含三个模块的聚焦技能，效果好于更大或面面俱到的技能包；小模型配上技能，可以追平不带技能的大模型。

5. 技能从哪里来

有三种来源：Harness 自带的默认技能；人为自己的工作编写，放进代码仓库的 .agents/skills/ 目录，或从别的仓库、技能注册中心安装；Agent 自己写。Hermes 提供 skill_manage 工具，可以创建、修补或删除技能；OpenHands 有一个 /skill-creator 命令，能根据 Agent 刚完成的工作流起草技能。两种情况下，人都可以在发布前审核。OpenHands 的建议是：不要从零开始写技能，而是在 Agent 刚完成一个你想重复的工作流后立即创建，然后测试几次。

Daniel 强调，创建技能时最好基于你已经做过的交互，而不是凭空设想。SkillsBench 里有一个结果：只给模型任务描述、让它自己先写技能再做任务，模型写得很差，表现反而下降。人来写会好一些，因为你知道自己想要怎么做，但即便如此，也最好基于实际做过的事，因为真正动手做的时候，才会暴露出一些你事先没意识到的要求。

6. 案例：维护一个代码评审技能

OpenHands 在自己的仓库里，对每个 PR 都运行一个类似 python-review 的评审技能，并形成一个维护闭环：记录每次运行、给每次运行打分、找出反复出现的失败、修补 SKILL.md。打分的方法是：PR 合并后，让一个模型作为裁判，统计 Agent 提的建议有多少被人类保留了。然后让模型读运行记录，找出反复出现的问题：大约 15% 的情况忽略了仓库自己的约定，大约 10% 的情况批准了带有严重缺陷的 PR。最后由同一个模型起草修改：只要发现严重问题就要求修改，发建议前先对照仓库检查一遍。

四、记忆：事实、教训和片段

1. 让 Agent 自己管理外部记忆

MemGPT（Packer 等，2023）的做法是：读写记忆都是 Agent 自己发出的函数调用。上下文窗口有限，放不下的内容存到外部，需要时由 Agent 主动检索回来。

Daniel 介绍说，MemGPT 是 2023 年的论文，是最早提出在上下文窗口之外管理记忆的工作之一，思路来自计算机系统里的存储层次：快而小的一层是上下文窗口，大而慢的一层是外部存储。当时的上下文窗口只有八千 token 左右，这个设计显得非常必要；现在窗口大了，但要存的东西也多了，对 Agent 来说依然很有必要。它的结构分几部分：不会被改动的系统指令；一块工作上下文，内容从外部记忆里取来，也会写回外部记忆，读写都由模型通过工具调用控制；另外单独保存原始的消息记录。比如用户提到 Six Flags（一家游乐园），模型就发出一次工具调用，在存储里搜索过去提到 Six Flags 的内容，把结果放进工作上下文，再据此回答。

2. 处理记忆冲突

新信息进来时，可能和已有记忆矛盾。Mem0（Chhikara 等，2025）为每条新信息选择四种操作之一：新增（ADD），还没有类似的记忆；更新（UPDATE），新消息改变了某条已有记忆；删除（DELETE），新消息否定了某条已有记忆；不操作（NOOP），已经存过或者无关。

Daniel 用换工作举例：你说过"我在 X 公司工作"，后来换了工作，系统应该用最新的信息；如果你说"我被裁员了"，系统可能应该直接删除那条记忆，而不是修改它。Mem0 的流程是：每来一条消息，用语言模型从中提取出可能要存或要改的事实；用向量检索从数据库里取出最相似的几条已有记忆；再让语言模型逐条判断该做四种操作中的哪一种。

他问学生：第三讲里有没有哪个方法也是为了能更新或删除记忆？学生想到了哈希。Daniel 说对，更具体地说是 DeltaNet：线性注意力只能往记忆里不断累加，而 Delta 规则会先取出某个查询当前存着的值，再把它改掉，这提高了效果。Mem0 可以看作它在文字层面的对应物，只是存的不是向量而是文字形式的事实。他还提到，第三种更新方式，也就是改模型权重，同样需要"忘记"的能力，尤其是存在相互冲突的知识时，"遗忘学习"（unlearning）就是这方面正在发展的方法。

3. 记住对失败轨迹的反思

Reflexion（Shinn 等，NeurIPS 2023）的循环是：尝试、由评估器判断结果、生成一段反思、带着反思重试同一个任务。课上的例子：问题是"1776 年 10 月 28 日在纽约 White Plains 附近打的一系列战役叫什么"。第一次回答"White Plains 战役"，错了。模型生成的反思是："问题问的是一系列战役，而我只给出了一场战役的名字……我会提供更多背景，比如战役所属的战役系列名称。"第二次回答"纽约和新泽西战役"，正确。

Daniel 认为 Reflexion 简单但有效，值得了解，如果你的项目希望 Agent 能从过去的经验中受益，它是一个很好的起点。反馈可以来自人，也可以来自另一个模型的判断。论文的结论是：以一段自然语言描述"哪里出错了"为条件，对第二次尝试帮助很大。这个想法可以推广：只要反馈写得足够通用，它除了能帮助重做同一个任务，也能帮助做相似的任务。

4. 用相似轨迹做示例

ExpeL（Zhao 等，AAAI 2024）以及 Agent S、Synapse、ICAL 等工作采用另一种思路：存下完整的轨迹，成功和失败的都存，有时在存储前改写和标注。轨迹池可以在训练阶段离线收集，也可以在 Agent 工作时逐步积累，或者事先由人写好。使用时，用文本向量找出和新任务最相似的几条轨迹，作为少样本示例放进提示。

Daniel 把这类方法概括为"Agent 版的 RAG"。有学生问轨迹具体指什么，他解释说：轨迹就是 Agent 从环境或用户那里收到的消息（观测）、它采取的动作（工具调用），可能还有它写的思维链，基本等于模型上下文窗口里的全部消息序列。另一位学生问怎样检索，他说通常是把新任务的文字描述用向量模型编码，和其他任务的描述比较，每个任务都关联着一条轨迹；也可以限定只在当前领域里检索。

五、让 Agent 自己归纳技能

1. 技能是任务中可复用的片段

回到开头的例子。"搜索商品"可以写成一个带参数的片段：把 {query} 输入搜索框并提交。"报告价格区间"可以复用这个片段，再加上几步：读出最低价和最高价，发给用户。这就引出一个问题：技能应该用文字表示还是用代码表示。

Daniel 先问学生：直接把 Agent 当时发出的那几个原始动作存下来，当作技能，有什么问题？学生答对了：页面元素的编号一变，技能就坏了。同一个页面，元素的编号方式可能变化；换一个搜索界面不同的网站，更是直接失效。第七讲会讲如何设计动作空间来缓解这个问题。

2. 相关的前人工作

从程序中归纳可复用函数，在 LLM 之前就有研究。Voyager 在 Minecraft 里归纳函数来完成越来越复杂的动作序列，每个新函数调用之前的函数。DreamCoder 归纳能压缩一批已解决程序的函数，之后搜索新程序时复用它们。Stitch 用快速的符号压缩找出能概括最多共同结构的函数。LAPS 用自然语言的任务描述引导归纳哪些函数、怎样搜索程序。LILO 让 LLM 写程序，用 Stitch 压缩成函数，再让 LLM 为每个函数命名和写文档。

Daniel 对其中两项做了展开。Voyager 用代码来控制 Minecraft 里的智能体，函数实现的是"合成某件物品""对付僵尸"这类子任务。子任务写成函数之后，函数可以互相调用，学会简单的函数后，就能把它们组合起来完成越来越复杂的任务。DreamCoder 来自程序归纳领域：先有一批用非常底层的函数构造出来的完整对象，在里面找反复出现的模式，把模式抽象成函数，反复进行，相当于不断压缩构造这些对象的程序。后续工作把大语言模型、Python 代码和自然语言描述结合了进来，其中的一些想法对今天用语言模型操作外部世界的 Agent 也适用。

3. 在线归纳的评估方式

评估任务一个接一个到来。Agent 成功完成一个任务后，从中归纳出技能存入技能库，后面的任务就能用上。评估指标是到目前为止所有任务的累计成功率。比如先完成"把索尼蓝牙耳机加入心愿单"，归纳出"搜索商品"和"加入心愿单"；之后遇到"查无线键盘的价格区间"时就能直接用。

Daniel 说这正对应了我们平时使用 Agent 的方式：让它连续做一系列任务，其中有些彼此相似，我们希望它在交互中学习，越做越好。评估要看的是：成功率是否一路上升，能不能在学会简单子任务的做法之后，解决越来越复杂的任务。

4. 技能的生命周期

课程把技能的一生分为三个阶段。学习：从一次经历出发，判断成败，归纳技能，决定是否收录进技能库。使用：从技能库中挑选或检索，执行，得到结果。维护：根据结果新增、修复或淘汰技能。

5. 用文字表示技能：Agent Workflow Memory

Agent Workflow Memory（AWM，Wang 等，ICLR 2025）的流程是：一次任务结束后，先让一个裁判判断最终状态是否正确，正确才继续；再用少样本提示让语言模型从动作序列中归纳出工作流，存入记忆。例子：任务是"告诉我店铺目前收到的评论里有多少条提到了 satisfied"，动作是点 Marketing、点 All Reviews、在 757 号输入框填 satisfied、点搜索、回复用户 2。归纳出的工作流是： 

Task: Search for reviews matching "{term}"
Actions:
# To find reviews for {term}, I will search for "{term}" in the reviews page
click("All reviews")
fill(757, "{term}")
click("Search")

AWM 的归纳提示大意是：给定一组网页导航任务，每个包含自然语言指令和一串动作，找出多个任务中重复出现的动作子集，提取成工作流；每个工作流应该是常用的子程序，不要生成相似或重叠的工作流，至少两步，非固定的部分（输入文字、按钮名）用有描述性的变量名代替。

这项工作是 CMU 的 Zhiruo Wang 主导的，Graham 和 Daniel 都参与了，她在课程后面还会做一次客座讲座。Daniel 强调了其中关键的一步：用裁判模型判断这条轨迹是否正确，只有判为正确，归纳出的工作流才写进记忆，因为记住错误的做法会在以后把模型带偏。使用时，工作流直接放进模型的上下文，形式上和 Agent Skills 标准很像，可以全部展示，也可以只展示文字描述，取决于技能数量和模型的上下文长度。

在一个地图工具的基准上，任务按固定顺序一个个到来。没有记忆的基线 Agent 准确率大约稳定在 10%；加上工作流记忆的 Agent 提升明显，两者差距逐渐拉开，而且后者最终能完成"找一家某地附近的酒店并显示步行路线"这类越来越复杂的任务，基线始终做不到。论文摘要给出的整体结果是：在 Mind2Web 和 WebArena 上，相对成功率分别提高 24.6% 和 51.1%，同时减少了完成任务所需的步数。

6. 文字技能和代码技能的对比

文字技能加示例的优点是灵活，它是一个提示，Agent 可以根据眼前的页面理解和调整。缺点是仍然要手动操作，Agent 还是得一步步发出每个底层动作，边抄边改。

代码技能是一个函数，比如： 

def search_product(search_box_id: str, query: str):
    """Search for a product using the search box."""
    click(search_box_id)
    fill(search_box_id, query)
    keyboard_press('Enter')

它可以直接作为工具调用。优点有三个：可测试，存储前先运行一下；可分层，技能可以调用技能；高效，一次调用代替多个模型步骤。缺点是死板，它严格照写的做，即使页面已经变了。代码技能的代表工作是 ASI（Agent Skill Induction，Wang 等，COLM 2025）。

Daniel 问学生代码技能的缺点，学生回答"非常死板"：调用这个工具就严格执行这三步，没有偏离的余地。他同意这是主要缺点，但代码也带来了很多好处：可以嵌套、分层；可以脱离整条轨迹，单独为这个函数写测试；还可以重构。

7. 归纳代码技能

ASI 的流程和 AWM 类似，但产出的是函数。同样的"统计提到 satisfied 的评论"任务，归纳出两个函数：open_marketing_reviews() 负责点 Marketing 和 All Reviews；search_reviews(search_box_id, search_button_id, search_term) 负责填词和点搜索。然后用这两个函数把原任务重写一遍：调用 open_marketing_reviews()，调用 search_reviews('757', '704', "satisfied")，回复用户 2。裁判除了判断结果是否正确，还要检查技能是否真的被用上，都通过才收录。

代码技能能被测试。SkillWeaver（Zheng 等，2025）的收录流程是：提出候选技能，在任务中练习使用，让奖励模型根据动作和截图判断是否成功，成功就收录，失败就修改后重试。代码检查也能发现问题，比如幻灯片的例子里，lint 工具警告参数 color 定义了但从没用过，修改后在函数里加上了按颜色筛选的代码。

课上对代码技能的验证讲得更细。ASI 里，裁判不再看原始轨迹，而是先执行用新函数改写后的那一版，再看最终结果。改写版做对了，就更有理由相信这些函数本身是对的，于是把它们作为工具加入工具库。SkillWeaver 的例子来自一个药品网站：Agent 写了一个 identify_pill 函数，参数有药片的品牌、颜色等，但第一版函数体里根本没用到颜色参数。lint 工具报出这个问题后，可以像 Reflexion 那样以这条反馈为条件改写函数，再执行、再存储；奖励模型的反馈也可以这样用。

9. 技能能迁移到别的网站吗

ASI 做了跨网站实验：在一个网站上归纳技能，到另一个网站上评估。问题很明显，比如 sort_listings 在原网站是点一个下拉菜单，而 Target 网站的排序是打开一个侧边栏，代码技能直接失效。

PolySkill（Yu 等，ICLR 2026）的解决思路借用了面向对象编程中的多态：定义一个抽象接口，组合型的技能只针对抽象方法写一次，每个网站只需要实现最底层的浏览器操作。

PolySkill 的具体做法是：Agent 第一次接触一个新网站时，先写一个抽象类，里面只有方法的桩，比如搜索商品、加入购物车、结账；再写一个针对这个网站（比如亚马逊）的具体实现。到了另一个网站，可以根据元数据，或者让语言模型自己判断"这个实现不适用了"，再写一个新的具体实现。Daniel 说这还有一个好处：可以有很多针对具体网站的技能，但同一时间只激活相关的那一部分。这就是把软件工程的最佳实践用在了 Agent 上。按论文摘要，它在见过的网站上把技能复用率提高到 1.7 倍，在 Mind2Web 上成功率最多提高 9.4%，在没见过的网站上最多提高 13.9%，步数减少超过 20%。

10. 三种表示的取舍

表示优点缺点
检索出的完整片段保留具体行为长，难以迁移
文字技能提供灵活指导不能提高效率
代码技能可执行、可组合、高效可能很脆弱

背后的问题是：多少行为留给模型临场决定，多少固定在产物里。

Daniel 指出，Agent Skills 标准允许文字和代码两种形式并存，怎样把它们结合得最好，还有很多可研究的地方。技能生命周期的各个环节都是开放的研究问题，适合作为课程项目。

六、技能的生命周期管理

1. 从失败中学习

ReasoningBank（Ouyang 等，ICLR 2026）的附录里有一个案例。任务是"给出索尼蓝牙耳机的完整名称，并告诉我在售型号的价格区间"。Agent 搜索"Bluetooth headphones Sony"，得到全店各部门共 5,578 个结果，每页 12 个，于是一页页往后翻，直到步数用完，什么也没回复给用户。从这次失败中归纳出三条策略：优化搜索词，模糊的查询把答案埋在了几千个不太相关的结果里，要先缩小查询再浏览；调整每页显示数量，每页 12 个意味着每点一次"下一页"都要花一步，覆盖却很少；使用筛选器，侧边栏的分类筛选可以不翻页就缩小列表。

失败对不同类型的记忆作用不同。归纳"策略"时（ReasoningBank），加入失败经验有明显帮助。存完整轨迹（Synapse）或工作流（AWM）时，失败经验帮助较小，因为一段"不该这样做"的示范很难直接拿来用。

Daniel 解释了这个失败的具体原因：这个网站的搜索把多个关键词当作"或"来处理，于是凡是和蓝牙、耳机、索尼沾边的商品全都出来了，五千多个结果，Agent 一页页翻，最后忘了自己要做什么。ReasoningBank 是 Google 的工作，框架和 AWM、ASI 类似，区别是它生成的是文字形式的策略反馈，既能从成功中总结，也能从失败中总结，而且写出来的东西就像人自己会写进技能里的内容。至于为什么失败经验对存轨迹和存工作流帮助不大，而对文字策略帮助很大，他的解释是：文字可以用一般性的语言说明"怎样避免失败"，而把失败的轨迹本身拿来当示例，模型很难从中学到什么。

2. 裁判的准确度有多重要

真实的裁判会出错。ReasoningBank 为了测量影响，换成模拟裁判：用真实标签，但按固定概率翻转，从完全正确一直到抛硬币。结果是表现确实依赖裁判准确度，但在很宽的准确度范围内，技能库仍然能带来提升。

3. 检索太多反而有害

ReasoningBank 发现，检索更多的经验放进提示，表现可能下降。SkillsBench 在人工挑选的技能上也发现了同样的现象。原因可能是有些经验不相关，也可能是模型能有效利用的内容有限。

Daniel 把原因拆成两种。一种是 Agent 做过的任务还不够多，记忆里本来就没有相关的内容，放得越多，无关的越多，这是这类方法的根本限制：只有做过的任务和要做的任务之间有相似性，才谈得上学习。另一种是模型本身的限制，上下文里东西多了就被带偏，这可以通过训练来改善，让模型学会不被无关上下文干扰。此外，也可以主动缩小记忆的规模，减轻模型挑选的负担。

4. 合并与淘汰

TroVE（Wang 等，ICML 2024）有一条简单的淘汰规则：如果一个函数被使用的次数少于 $\frac{1}{2}\log_{10}(n)$ 次（$n$ 是到目前为止见过的样本数），就删掉它。另一篇论文 Not All Skills Help 指出，对一类任务有帮助的技能可能会伤害另一类任务。

TroVE 的淘汰规则，Daniel 形容为一种类似缓存的做法：看每条记忆过去被用了多少次，用得少就删掉。这样上下文里要放的东西少了，效率提高；如果模型原本会被无关内容干扰，成功率也会提高。按论文摘要，TroVE 在数学、表格问答和图像推理的 11 个数据集上，用小 79% 到 98% 的工具箱得到了更简洁、更准确的解法。

Not All Skills Help 进一步量化了这个问题。作者用随机屏蔽的方法测量每个技能的因果贡献，发现技能库普遍存在"因果异质性"：同一个技能对某些类型的任务有帮助、对另一些有害，而这些相反的作用在总体上相互抵消，所以只看整体效果的方法根本发现不了。他们提出的 ASSAY 框架把"生成技能"和"筛选技能"分开：生成交给 LLM，因为这是创造性的工作；筛选则要靠实证，先在一个小的开发集上计算每个技能的因果贡献，离线重组技能库，并针对每个测试任务屏蔽预计有负面作用的技能。

5. 训练模型学会归纳技能

训练时有一个难题：任务一的奖励只说明任务一是否成功，说明不了"把部分解法存成技能"是否值得，这要到后面的任务复用时才知道。解决办法是把后续任务也放进同一个训练样本：SAGE（Wang 等，ACL 2026）在一次 rollout 里放两个相关任务；AgeMem（Yu 等，ACL 2026）用一条长轨迹。

SAGE 给任务一的奖励设计为：任务一本身的奖励 $r_1$，加上一项"两个任务都成功，并且任务二复用了任务一存下的技能"时才给的奖励。在 AppWorld 基准上用 Qwen2.5-32B 训练，场景完成率分别是：只看结果 55.4，要求两个任务都成功 56.6，要求技能被成功复用 60.7。

Daniel 说，前面这些方法都有点临时拼凑的味道：只是提示语言模型去预测"哪些东西以后可能有用"。很自然的问题是：能不能直接训练模型做这件事？这个方向才刚开始，SAGE 和 AgeMem 都是今年 ACL 的论文。整个过程很复杂，用到好几个模型，要存、要取、要用，而且不可微分，但强化学习不在乎这些，后面几讲会讲怎么做。他还提出一个延伸想法：可以再加一项奖励，鼓励技能库保持精简，起到正则化的作用，防止过拟合。这些都是可以探索的方向。

七、讨论：什么该保存，谁来决定

课程最后列出几组需要权衡的方向：保存精确的片段，还是泛化的技能；给灵活的指导，还是固定的执行；复用已有的，还是探索并替换；让记忆不断增长，还是更新、合并和删除。

决定人来做更有价值的情况Agent 来做更有价值的情况

八、指定阅读与参考资料

指定阅读

  • OpenHands 博客 How to Create Effective Agent Skills（2026 年 2 月）：出发点是软件工程里有大量重复性的苦差事，比如补测试、代码评审、升级过期的依赖库，而且这些事往往有固定的流程，比如组织规定的评审方式、测试覆盖率指标、必须通过的漏洞扫描。文章介绍了用技能让 Agent 遵守这些流程的做法，本讲的技能包结构、创建建议和代码评审技能的维护案例都来自这篇文章。
  • SkillsBench（2026）：第一个系统衡量技能是否真的有用的基准。87 个任务、8 个领域，每个任务配有挑选好的技能和确定性的验证器，在同一配置下对比"有技能"和"无技能"。主要结论见上文。
  • MemGPT（Packer 等，2023）：借鉴操作系统的分层内存，提出"虚拟上下文管理"，在快、慢两层存储之间搬运数据，并用中断来管理和用户之间的控制流。在两个受上下文长度严重限制的场景里做了评估：分析远超上下文长度的大文档，以及能跨会话记住用户的多轮对话。
  • Agent Workflow Memory（Wang 等，2024）：归纳常用的工作流，并有选择地提供给 Agent。既可以离线使用（事先从训练样本中归纳），也可以在线使用（边做测试任务边归纳）。在覆盖旅行、购物、社交媒体等两百多个领域、一千多个任务的 Mind2Web 和 WebArena 上做了实验。
  • Agent Skill Induction（Wang 等，2025）：主张程序是表示技能的有效方式，让 Agent 在和网页交互的过程中即时归纳、验证、使用程序形式的技能。论文还展示了在更大规模的网页活动中仍能保持高效和准确。
  • ReasoningBank（Ouyang 等，2025）：从 Agent 自己判断为成功或失败的经验中提炼可推广的推理策略，测试时检索相关记忆来指导行动，再把新学到的东西写回去。论文还提出"记忆感知的测试时扩展"（MaTTS）：给每个任务分配更多计算，让 Agent 产生更多样的经历，这些经历之间的对比能提炼出更好的记忆，更好的记忆又反过来让扩展更有效。

参考资料

  • Mem0（Chhikara 等，2025）：动态提取、合并和检索对话中的关键信息，还有一个用图结构表示记忆的增强版本。在 LOCOMO 基准上和六类方法做了比较，包括已有的记忆系统、不同设置的 RAG、把全部历史都放进上下文的方法等。
  • Reflexion（Shinn 等，2023）：不更新权重，而是用语言反馈来"强化"Agent：Agent 对任务反馈做口头反思，把反思存在情景记忆里，指导下一次尝试。反馈可以是标量，也可以是自由文字，可以来自外部，也可以由模型自己模拟。在 HumanEval 编程基准上达到 91% 的一次通过率。
  • ExpeL（Zhao 等，2023）：从一批训练任务中自主收集经验，用自然语言提取知识，推理时回忆提取出的见解和过去的经验来做决策，不需要更新参数。
  • Agent S（2024）：一个操作图形界面的 Agent 框架，提出"经验增强的分层规划"，在多个层次上结合外部知识搜索和内部经验检索。在 OSWorld 上成功率比基线高 9.37 个百分点。
  • Synapse（2023）：针对电脑操作 Agent 的三个问题：一个网页就可能占满上下文，所以先做状态抽象，过滤掉和任务无关的信息；以往的示例只是高层计划，表示不了完整轨迹，所以直接用完整轨迹当示例；以往依赖任务专属的示例，所以按相似度从记忆里检索示例。
  • ICAL（2024）：让视觉语言模型 Agent 通过自我反思和人类反馈，把不够好的轨迹改写成高质量的示例，标注因果关系、物体状态变化、时间上的子目标和与任务相关的视觉元素。示例库越大，抽象新示例需要的人类反馈和环境交互就越少。
  • Voyager（Wang 等，2023）：Minecraft 里的终身学习 Agent，由三部分组成：最大化探索的自动课程、不断增长的可执行代码技能库、结合环境反馈和执行错误的迭代提示。获得的独特物品数量是以往方法的 3.3 倍，解锁关键科技树节点最多快 15.3 倍。
  • DreamCoder（Ellis 等，2020）：通过写程序来解决问题，用"醒-睡"交替的算法，一边给语言添加新的符号抽象，一边训练神经网络指导程序搜索。它重新发现了函数式编程的基础、向量代数和经典物理中的一些定律。
  • Stitch（Bowers 等，2022）：自顶向下地合成库函数，捕捉一批程序里的共同结构。和 DreamCoder 的方法相比快三到四个数量级，内存少两个数量级，库的质量相当或更好。
  • LAPS（Wong 等，2021）：用自然语言标注来引导函数库的学习和程序搜索，即使测试时没有语言提示也有帮助。
  • LILO（Grand 等，2023）：结合 LLM 引导的程序合成和 Stitch 的符号压缩，再用自动文档（AutoDoc）为抽象出的函数起名、写说明。文档不只方便人读，也帮助合成器理解和使用这些函数。
  • SkillWeaver（Zheng 等，2025）：Agent 在新网站上自主发现技能、执行练习，把练习经验提炼成稳健的 API。在 WebArena 和真实网站上的相对成功率分别提高 31.8% 和 39.8%；强 Agent 合成的 API 还能提升弱 Agent 的表现。
  • PolySkill（Yu 等，2025）、TroVE（Wang 等，2024）、Not All Skills Help（2026）：见上文。
  • SAGE（Wang 等，ACL 2026）：题为 Reinforcement Learning for Self-Improving Agent with Skill Library，用强化学习训练带技能库的自我改进 Agent。
  • AgeMem（Yu 等，ACL 2026）：题为 Agentic Memory，学习统一管理长期记忆和短期记忆。
  • Hermes Agent 的 prompt_builder.py 和 skills_tool.py：本讲系统提示和技能工具例子的源代码。

九、小结

技能和记忆让 Agent 不必每次都从零开始。人写的技能通过渐进式披露控制上下文开销，在 SkillsBench 上把通过率从 33.9% 提到 50.5%，但也会在部分任务上帮倒忙。Agent 也可以从自己的经验中归纳技能：文字技能灵活，代码技能可测试、可组合、效率高，但更脆弱。技能库需要持续维护，包括从失败中总结策略、控制检索数量、淘汰不常用的技能。训练模型学会归纳技能时，奖励要能看到技能在后续任务中是否真的被复用。
