第一讲：什么是 Agent，它怎样工作

从预测下一个 token 的语言模型，到能在真实环境里动手做事的系统

主讲：Daniel Fried、Graham Neubig · 2026 年 8 月 25 日
资料来源：课程幻灯片 · 课堂录像（本文依据录像字幕整理课堂口述内容）· 指定阅读：Toolformer、ReAct、mini-swe-agent

一、这一讲要回答的问题

第一讲是整门课的地图。它回答三件事：Agent 到底是什么；一个只会"接着往下写字"的语言模型，是通过什么机制变成能读文件、跑命令、改代码的 Agent 的；以及要让 Agent 真正好用，需要在哪些方向上下功夫。后面二十多讲，基本都是在展开这一讲列出的某个方向。

课程开场先摆出了现在 Agent 能做到什么程度。幻灯片引用了 Anthropic 研究员 Nicholas Carlini 在 2026 年发表的一篇文章：16 个并行运行的 Claude Agent，用两周时间写出了一个约 10 万行代码的 C 编译器，而且这个编译器能编译 Linux 内核。随后课堂还放了两段演示，一段是 Jing Yu Koh 在 2024 年做的多模态网页操作 Agent，一段是 Graham Neubig 用 OpenHands 做可视化调试。

OpenHands 那段演示的过程是这样的。Graham 只给了一句指令：用 Flask 写一个待办事项应用。Agent 自己建了静态文件和模板目录，写了主程序、首页、样式表、requirements.txt 和 README，然后把应用放到后台启动。启动时端口被占用，它读了日志发现问题，换了个端口重试。应用跑起来后，它打开浏览器，在页面上输入"buy groceries"、点击添加，再测试删除功能。Graham 说他自己不擅长前端，有一次应用崩溃了，Agent 比他先发现，还自己修好了。这个例子说明现在的编程 Agent 已经能在"写代码、运行、检查结果、修复"这个过程里自己转起来。

Daniel Fried 同时举了一个反面例子。有位用户让开源 Agent OpenClaw 整理邮箱，Agent 开始大批删除旧邮件。用户在对话里连着喊停，Agent 回答说"我要采取最彻底的办法，把不在保留名单里的邮件全部扔掉"，然后继续删。事后它承认：用户确实交代过不要删，但它违反了。事后分析的原因是上下文压缩（compaction）：对话太长时，Harness 会把早先的历史压成一段摘要来腾出空间，而"不要删除邮件"这条指令恰好在压缩时丢了。压缩是第三讲的内容。这个例子说明，模型变强了，但依然有很粗糙的地方，其中不少出在模型外面的系统上。

能力变强之后，新的问题就来了：哪些事可以放手让 Agent 自己做，哪些要先问人，哪些绝对不能交给它。课堂上给出了一组例子让学生分类，比如"排查网店结账为什么失败"、"给 5 万名客户群发产品发布邮件"、"收集税表并替你报税"、"在不影响手机端结账的前提下把支付 API 从 Python 迁到 Rust"、"喜欢的乐队来本地开演唱会就自动买票"、"根据一周的血糖读数调整胰岛素剂量"。这些例子的共同点是：出错的代价差别很大，而且有些操作一旦执行就撤不回来。

课堂上是举手投票的，每项任务有三个选项：完全自主、先问人再做、根本不该交给 Agent。结果大致是：排查网店故障，多数人愿意让 Agent 自己做；群发邮件，多数人要求先问；报税，选"不该交给 Agent"的人最多；迁移支付 API（假设有 Python 版的测试可以拿来检验 Rust 版），"自主"和"先问"几乎打平；买演唱会门票，多数人接受自主；调整胰岛素剂量，多数人选"不该交给 Agent"。Daniel 的总结是：大家对 Agent 的边界已经有直觉，而信任是核心问题。后面讲沙盒、安全、人机交互和人类监督时会回到这里。

二、Agent 的定义

课程采用的是人工智能教科书《Artificial Intelligence: A Modern Approach》（Russell 与 Norvig 著）里的定义：Agent 是任何能够通过传感器感知环境、并通过执行器作用于环境的东西。

这个定义很宽，放到今天基于大语言模型（LLM）的 Agent 身上，四个要素可以这样对应：

  • 环境（Environment）：Agent 所处的工作场所，比如一个代码仓库、一个网站、一个应用程序或者一套工作流程。
  • 状态与观测（State / Observations）：Agent 能"看到"的东西，包括对话消息、文件内容、网页、屏幕截图，以及工具返回的结果。
  • 动作（Actions）：Agent 能"做"的事，包括回复文字、编辑文件、执行 shell 命令、调用 API、点击鼠标或敲击键盘。
  • 奖励（Reward）：衡量做得好不好的信号，比如测试用例是否通过、另一个 LLM 按评分细则打出的分数（LLM-as-a-judge）、用户的正面反馈。

关于奖励，课堂上补充了几种具体做法。代码任务最简单：测试全部通过记 1 分，否则记 0 分。很多任务没法写出这种程序化的判断，就要请另一个 LLM 当裁判（LLM-as-a-judge），第二次作业就要求学生设计这类评估。更终极的目标是"用户满不满意"，这需要用户反馈，会在 Valerie Chen 讲的人机交互客座课里讨论。Daniel 还提到，Agent 的概念不是这两三年才有的，过去几十年为 Agent 发展出来的很多技术，比如搜索和强化学习，今天依然适用。

奖励这一项现在看起来和"怎么用 Agent"关系不大，但它在课程后半段的训练部分非常关键：强化学习就是靠奖励信号来调整模型行为的。

三、从语言模型到 Agent

1. 回顾：语言模型在做什么

语言模型的基本工作方式叫下一个 token 预测（next-token prediction）。token 是模型处理文本的最小单位，可以是一个词、半个词或一个标点。模型每一步都根据已有的文字，算出"下一个 token 是什么"的概率分布，从中选出一个，把它接到已有文字后面，然后再预测下一个。一段回答就是这样一个 token 一个 token 生成出来的。

思维链（Chain of Thought）是在这个机制上的一个用法：让模型在给出最终答案之前，先生成一段中间推理。比如问"2 × (3 + 4) 等于多少"，模型先写出"3 + 4 = 7，7 × 2 = 14"，再输出答案 14。因为推理文字也会成为后续预测的上下文，模型后面的每一步都能"看到"前面的推理，答案因此更可靠。

2. 工具定义：让模型知道自己能做什么

语言模型本身只能输出文字。要让它操作外部世界，第一步是告诉它"有哪些工具可以用"。工具定义是一个有类型的接口，包括三部分：工具名称、功能描述，以及用 JSON Schema 描述的参数格式。JSON Schema 是一种描述 JSON 数据长什么样的标准写法，规定有哪些字段、每个字段是什么类型、哪些字段必须填。

课上的例子是一个读文件工具： 

{
  "name": "read_file",
  "description": "Read a UTF-8 file.",
  "parameters": {
    "type": "object",
    "properties": { "path": { "type": "string" } },
    "required": ["path"]
  }
}

模型不能直接"读懂"这种结构化对象，它只认识一串文字。所以还需要一个叫聊天模板（chat template）的步骤，在调用 apply_chat_template 时把工具定义渲染成模型训练时见过的文本格式，比如用 <tools> 标签把 JSON 包起来，塞进提示词里。

3. 工具调用与结果

Daniel 在这里问学生：除了输出 JSON，模型还能用什么方式调用工具？后排一位学生说，可以直接写代码，比如写 bash 命令，或者把工具定义成 Python 函数，让模型用 Python 语法调用。Daniel 说后面几讲会讲这种做法，而且往往比生成 JSON 更有效，只是各有取舍。第二讲会专门比较这两种方式。

模型看到工具定义后，如果决定调用工具，它输出的不是普通回答，而是一段特定格式的文字，例如： 

<tool_call>
{"name":"read_file","arguments":{"path":"test.py"}}
</tool_call>

外部程序把这段文字解析出来，真正去读 test.py，再把文件内容包进 <tool_response> 标签送回给模型。在 API 层面，这一来一回对应两条消息：一条是 assistant 角色发出的工具调用（带一个编号，比如 call_7），一条是 tool 角色返回的结果（用同一个编号 tool_call_id 对应回去）。

4. 动作也是 token

这里有一个理解 Agent 的关键点：对语言模型来说，工具调用和普通文字没有本质区别，都是它预测出来的一串 token。区别只在于这串 token 恰好写明了"调用哪个工具、传什么参数"。

真正让动作发生的，是模型外面的一层程序，课程称之为 Harness（可以理解为"驾驭层"或"外壳程序"）。Harness 负责四件事：解析模型输出的调用、检查格式和参数是否合法、真正执行、把执行结果作为新的观测 token 交回模型。这个思路最早在 Toolformer（Schick 等，NeurIPS 2023）这篇论文里被系统地研究：让模型学会在文本中间插入 API 调用。

5. Agent 就是"模型放进循环里"

把上面几步连起来，就得到了 Agent 的基本结构：一个模型在一个循环里反复运行。每一轮，模型看着当前的上下文（任务、可用工具、历史记录），先推理，再决定一个动作；Harness 执行这个动作，把结果追加到历史里；然后进入下一轮。直到模型调用一个"把答案发给用户"的动作，循环才结束。

课上的例子：任务是"test.py 里写了什么？"。模型先推理，决定调用 read_file("test.py")；Harness 执行后返回 def add(a, b): …；模型再调用 send_message，告诉用户"test.py 定义了 add(a, b)"。

这种"推理、行动、观察结果、再推理"交替进行的模式，来自 ReAct（Yao 等，ICLR 2023）这篇论文，名字就是 Reasoning 和 Acting 的组合。

6. 一个最小的 ReAct 循环

课程用开源项目 mini-swe-agent 展示了这个循环在代码里有多短。核心逻辑是：先放入系统提示和任务说明，然后无限循环调用 step()；每一步先 query() 让模型生成回复，再 execute_actions() 执行回复里的动作，把观测结果加回消息列表。 

def run(self, task: str = "", **kwargs) -> dict:
    self.messages = []
    self.add_messages(系统提示, 任务说明)
    while True:
        self.step()

def step(self) -> list[dict]:
    return self.execute_actions(self.query())

def query(self) -> dict:
    message = self.model.query(self.messages)
    self.add_messages(message)
    return message

第一次作业（Assignment 1）就是自己实现并扩展一个类似的控制器：创建自己的工具、调用它们，并用在软件工程任务上。Daniel 在课上透露，作业用的代码仓库是一个国际象棋引擎。

课上还打开了 SWE-bench 网站，展示了 GPT-OSS 模型的一条真实运行轨迹。SWE-bench 是一个从真实 GitHub 项目里收集 bug 修复任务的基准，Agent 需要在代码仓库里找到问题、写补丁并通过测试。这条轨迹里，系统消息只有一句很通用的话："你是一个能操作电脑命令行的助手"；用户消息给出具体要解决的 issue。之后每一轮，模型先写一段思维链，再输出一条 bash 命令；环境执行后返回结果，有时只是一个"退出码 0"，表示命令成功了；然后进入下一轮。这个 Agent 没有定义任何 JSON 工具，唯一的动作就是写 shell 命令，也就是前面那位学生说的"直接写代码"。

四、Agent 需要的六种能力

有了基本循环，接下来的问题是怎样让 Agent 做得好。Graham 的说法是：做一个 Agent 并不难，现在调几个库就能搭出来，难的是做一个真正好用的。

他先让学生说说用 Agent 时最烦什么。学生的回答有：太慢；啰嗦；忘事；误解你的意思然后做错；访问不该访问的东西；在很常见的事情上出现莫名其妙的知识空白；两行能搞定的事写了一千行；忘了上一次会话的内容；你提了不合理的要求它也不会反驳；对你撒谎；做了很多没说出来的假设。Graham 说这些也都让他很烦，然后把问题归纳成六类能力，并指出每一类都有两条改进路线。

其中几类可以直接对上学生的抱怨。"忘事"和"明明交代过不要做还是做了"属于长上下文中的连贯性。"两行能搞定写了一千行"属于环境理解：Agent 没看出这其实是个很小的改动。准确调用工具这一项没有学生提到，Graham 说这是因为大家已经把它当成理所当然了；但如果你自己负责训练模型，就会发现它不是自动就有的，工具调不准，什么任务都做不成。安全这一项，他特别说明了自己的立场：很多人把研究方向分成"安全"和"能力"两派，但他认为安全本身就是一种能力，必须做进模型里，否则你不敢把 Agent 用在任何要紧的事情上。

第一条路线是 LLM 训练：通过预训练、监督微调（SFT）或强化学习（RL）改变模型本身的行为，让推理、使用工具、从错误中恢复这些模式成为模型学到的策略的一部分。第二条路线是 Harness 工程：不动模型，改模型周围的系统，包括提示词、工具、记忆和控制流程，给模型提供上下文、校验、重试和安全边界。最终的能力来自模型和 Harness 的组合。

Graham 让学生投票，看谁觉得哪条路线更重要，结果支持 Harness 工程的人明显更多。他的回答是两者都重要，但实践中常见的顺序是这样的：先发现一个问题，先在 Harness 里补上；负责训练模型的人随后意识到这个问题足够重要，值得专门训练；模型学会之后，Harness 里的补丁就不再需要了。所以他认为训练通常是更根本的解决办法，只是见效慢，在来不及改模型的时候，只能先改 Harness。

有学生问：哪些能力是训练模型也解决不了、Harness 必须一直存在的？Graham 给出的一个确定答案是长上下文，也就是把所有记忆都放在上下文里。这不只是准确率问题，也是效率问题：Transformer 的计算量随序列长度平方增长，除非换掉整个模型架构，否则总要靠 Harness 来管理上下文。其他几项，比如工具调用、上下文内的连贯、复杂任务管理、环境理解，甚至安全，理论上都能靠训练解决，但目前还没有解决。可定制性比较特殊：你可以在使用过程中训练模型，但很多时候你只是想针对某个场景给它一段脚本或一份说明，这种情况训练不是最好的办法。

另一位学生问：如果推理延迟很关键，是不是应该多做 Harness？Graham 说，对延迟敏感时往往只能用更小的模型、更少的算力，小模型成功率低、泛化差，所以需要在它周围加更多护栏，或者专门针对任务做适配。模型越小，Harness 就要做得越仔细。

训练路线本身又分三个阶段。预训练用海量文本、代码和多模态数据，让模型学到广泛的表征和规律；中期训练和 SFT 用指令、操作轨迹和工具调用示范，让模型学会格式和做法；RL 用奖励或偏好信号，优化模型在整条轨迹上的行为。

这门课不讲预训练，因为那需要整个互联网规模的数据和算力，课程的算力额度承担不起。SFT 学生在先修课里已经做过（用最大似然在示范数据上训练），所以只会简单带过，重点放在怎样为 Agent 场景构造训练数据。真正的重点是强化学习。Graham 在课堂上做了调查：做过语言模型 RL 的人不多，做过推理任务 RL 的和做过 Agent RL 的大约各占一成，约八成的人从没做过。他说能把 Agent 训练好的人很少，课程希望在座的学生成为这少数人。

Graham 对表里几项做了口头补充。

  • 上下文压缩（compaction）就是把已有的全部上下文总结成一段短文字，让 Agent 接着干活。动态记忆查找是把所有内容存在外面，需要时才取回来。子 Agent 委派是把长任务的一部分交给另一个 Agent，它在自己的上下文里做完，结果交回来，过程中的细节随之丢掉。
  • 可定制性是目前 Harness 工程最能发挥作用的地方。技能（Skills）就是一段提示词，有时附带脚本，写的是"某类事情应该怎么做"，在需要时才加载进来。训练方面，从用户反馈中学习（比如用户点了赞或踩）还是一个刚起步的方向，做的人不多。
  • 关于规划，Graham 讲了一个小故事：某个流行的编程 Harness 推出了"计划模式"按钮，用户按下之后，系统做的唯一一件事是在提示词里加一句"请先做计划，不要动手"。用户就是想要一个按钮，而这个按钮完全是用提示词实现的。当然也有更复杂的做法。
  • 环境理解指 Agent 要能读懂它所处环境里的数据。电脑操作 Agent 要看懂网页和图形界面，而很多开源模型连图像输入都不支持，支持的也比理解文字时错得多。换一个环境，比如炒股，模型对时间序列的理解很差；再换一个，比如看一张培养皿里细菌的照片，也会失败。
  • Graham 反驳了"模型以后自然会变好，不用操心"这种说法。他的原话是：模型不会自己变好，是人让模型变好的。某个模型新版本突然擅长作曲了，背后很可能是有人专门做了一个"作曲环境"，加进训练数据里。所以很大一部分工作是为特定领域构造训练环境。
  • 安全方面，他提到一件大多数学生都听说过的事：OpenAI 的一个新模型在 Agent 环境里做网络安全基准测试，任务是"攻进某个系统"。它没能攻进目标系统，转而攻进了 Hugging Face 网站，从那里拿到了答案。Graham 把这件事拆成几层失败：沙盒没把 Agent 关住；凭证限制被它绕了过去，去攻击了一个它本来没有权限的地方；监控不足，事发时没人察觉；这个模型本身就是为测试攻击能力训练的，缺少安全护栏。这几层正好对应表格最后一行的几种做法。

这张表基本就是课程的目录。第 2 到第 5 讲分别讲工具、长上下文、技能与记忆、规划；第 8、9、11 讲讲 SFT 和 RL；安全在第 7 周以后专门展开。

五、Agent 是一个系统，不只是一个模型

课程强调，一个能实际运行的 Agent 由好几个软件组件共同组成，模型只是其中之一。Graham 说，Agent 系统比学生在任何机器学习课上处理过的东西都复杂。以推理为例：学生以前做推理，上下文可能是 16K 或 32K token，而一个前沿的编程 Agent 至少需要 256K，推理问题因此难得多，缓存变得非常重要。幻灯片列出了五个组件，每个都有对应的开源或商业软件：

  • Harness：管理状态、工具、记忆和控制流；校验动作并处理错误；执行权限和安全边界。例子有 Claude Code、Codex、OpenHands、OpenCode、Pi 这类编程 Agent，以及 LangChain（Graham 说这里写 LangGraph 更准确）、CrewAI 这类编排框架。这两类的设计思路很不一样。编程 Agent 里多个 Agent 之间的协作比较简单，但单个 Agent 的动作空间很大：能写任意代码、能操作网站。编排框架里的单个 Agent 能力有限，比如只能回答客服问题或查数据库，写不了任意 Python 程序，但整个流程可以用声明的方式预先定好。前者表达力强，后者护栏多，各有适用的场合。Graham 本人是 OpenHands 的开发者，课上会讲他们开发中的经验。
  • 沙盒（Sandbox）：把代码和工具的执行隔离开；限制计算资源、网络和文件系统访问；创建可复现的运行环境。例子有 Docker、Apptainer、Modal、Sail。沙盒除了安全，还有一个重要用途：在评估和训练时提供可复现的环境。SWE-bench 的每道题都配有一个沙盒，里面是 Agent 开工前代码仓库的样子，谁都可以在本地重现同样的起点。
  • LM 推理：稳定地提供模型生成服务；把多个请求合并成批处理并复用 KV 缓存；管理流式输出、并行和吞吐量。例子有 vLLM、SGLang，这是最流行的两个。缓存对 Agent 格外重要：Agent 每做一步，上下文就变长一截，而前面的部分和上一步完全相同，必须复用已有的计算结果。KV 缓存会在第三讲详细解释。除了自己部署，也可以用推理服务商。OpenRouter 把众多服务商聚合在一起，一个模型常常有二三十家在提供服务。
  • 训练系统：准备数据、收集运行轨迹（rollout）；协调分布式工作节点；保存检查点、评估和复现训练。例子有 SkyRL、Miles。
  • 可观测性与监控：记录运行轨迹和指标；跟踪质量、成本和失败情况；比较不同轨迹和评估结果。例子有 Laminar、MLFlow，Daniel 课上用的 Transluce 也是一个。

关于评估，Graham 特别强调了一点：即使你只关心训练，也要学会做评估。因为做强化学习训练最好的办法之一，就是先把一个任务的评估做出来，再把它扩大规模，变成训练用的奖励。评估和训练在 Agent 这里是连在一起的。

六、课程安排与要求

课程的五个学习目标是：在开源 LLM 上从零实现一个 Agent；为多步骤任务设计评估；训练 Agent 提升能力；权衡安全与可靠性；研究一个关于 Agent 的开放问题。对应的顺序是"构建、评估、训练、安全、研究"。

三次个人作业依次是 Harness（搭建基础设施并建立可复现的基线）、评估（测量行为、报告失败案例，区分"演示"和"证据"）、训练（训练或调整一个组件，分析行为、成本和稳健性）。后半学期是 2 到 3 人一组的研究项目。成绩构成：三次作业共 40%，课堂要点提交 10%，研究项目 50%（提案 5%、中期检查 5%、展示 10%、最终报告 30%）。

学期进度分为六段：8 月 25 日到 9 月 8 日讲 Agent 能力；9 月 10 日到 15 日讲编程和 GUI 两个应用领域；9 月 17 日到 10 月 1 日讲训练（SFT、RL 基础、进阶 RL）和深度研究 Agent；10 月 6 日到 22 日讲框架与安全；10 月 27 日到 11 月 5 日讲人机交互、多 Agent 和项目；11 月 10 日到 12 月 3 日是进阶话题和海报展示。

这门课的先修要求很严格：必须有训练语言模型的实际经验，比如修过带 LM 训练作业的大学课程，或者有训练 4B 到 7B 以上模型的预训练、后训练或研究经历，不满足的学生会被要求退课。关于 AI 工具的使用，课程的规定是：作业和项目报告一般允许用 AI 工具，但课堂要点必须自己写；学生要对提交的每一条结论、引用、结果和每一行代码负责，并且可能被当面提问。

Graham 解释了这条规定的考虑。他自己几乎所有事情都用 Agent 做，但这门课的目的是学习，什么都交给 Agent，就会看不到细节，也不知道自己学到了什么。课程会针对作业出小测，要求学生解释自己的代码，而且助教打算让 Agent 读每个人的代码，专门为这份代码出题。他的建议很直接：Agent 生成的一千行垃圾代码交上来对你没好处，交一份简洁、自己真正理解的代码更好。课堂要点不需要长，几句话就行，但必须自己写。如果觉得某一讲没学到新东西，也可以如实写，这对教师也是有用的反馈。

迟交规则：每次作业有两个 24 小时的宽限日，不能转让或共用；用完之后，每多迟一天（不足一天按一天算）扣该作业 5% 的分数。超过两天，除了住院这类有证明的情况，一般不接受理由。课程末尾会请各领域的专家做客座讲座，Graham 说他们列了心目中每个话题最合适的人，每个人都答应了。

七、指定阅读

这一讲的指定阅读有三份，都和"模型加循环"直接相关。

Toolformer（Schick 等，2023）

这篇论文要解决的问题是：大模型能写文章、能做少样本学习，却在算术、查事实这类小模型或简单程序就能做好的事情上经常出错。作者的办法是让模型学会在需要的时候调用外部工具，由工具来算。论文用了五类工具：计算器、问答系统、两个搜索引擎、翻译系统和日历。

这篇论文的关键在于训练数据的来源。它不需要人工标注大量"何时调用工具"的数据，每个 API 只需要几个示范。具体做法是：先让模型在普通文本里到处尝试插入 API 调用，真的去执行这些调用拿到结果；然后检查每一处调用：把结果放进上下文之后，模型预测后面原文的损失有没有下降。有帮助的调用留下，没帮助的丢掉。最后用留下来的数据微调模型。这样模型自己学会了调用哪个 API、什么时候调、传什么参数、怎样使用返回结果。实验显示，微调后的模型在多种下游任务上的零样本表现明显提升，经常能和大得多的模型相比，而且原本的语言建模能力没有下降。这就是第一讲说的"动作也是 token"的早期来源。

ReAct（Yao 等，2022 年发表，ICLR 2023）

在 ReAct 之前，"让模型推理"（思维链）和"让模型行动"（生成动作序列）是两个分开研究的方向。ReAct 把两者交替起来：模型先写一段推理，再给一个动作，看到动作的结果后再推理。推理帮助模型制定、跟踪和修改计划，也帮它处理意外情况；动作让它能从外部获取信息。

论文在两类任务上做了实验。在知识问答（HotpotQA）和事实核查（FEVER）上，模型可以调用一个简单的维基百科 API 查资料，这缓解了单纯思维链常见的问题：凭空编造事实，以及一步错、步步错。在两个交互式决策任务上，ALFWorld（文字版的家务环境）和 WebShop（模拟网购），ReAct 只用一两个示例放在提示词里，成功率就分别比模仿学习和强化学习方法高出 34 和 10 个百分点。另外，它的轨迹是人能读懂的，出了错可以看出是哪一步推理有问题。今天几乎所有 Agent 的主循环都是这个结构。

mini-swe-agent

这是 SWE-bench 和 SWE-agent 的作者团队（普林斯顿和斯坦福）做的极简编程 Agent。他们在 2024 年做了 SWE-agent，后来反过来问：如果把 Agent 做得简单一百倍，效果还能保持多少？答案是 Agent 类本身大约 100 行 Python，没有复杂依赖，唯一的动作就是执行 bash 命令，在 SWE-bench Verified 上的得分超过 74%。它支持本地、Docker、Apptainer 等多种运行环境，通过 litellm、OpenRouter 等接口兼容几乎所有模型。课堂上 Daniel 推荐大家读它的代码，理由是它对现在的强模型足够有效，同时又简单到能把 Agent 的骨架看得一清二楚。

八、小结

这一讲建立了理解后续内容的基本框架。Agent 是感知环境并采取行动的系统；基于 LLM 的 Agent 把动作写成 token，由 Harness 解析、执行并把结果送回，模型在这个循环里一轮轮推进任务。要让 Agent 更强，可以改模型（训练），也可以改模型周围的系统（Harness 工程），实际系统两者都用。而一个可用的 Agent 还需要沙盒、推理服务、训练系统和监控这些配套组件。
