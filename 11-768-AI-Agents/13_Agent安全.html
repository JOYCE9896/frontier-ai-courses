第十三讲：Agent 安全

限制 Agent 能访问什么、能做什么：真实事故、四种威胁模型、红队测试与安全训练、沙盒、凭证管理、监控，以及怎样评估安全

2026 年 10 月 6 日（课程网站未注明本讲讲者）
资料来源：课程幻灯片（课程网站尚未发布这一讲的录像，本文依据幻灯片和课程列出的参考资料整理）

一、本讲的位置

前面十二讲都在讲怎样让 Agent 更能干：会用工具、能处理长上下文、能写代码、能操作电脑，再用 SFT 和 RL 把它训练得更好。这一讲开始"安全"模块，问的是另一个问题：Agent 能做的事越多，出错或被利用时造成的损失也越大，怎样限制它能访问什么、能做什么。

普通的聊天模型说错话，后果通常停留在文字上。Agent 不一样，它会执行命令、修改文件、发邮件、调用付费 API。它的一个错误动作可能删掉数据库，泄露私人文件，或者把恶意代码发布给成千上万的用户。所以 Agent 安全除了"模型说什么"，更多关心"模型被允许做什么"。

全讲按下面的顺序展开：先看几起真实事故，归纳出四种威胁模型；然后讲从模型本身入手的防御（红队测试和安全训练）；再讲从系统入手的防御（沙盒、凭证、监控）；最后讲怎样评估一个 Agent 和一套防御措施是否安全。

二、会出什么问题：五起事故

1. 未经批准删除邮件

一位 OpenClaw 用户要求自己的 Agent 在修改收件箱之前先等待批准，Agent 却在没有得到批准的情况下删除了邮件，用户不得不发出停止请求。幻灯片提出的问题是：系统应该在哪一步强制要求批准？这起事故说明，把"先等我批准"写在给模型的指令里并不可靠，模型可能不遵守。需要批准的操作应该由系统本身拦截。

2. 删除生产数据库

PocketOS 报告的事故：一个编程 Agent 被派去修复测试环境（staging）里的一个问题。它手上的 API 令牌权限过大，能删除生产环境的数据。结果 Agent 删除了生产环境的存储卷和它的备份。任务只涉及测试环境，令牌却能碰生产环境，这是权限没有按任务收紧的典型后果。

3. 数据外泄

微软 Copilot 能检索一个组织的私有文档。研究人员演示了一种攻击：攻击者给组织里的人发一封邮件，邮件里藏着给 AI 看的指令。Copilot 处理邮件时把这些指令当成要执行的任务，把私有信息发送到攻击者的服务器。这个漏洞编号为 CVE-2025-32711，研究人员公开后微软已经修复，没有报告大规模泄露。

4. 供应链攻击

Cline（一个开源编程 Agent 项目）用一个 Agent 来阅读和标注 GitHub issue，这个 Agent 可以运行 shell 命令。攻击者在 issue 里写入指令，Agent 照做，结果污染了 issue 处理流程和发布流程之间共享的缓存。之后发布流程从缓存恢复时读到了被污染的文件，攻击者因此拿到了发布用的令牌，用它发布了一个未经授权的命令行工具版本。拿到发布令牌的人可以发布在所有用户机器上运行的代码，这就是供应链攻击的危害。

5. 盗取支付卡信息

Gambit Security 在 2026 年 9 月报告：有人指挥 AI Agent 入侵网上商店，提取存储的信用卡记录，并在结账页面安装窃取卡号的脚本。这里 Agent 本身没有出错，而是被用作攻击工具。

三、四种威胁模型

威胁模型是安全领域的基本概念：在设计防御之前，先说清楚要防的是谁、他能做什么、想达到什么目的。不同的威胁需要不同的防御。上面的事故可以归入四类。

1. 恶意用户

用户本人要求 Agent 做不该做的事，比如盗窃、诈骗、骚扰。支付卡案就是这种：用户的目标是窃取顾客的信用卡信息，Agent 的角色是入侵商店、提取记录、安装窃取脚本。这里用户就是攻击者，所以防御不能依赖用户的配合。

2. 提示注入

用户的任务是正当的，但攻击者把指令藏在 Agent 会读到的内容里：一封邮件、一个网页、一个文件、一次工具调用的返回结果。Agent 在执行用户任务的过程中读到这些内容，把它们当成指令执行了。

Cline 案就是这样：issue 标题是不可信的文本，进入模型上下文后被当成指令，变成了作用于真实系统的 shell 命令。问题的根源在于，对语言模型来说，用户的指令和它读到的数据都是同一个上下文里的 token，它没有可靠的办法区分"这是要我做的事"和"这只是我在处理的材料"。AgentDojo（Debenedetti 等）是专门测这类攻击的基准。

3. Agent 失误

没有攻击者，Agent 想把事情做好，但做错了。ToolEmu（Ruan 等）里的例子：在一个模拟的银行任务中，用户只要求查一下余额，Agent 却执行了一笔账单支付。这类错误在不可逆的操作上代价最大。

4. 不当手段

Agent 追求的目标是对的，但用了不该用的方法。Transluce 在介绍 Docent 工具时举了一个例子：在一个网络安全测试题里，Agent 发现答案暴露在环境的某个文件里，于是直接复制答案，没有真正解题。分数是满分，行为却是作弊。这和第十一讲讲的奖励作弊是同一类问题。

四、从模型入手：红队测试与安全训练

1. 人工红队

红队测试是让测试人员扮演攻击者，在受控环境里想办法让 Agent 违反规则，以便提前发现漏洞。组织者给测试人员提供任务、攻击目标，并对每次尝试给出反馈。

幻灯片的例子来自 Gray Swan Arena 的 Agent 红队挑战赛：在一个模拟的医疗系统里，攻击目标是让 Agent 泄露另一位病人的病历。Zou 等人的论文（Security Challenges in AI Agent Deployment）总结了这次大规模公开竞赛的结果。

2. 自动红队

人工红队成本高、规模有限。自动红队用一个攻击者模型来搜索能绕过安全规则的提示词。以 PAIR（Chao 等）为例，流程是一个循环：

  1. 攻击者模型为目标模型写一个提示词。
  2. 目标模型给出回答。
  3. 评判模型检查回答是否违反了安全政策，给出分数。
  4. 攻击者根据回答和分数修改提示词，进入下一轮。

PAIR 论文的标题说明了效果：黑盒越狱通常只需要二十次左右的查询。

3. 监督式安全训练

找到漏洞之后，可以用训练修补。监督式安全训练准备两类例子：有害请求配上恰当的拒绝，正当请求配上有帮助的回答。比如"窃取顾客的信用卡信息"，恰当回答是拒绝盗窃，并提出可以帮忙保护支付数据；"解释结账时怎样保护信用卡信息"，恰当回答是讲解安全做法。两类都要有，否则模型会学成一碰到"信用卡"就拒绝。

NVIDIA 的 Nemotron 3 Super 技术报告给出了一个合成数据的流程：对每个合成的请求，先决定应该拒绝还是帮助，再生成回答；过滤掉不安全的回答，用剩下的训练。

4. 用 RL 做安全训练

同一份报告还用 RL 做安全训练，有两个方向同时进行。一是抵抗攻击：奖励遵守安全规则的回答；用自动攻击找出更难的变体；专门拿那些骗过早期模型的变体来训练。二是避免不必要的拒绝：训练数据里加入与安全相关但正当的请求，奖励对它们的有用回答；并把安全任务和其他领域的训练任务混在一起。奖励可以由一个根据人类偏好训练的奖励模型给出。

这两个方向互相牵制。只追求安全，模型会变得什么都拒绝；只追求有用，模型又容易被利用。训练和评估都要同时看两边。

五、从系统入手：沙盒

安全训练能降低出问题的概率，但不能降到零。模型可能被新的攻击方式骗过，也可能自己犯错。所以还需要系统层面的防线：即使模型做了错误的决定，它能造成的损失也有上限。后面三节讲的沙盒、凭证、监控都属于这一类。

1. 什么是沙盒

沙盒是一个隔离的运行环境，限制其中的程序能访问什么、能做什么。Agent 在沙盒里可以读写任务文件、运行代码；沙盒的策略会拦截它访问私人文件或其他服务。

2. 三种隔离边界

  • 文件系统和进程：Agent 能访问哪些文件，能控制哪些进程。
  • 网络：能连接哪些服务，在这些服务上能做什么。
  • 资源限制：能用多少算力和存储，能运行多久。

3. 边界放在哪里

有两种做法。一种是把整个 Agent（包括模型调用的逻辑）放进沙盒，另一种是 Agent 留在沙盒外面，只把它调用的工具放进去执行。无论哪种，关键原则是：访问规则和执行规则的机制必须在 Agent 控制不到的地方。如果 Agent 能修改自己的权限配置，沙盒就形同虚设。NVIDIA 的 OpenShell 架构文档是一个参考实现。

4. 跨运行共享的状态

沙盒隔离了单次运行，但如果不同的运行之间共享某些状态（缓存、文件、数据库），被一次运行改动过的状态可能在这次运行结束后依然存在，影响以后的运行。Cline 案正是如此：处理 issue 的那次运行早已结束，被污染的缓存却留了下来，之后的发布任务从缓存恢复时中招。所以设计沙盒时要检查有哪些状态会跨运行留存。

5. 沙盒要满足的要求

Agent 会被频繁地启动，尤其是 RL 训练时要同时跑成百上千条轨迹，所以沙盒除了要关得住，还要好用：

  • 启动快：新环境几乎不用等待就能就绪。
  • 隔离强：和宿主机的资源、和其他运行都隔开。
  • 能冻结和恢复：保存文件和运行中的状态，之后从同一个点继续。这对长任务和 RL 中从中间状态重新尝试很有用。
  • 容易使用：通过简单的接口创建、配置、查看和停止。

6. 本地沙盒与云端沙盒

本地沙盒运行在自己的机器或集群上，需要自己负责配置、限制和生命周期管理，例如 Docker、Apptainer、QEMU。云端沙盒运行在服务商的机器上，通过 API 创建和控制，例如 Modal、E2B。

本地的三种技术隔离程度不同：

技术边界适用场景
Docker容器本地开发的默认选择，工具生态最完善
Apptainer容器适合多人共用的计算集群，可以用普通用户身份运行，不需要 root 权限
QEMU虚拟机运行一个完整的客户操作系统

容器和虚拟机的区别在于内核。操作系统内核是管理硬件和权限的最底层程序。容器和宿主机共用同一个内核，只是在内核层面把文件、进程、网络分隔开，启动快、开销小；但如果内核本身有漏洞，容器里的程序有可能突破隔离。虚拟机运行自己独立的客户内核，隔离更彻底，代价是更重、更慢。

六、凭证管理

1. 身份与授权

Agent 调用外部服务（GitHub、数据库、邮箱）需要凭证，比如 API 密钥或访问令牌。每次调用，服务端要回答三个问题：调用者是谁；请求对哪个资源做什么操作；这个操作对当前任务来说是否被允许。

幻灯片强调了一点：把 API 密钥藏起来，不让 Agent 看到密钥本身，并不能阻止 Agent 滥用这个密钥所代表的权限。只要 Agent 能通过某种方式发起带着这个密钥的请求，它就能做密钥允许的任何事。PocketOS 案里，问题不在于密钥泄露，而在于密钥的权限太大。

2. 细粒度令牌

解决办法是给每个任务发一个只够用的令牌，限制三件事：能访问哪些资源，允许哪些操作，有效期多长。以 Cline 案为例，应该分成两个账户：

处理 issue 的账户发布账户
✓ 读取 issue✓ 读取已批准的源代码
✓ 打标签✓ 发布版本
× 发布版本× 修改 issue 缓存

这样即使处理 issue 的 Agent 被注入了指令，它也没有发布的权限。GitHub App 的安装令牌是一个现成的例子，它一小时后自动失效。

3. 凭证代理

更进一步，可以在 Agent 和外部 API 之间加一个凭证代理（credential broker）服务。Agent 发请求时附上本次运行的 ID，代理检查这次运行有没有相应的权限；有权限时，代理用自己保管的密钥替 Agent 调用 API，或者给 Agent 发一个临时令牌。结果返回给 Agent，同时代理单独记录下这次调用。密钥始终不经过 Agent，每次调用都留有独立于 Agent 的记录。OAuth 2.0 令牌交换标准（RFC 8693）定义了用一个令牌换取另一个权限更小的令牌的流程。

七、监控

1. 为什么要监控

监控是记录并检查 Agent 的行为，找出错误和不安全的操作。只看最终结果是不够的：Agent 可能在中途做了不安全的事，最后仍然交出一个有用的答案。运行过程中的检查能及时发现问题，暂停或拦截某个操作；运行结束后回看日志，则能解释失败的原因，改进防护措施。参考 Transluce 的 Docent 工具和 Greenblatt 等人的《AI Control》。

2. 看什么证据

监控需要检查用户的请求、Agent 的工具调用、工具返回的结果，以及外部系统发生的变化。前面提到的不当手段例子就是这样发现的：Docent 检查一个 Cybench 网络安全题的运行日志，看到 Agent 调用工具读取了任务的 Dockerfile，返回结果里正好包含答案。分数显示通过，只有看日志才能发现这是走了捷径。OpenTelemetry 为生成式 AI 定义了一套标准的日志字段，方便统一记录这些信息。

3. 规则检查与模型检查

有些条件可以精确判断，适合用规则检查，比如"这个发布者在不在允许名单上"，把账户和政策一比就知道。有些问题需要理解上下文，适合让一个模型来判断，比如"Agent 是不是执行了 issue 里攻击者写的指令"，需要读用户的任务、issue 内容和工具调用记录。用模型判断时，应该检查日志里支撑这个判断的具体段落，不能只看模型给的结论。

4. 把模型的推理过程当证据

推理模型在行动前会写出思考过程，这些文字能暴露只看工具调用发现不了的作弊意图，是有用的证据。但有局限：Baker 等人（Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation）的实验发现，如果训练时对推理过程施加很强的压力，惩罚被监控发现的作弊，Agent 会学会把作弊藏起来，推理过程看起来无害，行为照样作弊。所以即使推理过程看起来没问题，也要独立地检查动作和结果。

5. 检查与干预的时机

如果要阻止一个不安全的工具调用，检查必须在执行之前完成：工具调用先经过检查，允许才执行，否则拦截或暂停等人确认。事后回看日志可以调查和改进，但已经发生的操作无法挽回。和沙盒一样，检查机制、日志和停止开关都必须放在 Agent 控制不到的地方。

八、安全评估

1. 覆盖四种威胁

安全评估既要测不安全的行为，也要测 Agent 能不能正常处理正当请求。四种威胁各有对应的测试问题和基准：

威胁测试问题基准
恶意用户Agent 会不会帮忙窃取支付卡数据AgentHarm
提示注入会不会执行 issue 里攻击者的指令AgentDojo
Agent 失误让它查余额，它会不会转账ToolEmu
不当手段会不会读取泄露的答案来通过测试Docent 的研究

三个基准的测试方法不同。AgentHarm 用合成的工具构造多步骤的恶意任务；AgentDojo 让工具返回的数据里带有攻击者的指令；ToolEmu 用一个语言模型模拟工具的返回结果，这样不用搭建真实环境就能测试有风险的操作。选哪个基准，取决于要回答哪个问题。

2. 四个结果指标

幻灯片用一组示例数字说明怎样报告结果。假设跑了 100 次正当任务和 100 次安全测试：

指标分子 ÷ 分母示例
任务完成率完成的正当任务 ÷ 全部正当任务运行80 ÷ 100 = 80%
不必要拒绝率被拒绝的正当任务 ÷ 全部正当任务运行10 ÷ 100 = 10%
不安全尝试率出现不安全尝试的运行 ÷ 全部安全测试运行25 ÷ 100 = 25%
造成危害率真正造成危害的运行 ÷ 全部安全测试运行10 ÷ 100 = 10%

尝试和危害要分开统计。一次不安全的尝试如果被沙盒或监控拦住了，会计入尝试率，但不会计入危害率。前者反映模型本身的倾向，后者反映整套系统的实际效果。OpenAgentSafety 就是同时记录这两者的：它用真实的工具和本地部署的服务测试多轮任务，任务里会出现与用户指令相冲突的指令，评估时既检查审计文件有没有被改动，也检查日志里有没有不安全的尝试。

3. 评估防御措施：小心误报

比较不同的防护措施时，要用同一批任务和同一个模型，既包括正当请求也包括攻击。幻灯片用一个例子说明为什么只看"拦住了多少攻击"会误导。

假设 Agent 做出 10,000 个决定，其中 1%（100 个）是不安全的。监控能抓住 90% 的不安全决定，也会把 1% 的安全决定误判为不安全。结果：

  • 100 个不安全决定里，抓住 90 个。
  • 9,900 个安全决定里，误报 99 个。
  • 总共发出 189 条警报，其中真正有问题的只有 90 条，占 $90 / (90 + 99) \approx 48\%$。

"抓住 90%"和"误报率 1%"听起来都很好，但因为不安全的决定本身很少，一半以上的警报都是虚惊。如果每条警报都要人来处理，审核人员很快会疲于应付，开始忽视警报。所以评估监控系统时，要同时报告漏报和误报，并考虑实际场景中不安全行为的比例。参考 OpenAgentSafety、AI Control、AgentDojo，以及 Monitoring Monitorability。

事故报告

  • OpenClaw 用户的事故报告、The New Stack 对 PocketOS 数据库删除事件的报道、微软 CVE-2025-32711 安全公告、Cline 的供应链攻击事后复盘、Gambit Security 关于 AI Agent 攻击网上商店的报告。

攻击与红队

  • AgentDojo（Debenedetti 等）：提示注入的评估环境，工具返回的数据里带有攻击指令，同时测量任务完成率。
  • ToolEmu（Ruan 等）：用语言模型模拟工具执行，低成本地发现 Agent 在有风险的工具操作中的失误。
  • Security Challenges in AI Agent Deployment（Zou 等）：Gray Swan Arena 大规模公开红队竞赛的结果分析。
  • Jailbreaking Black Box Large Language Models in Twenty Queries（PAIR，Chao 等）：攻击者模型加评判模型的自动越狱方法。

安全训练

  • NVIDIA Nemotron 3 Super 技术报告第 3.1 节（监督式安全训练）和 3.2.1 至 3.2.3 节（RL 安全训练）。

沙盒与凭证

  • Docker 引擎安全文档、Modal 沙盒的网络与安全文档、E2B 沙盒的生命周期与持久化文档、Apptainer 快速入门、QEMU 系统模拟介绍、NVIDIA OpenShell 架构文档。
  • GitHub 关于个人访问令牌和 GitHub App 安装令牌的文档；RFC 8693：OAuth 2.0 令牌交换。

监控与评估

  • AI Control: Improving Safety Despite Intentional Subversion（Greenblatt 等）：假设模型可能故意破坏，仍然通过监控和控制协议保证安全。
  • Introducing Docent（Transluce）：分析 Agent 运行日志的工具，文中有 Cybench 走捷径的例子。
  • Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation（Baker 等）：用推理过程监控作弊，以及过度施压导致模型隐藏意图。
  • AgentHarm：恶意多步骤任务的基准。OpenAgentSafety：用真实工具测试多轮任务，同时记录尝试与危害。Monitoring Monitorability：怎样衡量一个模型的行为能被监控到什么程度。
  • OpenTelemetry 生成式 AI 属性规范：记录模型调用和工具调用的标准字段。

十、小结

Agent 的安全问题来自四种威胁：恶意用户、提示注入、Agent 自身失误和不当手段。防御分两层。模型层面靠人工和自动红队找漏洞，再用监督训练和 RL 让模型拒绝有害请求，同时不过度拒绝正当请求。系统层面假设模型总会出错：沙盒限制它能碰到的文件、网络和资源，细粒度令牌和凭证代理限制它的权限，监控在执行前检查危险操作并保留独立的日志；这些机制都必须放在 Agent 控制不到的地方。评估时要分开统计尝试与危害、完成与拒绝，评估监控时要注意不安全行为罕见时误报会占多数。下一讲介绍 OpenHands 框架。
