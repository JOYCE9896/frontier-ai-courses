02 · 数据并行与 ZeRO

把模型复制到多块 GPU 上并行处理不同的数据，再把优化器状态、梯度和参数沿数据并行维度切开，省掉重复存放的显存

作者：Nouamane Tazi、Ferdinand Mom、Haojun Zhao、Phuc Nguyen、Mohamed Mekkouri、Leandro von Werra、Thomas Wolf（Hugging Face）· 2025 年 2 月发布 · 整理：Joyce（@JOYCE9896）
资料来源：The Ultra-Scale Playbook 中的 “Data Parallelism (and ZeRO)” 一章（本文依据原书英文网页整理，是中文转述和讲解，不是逐字翻译；图片引自原书，版权归原作者）

这一章讲什么

上一章停留在单块 GPU 上：显存里装着参数、梯度、优化器状态和激活值，靠激活重计算和梯度累积把一个大批次塞进有限的显存。这一章第一次用上多块 GPU。最直接的办法是数据并行（Data Parallelism，DP）：每块 GPU 放一份完整的模型，各自处理不同的数据，再把梯度平均起来。书里先讲怎么让 DP 的通信和计算重叠，再讲 DP 和梯度累积怎么一起决定全局批大小，然后用 benchmark 说明 DP 在几百块 GPU 以上开始掉速。

DP 还有一个问题：每块 GPU 都存着同样的参数、梯度和优化器状态，大模型连一份都放不下。后半章介绍 DeepSpeed ZeRO（Zero Redundancy Optimizer）的三个阶段，它们把这些重复存放的东西沿 DP 维度切分，代价是多一些通信。读完这一章，你能用 $gbs = mbs \times grad\_acc \times dp$ 配出一个数据并行训练方案，能写出 ZeRO-1/2/3 每块 GPU 的显存公式，也知道它们各自要多付多少通信。下一章的张量并行会处理 ZeRO 处理不了的激活显存。

01. 数据并行

原书小节：Data Parallelism

数据并行的做法是把模型复制到多块 GPU 上（每一份副本叫一个“模型实例” model instance），每块 GPU 拿不同的 micro-batch 同时做前向和反向。micro-batch 指一次前向/反向里单块 GPU 处理的那一小批样本。名字里的“数据”就来自这一点：并行的维度是数据。简单的训练示例里大多见过 DP，但书里会讲得深一些。

每块 GPU 的数据不同，算出来的梯度也不同。为了让各个模型实例保持一致，需要把所有实例的梯度求平均，用到的操作叫 all-reduce：每块 GPU 贡献一份张量，所有 GPU 最后都拿到这些张量的和（或平均）。这一步发生在反向传播期间、优化器更新之前。all-reduce 是本书遇到的第一个“分布式通信原语”（distributed communication primitive），负责 GPU 之间和节点之间的同步与通信。（不熟悉 broadcast、gather、all-reduce 这些通信模式的话，原书附录 A0 有一个速成讲解，见本笔记的 第 12 篇；TPU 语境下的集合通信见 How to Scale Your Model 第 3 章。）

朴素的 DP 实现会等反向全部结束、拿到所有梯度之后，再对所有 DP rank 发起一次 all-reduce。rank 指参与分布式训练的一个进程，通常对应一块 GPU。这种先算完再通信的顺序执行，原书用大写字母说是“A BIG NO-NO”，因为通信期间 GPU 只能空等，如上图。应该尽量让通信和计算重叠（overlap），同时进行。下面三个优化都在朝这个方向走。

第一个优化：梯度同步和反向传播重叠

朴素 DP 的主要缺点是：反向（计算）做完以后，还要等梯度同步（通信）做完才能更新参数。这段通信可以和计算重叠。看上图，某一层的梯度（粉色方块）在更早那些层（它左边的粉色方块）的梯度还没算出来时，就已经可以开始收集和求和了。比如最后一层的反向一做完（最右边那个方块），它的梯度就可以开始 all-reduce，同时反向计算继续往左、往前面的层推进。

在 PyTorch 里，可以给每个参数挂一个 all-reduce 的 hook 函数（hook 是在某个事件发生时自动被调用的回调）。某个参数的梯度一准备好，就触发它的 all-reduce，其他参数的梯度还在计算。这样大部分 all-reduce 都和梯度计算重叠了。挂 hook 的函数很简单： 

def register_backward_hook(self, hook):
    """
    Registers a backward hook for all parameters of the model that
    require gradients.
    """
    for p in self.module.parameters():
        if p.requires_grad is True:
            p.register_post_accumulate_grad_hook(hook)

计算和通信重叠以后，整个模型等待梯度同步的时间少了。梯度同步可以在同一个训练步里（至少部分地）和反向并行进行，DP 因此快了不少。原书给了一个带重叠的朴素 DP 完整实现：picotron 的 data_parallel.py 第 10–60 行，实现了一个给每个参数注册梯度 hook、梯度就绪即 all-reduce 的 DP 封装。

这是书里第一次出现“计算与通信重叠”。这项技术对扩展效率影响很大，后面的章节会反复用到它。

第二个优化：梯度分桶

GPU 上的操作在大张量上通常比在很多小张量上更高效，通信操作也一样。所以可以把梯度分组放进若干个“桶”（bucket），每个桶只发起一次 all-reduce，不再给每个梯度单独做 all-reduce。这叫梯度分桶（gradient bucketing）。

原书打了个比方：寄东西时，把物品装进几个大箱子寄出去，比寄很多小包裹效率高。每个桶一次 all-reduce，可以明显减少通信开销、加快通信。带分桶的实现见 picotron 的 data_parallel.py 第 62–171 行，实现了按桶收集梯度、桶满后发起一次 all-reduce 的 DP 版本。

第三个优化：和梯度累积配合

上一章讲过，梯度累积（gradient accumulation）是在调用 optimizer.step() 更新参数之前，先做多次前向和反向，把梯度加在一起。梯度累积和数据并行一起用时，要注意梯度同步的时机。

朴素的写法会在累积过程中每次反向之后都自动触发一次 all-reduce。这样不划算：只在最后一步做一次 reduce，效果完全一样，开销却小得多。PyTorch 里一般用 model.no_sync() 这个装饰器来解决：在不需要 reduce 的那些反向上关掉梯度同步。

原书的一条 Note：做通信操作时，张量在内存里必须是连续的，否则会多出冗余的内存拷贝。为了做到最优，通常会专门为通信预先分配一块连续的 buffer，大小和激活值或模型参数相当。这样通信更快，但也会推高训练时的峰值显存。

（DP 的通信量和它在 TPU 上何时被通信卡住的推导，见 How to Scale Your Model 第 5 章。）

02. 重新看全局批大小

原书小节：Revisiting global batch size

加上数据并行和梯度累积以后，批大小的公式更新为：

$$bs = gbs = mbs \times grad\_acc \times dp$$

其中 $mbs$ 是 micro-batch size，即单块 GPU 一次前向处理的样本数；$grad\_acc$ 是梯度累积的步数；$dp$ 是数据并行用的实例数；$gbs$ 是全局批大小（global batch size），即一次优化器更新总共用到的样本数。

给定目标全局批大小，可以拿梯度累积步数去换数据并行进程数，从而加快训练。实践中，大家倾向于尽量把 $dp$ 开大、把 $grad\_acc$ 压小，因为数据并行天然是并行的，梯度累积却是一步接一步顺序执行的。只有当 GPU 用完了、光靠扩大数据并行还达不到目标全局批大小时，才在数据并行之上再加梯度累积。（原书推荐的延伸阅读：siboehm.com 关于数据并行训练的文章。）

能把训练分到不同的样本上，就有了第一个并行维度，所以这叫 1D 并行。后面还会逐步讲另外四个维度。

03. 到目前为止的路线

原书小节：Our journey up to now

先简单总结一下怎样搭一个 1D 并行训练，也就是一份数据并行配置的草案：

  1. 先确定最佳的全局批大小（以 token 计），可以查文献，也可以做实验测模型的收敛情况。
  2. 再选训练用的序列长度，同样查文献或做实验。一般来说，对今天的评测基准，2k–8k token 都很稳。（书里不展开训练配方，但各团队通常会在训练末期加大序列长度，往数据里混入一些更长的样本，以达到现在常见的长上下文长度。）
  3. 现在知道了 $gbs$。在单块 GPU 上不断加大本地批大小 $mbs$，直到显存溢出（OOM），就得到最大的 $mbs$。
  4. 最后看有多少块 GPU 可用，定下目标 $dp$。$gbs$ 和 $dp$ 的比值（再除以 $mbs$）就给出还需要的梯度累积步数。

比如 DeepSeek 和 Llama 的模型在主要预训练阶段都用 4k token 的序列长度（原书旁注）。2k–8k 在预训练里好用，是因为网上更长的文档很少，详细分析见 Harm de Vries 的博客文章。

如果算出来的梯度累积比值小于 1，也就是 GPU 太多（原书说这是 GPU-rich 🤑 的情况），可以选择不用全部 GPU，或者试一个更大的 $gbs$，或者测试更小的 $mbs$ 能不能加快训练。选最后一种，就是把总吞吐放在单卡计算效率前面：故意用比显存允许的更小的 $mbs$，换取更快的训练。

看一个具体例子。假设要训练一个较新的模型，$gbs$ 是 4M token，序列长度 4k，那么批大小就是 1,024 个样本（取最接近的 2 的幂）。再假设单块 GPU 显存只放得下 $mbs=2$，有 128 块 GPU 可用。那么 $2 \times 128 = 256$，用 4 步梯度累积就能达到每个训练步 1,024 个样本、即 4M token 的目标。如果突然有了 512 块 GPU，保持 $mbs=2$、把梯度累积步数设为 1，就能达到同样的 $gbs$，训练也更快。

原书的 Note：到 512 块 GPU 以上的规模，取决于用的网络，通信操作会开始受环延迟（ring latency）限制。环延迟是信号沿着环形拓扑传一圈所需的时间。到了这一步，DP 的通信就没法完全被重叠掉了，计算效率和吞吐都会下降。这时应该开始考虑在其他维度上并行。

数据并行把梯度的 all-reduce 和反向计算重叠，省下了时间，但这个好处在大规模下会失效。GPU 加到几百上千块，它们之间的协调开销明显变大，对网络的要求也大到抵消了收益。结果是每多加一块 GPU，整个系统就更低效一点。benchmark 里能直接看到：

图里的数据（来自原书交互图）：DP=8 时每块 GPU 约 40,150 tokens/s；DP 翻倍到 16、32、64、128 时，吞吐依次下降 6.3%、6.0%、12.0%、15.0%，降到约 26,446 tokens/s；从 128 到 256 时一下掉了 40.6%，只剩约 15,700 tokens/s。每块 GPU 的显存在所有规模下都是 36.66 GB，不随 DP rank 增加而变。也就是说，过了某个界限，吞吐明显下滑，而单卡显存保持不变。

数据并行是书里第一个（也是最简单的）把训练扩展到更多 GPU 的策略。它和梯度累积的效果一样，只是把各个 micro-batch 的前向和反向并行起来做，从而提高了吞吐。

细心的读者会发现，这里有个前提：至少一个样本的前向（$mbs=1$）要能放进 GPU 显存。这不总是成立。更大的模型即使开了激活重计算，也常常放不进单块 GPU。原书的一个小技巧：把参数量乘以 2，就能快速估出模型参数本身至少要多少显存，比如 70B 对应 140 GB（= 133 GiB）。

按原书交互图的数据：1B 模型的参数和梯度各约 2.3 GB，优化器状态约 9.2 GB，激活值从序列长度 1024 时的约 1.06 GB 涨到 16384 时的 17 GB；8B 模型参数和梯度各约 15 GB，优化器状态约 59.8 GB，激活值从 4.25 GB 涨到 68 GB；70B 模型参数和梯度各约 131.4 GB，优化器状态约 525.7 GB，激活值从 21.25 GB 涨到 340 GB。70B 模型光参数就超出一块 80 GB 的 H100。

此外，前面也看到 DP 扩展到一定程度后，通信开销开始成为限制。对这些更大的模型或更大的批，还有别的办法：要么把一部分张量挪到 CPU 上，要么把权重、梯度、优化器状态这些张量切开，分到多块 GPU 上。

切分有两大类做法：并行（张量并行、上下文并行、流水线并行）和分片（sharding，即 DeepSpeed ZeRO 或 PyTorch FSDP）。两者基本正交，可以组合使用。分片这一类和 DP 关系很近，所以先看 ZeRO。

04. 零冗余优化器（ZeRO）

原书小节：Zero Redundancy Optimizer (ZeRO)

这一节介绍 DeepSpeed ZeRO，一种为了减少 LLM 训练中显存冗余而设计的显存优化技术。

数据并行扩展训练很有效，但每个 DP rank 都原样复制一份优化器状态、梯度和参数，带来大量显存冗余。ZeRO 把优化器状态、梯度和参数沿数据并行维度分区（partition），每块 GPU 只存一部分，同时仍然允许用完整的参数做计算。这有时需要 DP rank 之间做更多通信，这些通信不一定都能被重叠掉，后面会看到。（书里只讲 ZeRO-1 到 ZeRO-3，足以看清这项技术怎样省显存、要权衡什么；更多 ZeRO 变体见 DeepSpeed 文档。）

ZeRO 分三个优化阶段：

  • ZeRO-1：切分优化器状态
  • ZeRO-2：切分优化器状态 + 梯度
  • ZeRO-3：切分优化器状态 + 梯度 + 参数

这里的“分区”指沿 DP 轴切分，因为 ZeRO 是一种数据并行方法。后面会看到也可以沿其他轴切。

你可能注意到，能切分的东西里没有激活值。每个 DP 副本处理的 micro-batch 不同，所以各 DP rank 上的激活值本来就不一样，没有重复，也就无从切分。

重新看显存占用

上一章讨论过标准训练中优化器状态、梯度和参数占的显存。把模型参数量记作 $\Psi$（上一章用的是 $N$，这里沿用 ZeRO 原论文（Rajbhandari 等，2020）的记号）。在混合精度训练（mixed precision，书的后面章节会细讲）中用 Adam 优化器，各项需要的显存是：

  • 模型参数（半精度，即 BF16/FP16）：$2\Psi$
  • 模型梯度（半精度，即 BF16/FP16）：$2\Psi$
  • FP32 的模型参数和优化器状态：$4\Psi + (4\Psi + 4\Psi)$
  • FP32 的模型梯度：$4\Psi$（可选，只有想用 FP32 累积梯度时才需要）

BF16 和 FP16 是 16 位浮点格式，每个数占 2 字节；FP32 每个数占 4 字节。Adam 的两份状态（一阶动量和二阶动量）各占 $4\Psi$，再加一份 FP32 的主参数 $4\Psi$，合起来是 $12\Psi$。不用 FP32 累积梯度时，总显存是 $2\Psi + 2\Psi + 12\Psi$；用的话是 $2\Psi + 6\Psi + 12\Psi$。为简单起见，下面先只看不用 FP32 梯度累积的情况。

ZeRO 的思路是把这些对象切分到各个 DP rank 上，每个节点只存一片，需要时再拼回来。这样显存占用就被数据并行度 $N_d$ 除掉：

图中 $\Psi$ 是参数量，$k$ 是优化器状态的显存倍数（刚才算过，Adam 的 $k=12$），$N_d$ 是 DP 度。把正文给出的各阶段公式整理成表：

方案切分了什么每块 GPU 显存
普通 DP不切分$2\Psi + 2\Psi + k\Psi$
ZeRO-1优化器状态$2\Psi + 2\Psi + \frac{k\Psi}{N_d}$
ZeRO-2优化器状态 + 梯度$2\Psi + \frac{2\Psi + k\Psi}{N_d}$
ZeRO-3优化器状态 + 梯度 + 参数$\frac{2\Psi + 2\Psi + k\Psi}{N_d}$

如果在 ZeRO-2 或 ZeRO-3 中使用 FP32 梯度累积，梯度那一项还要再加 $\frac{4\Psi}{N_d}$（原书旁注）。下面逐个看每个阶段怎么工作。

ZeRO-1：切分优化器状态

普通 DP 里，反向之后所有 rank 收集到同样的梯度，然后同时做一模一样的优化器更新。这是大量重复劳动。ZeRO-1 想同时去掉这份重复和它占的显存。

ZeRO-1 把优化器状态平均切成 $N_d$ 份，$N_d$ 是 DP 度。每个 DP rank 上的模型副本只维护 $\frac{1}{N_d}$ 的优化器状态，优化器更新时也只更新 $\frac{1}{N_d}$ 的 FP32 权重。

可是前向时每个副本都需要全部参数。所以优化器更新之后要加一次 all-gather，让每个副本都拿到完整的、更新过的权重。all-gather 是书里遇到的第二种集合通信原语：每块 GPU 各持有一片数据，操作结束后每块 GPU 都拿到所有片拼起来的完整数据。这就是前面图里 ZeRO-1 的显存公式 $2\Psi + 2\Psi + \frac{k\Psi}{N_d}$ 的来历。一个训练步的操作顺序如下：

  1. 每个副本用同一份完整的 BF16 参数做前向，但各副本的 micro-batch 不同。
  2. 每个副本做反向，得到一份完整的梯度，各副本的 micro-batch 不同。
  3. 对梯度做一次 reduce-scatter。reduce-scatter 先把各 GPU 的张量求和，再把结果切片，每块 GPU 只拿到其中属于自己的那一片。
  4. 每个副本用本地的优化器状态（只有 $\frac{1}{N_d}$）做一步优化器更新，得到 $\frac{1}{N_d}$ 的更新后 FP32 参数，再转换成完整 BF16 参数中的 $\frac{1}{N_d}$。
  5. 对 BF16 参数做一次 all-gather，把每个副本缺的那些片发给它。这是 ZeRO 新增的操作，普通 DP 里没有。

原书旁注：reduce-scatter 比 all-reduce 快一倍。这是第三种通信原语。

从实际通信看，和普通 DP 相比，ZeRO-1 把梯度的 all-reduce 换成了 reduce-scatter，并在优化器更新之后对所有参数加了一次 all-gather：

普通 DP 可以把梯度的 all-reduce 和反向计算重叠。ZeRO-1 还可以考虑怎样把新加的 BF16 参数 all-gather 也重叠掉，主要有两种策略：

  • 在优化器更新期间重叠：优化器更新完第一片参数，就立刻发起 all-gather，这样通信有可能和其余参数的更新同时进行。
  • 在前向期间重叠：把每一层参数的 all-gather 和前向计算重叠。

原书的 Note：可惜这些技术实现起来不容易，需要精巧地使用 hook 和分桶。实践中，可以直接用 PyTorch 原生的 ZeRO-3/FSDP 实现，并把 FSDPUnit 设为整个模型（后面会细讲）。

ZeRO-1 里优化器状态已经切开了，每个副本只更新 $\frac{1}{N_d}$ 的状态。那么其实没必要让每个 DP rank 都持有全部梯度，优化器更新只用到其中一部分。这就引出了 ZeRO-2。

ZeRO-2：再切分梯度

每个副本只需要和自己那片优化器状态对应的那片梯度，所以梯度也可以像优化器状态一样切分。这样反向时就不做 all-reduce，只做 reduce-scatter。每块 GPU 只在显存里保留需要的 $\frac{1}{N_d}$ 梯度，比 ZeRO-1 又省了一些显存。

用 FP32 梯度累积时，只需要保留 $\frac{1}{N_d}$ 的 FP32 梯度，用来累加 reduce-scatter 传来的 BF16 梯度；优化器更新时用这 $\frac{1}{N_d}$ 的 FP32 梯度去更新本地那片优化器状态（原书旁注）。

现在可以看出，切分梯度之后显存变成 $2\Psi + \frac{2\Psi+k\Psi}{N_d}$。随着 $N_d$ 增大，显存最多可以比基线少 8 倍：基线是 $2\Psi + 2\Psi + 12\Psi = 16\Psi$，$N_d$ 很大时只剩约 $2\Psi$。通信方面，过程和 ZeRO-1 一样，区别只是边通信边释放显存：两者都要对梯度做一次 reduce-scatter，对所有参数做一次 all-gather。所以在通信量上，ZeRO-2 也和普通 DP 训练相当。

原书旁注：除了实现更复杂，用 ZeRO-2 代替 ZeRO-1 并没有真正的额外开销，所以 ZeRO-2 通常是更好的选择。

ZeRO-3：再切分参数（FSDP）

第 3 阶段把前面对优化器状态和梯度的切分，扩展到模型参数本身。PyTorch 对这一阶段的原生实现叫 FSDP（Fully Sharded Data Parallelism，全分片数据并行）。书里统一叫它 ZeRO-3，看到 ZeRO-3 时可以理解成 FSDP。（TPU 语境下 FSDP 的通信分析见 How to Scale Your Model 第 5 章。）

通信量这样算：前向时按需对参数做 all-gather，付一份 $\Psi$ 的通信“税”；前向用完参数就丢掉了，所以反向时还要再 all-gather 一次，又是 $\Psi$；最后对梯度做和 ZeRO-2 一样的 reduce-scatter，也是 $\Psi$。合计 $3\Psi$，ZeRO-2 是 $2\Psi$。

$$\text{ZeRO-3 通信量} = \underbrace{\Psi}_{\text{前向 all-gather}} + \underbrace{\Psi}_{\text{反向 all-gather}} + \underbrace{\Psi}_{\text{梯度 reduce-scatter}} = 3\Psi$$

听起来通信开销很大，但实际影响不大，因为可以把下一层参数的通信和当前层的前向重叠，这叫预取（prefetching）。有了预取，在做第 n 层前向时 all-gather 第 n+1 层的权重；做第 n 层反向时 all-gather 第 n−1 层的权重。当然，只有 DP 不扩得太大时，这种重叠才有效。经验法则是 DP 不要超过 512。（书里的“DP”既指数据并行这种技术，也指数据并行用的 GPU 数，即 DP = DP size = DP degree。）

显存方面，公式到这里成了最终形式 $\frac{2\Psi +2\Psi+k\Psi}{N_d}$。也就是说，只要能继续增大 DP，至少模型相关的那部分显存理论上可以无限压低。但它对中间激活值没有帮助，激活值要靠前面讲过的激活检查点（activation checkpointing）和梯度累积来处理。

小结一下 DP 和 ZeRO 这一段：用 DP 加模型副本，可以大幅提高训练吞吐；用 ZeRO 把参数、梯度和优化器状态切分到各 DP 副本上，即使模型本来放不进一块 GPU 也能训练，代价是一点通信。（想多了解 FSDP1、FSDP2 和它们实现上的复杂之处，原书推荐 这篇博客。）

不过这里也有限制：DP 只在模型的一层能放进单块 GPU 时才行得通；ZeRO 只能切分参数、梯度和优化器状态，切不了激活显存。上一章讲过，激活显存随序列长度和批大小增长。可以限制这两者，但实践中谁也不想因为硬件限制只能用很短的序列训练。

ZeRO 的级别越高，模型相关的三项越小，激活值一列在四种方案下完全一样，序列长度到 16384 时激活值本身就有 68 GB。

要解决这个问题，就要看一个新的、正交的并行维度：张量并行（Tensor Parallelism，TP）。ZeRO-3 依赖大量的参数通信；TP 则把参数、梯度、优化器状态和激活值都切分到各设备上，并且 GPU 之间完全不需要传模型参数。原书最后问：这怎么可能？下一章就讲这件事。

这一章的要点

  • 数据并行：每块 GPU 一份完整模型，处理不同的 micro-batch，在反向期间、优化器更新之前用 all-reduce 平均梯度。
  • 不要先算完再通信。三个优化：给每个参数挂 hook，梯度一就绪就 all-reduce，和反向重叠；把梯度分桶，每桶一次 all-reduce；梯度累积时用 model.no_sync()，只在最后一次反向后同步。
  • 通信要求张量在内存中连续，常预分配连续 buffer，这会推高峰值显存。
  • 全局批大小：$gbs = mbs \times grad\_acc \times dp$。优先加大 $dp$，GPU 不够时再用梯度累积补足。
  • 配方：先定全局批大小（token）和序列长度（2k–8k 很稳，DeepSeek 和 Llama 主预训练用 4k），再找单卡最大 $mbs$，最后由可用 GPU 数定 $dp$ 和梯度累积步数。例子：4M token、4k 序列长度、1,024 个样本、$mbs=2$，128 块 GPU 时累积 4 步，512 块 GPU 时累积 1 步。
  • 512 块 GPU 以上，通信开始受环延迟限制，DP 通信无法完全重叠。benchmark 中 DP 从 128 扩到 256 时每卡吞吐下降 40.6%，单卡显存不变。
  • 估算参数显存：参数量乘以 2，例如 70B 约 140 GB（133 GiB）。
  • 混合精度 + Adam 的显存：BF16 参数 $2\Psi$、BF16 梯度 $2\Psi$、FP32 参数和优化器状态 $12\Psi$，可选 FP32 梯度 $4\Psi$。
  • ZeRO 显存：ZeRO-1 为 $2\Psi + 2\Psi + \frac{k\Psi}{N_d}$；ZeRO-2 为 $2\Psi + \frac{2\Psi+k\Psi}{N_d}$，最多比基线省 8 倍；ZeRO-3 为 $\frac{2\Psi+2\Psi+k\Psi}{N_d}$。ZeRO-2/3 用 FP32 梯度累积时梯度项再加 $\frac{4\Psi}{N_d}$。
  • 激活值在各 DP rank 上不重复，ZeRO 不能切分它。
  • ZeRO-1 把梯度 all-reduce 换成 reduce-scatter，并在优化器更新后对参数 all-gather；reduce-scatter 比 all-reduce 快一倍。
  • ZeRO-2 相对 ZeRO-1 除实现复杂度外没有额外开销，通常更好；通信量和普通 DP 相当（$2\Psi$）。
  • ZeRO-3（FSDP）每步比 ZeRO-2 多 $2\cdot \text{num\_layers} -1$ 次 all-gather，总通信量 $3\Psi$；靠预取和计算重叠，经验上 DP 不超过 512。
  • 限制：DP 要求单层放得进一块 GPU；ZeRO 管不了随序列长度和批大小增长的激活显存，这需要下一章的张量并行。
