06 · 专家并行

MoE 模型的每个专家是独立的 FFN，可以直接放到不同 GPU 上；这一章讲专家并行是什么，为什么总要和数据并行一起用

作者：Nouamane Tazi、Ferdinand Mom、Haojun Zhao、Phuc Nguyen、Mohamed Mekkouri、Leandro von Werra、Thomas Wolf（Hugging Face）· 2025 年 2 月发布 · 整理：Joyce（@JOYCE9896）
资料来源：The Ultra-Scale Playbook 中的 “Expert Parallelism” 一章（本文依据原书英文网页整理，是中文转述和讲解，不是逐字翻译；图片引自原书，版权归原作者）

这一章讲什么

这是全书讲的最后一种并行方式，篇幅很短。前面几章的数据并行、张量并行、上下文并行和流水线并行对任何 Transformer 都适用；专家并行只对混合专家模型（MoE）有意义。读完能说清楚两件事：专家并行切的是什么，以及它为什么比张量并行轻量。各种并行怎样组合，放在下一章 5D 并行总览 讲。

  1. MoE 是什么
  2. 专家并行：把专家放到不同 GPU 上
  3. 和数据并行一起用

01. MoE 是什么

原书小节：Expert Parallelism（开头部分）

作者建议，没接触过 MoE 的读者先读 Hugging Face 之前写的一篇短得多的 MoE 博客。

混合专家（Mixture of Experts，MoE）是一种模型结构：每一层有好几个并列的前馈模块（feedforward，FFN），每个叫一个专家（expert）；一个叫路由器（router）的小网络决定每个 token 送去哪个专家处理，不同 token 走不同的专家。作者说这种结构最近因为 GPT-4、Mixtral 和 DeepSeek-V3/R1 等模型变得很受关注。

（MoE 的参数量和 FLOPs 怎么算，TPU 语境下的推导见 How to Scale Your Model 第 4 章的 MoE 一节。）

02. 专家并行：把专家放到不同 GPU 上

原书小节：Expert Parallelism

MoE 层的设计让沿“专家”这个维度做并行很容易，这就叫专家并行（Expert Parallelism，EP）。因为各个专家的 FFN 完全互相独立，可以直接把每个专家的 FFN 放到不同的 worker（一张 GPU 或一个进程）上。

作者拿它和张量并行比：EP 轻量得多，因为它不需要把矩阵乘法拆开（张量并行要把一个权重矩阵切到多张卡上再合并结果，见 03 张量并行）。EP 只需要把每个 token 的隐藏状态（hidden states）发到它该去的那个专家所在的 GPU。

03. 和数据并行一起用

原书小节：Expert Parallelism

实践中 EP 一般和其他并行方式一起用，最常见的是数据并行（DP）。原因是 EP 只作用于 MoE 层，并不切分输入 token。上下文并行会沿序列长度切 token，EP 不会。如果只用 EP，那么所有非 MoE 的部分（例如 attention）在每张 GPU 上都在算同样的东西，属于重复计算。

04. 实践中的技巧

原书小节：Expert Parallelism

让 EP 跑得高效有一些技巧，而且这些技巧和模型设计绑在一起。原书举的例子是 DeepSeek-V3：它在路由器里加了一条约束，每个 token 最多只能发往 $M$ 个节点（DeepSeek-V3 里 $M=4$），这样 token 尽量留在少数节点内，减少跨节点通信的开销。

作者还说，专家并行其实早就有了（原书引用的是 GShard 论文），只是随着 MoE 架构流行，最近才重新受到关注。他们计划之后在 Picotron/Nanotron 里补一个更完整的 EP 示例。

这一章的要点

  • MoE 层把单个 FFN 换成多个并列的专家，由路由器把 token 分到不同专家。
  • 专家并行把不同专家放到不同 worker 上；不需要拆矩阵乘法，只需把 token 的隐藏状态路由到对应专家，比张量并行轻量。
  • EP 只切 MoE 层、不切 token，单独使用会让非 MoE 部分重复计算，所以通常和数据并行一起用。
  • DeepSeek-V3 限制每个 token 最多发往 $M=4$ 个节点，以控制通信开销。
