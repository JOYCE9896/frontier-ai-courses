01. A0：并行编程速成课

原书小节：A0: Parallel Programming Crash Course

把训练从 1 张 GPU 扩展到几百张，需要在所有机器之间通信和同步权重、梯度和数据。完成这件事的一组分布式模式叫集合操作（collective operations）。这一节依次讲 Broadcast、AllReduce、Scatter 等操作。

一般设定是：有若干独立的节点（node），可以是 CPU 核、GPU 或计算节点。每个节点做一些计算，然后要把结果或其中一部分发给其他节点，用于下一个计算步（$t+1$）。

可能要把一个节点的结果发给所有其他节点，也可能要把所有节点的中间结果加起来得到总结果。通常有一个地位特殊的节点起中心作用，叫 root，它是某些操作的目标或数据来源。（TPU 语境下四种集合通信的代价推导，见 How to Scale Your Model 第 3 章。）

Broadcast

常见情形：数据在节点 1 上，要分享给所有其他节点做计算。Broadcast（广播）就是干这个的：

PyTorch 原生提供集合操作。先用 dist.init_process_group 初始化一个进程组（process group），它设置通信后端（后面会讲 NCCL），确定有多少个 worker（也就是节点），给每个 worker 分配一个 rank（编号，可以用 dist.get_rank 取得），最后在 worker 之间建立连接。（原文这里把函数名拼成了 dist.initi_process_group，下面代码里是正确的写法。）

演示 dist.broadcast：在 rank=0 上建一个非零张量，其他 worker 上是全零张量，再用 dist.broadcast(tensor, src=0) 把 rank 0 的张量发给所有 rank：

import torch
import torch.distributed as dist

def init_process():
    dist.init_process_group(backend='nccl')
    torch.cuda.set_device(dist.get_rank())

def example_broadcast():
    if dist.get_rank() == 0:
        tensor = torch.tensor([1, 2, 3, 4, 5], dtype=torch.float32).cuda()
    else:
        tensor = torch.zeros(5, dtype=torch.float32).cuda()
    print(f"Before broadcast on rank {dist.get_rank()}: {tensor}")
    dist.broadcast(tensor, src=0)
    print(f"After broadcast on rank {dist.get_rank()}: {tensor}")

init_process()
example_broadcats()

Reduce 和 AllReduce

Reduce（归约）是分布式数据处理里最基础的模式之一：用一个函数 f()（例如求和或求平均）把各节点上的数据合并起来。Reduce 只把结果发给 root 节点；AllReduce 则把结果广播给所有节点：

并没有一个“凭空存在”的节点来做这件事。一般是每个节点做一部分计算，节点之间组织成环（ring）或树（tree）结构。例子：节点连成环，要对各节点上的数求和。第一个节点把自己的数发给邻居，邻居加上自己的数再转给下一个邻居，绕环一圈后第一个节点就拿到总和。

下面是一个求和的 Reduce，用 op=dist.ReduceOp.SUM 指定操作（支持的操作见 PyTorch 文档）：

def example_reduce():
    tensor = torch.tensor([dist.get_rank() + 1] * 5, dtype=torch.float32).cuda()
    print(f"Before reduce on rank {dist.get_rank()}: {tensor}")
    dist.reduce(tensor, dst=0, op=dist.ReduceOp.SUM)
    print(f"After reduce on rank {rank}: {tensor}")

init_process()
example_reduce()

Gather 和 AllGather

很多实际情况下，各节点各自做了复杂的计算，需要在所有节点间分享最终结果，这时用 Gather 和 AllGather。它们和 Broadcast 相似，都是不加修改地在节点间分发数据。区别在于 Broadcast 是把一个节点上的一份数据发给所有节点；Gather/AllGather 中每个节点各有一块自己的数据，Gather 把所有数据收集到一个节点上，AllGather 把所有数据收集到所有节点上：

Gather 需要准备一个容器存放收集来的张量，这个例子里是 gather_list：

def example_gather():
    tensor = torch.tensor([dist.get_rank() + 1] * 5, dtype=torch.float32).cuda()
    if dist.get_rank() == 0:
        gather_list = [
            torch.zeros(5, dtype=torch.float32).cuda()
            for _ in range(dist.get_world_size())
            ]
    else:
        gather_list = None
    print(f"Before gather on rank {dist.get_rank()}: {tensor}")
    dist.gather(tensor, gather_list, dst=0)
    if dist.get_rank() == 0:
        print(f"After gather on rank 0: {gather_list}")

init_process()
example_gather()

Scatter 和 ReduceScatter

Gather 的反向操作：数据全在一个节点上，要切开分给各节点，中间可能还要做些处理。这时用 Scatter；如果分发前要先对数据做一个操作，就用 ReduceScatter。

Scatter（分散）把一个节点上的数据切片，每个节点分到一片。它和 Broadcast 不同，Broadcast 给每个节点发一份完整副本，不切片；Scatter 在逻辑上是 Gather 的逆操作。

ReduceScatter 稍复杂一些。和 AllReduce 一样，它对所有节点的数据做一个操作；但 AllReduce 中每个节点拿到完整的输出张量，ReduceScatter 中每个节点只拿到输出张量的一片：

Scatter 的代码写法和 Gather 相反：要准备的是要分发出去的源数据列表（Gather 准备的是接收用的张量列表），还要指定 src：

def example_scatter():
    if dist.get_rank() == 0:
        scatter_list = [
            torch.tensor([i + 1] * 5, dtype=torch.float32).cuda()
            for i in range(dist.get_world_size())
            ]
        print(f"Rank 0: Tensor to scatter: {scatter_list}")
    else:
        scatter_list = None
    tensor = torch.zeros(5, dtype=torch.float32).cuda()
    print(f"Before scatter on rank {dist.get_rank()}: {tensor}")
    dist.scatter(tensor, scatter_list, src=0)
    print(f"After scatter on rank {dist.get_rank()}: {tensor}")

Ring AllReduce

Ring AllReduce 是 AllReduce 的一种为可扩展性优化的实现，它用 ReduceScatter 加 AllGather 实现。所有设备两两直接通信可能造成通信瓶颈；Ring AllReduce 把过程拆成两步：

  1. ReduceScatter
    • 每个设备把自己的数据（例如梯度）切成 N 块（N 是 GPU 数），把一块发给一侧的邻居，同时从另一侧的邻居收到一块。
    • 每收到一块，就把自己对应的那块加上去（归约）。
    • 绕环一直进行，直到每个设备都持有一块完全归约好的数据，即这一块在所有设备上的梯度之和。
  2. AllGather
    • 每个设备需要收集其他设备上归约好的块。
    • 每个设备把自己归约好的块发给邻居，同时从另一侧邻居收一块。
    • 设备不断转发收到的块，直到每个设备都有全部归约好的块，也就拿到了完整的梯度和。

第二张是 AllGather 步骤，结束时每张 GPU 都拿到 AllReduce 的完整结果：

通信量的计算：$N$ 张 GPU 中每一张在 ReduceScatter 和 AllGather 两步里各发送、接收 $N-1$ 次。每次传 $\frac{K}{N}$ 个值，$K$ 是要在各 GPU 间求和的数组的总元素数。所以每张 GPU 收发的总数据量是 $2 \times (N-1) \times \frac{K}{N}$。$N$ 很大时，约等于 $2 \times K$，这里 $K$ 是参数总数。

关于 AllReduce 要记住两点：

  • $N$ 很大时，AllReduce 的通信代价约为 $2 \times K$。
  • 一次 AllReduce 可以拆成一次 ReduceScatter 加一次 AllGather，这两个操作各自的通信代价是 AllReduce 的一半，约为 $K$。

这种实现即使在节点间带宽有限时也能把带宽用得很充分。

Barrier

Barrier（屏障）是一个用来同步所有节点的简单操作：所有节点都到达屏障之前，屏障不会解除；全部到齐后，节点才能继续往下算：

给每个节点设不同的 sleep 时间来模拟有快有慢的节点，看它们各花多久通过屏障：

def example_barrier():
    rank = dist.get_rank()
    t_start = time.time()
    print(f"Rank {rank} sleeps {rank} seconds.")
    time.sleep(rank)  # Simulate different processing times
    dist.barrier()
    print(f"Rank {rank} after barrier time delta: {time.time()-t_start:.4f}")

init_process()
example_barrier()

rank 0 一秒也没睡，但它也花了 2 秒才通过屏障：

Rank 1 sleeps 1 seconds.
Rank 2 sleeps 2 seconds.

Rank 0 after barrier time delta: 2.0025
Rank 1 after barrier time delta: 2.0025
Rank 2 after barrier time delta: 2.0024

这样同步所有节点要小心，它违背了并行独立运算的初衷，可能拖慢整体处理。很多情况下，让快的节点先开始下一个任务完全没问题，因为它下一轮可能变慢，整个过程中的延迟会平均掉。

NCCL

在很多 GPU 上训练大模型，总会碰到 NCCL（读音同 nickel，原书在这里玩了个 “strike gold … encounter nickel” 的谐音梗）。PyTorch 支持几个实现集合通信的库：经典的 MPI（Message Passing Interface）、Meta 的 Gloo，以及 NCCL（NVIDIA Collective Communications Library）。它们提供的集合通信模式差不多，但针对不同硬件优化：NCCL 专为高效的 GPU 到 GPU 通信设计，MPI 和 Gloo 面向 CPU 到 CPU 或 CPU 到 GPU 的通信。PyTorch 有一份 选择后端的指南，归结起来就是：

  • GPU 训练：用 NCCL
  • CPU 训练：用 Gloo

决策树里还有一些细节，原书留给读者去看上面那份指南。

02. A1：分布式训练的性能分析

原书小节：A1: Distributed Training Profiling

Kernels

先假设 kernel 已经集成在 PyTorch 里。以 PyTorch 的层归一化函数 torch.nn.functional.layer_norm 为例，有几种方法 profile 它背后的 kernel。最直接的是用 Python 的 time 模块，但 CUDA 操作是异步的，这种方法只能测到在 Python 里启动 kernel 的开销，测不到 kernel 本身的执行时间。

解决办法是用 torch.cuda.Event 精确计时，并用 torch.cuda.synchronize() 等 kernel 执行完：

def profile_pytorch(func, input):
    # Create CUDA events to track time. CUDA operations are asynchronous.
    start = torch.cuda.Event(enable_timing=True)  # Event to mark the start time
    end = torch.cuda.Event(enable_timing=True)    # Event to mark the end time
    # Warm up to eliminate any overhead from the first run, which might not reflect 
    # the actual performance
    for _ in range(10):
        func(input)
    # Record the start time before executing the function
    start.record()  
    func(input)  # Call the function we want to profile
    # Record the end time after the function has completed
    end.record()  
    # Synchronize the CUDA operations to ensure all operations are completed
    # before measuring the elapsed time
    torch.cuda.synchronize()  
    # Calculate and return the elapsed time in milliseconds
    return start.elapsed_time(end)

更高效的办法是用 PyTorch profiler，例如：

import torch
import torch.nn.functional as F

def pytorch_layer_norm(input):
    return F.layer_norm(input, input.size()[1:])

a = torch.randn(10000, 10000).cuda()

with torch.profiler.profile(
    activities=[
        torch.profiler.ProfilerActivity.CPU,  # Profile CPU activities
        torch.profiler.ProfilerActivity.CUDA,  # Profile CUDA activities
    ],
    # Define a schedule for the profiler
    schedule=torch.profiler.schedule(
        wait=1,      # Wait for 1 iteration before starting to profile
        warmup=3,    # Warm up for 3 iterations to stabilize performance
        active=2,    # Profile for 2 active iterations
        repeat=1,    # Repeat the profiling schedule once
    ),
    on_trace_ready=torch.profiler.tensorboard_trace_handler('.'),

) as p:
    for iter in range(10):
        pytorch_layer_norm(a)
        p.step()

# Print a table of the profiling results, sorted by total CUDA time, limited to the top 10 entries
print(p.key_averages().table(sort_by="cuda_time_total", row_limit=8))

其中 layer_norm.py 是一个只执行层归一化函数的简单脚本。这个命令会输出日志，更好的办法是设置输出文件，便于可视化：

ncu --set full -o output python layer_norm.py

用 Nsight Compute 打开 output.ncu-rep，会看到下面这样的界面，里面有关于计算和显存利用率的明确警告，以及怎样让 kernel 更好地平衡计算与显存访问、达到最大占用率（occupancy）的建议：

（TPU 上看 profiler 的方法，见 How to Scale Your Model 第 9 章。）

CPP 扩展

如果要 profile 的 kernel 还没集成进 PyTorch，可以用 PyTorch 的 cpp_extension 模块编译运行自定义 CUDA 代码：在一个 .cu 文件里写 CUDA kernel，再在 Python 里用 cpp_extension 的 load 函数加载。一个简单的 add kernel 的 .cu 文件：

#include <torch/extension.h>
#include <cuda.h>
#include <cuda_runtime.h>

__global__ void add_kernel(float* x, float* y, float* output, int size) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;
    if (index < size) {
        output[index] = x[index] + y[index];
    }
}

void add_cuda(torch::Tensor x, torch::Tensor y, torch::Tensor output) {
    int threads = 1024;
    int blocks = (x.size(0) + threads - 1) / threads;

    add_kernel<<<blocks, threads>>>(x.data_ptr<float>(), y.data_ptr<float>(), output.data_ptr<float>(), x.size(0));
}
PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("add_cuda", &add_cuda, "Vector addition (CUDA)");
}

加载这个 kernel 的 Python 文件：

import torch
from torch.utils.cpp_extension import load

# Load and compile the CUDA extension
vector_add = load(
    name="vector_add",
    sources=["add_kernel.cu"],
    verbose=True
)

# Define input tensors
size = 10000
x = torch.randn(size, device='cuda')
y = torch.randn(size, device='cuda')
output = torch.empty(size, device='cuda')

# Run the CUDA kernel
vector_add.add_cuda(x, y, output)

这样就能像前面那样，用 PyTorch profiler 或 NVIDIA 的工具 profile 这个自定义 CUDA kernel。

03. A2：LLM 训练中的典型规模

原书小节：A2: Typical Scales in LLM Training

这一节给 LLM 训练里各种量的典型大小一个直观感受。谈显存或计算时，常常是在数“元素”，即张量里的数。要换算成字节，乘以每个数的字节数（BF16 是 2 字节，FP32 是 4 字节）。粗略的数字：

  • 输入 token：每个 batch 处理 $seq \cdot mbs$ 个 token，$mbs$ 是 micro-batch 大小，$seq$ 是序列长度。
  • 激活（隐藏状态）：单层的隐藏状态张量有 $seq \cdot mbs \cdot h$ 个元素。
  • 模型权重和梯度：模型里每个权重矩阵（例如一个线性层）约有 $h^2$ 个元素，梯度和权重一样大。
  • 优化器状态：对每个 $h^2$ 元素的权重矩阵，混合精度训练下的 Adam 用 FP32 保存动量和方差（$2 \times 2 h^2$），再加 FP32 的 master weights（$2 h^2$），合计每个权重矩阵约 $6 h^2$。
  • 模型总参数：每个 Transformer 块存
    • attention 参数：QKV 投影 $3h^2$，输出投影 $h^2$；
    • 带门控线性单元（GLU）的 MLP 参数：gate 和 up 投影 $8h^2$（两个 $h \times 4h$ 矩阵），down 投影 $4h^2$（一个 $4h \times h$ 矩阵）；
    • 每块合计：用 GLU MLP 是 $16h^2$，不用 GLU 是 $12h^2$；
    • 整个模型：$16h^2 \cdot num\_layers$（GLU）；
    • 其他参数：输入 embedding $vocab\_size \cdot h$；LM head $vocab\_size \cdot h$（如果不和输入 embedding 共享）；位置 embedding（如果用）$max\_seq\_len \cdot h$。
  • 前向和反向的计算量（FLOPS）：前向约为 $2 \cdot num\_tokens \cdot num\_params$，反向是它的两倍，$4 \cdot num\_tokens \cdot num\_params$。

原书注：更精确的前向加反向 FLOPs 公式是 $6 \cdot seq\_len \cdot num\_params + 12 \cdot num\_layers \cdot h \cdot seq\_len^2$，第二项来自 attention 在整条序列上的平方增长。为了简化，这里假设 $seq\_len^2 \ll h$。

（参数量、FLOPs 和 $6 \times$ 参数量 $\times$ token 数这条经验公式的完整推导，见 How to Scale Your Model 第 4 章。）

04. A3：通信与计算重叠的数学

原书小节：A3: Math for Compute/Communication Overlap

用 A2 的公式，可以估计分布式训练中通信什么时候能有效地和计算重叠。下面用到的 $peak\_bw$ 是峰值带宽，$peak\_flops$ 是峰值算力，比值 $\frac{t_{comm}}{t_{compute}} \leq 1$ 时通信能完全藏在计算后面。

数据并行的通信分析

以数据并行（ZeRO-0）为例。需要通信的梯度总量：梯度 = 参数 ≈ $num\_layers \cdot 16h^2$。

反向传播时，梯度按 bucket（默认 25 MB）分批通信。每个 bucket 做 all-reduce 的通信时间：

$$t_{comm} = t_{comm\_bucket} = \frac{bucket\_size \cdot 2(DP-1)}{DP \cdot peak\_bw}$$

（带宽计算用的是 NCCL 文档里的 bus bandwidth 公式，它考虑了 GPU 间计算有效带宽时的具体通信模式。）

反向传播的计算时间：

$$t_{compute} = \frac{4 \cdot num\_tokens \cdot num\_params}{peak\_flops}$$

要有效重叠，需要：

$$\frac{t_{comm}}{t_{compute}} = \frac{num\_params}{2 \cdot num\_tokens} \cdot \frac{DP-1}{DP} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$$

这个比值用来判断通信会不会成为训练瓶颈。小于 1 时，通信可以完全和计算重叠。

ZeRO-3（FSDP）的通信分析

ZeRO-3 把参数和梯度切到各 GPU 上。设模型的每个 Transformer 块有 $16h^2$ 个参数：

  • 前向时每个块：all-gather 参数，每个 rank $16h^2/DP$ 字节；
  • 反向时每个块：all-gather 参数 $16h^2/DP$ 字节，reduce-scatter 梯度 $16h^2/DP$ 字节（都是每个 rank）；
  • 每块总通信量：$3 \cdot 16h^2/DP$ 字节；
  • 整个模型：$3 \cdot num\_layers \cdot 16h^2/DP$ 字节。

all-gather 的通信时间：

$$t_{comm} = 16h^2 \cdot \frac{DP-1}{DP \cdot peak\_bw}$$

一个 decoder 层前向的计算时间：

$$t_{compute} = \frac{2 \cdot seq\_len \cdot mbs \cdot (16 \cdot h^2)}{peak\_flops} = \frac{32 \cdot seq\_len \cdot mbs \cdot h^2}{peak\_flops}$$

要有效重叠，需要：

$$\frac{t_{comm}}{t_{compute}} = \frac{1}{2 \cdot seq\_len \cdot mbs} \cdot \frac{DP-1}{DP} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$$

比值小于 1 时，下一层参数的通信可以藏在当前层的计算后面（ZeRO-3 的预取机制见 02 篇）。

张量并行的通信分析

张量并行在 TP 区域（例如 MLP 块）里把激活切到各 GPU 上：

  • 前向时每个列切分线性层（column-linear）：all-gather 激活，每个 rank $seq \cdot mbs \cdot h/TP$ 字节；
  • 反向时每个列切分线性层：reduce-scatter 梯度，每个 rank $seq \cdot mbs \cdot h/TP$ 字节；
  • 行切分线性层（row-linear）反过来。每个 Transformer 块有 2 个列切分和 2 个行切分线性操作；
  • 每块总通信量：$8 \cdot seq \cdot mbs \cdot h/TP$ 字节；
  • 整个模型：$8 \cdot num\_layers \cdot seq \cdot mbs \cdot h/TP$ 字节。

取一层里的一个 TP 区域，分析 all-gather 通信能否和下一个线性层的计算重叠。all-gather 的通信时间：

$$t_{comm} = \frac{seq \cdot mbs \cdot h \cdot (TP-1)}{TP \cdot peak\_bw}$$

下一个线性层（参数 $h^2$）的计算时间：

$$t_{compute} = \frac{2 \cdot seq \cdot mbs \cdot h^2}{TP \cdot peak\_flops}$$

要有效重叠，通信时间要小于计算时间：

$$\frac{t_{comm}}{t_{compute}} = \frac{TP-1}{2 \cdot h} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$$

这个比值决定 all-gather 能否藏在下一个线性层的计算后面。原书特意指出，它只取决于隐藏维度 $h$ 和张量并行度 $tp$，和序列长度、batch 大小无关。

流水线并行的通信分析

流水线并行在各流水线阶段之间传激活和梯度：

  • 前向时每个 micro-batch：接收和发送激活，$2 \cdot seq \cdot mbs \cdot h$ 字节；
  • 反向时每个 micro-batch：接收和发送梯度，$2 \cdot seq \cdot mbs \cdot h$ 字节；
  • 每个 micro-batch 总通信量：$4 \cdot seq \cdot mbs \cdot h$ 字节；
  • 梯度累积 $gas$ 步的总通信量：$4 \cdot gas \cdot seq \cdot mbs \cdot h$ 字节。

分析激活/梯度的通信能否和下一个 Transformer 块的计算重叠。下一个流水线阶段里各 Transformer 块的计算时间：

$$t_{compute} = \frac{32 \cdot seq \cdot mbs \cdot h^2 \cdot num\_layers\_in\_next\_pp}{peak\_flops}$$

点对点（P2P）传输的通信时间：

$$t_{comm} = \frac{seq \cdot mbs \cdot h}{peak\_bw}$$

要有效重叠，需要：

$$\frac{t_{comm}}{t_{compute}} = \frac{peak\_flops}{32 \cdot h \cdot num\_layers\_in\_next\_pp \cdot peak\_bw} \leq 1$$

和 TP 一样，这个比值与序列长度和 batch 大小无关，只取决于隐藏维度 $h$、下一个流水线阶段的层数，以及硬件的算力与 P2P 带宽之比。

（同样的“通信时间对比计算时间”的分析在 TPU 上的版本，见 How to Scale Your Model 第 5 章。）

这一章的要点

  • 集合操作：Broadcast（一份发给所有）、Reduce/AllReduce（合并后给 root/给所有）、Gather/AllGather（各自的块收集到一个/所有节点）、Scatter/ReduceScatter（切片分发/归约后切片分发）、Barrier（同步）。
  • Ring AllReduce = ReduceScatter + AllGather；每张 GPU 收发 $2 \times (N-1) \times \frac{K}{N} \approx 2K$，ReduceScatter 和 AllGather 各约 $K$。
  • GPU 训练用 NCCL，CPU 训练用 Gloo。
  • 给 CUDA kernel 计时要用 torch.cuda.Event 加 torch.cuda.synchronize()；更深入用 PyTorch profiler 和 Nsight Compute（ncu）；自定义 kernel 用 cpp_extension 加载。
  • 典型规模：每块 $16h^2$ 参数（GLU），前向 $2 \cdot num\_tokens \cdot num\_params$ FLOPs，反向是两倍。
  • 重叠条件：DP 为 $\frac{num\_params}{2 \cdot num\_tokens} \cdot \frac{DP-1}{DP} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$；ZeRO-3 为 $\frac{1}{2 \cdot seq\_len \cdot mbs} \cdot \frac{DP-1}{DP} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$；TP 为 $\frac{TP-1}{2h} \cdot \frac{peak\_flops}{peak\_bw} \leq 1$；PP 为 $\frac{peak\_flops}{32 \cdot h \cdot num\_layers\_in\_next\_pp \cdot peak\_bw} \leq 1$。TP 和 PP 的比值与序列长度、batch 大小无关。
