这一章讲什么

前面几章讨论的都是模型运算在高层怎么组织：把计算挪到不同的加速器上，考虑整体的显存限制，安排计算单元的大致调度。这些讨论忽略了更底层的一类优化，也就是弄清楚模型里的每个运算在单块 GPU 上是怎么被调度、怎么执行的，再针对它去改。

01. GPU 入门

原书小节：A primer on GPUs

计算这一侧：SM 和核心

GPU 的组织是层层嵌套的。计算这一侧，一块 GPU 由一组叫流式多处理器（streaming multiprocessor，SM）的计算单元组成，SM 可以理解为 GPU 里一个能独立调度线程的计算模块。每个 SM 里又包含并控制着一组流式处理器（streaming processor），也叫核心（core）。以 NVIDIA H100 为例：132 个 SM，每个 SM 有 128 个核心，合计 16,896 个核心（细节见 NVIDIA 的 tensor core 文档），每个核心都能同时处理多个线程。原书旁注说明，这里只讲到后文需要的概念层面。

（GPU 结构、SM 和 NVLink 的更多细节见 How to Scale Your Model 第 12 章。）

显存这一侧：从寄存器到全局显存

存储这一侧同样分好几层缓存和内存：

  • 寄存器（register）：最小的存储单元，执行时归单个线程私有。
  • 共享内存（shared memory）和 L1 缓存：由运行在同一个 SM 上的线程共享。
  • L2 缓存：再往上一层，所有 SM 共享。
  • 全局显存（global memory）：GPU 上最大的存储，比如 H100 宣传的 80 GB 指的就是它，但它也是访问和读取最慢的一层。

用 GPU 的目标，是借助这种计算和存储的层级结构，在可用的核心上并行跑尽可能多的工作。

kernel、host 代码和 device 代码

在 GPU 核心上运行的一段代码叫 kernel。kernel 可以用 CUDA 或 Triton 这类高层语言来写，然后编译成 PTX（Parallel Thread Execution），也就是 NVIDIA GPU 使用的底层汇编。

要跑起一个 kernel，还需要一段 host 代码。它在 CPU（host）上执行，负责分配显存、把数据和代码搬到 GPU 上。下面是两个向量相加的例子，先看 host 代码（改编自 CUDA C Programming Guide 和 codingconfessions）： 

// Host code
void vecAdd(float* h_A, float *h_B, float *h_c, int n) {
    // Allocate vectors in device memory
    int size = n * sizeof(float);
    float *d_A, *d_B, *d_C;
    cudaMalloc(&d_A, size);
    cudaMalloc(&d_B, size);
    cudaMalloc(&d_C, size);

    // Copy vectors from host memory to device memory
    cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B, size, cudaMemcpyHostToDevice);

    // Invoke kernel
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    VecAdd<<<blocksPerGrid, threadsPerBlock>>>(d_A, d_B, d_C, N);

    // Copy result from device memory to host memory
    // h_C contains the result in host memory
    cudaMemcpy(h_C, d_C, size, cudaMemcpyDeviceToHost);

    // Free device memory
    cudaFree(d_A);
    cudaFree(d_B);
    cudaFree(d_C);
}

流程是：在 GPU 上分配三块向量的显存（cudaMalloc），把 A、B 从 CPU 内存拷到 GPU（cudaMemcpy ... HostToDevice），按每个 block 256 个线程算出需要多少个 block，用 <<<blocksPerGrid, threadsPerBlock>>> 语法启动 kernel，最后把结果拷回 CPU 并释放显存。（代码照原书保留，其中 n/N、h_c/h_C 大小写不一致是原文如此。）

再看 device 代码，也就是 kernel 本身的定义：

// Device code
__global__ void VecAdd(float* A, float* B, float* C, int N)
{
    int i = blockDim.x * blockIdx.x + threadIdx.x;
    if (i < N)
        C[i] = A[i] + B[i];
}

每个线程用自己所在的 block 编号 blockIdx.x、block 大小 blockDim.x 和 block 内的线程编号 threadIdx.x 算出一个全局下标 i，只负责相加这一个位置。if (i < N) 用来防止最后一个 block 里多出来的线程越界。

kernel 的调度：线程、warp、block

kernel 一般这样调度：

  • 线程被分成 warp，每个 warp 有 32 个线程。warp 是 GPU 一起发射指令的最小线程组。同一个 warp 里的所有线程同步执行同一条指令，只是作用在不同的数据上。
  • warp 再组成更大的 block（线程块），block 的大小更灵活，例如一个 block 可以有 512 或 1,024 个线程。每个 block 分配给一个 SM，一个 SM 可以并行跑多个 block。但受资源限制，不是所有 block 都能马上被分配执行，有些会排队等资源空出来。

这里要记住的是：各级存储的容量、同时能跑的 block 数、warp 里的线程数，都是有大小和分配上的约束的。想把 GPU 架构用到最高效，就得把这些约束考虑进去。

大多数时候你不需要钻到这么细，可以直接复用社区里别人写好的 kernel 和代码。不过原书还是给了一些入门写 kernel 的建议，就是下一节。

02. 用 kernel 提升性能

原书小节：Improving performance with kernels

先从 torch.compile 开始

如果你想加一个还没有优化好的 kernel 的新运算，或者想让某个现有的 PyTorch 函数跑得更快，从零写 kernel 看起来是最直接的办法。但从零写出高性能的 CUDA kernel 需要大量经验，学习曲线很陡。原书建议更好的起点是 torch.compile：它会捕获你的运算，动态优化 PyTorch 代码，生成更底层、更高性能的 Triton kernel。

以指数线性单元（Exponential Linear Unit，ELU）激活函数为例：

$$\text{ELU}(x) = \begin{cases} e^x - 1 & \text{if } x \lt 0 \\ x & \text{if } x \geq 0 \end{cases}$$

先写一个简单的 PyTorch 实现，再在上面加上 @torch.compile 装饰器：

@torch.compile
def elu(x, alpha=1.0):
    return torch.where(x < 0, alpha * (torch.exp(x) - 1), x)

下图里编译版和未编译版的性能差距很明显，而改动只是加了一个装饰器（图中 $N$ 是列数）。

从生成的 Triton kernel 入手

如果这样的提升还不够，可以考虑自己写 Triton kernel。Triton 是 OpenAI 开源的一种用 Python 语法写 GPU kernel 的语言，以 block 为单位编程。起点可以是 @torch.compile 生成的那个 Triton kernel，只要把环境变量 TORCH_LOGS 设成 "output_code"： 

export TORCH_LOGS="output_code"

运行带 @torch.compile 装饰器的 Python 脚本后，它会输出对应的 Triton kernel，本例中是：

@triton.jit
def triton_(in_ptr0, out_ptr0, xnumel, XBLOCK : tl.constexpr):
    xnumel = 100000000
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    xmask = xindex < xnumel
    x0 = xindex
    tmp0 = tl.load(in_ptr0 + (x0), xmask)
    tmp1 = 0.0
    tmp2 = tmp0 < tmp1
    tmp3 = tl_math.exp(tmp0)
    tmp4 = 1.0
    tmp5 = tmp3 - tmp4
    tmp6 = tl.where(tmp2, tmp5, tmp0)
    tl.store(out_ptr0 + (x0), tmp6, xmask)

为了好读，可以改改变量名、加注释、做些小调整（也可以让 LLM 来做），得到下面的版本：

@triton.jit
def elu_kernel(input_ptr, output_ptr, num_elements, BLOCK_SIZE: tl.constexpr):
    # Calculate the starting index for this block
    block_start = tl.program_id(0) * BLOCK_SIZE
    # Create an array of indices for this block
    block_indices = block_start + tl.arange(0, BLOCK_SIZE)[:]
    # Create a mask to ensure only valid indices are processed
    valid_mask = block_indices < num_elements
    # Load input values from the input pointer based on valid indices
    input_values = tl.load(input_ptr + block_indices, valid_mask)
    # Define the ELU parameters
    zero_value = 0.0  # Threshold for ELU activation
    negative_mask = input_values < zero_value
    exp_values = tl.math.exp(input_values)
    # Define the ELU output shift
    one_value = 1.0
    shifted_exp_values = exp_values - one_value

    output_values = tl.where(negative_mask, shifted_exp_values, input_values)

    # Store the computed output values back to the output pointer
    tl.store(output_ptr + block_indices, output_values, valid_mask)

逐行看：tl.program_id(0) 给出当前 block 的唯一编号，用它决定这个 block 处理哪一段数据。block_start 算出这一段的起始下标，block_indices 是这一段里的下标范围。valid_mask 保证只处理 num_elements 以内的下标，这样 tl.load 读数据时不会越界。接着按值是否为负套用 ELU，最后用 tl.store 把结果写回显存。

Triton 的上限和四种写法的取舍

即使用 Triton，有时也达不到设备的峰值性能，因为这门语言处理不了 SM 内部的共享内存、调度这类底层细节。Triton 能控制的只到 block 这一层，以及 block 在各个 SM 之间怎么调度。想要更深的控制，就得直接用 CUDA 写 kernel，那里所有底层细节都能碰到。

CUDA 里有很多提升 kernel 效率的技巧，原书只讲其中几种：优化访存模式以降低延迟，用共享内存存放频繁访问的数据，以及管理线程的工作量以减少空闲时间。

进入 CUDA 例子之前，先总结一下能在 GPU 上写 kernel 代码的几种工具：

工具难度速度灵活性
PyTorch容易慢（原书未提）
@torch.compile容易快不灵活
Triton较难更快更灵活
CUDA最难最快最灵活（前提是写对了）

先看 CUDA 最常见的用途之一：优化访存。GPU 的全局显存（前面说过，它是最大的那块存储）和缓存相比延迟长、带宽低，在很多应用里是主要瓶颈。从全局显存高效地读数据，能大幅提升性能。（一个运算被访存还是被计算卡住，可以用 roofline 模型判断，见 How to Scale Your Model 第 1 章。）

合并访存（Memory coalescing）

要用好全局显存的带宽，得先了解它的结构。在 CUDA 设备上，全局显存是用 DRAM 实现的。

合并访存（memory coalescing）利用的是 DRAM 按突发（burst）方式送数据的特性：每次访问 DRAM 的某个地址，芯片里的多个传感器会并行读出包括这个地址在内的一串连续位置，读出后作为一次突发快速传给处理器。CUDA 的合并访存就是利用这一点：让一个 warp（32 个线程按同一条指令同步执行）里的线程访问连续的内存位置。比如线程 0 访问位置 $M$，线程 1 访问 $M + 1$，线程 2 访问 $M + 2$，依此类推，GPU 硬件就会把这些请求合并成一次大的、高效的 DRAM 突发访问，不用逐个处理。

以矩阵乘法为例。最直接的实现是让每个线程计算输出矩阵的一个元素：

__global__ void matmul_naive(int M, int N, int K, const float *A, const float *B, float *C) {
    const uint x = blockIdx.x * blockDim.x + threadIdx.x;
    const uint y = blockIdx.y * blockDim.y + threadIdx.y;

    if (x < M && y < N) {
        float tmp = 0.0;
        for (int i = 0; i < K; ++i) {
            tmp += A[x * K + i] * B[i * N + y];
        }
        C[x * N + y] = tmp;
    }
}

但用 ncu（NVIDIA 的 kernel 性能分析工具 Nsight Compute）分析这个 kernel，会看到一些问题，包括内存吞吐低、访存没有合并：

原因在于：这个 kernel 里，同一个 block 中线程 ID 为 (0, 0) 和 (1, 0) 的两个线程（它们会落在同一个 warp 里）读的是矩阵 B 的同一列、矩阵 A 的不同行。矩阵按行优先（row-major）存储，也就是同一行的元素在内存里地址连续（见下图）。于是在第一轮迭代 $i = 0$ 时，线程 (0, 0) 读 $A_{0,0}$，线程 (1, 0) 读 $A_{1,0}$，这两个元素在内存里离得很远。每一轮迭代都是这样错开的，访存就没法合并。

改进办法是换一种算 x 和 y 坐标的方式：

const int x = blockIdx.x * BLOCKSIZE + (threadIdx.x / BLOCKSIZE);
const int y = blockIdx.y * BLOCKSIZE + (threadIdx.x % BLOCKSIZE);

if (x < M && y < N) {
float tmp = 0.0;
for (int i = 0; i < K; ++i) {
    tmp += A[x * K + i] * B[i * N + y];
}
C[x * N + y] = tmp;
}

这里不再用二维 block，改用一维 block，并重新定义 x、y 的算法。这样，同一个 warp 里的线程（threadIdx.x 相近）有相同的 x、不同的 y，也就是读矩阵 A 的同一行、矩阵 B 的不同列。B 的同一行相邻列在行优先存储下地址连续，所以对行优先矩阵，访存可以合并了。

重新分析新 kernel，未合并访存的警告消失了，GPU 的内存吞吐提高了大约 10 倍。

kernel 的执行时间也缩短到原来的约十分之一。

分块（Tiling）

接下来是文献里经常提到的另一种技巧：分块（tiling）。它利用共享内存来优化访存模式。前面说过，共享内存是一块又小又快的存储，同一个 block 里的所有线程都能访问。数据放进去后可以被多个线程重复使用，减少从较慢的全局显存反复读取。

还是以矩阵乘法为例。block 里的每个线程都可能需要 A、B 两个矩阵里的元素。如果每个线程各自从全局显存读自己要的那一行和那一列，就会有大量重复读取，因为同一个 block 里的多个线程要的数据有重叠。分块的做法是把 A 和 B 的一块（tile）一次性读进共享内存，让 block 里的所有线程共用这份数据。

具体来说，每一轮迭代里，block 内所有线程合作把两块 tile 读进共享内存：A 的一块，大小 BLOCK_SIZE_M × BLOCK_SIZE_K；B 的一块，大小 BLOCK_SIZE_K × BLOCK_SIZE_N。tile 进了共享内存后，线程们对这两块做矩阵乘法，所需数据都能快速取到。tile 相乘的结果存到一个累加矩阵里，每轮迭代都把当前 tile 的乘积加上去，直到两个矩阵的所有 tile 都处理完。

实现里需要看懂的部分如下（原书旁注：为简单起见，这里用正方形 tile）：

// Set pointers to the starting elements
A += blockRow * TILE_SIZE * K; // Start at row = blockRow, column = 0
B += blockCol * TILE_SIZE; // Start at row = 0, column = blockCol
C += blockRow * TILE_SIZE * N + blockCol * TILE_SIZE; // Start at row = blockRow, column = blockCol
float sum = 0.0;
// The outer loop moves through tiles of A (across columns) and B (down rows)
for (int tileIdx = 0; tileIdx < K; tileIdx += TILE_SIZE) {
sharedA[localRow * TILE_SIZE + localCol] = A[localRow * K + localCol];
sharedB[localRow * TILE_SIZE + localCol] = B[localRow * N + localCol];

// Ensure all threads in the block have completed data loading
__syncthreads();

// Shift pointers to the next tile
A += TILE_SIZE;
B += TILE_SIZE * N;

// Compute the partial dot product for this tile
for (int i = 0; i < TILE_SIZE; ++i) {
    sum += sharedA[localRow * TILE_SIZE + i] * sharedB[i * TILE_SIZE + localCol];
}
// Synchronize again to prevent any thread from loading new data
// into shared memory before others have completed their calculations
__syncthreads();
}
C[localRow * N + localCol] = sum;

每个线程先从 A 和 B 各读一个元素放进共享内存。这种情况下做到合并访存很简单：把 threadIdx.x 用作局部列下标 localCol，同一个 warp 里的线程访问的就是两个矩阵里相邻的元素。block 里每个线程都把元素读进共享内存后（由 __syncthreads() 保证），再计算两块 tile 的点积。第二个 __syncthreads() 防止有线程在别人还没算完时就往共享内存里装下一块数据。所有 tile 遍历完（A 横向、B 纵向）后，累加和写到矩阵 C 的对应位置。

用 ncu 测这个 kernel，内存吞吐升到 410 Gb/s，kernel 执行时间减少约 43%，性能达到约 6.6 TFLOPS。

这些难懂的状态名，可以在 NVIDIA 的 Kernel Profiling Guide 的 “Warp Stall Reasons” 一节查到。其中 smsp__pcsamp_warps_issue_stalled_mio_throttle 的解释是：warp 停下来，在等 MIO（memory input/output，内存输入输出）指令队列不再是满的。MIO 流水线被极度占用时这个停顿原因会很高，这条流水线负责特殊数学指令、动态分支和共享内存指令。如果是共享内存访问造成的，可以尝试用更少但更宽的读取来减轻流水线压力。

也就是说，warp 在等共享内存访问返回。解决办法叫线程粗化（thread coarsening）：把几个线程合并成一个“粗化”的线程，让每个线程负责多个输出元素。这样共享内存的访问次数会大幅减少。

减少控制分歧（Minimizing control divergence）

写或改进自定义 kernel 时，最后一个要考虑的重要问题是减少控制分歧。

SM 按单指令多数据（Single Instruction, Multiple Data，SIMD）模型执行一个 warp 里的所有线程：任一时刻，取一条指令，warp 里所有线程同时执行它。线程们处理不同的数据段，但走的是同一条指令，这就是“单指令、多数据”这个名字的由来。SIMD 的主要好处是效率：负责取指令和分派指令的控制硬件由多个执行单元共用，控制部分的硬件开销小，更多硬件可以用来提高算术吞吐。

控制分歧（control divergence）指同一个 warp 里的线程走了不同的执行路径。比如一条 if 语句让一部分线程执行一段代码、另一部分执行另一段，warp 就只能把这两段串行执行，一部分线程空等另一部分做完。要减少控制分歧，kernel 设计上要让同一个 warp 的线程走同一条路径。做法有：重构代码减少分支，使用能让所有线程走相似路径的数据结构，或者使用谓词执行（predication，两边都算、再按条件选结果，避免真正跳转）这类技巧。

到这里，原书讲完了写自定义 kernel、改进 GPU 运算性能和显存占用的几个主要考虑。在进入真实例子之前，还有一个重要概念：融合 kernel（fusing kernels），见下一篇。

这一章的要点

  • GPU 计算侧分层：GPU 由 SM 组成，SM 内有核心。H100 有 132 个 SM，每个 SM 128 个核心，共 16,896 个核心。
  • 存储侧分层：寄存器（线程私有）、共享内存和 L1（同一 SM 内共享）、L2（所有 SM 共享）、全局显存（最大，H100 为 80 GB，也最慢）。
  • kernel 用 CUDA 或 Triton 写，编译成 PTX；运行它还需要在 CPU 上执行的 host 代码负责分配显存、搬运数据和启动 kernel。
  • 线程按 32 个一组成 warp，warp 组成 block（如 512 或 1,024 个线程），每个 block 分到一个 SM；资源不够时 block 会排队。存储容量、并发 block 数、warp 线程数等约束决定了 GPU 能用到多高效。
  • 多数时候直接复用社区写好的 kernel。需要新 kernel 时，先试 @torch.compile；不够再从它生成的 Triton kernel（TORCH_LOGS="output_code"）入手优化。
  • 四种工具：PyTorch 容易但慢；@torch.compile 容易、快、不灵活；Triton 较难、更快、更灵活；CUDA 最难、最快、最灵活（前提是写对）。Triton 只能控制到 block 及其在 SM 间的调度，碰不到共享内存和 SM 内调度。
  • 合并访存：让同一 warp 的线程访问连续地址，硬件把请求合并成一次 DRAM 突发。朴素矩阵乘法改成一维 block、让 warp 内线程读 A 的同一行后，内存吞吐提高约 10 倍，执行时间缩短约 10 倍。
  • 分块：把 A、B 的 tile 读进共享内存供整个 block 复用，用 __syncthreads() 同步。实测内存吞吐 410 Gb/s，执行时间再减约 43%，约 6.6 TFLOPS。
  • 线程粗化：分块 kernel 的 warp 主要停在 mio_throttle（等共享内存访问）；把多个线程合并成一个、每线程算多个输出，可大幅减少共享内存访问。
  • 控制分歧：warp 按 SIMD 执行，分支会让不同路径串行化；通过减少分支、调整数据结构或谓词执行，让同一 warp 走同一路径。
