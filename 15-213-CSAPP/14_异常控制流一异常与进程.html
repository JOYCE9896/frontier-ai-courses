第十四讲：异常控制流（一）：异常与进程

什么是控制流、为什么需要"异常"的控制流，异常表和四类异常（中断、陷阱、故障、终止），系统调用怎样进入内核，进程提供的两个抽象，上下文切换与并发，系统调用的错误处理和包装函数，fork 的"调用一次返回两次"，用进程图分析并发顺序，僵尸进程与回收，wait，以及 execve 和新程序的栈

资料来源：课堂录像（2015 年 10 月 15 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件

一、控制流与异常控制流

从开机到关机，处理器的每个核心只做一件事：一条接一条地执行指令。这串指令序列叫控制流，硬件实际执行的指令序列叫物理控制流。通常它按内存里的顺序执行下一条指令；目前见过两种改变它的机制：分支和跳转，以及过程调用和返回。它们响应的是程序状态的变化，比如分支先检查条件码再决定跳不跳。

但真实的系统还要能对系统状态的变化做出反应：数据从磁盘或网卡到达，用户按下 Ctrl-C，程序执行了一条非法指令，等等。这需要一种在程序正常控制流之外的机制，叫异常控制流（ECF）。它存在于系统的每一层：

  • 最底层是异常：响应底层系统事件（即系统状态的变化）而改变控制流，由硬件和操作系统软件共同实现。
  • 往上一层是进程上下文切换，也由硬件定时器和操作系统内核实现：你正在自己的进程里执行代码，忽然系统开始执行另一个进程的代码，你的进程被挂起了。
  • 再往上是信号，完全由操作系统软件实现，下一讲讲。
  • 最高一层是 C 的非本地跳转，由 C 运行时库实现。正常情况下函数只能返回到调用它的函数，非本地跳转可以打破这个规则，跳到别的函数或代码的别处，也是下一讲的内容。

O'Hallaron 第一讲就说过，异常控制流的概念让课程能在思想上连贯地从硬件过渡到软件。这一讲讲异常和进程。

二、异常

异常是把控制转移到操作系统内核，以响应某个事件。内核是操作系统常驻内存的那一部分；操作系统还提供列文件、切目录、列进程这些程序，内核是其中一直在内存里的部分。过程是：用户代码执行到某处，发生了一个事件（系统状态变了），异常把控制从用户代码转给内核里的一段代码，叫异常处理程序，由它做异常处理。处理完后有三种可能：返回并重新执行当前指令（这对实现虚拟内存的缺页很有用）；返回到下一条指令；或者终止。

异常由硬件和软件共同实现：真正的控制转移（改变程序计数器 %rip）由硬件完成，而异常发生时执行什么代码由操作系统内核设置。每种事件有一个唯一的异常号，作为下标查一张叫异常表的跳转表，取出对应异常处理程序的地址。事件 k 每次发生，都调用处理程序 k。

异步异常：中断

异步异常由处理器外部的状态变化引起，叫中断。外部设备通过把处理器的一个外部引脚（中断引脚）置高来通知处理器。比如磁盘控制器做完直接内存访问、把数据从磁盘复制到内存后，就置高中断引脚。中断处理程序返回到下一条指令，所以对你的程序来说只是短暂停顿一下，处理程序在幕后跑完，你的程序接着运行，通常不受影响。

最常见的中断之一是定时器中断：所有系统都有一个内置定时器，每隔几毫秒触发一次，有专门的异常号。需要它是为了让内核能重新拿到对系统的控制权，否则一个用户程序可以写个死循环永远跑下去，操作系统毫无办法。定时器每隔几毫秒就造成一次进入内核的异常，内核借此决定接下来做什么，比如调度另一个进程，或者让当前进程继续。另一个常见例子是外部设备的 I/O 中断。

同步异常：陷阱、故障、终止

  • 陷阱：程序有意引发的异常，最常见的是系统调用。内核提供各种服务，但用户程序不能直接调用内核里的函数，也不能直接访问内核数据，那些内存是受保护的。内核提供的接口叫系统调用，程序通过它请求服务，看起来像函数调用，实际上把控制转进了内核，处理完后返回到下一条指令。
  • 故障：无意的，但可能可以恢复。缺页就是一种：程序引用的那部分地址空间当前不在内存里，要从磁盘复制进来，然后重新执行引发故障的那条指令，这次就成功了。也有不可恢复的故障，比如访问没分配的内存造成的保护故障，浮点异常有时可恢复。故障处理后要么重新执行当前指令，要么终止。
  • 终止：无意且不可恢复，总是终止程序，比如执行了非法指令、内存损坏、机器检查出硬件问题。

系统调用

Linux 给每个系统调用分配一个号，比如 read 是 0，open 是 2。执行系统调用的指令叫 syscall。通常不直接在程序里写 syscall，Linux 把它们包装成系统级函数，由函数替你调用。看看它怎样工作：调用 open(filename, options)（选项如只读、只写）时，open 调用 __open，后者把系统调用号 2 放进 %rax，参数放在 %rdi、%rsi、%rdx、%r10、%r8、%r9，再执行 syscall。返回值在 %rax 里：负数表示出错；非负表示成功，open 返回的是一个小整数，叫文件描述符，后续的读写都用它。代码后面紧跟着一串比较，就是在检查是否返回了负数。

两个故障的例子

缺页：程序往一个合法区域写数据，但那块内存当前不在主存里，要从磁盘装入。写内存的 movl 指令触发缺页，控制转给内核的缺页处理程序，它把那一页从磁盘复制到内存后返回，并重新执行那条 movl，这次就成功了。

非法内存引用：程序访问一个根本不存在的数组元素，地址是非法的。movl 看上去也像缺页，但内核发现这个地址在虚拟地址空间的无效区域，没有任何东西可以从磁盘装入，于是给进程发一个信号，不再返回。这个信号会让程序打印出那句臭名昭著的"Segmentation fault"，信号怎样工作下一讲讲。

三、进程

O'Hallaron 说，进程是计算机科学中最基本、最重要的概念之一。经典定义是：进程是一个正在运行的程序的实例。它和程序不同：程序可以以很多形式存在，C 文件里的文本，二进制文件的 .text 节，装进内存的字节；进程是正在执行的那个实例。进程提供两个关键抽象：

  • 逻辑控制流：好像程序独占 CPU 和寄存器。你在进程里运行程序时，从不必担心别的程序改你的寄存器，甚至察觉不到系统上还有其他进程，除了偶尔某条指令似乎慢了一点。这由内核的上下文切换机制提供。
  • 私有地址空间：好像程序独占内存。每个运行的程序有自己的代码、数据、堆、栈，看不到别的进程用的内存。这由虚拟内存机制提供。

系统同时运行着很多进程，即使只有一个核心，它们也是并发运行的。O'Hallaron 在他的 Mac 上运行 top，看到共 123 个进程，其中 5 个正在运行，每个进程有唯一的整数进程号（PID）。

上下文切换

看起来是独占，实际上是共享，由操作系统管理。设只有一个核心：一个进程在运行，有自己的地址空间和寄存器；某个时刻发生了异常（定时器中断、故障或陷阱），操作系统拿到控制权，假设它决定运行另一个进程，就把当前寄存器的值保存到内存，调度下一个进程，把那个进程上次运行时保存的寄存器值装回 CPU，再把地址空间切换成那个进程的。地址空间和寄存器值合起来叫上下文，上下文切换就是换掉这两样。现代多核系统上，操作系统把进程调度到多个核心上，核心不够用时再像上面那样切换。

并发

每个进程都是一个逻辑控制流。如果只看所有的程序计数器值，那是物理控制流，执行着执行着突然变成了另一个进程的指令；但在单个进程内部，有一条由它自己的所有指令组成的逻辑控制流。两个进程的逻辑流在时间上重叠，就说它们并发运行，否则就是顺序运行。

例子：进程 A 运行一阵，被 B 打断，B 运行完终止；然后 C 运行一阵；然后 A 继续运行一阵；然后 C 再运行并终止。A 和 B 并发（B 开始和结束时 A 都还没结束）；A 和 C 并发；B 和 C 不并发，B 在 C 开始之前就结束了。这个定义和核心数无关，即使只有一个核心，只要逻辑流在时间上重叠就算并发。不管怎样，从各个进程自己的角度看，都可以把它们想成在并行运行。

上下文切换由内核管理。重要的一点：内核不是一个单独运行的进程，它总是在某个现有进程的上下文里运行，它只是地址空间上部的一段代码，因异常而被执行。所以应该这样想：进程 A 在运行，发生异常，控制转给内核；内核调用调度器，决定让 A 继续还是切换到另一个进程；比如决定运行 B，就改指地址空间，此时已经在 B 的上下文里运行，再装好 B 的通用寄存器，把控制交给 B，B 从上次停下的地方继续；之后又发生异常，内核又决定切回 A，A 从它当时正在执行的那条指令之后继续。

四、进程控制

Linux 提供一系列从用户程序调用、操纵进程的函数，统称进程控制。它们大多会执行系统调用，但包装成了更高一层的系统级函数，用户程序调用的就是这些函数。

错误处理

Linux 系统级函数出错时通常返回 -1，并设置全局变量 errno 说明原因。有一条铁律：调用系统级函数时，必须检查返回值，否则迟早会陷入大麻烦。唯一的例外是 exit、free 这类返回 void 的函数。比如用于创建进程的 fork，成功时返回新进程的 PID（总是正数），出错返回 -1，所以检查返回值是否小于 0，然后处理错误（课件里是打印信息并 exit(0)，有同学指出出错时按惯例应该以非零状态退出，O'Hallaron 同意）。

这样做必不可少，但在课上和书里展示代码时会很乱、占地方。所以课程定义了错误报告函数：对 Unix 风格的错误（返回 -1、设置 errno），打印信息并报告错误原因后退出，于是 if 语句的主体只要一行。更进一步，用包装函数，这是著名技术作家 W. Richard Stevens 开创的：每个函数都有一个接口完全相同、首字母大写的包装函数，比如 Fork，它调用原函数、检查错误，没出错就返回原函数的返回值，出错就处理并打印信息。这样代码既紧凑，又不违反"必须检查错误"的铁律。

获取进程号

最简单的进程控制函数：getpid 返回当前进程的 PID，getppid 返回父进程（创建当前进程的那个进程）的 PID。

进程的三种状态

  • 运行：正在执行，或者在等待被调度执行。
  • 停止：执行被挂起，在另行通知之前不会被调度。通常是因为收到了某种信号，下一讲讲。
  • 终止：永久停止，不会再被调度。原因有三：收到一个默认行为是终止的信号；从 main 返回（main 总是返回 int）；调用 exit 函数，以参数作为退出状态，按惯例正常返回 0、出错返回非零。从 main 返回一个整数也会设置退出状态。exit 很特别：调用一次，从不返回。这是所有进程控制函数的典型特点，普通函数调用一次返回一次，它们却不是。

五、fork

父进程调用 fork 创建一个子进程。fork 不带参数，返回一个整数。它创建新进程后，在父进程和子进程里各返回一次，第一次见时很难理解：父进程调用一次，返回两次。在子进程里返回 0，在父进程里返回子进程的 PID。子进程得到父进程虚拟地址空间的一份完全相同但彼此独立的副本：fork 刚返回时，所有全局变量、栈、代码都和父进程一样。子进程还得到父进程所有打开文件描述符的相同副本，所以能访问父进程打开的所有文件，包括标准输入和标准输出。唯一的区别是子进程的 PID 和父进程不同。

例子：程序在栈上有一个局部变量 x，初值 1，然后调用 fork。唯一能区分在父进程还是子进程里的办法是看返回值。返回值为 0 就在子进程里：子进程的 x 也是 1，它先把 x 加一再打印，输出 x = 2，然后 exit。父进程拿到的返回值非零（子进程的 PID），不执行那段条件体，先把 x 减一再打印，输出 x = 0。谁先运行没有任何保证：fork 返回时内核可能先调度子进程，也可能先调度父进程，无法预测，对此做任何假设都是错的。父子进程共享打开的文件，所以两者都打印到同一个终端上。

进程图

fork 可能很复杂，尤其是嵌套或多次调用时。无法对不同进程的执行顺序做假设，但可以用进程图刻画事件之间的偏序：每个顶点对应一条语句的执行；一条边 a → b 表示 a 发生在 b 之前；边上可以标出变量的当前值；printf 的顶点可以标出它的输出；图从一个没有入边的顶点开始。图的任意一个拓扑排序（所有顶点的一个全序，使所有边都从左指向右）都对应一个可能的事件全序。

对上面的例子：父进程里 x = 1，调用 fork；fork 在父子两边都返回；子进程把 x 加一并打印，父进程把 x 减一并打印，然后都 exit。这两条分支是并发的，可以任意交错。把边简单地重新标成字母，序列 a b e c f d 是一个拓扑排序，因而是可行的：a、b 之后执行子进程的 e，然后内核换出子进程让父进程执行 c，再调度子进程执行 f，最后父进程执行完。只执行一条指令就发生上下文切换不太可能，但是可行的。而让 f 出现在 e 之前的序列是不可行的，因为在子进程这条逻辑流里，f 在代码中就位于 e 之后，编译器不会调换它们。

  • 两次连续的 fork：父进程打印 L0，fork；父子进程都打印 L1，再各自 fork；于是共有四个进程，都打印 Bye。看不清时就画进程图。比如先打印 Bye 再打印 L1 之类的顺序是不可行的，因为在第一次 fork 之前不可能打印 Bye，画出来会有一条倒着走的边。
  • 在父进程里嵌套 fork（O'Hallaron 说不知道为什么会有人这么写，大概只是为了折磨 213 的学生）：父进程打印 L0，fork；fork 返回 0 的是子进程，它直接打印 Bye；返回非零的是父进程，打印 L1 后再 fork，新的子进程跳出条件、打印 Bye，父进程打印 L2 再打印 Bye。画出进程图就能判断哪些输出顺序可行，比如 L2 之前不可能先出现父进程自己的那个 Bye。

六、回收子进程

进程终止后，系统并不马上把它彻底清除，而是保留一点状态（退出状态和一些操作系统表项），直到被父进程回收。原因是父进程可能想等待子进程结束并查看它的退出状态。这种已经终止、但还没被回收的进程叫僵尸进程，半死半活。它一直是僵尸，直到父进程用 wait 或 waitpid 回收它，父进程得到退出状态信息，内核随即删除这个僵尸。

如果父进程不回收呢？父进程终止时，系统会安排系统里的第一个进程 init（PID 为 1）去回收它的孤儿子进程。所以只有长期运行的父进程才真正需要担心回收僵尸，比如 shell 或服务器：服务器可能创建上百万个子进程，每个终止后都变成僵尸，在内核里占着空间，不回收就是一种内存泄漏，最终可能填满内存、让内核崩溃。

僵尸的例子：fork 之后，子进程打印自己的 PID 后 exit，父进程打印信息后进入死循环，永不回收子进程。在后台运行这个程序（命令后加 &，否则它一直占着终端，没法查看），再用 ps 查看，能看到父进程 6639 和子进程 6640，后者标着 defunct，就是僵尸。用 kill 杀掉父进程 6639 后再 ps，僵尸也不见了，它被 init 回收了。

反过来，子进程不终止会怎样？子进程打印信息后进入死循环，父进程打印信息后退出。ps 能看到子进程仍在运行，尽管父进程已经终止。kill 掉子进程 6676 后，它没有父进程，由 init 回收，从系统中消失。

wait

最简单的同步和回收函数是 wait。wait(&status) 挂起调用它的进程，直到它的某一个子进程终止，不指定是哪一个。参数可选，不为空时，它指向的整数会被设置成表示子进程终止原因和退出状态的值，可以用书里详细介绍的一组宏检查。

例子：fork 出子进程，子进程打印 HC（hello from child）后 exit；父进程打印 HP（hello from parent），然后 wait 等子进程终止，再打印 CT（child has terminated）和 Bye。进程图上，父进程的 wait 一直挂起到子进程调用 exit，所以 CT 和 Bye 不可能出现在子进程终止之前。有同学问能否输出 HP HC CT Bye：可以，父进程打印 HP 后发生上下文切换，子进程打印 HC 并 exit，父进程的 wait 返回，再打印 CT 和 Bye。

更完整的例子：循环 N 次，每次 fork 一个子进程，子进程以一个能标识自己是第几个的状态值 exit；父进程再循环 N 次，每次 wait 一个子进程终止，但不能按特定顺序等待。wait 返回 PID，状态存在 child_status 里：用 WIFEXITED 判断是否通过调用 exit 正常终止，是的话用 WEXITSTATUS 取出退出状态，否则说明是因为别的原因终止的。

waitpid 和 wait 类似，但可以等待某个指定 PID 的子进程终止。它的用法相当复杂，书里有详细说明。

七、execve：加载并运行程序

fork 只是创建父进程的一份完全相同的副本，运行同样的代码、同样的程序。要在进程里运行另一个程序，用 execve(filename, argv, envp)：在当前进程里加载并运行 filename。filename 可以是二进制可执行文件，也可以是脚本文件，即第一行以 #! 开头、后跟某个解释器路径的文本文件。比如写 shell 脚本时，第一行是 #! 加上 bash 的路径，bash 就会读入后面的各行，像在命令行输入一样解释执行。argv 是参数列表，envp 是环境变量列表。按惯例 argv[0] 是被执行文件的名字，所以想在代码里打印正在运行的程序名，打印 argv[0] 即可。

execve 会覆盖整个虚拟地址空间，代码、数据、栈全都换掉，一旦调用，当前程序就没了。但它还是同一个进程，只是运行着新的程序，所以保留了 PID 和所有打开的文件。它调用一次、从不返回，除非出错，比如文件不存在，那时返回 -1。O'Hallaron 说这真的让人"脑洞大开"。

新程序开始时的栈

execve 完成工作后，创建新的栈，装入新的代码和数据，创建新的空堆，一切都是新的。新栈的结构（以启动代码 __libc_start_main 调用 main 之前为准），从栈底往上：

  • 最底部是以空字符结尾的环境变量字符串和命令行参数字符串。
  • 然后是环境变量指针数组 envp[]，每个指针指向一个"键=值"形式的环境变量字符串，以空指针结尾，由全局变量 environ 指向；如果传给 main，它的地址作为第三个参数在 %rdx 里。
  • 然后是参数指针数组 argv[]，每个指针指向一个参数字符串，以空指针结尾。运行程序时写的程序名和用空格分隔的参数就是这些字符串。argv 的地址是 main 的第二个参数，在 %rsi 里；参数个数 argc 是第一个参数，在 %rdi 里，符合 x86-64 的参数传递约定。
  • 再往上是一些填充、__libc_start_main 的栈帧，以及将来 main 的栈帧。

fork 加 execve

例子：在当前程序里执行 /bin/ls -lt /usr/include，即长格式列出 /usr/include 下的文件，按修改时间从新到旧排序。如果直接调用 execve，当前程序就被抹掉了。所以假定之后还要继续工作，标准做法是先 fork 一个子进程，在子进程里 execve，让子进程去干活，父进程通常会等待它结束。具体是：fork，检查返回值为 0，在子进程里调用 execve(myargv[0], myargv, environ)，程序名放在参数列表第一个元素里，myargv 已经设置好，环境变量直接传全局变量 environ，沿用父进程当前的环境，形如 USER=droh、PWD=/usr/droh。如果程序不存在，execve 返回 -1，子进程检查后退出；否则它不再返回，/bin/ls 这个二进制文件被装入内存执行，执行完就终止，此时子进程运行的已经是 ls 的代码，不再是原来的代码。

fork 和 exec 分开，第一次见会觉得奇怪：为什么不用一个命令创建新进程并在其中运行程序？Windows 就是这么做的。但事实证明单独有一个只创建进程的 fork 很有用。有时就是想复制当前进程，比如并发服务器，父进程 fork 出一批运行同样代码的子进程。它还允许在 fork 之后、exec 之前，在子进程里先执行一些代码，比如阻塞或解除阻塞某些信号，在处理信号时尤其有用。

小结：异常是对需要很规控制流（异常控制流）的事件的响应，可以由外部产生（中断），也可以由内部产生（陷阱和故障）；系统在任一时刻有多个进程，一个核心上同一时刻只能执行一个，内核让它们的执行交错进行，每个进程都以为自己完全掌控着处理器和地址空间；创建进程只有 fork 一种机制，调用一次返回两次；exit 终止进程，调用一次从不返回；用 wait 或 waitpid 等待和回收进程；用 execve 或它的变体加载并运行程序，调用一次，通常从不返回。
