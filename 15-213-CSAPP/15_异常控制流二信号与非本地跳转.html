第十五讲：异常控制流（二）：信号与非本地跳转

一、从 shell 说起

这一讲继续讲异常控制流中更高层的两种机制：Linux 信号和 C 的非本地跳转。大部分时间给信号，因为它有很多微妙之处，语义容易让人困惑；非本地跳转只简单提一下，细节在书里和课件末尾的补充页。

上一讲说过，Linux 上创建进程只有 fork 一种办法，所以系统上所有进程构成一个层级：开机时创建的第一个进程是 init（PID 为 1），其他所有进程都是它的后代。init 启动时创建守护进程，即长期运行、通常提供服务的程序，比如 Web 服务器；最终还会创建登录 shell，为用户提供命令行界面。登录 Linux 后，你最终面对的就是一个等你输入命令的登录 shell。

shell 代表用户运行程序。输入 ls，就是请 shell 运行名为 ls 的可执行程序，shell 会创建一个子进程，在子进程里执行 ls，那个进程还可能再创建子进程。shell 是一个应用程序，和其他程序没什么两样。Linux 默认的 shell 是 bash；更早的 Unix 有最初的 sh，叫 Bourne shell，因为是 Stephen Bourne 写的；伯克利发布自己的 Unix 版本时写了 csh。

读取求值循环

shell 的执行是一连串的"读取、求值"：打印提示符，等你在命令行输入并按回车。输入的通常是一个命令，后面跟用空格隔开的可选参数。读到后，先检查是不是文件结束符（终端上的 Ctrl-D），是就退出，否则对这一行求值，求值返回后再重复。

求值的步骤：先解析命令行，生成 argv 数组，argv[0] 是命令，后面是参数；按惯例，命令行以 & 结尾表示在后台运行这个作业，shell 不等它结束就进入下一次读取，否则在前台运行，shell 会等它。argv[0] 为空说明只按了回车，直接忽略。shell 还实现了内置命令，比如 jobs、bg、fg，如果 argv[0] 是内置命令，shell 自己执行。否则就是要运行某个程序：shell fork 一个子进程，子进程调用 execve，第一个参数是命令名，后两个是 argv 和环境变量；execve 只在出错时返回，返回值一定是 -1，但这里还是谨慎地检查并打印错误信息后退出。父进程重新拿到控制后，如果是前台作业就用 waitpid 等它终止并回收；如果是后台作业，打印一条信息就继续。

O'Hallaron 指出这里很有意思：前台作业和后台作业唯一的区别，只是 shell 有没有对它调用 waitpid。但这个简单 shell 有个问题：前台作业被正确回收了，后台作业却从来没人回收。后台作业多了会造成内存泄漏，可能拖垮系统。怎么办？异常控制流可以帮忙：每当某个子进程终止，内核都会通知 shell，shell 再调用 waitpid。这个通知机制就是信号。

二、信号是什么

信号是内核发给进程的一条小消息，告诉它系统里发生了某个事件。它和上一讲的异常很像，只是完全用软件实现。信号总是由内核发出，有时是应另一个进程的请求。之所以说是"小"消息，是因为它包含的唯一信息就是一个唯一的整数 ID，以及"它到了"这件事本身。几个例子：

编号名字默认行为对应事件
2SIGINT终止用户按 Ctrl-C
9SIGKILL终止强行杀死程序，不能被忽略或改写
11SIGSEGV终止段错误，访问了受保护或非法的内存
14SIGALRM终止定时器到时
17SIGCHLD忽略子进程停止或终止

在命令行按 Ctrl-C 时，内核给前台的每个进程发 SIGINT，默认行为是终止，所以前台作业被杀掉、提示符回来。SIGKILL 的效果一样，特别之处是无法忽略或改写，是最后的保险，而 SIGINT 等信号是可以捕获并忽略的。SIGALRM 可以让程序安排在几秒后给自己发一个信号，用来设定时器或超时，比如给某项工作设一个上限，防止它跑得异常地久。对 shell 最重要的是 SIGCHLD：每当一个子进程终止或停止，内核就给父进程发这个信号，shell 就是靠它来回收所有子进程。

术语要分清

O'Hallaron 说，信号的语义大概是 Linux 最棘手的部分之一，它在 Linux（Unix）生命早期就设计出来了，未必像它本可以的那样干净，所以要很仔细地定义术语。

  • 发送（或递送）：内核通过修改目标进程上下文里的某个状态，把信号送给它。此时只是一些位变了，没有任何立即的影响。内核发送信号，要么因为检测到某个系统事件（比如子进程终止），要么因为另一个进程请求内核代发，方式之一是 kill 系统调用。这个名字很不幸，kill 是发送信号的通用方式，效果有时并不是杀死程序。
  • 接收：内核强迫目标进程对信号做出某种反应时，进程才算接收了信号。反应可以是忽略、终止进程，或者执行一个叫信号处理程序的用户级函数来捕获信号。捕获信号很像响应事件执行异常处理程序，区别在于异常处理程序在内核里，而信号处理程序就在你的 C 代码里，在你的进程中执行：进程正在执行指令，接收到信号，控制转给处理程序，处理程序运行完返回，最终回到下一条指令继续，就像一次中断，暂停一下去执行处理程序，然后接着做原来的事。
  • 待处理：已经发送、还没被接收的信号。任一时刻，同一种类型的待处理信号最多只有一个。这对使用信号有很重要的后果：信号不排队。如果已经有一个待处理的 SIGCHLD，再来一个 SIGCHLD 就相当于被丢弃了。
  • 阻塞：进程可以阻塞某些信号的接收。它不能阻止信号被发送，但能让进程在信号到达时不必反应。被阻塞的信号可以被发送，但直到解除阻塞才会被接收。待处理的信号最多被接收一次。

内核用两个位向量记录这些状态：pending 表示待处理信号的集合，每一位对应一种信号，这就是信号不能排队的原因，每种信号只有一位，发送时置位，再发一次同类信号只是再置一次，毫无作用；信号被接收时内核清除这一位。blocked 和 pending 一样大小，实际是一个 32 位整数，用户可以通过 sigprocmask 系统调用设置和清除其中的位，Linux 文献里也把它叫作信号掩码。

三、发送信号

进程组

每个进程恰好属于一个进程组。例子：shell 的 PID 是 10，进程组 ID 也是 10；它创建了一个前台作业，PID 20，并把这个子进程的进程组 ID 改成和它的 PID 相同，即 20；这个作业再创建的子进程都继承进程组 ID 20。进程组 ID 可以用 setpgid 设置，用 getpgrp 获取。进程组的用处是可以一次给一组进程发信号。

用 /bin/kill 程序

/bin/kill 可以给单个进程或某个进程组里的所有进程发任意信号。例子：forks 程序创建两个子进程，进程组都是 24817，PID 各不相同，各自进入死循环，ps 能看到它们一直在运行。kill -9 24818 请内核给进程 24818 发 SIGKILL（第一个参数是信号编号，-9 就是 SIGKILL，通常想杀进程就用 kill -9）。O'Hallaron 说，他最喜欢的一个 213 Autolab 昵称就是"kill -9 15213"。PID 前加负号，比如 kill -9 -24817，就把它当作进程组，给组里每个进程都发信号，之后 ps 可以看到两个子进程都没了。

用键盘

在命令行按 Ctrl-C，内核给前台进程组里的每个作业发 SIGINT，默认终止；按 Ctrl-Z，发 SIGTSTP，默认挂起（停止）进程，直到收到 SIGCONT。例子：一个程序以父子两个进程在前台运行，按 Ctrl-Z，shell 提示它被挂起了，ps 显示两者状态为 T（停止）；输入内置命令 fg，把挂起的作业恢复到前台，程序又在前台运行了；按 Ctrl-C 发出 SIGINT 终止它，ps 确认它们都不在了。

用 kill 函数

第三种方式是在程序里调用 kill 系统调用。例子：创建 N 个子进程，各自进入死循环，记下每个子进程的 PID；然后在另一个循环里，对每个 PID 调用 kill(pid[i], SIGINT)；最后尽职地逐个回收这些子进程。其实函数一返回程序就退出了，严格说回收不是必需的，只是谨慎，O'Hallaron 自嘲可能有点过于讲究。

四、接收信号

设进程 A 在执行用户代码，因为某个异常控制转入内核，异常可能是定时器中断，也可能是用户发起系统调用的陷阱，但进入内核一定是因为某种异常。内核调用调度器，决定从 A 切换到 B，把 B 准备好；就在从异常返回、把控制交回 B 的用户代码之前，内核检查 B 有没有待处理的信号：计算 pnb = pending & ~blocked，即所有待处理且未被阻塞的信号，这些是应该被接收的。pnb 全为 0 就直接把控制交回 B；否则选出 pnb 中最小的非零位 k，强迫 B 接收信号 k，接收触发某种行为；对 pnb 里每个非零位重复这一过程；全部处理完，才把控制交给 B 的下一条指令。

每种信号都有预定义的默认行为：终止进程；终止并转储内存（core dump）；停止进程，直到收到 SIGCONT 重新启动；忽略这个信号。

安装信号处理程序

默认行为可以用 signal(signum, handler) 修改。这个名字和 kill 一样有误导性，它并不发送任何信号，只是修改与某个信号关联的行为。handler 可以是 SIG_IGN（忽略这类信号）、SIG_DFL（恢复默认行为），或者一个用户级信号处理程序的地址，即你在 C 程序里定义的一个函数。这个函数没什么特别的，只要原型正确：返回 void，接受一个 int 参数，处理程序被调用时这个参数就是信号编号。用 signal 指定处理程序叫安装处理程序；执行处理程序叫捕获或处理信号。处理程序执行时会打断进程正在执行的代码，返回时回到被打断的地方继续。

例子：main 里为 SIGINT 安装一个处理程序 sigint_handler，然后调用 pause，pause 挂起当前进程，直到收到一个信号并且有处理程序在这个进程里执行完，然后返回。O'Hallaron 问：做炸弹实验时，有没有人慌了按 Ctrl-C 想逃出去？当时那句刻薄的回应，就是课程组在你的炸弹里装了一个 SIGINT 处理程序打印出来的，之后才让你退出。

五、处理程序是一种并发流

信号是课程里第二次碰到并发。第一次是进程：逻辑流在时间上重叠就是并发。进程之间有各自独立的地址空间，并发的流互不干扰，从某种意义上说很好对付，一个进程不必担心被另一个进程干扰，要在进程之间共享内存反而要用专门的系统调用费一番功夫。

信号处理程序是另一种并发：它是另一条逻辑流，和主程序并发运行。比如进程 A 在执行一个 while 循环，接收到信号，控制转给处理程序，这条流和那个 while 循环在时间上重叠，处理程序返回后再回到 A。信号之所以棘手，就是因为这种并发：处理程序和主程序运行在同一个进程里，共享程序的所有全局变量，处理程序是你定义的一个函数，能访问程序的所有全局状态，这种共享会带来真正的问题。

用上下文切换图看：A 在执行，某个时刻有信号递送给 A，此时什么也没发生，只是 A 的 pending 位被置上；之后控制转入内核，内核从 A 切换到 B，B 运行一阵；又进入内核，内核调度 A，就在把控制交回 A 之前，发现这个信号的 pending 位被置上了，于是让 A 接收它，执行处理程序；处理程序返回时先短暂回到内核，再由内核把控制交回 A 原本要执行的下一条指令。

处理程序还可能被其他处理程序打断：主程序捕获信号 s，控制转给处理程序 S；S 执行时程序又捕获了信号 t，控制转给处理程序 T；T 返回到 S 被打断的那条指令，S 继续执行，最终返回到主程序被打断的地方。内核总会阻塞与当前正在处理的信号同类型的待处理信号，所以 T 类型的处理程序不会被另一个 T 类型的信号打断，但可以被别的类型打断。

显式阻塞和解除阻塞

除了这种隐式阻塞，内核还提供 sigprocmask 显式地阻塞和解除阻塞一组信号，配套的 sigemptyset、sigfillset、sigaddset、sigdelset 用来构造这组信号的集合，可以把它们想成对位向量置位和清位。这在接下来的 shell 实验里很重要。用法：用 sigemptyset 建一个空集合（全 0）；用 sigaddset 加入 SIGINT；有一段代码不想被 SIGINT 打断，就调用 sigprocmask(SIG_BLOCK, &mask, &prev_mask)，把集合里的信号加入阻塞集，同时把原来的掩码保存到 prev_mask；返回后 SIGINT 被阻塞，执行那段代码时不会被打断；最后用 sigprocmask(SIG_SETMASK, &prev_mask, NULL) 恢复原来的阻塞集。

六、信号为什么这么难

O'Hallaron 列了三件让信号处理变得棘手甚至讨厌的事：很容易写出不安全的处理程序，可能造成死锁，或者破坏主程序正在修改的全局数据结构，比如主程序正在更新一个链表，刚改到一半、处于不一致状态时被信号打断，而处理程序恰好也在读或改这个链表，就会碰上这个不一致的状态；信号不排队，稍不小心就会默认"收到一个信号就代表发生了一次事件"，用它来计数，而这是不行的；信号的行为在不同 Unix 之间都不一定可移植，Solaris 或某种 BSD 的语义未必和 Linux 一样。

写安全处理程序的准则

这些准则汇集了各种来源的经验：

  1. 处理程序尽可能简单。最简单的处理程序只设置一个全局变量就返回。CMU CERT 发布的合规编程准则里，唯一允许的合规处理程序就是这种。
  2. 处理程序里只调用异步信号安全的函数。常用的 printf、sprintf、malloc、exit 都不安全。
  3. 进入和退出时保存和恢复 errno。errno 是系统级函数出错时设置的全局变量，处理程序里调用的函数可能改写它，从而干扰主程序里依赖 errno 的那部分代码。
  4. 访问主程序和处理程序共享的数据结构时，在两边都临时阻塞所有信号，理由就是上面说的不一致状态。
  5. 把共享的全局变量声明为 volatile。volatile 阻止编译器把它放进寄存器，读写总是去内存。否则，假如编译器把变量放进寄存器，处理程序写这个变量只改了寄存器（实际上是它自己那份），主程序在循环里等这个变量被设置时可能永远看不到变化。
  6. 只读或只写（不做递增之类更新）的全局标志，可以声明为 volatile sig_atomic_t，系统保证对它的读写是原子的，即在一个不可打断的步骤里完成，所以访问它时不必额外保护。大多数系统上 sig_atomic_t 就是 int，一条指令就能读写，但为了可移植应该用 sig_atomic_t。

异步信号安全

一个函数可以安全地在处理程序里使用，要么因为它是可重入的，要么因为它不会被信号打断。可重入函数（讲线程时会细讲）访问的所有数据都在自己的栈上，没有全局变量，也没有指向全局变量的指针，所以可以同时存在多个实例，各自有一份变量。POSIX 标准保证 117 个函数是异步信号安全的，包括 _exit、write、wait、waitpid、sleep、kill 等，但不包括 printf、sprintf 这些大家很想用的函数。事实上 write 是唯一异步信号安全的输出函数。

为什么 printf 不安全？可以写出这样一个程序：主程序在一个紧凑的循环里不停 printf，同时有一串连续的中断执行处理程序，处理程序里也调用 printf。printf 这个库函数内部要先获取终端上的一把锁，保证同一时刻只有一个 printf 能写终端，别的 printf 想拿锁就得等着，直到持有者释放。锁是获取对共享资源互斥访问的一种手段。如果主程序里的某次 printf 刚拿到锁就被信号打断，处理程序里的 printf 去拿同一把锁，就会永远阻塞，因为持有锁的主程序已经被打断，永远不会释放它。这就是经典的死锁：一个进程在等一个永远不会发生的事件。O'Hallaron 说这种死锁并不难复现。

O'Hallaron 不想告诉大家程序里完全不能输出，而 write 又很难用，所以他写了一个小小的"安全 I/O"库，放在网站上发布的 csapp.c 里，有三个可重入的函数：sio_puts 打印字符串，sio_putl 打印一个 long，sio_error 打印消息后退出。用它们可以把炸弹的 SIGINT 处理程序改写成每个函数都是异步信号安全的版本。

信号不排队

例子：安装一个 SIGCHLD 处理程序，这正好接上 shell 怎样回收后台子进程的问题。程序创建 N 个子进程，每个睡一会儿就退出；父进程循环等待一个全局计数 ccount 变成 0（初值为 N）。处理程序每被调用一次，就 wait 回收一个子进程并把 ccount 减一，所有子进程都回收后 ccount 为 0，父进程退出循环。N 是 5，运行时"处理程序回收了一个子进程"的消息却只打印了两次：创建并终止了五个子进程，只回收了两个。

错误在于假定处理程序每执行一次就对应收到一个 SIGCHLD。实际上多个 SIGCHLD 被递送，一次次覆盖 pending 里的同一位，进程直到快要重新被调度时才对它们做出反应，而那时，即使递送了三个，也只接收一个。所以不能用信号来计数事件，这里的事件是子进程终止，收到一个 SIGCHLD 只能推出至少有一个子进程终止了。修正办法是：收到 SIGCHLD 时，假定可能有多个已终止的子进程，把回收用的 wait 放进循环，一直回收到没有已终止的子进程为止，此时 wait 返回 -1 且 errno 为 ECHILD，这不是真正的错误，只说明没有子进程可回收了；如果 errno 不是 ECHILD，才是真出错。改完后五个子进程都被回收。

可移植的信号处理

不同 Unix 的信号语义有差别：一些早期的 Unix 捕获信号后会把行为恢复成默认，每次处理程序被调用都得在处理程序里重新调用 signal 安装它，Linux 上不需要。有些系统上，所谓慢速系统调用会被信号中断。比如 read：内核不会干等数据到达，它给磁盘控制器发请求后就调度别的进程，等中断宣告数据到达后 read 才完成返回，所以 read 相当于分成了两段。在这类系统上，如果慢速系统调用完成之前进程收到了信号，内核会中止这个系统调用，返回一个 EINTR 错误。用户什么也没做错，只是倒霉被某个信号打断了，代码里却得检查这种情况并重做，即把 read 放在循环里一直重试直到成功，这很麻烦。还有些系统不阻塞与正在处理的信号同类型的信号。

解决办法是用一个较新的系统调用 sigaction 替代 signal，它提供可移植、可预测的信号处理。O'Hallaron 写了一个包装函数，叫大写的 Signal，参数和 signal 一样，内部调用 sigaction。细节不重要，要点是代码里总用 csapp.c 里的 Signal 包装函数，这样就总会阻塞与正在处理的信号同类型的信号，被信号中断的慢速系统调用会被自动重启。

七、并发带来的微妙错误

竞争：先删除、后添加

一个维护作业列表的简单 shell：每创建一个子进程就把它加进作业列表，子进程终止时把它删掉。主循环里，shell 创建子进程并在其中执行程序；父进程正确地在把作业加入队列时临时阻塞所有信号，加完再解除阻塞。SIGCHLD 处理程序也操作这个队列：它回收所有已终止的子进程，并把每个对应的作业从队列里删除。这是一个经典情形：两条并发流（主程序和处理程序）访问同一个共享数据结构，并且两边都正确地在更新时阻塞了信号。可它仍然有一个很微妙、很讨厌的 bug。

课上有同学说中了：子进程可能在父进程把它加入队列之前就终止了吗？可能。对父子进程的执行顺序和各自运行多久，不能做任何假设。fork 返回后完全可能先运行子进程，并且在父进程有机会把作业加入队列之前，子进程就终止了。于是处理程序去删除一个尚未加入队列的作业，之后父进程终于运行，把这个作业加了进去，它永远不会被删除。O'Hallaron 说，这就是并发里那种微妙、讨厌、可怕的 bug，要追踪所有可能的事件交错会让人头疼，只要有并发流访问共享资源就会出现，信号处理程序也不例外。后面讲线程时会讲处理这类共享的系统化方法。

修正：无法控制父子进程谁先运行、子进程运行多久，但能控制 SIGCHLD 处理程序何时运行，因为可以阻塞信号。所以在创建子进程之前，就用 sigprocmask 阻塞 SIGCHLD；然后 fork；子进程默认继承父进程的阻塞位向量，fork 返回后它的 SIGCHLD 也是阻塞的，如果不管，它将来创建的子进程就无法通过 SIGCHLD 处理程序回收，所以子进程在 execve 之前先解除对 SIGCHLD 的阻塞，这就是上一讲提到的"把创建进程和执行程序分开"的用处；父进程在调用 addjob 加入作业之后，才解除对 SIGCHLD 的阻塞。这样即使子进程终止得很早，处理程序也要等作业加入之后才会运行。这个场景和 shell 实验直接相关，O'Hallaron 提醒别犯这个错。

显式等待信号

shell 实验里还需要另一件事。前面的简单 shell 在主程序里用 wait 等前台作业，但真正的 shell 让 SIGCHLD 处理程序负责所有的回收，wait 必须放在处理程序里，不能放在主程序里。那主程序怎样知道前台作业结束了？可以让 SIGCHLD 处理程序回收前台作业时，把它的 PID 写进一个全局标志 pid（处理程序只设置一个标志就返回）。主程序里：像前面一样先阻塞 SIGCHLD，避免父子进程之间的竞争；创建子进程；父进程把 pid 设为 0；解除对 SIGCHLD 的阻塞；然后用 while (!pid) ; 空转，等处理程序把 pid 设成非零。这是正确的，但极其浪费：在一个紧凑的空转循环里不停执行，不知道要转多久，白白消耗宝贵的处理器周期。

历届 213 学生想过的其他办法：

  • 空转循环里改为 pause，等 SIGCHLD 处理程序运行后再回去检查 pid。仍然要放在循环里，因为还有 SIGINT 等别的处理程序，它们运行也会让 pause 返回，所以要反复检查是不是那个特定的处理程序运行了。但这是错的，有竞争：有同学指出，如果信号恰好在检查 pid 之后、pause 执行之前被接收，处理程序把 pid 设成非零，接着 pause 执行，就会永远阻塞，等一个已经来过、不会再来的信号。这种情况不太可能，但可能，代码看起来无害，程序却可能永远挂住。
  • 把 pause 换成 sleep(1)：检查 pid，睡一秒，回去再检查。正确但太慢，一秒是漫长的时间。nanosleep 可以按纳秒睡，但取什么值？太大就慢，太小又低效。

sigsuspend

正确的做法是 sigsuspend(&mask)。它相当于以下三步的不可打断版本：先 sigprocmask(SIG_SETMASK, &mask, &prev)，再 pause()，最后 sigprocmask(SIG_SETMASK, &prev, NULL)。原子性在于前两步不能被打断，总是一起执行，所以设置掩码和 pause 之间不可能插进一个信号；信号到来、处理程序执行完使 pause 返回之后，再把掩码恢复成原来的样子。

等待信号的正确写法：创建子进程之前阻塞 SIGCHLD；创建子进程；此时 SIGCHLD 仍被阻塞，处理程序不可能运行，安全地把全局变量 pid 设为 0；然后在 while (!pid) 循环里反复调用 sigsuspend(&prev)，用的是阻塞 SIGCHLD 之前保存的那个掩码，SIGCHLD 在其中是未阻塞的。所以在 sigsuspend 内部，SIGCHLD 被解除阻塞，处理程序可以被执行，而由于前两步的原子性，这一切是安全的。sigsuspend 里隐含的 pause 也可能被别的信号（比如 SIGINT）打断，那样就回到循环顶部，发现 pid 仍是 0，再带着解除阻塞的 SIGCHLD 进入 sigsuspend。这就是想要的行为：既不浪费资源，又消除了竞争。

八、非本地跳转

非本地跳转是 C 里一个怪异的东西，允许一个函数返回到并没有调用它的另一个函数。O'Hallaron 课上没有展开，书里和课件末尾的补充页有介绍。它由 C 标准库的一对函数提供：setjmp 把当前的调用环境（寄存器、栈指针、程序计数器等）保存在一个缓冲区里，第一次调用时返回 0；之后在任何地方（哪怕是深层嵌套的函数里）调用 longjmp 并传入这个缓冲区和一个非零值，就会恢复那个环境，使控制从当初那次 setjmp 处"再返回一次"，这次返回的是传给 longjmp 的值。setjmp 因此是"调用一次、返回多次"，longjmp 是"调用一次、从不返回"。典型用途是从深层嵌套的调用中直接跳出去做错误处理，而不必逐层检查返回值；也可以配合信号处理程序，让程序收到信号后跳回某个已知位置重新开始，这需要信号版本的 sigsetjmp 和 siglongjmp。
