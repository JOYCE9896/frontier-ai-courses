第二十二讲：网络编程（下）

getaddrinfo 怎样同时支持 IPv4 和 IPv6，hostinfo 程序逐行解读，客户端的 open_clientfd 和服务器的 open_listenfd，迭代式回声服务器的演示与代码，用 telnet 测试服务器，HTTP 与 Web 的基本概念，用 telnet 手工发一个 GET 请求，Tiny Web 服务器怎样提供静态内容，以及 CGI 动态内容的工作原理

主讲：Randal E. Bryant
资料来源：课堂录像（2015 年 11 月 12 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件
教材对应：CS:APP 第 11.4 到 11.6 节

一、这些 API 要反复看

Bryant 开场说，上一讲已经看到，这套 API 又大又乱，要花很多时间。他自己的经验是：看代码、看例子、读文档，来回反复十几遍才真正吃透。看示例代码帮助极大，书里和课程的 csapp.c 里都有，他讲多少天也替代不了自己花时间钻研。

上一讲演示的 hostinfo 程序，把域名（如 www.cmu.edu）翻译成 IP 地址（IPv4 是 32 位地址，通常写成点分十进制）。这次他只做了一处很小的改动：书的第三版新引入的 API 让写一份同时适用于两个版本互联网协议的代码变得容易。用改过的程序查 Facebook，返回了两个地址：一个是熟悉的点分十进制，每个数代表一个字节；另一个是 IPv6 地址，128 位即 16 个字节，通常写成十六进制、每两个字节用冒号隔开，双冒号表示中间是 0。Facebook 很可爱地在它的 IPv6 地址里嵌进了 face 这串十六进制。他在家里查和在这里查结果很不一样，重复查询结果也会变，因为这些大公司在全世界部署服务器，用多个服务器地址轮换，来平衡流量，不同的人会被不同的机器服务。谷歌给了他两个 IPv4 地址和一个 IPv6 地址，Twitter 给了四个不同的 IPv4 地址。

再回顾一下那张大图：服务器必须先存在，客户端才能联系它；客户端像打电话一样发出连接请求，服务器接受，就开始会话，两台机器在互联网连接上来回通信，这个例子里两端都像在读写文件；客户端完成后断开，像挂电话；服务器读的时候收到 EOF，就关闭这条连接。Bryant 纠正上一讲的说法：服务器这时并不关闭自己，只是回去接受新的连接请求，这叫迭代服务器，一次只能处理一个客户端，后面会讲能同时处理多个连接的多线程服务器。

二、再看 getaddrinfo

客户端和服务器的第一步，都是那个又乱又新的 getaddrinfo。它像一把瑞士军刀，有无数功能，吸收了很多原本独立的旧接口：无论 IPv4 还是 IPv6 用法基本一样；能从域名查到 IP 地址，也能反过来；能查 HTTP 服务对应的端口号，等等。所以它是个参数和功能都多得吓人的 API。

回顾一下：表示连接的数据结构是 sockaddr，无论 IPv4 还是 IPv6，这是 C 版本的子类型，靠强制类型转换实现。通用套接字地址只需要知道开头两个字节表示套接字的类型；IPv4 版本的 sockaddr_in 需要两字节的端口号和四字节的 IP 地址，即使在小端机器上，它们在结构里也按大端顺序存放。getaddrinfo 一个很好的特性，是基本免除了程序员操心字节顺序：传端口号时传它的十进制字符串，函数会自动转成 16 位整数并放成正确的字节顺序；把 32 位 IP 地址变成点分十进制也一样。

它的参数有的是输入、有的其实是输出：第一个是主机名，可以是域名、点分十进制，也可以是那种带冒号的 IPv6 地址；第二个是服务，查 IP 地址时通常传空指针。一般两者之中一个是字符串、另一个是空指针，因为同一个函数既可以用来查"HTTP 的端口号是多少"，也可以查"www.cmu.edu 的 IP 地址是多少"。hints 是传进去的，在一大堆信息里填上一小部分，说明这次请求具体要什么，比如要 IPv6 的还是 IPv4 的；最后它返回一个结果链表，所以传的是指针的指针，返回链表是因为 IP 地址和域名之间可能是多对多的映射。用完后调用 freeaddrinfo 释放链表的所有元素，不必自己一个个 free；gai_strerror 帮助解读错误码。

结果链表的元素是 addrinfo 结构，字段多得很，有的会用到、有的不会。传入 hints 时也用这种结构，有些字段是你填的，有些是它返回的，所以用起来有点让人困惑。它返回的有些字段可以直接用于调用套接字库的其他函数，于是你不必操心 sockaddr_in 的格式、怎样转成网络字节序，它都替你做了。反向的 getnameinfo：给它一个地址，它返回关于这个地址的信息，可能包括域名。第一个参数是一个 sockaddr 结构（课程和书里用 typedef 起了别名 SA，免得到处写 struct sockaddr）。传入一个 32 位 IP 地址，可以让它返回点分十进制形式，也可以让它查 DNS、返回域名。

hostinfo 逐行看

hostinfo 只做一件事：在命令行给一个域名，返回 IP 地址列表。这基本就是用 getaddrinfo 写代码的套路：先把 hints 整个清零，再设置需要的字段。课件里的版本只要 IPv4 连接，用 sockets 接口定义的常量 AF_INET；还要求 TCP 连接，即 SOCK_STREAM，前面说过，世界上 99% 的 IP 流量走的是 TCP，它在收发包之上提供了更高一层的抽象。然后调用 getaddrinfo：名字直接取自命令行，在演示里总是一个域名；服务传空指针；hints 说明要什么；listp 会成为指向返回结果的指针。

拿到链表后（里面可能有多个 IP 地址，也许只有一个，也许一个都没有），遍历它，取出每个地址的点分十进制形式，或者 IPv6 那种冒号隔开的形式（Bryant 坦白不知道那叫什么，他对 IPv6 知道得相对不多）。用的是 getnameinfo：它通常用来从套接字地址反查域名，但最后一个参数是标志，传 NI_NUMERICHOST 告诉它"我要的不是域名，而是数字形式"，再传一个缓冲区和它的大小，它就把地址的字符串表示填进去。也就是说，从每个链表元素里的 sockaddr（里面嵌着四字节的 IP 地址），翻转字节顺序并转成点分十进制。有同学问 p 为空会怎样：那就不会继续了，这是一个以 NULL 结尾的链表。

这次的改动只是把 hints.ai_family = AF_INET 这一行注释掉，即不再强制要求 IPv4，它就会返回这个域名支持的所有 TCP 连接，包括 IPv6 地址。Bryant 说，得相当书呆子才会觉得这很酷，而他确实很书呆子：可以这样写代码，无论互联网协议是哪个版本，都是同一份代码。

三、客户端：open_clientfd

按时间顺序其实应该先建立服务器，但客户端少几个调用，代码更容易懂，所以先讲它，假设外面已经有个服务器在等我们连接。拆开来看这张图也没那么吓人了：getaddrinfo 用来从服务器的名字得到 IP 地址；socket 是本地调用，为这个连接分配一些数据结构；connect 像拨电话，真的通过互联网给服务器发信息说"我想连你"；服务器接受后，会话就开始。

open_clientfd(hostname, port) 的做法：调用 getaddrinfo，这次给更多提示，因为要指定连接的更多特性：要 TCP 连接（SOCK_STREAM）；用 AI_NUMERICSERV 说明端口参数是数字形式，也可以传 http、ssh 这类服务的标准名字的字符串，这里用的是一种比较特别的用法；再加上书里推荐使用的 AI_ADDRCONFIG（课件说明它让连接只使用本机已配置的地址类型，书里有解释）。返回的链表基本就是一串 IP 地址，然后逐个尝试：拿这个地址试一下，失败就试下一个，比如 Twitter 那四个地址会一个个试。对每个地址调用 socket，它要的参数全都来自 getaddrinfo 的结果，你不必记着"这个数字要是网络字节序的 short"之类的事，直接把函数调用返回的信息传进去就行。socket 返回一个文件描述符，之后就像通过文件那样和网络代码打交道；它在互联网上什么也不做，操作系统里也几乎不费什么力气，只是分配一些本地数据结构，很少会失败。真正干活的是 connect：用 getaddrinfo 提供的参数尝试连接服务器，如果服务器不可用或者因为某种原因不接受你，就会失败。成功就跳出循环，否则关掉这个套接字，试下一个。最后释放链表，返回客户端的文件描述符；如果所有地址都试完都没连上，返回失败。

四、服务器：open_listenfd

服务器端前两步一样，需要一个套接字，但还要建立一个在特定端口上监听客户端请求的服务器，这是 bind 和 listen 的作用；accept 表示"服务器准备好了，我可以接受请求了"，它会停下来、无限期地等待，直到有连接请求进来。如果服务器没有任何客户，它可能永远等在 accept 上，其他调用都是一路执行下去的，真正的等待只发生在这里。顺带一提，connect 也会挂起等待连接形成，但通常内置超时，太久就失败，两者都可以调整等待的参数，这里说的是典型情况。

open_listenfd(port) 同样要调用 getaddrinfo，这次不是因为需要谁的 IP 地址：本地服务器已经有地址了，通常也不会事先知道客户端的地址，但要靠它填好那些麻烦的数据结构。提示里说：要 TCP 连接；要一个可以接受任何 IP 地址连接的被动套接字（AI_PASSIVE），即不是主动去联系别人，而是被动等待连接请求；端口号是数字形式，这就是服务器要用的端口。调用时主机名传 NULL，因为自己就是主机，只给端口号和提示。

课上的几个问答：memset 是把一段字节都设成某个固定值的标准做法，和以前用 bzero 清零是一回事，网页上建议用 memset、不再用 bzero，这里没有分配任何东西，hints 是一个结构体，也就是一串字节，调用 memset 就把它的每个字节都设为 0；AI_PASSIVE 表示这将是一个监听用的连接；AI_ADDRCONFIG 是个相当冷门、甚至不是必需的参数，Bryant 一时想不起细节，书里有。他也指出一件有意思的事：两边的代码都没有写 AF_INET，没有强制成 IPv4 代码，同一份代码对 IPv4 和 IPv6 都能用。

返回的链表通常只有一个元素，Bryant 也不清楚为什么会有更多，但处理方式一样：调用 socket 创建服务器用来监听连接请求的文件描述符；再用 setsockopt 设置一个比较冷门的选项，让服务器重启后端口能更快被释放、重新使用，书里有解释。真正的工作是 bind：把这个文件描述符和 getaddrinfo 填好的信息关联起来，其中最重要的是端口号。端口是这台机器上所有应用共享、也在争抢的资源，bind 是请求"这个端口给我用来建服务器"，如果端口已被占用，或者想在不允许的端口上建服务，比如没有 root 权限却想用 80 端口，就会失败。bind 成功后，只是在机器内部说"同意，这个进程可以在这个端口上监听"，但还没真正开始监听。Bryant 说不知道为什么要分成两步，但就是要分：还得显式调用 listen，说"现在我真的准备好接收连接请求了"，参数是允许排队多少个连接请求，超过就开始拒绝。这是个性能参数：设得太小，除非服务器很快，否则别人的连接请求会失败；太大又容易遭受某些拒绝服务攻击。最终返回一个文件描述符，服务器用它接收连接请求。

五、回声服务器

例子是一个很平淡的应用：回声服务器，把收到的东西原样发回去，代码在书里和课件里。Bryant 在自己的笔记本上启动迭代式回声服务器 echoserveri，让它用端口 15213，这是随便挑的。自己做实验时，一般挑 1000 以上的端口，端口号限于 16 位无符号整数，最大六万五千多。在公司环境里端口通常都被锁死，不允许这样做，CMU 的政策相当宽松，这里其实只在 localhost 上做。

运行客户端后，服务器说"收到来自 localhost 的连接，端口 55457"，这就是分配给客户端的临时端口，服务器用的是 15213。上一讲说过，一条连接由两端的主机和端口确定，客户端一侧通常分配临时端口，只给这次会话使用。然后就是回声服务器"惊人的功能"：输入什么，就返回什么。消息发到服务器，服务器读到后马上发回，客户端再读出来打印到屏幕上，这几乎是能想到的最简单的功能，服务器还会打印"收到了多少字节"，表明它确实在做事。输入 Ctrl-D 发送 EOF，客户端退出，服务器断开这条连接，什么也不显示；再启动一次客户端，这次分配了另一个临时端口。但一次只能服务一个：如果在一个客户端连着时再开一个，新的客户端就会挂住，拿不到连接，因为服务器一次只能处理一个客户端。

客户端代码

真正麻烦的部分是前面那些函数，应用本身很简单。echoclient 调用 open_clientfd，给出主机名和服务器的端口（这里是 localhost 和 15213），初始化一个用于网络通信的 RIO 缓冲区。循环里：用 fgets 读入键盘输入的一行，不是 NULL（即没遇到 EOF）就用 Rio_writen 写到客户端文件描述符上，这就是通过网络发送，即写那个描述符代表的套接字；然后用 Rio_readlineb 从同一个描述符读服务器的回应（RIO 的结构里记着用哪个描述符），放回同一个缓冲区；再用 fputs 打印到终端上，换行符也包括在内。buf 既是发送缓冲区也是接收缓冲区。要点是：套接字就像文件一样，既用来发，也用来收。

服务器代码

服务器代码稍微麻烦一点，因为要支持那些"惊人的功能"。有一个奇怪的结构 sockaddr_storage，它也是这套通用 API 的一部分，提供一个足够大、能放下任何类型套接字地址的缓冲区，这里用来存客户端的地址。在一个无限循环里调用 accept，它挂起等待客户端联系；返回一个新的已连接描述符 connfd，它和监听描述符 listenfd 不同，原因在这份迭代代码里看不出来，但设想一个要同时维持一千个连接的服务器：有一个描述符用来接新的请求，其余的分别对应正在通信的各个客户端。accept 还把客户端的信息填进那个地址结构，再调用 getnameinfo 由它得到客户端的主机名和端口字符串（填进两个缓冲区，传入缓冲区的指针和长度），打印出连接从哪里来，演示里看到的那行信息就是这样来的。然后调用 echo 函数，结束后关闭 connfd，回到循环开头，这个程序要用 Ctrl-C 才能退出。

echo 函数和客户端很像，只是读写反过来：从已连接描述符读一行，读到的字节数不为 0 就打印收到多少字节、再原样写回去；读到 0 说明遇到 EOF，就跳出这个小循环。echo 本身又在接受新连接请求的大循环里。读是接收客户端的信息，写是把信息发回给客户端。

用 telnet 测试

想测试程序时，可以用 telnet。它是 SSH 出现之前和别的机器通信的老办法，完全不安全，所以千万别真用它登录，现在大多数地方甚至连不上用 telnet 的连接，Bryant 感叹以前的生活多简单。但比如 telnet 到自己机器的那个端口，就开始一次会话，而且看起来很像一个回声客户端：telnet 把输入发给服务器，服务器设计成原样发回，telnet 再把回应打印出来。这个程序本身很简单，但真有时候，外面某处有个服务器，你想戳一下看看它在干什么，就可以用 telnet。用 Ctrl-] 退出，再输入 quit。

六、Web 和 HTTP

上面就是创建客户端-服务器应用所需的底层套接字编程基础。最好的客户端-服务器应用例子是万维网：Web 服务器，以及作为客户端的浏览器。它的协议建在其他互联网协议之上：TCP 建在最底层的包协议之上，HTTP（超文本传输协议）又建在 TCP 之上，用 TCP 连接在 Web 上收发数据。这套协议由 Tim Berners-Lee 在 90 年代初开发，经过几次修订，最新的版本 HTTP/1.1 仍是 1999 年的（课件发布于 2015 年）。

  • 内容类型：HTTP 的巧妙之处之一是能处理不同格式，可以发 JPEG 图片、文本等等。它们按一种叫 MIME 的格式标注类型，课上 Bryant 把它描述成一种把二进制值编码成字符串的方式，以及一端怎样编码、另一端怎样解码的标准；发送时要说明这是什么类型的信息，比如 text/html、image/gif、image/jpeg。
  • 静态内容和动态内容：传统上，静态内容是固定的网页，用 HTML 写成，每次看都一样；动态内容会变，比如一个提供天气的服务器应用，每次的页面都不同，你请求时它才生成。Bryant 说这有点过时了，如今因为 JavaScript 等在客户端执行代码、来回通信获取结果的语言，情况复杂得多，但无论哪种情况，真正在线路上传的都是某种文件。
  • URL（统一资源定位符）：由几部分组成：用域名（可能带端口号）说明信息在哪台主机上；以及在那台主机上的什么位置；如果什么都不给，有默认值，比如 index.html。前面已经见过 DNS 的种种花招，给的虽然是一个主机名，背后可能是很多台服务器，但概念是一样的。

浏览器想看一个网页时，向服务器发一个 HTTP 请求，让它做某件事、返回一个网页。有几种标准方法，最常用的是 GET，九成以上都是它，意思是"把页面给我"，此外还有 POST、OPTIONS、HEAD 等。服务器回一个响应行，响应里嵌着你要的东西，但前面有一个头部，里面有各种你可能关心也可能不关心的信息；也可能返回一个错误码，比如臭名昭著的 404。

用 telnet 手工发请求

Bryant 用 telnet 连到计算机系的 Web 服务器（端口 80），手工输入一个 HTTP 请求，即 Web 服务器看到的原始字节：GET /~bryant/test.html HTTP/1.1，这是他专门为此做的一个很简单的网页，要求用 HTTP/1.1 格式回应；还必须显式写一行 Host: www.cs.cmu.edu，因为一台机器可能为多个主机名服务，比如向 GoDaddy 付费托管一个域名，它同时服务成百上千个域名，要靠 Host 信息判断这是哪个客户的网站；最后输入一个空行。他说每次真的能成功都会让他惊讶。

响应：状态码 200，表示接受了，即 OK；接着是头部：日期、服务器、一些 cookie 信息，内容总长正好 479 字节，类型是 text/html；头部之后是空行，然后是那个网页的原始 HTML；最后关闭连接。这既返回了头部信息，也返回了实际内容，这就是一次 HTTP 事务的样子，课件里有另一个类似的例子。

七、Tiny Web 服务器

书里有一段很有意思的代码，Bryant 强烈推荐阅读和研究：Tiny，"世界上最小的能工作的 Web 服务器"，只有 239 行，处理静态和动态内容最基本的部分，可以坐下来通读。它缺很多功能，错误处理做得很差，缺少一般服务器应有的大量功能，被删到只剩骨架来演示概念，但它能工作，这很酷。Bryant 说他可以这么夸，因为不是他写的。

Tiny 作为服务器，接收浏览器"我要这个网页"或"我要执行这个动态程序"的请求：请求进来，比如刚才那种 GET，它取出请求的参数，即 URI（统一资源标识符）。URI 是 URL 的超集，URL 必须包含主机名和从任何地方到达任何地方所需的全部信息，URI 可以只是其中一部分。然后判断这是静态内容还是动态内容的请求。

提供静态内容

静态内容只需取出本机上的一个文件，按刚才看到的格式发回去。serve_static 是 Tiny 的一个辅助函数，它拿到的是：从 URI 解析出的文件名、通过系统调用查到的文件大小，以及这条连接的文件描述符。它用一串 sprintf 往一个缓冲区里写，把头部格式化成一个长字符串：响应行 200 OK、服务器名、连接关闭、内容长度（字节数，必须给）、内容类型。另一个辅助函数 get_filetype 判断文件的 MIME 类型，因为 Tiny 不只支持文本，还支持 GIF 和 JPEG 图片。Bryant 吐槽，不知道是 Tim Berners-Lee 的大智慧还是谁定下的，每一行都必须以回车加换行结尾，而不是 Linux 通常只用换行，所以代码里每行末尾都是 \r\n。然后把头部写给客户端。再打开文件，用 mmap（虚拟内存那一讲讲过，Bryant 一时记不清大家学过没有）把文件映射进内存，避免先把文件读进来再放进另一个缓冲区那一步多余的复制；然后把映射区域直接写给客户端，写完解除映射。也可以用普通的 read 实现，这样做更优雅一些。注意内容长度是文件的长度，不包括头部的字节数；头部本身不带长度，客户端只能靠从头部里取出这个数字，才知道接下来要读多少字节的响应。

提供动态内容

动态内容让你把参数传给一个程序去执行，由那个程序生成一个网页发回给你。Tiny 内置了一个演示：浏览器访问 localhost:15213，即本机上正在运行 Tiny 的 15213 端口，唯一的网页是一张"惊艳"的图，表明它能处理 GIF 和 text/html；它还支持一个能把两个数相加的程序，Bryant 开玩笑说这是"adder.com"，一个没能成功的创业点子。它是一个 CGI 程序：两个数嵌在 URL 里，比如 localhost:15213/cgi-bin/adder?15213&18213，返回一个"排版漂亮"的网页。URL 里 cgi-bin 是这个服务器（以及大多数服务器）约定的动态内容目录，adder 是一个可执行文件，参数串用问号开头，用 & 分隔各个字段，这是处理动态内容相当标准的方式，如今有更花哨的方法，但它至今仍在使用。

过程：一个 GET 请求进来，路径里是 cgi-bin，后面的部分被解释为文件名；服务器用大家在 shell 实验里已经很熟悉的 fork 和 exec 派生一个进程，执行这个程序；程序的任务是生成一个 HTML 文件；服务器把结果发回客户端。要让它工作，有几个细节要解决：参数怎样传给程序、程序怎样知道参数是什么；程序生成的 HTML 怎样交回服务器、让服务器发给客户端。这些就是 CGI（通用网关接口）规范规定的内容。

  • 客户端怎样把参数传给服务器：参数附在 URI 里，程序名后面用问号作结尾，参数之间用 & 分隔；参数里不能有空格，空格写成 %20，这叫转义码，某个字符不能直接用时，用别的方式编码它。
  • 服务器怎样把参数传给子进程：方式很怪：在 fork 出的子进程里，设置一个叫 QUERY_STRING 的环境变量，比如值为 15213&18213，CGI 程序再从环境变量里取出这个字符串。看起来似乎有问题：同时跑多个服务器怎么办？其实不会冲突，环境变量是每个进程各自的，所以应用程序能从操作系统那里取到传给它的参数。
  • 服务器怎样拿到子进程的输出：serve_dynamic 先向客户端写回响应行和几行头部；然后 fork，在子进程里设置 QUERY_STRING，用 dup2 把子进程的标准输出重定向到客户端的已连接描述符，再调用 execve 运行那个程序；父进程等待子进程结束。所以 CGI 程序往标准输出写的任何东西，都直接写给了客户端。

adder 程序本身：从 QUERY_STRING 里取出两个数，生成要发回的 HTML，这里很平淡，唯一的 HTML 标记是表示段落的 <p>，把这些内容存在一个叫 content 的字符串里。服务器已经写好了顶部的头部，adder 还要告诉客户端内容的类型和字节数，用 strlen 算出长度，打印 Content-length 和 Content-type 两行头部、一个空行，再打印内容，最后 fflush 确保都发了出去。也就是说，生成 HTML 并把它发回客户端，是 CGI 程序的工作。

Bryant 最后用 telnet 连到本机运行的 Tiny，手工输入 GET /cgi-bin/adder?17&13 HTTP/1.0，请大家现场挑两个数字，他说"没有多少次机会，所以要再核对一下自己在干什么"，结果成功了。返回的前三行是服务器代码生成的（OK 和服务器信息），Content-length 和 Content-type 是 CGI 程序 adder 生成的，后面是刚才看到的那段 HTML。

他评价说，大家谈起早期万维网时（后来它复杂得多）常说：Tim Berners-Lee 最了不起的地方，是想明白了它可以多简单。当时别人在研究让不同代理在互联网上互相对话的复杂得多的方法，而他发现：用标准的套接字接口把几个现成的想法拼起来，定一个相当直接的协议，处理不同的内容类型，用每次 fork 一个进程的方式建立动态内容。这种做法效率低得离谱，为了加两个数就 fork 一个完整的进程，简直荒唐，不过 adder.com 也一样荒唐。但他把一些已有的想法组合起来，认识到人们会从中得到的价值，把互联网从书呆子们互相交流的工具，变成了今天大家熟知的一切，是巨大的一步。即使从技术角度看它相当直接，Bryant 也给他完全的赞誉。
