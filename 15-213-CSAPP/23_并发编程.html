第二十三讲：并发编程

为什么并发难（竞争、死锁、活锁、饥饿与公平），迭代服务器的根本缺陷，三种实现并发流的方法：基于进程、基于事件（I/O 多路复用）、基于线程，进程式回声服务器及其注意事项，事件驱动服务器的工作粒度问题，线程是什么、和进程有何异同，Pthreads 接口与 hello world，线程式回声服务器，分离线程，以及一个因传错指针而产生的竞争

主讲：David R. O'Hallaron
资料来源：课堂录像（2015 年 11 月 17 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件

一、应用级并发

这一周要学怎样在程序里引入并发。之前见过的并发有进程和异常处理程序：进程是同时运行多个独立应用程序的机制；而应用程序内部也存在并发，信号处理程序就是一条和主程序并发运行的流。即使是没做多少事的信号处理程序，也很难推理，人脑倾向于按顺序思考，同时发生多件事就很难推理。根本原因是：要真正推理两条并发流，必须考虑它们所有可能的交错方式，而交错的数量随流的数量呈指数增长。shell 实验里就遇到过：主程序和信号处理程序两条并发流共享作业列表这个资源，必须很小心，防止在它处于不一致状态时被访问。这一周和下周要以更有原则的方式讨论这种应用级并发。

只要多条流访问共享资源，各种坏事就会发生，四十年来一直是计算机科学研究的对象：

  • 竞争：结果的好坏取决于某个任意的调度决定。shell 里的例子是：子进程恰好因为内核的调度先运行并结束，父进程还没来得及把它加进作业列表。又比如两个人同时访问航空公司的订座系统，谁拿到座位，取决于订座系统里的各种调度决定。
  • 死锁：多条流在等一个永远不会发生的事件。在信号处理程序里用 printf 就是一例：主程序里的 printf 拿到了某个系统资源的锁（O'Hallaron 认为是终端的锁），之后被信号处理程序打断，处理程序里的 printf 也想拿这把锁，但拿不到，因为主程序的 printf 要等处理程序返回才能释放，而处理程序要等拿到锁才能返回。现实中的例子：假设所有司机都严格守规矩，四向停车路口的规则是先到先走，如果四辆车恰好同时到达，就没有谁是第一个，谁都不走，大家都在等一个永远不会发生的条件。
  • 活性、饥饿和公平：饥饿是你想做某件事，却一直没有进展，因为活总是被别人拿去。比如有两个进程，内核总是调度 A 而不调度 B，B 就被"饿死"了，这样的调度策略就是不公平的，没有让系统中的每个实体都得到合理的一份处理器时间。

因为交错数量的指数爆炸，并发是一个很深、很难的课题，课程不可能全讲，但会讲一部分，让大家知道怎样在程序里合理地引入并发。

二、迭代服务器的根本缺陷

研究应用级并发，课程用服务器作为动机，因为不用并发就写不出正确的服务器。到目前为止看过的服务器都是迭代的，一次只处理一个客户端的请求，处理完才去处理下一个。以迭代回声服务器为例：每个客户端发连接请求，向服务器写一行文本，等服务器回显，在这个简单例子里随后就关闭；服务器等待连接请求并接受，然后读，等客户端写东西到连接上，再回显，再等下一行，直到客户端关闭连接，服务器才关闭这条连接，只有这时才再次调用 accept 等待下一个请求。客户端 2 也发了连接请求，但要一直等。

这里有个小细节：客户端 2 到底在哪里等？直觉上 connect 会阻塞到连接建立为止，但实际试一下会发现，connect 只是在内核里启动建立连接的过程就返回了，并不等连接真正建立；接着的 write 也立即返回，不会等到服务器读走那个字符串；它直到调用 read 等服务器回显时才阻塞。connect 能立即返回，是利用了内核可以把连接请求排队这个特性：内核在后台建立连接，应用程序继续往下走；write 不阻塞，是因为内核也能把写入的数据排队，记住它，等连接真正建立后再发出去。但 read 没法不阻塞，没有数据就不能返回。

迭代服务器的根本缺陷，也是必须用并发写服务器的原因：在回声服务器的例子里，一个客户端建立了连接，写了一行，服务器回显了；然后这个客户端不写下一行，也不关闭连接，因为用户出去吃午饭了，再也没输入任何东西。服务器调用 read，阻塞在那里等这个用户输入，可用户不见了，O'Hallaron 开玩笑说也许被卡车撞了。这次 read 会阻塞不确定的时间，而在此期间，同样想要服务的客户端 2 也只能阻塞。一个客户端就影响了系统里的所有其他客户端，谁都得不到服务；如果这是 Web 服务器，只要有一个客户端因为某种原因阻塞，其他用户就都无法访问这个网站。这显然不能接受。

解决办法是写并发服务器：用一条单独的并发流处理每个客户端的请求、和它交互。这样，即使某个客户端很慢、行为不端或阻塞了，也不会影响其他客户端，因为它们由别的并发流处理。有同学问服务器能不能把客户端的请求排起队来：O'Hallaron 说还得先 accept 那些连接才行，而 accept 调用是顺序的，没办法从其他客户端拿到数据；不过这位同学的想法很接近后面要讲的基于事件的服务器。

实现并发流有三种方法：

  • 基于进程：内核替我们处理所有调度，自动交错各进程的执行；每条流有自己私有的地址空间，彼此独立，由内核调度。
  • 基于事件：不靠内核，由程序员手工创建并交错这些流；因为是一个程序，所有流共享同一个地址空间，交错的手段是 I/O 多路复用，课上简单讲，书里详细得多。
  • 基于线程：前两者的混合，每条流用一个叫线程的东西实现，像进程一样由内核自动交错执行，又像基于事件那样，所有线程共享同一个地址空间，能访问程序里声明的所有全局变量。

三、基于进程的服务器

还是回声服务器的例子：客户端 1 请求连接后调用 fgets 等用户从键盘输入，但用户走了，它就阻塞在 fgets 里。服务器收到请求，从 accept 返回后 fork 一个子进程，由这个子进程负责和客户端 1 交互，子进程阻塞着等客户端 1 的数据，而数据永远不会来，因为用户走了。但这没关系，它不会让服务器停下：服务器 fork 完马上回去调用 accept，接受客户端 2 的连接请求，再 fork 另一个子进程和客户端 2 交互，那个子进程读到客户端发来的数据就回显，某个时刻关闭连接。行为不端的客户端 1 不再能伤害其他客户端。O'Hallaron 强调，创建并发流来和客户端交互这个思想，对于一个能工作的服务器实现是根本性的。

代码出奇地紧凑：通过 argv 传入要监听的端口；有一个监听描述符、一个已连接描述符，一个长度和一个地址变量，地址用 sockaddr_storage 以协议无关的方式声明，保证足够放下 IPv4 或 IPv6 的任何地址。先安装一个 SIGCHLD 处理程序；再用书里的 open_listenfd 在给定端口上创建监听描述符；然后进入循环，每次把 sockaddr_storage 的大小放进 clientlen，调用 accept，传入客户端地址和 clientlen 的指针；accept 收到连接请求后返回，带回连接另一端客户端的地址和这个地址的真实长度（IPv4 就是 4 字节），并返回已连接描述符，子进程用它和客户端读写交互。然后 fork：子进程关闭自己的监听描述符，调用 echo 和客户端交互，echo 返回后关闭已连接描述符并退出（这个 close 不是绝对必要，只是为了小心）。很重要的一点是：父进程要关闭已连接描述符，因为它自己不会用，只有子进程用；服务器在一个理论上永不结束的无限循环里运行，不关就会内存泄漏。SIGCHLD 处理程序要回收所有已终止的子进程，同样是为了避免内存泄漏。

accept 更细的过程：服务器创建一个监听描述符，描述符用小整数编号，比如 3，服务器阻塞在 accept 里等连接请求；客户端用 connect 发起连接请求；服务器接受，创建子进程，子进程用 accept 返回的已连接描述符（比如 4）和客户端交互。于是执行模型是：服务器进程一个接一个地监听连接请求，多个子进程并发地和多个客户端交互。子进程都是进程，彼此没有共享的状态；父子进程都继承了描述符表，都有监听描述符和已连接描述符的副本。父进程必须关闭它那份已连接描述符；子进程应该关闭监听描述符，因为用不到。

注意事项和优缺点

写基于进程的服务器其实很简单，只有几件事要记住：和任何创建子进程的程序一样，必须回收已终止的子进程，避免内存泄漏；父进程必须关闭它那份已连接描述符，否则不仅会内存泄漏，和这个描述符关联的状态还会永远留着，因为内核不会关闭这条连接。原因和文件 I/O 那一讲一样：内核为每个打开的套接字维护引用计数，fork 之后父子两个进程都在访问这个已连接描述符对应的打开文件表项，只有引用计数降到 0，连接才会关闭、这个表项才会从内核里删除，所以父子进程都得关闭这个描述符。

优点：它完成了我们要的事，能并发地和多个客户端交互；共享模型很清楚：父子进程和各个子进程之间地址空间私有，有各自的描述符表副本，共享同一张打开文件表；从某种意义上说，这是创建并发服务器最简单的方式，如果不需要共享全局变量或地址空间，就该用它。缺点：进程有额外开销，即使有写时复制这个共享地址空间的技巧，开销仍不小；而要在进程之间共享数据，得费很大功夫，比如想在多个进程之间建一个共享缓存，要么用磁盘上的文件，要么用某种内存映射，要么用还没讲过的进程间通信机制，大家最熟悉的大概是管道，它让一个进程把数据发给另一个进程，也有在进程间共享内存的办法，但都很笨拙，需要小心实现。

四、基于事件的服务器

思路：服务器维护一组活动连接，即一个存放来自不同客户端的已连接描述符的数组，外加一个监听描述符；用 select 或 epoll 系统调用（还有其他几种办法），判断这组描述符里哪些有待处理的输入。数据到达某个描述符叫一个事件，因为它改变了描述符的状态：事件一般都是某种状态变化，这里就是之前没有数据，之后有了数据、服务器可以读了。如果监听描述符上有输入，服务器就调用 accept 接受连接；对每个有待处理输入的已连接描述符，按某种顺序为它们服务，从中读取数据。

细节在书里，概念上很简单，实现起来却有点棘手：有一组活动描述符，正被用来和客户端交互；有些不活动，比如已经关闭的；还有些从没用过。用一个数组记录每个描述符的编号，用 select 或 epoll 等机制找出哪些活动描述符有输入，然后为每个描述符服务：监听描述符就调用 accept，已连接描述符就读取数据并做相应的工作，比如回声服务器就马上回显，Web 服务器可能去磁盘取一个文件返回。课件里这一页写的 clientfd 应该是 connfd。数据到达、读取、处理，这多次响应就是并发流：和每个客户端的交互都是一条并发流，并发地为各个客户端服务。虽然这是一个顺序程序，没有 fork 之类，就是一个普通的 C 程序，但写法让它自己创建了并发流。

优缺点

优点：只有一个进程、一个地址空间，可以用 gdb 这种普通调试器单步跟踪，什么都看得见、访问得到，在这个意义上更容易调试和理解；没有进程或线程的控制开销，为一个描述符服务时开销极小，唯一的开销是判断这个描述符有没有可用的输入。所以 Node.js、nginx、Tornado 这些高性能 Web 服务器都用基于事件的方法，想达到每秒一万个以上的请求，就得用这类方法。

缺点：比基于进程或线程的设计复杂得多，难写得多。最难的一点是：要决定响应一个事件时做多少工作。设想一个 Web 服务器，某个已连接描述符上有输入。最简单的做法是读完整个 HTTP 请求才返回，响应一个事件做的工作就是粗粒度的，指令很多，要读请求头的每一行；这很简单，但很脆弱：如果某个客户端行为不端，只发了请求的一半，就回到了之前的处境，一个客户端就能让整个服务器停摆。于是可以规定，响应一个请求的工作单位是读请求里的一行，读完一行就返回，交错地读各个客户端的单行，读完整个请求才发送响应。这是更细的粒度，更好、更健壮，客户端只要每次发整行，即使中途停下也不影响服务其他客户端；但它仍然脆弱，客户端可以只发半行。所以要写一个健壮的基于事件的 Web 服务器，唯一的办法是能处理不完整的行：描述符上有数据就读，有多少读多少，记住读了多少，不是完整一行就得把它缓冲起来记住。这就变得很复杂了，但这是换取低开销、易调试的模型所付出的代价。另一个缺点是它其实是一个顺序程序，无法利用多核，要提高性能只能复制多份服务器，单个服务器不能靠多核变快。

五、线程

第三种方法用线程创建并发流，和进程很像，但有重要的区别。先回到进程的传统视图：进程由内核里的上下文（内核为这个进程保存的数据）加上私有地址空间组成，地址空间里有代码、数据、堆和栈。进程上下文里，一部分和程序相关，比如数据寄存器、条件码、程序计数器、栈指针，叫程序上下文；另一部分是内核为实现进程这个概念所需的数据，叫内核上下文，比如虚拟内存的数据结构、描述符表、brk 指针。这些数据都存在内核里。

把图稍微挪一挪：把栈从虚拟地址空间里拿出来，连同栈指针和与程序相关的上下文（数据寄存器、条件码、栈指针、程序计数器），改叫线程上下文，内容完全一样；把栈加上线程上下文合起来叫一个线程；其余的不变，仍有代码和数据，仍有内核上下文。这样重构之后，就可以设想一个进程里有多个线程：每个线程保存一份自己的线程上下文，以及栈里与它相关的那一部分。所有线程共享同样的代码和数据、同一个虚拟地址空间、同一份内核上下文、同样的 I/O 结构，但各有独立的栈，局部变量这些放在栈上的东西是私有的、独立的；各有自己的程序计数器、栈指针、寄存器和条件码。唯一的不同是：进程仍有一个进程号，是内核上下文的一部分；而每个线程在自己的线程上下文里有自己的线程号。

这样，内核就可以把每个线程当作一条单独的流：每个线程有自己的程序计数器，从同一个代码段里执行代码，共享代码和数据，内核像调度进程那样调度它们。引入线程的根本原因在于：内核从一个线程上下文切换到另一个时，要保存和恢复的信息很少，只要把线程 1 的上下文存进某个数据结构，恢复线程 2 的上下文，开销很低，不必动页表、虚拟地址空间或进程上下文的其他部分。线程和进程的另一个区别是：fork 创建的进程有严格的父子层次，而线程可以看作访问同一份代码和数据的一池并发流，由内核负责调度它们，让每条流都分到处理器时间。

并发线程

和并发进程一样，两个线程的流在时间上重叠就是并发的，否则是顺序的。还是那个例子，只是把三个进程换成同一个进程里的三个线程：线程 A 运行一阵，内核把它换下运行 B；B 运行一阵，内核决定给 C 一些时间，保存 B 的上下文、恢复 C 的上下文，把程序计数器设成 C 上下文里的值，C 运行；然后内核再给 A 时间。A 和 B 在时间上重叠，是并发的；B 和 C 不重叠，不并发；A 和 C 重叠，并发。如果有多个核，每个核可以运行一个线程，就有了真正的并行。

线程和进程的异同

相同之处：每个线程和进程都对应一条逻辑流，可以和其他流并发运行，都由内核调度和做上下文切换。不同之处：线程共享除各自局部栈以外的所有代码和数据，而进程不共享这些状态，有各自私有的地址空间；其实那些局部栈也只是同一个栈区域被分给了各个线程，因为都在同一个虚拟地址空间里，一个线程可以访问另一个线程的栈，这样做不好，但是可能。线程比进程便宜，创建和回收的开销更小，主要原因是线程的上下文比进程少。在课程机器上测量：反复创建并回收进程，约两万个周期一次；创建并回收线程，约一万个周期一次。

六、Pthreads 接口

内核通过 Pthreads（POSIX 线程）接口提供线程，这是一个比较新的标准，所有 Linux、Unix 系统以及 Windows、Mac 都支持，用于操纵线程：

  • 创建和回收线程：pthread_create 有点像 fork，pthread_join 有点像 wait，但不完全一样，线程之间没有层次关系。
  • pthread_self 获取自己的线程号，类似 getpid。
  • pthread_cancel 让一个线程终止另一个线程。
  • pthread_exit 终止当前调用它的线程；普通的 exit 系统调用会终止所有线程；从线程例程 return 和 pthread_exit 类似，只终止当前线程。
  • 同步访问共享变量的函数，比如 pthread_mutex_lock 和 pthread_mutex_unlock，下一讲细讲。

线程版的 hello world

K&R 那本 C 语言参考书里，第一件事就是展示怎样写最简单的 C 程序，即著名的 hello world，这可以追溯到 1978 年这本书初版的时候，后来流行开了，学新语言或新概念时，大家总先写它的 hello world。线程版的 hello world 是 O'Hallaron 能想到的最简单的线程程序。

POSIX 规定，一个线程执行的是一个叫线程例程的函数的代码，它接受一个可选的通用指针作参数，返回一个通用指针。所以任何要传给线程的东西，都得想办法打包成一个对象再取它的地址，这样极其通用。hello 程序用 pthread_create 创建一个线程，不叫子线程，而叫对等线程，因为没有父子关系，任何线程都可以回收别的线程，无论是不是它创建的。pthread_create 创建一个执行第三个参数所指线程例程的线程，把线程号存进第一个参数所指的整数；第二个参数可以设置线程的属性，超出课程范围，总是传 NULL；第四个参数是传给线程例程的可选参数。这里就是"用名为 thread 的线程例程创建线程，不带参数"。线程例程打印 Hello, world! 然后返回，这里没有东西要返回，所以返回 NULL；想返回东西给调用者的话，可以返回一个指向某个通用对象的指针。

执行过程：主线程运行一阵，调用 pthread_create 创建对等线程，从此有两条并发流，主线程和对等线程；hello 程序调用 pthread_join 等对等线程结束；对等线程 printf 后返回 NULL，线程终止；pthread_join 随之返回，主线程继续，最后 exit 终止进程里的所有线程。

七、基于线程的回声服务器

写法和基于进程的设计很像：用 open_listenfd 得到监听描述符；在无限循环里，把客户端地址结构的大小放进 clientlen（它大到能放任何地址）；然后用 malloc 为已连接描述符分配空间，即在堆上分配一个整数大小的动态存储，用来放从 accept 得到的已连接描述符，O'Hallaron 强调这对避免一个讨厌的竞争很重要，马上会讲；调用 accept，把它返回的已连接描述符存进堆上这个位置；再调用 pthread_create，传入线程例程（就是程序里定义的一个叫 thread 的函数）和指向这个已连接描述符的指针。

线程例程解引用参数，得到真正的整数描述符；然后调用 pthread_detach 分离自己；再释放主线程 malloc 的那块内存，这很重要，必须释放才能避免内存泄漏；然后调用 echo 和客户端交互，直到客户端结束；最后关闭描述符，同样是为了避免可能致命的内存泄漏。

分离线程

默认情况下线程是可结合的（joinable）：可以被其他线程回收和杀死，终止后要用 join 回收才能释放资源，就像进程要被回收一样。分离线程不能被任何线程回收或杀死，但它终止时，内核会自动回收它的资源。默认状态是可结合的，要用 pthread_detach 把它变成分离的。这里把线程分离，就不用操心它结束时回收的问题。有同学问什么时候不该分离：分离就放弃了杀死其他线程的能力，O'Hallaron 说很难举出特别有说服力的例子，也许是这样：运行一池工作线程，每个都分到一份工作，最先完成的那个给出结果后，其他线程的结果就不需要了，这时可能想杀掉它们。

执行模型和注意事项

线程版服务器的执行模型和进程版很像：主线程一直在 accept 等连接请求；每个客户端有一个对等线程，用创建时传入的已连接描述符和它交互；每个线程有自己的栈，局部变量有独立的空间。O'Hallaron 说这就是线程真正强大的地方：声明局部变量，就能让线程互不干扰、独立运行。

注意事项：要分离线程以免内存泄漏。最大的问题是：线程的美妙之处在于共享同一个全局地址空间，共享数据结构很容易，比如用多线程构建的并发 Web 服务器，实现一个所有线程都能用的缓存很简单；但让线程好用的这一点，也就是让它棘手的地方。就像 shell 实验里的信号处理程序，只要有多条流访问共享资源，就得很小心，很容易出错，而且可能以出乎意料、并非本意的方式共享资源。比如一个线程把它栈上局部变量的地址传给另一个线程，被调用的线程就能访问调用者的这个变量，没有任何东西阻止它修改调用者栈上的局部变量，这样做很糟糕，但是可能的，你也许会忘了传的是一个局部变量而不是全局变量。

一个因传错指针产生的竞争

回到回声服务器：我们小心地 malloc 了空间来放传给对等线程的已连接描述符。直接把已连接描述符 connfd 的地址传给对等线程不是简单得多吗？简单得多，但是错的。设想 pthread_create 那里传的是 &connfd，线程例程再解引用这个指针得到描述符。有同学指出：这样对等线程就和主线程共享了同一块内存。为什么糟糕？因为这引入了一个竞争：它假定对等线程能在主线程回去拿下一个已连接描述符之前，先解引用那个指针。而在并发系统里，不能对内核怎样调度做任何假设，进程那里也一样。如果 pthread_create 之后先运行的是主线程而不是对等线程：传给对等线程的是这个客户端已连接描述符的地址，在对等线程来得及解引用之前，主线程又 accept 了一个新的连接、改写了 connfd；然后对等线程运行，解引用拿到的却是第二个客户端的描述符，于是两个线程用同一个描述符和同一个客户端通信。O'Hallaron 说这是因为非本意的共享而引入的那种很微妙的错误，根本原因正如那位同学所说，两个线程共享了调用者栈上的同一块内存。另一位同学问能不能直接把描述符本身传过去：可以，把描述符强制转换成通用指针传过去，对等线程不解引用、直接用它，这样能工作，只是有点难看。

八、三种方法小结

  • 基于进程：难以共享资源，但容易避免非本意的共享，从某种意义上更安全、更容易编程。
  • 基于事件：很底层、很繁琐，要很小心决定响应事件时的工作粒度；但对调度有完全的控制，可以决定为哪些描述符服务、按什么顺序；只有一条控制流，可以用调试器调试；但不能利用多核。
  • 基于线程：很容易共享资源，但共享本身会带来问题；比进程高效；对调度没有多少控制，不能控制哪个线程以什么顺序执行；可能很难调试，因为有些竞争极少发生，很难让它出现。
