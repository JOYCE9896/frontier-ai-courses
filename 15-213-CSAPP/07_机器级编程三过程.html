第七讲：机器级编程（三）：过程

过程调用要解决的三件事（传递控制、传递数据、管理局部数据），ABI 是什么，栈的结构和 push、pop，call 和 ret 怎样配合，前六个参数用哪些寄存器，栈帧，调用者保存和被调用者保存的寄存器约定，以及递归为什么"自然就能工作"

主讲：Randal E. Bryant
资料来源：课堂录像（2015 年 9 月 22 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件
教材对应：CS:APP 第 3.7 节

一、过程调用要做哪些事

Bryant 说，学完这一讲，炸弹实验除了最后一两关应该都能做了。这里的"过程"泛指函数、过程，以及面向对象语言里的方法。

过程调用的实现一部分靠 x86 硬件，更重要的一部分靠大家共同遵守的一套约定，叫 ABI（Application Binary Interface，应用程序二进制接口）。它是一份可以在网上找到的文档，最早在第一批 x86-64 机器开发时由一个工作组为 Linux 制定：所有编译器、操作系统、调试器等需要对机器资源达成共识的部分，都遵守这套规则。它超出了硬件本身，是软件层面的标准，"二进制接口"指的就是机器程序这一层的接口。Windows、OS X、FreeBSD 各有自己的 ABI，大部分相同，细节有差别。

即使是 C 这样不算复杂的语言，一次调用也涉及很多事。设过程 P 调用 Q：

  • 传递控制：转到 Q 的代码开始执行；Q 返回时，要回到 P 里调用 Q 的那条语句之后，而不是 P 的随便什么地方，所以必须记录返回地址。
  • 传递数据：P 传给 Q 的参数要放在 Q 能拿到的地方；Q 的返回值也要按约定交回给 P。
  • 管理内存：Q 可能需要局部变量的空间，进入时分配，返回时释放，否则内存会无限增长。

x86-64 把这三件事拆开的一个原因是尽量降低调用开销。好的编程风格（尤其是面向对象风格）鼓励写很多只做一点事的小函数，调用开销不该比必要的多。所以它只做绝对需要的事：不需要局部空间就不分配，没有参数就不传。这让教学有点麻烦，因为没有一个每次都照搬的模板，每个过程都是特例。

二、栈

栈不是一块特殊的内存，只是普通内存中的一个区域。程序用它管理过程调用和返回的状态。之所以能用栈来管理，是因为调用的性质：调用时可能需要一些信息，返回后这些信息全都可以丢掉，这就是后进先出。

x86-64 的栈从高地址开始，向低地址增长：分配更多栈空间时把栈指针减小。栈指针就是普通寄存器 %rsp，它存放当前栈顶的地址。按惯例画栈的图时是倒着画的："栈顶"画在最下面，地址从下往上增大。Bryant 承认这可能和直觉不符，但只能习惯，课件不会重画。

  • pushq 源：先把 %rsp 减 8，再把源操作数写到 %rsp 指向的地址。
  • popq 目的：先从 %rsp 指向的地址读出值，再把 %rsp 加 8，然后把值存入目的寄存器。

顺序很重要：push 要先减再写，因为原来的 %rsp 指着原来的栈顶元素，要在它下面腾出新位置；pop 要先读再加。push 和 pop 在 x86-64 里只对 8 字节操作。注意"释放"栈空间只是挪动栈指针，原来的值并没有被擦掉，仍留在内存里，只是不再算作栈的一部分。课上有同学问能不能用几条普通指令实现 push，答案是除了极少数特殊情况可以；但 call 和 ret 不能用其他指令模拟。

三、传递控制：call 和 ret

课上用 multstore 调用 mult2 的例子，看的是反汇编结果，因为要用到指令的地址。假设栈顶在 0x120（不现实，只为举例），%rip 指向 multstore 里地址 0x400544 的 call 指令。call mult2 做两件事：把下一条指令的地址（0x400549）压栈，%rsp 变成 0x118；把 %rip 设成 mult2 的起始地址（编码在 call 指令里，这条 call 有 5 字节，其中就包含目标地址）。压的必须是 call 之后那条指令的地址，否则返回后又执行 call，就成了死循环。所以 call 相当于 push 加 jump。

mult2 执行到 ret 时，ret 假定栈顶是一个要跳去的地址，把它弹出（%rsp 加回 0x120），把 %rip 设成这个地址，程序就回到 multstore 里 call 之后继续执行。有时会看到 rep; ret，其中的 rep 基本可以忽略。call 和 ret 只完成控制的部分，是过程调用三件事中的一件。%rip 不能用普通指令直接修改，只能通过 call、ret、跳转这些指令隐式改变。

四、传递数据

ABI 规定，整数和指针类型的前六个参数依次放在 %rdi、%rsi、%rdx、%rcx、%r8、%r9，返回值放在 %rax。这个顺序没什么逻辑，只能记住或者手边放张表。浮点参数用另一组寄存器传。超过六个参数时，多出来的放在栈上的内存里，被调用的函数从栈上取。IA32 时代所有参数都通过栈传递，现在改用寄存器，因为访问寄存器比访问内存快得多。

在 multstore 的代码里可以看到，它假定三个参数 x、y、dest 在 %rdi、%rsi、%rdx 里；mult2 用 %rdi 和 %rsi 里的两个参数，把结果放进 %rax 返回，multstore 接着就假定 %rax 里是返回值，把它存到 dest 指向的位置。只要大家都遵守同一个接口标准，甚至用不同编译器编译的代码也能互相调用。

五、栈帧和局部数据

在单线程模型里，任一时刻只有一个过程在执行，它只需要访问自己的数据和传给它的值（其中有的是指针，指向别处）。其余未返回的过程都处于"冻结"状态。所以可以为当前过程在栈上分配它需要的空间，返回后这些空间就不再需要。为某一次调用（一个过程的某个实例）分配的这块栈空间叫栈帧。

例子：yoo 调用 who，who 两次调用 amI，amI 是递归的，第一次会再递归调用自己两层。任何时刻，栈上只有已被调用、尚未返回的那些过程的帧：随着调用加深，帧一层层加上去，返回时一层层撤掉。每次调用 amI 都有自己的帧，所以每一层递归都有各自的局部状态。递归比迭代更费空间，栈越来越深；大多数系统会限制栈的总深度，防止失控的无限递归。

栈帧由栈指针 %rsp 和可选的帧指针 %rbp 界定。课程看到的代码一般不用帧指针，%rbp 当普通寄存器用，所以往往无法确切知道一个帧从哪里开始，只知道栈顶部分是当前函数的帧。有同学问：没有 %rbp，返回时怎么知道该把栈指针恢复到哪？答案是编译器在编译时就知道这个函数分配了多少，比如进入时减 16，退出时就加 16。只有少数编译时无法确定大小的情况，比如要在函数里分配一个大小可变的数组，才会用 %rbp。

一个典型的 x86-64 栈帧，从调用者一侧开始：调用者需要传第七个及以后的参数时，把它们放在自己的帧里；call 压入返回地址；然后是被调用者的帧，可能包括旧的 %rbp（如果用帧指针）、需要保存的寄存器、局部变量，以及为它将要调用的函数准备的参数区。通常函数开始不久就把 %rsp 减掉一个数，返回前再加回去。

例子：需要地址的局部变量

incr 函数的参数是一个 long 指针 p 和一个 long 值 val：它读出 *p 作为 x，算出 y = x + val，把 y 写回 *p，返回原来的 x。代码只有三条加 ret：从 %rdi 指向的地址读到 %rax（同时就是返回值），把 %rax 加到 %rsi 上，把 %rsi 写回 %rdi 指向的地址。

调用它的 call_incr 定义了一个局部变量 v1 = 15213，并把 &v1 传给 incr。寄存器没有地址，所以 v1 不能只待在寄存器里，必须放进内存，放在栈上。生成的代码：subq $16, %rsp 在栈上分配 16 字节；movq $15213, 8(%rsp) 把 v1 存在 %rsp+8 处。编译器经常多分配一些用不到的空间，是为了满足某些地址对齐的约定，不必在意。然后准备参数：movl $3000, %esi 把第二个参数设为 3000，虽然类型是 long，但 3000 是一个小正数，用 32 位的 movl 写 %esi 会顺带把高 32 位清零，而且 movl 比 movq 的编码少一个字节；leaq 8(%rsp), %rdi 把 v1 的地址作为第一个参数，这就是 lea 本来的用途，算出地址而不去读内存。call incr 之后，v1 变成 18213，返回值 15213 在 %rax 里；接着 addq 8(%rsp), %rax 加上 v1；最后 addq $16, %rsp 释放空间，ret。ret 之前必须把 %rsp 恢复原位，因为 ret 总是把 %rsp 指向的内容当作返回地址。

六、寄存器保存约定

设想 yoo 把 15213 放进 %rdx，然后调用 who，返回后还能指望 %rdx 是 15213 吗？一般不能，who 可能用过 %rdx。所以 ABI 对寄存器的使用也有约定。术语：发起调用的叫调用者（caller），被调用的叫被调用者（callee）。

  • 调用者保存：如果调用者在乎某个寄存器的值在调用后还在，就要在调用前自己把它存起来，被调用者可以随意改它。%rax（返回值）、六个参数寄存器 %rdi、%rsi、%rdx、%rcx、%r8、%r9，以及 %r10、%r11 都属于这一类。被调用的函数对传进来的值可以随便处理，所以这些寄存器常被当作临时存储，%rax 在设成最终返回值之前也常被多次改写。
  • 被调用者保存：%rbx、%r12、%r13、%r14 属于这一类，这是所有函数之间的一份契约：一个函数如果要改这些寄存器，必须先把原值压栈，返回前再弹回去恢复。%rbp 在使用帧指针时有特殊用途，不使用时也按被调用者保存处理；%rsp 是特殊的，不清楚自己在做什么就别碰它。

Bryant 说被调用者保存不那么直观，要过一阵才能体会它的价值。例子：call_incr2 和之前类似，但最后返回 x + v2，x 是它自己的参数。x 最初在 %rdi 里，可调用 incr 时 %rdi 要用来传新参数，调用后又要用到 x，放在哪？放在被调用者保存的寄存器里。代码一开始 pushq %rbx 保存 %rbx 原来的值，再 subq 16 分配空间（在已经因 push 占用的 8 字节之上），把 x 放进 %rbx。调用 incr 之后可以假定 %rbx 没变，因为 incr 如果用了它也会恢复。结尾先 addq 16，再 popq %rbx 恢复原值，然后 ret。可以看到进出代码像括号一样配对：push 对 pop，sub 对 add，退出时的顺序和进入时相反，这同样是栈的规律。如果函数不改这些寄存器，就不需要保存任何东西，这又是"只做必要的事"。

七、递归

递归在计算机科学里像一门魔法，但看了这些底层机制就会发现，编译器对递归函数不需要任何特殊处理，栈的规则自然就让它工作。例子是递归版的 pcount：x 为 0 时返回 0；否则返回 (x & 1) 加上对 x 右移一位后的递归结果。参数是无符号数，所以右移是逻辑右移，换成算术右移会很糟糕（负数会一直有 1 移进来）。

生成的代码：先把 0 放进 %rax，假定结果是 0；testq %rdi, %rdi 检查 x，等于 0 就 je 跳到末尾的 ret。否则：push %rbx 保存它；把 x 复制到 %rbx，用 32 位的 and 指令只保留最低位（高位顺带清零）；把 %rdi 里的 x 右移一位，作为递归调用的参数；call pcount。返回后，因为每个函数都守规矩，%rax 里是递归结果，%rbx 里仍是刚才保存的最低位（递归调用确实改过 %rbx，但返回前恢复了）；把两者相加作为返回值；pop %rbx 恢复调用者的值；ret。

回到 %rbp：如果某个函数需要帧指针（比如前面说的变长数组），它下面调用的函数，不管递归多深、做了什么，只要把 %rbp 当作被调用者保存的寄存器对待，返回时都会把它恢复原样，这个函数就总能拿到可靠的 %rbp。所以只要所有代码都遵守这些约定，一切就能互相信任地配合，这也是为什么新处理器出现时要尽早认真制定 ABI，让编译器作者、操作系统开发者、gdb 等工具的作者都有统一的标准。

为什么这套办法行得通

  • 每次调用都有自己的栈帧，所以递归很深时，其他尚未返回的调用的数据仍各自保存在自己的帧里。
  • 寄存器保存约定让函数不会破坏彼此的数据：用被调用者保存的寄存器就有义务保存和恢复，更深层的函数也有同样的义务。
  • 栈的规律和调用返回的规律完全吻合：P 调用 Q，P 返回之前 Q 一定已经返回，Q 的存储就不再需要。

互相递归（P 调用 Q，Q 又调用 P）看起来很神奇，实现方式也完全一样。Bryant 补充，有些更高级的语言（CMU 的 15-150 课程里会接触）不能依赖这种栈规律，需要让数据在函数返回后继续存在，必须用别的办法，比如在堆上分配栈帧；但 C 和其他常见语言正好适合栈，C 的设计者很清楚这一点。他最后建议：真正掌握这些，最好的办法是手工执行几个很简单的例子，或者用调试器一步步跑，亲眼确认各部分怎样拼在一起。
