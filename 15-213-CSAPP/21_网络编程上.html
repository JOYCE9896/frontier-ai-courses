一、苦学底层之后的回报

Bryant 说，网络编程对他来说是辛辛苦苦学完前面所有底层内容之后的回报：能真正理解并熟练编写网络软件。网络有大量内容课程不涉及，学校有很多专门的网络课，这里只给一点体验，而且和整门课一样站在程序员的角度：作为软件开发者，怎样使用和网络编程相关的 C 级 API。很多同学此刻正忙着让 malloc 跑起来、跑得快，这个话题更多面向将来，但和最后一个实验（代理实验）直接相关。

二、客户端-服务器模型

大多数网络系统基于客户端-服务器模型：外面有某种服务，你作为客户向服务器发出请求。比如在亚马逊买东西：亚马逊有很多服务器，你的浏览器联系亚马逊的 Web 服务器，你发请求、提供信息，它返回你可能想买的东西的漂亮图片，确认你的信用卡交易，这些都是典型的客户端-服务器交互。另一个有意思的例子是电话：它既是客户端也是服务器，我打给别人时我是客户端，对方的电话是服务器，它一直在等来电，电话打进来就建立连接，通话，任何一方挂断就结束。这个概念的内涵更丰富，双方的角色常常可以互换，但它是搭建网络系统时普遍使用的思路。

一般的流程是：客户端发请求给服务器；服务器在本地做些处理，比如从数据库取出你可能想买的东西；服务器把信息发回，比如一个排版好的购物推荐网页；客户端决定下一步做什么。客户端和服务器都是进程，它们可以在同一台主机上，也可以在不同主机上。

网络适配器像一个 I/O 设备

硬件上，网络和计算机之间的接口叫网卡（NIC，network interface card），尽管它不一定是一块卡。课程不讲硬件，最有意思的是：对计算机来说，它看起来就像一个 I/O 设备。Unix 处理网络的 API 让网络看起来像文件：磁盘挂在总线上，往里写、从里读；网络也挂在类似的总线上，发消息就是往一个叫网络的虚拟文件里写，收数据就是从里面读。所以几周前那一讲 I/O 和网络编程极其相关，这是早期 Unix 开发者建立的基本模型，后来被 Windows 等其他操作系统沿用。

三、计算机网络

网络是一组叫主机的系统，它们能通过某种通信结构互相通信。按范围大致分成局域网（LAN，一栋楼或一个校园）和广域网（WAN，一个城市甚至更大的范围）。CMU 这样一个机构的网络很复杂：这个教室里就有无线基站和你们的设备交互；学校内部有整套网络基础设施，再连到 AT&T 等商业运营商以接入商业互联网；还有匹兹堡超算中心托管的连接，接入大学之间通信用的 Internet2。做网络编程时，底下是一套惊人复杂的东西在运转。

小写的 internet 指"网络的网络"这个一般概念，比如把这个基站提供的局域网连到校园里其他网络，再连到全世界；大写的 Internet 指这个概念最重要的一个具体实例，即大家天天用的、按特定原则和协议组织起来的那个互联网。

以太网

大部分底层网络由以太网支撑。"以太网"这个词演变得太厉害，几乎更像一个品牌而不是一项具体技术。大家熟悉的有线版本：用网线插进一个盒子。历史上这种盒子叫集线器，它只是一个中继器，从一台计算机进来的东西广播给所有相连的机器，像一条合用的电话线，大家都听得到别人在说什么，所以只适合十来台机器。最早的以太网就是这样，所有主机通过一根传输类似无线电信号的电缆交互。这个房间里的无线网也像一个集线器：所有人发的包都使用同样的无线频率、同一个信道，有协议来检测两个消息同时发出而互相干扰的情况，所以最多大约扩展到一百台主机。有线世界里，从运营商那拿到的带很多端口的盒子其实叫路由器或交换机：它不广播给所有人，而是有选择地判断某条消息发往哪台主机，只发给那一台。这些盒子可以一层层连接，大约可以深达六层，组成一个有线网络，再往上还可以加更复杂的交换。从概念上，可以把以太网段想成一组能直接互相通信的主机。

互联网

互联网就是用路由器把这些局域网连起来，路由器根据要发往的地址按特定协议转发。概念上就是分布在全世界的大量主机，加上一个神奇的路由器系统，它根据一种已知的主机寻址方式，把消息经过多个路由器从一处送到另一处，无论是在校园里还是绕地球一圈。关于路由怎样工作、怎样保证可靠，有大量的知识，这里假定别人已经搞定了，程序员的工作只是让一台主机和另一台通信。

怎样设计一个系统，让不同厂商造的、在不同国家由不同电信管理机构管辖的各式系统都能协同工作？必须有协议，即一套共同的约定：消息长什么样、怎样发送、丢了怎么恢复，等等。协议首先要提供命名方式：要发给某台主机，得有办法指明是谁；其次要提供传送机制：路由系统要能可靠地把数据送到被命名的主机。如今被视为理所当然、但当初并非如此的一个思想是：把数据切成包，通常一千到两千字节，长消息被切成一个个包发送，所有通信都在包这一级进行。这和历史上的电话系统不同，那是面向连接的，打电话时电话公司会为这次通话专门保留一组线路，在整个通话期间锁定给你用。

封装

从主机 A 发一个包到主机 B：包里有一些数据，在前面加上小小的头部，里面是路由信息，相当于信封正面写的东西，在不同环节会有不同数量、不同格式的头部。具体过程：我要发一条消息；我机器上处理网络的软件先在前面加一个描述互联网路由的头部（互联网包头，PH）；再在前面加一个描述局域网路由的头部（帧头，FH1）；网卡负责把它发到本地网络上；路由器收到后剥掉 FH1、换上目标局域网的帧头 FH2，转发出去；接收端的网卡收到后逐层剥掉头部，主机 B 最终只看到发送的数据。这种"在前面加头部，其余部分只当作一串字节传下去"的做法叫封装。

IP、UDP 和 TCP

  • IP（网际协议）：规定怎样给互联网上的主机命名、怎样发送包，包有时叫数据报，即从 A 发到 B 的单个实体。IP 不保证送达，是"尽力而为"的通信：一路上情况好就转发，拥塞太严重，或者有人打开微波炉造成了射频干扰，IP 就把这个包丢掉，悄无声息，连句抱歉都不说。
  • UDP（用户数据报协议）：IP 之上很薄的一层软件，程序员可以直接用它发数据报，从进程到进程，不可靠。一般不想在这一层编程，但有些应用会这样做，比如电子游戏里要很快地发信息、丢一点也无所谓的场合。课上不讲。
  • TCP（传输控制协议）：承载了约 99% 互联网流量的协议，提供可靠的连接，相当于一条电话连接：能从 A 到 B 可靠地发送任意多的字节，保证送达，有时快有时慢。它建立在 IP 数据报之上，要把你发的东西切成单个的包，没送到就重发直到送到；包可能走不同路径、后发的先到，它要按正确顺序重新排好。底下的事很多，但可以假定它能工作，于是可以把它想成一条流连接：我从 A 发一串数据到 B，B 也能发一串数据回来。这就是看起来像文件 I/O 的那个版本：我不停地写一个文件，它在网络上把包发到另一端，对方也在给我发东西，我只是读字节，不必关心它们怎样被切成包。这就是套接字接口，"套接字编程"说的就是它。

从软硬件系统的角度看，客户端和服务器都作为应用程序运行在各自的主机上，它们使用用户态和内核态组合起来的软件和库，从而能直接访问资源。应用程序员使用的就是这套直接支持 TCP/IP 的软件 API，即套接字接口。

四、IP 地址和域名

IPv4 地址

主要讲 IPv4（第 4 版），它从 1980 年代初运行至今，是标准。IP 地址其实只是 32 位，通常写成点分十进制形式：四个十进制数，每个只能在 0 到 255 之间，因为每个数是一个字节，比如 128.2.203.179。这门课里一直写十六进制，但这里每个字节写成一个十进制数。地址按网络字节序存储和传送，即大端顺序，所以做网络编程时得操心大端和小端的事。地址的各部分有层次含义，比如以 128.2 开头的 IP 地址都在 CMU，CMU 大约拥有 $2^{16}$ 个可供校园使用的 IP 地址（Bryant 课上先口误说成 $2^{64}$ 又马上更正）。

还有一个新版本叫 IPv6，地址是 128 位。想想互联网上有多少结点：4 字节地址只有 $2^{32}$ 个，约四十亿，而 Bryant 自己就有手机、两台笔记本、几台台式机，如果每个人用好几个 IP 地址，世界早就没有地址可用了，全世界有七十亿人，不是所有人都上网，但很大一部分人上网。于是出现了各种疯狂的办法来应对有限的地址。显而易见的办法是分配多得多的地址，干脆跳过 64 位直接到 128 位，这就是 IPv6 的思路，但它已经推出十五年以上，采用率仍然很低，仍是"未来的技术"，人们想出各种花招坚守在 4 字节的限制里。

Bryant 说，这是你会希望自己不是在用 C 编程的地方，但你就是在用 C。很多软件协议在 C 发展成今天的样子之前就设计好了：大家手上的 K&R 是第二版，基于 ANSI C 或 ISO C，而这些协议可以追溯到更早的初版 K&R，那时连 void * 都没有，用 char * 当通用指针，所以这个编程接口里有很多陈旧的东西。比如 in_addr 结构体（internet address），它只包含一个 32 位无符号数。设计最初协议的人偏爱大端寻址，即使世界上大多数机器是小端的。所以有一组标准库函数在网络字节序和主机字节序之间转换：htonl、htons（主机转网络，32 位和 16 位）、ntohl、ntohs（网络转主机）。用了它们，软件在小端或大端机器上运行都会做正确的事，换机器不用改代码。没有转换 64 位数据的函数，Bryant 说不知道别人怎么办，他自己就写一个，或者干脆不转，因为知道另一端也是小端机器。点分十进制和 32 位整数之间也有转换函数：inet_pton 和 inet_ntop，p 表示"表示形式"（presentation），即点分十进制，n 表示网络形式。

域名和 DNS

想去谷歌时，你很少会想它的 IP 地址是多少，只会输入 google.com。人们用的是互联网域名，一种层次化的命名体系：.edu 用于教育机构，.com 用于商业，.net 用于一般网络，很多国家有自己的后缀，比如 .de 是德国，这些叫一级域名，下面还有层次化的名字。从这些层次化的名字映射到点分十进制或 32 位 IP 地址，由一个很庞大的分布式系统负责，叫 DNS（域名系统）。唯一集中管理的是最顶层：每个一级域名有一大批机器，记录所有映射到这个一级域名的 IP 地址；CMU 维护自己的命名权限，任何 xxx.cmu.edu 的名字，都由 CMU 内部的 DNS 服务器负责解析出 IP 地址。它是完全去中心化的，有一整套协议约束命名怎样进行，但概念上可以把它想成一个巨大的数据库：给一个域名，返回一个或多个 IP 地址；给一个 IP 地址，返回一个或多个域名。

大多数机器上都有一个程序叫 nslookup，还有一个叫 dig，可以双向探查 DNS。Bryant 演示了几个例子：查 www.cs.cmu.edu，返回说它是另一个更怪的名字 www-cmu-prod-vip.andrew.cmu.edu 的别名（课上读的是 web-lb.srv.cs.cmu.edu 一类的名字），IP 地址以 128.2 开头；查斯坦福的 www.cs.stanford.edu，说它的正式名字是 cs.stanford.edu，IP 以 171.64 开头。这说明域名和互联网地址之间的映射不是一一对应的：多个域名可以对应同一个地址，一个域名也可以对应多个地址。查 twitter.com 返回了四个地址，再查一次，地址集合和顺序都略有不同。原因是它有多台服务器：发往 twitter.com 或谷歌这些大型服务的流量，并不由互联网上某一个地方处理，而是由遍布世界的成千上万个地方处理，方法就是在 DNS 上耍花招：谷歌维护自己的 DNS 服务器，不断更新，还会根据你所在的地理位置给出不同的地址，尽量提供离你较近的服务器。还有一些域名没有任何 IP 地址，它们在层次命名体系里，但并不指向某台具体的主机。

有同学问怎样拿到自己的 IP 地址：要么借、要么买。比如 CMU 有一批静态分配的 IP 地址，固定分给某台机器，可以通过计算服务部门申请注册；但大多数地址是动态分配的，从一个地址池里"租"给你一段时间，之后可能重新分给别人，这是管理有限 IP 地址的方法之一。

五、连接、端口和套接字

TCP 是面向连接的协议：一台主机和另一台建立连接，双方可以互相发送任意长的字节流。连接是点对点的，连接一对进程，而且是全双工的，数据可以同时双向流动；它是可靠的，发出的字节流最终会按发送的顺序被收到。连接的每个端点叫一个套接字，套接字由 IP 地址和端口号组成，写作"地址:端口"。

端口是一个 16 位整数，用来标识一个进程。为什么需要它？因为同一台机器可以提供不同的服务：SSH、FTP、邮件服务器、Web 服务器……要用端口号区分；同样，客户端在任意时刻可能和几十台主机保持着连接，浏览网页、做各种事，也要靠端口区分不同的程序。客户端一侧的端口通常是内核在客户端发起连接请求时动态分配的，叫临时端口，只在维持这条连接期间分配给你。而客户端要联系某台服务器的某项服务，比如 DNS 告诉你 google.com 的 IP 地址后，还要知道联系的是它的 Web 服务（端口 80）还是安全的 HTTP（另一个端口），有一张标准的"知名端口"列表：echo 是 7，ssh 是 22，email 是 25，Web 是 80，它们的对应关系记录在 /etc/services 里，这也是互联网标准的一部分，规定了各种服务的端口标识和协议怎样工作。

一条连接由两端的套接字地址唯一确定，即一个四元组：客户端地址、客户端端口、服务器地址、服务器端口。数据到达一台机器时，区分不同的连接、决定唤醒哪个进程来处理，是内核的工作，方法是把每个端口关联到一个负责处理那些请求的进程上。客户端完全可以通过不同端口和同一台服务器交互，比如同时访问它的 Web 服务和 echo 服务，但那算不同的连接，互不干扰。

套接字接口

这就是套接字编程或者说套接字接口，在 1970 年代末、80 年代初随着互联网一起在伯克利发展起来，如今所有现代系统都提供它，包括所有 Unix 变体、Windows 和 Mac OS。逻辑上，套接字是连接的一端；从应用程序看，它就是一个文件描述符，可以像前面讲的底层文件那样读写。这是套接字接口提供的心智模型，但实现完全不同：写套接字会启动各种网络机制，写磁盘则是在操作磁盘控制器，在硬件层面甚至较低的软件层面，它们是完全不同的东西，只是应用程序员看到了共同之处。

套接字地址结构

Bryant 说，这又是一个你会希望用的是有类型层次的语言的地方，但你用的是 C，于是有数不清的结构体要熟悉。通用的套接字地址结构 sockaddr 是 16 个字节，其中唯一特别的是开头两个字节，表示这是哪一族的套接字：TCP 的 IPv4 套接字、IPv6 套接字、UDP 套接字等等，各对应一个不同的常量。connect、bind、accept 这些函数的参数就用它，很多高层代码不必知道是哪类连接，交给别的软件处理，所以叫"协议族相关"。课件注明：设计这个接口时 C 还没有 void *，所以只能用一个通用的结构体指针。

套接字的东西不一定指大写的 Internet，所以 IPv4 用一个更具体的结构 sockaddr_in：它填入 16 位端口号和 4 字节 IP 地址，即使软件跑在 x86 上，这两者也必须按大端顺序存放，最后用 8 个字节的 0 填充到 16 字节，因为这个协议用不满。Bryant 指出，这是 C 版本的子类型：如果熟悉 C++ 或 Java 这类有类型继承的语言，可以把 sockaddr_in 想成 sockaddr 的子类，兼容它但信息更多。IPv6 另有一种结构填写它的信息。

六、客户端和服务器的调用流程

课件上有一张图，是从程序员角度运行一整套客户端-服务器系统的样子，这一讲剩下的时间和下一讲要逐步讲完图里的每一步，程序员必须理解每一步做什么、什么意思、怎样用。好消息是有相当标准的模式，常常可以直接拿现成的代码（比如书里的）来用，不像看上去那么痛苦。图的右边是服务器的步骤，左边是客户端的。右上部分是建立服务器：一个运行着的程序，准备好接收客户端连接并提供服务，显然要先有服务器，客户端才能做任何事。然后启动客户端；然后是会话，客户端和服务器来回通信，具体内容取决于应用，用的是之前讲过的 RIO 函数来读写，即在互联网上收发消息；之后客户端关闭连接，相当于挂电话；再之后，如果服务器想关闭（也可能永远不关），有它自己的一套调用。

  • socket：双方建立连接的第一步。socket(AF_INET, SOCK_STREAM, 0)，第一个参数 AF_INET 表示 IPv4、32 位地址；第二个 SOCK_STREAM 表示 TCP 连接，叫流连接，因为可以双向发送任意多字节的流；第三个 0 是协议，这里不需要。这些大写名字都是常量，在相关的头文件里定义。它返回一个整数，就是一个文件描述符，用它来把这个套接字当作文件引用。这一步其实没做什么：只发生在应用里，不用操作系统的任何部分（课件说明它只是创建了一个套接字描述符），什么也不发到网络上，只是说"我要创建一个套接字"。课件建议用 getaddrinfo 自动生成参数，让代码和协议无关。
  • bind（服务器）：这一步要和内核交互。参数是套接字的文件描述符、一个套接字地址结构的指针，以及地址的长度。它请内核把服务器的套接字地址和这个描述符关联起来，即指定这个程序要提供哪项特定服务，由端口号给出。长度通常不直接写数字，而是用 getaddrinfo 的返回值填，这个较新的 API 是这一版书才引入的，以前的版本没有，现在已成为获取各个调用所需参数的标准方式，用它写出同时适用于 IPv4 和 IPv6 的代码只需很小的改动。
  • listen（服务器）：把这个套接字从主动套接字转换成监听套接字，告诉内核它是一个服务器，可以接受客户端的连接请求。bind 和 listen 显然相关，但两步都要做，而且要按这个顺序。第二个参数 backlog 是内核在开始拒绝请求之前可以排队的未完成连接请求数，课件说这里的细节讲不完，一般设成一个较大的值，比如 1024。
  • accept（服务器）：最后一步，相当于说"好了，我准备好接电话了"。它会一直挂着等，直到某个客户端发来连接请求；请求到达后，它设置一个新的套接字，返回另一个文件描述符，服务器通过这个新的描述符和这个客户端通信，客户端的地址也会被填写到参数里。
  • connect（客户端）：客户端也要先调用 socket，但不需要 bind、listen 和 accept，而是调用 connect 去和服务器建立连接。参数是之前 socket 返回的文件描述符，一个包含地址和端口组合的套接字地址，以及地址长度（同样通常用 getaddrinfo 的结果填），返回值说明连接是否成功。它会阻塞，直到连接建立成功或者出错；成功后，客户端描述符就可以读写了，这条连接由那个四元组刻画。

两种描述符

服务器经过 bind 和 listen 得到一个监听描述符，在上面等待连接请求。客户端调用 socket 得到一个描述符，发出连接请求，请求经过网络到达服务器，内核把它交给在那个端口上运行的程序，由 accept 处理；accept 返回一个新的文件描述符，服务器用它作为和这个客户端的连接端点。为什么要不同的描述符？因为一般而言，服务器要能同时处理多个客户端，同时和谷歌或亚马逊通信的人很多，一台主机要能为多个客户端服务，所以每个连接在服务器一端都分配不同的文件描述符。可以这样理解：监听描述符只负责听进来的连接请求，它在服务器的整个生命期中一直存在；一旦建立会话、开始来回通信，就通过各自的已连接描述符，它们用同一个端口、不同的文件描述符，只存在于为一个客户端服务的期间。

会话期间用 read 和 write 收发消息，按特定应用协议规定持续多久就多久。客户端结束时关闭连接，在服务器一端看到的是：试图读的时候收到了文件结束（EOF），这告诉服务器这条连接没了，于是关闭它，图上显示服务器可以绕回去接受另一个程序的连接。这叫串行（迭代）服务器，一次只能处理一个连接请求；后面讲多线程时，能让服务器在处理一个客户端的同时接受另一个连接的请求。

七、getaddrinfo

Bryant 提前讲了一部分原本属于下一讲的课件，因为下一讲要讲的东西很多。getaddrinfo 是 C 里处理主机名、主机地址、端口约定、各种结构体这些古怪东西的现代方式，比旧方法好在两点：它把 IPv4 和 IPv6 统一成了很相似的接口，写能同时处理两者的代码相当容易；旧函数是在多线程出现之前设计的，有各种静态分配的缓冲区，带来很多写代码时必须提防的问题，容易出错，新接口在多线程环境下表现更好。它在很多方面反而更难用，因为不能像以前那样把那么多细节藏起来；它还想当协议管理的"万能工具"，有点乱，课上只关注真正要用的部分。

调用形式是 getaddrinfo(host, service, &hints, &result)：host 可以是主机的域名，也可以是写成字符串的点分十进制地址，这些 char * 是真的字符串，不再是当通用指针用的假字符串；service 可以是服务名，比如 http，也可以是十进制的端口号；hints 是关于这次连接的一些附加信息，因为它想做成一个很通用的调用，所以叫"提示"；最后传入一个指针，它会填写并返回一个指向结果数据结构的指针。配套的 freeaddrinfo 释放这个结果占用的空间，gai_strerror 解释它返回的各种错误码。

结果是一个以 NULL 结尾的链表，元素是 addrinfo 结构，字段包括数据类型、套接字类型、规范名（只在第一个元素里有）、地址长度、一个指向 sockaddr 的指针（可以直接传给 connect 或 bind）、以及串起链表的 next 指针。其中几个字段正好可以作为参数传给 socket、bind、listen、connect。它也顺带解决了名字和地址"多对多"的映射问题：比如给 google.com，它返回所有当前有效的地址组成的链表，像 Twitter 那样有四个地址的话，链表就有四个元素（第一个还带着规范名）。程序员沿着链表逐个尝试地址，一个失败就试下一个，直到成功或到达链表末尾才说"不行"，客户端和服务器都是这样写。反过来的 getnameinfo 用于已知 IP 地址、要找它的域名的情况，因为这个映射也可能是一对多的。

例子：hostinfo

用 getaddrinfo 探查 DNS 服务器的例子：把命令行输入的字符串作为名字传给 getaddrinfo；hints 是一个结构体本身，用全 0 填好，因为不需要什么提示，只告诉它要 IPv4 的 TCP 连接（课上口头说成了 IPv6），而 listp 和 p 只是指向结构体的指针，没有分配空间；调用后它返回一个错误码，并返回指向结果链表的指针；然后用标准的链表代码遍历，对每个元素调用 getnameinfo，以点分十进制形式取出地址并打印；最后释放这个链表，否则会造成内存泄漏。

运行起来，它就像一个不太花哨的 nslookup，基本得到同样的信息，实际上就是在查询 DNS 服务器。Bryant 觉得奇怪的是，它每次都按同样的顺序返回地址，而 nslookup 的顺序一直在变，他认为和缓存有关，后来又看到顺序变了，说不清，建议大家自己玩玩这段代码。写代码时常用 localhost，它总是指你正在运行程序的这台机器，地址总是 127.0.0.1，开发时通常在一台机器上同时运行客户端和服务器来测试，很方便。也可以直接给它一个点分十进制地址，那就没什么意思了，它原样返回。Bryant 最后说，这类代码很乱，有很多结构体要初始化，有很多指针要传，看起来总有点陈旧，但接口就是这样，只能慢慢习惯。
