第十三讲：链接

为什么要分开编译，链接器做的两件事（符号解析和重定位），三种目标文件和 ELF 格式，全局、外部和局部符号，强符号与弱符号的规则以及它们带来的诡异 bug，重定位条目，可执行文件怎样装入内存，静态库和命令行顺序，共享库与动态链接，运行时用 dlopen 加载函数，以及库打桩的三种方式

主讲：David R. O'Hallaron
资料来源：课堂录像（2015 年 10 月 13 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件
教材对应：CS:APP 第 7 章

一、从硬件转向系统软件

这一讲开始，课程从"程序怎样和硬件交互"转向"程序怎样和软件，尤其是系统软件交互"。第一站是链接，也就是系统怎样把你的程序拼起来。最后会介绍一个很酷的技术，叫库打桩（library interpositioning），它能截获对 C 标准库等库函数的调用，这完全是链接带来的能力。

例子程序有两个模块：sum.c 里的 sum 函数对一个数组求和；main.c 定义一个两元素的 int 数组，调用 sum，再把结果作为退出状态返回（这么做有点怪，只是为了不让编译器把代码全部优化掉）。GCC 对每个 .c 文件依次调用几个翻译器：C 预处理器 cpp、真正的编译器 cc1（生成汇编）、汇编器 as（生成 .o 文件）。得到 main.o 和 sum.o 之后，链接器 ld 把它们"揉"在一起，生成一个可以加载运行的可执行文件。.c 是源文件；单独编译出来的 .o 叫可重定位目标文件，因为它们可以组合成完全链接的可执行目标文件。

为什么要分开编译

为什么不把所有代码放进一个大文件？两个理由。一是模块化：把相关的函数放进不同的源文件，可以定义库，这是好的编程方法。二是效率：时间上，改了一个模块，只需重新编译那一个，再重新链接，不必全部重编；空间上，可以把 C 标准库所有函数放在一起，但最终链接进程序的只有你真正调用的那几个，通常只用到标准库很小的一部分，没必要全部塞进程序。

二、链接器做什么

链接器有两项主要任务。

第一项是符号解析。程序定义和引用符号，在链接器看来，符号就是全局变量和函数的名字。定义一个函数 swap 是定义符号，调用 swap 是引用符号；定义 int *xp = &x 定义了符号 xp，同时引用了 x。汇编器把符号定义存在目标文件的符号表里，符号表是一个结构体数组，每项记录符号的名字、大小和位置。符号解析就是把每个符号引用和唯一一个符号定义对应起来。为什么这是个问题？因为多个模块可能定义了同名的全局变量，链接器得决定后面的引用用哪个定义。

第二项是重定位。每个引用都对上唯一的定义后，链接器把所有模块合并成一个可执行目标文件，并决定每个符号（每个函数和变量）最终放在内存的什么位置。之所以叫重定位，是因为合并之前，函数在目标文件里的地址只是它在模块内的偏移，链接器还不知道它会被装到哪里。重定位时，链接器给每个符号定下运行时的绝对地址，再找到所有对这些符号的引用，把它们改成正确的地址。

三种目标文件

  • 可重定位目标文件（.o）：汇编器的输出，是二进制文件，但不能直接装入内存，要经过链接器处理。
  • 可执行目标文件（a.out）：链接器的输出。最早的 Unix 开发者给可执行文件起的默认名字就是 a.out，这是历史原因。
  • 共享目标文件（.so）：一种现代的共享库技术，后面讲。

ELF 格式

三种目标文件都用一种统一的标准格式，叫 ELF（可执行可链接格式）。它是有严格结构的二进制，分成若干节：

  • ELF 头：字长、字节顺序、文件类型（.o、可执行文件还是 .so）等总体信息。
  • 段头表：只有可执行文件才有，说明各个段（代码、已初始化和未初始化数据、栈、共享库等）装到内存的哪里。
  • .text：代码，叫 text 也是历史原因。
  • .rodata：只读数据，比如 switch 语句的跳转表。.text 和 .rodata 都是只读的。
  • .data：已初始化的全局变量。
  • .bss：未初始化的全局变量。它在文件里不占空间，因为没有初值，但符号表里有它们的条目，程序装入时要为它们分配空间。这个名字可以追溯到 60 年代一条叫"block started by symbol"的伪指令，O'Hallaron 建议记成 "better save space"（更省空间）。
  • .symtab：符号表，函数、全局变量和所有带 static 属性的东西各有一项。
  • .rel.text 和 .rel.data：重定位信息。汇编器遇到对符号的引用时，留下一张便条：这个引用到时候要修正，因为我不知道这个符号最终放在内存哪里。
  • .debug：把源代码行号和机器码对应起来的信息，用 -g 编译时才有。
  • 节头表：说明各节从哪里开始。

三、三种符号

  • 全局符号：模块 m 定义、其他模块可以引用的符号，即不带 static 的全局变量和函数名。多模块程序里，编译单个模块时调用了在别处定义的函数，编译器不报错，它假定函数在别的模块里，由链接器去找。
  • 外部符号：模块 m 引用、但在别的模块定义的全局符号。例子里 main.c 调用 sum 就是引用外部符号。
  • 局部符号：只在模块内定义和引用的符号，即带 static 属性的全局变量和函数。这和 C 的局部变量不是一回事：局部变量由编译器在栈上管理，链接器对它们一无所知。

加 static 的函数或全局变量，作用域限于定义它的模块，这是 C 实现抽象和信息隐藏的方式。写一个 C 函数库时，想公开给别人调用的函数不加 static，只供内部使用的函数加 static，这样就只暴露想暴露的数据和函数。例子程序里：array 是 main.c 定义的全局符号，main 是全局符号，sum 是 main.c 引用的外部符号，而 val、i、s 这些都是栈上的局部变量，链接器不知道它们。

局部静态变量要分清楚：在函数 f 里定义 static int x = 0，在函数 g 里又定义一个同名的 static x，它们的作用域分别限于 f 和 g；但因为是 static，它们不在栈上，而是和全局变量一样放在 .data 里。编译器给每个定义分配空间，并起不同的名字来区分，比如 x.1 和 x.2，它们都在符号表里有条目。课上有同学问这有什么用：当你需要一个变量的值在多次调用之间保留时用它，比如早期的伪随机数生成器把算出的数存在一个静态变量里，作为下一次调用的起点。O'Hallaron 提醒，这通常不是好主意，后面讲线程时会看到，它让代码不是线程安全的。

四、强符号和弱符号

多个模块里出现同名的定义时，链接器靠一套规则选出唯一的定义。强符号是函数名和已初始化的全局变量；弱符号是未初始化的全局变量。比如一个模块里 int foo = 5 和函数 p1 是强符号，另一个模块里 int foo; 是弱符号、函数 p2 是强符号。规则：

  1. 不允许多个同名的强符号，否则链接错误。所以不同模块里定义同名函数，或者同名的已初始化全局变量，都会报错。
  2. 一个强符号加多个弱符号，选强符号，所有引用都指向它。
  3. 多个弱符号，任意选一个。

用 GCC 的 -fno-common 选项，多个弱符号也会报链接错误。

为什么要在意：链接器 bug

O'Hallaron 说，如果不了解这些，会遇到让人完全摸不着头脑的严重问题。链接器错误是最难调试的一类，因为大家一般不清楚链接器内部发生了什么，只有最好的程序员才真正懂。几个例子（每个方框代表一个模块）：

  • 两个模块都定义函数 p1：两个强符号，链接错误，这个还好。
  • 两个模块都写 int x;：两个弱符号，链接器选一个，两边类型相同，问题不大。
  • 一个模块写 int x; int y;，另一个写 double x;：都是弱符号，类型不同。如果链接器选了那个 8 字节的 double，整个程序里对 x 的引用都按它来，第二个模块往 x 写一个 double 时会写 8 字节，从而覆盖掉第一个模块里紧挨着的 y。链接器任意选，你不知道它会选哪个。
  • 一个模块写 int x = 7; int y = 5;，另一个写 double x;：x 是强符号，所有引用都指向这个 4 字节的 int。但第二个模块的编译器以为 x 是 double，往 x 写时写 8 字节，落在只有 4 字节的位置上，同样会覆盖 y。课上 O'Hallaron 一开始说错了，随即更正为这个结论。
  • 一个模块初始化了 x，另一个模块未初始化：第二个模块里对 x 的引用都指向那个已初始化的变量，而你写代码时可能以为它没有初值。

最可怕的情况是：因为大家遵守同一个 ABI，不同模块可以用不同的编译器编译，在一个编译器里可能是某种对齐，在另一个里又是另一种，排查起来是噩梦。有同学问 y 为什么正好紧跟着 x：全局变量在 .data 里，通常就是按声明顺序挨着分配的，这是一般情况，不是保证。

建议：能不用全局变量就别用；如果需要，尽量加 static，把作用域限制在模块里；定义全局变量时给它初始化，这样多个模块里出现同名的已初始化全局变量时会报错，问题会暴露出来；引用外部全局变量时，用 extern 告诉编译器，这是好习惯。

五、重定位

符号解析完成后，链接器要把这些可重定位目标文件合并成一个大的可执行文件。main.o 和 sum.o 各有代码，main.o 还有已初始化数据（数组），另外还有系统代码：程序真正开始执行的是 C 库里的启动代码，它做一些初始化，最后才调用 main 并传入 argc 和 argv；main 返回时回到启动代码，由它调用 exit。重定位时，链接器把各模块的 .text 按它定的顺序连续拼成一个合并的 .text，.data 也一样，符号表和调试信息也合并。

为此链接器要给 main、sum、数组等每个符号选定装入时的地址，而编译器编译时并不知道这些地址，所以编译器在目标文件的重定位节里留下重定位条目，告诉链接器"这里有一个对某符号的引用，合并时要修正"。

main.c 里有两个这样的引用。一是对数组 array 的引用：调用 sum 时要把数组地址放进 %edi（第一个参数），编译器不知道地址，就先生成一条把立即数 0 放进 %edi 的 mov 指令（编码里 bf 是 mov，后面四个字节全是 0），再加一条重定位条目：在 .text 偏移 0xa 处，有一个对 array 的 32 位绝对地址引用。main.o 只有 main 一个函数，所以 main 从 .text 偏移 0 开始，地址就是偏移。二是对函数 sum 的调用：编译器连 sum 在哪个模块都不知道，于是生成一个目标全是 0 的 call，再加一条重定位条目：在偏移 0xf 处，有一个对 sum 的 4 字节 PC 相对引用，附带一个 -4 的偏置。偏置的原因是 call 用 PC 相对寻址，而程序计数器总是指向下一条指令，后者在 4 个字节之外，书里有详细解释。

链接之后用 objdump 反汇编可执行文件：那条 mov 的四个字节已经填上了 array 的绝对地址，链接器把数组放在了 0x601018；那条 call 的四个字节填的是 5，这是一个按补码解释、可正可负的相对偏移。执行 call 时，取当前程序计数器的值（下一条指令的地址 0x4004e3）加上 5，得到 0x4004e8，就是 sum 的地址。O'Hallaron 指出，所有的聪明都在编译器那里，链接器只是逐条照着重定位条目去做。

可执行文件怎样装入内存

链接完成后，可执行文件里的代码和数据不需要任何修改就能直接装入内存。所有只读的节（.init，以及 .text 和 .rodata）原样复制进内存，组成只读代码段；.data 和 .bss 也直接复制，组成读写数据段，变量按符号表里的值初始化。每个 Linux 程序看到的地址空间里，程序都装在同一个地址 0x400000；代码和数据来自目标文件；紧接着数据段的是由 malloc 创建和管理的运行时堆，向上增长，堆顶由内核维护的变量 brk 指示；用户程序能看到的最高处是栈，向下增长，栈顶由 %rsp 指示，再往上是内核专用的内存，访问会段错误；栈和堆之间那片巨大的空隙里，有一块用于共享库的内存映射区域，.so 文件装在那里。这是简化的图景，第九讲已经提到，看 malloc 返回的地址会发现大对象另外放在高地址处。有同学问堆能长多大，O'Hallaron 说根据他做过的实验，会一直长到某个很大的上限为止。

六、静态库

链接的一大好处是能做库。程序员总想建立抽象，定义 API，实现并打包，提供给别的程序员用。怎样把常用函数提供出去？一种办法是把所有函数放进一个大 C 文件，让人把它链接进去，但库一大就很笨重，C 库有好几百个函数；另一种是每个函数一个文件，分别编译，空间和时间上更省，但程序员得知道每个函数在哪个文件里，写进 makefile，GCC 的命令行会长得离谱。

Unix 开发者给出的第一个方案是静态库：一个归档文件（.a），就是许多 .o 文件拼在一起，开头有一个目录记录每个 .o 的偏移。用 ar 工具把各函数编译出的 .o 打包成归档。把归档交给链接器，它只取出真正被引用的那些 .o 链接进来：归档再大，只调用 printf 的话，就只拿 printf.o。某个函数改了，就重新编译它，再重新归档。libc.a 有大约 1500 个目标文件，包括 printf、scanf、简单的整数运算等；数学库 libm.a 有几百个函数，比如浮点的正弦、余弦、正切。按惯例，库名都以 lib 开头，后面是表示用途的名字。

例子：建一个 libvector.a，里面有 addvec（两个向量相加）和 multvec（两个向量逐元素相乘）。main2.c 调用 addvec。把 main2.o、libvector.a、libc.a 交给链接器，它发现对 addvec 的引用，就只取出 addvec.o，忽略 multvec.o；printf.o 同理（以及 printf 再调用的东西）。最终得到完全链接的可执行文件 prog2c，c 表示编译时链接。

命令行顺序很重要

链接器按命令行上的顺序扫描 .o 和 .a 文件，过程中维护一张当前未解析引用的列表。比如先看 main.o，里面引用了 printf 但没有定义，这个引用进入列表。每遇到一个新的 .o 或 .a，就尝试用其中定义的符号解析列表里的引用。扫描结束时列表里还有东西，就报错。所以解析是从左到右进行的，命令行上文件的顺序会影响结果，顺序错了会出现令人费解的链接错误。

例子：libtest.o 调用了 libmine.a 里定义的函数 libfun。命令写成 gcc -L. libtest.o -lmine：-L. 表示先在当前目录找库，再去常规位置找；-lmine 是 libmine.a 的简写。链接器在 libtest.o 里发现未解析的 libfun，放进列表，然后在 libmine.a 里找到并解析。如果顺序反过来，gcc -L. -lmine libtest.o：先看 libmine.a，此时列表是空的，没有要解析的引用，什么也不取；再看 libtest.o，出现未解析的 libfun，但命令行已经到头了，于是报出一个很晦涩的错误，不知道这条顺序规则就无从调试。

七、共享库

静态库是老式的方案，现代方案是动态库，也叫共享库。静态库的主要缺点是重复：每个用到 printf 的程序都要带一份 printf 的副本，而几乎每个程序都用 printf。共享库只有一个实例，系统上所有运行的程序共享这一份副本（学了虚拟内存就会明白怎样做到）。

共享库里的代码和数据不是在编译链接成可执行文件时链接进去的，而是推迟到程序装入内存时才链接，甚至可以在运行中的任何时刻链接。它们有不同的名字：共享库、动态链接库（Windows 上叫 DLL）、.so 文件，说的是同一种东西。

过程：先用 GCC 的 -shared 参数把 addvec 和 multvec 编译成共享库 libvector.so，而不是归档；C 的开发者也提供了共享版的 libc.so，包含 printf 等标准库函数。把 main2.o 和这些 .so 文件交给链接器，此时链接器并不把 addvec 或 printf 复制进可执行文件，只在符号表里记下：这些引用要在程序装入时解析。它还记下程序需要哪些 .so 文件。这样得到的可执行文件是部分链接的，不能直接装入运行。装入程序（execve 系统调用，后面会细讲，它负责把可执行文件装入内存并运行）读取可执行文件，然后调用动态链接器，由它把所需的 .so 装进来，解析所有未解析的引用，过程和静态链接器类似。addvec 和 printf 的地址直到程序装入时才由动态链接器确定，之后程序才能直接执行。

有同学问 #include 的文件怎么处理：#include 和 #define 由 C 预处理器处理，它把被包含的文件原地展开，输出另一个 C 程序，等到链接器工作时这些早就不存在了。

运行时动态链接

更酷的是，运行中的程序可以随时决定加载、链接并调用任意 .so 里定义的函数，接口是 C 库里的 dlopen 一族。例子 dll.c：编译时它对 libvector.so 一无所知，就是一个独立的 C 程序。程序里声明一个函数指针 addvec，写明它的原型（两个输入数组、一个输出数组、长度）。先调用 dlopen("./libvector.so", RTLD_LAZY) 把共享库装进内存，RTLD_LAZY 表示先别解析函数引用，等真正要用时再说；它返回一个句柄，为空就说明出错了，比如 .so 不存在。再用 dlsym(handle, "addvec")，传入函数名字符串，得到指向这个函数的指针，之后就像调用普通函数一样用这个指针调用它。有同学问调用时要不要解引用：不用，直接用函数指针的名字调用就行；如果解引用，得到的只是这个函数的地址。

八、库打桩

O'Hallaron 承认，要让大家觉得链接有意思是件难事，但他想试试。库打桩的目标是截获对库函数的调用，通常是记录一些统计信息或做错误检查，然后再按原意调用真正的函数。做法是写包装函数：程序调用某个函数时，执行的其实是它的包装函数，而且完全不改源代码。

用途很多。他知道的最妙的一例：Facebook 工程师在 iPhone 应用里追查一个存在了一年的 bug，没人知道怎么回事，最后用库打桩截获了应用里所有写操作的调用，检查参数和调用方式，发现是网络栈里某处写错了位置。还可以用来监控和剖析，比如统计各函数被调用了多少次；用来生成地址轨迹，后面 malloc 实验评估你写的 malloc 用的轨迹，就是课程组用这个技术从 Netscape 等真实程序里截获所有 malloc 和 free 调用、记录地址和大小得到的。

例子：一个程序里有一次 malloc 和一次 free，想记录它们的地址和大小。可以在三个时机打桩：

  • 编译时：写包装函数 mymalloc 和 myfree，mymalloc 调用真正的 malloc，再打印大小和返回的地址。然后写一个自己的 malloc.h，用宏把 malloc 定义成 mymalloc、free 定义成 myfree，并给出原型，免得编译器糊涂。编译 int.c 时加 -I. 参数，让 GCC 先在当前目录找头文件，于是找到这个 malloc.h，C 预处理器就把所有 malloc 调用翻译成 mymalloc。运行时就会打印出 malloc 和 free 的轨迹。这需要能重新编译程序（不必修改它）。
  • 链接时：不必重新编译源文件。包装函数取特殊的名字 __wrap_malloc，它调用 __real_malloc 并打印信息。链接时用 -Wl,--wrap,malloc：-Wl 告诉 GCC 把后面的参数（逗号换成空格）传给链接器；--wrap,malloc 告诉链接器，把所有对 malloc 的引用解析成 __wrap_malloc，把对 __real_malloc 的引用解析成真正的 malloc。于是程序里每个 malloc 调用都进入包装函数，包装函数再调用真正的 malloc。
  • 装入或运行时：最惊人的是这一种，连 .o 文件都不需要，只要有可执行文件，而每个程序我们都有可执行文件。也就是说，可以在运行时截获任何程序的库调用。包装函数里用 dlsym(RTLD_NEXT, "malloc") 取得真正 malloc 的地址：我们会骗动态链接器先找到自己的 malloc，而这里要的是真正的那个，RTLD_NEXT 表示去它通常会找的下一个地方找。得到函数指针后调用它，再打印数据，free 同样处理。把包装函数编译成 mymalloc.so（用 -shared），把 int.c 正常编译成可执行文件 intr，这里完全没提 mymalloc.so。打桩发生在运行时：在 bash 里设置环境变量 LD_PRELOAD="./mymalloc.so" 再运行 intr。LD_PRELOAD 列出的位置会被动态链接器最先查找，之后才去系统常规的地方，于是所有对 malloc 的引用都落到了包装函数上。

O'Hallaron 的结论：库打桩是一项很酷的技术，它之所以可能，完全是因为有链接器。
