第十六讲：系统级 I/O

Unix 把一切看作文件，文件的类型和文件位置，文本文件与行尾符，目录和路径名，open、close、read、write 四个底层调用和不足值，用 strace 观察系统调用，带缓冲和不带缓冲的 RIO 包，文件元数据和 stat，内核表示打开文件的三张表，fork 和 dup2 怎样共享文件，标准 I/O 的缓冲，以及三种 I/O 各用在什么地方

主讲：Randal E. Bryant
资料来源：课堂录像（2015 年 10 月 22 日，YouTube 转载自 CMU 官方 Panopto 录像；本文依据录像字幕整理）、课件

一、为什么学底层 I/O

Bryant 前一天伤了膝盖，这节课大部分时间坐着讲。主题是从程序员角度看输入输出。大家已经熟悉 printf、scanf 这些标准库函数，这一讲先讲更底层、直接和操作系统打交道的 I/O。当晚发布的 shell 实验要用到一部分，之后好几个实验还会再遇到，包括最后的 Web 代理实验。这是写系统软件、即紧贴操作系统之上那一层软件时要做的编程。

Bryant 坦言，他自己是从 213 学会这些的：合著者 O'Hallaron 本来就懂，书里这部分是他写的，Bryant 是像学生一样读书学会的，后来在很多场合都发现很有用。这类内容一般只在面向系统程序员、相当晦涩的书里才有，否则只能靠读 man 手册，而那是理解一套 API 抽象的很费解的方式。

内容依次是：Unix 的底层 I/O；一个叫 RIO（robust I/O，健壮 I/O）的包，到最后的代理实验才会大量使用，但值得现在看；文件在内核里的表示，以及它们怎样支持标准 I/O 和 I/O 重定向；最后是大家熟悉的、带缓冲的标准 I/O。他特别建议研究书里 RIO 的全部源代码，代码不多，能体会到处理错误和异常情况的种种微妙之处，想真正理解一个软件系统，最好的办法就是去读高质量的源代码。

二、一切皆文件

Unix 对 I/O 的看法比其他任何操作系统都更简单、更统一，这是它的一个优秀设计：很多抽象都建立在文件这个概念上，而文件只是一个字节序列。Unix 不像 Windows 或早期 Mac 系统那样区分不同类别的文件，在操作系统层面它对文件内部的结构几乎一无所知。文件原本指存在磁盘等外部存储上、可以打开、读写、关闭的东西，Unix 还用它表示很多别的东西：连在机器上的 I/O 设备，比如 /dev/sda2 是一个磁盘分区，/dev/tty2 是一个终端（tty 是 teletype 的缩写，电传打字机，指早年人们把打字机接到计算机上的方式）；甚至内核本身也有一部分以文件形式呈现（/boot/vmlinuz）；网络连接叫套接字，通过互联网通信时，写套接字就是发送消息，读套接字就是接收。无论读写磁盘上的文件还是在互联网上收发数据包，用的是同一套底层 API。

文件的核心操作就是打开、关闭、读、写。大多数文件（但不是所有）还有一个文件位置：一个计数器，记录到目前为止读或写了多少字节，下次读写从这里继续，不必每次从头开始。可以用 lseek 改变它，叫"定位"。但这对终端没用，你不能往回退去拿之前输入的数据，也不能跳到还没输入的地方；网络套接字也不能在时间上跳跃，只能按到达顺序读写。所以有的文件有文件位置和定位操作，有的没有。

文件的类型

既然很多不同的东西都统一成文件，它们之间自然有区别，分类很多，课上主要关心：普通文件，就是磁盘上的文件；目录，它也是一种文件，但很特别，里面的条目描述其他文件的位置和属性；套接字，用于和另一台机器上的进程收发网络消息。其他的还有：管道，把一个程序的输出接到另一个程序的输入，写就是往管道里放东西，读就是取出来；符号链接，让一个文件有多个名字、多个指向它的指针而不必复制；以及字符设备、块设备等特殊设备。这一讲主要讲前两种。

文本文件和二进制文件

普通文件可以存放任意数据，操作系统并不深究它的内容。有些应用程序会区分文本文件和二进制文件，这不是操作系统层面的事。文本文件只含 ASCII 或支持非英文字母的 Unicode 等编码的字符；二进制文件是图像、目标代码、视频或音频等，里面的字节直接以某种形式编码数字。文本文件的要点是有些函数会特殊对待换行符，即十六进制 0a 这个字节，攻击实验里它是禁用的字节之一，因为 gets 会把它当作行尾。

在 Windows 和 Linux 或 Mac 之间传文本文件时要转换行尾：Linux 和 Mac 用一个字符 0a，即换行（line feed，LF）；Windows 用两个字符，回车加换行（CR LF）。Bryant 给大家看了一张老式打字机的照片，解释回车和换行到底是什么：打字时，夹着纸的滚筒一路向左移动，打到行尾要回到下一行开头，既要把滑架推回去（回车），又要让滚筒往下转一行（换行）。打字机左侧有一根杠杆，打字员"啪"地一推，两件事一次完成，这就是 CR LF 的来历。

目录和路径名

目录也以文件形式存储，但操作系统（至少是文件系统那部分）会以特定方式解释它的内容，即一组把文件名映射到文件的链接。每个目录里都有两个特殊条目：点（.）指自己，点点（..）指树结构中的父目录。课程不讲文件系统，只需知道文件按层次组织，每个目录指向它的子目录，它们本身又是文件。路径名是在这个层次中定位某个文件的方式：绝对路径以斜杠开头，从根一路往下；相对路径从当前工作目录出发；还可以用波浪号开头，作为某个用户主目录的简写。

三、Unix I/O 的四个调用

打开和关闭

open 的参数是一个路径名，加上一个整数，说明以什么方式打开，用一组预先定义的常量表示，比如只读 O_RDONLY、读写 O_RDWR、追加 O_APPEND（写的时候不从头开始，而从文件当前结尾开始）。每个常量是某个 2 的幂位置上的一位，或者某个字段里的一位，可以按位或起来组合。open 返回一个文件描述符，这是一个很重要的概念，shell 实验里很关键：它是一个小整数，指出你说的是这个程序当前打开的哪个文件。数字很小，因为程序启动后按顺序分配，而且大多数机器限制同时打开的文件数，在机器上输入 limit 能看到 descriptors 1024，即最多同时打开 1024 个文件；如果真开了一千多个，多半是你该关的文件没关。

每个进程创建时都有三个打开的文件：标准输入（描述符 0）、标准输出（1）和标准错误（2）。虽然可以可靠地依赖这几个数字，但不应该在代码里直接写数字。

关闭文件只需 close(fd)，参数是文件描述符而不是文件名。课程要反复强调的一条规则是：每次系统调用都要检查返回码，看有没有出错，并做适当处理。这很烦，会让代码满是条件判断，决定出错时怎么办往往比完全忽略错误更难，所以外面有大量代码只是祈祷系统调用永远不出错。返回码的约定也五花八门：有时负数表示错误，有时 0 表示错误，每个函数都要看文档。open 返回负数，说明打不开，比如文件不存在，或者没有权限以那种方式打开。为什么关闭一个已经打开的文件也会出错？后面讲多线程时会看到，两个部分同时运行、共享数据结构时，如果两边都去关同一个文件，第二次关闭就会出错，这是很糟糕的错误。所以即使是关文件这么平常的事，也该检查返回码。

读和写

read(fd, buf, n)：给一个文件描述符、一个你自己静态分配或用 malloc 分配好的缓冲区，以及缓冲区的长度，防止溢出。它的语义听上去很怪：读它想读的那么多字节，但不超过 n。至少读一个字节：对标准输入，它会挂在那里等，实际上会等到你输入一行并按回车，再把其中一部分读进程序；对网络连接，会一直等到有数据到达，再读进一些。读到的字节数在 1 到 n 之间，并没有保证。返回值类型是 ssize_t（有符号的，通常是 long）：正数是读到的字节数；0 表示遇到文件结束（EOF），即读到了存储文件的末尾，或网络连接被关闭了；负数是错误码。读到的比 n 少叫不足值（short count），这确实会发生，写代码时必须预料到。

write(fd, buf, n) 同理：写出缓冲区里最多 n 个字节，至少一个，但不一定全部写完，即使你说了要发这么多，这也叫不足值。返回值是实际写出的字节数，小于 0 表示出错。

一个很慢的例子

最简单的回显程序：每次 read 一个字节、write 一个字节，循环下去。因为 read 至少读一个、最多读 n 个，n 为 1 时就恰好读一个字节，write 也一样。这段代码能正确工作，但写得很糟糕：read 和 write 是相对昂贵的调用，每次都要把操作踢到操作系统，做一次上下文切换进入内核，执行操作系统的函数，再切回你的程序，大约要两万到四万个时钟周期。现在一个周期不到一纳秒，算下来也就十微秒，看起来不算什么，但发送几百万字节的文件时一次发一个字节，大部分时间都会耗在操作系统里。这是程序员很容易犯的错：用这么底层的读写，程序功能完全正确，就是慢得要命。

Bryant 用 strace 演示：给它一个程序名，它会记录程序运行时的每一次系统调用，通常吐出一大堆看不懂的东西。更有用的是加参数，只看某一类调用。只看 write，可以看到输入的一行字变成了一连串每次一个字节的 write 调用；看 read 和 write，可以看到它在循环里读一个、写一个（终端上标准错误和标准输出交错在一起，有点乱）。看上去程序是读一行再回显一行，那只是因为终端的接口要收到完整一行才唤醒程序，程序实际上是一个字符一个字符地回显的。

为什么会有不足值

  • 读时遇到 EOF。有同学问：读到 EOF 返回 0 算不算不足值？Bryant 说这确实是"很不足"的不足值，并补充：比如文件只剩 100 个字节，你要读 200 个，第一次 read 返回 100，第二次再读才返回 0，返回 0 是判断真正到了文件末尾的方式，也是唯一会返回 0 的情况。
  • 从终端读文本行：终端处理程序每次只送一行，以换行符结尾。
  • 读写网络套接字：长消息会被拆成较小的块，以太网规定的最大传输单元（MTU）是 1500 字节左右，所以读进一个大缓冲区时，数据通常一块一块地到。写的时候也一样，一次只能发出一个包能容纳的量，要继续往外发。

读磁盘文件时，除了遇到 EOF，不会出现不足值；写磁盘文件也从不会有不足值。有同学问，如果花一周敲一个超长的字符串再回车会怎样？Bryant 说那段代码被反复检查过，潜在的缓冲区溢出漏洞都清除了，不会出错，但会不会让你那样做他也不知道，有兴趣可以试试。总之写代码时要预料到不足值，这就是直接用底层 I/O 让人头疼的地方，所以通常把它包装进别的库。

四、RIO 包

O'Hallaron 写了 RIO 包，最后一个实验会用到，这里把它当作一个包装底层 I/O、让它好用一些的范例。它提供两类接口。

不带缓冲的输入输出

rio_readn 和 rio_writen 是对 read 和 write 的很薄的包装，语义和它们相同，但解决了不足值问题：调用 rio_readn 读 n 个字节，它读满 n 个才返回，所以要确保真有这么多字节，否则对网络套接字它会一直挂着等，对文件则在遇到意外的 EOF 时返回。准确地说，它只在中途遇到 EOF 时才返回不足值，此外不会。rio_writen 也一样，循环写到没有不足值为止。

看 rio_readn 的代码：参数是文件描述符、目标缓冲区和要读的字节数；返回负数表示出错，0 表示 EOF，否则是读到的字节数。主循环一遍遍调用 read，直到满意为止：读够了要读的数量；或者得到错误码，其中区分了错误的类型，有一种是被信号处理程序中断（EINTR），这时要重新调用 read，其余错误则返回负数；或者读到 0，即 EOF，这时返回已经读到的字节数，也就是不足值；否则把已读字节数加上去、剩余字节数减下来，继续读。Bryant 说这段代码初看有点乱，但仔细研究就全都讲得通，而且它对每个调用都检查了各种错误情况。

带缓冲的输入

实际中真正想用的是带缓冲的 I/O，标准的 Unix I/O 函数大多也是这样做的：在用户代码里建一个字节缓冲区，读的时候，存放已经从内核读进来、但应用程序还没取走的字节；写的时候，先在程序里攒一批字节，再一次性写进文件或发到网络上。RIO 的带缓冲函数有两种：面向文本行的 rio_readlineb，以及面向字节的 rio_readnb。

原理：每个打开的文件关联一个缓冲区（就是一个字节数组）。读的时候，用一个很大的 n（基本就是缓冲区的大小）调用一次 read，让系统尽量把缓冲区填满；之后应用程序要取字节时，先看缓冲区里有没有还没被读走的，有就直接返回，没有才重新填充缓冲区。也就是说，不是每次都去找操作系统要一两个字节，而是一次要尽可能多的字节，再由应用程序一次几个慢慢取用，期间不打扰操作系统。实现时只需记录一个指针，指出缓冲区里已经交给应用程序和还没交出的分界。放到整个文件里看，任一时刻缓冲区对应文件中的一段：前面一部分已经被应用程序读走，后面一部分已经从文件读进来但应用程序还没读。每个连接关联的数据结构 rio_t 里有：文件描述符；一个计数，记录缓冲区里还有多少字节没被读走；一个指向分界位置的指针；缓冲区本身的存储。

用 RIO 改写的回显程序：每次用 rio_readlineb 读一行（遇到换行符就停），再用 rio_writen 写出去。用 strace 看 write，整行只做了一次 write 系统调用，而不是逐字节写。Bryant 说他做过一些应用，拿 RIO 的代码来加上自己想要的功能，它是构建自己定制函数的很好的起点。

五、文件元数据

文件的数据是它的内容，即里面的字节。此外每个文件还关联着很多其他信息，叫元数据，由内核维护：文件是什么类型；读写执行的权限；所有者；大小；创建时间、最后访问时间、最后修改时间等。这些存在一个叫 stat 的结构体里。调用 stat(filename, &st)（或者对已打开的文件用 fstat），传入路径名和一个 stat 结构体的指针，函数会把这个结构体填好，之后用一组编译时常量和宏检查各种属性。这是这类函数的典型模式：有一个预先定义的结构体，你分配一个，把指针传进去，库函数负责填写。

例子 statcheck：对某个文件运行，它报告这是普通文件、你可以读；用 chmod 把所有权限设为 0 后再运行，它报告不能读了。有同学问 stat 到底做什么，Bryant 演示了查文档的方法：在命令行输入 man stat，得到的是 stat 这个 Unix 命令的说明，它可以打印文件的一些信息；输入 man 2 stat，得到的是系统调用的说明，因为 Unix 的 man 手册分成若干节，系统调用在第 2 节，内容会比你想知道的还多。

六、内核怎样表示打开的文件

Bryant 警告，这部分是"很讨厌的考试题"的来源，可以保证期末会考，而且能出得无比晦涩，要认真读书里这部分，做练习题，看往年考题。内核用三张表表示打开的文件：

  • 描述符表：每个进程一张。每个打开的文件在里面有一项，指向打开文件表里的一个条目。0、1、2 有固定含义，其余是程序运行期间打开、尚未关闭的文件。
  • 打开文件表：所有进程共享一张，由操作系统维护。每打开一次文件就分配一个条目，里面有文件位置（下一次读写从哪里开始），以及引用计数，即有多少个描述符表项指向这个条目。后面会看到多个进程可能共享一个条目，引用计数是追踪内存分配的标准方法，操作系统用它判断何时不再需要这个条目。
  • v-node 表：同样所有进程共享。每个文件一个，无论打开与否都有，包含这个文件的信息：存在哪里、stat 能拿到的那些信息、大小、类型等。

共享的几种情况

  • 两个描述符指向两个不同的文件：最常见的情况，各有自己的打开文件表项和 v-node。
  • 同一个程序对同一个文件调用两次 open：得到两个不同的文件描述符和两个打开文件表项，它们指向同一个 v-node，可以在同一个文件的两个不同位置读写。这有道理，比如想同时从文件的两个位置读；或者一个描述符用来往前写、另一个读已经写好的字节。两个描述符同时写同一个文件不是好主意，可能把文件搞得一团糟，但操作系统并不阻止，这是合法操作。要点是分清共享发生在哪一层：两个打开文件表项共享一个文件时，它们的文件位置可以不同。
  • fork 之后：子进程继承父进程的很多东西，其中之一是描述符表，得到一份副本，父子进程描述符表里的项完全相同，于是它们共享打开的文件，而且是在打开文件表这一层共享，文件位置也共享。父进程 read 一次，文件位置往前移，子进程再 read，就从新的位置读起。fork 会让引用计数加一，所以要父子进程都调用 close，文件才真正被关闭。之后父子进程还可以各自打开、关闭自己的文件，就更乱了。Bryant 说这就是考题会很有意思的原因。

I/O 重定向和 dup2

dup2 也给生活增添了乐趣，也给考题提供了素材。dup2(oldfd, newfd) 把描述符表的 oldfd 项复制到 newfd 项。它最常见的用途是 I/O 重定向，即命令行上的大于号和小于号：不从标准输入读而从文件读，或者不写到标准输出而写到文件，比如 ls > foo.txt。shell 的实现方式是在启动程序之后不久调用 dup2，让描述符 1 不再是原来的标准输出，而是要写入的那个文件；输入重定向同理。你也可以自己调用 dup2，而且确实有充分的理由这样做。

例子：标准输出指向终端；打开文件 B，得到描述符 4；调用 dup2(4, 1) 后，描述符 1 和 4 都指向 B 在打开文件表里的那一项，引用计数为 2。这时通常要关闭描述符 4（这发生在启动程序之前）。不关该关的文件会造成很多 bug，描述符表和打开文件表里一个东西有多个引用时很容易出错。有同学问 dup2 原来指向的那个条目怎么办：Bryant 说 dup2 的参数方向和直觉相反，意思是"让 newfd 变成 oldfd 所指的东西"；复制之前，它会先把 newfd 原来指向的条目的引用计数减一（必要时关闭它），否则那个条目就成了孤儿。dup2 很强大，也很危险。

七、标准 I/O

应用程序更常用的是标准 I/O，即 Kernighan 和 Ritchie 书里介绍的那套函数，它是 C 标准的一部分：打开关闭文件的 fopen、fclose，读写字节的 fread、fwrite，读写文本行的 fgets、fputs，格式化读写的 scanf、printf 等。标准 I/O 把打开的文件建模成流，即对文件描述符加缓冲区的一个抽象。C 程序开始时就有三个打开的流：stdin、stdout、stderr。它主要增加的东西和 RIO 一样是缓冲，从而避开底层 I/O 的一些麻烦。

例子：一段代码用 printf 逐个字符打印 hello，用 strace 看，只有一次 write 系统调用，和 RIO 一样先攒满缓冲区，直到调用 fflush 才强制输出。通常这会自动发生，打印一个换行符时就会刷新，所以 Bryant 说那句 fflush 可能是多余的。

三种 I/O 怎么选

现在见过三种 I/O：称为 Unix I/O 的底层调用；为书和课程专门写的 RIO；以及 C 标准库提供的、更大也更丰富的标准 I/O。RIO 和标准 I/O 都建立在 Unix I/O 之上。有人会问：既然 Unix 已经有带缓冲的 I/O，为什么还要自己写一个？原因是标准 I/O 对终端和文件很好用，对网络连接却不好用，它不是为此设计的，会出很多问题，所以主要是做网络时才会用 RIO。另外，标准 I/O 和 RIO 不能很好地共存，它们各自维护自己的缓冲区，互相不知道对方，会彻底乱掉，所以对任一个 I/O 连接只能二选一，不要混用。

  • Unix I/O：最通用、开销最低，其他 I/O 包都建立在它上面，能访问文件元数据，而且是异步信号安全的，可以在信号处理程序里用；缺点是从应用程序的角度用起来很痛苦，不足值和错误码都要自己处理，高效地读文本行需要某种缓冲，也很麻烦。
  • 标准 I/O：缓冲减少了系统调用、提高了效率，自动处理不足值，有 printf、scanf 这些好用的功能，统一且在所有系统上都有，相当标准化；缺点是不能访问文件元数据，不是异步信号安全的，不适合网络套接字的输入输出。

一般原则：日常使用文件时尽量用最高层的 I/O 函数，大多数 C 程序员一辈子只用标准 I/O 就能完成全部工作；需要时才用底层 I/O，比如信号处理程序里不应该用标准 I/O，而对性能要求极高的少数场合也会用它；做网络编程时用 RIO。

还有一个学生年年都犯的错：对不是文本行的东西用面向文本行的 I/O，比如 JPEG 图片。那些函数会特殊对待行尾字符 0a，遇到它就停，在 Windows 和 Unix 之间还会把换行和回车换行互相转换；strlen、strcpy 这类函数遇到空字节也会停，而发送网络包时这完全不是你想要的。所以对二进制数据、网络通信这类场合，你熟悉的那些函数可能完全不合适，要搞清楚自己在做什么。

延伸阅读

想真正弄懂这些，可以读 W. Richard Stevens 的书。他很早就去世了，但他的书仍在，一直有人接手作为合著者出新版本。Bryant 说如果想当顶尖程序员，这是最好的书，但书架会被压得够呛，有卷一、卷二、卷三，还有网络方面的几本，Stevens 是百科全书式的参考书。另一本只讲 Linux 的书更细，因为只讲一个系统，读起来没那么怪，而 Stevens 会说"这个版本的 Unix 这样、那个版本那样"，看得人发疯，但仍然是极好的书。最后课件里有一个打开几个描述符、做几次 dup2、再 fork 的例子，指针乱成一团意大利面，问程序会打印什么，这就是用来"折磨"学生的那类题，书里有类似的题，建议练一练。
