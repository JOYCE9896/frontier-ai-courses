Jonas Nelle、Sam Whitmore：Cursor 的第三个时代，云端 Agent

Cursor 云端 Agent 团队现场演示：给 Agent 一整台云端虚拟机，让它自己装环境、跑代码、测试、录演示视频再交 PR；顺带聊 slash 命令、子 Agent、多模型 best-of-N、能连跑三天的 grind mode、每个开发者的 token 开销，以及 Agent 的记忆和“自我认知”

主持：swyx · 嘉宾：Jonas Nelle（Autotab 联合创始人，现在 Cursor 做云端 Agent）、Sam Whitmore（此前在 New Computer 做个人 AI 产品 Dot，现在 Cursor 做云端 Agent）· 发布日期：2026 年 3 月 6 日 · 时长：1 小时 11 分 · 整理：Joyce（@JOYCE9896）

这一期的内容

这期在 Cursor 新办公室录制，只有 swyx 一位主持。两位嘉宾都是带着自己的创业公司加入 Cursor 的：Jonas Nelle 做过 Autotab，一家 2023 年就开始做“让模型操作电脑”的公司，节目说明里说这次发布的电脑操作能力就是他把 Autotab 的经验产品化；Sam Whitmore 之前在 New Computer 做个人 AI 产品 Dot，研究过持续学习和个性化。节目说明给的背景是：硅谷的共识是“IDE 已死”，连 Cursor 这家以 VS Code 分支起家的公司，内部用 Agent 的量也已经超过了 Tab 补全。云端 Agent（cloud agent，指在远程服务器上替你跑的编程 Agent，你关了电脑它也在干活）Cursor 去年 6 月就上线了，这次发布的重点是给每个 Agent 一整台配好开发环境的云端电脑。

前半段是屏幕共享演示：Agent 怎样自己测试改动、录一段演示视频交给你看，你还能远程接管它的桌面和终端；后面讲 /repro、/no-test 这些 slash 命令，用 Datadog MCP 诊断 Agent 故障，Slack 怎样变成团队一起开发的地方。后半段聊产品取舍（为什么网页版不给文件编辑器、要不要做托管）、多模型同题对比和“council”合成、子 Agent、能连续跑三天的长时任务模式，以及每个开发者每月会花多少钱在 token 上。swyx 追问最多的是 Cursor 要不要像 Lovable、Bolt 那样把部署也包下来，以及 Agent 公司要不要自带模型路由；Jonas 在托管问题上明确说现在不做。最后两位各给了一个年底前的预测。节目说明里的大会宣传已略过，节目本身没有广告。

01. 开场：为什么要给 Agent 一台电脑

节目位置 0:00:00–0:02:12 · Agentic Code Experiments / Why Cloud Agents Matter

片头两段

片头是从后面剪出来的两段话。Sam 讲了一个去年做过、当时没上线的实验：一个“LLM 裁判”，它不光在几份结果里挑一份，还自己能写代码，把两个或 N 个模型的长处合起来写一份新的 diff（代码改动）。他们发现底层用不同厂商的模型，效果比全用同一档模型更好，有种“协同”的输出。Jonas 的一段是：一个人配一个模型干得更快，好比让水流得更快；他认为未来几个月的大突破在把管子加粗，更多并行，用 Agent 集群或者并行 Agent，在同样的时间里做完多得多的事。

以前的云端 Agent 只能“视读”代码

swyx 开场说，这周是 Cursor 史上最大的发布之一。Cursor 以前就有云端 Agent，这次是“给 Cursor 一台电脑”。他半开玩笑问：是不是就是买了 Autotab 再重新包装一下？Jonas 笑着说这是很大一部分。

他解释，云端 Agent 以前也跑在自己的电脑里，但只能“sight-read”代码，就是只看不跑。那些机器通常是空白虚拟机（VM），没有按 Agent 正在处理的仓库配好开发环境（他们叫 DevX）。他让人设身处地想：如果你是模型，只能看着 token 流过去，只能读代码、吐 token，然后祈祷自己做对了，你会做得很差，显然你得把代码跑起来。他说这个观点不算反主流，但之前没人真做到。

他们做的是：给模型工具让它自己“入职”（onboard，自己装依赖、配环境），再让它端到端地做电脑操作（computer use，模型看屏幕截图、输出鼠标坐标和键盘操作）：“像素进，坐标出”，云端电脑里装着各种应用。Jonas 说这在 Cursor 内部带来的变化是，大家从“只拿它改改文案”变成“用它真正推进新功能”。

02. 现场演示：会测试、会录视频、可远程接管

节目位置 0:02:12–0:06:28 · Live Demo Tour / Testing Defaults and Controls / Videos and Remote Control

第一根支柱：交 PR 之前先测试

Jonas 打开 cursor.com/agents。左边是聊天，最经典的 Agent 界面；新东西是 Agent 会测试自己的改动。他演示的这个任务跑了半小时，因为模型不光写代码，还启动开发服务器、端到端测试、需要时再改。交回来的就不再是“我试了点东西”的 PR（pull request，合并代码的申请），换成了“我测过了”的 PR。他用来解释的一个类比是：同事没测就让你 review，你也会烦，只有真准备好了才该来找你。

swyx 问：有些 PR 就是改文案，也每次都测、都录视频吗？Jonas 说不一定，由模型判断。他们给了默认提示，告诉它哪些改动值得测；用户可以加 /no-test 命令让它不测。swyx 追问默认是不是测，Jonas 说默认是“校准过的”：很简单的文案改动不测，复杂一点的测。用户也可以在 agents.md（写给 Agent 看的项目说明文件）里规定，比如“改到 monorepo（单一大仓库）里这个子目录时永远别测，因为测不了”。

第二根支柱：演示视频

Jonas 说，在 Agent 能端到端写出多得多代码的新情况下，review 代码成了新瓶颈。看视频代替不了看代码，但比一上来就看一大坨 diff 好入手得多。通常的流程是：启动一个任务，做完回来先看视频。他演示的例子是给一个按钮加 tooltip（鼠标悬停提示），Agent 录了效果，有时还会自己搭一个类似 Storybook 的组件展示页，让你看组件在各种状态下的样子。

第三根支柱：完整远程控制

第三是你能完全远程控制这台 VM：可以悬停、打字，终端也能完全接管。他说视频有时就够了，但视频经常不完美，它告诉你的是这东西能直接合并，还是值得继续迭代。他有过几次第一版视频不完美，但让他确信方向对，再跟进两三轮就能合并了。有些东西你就想上手玩玩，什么都替代不了实时预览，这靠 VNC 远程桌面实现。swyx 问 VNC 是什么，Jonas 说就是远程桌面。

Sam：视频解决的是“需求没说清”

Sam 说视频对她帮助最大。她以前用 Agent 和云端 Agent 常遇到的问题是需求说得不够细（under-specification）。plan mode（先和 Agent 来回讨论出详细实现方案再动手）能降低这个风险，但就像人和人沟通，时间长了也会走样：她费劲把分支拉到本地跑起来，才发现“我说的是开关，你做成了复选框，这个细节怎么没做对”。视频摆在最前面，等于和 Agent 之间有了一个共同的参照物，对齐变得很清楚。

03. 更多演示：后端改动、Agent 改 Agent、best-of-N

节目位置 0:06:28–0:11:21 · Meta Agents and More Demos

只能做前端吗

swyx 正要问“是不是只适合前端”，Jonas 就拿出一个以后端为主的例子：保存 secret（密钥、令牌这类敏感配置，Agent 访问某些系统要用）的报错信息。云端 Agent 支持添加 secret，这是 Agent 入职时获取权限的一部分。swyx 指出这就是云端 Agent 在改云端 Agent 自己。Sam 说这会变得“super meta”。Jonas 说 Agent 能启动自己的云端 Agent、跟它们对话，所以他们目前禁止了云端 Agent 再启动更多云端 Agent，“也许以后会开”。

这个 bug 是：secret 有大小上限，超了以后只显示一个笼统的“保存失败”。Jonas 让它改成像样的报错。他说第一个亮点是他没教它怎么测：它没去把一个字符敲 5000 遍，直接打开浏览器开发者工具，写一段 JS，往输入框里塞 5000 个字母 A，关掉开发者工具，点保存，看到了新报错。视频末尾被截断了，但有一张报错截图。swyx 总结：前端加后端的端到端功能，需要一整台 VM、整台电脑把所有东西跑起来。

Autotab 的教训：给模型像素和一台机器

Jonas 说这是 Autotab 的经验之一。他们 2023 年开始做（他先说 2022，又改口），当时做法五花八门：浏览器操作、DOM（网页的结构化元素树）等等。最后他们变得很“AGI-pilled”：直接给模型像素，给它一个盒子。“盒子里的大脑”是你要的，要去掉上下文和能力上的限制，让瓶颈只剩智能；以今天模型的聪明程度，这个瓶颈还很远。给它整台 VM、像人一样把开发环境配好，对他们内部是一次能力上的台阶式提升。

swyx 说一年前模型还根本做不到这些，Sam 补充说半年前都做不到。swyx 听人说大约 Sonnet 4.5 时，纯靠像素全自动开始够用了。Jonas 说“够用”永远是个程度问题，他们觉得 Opus 4.5、4.6 和 Codex 5.3 又各是一次台阶，模型能自己去把细节弄清楚、做完再回来。

设计细节和 best-of-N 用得更多了

swyx 夸了几个设计细节：页面用的 TanStack Router（他说自己参与过给 TanStack 起名）；视频播放器有类似 Vimeo 的“章节”；Cursor 的鼠标指针是品牌化的；他向 Evan 抱怨“你们什么都品牌化了，就壁纸没有”，结果 Evan 说壁纸也是 Cursor 的。Sam 说壁纸是 Rio 挑的，视频章节大概是 Alexi、Matthew、Federico 等人做的。下载视频时末尾会加一段 Cursor 标识，像 TikTok 那样。

Jonas 说这个 TikTok 式片尾就是发布视频里 Alexi 演示的、由云端 Agent 做的功能。他借此说到视频带来的一个后果：他们用 best-of-N（同一个提示交给几个不同模型各做一遍，挑最好的）多了很多。以前的难处是跑四个模型，回来四份 700 行的 diff，你总不能全看一遍；现在回来四段 20 秒的视频，四段他愿意看。就算哪个都不完美，也能挑出最值得继续迭代的那个。

04. /repro：先复现 bug 再修

节目位置 0:11:21–0:14:13 · Bug Repro Workflow

Jonas 的下一个例子后来做成了 /repro 命令。思路是：Agent 有完整 VM，就可以先复现 bug、录一段 bug 出现的视频，修好以后按同样步骤再录一段 bug 不再出现的视频。他说这是变化最大的一类任务：以前这种 bug 很难复现，本地要花大量时间，就算交给云端 Agent，你也不确定它真修好了；现在可能 90 秒就合并了。

演示的 bug 在 cursor.com/agents 上：附上几张图片再删掉，提交提示时删掉的图片还是会被一起发出去。视频里 Cursor 用的是完整桌面，Jonas 特别指出，这种需要上传文件的场景如果只做浏览器操作就会很痛苦，Agent 是用系统原生的文件选择器上传的。这也是“Cursor Agent 在自己的环境里给 Cursor Agent 发提示”。修复前的视频里，提交时界面上只留了一张图，发出去的提示里却附着五张；修复后的视频按同样步骤附图、删掉几张、发送，附件里只剩一张。swyx 说“漂亮”，Jonas 说“轻松合并”。

swyx 问它什么时候会主动这么做，毕竟多了一步。Jonas 承认还没把模型“何时复现”校准好，有时它会自己做。他们比较保守，只在比较确定时才让它做，因为会多花时间；所以加了 /repro，你写“修这个 bug /repro”，它就知道要先录视频证明能复现。swyx 把这和机器学习里的 reward hacking（奖励作弊，模型钻评估规则的空子拿高分）联系起来：先写测试、看它失败，再让测试通过，就是经典的“红-绿”TDD（测试驱动开发）。

05. slash 命令、Datadog 诊断，以及开发搬进 Slack

节目位置 0:14:13–0:34:00 · Slash Commands and Diagnostics

几个好用的 slash 命令

swyx 说 slash 命令多得要命，问哪些好用。Sam 说他们也想提高可发现性。Jonas 说内部有很多不太有意思的，举了一个他给自己做的 /fix-bb，即 Fix BugBot。BugBot 是 Cursor 的自动代码审查机器人，刚上线了 BugBot Autofix，点一下或改个设置它就会自己修自己发现的问题，很多情况下效果不错。但有些情况下，让最初写这个 PR 的 Agent 带着原始提示和全部上下文去修更好，比如 bug 其实是一次回归，原意是另一种写法。/no-test 和 /repro 也在列表里。

Sam 最喜欢的是“cloud agent diagnosis”，团队里的 Nick 和 David 写的，重度依赖 Datadog MCP。MCP（Model Context Protocol）是让模型调用外部工具和数据源的通用接口标准。某个云端 Agent 出问题时，把它的 ID 作为参数传进去，命令会起一批子 Agent，用 Datadog MCP 翻日志，找出所有可能出错的地方。简单问题在 Datadog 界面里也能很快查，但这样把排查压缩成一次 Agent 调用，不用自己翻日志。

读另一个 Agent 的 transcript

Jonas 提醒 Sam 讲 transcript 的用法。Sam 说内部已经在用、不久会公开一些版本：起一个 Agent，给它另一个 Agent 的 transcript（完整对话记录），要么当外部调试器排查发生了什么，要么像 fork 一样接着那段对话继续。swyx 问 transcript 是不是包括 11 分钟、45 分钟里的全部思考过程，Sam 说是。她说这些都是同一套云端 Agent 基础设施、同一个 harness（包在模型外面的那层程序：提示词、工具、循环逻辑），只是提示不同；把外部 transcript 作为附件传进去需要一点额外基础设施，诊断命令则主要靠 Datadog MCP。

他们这次发布还顺带上线了云端 Agent 的 MCP 支持，Sam 说这被淹没了，下周会单独宣传。她说不确定 Datadog MCP 是否已公开，他们在内测。swyx 由此谈到 Datadog 的处境：Datadog 有自己的云端 Agent 产品 Bits，想做“自愈软件”那一块；Cursor 对编程 Agent 有强烈主张，会从这里分走一部分。对一个“记录系统”（system of record）公司来说，是把日志开放给 MCP 让别人做，还是自己做，是个有意思的问题。Sam 说她只知道自己很爱 Datadog MCP，swyx 说用户肯定会要求开放。

Tab 进博物馆：Cursor 的“三个时代”

swyx 问云端 Agent 什么时候上线，回答是去年 6 月，一直在慢慢演进。他提到 Michael 发过一张图，Agent 用量超过了 Tab，他认为这是过去一年代码领域最大的转变，但没什么人注意；对话里还提到，当天 Andrej Karpathy 也特别指出了这件事。swyx 开玩笑说 Tab 键该进博物馆，Jonas 说他自己也有一阵没用 Tab 了。

Jonas 说用 AI 写代码、乃至创造软件的方式在快速变化。他认为外界低估了一点：Cursor 对此很有自觉。Cursor 起家于第一阶段，即 Tab 和自动补全，那在当时很有用；但很多人还是看着文本文件改代码，现在他们管亲手敲字母叫“手写代码”（hand coding），swyx 说这听起来“好 Boomer”。这个转变先是慢慢加速，最近几个月急剧加速。他认为同样的事会再发生一次：Tab 的痛点是“我想多交给 Agent 一点，不想一次一个 Tab”；接下来会从“Agent 交回 diff、你陷在细节里、给它 30 秒到 3 分钟的任务”，变成“给它 3 分钟、30 分钟到 3 小时的任务，拿回来的是视频和可试用的预览”。

Slack 成了 IDE

Sam 说云端 Agent 在内部起飞后，另一个变化是开发从个人驱动变成协作式的。对他们来说 Slack 几乎成了 IDE：在问题频道和产品讨论频道里，大家一直在 @Cursor，这会启动一个云端 Agent。他们开了团队跟进功能：Jonas 在一个帖子里 @Cursor，她可以接着补充上下文。她有时让 Agent 先调查，再让它跑 git blame（查每行代码是谁改的），在 Slack 里把该参与的人拉进来。swyx 说 Cursor 应该更大声宣传这一点。

swyx 说他也有同样体验，只是参与的不都是开发者：他负责技术营销方向，设计师管设计，销售提供和客户谈好的法律条款，大家一起纠正 Agent。Jonas 说他们发现，这些帖子里人类剩下要讨论的，才是真正有意思的部分：要不要发、这个 UX 对不对、形态对不对、怎样让用户更容易看懂，至于 if 语句放哪，交给云端 Agent。也不用再讨论“你做还是我做”。swyx 建议加一个“静音键”，让人类先在帖子里自己讨论。Jonas 说目前设计就是不 @ 它就不插话，但它能看到中间的所有消息。swyx 问 Cursor 能不能 @ 另一个 Cursor，Jonas 说做过一些版本。

代码好写了，上线变难了

Jonas 说生成代码变容易的连带结果是，把代码送上生产环境还是比应有的难：“解决一个瓶颈，冒出三个新的。”内部有个笑话：聊到某个功能，总有人说“我已经有个 PR 了”。拿到 PR 很容易，从“有 PR”到“我有把握、可以合并”仍然相对难。他说未来几周到几个月，他们想的是怎样把算力投到这条从 Agent 初稿到合并的流水线上。swyx 问这不就是 Graphite（代码审查工具）干的事吗，是不是已经整合了；Jonas 说 Graphite 是很重要的一部分，以后会有更多可说，目标是端到端体验，Cursor 帮你创造软件，不只生成代码 token。

swyx 提到有两派看法：一派说需要 AI 来审 AI，另一派说 review 已死，给我看视频就行。Sam 说对她来说视频主要用来对齐，她多半还是想走代码审查、看文件。她很看重 BugBot，内部采用率很高，规定 BugBot 的评论不能不处理。只要有两三次合并后发现 bug、回头一看 BugBot 早就指出过，你就学会等它了。她认为会有不同层次的审查：代码层、功能层，以后大概还会有性能审查、安全审查等；有些像 BugBot 是同步的，合并前要等它。

Jonas 补充：云端 Agent 把并行度和代码量放大以后，10 人的创业公司开始需要过去 1 万人公司才需要的开发流水线，也就是大公司为了安全上线大量代码发明的那些东西：频繁发布、缓慢放量、分阶段发布、设检查点、自动发现回归。swyx 补上 stacked diffs 和 merge queue（合并队列），Jonas 说就是这些。swyx 说大多数人还不知道 stacked diffs 是什么，他和 Graphite 很熟，但因为没在大团队里工作过，从没需要过。他说 GitHub 好的一点是，它是协作软件，但对单人开发者也有用，很多开发工具没做到“从大往小”；Jonas 说 Cursor 正相反，是“从小往大”。

团队版：Marketplace 和共享配置

Jonas 说 Cursor 涨得快，部分原因是团队里任何人都能上手，很多人周末拿它做个人项目，喜欢到带进公司。现在 Cursor 在做团队体验：团队里第十个开始用 Cursor 的人，一上来就配置好了。他们最近上线了 Marketplace，别人可以配置 MCP 和 skills 这类插件。Sam 很喜欢 Datadog MCP 和 Slack MCP（后者也还没发布），如果她觉得某个必不可少，他的 Cursor 就该自动配好。swyx 问是自动共享吗，Jonas 说看 MCP：有些按用户授权，Sam 没法用自己的 Slack 授权他的 Cursor；有些是团队授权，管理员可以统一设置。

swyx 回忆 Cursor 只有五个人时请 Aman 上过节目，那时候大家都觉得 VS Code 分支很难走到团队版、企业版，现在居然成了，人们真会付钱。Jonas 说云端 Agent 预计也走类似的 PLG（产品驱动增长，用户自己试用再推广到团队）路线：一开始小团队采用多，因为代码库没那么难配；如果你需要某种疯狂的 Docker 层缓存才能让构建不用两小时，那要过一阵才能支持。前端加后端、一键就能装的，Agent 自己就能装好。

VM 的技术问题：规格、持久化、快照

  • 能不能选 VM 大小？还不能，计划加，像 Amazon 那样的 L、XXL 菜单。swyx 说某种意义上他们得变成一个 EC2，“租一个盒子”；Jonas 说他们常讲“盒子里的大脑”，Cursor 想做的就是这个。
  • 是 serverless 还是持久的？Sam 说希望有一定持久性，桌面应该过几天还能回来，比如一个功能你会琢磨一阵；swyx 问是不是整个挂起内存再恢复，她说对。
  • swyx 说他想要的是用自己的账号登录，但凭据不存进任何 secret store，就跟着镜像保留下来再“复水”（rehydrate）继续用；他认为多数基础设施是无状态的，只能存成 Docker 镜像，因为只有这样才能并行克隆多份。
  • Jonas 说他们有几种配置方式：有基于 Dockerfile 的；默认是快照，就是在一台 Linux VM 里跑一堆安装命令，然后对文件系统做快照，新 VM 从这个模板起。这和 Sam 说的休眠再恢复不同，后者是连内存一起快照，浏览器停在哪一页，恢复后还在那一页。

swyx 还问，演示视频为什么总带着桌面和浏览器边框，只演示前端时只拍浏览器不就够了？Jonas 说视频里有平移和缩放，Agent 录制和剪辑时可以决定突出哪里，他们试过几种分段方式。

06. 极简网页界面，为什么不给文件编辑器

节目位置 0:34:00–0:36:40 · Minimal Web UI Surfaces / Why No File Editor

下线了一半功能

Jonas 说现在 cursor.com 上看到的版本，大约只有功能最多时的一半，他们主动下线了不少东西。一个是本地浏览器预览：通过端口转发，在你自己电脑的浏览器里打开 localhost:4000，就转到 VM 里的 localhost:4000，swyx 说像 ngrok。下线的原因是远程桌面延迟已经够低，而且更通用：他们既做 Cursor Web 也做 Cursor Desktop，前面演示里 Agent 要上传文件，只有浏览器的话你没法打开文件选择器。

他说这话出自 Cursor 可能有点好笑：Cursor 从 VS Code 分支起家，继承了很多好东西，也继承了很多 VS Code 的老界面。网页版他们想刻意保持极简，只暴露一组合适的“应用界面”（app surfaces），这些是云端环境里你和 Agent 共用的东西：Agent 能控制桌面，你也能；Agent 能跑终端命令，你也能。下线的东西以后也可能重新上线，如果他们改变了对取舍的看法。swyx 说就是先放出去，等用户说想要再加回来。

文件编辑器：限制它，人就会多交给 Agent

另一个下线的是 Files 应用。内测时右侧除了 Git、Desktop、Terminal 还有一个能看能改文件的 Files。他们觉得限制你能做的事，人自然会把更多交给 Agent，养成委派的新习惯，他们认为这很有价值。所以现在 Cursor Web 里没法编辑文件，只能去 GitHub 上的 PR 里改，或者“告诉 Agent”。

swyx 说他为同样的事批评过 OpenAI：Codex 应用有文件查看器，没有编辑器。Jonas 问他常用查看器吗，swyx 说不常用，但有时就是想要。他是 Codex 早期测试者，当时有人指出界面上有“在 Cursor 中打开”“在 Antigravity 中打开”这类按钮，认为这是“设计异味”，说明你其实想要一个带编辑器的 VS Code 分支；OpenAI 的回答是“相信我们”。

Jonas 说 Cursor 作为产品要覆盖整条光谱：能在很高的抽象层工作，也能双击下去看最底层。但你不会在 Slack 里做那种事，所以有些界面限制 UX 能力反而更干净、更简单，把人推向新习惯。他们内部都开玩笑说没人手写代码了，所以要为未来造产品，不为过去。

07. Cursor 要不要连部署一起做

节目位置 0:36:40–0:38:49 · Full Stack Hosting Debate

swyx 的观察是：Cursor 这类公司从开发工具出发，一路走向云端 Agent；Lovable、Bolt 这些从 vibe coding（用自然语言让 AI 生成整个应用）出发，本来就是全托管的云端形态，“在别人有云端 Agent 之前就已经是了”。它们有完整的部署平台，拥有整个闭环：基础设施、日志、线上站点都在自己手里。Cursor 至今不拥有这个闭环，没有自己的 Vercel 这类部署设施。好处是任何人、任何企业都能用；坏处是没法完全端到端地调试。他问会不会有“全栈 Cursor”，比如 cursorapps.com，基本是个 Vercel 克隆。

Jonas 说这是个好问题，swyx 推演的逻辑他大体同意。但他们现在专注于下一个大瓶颈，而且 Datadog MCP 这类东西已经存在，他不认为现在做托管是帮客户发更多软件的最好方式；眼下最大的瓶颈是把代码送出去。另外 Cursor 和 Lovable、Bolt 不同，更关注现有软件，从零到一的新项目是很不一样的问题。他举例：想象去说服 Shopify 部署到你的平台上，那完全是另一回事，要很久才能看清，也可能永远不会发生。swyx 说确实诱人，因为一半的应用都是 Vercel、Supabase、Tailwind、React 这一套标准栈。

08. 模型选择和 Auto 路由

节目位置 0:38:49–0:40:59 · Model Choice and Auto Routing

swyx 指出云端 Agent 里的模型选择藏在左下角，今天是 Codex High，换成 Opus 他大概也不在乎。Sam 说他们一定会给用户跨模型的选择，因为“版本答案”变得很快：她曾是 Opus 4.5 的死忠，Codex 5.3 出来后立刻彻底切换，现在只用它。swyx 说他在 Slack 里用时，Cursor 会显示正在用哪个模型、怎么切换，其他时候都被抽象掉了，他觉得这样很好。

Jonas 说他们想在默认值上做更多，替用户推荐。桌面版编辑器里有 Auto，会帮你路由请求，云端 Agent 还没做，但会想做类似的。用户里既有 Sam 这种很懂、清楚自己要哪个模型的人，也有希望 Cursor 替他选最好模型的人。Cursor 既有流量，也有内部的品味和经验，知道什么最好。

swyx 讲了他的“Agent 实验室 vs 模型实验室”论点：Cursor 这类公司是 Agent 实验室，在写一套和模型实验室不同的打法，模型实验室很吃 GPU（他也提到 Cursor 有研究团队）。他认为每个 Agent 实验室最后都会有一个路由器，因为用户会问“到底该用哪个”，他自己不会天天跟进，他会说“把我放到 Cursor Auto 上”，用你们从所有用户那里得到的认识替我决定。他问 Auto 免费吗，回答是不免费，有不同价位。swyx 认为这会给 Agent 实验室额外的话语权，因为用户不再对某一家模型实验室忠诚。

09. best-of-N、并行 Agent 和多模型 council

节目位置 0:40:59–0:44:18 · Best Of N and Model Councils

每个 Agent 一台 VM

Jonas 说 best-of-N 在 Cursor 的 IDE 和网页版都有，问题在于在哪儿跑。他再次共享屏幕：在下拉框里勾选多个模型，发一个提示，五个模型同时跑。swyx 说这就是 Cursor 2.0 的做法。swyx 问 best-of-N 和并行 Agent 是一回事吗，Jonas 说 best-of-N 是并行 Agent 的一个子集，特点是同一个提示。

这里跑的是云端版本，比 worktree（git 的工作树功能，同一个仓库同时检出多个分支到不同目录）好的地方是每个 Agent 有自己的 VM，能各自跑命令，不会去杀掉另一个 Agent 正在用的端口，这些是大家以前常见的痛点。本地并行 Agent 之前主要靠 worktree，swyx 说这太让人困惑了，没人知道 worktree 是什么；Jonas 说他们正在逐步淘汰 worktree。

council：跨厂商模型合成更好

Sam 讲回片头那个实验：先跑一批 best-of-N，再加一层“合成器”模型，是 LLM 裁判，但也是 Agent，能写代码；它不光挑一份，还吸收两个或 N 个模型的长处写一份新 diff。他们发现，至少在当时，底层用不同模型厂商的模型更好，输出有协同效应，比全用同一档模型强。她的推论是：即便将来某个模型暂时领先，让多个顶级模型一起进 Agent 集群也可能有好处，因为各有长短。

swyx 说 Andrej 把这个叫 council（委员会）。Sam 说内部正好有个 Ian 写的命令叫 /council。swyx 说这个想法到处都有各种形式，但产品化很难：Cursor 现在的界面很灵活，再加一个 council 就太多了。Sam 说理想情况是用户只要选上，全部在后台完成，最后拿到更好的结果，不用迷失在中间的评判过程里。

10. 子 Agent：拿来管上下文

节目位置 0:44:18–0:47:41 · Subagents for Context

Jonas 接着说，另一种让多个 Agent 协作的方式是子 Agent（subagent，主 Agent 派出去做一部分工作、做完只交回结果的小 Agent），这个想法提了很久，最近才开始管用：不同提示、不同目标、不同模型、不同“年份”的 Agent 一起协作、互相委派。swyx 说他总在找“今年是 X 之年”，今年的 X 之一就是子 Agent，但他还没在 Cursor 里用过；他问了一串大家顾不上回答的基础问题：每次新建还是固定的？跟 slash 命令有什么区别？

Sam 说子 Agent 是另一个团队做的，她不代表他们发言，但内部的体会是子 Agent 很适合管理长线程的上下文，或者想往一件事上多砸算力的时候。他们用的是一个通用的任务接口，由主 Agent 决定交给子 Agent 什么。你说“探索我的代码库”，它可能起一个 explore 子 Agent，也可能起五个。swyx 追问自己能不能定义子 Agent，Sam 说有内置的，比如 explore 是预置的，你也可以指示模型用别的子 Agent，它会照做。你现在在 Cursor 里说“起 50 个子 Agent 探索这段代码”就能看到。

Jonas 在桌面版现场演示：他让主 Agent“用一个子 Agent 去探索”，点进去能看到子 Agent 跑了 find 命令。他的主模型是 Opus，但这个子 Agent 底下用的是 Composer（Cursor 自己的模型），因为探索要读大量东西，快一点的模型能更快给出答案，这是智能路由。他们想开放更多 hooks（钩子，让用户在特定节点插入自定义逻辑）让人配置子 Agent。

他说另一个内置子 Agent 是云端 Agent 里的电脑操作子 Agent。电脑操作的轨迹很长，带大量图片，还要执行测试验证，他们想用在这方面特别强的模型，这是用子 Agent 的一个理由。另一个理由是上下文：子 Agent 是一个很干净的边界，可以把整段操作和测试过程压缩成子 Agent 写的一条最终消息交给主 Agent，不用做全局压缩（compaction，上下文快满时把历史对话总结变短）。

11. grind mode、吞吐量、token 开销、招聘和预测

节目位置 0:47:41–1:04:38 · Grind Mode and Throughput

Wilson 的浏览器实验变成了 grind mode

swyx 说聊 Cursor 就不能不聊 Wilson：他用 Agent 做了一个浏览器、一个操作系统，试了很多架构，最后等于重新发明了软件工程师的组织结构图。他问有没有幕后故事。Sam 说 Wilson 的部分实验已经变成云端 Agent 里的一个功能：长时运行 Agent 模式，内部叫 grind mode，选择器里已经能看到一点影子，比如“grind until done”（一直干到完成）。当时 Ralph Wiggum 循环（一种让 Agent 反复循环执行直到达成目标的做法）正在流传，Wilson 也独立发现了它，这促成了这个产品形态。

核心想法很简单：定好完成标准，没完成就不停。实现上多一些复杂度：要先对齐，有一个规划阶段，它会和你一起定计划，双方都认可之前不进入 grind 执行模式。swyx 调侃“你不让我满意我就不干活”。Sam 说这很重要，因为人们常给一个很含糊的提示，然后期待魔法；它只跑三分钟还好，要跑三天的话，就该先花几个小时确认你把需求讲清楚了。她强调真的是三天，他们有过三天的运行，中间没有任何人工干预。

吞吐量：把管子加粗

Jonas 说，Cursor 里提供的长时 Agent，抽象地看是一个“工人节点”；做出那个浏览器的是一个由工人、规划者和各种 Agent 组成的“社会”。他们一开始只用一个工人节点做浏览器，后来发现系统的吞吐量不够，做不出浏览器这种规模的东西，于是它变成了众多节点之一。

这成了他们看云端 Agent 的一个重要思路，就是工程上经典的延迟和吞吐量的取舍。代码像管子里的水，未来几个月的突破是把管子加粗，更多并行，任何单个任务不一定要做得多快。他说你一旦看到 100 个并发 Agent 每秒输出几千个 token 的系统，就回不去了。他承认有很多保留：没人在现实中用那个浏览器，很多地方还不对，但能产出真正生产代码的这种规模的系统，会比人们想的来得早，你得开始想生产系统会变成什么样。他们最近就把自己的 GitHub Actions 搞崩了，因为 Agent 推的代码太多，CI/CD（持续集成和部署流水线）过载。Cursor 本来就在快速增长，而每人跑 10 倍的 Agent，相当于员工数涨了 10 倍。swyx 说这和做 RL 基础设施的研究员遇到的是一回事：大量并行 rollout（模型做一次完整尝试的过程），怎样调度、怎样让吞吐量最大。

每个开发者要多少推理算力

Jonas 提到录制前聊过内存芯片短缺。他说那个造浏览器的系统的并发规模很难想象，如果他和 Sam 各有一个那样的系统替自己发软件，每个开发者需要的推理量会大得惊人；他有时觉得，连最乐观的算力建设预测，都低估了这类集群系统能产出多少对经济有价值的代码。

swyx 问（说可以剪掉）他们自己每人用多少 token。Sam 说她有一阵不是用量面板的管理员，看不到，但她的用量涨了，做的事也更多了。她说至少短期内她不担心开发者丢工作，swyx 笑说“是你自己说到那儿的”。她说要做的东西太多了，她比以前更有野心，比以前任何时候都忙，用更多 token，也做更多事。

Jonas 说他没有自己的数据，但他们看到并预计会持续的是杰文斯悖论（Jevons paradox，东西变便宜后总用量反而上升）。他给了一个价格阶梯：

  • 第一阶段，Tab 自动补全，人们每月付大约 20 美元。
  • 第二阶段，今天和本地 Agent 来回迭代，每月几百美元。
  • 高度并行、在各自 VM 里长时间跑的 Agent，他们已经到了每人每月花几千美元的程度，他认为未来可能到每月几万美元甚至更多。

他说 Cursor 并没有贪心想多收钱，背后的原因是个人的杠杆变大了：一个人能顶 10 个人，让他做到这点的工具就值得花钱用最好的。

招聘怎么变

swyx 问招聘：LeetCode 已死，大家都说要做工作试用（work trial）；有些人很会用 Agent，有些人需要时间，因为没在 Cursor 这种“token 富足”的地方待过，待过之后工作方式就不一样了。他想知道 Agent 编程有没有改变他们对招聘的看法。

他们的回答大意是：不把“很会用最新的 AI 编程工具”当前提条件，但这能说明一个人在跟进、有好奇心、愿意提升自己，因为过去三个月玩法完全变了，“我每天做的事都很不一样”。基础功仍然重要，需要能双击下去看细节；今天的模型仍有弱点，让它跑太久不清理不重构，代码就会变得凌乱、抽象变差，所以还是需要搭过系统、见到好模式能认出来、知道往哪里引导的人。Sam 说 Cursor 动作很快，用 Agent 工程是现在能这么快的原因之一，所以招聘时会选能快速做好决策、在这种环境里游刃有余的人，会用 Agent 帮自己做到这点也是其中一部分。

一早开十个 Agent

Jonas 又演示了一个工作方式：并行带来的好处是能在多个线程之间快速跳转。本地 Agent 的痛点是上下文切换，这个 Agent 做了这件，那个做了那件。他早上起来启动 10 个左右 Agent，第一个做完就进去看视频：差不多了就发个跟进，比如“改成红色”，或者进桌面亲手试；90 到 120 秒内要么把它重新派出去，要么开始合并流程、让 CI 跑着；然后跳到下一个，觉得有意思就让它“在真实应用里跑一下，别只在展示页里”。不用再想“那个 worktree 在哪”“我的 diff 丢哪了”“本地又在重新构建”，等五分钟。人只负责注入品味：这个感觉不对，那个架构不对。

Sam 说云端还让她能利用碎片时间，通勤或过夜，不用开着电脑。swyx 问有没有移动 App，她说她一直在手机上用网页版，能看视频、能解除卡点。swyx 说这会让编程工具开始和生产力工具冲突，比如 Linear 和看板，其实你需要一个看板（开源的 Vibe Kanban 已经有了），因为代码本身不再重要，重要的是人怎样与 Agent 互动和检查进度。他还说去年是编程 Agent 之年，今年编程 Agent 会溢出到现实世界，比如 OpenClaw，而这些都建在编程 Agent 之上。

其他行业会走软件的路

Jonas 的预测是：其他行业会开始经历软件开发正在经历的事，因为模型写软件太强、造这些技术的人又都是早期用户，先用在自己身上。软件业关于“人的杠杆到哪一步”“什么时候岗位变得更通才”这些问题已经有一些数据，未来几个月会更多，这会在各个行业发生。

两个预测和语音编程

一位嘉宾的个人预测是：今年 12 月一整个月，自己手写的代码是零行，100% 由 Agent 写。swyx 问现在还不是零吗，回答是大概 1%：有时烦了，不想为改一个小地方去跟 Agent 说。另外是写提示词时，有时还会手动改，因为提示词是纯粹的意图传递，像写文章，写的过程就是思考，所以也不让 Agent 写提示词；她说自己“还是受不了 AI 写的文字”。swyx 问那就没有 DSPy 之类的提示词优化了？回答是内部有一些相关工具，但大量工作就是想清楚要给模型传达哪些概念。

swyx 说他注意到他们没用语音写代码，连 OpenAI 的人上节目也不用语音。他们说内部有人很喜欢，会在这方面做实验；一位嘉宾说偶尔用，绑在 Caps Lock 上，只要它把上下文倒进去，不需要它回话。swyx 说语音的好处是可以打断自己、跑题，全都录下来丢给 LLM。Jonas 讲了 Autotab 的经历：他们让用户录带声音的屏幕录像来教模型做任务，结果人们用“Siri 腔”，短句、一字一顿，因为他们上次用 AI 是两年前；swyx 说 Apple 毁了一代人对 AI 的期望。他们只好告诉用户：随便倒，重复、自相矛盾都行，模型足够聪明。swyx 认为语音编程最难，因为技术词的拼写和大小写都很重要，目前语音主要用在情感陪伴这类场景。

Jonas 的预测更具体：云端 Agent、在自己盒子里干活的 Agent 超过本地 Agent，会比人们想的、比他们自己想的都慢，但交叉点会在今年年底前出现；到年底，云端 Agent 的使用量大概会超过本地 Agent 的 2 倍。

12. 云端 Agent 还差什么：环境配置和记忆

节目位置 1:04:38–1:11:18 · Cloud Agent Future and Memory

入职太慢，环境会坏

swyx 问现在哪里还不好。Jonas 说难点不少。一是把沙箱（sandbox，隔离的运行环境，Agent 在里面乱来不会影响外面）做好。这次发布里他们花了大量时间的是 cursor.com/onboard：选一个仓库，加 secret，给权限，Agent 自己去装东西。swyx 说这是他整场最喜欢的部分；Jonas 说他和 Sam 为此熬了很多夜，但还有很多要做。swyx 直接说：太慢了。Jonas 说正在改。另外环境配置不是一次性的“配好或没配好”，会随时间坏掉：新依赖、新系统权限、数据库搬了地方。

二是 Agent 在云端更自主以后，他们明显感到缺记忆。模型开始“操作”代码库时，光有读文件工具不够：后端怎么启动、怎么查后端状态，这些都跟你的代码库有关；就算它很会 npm run watch 这类默认操作，每个代码库都有怪癖。他认为让 Agent 不仅在环境上“入职”，还在理解设计取舍、代码库怎样运作、怎样在某个代码库里当个好开发者上“入职”，会是一大突破。swyx 问那是 Cursor Rules 吗、是一个文件吗？Jonas 说不会是 Cursor Rules，会是别的东西。

Sam：记忆是指针，也是 Agent 的自我审计

Sam 说 Cursor 今年学到的一件事来自 Agent 质量团队（不是她的团队）发的一篇关于“动态文件上下文”（dynamic file context）的博客，核心是“一切都是文件系统”。她这一年对记忆的看法往这个方向变了：给 Agent 指向信息的指针和注释。

第二个变化是，她认为记忆是 Agent“自我审计”（self-auditability）和自我认知的一个子集。Agent 发现自己的功能、自己的 harness 有缺口，需要某条信息半永久地补上时，可以给自己提议注释、链接或记忆文件。自我审计还有别的副产品：发现互相冲突的指令，发现互相打架的 skills 和规则，修掉自己碰到的开发环境问题。她的结论是动态文件系统对记忆很有前景，同时 Agent 需要更能看出自己功能上的缺口并决定怎么补。

Agent 要知道自己在什么系统里

Jonas 说 Sam 一直推动他们在“自我认知”上多做：Agent 应该理解它的环境怎样运作、secret 怎样运作，对自己的 harness 和环境有自觉。swyx 问这不是模型本身就有的吗？Jonas 说这是具体情况：跑在 Cursor 里和跑在别的沙箱里不一样。更有意思的是模型开始修改自己的系统提示词，怎样安全地做到？swyx 问它真会这么做吗，还是研究阶段？回答是会的，它会管理自己的上下文，系统提示词也是上下文的一部分，它可能决定开关某些东西。Sam 强调，这里说的自我认知和意识无关，指的是知道自己运行在什么系统里、有什么约束，并且有能力为在这个系统里表现最好而优化自己。

Sam 讲了她在 Dot 上线时学到的第一课：那时的产品远没有今天这么 Agent 化，他们把它做得在一些事上很好，但它对自己的边界没有完整认知。用户问“你能做这件事吗”，功能明明在、也做得到，产品却说“不行”，她只能说“可是你能啊”。swyx 接了一句“相信你自己”。她的结论是：作为产品开发者，它既要能做这件事，也要完全知道自己能做；这两件事不一定一致，也不一定都写在提示里。她观察到，用户往往会觉得一个自我认知更强、更会调整自己去适应系统的产品“更聪明”。

swyx 说没想到一场 Cursor 访谈会聊得这么抽象，Sam 说他们平时就一直聊这些，这能让 Agent 整体变好。swyx 收尾说 Cursor 是他心目中 Agent 实验室成功的头号例子，大家都想知道他们怎么运作。
