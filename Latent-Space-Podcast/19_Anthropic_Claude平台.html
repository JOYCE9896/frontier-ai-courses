01. swyx 读 S-1：人均收入、算力效率和两个循环

节目位置 0:00:00–0:04:04 · Anthropic’s S-1 and this interview / Revenue per employee and efficiency / The improvement and investment loops

为什么加这段开场

swyx 说这是新尝试：Anthropic 当天提交了 S-1，Latent Space 会在上市前发一组相关节目。他说上市预计在两周后，估值两万亿美元。按报道，Anthropic 累计融资超过一千亿美元，累计烧掉的现金不到一百亿美元。他提到自己以前做过金融分析师，所以从 S-1 里摘了几句话。他说观众可能想看主持人直接对镜头说话，过去四年他们一直只和嘉宾对谈。

几组数字

  • 过去 12 个月的人均收入是 660 万美元，一年前是 140 万美元，接近五倍。他说任何老板和工程师都想提高人均收入，这既关系利润，也关系能给员工开多少钱。
  • 每一美元算力带来的收入大幅上升。2025 年第二季度，Anthropic 每一美元收入大约亏五毛钱；现在每一美元成本能带来两美元收入。
  • Anthropic 刚报告了第一个盈利的季度。swyx 特意强调这是按 GAAP（美国通用会计准则）算的利润，不是剔除各种成本后的调整后利润，利润率 19%。一年前是亏损收入的 129%。

两个循环

他说 Claude、Boris（Claude Code 负责人 Boris Cherny）和 Dario 都喜欢讲循环，S-1 里也有两个。第一个是改进循环：Claude 帮忙做出更好的模型，更好的模型带来更多用例，更多用例带来更多反馈，反馈又让 Claude 更好。第二个是投资循环：采用面扩大带来收入增长，增长带来更多投资，投资带来更强的能力，又回到更好的 Claude。他说按 S-1 的说法，这两个循环一起转，推动效率一直提高。

02. Claude Platform 在 S-1 里的位置

节目位置 0:04:04–0:07:30 · Why Claude Platform matters / Training incidents and production safeguards

swyx 说这期主要聊 Claude Platform。S-1 把它列为“Claude 扩散”的三条路径之一，称它是“我们全面的 agentic 开发环境”，给客户提供构建、部署和扩展自己应用的基础组件（primitives）。他提到节目里反复出现的一个概念：Anthropic 自己的很多产品就是用对外开放的同一套平台做的，内部叫 ant fooding（Anthropic 版的 dogfooding，自己先用自己的产品）。Claude Code 和 Cowork 用的都是 Claude Platform 暴露出来的同一批组件。

S-1 披露的另一组数字：过去 12 个月给 Anthropic 贡献 10 万美元以上收入的客户里，超过一半在用 Claude Platform。swyx 的解读是，Anthropic 正从一家模型实验室变成一个云平台，名字里的 Claude Platform 和 cloud platform 读音相近，现在这件事从设想变成了现实。

他还说 S-1 把公司的方向写成“从聊天机器人到副驾驶（copilot）再到虚拟协作者（virtual collaborators）”。Anthropic 用“虚拟协作者”这个词代替 agent，内容差不多：长时间自主工作、判断、自我纠错、迭代、调用工具，围绕一个目标和人一起工作，不局限在某个应用里。

他的个人判断是：在他们接触的高品味测试者里，大多数人认为 Opus 5.5 是目前最好的模型；Anthropic 手里还有 Fable 5.5，他猜两周内可能发布，因为对上市有利，但他说自己没有内部消息。

03. Opus 5.5 的发布、降价和防蒸馏

节目位置 0:07:30–0:14:35 · Opus 5.5 launch and pricing / Distillation and preserved thinking

这次发布最在意什么

主持人问发布后的个人体会。嘉宾说团队听到了很多反馈，说 Opus 5 写东西绕，这次专门做了清理，内部试用的感受也一样。关于降价，她说越来越多的人在看“每一美元能买到多少智能”，把“每一美元”这部分做对很重要。

博客里没写的部分：让 API 更难被蒸馏

蒸馏（distillation）是用一个强模型的输出去训练另一个模型，让后者学到前者的能力。嘉宾说这次在 API 上做了不少防蒸馏的改动，涉及“前缀锁定的思考”（prefix lock thinking）和思考 token 能不能跨模型重放这类问题。难点在于区分正当用途和恶意用途：开发者在做上下文压缩（compaction，把过长的对话历史压缩后继续用）时也会合理地处理这些思考内容。

swyx 提到一篇论文 Stealing Reasoning Traces from Proprietary LLMs（从闭源大模型窃取推理轨迹），作者向 Anthropic 做了负责任披露，漏洞已经修了。他问这篇论文在公司里有没有引起恐慌。嘉宾说要分开两件事：一件是中国模型的蒸馏，一件是这篇公开且受关注的具体技术。她说他们早就知道思维链提取是蒸馏模型最有效的方法之一，也早就在研究怎样让思考块（thinking blocks）在多轮对话里必须原样保留。

为什么要防蒸馏

嘉宾的解释是：Anthropic 在模型输出的 token 上跑了很多安全分类器（safeguards classifiers）。如果有人蒸馏了模型，再在没有这些分类器的情况下运行，就可能造成不好的后果。所以他们要在两边取舍：不想让正常用户更难拿到模型的能力，又必须做一些改动挡住蒸馏。

她把对用户体验的影响分成两层：第一层是你得改集成代码，麻烦，但原来能做的事还能做；第二层是原来能做的事做不了了，这是他们最想避免的。最近几个模型的做法是一系列渐进改动：强制要求跨轮次保留思考块，现在开始管跨多个账号这类情况，并上线了几个配套功能。

他们主动联系了开源 harness（围绕模型搭的运行框架，负责调用模型、执行工具、管理上下文）的维护者，告诉对方需要升级，也和在 API 上自己做 harness 的大客户沟通。有些客户的压缩策略会因为必须保留思考块而失效，所以他们在 API 里上线了一个新的压缩功能，替代客户原来手写的做法，并且兼容保留思考。她说他们没有直接宣布“从今天起必须这样保留”，那样会让很多人的系统坏掉。

效果和动机

主持人问效果。嘉宾说从他们能测量的范围看，蒸馏变得明显更难了，负面影响减少了。她再次感谢研究者的负责任披露，并说那篇论文在 Twitter 上传得很广，很多人都可能用到。

Angela 补充：网上很多人把这当成商业问题，觉得偷了模型就能便宜地跑。她说这是真的，但公司不太在乎这一点，更在乎安全。她的原话意思是：现实中你要蒸馏，就得先付钱调用 API，所以商业上 Anthropic 是赚到钱的。他们担心的是从 Claude 派生出来的模型被用在坏的方向。

04. 产品和工程怎样分工

节目位置 0:14:35–0:18:05 · Product and engineering at Anthropic

swyx 问两人的分工，以模型发布为例。Angela（产品）说她这边更多是在做取舍：模型要达到合适的智能水平，也要考虑成本。最近调整的缓存价格，是在鼓励开发者做对大家都有利的集成改动，再把省下来的钱让给用户。她还负责平衡安全措施和“让模型好用”之间的关系。集成体验更多由工程团队直接负责。她说团队里很多工程师很懂产品，很多产品经理也很懂技术，她希望是这种跨学科的组合。她自己更偏商业影响，工程师更在乎集成体验，相当于从 API 和开发者工具的角度做用户体验。

Katelyn 说她同意，她自己对产品有很多意见，“经常烦产品团队”，产品团队也能深入讨论为扩容做的技术决策。Angela 说两人在 Stripe 共事过很久，之后在不同的实验室工作过（文字稿提到 OpenAI，没说清各自经历），后来她也来了 Anthropic。她说 Katelyn 经常被误认为产品经理，她自己经常被误认为工程师，这种搭配让两边的决策更一致。

swyx 问：软件工程被“解决”以后，这两个角色会不会合并？既然你们还分开，说明还没到那一步，那剩下的是什么？Katelyn 说她不会用“软件工程被解决”这么强的说法，她的看法是人的目标会不断抬高。她举例说，团队现在一半的时间花在安全地发布模型上，这是最重要的工作，包括 agent 安全、离线和在线安全措施；另一半时间在扩容。

05. 平台扩张，以及每次发模型都要做的安全决策

节目位置 0:18:05–0:26:25 · Scaling the Claude Platform / Model access and safety decisions

一年前和现在

Katelyn 说她一年多前加入 Anthropic 时，Messages API 是一个 Python 单体应用，跑在一个 GCP 区域里，一切正常，她的亲友也都不知道 Claude 是什么。现在的情况完全不同，API 要支撑的流量很夸张，CPU 很紧张。扩容需要大量分布式系统经验，以及模型已经具备的语言和框架知识，但要运营和演进这样规模的系统，还远没到可以对 Claude 说“祝你好运，自己去改系统、安全上线、负责运维”的程度，人还有很多工作要做，她预计这会持续一段时间。

发前沿模型现在要做什么

主持人提到 Fable 首次推出时有 Glasswing 项目，前沿模型的发布方式变了，有了安全测试和延迟；新的 Sonnet 和 Haiku 应该会照常发布，但 Opus 5.5 或新的 Fable 现在是什么流程？

Katelyn 说一切从安全策略决策开始，分离线安全和在线安全两类。她举了数据保留（data retention）的例子：有些情况是一个大网络里很多人开很多账号，用各种方式调用模型，在 token 实时流过系统的时候不可能发现背后有恶意行为或蒸馏。所以他们开始实行数据保留政策，以便做自动审查和人工审查。每发一个模型都要决定这个模型用什么政策：昨天发布的 Opus 5.5 没有 Fable 那样的数据保留要求；如果某个模型有这类政策，就得把执行机制做出来。

另一类是访问计划：他们有网络安全验证计划，最近又加了生命科学验证计划，通过验证的用户在在线安全措施上有不同的待遇。确保这些计划在发布时到位也是工作的一部分。她说这些事以前发模型时都不用想，现在占了大部分工作量：防蒸馏、在线和离线安全措施、各种政策。

她举了一个系统设计的例子：他们做了一个授权系统，保证“允许使用某个模型”或“允许参加某个放宽安全措施的计划”这类授权能可靠地贯穿整个系统。她说不能是“你拿到了 Mythos 的访问权限，我们给你一个 API key、翻一个功能开关就完事”，要确保只有你、按规定的方式在用这个模型。

Angela 补充说，这些工作随能力增长而加码。模型在某些领域能力突然变强时，要额外关注，评估这些能力偏向进攻还是偏向防守，再决定策略。编程能力比较简单，就是让用户做出更好的产品；生物和网络安全是两用的（dual use），可能有负面影响，但用户也可能是正当的安全研究员或生物研究者。这些访问计划就是为两用能力提供通道，用户要说明用途。

“一键撤回”按钮

swyx 说人们容易忘记 Fable 曾经被撤回过，也有蒸馏攻击，有人抱怨 Fable 不支持零数据保留，但多想一些是对的。他说平台工程里常见的情况是出一次事故就过度准备，然后那种事故再也不发生，“现在你有了那个按钮”。

Katelyn 说确实如此，他们的工作清单里有一项是“做一个能一键为所有人撤回模型的系统”，团队还讨论过这项工作值不值得做，因为他们希望那种事永远不再发生。最后的理由是：管理验证计划和 Mythos 这类模型访问需要的基础组件本来就要做，把同一套东西放到所有人的模型访问下面，万一需要时控制手段就在。

产品路线图变成概率问题

Angela 说这类决策改变了他们做路线图的方式。传统产品管理里，你假设一组会发生的事，按顺序下注，赌注比较具体。她说没人能预料到 Fable 会以那种方式被政府要求撤下（文字稿用的词是 de-deployment），但显然概率不是零。所以产品管理变成了概率思维：这件事再发生的可能性有多大，要不要优先做？如果设想各种极端情况，他们对未来的走向其实没有多少把握，所以要对冲，建立一组赌注的组合。他们经常优先做这类对冲，结果发现大多数时候“这个东西我们真的用上了”。

06. 可信访问计划和 trust grant

节目位置 0:26:25–0:30:25 · Trust grants and product roadmaps

访问计划怎么运作

主持人要一个具体例子。Angela 用网络安全访问计划说明：比如你是做防守的安全研究者，想在 Opus 上用高级网络安全能力，可以带着用途申请；通过后，他们会降低你这个版本模型上的安全措施，让你能做这类工作。这需要逐个理解用途，范围限定到具体用户，一般不会对所有人开放。

她说设计时纠结过要做得多通用：是专门做一个验证门户加特定能力授权，还是做得更通用。他们选了通用，因为不知道以后会不会用到别处。结果这套东西后来被大量复用：整体的模型访问控制、所有可信访问计划的管理、模型撤下。她说按正常的产品思路，她会觉得“这不太合理，应该聚焦在明确的用例上”，但在这里，越选通用方案，越经常用到它。主持人说这是本来就需要、只是被事件逼着提前做的东西。

trust grant 是什么

swyx 说自己来自 AWS，熟悉 IAM 和授权（AuthZ），有人会聊 Zanzibar（Google 的授权系统）之类的架构，但没听过 trust grant。Katelyn 说说到底就是一种授权，Angela 说“就是 Anthropic 的 IAM”。Katelyn 解释：普通授权是你请求一个 API、底层要访问数据时，检查这是不是你的数据；trust grant 是他们建的一个干净的数据模型，表示“你被授予了某个特定模型或某个特定计划的访问权”，有很多种组合，团队几乎随时都在用。

她举例：Fable 5.1 首次推出保留思考的要求时，他们给一部分现有客户一个宽限期，让他们有时间改集成。为此要记录哪些客户需要额外时间，于是用 trust grant 实现，在请求的热路径（hot path，每个请求都会经过的处理链路）上跑一个服务，检查你有没有做这件事的授权。她说这和普通授权没什么区别，只是要做一个适合他们系统、能在需要的位置插入检查的服务。

07. 一个模型是怎么发布出去的

节目位置 0:30:25–0:35:55 · How Anthropic launches models

流程

主持人请她们讲一次发布要做什么（安全部分除外）。嘉宾说现在已经像一台机器：做出模型，做大量安全测试，评估它是否达到预期，做必要的取舍，然后切出多个版本做评测。内部大量 ant fooding，能很早发现问题，也帮助判断哪个候选版本更好。等对一组候选版本有信心了，再切一个版本给客户，有时先走自家产品（Claude Code、Cowork），有时走 API 客户的早期访问计划。客户要改自己的 harness，她提到 Cognition 等公司，他们有一套流程收集反馈：在你的评测上表现怎样，喜欢什么，不喜欢什么。有些反馈是感觉层面的，他们也想听；有些就是评测分数。综合起来大家都满意了才发布。

反馈还是很随意

主持人说模型反馈现在还很不结构化，基本是两家公司之间的一个 Slack 频道，“这个看起来怪怪的”，对方说“给我个 ID 我修一下”。嘉宾说这是非确定性产品的特点。她补充，能进早期访问计划的客户基本都有扎实的评测，因为团队在赛跑，想尽量缩短“切出测试版本”到“所有人可用”之间的窗口，所以选那些能马上跑完整套评测、迅速给出可操作反馈的客户，同时也听感觉层面的反馈。她说很多人会惊讶，世界上有那么多 agentic 产品没有好的评测。

swyx 提到两年前 Boris 上节目时说 Claude Code 没有评测，现在已经变了。他的看法是，很多团队的评测就是用户，没时间或没经验去形式化，这没关系，认真起来以后会有评测的。

什么反馈最有用

嘉宾说 API 客户的反馈特别有价值，因为他们把 Claude 放进不同的 harness，而 Anthropic 希望 Claude 足够通用，能在别人的 harness 里工作好，这类反馈是内部 ant fooding 得不到的。正面反馈让人安心，但通常不意外；她说最有用的是负面反馈，“它这里做得不好、那里做得不好”，然后他们去想怎么修。

另一位嘉宾说难的是，不是所有人都希望 Claude 在每个维度上停在同一个位置。比如“偷懒”和“主动”：有人抱怨“别偷懒，把任务做完”，有人抱怨“我们只是在规划，你怎么就去写了一堆代码、做了一堆我没准备好的操作”。完全做对不可能，因为每个人要的东西不一样。她说确实有过切出早期版本后发现太懒，于是“放回烤箱”再训练一段时间把它训掉。如果只靠内部产品测试，这类问题可能发现不了。

08. benchmark、默认行为和个性化

节目位置 0:35:55–0:42:10 · Benchmarks and model personalization

swyx 的问题

swyx 说他觉得给模型做产品经理最难的一点是对齐和个性化之间的取舍：有一个面向所有人的默认性格和默认行为，又要能快速响应某个人在 Claude.md 里写的“请比默认更主动一点”。他参与的 Frontier Code benchmark 在 Fable 发布时打出了名气，Opus 5.5 现在又回到了榜单上。这个 benchmark 的设计会惩罚改动过多的文件和过多的操作，所以模型曲线看起来有点怪。可他自己在 Claude.md 里写一句“别那样做”，模型就不会那样做。那他的 benchmark 没有个性化这一项，是不是在不公平地惩罚 Opus 5.5？每个人都有自己的 Claude.md，这怎么评测？

她们的回答：做得不好

嘉宾直接说“我们做得不好”，这很难，不同偏好互相冲突。主持人提到 Claude 的宪法（Constitution），嘉宾说宪法有帮助，但对于怎样根据差异很大的指令和偏好做个性化，很难做到。她们现在的办法是提供更多参数，让自家产品能按客户群体调整；对 API 客户则给出建议，由客户自己调。这些参数比如努力程度（effort，让模型投入多少推理）、选用多大的模型。她说这还达不到真正需要的个性化程度。

除了参数，她们现在会在大量反馈里比较互相冲突的偏好，然后做判断。她说随着客户和用户增多，这不是可扩展的办法，以后需要让 Claude 自己吸收你的个性化，比如通过某种信号或可以调的东西。

默认 effort 改成 medium

主持人提到默认推理 effort 改成了 medium，这会影响不碰这个开关的普通用户。嘉宾说这是 Claude Code 的设置，也是用参数做“轻度定制”的例子：默认值会按免费用户、专业版用户、Claude Code、Cowork、企业版、API 等不同群体调整，用户随时能改。她说他们不想让用户觉得自己控制不了 Claude，尤其是想用最高档能力的人，或者想用低档换速度的人。所以她们倾向于温和的默认值加可调选项，她说这“目前还算凑合”。

API 参数越来越乱

Katelyn 说她们对这一块都不满意。每次发布时，Claude 学会了一样新本事，有时就该在 API 上暴露成一个参数，结果现在有 effort、有 budgets，还有一堆别的参数，没人能搞清楚某个任务该怎么组合。她们正和客户一起摸索：哪些参数该废弃，哪些该把默认值设得更好，哪些该是 1 到 100 的刻度，哪些该是低中高三档。她说 Claude 被训练得能理解一整段连续的选项，但不可能把所有组合都暴露出来。

她说这也是 Claude Managed Agents 的卖点之一：它仍然是通过 API 以编程方式使用 Claude，但自带 harness；每次发新模型，她们会做大量工作，搞清楚新参数和不兼容的改动，在这个 harness 里把 Claude 调到最好，用户直接拿到结果，不用自己操心。主持人问 CMA 的更新在哪里发布，Katelyn 说在 Claude Dev 账号上。

09. Claude Managed Agents、记忆和 dreaming

节目位置 0:42:10–0:48:25 · Claude Managed Agents / Memory, dreaming, and agent harnesses

CMA 是什么

另一位主持人说很多人在 CMA 刚推出时没注意到，那时大家都在做 harness engineering，想自己掌控一切，现在的问题是还有没有必要自己做。Katelyn 介绍：Messages API 就是原始的 token 访问；Claude Managed Agents 是一组 API，你可以定义一个 agent，和它开一个会话（session），它是更高一层的抽象，让你跳过搭基础设施、搭 harness 这些工作，适合想用程序运行 agent 的人。

swyx 问 CMA 和 Claude Tag 是否共用基础设施，因为两者推出的先后顺序很像。Katelyn 说共用很多：平台团队既运营 API，也运营所有基础产品设施和产品服务，比如支撑 CMA 和 Claude Tag 等产品的沙箱集群就由她的团队管。但在 harness 这一层，两个产品要做的事不同，所以不共用 harness。swyx 说 CMA 推出后基本每家都做了仿品。

记忆和 dreaming 慢下来了吗

swyx 说上半年 Anthropic 在记忆方面做了很多，问现在是不是停了。Katelyn 说记忆和 dreaming 的目标是让 agent 随时间持续改进，这仍然是团队的重点。但发布模型在安全上越来越难，团队大部分精力从“做个好玩的功能让 agent 分数往上爬”转到了“怎样把安全带进所有这些东西”。和年初相比，技能（skills）、dreaming、记忆这类做法的推进确实慢了一些。swyx 问是不是放弃了 skills，两人都说“我们很喜欢 skills”，还在更新。

dreaming 是 CMA 套 CMA

另一位嘉宾（从语气看是 Angela）说她们看好开发者在 harness 层做 hill climbing（针对某个指标反复迭代、逐步提高分数）。她们提供的 harness 有意做得简单，不想太有主见，只想把最佳实践合进去，处理 agent 循环里那些难串起来又没什么差异的部分。在这层之上可以构造各种 hill climbing 策略，dreaming 就是其中之一：它在底层是一个基于 CMA 搭的多 agent 系统，会再启动一个 managed agent 去检查前一个 managed agent 的情况，然后给它写入记忆，“一路都是 managed agents”。

她说这是有意设计的，她们设想这些模块可以拼出很多东西：best-of-N（同一任务跑 N 次选最好的）这类多 agent 策略、验证者 agent，以及目标或结果导向的做法。她们看到有人做了很“野”的 harness，所有 agent 共享一套庞大的记忆，并行开大量 agent。她们很快会更新底层组件，把它开放出来，让用户自己构造多 agent 策略，并提供模板，比如“我们做 dreaming 是从这里开始的”，开发者可以在上面改。

Katelyn 说这个说法更准确：基础组件已经到位，可以让社区拿去用，同时提供工具让 Claude 帮开发者利用这些组件做出新的多 agent 策略，而团队的注意力转向确保大家能在这个系统里安全地用上模型。

10. 怎样评测 Agent

节目位置 0:48:25–0:53:25 · Evaluating agents

主持人请她们给 harness 和 agent 的评测提建议。一位嘉宾说评测有很多种：静态的确定性检查，LLM-as-a-judge（让一个模型按标准给另一个模型的输出打分），等等。她们看到的普遍情况是，你需要的评测比你以为的多，不存在一两套完美的评测就能告诉你怎么改进系统，大多数人最后需要一套规模不小的评测，而且可以让 agent 和你一起不断演进这套评测。她说投入不足是她们见到的最大错误。

另一位嘉宾补充：从简单的开始。有人看到一长串方法，忙着比较哪个最好，结果手上的评测数量是零，不如先做个简单的。

另一位主持人说很多人缺乏经验，不知道好的评测长什么样，所以 Anthropic 多发例子会有帮助。swyx 说他现在用 Fable 这类模型时，会把工程当研究来做：事先定义目标，尽量把它形式化成评测，然后找失败原因。他说有时是评测错了，嘉宾马上说“其实很多时候是评测错了”；有时是环境错了，有时是模型错了。他认为这就是 AI 工程正在变成的样子。

Katelyn 说 CMA 里会继续加功能，比如一个帮你给 managed agent 做评测的产品，用起来会像和 Claude 合作，因为 Claude 很擅长给 agent 写评测。swyx 说人看 JSONL 文件会走神，做一个好看的评测界面，左右对比着看，就是人类评分员和标注员本来会做的事，可以直接让 Fable 去做，它会输出评分、Elo（一种成对比较后算出的排名分数），也会写评语，Claude 又可以读这些再改进自己，但很多人不知道可以直接让模型写评测。嘉宾说这种做法也让系统可以被系统地更新：新模型出来时能看清系统处在哪个状态，替换任何一部分。

swyx 认为产品和工程在合流，应用层工程和模型研究也在合流：模型研究的人很习惯做评测，应用层的人以前只关心“符不符合需求文档”。主持人还提到 Anthropic 当天的一篇博客，讲怎样让 Claude 的界面加载更快，里面分享了工程师给 Claude 的原始提示词。主持人说团队给了 12 个目标和两周时间，Claude 大概三天完成了 9 个（后面另一位主持人引用同一篇博客时说的是 13 个目标、三天完成 12 个，两处说法不一致）。Katelyn 说她喜欢公开真实的提示词，很多人以为 Anthropic 有什么独门提示法，其实就是“再努力一点，Claude”。swyx 的意见是博客应该链接到 Workbench（Anthropic 以前的提示词调试工具），让一切可以重放，嘉宾说“收到”。

11. CPU 不够用，以及把 Messages API 移植到 Rust

节目位置 0:53:25–1:03:25 · CPU constraints and scaling / Rebuilding the Messages API in Rust

CPU 和 GPU 一样紧

Katelyn 说规模和安全是团队花时间最多的两件事。大家谈算力一般说的是 GPU 这类加速器，很少谈传统的 CPU，但现在 CPU 和加速器一样是问题。swyx 说虚拟机和沙箱怎么都不够。Katelyn 列了 CPU 的用处：运行产品服务、API 和所有应用；所有沙箱；还有 CI（持续集成，代码提交后自动跑构建和测试），因为代码写得多了，CI 运行次数大增，需要更多 CPU。她说不只 Anthropic，她接触的所有人都这样。

swyx 补充训练也用大量沙箱。Katelyn 说研究沙箱和产品沙箱不混用，但对 Anthropic 整体来说 CPU 是零和的：他们和云服务商谈下 CPU 额度，再在公司内部分给上面所有用途，包括研究沙箱和产品沙箱。过去只要预算允许，CPU 可以按需扩；现在必须提前做容量规划，她说这对所有人都是新问题。

应对办法有三层：尽量多拿 CPU；在基础设施层更高效地运行沙箱，同时不牺牲租户隔离等安全属性；在应用层让应用和 API 更省 CPU。

移植到 Rust

她说最兴奋的一件事是：上周，用 Rust 写的 Messages API 已经全量上线。今年早些时候他们就预见会撞上 CPU 墙，已经做了多区域部署等工作，但 Python 单体很费 CPU（她的原话是“very CPU inefficient”）。他们选了 Rust。她说这在当时是个疯狂的决定，因为团队里一个 Rust 开发者都没有。代码由 Claude 写，人负责设计系统：说到底这是一个分布式系统架构，Claude 既帮着写代码，也帮工程师讨论方案、学习设计这个系统需要的知识。她说最重要的两件事是做这件事的计划和对结果的验证，实现部分就是 Claude 写代码。

具体做法是用 Rust 完整做了一份整个 API 的分叉版本，然后把影子流量（shadow traffic，复制一份线上真实请求发给新系统，但不把新系统的结果返回给用户）导进去，比较 Python 系统和 Rust 系统的输出是否一致。主持人说“功能开关就是你需要的一切”。swyx 问现在团队里有没有 Rust 的人，Katelyn 说那些工程师现在大概会自称 Rust 开发者了，过程中也招了几个更有 Rust 经验的人做把关。

她说按以往的经验，她从没见过一个团队说“好，我们把整个系统移植过去”，这至少是好几年的工作，正常会把系统切成一块块分别迁移；这次是一次性整体移植，再慢慢开启流量，结果成功了。

效果

swyx 问 CPU 节省的量级。Katelyn 说大概 40% 到 50%；延迟方面，首 token 时间（time to first token，从发请求到收到第一个输出 token 的时间）改善了大约 10% 到 20%，长时间运行的负载改善更多。

忍住不加功能

swyx 说他参与过大型重写，总有人想“反正在重写，顺便加个新东西”，范围就会膨胀。Katelyn 说这次是纯移植，她更愿意叫它 port，团队忍住了。这个小突击队在做移植的同时，团队其他人还在给 API 加新功能；突击队做了静态分析，有人在 Python 那边加了功能却没考虑 Rust，就会被他们拦下。他们自己没有加功能，也没有改变系统行为。

下一步他们会做重新架构，其中一些会面向用户。比如：如果你愿意让他们把对话状态存一段时间，就不用每次请求都来回传完整对话，长对话的延迟和效率都会好很多。swyx 问现在的缓存 API 是否已经这样，Katelyn 说现在有提示词缓存（prompt caching），但仍然要回传整个对话状态。另一位主持人说按用户数这是小众需求，按 token 量看这类负载会是大头，也会让 Anthropic 更像一个云。

swyx 说 Cloudflare 的 Durable Objects（一种带持久状态的边缘计算对象）是需要续接状态的 Messages API 的合适形态，每家云都该做一个，开源替代品是 Rivet。Katelyn 说他们在试各种计算形态，但 Anthropic 跑在三家云上，除了最基础的形态，没法假设某种计算方式在所有地方都可用。

谁能卖 CPU 给你们

swyx 说有 50 个听众会因为他不问这个问题而“杀了他”：手上有 CPU 要卖，该找谁？Katelyn 半开玩笑说发邮件给她，然后说明：有一个负责加速器算力采购的团队，现在花了很多时间和她们一起找 CPU，采购不是她的工作。他们有质量门槛和规模门槛，如果拿不到足够的量，就不会去接入某种机器；这种规模的系统该有的属性，他们都在乎。swyx 列了几条：最低集群规模、SOC 2 认证、企业级、隐私保证。

12. 大脑和手：凭证和沙箱怎么隔开

节目位置 1:03:25–1:08:25 · The brain and the hands / Protecting credentials and sandboxes

架构的起点是延迟和可靠性

swyx 问：大家都难把 agent 关在沙箱里，它们总能逃出去，现在最好的做法是什么？Katelyn 说 CMA 发布时有篇博客讲“大脑和手分开”：harness 跑在一台持久的服务器上（大脑），执行环境是沙箱或容器（手），只在需要执行时才启动。这样做最初是为了延迟和可靠性：第一个请求可以很快返回 token；沙箱挂了，整个 agent 不会跟着挂，因为 harness 在别处持续运行，agent 的状态也单独存储。

她说第一版 agent API 很简单：把 Claude Code 扔进沙箱，上面套一个 API。他们没把它当作可扩展的正式方案推出，因为必须先启动沙箱、再启动 Claude Code，才能拿到第一个 token；沙箱一挂，整个 agent 就没了，可靠性不够。

她说从一开始负责这件事的产品经理就说这个架构最重要的属性是安全，当时大家都说“对对对，但延迟和可靠性更重要”。她昨天还专门向这个人道歉，说她现在逢人就讲对方几个月前说的话。

凭证放在保险库，agent 只看到占位符

agent 要调用 MCP 服务器（MCP 是 Anthropic 提出的模型调用外部工具和数据的协议）、命令行工具或某个 API，都需要认证，凭证得存在某个地方。他们的做法是：凭证放在一个完全独立的保险库（vault）里，agent 决定调用某个服务时只看到一个占位符；流量出站时经过一个代理，代理取出正确的凭证注入请求再放行。agent 和凭证从来不在同一个地方。过去“把 agent 启动在一个盒子里让它跑”的做法，必须把凭证送进盒子，再想办法清洗，防止 agent 拿着凭证做不该做的事。现在是一道基础设施上的墙，agent 根本碰不到凭证。

出站控制

另一点是沙箱的出站控制（egress control）：可以设域名白名单，也可以完全断网。这样 agent 写的不可信代码在沙箱里执行时，只能访问你允许的地方。她说这些属性让系统默认就是安全的。

她说客户常问：听说 agent 逃出沙箱、出了事，我该怎么想？她认为最重要的两点是架构（让 agent 根本不可能做不允许的事）和沙箱的配置，CMA 开箱就有这些，而且随着他们学到更多、改进系统，客户会自动得到更新。她说“大脑和手”“凭证注入”“出站”这些词，九个月前没人在说。

主持人说内部也在把所有东西升级成这种默认安全的模式，并提到之前和 Tariq 的那期节目聊过“云端大脑、本地的手”这种产品形态，嘉宾说大致是这样。

13. 训练中的越狱事件和生产环境的区别，发布节奏

节目位置 1:08:25–1:12:25 · Training incidents versus production / Pacing and launching frontier models

沙箱泄漏是理解问题还是没做好

swyx 说 Claude Code 以前以“危险地跳过权限确认”出名，现在终于走到了一开始就该在的位置。他问这些沙箱泄漏是我们对沙箱或容器技术的理解有根本问题，还是单纯没做好，比如没开白名单？

Katelyn 区分了两种情况。人们听到和读到的很多事故，发生在训练中的模型身上，各家的模型都有：训练时把模型放进一个盒子，说“解决这个不可能完成的任务，我要给你施压，开始”，它只能在环境里做事，于是有动机逃出盒子去解决问题。生产环境不同：线上安全措施在运行（训练时不一定开，因为训练的目的就是训练模型），而且周围有架构和基础设施，harness 在这边，手在那边，agent 不是一个只想逃出盒子的东西，这个问题根本不需要考虑。

第二点是长时间运行的 agent 还是新事物，大家都在边做边补控制措施。她说她不认为大家做得差，这个领域还很新。她解释 Anthropic 说的“为前沿定节奏”（pacing the frontier），具体指的是：内部所有 agent 都在做上面这些工作，并且把这些能力开放给所有客户，让正确的护栏默认就位。

主张节奏，却 11 天后又发新模型

swyx 说主张控制节奏、又在 11 天后发新的前沿模型，表面上矛盾，在他看来只是说明它通过了安全检查。Katelyn 说他们在三个维度上不断加安全属性：架构和基础设施安全；模型工作时运行的在线安全措施；对静态数据做的离线安全分类。Opus 5.5 在这三方面都达到了他们的要求，所以他们放心发布。

她还说，他们尽量给出最好的用户体验，同时继续减少误报（false positive），但分类器误判后降级到另一个模型，用户体验仍然让人沮丧，这需要继续改进。另一位主持人说从安全角度大家能理解，宁可多误报，而且发生过那起事件后他们仍然开放了访问。

14. 安全分类器、降级和模型路由，新的工作负载

节目位置 1:12:25–1:20:55 · Safety classifiers and model routing / Emerging agent workloads

swyx：这和模型路由是同一类问题

swyx 说降级问题是模型路由问题的近亲：要聪明的路由器还是笨的路由器？据他观察，Anthropic 的降级检测是一个单独在线运行的模型，命中分类器后按逻辑降到某个模型，这个分类器不是完整的 Fable，显然没 Fable 聪明，就会产生分类错误，出现不必要的降级。他举例：“我只是在做生物作业，提了一次 bio，就被降级了。”一个笨模型怎么能判断要不要路由到更聪明的模型？那是聪明模型才能解决的问题。他还说，从超级对齐的角度，模型往往能判断一个问题危险，即使它回答不了。

他说自己第一次用 Fable 时，把 Fable 的安全卡（system card）扔给它，让它分析里面有意思的内容，跑了五分钟，讲到网络安全时被切断，退回 Opus。他认为触发降级的是推理和整个上下文链条的组合，他的问题本身没有问题。

Angela：更一致的体验

Angela 说怎样解决这个体验问题可能是另一个问题，也许需要一个新的超强模型来处理。她设想的更合适的体验是和 Claude 的交互更一致：现在是降级之后还可能再降级，对用户来说很绕。她以“好用户”的情况为例：你在做生物作业，或者分析安全卡，完全合理，却被拦下降级。她认为模型或分类器应该聪明到能识别这种情况，把答案写出来，同时去掉那项能力被滥用的部分。

Katelyn 补充 API 上的做法：遇到拦截，你不一定要在降级模型上继续对话，那是他们自家应用的做法；API 里可以在服务端设置“我要自动降级”，SDK 里也有客户端的辅助工具管理降级；你也可以换个方式重新提示，继续用原来的模型。她说还会继续试一些中间方案，在安全的前提下减少对用户的阻碍。

路由为什么难

Angela 同意这和路由器有相同的体验问题。以成本路由为例：按任务复杂度选模型听上去合理，但做起来很难，因为你事先不知道任务的全部信息；就算完全了解每个模型（实际上做不到），你对任务的信息也不完整，所以无论分类器多好，路由逻辑都有误差。如果把这些逻辑都暴露给客户，“你的任务是居中一个 div，给你路由到便宜的；这个是找漏洞，给你路由到贵的”，她认为这也不是好的体验。

她更理想的形态是动态的 effort，或者动态理解任务复杂度，随着对任务了解增多而调整。在多个模型之间来回切会很割裂，更统一的做法可能是同一个模型、很低的 effort，很便宜，但能连续地往上加，人格保持一致。她说这是在 Claude 自家模型家族内部的设想，跨厂商的模型人格不同，会更复杂，她不知道那一层怎么解决。另一位主持人说意图识别本身就难，用户问个简单问题，模型却给出一整个 HTML 落地页。

新出现的工作负载

Angela 说聊了这么多安全和发布，最终是为了支撑用户的工作负载。她观察到：有些工作负载的智能需求越来越饱和，这是新情况；也有一类任务仍远未饱和，她认为比人们想象的多，回报越来越来自超长时间运行的 agentic 任务，过去没法暴力解决，现在有了更多智能也许可以。今天的典型负载有编程、企业流程加速，往往是把一个明确的具体流程自动化，有些领域已经开始奏效，有些还没有。另一类新负载是前面说的生物和网络安全，属于很复杂的硬工程或硬科学问题，这类负载也越来越多。

15. 团队里怎样对付 AI slop

节目位置 1:20:55–1:26:55 · Fighting AI slop

文档：质量由人负责，但别挑刺

swyx 问团队怎样对付 slop（指 AI 批量生成、没人认真把关的低质内容）。Katelyn 说团队内部也在争论，和别人没什么不同。她们的立场是：你要产出给别人看的东西，代码也好，文档也好，当然应该用 Claude 帮忙；但如果完全让 Claude 生成，自己没花时间读、没确认质量，就把额外负担转嫁给了读的人，她说这“完全不公平”。主持人总结为：人仍然对质量负责。

有意思的是另一面：因为有“Claude 腔”，比如文中间出现一个破折号，读者的大脑就会触发“这是 Claude 写的，不是人写的”，然后就不想读了。Katelyn 说读者要的是达到人会坚持的质量标准，未必要求全由人写。于是出现这种情况：作者其实花了很多时间保证质量，只是用 Claude 帮了忙，留下一点 Claude 的痕迹，读者就被劝退了，这也不利于工作。

她们在团队里定的标准是：要用 Claude，不用这么强的 agent 帮你提速很傻，但成品必须达到一定水平；作为读者，如果真的是 slop，就退回去，别浪费时间；但也别对那些小小的 Claude 腔太挑剔。swyx 说你们的 token 是免费的，用得比谁都多。Katelyn 说这和 token 多少关系不大，但确实是个问题，团队里明确不鼓励 slop。

代码：人管设计，Claude 管实现，靠验证兜底

主持人问工程上的 slop。Katelyn 说道理一样。她们现在的状态是：系统设计主要由人把关，实现大多是 Claude；很多代码只需要快速盖个章就能继续，不一定有人逐行审查，因为大家更关心整体计划和设计对不对，再靠大量验证保证上线的东西质量高。所以现在代码质量变成 slop 的讨论少了，一部分因为 Claude 变强了，一部分因为验证到位了。主持人说“相信你的测试”。

产品：别把能力用在多发功能上

另一位主持人问产品层面的 slop，并引用 Tariq 的推文：用好模型能力的方式，是花更多时间理解用户、做实验，别往生产环境多发 10 倍的功能；应该在发出第一条提示词之前多想想。他提到 Tariq 现在又说“不需要 plan mode 了”。Katelyn 说她经常讲：软件和产品怎样规划、怎样发布，有很多基础的东西不会因为 agent 加快了某些环节就改变。现在一些人身上出现一种偷懒，觉得“agent 在做，我就不用想这部分了”，可那些仍然是流程里最基础的部分，应该花时间和精力。

主持人说作为创始人，实验和探索的成本这么低，本能是多做；Tariq 说的是别这样，要服务于一开始就想清楚的目标。他说自己在慢慢接受，但很难，手里有个什么都能做的玩具，就想到处扔。另一位主持人又提到当天那篇提速博客：13 个目标，三天完成了 12 个，本来可以按两周冲刺只做这 13 个，但他们推进了 20 项；他说这不算产品 slop，因为是重构，不是新产品。

16. Angela 的旧推文、一年 200 本书和 Slack

节目位置 1:26:55–1:33:25 · Management, writing, and working styles

推文和读书

swyx 说他经常向人推荐 Angela 以前的推文，有几条“改变了他的 DNA”，他怀疑她删过一些。他问她最常推荐哪条，Angela 说没有最爱，被追问后说大概是“半做一件事，是一种昂贵的不做它的方式”这条，swyx 说和今天的话题很贴。他把她的推文比作 Naval Ravikant 式的格言。

Angela 说那是大约六年前。当时她觉得工作没有智力上的挑战，很无聊，就开始大量阅读，一年读了大约 200 本书。她怀念上学时那种被逼着学新东西、不好受但能拉伸自己的感觉，工作几年后就没了。她通勤很长，坐 Caltrain，正好用来读书。读完后想了很多，开始发推，不是为了涨粉，几乎没有关注者，是在练习用尽量少的字压缩一个想法。后来有人喜欢，她就继续写，再后来工作太忙就停了。

她最推荐的书是 Nassim Taleb 的 The Black Swan（《黑天鹅》），对她来说改变了看世界的方式。swyx 说 Fable 那件事发生时他就想到黑天鹅：一件你不知道会发生的事，发生之后永久改变了你对事情运作方式的理解。Angela 说想法很简单，但 Taleb 讲得很透，而且说明了这是世界上很多事的共同属性。swyx 推荐同作者的 Fooled by Randomness（《随机漫步的傻瓜》），问她喜不喜欢 Antifragile（《反脆弱》），她说没那么喜欢；swyx 说作者越出名越让人受不了。Katelyn 被问有没有常推荐的书，她说要想一想。

Slack 和产出

Katelyn 说 Angela 不发推了，但工作中经常进入“哲学家模式”，Angela 承认会在 Slack 里说这种话，不是有意的。主持人说在 Anthropic 成功的关键是很会用 Slack，Katelyn 说确实如此，那是个很密集的地方。她对邮件和 Slack 都追求清零，会积极整理频道，分清真正关注的和静音放在下面的。她说有些日子取消所有会议、不写文档、不干别的，只在 Slack 上回消息，也像干了一整天活。

Angela 说这就是她难以接受的：回了所有人、推进了一些事，却没有产出自己想做的东西，所以她要专门留时间思考和产出，才觉得自己有生产力。她承认收到过反馈说在 Slack 上不好找，现在常有人找 Katelyn 说“能让 Angela 回一下这个吗”。主持人问是否有个人助理，她们说有一位人类助理，Slack 里也有很多 Claude 帮忙。

Katelyn 说她处理的 Slack 消息大多是团队因为某个难决策卡住了，帮团队解除阻塞、高质量执行本来就是她的工作，只是碰巧发生在 Slack 里，但一天下来确实会觉得“我产出了什么”。swyx 说作为前管理者，你产出的是一个运转正常、没被卡住的团队。

17. Anthropic 的 DevRel 团队

节目位置 1:33:25–1:43:25 · Building Anthropic’s DevRel team / Developer relations and product voices

两个 DevRel 团队

swyx 说 Anthropic 在招 DevRel（开发者关系，负责和开发者社区沟通、写教程、收集反馈），最近招到了 Addy Osmani（文字稿写作 Adi Osmani），还有 Lance。Katelyn 说平台团队整体上很小，却要管平台、API 业务和所有产品基础设施。她加入时 DevRel 职能还很初级，不在产品和工程组织里。后来他们在平台团队和 Claude Code 团队里各建了一个 DevRel 团队，因为 API 业务和 agentic 编程是两个不同的开发者生态，两个团队有虚线汇报关系、经常一起工作。

她说以前在 Stripe 和 DevRel 打过很多交道，但从没负责过，当时完全不知道怎么做。swyx 给她讲了 DevRel 的三根支柱：产品、内容、社区。她现在能脱口而出，别人夸她懂 DevRel，她说是有人教的。swyx 说他那篇文章据说是 Google 新入职 DevRel 的默认读物。平台 DevRel 目前没有经理，她在招；DevRel 的个人贡献者直接向她汇报，一部分因为这是个难题，一部分因为她觉得好玩。

平台需要自己的声音

她说平台的难处在于：平台是一块很大的业务，但在公众叙事里容易被夹在中间，一边是研究、政策这些最前沿的工作，一边是 Claude Code、Cowork 这些应用。人们想到 Anthropic 时，往往想不到它在运营一个很多人在上面构建的大型开发者平台。所以平台 DevRel 的目标除了经典的“了解大家在做什么、把反馈带回产品”，还要找到平台的声音、品牌和叙事，在社区里确立自己是谁。

她说 Lance（swyx 介绍认识的）做 DevRel 的方式偏教学，写记忆、成本管理这类内容，写得很深，自己做评测，技术内容很多。她喜欢让 DevRel 团队成为这个新兴领域的思想引领者。swyx 说还有一种他喜欢的模式叫 master builder，借自乐高：乐高靠大师级拼砌师卖积木，他们拼出东西，你看了就想“我也要这么做”。DevRel 可以用平台做出东西，让人知道“原来 Claude 平台能做这个”。Katelyn 说团队里的 CJ 更多在做这类事，写 cookbook（示例代码集）、发例子、和社区互动。

cookbook 过时了，skill 接替

swyx 说 2023 年 LLM API 刚出来时 cookbook 很重要，现在没那么重要了。Katelyn 说现在人们不再复制粘贴代码，但 cookbook 仍能展示可能性和用例。她提到团队里有位工程师写过 computer use 的 cookbook，很复杂，至今让他耿耿于怀，那个年代你得自己处理截图等所有细节。现在有 Claude API skill，能在 Claude Code 或其他编程 agent 里帮你做高质量的集成，她希望很少有人还去翻那本复杂的 cookbook。Angela 补充，现在很多人直接把参考架构给 Claude，说“我要这样的”，Claude 就能做出来，效果更好。Katelyn 说帮人在 API 上构建的 Claude API skill 归 DevRel 团队所有，是 Lance 做的。swyx 说这是杠杆最高的 DevRel：把最佳实践提炼进 agent 会用的东西里。

swyx：DevRel 拆成前台和后台

swyx 说他被当成 DevRel 权威，但心里有一部分想说你们不需要 DevRel，可以让工程负责人和产品负责人当公众面孔。他举 Boris 的例子：“我是 Claude Code 的作者，这是我们的做法”，有本职工作，同时做了 DevRel 的事。他问为什么不是每个人都这样。Katelyn 说 Cloudflare 团队做得很好，大家不停地输出内容。swyx 说这也是好经理的标志：大家都乐于公开表明身份，没人离职。

Katelyn 说平台团队也想多这样做，问题是时间，以及知道怎样做到高质量。她把 DevRel 团队看作这方面的专家，可以整天做这些，也能帮团队其他人用很少的时间把这件事做好。swyx 把这叫作 DevRel 的拆分：一个前台、一个后台。典型的 DevRel 从头做到尾；也可以建一个后台，让产品和工程负责人站到台前，约定很简单：“你和我坐 30 到 60 分钟把脑子里的东西倒出来，然后回去工作”，后台负责代笔、制作、写作。他说人们其实不太想听 DevRel 说话，想听 Lance，想听产品里的人，不想听拿钱的代言人；但也不能指望工程师都擅长这个，所以要付钱给专业的人。他的类比是：每个人都在招人，但公司有 HR 部门帮你招人。

18. 用 Opus 5.5 可以试什么

节目位置 1:43:25–1:46:40 · What to try with Opus 5.5

主持人问用 Opus 5.5 该试什么。Katelyn 说它成本效率很高，没那么啰嗦，感觉很好。发布那天她收到很多朋友的短信说模型很棒，一位前老板说“Opus 5.5 刚在一次事故里救了我们”，团队的感觉是“我们回来了”。她建议：以前因为成本、token 效率而不敢放手让模型长时间跑的事，现在可以回头再试，能走得更远。

Angela 说可以试多 agent 的设置，会表现很好。swyx 追问更具体的提示，她先说“没有”，然后说想看看大家做出什么。swyx 补充，他觉得新东西是角色不事先定义、由 agent 之间自己分配：以前你可以给 agent 分配角色，现在是它们给自己分配工作。
