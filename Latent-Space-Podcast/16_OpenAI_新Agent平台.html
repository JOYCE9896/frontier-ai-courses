01. DevDay 发了什么，Dots 和它自带的云端电脑

节目位置 0:01:12–0:06:11 · OpenAI DevDay: Dots, GPT-6.1, Agents API, and Decisions API / Dots and Personal Cloud Computers

和电脑操作有关的几项发布

Vibhu 请 Ari 先把当天的发布捋一遍。Ari 说刚从主题演讲出来，和电脑操作相关的有这几样：

  • Dots：新的个人助理产品，带了不少电脑操作功能。
  • GPT-6.1 Sol：新模型。他说它对电脑操作特别合适，因为成本和速度。发布会上给的数字是：成本是 Astra 的五分之一，只看电脑操作任务的话是七分之一。
  • Agents API：现在带了电脑操作，开发者可以用上 Codex 和 ChatGPT 里同一套电脑操作实现。
  • 已有功能的演示：App Shots，可以把你电脑上正在做的事的上下文很快带进 Codex 和 ChatGPT；Mac 上的原生电脑操作，演示里 Roman 让它自动截取他的应用画面，同时他自己在电脑上做别的事。

swyx 补了一句还有 Decisions API，并问：这些是不是同一个模型，或者同一份数据蒸馏到不同的模型上？电脑操作是不是用了 Decisions API？Ari 说两者是分开的。Decisions API 并行做推理，没有推理（reasoning）过程，模型也比电脑操作用的那些小，所以很快；代价是做长周期、复杂的任务没那么好。他说怎样把这两条路合起来，还是一个开放的研究问题。

每个 Dot 都有一台自己的 Linux 电脑

Vibhu 说 Dots 现在挂着个人电脑，看起来更“持久”，他自己主要拿来处理客服问题：哪里出错了、不想登录不想做身份验证，就丢给它去找人解决。他问该怎么把它用到极限。

Ari 说 Dots 的不同之处是每个 Dot 都能用一台云上的 Linux 虚拟机。OpenAI 以前的产品要么是在云上开一个浏览器，要么是用你自己的电脑，现在是一整台云端 Linux 电脑，可以跑完整的桌面应用，也能用浏览器。他认为电脑操作的意义在于世界上所有软件都是为人设计的，agent 能用同样的软件，你在电脑上能做的事都可以交给它。具体什么最有用取决于用户是谁，他的建议是先想想自己花时间在哪些事上，哪些能交出去。

他举了自己的例子：为了吃得健康，他订了一家备餐服务，可以细到“鸡肉要多少克、米饭要多少克”。下一单要花他两个小时。他让电脑操作去做，15 分钟做完，他说相当于快了八倍，用的是 GPT-6.1 Sol。swyx 说他作为创作者，第一个用途是自动化 YouTube 后台：A/B 测试、发社区帖子这些都没有 API，只能放进虚拟机里跑。Ari 说 OpenAI 的开发者体验团队也常拿它操作 YouTube。

02. 电脑操作为什么“变了 180 度”：从 Sky 到会自己调试

节目位置 0:06:11–0:10:36 · Why Computer Use Is “180 Degrees Different” / From Sky to Self-Debugging Computer Use Agents

“两年没进步”这个说法

swyx 说想“辣一点”：一家头部 AI 播客、也是他们的朋友，说过电脑操作两年没有进步。他请 Ari 讲讲到底进展到哪了。Ari 说那句话大概是几个月前说的，他希望对方现在看法变了，因为电脑操作和那时相比“变了 180 度”。swyx 说那位很难被打动，Ari 回答“我们在努力”。

swyx 接着问他的职业主线：Apple 的 Shortcuts、Sky、再到 OpenAI，驱动他的是什么，以前做不到什么。Vibhu 加了一个更具体的问题：从上周的 Codex 电脑操作到今天，主要变化来自模型、Dots 还是 harness（harness 指包在模型外面、负责调用工具、管理上下文、执行动作的那层程序）？

Ari 的回答

主线是他一直喜欢自动化，帮人省下花在“精细操作电脑”上的时间。swyx 插了一句玩笑：像是一直在 Apple 外面“hack”Apple，最后 Apple 说算了你们进来做吧。

他说回看 Sky 那时，他们也在做电脑操作，但模型能力差得多；最近一年模型在这件事上变得极强。他看到的最大差别是：以前模型能稳定地开始一个任务，但一遇到问题就卡住；现在模型很会调试，会重试，会反省什么有效什么无效。此外整个领域的做法也往前走了：

  • 电脑操作现在经常写代码。在 Codex 里手动展开工具调用，可以看到它写一段 JavaScript 让电脑执行，并非一次只做一个动作，有时一次完成很多步，这既提速又多了能力。
  • 用更多的无障碍（accessibility）信息和多模态接口。模型可能用截图，可能用无障碍信息，可能用 Playwright（一个用代码控制浏览器的开源工具），按任务选机制。
  • 模型本身进步很快。

至于今天和上周比，他说他们一直在改进，一天的差别没有过去一两个月的累积那么大，今天值得关注的是 Dots 里的电脑操作和新模型。

怎么衡量进步

Vibhu 提到主题演讲里 Tejal 说电脑操作速度提升了 7 倍，几个基准测试也好了不少，问内部怎么衡量，提升来自 harness、模型还是后训练。Ari 说他们有很多测法，有些是在 harness 的不同组合和配置上测；情况有点复杂，因为线上产品有更多安全检查，而且按任务需要配置不同。但不管怎么测，提升都比较一致，有时来自 harness，有时来自模型。他特别提到，GPT-6.1 在电脑操作上的性价比提升，比它相对 Astra 的基础成本降幅还大。

03. 模型怎样“看”软件：无障碍树、DOM 和 App Shots

节目位置 0:10:36–0:13:21 · How Computer Use Sees and Operates Software

swyx 说直播里他喜欢一张图：模型和 harness 一起把帕累托前沿（Pareto frontier，这里指成本和效果的最优权衡曲线）往外推。他问有没有具体的“顿悟时刻”。

Ari 说还是那一点，加入更多模态最有用。具体例子是滚动：过去很多电脑操作产品花大量时间在滚页面上，截图、尝试、发现要往下翻、再截图、再翻。现在有了无障碍信息和对 DOM（网页的结构化元素树）的直接访问，模型能一次看到整个页面或整个应用，还能写代码一次做多步。这是最大的几次突破；另外还有很多不起眼的小改进，他说很多速度提升来自一个个要逐一排查的小毛病，“很多硬核工程”。

App Shots 是什么

swyx 说很多人没搞懂 App Shots，Codex 里看起来只是一张截图，其实每个按钮都能驱动，每段文字都以一种很省的表示带了进来。Ari 说想看细节的话：在 Codex 里连按两下 Command 键拍一张 App Shot，它会把当前应用的内容拿进对话；点开附件，再点右上角一个小按钮，就能看到原始文本和原始的无障碍表示。他们下了很多功夫，既要全部导出，又要节省 token，“有点像一门手艺”。

他说这套技术原本是为有无障碍需求、用屏幕阅读器的人发明的，结果对大模型用电脑同样有用。Vibhu 也说很多人连这个功能都不知道，它看起来像截图，实际上把元数据、代码都拉了进来。Ari 举例：网页截图不会包含链接指向哪里；日历截图里事件标题会被截断；App Shot 会给模型完整的上下文。swyx 顺带提到他请 Jason Liu 在 AI Engineer 大会上就此做过一场完整的工作坊。

04. 从比普通人快，到比专家快

节目位置 0:13:21–0:17:15 · From Faster Than Humans to Superhuman Computer Use

下一个目标

一位主持人问更远的问题：瓶颈在模型还是 harness，两年后会怎样，会不会一跑就是几小时。Ari 说团队过去几个月做到的事是，电脑操作现在在多数情况下完成任务的速度大概已经比普通人快。下一个前沿是“真正超人”，也就是用软件和他们这些熟练用户一样快甚至更快。他认为那时可以做出更实时的产品，而且用电脑操作的门槛降低后，大家会开始默认把一些习惯手动做的事交给 agent。挡在前面的是很多小毛病和瓶颈，分布在模型、推理、harness 和表示方式上。

等网页加载也成了瓶颈

他说电脑操作越快，就越被“做一个操作本身的速度”卡住。比如在他们的基准任务里自动化 doordash.com，不少时间其实是在等 doordash.com 自己加载。主持人开玩笑说那就写个 wait。Ari 说要尽量缩短“页面终于加载完”到“触发模型做下一步”之间的延迟，这本身是一门统计学问。能用事件驱动就用事件驱动，浏览器有页面加载事件，但有些事没法事件驱动，处理起来很复杂。主持人举的例子是和客服聊天：对方回复可能 30 秒，也可能 3 分钟。

主持人自己怎么用

一位主持人说他用 Codex 处理过大量客服机器人，担心对方看出这边是机器人，因为回复句子完整、大小写正确、编号全对，“显然太好了”。他给它的提示是“别装机器人，当一个很不耐烦的人”，回话要短；等对方回复的时候，用子 agent 去研究更好的办法。Ari 说一半时候对面也是机器人，两边是机器人在对话。

一位主持人说现在的一个里程碑是：三四年前大家还不敢把大模型接到网上和自己的设备上，现在他让它配置 DNS、付账单，“几万美元的东西”直接交给电脑操作去跑。

05. Agents API 里的电脑操作：信任、权限，以及让 agent 自己测软件

节目位置 0:17:15–0:20:26 · Agents API: Trust, Permissions, and Safety / Computer Use for Coding, Testing, and QA

给开发者的建议

主持人问 API 开放后开发者会遇到哪些坑。Ari 说很多开发者要和第三方网站、服务打交道，电脑操作的好处是普适，什么都能接，现在开发者能用和 OpenAI 自己一样的实现。自己写一套电脑操作 harness 可以做，但很难。另外，OpenAI 是在自己的电脑操作 harness 上训练模型的，所以用这套“在模型训练分布内”的 harness，可能在速度、成本和准确率上都有优势。

他说大家还在慢慢习惯和信任这项技术，有些人走得比大多数人靠前，所以开发者有责任一点点建立信任：做得可靠；加合适的安全检查；在做付款这类后果重大的事之前征得用户同意；按应用需要，只让它访问任务真正需要的网站和应用。

让 agent 测自己写的软件

Vibhu 问电脑操作对开发流程有什么影响，比如 Dots 出现在 Slack 里，有人用语音做开发，Roman 演示的“改这个应用、过程中发截图给我”。Ari 说他最喜欢、在实际使用中也最常见的用途，是让 agent 测试它自己写的软件。他说这比听起来重要得多：以前 Codex 帮你写完，你得自己去测，“你成了 agent 的 QA”。有了电脑操作，软件开发的闭环就完整了，agent 写完自己测，到他手里时已经能用。他有时在开发电脑操作本身，于是出现“一个电脑操作 agent 在用他的电脑操作 agent 去用别的东西”。

一位主持人说他自己做了一个“视觉试玩测试”的 skill，能抓出很多光看代码看不出的设计问题；另一个用途是克隆应用，如果某个 SaaS 很烂，就让电脑操作一屏一屏地点、截图、记录，再用 Codex 全部克隆出来。前半段到这里结束。

06. GPT-6 这一代 API：异步工具调用、中途插话、WebSockets 和 UltraFast

节目位置 0:20:26–0:24:33 · GPT-6 APIs, Async Tool Calling, and UltraFast Inference

Nikunj 的工作

Nikunj 自我介绍说他领导 API 团队的产品，来 OpenAI 大约三年，一直在做模型上线：每出一个新模型，就和后训练、研究团队一起搞清楚它新在哪，再把能力放进 API。

GPT-6 带来的新能力

  • 异步函数调用。在 Codex、Dots 这些产品里，工具调用往往很慢，现在不必在工具运行时暂停模型：发出工具调用后模型继续运行、继续推理，过一会儿再回来查看结果。
  • 中途插话（mid-turn steering）。可以在模型推理过程中注入消息，比如工具调用完成时把新指令塞进去。swyx 说这也是模型对齐上的能力，得在训练里教会模型中途改方向。Vibhu 说 App 里以前也能在推理时插话，只是效果一般，现在好多了。Nikunj 说 API 的原则是等这种能力在 harness 里训练得足够好了，才放进 API。
  • WebSockets。这些能力很多靠几个月前上线的 WebSockets 支撑，它在客户端和模型之间开一条双向通道，异步工具调用、异步推理、注入消息都在上面做。他强调这和 GPT Live 不是一回事，说的是 GPT-6。WebSockets 第一次上线是给 GPT-5.3 Codex Spark 用的（他说“不敢相信我们给模型起了这个名字”），因为要大幅降低和工具来回的开销。

swyx 说“这就是为什么我们是工程播客，能聊 WebSockets”。

UltraFast

swyx 说这和 UltraFast 很配，这是第一次在 API 里提供，基本是能拿到前沿智能的理论最快速度。Nikunj 说做这个项目最有意思的是看推理团队在 Astra 上“下厨”：他们一直开着 Codex agent 去榨性能。有几个月重点在效率和降成本，所以 Luna 的价格降了大约 80%，很大程度来自推理团队的改进；之后他们转向让模型跑得尽可能快，于是有了 Astra 上的 UltraFast。

Vibhu 说他的用量面板上一直有一栏 Spark 额度从来没用过，Nikunj 说那个应该已经去掉了。swyx 说 5.3 Spark 当时明确归功于 Cerebras，OpenAI 不确认也不否认 UltraFast 和 Cerebras 有关，但大家确实在猜，而且 OpenAI 也有自己的芯片。Nikunj 没有接这个话题。

07. Decisions API：一周做出来的快速决策接口

节目位置 0:24:33–0:31:36 · The Rapid Story Behind Decisions API / What Decisions API Is and How It Works

起因：Jev

swyx 称这是“房间里的大象”。他说 Latent Space 是第一个和 Jev 创始人 Diogo 做深度访谈的播客，也请他上过 AI Engineer。Jev 是一家做快速决策模型的创业公司。Nikunj 先说要给 Diogo 和 Jev 团队“大大的赞”，他们带起了这一整个细分市场。Jev 出来后大家都很兴奋，用户来找 OpenAI，内部团队也说“我们需要一个快得多的分类系统”。他暗示 Dots 之后会有一些基于 Decisions API 的、反应很快的功能。

主持人说四周前这件事还不在路线图上，Nikunj 说完全不在。swyx 说 OpenAI 算是第一家正式“克隆并采用”这种做法的前沿实验室。Nikunj 说 OpenAI 有很强的黑客文化：基础设施团队的一个人觉得这太棒了，动手做了原型，能用，现在团队在一点点压延迟，目标是几天内上线，达到延迟目标就发。后面他还说这件事大约一周前才开始。

它适合做什么

Vibhu 问大家该怎么看待它。Nikunj 说目前看到的主要用途是很快的分类。电脑操作的演示也很酷，但有局限：让 Astra 写一段 JavaScript 控制电脑，和让 Luna 一次选一个动作，智能水平不一样，不过有些电脑操作任务可能这样就够了。

他看到的另一个内部原型是接 GPT Live。GPT Live 是 OpenAI 双向实时的语音 API，结构是前端模型加后端模型，也就是 Thinker / Talker：GPT Live 是 Talker，很快，擅长转交任务，后面坐着 Astra 这样的模型。以前 GPT Live 里调用工具总觉得很慢，现在有人做了用 GPT Live 控制电脑的工具调用演示，感觉快得多、自然得多。

它和“Luna 加结构化输出”有什么区别

swyx 说过去两周大概出了 100 个 Jev 克隆，克隆 Jev 的 API 很简单，基本就是结构化输出，而结构化输出是 OpenAI 最早做的。他的追问是：决策模型和 Luna 同价，如果我把 Luna 的推理关掉再加结构化输出，是不是就有了一个 Jev？他认为不是，因为还有置信度这一层。

Nikunj 的回答很直接：

  • 没有为此训练新模型，完全建在同一套 Luna 权重上，“这真的就是 Luna”。
  • 在上面做的是约束输出，结构化输出是很大一部分；把推理栈优化到首 token 延迟（TTFT，从请求到返回第一个 token 的时间）很低；一次有多个问题时并行跑，也就是批处理；还有各种推理技巧在尝试。
  • 第一版等于在 Luna 上零样本地做这件事，先放出去看反馈，这是 OpenAI 一贯的迭代部署做法，之后按需要改进模型。

swyx 说至少有个好处：OpenAI 版本自带视觉能力，Jev 没有。Nikunj 说这是从 Luna 免费得来的。swyx 又说，如果权重没变，那置信度和校准（calibration，指模型给出的把握程度和它实际正确率是否一致）这部分的创新应该还没到，因为 RLHF（基于人类反馈的强化学习）会把模型推向“你想听的答案”，而不是真实的把握程度。Nikunj 同意，说这可能就是以后发新模型时要专门往上爬的地方。

架构上的两种猜测

swyx 说 Jev 没公开怎么做的，外界有两种猜测：一是用扩散模型（diffusion，一次并行生成整段输出）而非自回归逐个 token 生成；二是某种机械可解释性（mech interp）的做法，读取中间层的激活直接输出结果。两种都有人做过演示，他提到 Gemini 分享过 Gemini Diffusion。他的看法是 API 谁都能做，难的是速度、准确率和校准这些。Nikunj 说这个方向被带起来了，大家会互相学习，他很期待。

08. 内部已经拿新 API 做了什么

节目位置 0:31:36–0:33:35 · What OpenAI Is Building With the New APIs

主持人问平台团队希望开发者用 Decisions API 和电脑操作 agent 做什么，内部有什么例子。Nikunj 说 Decisions API 的内部用法很明显：用户运营团队马上就要拿它给全部客服工单分类；还有一些很酷的实时演示（字幕不清）；Codex 应用团队可能也会拿去做点东西。他强调整件事一周前才开始，还很早。主持人补充说评测里的“LLM 当裁判”（LLM-as-a-judge，用一个模型给另一个模型的输出打分）也很需要低延迟。

Agents API 这边，他说 OpenAI 有一批第一方产品完全建在它上面：刚发布的 Codex Security；当天上线的一个会议类功能，Sam 演示插件扩展时出现过，在日历里进入会议、会议记录流进你的空间，主持人说像 Granola。主持人说发布会上展示的空间、页面、协作、加入 Dot 等内容信息量很大，Nikunj 说这些都是用 Astra 做的，现在从想法到实现太快了。

09. Responses API 的性能、长时缓存和缓存预热

节目位置 0:33:35–0:36:32 · Prompt Caching, Pre-Warming, and API Performance

主持人问他最想要哪方面的反馈。Nikunj 说 Agents API 和 Decisions API 是最新的产品，什么反馈都要。Responses API 是他们的主力接口，现在的重点是性能，分两块：

  • 延迟：他们在重写整个 Responses API 的服务栈，让首 token 延迟等指标尽可能低。
  • 缓存：提示词缓存（prompt caching）指服务端把已经处理过的前缀存起来，下次相同前缀直接复用，省钱也省时间。个人 agent 这类“一个线程一直往下聊”的场景特别依赖它。现在保证 30 分钟内缓存命中；给某个用户新上了一个长得多的窗口，保证 12 小时缓存命中。这还不是公开 API，处于预览阶段，会尽快开放。做法是缓存写入多付一点钱，换来长时间的缓存读取保证，比如一个线程三四个小时后再回来，仍然能吃到缓存。

主持人提到新模型的缓存读取便宜了 95%，Nikunj 说是，他们在压缓存读取的价格。他建议开发者把应用做成“缓存感知”的，用他们的提示词诊断、缓存诊断工具去看缓存在哪里断掉。

他还介绍了缓存预热（pre-warming），API 里已经有了：如果你知道某个提示词马上要来，可以现在先付缓存写入费，接下来 30 分钟内随时可用。主持人说这样可以从同一个线程分出很多实例，Nikunj 说对，可以一直往下接。他说希望在这些底层性能上多拿反馈，让 Responses API 成为基于大模型开发时最快、最可靠的方式；新产品则是“随便用，然后来抱怨”，主持人说“帮我们定路线图吧”。

10. 上下文压缩、更高层的 API 和“AI 云”

节目位置 0:36:32–0:40:24 · Context Compaction for Long-Running Agents / Memory, Higher-Level APIs, and the AI Cloud

上下文压缩

主持人说缓存很好，但最后还是会撞上 100 万 token 的上下文上限，而且这在可预见的未来不太会变，所以还是需要好的压缩，最佳做法是什么？Nikunj 说 OpenAI 有自己专有的压缩（compaction，把过长的对话历史压缩成更短的摘要或状态，腾出上下文）：

  • 在 Agents API 里，它直接内置在 harness 里。
  • 在 Responses API 里有两种方式。一是服务端压缩：告诉 API 一旦达到某个 token 阈值就自动压缩、减少占用的上下文。二是 /compact：想完全自己控制的话，可以随时调用，用自己的逻辑决定什么时候压。

主持人说他讨厌 /compact，“这不是 AGI”，但承认这是手动挡。Nikunj 说很多大型编程 agent 喜欢手动做，开源的 Codex harness 里就能看到它用 /compact。他们也在做新的压缩技术，有些已经在 Codex harness 里实现，包括一些基于文件的系统，还在实验。

该在 API 里抽象到多高

时间快到了，主持人问平台未来他关心什么。Nikunj 说他之前在 Stripe 工作，Stripe 的很多功夫在于在核心支付原语之上搭更高层的原语和产品。他一直好奇在 AI 里怎么做最好。OpenAI 试过几次：很早以前的 Assistants API“不太对路”；现在的 Agents API 给你 Codex harness，但给多少灵活度是个开放问题。要不要做“记忆库”这类更高层的 API 对象，把存储这些概念再抽象掉一层，是他很想弄清楚的设计空间。他说 AI 里很多事情的做法是：提供一个底层 API 原语，再给一个示例 harness，让你的编程 agent 去照着实现；但多少东西该直接做进 API，是他一直在想的问题，欢迎大家提想法。

swyx 收尾时说他常用的类比是 OpenAI 在做一个“AI 云”，这是 Sam 一年前说过的话：有点像 AWS 当年发明 EC2、S3，只是现在要做的是这些东西的 AI 原生版本，“你们连给已知会来的东西预热缓存都做了”。他说这些都开放给开发者，能打开新的做法。
