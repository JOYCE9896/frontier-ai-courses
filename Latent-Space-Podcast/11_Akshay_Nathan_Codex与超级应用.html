Akshay Nathan：ChatGPT Work 与 OpenAI 的超级应用

OpenAI 负责 ChatGPT Work 的 Akshay Nathan 讲：Codex 为什么先在公司里的非开发者中火起来，ChatGPT Work 和 Codex 怎样共用一个 Agent harness，Sites 怎样替代幻灯片和表格，OpenClaw 带来的启发，子 Agent、记忆和 Chronicle 的设计取舍，以及 AI 时代怎样区分“忙”和“进展”

主持：swyx、Vibhu（本期客座主持）· 嘉宾：Akshay Nathan（OpenAI，节目里介绍为负责 Core Product Engineering，他自己说所在的部门叫 productivity；此前做过消费金融科技、AI 自动化测试创业公司，在 Airtable 做过无代码产品，2023 年加入 OpenAI，做过 ChatGPT Enterprise）· 发布日期：2026 年 7 月 28 日 · 时长：1 小时 10 分 · 整理：Joyce（@JOYCE9896）
资料来源：OpenAI’s Vision for the AI Super App — Akshay Nathan, OpenAI（本文依据 Latent Space 官方播客文字稿、视频章节和节目说明整理，是中文转述，不是逐字翻译；观点属于说话人，内容以发布当天为准）

这一期的内容

Akshay Nathan 的职业线索是“让不写代码的人也能用上代码的能力”：先做消费金融科技，再做一家在多模态大模型出现之前就尝试用 AI 做自动化测试的创业公司，然后在 Airtable 做无代码产品，2023 年加入 OpenAI 时公司大约 500 人。这期录在 ChatGPT Work 发布后不久。节目说明给的背景数字：ChatGPT Work 7 月 9 日上线，不到两周 OpenAI 宣布 ChatGPT Work 和 Codex 合计 1000 万用户；Codex 的月活比 2026 年 1 月涨了 10 倍以上；6 月时知识工作者已占 Codex 用户约 20%，增速是开发者的 3 倍多；上个月的一次重组让 Codex 的两位主要负责人 Greg 和 Tibo 接手了产品和 ChatGPT，节目说明把这称为 3 月就开始讨论的“超级应用”整合的完成。

这期围绕几个问题：Codex 为什么在 OpenAI 内部先被财务、市场这些非开发者用起来；ChatGPT Work 和 Codex 是一套 harness 还是两套，为什么合并又不做成一模一样；默认模型配置和 Ultra、Goal 等高级模式该怎么选；Sites（模型生成的托管网页）为什么在一些团队替代了幻灯片和表格；从开发者到知识工作者再到所有人的推进顺序；还有 OpenClaw 的启发、子 Agent 该给用户看多少、记忆和 Chronicle、团队角色怎样变化、怎样衡量生产力。swyx 追问最多的是绩效评估里用 AI 的分寸、权限问题和数据层够不够；Vibhu 主要分享他怎样用 Goal 和子 Agent，以及想要更多控制。节目没有广告；视频开头约一分半的片头预告（0:00–1:29）在文字稿里没有收录，这里从正式开场记起。

01. 开场：把代码的能力带给所有人

节目位置 0:00:00–0:03:02 · Hook / Introduction and Bringing the Power of Code to Everyone

正式开场在 1:32 前后。swyx 说 Akshay 刚发布了 ChatGPT Work，负责 Core Product Engineering；他觉得有意思的是 Akshay 起点是无代码、低代码，做过 Walrus 和 Airtable，而 ChatGPT Work 某种程度上是“超级应用中的超级应用”，终极的无代码：写一句提示就行。

Akshay 说确实绕了一圈回来。他职业生涯从消费金融科技开始，之后一直有一个假设：工程师用代码能做的事，如果能用更容易上手的方式带给更多人，会很神奇。他们曾做过一家创业公司，在大模型、视觉大模型出现之前，尝试用 AI 做自动化测试，“当时挺糙的”；后来在 Airtable 待了一阵，思路相同：把数据库或数据库背后的基本元素带给普通人。LLM 出现后他意识到，这就是缺的那块技术，可以让所有人用上代码的魔力，又不用懂底下发生了什么。他说这次发布和最近做的很多事，就是这个想法的落地。

02. 加入 OpenAI，企业版学到的事

节目位置 0:03:02–0:06:57 · Joining OpenAI and Preserving a Startup Culture / What OpenAI Learned from Enterprise AI Adoption

2023 年的 500 人和没变的东西

Vibhu 问他 2023 年加入时和现在比有什么变化，现在有 ChatGPT、Codex 应用、ChatGPT Work。Akshay 说更有意思的是没变的东西。他加入时公司大约 500 人，他本来担心不够“创业公司”，结果感觉比想象的还要创业公司，到现在也没变：自下而上的野心很强，任何人有个想法都可以做出来上线。使命上吸引他的是“把前沿智能带给所有人”，造出 AGI 再交到每个人手里。他说当时就承认这条路不会是线性的，会试不同产品，有成有败，但愿景和使命没变，现在开始看到各块拼起来了。

企业里没有一刀切的方案

swyx 问他做 ChatGPT Enterprise 学到了什么。Akshay 说是企业里没有一刀切的方案。ChatGPT 发布大约一年后，企业都很兴奋要引入 AI，纷纷成立预算巨大的“AI 部署团队”。问他们兴奋什么，起初得到的是标准答案：“我们有很多上下文和数据”；再问具体想让 AI 在工作中实现哪个用例，答案就五花八门。他说这类产品给你一个框，你说什么都行，这是魔力所在；反过来也意味着你不知道拿它干什么。在企业里，很大一部分工作是到用户所在的地方，弄清他们要解决什么，再教他们怎样用 AI 在那里获得杠杆。

swyx 问这和 FDE（forward deployed engineering，派工程师驻场帮客户落地）有什么区别。Akshay 说一边是销售落地，一边是产品。不管 FDE 做得多好，最终用户是坐在电脑或手机前的，产品自己要能引导他们、告诉他们往哪走。

下一个市场大 10 倍到 100 倍

Vibhu 问三年来有推理模型这样的台阶式变化，企业“黑箱不知道怎么用”的问题还在吗？Akshay 说现在采用量很大，几亿人在用 ChatGPT，大体知道怎样和 AI 打交道。但每解锁一个新能力，比如现在的 Agent，就有一小批早期用户真正懂：只要上下文对、连上对的工具、自己在旁边监督，什么都能做。后面还有一个大 10 倍或 100 倍的市场还没明白这一点。他说采用量在快速增长，但机会大得多，ChatGPT Work 要做的就是这块。

03. 为什么做 ChatGPT Work

节目位置 0:06:57–0:08:46 · Why OpenAI Built ChatGPT Work

swyx 问 ChatGPT Work 是怎么决定要做的，他提到有一个“超级应用”的整体合并，还停掉了浏览器产品。Akshay 说感觉过了很久，其实只有几个月。最直接的起因是：Codex 在内部上线后，让他们吃惊的是非开发者的采用出现了明显拐点（他说 OpenAI 最近公布过相关数据）。他在产品开发过程中去参加内部的 UXR（用户体验研究）访谈，发现战略财务、市场等部门都在用 Codex 做自己的事。

这本身很酷，但更让他印象深的是大家用 Codex 时的那份骄傲。swyx 插话：像是“我本来不该用这个，但我在用”。Akshay 说就是那种感觉：他们觉得自己走在新东西前面，也觉得自己有了超能力。团队意识到，Codex 和 Agent 的能力可以带给已经熟悉、喜欢 ChatGPT 的庞大用户群，难的是怎么做，这是个棘手的产品问题，有很多种做法。他们管这叫“Merge”和“超级应用”，最后以 ChatGPT Work 发布。起点就是那个认识：这种能力不只属于开发者，而且这一点比他们自己预想的来得早得多。

04. Codex 和 Work：同一个 harness，不同的界面

节目位置 0:08:46–0:13:36 · Codex vs. ChatGPT Work and the Shared Agent Harness

定位：凡是“工作相关”的事

swyx 问怎样区分这几个产品：Codex 从 CLI 到应用，现在 ChatGPT、Codex 和 ChatGPT Work 合在一起，是给普通用户、给企业还是给工作？Akshay 说定位是“做跟工作有关的事”，找不到更好的词。他负责的部门就叫 productivity（生产力），刻意没叫 enterprise 或 work，因为还有个人生产力。他举了内部 Slack 上有人发的例子：有人的快递没收到，快递员发来一张送达照片，他让 ChatGPT Work 找包裹在哪；Agent 很执着，拿着照片去比对附近的房源图片，找到了包裹所在的公寓楼。

关于 Codex，他说 Codex 是一个会长期保留的品牌，但他们有个原则：不让用户困在某个标签页或某种体验里拿不到产品的全部能力。所以桌面端 Codex 部分能做的，ChatGPT Work 都能做，反过来也一样。差别在一些有主见的产品决策上：在 Git 仓库里时，向用户暴露多少 Git 状态；展示 Agent 思考过程时是否以 diff 为主，让你一上来就看到改动；安全上，两种模式的沙箱默认设置怎样定。但他们不希望用户需要自己选在哪种体验里。swyx 说这对 AGI 是个好目标，人们不想选哪个版本的 AGI，只想让它替自己决定。

harness 是共用的

swyx 问得很直接：Codex 的 harness 和 ChatGPT Work 的 harness 是同一个吗？harness 指包在模型外面的那层程序，包括系统提示词、工具、执行循环和沙箱。只是界面不同，还是在提示词层面甚至更深有区别？Akshay 说 harness 是同一个，是共享的。为了让它适合知识工作，他们在两个产品里都改进了 harness，尤其是插件、电脑操作（computer use，模型看屏幕、点鼠标敲键盘）和 artifacts（模型产出的成品文件，比如表格、文档）；不管在哪种体验里都能用上。区别在 UX 上 Codex 模式该怎样表现的主见，以及前面说的沙箱设置，底层 harness 和能力应该一样。

swyx 想看一个两种模式下表现不同的例子。Akshay 建议让两边都做一个退休计算器表格：Codex 模式下（可能要在仓库里）你会看到它创建表格时的 diff 和文件编辑，Work 模式下看不到。他们当场在两边都开跑，放在后台。

OpenAI 的几个大部门

主持人问 productivity 之外还有哪些顶层团队，“生产力不就是一切吗”。Akshay 说有一个团队专注消费者的核心聊天体验，他不认为那全是生产力：人们每天用 ChatGPT 搜索、想怎么给亲人写消息、学新东西、生成图片，几亿用户在用，值得专门投入。另外还有企业、基础设施、API 等团队。

演示里，切到 Codex 版本立刻能看到差别：界面顶部的“灵动岛”默认你在 Git 仓库里。Akshay 提醒，有些差别在思维链里，在怎样展示改动上，直接看可能看不出来。

05. 为什么把 Agent 体验合到一起

节目位置 0:13:36–0:17:53 · Why OpenAI Merged Its Agent Experiences

工作的边界在模糊

swyx 问有没有想上线、收到反馈后又放弃的东西。Akshay 说另一种做法是把体验完全分开，做成不同应用，或者同一个应用里完全不同的体验。为什么要合？Codex 大家明明很喜欢。他的直觉是，每个人的工作都在被 AI 大幅改变，他自己每隔几个月醒来就发现在做和几个月前完全不同的事。

他们的假设是：这项技术在给人杠杆，把工作里琐碎的部分自动化，让你更快分享更多想法。这样一来，只写代码的人、写战略文档的人、办活动的人、做市场的人、做播客的人，界限会越来越模糊，按“你是谁”画硬边界会很难。应该让用户选择，但不该把他们框死。所以很多工作花在保持基本元素统一上，比如插件在这个产品和云端 ChatGPT 之间是统一的。他们可以就“什么时候用哪种体验”给出建议，但不想把任何人框住。

老 ChatGPT harness 和 Codex harness

swyx 想做一段“harness 工程口述史”：从 o1 时代到现在，ChatGPT 的 harness 撑了很久，现在实际上被 Codex harness 取代，两者有重叠，变了什么？Akshay 先纠正：ChatGPT 原来的 harness 还在。新开一个聊天、不进 Work，就是在和 instant 模型对话；如果你在聊天里要做表格，模型会自己判断，推你去 Work 模式。swyx 问这是路由器的决定吗，Akshay 说是模型在做判断，它看出你要做的事在 Work 模式里更合适。

他的看法是这里一直在“分化、收敛、再分化、再收敛”。聊天里搜索、学习这些用例，他们优化的是延迟、个性这些东西，人们喜欢 ChatGPT 就是因为这些优化做了很久。Codex 让他们学到的是：给 Agent 一台电脑这种无限灵活的环境，它能做很强的事。所以给知识工作选形态时，把它放进电脑环境更自然，对不熟悉的用户把电脑的细节抽象掉一些，但能力一样。最终他们希望各个地方都有这种能力，以后会继续让各场景的能力趋于一致，差别只在于产品过去专注什么、现在专注什么。

06. 模型、推理档位和默认配置

节目位置 0:17:53–0:21:55 · Models, Reasoning Levels, and Choosing the Right Default

先用默认值

Vibhu 说除了 harness，还有新发布的模型。大家喜欢精打细算，比如“Terra 只用高推理档”“这里该用 Sol”，swyx 插话“有 32 个选项”。对那些刚开始拿它干活、不清楚这些区别的人，有什么建议？

Akshay 先说，没有这些模型，这一切都不可能。做 Work 的灵感来自 Codex 内部的现象，而那又是因为模型能力大幅提升；现在又是一次台阶式跳跃。至于建议：他们希望默认值就是最好的，对默认值有主见，选了一个他们认为对所有人最好的。重度用户可以在底下调，他承认现在选项可能太多，正在简化。你可以提高推理档位（reasoning level，让模型在回答前花多少计算去“想”），也可以换模型档次，但默认值应该适合大多数用例。他建议大多数人就用默认值，觉得成本效率或智能质量不够时，再改设置看能不能更好。

Goal、Ultra 和多 Agent 适合什么任务

Vibhu 说他最近在用 Sol Lite 加 Goal（一种设定目标、让 Agent 持续执行直到完成的模式），他的理解是 Goal 等于用更多轮次和终止点来补推理力度，这样想对吗？和 Sol Ultra 或 Sol Extra High 比呢？Akshay 说很难讲，这是交互效应，也取决于个人偏好：你希望有多少个“终止点”让你插手、纠偏。他的划分是：

  • Ultra 或多 Agent 设置，适合很复杂、开放式探索的任务，或者很容易并行拆开的任务。
  • Goal 适合你知道能稳定推进、而且进展可以逐步验证的任务。
  • 大多数任务两边都不属于，至少在刚开始时，所以第一步最好用默认配置，再看往哪走。

一条滑杆

一位主持人说他们做的滑杆很减少焦虑，手机上尤其好用。Akshay 说思路是把多个维度投影成一个维度给用户：一头是速度和效率，另一头是质量和周全。主持人起初奇怪滑杆低档怎么用 Sol 那么多，看清后发现低档预设的是 Terra。主持人说更多人应该用 Terra，原因之一是 Sol 老是容量不够，有人笑说“都怪我”。这时 Work 那边的退休计算器做好了，用了大约十分钟（swyx 后面说是八分钟），界面看起来像 Excel；Codex 那边还在跑。

07. Artifacts、Agent 表格，模型和产品一起做

节目位置 0:21:55–0:25:51 · Artifacts, Agentic Spreadsheets, and Model–Product Collaboration

没买 Excel 许可的“Agent Excel”

swyx 说 OpenAI 新加坡团队的 Gabriel Chua 给他看过这个表格界面，他吃惊于它看起来就像 Excel，能编辑 Excel 文件，“你从没付过 Excel 许可费”，而且是 Agent 驱动的。Akshay 说 artifacts 是这次发布的一大重点，模型和产品两边都有。和 5.5、更早的 5.4 比，生成的 artifacts 质量提升很明显；产品侧的 UX 也是，比如托管网站，不用再自己找地方挂网页。

研究团队和产品团队怎样配合

swyx 问：5.6 和 ChatGPT Work 是同一天发布的，模型训练团队和 harness 团队之间有协同训练吗，还是日期刚好撞上？Akshay 说他们和研究团队合作很紧，这是这份工作最好玩的部分之一。以 artifacts 为例，底下有大量工作是确保有合适的基础设施能训练模型在这方面变强，产品侧则要有合适的体验让用户和模型一起改一个 artifact。

他说这个查看器背后的想法不一定是“你不再需要 Excel 许可”，这只是第一阶段。做退休计算器时第一版多半不是你想要的，你要迭代；如果你看到的东西和你同事收到后看到的高度一致，迭代起来就更容易，也更信任产品。

人只是在中间转发：多人协作和权限

Vibhu 问会不会有多人、多团队协作 artifacts，现在已经可以分享了。Akshay 说在积极考虑，不多谈路线图，但内部有个现象：常有人来问他事情，他转问 ChatGPT Work，再把答案转回去，然后他会想自己在这个环节里是不是必要的。也许他重新表述了问题、补了上下文，但他转回去的过程也是有损的，他给的只是自己对结果的理解，rollout（Agent 一次完整执行过程）里有大量上下文对方看不到。swyx 打趣：所以答案是预先回复所有请求？Akshay 说不是，只是描述他有时就这样工作，像一个“AI 到 AI 的消息转发服务”。

swyx 指出这里有一个轻度安全问题：你其实是权限层。他能查你查的东西、拿到自动回复，但也许他不该看到，而他自己不可能知道自己不该知道什么。Akshay 同意，尤其 ChatGPT Work 要你连上插件、读本地文件，Agent 能接触的上下文很私人，这必须守住，会是个挑战。

08. Sites 为什么能替代幻灯片和表格

节目位置 0:25:51–0:31:37 · Why Sites Could Replace Decks and Spreadsheets

原型工具，也是知识工作的成品

swyx 问：有 Excel、PowerPoint、Docs“办公三件套”，还考虑什么格式？Akshay 做过 Airtable，会不会有 OpenAI 版 Airtable？Akshay 说 swyx 漏了 Sites，这是这次发布的核心部分。X 上常讨论的是 Sites 当原型工具，这次发布里也是：前面那个模型滑杆几乎全是在一个 Site 里开发的，设计、工程、产品在 Site 上试交互、找手感。

较少被讨论的一面是 Sites 作为知识工作的成品。他前几天和公司金融团队的人聊，对方说团队每月一起做的报告，以前在幻灯片和表格里，现在都在 Sites 里，Sites 成了团队协作的载体。原因是信息带宽更高：PowerPoint 和 Excel 很灵活，但总会碰到边界，要么人不会用某个功能，要么产品不支持；Site 什么都能做，你要什么就能得到什么。

swyx 的案例：17 亿 token 做出一个桌游

swyx 展示了他的案例，他说这里集齐了所有热门话题：ChatGPT Work、5.6、“token 亿万富翁”和 token maxing、Sites、auto research（让 AI 自动做研究实验）。他喜欢一个叫 Strata 的桌游，要用实体积木玩。一个周末他拍了大约 30 张照片丢进 ChatGPT，17 亿 token 之后，出来一个可玩的网站，带 3D 积木放置。他这么做是因为游戏要实体积木、要朋友陪练，他想让朋友先练好；他还想训练 AI 玩它。

接下来是 AI 对 AI 自我对弈：AI 一开始很差，要定义损失函数让它变强。他当时在 San Mateo 开会，不想盯着，就让它做 auto research、建基准测试，结果参数多到他看不过来，于是让它做一个 Site，它生成了一个实验面板。后来他把这个挪出了 Sites，因为需要的数据库和基础设施超出 Sites 能提供的，现在已经公开发布。他说这是一个研究产出，你可以拿来琢磨训练游戏 AI 时在调哪些超参数，他还在做 scaling law（缩放定律，性能随算力、数据、参数量变化的规律）之类的东西。

他的体会是：他不再读 ChatGPT 的输出，改读 Site 的输出。问题是内容铺得太开，页面很长、数字很多，看着很累，还得自己修剪。另一位主持人说 Markdown 本来就不太适合人读，干脆写成 HTML 网站，可以用 skills 规定你要什么，Site 放在旁边，想要什么不要什么直接迭代。

Akshay 说他们看到各类团队都在这样用：以前标准的成品是一份幻灯片，现在变成一个 Site。因为它就是 HTML，无限灵活，在幻灯片里会被埋掉的东西可以放成主视觉。他承认要让它更容易协作还有很多工作，太长太啰嗦、可以拆开，这些都还要做。

09. 设计一个什么都能做的 Agent，从开发者到所有人

节目位置 0:31:37–0:37:36 · Designing an Agent That Can Build Almost Anything / From Developer Agents to Knowledge Work—and Everyone

简单和能力之间的平衡

主持人说 Akshay 的工作变得很 meta：他设计的是“做产品的产品”。Akshay 说他们一直在想怎样平衡简单和能力。一个能造出各种东西的产品，不能把所有可能都摆在你面前，否则会把人压垮。他们想做到：给用户足够的界面，让他们能表达需求、能核对 Agent 用的工具和来源对不对，然后界面让开；同时搭好系统，用“展示”代替“告诉”，让用户发现下一个用例、再下一个。

Vibhu 的 18 分 53 秒版本

Vibhu 说每个人的做法都不同。他也做了同一个游戏的版本，没拍棋盘、没给规则，丢进 Goal，18 分 53 秒、很多 token 之后，得到一个类似的版本，没有 auto research 那些。他用的是 Codex，不是 Work，头像是 GPT 图像模型生成的，他说很多游戏设计师很喜欢用 GPT 图像做素材。他说更大的意义在于测试工具：这也是对 5.6 的测试，他在 5.5 上做时得把规则喂给它，这个游戏很小众，模型自己找不到玩法；他们一直很想测 5.6 的能力，这些是他们“私下的评测”。

swyx 说这个过程体现了工作和个人生活怎样互相渗透：他为自己做的东西，给同事看了，同事说“GPT 还能这样用？”，他猜这就是增长策略。Akshay 说“用展示代替讲解”是很重要的一块，他们还没完全解决：怎样在合适的时刻向人展示产品能做什么，而不是靠文章或新手引导去教。swyx 开玩笑说这对他是职业风险，他以前做开发者关系，工作就是展示和讲解，产品经理却说产品足够直观就不需要你。Akshay 说这就是模型的魔力：可以按用户关心什么、以前做过什么、处在采用的哪一步，定制讲解和展示。

推进顺序：开发者，知识工作者，所有人

主持人问还有没有别的人群，是 ChatGPT、Codex 和 Work 都没覆盖到的。Akshay 说他把它看成一个顺序，愿景是把有用的 Agent 带给所有人：

  • 先从开发者开始。开发者历来是早期用户，愿意忍受更多摩擦、自己配置，Codex 就是这样起步的。
  • 下一个机会是“通用知识工作”，开发者周边的所有职能。这一步有天然难点：前面说的展示问题，让产品更好懂，以及加入对这群人更重要的能力，比如 artifacts、电脑操作。
  • 再下一步，把知识工作的经验带给所有人，不管他们生活里在做什么。

他说已经能看到一点：swyx 的游戏就在娱乐、个人生活和职业之间。他自己在家全天用 ChatGPT Work 做所有事，前几天用它做了一份饮食计划，存在它的电脑环境里，以后还能回去看。大家还没这么做，可能是因为名字里写着 Work。主持人们开玩笑说那就叫 ChatGPT Life、ChatGPT Cooking。

10. 给重度用户的建议，用 AI 准备绩效评估

节目位置 0:37:36–0:42:10 · Power-User Advice and AI-Assisted Performance Reviews

三个月、六个月前做不到的事，再试一次

主持人问有没有给重度用户的建议，怎样弥合“全天候使用的人”和“偶尔问几句的人”之间的差距。Akshay 的第一条是扩大对可能性的想象，这对他自己也是：技术进步太快，三个月前绝不可能的事，现在模型真能做了。

他的例子是 OpenAI 正在进行的内部绩效评估周期。大家早就说评估是模型擅长的事，也有“没人想写评估，交给 AI 吧”的套话。但他说以前出来的基本是 slop（AI 生成的低质量内容），有点用但不算有效。现在他发现模型做得比他好得多，尤其是在这个环境里收集上下文：大家在做什么、做了哪些有影响的事、他可能没看到的成果。它能接触代码、他们发现的问题、代码审查、Slack 等一切。六个月前上一轮评估时他也试过，完全没用；这次帮了大忙。所以他最大的建议是：持续推开想象的边界，以前试过不行的也再试。

第二条是投入越多越有价值。在这个环境里模型能接触你电脑上或 ChatGPT Work 里的一切，你可以不断创建 artifacts、存进资料库，模型以后都能用。你给它越多关于你所在领域的信息，不管是生活还是工作，它就越有价值，有时价值会出乎意料，比如主动调出你没想到的上下文。前提是它先要能接触到这些工具和上下文。

评估别人时的分寸

swyx 说绩效评估很敏感，他作为管理者，很不愿意把 LLM 生成的东西用在人身上，因为会显得你不在乎。OpenAI 的人大概更能接受被 GPT 评分，但有没有不成文的规矩？Akshay 说规矩是：他绝不会完全靠 AI 写东西再当作评估交给别人。他说的是收集上下文，这是它最有用的地方。swyx 说那就是搜索，Akshay 说是 agentic search（Agent 自己多步检索），而且比以前更能定制和引导。

他说这里有一个飞轮：因为有 Codex 和 ChatGPT，更多人能做多得多的事；做得多，就更容易漏掉东西，所以要用同样的工具跟上大家的影响。swyx 说他公司小，搜索容易，可在 OpenAI 这种 Slack 消息量下会不会漏？Akshay 说大概会，但他自己也会漏，这是相对的，达到人的水平就行。

一位主持人分享了自己的做法：他的 Codex 系统提示词设置成每个项目有单独的 notes.md，Agent 把学到的东西写进去，全局那份可以从所有项目里调。有时它会说“你四个月前做过一个项目，这里有当时的一条笔记”，把他早忘了的东西拉回上下文，他觉得这有点超人，能省下几个小时，或者找到已经做过的东西。他说这个方案一点也不复杂，就是需要时被调出来的 Markdown 文件。

11. 内部 meme 机器人和一千万用户

节目位置 0:42:10–0:46:08 · OpenAI’s Internal AI Memes and the Ten-Million-User Launch

从 Slack 和文档里挑 meme

Akshay 讲了一个相关的趣事。发布前几个月团队一直在赶工，Slack、文档里有大量讨论。一位同事设了一个定时任务，让模型看所有正在发生的事，挑出最好的 meme 发到共享频道。他说有两点有意思：一是模型渐渐真的开始好笑了，一年前完全不是这样；二是它会以意想不到的方式找到东西、建立你没想到的联系，这对做 meme 很有帮助，能让你真正被惊到、觉得好笑。他承认这不是最有生产力的用法，但它展示了一种正在出现的能力：找到你本来不会知道的信息。

一千万用户意味着什么

swyx 说他几乎认定这是很久以来最成功的一次发布，他个人觉得比 5.0 还成功，OpenAI 宣布了 1000 万用户。他问感觉有什么不同。Akshay 说一是感觉像一个阶段的完成：他们在内部看到 Codex 的魔力，很想带给更多人，现在看到它奏效、达到分发目标，很兴奋。另一面是要做的还多得多。ChatGPT 整体有几亿用户，几乎等于大家心里的 AI，“1000 万很酷，但我们要让所有人都用上”。

swyx 一直在跟踪这个数字，注意到它从“Codex 用户”变成了“Codex 加 ChatGPT Work 用户”，因为共用 harness，没法分开算。他问 ChatGPT 大约有十亿用户，为什么不是直接跳到十亿，不是默认开着吗？Akshay 说免费用户不会被默认放进 ChatGPT Work，它目前只对付费用户开放。还有一个教育用户、让他们试用、根据反馈改进的过程，目标是让喜欢 ChatGPT 的人都感受到 ChatGPT Work 的能力，但会是一段旅程。

主持人说 Codex 品牌在可见的将来还会保留。Akshay 说比这更进一步：开发者一直是他们的核心市场，Codex 专门为软件开发还能做很多，他们会继续做，这次合并不会削弱它，反而让 Codex 更有用，因为你可以在写 diff、做 artifact、为你的角色做搜索之间无缝切换。swyx 问普通用户要不要学会说“artifact”这个词。Akshay 说内部叫 artifacts 是团队的叫法，外面没人这么说；人们会按自己习惯描述，比如“ChatGPT Work 很会做幻灯片”，这就是他们想要的。

12. OpenClaw、个人 Agent 和“个人操作系统”

节目位置 0:46:08–0:51:53 · OpenClaw, Personal Agents, and ChatGPT as an Operating System

他自己的 OpenClaw 时刻

swyx 说，现在是 2026 年 7 月，对 OpenAI 来说另一件大事是 OpenClaw（一个开源的个人 Agent 项目），很多人第一次把一个 Agent 用到极致来处理私事，也延伸到了工作。据他了解 OpenClaw 仍是独立的。他问 Akshay 有没有自己的 OpenClaw 时刻，从中学到了什么。

Akshay 说有很多启发。他和妻子装了一个 OpenClaw，想让它管家里的所有事，给了它日历，它开始替他们建日程，挺有用；后来跑它的那台笔记本坏了，才又找机会捡起来。ChatGPT Work 的网页版和手机版有一个持久的电脑环境，可以存文件，文件在不同会话之间保留，就是为了支持这类用例。团队里有个同事把以前用 OpenClaw 做的事完全换到了 ChatGPT Work：健身计划和饮食记录。这不算工作，但属于个人生产力，用的是同样的基本元素：定时任务、在文件系统里存文件、随时间引用它们。

swyx 问 ChatGPT Work 会不会完全取代 OpenClaw。Akshay 说他不负责那边，没法谈 OpenClaw 的路线图，但他认为不会，总会需要那个团队做的这种开源技术。他说听说过、用过 ChatGPT 的人比用过 OpenClaw 的人多得多，如果能把 OpenClaw 的魔力带给他们，就算成功。

一个对话框里做完所有事

他说 ChatGPT Work 的核心体验是：你来到产品里，和 Agent 开一个对话（或者叫会话），在那个时刻什么都能做。他们希望不用点按钮、不用跳到别处，就能在这里拿到你的理财 App 或任何别的产品里的功能。所以要一个可扩展、带插件的系统，连上完成某个任务需要的工具，比如理财任务；做科研的话，也能扩展系统，比如写 LaTeX 并且表现良好。总会有在某件事上做到最好的专门产品，他们也会支持，但希望把尽可能多的魔力放进核心体验。

理财和健康

主持人问 Wealthfront 能做的事 ChatGPT 能不能都做。Akshay 说他试过：ChatGPT 还不能托管他的现金和资产，这部分还不行。但他在那边工作时研究过的退休规划、财务规划、预算这些，现在用理财插件在 ChatGPT 里都能做，至少这部分对他来说已经被替代了。主持人说他还没连，有点怕看到答案，健康数据也是同样原因。

Akshay 说传统 UX 里，想给用户越多能力，就要加越多旋钮和开关，理财和预算 App 总有一堆筛选、搜索栏；现在只要连上对的数据，你想问什么就问什么，直接得到答案。一位主持人说集中在一个地方也很好，他有智能体重秤、手表等各种健康 App，这也是 OpenClaw 的思路，一个个人操作系统，ChatGPT 大概也想变成这样。

即时拉数据够不够

swyx 说他有一点数据工程背景，认为只靠 MCP、CLI、API 即时拉数据还不够，还需要数据仓库、缓存或语义层，问他们有没有。Akshay 说没法谈所有实现细节，但这取决于访问模式：如果要立刻得到答案，从这么多来源拉数据确实很难；但 ChatGPT Work 想支持的很多用例不需要立刻出结果，是交给 Agent 去做、要花一段时间的任务。加上 programmatic tool calling（让模型写代码批量调用工具）和子 Agent，一部分时间可以并行，所以他认为靠 MCP 调用第三方服务能做到的上限已经大幅提高。

13. 子 Agent、Ultra 和用户需要多少控制

节目位置 0:51:53–0:56:08 · Sub-Agents, Ultra Mode, and How Much Control Users Need

展示子 Agent，但别让人淹没在信息里

swyx 追问子 Agent（主 Agent 派出去处理部分工作的小 Agent）：Ultra 是新模式，ChatGPT 里有专门展示子 Agent 的界面，但“除了看着，也做不了什么”。给做子 Agent 产品的人有什么设计经验？Akshay 说这回到前面讲的平衡：既要展示工具的能力，又要有足够抽象不把人压垮。他们想传达的是：一个有很多并行支线、或者复杂到适合子 Agent 处理的任务，这个产品能接，模型会去完成或尝试完成，这就是在产品里展示子 Agent 的目的。另一种做法是让你看到每个子 Agent 在干什么，他认为那最后会信息过载，所以现在的设计是一个刻意的取舍。swyx 说其实已经显示了不少 transcript；Akshay 说默认是折叠的。

Vibhu 想要更多控制

Vibhu 说他是那种把大量事情丢给 Goal、几乎每个 Goal 都要求“尽量用子 Agent”的人，看似多余，但他身边很多朋友也这样；另一些人会指定“这个子任务用子 Agent”，他们大概会想看子 Agent 怎么被用的。他用子 Agent 主要为两件事：一是节省总时间，分摊出去；二是成本，别用大而贵的模型，交给很多更小更便宜的模型。如果是重复做的事，比如每天固定跑的流程，他可能想逐个调子 Agent。他说 Anthropic 在 Claude Code 里提供了这个，可以让 Fable 或 Opus 用 Sonnet 当子 Agent，他认为这里不存在的话也能做出来。有人说那样开关太多，Vibhu 说这不是开关，是在对话里用提示告诉它。他举例：做播客准备时要对嘉宾做很深的调研，他可能想把网页搜索配成更便宜更快的模型。他认为现在默认折叠、可以展开看更多，已经挺好。

Vibhu 还提到 5.6 发布时大家议论的一点：它很爱开子 Agent，开得太多会让 ChatGPT 应用因为太吃处理器而崩溃。有人说自己没遇到过崩溃，主持人笑说“我们都有大笔记本”。Vibhu 说这又是一种“体感评测”，有人觉得 Sol 开的子 Agent 多得离谱，他觉得没问题。

Ultra 改成手动开启

Akshay 说刚上线时他们对 Ultra 是给谁用、什么时候用没那么有主见，之后改了：要在高级设置里手动打开，因为它是给知道会发生什么的重度用户的，根据用例也可能更快用掉你的额度，很多反馈就来自这里。主持人笑说“重置额度就好了”，Akshay 说今天就因为这个在重置。

14. ChatGPT 记忆、个性化和 Chronicle

节目位置 0:56:08–1:01:48 · ChatGPT Memory, Personalization, and Chronicle

Work 继承 ChatGPT 的记忆

主持人换到 harness 的最后一块：记忆。最近很多人评论 ChatGPT 的新记忆系统，有人说以前很差、现在好了，他也提到 Akshay 的同事 Samir 谈过记忆。Akshay 说 Samir 团队和研究团队一直在改进。他和朋友家人聊 ChatGPT 最让他们喜欢的地方，排第一的大概就是“它了解我”，他们的 ChatGPT 是他们自己的。在云端的 ChatGPT Work 里，所有对话默认继承你的 ChatGPT 记忆，知道你的背景，也能写回这份记忆。swyx 问是不是像一个小文本写入、写的时候会告诉你？Akshay 说是同一套 memory V3 系统，主持人接了一句“dreaming V3”。他说这让从 ChatGPT 到 ChatGPT Work 感觉像是在延续自己用了很多年的东西。

swyx 问这基本是一个检索问题：检索对了没有，是不是聚焦在错的东西上，假阳性和假阴性哪个问题更大？Akshay 说他不直接做记忆，没法确定地说，但两面都有：一面是让它了解你；另一面是要有“情商”，在对的时刻主动提起，以正面而非负面的方式让你惊喜。他说这很难，但他们认为做对了是很大的机会，所以投入很大。

聊天的“一次性”和工作的长项目

主持人问 Work 和普通聊天、和 Codex 的记忆有什么不同：聊天类应用一次性的对话多，Work 里一件事可能做一个月，同一个项目开四个线程，跨会话的记忆怎样做？Akshay 先提出异议：他不认为聊天和工作的记忆在深度或价值上有根本区别。聊天里短会话确实多，但 ChatGPT 这个产品存在这么久，人们早就在用它做工作和生产力相关的事。他自己的体会是，这些一次性对话日积月累，会变成一份相当稳定、相当准确的“我是谁”的画像。X 上时不时会流行“让 ChatGPT 说出它知道你的一切”，大家都惊讶有多深；主持人说就是那种“吐槽我”的玩法。所以他们觉得值得把这份记忆带进 Work，也希望用同样的基础元素和系统扩展这里的记忆，负责这块的团队正在做。

Chronicle：从你用电脑的方式里学

主持人说他其实不太用 Chronicle，屏幕上正好显示着它，问这算“超级记忆”吗？Akshay 说它的想法是从你怎样使用电脑中学习，作为记忆的另一个输入源。它目前是实验性的，默认关闭，但他建议试试。他说这回到前面的问题：ChatGPT 在 Slack 里搜索会不会漏？同样可以问，它会知道你在电脑上做的所有事、抓住你的意图吗？大概不会，但它大概会找到你不知道的东西，如果能在相关的时候主动呈现给你，在你做任务时，他发现挺有帮助。

主持人问主要是用于洞察和长期的东西吗？Akshay 说对，洞察，以及积累能让你在某些任务上更高效的上下文，但很难描述，要亲自感受。两位主持人讨论了一下：让它翻你的记忆或日志、生成 skills，这用定时任务也能复现；区别在于有 Chronicle 时记忆本身是从它那里产生的，所以更深。主持人说他想要更多例子，Akshay 的建议是打开它，看它在哪里开始帮到你，“你会惊讶的”。

15. 产品开发和技术岗位怎样变，想法和品味成瓶颈

节目位置 1:01:48–1:06:11 · How AI Is Reshaping Product Development and Tech Roles / Ideas, Taste, and Why LLMs Struggle to Generate New Ideas

想法到实物的循环变短了

主持人说 OpenAI 里有很多前创始人，问 Akshay 怎样看 AI 前后做产品的变化。Akshay 说变化很大，从想法到真东西的速度令人兴奋。五年、十年前，如果你很能将就、愿意只做最小可行产品，也能很快；现在能做的范围宽得多。他们内部看到的是，这让你能更快验证，和用户聊、和内部的人聊（这里字幕不清），确认方向对，这个循环比以往更闭合，对产品开发和用户都是好事，用户一开始拿到的产品就更好。

团队变小了吗？他说要做的事多了很多：个人或小团队能完成以前需要更多人的事，但同时要做的也更多，所以团队的野心更大。角色上，他看到典型的产品开发职能之间界限在模糊，EM（工程经理）、PM（产品经理）、工程师、设计师之间。

T 型人

主持人念了一句流传的说法：科技行业只会剩四种工作，“AI slop 大炮”（狂烧 token 的人）、SRE（站点可靠性工程师，更负责任的那批）、卖东西的大人，还有“好看的人”。Akshay 的猜测是，每个人都会变成 T 型：AI 让每个人都能当通才，比如他以前根本做不出设计，现在也许还缺视觉品味，但能借 AI 迭代出东西；同时每个人有一项专长，就是 T 的那一竖，借 AI 能钻得更深。有了这个基础，能做到的事几乎没有上限。

LLM 还给不出好想法

主持人问专长上的瓶颈是什么，要更多设计师、更多 slop 大炮，还是更多好看的人？Akshay 说瓶颈会变成想法和品味。因为谁都能动手做，这是自下而上野心的时代；要做的东西太多，你总会被手上想法的数量和正在做的事情的数量卡住。

主持人问模型能帮上忙吗？他举了自己的例子：他有一个前端设计 skill，让模型给出四个风格迥异的方案，很烧 token，然后他挑“这块喜欢、那块喜欢”再合起来，他有方向，但说不清。他说最希望能用、却用不了的自动化，就是“给我带来新想法”，LLM 在这件事上就是不行。Akshay 说想法不是凭空来的，通常有来处：在产品开发里，来自和用户聊、对你看到的摩擦或反馈做反应、在已经规划好的基础上延伸。所以前面说的那种通才永远有价值，由他们把循环闭合，提出扎根于反馈和用户对话的想法。

16. 衡量生产力：击球质量，忙碌和进展

节目位置 1:06:11–1:10:57 · Measuring Productivity, Quality At-Bats, and Motion vs. Progress

生产力的定义

主持人问他带 productivity 团队，怎样定义生产力。Akshay 说他们的使命是让人能做以前做不到的事。现在从知识工作的角度看：人不再被角色、背景或训练隔开，不管在哪个职能，你都能突然动手造东西、拿到原本可能看不懂的数据。延伸到个人生活，就是给你杠杆，让模型和产品帮你腾出时间做喜欢的事。

老的代理指标失效了

那怎样衡量杠杆？他说还没想清楚，部分原因是太多样了：每个人目标不同，真正的度量是他们能否达成目标，“我们帮到你了没有”。不提前知道目标、不为每个人定制，就很难测。主持人说 ChatGPT 的点赞点踩什么也说明不了，你不知道用户踩的是内容、语气，还是它有没有帮到目标。Akshay 说这很难，但 OpenAI 和整个行业都得解决，因为这就是衡量成功的方式。

衡量方式变了吗？他说一直以来真正想测的都是团队或个人有没有达到、或者更接近目标，以前用的是代理指标：代码提交数、代码行数，主持人补上“故事点”，还说故事点要回潮了。他说有了 AI，这些代理指标开始失效，用了多少 token、提了多少 PR，和“团队有没有达到或走在达到目标的路上”不再高度相关，需要新的度量。

给管理者的一条：看击球质量

主持人请他给收听的管理者一条可以试的东西。Akshay 说他看重的是 at-bats（棒球里的上场击球次数，这里指一次完整的尝试）：团队有没有练出不只数量多、而且质量高的击球能力？能不能高效地走完从产生想法、做出来、拿到反馈、对反馈做反应、真正验证或否定假设、再进入下一个想法这一整圈？这既关乎写出的代码、做出的设计、写出的规格，也关乎团队文化：有没有足够的谦逊，能一遍遍走这个过程，同时保持动力和兴奋。他说在这项技术的前沿、要做的东西这么多的时候，这是他们看得最重的一点。

陷阱：把忙碌当进展

主持人问衡量生产力有什么常见陷阱，他观察到很多团队“加了很多 LLM，做了各种仪表盘，但什么都没变”。Akshay 说陷阱大概就是把 motion（动起来、忙碌）和 progress（进展）混为一谈。有了现在的工具，动起来比以往任何时候都容易；进展要求你对自己到底想达成什么很明确、很刻意。他把这和前面的度量问题连起来：OpenAI 要为所有用户衡量生产力很难，因为太多样；但一个团队应该对“我们的进展长什么样”有很明确的看法，没有的话就很容易把这两者混淆。

swyx 说他很喜欢 motion 和 progress 这个区分，会放进节目文章里。最后他祝贺 1000 万用户，开玩笑说下一次是两个月后到一亿，又改口说两周。
