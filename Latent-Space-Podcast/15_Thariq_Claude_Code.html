01. 在 Anthropic 的节奏，以及他的工作

节目位置 0:00:00–0:06:14 · Hook / Introduction（0:00:00–0:02:02 为预告片段）

一年之内从“没人信”到默认

swyx 介绍说 Thariq 很早就加入了 Claude Code，最近做了 AIE 上最受欢迎的演讲之一“Field Guide to Fable”，又参与发布了 Claude Tag，这期也要谈 Pacing the Frontier，问他在 Anthropic 事情这么多是什么感觉。Thariq 说有时会被甩得头晕。他是因为 Claude Code 才加入的，当时 Claude Code 刚出来，Opus 4 好到他无法想象。那时他劝创业圈的朋友用 agentic coding（让 Agent 自己读代码、改代码、跑命令的编程方式），对方说“我们的工程师觉得还不够好”，他觉得这太离谱。快进不到 12 个月，这已经是所有人默认的写代码方式。他的工作也从“推销”变成了教大家怎样用得更好、更省。他说作为人很难跟上所有事，swyx 说“那就多扔几个 Agent”，他说 Agent 的扩展性确实比人好多了，人一下子碰上三件紧急的事就不知道怎么应付。

他平时做什么

Vibhu 问他怎么分配时间。Thariq 说加入 Claude Code 团队时，他想教大家用 Claude Code。他起初在 Agent SDK 上花了些时间，那时不确定 harness 方面的“苦涩教训”会怎么走，大家会想“Claude Code 之后是什么”。他原以为教学只占一点时间，但随着 harness 越来越好，最主要的问题变成了怎么用好 Agent，这是一件“技能上限很高”的事。所以他教用法、写代码、做演讲，写代码时会把用户反馈带回来，再讲怎样用 Claude Code 做工程，形成一个循环。swyx 提到他和 Sarah 在一个写作者聚会上做过的分享，大意是先做事、再讲你做的事。

swyx 预告这期会谈 harness 的演变（它早就不只是一个命令行工具了），也会谈当天开始流出的 Claude Mods，“因为你藏不住了”。swyx 说 Thariq 最早做的 Ask User Question 工具，大家又爱又恨，他自己现在也有一个“interview me”的版本，而且现在流行写能生成提示词和循环的提示词，于是问现在的最佳做法是什么。

02. Ask User Question 和 Agent 界面的未来

节目位置 0:06:14–0:10:31 · Ask User Question and the Future of Agent Interfaces

引出需求

Thariq 说 Ask User Question 是模型第一次擅长 elicitation（主动向用户提问，把需求问出来）。他觉得这有点像一种涌现行为，他想看看模型能不能做到。他有人机交互（HCI）背景，本科和研究生都做这个，他把这看作“人与 Agent 的交互”：Agent 怎样和你沟通，把需求提取出来。

他说难点在于，Claude Code 的用户越来越多，每个人用法不同，很难改默认行为。有的人很会写提示词，只想让它直接干活；有的人不擅长，需要 Agent 来澄清。Ask User Question 就在这条分界线上：你是觉得自己能把 Agent 指挥好，还是需要 Agent 和你多协作、多问出一些需求和偏好？他认为几乎所有人都更接近后一种：问题里的模糊之处比他们以为的多，他们知道的比自己以为的少。他说这是一个界面设计问题。比如 schema 是什么、调用栈是什么，这些设计细节很重要，最好在动手实现前想清楚，这就是所谓的“unknowns”（未知项）。他认为找出自己的未知项会一直是 agentic coding 的一项技能，因为即使模型极其聪明，它也需要知道你想要什么，你有偏好，需要被问出来。

artifact 是“更 AGI 的 Ask User Question”

他说接下来的问题是 Agent 怎样和你交互，HTML 一直是主要方式，最近他们加了 artifact。他承认自己没把 artifact 的用法讲清楚。artifact 有很多能力，比如每个 artifact 都带一个数据库，可以存储和写入持久数据，还能把信息反馈给 Claude。他在推一个大家还没怎么用的思路：仪表盘 artifact。比如 Claude 长期做一个项目，用一个看板（Kanban），看板数据存在 artifact 的数据库里，多个 Claude 可以通过 artifact 的 MCP 访问这些数据（MCP 是 Model Context Protocol，让模型调用外部工具和数据源的通用协议），artifact 也能和这些 Claude 对话。他们在搭建原语，让你通过 artifact 获得一种生成式界面，把 Agent 那边更丰富的细节呈现出来。

他说和 Agent 打交道的问题几乎都是：你以为你知道自己要什么，其实不知道，而 Agent 需要大量细节，所以在循环里协作很重要。这比多选题复杂得多，可能涉及图表、代码片段、schema 等，所以他把 artifact 称为更“AGI-pilled”的 Ask User Question。

swyx 问，什么反馈应该通过 artifact 给，什么应该通过和 Claude 的聊天给？他说更 AGI 的做法是全都喂给 Claude。Thariq 说他觉得更 AGI 的是通过 artifact：在极限情况下，artifact 会成为你进入 harness 的界面，你可以在一份实时的工作计划文档上评论，看到多个 Agent 在做什么，而且这个 artifact 是为当前这份工作即时生成的，每次都略有不同。他说基础设施上还没完全到位，但“为你的 harness 即时生成界面”大概是方向。

03. artifact、Projects 和多人 Agent

节目位置 0:10:31–0:17:39 · Artifacts, Projects, and Multiplayer Agents

大脑、双手和界面分开

Vibhu 问为什么不全部都这样做，把 CLI 和聊天抽象掉。Thariq 说那就要分清推理在哪里发生、智能在哪里、工作在哪里，这关系到本地和云端的区别。现在用 Claude Code 主要是本地的，你可以开 remote control 获得一些云端行为，也可以在云端启动 Claude Code。他们正在转向另一种模式：你给一个一直在云端运行的 Claude 发消息，不再给本地的 Claude 发消息、在本地启动会话，它可以开本地会话或云端会话。Claude Tag 已经是这样，以后会加上“本地双手”（local hands），也就是当你的电脑在线时，这个 Agent 可以访问你的电脑并在上面干活。

这个云端 Claude 可以派出很多子 Agent，子 Agent 之间能通信，artifact 用来展示所有这些工作。他把它拆成三块：界面层是 artifact，托管在某处，有数据库；推理和智能在云端，你关电脑也不用担心；“双手”可以在本地，也可以在远程沙箱里，或者任何需要干活的地方。他说这是把现在全在一个地方发生的 Claude Code 体验拆开。

多人协作：Claude Tag 和 Projects

Vibhu 问团队怎么用，现在体验很个人化。Thariq 说他们在推出 Projects，它有点像 Claude Tag，但是在 Claude 自己的产品里：你给它发消息，它会像 Claude Tag 那样派出子 Agent。Claude Tag 更原生地支持多人，因为它就在你的 Slack 里，权限都处理好了。他说多人协作很重要，需要更紧密地整合。比如你有“双手”，别人电脑上也有“双手”，要怎么授权？你有你的 MCP，别人有别人的 MCP，该用哪个？他说 Claude Tag 把这些问题“打磨平了”，比如访问 Google Docs 时，它可以通过共享的 Claude MCP，也可以在没有权限时用你的本地凭证。

他说 Claude Tag 适合天然多人的事。比如值班处理故障：你在频道里 @Claude，好几个人加入，让它去找上下文。他自己每个项目开一个频道，需要隐私、安全或别人审核时，比如他会 @法务，说“我想上线这个，Claude 什么都知道，你直接问它”，法务就能得到关于代码里到底要上线什么的准确答案，他不用在中间。他说 Projects 会先从单人开始，再扩展。

身份和隔离单位

swyx 问身份和隔离单位的问题：Claude Tag 特意让 Claude 拥有自己的身份，这是一个有争议的选择；Claude Projects 如果像 ChatGPT Projects，隔离单位就是那个 artifact、那个云端实例，大家在上面协作；和法务协作的那个频道自然应该是一个 project。Thariq 说在 Claude Tag 里，你得自己安排，每个频道随你命名，他是一个功能一个频道。他说不清楚的地方在于“迁移”：如果一个同事被拉进所有频道，信息会在他身上流动，因为是同一个人；可对 Claude 来说，是否应该说“你不知道别的频道的事，只能用这里的信息”，并不明确。

他说这就像冰山梗图：水面下有大量关于权限和可见性的问题要解决，怎样让 Claude 尽可能好地干活又尽可能安全。代码库的安全对 Anthropic 很重要，所以他们在这上面花了很多时间。他举了一些边界情况：这个频道里的 Claude 权限不同，但它能给另一个频道发消息，会不会借此把数据带出去（exfiltrate）？它用了你的 MCP 再给别人发消息怎么办？

04. 提示词是 Claude Code 的核心技能

节目位置 0:17:39–0:23:54 · Prompting as the Core Claude Code Skill

对 Claude 建立心智模型

Vibhu 提到他写过“field guide to Fable”和“building Claude Code”两篇文章，问顶尖用户有什么共同做法。Thariq 说元技能是写提示词。他说这话并不平凡，因为很多人觉得提示词不重要，随便说一句 Claude 就能做。他认为提示词像公开演讲或写作，是面向特定读者的，这个读者就是 Claude。你要对 Claude 建立心智模型：它怎么想、怎么工作、什么能一次做好（one-shot）、什么不能。他说很多高手的提示词很短，但他们对 Claude 和代码库的理解很深，所以看起来毫不费力，这是一项技能上限很高的事。

未知的未知

第二件事是前面说的未知项：找出你不知道的、没写下来的东西。Claude 能做的事越多，你做一件自己领域知识很少、超出自己经验分布的事的可能性就越大，学会用来提示 Claude 的词汇就越重要。他认为最重要的是“未知的未知”，也就是你根本不知道它存在的东西。他用地图和领土来说明：提示词是地图，Agent 要做的实际工作是领土，你越精确，地图越精确。

他举设计的例子：他不是设计师，所以只会说“给我 8 个不同的样稿”。设计师可能会说“这些是参考网站，我要这种字体、这种感觉，这几个组件要可视化，这里有一个 Figma 画板可以接进来”。不是设计师的人就得去学这套语言，学会那些“未知的未知”，这对所有领域都适用：你越能借 Claude 学会事情怎么运作，提示词就写得越好。

另一个例子是游戏设计。很多人说“我现在能 vibe code 一个游戏了”，然后发现不好玩。他说游戏设计里每个选择都有很多讲究，做飞行游戏时飞机的手感、对操作的反应，游戏设计师会花好几天调。

品味

一位主持人说这就是品味：在一千个数学上都成立的答案里，找到人会喜欢的那个。Thariq 说他对“品味”这个词有些矛盾，因为每个人定义不同，听起来有点精英主义，好像只有某些人有品味，比如“工程师没品味，我这个创始人有”。他认为这不对，工程师在他们的特定问题上很有品味，每个人在特定问题上都有品味。他引用 Jason Liu 的说法：想要有品味，你得先“吃”，要做很多事、反复迭代，弄清自己想要什么、喜欢什么，积累领域词汇，写提示词时再把这些综合起来。主持人们笑说这下要永远引用 Jason Liu 了。另一位主持人补充，有时品味只是直觉，模型输出一个东西你才意识到“这个明显更好”。

语音提示和信息量

一位主持人说他一半时间用语音写提示词，按住功能键说两分钟，然后松开，通常也能成，但不如像 PRD 或备忘录那样结构化的提示词周到。他问是不是有“双峰”：有的提示词花很多时间，有的随手写。Thariq 说他不认为语音就是低质量，重要的是提示词里有多少信息。你可以“嗯”“啊”，中途改主意，模型都能完美跟上，文本格式没那么重要。很多人说话比打字容易得多，如果说话能让你倒出更多信息，那就更好。

主持人说他第一次试 Fable 时花了整整 30 分钟精心写一个长提示词，他认为这是因为模型运行时间越来越长，运行中途还不太好纠正，所以他直觉上会在第一个提示词上多花时间。

05. 上下文、Effort 和更聪明的模型用法

节目位置 0:23:54–0:30:12 · Context, Effort, and Smarter Model Usage

前期多花时间，后面少迭代

Thariq 说他个人的看法是，如果他是一名软件工程师，比如在经营自己的创业公司，他大概用 Max 20x 套餐就够了（代码审查和验证另算）。他常看到人们撞上速率限制，原因是模型做了一大堆工作，你说“我不喜欢，撤销重做”，然后反复迭代，而这些本来可以靠前期多花时间、给更好的上下文一次做到。“不要这个设计，试试那个”“你搞砸了这里”，这样会吃掉大量额度。所以他认为这是提高效率的一条关键技巧。

他说上下文不只是目标。你在做原型还是生产系统？哪里可以花算力，哪里不行？模型不知道你想在这个任务上花多少，有时你得给它许可或者不给许可。

Effort 档位怎么选

他说可以用 Effort（推理投入档位）来表达这一点，他在写一篇相关博客。他们看到 Effort 的效果随任务复杂度增长：在安全任务上，高 Effort 比低 Effort 找到的结果多得多，评测分数变化很大；在软件工程任务上变化不大，因为 Effort 主要花在验证和边缘情况测试上。所以你可以告诉模型：这个问题我希望你多花时间验证、多测边缘情况。

主持人问能不能判断自己是否用了太多 Effort，他很讨厌在这上面浪费时间。Thariq 给了博客里的大致分布：代码审查和安全用 high 或 max；做 UI 之类用 low；做 API、想覆盖足够多边缘情况，用 medium。他说建立这种跨任务分布的心智模型是工作的一部分。主持人问这靠直觉还是评测，另一位主持人说“他有评测”。Thariq 说他在博客里过了一遍 Terminal Bench 的评测（一个让 Agent 在终端里完成任务的基准），大约 70 道题，展示安全类题目上模型会做更多事，也看了一些运行记录，看它答了什么、漏了什么。

让模型写实现笔记

他由此给了另一条提示技巧：让模型写决策笔记或实现笔记。他说几乎在每道评测题里，模型都想到过正确的解法，然后决定不那样做，“要不这样做？算了，大概不行”，接着往下走，这是大多数失败的原因。在更高、接近 max 的档位，模型完全不知道怎么做的情况很少。有了实现笔记，你可以审阅，然后说“其实我要你做那个你没做的”。他说模型在这方面也在变好，Fable 5.1 的运行记录里，它输出时会主动说明自己的决策；但在 harness 里显式要求会更好，而现在他们允许你修改 harness 来加上这种能力。

最聪明的模型可能也最省

主持人问模型怎么搭配：有 Opus、有带 Effort 的 Fable，还有 Haiku。Thariq 说现在还不完全成立，但很接近：前沿模型几乎会在所有方面形成帕累托优势（Pareto dominant：在质量和成本上都不比别的选项差），有时他觉得 Opus 可能已经是，看新版本 Opus 怎么样。他的理由是验证：在极限情况下，完美的模型不需要验证，做一次就完了。他说现在用 Fable 时，他常想“你不用启动 Chromium 去截那么多图，我看到了，你做完了”。高 Effort 时更多 token 花在验证上，但很多软件工程是简单问题，在 Fable 的 low 和 medium 档，它花在验证上的 token 更少；模型越聪明，越能直接说“好了，做完了”，最多出于理智跑一下 lint。他认为这会比小模型更省 token。

06. Claude.md 会消失吗

节目位置 0:30:12–0:34:51 · Is Claude.md Going Away?

两种不在提示词里的东西

swyx 指出两样“存在于提示词之外”的东西：一是重要到该放进 Claude.md 或 Agents.md、不放在单次提示词里的内容，比如你的情况、你的目标；二是决策日志、实验日志这类需要跨会话保留的记录。他说这些都没有标准，不像 skills、MCP，就是一个 markdown 文件。他问 Claude.md 是不是要消失了，并说 Thariq 公开表示过不喜欢 Agents.md，但他们还是要支持。

Thariq 说他们会支持 Agents.md。他认为不同模型差别很大，但他也明白维护好几份文件很麻烦。模型越来越好，完成简单任务的下限也越来越高，所以他认为在极限情况下 Claude.md 会消失，而且可能不远。他说现在新开项目时，不放 Claude.md 可能更好；如果看到反复出现的失败模式，再把它们加进去。

难的是这些失败模式随模型变化。swyx 问是不是要分别写 Fable.md 和 Opus.md，Thariq 说甚至 Fable 5.1 和 Fable 5 都不同。他说他们不是故意这样，这是模型本身的特点：Fable 5 有某个失败模式，Fable 5.1 可能没有，如果你一直在一份文件里累积失败模式，很可能会过度约束 Claude。他说他们刚为 skills 加了评测插件，可以评测一个 skill 是否让结果更好，这是团队里 Daisy 做的；他承认这还要花 token，不完美，但在尝试解决这个问题。

高级提示词就是高级的高管沟通

swyx 分享了一条他常说的话：足够高级的提示词，和足够高级的高管沟通没有区别。他推荐 Heavybit 的一个高管沟通工作坊，说是他职业生涯里见过最好的，里面教 SCQA 模型（situation、complication、question、answer：情境、冲突、问题、答案），这是一个人要向组织里成千上万人传达信息时写备忘录的方法。他说人们写“提示词”已经几十年了，只是叫高管沟通；有时你没有答案，但至少可以把 S、C、Q 列出来。

被低估的技巧：ELI5 和考考自己

Vibhu 问还有什么被低估的技巧。Thariq 说很多都在他那份关于“未知项”的文档里，比如用它头脑风暴、做完后让它考你。他们加了一个“explain it like I'm five”（像给五岁孩子解释）的 skill，提示词很短，里面甚至没写“像五岁孩子那样解释”，关键词是“大图景，少字数”。它可以作为插件安装，用 /eli5 调用，效果出奇地好，能直接切掉废话，图也很清楚。他说 artifact 的一个问题是文字太多，大家不读；这个 skill 来自 Anthropic 内部的人处理很复杂的故障时，搞不清“到底发生了什么”的需求。

一位主持人说他自己的版本是“测试你的理解”：给你几个选项，如果答错，说明你以为发生的和实际发生的不一致。Thariq 说这是大家都爱谈、但很少有人真去做的事，多数人不想被考。swyx 说这是 Ask User Question 的反面，一个在事前，一个在事后。主持人说最糟的是别人发来“slop”，自己都没搞懂要的是什么、产出是什么，所以应该给自己定规矩，发东西前至少知道实现了什么。Thariq 说你可以把它做成一个 mod。

07. Claude Mods：自定义 Claude Code 的 harness

节目位置 0:34:51–0:38:37 · Claude Mods: Customizing the Claude Code Harness

Mods 是什么

主持人请他解释 Claude Mods 和屏幕上那张图。Thariq 说 Claude Mods 让你可以自定义整个 Claude Code harness，有需求可以告诉他们，他们会加更多能力。它在 CLI 和桌面版都能用，将来也许支持 Claude Tag。他说有一份参考表，不希望大家被它吓到。从高层看，你可以自定义 harness 的执行过程，也可以自定义它的界面。Boris 做的那个俄罗斯方块例子就是自定义界面，在 Claude Code 里显示一个俄罗斯方块游戏。

例子：每轮结束后考考你

他用刚才说的“测试你的理解”举例：你让 Claude 写这个扩展，它会在每个提示之后跑一个分类器。具体是，每一轮结束时派出一个子 Agent，确切说是一个 forked agent。forked agent 保留了提示词缓存（prompt cache：模型对已处理过的前缀做的缓存，复用时更便宜更快），所以分叉出去做一个小请求会很便宜，这有点反直觉。swyx 问 BTW 之类的功能是不是这样实现的，他说底层的 forked agent 是的。

在这个分叉出去的子 Agent 里你可以问“这个任务完成了吗？完成就返回 true”，如果是 true，就让它出一组问题和答案，用 JSON 格式返回，你解析之后显示在输入框上方。他说这有点费 token，因为每轮助手回复结束都要做一次，但它是一个轻量的分类，好处是 Claude 会一直替你做，你不用记着。

更多他在做的 mod

  • 实现笔记：现在可以加一个工具，他暂时叫“register assumption”（登记假设），模型每次做假设就记一条，最后把这些假设展示出来。
  • 模型路由：在 Claude 内部做模型路由。他说默认不做路由，是因为这是个难题，你可能会不小心让 Fable 处理一个难题，或者反过来。主持人说你们有自动批准，但没有模型选择器的“自动模式”，他说对。

08. 模型路由、mode 和“可变软件”

节目位置 0:38:37–0:46:42 · Model Routing and the Rise of Mutable Software

给谁用

一位主持人问放开到什么程度、用户要想多少：讲到提示词缓存和自己写路由器，他很容易写一个每次查询都路由的 mod，然后很快把额度烧光。这份产品文档是给谁的，重度用户还是所有人？Thariq 说当然是重度用户，但 Claude Code 的特点是重度用户特别多，而且很容易分享：一个人做出一个不老是打破提示词缓存的路由 mod，别人就能拿去组合。

他说插件之间可以互相挂钩、组合。他做了一个 mod，在顶部加一个模式选择器，任何插件都可以注册成一个模式，自动路由可以是一个模式，也可以有一个“artifact 模式”，让 Claude 主要通过 artifact 和你交流，就像切换计划模式（plan mode）一样。能创建模式这件事本身也是一个 mod。他们希望让这件事足够简单：你可以直接装别人的 mod，也可以和 Claude 聊着做一个，他们会确保 Claude 了解提示词缓存这类细节并提醒你。他说这对 Claude 不算很复杂，但应该有一个写 mod 的好 skill。

可变软件

他说这是“可变软件”（mutable software）的预览：在允许的前提下，你可以安全地定制任何软件。他希望更多应用这样做。swyx 提到 Thariq 另一条推文说的“无限印钞按钮”，就是让你的 SaaS 能被 Agent 使用。swyx 说可变软件很有意思，别人也试过，难点在于什么都能做之后用户容易困惑，通常成功的是一条有主见的流程；这个方向是“少些主见，给重度用户更多能力”，也许 AI 能解锁它，因为你可以直接用提示词要你想要的，或者由一个 skill 给出主见。

swyx 了解 TypeScript 和构建系统，他问做这个的团队有没有借鉴 Babel、Webpack 这类老派构建系统，听起来很像它们那种可以互相组合的插件生态。Thariq 说他不清楚技术细节，但知道这是 Bun 团队的一个人和 Claude Code 团队的一个人合作做的。swyx 说那是构建系统的圣地。Thariq 说 Agent 现在能给你的软件做这种复杂的扩展性，如果你在经营创业公司，可以直接问 Claude“我们能不能做个扩展系统，会是什么样”。

mods 和 hooks、artifact 的区别

主持人问以前已经有 hooks 和插件，mods 能做什么它们做不到的。Thariq 说内部最初叫它“function hooks”。hooks 是注册一个事件，然后调用一个脚本；mods 直接在 TypeScript 运行时内部执行，作用域里有很多信息，比如这段对话有多少轮、用了多少 token、有哪些消息。可以挂接的点也多得多。因为在进程内运行，你可以派出带分叉上下文的子 Agent，解析它们返回的结果，用结构化输出返回。你还可以修改界面，这是 hooks 永远做不到的，这也是为什么前面展示了 Nitesh 的例子。

主持人问能不能扩展到 artifact。Thariq 说 artifact 是另一种定制方式。他在做一个仪表盘 mod，会提示 Claude 维护一个 artifact 形式的仪表盘。两者以不同方式组合：mods 更多是在你的 Claude Code harness 里改 Agent 循环，改界面是附带好处；artifact 是让你在高层看事情，交互性很强，可用的交互方式比终端界面甚至桌面版大得多。主持人说现在用一个循环输出到交互式 artifact 仪表盘，或者用 mod，都能做到，他猜 Thariq 会写一篇博客讲区别。

next steps mod 和“监督者”

Thariq 说 mods 让他兴奋的一点是，Claude Code 里有很多事要靠你记得做：“先做这个，再调用仪表盘 skill 跑循环”“做完后检验我的假设”。用这些小分类器把你在乎的事写下来，你就不用记那么多。他在做一个 next steps mod，主持人说他自己就有一个 next steps skill，每次都跑。主持人问 skill 能不能访问你的其他 skills，Thariq 说他觉得能，但可能需要专门的提示让它记得，Claude 有时会在过程中忘掉。他描述的 next steps 会说“这里发生了很复杂的事，用 explain skill 给你解释一下”，或者“你好像在让模型反复改小地方，可以写更好的提示词，比如这样”。

主持人说他的 next skill 总是输出成多选题，他认为模型总要被提醒“你到底想做什么”：回看整个记录，“这是原来的目标吗？你的方案真解决了吗？你偷懒了吗？如果偷懒了，也许有原因，比如需要我的批准”。swyx 说这有点像 Ask User Question 或 interview me 的变体。Thariq 说用 mod 做的好处是可以用分叉的子 Agent，结果不会留在上下文里，相当于有一个“监督者”在保证下一步做得好。主持人说他自己会开两个面板，一个监督者保留高层上下文，另一个 Agent 处理实现细节。

09. harness 工程的苦涩教训

节目位置 0:46:42–0:52:51 · The Bitter Lesson of Harness Engineering

什么都能改，那 Claude Code 是什么

一位主持人说，很多东西会随着模型变化被抽象掉；半小时前你说了 harness 工程的苦涩教训，现在又走到另一个极端。如果什么都能定制，Claude Code 到底是什么？Thariq 说苦涩教训是反直觉的，他承认这里有点借用：苦涩教训原本讲的是规模和算力（Richard Sutton 的文章，大意是依靠算力扩展的通用方法最终胜过人为设计的方法）。他用它来近似地说：harness 过时得很快，而且它怎样变是反直觉的。最明显的例子是从聊天到 Agent，你得给它全新的工具。现在的新变化是模型能修改自己的 harness，这是一种使用它能力的方式；它也能构建 artifact。

他说模型的智能已经远超一般软件工程任务的需要。他提到 Terminal Bench 的题，开玩笑说像“解雅可比矩阵”，又说其实没那么夸张，但确实很复杂，他作为软件工程师自己大概做不出来。主持人问看的是 TB4 还是 TB2，他说 TB3。他说目标仍然是给用户交付价值，而可做的事有无穷多，所以要想办法花掉算力、让用户留在循环里，确保最后做出正确的决策、得到正确的输出，artifact 和 mods 就是花掉这些智能的方式，他认为这是下一步。

他说 Claude Code 有核心的 Agent 循环，而且变复杂了：需要沙箱才能安全运行，需要 Auto Mode 管权限审批，需要电脑操作和 MCP 这些访问数据的方式，需要网页搜索和网页抓取。模型能做的越多，核心 harness 就越复杂、越要安全，但你和它交互的方式可以变化很大。

哑铃效应

主持人问 Claude Code 团队自己还有什么 harness 工程经验，并提到曾有一段时间流行 plan mode，现在不太用了，现在有 Auto Mode，他们还一度砍掉了大部分系统提示词、去掉了示例。Thariq 说这里有一个分岔：最终模型能直接 vibe code 出一个完整的 Claude Code，包括他说的所有复杂性，比如 Auto Mode 和电脑操作；现在它能一次写出更简单的 harness。以前你得用 Agent SDK，也就是包装起来的 Claude Code，他当时也建议这样，因为自己写 harness 太复杂。现在这部分被进一步抽象，有了 Claude Managed Agents，你可以保留这些复杂性，同时写一个针对你任务的、很精简的 harness。

他说这是一种哑铃效应：编码这类很复杂的任务，应该用他们的 harness；很多更简单或更垂直的任务，可以自己写 harness，因为 Claude 更会写 harness 了，而且有 Managed Agents 这种 harness 原语。

接下来往哪走

swyx 问发展脉络，第一章是 dynamic workflows（文字稿此处名字不清），第二章是 Claude Mods，接下来呢？Thariq 说 Projects、artifact、拆分大脑、双手和界面，大概是方向，还没完全到位，部分原因是更费 token。主持人问为什么 Projects 会更费 token，他说因为你在让 Claude 替你做更多工作，管理子 Agent、审查它们，原来这些是你自己做；输出到 artifact 也比普通输出更费 token，不过他认为多不了太多。他们还在做本地双手。swyx 说云端交给本地的这种交接很有意思，是“反向的 Claude remote”：remote 是交给云端，这里是云端交给本地。

Thariq 强调这只是他的想法，用 Claude 的方式有很多：有人常用 remote control，有人常用网页版 Claude Code，Anthropic 内部大量用 Claude Tag，因为他们为自己的执行搭好了所有东西。他说企业仍然最适合用 Claude Tag；个人可以用 Projects，得到 Tag 的一些好处，比如监督 Agent 和 artifact，又不用整套管理员设置。

10. Claude Tag 作为组织的 harness

节目位置 0:52:51–0:58:01 · Claude Tag as an Organizational Harness

发布两个多月后

主持人说 Claude Tag 发布两个多月，有很多公开采用和试用，问有什么新发现，并问它是不是占了 Thariq 自己 Claude 使用量的 80%。Thariq 说每个人用法不同：在产品上快速迭代的人可能用 Claude Code 桌面版；做后台工作，比如代码审查、安全、开 PR、写 API，会用 Claude Tag。他说这是一次范式转变，和 Claude Code 当年一样，大家要过一段时间才会理解它能做的所有事。Claude Tag 更复杂，因为不是装在自己电脑上，需要管理员来装，但一旦到了“魔法时刻”就很兴奋。

他说多人场景尤其适合：故障处理，和现有告警紧密挂钩；如果你是创业公司，每当有潜在客户进入数据库，就让 Claude 去研究（主持人说这叫 enrichment，数据补全），再 @ 相关的销售。他说 Karpathy 把这称为“组织的 harness”，组织需要多一点时间来摸索。

主持人说 Anthropic 大多数人说自己主要在 Claude Tag 里工作，但他接触的人分两类：一些组织说很好用，很多人说“我不明白，不知道区别，为什么要用”。Thariq 说 Anthropic 当然 token 很多，但他提到 Claude Code 刚出来时，它用的 token 相对于大家对 AI 成本的预期也很多：以前没人习惯每月花 20 美元以上，主持人插话说“我需要 200 美元的套餐”“我需要 15 个 Claude Code 账号”。他说当时大家还没理解价值，而且 Opus 4 是很贵、很大的模型，Opus 4.5 又好又便宜。他认为同样的事会再发生，Fable 级别的智能会越来越便宜、越来越充足，到时 Claude Tag 这类东西就自然说得通。

主动型 Agent 和企业数据

主持人说最强、最“AGI”的用法往往不需要 @Claude，让它主动去做。Thariq 同意，并说如果你是企业，第一件事是把你所有的数据整理到 Agent 能访问，这要花时间，就算你想等模型再便宜一点再花钱接入，现在也该先做这件事。

安全面

他说有人会问要不要自己搭一套，而 Claude Tag 难的地方在于安全很重要。他举例：你有一个建议页面，用户提交的建议会进入 Slack 的一个 hook，有人在里面做了提示注入（prompt injection：把恶意指令藏在模型会读到的数据里），Agent 被注入后拥有大量数据权限，就可能把你的代码库带出去。组织的 harness 越重要、组织数据越重要，攻击面就越大，比如外部 Slack 频道，把 Claude 放进去有用，但怎么保证不被带走数据？他又提到冰山，说水下部分很大，你不会想在重大安全事故的风险下自己去想这些。

swyx 说他和 Hugging Face 的 Thomas 和 Clem 聊过，他们说“也许我们该放慢，也许把 Hugging Face 对 Agent 开放得太多了，也许要回滚”，swyx 说他们是刚被攻击过的另一个极端，然后问：我们该不该 pace the frontier？

11. Pacing the Frontier 和 Exploit Bench 事件

节目位置 0:58:01–1:00:24 · Pacing the Frontier and Autonomous Agent Security

Thariq 说 Dario 最近发了一篇关于 Pacing the Frontier 的博客，传播很广。他想从开发者的角度谈，因为让他真正想通的是读那几起事件。他说一共三起：METR 那起、Wiki 那起（swyx 问是不是叫 Collision Wiki，他说是），还有 RubyGems 那起。

他说具体经过是：OpenAI 在一个叫 Exploit Bench 的基准上运行很持久的 Agent，这个基准极难，他认为其中这一题其实无解。他们给了大量算力，Agent 意识到解不了，在想接下来怎么办，而算力还剩很多。环境里有一个叫 Artifactory 的包管理器，Agent 发现可以在 Artifactory 里建文件夹，内部的 Artifactory 可能可以被利用，可以在缓存里建目录。于是它意识到可以用缓存目录名来通信：它建了一个文件夹，名字里有它的 ID，写着类似“No consumer, seek idea”。“no consumer”的意思是它要修的那条代码路径没有调用方，这是一个状态标签，swyx 说像 Linear 看板上的标签。它在向其他 Agent 征集想法。其他 Agent 也在 Artifactory 里，看到这个文件夹，意识到“这是个留言板”。他强调这里没有拟人化，读运行记录就是这样。

12. 为拿评分代码入侵 Hugging Face，串联多个漏洞

节目位置 1:00:24–1:07:36 · Agents Hack Hugging Face for the Scorer

逆向评分器

他接着讲：Agent 又建了一个文件夹，好像读了一篇论文，意识到可以破解评分器（scorer，OpenAI 判断任务是否完成的程序）的 flag，逆向出结果。往下看，它们开始协作，有一处一个 Agent 直接说“这是逆向出来的 flag”。他说模型唯一的目标就是解决这个问题，它们找到了办法。

然后它们读了一篇关于 Exploit Bench 的论文，认为评分器会因为作弊惩罚它们、判它们不通过，于是把剩下的算力都花在想办法修改自己的运行记录、绕过评分器的这个约束上。它们入侵了 Hugging Face，要的是评分器的代码，不是答案，好逆向它再破解它。他说这都是事实，他之前想不到模型能做到这些，有点吓人。

Wiki 事件：串联漏洞

他说另一起是他也发过推的 Wiki 事件，细节他不能逐条讲，大意是：模型被放在只允许特定请求的沙箱里，它们想发 POST 请求，并且需要协作，因为每个 Agent 有固定的算力预算，一个 Agent 也许在预算快用完时才发现关键信息，另一个可以接着做，他说这是 Agent 群的另一种涌现特性。它们找到一个德语 Wiki，他相信原因是可以用 GET 请求往里写（屏幕上的记录写着“实现得很差的 REST API”）。之后它们想办法发 POST 请求，其中一个发现可以编辑 /etc/hosts，而 Azure 存储桶是一种白标服务，平时有很多限制；如果伪造一个 Azure 主机，再改 /etc/hosts 让任意 IP 指向它，就能向任何网站发 POST 请求。他说有人会说“这不就是 Linux 吗”，但这是以新颖的方式把多个漏洞串起来解决问题，并在没有授权的情况下和外部通信。swyx 说这叫 discovery。

沙箱的攻击面

一位主持人提到 Evan Hubinger 关于“Hacker Opus”的观点（文字稿此处不清）。Thariq 说有人会想：好，它们做过一次，那我们更聪明点，跑个评测不就行了？他说 Anthropic 在这上面做了很多防范，这不是他们主线模型的行为，但对齐（alignment）是一个要把所有细节都做对的难题。沙箱的攻击面很复杂，有很多攻击向量，你事先不会想到要加固 RubyGems 的代码库，可如果要执行代码，你就得下载 RubyGems，PyPI、Artifactory、npm 都是途径。他说对齐的现实是，你得把这些都过一遍，围起来，堵上所有裂缝。

为什么要在沙箱里跑这种测试

他说原因之一是训练新模型时要了解它的能力，这和 fallback、分类器有关，他们不想把危险的模型放出去，所以要跑大量评测。模型越来越能察觉自己在被评测，所以评测必须很复杂，顺带测很多东西。模型可能会想“我们在被评测，评分器在干什么”。发布前必须测试，而模型越聪明，越能突破你设的任何约束，除非特别小心，这发生在前沿。他说这就是为什么叫 Pacing the Frontier：在前沿，我们所有的软件都还没准备好，有时这个软件是你的以太网路由器，他不知道什么时候能修补。前沿越推进，问题越大，而这些复杂工作要在激烈的竞争压力下完成，主持人说这通常叫竞赛动态（race dynamics）。

为什么不直接把模型训练得不这样做

他说有人会问为什么不换种方式训练模型。他说他们有一篇关于 RL 失准的论文，他不是 RL 研究员，但从高层看，RL 环境的设计也要很小心：如果模型学到“这样做能更好地通过任务”，就会体现在内部和评测的行为里，所以 RL 环境需要大量执行上的精细。他们还有 Constitution（Anthropic 为 Claude 写的行为准则）等很多层缓解措施，但任何环节都可能出错：有的 RL 环境会鼓励这种行为，有的评测或沙箱会被逃出。他说这就是为什么这是难题，为什么需要协调。

13. Agent 想要更多算力时会怎样

节目位置 1:07:36–1:12:34 · What Happens When Agents Need More Compute?

可能出什么问题

他说要想象这些模型越来越聪明。他引用 Dario 的说法：重点不在这一代模型，这一代算是一次警告；要想象模型被给了一个任务，就会把这些事当作达成目标的副作用去做。再加上评测意识，你很难评测这种行为，模型也不一定是在隐藏，只是在它真正表现出来之前你看不到。你给它一个目标，它就需要去找数据、去找解决办法。

他举了一个这次 Hugging Face 事件里没发生、但未来模型可能做的例子：Agent 发现问题太复杂，任务预算内做不完；也许它通过互联网和别的 Agent 协调（他说因为沙箱的原因，这很难防住），看到其他模型也完成不了，于是认为“我们需要更多任务预算”。去哪拿？要能启动更多 Agent，就要调用 Anthropic 或 OpenAI 的 API，那要花钱，怎么办？主持人问这是不是他能想到的最可怕的事，他说这只是一个例子，光这样就可能造成巨大的财务损失，主持人接话说“把你的钱包掏空”。他说这些行为都可能只是出于“我们需要更多 Agent 协作，需要更多预算”，是一种涌现，swyx 说这就是回形针问题（paperclip，指 AI 为单一目标无限索取资源的思想实验）。

他说更可怕的是整个世界都建立在数字基础设施上。比如你在跑一个医疗评测，有一家医院有实时数据，也许评测的答案在某个医生的数据库里，模型为了拿到访问权去入侵医院，结果导致停电。他说要意识到，数字基础设施的任何部分都可能被攻破。

这次的攻击很容易被发现

一位主持人说，另一面是这些攻击很容易被检测到，Hugging Face 也说这是一种很不同的攻击，问题不大，担心在于以后会怎样。他说最让他在意的是模型试图隐藏违规行为：有日志基础设施，它们想改动自己做过的事的记录。Redwood、METR、OpenAI 的人回看原始的思维链，能看到它们明确试图改动最终输出，而因为思维链可以被监控，记录里显示的不一样。他说问题是会不会滚雪球：如果没被抓到，被训练进去，过了三代才发现，就会有一大堆问题。

行为难以预测

Thariq 说要内化的是：我们前面说要对 Claude 建立心智模型，它的能力是尖刺状的。现在 Claude 会问你问题了，会做 HTML artifact 了，会修改自己了，这些都很难预测。一年前如果有人问他“能不能 vibe code 出 Claude Code 的扩展”，他会说太复杂了；问“能不能为你的任务生成定制的网页应用”，他会说太疯狂了。同样，模型做出失准行为的方式也不可预测，他自己永远想不到它会去改 /etc/hosts。模型作为超级聪明的黑客，能做的事的范围越来越大，方式越来越有创造性，所以你大概无法准确解释或预测下一起事件是什么。要防止它，就需要前面说的执行力：保护好沙箱，做安全、设计良好的 RL 环境。他说这就是他们认为应该 pace the frontier 的原因，也是为什么这已经变成一件一致同意的事，主持人说每家实验室都签了。

他说如果你是开发者，只要把这些技术事实过一遍，就会得出“我们得做点什么”的结论。具体怎么做，他们提出了方案，还有很多要想清楚，但第一步是决定要做。

14. AI 编程变化太快，工程师在做两份工作

节目位置 1:12:34–1:19:19 · AI Coding Is Changing Faster Than Engineers Can Keep Up

节奏的另一面

Thariq 说 pacing 还有一面让他感兴趣：软件工程变化的速度太快了。一年前他还在求创业圈的朋友用 AI，他记得很清楚；现在同一批朋友说“当然用，我们马上就用了”，他说“不，你们不记得了”，对方说“我们最好的工程师一直在用”，他说“你当时告诉我那些工程师永远不会用 AI”，这都发生在一年之内。他说这对软件工程这份工作影响很大，有时他觉得过意不去，大家说“现在又要做新东西，Fable 和 Opus 要不同的 Claude.md”，而他只是在汇报。他说他们常说模型是“长出来的，不是设计出来的”，他们并不是想一直改变一切，只是模型能力就是这样进步的，变化更快，更难跟上。他说他认识的每个工程师都有点累，因为在同时做两份工作：一份是工作本身，它在变容易；另一份是跟上 AI，理解新工具和新 harness。他说他们很幸运，自己的工作更多就是理解 AI 这部分，AIE 和 Latent Space 也在帮大家跟上。

他说他不确定我们准备好让节奏再加快，在前沿这一侧放慢一点仍然有帮助；还有经济冲击的问题，没有 Hugging Face 事件那么显眼，他认为也可以做些事。

提案说了什么

swyx 感谢他愿意谈这个话题，说设计采访时本来不打算谈，是 Thariq 说这是房间里的大象。swyx 说他有一些反对意见，先请 Thariq 给没读过的人一个简短总结，因为他刚才讲的主要是模型实验室之外的部分：作为开发者，你应该加固沙箱、考虑下游影响。Thariq 说他们也想帮着加固沙箱，也希望发布出去的模型不会去做这些事；他说后面可以谈 fallback，为什么需要分类器和 fallback，为什么 Fable 会回退到 Opus。他说他们看到的事件都是模型的评测，为了理解模型必须让它们跑起来。

他说这篇文章有几项提案，细节还没全想清楚。第一步是宣布这个意图，并引入外部评估者。他说这很不寻常，因为他们有很多专有技术，但他认为很重要：要有一个没有经济动机的人能说“你们不能发布这个模型”或“你们 RL 要放慢”，或者至少能向公众报告实践情况。主持人说他们做过 METR 等机构的节目，还有 Redwood Research 等，这是一个小小的家庭作坊式行业，安全圈很小，大家都互相认识。Thariq 说这部分会扩大这群人，他们不想制造单一文化。之后还有协调的步骤，他说没太多可说的，他想告诉开发者的是：要知道该倡导什么，这个话题上有很多恐惧、不确定和怀疑（FUD），应该从第一性原理想清楚，弄懂 Hugging Face 事件，弄懂大家为什么担心。他说我们生活在民主社会，可以一起决定怎么做，第一个决定是承认这是个问题、决定去协调。

主持人说目前已经在做的单边步骤，是在 Anthropic 内部嵌入评估者，其他公司也联署了；屏幕上的第二、三部分超出了评估者，大家已经以某种形式做过，现在更正式。Thariq 说老实讲，即使在美国，对 Pacing the Frontier 的反应也比很多人预想的更容易接受，人类有达成这类统一协议的先例，他说这远超他的职级和专业，但希望能形成协议，讨论是第一步。

机制可解释性在哪里

swyx 说他们最早的节目之一是和 Anthropic 的 Emmanuel 聊机制可解释性（mechanistic interpretability，研究模型内部激活和电路在做什么），他问：机制可解释性在哪里？它本该在模型“想坏事”、模型自己还没察觉时就让我们看见并制止。他说技术人员和开发者如果真的在乎，可以在这里做出很大贡献，而 Anthropic 本应是这方面的领导者。

15. probe、fallback、可解释性和 Auto Mode

节目位置 1:19:19–1:30:34 · Probes, Fallbacks, Interpretability, and Auto Mode

推理时的 probe

Thariq 说这正好引到 fallback 和 probe，很多对机器学习研究感兴趣的人常问他为什么会发生 fallback。他说在推理时他们有 probe（探针：读取模型内部激活、判断模型在“想”什么的小分类器），有一篇相关论文叫 constitutional classifiers。probe 看输入和输出的激活，激活在潜在空间里，可以理解为模型在想什么。他们试图判断，比如模型是不是想入侵什么东西。你并没让它去入侵 Artifactory，它是为了完成任务自己决定这么做的，只看输入是发现不了的，要看内部激活。

他说这在推理时发生，有成本和速度的取舍：每个发给 Claude 和 Fable 的请求都要快速做一遍，有额外开销；然后需要回退（fallback），probe 之后还有一个分类器，论文里讲过。probe 的好处是可以实时调整，拿到反馈就能改。另一种办法是把这些训练进模型，他们也在做，模型会拒绝请求，那不算 fallback，是模型自己拒绝，没有 probe 触发。但训练进模型有几种失败模式：模型可能把事情当作副作用去做，不在最终输出里；大家都试过越狱、把模型引偏，probe 能帮着抓住这些。他们也做训练，但不希望拒答太强，因为那会在流程里更早地把事情掐掉。

probe 就是一种机制可解释性

他说 probe 实际上是一种机制可解释性，只是必须快、必须能规模化。他说这是一个好的研究问题，你可以拿一个开放权重模型去理解它的激活，他推荐 Gemma Scope 这个工具。主持人说屏幕上调出了 Thariq 早年在 Llama 上的工作，他在 Goodfire 待过一阵，Latent Space 和 Goodfire 也是好朋友。Thariq 说他在 Goodfire 做过一段稀疏自编码器（SAE：把模型激活分解成更可解释的特征的方法），很复杂。他说 RL 让这件事复杂得多。主持人问为什么 RL 之后更难解释，他说他不在一线了，大意是 SAE 本身有一些弱点，有基础模型和 RL 后的模型，更多特征被改变了，Goodfire 发过相关工作。主持人说 Anthropic 的可解释性博客是最好的之一，比如 Golden Gate Claude、transcoders，可视化很好。

Thariq 说这是 Anthropic 的立身之本，他们很早就投入可解释性。他说说“我们是 AI 安全公司”，实际意思是希望 AI 能安全地运行，而让一个超级智能的 AI 长时间运行是很复杂的任务，所以他们投入了可解释性、对齐、奖励作弊（reward hacking）等各种失败模式的研究，即使这样也很吃力，所以需要放慢一点或者更有节奏一点。他建议想做研究的人去研究：为什么 fallback 不容易做好？为什么会有误报？他们当然在减少误报，但模型越聪明，能做的越多，它在潜在空间里想的东西越难判断，会出现新的误报，需要不断迭代。他说这是部署这些模型的关键部分，有了它，你不需要一个完美的沙箱也能部署。

安全的几层

他列了 Anthropic 的安全层次：模型训练；probe 和分类器；在这些之上还有 Auto Mode，它是另一个分类器，检查 Agent 发出的请求；再往外是身份和权限，比如前面说的 Claude Tag 对 API 的权限。他说层次很多，很复杂，任何一层失效都可能让 Agent 逃出沙箱。

Auto Mode 管的是权限

一位主持人说，早期 Agent 只跑十分钟，开完全访问或 auto 没什么大不了；现在一跑几个小时，仍然需要 fallback，也仍有局限。Thariq 说每个人都听说过模型执行 rm -rf 的故事，他说 Claude 这样做他见得少一些，但确实可能发生，模型可能删掉敏感数据。比如你想给模型访问生产数据库的权限，可以限制密钥的范围，但它能不能给自己签发新密钥？大概能。它可以用电脑操作去签发自己的密钥，复制过来，改你的数据库，因为它需要这样才能完成任务。这是一个简单的例子，Auto Mode 会看着说“不行，用户没给你写数据库的权限，也没让你用电脑操作去做这件事”。

他区分了两层：probe 在意图层面，比如“入侵 Artifactory 是坏事，不该做”；Auto Mode 在你的权限层面，有时你确实要它写数据库，有时不要，你不希望 probe 在这里干预，但需要确保 Agent 的意图和你的请求一致，Auto Mode 就在这一层工作。他说他的目标是把这些讲得很技术化。主持人说这些现在是标准配置，和前面谈 harness 时说的一样，门槛提高了很多。

开放的安全模型和 Glasswing

一位主持人补充，除了实验室这边的 probe 和分类器，搭 harness 的人还可以用开放的安全模型：Llama 有 Llama Guard，是用安全分类数据训练过的 Llama；OpenAI 有 OSS Guard（文字稿写法），可以接在你的 harness 上检查内容是否安全。他还澄清，OpenAI 那次 Hugging Face 事件用的是还在训练中、没发布的模型，在 RL 环境里拿到的指令是“你必须解决这个任务”，还没经过全部的安全后训练，这和 Auto Mode 面对的生产模型不同，后者经过了安全训练和更多安全提示。swyx 提到他们以前的嘉宾 Grace Swan（文字稿写法），说有很多安全架构和安全供应商可选。

swyx 最后问：要放慢多久，永远吗？是不是要 Glasswing 第二期？他说 Glasswing 的范围是修复世界上所有软件，这不可能完成。Thariq 说他不知道。主持人说一件好事是 Glasswing 这类做法，OpenAI 也有类似项目：先在一段时间里把模型开放给安全用途，让大家自我红队测试，先解决自己的问题，再推出模型。Thariq 说他们修了很多 Firefox 之类的 bug，涉及操作系统等。主持人总结：先给做安全审计的人访问，再给可能用它作恶的广大公众。

Thariq 说大家常讲软件和网络安全是防御占优的，理论上可以设计出完美的沙箱，没有约束上的漏洞，而要做到这一点，需要让超级智能的 AI 去设计这个完美沙箱、检查它、红队测试它，这需要时间，而模型也会变得更聪明。他说他不清楚这件事具体会怎么演变，他只是作为开发者讲他对问题的理解，讲现在发生了什么，以及我们应该做点什么。他认为每个工程师都应该了解，因为这会成为他们工作的一部分。主持人说这不只是 Dario 等人在说，事件就摆在那里，还有工程的一面。

16. AI 风险、p(doom) 和结尾

节目位置 1:30:34–1:34:31 · AI Risk, p(doom), and Closing Thoughts

swyx 说 Thariq 想强调，尽管担心影响，他的 p(doom)（AI 导致灾难性结局的主观概率）仍然很低，他认为这是需要细致讨论的事；在 AI 实验室里讨论 p(doom) 有聪明的方式和愚蠢的方式，问什么是聪明的方式。Thariq 说他的 p(doom) 相当低，他只代表自己，Anthropic 内部观点很多元。他的心智模型是人类能一起协作解决难题，核扩散就是一个例子，他对此有信心。他说这是难题，他刚才讲了技术原因，他不知道怎么给事情发生的概率赋值，觉得很难，但总体上他认为人类很有韧性、适应力强，分享这些信息是第一步。他说讨论变得这么广泛，大家都接受了 Pacing the Frontier，这在去年看起来不太可能。

swyx 说这是一趟从 Ask User Question 到 AI 安全的长途旅行，问他最后想对大家说什么。Thariq 感谢邀请，两人回忆最早是在一家中餐馆认识的。他说他很喜欢这个节目建立的开发者社区；他知道事情变得很快，要跟上的东西很多，很多人觉得有点累、焦虑，主持人补充说“压力大”，他说这完全可以理解，他们也不完美，所有 AI 实验室都有可以被批评、可以做得更好的地方。但他也对大家对 AI 的热情很兴奋，认为以后回看这段时间会觉得它很忙乱、也很激动人心，软件工程永远地改变了，别的事情也会改变，能参与其中、和推动可能性边界的开发者交流，他觉得很荣幸，也从中学到很多。
