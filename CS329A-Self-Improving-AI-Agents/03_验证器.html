第三讲：验证器

四篇论文看验证器研究的演进：训练验证器解数学题（GSM8K），逐步验证与过程奖励模型（PRM800K），不用人工标注的 Math-Shepherd，以及用弱验证器集成缩小生成—验证差距的 Weaver

主讲：Azalia Mirhoseini
资料来源：课堂录像（Stanford Online 公开，本文依据录像字幕整理）

一、为什么讲验证

上一讲看到，用反复采样等推理时扩展技术，模型似乎能"知道"很多难题的答案，问题是怎样自动选出正确答案，或者在生成过程中引导模型。这一讲读四篇论文，正好看出这几年验证方法的演进。

二、训练验证器解数学题（OpenAI，2021）

动机是大模型会产生幻觉，会很自信地给用户错误的解答，四年后的今天模型好了很多，但这一点仍然成立。这篇论文的一个贡献是提出了数学推理数据集 GSM8K：约 8500 道小学数学题，强调质量和多样性，更重要的是强调多步推理，题目虽然简单，但要几步推理才能得出答案，解答用自然语言写成。直到今天，GSM8K 对小模型的评估仍然有用，做项目时也可以考虑。

另一个贡献是训练一个验证器，输出"某个解答是正确的"概率。就像人解题时如果有评分标准、能知道自己对不对会很有帮助，验证器给语言模型提供同样的东西。训练方法：

  1. 先用这个数据集的一部分对生成模型做两轮监督微调（她说现在这一步未必还需要，语言模型已经很会遵循指令、懂数学，很多新的验证器直接训练验证目标）。
  2. 对每道题采样 100 个解答，和人工给出的标准答案比对，标记为对或错（题目和答案都经过人工整理，所以知道最终答案）。
  3. 用"题目、解答、标签"训练验证器一轮。验证器本身也是一个语言模型，加了一个小的标量输出头，对每个 token 给出一个二元预测；题目部分的 token 被遮住，不参与优化。损失有两个：二元正确性损失，加上普通的下一个 token 预测损失，论文说两个一起用效果更好。

测试时，生成很多解答，用验证器打分，选分最高的作为最终答案。他们做了消融实验：标签可以按句子打（每句话结束后判断这一步是否正确），也可以按 token 打（相当于很嘈杂的标签，要求每个 token 都沿着通向正确答案的方向）。最终整个解答的分数取最后一个 token 的预测。论文里有可视化：绿色表示验证器打高分，红色表示低分。一个正确解答中间有些低分，但越到后面越绿，最后是绿色；另一个解答开头不错，但接近末尾出了错，最后是红色，和真实结果一致。

几个结果：

  • 和直接监督微调相比，60 亿参数和 1750 亿参数（GPT-3）的模型上，验证器方法更好，尤其是验证器的训练集变大以后；训练集小时（比如 175B 模型上不到一千道题），验证帮助不大。学生问如果数据非常多，两者会不会趋同，她说可能会，但验证器的好处是不用改动基础模型，生成模型保持通用，再用验证器去引导它。
  • 大生成器配小验证器，比小生成器配大验证器效果更好。这在某种程度上符合直觉：平均来说生成比验证难。生成器和验证器的最佳规模比例是一个很好的研究问题，尤其现在基础模型强了很多，Hugging Face 上也有很多验证器和奖励模型的排行榜可以试。
  • 每道题的解答数增加到 400 左右时验证器收益很大，再往上反而下降，800 个时验证器就分不清好坏了。上一讲的多数投票在 10 到 50 个样本后就失效，这里能用到 400。学生问为什么会下降而不是持平，她说这里报告的是整个系统的输出（验证器从 800 个解答里挑分最高的，再和标准答案比），样本多了，可能有两个很接近、一对一错的解答，验证器区分不开。论文实际用的是 100 个样本，那里已经拿到了大部分收益。

三、逐步验证：过程奖励模型（OpenAI，《Let's Verify Step by Step》）

不到两年后 OpenAI 的另一篇论文。问题仍然是幻觉：一步一步解题时，开头一步错，整个答案就可能偏离。论文比较两种奖励模型：结果奖励模型（ORM）对整个解答给一个奖励，看的是整个解答是否正确；过程奖励模型（PRM）对每一步给不同的奖励。

训练数据的差别：生成器对一道题给出一个多步的解答；ORM 只需要和标准答案比对最终结果就有了标签；PRM 则请人工标注员逐步检查模型生成的每一步，给出对、错或中性的标签。整个解答的分数取各步正确概率的乘积；拿到分数后可以决定输出这个答案还是重试。这就是过程监督，它对"功劳"的分配更准确。

她特别强调一点：过程监督能更好地处理"假阳性"。模型会以出人意料的方式产生幻觉，可能推理过程是错的，却碰巧得到了正确的最终答案；过程监督看每一步，不太容易落入这种情况。它也鼓励可解释的、人认可的推理过程，因为标签是人给的。

论文发布了开源数据集 PRM800K，包含 80 万个步骤级标签。他们用一个技巧提高标注效率：优先把"有说服力的错误解答"（最终答案对、但中间步骤有错的样本）交给人标注，比随机挑样本的数据效率高 2.6 倍；并且迭代进行：先有一个很简单的 PRM（甚至可以直接让大模型判断某一步），收集数据、训练 PRM、再提高数据质量。举例：一个分数的分母比分子的 3 倍少 7，这个分数等于 2/5，求分子。前五步都被标为正确，最后一步模型算错了，被标为错误。

他们以 GPT-4 为基础模型，先在这个数据集上做监督微调，再分别训练 ORM 和 PRM；ORM 的分数取最后一个 token，PRM 取各步概率的乘积。结果：

  • PRM 优于 ORM 和多数投票。多数投票在大约 100 个样本后失效，PRM 在单题正确率低于 5% 的难题上也能找出稀少的正确解答。
  • PRM 的数据效率更高：两者都随标签增多而变好，但 PRM 用少得多的标签就能达到同样效果，比如 ORM 每题 100 个标注解答，大致相当于 PRM 每题一个。
  • 泛化：在新领域、新数据集上，多数投票反而比 ORM 好，但 PRM 整体上比多数投票更好，能容忍更大的分布变化。这是训练验证器和奖励模型时都应追求的性质。

学生问 PRM 会不会有害，比如某一步看起来不错但对最终答案没贡献。她说较新的方法往往把 PRM 和 ORM 结合起来，取两者之长；而且 PRM 的阈值是一个新增的超参数，要调。还有学生问，如果推理直接写"设分子为 x，所以 x = 14"，跳过中间步骤，PRM 能防住这种取巧吗？她说这里没有改动生成器，总可以提示生成器一步步推理再让验证器打分；如果用 PRM 来训练生成器，就要小心模型不再推理、只生成 PRM 喜欢的最终答案。这里的标签是人给的，跳过推理的步骤人多半会判为不好，下一篇论文讲的就是不用人工标签的情况。

四、Math-Shepherd：不用人工标注的过程奖励

PRM 比 ORM 更有潜力，但需要大量很难收集的数据。Math-Shepherd 想把步骤标签的收集自动化，并把奖励模型放进生成器的强化学习优化循环。

它把一个推理步骤的质量定义为"这一步通向正确最终答案的潜力"：从这一步出发，采样 $n$ 个后续补全，看最终有多少答对。

  • 硬估计：$n$ 个补全中只要有一个得到正确答案，这一步就标为成功。
  • 软估计：取得到正确答案的补全所占的比例。

比如从某一步出发采样 3 个补全，其中 2 个答对，硬估计为 1，软估计为 2/3。这样就用更多采样代替了人工标注，前提是有题目的最终答案。

她请大家指出这种方法的缺点。学生提到：如果一条不常见的路线才是解题的唯一途径，只采 3 个可能碰不到，这一步就会被打 0 分，也许需要 $n=100$ 才能看到；难题上很多样本都错，得不到信号；中间步骤有错但碰巧得到正确答案时，这些步骤仍会被标为正确，样本多一些也许能在别的轨迹里暴露错误，但不保证。

用法有两种：验证时，采样候选解答，用 PRM 打分，选分最高的；训练时，把 PRM 当作奖励模型，用强化学习鼓励模型生成 PRM 打分更高的步骤。结果：随着 $n$ 增大，软估计的损失表现更好，但在 $n=4$ 时就达到最好结果，硬软差别不大，最后用了更容易计算的硬估计。和自一致性（也就是多数投票）、ORM 比，Math-Shepherd 更好，而且完全没有人工标注；它还超过了用 PRM800K 训练的方法，在更难的 MATH 上优势更大；在 Llama 70B、LLemma 34B、DeepSeek 67B 等模型上都成立。用它的 PRM 做强化学习（PPO）训练生成器，也比只用 ORM 做强化学习更好，提升幅度比单纯的推理时扩展略小，但这是模型自我改进的另一种方式：用模型自己生成标注，训练 PRM，再用 PRM 在测试时和强化学习微调中改进生成器。强化学习之后再加验证还能更好，但优化到一定程度会进入平台期。

学生问能不能设计鼓励自我纠错的 PRM，因为只奖励每一步正确，未必能鼓励纠错。她说可以，比如为数据集设计评分细则，让模型按细则检查每一步，作为额外信号；或者让模型用工具，比如计算器，前面那道分数题用计算器就不会算错。工具和 Agent 式的推理时扩展可以改进验证过程。另一位学生问固定算力下，采样预算在生成器和验证器之间怎样分配，她说这是可以研究的问题；比较 ORM 和 PRM 时最好用同样的数据训练，否则不好比，训练数据非常重要。

五、Weaver：用弱验证器缩小生成—验证差距（Stanford，2025）

这是几个月前发表的 Stanford 论文。动机仍是生成—验证差距，但做法不同：不训练新的验证器，而是看能否用推理时算力，具体说是一组验证器的集成，来缩小差距。"弱"不是故意挑差的验证器，而是现有最好的验证器也都不完美：它们和真实标签相关，但有缺陷。验证器除了 PRM 和 ORM，还有"大模型当评委"：给它一个回答，直接问它是否正确，或者让它用工具和评分细则打分。

先看简单的集成：把不同实验室在不同数据上训练的验证器（都是输入查询、输出分数的语言模型）放在一起。在四个数据集上，按排行榜质量取前 1、前 5、前 10 个验证器，直接平均就有提升，但并不单调。始终有帮助的是给集成成员分配权重：如果有标签，可以用朴素贝叶斯或逻辑回归给每个验证器学一个权重。比如在 MATH-500 上用一部分有标签的数据学权重，再用在新的测试数据上，提升很大。

Weaver 的做法：

  1. 把各个验证器的输出归一化到同一尺度，并过滤掉质量差的验证器。即使只有很少的标签，也能看出哪些验证器差到应该剔除，她说这一步非常重要，验证器要达到一定质量才能进入集成。
  2. 用弱监督，只靠很少的有标签数据估计每个验证器的准确度，再据此组合各验证器的结果给出分数。这受 Stanford 的 Snorkel（Alex Ratner 等人）等弱监督工作启发：把很多弱信号组合成一个强信号。

设定是：$n$ 个查询，每个生成 $k$ 个解答，有 $m$ 个验证器，共 $n\times k\times m$ 个标签，目标是估计"查询 $i$ 的第 $j$ 个样本正确"的概率。关键假设是每个验证器捕捉正确性的一个独立方面：如果所有验证器给出同样的分数，就学不到新东西，信号来自验证器之间的相同与不同。在这个独立性假设下，结合基本的概率关系，可以写出一个优化问题，求出每个验证器的权重。和朴素集成相比，在 GPQA Diamond、MATH、MMLU-Pro 这些较难的问题上提升更明显。

扩展验证的算力有多种方式：多采样（10 个变成 100、1000 个），用更大的模型做生成和验证，增加验证器的数量。她比较了几种方法：pass@k 神谕（有完美选择器时的上限）；有监督（假设有大量标签学权重）；Weaver 的无监督设定（每个数据集只用 1% 的训练标签）；朴素集成（过滤后直接平均）。这些方法都明显好于多数投票和多 Agent 验证（MAV，提示多个大模型从不同方面给回答打分，相当于基本的评分细则，两种情况下都没有比多数投票好，甚至更差）。在这些难题上，准确率可以从 40% 出头提高到 70% 以上。

这还能缩小不同规模模型之间的差距。用 Llama 3.1 8B Instruct 做生成器，配 80 亿参数及以下的验证器集成，在这些数据集上平均约 70%，几乎相当于 700 亿参数级模型做多数投票的准确率；同样的做法用在 70B 级模型上，平均准确率 86.2%，和闭源的 o3-mini 相当，一般也高于其他同级模型。她提醒，这里说的是整个系统的最终准确率，不是覆盖率。

集成的问题是每个解答都要跑一大堆模型再平均，样本多了成本很高。所以她们训练一次 Weaver 后，把它蒸馏成一个小得多的模型，大约 4 亿参数（原来的验证器是 700 亿参数量级），能保留大型验证器集成约 97% 的准确率，测试时算力减少约 99%。原版和蒸馏版都已开源，可以用在 Agent 或推理时扩展的项目里。按总推理算力比较成功率，蒸馏版效率高得多；原版 Weaver 因为能达到更高的准确率，在那些准确率水平上也比朴素集成和多数投票更省算力。

六、小结和问答

  • 验证能同时在训练和推理时提升结果质量。
  • 过程奖励总体上比结果奖励更有效，但可能需要两者结合才能得到最好结果。
  • Math-Shepherd 表明，扩大验证器需要大量数据，数据越多越有效，还可以在强化学习中用来提高生成器的质量。
  • Weaver 换了个思路：对一组验证器做弱监督优化，也就是用更多验证器来做推理时扩展，再蒸馏到小得多的模型里，保留大部分质量。

学生问除了数学推理，编程等领域能不能做验证。她说编程是验证很有意思的领域，后面会讲 CodeMonkeys：不直接训练验证器，而是让模型生成单元测试，用这些测试当验证器。这类验证对任何推理任务都应该有用。

推理模型还需要这种生成—验证吗？她说推理模型的训练很大程度上就是生成推理步骤、用奖励做强化学习循环、得到正确的轨迹，再拿这些轨迹训练下一轮，推理时扩展本身就被用来生成训练数据；但它们仍能受益，因为多采样可以探索解空间的不同部分。将来会不会只在训练时用反复采样造数据，测试时只问一次？她说这是想去的方向，希望模型第一次就做对，更高效；难点在于把模型训练得过于"确定"（对数概率过于集中），可能会损失解答的创造性和多样性，而我们恰恰喜欢有创造性、思路多样的模型。

生成器和验证器的架构是否要很不同？她说这是好的研究问题。一般来说模型更认可自己的生成和自己的理解方式；后面会讲一篇论文，说明某些模型能从不同类型的验证器中受益，但她不知道有研究专门比较同一家族、同样规模与不同家族、不同规模的验证器对模型行为的影响。
