第二讲：推理时扩展

反复采样的覆盖率为什么符合幂律，哪些领域有现成的验证器，生成—验证差距，并行采样和串行修改怎样组合，结果奖励模型和过程奖励模型，以及用架构搜索组合推理时技术的 Archon

主讲：Azalia Mirhoseini
资料来源：课堂录像（Stanford Online 公开，本文依据录像字幕整理）

一、三个阶段和反复采样

大模型开发有三个阶段。预训练历来最耗时，可能要几个月、用大量 GPU，数据量以万亿 token 计；微调历来算力需求小得多，数据少几个数量级；推理阶段是使用模型的时候。这一讲讲的是：在推理时，不改参数、不做微调，怎样让模型更好用。

先回顾上一讲的 Large Language Monkeys：同一道题不只问一次，而是反复问 10 次、100 次，再用一个验证器挑出正确的回答作为系统输出。这样能让较弱的模型（比如 Llama 3 8B，单次不如 GPT-4o）在很难的数学、编程、问答题上超过更大的闭源模型。小模型似乎已经知道这些难题的答案，只是第一次没说出来，反复采样把答案"引"了出来。

这在目前试过的几乎所有领域都有效，包括 SWE-bench 这样模拟软件工程师改代码、提交补丁的 Agent 基准。横轴是采样次数（1 到 1000），纵轴是覆盖率（至少一个样本解出的题目比例），DeepSeek 的模型（她记得是 DeepSeek-V3）采样 1000 次后，能比 Claude 3.5、o1-preview 解出更多题。有意思的是，编程题如果有单元测试可以挑出正确的样本，就得到了一个端到端自动化的方法，从开源模型造出更强的系统。

二、推理时的缩放规律

预训练有缩放规律：按论文里的公式，增加数据、算力、参数量，可以可预测地降低测试损失。她们发现推理时算力也有类似的规律：覆盖率 $c$ 和并行采样次数 $k$ 之间的关系符合一种"指数化幂律"，大致是

$$\log c \approx a\,k^{b}$$

其中 $a$、$b$ 是拟合出来的系数。在 Llama 3 8B、70B，以及 Gemma、Pythia 等从 7000 万到 700 亿参数的一系列模型上，拟合曲线和实际覆盖率在大多数情况下非常吻合。这意味着可以预测要达到某个覆盖率需要多少样本、该分配多少资源。连 7000 万参数的小模型也有这种规律，跨领域也成立。

为什么会是幂律？乍看有点反直觉。对单道题 $i$，如果单次答对的概率是 $p_i$，那么 $k$ 次里至少答对一次的概率是

$$\text{pass@}k_i = 1-(1-p_i)^k$$

$(1-p_i)^k$ 是 $k$ 次全错的概率，1 减去它就是至少对一次。单道题是指数形式，但整个题集上观察到的是幂律。她们分析发现，出现这种幂律的充要条件是：存在一条由很难的题组成的长尾。实际统计也是如此：大部分题比较简单，单次就能答对；随着题目变难、单次正确率越来越低，有一长串难题，正是这种分布造成了整体的幂律。

这对大模型的工程意味着：过去公司在预训练上花几亿甚至几十亿美元，微调花得少得多，每次推理几乎不花什么，因为只是用户和模型一来一回；现在有了新范式，可以在推理上花多得多的算力来提高能力，而且可以离线进行，让 Agent 去解一个问题，一直生成 token，不断提高答案质量。

三、验证器和生成—验证差距

反复采样需要自动验证，否则不知道哪个样本是对的。有些领域验证更容易：

  • 某些数学题可以用形式化证明，用证明工具检查每一步是否正确。
  • 编程可以写单元测试，而写单元测试往往比写整个程序简单得多，可以由人来写。
  • "AI 当编译器"：她实验室的一个方向，用大模型把 PyTorch 这样的源代码生成为 CUDA 这样更底层、针对 GPU 优化的代码。这天然可验证：对任意输入，比较 CUDA 和原 PyTorch 的输出是否一致就行。在她们做的 CUDA 生成基准 KernelBench 上，覆盖率也随采样次数稳定提升。
  • 任何两种语言之间的翻译，比如把 Python 或 C++ 移植到 Java，都可以较容易地检验是否等价。

没有验证器的领域，"N 选一"的方法（多数投票、基于模型的排序器）和模型真实覆盖率之间有很大差距。多数投票就是选生成结果里出现次数最多的那个答案。实验中，覆盖率（假设有完美的选择器）一直上升，而多数投票在 10 到 50 个样本后就停滞了；题越难，差距越大，比如更难的 MATH 数据集上比 GSM8K 上差距更明显。用奖励模型给每个答案打分再挑最高的（奖励模型是训练来给回答质量打分的大模型，下一讲细讲），或者把两者结合，差距仍然很大。这就是"生成—验证差距"：模型能生成很多好回答，但验证决定了我们能抓住其中多少。

多数投票不行的原因是：最难的题，在一千或一万个样本里可能只被解对一两次、三次，这么稀少的正确答案，投票自然选不出来。GSM8K 简单一些，很多题投票是管用的，但最难的那些题正确答案出现的频率仍然很低，这让验证很难。

课堂讨论

她让大家讨论几分钟。学生的想法有：多采样很有用，但验证器的质量非常关键；先让模型在领域里自由探索、积累洞见，再做并行采样，可能得到更好的 pass@k 趋势（她说后面会讲搜索、工具使用等超越反复采样的方法）；有些难题判断对很难，但判断错容易，可以先剔除错误答案，或者用仿真等工具、另一个模型来过滤。她说一万个样本的数据都在 Hugging Face 上，研究怎样缩小生成—验证差距可以是一个好的课程项目。有学生问能不能生成一万个验证器再投票，她说这很有意思但算力成本高，下一讲会讲她们用弱监督方式集成十几二十个验证器的工作。有学生问覆盖率会不会被不完整的测试用例虚高，她说数学题她们人工检查过，正确率大约在九成以上；但如果单元测试没有真正覆盖代码，这确实是一种失败模式，验证器的质量很重要。

四、并行与串行，结果奖励与过程奖励

接着讲《Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters》这篇论文中和推理时扩展最相关的部分。

生成方式有两种：并行采样，对同一个问题生成多个答案；串行修改，模型先给出初始思路，然后不断修改、补充，从不同角度检查，直到有把握再输出。学生问修改是靠我们自己提示还是模型系统自带的，她说这里假设是靠提示，但推理模型已经被训练出了这种行为，有时会自己修改答案。

选答案的方式也有不同：

  • 结果奖励模型（ORM）：看最终答案，给出一个分数。它是训练来按输出给奖励的，到了新领域准确性可能有限。
  • 过程奖励模型（PRM）：给解答的每一步打分。比如一道数学题有五步，PRM 对每一步给分。

N 选一加验证器很简单：并行生成，用 ORM 选分最高的。也可以把奖励模型放进搜索过程：假设每一层有 4 个样本的预算，采样 4 个，用 PRM 打分，选分最高的 2 个，从它们继续采样，一层层展开，这就是用 PRM 引导的束搜索。学生问 PRM 是不是语言模型，她说一般也是从语言模型微调来的，在同领域任务上效果更好，如果要优化某个基准，用那个任务的一部分训练 PRM 会比跨任务好，但因为基于语言模型，也有一定泛化。PRM 是按 token 打分吗？不是，是按"步"，比如一个有意义的推理片段或一句话，一种做法是让人标注每一步是好是坏，再训练模型，后面几讲会讲。

直觉上，把 ORM、并行 N 选一和串行修改结合会更好，这方面还有很多未知。一种简单的组合是：不做一个并行样本加修改，而是做两个，每个都串行修改，用 PRM 引导每一步修改，最后用 PRM 或 ORM 从两个最终答案里挑一个。现在有很多现成的 PRM，可以找和自己任务最相关的来引导搜索，也可以用自己的数据训练 PRM 和 ORM。

论文用 MATH 数据集（约 1.2 万道训练题、500 道测试题）和 PaLM 模型做实验。他们按模型在每道题上的单次正确率定义"难度"，分成五档，以此分析哪种扩展方式对难题、易题更有效；还训练了自己的 PRM，并微调了一个专门做修改的模型。她说现在基本上任何经过指令微调的模型，只要你提示它，都能做修改。几个观察：

  • 随着生成预算增加，多数投票、ORM、PRM 和精心混合各种方式的准确率各不相同，怎样混合并行和串行来优化推理时扩展仍是开放问题，目标是对每个准确率，用最少的生成预算达到。
  • 容易的题，串行比例高（修改多、并行少）的配置准确率最高；最难的几档题，最优比例很难说，甚至第四档和第五档之间都不一样。
  • 对容易和中等难度的题，增加推理时算力可能比扩大预训练更划算；但对最难的题，更大、预训练更多的模型仍然更好。她说她们实验室内外的很多研究也看到这一点：开源模型、小模型加上更多推理时算力越来越有用，但最难的题仍然是前沿模型做得更好，即使推理预算很大。

学生指出预训练只做一次，推理每次都要花。她说是的，但这个观察回答的是"有了推理时扩展，是不是不用再预训练了"：不是，预训练仍然有用；而且不是谁都能预训练大模型，所以很多问题能靠推理时扩展解决，这本身很有意义。为什么难题上大模型更好？能不能把小模型微调成难题专家？当然可以针对某类题微调，但这里比较的是通用数据、通用训练配方下的情况。

第二轮讨论中，有学生说树搜索混合了并行和串行，她说总体感觉是两者结合更好，用 PRM 在每一层剪掉不太有希望的分支就是这样。还有学生说，易题通往正确答案的路径多，随便一条都可能走通，不太需要并行探索；难题路径少，需要大量并行才能找到一条；也可以在思维链的每一步都做验证、剪掉不对的分支。她说这是很直观的理解。

五、Archon：把推理时技术当作架构来搜索

可以把生成的 token 数看作一个提高回答质量的旋钮，问题是怎样分配它、怎样从模型中引出好的生成。Archon（这门课的一位助教是作者之一）把推理时扩展看成一个"推理架构设计"问题：输入是要优化的目标基准、推理调用预算、可用的一组大模型（可以混用不同模型）以及一组推理时技术；优化器 ITAS（推理时架构搜索）决定怎样把不同模型和技术组合起来，在给定预算下得到最好的结果；输出就是这个组合架构。

推理时操作有：

  • 生成：从模型采样，生成 $n$ 个回答，相当于反复采样。
  • 融合：给模型原问题和 $k$ 个回答，让它综合出一个最终回答。她说这个方法出奇地有效，模型在知道所有可能答法的情况下生成答案，属于"并行之后串行更新"。
  • 评论：让模型指出某个回答的优缺点。
  • 排序：让模型按质量给上一步的回答排序。
  • 验证：返回回答，同时说明为什么这样打分。
  • 单元测试生成和评估：让模型为编程、数学等推理任务生成单元测试；评估更"疯狂"，不是真去运行测试，而是让模型判断某个回答能否通过某个测试。比如题目是检查字符串里的圆括号是否配对，模型可能生成的测试有"括号数为奇数时应输出 no""遇到右括号时必须匹配最近一个未匹配的左括号"，还可以让它生成测试代码。

以上都是靠提示实现的，没有专门训练模型做这些。在一个问答推理基准上的胜率比较：随机选一个回答最差；让模型排序选第一好一些；"神谕选择"（假设有完美验证器，从生成结果中挑最好的，但不混合）更好；用融合把 5 个回答综合成一个，竟然比神谕选择还好；先选出前几名再融合，效果最好。换成多个不同模型各生成一个回答（按模型由好到差依次加入集成），随机选择会变差（因为加入了较弱的模型），但几种方法的先后顺序不变。

ITAS 找到的架构是分层的：第一层由不同模型生成，然后评论、排序，再由多个融合器各自融合，接着继续评论、排序。编程题上的一个优化架构是：生成大量样本，生成单元测试，再评估。她们发现，像深度学习里加层一样，叠加更多推理时技术层确实提高准确率：比如用多个模型集成、三层评论和融合、最后一层融合的架构，在很多任务上明显好于最好的模型只用一次，也好于最好模型采样 8 次加一层融合。

搜索很贵，要跑大量推理调用，所以她们缩小了搜索空间：离线发现"生成、评论、排序、融合"这个顺序效果好；每层只用一种技术；第一层总是生成；评论必须在排序和融合之前；单元测试生成之后必须跟评估。用一个留出的训练集，以"每个推理预算下的准确率"为目标，用贝叶斯优化来搜索，有很多好的开源工具。它比贪心搜索和随机选择更省样本。Archon 最后只输出一个回答，也就是优化的是 pass@1。结果：只用开源模型，就能在很多任务上大幅追平或超过当时的前沿闭源模型；既可以针对单个任务优化，也可以做成通用的，通用版本也表现很好，在指令遵循、推理、数学和编程任务上，pass@1 平均比 GPT-4o 和 Claude 3.5 Sonnet 高 14.1%。这说明设计出来的推理时架构可以推广到训练时没见过的任务。
