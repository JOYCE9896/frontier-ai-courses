02. Katelyn Lesse（Anthropic，Claude Developer Platform 工程负责人）：为 Agent 演进 Claude 的 API 平台

直播位置 0:06:51–0:20:30 · 英文原题 Evolving Claude APIs for Agents

她带领 Anthropic 的 Claude Developer Platform 团队。她说团队最喜欢服务那些“抬高智能上限”的开发者，也就是总想从模型里榨出最好表现的人。整场她用 Claude Code（Anthropic 自己的编程 Agent 产品）做例子，说明平台怎样从三个方向帮开发者拿到最好的效果。

一、把 Claude 学会的能力暴露成 API 功能

  • 扩展思考（Extended Thinking）：Claude 在很多任务上的表现随推理时间增长。API 让你决定是让它多想还是快速回答，还可以设一个思考 token 预算。Claude Code 用这个功能来判断：调试复杂系统时多想，简单问题快答。
  • 工具调用（Tool Use）：Agent 让模型调用外部函数的机制。平台提供内置工具（比如网页搜索），也允许你自定义工具，只要给出名称、描述和输入 schema。Claude Code 有大量工具，一直在调用它们读文件、搜文件、写文件、重跑测试。

二、管理上下文窗口

上下文窗口（Context Window）是模型一次能看到的全部输入。她说在正确的时间把正确的内容放进窗口，是提升表现最重要的事之一。编程 Agent 的窗口里同时可能有技术设计、整个代码库、指令和工具调用结果，管理起来很复杂。平台给了三类工具：

  • MCP（Model Context Protocol）：一年前 Anthropic 推出的开放协议，让 Agent 用统一方式连接外部系统。对 Claude Code 来说，GitHub、Sentry 这类窗口之外的信息和工具，都可以通过 MCP 接进来。
  • 记忆工具（Memory Tool）：第一版是一个客户端文件系统，数据由你掌控。Claude 会判断哪些信息值得存起来以后用，需要时再拉回窗口，比如代码库的模式、你的 Git 工作流偏好。
  • 上下文编辑（Context Editing）：第一版只做一件事，清掉旧的工具调用结果。工具结果往往很大，而且过去的结果对后面的回答帮助不大。Claude Code 一个会话里会调用几百次工具，读过的文件都占着窗口。

她给出的数据是：记忆工具和上下文编辑一起用，在 Anthropic 内部评测上比基线提升了 39%。部分模型现在支持 100 万 token 的上下文窗口，团队也在训练 Claude 感知自己的窗口还剩多少空间，并据此调整行为。

三、给 Claude 一台电脑，让它自己干活

现在业界在争论 Agent Harness（包在模型外面、负责调用模型、执行工具、管理循环的那层程序）应该做得多重、多有主见。她的看法是：Claude 会写代码，如果它也能运行这些代码，就能完成任何事。难点在于基础设施和领域知识。

她讲了 Claude Code 网页版和手机版上线的故事。本地运行时 Claude Code 用的是你的电脑；在网页或手机上开一个会话然后走开，它在哪里运行？团队要解决三个难题：一个让 Claude 安全地写和运行未经你批准的代码的环境、大规模容器编排、会话持久化（很多人开了一堆会话就走了，回来时结果必须都在）。

  • 代码执行工具（Code Execution Tool）：让 Claude 在 Anthropic 服务器上的安全沙箱里写代码并运行，容器和安全由平台负责。
  • Agent Skills：一个 Skill 就是一个文件夹，里面放脚本、指令和资源。Claude 根据你的请求和 Skill 的描述，自己决定什么时候把它加载进上下文并在沙箱里运行。她说 MCP 提供工具和上下文，Skill 提供使用这些工具和上下文的专业知识。例子是做落地页：Claude 知道这时该加载“网页设计”Skill，按你的设计系统来做。她提到第二天 Barry 和 Mahesh 会专门讲 Skills。

收尾时她重申三个方向会继续推进：模型有了新能力就在 API 里暴露出来；在记忆和上下文上给更多工具，让 Claude 决定拉进什么、存什么、清掉什么；继续投入 Agent 基础设施，也就是编排、安全环境和沙箱。

03. Michele Catasta（Replit，President 兼 AI 负责人）：自主性就是一切

直播位置 0:20:32–0:44:40 · 英文原题 Autonomy Is All You Need

Replit 做的是面向非技术用户的编程 Agent。他说这和场内大多数人面对的问题不一样，而自从 2024 年 9 月发布第一版 Replit Agent 以来，自主性一直是他们追的北极星。

自主性的第三个维度

他从 swyx 几周前发布的一张图讲起：一端是低延迟、人一直在环的交互，适合专家做深度工作；另一端是可以完全委派、几小时后回来看结果的 Agent；中间是一个尴尬的“死亡谷”，Agent 不够自主、没法放手，又跑得太久、让人跟不上节奏。他说包括 Replit 在内很多公司曾经在这个谷里待了几个月，现在已经有了能连续跑几个小时的 Agent。

他想补上图里没有的第三个维度：怎样为非技术用户做自主 Agent。他用自动驾驶打比方：Tesla FSD 是“有监督的自主”，你还得有驾照、坐在方向盘前处理长尾情况，今天多数编程 Agent 也要求用户懂技术；Replit 追求的是 Waymo 那样的体验，用户坐后排，不碰方向盘，也不需要驾照。原因是他们想让每个知识工作者都能做软件，而这些人没法替 Agent 做技术决策。

他回顾了 Agent 的几代：先是补全和辅助，然后是基于 ReAct（让模型交替“推理”和“行动”的提示范式）的第一代 Agent，然后是原生工具调用，再到他所说的“自主”一代，突破了一小时的自主运行，在长任务上保持连贯。这几代正好对应 Replit Agent 过去一年的版本，几个月前发布的 Agent 3 属于最后一代。

重新定义自主性

他说大家常把自主性和“跑很久”混为一谈，好像用户因此失去控制。他的定义是：Agent 包揽全部技术决策，但任务范围可以很窄。范围宽，Agent 就会跑几个小时；范围窄，它既自主又快。用户保留对“做什么”的控制，Agent 负责“怎么做”。所以运行时长不应该被当成炫耀的指标。他提出的目标是最大化“可约运行时间”：用户不必做任何技术决策、Agent 独立推进的那段时间。

他认为自主性有三根支柱：前沿模型的能力（留给模型公司）、验证、上下文管理。

支柱一：验证

没有测试，Agent 会造出很多“画上去的门”（painted doors）：看起来有按钮，点了没反应；页面上的数据其实是写死的假数据。Replit 内部评测发现，Agent 第一次做出来的单个功能里超过 30% 是坏的，这意味着几乎每个应用至少有一个坏功能。用户不会去点每个按钮，发现后会很震惊，这也是非技术用户不信任编程 Agent 的原因之一。

非技术用户给不出技术反馈，顶多做点手工 QA，而第一版产品上线后他们发现用户根本不愿意做测试。于是 Replit 转向自主测试。它解决三件事：打破对人工反馈的依赖；防止小错误在构建过程中不断累积；对付前沿模型的“偷懒”，也就是模型声称完成了但其实没有。

他列出了代码验证的光谱：LSP 静态分析、执行代码、生成并运行单元测试（只能测函数级正确性）、API 测试（只能测接口）、再到基于浏览器的测试。浏览器测试又分两类：Computer Use（模型看截图、像人一样操作界面，又贵又慢）和 Browser Use（通过 DOM 抽象来操作浏览器）。Replit 的做法是把这些混在一起：生成便于测试的应用，测试 Agent 大多数时候以编程方式和应用交互，查数据库、读日志、调 API、点页面，实在不行再退回截图。

技术细节上，常见的工具式浏览器 Agent 只暴露几个通用工具（开标签页、点击、填表单），难以覆盖长尾交互。Replit 让模型直接写 Playwright 代码。他说 LLM 很擅长写 Playwright，表达力是工具式方案的超集，而且写好的测试脚本可以反复运行，自然形成回归测试集。整体比 Computer Use 便宜、快一个数量级。

支柱二：上下文管理

他的观点是长任务不需要超长上下文模型。按他们的经验，大多数任务，包括很有野心的任务，都能在 20 万 token 内完成。办法是不把所有状态塞进窗口：让 Agent 边写代码边写文档，把计划和任务列表存在文件系统里，把记忆写进文件、需要时再读回来（他说这是 Anthropic 一直在推的做法）。他提到 Anthropic 发布 Claude Sonnet 4.5 时说它能专注运行 30 多个小时，OpenAI 在数学题上也有类似结果。

他认为让 Agent 跑得久的关键是子 Agent 编排。子 Agent 从一个全新的空白上下文启动，由开发者决定注入哪部分上下文，跑完只把结果返回主循环，这和软件工程里的“关注点分离”是一回事。他展示了 Replit 生产环境的数据：上线新的子 Agent 编排后，每次上下文压缩（Compaction）之间能容纳的记忆数从大约 35 升到 45 到 50，压缩频率降低了。

对测试来说，子 Agent 几乎是必需的。他们早期在主循环里既写代码又做浏览器操作，把浏览器观察结果塞回主循环，动作种类太杂，主循环会被搞糊涂。后来整个架构迁到子 Agent 上：主循环决定该验证了，就开一个子 Agent 做测试，测完丢掉它的上下文，只把最后的观察返回主循环。

下一步：并行

他认为并行的价值主要在用户体验。Agent 能自主跑很久，代价是用户脱离了状态：写一个长提示，去吃午饭，回来祈祷它做完了。并行 Agent 用更多算力换时间，但有两个成本：多个上下文窗口里大约 80% 的内容是重复的；最后要解决合并冲突，而他的用户连合并冲突是什么都不知道。

他列出并行带来的好处：测试可以和写代码同时进行（测试再怎么优化也慢）；可以有异步进程往主循环里注入有用信息；预算够的话可以同时采样多条轨迹提升效果。目前业界的做法是“用户当编排者”，任务怎么拆、怎么合并都在用户脑子里。Replit 下一版的主要押注是“核心循环当编排者”：由 Agent 自己即时拆分任务、决定并行，用软件工程里已有的技巧安排子任务，尽量让它们不互相踩脚，他承认合并冲突没法百分之百避免。

04. Lisa Orr（Zapier，工程负责人）：让客服团队也能提交代码

直播位置 0:44:46–1:00:20 · 英文原题 Your Support Team Should Ship Code

她刚结束 18 天、200 多英里的科罗拉多大峡谷漂流，没网没信号，下船才知道要来做这场演讲。她用峡谷的“侵蚀”来比喻 Zapier 的问题：Zapier 有 8,000 多个建立在第三方 API 上的集成，有的已经 14 年了，第三方 API 一直在变化和废弃，造成可靠性问题。她管这叫“应用侵蚀”（app erosion）。客服团队处在第一线，工单积压严重，导致集成不稳定、客户体验差，甚至客户流失。

两个并行的实验

实验一是两年前开始的：让客服不只分诊，还直接修 bug。理由是应用侵蚀是从客服流到工程的主要 bug 来源，客服很多人想转工程，而且有些人已经在非正式地维护应用。护栏是：只针对 4 个目标应用，客服提的合并请求都由工程审核，只做应用修复。

实验二由她领导，叫 Scout：能不能用代码生成更快地解决应用侵蚀。团队先做调研，她自己修过应用 bug，也跟着工程师和客服观察整个修复流程。最大的发现是收集上下文花的时间太多：第三方 API 文档、网上别人有没有遇到过、内部日志，要找要读的东西太多。

从一堆 API 到 Scout Agent

第一阶段他们做了很多 API，有的用 LLM（比如“诊断”工具，替人收集和整理上下文并给出诊断），有的不用（比如测试用例查找器，就是一个搜索查询）。还做了一个叫 Autocode 的网页 playground，请大家来试。问题是这些 API 没有嵌入工程师的日常流程，“又多一个要打开的窗口”，用的人很少；团队铺得太开；同时 Cursor 上线并在 Zapier 被广泛采用，让他们的一部分工具变得没必要。

唯一的大成功是“诊断”API，客服很喜欢，主动要求团队给 Autocode 做一个 Zapier 集成，把诊断嵌进“从客服问题创建 Jira 工单”的那个 Zap 里。她的结论是：工具要嵌进流程才有人用。

MCP 出现后，他们把这些 API 做成 Scout MCP 工具，工程师在 Cursor 里直接调用，离开 IDE 的次数少了。但仍有问题：诊断工具很有价值但运行很慢，在 IDE 里同步等待很烦；定制需求跟不上，有些工程师转去用 Zapier 自己的 MCP；工具使用很分散，每人只用其中几个。他们的假设是，真正的价值来自把工具串起来，于是做了一个负责编排的 Scout Agent。

Scout Agent 怎么运行

首个用户选的是客服团队，因为他们处理的是刚冒出来的小 bug。流程是：客服提交问题，Scout 先分类，再评估能不能修；能修就生成合并请求。客服第一次打开工单时，上面已经挂着一个 MR。客服审核和测试，不满意就在 GitLab 里直接提修改要求，Scout 再跑一轮，满意后提交给工程审核。

整个流程由 Zap 触发，嵌在客服已有的 Zap 里。先跑诊断，把分类和可修性结果贴到 Jira 工单；可修的话触发 GitLab CI/CD 流水线，分计划、执行、验证三个阶段生成 MR，用到的是 Scout MCP 工具和 Cursor SDK。最新加的功能是客服在 GitLab 里和 Scout 对话提修改，不用把代码拉到本地。

他们评估三个问题：分类对不对，是否真的可修，代码修复是否准确。目前分类和可修性两个评测（Eval）的准确率在 70% 到 75%。处理的工单越多，测试用例越多。

效果

  • 客服团队的应用修复中，40% 由 Scout 生成。

06. Bill Chen 与 Brian Fioca（OpenAI，Applied AI 创业公司团队）：能熬过模型换代的编程 Agent

直播位置 2:01:45–2:19:00 · 英文原题 Future-Proof Coding Agents: Building Reliable Systems That Outlast Model Cycles

两人在 OpenAI 的 Applied AI 创业公司团队，专门帮客户做编程 Agent。Bill 说编程 Agent 值得关注，是因为软件工程可以看作解决问题的通用媒介，它的进展是离 AGI 有多近的信号。问题在于模型更新太快，每出一个新模型大家就得在上面重建 Agent。

编程 Agent 的组成

他说一个编程 Agent 只有三部分：用户界面（CLI、IDE、云端或后台 Agent）、模型（比如前一天刚发布的 GPT-5.1-Codex-Max 或 GPT-5.1 系列）、Harness。最简化地说，Harness 就是一组提示词和工具，放在一个核心 Agent 循环里，负责模型的输入和输出。

Brian 接着讲 Harness 难在哪：

  • 你精心设计的新工具，模型可能在训练中从没见过；就算见过，也要针对这个模型的习惯调提示词，而新模型不断出现。
  • 延迟：模型思考多久，哪些事该提示它别想，思考过程怎么在 UX 里展示，要不要做摘要。
  • 上下文窗口管理和压缩很难。他说刚发布的 Codex Max 自带这项能力，“如果你要自己做，祝你玩得开心”。
  • API 也在变：Completions、Responses，以后还会有别的。

智能加习惯

Brian 的说法是：模型 = 智能 + 习惯。智能是它擅长什么语言、什么框架；习惯是训练中学到的解题方式。OpenAI 训练模型先规划、四处查看收集上下文、想清楚再写代码，最后测试自己的工作。摸清这些习惯就是做好提示工程的方法。

GPT-5 发布时，很多人把给别家模型写的提示词直接搬过来，要求模型“仔细检查每个文件再改代码”。GPT-5 本来就会这样做，再加这种指令，它就格外彻底，花很长时间，效果反而不好。他是直接问模型发现的：“我喜欢你的方案，但你花了太久，我的指令怎么改能让你更快？”模型回答：你让我把所有东西都看一遍，我其实不需要。他说这说明模型和 Harness 一起开发的好处，Codex 就是模型和 Harness 的组合。

Codex 能做什么

Codex 是 VS Code 插件、CLI，也能从 VS Code 插件或手机上的 ChatGPT 调用云端执行，可以从 Slack 调用，也能在 GitHub 上审 PR。Codex 团队的人告诉他，Harness 要做的事比想象的难得多：并行工具调用和线程合并；沙箱、提示转发、权限、端口管理等安全问题；压缩（什么时候触发、什么时候重新注入、怎样兼顾缓存优化）；MCP 的全部接入；图片要压缩到什么分辨率再发给模型。

Bill 把 Codex 称为“终端里的 Computer Use Agent”：在图形界面出现之前，人们本来就是在命令行里写代码、串联工具来操作电脑的。只要任务能用命令行和文件表达，Codex 就能做。他自己用 Codex 整理桌面照片，也可以用它分析一文件夹的 CSV，不一定是编程任务。

把 Codex 嵌进你自己的 Agent

他们从 Cursor、VS Code 等头部客户那里总结的模式是“Harness 成为新的抽象层”：你不用每次换模型就重新优化提示词和工具。Brian 假装问“那不就是套壳吗”，Bill 反驳说这样看太简化了，这种模式让你把精力放在产品差异化上。

  • Codex 有 SDK，可以通过 TypeScript 库调用，可以在 Python 里用 exec 程序化调用，有 GitHub Action（比如自动处理 PR 合并冲突），也能接进 Agents SDK 并给它配上连回你产品的 MCP 连接器。
  • Brian 的演进说法：先有能聊天的机器人，然后给机器人工具，现在可以给它一个能自己造工具的工具。企业软件可以当场为每个客户写出 API 层面的插件连接器，以前这是专业服务团队的活。他为 DevDay 做过一个能修自己 bug 的看板应用。
  • Zed 把 Codex 包了一层，接到 IDE 的界面上，自己专心做最好的编辑器。GitHub 也用 SDK 直接集成了 Codex，还可以把它放进 CI/CD 流水线。
  • 想深度定制也可以。他们和 Cursor 团队合作，让 Cursor 的工具和 Codex 模型（他们自嘲命名不好，模型和 Agent 都叫 Codex）的训练分布对齐，方法是对齐开源的 Codex CLI 实现。代码是公开的，可以 fork。

接下来

Codex 上线还不到一年，是使用量增长最快的模型，每周处理数十万亿 token，比 DevDay 时翻了一倍。他们的建议是朝模型要去的方向构建：模型会变强，能无人监督地做更长的任务，信任上限会提高。未来要面对的是庞大的代码库、非标准库、闭源环境、沿用现有模板和规范，SDK 会跟着这些能力演进，让模型边做边学、不重复犯错。

07. Martin Harrysson 与 Natasha Maniar（McKinsey 合伙人）：告别 Agile 之后是什么

直播位置 2:19:44–2:41:20 · 英文原题 Moving away from Agile: What's Next?

两人来自 McKinsey 的 Software X 业务，主要帮企业客户用 AI 做软件产品。这场讲的是人和运营模式（Operating Model）这一面。Martin 说他快 20 年前入行当初级开发者时，公司正在转向 Agile，开始用看板、站会和各种仪式，那是一次大变化；现在 AI 带来的是又一次范式转变。

个人提效和公司收益之间的落差

场内每个人都能举出 10 个例子说某件事从几天变成几分钟。但他们调研了约 300 家企业，平均整体提升只有 5% 到 15%。他们认为原因是出现了新瓶颈：某些环节快了，人与人的协作方式没变；代码多了，评审还是手工；Carnegie Mellon 的一份研究也指出新代码在放大技术债和复杂度。

两个具体的瓶颈：一是分配工作，AI 在不同任务上效果差别很大，不同人的熟练程度也差别很大，团队负责人很难决定怎么分配；二是评审，交给 Agent 的需求常常是写得很模糊的用户故事和验收标准，回来的代码不对，唯一的控制手段是人工评审，于是自动化了一部分又多出了人工评审。多数大公司仍然是 8 到 10 人的团队、两周一个 Sprint，这是旧范式下的约束。

表现最好的公司有什么不同

Natasha 介绍调研结果。表现最好的企业：

  • 拥有 AI 原生工作流的可能性高 7 倍，标准是在软件开发生命周期中规模化了 4 个以上用例，而不只是在代码评审或写代码上用点工具。
  • 拥有 AI 原生角色的可能性高 6 倍：更小的团队、不同的技能组合、新角色。
  • 投入持续的实操培训、影响度量和激励机制，鼓励开发者和 PM 采用 AI。
  • 结果是上市时间和交付速度提升 5 到 6 倍，产物质量更高、更一致。

她说不同类型的工作适合不同模式。遗留代码现代化需要整个代码库的上下文，产出定义清晰，可以像“Agent 工厂”：人给初始规格、做最终评审。新功能开发更像迭代循环，Agent 作为共创者提供多个选项，加快反馈。AI 原生工作流意味着从季度规划转向持续规划，工作单位从用户故事转向规格驱动开发（Spec-driven Development），PM 和 Agent 一起迭代规格，不再写长篇 PRD。AI 原生角色意味着从“两个披萨团队”变成 3 到 5 人的“一个披萨小组”，不再分 QA、前端、后端，产品构建者具备全栈能力，编排 Agent，理解整体架构；PM 直接用代码做原型。他们的文章里还写了 Cursor 内部是怎么运作的。

一家国际银行的试点

对仍按 Agile 运转的大企业，他们和一家大型国际银行试了几项团队级干预：团队负责人借助 Agent，根据团队速度和交付历史分配 Sprint 任务；和 Agent 共同做多个原型，一起迭代安全和可观测性方面的验收标准，减少下游返工；按工作流重组小组，一组专修小 bug，一组做新项目；Agent 在后台分析跨仓库影响；PM 直接看实时客户反馈来调整优先级，不用等数据科学家。结果是 Agent 使用量增长 60 多倍，与业务优先级挂钩的交付速度提升，代码合并量增加 51%。

Martin 补充角色方面：工程师从执行转向编排，PM 的角色也在变，但约 70% 被调研公司根本没改过角色定义。另一家客户把典型的两个披萨团队改成更小、角色合并的小组，同样人数组成了更多小组，每个小组保持原有产出水平，代码质量持平甚至提升。

规模化靠变革管理

他说变革管理（Change Management）就是同时做对二三十件小事：沟通、激励、培训。一家科技公司起初推出工具后使用量上下波动，加了用户整体影响也没变化，只好重来：重新设定期望（对开发者和 PM 的日常意味着什么），做更多实操培训，可以带自己的代码来，配教练，尤其是头几个 Sprint 形成习惯的阶段，再加上度量系统。另一家客户靠设立代码实验室和新的认证体系推动行为改变。

Natasha 讲度量：表现最差的企业连速度都不测，只有 10% 测生产率。他们帮客户搭的度量体系从投入（工具投资、培训和变革管理的时间）到产出（采用的广度和深度、速度、容量），再到开发者 NPS、代码安全性和质量、韧性（用优先级 bug 的平均解决时间作代理指标），最后到高管关心的经济结果：达到收入目标的时间、高质量功能的溢价、扩大客户数、每个小组的人力成本下降，以及能否把省下的资源再投入新项目。她说这是一个 MECE（互相独立、完全穷尽）的起点框架，代理指标会随工具演进而变化。

最后的建议：现在就开始，这是一场关于人的变化，需要时间；找到适合自己的模式，设定大胆的目标。

08. Yegor Denisov-Blanch（Stanford 研究员）：怎样量化 AI 在软件工程里的 ROI

直播位置 2:41:35–2:57:50 · 英文原题 How to Quantify AI ROI in Software Engineering (Stanford Study / 120k Devs)

他的团队过去两年在研究 AI 对软件工程生产率的影响。数据是时间序列（回看 Git 历史）加横截面（跨多家公司）。主要的度量工具是一个模仿专家评审团的机器学习模型：每个代码提交原本由 10 到 15 位独立专家从实现时间、可维护性、复杂度等方面评估，他们用数百万条这样的评估训练模型来复现专家的判断，这样就能大规模部署；如果有人怀疑，可以自己组一个专家团来对比，相关性很好。

什么在驱动 AI 带来的提升

他们把 46 个用 AI 的团队和 46 个相似但不用 AI 的团队配对，按季度测净生产率提升。截至今年 7 月，中位数约 10%。头部和尾部之间的差距在扩大。他很不严谨地往后外推了一下，说可能出现“富者越富”：早期成功者复利增长，落后者越掉越远。所以管理者必须知道自己现在属于哪一组。

  • Token 用量：每位工程师每月 token 用量（对数坐标）和生产率提升的相关性很弱，R² 约 0.20。约 1,000 万 token 处有个“死亡谷”，用这么多的团队反而比用得少一点的团队表现差。他的结论是使用的质量比使用的量重要。
  • 环境整洁度：他们做了一个实验性的“环境整洁度指数”，综合测试、类型、文档、模块化和代码质量，取值 0 到 1。它和 AI 带来的提升之间 R² 约 0.40，相关性不错。建议投资代码库卫生。

他用一张示意图说明：纵轴是任务中 AI 能完成大部分（绿）、能帮忙（黄）、帮不上（红）的比例，横轴是整洁度。干净的代码放大 AI 收益；不加控制地用 AI 会加速代码库熵增，把整洁度往左推，人得往反方向推；工程师得知道什么时候用 AI、什么时候不用，否则 AI 输出被拒或被大改，工程师失去信任、不再使用，收益进一步塌缩。

AI 工程实践基准

他们做了一个工具，扫描代码库里使用 AI 的痕迹，按活跃工程工作中使用每种模式的比例量化，并用 Git 历史按月回溯。等级分为：0 级不用 AI；1 级个人使用，提示词不共享不版本化；2 级团队使用，共享提示词和规则；3 级 AI 自主完成特定任务；4 级 Agent 编排整个流程。这个工具会开源，在他们的研究门户注册即可使用。对一家公司的分析显示，两个业务部门的工具、许可证、预算完全相同，一个部门约 40% 的工作用了 AI，另一个落后很多。他的结论是：有权限甚至有使用，不代表用法相同，管理者要了解工程师怎么用。

怎么算 ROI

理想情况是看业务结果（收入、净收入留存），但从“给 AI”到“业务结果”之间噪声太多，还有销售执行、宏观环境、产品策略等混杂因素。所以看工程结果，但必须超越“使用量”。他提了三点前提：产品职能要能把增加的产能导向有价值的事，否则是产品问题；工程是实际瓶颈（他说通常是），并用一组平衡的指标和不把指标当武器的文化来防范古德哈特定律；AI 很新，测代理指标总比不测好。

使用量的测法分两种：按权限（谁什么时候拿到工具，做试点组对照或同一团队前后对比，噪声大）和按使用（用编程助手 API 的遥测数据，是金标准）。不同厂商的 API 粒度不同，GitHub Copilot 给的是聚合数据，Cursor 更细。他强调可以用 Git 历史回溯测量，不用现在开始做实验再等 6 个月。

结果指标分主指标和护栏指标。主指标是工程产出，用他们的专家评审模型测，不是代码行数、不是 PR 数、也不是 DORA。护栏指标要保持健康但不追求最大化，分三类：返工与重构、质量技术债与风险、人与 DevOps。

案例：PR 涨了 14%，ROI 可能是负的

一家大企业里某位 VP 手下 350 人的团队今年 5 月采用 AI，他们比较前后各 4 个月：

  • PR 数量增加 14%。
  • 代码质量（0 到 10 的可维护性评分）下降 9%，而且波动变大，采用 AI 前一直很稳定。
  • 返工增加到 2.5 倍。
  • 有效产出没有明显变化。

他说如果这家公司只看 PR 数，会以为生产率涨了 14%，换算成几百万美元，远超 AI 许可证费用。实际 ROI 可能是负的。但他不建议放弃 AI，应该用这些数据找出哪里做错了。最后他邀请企业参与研究，尤其需要有 Cursor Enterprise 的公司，报名网址是 softwareengineeringproductivity.stanford.edu。

09. Itamar Friedman（Qodo CEO）：AI 代码质量的炒作与现实

直播位置 2:58:30–3:19:30 · 英文原题 The State of AI Code Quality: Hype vs. Reality

Qodo（原名 CodiumAI）的名字代表“quality of development”。他汇总了三份报告：Qodo 自己的、Sonar 的和 Faros 的，样本覆盖数千名开发者、数百万个 PR 和十亿行级别的代码。

开场的几个例子

他说过去三四周云服务出了三次大故障，这些公司都说自己用 AI 生成了 10% 到 50% 的代码，同时也重视质量。他不确定两者有没有关系。60% 的开发者说自己四分之一的代码是 AI 生成或塑造的，15% 说超过 80%。人们不只在 vibe coding，也在“vibe review”：他展示了 Claude Code 安全审查命令的提示词，开头是“你是一位资深安全工程师”，后面写着“请排除拒绝服务问题”。他半开玩笑说这也许是云故障的原因之一，要表达的是质量需要严谨对待。他还问观众：Cursor 或 Copilot 的规则文件，你觉得被完全遵守了吗？多数人的回答是“大部分遵守”，没人确定遵守到什么程度。

三层玻璃天花板

他先给结论：代码补全有一个生产率天花板；Agent 式代码生成的天花板更高，投入（比如规则）越多收获越多；AI 走出 IDE 后可以做 Agent 式的质量工作流，组织里（尤其 100 人以上）有大量质量相关流程可以自动化，这时才开始突破天花板；最后这些工作流和标准要持续学习、动态变化，才能真正看到被承诺的 2 倍乃至 10 倍提升。他说从 McKinsey 和 Stanford 的分享里也能看出，现在整个软件开发生命周期远没到 2 倍。

数据

  • 82% 的开发者每天或每周使用 AI 开发工具；59% 用 3 个以上，20% 用 5 个以上代码生成工具（他把 Lovable 这类也算在内，预测两三年内大家会用到 10 个）。一半的使用来自 10 人以下的小团队，但正在向企业大规模扩散。
  • 写代码的生产率提升可达 3 倍，但 67% 的开发者对 AI 生成代码的质量有严重担忧，说缺少处理和度量质量的框架。
  • 任务完成量多了约 20%，打开的 PR 多了约 97%，评审 PR 的时间多了约 90%。他说即便每行代码的 bug 率不变，代码总量多了，bug 总量也会多。以前写 10 行好代码要几个小时，现在 Claude Code 五分钟给你 1,000 行。
  • 大量使用 AI 代码的开发者报告：42% 更多的开发时间花在修问题上，35% 的项目延期（他承认问卷有偏向）。有报告显示安全事件多了 3 倍，他说这和写代码量多 3 倍是对应的。

他说代码生成在新项目和原型上改变了游戏规则，但服务数百万客户、处理金融交易的重型软件要面对代码完整性、治理、评审标准、测试、可靠性等水面下的问题。他从两个维度拆解质量：一是软件开发生命周期的各阶段（规划、开发、评审、测试、部署），每个阶段都会因为更多 AI 代码出现新问题；二是代码层面（安全、效率等非功能问题）和流程层面（学习和所有权，比如出了故障谁负责、验证、护栏、标准）。

怎么办

  • 测试：大量用 AI 做测试的开发者，对 AI 生成代码的信任翻倍。
  • 代码评审：它能同时覆盖流程和代码层面的问题，比如设置 AI 评审工具在测试覆盖率不够时阻止 PR 合并。用 AI 代码评审的开发者说质量收益翻倍，写代码的生产率提升 47%。Qodo 每月扫描约 100 万个 PR，抽取 100 万个分析，17% 含高严重度问题（还没有采用 AI 前后的对比数据）。
  • 上下文：开发者不信任 AI 代码时，80% 的情况是不信任模型拿到的上下文；问希望改进什么，排第一的是上下文（33%）。他说接入 Qodo 上下文引擎后，代码生成和评审工具对 MCP 的调用中约 60% 是调用上下文 MCP；在 Qodo 的评审中约 8% 的上下文来自标准和最佳实践文件。他提到 Jensen Huang 在 GTC 主题演讲中展示过 Qodo 的上下文引擎。上下文应包括代码、版本、PR 历史、组织日志等。

他的建议：投资自动化质量关卡，利用后台 Agent 做质量检查，用智能评审和测试，维护“活的”文档。他展示了自己讲了三年的那张未来图：规格和代码之间有多个并行 Agent 帮你写规格、改代码、从规格转代码、写测试（测试是可执行的规格），底下是上下文引擎这个“软件开发数据库”，围绕质量和验证构建 MCP 工具，再加上稳定安全的沙箱环境。

最后一分钟他演示了 Qodo：定义一条规则（比如“不要嵌套 if”），Qodo 会结合上下文生成正反例，构建专门捕捉这类问题的工作流，并统计建议被接受的情况；PR 里出现嵌套 if 时（尽管 Cursor 或 Copilot 里设了同样的规则）会被标出并给出建议，还提供 CLI 检查，并记录你采纳与否来调整标准，也会自动从你的代码中学习标准。

10. Olive Song（MiniMax 高级研究员）：MiniMax M2 是怎么训练出来的

直播位置 3:19:38–3:32:50 · 英文原题 MiniMax M2

她在 MiniMax 研究强化学习（RL）和模型评测，曾在纽约生活六年。她介绍 MiniMax 同时做基础模型和应用：文本、视觉语言、视频生成（Hailuo）、语音、音乐，以及内部的 Agent 应用。研究员和开发者坐在一起，所以能直接从内部开发者那里知道开发者需要什么样的模型。

MiniMax M2 是开放权重模型，激活参数只有 100 亿，专为编程和办公类 Agent 任务设计，成本很低。她说它在智能和 Agent 基准上都排在开源模型前列；但数字不能说明一切，有些高分模型接进实际环境很难用，所以他们更看重社区反馈：发布第一周下载量最多，在 OpenRouter 的 token 使用量冲进前三。

四个特点和背后的训练方法

  • 编程体验：扩展环境和扩展专家。用互联网上的真实数据，扩大训练环境的数量和基础设施，让模型在强化学习中和环境交互、针对可验证的编程目标学习，因此全栈、多语言都强。除了大家都在说的扩展环境，他们还“扩展了专家开发者作为奖励模型（Reward Model）”：内部大量资深开发者参与问题定义（修 bug、仓库重构等），识别开发者喜欢、信任的模型行为，对模型的行为和最终交付给出精确的奖励和评估。
  • 长程任务：交错思考加强化学习。普通的推理模型流程是：拿到工具信息和提示，思考，调用工具（可以一次多个），拿到工具结果，最后思考一次给出答案。真实环境有噪声、会变化，工具会出错、结果会出乎意料。M2 采用交错思考（Interleaved Thinking）：每轮工具调用之后再思考一次，判断信息够不够、要不要换工具，一次用户交互里可以有几十到上百轮工具调用。这样能适应环境噪声，在 Gmail、Notion、终端之间自动完成整个工作流。她展示了一个交易场景，上周股市波动时模型表现保持稳定。
  • 对不同 Agent 脚手架的泛化：数据扰动。起初他们以为泛化就是工具扩展，用足够多、足够新的工具训练，模型就能用好没见过的工具。这一开始有效，但换一个 Agent 脚手架就不行了。他们的结论是，泛化是对模型整个操作空间中扰动的适应：工具信息、系统提示、用户提示、聊天模板、环境、工具返回都可能不同。所以他们设计并维护了数据扰动流水线。
  • 多 Agent 可扩展性。模型小、便宜，适合多个副本并行跑长任务。她放了 MiniMax Agent 应用里的视频：多个 M2 副本分别做调研、写报告、做前端展示。

后续的 M2.1 和 M3 方向包括：更好的编程、记忆、上下文管理、面向办公的主动式 AI、垂直领域专家，也许还会整合他们的音频和视频生成模型。她请社区多给反馈。

11. Kath Korevec（Google Labs 产品总监）：主动型 Agent 与 Jules

直播位置 4:45:54–5:02:50 · 英文原题 Proactive Agents

午休后，Alex Lieberman 先回到台上预告下午议程，还提到他的联合创始人 Arman 会在 4 点左右讲“工程师应该像销售一样按产出拿钱”。然后是 Google Labs 的 Kath Korevec，她在一个叫 Ada 的小团队，负责异步编程 Agent Jules。

“洗碗”的心智负担

她家洗碗机坏了，丈夫说他来洗碗，结果她每天晚上都得提醒他。她意识到自己虽然没洗碗，但一直背着“这事做没做”的心智负担。她说异步 Agent 现在就是这样：它们能干一部分活，但开发者还在背着监控它们的负担。

人是串行处理器，我们以为自己在多任务，其实是在快速切换，而切换成本可能高达 40% 的有效时间。她看到推特上有人用三块大屏开 16 个 Claude Code 终端，她的第一反应是“但愿这不是未来的开发者体验”，她想写代码，不想管理 Agent。她希望 Jules 能“不用人说就把碗洗了”。

从被动到主动

今天的 AI 开发工具大多是被动的：你开 CLI 或 IDE 让 Agent 做事，它才回应。好处是只在你要求时用算力。但如果算力不再是限制，可以有几十个小的主动型 Agent 在后台并行，留意模式、发现摩擦，在你开口前处理你不想做的无聊活：修你一直回避的认证 bug、更新配置、标记潜在错误、准备迁移。

她认为主动系统有四个要素：观察（持续理解代码变化、你的模式和工作流）；个性化（学会你在意什么、忽略什么、哪些代码绝不能碰）；时机（太早会打扰，太晚就错过）；无缝融入（出现在终端、仓库、IDE 这些你本来就在的地方）。她举的生活例子是 Google Nest 恒温器学会你的作息，以及身体在你跑步时心率自动升高、快摔倒时手先伸出去。

主动性的三个等级

  • 一级（Jules 现在的状态）：在做你交代的任务时，顺手发现并修复缺失的测试、没用的依赖、不安全的写法，像一个保持厨房整洁、刀磨好的副厨。
  • 二级：理解整个项目，观察你的工作方式。后端工程师可能需要 React 帮助，设计师可能需要写数据库 schema；它会学你的框架和部署风格。
  • 三级（正在为 12 月努力）：理解后果，即选择对用户、性能和结果的影响。Jules 加上设计 Agent Stitch 和数据 Agent Insights 一起工作：Jules 看到软件哪里坏了，Stitch 理解用户怎么交互，Insights 连接分析、遥测、转化率等真实信号，一起提出跨边界的改进。人始终在环中，观察、细化、纠偏。她说这一级的重点是和项目对齐，自主程度排在其次。

Jules 新加的功能

  • 记忆：Jules 自己写记忆，你可以编辑。
  • Critic Agent：和 Jules 对抗式协作，保证代码质量并做完整代码评审。
  • 验证：Jules 写 Playwright 脚本、截图，放回执行轨迹里供你确认。
  • To-do 机器人：扫描代码里的 TODO，带着上下文主动去做。
  • 最佳实践建议、环境配置 Agent（内部原本用于跑评测，正在对外开放）。
  • 即时上下文（Just-in-time Context）：一张“小抄”，Jules 卡住时先查它，不用来问你。

演示

她说本来想现场演示，但相关改动还在推到预发布环境，所以用录屏讲解，并说要“温柔地修一下 Jed 的代码”（Jed 是第二天的主持人）。开启主动模式后，Jules 先索引整个代码库（演示用的是 ADK Python 仓库），列出它找到的 TODO 和可更新的最佳实践，按高（绿）、中（紫）、低（黄）置信度标注它觉得能做成的把握。你可以逐个点击启动，不用写提示、不用看代码，也可以删掉不想要的；自动启动的功能还在开发。点进一个任务能看到它建议修改的代码位置和理由。这套主动功能计划 12 月推出。

最后她讲了一个故事：她和丈夫住在旧金山 Haight-Ashbury 一条慢行街道上的维多利亚老房子里，万圣节路过的人很多。丈夫用泡沫、环氧树脂和玻璃纤维雕了一个六英尺高的电子动画大头（原型是 80 年代电影里 Pee-wee Herman 的头，孩子们叫它“秃头”），她负责用 Jules 写固件、控制步进电机、LED 和传感器。她最想做的是 LED 动画和让眼睛跟着路人转，结果大部分时间在修 bug、换库：提示 Jules，等 10 分钟，再重复。最后没做完想做的东西。她说 Jules 要填的就是工具摩擦和创作自由之间的这道缝。她给团队的建议是：今天做的产品不会是未来的产品，Git、IDE 乃至我们对代码的理解，一年后甚至半年后可能都不存在了，不要害怕质疑旧方法。

他开场调侃舞台像要从天花板掉东西下来，又说这份幻灯片不是 AI 做的：8 月用 o3 做了初稿，前几周想更新时 GPT-5 把幻灯片全弄乱了，最后只好手工做。

GenBI 是 Gen AI 和 BI（商业智能）的结合：一个像 BI 分析师一样用数据回答业务问题的 Agent。目的是数据民主化，不必依赖 BI 团队帮你找报表、解释含义。Northwestern Mutual 是一家有 160 年历史的金融服务公司，做人寿保险和财富管理。他说这里适合做 Gen AI，因为数据多、钱多、用例多、人才好；也难做，因为公司极度厌恶风险，座右铭是“代际责任”，他私下叫它“别搞砸”，毕竟卖的是可能持续 20 到 80 年的承诺。

四个挑战

  • 没人这样做过 GenBI。
  • 他们坚持用真实的、杂乱的数据，因为真正的困难在那里。
  • 信任：要同时说服用户和管理层，答案是准确的。
  • 预算：在风险厌恶写进 DNA 的公司里，怎样说服领导投资一件没人做过、连最终形态都不清楚的事。

为什么用真实数据

从概念验证（PoC）到生产的距离在 Gen AI 领域尤其大，用真实数据能让他们更确信实验里成功的东西在现实里也能成功。另一个收获是和每天使用这些数据的人一起工作：他们提供领域专业知识，以及大量“真实问题 + 当时给出的答案”，也就是评测数据。业务方因此成了研究的一部分，到产品成熟时，是他们主动来要求尽快打包上线。

建立信任

常规做法都有：沙箱环境、不用真实客户数据、处理安全风险。此外有两条：

  • 先爬再走再跑：先给 BI 专家用，他们知道好答案长什么样，工具只是帮他们加速，像 GitHub Copilot；再给业务经理，他们离 BI 团队近，能看出错误，也更愿意反馈；给高管还远，高管要清晰、简洁、可信的答案，系统还没那么准，也许永远到不了。
  • 一开始不写 SQL：先只返回生态里已经验证过的信息，也就是认证过的报表和仪表板。BI 团队告诉他们，80% 的工作就是把人指到正确的报表并教他怎么用。这样系统不编造信息，只是更快、更交互地交付你本来就会拿到的东西。

分阶段、可随时叫停的路线

说服管理层的方法是一个渐进的过程，每一步都有可见性和控制权，每一步都有业务可用的交付物，随时可以叫停。每个阶段是一个 6 周的冲刺：

  1. 纯研究：自然语言转 SQL、怎么写回答、怎么理解问题。
  2. 研究对 BI Agent 来说好的元数据和上下文是什么样。这一步本身就有价值：对 LLM 好的元数据，对人也好，正好为公司另一个语义层（Semantic Layer）项目提供了输入。
  3. 多上下文语义搜索，可以单独做成“找数据、找数据负责人”的产品。在他们公司，光是找到有什么数据、谁负责，可能要两到四周。
  4. 拉取信息并做轻量的数据透视。
  5. 面向企业级使用：用户角色、权限。
  6. （还有距离）完整的 GenBI Agent，自己跑 SQL、做复杂的跨表关联。

他说这种方式避免了沉没成本偏差（“都花了一百万了，做完再说”）。如果 Databricks Genie 这类外部方案变得更好，叫停也容易，而且他们已经有自己的基准和对“好”的理解，能用来测第三方产品，知道去问供应商哪些难问题。

架构

为什么不能直接把 schema 丢给 ChatGPT：schema 很乱，难以理解含义；治理很重要，从外部很难施加。他们的栈是数据和元数据层，加四个 Agent：元数据 Agent（结合数据目录和文档理解问题在问什么）、RAG Agent（从认证报表里找合适的报表；RAG 即检索增强生成，先检索相关资料再让模型回答）、SQL Agent（找不到合适报表时生成更精确的查询，即使报表不能直接用，也用它的查询做种子来扩展，相当于一个很接近目标的 few-shot 示例）、BI Agent（把数据翻译成业务答案，不把原始数据直接倒给用户）。上面是治理、信任、编排和情境化 UI。同一会话内会复用已经确定的数据上下文。三个 Agent 都可以单独上生产。

实际收益

  • 仅 RAG Agent：BI 团队（10 人）约 20% 的工作量是“把正确报表发给正确的人”，其中约 80% 被自动化，大约相当于两个全职岗位。
  • 元数据方面的经验让他们在语义层项目里做了 A/B 测试：同一组问题分别跑在有好元数据和没有好元数据的数据库上，证明了丰富元数据的可测量价值。
  • 正在试验数据透视机器人（实时改时间范围、视图、分组）；下一步评估 Databricks Genie 等工具，并系统地丰富数据目录的元数据和文档。

最后他谈了对未来的几点想法：数据准备会是大市场；会出现很多针对具体任务的模型和应用；Copilot 要在用户所在的地方服务用户；模型安全。他最想讲的是 SaaS 定价：一个人现在可能比以前高效 10 倍，软件该按席位、按用量还是按价值收费？他提到 Salesforce 的 Data Cloud 已经开始按用量定价，他认为这会影响全球 SaaS 的经济模式，哪怕产品本身不是 Gen AI。

他负责 Bloomberg 的技术基础设施部门，覆盖全球基础设施（数据中心、网络连接）、开发者生产力（SCM 和工具）和可靠性（遥测、事故响应）。Bloomberg 有 9,000 多名工程师，大多是软件工程师，每天处理数千亿级的市场行情数据，有 500 多人专门做 AI 研究和工程。旗舰产品 Bloomberg Terminal 上有数千个被称为“function”的应用，邮件是一个，新闻是一组，固定收益的价格收益率计算、交易工作流也各是一组。他说 Bloomberg 有世界上最大的私有网络之一，也有最大的 JavaScript 代码库之一，并参与创建了 KServe 和 Envoy AI Gateway 等开源项目。

先部署，再找真正有价值的地方

两年多前开始时，工具多到让人眼花，他们也不知道哪个能真正提升生产率和稳定性，只知道不部署就不会知道。于是很快组了团队，放出一批能力让大家试，再做度量。调查显示：概念验证更快、测试更快出来、一次性脚本大量生成，但一旦超出这类新项目场景，指标下降得很快。

他提醒工具的优点是快，问题也是快。处理过数亿行代码的人都知道，系统复杂度至少随代码规模呈多项式甚至指数增长，所以要谨慎对待软件资产。他们决定从更宽的“软件工程”定义出发，去做开发者不爱做的事：维护、迁移。

两个例子

  • Uplift Agent：理想是你收到“这个软件要打补丁”的工单时，已经有一个带补丁和说明的 PR。Agent 扫描整个代码库，找出适用补丁的地方并应用。以前他们有基于正则的重构工具，有一定效果但局限大，LLM 的效果好得多。他分享的挑战：需要确定性的验证手段，没有好测试和 linter 时补丁很难应用；部署 AI 工具后平均打开的 PR 数增加，合并时间也变长，因为代码多了还得有人审；工作重心从“怎么做”移到了“想达成什么”。
  • 事故响应 Agent：AI 快而且没有偏见，能迅速翻代码库、遥测系统、特性开关、调用链。人排查故障时常带着“肯定是这个”的偏见，结果不是。这类 Agent 需要大量 MCP 服务器连接指标和日志仪表板、网络和服务依赖拓扑、告警、SLO。

铺好的路（Paved Path）

9,000 人的组织里可能有 10 个团队想做 PR 评审机器人、20 个团队想做事故响应 Agent，很快就会混乱和重复。有的公司让业务单元完全自由，有的强制统一平台，Bloomberg 在中间：提供“黄金路径”和 Enablement 团队（帮其他团队用好平台的团队），他的团队就是其中之一。指导原则是：让正确的事极其容易，让错误的事难得离谱。他们和 AI 组织一起建的路径包括：

  • 一个网关，团队可以快速试不同模型，平台能看到用了哪些模型，并指导哪个模型适合哪类问题。
  • 工具发现：一个 MCP 目录 hub，团队 A 想做什么时先看有没有人已经在做，可以合作。
  • 工具创建和部署走 PaaS，标准化 SDLC 和运行环境，减少部署 MCP 服务器的摩擦。
  • 让概念验证尽量容易，以鼓励尝试；上生产则要求质量控制，因为稳定性是业务核心。

人的部分

  • 入职培训：Bloomberg 有 20 多年的培训体系，分初级和高级。他们把 AI 编程直接加进入职培训，结合内部原则和技术来教。新人回到团队会问“为什么不用新方法”，挑战资深同事，成了很有效的变革推动者。
  • 社区：Bloomberg 有十多年的 Champ 项目和 Guild 项目（跨组织的兴趣社区）。两年前他们借这个基础建了工程 AI 生产力社区，自然地去重、共享经验，也推动了内部开源和“访问工程师”（直接派人到另一个团队干半年到一年把事做完）。
  • 领导者：数据显示个人贡献者的采用率明显高于领导层。很多技术负责人和经理在 AI 时代缺乏指导团队的经验，所以他们在推出领导力工作坊。

他最兴奋的一点是：AI 改变了软件工程的成本函数，有些事变便宜了，有些变贵了，做与不做的权衡变了。他觉得这是工程师和工程领导回到基本原则、重新追问“什么是高质量的软件工程”的好机会。

14. Samir Mody（The Browser Company，AI 工程负责人）：从 Arc 到 Dia，做 AI 浏览器的经验

直播位置 5:44:18–6:01:50 · 英文原题 From Arc to Dia: Lessons learned in building AI Browser

The Browser Company 2019 年成立，使命是重新思考人们怎样使用互联网，他们认为浏览器是生活中最重要的软件之一，却没得到应有的关注。他放了 CEO Josh 几年前介绍“互联网电脑”想法的截图。2022 年他们发布了第一款浏览器 Arc，更个人化、更有条理，被数百万人喜欢，但团队觉得它仍只是增量改进，没达到最初的愿景。

2022 年他们拿到 GPT 系列模型，开始做原型，把一些想法放进 Arc。2024 年初公司发布了名为“Act Two”的视频，提出 AI 会改变人们使用互联网的方式，进而从根本上改变浏览器本身。于是他们从零开始做了一款以 AI、速度和安全为核心的新浏览器 Dia，今年发布：一个陪你在浏览器里工作的助手，了解你、个性化，能结合你的标签页和常用应用完成工作。他说它还没实现愿景，但在路上。

一、为快速迭代优化工具和流程

公司一直相信，不比别人更快地构建、发布、学习就赢不了。他们现在在四个方面投工具：AI 功能原型、构建和运行评测、为训练和评测收集数据、用于 Hill Climbing（反复小步改进、让指标一点点往上爬）的自动化。

最初他们做了一个很简陋的提示词编辑器，只在开发版里，只有工程师能用，迭代慢，而且没有个人上下文。对 AI 产品来说上下文决定体验好坏。后来他们把所有工具做进了全公司每天在用的产品里：提示词、工具、上下文、模型、所有参数都能调。他说这让构思、迭代和打磨的速度提升了 10 倍，从 CEO 到新员工都能带着自己的完整上下文创造新功能或改进现有功能。记忆知识图谱、Computer Use 机制也有对应的内部工具，他们在把 Computer Use 放进产品前试过几十种策略。他说这也很好玩，PM、设计师、客服、战略运营都能按自己的场景试想法。

二、用 GEPA 优化提示词

GEPA 来自今年早些时候的一篇论文。他说它的动机很简单：不用 RL 或其他微调（Fine-tuning），以样本高效的方式改进复杂的 LLM 系统，这对小公司很重要。做法是：给一组种子提示词，在一组任务上执行并打分，用帕累托选择挑出最好的几个，再让 LLM 反思哪里好哪里不好，生成新的提示词，循环往复。创新点在反思式提示变异、能探索更多提示空间的选择机制，以及调的是文本、不动权重。他展示了一个简单提示经过 GEPA 按他们的评分机制优化的例子。

他把功能开发分两个阶段：原型和构思阶段，扩大漏斗顶端的想法数量，降低谁能做、怎么做的门槛，每天每周都有各种人试想法、内部试用；如果有实际用处并且看得到达到质量标准的路径，就进入下一阶段：收集和打磨评测来明确产品需求，通过代码、提示词和 GEPA 这类自动化方法爬坡，内部试用，再发布。他说两个阶段同样重要，每周都有新可能被解锁，要尽量多尝试，但也别低估把想法做成高质量产品的路。

三、把模型行为当作一门手艺

他们定义的模型行为（Model Behavior）是：定义、评估、发布模型的期望行为，把原则变成产品需求、提示词和评测，塑造 Dia 助手的行为和个性。分三块：行为设计（风格、语气、回答形态）、为度量和训练收集数据、模型引导（提示词、模型选择、上下文窗口里放什么、参数等）。这是一个反复迭代的过程，内外部反馈不断回流。他拿网页设计的演进作类比：网站起初只求能用，后来产品设计成了一门手艺；模型行为先是提示词加评测，现在是目标导向推理、自主任务、自我纠错，乃至塑造个性。他认为它会在产品公司里成为一个独立的专门职能。

他最喜欢的故事：起初是工程师写提示词，有了内部提示词工具后，战略运营团队的一位同事某个周末用这些工具重写了所有提示词，周一早上发了个 Loom 视频讲他做了什么、怎么做、为什么。那组提示词让产品的能力和质量上了一个台阶，模型行为团队就这样成立了。他建议大家想想公司里有哪些人，不论职位，能帮忙塑造产品和引导模型。

四、AI 安全是产品构建的自然结果

他专门讲提示注入（Prompt Injection）：第三方通过内容覆盖 LLM 的指令来造成伤害，比如外泄数据、执行恶意命令、绕过安全规则。例子：你让 LLM 总结一个网页，网页 HTML 里藏着注入指令，LLM 转而打开一个新网址，把你的个人信息作为 GET 参数拼进 URL，数据就被带走了。浏览器处在“致命三要素”（Lethal Trifecta）的中心：能访问私人数据、接触不可信内容、能对外通信（打开网站、发邮件、安排日程）。

技术上可以把不可信内容包在标签里，让模型只听标签外的指令，但这很容易被绕过；也可以把指令放在系统角色、把第三方内容放在用户角色，再加随机生成的标签，这有帮助但没有保证。所以要在产品设计上把技术和用户体验结合起来。以 Dia 的自动填表为例：它用 LLM 结合上下文、记忆和你的信息填网页表单，一旦被注入，数据填到表单上就失控了。Dia 的做法是写入表单前，让用户以纯文本阅读并确认要填的数据。这不能阻止注入，但给了用户控制、知情和信任。安排日程、写邮件也有类似的确认步骤。

他最后说，他们起初只想“用 AI 让 Arc 更好”，后来发现这是公司层面的演变：怎么构建、组建了什么团队、怎么看待安全，以及怎么培训、招聘、沟通、协作。认清技术转变后要坚定地拥抱它。

15. Max Kanat-Alexander（Capital One 执行杰出工程师）：编程 Agent 时代的开发者体验

直播位置 6:02:05–6:19:50 · 英文原题 Developer Experience in the Age of AI Coding Agents

他做开发者体验（Developer Experience）20 多年，说从没见过过去 12 个月这样的情况：每两三周就有新东西让工程师目瞪口呆。以前有人问“能不能用昨天刚出的工具”，答案当然是不行；现在变成“呃，也许可以”。未来很难预测，很多 CTO 和做开发者体验的人在问：我现在的投资会不会全打水漂？到 2026 年底回头看，投什么会让我庆幸？很多人干脆认为编程 Agent 会自己解决公司的一切问题。他说 Agent 很了不起，但不是唯一需要投资的东西。

他提出两个问题：用开发者体验的原则判断，无论发生什么都会有价值的是什么？为了从 Agent 身上拿到最大价值，Agent 之外的各个层面要修好什么？他列出了一组“不会后悔的投资”，都是 Agent 的输入或周边环境。

不会后悔的投资

  • 标准化开发环境：用业界标准的工具，用业界通用的方式，因为那就是训练数据里的样子。可以写指令文件逼模型适应你魔改的工具链，但那是在和训练集对着干。如果你们自己发明了包管理器，大概应该撤回。也意味着别用冷门编程语言，他自己是编程语言爱好者，但在实际的 Agent 开发工作里已经不用了。至于以后还会不会有新工具，他说还会有爱好者去用；而且“刚出的、没在企业里验证过的技术能不能用来跑每秒 10 万次查询的服务”这个问题，答案一直都是不行。
  • CLI 或 API：Agent 要行动就需要 CLI 或 API。可以用 Computer Use 或让它写 Playwright 操作浏览器，但如果能给一个 CLI，让它用最熟悉的文本方式执行，为什么要选别的？
  • 验证：任何客观、确定性的验证都会提升 Agent 的能力，关键是错误信息要清楚。Agent 没法从一个没有其他信息的“500 internal error”里猜出你的意思。但让 Agent 给不可测的代码库写测试，它会写出“老板，我按了按钮，按钮按成功了，测试通过”这种东西。很多企业的遗留代码库没有为测试设计，只有一些高层端到端测试，缺少 Agent 能循环跑、能给出可行动错误的单元测试。
  • 系统和代码库的结构：结构好的代码库 Agent 干得更好。有些遗留代码库人根本没法推理，因为推理所需的信息不在代码里，结构也让人看不懂。Agent 只能和人一样反复试运行看哪里坏，能力大打折扣。最终都要落到可测试上。
  • 文档：Agent 读不了你的心思，也没参加那个没有记录的口头会议。很多公司靠部落知识理解需求和规格。如果代码本身好懂，就不需要再解释代码里有的东西，这类文档也许可以省掉，直接问 Agent 代码结构就行；但“为什么这样写”，以及程序之外的东西（比如某个 URL 参数传进来的数据长什么样，在代码还没写时）必须写在 Agent 能访问的地方。

代码评审成了主要工作

大家常说读代码的时间比写代码多。现在的区别是，写代码本身变成了读代码，每个工程师的主要工作变成代码评审；深度采用 Agent 的团队 PR 数量暴增，大规模评审成了瓶颈。他说要做的是让每一次响应变快，整个评审周期不必刻意压缩，因为评审是质量过程。和 Agent 迭代也一样，目标是拿到正确结果，不能“五分钟到了就把垃圾提交了”。

  • 他认为很多公司有一种“社交病”：在团队频道里发“谁能帮我审一下 PR”，结果总是同一个人在审，评审统计里一个人 50 次，其他人两三次。PR 一多，这个人扛不住。要分配给具体的人，用系统轮流分配，设 SLO 并有执行机制。
  • GitHub 这类工具不擅长显示“现在轮到谁动”。他现在主要靠别人在 Slack 上告诉他“可以再审了”，效率很低。
  • 要保持高标准。软件设计追求的是“够好、比之前好”，但对寿命很长的系统，“够好”的门槛比人们想的高得多。没有能拒绝坏代码的流程，Agent 带来的生产率提升会随时间下降。
  • 问题是最好的评审者都在开会、做战略，没有在做评审，也就没有在带初级工程师。他说 20 多年来他找到的唯一培养好评审者的方法，就是和他们一起做好的评审，需要某种学徒机制。

他描述了两种循环。恶性循环：糟糕的代码库和混乱的环境交给 Agent，Agent 产出程度不一的胡说，开发者越来越沮丧，最后说“我觉得能用”就提交了；评审者要么水平不够、要么忙不过来，“不知道，应该没问题吧”，大量橡皮图章式的 PR 合进去。他预测处在这种循环里的公司，Agent 生产率会在一年内持续下降。良性循环则相反，提高 Agent 帮我们的能力，它们就能让我们越来越快。他认为现在就该投这些看起来昂贵的基础工作，这会在同行之间拉开最大的差距。

他补充了一点：CLI 和 API 要在开发时就能跑。有些检查只在 CI 里跑，CI 要 15 到 20 分钟，而 Agent 比人有耐心也更容易出错，会连续跑五次“改一下、跑测试”，每次 20 分钟就完了，30 秒就好得多。他的总结是：对人好的东西对 AI 也好。这意味着即便在 Agent 上押错了，投资也一定能帮到人。

企业采用现状

  • 今年编程和软件工程的采用出现了大拐点，而且不只是工程部门，其他部门也在想怎么用代码构建东西。
  • 年初很多人预测今年是“企业 Agent 之年”。大规模自动化没有发生，但 Agent 的采用模式有明显变化：KPMG 季度调查（年收入 10 亿美元以上的公司）中，有完整生产级 Agent 部署（不算试点和实验）的比例从今年 Q1 的 11% 升到 Q3 的 42%。他认为 Agent 走出试点阶段比预想的快，重点开始转向人和 Agent 怎么协作，以及培训和支持工作；对 Agent 的抵触也在下降。
  • 同时大多数企业仍困在试点和实验阶段。McKinsey 的 State of AI 调查显示只有 7% 认为自己已全面规模化，约 62% 还在实验或试点。大组织在规模化上反而领先小组织，这和过去几年的观察一致。各部门的采用也很不均衡，IT 运维跑到了前面。
  • 领先者和落后者分化明显，领先者做得更多、更系统，不只看省时间这类第一层收益，也在想怎样增长收入、创造新能力和新产品线。
  • 支出只会增加：KPMG 调查里企业预计未来 12 个月的 AI 支出，去年 Q4 约 8,800 万美元，今年初 1.14 亿，最近一次是 1.3 亿；Deloitte 的数据显示 90% 以上的组织打算增加 AI 支出。
  • 对 ROI 的预期提前了：KPMG 年度 CEO 调查里，2024 年 63% 认为需要 3 到 5 年才能实现 ROI，20% 认为 1 到 3 年，16% 认为超过 5 年；今年认为 1 到 3 年的升到 67%，19% 认为 6 个月到 1 年，3 到 5 年的降到 12%。
  • 但 ROI 很难测：78% 认为 ROI 明年会更重要，也有 78% 说传统的影响度量方法跟不上新现实。他说 CIO 们反复跟他讲这一点。

他们自己的 ROI 调查

于是他们直接请播客听众自报用例的 ROI。调查 10 月底上线，到演讲时有 1,000 多个组织提交了约 3,500 个用例，他这周第一次分析了前约 2,500 个。他们把收益分为 8 类：节省时间、增加产出、提升质量、新能力、改善决策、节省成本、增加收入、降低风险，每个用例只能选一个主要收益。他提醒样本是高度投入的听众、自愿提交，有偏差。

  • 44.3% 看到中等 ROI，37.6% 看到高 ROI（显著加变革性），只有约 5% 是负 ROI（只表示目前投入多于收益）。
  • 67% 认为明年 ROI 会大幅增长；连目前负 ROI 的团队里也有 53% 这样认为。
  • 节省时间是默认起点，约占 35% 的用例，集中在每周 1 到 10 小时，尤其 5 小时左右。他说每周省 5 到 10 小时相当于每年赢回 7 到 10 个工作周，对企业很有意义。
  • 按组织规模分，200 到 1,000 人的组织更多集中在“增加产出”。按角色分，高管和领导更少关注省时间，更多关注增加产出和新能力，也更乐观，他们提交的用例里 17% 已经是变革性 ROI（可能有选择偏差）。
  • 最小的组织（1 到 50 人）更早获得变革性收益。他想再做一轮专门研究这个区间，因为 3 人公司和 40 人公司可能差别巨大。
  • 编程和软件相关用例的 ROI 高于平均，负 ROI 低于平均。
  • “降低风险”作为主要收益的用例只有 3.4%，但其中 25% 达到变革性 ROI，是所有类别里最高的。他做合规和风控的朋友也有同感，这些职能的难点往往是工作量本身。
  • 医疗和制造业的用例平均影响明显高于整体。
  • 提到自动化或 Agent 的用例，自报 ROI 大幅高于其他。
  • 一个组织提交的用例越多，ROI 越好，这和 McKinsey 的结论一致：系统地、跨部门地推进收益更大。

17. Arman Hezarkhani（10x 联合创始人、管理合伙人）：像付销售提成一样给工程师发薪

直播位置 7:19:03–7:34:10 · 英文原题 Paying Engineers like Salespeople: How Tenex Rebuilt the Incentive Stack for Modern Engineering

10x 帮企业做 AI 转型，他的联合创始人就是主持人 Alex。他说刚才在后台和一群他敬佩多年的杰出工程师聊起 10x 按完成的故事点（Story Point，敏捷开发里估算任务工作量的单位）给工程师发钱，不少人翻白眼。客户按交付的故事点付钱给 10x，10x 按工程师完成的故事点付钱给工程师。他说这听起来疯狂，但有效：他们招到了做过创业并退出的工程师、世界级的机器学习和 AI 研究员、NASA 的火箭科学家，代码交付快且可维护。他强调目的不在说服大家照做，他想说明的是引入这项技术后薪酬方式可能要变。

为什么想到这个

他学的是软件工程，在 Carnegie Mellon 读书和教过书，后来在 Google 帮助把 AI、云和移动业务扩展到国际市场，再后来做过几家风投支持的创业公司。上一家公司时他在纽约一家 WeWork 办公，看到旁边的人打开 VS Code，没有聊天窗口，一个字符一个字符地敲代码，而他的电脑上开着 45 个 Agent，三个在订午饭，两个在写代码，一个在做研究。他认为这种差别是激励问题：他是创始人，想榨出每一分效率，所以天天在推特、LinkedIn 和博客上追前沿；而那个人大概拿着固定工资加年终奖和一点股权，这套本该激励创新的模式没起作用。

一段“不准确的”薪酬史

他声明以下纯属示意：最早按小时付钱，没有理由干得快，甚至有反向激励；改成按项目付钱，工程师很不擅长估时间，为了不吃亏会报 15 到 20 小时而不是 5 小时；改成固定工资加奖金，人们朝九晚五；Larry Page 意识到自己拼命是因为拥有公司，于是有了股权，这是创业生态的基础。但不是每家公司都是 Google，想冒险的工程师会去 YC 或自己创业，不想冒险的选现金，现金不能谈、股权“有就行”。所以他认为 AI 时代这套模式要重新设计，直接激励人用好这些工具，同时保持高质量。

具体怎么做

10x 做两类工作：路线图和执行。客户来说“我们想要 AI”或更具体的目标（比如客服产出提升 10%），10x 调研后给出路线图，客户可以自己做或交给 10x，很多是定制开发。面向客户的有两个角色：策略师（大多懂技术，曾是 PM 或工程师）负责和客户把产品需求理清楚；AI 工程师接手写架构设计文档，这是他们花工程时间最多的地方，文档里包括工单，每张工单评定故事点。工单被验收后，工程师按故事点拿钱。工程师有固定底薪，每季度按完成的故事点结算。

两个项目

  • 一家户外广告牌公司（时代广场就有它卖的广告位）有类似“广告牌版 Uber”的自助产品，上传 PNG、选地点和时长即可投放。图片要经过公司内部和广告牌业主两轮审核，内部审核花钱、不准、耗时，广告每晚上线一刻都是收入损失。10x 两周做出一个审核模型，相对人工审核达到 96% 的准确率。
  • 一家服务全球零售商的公司在门店装了低功耗设备，只能跑一个做热力图的模型。10x 提出如果芯片算力稍强、把模型量化后并行运行，可以做更多事，最后做了五个能并行运行的模型，包括热力图、排队检测、防盗检测等。

风险和制衡

他列出三个风险：工程师虚报故事点（“加个按钮，45 点”）；为了赶工牺牲质量；工程师变得像销售一样互相抢。应对办法：

  • 故事点由策略师来定，并且要经过评审。
  • 两个角色互相制衡：策略师的薪酬按 NR 指标（字幕如此，他解释为客户满意度），每张工单都要经过内部多轮 QA（策略师参与）和客户验收。
  • 招对人。他们把招聘门槛定得很高，好让其他一切变简单。他引用 Alex 的话：AI 像哈哈镜，会把你的任何特点放大 10 倍，优秀的工程师更优秀，不好的更潦草。

他的结论是 AI 给人超能力，但现有的薪酬方式在拖后腿，请大家想想怎样换一种方式给团队发薪，不管是工程还是其他岗位。

18. Justin Reock（DX 副 CTO）：AI 辅助工程团队的领导方法

直播位置 7:34:16–7:52:00 · 英文原题 Leadership in AI-Assisted Engineering

DX 是一个工程效能度量平台。他说内容很多、时间很少，详细内容都在他们发布的面向高管的 AI 策略手册（PDF）里。

现在的影响：没人知道，而且差异巨大

Google 说大家生产率提升了 10%，但 Google 本来就很高效；METR 的研究（他说设计上有一些缺陷）显示使用编程助手后生产率下降了 19%，而且参与的每个工程师都觉得自己更快了。DORA 的研究基于行业平均：AI 采用率提升 25%，文档质量提升 7.5%，代码质量提升约 3.4%，温和但偏正面。DX 自己的聚合数据也类似：变更信心提升约 2.6%，代码可维护性小幅提升，变更失败率下降约 1%（行业基准是 4%，所以不算小）。

但按公司拆开看完全是另一回事：有的公司变更信心提升 20%，有的下降 20%，可维护性和变更失败率也一样。变更失败率上升 2% 意味着在 4% 的基准上多交付最多 50% 的缺陷。平均数看起来无害，掩盖了巨大的波动。

他总结的规律：自上而下的强制命令不起作用（“必须 100% 采用 AI”，那我每天早上改一下 README 就算合规了）；缺乏培训和支持会拖后腿，很多公司只是打开工具就指望大家会用；很难度量，甚至不知道该测什么。他展示了 DORA 的一张贝叶斯后验分布图：峰值越尖、越偏向正向一侧，说明越有把握该举措有正面影响，排在前面的是清晰的 AI 政策和给人学习的时间（光发资料不够，要真的给实验空间）。

几条建议

  • 减少对 AI 的恐惧。他引用 Google 2012 年的 Project Aristotle：Google 原以为高绩效团队的配方是高手加有经验的经理加无限资源，结果最大的因素是心理安全感。SWE-bench 上 Agent 能在无人干预下完成约三分之一的任务，也意味着三分之二做不了。他说要讲清楚 AI 用来增强工程师、不用来替代工程师，并且主动沟通，别等人害怕了再说。他的另一句话是：AI 不会抢你的工作，但很会用 AI 的人可能会。
  • 公开讨论度量。两个杠杆：速度和质量，不能用一堆 AI 垃圾换速度，把瓶颈踢到以后。三类数据：遥测（API 数据，有用但不总准，比如“建议被接受率”要求工程师在 IDE 里点接受，点了之后也可能全部重写）；经验抽样（比如在 PR 表单里加一栏“这个 PR 用了 AI 生成”）；自报和问卷（他们强调有效问卷：90% 以上的参与率，把开发者体验当作系统问题、不当作人的问题来设计问题）。他引用 W. Edwards Deming：组织 90% 到 95% 的产出由系统决定，不由个人决定。基础的开发者体验和生产率指标仍然最重要，AI 指标告诉你技术在发生什么，基础指标告诉你举措有没有用。
  • 他举了 Microsoft（采用指标，以及一篇讲“糟糕开发日”遥测的论文）、Dropbox（周活、日活和变更失败率）、Booking 的做法。DX 的 AI 度量框架分三个维度：使用、影响、成本，也可以看成成熟度曲线：先看谁在用、多少 PR 有 AI 参与、多少任务交给 Agent，再把使用和速度、质量关联起来，最后看成本。他说云计算热潮过去 15 年还有新公司在教大家优化云成本，而他已经听说有人一天烧掉 2,000 美元的 token。
  • 合规与信任：给系统提示建反馈回路。系统提示、Cursor 规则、AGENTS.md 这类文件控制模型行为。他的例子是模型总给出过时的 Spring Boot 2 写法，而团队要 Spring Boot 3。要有一个人或小组接收这类反馈，负责维护和持续改进这些提示。
  • 理解温度（Temperature）。模型预测下一个 token 时有一组候选和对应概率，温度控制选择时的随机性，也被叫作“创造力”，取值在 0 到 1 之间，他建议别用正好 0 或 1。演示里温度 0.00001 时同一任务两次输出逐字相同；温度 0.9 时让它写一个渐变，两次给出的方案差别很大，只有一个符合“写 JavaScript 方法”的要求。要按场景决定哪里要创造力、哪里要确定性，可以用 Docker Model Runner、Ollama、LM Studio 来试。
  • 教育和时间。他们抽样了每周至少省一小时的开发者，让他们给最有价值的五个用例排序，据此写了一份带代码和提示示例的指南，一些工程团队把它列为必读。排第一的用例是栈追踪分析，这是一个解读型用例，不是生成型。
  • 解除使用障碍。不要因为担心数据外泄就不试，可以用 Bedrock、Fireworks AI 等在安全环境里跑强模型，用自托管和私有模型；第一天就和合规部门合作，你可能发现很多“不能做”的假设是错的。
  • 覆盖整个 SDLC。他是 Eliyahu Goldratt 约束理论的拥趸：在非瓶颈上省一小时毫无价值。DX 对近 14 万名工程师的数据显示，AI 带来的年化时间节省被上下文切换、打断和会议日抵消掉了。案例：Morgan Stanley 的 DevGen.AI 读取 COBOL、大型机 Natural、Perl 等遗留代码（他自嘲作为老 Perl 开发者不愿承认 Perl 也算遗留了），为开发者生成规格，省去逆向工程，每年节省约 30 万小时；Zapier 用一系列机器人和 Agent 辅助入职，新工程师两周就能有效产出（行业好的水平约一个月，中等约 90 天），他们因此决定加快招聘，没有选择靠裁员维持现状；Spotify 在检测到事故时自动汇总运行手册等上下文推到 SRE 频道，省掉了事故开头那几分钟摸清状况的时间，显著改善了 MTTR。

下一步建议：把指南发给团队参考；确定度量和评估 Gen AI 影响的方法；跟踪 AI 采用并看它和整体影响指标的关系；持续迭代最佳实践和用例。

19. Dan Shipper（Every 创始人）：怎样建一家 AI 原生公司

直播位置 7:52:08–8:09:50 · 英文原题 How to build an AI-native company (even if your company is 50 years old)

他说自己其实没有一套“AI 原生公司手册”，因为手册正在被在座的人和他们公司一起发明。他能给的是“来自未来的报道”：Every 内部的实际经验。

90% 和 100% 之间差 10 倍

他的第一个观察：90% 的工程师用 AI 的组织和 100% 用 AI 的组织之间有 10 倍的差别。只要有 10% 的人还在用传统方式，整个组织就得迁就那个世界，没法做那些“没人再往编辑器里敲代码”时才能做的事。

Every 有 6 个业务单元、4 个软件产品，只有 15 个人。过去 6 个月 MRR 每月两位数增长，有 7,000 多付费订阅者、10 万多免费订阅者，总共只融了大约 100 万美元。99% 的代码由 AI Agent 写，没人手写代码，用的是 Claude Code、Codex、Droid 等。每个应用由一个开发者负责：

  • Cora：AI 邮件助手，左边汇总你的邮件，右边可以问问题，他当场问“我的 AI Engineer 演讲是什么时候”，它直接给出答案。主要由一个人做，加一两个合同工。
  • Monologue：语音转文字应用，类似 Superwhisper 或 Wispr Flow，一个人负责，有数千用户。
  • Spiral：也是一个人负责。

他说一年前这还不可能。转折点是 Claude Code：抛开代码编辑器的终端界面，把大家推向“把任务委派给 Agent”，于是可以并行做更多事。

具体的变化

  • 可以同时做多个功能和 bug。推特上有个梗说 vibe coder 开四个窗口其实什么也没干，他说确实可以那样，但 Every 里也有工程师在高效地同时用四个 Agent 窗口，这是一个人能做和维护生产应用的重要原因。
  • 代码便宜了，可以给高风险的想法做原型，做更多实验。启动一件事的门槛很低：“去研究一下我可能想做的这个大重构”，然后去干别的。
  • 走向演示文化：以前要写备忘录、做幻灯片说服别人，现在几小时 vibe code 一个东西给大家看，能做出那些“得亲手感受才明白”的奇怪东西。

复利工程（Compounding Engineering）

他说 AI 让他们发明了一套新的工程原语和流程，他们叫它复利工程。传统工程里每个功能都让下一个功能更难做；复利工程的目标是每个功能都让下一个更容易。循环有四步：

  1. 计划：和 Agent 一起做详细的计划。
  2. 委派：让 Agent 去做。
  3. 评估：测试、试用、让 Agent 自查、人工评审、Agent 评审等。
  4. 沉淀（Codify）：他说这是最值钱的一步，把计划、委派、评估中学到的东西写回提示词，放进 CLAUDE.md、子 Agent、斜杠命令里，把每个工程师在找 bug、改计划、委派中积累的隐性知识变成可以在全组织传播的提示库。

二阶效应

  • 隐性的代码共享：不同产品常要实现类似功能（团队功能、某种 OAuth）。以前要抽成库或者开会讲，现在可以让 Claude Code 去读旁边同事的仓库，学会他实现的过程，再用自己的技术栈和框架重新实现。开发者越多，可共享的就越多，没有额外成本。
  • 新人第一天就有产出：环境怎么搭、好的提交长什么样都写在 CLAUDE.md、Cursor 或 Codex 的配置文件里，Agent 帮新人搭好本地环境，知道怎么写好 PR。也方便请专精某件事的自由职业者来干一天。
  • 跨产品提交代码：大家都用公司所有产品，遇到 bug 或小的体验问题，常常直接给那个产品的负责人提 PR，因为让 Claude 或 Codex 读仓库、找到修法很容易。他推测几年后客户也许能让自己的 Agent 修 bug 并提交 PR。
  • 不必统一技术栈：至少到目前，他们让每个产品的人选自己喜欢的语言和框架，因为 AI 让在不同栈之间翻译和上手变得容易。
  • 管理者也能提交代码：他说这是他最喜欢的，也可能是部分开发者和他团队的噩梦。他身为 CEO 本来没理由写代码，但过去几个月确实提交过生产代码，因为 AI 让人可以在注意力碎片化的情况下工作：开完会让 Claude Code 去调查某个 bug，去忙别的，回来已经有计划或根因修复，再提 PR。不容易，也不是魔法，但做得到。

他的总结：100% AI 采用会带来 10 倍的差别；一个工程师应该能构建和维护一个复杂的生产产品；复利工程让每个功能更容易构建，并带来一系列让全组织更好协作的二阶效应。他调侃说“旧金山的很多人还不知道这些，你们是第一批听到的”。最后介绍了 Every：每日 AI 简报、新模型和新产品评测、上面这些应用，以及面向大公司的培训和咨询，打包成一个订阅。
