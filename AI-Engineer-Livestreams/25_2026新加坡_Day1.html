02. Vivian Balakrishnan（新加坡外交部长）：一个部长的第二大脑

直播位置 0:41:26–1:03:40

他开场说自己在这里像个冒牌货：他是退休的眼科医生，“在政治里绕了太久的路”，一直喜欢动手修东西。不做手术之后，他组装手表、给家电重新编程，现在又做了今天要讲的东西。

先说结论：三条信息

  • 现在可以外包计算、记忆、复制和知识传播，唯一不能外包的是你本人的理解。身处权责位置的人可以委派工作，不能委派问责。
  • 他引用剑桥大学机器学习教授 Neil Lawrence 在《金融时报》发表的一封短信：模型、数据中心、自上而下的规则属于宏观层面，真正为经济和社会创造价值的地方在基层，一个工作流一个工作流、一个部门一个部门、一个人一个人地发生。教师、律师、技术员、经理、医生，甚至部长，用上已经存在的工具，才是回报所在。所以他看重去中心化、个人化、定制化。
  • 做到这些的门槛已经塌了。工具都在，问题是让人知道有哪些工具，自己组装起来。

他的个人 Agent 是怎么搭的

大约三个月前，他被 OpenClaw 的热度吸引，但以他的工作身份，安全是硬伤。有人推荐了 NanoClaw（下一位讲者 Gavriel Cohen 的项目）。他看重两点：代码库很短，“像我这样的外行也能读懂个大概”；它跑在容器里。他说作为外科医生，他知道世上没有“常规手术”，东西一定会坏，坏的时候最好坏在隔离墙以内。NanoClaw 也没有配置文件，个性化改动都交给 LLM 去做，所以每个人跑的 NanoClaw 实例其实都是一个独立定制的系统，这有好处也有麻烦。

他列出自己的组件：

  • 通讯：通过 WhatsApp 和 Agent 对话，用的是开源库 Baileys。他说这个库模拟的是浏览器或电脑端登录 WhatsApp 的方式，“大概不完全符合 Meta 的意愿”。
  • 语音：Whisper 做语音转文字，他可以说话，Agent 也能用语音回他。
  • 记忆：他认为这是他这种用户真正的前沿。他用了一个图结构的记忆系统（字幕作 “Neman”，名称不确定），节点是实体，边表示因果、时间和语义关系；再在本地用 Ollama 跑一个 embedding 模型，这样除了关键词检索还能做语义检索。Embedding 是把一段文字变成一串数字向量，意思相近的文字向量也相近，语义检索就靠这个。
  • 知识整理：他把演讲稿、会议记录，尤其是自己在国会的发言，放进这个记忆库做抽取；同期 Andrej Karpathy 提出了让 LLM 维护个人 wiki 的做法，他也加了进来。
  • 界面：Obsidian，因为它可以走 Apple iCloud 同步，从记忆库生成的 wiki 自动变成他的私人云端笔记。

用下来怎么样

他这个月要访问 12 个国家，见几百个人，要了解每个国家的经济、地理、文化、历史和战争与和平，还要把每个人当作具体的个人来了解，光看简报上的名字不够。外交官的认知负荷很大。这套系统让他随时能查到一个事实，需要时还能一路深挖下去。LLM 用来做分析、抽象、起草简报和讲稿、草拟答问，包括国会质询。他说三个月前他把国会辩论全文喂进去，生成的问答“恕我直言，比一些同事更犀利”。他的梦想是哪天让 Agent 替他回答国会的补充质询，“合法性我不确定”。

今天的幻灯片也是 Claude 生成的。他说最能证明有用的是：三个月来他一直不敢把它关掉。NanoClaw 从 v1 升到 v2 时迁移并不顺，他就让 v1 继续跑，在另一台电脑上装 v2。他每天用得最多的那个 Agent 跑在一台两三年前的 Raspberry Pi 上，只有 8GB 内存。

他强调这些组件（Claude、Baileys、记忆系统、Whisper、凭证管理）一个都不是他写的，他连 vibe coding 都不敢自称，只是在“组装工具”，没写一行胶水代码。NanoClaw 每次给 Agent 开 bash 权限都要他批准，所以他会扫一遍代码，懂一点代码会有帮助。

边学边做，以及几点提醒

他的方法是动手学：光读标题和摘要不够。Claude 给他写了一句话，他起初怀疑是不是别人说过，Claude 说没有，他也同意这句话，并把它送给政府同事：“你无法治理一项你只听过简报的技术。”

  • 成本：他认为现在的 token 价格相当于 AI 大厂在补贴用户。算力有限，电价在涨，战争也不帮忙。不要把每个问题、每个步骤都扔给 LLM，“拿着锤子看什么都像钉子”。确定性系统和专家规则系统仍有位置。
  • 作为生物学背景的人，他相信最后会走向某种神经符号（neuro-symbolic）系统，并对 Yann LeCun 的观点有同情：人脑的计算层数可能比今天很多大模型还少，视觉、语言、认知的皮层计算结构比今天耗电的系统高效得多。但他也承认，这些系统就是带注意力和记忆的模式识别，简单能力之上涌现出了概念理解和语言。所以要谦虚。
  • “工具比模型更重要。”他说已经告诉 Gavriel，6 月 15 日前要让 NanoClaw 把所有模型都当作一等公民支持。
  • 记忆是这个前沿最大的未解问题。
  • 安全：就算有人黑进他的系统，最多拿到他的手机号和一些外交政策摘要；而他放进去的都是已经公开发表、他本人表态过的内容，“拿走我的系统，它生成的还是新加坡的外交政策”。只放公开材料、让系统经得起审视，是他处理安全的一种方式。他也提醒，商业竞争、国家安全、网络安全和大国博弈会影响 AI 的可得性和扩散速度，这是另一场值得深谈的政治话题。

政策目标

他相信在边缘部署（deployment at the edge）。因此公共政策目标是工具的民主化，路径必须是去中心化、自下而上。他引用副总理颜金勇在经济战略检讨委员会上的话：新加坡不太可能站在模型研发的前沿，但可以站在大规模部署的前沿。他说自己今天来，是因为这场大会是 65 Labs 不到三个月前才组织起来的，组织者都不是全职在做，这就是他相信未来被创造出来的方式。

03. Gavriel Cohen（NanoCo，NanoClaw 作者）：NanoClaw 的安全设计与自动审 PR 的 Agent 工厂

直播位置 1:10:04–1:24:00

他开场说，他的 Telegram 里有一个 AI 助手，连着他的邮箱、日历和通话记录，能读邮件、发会议邀请。演讲结束时他会让全场所有人随便和它聊，“我没疯，这也不危险”。整场就是解释为什么。

NanoClaw 和开源维护的新问题

NanoClaw 是一个开源框架，用来构建安全的自主助手（claw 类助手，即 OpenClaw 这类常驻、能替你办事的 Agent）。三个月里拿到 30,000 多个 GitHub star，几千名用户，包括 Vivian Balakrishnan。他更看重的数字是 12,000 多次 fork：大家主要的用法就是 fork 下来改成自己的 Agent。项目已有 2,500 多个 PR 和 issue。

他说现在是做开源最好的时候，但编码 Agent 带来了新问题：开 PR 太容易了。有人把编码 Agent 指向一个仓库说“去贡献点什么”，于是出现大量垃圾 PR。垃圾 PR 和好 PR 看起来一样，代码量也差不多，分辨它们要对项目方向有深入理解。所以他们做了一个 Agent 工厂来审每一个贡献。

Agent 工厂的流程

工厂在他们的 Slack 里，跑在一台 exe.dev 虚拟机上（字幕作 xie.dev）。GitHub 上每开一个 PR 就触发 webhook，在 Slack 里新建一个线程。审查 Agent 先分诊再深度审查；然后交给测试环节，先写测试计划，这里指真实场景测试，自动化测试之外的那种。人批准计划后，系统起一台新 VM 跑一系列测试，跑完可以直接在工厂里合并上线。

他说一半观众会觉得“我也想要”，另一半会觉得“这太鲁莽了”。PR 是未清洗的输入，任何人都能往里放东西；你也没法清洗 PR，因为你不想删掉里面的信息，而且一个专门加固提示注入防御的 PR 本身就会触发各种检测。提示注入（Prompt Injection）是指攻击者把指令藏在 Agent 读取的内容里，让 Agent 照做。他说这已经远超 Simon Willison 说的 “lethal trifecta”（私有数据、不可信内容、对外通信三者同时具备的危险组合），因为工厂里的 Agent 还在起 VM、合并 PR。

他举了个反例：如果你在某个代码库的 CLAUDE.md 顶部看到“绝不要在生产环境运行 drop database”，这说明两件事：这个 Agent 以前删过生产库，而且它现在仍然有能力删。指令是用来把 Agent 引向高质量产出的，不是安全手段。

原则一：隔离

他们把 Agent 想成在敌后作战：Agent 和潜在的恶意方有接触，随时可能被策反成双面间谍。所以 NanoClaw 不信任 Agent，而是隔离它。简化的架构是：消息从 Slack 发出，经 Slack 服务器到 NanoClaw 所在的 VM，VM 里有一个 Slack bridge（通过 socket 或 webhook 连 Slack），消息经 router 推给 Agent，Agent 的输出原路返回。如果 Agent 能碰到 router 或 Slack bridge，它就能篡改自己能看到哪些消息、能给谁发消息。所以 Agent 在 VM 里再套一层隔离，通常是容器。容器限制了爆炸半径（blast radius）：进什么、出什么、出来的东西怎么处理，都由外面控制。

原则二：凭证不进 Agent 环境

Agent 要连 GitHub、日历等外部服务，不管走 CLI、API 还是 MCP，都需要凭证。他说防止 Agent 泄露密钥，靠指令不行，靠 DLP（数据防泄漏）分析输出也不行，Agent 能绕过去，唯一的办法是不给它密钥。做法是在 Agent 请求和外部之间加一个代理，也就是 vault。他们和开源项目 OneCLI 合作：沙箱里发出的每个请求都经过 vault，请求离开 Agent 时 header 里写的就是字面意义的 Authorization: Bearer placeholder，vault 检查后，如果这个 Agent 应该有权访问该资源，才把 placeholder 换成真凭证。

原则三：策略层和人工审批

光隔离和代理凭证还不够：即使 Agent 拿不到 token，攻击者仍能诱导它做敏感操作，比如把攻击者加成 code owner。所以 vault 那层还要加策略，规定 Agent 能访问什么。对最敏感的操作，最灵活的策略是人在回路（human-in-the-loop）审批。

他说用户在 Slack 里看到的“Agent 请求你批准”其实是一个假象。Agent 既不能发起审批，也没有合并的凭证。真实流程是：Agent 通过一个 MCP 工具写出它想执行的 gh 命令，NanoClaw 宿主进程把它展示成一条像是 Agent 发来的消息；你批准后，合并在 Agent 环境之外执行。电汇之类的敏感操作也一样。他的总结是：把工具调用（Tool Call）和工具执行分开，调用发生在红区里，执行在红区外，并在执行前套用策略。

工厂里有一个他们觉得有意思的模式：多个人轮流监督审查、计划和分诊，谁按下批准按钮就用谁的凭证。所以他们 GitHub 上没有一个 PR 是 NanoClaw Agent 合并的，按钮是他按的，责任也是他的。

07. Annie Luo（Google，UX 研究员）：主观决策里值得保留的摩擦

直播位置 2:14:21–2:22:27

她在 Google 做 AI 购物方向的用户研究。前面的演讲多在讲让编码 Agent 更快、摩擦更少，她讲另一类问题：效率不是目标，消费级 AI 产品里有些摩擦要留着。

主观问题和工具性任务不一样

对着镜子问“我穿这件夹克好看吗”，底下其实是“这反映了我想成为的人吗”“这件皮草有点超出我平时的范围，我够胆穿吗，会不会显得太用力”。这些不是 prompt 或搜索词。第一波 AI 擅长去掉摩擦，比如总结文档、订最便宜的机票，这类工具性任务的成功标准很明显。现在 AI 被要求帮忙回答“我穿这个好看吗”“我想要什么样的旅行”，正确答案取决于人、时刻甚至心情，效率不再能判断功能有没有帮助。

她说这时有三件事变了：

  • 人在看到一系列对比之前，不知道自己想要什么。
  • 信任的建立方式不同。第一次见造型师，信任来自开头的闲聊、对你当天穿着的一句评价；如果一上来就给你一排推荐，你不会相信他懂你。
  • 个人决策里的信心，来自“这是我自己拿的主意”的感觉。

例子一：Google Shopping 虚拟试穿

她参与的虚拟试穿功能用一个时尚领域定制的图像生成模型，去年在美国和亚太上线，目前在澳大利亚、印度尼西亚和印度可用。你看中一件牛仔夹克，上传一张全身照（她用的是自己在纽约中央公园的照片），AI 把夹克渲染到你身上和你的场景里。她说它帮你回答的问题是“我穿这个好不好看”。你可以换白色的试试，放在蓝色旁边比较，才发现自己更喜欢白色；也许发现棕色其实很好看。如果最后一件都不喜欢，按工具性指标看什么都没发生，用户没买；但主观上用户收获了很多，她磨练了品味，也知道了“那件紫色裙子不适合我”。

例子二：Google Travel 的地图

“下一次去哪旅行”底下的问题是：想被挑战还是放松，这次想当博物馆型的人还是海滩型的人。订票 Agent 回答不了，人们规划旅行部分就是为了想明白这些。Google Travel 把地图当作可以漫游的地方，用来探索，也用来选目的地。也许你在 Aspen 和 Whistler 两个滑雪地之间看，然后觉得滑雪不对，转去看 Yellowstone 或 Yosemite。聊天机器人可能五条 prompt 之前就把你锁定在滑雪上了，地图界面让你可以改主意。

设计“决定的过程”

08. Jimmy Lai（Vercel，Next.js 负责人）：为 Agent 设计框架，以及什么时候不该用 AI

直播位置 2:40:47–2:59:45 · 英文原题 Shipping what's next

他在 Vercel 带 Next.js 和 React 团队。Next.js 是一个用来做网站的 Web 框架。他给了一个数字：四年前他加入时 Next.js 每周下载量约 400 万，现在约 4,200 万。他说团队功劳当然有，但很大一部分要归功于编码 Agent。过去半年这个变化追上他们的速度超出预期，团队也在想“我们以后还有工作吗”。他的结论是：这份工作一直包括决定哪些任务应该存在、愿不愿意为结果负责，执行只是其中一部分。AI 让执行更快，一天的时间却没变，所以“负责”这件事变得更贵。

一：用户换成了 Agent

2026 年维护框架的怪事是，你设计的对象不再是坐在键盘前的人，而是夹在人和代码之间的东西，以前是编辑器和文档页，现在是一个能访问你整台电脑、可能权限过大的 Agent。他说 Next.js 文档如今约 60% 是以 Markdown 形式被取走的，来自编码 Agent 和各家实验室的抓取，手动点文档的人越来越少。

他说 Agent 是一种“烦人的用户”：照字面读你写的东西，复制示例，运行命令，严格按报错走。流程断了它不会去喝杯咖啡、睡一觉、第二天早上 5 点想出办法，只会一直重试、一直烧钱。这反过来告诉团队哪里还需要人、哪里该优化。

  • 文档从被动资料变成了 Agent 的“圣经”，会被立刻照做。这不只适用于框架，你代码库里的 README、PR 描述、playbook，每一份过时文档都是一颗等着引发幻觉的定时炸弹。最危险的是“略有误导”的文档，缺失的文档 Agent 还能读代码自己弄明白。过去一个过时示例一次误导一个人，现在会在有人察觉前误导几十万个项目；如果错误信息进了训练数据，模型本身就被污染了，他说 Next.js 有些功能确实发生过这种情况。
  • 编译报错也一样。Next.js 里有一条报错写着“这是 Next.js 的 bug，请开 issue”，他说在今天这算是一种罪过，因为他从没见过 Agent 去给 Next.js 开 bug 报告。银行网站要走十步才能转账，这类问题以前就存在，Agent 让它更突出。
  • Agent 也是检验设计的好办法：它没有 Stack Overflow，也没有 Twitter 上流传的经验，API 设计差、命名差，它马上卡住。
  • 系统要尽可能显式。别出现那种什么都不说的 500 状态码。Agent 将来会在后台为每个人被动运行，你的系统也要能被被动地修复。所以要在代码库里写清楚“可靠”“快”“安全”对你意味着什么，Agent 才能自主运行并交付修复。

二：团队内部怎么用 Agent

他说过去半年业界进入了一种“精神错乱”阶段，人人都想把世界上所有东西都做一遍，他自己圣诞节期间靠 Opus 也干了不少。过了那个阶段，他意识到真正的工作是品味和判断，Agent 适合帮你处理判断周围的一切：快速调研、把一团乱的排查变成整洁的文档和 spec。

工程师最宝贵的是专注时间。他引用了一项常被提到的研究：被打断后平均要约 30 分钟才能回到心流。他自己的教训是：强迫自己别再和 Agent 聊天。同时开十个对话会带来持续的多巴胺，但瓶颈在你自己。现在下功夫把 prompt、评测和护栏准备好，避免事后反复纠正 Agent，才能扩展到后台跑上百个 Agent。

三：知道什么时候不用 AI

他说这可能是全场最重要的一点。有人跟他说，过去六个月像是这辈子最累的五年：每周都有新模型、新 demo、新功能。本能反应是跟着生成更多代码、交付更多功能来压过竞争对手，但做了十年开发者工具，他知道结果是在“速通技术债”。过去半年交付的 demo，现在你得处理可观测性、定价、可靠性。

  • 你可以花一个周末和一堆 token fork 一份 Next.js，但 fork 框架就要负责它的一切。最极端的例子是安全。去年他主导了对 React2Shell 这个严重漏洞的响应：Next.js 发布多年，他们仍然要为几十万用户修复。一年后你自己造的 meta-framework 出了事，你真的想管吗？
  • 他说最近每个月都有大量漏洞被披露，因为 AI 让发现漏洞容易多了。收到安全补丁看起来像软件不安全，其实说明系统在正常工作，有人报告了。自己造的框架得不到安全研究者的关注，攻击者发现你跑的是自研栈，会在你不知情时下手。这是开源重要的原因：大家一起站在稳定的地基上。
  • Vercel 有句话叫 “you can just ship things”，靠这个做出了很多好产品。今年起他们也开始反过来做：用 AI 删东西。功能变得这么便宜，你一小时能做的竞争对手也能做，拉开差距的是专注。他宁愿慢下来，想清楚产品的差异在哪里。他说这样做是为了保护持续交付的能力，并不是叫人别交付。
  • 他在 Meta 工作时见过“非我所创”综合症（not invented here），人们把能重做的库都重做一遍，他说 Meta 内部一度有三个版本的 React Native。现在这个问题会落到每个人身上。

他的回顾：为 Agent 构建时，多想想 happy path 之外的情况，用户不靠自己写 prompt 能不能完整用你的工具，文档、报错和 CLI 要定义清楚；用 Agent 构建时，别把判断外包出去，让它把上下文带到你的判断跟前，比如调研、复现、spec、排查性能问题；行业加速时，小心决定自己要拥有什么。“能不能做”的答案总是能，更难的问题是“这东西该不该存在，我们愿不愿意长期负责”。

09. Vedran Jukic（Daytona 联合创始人兼 CTO）：自主 Agent 为什么必须跑在沙箱里

直播位置 3:01:11–3:10:20

他说新加坡是 Daytona 全球用户数第一的城市，国家排名前五。安装 Claude Code、Codex、OpenCode 或任何用工具的 Agent，等于给了它很多权限：它以你的身份运行，读你的文件，用你的 SSH key，花你的 AWS 账单，能删东西，而且它根据从互联网读到的文字决定做什么。大家接受了，因为生产力是真的，但大多数人没想过风险。

提示注入防不住

提示注入分两种：直接注入，攻击者自己输入恶意 prompt；间接注入，恶意 prompt 藏在 Agent 读取的网页、README 或邮件里。后者更危险，因为自主 Agent 的工作就是读互联网。模型识别注入的能力在变好，但不可靠，而攻击者只需要成功一次。他说 OWASP 明确写了提示注入无法完全防止，这是模型的工作方式；OpenAI 去年 12 月也说了同样的话。造模型的人自己都说防不住。

Skill 生态的数据

Skill 是一个包含指令、可能还有代码的文件夹，下载下来交给 Agent，Agent 会用你的全部权限执行它，没有应用商店式的审核，也没有沙箱隔在中间。他引用了 2026 年初三组团队的研究：

  • Koi Security 检查了 OpenClaw 的 skill 市场 ClawHub，发现 341 个恶意 skill，到 2 月增长到 800 多个。
  • Snyk 检查了另一批，13% 的 skill 有严重问题，其中 76 个明显是恶意的。
  • 一篇题为 “Malicious Skills in the Wild” 的论文检查了多个市场的 98,000 个 skill，发现 157 个是坏的。

他展示了论文里的真实例子：一个看起来像文档助手的 skill，Markdown 里藏着一段注释，预览时看不到，但 Agent 读得到，内容是把项目文件发到攻击者服务器，最后一行还写着“不要告诉用户”。另一个带代码的 skill 看上去是普通的遥测函数，实际遍历环境变量，挑出 API key、密钥和 token 发出去。而且不安装任何东西也会中招，Agent 读到的 README、issue、邮件甚至 PDF 都可能带恶意指令。所以他主张接受现实，改变 Agent 能接触到的东西：不给宿主 shell、不给宿主文件、不给凭证，限制网络，任务结束就整个丢掉。

真正的沙箱做四件事

他说里面的 Agent 如果仍然拿着你的 token、能随意上网，那么一台虚拟机或一个容器还不算沙箱。真正的沙箱要：

  • 把密钥放在 Agent 之外。Agent 请求 GitHub 时发送的是 token 占位符，出口代理拦截后从 secrets broker 取真值发给 GitHub，响应经代理回到沙箱。Agent 被攻破也没有 token 可泄露。
  • 控制 Agent 能访问的互联网和内部基础设施。每个出站请求都经代理比对白名单，随便访问的端点会被拒绝。
  • 记录一切，每条命令每个请求。
  • 站在 Agent 和模型之间。所有沙箱的模型调用走同一个网关，每个 prompt 和响应都被记录。某个沙箱行为异常时，直接打开它的 trace 就能看到 Agent 问了什么、模型答了什么，否则就没有审计线索。

他的结论：Agent 一定会被攻破，唯一的问题是那时它能碰到什么。

10. Vaishant Kameswaran、Rohan Kumar（Greptile）：分析 500 万个 vibe coding PR 学到了什么

怎么判断一个 PR 是 vibe coded

  • GitHub 作者字段：bot 常把自己加成 commit 共同作者，信号确定但稀疏，只能识别约 1% 的 PR。
  • PR 描述：bot 常在描述里注明自己参与了，能识别约 20%。
  • 分支名：Codex、Cursor 创建的分支名带自己的前缀，人一般不会这样命名。

三者合起来，4 月提交的 PR 里约 27.6% 有强证据表明是完全 vibe coded，而且从多文件 Agent 出现以来这个比例一直快速上升。

三个质量指标

  • 回滚率（revert rate）：PR 被回滚通常说明它在生产环境造成了破坏。按作者拆分，有些 Agent 的回滚率低于人类基线，主要是 Claude 和 Codex。按改动文件数拆分，PR 越大，AI Agent 的平均回滚率比人类低得越多。
  • Greptile 评论的严重度：Greptile 审查时像人一样留评论，并按 P0 到 P2 评级，P0 是会导致破坏的严重问题，P2 是小毛病（nit）。多数 bot 产生的严重 bug 平均少于人类，想避免搞垮生产环境的话 bot 反而更可靠。但看整个严重度分布，只有部分 bot 在所有级别上都少于人类。
  • 合并前的审查轮数：一轮是 bot 开 PR、人留评论、bot 修改。这同时反映第一次写得好不好，和吸收反馈时会不会引入新 bug。Devin 和 Claude 在这项上最好，平均比人类更快合并。

他们的结论是没有稳定的赢家，取决于你量什么。所以更该问的是 bot 怎样产生 bug，和人有什么不同。

Bug 的“形状”

他们画了一张热力图，按 bug 类型比较每个 bot 和人类基线，红色表示 bot 更常犯，蓝色表示更少。各家差异很大：Cursor background agents 更容易犯 N+1 查询错误（循环里每次单独查数据库，导致查询数暴涨）；Claude Agent 更容易漏掉租户检查（missing tenant check，多租户系统里没校验数据属于哪个客户）。没有一个 bot 在所有类型上都赢。

他们的看法是：bot 的 bug 和人类的不一样，未必更好或更差；而 bot 让代码产量大很多。质量大致相当、形状不同、规模更大，所以 AI 编码 Agent 是好的，前提是你清楚它们会犯哪类错。代码验证系统也要跟着扩展。Greptile 会研究各个模型的强弱，组合使用来抓更多 bug。

11. Yuntong Zhang（Sonar 研究顾问）：代码质量流水线里的 AI Agent，以及怎样可靠地评测 AI 代码审查

直播位置 3:21:10–3:31:30

她是 Sonar 的研究顾问，也是新加坡国立大学（NUS）的博士最后一年学生，声明观点仅代表个人。她把代码进入仓库的流程简化为三步：Agent 写代码；Agent 审代码（因为代码太多，现在几乎都由 Agent 审）；人决定是否合并。她讲两部分：写代码环节 Sonar 怎样构建并保护它的修复 Agent；审代码环节怎样更可靠地评测 AI 生成的审查。

SonarQube Remediation Agent

SonarQube 是广泛使用的静态分析工具，扫描代码找问题。在 PR 上发现问题后，可以调用 Remediation Agent 自动生成补丁：它在你的 PR 之上再开一个 PR，说明修了哪些 SonarQube 问题，按 hunk 给出改动，并解释每处改动为什么能修复问题。目前是公开测试版。

她重点讲生产环境里的安全。沙箱很重要，他们部署时也用了，但她主张纵深防御：沙箱之外，在 Agent 内部和 Agent 交付之后也加安全层。

  • 受约束的工作流：Agent 只做修 Sonar 问题这一件具体的事，所以没有自由终端，不能随意上网或执行任意命令。
  • 除了 MCP 和 skill，代码库本身也是攻击面。恶意的开源贡献者可以在 PR 里注入恶意命令。所以运行时他们把代码里的这些命令替换成别的标识符，Agent 完成后再换回来。
  • 供应链攻击：比如有人在 pip 上抢注名字相近的包（typosquatting），他们做了很多导入守卫，防止 Agent 引入恶意库。
  • 交付后的验证：对 Agent 生成的补丁再跑一遍 SonarQube，发现回退或安全问题就带着上一轮的反馈让 Agent 重试，只有通过质量门（quality gate）才发给开发者。

怎样评测 AI 代码审查：c-CRAB

AI 审查工具很多，怎么知道哪个适合你的场景？常见思路是拿历史 PR 上人类的审查意见做参照，看 AI 能不能抓到同样的问题。现有方法各有缺陷：文本相似度不行，同一个问题可以有很多种说法；位置匹配只看评论落在哪一行，不看语义；LLM-as-a-judge（让一个模型判断两条评论是否说的是一回事）有时有效，但很难判断是否可靠。她想要一种确定性的检查办法。

他们做了一个基准（字幕作 “Crap”，名称未能确认），核心想法是把每条人类审查意见变成一个可执行的测试。例如人类审查说某段改动在某些输入下会抛异常，应该安全地返回 false，他们就写一个测试：意见被落实则测试通过，否则失败。评测时，把 PR 给 AI 审查工具，让它评论；再让另一个编码 Agent 按这些评论改代码；最后跑这批测试，看通过多少，就知道 AI 抓到了多少人类指出的问题。

  • 结果数据是 2026 年初得到的，各工具的具体分数不重要，工具和模型每天都在变。她强调的是：所有 AI 审查工具加起来，也只落实了人类审查意见的 41.5%，不到一半。
  • 但这不是全部。AI 也会指出人类没发现、但有价值的问题。他们把人类和 AI 的评论按类别归类：安全、效率、兼容性、健壮性、测试，一直到文档和可维护性。AI 在健壮性和测试上表现好，会让你多写测试、指出边界情况，这和她个人经验一致。人类在可维护性和设计上强得多，会说“改这么多以后这段代码就没法维护了，应该换种组织方式”，因为人对代码库有更多上下文。

她的建议：目前 AI 和人一起审，AI 做第一层，人重点看 AI 不擅长的那几类。两个主题各有一篇论文，现场放了二维码。

13. Max Buckley（Exa AI 知识研究负责人）：2025 年 11 月 24 日，之后会怎样

直播位置 3:41:49–3:53:00 · 英文原题 November 24th, 2025: What Comes Next

他是 Exa 的知识研究负责人，正在筹建苏黎世办公室，之前在 Google 工作。他说这是一场“存在主义”演讲，不讲 Exa。题目里的日期不是笔误：2025 年 11 月 24 日是 Claude Opus 4.5 发布的日子，他认为这一天会被记作事情发生变化的一天。

社会的博弈论在变

他的论点是，生成式 AI 正在改变社会底层的博弈论。现有制度建立在“某些事有成本”的假设上，成本让系统运转；成本被拿掉，围绕它的系统就可能失灵。

历史例子是 ChatGPT 对“工作量证明”的冲击。很多制度要求人付出努力来证明自己付出了努力，学校借此让人学习，公司借此筛出真正想来的求职者，人们借此判断可信度。现在他收到一封写得很好的邮件或 LinkedIn 消息，不会觉得对方口才好、用了心，只会觉得用了 LLM；带错别字的，要么是让模型故意生成错别字，要么是手动加的。他说这件事你没法选择不参与：大学即使禁止用生成式 AI，学生也只是把 “delve” 删掉、把破折号去掉。

编码里正在发生同样的转变

八年里从 tab 补全一行，到补全函数、生成文件，再到编码 Agent：给一个高层 prompt，它跑几分钟到几小时，构建、测试、验证完再回来。他说模型自己都没意识到这个变化：给 Claude 一份大 spec，说“实现这篇论文”，它会估计要 12 周；把 Markdown 粘到 Claude Code，跑了 30 分钟就做完了。他说这个估计本身没错，在 Google 交给一个初级工程师确实要 12 周，包括各种 check-in 和迭代。

他还讲了“IT 素养”：过去很多人怕电脑，因为电脑极其死板，少个分号就报错。现在编码 Agent，或者说电脑上跑着的任何 Agent，给电脑加上了自然语言界面。普通人只剩一道门槛：怎么打开终端、怎么启动 Claude Code。之后就能用自然语言让它教自己配网络打印机、截屏、排查摄像头。他认为“编码 Agent”这个说法低估了它的潜力。开源是下一个：过去开源意味着对工程师开放，现在意味着对任何识字、有电脑的人开放。

稀缺经济学的假设要变

去年底之前的假设是：软件开发贵，会写代码的人少、时间值钱，每个功能都有机会成本，组织里有一整套角色（各种 PM）争论做什么、砍什么、修 bug 还是加功能。开发也慢，小功能几小时到几天，大功能几周到几个月，大的重构多人几年。路线图按季度排，因为工作本来就是按季度完成的。他在 Google 时，每人一个季度分到四五六条任务，通常完成 70% 到 80%。销售提交几百条需求，项目经理筛到 30 条，工程经理划线做前 16 条，再分给工程师。所有流程、习惯和组织架构都基于这些假设。

  • SaaS：以前一群好工程师理论上也能做出 Workday 的竞品，问题是你愿不愿意投几个人、几年、几百万美元做个基础版，再去说服客户换。现在容易多了，护城河不再是代码，而是品牌和渠道。他认为 ML 和数据的护城河会撑得更久，因为边界更模糊，比确定性软件难逆向。
  • 不必再靠专业判断把 30 个点子砍到 3 个：可以 30 个都做，做好评测和基准，看哪些值得，其余回滚。因为没花三个月，晋升材料也不靠它，回滚时不会舍不得。
  • 软件供给会爆发。他引用 GitHub COO 最近的推文：按当前速率，GitHub commit 数同比增长 14 倍，而 2025 年已比 2024 年增长 4 倍。
  • 新工具的边际成本接近零：标数据、调 bug 时，可以花 20 分钟让 Claude 做一个一次性的定制 UI，可能让你效率提高十倍，因为人擅长看视觉信息。以前没有哪个季度能为这种小应用立项。
  • 瓶颈转向市场推广和代码审查：你能做一切，别人也能，大家会更激烈地争夺注意力。

现在值得投资什么

  • 统计学。在 Google 这样的大公司，一直有专门团队做实验评估工具，其他工程师直接用。现在每个人都要以各种方式评估东西：性能 profiling、基准、A/B 测试、用户行为指标，统计应该成为更普遍的技能。
  • 想法和品味：决定做什么变得更重要，然后快速迭代。
  • 知识的价值在变：从精通具体语法的深度技术专长，转向知道有什么、何时怎样用。笼统地 prompt 模型会得到笼统的结果，用对词会解锁它的能力。他的例子：说“帮我 benchmark 一下这个改动”，模型常常 n=1，跑一两次比谁快；说“用统计方法”，它就开始讲 p 值、t 统计量、大样本。

他的结尾：问题不再是能不能做出来，而是什么应该存在。

14. Mark Doyle（Stripe，编码 Agent 平台工程师）：Minions，从 prompt 一次直达 PR

直播位置 3:54:00–4:08:00

他在 Stripe 负责编码 Agent 平台，基本上和用 Agent 写代码、和整个软件工程生命周期有关的事他都参与。他先交代约束：全世界约 2% 的 GDP 经过 Stripe 处理，所以即使他们想站在 AI 的最前沿，对用户、客户和全球经济也有维持质量和安全标准的义务。

数字：100% 的 Stripe 工程师在写软件的某个环节用 AI，91% 每天用 AI 合并代码；过去一年完全由 AI 生成的 PR 数量增长了 500%。

One-shot Agent 和 co-pilot Harness 的分工

Stripe 也用 Claude Code、Codex、Cursor，他们把这些看作 co-pilot 式的 Harness：工程师和它坐在一起反复迭代。One-shot 编码 Agent 指从一条 prompt 或一个 Slack 线程直接到 PR，中间不需要任何交互。适用场景是工程师大概知道 PR 应该长什么样。他说让工程师同时开一堆终端会话、连着不同机器上的 Agent 来回切换有点浪费，不如先和 Agent 做一次规划，然后启动 one-shot，直到代码审查前都不用管。目标是把建开发环境、建分支、开 PR 这些活也交给 Agent，写代码只是其中一部分。

他演示了一个例子：他在排查 Stripe 一个 MCP 工具的问题，在 Slack 里问 Agent 可能是什么原因。Agent 读了代码和文档，指出问题，修复只是三个字符的 diff，谁都能改。这时他不想再花十分钟建分支、起 Agent、重新解释问题、复制上下文，只想说“去修”，等 PR 回来让自己或同事批准合并。之后 minion（Stripe 对 one-shot Agent 的叫法）回消息说完成了，请去看代码，整个过程开发者不在回路里。

Devbox：Agent 的家

Stripe 工程师不在笔记本上写代码，而是在远程开发环境 devbox 上写。原因是 Stripe 的 monorepo 是世界上最大的 Git 仓库之一，接近 3 亿行代码，克隆下来约 90GB，代码生成也很慢。他们有一个预热好的 devbox 池，要新分支马上就有。他说多年投资 devbox 很幸运，现在它们成了 Agent 舒服的家，工具齐全。它们和业界常见的轻量沙箱不同，是大机器：很多核、64 到 128GB 内存。每个 minion 有自己的 devbox，安全上是隔离的，同时也是写代码的好环境。

Minion loop

  • 先收集上下文：Slack 线程、里面提到的 ticket、PR、同事补充的信息，交给一个 analyzer Agent，它判断应该把 Agent 指向代码库的哪一部分，并把任务总结成 prompt。
  • 进入 minion loop，保证一定产出 PR、Agent 不会半路停下。编码 Agent 就是普通的编码 Agent，像 Claude Code 或 Codex 那样推进一轮，然后跑 lint、测试和类型检查。
  • 这里和 co-pilot 不同：结果不回给人，而是交给一个 LLM judge。Judge 只拿到原作者的 prompt 和当前 git diff，回答“任务完成了吗”。它的上下文不会被编码 Agent 的对话和各种“为什么停下、为什么做不到”的借口污染。
  • 完成了就开 PR，通知工程师审查。没完成就交给 diagnostic Agent，它看 judge 的输出、编码会话和原始 prompt，判断原因，比如测试没过，或者做错了：建了 API endpoint 却没接前端，这是编码 Agent 常漏的事。诊断结果放回循环，并且尽量简短，避免撑爆上下文窗口。循环一直跑到得到像样的 PR 为止。

目前 Stripe 约 65% 的 minion PR 一次合并，无需人工干预，模型越好比例越高。没成功的，工程师可以在网页界面继续引导对话，也可以在 VS Code 或终端里直接打开 minion 所在的 devbox 接手。Stripe 每周用 minion 合并约 3,000 个 PR，小问题和工程师能提前给足上下文的较大任务都适用。

三条经验

  • 能确定性就确定性。他们的各个 Agent 都有很详细的 prompt，代码库里有几千个 CLAUDE.md 和 AGENTS.md，它们很有价值。但如果你在 loop 的 prompt 里反复写“请在 commit 前跑测试”“别在自己跑测试前就推上去跑昂贵的 CI”“commit message 要按某种格式”，甚至用全大写去说服 Agent，那就该改成确定性的步骤。和 Agent 争论是一种代码坏味道，涉及安全时尤其如此。自己的个人工作流靠这些大写的上下文文件也许没问题，几千名开发者跑几千次 minion 时不行。
  • 开发者工具比以往更重要。Stripe 一直在开发者工具上投入很多，比如开源的 Sorbet，它是 Ruby 的静态类型检查器，相当于 JavaScript 的 TypeScript。现在工具不好，损失的不再是工程师每周一小时，而是几千次失败或变慢的 Agent 循环。所以他们加倍投入 linter、formatter、静态分析这些非 LLM 的东西。
  • 在 Slack 上构建。在 Slack 里 @devbox 或 @minion 就能启动，非工程师也能用。工程师看到同事公开地 @ minion 去干活，就会学着用，这对让大组织接受 AI 很有帮助。

他的团队在招工程经理。

15. Li Hau Tan（Simular）：电脑操作 Agent，从玩纸牌到操作 ERP

直播位置 4:08:30–4:20:00

他问全场每天移动光标多少小时。几个月前他们追踪了一群朋友，有 AI 工程师，也有医生、行政和会计：有人每天在触控板上移动手指超过 5 小时，超过清醒时间的三分之一，不是在创造或思考，只是在点击、滚动、翻菜单。他说 1981 年的 PC 让人摆脱了文件柜和纸，40 年后人们只是把一种手工劳动换成了另一种。下一步是电脑自己操作：看屏幕、理解任务、去做。Simular 把这叫作自主电脑（autonomous computer）。

他是 Simular 的技术人员，做自主电脑的基础设施。去年 12 月，他们的研究 Agent Agent S3 在 OSWorld 上超过了人类水平，OSWorld 是电脑操作 Agent 的标准测试。

演示和定位

演示里左边是聊天界面，LLM 在理解任务：玩纸牌接龙，看屏幕判断下一步，然后移动鼠标拖牌；右边是它运行的机器。等了一会儿，它把一张牌从左拖到了右。他说这只是一个规则清楚的应用，真实工作里有邮件、Slack、表格、PowerPoint、QuickBooks、SAP，以及公司不肯淘汰的遗留系统。有 API 的，去年的 API/CLI Agent 和函数调用已经解决；在浏览器里的，有 browser use Agent；剩下的桌面应用、遗留系统和专有工具没有 API 也不在浏览器里，唯一入口是屏幕，这就是电脑操作（computer use）。他们的自主电脑把 API/CLI Agent、浏览器 Agent 和电脑操作 Agent 组合起来。

挑战一：可靠性

对用户来说可靠就是每次都能用，需要两点：grounding（看清屏幕并精确操作）和 consistency（重复一百次都一样）。

  • Grounding：起点是像盲人用的屏幕阅读器那样读无障碍树（accessibility tree），它是界面上每个元素的名称、类型、状态的结构化地图。但很多应用的树不完整，按钮藏在菜单和下拉里，元素动态出现，有的应用几乎没有树。所以他们用专门的视觉模型补上，一个读文字，一个找按钮和元素，树有缺口时用视觉填补。
  • Consistency：研究里常用 pass@k，即给 k 次机会至少对一次就算通过，比如 k=5、第三次成功算通过。用户要的是他所说的 pass^k，连续 k 次都对。比如给 100 个销售线索各发一条个性化 LinkedIn 消息，如果每一步都由 LLM 驱动，同一任务跑 100 次可能有 100 种行为。
  • 他们的办法是神经符号方法：LLM 观察屏幕、推理该做什么，然后写成程序代码去执行，相当于“大脑写菜谱，机器照着做”。第一次需要 LLM 推理，之后第二次到第一百次直接重放代码，不需要推理，几乎零成本。代码用的是他们为电脑操作设计的领域专用语言 Simulang，可读、可改，他说这周向开发者开放。

挑战二：信任

能在电脑上做任何事的 Agent 可以发邮件、删文件、下单，误解一条指令或产生幻觉就可能酿成灾难。他说这已经发生在 Meta 的 AI 对齐总监身上。Simular 把护栏做成和规划 Agent 分开的独立系统：决定做什么的和判断是否安全的不能是同一个，模型不能既当运动员又当裁判。规划模型糊涂了，护栏系统也会在危险发生前拦住。

挑战三：可扩展性

Simular 的使命是把用户生产力提升 100 倍，办法是 100 台自主电脑，不是长出 100 根手指。不是人人都愿意买 100 台 Mac mini 来配置，所以他们做基础设施：注册 Sai（他们的产品）后会给你起一台机器，你可以装应用、按自己的习惯配置，然后让 Sai 接手；能起一台就能起五台、一百台，一台跑回归测试，一台通话后更新 CRM，一台跑报表，全部并行。

16. Ryo Lu（Cursor 设计负责人）：设计 Cursor 3，让做软件重新像玩

直播位置 5:33:01–5:54:10 · 英文原题 Designing the next Cursor

午休后的第一场。主持人说她自己 2024 年中作为完全的非工程师，就是用 Cursor 学会写代码的，那时 Cursor 只有 tab 补全和行内编辑，还没有 Composer 和多文件编排；Cursor 的很多设计模式后来成了各家编码 Agent 的标准。Ryo 说他要讲三件事：Cursor 怎样把设计师和工程师带回“做软件像玩”的起点，用 Cursor 设计 Cursor 怎样让设计流程变得流动，以及他们对未来的设想。

设计和工程原本是一门手艺

他说最早的软件设计和工程是同一件事，想出软件的人也是做出软件的人，材料就是代码本身。例子是 Bill Atkinson：早期 Macintosh 团队成员，写了 2D 图形引擎 QuickDraw，设计并编写了 MacPaint 和 HyperCard，发明了“蚂蚁线”选区，用 68K 汇编做像素级精确的 UI。还有 Alan Kay：在 Xerox PARC 发明了 Smalltalk 和 Dynabook 构想，“预测未来的最好方式是发明它”，他写代码做出能运行的系统来证明想法。他问：他们是设计师还是开发者？那时这个问题没有意义。

后来，尤其是过去十年，行业把自己“fork”成了专门角色：设计师出 mock，工程师实现 mock，PM 写 spec、开会。承诺是专业化会更快，现实是更慢、离代码更远。工具也分家了：工程师留在终端和 IDE（Vim、VS Code、Sublime），代码仍是事实来源；设计师从 Photoshop 的位图到 Mac 专属的 Sketch，再到浏览器里协作的 Figma，mock 很漂亮但不是真的；PM 和协作散落在没人想更新的 Jira、写 spec 的 Google Docs、Notion 和 Slack 里。“一切都 SaaS 化”和各种专用工具让鸿沟更大，线性交接成了常态，“对齐 Figma”成了目标，从想法到上线要几周。设计师碰不到真东西，工程师没有 ticket 就不能探索。他说我们把这叫进步，其实是用流程换掉了手艺，用协调换掉了构建。

现在 Agent 在写代码，你可以通过提问、指挥、打磨来设计，代码重新成为材料和事实来源。手艺变成知道该做什么、它应该是什么感觉，用真实材料和其他人、其他 Agent 一起把它做出来。

Cursor 3：从以文件为中心到以 Agent 为中心

Cursor 一开始从 VS Code 继承了大量复杂度。过去一年 Agent 成了人们用 Cursor 写代码的主要方式，这些遗产对重度使用 Agent 的程序员成了负担，大量以文件为中心的视图不再有意义；新手打开就被一堆吓人的 UI 和概念淹没。同时，工作从操作本地文件状态，转向多个 Agent 在不同项目上运行、越来越多跑在云端，层级要围绕 Agent 和它们的环境重组。在 VS Code 上硬改布局会产生大量 UI 分叉、边界情况和坏状态，跟不上变化。

他说做 AI 工具有两种哲学：

  • 黑箱：你输入需求，AI 在你看不到的地方做事。成功了你什么也没学到，跳过了思考；失败了你不知道为什么，新手只会不断烧 token。看不见、插不了手、改不了，要么批准每一处改动，要么放弃。
  • 玻璃（glass）：一开始很简单，但想看就能看到更多。Agent 的输出流式出现，代码在后台运行，你可以中途纠偏、随时停下、亲手改那 2 像素的 padding。不必读每处改动，但永远可以。老手让 Agent 跑，在合适的时候审查和修改；新手通过提问、构建、折腾，看到系统更深的一层，学到新概念。

他认为 AI 越强，玻璃越重要：跑几个小时的自主 Agent 需要对人可读，人才能监控和插话；多 Agent 系统需要可检查、持久、由人划定边界的计划；人和 Agent 需要共享空间和可塑的界面。Cursor 选择了玻璃：每个 Agent、它的动作和产物都可见可改，计划可以塑形，Agent 状态可以检查，“零隐藏魔法，无限控制”。

  • 起步简单：现在可以关掉编辑器用 Cursor，不自动打开文件，像一个放在其他工具旁边的助手。
  • 随用随展开：在规划、设计、执行、审查等不同阶段，界面会变形来适应你。老手可以带多个 Agent 快速推进、审查、精确修改；设计师可以画草图，在浏览器里看到运行中的代码，标注和微调每个细节并立刻看到反馈；产品人员可以在一个完全可交互的协作文档里，和了解整个团队上下文的 Agent 一起规划、比较方案和取舍。
  • 核心保持简单，通过 plugin 和 skill 等可扩展概念定制；尊重用户习惯，从不强迫剧烈改变，不拿走任何东西，只是给愿意的人展示一种更简单的新方式。

用 Cursor 设计 Cursor

他说新界面的设计大约一个月就完成了，起点是年初一个随手做的原型。他和 Lee、Rob 一起启动了 Baby Cursor 3。Baby Cursor 是他们的原型环境，大家可以 fork、探索想法、分享。设计 AI 工具时会遇到大量非确定性的情况，静态 mockup 抓不住细节，必须亲身感受。

  • 新版原型是基于 Cursor CLI 的完整可用 Electron 应用。他设计了一个布局架构，支持一到多个 Agent、一到多个项目、零到 N 个内容标签页和分屏，适配任何空间限制。在 Figma 里做这些动态状态可能要几个月，而且没有在代码里玩的手感。高层的信息架构和流程大约一周就定了。
  • 传统设计工具里很容易复制画板和状态，结果是一堆状态快照，看不到一个整体。Baby Cursor 3 内置了 feature flag 系统，设置存为文件，既能探索大的架构分叉，也能探索每个小细节的排列组合，看它们怎样组合在一起。
  • 每天玩原型会暴露影响深层架构的约束。例子：在 Agent 之间切换时布局怎么变？右侧标签页跟着 Agent 走，按工作区或环境划分，还是像 VS Code 那样各自独立？这很难用文字解释，但现场一感受就清楚。
  • 他们把 Baby Cursor 发给全公司玩，工程师 fork 下来加入自己的想法，他再汇总迭代。原型帮他们回答了：真实使用下哪些布局合理，暴露哪些默认值和自定义选项，怎样让复杂显得简单，多少控制该可见、多少该隐藏，渐进披露（progressive disclosure）怎样起作用。
  • 他从原型代码反推出一份高层 spec，记录每个选项和细节；视频和截图成了新 Cursor 的 mock。RFC 上经过 33 个长讨论线程后开始落地。
  • 工程团队受原型速度启发，决定从零重写整个 UI：用 React 重写，建全新的设计系统组件库，花了两个月。期间他继续在原型里做侧边栏分组、输入框定制、预览等细节，然后第一次回到 Figma，玩了最终没上线的 liquid glass 效果和各种视觉细节。
  • 差不多成形后，他们用新 Cursor 构建它自己，把还别扭的地方都 dogfood 一遍。设计师也回到代码里打磨组件、图标、颜色、主题、vibrancy、动画，这些是“模型看不到的小细节”。设计流程不再线性，哪个工具最适合打磨手艺就用哪个。
  • 3 月底发布 alpha，和内部及外部真实用户建立快速反馈循环，首版重点是性能和质量。

Cursor 3 发布后他们又做了 Baby Glass，下一代原型环境，用一个原型可视化 Cursor 从当前到未来的样子。它基于新设计系统，用的是 Cursor 3 的真实组件；回到了 Web 而不是 Electron，因为分享状态和链接很方便，别人点链接就能给反馈。feature flag 和版本系统也改进了，可以展示从当前生产状态到未来里程碑的每一步。交接流程也更好，Baby Glass 原型可以变成工程师在真实代码库里继续开发的第一个 PR。里面甚至有桌面、壁纸、主题，还有一个生成 mockup 和视频的工具，他们打算用于官网演示。

对未来的看法

  • 更协作：人和成队的 Agent 在同一上下文和工具里工作。Agent 承担更大的目标时，人和 Agent 共享空间更重要。人人都在成为 builder，不同学科的人可以用同样的 Agent 配置、工具、知识和产物朝同一目标工作。
  • 更可定制：界面和工具适应人，而不是人适应工具。
  • 更自主：Agent 处理重复工作流，比如 bug 分诊、发布说明、安全和代码审查；人定义系统和边界，设计验证循环、定义什么是对的。
  • 更有野心：别只是做更多东西、制造更多 slop。用省下来的时间深入思考最简单的抽象，为用户做对的东西。

他的结束语是：“No black boxes. Stay glass.”

执行变便宜，协作成了瓶颈

他说今天的 AI 工具专注于让个人快 10 倍，更难也更有意思的问题是能否让一群人一起快 10 倍。他引用了 GitHub 研究工程师 Maggie Appleton 在另一场 AI Engineer 演讲里的说法：执行变便宜后，协作和对齐成了瓶颈。决定做什么、不做什么比以往更重要，探索、规划、对齐的方式不变，团队进度就会卡住。他说这也呼应了 Ryo 刚才讲的。

多人场景里的 Agent 需要“具身的在场感”

他说大多数 AI 工具让 Agent 替我们做该自动化的任务，这没问题；但在人和 Agent 互相即兴发挥的协作探索里，空间要足够宽容，大家可以碰彼此的作品、实时改同一个东西。所以他在 prompt 框里加了 “make edits” 选项，可以覆盖修改，这就带来冲突编辑的可能：比如他要把主题改成中世纪，同时别人在给视觉风格加两层视差。他说这应该被允许，就像 Google Docs 或 Figma。原计划是能看到 Agent 的光标在旁边一起改，Agent 的输出要替换他的修改时会先问他，并展示流式输出让他比较再决定。

他的结论：要让 AI 多人化，必须设计 Agent 的具身在场（embodied presence）：它的表现形式要设定预期，显示它在编辑哪个文档，有自己的文本指针，可视化它的改动范围，以及怎样处理和人或其他 Agent 的冲突。这和今天为人类设计文档或画布里的光标很像。

下一步：多模态

他说多模态是拓宽沟通渠道，让人和 Agent 都能更丰富地表达。三个方向：

  • 真正的多模态模型。他提到 Thinking Machines Lab 几天前发布的研究，他们称为 interaction models，原生多模态、以很细的轮次实时交互。他很喜欢他们的说法：回合制的 AI 像是通过邮件而不是当面和 Agent 说话。他说这比他的演讲酷多了，推荐大家去看。
  • Agent 在更丰富的数字媒介里的具身表现。光标就能通过位置、移动和点击表达很多，就像人通过肢体语言读懂彼此的意图，也要为 Agent 设计肢体语言。
  • 交互模态本身。GUI 已经帮人更直观地表达意图，有几十年经验可用：同时用多点触控、笔和语音，比如 Diana Lu 的一个界面实验；以及在界面里构建多少确定性，比如他参与的 Figma Weave，一个基于节点、生成富媒体的工作流工具。他说这类基于节点的 AI 原生工具把模型和熟悉的 GUI 模式结合起来，给创作探索提供精度和控制。

19. Alberto Taiuti（Reactor CEO）：世界模型、实时视频和生成式软件

直播位置 6:18:52–6:29:15 · 英文原题 World models: a look at the future

Reactor 刚结束隐身期。他先放了一段看起来像实拍或游戏的视频：他在抚摸一只北极熊。他说这不是视频，是在 Reactor 平台上实时生成的，录制时 30 帧每秒，只从一张图片开始，用键盘控制，画面实时变化。他想先让大家知道世界模型已经能做到什么。

他是 Reactor 的 CEO 和联合创始人，此前联合创办 Luma AI 并任 CTO，也在 Apple 做过 Vision Pro，一直喜欢空间、视觉、3D 和实时方向，由此认定下一个前沿是世界模型和实时视频生成。

什么是世界模型

他说今天的文本、音频、图像、视频生成都是被动的：你 prompt 一个图像模型，最后拿到一个文件，生成过程中你不能交互，模型也不能响应外部刺激。未来越来越多的 AI 负载会是实时交互、感知周围世界的，否则没法部署到真实世界。他们对世界模型的定义和很多人不同，有四个特性：

  • 长期记忆，他们称为持久性（persistence）：知道自己之前生成了什么。
  • 实时：你可以戳它、和它交互，它会响应。
  • 因果地思考：记得之前发生的事，并在生成下一步时把它考虑进去。
  • 可交互：人可以影响它，外部的物理事件或互联网事件也可以。

所以可以把它看作一个状态机：理解外部输入，考虑过去，生成新输出。图像和视频模型没有“之前发生了什么”的概念。他说这改变了软件本身：当前一代生成式 AI 生成的是产物，下一代生成的是应用。

用例

  • 机器人：越来越多机器人公司用世界模型替代 VLA 和 VLM，因为它更能感知机器人周围的情况，甚至能在视觉上想象机器人应该怎么做。
  • 虚拟形象和数字人：比基于显式 3D 表示的方法强大得多，因为能适应各种情况。
  • 广告：按用户实时个性化内容，他说这是媒体和广告的圣杯，也会催生新的艺术形式。
  • 仿真：实时运行更精确、更接近真实世界的生成式仿真。
  • 生成式软件，他们最兴奋的方向：屏幕上每个像素都实时生成。他说人和别人定义的、对自己不好用的界面打交道时有很多挫败感，生成式软件可能改变这一点。

他还认为世界模型在通往 AGI 的关键路径上，因为视觉输入的信息比文本丰富得多，能和真实世界交互并理解它的系统才能真正有用地部署。

Reactor 做什么

Reactor 是世界模型的开发者平台。他说世界模型长期被使用难度锁住了，大规模运行要处理延迟、流式传输、超采样（super sampling），Reactor 都替你处理，开发者只写应用代码。前沿实验室和研究机构也可以很容易地把模型部署到 Reactor 上测试、分发，甚至从使用中获得收入。他们已经和主要的世界模型都建立了合作，reactor.inc 上可下载 SDK（字幕作 “reactor.in”）。

最后的演示：他生成了一张 Jensen Huang 在 Nvidia 的图片，然后实时控制他穿着皮夹克在 Nvidia 里走来走去，还有一些“变得有点诡异”的例子。他说这类东西不用世界模型无法实时做到。

  • 多条入口路径都要执行全局限流，防止通过地域套利绕过限额。他们的平台吸引了不少滥用和欺诈，攻击越来越复杂，识别到的滥用指纹在增加，所以限流和监控很重要。
  • 不同时段、不同地区、每周的模型需求都在变，要能快速把任何模型部署到任何区域。他们用声明式的简单 manifest 快速调和（reconcile），合并配置后一两分钟就能在全球任一区域部署新模型，包括 canary 测试和预热。

模型怎样跑到自研芯片上

通常从 Hugging Face 拿开放权重和 PyTorch 参考实现，编译成 Groq 的张量算子方言（基于 MLIR），调度并切分到多块芯片上，用不同的预设，最后编译成在硬件上执行的程序。执行完全由编译器调度，网络也由软件调度，所以每个请求的延迟高度可预测。

企业需求和异构计算

大企业在 2026、2027 年越来越要专用算力，数据驻留仍然重要；模型越大，decode 延迟和单位经济越受关注。即使是 AI 原生公司需求也很分散：有的要一键部署，有的要托管服务，有的要自带模型和权重，有的要自己的推理栈。最后他提到 Nvidia GTC 上 Jensen 宣布的 Vera Rubin 加 Groq 3 LPX 系统，思路是分离式推理（disaggregated inference）：prefill 和部分层在 GPU 上跑，decode（也许是 FFN 部分）在 LPU 类芯片上跑。他认为异构计算会更常见，并需要和编译到这些硬件上的模型生态对齐。

22. Daria Soboleva（Cerebras 首席研究科学家）：在晶圆级芯片上训练 MoE，绕开 GPU 通信瓶颈

直播位置 6:51:20–7:01:52 · 英文原题 MoE at scale: from GPUs to wafer-scale

她是 Cerebras 的首席研究科学家（head research scientist），过去几年研究 MoE 网络，发布了一份 MoE 101 指南，讲怎样高效训练和推理 MoE；目前领导 Cerebras 硬件上的前沿规模训练。之前在 Yandex 做 Transformer，参与了他们部署到生产的第一个 Transformer；更早在 Google 做语音转文字模型。

怎么走到 MoE

  • GPT-3：1,750 亿参数，同时发布了扩展定律（scaling law），模型越大质量越好。
  • Llama 3 系列把模型扩到约 4,000 亿，并在高效利用数据上下功夫。Chinchilla 扩展定律提出模型和 token 预算要一起扩，每个参数约 20 个 token 被认为是算力最优的。
  • 线性地扩模型和数据会很快变得极贵，而大家想在万亿级数据上训练万亿参数模型。DeepSeek-V3 是另一个突破：总参数 6,710 亿，但运行速度相当于 370 亿激活参数的稠密网络。

MoE（Mixture of Experts，混合专家）的做法：Transformer 解码块里有 embedding、attention 和 FFN 层，把 FFN 复制多份，每份叫一个专家（expert），上面再加一个 router 网络，决定每个 token 交给哪个专家处理。加专家能扩大容量，但每次只激活一小部分，所以计算量小。她展示了一张图：在相同 FLOPs 下，32 个专家的 MoE 比稠密网络损失低最多 5%，等于“免费”；换个角度说，用三分之一的算力就能训练到同样的损失。而 32 个专家在今天很少，前沿模型用几百个。她说这是这些年少有的能如此有效地移动扩展曲线的方法。

为什么 MoE 在 GPU 上反而慢

理论上 MoE 应该比稠密网络快，但在 GPU 上实测更慢，MFU（模型算力利用率）更低。GPU 显存有限，大模型要切分，MoE 用专家并行（expert parallelism）：不同组的专家放在不同 GPU 上，比如专家 1 到 3 在 GPU 1，4 到 6 在 GPU 2。因为同时还在做数据并行，事先不知道 token 要送到哪块卡，所以要加两次 all-to-all 通信。Profile 下来大部分时间花在通信上，她说 GPU 这边没有根本办法，取决于物理连线。

Cerebras 的做法

  • 对比：B200 GPU 有 126MB 的 SRAM（L2 缓存），内存带宽 8TB/s，芯片很小；Cerebras 的晶圆级芯片有餐盘大，44GB SRAM，内存带宽高出几个数量级。这让很大的网络可以在单芯片上训练，不用任何模型并行。
  • 超过 44GB 时，他们给芯片接上 MemoryX 节点作为“权重库”，即外部存储，放大部分模型参数。做梯度更新时逐层把权重从 MemoryX 流到芯片上算梯度，再把梯度送回 MemoryX 更新权重。这样一块芯片就能训练一万亿参数乃至更大的模型，不需要模型并行和额外芯片。对 MoE 特别有用：专家都在同一组 MemoryX 节点或同一芯片上，没有通信开销。
  • 但在 Cerebras 上 MoE 也比稠密慢，原因不同：现在的趋势是很多很小的专家，算术强度（arithmetic intensity，每读一个权重做多少计算）太低，MoE 层搬了大量权重却只做很少计算。
  • 他们的解法叫 batch tiling on attention（字幕作 “budge styling”）。提高算术强度最简单的办法是加大 batch，但对所有层统一加大会伤害 attention，因为 attention 受激活内存限制，batch 变大会把更多东西挤到 MemoryX 里。所以把 attention 和 MoE 层的 batch 解耦：attention 保持原来的小 batch，循环跑 G 次再把结果拼成大 batch，送进 MoE 层，恢复它的算术强度。G 可以根据稀疏度配置。
  • 实测：在 Qwen3 网络的不同稀疏度下，没有 BTA 时 Cerebras 上的 MoE 最多比稠密网络慢 7 倍；用了 BTA 后能达到 MoE 的理论承诺，DeepSeek 的 6,710 亿 MoE 能以 370 亿稠密网络的速度运行。

她的要点：她认为 MoE 是通往 AGI 最快的路，算力效率很高；MoE 在 GPU 上效率不高，会撞上通信瓶颈；在 Cerebras 晶圆级引擎（WSE）上能完全实现 MoE 的理论承诺。最后放了 MoE 指南的二维码。

为什么长程任务重要

他说 GLM-5.1、Opus 4.7、Kimi K2.6 最近的发布文章都在强调 long-horizon 或 long-running 能力。原因有两个：

  • 有用：以前 Agent 30 分钟就做完一个任务，你睡八小时，它大部分时间闲着。另外，OpenClaw、Hermes 这类 Agent 有 heartbeat、记忆、MCP，会不断打断工作流，模型如果没有长程能力，就会跟着最新的指令走，完全忘了原来在做什么。他举了一个例子：Z.ai 第一次办 48 小时黑客松，中间隔着一个晚上，大部分参赛者选择睡觉时让 GLM-5.1 跑任务，9 个获奖者里有 7 个这么做了。
  • 难：这是他花更多时间讲的部分。

三个误解

  • 长程等于长上下文窗口。他说 GLM-5.1 只有 200K 上下文窗口。它强的地方在于理解上下文、计划和记忆，在 Claude Code 里上下文经常被压缩时仍能抓住原始目标。有的模型号称 100 万上下文，用到接近 50 万时就忘光了，只记得最新的指示，不再遵守原计划或 CLAUDE.md。
  • 提前给足指令就够了。模型如果没在这方面训练过，到某个阶段之后就会按自己的方式乱做。
  • 越长越好。各家比谁能跑 8 小时、12 小时、一天、七天，他认为没意义，因为推理越来越快：很多推理服务商超过每秒 200 token，把模型“硬写进芯片”的最新技术接近每秒 17,000 token，那样 8 小时的活一分钟就跑完了。所以他说 long 指的是深度，和时间关系不大，原话是“not longer but deeper”：持续找到有意义改进的能力。例子是抓取 10 个 X 粉丝的信息，扩到 100、1,000、10,000 个，任务本身变化不大，这不算有意义的深入。

两类长程任务和对应办法

第一类是主观目标，比如做一个网站、一个系统，没有“最好的网站”这种明确指标，模型可以一直跑下去，在哪里停取决于你的判断。他本来要放一段视频：GLM-5.1 用 8 小时从零构建了一个 Linux 系统，先搭一层让所有应用能集成进来，再打磨界面、测试应用，最后加了 50 个应用。视频没放出来，他请大家去看 GLM-5.1 的博客。

他说人仍然被需要，因为模型会犯错，而且经常犯。三类主要错误和建议：

  • 偏离原始目标：让模型优化 5 次可能表现完美，600 次就可能忘了初衷，比如做着 Linux 应用聊到 iOS 就混了。建议准备一份 checklist，并要求它每隔几步重读目标。
  • 错误累积：第 400 轮的小错到第 800 轮可能毁掉一切。要让模型自己验证，像训练模型存 checkpoint 一样，从 0 到 100 设多个检查点。
  • 不会转向：模型被训练得很拼，会在循环里一直做同一件事，很难放弃。要让它在发现方向错了时放弃或换方向，checklist 也有用，并由你或 Agent 评估该继续、停下还是修改。

第二类是客观目标，比如速度、价格这类有具体数字的任务。案例是优化一个向量数据库：他说团队里负责训练的研究员都没有这方面的领域知识，但模型做到了。从零开始自己优化，100 轮时已有显著改进，一直跑到 600 轮，得到大约六到八个“科学发现”。图上模型多次换方法，从技术一到技术二再到技术四，大部分轮次是失败的（图上的叉）。他说长程任务不意味着每次都成功，“就像人生”，关键是模型能反思、规划、换思路、持续改进。

评测和自我改进

他推荐的长程评测叫 Frontier Suite（字幕拼写），他说大家都知道 SWE-bench 和 SWE-bench Pro，而这个基准评估包括主观和客观目标在内的长程能力，分三类：实现（从零到一，做应用和 Agentic 任务）、研究（比如交易，要从过去的失败里学习、研究市场，长程任务不只属于工程师，交易员和科学家也能用）、优化。他说 Z.ai 的模型团队已经在用 GLM 优化 CUDA kernel 和向量数据库，用模型改进模型自己和它的推理，是一个 AI 原生团队。

24. Boris Starkov（ElevenLabs 增长工程师）：怎样让语音 Agent 真正能对话

直播位置 7:55:32–8:05:50 · 英文原题 The speech engine: what makes an agent conversational

ElevenLabs 是前沿语音 AI 实验室，他们相信语音会是人和 Agent 交互的主要媒介。他说很多编码 Agent 都有语音模式按钮，但实际用起来是：你说话，等转写，再等 Agent 处理，第三次等语音合成。输入输出是语音，但不是对话。他要讲的是保留这套级联架构，加上很多小改进，合起来差别很大。

语音识别这一侧

  • 语音活动检测（VAD）：把用户音频流切成约 20 毫秒的块，用一个很小、很便宜的模型判断每块有没有人在说话。下游据此判断谁在说、轮到谁，也省算力，没人说话的块就不用跑更贵的 ASR（自动语音识别）模型。
  • 检测静音和检测说话轮次结束是两个问题。Agent 问他问题，他回答“我觉得……嗯……”，中间有很长的停顿，但话没说完，他不希望 Agent 插嘴。所以他们训练了一个轮次检测（turn detection）模型，除了语音活动还看之前说了什么的上下文，预测句子是否结束。另外有很多启发式规则：用户在念车辆信息、信用卡号、邮箱，或说了某些触发词，就当作强信号，接下来的停顿大概率不代表说完。
  • 推测式轮次（speculative turn）：人和人对话时，对方停下后你大约等一秒确认他没话了才开口。Agent 等不起这一秒，因为它还要时间生成回复。所以模型一判断用户可能说完了，就同时开始推测性地生成回复。大多数时候判断是对的，回复来得早很多，显得延迟低、自然；偶尔误判也没关系，向生成模型发送取消，继续听。

语音合成这一侧

  • 缓冲：Agent 一个个吐 token，用户期待听到的是句子。等整句再送去合成，用户要在沉默中等；逐 token 合成又会忽快忽慢、卡顿不稳。他们取中间：攒五六七个词的短语就送去合成。当前短语在播放时，下一个短语已经在合成，再下一个在缓冲区里拼装，同时进行。
  • 级联容错（TTS cascading）：主 TTS 模型运行时始终有一个备用模型待命，主模型失败或崩溃时立即接手，用户感觉不到，接近 100% 可用。
  • 打断处理：他说这本身能讲一整场，只举几个例子。打断极短，只有几帧、40 毫秒左右，通常是咳嗽、噪声或 VAD 误报；发生在 Agent 开口后前 200 毫秒左右，多半是回声；用户说“嗯”“对”“好的”是积极聆听，也不是打断。

Speech Engine

他说听完这些步骤你可能有点被吓到，于是介绍了尚未正式发布的新产品 Speech Engine，下周开始测试。它把所有让对话自然的复杂度封装起来，你自带 Agent 接进去即可，可以是聊天机器人、OpenClaw、NanoClaw、Hermes Agent，任何复杂度都行。他强调它比语音转文字加文字转语音多做了很多，是一个完整的对话引擎，希望让“几百万个沉默的 Agent”开口说话。

25. Jackman Ong（Prime Intellect 创始研究工程师）：强化学习和递归语言模型

直播位置 8:06:54–8:18:20

主持人说长时运行的 Agent 怎样边跑边变好是这两天反复出现的主题。他说自己换了个更吸引人的题目，内容仍和持续学习、长时 Agent 有关。他说两年前（2024 年 Cursor Agent 刚发布时）Agent 跑超过 5 分钟就别指望它还在做有用的事，现在大家让 Agent 整夜跑、消耗几百万 token。模型有用已无疑问，剩下的是经济问题：能否可靠、高效、足够快地完成我的任务。他的主张是：训练你自己的模型，具体用强化学习（RL），并且用 RLM。

长上下文的问题

他说用过 Claude Code、Codex 或各种 claw 的人都知道，模型并不擅长长上下文，接受 100 万 token 不代表能在 100 万 token 上推理。各大模型卡里的长上下文部分通常有两个基准：MRCR，类似大海捞针，测在长文本里找到特定信息，上下文越长越差；GraphWalks，把节点和边的列表放进 prompt，问图的问题，比如“列出 X 的所有父节点”“从 Y 做 BFS 列出子节点”，同样上下文越长越差。

RLM：把上下文当作变量

RLM（Recursive Language Model，递归语言模型）的思路是不把整个上下文塞进窗口，只给模型一个对上下文的引用。他用数据科学做类比：做探索性数据分析时，你不会把整个 CSV 贴进 Python 代码，而是导入库、定义一个 DataFrame，用一段段代码去摸清数据结构和分布。这样设计 Agent，很多事变得容易：上下文分块、工具调用、子 Agent 委派，因为编排 Agent 不必自回归地把上下文原样复述一遍，只要传一个变量。

进一步，可以用全部编程结构。比如要处理 10,000 份文档，传统做法要编排 Agent 正确地连续做 10,000 次工具调用、正确传上下文，还要“向摘要之神祈祷”压缩后它还记得做到哪了。用 RLM，模型写一个 for 循环，循环里做 LLM 查询就行。

  • 他说会用 Agent 的人其实已经在做 RLM：Claude Code 老手总在 prompt 里写“别把子 Agent 输出放进上下文”“别把工具输出放进上下文，会搞乱，全部写进文件”，因为他们知道压缩不太管用，看到压缩提示就知道“完了”。ChatGPT、Claude、AI Studio 里你贴一大段文本，它们也会自动变成文件。但大家只用了“引用上下文”这一点，没用到完整 Python REPL 的表达能力。
  • RLM 已被用于视频、游戏、编码、数学等需要长上下文理解的场景。
  • RLM 的第一作者 Alex Zhang 写过一篇他推荐大家读的文章，叫 “mismanaged geniuses hypothesis”：模型已经足够聪明，拖后腿的是脚手架，我们不知道怎样编排 Agent、记忆放哪、子 Agent 怎么分工。按 bitter lesson 的思路，不该让人来做这些，应该让模型在推理时动态写自己的脚手架。他说今天的 Claude Code、OpenClaw 都是大量 vibe coding 出来的，说明模型已经能写出很好的脚手架。

为什么要训练

但如果你回家试 RLM 的仓库，可能会失望，因为模型没在这个脚手架上训练过，不是好的 RLM：想不到要委派子 Agent，不会切分上下文。博客里的例子显示，基础模型加基础 RLM prompt 表现不好，做一点 prompt 工程就能大幅提升并总是超过基础模型。既然 prompt 工程就能做到，为什么不把好的 RLM 策略直接训练进模型？

这就是 Prime Intellect 在做的：一个为训练和部署自己模型的人服务的平台，支持 GPT-OSS、Llama、Nemotron 和各种 Qwen 等开源模型，有实验管理，能看指标和配置，最重要的是能看 rollout，看失败案例和数据。两个用户案例：

  • 大约两周前 Ramp Labs 宣布和他们合作，训练了一个小 Qwen 模型，在 Excel Agent 的检索任务上超过 Opus 4.6，准确率更高，同时更便宜、延迟更低。
  • 数据供应商：他提到硅谷数据圈的一位人士（字幕作 Shan Chai）观察到，哪些数据公司能活下来，取决于有没有内部训练能力。买数据的实验室知道数据质量参差，签百万美元合同前想知道这批数据能不能提升模型。最直接的证明是展示奖励曲线：用我的数据训练，奖励上升，或 Agent 完成任务的效率显著提高。

葡萄牙酒店大堂的一晚

她在 Apple 时常参加谈判，作为一个“小个子亚洲女性”，屋里往往是另一种样子的人，所以她每次都紧张。第一次是飞到葡萄牙，前一晚她在酒店大堂反复看技术细节：要和外部供应商谈什么，Apple 的立场，怎么讲技术。经理让她先忘掉技术细节，花一小时给她讲和这家供应商过去十年的历史和“八卦”：谁和谁什么关系，以前怎么和这个人谈，他在意什么，他和大老板打过什么交道。经理说这比背技术规格有用得多。她由此意识到，大多数场合需要理解纵向的长期关系，要做 Apple 的智能代理，就要掌握和每个供应商的完整双边上下文，并以长期有利的方式推进关系。人凭直觉就能做，但在以利益为导向的对话里随时间建模和平衡关系状态很难，数学上也很难证明。她认为情商是让 AI 成为人的有用策略性替身的关键：今天的语言模型对人的工作很流利，但在策略上并不胜任。

三项研究

  • 去年发表在 Nature Human Behaviour 的研究：让 AI 玩囚徒困境（自利博弈）和性别之战（协调博弈）。结果不对称：自利博弈里模型表现不错，该合作时合作、背叛有利时背叛；协调博弈里表现很差。她说这很麻烦，因为大多数人际互动是协调博弈：葡萄牙那次，双方都不想背叛对方，都想成交，问题只是什么样的交易。研究还发现“社交思维链”（social chain of thought，让模型同时建模自己和对方）能提高合作率。
  • Google DeepMind 今年的研究：人类、前沿模型（她记得是 Gemini 1.5 Pro 和 GPT-4o）和一个定制训练的贝叶斯 Agent 玩交换筹码的讨价还价游戏。贝叶斯 Agent 很强硬，常被拒绝，但拿到最大剩余的 80%；人类更公平，有给有取；LLM 极度让步，愿意给出比得到更多的东西来促成交易，每笔都被接受，而且整局都不会自我调整。她说合适的做法是：初次见面先让一点建立关系，到大交易时再更像贝叶斯 Agent 那样谈。这说明 Agent 的谈判方式是静态的。
  • 一篇被 ACL 接收的计算心理学论文，研究固定的心理画像，比较“状态”和“特质”：用户在某个时刻、某段关系里的状态（比如第一次见这些人、身处某类人中间而紧张），比“我天性冷静”这类人格特质更能决定他的行为。所以静态地建模人格还有很大改进空间。

她的归纳：模型无法在变化的条件下协调，把自己的行为当成静态的，而且天生爱让步。

开放问题和 Bluelabs 的尝试

  • 能否训练模型在不同策略语域之间切换，知道什么时候推、什么时候收？
  • 关系最合适的架构表示是什么？双边嵌入（dyadic embeddings）、反思式记忆层级都是开放课题，她说有想法的人很快就能做实验。
  • Bluelabs 的第一个架构尝试叫 Blue JST，一个联合状态引擎（joint state engine），核心是双奖励机制，把关系建设和利益优先当作同等目标，不把一个化约为另一个。

27. Jacky Mok（Reka 应用 AI 负责人）：从语言模型走向物理智能和世界模型

直播位置 8:30:08–8:38:58

Reka 做视频、图像和文本的多模态 AI，几年前因模型在排行榜上排名靠前为人所知，最近更专注视觉模型和不同模态，研究怎样用到真实场景。

CV 和 VLM 一起用

他说检测车辆、追踪物体这类传统计算机视觉（CV）已经是解决了的问题，可以用比较确定性的方式帮部署系统理解视频里发生了什么，但机器并不真正理解自己看到的东西，只看到热力图和边界框。VLM（视觉语言模型）出现后，可以看场景、思考场景、再采取行动。但他们没有用 VLM 替代 CV：生产部署里，先用便宜的 CV 做检测、追踪和识别，再用 VLM 推理，最后针对具体场景发警报。单独哪一个都不够，也都还不算物理智能。

两条路径

  • 预测下一个 token：VLM 把视觉空间编码成 embedding，再生成下一个 token，能解释图片和视频里随时间发生的事，但输出主要是文本。
  • 预测下一帧：扩散模型生成图像或视频，现在机器人和物理 AI 也在用这条路生成机器人轨迹。他展示了一个他们从零训练的扩散模型，原本用于生成 5 秒的电影感视频；用在机器人上的好处是零样本：以前要用机械臂动作数据训练机器人，现在扩散模型直接描绘手臂为达到目标应走的轨迹，机器人事先不需要知道这些，结果出乎意料地好。

他说这两类都还不是世界模型，世界模型要预测下一个动作，两条路都会帮他们走到那里。

短板和新评测集

他说做模型的办法是弄清哪里坏了，然后建评测。VLM 的物理很差：物体会凭空消失、无故变小，不符合物理规律。现有评测也有盲点：模型给出了对的答案，但输入是抽帧的，信息已经丢了一部分；很多模型由其他 VLM 评判，互相打分。所以他们在建新的数据集来确定真值，覆盖球是否变小、下落是否合理、两个物体碰撞后怎样、运动是否正确、东西会不会自己动起来，用合成数据测真实感，他说最好的模型表现也不好。

  • 原因一：VLM 不看每一帧。基于 LLM 的方法 token 太多，通常要抽帧。他们的实验显示每帧都送时模型可能理解，随机抽帧时它会自己插值，就不理解了。
  • 原因二：物体在画面边缘时，模型分不清人是消失了还是走出了画面，会假设人消失了。
  • 原因三：VLM 最后回到文本世界推理，懂的是文本里的物理规律。所以部署时要加 CV 补充信息，比如告诉它“这个场景里有某个身份，已经跨多个镜头被追踪”，VLM 表现才会提升。他归纳：它们跳帧，匹配的是位置而不是运动，物理知识来自文本。

Reka 即将发布这些评测集，帮助别人训练下一代具身模型。他们的路径是：LLM 和 VLM 预测下一个 token，外面套 Harness 去控制监控或机器人；扩散视频模型生成机器人控制轨迹；两者结合成预测下一个动作的世界模型；评测集用来判断自己是真的理解了，还是在盲飞。

28. Gokul Srinivasan（Antim Labs 联合创始人兼总裁）：仿真、游戏和机器人训练

直播位置 8:41:38–8:52:08

他说从 1950、60 年代起机器人一直“在笼子里”：一切预先编程，环境固定，是为机器人专门搭的。要释放经济价值，机器人得在现有环境里工作。过去 10 到 15 年大量研究让机器人更通用，但业界对什么模型架构能带来显著的通用性还没有答案：世界动作模型、VLM、VLA、视频动作模型，也有人还在用经典算法。模型不同，数据采集方法也不同：遥操作、用互联网视频训练视频动作模型、仿真合成数据、UMI 式采集。

仿真是共同点，但很难做

他认为这些方法的共同点是仿真，它会成为研发和部署流程里几乎躲不开的一环：生成合成数据；做环境的数字孪生，先在孪生里验证再部署实体机器人；覆盖边界情况（自动驾驶里用得很多）；部署前原型验证策略。问题是仿真极难做，Isaac Sim、MuJoCo 这类软件学习曲线陡，成了专家还是难。他放了创建并摆放一个资产的流程图，场景复杂时每个资产都要来一遍，要几天甚至几周。

他们做了 Gizmo，一个 prompt 到仿真的工具：给一段自然语言或一张图片，系统会起一批子 Agent 去完成各步，最后得到完整的 3D 仿真，目前约 20 分钟，需要人工补的话几小时内也能完成，对比现在的几天或几周。之后会提供 API，Codex、OpenClaw 等 Agent 在工作流任意环节都能自己起一个仿真，这让大规模仿真成为可能，也能做端到端闭环机器人学习，比如说“训练一只四足机器人走到场景里我指定的点”，Agent 就有足够信息去做完全部事情，交回一个训好的策略。

他承认 sim-to-real 差距仍然存在：仿真还不是 100% 准确，根本上是物理问题，接触物理有问题，材料属性是近似的，形变很难建模。他预计差距会逐年缩小。

为什么是游戏

他说在合成世界里不只可以训练操作、导航、移动，还能训练高层认知：目标不清时的探索；计划执行中世界变化、状态变差后怎样恢复和重新规划；信息不完整时决策的好坏。这对 LLM 也重要，对机器人尤其重要，因为这些能力要建立在时空记忆之上。

他们训练了一个 Agent：基于 20 亿参数的 Qwen VLM，像电脑操作 Agent 一样控制键盘和鼠标。先用约 400 小时“画面-动作”配对的游戏录像预训练，让模型有玩游戏的本能；再用约 60 小时指令跟随数据做指令微调，引导它在游戏里行动；下一步（还在做）是训练它输出推理轨迹，作为下一步的指令。因为是玩游戏，必须实时：输入、处理、解码输出要在 200 毫秒内完成。他说这还是早期工作，远不完美，随后播放了 Agent 玩游戏的演示。

坑一：语音信箱检测

他没想到企业客户每天都在跟踪语音信箱检测准确率。原因是大多数外呼电话接不到真人，而是进语音信箱，系统要在各种场景下稳定判断。比如现在 iOS 和 Google Voice 有来电筛选，接通前会说“请说出姓名和来电原因”，然后有一声提示音。很多人用 Twilio 的应答机检测功能，本质是一个提示音检测模型，效果不好，企业客户靠不住。他在 Bland 做了一个 CNN 模型，看每个音频块的梅尔频谱图（mel spectrogram，把声音按时间和频率展开成图）。他发现不同手机的提示音长度和频率差别很大，有些是双频，和 DTMF 音（通话中按数字键的声音）一样，要避免误报。他们还做了一个网站，用来测试和比较语音信箱检测。他建议引入语音 AI 时一定要看供应商这方面做得怎样。

坑二：“我的 Agent 为什么和昨天不一样”

他说他最常收到的客户消息就是这句。他自己用 Claude 时也讨厌东西突然变了。有时他什么都没改、没推新代码，客户也会说他把系统弄坏了，但他理解，客户在平台上花了几个小时调 Agent。他也讲了自己搞砸的一次：改进知识库功能的混合检索算法（他们自托管向量数据库），想提高准确率，结果对一些客户有效，对另一个客户造成回退，破坏了信任，很难重建。现在 Bland 为每个企业客户提供专用基础设施（满足数据驻留等需求），支持 canary 部署和带版本的 Agent 发布：客户可以起一个单独容器测试新版本 Agent，把一部分流量或几个电话号码路由过去，确认后再上线。

坑三：重复数字的 tokenizer 问题

他们给一家财富 500 强租车公司做电话 Agent，收集租车订单的数字 ID。上线后发现数字对不上。排查管道：转写正确，TTS 正常，是 LLM 在幻觉，输入的数字是对的，输出却不一样。Prompt 工程没解决。他查到 tokenizer 层，发现重复的数字被当成一个 token，而不是每个数字一个 token。最后彻底解决问题的办法是在每个数字之间加逗号，让每个数字成为单独的 token。他们修好后才看到一篇 2024 年的论文讨论这个现象（论文名字幕不清）。这个问题只在千分之五的情况下出现，但对企业客户来说五次也太多。

一个遗憾

种子轮阶段，YC 式的建议是 move fast, break things。他后悔当时推改动时不够审慎，造成了客户的痛苦，应该更注意区分单向门决策和双向门决策（能否轻易回退）。

32. Stefania Druga（Sakana AI 研究科学家）：主权 AI 是一组可以选择拥有的层

她先让全场站起来做了一个呼吸练习。她在东京 Sakana AI 做研究科学家。她说的主权 AI（sovereign AI）不一定是每个国家自己造一个模型，而是在全球能力之上保有本地的主动权。实践中要考虑三件事：数据（哪些数据要留在本地，什么模型最适合本地使用）；算力和评测（需要什么算力，哪些工作流在本地跑、哪些上云）；问责（AI 进入机构后谁来负责）。

她来自罗马尼亚特兰西瓦尼亚的一个小村庄。做 AI 研究前，她在世界各地给孩子、家庭和教师办 AI 素养工作坊，包括新加坡，她放了 2013 年和孩子们办黑客松的视频。她在教室、创客空间、图书馆里看到，人们很想用 AI，但模型常常不适配他们的语言和本地需求。她说今天的前沿 AI 也是这样：我们期待社区去适应 AI，很少让系统去适应本地需求。在日本，本地化意味着要考虑不同的语言敬语层级、文化规范、工作流、科研惯例和安全政策，是机构层面的、多方面的问题。

主权是一个栈

她把主权看作一个栈：数据（需要什么独特数据）；评测（中立性、事实性、国家特定基准）；适配（主要通过后训练、微调、RAG、工具使用）；路由（感知政策的模型选择）；交互（用户是谁、有哪些画像、怎样呈现给用户的 UX 决策）；治理。再往下还有物理层：预训练需要大量数据和算力，成本多数情况下高得难以承受；后训练要很在意本地规范和偏好。

Sakana 的几个项目

  • Sakana Chat：她说 3 月 24 日上线的第一款消费产品，日本境内免费，带网页搜索。支持标准模式（中性的默认日语）、敬语模式（正式场合）和大阪模式（用关西方言回答），用户很喜欢，日活超过 30,000。这里后训练是主权控制点：从 DeepSeek、Llama、GPT-OSS 等开放前沿模型出发，用日本独有的数据做评测和偏好，和政策专家小组一起定义了一组中立性指标，后训练出一个叫 Namazu 的模型。后训练模型在中立性和事实准确性上超过原模型。她说更重要的是，很多原模型对敏感问题直接拒答，比如问 DeepSeek“各国政府的互联网审查情况”，它会拒绝或给笼统回答；Namazu 会给出多角度的回答，附上可信新闻的链接。
  • AI Scientist：把科研能力当作一种主权。多个 Agent 支撑整个研究流程：生成想法、查新颖性、给想法打分，用树搜索做实验，生成代码，做消融实验，最后写出完整论文。她说这项工作上个月登上 Nature；系统生成的论文是第一篇完全由 AI 生成并通过 ICLR 同行评审的论文（去年）。
  • 多 Agent 协调：switchboard 根据任务难度自动把任务路由到最合适的模型，兼顾成本和安全。和日本语境强相关的请求送到日本后训练模型，很敏感的请求送到本地部署的安全模型，或请人工审核。她说路由也是一种主权，它的作用不是把本地方案和全球方案隔开。
  • Sakana Fugu：他们押注最强的 AI 系统是专门化 Agent 的集合，而不是单个规模化模型。Fugu 是一个学出来的编排器，能为特定任务挑最好的模型，遇到难任务还能递归调用自己。现已开放 beta，相关工作在今年 ICLR 上发表了两篇论文。评测显示“组合胜过规模”：Fugu 协调一组前沿模型，在 LiveCodeBench、SWE-bench Pro 等基准上超过组里任何单个模型。
  • 领域适配：大量隐性知识没有数字化，是缺失的数据集。和银行、医院、政府合作时，要有把专家批评和反馈带回模型的流程。比如和 MUFG、SMBC 等日本大银行做信用备忘录（credit memo），收集了 1,000 多条反馈喂回模型，让它为分析师写出更好的备忘录。
  • 支持日本政府：团队用 AI 分析社交媒体，展示虚假信息运动是怎样发起和运作的。
  • 她说最重要的一种主权，可能是保有质疑主流架构的本地能力。Continuous Thought Machine（CTM）提出了 Transformer 之外的新架构，受大脑启发，推理来自神经元随时间的同步，不是单次 attention，多个 attention head 协同。它学会了走迷宫，过程对人可解释，能看到底部的激活；在图像分类上能看到 attention 随时间关注图像的哪些部分，而且计算量会自适应，简单图片花的时间比复杂图片少。

这些项目多数开源，在 Sakana 的 GitHub 和博客上。她说没有哪个国家会拥有栈的每一层，每个国家选择自己想拥有、也能够拥有的层，不同国家做出不同的所有权决定，这就是主权在实践中的样子。最后她说，从孩子、家长到研究者和 AI 工程师，都要意识到自己有主动权，本地主动权比全球能力更重要。

Agent 实验室 vs 模型实验室

他在一篇叫 agent labs thesis 的文章里写过，在纽约的 AI Engineer 峰会上也列过两边的名单。一张图概括：模型实验室把资源主要投在训练和算力，部署较少（虽然在增加）；Agent 实验室几乎相反。现在双方在互相侵入地盘：模型实验室内部在建 Agent 团队，OpenAI 和 Anthropic 也在招 FDE（前线部署工程师）；Agent 实验室在做自己的模型，Cursor 和 Cognition 都投了大量算力做 RL。然后他讲“细节”：

  • “把编码 Agent 塞进容器就行”不对。要做有状态的会话，给它真实机器的语义和真正电脑操作所需的工具。他举了同一根因的真实事故：并行 Agent 会话因共享缓存互相干扰；一个 Agent 在自动接受模式下把整个公司的源码发到了个人 GitHub，因为密钥混在一起。容器没有隔离边界，不是为在 Agent 会话之间切换上下文设计的。所以最后你要做的是 Agent 平台，即 VM 或容器之上的一切。他展示了一张完整清单，说相当于开源出来，想做 Agent 实验室要逐项做，想采购的话也按它评估。
  • 安全：多人、多层团队和组织时，Agent 需要限定范围的身份和最小权限，要设计好权限模型。
  • “GPT wrapper”：在某种程度上可以骄傲地当 wrapper，关键是做厚、做得有价值。Agent 实验室押注模型多样性，这一直是好赌注：OpenAI 的份额从七八成降到三成多（看数据源）。而且也能用自己的领域数据训练模型，比如 Cognition 的 SWE-grep 和 SWE-1.5（字幕不清，他说自己参与了），Cursor 也在做；有能力的 Agent 实验室都应该做，因为对主要负载更合适。
  • 评测：大多数人只告诉你看 SWE-bench，“我比别人高 0.1%”。现实是多维的，他展示了 Cognition 内部跑的各种评测，每个真实场景背后可能有几千万到几亿美元，没法用 SWE-bench 概括。他的观点是企业是最难的评测，“给我看一个比企业更难的 RL 环境”。Cognition 自己就是一个有多个组织、多个 Slack、多套 IT 系统的企业。他说这在过去六个月才真正被解决，他六个月前加入时觉得已经不错，现在对“好”有了新定义，这和已公开的 ARR 增长相关。

为什么是新加坡

他说新加坡经济发展从贸易到石油再到金融，“在生物上有过一段”，“加密就别提了”，下一个阶段就在这里。他宣布新加坡被选为 Cognition 的亚洲总部。他说新加坡一直希望跨国公司把基地放在这里，除了销售，也做工程和研究；你得先在海外成功才会在本地被认可。Cognition 收购了 Havana（字幕拼写，团队成员 Nathan 在现场），他让想加入的人去找 Nathan。他说自己整个成年后都在新加坡科技圈，从没见过外国尤其是美国对在新加坡设立工程和研究有这么大的兴趣。

他让 Nathan 翻了客户通话记录，分享亚太的需求：

  • 有机构每年在 LLM token 上花几百万到几千万美元。
  • 银行的贷款业务靠业务分析师的电子表格运作，而这些分析师不会一直在，要把它系统化，写成代码。政府和其他科技领域也一样。
  • “10 倍交付加速”这类数字很难体会，他给了基线：一家本地银行有 200 万行 COBOL，没有文档，也没有工程师负责。他说新加坡以外、这家银行以外也一样，所有大规模的企业都这样：上亿美元的 AI 预算，每次推广 600 名开发者，大量工作因为枯燥、用的是没人想碰的语言和系统而招不到人做。

Cognition 摸索出来有效的做法：

  • Devin 的 playbook：比普通聊天结构化得多的模板，能更可靠地并行调度 Agent。他认为一个 playbook 可能值上亿美元，有人在用它们改造银行。
  • 代码库理解是护城河：没有文档，就先让 AI 写文档，再用文档做迁移。Cognition 最早做了 DeepWiki。存量系统（brownfield）的工作里有几十亿美元的收入。
  • 企业安全：销售会说“对方不给我们定制 SSO 就不接电话”，因为他们锁死了 GitHub 和 GitLab，他们托管着几百万人的信任和钱。服务这些企业的人也必须这样考虑安全，不能像个人那样随手把东西丢进 Obsidian 和自己的 OpenClaw。

Agentic 国家

他引用早上的“前线部署部长”（观众 Abhishek 给 Vivian Balakrishnan 起的外号）讲的三个 D：部署、民主化、去中心化（“不是加密”）。他说新加坡 AI 工程人才的需求约为供给的四倍，差距还在扩大，这类岗位需求每年增长 40%，数据来自 LinkedIn 的调查。

他的“辣评”是：他已经对政府放弃了。他等了很多年，等政府为科技行业做点什么，还和部长 Josephine Teo 录过播客、一起散步聊未来（字幕作 “Josmin”），结果什么也没发生。他说新加坡有政府主导经济发展的传统，新时代会是先由私营部门带动，再带入公共部门。这场大会就是例子：没等政府批准或支持。有 IMDA、AI Singapore 在展区，有外交部的支持很好，“但我们不需要他们”。他请大家为站在侧台的 65 Labs 组织者鼓掌，这是他们的业余项目。他希望大家离开时在生活里更 agentic，把新加坡变成一个更 agentic 的国家。
