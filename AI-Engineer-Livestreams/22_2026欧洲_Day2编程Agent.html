01. Omar Sanseviero（Google DeepMind）：Gemma 4 与端侧模型

直播位置 0:15:44–0:30:09

从 Gemma 3 到 Gemma 4

Omar 来自 Google DeepMind，负责 Gemma。他说 Gemma 4 在七天前刚发布，这是他第一次在会议上讲它。Gemma 是 Google 的开放模型（Open Models）系列，开放模型指权重可以下载，能在自己的服务器或设备上运行，也能针对自己的场景微调。

一年前发布的 Gemma 3 覆盖 1B 到 27B 参数，当时是能装进单块消费级 GPU 的最强开放模型。他放了一张 LMArena 分数图，每个模型下面用小圆点表示加载它需要多少块 H100 或 A100，Gemma 3 用很少的卡就拿到了很高的分。

Gemma 4 从 2B 到 31B，有几种不同形态：

  • 两个最小的模型（E2B、E4B）能在 Android 手机、iPhone，甚至树莓派上跑，多模态、带推理，能做端侧的 Agent 任务。
  • 一个混合专家（Mixture of Experts, MoE）模型，约 26B，延迟很低。MoE 的意思是每个 token 只激活模型里的一部分“专家”子网络，所以算力花费比总参数量小得多。
  • 31B 稠密模型，能力最强，也能在消费级 GPU 上运行。他说“开发者友好的尺寸”对团队很重要。

演示

他放了三段视频：一是在 Android 手机上运行 Gemma，用户挑选不同的 Skill，模型调用一个弹钢琴的 Skill，然后真的弹起了钢琴；二是 Gemma 在手机上离线写代码，开着飞行模式，没有任何 API 调用；三是在一台笔记本上用 llama.cpp 并行跑 10 个 Gemma 实例，每个各自生成一张 SVG，速度大约每秒 100 个 token。他说 Gemma 能写代码、能做 Agent 任务，连 Android 应用开发都可以，全部离线。

LMArena 的散点图上，横轴是参数量，纵轴是分数，Gemma 4 落在左上角，也就是“很小但很强”。他承认 LMArena 不是完美的基准，但能大致反映社区在日常对话这类用途上喜不喜欢一个模型。从 Gemma 2 到 3 到 4，模型没变大，各项能力一直在涨，所以他估计一两年后我们口袋里会有能力很强的本地模型。他还提到有人把 llama.cpp 装进了 Nintendo Switch 来跑 Gemma。

许可证和 E2B 的“E”

以前社区抱怨 Gemma 的许可证不是真正的开源许可证，Gemma 4 改成了 Apache 2.0。

E2B 的 E 是 effectively（等效）的意思。E2B 实际有四五十亿参数，但用了一种叫逐层嵌入（Per-Layer Embeddings, PLE）的新结构，去年夏天发布过。每一层都有一张自己的嵌入表，用起来像查表，不需要矩阵乘法，所以这部分可以放在 CPU 内存甚至硬盘上，GPU 里只需要装大约 2B 参数。这是专门为手机这类设备做的设计。在 llama.cpp 里用一个 --override-tensor 参数把 PLE 挪到 CPU 或磁盘，开箱就能用。

多模态和多语言

小模型能理解图片、视频和音频，可以做语音识别，也能把语音直接翻成另一种语言的文字，比如说西班牙语输出法语文字。大模型的多模态理解更细，能在图里指出羊驼在哪、做目标检测。Gemma 4 用 140 多种语言训练，分词器（Tokenizer，把文字切成模型能处理的 token 的组件）沿用了 Gemini 的。他说分词器是专门为多语言设计的，所以拿 Gemma 去微调一门数字资源很少的语言（他举了秘鲁的克丘亚语和印度的官方语言），即使模型本身对这门语言掌握有限，效果也往往不错。演示里有用日文解释一张带日文的图片。

生态数字

  • 发布一周，Gemma 4 系列下载量 1,000 万；社区已经做了 1,000 多个衍生模型（量化版、微调版）。
  • 整个 Gemma 家族下载 5 亿次，衍生模型超过 10 万个。
  • 发布时就和 Unsloth、MLX、Ollama、Hugging Face、vLLM、SGLang 等合作，目标是大家在自己习惯的工具里直接能用，比如用 Hugging Face Transformers 微调的人不必改用 Keras。有人用 Gemma 做了完整的代码仓库审计。
  • Android Studio 的 Agent 模式现在有离线模式，可以用 llama.cpp、Ollama 或 vLLM 驱动的 Gemma；训练时加入了 Android 相关的数据集和基准，所以它在 Android 开发上表现不错。

官方和社区的变体

Google 自己出了 ShieldGemma（一组护栏模型 Guardrails，用来拦截不符合政策的图片和文字）和 MedGemma（基于 Gemma 3 的多模态医疗模型，能读胸片等）。社区里，AI Singapore 在做东南亚语言模型；印度的 Sarvam 属于政府投资的主权 AI 项目，训练本国语言模型。去年 12 月 DeepMind 的研究者发表论文，用 Gemma 3 提出了癌症治疗通路的假设，送到真实实验室验证，结果得到了证实。

他最后建议大家在接下来两周里花一小时玩一下最新的开放模型，搞清楚它们能做什么。要最强的原始智能还是用 Gemini 这类 API 模型，但离线、隐私（数据不出服务器）、地铁和飞机上、浏览器扩展里看屏幕、设备控制这些场景，开放模型已经够用了。

02. David Soria Parra（Anthropic）：MCP 的下一步，渐进式发现与程序化工具调用

直播位置 0:31:00–0:48:48

从一份规范文档到每月 1.1 亿次下载

David 是 MCP 的作者之一，Anthropic 的技术人员。MCP（Model Context Protocol，模型上下文协议）是一个开放协议，规定 AI 应用（客户端）怎样连接外部的工具和数据（服务器）。

他开场先放了一个 MCP 应用（MCP Apps）：Agent 自带的界面，通过 MCP 服务器下发，不靠插件、不靠 SDK，也不是模型临时生成的。同一个服务器放进 Claude、ChatGPT、VS Code、Cursor 都能用。要做到这一点，客户端和服务器两边都得理解对方在说什么、知道有一个 UI 要渲染，这就需要协议层面的语义。他说 MCP 服务器既能下发一个给人用的应用，也能同时下发给模型用的工具，人和模型操作同一个界面，这一点大家还没怎么探索。

18 个月前 MCP 只是一份小规范和几个 SDK（大部分由 Claude 写的），只能本地运行，基本只有工具。之后他们加了远程能力、集中式授权、Elicitation（服务器向用户追问信息）和 Tasks（异步任务）等新原语，以及 MCP Apps 这样的实验特性。现在 MCP 每月下载 1.1 亿次，大部分来自别人的项目：OpenAI 的 Agents SDK、Google 的 ADK、LangChain 和成千上万的框架都把它当依赖。他对比说 React 达到同样的下载量用了大约两倍时间。大多数 MCP 服务器在企业内部，把公司系统接到 Agent 上。

2026 年是“连接性”之年

他的时间线是：2024 年大家做演示；2025 年是编程 Agent 之年，编程是 Agent 最理想的场景，本地运行、结果可验证、能调编译器，出错了有开发者坐在电脑前修；2026 年会出现做知识工作的通用 Agent，比如金融分析师、市场人员要用的 Agent。这些人不需要调编译器，需要的是连上五个 SaaS 应用和一个共享盘，所以最重要的是连接性。

他说如果有人告诉你某一种方案能解决所有连接问题，不管是 Computer Use 还是 MCP，那人多半错了。他把连接栈分成三块：

  • Skills：一个简单文件里装的领域知识，可复用，各平台之间差别很小。
  • CLI 或 Computer Use：本地编程 Agent 里很流行，能在 bash 里组合，模型能自己发现 CLI 能做什么；像 Git、GitHub 这种预训练里见过很多的 CLI 特别好用。前提是有沙箱、有代码执行环境。
  • MCP：需要丰富语义、能显示长任务的 UI、资源（Resources）、完全解耦和平台无关、没有沙箱、需要授权和治理策略这类“无聊但重要的企业需求”，或者想用 MCP Apps、即将到来的 Skills over MCP 时，用 MCP。

他的结论是 2026 年的好 Agent 会把这些全都无缝用上。

客户端要做的事：渐进式发现

他说大家一提 MCP 就想到上下文膨胀（Context Bloat）。协议只负责把信息送过线，怎么处理是客户端的事。早期大家都把所有工具定义一股脑塞进上下文窗口（Context Window，模型一次能看到的全部输入），然后惊讶于上下文变大了。

应该做的是渐进式发现（Progressive Discovery）：用 Tool Search 之类的机制延迟加载工具，模型需要时再加载。Anthropic 的产品和 API 已经有这个功能，别家 API 上也能用，也可以自己实现：给模型一个“加载工具的工具”，模型觉得需要时去查有哪些工具，再按需加载。他放了 Claude Code 加这个功能前后的对比，工具占用的上下文大幅减少。

程序化工具调用（Code Mode）

第二件事是程序化工具调用（Programmatic Tool Calling），也有人叫 Code Mode。如果让模型调一个工具、拿结果、再调下一个、再拿结果，就是让模型自己做编排，每一步都要一次推理，慢且贵。更好的做法是写一段脚本把调用组合起来，Claude Code 写 bash 命令时其实一直在这样做，MCP 也应该这样用。

具体做法是给模型一个 REPL 工具和一个执行环境，比如 V8 isolate、Monty 或 Lua 解释器，让模型写代码、执行、组合结果。MCP 有一个叫结构化输出（Structured Output）的特性，声明工具返回值的类型，模型可以据此推断类型，把调用串起来。他的例子里原本两次调用变成一次，模型还能在代码里过滤 JSON。如果服务器没有声明结构化输出，可以先叫一个便宜的模型按期望的类型把结果抽出来。他说业界在 Harness（围绕模型的那层运行框架，负责工具、上下文、循环）里这件事做得还不够。

服务器作者要做的事

  • 别再把 REST API 一对一翻成 MCP 服务器。他说每次看到又一个 REST 转 MCP 的工具都有点尴尬，结果都很糟。应该为 Agent 设计，先想你作为人想怎样和这个服务交互，这是很好的起点。
  • 服务器端也可以只提供一个执行环境，不暴露一堆工具，Cloudflare 的 MCP 服务器就是例子，省 token、降延迟、组合能力更强。
  • 多用 MCP 独有的丰富语义：MCP Apps、Skills over MCP、Tasks、Elicitation，这些目前用得太少。

协议本身的路线图

  • 现在的 Streamable HTTP 传输对超大规模云厂商很难扩展。Google 提了一个无状态传输方案，让 MCP 服务器能像普通无状态 REST 服务一样部署到 Cloud Run 或 Kubernetes，预计 6 月的新规范里落地。
  • 改进异步 Task 原语，他说这其实就是 Agent 之间的通信。现在的实验版本很少有客户端支持。
  • 发布 TypeScript SDK v2 和 Python SDK v2。他问谁在用 FastMCP，很多人举手，他说 FastMCP 比官方 Python SDK 好得多，“这怪我，Python SDK 是我写的”，现在有更好的 Python 开发者在帮他重写。
  • 面向企业的 Cross-App Access：和身份提供商（Google、Okta 等）合作，在公司身份系统登录一次，就能使用各个 MCP 服务器，不用反复登录。
  • 服务器发现：在 well-known URL 上声明 MCP 服务器，爬虫、浏览器、Agent 访问网站时能自动发现“这里有 MCP 服务器可用”，也在 6 月的规范里。
  • 扩展机制：MCP Apps 只会在网页类客户端里支持，因为 CLI 很难渲染 HTML。Skills over MCP 是他最期待的扩展：工具很多的服务器可以附带“这些工具该怎么用”的领域知识，服务器作者能持续更新 Skill，不依赖插件市场。现在给模型一个 load skills 工具就能先做出简易版。

他说 MCP 已经成立了基金会，主要以开源社区方式运作，有 Discord 和 issue，欢迎反馈。最后他展示了 Anthropic 最近上线的一个功能（模型在对话里画图表），说底层就是一个 MCP 应用。

03. Ido Salomon（AgentCraft / MCP Apps）：用即时战略游戏的方式编排几十个 Agent

直播位置 0:49:44–1:00:13

瓶颈是人

Ido 是 AgentCraft 和 MCP-UI 的作者，也是 MCP Apps 的发起人和共同维护者。他的出发点是：一个 Agent 这么好，为什么不开 10 个、20 个、100 个？开起来很容易，放进一个大屏也很壮观，但实际上不行，因为人是编排的瓶颈。工程师平时并不习惯同时管理几十个“鲁莽的员工”。他说这种技能其实藏在别处：玩过游戏的人对同时指挥几十个单位并不陌生。所以他做了 AgentCraft，一个借鉴即时战略（RTS）游戏的 Agent 编排器。

演示：从看见到反应

  • 地图上的小人就是一个真实的编程 Agent 会话，可以是 Cursor、Claude Code、Codex、OpenClaw 等，AgentCraft 能检测到本机上正在跑的会话并显示出来，也能直接在里面新建。可以用语音、文字、图片给它下指令。
  • 地图上的建筑代表功能，比如一栋楼管理 Skill 和插件，还集成了终端和 Git。
  • 可见性：侧边栏显示每个 Agent 的任务状态摘要。地图本身是文件系统的投影，目录是区域，文件显示成符文，能看到 Agent 正在改哪个文件、完整的改动列表，以及哪个 Agent 在什么时候改了什么。进一步做成热力图，就能看到冲突，甚至提前阻止冲突。
  • 反应：借用 RTS 的肌肉记忆，用快捷键在需要你处理（批准计划、回答问题）的 Agent 之间快速切换。

把人一步步移出循环

他说做到这里，能同时用的 Agent 多了，但只能维持很短时间。原因之一是人脑里同时装不下那么多点子，于是他让 Agent 自己找任务，做成“Quest”，点一下按钮，Agent 就去做重构、补测试这类他不想做的事。原因之二是照看太花时间，于是有了“Campaign”：粗略说出想要什么，系统起一个容器，让 Agent 在里面拆解、规划、把计划拿给他看，因为在容器里，随便它们折腾；拆解完由一个 Campaign 编排器负责照看，人的精力只花在规划和审查上。再往后，他用定时任务让 Agent 每天去 Twitter 扫有意思的点子并实现，他只挑要哪个，他说 AgentCraft 的“频道”功能就是这么快做出来的。

PR 多了以后，有“审查包”（Review Bundle）：每个改动附上为什么做、对应什么任务，还有截图和视频作为可视证据。审查变便宜后，规划也可以少花时间：同一件事做 10 遍，挑最合适的。

人和人、人和 Agent 的协作

他最喜欢的功能是工作区（Workspace）：他可以和团队的产品设计师共享，设计师能看到他的 Agent，他也能看到设计师电脑上的 Agent。演示里设计师的 Agent 在设计一个新页面，他可以等它完成，也可以直接把工作接过来交给自己的 Agent。还有一个人和人、人和 Agent 共用的聊天室：Agent 说“我开始做某件事了”，他回“我也在做”，下次 Agent 就知道有人在同一块地方工作，各自改哪些文件也会互相知会。

他的总结是这些不算新技能，只是我们以前没在工作里用过。AgentCraft 免费下载，还在实验阶段，有 Discord 收集反馈。

04. Mario Zechner（Pi）：在满是垃圾代码的世界里造 Pi，三幕悲剧

直播位置 1:01:05–1:18:57

Mario 是编程 Agent Pi 的作者，Pi 也是 OpenClaw 里的 Agent 内核。他的演讲分三幕。开头他说自己 T 恤上的广告位是网友出钱买的，钱全部捐给慈善。

第一幕：为什么不用 Claude Code，自己造 Pi

他先声明喜欢 Claude Code 团队，他们聪明、速度快、开创了这个品类，所以他说这场不算吐槽，就是一个老头解释自己为什么换工具。他 2025 年 4 月左右在 Peter（Steinberger，OpenClaw 作者）的推荐下开始用 Claude Code，当时它简单、可预测，适合他的工作流。后来团队变大、功能变多，bug 也变多。他说自己在工地干过活，锤子天天坏会发火，开发工具天天坏也一样。他提到屏幕闪烁问题成了梗，Ghostty 的 Mitchell（Hashimoto）也出来讲过，闪烁修好了别的又坏了，终端渲染器大概已经重写到第三版。

他说真正的问题是“我的上下文不归我管”：

  • 系统提示词和工具定义每个版本都变，工具会被删改。
  • 会在很不合适的位置插入 system reminder，内容大意是“这里有些信息，可能和你在做的事有关，也可能无关”，这会把模型弄糊涂，打断他的工作流。
  • 几乎没有可观测性，他想知道 Agent 在干什么。
  • 不能换模型，这对 Anthropic 自家的 Harness 来说可以理解。
  • 扩展性很弱，Hook 的数量和深度都很浅，每次触发 Hook 都要新起一个进程，效率不高。

他也看了别的选择。他称 Amp 和 Factory 的 Droid 是编程 Agent Harness 里的保时捷和兰博基尼，用得起就用，团队都很棒。因为自己做开源，他倾向于 OpenCode，团队也很好，但看了它的上下文处理后发现：在某些条件下会在超过一定 token 数后裁掉工具输出，等于让模型失忆；接了 LSP 服务器后，每次调用编辑工具都会去问有没有报错，再把错误塞进编辑结果，他说人写代码也不是写一行查一次错，这会干扰模型；会话里每条消息存成一个单独的 JSON 文件；默认起的服务器 CORS 头设置得让你浏览器里打开的任何网站都能访问 OpenCode 服务器。

另一条线索是基准。他研究了 Terminal-Bench（一个评测终端里编程 Agent 的基准），发现它自带的参考 Harness（Terminus）极简：只给模型一个往 tmux 会话发按键、读输出的工具，没有文件工具，没有子 Agent。可是在 2025 年 12 月的排行榜上，不管哪家的模型，用这个极简 Harness 的分数常常比该模型的原生 Harness 还高。他的两个论点：一，我们还处在编程 Agent 的“瞎折腾试错”阶段，现在的形态不是最终形态；二，我们需要更好的试错方式，对他来说就是可自我修改、可塑的 Agent。

Pi 是什么

  • 四个包：ai（跨模型供应商的抽象，支持在供应商之间交接上下文）、agent-core（就是一个 while 循环加工具调用）、一个自写的终端 UI 框架（他出身游戏开发，做了一个不太闪的）、以及编程 Agent 本身。
  • 系统提示词很短，他直接放在一页幻灯片上。业界出了 Skills 标准（就是 Markdown 文件）后，提示词里加了几行。
  • 让 Pi 能修改自己的“魔法”：随包附带他和 Agent 一起手写的文档和扩展示例代码，告诉 Agent“这是文档，这是怎样写扩展来改你自己”。
  • 只有四个工具：读、写、编辑、bash，工具定义也很短。他说模型被强化学习（RL）训练得透透的，后训练时练的就是编程 Agent Harness，你不需要一万个 token 告诉它“你是编程 Agent”。
  • 默认 YOLO 模式（不逐条请求批准）。他认为每次调 bash 弹窗让你批准算不上聪明的安全机制，每个人的安全需求不同，所以他给足够的绳子，让你按自己的需要搭。
  • 子 Agent、计划模式、MCP 支持都不内置，需要就让 Pi 给你写一个。

扩展就是 TypeScript 模块，最简单是磁盘上一个 TS 文件。扩展 API 能挂进所有环节：注册工具、斜杠命令、快捷键，监听任何事件并作出反应，在会话里存状态（可选择是否给 Agent 看，也可供分析会话的工具使用），自定义压缩（Compaction，上下文快满时把历史压成摘要）、自定义模型供应商，完全控制 TUI。打包可以发到 npm 或 GitHub，他说不需要再造一堆叫“市场”的孤岛，已经有包管理器了。所有东西支持热重载，在会话里写扩展、重载、立刻看效果，这也是游戏开发的习惯，追求极短的迭代周期。

例子：Anthropic 出了一个 /btw 命令（让你在 Agent 跑主任务时跟它插话），他在 Twitter 上开玩笑贴了一段提示词，有人五分钟就做出来了，功能还更多，不用 fork Pi，只是让 Agent 按提示写了个扩展。扩展作者 Nico 做了一个让他所有 Pi Agent 互相聊天的聊天室，UI 全是自定义的。还有人在 Pi 里玩 NES 游戏、玩 Doom。怎么写 Pi 扩展？他的回答是“你不写，让 Pi 按你的需求写，然后热重载迭代”。成绩方面，去年 10 月 Pi 还没有压缩功能时（后来为 Peter 的 OpenClaw 加上了）在 Terminal-Bench 上排第六。他说这些都不是重点，重点是拿回对自己工具和工作流的控制权。

第二幕：Clanker 时代的开源

Peter 把 Pi 放进 OpenClaw 当 Agent 内核后，Pi 的开源仓库成了大量 OpenClaw 实例的目标，它们的主人往往不知道。“Clanker”是对 AI 机器人的戏称。他展示了几个项目关闭 issue 或 PR 通道的例子，以及 OpenClaw 和他自己的 issue 列表，他说一半是 OpenClaw 实例发的垃圾。他的对策：

  • 所有 PR 自动关闭，附一条评论，请你用人类的口吻写一个不超过一屏的 issue。他看过觉得可以就回“lgtm”，你的账号名会被写进仓库里的一个文件，下次 PR 就放行。机器人发完 PR 不会回来看评论，所以这是个完美的过滤器。Mitchell 后来把这个做成了 Vouch 工具。
  • 和 OpenClaw 有过互动的账号，issue 会被降低优先级。
  • 把 issue 和 PR 文本做嵌入，投到 3D 空间里看聚类。
  • 发明“开源休假”：想关就关掉 issue 追踪，他说自己因此找回了生活。

第三幕：慢下来

他说现在什么都是坏的，有人还骄傲地说“我们的产品 100% 由 Agent 构建”，他回应“我们知道，它现在很烂，恭喜”。他列举了他认为不健康的风气：同时开一支 Agent 大军；用 Beads（他说那基本是卸不掉的恶意软件）；Anthropic 让 Agent 写了一个 C 编译器，“能用但其实不能用”；Cursor 让 Agent 写浏览器，也很破，大家寄希望于下一代模型修好；“SaaS 已死”“软件六个月内被解决”“我奶奶用 OpenClaw 给自己做了个 Spotify”。

他的核心论点：Agent 在不断累积错误，没有学习，没有瓶颈，痛苦延后，而延后的痛苦归你。一个人、一个 Agent、十个 Agent 产出的代码，你能审多少？换成每天产生的错误数，你能发现多少？有人说“我有审查 Agent”，他说那是衔尾蛇，能抓到一些问题，但不够。

  • Agent 的复杂性是从互联网学来的，而互联网上 90% 的代码是我们过去的垃圾，只有少数设计良好的系统。
  • Agent 的每个决定都是局部的，代码库大到装不进上下文时更明显，于是到处加抽象、重复代码、向后兼容、层层防御，“两个人加十个 Agent，两周就能得到企业级复杂度”。
  • “我有详细的规格说明”：足够详细的规格说明就是程序。你留空白，模型就用它从互联网学来的平庸代码去填。
  • “人也会犯错”：人是会犯错，但人能学习，人是瓶颈，每天能往代码库里加的错误有限；而且人会痛，痛多了会辞职、甩锅，或者大家一起重构。Agent 会一直往代码库里堆，AGENTS.md 和复杂的记忆系统救不了你，Agent 的学习方式和人不同。
  • “我已经不读代码了”：出了事、用户在叫的时候你找谁？你没读过代码，只能靠 Agent，而代码库已经大到 Agent 拿不全需要的上下文。他说长上下文窗口是权宜之计，今年大家都换到百万 token 上下文后会发现这一点；Agentic Search（Agent 自己搜代码）也在失效。Agent 局部打补丁、全局搞砸，最后你既不能信代码，也不能信测试，因为测试也是 Agent 写的。

他建议的用法：给 Agent 的好任务要有边界，能保证它找到需要的一切，所以要把代码库模块化；如果还能给它一个评估函数就更好（爬山式优化、自动研究）。非关键的、无聊的代码随便让它写；用户报告的 bug 往往信息不全，让 Agent 做复现最合适，他早上已经不再花时间做这件事；身边没人时也可以当小黄鸭。做完要评估，挑合理的部分，他说大部分不合理。

最后一页：慢下来，想清楚你在做什么、为什么做；学会说不，少做功能，做重要的那些，再用 Agent 把它们打磨好；控制需要审查的生成代码量；关键代码每一行都读。怎么知道哪些是关键代码？读代码。重要的东西手写，可以让 Agent 帮忙，但别让它替你做决定。他说摩擦是在你脑中建立系统理解的东西，也是你学新东西的地方，这些都需要纪律和能动性，也仍然需要人。

05. Armin Ronacher 与 Cristina Poncela Cubeiro（Earendil）：摩擦就是你的判断力

直播位置 1:19:33–1:37:26

两位讲者

Armin 开场放了一张图：某公司因为一次配置变更引发安全事故，事故说明帖的社交预览图上自动带出了该公司的营销口号“无摩擦地发布”（ship without friction）。他们这场就是想劝大家加一点摩擦。

Armin 做了 20 年软件开发，大部分在开源领域，是 Python 框架 Flask 的作者。他说 Flask 在模型权重里分量很重，现在很多人是因为机器在生成 Flask 代码才知道它的。他去年 4 月离开 Sentry，正好赶上 Claude Code，于是一头扎进 Agent 工程，在博客上写了很多。去年 10 月他和朋友创办了 Earendil。Cristina 在 Earendil 工作，之前在 Bending Spoons。她称自己是“AI 原生工程师”：这些工具出现的时间比她当工程师的时间还长，她就是靠它们学会这份工作的。

他们和 Agent 一起开发了 12 个月左右，有过很大的杠杆，也有过很大的失望，反复遇到两类问题：心理问题和工程问题。他们说自己也没有全部答案。

心理问题：从乐趣变成压力

Cristina 讲了这个转变：一开始提示来提示去效果一般，某天突然开窍，工具变得很有用，那时用的人少，等于多出了时间，工作也更有趣。很快所有人都在用，基线预期变成“你必须用”，乐趣和空闲变成了压力：要发布得更快，产出更多代码，没时间审查，没时间思考。

她说陷阱有两层。一层很多人讲过：这些工具让人上瘾，你永远不知道下一个提示是让产品跑起来的那一个，还是压垮产品的最后一滴垃圾。另一层大家意识得少：产出很快，让我们误以为自己更高效，实际上效率反而降低了，因为没时间停下来设计、问自己有没有更好的实现方式。人处在这种心流里很难自己停下来，Agent 更不会停，它在到处读本不该读的文件。所以得由人来掌控。

Armin 补充了团队层面的变化，他花了很久才意识到：过去团队受写代码速度限制，写和审的比例大体平衡；现在每个工程师的产出能力远高于审查能力，PR 堆积起来。同时参与工程的人在变多，他听很多工程师说市场部的人开始提交代码，以前当过工程师的 CEO 又开始写代码，但这些人在公司里的角色并不承担代码的责任，责任仍在工程团队。参与写代码的人和机器的数量，超过了能承担责任的数量，而机器还不能为代码变更负责。结果是越来越多的代码审查被跳过或走过场。收到一个 5,000 行的 PR 时最该思考，可这也是最让人想放弃的时候，而大家在制造越来越大的 PR，因为现在写代码是免费的。

工程问题：Agent 写出的代码更脆

Armin 说 Agent 被优化成“写出能跑的代码，跑测试，取得进展”，强化学习把这一点刻进去了。所以它会写出人类工程师学写代码时不会写的东西。他的例子：读配置文件，读不到就加载默认值。工程师知道这不好，因为你可能根本没发现读的是默认配置，两小时后才发现已经用错误数据写了数据库记录。机器倾向于让自己不被卡住，结果制造出比人写的代码多得多的失败路径。人写这种代码时心里会不舒服，Agent 没有感受。这样的服务表面上能从局部故障中恢复，整体却很脆弱，而且代码库很快会大到 Agent 自己都挖不出来：它开始不读该读的文件，在新文件里重写别处已有的逻辑，熵越来越高。

库和产品的差别，以及“Agent 可读的代码库”

Cristina 说他们发现 Agent 写库（Library）比写产品好得多。库的问题定义清楚，功能能映射到 API 表面，约束紧，核心通常简单、可插拔。产品有 UI、API 响应、随功能开关和计费变化的权限等大量交织的组件，Agent 不可能把这些全装进上下文窗口，局部很合理，全局就“有点痴呆”。他们的提议是：代码库现在是基础设施，要设计成对 Agent 可读（Agent Legible）。

  • 模块化，组件之间界限清楚。也包括把代码流程模块化：她在重构一个 AI 助手时，把“收到用户消息、交给 Agent 循环、处理输出”这几个关键节点定义清楚，结果发现 Agent 最爱在节点之间乱加东西，比如在各种类型之间来回解析、往状态里塞不该有的东西，产生你不想支持的行为。
  • 遵循众所周知的模式，别和 RL 对着干，越顺着它输出越好。
  • 核心简单，复杂性推到其他抽象层。
  • 不要隐藏的魔法：比如 React Server Actions，或用 ORM 代替原生 SQL，会把意图藏起来，Agent 看不到的东西就不可能遵守。

他们在公司里用的机械化约束，大部分通过 Lint 规则实现：不许裸 catch-all；SQL 统一走一个查询接口，免得 Agent 到处找，漏掉一处就出事；UI 只用一个基础组件库，不许直接写原生 input；不许动态 import；强制函数名唯一，除了可读性，也为了 token 效率，Agent grep 一个功能时只得到一个结果，后续循环会顺利得多；最近在试 TypeScript 的 erasable syntax only 模式，代码基本就是 JavaScript 加类型注解，没有转译这一层，代码和编译器只有一个事实来源，Agent 找错误时不会搞混。

用 Agent 唤醒人的判断

Armin 说要找到办法去感受 Agent 感受不到的痛。他们给 Pi 写了一个审查扩展，把审查意见分成两类：一类是机械性的 bug、明显违反 AGENTS.md 的地方，可以直接交还 Agent 自动修；另一类专门标出需要人重新动脑的改动，比如数据库迁移，要看锁、看生产数据量，绝不该在没有人判断的情况下合入；权限变更，往往文档不全；新增依赖，他要自己去看这个依赖值不值得引入、维护者是否可信。这些是他们“漏了就后悔”的教训。看到这类标注时，人会有一点被刺一下的感觉，然后进入状态。

他承认速度让人上瘾，很爽，但在不该依赖速度的地方依赖它很危险。他觉得 Agent 净收益明显的地方：客户报的问题，让 Agent 完美复现，得到一个好的起点；探索不同的产品方向，只要不承诺用它生成的代码。系统架构、系统可靠性则需要慢下来。几周甚至几天就能制造出几个月的技术债，对自己代码的理解一下降就很难找回。他说自己发现过生产中根本不工作的代码，而那是他和 Agent 一起提交的，当时没看出来，这种发现自己才是搞砸的人的感觉很失望，也说明人很难客观判断代码库的状态。

最后他说，每个工程团队都说要去掉发布流程里的摩擦，很多摩擦确实该去掉。但大公司里的 SLO（服务等级目标）就是有意设计出来的摩擦，逼你想清楚是否需要这样的可靠性、服务有多关键、人手够不够。有了 Agent，大家想把这些全去掉，其实我们需要它们。从物理上说，没有摩擦就没法转向。摩擦是你的判断力和经验所在。

07. David Gomes（Cursor）：用 Markdown Skill 替掉 15,000 行 worktree 代码

直播位置 2:26:10–2:44:33

原来的 worktree 功能

David 在 Cursor 工作，这场讲他们怎样把一个完整功能（大量代码、依赖、复杂度和测试）换成一个轻量的 Skill。他先介绍 Git worktree：同一个仓库的多个独立检出（Checkout），不同 Agent 可以在各自的 worktree 里并行工作，互不干扰。在 Cursor 里可以让 Agent 跑在单独的 worktree 上，同一个文件在两个 worktree 里内容不同；Agent 运行的命令、Lint 都限定在那个 worktree 里；可以在屏幕上开一格一格的 Agent；让它开 PR，它就从那个 worktree 开。

他们还有 Best-of-N：把同一个任务同时交给不同模型，比较结果；如果是前端项目，还能预览各个实现的视觉效果，挑喜欢的那个。这些功能去年 10 月随 Cursor 2.0 上线，实现很复杂：创建和管理 worktree、把它作为上下文喂给 Agent、确保 Agent 被隔离、出不了 worktree；用户可配置的 setup 脚本，每次 Agent 进入 worktree 时运行；一个评委（Judge）模型给各实现打分，界面上点赞图标标出最好的那个；在 Harness 里加 system reminder 让 Agent 别跑偏；还要清理，因为有人开几百个 worktree 把磁盘撑爆。

新做法：Skill 加子 Agent

他最近开了一个 PR 删掉整个功能，大约删了 15,000 行代码。新实现几乎一样好，维护起来轻得多，还有一些新好处。用到的两个原语都是 Cursor 已有的：Agent Skills 和子 Agent（Subagent）。

  • /worktree：一段 Markdown 指令，告诉模型怎样创建 worktree、运行用户配置的 setup 脚本、之后一直待在这个检出里。演示是“修一下网站页脚的错别字”，Agent 在隔离的 worktree 里完成。
  • /best-of-n：更短，一屏放得下，大约 40 行。指示父 Agent 为每个模型起一个子 Agent，每个子 Agent 建自己的 worktree 并在里面工作，等所有子 Agent 完成后给出点评，最好打分、批评、用表格帮用户选。原来这部分大约 4,000 行代码。
  • /apply-worktree 把旁边 worktree 的改动搬回主检出，/delete-worktree 删除。

写 Skill 时要考虑跨平台，Windows 和 Linux/macOS 各有指令；要让父模型给每个 worktree 跑 setup 脚本；最难的是让模型留在 worktree 里，他们靠“激进的提示词”。严格说这些在 Cursor 里是命令（Command）不是 Skill，但工作方式几乎一样，提示词只在用户选用时才加载进上下文。做成命令是为了让提示词放在 Cursor 后端控制，他改进提示词后，用户下次使用就拿到最新版，不用升级客户端。

Best-of-N 的演示把同一个任务交给 Kimi、Grok、Composer、GPT 和 Opus，父 Agent 起五个子 Agent，各有自己的 worktree 和上下文，Opus 照例最慢。结束后父 Agent 比较：这两个基本做法一样，这个做了别人都没做的事。你还可以说“我喜欢 Opus 的这部分和 GPT 的那部分，合起来”，父 Agent 会帮你合。

得与失

好处：

  • 要维护的代码少得多。这是高级功能，用的只是一小部分喜欢并行的重度用户，不值得花大量维护时间。
  • 聊到一半可以切到 worktree，以前不行，因为他们不想在输入框里塞一堆下拉菜单。
  • 多仓库也能用了。前后端分仓很常见，以前这种情况 worktree 直接被禁用；现在 Agent 会在每个仓库建 worktree，开 PR 时开两个。
  • Best-of-N 的评判好得多，父 Agent 对每个子 Agent 做了什么有更多上下文，还能拼接不同实现，以前只能选一个。

坏处：

  • Agent 很难一直待在 worktree 里。以前物理上不可能碰 worktree 之外的文件，现在只能信任模型，他说这有点靠感觉。长会话里模型容易忘记该在哪工作，差一些的模型会胡来。
  • 感觉更慢，因为你在聊天里看着 Agent 建 worktree，其实并不慢。
  • 更难发现。原来打开 Cursor 有个下拉框选本地、云端还是 worktree，现在没了，你得知道有 /worktree 才能用。论坛上反馈褒贬不一，有人习惯了旧方式不高兴。

怎样改进：Eval 和 RL

两条路。一是 RL：Cursor 训练自己的模型 Composer，Composer 2 的成千上万个 RL 任务里没有一个是在这种 worktree 环境下操作的，他们正在往 RL 流水线里加这类任务，让 Composer 3、4、5 做得更好；别家的模型他们改不了，但一直在给各家实验室反馈。

二是评测（Eval，用一组固定用例自动检查模型或系统表现）。他说自己刚开始写 Eval，用 Braintrust 发现很容易，几乎不用懂什么，让 Agent 写就行。做法是启动无头（Headless）的 Cursor CLI，配两个评分器：一个检查模型有没有在 worktree 里干活，另一个反过来检查有没有在主检出里干了不该干的活。目前的 Eval 还很简单，模拟不了很长的会话（那才是模型变差的时候），但已经能看出差别：Haiku 这种小模型经常跑到主检出去干活，Composer 和 Grok 表现好得多。下一步是找出规律改提示词，并加更好的 system reminder。

接下来

他们会退一小步：最近发布的 Cursor 3.0 有一个更偏 Agent 的新界面（仍可看代码和改代码，但 UI 围绕 Agent 和聊天），他们认为那里适合做一个完整的原生 worktree 实现，因为喜欢本地并行的人也更可能用这种界面。Skill 会继续通过 Eval 和训练改进。他们也在研究 Git worktree 之外的本地并行原语，因为 worktree 创建慢、占磁盘，而且只能用于 Git 仓库。

09. Sarah Chieng（Cerebras）：快模型需要慢开发者，Codex Spark 每秒 1,200 token

直播位置 3:08:39–3:25:54

介绍她之前，Tejas 现场问大家最常用的编程模型，最多人喊 Opus。他说自己最近的做法是让 Cursor 的 Composer 2 很快解决问题，再把 diff 交给 Opus 评审，Opus 每次都回 LGTM。他说我们总觉得快的模型一定差，其实不一定。

慢模型养成的坏习惯

Sarah 是 Cerebras 的开发者体验负责人，Cerebras 在做世界上最大、最快的 AI 处理器，她的工作之一是让开发者第一次用上快速推理。她说过去几年代码生成很慢，开发者养成了一些坏习惯：写超长的提示词想一次搞定，提交巨大的 commit，屏幕上同时开 10 个 Agent 在“思考”。

大约一个月前，Cerebras 和 OpenAI 发布了 Codex Spark，生成速度每秒 1,200 个 token；Sonnet、Opus 系列大约每秒 40 到 60 个，相差 20 倍。她说如果习惯不改，以前每秒 50 个 token 的烂代码会变成每秒 1,200 个 token 的烂代码。过去两年模型变大变聪明、上下文变长，但速度基本没变，Gemini、Claude、GPT 各家一直在每秒 50 到 150 token 之间，Codex Spark 快到图表纵轴得重画。

为什么模型突然变快：整个推理栈同时在优化

  • 硬件：最大的问题是内存墙。推理时要不断在内存和芯片之间搬运权重和 KV Cache（缓存的注意力中间结果，避免每步重算），她说这部分占推理延迟的 50% 到 80%。NVIDIA GPU 的内存在芯片外的 HBM 上，带宽是瓶颈。Cerebras、Groq 这类公司把内存尽量挪近芯片，Cerebras 的晶圆芯片把内存以 SRAM 形式分布在整片芯片上，每个核心都能直接取到需要的值。
  • 分离式推理（Disaggregated Inference）：推理分两步，预填充（Prefill）并行处理用户输入的所有 token，受算力限制；解码（Decode）逐个生成输出 token，是串行的，受内存限制。传统上两步在同一块硬件上跑，现在拆开，预填充放在算力优化的硬件上，解码放在内存优化的硬件上。她说这在最近几个月开始商业化，这也是 NVIDIA 几个月前花 200 亿美元买 Groq、Cerebras 和 AWS 合作把晶圆芯片与 Trainium 搭配提供服务的原因。
  • 模型结构：层的维度、显存和模型大小都在迁就硬件。MoE 让模型有大模型的智能、小模型的算力成本。在此之上还有 REAP（Router-weighted Expert Activation Pruning），看在具体场景里哪些专家根本没被激活，直接剪掉。
  • 推理优化层：Together、Baseten、Modal、Fireworks 等公司在做，最重要的是 KV Cache 复用。

开发者这一层的打法

她展示了网上流行的画面：同时开六个 Claude Code 终端、500 多个 Agent 的编程蜂群、五块屏幕八个 Agent。她理解这种诱惑，Twitter 会让你觉得不这样就活在石器时代。但现实是大量代码没人验证，推理更快以后这更危险，技术债会以前所未有的速度产生。她的建议分几类：

  • 按模型长处编排。以前选模型看智能和成本，现在多了速度这一维。用 GPT-5.4 这类大模型做规划和长程任务，用 Codex Spark 这类快模型当执行者：大模型出计划，再用 Codex Spark 起子 Agent 逐步执行。另一个技巧是把成功的会话做成 Skill：先让大模型做一次较难的任务，把轨迹存成可验证、可重复的 Skill，再让快模型在后台一遍遍执行。
  • 验证几乎免费。每秒 1,200 token 时，测试、Lint、pre-commit hook、diff 审查、浏览器 QA 自动化都可以放进每一步，不必留到最后推送前。
  • 多生成再挑。她要一个午夜蓝、四个图标的导航栏，结果还行；用快模型可以在原来生成一版的时间里生成 15 版，再开五个子 Agent 各生成 15 版就是 75 版。适合看重数量和多样性的事情：研究方向、架构方向、平面设计。她说这相当于人为地给模型输出加入品味，模型本身没有品味，过去的绕法是自己做示例、找示例，或者把提示写得详细到不如自己做。
  • 当成结对编程。模型快了，就不该开个会话去吃汉堡刷 Twitter 再回来，应该坐下来实时协作：让它收集整个仓库的上下文，问它这块怎么工作，人坐在驾驶位做决定，AI 的角色始终是帮你做决定。
  • 避免垃圾代码（Slop）。别开 10 个 Agent 从不验证、被人问起才第一次读代码；开两三个会话，坐在代码旁边引导。可以很具体：禁止删除文件，限制最大 diff，只许读写，实时下指令，比如“只改这里，类型先别动”“刚才那个实现不对，重来”。
  • 持续重构。和验证一样，每完成清单上的一项就自动让模型删掉没用的 import、清理多余代码、统一函数结构。
  • 上下文管理更要紧。以前 10 分钟才填满上下文、触发压缩，快 20 倍就是 30 秒一次。大任务一定拆成小的有界目标，避免上下文占用到 80% 到 100% 触发压缩丢信息。

她推荐一个四文件的外部记忆系统，每次新会话都能接上：AGENTS.md 定义 Agent 和子 Agent；PLAN.md 在开始时生成完整计划和逐步清单；PROGRESS.md 记录做了什么、还要做什么，新 Agent 没有上下文，进来先看它就知道从哪接；VERIFY.md 在每一步用来检查代码干净、可以进入下一步。组合方式还是 GPT-5.3/5.4 Codex 出计划，GPT-5.3 Codex Spark 逐条执行。最后一页是 Codex 的几个实用命令（权限、实验性 Skill、review、rename）。她说重点不在快本身，而在开发体验会好很多，避免写烂代码的方式不再那么折磨人，不必盯着屏幕等 30 分钟。

一：让 Agent 能用你的 Eval

他说 Eval 就是 AI 的单元测试：给提示词一段输入，运行，得到输出，按评分标准判定通过或失败。incident.io 全部用 Go 写，Eval 文件就放在 Go 提示词旁边，改提示词合并之前先证明它会做你想要的事。他用一个故意很傻的提示词举例：把一条消息翻译成海盗腔。评分标准两条：输出像海盗腔；含义和输入一致。Eval 是一个 YAML 文件，列了三个测试用例。

问题是：真实的测试数据很难造，他们的生产 Eval 常常要包含几乎整个事故，只有那样才能触发坏行为。他们早期做了一个按钮，能把生产中出问题的交互“偷”下来放进代码库当 Eval。但这样的 Eval 动辄两兆的 YAML，不像好的单元测试那样聚焦，而且太大，编程 Agent 读进来就撑满上下文，没法用。

解决办法是一个小 CLI，叫 eval tool，让 Agent 能列出用例、编辑、替换、新增。有了它，他们写了一份给编程 Agent 用的 runbook（也可以打包成 Skill）：你告诉 Agent“这个提示词有问题，我希望它这样做”，Agent 先加一个能证明失败的 Eval 用例，再改提示词让它通过，然后检查没有打破其他用例，最后再做一轮精简提示词，因为反复这样改，提示词会越来越长。他演示在 Claude Code 里对一个真实提示词（把人的问题转成 Loki 日志查询）跑这套流程，Agent 加用例、按设定次数重复跑、确认通过率可接受。

二：把调试 UI 变成可下载的文件系统

上面只解决了“已知要改哪个提示词”的情况。生产 AI 系统往往是很多提示词。他画了他们事故内聊天机器人背后的提示词、工具、Agent 层级图，大约 10 个 Agent、50 多个组件，屏幕都放不下。调查系统更复杂，每个步骤展开是一条链路，每个绿色块里又可能有几百次提示词和工具调用，任何一处细小错误都可能导致整个根因分析（RCA）错误，却很难追溯源头。他们做了给人看的 UI，但人没时间看，Agent 又用不了这些 UI。

他说 Anthropic 做 Claude Code 时发现 Agent 很擅长用标准工具浏览文件系统，于是他们把 UI 里的全部内容做成可下载的文件系统，丢进沙箱里的 Claude Code。Agent 能看到所有提示词的输入，结构自带说明，再加上代码库，它能告诉你应该改系统的哪个地方，然后用前面的 Eval 红绿循环去改。链路追踪也可以原样转成文本文件，LLM 读起来很顺。现在他们的调试流程变成：听说某次体验不好，把那次交互下载进沙箱 Claude Code，问它“你觉得哪里出错了”“我其实想要这样，你会改哪部分”，它沿着工具和提示词的层级找到位置，在同一个会话里直接改，再用 Eval runbook 证明。

三：可重复的分析流水线

单次可以这样做，但他们每天在几百个客户账号上跑几千次调查，需要知道系统在变好还是变差。他们有回测（Backtest）：每天对自己的账号和一批客户账号跑一批调查，最后得出一个汇总数字，比如自己账号上 RCA 准确率 86%。但这个数字不告诉你为什么涨、为什么跌。

于是他们把这些调查也下载成文件系统，交给一个由 Claude Code 驱动、用 Markdown playbook 规定步骤的分析流水线，放在一个叫 scrapbook 的仓库里。要点：

  • 先并行，比如同时起 25 个子 Agent，每个分析一次调查。
  • 再做群组聚类，找同类的失败模式，最后得到一份报告，说明系统在这个客户账号上为什么表现好或坏、该怎么改。
  • 所有分析结果存成文件放在下载目录里，增量积累，可以中断和恢复。
  • 结合驱动系统的代码库，发现问题时直接定位到代码，提出修改方案。
  • 最后在同一个会话里让 Claude Code 或 Codex 去改，用 Eval 红绿流程确认。

他展示了一个这样产生的 PR：回测显示几次调查出错，他知道问题所在，和 Agent 讨论了一个要改的功能，部署后在生产中观察效果。他的结论：调试工具要优先做到让编程 Agent 好用；文件系统是极好的 Agent 上下文，他说在这上面套 MCP 或让 Agent 操作 UI，效果都不及一次性批量下载所有信息让 Agent 去翻；凡是复杂分析，都写成 AI runbook，能省下几天甚至几周。最后他说 incident.io 在伦敦招人。

11. Luke Alvoeiro（Factory）：能连续跑好几天的多 Agent Missions

直播位置 3:45:47–4:03:32

瓶颈是人的注意力

Luke 出身开发工具领域。两年半前他在 Block 发起了一个项目，后来成了开源编程 Agent Goose，最近捐给了 Agentic AI Foundation。现在他在 Factory 负责核心 Agent Harness，Factory 的目标是把自主性带到整个软件开发生命周期。

他的主张：软件工程现在的瓶颈不是智能，是人的注意力。最好的工程师一次也只能推进几个任务，积压了 50 个功能，每天只能推几个，因为每个任务都要他关注、每个 commit 都要他审。模型已经足够聪明能想清楚这 50 个任务，缺的是监督它们实现的带宽。所以他们想：人决定做什么，系统想办法怎么做，Agent 连续工作几小时、几天，你回来时工作已经完成。

多 Agent 的五种模式

  • 委派（Delegation）：一个 Agent 派生另一个，比如“去把数据库 schema 弄清楚”，拿回结果。最简单，大多数人先做这个，编程工具里的子 Agent 就是。
  • 创建者与验证者（Creator-Verifier）：一个做，一个查。写代码的 Agent 有沉没成本偏差，希望代码能用；带着新上下文的 Agent 更容易发现问题，人做代码审查也是这个道理。
  • 直接通信：Agent 之间像私信一样直接对话，没有中央协调者。难做好，状态会散落在各段对话里，没有单一事实来源。
  • 协商（Negotiation）：围绕共享资源沟通，比如都要用同一个 API、改同一块代码。不一定是对抗，最好的情况是双赢的交换。
  • 广播（Broadcast）：一个发给多个，比如状态更新、新的共享约束。不显眼，但对长任务保持一致性很重要。

Missions 的三角色架构

Missions 组合了其中四种（委派、创建者与验证者、广播、协商）。你描述目标，通过对话确定范围，批准计划，系统就去执行几小时或几天。一个 Mission 由一群通过结构化交接和共享状态通信的 Agent 组成，不是单个 Agent 会话，分三种角色：

  • 编排者（Orchestrator）：负责规划，像一个参谋，问你关键的战略问题，检查需求里不清楚的地方，最后产出包含功能、里程碑和“验证契约”（Validation Contract）的计划。验证契约在写任何代码之前就定义“完成”是什么意思。
  • 工作者（Worker）：负责实现。每个功能交给一个上下文干净的 worker，没有积累的包袱，注意力不衰减；读规格，实现，用 Git 提交，下一个 worker 继承一个干净的、能工作的代码库。
  • 验证者（Validator）：负责检验。大多数系统跑 Lint、类型检查、测试，也许做代码审查；Missions 都做，还验证行为，问的是“端到端能不能用”。

验证契约和两种验证者

他说用过编程 Agent 的人都见过：Agent 写功能、写测试、测试通过、覆盖率满，但测试是照着代码写的，不是照着代码要做的事写的。实现之后写的测试抓不到 bug，只是确认已经做出的决定，依赖这种验证系统迟早会漂移。验证契约在规划阶段写，独立于实现定义正确性。复杂项目可能有几百条断言，每个功能分配一条或多条，所有功能加起来要覆盖全部断言。

每个里程碑结束后跑两种验证者：一是审查验证者（Scrutiny Validator），跑测试、类型检查、Lint，并为里程碑里每个完成的功能起专门的代码审查 Agent；二是用户测试验证者（User Testing Validator），像 QA 工程师一样把应用跑起来，通过 Computer Use 之类的方式填表、检查页面渲染、点按钮，确认功能流程整体可用。后者慢得多，他们发现 Mission 的大部分墙钟时间花在这里，等待真实执行，生成 token 反倒花得少。两种验证者之前都没看过代码，对实现没有投入，所以验证在设计上就是对抗性的。

结构化交接

worker 完成后不能只说“做完了”，要填一份结构化交接：完成了什么，没完成什么，循环中跑过哪些命令、退出码是什么，发现了什么问题，是否遵守了编排者为它定的流程。错误在里程碑边界被抓住，纠正工作被重新界定，Mission 靠强制写下来再处理把自己拉回正轨，不靠 Agent 记性。他们最长的一次 Mission 跑了 16 天，比一个完整冲刺周期还长，他们认为能跑到 30 天。

串行，而不是大规模并行

最显然的想法是并行：10 个 Agent 同时跑，10 倍吞吐。他们试过，在软件开发里不太行：Agent 会互相冲突、覆盖彼此改动、重复劳动、做出不一致的架构决定，协调开销吃掉速度收益，还烧 token。Missions 按功能串行，同一时刻只有一个 worker 或 validator 在跑；在功能内部，只读操作可以并行，比如搜代码库、查 API，验证者里的代码审查也并行。纸面上慢，错误率大幅下降，对跑好几天的任务，正确性会累积。

普通聊天界面不适合跑好几天的东西，所以他们做了 Mission Control：一眼看到完成了多少、预算花了多少，当前 worker 在干什么，读交接摘要看 worker 或 validator 发现了什么、接下来怎么调整方向。你可以当项目经理盯着，也可以晚上出去和朋友玩。

每个位置放合适的模型

规划适合慢而细的推理，实现适合快速流畅、有创意的代码能力，验证需要精确遵循指令，没有一个模型或一家供应商三样都最好。他说用 Missions 需要一种新技能，内部叫“Droid 驯兽术”（Droid Whispering）：能在脑中模拟不同 LLM 怎样互动、在哪里失败、失败在多天运行中怎样放大，再有意识地决定哪个模型坐哪个位置。Missions 原型的作者 Theo 定了默认模型配置，他们鼓励用户按项目改。比如验证可以用完全不同的供应商，避免被同样的训练数据带偏。他说你只和最弱的一环一样强，锁定一家供应商就受限于那一家最弱的能力，这是模型无关架构的结构性优势。反过来，验证契约和里程碑检查点也能弥补非前沿模型的不足，用开放权重模型也能把 Missions 跑得很成功。

一个 Slack 克隆的数据

  • 60% 的时间和 60% 的 token 花在实现上。
  • 验证从来没有一次通过，几乎总要新增后续功能，说明这个 QA 循环有价值。
  • 最终代码里 50% 的行是测试，测试覆盖率 90%。
  • 大量使用提示缓存（Prompt Caching）来抵消长任务的成本。

企业用户用 Missions 一夜之间做出新想法的原型、快速搭内部工具、跑大型重构和迁移、做 ML 研究，以及把代码库现代化，让 Agent 在里面更高效。

苦涩的教训

做多 Agent 系统的人都怕下一个模型一发布，自己的架构一夜过时（他引的是“苦涩的教训” The Bitter Lesson：通用方法加算力终将胜过手工设计）。所以他们要求系统随模型变强而变强：几乎所有编排逻辑写在提示词和 Skill 里，没有做成硬编码的状态机。怎样拆解功能、怎样处理失败，总共约 700 行文字，改其中四句话就能显著改变执行策略。worker 的行为由编排者为每个 Mission 定义的 Skill 决定。确定性的逻辑很薄，只做记账：跑验证、交接问题没处理时阻止进展。Missions 保证纪律，模型提供智能，用的是模型已经熟悉的原语，比如 AGENTS.md 和 Skill。

他说经济账在变：五个工程师原来能同时推 10 条工作流，用 Missions 也许能到 30 条，团队可以专注架构和产品决策。而且代码库最后比开始时更干净，端到端测试、单元测试、Skill 和结构让之后的 Agent 和人都更高效。还没解决的问题有：怎样让 Missions 内部更多并行以跑得更快，怎样把多个 Mission 编排成更复杂的工作流。他建议大家打开 Droid 试 Missions，和编排者争一争范围，批准计划，然后去做别的事。

13. Ben Burtenshaw（Hugging Face）：让编程 Agent 做 AI 系统工程，从 CUDA kernel 到自动研究

直播位置 5:41:46–5:59:30

Ben 是 Hugging Face 的机器学习工程师，维护 Hugging Face 的 Agents 课程、MCP 课程、LLM 课程等。他的两个要点：编程 Agent 可以去啃 AI 里最难的工程问题，也就是系统工程和机器学习工程；为此需要标准化的仓库放在 Hub 上，很多已经有了。他说编程 Agent 最近几个月越过了一个接受度门槛，更多人在用，那么工程师怎样保持职业竞争力？他的建议是离硅更近，去做更难的问题。他把演讲分成三个越来越难、越来越自主的“Boss 关”。

第一关：写 CUDA kernel

Kernel 是模型在 GPU 上运行时真正执行计算的函数，用针对特定硬件的语言写，可以利用别的硬件没有的特性。自定义 kernel 针对某个数学运算把硬件榨干，让模型推理更快。过去大家认为 Agent 写不了 kernel，因为需要复杂的 DSL，还得接上硬件做基准和测试。他说这在多数情况下是错的：看 GPU MODE 社区的 kernel 黑客松、最近的 AMD 黑客松、KernelBench 这类论文，Agent 能写出正确且优化过的 CUDA kernel，他自己也参与 GPU MODE。问题是写出来以后怎么分发，怎么进入推理引擎真正被用上。

他解释了深度学习效率的三部分：计算（矩阵乘法等实际运算，FLOPs）、内存（把张量在慢内存和快内存之间搬运的时间）、开销（Python 环境、PyTorch 分发 kernel 等其余一切）。很多人以为计算是瓶颈，其实多数情况是内存：一块 H100 每秒能算约 1 PFLOP，内存带宽却只有约 3 TB/s，GPU 经常闲着等张量。FlashAttention 是优化 kernel 的代表，思路是提高算术强度（Arithmetic Intensity），每读写一次做尽量多的运算，也就是“让 GPU 保持热”。还有安装上的麻烦：硬件、软件、CUDA 版本组合成一个很大的兼容矩阵。

Hugging Face 有一个叫 kernels 的库，由 kernel 作者维护，正在扩展到 Agent 工作负载。它是分发 kernel 的方式：一个 TOML 文件声明支持哪些硬件、需要哪些 CUDA 等软件版本；kernel 现在和模型一样是 Hub 上的仓库，能看到各硬件的兼容性。他说你可以像发布模型一样发布 kernel，这对想拓展职业的 AI 工程师是一片沃土。

怎样帮 Agent 做这件事？用 Skill。他喜欢把 Skill 保持简单，就是基于文件的上下文，能打开关闭、能做版本管理，Agent 需要时打开。他说 Skill 把任务从零样本（Zero-shot）变成少样本（Few-shot），也就是给 Agent 示例。Hugging Face 的做法是每个项目自己维护本项目的 Skill，这样更稳；更实验性的放在 huggingface/skills 仓库。kernels 的 Skill 侧重基准测试，附带脚本和示例。他们用它给 Qwen3-8B 在 H100 上生成了 kernel，提速 94%。他说这不是该模型的最好成绩，重点在兼容矩阵：很多模型的 kernel 没有为你要用的那代硬件优化过，比如你云厂商那里便宜的卡，这里有容易摘的果子。

怎样知道 Skill 好不好？他们维护一个开源库 upskill：生成 Skill，为它生成 Eval，再比较不同模型用同一个 Skill 的表现。他展示的结果里，GPT-OSS 用同样 token 准确率略低，Kimi 更准且 token 更少，Haiku 也更准、token 更少。常用某个 Skill 又想省钱换模型时可以用它迭代。

第二关：让 Agent 训练模型

他讲得很快，说前一天同事 Merve 有专门的演讲。Hugging Face 去年年底发过博客，让 Claude 做微调：直接说“在这个思维链数据集上微调 Qwen3-6B（字幕如此）”，现在已完整集成到 Hub，GPU 也能在 Hub 上跑，用的是 HF CLI 的 Skill。还有一个和 Unsloth 合作维护的版本，更便宜，博客附近常有免费额度。

第三关：多 Agent 自动研究实验室

Andrej Karpathy 大约一个月前发布了 autoresearch，基于他的 nanoGPT 和 nanochat，让 Claude Code 改训练脚本来改进训练过程，每次实验改一处，用 bits per byte 衡量效率，最后得到最好的结果。Ben 觉得一个 Agent 单线程找改进、实现改进有点怪，于是把它分布成一个研究团队，四种角色：

  • 研究员：文献侦察，用 HF Papers（有 CLI，能直接从 Hub 搜论文）或 arXiv 找点子，写成假设。
  • 规划者：接收假设，维护一个任务队列。
  • 工作者：领取假设，实现为训练脚本，比如改一处结构或一个参数，通过 HF Jobs 在 Hub 上用需要的硬件跑。
  • 报告者：监控所有任务，维护一个看板。

结构上是一个 Git 项目：main 分支维护训练脚本和一个存分数的数据结构，每个实验一个分支，另留一份原始训练脚本。他这次的演示用 OpenCode，仓库里也有 Codex 和 Claude 的实现，还在 Gas Town 上实现过，但那是“狂野西部”，放在单独的项目里。他说这更多是一个概念实现，哪里都能跑。

在 OpenCode 里他建了一个叫 autolab 的 Agent 配置，提示词大意是“在仓库里按既定角色跑一轮自主本地研究：让 planner 提出最多两个新的单变量实验，让 reviewer 否掉重复或过时的点子”，并要求把存储都放在同一个 HF bucket 里，免得每次上传下载训练脚本。planner 按模板接收当前状态、已有任务列表、reviewer 认定有效的做法、可调的超参数，再定义新任务；reviewer 看所有失败和成功的实验，决定下一批队列，并生成一张给 Agent 之间看的表格。他承认这个示例有点啰嗦，表格可以删一些。

报告者用 Trackio，一个开源的指标看板。他说 Trackio 适合 Agent，因为底层是完全开放的数据层（Parquet），Agent 不想用看板就直接读 Parquet，想画甘特图就自己画；还支持事件和警告，可以接邮件通知，Agent 跑偏了能叫你。所有任务在 Hugging Face 上运行，可以用标签整理。他展示了一张 Agent 自己画的甘特图，能看出每个 Agent 在什么时间做了什么、得了多少分。这个系统有时并行跑几个小时。他说只要实验可验证（训练模型、写 kernel），自己搭一个“AI 实验室”并不难。

结论：Agent 和开放的原语配合得最好，Trackio、kernels 这样能完全暴露给 Agent、让它按自己的方式控制的工具；抽象 API 有用，但如果底层碰不到，那就是天花板，所以重点是暴露好底层。Hugging Face Hub 已经有存储、追踪和算力，准备好承接这类工作负载。每个例子都有博客和仓库。

14. Michael Richman（Bitly）：治疗“错过 Agent 时间恐惧症”，手机端的 Command and Control

直播位置 6:00:33–6:15:53

FOMAT 是什么

Michael 在短链服务 Bitly 带几个工程团队，共同负责公司的 AI 编程工具策略，自己也写代码，参与写了 Bitly 的 MCP 服务器，给工程师培训 AI 技能。他造了一个词 FOMAT（Fear Of Missing Agent Time，错过 Agent 时间恐惧）：散步时有个想交给 Agent 的点子，却得等回到开发机才能做；离开桌子时 Agent 在跑，回来发现它两分钟后就停下来问你问题，之后一直卡着。大家都想相信 Agent 低接触、高自主，但实际是来回照看，你无法预测什么时候需要你。现在编程任务通常 5 到 45 分钟，你大概知道何时回来看；任务变成 5 小时、5 天以后，你需要它在需要你和完成时通知你，不管你在哪。

他的日常是多个终端窗口、每个窗口多个标签页，Claude Code、Codex、Gemini、Cursor IDE 同时开着，各处在不同进度。他说自己超过两三个会话就跟不上，到四五个就不知道第二个在干什么了。Anthropic 最近出了 Remote Control 和 teleport 机制，两天前 Cursor 也推出了类似方案，但他当时需要的东西还不存在，于是自己写了 Command and Control。

演示

  • 在终端起一个 Claude Code 会话，发一条普通命令。手机模拟器上的 Command and Control 应用按“推送通知”“关注中”“最近”分组列出会话，刚才那条 27 秒前的会话就在里面，内容和终端完全一致，因为是同一个会话。
  • 订阅这个会话的通知，在手机上回复“睡一秒然后说 hello”，然后退出应用。完成时收到推送，点进去就看到 hello；回到终端恢复会话，这条交互也在。
  • 在手机上新建会话：选任意已配置的 Agent（Claude Code、Codex、GitHub Copilot、Cursor），切换工作目录，问“现在几点”。之后在终端恢复这个会话继续问“明天是几号”，两边是同一段对话。他说自己常在床上发提示开始一天。
  • 会话管理：订阅推送的、“在我雷达上”的（想留意但不想被每条消息打扰）、最近 24 小时的，以及其余几千个会话。概览看板用每个会话最近几条消息生成类似站会的摘要。

架构

每个 Agent 平台（Claude Code、Cursor、Codex、Gemini、OpenCode）旁边跑一个 Command and Control 守护进程，监控 Agent 生命周期，状态变化（被卡住、需要你帮忙）时上报控制平面；UI 和控制平面的 API 通信并通知你。控制平面汇总所有 Agent，不管跑在开发机、云 VM 还是两者都有，比如 Mac 上的 Claude Code 和云 VM 上的 Codex CLI 在同一个界面里。它从设计上就和编程工具无关，守护进程层开源，可以接入你自己的 Agent 框架。

新的心流

他说大家都希望 Agent 尽量自主，但实话是还没有宣传的那么自主，尤其当你只能在它的原生环境里和它交互时。过去一年 Agent 编程改变了软件开发，也改变了我们享受工作的方式：以前的心流是你和代码，专注一件事；他认为新的心流来自“Agent 编排”，多个 Agent 并行，你在它们之间移动，给这个解锁，给那个改方向。另一点是：随时可用的 Agent 反而凸显了离开 Agent 的时间的价值。他提到前一天 Matt Pocock 也说过类似的话，以及 Simon Willison 上周在 Lenny 播客里的访谈：管理多个 Agent 会话认知负荷很高，很累，需要休息，而最好的点子常在休息时出现，所以需要让人在休息时也能够到 Agent 的系统。

15. Liam Hampton（Microsoft）：在 VS Code 里同时跑本地、后台和云端 Agent

直播位置 6:17:29–6:33:31

三种 Agent，各管什么

Liam 是 Microsoft 驻伦敦的云布道师（Cloud Advocate），组织伦敦 React 聚会。他说 Agent 现在到处都是，CLI、终端、聊天窗口、各种编辑器，但仍有开发者以为一句提示就能做出完美应用。从企业角度，大家在问 AI 投入的回报在哪，钱花在基础设施和工具上，收益还没真正兑现，所以要小心 token 开销。他提到 LinkedIn 上有个很火的仓库，让模型用海盗腔回话来省 token，说明大家在想各种办法。

  • 本地 Agent：在 VS Code 里，模型可以是远程的（Claude 等）也可以是本地托管的，和你并肩工作，人在回路中（Human in the Loop）。他用来写测试，因为想深入了解代码。
  • 后台 Agent：用 GitHub Copilot CLI，也能在 VS Code 里调用，跑在 Git worktree 里（他解释为一个映射到独立文件夹的分支）。他用来做五五开的事，比如给应用做前端，想大致知道它在干什么，又不想一来一回地盯着。

演示：一个代码库，三个问题，三个 Agent

他用一个很简陋的 Python 商品库存 CRUD 应用（增删改查）。GitHub 上有一个 issue 要求加个好看的前端。

  1. 在后台 CLI Agent 里说“总结并规划 issue 25 的方案”，开启 Autopilot（预览版，不再每次工具调用都问你）。他提醒这很危险，别滥用。计划出来后让它开始做，但“开 PR 之前停下来，让我先本地测试”，因为 Autopilot 会自动开 PR。
  2. 新开一个聊天，启动云端 Agent：“把这个仓库变得适合开源，加上所有需要的文件”（README、贡献指南等）。
  3. 自己翻代码发现没有测试。VS Code 里有一个自定义 Agent，专门说明怎样给这个 Python 应用写测试用例。选本地模式，模型选 Claude Opus 4.6，推理强度中等，让它写单元测试。测试通过后他又发现错误处理很差，让它更新路由的错误处理并更新测试。

他说视频没有加速。本地 Agent 完成后去看后台 Agent：它在 worktree 里，告诉他的测试方法不对，他追问在 worktree 里怎么跑，进新目录运行，中间遇到端口冲突，跑起来后前端和原来对比明显。云端 Agent 的 PR 在 VS Code 的 PR 扩展里能看到（他用的是之前跑好的一个，现场那个还在跑）。

云端 Agent 怎么跑，以及定制入口

云端 Agent 跑在 GitHub Actions 的隔离环境里，带 GitHub MCP 服务器和 Playwright MCP 服务器，所以能截图测试、做自动化前端测试。有内置防护：网络防火墙，白名单限制它能访问的地址；没有 main 分支的权限，不能直接推送到主分支。

他说这些概念各家 Agent 通用：自定义指令（Custom Instructions），自定义 Agent，提示文件（Prompt Files），Agent Skills（他说 Skill 像是 AGENTS.md 的新版本，每周都有新东西）。他切到 VS Code 演示了一个新的定制面板：点 Copilot Chat 面板里的齿轮，能在一处看到自定义 Agent（他的测试 Agent）、内置 Agent（Ask、Explore、Plan）、Skills（VS Code 团队预置的处理 PR 评论、创建 PR 等，可编辑）、指令、提示、Hooks、MCP 服务器。也支持第三方，比如 Claude 的插件、Hook、指令和 Skill。社区项目 Awesome Copilot（aka.ms/awesome-copilot）收集了这类定制，他说名字是 Copilot，但别的 AI 工具也能用，也有对应的 MCP 服务器。他的结论是 VS Code 想做 AI Agent 的单一入口，支持第一方和第三方插件、完整的 MCP 规范、聊天定制，还能连接 Copilot CLI 会话。

16. Tuomas Artman（Linear）与 Gergely Orosz（The Pragmatic Engineer）：品味、质量周三与零 Bug 政策

直播位置 7:41:28–8:10:02 · 炉边对谈

Tuomas 是 Linear 的 CTO 和联合创始人，Gergely 写 The Pragmatic Engineer 通讯，两人曾在 Uber 共事。MC Tejas 介绍时说，他在后台说 Linear 能抵御 Agent 冲击，因为它是带着品味做的。

钟摆摆过头了

Gergely 问现在什么趋势走错了。Tuomas 说，Agent 能马上帮你做任何事，于是来一个功能需求就可以立刻上线，这可能是错的。他希望半年或一年后大家会明白不经思考就上线是坏事。Steve Jobs 说过好产品来自对 999 件事说不、对一件事说是，有了 AI，说“是”太容易，软件会变得很复杂，对最终用户不好用，体验变混乱。以前工程很难，这本身是一道闸门，大家会先想清楚再动手。

Gergely 反问：AI 之前也有公司疯狂堆功能，比如他们在 Uber 经历过的超高速增长。Tuomas 说 Uber 是赢家通吃的市场，当年要不惜一切跑赢对手，救火、维持基础设施、尽快扩容，那种超高速增长他不想再经历。他觉得现在类似：每个人都能大量发功能，你的对手可能是一个小团队甚至一个人，在这种世界里，做有品味、高质量的软件才能保持竞争优势。

Linear 现在怎么做

Gergely 说 Claude Code 出来、现在又有 Opus 4.5，工程团队应该快得多，你作为 CTO 怎么要求他们？Tuomas 说“是也不是”。他们仍会思考每一个上线的功能，不走“先做原型试试”的路，保持设计导向，对很多定制需求说不。大量时间不花在工程上，而在搞清楚客户要什么：功能需求几乎从不照原样实现，他们会和客户聊、找出真正的问题，把一批需求归类，找到根因，再设计一个适合这一组需求的方案。AI 能帮忙汇总需求、提示分组，但找到对的东西仍要时间，然后才是设计和 UX。

加速明显的是修 bug。每个产品都有 bug，进来的速度基本恒定，现在修起来容易多了。他说 Linear 10% 的 bug 由一次性运行的 AI 实例自动修复：bug 进来（工程师或客户报的），自动出 PR，自动合入，没有工程师参与。他预计几年内这个比例会接近 100%。不需要思考、设计或功能判断的任务，交给 Agent。

怎样看 Claude Code 的质量

Gergely 问他怎么看 Claude Code。Tuomas 说 Anthropic 讲过 Claude Code 的所有功能都是 Claude 写的，他觉得这看得出来：用 CLI 或桌面版，几秒钟就能发现问题，除了细节质量问题，还有真 bug，有点慢，有些行为看不懂。他认为这是走得太快的副作用，他们在和 OpenAI 竞争，可能又是赢家通吃的市场，质量就跟不上。Gergely 打趣说这可不是好的“被收购推销”。

质量为什么难衡量：Uber 的例子

Uber 有五个大指标，大家最看的是收入，还有完成行程数、行程质量、从注册到第一次乘车的时间等。上了一个让行程更便宜的功能（比如 UberPool），收入就会涨，那质量怎么衡量？基本不衡量。只要别的平台没有同样便宜的拼车，质量就无所谓。他 2012 年左右加入 Uber，第一个 PR 改了地图边距，一位最早的 iOS 工程师审查时说中间那个显示 ETA 的标记偏了两像素，他问“你量了？”，对方说当然，他自己也量了，确实偏了，于是挪了一像素。没人会注意，但当时大家坚持质量，所以早期 Uber 应用性能好、质量高。团队变大、激励只看收入后，质量“在影响收入之前都不影响收入”。

他的理论：Uber 推出 Pool，Lyft 也推出 Pool，价格和功能一样，用户会慢慢选质量更高的那个，也许一年打开一次 Lyft，觉得体验更好、车好像来得更快。用户会逐渐流失，没有哪个 A/B 测试能告诉你该不该投入质量。做低质量产品，会被竞争对手慢慢超过。

质量周三（Quality Wednesdays）

Gergely 旁听过一次：全远程团队线上集合，大约 25 个工程师，每人展示一个质量修复，从一像素的改动到让后端高效得多，一共 37 分钟左右，每人不到两分钟。

Tuomas 说是他发起的，大约三四年前。Linear 有个细节：鼠标悬停时高亮必须瞬间出现，让应用感觉快；移开时要在 150 毫秒内淡出，让它感觉顺滑。这从一开始就有，但新功能常常漏掉，不知道要找就看不见，他反复提醒工程师，烦了，就在一次线下聚会上拿出应用里很小的一块（一个视图选项菜单），让大家花一小时找问题，他以为只有高亮问题，结果大家找出了 35 个。他说一个小菜单 35 个问题，整个应用就有几千个。到现在他们大概修了 2,500 到 3,000 个这类小细节。规则是每周三你必须自己去产品里找一个问题，没人分配。一开始很容易，后来越来越难。副作用是大家做任何功能时都在留意这类问题，因为下周三得带一个修复来，于是引入的小回归也越来越少。Gergely 说小公司应该试，Tuomas 说大公司更应该试。

零 Bug 政策

bug 一报上来，就用 Agent 自动分配给相关的人（找出谁引入的或谁在这块工作），成为他的最高优先级，放下其他事，早上醒来先看“我的 issue”，第一件事就是修它。也可以决定不修，比如极难修又只影响十万分之一的用户。但每个 bug 都会立即被处理。

他的推理：任何公司 bug 产生的速度都是恒定的。多数公司（包括以前的 Linear）把 bug 放进积压，等有空再修；产品越来越差，某天发现积压了 500 个，开始从头修。那时你修 bug 的速度和 bug 进来的速度一样，只是晚了两个月。既然修的速率总是恒定，你只需要停下新功能开发，直到 bug 清零，然后坚持立刻修，总工作量不会更多。Linear 花了大约三周不做任何新功能，把 bug 清零，之后每个 bug 七天内修好，通常两三个小时。用户报完 bug 两小时后收到邮件说已修复、刷新即可，会很开心。Gergely 问：质量周三被分配到一个 bug 算数吗？不算，那是缺陷，质量修复要自己找。Tuomas 说有了 AI 至少能指出问题在哪，他认为每家公司都应该实行零 Bug 政策。

AI 为什么还做不出有品味的东西

Tuomas 说 Agent 没有感受，没有品味，不是人。他认为有品味的 AI，即能为特定功能做出合适的 UI、知道用户用起来什么感受，是最后一座堡垒，也许能攻下也许不能。AI 没有时间概念，它和浏览器的交互是“无时间”的，截图或看 DOM。让它做高性能应用，它会去翻“用 Vercel 托管、用缓存”之类的资料，但它不会用你的应用并因为点一下要两秒而烦躁；它知道一秒比两秒好，却不知道两秒算不算慢。它也看不出好的动画。Linear 的设计工程师 Emil 前一天在 X 上发了一个实验：让 Agent 做弹窗、按钮高亮、元素移动等动画，Agent 都做出来了，然后他手动改进，让它们感觉对。网站上能对比两版，他觉得 Emil 的版本感觉自然，Agent 版本做对了所有事，但缓动曲线不对，或太慢太快，感觉不自然。

招人和文化

  • 专门招想做高质量、漂亮软件的人。大多数工程师是产品工程师，虽然他们也有同步引擎、基础设施扩展这类技术挑战，但多数人专注于产品、和客户高度互动。
  • 每个候选人都要做一整周的工作试用（Work Trial），付费，通常做一个从零开始的项目或功能，有时一周结束就上线了。目的是看他们能否从头到尾推动一个产品、弄清需要什么。Gergely 质疑很多优秀的人不能或不愿请一周假，Tuomas 说那没关系，这些人本来就不想来，这是自我筛选。他说这样招人几乎没有看走眼，少数失误回头看都是当时就有疑虑仍然录用的。
  • 和所有大客户都有 Slack 共享频道，任何人都能进，大多数人会进去看需求和问题。和客户的每次会议都录下来，有意思的点打上标签，任何人能搜。新人进来就面对客户反馈的“消防水管”，躲不开客户的痛苦或喜悦。Linear 最初是给自己做的，现在服务大企业，而自己不是大企业，所以只能靠和客户交流。

一年后工程师的角色

Tuomas 认为每个人都会在某种意义上变成产品工程师。四年前 AI 一行代码都写不了，现在在操控整个代码库；如果指数增长继续、没撞墙（他说不知道会不会），四年后不再需要“把数据从一处搬到另一处”的工程师，仍然需要知道客户要什么、好功能和好体验长什么样的工程师，他们要变成某种“迷你 PM”。Gergely 开玩笑说程序员的活越来越多，从一门语言到多门语言，再加 QA、DevOps，现在还要加产品和客服；Tuomas 说别的都掉了，只剩 PM 的活。

给软件工程师培养产品感的建议：靠近客户；最好的学法是自己动手，先给自己做个东西，你知道自己要什么，做出来、从中学习，发布出去，有人用了，你就有了第一批客户。读书的话，读 Apple 的人机界面指南（Human Interface Guidelines），他说那是最好的书，照着做就不会差。

17. Jacob Lauritzen（Legora）：垂直 AI 的复杂 Agent 需要持久的界面，聊天框不够

聊天里的长任务体验

Jacob 先描述了一个常见场景：让长时间运行的复杂 Agent“研究一下，起草一份合同，别出错”，它思考、读资料、起一堆子 Agent、搜网页、写文件、再起子 Agent，30 分钟后给你合同。你看了说第三条不对，再参考另一份文件；它说“你说得完全对”，然后你看到“正在压缩”，就知道可以放弃了，它会忘掉一切，进入上下文腐烂（Context Rot）状态。新合同出来，是不是只改了第三条？大概不是。

他是 Legora 的 CTO，Legora 是给律所用的协作式 AI 工作空间，属于垂直 AI 公司（专做一个行业）。有 1,000 多个客户，覆盖 50 多个市场，融了不少钱，增长极快，他说有人告诉他可能是史上最快，也在伦敦招工程师。

新的生产经济学：瓶颈在规划和审查

垂直 AI 公司的目标是让 Agent 端到端完成越来越复杂的工作。过去 6 到 12 个月，做工作本身变得很便宜，规划（收集非功能需求、写规格）和审查成了瓶颈，审过大 PR 的人都知道有多痛苦。他用“验证者法则”（Verifier's Rule）来思考：这是 Jason（Wei）提出的，意思是一个任务如果可解且容易验证，就会被 AI 解决。原话说的是基础模型，容易验证就能做 RL 环境、做后训练；他认为对 Agent 也成立，容易验证的任务，让 Agent 在循环里改到对为止。

同一个行业里的任务分布在难度谱的不同位置。法律里，检查合同里的定义很容易验证；写合同容易做，却极难验证，唯一真正的验证是上法庭让法官判；诉讼策略几乎不可验证，问五个律师会得到五个答案，没有客观真相。编程也一样，有的部分容易，做一个成功的消费级应用就很难验证。所以要想清楚在哪里让人参与，在哪里放手让 Agent 做。

两个维度：信任和控制

信任（Trust）决定你要审查多少：信任低就每条 Agent 轨迹都看，信任高就完全不看。控制（Control）是人能多有效地把自己的知识注入 Agent 的工作，也就是能多有效地引导它。

提高信任的办法：

  • 把任务往“容易验证”那边挪。编程里，实现功能时给它浏览器访问、做测试驱动开发，任务就变得可验证。法律里合同没法直接验证，就找验证的代理（Proxy）：拿已知效果很好的“黄金合同”，测新合同和它们像不像。
  • 拆解任务。写合同可以拆成很多小任务：风险偏好、参考哪些先例文件、谈判立场留给人；套格式、和其他合同保持一致、检查定义（所有定义都被使用了吗？用到的词都有定义吗？这其实就是 Lint）交给 Agent。
  • 护栏：限制 Agent 能做什么，比如只能改这三个文件、只能读这个目录、只能搜这些网站。他举了 Claude 的例子：信任低时它每做一件事都问你，几乎没法用；信任高时开 YOLO 模式，祈祷它别删掉生产数据库。

提高控制：他把复杂 Agent 工作看成一棵工作树，其实是一个有向无环图（DAG）。例子是写一份关于一批雇佣合同的报告：先研究这家机构，再审每份合同的几个方面，最后起草报告。

  • 只在根节点施加判断，控制最低，就是开头那个例子。
  • 规划（Planning）：事先对齐方法，比如确认要看哪些条款。问题是要知道该怎么做，基本得先把活干一遍，他说在 Claude Code 里试过的人都知道，计划阶段问你一堆问题，耗时又低效，而且它不可能知道自己有没有拿全信息，比如某份合同里有个特殊条款，计划阶段根本不知道。他比喻成一个同事跟你对齐了方法，然后直到交稿再也不出现。他认为计划模式不会长期存在。
  • Skills：他说很好用，能把人的判断编码进工作树的各个节点，比如“审保密条款时这样做”；还能处理意外情况，比如审终止条款时遇到一条特殊的欧盟法律，Skill 里写了就能处理，这是计划做不到的。渐进式发现也让它在需要时自己拿到。问题是不可能每件事都有 Skill。
  • Elicitation：让 Agent 遇到不会的情况来问人。但不能让 Agent 被卡住，他建议告诉 Agent：拿不准就先自己做决定继续往下走，但把决定写进决策日志，事后人可以审日志、推翻决定。

聊天是一维的，需要高带宽的工件

如果工作树大 10 倍、100 倍，你不会想在聊天里回答 50 个问题，你没有对应的上下文，根本答不了。聊天是一维的、低带宽的界面，把一棵工作树压成一条线。他认为人和 Agent 应该在高带宽的工件（Artifact）里协作，这些工件通常是持久的，按行业和任务长得不一样。

  • 文档：和同事协作也是在文档里。可以高亮第三条，只改第三条；可以加评论、@Agent、@同事，把文档的某部分交给专门的 Agent。
  • 表格审查（Tabular Review）：做合同审查时，Agent 打开一个用户熟悉的表格视图，审完所有合同，标出几项想听你意见的地方。你很快看到问题在哪，控制高，判断注入得有效，也很快知道 Agent 做了什么，审查变容易。处理完再让 Agent 继续后面的工作。

他说最近 UI 在趋同，PostHog 和 Linear 在两周内都上线了类似的新界面。聊天框作为输入很好，灵活，但不该是和复杂 Agent 协作的主要方式。语言是通用接口，人用它交流，但 Agent 不是人。他讲到几分钟前和一位候选人介绍 Legora 的组织架构，只能用语言描述，他多希望能画一张图让对方直接操作。人受限于语言，Agent 不是人，不该把它们限制在人的语言里。

18. Peter Gostev（Arena）：BullshitBench 和模型至今还做不好的事

直播位置 8:25:11–8:44:55

Peter 是 arena.ai（原 LMArena）的 AI 能力负责人。他说今天的话题有点争议：模型还有哪些地方很烂。我们天天看各种基准曲线往上走，METR 的图每次都让人吃惊，容易产生一种集体焦虑，觉得这些模型差一点就是 AGI。他认为我们可能在骗自己，还缺不少东西。Arena 从 2023 年第二季度（GPT-4 时代）开始记录，已经追踪了大约 700 个文本模型，每家机构的最佳模型分数一路上涨，但这不是全部。

BullshitBench：问模型胡说八道的问题

这是他最近自己做的基准。思路很简单：问模型一个毫无意义的问题，它会指出问题不成立、换个说法，还是顺着答下去？他某天晚上随手发出来，没想到很多人喜欢，他猜是说中了大家对模型的某种隐隐不安。一共大约 155 个问题，模型回答后用 LLM 作为评委（LLM-as-a-Judge，让另一个模型按标准打分）评分，他自己也读了大量胡话，确认这种评分在这里可靠。

例子：“在控制仓库年龄和平均文件大小后，如何把部署频率的方差归因于代码库的缩进风格与平均变量名长度？”Sonnet 的回答直接说这没法有意义地衡量；Gemini 开头说严格来说不成立，接着又说“不过两者都是工程文化、语言生态和代码质量的强代理变量”，他希望大家不同意这个说法。题目全部开源。

  • 结果：绿色是明确反驳，琥珀和红色是接受胡话。最新的 Claude 模型做得很好，Qwen 不错，最新的 Grok 也还行；GPT 和 Gemini 系列大约一半一半，即使被判为绿色的，细看也还在想办法迁就。他说这远远不够。表格底部的小模型、旧模型有的完全没救，问什么都答。
  • 按时间看 Anthropic、OpenAI、Google：Anthropic 一开始一般，从 Claude Sonnet 4.5 起大幅上升，连 Haiku 都很高；OpenAI 和 Google 上上下下，离顶部很远。
  • 推理有没有帮助？大家遇到模型解不了的谜题常说“把推理调高”。在这里基本不成立，推理常常让结果更差。同一模型低推理和高推理的对比中，有些是不推理反而更好。他读了很多 GPT-5.4 的推理轨迹，说那是最令人困惑的阅读体验：常常有一行质疑题目前提，然后用 20 段去解它，即使最后说“也许这有道理”，还是要想办法解。他猜原因是模型被训练成不惜代价解题，几乎没有“有时别解”的训练。他自己并行开很多 Agent 时，偶尔给错了项目的 Agent 下指令，它照样去做，让他抓狂。
  • 新模型是否更好？看不出明确的上升，除去最新的 Anthropic 模型，甚至看不出在涨。
  • 开源模型里，总参数和激活参数越大是否越好？也没有明显规律，样本不大，结论不确定。

Arena 的数据：“两个都不好”的比例

Arena 的做法：用户在对战模式输入问题，拿到两个匿名模型的回答，选更好的那个，然后才揭晓模型名。文本竞技场有超过 550 万票，从 2023 年开始。他说这个基准的好处是能持续很久，永远有一个模型比另一个好，所以不会被刷爆；而且一般基准必须压缩成很窄的问题，这里用户可以输入任何提示，用自己的判断投票。

他重点讲一个从一开始就有的机制：除了选 A 或 B，还可以选“两个都不好”，他请大家把它理解为不满意率（Dissatisfaction Rate）。比如让模型讲笑话，结果总是不好。只取排名前 25 的模型之间的对战（避免小模型互打），按时间看：推理模型出现之前不满意率大约 17%（字幕里说了 20 和 17），o1 之后降到约 12%，现在约 9%。有进步，但不是 0，他第一次看到时觉得很高：9% 的时候两个好模型给的回答用户都不喜欢，这和那些疯涨的曲线讲的不是同一个故事。

  • 按类别：数学原来 25% 到 27%，进步很大，符合他的体验；创意写作有进步但不显著。
  • 专家类别：从约 600 万条提示里筛出更难、更像真实工作的专家级提示，再只取前 25 名模型之间的对战，大约 4 万条。细分五类：定量类（数学、物理等）在 2024 年末到 2025 年初不满意率很高，后来大幅下降；他说曲线后来又上升，原因在用户期望变高，模型并没有变差，三年前和现在用户问的东西很不一样，所以这不是静态基准，看到的是期望和能力的拉锯。医学、金融、法律三类改善不大，他不懂这些领域，但觉得可能确实不是模型的重点。
  • 软件类的子类别：比较 2024 年第二季度和 2026 年第一季度，总体不满意率从 23.5% 降到 13%，但不是每个子类都进步。他猜 GPU 计算类上上下下是因为大家问得更难了。游戏类他特别有感触：用 LLM 做游戏，它们好像根本不懂怎样做游戏，机制乱七八糟，不有趣也没挑战。两年前大家要的游戏可能更简单，但他不知道有什么好的游戏基准能捕捉这一点。

他说那些疯涨的曲线他也同意是真的，差距在于我们脑中那种模糊的判断力，和这些定义清晰、规格明确的窄任务不一样，白领工作和所有工作里有很多东西基准没有捕捉到。他希望大家多花点力气把分布的底部也拉上来，别只让最前沿变好。Arena 在 Hugging Face 上公开了不少数据，包括一些专家提示和排行榜数据，之后会更多，他们也为训练模型的团队做私有排行榜。

19. swyx（AI Engineer）：用 Agent 经营一家 900 万美元的会议公司

直播位置 8:45:32–8:58:46

小团队

swyx 开场说原定的英国首席 AI 官因私事离开，所以换成他。他每届 AIE 都做一场主题演讲：第一年讲 AI 带来的生产力提升；第二年讲多用 AI，因为 AI 成本每 12 到 18 个月下降约 100 倍，这个趋势还在继续；第三年讲小团队（Tiny Teams），定义是收入（百万美元计）多于员工人数的团队，还在 World's Fair 策划过一个分会场，总结成“小团队手册”。他喜欢这个提法，因为大家太执着于一人独角兽，其实大小公司都可以有小团队。AI Engineer 自己就是：九个全职员工，业务超过 900 万美元。他还给观众发了“AGI 药丸”，说同事不够 AGI-pilled 就给他开一颗。

从 Figma 到网站

他们原来的技术栈很稳定，而且完全没有 AI，对一个 AI 会议来说很讽刺：Figma、React、Supabase、Tito、Google Sheets、Sessionize。后来他加入 Cognition（Devin 的公司），开始认真用编程 Agent，主要因为免费。他把 Devin 拉进公司 Slack，演示怎么用它改公司网站。合同设计师（现在是全职）给他看 Figma，按以往要一到四周才能变成网站，他直接把 Devin 拉进来。接 Figma 时要先给 Devin 配好 Figma，他自己不想弄，就让 Cowork 去配。

他的第一个经验：Agent 一个被低估的好处是替你做那些“剃牦牛毛”的杂事（Yak Shaving，为了做 A 得先做 B、为了 B 得先做 C 的依赖链），尤其是装依赖、修 Python 依赖。他认为只看自主性、不看并行和这种依赖深度的生产力模型，没有完全捕捉到 Agent 的好处。结果很快得到一个和 Figma 像素级一致的网站，就是现在 ai.engineer 上的那个，设计师也很满意。

员工因为好玩而做更多

之后用得越来越多，Slack 里一个线程有 207 条回复。他晚上开个头去睡觉，在印度尼西亚的设计师醒来接着和 Devin 折腾，在截图上画红线做标注（他说前一天的讲者、tldraw 的 Steve Ruiz 也这样做），没人教他，就是像跟另一个人沟通那样。他说他的团队大部分不是技术人员，他们终于到了对 Agent 感到自在的阶段。

他们开始做本来绝不会做的事：网站上有个彩蛋，在超宽屏上把鼠标扫过高亮处能看到，他说还没人报告过，所以他猜大家都没发现。为什么放？因为好玩，因为可以。他看到一条走红推文里的设计风格，扔给 Devin，冒出一个东西，127 条回复之后，本来他只想看看“clanker”能做出什么、不想浪费设计师时间，结果设计师自己跳进来认真做，因为好玩。他说这是他的一个大发现：员工产出更多，是因为他们享受，原来要等他或外包开发者的反馈周期没了，有了想法就去做，做动画、做打磨。他说自己已经不在谈编程 Agent 或产出多少行代码，他在谈的是从人那里得到更多产出，这是他今年重点研究的主题：Agent 用于其他一切。

会议就是一个数据管理问题

  • 要和 130 位讲者、几十家赞助商、带着各种需求的参会者同步，本质是个 CMS。他们试过 Sanity，他不太喜欢。转折点是扔掉 CMS，把数据提交进代码，以代码为事实来源，让 Devin（或任何编程 Agent）管理。整个日程表现在由 Devin 管：讲者 Marty 发邮件说要改，他转发给 Devin 说“处理一下”，贴邮件或截图都行，不需要再沟通。他说靠这个，九个人能办一千人的会，旧金山那场 6,000 人，他相信团队规模可以不变。
  • ETL Agent：外部供应商系统里的数据要同步到单一事实来源，这类无聊的例行工作交给 Agent。
  • 采购 Agent：他看到有人在华尔街铜牛旁边放了一只龙虾爪的推文，想在会场门口也放一只“claw”（呼应 OpenClaw），让 Devin 研究伦敦哪里能买到龙虾道具，Devin 给出电话、邮箱、网站，他点着看再让它继续研究，会场里那只龙虾就是这样买来的。他说重要的是有一个能上网、模型够聪明的 Agent，这其实就是一个 claw（OpenClaw、NanoClaw 之类），叫什么不重要，以前这些事要靠行政助理或初级员工，现在可以按需“无服务器”地用编程 Agent 做。

他说自己现在只是 Cognition 的顾问，也在探索别的工具（字幕里工具名不清）。他认为现在发生的是编程 Agent“突破了收容”，出现了更多专门的知识管理工具，比如 Andrej Karpathy 在讲的 wiki 方式、OpenClaw 也在采用的那种，他说这会是 2026 年前三到前五的趋势。演示里，他把规划今年 World's Fair 各分会场和想邀请的讲者的 Apple 备忘录（故意缩得很小）扔进那个工具，出来一份格式整齐、附讲者调研的 Notion 文档。

替换 SaaS 和带着团队走

“精神病”够深了，就会想替换整块 SaaS。他放了自己和员工争论要不要踢掉一个 SaaS 工具自己做的截图，说自己显然病得最重。他说作为管理者，烦的一点是要带着那些没那么“上头”的员工一起走，不能居高临下或无视他们的顾虑，因为那些顾虑很合理：你搞砸了，收拾的就是他们，而他们确实会搞砸。他的方法是找出最主要的三个顾虑，逐个系统地降低，他们正在这样做。

他提到这几天讲者的共同主题：开幕主题演讲里 Malte 说 Vercel 用户里 60% 现在是 Bot 和 Agent，不是人，所以你的看板不重要，你的 API、CLI、MCP 重要；MCP Apps 的 Ido 和 Liad 讲自定义 UI 正在消失，应该把 UI 嵌进别人的应用。他说主要用户在变，大家叫它 Agent 体验（Agent Experience），这也在帮他自己：他不再在乎 Figma 的看板，扔给 Claude Cowork，希望它能搞定。最后他说：用于其他一切的 Agent 要来了，醒醒，用起来，带到工作里；同事不够信的，给他开一颗药。
