03. Malte Ubl（Vercel CTO）：Agent 是新的应用层

直播位置 0:24:25

开场和背景

Malte 是 Vercel 的 CTO，之前在 Google，有 25 年以上的软件工程经验。他先展示了自己最近在折腾的两个项目：chat SDK，用来把 Agent 接到 Slack、Telegram、WhatsApp 等聊天应用；Just Bash，一个用 TypeScript 写的 bash 解释器，相当于给 Agent 一个启动时间以纳秒计的沙盒（Sandbox，隔离的运行环境，Agent 在里面执行命令不会影响宿主机），因为 Agent 很爱用 bash。

他以前在柏林办 JSConf EU，2019 年夏天办完第十届就收手，结果第二年遇上疫情，原本希望有人接手也没实现。他认为 2026 年能把欧洲技术社区重新聚起来的会议，自然就是 AI 工程会议，因为 AI 工程是 Web 开发之后下一个主流工程学科。现在既是“怎么做软件”在变（用 AI 做），也是“做什么软件”在变（做 AI 和 Agent）。

工程师还有位置吗

常有人问他工程师还有没有未来。他的回答是有。他举例说自己不适合拍 TikTok，因为不是在那个环境里长大的；同理，在 AI 环境里成长起来的新一代初级工程师会比老一代更擅长这门手艺。

他的核心论点是 Agent 是一种新软件。以前很多值得自动化的事情用传统软件写不划算：要写一大堆 if 判断，要把业务知识硬编码进去。他画了个韦恩图：大圆是“所有应该存在的软件”，以前只能写出其中一小块，现在 Agent 让剩下的部分变得经济可行。企业在“买 SaaS 还是自己做”的选择上越来越多地选自己做，硅谷管这叫 SaaS 末日，但他觉得 SaaS 公司也会没事。他说我们正在快速验证一个经济学实验：软件市场有多大弹性。软件越便宜，做出来的软件越多，所以他看到的情况是工程师需求在上升，暂时看不到 S 曲线的顶。

今天就能落地的四类 Agent

他说大家被编程 Agent 惯坏了，以为能直接搬到所有领域，结果常常不顺。其实有很多低垂的果实，不需要大改流程就能给公司省下大钱：

  • 从朝九晚五到 7×24：客服 Agent 是第一代“Agent 即服务”创业公司（他提到 Sierra、Decagon 这类）在做的事。值得问的是：哪些岗位如果能全天候运转会带来很大变化。
  • 压缩调研环节：很多业务流程都是“业务事件 → 调研 → 人做决定”。只把调研那一步交给 Agent，流程本身不变，风险也不变，但原来 30 分钟的事变成 5 分钟，一年跑 10 万次就省很多钱。Vercel 官网的“联系销售”按钮背后就是 Agent，大约 75% 的情况它判断对方其实是要技术支持，转给支持团队；其余的它会去查 LinkedIn、搜公司规模、转给对的销售。滥用举报也是同样的结构，Agent 先调研，专业人员最后拍板。
  • 把已有的信息浮出来：公司里的信息往往已经存在，只是用不上。比如 issue tracker 通常不是最新的，但 Slack 里聊过、Granola 会议录音里提过，Agent 可以据此自动更新。经理要周报，为什么不能早就由 Agent 汇总好？
  • 问员工“你最讨厌工作里的哪部分”：Vercel 自建的客服 Agent 有 90% 的分流率（deflection rate，指 Agent 直接解决、不需要转人工的比例），结果客服团队的工作满意度大涨，因为“信用卡被拒”之类的重复问题不再落到他们头上，他们可以去处理真正需要帮助的案例。

软件的用户也在变成 Agent

他公开了一个此前没说过的数字：过去 7 天里，vercel.com 超过 60% 的页面浏览来自 AI Agent。用户使用 Vercel 平台的方式也从点控制台转向 API 和 CLI。现在有人给他看新功能的 UI，他第一句问的是 CLI 在哪、Agent 怎么用。另外，代码不是自己写的，开发者对它在生产环境怎么跑也就没那么在意，所以基础设施要适应“大部分代码由 Agent 写、提完需求就该能跑”的模式。

安全方面他说我们正一头扎进安全噩梦，有点像 1999 年什么都能被黑的时候。他举了一个架构问题：他认为目前流行的 Agent Harness（Harness 指包住模型、负责循环调用工具、管理上下文的那层程序）几乎都犯了同一个根本错误，把 Harness 运行的地方和它生成的代码运行的地方放在一起。他说就在前一天，Anthropic 新发布的 Agent 产品把两者分开了，他认为这一点很关键。

欧洲和应用层的未来

他认为应用层可以独立于模型繁荣，今天这个模型强、明天那个模型强，AI 工程师在上面搭一个稳定的层，不必在模型实验室工作也能推动创新。他说欧洲其实是 AI 工程创新的领先者：Vercel 的 AI SDK 每周下载超过 1,000 万次，负责人 Lars Grammel 住在柏林；编程 Agent Pi 出自奥地利（作者 Mario 第二天会讲）；还有 OpenClaw。欧洲不会在模型层扮演主要角色，但他认为也不需要。

他描述了两种未来。一种是大模型实验室通吃，AI 一直很贵，价值都归模型公司，工程师都变成某家实验室的 forward deployed engineer（驻场工程师）。他认为这不太可能。另一种是模型商品化：Claude 很好，Codex 很好，Google 会追上来，而且 Google 成本最低，会持续压价。在那个世界里，价值在应用层，OpenClaw 这种东西在应用层被发明出来。

04. Raia Hadsell（Google DeepMind 研究副总裁）：语言模型之外的前沿 AI

直播位置 0:42:39

自我介绍

Raia 在 DeepMind 将近 13 年，今年也是英国的 AI 大使，帮政府、学术界和产业界沟通。她按年代介绍自己：90 年代本科读宗教哲学；2000 年代转计算机，在纽约跟 Yann LeCun 读博，做用于机器人的卷积神经网络；2010 年代加入当时只有三四十人的 DeepMind，做 Atari、围棋、星际争霸和机器人；现在是副总裁，管理 10 个实验室约 1,200 名科学家和工程师。她说 DeepMind 的方法是找“根节点”问题，不在叶子上浪费时间。这场演讲的主题是“不直接是语言模型的东西”。

Gemini Embedding 2

她先问谁知道“Jennifer Aniston 细胞”。这是神经科学里的概念：大脑里有一小群神经元只对某个特定的人、物或地点激活，而且不管是听到名字、看到照片、看到视频还是听到声音，激活的都是同一群细胞，用于快速检索、识别和比较。人工神经网络里对应的东西是嵌入模型（Embedding Model，把文本、图片等输入映射成一个向量，语义相近的内容向量也相近）。训练这类模型用的是对比损失（Contrastive Loss，让相似样本的向量靠近、不相似的推远），她博士期间研究的孪生网络（Siamese Network）就是早期的对比学习方法。她说嵌入模型是生成式 AI 的重要搭档：有时要生成，有时要检索。

Google 最近发布了 Gemini Embedding 2，她讲的要点：

  • 完全全模态，由 Gemini 派生，带着 Gemini 对世界的知识。
  • 统一的多模态表示意味着不必先分别处理音频、图像、文本再拼起来，端到端不丢信息。一个向量可以表示最多 8K token 的文本、128 秒视频、80 秒音频，或一整份 PDF。
  • 用了 Matryoshka 表示学习（MRL，同一个向量的前若干维本身就是一个可用的低维嵌入）。比如先用 256 维做粗检索，需要时再扩展到更多维度。

用 AI 预测天气

几年前英国气象局（Met Office）的一位科学家问她：能不能用 AI 比物理模型更好地预测降雨？团队发现，虽然用物理模拟预测大气很难，但有 40 年的全球天气数据，神经网络做这件事其实是可行的。

  • GraphCast：用球面图神经网络（Graph Neural Network，在图结构上传递信息的网络，这里的节点从地表一直排到平流层下部）自回归地预测上百个大气变量（风速、温度、湿度等），覆盖全球，最长 15 天。她展示了飓风 Lee 的例子：模型提前 9 天准确预测了它在新斯科舍登陆的位置，当时最好的物理模型只能提前 6 天。她说对大飓风来说，多出的 3 天很重要。
  • GenCast：同样基于网格，但是概率模型，因为天气是混沌系统，需要知道尾部情况。和 1,300 个基准天气预报对比，它 97% 的情况更准；15 天预报在单块芯片上 8 分钟出结果，物理模型需要大型超算跑几个小时。
  • FGN（Functional Generative Network）：直接预测气旋，不再是先预测天气再外接一个气旋检测器。气旋的识别、轨迹、风速、风眼形成都在网络里一起训练。美国国家飓风中心已经在用。

世界模型 Genie

第三部分是世界模型（World Model，能根据动作生成并维持一个可交互环境的模型），来自 DeepMind 长期在游戏和模拟环境上的工作。这段幻灯片和视频播放出了故障，她等了一会儿才恢复。

  • Genie 1：只能跑几秒，生成 2D 平台跳跃游戏，能响应左右按键。团队觉得“有点东西”，于是扩大数据重新训练。
  • Genie 2：3D 游戏环境，可交互但不是实时，画面达不到真实世界的质量。
  • Veo 3 这类视频模型画面逼真但不能交互。Genie 3 想同时做到可交互、实时可玩、高画质。

视频恢复后她演示了几段：在肯特郡一条泥泞小路上走，低头能看到自己的身体，水会随动作变化；滑雪；艺术家先手做了几秒视频，Genie 3 接着把他的世界变成可以飞行穿梭的环境。她说这些世界有记忆：提示“我是折纸世界里的折纸蜥蜴”，往一个方向跑一分钟再跑回来，一切和原来一样。还可以边玩边改提示，比如在 DeepMind 办公室附近的卡姆登运河上走，实时改变世界。她设想一种新游戏：别人对抗性地改写你所在的世界；也可能用于教育。Project Genie 已向 Gemini Ultra 订阅用户开放。结尾她预告第二天同事 Omar 会讲 Gemma 4，“那是个语言模型”。

05. Ryan Lopopolo（OpenAI）：Harness 工程，人掌舵、Agent 执行

直播位置 1:07:08 · 英文原题 Harness Engineering: How to Build Software When Humans Steer and Agents Execute

代码是免费的

Ryan 是 OpenAI 的技术人员。他说过去九个月他只用 Agent 写软件，自称“token 亿万富翁”，并且禁止团队成员碰编辑器，所有工作都通过模型完成。他的出发点是：实现已经不再是软件工程的稀缺资源，代码是免费的。招“敲键盘的手”只受 GPU 容量和 token 预算约束，每个工程师每天 24 小时都能调动 5 个、50 个或 5,000 个工程师的产能。工程师的技能重心在往系统思维、系统设计和委派转移。

他说转折发生在 2025 年底，对他来说魔法时刻是 GPT-5.2，它出来时已经能做完整的软件工程师工作，在真实代码库里写出高质量代码。代码会带来维护负担，他承认这一点，但他认为我们觉得代码是负担，是因为它占用人的同步注意力；模型极有耐心、可以无限并行，生产、维护、重构、删除代码都不再是分配资源的约束。他说每个人都是 staff engineer，手下有多少人取决于你能同时驱动多少 Agent、有多少 token。

稀缺资源和优先级

他认为剩下的稀缺资源有三个：人的时间，人和模型的注意力，模型的上下文窗口（Context Window，模型一次能看到的 token 上限）。人的时间稀缺时，团队只做 P0 和 P2，P3 永远做不完；代码免费时，P3 可以立刻开工，甚至并行跑四份挑一个最好的合进去。他在 OpenAI 内部做了很多提效工具，因为代码免费，这些工具从第一天就有本地化，伦敦、都柏林、巴黎、布鲁塞尔、苏黎世、慕尼黑的同事都能用母语使用。

把非功能性需求写下来

他说重要的已经变成产生代码的提示和护栏（Guardrails，约束 Agent 输出的规则和检查）。所以要留下面包屑：文档、ADR（Architecture Decision Record，架构决策记录）、面向不同角色的“什么叫做得好”的文档、历史工单和代码评审记录。这些要写成 Agent 原生能读的形式，尊重有限的上下文，并尽量让东西保持一致，减少模型完成任务需要动用的注意力。大规模重构现在是免费的，迁移不会再拖半年收不了尾，因为可以一次派出 15 个 Agent 把它做完。

他估计一个合格的补丁背后有大约 500 个关于未明说的非功能性需求的小决定。模型训练时见过万亿行代码，每种选择都见过，所以工程师的工作是把“什么样的选择能被合并”写下来。Agent 达不到要求时，就要愿意承受短期速度损失，深入看它卡在哪，加上护栏，然后再退出来做更高杠杆的事。他团队里有前端架构、后端扩展性、产品思维等不同专长的人，让每个人把自己的专长写下来，每个驱动 Agent 的工程师就都能用上全队的经验。比如一个人写好“怎样写 QA 计划”，以后每条 Agent 轨迹都会产出好的 QA 计划。

持续给 Agent 注入提示的手段

  • AGENTS.md 文件有用，但现在自动压缩（auto-compaction，上下文快满时自动总结旧内容腾出空间）越来越好，他说用 GPT-5.4 和 Codex 后基本不用开新会话了，他甚至把笔记本绑在车后座上，通勤时继续跑推理。所以要预期上下文会被换出，需要在任务过程中不断补充上下文。
  • 评审 Agent：代码库里有安全和可靠性评审 Agent，在每次 push 和 CI（持续集成，提交后自动跑的构建和测试流程）中运行，对照文档检查补丁，比如网络调用有没有超时和重试，新接口是否安全、难以误用。
  • 定制 lint（静态代码检查规则）：他承认自己就是那种出了网络故障、加上重试和超时修完就算了的人。写一条只针对自己代码库的 lint，检查每次调用 fetch 都包了重试和超时，再让 Agent 把整个代码库迁移一遍，问题就一劳永逸解决了。方法论是：找出人和 Agent 反复犯的那一类错误，设计办法系统性消除，然后继续观察。
  • 针对源码本身写测试：比如限制文件不超过 350 行，让代码库适应模型的上下文效率。
  • 报错信息里写上修复步骤：除了说 lint 失败，还要告诉模型“这里不该有 unknown，我们在边界处用 parse don't validate，这个类型应该从 Zod schema 推导出来”。

他说一个有趣的规律是，每次和模型交互方式的进步，都来自模型能力的提升加上更小众的注入提示的位置：rules 文件是提示，skills 是提示，lint 报错是提示，评审 Agent 在 PR 上留的、必须处理才能合并的评论也是提示。还可以在测试里嵌入 Agent SDK，用提示评审代码是否合格。写提示写累了，他让 Codex 读完 OpenAI 开发者指南里所有提示工程的 cookbook，总结出一个“怎么写提示”的 skill，再用它来写提示。

回到 QA 计划的例子：要写好 QA 计划，就得先把所有功能、关键用户路径写下来；有了“所有面向用户的改动都要有 QA 计划”的规定，评审 Agent 就能检查 PR 有没有附上证明功能可用的截图或录屏。这样他更信任输出，不用盯着 Agent 干活，可以把自己进一步移出循环。他最后说：模型渴望 token，去让 Agent 做完整的工作，因为它们做得到。

06. Peter Steinberger（OpenClaw 作者 / OpenAI）：State of the Claw

直播位置 1:25:48

项目现状

OpenClaw 是 Peter 做的开源个人 Agent，可以通过 WhatsApp、Telegram、Discord 等聊天软件和它对话，它能操作你的电脑、邮件和各种服务。现场约三四成观众举手说在用。他说项目刚满 5 个月，可以说是 GitHub 历史上增长最快的项目；别人的星标曲线是曲棍球棒，他们的是一条直线，朋友戏称“钢管舞式增长”。现在除了几个教育类仓库，它是 GitHub 星标最多的软件项目，大约 3 万次提交，贡献者接近 2,000 人，PR 快到 3 万个，速度没有放缓。

他面前有两条路：再开一家公司，他不想再来一遍；最后他加入了 OpenAI，同时成立了 OpenClaw 基金会，于是等于有两份工作。他说经营基金会是“困难模式下的开公司”，事情一样多，但志愿者没法指挥。他一直在改善“巴士因子”（bus factor，项目依赖少数人的程度），情况在慢慢好转但还不够。现在有 Nvidia 的人加入，Microsoft 有人帮忙做 MS Teams 和 Windows 应用，Red Hat 有人帮做安全和容器化，还有腾讯、字节跳动的人。他说中国用户的规模比其他任何大洲都大。

被安全通告“DoS”

他说大家都看过“OpenClaw 不安全”的梗图，Nvidia 等公司也推出了 NemoClaw 之类的安全层。过去两三个月里有些版本出了问题，因为他基本被安全通告淹没了：截至当天收到 1,142 份安全通告，平均每天 16.6 份，其中 99 份标为严重；已发布约 469 份，关闭了 60%。作为对比，Linux 内核每天大约 8 到 9 份，他们是两倍；curl 至今共约 600 份报告，他们也是两倍。他的经验法则是：报告者喊得越响、说得越严重，越可能是 AI 生成的垃圾。

他说 AI 工具已经很擅长发现奇怪的多步串联漏洞，我们会进入一个必须改变软件构建方式的世界。例子：Nvidia 发布 NemoClaw（给 OpenClaw 加沙盒的插件和安全层）前一天邀请他去合作，他接上 Codex Security，半小时内找到 5 种逃出沙盒的方法。他解释这是因为那个产品能用到网络安全能力没有被削弱的模型，比公开版本更强，正因为危险才不公开。另外，安全研究圈靠发现漏洞积累名声，OpenClaw 成了所有人都想攻破的目标，几百人开着自己的 Agent 去攻击它，常见类型是远程代码执行、绕过审批、代码注入、路径穿越。

他举了一个 CVSS 10 分（CVSS 是漏洞严重程度评分，10 分为最高）的例子：iPhone 应用还没发布，如果同步时只给只读权限，有办法拿到写权限。他说实际中几乎所有人要么能访问自己的网关，要么不能，这个分级权限模型是他自己想做得更灵活而犯的错，几乎没人用；但按 CVSS 规则算就是 10 分，他也照规则办。真正影响用户的也有：疑似来自朝鲜的 GhostClaw，用名字相近的 npm 包骗人，去错网站下载就会装上 rootkit；还有 Axios 供应链攻击（Supply Chain Attack，通过污染依赖包来攻击下游项目），OpenClaw 自己不用 Axios，但依赖的 MS Teams 或 Slack SDK 用了而且没锁版本，所以也受影响。

他一度想自己处理所有报告，这不可能。最快的帮助来自公司，Nvidia 派了人全职筛选这些报告、加固代码库。

恐慌营销和真实风险

他批评了一些公司和大学的恐慌营销。论文 “Agents of Chaos” 声称讨论 Agent 普遍问题，但用了四页详细描述 OpenClaw 的架构，却没提安全页面上的安装建议。OpenClaw 的建议是：个人 Agent 不要放进群聊；放进群聊就打开沙盒，因为任何能跟它说话的人都能让它泄露它能拿到的东西；团队 Agent 只应该知道团队可以知道的东西。他私下问作者，对方承认为了让 Agent 最强而用 sudo 模式跑，这需要改代码才能做到，但报告里没写。另一个例子是一个让比利时网络安全部门发布警告的远程代码执行漏洞：恶意网站构造链接触发网关并转发网关 token。但在默认和推荐配置下，网关 token 只在本地或私有网络可用，外部网站访问不到，除非用户不看文档、用 Claude Code 硬改配置。

他承认风险确实存在，主要是“致命三要素”（lethal trifecta，Simon Willison 提出：Agent 同时能访问私有数据、会接触不可信内容、能对外通信，就有数据外泄风险）。这不是 OpenClaw 特有的，任何强大的 Agent 系统都有，越强大越需要理解它在做什么。

维护负担方面：大部分报告由 Agent 生成，但他仍然要用脑子读，因为还不能完全信任 Agent 自己判断。他说报告写得太客气、或者作者道歉，大概率是 AI，因为搞安全的人通常不道歉。很少有报告附带修复，附带的通常也是糟糕的修复；早期他着急合并，确实把产品弄坏过。他说 ffmpeg 等开源项目也在公开抱怨同样的问题。

OpenAI 和基金会

他说外界说 OpenAI 买下了 OpenClaw，这不对，“他们最多买了我的 soul.md”。OpenAI 理解世界需要更多人玩 AI，从而理解它的风险和可能；在家用过 OpenClaw 的人会回公司问为什么我们没有 AI。要让项目成功，它就不能属于一家公司，所以他在建“瑞士”，也就是 OpenClaw 基金会，有一位叫 Dave 的人在帮忙，参考了 Ghostty 的做法。基金会快完成了，卡在美国银行系统对非美国人很慢。建成后可以雇全职人员保持速度、提高质量，也让他腾出时间做好玩的东西。

07. swyx 对谈 Peter Steinberger：OpenClaw AMA

直播位置 2:28:13 · 日程表上主持人是 Gergely Orosz，实际由 swyx 主持

“Closed Claw”和开源

swyx 先问了最尖锐的问题：Peter 加入 OpenAI 后，大家担心 OpenClaw 会变成 “closed claw”。Peter 承认 OpenAI 过去对开源并不总是友好，但他说变化很大：Codex 开源了，OpenAI 还发布了一个编排层 Symphony。OpenAI 明白 OpenClaw 必须保持开放、支持任何模型，包括本地模型。他说 OpenAI 其实愿意派更多人来，但他自己控制了人数，免得看起来像被接管。他拉来了 Nvidia、Microsoft、Telegram、Salesforce（Slack 插件的维护者来自 Slack）、腾讯、字节跳动，也和阿里巴巴、MiniMax、Kimi 等模型厂商聊过。他特别称赞 Nvidia 的工程师“有主动性，直接动手做”。swyx 补充说贡献者图表显示高质量贡献者很难留住，因为维护者老被别的公司挖走。

本地模型和数据归属

他做 OpenClaw 的部分动机是：大公司通过连接器访问你的 Gmail，邮件托管在别处，那家公司就能看到全部。他更想让数据掌握在自己手里，需要顶级 token 时才把一小部分发到云端。他说“我骨子里是欧洲人，你想拥有自己的数据”。另外，创业公司想接 Gmail 要走半年的审核，但个人的 Agent 可以点击任何网站，连“我不是机器人”都能点，所以能绕过大公司建的数据孤岛，做出大公司做不了的自动化，他称之为黑客的方式。关于 GPT-OSS 他不便透露，只说 OpenClaw 让公司里更多人对开源兴奋起来；相比之下，某个以 A 开头的顶级实验室会因为泄露源码起诉你，或者你太成功就封你。

他怎么写代码

他的“prompt request 代替 pull request”说法已经流传开，他在 OpenAI 的 token 用量也让人吃惊。他说用 Codex 配 GPT-5.1 时比较慢，他最多同时开近 10 个会话；现在速度快了，还有 fast mode，通常五六个窗口就够，因为每轮循环更快，他思考的工作量差不多，不太需要分屏了。他认为同时做六件事并不自然，只是在 token 速度更快之前的变通办法。

swyx 问他怎么看完全不看代码就合并的“暗工厂”（dark factory，借用无人工厂的说法，指 Agent 全自动产出代码、人不审查）方式。他说越来越可行，但暗工厂意味着一开始就想好要做的所有东西，他不认为好软件能这样做出来。去山顶的路从来不是直线，会走偏、会发现新东西和捷径；第一个想法很少是最终产品，用回瀑布模型就锁死了。他是迭代式的：做一步，玩一下，看感觉，提示也随之改变。某些环节可以做流水线，但 PR 不能全自动合并，因为很多 PR 没有意义，用户会把产品往各个方向拉，AI 不太可能知道正确方向。他写了愿景文档来引导，但瓶颈仍然是思考和品味。

什么是 taste

他说当下最低层次的品味是“闻起来不像 AI”：写作风格、个性，还有 UI。swyx 举例说左边带彩色边框的卡片就是 AI 做的，Peter 补充说之前是紫色渐变。他说你能像认出 AI 写的垃圾文字一样立刻认出来，所以他用“气味”来形容。更高一层是：既然很多事都能自动化，就可以花更多时间在小细节上，比如运行 OpenClaw 时偶尔会弹出一条吐槽用户的消息，这种让人愉快的细节靠高层提示是得不到的。

swyx 提到 Peter 在 soul.md（定义 Agent 性格的文件）上下了很多功夫。Peter 说 2023、2024 年的 ChatGPT 是我们在不理解 AI 能做什么时重造了一个 Google，你不会期待搜索框有性格。但做 Agent 不一样：他最初把 WhatsApp 中继接到 Claude Code 上，发现虽然 Claude Code 有点个性，但不像朋友发消息的样子，太啰嗦，省略号太多，于是开始调教它“写得更像人”，“像只龙虾”。他认为 OpenClaw 不可能出自美国公司，因为在发布前就会被法务毙掉；它有些行业尚未解决的问题，大实验室也没有市场证据证明人们想要它。他刚做的时候想过最坏情况：泄露 token、邮件、上传照片，都不至于致命，他能接受这个风险；公司场景需要不同的做法。

未来形态、提示注入和“做梦”

  • 形态：他希望在家里任何房间说一声就能和 Agent 对话，像《星际迷航》里喊 “computer”。他在每个房间放了 iPad，Agent 能用 canvas 功能在离他最近的屏幕上展示内容。将来可能你有一个大写的私人 OpenClaw，公司里有一个小写的公司 claw，两者能以双方都放心的方式对话。swyx 说 Marc Andreessen 和 Andrej Karpathy 都在用 OpenClaw 管家里的设备，讽刺的是这之所以可行，是因为智能设备的安全性普遍很差。
  • 提示注入（Prompt Injection，把恶意指令藏在网页、邮件等内容里诱使 Agent 执行）：他说可能还没想够，但前沿模型已经很擅长识别，网页或邮件里随机混进来的内容把它标为不可信，就很难再借此让它泄露数据；如果攻击者能无限制地轰炸你的 claw，仍有机会。他担心的是有人用一个 200 亿参数、毫无防御训练的本地模型去浏览网页和读邮件，所以 OpenClaw 用小模型时会警告，结果被人说成“讨厌本地模型”。swyx 提到 Simon Willison 的双 LLM 方案，以及从 Vincent 那里听说 OpenClaw 也实现了 Tobi Lütke（Shopify）那种随时间积累信誉、信誉越高权限越大的信任系统。
  • 做梦（dreaming）：维护者在他忙的时候做了一个“做梦”功能，即整理记忆、生成梦境日志、回顾会话记录。他类比人睡觉时大脑做垃圾回收，把一部分短期记忆转为长期、丢掉其他的。swyx 说从 Anthropic 源码泄露里看到他们也在做 dreaming。和 Karpathy 说的 wiki 相比，Peter 说 wiki 更偏记忆，各种东西会混在一起。OpenClaw 这几个月从一团意大利面代码变成了一切都是插件，记忆、wiki、dreaming 都能替换，更像 Linux，你可以装自己的部件，不必都提 PR。

日常和给工程师的建议

swyx 说他在两场活动之间还在后台写代码。Peter 说现在工作更多是交谈和引导方向，他在 OpenAI 的部分职责是帮他们避免重犯 OpenClaw 已经犯过的错，在 OpenClaw 则继续尝试新东西，让公司不必 fork 就能定制自己的 claw。“有时候我也睡觉。”

最后问工程师该培养什么能力。他说品味、系统设计，以及“说不”。不想系统设计，迟早会把自己逼进死角；所有知识都在模型里，但你得问对问题。再疯狂的想法都只差一个提示，单个想法从来不是问题，难的是这个加那个加那个之后怎么拼在一起。他让大家站在 Agent 的角度想：被扔进一个代码库，AGENTS.md 可能过期，根本不知道这是什么，你让它“加用户资料”，它就接上看到的两处地方，但没看到整个系统，于是产生大量局部解法。人的工作是给它提示：考虑一下这个、看看那里、这和那怎么交互，最终得到可维护的系统。

08. Vincent Koc（Comet ML / OpenClaw 核心维护者）：暗工厂，OpenClaw 怎样发得比你读 diff 还快

直播位置 2:55:01

背景

Vincent 是 OpenClaw 的核心维护者之一，白天在 Comet ML 做评测（Eval，系统性地衡量模型或 Agent 表现）相关的研究和开发者关系。他在东伦敦长大，在威斯敏斯特上的大学，后来移居澳大利亚。他放了一张 2013 年戴早期 VR 头显的照片：说明书写着每次只能用 5 分钟，他玩了 3 小时《军团要塞 2》，然后吐了 3 小时。他说处在技术边缘的东西都很粗糙，在 OpenClaw 以这种速度提交代码，他每小时都会被 GitHub 限流。他拿英国工业革命作比：以前瓶颈是织工的手，现在工程师在变成工厂经理，瓶颈变成品味。

速度有多快

他说就像 ChatGPT 刚出来时大家嘴上否认、私下都在用一样，大规模使用自主 Agent 也正在发生。公开的例子有：Anthropic 用 Agent 构建了一个新的 C 编译器；Spotify 说不再手写代码；Steve Yegge 一个人每天推 50 个 PR，自称“vibe maintainer”。OpenClaw 高峰期一天 800 次提交，而核心维护者只有 10 到 15 个人，都有白天的工作。他个人在 3 月 15 日接近一天 3,000 次提交，从他的提交记录能看出他几点睡觉、几点起床。

他们先做了“commit maxing”，这让他想到 Ralph 循环（Ralph loop，把同一个任务丢给 Agent 反复循环跑，烧几个小时 token 看会不会做出来）。他问：能不能更有主见一点？一位维护者开玩笑叫它 “Bart looping”。要跑循环，但要聪明地跑，奖励机制是什么。

在 Nvidia 的那一晚：大重构

提交量爆发的前一天，他和 Peter 在 Nvidia 帮忙做 NemoClaw。Peter 跑大约 15 个 Codex 会话，他自己通过 VPN 连回家里的 Mac Studio 再跑 10 到 15 个，算上子 Agent 两人一共大约 60 到 70 个 Agent，前台大约 15 条“泳道”。同时另一位维护者挪了几个文件夹，把 MS Teams、Slack 等聊天渠道的代码整体换了位置。

ACP（Agent Client Protocol）由 Zed 发起，Zed 是一个用 Rust 写的编辑器，比 Electron 系编辑器更省内存，他从去年秋天开始用。他区分了几个协议：MCP 是给模型提供工具的；ACP 是标准化 Agent 和客户端（比如编辑器）之间交互的，现在 VS Code 里的 Codex、Claude Code 插件各做各的，大量重复劳动，统一接口后只需做一次；另外还有 Agent 对 Agent 的协议。ACP 是人对 Agent，但 Agent 也可以用它来和其他 Agent 对话。他说长远会都支持，当初选 ACP 是因为他最需要 Codex 和 Claude Code 的适配器，当时只有 Zed 做了，Google 那边还没有。

OpenClaw 里加功能通常通过 CLI，所以他做了 acpx：一个 ACP 的命令行工具，让任何 Agent 都能通过命令行调用其他 Agent，现在它在慢慢变成 ACP 的瑞士军刀。

把 PR 分诊做成工作流

OpenClaw 的 PR 像消防水管：累计超过 6 万个，平均每天新开 300 到 500 个。几万个利益相关者想往里加功能，项目最大的挑战是吸收这些需求而不产生 AI 垃圾。很多 PR 是用户遇到问题后让自己的 OpenClaw 说“请修复”产生的，不能合并，但也不能直接丢，因为它是用户反馈，说明某处坏了，要分类归档。他和 Peter 的做法是问 Agent：这是什么？这是最好的修复吗？多数时候答案是否定的。他发现这些步骤很机械，于是“自动化这个自动化者”，抽象出一个流程：

  • 找出 PR 的意图，复现 bug，判断实现是否合理。
  • 检查冲突，处理评审意见，让 CI 通过（很多提交者根本不管 CI）。
  • Ralph 式的评审加重构循环：他认为只要不让循环做设计决策，只让它发现浅层 bug 并修复，就不会产生垃圾。浅层重构自动做，需要根本性重构的转给人。解决合并冲突现在也不需要人手了。

他把这些做成了“给 Agent 的标准作业流程”，内置在 acpx 里：一个类似 n8n 的工作流引擎，驱动 Codex 会话，每一步输出 JSON 结构化数据，可以接进 ETL 式的流程。他播放了一段处理单个 PR 的回放：复现、判断、重构、评审循环。他说这是个通用工作流引擎，Agent 应该像药膏一样“大量涂抹”在一切能用 Agent 解决的问题上。

一次性企业 Agent：Spritz

他认为个人 Agent 和企业 Agent 是一个光谱，企业场景会消耗多得多的推理，所以钱也更多。他相信按需、一次性的 Agent，一个任务一个 Agent。问题是在 Slack、Teams、Discord 里，一个 OpenClaw 就是一个应用实例，要多一个有独立名字和头像的 Agent，就得再建一个 Slack 应用、写应用清单，聊天平台还不支持多 Agent 批量创建。在平台支持之前，他用别的 UI 解决。

需要的组件：Kubernetes、Agent Harness（OpenClaw、Codex、Claude Code 或任何 ACP Agent）、GitHub 读写权限、状态同步（类似 rsync 或 Dropbox 用的算法）。他的日常工作是一个开源编排器，仓库是 textcortex/spritz，一个 Go 写的 Kubernetes operator，用 Helm chart 部署。用户在 Slack 上和一个“礼宾”Agent 聊，100 个员工同时用会成为瓶颈，于是它可以为其他任务创建新的 Agent，并给出网页链接。他们目前用在错误报告上：在 Slack 里问“新版本发布后有没有新 bug”，让它派一个 Agent 去调试，因为没法把那个 Agent 放进 Slack，就在集群里一个 React 网页上开对话，体验类似 Codex Web 或 Devin，但每个 Agent 用一个完整的 Kubernetes Pod。他承认这很浪费，但认为是更好的抽象，因为 OpenClaw 证明了给 Agent 一整台电脑会强大得多。他提到 OpenHands 用 Firecracker 虚拟机，自己对各种虚拟化框架也在边做边学。Agent 通过 ACP 抽象，不锁定某一家。他说最后这部分属于他在 TextCortex 的工作，和 OpenClaw 无关。

17. Matt Pocock（AI Hero / Total TypeScript）：软件基本功比以往更重要

直播位置 8:29:42 · 英文原题 It Ain't Broke: Why Software Fundamentals Matter More Than Ever

反对 specs-to-code

Matt 是一名教师，最近在教一门叫 “Claude Code for Real Engineers” 的课。设计课程时他遇到了 specs-to-code 运动：写一份规格说明，让 AI 变成代码；出问题就改规格、重新“编译”，不看代码。他试了，忍不住还是看了代码，发现每重跑一次代码就更差一点，最后成了垃圾。他认为忽略代码让它自己管理，只是换了名字的 vibe coding。

他去翻老书，想用英文告诉 LLM 什么是好代码库。John Ousterhout 的《A Philosophy of Software Design》把坏代码定义为复杂：任何让系统难以理解和修改的结构都是复杂性，所以好代码库就是容易改的代码库。《The Pragmatic Programmer》里的“软件熵”说的就是他看到的现象：每次改动只考虑这次改动、不考虑整体设计，代码库就会越来越糟。他说 specs-to-code 背后的理念是“代码很便宜”，现场很多人听过。他不同意：坏代码是有史以来最贵的，因为代码库难改，你就拿不到 AI 能给的好处，而 AI 在好代码库里表现很好。这就是他的论点：好代码库比以往更重要，所以软件基本功比以往更重要。

失败模式一：AI 没做我想要的

《The Pragmatic Programmer》说没人确切知道自己要什么，和 AI 对话其实是它在做需求收集。Frederick Brooks 的《The Design of Design》提出“设计概念”：多人一起设计时，大家之间漂浮着一个关于要做什么的无形共识，它不是一份资产，没法写进 Markdown。他意识到问题是他和 AI 没有共享的设计概念，于是写了一个叫 grill-me 的 skill，大意是： 

Interview me relentlessly about every aspect of this plan until we reach
a shared understanding. Walk down each branch of the design tree,
resolving dependencies between decisions one by one.

“设计树”也来自 Brooks。这个 skill 所在的仓库有大约 13,000 星。这几行会让 AI 问你 40 个、60 个，甚至 100 个问题，直到达成共识。生成的对话可以整理成 PRD（产品需求文档），小改动可以直接拆成 issue 交给后台 Agent。他个人认为这比 Claude Code 默认的 plan mode 好，因为 plan mode 太急于产出一份计划然后开工。

失败模式二：AI 太啰嗦

这像和领域专家合作：比如对方懂芯片你不懂，必须建立共同语言，否则你把听不懂的术语翻译成你自己都不懂的代码。他转向 DDD（Domain-Driven Design，领域驱动设计），其中的“通用语言”（ubiquitous language）要求开发者之间的对话、代码里的表达、和领域专家的对话都来自同一个领域模型。实践上就是一个 Markdown 文件，列出你和 AI 共用的术语。他做了 ubiquitous-language skill：扫描代码库找术语，生成一组 Markdown 表格。他在和 AI 讨论计划时一直开着这个文件。他读 AI 的思考轨迹发现，这不仅改善了规划，还让 AI 思考得更简洁，实现也更贴近计划。

失败模式三：做出来了但不能用

显而易见的办法是反馈回路：静态类型（不用 TypeScript 是疯了），给做前端的 LLM 浏览器访问能力，自动化测试。但他注意到 LLM 不会像老手那样用好反馈回路，它会一口气写一大堆代码，然后才想起该跑类型检查或测试。《The Pragmatic Programmer》把这叫“开得比车灯照得还远”：反馈的频率就是你的速度上限，应该边走边测、小步前进。所以他用 TDD（测试驱动开发：先写一个失败的测试，让它通过，再重构），它迫使 LLM 小步走。

难点是测试本身一直很难：测多大的单元、mock 什么、测哪些行为，这些决定互相依赖。他的观察是好代码库就是容易测试的代码库，代码库越好，反馈回路越好，AI 产出的代码越好。Ousterhout 主张深模块：少量大的模块，接口简单，背后藏着大量功能；浅模块则功能少、接口复杂。AI 很爱写出由大量小块浅模块组成的代码库，它自己探索时也会迷路，找不到对的模块、看不清依赖。深模块的代码库是同样的代码，被装进有清晰边界的模块里，顶上是接口。接口应该由你仔细设计，实现可以多交给 AI。他做了 improve-codebase-architecture skill，反复执行一套步骤：探索代码库，找出相关的代码，把它们包成深模块。边界简单，就在接口处测试，这样的代码库奖励 TDD。

失败模式四：脑子跟不上

他问谁觉得自己比职业生涯任何时候都累，很多人举手，他也是。浅模块的代码库对人脑也更难，因为你和 AI 都得把所有信息记在脑子里。深模块可以当灰盒：设计好接口，不必太细审实现。金融这类关键部分不能这样，但应用里很多模块只要有可测试的边界、你理解它的用途并从外部设计好，就不必太操心内部。他说这救了他的脑子。所以第五条建议是：设计接口，委派实现。

这要求你在规划时始终清楚应用的模块地图，把它纳入通用语言和规划 skill。他的 write-a-PRD skill 会明确写出哪些模块要改、接口怎么变。他引用 Kent Beck：每天都投资于系统的设计。specs-to-code 是在从设计中撤资。他的比喻是 AI 是很强的一线战术程序员，像地面上的军士，上面需要有人做战略层面的思考，那就是你，而这需要用了二十多年的软件基本功。skills 在 GitHub 的 mattpocock/skills 仓库，他的课程和通讯在 aihero.dev。

18. Sunil Pai（Cloudflare 首席系统工程师）：Code Mode，让模型写代码而不是调工具

直播位置 8:48:31

工具调用在规模上会坏

Sunil 做过开源实时多人应用工具 PartyKit，现在在 Cloudflare 做 Agents SDK。他说 Code Mode 不是他们发明的，有前人做过，这场讲的是它带来的影响。工具调用（Tool Call，模型输出结构化的 JSON 请求，由程序执行后把结果返回给模型）在工具少、任务短时没问题；一旦接上 Google 服务、Jira、wiki，几百个工具塞满上下文，就开始出问题，组合起来也别扭，和模型来回往返很慢。

他们的做法是让模型生成代码（通常是 JavaScript），在一个环境里执行。好处是：有类型化的 API，可以做类型检查，有语法错误提示；模型训练数据里有海量代码；一次执行就能完成原本要来回多次的事；代码天然支持循环、保存状态、顺序和并行执行。

Cloudflare API：从 120 万 token 到 1,000 token

第一个应用来自同事 Matt Carey（第二天有他的演讲）。Cloudflare API 有大约 2,600 个端点，每个暴露成一个工具，第一次调用就要约 120 万 token，所以不可能为整个 API 做一个普通的 MCP 服务器。Matt 只暴露了两个工具：search 和 execute，输入都是一段代码。search 的函数输入是完整的 OpenAPI JSON 规格；execute 提供一组可以调用的函数。这样把一百多万 token 压到大约 1,000 token，他说大约减少了 99.9%。

他的例子：客户凌晨三点被 DDoS 攻击，说“找出所有攻击我们的 IP 并封掉”，这时没空在 Cloudflare 那个出了名难用的控制台里找菜单，也找不到客户经理。普通 MCP 要大约 8 次往返，Code Mode 下模型生成一段代码，在 API 旁边一次跑完。

现场演示：他用只读权限的服务器让它“列出我的 workers”。它先搜索相关端点，再跑代码请求，之后开始处理分页并遇到 JavaScript 错误，界面渲染不完整，他说测了 10 次都好好的，“我得付钱用 Mythos 模型才行”。他指出后台确实在列 workers。他说如果这只是一场 MCP 优化的演讲，到这里就讲完了，但这让他们意识到有更深的东西。

“栖居于状态机”

他举例：桌面上有 200 张照片要分类重命名，程序员会打开编辑器写个小脚本，可能把每张图丢给视觉模型取标题，然后重命名。他母亲不会这样做，她只能打电话给他，或者买一个每月 7 美元、还要装个守护进程的通用照片管理应用。过去这是可接受的分工：非技术用户用别人为他们做好的界面。LLM 打破了这个边界，地球上每个人都有了一个能写代码、能和系统交互的伙伴，只要能安全执行。

第二个例子来自 Cloudflare Workers 的创造者 Kenton Varda。Kenton 给自己做了个 vibe coding 环境，让它生成一个类似 tldraw、Excalidraw 的画布，然后在上面画了井字棋棋盘，在左上角画了个 X，让模型陪他下棋。模型开始写一个井字棋应用，Kenton 马上叫停：你能访问系统的全部状态，就是一组笔画数据（网格线、X 的笔画），去看它，然后跟我下。模型把状态读进上下文，认出这是井字棋棋盘、左上角有个 X，就在中间画了一个完美的圆。系统里没有任何井字棋代码。后来模型输了，看推理轨迹发现 Opus 是故意让 Kenton 赢的，他说那是另一个对齐话题。他们内部开始用一句话描述这种现象：模型停止生成程序，开始栖居于状态机之中（it stopped generating a program and started inhabiting the state machine）。没有单独的“生成应用”阶段，模型本身就是交互的一部分。

新的软件架构

他说过去三到六个月大家都意识到编程 Agent 是很好的通用计算机器，所以人人都在做 Harness，在 Mac Mini 上跑 Claude Code 或 Pi（他吐槽为了调 API 不需要花几百美元买 Mac Mini，二手价格都被炒高了）。这种架构的关键是有一个安全空间执行生成的代码，并向其中暴露能力。他也承认“沙盒”这个词被用滥了，Cloudflare 自己也有基于容器和虚拟机的 Sandbox SDK，但他说的不是那个。他要的沙盒特性是：

  • 从零能力开始：容器自带一堆功能，再从外面加安全措施；他说的沙盒唯一能做的是执行代码，不能 fetch，没有任何 API，然后显式地授予能力。
  • Cloudflare 用的是 dynamic workers，基于 V8 isolate（V8 引擎里的轻量隔离执行环境，启动极快），有约 10 年的安全加固。他们可以控制所有外发请求和网络连接，推荐默认禁止外发请求，只暴露 API。
  • 要快，并且要有完整的可观测性：如果它上周二做了一笔 230 万美元的交易，你必须能回去看当时的代码。
  • 也可以用 WebAssembly 或自定义 JavaScript 解释器，重点是能执行、能暴露能力、运行快。

在此基础上可以更有野心：生成运行几天、几个月甚至几年的长期工作流，每个实例在生命周期中携带自己的状态；为每个用户生成完全定制的 UI。他用电商举例：产品越受欢迎，UI 越要迁就所有人而变得平庸；有了用户的全部上下文（喜好、购物车、让他不爽的事），可以按需生成界面，比如“我要退这双鞋，再找一双 100 美元以下的类似款”和“我的延误订单怎么了”会得到完全不同的程序。他还说很多人发现把 Harness 放在离用户更近的地方（比如手机上）更强，因为可以把不同服务按任务拼在一起，他自嘲这快成反 Cloudflare 演讲了。

他说作为 React 程序员，这意味着要重新思考 UI，这是一条科技树上 30 年没探索的分支，因为以前没有安全的 eval。你的下一批十亿用户是替人写代码的小机器人，客户仍然是人，但和你系统交互的是它们。它们待在包注册表里，“梦里是类型和语法错误”，所以要考虑 Agent 的开发者体验：Markdown 文档、告诉 Agent 下一步怎么做的报错、可搜索的发现机制。他最想让大家记住的是基于能力的安全（Capability-based Security，代码只能使用被明确授予的能力，没有默认权限）。语言不限，Python、Wasm 都行，他希望 Lisp 能复兴。他认为 UI 程序员离用户最近，会在这里做得很好。他的结尾是：过去程序员拥有代码，能和任何系统交互；其他人只有按钮和表单。这个区分正在消失，要让代码去说话。
