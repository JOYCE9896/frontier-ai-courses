01. Jakob Pörschmann（Black Forest Labs AI 解决方案负责人）：从像素到机器人

直播位置 0:18:40–0:42:06 · 英文原题 From Pixels to Robots

Jakob 带领 Black Forest Labs 的 AI 解决方案团队，包括前线部署工程（Forward Deployed Engineering，派工程师到客户那边做定制落地）和解决方案工程。Black Forest Labs 是德国的研究实验室，做图像和视频基础模型 Flux，背景里播放的样例来自最新的 Flux 3。他开头问观众信不信同一个视频模型能控制机器人、玩视频游戏，然后放了两个例子：左边是 Flux 在玩游戏，画面是 Flux 接管控制后生成的帧；右边是一台 LeRobot 机械臂在 Flux 3 作为“智能主干”的控制下完成抓取放置任务。他说两者之间的桥梁是对模型的定制，这也是他的团队每天在做的事。

推理管线的六个环节

他把和企业客户合作时的推理管线拆成六步，每一步都是可以定制的地方：

  • 用户输入：文字、图片或视频提示词。
  • 提示词上采样（Prompt Upsampling）：在用户和 Flux 之间放一个 LLM 或 VLM（视觉语言模型），理解用户意图，把提示词改写得更接近用户想要的结果。
  • 审核（Moderation）：决定用户能看到什么、不能看到什么。它大多不在模型里，但属于用户体验的一部分，他说这是最重要的产品界面之一。
  • 模型权重：可以做微调，比如训练 LoRA（低秩适配，只训练一小组附加矩阵的轻量微调），针对风格、角色、产品或行为微调，甚至加入新的模态。
  • 后处理：放大、修复、再审核等。
  • 部署与服务：怎样部署、优化、蒸馏模型。

提示词上采样：一个真实客户案例

他先举了个简单例子：直接把“森林里的小木屋”发给 Flux，得到一张普通的小木屋；默认上采样器按一般用户偏好把它扩写成“超写实、石头烟囱、柔和金色光线”之类，出来的图更讲究。

真实案例是一个客户想给应用里用户的对话配插图。话题是机器生成的，比如“适合家庭的旅行目的地”“给洗碗机排水”，既不是人写的，也不是图像提示词。客户还有设计规范：主体放在右侧，画面干净，左边留大片空白放文字，不能出现人物和地标等。他说这时图像模型已经不是瓶颈，模型什么都能画，瓶颈是设计规范。上采样要做的是把用户话题、设计规范和 Flux 的训练分布对上，找到能稳定产出合规图片的那个提示词区域。他对比了三种结果：不做上采样，图片乱七八糟，比如明信片风格，不同随机种子之间差异很大；用默认上采样器，更像插画，但不符合规范；把设计规范写进定制的上采样器（其实就是一个系统提示词），就得到主体在右、左侧留白、画面干净的图。

他总结这个方法的好处是迭代快，只改系统提示词，不需要训练，适用面广。他还说企业客户那边的经验是“用户很懒”，不会去研究 Flux 的训练分布和提示词写法，这一步替他们做了。

审核与安全：配置和 Slider LoRA

他说很多人用视频模型时见过“图片可能包含真人肖像”之类的报错，这不是模型能力的限制，是审核服务拦下了。对大客户来说这是大问题。第一种做法是改配置：API 上有一个安全参数，给特定客户还能细到按类别放行或拦截（暴力、色情、自残、IP 和肖像），再配合每个客户自己的黑名单和白名单。他举了三类客户：儿童平台全部从严，外加专门的黑名单；时尚零售商对偏性感的提示词宽松一点，但拦截竞品品牌，只允许生成自家产品；影视公司可以放开一些暴力，放行自己有授权的角色，拦截其他没有授权的角色。

第二种做法用在模型部署到客户自己基础设施上的场景，这时不会把整套审核栈一起交付，需要把安全性写进权重。他介绍了 Slider LoRA：让 LoRA 学到一个抽象概念，推理时反向使用。以“去性感化”为例，用一批通用的人物图片训练，比如一张穿黑裙的女性照片，每轮训练同一张图配两种文字描述，一种朴素，一种带性暗示。两种描述都包含“女性、黑发、黑裙”等内容，差别只在性暗示，于是 LoRA 矩阵里留下的就是“性感化”这个概念的方向。推理时用负的 alpha 系数把它加到权重上，让模型往反方向走。他给的结果是裸露检测减少约 20%（字幕作 minus 20），68% 的评判认为图片性暗示更少，整体画质和原来打平。

他的经验是：安全是产品的门面，用户最先碰到的就是它，有时甚至可以成为卖点或商业模式；模块化更划算，写进权重的方法训练贵、是静态的、需要更新，所以大多数情况下他们还是用配置。

Flux 3 Action：给视频模型加一个动作模态

他说微调一般是为了风格、物体、角色或行为（扩图、局部编辑、去性感化都属于行为微调），再往前走就是通过中期训练和后训练加入新模态。Flux 3 Action 是在 Flux 主干上继续中期训练、后训练并微调出来的动作预测模型，演讲前一晚刚以开放权重发布在 Hugging Face 上。

它的输入有文字条件（描述任务）和视频条件。演示用的是 LeRobot 的 SO-101 机械臂做抓取放置，机器人有两个摄像头，一个在夹爪上，一个在上方。模型针对这款机械臂的“具身”做了微调：机械臂有六个轴，每一帧用一个六维向量表示各轴该往哪个方向动。输出是后续视频帧，同时输出这个动作向量，机械臂据此运动。

架构上，普通视频模型先用变分自编码器（VAE）把像素帧投影到潜空间（一种压缩的抽象表示），在潜空间里做去噪预测下一帧，再用解码器还原成像素。Flux 3 Action 是一个世界动作模型（World Action Model）：动作向量不经过 VAE，直接归一化到潜空间的维度，和视频潜变量在同一个 Transformer 里一起去噪。做动作任务时，视频部分的解码器甚至不用，只把动作部分反归一化后交给机器人执行。他说这个模型发布后在动作预测的排行榜上排第一。

最后他的结论是：好的定制要“按需具体、尽量通用”，把一个具体问题解决到够用的程度，同时能推广到整个领域。

02. Dorian Lods（ElevenLabs 创意工程师）：规模化生成视觉身份

直播位置 0:44:03–1:07:53 · 英文原题 Generating Identity at Scale

主持人介绍说，用过 ChatGPT 语音模式或 ElevenLabs 的人见过的那个小圆球（orb），很可能就是 Dorian 做的。Dorian 是 ElevenLabs 的创意工程师，现在在巴黎。他讲的是自己的工作方式怎样从“做东西”变成“做那个做东西的系统”。

从一个球到 4,000 万个球

他以前做沉浸式创意网站（主要用 WebGL）和装置，每个作品都围绕一种感觉打磨上千小时，只为一个结果。期间他用过 ComfyUI 这类工具搭更复杂的 AI 流程，但产出仍是单一的。他做过 OpenAI 发布语音模型时的那个球，那是他做的第一个标志性的球：完全手工调校、确定性的，屏幕上的一切都由着色器（Shader）计算出来，颜色、输入、行为都仔细调过。他花了几周设计一个球，到了 ElevenLabs 要为 4,000 万个声音设计。

他介绍了 ElevenLabs 的一组数字：支持 90 多种语言；平台上有数百万企业、开发者和创作者；6 月底 ARR（年化经常性收入）超过 6 亿美元；2 月估值 110 亿美元；团队 700 多人，分布在 50 个国家；平台上有 1,000 多万个 Agent；每天生成超过 34 年时长的音频；音乐模型生成了 2,500 万首曲目；为 11,000 多位因疾病或受伤失声的人免费恢复了声音，这是他最喜欢的数字。

他加入的是设计团队，第一个任务是：声音是 ElevenLabs 的主要交互方式，怎样让每个声音有一个视觉身份，并且在整个产品里通用。现场放了一段宣传视频。他们的出发点是“每个声音都是一张脸”：平台上有 4,000 多万个声音（用户用提示词生成的、克隆的等），每个都要有可辨识的形象，体现声音的特点，同时一看就是 ElevenLabs。

两层结构：图像层和实时层

球由两层叠成。底下是图像层，承载品牌特征，并和声音绑定；上面是实时层，负责交互和“活”的感觉。

图像层的做法：一个声音对应一张脸。他们分析每个声音的音频输出，提取关键指标，分成音高、能量、表现力等类别，驱动后面的管线。一开始想直接用嵌入向量（Embedding，把数据表示成一串数字），后来发现太复杂。为了摸清需要覆盖的范围，他们抽取了平台上最受欢迎的 20 万个声音，发现分布很不均匀：低沉的声音多，主要用于旁白；高亢、能量很强的卡通声音属于小众。

为了让模型“说 ElevenLabs 的语言”，他们做了合成数据集，在现成模型上训练了一个专门的 LoRA。他觉得有意思的一点是用文字描述（caption）引导推理：训练时在描述里加入人工挑选的颜色等关键词，对应高音、中音等不同声音类型；这些关键词存成一个词表，推理时重新组装提示词，模型就能用训练里见过的同一批关键词。他们试了几种开放权重模型（他说其中一个来自“我们的朋友”，指上一位讲者的公司），目标是在推理成本、大规模生产和质量之间找到平衡。生成底图后还有一步“后推理”：把图模糊化，再在图内裁剪，让每个球都有足够的变化，并为着色器做准备。

实时层是一个着色器，叠在底图上。设计阶段他们把代码当作主要的设计媒介，做了一个界面让整个设计团队调参数看效果，有些参数由音频反馈驱动。官网和产品里用 WebGL 实时渲染，另外转成 OpenGL 支持服务端渲染，给不能直接跑着色器的地方出预览。着色器有六层，包括与音频联动、带涟漪效果的实时流体模拟，多层噪声（FBM 等），一层和旧版球呼应的声波，以及品牌统一的颗粒质感。他说设计目标是让球扎根于自然，看起来有机。

大规模调试和成本

“一个声音一个结果”意味着不能挑结果，每一个都必须对。调试时挑的几个样子很好，大规模跑起来就可能出问题，所以他们做了内部的大规模审查工具。然后财务来了：每张图 10 美分，乘以几百万太贵，必须降低延迟和成本。他们回到声音分布图，一次性生成一张巨大的图集（Atlas），新声音不再单独生成图片，改为从图集里裁取，再加旋转、不同裁法、色调调整，保证每个声音仍然独特，并且和音频特征挂钩。这样省下了 360 多万（字幕没说币种），速度快 10 到 15 倍，每个声音生成视觉不到 3 秒，用户新建声音时在后台完成，察觉不到。

整条管线是：声音分析，把指标映射成视觉参数（颜色、能量、纹理等）；生成管线准备底图、着色器参数、纹理、预览、缩略图和 MP4 动画，分发到 CDN；最终产出 4,000 多万个结果。他们要求 iOS、Android 和网页上的着色器看起来一致，还有一个后台界面可以审查每个声音的球。后来这些做成了一个独立的云服务，叫 Picasso（“因为是画家，而我是法国人”），作为共享 API 给所有地方用：主应用、官网、iOS 和 Android、音乐品牌 ElevenLabs Music，以及品牌工具和动效设计。系统向后兼容旧版球，他们对 4,000 万个声音跑了几天的回填（Backfill），他说那几天很紧张，最后成功了。

他展示了实际效果：低沉的声音偏暗，能量高的带蓝色调，可以在平台上筛选声音看特征怎样变成视觉。球也走出了屏幕，比如在法国为客户 Alan 做的户外广告、在伦敦一个主要广场按地铁线路颜色做的投放、巴黎地铁里的广告。

他的经验

  • 把机器学习当成主要创作媒介，会改变设计方式：除了结果本身，还要想结果是怎样生成的。
  • 制作成本降低后大家倾向于越来越快地发布，他们认为质量会成为品牌的优势，所以要像对待自己亲手做的作品一样对所有输出负责。
  • 手艺转移到了数据和规则上，每个环节都要守住品牌的设定。
  • 要部署 4,000 万次的流程必须按规模调试，先在小规模上多跑几轮。他说现在他设计的是产生这些球的条件，每个球不再由他亲手设计。

03. Harry Mellor（Hugging Face 机器学习工程师、vLLM 维护者）：一个 Transformers 模型如何在 vLLM 里加载

直播位置 1:08:42–1:31:05 · 英文原题 How a Transformers Model Loads in vLLM

Harry 是 Hugging Face 的机器学习工程师，也是 vLLM 的维护者。他讲 Hugging Face Transformers 库里写的模型代码怎样直接在 vLLM 里运行，而且速度和 vLLM 里专门实现的模型一样快。

背景

vLLM 是开源的 LLM 推理引擎，出自 UC Berkeley Sky Lab，现在是 PyTorch 基金会项目。它的主要能力：PagedAttention，高效管理 KV Cache（推理时缓存前面 token 的注意力中间结果，避免重复计算）；连续批处理（Continuous Batching），请求一到就处理，不用等下一批开始；快速算子；多种并行方式扩展；可移植，能在各种硬件和环境上跑；支持数百个模型，既有专门实现，也有 Transformers 建模后端。

Transformers 建模后端让模型定义、配置和权重都来自 Transformers，运行时和性能关键模块来自 vLLM。他说用它有三个理由：已经在用 Transformers 生态，不想为每个推理引擎重写一遍模型（vLLM 和 SGLang 都有这种后端）；做强化学习（RL）时，以前训练用 Transformers、生成 rollout 用 vLLM，两套实现可能有偏差，现在训练和推理可以用同一份代码；有些模型只能这样跑，目前有 14 种架构官方只通过这个后端支持，而且在增加。

启动和选类

他用 Qwen3-VL 的 MoE（混合专家，每个 token 只激活部分“专家”子网络）模型做例子。这个模型在 vLLM 里有专门实现，所以启动参数里要强制使用 Transformers 后端。他故意用了一个不推荐但可行的并行方案，8 块 GPU 上同时开张量并行、流水线并行、数据并行和专家并行，还给多模态编码器打开了 torch.compile。他说因为后端是通用的，只要 Transformers 代码里的多模态编码器能编译，开这个参数就能用。

第一次从 vLLM 跨到 Transformers 是读配置：模型是什么、什么形状、用什么量化方案。然后根据配置选后端类：配置里同时有文字和视觉配置，判定为多模态；专家数大于零，判定为 MoE；默认是因果语言模型（ForCausalLM），除非指定做池化任务。于是选中 TransformersMultiModalMoEForCausalLM 一类的类。为了避免一堆重复代码和维护难题，这些类都由 mixin 组合：MoE mixin 提供专家并行和专家负载均衡所需的协议；多模态 mixin 负责视觉编码、编码缓存、M-RoPE（多模态旋转位置编码），并把视觉嵌入合并进文字嵌入后再交给 Transformers；因果 mixin 负责 LM Head 和 logits 计算；最底下的基类做大部分工作，包括权重加载、权重映射和各种提速改造，并实现量化、LoRA、流水线并行、EAGLE 和 EAGLE-3 等协议。

实例化时做了什么

  • 先向 Transformers 的注意力注册表登记两个 vLLM 注意力“垫片”（shim），一个普通注意力，一个 MLA 注意力；再修改配置，让前向时选中垫片，不再用 FlashAttention、FlexAttention 等模型声称支持的选项。
  • 给语言模型加 torch.compile 装饰，按启动参数也给视觉塔加上，告诉 vLLM 两者可以各自作为完整计算图编译，不让 torch.compile 自己去猜。
  • 在 meta 设备上用 AutoModel.from_config 实例化。AutoModel 只加载 Transformers 说的基础模型（语言主干和视觉塔，不含 LM Head）。
  • 建立 HF 到 vLLM 的权重映射器，说明检查点里的权重名怎样对应到新的 Python 类。Transformers 自带一些映射，比如从旧式 MoE 改为融合式 MoE 的；后续改造过程中会不断往里加。
  • 删掉当前流水线阶段用不到的层。例子里是 rank 0，删掉后半层和最后的 LayerNorm。

递归替换

大部分提速工作在递归替换里完成。MoE 模型分两轮。第一轮处理 MoE：这个模型走“内部路由”，用 torch.fx 探测稀疏 MoE 块的结构，如果完全能由 vLLM 的 MoE runner 表示，就整体替换：专家换成 MoE runner，路由器换成门控线性层传给 runner。这样能用一体化的路由和专家算子，如果有共享专家还能异步计算。

第二轮是基类对基础模型的所有子模块做深度优先遍历，逐层替换：

  • 先遍历视觉模型，把能替换的层换掉。vLLM 的并行能力都内置在它的层里，换成 vLLM 的线性层和专家层，就获得了张量并行、专家并行等。
  • 替换词表并行嵌入，只替换 torch 的 nn.Embedding 模块，像 Gemma 那样在嵌入时做缩放的逻辑保留不动，vLLM 不用写特例。
  • QKV 融合器：用 torch.fx 找到 Q、K、V 和输出投影，换成 vLLM 的 QKVParallelLinear 和对应的 RowParallelLinear。探测用 torch.fx，实际修改用 Python 的模块操作，此时还没有编译任何东西。
  • 替换 RMSNorm。他说它看着简单，换起来意外地难，但必须换，因为 vLLM 的全局编译 pass 是靠识别自己的模块来做算子融合的。
  • 创建 vLLM 的注意力实例，从而用上 vLLM 的 KV Cache，以及卸载、节点间的 Prefill/Decode 分离、KV Cache 复用等能力，不需要 Transformers 里的 KV Cache 实现。
  • 把还没动过的模块移到设备上（这个例子里只有视觉模型的两个 norm），最后确保 Transformers 要求保持 FP32 的部分仍是 FP32，即使模型其余部分是 FP8。

前向传播的两个接缝

请求经 vLLM 调度到达基类的 forward，这是第二次跳回 Transformers：直接调用原始 Qwen3-VL MoE 类的 forward，传入 inputs_embeds（多模态模型由 vLLM 预先算好视觉部分并插入文字嵌入，一次传入），显式关闭 Transformers 的 KV Cache（由 vLLM 的注意力模块管理），位置 ID 照传，M-RoPE 模型在多模态 mixin 里稍作修改。

前向过程中有两处性能关键的地方回到 vLLM。一是注意力：Transformers 原生类查注册表，选中预先登记的 vLLM 垫片，进入 vLLM 后做少量形状变换，选用当前设备支持的注意力算子，通过注意力上下文拿到 KV Cache，算完把结果交还 Transformers。二是内部路由的 MoE：整个块的 forward 就是 runner 的 forward，在 vLLM 里做门控、取 top-k、执行专家计算，再把结果交还。Transformers 模型跑完后，logits 计算、LM Head 和采样都由 vLLM 完成。他说 Transformers 在这里提供的是模型的计算图结构，实际执行的模块都已是 vLLM 的。

没用到的功能

  • 外部路由：MoE 块不符合预设结构时，只替换专家本身。大部分计算在专家里，性能大头保住了，路由部分可以随意写。
  • 共享专家：内部路由下会被纳入 MoE runner，按配置用比外部路由更高效的方式计算。
  • LoRA、EAGLE、EAGLE-3 取决于检查点和请求。
  • 多种注意力：BERT 这类仅编码器注意力（支持仅编码器模型，不支持编码器-解码器模型）；Gemma 里全注意力和滑动窗口注意力交替的形式；MLA 注意力通过单独的融合器支持，能拿到 KV Cache 压缩的好处，以前加载 MLA 模型时只能填充成全注意力。
  • 池化和分类任务：可以用 LM Head 建分类头，或直接返回模型末端的原始嵌入。

05. Hervé Bredin（pyannoteAI 联合创始人、首席科学官）：为语音 AI 重建流式说话人分离模型

直播位置 2:49:17–3:11:27 · 英文原题 Rebuilding a Streaming Model for Voice AI

Hervé 职业生涯大部分时间是学术研究者，两年前和别人创办了 pyannoteAI，过去 15 年主要研究说话人分离（Speaker Diarization），也就是回答“谁在什么时候说话”。

说话人分离是什么

输入是多人对话的录音，输出是关于它的元数据，分几步：

  • 语音活动检测（Voice Activity Detection）：找出有人说话和没人说话的部分。
  • 分段（Segmentation）：把很长的语音区域切成单个说话人的片段，包括说话人切换检测和重叠语音检测。重叠里常有很短的“附和”（Back Channel），比如“嗯”“好”“对”。他说这些事件对语音 Agent 理解对话很重要，光有文字不够，知道谁打断了谁、谁在附和，能提供更多信息。
  • 说话人分离：把每段话分配给对应的说话人。难在事先不知道有几个人，也不知道他们是谁，必须泛化到训练集里从未出现的人。

应用场景里，“谁说的”和“说了什么”同样重要：视频配音需要知道原片里每句话是谁说的，才能把正确的克隆声音放到正确的人身上；会议记录在混合会议里尤其需要，几个人共用一个会议室时只有一路音频；播客分析可以跨节目追踪某位嘉宾或主持人。他们的开源工具包 pyannote.audio 在 Hugging Face 上平均每月下载 1,000 万次，三行代码就能从 Hugging Face 下载开源模型 community-1，对录音跑完分离流程，遍历结果拿到每段的起止时间和说话人标签。

为什么要实时

语音 Agent 通常只有一个人在和它说话，用不上说话人分离。但他说 Agent 很快会旁听会议，比如实时提醒某人打断别人太多次或说得太多；家里有了机器人之后，要回答孩子还是大人，也得知道谁是谁。

批处理版本怎样工作

以一小时录音为例，community-1 先用滑动窗口把录音切成 20 到 30 秒、彼此有重叠的块，第一个神经网络对每块单独做分离，输出一个“时间 × 说话人”的 0/1 矩阵，表示每个人什么时候在说话。分块的原因是每块里的说话人数有限，学习任务更容易、更稳。问题是同一个人在不同块里可能有不同标签，所以第二步用说话人嵌入：另一个神经网络把每段话映射到高维空间，同一人的片段靠近，不同人的远离，再在这个空间里聚类，把各块的结果拼起来。

两步改成流式

第一步是把全局聚类改成增量聚类。流式时看不到未来，聚类算法只有有限的视野，他放的模拟动画里算法要过一阵才意识到有两个人，中途会犯错，最后才纠正。这个方法实现在开源工具包 diart 里，作者是他们的 CTO Juan Manuel Coria（字幕作 Ka）。效果是分离错误率比批处理略高，延迟约 5 秒，因为块之间的步长约 5 秒。

第二步是把分块分段改成“因果分段”（Causal Segmentation），不等整块到齐就处理。以说话人切换检测为例：批处理时可以在整段对话上滑窗，比较左右两边的差异，在切换处得到清晰的峰值；流式时看不到未来，模型需要在当前时刻之后再等一小段时间才有足够把握判断是否换人，这段叫“前瞻”（Look-ahead），是去不掉的延迟。研究团队用比分块模型大得多的模型和一些损失函数上的改进（他说细节可以会后聊），做到了和批处理同等的准确率，延迟 400 毫秒。

400 毫秒里有什么

  • 客户端把音频切成 100 毫秒的块，等一块凑齐就有 100 毫秒延迟。他说这部分常常不被算进别人公布的数字里。
  • 用 Cloudflare Durable Objects 把块发到最近的 Cloudflare 服务器，平均约 20 毫秒，取决于客户端位置。
  • 服务器把许多路音频流的块打包成批，发到 GPU 上的模型。以批大小 32 为例，推理约 50 毫秒。
  • 200 毫秒的前瞻：模型在时刻 t 预测的是 200 毫秒之前发生了什么。
  • 说话人嵌入提取和聚类完全异步并行，不增加预测延迟，记为 0 毫秒。
  • 返回约 5 毫秒，再用 Cloudflare 里存的状态把各段拼起来、序列化后发回客户端。

他把这些归成三类延迟：网络延迟，平均约 50 毫秒，取决于客户端；推理延迟，批越大越慢但单路成本越低，这里是成本和延迟的取舍；算法延迟，占大头，是准确率和延迟的取舍，前瞻越长预测越准。缩小块大小能降延迟，但块变多会推高推理开销，取舍更难。

演示和结论

他请联合创始人（字幕作 Vanson）上台对话，两支麦克风只是摆设，实际由他的笔记本电脑收音。两人聊天、故意抢话，屏幕上实时标出说话人；联合创始人说通常约 20% 的语音是重叠的。主持人在台下插了一句话，系统立刻识别出一个新的说话人 02。

他的三点结论：批处理和实时分离输入输出相同，但约束完全不同，是两个不同的机器学习问题；延迟不是一个数字，说话人分离里最大的延迟来自算法本身；延迟、准确率和成本之间有多种取舍方式。

06. 炉边对谈：Yann Léger（Mistral 计算副总裁）与 Adolf（NVIDIA 高级解决方案架构经理），下一代 AI 背后的基础设施

直播位置 4:50:58–5:17:07

午休后的炉边对谈由主持人提问。嘉宾是 Mistral 计算副总裁 Yann Léger，和 NVIDIA 的高级解决方案架构经理 Adolf（字幕里姓氏作 Hall，无法确认拼写）。Yann 去年作为 Koyeb 的代表在这里演讲并承办了大会，之后公司被 Mistral 收购，他说 AI 时间里一年像过了很久。

过去一年变了什么

Yann 说这两年他一直在讲 AI 基础设施，去年重点是沙箱（Sandbox，给 Agent 运行代码的隔离环境），认为它正在形成一个新的基础设施类别，现在已经在实际发生：那时 Agent 时代刚开始，如今大量软件由 Agent 编写，Agent 工作流渗透很深。GPU 仍是核心，但 CPU 也加入进来，这是和前几年的主要区别。Mistral 仍在训练前沿模型，同时做大规模推理，Agent 进一步推高了推理消耗，技术栈更复杂。

Adolf 说以前谈的是计算、网络和存储，现在 Agent 负载占主导，人们常常忘了问 Agent 的工作负载在哪里执行，这是 CPU 的问题。模型架构方面，MoE 对通信有独特要求，影响下一轮芯片和基础设施设计。新模态方面，他说业界已经用完了世界上的书，很快会用完所有电影和多模态数据，但这不是终点，机器人领域需要反馈，提供反馈就要靠仿真，这会带来新的挑战。

硬件节奏和训练推理的融合

主持人提到 NVIDIA 的 Rubin 已全面量产，号称效率提高 10 倍、GPU 用量减少到四分之一，问工程师该怎样跟上。Adolf 说整个行业都在学习，他加入 NVIDIA 时是 Pascal 和 Volta 架构，大约七八年前开始的技术路线一直延续到今天；软件和硬件同步演进，要用上新硬件得通过软件。他观察到训练和推理的基础设施正在合流，原因是经济上的：分成固定的池子，每个池子都有浪费。

Yann 同意，并补充：训练集群需要最高性能和最新硬件，推理负载更宽容，可以用上一代硬件。所以设计物理基础设施时要考虑用途会变，一个集群可能前两年用于训练、第三四年用于推理，更理想的是动态地把训练集群重新分配给推理，这主要靠编排软件。模型大小差别也很大，训练 1 万亿参数和 80 亿参数的模型需要的基础设施不一样。长期看他认为会走向一个统一的资源池，在不同训练和推理任务之间重新分配。

NVL72 和机架级计算

Adolf 解释 NVL72：他刚入行时花 150 美元买块 GPU 就能参与 AI，现在规模大到 Mistral 最小的问题也放不进一台服务器。多个部件要经济、高效地协同，通信必须很快，所以 NVIDIA 设计了 NVL72，一个机架里的系统，内部互联比任何基于 TCP/IP 的方式都紧密得多，他说这是目前高度并行训练最经济的方式。主持人问机架是否成了新的服务器，他引用 NVIDIA 的说法“数据中心就是计算机”，并说 NVL72 本身是一个分配单元，可以切开用，但会离开这个系统的最佳点，所以说计算单位从单机上升到机架是对的。

Yann 说 Mistral 训练前沿模型用最新硬件，带来显著的效率提升，要留在前沿就还需要更多算力。他们不只部署 NVL72，训练用高性能互联的系统，也有专门为推理部署的不同配置。AI 浪潮已经持续好几年，各代硬件并存，基础设施越来越异构，形成了有点像 CPU 那样的长期轮换周期，必须应对异构硬件。

推理经济和“智能”怎么量化

主持人问 NVIDIA 用每秒每美元每瓦的 token 数衡量“AI 工厂”，推理收入什么时候能撑起这轮建设。Adolf 说经济规律不会变，过去有用旧训练系统跑推理的做法，但推理需求正在暴涨，他自己一直在用，已经不按传统方式搜索了，所以推理从第一天就要考虑。Yann 说以前确实担心推理需求起不来，但过去一年 Agent 工作流兴起，推理起来了，比如软件工程团队在 AI 工具上花多少钱已经是常见话题；业内有“token 最大化”（Token Maxing）的讨论，但现实是它已经是每个软件工程师的日常工具，过去的投资正在产生收入。主持人说 NVIDIA 不太相信 token 最大化，更相信“结果最大化”。

被问到怎样量化智能，Yann 说这取决于业务结果，差异极大，很少的 token 用对了地方能产生巨大价值；有些流程按产出看用了不正常数量的 token，还有很多优化空间。他说价值不只在模型和训练，还在整个 Harness（模型外面那层负责调用工具、管理上下文、编排流程的程序）以及怎样用好 token；基础设施层只是提供 token、优化每一层，价值主要被上层捕获。

推理模型带来的压力

主持人问推理型 Agent 产生大量 token，栈里哪一部分最没准备好。Adolf 说他喜欢推理模型，但代价是更多 token，意味着需要内存保存长上下文、需要缓存来复用对话。他认为现在正进入分布式缓存越来越重要的阶段，有明确迹象表明推理在走向分布式服务，缓存是其中的重要部分，明年再坐在这里时大家会重新评估缓存的价值。

快问快答

  • 五年内会不会有在欧洲 AI 工厂训练的前沿模型？Yann 说 Mistral 正在做，明年上线 200 兆瓦算力，到 2030 年 1 吉瓦，很多在欧洲，现在的 Mistral 模型已经在自己的基础设施上训练，所以五年内肯定会有。
  • 2026 年最被高估的基础设施趋势？Adolf 答：什么都“自愈”。
  • 最被低估的？Yann 说要看哪一层，在纯基础设施层面，是让基础设施运转起来的软件。

07. Charles Frye（Modal 推理工程）：低延迟推理工程手册

直播位置 5:17:07–5:43:04 · 英文原题 The Low-Latency Inference Engineering Playbook

Charles 在基础设施平台 Modal 做推理工程，讲他们总结的低延迟 LLM 推理优化方法，以及为什么低延迟重要。

为什么低延迟重要

他从最近发布、当天“每五分钟就被提一次”的 Jev（字幕拼法）说起：一个决策模型，即通用的零样本分类器，跑得很快。有人在 Twitter 上做了输入一个词就生成配色板的演示，作者说它又便宜又快，像是新 UX 范式的一次跃进。长期做 NLP 的人反而奇怪大家为什么这么兴奋，他的解释是：这种智能一直都有，现在同时变便宜又变快，就打开了新用途。如果不用担心撞上用量上限、为了让一个图标转起来花 1,000 美元，或者等 30 分钟，机会就多了。他补了一句“企业赞助声明”：Jev 运行在 Modal 上。

他把基于序列模型的应用分成三类，各有不同的性能指标：聊天机器人和 Agent 看每个用户每秒拿到多少 token；决策模型看单次延迟；数据处理类（比如 Reducto 处理成千上万份 PDF）看每美元能处理多少百万甚至十亿 token，属于高延迟推理，这次先不讲。他们给 Moonshot AI 的 Kimi 模型做推理服务时，相比照着 SGLang 或 vLLM 官方指南直接部署，经过负载分析、配置调优和一些性能工程，每 GPU 每分钟的 token 数提高约 5.5 倍，单用户速度快约 3 倍，从每秒 130 多个 token 提到约 400 个，通过 OpenRouter 等平台大规模提供。低延迟方面，他们和 Decagon 合作，为其语音 Agent 管线里的决策环节做到尽可能低的延迟。

第一步：理解负载和硬件

负载告诉你要做什么，硬件决定什么容易、什么难。他先解释推理过程：输入（他用《沙丘》里橙色天主教圣经的诫命“你不可制造模仿人类心智的机器”做例子）先在预填充（Prefill）阶段算出模型内部表示，生成第一个 token，再在解码（Decode）阶段一个个循环生成后续 token，中间表示存进 KV Cache 以便复用。Agent 负载里，用户输入、模型回复、工具调用结果一轮轮叠加，每次请求都带着之前的全部上下文，所以 KV Cache 对低延迟 Agent 推理很重要；Jev 这类负载请求结构不同，KV Cache 没那么关键。他认为“用户、模型和外部系统迭代地共同构建上下文”这种形态会长期存在，即使以后模型装进家用机器人、输入输出视频，也大概还是这样。

硬件方面的好消息是，追求高交互性、低延迟时一般不超过 8 块数据中心 GPU。他引用 SemiAnalysis 的 InferenceMAX 基准：要最高单卡吞吐，需要 NVLink 域里 40、64 块 GPU 的大型机器；要最高单用户每秒 token，最优点用的是 4 或 8 块 GPU，运维上省事很多。

第二步：按顺序优化

顺序是：先拿大收益（推测解码、量化）；再做主机侧的中等规模优化，通常能提 50% 到 2 倍，做的事情越特殊，这部分收益越多；最后才是大家最兴奋的 GPU 算子优化。

推测解码（Speculative Decoding）：用一个便宜得多的模型先猜后面几个 token，再让大模型一次性并行验证。思路和处理器的推测执行一样，逐 token 运行的 LLM 有闲置算力，可以用来做可能被丢弃的工作。他说这经常带来 5 倍以上的提速，提速幅度和平均被接受的 token 数大致成线性关系，是 4 倍、8 倍这种整数倍，而性能工程里平常是为 5%、10% 拼命。针对具体负载训练推测模型（Speculator），让它学会目标模型在这类数据上的行为，可以从 3 倍提到 5、6 倍，他说这是“苦涩的教训”用在了性能工程上。小模型能猜中大模型，主要因为输出有大量结构：聊天模板里的特殊 token 可预测，用户的话往往在前文出现过，说了要读文件后能调用的工具就那么几个。目标模型在处理这些 token 时构建的丰富内部表示，现在的推测模型也会拿来用，它们不是从零开始的 n-gram 或独立小模型。他们投入最多、效果最好的推测架构是 DFlash（字幕作 Dlash），比一些模型自带的推测解码和基线都快不少。

量化（Quantization）：把权重或激活的浮点位宽从 16 位降到 8 位甚至 4 位，内存带宽需求线性下降，每秒浮点运算线性上升。他说这需要全栈协调：往下要看硬件是否支持，FP8 需要 H100 及以后，FP4 需要 B200 及以后；往上它会改变模型输出分布（推测解码不会），所以要回到应用层确认能力是否还够。他展示了 Modal 的 LLM Engineer's Almanac 里的可视化：一只鹦鹉图片的 4 位量化版本，前排能看出有点粗糙，后排和看手机的人大概看不出来。

主机侧优化：GPU 干活，但 CPU 负责协调，CPU 不能拖住 GPU，否则形成空泡（bubble）。他说写过事件循环的人都懂“不要阻塞快的那一方”。CUDA Graph 捕获可以把一次运行的所有算子录下来，之后一次性提交，省掉大量主机开销。他最喜欢的监控方法是看 GPU 功率和温度，GPU 达到峰值性能时基本受功率限制，离 100% 功率远就说明没用满；他展示了一张图，一个配置远低于 2,000 多瓦的功率上限。定位问题要用 Nsight Systems 或 PyTorch Profiler 看时间线。一个实际案例里，多块 GPU 都在跑 DeepGEMM，其中三块在等一块慢的，原因是 NUMA 区域没对齐，那块卡在错误的 CPU 插槽上。Python 层可以用 py-spy。他们的博客写过一个例子：把一个反复分配的操作改成一个缓存（其实就是一个 Python 字典，存 CUDA IPC 句柄），整体快了 10%。

扩容后的路由：单副本上测得的性能扩容后可能达不到，会出现看起来随机的长尾延迟，原因就在路由。对 Agent 负载影响尤其大，因为 KV Cache 命中和未命中可能是 500 毫秒和 30 秒的差别。他们在一次部署里发现，本应每个副本四五个并发请求，实际分布高度离散，解决办法是让路由器有状态，感知负载和 KV Cache 状态，长尾尖峰随之消失。

GPU 算子：一般算子已经接近硬件极限，架构变化不大，NVIDIA 等提供的现成算子很好，只剩几个百分点的空间，规模大时重要，起步时不用操心。底层工具是 Nsight Compute，可以看到汇编级别。但在用它之前，他建议先拿白板笔算一算：Tri Dao 和 Together 写 FlashAttention 4 的博客里，决定做什么的方法就是写下“进出速度”，有多少数据进来、要做多少运算、多快能送出去。他说理解硬件的这些基本参数，能少走弯路、少花冤枉钱。

当天发布：AI SQL 的高吞吐推理

他说本来不讲高吞吐，但有一项当天才发布的工作。AI SQL 指的是用 SQL 生成给 AI 的提示词（方向和“AI 写 SQL”相反）：比如想问“哪些客户可能买哪些产品”，可以写成一个关系连接，但对专有 API 跑，可能一下生成 800 万个请求，token 预算瞬间烧光。这类问题的优化空间在于结构：查询计划把要用的文档、它们怎样组合、会生成哪些提示词都写清楚了，而现有推理引擎只懂请求-响应或批量请求，不懂 SQL。他们和 CMU 的 Shreya Shankar（字幕作 Treya Shankar）合作，把数据库的查询规划和推理引擎结合，在他展示的那个查询上比基线 vLLM 快约 14 倍，单块 H100 上每分钟处理超过 10 亿 token，整个查询花约 2 美元，vLLM 要近 30 美元，用最小的 OpenAI 模型还要贵得多。项目开源，在 Full Stack Data Labs 的网站和 GitHub 上，Modal 博客有详细介绍。结尾他推荐了 Modal 的自动推理端点（auto endpoints）服务。

08. Dominic Pajak（Arm 高级总监）：Eyes Up，边缘 AI 的创新

Dominic 在 Arm 负责让新类别的设备落地上市。他说三件事同时在发生：能力不错的小型开放权重模型出得很快；能装这些模型的硬件到处都是；于是可以做出更懂用户意图的设备，带来以前没有的体验。Arm 的架构从高能效数据中心、汽车和机器人等实时安全关键的物理 AI，到几乎每一部智能手机、PC、工业物联网都有。

人机交互的倒转

他自称计算机史迷，还提到 Station F 所在的地址是 Parvis Alan Turing。过去 80 年，人和机器的接口从打孔卡、纸带到键盘、鼠标、触屏，每一代都更容易用，但始终是人把注意力交给设备，把想做的事转换成机器能懂的步骤输进去。AI 时代把这个关系倒过来了：机器能理解自然语言，把意图转成动作和工具调用。

边缘推理本身不新，CNN 做物体检测在工厂质检、停车位监控上跑了很多年；更近的是嵌入、LLM，以及刚刚变得可行的 Agent 应用（推理能力够强、能调用工具、能处理足够长的上下文，可以替用户自主行动）。他画了一张图：从 GPT-3.5 开始，同等能力被压缩进越来越小的模型，现在大约 10 亿参数就够，能在手机或手里的 Raspberry Pi 上跑。他承认基准不完美，MMLU 更是如此，但趋势会继续。推理能力也一样：4B 激活参数的模型（MoE 推动了这一点）在 GPQA Diamond 上已经超过 Claude 3.5 Sonnet 刚发布时的前沿成绩，那大约是一年半前。还有能在端侧以可用延迟做语音转文字的模型，做语音界面不用上云。

延迟目标应该以人的预期为准。他放了一项关于对话轮替间隔的人类学研究：间隔因文化和语言而异，日语回应快，丹麦语慢（他开玩笑说也许是动词在句尾的缘故），英语居中。

为什么放在边缘

  • 效率：很多人在看自己的 token 用量，想把一部分转到本地或本地部署的设备上。
  • 定制：可以用个人数据或组织的专有数据，留在内部。
  • 感知意图的设备一直在听、在看，很多人希望自己决定这些数据是否离开设备。

Reachy Mini 和社区

硬件创新者多年来用 Raspberry Pi、Arduino 这类模块拼出新设计，他认为再加上开放模型会有很大空间。他最喜欢的例子是 Hugging Face 旗下 Pollen Robotics 的 Reachy Mini（法国产品）。他参加了内测，去年圣诞节和儿子一起组装了一台。它用 Stewart 平台让头部做出表情，有一组舵机，里面有 Arm Cortex-M0，天线上有执行器，Wi-Fi 版用 Raspberry Pi Compute Module 4，可以在本机跑应用，也可以调用外部推理服务。它还有开源 SDK 和开发者社区。Arm 同事 Marco Domingo 做了一个应用：放在桌上，你一拿手机刷屏或分心，它就提醒你别刷了。这个应用得了奖，奖品是 NVIDIA GTC 圣何塞的 VIP 门票和一台 DGX Spark，用的还是 Dominic 那台 Reachy Mini。他说自己不嫉妒。这个应用现在在 Hugging Face 的 Reachy Mini 应用空间上。

端侧应用要在算力和内存的限制下拆分任务。视觉应用常见的做法是：运动检测触发物体检测，识别到感兴趣的东西再截取区域做图像嵌入，最后才调用 VLM，这些任务可能分配给设备上不同类型的处理器，甚至别的设备或数据中心。他自己内测时做的应用完全跑在 Raspberry Pi 5 上：你一说话，Reachy 就转头看你再回答，他说这种具身的反应比智能音箱响一声、亮个灯有感觉得多。为了延迟，他没用 LLM，改用嵌入做语义匹配再调用工具，能问天气、时间，本机用语音合成回答。Marco 的演示用他赢来的 DGX Spark 跑 Mistral 的 Ministral 3，本机做语音转文字、生成回答、语音合成，还能调用工具。视频里 Reachy 向全场打招呼，看了 Dominic 的参会证后说出他来自 Arm 并介绍了 Arm，还跳了一段舞。

意图经济和混合 AI

09. Yannis Psorakis（Cognition 工程副总裁）：用 Agentic Map-Reduce 处理大规模编码任务

直播位置 6:07:47–6:24:59 · 英文原题 Agentic Map-Reduce for Large-Scale Coding Tasks

Cognition 自称应用 AI 研究实验室，创始团队背景是 AI 研究和编程、数学竞赛，总部在旧金山，欧洲基地在伦敦，Yannis 就在伦敦。他们做 Devin，他说这是第一个云端 AI 编程 Agent，现在有本地和桌面等多种形态，也覆盖软件开发生命周期（SDLC）的多个环节。客户从高盛、花旗、桑坦德等系统重要性银行，到美国陆军、大型科技公司和快节奏的创业公司。

两类任务

局部任务：一次普通的 Agent 会话，比如实现一个功能、给某块代码补测试、优化数据库代理里某部分的查询。问题有边界，相关文件就那么一组，要么你直接指给 Agent，要么它很容易自己找到。

全代码库任务：可能跨多个仓库。比如安全扫描，单个模块各自的安全水平之外，更要紧的是它们在现实中怎样相互作用、串起来暴露漏洞。几个微服务单独看都只有低优先级漏洞，可以放进待办，串在一起可能构成严重攻击。又比如抽取公共逻辑，他们有客户代码库很大，想统一金融公式、计算方式或访问数据库的方式，这首先是搜索问题，还要理解各种变体的细节。这类任务只有看到整个代码库或整个部署后的应用，结果才可信。端到端测试和 SDLC 的质量关卡当然有，但目标是尽早发现。

单个 Agent 处理这类任务有三个难处：找工作本身是搜索问题，Agent 会花大量时间搜索、回溯、烧 token；上下文被污染，大量多样的内容争夺注意力；不知道何时该停。他承认没人会一句话就让 Agent“修复所有安全漏洞”，大家都会做某种编排，外层循环拆任务、定义 DAG（有向无环图），再跑内层循环。他要讲的是一个在效果和成本上都更好的框架，而且他们把它做成了产品里的一等功能。

Agentic Map-Reduce

MapReduce 是 Google 提出的分布式数据处理框架：比如统计分布式文件系统里每本书的词数，map 函数是无状态的纯函数，可以并行对每本书计数，reduce 步骤汇总结果。他们把它搬到 Agent 编程里，把“海量数据”换成“海量代码库”：

  • 规划：主 Agent 读取你的提示词、技能、仓库里已有的知识等，制定计划。
  • 选择器（Selector）：主 Agent 写出一组确定性的函数，运行后生成代码库的候选区域目录。
  • Map：对每个候选区域并行启动子 Agent，只看这一块，做分析。
  • Reduce：主 Agent 汇总各子 Agent 提炼后的结果，做去重、排序或更深入的综合分析。

以安全为例：你提供威胁模型和代码库的额外背景，预处理阶段写出确定性的搜索函数，找出安全相关区域，比如 API 边界、令牌签发和传递的地方、SQL 入口、代码执行入口。选择器运行后把代码库切成若干批或分片，每个子 Agent 在干净、有边界的上下文里调查并写报告。Reduce 阶段主 Agent 做整体推理：去重；按严重程度排序；最重要的是找链式漏洞，把多个低危发现组合起来评估是否构成严重问题。配上合适的 Harness，Devin 还能实际测试、模拟攻击路径，复现漏洞，也包括排除误报。他说他们把代码库看成一张引用关系的图，选择器找出鉴权区域、API 入口、SQL 入口，便宜且确定地跑完，再在每条窄路径上派出一个 Devin。复现很重要，因为不想只交一堆工单，安全扫描工具每次发版都会报出一大堆要处理的东西，他们要交的是针对确认漏洞的真实 PR。

成本和效果

他说可以跑很贵的 Agent，但在大代码库上最该想清楚的是怎样降低搜索成本、避免上下文污染和溢出。主 Agent 写确定性选择器、生成大量有边界的上下文，成本更低，召回率也比对比方案好。他们在一个 50 个漏洞的数据集上测试过，漏洞来自 GitHub，涵盖 Go、Python、Java 等多种语言（具体对比数字字幕里没有）。这个方法也能推广到其他全代码库任务，比如死代码检测和删除、把公共逻辑抽成中心库。他们从研究出发先用在安全上，正在把它做成产品的一等功能。最后他提到 Cognition 的其他研究方向：自研编程模型、模型 Harness、Agent 基础设施等（具体名称字幕不清），可以看他们的研究博客。

10. Matt Pocock（AI Hero，前 TypeScript 讲师）：解决 PR 瓶颈

直播位置 7:16:34–7:39:22 · 英文原题 Fixing the PR Bottleneck

主持人介绍 Matt 以前以“TypeScript 巫师”出名，在 Vercel 工作过，后来开始讲技能（Skills）和 AI。Matt 说没人评审的 PR 堆积是 AI 之前就有的老问题，AI 让它严重得多。他用自己的一套技能作为框架来讲，并发布了两个新技能。

软件工厂需要刹车

他说软件工厂是当天最热的词。他的定义是：发起工作的不再全是人，一部分由 Agent 和确定性代码触发，比如收到问题后用 Jev 这样的分类器判断，转成修复、复现，或直接通知人；接上 PlanetScale，慢查询报告触发另一条流水线。这些是油门，把更多代码推过工厂。只有油门会变成“垃圾炮”，产出一堆没法看、没法评审的低质量 PR。所以需要刹车，保证质量，防止代码库陷入熵增，因为代码就是 Agent 工作的环境，坏代码会生出更多坏代码。他说三道刹车反而能让你更快：

  • 自动检查：lint、测试、类型检查、代码质量指标，每次结果都一样。
  • 自动评审：Agent 看代码，发现测试没抓到的问题，看整体结构。
  • 人工评审。

目标是靠前两层让人工评审更快。第一原则是“阻止垃圾”，提交的代码质量越高，人需要干预的就越少。

自动检查会撒谎

自动检查便宜，只花 CPU，不花 token 和人力，测试发现 Agent 写的 bug 后修复花的 token 也值，所以可以大量叠加，他说大多数人用得不够多、不够有创意。但检查会撒谎，CI 全绿不等于可以合并，后两层就是“测谎仪”。他展示了几种“谎言”，都来自他自己 Agent 的真实代码：

  • 同义反复测试（Tautological Test）：测试只是重复实现。他说 Opus 5 特别爱写这种。代码里写了 X 帖子字数上限常量为 280，测试就断言这个常量等于 280。这类测试对内部结构过度敏感，改值会挂，改名也会挂。
  • 更离谱的例子：要测页面上视频区块出现在内容计划之后，测试没有渲染页面，直接把源文件读进内存，找两段文本的位置比先后。源代码格式一变测试就挂。
  • 不可能失败的测试：一个 useAudioBoost 函数内部用浏览器的 AudioContext API，测试把它整个打桩成假方法。AudioContext 在某些条件下会以复杂的方式报错，打桩后测试永远覆盖不到，线上就会出现测试抓不到的错误。

他说 AI 不是故意写坏测试，只是照指令写，写得太贴结构、没有真正执行代码。

用代码库设计让检查更难作弊

他之前在 AI Engineer 讲过“深模块”（Deep Module），出自 John Ousterhout 的《A Philosophy of Software Design》：用简单的接口隐藏复杂的实现。浅模块则是接口很大，每个函数做的事很少。深模块把更多实现藏在接口后面，测试只能打在接口上，对结构敏感的测试自然变少。你要做的是逼 Agent 通过那个小接口测试，不要伸手进实现细节。他有一个技能，能在再烂的 vibe coding 代码库上找出加深模块的机会，生成一份 HTML 文档，列出每处改动的前后对比（减少重复、做出可测试的深模块），再去实现。配套还有一个“代码库设计”技能，统一团队描述模块的语言，因为查怎样组织代码库，会看到 20 种方法、全都叫 DDD。里面定义了局部性（Locality，改动能否集中在一处而不波及其他模块）、杠杆（Leverage，调用方调用一个简单函数就能得到很多价值）和接缝（Seam），他说这些对代码库和 Agent 都有好处。

编码规范不要放进实现 Agent

他认为大多数人在这里做错了。实现 Agent 的一个上下文窗口里要探索代码、修改文件、跑检查和调试，已经超载，再塞编码规范只会更差。他的做法是一个代码评审技能：接收 diff，读取仓库里你自己写的 CODING_STANDARDS.md，检查代码是否符合，并且在子 Agent 里跑，有独立的上下文窗口和预算。评审 Agent 要做一些探索来理解上下文，但不用实现和调试，所以“实现超载、评审欠载”，可以放进大量规范。他承认这让人不舒服，大家都想一次写出好代码，但他的两步法是：实现让代码能跑，评审让代码变好，类似“红-绿-重构”，一个上下文做红绿，另一个做重构。所以编码规范不要放在 AGENTS.md 这种全局位置，会淹没实现 Agent，放在 CODING_STANDARDS.md 里只给评审 Agent 读。

很多人说用第三方服务做自动评审，比如 Cursor Bugbot、CodeRabbit。他试过做通用的代码评审技能，发现太通用就满是和你无关的误报，太具体（比如专找 TypeScript 问题）别人又用不了。所以他建议不要外包自动评审，自己建、逐步积累编码规范、团队共享，没人看的文档正好放这里。还有一点：评审 Agent 不应该只在 PR 上写评论，那会给人工评审增加工作量，读一堆冗长评论再决定改不改。默认应该是直接提交修复，有疑问的才评论，这样人看到的是已经改好的版本。

给人看的 PR：新的 PR 技能

他发布了一个还在完善中的 PR 技能，做法是把大家最好的点子都拿来。原则一：评审的重要性不一样。用 AWS 的说法区分单向门和双向门：大多数 PR 是双向门，合并后随时能撤回，这是软件工程师比土木工程师幸运的地方；但一个简单改动也可能意外给 6 万人群发邮件，涉及昂贵的迁移或数据丢失，这些是单向门，要狠狠地审。再加上影响范围（Blast Radius）：出错时会坏到什么程度。他的 PR 底部会有一个“合并风险”摘要，比如“双向门，影响范围局部”，他就知道可以轻看。

原则二：让人尽快看懂 PR 在做什么。他试了很多办法，最好的是伪代码和图。他特别感谢 HumanLayer 技能仓库里 Dex Horthy（字幕作 Dex Holley）写的 show-me 技能，它少用文字、多用图和示意图，有 Mermaid 图、UML 时序图，也有很简单的图，比如一眼看出 CLI 新增了一个命令和两个参数。他说这种改变的效果难以夸大。

评审的是生产代码的系统：retro 技能

原则三：现在大家围绕同一套技能文件和引导文件协作，一起为 Agent 搭环境，所以产出代码的流程和代码同样重要，人工评审时评的也是生成代码的系统。理想是同一条评论永远不写第二次。为此他发布了新技能 retro（retrospective，复盘）：可以复盘一次 Agent 会话、一个 PR 加会话，或者过去一周所有 PR 和评审，然后建议新增的自动检查和编码规范，让下一次人工评审质量更高、工作更少。它还会看导航指针（Agent 找信息容不容易，能否在 AGENTS.md 里加个指引）、工具经济性（会话里用的工具能否更省 token）、臃肿（引导文件和技能是否过于冗长，能否整理）。他说这些问题从外部很难排查，它能抓到的东西多得惊人。

他的结论：用自动检查和自动评审层层把关，让人工评审尽量轻松、简单，甚至可选；双向门不必每个都审，单向门必须审。技能在 aihero.dev/skills，1.3 版本当周发布。

11. Maarten Grootendorst（Google DeepMind）：Gemma 4 的效率

直播位置 7:41:50–8:02:04 · 英文原题 The Efficiency of Gemma 4

投影一开始没有画面，修好后 Maarten 开讲。他说开放模型一发布就会受约束，因为它们跑在手机和笔记本上，不是数据中心里，所以效率是发布开放模型的核心。他从知识、大小、速度、复杂度和架构五个角度讲 Gemma 4 的设计。

知识：逐层嵌入（Per-Layer Embeddings）

Gemma 4 的小模型 E2B 和 E4B 大量使用逐层嵌入。MoE 模型名字里的 A 表示激活参数，这里的 E 表示 effective（有效参数）。Gemma 4 的一般架构有局部注意力、全局注意力、分组查询注意力（GQA）和若干归一化层，小模型在最后多了逐层嵌入：和普通 token 嵌入类似，但每一层都有一份，同一个 token“hi”在第 1 层、第 4 层、第 10 层的嵌入不同，每层加进去，模型可以按上下文决定侧重嵌入的哪些方面。它是一张关于 token 的查找表，不用放在显存或内存里，可以放在任何存储上，推理时只加载用到的 token，有点像 RAG（检索增强生成，回答前先从外部检索相关资料）的行为。这些表有数十亿参数，但推理时不参与计算，所以叫“有效”参数。他说把知识和模型能力分开，在开放模型里越来越明显。

大小：量化感知训练和移动端量化方案

量化感知训练（Quantization-Aware Training）在训练时就考虑降低精度，尽量保住能力。他们更进一步，给两个小模型设计了专门的移动端量化方案，因为小模型再压缩容易掉性能：token 嵌入层压到 2 位仍保留大部分能力；全局注意力用 4 位，大小和能力的平衡点；局部注意力用更高一点的精度，尤其对 KV Cache 有帮助；前馈网络 4 位；逐层嵌入 2 位，它们也在补偿 token 嵌入的低精度。他说在 20 亿、40 亿参数这个尺度，追求效率意味着大量针对具体模型的定制。

速度：多 token 预测的推测解码

用一个小的草稿模型先提议几个 token，大的目标模型只需一次前向就验证全部，省去逐个生成。Gemma 4 的做法是共享 KV Cache：目标模型对查询做一次前向，生成 KV Cache 并交给小模型，小模型接着生成一个、三个甚至八个 token，目标模型一次看完，比如只接受前两个，再顺手补一个自己的 token，相当于用约一个 token 的成本生成三个。代价是多了一个小模型，提速幅度随用例差别很大：代码这类结构化任务里 token 好猜，创意任务里小模型很难猜中、被拒得更多。他说好在结构化任务越来越多。

复杂度：去掉编码器的模型

闭源模型多复杂对用户无所谓，开放模型要让人容易理解、使用和微调。Gemma 4 系列很多模型有音频编码器和图像编码器，效果好，也是行业标配，但占不少参数，会拉长首 token 时间（TTFT），微调时还要多考虑一个部件。他们发布的无编码器模型（Encoder-free）把处理多模态输入的工作交给语言模型本身。音频：输入是一串振幅值，切块成音频 token 序列，线性投影到模型的维度，参数只在这个投影里，原来音频编码器做的上下文处理全由 LLM 来做。图像有二维空间信息，不能简单切块排成序列，他说这样模型处理不好，所以给每个图像块加上位置信息再投影，比如第 4 块在很宽的图和很高的图里含义不同。好处是首 token 时间更短，能力集中在模型里，省下编码器的参数。他说三五亿参数在千亿级模型面前不大，但在 20 亿或 120 亿的模型上差别很大。

架构：扩散 Gemma

普通 LLM 是访存受限（Memory-bound）的，他问如果反过来做成计算受限（Compute-bound）会怎样，他的答案是放弃自回归，改用扩散（Diffusion）。扩散 Gemma 里有一个“编码器”，其实仍是带因果注意力的解码器，是微调过的 Gemma 4 模型，叫编码器是因为它负责处理提示词，生成 KV Cache。生成时从一块约 256 个 token 的噪声画布开始，不是从第一个 token 逐个往后写，由去噪器迭代地填入有把握的 token。去噪器和编码器是同一个模型、同一套权重（Gemma 4 26B），区别是去噪模式下用双向注意力，因为要同时更新画布开头和结尾。每一步去噪器读取编码器的 KV Cache，预测画布上各位置的 token，把有把握的接受，没把握的重新加噪，进入下一步。他们发现只这样做不够好，因为第一步虽然有些 token 没被接受，模型已经有了方向，所以加了一个跳连，即自条件（Self-conditioning），把上一步的 logits 喂给下一步的输入。通常约八步（有时多有时少）得到 256 个 token，在大 GPU 上为单个用户服务时速度很快。

他说没想到的是最近一周爆火的 Jev（字幕拼法），一个通用的决策模型，也就是基础分类器，恰好很适合扩散。做法：描述情境，比如“打印机着火了”，用编码器生成 KV Cache；画布不是全噪声，预先填好和候选动作相关的 token，比如“撤离”或“打电话”，这些不变，只让模型填剩下的空位，对这两个选项给出概率。只需一步去噪，技术上可以多步，但要快速决策一步就够。他说没人微调过这个模型，只是对它加了限制，这也说明限制某些用法可以打开没想到的用途。

他最后说效率是给社区的：模型跑在手机、笔记本还是大 GPU 上都一样要有用，而社区也会回馈，比如用一个本不是为此设计的模型做出决策模型。模型再好，跑不起来就没意义，端侧的小模型必须既有能力又快。

12. Olivier Teboul（Gradium CTO、联合创始人）：对话式 AI 缺失的几层

直播位置 8:07:11–8:30:14 · 英文原题 The Missing Layers of Conversational AI

Gradium 成立一年，训练和提供语音模型：语音转文字（STT）、文字转语音（TTS）和语音到语音（S2S）。它的前身是 Kyutai（字幕作 QAI），2023 年在巴黎成立的开放科学实验室，资金充足、自由度高，做出了 Moshi 等成果。研究成果反响很大，他们觉得要让研究走得更远就得做成产品，于是成立 Gradium 衔接研究和产品。

语音 Agent 简史

他把 LLM 之前称为语音 Agent 的“史前时代”，以 iPhone 上的 Siri 为代表。他说那时感觉像离 AGI 最近的一刻，其实 Siri 是一个分六层的工程产品：语音识别；把文字送进一组分类器，判断意图、对象、主语等；对话管理器；调用天气、日历等 API；他猜最依赖模板和正则的文字生成；TTS 读出来。LLM 出现后，自然语言理解和模板都不需要了，对话管理器在现代语音 Agent 里仍然存在；LLM 变强后能连接数据库、网页搜索、MCP、工具调用、RAG，成为语音 Agent。他说 99% 的语音 Agent 是级联模型：ASR（语音识别）、LLM、TTS 三个独立训练的模块接起来。延伸做法是用一个大模型完成全部，叫语音到语音，模型自己知道什么时候说、什么时候听，不用另外处理轮替。Gradium 做 TTS、STT、端侧 TTS、语音到语音翻译、声音设计（按口音、性别、音高等定制声音），语音到语音模型即将推出。

缺了什么

他说有人会让你相信这张图已经完整，其实没有。语音 AI 放到真实环境里：多人说话会让 Agent 混乱；噪音会让它混乱；长对话会丢上下文；还有真正的全球规模，他说的是像当年 Siri 那样，每个人都能对着手机说话而不打字。背后的挑战里他挑了两个讲：快和规模，要从模型设计、推理优化到服务基础设施一开始就考虑。

怎样设计语音到语音模型

需求是：随对话推进不断接收语音，尽快开始回话，语音进、语音出。LLM 满足三条里的两条，只是它进出都是文字。他解释了自回归：给定上下文“Gradium 是一家 AI 模型公司，总部在……”，模型给每个候选词一个概率，预测出的词加入上下文，再预测下一个，逐步生成整句。音频也是序列，问题在维度：这句话九个词，读出来约 3 秒，按普通音质每秒 24,000 个采样，就是 72,000 个数值，序列长了约一万倍，而 Transformer 的自注意力是平方复杂度，注意力矩阵大约一亿倍，算不动。

第一个技巧是神经编解码器（Neural Codec）：训练一个模型把音频压缩成 token，从 24 kHz 降到 12.5 Hz，约两千倍，序列长度就可以处理了，最后再解码回音频。但对话不是对讲机，不是你一句我一句，双方会同时说话，所以他们发明了 LLM 里没有的多流层级 Transformer：上下文有两条时间线，一条是我说的，一条是你说的，两条互相关注来预测下一步，模型可以同时听和说。他放了一段 2024 年首席科学官 Alex 和模型的对话录音，问去天狼星 22 的航线要多久，模型回答约五个月，接话自然、几乎没有延迟。

他说 2024 年 Kyutai 就有这项技术，但没有商用。缺的那层是：一个小模型同时负责听、说和语言处理，任务太多，用一会儿就能感觉到能力有限；更严重的是它与外界隔绝，不能调用外部系统，不能在生产里帮你预约之类，只是个玩具。所以语音到语音现在的大挑战是和工具调用无缝结合。

怎样服务到全世界

以 TTS 为例，客户端发文字，服务器返回音频，接进语音 Agent 时必须实时，即全程 300 毫秒以内，否则对话很别扭。这一趟要过三层：传输层；产品层（请求是否合法、有没有权限和额度、要的声音是否存在、在哪里，补全或拒绝请求）；计算层。

延迟：服务器在欧洲、客户在美国，横跨大西洋往返就浪费约 100 毫秒，预算的三分之一。办法是到处部署服务器，更贵，而且从无复制的系统变成分布式系统，信息需要同步。为了快要加缓存，单个缓存的失效问题本来就难，现在许多缓存要一起同步，否则你刚建的 API 密钥到了加州节点还不认识。他说这是用工程复杂度换延迟，可以处理，但要心里有数。

GPU：一年前他们就认定不可能在 300 毫秒内向云厂商要一块新 GPU、拉权重、拉 Docker 镜像、预热，最快也要几分钟，所以必须预测负载提前准备。现在更糟的是 GPU 太稀缺，可能第二天都拿不到，区域里根本没有。缓解办法同样是增加复杂度：多找几家供应商；让模型能跑在不同架构和不同芯片厂商上，不只 NVIDIA 或 H100。突发流量有两种对策：利用多个集群，把流量转到最近的另一个；或者在高峰时调大批大小，用一点延迟换吞吐，峰值过后再调小。

他展示了当周在做的新 TTS 测试版模型和几家服务商的首段音频延迟比赛视频，最好的模型原来约 150 毫秒，他们快了约三倍。他说延迟不可能到零，但能不能做到传输 0 毫秒、产品层 0 毫秒？办法是把计算从服务器挪到客户端，用能在手机、浏览器、Raspberry Pi 上跑的小模型。他们发布了一个只有 1 亿参数的端侧 TTS（名字字幕作 grad phon），准确率很好，能用任意给定的声音说话，现场播放了用 10 秒录音即时克隆新声音的样例。
