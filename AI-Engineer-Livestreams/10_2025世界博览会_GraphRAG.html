这一场的内容

这是 2025 年 6 月旧金山 AI Engineer World's Fair 的 GraphRAG 专场，主持人是 Neo4j 的 Andreas Kollegger（字幕里被称作 "Andreas"，Tom Smoker 称他 "ABK"）。先说两个基本概念。RAG（检索增强生成）是先从外部资料里检索相关内容，再交给 LLM 生成回答；GraphRAG 是在 RAG 里用知识图谱（Knowledge Graph，用"实体-关系-实体"三元组表示知识的网络）来组织和检索资料，不单靠向量相似度。

反复出现的主题：向量相似度不等于相关性；知识图谱的质量取决于本体（Ontology，事先定义好有哪些实体类型、关系类型）和抽取质量；Agent 记忆需要时间维度和因果关系；按业务领域建模图谱结构。Neo4j 是这个专场的合作方，多数演示都跑在 Neo4j 上。

01. Mitesh（NVIDIA 开发者布道团队负责人）：混合 GraphRAG 系统怎样搭、怎样优化

直播位置 0:00:00–0:21:10

他在 NVIDIA 带开发者布道团队，团队的工作是为各类应用写技术工作流和 notebook，放到 GitHub 上。这次讲的是和一个合作伙伴一起做的项目：怎样搭 GraphRAG 系统，加上混合（Hybrid）检索后有什么好处。他说只讲"一万英尺高度"的全貌，代码细节都在最后给出的 GitHub 链接里。

开场：RAG 死了吗

上午主题演讲时组织方抛出一个说法："RAG 已死，Agent 正在取代 RAG"。他现场问多少人在生产中用了 RAG，举手的人很多。他的看法是，如果 RAG 能解决你的问题，就不需要 Agent，反过来也一样，能用小工具解决就别建埃菲尔铁塔。

知识图谱为什么有用

知识图谱是表示实体之间关系的网络，实体可以是人、地点、概念、事件。他举例：他和这场大会的关系是"讲者"，他和在座听众的关系是"你们听了我的讲座"。这种实体之间的边只有图结构能充分利用。和纯语义检索的 RAG 相比，图谱更细地记录了实体间的信息，能把多个来源的数据组织在一起。

整体架构：离线构建，在线查询

他把流程分成四块：数据、数据处理、图谱构建（或语义向量库构建）、推理。他说数据处理得越好，知识图谱越好，检索就越好。数据处理和建库是一次性的离线工作；之后的查询和生成回答是在线部分，而且回答必须是用户读得懂的话，不能甩给用户三条关系让他自己去猜。

流程图上半部分是语义向量库：把文档转成向量嵌入存进向量数据库。下半部分是知识图谱，步骤更多，要格外小心。

从文档抽取三元组

例子是一份 ExxonMobil 的季度业绩文档，用 LLM 抽取关系：实体 "ExxonMobil"（公司），关系 "cut"（削减），另一个实体 "spending on oil and gas exploration and activity"（油气勘探支出）。这件事很难，所以要用 LLM，而且提示词要写得很明确：根据你的用例先定义本体，放进提示里，让 LLM 按本体抽取信息并整理成三元组格式。

他说这一步最重要：本体不对、三元组有噪声，检索就有噪声。他估计你会把 80% 的时间花在这里，反复迭代把本体调好。

语义向量库和检索策略

向量库这边比较成熟：他用《Attention Is All You Need》论文第一页举例，按块大小（chunk size）切分，并设置重叠（overlap），否则前后两块之间的上下文会丢失。但实体之间的关系这种信息，向量库利用不到，这是 GraphRAG 的长处。

检索时，如果只做单跳（single hop），就浪费了图谱最大的优势：沿多个节点走下去。要考虑走一跳、两跳还是更深；越深上下文越好，但耗时越长，在生产环境里延迟是要权衡的。部分图搜索可以加速，NVIDIA 做了 cuGraph（字幕作 "cool graph"），已集成进 NetworkX 等库，让你能走更多跳同时降低延迟。

评估

他本人负责评估这部分。可评的维度有忠实度（faithfulness）、答案相关性、精确率、召回率，用 LLM 打分的话还有有用性、正确性、连贯性、复杂度、冗长度等。他推荐 Python 库 Ragas，能端到端评估 RAG：查询理解、检索和回答都评。Ragas 底层用 LLM，默认接 GPT，也可以接自己的模型。另一条路是用专门的评分模型，比如 NVIDIA 几年前发布的 Nemotron 340B 奖励模型（Reward Model，专门给其他模型的回答打分），按五个维度打分。

最后 20% 的优化

他用二八定律：搭出能用的系统只占 20% 的时间，把它调到足够好要花 80% 的时间。他们和合作伙伴试了几种做法：

  • 数据清洗：用正则去掉撇号、括号等对三元组生成没意义的字符，效果变好。
  • 缩短输出：避免过长的输出，结果更好。
  • 微调：用 LoRA（一种只训练少量附加参数的高效微调方法）微调 Llama 3.1。在 100 份文档上测试，直接用 Llama 3.3 准确率 71%，LoRA 微调后升到 87%，再加上前面的小调整还能更高。他提醒文档多了准确率会下降，但相对提升是真实的。
  • 延迟：图谱到了百万、十亿节点，搜索要靠加速。用 cuGraph 加速的 NetworkX（也是 pip 就能装），他们测了几个算法，执行时间大幅下降。

什么时候该用图、向量还是混合

他给了"看情况"的回答，但说了两条判断依据。一是数据：零售、金融服务、企业员工数据库这类结构清楚的数据很适合图；即使是非结构化数据，如果能从中建出好的知识图谱，就值得一试。二是应用：只有用例需要理解复杂关系才用图，因为图系统计算很重。所有代码，包括 LoRA 微调，都在 GitHub 上，还有一个两小时的配套工作坊。会后他在 Neo4j 展台答疑。

02. 一家 AI 初创公司创始人（姓名字幕不清）：用"智慧图谱"存储专家的决策方式

直播位置 0:22:58–0:32:54（录像在演讲中途被切断）

讲者自我介绍为一家 AI 公司的创始人兼 CEO，字幕里名字作 "Ching Kyong Lamb"，公司名作 "PO.AI / PTO AI"，都无法确认，这里不写具体名称。主持人介绍说他会从哲学角度讲。公司两年前起步于美国国家科学基金会（NSF）SBIR 资助的 LLM 研究，做过 LLM 驱动的药物发现应用，现在为几家大公司客户做"专家 AI 系统"，客户要的是能做研究和顾问工作的系统，超出了 RAG 的范围。

从知识到智慧

他先给定义：知识是通过经验、教育和对事实原理的理解获得的认识；知识图谱是通过连接知识、形成关系网络来保存智慧的系统方法，代表一个专业领域的思考过程和完整分类体系。他介绍了 KAG（Knowledge Augmented Generation，知识增强生成），说它用结构化知识图谱增强语言模型，目标是理解，不停留在检索。

他访谈客户后发现，专家的思考和决策过程有共同模式，适合用图来表达。他展示了一张状态图：核心是"智慧"节点，输出到"决策"，决策要分析"情境"；输入来自"知识"（书本、百科、你存储的一切）、"经验"（以前什么管用）和"洞察"（从混乱中找模式，比如从社交媒体上追踪自家和竞品的舆情）。最重要的是反馈回路：情境、经验、洞察都反过来更新智慧。他用做披萨打比方：知识是菜谱，经验是知道自家烤箱会烤焦饼边，洞察是发现饼皮里加点蜂蜜能焦糖化。

映射到一个竞争分析客户

一个客户原来有建模部门做竞争分析，想让 AI 来做。他保留同一套分类：智慧引擎对应一个编排 Agent，负责决策和建议下一步；决策映射为策略生成器；知识对应市场数据；经验对应过去的营销活动；洞察对应行业洞察数据库；情境对应"我的产品卖得怎么样"，并映射为竞争对手的弱点。他说像"我怎样在这个市场赢过竞争对手"这种问题，简单 RAG 回答不了。

实现上他用 n8n 做原型。他说自己以前在 IoT 项目里用过 IBM 开发的 Node-RED，n8n 也是看似无代码、底下全是 Node.js 代码，很适合验证概念；n8n 里有 AI Agent 节点，可以驱动 OpenAI、Anthropic 乃至本地部署的模型。讲到状态机怎样跑起来时，录像被切断。

03. 讲者（未报姓名，疑为 Writer）：知识图谱加 Fusion-in-Decoder

直播位置 0:32:54–0:36:05（只有结尾）

录像从另一场演讲的结尾部分接入，讲者姓名和公司都没有出现。讲者说团队"自己训练模型"，并用 Amazon 的 RobustQA 数据集和七个向量检索系统做过对比，这和 Writer 公司发布过的基准测试一致，所以推测是 Writer，但无法确认。

讲者说团队的"下一个突破"是知识图谱结合 Fusion-in-Decoder（FiD，一种把多段检索到的文本分别编码、在解码器里融合生成答案的方法）。相关论文用知识图谱理解检索到的段落之间的关系，对段落做两阶段排序，缓解效率瓶颈并降低成本。团队基于这些研究做了自己的 FiD 实现，显著降低了幻觉率，并发布了白皮书。

去年的基准测试里，他们的检索系统（知识图谱加 FiD 等）在 RobustQA 上和七个向量搜索系统比，准确率最高、响应最快。产品上带来的功能：可以展示思考过程（片段、子查询、来源），并通过 API 开放给开发者；能回答跨多份文档、多个主题的多跳问题；能处理向量检索吃力的情况，比如答案分散在多页，或者用户用的词和文档里的词不完全一样。

讲者的结论是，得到知识图谱好处的方式有很多：图数据库、在已有系统上做些创造性的改造、或者搜索引擎，重点是利用关系。团队的做法是关注客户需求，不追热点，根据团队专长保持灵活，让研究去挑战自己的假设。

04. Daniel Chalef（Zep 创始人）：你的 Agent 记忆做错了，用时序知识图谱 Graphiti

直播位置 0:37:38–0:54:52

Daniel 是 Zep AI 的创始人，Zep 做 AI Agent 的记忆基础设施。他开场的说法是："你的记忆做错了"，或者说你用的 Agent 框架做错了。他认为知识图谱除了做 GraphRAG，也应该用于 Agent 记忆。

为什么 RAG 当不了记忆

Agent 经常忘记用户的关键上下文：对话里的动态信息、业务系统里的数据。结果是回答空泛，甚至产生幻觉。他说记忆和语义相似的内容是两回事，后者 RAG 做得很好（这里的 RAG 主要指向量数据库 RAG）。

他的例子：Agent 先学到 Robbie 喜欢 Adidas 鞋；后来 Robbie 的 Adidas 鞋坏了，他很失望，偏好变了。Robbie 再问"我该买什么运动鞋"，这句话和第一条"喜欢 Adidas"的事实最相似，向量库会把它排在最前，Agent 就答错了。在 RAG 里，每个事实都是孤立且不可变的内容，没有因果，语义搜索无法推理事物为什么随时间变化。向量嵌入只是抽象空间里的相似度，彼此之间没有显式关系。知识图谱可以定义显式关系，表达"为什么"；Zep 还让它表达"什么时候"，加入时间维度供 Agent 推理。

Graphiti 怎样工作

Graphiti（字幕作 "graffiti"）是 Zep 开源的实时动态时序图谱框架，GitHub 上一万多星，接近 11000，最近六周翻了两番。它的做法：

  • 为每个事实提取多个时间维度，记录它何时生效、何时失效，所以能回答"用户二月份喜欢什么"这种 RAG 答不了的问题。
  • RAG 只会留下一堆互相矛盾、没有解决的嵌入；Graphiti 能理解"鞋坏了"让"喜欢"这条关系失效，建立"鞋坏了 → 失望 → 品牌偏好改变"的因果链。
  • 不删除历史事实，只把它们标为失效，图上保存一串状态变化。最终图上旧的 Adidas 偏好仍在但有失效日期，新的 Puma 偏好有效且没有失效日期。
  • 不放弃嵌入：用语义搜索加 BM25 全文检索（一种经典的关键词相关性打分方法）找到子图，再用图遍历找相邻事实，最后把结果融合。内置多种搜索方案可选。
  • 新功能：开发者可以按业务领域定义自定义实体和边。心理健康应用和电商 Agent 要记的东西完全不同。例子是定义一个"媒体偏好"结构，记录用户喜欢的播客和音乐，检索时就能只取媒体偏好，过滤掉其他噪声。

什么时候用哪种

他不主张到处替换 RAG。RAG、各种 GraphRAG 和 Graphiti 各有适用场景。Graphiti 的强项是不需大量重算就能增量接入动态数据、建模业务领域、低延迟检索（检索路径上没有 LLM）。他说很多 GraphRAG 在检索路径上有 LLM 做增量总结，要几十秒；Graphiti 在数百毫秒以内。多数 Agent 应用可以同时用 RAG 和 Graphiti。他们今年发了一篇论文讲 Graphiti 架构和 Zep 的表现。Zep 本身在此之上做统一的客户记录，可以同时接入聊天记录和 CRM、计费等业务数据。

问答

  • 用 Graphiti 必须用 Zep 吗？不用，Graphiti 开源，只需要 Neo4j，他推荐 Neo4j Desktop。
  • 怎样让边失效，用 LLM 吗？是的。Graphiti 大量用 LLM 解析进来的非结构化数据（对话、邮件）和结构化数据（JSON），在流水线里识别冲突的事实；LLM 能理解事件的情感倾向，所以能从"鞋坏了"推到"失望"再到"换品牌"。
  • 状态翻回以前怎么办？看情况，可能新建一条表示后续事实的边，也可能把原来的失效日期清空。
  • 为什么 Graphiti 能实时更新而 Microsoft GraphRAG 不能？他简化地说，Microsoft GraphRAG 是在多个层级反复对文档块做摘要，摘要的摘要的摘要，计算很贵，底层数据一变就要级联重算。Graphiti 只找出受这次更新影响的具体节点和边，精确地让它们失效，或者只添加新的节点和边，改动轻量便宜。
  • 本体怎么来？两种方式：Graphiti 自动构建并小心去重节点和边的类型；或者开发者用 Pydantic、Zod、Go struct 等自己定义。

05. Mark Bain：AI 记忆、物理学和因果关系（午餐专题开场）

直播位置 1:24:54–1:42:10

午餐时段是一个约 45 分钟的 Agent 记忆专题，主持人说比其他场次长。Mark Bain（字幕作 "Mark Bane"）主讲，嘉宾有 Cognee 的 Vasilije Markovic、Zep 的 Daniel Chalef 和 Neo4j 的 Alex Gilmore。安排是：Mark 先做一个短演讲，然后四个现场演示，再介绍他们提出的 GraphRAG Chat Arena，最后简短问答。现场有 Slack 频道和配套文档供大家跟做。这是 Mark 第一次在 AI Engineer 演讲。

个人经历

他说自己 16 岁时擅长数学，参加数学奥赛，同场有后来的 OpenAI 联合创始人 Wojciech Zaremba。2014 年 9 月他来斯坦福读书，在一次聚会上遇到当时在 Google 的 Ilya Sutskever 和 Wojciech，两人跟他说 AI 会有一场大革命，他当时没太被打动，也没看出 GPU 会带来那么大的算力优势。他在聊天最后问 Ilya："AI 系统之间会怎样交流？"Ilya 答："我不知道，我想它们会发明自己的语言。"

他对记忆的定义

他说过去两年在研究"AI 的物理学"，研究了注意力、扩散模型、VAE 等架构。他的结论是：AI 记忆是任何格式的任何数据，包括代码、算法和硬件，以及影响它们的任何因果变化。他也提到生物系统、宇宙结构和量子结构在某种意义上都有记忆。

以下是他本人的理论观点，他说正在和导师合写一系列论文，尚未发表：

  • 他说物理定律的数量和数学定律的数量对得上，数学常数和物理常数也对得上，同样的原理支配着 LLM、神经科学和数学。
  • 他提到 Perelman（拒领百万美元奖金、证明了关于三维球面的猜想的数学家），说 Perelman 的公式把熵和曲率联系起来，而曲率对应注意力，也对应引力。
  • 他提出"记忆 × 计算 = i²（虚数单位的平方）"。他说如果完美对称成立我们就不会存在，存在需要不对称。在 LLM 里，计算把原始数据变成权重，权重给出结构，偏置是让模型稳健适应现实的小偏移；数据无限的话就不会有偏置。
  • 他说宇宙其实是一个网络数据库，是图结构，也是时序结构。规则必须带模糊性，否则一切都可预测。在量子层面的每一个不对称都保留了因果链接。

他想让听众带走的一点

他说简单 RAG、混合 RAG 等各种 RAG 和 GraphRAG 的区别在于：GraphRAG 能在记忆系统里保留因果链接，关系保存了因果。他认为这能帮助解决幻觉、优化假设生成和检验，推进生物和化学研究。他还说 Wojciech 曾告诉他，当记忆或算力不足以覆盖问题的组合空间时，幻觉是解题的必要手段；推理则是读取这些不对称和因果链接。他认为 Agent 系统遵循网络数据库的原理，要从模糊性里恢复因果，就需要图数据库。

09. Mark Bain：Agentic 防火墙、GraphRAG Chat Arena 和专题问答

Agentic 防火墙

Mark 说做 Agent 记忆之前，他带过一个私营网络安全实验室，客户是国防领域的大客户。有个项目要在二十七八个终端和 shell 之间切换，每种 Linux 发行版、防火墙、网络设备往往有自己的专有 shell，还有 PowerShell，得懂很多种语言。他发现 LLM 不仅能翻译这些语言，还能做一种"人话 shell"。这种 shell 如果有情景记忆（Episodic Memory，记录过去发生过什么事件的记忆），知道这个 shell 里历史上发生过什么、用户在做什么，就能管控每一次代码执行，包括 Agent 的执行。他和投资人、顾问把这个方向叫作 Agentic 防火墙。

10. Michael Hunger、Stephen Chin（Neo4j）：GraphRAG 的成功模式

直播位置 2:24:31–2:44:10

Michael Hunger 是 Neo4j 产品创新副总裁，Stephen Chin 负责 Neo4j 开发者关系。两人正在为 O'Reilly 合写《GraphRAG: The Definitive Guide》，上周末为了交稿没睡觉。Stephen 讲为什么需要 GraphRAG，Michael 讲具体模式和工具。

为什么需要 GraphRAG（Stephen Chin）

他说 LLM 缺少企业领域知识，无法验证或解释答案，会幻觉，还有伦理和数据偏差问题，像只会学舌的鹦鹉。业界逐渐意识到这是数据问题。普通 RAG 的不足：只按向量相似度取回一小部分信息；很多新的向量数据库上手容易但不够成熟，缺少可扩展性和容错；向量相似度不等于相关性，取回的东西相关但不完整，也难以解释。

知识图谱是节点、关系和属性的集合。他举了自家的例子：两个人住在一起，有一辆车，但车主不是开车的人，他妻子管账单，上高速时就把钥匙交给他，因为她讨厌开车。另一个例子是 Stack Overflow 数据建成的图。GraphRAG 带来的好处：相关性更好；能用图上的邻近关系取回相关信息，上下文更多；有节点和结构可看，结果可解释；可以加安全和基于角色的访问控制。

他引用了几项研究和报告：Microsoft Research 的 GraphRAG 论文显示效果更好且 token 成本更低；data.world 的研究比较了在 SQL 上做 RAG 和在图数据库上做 RAG，LLM 回答准确率提高到三倍；Gartner 2024 技术成熟度曲线上，生成式 AI 在下滑，RAG 在越过峰顶，GraphRAG 等技术在上升；LinkedIn 在客服场景用知识图谱的论文里，每个问题的中位解决时间降低 28.6%。

构建知识图谱的三步（Michael Hunger）

Michael 说 GraphRAG 有两面：先建图，再用图检索。建图分三步：

  • 词法图（Lexical Graph）：表示文档、块及其关系。可以简单到只有块，也可以是书、章、节、段落的层级，段落是语义完整的单位，用来做向量嵌入。图里能记录每个块的前驱、后继、父元素，还可以用向量或文本相似度把块连成 k 近邻相似度图，在边上存相似度分数。检索时就能按文档、时间顺序、相似度去找相关块。例子是把一份 RFP 按结构拆分。
  • 实体抽取：NLP 早就在做，LLM 凭多语言理解和灵活性把它提高了一个层次。给 LLM 一个图 schema、一段指令和文本，现在大上下文能一次塞进一万到十万 token。如果已有结构化数据（产品、基因、合作方、客户），可以作为真值一起传入，让 LLM 做识别，不必自由抽取。抽出的实体还能连到已有知识图谱，比如把通话记录里的信息连到 CRM 里已有的客户和线索上。
  • 图算法增强：比如在实体图上做聚类得到社区，让 LLM 为每个社区写摘要。他说这能找出跨文档反复出现的主题，因为每份文档只是信息的一个纵切面。

他们把在客户和论文里看到的反复出现的做法整理成模式，放在 graphrag.com 上（字幕作 "graph.com"），每个模式有名称、描述、上下文、示例图和对应的查询。

检索阶段

图检索器不是只做一次向量查找。先用索引搜索（向量、全文、混合、空间等）找到图里的入口点，再沿关系走到一定深度或一定相关度，取回更多上下文。上下文可以受外部信息影响，比如财务部门和工程部门的人查同样的数据，返回的内容不同。最后交给 LLM 的除了文本片段，还有一个更完整的上下文子图。他说现在的 LLM 在图结构上训练得更多，能处理"节点-关系-节点"形式的上下文。还可以用聚类、链接预测、PageRank 等图算法增强数据。

演示

  • Neo4j LLM Knowledge Graph Builder：能导入 PDF、YouTube 字幕、本地文档、网页文章、Wikipedia。他展示了从 Google DeepMind 的 Wikipedia 页面抽取的结果：一部分是文档和块，另一部分是按 schema 抽出的公司、地点、人物、技术等实体。可以选多种 LLM，可以在"图增强"里提供 schema，比如"人 为 公司 工作"。检索器可选向量、图加全文、实体等。他问"DeepMind 做过什么"，回答之外还能看到用到了哪些来源（AlphaFold 的 Wikipedia 页面、一份 PDF）、哪些块、哪些实体，可解释性很好；也可以用 Ragas 评估。项目开源。
  • Agent 式检索：把多个领域专用的检索器做成工具，每个工具执行一条 Cypher 查询，有输入参数和描述。Agent 把用户问题拆成任务、提取参数，顺序或循环地调用工具。他还提到 NeoConverse，能输出图表和网络可视化。
  • neo4j-graphrag Python 包：把构建和检索都封装进一个包，能建图、实现检索器、搭流水线。例子是传入 PDF 和图 schema，导入 Neo4j，再在 notebook 里可视化。

资源都在 graphrag.com，欢迎贡献。Stephen 补充说 Michael 的团队做了 Knowledge Graph Builder 等很多工具。

11. Ola Mabadeje（Cisco Outshift 产品负责人）：用多 Agent 和网络知识图谱做变更管理

直播位置 2:45:30–3:04:00

Ola（字幕作 "Hola Mabad"）在 Cisco 做了三年 AI 产品，所在的 Outshift 是 Cisco 的孵化部门，负责评估新兴技术怎样加速传统业务部门的路线图，也做量子网络。他是电子工程出身，后来转做网络工程。他说自己是产品人，讲得会偏产品一些。Outshift 的流程是：先访谈客户、做原型、A/B 测试，再把 MVP 放进生产环境，找到产品市场契合后交给 Cisco 的业务部门。

客户问题

一个客户说网络变更管理经常在生产环境出故障，问能不能用 AI 减少。他们深入后发现这是全行业的大问题。分析工作流后，他们找出其中第三、四、五步是 AI Agent 能真正发挥作用的地方，其余可以用规则自动化。

方案的三块

  • 自然语言界面：网络运维团队可以直接对话，其他系统也可以，比如他们让自己的 Agent 和 ITSM 工具 ServiceNow 那边的 Agent 对话。
  • 多 Agent 系统：不同 Agent 负责影响评估、测试、推理潜在故障等。
  • 网络知识图谱和数字孪生（Digital Twin，生产网络的虚拟副本）：孪生 = 知识图谱 + 一组执行测试的工具。

怎样把网络表示成图

网络很复杂：客户环境里有多个厂商、多种设备（防火墙、交换机、路由器），数据格式各不相同。数据来源有控制器、设备本身、设备上的代理、配置管理系统；格式有 YANG、JSON 等；形态有流式遥测、配置文件等。产品侧的需求是：多模态灵活性（懂键值对、JSON、实体间关系）；性能（工程师查询任何节点都能即时拿到信息）；运维灵活性（能统一到一个 schema 框架）；支持向量索引以便做语义搜索；生态稳定，部署到客户环境时不需要客户大量集成，支持多厂商。

工程团队比较了 Neo4j（他称之为市场领导者）和若干开源方案，最后在 Neo4j 和 ArangoDB 之间选了 ArangoDB，原因是历史上安全领域有一些类似推荐系统的用例已经在用它；部分新用例仍在评估 Neo4j。

架构：左边是生产环境的控制器、Splunk（SIEM 系统）、流量遥测，进入摄取服务做 ETL，统一转成 OpenConfig schema。OpenConfig 是面向网络的 schema，网上文档很多，所以 LLM 很熟悉。图按层组织：做配置漂移测试只需直接去原始配置层比较；做可达性测试则需要原始配置层、数据平面层、控制平面层几层。Agent 根据请求知道该去哪一层取信息。

Agent 层和 AGNTCY

他介绍了 Cisco 参与的开源协作项目 AGNTCY（agntcy.org，字幕作 "agency.org"），成员包括 Outshift、LangChain、Galileo 等。愿景是让全世界的 Agent 能互相对话，不必每次集成都重写 Agent。内容包括身份、描述 Agent 技能和能力的 schema 框架、存放 Agent 的目录、在语义层和语法层组合 Agent 的方式、以及运行过程的可观测性。GitHub 上有代码、文档和示例应用，也兼容 MCP、A2A 等协议。

这个应用目前有五个 Agent：一个助手 Agent 做规划编排，其余都基于 ReAct 推理循环（Reasoning + Acting，模型交替思考和调用工具）。他特别提到查询 Agent，它直接和知识图谱交互。他们起初试图用 RAG 来查图，效果不好，于是用 schema 信息和示例查询微调了这个 Agent。之前生成的 AQL 查询（ArangoDB 的查询语言）会在推理循环里遍历图的所有层，消耗大量 token、耗时很长；微调后 token 消耗和响应时间都大幅下降。

演示：一次防火墙规则变更

  1. 网络工程师为接入一台新服务器，需要改一条防火墙规则，先在 ServiceNow 提交工单；系统已摄取工单内容。
  2. 第一个 Agent 把信息总结成摘要。
  3. 做影响评估：这次变更会不会影响目标区域之外的地方，并让 Agent 把评估结果附到 ITSM 工单上。
  4. 生成测试计划。他说客户最大的痛点之一是跑了很多测试却漏掉该跑的那些。Agent 根据工单意图和网上大量测试计划资料，列出要跑的测试和每项的预期结果，同样附回工单，供变更审批委员会查看。
  5. 把变更用的配置文件在 GitHub 上提一个 PR，把链接贴进工单。
  6. 执行 Agent 读取测试用例，到知识图谱里取网络最新快照，把 PR 里的配置和快照结合，在数字孪生里逐项跑测试。测试工具可以是 Batfish、RouteNet 等网络工程工具。
  7. 生成测试报告：哪些通过、哪些失败，失败的给出修复建议，并附回工单。

最后他说评估很重要，他们在评估 Agent、知识图谱和数字孪生三部分；知识图谱主要看外在指标，少看内在指标，因为要对应到客户用例。这还是 MVP，目前的体会是知识图谱和开放的 Agent 框架这两个基础模块对做出可扩展的系统不可或缺。他提前 8 秒讲完。

12. Tom Smoker（WhyHow.AI 技术联合创始人）：法律行业里的图谱和多 Agent 系统

直播位置 3:05:34–3:24:54

Tom 是澳大利亚人，开场说自己视力不好又有口音。他做图大约十年，2016 年开始读图方向的硕士和博士，以前是多 Agent 系统方向的学者，现在是 WhyHow.AI（字幕作 "yhar.ai"）的技术创始人。公司的业务是赶在律师之前找到案子交给律师：主要是集体诉讼和大规模侵权（mass tort），比如很多人用了某种药品、受到伤害、科学证实了这种伤害，律所就可以把这些人集合起来起诉药企。公司不打官司，只支持律所。他们用图、多 Agent 系统、信号等组合，抓取网页，用专有流程筛选。

他指出，光是描述业务就已经出现一个 schema：个人、产品、成分、浓度、批号……这些点对领域专家很有价值，而且很适合可视化。

他怎样定义图和多 Agent 系统

他认为图的价值在关系：能看到什么和什么相连，能明确地表达这种连接，能对连接做大规模分析。关系可以是多跳、分叉、分布式的。图容易的地方是大家一看就觉得懂了，难的地方是两个人说"懂了"时理解可能并不一致，存储方式和说法也五花八门。

多 Agent 系统，他的用法是：把复杂的白领工作流拆成一组可以单独做输入输出测试的步骤，每步有不同的要求、频率和状态，状态通常由图来控制。律师不喜欢出错，整个行业要求精确、恰当、措辞正确，单独用概率性的 LLM 不行，必须有明确的控制、结构和 schema，能随时定位哪里对了哪里错了。

他的问题清单：工作流里有些步骤比别的重要得多；写一个坏提示词很容易，于是就有了一个坏 Agent，他真正信任的 Agent 很少，所以花大量时间加护栏（Guardrails）；记忆除了即时的，还要有情景式的，要记录状态随时间的变化并修剪。捕获、扩展、修剪、结构化、查询状态，这些他们都放在图里做。还有一笔账：单个 Agent 95% 准确已经很难，五个 95% 的 Agent 串起来，期望准确率只有 77%，而五步的工作流并不长。他把核心难题概括为不确定性下的决策。

法律行业的特点

法律工作首先要求一切准确、格式正确，其次是创造性的论证。他的例子：Netflix 收集用户数据有法定上限，超出就可能被起诉，但需要先例。先例是多年前 Blockbuster 因保存过多用户租借实体 DVD 的信息而被起诉。把 Blockbuster 和 Netflix 联系起来，就是创造性地运用细节。准确性、创造性、分散在各处的信息、专家脑中的隐性知识，这些和概率性的 Agent 发生冲突。他说自己不是律师，联合创始人是。

证据开示（Discovery）

被告药企有义务把信息交给律所，往往一下给 500GB 无关紧要的邮件，"你们自己看吧"。诉讼有时间线，物理上不可能全部读完，现在大多靠人工审阅加各种捷径。如果把这些信息抽取出来并一致地结构化，大量邮件可以直接排除，剩下真正有用的部分；在图上还能结合其他信息，以可视化的方式交给专家快速判断。比如成分浓度超标、在某个时间出了问题，在可能上百万节点的图里只有少数人和这件事有关。这样的图不算大，schema 一致，检索相对容易；他们已有生产中的 Agent，律师可以用自然语言查询案件和当事人。

案件研究

很多人用了某个产品后会在小众 subreddit、Twitter、论坛、IRC 上抱怨，用的是相似的说法，但传统的案件研究很少发现这些信号，大多靠人脉和订阅简报。他们的流程是：抓取整个网络，按和律所一起制定的 schema 把信息筛到对方关心的部分，再为每位律师生成报告。他说没有"最好的案子"，取决于哪个律师、合伙人或律所愿意接，所以问题在于具体和个性化，这也是 LLM、多 Agent 系统和图有用的地方：不同律师可以有不同的多 Agent 系统和不同的图，报告结构对每位律师固定、内容各不相同。他把这概括为"把个性化服务自动化"。

案例：汽车起火

有些车主开着开着车就冒烟起火，他们会去政府网站、carcomplaints.com、特定的 subreddit 或论坛投诉。追踪、抓取、结构化、套 schema、分析之后，可以算出某车型、某年款、某问题的投诉密度，即投诉数量乘以投诉速度（比如每月多少条，持续几个月）。他们现在还在建模型，用公开且记录完备的历史诉讼来训练，不必等速度信号出来。大型律所大概在人们开始投诉后八九个月才可能接案，他们能在约 15 分钟内发现，通常再花一个月左右确认这是想要的信号。他展示了一个为某位律师做的例子：车辆起火案，限定金额、品牌型号、司法管辖区。每位律师有自己想要的图，还能对结果做过滤和反馈，所以图不是静态的；图结构可扩展、可更新、可跨图查询。

他说他们的 RAG 较少是聊天界面，更多是生成报告，因为律师除了想要答案，还想要熟悉的文书形式。每天持续构建这些图，从大图里取出子图组成律师可以直接用的报告。

他的看法

他说生成式 AI 不比机器学习更好，LLM 也不比传统 ML 系统更好，各有适合的场景。以前搭多 Agent 系统时，工作流中总有某一步卡住，因为两段信息接不起来，太随机、太不一致，或者没法用二值特征描述。现在 LLM 可以把这些步骤接起来，但他们的系统主体仍是 ML 过滤，LLM 让端到端打通成为可能。能迭代地建图、修剪图、管理状态，让每份报告都更好，这是客户愿意和他们合作的原因。
