这一场的内容

这是 2025 年 AI Engineer World's Fair 在旧金山举办期间，Evals 分会场一整天的直播。评测（Eval）指的是用一组固定的输入和打分规则，去量化一个 AI 系统表现好坏的测试，类似软件里的测试集，但输出是不确定的。这个分会场由 Braintrust（一家做评测和可观测性平台的公司）主持。主持人在每位讲者上台前，会让不同的模型（Llama 3、Claude 4、Gemini 2.5 Flash、GPT-4o mini、Claude 4 Sonnet 等）根据讲者资料写介绍词，再当场念出来让讲者纠错，算是给 AI 介绍词做了一次现场评测。有一次 Gemini 把 Braintrust CEO 的履历编成了“曾领导 Google Cloud AI 平台产品”，主持人当场说这不对。

全天共 9 场演讲，其中一场是临时补位的 3 分钟演示。几条线索在多场里反复出现：一是“看你的数据”（Look at your data），几乎每位讲者都说了；二是评测数据应该从线上真实使用中来，用户反馈、日志、对话里的抱怨都要变成测试用例；三是像单元测试那样细粒度的评测容易过拟合到当前模型，新模型一来分数反而下降；四是 LLM 当裁判（LLM-as-a-Judge）好用，但裁判本身也要校准。午饭休息、换场调试和开场前的闲聊没有收录。

01. Omar Khattab（DSPy、ColBERT 作者）：在苦涩的教训之下，怎样构建能长期存活的 AI 系统

直播位置 0:11:46–0:28:32。直播字幕从演讲中途开始，开头一两分钟没有录进字幕。

问题：每周都要追新东西

他先描述了一种普遍处境：模型厂商不断发布越来越长的提示词指南，有时指南还写得不好，只能自己摸索；每天都有新的 arXiv 论文或推文，介绍新的学习算法、强化学习技巧、提示词优化方法、推理策略、Agent 框架。模型 API 有时在同一个名字下悄悄换了底层模型，你被迫跟着改。他说更尖锐的问题是：照模型进步的速度，你还能折腾多久，模型会不会直接把你的活干了。

苦涩的教训，以及 AI 工程到底在干什么

“苦涩的教训”（The Bitter Lesson）是强化学习先驱、图灵奖得主 Rich Sutton 大约六年前写在个人网站上的短文。大意是：70 年的 AI 研究表明，研究者用领域知识去解决问题（比如下棋），会做出复杂、无法扩展的方法，最后被能更好利用规模的通用方法打败。Sutton 认为最有效的是两类通用方法：搜索（探索很大的空间，放到 LLM 里大概相当于推理时扩展）和学习。

他接着问：如果利用领域知识是坏事，那 AI 工程还有什么意义？工程本来就是理解领域、用人的聪明才智按原则做事。他的解答是：Sutton 讨论的是怎样最大化智能，也就是在新环境里快速搞懂事情的能力。但我们写软件，并不是因为缺 AGI。世界上已经有 80 亿个通用智能体，他们不可靠，因为智能本来就不可靠，而且他们没有解决我们想用软件解决的问题。我们写软件是为了得到可靠、稳健、可控、可扩展、能推理和理解的系统。工程和制度设计里的各种制衡，做的事情是在恰当的位置小心地减少自主性和智能，其他地方不加限制。

所以他的第一条结论是：扩展搜索和学习最适合提升智能，如果你是研究学习型 Agent 的研究者，就别硬编码。但做 AI 系统时要问：搜索什么？为了什么而学习？你的系统要解决的根本问题是什么？这才是要工程化的部分，搜索和学习的具体细节反而不是。

过早优化是软件版的苦涩教训

他把 Sutton 的话和 Knuth 那句“过早优化是万恶之源”联系起来，说 1970 年代结构化编程的时候人们就讲过这个道理。人的领域知识本身无害，有害的是在理解不足时过早地用它约束系统。但工程领域又不能不做工程，否则就是放弃。

他展示了一段很难看懂的代码：用位运算和写死的常数，在某台老机器的浮点表示下计算平方根。换一种机器架构、浮点格式或更好的 CPU，它会算错，而且可能比一条普通的平方根指令或编译器优化后的版本更慢。他说经常写这种代码的工程师大概是做错了。

他提到自己做过两个已经存在好几年、基本结构没变的系统：ColBERT（一种检索模型）和 DSPy（一个用代码而不是手写提示词来构建 LLM 程序的框架）。它们从 BERT、text-davinci-002 一直用到 o4-mini，现在用的人比以往都多。他的假设是：当且仅当你在比自己能论证的更低的抽象层上硬编码时，才是在过早优化。要平方根，就直接说“给我平方根”，别去做迎合今天这台机器的位运算；甚至应该先退一步，问自己是不是其实在算更一般的东西。只有在证明高层抽象不够用时，才往下走一层。

提示词是糟糕的编程抽象

他说应用机器学习，尤其是提示词工程，在这方面问题很大。软件工程早就知道过度耦合不好，但做机器学习系统时很少有人谈，常见做法反而是“新东西出来了，全部重写去适配它”。他引用了自己 2024 年 5 月的一条推文：苦涩的教训只是缺乏好的高层机器学习抽象造成的现象；扩展深度学习的收益可以预期，但每次范式转变之后，最好的系统总会包含模块化的专门设计，这些设计每次看起来都差不多，本该可以复用，却因为代码写得差而无法复用。

他举了一篇 2006 年的论文《A modular approach for multilingual question answering》，里面的系统架构图有执行管理器、问题分析器、面向多个语料库的检索策略，上色之后像去年的多 Agent 论文。架构本身不算错，在普通软件里，换台新机器、新操作系统它就能继续跑，可机器学习系统做不到，因为它们的表达方式不对。

他最强烈的观点是：提示词作为编程抽象很糟糕，必须尽快改。作为管理抽象它还行，管理一个员工或 Agent，提示词就像给远程员工发 Slack 消息。原因有几条：

  • 它是一块只有字符串的画布，没有结构，即使结构其实隐含在里面。
  • 它把你要表达的核心任务定义，和一堆针对某个模型过拟合、半成品的技巧缠在一起，比如“这样说这个模型就听懂了”“加这个例子就管用了”，事后根本分不清哪些是根本的、哪些是偶然的技巧。
  • 它把推理策略也写死进去。告诉模型“你是一个 Agent”，可你的系统本来不需要知道自己是 Agent 还是推理系统。
  • 它把格式和解析也混进去，比如“用 XML 输出”“用 JSON 回答”，这些大多数时候和你要解决的问题无关。
  • 还有“你是爱因斯坦教授”“我给你 1000 美元小费”这类写法。他说这不是工程。

关注点分离：自然语言、评测、代码

他给的答案是老办法：关注点分离（Separation of Concerns）。工程师的工作是投资系统设计，从规格说明（Spec）开始，而规格不能归结为一种东西：

  • 自然语言定义。这是新范式的力量所在，但它和提示词不同，是一小块一小块局部的、只能用自然语言说清楚的模糊内容。
  • 评测。很多时候你在改措辞，是为了让某个模型在你心里的标准上表现好，却没有把标准告诉它。评测就是把“我真正在意什么”写下来，换了模型，评测仍然代表你在意的东西。他说这是这场演讲里唯一一句关于评测的话。但评测不能定义系统的核心行为，因为从数据里归纳学习比照着指令做要难得多。
  • 代码。谁来定义工具？谁来定义结构？信息怎么流动，私密信息不能流到错误的地方？函数组合怎么做？神经网络学东西不够可靠，LLM 很不擅长组合，而软件里的函数组合天生可靠，所以很多事最好交给代码。

一块好的“画布”要能把这三者流畅地组合起来，并且和变化中的东西解耦：模型要能热替换；推理策略要能从思维链换成 Agent，再换成蒙特卡洛树搜索；学习算法要能在整个系统的层面上做强化学习或提示词优化。他的第二条结论是：投资定义你的 AI 系统特有的部分，和底层可替换的部件解耦，因为它们过期得比以往都快。

DSPy 和最后的建议

他说团队做 DSPy 已经三年，它把你的工作（写上层 AI 软件）和他们的工作（提供不断演进的学习、搜索工具，以及通过适配器切换 LLM）分开。要学的只有一个新概念，叫签名（Signature），一种声明模块输入输出和任务含义的写法。因为时间不够，这部分他跳过了。

他的总结是：他不能预测未来，但最低限度要做到，别在比今天的工具允许的更低的层级上手工调。几样相对安全的投资：模型短期内不会读心知道你的规格，也不会自动收集你应用特有的结构和工具，所以要投资签名、必要的控制流和工具，以及亲手做评测；然后乘着可替换模型、现成模块和优化器（可以做强化学习或提示词优化）的浪潮走。更多内容见 dspy.ai。

02. Vitor Balocco、Rafal Wilinski（Zapier）：把 Agent 的失败变成评测和改进

直播位置 0:29:23–0:49:10

背景：两年做 Zapier Agents 的教训

两人是 Zapier 的 AI 工程师（主持人用 Llama 3 生成的介绍里称两人分别是 AI tech lead 和 staff AI engineer），在做 Zapier Agents。Zapier 本来是自动化软件，满屏方框和箭头；Agents 是更 Agent 化的版本：你描述想要什么，系统给你推荐一组工具和一个触发器，打开后就自动跑你的业务流程。

他们说两年下来最大的体会是：做好 Agent 很难，做一个让非技术人员也能搭 Agent 的平台更难。AI 本身不确定，用户比 AI 还不确定，会用你想不到的方式使用产品。很多人以为做 Agent 不难：找个 LangChain 教程，改改提示词，接几个工具，聊两句觉得能用，就上线收钱。现实的细节多得惊人。他们认为做概率性软件和传统软件不同，原型只是开始，上线之后你的职责变成搭建数据飞轮：收集反馈，理解用法和失败，写更多评测，做更多功能，产品变好，用户变多，失败也更多，循环往复。

第一步：埋点和收集反馈

  • 完整记录 Trace。Trace 指一次运行从输入到输出的完整调用记录。不管用 Braintrust 还是别的工具，只记 LLM 调用不够，还要记工具调用、工具报错、前处理和后处理步骤。尽量让运行可复现：按运行时的同样结构记录数据，之后就能直接把 Trace 转成评测用例，输入和期望输出都能预填。工具调用如果有副作用，评测里需要 mock 掉，这些信息 Trace 里也都有。
  • 显式反馈。点赞点踩的信号强，但很少有人点。要在合适的时机更主动地问。他们的做法是：Agent 跑完一次（哪怕只是测试运行），在底部显示“这次运行达到你的预期了吗？”，这个小改动让反馈提交量明显上升。要找用户最可能给反馈的时刻，要么很满意，要么很生气。
  • 隐式反馈。用户测试完 Agent 后真的把它打开，是很强的正面信号；复制模型回答也是正面信号，OpenAI 的 ChatGPT 也这么做。对话里也有信号：用户明确表示不满、让 Agent “别偷懒”、把上一条消息换个说法重发看模型能不能理解，都是负面信号，还有大量骂人的话。他们最近用 LLM 检测和归类用户的挫败情绪，每周在 Slack 里发报告，但花了很多功夫才让 LLM 理解在他们产品语境下什么叫挫败。
  • 传统业务指标。比如找出最近 7 天流失的客户，去看他们离开前最后几次交互，常能找到问题。

第二步：LLMOps 工具和失败分析

一次 Agent 运行可能包含多次 LLM 调用、数据库操作、工具调用和 REST 请求，每一步都可能出错，要把整个故事拼起来，才看得出是什么导致了连锁失败。他们既买现成的 LLMOps 软件，也自己做。他们说现在用 Cursor 和 Claude Code 写内部工具很容易，回报很大：一是能按自己领域的语境理解数据；二是可以做到看到任何有意思的案例或失败，一键转成评测，这应该变成本能。

单条运行看懂之后，就可以做规模化分析：反馈聚合、聚类、按失败模式分桶，看出哪些工具失败最多、哪些交互最成问题，这几乎自动生成了一份路线图。他们还在试用推理模型解释失败：把 Trace、输入输出、指令等都给它，它找根因的能力不错，即使找不到，也能把整个运行讲清楚或指出值得关注的地方。

第三步：评测金字塔

他们把评测分成三层，类似软件测试金字塔：

  • 底层：单元测试式评测。给定当前状态，预测下一步（N+1 状态），做简单断言：下一步是不是某个工具调用，参数对不对，回答里有没有某个关键词，Agent 是否判断任务已完成。刚起步建议先做这种，最容易加，能练出“看数据、发现问题、写评测复现、修掉”的习惯。但别把每条正面反馈都变成评测，这类评测最适合针对具体失败模式做爬坡优化。
  • 中层：轨迹评测（Trajectory Eval）。他们发现自己过度依赖单元测试式评测：新出的模型明明更强，在内部基准上却更差。评测太细，比较不同模型时噪声很大，只见树木不见森林。他们用 Braintrust 的 MCP 接口加一个推理模型，让它对比两次实验，比较 Gemini Pro 和 Claude：结论是 Claude 是果断的执行者，Gemini 话多、爱追问、需要正面鼓励，有时还会生成错误的 JSON 结构。这也暴露出单元测试式评测的问题：不同模型达成同一目标的路径不同，评测写死了一条路径，会惩罚其他路径，等于过拟合到了旧模型和用旧模型采集的数据。轨迹评测让 Agent 一直跑到结束，不只评最终状态，还评沿途的所有工具调用和生成的产物，可以配合 LLM 当裁判。投入产出比高，但难搭：工具有副作用时（你不想在评测里替客户再发一封邮件），他们决定不 mock 环境，因为 mock 出来的数据不反映现实，而是镜像用户的环境，做一份合成副本。这类评测也慢，有时要跑一小时。
  • 顶层：A/B 测试和分阶段放量。

关于 LLM 当裁判（用一个 LLM 给另一个 LLM 的输出打分或比较结果）：很诱人，但要确认裁判判得对，这出乎意料地难，还要小心引入细微偏差。他们最近在试基于评分细则（Rubric）的打分：数据集里每一行都有人手写的、自然语言描述的评分要点，告诉裁判这条运行该关注什么。例子是“日历 API 返回意外错误时，Agent 有没有反应过来并重试”。

他们现在的分工是：LLM 裁判和细则评测用来建立系统能力的总体视图，适合评估新模型；轨迹评测用来覆盖多轮对话的标准；单元测试式评测用来调试具体失败，但要防过拟合。

收尾：别迷信指标

指标一旦成为目标就不再是好指标。评测分数接近 100%，说明的是数据集不够有挑战，毕竟还没有 AGI。他们正在把数据集分成两个池：回归集，确保改动不破坏客户已有的用例；理想集，放极难的任务，比如连续正确完成 200 次工具调用。最终目标是用户满意度，裁判是用户，所以最终的验证方式是 A/B 测试：把一小部分流量（比如 5%）导向新模型或新提示词，看反馈和激活率、留存等指标。

问答

有人问细则评测怎样驱动产品决策。回答是细则评测还在试验，对评估轨迹和比较新模型最有用；真正决定路线图的是所有评测加起来的聚合视图：按桶分组，找出最该做的方向，再切出对应的数据子集迭代，最后跑全量防回归。另一位提问者问对齐评测花不花时间。他们说从负面反馈入手，以前开过“标注派对”，大家一起看 Trace 讨论哪里出错、期望行为是什么；现在有一个 Slack 频道和值班轮换，总有一名工程师负责看。没有严格流程，是尽力而为。他们走过的路是：一开始做长轨迹评测加 LLM 裁判，后来全押单元测试式评测，忽视了其他类型，现在吃到苦头，正在重新分散到各类评测，还在摸索比例。

03. Ido Pesok（Vercel v0）：应用层评测入门，从“水果字母计数器”讲起

直播位置 0:50:00–1:09:18

v0 近况

他是 Vercel 做 v0 的工程师。v0 是一个全栈 Vibe Coding 平台，用对话生成网页应用。他介绍了刚上线的 GitHub 同步：可以把生成的代码直接推到 GitHub，自动把 GitHub 上的改动拉回对话，切换分支、开 PR 和团队协作。v0 刚突破 1 亿条消息。这场演讲讲的是应用层的评测，和研究机构发布模型时引用的模型层评测不同：模型离开实验室之后，要在你的用例、你的用户和你的数据上管用。

水果字母计数器的故事

他编了一个应用叫 Fruit Letter Counter，只做一件事：数水果名字里有几个某字母，调侃的是“strawberry 里有几个 r”这个经典问题。Logo 用 ChatGPT 做，界面和后端让 v0 写，v0 用 AI SDK 的 streamText 调用模型。GPT-4.1 第一次就答对了 3，他测了两次都对，于是上线了 fruitlettercounter.io（.com 和 .ai 被占了），部署在 Vercel 上。然后用户 John 发推：“我问 strawberry 里有几个 r，它说 2。”

他说这就是 LLM 天生不可靠，从小应用到最大的 AI 应用都一样，而没人会用不能用的东西。AI 应用还有个特点：演示效果很好，给同事看也很好，一上生产就被幻觉找上门。他接着“熬夜改提示词”，写成“你是一个热爱水果、踏上史诗征程的 AI……”，这次在 ChatGPT 上连续测了 10 次都对，又上线了。John 再次发推，问的是 strawberry、banana、pineapple、mango、kiwi、dragon fruit、apple、raspberry 一共几个 r，它答 5。

他说这在生产里很常见：用户会提出你想不到的问题。有意思的是，应用 95% 的部分 100% 可靠，每个函数有单元测试，登录登出有端到端测试，偏偏是最核心的那 5% 会失败。

篮球场：理解你的“场地”

他用篮球场来可视化评测（他提到当天是 NBA 总决赛第一场）。篮筐是发光的金色圆圈，蓝点是投进，红点是没进；离篮筐越远越难；场地有边界，出界的球即使进了也不算。

  • “strawberry 里几个 r”改完提示词后大概能对，标蓝，放在篮下。
  • 那一长串水果的问题标红，放远一点。
  • “把元音都换成 r 之后，这几个水果里有几个 r”，问题很离谱但仍在业务范围内，标红，放更远。
  • “carrot 有几个音节”算出界，用户不会问，也和应用无关。

对应到评测的三个部分：数据（Data）是场上的点；投篮的方式，Braintrust 里叫任务（Task）；打分（Score）是看球进没进。他说做好评测最重要的一步是理解你的场地，并提醒两个陷阱：一是出界陷阱，别为用户不在乎的数据写评测，你在乎的问题已经够多了；二是点太集中，要覆盖整个场地。

收集数据的办法：点赞点踩（有噪声但能指出应用在哪挣扎）；有可观测性的话，每周随机读 100 条日志样本；社区论坛里用户会报告 LLM 的问题；X 上也有，但噪声大。他说没有捷径，只能自己下功夫。做得好的话，你会清楚边界在哪、哪里是蓝哪里是红，就能决定下周让团队集中处理右下角那片红区。

结构：常量放数据，变量放任务

像数学和编程里提取常量一样：用户会问的问题（“strawberry 里几个 r”）是常量，放在数据里；你要试的东西，比如不同的系统提示词、不同的前处理、不同的 RAG（检索增强生成，先检索相关资料再交给模型回答），放在任务里。这样改系统提示词时不用重做数据。他推荐 AI SDK 的中间件（Middleware），把前处理、RAG、系统提示词等逻辑放进去，让线上 API 路由和评测共用同一份代码。用篮球比喻，训练要尽量像真正的比赛。

打分：尽量简单、确定

打分方式因领域差异很大。这个例子只需检查输出里的数字对不对，写作类任务就难得多。原则上倾向确定性的、通过/不通过的打分，因为调试时日志很多，要尽量容易看出哪里错了；打分设计得太复杂，团队之间很难共享和理解。可以问自己：看数据时，我靠什么判断它失败了？v0 看的是代码能不能运行，写作任务可能看某些语言特征，把这个判断写成代码。实在写不出来就做人工审核，也没关系。一个技巧是评测时在原提示词后加一句“把最终答案放在 answer 标签里”，方便字符串匹配，生产里不需要。

他还建议把评测放进 CI（持续集成，每次提交代码自动跑的检查）。Braintrust 会出评测报告，列出改进和回归，比如同事改了提示词，能看到场上有多少格从红变蓝、有没有修好一处又弄坏另一处。他总结说，评测就是练习，换模型就像换球员；没有测量的改进是有限而且不精确的，评测带来更好的可靠性和质量、更高的转化和留存，也少花时间在客服和运维上。演讲里的篮球场图是他用 v0 做的小应用画的。

问答

  • 多久跑一次？他们至少每天跑，看哪里在失败、有没有回归。同一个问题跑多次也可以统计通过率，越难的点通过率越低。
  • 怎样分析成千上万条轨迹？v0 的领域是代码，可以真的运行生成的代码并收集错误，所以大量测量基于这些错误；写作类任务更难测，可能需要更多人工评测。他们和 Zapier 的结论相似：先看最终输出，应用能不能用；不能用再逐步排查是哪一步坏了。
  • 长对话怎么评？长对话相当于场上很难的一球，单独测；一段对话里可以有多个评测点，每次只测往前一条消息。
  • 错误出现在第三到第五轮怎么复现？v0 保存了每一步的状态，所以容易回到那一点。如果已经进入坏状态，就不太值得再测，因为 LLM 很不擅长从坏状态里恢复；重点是找到出错的那一步，减少这种点。他们也在做更好的纠错循环。

05. Diego Rodriguez（Krea）：当评测要考虑人的感知和审美

直播位置 1:15:48–1:32:16

o3 看不出一只坏掉的手

他是 Krea 的联合创始人，公司做生成式媒体（图像、视频等多模态生成）。他要讲的是评测里涉及人的感知、主观意见和审美时该怎么想。开场他放了一张 AI 生成的手，很明显很难看。他问 o3 怎么看，o3 想了 17 秒，调工具、跑 Python、用 OpenCV 分析，花了他几美分，结论是“基本自然，只有一两处小问题”。他说很多人称之为接近 AGI 的模型，答不了这么简单的问题；而人看到那张图，会立刻本能地觉得不对。他认为 AI 模型是用人类数据、人类偏好数据训练的，也因此被人类的感知和先入之见所限制。

信息论、压缩和感知

他回顾了 Claude Shannon：硕士论文为数字电路奠基，后来的工作被称为信息论的奠基之作，但他说 Shannon 当时始终关注的是通信，论文里那张“信源、信道、信宿、噪声”的图，眯着眼看有点像变分自编码器或神经网络。

他用 JPEG 说明压缩如何利用人的感知：人对亮度敏感，对颜色不敏感。他放了一张经典错觉图，A、B 两格看起来深浅不同，其实是同一种颜色。JPEG 把 RGB 转换到把亮度和颜色分开的颜色空间，对颜色通道降采样，还原出来的图在人眼里一样，信息量却少了大约 50%，再加上 Huffman 编码等步骤。对声音做同样的事就是 MP3，在时间上再做一遍就是 MP4。他大学学的工程专业研究麦克风、扬声器这类东西，写代码删掉信息、重新渲染却看不出差别时，他第一次直观地体会到“我们被感官所限”。

他的推论是：训练数据大量来自互联网，其中的图片很多被压缩过，我们的缺陷可能“传染”给了 AI。更麻烦的是指标本身：他引用了 Clean-FID 论文里的截图。FID 是衡量扩散模型生成图像质量的标准指标，加入 JPEG 压缩痕迹后 FID 判定图像很差，但人眼看四张图几乎一样。那为什么还用 FID 这类指标判断生成模型好坏？他说我们常常只测容易测的东西：用 CLIP 测提示词遵循度、数物体个数、颜色对不对。他放了一张钟表融化的超现实画作，按这些指标它是“糟糕的生成结果”，钟不长这样，天空也不合理，但它是艺术，有只有人能读懂的含义。他的公司要帮各类创作者表达自己，而现有指标衡量不了这些。

“预测汽车容易，预测堵车难”

他在 Midjourney 工作的一位朋友一年多前对他说：在马车时代预测汽车不难，把马换成发动机就是汽车；难的是预测堵车。他一直在想：作为工程师、研究者、创始人，我们漏掉的“堵车”是什么？大家都在关注“能把 JSON 转成 YAML”这类事，大图景是什么？

朋友还提到巴别塔的故事：人类想造塔去见上帝，上帝让人说不同的语言，于是无法协作。他开玩笑说这很像后端工程师的基础设施会议，有人要 Kubernetes，有人要别的，什么都建不起来。现在模型在很大程度上解决了翻译，每个人都能说自己的语言同时互相沟通。他自己有时亲自给 Krea 做客服，会用日语回复日本用户，而他并不会日语，这让他能给一个原本服务不了的国家提供创始人级别的支持。

评测要能包含个人意见

回到评测：如果每个人都能更好地表达自己的意见，评测就不该只问“图里是不是四只猫”，还要问“这只猫是蓝色还是青色，哪种蓝，我喜不喜欢这种蓝”。他希望指标能考虑“我的意见”；考虑人类如何感知图像（比如人是视觉学习者）；考虑数据本身的性质，比如训练数据大多是互联网上的 JPEG，训练时要把压缩痕迹等因素考虑进去。最后他介绍 Krea 用 8 个人做到了可观的用户量和收入，现在 12 人，在招做审美研究、超个性化、多媒体生成模型实时扩展的人。

问答里有人问有没有感知敏感的指标。他说有，有些在传统编码里也在用，FID 对 JPEG 痕迹反应很大，有的指标则几乎不变。他更想说的是：可以训练一个分类器或连续打分器，告诉它“这五张图都是好的”，即使它们带着各种痕迹。他说这种“看到就知道”的主观判断，机器学习最擅长。

06. Doug Guthrie（Braintrust）：Braintrust 评测入门，从离线评测到线上打分

直播位置 1:52:56–2:40:32

公司和为什么要做评测

他是 Braintrust 的解决方案工程师，入职第三周。Braintrust 是一个面向 AI 产品的端到端开发平台，主要做评测和可观测性。他提到 CEO Ankur Goyal 在前两家公司都从零自己做过类似的评测工具，这就是 Braintrust 的起源；已经有很多公司在生产里用。评测能回答的问题：换了底层模型，应用变好还是变坏？改了提示词呢？能不能检测回归？他转述 Ankur 的说法：很多人把评测当成单元测试，那是防守；评测也可以用来进攻，给开发过程带来严谨性。商业上，评测形成飞轮：把生产中的日志筛选出来加进数据集，反过来指导离线开发，缩短开发时间，提高质量。

评测的三种原料

  • 任务（Task）：要评估的代码或提示词，可以是一个提示词，也可以是调用工具的完整 Agent 工作流，复杂度没有限制，只要求有输入和输出。
  • 数据集（Dataset）：真实世界的例子，任务要在它上面跑。只有输入是必填的，可以加期望输出（Expected），比如用 Levenshtein 编辑距离比较输出和期望输出的差异；还可以加元数据，方便以后过滤。
  • 打分（Score）：评测的逻辑。一种是 LLM 当裁判，给它输出和标准，判断是优秀、一般还是差，对应 1、0.5、0；另一种是基于代码的打分，更偏启发式或二元判断。

两种思路：离线评测在上线前做，用于迭代、发现和修复问题，在这里定义任务和打分；线上评测是生产中的实时追踪，记录模型输入输出、中间步骤、工具调用，诊断性能、可靠性和延迟问题，还能拿到成本、token 数、耗时等指标。他转述 Ankur 的建议：先开始，建立基线再迭代，很多人卡在先造一个完美的“黄金数据集”上，没必要。还有一个判断矩阵：输出好但分数低，改评测；输出差但分数高，改打分方式。

平台功能

提示词可以在平台里写：选底层模型、写系统提示词、接工具，支持 Mustache 模板传入用户问题、聊天历史、元数据；可以添加多轮消息；可以给提示词挂工具（RAG、网页搜索等），提示词里写“用某某工具”，运行时就能调用。还有一个 Beta 功能，把多个提示词串起来，前一个的输出作为后一个的输入，加上各自的工具，可以搭出类似多 Agent 的工作流。

打分函数可以在界面里直接用 TypeScript 或 Python 写，也可以在代码库里写好推送到平台，让不在代码库里的同事也能用。他们有一个开源库 AutoEvals，内置现成的 LLM 裁判和代码打分。客户经验：打分用更强的模型，即使应用本身用便宜模型；打分要聚焦，比如他演示的变更日志应用，准确性、格式、正确性拆成三个打分，而不是一个打分同时评三项；打分提示词先在 Playground 里测；别给打分塞太多上下文，只给相关的输入输出。

Playground 用来快速迭代：拉入提示词或 Agent、数据集和打分，点运行；有家医疗公司让医生直接进 Playground 操作，还做人工审核。实验（Experiments）是评测的时间快照，用来看过去一个月里改动是否让应用变好。评测既可以在平台上跑，也可以通过 SDK 跑。

演示：变更日志生成器

演示应用输入一个 GitHub 仓库地址，抓取最近的提交，生成变更日志，用户还能给反馈。他事先在代码库里写好两个提示词、一个数据集和几个打分，推到平台。新建 Playground，载入第一个提示词，复制一份把模型改成 GPT-4.1，加上数据集和打分，点运行，并行跑完后看汇总视图：基准版本在完整性上略好，在准确性上略差，两者格式分都是 0%，说明格式还有工作要做。

他还演示了当天刚发布的 Loop 功能：一个类似 Cursor 的界面，让 AI 帮你优化提示词。它能读到评测结果，改完提示词后自己跑评测，看分数有没有提高。演示里生成了一个 diff，点接受后本该重跑评测，但他的 Anthropic API key 出了问题。

用 SDK 写评测

有 Python 和 TypeScript SDK，也有 Go、Java、Kotlin 版本，大多数用户用前两个。他展示了在代码里定义提示词、定义打分、定义数据集，然后执行 braintrust push 推送到平台，这些资产都有版本控制。评测本身也可以写成代码：一个 Eval 调用，传入数据集、任务和打分，用命令运行后平台上就能看到实验。也可以放进 CI/CD，文档里有 GitHub Action 的例子。把打分推送到平台的一个重要原因是线上打分要用同一套打分。

上生产：日志、线上打分、人工审核

  • 初始化 logger，指向一个项目。项目可以理解为一个功能的容器，装这个功能的提示词、打分和数据集。
  • 最简单的是包一层 LLM 客户端（他演示包了 OpenAI 客户端，以及 Vercel AI SDK 的模型），token、耗时、成本就自动进日志。进一步可以给函数加 trace 装饰器，追踪工具调用；或用底层 Span 接口自定义输入、输出和元数据。Span 是 Trace 里的一个步骤。自定义输入输出的意义是让日志结构和数据集结构一致，方便把日志加回数据集。
  • 线上打分：在平台上配置规则，选打分，设采样率（比如只对 10% 或 20% 的日志打分，演示时设成 100%）。打分可以只作用在某个 Span 上，比如单独评估 RAG 步骤返回的内容和用户问题是否相关。还能设自动化告警，分数低于阈值就提醒。
  • 用户反馈：演示应用里点踩加评论，会记进 Braintrust。可以把日志过滤成“用户反馈为 0”，保存成视图，给做人工审核的人用。按 R 键进入人工审核模式，界面更精简，可以按自己配置的审核分数打分。
  • 他又展示了一个对话式数据分析应用：第一步是根据聊天历史改写用户问题，这一步改写得差，后面全错，所以可以单独给这个 Span 打分，再单独评估意图识别是否正确。

他提到周二的工作坊上 Notion 的 Sarah（Braintrust 客户）讲过 Notion 怎么做人工审核：他们有一种专门角色，像产品经理和 LLM 专家的结合，负责审核；小公司则让工程师来做也很合理。人工审核不会消失，它提供了基准真值。

问答

  • 人工审核如何回流到离线评测？筛出有意义的日志行，选中后一键加到离线评测用的数据集里。
  • 生产里能否同时跑多个模型比较？可以，按模型分组看分数，等于做 A/B 测试。
  • 多个审核人标准不一怎么办？先给审核人一份评分细则和指南；平台能看到每条是谁打的分，能否导出成数据集比较差异他不确定。
  • LLM 裁判的分数往往是相对的，线上新数据怎么判断绝对好坏？很多客户在“评测评测”：裁判打分时附带理由，可以再评估裁判做得对不对，Notion 在工作坊里讲过类似流程。
  • 一位为政府做项目的提问者说客户要先看到准确率才肯上线。他说这就是离线评测，用专家写的问题和打分建立基线，分数从 20% 到 30% 到 40% 逐步上升，就是建立信任、推动上线的依据。
  • 数据能否导出到自己的统一仪表盘？SDK 都能拉取实验和数据集，有客户基于 SDK 自己做了界面。

07. Ankur Goyal（Braintrust CEO）：关于评测的五条实战教训

直播位置 2:52:22–3:13:27

一些使用数据

Braintrust 的用户（包括免费用户）平均每个组织每天跑将近 13 次评测；最深度的组织每天跑超过 3000 次；深度使用评测的用户每天大约花两小时看数据，研究什么有效、什么无效。

教训一：评测有没有用，看三个信号

  • 新模型发布后，能不能靠评测在 24 小时内上线一个用上新模型的产品更新。他说 Notion 最近几次模型发布都做到了。做不到就说明评测还要下功夫。
  • 用户抱怨某个问题时，有没有一条清楚直接的路径把它加进评测。没有的话，大量有价值的信息就流失了。
  • 能不能用评测来进攻：上线之前就知道哪些用例能解决、解决得多好，而不是像单元测试那样只查回归。

教训二：好的评测要靠工程做出来

合成数据集和网上随便找的 LLM 裁判打分不会自动给你好评测。没有哪个数据集完全贴合现实；真贴合的情况（比如竞赛数学题）往往用例本来就已经能用了。大多数真实用例里，事先想出的数据集都不代表用户实际遇到的情况，最好的数据集是能随着现实不断校正的，做到这一点需要相当多的工程。打分也一样：很多人问 Braintrust 自带哪些打分，好让自己不用想。他们的开源库 AutoEvals 刻意做得灵活，因为足够成熟的客户都在写自己的打分函数并不断修改。他说可以把打分看作 AI 应用的规格说明或 PRD（产品需求文档），用开源的通用打分，等于用了别人项目的规格。

教训三：重点从提示词转向上下文

现代 Agent 的提示词通常是一段系统提示词加一个循环：调 LLM、发工具调用、把结果放回提示词、继续迭代。他们从实际 Agent 轨迹里统计了各类消息占的 token 比例，结果大部分 token 来自工具定义和工具返回结果，系统提示词只占小部分。所以系统提示词要写好，但如果不精确地设计工具和工具输出，就浪费了大量空间。他说不能把工具简单当作现有 API 或产品的映射，要从 LLM 想看到什么出发设计；写好工具往往会对项目带来很大改动，远比在已有东西上加一层 API 多。工具输出也一样：他们有个内部项目把工具输出从 JSON 改成 YAML，效果明显变好。他知道这在 AI 圈有点像段子，但 YAML 更省 token，LLM 做分析时也更好读；对 JavaScript 来说两者都是结构化数据，对 LLM 则差别很大。

教训四：新模型可能改变一切

他说这个模式要归功于 Replit 的人。他们有一个评测，衡量一项新功能能否成立，每隔几个月跑一次：GPT-4o 时期分数很低，GPT-4.1 好一点，Claude 3.7 Sonnet 好很多，Claude 4 Sonnet 又明显更好。分数在 10% 左右时这个功能对用户没法用，后来突然可行了。Claude 4 Sonnet 两周前发布，他们当天就上线这项功能的第一版，因为评测早就准备好了。他鼓励大家写很有野心、今天的模型大概做不到的评测，并设计成新模型一来就能直接替换进去试。Braintrust 有个工具叫 Braintrust Proxy（类似工具很多），不改代码就能切换模型厂商。他提到 Gemini 2.5 Pro 0520 在这个基准上只有 1%，所以没放进图里；Google 当天又发了新版 Gemini，也许演讲完就能测一下。

教训五：优化整个系统，包括数据、任务和打分

要把 AI 系统当整体看：评测用的数据和获取数据的方式、任务（提示词、Agent 系统、工具等）、打分函数。他们用同一个基准做了实验：让 LLM 自动优化提示词，一次只给提示词，一次同时给提示词、数据集和打分，要求优化整个系统，结果差别很大，同样让一件事从不可行变成可行。

这就是当天开始发布的 Loop：Braintrust 用户在功能开关里打开 Loop，就能在 Playground 里让它根据提示词、数据集和打分自动优化，它也能生成提示词、数据集和打分。效果好的用法比如：优化这个提示词；这个数据集里漏了什么值得测的；为什么我的分数这么低（或这么高）；帮我写一个比现在更严格的打分。他们测下来 Claude 4 Sonnet 效果最好，Claude 4 Opus 再高几个百分点；也可以用 o3、o4-mini、Gemini 或自己微调的模型。他认为 LLM 已经能看提示词和数据并提出有建设性的改进，评测工作中很多体力活可以不用人做了。

问答

  • 把反馈变成评测会不会过拟合？他说他更担心的是数据集脱离用户反馈而过拟合。数据集最重要的不是某一时刻的状态，而是你能否持续把它和想要的现实对齐。产品里刻意不自动把用户反馈加进数据集（有人为此抱怨），因为希望由一个有品味、对问题有直觉的人挑出有意思的数据点。
  • 那张 token 占比图是什么？他们分析了一些 Agent 的 Trace，统计系统提示词、工具定义、用户和助手文本、工具返回各占多少 token。结论是在现代 Agent 系统里，工具占据了绝大部分 token 预算，所以不能把你的 GraphQL API 直接丢给 LLM 当一堆工具。
  • 一位做政府项目的提问者说，用户会因为不喜欢税务问题的答案而点踩，他们加了一个“答案是对的，但我不喜欢”的选项。她问换模型看不出大差别，只有 GPT-4.1 mini 好像完全无视系统提示词，“改变一切”具体指什么？他说 Loop 就是例子：这是一个很有野心的 Agent，基准分数长期停留在 GPT-4o 的水平。但并非所有任务都这样，他们的评测集里有“根据电影台词判断出自哪部电影”这类任务，从 GPT-3.5 起就做得很好。所以要准备好有野心的评测，新模型一来按个按钮就知道。

08. John Dickerson（Mozilla AI CEO，Arthur AI 联合创始人）：2025 终于是评测之年

直播位置 3:14:20–3:33:40

讲者和论点

他现在是 Mozilla AI 的 CEO，Mozilla AI 做开源 AI 工具、支持开源 AI 技术栈，目标是让开源社区在讨论 AI 未来时能和 Sam Altman 坐在同一张桌子上。之前六年他是 Arthur AI 的联合创始人兼首席科学家，Arthur 做传统机器学习和生成式 AI 的可观测性、评测和安全；介绍里还提到他曾是终身教授。这场演讲他主要从 Arthur 的视角讲。

他的论点：机器学习的监控和评测是同一把尺子的两面，不能测量就谈不上监控。过去评测一直没进入 C-suite（CEO、CFO 等高管）的视野，直到三件事同时发生：一是 ChatGPT 让 CEO、CFO、CISO 这些非技术高管也能理解 AI；二是 2022 年底企业因担心经济衰退冻结了 IT 预算，只剩下给 CEO 心头项目的钱，而这个项目就是生成式 AI；三是现在的系统开始代表人和团队去行动，过去它们只给更大的系统提供输入。他说三者叠加，Braintrust、Arthur、Arize、Galileo 等评测公司都看到了起飞。

回顾：ChatGPT 之前

以前机器学习模型输出一些数字，交给更复杂的系统，复杂性把模型本身掩盖了，决策者不会关心模型输出，最多到 CIO 那一层，所以评测的必要性在高管层面不明显。数据科学团队一直用统计方法监控，但和下游业务 KPI 的联系很弱，而企业买产品看的是省了多少钱、赚了多少钱。高管们谈 AI/ML 的 ROI 多是口头说说，实际上还是只卖给 CIO。

他列了从 2012 年前后开始的几代 AI/ML 监控公司：H2O、Algorithmia、Seldon，然后是 WhyLabs、Aporia、Arize、Arthur、Galileo、Fiddler、Protect AI 等，还有 Snowflake、Databricks、Datadog、SageMaker、Vertex、微软的产品。那时和客户谈，总听到“我们懂，但安全或延迟才是更大的问题”。他给风投做尽调时发现，2010 年代中期以后这个领域几乎每份融资 PPT 都有一页写“今年会有 CEO 因为机器学习出事被解雇”，据他所知至今没发生。他还引用了 JPMorgan 的 Jamie Dimon 2022 年 4 月的年度信：消费者业务从 2017 年到 2021 年底在 AI/ML 上投入了 1 亿美元，他说对 JPMorgan 来说这个数字小得好笑。

2023 到 2025：从科学实验到规模化

2022 年中到年底，企业对衰退的担忧很深（后来并没发生），大多数企业在十、十一月制定次年预算时冻结或削减了 2023 年的 IT 预算。ChatGPT 就在 11 月 30 日、节假日前发布。他说 Arthur 和 A 轮投资方 Index Ventures 当晚正在 NeurIPS 办活动，一屋子技术人员都被震住了，其他人也一样：让 Eminem 用 Taylor Swift 的风格说唱、让妈妈写个段子。可支配预算于是解锁给了 CEO 的心头项目。

  • 2023：预算紧缩，唯一流动的新钱流向生成式 AI，企业内部出现各种实验项目。
  • 2024：生成式 AI 应用开始上生产，主要是内部聊天应用、内部招聘工具等。穿西装的人开始问 ROI、治理、风险、合规、品牌形象。要定量评估风险，就必须评测。
  • 2025：规模化。前沿模型厂商和在座很多公司的收入都在涨，因为使用量在涨；高管们已经习惯谈论 AI 并投入真金白银，2024、2025 年的 IT 预算专门为 AI 留了钱。技术本身也确实惊人。再加上第三个因素，系统走向自主，所以今年是 Agent 之年。

他给了一个 30 秒的 Agent 定义，说源自 1950 年代末：要感知环境、学习、抽象和泛化，并且和传统机器学习不同，要推理和行动。复杂性和风险都大幅增加，对做评测的人是好事。评测终于成了一线议题，因为向企业卖任何产品，都要和下游业务 KPI 挂钩，而这需要量化。

每位高管为什么在意

  • CEO：从 ChatGPT 发布起知道这项技术能做什么，不一定懂注意力机制，但能和专家讨论、分配预算、向董事会和股东汇报。
  • CFO：关心对利润的影响，要往 Excel 里填数字，这些数字部分来自定量评测。
  • CISO：把它视为重大安全风险和机会。他说 CISO 往往比 CIO 更快签小额支票，组织小、流程少、更愿意试新工具。在 Agent 之前，生成式 AI 刚兴起时，幻觉检测、提示词注入就被归到安全领域，所以很多护栏（Guardrails）产品，包括 Arthur 和竞争对手的，都是卖进 CISO 办公室的。
  • CIO：一直在船上，想保住饭碗，让船继续开。
  • CTO：要标准，要基于数字做决策（字幕里提到的一个标准名称不清楚，可能指 OpenTelemetry 一类）。

他说所有评测、可观测性、监控、安全公司都已转向 Agent 和多 Agent 系统的监控，“要监控整个系统，而不是某个 Agent 用的单个模型”这一点在业界和政府已被广泛接受。4 月中旬 The Information 有篇文章披露了 Weights & Biases、Galileo、Braintrust 等评测创业公司的收入，但数据滞后六到八个月，据他和同行聊，那些数字已经不代表现在的水平，他预计 2026 年初的报道会说评测公司收入不再滞后。结尾一段字幕不清，之后他推荐了 Mozilla AI 的 any-agent，它在统一接口下实现了多种多 Agent 框架。

问答

  • 生成式 AI 的评测大多需要领域专家，比如多 Agent 系统做现金流折现（DCF）分析，怎么判断对不对？他提到自己在 Nature Machine Intelligence 发过一篇论文，讨论基于人设的 Agent（“扮演一位 40 多岁的俄亥俄州农民”）的问题，有价值但做不完美。他提到 Mercor（一家帮公司雇专家的公司）泄露的表格显示，Google、Meta、大银行以每小时 50、100、200 美元雇专家，坐在多 Agent 系统旁边同步做人工验证。对 DCF 这种做错会赔钱或丢工作的事，花这笔钱值得。他说数据集和环境的构建比什么都重要，花钱做出好的 DCF 环境本身就可能成为竞争壁垒，已经有资本支出投向这里。
  • 评测什么时候会主要由 LLM 来做？他说 LLM 当裁判已经在实践中大量使用，但有问题。他们上个月在 ICLR 有篇论文，讨论 LLM 裁判相对人类的偏差，比如对简洁、有帮助这类特质的偏好。它在某种意义上解决了数据集构建问题，像穷人版的人类评审，很多人把它当拐杖用，但必须验证，确保没有偏向奇怪的方向。

09. Jeff Huber（Chroma CEO）、Jason Liu（567 Studio）：看你的输入，看你的输出

直播位置 3:34:30–3:55:16

开场

Jeff Huber 是开源向量数据库 Chroma 的联合创始人兼 CEO，Jason Liu 是机器学习工程师、顾问和讲师。他们说演讲里所有内容都开源、有代码，不推销工具。大家常问的问题，比如用什么分块（Chunking）策略、我的嵌入模型是不是最适合我的数据，答案都一样：你只能管理你能测量的东西（他说这句话出自 Peter Drucker），所以要看你的数据，他们的目标是在演讲里说至少 15 遍。第一部分 Jeff 讲怎么看输入，第二部分 Jason 讲怎么看输出。

第一部分：快速评测检索系统

怎么知道检索系统好不好、怎么改进？可选的方法有：猜一猜、祈祷；用 LLM 当裁判，跑那些检查事实性等指标的框架，花 600 美元、跑三小时；看公共基准，比如 MTEB（一个嵌入模型排行榜），看哪个模型英文最好。他们主张用快速评测（Fast Evals）：一组“查询-文档”对，意思是输入这个查询，应该返回这篇文档。一组这样的对叫黄金数据集。把所有查询跑一遍，看对应文档有没有被检索出来，可以看前 5、前 10 或前 20 条。它又快又便宜，因而可以大量快速实验。他说点了运行要等六小时，实验的精力就没了，这些指标应该几分钱、很快跑完。

如果你有文档、有分块，但还没有真实查询，可以用 LLM 生成问题。直接说“给这篇文档写个问题”效果不好，但可以教 LLM 写出好的查询。他举了 MTEB 数据集里的例子：“花园里的凉棚（pergola）有什么用？”对应文档开头就是“花园里的凉棚……”，说明很多基准数据过于干净，真实数据从来不是这样。他们的报告深入研究了怎样让合成查询贴近真实查询，因为合成查询太贴合你的数据，很容易让你误以为系统很好。图表显示，他们能在语义上把合成查询的具体程度对齐到真实用户查询。这样一来，Twitter 上大家热议的新嵌入模型出来时，你可以用数据判断它在你的数据上是否更好，而不是改代码碰运气。当然换嵌入模型还要考虑重新嵌入的成本、速度、API 稳定性等，但“我的查询能召回多少文档”这个北极星指标快速有用，让改进更系统、更确定。

他们和 Weights & Biases 合作，拿它的聊天机器人做了实验：四个嵌入模型的 Recall@10（前 10 条检索结果里找回正确文档的比例），对比真实查询（记录在 W&B 的 Weave 里）和合成查询。两者结果接近，模型排序一致，没有大的翻转。几个发现：

  • 这个应用原本用的 text-embedding-3-small 在四个模型里表现最差。
  • Jina Embeddings v3 在 MTEB 英文榜上远超其他模型，在这个应用上表现却一般。
  • 表现最好的是 Voyage 3 Large，这是跑快速评测、看自己的数据得出的。

完整报告在 research.trychroma.com，附有视频和全部开源 notebook，可以在自己的数据上跑。

第二部分：从对话里提取结构

Jason 说，系统的输出可能是一段对话、一次 Agent 执行。分析输出可以告诉你该做什么产品、该给 Agent 配哪些工具。只有几百条对话时，人工全部看一遍很好，仔细想每次交互；他的说法是，只有当你觉得自己没有模型聪明时才交给语言模型。产品做起来后有成千上万条对话，量太大、细节太多，长对话里还有工具调用链和推理步骤，很难扫读，你也未必是能判断好坏的专家。但这些对话里有大量价值：用户会说“再试一次”“不是我想要的”“下次别偷懒”，很多反馈就在对话里，比反馈按钮收集到的多。

他用营销举例：评测分数 0.5、事实性 0.6，你不知道算好还是坏。可如果一个广告 KPI 是 0.5，你发现 80% 用户在 35 岁以下，年轻用户效果好、年长用户效果差，就等于划了一条线，可以决定是加倍投入年轻人，还是研究为什么年长用户不买账、该去哪些播客投放、要不要投超级碗广告。分群之后才能决策，“把广告做好一点”是空话。

做法是用 LLM 从每段对话里提取结构化元数据：发生了什么的摘要、用了哪些工具、出现了哪些错误、满意度、挫败程度等，然后嵌入、聚类、找出分群，再验证假设，和普通产品工程师或数据科学家做的数据分析一样。他提到 Anthropic 的 Clio 研究发现，代码类使用在 Claude 用户中的占比是它在 GDP 中占比的约 40 倍，这类分析能告诉你该往哪投入。

他们为此做了一个开源库叫 Cura：总结对话、聚类、构建聚类层级，并能在不同 KPI 上比较评测结果。比如整体事实性 0.6 说明不了什么，但如果发现需要时间过滤的查询事实性很低、合同搜索类查询事实性很高，就知道问题在哪。流程是三类模型：摘要、聚类、聚合。演示用一份用 Gemini 生成的假对话数据，聚出了数据可视化、SEO 内容请求、认证错误等类，再往上归成技术支持等主题，于是可以问：Agent 有没有调试数据库问题的工具？有没有调试认证的工具？有没有做数据可视化的工具？

他说很多时候解决办法是提供合适的基础设施，不用把 AI 本身变强。很多查询用到时间过滤而你没加时间过滤器，加上就能显著提高评测分数；有个项目要判断合同是否已签署，在 OCR 流程里多提取一个字段，就能做大规模过滤。

他给了一个使用量和表现的二乘二矩阵：

  • 使用多、表现差：必须修。
  • 使用多、表现好：没问题。
  • 使用少、表现好：可能需要改产品或教育用户，比如加预填问题，让用户知道有这个能力。
  • 使用少、表现差：也许在提示词里加一行“抱歉，这个我帮不了，请找你的经理”就够了。

理解之后可以构建意图分类器、路由、更多工具，按类别监控表现随时间的变化。单个 0.5 没意义，某类指标的变化能说明很多。他们曾因此发现新接入的客户和老客户用法很不一样。他认为现在常常是研究引领产品；进步的标志是能提出高质量假设并大量验证：分群让假设更清晰，快速评测让实验更多，持续监控带来反馈。这对任何产品都适用。

两人的总结

  • 输入端：别依赖公共基准，在自己的数据上建评测；先把检索做好，因为这是 LLM 进步解决不了的部分，检索好了才有资格去调 LLM；还没有用户时可以用合成数据补充。
  • 输出端：从对话中提取结构，统计有多少对话、工具误用频率、错误类型、用户为什么沮丧，做群体层面的数据分析，得到按影响加权的判断。比如说“我们该多做数据可视化工具”不如说“40% 的对话关于数据可视化，而代码执行引擎只有 10% 能做好，我们该加两个画图工具试试”。
