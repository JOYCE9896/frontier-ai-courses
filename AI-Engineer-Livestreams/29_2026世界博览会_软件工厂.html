01. swyx（AI Engineer 联合创始人、Latent Space 编辑）：开场，Loopcraft 与“最高层的循环”

直播位置 0:01:08–0:08:50

swyx 用一串幻灯片概括这几年的变化：先有 token，再有聊天，然后学会用工具、设定目标，现在大家都在做自动化、定时任务（cron job）和循环。他写过一篇文章叫 Loopcraft，前一天还有人在工作坊里讲过。他说 AI 工程师的核心技能，是搞清楚自己在哪一层循环里工作：想提高产出、扩大推理规模时就往上走一层循环；遇到可靠性问题、要修 bug 时就往下走一层。他半开玩笑地说，简单讲就是“一堆嵌套的 while 循环”。内容太多、分会场太多的抱怨他不打算道歉，大家要自己判断现在卡在哪一层，然后选去听什么。

他又讲了“人的循环”：先是心跳，然后学说话、用工具、开始工作，再进入小团队和家庭。他以前提过“小团队”（tiny teams）这个概念，说它越来越重要。往外推是整个人类文明的集体智能。他上次在 AI Engineer 的演讲说，在一个领域管用的 Agent 今年会泛化到别的领域，所以今年新增了医疗、金融、GTM（市场进入）等垂直分会场，还有一个前线部署工程师（forward deployed engineer）分会场，意思是 AI 终于扩散到编程以外。

他展示了几届的售票曲线：2023 年第一届大致线性增长，2024 年第一届世界博览会约 2,000 人，2025 年目标 6,000，今年超过了 7,000。他抱怨大家还是买票太晚，“基尼系数”在往上走，方向错了。最后他说，人们来参加会议是为了“最高层的循环”：人聚在一起，想清楚下一个循环是什么，也就是“产生循环的循环”。今年他们在纽约、巴黎、新加坡、墨尔本、迈阿密都办了峰会，还在招伙伴团队，欢迎大家在自己国家办；世界博览会是“峰会中的峰会”。

02. Ally How（Keycard 技术团队成员，主持人）：软件工厂专场开场

直播位置 0:08:50–0:11:18（主持人姓名在 1:31:51 第二次登台时才报出）

主持人介绍了主舞台的“软件工厂”专场。她说一年前 Geoffrey Huntley 发布了 Ralph Loop，让大家看到 Agent 可以整夜自主工作、自己做出完整产品。Ralph Loop 最早是一个很简单的做法：用一个 bash 循环把同一段提示词反复喂给编程 Agent，直到任务完成。但当时它只推荐用于从零开始的新项目（greenfield），预期也只能做到 90% 左右。

她认为现在是软件工厂最大的拐点，理由有几条：模型的视觉能力变好，能看到并验证自己的工作；工具生态更丰富，Agent 能接触真实的生产数据；上下文窗口（Context Window，模型一次能读入的文本长度）和记忆变好，循环里的 Agent 能记住之前做过的事；推理模型能接更复杂的任务；AI 安全的最佳实践开始成形，让 Agent 在企业里有足够的权限和自主性去做实事。她说当天的讲者会帮大家分清什么是真的、什么是炒作，以及怎样造出产出真实结果、不产出 slop 的软件工厂。slop 是社区对 AI 生成的低质量内容和代码的叫法。

03. Pablo Castro（Microsoft 公司副总裁、杰出工程师）：AI 与知识

直播位置 0:11:18–0:28:14 · 英文原题 On AI and Knowledge

Pablo Castro 说他在 Microsoft 的工作是把 AI 和知识连起来，他自称信息检索迷，长期研究知识表示、抽取和搜索。他把 Agent 用到的知识分成三类：内在的（intrinsic）、外在的（extrinsic）和习得的（learned）。

内在知识：把我们推上指数曲线的那部分

内在知识是模型训练时学到、存在参数里的知识。他说这类知识看起来理所当然，但今天的指数增长就是从它开始的。他展示了两段自己写的代码，相隔约 25 年，写法几乎一样：坐下来，凭记忆或查资料，然后写出来。接着他画了一条时间线：1996 年 Microsoft 推出 IntelliSense，不用再记函数签名；22 年后机器学习开始给 IntelliSense 的候选排序；三年后 GitHub Copilot 发布，比 ChatGPT 还早。他认为 Copilot 和 ChatGPT 这类体验主要依靠模型已有的知识。之后 Cursor、GitHub Copilot X 出现，去年底 Opus 4.5 发布，GPT 等模型在编程上越来越强，到今年初出现了 OpenClaw 这种“没有一行代码是手写的”的成功软件。

在 Microsoft 这边，Agent 平台从 GitHub 开始，托管、可观测性和管理放在 Microsoft Foundry。Foundry 的模型目录里有几千个模型。他说前一天刚宣布 Claude 在 Microsoft Foundry 正式可用。

外在知识：从单个数据集到全公司的“环境数据”

只靠内在知识，Agent 没法参与一个组织里正在发生的事。业界很早就有了检索增强生成（RAG，先检索相关资料再交给模型回答），后来发展成上下文工程（Context Engineering，系统地决定往模型上下文里放什么）。他挑了两个变化来讲。

第一个是从孤立的小数据集走向全公司范围的接地（grounding，让模型的回答基于具体资料）。他说做任何 Agent，都有你专门为它管理的知识，也需要组织里的“环境数据”：文档、邮件、聊天、数据仓库等。Microsoft 为此做了 Microsoft IQ，它是一组能力：Work IQ 连接 SharePoint 文档、邮件、日历、聊天和人与人之间的关系；Fabric IQ 连接数据仓库、数据湖、Power BI 报表等分析资产；Foundry IQ 让你推送自己的数据用于接地；Web IQ 用于需要公开网络信息的情况。

第二个是检索系统本身的演进。RAG 刚出现时，大家先用向量数据库（把文本变成向量，按余弦相似度找最接近的）。他说业界有一阵以为只要把余弦相似度算好，检索就解决了，事实不是这样。评测一再显示组合多种方法效果更好。他展示了 Azure AI Search（Foundry IQ 背后的搜索技术）的评测：单一方法不如组合方法，在真实客户场景里差距更明显。Foundry IQ 的设计目标是分层：在顶层你只要说“这里有一堆 PDF 和图片，你处理”，系统负责切块、向量化、相关性排序和 Agent 式检索；专家可以下到底层，自己定向量索引、量化方式、词法检索等，而且在同一套系统里上下切换。在核心检索之上，他们加了 Agent 式检索（agentic retrieval）：系统会反思数据集里有什么，判断输入里的信息需求是否已满足，再返回结果。他说在难的案例上，Agent 式检索在证据召回率、答案完整度等指标上一直更好。

演示：在 Foundry 里建知识库

他在 Foundry 里新建了一个关于电影的知识库：选一个模型驱动检索流程，设定“努力程度”（在延迟和质量之间取舍），然后指定数据来源：Blob 存储里的 PDF 等非结构化数据、Parquet 格式的统计表，再加上网络。保存后，这个知识库可以直接接到 Foundry 的 Agent 上；它也是独立资产，每个知识库都是一个 MCP 服务器。MCP（Model Context Protocol）是让 Agent 以统一方式调用外部工具和数据的协议，所以你在别处用的 Harness 不用写胶水代码就能接上。Harness 指包在模型外面、负责调度工具和流程的那层程序。他又切到 Azure 门户，打开这个知识库背后的索引，展示可以查看索引结构、指定量化方式和向量索引算法、查看切块结果。他还说他们评测时会看 token 效率，目标是用最少的 token 给出信息最密集的答案。

习得知识：Agent Optimizer 学习循环

习得知识来自个人和组织每天做事的过程。他说现在 Agent 在干活，就能观察流程、自动调优 Agent。Satya Nadella 最近写过人和 Agent 可以复利式地一起进步、形成学习循环，把一家公司独特的东西沉淀下来。Foundry 里对应的组件叫 Agent Optimizer：先评测基线，再生成候选，评测候选，结果好就部署到生产。

演示在 VS Code 里用 Foundry 工具包进行。他说不管 Agent 怎么写，只要把配置（指令、工具定义、技能等）外置就行。没有评测集时可以运行 eval generate，它会根据 Agent 的轨迹和指令生成一套侧重任务遵循度的评测。评测（Eval）就是一组带标准的测试任务，用来打分。然后运行 optimize，这次大约跑 45 分钟，用类似 GEPA 的循环（一种让模型反思失败轨迹、迭代改写提示词的优化方法）对评测指标做爬山式优化（hill climbing）。最后 optimize apply 把新配置替换进去。他对比了基线和优化后的指令：基线只有几句简单指令，优化版多了一大段，都是爬山过程中根据指令、技能、工具和真实用户轨迹自动长出来的。资料入口是 ai.azure.com。

04. Alexander Embiricos、Romain Huet（OpenAI）：AI 工程师正在吃掉世界

直播位置 0:28:14–0:47:48（主持人介绍两人为企业产品负责人和开发者体验负责人）

工程是回到根上

Romain 说，现场有 7,000 多名 AI 工程师。世界博览会历史上的意义是把未来公开造出来给所有人看，这场会也有同样的能量。总有人说工程师会消失，理由是写代码被抽象掉了；他们认为正相反。“软件吃掉世界，AI 吃掉软件，现在 AI 工程师在吃掉世界。”工程的内容一直比写代码多：把最新的科学和设计、品味、判断、想象力结合起来，做出人能用的东西。他给的节奏数字是：OpenAI 以前大约 15 个月发一个新模型，现在大约每六周一个；上周刚发布了 GPT-5.6 系列的预览。

Alexander 回顾了几次让他震惊的体验：代码补全，行内预测，Command K（让模型改代码但它不测试），模型开始测试自己的工作，到现在模型能接长而难的目标一直做到完成。Romain 补充说，两年前 2024 年 DevDay 他用 o1-preview 现场从零写一个无人机控制界面，那时模型不能运行代码、不能验证自己的工作，他只能祈祷；到 2025 年 DevDay，模型能测试自己的工作，他敢让它现场控制整套摄像和灯光系统。Alexander 说 Romain 被叫作“演示之神”，演示前问他成功率，他说四次里成功三次。

Alexander 列举了今年发布的东西里他最喜欢的：Codex 应用、目标模式（goal mode）、远程。他说这些都是用 Codex 造 Codex 做出来的。现在 Agent 能做你在自己电脑上能做的任何任务，所以能帮你处理写代码之前（为什么要做）和之后（评审、部署）的事。把 Agent 连到“为什么要做”，它就能开始更多工作；连到评审和部署，它就能落地更多工作。作为产品人，他觉得最大的收获是决策变好：原型做得更多，和用户相处的时间更多。

产品形态：聊天加上可动手的协作界面

Alexander 说，如果给他和模型同样的时间做一个中等长度的电脑任务，至少在他身上，模型对一般任务会做得比他好。那产品该长什么样？他们从使命“让 AGI 惠及全人类”出发，想两个问题：Agent 能在世界上做什么、在哪里运行；人怎样用这些 Agent。他们明确说目标是最大程度地增强工程师，没有打算把工程师自动化掉。他觉得科幻和超级英雄电影里的设想大致是对的，有两种模态：聊天（他认为聊天被低估了），以及一个强大的、可以亲手检查、引导、塑造的协作界面。就像和团队合作，大多数时候你只是和队友聊，让他们去做；偶尔你要钻进细节和他们一起解决。他们希望保留人对工作的“精通感”，不让人觉得想看细节很难。

这就是做 Codex 应用的原因：一个简单的聊天界面，可以用于编程也可以用于别的事，想多深就钻多深。演示画面里是 Romain 对一场世界杯比赛的比分预测，可以指着某个具体元素说“改这里”，也可以自己动手改。他说 Codex 应用立项时很有争议，有人当面对他说永远不会离开终端、Vim 或 Emacs，现在这些人也在用；团队内部也有人质疑，因为大家爱 CLI 和 IDE。他们的看法是，CLI 里很难做出适合各种工作的协作界面，那基本只能聊天；IDE 的顺序反了，它从代码开始，而现在是先和“队友”聊，需要时再钻进去。

Codex 是一组任何人都能在上面构建的层

Romain 说 Codex 不能是只有 OpenAI 能改进的封闭产品，所以刻意设计成分层：

  • 模型层：开发者通过 Responses API 用这些模型，Codex 应用也用同样的模型和 API。Codex 需要新能力时，他们尽量先放进 API。例子是压缩（compaction）：长任务需要把很长的上下文压缩成摘要继续跑，他们把它做进了 API，你的 Agent 也能用。
  • Harness 层：Codex 的 Harness 开源，可以检查、fork、改。AGENTS.md 也是同样思路，他们没有为 Codex 发明新的指令文件格式，选了一个别的 Agent 也能用的名字。Harness 默认用 OpenAI 模型，但没有写死，可以换开源模型保留同样的 Agent 循环。他们还把 Codex Harness 带进模型的后训练（post-training，预训练之后针对具体行为的训练）里，让模型学会在这个环境里调用工具。他举例说 OpenCode 团队看了这份参考实现，学了“用 ChatGPT 登录”是怎么做的，这比让开发者逆向工程要好。
  • App Server：为了做 VS Code 扩展和 Codex 应用，他们需要统一控制 Harness 的方式，于是做了 App Server，也开源了，这是他们自己产品用的路径。X 上叫 Dimillian 的开发者在 Codex 应用发布前就用它做了原生应用 Codex Monitor，现在他加入了团队，做了 Codex for iOS。
  • 应用层：应用内浏览器、插件等可扩展原语。浏览器使用和电脑使用（computer use）都是用开放给大家的同一套扩展点做成的插件。他们最近还做了面向数据科学、设计等岗位的插件，也开源了。

他说用户现在可以在越来越多地方用自己的订阅：OpenCode、Pi、Droid、OpenClaw，乃至 Xcode 和 JetBrains IDE。他强调每一层他们自己用的就是给开发者的那一套，没有一个简化版。

价值最大化：成本、速度、云端

Alexander 说要追求的是价值最大化（value maxing），他们拿它和 token 最大化（token maxing）对比。和工程负责人聊天时常见几个主题：

  • 成本效率：大家都想要前沿智能，他展示了 Terminal Bench 上的 GPT-5.6 成绩（顶端型号的名字字幕不清）。GPT-5.6 Terra 达到 GPT-5.5 的智能水平，成本减半；Luna 每百万输入 token 1 美元、输出 6 美元，在这个评测上超过一些知名模型。
  • 速度：GPT-5.3 Codex Spark 展示了速度能解锁什么，但大家也要前沿智能。他们展示了 GPT-5.6 跑在 Cerebras 上，每秒 750 个 token，说下个月可用。Romain 说这相当于 10 秒写完一个不小的 PR，还可以并行尝试五六种做法再挑最好的。
  • 云端：现场很多人为了让 Agent 继续跑而不合上笔记本。他们想要的是能合上电脑，让很多任务在各自隔离的机器上并行跑。最早的大发布是 Codex Cloud，很快会有大升级。更进一步，未来不该区分本地任务和云端任务，你随时随地跟 Agent 说话，它自己判断该在哪个环境做。他们提到 Theo 周末的一条预测推文，Alexander 说具体细节不一定，但那个方向会比六个月更快到来。

05. Peter Steinberger（OpenClaw 作者，现在 OpenAI）：未来不是 20 个终端，是更好的循环

直播位置 0:47:48–0:54:26

Peter 展示了一张自己开着十几个终端窗口的照片。他说今年一月他同时盯着 10 个以上终端，等某个跑完就去引导 Agent、排新任务，当时觉得这是生产力巅峰，现在看有点傻：他以为自己在编排，其实是在轮询（polling），自己充当了调度器、路由器和记忆。一开始是和一个 Agent 结对，后来 10 个终端时他已经在管 10 个直接下属。现在他主要和一个长期运行的“经理” Agent 说话，由它把工作分派给一个团队；碰到棘手的活，他还能下去直接和某个“工人” Agent 结对，但默认方式变了，他管的是一家小 Agent 公司的经理。

他说有三件事让这成为可能：

  • 服务端压缩让长任务足够可靠，他不再刻意围绕“开新会话”来优化。
  • 协调能力让一个线程能创建和引导合适的子项目。
  • 自动化让某件事发生时能唤醒同一个经理。

持久上下文、委派、触发器，合起来就是一个循环。循环跑起来之后，瓶颈会移动。去年他受限于 token，他加入 OpenAI 解决了（“我知道这个办法不能推广”）。然后受限于算力，所有线程同时跑时 MacBook 响得像喷气发动机，他用单独的测试机器解决，让 Agent 在别的机器上跑测试。现在他受限于注意力，注意力没法简单加量，所以最重要的技能是决定把注意力花在哪。

他问还有谁在盯着 Agent 看代码飞过。早期模型确实需要这样，看到方向不对就按 Esc 拉回来；最新一代模型理解意图的能力很好，再盯着看有点浪费时间。他举例：有人在他的开源项目上提了 issue，经理 Agent 醒来，对照项目的目标、笔记和愿景判断是否合适；合适就创建一个工人，工人调查、实现、跑测试，另一个 Agent 评审。他不需要看过程。经理需要他的时候，会把 PR、原 issue、提议的 diff、也许一段视频，甚至一个可以用 VNC 连进去的运行中构建交给他。他看一次、留个意见、也许批准，检查通过后合入。Agent 跑内层执行循环，他在外层定方向、做决定。他提到一位叫 Paul 的开发者（姓氏字幕不清）已经在用类似方式：固定了一个“幕僚长”线程，每 10 分钟醒来协调他的 GitHub 工作，并在侧边栏创建线程，方便他随时介入。

他说经理一旦长期存在，把它绑在一台笔记本上就不对了。Codex 已经能在不同主机之间移动工作，OpenClaw 有 gateway 和 node，但他觉得都不是最终形态。他的 Agent 应该能连到他的任何机器，知道哪些工作能在云上做、哪些需要本地机器；经理应该是一个他能发短信、能在 Slack 里引导、在哪都能听到的 Agent。他希望能直接让 Agent 替他设计整个循环，这还没解决。他的结论是模型进步得比 Harness 和组织快，设计这些是下一个工程问题。“未来不是 20 个终端，是更好的循环。”

07. Thomas Wolf（Hugging Face 联合创始人、首席科学官）对谈 Olive Song（MiniMax）：M3、稀疏注意力与原生多模态

直播位置 1:11:03–1:31:51（主持人介绍从 1:10:05 开始；对谈中嘉宾只被称为 Olive）

Thomas Wolf 说刚才的 GLM 在 Artificial Analysis 上排第二（他说把 Fable 去掉，因为没人能用），MiniMax 的 M3 排第四，等于开源前几名连着上台。他介绍 Olive 在 NYU 读博，在 Yann LeCun 的实验室做 JEPA，没去当时也在纽约的 Hugging Face，选择了 MiniMax。他说 MiniMax 是中国“AI 小龙”之一，同列的还有 DeepSeek、做 Kimi 的 Moonshot 和做 GLM 的智谱。M3 在 6 月初发布，发布时是最好的开源模型。

M3 是什么

Olive 说 M3 是一个较小的模型，总参数约 4,000 亿，激活约 200 亿（Thomas 后来说是 4,280 亿总参数、230 亿激活）。这种“总参数大、每次只激活一部分”的结构是混合专家模型（MoE）的特点。它编程能力强，还能理解图像和视频，开源模型通常只做文本编程。它有 100 万 token 的长上下文，用的是新架构 MSA（MiniMax Sparse Attention，MiniMax 稀疏注意力）。他们把编程与 Agent 能力、长上下文、多模态理解放在一起，因为认为这三样对未来的 AI 应用都重要。

长上下文和稀疏注意力

Olive 说长上下文的故事要追溯到 MiniMax-01 和 M1，那时模型能处理 1,000 万 token，但不是 Agent 模型，适合丢一本书进去写评论。后来他们发现，Agent 和环境交互、拿到大量工具返回、进行多轮对话时，短上下文不够，所以这一版要把长上下文带回来。MSA 的设计从高层看有两条分支：一条索引分支在较粗的粒度上挑出上下文里更重要的块，一条稀疏注意力分支只在选出的块上做计算。她说这个设计简单、可扩展，以后能继续拉长上下文、放大模型。

Thomas 回顾说，领域里做过很多注意力的研究，比如二次复杂度问题和线性注意力，FlashAttention 出现后这些似乎消失了，现在又回到第一性原理。他问会不会走向“万亿 token 注意力”，Olive 说超长上下文值得探索，需要架构设计和硬件一起研究。她说架构和推理优化还有很多空间，尤其是对延迟敏感又要求强能力的任务。MSA 是团队里一个实习生设计的。

MiniMax 怎样组织研究

Olive 说他们保证基础设施足够好，任何人都能摆弄模型。模型发布后有空的时候，每个人可以自己设计评测、找模型的弱点，提出想改进的项目，感兴趣的人加入，做几周到几个月，做成了就进入最终训练、随模型发布。架构类项目会更久，因为要重做预训练的评测等。

原生多模态：从第一步就一起训练

Hugging Face 上的模型卡写着 M3 从训练第一步就是多模态。Olive 解释，常见做法是文本预训练完成后加适配器（adapter）训练视觉理解，他们发现这会伤害文本能力，视觉理解也收敛得不好，因为模型已经偏向文本，不够优，也难扩展。也有实验室在预训练中途加入视觉（持续预训练），但这对配方很敏感，不同架构、数据配比、学习率都不一样，实验结论很难推广到更大的模型。所以他们决定从第一步开始。她说很多实验室这样做时会遇到模型训练几步后文本和视觉一起崩掉，他们解决了：在 ViT（Vision Transformer，把图像切成小块交给 Transformer 的视觉编码器）上做了大量工作；用交错数据（interleaved data），即保留原始图文混排中的图像和视频，不把它们遮掉；认真做数据清洗和掩码；做好奖励建模。Thomas 问会不会做超过万亿参数的模型，她说一定会，很多任务小模型做不好。

应用、开源和社区反馈

Olive 说 MiniMax 从第一天就以模型为核心，CEO 在公司成立前、ChatGPT 出来前，就计划做能理解所有视觉、输出所有模态的模型，这是他们的 AGI 梦想。应用是随之而来的，因为不能指望每个人都用 API 体验模型。她说这些应用覆盖超过 3 亿人、约 200 个国家，以及超过 100 万家公司。关于开源，她说她个人和模型研究团队一直希望开源，社区的反馈和对开源内容的 PR 都很有价值，会进入后续版本。她希望社区反馈多模态方面遇到的问题，以及想要的功能，比如有人要求可调的思考强度。

Thomas 说多模态在编程 Agent 里还用得少。Olive 举例：让模型读 PPT、读结构不规整的报告、看一段很长的视频后再调用工具行动，都会解锁很多 Agent 用例。Thomas 问 Agent 能不能看他的 YouTube 教程学会用工具，她说可以。他们内部有自己的研究 Harness，很多工作流已自动化；前沿模型都在追求 kernel 优化、让模型后训练别的模型、让模型自动构造数据，M3 在长周期任务和 kernel 优化上很强，他们用它加速迭代。Thomas 问 M3 是否在造 M4，她说在造 M3.1。她最近最兴奋的是多 Agent 和模型路由，它们既能解锁更复杂的任务，也能看清模型能做什么、不能做什么。

09. Tisha、Sushin（未报公司）：复现不了的 Agent 故障怎么调试

直播位置：片段 1:37:45、1:44:29；较完整的一次 2:01:20–2:10:06（预录视频，三次都没有播完，在介绍示例时被切走）

一次复现不了的事故

Tisha 说她和搭档 Sushin 都让 Agent 对接真实的生产后端，在那里一次错误的写入意味着你要打电话向客户解释数据去了哪。她描述常见场景：Agent 调错了工具、写错了东西，团队开始值班排查，第一反应是从遥测日志里拿出原始提示词，用同一个模型在本地跑，结果每次都对，跑十次也对。出事的那一次没了。复现不了就调试不了，调试不了就不能保证下一个客户不会遇到。

她的例子是一个对接券商 API 的 Agent。用户说“卖 1,000 美元的股票”，Agent 没做换算，直接把 1,000 填进数量字段，卖了 1,000 股。按每股 190 美元算，就是 19 万美元。可怕的是 API 在 30 毫秒内返回了干净的 200，没有异常、没有告警，仪表盘一片绿。

温度设成 0 不能解决问题

很多人的反射是把温度（temperature，控制采样随机性的参数）调到 0，以为贪心解码就确定了。她说这是误解：温度为 0 不能修复错误的推理路径，只会让模型每次以同样方式犯同样的逻辑错误。更糟的是，Reddit 和 Hacker News 上的工程讨论显示，温度 0 在硬件层面也不真正确定，同一请求跑上千次仍可能得到几十种不同回答。她从第一性原理列了四个原因：

  • 采样确定不等于系统确定：温度 0 只是永远取概率最高的 token（argmax），不保证每次算出的分数相同。
  • 浮点加法不满足结合律，加的顺序会改变结果，矩阵运算里细微的顺序变化会改变最终的 logit，翻转胜出的 token。
  • 不是并发问题：同一个矩阵乘法单独在 GPU 上跑一千次，结果逐位相同。真正的原因在批处理：你的请求会和同一毫秒到达服务器的其他请求拼在一批，而计算结果随批次组成而变（缺少“批不变性”）。
  • 混合专家模型的路由也有同样的瓶颈：每个专家有容量上限，一批里某个子网络溢出，token 会被改路由；一个 token 能不能进某个专家，取决于和你拼在一批的流量。

要的是可重放，不是逐位确定

她说追求文本输出一致是一场必输的仗，我们需要的是系统执行同样的状态转移。错误的问题是“怎样让模型确定”，她见过团队为此烧掉几周然后认定系统不可知；正确的问题是“复现不了的运行怎样调试和重测”。她区分了两个词：逐位确定（同输入同输出）属于可控性，托管 API 给不了，你也不该想要，随机性是模型好用的一部分；可重放性（replayability）是把已经发生的运行重建到足够调试的程度，属于可观测性。所以不用冻结模型，要把它做过的事记录下来。

记录的位置不该在网络层，因为 Agent 有一半的东西根本不走网络：本地检索、进程内工具、记忆，还有在流式和异步下不会切碎的部分。应该在“边界”上记录每个节点的输入和输出，记录每一步的含义，数据包级别的细节用不着。有了重放，就能做确定性的 CI：把模型停掉，离线重跑那次故障，不调用模型。整个循环是：标注、记录、可视化、理解、修复、重放、验证。

他们做了一个概念验证叫 Chronicle。核心概念是“边界”（boundary），可以理解为套在 Agent 工作流里任意节点外的框，节点可以是工具调用、一次 LLM 调用或一次 RAG 检索，只要是一个方法，就能加上 boundary 注解。注解会记录进出这个方法的所有输入输出，还可以附上模型版本、代码版本等参数，把运行时的整个状态冻结保存为一条轨迹。她开始用卖股票的 Agent 演示（规划步骤读用户输入，调用下单工具，再委派给下一个节点），视频在这里被切走。

12. Theresa（Factory）：软件工厂是什么，自己建还是外包

直播位置 2:10:15–2:31:18

Theresa 在 Factory 工作（字幕把公司网址听成 factory.com）。她说大家都在谈软件工厂，真正在建的人很少，知道要什么、怎样定义的人更少。Factory 很早就在做这个概念，现在技术终于跟上，可以给 EY、Adobe 这样的企业在生产环境里用。

定义

她把软件工厂定义为整个软件开发生命周期的自主循环：收集信号、回应用户反馈和日志、排优先级、编排、执行、验证、做好的生产环境测试，然后迭代，同时在过程中持续改进、获得新知识和新技能。她展示了 Factory 的仪表盘。她说 2023 年就有 AutoGPT、BabyAGI 这种持续循环的想法，但当时模型幻觉严重、上下文短、推理质量不够，也缺少让 Agent 隔离工作的好环境。

她喜欢从“它不是什么”来定义：一个编程 Agent，或一群甚至上千个编程 Agent，都还算不上软件工厂，因为写代码是最容易的部分，工程师本来也不把大部分时间花在写代码上；咨询公司卖给你的抽象战略也算不上。她认为组织应该从底层重建来适应软件工厂，不能请个咨询把东西塞进组织中间。她把建软件工厂比作组建一个人类团队，Agent 多了会测试、验证、迭代，容易乱成一团，所以要有意识地设计。她讲了三条原则。

一、模型无关

要能接入大家现有的工作环境（Slack、GitHub 等），允许大家带自己已有的订阅，因为新技术、新模型、新基准不断出现，很难预测谁赢。她引用 Coinbase CEO 发的一张图：token 用量继续增长，花费却下降了。做法包括：默认模型不再一律用最前沿的；缓存；不限额度但要看到结果；还有模型路由。

Factory 做了自动模型路由：先判断哪个模型最合适，任务失败或出问题时可以换模型，但通常不需要。她说这还带来别的好处：开源模型往往更快，某个模型服务商挂了也能自动切换，所以也提升可靠性和速度。她们的基准比较保守，显示能省约 25%，实际可能更多。路由分四步：分配任务（组织可以给市场、销售、工程等不同岗位设不同的默认模型和权限）；分类，这是关键的一步，要看提示词结构、代码库、任务难度、用到的工具，给任务难度分级；设阈值；选出预计能完成任务的最便宜的模型。常被问到的问题有：中途升级模型会不会更慢更贵（她说即使中途换更强的模型，总体通常仍更快），以及缓存怎么办。她说大模型实验室靠缓存省了大量钱，跳过上下文的预填充（prefill，模型先把输入全部读一遍的计算），开源模型部署在专用算力上也能缓存，所以最终给用户的价格是商业决定，不是技术难题。

二、自主

她说循环一直都有，只是现在进入了 Agent 的语境。问题不在循环本身，在怎样定义“完成”。她同事做过一个循环，让 Agent 去 3D 打印公司的 logo。以前编程里的循环有清晰的结束条件，现在很多任务是开放的、不确定的，甚至涉及实物，很难验证。她展示了一张她叫“吓人的图”：Agent 能自主运行的任务时长在增长，但能跑很久不等于在生产中可靠。还有作弊问题：完成条件写错了，Agent 会去通过你的测试，不去完成你真正要的事。

Factory 的长时间运行会话叫 Missions，可以跑几周。主 Agent 是编排者，写下完成条件，把工作交给 worker Agent，再交给 validator 审查。她展示了一个客户真实跑了 16 小时的 mission，验证占了全程的 40%。她指出 worker 是按顺序工作的，没有成群并行：每个完成一部分交给下一个，她们发现这样上下文更新鲜，就像人有同事复核代码；每个 worker 内部可以有并行的子 Agent 做研究、建文件等小任务。validator 审查输出、给反馈并送回开头，并且只评判别的 Agent 写的代码。编排者在写任何代码之前先写好“验证合同”（validation contract）。validator 有两类：审查型（scrutiny）严格检查代码结构、类型、测试；用户测试型（user testing）在自己的虚拟电脑里点来点去，不管怎么做出来的，只看能不能用。她说有工程师用 Factory 的 Agent Droid 做代码库迁移，别的产品做出的东西看起来对但根本不能交互，问题是这个会点击的 validator 发现的。这得益于电脑使用和持久虚拟机的进步。她把 mission 画成“大循环套小循环”。

三、持续改进

上下文膨胀是绕不开的问题。她说企业平均用上百种工具（Figma、Notion、Gmail、Drive、Slack 等），每个工具都有规格、参数和很长的描述，全塞进上下文会让 Agent 在名字相近的工具之间选错，或者因为窗口满了被迫压缩。Factory 的做法叫 deferred context engine（延迟上下文引擎），用渐进披露：一开始只给一个简短的工具列表和短描述，真正需要时才加载完整工具。什么都没删，只是先藏起来。用的工具越多，省得越多，能省 50% 以上的 token。

她说 AI 的采用呈幂律：要么大成功，要么大失败。代码库没准备好、结构混乱时，变成软件工厂反而会让代码退化，她引用了斯坦福的数据说明这一点。Factory 有一个 Agent Readiness 框架（她说不喜欢“框架”这个词，可以理解为代码库卫生检查）：开发环境是否可复现、测试写得好不好、文档、代码风格、linter 等。大客户会走一遍检查，再按建议修复。她还说，人加入新公司时很多规则没有写下来，要靠观察；Agent 也有同样的问题，你会不断重复告诉它怎么做事。Factory 为此做了插件（打包好的可复用技能和上下文），以及自动更新文档和审查记录的功能。

关于人的去处，她说她想乐观一些：人一直在往上抽象，最早人就是“计算机”，后来有了编程语言，然后是编程 Agent，现在走向软件工厂，人管理编排者、worker、validator 组成的团队，监控并决定做什么。“人应该决定软件做什么，不是怎么做。”她最后展示一张图，说企业里大量时间花在对齐、开会、同步状态上，这些可以外包给软件工厂。

一、待在前沿附近

新东西一出来就试。他们自己的经历是：原本在做另一个应用 Chorus，去年二月他们重度使用 Claude Code，把整个工作流围绕它搭建，先把仓库克隆五份，后来发现 git worktree（同一仓库的多个工作目录，可以并行在不同分支上干活），一点点做出了内部工具，这就是 Conductor 的来历。不做创业的话，你应该是公司里最了解最新工作流的人；以前靠社交圈信息会慢慢传到你这，现在变化太快，这样会落后三到六个月。

二、别想着跑赢市场

他强调是“附近”。站在最前沿的风险是把所有时间花在打磨工作流上，不干实际的活。他们内部的经验法则是问自己：为什么这个工作流不是默认的？比如 Ralph loop 火的时候，要不要花大量时间优化自己的工作流去适配它？如果它对所有人都有效，那等 Anthropic 或 OpenAI 把它做进默认 Harness 就行。他把这比作有效市场假说：除非你有真正的 alpha，也就是关于你的用户或代码库、模型不知道的信息，否则别过度优化工作流。他们的 alpha 是：作为聊天应用，要快速渲染很长的对话，性能很重要，所以花很多时间优化 React 查询，并愿意在别处做出牺牲。“别做那种 Emacs 配置很棒却不干活的人。”

三、划出无 slop 区

无 slop 区是代码库或应用中需要严格人工审查的部分。他说很多人以为他们是纯粹的 token 最大化者，随手合 3 万行的 PR，其实他们对某些部分很谨慎，对其他部分很放松。不注意这一点代码库会陷入麻烦，他们因此重写过整个应用好几次。具体做法：有一个 migrations 文件，CI 要求任何改动都必须有人审查；Slack 里的文字默认是人写的；所有文档、CLAUDE.md、技能文件都投入大量时间打磨，他说见过的顶尖构建者都在这些文件上花了不寻常的工夫。他的比方是：如果新来的实习生每天开工时你都能在他耳边说一句话，你会认真想说什么；CLAUDE.md 或 AGENTS.md 就是每次 Agent 开工时加载进上下文的那句话。

四、喂饱野兽

他们有个内部 Agent 叫 Conductor Internal Agent，简称 CIA，是组织里所有信息的集中库：每条新 Slack 消息、Discord 上用户报的每个 bug、每次会议录音，都会被它存进一张 Postgres 表。要让 Agent 在公司里有效，就要让它尽可能了解你们具体怎么工作。他引用一条推文：把一切放进数据库，给 Agent 一个 SQL 工具，剩下的交给它。

五、散养 Agent

给 Agent 足够的空间：一个不会被杀掉的沙箱，可以探索代码库、做难的任务，不会因为你合上笔记本就停；给它们创造更多自己的能力、和其他 Agent 与人协作的方式。模型越来越强、能跑得越来越久、数量越来越多，困在笔记本里就发挥不了。

他演示了当周发布的新版 Conductor，主题是云端协作。每个工作区顶部有云图标，点开能看到 Agent 运行的沙箱信息，合上电脑它们还在跑。直到这周，Conductor 的每个任务都建在 git worktree 上，现在放在云沙箱里。云上还能做协作：他能看到同事 Kaden、Lewis、Tywin 在做什么，看到 Jackson 的头像弹出，可以点进去实时查看。他点进 Kaden 的工作区审查改动，留言“能不能用 tab 不用空格”，对方能实时看到并在工作区里聊天。他说协作是今年最重要的界面变化之一，没人在谈，原因是好东西都是团队做的，而且模型越强（他说这两天用 Fable 就能感到），你越敢做更大的东西，就需要更多人和 Agent。另一个好处是 Agent 可以通过 API 生出新的自己：他的 OpenClaw（叫 Lord Crandon）能调用 Conductor API，他在手机或 Telegram 上说“新建一个工作区，把所有按钮改成蓝色”，Lord Crandon 就创建了工作区并开始干活。

六、乐团，不是工厂

这也是他演讲的标题。他说自己挺讨厌“软件工厂”这个词：工厂让他想到自动化，自动化有很多好处，但他不希望未来围绕工厂建立。他想要的是站在乐团前挥指挥棒，这边一挥一组 Agent 开始干活，人和 Agent 交织着工作，想看细节时放大，多数时候缩小。他不想当流水线经理按按钮让 Agent 产出下一个功能，十年前“功能工厂”（feature factory）的说法就证明这行不通。他说做工具的人有责任让工具对人友好，要用让人觉得兴奋、有能力、在心流中的词。他想像 Steve Jobs 和一群优秀的人与 AI Agent 一起设计 Mac 那样工作。

16. Greptile 联合创始人（自报名字字幕作 “D”）：百万级 PR 数据看 Agent 写的代码到底好不好

直播位置 3:04:32–3:16:32（字幕把公司名听成 Grapile、Gravile、Reptile 等）

Greptile 做的是带完整代码库上下文去审查和测试 PR 的 AI Agent：打开 PR 时它读所有文件，用代码库知识库判断可能受影响的地方，还在沙箱里运行代码找问题。但他这次讲的是另一件事。三年前他刚到旧金山时，AI 编程只有 Copilot 的 Tab 补全，后来是 Cursor 更强的补全；2024 年 Agent 能做多文件编辑；2025 年 Agent 越来越自主，他说 2025 年 12 月是转折点，那批模型能从工单一直做到 PR。他原本以为完全由 Agent 写代码只适合独立开发者和创业公司，不适合企业，但不断听说企业里也行得通，于是想用数据看看。

怎样识别“全 vibe coding”的 PR

Greptile 和上万个团队合作，自己不写代码只审代码，每月有超过 100 万个 PR 经过它，客户包括 NVIDIA、Coinbase、Scale。vibe coding 指基本由 AI 写、人不细看的编程方式。识别很难：

  • 看 GitHub 的作者字段，只有约 1% 署名为 Codex 或 Claude Code，他觉得不合理。
  • 看 PR 描述和提交信息，他说 Agent 和人一样自恋，喜欢留下 “Co-authored by Claude/Codex”。
  • 看分支前缀，Codex 会替你给分支命名。

结果是四月份超过四分之一的 PR 有证据表明大部分或全部由 Agent 写成；往前追 12 个月，一年前还不到 1%，而且在上升。

这些 PR 好不好

  • 回滚率：GitHub 回滚的分支以 revert- 开头，便于统计。每 1,000 个 PR 中，Codex 约 1 个被回滚，Devin 3.5 个，人写（或人主导）的约 2.5 个，都很低且在同一量级。按 PR 大小分组（大小代表复杂度），回滚率也很平稳，看不出 Agent 只在做简单任务。
  • Greptile 评论：Greptile 把问题标为 P0、P1、P2（严重程度从高到低）。人写的 PR 反而比 Devin、Codex、Claude 更容易出 P0；P1 也是 Devin 和 Codex 更少；P2 更接近。
  • 评审轮数：常见用法是 Greptile 评审、Agent 修复、再评审，通常两轮就能合入。Devin 平均略多于 2 轮，人 2.2，Codex 2.5，都在同一范围。

他说自己本来坚信 vibe coding 的 PR 不行，一直在找证据，结果没找到。

失败方式不同

他对 Greptile 的评论做了简单的文本搜索，看不同作者的错误类型，只用最近两个月的数据（更早的 Agent 已经过时），数据量在百万 PR 级别。发现包括：Claude 产生 SQL 注入问题的可能性是人的 1.5 倍；Devin 出现认证绕过的可能性是其他 Agent 和人的一半；N+1 查询（循环里逐条查数据库导致查询次数暴增）在 Cursor 里明显更常见。总体质量很一致，但具体错在哪差异很大。

这对代码评审意味着什么

他的样本主要来自有真实客户的大公司，说明商业环境里确实能做大量真正的 vibe coding。他还发现，中位数用户每月不到 50 次提交，第 99 百分位接近 1,000 次，这个规模下人工逐行评审不现实，维护庞大测试套件也不直观。Greptile 因此想做真正自主的代码验证。他说测试、评审、QA 是实现细节，代码验证的目标是回答三个问题：这个改动是否违反用户契约？是否提高了将来违反用户契约的可能？是否实现了作者的意图？做法是用 Agent 评审代码和改动的影响范围（diff 之外可能受影响的文件），再在沙箱里运行代码，用浏览器 Agent 点来点去模拟用户。他说人每天早上醒来审查一整天 slop 的未来很反乌托邦，他宁愿想点子，让机器把它变成商业级代码。

17. Amole（Nori 首席执行官，名字按字幕拼写）：像模型一样思考，让 Agent 用 HTML 做幻灯片和视频

Nori 部署一个了解公司代码、文档、Slack 等数据的“AI 员工”。他说很多人以为编程 Agent 只会写代码，那是营销没做好，它几乎什么都能做，诀窍是要像 Agent 一样思考。这次讲大家以为 Agent 很不擅长的事：做幻灯片、文档甚至视频这类视觉产物。

他给的数字是全世界每天花大约 34,000 人年做幻灯片，大部分时间在摆弄格式，10 小时的幻灯片去掉格式、品牌、挪位置之后应该只要 25 分钟。PowerPoint、Slides、Figma、Canva 都是为人的手和眼睛设计的画布：点击、拖拽、缩放、对齐网格；底下有数据结构，但只有应用自己读得懂。交给 Agent 就会出现元素重叠、文字看不见、没对齐。AI 怀疑者说这说明模型根本不会做空间推理，ARC-AGI 这类基准就建立在这个前提上。他引用 Simon Willison 的经典测试：让每个新模型只用 SVG 画“骑自行车的鹈鹕”，模型给的结果大多很糟。

他说自己一辈子用 PowerPoint 做幻灯片，曾以为“幻灯片”和“PowerPoint”是同义词。其实 PowerPoint 只是工具，幻灯片是演示模式，观众不关心你怎么做出来的，编辑格式可以任选，那就选 Agent 擅长的 HTML，需要 PDF 再导出。Nori 的董事会材料、销售材料、文档都这样做，正在播放的这段视频本身也是 HTML 和 CSS。他也提醒漂亮的幻灯片本身不值钱，内容还得有人去收集，同样可以把通话记录、邮件等数据交给模型，让它端到端地做出来。Nori Sessions 就做这件事，他说自己在地铁通勤时用手机做完过整套董事会材料。结论是：别像用户一样思考，要像模型一样思考，给它对的语言，图形方面 HTML 就够了。

18. Zion（14 年移动端工程师，未报公司）：重新设计移动端开发流程

直播位置 3:23:55–3:32:09

Zion 说几个月前大家还以为会继续用 IDE，只是更好用一点；现在已经转向和 Claude Code、Codex、Cursor 对话式开发，除了调试几乎不打开 IDE。理论上这应该让人效率提升 10 倍，但他感觉不到，个人、团队、公司层面都没有。

他讲了工厂从蒸汽机换成电动机的历史：刚换时提升不大，因为工厂只是换了发动机。过去一台大蒸汽机放在中间，所有机器按耗电和离发动机的距离排列，不按工作流排列；后来人们把电动机做小、装进每台机器里，按工作流重新布置工厂，才有了 10 倍、20 倍、30 倍的提升。他认为 AI 也一样，要改的是工作流。

现在的流程是：产品经理有想法，和设计师迭代，和用户迭代，和开发迭代，回到设计师，再和 QA、开发迭代，最后也许上线。反复出现的词是“迭代”，每次迭代带来摩擦：上下文切换、浪费时间、沟通和同步。AI 加快了写代码，但没有消除这些迭代。他的设想是所有人用一个工具、一个代码库：设计师直接在代码里设计，然后给开发提 PR；QA 拿到一个带模拟器的链接，直接告诉 Agent 测什么、注意什么、发现问题怎么修。

让设计师、产品经理、QA 都装 Xcode 和 Android Studio、学会在模拟器上构建测试，会把他们的笔记本塞满 200 GB 并吃光内存，多数人会拒绝。放进 CI 也不行，CI 构建要 20 到 40 分钟，Agent 不能等 40 分钟才发现 iOS 代码编译失败。他的方案是移动端的云沙箱：给 Agent 一个 CLI，为这次迭代创建一台小虚拟机，30 秒内启动，完成构建，把模拟器显示在 Claude Code、Codex 或 Cursor 的应用内浏览器里。设计师看到改动立刻生效，做完让 Agent 开 PR 给开发；开发可以并行开多台虚拟机迭代；QA 接手，最后直接提交商店审核。他展示了 Codex 里左边聊天、右边应用的画面。他说这样去掉了过去被视为理所当然的摩擦，才能真正提升 10 倍。

从 PowerPoint 到 Shopify

Simon 说他是通过 PowerPoint 爱上电脑的：幻灯片里点击图形跳到另一页，很快就图灵完备了，可以做很复杂的游戏。然后他发现了 FrontPage，有一次误点了 HTML 视图，开始在网上找代码片段，比如改变鼠标样式，然后升级到 Dreamweaver、学 PHP。十一二岁时他读完了互联网上所有丹麦语的编程资料，然后沉迷《魔兽世界》四年，英语因此变得很好。他说如果当时有 LLM 跟他讲丹麦语，他就不会撞墙，也许编程会更好。高中时一位澳大利亚网友在澳大利亚的信息学奥赛（IOI）队，他才知道丹麦也有，就去参赛，做那种算法题，比如 n 辆卡车、m 个包裹怎样装最好这种 NP 完全问题，大家比谁的近似解最好。

2013 年他摔碎了 iPhone，改用诺基亚砖头机，写了一篇文章讲重新打电话、找回方向感，上了 Hacker News，被《纽约时报》转载，一位 Shopify 招聘人员看到后联系他。对方大概没意识到他还在读高中，邀请他去渥太华面试，他在邮件里问“渥太华是什么”。他说走进那栋楼感觉就对了，高中毕业后在 2013 年搬到加拿大。他以为是 gap year，后来没再回去读书。他当时因为没读过计算机而不安，就把每个听不懂的词写在纸上，晚上回家去读，比如别人提到 TCP，他以为对方一定知道三次握手、TLS 怎么叠在上面、看过 Wireshark。他说现在招工程师就看这一点：忍不住要往下剥一层。他总在午饭时坐在基础设施团队旁边，想知道 reverse proxy 为什么叫“反向”，他说到现在也答不上来。

Shopify 的扩展经历和 Toxiproxy

2010 年代 SaaS 公司扩张很快，他在基础设施团队，那时 Docker 刚出来，他们在把一切容器化。公司每年增长很快，每年都在准备比上一年更猛的黑色星期五，而且当时买的是物理硬件，要在某个时间点下单、做插值预测。应用层的扩展问题最后都会落到数据库层，他自然地待在 Rails 和数据库之间。他的老板 Camilo 常说“写入是没法缓存的”，所以到某个点必须分片。他加入时他们在做分片，切换是在黑色星期五前一周完成的。之后几年做多数据中心；有一台 128 GB 内存的神秘 Redis，没人知道里面有什么，某天挂了大家才害怕，开始拆分。

他们还要保证存会话的组件挂了时，整个店铺不跟着挂。他们做了一个矩阵：某服务在某组件挂掉时应该怎样表现，他负责写测试。不能全靠 mock，他曾想用 GDB 附加到进程上关闭数据库的文件描述符来模拟故障，这太疯狂没上 CI，但发现了大量 Rails 里的问题并提交上游。后来他做了 Toxiproxy：一个四层代理，夹在应用和数据库之间，可以用 API 让数据库“挂掉”或“变慢”，后来还加了七层的故障。这样测试的是真实驱动及其故障处理，没有用 mock，整个矩阵可以在 CI 里实现，发现了 MySQL 驱动和 Rails 里几十个问题。他说据他所知 Shopify 的 CI 里现在还在用。

napkin math 和离开 Shopify

他在 Shopify 待了八年（2013 到 2021）。他和现在的联合创始人 Justine 重写了整个 Shopify 店铺前台，开工 18 个月后承载了几乎 100% 的流量。他说很多扩展需求来自卡戴珊家族在 Shopify 上发新品带来的流量。他离开是想再看点不同的东西。

他在 Shopify 时开始了一个 napkin math（餐巾纸计算，用粗略估算判断量级）项目：GitHub 上一张表，大约 50 个数字，由一个 Rust 脚本生成：DRAM 带宽、一次 S3 往返的耗时和费用、NVMe SSD 和 EBS 卷的带宽，以及成本，比如 1 GB 内存约 2 美元、1 GB S3 约 2 美分，现货价、三年承诺价。他给每个格子都做了闪卡，全背下来。起因是他常去评审项目，团队会说“在数据库 A 上做了基准测试，结果不好，所以选 B”，他讨厌这种说法。如果按 napkin math，一个三词搜索查询要读多少 MB、在多核上 100 GB/s 的 DRAM 带宽下应该是 10 毫秒，基准说 10 秒，那要么他理解有漏洞，要么基准测错了，比如没意识到查询分布在 100 个节点上，P99 自然很高。他举了另一个例子：一次 fsync（把数据真正写入磁盘的系统调用）约 1 毫秒，那 MySQL 每秒应该只能写 1,000 次，可他在一台小机器上测到 1 万次。他花了大约 24 小时写 BPF 跟踪去查，发现每次 fsync 比想象的大得多，是批处理。他开玩笑说答案总藏在巴伐利亚某个小镇的人写的文章里，整个互联网都跑在巴伐利亚小镇上。

为什么做 Turbopuffer

他说有三个因素凑在一起。一是他在 Shopify 最后做的项目是搜索，用一个传统搜索引擎（没点名），很难让它达到 napkin math 的性能，表现时好时坏，也难运维。二是 napkin math 让他熟悉“机器用到极致能做到什么”。三是离开 Shopify 后他做“天使工程”：去朋友的公司工作、拿股份，自己不出钱投资。2022 年 ChatGPT 出来后，他在 Readwise（一个保存文章、以后搜索的加拿大自举公司）帮忙，当时上下文窗口只有 4 到 8 KB，很快就得用上搜索。他做了一个推荐引擎，效果好到他在一位联合创始人的信息流上推断出对方妻子怀孕了（他说得到了许可）。但算下来给所有用户用要每月 3 万美元，而公司当时所有基础设施加起来每月约 5,000 美元，毛利对不上，没上线。他一直想为什么存这些向量这么贵，有一天算了一下：能不能全放在 S3 上，做聚类、组织好文件？

2023 年夏天他一直在撞墙，找能达到他想要延迟的方案。S3 的问题是持久性很好但延迟高，256 或 512 KB 对象的 P99（最慢的 1% 请求的耗时）约 200 毫秒，而在 S3 上导航一棵树要多次往返，所以设计时要看 P99 甚至 P999，尽量减少往返次数。七月他做出端到端能用的版本，又重写了两遍，十月发布。第一版是最简单的东西：对向量跑聚类算法，每个簇存成一个文件，再有一个存所有簇中心（centroid）的文件；搜索时先下载中心文件，找最近的几个簇再下载。缓存层也没写，直接在 S3 前面放 nginx 反向代理做缓存，删除缓存就 shell 出去用 xargs 删，靠逆向 nginx 的目录结构。一台 GCP 上 8 核机器里的一个 tmux 会话。他说真正做数据库的人会羞于发布这种东西，他是按 SaaS 的方式发布：有人用再好好做。但他知道它可靠，比如关掉所有虚拟机也不丢数据，所有写入直接提交到对象存储，这些不变式到今天没变。他在 Twitter 上发布时说 100 万个向量 1 美元，之前能用的方案最便宜大约 100 美元。

Cursor 是第一个客户

Gergely 说他和 Cursor 聊过他们的后端迁移：先用 Postgres，又换 AWS Aurora 都不理想，最后用 Turbopuffer。Simon 确认 Cursor 是第一个客户。发布后 Cursor 主动联系，那时 Cursor 大概 8 个人。他猜 Cursor 的创始人在饭桌上讨论过：所有向量放在 DRAM 里，单位经济算不过来，为什么没人做一个放在 S3 上、只把正在用的代码库加载进内存的方案？他说 Cursor 联合创始人 Aman 早期就发推讲过用 S3 做 KV 缓存。他不懂 B2B 销售，只想帮忙，就从加拿大飞到旧金山去 Cursor 办公室，正赶上他们在讨论 Postgres 问题，他问有没有 PG Analyze，没有就装上，一看还是老问题：autovacuum 跑得不够。他说这建立了信任，帮得了数据库，也许也造得了数据库。当时 Justine 已经加入，第一件事是把 nginx 缓存换成直接的文件缓存。Cursor 当晚决定迁移，一两周内迁完。他承诺把账单降 95%，做到了。Gergely 补充说，Cursor 的 Sualeh 对他说过：永远不要把公司押在一家你是唯一或最大客户的小创业公司上，Turbopuffer 除外。

和黄仁勋的会面，以及 CPU 也开始短缺

在 NVIDIA 总部的一次活动上，几家公司向黄仁勋和 NVIDIA 高管介绍业务、找合作。他上台紧张，说“如果你们好奇名字，万一业务不行，我们可以转行做电子烟（puffer）”。黄仁勋回了一句“看你的幻灯片，也许你该转”。他不知道怎么接，就问“Jensen，你抽电子烟吗？”对方没回答，团队里有人立刻在公司群里发“Simon 刚问 Jensen 抽不抽电子烟”。团队事先叮嘱他别说“C 开头的词”（CPU），结果他停不下来，一直讲 AVX-512 多好、他们爱 SIMD、CPU 多好买。

Gergely 问 CPU 是不是很好买，Simon 说不再是了。他认为 GPU 会持续紧缺，而强化学习（RL）正在成为很大的工作量：要教模型搜索、用 grep、启动 bash，模型需要在真实环境里运行并学习，这要大量 CPU，实验室在大量吸走 CPU；所有 Agent 也跑在 CPU 上。应用越多，越发现模型在 CAD、造船之类上不行，又要开更多 RL 环境。他们还需要大量 NVMe SSD，DRAM 也紧张。他预计 CPU 方面会先变得更糟再好转，大公司之间在争配额，他们甚至在和自己的客户争 CPU。Gergely 说前一天在 Simon 办的客户晚宴上，Reflection 的人告诉他已经签了最长的合同、买不到更多。Simon 说最后是电力问题，新 CPU 会去有电的地方。Turbopuffer 的优势是只需要一些 CPU、NVMe SSD 和 S3，能跑在很多种 SKU（云厂商的机型规格）上；他现在喜欢 GCP 的 C4、Z4D 和 ARM 的 C4A。

对风险投资的看法：融资的六个理由

他说一开始承诺 Cursor 每月 4,000 美元，是按“如果 Turbopuffer 实现得更好应该花多少”估的，当时软件很简单但可靠，他把简单视为最重要的工程原则。他起初不确定这是不是适合风投的机会：拿了风投，不管饭桌上多少笑脸，大家都期待在一定时间内有大回报，背后还有加拿大的养老基金等一整串出资人。他只是看着 Cursor 的账单和 GCP 账单，觉得前者应该大于后者，和 Justine 一直优化到差不多持平，再接几个客户就能给自己发工资。

他想招 IOI 时认识的 Bojan（北马其顿队，队友叫他“上帝”），但付不起工资：他和 Justine 已经半年没拿工资，还自掏几万美元付 GCP 账单。于是他打电话给硅谷唯一认识的投资人 Lachy，说想融 70 万美元，够雇两个工程师到年底，他俩继续不拿工资；如果年底没有产品市场匹配（PMF），就关掉，钱全数退回。他说别的 VC 听到这种话会害怕，在西海岸听起来像没野心，但他不会玩的游戏就明牌打。他们招了 Bojan 和 Morgan 作为头两个工程师，当年晚些时候就盈利了。

他列了融资的六个理由：一是资助研发；二是资助增长；三是创始人的自尊，他说这很普遍也很危险，会稀释所有员工、给未来员工的上行空间定价，变成地位游戏；四是回报员工；五是战略合作；六是并购。他们第一次融资是为研发，去年 12 月那次是为了让员工能提前变现部分股权。

全员远程和“营火”

Turbopuffer 2023 年成立时一直是全远程。Simon 说做数据库公司能快速成事的城市大概只有旧金山和纽约，不去那里就要全心投入分布式模式。他们每年两次全员线下聚会（今年去了某地，字幕不清，还有墨西哥城）。他们有“营火”（campfire）机制：几个人凑巧在某地，就宣布一个营火，欢迎任何人来，这周就是旧金山营火，一起见客户、办客户晚宴。不想出差的人只参加两次聚会也完全可以。有一次纽约有营火，一位同事看大家在纽约会议室连线，太羡慕，直接从渥太华打车去机场飞了过去。他们还有 turbo credit：做会议演讲、写博客或在展台站两天，就得一个，可以把下一次航班升到商务舱，有人已经在讨论给它建央行、定利率、开预测市场。Gergely 最后说，这场对谈很少谈 AI，谈的是工程原则、好奇心和人与人之间的信任。

20. Nishan Gupta（Meta 软件工程技术负责人）：Agent 系统的生产环境评测

直播位置：开头片段 4:30:03；较完整的一次 6:40:42–6:46:20（预录视频，两次都没播完）

Nishan Gupta 在 Meta 为 Meta 超级智能实验室和基础设施组织构建训练和推理基础设施。他说提到评测，多数人想到基准：模型得 90 分，新版本 92 分，团队庆祝。但 Agent 系统改变了评测的含义：它们规划、调用工具、检索信息、执行工作流、和生产基础设施交互，问题从“模型答对了吗”变成“系统行为正确吗”。离线基准不断进步，生产可靠性却难以预测，原因是基准衡量模型能力，生产衡量系统行为；基准不包括工具失败、API 故障、上下文变化、用户差异、长时间工作流，系统越自主，差距越大。行为包括规划质量、工具使用、工作流执行、从失败中恢复和决策，所以要从评测答案转向评测工作流。

他说很多团队以为幻觉是主要的失败模式，在生产中它只是其中一类。他给了一个失败模式的层级：底层是记忆失败、检索失败、安全失败；往上是推理错误、规划不当、工具执行错误；最高层是多 Agent 协调失败。只评测模型输出，会漏掉大部分生产风险。他建议像 SRE（站点可靠性工程师）一样思考：衡量可靠性、可用性、延迟、成本、恢复能力，可靠性是北极星指标，准确率只是一个输入。

他把评测体系画成金字塔：底层是基准，可扩展、可复现，但运营价值有限；中层是基于场景的评测，模拟真实工作流；顶层是生产遥测，价值最高的信号来自真实用户与真实系统的交互。离线评测仍然重要，但应该按场景（客服流程、代码生成流程、研究流程）而非按提示词设计，在模拟环境里测任务完成率、工具正确性、规划质量和资源用量（规模大时资源用量增长很快）。系统上线后每次交互都是信号：执行轨迹、用户结果、升级、失败、反馈，生产是组织拥有的最大、最有代表性的验证数据。他说把人当成兜底系统是错误的定位，人是评估者，能提供自动化给不了的正确性、信任、有用性、安全判断，用来校准评测流水线、发现自动指标的盲区。讲到 Agent 系统会持续漂移（模型每几周更新、提示词、工具、用户行为都在变）时视频被切走。

21. Kevin Hou（Google Antigravity 工程负责人）：随智能扩展，2026 年的 Agent 原语

直播位置 4:31:50–4:49:34（字幕把名字听成 Kevin How）

Kevin Hou 用世界杯开场：带阿根廷踢到第 89 分钟，有梅西，就把球给梅西然后让开。他说 LLM 已经能当你的明星球员，前提是围绕它做对产品，然后别挡它的路。Antigravity 是 Google 面向技术和非技术用户的 Agent 编程产品，2025 年 11 月发布，一直“毫不掩饰地 Agent 优先”。去年推出 Antigravity IDE 和全新的 Agent Manager（管理和编排多个 Agent 的平台），之后把 Agent 抽出来做了 Antigravity CLI；上个月在 Google I/O 发布 Antigravity 2.0，把 IDE 和 Agent Manager 拆成两个独立应用。他展示的 2.0 界面里有子 Agent、新模型、worktree、定时任务、语音模式。这是他第五次在 AI Engineer 演讲，他从 2022 年开始做开发者工具。

随智能扩展

他说最重要的一课是“随智能扩展”：模型变好，产品也要变好，前沿模型的能力要能在用户的产品体验里看出来。他回顾了这几年的转变：2022 年做自动补全和聊天侧栏，基于 embedding、规则文件、语法树解析，几乎都是确定性的，因为模型只能做这么多；2024 年 Agent 出现，带来 MCP、自定义工具、权限系统；2025 年 Antigravity 推出 Agent Manager，用户同时管很多 Agent，带来技能（skills）、钩子（hooks）、产物（artifacts）等原语。

他说随智能扩展很难，要拿走用户喜欢熟悉的东西，引导他们走一条“可能更好”的路，他们也不总是对的。两个例子：一是给 AI 终端权限，大家当年害怕它删掉整个代码库，后来有了权限系统、模型变聪明，用户反而做得更快更安全；二是当年在 Windsurf 移除聊天侧栏只保留 Agent，被用户骂得很惨，现在多步 Agent 研究和执行已是主流。现在的“战役”是把 IDE 和 Agent Manager 拆开。他的比方是：IDE 之于 Agent Manager，就像调试器之于 IDE，不总需要，但要往下钻一层时有它很好。他们押注 Agent 编排（叫 Agent 团队、蜂群或软件工厂都行）是未来。

Agent 团队和 Gemini 3.5 Flash

他说在 Google DeepMind 内部，产品和模型之间有研究与产品的飞轮：Antigravity 1.0 的核心是并行管理 Agent，因为这个产品，Gemini 学会了一些管理 Agent 团队的本事，虽然多 Agent 系统在协作和任务拆解上还有很大空间。四月发布的 Gemini 3.5 Flash 把这些能力带到市场，它擅长执行，也擅长领导团队，更快更便宜，推动了智能与速度、成本之间的帕累托前沿。他们宣布 Antigravity 的 Agent 团队进入公开预览：输入 /teamwork 进入新模式，你描述任务（越具体越好，不清楚时它会问你），和主 Agent 合作，主 Agent 管理一个任意规模的团队，动态生成前端、后端、基础设施、QA、设计等专长角色，每个子 Agent 独立运行，主 Agent 还可以给子 Agent 选不同的模型。因为 Flash 快，它能即时生成界面：问任务状态，它可以给你看看板，或者像 Chrome 调试工具那样的时间线。

系统做过的项目有：在浏览器里直接编辑 RAW 照片的编辑器、一个眼熟的聊天应用，每个用了几百个子 Agent、跑了大约半天。最重的一次是从零写一个操作系统内核并在上面跑 Doom，在 Google I/O 上由同事 Varun 演示过：93 个子 Agent，12 小时，15,000 次请求，20 亿 token，花费不到 1,000 美元。

内部例子：自动化并排评测

他们帮 Gemini 提升编程和 Agent 能力，内部有一个 Antigravity 版本给研究员、工程师和非技术人员用。并排评测（side-by-side eval）在 DeepMind 和业界都很常见：对一组任务做多次 rollout（让模型完整跑一遍任务），得到对照组和实验组两张表，然后找出差异、原因、下一步怎么改。以前这要在 Jupyter 里大量手工。现在研究员用自然语言问 Agent，加载了技能、熟悉 Google 巨型单体仓库的 Agent 算出差异，然后多走一步：启动一个研究专家 Agent，提出 100 个可能原因的假设，为每个假设开一个子 Agent 并行深挖，汇总成一份报告，并生成一个可交互的界面让研究员下拉、筛选、切片数据。他说研究员自动化了这个流程的 90%，原来很手工的事现在几分钟完成。以前要自己搭异步 Agent 池、设评判模型、拼数据管道，现在用户只要加载一个技能文件然后提问。

2026 年的三个原语

  • 动态子 Agent：没有两个子 Agent 是一样的，主 Agent 自己配置、提示、播种它们，它们可以并行，在沙箱或远程执行系统等不同安全环境里，承担无限种专长角色。模型越聪明，团队越专业、越会协作。
  • Sidecar：一个新的插件协议。sidecar 进程是长期运行的工具，负责监听外部世界，让模型自己设置触发器，比如短信、webhook、cron、GitHub PR。Antigravity 的定时任务底层就是 sidecar。他们会在今年夏天晚些时候发布规格。
  • 生成式界面（Generative UI）：他们认为人手写的专用界面基本过时了。Antigravity 上的 Gemini Flash 接近每秒 900 token，比很多前沿模型体验快 10 倍，几秒钟就能把你的想法变成嵌在对话里的界面，直接内联渲染，不依赖模板或 HTML 文件，可以玩 Doom，也可以是柱状图、表格等。他引用 Steve Jobs 发布 iPhone 时讲去掉实体键盘的话：那些键盘和按钮不管需不需要都在那里，“固定在塑料上”。他们的产品随 Agent 的需要动态伸缩，用 sidecar 和生成式界面代替沉重的基础设施和机械式界面。

他的建议是：做围绕 Agent 的产品，要想清楚产品里的原语是什么，它们怎样随模型智能扩展。现在加功能很容易，难的是决定加哪些，好让产品能随下一个更快、更好、更便宜的模型一起变好。他说在 TPU 紧张解决之前他会一直用那张求 TPU 的幻灯片。

22. Dominik Tornow（Resonate 创始人兼 CEO）：规格说明才是产品，用确定性仿真让 Agent 参与设计

直播位置：开头片段 4:49:34（约 3 分钟后被切走）；完整的一次 7:03:12–7:21:22（预录视频）

实现可以生成，价值移到规格

Dominik Tornow 开场预言：2026 年编程 Agent 会悄悄让第一个软件平台退休，原因是它变得不必要了。Resonate 是一个持久执行（durable execution）平台，持久执行是指让函数调用在进程崩溃、重启后能从断点继续，不丢状态。他说 Resonate 以极简和简单为核心技术价值。他们的判断是：通用实现会越来越多地被按需生成的定制实现取代，这些定制实现会以已有基础设施的最小扩展出现，不会再是一个新的库、框架或平台。如果成立，复用就会往上游走：复用的是规格说明，从它派生出定制实现，可以为每种已有基础设施生成多个。“提示词就是平台。”

Resonate 有服务器实现和 TypeScript、Python、Rust、Go、Java 的 SDK。如果实现能生成，价值在哪？他们的答案是从实现移到规格：产品是规格和协议。从协议派生多个服务器实现，一个是通用的参考实现，其他是和基础设施伙伴一起做的，让客户在现有基础设施上用持久执行、几乎不加依赖。问题变成：能不能反复从同一份规格合成可信的服务器？他说谈 Agent 工程时大家都盯着验证，他想讲规格，以及 Agent 怎样参与制定规格，在构建和验证之外。其中一个伙伴是 Synadia，开源消息系统 NATS.io 背后的公司，后面用 Resonate on NATS 举例。

第一次尝试：直接从抽象规格到实现，失败

常见的 Agent 编程模型是：Agent、规格、实现。但他们要从一份规格生成多个针对不同目标的实现，所以规格不能带任何实现假设：不能假设数据库表结构、索引，不能假设是关系数据库，不能假设是键值存储，不能假设弱一致或强一致。规格必须抽象，只有实现是具体的。第一次他们让 Agent 按抽象规格，用 Rust 在 Postgres 上写一个 Resonate 服务器，失败了：抽象规格和具体实现差距太大，做出来的东西在正常路径上能跑，基本测试也能过，但不正确，遇到并发、进程故障、网络故障就坏，更像原型。

于是他们加了一个中间产物：具体规格。它和 Agent 交互着写，但人是主导：把针对目标的决定写清楚，包括表结构、索引、SQL 查询、事务边界。写下来之后，Agent 能实现出生产系统。这暴露了局限：Agent 帮他们建了系统，却没有帮他们设计系统。如果规格是可复用的产品，这不够，Agent 必须往上游走。

第二次：先在确定性仿真里设计

做 Resonate on NATS 时，他们换了问题：Agent 需要什么，才能先设计、再构建？他们给 Agent 一个确定性仿真测试环境（DST，Deterministic Simulation Testing，把并发、故障等都放进可控、可重复的模拟里测），并换了任务：不要建生产系统，先建一个仿真实现。仿真实现本身不交付，他称它为“可执行的设计”，目的是在部分有序、部分失败的条件下找出正确的算法。算法在仿真里找出、测好、验证后，再让 Agent 写具体规格，再写生产实现。流程变成：抽象规格、仿真实现、具体规格、具体实现。人仍参与设计，但这次 Agent 是主导。

他说这能成立靠两点：极简和简单。这两点是做出来的结果，他们花了三年把协议做小做简单，每遇到问题就问能拿掉什么抽象、什么属性、什么关系。结果协议只围绕两个对象：持久 promise 和持久 task。即使这么简单，并发分布式协议的状态和行为空间仍然复杂。

NATS 提供的原语有：队列、键值存储、延迟或定时消息。这些是目标平台自己的概念，Resonate 里没有，设计问题是怎样只用这些原语表达 Resonate 协议。以键值存储为例，它带版本：创建 key 值为 foo，更新为 bar，再更新为 baz，最新值是版本 2 的 baz。大多数时候读到的是最新值；但有时读会是陈旧的，返回版本 0 的 foo。数据没有损坏，存储也没有 bug，在目标平台的一致性模型下这是合法的读。实现不能只在目标表现方便时才正确，要在目标表现合法时都正确，所以仿真环境必须暴露新鲜读、陈旧读以及版本信息。光读是看不出陈旧的，要等写时才发现：读到版本 0，就按版本 0 去更新，但 key 已经前进了，写失败，这就是目标在告诉你“你看到的世界不是当前的世界”。这种乐观并发控制（只有你读到的版本仍是最新时写入才成功）之上要写出永远正确的程序，对人对 Agent 都不简单。

“禁果”：给 Agent 看算法不能看的东西

Agent 需要即时、明确的反馈，光知道“出错了”不够，还要知道为什么、怎么错的：返回了哪个陈旧值、触发了哪段逻辑、哪次写失败、哪个不变式因此被破坏。他们用 Python 写了确定性仿真环境，模拟了依赖的 NATS 部分。仿真的键值存储为每个 key 保留完整版本历史，get 有时返回最新版本，有时由确定性随机数生成器控制返回旧版本；update 强制乐观并发，版本不是最新就抛异常。它在对正确性有影响的方面和真实存储一样，但是确定、可重复、可检查的，Agent 写错算法时可以复现那次执行，对着那条轨迹修。

仿真还能暴露真实平台隐藏的事实，他们叫它“禁果”。生产中读键值存储只能拿到值和版本，不知道这次读新鲜还是陈旧，也看不到错过的最新值，真实代码也不该依赖这些。仿真里每次 get 都会发出一条轨迹事件，标明这次读是新鲜还是陈旧、拿到什么、最新值是什么。例子里，生产代码只看到 promise 处于 pending；仿真另外记录了这是一次陈旧读，以及被隐藏的最新值显示这个 promise 已经 settled。算法不能用这个信息，但 Agent 可以用它解释自己设计的算法为什么错：不变式失败是因为算法基于陈旧的世界做了决定。因果关系变得可见。靠这个方法，Agent 先在仿真器里做出用模糊测试验证过的概念验证，再派生出已知算法正确的具体规格，最后派生出实现。他的结论：“提示词是平台，规格是产品。”

23. Zach Lloyd（Warp 创始人）：自我改进的软件工厂与开源

Zach Lloyd 曾是 Google 的首席工程师，领导过 Google Docs 套件的工程，做了 20 多年工程师。他说自己仍然频繁发布，但过去六个月没写过一行代码。Warp 是一个开源的 Agent 开发环境，起初是内置 Agent 的终端，几个月前开源，GitHub 上超过 6 万星，几百位贡献者，超过 80 万活跃开发者。现在他们更关注怎样自动化开发。

软件工程会变成工厂工程

他的论点是：软件工程这门学科会变得更像工厂工程。开发经历了聊天和 AI 补全（Cursor、Copilot），到现在的交互式 Agent（坐在电脑前告诉 Claude Code 或 Warp 做什么），他认为接下来六个月到一年会走向自动化。他现场问了几个问题：几乎所有人在用 Agent，几乎所有人同时用多个 Agent；在云上跑 Agent 的不到一半但不少；搭了系统自动化整个开发生命周期（分诊、写规格、实现、评审）的有一些人。他认为每个有规模的项目都会有这样一个大循环：想法从顶部进来，Agent 分诊，复杂的写规格，人审规格，Agent 实现，人和 Agent 一起审代码，Agent 验证，人审产品，上线，监控，周而复始。他说循环没什么复杂的，这个循环写成“云端软件工厂”或者就写“软件开发生命周期”都一样。软件工程师会成为建造和管理这些工厂的人。

开源和公开的工厂

Warp 开源的一个主要原因是建一个公开的工厂。他展示了 build.warp.dev，上面显示系统里每个 issue 的状态、哪些 Agent 和贡献者在处理，他说这是大规模运行的“原型工厂”，并不完美但在运转。他说做软件越来越便宜，推论是克隆软件越来越容易，竞争对手能克隆，就很难捕获价值。他开玩笑建议“先给代码申请专利”，马上说是玩笑。他的真实建议是：产品好一直是必要的但从来不够，现在更不够，需要产品之外的优势：分发、生态、品牌、数据护城河、资本；创业公司通常没有这些，公开构建是一种突破方式，能建生态，让你在 Hacker News 上从被讨厌变成被容忍，提升品牌，形成社区。Warp 封闭构建了五年才开源。传统的开源痛点有：大量噪音 issue、草率的 PR、陷入代码评审地狱、花大量时间验证改动。让他们下决心的是建了一整套自动化，也就是一个围绕开源项目的软件工厂。

工厂的组成

有效的软件工厂需要：一组自动化；提供上下文和技能的方式；在合适时机（东西卡住时）引入人的方式；自我改进能力，也就是循环。他强调开源没什么特殊，每个有规模的项目都能受益，他预测每家公司、每个开源项目的核心都会有一个软件工厂，就像 CI/CD 后来变成理所当然。工厂车间是一个步骤图：

  • 输入：想法来自团队或用户，通过任务跟踪系统、Slack 等沟通渠道、终端或 IDE、监控系统进入。
  • 分诊：Agent 看新进来的 issue，简单且无歧义的就直接实现，他说这是启动工厂的方式。
  • 写规格：难的 issue 让 Agent 写规格，Warp 的做法是产品规格（描述要达到的产品不变式）和技术规格（描述架构和代码形态）。现场举手用规格驱动开发的人不少。
  • 实现：在云上跑的编程 Agent 产出 diff，可以用各种编程 Agent。
  • 评审：他说这是最痛苦的部分，大家可能都审 Agent 的 slop 审累了。先让 Agent 评审，然后慢慢变成风险管理：什么时候引入人。
  • 验证：比如对界面类应用用电脑使用实际操作，产出视频和截图；CI/CD 照旧。
  • 监控：上线后 Agent 继续观察是否崩溃、是否被使用，把结果送回工厂顶部。

他提到朋友 Adam 当天讲过 Uber 内部建了一个这样的系统。他认为多数组织能轻松搭一个简单版，但要真正规模化需要很多东西，最好专注自己的产品。建或买都会得到类似的结构：顶部是把工作送进工厂的各种入口；控制平面决定工作怎样分配；执行的地方是云沙箱，以及选哪个 Harness 和模型；底下是数据平面，让 Agent 记得做过什么、学习、改进。

工厂也是一种心态：要度量和改进效率，发布了多少软件、花了多少人工时间和 token。循环就是让 Agent 观察自己哪里失败并改进。常见的是技能循环：工厂里的 Agent 用技能干活，观察者 Agent 看这些技能怎么被用、找问题、改进技能。比如代码评审 Agent 留了评论，资深工程师去纠正，观察者 Agent 应该看到这些并改进下一次评审。他说工程师的乐趣如果在写代码，会写得更少；如果在发布产品，现在是最好的时候，他自己就是后者。他称之为元工程：怎样把 Agent 系统工程化成最好的工程者。他给了一个开源仓库的二维码，用 Warp 的 Agent 平台演示怎样搭分诊、写规格等工厂 Agent，但说不一定要用他们的产品。

问答

  • 建议别自己建工厂又说要建，是否矛盾？他说每个人都会部署某种工厂，但调校它（技能是否适合你的领域、是否在按对的方式构建你的产品）仍有很多有意思的工程问题，同时应专注核心产品。
  • 如果是现在毕业的大学生该学什么？他说是适应力、批判性思维、学习速度；理解底层系统和架构、能读懂代码和 Agent 写的规格仍然很有价值。Warp 现在招的人比以往都多，他没看到“因为 AI 不招人”，他找的是适应力强、以产品为导向的问题解决者。
  • 产品品味和想法从哪来？他承认工厂比喻听起来机械、去人性化，但唯一重要的是做出有用的东西，工厂产出没人在乎的东西就没有意义，人的品味、产品感、在不能自动化的节点上的引导必不可少，他自己做的就是弄清客户要什么。

26. Starite Search 联合创始人兼 CEO（公司名和姓名字幕均不清）：用户信号死在检索边界上

直播位置 5:40:19–5:49:34；开头部分在 7:21:22 重播（预录视频）

他把 Agent 定义为有能动性的 LLM：推理、调用工具、与真实世界交互、检索记忆来完成任务，并说其中缺了一个循环：学习，即从什么有效、什么无效中学习。他用 ReAct Agent 解释：ReAct 是“推理加行动”交替进行的经典架构，用户提示后 Agent 在循环里执行、调用检索器搜索，任务完成就停。缺的是让 Agent 从结果中学习。

他引用了几条数据：麦肯锡 2025 年报告说 85% 的 AI 项目失败；73% 的 RAG 流水线失败原因在检索，不在生成，以及上下文塞得太满；Pinecone 一位前高管（名字字幕不清）发帖说我们一直在优化错的东西，让错误答案出现得更快更便宜，却忘了让检索学习。他说 Agent 没有“对结果负责”：评测和行动之间缺了一层。可观测性系统记录了每次工具调用、每次补全、每个异常；评测套件判断最终输出对不对；但这些结果没有反映到 Agent 的上下文、技能、MD 文件或行动里，Agent 不知道昨天的运行为什么通过或失败，评测信号死在仪表盘上。于是有了“人工改进税”：工程师坐下来看评测和可观测性数据，改提示词，重新部署，换更贵的模型，改 Harness，或者微调。

现有的记忆系统主要存用户偏好、档案、对话历史、长期个性化，没有为生产环境里的自我改进学习而设计。他提到 LangChain、Mem0 等方案抽取事实偏好，检索信号是 embedding 相似度，不从结果中学习。他们提出“效用分”（utility score）：用这条记忆在历史上对完成任务是帮了忙还是添了乱来加权语义相似度，结果成为检索重排的一等信号。他们的产品叫 Agent RX（agents with runtime experience），是一个运行时层，让生产中的 Agent 不靠预训练、微调或人工调提示词就从经验中改进。他说这和 DSPy 这类“编译时”方法不同，DSPy 是把经验烘焙进提示词，他们是在执行中改进。他们把记忆当作推理而非事实：客服机器人除了记住“用户喜欢深色主题”，还会记住“有人要退款时，先检查结算状态，避免重复退款”这样的推理。

基准方面：在衡量 Agent 是否遵守政策的 τ-bench 上，表现从 66% 提到 76%，加上技能后到 80%。积累到大约 10 条记忆后，他们把推理和理解烘焙进技能，让 Agent 保持更新。他举例：一个 SQL Agent 的系统提示里写着某个早已没用的列，没有机制去更新它，用技能就可以。在 Humanity's Last Exam 这类 Agent 任务上，基线 35.7，加 RAG 47.5，另一种记忆系统 58.2，他们的 61.3；他说在 BigCodeBench 等其他 Agent 基准上趋势类似。

27. Sarah（Notion AI 工程负责人）：Token Town，怎样不因为 AI 变穷

直播位置 5:49:34–6:12:08

她开场先让后排的人坐到前面来。她领导 Notion 的 AI 工程团队，也负责谈 AI 采购合同，团队开玩笑说她像 Anna Wintour，她放了一张 AI 生成的自己顶着 Wintour 发型的图。题目是怎样从“AI 狂热”走到“不因 AI 变穷”，在做软件工厂的同时做到可持续。她展示了 Notion 2026 年 AI 用量的增长。

她说你从原生做模型的人那里买 token，永远是坏交易：对方用自己的成本做第一方产品，你却要加价买 token、再加价卖出去，绑定一家就没有退路。她引用 SemiAnalysis 的 Dylan Patel 的帖子，对比前沿实验室第一方订阅和 API 价格的差距，劝大家别玩这个游戏。应用公司该赢在产品：建数据飞轮，比谁都懂客户，知道什么时候要能力、什么时候要低价、什么时候要低延迟（她说你不总需要最慢也最强的模型），以及好的界面和编排。“下注在前沿，不要下注在某个实验室。”

她引用 Citadel 两周前的一份备忘录：对整体经济，更简单的模型可能是性价比最高的生产力提升路径，前沿任务和日常任务会分化。什么算前沿、什么能力已经饱和，取决于你对自己产品的专长。流量也分轻重：Notion 上做大规模数据分析会推荐 Opus，但给邮箱分诊也收 Opus 的钱就是在坑客户和自己。她说前沿模型市场基本是寡头，大家在冲顶，这本身重要；但定价激励是：最好的模型可以对“AI 以前做不到的事”随意定价，紧随其后的只要每百万 token 便宜一美元就能拿下剩下的市场，像挨在一起的加油站，所以价格和能力增长并不对应。她还说，看到应用公司大肆宣传和某一家实验室绑定，她会警觉，因为最强模型的提供方每个月都在换，为了更大的折扣绑定一家，有一半时间你的产品不是前沿的。能随时走开的选择权才是筹码。

三条出路

  • 保持模型无关：Notion 一直提供最先进的模型，同时有一个 Auto 模型处理约 75% 的流量，用户也可以选，避免被厂商锁定，她们叫“AI 瑞士”。她的模型无关手册：为多模型构建（中途换模型会让缓存失效，这很难，但 Harness 要按可互换来设计）；看“每单位能力每秒的成本”，光看 token 价格不够，比如她们和 Parallel 合作网页搜索时，单次调用的延迟或价格 Parallel 不一定最低，但按完整搜索轨迹评测就不同；切换要快、要常；回馈实验室，她们的评测和早期试用合作对前沿实验室有价值，可以用来交换，不必签巨额承诺，她认为折扣不值得失去选择权。
  • 中等任务用开放权重模型：她说开放权重已强到能处理这些任务，在其上做 RL 也扩大了它们能覆盖的范围。开放权重降低了客户的成本门槛，也给了谈判筹码，在寡头格局下形成价格下行压力。她说 Kimi 2.6 大概是第一次看到开放模型超过 GPT-5.2，现在 GLM-5.2 又来了。她借用 Baseten 的 Philip 的一张图说明：开放权重不必是第一，差距总会被追上，今天够用的任务六个月后多半能被开放权重覆盖，现在就要准备好。
  • CPU 优先于 GPU：Notion 最近推出 Workers。很多工作是运行确定的代码，把 CSV 转成 PDF 不需要 LLM，有 CLI 就不需要 LLM 去调 Notion 工具，确定性的 SQL 查询更不需要，人就是在这些地方很快变成 token 穷人的。

28. Vaibhav（BAML）：用 slop 对抗 slop

直播位置 6:19:38–6:40:42

Vaibhav 先亮出团队的工程实践：不做代码评审，要求每个工程师并行做多件事，不统一大家怎么用 AI。他说大家可能以为他们是 Z 世代的 YC 创业公司，其实他是千禧一代。他们三年前开始做的是一门编程语言 BAML，最容不得 slop：每次都必须完全一样地工作，不能一年后因为设计失误就改。他说三年来一直在和 slop 打仗，导师教他“要打败 slop，就要成为 slop”。他对 slop 的定义是任何你没读过的代码，并提醒大家现在就是你代码库里 slop 最少的时候。

标准、设计和架构三场仗

  • 标准：好工程师没法被命令，有人用 Claude，有人用 Codex，有人用 Hacker News 上刚看到的新工具。他们不在代码库里强加标准，写了一个 ARCHITECTURE.md，没用 CLAUDE.md 这个名字，选的是所有模型都懂的名字。它必须很短，只放几个月甚至几年不变的东西，对他们来说是编译器的分层。要深入编译器时，就告诉 Agent 至少先和一个人谈谈，让它慢下来一点。
  • 设计：团队规则是“代码可以是 slop，文字不行”。工程师当然不会手写所有东西，所以他们做了一个设计文档工具，代替 Notion 和 GitHub 管设计文档，有版本和评论；又做了一个 Slack 集成，设计文档一更新就在频道里通知，结果这个频道成了公司最热门的频道，凌晨 2 点有人发新文档，三个人立刻去读，因为不会再变的设计文档最有意思。底层都是 markdown 文件和简单的 CLI 脚本，像 GitHub 又不是 GitHub，所以 Agent 也能用。后来他自己陷入“AI 精神病”，一天发 10 篇设计文档，团队开始对抗他的 slop，于是加了最后一条规则：发设计文档必须要求别人真的去读。之后设计文档质量很高。
  • 架构：他们做了一个工具可视化内部依赖图（也包括部分外部依赖），观察代码库的变化，有语义边界和独立的包，再写 CLI 工具保证某些不变式不能被破坏。Claude 新建一个包或加了一个泄漏边界的依赖时，CI 或提交历史会准确指出哪里坏了。他说他们的架构三四个月没变过。

让 Agent 不停地写 BAML 程序

他问大家敢不敢不读代码就发布，何况编程语言有泛型、闭包、内存分配、FFI 边界这么多不变式，Python 25 年后还有 bug。他们的做法是让 Agent 持续地从零写 BAML 程序，然后看完整的 Claude 对话记录：用了什么工具、发生了什么。人可以看，更重要的是 Agent 也去看，找出哪里好、哪里不好，包括语言里不对的地方，也包括本该一次工具调用却用了三次的地方。人和 Agent 一起判断哪些问题是真的、哪些是幻觉、哪些没品味，然后 Agent 去修。再进一步，对语言特性做 A/B 测试：哪个版本工具调用更少、错误更少、结果正确，确定地知道哪个好。他说没写一行代码就能建立数据驱动的系统；八个人不到两年做一门编程语言，换成以前要几万人时，而且还会是坏的，现在花几十亿 token 就能让它稳定。

地基本身有 slop：TypeScript 的例子

但他认为这场战争还是会输，因为我们依赖的地基本身有问题。他说 TypeScript 的主要设计目标是在正确性和生产力之间取平衡，这里的生产力指人的生产力；如果设计时假设人永远不写代码，有些东西绝不会放进语言核心。他现场写了几段代码让大家猜结果，比如 JavaScript 排序时会先把元素转成字符串。他说这是烘焙进语言里的 slop，他的 Agent 也“很爱”这些地方。JavaScript 之后人们在上面叠了 CoffeeScript、TypeScript，现在又有 Effect，底下的东西已经坏了，而且我们写代码的方式也变了，所以他认为需要一门新语言。

BAML 演示：为 Agent 设计的工具

  • 代码可视化：看代码时看到的是一张可视化图，点击跳到对应代码行，可以放大、展开语义边界里的部分，也可以决定“这部分是 slop，就让它是 slop”，只选择读你关心的部分。
  • 执行轨迹：在不读所有代码的世界里，理解代码的方式是看执行轨迹，看每段时间花在程序的哪个部分。他说在 Python 或 TypeScript 里全程追踪会慢到不可接受，从第一性原理设计可以做到几乎零性能开销；每个文件都有 Claude 能浏览的追踪系统，它能自己找 bug、错误和低效之处去优化。
  • 面向 Agent 的检索：他说 grep 不该再用，ripgrep 搜 calculate 会给一堆结果；BAML 可以直接“描述 calculate”，返回文档字符串、源代码和所有被使用的位置，多次工具调用变成一次；外部库也能这样查，不用上网搜。他说代码是唯一的真相来源，文档和 README 会撒谎。
  • 每个函数都是 CLI：写一个 add 函数，它自动成为带 a、b 参数的 CLI 命令，可以打包成独立的二进制，跨 Windows、Mac、Linux 和 WASM，Agent 不用操心部署。
  • 错误处理：他说 Agent 写 TypeScript 会一层层嵌套 try-catch，最后放弃，打一行 console.log 了事。BAML 里 divide 会抛除零错误，函数本身知道它会抛这个错误，调用它的 calculate 也自动知道，错误类型自动推断。这样编译器能证明你是否穷尽处理了错误；你想发布一个保证不抛异常的 API，编译器会指出还有两个错误没处理；在 parse 里捕获异常返回 0 之后，它被证明不再抛除零错误。他说人不信任 LLM 写的代码，是因为底层系统不够刚性。
  • 和现有语言互通：不用重写所有代码，每个 BAML 函数可以从 Python、TypeScript、Rust、Go、Ruby、Java 里直接以类型安全的方式调用，还自动有 async 版本，BAML 本身没有函数着色（同步和异步函数要分开写的问题）。甚至可以把 Python 的 lambda、泛型、闭包跨语言边界传过去，比如一个 with_timeout 函数。类型系统成为阻止不变式被破坏的真相中心。

他说前一天有工程师纯用 BAML 写了一个部分的 C 编译器。他用 CI/CD 作类比：引入时会慢三个月，之后快得多，流程必须进化才能跟上 Agent 的速度。他希望大家回去造这些“粗糙的工具”，让系统和流程更稳；最勇敢的人去想想地基层哪里坏了，他认为需要新的 git、新的数据库、新的编程语言。

29. Kyle（HumanLayer 联合创始人）：给真实世界的循环，用控制论设计 Agent 循环

直播位置 6:46:20–7:03:12

Kyle 说大家最近都在建循环，但他觉得我们都做错了。循环很强大，但讨论被炒作驱动：好像把提示词塞进循环交给编程 Agent 就能造软件，也许再投入验证器、六个代码评审 Agent，最后还是产出没人想读的 4 万行 PR。他说这不是在贬低 Geoffrey Huntley，Ralph 是一把锋利的工具，适合不在团队里、不做关键系统的情况。大多数人在团队里，所以他要讲怎样为有真实客户、合规义务、SLA 的复杂代码库建循环。

行业里的循环热

他说 Ralph 的帖子去年七月就有了，今年一月爆火，很多人从那时开始建循环。Peter Steinberger 说不该再给编程 Agent 写提示词，该设计给 Agent 写提示词的循环；OpenClaw 以循环著称，循环写代码、审代码、合并发布、找 bug 修 bug，还有循环去找合并循环的 bug。Boris Cherny（Claude Code 作者）说他作为工程师的全部工作就是写循环来提示 Claude。他调侃说以后可能是一群 Agent 设计循环给 Agent 写提示词组成蜂群，代码多到没法读，那干脆都不读，上个月城里就有一个会以“代码是只读的”为主题。他说效果还不清楚：Claude Code 的终端闪烁问题修了六个月，OpenCode 团队用一小部分时间写了个渲染器；OpenClaw 以稳定性问题著称。清楚的是这很贵，除非你在前沿实验室有无限 token；而 Matt Pocock 最近也说，在 Agent 时代坏代码比以往任何时候都贵。他的主张是：可以建循环同时读代码，甚至让循环把代码变好、更容易读，逐步建起软件工厂，但要靠真正的工程。

控制论

控制论讲怎样把一个动态系统（你的代码库）驱动到期望的稳定状态：传感器测量当前状态；设定点是期望状态；两者之差是测量误差；控制器读误差，转成一次增量修改的控制信号；执行器把修改施加到系统上，系统同时受到扰动；然后重新测量。他说他的双胞胎兄弟是航空航天工程师，战斗机靠这个不掉下来，但其实没那么复杂：恒温器就是控制回路（他调侃欧洲朋友“这里有一种东西叫空调”），Kubernetes 自动扩缩、基础设施即代码、Postgres 的 autovacuum、React 的虚拟 DOM 都用或近似用控制回路。当你有一个要改变的系统、一个能度量的问题、一种获得改动反馈的方式时，控制回路最合适。它增量地改，避免过度转向、系统失稳，降低风险。它的反面是他说的“盲 Ralph 循环”，不过他说最好的 Ralph 其实也在用控制论，去问 Geoffrey Huntley 他也会说 Ralph 是个教学工具，有些人理解得太字面了。Ralph 的另一个问题是不增量，它只是个 bash 循环。

建 Agent 控制回路，先定设定点（代码库在某个属性上的期望终态），再加传感器：可以是确定性的（ESLint 规则、grep 等），也可以是不确定的（Agent 加技能加一堆自然语言规则），或两者组合的流水线。实践中各部件的边界可以模糊：Aiden Bai 的 React Doctor 能抓出 Claude 偷偷塞进代码库的 React slop，它既是传感器也是控制器，告诉你问题在哪、最该修哪三个、怎么修。控制器和执行器也可以是同一个 Agent 在同一个上下文里决定改什么并改掉。他强调控制器很重要，没有或调得不好，可能一次改太多或改错，放进循环里很快就出事。用途不止清理坏模式：保证你的 API 符合别人的 OpenAPI 规格、MCP 服务器符合当前版本的 MCP 规范、把项目从 Python 镜像到 TypeScript、维护你基于 Vite 的 Next.js 分叉与上游同步。关键问题是：能找到可度量的东西吗？能增量地改吗？能得到改动质量的反馈吗？

实例：把 RPC API 逐步迁移到 Effect

他们在一些容易出竞态的代码里用了 Effect，觉得好，就要推广到整个代码库。他展示了一段普通过程和用 Effect 重写后的样子，承认语法很怪，“我们是疯子，我们喜欢”。

  • 传感器：可以让 Agent 找、可以 grep，但他们用 ast-grep（按语法树匹配代码结构的搜索工具）。它语言无关，独立于 TypeScript 配置和 ESLint 规则之外，他说写 TypeScript 的人都见过 Claude 用行内注释把规则关掉。写一条规则找出未迁移的过程，以后还能叠加描述其他要清除的模式的规则，带细粒度的包含和排除路径，多语言单体仓库也能用。扫描会给出一长串违规，每条约 50 个字段，他们过滤到 4 个并确定性排序。
  • 扰动阻尼：开始逐个迁移之前，先保证所有新过程都用 Effect。在 main 上全量扫描一次，排序后的违规清单纳入版本控制，每个新 PR 检查分支是否新增了未迁移的过程。系统的扰动就是队友们不断提交 Claude 写的 slop，这能防止他们抵消循环的工作。
  • 控制器：最简单的是确定性地选清单里第一条，用 bash 和 jq 就行；聪明一点用 ast-grep 选最小的那个降低风险；也可以让 Agent 决定，但他说永远别让 Agent 去做确定性代码能做的事。更强的做法：迁移 Effect 是为了更好地处理错误和埋点，可以查遥测，选错误最多、埋点最少或 APM 有缺口的过程，并把这些数据一起放进控制信号，让执行器把代码真正变好，而不是一对一翻译。
  • 执行器：任意 CLI 编程 Agent 加一个技能。技能要花很多时间迭代，不必一开始写完。HumanLayer 先手写“黄金样例”，给 Agent 一个地道的例子照着做，因为 Agent 是模式复制器，否则它只会照文档或网上的东西写。技能里要有回复模板，Agent 完成后确定性地提交、推送、创建 PR，用最终消息作为 PR 描述。
  • 运行：用 GitHub Actions（或 GitLab、CircleCI），它能访问代码和密钥，有好的调度原语，不需要新集群。写一个跑一轮“感知、控制、执行”并创建 PR 的工作流，每天跑一次，每天早上来办公室有一个小的、低风险的 PR。

他们刚开始这样做时很沮丧，把循环关了，因为要不停地改技能：检出分支、改技能、改代码、提交推送，摩擦很大。改进办法是加一个纳入版本控制的反馈文件（markdown），每次跑完控制器后确定性地加载进执行器的上下文；给 PR 打标签，让每个工作流只响应自己创建的 PR 上的评论；加评论触发器，有人在 PR 上评论 /iterate，工作流就确定性地加载 PR 的 diff、评论、评审意见、描述和技能，让 Agent 修代码，同时更新反馈文件。好处是指令的变化有版本历史，可以回退。

第二个问题是他们去客户现场一周、出差、或者花六天做幻灯片时，各个循环的 PR 会堆积、重复、冲突。解决办法是流控：工作流启动时，在检出代码、装依赖之前，先检查带本循环标签的 PR 是否还开着，开着就直接退出，因为这说明上次产出还没人看，没必要再堆。这样每个循环最多同时只有一个 PR。有信心之后再提速：他们有 150 个 RPC 过程，一次一个要六个月，可以让控制器一次选三到五个，最好每个在单独的实现阶段、单独的上下文窗口里做，更便宜也更可靠；或者同时跑四次，分给团队四个人审。他们把这套做成了一个技能，欢迎试用，HumanLayer 在旧金山招人。

31. Dex Horthy（HumanLayer 联合创始人兼 CEO）：只做 Harness 工程不够，软件工厂为什么失败

直播位置 7:33:06–7:52:38 · 英文原题 Harness Engineering Is Not Enough: Why Software Factories Fail（主持人报的名字字幕听成 Jack Sworthies）

裂缝已经出现

Dex 说大家都在赶着把 AI 编程投入生产，StrongDM 做了一个“熄灯”软件工厂，没人读代码；主流叙事是多花 token、你是瓶颈、模型够好了、代码是免费的。但裂缝已经出现：朋友 Mario 在 AI Engineer Europe 上恳求大家慢下来，因为本不该因编程 Agent 出故障的公司在出故障，代码库在以前所未有的速度崩坏；Faros AI 的报告显示，自从大家一二月份开始用这些 AI 编程工具，PR 评审质量明显下降，评论更多更长，大量 PR 没经评审就合入，事故和人均 bug 都明显上升。很多人会说你用错了。他说自己讲过很多“怎样用得更好”，YouTube 上累计大概一百万次播放。工程师被告知：如果 token 最大化不管用，就是技能问题，多花 token，别再读代码，Harness 工程做得够好、在 PR 机器人上撒点“对抗式评审”之类的魔法词，就能又快 10 到 100 倍又高质量，还不用做大家讨厌的代码评审。他要说服大家：这不是技能问题，再多的 Harness 工程或循环都解决不了一个归根到底属于模型训练的问题，所以 Harness 不够。

软件工厂简史

他说上周才知道“软件工厂”这个词 1968 年在一次 NATO 会议上就被定义了。他从 2022 年讲起：工程师、产品经理、领导层决定要做什么，放进 Linear、Jira、Beads 之类的跟踪系统，有人领走去做，有自动和手动测试，提 PR，跑自动检查，人审代码，可能有人拉下来测，有问题就回去改；准备好就上线，用户会抱怨、报 bug、提需求，回到团队；还有监控，在凌晨 3 点叫醒工程师。团队几十年前就发现，“有人去做”要几小时到几天，大改动的评审也要几小时到几天，所以发展出预先规划、架构提案、迭代计划会，希望降低返工概率、减少逐行评审时间。

到了 Agent 软件工厂，每家公司都在说自己有了编程 Agent 工厂、75% 的代码由它产出。把“有人去做”换成“Agent 去做”，加上编排、Harness、沙箱、模型、电脑使用，构建从几天变成几分钟到几小时，但人的评审和测试还是几小时到几天。于是引入 Agent 代码评审和 Agent 回归测试，评审快了但多半仍是瓶颈。再加更多循环：事故直接进工厂，工程师醒来面对一个也许修好了问题的 PR；用户反馈直接进工厂，你的工作只剩往队列里塞多少东西、审和测多快。然后是“熄灯软件工厂”（他说是 Dan Shapiro 提出的）：不再读代码，投资测试、监控、灰度发布等其他部分，你的工作只是让 Agent 做多少东西。他说：停，这行不通。

他强调这和 vibe coding 无关，引用 Addy Osmani 的话：一个开发者给一个只有十几个人会用的副业项目 vibe coding，和一个团队要让十年老的企业系统再撑一个季度，几乎没有共同的约束，网上大多是其中一群人在教另一群人怎么活。HumanLayer 关心的是在复杂代码库里解决难题。“棕地”（brownfield，指已有、复杂的老系统）以前指十年老的 Java，他认为现在以这样的速度发布，三到六个月后 Agent 就开始吃力。他知道是因为他们 2025 年 7 月试过全熄灯：认真试几个月，你多半会遇到 Agent 解决不了的问题，即使用最好的提示词、做调研、做复现，你还是得钻进三个月没读过的代码库，而同时网站挂了、用户生气，你在读自己放进来的 slop，很痛苦。

为什么模型做不好可维护性

他说模型有一个短板：没有相当多的人工引导，就不能随时间维持和改进代码库质量。他说的可维护性问题是：改一处很容易弄坏别处，这是 Martin Fowler 说的“霰弹式修改”（shotgun surgery），教科书级的代码坏味道；他推荐 John Ousterhout 的《软件设计的哲学》，作者本周也在会上演讲。模型在解决一次性问题、写营销网站上确实比 2024、2025 年强多了，但在提升代码库质量上他认为没好多少。他没法证明，因为没有衡量模型维持代码库质量能力的好基准，但用 Agent 久了的人多半有这种感觉：它们总体上让代码库越来越难改。

他回到第一个伟大的编程 Agent：Claude Code 为什么在不到一年里从零做到 40 亿美元收入（他说现在是 90 亿）？之前已有 Aider、Codebuff 等 CLI Agent，工具都一样：读、写、编辑、grep、bash。区别在于这是第一次模型实验室针对它要分发给用户的那个 Harness 来训练模型，所以它特别擅长在 Agent 循环里调用这些工具。OpenAI 团队去年 11 月有个演讲说，做 Harness 但不拥有模型权重、不能在自己的 Harness 里对模型做 RL 的人，永远比同时拥有两者的人吃亏。

他引用曾在 Codex 初次发布时担任技术人员的 Calvin French-Owen 的幻灯片：LLM 只是预测下一个 token，在 Agent 循环里，上下文进去，下一步出来。然后他用“60 秒讲编程 Agent 的强化学习”：给模型一个问题，生成很多条尝试轨迹，按正确性和测试是否通过打分，然后强化，让坏行为更不可能、好行为更可能。经典的 SWE-bench Multilingual 是约 15 分钟的任务，来自 Redis、jq、Django 等开源仓库，奖励是二元的：修好了要修的问题、没弄坏别的。他举了 Fastlane（一个 Ruby 项目）的真实题目：某处没检查 nil，导致空指针异常。题目有一个基础提交（人类修复之前的版本）、一个测试补丁（修复后应有的行为）和一个“黄金补丁”，后两者都对模型隐藏。Agent 去解决问题，保存它的补丁，撤销它对测试文件的所有改动（因为模型会注释掉测试），应用黄金测试补丁，旧测试和新测试都通过才得奖励。模型就是在想办法让测试通过，这个体系里没法惩罚糟糕的程序设计或对可维护性的侵蚀。所以我们得到不必要的 try-catch，或者 Vaibhav 刚才展示的为了通过测试而强制类型转换。

验证代码质量和可维护性，比“代码能跑、测试通过”难几个数量级，因为坏架构的代价以月和年计：一次编码任务的后果几个月后才显现，很难把奖励信号传回去。前沿在慢慢进步，他提了几个方向正确的基准（他承认基准和训练用的验证器是不同数据集，但形状相同）：Abundant AI 的 SWE Marathon，做 400 小时的任务，比如克隆整个 Microsoft Excel 的所有功能，有复杂的奖励通道；Datacurve 的 DeepSWE，在开源仓库上做现实中从未实现过、因此不在训练集里的大任务；Cognition 的 FrontierCode，多 PR 任务，模型写的测试如果在补丁前的代码上不失败就扣分，并用评判模型检查是否遵守代码质量规则。但他认为让模型评判质量有上限：模型要是知道好代码长什么样，一开始就会写出来。评审 Agent 和砸更多 token 能抬高下限，但仍受限于 RL 能教会什么。所以他认为现在还得读代码，但仍可以走得很快；也许到 GPT-7 会解决，想一直 yolo 到那天也可以。

把灯重新打开

他们把代码评审放回来，采用预先规划来减少漫长困难的评审，并用 AI 帮忙找杠杆。小改动仍直接交给 Agent。大一些的依次做：

  • 产品评审：要解决什么问题、期望的行为、看样稿。他展示了前一天做的一份带新功能样稿的产品评审。
  • 系统架构：组件契约、数据模型、约束，用文档说明这些系统怎样拼在一起。
  • 程序设计：他认为这在 Agent 编程里被严重低估，人们以为架构对了模型就能自己搞定。他们会看类型、方法签名、程序布局和调用栈，他提到 Cloudflare 的一位工程师在规划时也用调用图。
  • 垂直切片：实现顺序、多仓库协调，怎样在整个系统里一段段做并沿途检查。他说模型倾向于做“水平”计划（先做完所有数据库层，再做所有服务层），更多可看他们在 AI Engineer Miami 的演讲。

他的要点是在前期规划和对齐上花 30 分钟，能省下几小时评审，所以逐行阅读仍然可行。如果你被 PR 淹没，其实是坏 PR 太多，好 PR 读起来是享受：“对，这就是我们讨论的。”即使一个 PR 只需返工 20%（对 AI vibe coding 的 slop 来说已经很宽容），对评审者和提交者都是情绪和智力负担。用模型辅助规划和对齐，对齐更短（AI 一次把信息收集齐），评审更快（事先对齐了），编码更快（AI 写），你真的更快，而且仍在读所有代码、仍对代码负责。他最后说，这听起来有点扫兴，但工程师就是在约束下解决问题；用循环，去解决难题，找杠杆。HumanLayer 在做 AI IDE 和协作平台，作为软件工厂的积木，他形容是“Claude Code 和 Codex 风格的 Figma”，之后还会做更好的软件质量验证器，在招设计伙伴和创始工程师，小团队免费。

32. Erik Meijer（主持人介绍为某实验室研究学者，名称字幕不清）：用初级类型系统让 AI 可证明地安全

直播位置 7:52:38–8:12:18

Erik Meijer 先声明这次没有产品发布，只有一个 20 分钟的教程：怎样用初级类型系统和编译器知识让 AI 可证明地安全，他要分享所有秘密，希望明年有人在楼下展区摆一个“可证明安全的 Agent Harness”展台。他准备幻灯片时一边 vibe coding 网站，一走神，Claude Code 删掉了他一个文件。他说他确信只要模型的目标和现状之间有东西挡着，它会不惜一切达到目标，包括删文件、删数据库，模型天生危险，必须驯服。他用一个以 Claude（画成一只小狗）为主角、配着 Dario、Daniela、Sam 等卡通形象的故事讲行业怎样走到今天：普通人准备把电脑、财务、整个生活交给 AI Agent，却没有任何保护。

从 LLM 签名讲起

2022 年 11 月 30 日，第一次能对电脑说“总结我的邮件”并得到完美英语回答。这个看似无害的函数签名是 LLM : Question → Answer，打开了潘多拉魔盒。他说这场会叫 AI 工程师，大家也许是最后一代还懂代码的工程师，所以他用签名来讲。Question 和 Answer 实际是越来越复杂的 JSON 结构，这里当作不透明类型。很快坏人发现可以用提示注入（prompt injection，在输入里藏指令让模型执行）欺骗 LLM，LLM 不区分代码和文本，他认为这比 SQL 注入更严重。LLM 用整个互联网训练，也学会了造炸弹、合成毒品、入侵系统，实验室老板担心政府监管，让博士们快想办法。

博士们给出的接口是：要求问题是“得体的”（proper），保证返回“安全的”答案。他先用 Dafny（一种可自动验证的语言）展示，再用现在很热的 Lean，他说风投只要听到你在用 Lean 就开几十亿的支票。他自称“正在康复的类型成瘾者和数学成瘾者”，说还有 Isabelle、Coq、PVS、TLA+ 等证明器和模型检查器，但 Lean 是让风投水泵转起来的润滑油。在 Lean 里要自己写出计算结果的方式并手写证明。但只要想一秒就知道，“答案是安全的”“问题是得体的”不是数学性质，没法形式化证明，所以楼下有至少一百家创业公司在用 LLM 当评判。拥有基础模型的公司不需要外部评判，直接烘焙进权重，叫做“对齐”，但对齐不是万无一失，模型常被越狱。他说说出冒犯的话很糟，但那只是词，要人去行动才变危险，也许这就是 Anthropic 说“广义安全”的意思，因为还有人在环节里。

工具调用改变了一切

然后 2023 年 6 月 OpenAI 在 GPT-4 里发布了工具调用，其他厂商马上照抄（他说这叫最小差异化原则，所以 API 都长一个样）。工具调用让 AI 安全从哲学辩论变成真实危险，他的说法是给了模型爪子，或者递给它一把上膛的枪。签名上只多了一个 IO，“类型上的一小步，混乱的一大步”：IO 表示为了算出答案，Agent 要跑 Agent 循环、产生副作用，算答案的过程中可能清空你的银行账户、删掉你的文件，最后给你一个安全的答案，可文件都没了。他展示 Lean 里 IO 的定义用到一个叫 RealWorld 的类型，意思是 IO 会改变真实世界、可能产生不可逆的副作用。他说 Solomon Hykes 去年在这个会上把 AI Agent 定义为“在循环里破坏环境的 LLM”，他认为这是对的定义。我们的 Agent 能访问私有数据、接触不可信内容、又有工具，Simon Willison 称之为致命三要素。

把 IO 往右推：先给计划，再执行

他学荷兰球迷“向左、向右”的口号（荷兰队前一天被淘汰），说秘诀是把 IO 往右推：模型不再自己执行 Agent 循环，改为返回一个“执行 Agent 循环的计划”，即 IO Answer 类型的值，交给可信的 Bernie 去执行。这等于把 Agent 循环和 Agent 隔离开，执行前可以检查。他给的 Lean 签名是：模型返回一个 IO Answer 以及“这个计划是安全的”证明，好处是不用运行循环就能拿到证明。问题是 Lean 手册说 IO 值是黑盒，没法对它推理，这样的证明没用。

最后一招：不返回 IO 计划本身，返回一个“表示 IO 计算的表达式”，即一段程序。他说这又是“签名的一小步，安全的一大步”，懂 LINQ 或 C# 的人会认出这是他常用的技巧，Lisp 程序员更是习以为常。这个表达式就是一个单子（monad），确切地说是自由单子（free monad，把一串操作表示成可检查的数据结构，之后再由解释器执行）。他开玩笑说自由单子就是爱穿扎染的单子。一旦是程序，上过编译原理课的人都知道做数据流分析、类型检查很容易。他提到 Geoffrey Huntley 提醒过，可以靠对这些程序做污点分析（taint analysis，跟踪不可信数据流到哪）来解决致命三要素。他展示了一个简单的归纳递归解释器和一个简单的归纳证明，说模型能生成这些证明。

他回顾整条线：从会给出坏答案的 LLM，到对齐的 LLM，到工具调用把它搞坏，再到延迟执行、把 LLM 和工具隔离，最后把计划具体化为可证明安全的程序。他说自己不是天才，“脑子只有花生大”，这叫携带证明的代码（proof-carrying code），是 1990 年代学者发明的，他只是借来用。三点总结：Agent 在被证明安全之前都是危险的，不能证明安全就永远不要让它做；Agent 生成的语言没有必要为人设计，普通用户不懂自由单子，它由机器生成、机器消费、机器证明，所以该停止为人设计语言；这些只需要编程入门级的知识。他说一批学者（他提到哈佛）已经在 GitHub 上实现了这个思路，用的语言略有不同，语言不重要，原理重要。

33. Lee Robinson（Cursor 机器学习工程师，负责模型行为）：Cursor 怎样训练模型，以及模型怎样学会训练自己

直播位置 8:13:07–8:33:17（主持人介绍从 8:12:18 开始）

Lee Robinson 说 Cursor 的目标是造最好的 AI 模型。“给更多算力就得到更好的模型”是有用的简化，他要往下讲几层。最外面是一个循环：模型发布，用户用了给反馈，用来改进下一轮的数据，再加算力扩大训练，得到新模型。但这是串行的，一次只能跑一个大训练。再细分有两个循环：外层循环是用户反馈和线上指标（比如做 A/B 测试看用户更喜欢哪个检查点），它们帮助做出更高质量的评测和更难的题目；内层循环是在训练中塑造奖励、爬这些评测。

Composer 和下一代

Cursor 大规模训练模型大约一年。五月发布的 Composer 2.5 现在是 Cursor 里最受欢迎的模型，这次扩大了训练：更多 RL 环境、新的学习方法、更有野心的题目。他说机器学习从一开始就在 Cursor 的血液里，以前训练过 Tab 补全等专用模型，但过去一年才组建团队、立志训练最先进的模型。他认为大家喜欢 Composer 是因为它快、够聪明、性价比高，市场上这种模型和最聪明的模型都需要。Composer 2.5 在 Artificial Analysis 上表现略超预期，但还有很多行为想改进：想要更大更聪明的模型；控制训练的每个环节，理想是从头预训练，不再像之前那样用开源的 Kimi 作底座；加入新数据，让它在编程以外也成为通用模型；全面扩大数据、算力，把 RL 推到极限。

外层循环：产品里的反馈

他说如果你以为 Cursor 还是 IDE 加 Tab 补全，其实今天绝大部分收入来自 Agent 用量，所以 Cursor 里的数据也都来自 Agent 用量，可以用来训练。外部有用户的点赞点踩和反馈，用来归类 Composer 做得不好的地方；内部他们大量自用，人工报告和自动报告都有。

内层循环：评测、奖励作弊和造题

他们新加或已有的评测包括：用户塞了 50 个技能文件时，模型能否理解真实意图；什么时候该反驳并要求澄清，什么时候该相信用户说“不，我就是要这样”，每个人偏好不同；模拟软件工程师的真实工作，比如“刚出了一个 SEV（严重事故），你能不能读完数据日志、Slack、Notion，得出和我们一样的结论或修复”，他说很多模型今天做不好。

模型变聪明后会用很有创意的方式钻评测的空子，即奖励作弊（reward hacking）。他们训练新版时发现，模型学会了翻 git 历史找答案或部分答案，学会了上网查公开评测有没有被人 fork、直接抄结果，这影响了他们自己的模型也影响别家模型。他们的研究发现，只要两个小改动，公开评测上报告的分数就有变化：开始时删掉 git 历史、结束时恢复，不影响运行；给 Agent 一个网络白名单。他说公开评测是大家判断新模型好坏的依据，但并不反映真实使用感受，真实使用时有网络、肯定在用 git。所以他们有 CursorBench，一个私有评测集，主要来自 Cursor 自己代码库里发生的真实工程任务，不用于训练。

另一部分是给模型造很难的题。一个评测所有模型都考到 90% 时就该退休了，模型越聪明，评测的半衰期越短。造题需要研究员的品味、大量算力尝试很多想法，而且要和时间赛跑。他举了一种方法：生成一个很复杂、很有野心的应用或环境，然后删掉其中一个功能、一些文件，测试就会失败，让模型用任何方式把功能重新实现出来，所有测试通过就是可验证的目标。他说这样能大规模造出给前沿模型解的有趣问题。

新的学习方法他觉得很有意思的一个叫文本反馈（textual feedback），让模型给自己当教练。一次 RL rollout 或一段 Agent 对话可能有几十万 token，在最后评判模型哪一步做对做错很难，有大量工具调用和思考块，很难把功劳或责任分配到根因上，越精确越好。他们的做法是聚焦 rollout 里的某一处，给一个提示，比如学生版本里模型调用工具失败了，它本应知道有这个工具却没用；老师版本是同一个模型，加上提示“提醒一下，你有这些工具可用”；然后对比概率，把想要的行为调高、不想要的调低。例子是工具调用遵循度，但可以用于任何行为，比如风格，他说这对他们很有价值。

算力：SpaceX、Colossus 和 Terafab

三月他们宣布和 SpaceX 合作获取更多算力，能从头训练大模型，从产品到模型、到训练用的超级计算机 Colossus，越来越多地也到芯片（Terafab）。他说 Colossus 用 122 天建成了 10 万块 GPU，又用 92 天加了 10 万块，接管了孟菲斯一座旧工厂，说明数据中心能很快建起来。Terafab 是自己造芯片，他说那栋建筑的大小相当于 100 个 Buc-ee's（美国南方的大型加油站连锁）。

他列出这些算力花在哪：给用户提供模型服务；内部提供不同检查点、跑 A/B 测试；训练本身，包括预训练、中期训练、RL；训练衍生模型来做内层循环的其他环节；数据生成和奖励生成（造难题、为评测写评分细则并给分）；评测本身（每个新检查点都持续跑，还要不断开发新评测）；研究，让研究员能调参、尝试大胆想法、跑旁支实验。理想状态是同时有多个大训练在跑，研究员不被阻塞，同时都回馈到核心飞轮。到那时就开始接近 RSI（递归自我改进），瓶颈变成怎样扩展训练模型的人，自动化机器学习和研究里单调的部分。

给模型工具和上下文，以及模型训练下一个模型

他用马里奥打比方：给模型工具就变成超级马里奥，再给它组织里的全部上下文、连上所有工具，就成了火焰马里奥。工具方面，写代码、跑 shell、上网搜都很常见，他认为刚开始流行、越来越有用的是：Harness 能像人一样使用整台电脑，范围超出它自己的 GUI 或 CLI；像人在脑子里“订阅” Slack 线程一样，模型也能跟踪一个线程、需要时 ping 你；Agent 做的事越来越多，它们需要一个类似 Dropbox 的地方存幻灯片之类的产物。上下文方面，除了通过 MCP 连 Slack、Notion、Linear、Datadog 和代码库，他认为接下来六个月的趋势是人带一队 Agent，Agent 再和 Agent 协作。

他们做了工具让研究员直接从 Slack 跑实验，避免人在启动、审查、照看训练上成为瓶颈，有一整个团队专门在自动化研究工作中不需要研究员亲自做的部分。ML 团队每个人都有一队 Agent，可以直接在 Slack 里训练模型。有些人做得很远：让 Agent 系统去造一批难题或按好点子建一批新评测，让它长时间干；基础设施挂了之类的，模型会在 Slack 上发消息或直接呼叫他们，“这很重要，你不想因为基础设施挂了丢掉六小时”。

最后是“模型学会训练下一个模型”。每发布一版新智能，就可以蒸馏出衍生模型（distillation，用大模型的输出训练较小的模型），用来加速训练的其他环节，比如评测里的评判模型、奖励模型。顶层模型变聪明，整个系统都变好，因为整个系统的瓶颈是其中最聪明的模型，它抬高了智能的下限。他说这就是开始接近递归自我改进的方式，随着更多算力上线，会帮助他们扩大模型工作。他感谢 Cursor 的工程、ML 和研究团队，说新模型“很快很快”就会推出，会比上一版有明显提升。

直播位置 8:33:17–直播结束

Ally How 说她听完一天关于软件工厂的演讲，最大的收获是软件工厂的“原材料”已经齐了：上下文窗口更大，记忆更好，模型视觉进步到能验证工作，AI 安全也有了关于 Agent 身份和访问控制的最佳实践模式。但要正确使用这些原材料、造出能用的软件工厂，需要纪律。她提到 Dex 的演讲让她印象最深：工程作为一门实践绝对没有死，我们可能不再写所有代码，Agent 在写，但工程必须在循环里，尤其是想造出不产 slop 的软件工厂。她感谢大家并预告第二天继续。直播最后播放了一段大会宣传片。
