02. Gabe Greenberg（G2i）：大会的由来与 Orchestrator AI 发布

直播位置 0:06:51–0:16:36

他是谁

Gabe 是 G2i 的创始人兼 CEO（g2i.ai），公司做软件工程方向的强化学习环境和人类数据。强化学习 RL（Reinforcement Learning）是让模型在一个可以打分的环境里反复尝试、按得分改进的训练方法，“RL 环境”就是给模型练习用的任务和打分器。他也是 AIE Miami 和 React Miami 的联合组织者。

大会的来历

2016 年他一个人飞到旧金山参加 React Conf，第一个认识的人是 Ryan Florence，对方笔记本锁屏是 Brad Pitt，他觉得来对了地方。之后他深度参与 React 生态。几年后他得了重病（霉菌毒素中毒和汞中毒），持续了八年：偏头痛到要在桌子底下睡几个小时，有时连简单算术都做不了，周一去治疗，要到周五才能工作。确诊后他和妻子在 Twitter 上求助，React 团队的 Dan Abramov 转发说“我们帮帮 Gabe”，社区一共筹到 22,000 美元。他几年前康复了。

后来他半夜在 Twitter 上问“有人想在迈阿密办 React Conf 吗”，Ken Wheeler 回复说会去；Michelle 和她的姐妹 Becca 说“我们加入”，并说服他在疫情刚结束、没有钱的情况下办起来。他说办会是对社区当年帮助他的回报，所以不想把它办成以盈利为目的的企业活动。swyx 几乎每年都来 React Miami 演讲，他创办了 AI Engineer 大会，主持 Latent Space，现在在 Cognition。swyx 问 Gabe、Michelle 和 Becca 能不能办“美国的第一场 AIE”（原话如此），于是有了 AIE Miami。

发布 Orchestrator AI

G2i 和前沿实验室合作多年，需要在很短的周期里交付生产级软件。他当场发布了 Orchestrator AI（orc.ai），一个面向复杂工程任务的多 Agent 编排平台，内部已经用了一段时间。他介绍的设计：

  • 一个协调者（coordinator）调度多个角色：实现者、审计者、评审者、验证者、研究员等，单个任务最多可以开 16 个 Agent。
  • 每个结果带置信度分数，并列出已知问题和各个 Agent 做出的假设。
  • 他称之为“真正的对抗式治理”，用来抓住大模型的漂移（drift）；Agent 之间通信很快；不绑定具体模型。
  • 上下文记忆会自动修剪，减少上下文膨胀；一个 meta observer 在发现机会时自动添加新的 skill，另有可观测层可以手动增删 skill。

他给出的基准数据

G2i 做很多按规格说明（spec）驱动的后端开发。他们比较了 Orchestrator 和单 Agent Harness（他举的是 Claude Code）。Harness 指包在模型外面、负责调用工具、管理上下文和循环的那层程序。

  • Pet Store API：两者都接近满分，Orchestrator 高约 6%，“差别不大”。
  • 一个创业公司规模的 API：Orchestrator 路径覆盖率 100%、语义得分 100%；Claude Code 是 78% 和 60%。
  • 规格复杂度再提高约 8 倍：单 Agent Harness 语义得分 22%，Orchestrator 92%，路径覆盖率 100%，用时减半。
  • SWE-bench Pro（约 731 个任务），底层模型是 GPT-5.4 high。按难度分桶：easy 提升 17.1%，medium 14.8%，hard 1.7%，very hard（跨多天的长程问题）5.7%，整体在模型本身之上提升 8.4%。他拿来对比的是：GPT-5.2 到 5.4 大约提升 4 个点，Opus 4.5 到 4.7 大约 7 个点。他说用 GPT-5.4 加 Orchestrator 跑 SWE-bench Pro 的成绩超过了 Opus 4.7。

为了赶出最后这个基准，他们在 72 小时里专门租了一个酒店房间放笔记本跑测试，因为会场酒店的 Wi-Fi 不好。他们夏天在招设计合作伙伴（design partner）。

03. Dax Raad（OpenCode / Anomaly）：你没有什么好点子

直播位置 0:17:25–0:32:33 · 英文原题 You Don't Have Any Good Ideas

Dax 是 Anomaly 的联合创始人，公司做开源编程 Agent OpenCode。他没带幻灯片，在台上边走边讲。开头他调侃：大家来迈阿密学最新技巧，回去就能把所有想法做出来、发财、让妈妈骄傲，“只有一个问题，你们其实没有好点子。我也没有。”他说这是他自己和公司眼下最头疼的问题，整场讲的是产品上的克制。

过去的慢，其实在帮我们过滤

两年前，有人带着新需求来找工程师，工程师总是想办法推回去，因为积压的工作已经很多。他说其他部门讨厌工程团队是有道理的：客服被用户骂，是因为工程没交付修复；销售丢单，是因为竞品有我们没做的功能。软件是虚拟的，大家总觉得想到了就该立刻存在。

那时候 Figma 原型比能跑的原型便宜得多，所以产品和设计会先一起打磨想法，很多想法在这一步就死了，或者被改成完全不同、更好的东西。这是组织里自然发生的过滤。

现在发生了什么

  • 组织里任何人都能花一小时让编程 Agent 做出一个 MVP。MVP 的问题是看起来“差不多做完了”，一旦看起来差不多完成，它就有了惯性，没人好意思再从第一性原理质疑它，下周它就进了产品。
  • 行业又在鼓励“快、快、快”，有 token 排行榜，“如果你花在 token 上的钱不到工资的五倍就会被开除”。
  • 结果是产品膨胀：功能放在奇怪的位置，同一件事有三种做法。他看自家上线不到一年的产品，会问“这些功能什么时候进来的？”
  • 团队关系也变了：设计第一次落后于工程。设计师面前堆着一百个已经上线的功能要逐个打磨，逐个打磨加起来也不等于一个好产品，他们没机会去做端到端的整体体验。
  • 工程这边，以前往系统里塞一个不合适的功能，你得自己去做那个 hack，以后它和别的功能冲突时也是你受罪。现在可以丢给 Agent，工程师对代码库的底线“已经掉到地板上了”，因为自己不再付出代价。
  • 老借口是“以后再回来修”，三个月变三年。新借口是“Agent 以后会修”“模型会变好的”，他称之为一种靠信念的做法，实际上不会发生。

他的结论是产品腐烂得很快：不到一年的产品用起来像五年前的老产品，像被私募收购后的那种劣化，只用了几个月。能力越大，越放大判断力的好坏，所以需要更多克制。

他自己的做法

  • 不要用户一报问题就立刻修。10 个问题各修一遍，就得到 10 个零散方案。慢下来多听，可能发现这 10 个问题其实相关，一个改动能解决它们，外加 50 个还没人提的问题。他说做产品的人不该只是“把用户抱怨路由给 Agent 的 prompt 路由器”。
  • 每个产品基本只有一个好点子，onboarding 的任务是让用户尽快理解这个点子。打开产品就有十几个方向可选，用户不会去探索，只会离开。
  • 每个新功能都要设计好“用户怎么发现它、怎么知道何时用、怎么理解它”的路径。他有很多自己很喜欢的功能，因为找不到让大多数人发现它的方式，最后没上线。
  • 按这些标准过滤，大部分每天冒出来的想法过不了。他认为每几个月有一个好点子就算不错，AI 让你更快，但不会让你的好点子多出 10 倍。

结尾他说，过去大家对工程慢的那种挫败感，回头看应该有点感激，它一直在替我们挡掉坏点子；现在这道过滤没了，要主动意识到大多数点子都不好，这很正常。

04. Dexter Horthy（HumanLayer）：我们在 RPI 上做错的所有事

直播位置 0:33:21–0:53:17 · 英文原题 Everything We Got Wrong About RPI

背景

Dex 是 HumanLayer 创始人，在 AI Engineer 讲过多次，其中 “No Vibes Allowed” 播放量接近 50 万。RPI 是他们提出的编程 Agent 工作流：Research（调研代码库）、Plan（写计划）、Implement（实现）。起因是一项研究（他提到 Yegor，字幕写作 Eigor）的结论：用 AI 交付得更多，但很多是在修上周交付的垃圾代码，而且在已有的老代码库（brownfield）上效果不好。他们去年 9 月把方法论发到 Hacker News，在首页挂了一整天，大约 1 万人下载了他们的开源 prompt；他找到 Uber 和 Block 在用 RPI 的公开证据。

但这场他要讲的是做错了什么。他们以前说过：可以不读代码；要读很长的计划文件；隐含的意思是让 Claude 产出一点垃圾也没关系。现在他们走到了光谱的另一端（他称之为 “Zechner/Pocock 连续谱”，大概是指 Mario Zechner 和 Matt Pocock 关于要不要读代码的两种立场，字幕不清）。

发现一：调研质量差

自 10 月以来他们和几千名工程师合作，发现同一套工具，专家用效果很好，交给团队就不行。原因之一在调研阶段：原设计是派出多个子 Agent（sub-agent）在代码库里做纵向切片，最后压缩成一份只描述“代码现在怎样工作”的文档，要客观，不带观点，不做实现规划。好的工程师会先把工单拆成问题，比如“要加一个跨租户 reticulate splines 的端点”，就去问端点怎么注册、哪些代码碰 splines、处理 reticulation 的 worker 在哪。偷懒的人直接说“我要做这件事，去调研”。模型被训练得一心想解决你的问题，一旦知道任务，调研就会掺进它对第一个方案的倾向。“不要把思考外包出去。”

发现二：计划质量差，指令预算

原来的 create plan 是一个约 85 条指令的单一 prompt。理想情况下模型会先和你来回讨论问题、确认实现顺序和测试方式，最后才写计划。但如果你赶时间没写对 prompt，它直接吐出计划，你只拿到模型想到的第一种方案。专家的秘诀是要说“魔法咒语”：“work back and forth with me, starting with your open questions and outline before writing the plan”。不说的话大约 50% 的情况它会跳过讨论。他说如果一个工具需要几个小时培训才能用好，应该去修工具。

他的核心结论是指令预算（instruction budget）：联合创始人 Kyle 写过一篇调 CLAUDE.md 的文章，结论是前沿模型大约能可靠遵循 150 到 200 条指令，再多就每条都只注意一半（那是一年前的数，可以往上调一点）。85 条指令加上 CLAUDE.md、系统提示、工具定义、MCP，很难有好的遵循度。MCP（Model Context Protocol）是让模型以统一方式接入外部工具和数据的协议，每接一个工具都会往上下文里塞说明。

发现三：读计划不划算

他去年 11 月在台上说“如果不读代码，就一定要读计划”，有团队还专门开会评审计划。但一千行计划约等于一千行代码，计划里也会有意外，读完计划再去读实现出来的代码，工作量反而更多。新建议是：不要读计划，读代码。“我们试了大约 6 个月不读代码，结果不好，最后不得不大面积推倒重写。”

他对现在流行的“熄灯软件工厂”（无人值守、没人读代码）很警惕：如果凌晨三点会有人因为故障被叫醒，请读代码。他担心的场景是三个月没人读过代码，出了一个 Agent 解决不了的 bug，团队要花三周重新熟悉代码库，这三周里客户流失，公司就死了。他认为在每一行都读、自己拥有架构的前提下，2 到 3 倍的提速是可以做到的；如果快 10 倍但半年后全部推倒，那只是在烧钱和时间。所以他对 agent swarm（大量 Agent 并行）也持保留态度。

怎么修：用控制流代替 prompt

  • 调研：程序层面把工单对调研 Agent 隐藏。一个上下文窗口负责从工单生成问题，另一个只拿着问题去调研。上下文窗口 Context Window 是模型一次能看到的全部输入。
  • 他提到 Geoff Huntley（当天下午也有演讲）讲过的观点：上下文用得越多，结果越差，超过大约 10 万 token 就进入“笨区”（dumb zone），这是 Claude 的数字，GPT 不同。问题除了信息太多，还有指令太多。
  • 举例：客服机器人如果用 prompt 写“如果是产品反馈就这样，如果是账单问题就那样”，规模变大后准确率会下降。常见做法是先用一步分类，再给每类配一个小的指令模块，更快更准，还能换更小的模型。
  • 他们把 create plan 拆成 design、structure、planning 等多个 prompt，每个都在 40 条指令以内。原话大意：能用控制流做控制流，就别用 prompt 做控制流，switch 和 if 语句挺好的。

他自嘲：去年 6 月他们在 AIE 上说别做“全量 Agent”，要用 workflow 和 pipeline；8 月 Claude Code 出来，“工具循环好像又回来了”，他们又做了巨大的单体 prompt。现在是“喝自己的药”。

会不会被 Bitter Lesson 淘汰

常有人在 Twitter 上说这些技巧会被“苦涩的教训”（Bitter Lesson，Rich Sutton 的观点：长期看通用的算力扩展总会胜过人工设计的技巧）淘汰。他的看法：新模型会让大部分上下文工程失效，但你再做一轮，又能在前沿之上多出 1% 到 10%。这在长程任务上很重要：第 20 轮时，每步 99% 和 97% 的成功率会拉开 27% 的差距。Dan Shipper 称之为“冲浪模型”。swyx 的说法是 Bitter Lesson 终有一天会干掉这些，但现在有用。如果你能让小而便宜的 GPT-OSS 做现在 GPT-5 high 的活，就抓住了有价值的东西。

更高杠杆的中间文档

  • Design 讨论：当前状态、期望的最终状态、要遵循的代码库模式和架构模式。老代码库里同一件事总有六种做法，这一步可以在 Agent 写出一堆垃圾之前给它“做脑部手术”，指出该用哪个模式。它还记录已解决和待解决的设计问题，类似 Claude Code 的 plan mode，但写成约 200 行的 markdown。他引用 Frederick Brooks 的“设计概念”（design concept）：大家脑子里都有但从没写下来的东西。他认为这里必须有人参与，因为架构没法用 RL 训练，坏架构的代价要几个月几年才显现，不是 5 分钟的单元测试循环能测出来的。
  • Structure 大纲：design 是去哪里，structure 是怎么去，对应设计评审之后的 sprint planning。模型特别喜欢“横向计划”：先做完整个数据库层，再服务层、API 层、前端，1200 行之后才发现坏了，排查面很大。他们要求纵向切：写一点就检查一点，先接业务逻辑，再做错误处理。
  • 最后的 plan 包含逐行改动，是写给 Agent 的，人只扫一眼，把认真的评审留给代码。
  • 这些文档也帮助人和人对齐。以前在几百人的公司里，两小时写完的功能要两天才能上线，因为要对齐、评审、返工。只用 AI 写代码，不会快到 2 倍 3 倍；让模型帮你做规划和团队对齐，代码评审也会更快。

QRSPI 和建议

  • 权限：台下大约 40% 的人一直用 YOLO 模式（跳过所有权限确认）。他觉得 Agent 有风险，自己试过越狱它们。但即使批准了一大堆规则，经常是开了任务一小时后回来，发现它 30 秒时就停下来等确认了。
  • 算力：跑连数据库的大测试套件，两三个 Agent 就把 CPU 打到 100%，风扇狂转，连浏览网页都卡。

云端 Agent 产品（他提到 Claude 的托管 Agent，OpenCode 也在做类似东西）他两个月前试过，不满意：比如 Claude 的沙箱有网络代理，他连不上自己的数据库服务商。最后他总是把云端开始的工作拉回本地，扔掉一半，并没有更快。

他现在的配置

他想，与其用各种半成品的 Linux 沙箱，不如直接用 Linux：一台 Linux 机器，用 SSH 加 Tailscale 远程登录，里面开 tmux，再在 tmux 里跑编程 Agent。

  • 机器：发行版无所谓，Ubuntu 可以，他用 Arch。想省事就去 VPS 服务商点一下按钮；想要更多算力就用自己的电脑，他地下室有一台专门的机器，“不是跑 OpenClaw 的 Mac Mini”。不想配 Linux，就让编程 Agent 帮你配，这让 Linux 对他变得容易接近。
  • Tailscale：建一个私有网络连到自己的机器，不用暴露端口，到处都能用。
  • tmux：终端里的窗口管理器，有窗口和窗格（pane），支持鼠标；断线后能重新接回会话，合上笔记本、SSH 断开，回来一切都在；而且可以被 Agent 用脚本控制。

现场演示

他在本机一个 Linux 虚拟机上演示（说用真正的远程机器加直播不是好主意），开头还在 tmux 里迷了路。他在 tmux 会话里打开 OpenCode，用 Kimi K2.5（因为速度快，适合演示）说“开几个窗格，放点很 Linux 的东西”，Agent 开出了 htop、实时磁盘占用等窗格，然后他让它全部关掉。他说没有装任何 skill 文件，这能成功是因为 tmux 完全通过 CLI 控制，Agent 只是在调用 shell 命令，不需要 MCP：列出窗格、拆分窗口、读取窗格内容、发送按键。

他的收益：机器里没有其他数据，可以一直跳过权限确认，坏了就重开一个 VM；算力更多；笔记本电池更耐用、风扇不转；远程机器 24 小时连着快网络。他坐 6 小时火车从多伦多去蒙特利尔，车上只有大约 1 Mbps，直接和 Agent 工作几乎不可能，但连远程 tmux 会话足够了，整趟没有中断。他说自己的办法很朴素，没有让 Agent 在云端独立干活，只是更有效地和它们一起工作。

  • 他把 tmux 看作“终端里的 Playwright”：Agent 可以直接读取窗格里的日志输出。Playwright 是浏览器自动化测试工具，Agent 常用它操作和检查网页。
  • termdraw：基于矢量的终端绘图工具。他画了一个弹窗草图（标题、关闭按钮、线条）发给 Agent，说“把弹窗改成这样”。他的理由是 Agent 理解 ASCII 很好，给截图的话模型要花几千 token 把它拆成文字描述，精度也不会比 ASCII 高。随后他让 Agent 在 1 号窗格里运行自己的 TUI 应用，看它反复修改。TUI 指终端里的文字界面程序。

07. Shashank Goyal（OpenRouter）：真实用量数据里的推理成本与 Agent 工作流

直播位置 2:22:56–2:45:48 · 英文原题 Evaluations and Benchmarks in the Wild

OpenRouter 看到的生态

Shashank 是 OpenRouter 的创始工程师，公司成立约两年半，他加入约两年。OpenRouter 是模型聚合平台，一个接口调用生态里的各家模型，所以它同时看得到“用了哪些模型”和“哪些应用在用”。他报的规模：每月约 75 万亿 token，每月超过 500 万用户，60 多家供应商，300 多个模型。主持人介绍时提到他招人看的是热情和会不会问对问题。

他说没有哪个模型在某个场景里一直最好，用户一个工作流里往往用不止一个模型。所以他们做了排行榜页面，展示的是用户实际把钱花在哪里，而不是每次发布会上那些“刷榜”的基准分。排行榜上 Anthropic 的模型在前面，但 DeepSeek、MiMo、MiniMax、Gemini、OpenAI 都有大量用量，“这不是赢家通吃的市场”。应用排行里，编程 Agent 除了 Kilo Code、Claude Code，还有大家可能没听过、正在快速增长的 Hermes Agent。

三条趋势和几个数字

  • 最佳实践按周变化；模型越好，prompt 里要交代的东西越少；模型轮换很快。
  • 推理正在变成像互联网一样的基础设施：token 停了，工作就停了。推理 Inference 指用训练好的模型生成输出的过程。
  • 过去一年平台 token 消耗增长超过 14 倍。OpenRouter 上每个 token 都是用户付了钱的，所以这代表用户得到的价值。增长是分散的，不靠单个用户或应用。OpenClaw 上个月一个应用就在 OpenRouter 上消耗了超过 18 万亿 token，约 180 万美元，而且它是 MIT 许可的开源项目，最流行的 Agent 本身就是开源的。
  • 成本崩塌：两年前 GPT-4 是每百万 token 输入 30 美元、输出 60 美元；今天同等水平的 Gemini 2.5 是 15 美分到 60 美分，他说便宜了约 50 倍。前沿模型本身价格没降，但今天的前沿智能一年后会便宜 10 到 20 倍。所以他建议按“Opus 4.7 能部署到所有任务”的世界来设计，而不是只把它用在高价值任务上。
  • 市场在去中心化：前 5、前 10 模型的份额在下降，MiniMax、DeepSeek、Xiaomi、Z.ai 等中国开源实验室占了可观份额。他建议工作流要对多个模型做评测，质量和成本之间有一条很宽的帕累托前沿。
  • 推理（reasoning）已经是默认：几乎所有模型都会先思考再回答，也就是测试时计算（test-time compute）。他特别提到 DeepSeek 很久没发大版本，用量仍在增长，因为性价比高，工具调用好，推荐做 Agent 工作流的人试试。
  • 开源模型占 35% 到 40% 的 token，但因为便宜，在花费里占比小得多。

Agent 已经是主要负载

他们用元数据判断一个工作流是否是 Agent 式的：大量工具调用、多轮循环、使用编排。按这个标准，约 40% 的工作流是 Agent 式的，超过 15% 的花费来自 Agent 工作流。即使用户界面看起来是一问一答，背后也在调很多次模型和工具。工具调用 Tool Call 是模型在预训练记忆之外获取上下文或对外部世界采取行动的方式，他说这条曲线是过去 12 个月最大的趋势，像曲棍球棒一样上翘。

  • 非 Agent 工作流每次请求的 token 数一年来几乎没变；Agent 工作流的每请求 token 数高得多，能用满上下文。
  • 会话长度：非 Agent 一般两三轮，Agent 会话平均轮数接近 80，约长 11 倍。
  • 使用 Agent 的用户会用更多推理、缓存命中更好，平均试用 6 个模型，非 Agent 用户是 3 个。

为什么是现在

他说这是一年半慢慢累积的：2025 年 1 月有了第一个推理模型；那时工具调用成功率只有 85% 到 90%，一个 80 轮的会话里就有大约 8 次失败机会；8 月到 11 月左右，前沿模型的工具调用成功率升到 99% 到 99.5%；去年 12 月 Harness 大爆发（Claude Code、Cline、OpenHands、OpenClaw）；今年 1 到 2 月一切汇合。他自己用 Claude Code 八九个月，感受到的拐点是 Claude Opus 4.5 发布的 12 月，以及之后大家学会充分利用 Harness 的时候。

他总结了五个力量：模型更聪明、推理更便宜、上下文更长、工具调用更可靠、Harness 更好。多数前沿模型已有 100 万 token 的上下文窗口，很多完整代码库能直接放进去，连 grep 工具都可以不用。

OpenRouter 自己怎么用 Agent

  • Spawn（openrouter.ai/spawn）：一键把 Claude Code 之类的 Agent 部署到 VM 里，可以用手机控制。它的整个代码库 100% 由 Agent 编写，没有人类提交过 PR，偶尔有人类提 issue。写代码、评审、安全分析、issue 分诊、端到端测试都由一群 Agent 持续在仓库上运行，仓库开源。
  • Scouts：他们想跟踪 OpenClaw 等集成了 OpenRouter 的开源仓库里用户遇到的问题。简单的 cron 任务每天都返回同样几条没解决的热门 issue。Scouts 把 GitHub PR 当作 Agent 的记忆：新建一个 PR、写一小段系统提示就创建一个 scout；另一个 Agent 扫描所有打开的 PR，发起网页搜索，结果追加到 PR 里作为历史。一个文件就让每日任务记住了之前看过的一切。
  • OpenRouter Intern Manager：单个 Agent 做太多事更容易失败，所以他们部署很多只做一件事的“实习生”，大约 20 个。Dexter 帮你在几千个 Slack 表情里按心情挑表情；Buddy 负责接入新模型和端点，比如告诉它“Anthropic 周四发布了 Claude Opus 4.7”，它就完成接入和测试；Sniffer 做 KYC，Tony 做客服。每个实习生有自己的 VM 和 GitHub 仓库，可以给自己的仓库提 PR 来学新能力；manager 还能新建或删除实习生、批量推送改进、管理所有 Agent 的凭证。

他的三条经验：尽量多实验；生产环境依然很难，所以他们用很多小 Agent 而不是一个大 Agent；把日常工作自动化。他们每天提醒自己：“我们不再是在构建 OpenRouter，而是在构建那台构建 OpenRouter 的机器。”

  1. 定义对你来说什么是代码质量：既有可以从外部资料收集的通用标准，也有项目、团队、组织特有的要求。这些都要写成文字，因为对 Agent 来说它们就是上下文。
  2. 决定这些标准放在哪里：AGENTS.md 一类的文件、内部文档、工程规范、代码评审标准、组织策略。她顺口说起不确定大家还用不用 CLAUDE.md，因为有篇论文说它效果不大。Qodo 的规则系统把组织级、仓库级、语言或框架级的规则集中在一处，按正确性、可靠性、质量分类，并标注严重程度。她称之为集中的“上下文平面”，团队成员和 Agent 都能看到。
  3. 在你已经在用的地方设计验证层：IDE、CLI、Git 平台、CI/CD 流水线。

尽早、经常地执行质量

  • 规划阶段就把标准带进去：通过 prompt 写法，以及用 Agent skill 从上下文平面拉取规则。她展示了自己在 Codex 应用里收集的一大堆 skill，“像收集游戏王卡牌一样”，很多是清理死代码、处理 Agent 老是做不好的错误处理，还有 TDD、BDD 相关的。她用一个 Qodo get rules skill 拉下规则，挑出与当前任务最相关的，在实现时执行，完成后再验证。
  • 本地代码评审：在 IDE 或 CLI（Codex、Claude Code）里对未提交或已提交的改动先跑一遍，在开 PR、“让全世界知道你刚生成了 AI slop”之前把能抓的问题抓掉。
  • PR 阶段的自动 AI 评审：在 linter、测试、安全检查之外作为第一遍评审。它可以更慢、更彻底，对照整个代码库甚至多个仓库，比如发现某个 API 合约改动会弄坏另外几个仓库。

一个 1,900 行 PR 的实验

她说有统计显示，单次评审超过约 400 行改动后，人的有效评审能力会明显下降。她故意做了一个 1,900 行改动的 PR，是她正在写的策略执行 MCP server 和 CLI 工具。整个流程跑完，只发现一个 bug：一个未处理的设置异常。她在 Codex 里本地修掉。她承认自己有偏向（每天都在用 Qodo），但认为这证明了她的流程有效。

她的规划模板来自 Aaron Francis（faster.dev）的审计类 skill，她强制 GPT-5.4 xhigh 在计划里写明要用哪些 skill，计划结构包括范围、规范合约（canonical contracts）、组件设计、测试计划、完成标准（definition of done）。

为什么需要独立的评审系统，而不是只用生成代码的那个 Agent 自己评审？她说 LLM 有偏向，编程 Agent 被优化成“加强版自动补全”，目标是尽快写完代码，所以需要一个架构和目标都对抗式的独立系统，才能找出细微的 bug。

她的清单和一个加分项

清单：定义质量标准；放到集中的上下文平面；在规划和生成时用 Agent 和 skill 拉取这些上下文；开 PR 前用 linter、测试和本地评审验证；把更重的代码评审自动化。加分项：用自动化迭代改进 skill 和规则。Qodo 的规则系统会根据 PR 和评论的历史建议新规则；她自己还用每周运行的定时任务分析所有 PR 的趋势，决定新增或改进哪些 skill，让反复出现的问题在评审之前就被处理掉。

10. Philip Kiely（Baseten）：怎样量化模型而不毁掉质量

直播位置 4:57:32–5:18:29 · 英文原题 How to Quantize Models (Without Killing Quality)

主持人的开场是：模型输出质量差，供应商卖你“垃圾 token”，谁的错？量化。Philip 在 Baseten 每天做推理。量化 Quantization 是把模型里的数字用更少的比特来表示（比如从 16 位降到 8 位、4 位），让模型更小更快。他说网上普遍怀疑推理供应商偷偷把模型压到 4 位来赚钱，而 Dax 早上也说过一些质量最高的供应商就是用 FP4 提供服务。他的目标是让 token 便宜、快 30% 到 50%，同时说明量化只是推理优化的几十种技术之一，“没人会因为推测解码或张量并行在 Twitter 上吵架”。

为什么推理慢，量化为什么两头都有用

LLM 推理分两个阶段。预填充（prefill）处理输入，主要受计算速度限制，决定首个 token 的延迟；解码（decode）逐个生成 token，主要受显存带宽限制，决定每秒 token 数，也就是把数据从显存搬到缓存的速度。图像和视频生成常常受计算限制，语音转写和合成常常受带宽限制。量化是少数同时缓解两种瓶颈的技术：数字更小，同样的带宽搬运的信息翻倍；低精度的计算核心更快；如果对 KV cache 做量化还能提高缓存驻留。KV cache 是模型保存已处理 token 的中间结果，避免重复计算。

麻烦在于生成式模型的行为是涌现的，相当于把一堆数字四舍五入再相乘，误差在整个推理过程里累积，logits 偏一点点，下一个 token 就可能变了。他讲的是训练后量化（post-training quantization）：从 Hugging Face 拉下已经训练好的权重，不再做蒸馏、微调或 RL，只想让它变快而不变笨。

数据格式与 NVFP4

  • 浮点数由符号位、指数位和尾数（mantissa）组成，指数位决定动态范围，也就是能同时表示多小和多大的数。
  • FP8 随 2022 年左右的 Hopper 和 Ada Lovelace 架构出现，FP4 随 Blackwell 进入生产推理。在 Ampere、Turing 或本地硬件上做的大多是整数量化，效果不太好，他认为业界对量化的坏印象主要来自整数量化。
  • FP16 有 5 个指数位，FP8 通常还有 4 个，只损失一位动态范围；到 FP4 又少两位，4 位只能表示 16 个值，却要映射原来 65,000 个值。
  • 办法是缩放因子（scale factor），可以在张量、通道或块级别加。目前最好的是基于块的 microscaling 格式。NVFP4 用两层缩放：每 16 个数一个 E4M3 格式的块级缩放因子（带尾数，更精确），再加一个 FP32 的全局张量缩放因子补足动态范围。这些开销都做进了 Blackwell 硬件。

哪些能量化

  • 权重里的大线性层通常比较安全，常常能降到 4 位。
  • 激活值和 KV cache：一两年前连 8 位都有风险，现在 8 位已经比较成熟。
  • Attention：别碰，除非那天你觉得自己运气特别好。
  • 层与层不同：输入和输出层更敏感，可能只量化中间层；视觉语言模型里视觉编码器小而敏感，可以保留原精度。他推荐朋友 Ali 一篇名为 “four bits” 的文章，逐层分析了一个图像模型。
  • 硬件和 kernel 支持：NVIDIA 说能跑不等于生产里跑得好。很多开源 kernel 工作还针对 Hopper 的 FP8，想跑 NVFP4 要准备做大量移植，比如把 DeepGEMM 移植到 Blackwell。
  • 模型越大越耐量化，单个离群值在万亿参数模型里的影响比在十亿参数模型里小。量化感知训练（quantization-aware training）也有帮助，比如 GPT-OSS 原生就是 MXFP4，他认为这是它在市场上经久不衰的原因之一。
  • 校准：用 NVIDIA ModelOpt 等工具计算新权重和缩放因子时，校准数据要贴近生产用法，拿聊天数据集校准一个用来写代码的模型不合适。

真实收益和质量检查

别按规格表推算 3.5 到 4 倍的提速，也别按 kernel 剖析推算 1.9 倍。实际观测到的是每降一级（FP16 到 FP8，FP8 到 FP4）快 30% 到 50%，相当于每秒多 60 个 token、首 token 少 100 毫秒、推理账单少几百万美元。

质量检查：先看输出。他放了两张同种子同设置生成的老虎图，一张全精度一张 NVFP4，看不出区别，而且他故意把标签对调了。对 LLM 和复杂 Agent，看困惑度（perplexity）不要上升；用原权重和量化权重跑同一套评测 Eval，差异要在噪声范围内；抽查函数调用、长上下文等。模型“变笨”也可能来自推理强度设置、聊天模板、新 checkpoint，不要什么都怪量化。最后他宣传了自己的书，扫码加入等待名单，现场合影私信他可以拿免费码。

问题：不难，但重复、排队

难点不在技术复杂度，而在大量例行请求：数据访问申请、建 schema、IP 白名单变更。流程很固定：查有哪些角色、谁需要访问什么、对方是否已有权限，最后生成一段对 Snowflake 执行的 SQL。但工单会在队列里等好几天。

两条原则

第一条半开玩笑：好 Agent 需要好吉祥物，她喜欢给 Agent 起名字。第二条：Agent 的权限要匹配工作流的风险。Snowflake 里存着敏感生产数据，而且是 SOC 合规系统，任何流程都必须可审计，不能让 Agent 改数据、搞乱报表。风险低的场景可以给更多权限。

  • Agent 能做的：理解请求，判断缺了哪些信息，收集上下文和做查询，生成 SQL，开 GitHub PR，并写 PR 摘要。
  • Agent 不能做的：写生产环境；执行它生成的查询（“万一它把整个数据仓库删了”）；批准自己的改动（可以让其他 Agent 做代码评审）；在没有约束的情况下行动。

架构

三部分：接收（工单、Slack 消息等）；Agent（一个 LangGraph 工作流）；受治理的执行。PR 出来后一定有人评审，确认准确、语法正确、没有授予离谱的权限；然后仍然走原有的标准化部署和 CI/CD 流程去执行，Agent 拿不到生产系统的钥匙。现在她的团队在被通知有 PR 待评审之前，甚至不知道有请求进来；最坏情况是 Agent 把需要人工处理的问题升级给他们。

为什么用 LangGraph：运维工作流不是一次完成的。请求常常信息不全，即使表单里问了“要读权限还是写权限”，大家还是会漏填，Agent 要去追问并等待；数据访问请求必须等数据所有者审批，不是 Agent 能决定的。所以有入口、重入点、出口和特定分支，Agent 要记住停在哪里。LangGraph 是有状态 Agent 的工作流编排框架，他们把状态记在工单上，回来时从断点继续，不用重跑校验步骤。

在哪里给自主权

流程步骤是确定的，但各步内部用 LLM，仍是非确定的。她说要想清楚哪里给自主权、给多少。“校验请求”只是一个带有效性标准的单次 prompt。“收集上下文”步骤自主性最高：每个用例要查的东西不同，所以有一个元数据子 Agent 连着 Snowflake MCP server，对元数据视图迭代查询，看到结果再决定下一步查什么，最后把结果整理成结构化输出。换成 Zendesk、Jira 等系统，就给它对应的 MCP。

“审查与修复”：不要盲信第一遍输出。他们给 SQL 模板，比如 Snowflake 的 CREATE ROLE IF NOT EXISTS，让 Agent 自己决定要不要建、建几个角色，但不保证它不会在角色名里插一个分号。所以生成后让 LLM 再审一遍（也可以用确定性检查，他们选 LLM 是因为它也擅长读 SQL）：语法是否正确、是否真的解决了原请求，比如别人要 Jira 数据，它是不是授予了整个数据仓库的权限。发现问题就有限次数地修复，仍解决不了就升级给人。

为什么能过安全和法务

  • 从有边界的工作开始：高频、造成瓶颈、步骤清楚、输出明确的请求。
  • 有推理、无权限：他们从没给过 Agent Snowflake 的写权限，Agent 照样有用。
  • 复用已有控制点：PR 评审可以有代码评审 Agent 加速，但人仍然要检查，包括检查评审 Agent 的输出；已有 CI/CD 能用就别往里塞 LLM。
  • 限定自主范围：不要让它一次解决所有事。
  • 为重入而设计：需要更多信息、等待审批、升级给人。

她留给大家的一句话：有用的 Agent 需要边界，而不需要更多权限。这是让安全、隐私、法务团队满意、让 Agent 真正上线的条件。

从工具调用到上下文膨胀

两年半前的 LLM 像一个没有手的大脑，后来工具调用变好，才能做像 Kody 这样替人行动的 Agent。早期每个 Agent 自己从头实现工具集成；远程 MCP 让工具可以分享给你从没见过的 Agent。但上下文随之膨胀：Cloudflare 的 SDK 覆盖 DNS、Workers、R2、清缓存等，工具描述加起来超过 170 万 token；整个 OpenAPI 规格要 230 万 token，超过最大模型的上下文。

他们先按领域拆成多个 MCP server（API、文档、Workers、可观测性），但这把选择负担推给了用户，部署 worker 用一个、看日志又要重新走一遍 OAuth。另一个问题是 LLM 在工具调用上容易糊涂：问某个日期，它会假设训练数据里的某个日期；工具一多就选错，很多工具名里都有 create。她的解释是 LLM 训练时见过全世界的代码，所以写代码很强，工具调用是后来加上去的。

Code mode 演示

她用自己周末 vibe coding 做的 Fluma（假的 Luma 活动平台）对比两个 Agent：

  • “周三上午 9 点在 Hyatt Regency Miami 办黑客松”：普通 MCP Agent 要她确认日期，猜的是 2024 年 1 月 10 日；code mode Agent 写代码调了一个获取今天日期的函数，直接建好活动。
  • “2026 年 5 月每天晚上 7 点在 Cloudflare party house 办一场 AI 工程 / MCP 主题的 meetup”：普通 Agent 发出一连串调用；code mode Agent 生成一段带不同主题的 for 循环代码。两边用时差不多，但 code mode 少用了约 70% 的 token，因为不用在上下文里背着所有工具调用。

服务端 code mode

客户端支持 code mode 很慢，她说父母是苏联人，常说想办成事就得自己来。于是他们在服务端实现：MCP server 只暴露两个函数。search 在规格里只找匹配的 API，即使把所有 Workers API 都搜出来也不到 2,000 token；execute 根据 search 给的 TypeScript schema 写代码执行，比如列出所有 worker、部署 worker、加访问控制。她现场走完 OAuth、选账号，search 返回 Workers 相关 API，execute 生成并立即部署了一个 hello world worker。

三种模式对比：普通 MCP 工具调用最费 token；客户端 code mode 高效但客户端支持不全；服务端 code mode 从 200 万降到 2,000，约 99.9% 的 token 节省。

怎么安全地执行 LLM 写的代码

直接执行没人看过的代码有风险：如果和应用跑在同一个容器里，它能读文件系统、带着数据发恶意网络请求、写死循环、吃光内存。替代方案都不理想：DSL 写过一次就不想再写；VM 启动慢、成本高；人工审代码比 VM 还慢。她的答案是 dynamic workers：基于 Cloudflare 运行了九年多的 Workers 技术，可以即时创建一个 worker 并立刻执行。可以设置兼容日期、模块，以及允许访问的出站主机；不设就完全不能联网。演示里，试图读 process 里的密钥，全局对象里只有 Cloudflare 默认提供的函数；试图访问 httpbin，返回“此 worker 不允许访问互联网”。

算力账：CPU 不够

她认为 Agent 的下一步是每个人随时跑很多个。现在大家主要在笔记本上跑 OpenCode、Claude Code、Codex，所以会场里的人都不愿意合上电脑；OpenClaw 火了以后大家去买 Mac mini，但这没法普及。她的估算：美国劳动力约 1 亿人，按 50% 并发（她说这很保守，Agent 不睡觉）；全球 80 亿人每人一个个人 Agent、50% 并发，需要 8,000 万到 1.6 亿颗 CPU，而服务器 CPU 年产量只有几千万颗，已经差一个数量级；每人三个、十个 Agent，就差好几个数量级。大家都在谈 GPU，很少有人谈这部分 CPU。

她的解法还是 isolates（隔离沙箱）。VM 每个应用都要起一个操作系统；容器共享操作系统，但每次要带上完整的语言运行时和应用；isolate 只导入生成的那段代码就执行，同样的硬件效率高约 100 倍，正好补上这个缺口。Cloudflare 九年前押注这项技术，没想到会以这种方式变得重要；也有其他公司在做 isolate 实现，她认为这是对路线的验证。需要 git、bash、文件系统的 Agent 仍然要容器，但消费级场景里 isolate 会越来越重要。

dynamic workers 已开放公测；可以用 Cloudflare Agents SDK 试 code mode；Workers AI 刚上线 Kimi K2.6。Cloudflare 在招人，她还带了“agents never sleep”帽子送给第一个到展位的人。

Pi 更精简：定义工具的方式和 AI SDK 类似，但创建 agent session 时启动的是完整的 Agent Harness。他在 AGENTS.md 里写“总是用法语回答”，代码里没有显式加载这个文件，跑出来的结果却是法语，因为它就是一个完整的编程 Agent。OpenCode 同样如此但更“开箱即用”，是客户端/服务器架构，启动时会起一个服务，自定义工具放在 .opencode 目录下。他的比喻是 OpenCode 像编程 Agent 里的 VS Code，默认配置好、可扩展；Pi 像 Neovim，开箱只有最基本的，但能无限扩展。他建议学 SDK 的方法是把 GitHub 仓库链接丢给编程 Agent，让它克隆到临时目录再问它问题。

GStack 和“用 markdown 写程序”

GStack 是 Garry Tan 的项目，在 Twitter 上被大量调侃（一天 4 万行代码、几十万行 vibe coding 的 Ruby 做出来的静态博客 Garry's List）。他一周半前本想去看笑话，打开 office hours 这个 skill，第一眼是一段 30 行、看起来像病毒的 bash 脚本。读下去他意识到这是一个程序：里面有 Agent 要运行的命令和步骤，定义了一个工作流，用自然语言在编程 Agent 之上构建了一个完整应用。“Garry 可能找到了什么。”

他自己的例子是 YouTube 数据同步：从 YouTube API 拉数据存进 Postgres，这是他日常工作需要的。以前是一个复杂的 TypeScript 项目，要处理重试、编排、cron，要解析视频赞助商、评论情感时再接 LLM，用的是 BAML。BAML 是一门为 LLM 调用设计的语言，给定输入和输出结构，它在底层保证模型每次都输出正确结构，把 99% 的成功率推到稳定可用；他用它和 Gemini API 识别出某个视频的赞助商是 G2i，“和这场大会一样”。

新的做法是把整个程序写成几个 markdown skill：顶层的 YouTube 同步 skill 写明步骤，配几个辅助函数（比如 fetch channel）。他说第一个版本里只有一份 markdown，写着“从 YouTube API 同步数据，这是 API key，存进 Postgres 数据库，祝你好运”，它也做得很好。加辅助函数只是因为要部署，想更稳。这种程序有一种近似自愈的性质：遇到限流错误，Agent 会自然地等一等再重试，不用自己写指数退避。可以在 Pi 里直接输入 /sync 运行；想放到云端沙箱定时跑，就用 OpenCode SDK 创建实例和会话，传一个让它使用该 skill 的 prompt，因为它是完整的编程 Agent，会读取 skill、AGENTS.md，甚至认证信息，他配的是 GPT-5.4 mini。

他的结论是这类东西的形态变化得很奇怪也很快。三个月前如果有人说他会上台为 GStack 和 markdown 编程辩护，他会笑。他每次学到新东西都会在脑子里画一条“它能做到这里”的线，然后困在线里，现在这样不行了，有奇怪的想法就去试，因为它可能真的能用。他观察到的方向是，Agent 被给予的自由越来越多。
