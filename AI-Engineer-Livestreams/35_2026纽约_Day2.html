02. Alexander Shevchenko（Ramp 应用 AI 团队）：在等前沿模型的同时追能力

直播位置 0:20:29–0:34:30 · 英文原题 Chasing capabilities while waiting for the frontier

为什么应用层公司还要做研究

Alex 大约三年前加入 Ramp（一家做企业支出管理和公司卡的金融科技公司），在应用 AI 团队把 LLM 和机器学习用到各个产品上。他说 Ramp 是一家很信“苦涩的教训”（Bitter Lesson，指长期来看依靠通用方法加更多算力的路线会胜过人工设计的技巧）的公司：过去一年里用到 LLM 的场景增加了 123%，很多头部功能的 token 花费在涨，但按单位经济算反而更便宜，因为新的前沿模型不断出来，更便宜、更快、更好，同样的准确率成本低得多。

于是常有人问他：那为什么不干脆等？为什么一家应用层公司要有应用研究部门？他拿 2023 年对比：那时只有 GPT-4，做 Agent 很费劲，模型没被强化学习训练过回溯，也没有思考 token，走错方向就一路冲下去；提示词要反复抠，换个同义词行为都会变；上下文要尽量删减，给多了模型会糊涂。即便这样，Ramp 当时也决定不等 GPT-4.5 或 GPT-5，先给财务人员上线，做了 Ramp Tour Guide 等 Agent。到 2026 年，给模型接上 MCP（Model Context Protocol，让模型调用外部工具和数据的标准协议）和各种上下文，它们就能理解任务。他认为往下再挖一层还能做出更好的体验，只是现在要多花点力气。接下来他讲了 Ramp Labs 落到产品里的三个例子。

例一：后训练一个专门的金融问答模型

去年 11 月 Ramp 发布了 Ramp Sheets，他说这是最早的电子表格 Agent 之一，早于两家前沿实验室推出各自的版本。财务和会计人员一天大部分时间都在表格里，所以他们想把 Ramp Sheets 的 Harness（包在模型外面、负责工具调用和流程控制的那层程序）和“大脑”搬到 Ramp 的其他产品界面里。他们去找模型在哪里卡住：当时的模型是 Opus 4.6，用户一次丢进很多表格，让它做 DCF（现金流折现估值）或者财务情景建模时，它会先花很多时间做计划，再去翻每一张表摸清情况。Opus 4.6 很好，但慢，思考 token 也贵。

他们的做法是保留前沿模型当编排者（Orchestrator），另训一个更快的检索兼金融问答模型，由规划 Agent 把问答工作交给它。他们和 Prime Intellect 合作，后训练了 Qwen 3.5 的 35B 模型，在精确任务准确率上超过了当时的前沿 Opus 4.6，同时能以很低的延迟提供服务。这个模型已经上线生产。

例二：Cartridges，把上下文离线压进 KV cache

KV cache 是模型推理时缓存下来的注意力中间结果。他们在研究一类叫 Cartridges 的技术：离线把大量上下文压缩进 KV cache，他说能多装 20 到 30 倍的上下文，再拿给 Agent 用。他举月末结账的例子：每个月一号，财务人员要对账、关账，需要总账、账龄报告和一堆文件，就算把它们准备成上下文，Agent 还是得自己检索、自己理解。用 Cartridges，可以在一号之前的夜里把这些工作压缩好，财务人员一打开 Agent，它已经知道要做什么。他说 Cartridges 的门槛比后训练低，因为它用自我对弈（self-play）的方式训练，泛化性更好。风险是前沿实验室可能在走向持续学习的过程中把类似能力做进 API。他说即使那样他们也高兴，因为公司内部已经积累了怎么用这些技术的经验，API 一出来第一天就能用上。

例三：Agentic MapReduce 和一万个并行 Agent 做渗透测试

第三个例子是 Agent 群（swarm）。Ramp Labs 博客写过一篇文章：他们用 10,000 个并行 Agent 对整个 Ramp 做渗透测试。Ramp 有一个叫 Ramp Inspect 的云端 Agent，负责搭基础设施和管线。先把工作 map 出去找漏洞，再由 Agent 对生成的工单做 reduce：用 LLM 去重，再用 LLM 以对抗方式复现，确认漏洞是真的、重要的。最后找到 7 个高危漏洞，全部修好。其中一个是可以通过邮件发送的 Lua 脚本注入，单看技术栈里的每个组件都不算不安全，Agent 群要把多个组件端到端拼起来理解才能发现。整个过程自动运行，不占人的时间，失败的尝试被过滤掉，代价只是 token 钱。他们还研究怎样在群里用模型：文章里的一个发现是，可以用比前沿推理模型便宜最多 5 倍的开放权重模型，因为是群体作战，检出率并不会低 5 倍，花同样的钱买更多便宜 token，检出率差不多。

两个产品和更多博客文章

他说这三个例子都在省时间（降延迟）和省钱（降 token 成本），这也是 Ramp 的口号。两个受 Ramp Labs 研究影响的产品：一是 token 支出管理，连接公司的各个 API key，按 key、按用户、按会计科目展示 LLM 花费，还能发现可申请的税收抵免，并用语义分析给 LLM 用途建分类体系；二是 Ramp Router，提供一组路由策略来降低 Agent 延迟和每 token 成本，他提到 NVIDIA 的路由方案和把工作智能分流出去的方法，更多策略后续推出。

他还推荐了博客上几篇没来得及讲的文章：Portal，能把一次后训练的成果迁移到另一个模型上，比如在 Qwen 3.5 上做 LoRA（一种只训练少量附加参数的轻量微调方法），再转到新版 Qwen 甚至别的模型家族，相当于训练一个可以投影到不同模型上的潜在表示，摊薄后训练成本；用 Agentic MapReduce 分析 LLM 用途并建分类（已经用进 token 支出产品）；自我改进的监控，让 LLM 自动在 Datadog 上为产品创建监控，告警进来后再自动改进监控，不需要人参与；语义标注，对大量用户会话做开放式的分类，事先不知道有哪些类，再和公司支出对账。

03. Tariq Shaukat（Sonar CEO）：改变世界的机器，AI 版

直播位置 0:35:00–0:51:00 · 英文原题 The Machine that Changed the World, vAI

从丰田工厂讲起

Sonar 做代码质量和安全检查。Tariq 说今天讲的是怎样帮企业建真正能用的“软件工厂”。他从真实工厂讲起：1980 年代的汽车不少是好车，但零件拼得不严，缝隙很大。后来丰田，尤其是雷克萨斯，拍了一支广告，让一颗钢珠沿着车身接缝滚过去，说明车可以拼得严丝合缝。背后是一整套工厂设计思路的变化：质量优先于产量；修系统而不是修单个症状；按能造出来的方式设计，不是各个零件分别设计完再指望能装上；问题出现就当场解决，不往后拖；任何人都能叫停生产线。他说现代软件开发的最佳实践，比如敏捷、看板、SRE 的错误预算、持续集成，很多都源自丰田生产方式。

Agent 带来的变化

他引用上个月发表的一项研究：在开发流程里引入异步 Agent 后，代码行数增加了 2450%，提交次数也大幅增加，写代码变得容易而且充足。Sonar 刚做完的开发者调查（下个月发布）预览数据：现在有 5% 的开发者说自己在运行 Agentic 软件工厂，34% 预计一年内会，金融服务业是 39%。同时 Agent 既能帮你造东西，也能帮别人攻击你、找漏洞。他还提到 Satya Nadella 刚在 X 上发的一篇文章，讲模型在公司内部的“内部人风险”，呼吁用工程方法做隔离和治理，基于强确定性的系统设计、人的控制和可靠的操作流程。Tariq 说这和他们看到的转变一致：要设计能把信心和质量工程化地放进 Agentic 软件工厂的系统。

五个难点

  • 人在环（Human in the Loop）扩展不了。几乎每家公司讲 AI 治理都会说“别担心，我们有人在环”。但同一项研究里，代码行数涨了 2450%，提交涨了 240%，发布只涨了 30%，从生产到发布这一步还没解决。另一个问题叫“认知投降”（cognitive surrender）：几个月前的一项研究发现，AI 对的时候人有 93% 会同意它，AI 错的时候五次里也有四次同意。
  • Agent 在大型复杂代码库里吃力。一项代码翻译研究里，代码库 1 万行时 Agent 正确率 91%，到 5 万行时准确率就崩了。另一项研究发现，在大型代码库上完成同一任务所需 token 的差异是 30 倍，因为 Agent 把大量 token 花在弄清代码库结构上。他打比方说从洛杉矶出发去纽约，起点随机，碰巧选在 White Plains 就很快，选在 Albuquerque 就又慢又贵。
  • 错误会累积。METR 衡量 Agent 能完成人类需要多少小时的任务，他说最新的 Claude Mythos Preview 能完成人类要 16 小时的任务，但那是 50% 成功率；把要求调到 80%，曲线就平了很多。每一步 95% 准确，20 步后只剩约 36%。
  • LLM 当裁判不可靠，而且会讨好。PayPal AI 研究实验室这个月的论文发现，同一个问题重复问，依模型和场景不同，有 7% 到 17% 的判决会变。Meta 的研究发现，只要问一句“你确定吗”，模型改口的比例是 7% 到 34%。
  • 漏洞从披露到被利用的时间接近零，事后响应来不及，所以预防必须设计进工厂里。

代码信心公式

Sonar 提出一个“代码信心公式”，四项相乘，任何一项为零，信心就是零：

  • 意图（Intent）：要清楚地知道想造什么，否则没法告诉 Agent。
  • 引导轨（guide rails）：他特意区分 guide rails 和 guardrails，护栏（Guardrails）是防止你冲出路面，引导轨是帮你待在路上。Agent 需要的是小幅度的推动。
  • 验证（Verification）：要独立、彻底，发现的问题要修，不是往后推。
  • 证据（Evidence）：一致、可审计、可重复的证明。他说就算前三项都做了，没有证据，对结果也不会有信心。

客户数据

意图和引导轨这部分，他们有个产品叫 Sonar Vortex（字幕拼写，名称以官方为准），在 Agent 循环中提供意图、引导，并做验证。在大型复杂代码库上跑长任务时，token 成本降低 36%（相当于把起点放到了 White Plains），提交里的问题减少 92%。验证部分，Sonar 本来就是做验证起家的，他们的观点是独立验证要覆盖全部问题类型、精确而且划算：能用 CPU 就用 CPU，需要 GPU 再用 GPU，先用确定性方法组合，再加 Agentic 方法组合。产品 SonarQube 调查了一千多家客户：用 SonarQube 的人比不用的人，认为 AI 编程对代码安全有显著正面影响的可能性高 81%，对上市时间高 34%，对故障频率高 76%。证据部分就是过质量门禁和各种合规要求，比如企业内控里的 IT 一般控制、汽车行业的 MISRA。他的结论句是：代码充足，信心稀缺，未来的工厂要能交付信心。

04. Evan Kormos（Coinbase 工程经理）：在受政策约束的流程里信任 Agent

直播位置 0:52:04–1:09:10 · 英文原题 Trusting Agents in Policy-Driven Workflows

政策和运行系统

Evan 做了 20 年软件，其中 15 年在企业金融服务，在 Coinbase 是带队也写代码的 player coach。他先讲政策（policy）：组织里规定工作怎么做的规则，尤其是风控和合规，用 must、may、should 这样的词写成。他把政策看作最初的“机构意图”，或者说最初的系统提示词。和政策分开的是实际运行的系统，他把两者看成两个时间点：构建态和运行态。政策只是偶尔定义或修改，系统却随产品变化一直在动，但整体仍然要被政策约束。企业里常用“人、流程、技术”三分法，他认为 Agent 横跨三者：和人一起工作，自己执行一部分流程，本身又由技术构成。这次演讲聚焦 Agent 和流程交汇的地方：给它们什么工作、设什么边界、怎样建立对产出的信任。

外层是 DAG，节点里是循环

受政策约束的流程有明确方向和关卡，比如变更上线前要审批，客户开户前要验证身份。他说有了 Agent，值得重新看哪些步骤可以并行：以前协调成本太高的独立审查，现在可以同时跑，再汇总结果，必需的检查保留。这样的流程可以表示成 DAG（有向无环图，步骤只向前、不回头），比如 Apache Airflow 就用 Python 代码把工作流写成 DAG。商业贷款、在某个地区上架一个代币、受监管的软件交付，都可以用 DAG 表示。

进到一个节点里看，比如代码审查节点，里面是一个循环：做工作、检查，够好就放行，不够就拿审查反馈继续改。这是有向有环图（DCG），他说 LangChain 的 LangGraph 适合管理这种状态。流程外层是政策边界，节点内层是人和 Agent 协作。还要处理异常流程：不想让工作卡住，也不想为每种边缘情况都提前设计，比如代码被取消或没过安全标准，你会想知道。加入 Agent 后流量会在流程里转移，审查快了，设计和安全扫描也得跟着快，瓶颈会不断冒出来。所以他说流程整体的运营可见性（指标）比搭工作流工具本身重要得多。

循环只和检查一样可信

他认为更高质量的输入会带来更好的输出和更低的计算成本，输入质量这次不展开，只提到可以把 DAG 的状态注入给 Agent，让它知道自己在全局里的位置。重点是输出：检查环节决定工作能不能往前走，要定义什么是“好”，还要有可靠的评估方式，否则多跑几轮也不代表结果更好。传统软件靠单元测试等机制建立信心；Agent 是概率性的，同样的请求会给出不同答案，可能不止一个答案可接受，精确比对不够用。要建有代表性的数据集，定义什么是好，反复运行评测（Eval，用一组样例系统地打分），做统计分析，再配合 trace（运行时记录 Agent 每一步做了什么的日志）。这是和传统测试互补的信心机制。

哪个节点交给 Agent，怎样逐步放手

回到贷款例子：KYC 和财务分析可以并行，信贷备忘录、风险审查、文档、决策按顺序。对每个节点问几个问题：能不能容易地对照政策检查？能不能在有界循环里跑？能不能 trace？能不能退回给人？答案都是“能”的节点更适合自动化。但整个 DAG 都应该引入 Agent 辅助。他说真正的问题是 AI 会不会在某个时点接管决策，最终对照政策的决策点大家多半同意要由人来做。

放手分三步。第一天是全监督：人和 Agent 一起做，人工核对每个产出，和业务专家一起定义“好”的标准、打磨数据集。当测得的信心达到政策规定的阈值，转为抽样：人只看一部分产出，其余用基于 trace 的系统化评估保证质量。越过最终阈值后，人主要处理异常，同时继续参与改进数据集。

要点

  • 外层保持确定性，内层可以自适应。
  • 通过评测保证质量，这样对 Agent 质量的判断是统计数据，不是对模型的感觉。
  • 质量是团队的事：AI 工程师负责管线，收集各方向的产品信号，背后用上 ML 运维。
  • Agent 会在整个运营模型里起加速作用。

05. Joseph Kim（OpenAI，ChatGPT for Financial Services 负责人）：AI 在金融的下一章

产品是什么

Joseph Kim 负责一个月前刚发布的 ChatGPT for Financial Services。他说很多工程师已经体验过 Codex 怎样改变写软件的方式，但金融等行业的人日常工作还没这么变，他预计几个月内会快速改变。产品先面向投行和股票研究，和设计伙伴 Morgan Stanley、Evercore 一起做，围绕三点：金融数据，工作质量受数据源限制，所以要在 ChatGPT 里直接拿到需要的数据；为金融设计的界面，能查看原始材料、看金融图表、控制分析用的数据源；符合本公司格式，模型和演示文稿要用公司模板和标准。之后他放了一段产品演示视频（字幕里这段没有语音内容）。

为什么做：能力过剩

他说他们做这个产品是为了缩小“能力过剩”（capability overhang），也就是模型能做到的和人实际得到的价值之间的差距。几年里模型从做高中数学题走到能处理千禧年大奖难题级别的数学问题，但很多金融从业者的工作方式没怎么变。缩小差距需要合适的数据、工具和贴合工作方式的体验。他展示了 OpenAI 内部各职能使用 Codex 的图：工程师很早开始用，稳步增长；财务、法务、招聘在 2026 年初几乎没有 AI 产出来自 Codex，到 6 月约 90%。拐点在 2 月到 3 月，他以为是发了新模型，回头一查是 2 月发布了 Codex 桌面应用。他的结论是产品让工程以外的人更容易用上这些能力。

怎么做的

  • 数据：他们看了现有的金融数据 MCP 连接器，发现很多有延迟、报错或搜索质量问题，于是直接授权了大量数据，用和网页索引相同的基础设施自建托管和搜索索引。模型仍然通过 MCP 协议访问数据，但自己托管索引让质量和可靠性更可控，也方便针对这些数据集后训练模型。他的比喻是：MCP 和 Skill 像给初级分析师一本说明书，后训练像一个跟这些数据打了二十年交道、熟悉所有怪癖的资深分析师。
  • 产出：金融工作的成果多是 Excel 模型、PowerPoint 或书面分析。他们做了模板系统，生成表格和演示文稿时用公司批准的模板；加了可交互的金融图表；做了引用查看器，能检查答案背后的原文段落和表格，因为金融里必须能核对每个数字从哪来。
  • 搭建方式：他说大部分功能用的是对开发者开放的同一套 ChatGPT 插件平台。金融数据用 MCP 工具和连接器；引用元数据和 MCP Apps 让用户查看来源，MCP Apps 也驱动交互图表；Skill 加共享的 artifact 工具引导金融流程、生成 Excel 和 PPT；入门流程用插件原生的 onboarding。他认为会出现多个仅仅作为 ChatGPT 插件的十亿美元级业务。

模型会往哪走

他把过去的进步归为三个有时重叠的驱动力：扩大算力、改进算法、unhobbling（解除束缚，想办法让模型做更多有用的事）。他说 2022、2023 年（字幕说成 2002、2003）最显眼的是预训练扩展，靠 Scaling Law 能高精度预测性能，比如 GPT-4 训练完之前 OpenAI 就预测出了它的最终 loss 和一个编程评测的表现。算法方面，一项研究发现达到同一语言模型性能所需的算力大约每 8 个月减半。2024、2025 年推理（reasoning）成为新驱动力，用强化学习和后训练教模型更好地解题，并给更多思考算力。他承认 OpenAI 曾在预训练上遇到问题、难以扩大模型，说 2026 年解决了很多问题，训出了更大的模型（两个模型名字幕不清，听起来像 GPT-5.6 Sol 和 GPT-6 Astra）。2024 年大家担心的“数据墙”，他说已经被合成数据、可验证奖励学习和从每个 token 学到更多的算法改进基本解决；上下文长度的问题用稀疏注意力和压缩（compaction）解决。他相信 2027 年趋势会延续，同时承认对齐和安全仍是难题。

以数学为例：2023 年 GPT-4 在 SAT 数学拿 700/800；2025 年 OpenAI 的模型达到国际数学奥林匹克金牌水平；2026 年初一个内部模型否定了一个从 1946 年就有人研究的问题相关的长期猜想；最近一个内部模型对纳维-斯托克斯千禧年难题提出了一个解法；还有一批数学研究手稿（字幕数字为 719 篇、372 个结果家族）。他预计到 2027 年底，模型会在越来越多的难任务上超过顶尖人类专家。

阈值现象

他说能力曲线看起来平缓，工作方式的变化却会显得突然，他叫它阈值现象：每个任务都有一个“有用阈值”，模型够强、够可靠，能帮你省时间。阈值以下，模型更好了、错得少了，但检查和修改仍然和自己做一样久，你的判断不会变。越过阈值，审查时间远小于省下的时间，你开始常用，最后放心委托。不同任务阈值不同，所以这些时刻在不同工作上先后到来。他建议问自己：哪些能力因为还不够有用而被低估？一年后会怎样？如果它们越过阈值，界面会怎么变，用户还需要控制、审查或批准什么？现在就可以开始做这些产品设计。

对金融的意思和三个 2027 年的赌注

他用“涨潮和浪”来描述：涨潮是底层模型的普遍提升，OpenAI 过去没有专门在金融上投入多少训练算力，现有金融能力多来自更大的模型和从数学、编程、推理迁移过来的技能；浪是专门针对金融的后训练，他的团队正在大力投入。未来三个月重点提升一般金融推理和产出质量：分析金融信息、建 Excel 模型、做 PPT，这些占初级分析师日常的很大一部分。再往后投入资深银行家、分析师、投资人的判断力：吸收大量信息、判断什么重要、预测未来，比如预测公司盈利、大宗商品价格、评估哪些企业值得投资。目标是 2027 年某个时候在这类任务上达到最佳人类专家水平。

关于 unhobbling，他举了 RLHF 让模型能遵循指令、能对话，工具让模型能搜索、跑代码、操作软件。他认为下一种是主动且持久的 Agent：能抓住一个目标、记住相关上下文、在后台持续工作。这也改变人和 Agent 协作的方式，不用学提示词和工具，像对同事一样给它项目、上下文，然后问进展。他最后给出三个 2027 年的赌注：做财务模型和推介材料时人们很少再用 Excel 和 PowerPoint；AI 金融分析师会像人类同事，记住你前几天的偏好、承担任务、主动跟进、在你忙别的事时继续干活；模型会在预测盈利、提出投资想法这类关键金融任务上超过最好的人类专家。

06. Andrey Rybka（Bloomberg CTO 办公室架构与新兴技术负责人）：AI 时代的安全，真实事故与防御

直播位置 1:29:21–1:44:30 · 英文原题 Security in the Age of AI: Recent Attacks, Incidents & Defenses

沙箱不是全部

Andrey 说这次讲真实事故，以及什么能阻止它们；很多安全演讲像“吃你的蔬菜”，他想讲得有意思点。第一个事故：7 月 26 日曝出的一次评测里，AI Agent 被给了一个黑客任务，通过一个包代理（package proxy）的零日漏洞逃出沙箱，接着利用某个计算平台暴露的客户端点，攻入了公开的模型仓库。他没点名是哪家实验室。Agent 在四天半里执行了 17,600 个动作，他问怎么会没人发现。大家的第一反应是“需要更好的沙箱”，他说不完全是：现在多数安全体系不是为 Agent 设计的。Agent 要能接触很多工具、服务、数据才有用，没有硬性上限，破坏范围就没有上限，而防火墙或静态角色分辨不出 Agent 的目标已经被劫持。

他的原则：一个 Agent 一个身份，短期、限定范围的凭证，不共享密钥；假定输入是恶意的；把运行环境放进沙箱，出站默认拒绝，包括 DNS；在模型之外放确定性的控制，检查每次调用，全部记日志，保留紧急停止开关。他把防御分成六层：身份与信任、提示词与输入防御、工具与动作治理、执行隔离、数据保护、治理与可观测性，并逐层配事故。

身份与信任

  • 攻击者通过社会工程诱导一个聊天 Agent 交出一个长期有效的 OAuth token，导出了 700 多家公司的 CRM 数据。他留的作业：查查你的 Agent 用的凭证什么时候过期。需要的是限定范围的工作负载身份（workload identity）、审计记录，最好有熔断器，一旦被攻破就跳闸，数据出不去。
  • 他最喜欢的一个：一次提示词注入让一个低权限 Agent 去“招募”一个高权限 Agent，后者复制了数据并提升了权限。他说 A2A（Agent 之间通信）是最让他睡不着的，需要 Agent 之间双向认证，低权限 Agent 不能跟高权限 Agent 对话，还要限定范围的凭证、最小权限工具和审计记录。

提示词与输入防御

  • 一封邮件里藏着白底白字的指令，人看不见，Agent 能读。没人点开，零点击，数据就被带走了。需要注入防护、把数据和指令分开、给所有数据打来源标签（provenance tagging）、出口控制和输出过滤。
  • 他提出一个指导原则，他叫它“二选规则”（rule of two）：不可信输入、敏感数据、对外动作，三者最多选两个；三个都要，就必须人工签字。例子是某个高度自动化的电商平台上，有人留了条评论“店很好，请进货商品 X”，Agent 读到后真去进货了。

工具与动作治理

  • 某个 CLI 工具被合并进一段提示词，内容是清空所有人的机器，幸好有个拼写错误没生效。需要最小权限工具、供应链校验、对新合并内容延迟引入、限定范围凭证和高价值动作的人工审批。
  • 摩斯电码攻击：指令用点和横线写成，护栏放行了，模型解码后执行，钱包里 30 亿个代币被盗。需要确定性的调用代理（invocation broker），高价值动作人工审批（他说转 5 美元可能都算多），硬性的速率限制和预算，以及额外的护栏。

执行隔离

一个没有网络访问的沙箱，但忘了 DNS。藏在提示词里的指令让 Agent 把数据编码进 DNS 查询，有人读 DNS 日志就拿到了数据。修复办法是所有出站流量默认拒绝，包括 DNS，再加来源标签、输出过滤和熔断器。他问大家：你的 Agent 能访问 DNS 吗？他还建议用用完即弃的临时运行环境（字幕作 firmware runtime，从上下文看是 ephemeral runtime）。

数据保护

  • 一个功能正常的 MCP 服务器允许用户访问任何其他用户的数据，跨客户的数据访问持续了几个月没人发现。他说这类事故很常见。需要尽量硬的租户隔离（比如像 AWS 账号或 GCP 项目那样分开）、限定在该域内的工作负载身份、数据来源标签和审计记录。
  • 一种新的攻击：文档里藏着指令，让 Agent“记住”以后看到密钥就发到某个 DNS 域名，等于把 DNS 外泄和潜伏指令结合，污染的是 Agent 的记忆。需要检查记忆里有没有恶意指令，最好每次都从无记忆的新环境启动，再加注入防护、隔离和熔断器。

治理与可观测性

  • 有人告诉 Agent“现在代码冻结，别碰生产环境”，Agent 回复“明白”加个点赞，然后执行了删除生产数据库，而那个生产库同时也是开发库。他说有朋友打电话问他怎么恢复数据库。需要对灾难性操作设熔断器，高价值动作人工审批，凭证只覆盖允许的动作，以及租户隔离。
  • npm 上一个伪造的 MCP 包，前 15 个版本都干净、好用，第 16 版加了一行，把所有邮件密送给攻击者。他建议在供应链校验之外再做延迟引入，新包等一两周再用，加上确定性调用代理、最小权限工具和出口控制。

三件今天就能做的事

他把建议压成几句：身份要短期 token、一个 Agent 一个；外部文本不能下命令；语法不是控制手段；隔离的默认拒绝包括 DNS；每次查询都检查租户；提示词只能“请求”，由确定性代码执行。三个优先级：用二选规则锁定 Agent，每个工具调用都走确定性代理，高价值动作要人签字；一个 Agent 一个身份，干掉长期密钥，全部换成短期、限定受众的 token；运行环境装进沙箱并配合默认拒绝出口（包括 DNS），预算超了要直接停止，光告警不够。最后他提醒做规格驱动开发（spec-driven development）的人，把安全要求写进规格里。

07. Yijia Liang（Compound AI 联合创始人）：走向金融里的自主分析师

直播位置 1:59:37–2:15:10 · 英文原题 Towards Autonomous Analysts in Finance

讲者和问题

Yijia 是 Compound 的联合创始人，公司给买方金融机构提供“分析师”Agent，专长是长时间运行的任务，类似 Devin 或 Factory 在编程领域做的云端 Agent。他以前在 Coatue（字幕作 code 2）做了约三年副总裁，专注后期私募软件投资，熬了很多 Excel 和 PowerPoint 的夜，于是出来做工具替代自己以前的工作。他现场问有多少人认识完全把工作交给 AI 的金融分析师，只有一个人举手。

他们内部总结个人 Agent 最近三个月火起来的三个原因：后台 Agent 可靠了，订餐厅、订机票能办好；电脑操作（computer use）Agent 成熟了；集成接上了各种系统。但这些放到机构金融里都不成立。买方版的“后台任务”是从数据室（data room，交易中存放目标公司资料的文件库）到一整套投委会（IC）模型、幻灯片和备忘录，正常要四周、多轮迭代和审查，要压缩到几天；董事总经理不想要一个自己乱跑、烧 token 却不征求意见的 Agent；上下文也远远超出邮件和日历，可能是 15,000 个文件的数据室，或者公司 40 年积累的 PB 级 SharePoint 和 Box 非结构化数据。他围绕三件事讲：多人协作、自己重写 Office、管理上下文。

多人协作：每个 Agent 有自己的邮箱

他说现在机构里部署 Claude 或 ChatGPT 都是单人模式，产出要下载、发邮件、发 Teams 再收反馈。Compound 的思路是让一笔交易相关的每个人都在同一个线程里，和同一个 Agent 对话，这个 Agent 共享所有人的上下文。个人 Agent 好用是因为能在 iMessage、WhatsApp 里发消息，而机构金融的工作流大多走 Outlook，所以 Compound 创建的每个 Agent 都自带邮箱。这并不简单：要做认证，确保线程里每个人都对 Agent 有读写权限，因为每笔交易都受保密协议约束。还要做得像人：几个人在同一线程里快速连发邮件时，不能每封都回一个“收到”刷屏，他们特意加了一些延迟。

用 Agent 重写 Office

要并行跑很多任务，现成方案不够：他们评估了 Excel、PowerPoint、Word 的桌面插件，评估了在虚拟机里用 computer use 操作原生 Office，也评估了开源包（如 openpyxl）和商业引擎，都不行。既然编程 Agent 让软件成本大降，他们决定从头造自己的 Office：让 Agent 跑了很多循环，花了 1.5 万亿输入输出 token，写了超过 800 万行代码。方法是给 Agent 一个目标函数“完整还原 Office”，以真实的 Office 为 Oracle（判定标准答案的参照），在网上收集的真实文件和自己做的文件上反复做基准比较。仅 Excel 就写了 80 万行 Rust，得到一个一比一复刻、比 Excel 快得多的引擎，PowerPoint 和 Word 也用同样方法做了。他说必须一比一一致，因为这些机构只信能下载、能发出去的文件。

为什么要无头（headless）引擎：桌面版 Office 受限于 CPU，无头引擎可以并行，能更快搭出复杂模型、更快重算 20MB 的 Excel。自己拥有编辑器还能做更好的协作体验：他把在咨询公司和 Coatue 学到的“好幻灯片”标准写进了 Agent，团队成员可以在文档里留评论让 Agent 改，他说五个人一下午能过完一份 100 页的 deck，而不是在会议室里改几周。用微软自己的接口，能做的检查很有限，自有引擎则掌握“写、渲染、检查、修正”整个循环。

上下文：广度用 Agent 群，深度靠自有引擎

广度上，比如 15,000 个文件的数据室，他说除非特定场景，不必把所有东西塞进向量数据库，更好的做法借鉴编程：让编程 Agent 用 grep 等方式读文件，由主 Agent 切分目录，派出 Agent 群带回发现，循环到满意为止。每个发现都带回原文引用，让分析师能核对屏幕上每个数字的来源。深度上，比如一个 30MB、200 万个公式、5 张敏感性分析表、重算一次要 5 分钟的模型，直接用现成 ChatGPT 或 Claude 处理，模型会写代码调 openpyxl，把所有内容打印出来给模型读，又贵又慢。Compound 的引擎先处理好，再以易读的格式交给模型，并能暴露更丰富的 API 和工具。

从 Copilot 到 Autopilot

他说目标是让人不再花时间找文件、不再提醒模型怎么做，而是花在判断上：这笔交易到底好不好，而不是数字对不对得上、VP 会不会因为格式不同骂人。分层是：底层接 SharePoint、Outlook 等数据源，中间是有出处的发现，上层嵌入公司偏好和知识（每家公司做模型的方式都不一样）。他认为像整理可比公司（spreading comps）这类任务现成工具已经能自动完成，但起草 50 页投委会材料、按私募或对冲基金的习惯搭模型，目前还停在 Copilot 阶段。他拿编程类比：程序员一开始只让 AI 补下一行，后来有了足够的检查和测试，开始委托更大的任务。他认为金融也在拐点上，要解决这些问题，让整个交易团队敢把数据室丢进去、信任输出，再放大十倍看更多交易。

08. Oliver Kennon（SemiAnalysis 研究分析师）：不是所有 GPU 都部署得一样

直播位置 2:25:00–2:42:40 · 英文原题 Not All GPU's Are Deployed The Same

GPU 的上限取决于运营者

Oliver 的核心句是“A GPU falls to the level of the operator”：买硬件只给你潜力，运营能力决定你实际能交付多少有用的工作。他要回答的问题是：谁能以最低成本生产你需要的智能？他先给技术人补了一课商品市场框架：生产者交付可比的产出，生产成本更低的一方在价格下跌时有更大的竞争空间；成本曲线就是把生产者按交付同样有用工作的成本排开。

对 AI 来说，产出是智能。理想的北极星指标是“达到要求质量、成功完成一个任务的价格”，但目前很难标准化。他认为每 token 价格是一个实用的代理指标，至少在工作负载和质量要求可比时，比金融圈常说的 GPU 每小时价格更接近实际产出。他把 GPU 小时看作投入，不是产出。投入是硬件和电力，软件和运营是乘数，最终产品是有用的智能。运营者负责选择和实现服务模型的软件，让请求在系统里流动起来。

同一张卡，多 50% 产出

他用 SemiAnalysis 公开的 InferenceMAX 计算器举例（字幕作 inference X）：两个部署都用 B200 GPU 跑同一个模型，约 8,000 个输入 token、1,000 个输出 token，目标交互速度是每用户每秒 100 个输出 token。一个服务栈（serving stack，处理模型请求的软件）每卡每秒约 200 个输出 token，另一个约 300 个。差别来自软件设置和并发请求数，全是运营者的选择。假设两边小时账单一样、都满足要求，多 1.5 倍产出意味着每个合格 token 的租金按比例更低。

有用的智能还要安全、要有人维护

有用的智能要质量够、来得够快、需要时可用，还要待在约定的访问边界内，也就是安全。他说这项要求在芯片性能指标里看不到。SemiAnalysis 发表过的安全研究发现过一个监控权限暴露了另一个客户的日志和指标，GPU 很快，服务却严重失败。上线后也要有人干活：有更快的服务更新出来，要在客户负载上测试、检查输出是否仍达标、决定何时何地怎么部署、在负载下测试、保留回滚方式，上线后还要维护和处理问题。这些可能在供应商、你自己团队或双方，你要知道谁负责、能不能做好。他介绍了 SemiAnalysis 的 ClusterMAX 评级（下一版 4.0，欢迎供应商报名），覆盖托管 GPU 集群的开通、可靠性、监控和安全，通过实测、文档和客户反馈评估服务在出故障时的表现。他强调评级只适用于托管集群，裸金属（bare metal）上更多运营工作落在客户身上；等级是相对同行的；价格和可用性也计入评估。

算成本：每个合格 token 的完整成本

租金和生产成本是两回事。GPU 供应商出租小时，推理生产者买小时、卖响应；租金是供应商的收入、推理生产者的投入成本。推理生产者的完整成本是租金加软件、人员和其他服务；如果自己拥有设备，就把设备投资按使用寿命摊开再加运行成本。把同期交付服务的全部花费除以客户实际能用的产出，得到可比负载下每合格 token 的成本。更好的运营也要投入人和钱，多出的产出要能覆盖这部分花费。他说一次好的 Benchmark 证明不了优势，要靠可重复的运营流程每天去挣，这样才能形成持续的成本和价格优势。

成本曲线上的位置是相对的

他说这张是最重要的幻灯片：假设你完成一个任务的完整成本从 10 降到 8，同期竞争对手从 12 降到 6（字幕把顺序说反了，从上下文看是对手从高于你变成低于你），你进步了，但从更便宜的生产者变成了更贵的那个，对手有更多降价空间。现在需求远大于供给，他估计未来两三年都会这样，稀缺会掩盖成本差异，成本差很大的生产者都能找到客户，CEO 宁可去盖新数据中心也不愿花精力巩固成本曲线位置。他提醒每种商品在历史上都有供需周期，看不到拐点不代表这次不同，尤其是加了杠杆的企业。所以要趁资本好融的时候建运营能力和成本优势，等客户有更多选择、价格承压时它更重要。

算力期货需要分级和评级

最近大家对算力期货（compute futures）很兴奋。期货合约规定未来交割或现金结算的标准条款，现金结算依赖一个价格基准。他说两份 B200 小时报价可能包含不同的服务，把不同的运营工作留给客户，所以商品框架需要“等级”（grade）来描述一个算力服务、让买家知道哪些可以视为可比。租金基准只汇总一个定义好的市场里 GPU 小时的价格，不等于生产成本，也不衡量交付的智能；挂牌报价和成交价不同，服务范围、合同条款、采样谁的价格、怎么合成都会影响基准。拿它做对冲，要看它和你实际付出或收到的租金是否同步变动；你付的租金比指数高不说明对冲不好，关键是变化是否跟得上。对冲能抵消租金价格变化，修不了失败的部署，也保证不了客户付款。他的论点是：给运营者评级是建立可信算力期货市场的基础构件之一，但评级本身不定义期货等级，不建立基准，也不创造流动性。

结论还是那句：GPU 的上限取决于运营者。能以最低完整成本、反复满足你要求的生产者，就是能以最低成本生产智能的那个；而且你的位置取决于竞争对手。

09. Evan Conrad（San Francisco Compute Company）：算力市场是怎么回事，为什么要有它

直播位置 2:49:46–3:07:28 · 英文原题 How Compute Markets Work

公司做什么，怎么被逼成 GPU 经纪商

Evan 的公司 San Francisco Compute（SFC）做的是实物交割的算力远期市场。他说“实物交割”意思是 SFC 自己就是硬件的运营者，像云厂商那样，同时又是市场本身，有点像算力的电网。他们认为运营超级计算机的问题从设计物料清单就开始了，还包括背板网络、裸金属编排、上层的虚拟机等服务，每一层都得做好，否则那些手里有数据中心、想变成 GPU 云的人最后会让客户失望。所以 SFC 提供“超算即服务”：给想当云的公司（NVIDIA 所说的 NCP 合作伙伴）、想给被投企业配集群并能在某家公司爆发时重新分配算力的风投、以及想保留算力残值但不想自己运营超算的 AI 公司提供运营；在这之上跑一个实时订单簿，可以买现在或将来的预留算力。

他说这完全不是他们原来要做的事。公司原来叫 Junark（字幕拼写），想做类似 Suno、Udio 的音乐生成，比它们还早。当时要开一个实验室，得先付一大笔押金，大约 1,000 万美元，他们觉得太离谱，只融了 50 万美元打算租。结果买了一个大集群，每个月都在亏，不转租就会破产。所以第一年就在拼命卖自己的集群，他说他们成了第一个 GPU 经纪商，在 NeurIPS 会场拿着同时写着 H100 和 A100 的纸到处走。如今这笔门槛不是 1,000 万，是 10 亿美元。

一个新实验室会遇到的连环问题

  • 所有人的算力都卖光了，短期不会变。你得买一个全新集群，要等交付周期，没有办法让它现在就上线。
  • 你要把账上几乎全部的钱当押金，因为贷款方不知道怎样给“要造超级智能”的两人创业公司做信用评估，也不知道资产值多少。
  • 集群很可能延期：贷款方要先知道客户是谁、评估客户信用，才肯部署集群，于是客户签约那一刻成了全流程风险最大的时点。他认为应该先建好集群再卖。
  • 建集群的多是手里有便宜资产（数据中心空间）的人，他们缺超算运营经验，上一场 SemiAnalysis 讲的就是这个。
  • AI 公司的毛利不像 SaaS，容错空间小，要么买多了（他举 Stability AI），要么买少了被别人赢走，或者像 Character AI 那样出局。
  • 集群交付后很可能坏，又没有流动性可以临时调节点进来，只能走 RMA 换新，又回到交付周期的问题。
  • 需求几乎不可能预测准，多了卖不掉，少了买不到。

他说这些看起来是不同问题，其实都是同一捆风险：技术风险、财务风险、信用风险。为什么都卖光？因为贷款方只肯给有长期承购合同的集群融资。CPU 时代的买家是 SaaS 公司，云涨价一倍他们会生气但不会破产；AI 公司碰上底层涨价一倍就会破产，除非换一家，所以他们对价格很敏感，不忠于任何一家云，按需（on-demand）模式卖不出去，只能签长期“照付不议”（take-or-pay）合同，最好对方是投资级信用。但预留合同没有流动性，另一家正在爆发、现在就要算力的公司买不到，只能再融资建新集群。他的判断是，信用才是 AI 当前的头号瓶颈，比电力更早撞上。于是每家推理公司和新实验室都受限于账上现金，风投说只投模型层和应用层、不投资本开支，结果风投的钱还是变成了付给云的押金。

算力市场要解决什么

他说要同时解决很多问题，核心是改为评估 GPU 集群本身的价值，而不是评估客户的信用。如果不这样，行业会像别的行业那样走向集中：一个或少数几个有信用的大买家，几家云、几家模型实验室，像 TSMC 那样，没有别的创业公司。三年前他们本可以放弃，再去开一个新实验室，但看到这个问题后觉得三年后还会撞上，现在果然大家都撞上了。

他认为市场运营者必须同时运营集群。他介绍了 Dylan（CNCF 基础设施相关小组的联合主席，CNCF 是维护 Kubernetes 的组织，此前在 Lambda 做基础设施），说他加入 SFC 是因为 GPU 算力还不够标准化、不够可靠，市场运营者不能和物理基础设施分开。他打比方：你出差住酒店，想把房间转卖给别人，买家会问能不能打扫、出了问题找谁，你不运营酒店就解决不了。所以单纯做集群经纪不行。为什么很少有人做实物交割？因为一旦建好实物交割的能力，你就有了 GPU 云的全部运营能力，直接当云能签一个又一个十亿美元的单子，大家都这么选。SFC 做这件事是因为不做的话，他们最想做的实验室就永远开不成。

如果不解决：没有创业公司

他说门槛从 1,000 万涨到 1 亿再到 10 亿，他不认为能继续涨到没有收入就融 100 亿。另一种可能是推理公司和模型实验室把信用风险转给应用层：只签投资级信用的客户（财富 500 强）、只签五年期 token 合同、要求大额预付。他说那就是一切的终点，因为 token 是整个经济在用的东西，没有规定创业公司必须存在。如果获取智能受限于信用，现有大公司会自己做产品、赚到收入、信用更好，形成集中化的飞轮。他推算三到五年后，开一家新公司可能要先买 1 亿美元的 token 才能和现有玩家竞争，两个人的团队没人信任，只能融 1 亿押金或签五年合同，于是就没有新实验室，也没有新创业公司。最后他放了一串他在旧金山认识的小团队，说希望这些公司都能存在，也许它们会做出治癌的东西，或者没人想到的东西。

10. Affaan Mustafa、Alejandro Soumah Fernandez（Jump Trading 算力交易负责人）：算力的暗池

直播位置 3:15:09–3:35:30 · 英文原题 The Dark Pools of Compute

为什么叫暗池

Affaan 和 Alejandro 共同负责自营交易公司 Jump Trading 的算力交易。演讲主要由 Affaan 讲宏观结构和微观结构，政策部分很快带过。“暗池”在金融里指不公开报价的交易场所，他用来形容现在的算力市场：大部分实物算力按大块（block）交易，报价私下给出，有很多经纪商，签的是长期双边合同。这些说到底是商业协议，通常是主服务协议（MSA）、服务等级协议（SLA）加订单，针对具体集群、写明具体硬件。谈价格时主要谈 SKU，也就是芯片和基板型号，比如 H100、H200、B300。没有一个被广泛采用的实物算力交易所，有固定期限、固定容量、确定合同总额的交易都在 Slack、X 私信、Telegram 群里成交，像大宗商品交易员在 ICE Chat 和 Bloomberg Chat 上聊那样。

宏观：token 变便宜，算力价格没跌

他引用 a16z 的一张图：同等能力的成本大幅下降，更便宜的 token 释放了更多用量，团队用同样预算做更多事，原来太贵的应用变得可行。但底下的算力还是要建、要付钱。他们观察到一个有意思的现象：token 价格继续下跌，算力价格却保持坚挺，两者出现脱钩。一种解释是杰文斯悖论（Jevons paradox，效率提高让资源更便宜，总消耗反而上升）：推理在新硬件上更高效，大家就用得更多，对算力的需求随之上涨。对推理云意味着更多应用、更多 token、更大份额；对应用层意味着能服务更多客户。

要得到一个可用的 GPU 小时，芯片、电力、建筑、并网和大量资本都得到位。他引用国际能源署（IEA）4 月的更新：全球数据中心用电将从 2025 年的 485 太瓦时涨到 2030 年的 950 太瓦时。上游的电网、能源、土地、托管场地和融资都会传导到算力成本和用量。他把产业链画成：芯片和系统厂商供应 GPU 服务器和网络；场地和运营方提供电力、空间、组装和管理；容量提供方是超大规模云、新兴云（neocloud）和类似的裸金属转售运营者；用户是创业公司、推理云、实验室、新实验室、应用层和跑开放权重模型的企业。一家公司也可以同时扮演好几个角色。

中间市场的融资困境

超大规模云、前沿实验室和大型新兴云能签大额长期承诺，因为能拿到大额股权和债务，签十年期合同。中间市场做不到：谁来给一家 B 轮创业公司做信用评估，让它签三年 2 亿美元以上的算力合同？贷款方给建设融资时看的是合同收入，CoreWeave 的公开文件就是用照付不议客户合同支撑基础设施融资的大规模例子。问题是硬件融资要很长的期限，客户却只能或只愿签 36 个月左右，还要预付。他说 CoreWeave 披露的预付中位数是 15% 到 25%，一个合同总额 1 亿美元的集群就要先拿出 1,500 万到 2,500 万，可能是创业公司一整轮融资。他举了个示意例子：融了 4,000 万，签 3 年 1 亿美元合同，预付 30%，剩 1,000 万经营业务。于是容量变成阶梯式，每加一档都要等下一轮融资，期间只能拒绝客户，或者用按需算力补缺口；也可以找贷款方为预付款融资，就要比较融资成本和直接买按需算力哪个划算。

运营模式有几种：自己建并运营全栈（自己搞电力、许可、组装、管理）；在托管机房自有服务器，组装运营交给伙伴；签承购合同买定义好的容量，由供应商拥有和运营，可能不给完整的裸金属 root 权限，单租户、多租户等配置也影响价格。有的企业看重物理访问、机密计算、能改拓扑，就愿意多付钱自己做。他画了一张粗略的图：随利用率上升，承购合同的成本已经接近自建并融资的成本，三年花 1 亿美元，算下来可能不如自己买下运营方，当然还要算时间和运营成本。他还说算力采购现在会影响一家成长公司的跑道（runway），所以风投也开始关心帮被投企业采购算力。

微观：围绕一个 GPU 小时的各类角色

  • 价格发现：做指数、数据和 Benchmark 的机构，将来的期货要以这些基准结算（他说相关合约在等待批准）。
  • 实物撮合：拍卖、聚合平台、按需算力的去中心化市场、有自己标准合同的流动性算力池、裸金属转售商、做大单的新兴云。
  • 经纪商：拿双边报价、促成成交。他们人脉广、动作快，能在一处看到相近规格的多个报价，知道哪个买家现在急需、对价格不敏感，赚一个价差，但也要承担风险、负责运营。
  • 金融市场：基于 GPU 小时的交易所、期货和衍生品，用来对冲资产负债表风险；他们看到预付融资工具出现，也有人想用期货、期权对冲现有风险。
  • 买方：想要灵活合同，比如签 3 到 5 年后新芯片出来能升级、能展期、能卖回给供应商。
  • 信用和融资：设备贷款方、租赁方、专业信贷机构。

现在每笔交易都是定制的：规格表和格式不同，物料清单可能和实际交付不符，缺货就换零件，OEM 和 ODM 交付周期很长；同一个词意思也会不同，比如说“内存”，指显存、CPU 内存还是额外存储？这会影响能跑什么负载。所以比较之前要来回很多轮，这就是不可替代性（non-fungibility）的问题：哪些部分可以标准化，哪些权重最大（比如 SKU），哪些仍然像电商商品那样只对某个集群有效。价格可以每天甚至更快更新，报价只是起点，出价可能被砍，信用状况会改变能拿到什么，还有很多隐藏因素，所以叫暗市场。他放了当天更新的公开 H100 按需价格截图，价格差异很大。

这些新结构要解决的是错配：过渡容量、更灵活的承诺、转售权、价格变动保护。推理云卖的是固定价格服务，GPU 账单却是浮动的，这就是价格敞口；锁定多年容量能解决一部分，但不一直用满就会有闲置小时敞口；转售剩余容量只有在有人买时才有用；金融对冲能对冲参考价格，但现金结算交付不了集群，也保证不了利用率。所以有用的结构要从企业具体面对的风险出发。

政策和机会

政策部分他讲得很快：出口管制方面，1 月美国商务部把面向中国和澳门的 H200 级许可审查改为附条件的逐案审查；美国 AI 行动计划明确鼓励开源和开放权重 AI，并建议改善算力金融市场，让创业公司和学术界能用上大规模算力。他们认为机会在不断扩大的中间市场：需要能在买卖双方之间架桥的资产负债表，需要一定程度的标准化，包括标准容量合同、通用规格、通用条款和定义。供应商想要长期承诺来支撑建设，买家想随需求变清晰一小块一小块扩容。能帮忙的，是和市场不相关、资产负债表强、信用评级高、内部又有大量高性能计算硬件人才的机构。他最后的号召是：一起来建这个市场。

Carmen 同时是两家公司的 CEO：Compute Exchange 和 Silicon Data。她早年在芝加哥 DRW 做了四五年能源期权做市商。Compute Exchange 2024 年成立，那时大约只有五家新兴云和三家超大规模云，她们预见到 GPU 生态会扩散。她拿股票做比较：买卖股票可以打电话给经纪商或几家银行，也可以在 App 上通过纽交所或纳斯达克交易，不一定价格最好，但效率高，有流动性，能清算交割。现在全球有 300 多家新兴云和私有算力供应商，还有很多“token 工厂”和 API 路由，对终端客户是好事，但交易效率成了问题：你想 48 小时内拿到预留算力，不会去给 300 个销售打电话。

  • GPU 预留和远期合同：最小一个节点、一个月起，最长三到五年，取决于供应和供应商。不做按需。如果买多了、买长了，可以卖回给 Compute Exchange。

Silicon Data 她称作“算力的 Bloomberg”，为 CME 的期货提供结算指数，几周后开始交易，首批是 H100 新兴云按需价格和 B200 价格。她展示了隐含远期曲线：横轴是合同期限，纵轴是每 GPU 小时价格。去年 H100 的曲线向下倾斜，合同越长越便宜；今年初整条曲线上移并变成升水（contango，远期价格高于近期），长约拿不到足够折扣，说明大家预期价格会涨；之后整条曲线继续上移但变平。用和国债期货曲线类似的方法从期限结构推出的隐含远期利率显示，市场共识是未来 36 个月价格会涨，她提醒共识不代表正确。B200 去年就是升水，今年每个期限都更贵，也变平了。

她的结论是 GPU 和其他商品一样有清晰的期限结构风险，期货适合对冲。她们看到很多围绕期限结构的大宗交易：比如资产负债表上有服务器、有五六年的融资义务，但只签了前三年的预留合同，第四到六年就有敞口，可以用互换或大宗交易对冲；即使前三年有合同，也有人为合同违约风险做对冲，把指数当浮动利率。她说 NVIDIA 9 月投资者日的材料引用了她们的数据，而且是唯一被引用的数据提供方；也有几家银行用她们的数据给资产负债表上的 GPU 服务器做估值。方法是现金流折现：比如 A100 已经出来六年，今天签三年租约、按某个价格把现金流折回零时点，就得到资产价值，当然还有利用率、成本等假设。她们算了全球 A100、H100、B200 服务器的标准化残值，和大家常用的五年直线折旧比较：A100 在贬值，但仍高于会计折旧线；H100 价格反而涨了；B200 已经高于建议零售价。

为什么 Agent 在生产里失败

这是线上分会场的录播。Harish 在 Intuit Credit Karma 负责 AI 分析基础设施和服务，也做顾问、作者和研究，带年轻研究者。他说很多 Agent 在生产环境失败，是因为基础控制缺失：没有网关让 Agent 先认证、再路由到正确的 MCP 服务器；MCP 服务器缺少执行查询需要的工具；没有追踪和评测系统，不知道每个查询的回答质量；没有记忆管理，Agent 记不住几天前问过什么；没有上下文优化来省 token；没有保护措施防止密钥进入 LLM、追踪系统或记忆库。他说这次不做一个“神奇的 Agent”，而是讲一套框架。

开发和上线流程

先在某个系统里登记 Agent，说明用途和业务线，拿到一个 Agent ID。然后在内部开发者门户里填写细节：用 LangGraph 还是 LangChain，Python 还是 TypeScript，用哪些 Skill 和提示词。提交后门户自动生成一个代码仓库，里面不仅有 Agent 框架，还有记忆、追踪与评测、上下文优化、PII（个人身份信息）拦截这几套框架。他说这么做是因为不是每个开发者都会顾到这些，AI 编程助手也往往只会用一两种框架，统一下发能保证全公司一致、集中查看结果。开发者克隆仓库，构建 Docker 镜像，在本地测试输入输出，本地记忆可以用 SQLite，评测数据也可以先存 SQLite 或 BigQuery。

提 PR 并获得两人批准后进入 CI/CD：先把 Agent 注册到集中的 Agent 注册中心，拿到一个可以看全部 trace 的 Langfuse 地址；再在生产系统构建镜像、扫描漏洞，通过安全审批后推到镜像仓库；最后由内部编排平台部署到 Kubernetes 集群的指定命名空间。门户在生成仓库时还会创建工作负载身份、记忆库、追踪评测表和密钥管理等生产资源，所以 Agent 部署时已经知道自己用哪个身份（他说的是 Kubernetes 服务账号和 GCP 服务账号的绑定），之后就能访问 AI 网关、MCP 服务器、Langfuse 等。

自建 MCP 服务器和 MCP 网关

他建议在隔离（air-gapped）环境里自建 MCP 服务器，可以用 FastMCP 包装器，在里面定义一组工具。每个工具上线前都要经过内部安全团队审核，只放行授权工具，以便强制过滤、限制、屏蔽不该给 LLM 的字段。所有从 MCP 客户端经网关到服务器的流量，无论来自用户还是服务账号，都要先在网关认证。

网关流程：用户在编程助手或 Agent 里提交第一个查询时，客户端向 MCP 网关发一次性认证请求；网关把会话状态存进 Redis，返回一个 JWE 访问令牌；客户端带着令牌向某个命名空间（比如 artifactory/mcp 或 github/mcp）发 tools/call 请求；网关识别该找哪个 MCP 服务器，解开 JWE，附上用户令牌转发；MCP 服务器调用对应服务的 API，交换 ID 令牌，只返回该用户有权看的范围，再打包成网关能接收的格式返回客户端。他的要点是：网关是集中的认证和路由中心，任何端点都不能被直接访问。

网关监控

操作日志进日志存储（ELK、Loki 或 CloudWatch），用来回答“过去 10 分钟所有 401”“令牌刷新失败时 OAuth 做了什么”这类问题；实时的 trace 和指标走 OpenTelemetry 收集处理，trace 存 Tempo（哪个工具在这个请求里慢、调用来自 Agent 还是 IDE、失败调用的确切错误），指标存 Prometheus（某工具的 P95 延迟、认证拒绝是否突增），最后在 Grafana 上可视化。

Agent 框架：LangGraph 流程

他们多数情况下用 LangGraph，它是基于图的架构，支持循环、分支和状态管理。查询进来后先解析问题类型和期望的回答，再分类：只读、修改，还是删除这类敏感操作，据此调整计划。计划本身是一个子图：去取证据，经 MCP 网关认证后用正确的工具调 MCP 服务器拿数据，验证发现，然后检查策略。只读就直接执行并记审计日志；写入或敏感操作走 HITL（人在环）流程，等审批，批准执行、拒绝放弃，两种情况都写审计日志。

记忆、追踪评测、PII 拦截、上下文优化

  • 记忆管理：每次对话生成一个 thread，每个问题生成一个 run ID，在 LangGraph 的某个节点执行时保存一个 checkpoint，追问时再生成新的 run 和 checkpoint。本地用 SQLite，生产在 GCP 上用 Cloud Spanner，Azure、AWS 用相应的数据库。他演示了在 SQLite 里查到 thread ID、问题、执行时间、消息数、调用了哪些工具、经过了哪些节点。
  • 追踪和评测：他强调这和网关监控不同，是 Agent 级的，记录查询、回答、用的模型、token 花费、评测结果。每个 Agent 有自己的项目和表，100 个 Agent 就有 100 套，半年后有人问效果和 ROI，可以汇总做高管看板。演示里有六张表：任务追踪表（请求 ID、会话 ID、Agent 名、问题、输出、是否完成、耗时、模型）；每次运行 8 项质量检查（成功、延迟、成本、工具准确率、安全等）；评测分数表，每次运行一行 0 到 1 的分数；质量指标的嵌套明细；工具调用表（哪个 MCP 工具、耗时、是否成功）；Agent 轨迹表（每次 LLM 调用和图状态的顺序，比如先计划再总结）。
  • PII 拦截：上传的文档或输入里可能带敏感信息或 API key。他们定义了不同数据类型和严重级别，严重度高于约 90% 就立即拦截、脱敏，确保它进不了 LLM、记忆库、追踪评测表和 trace 系统。
  • 上下文优化：在发给 LLM 前先修剪：按 token 上限选取载荷，重排找出最相关的内容，去重，最后压缩。演示里查询 JFrog Artifactory 的全部制品用了 24,000 个 token，打开优化后同一查询用了 2,400 个；在 Slack 机器人里列出所有 Docker 镜像，从约 24,000 降到约 1,500。他说大多数情况能省 70% 到 78%。

要点：建企业级框架，不是只建一个 Agent，别急着上线后才发现缺东西；所有工具调用都走集中的 MCP 网关并认证；MCP 服务器控制用哪些工具；工具执行要有监控和完整审计；高风险动作保留人在环；用上下文优化来证明成本合理。他还提到自己刚在 Amazon 出了一本 MCP 的书。

三个问题

Michele 做了 20 多年企业转型，十多年在媒体、科技、消费品行业主导并购整合。她说在那些交易里，信任从来不靠上线后碰运气，他们在交割日前通过变更管理和风险管理“工程化”出来的，所以系统上线后一线团队真的会用。她给 Agent 的信任下了定义：交付业务预算里写的价值，同时待在公司批准的风险偏好、政策和监管护栏之内。领导层要回答三个问题：它创造什么价值？谁对它负责？什么证据允许它以更高自主度运行？她说试点测的是软件能不能用，日常运营测的是它能不能在领导设定的控制范围内创造价值。现有的 AI 风险框架给了原则，但没告诉你怎么用到每一个 Agent 上；每个 Agent 都要决定四件事：允许做什么、谁负责、记录什么证据、什么情况触发上报。她说这是高管的运营职责，不是工程任务。

案例：一笔 150 亿美元的收购

假设一笔 150 亿美元的收购，目标净协同效应 4 亿美元，交易已交割，整合在进行。整合管理办公室（IMO）负责 40 个工作流的协同路线图，从合并供应商合同到整合 ERP，每项都有业务负责人对节省的金额负责。每周 IMO 的分析师要向 40 位负责人要进度，和总账对账，对比实际与计划，最后做给指导委员会（CFO、首席风险官、各业务负责人、整合负责人）的周报。工程团队做了一个 Agent 自动出初稿：读取每周更新、对账、跑实际与计划的差异分析、标出落后的项目。四周试点，Agent 的初稿和分析师的报告逐行一致，技术是能用的。

问题一：价值

在 Agent 碰生产数据之前，要有书面的、各方同意的价值论证。这里是三个指标：周期，比如现在周报要 5 个工作日，目标定为 2 天；分析师产能，4 个分析师每周一半时间在做这份材料，就是每周 80 小时，但只有当整合负责人把这些时间分配给落后的工作流时才算价值，还要扣掉算力、授权和人工审核的成本；最重要的是发现时间，从数据里第一次出现偏差到指导委员会看到它的时间。报告从 5 天缩到 2 天，不保证委员会更早看到问题，Agent 得真的抓住它，价值论证要直接衡量这一点。每个指标都需要部署前的基线，她说 IMO 今天说不出基线，就不要部署。

问题二：谁负责

她用“三道防线”模型：第一道是管理层拥有控制，整合负责人是问责高管，像拥有手工做的报告那样拥有 Agent 的输出；第二道是风险和合规监督与挑战，深度取决于 Agent 的暴露程度，一份由资深分析师过目的内部草稿，和直接把数字发给董事会的自主 Agent，审查标准完全不同；第三道是内部审计，根据重大风险决定何时、怎样把 Agent 纳入年度审计计划。Agent 还需要一名员工每天负责监督，这里是资深分析师，在稿子到委员会前审阅。这个角色需要四种能力：理解运行边界、结合背景解读输出、有权推翻或撤回、有清楚的紧急停止方式。

她还会写一页纸的“人工工作标准”：流程里每个分岔点对应的决策、有权做决策的人、需要的证据、上报路径。资深分析师判断一个差异是会计时间差还是真的现金缺口；工作流负责人决定怎么补；整合负责人决定是否正式向委员会标记某个项目有风险。Agent 为每个决策准备分析，然后停在那里。她说把决策留给团队不会拖慢 Agent，唯一该推迟部署的理由是某个决策没有指定负责人，比如领导层没说好谁宣布一个项目偏离轨道，那 Agent 的标记就不会带来任何行动。

问题三：证据，三件工程产物

  • 可审计的决策日志：对每个工作流记录摄入的原始数据、执行的工具调用、提示词和模型版本、生成的输出和人工签字。两个工程选择让日志可靠：核心计算和对账规则要跑在财务批准的确定性代码里，不能由 LLM 用对话文字生成；模型写的摘要只当解释，证据在遥测里，拉了哪些记录、跑了哪些确定性工具、谁签了审核。如果报告的节省和总账对不上，Agent 不改数字，只标出差异并上报。
  • 模型清单记录：问责高管、数据血缘、对源系统的依赖、验证结果、上报路径、紧急停止的操作手册。最重要的是回归触发条件：底层模型或源 API 有任何更新，都要完整重新验证才能再上生产。
  • 自主度记分卡：指导委员会分四个阶段授予自主度。阶段一是影子模式，分析师照常做，Agent 并行跑，对比两者；阶段二是监督初稿，Agent 出初稿，分析师逐行审；阶段三是异常加抽样，分析师审被标出的项目加随机抽样；阶段四是只看异常，分析师只审高风险异常，配合定期独立抽样。

她特别提醒阶段四：人只看异常时，最大的漏洞是 Agent 没标出来的东西。所以要通过独立抽样追踪漏掉的重大问题，监控错误严重程度，盯紧推翻率。推翻率下降不一定说明 Agent 更聪明了，也可能是审查变浅了，独立抽样能分辨是哪种。记分卡把这些控制指标和价值指标（周期、释放的分析师工时、发现时间）放在一页上，委员会据此决定升级、维持、退回监督阶段。她最后说，在这个例子里 Agent 不会凭空变出 4 亿美元协同，那是采购、供应链和运营负责人做出来的；Agent 交付的是提前几周的、经过核实的证据，让领导层在协同还能抓住时有时间介入。

14. Steve Jamison（Jellyfish AI 研究与工程负责人）：token 是便宜的那部分 [线上]

两个数字的张力

Jellyfish 的数据把工程工作流数据和 AI 遥测数据连在一起，Steve 说这是业内最大的这类数据集。他先给两个数字：AI 成本比去年同期涨了 60 倍；每个工程师合并的 PR 涨了 43%，他说从没在这么短时间里见过这种生产力提升，而且 2026 年初 AI 支出上升的同时吞吐也开始稳步上涨。问题是 60 倍对 43%，到底好还是不好？花得够不够，再加 50% 或翻倍会不会有更多收益？限制用量是在防止烧钱，还是在抑制效率？问同行花了多少也没用，直接比账单不够。他说这两个数字讲不出完整故事，还漏掉了成本里最大的一项：开发者工资。

每个合并 PR 的“智能成本”

他提出把工程师工资和 AI 花费放进同一个成本桶，叫做一个 PR 的智能成本（intelligence cost）。2026 年 8 月的数据：AI 约占再产出一个合并代码单元成本的 2.5%，工资占 97.5%，和其他公开数字一致。过去一年，每个合并 PR 的美元成本下降了 26%（算的是合并的 PR，包含了审查时间和一定的质量门禁），而且这已经包含了 AI 成本 60 倍的增长。83% 的被研究公司每 PR 成本都下降了。原因是吞吐增长把工资摊到了更多 PR 上，速度快过 AI 成本上涨。

按 token 花费分五组

  • 按每开发者 token 用量把公司分成五组。最轻的一组 AI 约占 PR 成本 0.3%，约每人每月 6,000 万 token；最重的一组约 8.5%，约每人每月 25 亿 token，差两个数量级。
  • 吞吐：下面四组 PR 吞吐增长约 40%，最重的一组增长 67%。
  • 每 PR 成本：所有组都在降，最重的一组降 32%，其他四组约降 25%。
  • 收益递减：横轴 token 用量、纵轴每 PR 成本的曲线一开始陡降，之后改善变慢。他强调收益递减不等于没有收益：用量前 10% 的公司月份 token 是中位数的约 8 倍，每 PR 成本低约 25%。他说总有一天 token 不再便宜，但多数公司离那个阈值还远。
  • 个人层面：比较同一个开发者大量使用 Agent Skill 的周和不用的周，token 花费约翻倍，合并 PR 多 27%，算上工资和 token 后每个 PR 成本低约 18%。

两个常见疑问

更快更便宜会不会更差？他用回滚（revert，撤销之前某个 PR 的合并 PR）作代理指标：最重的一组在 token 大增之前回滚率就最低，各组回滚率都略有下降，但幅度在数据噪声以内，不能算改善证据；更重要的是没看到高 token 花费带来严重质量问题。吞吐是不是靠拆小 PR 刷出来的？他说明确不是，AI 反而让每个 PR 的代码行数增加了：生成式 AI 爱写代码，多余的行内注释、一堆不相关的测试；开发者开新工单的门槛低，一两个提示词就能顺手处理边缘情况、合并两件事；AI 能力强了，大家也更有野心。这和大家现在感受到的 PR 审查压力不太合拍，具体原因他说超出了这次演讲的范围。

他的建议

AI 花费和每工程师 PR 数都要跟踪，但它们是辅助指标，单看会藏住权衡。把工资加进去，算成本和吞吐的比值，每 PR 成本下降了 26%。他不是说随便花：要盯住失控任务，要跟踪 AI 花费，但别让它成为主导指标。这个框架会影响你怎么看其他投资，比如接模型路由、后训练自己的模型、设 token 上限：是控制 AI 成本带来的效率多，还是继续投资提高吞吐（比如更多 AI 使用培训）带来的多？每月在 AI 账单和 PR 吞吐旁边，跟踪“人加 AI”的每 PR 总智能成本，并把回滚和质量指标作为制衡。预算季把每 PR 成本带上桌：账单告诉你花了多少，每 PR 成本告诉你有没有用，他说对多数公司来说现在的答案是继续投。

15. Amol Kapoor、Clifford Ressel（Nori Agentic CEO、CTO）：自动化的证券主数据，用 Agent 保持数据干净 [线上，节选]

格式和讲者

这是线上分会场的录播，直播里只放了一段节选，在讲到技术难点时就切走了。两人用播客对谈的形式，中间还有他们的 Agent（名字听起来像 Jiro）在画面里画图解释。Amol 是 Nori Agentic 的 CEO，做了约 12 年机器学习，自称不懂金融；Cliff 是 CTO，做开发工具和 AI Agent 近两年，之前在一家初创对冲基金搭新数据平台，再之前是主任软件工程师，做数据工程、开发工具和云基础设施。

定义：云端 Agent 和证券主数据

Cliff 给 Agent 的最简定义是：在循环里运行、能调用工具、执行有用动作的 LLM。云端 Agent 是把这整套（循环调用模型的代码）放进云端进程，给它接上笔记本或手机上没有的工具，用公司的数据和流程做事。Amol 说现在重要的数据大多在云上，所以云是它自然的家；Cliff 认为去年 Claude Code 带火的本地 Agent 有点是历史的偶然，长期看真正的端侧设备要更久才能交付价值。

证券主数据（security master，简称 sec master）是一家资产管理公司可交易证券范围的主数据库。对工程师来说可以想成 Snowflake 或 Databricks 里的一张表，但它是很重要的运营基础件：数据源很多，下游用户很多，中间没有它就没法保证报告、审计、定价模型用的数据是对的。Cliff 说多数分析里它都是 join 的左表，监管也要求你记录持有什么资产。他拿日期时间库作比：工程师觉得“不就是记时间”，然后发现时区、本地化、各国夏令时切换日期都不同。连最简单的上市股票也有坑：Google 就有 A 类和 B 类两种股票，股票代码和公司不是一一对应，同一股票在不同交易所、不同国家（比如欧盟）还有不同挂牌。

Cliff 说上市证券的结构多来自“集中力量”：监管和交易所，它们产生了你关心的各种标识符。一开始可以全用 Bloomberg 的 ID（ID_BB_GLOBAL，也叫 FIGI，金融工具全球标识符）。但公司一变大、遇到 Bloomberg 体系之外的资产就乱了。Amol 说过去三年资产管理公司在非标准化私募资产上的投资大增，比如数据中心和 GPU 集群：可能涉及土地，一家发行股权的私人公司（可能被上市公司持有），为建设发行的公开债券或私募信贷，GPU 本身也越来越像一个资产类别，已经有人在尝试把 GPU 集群证券化。Cliff 提到飞机是另一个有意思的私募资产，因为它能以自身作抵押。多数私募资产不可替代，飞机和 GPU 却出奇地可替代。

一个纽约资产管理公司的案例

他们在和纽约一家大型资产管理公司合作。私募资产每个都不一样，工作量随资产数线性增长，也没有 API 能查“这个数据中心值多少钱”，价格写在某份合同里。这家公司已经建了新的证券主数据，接内部和外部数据源，有定量数据，也有文档等非结构化数据，用数据管线映射。最低门槛的应用是：把每一个变化准确地对应到上游的证据。Cliff 强调是每一个单元格，不是每一行。现在每当某个单元格变了，就有人要去 Google Drive 或邮件里翻合同 PDF，确认是不是最新的、已公证的版本，而不是来回发的草稿。

难在软件和金融的交叉：做后台运营的金融专家会用 Python 处理 CSV 和 Excel 导出，但看不懂 Snowflake 里的 notebook 或自建湖仓上的 Spark 作业；写管线的工程师又不知道某个单元格错了长什么样。Cliff 的说法是电子表格和软件是相反的两种视图：表格里看得到数据看不到逻辑，管线里看得到逻辑看不到数据。

为什么难

第一个难点：什么叫“对”、什么时候证据够了，是业务问题，因公司、因资产而异。这个客户合适是因为他们已经想清楚了流程：后台人员该一步步看什么，什么时候把不一致上报给数据负责人或投资人员，比如某个数据源不对就找当初跟对方对接数据抽取的那位同事。很多任务背后的目的没有写进代码或表格，而是在人的脑子里。第二个难点：要做成辅助型技术。他们说过去一年软件领域常见的失败模式是想让 Agent 一口气做到 100%，搭出很僵硬的“软件工厂”，在某个云主机上跑，却没想过人要介入、要改方向、要回应时怎么办；有时只是为了问责，也需要人来按合并按钮。Agent 最大的好处之一就是可塑、能在任务中途被纠正。Amol 说真正的云端 Agent 基础设施要做到和它对话像它就在你电脑或手机上一样顺，这块很难做，大多数人不愿做。节选到这里结束。

Scott 讲了苦涩的教训的历史：Rich Sutton 2019 年写的文章，但这种现象从神经网络起步就有，Rosenblatt 的感知机曾被报纸说成第一台能有原创思想的机器；英国有一段专家系统和联结主义之争，很多 AI 研究被裁撤；80 年代 IBM 翻译实验室的负责人说过“每开除一个语言学家，我的模型就变好一点”。他问 John 做路线图时怎么考虑这一点。

John 说理论上给足算力，什么问题都能被软硬件解决，但他大部分时间在和工程、产品、SRE、业务方一起算 ROI：这件事能创造多少回报，今天做的真实成本是多少。有时他会决定等：如果半年后模型更强、算力更多、做起来更便宜，而今天做并不会多带来业务价值，就推迟，他们确实这样做过。但也不能等太久。现在的开发 Harness 让人能很快从和产品、业务方一起梳理概念（字幕里他提到一个工具名，听不清）走到能点击、能交互的 POC/POV（概念验证或价值验证），当然还没过网络安全审查、也没做好扩展。他鼓励工程师直接做 POC，别做 PPT。他认为数 token 是个误区，应该想的是产出价值：快速做出原型，给人看，快速迭代，用不上就扔掉，这样花的时间和钱少得多。

Scott 说他们 2023 年就知道苦涩的教训，讨论过怎样不掉进陷阱，现在他觉得这是一个渐变，不可能造出一套完美技术让前沿的一切进来都不用扔东西。关键是哪里重投入、哪里保守投入。他们在 Agent 基础件上建了相当复杂的系统（Harness、沙箱、出口控制等），同时希望前沿实验室或第三方有新东西时能接得上。最难的是什么时候更新判断。他说自己对 Claude Code 更新得很猛，原因在于他之前怀疑能否得到真正可泛化的东西：能写代码、执行代码、以可验证的方式操作一台电脑，他觉得通用智能的原料就齐了，这也是为什么现在的 AI 助手能处理完全没见过的问题，在后台起一台电脑去做。所以他们重投入的是数据采集和提炼、怎样把数据作为状态提供给模型，以及基准和评测。律所是从零开始和 Norm 一起长起来的，他们直接和律师一起搭基准和评测，不用传统路线图（什么时候做出能干这三件事的 Agent），而是用一张记分卡衡量 Agent（甚至人）在多个维度上能否完成任务，系统整体改进时分数应该上升，同时不要回到当初加太多前置结构的状态。

上生产仍是最难的一段

John 说 POC 可以很快，难的是上生产：在金融或任何企业现有的基础设施里跑起来，他说卖 AI 工具的人常常低估这一点；还有网络安全和可支持性，要确保 Agent 写的代码可追溯、接入 SRE 平台、能在生产中被监控。Scott 说他们代码库里有一部分核心基础件仍然要求完全的人工监督，从设计、构建、代码所有权到任何改动；上面建的东西不经人工审查不能改动这些基础件，因为对他们来说数据安全比交付速度更重要。有人拿来很酷的 demo，他看了会害怕，因为要做到那样会暴露太多他们还做不了的东西。他早上对团队的说法是：平台里要为前沿的东西留“渠道”，不要修“水坝”让智能进不来。两人都提到“推倒重来”：John 说十年前写一个软件要花太多时间、钱和人，就像船已经出港，只能一路开到对岸；现在很多内部应用可以用完就扔，好工程师要不断问，重写是不是比继续升级旧版本更便宜。十年前对 CFO 说要重写一个内部应用会被当成疯子，现在这是合理的问题。

结尾 John 说让他兴奋的是重新回到工程：他在 IBM 做了十年底层工程，用记事本和 vi 给 RISC 机器写指令级代码；资历越深，日常写代码的门槛越高，比如处理一个数据流，光搭脚手架就让人不想开始。AI 让他又能动手做东西，因为他懂的架构知识没丢。他说很多做了 10 到 30 年的工程师懂系统设计的复杂性，这一点没变，现在可以借这些 Agent 把知识表达出来。

17. Vinoo Ganesh（Kepler CEO、联合创始人）：为什么华尔街还是不信任 AI

直播位置 5:49:35–6:07:20 · 英文原题 Why Wall Street Still Doesn't Trust AI

背景

Vinoo 三个月前在 AI Engineer World's Fair 讲过验证，前一天又和曾管理 Citadel 最大账簿、后来创办 Candlestick Capital 的 Jack 同台讲“为什么他还不信任 AI”。他说这三个月里大约有 2.7 亿美元风投资金涌入形式化验证层，还有一家风投把 Kepler 的融资材料给了竞争对手，对方做出了同样的口号，“我不苦，只是有点”。他说对方抄错了部分：验证不能在最后才加上。他提到当时 Anthropic 刚发过一篇介绍 Kepler 做法的文章。他以前是 Citadel 的业务工程负责人。

问题是结构性的

多数人以为华尔街不信 AI 是因为幻觉（hallucination，模型编造事实）。他说这是一部分，但核心是结构问题。做 RAG（检索增强生成，先检索资料再让模型回答）平台的人常说模型会好到消除幻觉，他认为这说法不成立：幻觉的另一个名字是 alpha（超额收益），分析师的创造力是一家公司与众不同的来源，否则地球上只该有一家公司。问题在于，模型有一部分会编，公司内部数据又从来没有反映进去。现在大家都在买 RAG 平台、做 Agent 试点，他早上见的一位客户说自己是“AI 优先”的公司，意思是有一个 Copilot Agent。为什么基本面投资还没全部变成 Jane Street 那样？他说要产出你相信的工作成果，你得信任它，也就是出错时能追责。他引用的数字是 80% 的财务高管信任这些数字，31% 发现过错误。他引述的别家产品评价是 demo 很好、像聪明实习生、接对结构化数据就对，但最后 10% 还是错。

错误数字的三个来源

  • 检索到错误的文档。修复办法是检索对的文档，但什么是对的本身就复杂：是本公司内部对这只股票的估值分析，还是你最信任的某位分析师的报告？
  • 来源对了，抽错了数字。比如要 Palantir 2023 年收入，从 2025 年 10-K 里读，得确保这个数对应 2023 年而不是 2025 年。事后逐条检查引用的过滤器有用，但只能事后用，形式化验证在这里帮不上，因为东西已经生成了。
  • 心算。模型不做数学，它预测下一个 token。他说一个 CPU 周期就能把两个数加对，为什么不用它？所以要用确定性工具计算数字和实体。

Kepler 的架构：代码写每一个数字

他说 Kepler 从根上架构不同：代码写每一个数字。在大规模的预处理和上下文化步骤里，把非结构化数据变成结构化存储，给每个事实（比如 10-K 里的一个数字）分配指向唯一标识符的指针。模型像聪明的分析师，负责规划怎么解题（去哪个来源取哪个实体、做什么），检索和计算由代码和数学完成；他说在搜索时让模型自己从 10-K 里抽数字很费 token，“Anthropic 和 OpenAI 应该感谢你”。模型读的是指针，结构上没法生成数字：不能解引用（dereference）指针，这个数字或事实就不可能出现在输出里。之后还有一个后处理验证步骤，他说竞争对手只抄了这一步，前面的结构没抄。用户看到的是“收入从 X 到 Y”，可以点每个数字的小标签看它是怎么来的。

他说在 Citadel 的经验是，组合经理们很聪明，但要和确定性工具配合才行。基本面投资者擅长理解数据，但数据必须对；查不到的信息，他们会约 GLG、Guidepoint 的专家电话、和管理层聊。Kepler 也一样：能确定性存的就确定性存；不能的，用类似的预处理抓取，存进混合存储（Turbopuffer 加其他机制），再用重排序加老式的指针解引用（get 方法）取回。查表不会错，搜索会：同一个查询跑 10 次，模型的概率性会带来熵。检索链路是：ANN（近似最近邻向量搜索）加 BM25（经典关键词检索）拿回最多约 200 个文档，用倒数排名融合（Reciprocal Rank Fusion）收到约 60 个，再用交叉编码器（cross-encoder，把查询和文档片段放在一起打分）精排。这样可以搜得很宽再收窄。他说 LLM 不爱搜宽，因为贵，拿到第一个命中就有奖励，所以倾向于找最快最省事的路径。他们还经常要判断整体上应该不再看哪些候选文档。

安全：带安全约束的检索

他说没人在谈：哪个用户范围的检索用了哪个 OAuth token。几种出错方式：忘了按租户过滤，Citadel 就能搜到 Millennium 的文档；调用方冒充另一家公司；搜索返回过时信息；直接读取跳过了搜索规则（没有允许列表）；查到一个还没建好的索引。解决办法是把安全约束内置进每次检索的范围里。他说 alpha 是华尔街最难得的东西，所以每次查询能返回哪些文档必须严格限定。

验证和生产数据

代码写指针，模型只能读指针，数据库里有才能取回，就像从 hashmap 取一个不存在的 key 什么都拿不到。源 ID 是哈希，他说这些都是大家在自己系统里就能做的简单事。最后形成的约定是：引用要么已验证，要么在检索时被纠正，要么直接拒绝输出。他说这也适用于事实，比如法律案件里被编造的判例，可以把判例确定性地存起来，只允许从列表里检索。他展示了生产数据：“拒绝”（模型无法解引用指针、因此不输出数字）的次数大幅下降；没有降到零是因为模型仍是概率性的，推理时仍可能编数字，所以后面还有一道后处理。

他说担心的是华尔街因为许多公司和自建团队造成的恐惧而永远不信这项技术。现在大多数金融 AI 工具在给 PPT 排版，还没人真的从头到尾做出一个 DCF，否则华尔街会一夜之间全部采用。他给评估供应商的问题清单：模型是否写指针？有没有验证输出的机制？每条引用是否核对来源？算术是否核对？能否阻止文件发给不该收到的客户？一个“凭空出现”的数字会被怎样处理？他的结论是模型再聪明，也还有数据库的老问题：查一行一列，值不存在就查不回来。他说我们已经走出 AI 的搜索阶段，要去建能用起来的基础设施、脚手架和 Harness。

18. Philipp Schmid（Google DeepMind）：写一个自主的华尔街同事，自定义 Skill、连接器和事件钩子

Gemini 4 和 Managed Agents

他说的新功能：100 万的统一上下文窗口，最多可以生成 100 万个输出 token；数学和推理任务提升明显，模型有超过 64K token 的思考空间。他知道有人觉得 Gemini 只会刷 Benchmark，所以强调 Google 内部已经大量使用：Chrome 团队用它加速 Chromium 的解耦工作，Gemma（Google 的开放模型）团队用它让 Gemma 更容易高效运行，ADK（Agent 开发套件）团队用它改进框架，内部代码库也有明显提升。他展示了同事让 Gemini 用纯 Python 从零写一个 3D 光线追踪器，并用 Gemini 的 TTS 和一个音乐模型配了解说。上手方式是 Interactions API，四行代码，在 AI Studio 拿 API key；价格他说是每百万 token 输入 2 美元、输出 10 美元。

Gemini API 里有一个产品叫 Managed Agents，用来搭远程 Agent：给 Gemini 一个沙箱，让它在里面跑工具。平常搭 Agent 是一个工具调用循环：发请求，模型生成 JSON 格式的函数调用，你在自己机器上执行，再把结果发回去。Managed Agents 提供沙箱，模型可以直接在里面执行代码、写文件，只要一次 API 调用：把模型 ID 换成 Agent ID（演示里是 antigravity-preview-09），给提示词，环境设为远程。底层用的是和 Google 编程 Agent Antigravity 相同的 Agent Harness。

按七样东西搭一个叫 Buck 的同事

  • 大脑和电脑：定义自己的 Agent，给 ID、基础 Agent（Antigravity Harness）、模型和系统指令，之后调用时用这个 Agent 的名字。
  • 工作手册：可以内联文件，挂一个公开或私有的 GitHub 仓库（里面放 Skill 或 AGENTS.md），或连 GCS 存储桶，预先布置好工作环境。Managed Agents 里一切都是文件，Skill、钩子、系统指令都是，Agent 可以给自己写新 Skill、存上一次会话的记忆。他把知识分三类：每次请求都要带的系统指令，要尽量短，因为每次都付费；Agent 自己决定何时读取的 Skill，只放一句简短描述，正文也别太长；再往下拆成专门的参考文件和脚本，需要时再看。示例 Skill 是“组合审计”，包括运行一个 Python 脚本，以及结果怎么处理、存到哪。
  • 工具：内置工具如 Google 搜索、代码执行，不用额外配置；Google Workspace 现在有 Gmail、表格等的 MCP 服务器；也可以接自己的 MCP 服务器或本地函数，本地函数照常由 Agent 生成调用、你返回结果，适合不想在沙箱里执行的操作。
  • 凭证：他说这是他最喜欢的功能，因为凭证很难做对。支持 Bearer token、面向消费级 MCP 服务器的 OAuth、给 CLI 用的环境变量三种。凭证不放进沙箱，而是在外部创建，只能写不能读，写进去后只能覆盖、无法取回。你规定每个凭证只能用于哪个域名或环境变量。沙箱外有一个网络代理监控所有进出流量：沙箱里的环境变量只是一个假值，Agent 发请求时代理识别出目标是你指定的域名，再把假值换成真凭证，Agent 并不知道。所以即便提示词注入让 Agent 打印 .env 里的所有值，也拿不到真密钥；恶意 MCP 服务器也偷不到你的 Gmail token，因为代理只为你指定的域名替换。
  • 规矩：钩子（hooks）用确定性方式拦截某些决策，比如需要监控或人工审批的命令。和其他 Agent Harness 类似，用正则表达式做匹配，每个工具调用都检查是否命中。钩子也是文件，但受保护，Agent 改不了，也绕不过去。
  • 时间表：目前支持 cron 定时触发，比如每天早上某个时间用同样的环境跑一次尽调或审计；正在做 webhook，让外部服务直接唤起 Agent，Agent 先做初审，再发到 Slack 或 Microsoft Teams，不用你管基础设施。

演示

他让 Gemini 在浏览器里做了一个仿 Google Sheets 的页面。点一下模拟 cron 触发，真实调用 Managed Agents：Agent 先读组合审计 Skill，再调用金融数据查看股价是否变动，最后自动更新表格；这个触发设定为每天 8:30 运行。如果 Agent 有 Slack 权限，还能发到交易频道说明变化。第二个演示是在 Slack 线程里问它有什么建议，它基于之前几轮对话给出了三个持仓的情况和变化，但按系统指令并不采取行动。

19. Joao Wenzel（Citadel Securities）：你的公司没有一个关于自己的模型，用 Slack、幻灯片和会议搭一个世界模型

公司里那个什么都知道的人

他让大家想想公司里那个好像什么都知道的人：经历过 17 次重组，知道所有八卦和政治，总能预测大的战略动作会带来什么。他说这个人就是公司的世界模型，问题是不能扩展，也没人把他说的写下来。Citadel Securities 从芯片往上都自己造技术，超过三分之二的员工写代码，Agent 已经在帮很多忙。于是领导层问：这些 Harness 写代码很好，能不能帮忙制定和打磨公司战略？他借用 Tim Urban 的图：战略归结为三个问题，我们现在在哪、接下来会发生什么、我们是怎么走到这里的。要回答它们，Agent 需要一份关于公司的丰富画像，他称之为工程化的“机构记忆层”：关系（重组后不再说话的两个团队）、故事（某个项目为什么被反复调整范围）、政治（谁在场、说了什么、没说什么）。

数据有两个入口。自上而下是幻灯片、战略文档、会议和状态报告，整齐干净，但人会把自己的看法加进去，于是出现他说的“西瓜项目”：外面绿，里面红。自下而上是会议记录、Slack、代码变更，甚至是员工使用编程 Harness 的会话 trace，噪声大但信号多。模型在两者交汇处综合证据。证据常常不全或错，他说机器人学里有现成的办法：状态估计器（state estimator）。你对某件事有一个信念，越久没看到支持它的证据，就越不信它，信念变模糊，直到新的幻灯片、线程或会议记录带来新证据，再收紧并更新。更新时要考虑三件事：距离上次收到信号多久了；信号从哪来、还可不可信；它和其他“传感器”是否一致。他说这和自动驾驶有很多相似之处。

从一张状态幻灯片读出信息都不容易

比如业务运营部门每月做的状态幻灯片。解析文件会遇到概念问题：解开 PowerPoint 得到 XML，什么颜色算“绿”，十六进制码是多少？截图丢给视觉模型也不行，有人把截图又粘回 PPT，模型就得眯眼分辨是 31 还是 81。他的办法是把 XML 和视觉模型的输出合在一起，才能得到真实情况。还要建立时间上的连续性，比如某个项目 3 月突然改名，要有可追溯的纵向记录。即便这些都做好，也只看到一半：幻灯片是 5 天前的，Slack 上有人说进度正常，另一个人回了一张仪表盘截图，情况又变了。

五步循环：更新、衰减、观察、打分、纠正

Citadel Securities 搭的系统在循环每一步都有 Agent，但由模型提出修改，由代码和人决定记录怎么更新。他也回答了“为什么不直接用 RAG”：他问某项目 3 月 16 日的状态，普通做法会抓几条 Slack 和幻灯片说“绿”，缺了大量上下文。

  • 更新（update）：每个月拿上月的记录和本月的幻灯片，构建纵向记录。他们做了三年，积累了大量历史记录。模型能根据参与的人和目标的连续性，推断出一个改了名的项目其实就是 Project Northstar。更重要的是让 Agent 区分“报告说什么”和“证据说什么”：幻灯片上是绿，但有人留言说还有依赖没解决，就应标黄并提示。不改以前月份的记录，只向前修正，这样以后能做可靠的评测。更新步骤写下的内容很简单：报告说什么，证据指向什么，为什么。
  • 衰减（age）：每个事实都有半衰期。上线日期 1 月说 Q2，后来说 Q3，现在说 10 月。他们三年的数据显示，一半的交付日期在两个月内会改，其中 90% 改到比原定更晚。所以每条结论都要关联一个日期，让 Agent 在被问状态时偏向近期信息。
  • 观察（observe）：一开始他想“YOLO”一下，让 Claude 之类的模型直接看全部材料，结果丢了很多细节。后来做了一个简单的 Agentic 工作流，一组专家 Agent 拆解材料、找特定内容、再由别的 Agent 审查，每个项目有洞察的更新数量翻了一倍多。
  • 打分（grade）：比较观察到的和预期的。世界模型应该能告诉你下个月哪个绿会变红。可以回测：取某个过去时点（比如 2 月）的快照，对照之后实际发生的标签，看 Agent 当时标记的是否真的出了问题。结果是被标记过的“绿”状态，变黄或变红的概率是其他的两倍。他说这不能精确预测哪里会出错，但能告诉你该看哪里。
  • 纠正（correct）：让人给系统反馈。他花了不少功夫研究怎么收集：在用户所在的地方找他们（正在用的应用、Slack、邮件），越近越简单越能扩展。问什么也重要：问一个事实只能修一个输出，问一条规则，Agent 理解后能修正它覆盖的所有输出，现在和以后都是。记录里因此区分“Agent 推断的”和“有人确认过的”。

自下而上的数据和“传感器失灵”

会议里人们会直接说出强信号；Slack 持续而嘈杂，但更接近真相；代码变更说明了实际发布了什么；Agent 会话展示“香肠是怎么做出来的”。Slack 的处理相对简单：看每个线程的附件、参与者和内容，提取 Agent 要记录或更新的结论，什么时候、谁负责、关于哪个项目、证据链接。PR 能看项目怎么演进，而在员工自愿开启的前提下，会话 trace 能看到需求怎样变化、测试失败、开发者的具体决定，最终汇成一个 PR。他提醒要注意不同传感器信号的有效性：开车时速度表突然不显示，不代表车速是零。他们遇到过某个频道“变安静了”被当成零信号的情况，后来改成记录上次尝试从这个传感器取数是什么时候、上次正常是什么时候、出现分歧时怎么办。最终的记录会说：不是绿，上线日期推迟了两次，证据指向黄，大家在讨论测试失败。

用在哪里，还没解决什么

用途：引导领导层讨论，不再发一份大家都略读的幻灯片，而是从幻灯片和证据不一致的地方开始谈；每周给管理者一份“什么卡住了、什么变安静了”的简报；最重要的是为所有 Agent 提供一个可依赖的上下文层。他们也想把这个模式扩展到客户业务，了解某个客户持有什么、关心什么、怎样预判需求。两个还没有好答案的问题：一个客户在四个系统里有四条记录、没有统一标识符时怎么优雅地映射；怎样最有效地从相关人员那里收集信号，模型有把握且风险低就自动应用，模型没把握就等更多证据，风险高时问谁、什么时候问就很关键。他的三条建议：把公司的模型当作状态估计器，别以为把一切建索引、编目录就够了；用“接下来实际发生了什么”给它打分，从一开始就设计评测；设计好让模型、Agent 和相关人员协同的机制。他鼓励还没开始的公司现在就开始收集数据，尤其是有成千上万份幻灯片的大公司。

20. Will Brown（Prime Intellect 应用研究负责人）：会自我改进的组织

直播位置 7:05:28–7:25:10 · 英文原题 Self-Improving Organizations

下一阶段是组织

Will 说想讲的是从现在的做法往后会出现什么。他提到 ChatGPT 早期 OpenAI 列过通往 AGI 的几个阶段（聊天机器人、推理者、Agent、创新者、组织），他觉得大家走得比预想快：18 个月前他在纽约的 AI Engineer 上讲时，推理模型刚出现，还没有真正的 Agent，现在已经很快走过了 Agent 和创新者。下一个问题是组织：一家大企业真正 AI 原生是什么样子，他指的是大企业规模，不是一个大量用 Agent、用 Claude Code 写一切的创业公司。Prime Intellect 做训练、部署和持续改进模型的基础设施，尤其是开源模型和开源工具，大致是大实验室内部会做的那些事。他们设想的未来是：开源模型随时可以在你自己的工作流、数据和 Harness 上训练和部署，和组织一起成长，把机构知识和优势复利积累下来，同时也用前沿实验室的模型。

写不下来的知识

组织越老，没写下来的隐性知识越多。代码库、邮件、流程是写下来的，但很多东西在人的脑子里，在邮件和会议记录的字里行间，在谁跟谁说话里。很多公司有纸面上的组织架构图，还有一张真实的“谁真正做决定、变化怎样被采纳、哪些指令会生效”的图。他认为这是 AI 在组织层面的大机会：很多人没有能力改变组织里坏掉的东西，因为没人有全局视角说“这里低效”“这个问题在很多团队重复出现，其实某个团队已经找到解法”。Agent 擅长翻大量非结构化文本、找出这类模式并呈现出来。他希望这能成为组织采用 AI 的常态方式，而且持续进行：Agent 能拿到需要的上下文，同时改进 Agent 自身和组织。

人类同事在工作中学习，Agent 现在的学习方式很原始，靠上下文学习（in-context learning）：读别人写的 Skill 文件或翻代码库，拿不到机构层面的潜在知识，于是不断重新学、重新发现，花大量输入 token。他说现在很多人意识到缓存后的输入是很多 Agent 成本的瓶颈，即使缓存率高、缓存便宜，每次重做工作流还是要重新处理大量输入。所以要把更多东西“烤进”模型权重里，尤其是难以写成规则的东西。他用两条光谱：从规则到模式，从代码到数据。Skill 和规则像代码；偏好、摩擦点、经验法则、趋势是数据，组织靠大量这类数据运转，员工会隐性学到，模型从来没机会学。他认为这阻碍了 Agent 成为真正的同事。什么放上下文、什么放权重，要“挣”来，不是一开始就放进权重。但他说每一代模型变好靠的是训练得更多，训练有用。

现在的训练链条像传话游戏

他描述模型怎样学会用一套 Salesforce 工具：一个以前在用这些工具的公司工作过的人，在专家网络平台上兼职挣钱，把知识分享给专家网络公司的人；这个人把数据交给做强化学习环境（RL environment，让模型练习任务并获得奖励的模拟场景）的人；环境卖给一个不懂这个领域的实验室研究员，再精炼进训练管线，进到下一次前沿模型训练。他说链条太长，而且基本不公开，真正懂的人不监督训练，也没法像对自己的编程 Agent 那样直接影响训练。他们想缩短这条链：你对编程 Agent 每次说的“别再犯这个错”“在这种情况下我更想要那样”，可以变成持久的学习，不再只是 AGENTS.md 里不断累积又不断重构的一行。这种反馈数据的形状本来就很接近训练管线需要的数据。

从评测开始：把模型当代码库管理

他认为对多数组织最实际的持续学习（continual learning），是把模型当成一个代码库：有生命周期，可以加测试用例、加功能、加资产。用 Agent 的过程本身就在积累 trace，里面有提示词和你对模型行为的反馈，这些就是做评测需要的素材。以前做评测很痛苦，现在 Agent 已经能帮忙整理评测，并且会越来越懂怎样做出稳健、适合学习的评测。

两个容易落地的例子：一是路由，大家每月在 Claude 上花很多钱，想知道什么时候用便宜模型，可以让大模型和小模型做同一个任务，判断小模型是否一样好，好就多路由给小模型，这就是训练数据；二是最近几周很火的“决策模型”（字幕里提到的人名不清），学习模仿人在某种情境下的判断，人的审批就像我们在 Claude Code 里批准工具调用一样，是一个可以打标签的动作。他说大多数人已经开了自动接受工具调用，但每个组织在工具安全之外都有自己的规则和偏好，可以积累成决策模型。他认为这是很多人明天就能接上、马上见效的持续学习形式。

更大的项目是 Prime Intellect 的主要工作：和组织合作，把高流量生产场景的 trace 变成真实和合成数据混合的环境，捕捉他们想用长时间运行 Agent 处理的真实任务的复杂性。他说在足够的编排、工具和人在环下，Agent 很擅长把 trace 变成足够丰富的训练环境，而且每一代开放和闭源模型都让这件事更自动化，自我改进循环会从“用 Agent 整理数据、给人提供表达意图的界面”里自然产生。

动态 UI 卡片，以及一个夜间训练的原型

他自己在试一种他认为会流行的交互：模型现场写代码生成小部件卡片，一种实用的动态 UI，用来征求人的决定，像工具调用审批，但更个性化。他说大家在一个 bot 和二十个 bot 之间来回摆动，真正想要的是做决定：把想法交给 Agent，让它去跑，需要决定时再回来找你，并且 Agent 能判断什么时候该找你。现场生成的界面比在长消息里找问题在哪更顺手，同时也是完美的训练数据：人的输入直接成为标签，有明确目标，可以绕开很多奖励作弊（reward hacking）的问题。这不必用于整个技术栈里的每个模型，可以从编排层模型或决策模型开始。

他举了一个当天刚加的例子：一家朋友公司（字幕名称不清）用他们的工具花了 30 万美元训了一个模型，在表格和幻灯片等知识工作上处于帕累托前沿（成本和效果的最优权衡）。他说这相当于雇一个员工的投入，可以选择雇一个软件工程师，也可以训一个模型，而且需求每个月都在涨，因为开放模型已经好到可以通过你的领域、Harness 和环境训练得更好、更个性化。最后他展示了内部原型：持续收集 trace，每晚看系统提出的实验和被标记的问题，启动一次夜间训练，白天推理算力服务 Agent，晚上员工用得少就拿来训练。他说这是组织很快就能真正在权重里做持续学习的方式。路径依次是：发现工作流、写 Skill、做评测、做路由，然后追求组织内部数据带来的规模经济和复利，让组织持续自我改进。

21. Jemima Abu（CAIS 产品工程师）：AI 里的无障碍成本 [线上]

直播位置 7:26:05–7:36:20 · 英文原题 The Cost of Accessibility in AI

Jemima 是 CAIS（一家另类投资平台）的产品工程师，也是 Google Developer Expert、Microsoft MVP，持有 CPACC 无障碍认证。她给这场起的副标题是“别再把 token 浪费在别人用不了的产品上”。无障碍（accessibility）是指产品能被任何人使用，不论是否有残障。她引用 WebAIM 的研究：全球前 100 万网站中 96% 的首页有某种无障碍问题。她常听到的理由是“太费时间”，但她认为 AI 写大部分代码之后，做无障碍反而更容易，做不无障碍的网站才更贵。

她在公司代码库上做了个小实验：同一个简单提示词“按 Figma 实现这个设计”跑两次，一次不带无障碍 Skill，一次带她自己写的 Skill。带 Skill 的那次成本降低 58%，用时只有约三分之一。她马上说明这是一次性实验，不在受控环境里，不能作为实证结论，但可以看原因。第一，人的偏见会变成 AI 的偏见：开发者习惯“在我电脑上能用就行”，不管屏幕阅读器和弱光环境，代码库里从没提过无障碍，Agent 就会学到并继续写出不无障碍的代码。第二，没有指导时 AI 默认写啰嗦的代码，让它做一个手风琴组件或模态框，它不会先看有没有现成的语义化 HTML 元素，而是从头造一个，复刻原生功能要更多测试和实现。她用蓝莓松饼打比方：把蓝莓塞在做好的松饼上不算蓝莓松饼，网站做完再到处塞 ARIA 标签也不算无障碍，而且从业务想法、设计到 QA 每一步都要考虑。最后再做还会浪费大量回归测试和重构时间。业务上，说“我们的用户不用辅助技术”是自我实现的预言，用辅助技术的人根本用不了你的网站；法律上，美国《残疾人法案》（ADA）要求面向公众的产品可被残障人士使用，否则可能被罚款和起诉。

她的做法：先确定你所在平台的无障碍要求；审计现有代码库，先修掉已有问题，免得 Agent 当成最佳实践照抄，可以用自动化工具或让 Agent 来做；最好有可复用的组件库或设计系统，一处修好处处生效；最后强制使用无障碍 Skill。她推荐 Chrome 的 modern web guidance Skill，让 Agent 用最新的 HTML 和 CSS 特性而不是自定义 JavaScript。轻量版的最低要求：尽量用语义化 HTML，只有语义化 HTML 表达不了时才用 ARIA；凡是鼠标能操作的交互元素都要能用键盘操作；元素要正确标注，能被屏幕阅读器读出；运行前让 Agent 按这些要求自查。她说这不足以做出完全无障碍的网站，仍然要自己手动测试，但有总比没有好。

Rowspace 是一个 Agentic 平台，用 Agent 做数据工程的工作，从各个系统核对（reconcile）凌乱、分散的数据，让组合经理和交易员更快更准地做决定。Jack 是 Apollo 的 principal（合伙人级职位），也是 Redding Ridge Capital 的首席运营官。Redding Ridge 是 Apollo 旗下的结构化信贷和 CLO（贷款抵押债券，把一大批企业贷款打包后分层发行的证券）管理人，是独立运营的公司，管理约 500 亿美元资产，以 CLO 为主。他 2020 年加入 Apollo，待过金融机构组、资产支持组。

Jack 说他们管很多基金实体和投资，每天有成千上万个数据点进来，管理约上千个名字的贷款池。CLO 管理很活跃，在广泛银团贷款市场交易，所以要随时掌握信息。这些私募信息不像上市股票或公开固定收益那样公开，而是散落在各种文件里。所以他们找 Rowspace 合作，让对方来和团队坐在一起，理解他们用的计算和信息，什么才是“黄金数据源”，再不断改进 AI 引擎去重复这些逻辑。

两个例子

  • 组合构建：CLO 规则很多，有各种测试，资金流向有特定的瀑布（waterfall）结构，这些都写在很长的契约文件和多份法律协议里。组合经理以前要读文件、建 Excel 模型、用 200 到 400 个单一信用名字搭模拟组合，手工要两三天。现在能拿到实时的最新信息，几分钟搭出一个完成度 80% 到 90% 的组合，再由组合经理用判断完善最后 10%。数据来自文档库、交易和合规系统、实时定价等。
  • 仓储期买卖活动：他们靠银行融资，可以随时在固定收益市场买贷款。以前每周要做交易核对，手工进银行账户看对账单、确认结算，由专人核完再发邮件给管理层。现在同样的报告放进 Rowspace 做可视化，一分钟内生成、可重复，全部自动化，团队每天只做 QA 检查。以前这每周要两三个人花很多小时。

为什么不直接用 Claude 或 ChatGPT，信任从哪来

Jack 说 Claude、ChatGPT 这些 LLM 很有用，但基于的是通用信息，不是你自己的数据，适合做研究、快速了解某个产品或投资。他们在 Redding Ridge 的 AI 建设思路是拥有自己的数据，在上面放一层确认为真的平台和技术。他说 Rowspace 和他们合作过的其他技术公司不同，是“靴子踩在地上”：Michael 几乎每天和他们团队坐在一起，理解信息流，因为一个数据可能有 20 个来源，只有一个是对的。Rowspace 和组合管理、财务团队一起搞清楚计算方式、哪个数据正确、哪个要覆盖其他来源，再汇总起来。来源包括交易订单管理系统、业绩系统、Bloomberg 和各种定价指数。他们公司内部其他很多系统仍然是分散的，要手工从这边搬到那边。

Apollo 的文化和金融业的进度

Michael 说早在去年初、Claude Code 还没出现、Cursor 还在 Tab 补全的时代，Apollo 就是他们接触过的最“AI 化”的公司之一，说要用 AI 原生的方式重建公司，要平台而不是点状方案。Jack 说 Apollo 一直以替代资产管理和金融业的领先者自居，管理层强调持续提升团队能力、保持灵活、跟着市场走，认为 AI 已经来了，要适应和采用，组织扁平开放，愿意接受变化。

Michael 问金融在 AI 的进程里处在哪里，软件工程已经完全变了，法律和客服可能也快了。Jack 说大型金融机构的中后台支持很多，成长空间很大，但他们的业务极其复杂；在资产管理、投行、机构业务里他认为还很早。建模或快速了解一家公司、汇总研究这类事已经有价值，但他认为附加值较低，以后某些职能的初级支持可能会减少。现阶段他们是把技术用于例行任务，释放产能去做别的项目，因为要做的事情无穷无尽。

AI 会只是像 Excel 那样人人都有的生产力工具，还是能带来持久的竞争优势？Jack 认为用得好会更有竞争力。资产管理和投资在活跃交易市场里，最终取决于流程和你手边的信息：执行流程是否扎实，是否清楚可用流动性、价格和价值。公开市场已经如此，私募市场还在演进，Apollo 在推动这件事；有了准确信息、团队知道它是对的，就会变成竞争优势，因为最不想发生的是基于错误信息做决定，再一路传到企业和投资人那里。

Michael 说他连自己团队下周用 Codex 还是 Claude Code 都预测不了，所以不问五年后，只问接下来几个月 Jack 希望看到什么。Jack 说一是对发给投资人的信息完全有信心，不用花几小时手工核对，他们有 400 多家全球投资人；二是更技术化的思维，团队以前不缺这种意识，但技术常是事后才想到的，他希望大家在解决问题时首先想到：这个流程为什么存在，能不能改进或换一种技术来做。最后 Michael 问对想把 AI 用到这类领域的工程师有什么建议，Jack 说这些机构极其复杂，有些东西看起来奇怪、不合常理，但多半有原因；花时间和你要服务的前台团队坐在一起是值得的，Rowspace 产品进度超出预期，就是因为 Michael 的团队几乎每天都和他们坐在一起理解工作流。

25. Mitchell Troyanovsky（Basis 联合创始人）：给做长周期工作的 Agent 做过程监督

直播位置 8:09:22–8:28:30 · 英文原题 Process Supervision for Agents That Do Long-Horizon Work

为什么个人生产力涨了，企业没涨

Basis 在纽约，研究怎样让 Agent 可靠地完成生产规模的工作，被全美的会计师事务所端到端信任和使用。Mitch 问：在座各位用 Codex、Claude Code 之类，生产力可能涨了很多，他自己可能涨了 100 倍，但一般企业的生产力没有涨 10 倍、100 倍，为什么？Basis 内部有句话：人本来就习惯和非确定性系统一起工作，只不过那些系统通常是同事，不是电脑。组织要扩大生产力，就要相信每一层的人都会稳定地产出好结果。会计师事务所的负责人完全不知道最底层员工每天具体在做什么，却信任工作会被完成，靠的是流程，人本身并不是确定性系统：如果制定流程的人认为流程能推广到好结果，那即使执行的人不是确定性的，按流程走一般也会得到好结果。哪怕最小的一步也有流程，比如对账要先拿银行数据，流程可能只是“用批准的软件提取”，公司不会让员工随便上网找个 PDF 提取工具。

他认为“编程式 Agent 产品”（你对 Agent 说一句话让它去做）有两个问题。一是能力鸿沟：Agent 把复杂性外包给用户，用户得管理 Skill 和记忆、知道什么时候用、对它有心智模型，大多数知识工作者不会。二是流程鸿沟：如果“这是你的 Agent，想怎么用都行”，工作方式就取决于每个用户怎么定制 Agent，这和组织的扩展方式相反，流程应该由高层往下定，而不是每个员工自己决定。所以他们认为关键是：让用户用起来简单，甚至感觉不到它是 Agent，就像和同事合作；并且让 Agent 可靠，不是今天灵光一现明天忘东忘西。他说没人要求完美，人也不完美，要的是可靠、一致、可信，包括做不到的事要稳定地做不到，然后像人一样慢慢变好。

要有主见（opinionated）

要简单又可靠，Agent 必须有主见。例子：读 PDF 的最佳方式是什么？丢给视觉语言模型（VLM）、写 Python 用开源 OCR 库、用专门的 OCR 模型供应商、OCR 后让 VLM 检查、让 5 个或 100 个 VLM 检查取最好的，可能性无限。如果只说“去提取 PDF”，结果可能不错但不可靠，原因是过程没有主见，过程本身未必差。主见可以来自专业直觉：做税务时，Agent 先读原始法规再回答用户更可能准确，不需要评测来证明；做 PPT 时，回给用户前先截图看一眼，格式错误更少。主见也不只关乎准确：截图会增加延迟，如果格式出错只有百分之一，你可以接受，就不必截图。这场不讲怎么形成主见，讲的是为什么主见重要、规模化后怎么利用它。

结果评测不够：看行为

结果型评测是传统意义的评测，有标准答案或评分细则。你可以有 100 个用例，但生产中会遇到几十万种情形，而且轨迹越长、决策越多，情形呈指数增长，你没法给每条轨迹一个标准答案。但你可以看轨迹里你主张的行为是否发生，如果发生了，就更可能推广到生产。例子：银行对账有差异时，他们希望 Agent 解释差异，而不是记一笔调平分录（plug）凑平。这是主观的，你可以选另一种，但不能让客户这次是一种、下次是另一种。

行为不是在系统提示词里写两句就行，它由系统提示词、渐进式披露（progressive disclosure，按需逐步给 Agent 更多信息）、工具描述、模型训练等共同决定。他的建议是把 Agent 工作时看到的上下文当作“运行时训练数据”，他觉得“提示词”这个词把它看轻了，每个 token 都要在意。Basis 发展出“行为规格”（behavior spec）：在写或改上下文之前，先写清楚想要什么，有点像 Agent 时代的产品规格。不写每个细节，只写最重要的主见，否则会重复状态。它既能对齐团队，也能当评分细则：在任何没有标准答案的轨迹里，Agent 是否遇到了这个行为相关的情境，如果遇到了，是否表现出该行为。这样获得信号的规模远大于增加结果型评测的标准答案。

分叉和模拟

第二个工具是分叉（forking）。Claude Code 或 Codex 的网页版里每条消息下面有个分叉图标，可以复制一个 Agent。在本地电脑上这很好做，在云端要完美重建数据库环境、提示词等各种环境就难。流程是：某条轨迹（来自评测集、测试或生产）没通过行为评测，你回到 Agent 做出违背行为的决定之前或之后，分叉出来，问它为什么那么做，或者改上下文看行为是否改善。结果型评测只告诉你失败了，一条 5 小时、可能有上千次推理调用的轨迹，你很难知道为什么。

他最喜欢的第三个工具是模拟（simulations）：让编程 Agent 创建一个子 Agent，扮演你的生产 Agent，告诉它不许作弊，把系统提示词和 Skill 都完整呈现给它，然后问它在某个情境下会怎么做，看能否重现评测或生产中看到的情况；能重现，就改上下文，看子 Agent 的行为会不会跟着变。他承认这远不如分叉，但便宜、快，不用建任何东西就能迭代想法，在内部做出分叉功能之前他这样做了一年半以上。通过这些方法监督过程，就能获得额外信号判断 Agent 是否在泛化，信号多了就能闭环，而主见是能闭环的前提。

信任像对同事

回到公司：Agent 一开始做窄的事，大家觉得好用、可靠，随着它变好就越来越信任。他用审 PR 来比：看两个维度，这个 PR 的影响范围有多大，你觉得提交的人有多能干。公司里最不靠谱的人改核心服务，你一定细看；最能干的人改内部文档，你可能不怎么看。人和 Agent 合作也是这样。有人会问：让 Agent 自由发挥，它不会找到更好的办法、走出“第 37 手”吗？（指 AlphaGo 对李世石第二局那步出人意料的妙手。）他说可能会，但那不是扩大 GDP 和产出的方式，没人想要 Agent 给自己的报税单走出第 37 手，大家要的是可靠、可规模化、可信任、员工知道怎么配合。他的结论：Agent 要普及就要简单，团队要信任就要可靠，做到简单可靠靠的是对 Agent 行为有主见，主见又让你能建立额外信号、闭环，在生产中实现自我改进的 Agent。

26. Cristóbal Valenzuela（Runway 联合创始人、联席 CEO）：一切都将被模拟

直播位置 8:29:11–8:45:40 · 英文原题 Everything will be Simulated

从一颗橙子说起

Cristóbal 做 Runway 快十年了，公司大约十年前在纽约起步。他先放了 Runway 2019 年做的第一部 AI 短片《The Orange》：一颗橙子从树上掉下来，走过世界不同的地方。当时的模型生成 128×128 像素的画面，再硬放大。他说现在看像 1900 年代的老电影。那时他们只能说服自己：继续扩大规模，它会自然变好。接着他放了当下最先进的视频，人物和地点都是生成的。他说看着这些，他仍然相信过几年它们会像那颗橙子一样显得原始。Runway 处在艺术和科学的交叉点，扎根在创意社区，也有顶尖的扩散模型和大视频模型研究者。

下一帧预测学到了物理

他说公司的核心想法电影在 120 到 130 年前就发现了：视频是一种视错觉，帧拼得够快就有了运动。Runway 做的是把下一帧预测（根据前面的帧预测下一帧）做得足够快、规模足够大，希望得到比好看的创意视频更多的东西。他们相信 Scaling Law 也适用于视频，现在正在大幅增加训练算力。他说他们会量化人能否分辨真实视频和生成视频，这个“图灵测试”他们认为已经通过，人分不出来。更有意思的是，预测下一帧时模型学到了物理、物体恒存、重力、遮挡、运动。比如一个复杂场景（他举了骆驼站在球上、容器里的水），要生成连贯视频，模型必须理解每个对象是什么、彼此怎样关联。所以他们评估视频模型的很多 Benchmark 衡量的是物理、几何和物体在现实里的行为。

在类似游戏的 3D 环境里做下一帧预测，就接近一个物理引擎或模拟系统，但没有写任何物理规则，模型靠规模学会了。他放了一段像 GTA 的游戏画面，说那并非 GTA，是在一个不存在的软件里“模拟一次模拟”。

实时和可交互

之前的视频都不是实时的，要几秒或几分钟生成。他说接下来三四年的重点，除了继续扩大规模带来更多涌现能力，就是让模型可交互：在下一帧预测的任何时刻都可以插入动作，从而模拟世界里任何可能的分叉。可以点画面任何部分，改变那个世界的后果。Runway 正在建一个机器人实验室，他说纽约办公室一半像好莱坞片场，一半是走来走去的机器人，他们想让这些模型成为自主和具身系统在世界里行走和推理的“大脑”。

他还展示了把屏幕上任何像素都当作视频模型的用法。一张汽车图片，实时跑视频模型，点击就能开车灯、把车转过来、打开引擎盖看里面，背后没有 Unity、Unreal、Blender，没有任何 3D 表示，只是一个学会理解界面里动作和点击的视频模型，他们叫它“世界界面模型”（world interface model）。另一个例子是在一张房间图片里移动物体，物体会像在真实房间里那样移动，这个房间也许从来没被建模过。

Continuum：视频模型做的操作系统

他说外推可能是当下 AI 和创业里最重要的技能之一：如果继续扩大模型、加数据、让它成为能预测屏幕上任何东西的通用模拟系统，会怎样？他们在做一个叫 Continuum 的研究项目，还很早期：一个操作系统，你打开电脑，屏幕上流式显示的内容可能来自视频模型。

  • 他在研究旧金山的雾，打开一个网页，选中任意一段内容，把它变成“传送门”（portal），这是一个根据所读内容生成的、完全可交互的实时视频，也可以是 3D 可视化。右侧保存你看过的所有传送门，像一块“想象”的硬盘。他回到之前关于电池的传送门，可以点击、移动、提问，视频内容随交互变化。
  • 学光合作用时，调整窗口大小，体验也会跟着变；可以点进细胞的不同部分。他说自己不知道该怎么称呼这种东西，不像可视化，不像视频，也不像游戏，需要大家一起想个名字。
  • 视觉思考（visual thinking）：他们把 Continuum 接到一个编程 Agent 上，比如让 Agent 给自行车做一个 3D 模型，Agent 不只用代码思考，而是起一个 Continuum 实例，以视觉方式思考问题。人也能看到并据此引导 Agent，比只用文字引导更好。他说这是他们觉得探索最少的方向。
  • 搜索火星时，Continuum 理解意图，实时生成专门的界面：一个火星前哨站，他说应当和目前在火星上的机器人或 2030 年规划中的数据一致，可以在里面四处走动。

他希望几年或几个月后回头看，Continuum 也会像那颗橙子一样显得原始。他说这些还在早期，但已经能用、能扩展，未来 8 到 12 个月会把这次展示的大部分开放给所有人使用。
