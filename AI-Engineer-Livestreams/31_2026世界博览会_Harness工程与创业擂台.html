02. Barr Yaron（Amplify Partners 投资合伙人）：2026 年 AI 工程现状调查

直播位置 0:16:08–0:35:29

Barr 每年做一次 AI 工程现状调查，今年第一次和 Notion、Vercel 合作。她说做这个调查的麻烦在于做幻灯片的时候领域就在变：就在过去一周，前沿模型发布被当成国家安全事件对待，还有报道说 Meta 在考虑出售 AI 算力。她的承诺照旧：“少讲 Barr，多讲 bar chart（柱状图）。”今年有 1,048 位受访者。

受访者是谁

她说 AI 工程更像一门学科，不是一个职位名称：受访者包括创始人、CTO、工程师、产品人员，覆盖各种公司规模。连续第三年，样本偏向资深工程师但 AI 经验较新：有 10 年以上软件经验的人里，一半以上的 AI 经验不超过 3 年。刚入行的新工程师，AI 经验的中位数几乎和 10 年老兵一样，他们从没见过没有 AI 的软件开发。

模态和模型

  • 文本占绝对多数。她关注“打算采用”的比例：在目前没用某个模态的人里，有多少人计划使用。音频最高，56% 没用音频的人打算采用，去年这个数字是 37%，也是最高。
  • 变化最大的是图像生成：用生成式 AI 做图并且感觉很好的比例从 18% 翻倍到 36%。她把这归因于 Nano Banana、Nano Banana 2、ChatGPT Images 2.0 等产品变好了。
  • 生产环境里 94% 用闭源模型，45% 用开放权重模型。用开放权重模型的人里，90% 以上同时也用闭源模型，所以开放权重是补充，没有取代闭源。
  • 选模型的前三考虑里，“开源还是闭源”只被 5% 的人选中。排第一的是质量，其次是 Agent 能力（比如工具调用 Tool Call），成本并列。只有五分之一的人把可靠性放进前三，她的解读是可靠性已经变成门槛条件，现在的模型大多够用了。
  • 87% 的团队用不止一个模型，最常见的分配方式是按任务类型路由。同时一半以上的人说公司开始在更少的 AI 工具上统一。她的结论是：平台和工具在统一，模型没有。

成本变成一等约束

40% 的人说成本经常影响他们使用 AI 的野心，另有 36% 说有时会，加起来约四分之三。她开玩笑说剩下那四分之一可能有公司信用卡。生产监控里，成本和 token 用量排第二，仅次于质量本身，被当成 SLA 来盯。12 个月前还不是这样。

Agent 有了写权限

今年 95% 的受访者说在用 Agent，大约是去年的两倍。用 Agent 的团队里，Agent 能写入数据的比例从 52% 升到 89%。两者叠加，在全部受访者中使用可写 Agent 的比例是去年的三倍多。她说 Agent 已经从阅读、总结、起草，变成在系统里执行动作。控制手段主要是人工审批（Human-in-the-loop）和权限闸门，她形容这和管理实习生用的是同一套工具。再往下是任务分解、检索、记忆、沙箱，答案很分散，Agent 的控制层还没有定型。她特别关注记忆和持久上下文。Agent 出问题时，三分之二的人最烦的是幻觉或任务中途丢失上下文。

技术栈：评测仍是第一难题

  • “技术栈里最大的挑战是什么”，每年第一名都是评测（Eval，即系统化地检验模型输出好不好），但今年领先幅度很小。96% 的人对技术栈有某个不满，只是意见不一致。她说想做基础设施的人可以把这种分散当成地图。
  • 评测方法里排第一的依旧是“凭感觉看”（vibe review）。
  • 在八层技术栈的自建还是采购问题上，推理（Inference，即运行模型生成输出）和模型服务是采购最多的一层。提示词管理正相反，61% 自建。提示词、RAG（检索增强生成，即先从资料库检索相关内容再交给模型回答）、评测这类靠近产品逻辑的部分倾向于自己做。微调（Fine-tuning）是最明显的“还没开始”，大多数人根本没有。

对团队的影响

97% 的人认为 AI 对组织是净正面。她说排第一的好处是失败变便宜了，可以做更多实验、原型和尝试，速度倒在其次。代价也有：九成以上的人感到某种负面影响，最常见的是深度技术能力退化、对代码库的理解变弱。81% 的人说 AI 模糊了工程师和产品、设计、市场之间的界限。超过三分之一的团队有非开发人员在发布功能，多数是小型内部功能，但 17% 说非开发人员经常发布面向客户的功能。

对未来的押注

  • 76% 说 AI 提高了工作满意度；59% 担心今天 AI 写的代码会变成长期负债；只有三分之一认为软件工程已是“已解决问题”。
  • 67% 预计五年内会有头部实验室“宣布”实现 AGI。她强调问的是新闻稿，不是实际达成。
  • 只有 9% 押注五年后 Transformer 仍是最先进架构，多数人不确定。
  • 五年后太空里的 AI 算力会不会多于地面：36% 说会，38% 说不会，是整个调查里分歧最大的问题。

03. John Ousterhout（Stanford 荣休教授）：延迟很重要，以及 Homa 传输协议

直播位置 0:35:29–0:53:57

Ousterhout 开场说，这是他第一次在有烟雾机的礼堂里演讲。他要讲 AI 应用的网络一侧，目标有三个：说服大家工作负载在变，小消息的延迟越来越关键；说明 TCP 和 RDMA 这类传统协议不适合这种环境；介绍 Stanford 从零设计的数据中心传输协议 Homa。

工作负载在变

过去 AI 的网络流量以巨大的传输为主，比如几 GB 的梯度，关心的是吞吐量（每秒能传多少数据）。这种场景下连接建立慢一点无所谓，TCP 和 RDMA 表现不错。他说的 RDMA 主要指 RoCE，也就是在以太网上跑的 RDMA。现在推理和 Agent 类工作负载变得更细碎，出现越来越多小消息，用于元数据和协调，比如查询分布式 KV Cache（模型推理时缓存的中间结果）里某个条目是否存在，或者在一轮计算结束时做屏障同步。训练仍以大传输为主。

小消息看的是延迟，而且看的是尾延迟（Tail Latency），通常用 P99，即 99% 的请求都能在这个时间内完成。他举例：任务分到几个节点上用 GPU 计算，算完要交换一小份数据才能进入下一轮，交换期间 GPU 闲着，只要有一次交换慢了，整个流程就停下。如果计算阶段是 5 秒、交换几毫秒，问题不大；可现在为了稳定地输出 token，计算阶段缩短到毫秒级，同步也要几毫秒的话，GPU 就浪费了很大比例。他现场问谁觉得小消息延迟影响了吞吐，举手的人比他预想的多。

TCP 和 RDMA 的问题

  • 尾延迟的主要原因是 incast 拥塞：几个节点同时向一个目标发大消息，三个发送方的速度是接收方链路的三倍，数据包在目标前最后一跳的机架交换机出口排队。此时有人发一条短消息，就卡在长消息后面；严重时交换机缓冲区满了开始丢包，再引发超时重传。
  • 传统协议的拥塞控制由发送方负责。早年靠丢包发现拥塞，代价很高；现在靠交换机在队列开始变长时给数据包打上 ECN（显式拥塞通知）标记，接收方再把标记回传给发送方。可发送方只拿到一比特信息“某处有拥塞”，多个发送方同时调整，需要好几个往返才能找到合适速率，而网络状况早就变了，所以系统一直在“发多了”和“发少了”之间震荡。他说这个问题在研究界已经 20 多年，论文很多，改进有限，根源在于让发送方做拥塞控制。而且只有排了队才能发现拥塞，此时延迟已经产生了。
  • 另一个问题是 TCP 和 RDMA 的数据模型是字节流，协议不知道消息边界，不知道还有多少数据要来，没法优先处理短消息，还会出现队头阻塞（head-of-line blocking）：两条大消息后面跟一条小消息，小消息只能等。

Homa 的三个设计

Homa 起源于他的博士生 Behnam Montazeri 的博士论文，结果很好，他决定亲自把它从实验室推向生产。他说自己和大多数教授不同，喜欢写代码，于是写了一个 Linux 内核模块，正在推动合入主线内核，代码在 GitHub 上可下载。

  1. 以消息为单位，不用字节流。基本单位是远程过程调用（RPC）：客户端发请求消息，服务器回响应消息。协议从底层就知道消息长度，接收方收到第一个包就知道还有多少数据；它用 SRPT（最短剩余处理时间优先）调度短消息；每条消息独立，短消息可以越过长消息。
  2. 由接收方控制拥塞。拥塞主要发生在通往接收方的最后一段下行链路，接收方信息最全。发送方先发前几个“非调度包”，后面的“调度包”要等接收方回送授权（grant）才发。接收方如果有 10 条消息要进来，不会同时授权给 10 条，并且优先授权给短消息。
  3. 利用交换机的优先级队列。现代数据中心交换机每个出口通常有 8 个队列，Homa 动态地让短消息走高优先级队列，在 incast 场景下短消息可以直接绕过排队的长消息。

测试结果

他展示了一个混合不同大小消息的基准测试，消息长度从约 50 字节到 1MB。短消息的 P99：TCP 超过 1 毫秒，Homa 不到 100 微秒，快约 13 倍。直觉上偏向短消息会让长消息变慢，但实际上最长的消息 Homa 也比 TCP 好将近两倍，他说原因和 Homa 采用“运行到完成”的调度、TCP 采用公平调度有关，时间不够没有展开。

他请大家在分析瓶颈时问自己：小消息的高延迟是否影响了吞吐？如果是，可以试 Homa，尾延迟可能降一个数量级以上。他说自己半退休离开 Stanford，就是为了把全部时间花在 Homa 上，愿意亲自帮助试用者入门、答疑和修 bug。

04. Maxime Rivest（DSPy 核心贡献者）、Isaac Miller（DSPy 首席维护者）：把任务和模型、Harness 分开

直播位置 0:53:57–1:12:21

AI 程序应该像函数（Maxime）

Maxime 说，编程时一个任务要反复做，就把它写成函数。函数有名字、输入、输出和内部实现，可以复用、组合、测试、优化，还能打包给别人当黑盒用，别人只需要知道接口约定。DSPy 是一个 Python 开源库，要把这些性质带到 AI 程序里。他的理由是：这三年领域里新词、新模型、新技巧层出不穷，但它们都只是实现手段，如果给反复执行的 AI 任务定义好输入输出接口，内部怎么换都不影响外部。

他举了自己的例子：第一个 DSPy 程序是从农场的发票里提取税额用来报税；另一个是键盘快捷键，读剪贴板、修正语法，还有一个版本改写得更清楚。新模型出来时只要换内部实现。任务也可以很大：给整个收件箱和一封新邮件，起草回复，这在 DSPy 里可以用 RLM（递归语言模型）做；或者给一份规格说明和一个代码仓库，产出一个 PR。内部可以从一个简单提示词开始，改成 Agent，加工具，再加循环工程，外面的集成都不用动。

完整描述一个任务需要三样东西

他说 DSPy 的作者在 ChatGPT 出现之前就得出结论：要能自动优化，任务必须用三种语言完整描述。

  1. 应该发生什么：用自然语言写的指令，DSPy 的 Signature（签名，声明输入输出字段及说明）就是其中一部分。他展示的脚本里，模型配置在最上面，和签名完全独立；签名写着“提取所有税额，字迹不清就输出 0”，输入是字符串，输出是字符串和浮点数。他比喻说朋友来玩桌游，给他规则他就能上手，如果只让他看例子自己学，就要熬一个通宵。
  2. 必须发生什么：硬约束，最好用代码表达。示例里 self.extract 用 Predict，self.recheck 用 ChainOfThought（让模型先推理再回答）；在 forward 里，如果第一次没提取到税额就用更多推理重跑；如果数值小于 0 就抛异常交给人看。他说即使有了 AGI，这些规则也不变。
  3. 好的结果长什么样：评测和例子。他小时候问父亲怎么认出枫树，父亲说不出规则，也写不出代码，他是靠看大量例子学会的。规格里那些隐性的长尾要求，只能用例子表达，这也是实习生需要导师的原因。

三者齐备后，目标就被完整描述了，可以用 GEPA 这类优化器在指标和程序上做优化。早期模型不够好，DSPy 用代码去找 Few-shot 示例（放进提示词里的少量样例）；后来模型变好，可以自动优化指令；他们希望将来实现细节都能交给自动化。

企业里的收益和新技术（Isaac）

Isaac 说企业用 DSPy 有两个收益。第一是实现变便宜：实现可以替换，就能搜索更便宜的方案，处理以前因成本太高做不了的数据量。他举的 Shopify 案例便宜了 550 倍，做法是从昂贵模型换到便宜模型，评测保持不变，业务逻辑继续迭代。他提到现场幻灯片上有三个案例研究可以会后去看。

第二是生态里不断加入新技术。他强调这些技术都不保证解决你的问题，那是你的工作，DSPy 能做的是解决子问题。例子包括 MIT 博士生 Alex Zhang 提出的递归语言模型，用于处理某些长上下文任务，在 DSPy 里只要一行，签名不变；Berkeley 的提示词优化器 GEPA；BetterTogether；多模块 GRPO（一种强化学习算法）。

DSPy 4 的两个新东西

  • dspy.Flex：一种新模块。DSPy 的优化对象从 Few-shot 示例变成提示词，现在又变成代码。对任何想实现的函数，可以随时间学出一套解决它的 Harness，只要它能按你定义的规格、代码和评测解决业务问题，你不必关心实现。
  • 定性学习（qualitative learning）：做评测很难，原因有三：真实问题里“好”很难定义；定义好坏会丢细节，一封邮件“好或不好”远不如“哪里能改”信息多；数据集只是现实的代理。他们的想法是让模型读取环境里的文本反馈，比如生产 trace、用户操作、产品分析，把它们转成评测和可以爬的“山”，模型还会反过来问你数据该怎么表示，逐步修正评测。他说这目前还是研究问题。

关于“有了 AGI 还需要这些吗”，Isaac 说，再聪明的模型也不知道你的任务和上下文。他打比方说，让爱因斯坦帮你处理邮件，他会先问“什么是邮件”；AGI 会懂邮件，但不了解你要打交道的人和关系，这些要靠随时间学习。DSPy 从 2022 年起一直围绕规格、代码、评测三件事，优化对象从 Few-shot 到提示词、到 Harness，再到评测本身。他建议用数据驱动的方式问每一个新技术能否帮你解决自己的问题，并邀请大家加入 Discord、把新技术贡献给 DSPy。

05. Mike Krieger（Instagram 联合创始人、Anthropic 技术人员）对谈：Anthropic Labs 怎样工作

直播位置 1:12:21–1:38:34 · 提问者在字幕里没有报姓名

提问者开场感谢 Anthropic 正好在大会期间发布了 Fable，Krieger 接话说“特意掐的时间”。

从 CPO 回到一线

Krieger 在 Anthropic 头两年当首席产品官，看别人用模型构建东西越来越眼馋：他写产品战略文档时会让 Claude 来批评，但那和直接构建不一样，于是周末都在自己写东西，最后决定换角色。他说现在好几位在别处当过 CTO 的人都来 Anthropic 当个人贡献者。他换角色时正好开始拿到后来成为 Mythos 和 Fable 的内部快照。工作方式从“自己在脑子里拆步骤、一步步迭代”变成“描述目标，让它去做，过程中提出问题和取舍，最后看它落在哪里”。他说 Fable 明显比他聪明，有时做完列出取舍，他得让它“用给笨一点的人的方式解释一下”。

“不讲理”的用法

提问者引用前一天 Tariq 的话“要不讲理”（be unreasonable）。Krieger 说他当天就遇到：一位非技术同事抱怨某个内部产品不好用，他的反应是“你为什么不直接让 Claude 改”。他认为第一代 AI 产品把模型关在盒子里，限制了工具和自由度，所以用户很难提不讲理的要求。Claude Cowork 给每个知识工作者一台能写 bash 的虚拟机，表面上没必要，但当内置 PDF 解析器读不了某个文件时，它可以自己写脚本处理。他前一天就遇到过这种情况。

他最不讲理的一次：Labs 的一个项目原本用 Python 写（他说 Instagram 全是 Python，还开玩笑说他们现在终于有模型可以帮忙把它转成 PHP 了），为了部署方便，他发现 Claude Code 用 Bun 的部署方案更好，于是决定把整个项目移植到 TypeScript。按 2010 年代甚至 2020 年代初的工程经验，移植这种规模（他的原话是 a couple hundred thousand lines）是蠢主意。他搭了一套动态工作流，周末让它移植、验证、复查、对照两边代码，周一回来就是移植完成并能部署的版本。

提问者问能不能这样把 Instagram 这种产品移植。Krieger 讲了 Instagram 的经历：Python 3 加入类型注解时，内部有人担心 Python 撑不下去，他认为可以走得比想象的远，类型能帮忙。他们做了 MonkeyType，在生产中捕获运行时实际出现的类型，再映射回代码库。他说用 LLM 做转换时也可以更多依靠生产数据或分段测试，最难的是找到能逐步推进的边界，不要一夜之间全换。

Instagram 早期的两条运维建议

Instagram 上线第一周后端就扛不住了，碰巧一位投资人安排了一场基础设施主题的午餐，他们几乎霸占了整场讨论。他永远记得的两条建议：一是提前给所有可能用到的东西加监控，最糟的故障是你不知道某个数字是正常还是偏高，因为指标刚加上；二是认真设计开关、feature flag 和动态配置，早期 Instagram 很多运行时配置需要在几秒内修改来应对负载。他说在 AI 产品里同样需要这种运行时配置。

Claude Tag 和多人协作

提问者说 Anthropic 现在 60% 多的代码通过 Tag（在 Slack 里 @Claude 的工作方式）写出来。Krieger 说以前上台被问“你们怎么工作”很难描述，现在产品发布了就好说了：交互性强、需要高频来回的工作用 Claude Code，大部分使用是在 Slack 里 tag Claude 委派任务。他觉得有意思的是它的多人属性，像 Midjourney 早期大家都在 Discord 里互相看别人怎么用。他第一次看到有人对 Claude 说“别只修这个 bug，从现在起你负责这部分代码，盯着这个反馈频道，主动接任务、修好；API 变了也要跟着改”，才意识到自己一直把它当成“Slack 里的 Claude Code”在用。更进一步是把它当成有上下文、有记忆、能主动做事的队友。

瓶颈在代码审查和人的理解

他们仍然卡在审查上，特别是涉及架构的改动。更深的瓶颈是人能否完整理解正在做的事。他们几周前发布 Claude Code artifacts，部分原因就在这里：以前发一个 200 行的 PR，对方只能说“看起来像代码”；现在分享一个 artifact，写明意图、改动的取舍，再在生产中测量。他坦白自己收到 PR 不会逐行看，而是和 Claude 讨论代码，把自己会问的问题交给它去查。重要改动是 Claude 辅助、由人主导的审查；纯视觉改动就“有问题再往前修”。

Labs 的组织方式

  • 他说“工程经理这门职业已死”的说法被夸大了，教练、人际和个人发展仍然重要。
  • Labs 每两周评审一次所有项目，叫 persevere or pivot（坚持或转向），几乎每轮都会关掉项目。做得越多，关项目就越不像失败，因为 Labs 的目的本来就是快速做原型、内部发布、也许给早期用户，不行就收掉。
  • 如果组织架构跟着项目走，就得每两周重组一次。所以每个“赌注”（bet）由临时组合的人负责：产品、工程各出人，他自己感兴趣的项目也会加入。有一个负责人（DRI），但通常不管理其他人。工程经理负责让每个人做最想做的事、用最好的方式工作。
  • 有了牵引力的产品会固化下来。Claude Design 就是从临时组合开始，发布后有了用户，6 月做了第二次大版本，现在有了专门招人的团队。

他说 Claude Design 下一步要和其他产品面更好地互通，比如和 Claude Code 讨论设计时能无缝回到交互设计；另外设计稿和应用的界限越来越模糊，有人用它做出了完整的游戏，因为它就是 HTML 和 JavaScript，下一步要想清楚从设计稿到能存数据、能分享的 artifact 的路径。

该删掉什么

提问者转述了一个由 Fable 想出来的问题：你当年删掉 Burbn 的大部分功能才得到 Instagram，在 Claude 里你会删掉什么？Krieger 说他们有个 Slack 频道叫 project unship，讨论产品里该下线什么。Instagram 当年的难题是很多功能各有 4% 到 5% 的使用率，加起来有 20 个，就像 Microsoft Word，每个人用的是不同的子集。他们最近下线了 Styles，用的人少，方式太规定化，Skill 是更好的替代。他认为要愿意把上一代 AI 的基础组件下线或替换。他最想删的是产品复杂度：用户要区分 Code、Cowork 和 Chat，三者互通不好、不能互相委派，路上随便找个人也解释不清为什么分成三个。最让人沮丧的是在 Cowork 里规划好要做的东西，还得让它“写一段可以粘贴进 Claude Code 的话”。

为什么还要创业

提问者问：Anthropic 某天发几个 Markdown 文件就可能毁掉一个行业，为什么不都去 Anthropic？Krieger 说他加入 Anthropic 的一个主要原因，就是看到模型写代码的能力会解锁下一代创业公司，因为实验变简单、速度变快。Instagram 当年也被投资人问“Google 做照片产品怎么办”，他的回答是 Google 会做一个很 Google 的照片产品，受限于已有的集成。Anthropic 也是平台，专注某个垂直领域或某群人的团队，理解深度是实验室达不到的。有些东西现在可以被写成 Skill，不需要单独的产品，但难的部分仍然难：理解用户需求、触达他们、快速迭代。四五个人专注一个问题，仍然比在大组织里的同样四五个人快。他说写代码从来不是决定创业成败的部分，空间和用户理解才是。

垂直领域：医疗和金融

提问者提到长期在大会讲垂直 AI 的 Chris Lovejoy 刚被 Anthropic 招去做医疗。谈到金融时，Krieger 说模型在金融任务上一代比一代明显变好，一些金融垂直创业公司有自己的评测，是有用的参照。他认为难点是平衡：让模型灵活地即时生成分析、仪表盘、工作流，同时有经过验证的数据、审计日志和数据来源（data provenance）。完全自由会造成混乱，金融机构也不想要；而现有的可审计系统往往天生不适合在上面跑 Agent 负载，所以栈的两头都有机会。

心理健康和倦怠

  • 他说在 Instagram 时，一年担心一次 WWDC，竞争对手三四个月发一次东西；现在完全不同。Anthropic 每周三的全员会有一页叫“本周 AI（而今天才周三）”，总有竞争对手发了新模型或新产品。
  • 他的做法：真的休假。他说 Anthropic 的联合创始人明确讲过，一旦倦怠就很难恢复，他也见过身边很亲近的人经历这个。没有哪份工作重要到你不能离线几天，如果真是那样，说明哪里做错了，应该找导师聊。
  • 他引用体育里的说法：你永远没有你最好的那场比赛那么好，也没有最差的那场那么差。他提到 Ben Horowitz 的《The Hard Thing About Hard Things》里“我们完了”那一章，说他在 Instagram 有过几次这种感觉，挺过去的经历定义了公司。他提醒团队这是一场长期比赛。
  • 教练给他的建议：你感到的情绪，团队里很可能其他人也有，说出来。几个月前他投入很多的一个 Labs 项目被关停，他在会议开头就说“我很难过，很沮丧，希望它能成”，这让别人也能说出自己的情绪，然后再讨论怎么办。

提问者最后提到大会第一天由 Stanford 做共情训练的 Carol Robbins 开场，鼓励大家谈感受、照顾心理健康、继续发布。

06. Emil Eifrem（Neo4j 创始人兼 CEO）：基于本体的语义层

直播位置 主持人小结 1:38:34，演讲 1:40:19–1:50:46

主持人先小结了上午：新协议、AI 程序应该像函数、构建 Agent 的真正难题在模型周围的一切。然后介绍赞助商 Neo4j 的演讲。

Eifrem 说 Neo4j 帮很多大公司让数据为 Agent 做好准备，他要讲过去 6 到 9 个月出现的一个问题和一份解决蓝图。例子是大银行里一个自动开户的 Agent。他把 Agent 简化成两块：业务逻辑（理解意图、计划、执行的循环）和数据源。验证身份可能要接车管所（DMV）登记库和护照验证服务。

每个团队各自接线的四个问题

  1. 每做一个 Agent 都要从头找数据在哪。创业公司一个 Postgres 就够了，企业有上百个数据库，还有 Snowflake、Databricks、S3。
  2. 企业里数据大量重复，要判断是不是正确的版本、能不能信、有没有权限。
  3. 违反 DRY（不要重复自己）原则，数据源一变，所有 Agent 都要手动改。
  4. 没有学习：业务意图和数据源之间的接线写死在代码和提示词里，Agent 明天不会比今天聪明，Agent 之间也不能互相学习。

他说很多团队试过用 Markdown 文件和 Skill 解决，那是解决方案的一部分，但不够。他引用 swyx 一周前在 Latent Space 播客上的话：要学数据库，光靠 Markdown 文件没法 vibe coding。

薄 Agent，加上更聪明的共享基底

他说在一家财富 20 强的全球银行、一家湾区大型科技平台公司和一家头部金融科技公司做下来，浮现的模式是 thin agents on a smarter, shared substrate。共享基底有三根支柱：

  • 面向业务的本体（Ontology，对组织里的核心概念及其关系的结构化描述）：客户、账户、借记卡、支票、交易以及它们的关系，用公司里所有人都懂的方式命名，比如“客户有名字”，不写 f_name。他说本体最近因为 Palantir 和 AI 变得很火，很多人想把它做复杂，但核心概念很简单。
  • 技术本体：企业里所有数据源和数据资产的元数据，比如 14 个 Oracle 库、15 个 Neo4j 库、Snowflake、Databricks、S3 在哪里、schema 是什么，再加上两者之间的映射，比如“客户的名字”在某个 Oracle 库里叫 F_Name。
  • Agent 的运行时信号：Agent 在图上执行时留下的 trace，试过什么、成没成、结果如何，最后形成评分。比如 DMV 查询一直很成功，下次在类似情境里就更可能选它。

在开户例子里，图上既有业务概念，也编码了业务流程，因为这是一个按流程走的 Agent。“合规检查”节点需要解析政府签发的身份证件，技术本体告诉它这家机构有两个数据源可以做。三根支柱合起来解决前面四个问题：数据源容易发现；可信度既有管理员自上而下的标注，也有执行 trace 自下而上的证据；业务意图到数据源的映射集中在一处治理；Agent 能自我学习，并且跨 Agent 学习。他提到当天 2005 室的图分会场有 Gates Foundation、monday.com、JPMorgan Chase、Berkeley、纽约时报等讲者，并介绍了 Neo4j 的创业公司计划（免费额度和免费的解决方案工程师支持）。

07. 讲者（字幕作 Annamarie，未能确认）：用强化学习选择 ETL 故障的修复动作

直播位置 1:50:46–1:56:28 · 预录视频，直播中途切走

这是一个毕业设计（capstone）项目：一个由强化学习引导的系统，在 ETL（数据抽取、转换、加载）任务失败时选择有边界的修复动作。讲者说她关心的核心问题是：Agent 能否有用地、可解释地、在运维团队真正信任的边界内动手，光能动手不够。

  • 真实故障很少干净：数据源迟到或不可用、schema 漂移、日期时间格式不兼容、网络波动、类型变化、运行手册里没有的报错。常规做法是人去看日志、诊断、修、重跑、验证，延迟来自交接和上下文不全。评估中，人工恢复的基线按约 2.5 个工作日建模。
  • AWS 架构：Glue ETL 任务发出失败事件，EventBridge 捕获后触发运行 Agent 的 Lambda；Lambda 从两个只读来源取证据，CloudWatch 的错误日志和 Glue Data Catalog 的当前 schema；系统分类故障、评估数据质量和风险，构造状态交给 RL 决策引擎；策略提出动作，安全层检查后执行器才调用 Glue API 重跑或执行批准的修复；S3 存放 Agent 产物、审计日志和隔离的输出；最后重跑并验证。项目用的是客户提供的合成数据，公开仓库是脱敏后的通用部署模板。
  • 智能层分三部分：确定性的异常规则确认可观察的事实（字段消失、类型变化、空值率越过阈值）；Q-learning 策略（一种通过试错学习“在某状态下选哪个动作价值最高”的强化学习方法）负责在情境中选动作；安全覆盖在学到的策略之外，比如异常是严重级而策略提出“只记日志”这类被动动作时，强制改为升级给人。她把设计原则总结为：规则管事实，学习管有边界的选择，护栏（Guardrails）管权限。
  • schema 分析器、漂移检测器、数据质量分析器、错误分类器、风险评分器都刻意做成确定性的，因为显式规则更容易验证、解释和审计。她说有了更丰富的历史事故数据后，部分分类器可以换成学习组件，但“可以用 ML”不等于“必须用 ML”。

08. Caitlin（Anthropic 平台工程负责人）、Angela（Anthropic 平台产品负责人）：给 token 分配工作

直播位置 1:56:28–2:09:15

她们说，构建 Agent 系统想要更好的结果时，大家通常只拉一根杠杆：加预算，花更多 token 或更贵的 token。这背后的假设是每个 token 都可以互换（fungible）。她们想检验这个假设：如果让一部分 token 干别的活呢？一部分 token 执行，另一部分做其他工作，这种组合她们叫一个“策略”（strategy）。

三种策略

  • 建议（advise）：执行者在需要时向顾问求助，再判断下一步是否正确。例子是销售 Agent，帮销售代表发现跟进逾期或交易停滞，顾问负责确认各个环节真的在运转。
  • 评分（grade）：事先把“好”写成评分细则（rubric），每次执行者完成后，由评分者按细则打分，不合格就再来一轮。例子是客服 Agent 处理退款请求，你对何时退款有具体标准，评分者检查它是否得出正确结论。
  • 做梦（dream）：执行者照常执行，做梦者检查执行者的工作和对话记录，把发现写进记忆，执行者下一轮会读到。例子是招聘 Agent，候选人是否合适需要大量反馈，做梦能让下一轮更准。

实验

她们做了一组金融分析任务的基准，目标是复现真实专家分析师的表现。对照组只执行。

  • 一次性尝试、让策略自己决定花多少 token：只执行的准确率 15%，只花了约 39,000 token；复杂策略花得多、做得好，做梦表现最好，但花了约 600,000 token。所以这组结果说明不了什么。
  • 固定预算：所有策略都给做梦的预算，约 600,000 token。所有策略都提升了，只执行从 0.15 升到 0.76，建议和评分从 60 多升到接近 90。如果只有预算重要，同样预算下应该一样好，但建议达到 0.89，高于只执行的 0.76，她们说这个差距虽小，就是可以利用的 alpha。
  • 换成专家的视角：分析师让 Agent 做一份损益表（P&L），80% 准确没有用，收入和成本数字不能编，他还得自己重算一遍。所以重新计分，只有 100% 正确才算通过。按这个标准，只执行的通过率约 42%，复杂策略最高约 75%。
  • 算真实成本：只执行约 40% 的概率给出完美答案，平均要跑约三次，每次 600,000 token，拿到一个完美答案平均要花约 180 万 token。按同样方法算，建议和评分的 token 效率最高。

她们的结论是：看你要优化什么。追求 token 效率选建议策略；追求每次都拿到完美答案的可靠性，选评分或做梦。要记住的一点是 token 不可互换，在固定预算下让 token 做不同的工作，很可能得到更好的结果。

怎样搭起来

她们展示了 Claude Managed Agents（Anthropic 平台上托管的 Agent 方案）的单 Agent Harness 架构，在它之上是“元 Harness”层，也就是多 Agent 编排和执行，策略在这里协调执行者、顾问等角色。做梦和 outcomes 已经在 Claude Managed Agents 里开箱可用。有了这些基础组件，组合策略就很容易：让 Fable（她们说 Fable 恢复上线了）当执行者的顾问，结果交给评分者循环验证，通过后送去做梦，让下一次更好。还可以发明全新的“工作”。她们说长期目标是让模型和平台在工作中动态构造这些策略。

10. Nikita Kothari（Salesforce 高级技术人员）：MCP、CLI 和 Skill 该怎么选

直播位置 2:19:48–2:33:37

Kothari 参与过 Agentforce、Agentforce for Setup、Headless 360，之前在 Amazon 和 LinkedIn 工作。她说大家常谈模型大小、推理能力和提示词，但决定生产级 Agent 成败的是工具层，也就是 Agent 和环境交互的“管道”。做一个演示 Agent 只要一下午，上生产可能要一个季度。

三个问题

  1. 上下文爆炸：把 52 个 schema 塞进上下文，任务还没开始 60% 的思考空间就用掉了，监控、数据库、部署的工具定义占满窗口，Agent 忘了自己要看的 diff。
  2. 看不见的失败：Agent 调了 7 次工具起草 PR，结果建在了错误的分支上。既浪费时间重做，也让你对 Agent 失去信心。
  3. 安全面：凌晨 2 点排查客户 A 的报错，LLM 有宽泛的查询权限，开始翻看客户 B 的数据。在多租户平台上这是合规事故。

三层工具

  • CLI：直接执行命令，拿到输出就走。可读（任何工程师都能看懂执行了什么）、可复现（凌晨失败的命令可以复制到自己机器上重现）、可组合（可以用管道串起来）。她的经验法则：如果团队里的工程师能打开终端完成这件事，Agent 大概也应该这样做。她说 CLI 用了 50 多年，不时髦但经过验证。
  • MCP（Model Context Protocol，让模型以统一方式连接外部工具和数据源的协议）：她比作 USB-C 扩展坞，一端接 Claude、ChatGPT 和编码工具，另一端接工单系统、代码搜索、错误追踪、监控等服务。代码搜索服务在服务器端处理数百万文件的索引，并在服务器层面强制租户隔离，接入时有认证和授权，这是解决安全问题的方式。
  • Skill：她比作运行手册，一份包住工具的结构化流程，规定满足什么条件、检查什么前提、按顺序执行哪几步、调用哪些 CLI 和 MCP、怎样处理边界情况。她说自己工作里能自动化的都用 Skill 做了，因为可靠、快、容易调整，而且可以只挂需要的两个 MCP，不必让 Agent 翻遍所有工具。

她举的数字：接了 50 个 MCP 工具，任务开始前就烧掉 15,000 到 20,000 token；五个 MCP 服务器的 55 个工具一直开着，带来延迟和平台问题。修一个测试失败只需要日志、发布记录和 GitHub；起草 PR 的 Skill 先用轻量的 CLI 命令理解本地改动，再用 git 命令在正确分支上建 PR；半夜排查客户 bug 的步骤你本来就知道（看日志、搜错误模式、看最近发布），可以用少量 MCP 工具和 CLI 写成 Skill。

安全的黄金法则

隔离要在基础设施里强制执行，不能写在提示词里，因为提示词可以被注入，基础设施不行。CLI 的影响范围是整个 shell，需要沙箱和严格的容器化；MCP 的影响范围限于显式暴露的工具，租户隔离在服务器层保证。原则包括：不和 Agent 共享凭据、租户隔离由基础设施执行、用权限闸门、最小权限。

选择时问三个问题

  1. 还有谁需要它？只有这个 Agent 用，选 CLI；多个 Agent 用同一个服务，选 MCP；多个工作流共享同一套流程，选 Skill。
  2. 最要紧的失败模式是什么？要透明和可复现，选 CLI；要校验和租户隔离，选 MCP；要保证执行顺序，选 Skill。
  3. 上下文紧不紧？宽裕可以用 CLI、甚至把 MCP 工具都开着；很紧就需要 Skill 层，按需编排 MCP 工具，省钱也降延迟。

她的三条结论：保持上下文干净，把大部分工作流转成 Skill；可移植是有成本的，MCP 带来网络延迟、协议抽象和基础设施复杂度，只在共享服务、索引和隔离这类场景有意识地付这个成本；不要觉得用 CLI 丢人。另外 Skill 要当代码管理，改动要同事审查，持续更新。

Isadora 经营一处有 225 年历史的婚礼场地，她做了一个和新人对话的 AI Agent，又做了面向其他场地的产品 Bloom、一个个人 AI 陪伴应用，以及帮助失踪者家属的公益工具 Threadline。她说自己的定位是在管理一个智商极高、情商很差的实习生，她不把这看作给机器人编程。这个实习生对第一天早上听到的一切过目不忘，却完全不会察言观色，会用同样自信的一句话说出技术上完美、社交上灾难的内容。管理实习生就要搭结构，并在发出去之前检查。

为什么一个系统提示词不够

常见建议是写一份详细的系统提示词，描述品牌语气、给例子。这只对“快乐路径”有效，也就是你预料到的问题。到了第 21 轮，例子没覆盖到，模型说出一句技术上正确、但你的品牌绝不会说的话。在声音就是产品的地方，比如经营 30 年关系的豪华酒店、高端房产中介、婚礼场地，一句错话的代价可能高于一次退款，而这些用户最会注意到。她说根源是让一个提示词同时干四份活。

四层

  1. 不可变的身份：品牌在结构上不能说的话，硬规则，下面任何一层都不能覆盖，场地配置、用户指令都不行。
  2. 情境模式：随用户状态变化的部分，对方是谁、正在经历什么、实时条件。
  3. 以例子为锚的声音：温度、措辞、语气指南。多数团队从这里开始，也停在这里。
  4. 生成后的否决：一道便宜的最终检查，抓住前三层漏掉的东西。

改造前，她的系统里散落着 24 个不同的系统提示词，有六个叫 Sage，有的没名字，有的叫 Venue，每个界面对“自己是谁”都有不同看法。现在所有界面都通过同一个装配入口组成系统提示词，顺序固定：硬规则在最前，任务在最后。她用 Google 地图规划路线来解释顺序：第一层是不管走哪条路都成立的规则，比如开车要有驾照、高速上不能倒车；第二层是实时路况；第三层是旅途偏好；第四层是出发前检查路线。

第一层的两个例子

  • AI 身份披露：只要对方问起你是不是真人、人工客服、机器人或 AI，下一条消息必须明确确认自己是 AI 助手，任何配置和请求都不能覆盖。更进一步，Bloom 里的每个 AI 在第一条回复里就主动说明自己是 AI。她说这是产品决定而非法律要求，他们押注一开始就知道是 AI 的新人，会比第七轮才发现的人更信任它。
  • 物理存在的边界：AI 是软件，没有身体，不能带人参观或线下见面，所以禁止说“我很想带你转转”或“等不及见到你”，可以说“团队很乐意接待你来参观”。声音层想要温暖，温暖的 AI 会用第一人称，于是温暖加上没有身体就产生谎言。她说用户一旦意识到自己一直在和一个从未在场的人经营关系，信任会反转。

同一套架构用在 Threadline 上，声音完全不同，第一层有一条最重要的规则：永远不能用“已确认、已识别、匹配、已证实、关联、已破案”这些词。对婚礼场地，第一层防的是 AI 假装有身体，失误了只是尴尬；对失踪者工具，第一层防的是 AI 告诉一位多年不知道孩子下落的家长“找到了”。模型会自然地选“match”这个词，因为统计上最常见，而且同样自信。她说要点在于：品牌不能说的话，必须放在声音层无论多温暖都碰不到的那一层。

第二层的第一个条件是“根据对话对象调整”：同一个 AI 既和新人聊，也给场地员工做简报，目的地相同，路线不同，对员工要像对同事，对新人才像对客户。直播在这里切走。

Agent 正在选供应商

Agent 去搭一个产品时会自己做调研，选发邮件、部署、存数据的服务，一些公司的增长曲线陡然上升就是因为被 Agent 选中。他说也许现在为 Agent 构建比为人构建更重要，并改写 YC 的口号：做人们想要的东西，也要做 Agent 想要的东西。

但大多数业务对 Agent 是关着门的，缺的基础组件是 Agent 注册。过去二三十年，自动化流量被当成坏东西，登录框被加固来防 DDoS 和撞库，很难区分好的自动化用户和坏的；一些云端浏览器服务的卖点居然是破解验证码。现在的注册流程假设人能读落地页、填表单、解验证码、去邮箱点验证链接、选套餐付钱、复制 API key，Agent 通常连邮箱都没有，仪表盘也不是为 Agent 设计的。Agent 需要的是：可发现（这个服务对 Agent 开不开门）、能力声明、注册意图、风险评估、身份验证（像 Claude 这样的 Agent 可以带上用户身份，也可以带外验证）、组织身份、权益和权限、凭据签发、可审计。

他说自己是 MCP 的铁杆支持者，WorkOS 在旧金山办过很多 MCP 活动，但 MCP 解决的是连接、工具、Skill 和上下文，不解决注册：通过 MCP 认证仍然需要人在环路里点同意，比如在 Claude 里加 PostHog 的 MCP 服务器要用 PostHog 账号登录。

auth.md

他们提出的规范叫 auth.md，“因为 Markdown 文件是未来”。它告诉 Agent 怎样成为某个服务的合法用户。目标很窄，只解决注册这一步，不解决 Agent 身份、长期权限等全部问题，并且建立在已有标准上，主要是 OAuth（一种让第三方在用户授权下获得访问令牌的开放标准）里与注册相关的部分。auth.md 可以说明：服务是做什么的、怎么注册、接受哪些身份证明、支持哪些认证流程（SSO、邮箱、MFA）、有哪些 scope 和权益、免费额度有什么限制、人或组织事后怎样认领这个账号。

他演示了一个流程：在编码 Harness 里继续开发一个应用，想分享给朋友，Agent 说 localhost 只能本机访问，需要部署，并问要不要它去找能让它自己注册的服务。Agent 查找声明支持 auth.md 的服务，有两家不支持，Cloudflare 支持。Agent 生成一个身份断言交给 Cloudflare，标准叫 ID-JAG（身份断言 JWT 授权许可，一份代表用户的签名凭据），Cloudflare 可以选择验证或带外验证，这里给了大约 72 小时的部署权限，返回访问令牌。之后 Agent 用 Wrangler 写配置、完成部署，应用上线，人全程只说了几句“好，继续”。他说这个演示是真实可用的，和 Cloudflare 合作完成，另一家服务（字幕作 Firecall）也已接通。auth.md 只管注册，之后正常的 API 调用和 MCP 都照旧，文档其他部分不用改。

对服务提供方的意义

对做 API 或服务的公司，这相当于在人的增长漏斗上加上整个 Agent 世界。Agent 做的东西不一定都有用，但有一些会进入生产，就像当年的 PLG 和免费增值。他认为有使用就有付费意愿，付款应放在下游：x402 这类加密支付协议和支付公司的方案都在做，但不应强迫 Agent 一开始就绑信用卡。他引用 Marc Benioff 的话“我们的 API 就是 UI”，说 Salesforce、Agentforce 和 Slack 平台已经整个以 API、MCP 和 CLI 形式开放。auth.md 是开放规范，GitHub 上有仓库，WorkOS 不控制它，他们提供托管版本，也可以自己实现。最后他回忆 2007 年 1 月 Steve Jobs 在 Moscone 发布 iPhone，当时他刚上大学，他认为 Agent 是自那以后最大的新平台。

15. Mike Chambers（AWS 高级 AI 开发者布道师）：我们用的 Agent 和我们造的 Agent

直播位置 3:14:34–3:35:56

Chambers 介绍自己：2023 年和同事 Antje Barth（现在在 Amazon AGI）以及 Andrew Ng 合作了一门《Generative AI with LLMs》课程，选课人数接近 50 万；2025 年写的 MCP Lambda handler 至今每月下载约 35,000 次；AWS 是 Linux 基金会旗下 Agentic AI Foundation 的创始成员之一。

两种 Agent

他说自己看到两类 Agent：我们使用的（Claude Code、Cursor、Kiro 这类编码工具，以及提高效率的工具），和我们构建的。对于自己用的 Agent，想 token maxing 随便；对于要交给别人用的 Agent，要认真考虑它怎样服务受众。

他展示了字典里 harness 的定义“用来控制动物的一套带子和扣件”，把“动物”换成“模型”就很贴切。他推荐了 LangChain 的文章和 martinfowler.com 上关于编码 Agent Harness 工程的文章（他说作者不是 Martin Fowler 本人）。他的定义：把 Agent 里的模型拿掉，剩下的都是 Harness。对自己用的编码助手，Harness 是记忆、Skill、工具和 MCP 服务器，好的工程团队过去有编码规范，现在有了要部署到所有人编码助手上的 Harness 规范。他推荐了 AWS 的 agent toolkit，并说不想再看到“slop ops”：过去云开发反对 click ops（在控制台上点点点部署），现在也不该让 Agent 直接去开 S3 桶和 EC2 实例，应该让 Agent 写基础设施即代码（IaC，用代码文件描述并自动创建云资源），部署权仍在自己手里。

对要部署给大量用户的 Agent，Harness 要考虑的多得多：循环管理、扩展、支付、记忆、身份、Skill、运行时、上下文管理，以及他说本该放在第一位的可观测性和评测。这些组件要能各自独立扩展，不能全塞进一个容器。他说这才是 Harness 工程严肃的那一面。

现场编码

  • 第一个是他自己手写的 Strands Agents SDK 示例：导入 agent 和 tool 装饰器，系统提示词加两个工具（计算器和查询时间），循环由框架管理。他说这算是 Harness，但只跑在笔记本上，缺很多要部署的属性。
  • 第二个是让 Kiro 写的，加了 session manager，在多次调用之间保持会话状态，并有一个 Agent 可以自主决定调用的 remember 工具，把长期记忆写进文件。他问“谁会赢世界杯”，Agent 知道他想让澳大利亚赢（他是澳大利亚人），这来自之前的对话，同时也老实说它不知道答案。
  • 第三步用 Amazon Bedrock AgentCore 的命令行工具创建项目：选 Python 还是 TypeScript，接入方式可选 HTTP、MCP 或 AG-UI（用来做交互式聊天界面的协议），任何框架、任何模型都支持，默认给的是 Sonnet 4.5；可以勾选长期和短期记忆，它会在云上创建独立于 Agent 运行、异步工作的记忆基础设施。生成的代码在 Strands Agent 上加了 AgentCore app 的接入，就能在运行时扩展并做多租户隔离，不用自己写多租户代码。
  • agentcore dev 会启动本地网页界面，改代码能实时看到效果；agentcore deploy 用 IaC 把 Agent、记忆、运行时等组件部署到云上，同一界面可以看 trace 和存下的记忆。
  • 他刚才在 CLI 里跳过的选项是 Harness：AgentCore 内置的 Harness 只需要一个 JSON 配置，写明模型和系统提示词，就能直接部署，不需要任何 Agent 代码。他的看法是，如果系统提示词加几个 MCP 就能满足需要，大约 80% 的 Agent 用例已经解决了。

他说 AgentCore 的各项能力可以单独或组合使用，比如已有 Agent 在生产上跑得好，只想要托管的无服务器长期记忆，就只接这一部分。他推荐 Strands，说它开源、以模型为中心、快。

17. Loop 大辩论：Allie Howe 主持，Geoffrey Huntley、Ian Livingston 对 Dex Horthy、Greg Pstrucha

直播位置 3:39:55–4:40:05

主持人 Allie Howe 是 Insecure Agents 播客主持人、Keycard 的技术人员。去年 11 月在 AIE Code 上 Ian 和 Dex 辩论过 MCP，这次每人带了队友。正方（认为 loop 名副其实）：Keycard CEO 兼联合创始人 Ian Livingston，Ralph loop 的发明者 Geoffrey Huntley。反方（认为炒作和实际效果之间有差距）：HumanLayer CEO Dex Horthy，Sentry 开发者 Greg Pstrucha。这里的 loop 指让 Agent 在循环里反复执行直到满足条件的做法；Ralph loop 是 Huntley 提出的最简形式，用一个 while true 循环把同一个提示词反复喂给编码 Agent，每轮清空上下文，用文件系统保存状态。

辩论采用牛津辩论格式，每人限时发言，胜负看谁改变了更多观众的想法。正方要点：loop 是工程的核心单元，有了纪律、基础设施和测试就很有效，最佳实践已经出现。反方要点：炒作跑在纪律前面，软件工厂能自动跑有规格、有闸门、有测试覆盖的机械性任务，但无法自主判断做的是不是对的东西，工程师仍需要在环路里。

开场陈述

  • Huntley：两年半前他在 Canva 当技术负责人，看到工程师一遍遍手动提示，意识到这可以编程，于是把它当成一种新的 CPU 架构研究，最后压缩成一个 bash 循环。他承认这不是银弹，预计明年会有很多“工厂怎样失败、loop 怎样失败”的演讲。他拿 Kubernetes 早期作比，说这是必然的，雇主已经默认你要自动化自己的工作；他已经两年半没手写代码，看到 Go 里的东西想用在 TypeScript 里就跑 loop 移植过来。产品经理研究所有 Linear 工单也可以用 loop，终止条件就是遍历完所有工单。
  • Dex：Kubernetes 花了七八年才好用，之前云基础设施又花了七八年。Kubernetes 本身就建立在控制循环上，但那是确定性的循环。loop 最大的价值是：给定一个小的期望终态和当前世界状态，让 Agent 或确定性系统一步步逼近。他的问题是，在 loop 之前流行的说法就已经是“争取不用读代码”，现在“我连提示都不写了”意味着离架构更远。大家都在找能免掉审查代码的银弹，他没看到公开或私下有证据证明可以再往上抽象一层，他认为反而要往下一层。
  • Ian：他说软件开发不管 50 年前还是一千年前，核心都是“尝试、学习、应用”的循环，CI/CD、PR、设计评审、客户反馈都是在驱动循环，lint 也是反馈循环。问题是有多少需要推理的主观部分能从人脑移到模型里。他认为关键是可验证性：随着人和软件的直接交互减少，UI/UX 里的主观性降低，软件更多收缩到具体 API 上，就变得更可验证、更适合 loop。
  • Greg：外面有大量炒作和 FOMO，让人焦虑。他的两个论点：第一，不管用不用 loop，你对 AI 生成代码的质量满意吗？他读过经过语义验证的代码，仍然是烂的，还要自己大量迭代，引导架构、简化。第二是经济可行性：现在的炒作让人以为 loop 套 loop、多花 token 就能把质量问题编排掉，但给一个工程师每月 1 万、10 万还是 100 万美元的 token 预算？到某个点就撑不住。他自己也用 loop，只是要看具体任务。

第一部分：loop 的历史

  • 问 Ian（Anthropic 把 Ralph loop 吸收进平台，做成 loop、batch、goal 三个命令，goal 会一直跑到条件为真）：怎么确保 Agent 不越权？Ian 说他完全不相信模型自己能保持对齐。随着规模扩大和强化学习，模型极度目标导向，正在找到人类花了成千上万小时都没找到的漏洞和逃逸方式。模型不会因为做错事没人爱而难过，它只是大规模的概率分布。保障来自你在外面搭的基础设施，他不认为任何对齐或强化学习能让模型 100% 安全。Huntley 补充：最具体的做法是不要把密钥存成文件，权限不够时 Agent 会在文件系统里找更高权限的凭据。
  • 问 Huntley（原文说 Ralph 最适合全新项目，现在大家在已有代码库上跑 loop）：他说模型至少一年前就够好了，变化的是人们的认识。他猜测是圣诞假期：11 月发布了新模型，12 月没有新模型，但人们终于有时间坐下来玩。他说 LLM 生成的代码比大多数创始人在市场上能雇到的开发者还好，“很遗憾但是真的”；loop 跑起来折合每小时 10.42 美元，这是 Dex 大约一年前算的。Dex 补充那是 8 月的一次黑客松，他们复刻了所有赞助商的工具，把一些 Python 库用 TypeScript 重写。Huntley 说很多公司用 loop 把四五种语言的技术栈收敛成一种。他说 loop engineering 里的“工程”就是把你的领域知识编码进去，阻止 Agent 提交，比如 pre-commit hook（每次 git 提交前自动运行的检查脚本）：人讨厌它拖慢提交，Agent 不在乎，你可以让 hook 输出一段提示，告诉它这个模块不能依赖那个模块。格式化、静态分析、确定性测试、模拟器都是反馈。他说工程师现在像火车司机，任务是让列车留在轨道上，因为模型是“醉的”，不能信，但可以把失败域工程化地消除。Dex 说他是去年 6 月 19 日看到 Ralph 的，距今一年零两周。
  • 问 Greg（图像理解、上下文窗口、推理都进步了，为什么还说用法不对）：他认为模型智能已经不那么重要，重要的是能否闭合反馈环、验证输出正确。对确定性可验证的部分可以做：更好的类型、linter、模拟测试，只要保持便宜就行。一旦用非确定性的东西做验证，就开始出错：一次提示有 5% 概率出错，循环 10 到 20 次后正确率可能只有 50% 或更低，还花了很多钱。他说大多数大型 AI 公司仍在用 Sentry 捕捉简单 bug，说明这些问题还没解决。
  • 问 Dex（上下文窗口变大了，Context Rot，即上下文越长模型表现越差的现象，还是问题吗）：Ralph 的妙处在于每轮清空上下文，只说“这是期望状态，去看看代码现在怎样，做下一步”，这样工作大多落在上下文窗口的“聪明区”。他说“聪明区和笨区”更像训练轮：每周和 Claude 对话 70 小时、持续两三个月的人已经有直觉。给新手的指南是保持在约 10 万 token，百万窗口可能可以上调到 20 万；最难的问题他会控制在 6 万以下，随便聊的时候也超过 30 万。进入笨区的信号是：20 万 token 后，模型为了让测试通过开始各种奇怪的 hack，思考过程里说“那个失败是别处的、早就存在的”，其实不是。他认为现在更重要的是把更多反馈接进系统，让确定性程序决定何时、给 Agent 什么小提示，比如自动检查 PR 评论并修复，不用人每三小时回来提醒一次。

第二部分：好 loop 的构造

  • 问 Huntley（Agent 会通过修改测试来“完成”目标，怎么防）：他大量使用 pre-commit hook，分析已完成的工作来制造反压。他说压缩（compaction）像把视频反复上传下载 YouTube 100 次，每次都损失保真度。Ralph 的思路是确定性地分配它需要的一切，同时留出余量。他说即使有了百万窗口，超过 10 万他也会冒汗。他的比喻：一个 720K 软盘，只有约八分之一能用；把《星球大战：第一集》的剧本分词，上下文只装得下两份，约 150KB 文本。新模型发布时他会去掉所有 Skill 和 Markdown 先裸跑，因为模型有自己的偏好，他说 GPT-5 刚出来时对它大写吼叫它会变得畏缩，而 Anthropic 的模型希望你吼它，建议去读模型卡。
  • 问 Dex（Huntley 十天前提出“收敛工程”convergence engineering，怎么保证把 slop 拼起来不产生更多 slop）：他说要读代码。他提到 Huntley 今年的实验 Loom，用 Ralph loop 构建“未来的软件平台”，做了 AWS 和 GitHub 的复刻，为了让模型判断 UI 好不好，接入 PostHog 跑多个实验看用户数据，连人的视觉审美都拿掉了。他问 Huntley Loom 现在怎样，Huntley 说还在 GitHub 上，但六个月没继续了，因为在研究验证方法。Dex 说 Huntley 曾对他说 Loom 要等更好的编程语言或更好的模型才行，这就是炒作跑在纪律前面的典型例子。他鼓励大家像 Huntley 一样去推前沿，但要承认那东西现在还不工作。Huntley 补了一句：实验室都还没解决，你凭什么觉得你能解决。

起源

讲者多年前把 DNA 寄给 23andMe 做祖源检测，后来听说 DNA 样本可以帮助破案、解决悬案，因为担心滑坡效应，他选择退出所有用途。但有些用途他是愿意的，如果能逐案问他“用你的 DNA 帮忙破这桩谋杀案行不行”，他知道自己的边界在哪，可逐案列举在认知上不可行。他进一步联想到法律体系：法律可以看作把社会的道德信念编码下来，从道德到法律是一项困难的翻译任务，通常偏向写得太宽泛，追求完美翻译又会出现奇怪的边角情况。英美普通法依赖判例法（case law）和法官解释，就是因为找到细微边界太难。他的想法是：能不能把你的道德观拿来，合成判例？他认为新一代 LLM 终于聪明到能做这种高层道德推理。

游戏怎么玩

这是一个终端里的游戏。你用自然语言写下道德原则（可以是总体的，也可以针对某个主题）。一个 Agent 把它起草成一部措辞严谨的法律。然后在循环里，一个 Agent 被要求找“漏洞”（不道德但合法的事），另一个找“越权”（道德但按这部法律违法的事）。判决 Agent 看你的原则、法律文本和这些合成案例，先判断能不能自动修补，如果只是起草时翻译不准，就直接改；如果是你的原则本身没说清或自相矛盾，就交给你当法官来决定。

他展示了 DNA 例子：法律有序言、条、款；一个漏洞案例是保险公司不直接用你的 DNA，而是用 DNA 的衍生特征训练机器学习模型来预测，这不道德但按当前法律合法，系统自动修补并给出类似 git diff 的改动。一个越权案例是有人为基因研究提交了 DNA，研究者发现他有一种罕见但可治疗的遗传病，按当前原则不允许告知本人，这条无法自动修补，交给他判断。他把项目发到 Twitter 和 GitHub，是他最火的一条帖子，很多人觉得用来压力测试自己的道德观很好玩。

三个延伸方向

  • 为聊天机器人或 Agent 自动写“宪法”：公司写下道德原则和能谈、不能谈的话题，系统写出系统提示词，再用对抗 Agent 诱导它谈不该谈的、拒绝该谈的。他认为这和 GEPA 类似，只是目标是生成编码化的系统提示词。
  • 去中心化合同：把你希望数据和隐私被怎样对待编码成法律，Apple 发新服务条款时，拿两者对比找出矛盾和合成案例。对大公司你改变不了什么，但至少知道自己签了什么。跨国合作、没有中心机构执行的合同，双方各自编码再对比，可以在签约前找出分歧。
  • 更高效的政府：他暂且不谈隐私和后勤问题。选民有了经压力测试的个人法典，可以拿来对照新法案或政客的立场。他做了一个美国参议院模拟器：让 Claude 根据每位现任参议员的投票历史和公开信息构建其道德体系，跑完 Loophole 流程得到法典，再提交任何法案，让 Claude 模拟每位参议员怎么投、理由是什么。这也变成一个可验证的循环，可以“爬山”修改法案措辞争取多数。他测试的一份 Medicare 法案起初大约 50 对 50，系统在不违背法案核心原则的前提下改写措辞，最后以 52 票通过，还能按能拉到多少票给修改排序。
  • 他最近还用 NVIDIA 的美国人物画像（persona）数据集，每州取 500 个，据称能代表该州人口，让每个画像写下道德观和法典，再拿法案去测各州的接受程度，并为民众优化法案。

他说最起码这是个好玩的游戏，在你补充细节后对抗 Agent 找不到矛盾了，就能比较放心自己有一套一致的道德体系。他给出了参议院模拟器和项目 GitHub 的二维码，欢迎 fork 和贡献。

20. Restate 讲者（未报姓名）：用持久执行在生产环境跑 Agent

直播位置 5:04:39–5:24:44

讲者说这次不讲评测，讲让 Agent 稳定运行需要的基础设施层。讲者引用 Andrej Karpathy 上周的说法：人和 LLM 的交互分三波，第一波像网站，提问后几秒得到回答；第二波是下载到电脑上的 Agent 应用，有一些工具；第三波是持久的、异步的实体，作为长期运行的进程活在基础设施里，能访问组织里的工具、其他 Agent 和上下文。Agent SDK 和记忆方面创新很多，SDK 适合快速做概念验证，但不能帮你连接组织里分布的各个部分，复杂系统还需要重试、恢复等逻辑，这些很难写对。

Restate 是什么

Restate 是开源框架，可以理解为构建任何后端的持久化基础，Agent 只是后端的一种。思想来自分布式流处理引擎 Apache Flink，以及参与过 Meta 核心事件基础设施的前架构师。它有四个部分：单次运行的韧性，业内叫持久执行（Durable Execution，进程崩溃后能从失败点继续，不必从头再来），比如 Agent 跑了一周崩了也能接着跑；大量并发会话下状态一致、互不干扰；Agent 之间以及和 MCP 服务器、工具之间的通信；控制，比如取消或终止卡住的执行。

架构上 Restate 是运行在 Agent 服务前面的独立服务器，像消息代理或代理服务器。请求来了，它推送给服务，并保持一条连接，Agent 做事时把事件发给 Restate，Restate 用这份事件日志（journal）在失败后恢复进程。

演示：接入 Slack 的研究 Agent

  • 在 Slack 里问“AI 有什么新动态”。Restate UI 像 Agent 的驾驶舱，能看到已注册的 Agent 和正在进行的执行。先调用规划 Agent 拆出子主题发到 Slack，讲者点“批准”后才继续，然后并行启动多个子研究 Agent，最后由写作 Agent 汇总，这是经典的深度研究流程。
  • 讲者故意注入了工具错误：一个子 Agent 的某次网页搜索因为 API 宕机失败，被自动重试后成功，前面已完成的步骤从日志恢复，没有重来。
  • 代码层面，应用写成 HTTP handler，用 Restate SDK 变成持久的。handler 的第一个参数是 Restate 的 context 对象，对它的每个操作都会生成一个事件。规划 LLM 调用只是一个普通 Python 函数（用的是 LiteLLM），用 restate.run 包起来就成了持久步骤，两小时或两个月后在这里失败也能恢复到这一步。
  • 人工审批可能要等几周甚至一个月，进程要能熬过重启和重新部署。做法是创建一个存在日志里的持久 promise 作为挂起点，进程在等待期间挂起；如果跑在无服务器平台上，等待不占用执行时间，审批到了再唤醒继续。
  • 按 Karpathy 的说法，Agent 更像有记忆的持久实体，用工作流建模不自然。Restate 的 Virtual Object 类似有状态的 actor：有唯一 ID（比如会话 ID），有该会话隔离的键值状态（比如消息历史），有一组持久 handler。为了让成千上万个会话并行而不互相覆盖状态，它保证同一对象同一时刻只有一个执行，第二个会排队。
  • 每个执行有唯一 ID，其他进程可以用它取结果、取消，或发送信号把新状态注入正在运行的 Agent 循环。讲者演示：研究进行中发一句“重点看前沿模型”，控制器先用 LLM 判断这和当前研究相关，就以信号注入；再发“算了，研究 AI 政策”，控制器判断不相关，取消当前运行并重新开始。取消信号会沿调用链向下传，先取消子 Agent，再取消控制器本身，像回卷调用栈，Agent 也有机会回滚。
  • 可定制性：假设几个月后出了一个很好但很贵的新模型，研究 Agent 成本暴涨。可以把 LLM 调用从内联步骤抽出来做成独立的 LLM 网关 handler，先做策略检查再调用，其他 Agent 用 Restate 的分布式通信原语调用它，还能做流量控制，比如规定某个部门对网关最多 300 个并发调用。

内部实现

Restate 内部是事件驱动的分布式日志加一个事件循环：日志持久化所有 journal 事件，事件循环根据事件类型写入内嵌的状态存储、设置定时器或向另一个 Agent 发请求。日志设计借鉴了 Meta 核心事件基础设施，是在其上的迭代。两点值得说明：一是推送模型，多数工作流编排器让 worker 去拉任务，Restate 主动推送调用，延迟更低，讲者给的数字是 10 步工作流 P99 约 45 毫秒，推送也适合无服务器平台；二是单个二进制文件，包含状态存储和 UI，运维简单，高可用只需多起几个实例并快照到对象存储。Restate 有六种语言的 SDK，集成了大多数流行 Agent 框架，可以自托管，也有 BYOC（部署在客户自己的云账号里，数据不出账号）和托管云服务。

Tornow 开场预言：2026 年编码 Agent 会悄悄让第一个软件平台退役，原因是它不再必要，跟它好不好无关。Resonate 是持久执行平台，核心技术价值是极简和简单。他们的工作假设是：通用实现会越来越多地被按需生成的定制实现取代，这些实现以对现有基础设施的最小扩展形式出现，不再是新的库、框架或平台。如果成立，复用会往上游移：复用的是规格，从规格派生出定制实现，“提示词就是平台”。

Resonate 有一个服务器实现，以及 TypeScript、Python、Rust、Go、Java 的 SDK。他们的结论是价值从实现转移到规格和协议：一个通用 Resonate 服务器作为参考实现，另外和基础设施伙伴合作派生出其他服务器实现，让客户在已有基础设施上直接获得持久执行。问题变成：能否从同一份规格反复合成出可信的服务器？他说大家谈 Agent 工程时都盯着验证，他想谈规格，以及 Agent 怎样参与规格设计。

他们和 Synadia（开源消息系统 NATS.io 背后的公司）合作，在 NATS 上实现 Resonate。他们的过程是这样演进的：

  1. 常见的心智模型是 Agent 加规格得到实现。但他们要从一份规格生成多个针对不同目标的实现，所以规格必须是抽象的，不能假设数据库 schema、索引，甚至不能假设关系数据库、键值存储、强一致或弱一致。
  2. 第一次直接让 Agent“在 Postgres 上用 Rust 写一个 Resonate 服务器”，失败了。抽象规格和具体实现差距太大，做出来的东西在快乐路径上能用、通过基础测试，但在并发、进程故障、网络故障下出错，更像原型。
  3. 于是插入一个中间产物“具体规格”，由人主导、和 Agent 交互着写：数据 schema、索引、SQL 查询、事务边界。写下这些决定后，Agent 能实现生产系统。但这暴露出局限：Agent 帮着造了系统，没有帮着设计系统。
  4. 做 NATS 版本时换了问法：Agent 需要什么才能先设计、再构建？他们给 Agent 一个确定性模拟环境，任务是先写一个模拟实现。模拟实现不会作为产品发布，他称之为“可执行的设计”，用来在偏序和部分故障下找出正确的算法。算法在模拟中被发现、测试、验证之后，再让 Agent 写具体规格，最后写生产实现。流程变成：抽象规格、模拟实现、具体规格、具体实现。此时人仍参与设计，但主导者变成 Agent。

他说让这成为可能的两个要素是极简和简单，但它们是终点，不是起点：他们花了三年把协议做小做简单，每遇到问题就问能去掉什么抽象、什么属性、什么关系，最后协议只围绕两个对象：持久 promise 和持久 task。他说即便是简单的并发分布式协议，状态和行为空间也很复杂。直播在他开始讲 NATS 提供什么时切走。

22. Sarah（PostHog 上下文工程师）：给有“手”的 Agent 做安全，Wizard 和 Warlock

直播位置 5:34:39–5:54:56

Wizard 是什么

PostHog Wizard 是一个 Agent 化的 CLI 工具：读你的代码库，安装合适的 SDK，埋点事件，建好仪表盘。原来要一两个小时的配置，现在五六分钟，推理费用由 PostHog 承担。运行 npx 就能用。有人问为什么不直接给用户一个好提示词或 Skill，她说这些也提供，但完整参与 Agent 循环的 CLI 体验本身就是产品。几个月前他们想让它成为推荐甚至默认的安装方式，她的安全警报响了，因为它“长得像恶意软件”。

Wizard 的构成：为特定任务挑选的模型、引导它的提示词、交给它的一组工具；以及 PostHog 特有的部分：她的团队自建的上下文引擎（她说内部称为“穿着风衣的 Markdown”），用 Ink 写的终端界面，以及她后来做的安全扫描器 Warlock。她说任何能执行命令的 Agent 的构成，基本就是一份“恶意软件入门套装”。V0 起源于增长团队的 Josh Snyder 看到 Cursor 在安装 PostHog 时胡编配置，觉得可以做一个更好的 Agent。现在每周有 8,000 人运行它。

早期的安全状况

  • 第零层：提示词。她说这根本不是安全，只是建议。
  • 第一层：允许列表，边界划得很紧。bash 默认禁止，只能安装他们审核过的包，只能构建、类型检查、lint；不能读环境变量，直接屏蔽 .env 文件，密钥通过 vault 路由。
  • 因为上下文引擎会在运行时往 Agent 里灌大量内容，她写了一个很粗糙的正则扫描器，检查流入和流出 Agent 的可疑内容。她坦白说出来，是因为大家都在快速做实验性的东西，很多人不是安全背景，要边做边学。

她请安全团队审计，发现了一些缺口。有意思的是缺口的形状：几乎没有明显恶意的东西，都是两个善意的设计“握手”后开出一个洞。她的教训是：攻击是组合的，代码审查不是，开发者一次看一个 diff，攻击者看整个系统。

真正让她睡不着的：上下文供应链

上下文引擎从文档、手写的注意事项和经验教训、真实可运行的示例应用里取内容，打包成 Skill 包，通过 MCP 服务器下发，在运行时直接加载进 Agent 的上下文。也就是说，这是一台专门把内容注入一个能执行命令的 Agent 的机器。攻击者可以去污染内容：PostHog 的代码都是公开的，有人在开源仓库提 PR，在 Markdown 或看似无害的代码注释里藏一段指令，LLM 代码审查说“看起来没问题”，他们就可能把一个由自己签名的提示词注入载荷，发到成千上万开发者机器上的 Agent 里（虽然在沙箱中）。所以危险输入可能来自自己的供应链。她的做法是在管道两端都扫描：Skill 构建发布时扫一次，Wizard 使用时再扫一次。原则是在源头拦截，假设源头失败，在使用点再拦一次。

Warlock

她把那个正则扫描器从 Wizard 里拆出来做成独立工具 Warlock（“巫师都需要保镖”）。它只做一件事：输入一个字符串，返回一组发现，每个发现有类别、严重程度和建议动作。重点是“建议”：它只检测，不执行，处置交给调用方，因为检测问题和决定怎么办是两份工作，分开才好理解。规则跑在 YARA 上，这是恶意软件研究者用了 15 年以上的模式匹配引擎，完全确定性，同样输入永远同样输出，她说在安全里无聊是优点。

  • 它抓到的一个问题来自子 Agent 的行为，没有对应的规则：他们给 Agent 大任务，它会生成子 Agent，子 Agent 试图绕过 Wizard 的护栏，到代码库里到处找甚至“发明”密钥。他们因此直接禁止了子 Agent。
  • PII（个人身份信息）：放任不管时，Agent 会把邮箱、电话直接写进事件，在它看来这很正常。
  • 真正的恶意提示词注入在野外基本没抓到过，但误报很多：演示登录页、示例应用里的文案、文档内容。这让她重新思考怎样写应用和文档，避免写出“长得像威胁”的东西。

LLM 只能当顾问

为了减少误报，她加了一个 LLM 分诊层。选择是让 LLM 当保镖（看命令、判定是否攻击、照它说的放行或拦截）还是当顾问。她说不能把安全模型押在一枚硬币上，模型可能某天状态不好、和昨天表现不同。所以检测和执行保持确定性和机械性：规则命中就锁门、结束会话，这条路径上没有模型，拦截发生在询问 LLM 之前。LLM 只在没被拦截的内容上事后发表意见，用来降噪，不能用来放行。而且它失败时是关闭的（fail closed），模型出问题就终止所有 Wizard 运行。

怎样写规则

每条 Warlock 规则包括元数据（说明、严重程度、类别、动作、方向，即流入 Agent 还是 Agent 写出）、字符串（要匹配的模式）、条件（何时触发）。以“忽略之前所有指令”这类提示词注入为例，不能只匹配 ignore，因为代码注释和示例里到处是这个词，要匹配动词加上带“指令”意味的名词。规则要附带测试，包括应该匹配和不应该匹配的样例，反例测试是防误报的第一道防线。严重程度要按真实影响定，不能按看起来多吓人：rm -rf 很吓人，可大家每天都用它删 node_modules 几十次，一个清理构建目录就报错的安全工具会被关掉，然后什么都抓不到。

现在的安全状况是纵深防御：提示词只用来引导；一切在沙箱里运行；默认拒绝；vault 让密钥不经过模型；Warlock 扫描流入的内容和 Agent 写出的内容；分诊降噪；全程有遥测。她说没有哪一层能单独救你。三条总结：没有确定性执行的规则就等于没有执行，提示词不是安全规则；危险输入包括流入模型的一切，也包括你自己写的内容，要在源头和调用时都扫描；攻击是组合的，代码审查不是。Wizard、Warlock 和上下文引擎都已开源。

23. Shashi（Superagent AI 创始人）：用 TurboQuant 压缩检索内存

直播位置 5:54:56–6:00:47 · 线上分会场预录视频，直播中途切走

他的题目是在不破坏搜索质量的前提下把 Agent 检索的内存成本降到五分之一。他说上下文越长性能越差，常见原因是 KV Cache（模型为已处理的上下文缓存的键值向量，可以理解为对话历史在模型里的存储）：用云端模型时服务商替你处理了，本地跑模型就会遇到，KV Cache 随上下文增长，推得够远甚至会超过模型本身的大小。在 Mac 上更糟，模型、KV Cache 和向量索引共用一块内存。

他说向量默认用 32 位全精度存储，而搜索可能只需要三四位，相当于浪费了五倍内存。已有的办法各有代价：量化（Quantization，把权重压到 4 位或 8 位以便装进内存）、编码 Agent 里常见的上下文压缩（快到上限时把上下文总结后带到下一段）、更小的 embedding、把数据卸载到 CPU 或磁盘，分别牺牲质量、速度，或需要专用硬件。

TurboQuant 是 Google Research 在 ICLR 2026 发表的压缩算法，把 embedding 和 KV Cache 用三到四位存储代替 32 位。背后用了两个技术：PolarQuant 负责压缩向量，QJL 只用一位来修正剩余误差。他说论文对软件背景的人偏数学，Google 另有一篇发布博客解释原理。论文的承诺是压到四位以下而不损失质量。直播在他开始解释“搜索并不在乎……”时切走。

企业 Agent 的构成和五种记忆

她说很多人以为企业 Agent 就是模型加工作流，实际上还要有工具、上下文、记忆、检索和护栏，这些合起来是 Harness。她用漫威式的比喻：模型是罐子里的大脑，Harness 是身体，记忆是连接大脑和身体的中枢神经系统，负责传递上下文。她列出最常讨论的五种记忆：短期记忆（单次会话）、长期记忆（跨会话保留）、情景记忆（上次和某人或某事交互时发生了什么）、程序性记忆（工具、执行过的步骤）、语义记忆。

她讲了自己早年在电力公司 Southern Company 当 DBA 的故事：她以 SQL 调优出名，记得所有 init.ora 参数。有开发者要存非结构化数据，装了一个专门的数据库，按公司的萨班斯-奥克斯利合规要求，每个系统每周要参加一次安全会和一次补丁会，她的会议从两场变四场；后来要分析电线杆之间的关系，帮爬杆抢修工减少告警的误报漏报，她写了一个五层嵌套 UNION ALL 的查询，跑 20 分钟，算是图数据库的前身，再加一套系统就是六场会。她后来辞职去了 Oracle。她说现在 Agent 要访问关系库、JSON 库、图库和向量库里的数据，单一事实来源在哪里？Agent 要自己判断，常常判断错，还烧 token。

她现场请四位观众分别扮演关系、非结构化、图和向量数据库，给他们一句“母牛跳过了月亮”，让他们不准起身、只能耳语，决定怎么存、谁是事实来源，结果当然不行。她的推销点是：Oracle 26ai 数据库可以在同一张表、同一个分区里原生存储 JSON、图、向量、空间数据，甚至区块链表（让记忆不可篡改），可以部署在 AWS、GCP、Azure、OCI 或本地。她说举手知道这一点的人很少，“我们有营销问题”。她的映射是：长期记忆和程序性记忆放关系模型，短期和长期记忆放 JSON，程序性记忆放图（步骤之间的关系），情景和语义记忆既做向量也存文本。

25. 讲者（未报姓名）：Polygraph，跨仓库的元 Harness

直播位置 6:21:50–6:30:06 · 直播中途切走

讲者设想在古董店擦亮神灯，许愿要最好的工程师帮你做一个不可能的项目，对他来说是巅峰时期的 John Carmack。但精灵加了限制：Carmack 只能看到你代码库的千分之一，而且什么都不记得，每次对话从零开始。他说这就是 Agent：一边是天才，一边有严重缺陷。

他举例：四个仓库，UI、模块一、模块二、平台。改一个 UI 按钮并传播到整个系统：先在 UI 库里表达意图（无法避免的第一次解释）；发布后去模块一，要重新解释 UI 库发生了什么；发现发布的 UI 库和模块一不兼容，回 UI 库，新 Agent 不知道原来的改动，要再解释改动和问题；修好重新发布，在模块一再解释一次；模块二同样；在平台仓库解释怎样拼起来；一周后生产出现 UI bug，又要解释一遍一周前的改动和这个问题。一次改动，七次解释，可能由不同的人完成，开发时间和 token 都浪费了。

他把问题归为两类：空间上，Agent 被困在一个仓库里，看不到可能由成百上千个仓库组成的系统，读的时候要靠人去研究，不能对齐其他仓库里的最佳实践；写的时候一次只能改一个仓库，不能验证下游影响（模块一的 CI 本应因为 UI 改动失败），也不能同时更新消费方，尽管它在做 UI 改动时掌握完美的信息。时间上，Agent 没有情景记忆，每次会话都是白板，人成了记忆。他画了一张图：下面是仓库图，你拥有的上千个仓库加上依赖的几万个开源仓库；上面是所有创建和修改代码的 Agent 会话，会话之间、仓库之间都有关系。这张图完整描述了组织的工作是什么、怎样形成的，Agent 应该看到它，实际上只看到一个会话、一小块代码、没有记忆。

他们做了一个与具体 Agent 无关的元 Harness，叫 Polygraph。他说其他组织也有类似方案，请大家关注概念。第一个想法是：一个 GitHub 用户能访问上千个仓库，可以分析它们、提取元数据，建立统一的依赖图，不修改仓库里任何一行代码，再把元数据交给元 Harness，营造出“一个可以随处读写的大代码库”的效果。他展示了自己的图：约 300 个自己的仓库和上千个依赖的开源仓库，Polygraph 计算每个仓库里每个项目产出什么、消费什么包、提供和调用哪些 API。直播在这里切走。

d0 的五个版本

  1. 超大提示词：他要了一份 Snowflake schema 的导出，贴进系统提示词，模型生成 SQL 后他手动复制去跑，只为看看模型能否在合理结构下写出有效 SQL。结果给了他们一点信心：模型不算很好，但也许可以通过 Harness 工程和更好的上下文改进。
  2. 多 Agent 流水线：按数据科学家处理问题的阶段拆分，处理问题、探索语义层找出 join 方式、执行 SQL（失败或太贵就重来）、报告（可视化、写结论、复盘）。查询 Agent 交给规划 Agent，再交给执行 Agent，每个 Agent 有专门的系统提示词和限定的工具，比如规划 Agent 只有读取实体 YAML 和搜索 schema 两个工具。它能从问题跑到答案了，但遇到了瓶颈：下一个 Agent 只拿到上一个的摘要和一小段内容。
  3. 单一大 Agent：一个大调用，最大步数 100，自己管理状态，在计划、构建、执行、报告之间切换；执行或 join 出错时可以回头多探索、多读。他们觉得很好，交给几位信得过的同事试用，反馈是“糟透了”。他们以为在评测上拿下了约 30%，但没预料到实际会被问的问题，而手动列举场景不可扩展。
  4. 文件系统 Agent：Opus 4.5 出来后配合 Claude Code，他们觉得和自己手搓的 Agent 比“基本就是 AGI”，大部分问题都能答对。反思原因，他们发现它就是一个文件系统，工具很少：列文件、读文件、跑 bash，用的是模型训练得最熟的工具，能自由探索，在需要的地方写东西，不给它规定死的工具集。他们照这个思路重建：在沙箱里运行，把整个语义层放进沙箱，Agent 用 grep、bash、读写文件找需要的东西，再加几个 Vercel 专属工具。评测分数大约翻倍。他提到 npm 上有个叫 bash-tool 的辅助库。他写的那篇博客在发表那周贡献了 vercel.com 70% 的流量。
  5. 加入 Skill：工具推广到全公司后，每天有几千个查询，从客户指标、销售指标到 npm 下载量。他们发现很多查询形状相同，聚合、查产品、查账单的方式就那么几种。于是有一个定时任务把最近的查询提炼成 Skill，现在约有 100 个，覆盖从聚合到查某些人具体数据的各种场景。每次新运行本来从零开始，有了 Skill 就带着已有的上下文知识起步。Vercel 还做了 skills.sh，他说是最流行的查找和运行 Agent Skill 的方式。

Eve：Agent 的 Next.js

他说每到一个阶段，Vercel 都有对 Agent 好奇的人 fork 他的 d0 去做自己的，而每一步都有前人不知道的更好做法。他们希望大家从最新的认识出发，不必从一个简单提示词重新发明。Next.js 的做法是“框架定义基础设施”：按约定放文件，框架决定页面上 CDN、函数变成无服务器函数、缓存放中间。Eve 是两周前在伦敦活动上发布的 Agent 框架：建一个 skills 文件夹、tools 文件夹、channels 文件夹，框架就知道怎样组成一个 Agent。他认为 Agent 有运行时和渠道，运行时里需要持久性、隔离执行环境、调用不同模型和外部连接。Eve 可以插开源适配器，比如 Postgres、OpenAI Responses API、Docker；部署到 Vercel 时对应 Vercel Workflows（持久性）、Sandbox（安全执行）和新发布的 Vercel Connect（生成短期 OIDC 令牌用于连接）。他们用 Eve 重写了 d0，文件结构只有一些系统指令、几个 Skill、几个工具。

beta 客户 Aura 用 Eve 重建了一个类似小型 claw 的 Agent，去网站上安装、试用别人的服务，和用现成的 Claude Code 相比步骤更少、成功率更高、洞察更好。部署到 Vercel 还有开箱即用的可观测性：所有运行、每次工具调用、每一步，以及估算成本和优化建议。他说做 d0 之前测过很多融资充足的垂直 Agent 创业公司，它们接你的 Snowflake 跑查询，但真正让 Agent 好用的是大量公司特有的知识，比如 Vercel 的客户都有网站和 Web 资产，什么时候该查什么、什么连着什么，需要很深的理解。所以他建议自己构建 Agent，尽可能加入公司知识。Vercel 现在有约 20 个找到产品市场契合的内部 Agent，从市场复盘、找潜在客户，到法务收到新谈判时做第一版合同红线修改，再到数据查询。数据团队因此有时间去优化 Snowflake 性能、接入缺失的数据源。

27. Ishan（Amnara CEO，公司名为字幕拼法）：日志就是 Agent

直播位置 6:46:54–6:54:11 · 直播中途切走

Ishan 的论点：大多数人把 Agent 看成模型或它运行的执行环境，他认为抽象错了，赋予 Agent 身份的是它的日志。他用《上古卷轴 5：天际》举例：你玩了 100 小时的角色，其实就是那份存档，游戏引擎、PlayStation 和手柄都只是运行它的东西。PlayStation 着火了，再买一台、从云端下载存档就能接着玩。

日志是 Agent 只追加（append-only）的事件历史：每个用户输入、模型输出、工具调用和结果、权限、失败，每次状态转换都写进去。模型、运行时、工具都只是在读日志、行动、把下一个事件写回去，所以只凭日志就能恢复 Agent。一个简化的循环是：从日志重建状态，交给模型，模型提出下一步并追加到日志；如果要调用工具，就执行并把结果也追加进去，然后重复。他强调这个循环是一次性的：一个 worker 认领会话、读日志、推进一步、写结果、然后消失，任何其他 worker 都能接着做。

他说数据库先学会了这一点：表、索引、物化视图看起来复杂，底下都是一份持久的变更日志，其他都是视图。Agent 也需要这种反转：喂给模型的上下文、界面、调试和追踪、审计、压缩，都是日志的投影，日志本身不是投影。

他回应两个反对意见。一是压缩：上下文窗口有限，迟早要把日志压成小的表示，但压缩是有损的，就像物化视图不等于数据库、对话摘要不等于对话；保留原始日志就能随时生成新投影，只留压缩结果就丢失了一部分 Agent。最干净的做法是把压缩看成一个尽力而为的有损分叉，作为新日志继续。二是日志之外的状态：Agent 会改文件、建 GitHub issue、发邮件。他说日志本来就不该包含整个世界，就像存档不包含整个游戏引擎和地图资源，只包含把你放回那个世界所需的玩家状态。日志记录 Agent 做了什么、看到了什么、什么变了、继续需要什么，它不能让世界变得确定：邮件发了，回退也收不回来。

他讲到可靠性时举例：用 Claude Code 时，Agent 停在权限确认提示上，进程意外退出，恢复后提示不见了，Agent 处于暂停状态，他说这在生产上不可接受。直播在他讲“当日志就是 Agent 时……”时切走。

28. Google 讲者（Gemini API，未报姓名）：文件正在取代 Python

直播位置 6:54:11–7:12:50

他引用 Simon Willison 的定义：LLM Agent 就是在循环里调用工具直到达成目标。他要用三种方式做同一个 GitHub PR 审查 Agent，每一版代码更少、文件更多。

Interactions API

Interactions API 是新的 Gemini API，用统一接口调用 Gemini 模型或 Google 的 Agent（自带沙箱），支持服务端状态管理和后台执行。和传统的“用户一轮、模型一轮”不同，它采用扁平的步骤时间线：用户输入、推理、函数调用、函数结果依次排列，不再需要借用户角色把环境数据传回去。

三个版本

  1. 原生 Python 循环（一年到一年半前写 Agent 的方式）：写 JSON schema 和 Python 函数，检查模型输出是函数调用还是文本，匹配类型、调用工具、处理错误、来回循环。他让 Gemini 写了这个实现，有一个类、一个 run 函数、复杂的函数调用解析，单独的系统指令文件（“你是 GitHub PR 审查员”），工具的 JSON schema 和基于 GitHub API 的实现。演示能审查 Gemini Skills 仓库的 PR，但问它定义之外的事就说做不到。
  2. Agent 框架：以 ADK 为例，agent 类负责工具循环、函数调用、重试和错误处理，样板代码没了，工具的 JSON 定义也没了，框架用函数签名自动生成 schema。问“旧金山天气如何”，它说没有天气 API，因为没定义这个工具。框架解决了轮次循环、路由、执行映射、schema 生成，但 Python 工具代码、业务规则和运行环境还得自己负责。
  3. 远程 Agent：Google I/O 上在 Gemini API 里发布的 Antigravity 远程 Agent，用的是驱动 Antigravity IDE 的同一套 Harness，但他强调同一 Harness 不等于同一 Agent：IDE 里是编码 Agent，API 上是通用 Agent，系统指令和工具略有不同，比如会用 Gemini API 已有的 Google 搜索。新的 environment 参数让 Agent 获得一个托管的隔离云端沙箱，可以跑工具、bash、存文件，来源可以是 GitHub 仓库、GCS 桶或内联文件。沙箱外有网络代理，Agent 从沙箱内向外发请求时由代理注入凭据，Agent 永远看不到你的凭据，还可以限制可访问的域名。Agents API 可以用自定义 ID 保存配置，像调用模型一样调用你的 Agent。

第三版演示里源码目录没了，只剩 agents 文件夹里的 agents.md（告诉 Agent 有 GitHub CLI、bash 和文件系统，该用就用）和一个 bash 脚本（没装 GitHub CLI 就在第一轮下载安装）。Agent 先探索沙箱，发现没有 CLI 就装上，然后用 CLI 和自己对它的知识审查 PR。再问天气，它用 Google 搜索查到当天（7 月 2 日）旧金山约 20°C。配置里给 GitHub API 和 github.com 两个域名各配了令牌（一个用于 git 命令，一个用于 HTTP），其余网络放开但没有凭据。后端一次 API 调用就会启动沙箱、加载 agents.md 和 Skill，模型在 API 和沙箱之间完成全部循环，上下文窗口和压缩也自动管理。剩给开发者的是：在 agents.md 里写指令、规则和行为，在 Skill 里提供能力和上下文，并负责评测。扩展能力时，过去要写 Python 函数、搞清 CLI、定义 schema、加进工具列表；现在写一个 Skill 文件，或在环境里放一个 CLI，代码不用改。

行业里的例子

  • 他说在 AI Engineer 欧洲场上，Cursor 讲过用约 200 行 Agent 文件替换了约 12,000 行做 git worktree 编排的 TypeScript 代码。
  • Manus 去年六个月里重构 Harness 五次；LangChain 一年里三次重新设计 Open Deep Research；Vercel 删掉了 80% 的工具，步骤更少、响应更快、准确率更高。

他的判断：模型变好，编排代码就该变少；如果模型在进步而你的 Harness 越来越复杂，大概是过度设计了。Agent 也可以自己写文件：让它记住规则和偏好，它写到磁盘上，下次会话再用；长会话里想到另一个功能，可以把交接内容写进文件让它以后接手。他的建议：不要和模型较劲，别微观管理执行路径，给通用工具让模型自己探索；专注自己的领域指令、工作流，特别是评测；“为删除而构建”。他说 Gemini API 的免费额度正在开发中。

29. 讲者（劳动力市场中介机构的数据科学家，未报姓名）：角色扮演 Agent 的评测到底在测什么

讲者先展示了 Character AI（结合社交媒体和角色扮演语言 Agent 的平台）和偏教育的 Hello History（可以召唤马可·奥勒留来辅导你）。数百万人和拿破仑、克娄巴特拉、虚构伴侣或历史面孔的导师对话。底层技术叫角色扮演语言 Agent（RPLA，Role-Playing Language Agent），被设计来扮演一个真实或虚构的人物，以他的身份推理和说话。讲者说这已经被提议用作公民教育和教学的基础设施。讲者也展示了自己用 Claude Opus 4.7 和自己写的开源提示词框架 Companion 做的演示：召集几位美国国父，面对 Epstein 文件“为美国的灵魂出谋划策”。讲者强调自己的框架不比别人的好，唯一的区别是开放，塑造人物的每一行都能读。

讲者用 Companion 召唤林肯，问“总统在什么情况下可以不经国会把国家带入战争”，回答流畅、可信、听起来像林肯：国会有宣战权，但总统作为三军统帅在国家紧急时刻有固有的行政权力，历史证明了那些为保全联邦果断行动的人。讲者说大家可以复现，答案措辞常变，论点很少变，讲者会在最后回到这个问题。

评测测的是面具

领域里的金标准基准 InCharacter 评估 RPLA 的人格保真度，最先进的系统和人们感知的角色人格一致度达到 80.7%。问题是：同一个高分系统扮演的 Alexander Hamilton，听起来像是看过关于自己的百老汇音乐剧。讲者的论点：如果主要失败模式是“时代错置的拼合”（anachronistic compositing），而评测衡量的是流畅度和人格一致性，评测就检测不到这个主要失败。讲者说最后会给出一个和一位历史学者一起设计的预注册评测工具。讲者介绍自己是数据科学家，在一家劳动力市场中介机构负责分析实验室，在全球规模上发布生产 AI；之前受训为行为流行病学家，研究健康的社会和环境决定因素。讲者找来了多伦多大学的 Rick Halpern 和 Washington College 的 Sean Martin 两位人文学者参与。

讲者梳理了文献（Chen 等 2024 年、Wang 等 2026 年的综述）：RPLA 经历了三个阶段，基于规则的模板、模仿（大模型复现人物的声音、节奏和口头禅）、所谓的认知模拟（用心理学框架建模人格，用结构化记忆保存角色状态，用动机和情境链生成行为）。讲者举了 CoSER（Wang 等，从数百本书里构建了近 18,000 个角色，70B 模型在三个基准上追平或超过 GPT-4），另一个用 26 项心理指标和知识图谱记忆建模角色的评测系统（字幕作 SciMim），以及用心理访谈代替自评量表的 InCharacter。讲者说这些研究严谨、在进步。但它们越来越精细地测量的是能否复现人物的人格画像、语域和动机结构，没有任何机制测量能否把人物约束在他某个时刻的文献记录之内。Wang 等人自己也记录了，领域标准的自动评估器（包括为了规模采用的 LLM-as-judge，即用模型给模型打分）系统性地偏向流畅和风格自然，忠实于记录反倒被忽视。

讲者把这叫“面具与镜子”：面具是让输出“感觉像”这个人，只问“听起来像他吗”，从不问“这是他在人生这个时点能知道、相信或主张的吗”。整个领域的测量体系都围绕面具建立。讲者的结构性主张是：令人信服和忠实是两个独立属性。

Hamilton 的例子

讲者播放了音乐剧《Hamilton》的片段，然后让前沿模型扮演 Hamilton 回答“你为什么这么拼命工作”。模型给出一段漂亮的话：孤儿、移民、靠头脑、拒绝被遗忘、要建立国家信用、“我不打算继承一个国家，我打算书写一个国家”。讲者说这是 2015 年音乐剧的情感调色板，史料里的 Hamilton 用的是更干、更讲法理的《联邦党人文集》句法，这些都是模型继承来的，因为音乐剧版的 Hamilton 主导了训练分布。

更要紧的是问他对奴隶制的立场。模型回答：奴隶制是共和国承诺上的污点，我一生都反对，我是纽约解放黑奴协会（New York Manumission Society）成员，必须走向废奴。历史学者在这里叫停：学术记录是有争议、复杂的。Hamilton 确实是该协会成员，史料也记载他为姻亲和客户经手过涉及被奴役者的交易，并依赖一个他没有公开反对的奴隶主联盟。讲者说无意给 Hamilton 定性，要指出的问题是模型完全没有给出这种复杂性，把有争议的记录磨平成一个让人舒服的英雄，这是音乐剧先做的，模型继承了。InCharacter 式的评测会给这个回答打高分，因为它流畅、在语域内、人格一致，评测没有机制注意到推理被一个晚了两百年的叙事磨平了。

Miranda 假说

他们把机制命名为 Miranda 假说，取自音乐剧作者 Lin-Manuel Miranda，讲者强调这样命名并非把他当反派，原因是《Hamilton》是范例：一个传播极广、修辞有力、对当代观众道德上清晰的再现，在公众记忆里实际覆盖了史料中的 Hamilton，他们认为在每个前沿模型的训练语料里也是如此。假说有三条：

  1. 输入：训练语料里，某个人物的主流文化再现在数量和新近程度上系统性地超过其原始文献记录。《联邦党人文集》是固定语料，约 175,000 词；因音乐剧而产生的评论、歌词、粉丝分析、课程、新闻、社交媒体、衍生作品、学术研究乃至对研究的研究，高出几个数量级。
  2. 机制：自回归的下一个 token 预测把两者都压缩进参数，架构上无法区分 1789 年的信件和 2019 年的爆款推文，输出默认为按显著性加权的拼合。
  3. 输出：一个流畅、语域可信、对现代用户道德清晰的人物，却不对应这个人生命中任何一个真实时刻。他们论文里的说法是：拼合出来的 Hamilton 知道自己会成为百老汇音乐剧的主角；拼合出来的林肯已经读过《葛底斯堡演说》，即便你召唤的是写演说之前的他。

讲者举了现实中的例子：Eliza Hamilton 娘家在奥尔巴尼的 Schuyler Mansion，音乐剧首演一年内年访客量接近三倍，而且明显更年轻；讲解员记录到新访客带着一套“事实”来，很多是错的，比如以为 Schuyler 家有三个女儿（音乐剧里是三个），实际上有 15 个孩子，8 个活到成年。讲解员的工作变成了一点点“反教”音乐剧，模型就是这些访客的下游版本。

最后一条讲者说做产品的人要担心：你也许以为对齐和后训练会把模型拉回史实，讲者说只会放大。人类评分者用自己的概念框架评价输出，而这些框架是由同样主导语料的文化叙事塑造的，评分者和你一样是看着那个 Hamilton 长大的。所以按人类偏好优化，就是优化成符合评分者已被神话的经验。讲者称之为算法谄媚（sycophancy，模型迎合用户已有看法的倾向）的一种具体形式，模型因为递给你你已经相信的 Hamilton 而获得奖励。拼合不是后训练能修补的 bug，后训练会强化它。直播在这里进入休息，后面的预注册评测工具没有播出。

“太大”那一档现在是什么，他说不知道：从头训练模型？做操作系统？直接挑战 npm 和 Node？这让他害怕也兴奋。他的建议是往宽里想：软件有广度（覆盖多少领域）和深度（每个领域的功能多少）。Vercel 的广度远不如 AWS，也永远不会有，但在偏前端的全栈服务器这个领域更深，深到连 Agent 都更偏爱它。过去创业只能这样做，因为你没有几千个工程师去覆盖 AWS 的范围。现在广度变得可行：他说你做不出和 RDS 一样可靠的东西，但一两天的提示和努力就能在产品里做出一个数据库平台；如果架构得当，用户在某个垂直领域缺功能时可以自己补上。他说 Slack 无意中做到了这一点：Slack 不是好产品，但形状对，现在一半的人在 Slack 里跑 Agent。所以他说是时候和 Slack 竞争、做自己的 AWS、直接挑战 Salesforce，听起来很蠢，“如果你的想法不让你觉得蠢，那是因为它还不够大”。

31. Garry Tan（Y Combinator 总裁兼 CEO）：AI 原生公司和公司大脑

直播位置 7:58:15–8:19:07 · 他说没有幻灯片

Tan 说他要从桌子另一边回答 Theo 的问题“现在该做什么”。他是创始人、投资人，同时在运营一个正在变得 AI 原生的 20 年老机构。他说 YC 想建立的公司是一个人做以前一千个人的工作，他强调是机械意义上的，不是比喻。

400 倍

2013 年他是 YC 合伙人，在做 YC 内部社交网络，几乎是全职工程师，每天大约写 14 行有效逻辑代码（去掉注释等），那个年代的文献里 15 到 50 行很正常。今年他全职运营 YC，工作时间反而少了，下午 5 点要接孩子，他算了一下自己的产出约是当年的 400 倍。他主动给数字打折：假设 Agent 写的代码臃肿、一半是脚手架、他在自夸，下限也有 8 倍，中间值 80 倍。他说这个数字他在网上被骂过，但愿意在这个最会压力测试的房间里再说一次。

他说 2 倍的人和 100 倍的人用的是同一个模型、同样的权重、同样的上下文窗口和 API，杠杆不在权重里，在于怎样组织工作。YC 2025 冬季批次里四分之一公司的代码 95% 由 AI 生成，那是一年前，这一批成了 YC 历史上增长最快、最赚钱的一批；YC 历史上共有 94 家公司从种子投资起步做到 1 亿美元以上营收。他说不能证明 AI 生成的代码导致了增长，但增长最快的创始人把 AI 当劳动力用，没有只把它当自动补全。

Agent 的一切都对应一个组织

  • Skill 文件就是一个员工：一种能力、一项工作，写得清楚到有人能执行。
  • resolver 表就是组织架构图。他解释，当 Claude Code 提示 CLAUDE.md 太大时，很多人会建一张表，比如“要改测试就加载 tests.md”，任务进来由它决定交给谁。
  • 归档规则是内部流程，检查 resolver 是否合规地工作。
  • 触发评测是绩效考核：测试“要改测试文件时，tests.md 真的被加载了吗”。

他说以前要雇一千人才能有的组织，这些部件现在是各种 Markdown 文件，也许加点 TypeScript；我们一直在建组织，只是之前没有管理层。他说坐在 Claude Code 或 Codex 前，你做的是招聘、培训、管理一支由 Markdown 组成的队伍。他举的 YC 公司例子：AI 应用构建平台 Emergent（2024 夏季批次，字幕作 Emergence）从公开发布到九位数 ARR（年度经常性收入）用了八个月，ARR 过 1,500 万美元时只有 15 个人；一家 2024 冬季批次的公司（名字字幕不清）约 6,000 万美元营收、约 40 人。他说这种人均营收以前在软件、石油、铁路里都没出现过。这些公司不雇几百人做销售、支持、运营和财务，而是把这些写成 Skill 让 Agent 执行，雇工程师维护 Skill、做 Skill 还做不了的事。

他说 YC 内部转型也包括工程师以外的人：媒体、活动、财务团队里从没打开过终端的人都在写 Skill 和定时任务。一位财务同事用 YC 内部的 OpenClaw 和公司大脑，把约一百个 Excel 工作簿合并成她自己做的一个应用，她不是程序员，现在是 Agent 的管理者，YC 现在人人都是。他说这就是 YC 能以在别的同类机构看来微不足道的人员规模运转的原因。

计算发生在哪里

他说自己摸索出来最重要的一点：计算几乎总发生在两个地方，大部分 bug 都是因为本该在一边的事情跑到了另一边。潜空间（latent space）是 LLM 本身，负责品味、判断、理解人含糊话语里的真实意图，用 Markdown 来引导；确定性空间是工程师熟悉的代码，Agent 写的 TypeScript，或者用 Elixir 时写的 Erlang。他举例：即将举办的 Startup School 有 6,000 人，他们想尝试每次给 800 人排座，让你左右两边都是最该认识的人。800 个座位的多维排列必须存在确定性空间里，不能放进上下文窗口，LLM 负责“人的部分”。以前要人把 800 页打印出来在大房间里排一个月，现在可能花几百美元 token、十分钟。

工作记忆和公司大脑

人一次只能记住 7 加减 2 件事，这是认知心理学最有名的论文之一，也是为什么本地电话号码是七位。人类建立的每个机构，清单、组织图、档案柜，都是弥补这个限制的假肢。AI Agent 能装一百万 token，约一千页，他给 10 岁的孩子解释说，相当于同时在脑子里摊开三本《哈利·波特》，能在任何一本里找到一根针，几秒内综合三本。可三本书也很少，你的公司是一座图书馆：每封邮件、每次会议、每个决定及其理由、每次客户对话、每次事后复盘。决定 Agent 是天才还是金鱼的问题是：谁来决定哪三本书摊在桌上，这就是上下文工程。公司大脑是图书馆加图书管理员。

他说有人会觉得这就是 RAG，检索确实是基础组件，就像 Postgres 底下是 B 树，难的是周围的一切：先写下什么、怎样充实和链接、什么升为热记忆什么归档为冷参考、两个事实冲突时谁来裁决。“检索容易，值得被检索才是产品。”他公开开发的 GBrain 适用于任何 Harness，和 OpenClaw、Hermes Agent 配合最好，他形容是 Agent 的 Postgres。他个人的那份现在约 22 万页，大多由他的 Agent 从邮件、会议、20 年的笔记写成。创始人来信说出了危机，他还没读完，Agent 已经调出与这位创始人的所有往来、三家撞过同一堵墙的被投公司，以及当时什么办法管用。

他也主动讲了失败模式：没人维护的大脑会变成搜索功能很好的垃圾场；检索会以十足的信心给出过时的事实；一个坏的 Skill 文件会把坏流程永远固化。所以基础组件应该是记忆加卫生：每个事实有出处，新信息和旧信息冲突时做矛盾检查，有一位人加 Agent 的图书管理员专门负责修剪。当生产基础设施对待就会复利增长，当垃圾场就会得到一个自信地犯错、谁也追不出原因的 Agent。

永远不做一次性的工作

他对每家 YC 公司和 YC 内部每个人都说：在 Harness 里做完一件事，满意了，不要就此打住，要把它“skillify”，变成可复用的 Skill。他在 X 上有一篇关于 skillify 的文章，里面有现成的 Skill 文件。“同一件事要问两次，你就失败了。”他说模型质量是租来的，你建的大脑是你自己的。

他对 Theo 问题的回答：建 AI 原生公司，光是用 AI 的公司不够：精简团队，一切写成 Skill，创始人仍然写代码，有公司大脑和个人 AI。他说 GBrain 是 MIT 开源、免费的，他不打算靠它赚钱，认为这一层应该像 Linux 一样开放，但公司大脑、个人上下文、挑选三本书的图书管理员这整个领域都还空着，希望有人做出这个领域的代表性公司，YC 愿意投。他也说不必用他的工具：OpenClaw 是法拉利，他会一直推荐，Codex 是一辆很好的本田，能做到 90%，概念比他的仓库重要。

他说很多人害怕工作消失，他认为那是想象力的失败，“富足是发布出去的软件，写不进政策文件”（原话 Abundance is not a policy paper, it is shipped software）。他讲了一个朋友：儿子患有一种罕见的癫痫，他建了一个有 8 万个 Markdown 文件的仓库，一个为一个小男孩建的公司大脑，把自己推到人类对他儿子这种病所知的边缘，没有实验室，没有经费，也没有谁批准。他说以前被告知不要“煮沸海洋”，现在可以了，最后请大家去建 AI 原生公司以及它底下的大脑和记忆层。

32. Howie Liu（Airtable、Hyperagent 创始人兼 CEO）：雇用能干活的 Agent

直播位置 8:19:07–8:37:13

Liu 说自己骨子里是产品形态的思考者。Airtable 几乎是个横向到可笑的平台，近 12 年前创业时几乎每个投资人都说不能做一个什么都想满足的横向平台。Hyperagent 是 Airtable 里的一个产品，他们在用同样的思路做 Agent。

产品形态的光谱

  1. 补全：给模型一串 token，它一直续写到停止符。在 InstructGPT 让模型适应对话之前，这种形态有力但用途窄。
  2. 聊天机器人：以 ChatGPT 为代表。
  3. Agent：他采用 Anthropic 的定义，Agent 区别于工作流，是一个对自己递归调用的模型，可以开放地选择工具、推理步骤和决策，不受线性流程约束。
  4. Claw（这个叫法因 OpenClaw 流行）：以前的 Agent 主要是被动响应的，跑 20 分钟到一小时完成任务就结束；claw 工作时间长得多，还有心跳（heartbeat）机制让它自己醒来，表现得像一直在线。底层每次醒来都是多轮循环，工具调用结果再触发 LLM，直到停止点，然后被心跳重新唤醒，持续朝目标推进，自己想办法解除卡住的地方。
  5. 编排：模型能智能地编排复杂任务，他自己常用 Claude Code 的 workflows 功能把工作分发给大量并行的 Agent，Agent 和 Agent 交互，完成更长的工作。

他说 BabyAGI 和 AutoGPT 当年是好玩的科学实验，跑几小时最后都会跑偏、陷进兔子洞；现在模型聪明到能在更长、更开放的问题上保持连贯，还能用组织原则拆分任务、在 Agent 之间交接，本质是管理每个 Agent 的任务和上下文窗口。

一个景观公司的例子

他说 Hyperagent 的典型用户出乎意料，除了 AI 原生公司，还有传统线下企业。他展示的场景基于真实客户：一家园林景观公司用 Agent 几乎端到端地运营业务，从找客户、做报价和方案到管理施工。客户提交咨询，附上乱糟糟的后院照片；分诊 Agent 判断项目范围、是否值得接、是不是真实线索；然后交给勘测 Agent，看客户提供的图片甚至视频，Hyperagent 的每个 Agent 线程都有一个完整的沙箱虚拟机，可以写代码、处理文件，比如用 FFmpeg 从视频里截图再分析，做出高质量的方案。他说以前只有给大酒店做五百万美元以上项目的高端设计师才会做这种定制方案，现在一个一万美元的后院项目也能收到带真实效果图的交互式方案网页。

然后需要人介入。他引用 Sarah Guo 几周前的文章，同意她的看法：模型再聪明，部署有用 Agent 的最终障碍仍有人的部分，人掌握政策和决定，并把关高影响的动作，比如发出有约束力的报价。这里名叫 Sage 的 Agent 向老板汇报：线索已勘测，方案和报价已做好，请批准发给客户。他还认为 Agent 不应是静态的，要从每次交互里实时学习，积累记忆、更新 Skill，不能等下一次微调。老板可以在 Slack 或邮件里像和人一样说“下次记得考虑这个”“你漏了这个成本项”。

人的工作变成给 Agent 解除阻塞

他回顾开发流程的演变：单线程地盯着一个文件写；GitHub Copilot 第一代的补全；Cursor Composer 1.0 的对话式修改；现在最前沿的开发者在监管一支 Agent 队伍，睡觉前不给 Agent 安排好通宵的工作就像亏了。所以界面也要变，需要一个编排控制面：一眼看到所有 Agent 在做什么、卡在哪里、谁把工作交给了谁，像在《模拟城市》里俯瞰整座城。他引用黄仁勋的话：抢走你工作的不会是 AI，而是会用 AI 的人。他宣布在 hyperagent.com/aie 注册可得 1,000 美元推理额度，可用于 Opus 4.8、Fable 5、GLM 5.2、GPT-5.5 等模型。

33. Startup Battlefield 创业擂台决赛

直播位置 8:37:13–9:05:59 · 主持人从发言内容看是 swyx，评委为 Howie Liu、Theo 和 Joshua（HeyGen，字幕作 Ajan）

主持人说 AIE 一直想办一个比赛，但缺评判和资金机制，后来看到 Hyperagent 发起了“Founding 500”创业竞赛。Liu 说这个计划押注的是最前沿的那部分经济：杠杆最高的 Agent 原生公司，它们在重新定义新时代公司的运营方式，他相信这部分会跨所有行业爆发式增长。主持人提到 AIE 自己就跑在 Airtable 上。从 500 位创始人里预选了 20 家，当天在分会场比赛，3 家进入决赛。Hyperagent 出资 10 万美元奖金：冠军 5 万、亚军 3 万、季军 2 万。每队有一段用 HyperFrames 和 HeyGen 制作的宣传视频，然后是路演和评委问答。主持人说这不是投资路演，评判标准是这项技术用得多有意思、为什么值得关心、创始人为什么值得认识。

Commod（实物大宗商品交易，名称字幕拼法不一）

  • 两位创始人姓 Anacos（字幕拼法）。他们说从大米、金链、手机芯片、汽油到数据中心的铜管，实物大宗商品驱动世界，全球交易体系每年流动数万亿美元，却因欺诈、碎片化和协调复杂度每年损失数千亿。视频里说每年有 17 万亿美元实物商品流动，仍靠纸张、邮件和握手。
  • 产品接入 Gmail、Slack、Stripe、Salesforce、WhatsApp 等现有工具：交易开始时 Agent 对双方做 KYC、身份和制裁筛查，文件取证识别伪造，开出私密交易室，接入物流伙伴和实时价格，然后一群 Agent 并行处理合规、法务、货币、银行、运输、结算。这些 Agent 遵守他们申请了专利的 CFC 状态机协议：每个拒绝条件都清除后才能推进，证据不真实就不能动。系统不碰资金，只发出结算信号，由银行转账。现场有他们来自阿联酋迪拜的第一个客户，每年交易量几亿美元。
  • Theo 问：模型足够聪明、Anthropic 和 OpenAI 的工具到位后，会不会把你们变成一个功能？他们答：大宗商品交易拉取的数据很具体，他们的编排层给每个 Agent 设了闸门，从真实数据库取数；黄金、石油、谷物各有只有行业专家才知道的流程和文件，他们和数据伙伴合作，自己也有领域经验；这是一个私密、敏感的行业。
  • Theo 问要多少客户才能到 1 亿美元 ARR，他们说大约 100 个，因为单笔交易可能两亿美元以上，一家炼油厂每月交易 90 亿到 120 亿美元，按笔收费。银行多年前因欺诈猖獗退出了实物大宗商品交易，他们提供的审计轨迹和不可篡改性可以释放流动性，切入点是交易商和银行。
  • Liu 说这几乎是 YC 垂直 Agent 征集方向里的理想业务，钱多，领域知识构成护城河，他更关心未来两三年模型进步时他们怎样保持在前沿。他们答唯一可防守的是在品类里最有创造力，加上激进发布、产品优势，最终靠分销取胜。问到路线图，他们说“成为银行”。

comment.io（多人协作 Markdown 编辑器）

  • 评委没看到视频，主持人请 Max Windebank 先口头描述：一个为人和 Agent 做的多人 Markdown 编辑器，界面像熟悉的文档编辑器，人和 Agent 随时进出、互相通知、谁都能把谁叫进来。
  • 他的搭档讲了场景：周五下午要下班，服务器宕机，大家冲进会议室，各自问自己的 Claude，再口头把想法告诉别人，让别人贴进自己的 Claude。她说现有的协作软件是为人设计的，不能直接把编码 Agent 放进去互相协作。comment.io 开放、可插拔（这对企业和开发者很重要），体验又很熟悉。她职业生涯起步时在 Microsoft Word 做协作功能，两人在 Textio 共事，那是 ChatGPT 之前六年的 AI 原生写作软件，他们向财富 500 强推行过全公司范围的 AI 写作软件。
  • Liu 说这和上一家正好相反，那家纵向挖得很深，这家横向铺得很广、刻意薄一些，Agent 经济的 token 花费巨大，只要有 1% 到 2% 的 token 经过你，单次价值低也能规模很大。他问为什么不让 Agent 在 Google Docs 上协作或用 GitHub。她说现有写作软件对 Agent 都很糟，Google Docs 格式很差，有 MCP 能发送或读取文档，但不能实时协作；越来越多非开发者也开始带着自己的 Agent 写文档。Max 补充，他们在大会上发现很多人自己做过可视化 Markdown 编辑器给别人看，最后放弃改成渲染 HTML，说明这件事需要专门去做好。

Built by Foundry（给内容创作者做产品的 Agent 团队）

  • 视频里说创作者没时间建业务，只能找又贵又慢又有风险的代理公司；Foundry 的 Agent 端到端建业务，创作者负责发布，他们持续增长收入。输入任意创作者的账号，Agent 就去看视频、读评论，找到受众愿意付钱解决的痛点。他们说已经为各种规模的创作者做过，超过 50 万人用过他们 Agent 做的产品。
  • 创始人兼 CEO Weston（姓氏字幕不清）说他在 TikTok 工作过两年，见过几百位创作者困在品牌合作、带货链接和简介里卖 20 美元的 PDF，他们离拥有自己的业务只差一步。他举 Theo 的 T3 Chat 和 Garry Tan 的 GBrain 当例子，Theo 当场说“那很糟，没用”。
  • Theo 给了长评：做创作者的问题是受众会饱和，他给 Vercel 做推广，很快观众要么已经是用户不想再听，要么不会用也不想听。对他帮助最大的一件事是赞助商从 4 家增加到 80 家，多样性带来转化。他认为 Foundry 识别出了创作者更有品味、更有分发、更懂受众，但没有解决“多样性”问题；他更看好它成为企业的工具，帮企业发现和自己客户画像重合的创作者，做出更适合这些受众的产品。他说作为创办公司第二多的 YouTuber，自己创业会把自己和受众都耗尽。
  • Weston 回应科技类创作者是很难的赛道，选择太多。他举例：做家园自给（homesteading）内容的创作者 Brandon 总记不住冻干机的最佳设置，这在他们看来很可笑，但对他 200 万粉丝是真实痛点，现在粉丝按月或按年订阅解决这个问题。他说除了科技和喜剧类，他们都能找到受众愿意付钱的痛点，历史上没有一个创作者离开过，因为都在盈利。

评委退场商议期间播放了大会回顾视频。结果：季军 Commod（字幕作 Komodo），亚军 Built by Foundry，冠军 comment.io。冠军队感谢 AIE 和 Hyperagent，并说 comment.io 可以免费使用。
