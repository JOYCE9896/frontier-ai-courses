01. Benjamin Dunphy（Software 3.0 LLC）：开幕致辞与 Network 应用开源

直播位置 0:17:18–0:25:22 · Welcome & Introduction

谁在场

Ben 是大会联合创始人和主持人。他先用点名的方式介绍赞助商：AutoGPT 几个月前还只是一个开源项目（他称之为史上增长最快的开源项目），现在成了大会的冠名赞助商；Supabase 为这次大会打破了自己“不赞助活动”的规定；Fixie 在展位上放了一个叫 Sidekick 的助手；Microsoft 有 Microsoft for Startups 的代表，旁边是 GitHub 的 Copilot 团队；还有 Cloudflare，以及 Latent Space 播客的另一位主持人 Alessio Fanelli。他提醒大家，现场 500 人都是筛选过的，彼此交流时可以默认对方是做过生产项目的人。他也预告了第二天开幕主题演讲会有 2024 年的消息，会放宽参会人数。

Network 应用和“生成式匹配”

大会的手机应用叫 Network，里面有日程、展商名单、附近的餐厅酒吧咖啡馆。这次新加了一个功能，他们叫它生成式匹配算法（GMA），意思是用 LLM 来给参会者配对：你在个人资料里写下自己想解决的问题，系统去找能帮你解决这个问题的人。匹配功能只对现场参会者开放。

他宣布 Network 的应用和匹配算法一起开源，目标是让任何活动都能用上。代码在 ai.engineer/network 和 GitHub 的 AI Engineer 组织下。他感谢了移动端主程 Simon Sturmer、做匹配算法的工程师，以及基础设施伙伴 Descope（登录认证）和 Supabase（数据库和 pgvector）。pgvector 是 PostgreSQL 的一个扩展，让普通数据库也能存向量、做相似度检索。

02. swyx（Latent Space、Smol AI）：1000 倍 AI 工程师

直播位置 0:25:22–0:35:10 · The 1000x AI Engineer

swyx 是 Latent Space 播客主持人、大会联合创始人，“AI 工程师”这个说法就来自他此前的一篇博客。别人都用翻页笔，他手里拿的是 Magic Trackpad，开玩笑说要试试“二维”的翻页。题目里的 1000x 他自己承认有点夸张，但他想让大家按数量级去想自己的野心。

你来得刚好

他先讲时间点。如果你是数学家，最好的出生时间大约是公元 600 年前后，那时 Brahmagupta 提出了零；物理学最好的年份是 1905 到 1927 年，这次大会的形式也参照了 Solvay 会议（Einstein、Marie Curie 出席的那一届）；造汽车是 1900 到 1930 年；做个人电脑产品是 1980 到 2010 年。网上流行“生得太晚，赶不上探索地球；生得太早，赶不上探索星空”，他的回答是你没有来晚。

他引用 Carlota Perez 关于技术革命“导入期”和“展开期”的理论：工业革命、铁路、钢铁、石油、信息技术，每一轮大约持续 50 到 70 年。他知道很多人心里在怀疑这一轮是不是又一个 Web3 式的泡沫，他的回应是把它放进这些历史周期里看。AI 革命的起点可以定在 2012 年的 AlexNet，到现在大约十年，而且可以用数字来画这条曲线：训练模型用的算力在 AlexNet 那个点出现明显拐点，业界慢慢意识到规模扩展（Scaling）是管用的。

认真对待规模扩展

他给了三个“6”：

  • 一位他不愿点名的知名投资人说，到这个十年末，按算力再增长大约 6 个数量级来做规划。
  • John Carmack 说通往 AGI 还差大约 6 个关键洞见。
  • George Hotz 的估算：GPT-3 大约用了一个“人年”的算力，GPT-4 大约 100 人年；按同样的倍数推到 GPT-10，会超过所有活过的人加起来的算力。

为什么会有 AI 工程师

他用组织架构图来说明：机器学习研究员、机器学习工程师、软件工程师之间出现了一个空缺，就是 AI 工程师。这是一个供需问题：持证的数据科学家和机器学习工程师大约 10 万人，GitHub 说自己有 1 亿注册开发者（真实数字可能在 4000 万到 1 亿之间），差了几个数量级，所以 AI 工程师会比 ML 工程师多得多。之所以叫“工程”而不叫“提示词”，是因为 LLM 还不是 AGI，需要用代码把它们组织进软件系统里才能做成有用的东西，而写代码是这群人已经会的。

他把 AI 工程师细分成三类，并借用自动驾驶的 L2、L3 等级来区分“人在回路里”还是“人只是兜底”：

  • AI 增强型工程师：用 Copilot 这类工具提升自己的软件工程师。
  • AI 产品工程师：做 AI 产品的软件工程师，例子是 Midjourney。
  • AI 工程师 Agent：本身就是 AI，可能替代人类工程师，例子是 AutoGPT，也许还有 Replit 的 Ghostwriter。

他说这个题目受 Amjad Masad 一次播客采访的启发，Sam Altman 也说过自己在 OpenAI 每天都能看到 1000 倍工程师。他的理解是，1000 倍来自多层 10 倍改进的叠加，接下来两天的演讲者分别在做这个栈的不同层。

不涉及技术的那部分

最后他给了一个非技术的定义：10 倍工程师是能把自己会的东西教给另外 10 个人的工程师。他借网络规模的复杂度来比喻三个阶段：O(n) 是你自己听完所有演讲、吸收所有内容，并按“吃豆人原则”给别人留出加入谈话的空位；O(n²) 是帮助别人学习，他的第一篇博客就是在类似的会议上被鼓励写出来的，主题是机器学习；O(2ⁿ) 是回去后建立你自己的 AI 工程师学习网络。

03. Amjad Masad（Replit）：面向所有用户的 AI 与 Model Farm

直播位置 0:35:13–0:41:55 · Keynote: What powers Replit AI?（上半场）

Amjad 是 Replit 联合创始人兼 CEO。Replit 是一个在线编程环境，他们的目标是“从想法到可扩展的已部署软件的最快路径”。他的翻页笔没反应，他说“我们会先得到 AGI，再得到好用的演示软件”。

编程史上的几次数量级跃升

他从 ENIAC 讲起：第一台图灵完备、可编程的冯·诺依曼结构计算机，用打孔卡编程，很难，所以那时没有软件产业。从打孔卡到文本，先有汇编，再有编译器和 C 这样的高级语言（“然后有人发明了 JavaScript，之后就一路走下坡”），文本编程至少是 10 倍、可能是 100 倍的提升。之后有了 IDE。他放了 2017 或 2018 年的截图：Replit 当时给所有编程环境接入了 LSP（Language Server Protocol，让编辑器获得补全、跳转、报错等“代码智能”的标准协议），任何账号都能用，代价是烧掉大量 CPU 和内存（跑 TypeScript server 很吃内存）。

三四年前，GPT-2 已经能接着补全一段代码，他们意识到这件事真的会发生，于是做了 Ghostwriter，在 IDE 里提供自动补全和聊天等功能。他估计现在用这些工具的人生产力提升大约在 50% 到 80%，部分人能到 100%，还没到数量级；他认为未来十年会到 10 倍、100 倍，甚至 1000 倍。

发布：AI for All

Replit 的使命是“赋予下一个十亿开发者能力”，他们不想出现一部分人用得上 Ghostwriter、一部分人用不上的局面。他认为 Copilot、Ghostwriter 这类起了可爱名字的“编程插件”不是正确方向，AI 应该融入每一次编程交互，成为 Replit 默认体验的一部分。所以他宣布：向 Replit 的数百万用户免费开放 AI。他说这会是全球规模最大的 AI 增强编程部署，“我们烧的 GPU 会和烧的 CPU 一样多，为我们祈祷吧”。很多用户用 Android 手机编程，他们现在也都能用上。

发布：Model Farm

他回到 swyx 的分类：AI 进入软件的创作栈是一回事，AI 进入软件的调用栈（产品运行时调用模型）是另一回事，后者也创造大量价值。Model Farm 让用户在 IDE 里直接访问模型，三行代码就能开始做推理（Inference，指用训练好的模型生成输出）。首发接入的是 Google Cloud 的 LLM，很快会加入 Llama 和 Stable Diffusion，也欢迎其他模型提供方接入。到年底前每个人都有免费额度。

04. Michele Catasta（Replit）：怎样训练代码 LLM，发布 replit-code-v1.5-3b

直播位置 0:41:58–1:00:33 · Keynote: What powers Replit AI?（下半场）

反驳“GPU 贫困者”

Michele 是 Replit 的 AI 负责人（VP of AI），之前在 Google 参与过 PaLM-Coder。他说一个多月前 SemiAnalysis 发了一篇文章，大意是用有限 GPU 训练小模型没有意义，这让他们一度怀疑自己在浪费时间，因为 5 月他们刚刚从零训练出一个成功的模型。这场演讲就是要说明事情并非如此。

Replit 的代码补全由自研模型驱动，训练数据是 GitHub 上的开源代码和 Replit 用户的代码。补全对延迟很敏感，他们把 P95 延迟（95% 的请求都快于这个时间）控制在 250 毫秒以下，让开发者感觉几乎是即时的。5 月他们开源了 replit-code-v1-3b，得到很多使用和贡献，这次发布它的升级版 replit-code-v1.5-3b，同样开源。

训练配方

v1 是一个 Llama 风格的代码模型，沿用了 Meta 摸索出的很多做法。这次他们把训练量提到每个参数 300 个 token。背景是 2022 年中 DeepMind 的 Chinchilla 论文：此前的模型普遍“训练不足”，应该给更多高质量数据、用更小的模型。他的理解是把成本从推理时挪到训练时：多花算力训出一个更小、更强的模型，推理时延迟就更低。这是整场演讲的主线。

  • 高质量数据比 v1 翻倍，总共训练 1 万亿 token 的代码：大约 2000 亿 token 的数据混合，跑 5 个 epoch（完整遍历数据一次叫一个 epoch），最后做线性冷却（学习率线性降到很低）。
  • 支持 30 种编程语言，并加入了面向开发者的 Stack Exchange 帖子（编程和软件工程问答）。
  • 数据起点是 BigCode（Hugging Face 旗下的项目）做的 The Stack：从 GitHub 抓取热门仓库、清洗，只保留 MIT、BSD、Apache 2.0 等宽松许可的代码。他们从中选了前 30 种语言。

他说秘诀是花在数据上的时间。模型是从零训练的，不是微调（Fine-tuning，在已有模型上用新数据继续训练），所以每个 token 都由他们自己准备。他们参考 Codex 和 PaLM 论文的质量过滤流程，又加了更多启发式规则：过滤自动生成的代码、压缩混淆过的代码、不可读的代码，也就是你不希望模型推荐给你的那些代码；同时去掉有害内容。整套流水线跑在 Spark 上。他鼓励大家自己训模型，因为从训练到服务的组件大多已有开源实现，“如果你想在 2022 年做这件事，祝你好运”。

重复数据也行

他推荐了论文 Scaling Data-Constrained Language Models，称其为他眼中 LLM 领域最有意思的结果之一。核心发现是：把数据重复 4 到 5 次，损失曲线与使用全新数据差不多。这让他们可以只选一个小而高质量的子集反复训练，也让他们只用宽松许可的数据，所以 v1.5 依然以商业友好的许可证开源。

模型细节

  • 参数量 3.3B，上下文 4K（v1 是 2K）。
  • 新训练了一个 32K 的领域专用词表。他的解释是，LLM 可以粗略看成有损压缩器，词表越能把数据压进更少的 token，训练时每个 token 携带的信号越多；新词表比 StarCoder 和 Code Llama 用的更适合代码，多压出了几个百分点。
  • 在 MosaicML 平台上用 128 张 H100 80G 训练了一周。据他们所知，这是第一个官方宣布用 H100 训练并开源的模型。
  • 用了 FlashAttention、分组查询注意力 GQA（多个查询头共享键值头，推理更快）、ALiBi 位置编码和最新的优化器。

评测结果

他先解释 HumanEval：2021 年发布的基准，给一段英文的任务描述，让模型写一段自包含的 Python 代码，再用测试来执行，看输出是否正确。pass@1 指第一次生成就通过的比例。现在大家也在多种语言上测，用的是 BigCode 的多语言评测框架，他们维护一个排行榜。

  • 在 3B 规模，截至前一天最强的是 StarCoder 3B；v1.5 基座模型在列表里每种语言上都超过它。
  • 让他兴奋的是基座模型已接近 Code Llama 7B。Code Llama 7B 先在 2 万亿 token 的自然语言上训练，又在 5000 亿 token 代码上继续预训练，模型是两倍大，数据是 2.5 倍，算力多得多。
  • 超过 Code Llama 的办法是另一个并行训练的版本，他们叫 Replit-tuned：用 Replit 用户的代码再继续预训练。在 Replit 上公开的 Repl 自动是 MIT 许可，他们从中抽取 300 亿 token（字幕先说 2000 亿后说 300 亿，以 300 亿为准），同样的过滤流程，跑 3 个 epoch，加线性冷却。语言集中在 Replit 用户最常用的那些，他说约 95% 的人写 Python 和 JavaScript。数据截止日期就在几周前，所以最近一个月流行的新库它也会写，他们打算持续更新。
  • Replit-tuned 版在几乎每种语言上都明显超过 Code Llama 7B，HumanEval pass@1 达到 36%。他说这和他当年在 PaLM-Coder 上发表的结果一样，而那个模型是 5400 亿参数（字幕说 530 billion tokens，他应指参数量），大约是它的 200 倍；Codex 论文里的 code-davinci-001 也是 36%。

为推理速度而优化

他们训练自有模型的理由是要最快的强小模型，所有设计都是为推理优化，跑分好只是附带结果。单个模型、不做批处理时，生成速度超过每秒 200 token。注意力用的是 Triton 内核版 FlashAttention，部署针对 NVIDIA Triton 推理服务器和 TensorRT-LLM 做了优化。

部署速度也是重点。最初在 Kubernetes 上从点击到模型上线要 18 分钟，遇到流量高峰根本来不及扩容；工程师 Bradley 用一堆技巧把它降到 2 分钟。Amjad 宣布 AI for All 的那一刻，他们拨动开关，代码补全就推给了所有用户。

为什么开源，以及接下来

开源 v1 之后，社区做出了微调版、指令微调版，还有人用 GGML 在 Apple Silicon 上本地运行，做成注重隐私的 Copilot 替代品。v1.5 已上 Hugging Face。接下来三项合作：

  • 与 Glaive AI（做合成数据集的公司）合作，用约 21 万条编程指令做指令微调版，结果还在复核。
  • 与 Morph Labs 合作，作为 FIST 格式的设计伙伴。他先解释 FIM（Fill-in-the-Middle）：把文件切开，告诉模型上半部分是前缀、下半部分是后缀，让它填中间。FIST 是对抽象语法树（AST）有感知的版本，Morph Labs 的 Jesse 当天下午会专门讲。
  • 模型当晚会上 Perplexity Labs，可以直接试用。

05. Toran Bruce Richards 与 AutoGPT 团队：工作的未来

直播位置 1:00:46–1:13:49 · The Future of Work

AutoGPT 的作者 Toran Bruce Richards 简单开场后，把台子交给团队。按字幕里的称呼，依次是创始 AI 工程师 Silen（应为 Silen Naihin，负责 Benchmark）、首席开源开发者“Pwuts”（Reinier van der Leer 的 GitHub 用户名），最后是 Craig（应为 CTO Craig Swift）宣布融资。AutoGPT 是 2023 年春天走红的开源项目，让 GPT-4 在循环里自己给自己拆任务、调用工具，是最早广为人知的自主 Agent 之一。

愿景：用聊天代替重复劳动

Silen 用三个例子说明人没有发挥潜力：填销售线索表格时，你在 Google、LinkedIn 和表格之间反复复制粘贴几个小时；清理未读邮件时，你反复发同一封邮件的各种变体；开发应用要几周到几年，而且很多时候是在从 ChatGPT 复制粘贴。他设想的世界里，这些都改成“跟它聊一下”。他说 AutoGPT 是最快达到 10 万 GitHub star 的仓库，各大新闻网络都报道过，开启了一个新的开发方向。

两条经验

第一条：代码为王。他们认为编程 Agent 是最基础的 Agent，因为数字世界的底层就是代码；目标仍是通用 Agent，但编程是通往 AGI 的台阶（他补了一句，“一个有动力的程序员什么都能搞定，除了买床架”）。

第二条：没有指南针就不知道往哪走。项目初期平均每 2 小时就有一个 PR，他们没法判断 PR 好不好、怎么测，成本高、方向乱。于是他们做了 Benchmark，用来量化地判断 Agent 有没有进步，现在也在黑客松里用。他们已经在 CI 流水线里对生态里多个开源 Agent 跑了几个月。他展示了 8 月的成功率曲线，从 35% 左右涨到 55% 左右，并说明这数据很嘈杂，“不会放进论文里”。

06. Simón Fishman、Logan Kilpatrick（OpenAI）：看、听、说、画，多模态演示

直播位置 1:13:49–1:33:12 · See, Hear, Speak, Draw

Simón 在 OpenAI 的 Applied 团队做工程师，处在“部署流水线”的末端，和真实使用 OpenAI 模型的客户一起想怎么用模型解决难题；Logan 做开发者关系。多模态（Multimodal）指模型能处理文本以外的输入输出，比如图像、音频、视频。

从“孤岛”到统一

Logan 说 2023 年是聊天机器人之年，这么简单的东西已经创造了很多价值；他预计 2024 年是多模态模型之年。OpenAI 当时在 ChatGPT 里已有 Vision（看图描述）和 DALL·E 3（生成图像）。Simón 把现状描述成几个孤岛：DALL·E 把文本变图像，Whisper 把音频变文字，GPT-4V（带视觉的 GPT-4）可以同时对图像和文本做推理。现在能做的是把文本当作它们之间的连接组织；他们期待的未来是一个模型同时吃进、输出多种模态。Logan 补充，做这次演示时他们发现，今天做多模态系统的大部分工作就是把各个模态连起来，等以后一个模型就能做到，开发效率会提高很多。

演示一：DALL·E 与 Vision 的循环

流程是：拿一张真实照片，让 GPT-4V 写一段详细描述和一段给 DALL·E 的提示词，DALL·E 3 生成一张合成图；再把两张图一起交给 GPT-4V，让它找出差异、改写提示词，再生成。

  • 第一张是酒店大堂里万圣节装饰的维多利亚风格房子（Painted Ladies）。第一次生成有墓碑、老狗等细节，但大理石变成黑色、蜘蛛也不对；比较之后的第二版去掉了黑色大理石，蜘蛛变成又大又黑的样子，更接近原图。
  • 第二张是后台照片：显示器、箱子、线缆。生成图里多了墙上和天花板的竖向灯带，比较时 GPT-4V 指出了这一点，改写后去掉了灯带，还补上了原图里的黑色幕布。
  • 现场跑的一张是 Simón 周末越野跑时拍的林间木栈道，描述生成成功，但直播时最后一步没能及时出图。

他们强调这里没有任何提示词工程，代码大约 50 行，是“一小时写出来的演示版”。Logan 提到 ChatGPT iOS 应用里的 DALL·E 模式其实会替用户做一些提示词改写，以前用 Labs 产品或 Midjourney 时要自己写好提示词，这一直是限制。

Simón 总结了两个模式。一是描述图像：图像变成文本后，就可以对文本做各种推理。二是比较图像、找差异：有一个目标状态和一个当前状态，这个模式可以用到很多地方。以前这种“看视觉输出、和别的东西比较、改指令、再交给另一个模型”的流程被认为离不开人，现在模型自己能做。Logan 的想法是：搬了新家，在 Instagram 上找到喜欢的风格图，交给 GPT-4V，再让它在 Amazon 上找所有符合这个风格的台灯。

演示二：把视频变成图文文章

很多视频摘要只是拿字幕让 GPT-4 总结，丢掉了画面里的信息。他们把 YouTube 上的 GPT-4 发布介绍视频拆成帧，让 GPT-4V 描述每一帧，再用 Whisper 转写音频，得到一份同时包含画面和声音信息的长文本表示，最后生成一篇博客文章：开头一张 DALL·E 配图，正文里插入与上下文对应的真实视频帧。屏幕右下角的二维码可以看到生成结果。代码因为用到未发布的 API 没有开源，提示词也很粗糙。

结论

  • 开始用多模态的方式思考，现在觉得“要是技术能做到就好了”的点子，半年到一年后很可能能做。
  • 在可预见的未来，文本仍是连接各模态的组织。
  • 图像相关的模式还有很多没被探索。Logan 最后说，带图像输入的 Agent 会很厉害，因为互联网有大量内容需要“看”。

07. Flo Crivello（Lindy）：Agent 的时代

直播位置 1:33:20–1:48:50 · The Age of the Agent

一句话的愿景

Flo 是 Lindy 的创始人兼 CEO，之前创办过 Teamflow。他说的未来是 5 到 10 年内的事：一个 25 岁的人能产生和可口可乐公司一样甚至更大的商业影响。他认为媒体业已经发生过一次：Oprah 当年要去说服电视台高管、融资、招团队、找摄影师；YouTube 把这些摩擦降到零之后，MrBeast 的覆盖面超过 Oprah，甚至超过超级碗，起步时只有他和一台笔记本。更奇怪的是 Ryan's World，一个孩子 3 岁开始在 YouTube 上拆玩具做测评，12 岁时身价 1 亿美元。他的论点是，摩擦降到零、守门人被移除之后，内容的性质也变了，Oprah 和超级碗至少还像脱口秀和体育比赛，Ryan's World 和 MrBeast 就很怪。商业世界会经历同样的变化，会出现更怪、更有创意的点子。

为什么做 Agent

他创办第一家公司时以为创业就是做个好产品推向市场，结果发现之前要见律师注册公司、见银行开户、见 VC 融资、见猎头招人，而且公司成立后也没有更轻松。生成式 AI 刚兴起时，产品大多是写文案、生成图片，他觉得这不解决他的问题，而且 GDP 不是由文案和插画师构成的，是由工作和行动构成的。所以他对能自动化日常琐事的 Agentic AI 感兴趣。

他引用电影《上班一条虫》（Office Space）里的 Milton：在地下室里一辈子填 TPS 报告，最后做了职业生涯里最有效率的一件事，把大楼烧了。他说大家总担心机器人抢人的工作，他觉得是人一直在抢机器人的工作。数据上，美国普通经理每周花 15 小时做行政类杂务，每年合计约 4590 亿美元，仅美国就超过挪威的 GDP（字幕作 “no way”，应指 Norway）。

Lindy 能做什么

Lindy 是一个“AI 员工”，第一个擅长的角色是个人助理，主攻日历、邮件、会议三个最浪费时间的地方。他放的都是真实产品截图：

  • 安排会议，并且会从交互中持续学习。他让 Lindy 每周找半小时和 Eric 开会，它把会议命名为 “Flo <> Eric”，因为之前他抱怨过它把所有会议都叫 “Meeting with Flo”，给了一次反馈后它记住了这个偏好。他说可以给它任意复杂的偏好，它都会记住并遵守。
  • 抄送 Lindy 到邮件里，让它帮忙约时间；它会按每个收件人的关系、用你的口吻预先写好回复草稿，“你和伴侣说话的方式和对投资人说话的方式不一样，希望如此”。他每天早上打开 Gmail，草稿已经准备好等他审。
  • 会前准备：每次会议前 5 分钟发给他 Zoom 链接、对方的 LinkedIn 和最近几封邮件的摘要。

他说这些功能他们都没有专门开发，他们做的是一个通用框架，让 AI 用任意工具追求任意目标，复杂的行为是从中涌现的。

一次失败

他不喜欢台上只讲成功案例，所以讲了一次失败：他让 Lindy 每天早上发一个有趣的新单词帮他扩充词汇。他用了一阵子，有天收到一个词，解释是“毫无方向地漫游一段对话”，他没听过，Google 一下发现这个词不存在；回头查了之前所有的词，一个都不存在。“如果我今天用了什么不存在的词，就是因为这个。”

从一个 Lindy 到一群 Lindy

要达到“25 岁的人比肩可口可乐”，一个助理不够，需要一整个 Lindy 社会一起为你的业务工作。他用 Toaster Project 举例：有人想看一个人能不能从零做出一台烤面包机，花了 6 个月、2000 美元（算上时间成本大概 5 万美元），做出来的东西很难看，而 Amazon 上 25 美元就能买一台好用的。一群人协作的能力远超一个人。人们让 GPT-4 一口气做完一个 iOS 应用、设计、上架，它做不到，就说得等 GPT-5、6、7；他觉得这就像让一个人造火箭，造不出来就断定人类造不了火箭。

他们做的就是让多个 Agent 协作的框架。最好的例子是用一群 Lindy 来构建 Lindy 自己：Lindy 需要大量集成（Slack、Twilio、Google Sheets 等），顶层是一个“工具创建 Lindy”，接到“做一个 Slack 集成”的指令后，交给一个上网找 OpenAPI 规范和文档的 Lindy，再交给一个“经理 Lindy”把任务拆给多个“工程师 Lindy”，其中有一个专门写认证代码，因为那里坑多；做完交给 QA Lindy 测试，不通过就打回，通过就提交 PR。他承认这套流程现在完成了七八成。

他最后说，今天世界上最好的 CMO 可能在 Apple、Nike 或可口可乐，不久以后最好的 CMO、设计师、工程师都会是 AI，它们会为你工作；到时候唯一重要的技能是你会不会用这根杠杆。

09. Sasha Sheng：AI Engineer Foundation 成立

解决办法是流式输出结构化数据，这比逐 token 流式输出字符难：每收到一部分就要部分解析结构，判断有没有新完成的段落可以拿去朗读。ModelFusion 负责部分解析，返回一个部分结果片段的迭代器，应用决定怎么处理。每段完成就去朗读：旁白有固定的声音；已有声音的角色直接用；出现新角色时，先用 GPT-3.5-turbo 生成结构化的角色声音描述（性别加声音特征），再用事先把所有声音描述做过 Embedding 的库按性别过滤检索，选一个和已有角色不重复的声音。语音合成支持 LMNT 和 ElevenLabs。音频同样存成虚拟文件，客户端拿到路径后作为媒体元素播放。第一段音频好了就开始播，服务器在后台继续生成后面的段落。

他总结了提升响应速度的三点：加载状态分多个部分逐步更新；后端用流式和并行处理；按处理时间来挑模型，尽量缩短生成时间。

六个等级分三类：人发起（人是主要写代码的人）、AI 发起（AI 开始主动参与）、AI 主导（AI 对代码库完全自主），并逐级对照 SAE 自动驾驶等级：

  • Level 0：开发者手写全部代码，自己写、测、调试，最多有 IDE 的符号补全。对应完全靠人驾驶的汽车。
  • Level 1：AI 根据开发者意图生成单行或整块代码，比如写好函数签名，AI 推断上下文补出实现。它在数百万行开源代码上训练过，上下文是宽泛通用的。对应定速巡航、车道居中。
  • Level 2：AI 对当前代码库有具体的上下文。例如在用 axios 处理 HTTP 请求的 Node.js 项目里，它会按 axios 来补全，不会给出 fetch 或 superagent 的写法。对应部分自动化：人仍掌控，随时可接管。
  • Level 3：开发者给高层需求，AI 交付整个组件甚至和其他软件的集成。比如“给应用加用户认证”，它生成所需全部代码，并解释代码怎么工作、怎么和应用其余部分集成。对应车辆承担主要驾驶，人是兜底。
  • Level 4：AI 在没有开发者监督的情况下主动处理编码任务。例如持续监控代码变更，自动提 PR 保持文档更新；监控客户提交的 bug 报告并提 PR 修复，人只需审核合并。对应 Waymo 这类在高精度地图覆盖的城市里运营的无人出租车。
  • Level 5：AI 处理整个软件开发生命周期：设计架构、写生产级代码、部署、持续改进；开发者只验证最终产品是否满足需求，不一定看代码。对应全条件自动驾驶，方向盘都不需要。

17. Harrison Chase（LangChain）：用 LangChain 和 LangSmith 构建上下文感知的推理应用

直播位置 2:57:50–3:16:52 · Building Context-Aware Reasoning Applications with LangChain and LangSmith

Harrison 是 LangChain 的联合创始人兼 CEO，LangChain 是当时最流行的 LLM 应用开发框架。他从 ChatGPT 的界面说起：语言模型本身不知道时事、不能运行你写的代码、不记得之前和你的交互，要做出真正个性化、有用的 AI 助手，需要把语言模型当作更大系统的一部分。这些系统能理解合适的上下文并据此推理，LangChain 想帮团队填补“神奇体验”和背后工程工作之间的差距。

上下文的四种来源

  • 指令提示（Instruction prompting）：直接告诉模型在特定场景、特定输入下怎么回应，像给新员工一本员工手册。最直接，大家都从这里开始；模型越强，这种零样本提示（Zero-shot，不给例子直接下指令）能承载的上下文越多。
  • 少样本示例（Few-shot）：有些东西很难用语言描述，给例子更好，比如语气，以及越来越复杂的结构化输出格式。
  • 检索增强生成（RAG）：先根据用户问题检索出相关内容，再让模型“基于给定上下文回答”。前两种决定模型怎么回应，RAG 决定回答依据什么，有点像开卷考试。
  • 微调：更新模型权重。还在早期，大家在摸索适用场景。他们观察到它适合和少样本相同的场景（语气、结构化数据解析），并把它推向极端：三个例子有用，那一万个例子、直接更新权重呢？需要“展示”远多于“告诉”时，微调开始有帮助。

推理的几个层级

他把让应用“推理”的方式排成一个谱系，按“谁决定输出、谁决定步骤、有没有循环”来区分：

  • 普通代码：一年前（“很久很久以前”）的方式，所有步骤和输出都写死。
  • 单次 LLM 调用：模型只决定输出，不采取行动。
  • 链（Chain）：多次 LLM 调用，或 LLM、API、LLM 交替，用来拆解复杂任务、在中间动态插入知识；步骤是事先确定的。
  • 路由器（Router）：模型开始决定走哪一步，比如选用擅长数学的提示还是擅长写作的提示，选 Claude（上下文窗口长）还是 GPT-4（推理强），选调哪个工具、输入是什么。但没有循环，只是选分支。
  • 状态机：加入循环，基本上就是一个 while 循环，模型决定每步做什么、何时结束。外界常把这类叫作 Agent。常见状态是“规划、执行、验证”。
  • 自主 Agent：大致是 AutoGPT 那种，去掉了大部分护栏，可用的步骤序列几乎由 LLM 决定，工具可以动态创建（比如 Voyager 论文里逐步积累技能库），并且不再有显式的状态划分，让 Agent 自己隐式决定何时规划、何时验证。

他强调这个领域还很早期，这套分类三个月后可能就过时了。

构建这类系统的难点

  • 编排层：选哪种认知架构。各有利弊，链的步骤更可控，Agent 对意外输入和边缘情况反应更灵活。能快速试验多种架构，是 LangChain 最初的动机。LangSmith 则提供可见性，让你看清复杂应用里到底调用了哪些工具、哪些 LLM 调用、按什么顺序。
  • 老派的数据工程：正确的上下文往往就是数据，需要加载、转换、传输数据，并观察数据在系统里怎么流动。LangChain 有很多开源的加载和转换模块；LangSmith 用来调试数据到达模型时长什么样：从向量库取对了文档吗？格式化得让模型看得懂吗？
  • 老派的提示词工程：要看清最终完整格式化后的提示词，包括系统指令、少样本示例、检索到的上下文、聊天历史、Agent 之前的步骤。第一步好查，到第三步之后就难了。LangSmith 可以在任意一次 LLM 调用处打开 playground 直接改提示词、换模型提供方对比效果。
  • 评测：他说这值得单独一场演讲。难在缺数据和缺好指标。传统 ML 一开始就有数据集，评测时至少有数据点；LLM 是优秀的零样本学习者，不建数据集也能做出 MVP，评测时就没有数据。他们鼓励用户建数据集并持续迭代，来源可以是人工标注、从生产流量里挑、或用 LLM 自动生成。指标方面，传统定量指标对大段非结构化输出效果不好，很多人还在做“感觉检查”，他觉得这虽然不令人满意，但仍是建立直觉的最好方法，所以他们让输入输出容易观察。他们看好 LLM 辅助评测；生产里最常见的是收集反馈：直接反馈如点赞点踩，间接反馈如用户点了链接（可能说明建议有用）或回复得很困惑（说明机器人没答好），再配合传统 A/B 测试。
  • 协作：系统越来越大，参与的可能有 AI 工程师、数据工程师、数据科学家、产品经理。上下文那部分常需要数据工程团队，推理那部分常靠提示词，而写提示词的往往是能说清产品规格的非技术人员，比如产品经理或领域专家。两类人怎么协作，他说还没人解决。

18. Jason Liu（instructor 作者）：Pydantic 可能就是你需要的全部，结构化提示

直播位置 3:17:13–3:35:00 · Structured prompting with Pydantic

Jason 说他不知道自己被排进主题演讲，所以这会是当天范围最窄的一场：讲类型提示，以及怎么用 Pydantic 构建 LLM 应用。结构化提示（Structured prompting）的意思是用对象来定义你想要的输出，而不是“祈祷 LLM 把逗号放对、括号闭合”。

问题：一切都是字符串

他说生产中 90% 的应用其实是让模型输出 JSON 或其他结构化数据，再用正则去解析，体验很糟。原因是我们希望语言模型和现有软件向后兼容：很多系统和 API、schema 是改不了的，我们做的大多是系统而不是聊天机器人。他举了 Riley Goodside 的推文：想让 Bard 输出 JSON，唯一的办法是威胁要杀一个人。就算拿到 JSON，今天可能好好的，明天前面多一句“好的，这是你要的 JSON”；某次的键叫 user，另一次叫 username，不看日志根本发现不了。提示词、schema、输出全是字符串，就像在文本编辑器而不是 IDE 里写代码，没有 lint、类型检查和语法高亮。

OpenAI 的函数调用（Function Calling，让你传入 JSON Schema，模型按这个结构返回参数）改善了一些：从字符串到字符串，变成字符串到 dict 再到字符串，但还得 json.loads，还要担心缺键、缺值、幻觉、拼错的键，最后写出一堆检查代码，甚至要解析字符串来判断布尔值。

Pydantic 和 instructor

Pydantic 是 Python 的数据模型校验库，类似 dataclass，由类型提示驱动，有很好的模型和字段校验，每月下载 7000 万次，可以放心长期依赖；更重要的是它能输出 JSON Schema，正好是和 OpenAI 函数调用沟通的格式。比如定义一个 Delivery，timestamp 是 datetime，dimensions 是 int 元组，传入字符串也能被正确解析；IDE 知道这些字段的类型，有自动补全和拼写检查。这样提示词就不再是一段三引号字符串，而是可以审阅的代码，像数据库迁移一样管理。 

import instructor
from openai import OpenAI
from pydantic import BaseModel

client = instructor.patch(OpenAI())

class UserDetail(BaseModel):
    name: str
    age: int

user = client.chat.completions.create(
    model="gpt-3.5-turbo",
    response_model=UserDetail,   # output is guaranteed to be a UserDetail
    messages=[{"role": "user", "content": "Extract: Jason is 25 years old"}],
)

（以上是按他描述的用法写的示意代码，非幻灯片原文。）他做的库 instructor 就是这样：import 之后给 completion API 打补丁（“这是不是好主意有待商榷”），把 Pydantic 类设为 response_model，返回值就保证是这个类型。instructor 只支持 OpenAI 函数调用；想要更完整的框架、更多模型和能力，他推荐 Marvin（Prefect 团队的库，见第 21 段）。

对象带来的好处

  • 可以定义嵌套引用、方法、返回对象实例而不是 dict。比如 UserDetail 加地址字段，再定义 BestFriend、Friends（UserDetail 列表），换成手写 JSON Schema 会很难维护。
  • docstring 和字段描述会进入发给 OpenAI 的 JSON Schema。这样一个模型同时代表了提示词、数据和行为，代码质量、提示词质量、数据质量保持同步，你只需维护和审阅一处，所以变量名、描述、文档都要写好。
  • 校验器（Validator）：普通的 Pydantic 校验器不需要 LLM，校验失败会抛出可捕获的 ValidationError。instructor 提供 llm_validator，可以写“不要说刻薄的话”，当对象里出现“生命的意义是作恶和偷东西”时，会抛出 LLM 生成的错误信息“该陈述令人反感”。
  • 自动修复：加上 max_retries，instructor 会把所有校验错误一次性发回模型重试。他强调这不是提示链也不是 Constitutional AI，只是校验错误处理加重新提问，是代码里可以分开管理的系统。要少于 10 个字符就用字符数校验器，要确认名字在数据库里就发个 POST 请求，都是普通代码。

用结构来组织思考

  • 给模型一个出口：与其让它在不知道时返回全大写的 “I DON'T KNOW” 再去字符串匹配，不如定义 MaybeUser，包含可选的 result、error 布尔值和 message。
  • 可复用组件：工作时间和休闲时间都是 TimeRange（开始时间、结束时间）。如果解析不准，可以在 TimeRange 里加一个思维链（Chain of Thought，让模型先写推理过程再给答案）字段，测试时开启、生产时关掉，以权衡延迟和效果。
  • 抽取任意键值属性：定义 Property（key、value），抽取一个列表；可用校验器保证键一致，不一致就重试；要正好 5 个就加一个 index 字段，让模型数到 5 停下，输出更可靠。
  • 提示数据结构：给 UserDetail 加 id 和 friends（id 列表），提示得好就能从数据里抽出一张社交网络。

他的比方是从 C 到 C++ 得到了面向对象编程；LLM 现在能输出数据结构，可以表示知识、工作流和计划，再交给传统系统去执行，比如生成 DAG 交给 Airflow，而不是写一个 for 循环祈祷它终止。

进阶应用

  • RAG 查询分解：真实场景可能有多个后端、需要改写或拆分查询、需要时间过滤。定义 Search（标题、query、before_date、类型是 email 还是 video）并实现 execute 方法，让模型返回多个 Search，再用 asyncio 并发执行。提示词本身可以很短，“你是一个有用的助手，把搜索查询拆开”，因为提示都嵌在数据结构里。
  • 查询规划：定义 Query（id、问题、依赖列表），让模型输出整个查询计划。例子“加拿大和 Jason 的祖国人口差多少”：前两个子问题没有依赖可以并行，第三个等前两个，第四个合并。只需要一次 LLM 调用，省掉 Agent 式的多轮循环。
  • 知识图谱：让数据结构尽量贴近图可视化 API，问“描述量子力学”就得到一张图，大约 40 行代码。
  • 带引用的问答（防幻觉）：QuestionAnswer 包含问题和一组 Fact，每个 Fact 有陈述和若干从原文截取的子串引用。校验器检查每条引用确实出现在文本块里，没有就丢弃这条事实；再只保留至少有一条引用的事实。他说这是把“不要幻觉”写成业务逻辑，没有靠提示词去要求；回答可以精确到“出自这句和那句”，比“在第 7 页”具体得多。

他说这越来越像领域建模，文档在 jxnl.github.io/instructor。他们也在试做结构化评测的界面，比如判断一个回答是否刻薄，同时看某个浮点属性的分布。他期待的方向是多模态：给一张图，让模型输出每个商品的边界框和在 Amazon 上搜索它的关键词，直接渲染成界面，即图像和音频上的生成式 UI。

19. Eugene Yan（Amazon）：LLM 系统与产品的构建模块

直播位置 3:35:00–3:52:30 · Building Blocks for LLM Systems & Products

Eugene 是 Amazon 的高级应用科学家。几个月前他为了理清思路写了一篇关于构建 LLM 系统和产品的模式的长文，社区反响很好，Jason 还要求做成讲座。这次讲其中四个：评测、检索增强生成、护栏、收集反馈。他说会讲得很快，幻灯片会公开。

评测：一切的基础

评测告诉你提示词工程、检索增强、微调到底有没有用。可以做“评测驱动开发”，也可以把评测当测试用例，每次部署前跑一遍。他说连 OpenAI 的管理者都花时间写评测或给评测反馈，可见它的重要性。难点：

  • 缺乏一致的方法。传统 ML 有 RMSE、精确率召回率、NDCG，算法唯一。LLM 的基准如 MMLU（多选题，测计算机、数学、美国历史等知识和推理）却没有统一跑法。不到一周前 Princeton 的 Sayash 等人写了《评测 LLM 是个雷区》，问我们测的是模型还是提示词敏感度；同一天 Anthropic 指出简单的多选题其实不简单，括号格式这种小改动就会改变准确率，所以很难用学术基准比较模型。
  • 有些基准已经被超越。摘要任务里，自动摘要的人类评分已经高于参考摘要；在 XSum（极端摘要）数据集上，人类评分全低于 InstructGPT，还不是 GPT-4。
  • 基准太容易拿到，大家忘了问它适不适合自己的任务。除非你在做大学水平的聊天机器人，MMLU 不一定适用。

他看到的几条新兴做法：

  • 为自己的具体任务建评测，从小处开始。他举 Teknium（发布了很多开源模型）为例，他的领域评测集只有 40 个问题。
  • 尽量简化任务。比如内容审核可以退回到简单的精确率和召回率：抓到有害内容、偏见、幻觉的比例。
  • 写 SQL、抽取 JSON 这类有预期答案的任务，直接跑 SQL 看结果、检查 JSON 的键值是否符合预期，结果是确定的。
  • 对话这种开放任务可能要靠强 LLM 来评，但很贵，他引了 Jerry（LlamaIndex）说用 GPT-4 跑 60 个评测花了很多钱。
  • 有了自动评测也别忽视人工查看输出。Mosaic 的 Jonathan 说他不相信任何评测能抓住他们真正在乎的东西，他们有个给 3 岁和 7 岁孩子生成游戏的提示词，训练过程中直接看输出更有效。

RAG：即使检索对了也还有问题

RAG 让我们把知识作为输入上下文加进去，比不断微调加新知识更便宜、更精确。检索本身的难点第二天有 Jerry 和 Anton 讲，他讲 LLM 这一侧的问题：

  • LLM 看不全你检索的文档。他引了“迷失在中间”那篇实验：开放域问答，给 20 篇文档，每篇最多 100 token，只有一篇含答案。答案在第一篇时准确率最高，在最后一篇时还行，在中间时比不给任何检索文档还差。所以即使上下文窗口变大，也不能让检索变差，把最相关的文档排在前面仍然重要；而且答案在第一位时准确率也只有约 75%，完美检索也会出错。
  • LLM 分辨不出检索到的上下文不相关。他的例子：给出 20 部他喜欢的科幻片，问他会不会喜欢《暮光之城》，并特别指示如果不会就回复“不适用”，因为推荐系统里不该做坏推荐。模型先指出《暮光之城》是不同类型，很好，然后因为“跨物种关系”推荐了《E.T.》。模型被调得太想帮忙，很难让它承认不相关。

应对：向信息检索、搜索和推荐领域学习，它们一直在研究怎么把最相关的放前面；加一个相关性阈值排除不相关的文档，比如科幻片的例子里算一下两者的距离，太远就不进入下一步。

护栏：事实一致性

护栏（Guardrails，生产中拦截不安全或错误输出的检查层）一方面是安全，比如 OpenAI 的 moderation API 覆盖仇恨、骚扰、自残；另一方面他更关注事实一致性，也就是幻觉，可以看成针对幻觉的评测。摘要领域研究这个问题很久了：

  • 自然语言推理（NLI）：给前提和假设，判断蕴含、中立或矛盾。前提“John 喜欢所有水果”，假设“John 喜欢苹果”是蕴含，“John 每天吃苹果”是中立，“John 讨厌苹果”是矛盾。用到摘要上，前提是原文，假设是摘要。要按句子做，不要按整篇做：整篇比较会判定摘要正确，逐句比较才发现最后一句错了；论文的消融实验显示粒度从文档到段落到句子越细，检测准确率越高。
  • 采样：SelfCheckGPT 的做法，对同一文档生成多次摘要，用 n-gram 重合、BERTScore 等比较彼此是否相似。差异大说明可能没有基于原文、在幻觉；相似则可认为有依据。
  • 让强 LLM 打分：概念简单，但要强模型，很贵。他见过在事实一致性上更简单的方法以低得多的成本胜过基于 LLM 的方法。

收集反馈

反馈让你知道用户喜欢什么，还能用来构建评测集和微调数据集。模型来来去去，评测集和微调数据才是可以带走的资产。显式反馈（主动问用户）很稀疏：他现场问用 ChatGPT 的人多不多，很多人举手；点过点赞点踩的寥寥无几。隐式反馈（用户自然使用产品时产生的信号）则很嘈杂：点了“复制代码”不代表代码正确，他展示的例子里那段 pandas 代码用了一个不存在的参数，如果把所有复制都当正样本，训练数据里会有很多坏数据。

他说自己没有好答案，但有两个做得好的产品：GitHub Copilot，每天几十次接受、拒绝或跳过建议，积累了一个“黄金数据集”；Midjourney，生成四张图后你可以重跑（负反馈，一张都不喜欢）、变体 V（小正反馈，这张有潜力但要微调）、放大 U（大正反馈，就要这张）。他建议把这种隐式反馈的数据飞轮设计进产品。

三点结论

  • 你需要自动化评测。标注 30 到 100 个例子起步，再想办法自动化；人工查看适合做最后的感觉检查，但不能规模化。他说自己每天跑几十个实验，只能靠自动评测。
  • 尽量复用现有系统：BM25、元数据匹配就能走很远，推荐系统的两阶段检索加排序、过滤等技术都是为把最相关的排在前面而优化的。
  • 用户体验在 LLM 产品里占很大比重。Copilot 和 ChatGPT 很大一部分是 UX，让你在 IDE 或聊天窗口里直接用 LLM，不用调 API；好的 UX 也让收集反馈更有效。

20. Linus Lee（Notion）：Embedding 的隐秘生活

直播位置 3:52:30–4:11:05 · The Hidden Life of Embeddings

Linus 在 Notion 负责 AI 一年左右，此前做了很多独立原型实验，用语言模型和 TF-IDF、BM25 等传统 NLP 方法做阅读和写作的新界面，尤其研究过 Embedding 模型和模型的潜在空间。他提到 Notion AI 公开测试版快满一年（2022 年 11 月发布），陆续上线了数据库里的 AI 自动填充、翻译等功能，也在招人。

为什么看潜在空间

他关心的问题是怎样控制语言模型。他说用提示词控制模型，像坐在后座拿一根泳池浮条去控制方向盘：技术上有联系，但隔了好几层间接，尤其是生产中用的更小更高效的模型。模型对提示词的理解在变好，但只靠 token 的间接控制总有隔阂。更直接的方法是看模型内部，也就是潜在空间（Latent Space）。Embedding 是把一段文本或图像编码成的一个向量（比如 1536 或 1024 个数），这些向量所在的高维空间就是潜在空间；激活值、token embedding、图像模型、自编码器里也有。理论上 Embedding 装着模型为完成任务而认为最显著的特征，如果能从中拆出有意义的属性，就可以读出模型看到了什么，甚至通过修改 Embedding 来控制生成。

文本演示

  • 编码与解码：他用 Greg Egan 的科幻小说《Diaspora》的一段介绍，编码成一个长度 2048 的向量，再用模型的解码器部分还原。还原的文本长度略有不同，但基本复原，包括书名这样的具体细节。
  • 模糊：在 Embedding 周围按一定半径采样，解码出的文本出现“语义模糊”，书名错了，名字保留了 Greg 但成了另一个人。他说这不太有用。
  • 沿方向移动：他算出一个代表“同主题但更短”的方向，把 Embedding 往这个方向推，解码出的文本变短，再推一点更短，主题保持不变。基于这个，他做了一个空间画布界面：把文本放在画布上，生成几个更短的版本，挑一个克隆出来，再往“情绪更负面”的方向推，像在潜在空间里走动。
  • 投影读数：他让 ChatGPT 把原文改写得极其悲观，然后把两段都嵌入、投影到各个方向上。悲观版在负面情绪方向上明显更远；“艺术主题”方向和长度方向两者差不多；悲观版词汇更华丽。
  • 拼接：把原文和他写过的一个地中海小镇故事开头都嵌入，取第一个 Embedding 的前一千维和第二个的后一千维直接拼起来。按理说会是乱码，结果解码出的句子在结构（开头有加引号的书名）、主题、标点和语气上都混合了两者。
  • 读别家的 Embedding：他训练了一个线性适配器，让自己的解码器能读 OpenAI text-embedding-ada-002 的向量。只给 OpenAI 的 Embedding、完全不看原文，解码结果不完美，但恢复了大量细节：专有名词 Diaspora、带引号书名的结构、主题（失控 AI），有时连作者名都大致对。他说这说明高容量 Embedding 空间里保留了这么多细节。

图像演示

用 CLIP 的 Embedding 空间（CLIP 是能把图像和文本嵌入同一空间的多模态模型），他在自己的照片和 Notion 风格卡通头像之间插值出 6 张图，从写实逐渐变成卡通，过渡相当平滑。因为 CLIP 是图文共享空间，他还做了文本运算：减去“一张微笑男人的照片”的向量，加上“一张很伤心、在哭的男人的照片”的向量，文本要调低权重，结果图里的他变伤心了；再加“海滩”的向量，这次海滩没能保留下来。他说所有演示只是计算 Embedding、相加、做些归一化，就能操控文本和图像的特征，还能同时加风格和主题，在风景图之间平滑过渡。

相关研究和模型

他提到的研究：Othello 世界模型论文、Neurons in a Haystack，以及刚出的 Anthropic 新工作（还有 Conjecture 等实验室），用无监督方法自动发现模型内部的特征方向；他的演示是用给例子、算质心的方式得到方向。

文本模型是他自己的：从 T5 检查点微调成去噪自编码器，编码器-解码器 Transformer 加了一些改动，编码器后接池化层得到 Embedding，解码器里有一种特殊的门控层从 Embedding 读取信息。读 OpenAI Embedding 时只训练那个线性适配器层，解码器不变。他当场宣布这些模型在 Hugging Face 上开源，并配有一个 Colab 笔记本，可做插值和特征解读。图像模型是 Kakao Brain 的 Karlo（unCLIP 模型，类似 DALL·E 2 的训练方式，用扩散模型把 CLIP Embedding 还原成图像）。

他的结论是：面对复杂的模型和难以理解的数据，把它们变成能“拿在手里”、能看到、能直接操作的东西，能帮我们更深地理解模型怎么工作、怎么改进。他引用 Bret Victor：思考媒介的目的，是把思想带到头脑之外，以能被感官看见、被身体操纵的形式表示概念，这样媒介就成了心智的延伸。

21. Brittany Walker（CRV）主持，Chris White（Prefect）、Bryan Bischof（Hex）：公司怎样转向 AI

直播位置 4:11:40–4:47:12 · The AI Pivot: Fireside chat with Chris White of Prefect & Bryan Bischof of Hex

Brittany 是早期风投 CRV 的 principal，主要投种子轮和 A 轮。Chris 是 Prefect 的 CTO，Prefect 做工作流编排的开发工具和托管编排服务；他是数学博士，研究非凸优化，后来做数据科学，再转到开发工具。Bryan 在 Hex 负责 AI，Hex 是数据科学 notebook 平台；他也是数学博士，做了约十年数据科学和机器学习。

为什么决定投入 AI

Chris 给了几个理由：Prefect 的用户主要是数据工程师和数据科学家，他们判断语义搜索、检索、摘要这类 AI 场景很大程度是数据驱动的，想在“人们怎么把这些东西投产”的讨论里有一席之地，比如在向量数据库之间搬数据有没有新的 ETL 问题；他把生产中的 AI 看成一个昂贵、脆弱、不确定的远程 API，那就是一个数据 API，编排经验可以迁移；还有就是好玩，想公开地学习，于是开了一个新仓库 Marvin（Jason 前一场提到过）。

Bryan 说数据科学处在商业判断、创造力和有时很难的编程之间，能让人释放更多创造力和商业判断是很少见的机会，大多数数据人最不喜欢的部分是记 matplotlib 语法。而且任何不集成 AI 的数据平台都是在自取灭亡，这很快会成为标配。

怎么决定做什么

Chris 说 Marvin 的成功标准是看人们怎么试验 LLM、直接和用户聊，他们的 AI 负责人每天至少和用户通话几次。核心产品方面，他喜欢按失败模式选工具：工具失败时能不能快速恢复、理解原因。所以 AI 功能也围绕这一点，比如在仪表盘上显示错误摘要方便快速分诊，衡量标准很容易量化：用户多快到达想去的页面、多快调试好工作流。

Bryan 的团队章程很简单：让使用 Hex 感觉像魔法。例子是 explode 功能：把一个由很多 CTE（公共表表达式，SQL 里的 WITH 子句）组成的超长 SQL 拆成多个在平台里串联的单元格。他说这做起来很简单，但他想要这个功能想了八年。

人员上，Hex 一开始只有一个人做了原型，显示出潜力后扩到几个人；现在路线图够 20 个工程师做，团队保持在 5 人左右，他说这是刻意的，残酷的优先级排序是优势。Prefect 招了一个叫 Adam 的人负责大部分 AI 工作，公司里任何想参与的人都可以加入，有一位工程师因此实际上转到了 Adam 的团队。

怎么衡量成功

Chris 说他们已经达到了成功标准：核心产品里加了一点 AI，用户获得价值的时间明显缩短；同时一直在参与公司们早期讨论如何把 AI 投产的对话。Bryan 说看用户多频繁地用 Magic（Hex 的 AI 功能集合），如果每个单元格、每个项目都在用，说明做对了；为此要让平台的每个部分都有 Magic 能帮上忙。

自建还是购买

Bryan 入职时（2 月）问的第一个问题就是评测怎么做，他说那时还没人谈评测，但他在机器学习领域做了很久，知道目标框定和评测做不好就没希望。那时也还没有 25 家评测创业公司（现在超过 25 家了）。他们选择自建评测，理由是评测要尽量贴近生产，能用生产环境就用，这需要深入平台的钩子，以他们的速度，外部 SaaS 很难做到。向量数据库则选择不自建：他做了六七年向量语义搜索，用过 FAISS 和早期的 Pinecone，觉得很复杂，最后用 LanceDB 做了一个高度定制、契合他们场景的向量检索实现，因为 RAG 流水线的效果取决于它。他的原则是看复杂度值不值得。

Chris 也绝不会自建向量数据库，他们试过 Chroma 和 LanceDB，但还没用于生产。他观察到的投产路径是：先在框架里大量试验，然后把用到的提示词拿出来直接用，中间不再有框架；到那时就只是和一个 API 交互，而这方面的工具已经很多。所以他们的决策是看现有开发工具能否支持它被观察和监控，结论是够了，全部自建。

希望有人做的工具

Bryan 说很难卖给他评测平台，但可能卖给他 LLM 可观测性平台（他声明自己是 Weights & Biases 校友，有偏见）。他在关注 Ironclad 开源的 Rivet，觉得它做实验和迭代的方式很好，如果能和可观测性结合好他会很兴奋。Chris 希望更多关注机器对机器的那一层：输入总是自然语言字符串，但输出应该是有保证的类型，比如函数调用，这是把 AI 集成进后端流程的一步。

遇到的挑战

Chris 说工具和投产方面没有问题，问题在文化：一开始大家什么都想让 AI 做，监控、全部功能，他们得往回收，就聚焦在减少用户摩擦上；克制热情是最大的挑战，至今仍在。Bryan 的版本类似：工程师本来就不擅长估时间，AI 功能更严重，最初几个实验很快就显得很有希望，但长尾比一般工程还长，从“几个例子能跑”到“完全可靠”的路特别长。

怎么在过程中测试：Bryan 说还是评测，尽量把需求写成评测。有人说“要是 Magic 能做 X 就好了”，他会追问：对这个提示你期望它做什么？他用的标尺是“一个对公司几乎没有背景的新数据科学家能不能做到”，以此划定可行的边界。

独立品牌与融入产品

Brittany 说她观察到这一波里很多公司在核心产品旁边另起一个品牌。Chris 说他们的原则是用最小的承诺最大化学习：开一个开源仓库，需要维护，但代价不高；没人注意也没关系，至少学会了怎么写对接各种 LLM 的 API；结果它火了，他们认识了很多做 AI 和数据相关工作的人。核心产品方面，Prefect 是通用编排器，用例范围理论上无限，帮人写任意代码不是他们能胜过 OpenAI 或 GitHub 的地方。他们一开始试过把 AI 直接放进 SDK，很快发现范围太大，用户不如自己做，于是只做边际上的增量功能。

Bryan 说 Magic 不是独立产品，是对 Hex 的增强，是一组让产品更好用的功能，这让设计决策变得容易：不能分散对核心体验的注意力。他讲了一个故事：有一个 sprint 他们做了一个叫 Crystal Ball 的东西，能力很强、体验很好、设计很漂亮，但它把用户从 Hex 的核心体验里拉走了。CEO 指出这是在把 Magic 分裂成自己的小生态，他们就把 Crystal Ball 砍掉了，因为每个 Hex 用户都应该能受益于 Magic。

发布和上线后的度量

Bryan 说他们先做私测，再尽快扩到公测，早期找的是投入度高、能接受 AI 工具局限（随机性）的用户，而且数据科学工作流本身就复杂，所以先找技术水平高的，再逐步覆盖技术能力较弱的用户。Chris 说 Marvin 就是玩够了、觉得满意，点了公开、发了条推特；核心产品的客户很多是金融服务和医疗的大企业，安全意识很强，所以 AI 功能必须明确选择开启，并有提示说明点了之后会把少量数据发给第三方提供商。

上线后的度量，Bryan 说他听说“吃自己的狗粮”有个更友好的说法叫“喝自己的香槟”，他每天全天都在用 Magic；分析产品表现本来就要用数据科学，所以他在用 Magic 分析 Magic，“有一种衔尾蛇的感觉”。Chris 说早期还是纯字符串输入输出时，他们写测试用 LLM 做语义比较，有问题但也管用；Marvin 转向保证类型的输出后，测试容易多了，这也是他总在讲“类型化握手”的原因之一。

关于模型随时间变化，Bryan 提到 6 月有一篇引起轰动的论文说模型在悄悄变差，他说在生产里做事的人早就知道了：新端点上线第一天他的评测就挂了，他甚至还没切过去。他的建议是想清楚你在乎什么性能，把用例归结成传统的评估方法，不需要潜在距离分布和 KL 散度，BLEU 这类相似度分数对 LLM 输出不好用早就是共识；把任务归结成二元的是或否，再跑评测。对“我的任务太复杂没法判断对错”的人，他的回答是再努力一点，他评的任务也很微妙复杂，但一直找下去总能找到。他也说类型检查、可组合性这些观点，ML 领域的人已经讲了五年，只是对现在谈评测的一些人来说是新的。Chris 补充，Bryan 描述的是一个高度不确定、动态的实验工作流，这就是 Prefect 核心产品服务的对象，他更感兴趣的是这类工作流的结构。

互问与“今日暴论”

  • Bryan 问：做 Agent 流水线（越来越像 DAG 和结构化的请求响应链）时，你的领域有什么是每个 AI 工程师都该知道的？Chris 说是想清楚失败模式：失控的进程、尽早用可观测性层抓住输入输出里的异常，越早接好越好；缓存“这是我唯一一次这么说”是你的朋友，但也是万恶之源，要平衡；尤其是会立即执行返回代码的场景，监控层很关键。
  • Chris 问幻觉怎么处理。Bryan 说他找参考资料时发现大家的建议基本是“把 RAG 做得更狠”，回头看自己确实也是这么解决的：Magic 的幻觉减少靠的是更仔细地设计检索，而那个检索机制不在任何书里，包括他刚出版的书。
  • Chris 的暴论：别再做聊天界面了。聊天是产品，AI 是工具，应该改进机器对机器的接口，让开发者更直接地用 AI。
  • Bryan 的暴论（他先道歉说有点刻薄）：你在构建 AI 能力的路上，很多工作会无比枯燥，要做好准备。能力令人兴奋，但 ML 一直如此，过程很乏味，前面有大量数据工程工作，人们还没意识到它有多重要。
