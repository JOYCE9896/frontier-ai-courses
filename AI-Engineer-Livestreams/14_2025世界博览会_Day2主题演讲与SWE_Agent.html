02. Logan Kilpatrick（Google DeepMind）：Gemini 2.5 Pro 06-05 发布，一年的进展和接下来

直播位置 0:20:17–0:32:14 · 英文原题 Gemini 2.5 Pro 06-05 Launch - A Year of Shipping and What Comes Next

Logan 是 Google DeepMind 的产品负责人，管开发者相关的事情。他把演讲分成三块：新模型发布、回顾一年进展、接下来在模型、Gemini App 和开发者平台上要做什么。

新模型

当天发布了新的 Gemini 2.5 Pro（版本号 06-05），他说希望这是 2.5 Pro 的最后一次更新。他提到它在 Aider（一个代码编辑基准）和 HLE（Humanity's Last Exam，一个高难度综合问答基准）上达到 SOTA，并且补上了开发者对前几个版本反馈的不足。他说 2.5 Pro 无论在内部还是开发者眼里都是 Gemini 的转折点。可以在 ai.dev 和 Gemini App 里试用。

一年的进展和组织上的原因

  • 他引用 Sundar Pichai 在 Google I/O 上的一页幻灯片，说过去 12 个月像是塞进了 10 年的 Gemini 进展。DeepMind 在科学、机器人等方向的研究最后都汇入主线 Gemini 模型，例如 AlphaProof、AlphaGeometry 这些定制模型的经验提升了主线模型在相应领域的表现。
  • 采用速度：同样引用 Sundar 的数据，Google 服务器处理的 AI 推理量一年间增长了 50 倍。
  • 他认为一个不太好玩但重要的原因是组织调整：2023 年 Google 把分散的 AI 研究团队合并，让 DeepMind 除了做基础研究还要做模型并交付给 Google 和外部；2025 年初又把产品团队并进 DeepMind，现在 DeepMind 同时做研究、模型和产品（消费端的 Gemini App，开发者端的 Gemini API）。他总结的公式是：把最好的人放在一起，找到基础设施上的优势，然后发布。
  • 视频模型 Veo 很受欢迎，他说它“把 TPU 都烧了”。

接下来

  • Gemini App 的目标是做通用助手。他的观察是过去串起 Google 各产品的只有 Google 账号，但账号本身没什么状态；现在 Gemini 正在成为把 Google 所有产品连起来的那条线。他最期待的趋势是主动性（proactivity），现在多数 AI 产品还是要用户自己去做所有事。App 的问题请找 Josh（Gemini App 负责人），他说不要 @ 他。
  • 模型方面：Gemini 从一开始就是单一多模态模型，I/O 上发布了原生音频能力（TTS、可以直接对话），支撑 Project Astra 和 Gemini Live，方向是“全模态”（omnimodal）模型，希望把视频也并入主线模型；扩散（diffusion）语言模型的早期实验能做到很高的每秒 token 数，但还是研究方向。
  • “默认就是 Agent”：过去他把模型看作 token 进 token 出的东西，生态里有大量脚手架（scaffolding，围绕模型搭的提示、工具调用、流程代码）。他觉得模型本身越来越像一个系统，很多脚手架的工作会被吸收进推理（reasoning）这一步，这对做产品的人有影响。
  • 会有更多小模型，也会有大模型。无限上下文：他认为现在的范式做不到，注意力机制无法这样扩展，需要新的创新。模型产品由 Tulsee 负责。
  • 开发者平台：Gemini Embedding 模型（他说是 SOTA）未来几周更大范围开放，嵌入（Embedding，把文本变成向量以便检索）是多数 RAG 应用的基础；一个专门的 Deep Research API；Veo 3 和 Imagen 4 进入 API；AI Studio 会明确定位为开发者平台，减少消费产品的感觉，并内置 Agent，可能把 Jules 等编程 Agent 原生放进来。

03. Jack Rae（Google DeepMind）：Gemini 的思考能力是怎么来的

直播位置 0:32:23–0:50:54 · 英文原题 Thinking Deeper in Gemini

Jack Rae 是 Google DeepMind 的首席研究科学家，Gemini 里“思考”（thinking）方向的技术负责人。开场幻灯片没出来，耽误了一两分钟。他的结构是三段：研究动机、思考在 Gemini 里是什么以及对开发者有什么用、接下来做什么。

进步来自找到瓶颈

他的论点是，AI 的进步往往来自识别当下最关键的瓶颈，然后解决它。他按时间讲了几个例子：

  • 1948 年 Claude Shannon 在《通信的数学理论》里做了一个二元语法（bigram）语言模型，用的是手工统计的词频表，他觉得如果能把这种方法放大会更好。瓶颈是数据少、统计方法原始，解决它需要人类知识的数字化和现代计算机。
  • 2000 年代 Google 的同事（如 Jeff Dean）在万亿级 token 上训练 n-gram 模型，支撑当时最好的语音识别和翻译。瓶颈是上下文很短，因为存储成本随上下文长度指数增长。
  • 2010 年前后出现循环神经网络（RNN）语言模型，把过去压缩进网络状态，能建模句子乃至段落。几年后发现新瓶颈：状态大小固定，信息会丢。
  • 解决办法是把过去所有的向量都留着，用注意力（attention）按需汇总，由此有了注意力机制和 Transformer。
  • 到 2024 年，大模型已经是很强的通用对话 Agent，但它们被训练成立即回答。也就是说，从问题到答案，模型在测试时（test time）花的计算量是固定的。

测试时计算和思考

测试时计算（test-time compute）指模型在回答你这个具体问题时花的计算。一次前向计算里，每层有并行计算、层与层之间有迭代计算，总量固定。把模型做大可以多一点计算，但用户可能希望在难题上多花千倍、百万倍，在简单问题上少花，而且由模型自己动态决定。这就是“思考”的动机。

机制上，Gemini 在给出最终答案前插入一个思考阶段，模型可以先输出额外的文本。这相当于多了一个计算循环，可以循环几千到几万次，次数由模型自己学着决定。训练方法是强化学习（RL）：预训练之后，让模型做大量任务，按是否做对给正负奖励。他说这个信号很模糊，团队当初并不确定它能通过整个思考循环反向传播出有用的行为，也不确定该给推理阶段加多少结构。

他展示了一个早期 RL 实验的“历史文物”：一道整数预测类的数学题，模型在思考里先提出假设、验证、发现公式不成立、否定自己、换一种方法。他说团队当时真的被震到了。现在模型学会的策略包括拆解问题、探索多个解、分段写代码再拼起来、做中间计算和调用工具。

对开发者的意义

  • 能力：测试时计算的扩展可以叠加在预训练（扩数据和模型规模）和后训练（扩人类反馈的质量和多样性）之上，效果相乘。他展示了一张图，横轴是对数刻度的测试时计算，纵轴是数学、代码、科学的表现，从去年 12 月不带思考的 2.0 Flash Experimental 到 2.5 Pro，性能随测试时计算一起上升。
  • 成本与质量的调节：以前只能在几个离散的模型尺寸之间选，现在有连续的思考预算（thinking budget），2.5 系列的 Flash 和 Pro 都支持，可以按任务细调花多少钱换多少能力。

接下来

  • 效率：他承认能找到模型“想太多”的例子，目标是让思考自适应，开发者不用花太多精力去调。
  • 更深的思考：Deep Think，I/O 上宣布、向受信测试者开放，是建立在 2.5 Pro 上的高预算思考模式，用于愿意异步等待更强答案的难题，做法是更深的思维链加上可以相互整合的并行思维链。USAMO（美国数学奥林匹克）上，今年 1 月的最强模型几乎得不了分；2.5 Pro 大约在全部参赛者的第 50 百分位，Deep Think 到第 65 百分位。他放了一段动画：一道代数题里模型从反证法出发，分别探索 Rolle 定理和 Newton 不等式，最后整合出正确证明。
  • 开放式编程：同事让 Gemini 照着 DeepMind 最早的 DQN 论文，“vibe code”出了训练框架、算法甚至一个 Atari 模拟器，能玩部分游戏。他说这类事以前要他和同事花几个月。
  • 他心中的标杆是人脑，举了 Ramanujan 的例子：几乎与数学界隔绝，手里只有一本教材，却从少量问题出发想出大量数学。他希望模型能数据高效，能在百万级甚至更多的推理 token 里积累知识和产物，最终推进人类认知的边界。

04. Manu Goyal（Braintrust）：为什么要做评测

直播位置 0:51:05–0:56:36 · 英文原题 The Importance of Evals

Manu 是 Braintrust 的创始工程师，Braintrust 做评测（Eval）平台。评测指用一组有代表性的样本和打分方法，系统地衡量 AI 应用在真实任务上做得好不好。这是一段带表演性质的短讲。

他用一张小时候玩任天堂 64 的照片开场，说那个男孩对“基于规则、永远重复同样动作”的技术很失望，于是立志做 AI。他后来进入自动驾驶行业，学到的是：调模型、改结构、改损失函数都不够，图像分类准确率从 98% 到 99% 不能直接上路，你需要知道它在真实场景里会不会避让行人、会不会处理路口、守不守法，这些要靠评测。

他的观点：评测的用处超出给 AI 写单元测试、抓回归。没有评测，唯一的信号来自上线，又贵又慢又冒险；有好的评测，你可以在上线前完成 90% 的产品迭代。如果把离线评测的指标也用在线上生产数据上，就能知道哪些线上样本最值得拿来做下一轮迭代。他放了 Kevin Weil、Garry Tan、Mike Krieger、Greg Brockman 谈评测的语录，说这么多人都这么讲，总不至于是骗局。Braintrust 的定位是围绕评测的开发平台：在 playground 里调提示词、记录日志做可观测性，把这些连成数据飞轮。最后他邀请大家去 Golden Gate Ballroom B 的评测分会场。

05. Solomon Hykes（Dagger）：管住编程 Agent 的混乱，发布 container-use

直播位置 0:57:05–1:19:45 · 英文原题 Containing Agent Chaos

Solomon Hykes 是 Docker 的创造者，现在是 Dagger 的 CEO。他一上台就说，十年前几乎同一天，他就是在这个舞台上主持了 DockerCon 2015 的开场。

用编程 Agent 的人都成了平台工程师

Dagger 的社区是平台工程师（platform engineer），他们的工作是让其他开发者高效地构建和发布软件，自己不写那些酷的功能，也很少有人道谢。他对台下用编程 Agent 的人说：欢迎加入平台工程，你们现在的工作是让机器人去写软件，自己花越来越多时间给它们修环境。

他引用 Anthropic 那张 Agent 示意图，把定义改成一句玩笑：Agent 就是一个替人类在循环里把东西搞坏的 LLM。单个编程 Agent 在你电脑上工作，你得盯着一个个批准。想扩成一个团队，现在有两种做法：

  • YOLO 模式：直接跑 10 个，它们共享同一个环境，互相踩脚，“盯着看”的方法马上失效。
  • 全包的云端后台服务：模型、工具、环境、算力、密钥都由对方提供，提 issue 等 PR。他说这些产品不错，前两天就发布了好几个，但出问题时你想“把键盘给我”，或者想在自己机器、自己选的算力和模型上跑，这时就受限了。

他想要的是四件事：后台工作，不用盯每一步；轨道（rails），能预先约束 Agent，告诉它项目上下文、代码风格、怎么构建、怎么测试、用哪个基础镜像、能访问哪些密钥，不然会浪费大量 token 来纠正；需要介入时有高效的方式，介于“盯每个动作”和“等 PR 做代码审查”之间；可选择性，不想绑死在某一家，因为市场每天都有新东西。对应到环境的属性就是：隔离、可定制、多人协作、开放。

他说技术已经有了，容器和 git 都被低估了，大家习惯的是为人设计的第一代工具。很多人在用 git worktree（同一仓库的多个工作目录）拼凑并行 Agent。他们的方案叫 container use，对应 computer use、browser use 的说法，让 Agent 用容器创建环境并在里面工作。他强调这和沙箱（sandbox，把代码放在隔离环境里执行）不同：沙箱是安全地执行 Agent 的输出，container use 是 Agent 整个开发过程都在容器里。

现场演示

  • 他强调 container use 本身不带 Agent，它提供的是能接到任何编程 Agent 上的便携环境，Claude Code、Codex、IDE 里的、命令行的、CI 里的都行。
  • 他在空目录里用 Claude Code（他给跳过所有权限确认的参数起了个别名，说自己老记不住），让它做一个项目主页，用 Go 写 Web 应用并运行。Claude Code 通过 MCP（Model Context Protocol，让模型调用外部工具的标准接口）接入 container use，于是能给自己创建环境、在里面改文件、构建、测试、运行。每个动作都在临时容器里执行，然后快照返回。
  • 他的工作目录没有被污染。文件状态和容器状态以特殊 git 对象的形式保存在仓库旁边，都在本地。
  • 命令行工具叫 cu，可以列出环境（新环境有个随机名字），可以打开终端看到 Agent 看到的一切，包括 Agent 给自己配的 Go 版本。密钥可以从 1Password 直接接入，他说不想用 AI 公司的密码管理器，但团队不让他现场演示这个。
  • 因为会场网络不可靠，他的环境实际跑在大约一英里外他家地下室的服务器上，文件上下行都是无感的。

08. Scott Wu（Cognition）：Devin 2.0 与软件工程 Agent 的“摩尔定律”

直播位置 2:29:00–2:45:08 · 英文原题 Devin 2.0 and the Future of SWE

Scott Wu 是 Cognition 的 CEO，Devin 是他们的自主编程 Agent。他说一年前就在这个大会上讲过，并开玩笑说这种大会应该每两个月开一次。

AI Agent 的摩尔定律

衡量 Agent 能力的一个办法是看它能不间断工作多久，直到需要人介入。GPT-3 大概写几个词就会跑偏，之后每代都更好。他说一般任务上这个长度大约每 7 个月翻一倍，代码上更快，大约每 70 天翻一倍，一年 4 到 6 次，也就是每年 16 到 64 倍。他说这和他们过去几年看到的大致相符：18 个月前代码领域唯一有产品市场契合（PMF）的形态只有 Tab 补全，现在已经是能独立完成任务的 AI 工程师。

他的核心观点：什么是对的交互界面、什么是最重要的能力、瓶颈在哪，这些问题的答案每两三个月就会变，因为每升一级，遇到的问题都不一样。接着他按时间讲 Devin 经历的几级：

一级一级往上走

  • 2023 年底起步时，“Agent”这个概念几乎还不存在。
  • 大约一年前：重复性迁移。比如 JavaScript 转 TypeScript、升级 Angular 版本、换 Java 版本。步骤清楚但不能写成确定性程序，要对上万个文件一个个做。当时这是唯一能稳定信任 Agent 做的事，也恰好是人最烦的事。要解决的主要是指令遵循，他们做了 Playbooks，把步骤写清楚让 Devin 一步步执行；还做了知识/记忆系统，记住人类给的反馈，在之后的任务里用上，这部分后来重写了很多次。
  • 去年夏末到秋天：相对独立的小 bug 和小功能，像给实习生的活，例如“在仓库选择下拉框里把已选中的放到最上面”。通常只改一两个文件，但仍然要能配置仓库、跑 lint、跑 CI（持续集成，提交代码后自动跑的构建和测试）。他们做了提前配置仓库并生成快照的能力，可以重载、回滚，在干净的远程虚拟机里跑 CI 和 linter。这时 Devin 开始像一个初级搭档。
  • 秋天之后：更宽的 bug 和需求，要跨文件诊断，改动常有几百行。这里除了把代码当文本，还要把它当成层级结构：调用层级、语言服务器（language server）、git 提交历史。这时可以直接在 Slack 里 @ Devin 让它处理 issue，他们也在这个阶段正式开放（GA）。重点是对代码库的理解和规划。
  • 今年春天：任务更难时，人自己在派任务的那一刻也不知道到底要做什么，例如“这个函数慢，profile 一下看看”。两三行提示不够了。他们发布了 DeepWiki，起因是 Devin 内部本来就有一份代码库的表示，人看了也有用；还有代码库搜索问答。工作流变成先和 Agent 一起探索代码库、问几个问题，再放它去做。Devin 2.0 的 IDE 内体验也是这个思路：前 10% 到 20% 紧密跟着，剩下 80% 到 90% 让它自己做。
  • 现在（6 月）：清空 backlog，一次交给它很多任务。这要集成 Linear、Jira，要能界定任务范围，判断什么时候该找人确认，甚至判断该改哪个仓库。需要两样东西：可靠的置信度判断（确定就执行，不确定就求助）；以及异步测试，Agent 要能在本地跑代码、知道测什么、看什么。
  • 再往后是整个项目，然后是项目之后的东西。

他的结论是：从远处看每次翻倍都一样，实际上每次翻倍都是不同的问题。Tab 补全时代只是文本问题，现在要考虑在 Linear 和 Slack 里怎样与人协作、怎样接受反馈和引导、怎样帮人规划，以及 Devin 怎样自己测试、调试、跑对的 shell 命令拿反馈。他预计未来 12 个月还会有 16 到 64 倍。

  • 他先在 Linear 里列任务。第一步是加测试，让并行 Agent 有办法知道自己做对了没有；用“多种变体”的方式同时让一个用 Jest、一个用 Playwright 写测试，比较覆盖率。然后并行做功能：加到 Google 日历的链接、点击描述时用 Gemini 生成摘要，还有平时总被搁置的可访问性审计和 Lighthouse 分数优化。

  • 日历按钮那个任务第一次测试没过，Jules 改了之后通过。可访问性审计他是在模拟手机视图里发起的，说明也可以在手机上做。

建议

  • 并行的前提是清楚定义成功，因为没人想整天审 PR。开始前先想好怎样轻松验证结果，并和 Agent 约定，例如“看到 X 之前不要停”。结尾要有可靠的合并和测试框架。

四个阶段

  • 代码补全：开发者在状态里打字，Copilot 建议下一行、下一个代码块、函数甚至类。
  • Chat：先有 Ask 模式，问问题或生成单个文件；然后是 Edit 模式，由人驱动它改多个文件，比如改一个网页就涉及 HTML、CSS、JavaScript 三个文件。

演示一：IDE 里的 Agent 模式

他先加了一个针对 API 端点的指令文件（instruction file），给 Copilot 额外说明怎么写。他说 Agent 模式也许能自己推断出来，但“不要对 Copilot 搞被动攻击”，重要的信息就直接告诉它。然后他让 Copilot 创建“列出所有出版社”和“按 ID 获取出版社”两个端点、写测试、确保测试全过。Copilot 先说明计划，然后搜索代码库、找已有的路由、创建 publishers 文件、写测试、运行。四个测试一次全过，他说本来希望它失败一次好展示自我修复。

他强调每处改动都有 Keep 和 Undo 按钮，还有历史记录便于来回迭代。他的观点是 AI 不改变 DevOps 的基本面：以前代码有的是自己写的、有的是从 Stack Overflow 复制来改的，所以才有代码审查、linter、安全检查，引入 AI 后这些照样要做，开发者仍然说了算。

演示二：Coding Agent

  • 他在一个 issue（“添加编辑和删除端点”）上把负责人指派给 Copilot，issue 上出现一对小眼睛表示它在工作，随即生成一个新的 PR，Copilot 用它来汇报进度。点 View session 可以看到它正在启动开发环境。
  • 运行位置是 GitHub Actions（GitHub 的自动化平台），可以用一个专门的 copilot-setup-steps 工作流配置环境，比如安装 Node、Python 和依赖库。
  • 默认不能访问任何外部资源，不能上网，不能调外部服务；需要的话可以配置 MCP 服务器，或在防火墙上开口子。环境是临时的，用完就删。
  • 它不能自动触发仓库里的其他工作流（比如单元测试、端到端测试），要人点同意才跑。它开的 PR 是草稿状态，必须有人审。

  • 它新建的分支叫 copilot/fix-3，3 是 issue 编号，Copilot 只对这个分支有写权限。这个分支和普通分支一样可以拉到本地检查。

他说 GitHub 的原则是“用 GitHub 构建 GitHub”，Coding Agent 本身就是在 Coding Agent 帮助下做出来的，在它自己的代码库里是提交最多的贡献者之一，除了新功能也处理了不少技术债。他认为技术债和永远做不完的 backlog 是 Coding Agent 最能发挥的地方。

12. Boris Cherny（Anthropic）：Claude Code 与 Agent 式编程的演变

直播位置 5:13:45–5:31:35 · 英文原题 Claude Code & the evolution of Agentic Coding

午休后专场继续，主持人说专场一般不做问答，这一场破例留了提问。Boris Cherny 是 Anthropic 的技术人员，Claude Code 的创造者。台下几乎所有人都用过 Claude Code，所以他决定先拉远讲历史，再拉近讲用法。

他的总纲：模型进步是指数级的，写代码越来越好，产品却跟不上；他们觉得能为这么强的编程模型做的产品还有很多，自己只做了最小的部分，并且有意不预设产品形态，因为他们也不知道对的形态是什么。安装方式是 npm 安装；他说前一天起 Claude Pro 订阅也能用，Max 订阅也支持。

编程界面的历史

  • 1930 到 40 年代是接线板，没有软件这个概念；1950 年代有了打孔卡。他的祖父是苏联最早的程序员之一，他母亲小时候会在祖父带回家的成摞打孔卡上用蜡笔画画。
  • 语言层面：汇编、COBOL、有类型的语言、C++，90 年代初出现 Haskell 家族、JavaScript、Java、Python 等。他觉得今天的语言眯着眼看都差不多，写 TypeScript 像写 Rust，像写 Swift，像写 Go，抽象在收敛。
  • 界面层面：IBM 029 打孔机算当时的“MacBook”；第一个文本编辑器 ed 是 Ken Thompson 在贝尔实验室写的，今天 Mac 上还能打开，没有光标、没有回滚、几乎什么都没有，因为它是为把程序打印到纸上的电传打字机设计的；Vim 和 Emacs；1980 年的 Smalltalk-80 是最早的图形化编程界面之一，那时就有能用的热重载，他说今天在 React 里配热重载还很费劲；1991 年 Visual Basic 把图形化编程带到主流；Eclipse 把基于静态分析的代码提示带到主流，也是第一个大的 IDE 第三方生态；Copilot 带来单行再到多行的 AI 补全；他认为 Devin 是第一个把“用自然语言编程”带到主流的产品。
  • 验证方式也在变：从人工调试、看输出，到模糊测试（fuzzing）、漏洞测试、Netflix 的混沌测试这类概率性验证。

Claude Code 的做法

他说语言已经趋于平稳，但模型和编程界面都在指数增长。Claude Code 的思路是从终端开始，在你还能保持高效的前提下，给你尽可能底层地接触模型的方式，不放花哨的 UI，不加挡路的脚手架。一部分原因是 Anthropic 是模型公司，希望大家直接体验模型；另一部分是他们真的不知道对的界面是什么，所以从简单开始。他墙上贴着装裱好的 The Bitter Lesson（Rich Sutton 的文章，大意是更通用、更依赖算力的方法最终胜出），他说更通用的模型总会赢，模型周边的东西也一样。

  • 终端：任何终端都能跑，iTerm2、WSL、SSH、tmux、VS Code 和 Cursor 的内置终端。
  • IDE 里运行时多做一点：diff 显示在 IDE 里，并读取 IDE 的诊断信息。他说这比不上 Cursor、Windsurf 打磨得好，他自己每天也用这些产品，Claude Code 只是做了让你直接体验模型所需的最少部分。
  • GitHub：几周前发布，在 Claude Code 里运行 /install-github-app，选仓库，就能在任何仓库里用 Claude。运行在你自己的计算资源上，数据不经过 Anthropic，几分钟就能配好。
  • SDK：最极端的形态，用 claude -p 以编程方式调用，自己做集成。他举自己的例子：排查线上事故时把 GCP 日志通过管道传给 claude -p，再用 jq 处理结果，把模型当 Unix 工具用。他说这个方向大概只被探索了 10%。

使用技巧

  • 新手先从代码库问答开始。Anthropic 每个工程师入职第一天就学 Claude Code，入职上手时间从两三周缩短到大约两天，他也不再被问问题。他每周一站会前会问 Claude“我这周发布了什么”，它会去读 git 提交。
  • 教 Claude 用你的工具：给它 bash 工具和 MCP 工具。他常说的一句是：运行某个 CLI 的 --help，把学到的写进 CLAUDE.md，Claude 就会用了，不需要像 Emacs、Eclipse、VS Code 那样写插件。工具成组或需要流式等复杂功能时再用 MCP。
  • 先探索、做计划、给他看过再写代码。可以让它使用扩展思考，但他说在上下文里已经有东西时效果最好：先用工具把信息拉进上下文，再思考；一上来就思考多半是浪费 token。
  • 测试驱动开发（TDD，先写测试再写实现）：他说自己以前很难坚持，现在因为是模型在做，效果很好。做法是让 Claude 先写测试，明确告诉它测试现在不会通过、不要去跑，提交；再写代码，提交。更一般的原则是给 Claude 一个可以迭代的目标：单元测试、集成测试、iOS 模拟器截图、Puppeteer 截图。他们甚至教 Claude 用 3D 打印机，配一个摄像头让它看到成品。能看到输出并迭代，第一版一般，第二三版就挺好。
  • 当天发布 Plan 模式：按 Shift+Tab 切换，Claude 只做计划、等待批准，不会直接动手。需要重启 Claude Code 才能拿到更新。
  • 给更多上下文：仓库根目录放 CLAUDE.md，子目录里的按需加载，home 目录里也可以放；在 .claude/commands 目录放 Markdown 文件就成了斜杠命令，适合可复用的工作流；输入 # 可以让 Claude 记住某件事，并让你选写进哪一份记忆。他说记忆这块的界面还很粗糙，是第一个能用的版本，希望听到反馈。

问答

只剩一分钟，主持人念了 Slack 上的一个问题：委派得越来越多，同时开 10 个 Claude 各跑 10 分钟，该怎么用？他说很多重度用户都在“多 Claude”：开几个终端标签，用代码库的几份副本或同一仓库的不同 worktree 并行；用 GitHub Actions 更容易，直接起一批 action。多数情况下不需要它们之间协调；如果需要，最好的办法是让它们写同一个 Markdown 文件。

13. Robert Brennan（All Hands AI）：软件开发 Agent，哪些有用哪些没用

直播位置 5:32:25–5:49:11 · 英文原题 Software Dev Agents: What Works & What Doesn't

Robert Brennan 做开源开发工具十多年，他和团队做了开源软件开发 Agent OpenHands（原名 OpenDevin）。

写代码会消失，软件工程不会

他想说服大家：写代码这件事会大幅减少，但工程师拿工资是因为批判性地思考问题。AI 擅长“写代码、跑代码、再写再跑”的内循环，不擅长需要理解用户、考虑业务目标和长期架构的大问题，那是工程师的位置。做对的话，我们会少花时间凑在 IDE 前，多花时间想用户到底要什么。

他说“Agent”这个词的含义在漂移，核心是 agency，在真实世界采取行动。软件工程师的主要工具是代码编辑器、终端和浏览器（查文档、从 Stack Overflow 复制代码），给 Agent 的也就是这三样。从 Copilot 补全几行，到能自己走几步的 AI IDE，再到 Devin、OpenHands 这种给一两句话就自己工作 5 到 15 分钟的 Agent，越来越异步，也越来越强，可以一次派出多个。

Agent 的内部

Agent 就是 LLM 和外部世界之间的循环：每一步问 LLM 下一步要做什么（读文件、改文件、跑命令、看网页），去执行，把输出塞回给 LLM。他逐个讲了工具里的难点：

  • 编辑器：最朴素的做法是让 LLM 重写整个文件，几千行改一行会浪费大量 token，所以现在多用查找替换或基于 diff 的编辑；还常提供抽象语法树（AST）之类的方式帮助导航代码库。
  • 终端：长时间没有输出的命令要不要杀？要不要让 LLM 等？怎样并行跑命令、后台跑命令，比如先起服务器再 curl 它？
  • 浏览器：最复杂。直接给 HTML 太贵，里面很多冗余；他们发现给无障碍树（accessibility tree）或转成 Markdown 效果好，内容多时让 LLM 滚动；交互时可以让 LLM 写 JavaScript，或者给一张带编号节点的截图让它说点哪个。他说一个月前有人贡献的改进让网页浏览准确率翻倍，这个方向值得关注。
  • 沙箱：所有 Agent 默认在 Docker 容器里运行，和你的工作站隔开，不会 rm -rf 掉你的主目录。越来越多地给 Agent 第三方 API 权限（GitHub token、AWS 账号），一定要收紧权限，遵循最小权限原则。

最佳实践

  • 从小处开始：一次提交能完成、有清晰完成定义（测试通过、冲突已解决）、你也容易验证的任务。先从琐事开始，比如 PR 上有一个测试挂了、有 lint 错误、有合并冲突。熟悉之后可以给更大的任务。他说他自己和联合创始人、重度用户大约 90% 的代码经过 Agent，只有 10% 的时候要回到 IDE 亲手改。
  • 说清楚要什么，也说清楚怎么做：用哪个框架、要不要 TDD、改哪些文件和函数。这样更准、更快，也省推理成本。
  • 代码变便宜了，可以扔掉。他在上班路上用语音告诉 OpenHands 做某件事，到公司时 PR 已经在等他，一半直接扔掉，一半很好就合并。方向接近就在同一对话里继续迭代；偏得太远就扔掉，带着学到的东西换个提示重来。他说要练出“敢扔”的肌肉记忆。
  • 他认为最重要的一条：必须审 AI 写的代码。他见过不止一个组织以为能靠 vibe coding 做出生产应用、自动合并 AI 的产出，结果技术债暴涨、到处是重复代码。要审，也要拉到本地或临时环境里跑一下。原则是“信任但要验证”，人必须在回路里。
  • 他们自己的教训：早期 OpenHands 开的 PR 归属于 OpenHands 账号，带来两个问题。一是触发它的人可以自己批准，绕过了“需要第二个人审”的流程；二是这些 PR 没人认领，测试挂了没人管，合并后出问题也找不到负责人。现在用 OpenHands 开的 PR 上显示的是你的头像，你对合并和后续问题负责。

适合第一天就交给 Agent 的事

  • 解决合并冲突：他最喜欢的用法，OpenHands 代码库变化快，他几乎每个 PR 都有冲突，@OpenHands 让它修，他说 99% 能搞定。
  • 处理 PR 评审意见：别人已经写清楚要改什么，直接让它“照那个人说的做”。他举例说前端同事提了一堆他不熟的 React 术语，OpenHands 都懂，完全按要求改好。
  • 修小 bug：例如一个本该是数字类型的输入框写成了文本，他在 Slack 里直接 @OpenHands，不用打开 IDE。
  • 基础设施改动：Terraform 这类冷门语法 LLM 往往知道，不知道就用浏览器查文档；Slack 里出现内存溢出报警，直接让它加内存。
  • 数据库迁移：他自己常忘记加索引、设外键，LLM 在这方面很守最佳实践。
  • 修失败的测试、扩大测试覆盖率：后者很安全，只要测试通过一般就能合并。
  • 从零做应用：生产代码不要 vibe code，但内部小工具可以，比如他们做了一个调试 OpenHands 轨迹的 Web 应用，内部用，不必逐行审。

14. Josh Albrecht（Imbue）：走出原型，Sculptor 的设计思路

直播位置 5:51:30–6:09:34 · 英文原题 Beyond the Prototype

Josh Albrecht 是 Imbue 的 CTO，公司目标是做更稳健、更有用的 AI Agent，目前聚焦软件 Agent，主要产品是 Sculptor，一个实验性的编程 Agent 环境，还在研究预览阶段，功能可能会变。

只做和你的问题相关的部分

他说可以做的东西很多：提升长上下文表现、更便宜更快、更好地解析输出。但他认为这些在未来 3 到 24 个月里会随着模型和 Agent 变好被解决，就像你不会自己写数据库，应该专注于自己业务里真正要紧的那一块。Imbue 选的问题是：这个 diff 有什么问题？Agent 说“我加了 59 行”，你要么逐行看，要么直接合并然后祈祷，两者都不好。他们想提供第三种选择：让另一个 AI 系统来查，有没有竞态条件、是不是把 API key 留在了里面，用 AI 帮人建立对代码的信任。

他对高质量代码的定义来自学术界：看缺陷数量、修一个缺陷要多久、某种技术能抓到多少缺陷。越早发现问题越好，所以 Sculptor 刻意不做 PR 审查工具。它在你刚生成代码、刚改一行时就同步给反馈，人和 Agent 修起来都容易。

预防问题的四个办法

  • 先学习：在 Sculptor 里问问题、让它做调研，了解有哪些现成技术和别人解决类似问题的方法，免得重复造轮子。
  • 先计划：演示里让 Agent 实现一个 Scrabble 求解器，先把系统提示改成“只做计划不写代码”，计划出来后再改系统提示让它写代码。他说直接口头告诉 Agent 也行，但改系统提示约束更强；可以搭出“总是先计划、再写代码、再跑检查”的定制 Agent。
  • 写规格和文档：以前不爱写，因为维护麻烦，但 Agent 读不到你的邮件和 Slack，需要这些上下文。Sculptor 会检测代码和文档是否不一致、规格之间是否互相冲突，降低维护成本。
  • 严格的风格指南：Sculptor 会给出建议，例如“把这个类做成不可变的，避免竞态条件”，来自他们鼓励函数式、不可变风格的风格指南。他们还在写一份专门针对 AI Agent 的风格指南，帮它避开最常犯的错误。

发现问题的三个办法

  • 跑 linter：ruff、mypy、pylint 等。人来修这些小错很烦，AI 修得很好，Sculptor 会自动检测并修复。他现场问谁有 linter、谁的代码库零 lint 错误，只有两个人举手，他说“我们雇你”。所以 Sculptor 会记录 Agent 动手前已有哪些问题、动手后有哪些，至少保证 Agent 不新增问题，即使代码库本来不干净。
  • 写测试并运行。以前不写测试是因为费劲，现在生成测试很容易，可以让 Agent 写一堆测试、扔掉不过的、留下其余的。他引用 Google 的说法“如果你喜欢它，就该给它加个测试”，有了 Agent 更要紧，因为你不想让它悄悄改变系统行为。怎样写好测试：
    • 用函数式风格写代码，即没有副作用，这样容易验证；不要让测试碰到真实的 Gmail 环境之类，一个失误就可能删光邮件。
    • 区分快乐路径测试（证明能用，少量就够）和不快乐路径测试（找 bug）。对函数式代码，可以让 LLM 生成成百上千个输入，看输出，再问 LLM“这看起来奇怪吗”，它说奇怪时往往就是 bug，于是得到一个复现 bug 的测试用例。
    • 有时可以把生成的单元测试扔掉。重新生成很便宜，保留太多对你不在乎的行为的测试，以后改行为时会让 LLM 困惑。
    • 重点放在集成测试，从用户角度验证程序可用。先写测试计划（“用户点加入购物车，商品就在购物车里”），再让 AI 写测试，几乎总能写对，这样可以在“含义”这一层工作。
    • 把测试覆盖率当核心指标。如果告诉你改了多少行，同时覆盖率 100%、测试全过、另一个 AI 看过测试认为合理，你点合并时就没那么怕了。
    • 尽量在沙箱里、不带密钥跑测试，减少事故和不稳定的测试。
  • 问 LLM：提交前当前改动有没有问题、要做的事是否合理、当前分支有没有问题、是否违反风格指南或架构文档、规格是否缺细节、规格是否被实现和测试，或任何自定义检查。Sculptor 允许用户加自己的检查，让最佳实践被持续检查。

修复和之后

修复问题他讲得很少，因为比想象中容易。他引用“问题陈述清楚就解决了一半”。对编程 Agent，简单策略就很有效，比如换个 Agent 试一百次；前提是有好的沙箱，才能在成本允许下并行跑很多个，有一个成功就用它。他列了接下来会出现的工具：部署后的调试、日志、追踪、性能分析，AI 自动 QA（在网站上点来点去看用户能否完成任务），从设计稿生成代码，更好的上下文搜索。他希望和做这些工具的人合作，把它们集成进 Sculptor。

15. Eno Reyes（Factory）：用 Agent 几分钟交付生产软件

直播位置 6:10:50–6:26:36 · 英文原题 Ship Production Software in Minutes, Not Months

Eno Reyes 是 Factory 的联合创始人，他说自己两年半前、GPT-3.5 出来时开始做 LLM。Factory 的 Agent 叫 Droid，主要面向企业。

从人驱动到 Agent 驱动的开发

他认为软件开发正从人驱动转向 Agent 驱动。现在流行的做法是拿 20 年前为人逐行写代码设计的工具，往上一层层撒 AI，期待某天出现跃迁，他引用福特那句“如果问人们要什么，他们会说要更快的马”。要让团队把软件生命周期里多数任务交给 Agent，平台需要：直观的任务管理和委派界面；汇集所有工程工具和数据源的集中上下文；稳定产出高质量结果的 Agent；支撑成千上万个 Agent 并行的基础设施。他说团队过去两年一直和大型组织合作往这个方向做。

他说 Karpathy 讲过“英语是新的编程语言”，按 Twitter 上的印象好像什么都能 vibe code 出来，但你没法 vibe code 一个处理全球 5% 银行交易的 Java 7 遗留系统。他把 Agent 比作登山装备，构建生产软件像攀登珠峰，装备让攀登更容易，但仍要靠已有的专业能力。

演示和“上下文”

视频里，Droid 接到任务后先“落地”：用工具搜索代码库、确认 git 分支、查看机器上有什么、看最近的代码改动、读取它和这位用户以及整个组织交互的记忆。然后给出计划，并请用户澄清几个问题。他说我们应该期待 Agent 质疑我们的要求，不要照单全收。拿到答复后它写代码、跑 pre-commit 钩子和 lint，最后开出一个通过 CI 的 PR。

他说 AI 工具的好坏取决于它拿到的上下文。所谓提示工程，很大程度上是在脑中模拟一个只拿到现实世界一小片上下文的“外星智能”。他们分析了几千次 Droid 辅助开发的会话，发现失败多半是因为缺了关键上下文，LLM 能力不足反倒是少数。模型变好会减少失败，但真正的解决办法是把缺的上下文补上：LLM 不知道你早上的站会、临时开的会和白板，但你可以把笔记转写、把照片上传。

规划

他说软件开发最难的部分是想清楚做什么，写代码倒在其次。演示里 Droid 被要求查找一个新模型发布的最新信息并集成到现有聊天应用里，它用了网页搜索、代码库知识、组织记忆里的产品目标和上周的设计文档，产出一份计划，可以导出到 Notion、Confluence、Jira，无需配置。他说 MCP 很好，但让每个开发者自己装一堆服务器、到处传 API key 并不理想，平台会解决这些。

他举了内部的例子：规划云开发环境相关功能时，他们有三个月的用户访谈转写（Factory 会转写每一次会议），加上一位工程师用 Granola 记的临时会议笔记，一起交给“知识 Droid”。他们没有直接说“帮我规划功能”，问的是“客户反馈里有哪些模式和我们的假设对得上”“现有技术有哪些限制”，得到四五份中间结果，再迭代出最终 PRD。能操作 Linear 和 Jira 的 Droid 把 PRD 拆成路线图：8 张工单，有依赖关系，可以分给 8 个编程 Droid 并行。他的说法是人会从执行者变成编排者。PRD、设计文档、RCA（根因分析）模板、季度路线图、会议转写，在 Agent 原生的公司里都成了 Droid 学习团队思维方式的知识库，记录决策背后的原因对未来的开发者和 Agent 都有用。

站点可靠性（SRE）

他说不会声称今天能完全自动化事故响应，但演示了 Droid 把一个 Sentry 告警变成完整的 RCA 和缓解方案。传统事故响应像拼图，日志、指标、历史、人脑里的知识散落各处；Droid 可以拉取相关日志、过去的事故、Notion 或 Confluence 里的 runbook、Slack 讨论，把几小时的搜寻压到几分钟。有了用户和组织级的记忆，它会逐渐了解团队的响应模式，生成新的 runbook、更新流程。他说看到有团队事故响应时间减半，重复事故减少，因为同样的事第三次出现时 Droid 会提出“也许该根治了”；新人可以直接问 Droid 某件事怎么做。

结尾

他说最好的开发者花在 IDE 里逐行写代码的时间少了很多，他们管理多个 Agent、搭建能超越内循环的模式，转向外循环；最重要的技能是清楚地思考、有效地和人与 AI 沟通。现场扫码注册送 2000 万免费 token。他强调 Factory 是企业平台，关心审计日志、Agent 闯祸时谁负责（比如执行 rm -rf）、所有权和免责条款，认为企业里不该用 YOLO 模式。

16. George Cameron（Artificial Analysis）：AI 前沿的几条趋势线

直播位置 7:15:31–7:32:57 · 英文原题 Trends across the AI Frontier

傍晚的主题演讲由 Laurie Voss 回到台上开场（他把观众分成 A、B、C、D 四队喊了几嗓子，说只是为了让大家醒醒）。George Cameron 是 Artificial Analysis 的联合创始人，这是一家独立 AI 基准测评公司：测模型的智能水平，测 API 端点的速度和价格，测硬件加速器，覆盖语言、视觉、语音、图像和视频生成。网站上免费公开 150 多个模型的数据，另有部分公开的报告和面向企业的订阅。

当前的智能前沿

他们的 Artificial Analysis Intelligence Index 是 7 项评测加权组成的综合指数。当时的排序：o3 第一，紧跟 o4-mini（高推理档），然后是一两周前更新的 DeepSeek R1、Grok 3 mini（高推理档）、Gemini 2.5 Pro、Claude 4 Opus（思考模式）。他的主旨是前沿不止一条，获取智能有代价，不应该总用最聪明的模型。他讲了四条：推理模型、开放权重、成本、速度。

推理模型：话太多

  • 把智能指数和跑完指数所用的输出 token 数画在一起，分成明显两群：非推理模型 token 少、智能较低；推理模型 token 多、智能高，差一个数量级。
  • 跑完指数：GPT-4.1 用了 700 万 token，o4-mini high 用了 7200 万，最“话痨”的 Gemini 2.5 Pro 用了 1.3 亿。
  • 延迟：通过 API 拿到完整回复的中位时间，GPT-4.1 是 4.7 秒，o4-mini high 超过 40 秒，又是 10 倍。他提到 Facebook 关于消费应用延迟与用户流失的研究。
  • 对 Agent 影响更大：一个 Agent 连续调用 30 次模型很常见。每次 10 秒就是 300 秒，5 分钟；每次 1 秒就是 30 秒。客服中心场景 30 秒也许可以接受，5 分钟不行。他建议大家实测这些权衡。

开放权重

开放权重（open weights）指模型权重公开可下载。GPT-4 时代，Llama 65B、Llama 2 70B 和 GPT-4 差距很大；后来 Mixtral、Llama 3.1 405B 等缩小了差距；2024 年底 o1 又拉开；然后 DeepSeek V3 在 12 月 26 日发布（他说毁了他的圣诞假期，得跟家人说要去读论文），1 月 R1 发布。现在开放权重和闭源的差距是有史以来最小的，最近的 R1 更新只差智能指数几分。领先的开放权重模型，无论推理还是非推理，都来自中国实验室：DeepSeek 两类都第一，阿里的 Qwen 3 在推理类第二；Meta 和 NVIDIA（基于 Llama 微调的 Nemotron）也接近。

成本

  • 跑一遍智能指数，o3 花了将近 2000 美元，TechCrunch 还为此写过文章。GPT-4.1 便宜约 30 倍（字幕里对比对象听起来是 o1），GPT-4.1 nano 比 o3 便宜 500 多倍。他说一个 Agent 应用的 30 次调用换成 500 次小模型调用，可能仍比一次 o3 便宜。
  • 他强调不能只看每 token 价格，还要看模型有多啰嗦：推理 token 按输出 token 收费，即使有的实验室把它们藏起来。非推理模型之间的啰嗦程度也差很多。
  • 按智能水平分档看价格趋势：获得 GPT-4 水平智能的成本自 2023 年中下降了 100 多倍；新出现的档位，比如 2024 年底 o1-mini 的水平，几个月内成本就减半。他建议设计应用时想一想“如果成本不是障碍会怎样”，现在不可行的成本结构半年后可能可行。

速度

  • 输出速度（每秒输出 token 数）自 2023 年初大幅提升。2023 年 GPT-4 大约每秒 40 个 token，现在同等智能能做到每秒 300 多个。
  • 原因：模型更稀疏，混合专家（MoE，每个 token 只激活一部分参数）模型越来越多、激活比例越来越小；小模型通过蒸馏（distillation，用大模型的输出训练小模型）变得更聪明；推理软件优化，如 FlashAttention 和投机解码（speculative decoding，用小模型先猜几个 token 再由大模型一次验证）；硬件进步，H100 比 A100 快，他们刚上线 B200 的测试，每秒超过 1000 个输出 token；还有 Cerebras、SambaNova、Groq 等专用加速器。

他们的“house view”：效率在提高，同等智能越来越便宜，但对算力的需求会继续增长，因为模型更大（DeepSeek 总参数 6000 多亿）、对智能的需求无止境、推理模型推理时更耗算力、Agent 一次任务要连续调用几十上百次。这些因素相乘，净效果是算力需求继续上升。

18. Barr Yaron（Amplify Partners）：2025 年 AI 工程现状调查

直播位置 7:38:30–7:50:50 · 英文原题 State of AI Engineering 2025

Barr Yaron 是 Amplify Partners 的投资合伙人，投技术型创始人。她分享 2025 年 AI 工程现状问卷的初步结果，完整报告一周后发布。

谁在填问卷

  • 约 500 人作答，最大群体自称工程师（软件工程师或 AI 工程师），但头衔五花八门。她现场让职位真叫“AI 工程师”的人举手，寥寥无几；职位叫别的、但觉得自己做的事和 AI 工程师一样的人，几乎全场。
  • Google Trends 上“AI engineering”在 2022 年底 ChatGPT 发布前几乎没有搜索量，之后一直上升。
  • 有 10 年以上软件经验的工程师里，将近一半做 AI 不超过三年，十分之一是今年才开始。

在做什么、怎么做

  • 超过一半的人同时把 LLM 用在内部和对外产品上。对外产品使用的模型里，前五名有三个、前十名有一半来自 OpenAI。
  • 最主要的用途是代码生成和代码智能，以及写作辅助和内容生成。她说更重要的是多样性：用 LLM 的人里 94% 至少用于两种用途，82% 至少三种。
  • 定制方式：除了少样本提示（few-shot），RAG（检索增强生成，先检索相关资料再交给模型回答）最常见，70% 在用。让她意外的是微调（Fine-tuning）比预期多，研究员和研究工程师做得最多。开放题里，40% 提到 LoRA 或 QLoRA（只训练少量附加参数的参数高效微调），也有人用 DPO、强化微调；最常见的还是监督微调（SFT），很多人混合使用。
  • 更新频率：超过 50% 至少每月换一次模型，17% 每周换；提示词改得更勤，70% 至少每月改，十分之一每天改。她开玩笑说看了一篇 Simon Willison 的博客，原来的提示词就不够好了。但 31% 的人没有任何管理提示词的方法。
  • 多模态：图像、视频、音频在工作中的使用远落后于文本，她称为“多模态生产差距”。在还没用的人里，音频的计划采用意愿最高，37% 打算以后用，她说准备迎接音频浪潮。

Agent、监控与存储

  • 问卷对 AI Agent 的定义：由 LLM 控制核心决策或工作流的系统。80% 说 LLM 在工作中好用，说 Agent 好用的不到 20%。多数人还没用 Agent，但大多计划用，说永远不用的不到十分之一。
  • 已在生产的 Agent 多数有写权限，通常有人在回路中，也有一些能独立行动。
  • 监控（多选）：60% 用常规可观测性工具，超过 50% 依赖离线评测。评估质量时综合使用用户数据收集、基准等方法，最常用的仍然是人工审核。监控模型用量多靠内部指标。
  • 65% 使用专门的向量数据库（存储嵌入向量、按相似度检索的数据库），她认为说明专用向量库在很多场景比通用数据库加向量扩展更有价值；其中 35% 主要自托管，30% 主要用第三方服务。

其他

  • 多数人认为 Agent 应该声明自己是 AI；多数愿意为推理时计算多付钱，但优势不大；多数认为 2030 年 Transformer 仍占主导；多数认为开源和闭源模型会趋同。
  • 对“美国 Z 世代有 AI 男女朋友的比例”的平均猜测是 26%。
  • AI 工程最痛的事：评测排第一。
  • 她还列出了大家每月至少从中学到东西的播客和通讯各前十，swyx 的 Latent Space 两个榜都在。

19. Alex Atallah（OpenRouter）：做 OpenRouter 的几个故事

直播位置 7:51:38–8:09:39 · 英文原题 fun stories（题目由 swyx 起）

主持人介绍：Alex Atallah 联合创办了第一个 NFT 市场 OpenSea，2017 到 2022 年做到每月 40 多亿美元交易量；2023 年创办 OpenRouter，第一个 LLM 聚合与分发平台，每周处理超过 2 万亿 token，覆盖 400 多个模型。

起点：推理市场会不会赢家通吃

2023 年初创办时他心里只有一个问题：推理可能是软件史上最大的市场，大家默认它会赢家通吃，OpenAI 遥遥领先，是不是真的如此？他做了几个原型，也去看开源模型。

  • 2023 年 1 月，第一个信号是内容审核：用户想要知道自己会不会被封、审核政策是什么的模型。有人用模型写侦探小说，第四章侦探发现凶手开枪杀人，OpenAI 当时有时拒绝生成，或者处在服务条款的灰色地带；角色扮演也是一大块灰区。
  • 2 月开源竞赛开始。他现场问谁用过 BLOOM 176B（大约十人举手）、Facebook 的 OPT（大约五人），这些当时用处不大。Meta 发布 Llama 1，摘要里说在多数基准上超过 GPT-3，13B 版本能在笔记本上跑，大家都疯了。但它主要是文本补全模型，本地运行很难，基础设施还不行。
  • 3 月，他认为长尾模型真正诞生的时刻：斯坦福的 Alpaca，用 GPT-3 生成一批输出，在 Llama 1 上微调，总花费不到 600 美元。这是他第一次看到大模型的风格和知识迁移到小模型上，意味着不需要千万美元的训练预算，也意味着可以把独有的数据以语言模型的形式作为服务提供。他想到会有成千上万这样的模型，需要一个地方去发现它们、弄清它们擅长什么，因为开放权重的模型也是黑箱，你只拿到 70 亿个浮点数。现场用过 Alpaca 的大约 12 人。
  • 4 月，他先做了 Window AI，一个开源 Chrome 扩展，让用户自己选模型，网页应用直接接入，比如在网页里把 OpenAI 换成 Together 部署的开源模型。他想验证用户是否愿意把自己选的模型带到通用网站上。
  • 5 月，OpenRouter 上线，联合创始人是 Window AI 所用框架 Plasmo 的创始人 Louis。

OpenRouter 是什么、怎么变成市场

  • 过去两年每月增长 10% 到 100%。一个 API 访问所有语言模型，付一次费，模型间切换成本接近零；400 多个模型、60 多家活跃供应商；支持多种支付方式包括加密货币；替你处理工具调用和缓存的格式统一。公开的排行榜页面也成了“谁在用哪个模型”的数据来源。
  • 一开始它只是模型合集。早期一个开源模型只有一两家托管，就设一个主供应商一个备用，连供应商名字都不显示。后来托管的公司越来越多，价格、性能、支持的功能（如 min-p 采样、缓存、工具调用、结构化输出）都不同，生态变成一个失控的异构怪物。他们把所有供应商汇集起来，按不同价位排列，就成了市场。例如 Llama 3.3 70B Instruct 有 23 家供应商。
  • 闭源模型也有问题：供不应求。OpenRouter 通过聚合多家供应商提升可用性（uptime boosting），并用真实数据展示各模型的延迟和吞吐。
  • 其他功能：用自己的提示词对比模型，细粒度隐私控制和 API 级覆盖，统一查看所有模型的用量。

数据和判断

按模型作者统计 token 量：Google Gemini 从去年 6 月约 2% 到 3% 稳步涨到 34% 到 35%；Anthropic 是平台上最受欢迎的之一；OpenAI 在他们的数据里偏少，因为很多开发者用 OpenRouter 是为了让其他模型有 OpenAI 式的接口，但 OpenAI 也增长了很多。他们的结论是不会赢家通吃：

  • 未来是多模型的，大量客户为不同用途用不同模型并从中获益。
  • 推理是大宗商品。他们希望 Bedrock 上的 Claude 和 Vertex 上的 Claude 看起来完全一样，开发者只需选择，不用操心谁在提供。
  • 推理会成为主要运营开支，选择和路由很关键。平台上活跃模型数持续增长，用户并不是频繁跳来跳去，模型选择有黏性。

技术故事

  • 他们没有做 MCP 市场，但需要给所有模型加能力，比如网页搜索、PDF 解析。MCP 能做调用前的准备工作，他们还需要在结果返回用户的路上改写输出，所以做了一套为推理优化的 AI 原生中间件（middleware），写法类似 Next.js 的中间件。插件里可以调用 MCP，也能在流式输出中实时给结果加网页引用标注，不需要等全部 token。
  • 延迟：通过大量定制缓存把额外延迟压到大约 30 毫秒，他认为是业内最好。
  • 流取消：各供应商的策略完全不同，有的你断开流就按全部计费，有的不收，有的会收你没收到的后 20 个 token。他们花了很多功夫处理这些边界情况。

接下来：更多模态，他特别提到 LLM 生成图像的“transfusion”模型（Transformer 与扩散模型结合），会让图像有更多世界知识、可以对话式修改，他听说有人用它为外卖应用生成整份菜单；更强的路由，包括地理路由、把请求送到合适地点的 GPU、企业级优化；更好的提示可观测性；更细的模型分类，比如“输入日语、输出 Python 代码最好的模型”；更低的价格。

20. Sean Grove（OpenAI）：新的代码，规格说明（Specification）

直播位置 8:10:25–8:31:25 · 英文原题 The New Code

Sean Grove 在 OpenAI 做对齐研究，主持人介绍他的工作是把高层意图翻译成可执行的规格和评测。他的论点：规格说明（specification）是新的代码，写一次意图就能“到处运行”。结构是：代码与沟通、规格的构成（以 OpenAI Model Spec 为例）、用规格和人沟通（以 GPT-4o 谄媚问题为例）、让规格可执行、把规格当代码、几个开放问题。

代码只占价值的一小部分

他先让写代码的人举手（vibe coding 也算），再让“工作就是写代码”的人保持举手，再问其中谁认为自己最有价值的工作产物是代码，不少人仍举着。他说这很自然，代码看得见、能量化、能争论，但它大约只占你价值的 10% 到 20%，另外 80% 到 90% 是结构化沟通：和用户聊、理解问题、提炼故事、构思方案、规划、和同事分享计划、把计划翻译成代码、测试验证，而验证的对象是代码运行后是否达成目标、是否解决了用户的问题。结构化沟通是瓶颈，模型越强，这个瓶颈越明显；不久之后，沟通最有效的人就是最有价值的程序员。

他说 vibe coding 感觉好，是因为它以沟通为先，代码是下游产物。但我们的做法很奇怪：把意图写在提示里交给模型，拿到代码，然后把提示扔掉。这就像把源代码碎掉，却小心地对二进制文件做版本控制。编译 TypeScript 或 Rust 时，大家每次都从源码重新生成二进制，源码才是有价值的东西。

规格比代码更有力

写下来的规格能让人对齐共同目标，是大家讨论、争论、引用、同步的对象；没有规格就只有模糊的想法。他认为代码是规格的有损投影：反编译 C 二进制拿不回注释和好的变量名，读代码也很难反推团队的意图和价值。好的规格像源码交给编译器可以编出 ARM64、x86 或 WebAssembly 一样，交给模型可以产出 TypeScript、Rust、服务端、客户端、文档、教程、博客，甚至播客。他让做开发者产品的人想一想：把整个代码库丢进播客生成器，能生成告诉用户怎么成功的内容吗？还是那些信息根本不在代码里？他认为新的稀缺技能是写出完整表达意图和价值的规格，掌握它的人会是最有价值的程序员，很可能就是今天写代码的人；产品经理和立法者也在写规格。

OpenAI Model Spec

  • OpenAI 去年发布 Model Spec，一份活文档，尽量清楚地表达 OpenAI 希望模型具有的意图和价值；今年 2 月更新并在 GitHub 上开源。它就是一堆 Markdown 文件：人能读、有版本、有变更记录，用自然语言写，所以产品、法务、安全、研究、政策的人都能读、讨论和贡献同一份“源码”。
  • 每一条款都有 ID（他举的例子类似 sy73），仓库里有同名的 Markdown 文件，存放针对这条款的若干高难度提示，也就是文档自带成功标准，被测模型必须按条款回答它们。
  • 案例：GPT-4o 的一次更新导致严重的谄媚（sycophancy，过度迎合、奉承用户）。他展示了用户指出模型在牺牲客观事实来讨好、模型却夸用户有洞察力的例子，还有其他研究者发现的例子。他说这样上线会侵蚀信任，也引出问题：是故意的吗？为什么没被发现？Model Spec 从发布起就有一节“不要谄媚”，解释谄媚短期让人舒服、长期对所有人不好。既然规格是大家认可的意图，行为不符就是 bug。他们回滚了更新，发表了研究和博客，修复了问题。在这期间规格起到“信任锚点”的作用，让外界知道什么是预期内的、什么不是。

让规格可执行

他介绍了 OpenAI 的论文 Deliberative Alignment（审慎对齐）的思路：拿规格和一组很难的输入提示，从被测或训练中的模型采样回答，把回答、原始提示和政策条款交给一个评分模型，让它按规格打分，再根据分数强化权重。这样文档既是训练材料也是评测材料。你也可以每次把规格放进系统消息或开发者消息里，提示过的模型会有一定程度的对齐，但会占用本该用于解决问题的算力；通过训练把它推进权重里，模型就像有了肌肉记忆。规格可以是任何东西：代码风格、测试要求、安全要求。

规格就是代码

  • 规格可以组合、可执行、可测试，有和现实世界的接口，可以作为模块发布。
  • 类似类型检查器：部门 A 和部门 B 写的规格如果冲突，应该能提前发现并阻止发布。政策可以自带单元测试。也可以有 linter，用词含糊会让人和模型都困惑。也就是一套类似的工具链，只是检查对象从语法换成了意图。
  • 立法者也是程序员：他说美国宪法就是一份国家级的模型规格，有文本、有版本化的修正案流程、有司法审查（相当于评分者判断某个情况是否符合政策）；规则没覆盖到的情况在司法审查中花大量“算力”去裁决，形成判例，判例相当于输入输出对的单元测试，消除歧义、强化原规则；还有指挥链；长期执行就是一个让所有人对齐的训练循环。程序员用代码规格对齐硅片，产品经理用产品规格对齐团队，立法者用法律规格对齐人；每次写提示，你都在写一份雏形规格。

他给软件工程的定义是：人类对“用软件解决人类问题”的精确探索，一直如此，代码只是手段。建议做下一个 AI 功能时先写规格：期望发生什么，成功标准是什么，是否写清楚了；让规格可执行，交给模型并对照规格测试。他提出一个问题：未来的 IDE 是什么样？他希望是一个“集成思维澄清器”，在你写规格时把歧义找出来让你澄清。最后他说“大规模对齐 Agent”最需要规格，引用了一句“你这才意识到你从没告诉它你想要什么，也许你自己也从没完全想清楚”，并为 OpenAI 新成立的 Agent 稳健性团队招人。

21. Ben Dunphy 与 swyx：首届官方黑客松决赛与讲者颁奖

直播位置 8:31:25–9:04:28 · 英文原题 AI Engineer Official Hackathon

两位创办人上台。黑客松和湾区的 Cerebral Valley 社区合办，500 人申请，160 名工程师参加，现场展示了 46 个项目，选出 3 个决赛队，各有不到 5 分钟展示 48 小时的成果，奖金共 1 万美元，由现场观众欢呼投票。

决赛项目

  • Survival of the Feature：用 Agent 自动做 UX 的小迭代和 A/B 测试。痛点是优化 UX 要不断做小变体（改文案、改一行代码），A/B 测试流程笨重、信号不清。方案是接入 GitHub 仓库后，一个 Agent 找出用户交互最多的页面（落地页或仪表盘），另一个 Agent 分析并做小改动、开分支；再根据过去的用户交互记录，把一小部分流量导到新变体，表现好就逐步扩大，相当于渐进式发布。他们在做让客户自定义优化指标的功能。swyx 说这几位十天前才认识，一起参加了很多黑客松，赢了不少。
  • Tab RL：一位物理学背景的成员和一位 AI 工程师在黑客松上认识。他们的想法是网页里已经有 Bolt、Lovable 这类全栈自动化平台，机器人领域却没有。他们用 MuJoCo（被 Google DeepMind 收购的物理仿真引擎）做了一个在浏览器里操作的强化学习环境：选一个 3D 机器人模型（演示里是机器狗），用自然语言描述目标（坐下、伸爪子），由 o3、Claude Opus、Gemini 各生成三个奖励函数（reward function，告诉 RL 什么行为得分），然后在 Modal 提供的沙箱里训练，一共九个。他们展示了每家模型各一个结果，Claude 那个因为步数不够没收敛，Google 和 OpenAI 的有收敛。swyx 说评委都特别称赞他们的沙箱设计。
  • Featherless Action R1：讲者 Eugene（Featherless AI，长期训练非注意力、次二次复杂度的模型，曾是 Latent Space 播客第一位海外嘉宾）。他介绍团队做过一个 72B 参数、不含 Transformer 注意力的模型，基于 RWKV 架构，他说推理成本便宜上千倍、性能相当，但强调这只是背景。他的观点是“扩展已死”，靠扩展解决不了可靠性：他引用 DeepMind CEO 说解决复合 Agent 误差可能要 10 年、Yann LeCun 说需要新架构，以及 90% 的 AI 项目达不到企业要求的说法。他说多数公司不需要会做博士数学的 AI，需要的是每次都能订机票、发邮件、处理发票不出错。他的 Action R1 模型在 REAL 评测（由 AGI Inc. 提供端点和排行榜的真实网页任务基准，如在 Amazon 购物）上得到 65%，他说 Claude 和 Gemini 约 45%。他现场在 Cline 里通过 MCP 让它去 Amazon 搜一本 AI 工程的书，说模型不快，一次要 5 分钟，所以改放录屏；又现场把评测批量提交到排行榜。他说 65% 还不够，目标是 99%。
