02. Emil Eifrem（Neo4j）：AI 工程里的“状态”，好的数据层要满足四个条件

直播位置 0:20:55–0:53:18 · 英文原题 The State in AI Engineering

Emil Eifrem 是图数据库公司 Neo4j 的联合创始人兼 CEO。主持人介绍时提到，Neo4j 帮调查记者破解过巴拿马文件，也帮 NASA 的火星项目提前两年完成。他开场用法语说了句 Bonjour，说这是他会的全部法语。幻灯片标题写着 “The State of AI Engineering”，他说这个题目该 swyx 或 Ben 来讲，自己在数据库和知识表示上做了二十年，所以要讲的是 AI 工程里的“状态管理”（state）。内容来自 Neo4j 过去几年在大小公司里观察到的几百个 AI 项目。去年在旧金山他讲的是 GraphRAG 的实操，这次更偏观点：AI 应用的数据层应该往哪里走。

从上下文工程说起

他先引了 Karpathy 对上下文工程（Context Engineering）的一句话定义：在上下文窗口里放进下一步刚好需要的信息，这是一门精细的手艺。这个词出自 HumanLayer 的 Dex Horthy（字幕作 Dexworthy），他写的 “12 Factor Agents” 系列第三条讲的就是上下文工程，开头三句话：一切都是上下文工程；LLM 是把输入变成输出的无状态函数；所以想要最好的输出，就得给它最好的输入。Emil 说他这次要讲 AI 工程中状态的三个主要来源：RAG 语料（检索增强生成 RAG，就是先从资料库里查出相关内容再交给模型回答）、Agent 记忆、应用本身的状态。

应用架构的简史

  • 2022 年以前的典型 CRUD 应用：UI、后端、数据库。结构化数据进数据库，非结构化数据进对象存储，UI 和后端之间传 JSON 这种半结构化数据。
  • 2022 年底 ChatGPT 发布，半年多以后 swyx 提出 “AI Engineer” 这个词。2023 年大家做的是聊天机器人：一个编排层，下面是向量数据库，里面放的其实是非结构化数据的简化版，也就是 Embedding（把文本变成一串数字向量，语义相近的文本向量也相近）。
  • 2024 年大家开始谈 Agent，年底 Anthropic 发布 MCP，工具接入变简单了。
  • 到 2025 年，上半截技术栈成形了：上面是真正的应用，AI 功能嵌在其中；编排层变成一个或多个 Agent，它们包装提示词、调用工具、使用记忆和一个或多个 LLM。

下半截的数据层还很乱。向量数据库发现光靠语义近似检索（ANN，近似最近邻）不够，于是加上结构化数据，叫它“元数据”，用来做过滤；关系数据库、文档数据库、图数据库则反过来把向量当成一个新功能加进来。以非结构化为中心的在补结构化，以结构化为中心的（比如 Postgres）在补非结构化，以 JSON 为中心的也在补。他说现在“底下是个派对，有点乱”，问题是会往哪里收敛。

四个条件

第一，在一个数据层里同时处理结构化、非结构化、半结构化数据：要能存取，还要能建索引、在三类数据之间保证事务范围。

第二，能稳定地从非结构化数据里抽取实体。他的理由是：AI 应用也是应用，要写大量软件工程代码，开发者想要类型、类和对象，比如一个 Person 类，但很多信息躺在非结构化文本里。他举了三句话：“Andreas 今天在这里。他是个木匠。向 ABK 致意。”第一步是命名实体识别（NER），找出 Andreas、he、ABK；第二步是实体消解（Entity Resolution），判断这三个指的是同一个人并合并。合并后的结果就是结构化数据，可以映射成应用里的对象。

第三，能把 Agent 记忆里的实体和来自 RAG 语料的应用数据链接起来。他用一个在线家具店举例：中间是产品画廊，卖一张有北欧名字的 Kiruna 桌子；旁边是一个 AI 驱动的社区论坛，有一个帮人看装配说明的机器人。数据层里有产品表、物料清单（BOM）表、产品问题追踪表，也有从装配手册里抽出来的实体。论坛里用户 ABK（一位木匠）留言说：Kiruna 桌子的说明书写得不好，但在第 8 步之前给桌腿滴两滴木胶就很好装。装配机器人回答问题时应该能同时用到手册和这条记忆，前提是这几个 “Kiruna 桌子” 被链接成同一个东西。可以在检索时链接（分别查各个数据源再拼起来），也可以在数据层里就链接好。他认为后者对多数应用更好，理由有三：

  • 性能：跨多个工具多次检索，检索之间常有依赖，延迟会叠加；中间结果往往很大；等于在应用层重新实现 Join，占大量内存。
  • 复杂度：Neo4j 花了 15 年把 Join 做好，到现在还在改进，这件事并不简单。
  • 可靠性：假如 Kiruna 这个名字遇到商标纠纷要改名，检索时链接的做法得在所有数据源里做文本搜索再更新；在数据层链接好的话，改一处就会传到整个应用状态里。

第四，能区分第一方数据和衍生数据。第一方数据是应用直接从自己用户那里收集的数据，比如用户填的名字、偏好、使用时长、交易记录；CRUD 时代的应用几乎全是第一方数据。现在的 AI 应用里，从 RAG 语料（比如 Kiruna 的装配手册）抽出来的是衍生数据。把两者混在一起，映射到 TypeScript 应用里的 Kiruna 对象信息最全，查询效果也更好；但两者要分开处理。RAG 语料更新时，最常见也最简单的做法是把衍生数据全部删掉重建（有人尝试增量变更集，他觉得实际很麻烦），这时不能顺手把混在一起的第一方数据也级联删掉。

他特意说明，这些不是“销售先说你需要什么，再拿出刚好满足需求的产品”的套路。Neo4j 今天还没有全部做到，但这是他们的方向，作为 CEO 他对产品路线图有一些影响力。

演示：知识图谱构建器

他演示了前两个条件。把维基百科“巴黎”词条的 URL 贴进 Neo4j 的 Knowledge Graph Builder，系统把页面切块（chunk），以两种形式写进图里：原始文本块，以及抽取出来的实体。隐藏实体后能看到一个个文本块；打开实体后能看到人口信息（巴黎的英国公民、美国公民）、“巴黎位于法国”这种关系，还有自动抽出的一串巴黎名人，比如 Igor Stravinsky。他说有了这些实体，就很容易映射成应用里的类型化对象，也很容易做有语义的查询。最后介绍了 Neo4j 的云服务 Aura 有免费版、GraphAcademy 课程，以及几周前推出的创业公司计划（免费额度和专家团队）。

问答

  • Agent 记忆的未来：他问现场有多少人在用 Agent 记忆系统，大约三分之一。他观察到很多人在没和他聊过的情况下独立得出结论：Agent 记忆天然是图结构的，比如 YC 的 Zep、Mem0、Cognee。MCP 最初发布时附带了一个很小的记忆服务器实现，只有 300 行 Python，是个玩具，但它也是一张图。
  • 企业是自建还是购买：Neo4j 主要卖给全球 2000 强，所以才能给创业公司免费用。12 到 18 个月前，企业采用 AI 几乎都是买现成应用；一年前开始试着自建；2025 年开始真正上生产，自建大幅增加。原因之一是 AI 让工程师更高效，写代码的门槛也在降低。他认为趋势会是自建远多于购买，“至少我希望如此，因为他们是在我们上面建”。
  • 他举了 Klarna（两周前刚上市的瑞典金融科技公司）：CEO 发长推说用自建的 AI 平台替掉了 Salesforce、Workday 和另外 1200 个 SaaS 工具，推文里说核心是图和 Neo4j。他说跟财富 500 强的 CIO 聊，从没见过这么强烈的反 SaaS 泛滥情绪，上一次是对 Oracle 的厌恶（他补充说自己觉得 Oracle 是好数据库）。Neo4j 自己一千人，也不清楚到底买了多少 SaaS。他认为“去掉用不上的 100 个功能、只要定制的 4 个”的前景很大，但还没真正兑现。
  • 创新在哪里：Neo4j 技术上是美国公司，在 Delaware 注册，总部在硅谷，但他在瑞典创立，工程团队主要在瑞典和伦敦。他们内部说要做“有瑞典灵魂的美国公司”。他 2011 年搬到硅谷，疫情前搬回瑞典。2011 年做开发者和基础设施公司必须在湾区；2023 年到 2024 年初的 AI 创新集中在旧金山“八个街区的半径”里。现在变化很快，巴黎、斯德哥尔摩（有 Lovable）、柏林都起来了，伦敦比他预期的慢。如果今天从零开始，他不确定自己还会搬去硅谷。

03. Tushar Jain（Docker）：让 Agent 的构建、分享和安全变简单

直播位置 0:53:18–1:00:36 · 英文原题 Democratizing AI Agents: Building, Sharing, and Securing Made Simple

Tushar Jain 是 Docker 的产品与工程总裁（主持人介绍为产品工程副总裁）。他的框架是“Agent 是新的微服务”：Docker 过去十年让大家方便地采用微服务和容器，靠的是标准、易用的工具和生态里的信任（官方镜像、Docker Hub）。从单体走向微服务需要容器；现在走向 Agent 互相调用，容器仍然是对的底座，但要在上面加东西：理解 Agent 及其依赖的标准打包方式、可信的目录、方便的分享和使用。

Agent 的标准打包

把 Agent 直接打进容器，容器并不知道它用了哪些工具。分享出去以后还是老问题：工具是什么、配置是什么、需要什么运行时、怎么在任何环境里跑。他设想应该有类似 Dockerfile 的 “agent file”，以及 docker agent build / push / pull / run。作为起点，Docker 开源了 cagent：一个易用的 Agent 构建器，能把 Agent 打包成 OCI 制品（OCI 是容器镜像的开放标准格式），通过 OCI 镜像仓库或 Docker Hub 分享。他说这还是早期探索。

MCP 的打包、发现与安全

他认为开发者用 MCP 需要几样东西：好的打包（把本地 MCP 服务器打成容器，顺带获得隔离和安全）、方便的发现、可信度（哪个 MCP 服务器是靠谱的，相当于 MCP 版的 Docker 官方镜像）、以及防 rug pull（工具被悄悄替换成恶意版本）等安全威胁的工具。Docker 做了两件事：

  • MCP Catalog（hub.docker.com/mcp）：可信、经过验证的 MCP 服务器目录，之后会加社区服务器，也会让任何人提交，同时在上面加安全措施；本地服务器容器化，也支持远程服务器。
  • Docker Desktop 里的 MCP Toolkit：现在要在 Claude Desktop、Claude Code、Gemini 等客户端里分别配置 MCP，Toolkit 让你配置一次、多处使用，而且是在本机上运行容器化的服务器，不用 npm install 一堆能访问整台机器的随机软件。

演示

场景是产品经理在 Notion 里收集了 Docker Desktop 的用户反馈，他想让 Agent 读这些反馈并在 GitHub 里建 issue。他在 MCP Toolkit 里添加 GitHub 服务器（已配置好 OAuth）和 Notion 服务器（密钥由内置的秘密管理保存），在客户端列表里点一下就连上 Claude Desktop，不用手改配置文件。Claude 启动后工具列表里出现 Docker 提供的一组工具，他先让它读出 Notion 页面的名字和内容，然后新开一个对话让它“看反馈、分类、放进 GitHub”。任务要跑一阵，他没等跑完。他强调的是配置简单、用的是可信的官方服务器、服务器跑在容器里拿不到不该拿的权限，之后还会加更多安全控制，并且会用这套工具让大家方便地构建 Agent。

04. Martin Woodward（GitHub）：在 GitHub 的规模上做 MCP 学到的事

直播位置 1:01:30–1:28:20 · 英文原题 Building MCP's at GitHub Scale

Martin Woodward 是 GitHub 开发者关系副总裁，从第一版起就参与 GitHub Copilot。他说很高兴上台前刚看到 Docker 现场演示了 GitHub 的 MCP 服务器，“它还能用”。他说这次不太讲 GitHub MCP 服务器本身，主要讲 MCP 协议和怎么参与 MCP 社区。

怎么走到今天

  • 2021 年 6 月推出 GitHub Copilot。那时 LLM 还不够好，只做自动补全，因为只需要改一小段代码。后来模型变强，做了聊天；到 2025 年模型能长时间无人监督地运行，进入软件工程 Agent 阶段。Copilot 现在有超过 1500 万用户。
  • GPT 到 2023 年 6 月才有函数调用（Function Calling），离现在两年出头。随后 GitHub 推出 Copilot Extensions，让开发者给 Copilot 提供工具，连接开发体系里的其他系统。
  • 2024 年底 Anthropic 发布 MCP。和偏 API 风格的函数调用相比，MCP 的工具发现更动态：可以告诉 LLM 有哪些工具，并给它足够的上下文去调用。VS Code 完整支持 MCP。
  • 2025 年 4 月 GitHub 发布官方的本地 MCP 服务器（Anthropic 最初做过一个基于 GitHub API 的版本，后来双方合作，GitHub 做了自己的并开源），之后又有了远程 MCP 服务器，不想装任何东西可以直接连远程的。

第零课：MCP 除了工具还有别的

工具（Tools）是 MCP 成功的原因：建 issue、发邮件、执行脚本，或者取数据加进提示词的上下文。但只用工具会错过协议的其他部分。他把协议的基本构件过了一遍：

  • Resources（资源）：客户端可以单独向服务器要资源，比如 GitHub 上的文件和 issue、Notion 的页面、数据库的 schema。
  • Prompts（提示词）：他比作 MCP 世界的存储过程。可以问服务器“你有哪些好用的提示词”，支持变量替换。
  • Sampling（采样）：客户端允许服务器借用客户端正在用的 LLM。GitHub Copilot 让开发者自选模型，所以 GitHub 的 MCP 服务器需要能说“用这个用户选的模型帮我做这一步”，无论是 Claude Sonnet、Gemini 还是别的。
  • Roots（根）：客户端指定服务器能访问的文件系统范围，让服务器待在沙箱里，不去碰需要 root 权限的东西。
  • Elicitation（征询）：服务器告诉客户端“我需要关于 X 的更多信息，A 还是 B”，通常变成问用户的问题，也可能由 LLM 决定。他说这能减少幻觉和没有依据的工作。

他周一统计了约 80 个 MCP 客户端实现：79 个支持工具，只有 3 个实现了 Elicitation。规范 6 月才写好，这不是谁的错，只是还早。想把协议每个部分都测一遍，他推荐 VS Code（他说自己不在 VS Code 团队，那是兄弟团队），这是唯一完整实现 MCP 协议和所有认证规范的终端客户端。

第一课：工具多了反而坏事

和人一样，给 LLM 的选择越多越容易困惑。他引了 LangChain 的研究：可用工具越多，模型做编程任务的表现越差，速度也越慢。GitHub 的用户是开发者，所以最初的做法是把开关交给用户，让他们自己选启用哪些工具；但订机票、比保险的普通用户不会想挑工具。所以需要动态工具发现：6 月版协议加入了服务器在对话进行中通知客户端“现在多了一个工具”或“这个工具没了”的能力，让同一时间暴露给模型的工具更少，准确率更高。

第二课：本地安装 MCP 很痛苦，而且没人升级

跨平台安装本地 MCP 是噩梦，定义服务器时能写的命令五花八门，要在 Linux、Mac、Windows 上都稳定跑起来几乎不可能。Docker 的容器化对开发者很好，但对普通人走不远。他还 grep 了调用 GitHub 端点的日志，发现一个本地 MCP 只要能用，就没人升级。协议变得这么快，这不可持续，而本地安装方式也让自动升级几乎做不到。

远程 MCP 服务器从一开始就在协议里（MCP 一直是网络协议）：装在远端，不经同意碰不到客户端文件系统，容易升级、容易扩展。缺点是开发者得先搭一个远程服务，迭代慢。GitHub 的办法是本地服务器完全开源、谁都能贡献，团队内部快速迭代，然后把同一套逻辑托管成远程服务器，一起升级。这样还支持服务器到服务器的场景，比如在 github.com 上直接用 GitHub MCP 服务器。

第三课：别用密码或 PAT 认证

用密码或个人访问令牌（PAT）认证是反模式：秘密难管理，总会变成长期有效的秘密；能访问文件系统的其他 MCP 服务器也可能读到它。6 月的协议加入了 OAuth 支持，用短期令牌，也支持 OIDC。不是每个客户端 SDK 都支持 OAuth，做 OAuth 集成也有摩擦，但这是上生产前必要的摩擦。本地开发可以凑合，生产环境必须支持 OAuth。

第四课：没人找得到的 MCP 等于没有

社区两周前发布了开源的 MCP Registry，可以通过 API 把自己的 MCP 服务器信息发布出去，所有人共享一个基础仓库。他经历过很多语言的包管理器（npm、.NET 等），最想避免的是单点故障或单一垄断的仓库：没有一个仓库能解决所有人的问题，启用哪些 MCP 涉及信任，所以要允许各家有自己的 Registry。GitHub 现在有一个自己的 MCP 目录，在基础目录上加了星数、热度等数据，能看到 Context7 很受欢迎，还有微软的 MarkItDown（把 Office 文档等转成 Markdown，方便抓取）。设想是中心 Registry 加上各自的本地 Registry：Docker 有自己的，公司也应该有一个，决定内部信任哪些服务器。

他说 MCP 已经成为 AI 的 API 层，A2A（Agent 之间通信的协议）这类东西是补充，但在工具调用上 MCP 就是大家要用的协议。协议完全开放，现在加入社区就能影响接下来二十年大家依赖的东西，并给出了 MCP 社区网站和 Discord。

问答

  • 协议还缺什么：他认为 6 月版对已知需求来说基本完整了。下一步是客户端实现和 SDK，让开发者不用关心 Elicitation、动态发现这些细节，只调用一个 API 就能“用好的方式调用”；再往后是 Registry 里的发现。
  • Agent 能不能自己找合适的 MCP：Registry 提供 API 就是为了让 Agent 自主发现，但信任需要判断；而且假如有五个订机票的 MCP，调用哪一个是你想自己掌控的核心业务逻辑。
  • 要不要先把自家 API 变成 MCP 服务器：他说 LLM 写 MCP 服务器特别拿手，打开 VS Code 加 Copilot 或者 Claude Code，让它写一个来玩。他自己做过一个下井字棋的 MCP 服务器。在本地跑一遍能帮你理解协议，之后很多企业有一个远程 MCP 端点会合理。他还认为平台工程很需要 MCP：开发者在开发环境里一句话就能要一个新环境、加一个数据库连接，不用排工单等人。
  • 给计算机专业学生的建议：他儿子在读计算机硕士，他在 GitHub 管全球教育项目，覆盖几百万学生。他认为明天需要的计算机学生比今天更多。学生免费用 AI 工具后，有了更多“和别人合作”的经验：审阅另一个 Agent 写的代码，看哪里对哪里错再修，这是工程师每天都要做的事。他也呼吁公司继续招初级开发者，“没有什么比带一个初级开发者更能让高级工程师成长”。他认为初级开发者没有死，而且能产生的影响比以前大。对英语不是母语的人尤其如此，LLM 可以用母语给你讲代码。

05. Yann Leger（Koyeb）：为 Agent 时代准备的基础设施

直播位置 2:00:22–2:23:52 · 英文原题 Building for the Agentic Era: The Future of AI Infrastructure

茶歇回来，Yann Leger 第二次上台，这次讲 Koyeb 自己的业务。他做了 14 年基础设施，从云计算早期一路看到这一波 AI。

技术栈变复杂了

2023 年初的 AI 栈很简单：一个 API，一边是向量数据库，模型选择有限，主要是 OpenAI 的闭源 GPT，开源有 Meta 的 Llama 和 Stability 的模型，Mistral 还没出现；跑在 GPU 上，推理服务多半是 Triton Inference Server，因为连 vLLM 都还没有。两年半以后多了视觉语言模型（VLM）、视频模型、vibe coding、MCP 和 Agent。现在的 Agent 栈：前端常用 Manus、Lovable 这类工具 vibe code 出来（Koyeb 团队在展区做了个实验）；API 因为 SDK 多了，语言更多样；Agent 大概率还是 Python 写；传统数据库都加了向量能力；再加上 MCP。推理硬件也更多样：AMD 已经是可信的选择，适合跑某些模型；还有 Tenstorrent 这类想挑战 NVIDIA 的新加速器（字幕作 tensor）；你也可能完全看不到这些，直接用更高层的推理端点。

他按工作负载分了硬件：大规模训练仍用 GPU；微调和小规模训练多半也是 GPU，有人开始用 AMD GPU 训练；推理可以用加速器，AMD GPU 用得最多；Agent 工作负载跑在“老式 CPU”上。

Agent 对基础设施意味着什么

他先给了一个常见定义：用 AI 代表用户追求目标、完成任务的软件系统，具备推理、规划、记忆，有一定自主性。对基础设施来说重要的是：它终究是跑在服务器上的 Python 或 TypeScript；有自主性，意味着要运行由非确定性模型生成的不可信代码，“做过安全的人都该想想这有多危险”。由此得出几条需求：安全的沙箱环境；性能要快；大多是短命的（ephemeral）；量大，所以效率重要；部署速度也重要。

演示：用 MCP 创建沙箱

他用 Claude Code 加上 Koyeb 的 MCP 连接器（他们也做了一个用 Mistral 的版本），让 Agent 用 Koyeb Sandbox 执行一段“不可信代码”（其实是简单加法）。在 Koyeb 控制台里能看到一个叫 calculation sandbox 的沙箱被创建、变成健康状态，然后结果返回。他说这次是自己手动让它做，编程 Agent 会在你不知道的时候自动做这件事。

冷启动的瓶颈在哪

Agent 工作负载每天要创建成千上万个安全沙箱，还要亚秒级启动。今年开始有客户来说“我们一天要部署 1 万个容器”，比如用 Lovable 时，它在背后就会在 Koyeb 这样的平台上自动创建容器。Koyeb 的栈：裸金属服务器上跑 Cloud Hypervisor 做虚拟化隔离，里面是客户的容器和 Agent，推理负载还会有 vLLM 这样的推理引擎。瓶颈有好几层：从零创建裸金属服务器要几分钟；从镜像仓库拉镜像，小镜像也要几秒，大模型更久；网络配置要在服务器之间收敛；Agent 自己的运行时（比如 Python）启动也要时间。

他说很多人以为瓶颈在虚拟化引擎（Firecracker 最近很流行），但在他们这里主要是网络；在你的系统里也可能是别的，比如 Vault 这类秘密管理系统扛不住请求量。他们的对策：提前启动机器、在 Hypervisor 上缓存镜像、大量网络优化。Python 运行时他们不去优化，这部分仍然要时间。

缩容到零与内存快照

Agent 负载有两种模式：只跑一分钟左右的短命沙箱；以及像 Lovable 那样最后生成一个常驻的 Web 服务器。后者的问题是很多人试一下就不管了，留下一大批大部分时间空闲、但偶尔还有人访问的服务。为了控制成本，Koyeb 把它们缩容到零（scale to zero），配合自动扩缩容。缩到零的老问题是重启慢，因为 VM 完全关掉了。他们用内存快照解决：把 Agent 的内存保存下来，这个机制叫 Light Sleep，冷启动从几秒降到 100 到 200 毫秒，终端用户感觉不到。CPU 上已经可用，GPU 上也有缩容到零，正在把内存快照带到 GPU。

问答

  • 主持人特意澄清 Koyeb 是基础设施公司，不是活动公司。
  • 14 年里什么变了：有些东西没变。他们四年前用 Firecracker 做虚拟化，加 GPU 支持时因为 Firecracker 不支持，又回到了 QEMU/KVM，那是他们 14 年前就在用的技术。2017 年他们就在部署 GPU，只是当时是 NVIDIA 消费级卡，数据中心级 GPU 才刚出现。变的是规模：以前要很多客户才有的量，现在一个客户就能带来；还有加速器的多样化。
  • 他预测 NVIDIA 的垄断会被打破，但至少还要五年才会有像样的竞争。类比是 CPU：十年前 ARM 在数据中心几乎不存在，Intel 独大，AMD 挣扎；后来 AMD 抢回份额，现在 Intel 处境不好。问题只是多快。主持人补了一句“这不是投资建议”。
  • 他说 AI 栈现在又像微服务栈：两年半前大家只是堆 GPU，一批新玩家只卖 GPU；现在像样的基础设施需要一组要协调的服务。
  • 沙箱还缺什么：底层需要快速启动的容器（大家想要运行任意运行时的灵活性）和隔离，Koyeb 提供这些积木；上层大家想要简单的 SDK 快速创建沙箱、不用操心生命周期，演示里的 MCP 工具就是在做这件事。

06. Andreas Blattmann（Black Forest Labs）：FLUX 是怎么工作的

直播位置 2:24:13–2:57:16 · 英文原题 Inside FLUX, How It Really Works

Andreas Blattmann（自称 Andy）是 Black Forest Labs（BFL）联合创始人。主持人介绍他曾在慕尼黑大学（LMU）、NVIDIA、Stability AI 做研究，是 Latent Diffusion（潜在扩散）的共同发明人之一，这项技术支撑了 Stable Diffusion、Midjourney 和 DALL-E。

公司和产品线

BFL 认为视觉媒体会成为人类沟通的核心界面，目标是成为支撑这种沟通的基础设施提供者，能力远超相机。公司 2024 年 4 月注册、8 月发布，现在 40 名全职员工，总部在德国黑森林里的 Freiburg，今年还开了旧金山办公室。发布公司当天就发布了 FLUX 模型家族，之后按三档发布：

  • FLUX Pro：质量最高、最快，只通过 BFL API 提供，面向企业，可以从零瞬间扩到大规模。
  • FLUX Dev：开放权重，可以从 Hugging Face 下载、自己部署、任意微调，已经有大量 LoRA（一种只训练少量附加参数的轻量微调方法）和微调版本。
  • FLUX Schnell：完全开源，极快极轻，适合入门。

他展示了 Hugging Face 上的 Model Atlas，图里显示各领域基础模型衍生出的生态，单个模型生态最大的是 FLUX Dev。

为什么要把生成和编辑放进一个模型

过去五年图像生成进步很大，但图像编辑直到最近都没跟上。他认为编辑至少和文生图一样重要，因为可以对内容多次迭代、逐步修改，控制力更强，“专业做过图片的人都懂”。2025 年 6 月发布的 FLUX.1 Kontext 是第一个把文生图和编辑合在一起的扩散或流匹配模型，带来了角色一致性、风格参考、局部和全局编辑，几秒内出图。示例：去掉人物脸上的物体，保留人物放进城市街景，再变成雪景；风格迁移；把招牌上的 Montreal 改成 Freiburg 且字体不变；把一张随手拍的裙子变成产品图；把草图变成完整渲染。在 Photoshop 里这些都要很久。

文生图流程是：一段描述整个场景的提示词进网络，出来一张图。编辑流程不同：输入一张图，加一句“指令型”提示词，告诉模型怎么改，比如“把它变成乐高场景”，教堂就变成乐高版。以前要做编辑得靠手工微调或复杂工作流，合进一个模型后这些都不需要了。

Latent：只建模人眼在意的信息

他展示一张 JPEG 和一张 PNG，看起来完全一样，但 JPEG 文件小了将近一个数量级，说明可以去掉大量信息而察觉不到。把“近似图和原图的感知相似度”对“文件大小”作图，曲线先快速上升然后变平。平的那段是高频的、人眼察觉不到的细节，在这上面训练生成模型是浪费算力和时间。Latent 生成建模（他和联合创始人五年前读书时提出）就是先找一个只保留人眼在意细节的表示，叫 Latent Space（潜在空间），再在这个空间里训练生成模型。

做法是先训练一个自编码器（Autoencoder）：输入图片经过 CNN 编码器得到潜在表示，再做一个正则化操作，逼模型丢掉信息（可以是离散的，也可以是连续的，他们主要用连续的），然后用解码器重建。端到端训练，损失包括重建损失（重建图和原图的差异），以及一个判别器损失，他称之为“人类感知的先验”，保证保留下来的细节是人眼在意的。

Flow Matching：从噪声流到图片

Flow Matching（流匹配）是一类算法，目标是学一个由神经网络参数化的向量场，把简单分布（正态分布）映射到复杂且未知的自然图像分布，这一切都发生在潜在空间里。训练方法很简单：把每个数据样本和一个随机的正态分布样本配对，对整个数据集都这么做，就得到一个人工构造的向量场。它看上去“错得离谱”，因为轨迹会交叉，而真正的向量场里轨迹不能交叉；但让模型去拟合这个错的向量场，做足够多次，模型最后学到的就是轨迹不交叉的真实向量场。为了用文字控制输出，网络始终以文本提示词为条件。

采样时从正态分布取一个样本，用数值积分一步步沿着向量场走，每一步是一次网络前向计算，大约 50 步走到数据分布里的一个样本，再用解码器解成图片。

Kontext 的架构：多放一张上下文图

FLUX 的骨干是一个 Transformer，以文本提示词为条件。除了要生成的那张图，Kontext 再加一张“上下文图”作为条件。两张图都进潜在空间，变成图像 token，和文本 token 拼成一个序列。网络由两种块组成：double stream 块，视觉 token 和文本 token 各有自己的“领域专家”；以及普通的 Transformer 块，所有 token 一视同仁。去掉上下文图就是文生图，加上就是编辑，他说“最后就是一个条件化的小技巧”。

为什么这么快：对抗式扩散蒸馏

他的对比图显示 FLUX 在生成和编辑上都比竞品快：文生图比 GPT Image 1 快 25 倍，编辑比最慢的竞品快到 10 倍。靠的是减少数值积分的步数：

  • Adversarial Diffusion Distillation（ADD，对抗式扩散蒸馏）：从预训练的流匹配模型初始化两个网络，一个是老师（就是原模型），一个是学生，学生要在 4 步内生成和老师 50 步一样好的图。训练时学生 4 步生成一张图（一开始很糊），把这张图再编码，让老师用 50 步生成一张高质量的图，用蒸馏损失让学生向老师靠拢。光这样不够，再加一个用 DINOv2 特征提取器初始化的判别器损失（又一个人类感知先验），让学生的图边缘锐利、看起来真实。这样能从 50 步降到 4 步，但要编码两次、解码两次，训练繁琐且算力重。
  • Latent ADD（LADD，潜在对抗式扩散蒸馏）：FLUX 实际用的是这个。把整个过程搬进潜在空间，去掉所有编码解码；用老师模型本身替代 DINOv2 当判别器的特征提取器；完全扔掉蒸馏损失。算力需求少很多，同样从 50 步降到 4 步，他图上标的是 12.5 倍加速。

现场演示

他用 BFL 的 Playground 拿他最喜欢的球队 SC Freiburg 的队徽做了一串编辑：先“把这个队徽印到 T 恤上”（第一次因为网络慢了点，他说这对 FLUX 来说太慢了）；再“队徽太大，缩小并放到右上方”；再“把 T 恤变成红色”；然后做全局变换“让一个人穿上这件 T 恤，放到公园里”；最后做风格迁移“变成水彩画”。每次出四张图。主持人在问答开头调侃：“Zuckerberg，这才叫演示。”

问答

  • 还能快多少：他认为模型更大以后可以做到一步生成，这是目标（FLUX Schnell 是 4 步）。加上更好的硬件、算法和优化，比如 Blackwell 芯片支持 FP4 量化，流匹配模型肯定能做到实时生成。
  • 为什么更大反而更快：网络学的是从输入到输出的映射，参数越多，能表示的函数越复杂。用分段直线逼近一条曲线，段数越多越准；更复杂的模型能让每一段本身带曲率，所以用更少的步数就能逼近复杂的曲线。
  • 会不会取代 Photoshop：他说这些模型很快会集成进 Photoshop（主持人说“突发新闻”），BFL 自己的平台也会很快给出使用方式。他“百分之百确定”这类模型会成为未来所有图像编辑的底座。
  • 开源和前沿怎么平衡：API 里放最强的模型，给不想碰定制和微调的人；很多实际应用需要大量定制，比如做人脸编辑 App，开放权重最合适，整个开源社区的研究成果都能为你所用。两者互补。他不认为“大多数人会用闭源模型”，这是一个一直在变的分布，未来可能都用开放模型，也可能都用闭源模型，所以两边都要做；从个人角度他们也停不下做开放模型。

07. Laurent Sifre（H Company）：用专用开放模型做电脑操作 Agent

直播位置 4:29:08–4:53:00 · 英文原题 Assembling the Future: Open Source Bricks for the Next Generation of AI

Laurent Sifre 是 H Company 联合创始人兼 CTO，此前在 DeepMind 将近十年，参与过 AlphaGo、AlphaFold、AlphaStar、Chinchilla、RETRO、Gemma 和 Gemini。午饭后第一场。

为什么要做电脑操作 Agent

他从自己的一天讲起：本想专心做这份幻灯片，打开邮箱有 289 封未读（他是 inbox zero 的人，很难受），工作邮箱还有 1000 封，再打开日历，一整天都在做小任务。他的桌面堆满文件，满了就新建一个 old 文件夹，old 被占用了就叫 old4。H 做的事在三者交叉处：Agent（自主、决策、规划）、UI 自动化（通过界面操作软件，比如 RPA 和任务执行）、模型（他们认为在大通用模型上搭东西效率很低，专用模型能好很多）。

具体就是 Computer-Use Agent：像人一样通过图形界面控制电脑。输入截图和一些上下文，输出鼠标点击、滚动、按键这类人的动作。他说现在很多 Agent 公司做的其实是 RAG、工具调用、MCP 和 API，把 LLM 接到强类型的工具上，但这解决不了长尾任务，因为不是所有软件很快都会有 API 或 MCP：

  • 惯性：大企业里事情推进慢。
  • 对抗性的原因：很多老软件按席位卖许可证，一个许可证配上 Agent 能干更多活，厂商就少赚钱，所以有动机拖慢这个过渡，而且有的厂商处于垄断地位。
  • 积极的原因：UI 里本来就凝结了开发者组织信息的心思，可以直接当作 LLM 的上下文；而且和人在同一个动作空间里工作，人可以示范给 Agent 看，Agent 也可以做给人看。

RPA（机器人流程自动化，用脚本按固定步骤操作界面）部署很重，流程稍变或者有歧义就失效。

演示：Surfer H 在 Google Flights 上订票

任务来自 WebVoyager 基准：在 Google Flights 上找 1 月 10 日从布宜诺斯艾利斯到阿姆斯特丹的单程商务舱航班，并给出最短航班的详情。视频里 Agent 点击出发地、输入城市；每一步输出三样东西：notes（它认为上一步发生了什么）、thoughts（现在想做什么）、action（比如点开“往返”下拉框改成单程）。日期最难，每个网站的日历都不一样，要一直点“下个月”直到出现 1 月再点 10 号，用 RPA 写这个循环很费事。然后选舱位、搜索、展开最短的那班。这里只用了一句提示词。

Agent 的结构

  • 记忆：任务、thoughts、actions、notes 和之前的截图。
  • Policy 模型：一个 VLM（视觉语言模型），可以是 GPT-5、Sonnet 或别的，输出动作。动作有 refresh、goto、scroll、wait、write、click。
  • Localizer（定位器）：动作需要目标元素时，再调用一个模型输出该元素的坐标。
  • Validator（验证器）：给出最终答案前，再调一次模型判断任务是否完成；完成就返回答案，否则把反馈写进记忆继续。

这些位置都可以用任何模型，也可以用 H 自己开源的 Holo 系列模型（字幕作 olo），他说在定位任务上是最强的。

为什么要做专用模型：国际象棋的算账

“现在是 2025 年，大家都是给大模型写提示词、填上 API key 就上线。”他用国际象棋解释效率：GPT-5 或 Grok 能下到大约 1600 Elo，比现场多数人强，没专门训练能做到这样很了不起。但 AlphaZero 是 3600 Elo，高 2000 分，意味着 GPT-5 大约十万局才赢一局。规模上，一边是约一万亿参数、跑在价值约一百万美元的 GB200 机柜上，一边是约 2000 万参数、能在便宜游戏本上跑。算下来 GPT-5 下棋的效率大约低 50 亿倍，在经济上没有道理。

H 想在电脑操作上推动性能和成本的 Pareto 前沿。在 WebVoyager（约 600 个任务，按成功率算）上，对比 GPT-4、GPT-4.1 等通用模型，他们的专用模型目前成本效益大约是 5 倍，目标是接近“50 亿倍”。在定位任务（给一张截图和一个意图，比如“点击出发日期输入框”，预测坐标）上，他画了一张性能对模型大小的图，提出“专用化前沿”：下方是通用模型（Qwen、Sonnet，GPT 更靠下），上方是专门训练过的模型，比如蚂蚁集团的 UI-Venus、字节跳动的 UI-TARS，都有大团队专门做，以及 H 两周前发布的 Holo1.5。他认为会看到越来越多这样的 Pareto 图，大家会因为通用模型不划算而转向专用模型。

Holo 怎么训练

  1. 从 Qwen2.5-VL 初始化，他认为这是当前最强的开源 VLM，因为输入是截图所以必须是 VLM。
  2. 监督微调（SFT），数据混合了：从大量软件和网站抓取的 UI 定位样本（截图、意图、坐标）；表格和界面上的问答等辅助任务；以及大量 Agent 执行轨迹。他们把 WebVoyager 扩展成约 10 万个合成任务，让 Agent 去跑，只保留成功的轨迹来训练，覆盖 Web 和 Android。
  3. 再做一点 GRPO（一种强化学习 RL 算法），端到端地优化“任务成功”，而不是复现训练数据。目前只在 UI 定位任务上做，希望扩展到更多任务。

为什么开放权重

  • 对客户：建立信任，知道 Agent 里装的是什么；H 是创业公司，客户不想完全依赖它，拿到模型就知道哪怕 H 倒了也能自己跑；是开启对话的好话题；可以先试再买。
  • 对品牌：不用相信他，下载权重自己跑评测，性能可验证。
  • 对技术：他们也是开放生态的消费者，从 Qwen-VL 起步，用现成的训练管线（比如 Hugging Face 的 TRL）和推理引擎（vLLM），不用重新造轮子，专注在自己增加价值的地方。
  • 对员工：创业成功的路可能很长，开源发布给了中间里程碑和曝光，有助于留人和招人。

下一步

研究上：从 Web 扩到桌面和手机；提高泛化，以前在 WebVoyager 上训练也在上面评测（他说因为是 RL 勉强可以接受，但并不好），现在只在那个大的合成任务集上训练；更多人在回路里标注，Agent 卡住时人直接示范，他们在做相应工具；更多多轮、端到端的强化学习。平台上：演示里的 Surfer H 会很快公开，有门户可以注册、拿 API key、启动 Agent 或调用模型推理。

问答

  • 最大的挑战：部署上问题很多。本地跑还是在虚拟机里跑？凭证怎么办？订完机票之后呢，是否已登录，把信用卡号放进提示词显然不是好主意。他认为角色和权限是个机会，人用的界面里这些已经有现成做法可以复用。具体看部署方式，比如 Agent 直接控制你的笔记本、用你的凭证，但下单或发邮件前先发确认给你。
  • 商业模式：Surfer H 展示版能试用但不打算收费。他们不想按 token 收费，认为那是“向下竞争”；会用前沿部署工程师（Forward Deployed Engineer）模式，CEO Gautier（字幕作 goautier）来自 Palantir，在那里做这个很成功。按价值收费，拿客户多做成的事情里的一部分，“按 OpenAI 那种每百万 token 2 美元的方式，我们赚不到钱”。主持人补充说电脑操作 Agent 要用多少 token 本来就很难估。

08. Andreas Kollegger（Neo4j）：和数据一起 vibe：多 Agent 建知识图谱

直播位置 4:53:48–4:58:34 · 英文原题 Vibing With Data

Andreas Kollegger 是 Neo4j 开发者关系的生成式 AI 负责人，主持人介绍他自称“技术人文主义者”，为 NASA 做过系统，在赞比亚做过医疗信息化，座右铭是“万物相连”。这是一场 5 分钟的速通，完整版他之后再分享。

他接着上一场说：一做 Agent 就会遇到各种问题，最后走向多 Agent 系统。原因是单个 Agent 职责太多会困惑，会出现 context rot（上下文越来越长后质量下降）和语义漂移，所以要把问题拆小，让每个 Agent 专注一部分。拆开以后还能给每一部分用专用模型，他说专用模型在各项任务上都胜过通用模型。他做的多 Agent 系统用来帮人建知识图谱：顶层 Agent 和用户对话、弄清用户要什么，下面有三条专门通道，分别处理结构化数据导入、非结构化数据导入，以及建好图后的检索（GraphRAG）。代码全部开源。

演示视频：他说想建一个物料清单（BOM）图谱。系统先在各 Agent 之间路由，判断还不清楚用户要做什么，于是追问。他回答：想从产品一路追到物料清单再到供应商，以便对网站评论里报告的产品问题做根因分析。他说人在回路里对他很重要：Agent 复述“我理解你是这个意思，对吗”，他批准后才进入下一步。第二个 Agent 用文件系统工具浏览可用文件、查看内容，推荐了产品、装配和供应商相关的文件，再请他批准。第三个 Agent 只负责根据用户目标和数据提出图模型方案，他滚动检查节点是否齐全、连接是否合理，然后批准。最后交给构建 Agent 导入数据、建图，还推荐了几条查询。他说构思阶段可以用 OpenAI 这类通用模型，一到专门任务，专用的 Agent 和模型就最有价值。到数据库里查一个叫 Stockholm 的产品（他忘了是桌子还是椅子），能看到它由哪些组件构成、组件有哪些零件、零件来自哪些供应商，全部由多 Agent 系统现场生成。时间只剩 10 秒，没有问答。

09. Vaibhav Srivastav（Hugging Face）：2025 年开放大模型的现状

直播位置 4:59:21–5:22:58 · 英文原题 State of Open LLMs in 2025

Vaibhav Srivastav（VB）是 Hugging Face 开发者体验与社区负责人，长期推动开源、音频和端侧机器学习。他说这是一份 2025 年开放 LLM 的现状报告，希望大家听完就去试。

开放模型能打吗

他引用 Artificial Analysis（一家专门用统一评测集测闭源和开放模型的公司）的综合智能指数，涵盖数学、编程、科学推理等。前十里有三四个开放模型。绝对分数上，推理强度设为 high 的 GPT-5 是 67，OpenAI 的开放模型 gpt-oss 是 58。他补充一个前提：闭源模型达到这些分数的成本更高、用掉的 token 也更多（要推理更久）。

好用吗：三种用法

  • Serverless API：和用 OpenAI、Anthropic、Gemini 一样，五行代码，给模型 ID 和提示词就有输出。2025 年 OpenAI 的 Chat Completions 和 Responses API 格式已经成了标准，几乎所有开放模型都能这样访问，把 GPT-5 换成 gpt-oss 或最新的 Qwen 即可。路由服务可以选 Hugging Face Inference Providers、OpenRouter 等。
  • 托管部署：去一个 LLM 市场（Hugging Face Inference Endpoints、Lambda Labs、Prime Intellect、Modal 等，竞争很健康），选 GPU（H100、A100、T4、L4 等看预算），比如选 Qwen3-Next，点部署，两三分钟后拿到一个端点。适合想要更多控制、又没有专门 DevOps 或 MLOps 团队的情况。
  • 自己部署：选推理引擎（vLLM、SGLang、TGI 等），自己准备 GPU 集群，云上的或“地下室里的一张卡”都行，得到私有、安全的部署。适合需要完全掌控提示词和输出去向（provenance）的情况。

为什么需要这么多选项：这是经典的自建还是购买的问题。不管你在创业的哪个阶段，都应该保留可选性，有一个挂了还能切到另一个，不要只依赖一家。他举了 Anthropic 最近发的事故复盘博客（他说“无意冒犯，我每天都用 Claude，Anthropic 的人我爱你们”）：Claude Sonnet（他记得还有 Opus）在上下文窗口和请求路由上出了问题，结果是同样的调用方式下，有一小部分请求的输出质量下降。你在上游没有任何可见性，只能看到输出变差。还有“Sonnet 白天变笨、晚上更聪明”的段子，很多是心理作用，但拿不到权重就很难查清楚。他引用 Karpathy 的话：“not your weights, not your brain.”

三个趋势

推理模型。到 2024 年 12 月为止，OpenAI o1 是最强的推理模型，也就是在给出最终答案前先“思考”的模型，思考后质量更高，但 o1 把思维链（Chain of Thought）藏起来了。2025 年 1 月 DeepSeek 发布 R1：6850 亿参数，MIT 许可证可商用，和 o1、当时的 Gemini 有竞争力，而且完整公开思维链，思维链不再是闭源独有的东西。DeepSeek 还证明了可以把 R1 的思维链蒸馏到小模型里：他们蒸馏到一个 Qwen 8B 上，专门在数学上训练后，打败了一个大 25 倍的开放模型（他说的是 2350 亿参数）。从那以后推理成了标配，GPT-5 系列都有推理并能设定推理强度（low、medium、high），开放模型也几乎都有思考版和非思考版。

上下文长度。LLM 的表现取决于给它多少上下文，比如总结论文时只给摘要和给全文差别很大。2024 年开放模型（Llama、Qwen、Gemma 等）的上下文一般是 32K 到 64K token，做不了长上下文任务；2025 年 128K、256K 成了标准，Qwen 有支持 100 万上下文的模型，Llama 4 甚至有 1000 万。上下文变长的同时成本在下降，来自软件、硬件和架构上的优化，同样一欧元或一美元能买到的比去年多得多（他引了 Artificial Analysis 的图）。

上手门槛。2024 年部署本地 LLM 很陡：要检查 Chat Template（把对话格式化成模型训练时见过的样子的模板）对不对，那时的模板常常是坏的、没有标准；工具调用很难；不知道模型训练时的精度和部署时的精度是否一致；还有延迟和显存问题。2025 年大家都默认用 ChatML 格式；4 bit 和 8 bit 量化（Quantization，用更少的比特存储权重以省显存）成了一等公民，新模型基本是 FP8 原生，不损失性能；gpt-oss 之后 4 bit 也在变成标准。

闭源模型还在哪些地方领先

  • 通用推理：开放模型在工具调用、数学、科学、编程等单项上很强，但没有一个在所有方面都强，而闭源模型是一个模型什么都行。
  • 端到端多模态：尤其是 OpenAI 的 GPT Realtime、GPT-4o 和 Advanced Voice Mode，可以聊五分钟，让它说快点慢点、教你法语德语。开放生态还没到这一步。
  • 安全和防越狱的配套：闭源模型已经做得很成熟，用开放模型往往要自己定义。

他的试用步骤：挑一个简单项目，把闭源模型换成开放模型，用原来的测试评测，再换另一个模型，调提示词，然后上线。

他期待的方向

  • 更小的领域专用模型，比如 Google DeepMind 的 Gemma 团队最近发布的小型多语言模型（字幕听作 2.9 亿参数，实际发布的是 Gemma 3 270M），能在浏览器和设备上跑，成本低、更多人能用。
  • 按强度推理：同一个模型设 low、medium、high，相当于一个部署当三个模型用。
  • 更好的量化方案，FP4 和 4 bit 成为部署的默认。
  • 更稀疏更快：前沿 LLM 都是 MoE（混合专家，每次只激活一部分参数），越稀疏激活参数越少，推理越快，他希望社区在这上面加码。

结尾两句：离源头近一点，默认选开放。

10. Aparna Dhinakaran（Arize AI）：Agent 的系统提示词学习

直播位置 5:23:48–5:46:26 · 英文原题 System Prompt Learning for Agents

Aparna Dhinakaran 是 Arize AI 联合创始人兼 CPO，此前在 Uber、Apple、Adobe 做机器学习基础设施。Arize 做 AI 可观测性（Observability）：帮团队给应用做追踪（Tracing）、评测（Eval），并通过提示词迭代来改进。她开场说会顺便回应 swyx 前一天关于评测的“争议言论”。

Agent 为什么脆弱

她放了一条 Hacker News 帖子：有没有 AI Agent 真正干活的例子，不是改了名字的工作流自动化？她说这种怀疑来自 Agent 在真实世界里太脆弱。好的 Agent 有几个共同模式：系统提示词持续更新（这一场的主题，提示词一成不变，Agent 就学不到环境里的东西）；会更新的规划（Cursor 和 Claude 里那些待办列表）；关于怎么调用工具的指导；上下文工程，尤其是 Agent 之间交接时上下文没传好。

Karpathy 的“系统提示词学习”

Karpathy 5 月有一条很火的推文：LLM 学习缺了一个大范式，他叫它 system prompt learning。预训练学知识，微调学习惯性行为，但人类很多学习更像改系统提示词：某件事没做好，给自己记一条“下次遇到这种情况就这么做”。放进预训练或微调都很费劲，而你手上本来就有英文的反馈和解释，可以直接写进系统提示词。这种反馈的维度比 RL（强化学习）里一个标量分数高得多。

她举了 GitHub 上泄露的 Claude 系统提示词，篇幅很长（她念的数字是 2.4 万，单位字幕不清），对各种情况下怎么表现写得很细。她的结论是这不可能一次写出来上线，一定是收集数据、看 Claude 哪里没做好、再反复迭代出来的。

三类提示词优化方法

  • 传统 RL 式：标量奖励加类似梯度下降的算法去更新系统，需要大量样本，成本高。
  • Meta-prompting（元提示）：直接改提示词，但仍然用标量分数决定怎么改。
  • Prompt Learning（受 Karpathy 启发）：用英文反馈改提示词。输入是数据（输入、输出、解释或标注）加原始提示词，一起放进元提示，得到新提示词。

在 Cline 上做的实验

Cline 是领先的开源编程 Agent，系统提示词完全公开，大约 30 页（幻灯片上大幅删减了）。它有一个可以加 Rules 的段落，类似 Cursor 的 rules，开箱是空的。实验设置：

  • 基线：空规则的 Cline 在 SWE-bench Lite（300 多个真实软件工程问题）上跑 Plan 模式。Cline 有 Plan 和 Act 两种模式，Plan 只生成计划、不写代码运行；Act 模式的结果他们还在做。基线大约 31%。
  • 失败例子一：marshmallow 库（转换复杂数据类型），任务是修复输入为 None 时程序崩溃。Cline 只加了“如果是 None 就 return”，但输入还可能是列表或复杂类型，它没检查所有情况，直接跳到最小修复。
  • 失败例子二：SymPy（符号数学库），矩阵和 @ 这类运算符组合时错误地按乘法处理，正确做法是报错。Cline 忽略了 Python 语言在回退时该怎么做的约定，写了个只覆盖部分情况的临时修复。
  • 方法：用原始提示词跑完整个数据集，把 Cline 的方案和 SWE-bench 自带的标准答案（真实 PR 和测试补丁）一起交给 LLM-as-a-Judge（让另一个 LLM 当评委打分）。不只要“对或错”，还要它写出为什么错。她说不管是 LLM 评委还是人工标注，这段解释就是 Karpathy 说的英文反馈。然后把原始提示词、问题、Cline 的方案、对错和解释一起放进元提示，生成新的系统提示词。
  • 结果：新提示词的 Rules 段从空变成了很多条，5 到 10 轮后接近 100 条，对应 Cline 常犯的各类错误。前面两个失败例子用新提示词重跑都对了，各自有一条对应的规则。数据按 50% 训练、50% 测试切分，大约 10 轮后测试准确率从约 30% 提到约 45%，提升约 15 个百分点。她说用 Cursor 或 Cline 的人今天就能这么做。
  • 她们还在 BBH（一组对语言模型更难的任务）上测，在 salient translation error detection、snarks 这类较难的类别上，5 轮就有大幅提升，其他类别几乎没有退步，结果之后会公开。

给 Agent 开发者的建议，以及对 swyx 的回应

第一是收集错误，做评测或标注，否则不知道该修什么。她展示了 Arize 里对整个应用做追踪的界面。swyx 前一天在主题演讲里质疑评测该不该成为上线前的门槛，她同意不该：应该先上线。她认为大家很少谈的是在线评测（在生产数据上跑评测）更重要，因为那是你自己的数据、真实的 traces 和日志，而不是“写一些胡扯的测试当门槛”；然后信任这些 traces，把它们喂回迭代。迭代过程中跑的离线评测，她当作单元测试：重要，但真实生产系统的可见性往往更重要。她们在迭代时就用实验视图对比不同系统提示词和规则的效果，像单元测试一样用来决定是否部署。

其他领域的结果：结构化 JSON 网页生成，5 轮后准确率明显上升，但规则不是越多越好，规则集变大时准确率不一定一直涨，要按自己的场景调规则数量；客服问题分类，从 1 轮到 5 轮准确率提升约 8 到 9 个百分点。她预计接下来大家会更多谈“提示词怎么持续从环境里学习”：有的靠人在回路里改，更多会完全自动化，收集数据、跑评测、跑提示词优化、更新系统提示词。

问答

  • 新提示词会不会越来越长：可以在元提示里加约束，比如新提示词不超过多少字。
  • 样本太多塞不进元提示的上下文窗口怎么办：她说这是更难的问题。生产跑得越久，失败场景越多，这是好事。她们建议做错误分析和错误归类，按类别挑代表性样本放进元提示，不必每个错误都放。

11. Steeve Morin（ZML）：在 CPU 上跑稀疏对数注意力，走向无限上下文

直播位置 5:47:15–6:09:39 · 英文原题 Towards unlimited contexts: faster-than-GPU sparse logarithmic attention on CPU

Steeve Morin 是 Zenly（后被 Snap 收购）创始团队成员，现在是 ZML 创始人。ZML 在做一个通用推理栈：同一套代码、甚至同一个二进制，能在任何芯片上跑任何模型。但这次他讲的是他们认为 LLM 最根本的问题之一。

问题：注意力是平方复杂度

他以 Llama 架构为例，每生成一个 token，每一层都要做一次注意力（Attention）。注意力的计算量随序列长度平方增长，加一点内容就要多算它的平方，这限制了从硬件到上下文窗口的一切。他让大家“眯眼看”注意力公式里的 softmax：对所有元素取指数再除以指数之和，结果是小信号被放大、大部分值接近零。他展示了真实的注意力输出图，大部分是空的，只有零星的“黄点”，所以有大量几乎无用的计算。

把注意力当成图问题

作为前后端工程师，他看着这张图想：这是不是一张图，能不能只算黄点？他说确实是一张图，只是在潜在空间里。把它建模成图问题而不是纯矩阵乘法，复杂度可以做到 log n，随上下文增长曲线趋平，为无限上下文铺路。麻烦在于图需要分支，而 GPU 很不擅长分支；CPU 擅长。所以问题变成：只在 CPU 上算，能不能足够快？

算时间预算

  • Llama 8B 有 32 层，想跑到每秒 100 token（大约 RTX 5090 的水平），每层预算约 300 微秒。
  • 注意力之外的其他运算已经占掉约 200 微秒（字幕里说成毫秒），留给注意力约 100 微秒。
  • 因为只算黄点，CPU 上实际计算注意力只花约 30 微秒。他展示了一层的完整 trace。

附带好处：KV Cache 离开 GPU

KV Cache 是模型把之前每个 token 的 Key、Value 存下来，避免重复计算的缓存，它常常占掉 GPU 显存的大部分，在生产部署里带来静态路由等一堆问题。注意力在 CPU 上算，KV Cache 就可以放在系统内存里，GPU 只放模型，而且 GPU 完全无状态。流程是 GPU 把数据发给 CPU，CPU 计算并更新 KV Cache，再把注意力结果发回 GPU。代价是需要很多 CPU 核，大约每个 KV 一个核。

CPU 能不能通过网络借来

GPU 服务器的 CPU 往往很弱（除了给 PCIe 通道几乎没用），既然注意力和 KV Cache 已经和 GPU 分离，能不能从网络上借 CPU？30 微秒算完后还剩约 70 微秒。他算物理上限：一个 8B 模型每层每个请求要传的数据约 10 KB（按注意力头、KV 头等估算）；保守按 10 Gbit 网络（不用 InfiniBand），一次往返约 16 微秒。用约 15% 的时间预算换来几乎无限、能随时开关的 CPU 核，他认为很划算。架构是 GPU 做稠密计算，把数据通过 UDP 发到另一台机器，CPU 算注意力再发回，而且要比 GPU 自己算更快，能做到是因为他们算得少很多。

他放了一次普通 ping 的结果，延迟远超预算，“物理站在我们这边，工程不在”。办法是绕过内核（Kernel Bypass）：Linux 内核在这个尺度上太慢，他们用 DPDK，把网卡驱动直接做进应用，以极低延迟和网卡通信。理论 16 微秒，实测约 20 微秒，仍在预算内。这套东西叫 attnd（字幕作 attention D）。

演示

  • 录屏：一台有 GPU 的机器和一台没有 GPU 的机器。左边是 attnd 在无 GPU 机器上跑，所有核 100%；右边是标准 Llama 推理，模型侧没有任何改动，两边通过网络通信。播放到一半 QuickTime 窗口找不到了。
  • 现场：既然 KV Cache 不在 GPU 上，就可以把 GPU 塞满模型。他在 32 GB 显存的 GPU 上跑 FP8 的 Qwen 32B，加载完只剩 20 MB 显存，正常情况下没有任何 KV Cache 空间，这个模型根本跑不起来。下方终端跑 attnd，上方让模型写一个 MLP 的 CUDA kernel。第一次崩了（“这说明是真演示”），第二次成功生成。他说据他们所知这是第一次做到。为了证明不是假的，他杀掉 attnd，生成立刻停止，因为数据包“打进了虚空”。项目开源。

问答

  • T 恤上写的是什么：致敬 Zuckerberg 那件 “Zuck or nothing” T 恤，他们的版本意思是“ZML or nothing”。
  • 为什么 GPU 不擅长分支：GPU 按 SIMT（单指令多线程）方式工作，一组核共享同一个指令序列。有分支时，走一边的核要等走另一边的核做完。比如按奇偶数分两半做不同的事，中间有个 if，GPU 总有一半在睡觉。所以图像处理（每个像素做同样的事）和矩阵乘法很适合 GPU，分支多的就不适合。
  • 是否只适用于 Transformer：和 Transformer 的注意力相关。大家都在想办法绕开 n²，它是 HBM 存在的原因，也是大家拼命量化缩小数据的原因。也有 Mamba 这类线性架构和各种混合架构，但到目前为止还没有人把 Transformer 拉下来。
  • ZML 接下来：他们在推理的每一层都追求极致，从个位数微秒级的东西到吞吐，比如有基准能在一秒内从 SSD 加载整个模型。他说现在推理太贵，而且很久以来瓶颈已经不是算力。目标是围绕“通用芯片支持、极低延迟、每条路径都是热路径”建一个软件栈和产品线。演示的注意力机制理论上可以用 PyTorch 实现，但可能只有每秒一个 token，因为 30 微秒会变成毫秒。框架是开源的，他们自己是第一批用户，变化快，会有更多演示。

12. Tuana Çelik（LlamaIndex）：做一个开源的 NotebookLM 替代品

她们发现可以直接用 LlamaExtract 生成笔记本的初始内容：定义一个 schema，要文档摘要、要点列表、问答对。

项目叫 Notebook Llama，她说主要是同事 Clelia（开源工程师，字幕作 Cleia）的作品。她强调这不是打磨好的成品，只是一个起点，欢迎贡献。功能有：思维导图生成（第一个实现的）、对文件问答、抽取表格和图片、播客生成，以及最近加上的可观测性。

LlamaIndex 的 Workflows 是一个可以继承的类，由两样东西组成：step（方法）和 event。每个 step 接收某种 event，也可以发出 event，event 可以完全自定义。首页流程需要三个自定义 event：开始事件 FileInputEvent（就是一个文件名）、结束事件 NotebookOutputEvent（包含思维导图、摘要、要点等），以及中间的 MindMapCreationEvent（Clelia 写的代码，用摘要和要点从头生成思维导图）。step 有两个：extract_file_data 接收 FileInputEvent，可以分支，失败时直接返回一个空的 NotebookOutputEvent 并附上失败原因，成功时发出思维导图事件；generate_mind_map 生成思维导图并组装最终的 NotebookOutputEvent。这样应用的路径是她们设计好的，不依赖 LLM 先做决定。

为了满足“可复用”的约束，大部分逻辑都写成了 MCP 服务器里的工具，想用思维导图生成器的人可以直接拿去配 Claude 用。她说 MCP 工具最重要的是描述，因为 LLM 只能靠描述判断该不该调用。

  • 文档问答工具：用 LlamaCloud Index 当向量库（也可以接你自己的向量库），描述很简单，“查询一个 LlamaCloud 索引”。内部用 LlamaIndex 框架的 CitationQueryEngine，LLM 可替换，检索器是 LlamaCloud 索引，还做了 claim verification（声明核验）。这里选开源框架，是为了方便换模型，或者放进完全不同的工作流。

最近的新功能：已有 MCP 服务器的话，可以把其中的工具直接交给 LlamaIndex 的工作流 Agent 或 Function Agent，像普通工具一样用，不必自己定义。反过来，LlamaCloud 上的任何抽取 Agent 和索引也可以作为独立的 MCP 工具运行，配上你自己写的描述。这个 MCP 服务器也是开源的。

  • 最好的 Agent 框架是哪个：她给了一个“很政治”的回答：大家都在奔同一个目标，看你要什么样的开发者体验。有的框架集成最新研究快，有的更稳定，有的自带可观测性和追踪，有的专注别的 AI 功能。主持人追问后她说：“我是 DevRel，所以答案是 LlamaIndex。”

在 Stream 功能里可以写系统指令（比如“只用法语和用户说话”），共享屏幕或摄像头，让模型实时互动。她开启 Google 搜索 grounding（让回答以搜索结果为依据），共享了 Google Colab 的页面（“别看我有多少个未命名笔记本”），问 Gemini 屏幕上有什么，它答对了；再问怎么改 Colab 的运行时类型，它一步步指导她点哪里。问巴黎今天会不会下雨时，回答没对上，她说模型能查 Google 搜索，也能用你自己定义的函数调用。

演示三：Colab 里的数据科学 Agent

她说这是一个“很少被重视”的功能。在 Colab 里给出一个 CSV 文件路径（也可以给 URL 让它抓网页），输入“做探索性数据分析，并建一个预测加州房价的模型”。Gemini 先列计划：加载数据、EDA、特征工程、预处理、模型选择，然后逐个写代码、执行、根据每个单元格的输出决定下一步，生成详细的图表，最后选了线性回归，训练后给出 MSE、R² 和结果总结。她 2009 年开始做机器学习，那时 scikit-learn 还没成气候，看到这些工具的变化让她很感慨。

Veo、Imagen、Lyria

Google 公开的生成式媒体模型有三个：Veo（视频）、Imagen 4（图像）、Lyria（音乐）。她说“没有 Karpathy 引语的 AIE 演讲是不完整的”，并说她看好视频，因为它适合教育和沟通，她的侄子侄女已经说“没人读东西了”。Veo 2 时代的功能：参考图驱动的视频（一个人加一条走廊，生成这个人走在这条走廊里；同一个小怪物出现在不同场景和光照里）、图生视频、带引导的动画（比如“一个女人走在德州的路上”）、镜头控制、外扩画面（Outpainting，DeepMind 用它修复《绿野仙踪》以便在拉斯维加斯 Sphere 上放映）、增删物体（Nano Banana 也能做）、用参考人脸动作驱动头像、首尾帧插值。Veo 3 更进一步，能生成带声音的写实视频，她放了几段纯靠提示词或提示词加图生成的片段，还有 Google 巴黎办公室同事做的一段像 Daft Punk 风格的短片。

她做过一个对比实验：复刻一条电视上的 Chick-fil-A 广告（广告里的人恰好也叫 Paige）。用 Veo 2 时：把原视频给 Gemini 2.5 Pro，切成 8 秒片段并为每段生成提示词，引导 Veo 2 生成（Veo 2 没有声音）；用 Gemini 的 TTS 生成旁白，用音乐模型按 Gemini 2.5 Pro 写的描述生成 30 秒配乐，再用 Camtasia（也可以用 MoviePy）拼起来，端到端大约 25 到 30 分钟。她说同事指出那个炸鸡的面包糠明显是 Popeyes 的不是 Chick-fil-A 的。用 Veo 3 时：让 Gemini 2.5 Pro 只为前 8 秒写一个详细提示词，交给 Veo 3，一个提示词就得到带声音的结果。

Genie 3 和端侧模型

Genie 3 是探索世界的前沿模型，用方向键导航，背后用了和 Veo 类似的技术并大量集成 Gemini，她称之为一种 Harness（把多个模型和工具组织起来协同工作的外层框架）式的做法。可以用提示词或图片生成世界，而且有一致性：在墙上画了东西，或者低头看到自己的雨靴是黄色的，整个探索过程中都会保持。还能体验在佛罗里达公路上遇到飓风。可信测试者计划很快会开放。

小模型方面：Gemini Nano 能放进手机和浏览器。Gemma 3 的 27B 版本能放在一张 H100 上，而跑 DeepSeek R1 或 V3 需要 32 张。Gemma 3n 是 40 亿参数级别，能在笔记本上本地跑、下载权重免费用，能力超过了六七个月前 Google 最好的 Gemini 1.5 Pro，那个模型要多块 TPU。她由此推断，六个月后今天的前沿能力（Genie 3、Veo 3、Nano Banana）或类似的东西大概都能在本地设备上跑，而前沿本身也会大不一样。她认为开放模型和本地模型是未来，Google 在 Pixel 上的 Gemini Nano 之外，5 天前还宣布了 Chrome 里的 Gemini：能跨标签页总结信息，很快还会有类似 Project Mariner 的功能，比如收到一封邮件请你买东西，就让它去 Instacart 把东西放进购物车并结账。

最后她说现在是创业的最好时候，几乎没有什么能阻止你做出一家现金流为正的公司；合作的 VC 比以前更愿意支持单人创始人；小团队能做出大量工作，她举 Black Forest Labs 和 Mistral。作业是去 ai.dev 拿一个 API key 开始用 Gemini。

问答

  • Veo 2 还有用吗：有些功能目前只有 Veo 2 API 有，正在迁移到 Veo 3，以后应该不需要 Veo 2。Veo 3 的价格过去一两个月已经降了不少，建议优先用 Veo 3。
  • Genie 3 有没有用来训练自动驾驶和机器人：她认为 Genie 3 目前没有为自动驾驶生成训练数据。但 Gemini 家族的预训练和后训练里有合成数据；Agent 在游戏里完成任务、探索世界的录像，对世界模型、Veo 3 和 Gemini 的视频理解都是有用的训练数据。
  • DeepMind 模型有什么独特之处：多模态输出（音频、视频）走在前面；开源也是大家在意的，Gemma 团队做得很好；她最期待 Chrome 里的 Gemini：数据留在本地，能在零成本的本地模型和服务器端模型之间高效切换。

14. Neil Zeghidour（Kyutai）：把实时语音 AI 做到规模化

直播位置 7:54:17–8:22:38 · 英文原题 Scaling real-time voice AI

Neil Zeghidour 是 Kyutai 联合创始人、首席建模官，此前在 Google Brain 带生成式音频研究，更早在 Facebook AI Research 做语音识别。Kyutai 是两年前在巴黎成立的非营利 AI 研究实验室，资金来自 Xavier Niel、Rodolphe Saadé 和 Eric Schmidt 的捐赠（字幕作 Xavier Rodul Sad）。实验室专注开放研究和开放科学，主攻多模态 LLM；因为是非营利，所有成果都公开发表并开源，也培养博士生、和学术界合作。

没被满足的需求：交互式、海量的语音

现在 ElevenLabs、Azure 等方案主要做离线内容：有声书、电影里几句合成台词、游戏里的小角色。这类内容质量要求高、生成量小，有声书生成一次被很多人听，可以花钱花时间反复调。没被很好解决的是交互式、量极大的内容：现场生成、马上处理、只有一两个人听、用完就扔。比如游戏里能对话的 NPC，每段对话只有一个玩家听到；人形机器人以后会大量存在，和它们的交互主要靠说话；个性化新闻，每个人有自己的新闻摘要而不是看同一份。这些都需要比现在多得多的合成语音。

语音 AI 的任务不只语音合成：合成（文字到语音）、转写（语音到文字，比如会议）、翻译（最好实时并保留声音）、变换（各种声音效果，他说 TikTok、Snap 里的视觉特效大量用 AI，声音特效还停留在升降调、变速，可以丰富得多）、完整的对话体验（语音 Agent）。质量要求包括：保真度（像录音棚而不是地铁里用手机录）；能设计声音，克隆或者用自然语言描述（“一个烟抽太多、嗓音低沉的中年男人”）；情绪理解和表达要对，你在哭它却说“太好了”就不对；对话流程要自然，现在和 AI 说话需要很多“纪律”；延迟要极低。规模化有两条路：在云上大规模生成（比如每月几百万小时的 NPC 语音），或者在设备上小规模生成（每个人在自己的 PS5 上跑本地 TTS）。

质量和规模的取舍

  • 语音合成：有声书质量高、规模小（做一次哈利波特有声书卖很多钱）；语音信箱规模大、质量可以很差；两者交叉的是个人助理，每个人都要自己的交互，又想要有声书级的质量。
  • 翻译：外交口译对可靠性要求极高，不是他们现在的重点；Netflix 配音质量要求也极高；旅行时的翻译质量可以低一点，但要能在设备上跑（他提到最近 AirPods Pro 的相关发布）；交叉处是会议、电话和小创作者，小创作者的内容每份看的人少，但总量巨大。
  • 语音 Agent：替人向航空公司索赔的创业公司，一次能拿回几百美元，语音花 10 美元也行；麦当劳点餐机器人必须极便宜，质量差点只要能下单就行；交叉处是游戏 NPC、互动播客、在线教育，用语音学语言既要便宜（没人想每月花 500 美元），又要体验好。

质量：Moshi 和全双工对话

Kyutai 第一个项目 Moshi 是第一个全双工（Full Duplex）对话 AI，比 OpenAI 的 Advanced Voice Mode 发布还早一年多。他说现在所有对话机器人，没有例外，仍然是半双工的，像对讲机：AI 要么在说要么在听，所以你打断它或者咳嗽一声，它以为你在插话，对话就断了，你得去适应它的限制。全双工是模型一直在说也一直在听，随时可以插话也可以被打断，像人类对话。和家人打电话时，大约 20% 的时间双方在同时说话。

另一个目标是去掉级联系统。典型的语音机器人是语音转文字、LLM、文字转语音三段，合成一个模型就不会因为经过文字而丢失情绪信息，延迟也更低。做法借鉴文本 LLM（给一串词预测下一个）。直接把原始音频放进 LLM 行不通：“Kyutai is an AI lab based in Paris” 八个词，token 很少，念出来约 3 秒，按 24 kHz（还不到录音棚质量）就是 72,000 个采样值；自注意力的成本和序列长度的平方成正比，用 LLM 处理音频要比文本贵约一亿倍。所以他们发明了 Mimi：一个音频编解码器（类似 MP3、Opus），压缩得很密，像文本表示一样。同一句话从 72,000 个采样变成 37 个 token，LLM 就能直接预测这些音频 token，再由一个生成对抗网络（GAN）解码器重建高质量音频。音频生成就变成了语言建模。

Google、OpenAI 等的标准做法是音频 LLM 加一个 token 序列，序列里轮流是模型和用户，根据前一轮预测下一轮，能做出现在的语音机器人，但仍是对讲机。Kyutai 的 multistream（多流）建模是并行两条流，可以两边同时说、同时沉默、一个说一个听。他放了一年多前发布时的演示：和 Moshi 的对话（“行星是 Sirius 22，规划一条航线”“大约 5 个月到达”），延迟仍是最低的，有时猜到你要说什么就提前开口，同时说话也没有问题；以及他在很吵的办公室施工现场和 Moshi 对话，全双工模型不需要别扭的轮次判断，所以对背景噪声很鲁棒，“我自己都听不清，模型没问题”。

能力：同一个架构做很多任务

  • 实时语音翻译：两条流一条是他说法语，一条是他说英语，从法语流预测英语流就是实时语音到语音翻译。演示里手机开着飞行模式，模型完全在手机上运行，可以在 Hugging Face 免费下载。他说这个模型是一个硕士实习生几个月做出来的，因为架构一样，只要生成新的训练数据。另一段演示是同事在放着很响音乐的环境里测试，仍能实时翻译（背景音乐是 Kavinsky）。
  • 实时转写：从语音流预测文本流。他说这是目前世界上最准、最快的实时转写，开源。现场演示切回英语后正常工作。
  • 流式 TTS：反过来从文本预测语音。特别之处是在文本上流式，打字时词一出来就开始发声。对人没用，但接 LLM 很有用，不用等 LLM 写完一段才开始合成。演示里播出了一句“接下来是 AI Engineer Paris 的 afterparty”，他赶紧让观众别走。
  • 带说话人标注的转写：同时预测文字和“谁在什么时候说”，会议里除了转写文本，还要识别说话人并对上各自的转写，仍然实时。他提到当天另一场 pyannote（字幕作 Pyote）的演讲。演示素材是一段法庭对话。

把实时 STT 和实时 TTS 夹在一个 LLM 两边，又回到了级联系统，延迟更高、也不是语音到语音。但好处是完全可定制，不用动 LLM：你的 LLM 已经有视觉、函数调用、工具、RAG，大多数人只想让它开口说话，不想训练一个替换整个文本栈的新模型。这个系统叫 Unmute。演示（他说半小时前这个演示还让他慌了）：上传一段 10 秒声音样本，他用的是一位法国将军的声音（字幕不清，从回答里“二战最黑暗的日子”“团结法国人民”推断是戴高乐），再写一段人设提示词。他先用法语聊，然后请“将军”为英语观众切换成英语，解释音频语言模型，“将军”回答说想到了沟通的重要性，二战时要清楚而坚定地传达信息，这些模型也必须精确。

规模

  • 设备上的语音翻译模型也能在云上跑，一张 H100 能同时处理 320 路对话。
  • 他们的流式 STT 比 Whisper 更准，吞吐（每秒能处理的音频秒数）约 400 倍实时，Whisper 流式约 5 倍。
  • 开源 TTS 和 Dia、CSM、Chatterbox 等主要开源 TTS 相比，吞吐高 100 倍以上，词错误率更低，发音更准。

他说这样才能支撑前面那些应用，比如开放世界游戏里每人身边有 20 个能对话的村民。落地例子是法国报纸 La Provence（字幕作 LA province）：网站上的文章可以用他们的模型朗读（他为文章话题道歉），这是“一份内容给所有人”；App 里还有个性化新闻摘要，只有能规模化的方案才能给每个读者生成自己的新闻流。他们的目标是消除质量和规模之间的取舍。代码在 GitHub，预训练模型在 Hugging Face，研究都发在 arXiv 和会议上；他们也考虑开放有限的 API，给想做大规模生成原型的人，欢迎游戏 NPC、客服自动化、教育应用等场景通过 Google 表单联系。

问答

  • 做全双工模型最难的是什么：2024 年初开始做时，对话是没人攻下的任务，TTS 已经能用，他在 Google 做过音乐生成。Kyutai 是小团队，策略是选很新、靠深度专业知识就能解决、不需要堆资源的问题。他喜欢音频的一点是模型很小，大约 10 亿到 30 亿参数，难点在于理解人的听觉和发声机制并把这些知识放进机器，光有一般的机器学习知识不够，要深入了解音频领域。
  • 为什么做非营利：目标是孕育突破性的新想法。他举 Transformer：它是为机器翻译这个具体应用发明的，但出自 Google Brain 这个基础研究实验室，因为它是对序列建模的彻底重想，和当时的 RNN 没有关系，需要愿意从第一性原理出发、可能浪费一年。这在创业公司很难做，所以选择非营利，可以尝试、失败、专注做大事，捐赠人也乐意支持。
  • 为什么也做商业合作：他们的研究模型在基准上已经能和商业方案竞争，所以愿意让产品用上；比如有人需要某种特定语言的模型、并同意开源，他们可以合作，只是团队小，要找到可行的方式。
  • 接下来：Moshi 是第一个全双工模型，而 Unmute 是级联的；整个领域似乎又回到了级联，因为对产品来说更简单方便，全双工模型从 Moshi 之后进展几乎停滞。他认为全双工才是终点，所以会继续走这条路，目标是既有深度相互理解、聊起来愉快，又不放弃 RAG 和函数调用，否则只是一个很自然但没什么用的闲聊伙伴。
