02. Chris Lattner（Modular）：超越 API 端点，Max 框架与 Mojo 语言

直播位置 0:21:46–0:40:13

为什么要离开端点

Chris Lattner 是 Modular 的创始人，主持人称他是“这个行业的传奇”。他开头说，生成式 AI 好部署，现成的推理端点很多，做原型很快。但有时你需要更多：自己掌握数据，不想把数据发给别人；把模型接进公司自己的安全体系；定制模型；省钱，因为端点很贵；或者想试主流之外的硬件。这些需求都要求你“越过端点”。

过去的答案是 PyTorch、TensorFlow、Caffe，推理变重要后有了 ONNX、TensorRT，现在又冒出一大批框架，有些只服务某一个模型。他反对的是这种碎片化：它拖慢研究成果进入产品的速度。他说去年是“生成式 AI 演示之年”，但把它经济地放进产品仍然很难。这不怪 AI 工程师，新模型每周都出，每个产品都要加 AI，一上线就按调用量付费，成本难以扩展。

Modular 和 Max

他介绍团队：Modular 成立两年左右，成员参与过 TensorFlow、PyTorch，以及 LLVM、MLIR、XLA 这些编译器。他半开玩笑地为这些工具难用道歉，说五年前世界不一样，那时还没有生成式 AI。Modular 的目标是让你“拥有自己的 AI”：拥有数据、控制产品、部署在想要的地方。做法是把一流技术整合成一个栈，而不是每个模型一套方案；服务 Python 和 PyTorch 用户，不要求大家推倒重来；他在 Apple 待过很久，希望东西“直接能用”。

Max 包含两部分：免费的 AI 框架，以及赚钱的托管服务（这次不讲）。框架目前专注推理，原生支持 Python，也有 C++ 接口。PyTorch 模型可以直接带进来，支持 ONNX、TorchScript、torch.compile 等路径。想深入的人可以用原生 API，自己处理 KV Cache（推理时缓存已算过的注意力键值，避免重复计算）和 PagedAttention 之类的技术。Max 的特点是不建在 cuDNN、NVIDIA 库或 Intel 库之上，他们用一套统一的栈替换了这些库。

性能数据

  • 他们刚发布的 int4 / int6 K 量化（Quantization，用更少比特存权重以加速和省内存）在云端 CPU 上比 llama.cpp 快 5 倍。
  • GPU 方面，他说大多数团队的 GPU 利用率在 30% 到 50%，等于多花了两到三倍的钱。Modular 的愿景是在 Python 里像写 CPU 程序一样写 GPU 程序，同时拿到 CUDA 的全部能力。
  • 他批评“一行代码把 CPU 换成 GPU”这种演示，因为背后通常是两套完全不同的栈（一套基于 Intel MKL，一套基于 CUDA）。Modular 重写了矩阵乘法、融合注意力层、图层等整层技术。
  • 高级开发者可以直接对 Max 写自定义内核 Kernel（在 GPU 上运行的底层计算函数），他说比 Triton 好用；不写内核的人有自动融合的编译器。
  • 矩阵乘法微基准上，他们对比的是 NVIDIA 自己的 cuBLAS 和 CUTLASS，Max 达到并超过两者，他提到领先可达 30%。

Mojo

为了造 Max，他们先造了一门语言 Mojo。不想学 Mojo 的人可以只用 Max。Mojo 的目标是成为扩展 Python 的最好方式，让人不必再写 C、C++ 和 Rust。它长得像 Python，有完整工具链，支持 VS Code，开源，跑在 Linux、Mac、Windows，Discord 有约 2 万人（字幕里另有一个 20 万的数字，不清楚指什么）。他的说法是：Python 好在开发者、生态、库、社区和包管理，差在实现；Mojo 把这些优点和 MLIR 编译器技术结合起来。

他说很多人发现 Mojo 比 Python 快 100 到 1000 倍，极端情况更多，但速度本身不是重点。在 Python 里你不该写 for 循环，在 Mojo 里可以写普通代码。他展示了 Mojo 版 Llama 3 里的分词代码，里面有链表、if 和 for 循环。对研究者这意味着全栈可改；对管理者，团队里不用再分 Rust、C++ 的人。他让大家去 Modular 博客看一篇“比 Rust 还快”的文章。

最后：Max 可以免费下载，支持在 Kubernetes 和 SageMaker 上生产部署；GPU 支持很难，计划 9 月正式发布，加入 Discord 可以提前试用。

03. Antje Barth、Mike Chambers（AWS）：从软件开发者到 AI 工程师的五步

直播位置 0:40:13–1:00:00 · 其中 Mike Chambers 的 Minecraft 演示从 0:55:01 开始

Antje Barth 是 AWS 首席开发者布道师。她说幻灯片上的头像是让 AI 把她画得“更 agentic 一点”的结果。她从 swyx 那篇定义“AI 工程师”的文章讲起：以前要几个月甚至几年才能上线的 AI 项目，现在几个 API 调用就能做到，不一定要当 ML 研究员或数据科学家。

第一步：理解基础

她说仍然要懂基础模型大致怎么工作、为什么会给出意料之外的输出、怎样微调 Fine-tuning、怎样让模型调用函数。她推荐了 AWS 同事和 Andrew Ng、DeepLearning.AI 合作的课程 Generative AI with Large Language Models，在 DeepLearning.AI 和 Coursera 上。

第二步：用 AI 开发工具

她说开发者常有多达 70% 的时间花在样板代码、写文档、维护老代码上，只有约 30% 花在有创造性的部分。这促使 AWS 做了 Amazon Q Developer。她强调它用 Agent 完成更复杂的任务，比如功能开发和代码迁移（例如把老 Java 项目升级到新版本）。

Mike Chambers 录的演示：在 IDE 里问 Q“怎样创建 Serverless 应用”，它给出安装 AWS SAM CLI 等步骤；右键一段生成的代码让 Q 解释；写一行注释让它生成一个去掉字符串首尾空格的输入检查函数；再用 /dev 命令描述一个按类别查询 DynamoDB 的函数。Q 给出一个计划（修改 template.yaml、新建 search-by-category.mjs 等），然后自己执行，生成一个变更集，可以先看 diff 再点按钮插入项目。

第三步：做原型

流程是定义用例、选模型、决定用提示工程、检索增强生成 RAG（先检索相关资料再交给模型回答）还是微调，全程要有负责任 AI 策略和护栏 Guardrails（拦截不当输入输出的规则或模型）。她说没有一个模型能通吃所有用例，所以有了 Amazon Bedrock：一个托管服务，提供 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 自己的 Titan 等模型。上周 Claude 3.5 Sonnet 发布时也同步上了 Bedrock。

几周前 Bedrock 推出了统一的 Converse API：不管选哪个模型，请求参数和消息格式都一样，平台负责把参数翻译成各模型的格式，处理 system / user / assistant 提示，输出格式统一，并原生支持函数调用。她展示了 Python 代码：建 SDK 客户端，定义消息列表，调用 converse 时传入 model ID（示例用 Anthropic 模型）、消息和推理参数；要用工具时再传一个 tool 列表。示例代码在 community.aws 的生成式 AI 专区，作者 Dennis Traub 也在现场。

第四步：把 AI 集成进应用（Agent 演示）

Mike 在 AWS 控制台里用 Bedrock Agents 做了一个玩 Minecraft 的 Agent，叫 Rocky，全程 Serverless。Agent Builder 里能看到他用的模型是 Claude 3 Haiku，指令其实就是提示工程，告诉 Agent 怎么玩。工具通过 Action Group 加入，有“Minecraft actions”和“Minecraft experimental”两组，每个动作（跳、挖、获取玩家位置、移动到某坐标）都连着代码，描述和必填参数也是提示的一部分。

游戏里他先把时间调成白天，然后退远一点，在聊天里说“come to me”。并没有“走到玩家身边”这个工具。Agent 自己推理出步骤：看是谁发的消息，拿到这个名字，查这个玩家的位置，规划路径走过去。项目代码在 GitHub 上。

第五步：跟上社区

她宣布 AWS 会把旧金山的 AWS Loft 改造成面向社区的 AI 工程中心，办工作坊和聚会，可以填问卷提议题或申请主讲。当晚还有和 Anthropic 合办的 happy hour，已经满员。

04. Alex Albert（Anthropic）：从电气化工厂说起，Claude 3.5 Sonnet、Artifacts 与 Projects

直播位置 1:00:06–1:14:10

一段历史

Alex Albert 负责 Anthropic 的开发者关系。他从 1882 年讲起：世界第一座商业发电厂开张，电被认为会改变一切，但制造业生产率并没有马上提高。原因是工厂主把蒸汽机换成电动机，其余照旧。当时的工厂一头是烧煤的大蒸汽机，顶上的传动轴带着几百台机器同步运转，哪怕只有一个工位要用电也得开整台机器，厂房布局由传动轴决定。真正的变化要等到人们以电为核心重新设计工厂：工具变小、变专用，工人可以带着工具走到工件旁边。

他说今天的 LLM 也在这个阶段。很多公司只是在现有产品上加几个“星星图标”按钮。移动互联网早期也这样，大家把网页缩小塞进手机，直到有人围绕常开的摄像头和 GPS 重新设计应用，才出现 Snapchat 和 Uber。他说这不能怪开发者：LLM 不确定，难以在上面构建，可靠性仍是问题，提示要反复优化，除了文本框之外还没什么产品形态留下来。

Claude 3.5 Sonnet

  • 上周四发布，是 3.5 家族第一个模型，只是中档，却比上一代最强的 Claude 3 Opus 更好。MMLU、HumanEval、GPQA、工具使用等基准都领先。
  • 200K 上下文窗口 Context Window（模型一次能读入的文本长度），整个范围内召回接近完美，适合 RAG。
  • 写代码时更会调试，较少陷入同样的循环。Anthropic 内部用 pull request 做评测，因为 PR 有明确任务、需要几步、模型可以边写边测。3.5 Sonnet 得分 64%，Claude 3 Opus 是 38%。
  • 视觉能力几乎在所有测试基准上都比 3 Opus 好，表格转写、OCR 很轻松。他把一张数字很密的表格给它，它几乎完美地转成了 Markdown，他说自己逐个核对过。
  • 在 Anthropic API、AWS Bedrock 和 Google Vertex AI 上可用。价格比 3 Opus 便宜 5 倍：每百万输入 token 3 美元，每百万输出 token 15 美元。

Artifacts 和 Projects

他认为对开发者更有启发的是 Artifacts：把 Claude 生成的内容从对话中分离出来单独显示，可以和 Claude 一起改 SVG、React 网站等。他演示了只用一张截图就让 Claude 用 React 复刻出 claude.ai 的聊天界面。他说这个能力其实已经“藏在眼皮底下”一年半了，说明我们还在 LLM 产品化的 S 曲线早期。

周二发布的 Projects 让团队把风格指南、代码库、会议记录、过去的作品上传，让 Claude 的输出以这些知识为依据；Team 套餐里可以把 Project 里的对话分享给同事。Anthropic 内部工程师会上传代码仓库和文档，他看到有人直接分享对话和 Artifact，替代 Google Docs 或文档站。

API 和控制台

一个月前发布的工具使用 Tool Use API 让开发者给 Claude 定义客户端函数，Claude 自己决定何时调用；它也能稳定输出结构化 JSON。他看到有开发者一次给 Claude 几百个工具。开发者控制台新增提示生成器：输入任务描述，Claude 帮你写出优化过的提示，然后在 Workbench 里直接编辑，支持变量和提示模板。还有一个带 beta 标签的 Evaluate 功能。

接下来

3.5 Haiku 和 3.5 Opus 年内推出。每一代都会更聪明、更快、更便宜。他对开发者的建议是：规划产品路线图时，要假设开发期间就会出新模型，按几个月而不是几年的节奏变化。

可解释性方面，他提到论文 Scaling Monosemanticity：在模型里找到对应不同主题的“特征”，把某个特征的值固定住调高或调低，就能引导输出。Golden Gate Claude 就是把“金门大桥”特征调高的版本。目前有少数 beta 测试者在试一个 steering API，可以找到并固定某些属性的特征，作为提示之外的另一种控制手段。最后他宣布新一届 Build with Claude 比赛，到 7 月 10 日截止，前三名各得 1 万美元 API 额度。

05. Harrison Chase（LangChain）：LangGraph 稳定版、LangGraph Cloud 与 LangGraph Studio

直播位置 1:14:10–1:21:51

Agent 的一段历史

LangChain CEO Harrison Chase 说 LLM Agent 并不新：ReAct 论文（让模型交替“推理”和“行动”的方法）2022 年 10 月发表，LangChain 一个月后发布，AutoGPT 也有一年多了。他认为 AutoGPT 是 Agent 热度的顶点，之后几个月热度下降，因为人们发现通用的 Agent 架构不够可靠，没法上生产。这段时间里他觉得 OpenAI 的 Assistants API 有几处新意，后面会回来讲。

LangGraph

今年早些时候发布的 LangGraph 是专门为 Agent 做的。它底层、可控，因为他们看到真正把 Agent 上线的公司都在写定制的“认知架构” Cognitive Architecture（Agent 每一步怎么想、怎么走的流程设计），里面有很多细小差别。它自带持久化层，支持很多人在回路 Human-in-the-loop 的交互模式；它以流式输出为先，因为流式对 LLM 界面很重要。LangGraph 可以不依赖 LangChain 单独使用，和测试与可观测平台 LangSmith 无缝集成。用户包括开源项目 GPT Researcher、Replit、Norwegian Cruise Line、Ally Bank、Elastic。当天发布第一个稳定版。

LangGraph Cloud

他回到 Assistants API：它除了框架，还带了基础设施，内置持久化帮你存消息，支持后台运行长任务，可以配置 Agent。缺点是你无法完全控制认知架构，它预设应用的状态就是一串消息，比较死板。于是他们想把 LangGraph 的自定义架构和这些通用基础设施结合起来，这就是 LangGraph Cloud：用 Python 或 JavaScript 写的 LangGraph 应用不改代码就能变成生产级的 Agent API。

  • 对任意 LangGraph 状态的内置持久化，用任务队列管理后台运行，可以为同一张图配置不同实例（换 LLM 或提示）。
  • Double texting：Agent 还在处理上一条消息时用户又发来一条，他们提供了四种处理模式。
  • 内置 cron 定时任务，因为 Agent 不只由聊天触发。

08. Vik Korrapati（M87 Labs / Moondream）：一个不到 2B 参数的视觉模型为什么能打

直播位置 2:33:53–2:53:35

Moondream 是什么，怎么来的

Vik Korrapati 是 M87 Labs 的 CTO，之前在 AWS 工作了约 9 年。他做的 Moondream 是一个开源的小型视觉语言模型 VLM（能同时看图和理解文字的模型），不到 20 亿参数，可以在任何地方跑，Apache 2.0 许可。它能回答关于图片的问题、生成描述、检测物体并给出坐标、计数。他的演讲标题叫“小视觉模型为什么能打这么狠”。在 VQAv2 和 GQA 两个视觉问答基准上，Moondream 过去三个月的版本持续提升，表现接近大约大四倍的 LLaVA 1.5（7B）。

他原本想做一个 QA 自动化测试应用，需要 Agent 看懂用户屏幕上的浏览器页面。先试了 GPT-4V，但当时安全拒答太多，图里只要有人就拒绝处理，而且又慢又贵。他决定自己控制模型。任务很窄，只要描述屏幕、回答关于屏幕的问题。他在家里用几块 3090 训了一个小版本，打算之后租云机器训大的。小版本效果不错，他发到 Twitter，以为能有 20 个赞，结果火了。其他自动化测试公司和 Open Interpreter 都来找他，于是他暂停测试应用，专心做 Moondream。

小模型成功的几个原因

  • 先决定模型解决什么、不解决什么。Moondream 定位为开发者工具，重点是准确、不幻觉；它的世界知识不多，不帮你写诗。MathVista 这类看图解数学题的基准就是非目标，最多让它输出 LaTeX。
  • 没有从零预训练。他们把 Google 的视觉编码器 SigLIP 和 Microsoft 的文本模型 Phi 1.5 融合起来。Phi 1.5 本身主要用合成数据训练，和他们的流程很像。他说从零预训练对这类任务没有区别，还很贵；换过多个底座模型，差别都不大。
  • 真正有区别的是训练数据。最新版本用了约 3500 万张图。人工标注很贵，他听说有的标注公司要先签七位数的合同才愿意谈；网上的图片和 alt 文本又噪声大，小模型对噪声很敏感。所以他们做合成数据 Synthetic Data（用模型生成训练数据）。

合成数据的细节

他说很多人在用 GPT-4 的输出训练，这是公开的秘密，但他不建议：一是条款上有问题，二是 GPT-4 有小模型学不到的推理和知识，小模型学到的反而是幻觉，生成听起来合理、但它不可能记住的细节。

反面例子是 COCO 数据集：约 20 万张图，每张有五条简短描述和物体标注。直接把这些丢给 GPT-4 让它写详细描述，它会说“港口右侧有一个人”，其实那里只有五个像素，可能是根柱子，因为原始标注就不准；它还会自由发挥，说“有五艘游艇格外显眼”。所以要先做预处理。

正面例子是 Google 的 Localized Narratives：标注员一边口头描述图片，一边把鼠标移到正在描述的位置，因此描述很详细，带空间位置，比如“前面的女孩在弹吉他”。空间推理恰好是 VLM 的弱项。他为此搭了一条复杂的处理管线，每张图要调用约 20 次 LLM，用的是 Mixtral 8x7B，花费很高，但训练数据是最大的提升因素。他估计他们花在生成数据上的算力比训练模型本身多一到两个数量级。这个数据集已经在 Hugging Face 开源。

他们会故意生成“干扰问题”，比如“图里的孩子对快乐的存在有什么理论”，让模型学会不总是顺着用户的问题说。他讲了两个坑：

  • 有用户问了一个很简单的问题模型却答不上来，原因是问题首字母没大写，训练时从没见过。所以训练数据要和真实查询分布接近，他们加了一步人为注入大小写问题和错别字。
  • 模型坍缩 Model Collapse：让 Mixtral 生成“和图片无关的问题”，它总是问恐龙和外星人，训练后模型学到的是“问恐龙和外星人就答不是”。需要往生成过程里加入随机性，比如让模型描述图片时“参考 alt 文本，相关就用，不相关就忽略”。

三个月里的体会

  • 社区很关键。最初的热度让他意识到这个模型比测试应用更有价值；可以直接在 Twitter 私信用户，也找到了合作伙伴和导师。
  • 开源是必要的。他说竞争对手是免费的，他没得选。企业用户未必自己部署，但需要有这个选项，因为很多企业遇到过供应商倒闭或坑人。社区还帮忙把模型移植到不同平台，包括浏览器里运行。
  • 他承认有争议的一点：安全护栏应放在应用层，不该烤进模型里。他理解 OpenAI 的考虑，但测试应用拒绝所有含人的图片毫无道理；开发者工具是 B2B，应该让开发者自己决定护栏。做 C 端助手时把它放进模型更合理。
  • 他认为小模型会主导计算机视觉。处理 30 帧每秒的视频，按每秒 0.7 美分算很快就很贵；还有隐私和延迟要求，需要在决策发生的地方附近运行。大模型更多会留在开发环境里，比如生成训练数据，部署的会是小模型。
  • 出乎他意料的是，很多人用 Moondream 做传统视觉任务：画面里有没有人、有没有可疑情况、路口摄像头里公交车在哪。这些以前训一个 YOLOv3 就行，但他的结论是：用英文写提示比自己收数据、标注、训练定制模型的体验好太多，很多开发者因此才愿意把视觉加进应用。

接下来和现场演示

他说团队不是“AGI 派”，只想让开发者更容易做视觉应用。现在每张图用 729 个 token 表示，只能一次发一张图；他们在做更压缩的表示，适合不需要读字的分类任务，在 CPU 上更快。他们刚完成种子轮融资，投资方有 Felicis、Ascend 和 GitHub Fund，夏天晚些时候有新版本。

09. Ben Hylak（Dawn）：无边界产品的时代，AI 产品怎样加结构

讲者和问题

Ben Hylak 是 Dawn 的创始人，Dawn 帮 GitHub 等公司做“更可预测”的 AI 产品分析。他一直在做“无边界产品”，也就是超出鼠标和显示器的产品：八年级开始做机器人，后来在 SpaceX 做火箭，最近四年在 Apple Vision Pro 设计团队，参与了第一版 visionOS。

他说 AI 让产品比以往都更没有边界：可以打字、说话、发图片和视频，还可以恳求、讨价还价、倾诉。这会让产品难以预测、难以理解。用户以为它能做某件事，试了不行，就离开，以为连它能做的事也做不了。圈外人学用 ChatGPT 多靠口口相传，比如听朋友说用它做旅行计划；技术人员会反复试错，但多数人试一次不行就不再试。他的演讲分过去、现在、未来三段。

过去：Vision Pro 的三条经验

屏幕软件靠点、滑、按，发生什么由开发者决定，用户一看按钮就懂，开发者加个 Amplitude 或 Mixpanel 埋点就知道用户做了什么。他说上一次大变化是多点触控：多一根手指就多了距离和旋转，这让小屏手机变得好用。现在的产品已经无边界到“软件在旧金山街头自己跑，还被人围攻放火”。

他说无边界产品由一连串“如果”定义：如果用户从客厅走到卧室躺下，应用该怎样？在飞机上呢？身边有朋友呢？用户有残障、不能转头、卧床呢？设计 macOS 不用想这些。做 AI 产品的人也一样，总在想“如果用户输入这个呢”，于是有了 eval。没有结构就是混乱，结构带来清晰。他们在 Vision Pro 上用了三种办法：

  • 突出重要的东西，而且要快。visionOS 打开就是主屏，上面有应用、人和环境，这些是他们认为最重要的。以前的 VR 产品很难让人看懂它是干什么的。
  • 层级。主屏是一切的起点和终点，窗口有边界，可以缩放移动，单个窗口可以全屏。
  • 熟悉感。visionOS 的 TV 应用像 tvOS 的 TV 应用，控制中心也很像，这不是偷懒，人在陌生环境里需要尽量多的“家的标志”。Dawn 的第一版原型是一个可以探索的星团界面，现在改成了表格、图表和示例。

现在：AI 产品里的好结构和坏结构

  • Dot（一个 AI 陪伴 / 日记应用）：双指捏合可以按天看，像日记本；点一个人，能看到你每次向 Dot 提到他们的时间线。结构被从聊天里抽出来了。
  • Perplexity：把你的问题放在顶部当标题，列出来源，答案占满整页，看起来更像搜索引擎、更像一次性结果，较少像来回聊天。
  • 他批评的反例是 Vercel 的聊天机器人演示：在对话流里嵌入临时 UI，比如问买 Doge 时出现一个滑块。问题是追问几次后这个 UI 就被顶上去“飘走”，甚至出现两个；他回到第一个点了购买，其实操作的是另一个东西。他说答案是把结构从对话里拿出来，放到一边，对话继续时更新它。
  • Claude 的 Artifacts 就是这么做的：正在迭代的应用被拿出对话，还可以在版本之间切换，不用滚动聊天记录。
  • 版本控制：ChatGPT 最早就有编辑消息后在不同版本间切换的功能，背后维护着一棵树。Vercel 的 v0 做得像 Google Slides，可以放心反复改 UI。
  • 记忆：ChatGPT 的跨对话记忆没有边界，他在写 JavaScript 时它记得他之前提过的健康问题，让他觉得奇怪。Claude 的 Projects 按项目共享上下文，这个结构更熟悉。
  • Agent 对多数人很陌生，但电子表格很熟悉。他说他见过唯一真实落地的 Agent 用法就是表格，比如 Clay：每一列是用户定义的一步，每行像一次 eval，先跑 10 行看对不对，再跑 5 万、10 万行，最后一列得到个性化邮件。
  • 示例和预设：ChatGPT 早期的“安慰朋友”“计划放松的一天”；v0 的示例加上一个看别人在做什么的 Explore 页面；Notion 直接给“改变语气”的菜单，不用写“你是一个简洁的 GPT”。

未来：更少的提示工程

他引用去年大会上 Linus（字幕作 “lus”）的说法：提示工程像一只羊驼坐在后座用泳池浮条开车。他认为未来提示工程会少很多。已经有例子：Apple 的生成图片通过混搭概念来控制；Twitter 上有人在情绪之间拖动；Figma 前一天发布了在“专业 / 随意 / 扩写 / 精简”之间调整文字语气的功能。问题是“随意”对一家财富 500 强和一家在 TikTok 投广告的美妆品牌意思不同。他的答案：

  • 把预设数量放大一百万或十亿倍。稀疏自编码器 Sparse Autoencoder（从模型内部激活里拆出可解释特征的方法）给出了路径，比如 Golden Gate Claude。他一位朋友做了图像版演示，可以调高“光影”“宁静溪流”“威尼斯运河”这类特征。
  • 排序后的预设：个性化、可搜索、可以用自然语言调用，甚至不直接展示给用户。用户输入“更友好一点”，系统找出“亲近程度”“对抗程度”等对应预设。
  • 开发者定义的个性化：有了这些特征就能按用户调参，而文本提示像纸牌屋，删一个词输出就全变。
  • 从 eval 转向分析：像“第一任总统是谁”有标准答案，但“给某个用户的总结该用什么语气”没有。他认为以后更重要的是了解你是否满足了用户需求。

10. Karan Goel（Cartesia）：实时智能与状态空间模型

直播位置 3:15:00–3:30:00

批处理智能和流式智能

Karan Goel 是 Cartesia 的 CEO，公司成立 8 个月。他说过去四五年 AI 主要在做“批处理智能”：在云端调用模型，等几秒拿到好答案，适合长时间推理解一道数学或物理难题。另一类应用需要流式、实时、立刻响应，比如生成视频音频、理解传感器数据流。他列举了几类：

  • 对话式语音：能听懂你并替你办事的系统，比如做客服、回答医保问题、打电话约人取货。人类可以去处理更难的事，比如很生气的客户或高价值客户。
  • 端侧助手：在手机、笔记本上低功耗常驻。
  • 世界生成：像 GPU 实时渲染画面一样实时生成游戏。
  • 机器人：在一台设备上同时处理音频、视频、传感器，并立刻响应。

为什么要新架构

他读博时的导师是 Chris（Ré），团队里很多人是同门。他们几年来研究的是能在信息流入时就压缩信息的模型，Mamba 是这条路线较新的一版，他读博时做的是更早、“现在没人用”的版本。他说文本是最没意思的长序列，因为文本已经很压缩了；音频、视频信息量大得多，比如一整天的监控画面，有用的只有一点点。他认为压缩是智能的基础，而现有 AI 系统建立在检索上：把所有上下文留着，每次在上面推理。

他做了个粗略估算：一个人一年大约处理 10 亿个文本 token、100 亿个音频 token、1 万亿个视频 token，同时进行，用的是脑袋大小的计算机，几顿不吃饭也照常运转。最好的模型现在在 1000 万到 1 亿 token 的量级。人能毫不费力地记起 30 年前的事，不需要 RAG。

Transformer 的计算量随上下文长度呈平方增长，主流做法是堆算力。多模态上下文比文本长得多，如果推理量增加一千倍、十万倍，按现有方式扩展会极其昂贵，难以普及到他说的那些应用。他们的方向是以压缩为核心的新架构，对上下文长度接近线性扩展，内存低，可以低功耗实现，并扩展到更长的上下文。

SSM 的直观理解

他的解释：Transformer 生成时要注意之前每一个 token，比如要从 “the quick brown fox” 生成 “jumps”，得看整段上下文，生成后放回上下文，再来一次。状态空间模型 SSM（State Space Model）是流式的：token 进来，更新模型内部的记忆状态，然后 token 就丢掉，过去的信息被压缩成一个状态，用于以后生成。这用的是循环 Recurrence 的思路，他说人类推理很多时候也这样。他还提到 Jensen 在 Wired 的一篇报道里谈过 SSM。

关于质量，他说压缩和保留全部信息之间有取舍，但压缩对长上下文有帮助：看 24 小时监控，边看边压缩比每次回看全部 24 小时更能回答问题。他的经验法则是长上下文和多模态问题上 SSM 质量很好，短上下文上压缩帮助不大。他预计未来三到五年这类模型的作用会变大。

语音模型

几周前 Cartesia 发布了一个文本转语音 TTS 模型，用 SSM 做训练和推理，是他们把多模态数据放进单一模型的一步。他最自豪的是延迟压得很低，在 playground 里几乎即时从数据中心返回语音；他们也在让这些模型在 Mac 等设备上本地运行。时间到了，他没能做现场演示，请大家去网站的 playground 试。

  • 最顶层是人工标注，用来改进分类器、改写有问题的合成数据。

他展示了一段 YAML 配置，里面嵌了 SQL，用来“物化”数据集。他说训练格式（TFRecord、JSON Lines）是训练中最容易出错的环节之一，所以他们把数据物化和训练任务分开。多模态数据量大时，数据加载是个独立的难题。Lance 支持快速随机访问，可以只打乱行的引用而不是行本身，洗牌很便宜。他的目标是“看着 GPU 转、数字往上走”。

Chang She：AI 数据的“新 CAP 定理”

他用分布式训练举例：先过滤选样本，需要快速扫描；再随机抽行洗牌，需要快速随机访问；最后把文本、图片、视频从对象存储流式送进 GPU，需要处理大二进制块。一个负载就同时要这三样，但现有格式最多满足两样，常常只满足一样。他把这叫“AI 数据的新 CAP 定理”，也是设计 Lance 格式的动机。

规模让问题更严重：一行纯标量的表格数据平均约 150 字节；加上嵌入向量大 20 到 25 倍；加图片再大 20 倍；加视频就更夸张。生成式 AI 的数据以每秒几千 token 的速度产生。他说过去管理几十 TB 就算大公司，现在做生成式 AI 的小团队管理几十 TB 甚至 PB 级数据并不稀奇。

Lance 格式的三点：

  • 列式文件格式 Columnar（按列而不是按行存储，扫描某几列很快），像 Parquet 一样扫描快，但支持快速点查；去掉了 Parquet 的 row group 限制，可以内联存储大块数据。
  • 轻量表格式：写入自动版本化；加列不用复制原数据（零拷贝的 schema 演化），方便试实验性特征再回滚；支持时间旅行，数据出错能立即回到上一个好版本，不污染下游训练。
  • 索引扩展：Parquet 的索引能告诉你要哪些行，但不支持随机访问，取行仍慢。Lance 加了向量索引，可以直接在 S3 上做十亿级向量搜索；还有标量索引用于快速过滤元数据，以及全文索引做关键词和模糊搜索，他说这样就不需要单独的 Elasticsearch 集群。

结果是一张表服务多种负载：元数据和时序列可以接 DuckDB、Trino、Spark 跑 SQL；大块数据和张量可以直接接 PyTorch 训练；嵌入可以做相似度搜索。LanceDB 是建在这个格式上的向量数据库，支持分布式向量搜索，他说用比其他向量数据库少一个数量级的基础设施做到低延迟高 QPS。他说“多模态”有三层意思：数据多模态，负载多模态（SQL、向量搜索、全文搜索、过滤），场景多模态（线上 RAG 和个性化、训练、数据湖分析）。Noah 收尾说，速度是他们最好的策略，很多工具在多模态负载下会变慢。两家都在招人。

速度：500 毫秒

他说有两种快：吞吐量和延迟。对话场景下吞吐量已经够了，LLM 生成速度比人读或听快；难的是延迟，也就是首字节、首 token 时间 TTFT。吞吐量往往每几年提升一个数量级，延迟的改进是线性的，远远落后。

人和人对话，超过约半秒不回应就会觉得怪。人其实回应得更快，录下来常在两三百毫秒，像是在做投机解码：对方话还没说完四五个词，你已经在准备回答。如果来不及，人会给出某种信号。所以 500 毫秒是重要目标，超过就进入恐怖谷。他承认刚才 Chad 的视频里响应时间偏慢。作为参照，Gemini Pro 的首 token 时间约 900 毫秒，已经接近目标的两倍。

他测的是语音到语音延迟 Voice-to-Voice Latency：从我停止说话，到我听到 AI 开口的间隔，包含所有环节。典型数字（中位数，测量有粗糙之处）：

  • macOS 笔记本麦克风本身就有 30 到 40 毫秒延迟，因为有回声消除、降噪、增益控制等处理。在软件还没拿到数据之前，500 毫秒预算已用掉 40 毫秒。
  • 然后是音频编码、网络发送、包处理、在接收端的抖动缓冲区 Jitter Buffer 里重组、解码。
  • 转写和端点检测做得很仔细能压到两百毫秒左右。
  • LLM 首 token 希望在 100 毫秒左右。
  • 再做 TTS，再过网络回来播放。
  • 合计乐观也有 600 到 700 毫秒。

演示和 Pipecat

前一天他们在 Twitter 发了一个低延迟演示，开源容器能做到 500 到 700 毫秒。现场播放：机器人出地理题，撒哈拉、亚马逊、堪培拉、比利牛斯山都答对；他想说 Stockholm 却口误成 “visit Stockholm”，机器人以为他说了 visit.com，又反应过来；他把波兰最大城市答成 Kraków，机器人纠正为华沙；然后他反过来问机器人各国首都，中间口误把“瑞典的首都”说成“斯德哥尔摩的首都”。他说这个演示不在乎提示工程，只为测延迟。界面中间的大数字是客户端测得的语音到语音延迟，四周是服务器回传的各环节指标。

四个重点方向

  • 文本智能：他说现在的模型像一年级学生，会出错，一年后可能变得认不出来，在医学研究、科学推理上达到硕士水平。下一代前沿模型在推理上会有阶跃式进步。
  • 更快更便宜：GPT-4 的价格一年降了 80%，会推出不同尺寸的模型，但没有时间表。几个月前推出的 Batch API 对异步任务再打五折，适合批量分析文档和图片。
  • 模型定制：微调 API 对所有人开放；OpenAI 还帮 Harvey（做法律产品的创业公司）用美国判例法深度定制了 GPT-4，效果很好。
  • Agent：去年 11 月 DevDay 谈过愿景。Agent 会用多种模态感知和与世界交互，协调多个 AI 系统、安全访问你的数据、管理日程。他举 Cognition Labs 的 Devin 为例：能拆解复杂任务、查在线文档、提交 PR。他还引用 Paul Graham 的观察：22 岁的程序员常常和 28 岁的一样好甚至更好，因为他们手边有 AI 工具。

他已经用 Sora 生成了一段树蛙纪录片风格的视频（Sora 尚未开放）。他从视频里截取 6 帧发给 GPT-4o 的视觉接口，让它像纪录片旁白一样描述，每次生成都不同。然后他展示还没公开的 Voice Engine：只需很短的音频就能生成定制声音，OpenAI 内部和配音演员合作用它做 API 和 ChatGPT 里的声音，出于安全考虑尚未广泛开放。他现场录了几秒自己的声音，把刚才生成的旁白交给 Voice Engine，用他的声音念出“在茂密多雾的森林深处，一只鲜艳的青蛙沿着长满苔藓的树枝小心前行”，然后又生成法语版（他本人会说法语）和日语版。

15. Charles Frye、Bryan Bischof：一年 LLM 应用经验（战略篇）

直播位置 7:32:08–7:47:00

这场演讲的来历

Charles Frye 说，一群人在 Twitter 和博客上抱怨 LLM，组了个群聊，发现大家都要写同一篇博客“我们这一年学到了什么”。于是六个人把几篇短博客合成一篇发在 O'Reilly 上的长文 What We Learned from a Year of Building with LLMs，分战略、运营、战术三层。反响很好，从 Postgres 贡献者到风投到工具开发者都说有共鸣，于是被邀请做主题演讲。Scott Condron 形容这是“复仇者联盟集结”。演讲也分三段，每两人一段。他还特意澄清：他们不是刚发现 GPT-4 是新 Web3 的币圈人，他们都在要手写梯度的年代训练过第一个神经网络。

Bryan：模型不是护城河

Bryan Bischof 先反讽“要赢就得自己训模型”，然后说对这里几乎所有人，模型都不是护城河。应该在自己最擅长的地方做，用你的产品专长或现有产品，找到细分领域深挖；做模型厂商不会做的东西，因为他们要为所有客户做很多事，借用 Sam Altman 的话，这些会被“碾压”。把模型当作普通 SaaS 产品，有明显更好的竞争者就换掉，他调侃说“无意冒犯 GPT-4o，但 Sonnet 3.5 看起来很不错”。

他说高 MMLU 分不是产品；Spider SQL 基准 87% 不等于能自动完成所有数据请求，甚至不等于能完成 87%；HumanEval pass@1 67% 也卖不出去，至少他的销售团队不知道怎么卖。好的 LLM 应用就是好产品：设计好，完成用户要做的事，增强用户能力。应该做的是：能随更聪明更快的模型受益的东西，在不确定下保持产品质量的东西，以及帮助持续改进的东西。

Charles：持续改进不是新东西

Charles 说，自上届峰会以来大家的重心转向评测和数据，合著者 Hamel Husain 有一张“良性循环”图，中心是评测和数据，目的是驱动持续改进。他一层层往前追溯：MLOps 有同样的循环（他引用合著者 Shreya Shankar 论文里的图）；MLOps 的名字来自 DevOps，DevOps 关注用生产监控信息改进产品；DevOps 建立在 Eric Ries 的精益创业上，那是对整个业务做“构建-测量-学习”；精益创业又源于丰田生产方式和 Kaizen（持续改进）。

丰田的一条原则 Genchi Genbutsu 意思是“现地现物”，丰田会让高管去车间。对 LLM 应用来说就是看你的数据，它是应用怎样给用户创造价值的真实信息。他提醒，会场里很多人在卖工具（包括他自己），容易沉迷于搭建改进循环本身而忘了价值从哪来。他引用丰田 Shigeo Shingo 的话：只有金属被弯折时才创造价值。不要只顾着建 eval、算概念漂移，要去给用户创造价值。

Bryan：先上线，再看真实交互

他说要让数据飞轮转起来，就要把东西放到用户面前，并用评测表达系统的目标。评测不是什么奇怪的定制指标，评测就是目标，任何能捕捉这种行为的系统都够用。“恐惧是思维杀手”，先以 beta 上线，Apple Intelligence、Photoshop 和 Hex（他所在的公司）都这样做。LLM 的输出值得人眼看，可以加 AI 来看，但一定要用人眼看。先收集二元的人类反馈，丰富反馈之后再加。用户请求会暴露产品之下的 PMF 机会：用户在问你的聊天机器人什么你还没实现的功能，那就是方向。

Charles：用成本曲线规划未来

他说预测未来的好办法是看过去那些“预测了现在”的人怎么做。Alan Kay 等人在 PARC 把摩尔定律往前推，自己造昂贵、卖不出去、又慢又有 bug 的系统，提前体验未来。LLM 也已经有类似规律：在三个能力档次上，成本每 12 到 18 个月下降一个数量级。这三档是原始 GPT-3 API 的 Davinci、ChatGPT 背后的 text-davinci-002 系列，以及最新的 GPT-4 和 Sonnet。每档大约 15 个月成本降一个数量级，比摩尔定律还快。

他的例子：2023 年用聊天机器人驱动所有 NPC 的游戏，每小时成本约 625 美元；1980 年玩 Pac-Man 每小时约 6 美元（已按通胀调整）。如果等两个数量级的下降，也就是从 2023 年中起约 30 个月，就能以每小时 6 美元左右提供这样的游戏，人们大概愿意付钱。现在卖不出去，但你可以先体验、先设计，到时候就准备好了。规划时要想：到你下一轮融资时，哪些现在不划算的应用会变得划算。

16. Jason Liu、Hamel Husain：一年 LLM 应用经验（运营篇）

直播位置 7:47:01–7:56:00

Jason：怎样毁掉你的公司（反话）

Jason Liu 说他和 Hamel 过去一年做 AI 咨询，合作过约 20 家公司，从种子前到上市公司都有。他不想再给泛泛的好建议，于是反过来讲“怎样毁掉你的生意”：

  • 淘金热里卖铲子，所以你也要不停买铲子。往哪挖？买铲子。什么时候停？铲子会告诉你。RAG 不好用就换个向量数据库，方法不行就实现一篇新论文，也许换个嵌入模型就找到 PMF 了。专长、流程、决策框架都不重要，对的工具会解决一切。

Hamel：AI 工程师这个角色被误解

Hamel Husain 接着正面讲。他喜欢 “AI engineer” 这个词，感谢 swyx 推广它，但他认为大家误解了这个角色需要什么技能，期望也被抬高了。他展示那张大家都见过的图：AI 技能是一条光谱，中间有一条 API 分界线，分界线右边是 AI 工程师，技能是链、Agent、工具和基础设施，而评测和数据不在其中。他说很多人把这张图看得太字面，以为不用懂评测。

他说靠“凭感觉检查” Vibe Check 和现成工具，从 0 到 1 比以往任何时候都快；但没有评测就无法快速进步，会停滞，因为量不出来就改进不了，也走不出 0 到 1。他们的经验是，评测和数据素养通过四到六周的刻意练习就能掌握，所以这两项应该进入 AI 工程师的核心技能。

关于职位名：模糊的职位会带来过高期望，一出问题大家都找这个角色。数据科学家十年前也是这样，被当成同时懂软件工程、统计、数学和领域知识的独角兽，后来行业把它拆成决策科学家、ML 工程师、数据工程师等。他认为 AI 工程师可能也会经历类似拆分。他展示了 GitHub Copilot 团队的一些招聘职位，说它们对所需技能和产品写得很具体。按成熟度招人：刚开始只需要应用开发、软件工程或 AI 工程，做从 0 到 1；然后需要平台和数据工程来收集数据；之后才招 ML 工程师。没有数据就不要招 ML 工程师。他的总结是：AI 工程师常常职责过宽，定义又不清，补上评测能力可以解决很多问题。

17. Eugene Yan、Shreya Shankar：一年 LLM 应用经验（战术篇：评测、监控与护栏）

直播位置 7:56:09–8:07:30

Eugene：把评测拆简单

Eugene Yan 先引用一句 Hacker News 评论：团队对评测的重视程度，决定了它是在交付垃圾还是在做真正的产品。他举 Apple 的例子：Apple 介绍自家 LLM 时说收集了 750 条推送通知和邮件摘要作为评测集，因为它们代表真实用例。

他的建议是把评测拆简单。抽取商品属性时，拆成标题、价格、评分，各做断言 Assertion（写死的检查条件，比如“价格是否等于 X”）；摘要拆成事实不一致、相关性、信息密度几个维度；自然语言转 SQL 时检查是否用了预期的表和列。断言只能走这么远，之后可以训练评估模型，比如事实不一致分类器或相关性奖励模型；评测是分类和回归形式时更容易。

LLM-as-Judge 的辩论

两人在台上就 LLM-as-Judge（用一个 LLM 给另一个 LLM 的输出打分）唱反调。Shreya Shankar 说自己很看好它，还指着前排一位“真的法官”开玩笑。他们比较了几点：

  • 原型速度：LLM-as-Judge 最容易，写一个检查标准的提示，加几个好坏的 few-shot 示例就能对齐偏好。微调评估模型要收数据、建训练管线，前期投入大。
  • 对齐难度：Eugene 说让 LLM 裁判对齐到具体业务标准很难，台下没人举手说没遇到过困难；只要有几百到几千条样本，微调一个简单模型会更准。
  • 延迟：LLM 裁判要准往往需要思维链 Chain of Thought，一次要 5 到 8 秒；简单分类器或奖励模型每次约 10 毫秒，低两个数量级。
  • 技术债：LLM 裁判的 few-shot 示例如果不动态更新、不能持续对齐你对好坏的定义，就会失效；微调模型如果不持续用新的生产数据重新训练，也会漂移。

结论是看资源和阶段：刚做原型、需要低开发成本、评测量不大时，先用 LLM-as-Judge 并逐步投资对齐；资源更多或确定产品会留存时，用微调模型。

Shreya：怎样看数据

她说要知道该定什么评测标准，答案是看数据，她把那句“优秀的 AI 研究员会看数据”改成了“优秀的 AI 工程师会看数据”。

  • 什么时候看：有人从来不看，有人只在上线后看一次，都不对，要经常看。她合作的一家创业公司每上线一个新 Agent，就开一个 Slack 频道实时推送所有输出，几周后改成每天批量查看，看有没有没预料到的错误。
  • 看什么：找容易描述的数据切片，比如来自某个来源、包含某个关键词、属于某个主题。只说“这些都不好”而没法归类，就没法改进管线。
  • 代码库、提示、管线组件变化很快，检查轨迹 Trace 时要能知道它对应哪个 GitHub commit、模型版本、提示版本。她说 MLflow 这类传统 MLOps 工具在可追溯和重放上做得好。
  • 把 LLM 当 API 用时要固定模型版本，比如 GPT-4 1106 或某个固定的 GPT-4o 版本，因为 API 的行为变化很难量化。

Eugene：护栏和无参考评测

要一直看数据，就需要自动化的护栏。他改写了 Brandolini 定律：发现和修复缺陷所需的精力，比制造缺陷大一个数量级。调用 LLM API 很容易，难的是知道结果是否糟糕。基本护栏有毒性、个人身份信息、版权和预期语言。他说语言检查听起来简单，但你未必控制上下文：英文网站上有人用别的语言发广告，你让 LLM 抽取属性或总结，总有一定比例输出变成别的语言。幻觉也比想象中常见：只给电影预告片简介让它写摘要，它为了“帮忙”可能加入剧透，这些信息原文里没有。

他的技巧是建无参考评测 Reference-free Eval。有参考的评测要把输出和理想样本比较，收集理想样本很贵；无参考评测直接和源文档比较，比如判断摘要是蕴含还是矛盾于原文，这就成了幻觉评测，可以作为护栏用于所有新输出。

收尾

Shreya 提到 2015 年那篇 MLOps 经典论文（机器学习系统中的隐性技术债）里的图：模型只是一小块，周围有数据验证、特征工程、基础设施监控等。她说这些在 LLM 时代仍然适用，每个组件都能找到对应：特征工程对应 RAG，也就是检索相关上下文、组织好、别让 LLM 分心；数据验证对应评测和护栏。不能只给 GPT 包一层软件就上线。

Eugene 用 Karpathy 的话收尾：有一大类问题，很容易想象和做演示，但极难做成产品。Charles 找到一篇 1988 年用神经网络驾驶汽车的论文；25 年后，2013 年 Karpathy 第一次体验了自动驾驶演示；又过了 10 年，Waymo 拿到了在旧金山无人驾驶的许可。从演示到生产需要时间。

18. Thomas Dohmke（GitHub）：Copilot 的起源、Workspace 和他对 Agent 的看法

直播位置 8:07:40–8:26:00 · 访谈形式，提问人未报姓名（Dohmke 在回答中提到“你们 Amazon”）

Copilot 的起源

GitHub CEO Thomas Dohmke 回忆 2020 年疫情封城期间，大家在 Zoom 上，GitHub Next 当时的负责人（字幕作 “uger”，应为 Oege de Moor）拿到 OpenAI 一个 GPT-3 版本 Codex 的早期权限，大家口述提示让它写代码。他的第一个惊喜是它写 JavaScript 能把花括号放对，写 Python 也行，尽管它没有编译器那样的语法树，“或者你也可以说它就像我们一样懂”。他们决定做自动补全，第一个 Copilot 完全是远程做出来的。他说如果投资人说你必须在一个房间对着白板才能创新，在家里也一样可以。

内部预览（GitHub 叫 staff ship）的 NPS 达到 72、73 左右，早期产品通常低得多，何况那时 UI 还没定型、还有幻觉。2021 年中正式发布后，团队看遥测数据说它在启用的文件里写了约 25% 的代码，他第一反应是“遥测错了，回去核对”，结果是真的。现在大约一半，Java 等语言的接受率和代码行数更高。

怎样在整个 GitHub 推进

他说作为 CEO 要不断调整方法，AI 世界几乎每天都在变，不再有那种“长期战略、功能排好、按 backlog 推进”的做法，即使是 3000 人、隶属于全球最大公司之一的组织，也要尽量敏捷。第二点是在开发者所在的地方满足他们：“我们要做的是给工程师用的 AI（AI for engineers），不打算做一个 AI 工程师”，Copilot 这个名字就表达了以人为中心。

为什么从 IDE 里的灰色提示文字 Ghost Text 开始？他说这是绕开幻觉的办法：自动补全本来就不总是对的，你会边打字边调整，然后在合适的时候按 Tab。他描述开发者的日常：高手写很多代码才卡住，新手和像他这样很少写代码的人卡得更频繁，然后切到浏览器打开 Google、Stack Overflow 或 GitHub，找代码、和别人争论、复制粘贴再修改。他说 Stack Overflow 的“幻觉”和模型差不多多，答案本身未必不好，问题在于世界变得太快，比如他写 Swift 时每年 WWDC 后 API 都会变。Copilot 的核心是让开发者留在心流里，十年前这大概只会被叫作“更聪明的自动补全”。

Copilot Workspace

2022 年 11 月 ChatGPT 出现后，2023 年初他们把聊天和 GPT-4 加进 IDE 侧边栏，带 RAG 和 IDE 里的上下文。Workspace 更进一步：从一个 GitHub issue 或一个任务描述出发，结合你的仓库，帮你走到 pull request。每一步人都在中心：写规格说明、分析仓库现状、根据描述确定怎么改、写出修改每个文件的计划、生成 diff，人可以改每个要点和代码。他说它像一个帮你探索代码库的结对程序员，因为换新项目、改开源项目或者度假回来，最大的难题是在上千个文件里记起什么在哪。他强调目标是做帮助人完成任务、并让人在过程中学习的 Agent，他们不打算做自主 Agent。比如过程中会发现“这个测试文件也要改”。

非开发者也能用。去年 11 月 GitHub Universe 发布后，第一封反馈邮件来自一位产品经理，说现在写完用户故事就能看到它在代码里意味着什么。他说最大的挑战是把任务写得足够具体，很多事“在不明显之前都很明显”；估时也很难，他提到 The Pragmatic Engineer 最近写到《人月神话》仍然成立，多数估计只有实际时间的一半。Workspace 能帮你判断描述是否具体到可以写代码或做计划。

自然语言编程和 Agent

他的 T 恤上写着 “Copilot speaks your language”。大模型几乎会所有主要人类语言，孩子可以用德语、印地语、巴西葡萄牙语、西班牙语、中文学习布尔逻辑，而世界上大多数人的母语不是英语。这让家长没有技术背景、或者家长没有无限耐心的孩子也能接触技术，他说自己有两个孩子，深有体会。在职场上，新员工最大的难题是机构内的隐性知识，人们不愿问一千个问题，怕别人觉得自己笨，Copilot 能让人更平等地获取公司里的信息。

被问到 Agent 的定义，他说 Agent 像 AI 洗碗机：把碗放进去，让它自己运转，最后你把碗放回柜子。CI/CD、过去叫“机器人”的东西、监控 GitHub 是否宕机并自动呼叫值班的系统，在很多意义上都是自主 Agent。他说现在的安全工具反而制造工作：它告诉你碗脏了，然后你得自己洗，比如周五晚上本想烧烤却要去升级所有 Log4j 依赖。很多开发者把自己看作艺术家和创作者，而不是生产线工人，但公司、政府和世界要求他们做大量其他工作，所以需要 AI 来自动修复安全问题等。他最想要的 Agent 是能“烧掉”他的整个安全 backlog 的那种：全做安全合规，客户会因为功能停滞离开；全做创新，一出安全事故客户就失去信任。他还说，每次问团队一个想法要多久，估计都让他觉得自己做会更快，当然这不是事实，现在流程里有太多其他环节，需要新的抽象层。

给开发者的建议

他说自己出生在 PC 发明前不久，经历过 Commodore 64、90 年代的 PC、开源和互联网（互联网之前开源靠在书店买 CD 和 DVD）、SourceForge 和 GitHub、移动浪潮。每次阶跃，软件开发都变得更有趣，现在又是一次。作为 CEO 他很少有机会写代码，周日下午写代码时不想把时间都花在更新依赖、查 API 文档变化、研究怎么把容器部署上云上。他认为 AI 会把乐趣带回软件开发，鼓励大家回家去做点酷东西。
