02. Sam Green、Aaron Linsky（Bridgewater Associates）：Vault，让非结构化数据进入投资流程

直播位置 0:06:53–0:23:50 · 英文原题 Vault: Making Unstructured Data Work for Investing

Sam Green 是 Bridgewater 应用 AI 的团队负责人，Aaron Linsky 负责工程。他们讲的 Vault 是 Bridgewater 自建的数据平台，用来把非结构化数据变成投资流程里的一等资产。开头他们先给出三条经验：人和 Agent 对数据平台的需求很不一样，要分别满足；一个工具能同时满足两者时影响最大；最大的收获是打好基础，让 Agent 主动参与投资流程，不再只是等人来问的工具。

背景：从黄色便笺上的规则到 AIA

Sam 说，Bridgewater 50 年来一直在追求对市场和经济运行方式的最好理解，并把这种理解系统化地编码下来，以便长期压力测试自己的逻辑。最早是写在黄色便笺本上的 if-then 规则，后来变成以人为中心、持续复利的研究流程，最近他们在做 AIA（Artificial Investment Associate，人工投资助理），把机器放在这个流程的中心。过去的大部分历史里，这意味着在结构化数据上构建和监督时间序列模型，数据要对齐公司内部的本体（Ontology，即公司对“世界由哪些概念、概念之间什么关系”的统一定义）。有了语言模型后，他们可以使用新闻、研究报告、会议记录、政策文件，以及公司内部的备忘录、会议转录和争论。这些数据同样需要清洗、治理，既能回答“当下”的问题，也能用于跨时间的系统研究。市面上的数据供应商和平台给不了他们需要的控制力，所以他们自己建了 Vault。

他的数据是：Vault 里有超过 1 亿份文档，来自 135 个外部来源，每天还在按分钟新增数千份，另外还有 Bridgewater 内部的全部数据。这些数据会对齐内部本体，补充国家、概念、市场，以及最重要的“讨论的是哪个时间段”这些标注。

演示：韩元的问题

他向一个企业版聊天客户端提了一个典型的投资问题：AI 基础设施投资怎样影响韩元，市场参与者是否预期这种影响会持续。Agent 上网找到 15 个资料来源，但最终只用了其中一两个，结尾还承认自己没能在公开网络上找到足够文档来确认市场共识。更糟的是，它主要依据的一篇笔记发布于 2026 年 7 月，而他提问是在 10 月初，他说在 AI 投资的时代，三个月是很长的时间。同一个问题接上 Vault 后，连接会提示 Agent 关注特定时间段，于是它聚焦在 10 月 1 日到 8 日，找到 52 份相关候选文档，最后引用了 7 份，给出更完整、Agent 自己也更有把握的回答。他的结论是：要让 Agent 有用，需要好的数据和合适的连接器。

为两种读者设计搜索

Aaron 说搜索本来就难，同时为人和 Agent 两种读者设计更难。人需要精确度和高信噪比，因为读得慢，快的人每分钟大约 300 词；Agent 对精确度不那么敏感，只要数据在那里它就能找到，交给它的东西都会被“注意”到，它的阅读速度大约每分钟 3 万词，是人的 100 倍。他们列出五个维度：召回率（Recall，相关文档有多少被找回来了）、精确度（Precision，找回来的文档有多少是真相关的）、过滤、权限（Entitlements）和规模。他重点讲了三个：给人的精确度、给 Agent 的规模、两者都需要的过滤。

  • 精确度：数据和法务团队把 Vault 填满后，召回率不再是问题，但用户的头号抱怨是“Vault 搜索很烂”。他的回应是建基准。他们手工收集问题、找出最佳文档，也标出那些看起来有用其实没用的文档，一共约 200 个例子，不到一周完成。跑下来确实很烂：核心指标 Precision@10（前 10 条结果里有几条是对的）大约 60%。之后做了五项改进（幻灯片上列出），到做完 Agentic Search（让 Agent 多轮自主检索）时达到 90% 到 95%。
  • 过滤：从生产环境的 trace（每次调用的完整记录）看，几乎每次查询都带条件：截至某个日期、来自某个来源、关于某个资产。向量数据库（按语义相似度检索文档的数据库）传统上有两种过滤方式。后过滤先用向量索引找最相似的结果，再按元数据筛，速度快但召回率可能很低，因为全局最相似的结果未必满足条件；前过滤先按条件筛，再对所有匹配项算距离，召回率好但可能很慢。他们最后换到 turbopuffer，它的“原生过滤”只在含有匹配项的最近簇里查找和打分，速度接近后过滤，召回率接近前过滤。
  • 规模：人的用量很小，300 个用户，每小时约 100 次查询，读一篇文档要几分钟。Agent 轻松达到每秒 100 次以上，Agent 群可以到每秒数千次，读文档只要几秒。turbopuffer 也扛住了。权限这一项他说当天晚些时候另有分享。

先迁移旧习惯

Aaron 的第二条经验是，工具再好，直接放到投资人桌上也不会被用起来，研究员还是不会每天早上打开 Vault。他们观察到很多研究员活在邮件里：券商研报直接发到邮箱，用订阅列表和规则把邮件分进文件夹，这套方法熟悉可靠，也让他们确信没漏掉东西。于是他们把这些功能搬进 Vault：一切可搜索，订阅列表变成保存的搜索，文件夹变成保存的集合。习惯不变，换了个地方。习惯迁过来以后，才能引入新习惯：跨全部数据提问，按主题订阅动态信息流，把集合交给 Agent 做后续处理。他说到这一步才明确有了产品市场契合（Product-Market Fit）。之后用户希望到处都能用，他们就做了聊天入口、手机 App、Slack 和 IDE 集成，也把这些开放给 Agent，包括一个 CLI，“因为 Agent 喜欢 CLI”。

基于 Vault 的应用有：Pocket Analyst，他们的第一个 AI 分析师，几分钟、几美元就能完成几小时的研究；下一代的 Researcher，把同样的思路扩展到几天或几周的任务；在 Vault 数据上训练的定制模型，和其他基础模型一起供给系统化决策流程，第一个是 Forecaster，生成和宏观相关的 AI 预测；还有从 Vault 构建的投资信号，把非结构化数据变成结构化的可交易策略。

投资人工作台：让 Agent 主动工作

Sam 最后介绍了 Investor Workbench。Agent 始终在线，跟踪每位投资人关心的东西，把最需要注意的话题推给他们。界面上每个话题是一张卡片，比如前面那个 AI 对汇率的影响，卡片里有 Agent 的摘要、它所依据的原始证据，以及通往分析工具研究结果的入口。投资人和 Agent 一起深挖时，双方协作得出的结论会自动写回 Vault。他说 Vault 能让知识复利：它把正确的内外部信息交到投资人和 Agent 手上，又自动把他们产出的综合结论放回语料库，供下一轮使用。结尾他问听众：你的 AI 知道世界上正在发生什么吗？它记得你的公司对此学到了什么吗？

03. John Feminella（Two Sigma 架构 SVP）：在加速和安全之间平衡 AI Agent

直播位置 0:23:59–0:43:10 · 英文原题 Balancing Acceleration and Safety for AI Agents

John Feminella 在纽约对冲基金 Two Sigma 负责 AI 架构和工程。他先放了一张法律免责页：不推销任何证券，所讲内容只代表个人观点。他说这张页本身就体现了这个行业受监管的程度，而要理解为什么需要管控，最好看看管控失效时发生了什么。

Revlon 与 Citibank 的 9 亿美元事故

2020 年 8 月以后，很多商业贷款合同里出现了一个新条款。他用柠檬水摊打比方解释它防的是什么：你向贷方借钱，中间的银行在一次灾难性失误中把你欠的全部钱都打给了贷方，贷方可能会说“你已经还清了，我们不退”。Revlon 当时有一笔 2016 年的大额定期贷款，拆给了 300 多家贷方（对冲基金、信贷基金、CLO、其他银行），Citibank 是行政代理行，负责在借贷双方之间转钱，不出自己的钱。2020 年 8 月 11 日的计划是 Revlon 付约 800 万美元利息，本金转入新的贷款安排，只是换纸面，不动现金。

Citi 用的内部系统叫 Flexcube。在 Flexcube 里，最方便的做法是假装记录 Revlon 全额还款，以触发正确的利息计算，本金部分则应转到银行自己的内部“洗账户”（wash account），不离开银行。为此，几个字段都应填上洗账户号并勾选旁边的复选框，但出于各种原因没有勾选。Flexcube 弹出警告说“钱要离开银行了，确定吗”，这个警告本身是对的，因为利息确实要付出去，所以三位审批人都认为没问题并放行了。结果 Flexcube 把全部未偿本金约 9 亿美元打给了 300 家贷方，而原本应该是 800 万。Revlon 当时经营困难，贷款的交易价格只有面值的 60% 左右，拿回全部本金对贷方是好事，所以 Citi 打电话求退款时很多贷方拒绝了。此后商业贷款合同普遍加入了防这种情况的条款。

他说这个故事和 AI Agent 的关系是：银行有流程、有管控，每个人都做了自己认为正确的事，事故还是发生了。我们每天都在给真实的 Agent 真实的自主权，去操作 Flexcube 这样的系统，问题是怎样在不把一切锁死、也不靠运气的情况下防止事故。

基本立场

他说你无法提前知道 Agent 会做什么，它是非确定性的；人也是非确定性的，也会犯错，但公司不会为了降低人犯错的风险把人锁在房间里、互相复查所有工作；公司的做法是给人一定自主权加一定管控：边界、可见性、帮他们做好工作的系统。所以他认为安全和创新可以同时拥有。他们试过但不适合的做法有三种：把一切放进沙箱，安全但没有真实访问权限就没什么用；让 Agent 随便做，隔离太弱，不适合强监管企业；只写政策文档放进提示词，运行时无法强制执行。

他说的“管控”指护栏（Guardrails）和共享能力，让团队可以照常推进，不必先等别人造好桥。这些管控是可组合的，每个只做一件事，合起来让 Agent 在合适的安全水平下拥有真实自主权。他讲了五个。

五项管控

  1. Agent 注册表：Agent 到处都是，大团队有很多，小团队有几个，个人也在不受控地跑东西：聊天机器人、拼凑起来的 MCP 服务器（MCP 是让模型调用外部工具和数据的开放协议）、笔记本实验、实用的网页工具。很难回答谁拥有它、它能用什么工具、该做什么不该做什么。无法治理也就无法复用，大家会重复造轮子。常见做法是设一道闸，所有东西登记审批完才能运行，但这样一个简单的笔记本实验也要排在高风险项目后面，多数人会放弃或转向更不透明的影子 IT。所以第一个管控是注册表，记录每个 Agent 声明的工具、访问的端点、所属产品和负责人，人、程序和其他 Agent 都可以查。使用公司批准的 Agent 框架时会自动注册，不需要额外工作，也可以手动注册。
  2. 风险评分：总结 Jira 或 Linear 工单的 Agent 和能碰线上系统的部署 Agent 风险完全不同。如果都走同一套人工审查，就会出现一个简单的总结器和动生产系统的 Agent 一样等两个月签字。他说大多数有价值的 Agent 想法起初都是小实验。企业里多数 Agent 是专用的，目的明确，不像 Claude Code 或 Pi 这类开放式编码 Agent 那样不知道用户下一句要问什么，可以根据它们事先声明的工具、端点和管控来区分风险，让人工审查集中在该去的地方。
  3. 按用途授权的护栏：越开放的 Agent 能做的事越多：调内部 API、跑网页搜索等，每一项都是不同的风险入口。给一个 Agent 某个角色账号的权限，比让它读公开网页危险得多。给所有 Agent 同一份短白名单、其余全部封禁是安全的，但没用，团队会放弃或绕过去。他引用 John Shedd 的话：船停在港里是安全的，但造船不是为了这个。他们的做法是让 Agent 事先声明用途和需要的工具，比如研究总结 Agent 可以用网页工具，发布部署 Agent 没有理由用，默认就拿不到。作者最清楚自己需要 500 个工具里的哪 4 个。执行层面，Agent 在托管环境中初始化时会去注册表查适用的策略，并转成可执行的规则：能访问哪些端点、哪些主机、哪些资源。只要符合风险评分并登记在册，就算获得批准，不需要每次开工单。
  4. 共享的 Eval：各团队评测 Agent 的方式五花八门，有的团队什么都没有。他说不写单元测试大家会不高兴，Eval 也一样：模型相当于应用的运行时依赖，换模型后没有 Eval 就不知道输出质量变了没有。一套中央评测方法加委员会签字会让每次改提示词都排队。所以他们把各团队 Eval 的共同部分做成公司统一运营的共享能力，团队只需写清楚“关于自己的 Agent 什么是对的”。
  5. 运行时分类器代替逐条审批：Human-in-the-loop 小规模时没问题，Agent 并行或上生产后，审批请求来得比人能处理的还快，人会陷入审批疲劳，一路点“是”，终有一次点到不该点的。他举了今年早些时候的例子：一家 AI 研究实验室的总监让她的 OpenClaw Agent 建议可以删除哪些邮件，并等她批准；但收件箱太大，Agent 做了上下文压缩（Compaction，把较早的对话压缩成摘要以腾出上下文窗口），丢掉了“等我批准”这一条，删了几百封邮件，她叫停也没停。他的做法是：有明确规则时走确定性的快速通道；规则不明确时交给独立的、偏保守的分类器判断常规调用，只把模糊或可能危险的请求交给人，明确危险的直接拒绝。如果 99.99999% 的情况都会点“是”，那就该写成规则，而不是去问人。

他最后把五项串起来：注册表让每个 Agent 从创建起就可见；评分让人工审查放在对的地方；护栏让 Agent 只碰需要的东西；共享 Eval 让大家不用重复造轮子就能达到同一标准；运行时治理让分类在运行时完成。结尾他问：汽车为什么有刹车？为了能开得快，同时能安全停下。

04. Max Kanat-Alexander（Capital One 首席软件工程师）：代码质量还重要吗

直播位置 0:43:16–1:00:15 · 英文原题 Does Code Quality Even Matter?

Max Kanat-Alexander 是 Capital One 的首席软件工程师，著有《Code Simplicity》。他开玩笑说选了一个“没人有意见”的话题，社交媒体上关于“AI 时代代码质量还重不重要”的说法都很“有深度”。资深工程师对每个问题的标准答案都是“看情况”，但这没用，要说清楚看什么情况。他想给出一个推理框架。

理解和执行

他说软件上想达成的任何事都只取决于两个因素：理解，以及基于理解去执行。调试器、可观测性、Eval、测试都是为了提高这两者，代码质量领域做过的一切也只为这两者服务。对软件工程师最重要的两种理解是：系统实际的行为是什么（不是文档说的），以及怎样正确安全地修改这种行为。一个打印 hello world 的小程序很好理解；真实系统复杂得多，他放了 Chromium 代码库的结构图，说整体行为几乎有无穷多种可能，没法用语言描述，但可以描述其中一个组件，比如 URL 解析器。他说代码存在的理由就是结构：他对比了两段在 Linux 上都能打印 hello world 的代码，一段有可识别的“hello world”身份和结构，另一段只是一串指令，规模小时都能懂，几百万行时就不行了。过去讲的可读性、可测试性，说到底是系统有没有可理解的结构。

修改系统有两类风险：引入问题（包括 bug，也包括延期、预算超支、行为不符合用户需要），以及让未来的修改更难，也就是增加未来的风险。这两者都源于理解困难：系统本来难懂，修改又让它更难懂。他说他读过的每一份事故复盘都能归到这两点。第二点会反过来加剧第一点，形成非线性复利，最终所有系统都会走到每次修改都出问题的地步，比如那些上亿行的大型机代码库。至于未来模型能不能无限处理复杂度，他说也许能，但今天不讨论。

一次性软件

他说模型正在制造一类一直存在、但即将比其他软件多十万倍的软件：一次性软件（Disposable Software）。设想失败的后果很小，几乎没人和系统依赖它，几乎不需要变更管理，替换成本接近零（几小时或几天重写），维护几乎不花钱。在这种情况下代码质量不重要，因为它要防的长期复利风险不存在。传统软件是耐久软件（Durable Software）：存在多年，被成千上万人依赖，失败可能是业务灾难，需要大量维护，世界上多数工程师的时间都花在维护这类系统上。他认为耐久系统仍会是世界上最重要的系统，数量还会增加，但数量最多的会是一次性软件：不喜欢系统自带的计算器就自己做一个，给孩子办派对就写一个只用一次的派对规划软件，用完扔掉。

他说以后工程严谨程度应该按软件的一次性程度来定，判断依据是四个因素：后果、替换成本、依赖、维护成本，四者都低就是一次性软件，都高就是耐久软件。有经验的人知道应该往耐久那边估。同时也有了一件新的事可做：主动让软件变得可丢弃。方法包括：更好的隔离环境（比如只能访问你自己的数据、没有客户数据和个人身份信息的环境）；强制独立（该环境不允许其他生产系统调用进来）；冗余（保留一个老旧但可靠的后备系统，大家想用 vibe coding 自己做更顺手的前端就随他们，坏了还有后备）；限制范围。他认为“怎样提高可丢弃性”是一门新的软件工程分支。他再次强调耐久软件工程不会消失，这是社交媒体上最大的误解；AI 编码工具让做耐久软件更容易，耐久软件的绝对数量会增加。一次性和耐久之间是连续的光谱。

降低严谨的成本

他说最值得关心的是降低严谨的成本：严谨越便宜，越不用纠结软件在光谱上的哪个位置；原以为是一次性的、后来发现要耐久时，也更容易改主意。他只有五分钟，讲了几项：

  • 标准化：它的作用是消除可能性。系统里没有 PHP，就不用研究 PHP 的 linter、最佳实践和安全漏洞。框架、RPC 协议的标准化也是同样道理。Agent 当然可以给每种技术栈都写一套工具，但每次都得重来。
  • 工作流内工具：程序员不需要主动运行、也不需要懂它怎么运行，它自动发生，感觉像免费的，而且可靠（误报少、快）。这样一次性软件也能用上。比如他一直希望每个服务都提供内存版的假实现，让测试又快又确定，现在编码 Agent 就能做，但得有人决定去做并开放给所有人。
  • 最大严格度：把所有 lint 规则开到最高，从不妥协。只要误报率低、后果不严重，偶尔 linter 错了也无所谓，省下的是未来大量的问题。在百万行代码库里事后打开 linter，往往就是一个十万行的改动。

他的回答是：一次性软件的代码质量不重要；耐久软件的代码质量重要；严谨不一定昂贵。

05. Aparna Dhinakaran（Arize AI 联合创始人、首席产品官）：AI 工程师到底做什么

直播位置 1:00:22–1:16:00 · 英文原题 What Does an AI Engineer Do?

Aparna Dhinakaran 说每年大家对 AI 工程师的定义都在变。她准备这次演讲时，Andrej Karpathy 刚好在周末发了一条推文，讲前沿用户和普通用户之间越来越大的差距。按他的漏斗：60 多亿人接触过 LLM，10 到 20 亿是偶尔使用的免费用户，约 2000 万是把几周的工作缩到几天的专业用户，而在最前沿、同时运行成千上万个 Agent 的人大约只有 5000 个。她说过去几十年抽象层一直在升高，近几年更快：从写高级语言，到复制粘贴代码，到本地 Agent、云端 Agent，现在的期望是每个人都运行一支 Agent 团队或 Agent 工厂。

从“写功能”到“建循环”

她对比了 AI 工程师过去和现在的工作：以前是写一个 AI 功能，现在是搭建写这个功能的循环；以前是读 diff 做代码审查，现在是搭系统和 Agent 去做审查，再写 Eval 来检查这些非确定性任务；以前是设置指标和遥测，现在是让 Agent 去读可观测性数据、找出模式。构建、评测、发布、监控、改进这个循环，AI 工程师现在要负责的是搭出执行每一步的那个循环。

Signal：Arize 的常驻 Agent

Arize 在产品里推出了 Signal，用来替 AI 工程师跑这个循环。它读取所有 trace 和遥测，识别其中的模式，如果有代码库权限还能提交修复的 PR。她讲了构建它的经验：

  • 遥测的主要消费者已经变成 Agent。可观测性数据可以成为唤醒常驻 Agent 的触发器。Signal 的触发方式可配置：按固定周期（每 3 小时、6 小时拉取最近一批 trace），按事件（比如用户在 Slack 里抱怨），或按指标。
  • 每次运行时，他们把 trace、第三方遥测（APM 日志和指标）、代码库访问权限和需要的密钥放进一个沙箱。进出沙箱只能通过一个代理，沙箱里发生的一切都被追踪，生成的问题保存到记忆里。它还要记住以前见过的问题：某个之前看起来像问题但没被记录的现象，数据多了以后可能变得更严重。
  • 运行结束后，保留的是发现的问题（存入记忆，下次不用从零开始）、Agent 自己的 trace，以及运行中学到的技能（Skill，可以写回代码库）；丢掉的是沙箱本身、凭据和代码库访问权限。
  • Signal 设计成持久执行的：沙箱或 Harness（包在模型外面、负责调用工具和管理循环的程序）中途失败时，状态保存在沙箱外的记忆里，可以重新启动沙箱和 Harness，从失败的那一步继续。
  • 它不绑定模型和 Harness：从 Claude Code 起步，现在也支持 Cursor 和 Codex，目标是支持主流的开源 Harness；用 Claude Code 时可以选 Anthropic 家族的任意模型。她说这样方便评估 Agent 质量、控制成本，看能否在用更便宜模型时保持发现问题的质量。

AI 工程师要会写 Eval，还要评测评测器

Signal 每次提 PR，上面都有 Eval 来检验。Eval 可以很简单，比如一个数据集加一个提示词，检查有没有回退；但它需要和人的判断对齐。她认为 AI 工程师应该把大量时间花在和 Agent 一起看 trace、找出常见错误上。她提到前一天 Lance 讲了 Claude 的一个用来构建 Eval 的 Skill，Arize 也有一个 evaluator Skill 帮助编写和对齐 Eval。很多团队问她：怎样信任评测器？Arize 自己的做法是评测评测器：构建人工标注的金标准数据集，跑 Eval，和人的结果比对，确认 LLM 评审（LLM-as-a-Judge）和人的判断一致后才发布新的评测器。这些 Eval 既可以用于离线测试，也可以在线运行。

她的收尾是一个完整的系统：Agent 上线前跑离线 Eval；上线后追踪一切，包括构建这些 Agent 的编码 Agent（Claude Code、Cursor、Codex 都可以追踪）；在遥测上跑在线 Eval；这些结果再交给读遥测的 Agent 去找问题、补差距。她说实验室和企业之间差距很大，部分原因是企业数据比实验室里受控、可测试的环境乱得多，AI 工程师的角色就是缩小这个差距：追踪一切，学会测试，搭建让 Agent 从遥测中改进系统的机制。

06. Freddy Lecue（Wells Fargo AI 建模负责人）：Wells Fargo 交易基础模型与大规模欺诈检测

为什么要做“交易基础模型”

他说基础模型不一定要基于语言。金融机构有大量语言数据，但更多的是表格形式的结构化数据：客户的借记卡、信用卡、电子支票交易，来自多个渠道，每月数十亿笔。把这些直接塞进语言模型能有收获，但不是最好的方式。他们的目标是建一个“骨干”模型，学到客户交易的表示（Representation，模型对数据的内部向量化理解），然后针对下游任务微调：信用评分、欺诈检测、反洗钱、营销。过去这些模型分散在各个部门，现在可以共用一个骨干。

他先剧透了结果：表格数据大家通常会用 XGBoost（一种梯度提升树算法，表格任务的常用强基线），他们生产环境里原本就是 XGBoost 模型；新模型在欺诈检测上超过了它，检测率更高，误报更少，延迟也满足要求。他说的“基础模型”指的是 Transformer 结构。

数据和分词

语言模型处理文本 token，预训练学会预测下一个 token，再做监督微调和 RLHF、RLVR 等后训练。交易基础模型把基本单位换成交易，预测下一笔交易或交易里的下一个 token，目的同样是学到表示，用于下游任务，学习交易随时间的关系，以及不同客户交易之间的关系。他强调是从零预训练：只用现成的架构，不用任何开源权重，在自己的 GPU 集群上训练几天到几周。

数据规模是数十亿笔交易、上百万个账户，每个客户每月几百笔交易。他们看五个维度：谁（客户或商户）、什么（买了什么）、怎样（哪个渠道，信用、借记还是电子）、何时、何地，展开有上百个特征。现有生产模型里有大量手工特征工程，很耗时间；他们退回去寻找真正需要的原始特征，最初有上千个，最后精简到约 100 个，让 Transformer 自己学特征之间的关系。这套词表是金融业特有的，这也是他们不用现成预训练模型的原因。

他说最难的是分词（Tokenization）：数值、类别、邮编这类信息怎样变成 token。每个邮编都单独做一个 token 吗？词表太大训练会出问题。所以要花很多功夫决定“值到 token”的映射，再做 token 到 ID、ID 到嵌入向量的查找。类别特征有的只有 8 种取值，有的多得多；交易金额很重要；还有两笔交易之间的时间差、IP 地址、邮编等，可能编码成一个二值 token，也可能需要很多 token。美国邮编远多于他们用的约 2800 个 token，他们按分布对邮编分组。

架构和训练

  • 他们参考了 Chinchilla 的缩放规律（关于参数量和训练 token 数怎样搭配最省算力的经验公式）来确定规模，也借鉴了已有的表格基础模型的开源工作。
  • 模型约 10 亿参数，是能带来最大提升的最小规模；下一版在做更大的规模（字幕为 11 billion）。他说不想和语言模型领先者比参数量。
  • 只有解码器的结构，预训练目标是预测下一笔交易。最初按 Chinchilla 每参数约 20 个 token 估算数据量，实验后发现需要的 token 数还要多 10 倍。
  • 训练配方没有新东西：混合精度、分布式数据并行、尽量大的批量、Muon 优化器、RoPE 位置编码、FlashAttention、激活检查点。他说秘诀在分词和后训练。

欺诈检测结果

下游任务是判断一笔交易是否欺诈。XGBoost 在大量标注过的交易上训练，但它看不到当前交易和该客户历史交易之间的关系，除非费力地手工编码；Transformer 的注意力机制可以让当前交易“看到”过去的交易，他们认为这是检测率提高的主要原因。推理时输入的是客户的交易序列，判断最新一笔是否欺诈。拒绝交易必须在 250 毫秒内完成，他们的延迟比这个快约 10 倍。

主要指标是检测率和误报率，它们直接对应钱：误拒一笔正常交易，客户会打电话来，产生运营成本，还会丢掉这笔交易。新模型标记出更多欺诈，同时减少了误报，他说相对 XGBoost 基线节省了数百万美元。现在同一个骨干正在被研究用于提升信用额度、反洗钱和营销，供 Wells Fargo 的不同部门共用。

07. Aman Singh（Arca AI 负责人）：运营公司业务的长周期 Agent

直播位置 1:53:30–2:06:35 · 英文原题 Inside Arca's Long-Horizon Agents That Run the Business

Aman Singh 负责 Arca 的 AI。Arca 是一家 AI 原生的金融服务公司，提供财务规划、税务规划、资产管理和投资建议，客户既有想提前退休的科技高管，也有刚攒到第一个一百万、终于想买房的新罕布什尔家庭。他说的 AI 原生是 Agent 运营业务，执行那些决定客户结果的决策，不在角落里当副驾驶。Arca 不卖软件，它自己就是这家服务公司，是一家恰好在经营金融服务的应用 AI 公司。

长周期，不是长时间运行

他说金融服务的工作是“长周期”（Long-Horizon）的，不太是“长时间运行”的：Agent 并不连续几小时几天消耗 token，典型情况是一个客户目标跨越 10 天，走走停停，中间有很多参与者、决策点和交接。例子是客户 Jane，4 月 15 日有一大笔税要交，要找出最节税的筹钱方式：顾问分析账单、设计方案，交易员卖出资产，资产结算要几天，运营人员再发起转账，转账又要几天。客户一多，公司在这类工作上花的时间就会成倍增加。

一封邮件的旅程

Arca 让 Agent 端到端负责这种长周期结果，给了它们几样东西：来自外部世界的信号，让它们知道发生了什么；全部运营上下文，知道遇到这种情况行业里怎么做；一个 Harness，提供工具、护栏，以及最重要的跨长周期的持久记忆；和人协作的能力。他说他们做的事就是把人从这项工作的关键路径上拿掉，没人需要连续几天盯着一个目标。

  • 信号：Jane 发邮件说要交 10 万美元税。邮件和电话、进来的文件、会议、托管机构的事件、市场波动一样，都是后台 Agent 持续评估的信号。
  • 执行：Harness 告诉 Agent 怎么处理；Agent 有深度的客户记忆，比如知道 8 个月前 Jane 在电话里说过永远不要动她的 Apple 持仓；金融计算在沙箱里做。他说现在的 Harness 正趋向同一种形态，更有意思的是 Harness 之外发生的事。
  • 协作空间：Agent 产出的方案不能脱离人执行。Agent 会建一个“空间”，把方案放进去，多人可以和 Agent 聊方案，需要人做事时 Agent 把人拉进来，比如批准方案、批准发给 Jane 的邮件。
  • “替人盯着世界”：Agent 可以登记对某件事的兴趣，“Jane 回复时通知我”“转账到账时通知我”，后台的信号系统把信号路由给关心它的 Agent。信号一直不来，Agent 也可以按计划自己醒来跟进。
  • 现实很乱：Jane 一直没回邮件，团队当面见到她得到了新信息，录入到界面里。在界面里录入信息、改日程、把任务标记完成，这些动作本身也是唤醒 Agent 的信号，所以系统同时知道外部和内部发生的事。Agent 之间也会互相通知：一个后台 Agent 读到这条信息，通知另一个 Agent 把空间里的金额从 10 万改成 8 万。
  • 在对的时候拉对的人：Agent 读运营上下文，知道下一步该让负责交易的人上场，就给那个人派一个任务。

他说这些就是驱动长周期工作的原语：保持感知（信号系统）、知道下一步做什么（运营上下文）、做事（Harness）、保持状态（持久记忆）、在对的时候拉进对的人。想法简单，但涌现出的复杂度很高：任何时刻都有上百个信号进来，任务被派到人手上，后台 Agent 互相通信。过去 6 个月他们在补上下文缺口、提高任务的精确度（该现在做的变成任务，未来要跟踪的放进 Agent 记忆）、提高长周期保持状态的能力。因为他们就是这家公司，他们还在统一和规范公司内的工作方式，把它转成 Agent 的状态；用产品的是同事，同事给出的推理过程会变成改进系统的 Eval。

Agent 提示人，多过人提示 Agent

在 Arca，员工登录后看到的是 Agent 为他们准备好的任务列表：邮件已经读过，文件已经看过，90% 的工作已经做完，只在需要人行动时才拉人进来。他说到了这一步，Agent 提示人比人提示 Agent 更多。再进一步，Agent 可以推动业务本身：Jane 那封邮件其实是一次失败，公司本该主动。于是设一个新的业务目标“主动性”：每年 1 月为每位客户准备好税务情况，在客户开口前主动联系。在 AI 原生公司里，只要把这个目标加进 Agent 的目标集合，它们就会开始推动：1 月份每位客户的分析做好了，带完整方案、一键批准的邮件出现在员工的任务里。他说区分“用 AI 工具的公司”和“AI 原生公司”的标准是：能不能通过引导 Agent 来引导业务。

08. 圆桌：Allie Howe、Ian Livingstone（Keycard），Michael Davis（JPMorgan Chase），Dick Hardt（AAuth）：基于意图的授权

直播位置 2:15:49–2:59:30 · 英文原题 Intent Based Auth

主持人 Allie Howe 是 Keycard 的技术员工。嘉宾是 Keycard CEO Ian Livingstone、JPMorgan Chase 全球首席安全架构师 Michael Davis（大家叫他 Davis），以及 AAuth 的创始人、OAuth 的共同创作者 Dick Hardt。

Allie 先定义了话题。运行时授权（Runtime Authorization）是指对 Agent 的每一次工具调用单独授权，而不是让 Agent 长期持有最终会被滥用的宽泛权限。但“这次调用该不该放行”从来不简单：很多 MCP 工具和 API 的权限粒度很粗，人很难写出完美的策略，Agent 运行时环境也在变。意图（Intent）可以提供额外的上下文，帮助运行时做出更好的授权决定。

为什么模型这么强，Agent 的自主权还是给不出去

  • Ian：金融等受监管行业几乎总是安全优先，创新排第二、三、四位。企业里到处是零散的身份和系统孤岛，Agent 很难在其中导航、申请权限。多数系统的权限是粗粒度的，他举 Salesforce 为例，很长时间里它的 OAuth 只有一个叫 “api” 的 scope。这些安全系统是为人做决定、软件是确定性的世界设计的。
  • Dick：大家找 Agent 授权方案时，架子上现成的工具就是 OAuth。但 OAuth 原本是为“让这个网站和那个网站对话”设计的，OAuth 2 才加了 scope，它要求客户端预先注册，假定有浏览器和重定向。Agent 的世界不同：事先不知道 Agent 要做什么，不同实例需要不同权限，把现有 scope 直接映射给 Agent 粒度太粗。
  • Davis：做得好的企业像入职开发者一样入职 Agent，第一天不给全部提交权限，随着成熟逐步加能力。判断一个 Agent 是否安全，不能只看 Agent 自己声称什么，还要看它周围的环境，比如沙箱在哪里运行、是否在沙箱里。

Allie 举了粗粒度的例子：Notion 的 MCP 服务器可以“获取这个页面”，但不能只获取页面上的某个数据库。Davis 说银行很早就从“认证和授权人”转向“授权交易”，而交易是在运行时发生的，Agent 授权可以借鉴这些教训。他用支票打比方：支票上的备注栏写的是这笔付款的意图，但支票本身仍有金额、收款人、日期等限制。Dick 补充，判断一笔付款该不该做，要知道为什么付、之前发生了什么，比如 5 秒前是不是刚付过一笔一样的，这次就是重复付款。所以 AAuth 引入了“任务”（Mission）的概念：Agent 整体上要完成什么，每个决定都在这个任务的上下文里做。Ian 举的例子是两个 ChatGPT 或 Claude 会话，一个帮你购物，一个帮你查生产环境 bug，权限画像和什么时候该叫人回来完全不同。他说如果不能传递用户或企业的意图，就无法实现真正的自主；上午好几场都在讲“用 Agent 运营业务”，可一旦出现 PocketOS 那样的事故，Agent 因为权限粗糙误删了生产数据库而不是测试库，问题就来了。

Mission、监督 Agent 和意图的交集

Dick 说，在 AAuth 里，Agent 代表“人”行事，人可以是个人或组织，因为最终是人对 Agent 的行为负责。Mission 是人交给 Agent 的事，好的 Agent 会和人协商参数，类似以前（他说“好像就是三个月前”）先让 Agent 写计划再执行。Mission 的标识会贯穿所有操作，事后可以审计这个任务里做过哪些事、做了哪些决定。今天几乎没有好的 Agent 身份或任务的概念。

如果用户让一个 Agent 去读 CEO 的邮件，超出了它的范围怎么办？Dick 说应该拒绝。他主张关注点分离：一个 Agent 干活，另一个独立的监督 Agent 不干活，只决定干活的 Agent 能做什么。读别人的邮件这种明确的事，确定性策略马上就能拦住；“把 CEO 的邮件转发到外部”这种更模糊的事，就该交给监督 Agent 判断。

Ian 说他和 Davis 很早就讨论过审批疲劳（Consent Fatigue）。Keycard 的观点是：先有宽泛的确定性策略，规定什么绝对不能发生、什么必须有人参与；但人或组织能写出的策略和某个具体任务真正需要的策略之间有很大空隙。意图有两种：企业为什么采用这个 Agent（比如买 Claude Code 是为了让开发者更成功），以及此刻为什么用它（修复测试环境里的一个 bug）。把两种意图都转成 Agent 能做什么的边界，取交集，就得到这次可以做的事。难点是只在绝对必要时才把用户叫进来，否则会影响采用。Davis 接着说，这种交集的好处是不同意图可以来自组织的不同部门，各自独立维护，再组合成一个决定，而且这个决定不必是静态的：如果上下文显示请求者是 CEO 的行政助理，也许她就该能读邮件，或者只能读日程。他说这在企业里还很新，但能让开发者更容易推理、也更容易互操作；意图可以贯穿很多事件，持续几周。他还开玩笑说，很多企业还在处理“权限写着只读、实际是读写”的问题。

Agentic Commerce 和 Agent 身份

Allie 说意图授权对 Agent 购物（Agentic Commerce）很有用：用户能确保 Agent 用自己的预算买对东西，商户能知道为什么买、要不要信任这个 Agent。Davis 说这延伸了“了解你的客户”（KYC）的概念，现在还要“了解你的 Agent”，并把 Agent、用户、运营方、处理方的意图都关联起来，这对监管要求也有帮助。Ian 说网络一直有“未注册客户端”的问题：你在 eBay 没登录，怎样证明你是人、能用 50 美元出价？他提到 Muse、Instinct、Grokbot 这些个人 Agent，以及最近 Sierra、Decagon 等公司宣布的个人 Agent 协议。验证码原本用来防垃圾和滥用，现在已被 Agent 攻破。他举了两三年前 Vercel 在西班牙被封的例子：Vercel 上所有站点共用同一批 IP，其中一个站点非法播放足球联赛内容，西班牙就封了整个 Vercel。Agent 的问题类似但严重得多：从没见过的流量来到门口，要决定让不让它进。Dick 说他支持个人 Agent 协议（他称为 Poppy），但它走得不够远。他认为需要标准，这样不同来源的组件可以互相替换；Agent 做的事多到人不可能逐个审批时，就需要一个属于你自己的、独立于干活 Agent 的监督 Agent 来执行你的策略，否则护栏由 Agent 的厂商决定。Ian 补充，问题在于业界会不会选择偏向少数大厂的方案，还是像 OIDC、TLS 那样走联邦式的开放协议。

Davis 还提到“心理所有权”：有了意图，人和 Agent 的结果之间就有了联系，出错时人更容易承担责任。他引用了 1979 年 IBM 培训手册里那句常被转发的话（大意是计算机永远不能被追责，所以不能让计算机做管理决定）。Allie 说意图的另一个说法是动机。Davis 说，把意图换成动机，诊断就变成了取证：调查失控的 Agent 时，很难分清它想做什么和用户想做什么，意图信息如果不可篡改地沿系统传递，就能更快判断是人的错误还是 Agent 软件的错误，控制影响范围。

预算、大脑与双手的分离

Allie 提到最近的 Resy 事件：一个 Instinct 的 Agent 替用户在 resy.com 订餐厅，太积极，一小时调了 200 次 API，导致用户账号被封。Dick 说过去这是 bug，修掉就行；现在 Agent 会“一直试到成功”，它们不知道这算滥用，也没有信号告诉它们该用多少。所以 AAuth 加了预算（Budget）：给 Agent 的令牌不仅有时间限制，还有资源用量限制，令牌过期或预算耗尽都会失去访问。耗尽后由监督方决定要不要追加。和传统限流直接切断不同，预算会持续反馈给 Agent 还剩多少，让它像人一样知道资源稀缺、省着用。

Allie 问到“大脑与双手分离”的架构（会场回声太大，Dick 没听清，Ian 接过来回答）。Ian 说他总记得 PocketOS 事件里 Agent 在磁盘上翻到一个随机密钥，Agent 是高度目标驱动的。大脑是模型，双手是放在沙箱里的工具，沙箱的意义在于你能控制里面有什么，它拿不到 API 密钥；沙箱外有一个出口代理（Egress Proxy），授权边界就设在那里，也可以在那里和外部系统做协议转换，运行 AAuth。他说这是 Anthropic、OpenAI 等实验室目前主要采用的模型：里面让 Agent 自由尝试，外面有确定性的一层。Davis 补充，大脑不止一个，记忆系统就可能把“大脑”放进循环里：写进记忆的内容会影响后续每个 Agent 的决定。他提出要关注“有毒组合”，并举了动态移除工具的例子：Agent 要写邮件时，在邮件工具完成、任务结束之前，禁用网页搜索等所有能对外发送的工具，之后再恢复。Ian 说，MCP 曾被抱怨上下文膨胀，意图系统能在对的时间给 Agent 对的能力，让它少走错路，也少花 token。

放到生产环境里

Davis 说这些讨论把话题从认证推向授权：怎样动态授权、怎样验证、怎样在对的时候让人参与。他同意 Dick 的看法，Human-in-the-loop 在很多情况下是反模式，人会疲劳，但重要时刻必须能把人拉进来。这些以前不是工程讨论，现在工程师参与授权设计，威胁建模和攻击面分析的方式都在变；Agent 能做的事越少，决定越好，他们见过真实案例里 Agent 循环因此更快更准。安全团队和应用团队也开始用同一种语言交流。Ian 介绍 Keycard 当天在 agentbaseline.org 发布了“安全软件工厂”参考架构，分三级：人驱动、工作流驱动、Agent 驱动。运行时授权是其中的核心组件，决定何时叫人、哪些 Agent 可以把工作交给哪些 Agent、能不能让一个 Agent 有生产权限去自动打补丁。他说现在生成软件从没这么容易，瓶颈卡在把它送进生产、确保它能工作上。

Allie 提到她和 Davis 在播客里聊过网络安全可以向机器人学学习：机器人抬手臂前不仅问“我被允许吗”，还看外部环境有没有变化。Davis 说今天组织里的授权多是单一的二元决定，未来要把意图和环境信息结合：从哪里访问、什么时间，甚至“这台服务器有高危漏洞、管理员的系统还没打补丁，该不该让他用 Firefox 访问”。他设想把这类上下文放到 OpenTelemetry 的 span 级别，看 trace 时既知道用户意图，也知道当时应用外部的环境。Ian 说审计日志必须放在 Agent 控制之外，和执行点必须在 Agent 的“大脑和双手”之外是同一个道理。他提到 Hugging Face 的事件：一方面利用了 Squid 代理里一个未知漏洞，更重要的是没有任何地方记录这个 Agent 在做什么。他认为 Agent 不需要更多监管，现有的责任法就够了：雇用 Agent 做事造成损害，责任在雇用它的人或组织，而要回答“是谁做的”，就需要防篡改的审计日志。

P(doom)

最后 Allie 问每人怎么看“AI 毁灭论”。Dick 自称圆桌上的悲观者：完全自主、不属于任何组织的 Agent 还是科幻；负责任的组织会建好管控；他担心的是管理混乱的组织里内部人员放出 Agent 作乱，更担心有意作恶的人拿到这些工具。他提到 Hugging Face 团队在 Black Hat 上的演讲是一次警示：没人想让坏事发生，坏事还是发生了；他预计会出现一些接近自然灾害规模的事件。Davis 说不给具体概率，但他相信工程师能解决问题。Ian 说他的看法最激进：概率趋近于零，大多数人的动机是让世界继续运转，责任框架还在，人总体是好的，而且 Agent 就是计算机，可以拔掉电源。他说出了问题造成损害，社会就会产生“抗体”；PocketOS 创始人丢了数据很不幸，但所有人都从中学到了东西。

09. Matt Ragone（Range 注册理财规划师）：让理财规划师自己写 Agent

直播位置 2:59:31–3:09:20 · 英文原题 We Let Our Financial Planners Write the Agents

Matt Ragone 说自己不是工程师，是注册理财规划师（CFP），每天和客户谈现金流、税务、保险、退休和遗产规划，同时负责 Range 规划团队的 AI 推广。Range 是一家一站式财富管理公司。他说多数 Agent 演讲来自搭平台的人，他是接过平台的那一方。他们的产出是给真实客户的财务建议，审核这一步不能省，所以他讲的是一种方法，不是推销。

瓶颈从来不是打字速度

他们一开始和大家一样把 AI 当聊天机器人：写好客户消息贴进去，让它改得清楚友好一点，省几分钟，但所有工作还是自己手动做，只是快一点。后来他们意识到，规划师的限制是同一时间只能在一个地方：在和一个客户通话，就不能同时做另一个客户的方案。现在的一天是这样的：他和一个客户通话时，Agent 在为另一个客户起草完整的现金流分析或保险分析；通话结束，他打开草稿，完整审核、调整，再把建议发给客户。他强调 Agent 不发送任何东西，每一条建议在客户看到前都经过规划师审核。变化在于初稿不再需要他坐在电脑前。

要做到这一点，需要两个条件：Agent 要在工作所在的地方工作，不用在独立的聊天窗口里来回复制粘贴；它要知道 Range 的做法，理财规划的一般做法模型已经知道，比如先看什么、总会标出什么、某条建议怎么措辞。他说这两者合起来就是一个 Skill：把公司做某项具体工作的方式写下来，让 Agent 能照着做。

五步：挑、教、打包、测试、上线

  1. 挑一个重复做的工作流。直觉会去挑最炫、最耗时、最复杂的，他建议别这样，挑每周都做、你清楚好结果长什么样、一眼能看出草稿好坏的，最好是不太复杂但手工量最大的。对 Range 来说是现金流分析和保险审查。判断不了输出，就没法测试，也没法信任。
  2. 给它看几个真实案例。拿几份以前交付过的客户案例，从头走一遍，边做边把判断说出来：不只说“下一步打开工资单”，还要说为什么打开、在找什么、什么情况会让你停下来问问题。他说这些讲述是整件事的核心，步骤容易写，判断才让它成为你们公司的工作，而不是泛泛的建议。
  3. 打包成 Skill。最重要的两样：开始前必须问的问题（它需要知道什么，什么该向我确认而不是猜），以及必须遵守的限制（它绝不自己做什么）。在他们这里，最大的限制是绝不直接发东西给客户，只起草，由规划师决定发送还是修改。只写步骤，得到的是一个自己乱跑的东西；写了问题和限制，才得到可以信任的东西。他说 Skill 像一份菜谱，Claude 学会后会按命令重复你的流程。
  4. 在真实案例上跑 5 到 10 次，再给别人看。这是大家最想跳过的一步。每次运行都会暴露 Skill 不知道的东西：一个边界情况，一个本该问的问题，一处说得很自信却是错的地方。修好、保存、再跑。5 到 10 次听起来多，但比把半成品发给团队里 15、20、100 个人再去收拾要省事。
  5. 上线时指定负责人和审核人。负责人保持它更新，流程会变，税法会变，3 月正确的 Skill 到 12 月可能就错了。审核人在团队依赖它之前检查，而且不能是作者本人，和做方案一样，不能自己给自己打分。

六个月的结果

六个月后，全公司有 24 个 Skill，17 个在规划部门。他没想到的是这种做法自发扩散到了销售、产品和市场部门，没有任何指令，大家看到规划师在做，就开始做自己的 Agent。所有 Skill 都由规划师、市场和销售人员编写和维护，不是开发者。领域专家来做以后，Skill 变得更具体：最懂保险的人做保险 Skill，最懂税法的人做税务 Skill；审核也自然发生，他们本来就互相审方案，现在也互相审 Skill。他说瓶颈已经转移了：模型能不能起草现金流分析已经不是问题，问题是谁把公司的做法写下来、谁在上线前测试、15 个人依赖它之后谁负责。如果你要把 Agent 推广到工程部门以外，很快会遇到这些问题。

10. Kim Maida（Keycard 创始 GTM 工程师、开发者关系负责人）：你的 Agent 就是一个“致命三要素”，以及怎么办

直播位置 3:09:30–3:34:50 · 英文原题 Your Agent Is a Lethal Trifecta (and What to Do About It)

开场演示：一个权限过大的值班 Agent

Kim Maida 一开始就放了演示：一个值班分诊 Agent，读写一个事件告警平台（演示里叫 Incidex），能解决的工单直接处理，处理不了的升级给早班团队。它对云托管 API、客户数据仓库（Snowflake）和账单数据库都有完全访问权。

  • 账单异常（一批客户昨晚被多扣款）：Agent 用 API 密钥读工单，用 Snowflake 密钥查客户数据，决定升级，写给早班的报告里直接贴了从数据仓库拉出的客户数据行，把个人身份信息发了出去。
  • 机房备用电源故障：判断是物理问题，直接升级，没调用其他服务。
  • 网站 TLS 证书即将过期：用 API 密钥调用云托管 API 的证书续期接口解决了，并留了报告。
  • 账单数据库坏了、付款失败：文档里的恢复步骤是删库再从快照恢复，Agent 用含管理员密码的数据库连接串照做了，然后让早班去确认快照恢复成功，它自己没有权限验证。她说权限过大的 Agent 删掉生产数据库，已经有好几家公司真实经历过。
  • 订单卡住、主服务器冻结：Agent 用静态 API 密钥调用重启接口，生产环境下线。
  • 三分之一访客访问失败：Agent 把服务从 4 个 pod 扩到 40 个，每小时多花 420 美元，然后“贴心地”给早班留言说明。

致命三要素

她说让 Agent 有用的能力通常包括：读取你拥有的数据（邮件、文档、CRM），自己做研究（搜网页、读文档、拉 GitHub issue），使用外部工具（MCP 服务器、API、SaaS 平台）。这三项合在一起就是 Simon Willison 所说的“致命三要素”（Lethal Trifecta）：能访问私有数据，会接触不可信内容（比如用户提交的工单、其他 Agent 的报告、外部文档），能对外通信。三者同时存在就给攻击者敞开了大门。她说这些事故的原因是人给了 Agent 远超所需的权限；强制人工审批只是把访问控制推给一个已经审批疲劳的用户，几十年来解决的人类访问管理问题又被推回到用户身上。去掉任何一项能力，Agent 都会变得没那么有用，所以要在保留三项的同时控制访问，缩小攻击面、控制影响范围。

现有方案为什么不够

  • OAuth 把访问绑定到一次授权：用户在授权时就同意了 Agent 可能用到的所有权限，而此时具体任务还不存在。授权宽，就有长期权限，对任何一个具体任务都过度；授权窄，Agent 能力就弱。单靠 OAuth 做不到按任务限定权限，一个积极的 Agent 在只该读的任务里也能写。
  • MCP 网关把执行绑定到一条路由：有可观测性、限流和一个统一的策略决策点，按请求运行策略、按用户授权，但网关自己持有长期凭据，Agent 获得的访问比任何单个任务都长。
  • 沙箱把执行绑定到一个进程：能控制影响范围，但有用的工作总要伸到沙箱外，一伸出去又是长期权限；也有不少 Agent 突破沙箱的故事。沙箱限制进程能做什么，但不管沙箱外谁被授权行动。

她说三者都用上，Agent 仍然拿不到一个只限于当前任务的运行时凭据。回到演示的问题：审计日志里看不出谁在用 API 密钥，凭据没有归属到用户或 Agent 身份；Agent 能用密钥的全部权限；而人工审批不能到处加，人也会犯错，很多 Agent 本来就自主运行。

令牌交换与安全令牌服务

她的方案从令牌交换（Token Exchange）开始，这是 2020 年发布的、扩展 OAuth 2 的现有标准。流程如下：

  1. 先确认用户是谁。授权服务器（Google、Okta、Auth0 等身份提供商都有）验证身份并签发令牌。用户登录后，授权服务器请用户同意把自己部分权限（scope）委托给 Agent，这是第一次收窄权限。这一步已经比演示好：知道用户是谁、能访问什么。
  2. Agent 是一个调用 LLM 的控制循环。通常在 Agent 和资源之间有 MCP 服务器提供定义好的工具，MCP 客户端把模型提出的工具调用分发给服务器。演示里的 Agent 直接拿 API 密钥、数据库连接串这类长期静态凭据访问资源，现在给它加一个 MCP 服务器，既提供工具，也负责代理对资源的访问。Agent 运行时可以是 Claude Code 这样的 CLI，也可以是用 Agent SDK 写的自定义应用。
  3. 已认证用户的令牌成为“主体令牌”（Subject Token），标识 Agent 代表谁行动。令牌交换需要一个能执行代码的 OAuth 客户端，可以是 MCP 客户端和第三方 MCP 服务器之间的网关，也可以是你的自定义应用。
  4. 模型提出一个工具调用时，运行时用自己的应用凭据或工作负载身份向安全令牌服务（Security Token Service，STS，专门做令牌交换的授权服务器）认证，同时带上主体令牌，请求只为这一次工具调用访问 MCP 服务器。这时三样信息齐了：哪个 Agent 在请求，代表哪个用户，用户给了它什么级别的权限。
  5. STS 按治理策略评估：请求访问什么资源、Agent 身份、用户身份。通过就签发访问令牌，保留用户主体，加上执行交换的应用（这里是值班 Agent）。这个令牌几分钟内过期，不应存储。MCP 服务器验证令牌、授权调用；若需要访问下游资源，再拿这个令牌去 STS 换一个只限于这次调用的资源令牌，委托链继续延长，所有活动都能追溯。MCP 服务器用完立即丢弃令牌。

她说策略只是上限，Agent 在策略允许范围内也可能做出你没想要的事。这就引出基于意图的授权（Intent-Based Authorization，IBA）：在 Agent 行动之前检查你的本意。它还不是定稿的标准，仍在征集提案，她讲的是 Keycard 的实现方式：网关作为策略执行点；用户发出提示后，Agent 提出一个 Mission，包括目标、允许的动作和限制。比如“分诊事件 2294”意味着读这张工单、总结或升级，不读其他工单、不用其他服务，这类低风险任务可以按管理员策略自动批准；而“处理用量激增”会增加“扩容一次”的权限，不能用别的工具，这时 Mission 要交给用户审核。批准后 STS 给 Mission 一个 ID，每次工具调用都带着它，网关用这个 ID 问 STS 这次调用是否符合任务，符合才去做令牌交换。

同一个演示，加上 STS 之后

第二次演示用的是基于任务的策略治理，还不是 IBA（她说当月晚些时候的 Agent Con 上会有 IBA 演示）。她先用 Google 登录值班应用，再登录 Incidex，同意 Agent 代表她升级事件、发备注和摘要、读队列；再登录云托管平台，同意部分能力。工单还是那些，Agent 大概还会照原来的方式尝试，但每个请求都要经过 STS 和策略评估：

  • 账单异常：Agent 想查客户数据仓库，策略不给它签发凭据，因为客户个人信息不该进入 Agent 上下文或工单。它在没有客户数据的情况下升级了。
  • 证书过期：这在权限内，STS 批准，审计日志里能看到是值班 Agent 在为续期请求 prod-infra MCP 服务器的工具令牌，然后 MCP 服务器再请求云托管服务的访问。
  • 账单数据库：Agent 得出同样的结论（删库恢复），但策略禁止 Agent 删除生产数据库，必须人手动做，审计日志显示 STS 拒绝了这次交换。
  • 主服务器冻结：Agent 想重启，先向她请求批准，她点了批准，但还是被策略拦下，因为她本人的角色没有这个权限。Agent 代表她行动，她做不了的事 Agent 也做不了。
  • 三分之一访客失败：Agent 申请扩容并说明成本，她批准了，她的角色有此权限，扩容执行，工单解决。

她总结：用户和 Agent 的身份沿整条链路可知；Agent 对 MCP 服务器和下游资源的访问是按任务限定、短时有效的；人工审批背后有真正的访问控制和策略支撑；关键能力都保留了。令牌交换是公开的开放标准，研究充分，任何人都能实现，能和现有策略引擎、标准身份提供商、网关、沙箱、现成或自定义的 Agent、CLI、MCP 服务器、软件工厂、Agent 对 Agent 的跨应用访问互通。

11. Branislav Brzak（Stealthium 安全研究员）：共用 GPU 的邻居能“听见”你的模型

直播位置 3:35:00–3:48:10 · 英文原题 Your GPU Neighbor Can Hear Your Model

这是一段录制好的演讲。讲者是 Stealthium 的网络安全研究员（字幕里名字听不清，姓名依据章节），研究方向是底层 GPU 安全。Stealthium 为 AI 系统运行的环境提供安全和可观测性。他讲的是：如果你在云上和其他租户共用一块 GPU 运行模型，旁边的人只靠计时就能知道你在跑什么模型、生成多快、正在做什么类型的工作，不需要 root 权限，也不需要传统意义上的漏洞利用。这类攻击叫侧信道（Side Channel）攻击，指不直接读数据，只从时间、功耗等副产物里推断信息。

能知道什么，不能知道什么

演示视频左边是受害方在跑 Qwen3（字幕作 “quentry”），右边是攻击方的面板。他列出的结果：模型的架构和层数，准确率 97%；解码速度，准确率 99.3%；什么时候忙、生成了多少 token、回答多长；正在做哪类工作（代码、散文、JSON 还是检索）。拿不到的是实际的提示词、回答和内容，只有时间信息。实验都在真实的 H100 上、跑真实的 LLM。

MIG 隔离漏了什么

NVIDIA 的 GPU 隔离靠 MIG（Multi-Instance GPU，把一块 GPU 切成多个硬件隔离的实例）。每个 MIG 切片有自己的计算单元和显存。他们的例子里，被攻击的 LLM 跑在 3 个计算单元、40 GB 显存的切片上，攻击程序只用 1 个计算单元、10 GB 显存。被隔离的有计算单元、显存容量、带宽配额和故障；L2 缓存也按实例分区，不会跨实例驱逐。泄漏点是内存屏障（Memory Barrier）：它是整块 GPU 范围的，一个实例发出的屏障会作用到卡上所有 L2 分区。所以一个租户忙的时候，其他租户的读操作会稍微变慢。

攻击程序只读自己的一小块内存、只给自己的读操作计时，从不碰受害方的内存，每 5 微秒重复一次。他说这个原语和 MIG 内存屏障泄漏不是他们发现的，来自另一组研究者的工作（字幕里像是叫 “Behind Bars”），他们在其基础上扩展。肉眼看空闲和在跑 LLM 时的延迟几乎没区别，中位延迟只高 3 微秒，但这就够了。

从时间曲线里读出模型

  • 解码速度：攻击方延迟曲线的频谱上，基频约 81 赫兹（字幕作 “.81 hertz”，含义不完全清楚），就是每秒 token 数，加上谐波。单个 token 在时域里有 39 个“鼓包”，其中一部分是层的调用，其余是层之间的处理。只靠计时就能准确恢复 token 速率。
  • 只靠速度不够：Qwen3 8B 和 Llama 3 8B 的 token 速率只差 1.6%。所以要数层数。他们把同样的“折叠平均”方法按模型做一次，得到的鼓包数几乎正好是整数，22 条 trace 离整数的平均距离只有 0.028；如果只是固定的硬件伪影除以不同速率，会得到小数。每个计数等于模型层数加上一到三个额外的峰。
  • 这不是训练出来的机器学习分类器：没有训练集、标签和配置，不到 30 行代码。方法是对 16 到 48 层的每个候选深度，测量其预期特征在真实 trace 里有多强，选最好的那个。对 Qwen3 8B，36 层以明显优势胜出。因为是拟合检验而非查表，它对没见过的模型也有效，包括闭源或未发布的模型。分类器还会输出置信度，测试中只有两个置信度最低的答案是错的。
  • 同一基座的微调和蒸馏模型也能区分：Llama 3 8B、Llama 3.1 8B 和 DeepSeek 的 R1 Distill Llama 8B 都是 32 层，每层计时只有很小的差异，分类器仍能分开。

它正在写什么

更深一层的问题是模型此刻在做什么，他们看四类：散文、代码、JSON、检索。每半秒基于过去 5 秒的计时做一次判断，40 次判断里对了 31 次，4 个完整回复靠多数投票都判断正确。前提是开启了推测解码（Speculative Decoding，先用小模型起草几个 token、大模型一次验证的加速技术），这在 vLLM 里要手动开启，不是默认。原理是文本越可预测，每步被接受的草稿 token 越多，步长时间随之变化。他们测了 11 种配置（稠密和混合专家、BF16 和 FP8），都出现了同样的特征，只是强度差别很大：gpt-oss-20b 上差异达 70.2%，GLM 的一个模型上只有 0.9%；11 种里散文都是最快的，而随机猜只有四分之一的概率猜中。

不在同一块芯片上也行：NVLink

MIG 攻击需要和受害方在同一块物理芯片上。另一种设置是 8 卡 H100 服务器，通过 NVSwitch 互联，受害方用张量并行跑在 GPU 0 和 1 上，攻击方只要在同一台服务器的任何其他 GPU 上，比如 GPU 2。GPU 之间的对等访问是正常功能，多卡任务本来就这样工作；而且 MIG 和张量并行不能在同一设备上共存，所以这是另一批部署场景。探针在 GPU 2 上对 GPU 0 上的内存做指针追逐，给每一跳计时：空闲时一跳约 890 纳秒，受害方开始工作后升到 300 微秒左右，三段半秒的捕获里肉眼就能数出 token。这个距离上层数信号淹没在噪声里，剩下的主要是节奏。五个模型在相同设置下识别准确率 79.2%，失败的地方正在预料之中：Llama 3.1 8B 和 R1 Distill 8B 解码频率只差 3 赫兹，混在一起。他说信噪比更差不等于安全，79% 对比 20% 的随机基线仍然是真实的指纹。

防御

他说他们自己的产品开箱就检测到了这个攻击：它监控每块 GPU 上的每次 kernel 启动，分析可疑负载并走完整告警流程。这个攻击的特点是同一个 kernel 重复启动约 3000 次，反复访问同样的 40 KB 内存，整个过程只回传约 1 KB 数据给 CPU，因为计时本身就是有效载荷。从开始到告警不到 600 毫秒，受害方的回复还不到 50 个 token。三条建议：放置位置是运营方能控制的，不要把不可信租户的 MIG 切片放在敏感模型旁边；知道取舍，MIG 不支持对等通信，也就不能做张量并行，而通过 NVLink 分片则把泄漏限制在节奏信息，不含层数；监控 GPU 本身，确认宿主基础设施在主动检查没有恶意负载。

12. Mahmoud Abdelwahab（Railway）：别再做粗糙的一次生成 SaaS 替代品了

这也是录制的演讲，他坐在苏格兰爱丁堡户外的一张长椅上录的（他给这张长椅打了 10 分）。他说“SaaS 已死”早就不算新观点了，让 Agent 自己做就行；但他觉得少有人提一点：一次生成（One-Shot）能跑的软件，和自己真会每天用、打磨过、用着舒服的软件之间，差距很大。他为 Railway 的市场部门替换了一批 SaaS，做了一个一体化内部工具：管理官网、更新日志和博客的内容，发邮件，同时发布到所有社交平台，管理网站媒体，一个和外部创作者合作用的迷你 CRM，任务跟踪、发布计划、日历，还有评论和实时协同编辑，全部用 Agent 构建，跑在 Railway 上，自动部署。他说 GPT-6 出来时他感到了突破。他也声明录制时间是 2026 年秋天（10 月），这些看法可能几个月后就变。

技术栈其实重要

很多人说用什么语言和框架无所谓，让 Agent 做就行。他部分同意，但他发现给 Agent 一个抽象清晰的代码库，加新功能时结果会和已有部分一致得多，因为 Agent 不用每次重新发明轮子或引入新模式，照着现有模式做就行。具体选什么不太重要，只要结构好。他现在的选择是：Web 端用 TanStack 系列库；内容相关的用 Payload CMS，他比较了很多 CMS，认为没必要自己从零写。

Agent 默认不会做的交互细节

他说用自己喜欢的 SaaS 时很多细节注意不到，自己复刻时才发现每个流程背后有多少心思。用服务端渲染加表单提交当然能实现“发邮件”“发布内容”，但每天都用的工具不该是那种感觉。他列出 Agent 通常不会主动做、需要你明确要求的模式：

  • 自动保存：文档编辑器里不必手动点保存，后台非阻塞地保存；再加一层，有未保存修改时阻止关闭浏览器标签页。更进一步是实时协同编辑，他说 Agent 做起来毫不费力，讨论和审查方案之后，“只花了 7 亿 token”就有了实时协同。
  • 乐观更新（Optimistic Update）：用户操作后先显示成功状态，后台同步，失败了再回滚并提示，界面会感觉快得多。不是所有操作都该这样，有些场景需要等待确认。可以直接让 Agent 列出哪些地方适合做乐观更新。
  • 撤销：Agent 实现删除通常是一个删除按钮加确认对话框。更好的体验是点删除后立即从界面上移除，给用户几秒钟撤销，没撤销再真正执行。
  • 归档：允许归档和取消归档，用户想从界面或搜索结果里隐藏某样东西时不必删除它。
  • URL 状态：筛选、排序等条件在合适时存进 URL，这样把链接发给同事，对方看到的就是你想让他看的。
  • 无限滚动：不想一直点“加载更多”或“下一页”。
  • 以现有页面为参照：明确让 Agent 参照已有页面的 UI、数据获取方式和整体结构，“好”只需定义一次，后面复用。他承认有时说了 Agent 也不照做，但总体成功率更高，界面也更一致，同类的增删改查列表应该几乎一模一样。

把偏好打包成 Skill，最后一定要验证

他说有偏好就打包成 Agent Skill，Agent 构建时会照着做。他常用三个：两个设计工程类的 Skill，一个改进 UI、排版、布局和错误信息，一个改进动画等细节；还有 Railway 自己的 Agent Skill，他们所有内部工具（存储桶、数据库、应用本身、实时服务器）都跑在 Railway 上，给 Agent 这个 Skill 它就能部署一切。

他认为最重要的一步是验证。Agent 通常会说“功能做好了，构建通过，测试通过”，但实际试用时体验可能完全是坏的。有了验证循环以后差别很大，能看到 Agent 说“我做了，试了，失败了，我来修”，一直做到真正测完。计算机使用（Computer Use，模型直接操作图形界面）变得很好用以后，他每次加功能都在最后加一句：要真正运行基础设施，端到端验证这个功能能用。他希望听众也能做自己公司的“SaaS 层”。

13. Hrishi Olickel（Southbridge 创始人）：即时本体（Just-in-Time Ontologies）

直播位置 4:02:28–4:23:40 · 英文原题 Just-in-Time Ontologies

这也是录制的演讲。他从 DuckDB 的 Hannes 的一篇文章说起：我们是不是浪费了十年去追逐分布式架构，而那套架构的前提是计算和存储又慢又贵。他说每个时代的能力决定架构和工具，而工具总是落后：先让计算比存储便宜，再普及给所有人，再变快，每次架构都大变。今天所有数据基础设施都建立在“数据转换很昂贵”的假设上。他认为数据转换的最后一个瓶颈，通用智能或者说判断力，已经被解决，而且沿着整条帕累托前沿（Pareto Frontier，在成本、速度、准确率之间不能同时改进的那组最优方案；字幕作 burrito frontier）随取随用。

开头的例子：一个叫 Jev 的新决策模型（字幕拼写不一，有时作 Jeff）发布时，他们正在做俄亥俄州竞选资金记录的实体解析（Entity Resolution，判断不同记录是否指同一个人、公司或委员会），预计花费约 1 万美元。他们的系统接入这个新模型，找到它适合的位置，测试了十几种方案并集成进去，首次调用后 10 天，就以不到 800 美元拿到了俄亥俄全部捐款人案例的最终标注结果。

没有统一的模式

他说本体是企业版的思维导图，是个吸人的泥潭，他两年前创办 Southbridge 时也讲过“单一的通用模式”。通常的说法是迁移和本体失败是因为缺乏认同，做一半就弃了，这都对，但不是主要原因。就算能瞬间把所有信息迁进一个“超级模式”，也没有这种超级模式，实际上有四种模式。他用“请你记下温度”举例：

  • 来源模式：你手边有什么，手机给的地区温度、桌上不太准但更近的传感器、手表，甚至你有没有耐心照做。
  • 存储模式：你能记下的有限，不可能写下设备固件，也没法精确到秒。
  • 决策模式：我为什么要你记温度？想知道你什么时候舒适，就要你一天里多次测、而且必须是你测；做天气迁移图，就不在乎谁测，但很在乎精确位置、时间和设备；决定在哪里装精密设备，你本人反倒成了要抵消掉的变量。
  • 第四种是模型自带的先验，后面再讲。

问题是四种模式只有在做决定那一刻才同时可知。几乎所有企业里记录下来的数据都不知道将来会被用来做什么。比如“客户”这个每个本体里的第一个框：对账单部门是付钱的人，对客服是打电话来的人，对合规是公司要为之负责的人。只有决定明确了（要不要给这笔订单退款？能不能给这个账户更多信用额度？），需要知道什么、到什么程度才清楚。所以没有脱离问题的“客户”概念。把记录时的上下文和决策的上下文合并，就是数据转换，需要判断力；在决策空间已知时再做这种合并，就是他说的“即时本体”。

三种工作形态，三种模型角色

他说他们是一群“把智能嵌进流水线”的偏执者，流水线能反复运行、自己在成本和速度上成熟。数据工作分三种：写一次跑一次（一次性的大任务，比如合并数据集、回答一个问题）；写很多跑一次（大型迁移，很多子任务为一次搬迁服务，单独验证再互相核对）；写很多跑很多（最常见，持续维护的可重复流水线，他们从基准设计、跟踪、编码到给想看的电影做字幕，都放进了这类系统）。两年里他们从让早期 GPT-3.5 Turbo 级模型在医疗、矿业研究等任务上可靠，到构建开源的数据工作 Harness Hankweave（字幕作 Hank wave），再到让模型在 TB 级数据上协作。

他讲了上一份工作的故事：最常听到的问题是“能不能用数据来做这个决定”。平台上有几千艘船时这没问题，只有 50 个用户时也这么问，就有问题了，对 50 个用户做 A/B 测试的麻烦在于你一定会得到一个结果，一旦有了数字，它就会为某个结论辩护，所以唯一的办法是根本不产生这个数字。今天更糟，交互式 Agent 总会给你答案，又快又自信，聊天里的一个瞬间可能变成生产环境里一直潜伏的噩梦。

他说原因在于数据工作里的智能占三个角色，编码 Agent 把它们混在一个上下文窗口里：

  • 设计流水线：拆解问题、写早期规格、批准花费。适合慢一点、思考更多的大模型，能看清各个角度、读懂文档、事先预测结果（他说 Opus 或更高）。
  • 在流水线里干活：读 PDF、写数据库、检查结果。要的是相反的：更便宜、更快、更专门、擅长遵循指令、缺陷已知的可重复工人。他举切叶蚁为例，一个群落有四种体型的工蚁。新出现的“决策模型”就属于这一层，为快速接触信息而生，部署在大型任务的底层。
  • 爬山者或冲浪者：能拿到第一次运行结果后自我优化的模型。给它正确的知识、指令和稳定的立足点，它能尝试新方法、调节预算控制成本、快速调试、做笔记，找到最优解，他们称之为“帕累托冲浪”。

俄亥俄案例：钱花在哪里

他们在小的开发集上先试了三种设计：便宜的推理模型单独做；Jev 加一个推理模型处理它没把握的情况；推理模型提出答案、Jev 检查，在约 200 个留出的家庭样本上比较。便宜推理模型单独做和 Fable（字幕中的一个前沿模型名）效果一样，成本约 2%。Jev 把核心答案做对了，但漏了 9 个同户关联，因为它对这些全都自信地说了“否”。他们没改模型和阈值，只改写了问题：同户问题现在说明了什么算足够证据，Jev 在 13 个开发问题上从全部“否”变成“是”。扩展到全州时做了十几轮这样的修正，每轮修正一个定义：委员会是什么，申报人指什么，两个人住同一地址意味着什么。俄亥俄的 23,317 个案例每个都有一个标签，写明答案依据什么、核查到什么程度。

全州任务总共花了 795 美元，预算是事先定的 800 美元。检查的花费约是做的四倍：二次意见、解决分歧和审计花了约 545 美元，第一遍答案只花了约 128 美元（字幕数字有些含糊）。之前预计这项工作要 1 万美元；现在流水线已经建好验证过，他们预计下一个州的审计预算接近零。他说最惊人的是，他们的 Agent（先跑在 Astra 上，后来跑在 Opus 上）大部分方法是自己一步步发现的：构建系统、运行、调试、尝试新方法，跑了 10 天，试了十几种架构，Hankweave 运行 4000 多次，调用 Jev 9 万次，几乎试遍了帕累托前沿上的模型，内部模型共处理约 60 亿 token。每次迭代都是一个版本受控的运行，容易回滚、理解、调试和评审。学到的东西写回了他们的 Agentic 模式库。

模型的先验

模型能原生做到这些吗？他说还不能，缺四样东西。另外有一件事不会随模型变大而消失：先验（Prior）。模型和人一样，带着自己对世界“应该是什么样”的信念进入任务，这就是第四种模式。他说更大的模型在某种程度上更糟，有时会更强硬地坚持和辩护自己的信念。他们遇到的例子：

  • 一条流水线找下划线拼写的 “in_kind”，文件里是大写 I 加连字符，于是 15,658 笔实物捐赠被当成普通现金，没人复查；贷款还款也以同样方式消失了。
  • 另一条试了四种日期格式，文件用的是第五种，99.4% 的交易日期变成空值，但每个行数和金额总和都对得上，Agent 就继续了。
  • 好几次运行发现贷款金额是负数，认为符号是多余的，存了绝对值，净额 78.4 万美元变成了 530 万美元的债务，最后还被多个模型验证通过。

他说这正在成为各公司数据工作里最大的一类错误。有时只要不靠感觉、认真检查结果、用人的直觉就能解决，这时你做的其实是用自己的先验和模型的先验求交集：懂竞选资金的人一看就会发现实物捐赠不见了，他们就是这么发现的。但人贵、慢、会拖进度、比模型还不确定，而且讨厌被打断。跨模型的先验交集也能走得很远：在 200 个留出家庭上，Jev 和 Luna（另一个模型）有 194 个答案一致，一致的答案没有一个错，所有错误都在它们意见不同的 6 个里。不同家族的模型分歧更多、先验更不同；例外是在同一公司之外蒸馏出来的模型（他没说是谁）。这样能把错误面缩小到一小类 LLM 作为一个“物种”共有的问题，比如一个基准里四个模型家族给出完全相同的总数，因为它们共享一个答案标准里没有的符号约定。到这一步只能列出这些问题、逐个提防、针对性解决。

自我优化缺的四样东西

  1. 稳定的部署面：他们用 Hankweave，把 Claude Code、Pi 这类快速变化的 Agent 运行时包起来，暴露一致且经过测试的日志和 API 接口，内置检查点、回滚和预算强制。他说对无界面的数据工作，Hankweave 是最老、最稳、最开放的，并放出了相应的 Skill。
  2. 限定实验范围的方法：不能控制成本、时间和访问，就没法测试。
  3. 知识和方法论：新一类模型能把他们两年部署积累的 Agentic 模式、调试技巧、提示方法用到复杂问题上，有合适的抽象层就能用很省 token 的方式表达。
  4. 失败面（Failure Surface），他说最重要：阿基米德说给我一个支点就能撬动地球，他们还没遇到给了稳定的技术栈和失败面却迭代不出来的问题。这一项最难用语言、工具和指令表达，当前最好的模型也只是勉强能做到。

整个流程分六步：先写规格并拆分（俄亥俄案例里，把约 80 万行拆成约 20 万个小案例，每个案例再拆成有类型的问题）；确定失败面（用好模型在一小片数据上跑并部分人工核查，建立基线；其他场景里也用过自动失败检测、模式检查、行为度量），一定要在开始前定义；跑最小的、有边界的试点测试架构；有效后把检查移进“rig”，即在有边界的工作片段（他们叫 codon）之间运行的代码，codon 可复用、独立循环、验证后按顺序排列；最后把可用的流水线部署到生产，让它慢慢成熟。冲浪发生在中间：找到一个结果可靠的架构作基线，换更快更便宜的模型和部件，和已知的中间结果比对，每次收紧成功标准，看着前沿移动。在这样的系统里，本体作为智能和结果之间的中间产物存在，需要时构建，连同凭据一起保存，下次需要同样东西时复用，这是“即时本体”的另一半含义。他最后说要道个歉：答案是不存在通用的本体，从来没有；好消息是，只要能标注并保留上下文，每个本体和模式都有效。

14. Karthic Rao（Perpetual CTO）：为金融、财富管理和保险构建可靠又聪明的工作流

直播位置 4:23:48–4:39:20 · 英文原题 Building Reliable, yet Smart Workflows for Finance, Wealth and Insurance

这是录制的演讲。Perpetual 是一家财富管理整合公司（Rollup），收购传统财富管理公司，用 AI 提高它们的产能和收入。他说在受监管领域，工作流要可靠到满足监管标准，又要聪明到能应付现实世界；可靠和智能并不对立，边界画在哪里由你决定，这就是这场演讲的主题。

四个事实

金融和财富管理的工作流有四个特点，都把架构推向同一个方向：流程复杂，需要随过程展开在运行时决定策略，没法提前写好每条路径；数据敏感，需要有办法把工作流完全迁到私有部署的模型上；在强监管行业里违反政策不是一个 bug 报告，后果严重；所以执行必须高度可靠和确定，只在真正需要运行时判断的地方注入智能，其余尽量少依赖 LLM。他说大实验室告诉开发者的多是怎样烧更多 token，在受监管行业里“token 最大化”是错误目标。这些任务接近封闭领域，可以事先列出来做成一个大型状态机，只需要一点智能来导航：大多数步骤沿下一条边走，只有少数判断点由模型选分支。

“帮 Harper 先生填 W-9”

顾问对助理说一句话：帮 Harper 先生填 IRS W-9 表（美国纳税人身份证明表）。他展示了人执行时实际发生的事：

  • 助理从公司记录或 IRS 网站找到表格，在记录系统（System of Record）里查 Harper，发现有三个 Harper 家庭，于是打电话问顾问是哪一个。一行任务的第一分钟就有查找、歧义和人工介入。
  • 填表听起来是数据录入，其实每张表都是一个小程序：W-9 先决定纳税人是谁（本人，还是被忽略实体的所有者），外国人到这里就要改填 W-8；然后看税务身份，第 3a 行只能勾一个框，LLC 还要加字母，这又决定第 1 行和第 2 行填什么名字；然后是用 SSN 还是 EIN，只能二选一，必须取自经过核实的文件，不能凭记忆；豁免代码只适用于部分实体，S 公司永远不适用；最后是谁在伪证罚则下签字。每个答案都会改变下一个问题，而参与者只会碰到三种关口：一个问题、一份要收集的文件、一个签名。
  • 开始填时发现记录系统缺三个值，查了文件和系统还是没有，于是给客户发邮件要这三个值。任务现在取决于公司外的人和他们的时间。客户两天没回，助理跟进，并在每日站会上告诉顾问；客户只回了两个，再跟进第三个；三个都到齐后填完表，把新信息连同获取经过写回记录系统。他说在这个行业，你怎么知道一个值和这个值本身一样重要。
  • 填好后发电子签名，客户一两天不签就再提醒，签完归档、发确认，并在第二天站会上更新顾问。

一句话变成了持续几天、跨多个系统、等两个人、多次回环的流程，里面有要消除的歧义、要收集的数据、以天计的审批等待、跟进循环和最后的证据链。现有的工作流自动化工具很少能处理这种复杂度：固定流程图在第一个“哪个 Harper”就会断；一个即兴发挥的 Agent 又是合规团队没法签字认可的。

边界画在哪里

流行的看法是给更多自主、等更好的模型；受监管公司的本能反应正相反，少自主、多规则、写死每条路径。他说两者都选错了维度，可靠性来自你在“必须确定的部分”和“真正需要判断的部分”之间放边界的位置。他的原则是：确定性系统管控制流、证据和副作用，也就是接下来运行什么、我们知道什么以及怎么知道的、以及任何改变外部世界的动作（写一条记录、发一封邮件、提交一张表）；智能负责解释和判断，比如读懂含糊的指令、决定是哪个 Harper、理解客户的回复。模型回答一个有类型的问题，确定性系统决定拿这个答案做什么。两者可以递归：一次判断可以开启一个新的、更小的计划，再次编译、设关口、确定执行。

他们的工作流引擎

  • 规划器（Planner）是一次模型调用，唯一任务是翻译：输出一个有类型的语义图，包含意图、实体、事实、产物、事件和约束，每个节点都指回请求里对应的原话，并列出发现的歧义。
  • 编译器从不调用模型，分 11 个确定性阶段把语义图变成执行 DAG（有向无环图），或者“失败即关闭”（Fail Closed）。只有三种结论：有效、需要澄清、拒绝。“哪个 Harper”会作为问题返回，不会被猜。编译后的计划不可修改，用哈希固定。
  • 编译器按“语法”检查计划，也就是公司被允许做的事的词汇表：42 个有类型的动作契约，覆盖表单、文件、邮件、电子签名、日历和人工步骤。规划器要求的每个动作都必须匹配一个契约，不在语法里或接错了就拒绝，大约有 40 种失败即关闭的情形，从图里有环到不支持的动作。同一份契约摘要固定在引擎、后端和 UI 里，三者对每个动作的含义一致。他说这就是封闭领域的好处：模型只能要求公司已经知道怎样安全执行的事。
  • W-9 追收计划的样子：给客户发表格，等回来，检查，归档。执行前先由人批准整个计划。起草邮件是模型调用，可以；发送是一个动作关口，那封邮件被人批准前什么都不会离开公司。等回复，再由一个评审模型读回复，核实返回的表格，匹配就在另一个关口后归档，不匹配就跟进。图里的虚线步骤（渲染 PDF、附件、评审回复）规划器没要，是契约要求、语法自动加上的。
  • 在人工流程里占大头的等待、审批和跟进，在这里是计划里的节点，不是提示词。回复等待默认 72 小时，显式期限可以是 1 分钟到 30 天，到期由规则决定怎么办，不由模型决定。一次批准覆盖整个计划，每个外部动作（发邮件、发签名请求）还有自己的关口；批准绑定到确切载荷的哈希，发送前再检查一次。
  • 客户只回了部分内容，评审模型标为“部分”，这个判断是临时的，步骤保持阻塞直到人确认；确认后跟进作为一个新的子计划运行，已批准的父计划不变，最多五轮。
  • 计划批准后由状态机运行，它选择每一步、记录每个结果。需要判断时做一次固定模式（Schema）的模型调用：写邮件、评审回复、找缺失值、提取字段、核实文件。答案以类型化形式返回，状态机决定下一步。副作用有自己的生命周期：准备、发送中、成功，或在外部没有干净回应时进入“结果未知”和人工审核。没有自动重试。聊天消息可以批准一个步骤或回答一个问题，但不能修改已批准的计划。他的说法是：模型掌舵，从不驾驶。

95% 的判断不需要前沿模型

规划器之外剩给模型的判断都很小、有类型：这个回复完整吗？这个文件匹配吗？哪个字段是哪个？快速的小模型（Flash 级）就能处理。在一次示意的运行里，20 个决定中 19 个给 Flash 级，1 个给前沿模型，所以他们按“工作流里约 95% 的模型决定永远不需要前沿模型”来设计，Flash 级可以跑在自己控制的硬件上。这 5% 也不是永久成本：每个判断都有类型并被记录，临时判断由人确认或否决，于是每个前沿决定天然产生 Eval 级别的真实训练数据，可以用来后训练 Flash 级模型。记录和 Eval 已经有了，训练循环是下一步，这样前沿份额会一版一版缩小。因为每次模型调用都小、有类型、经模式检查，把它指向私有部署的模型只是改配置，改一行，返回同样的答案，所以约 95% 本地推理是架构的自然结果，合规风险可以作为工程路线图逐版下降。他最后说：别问系统该多一点还是少一点自主，问边界在哪里。

16. Akshat Bubna（Modal CTO）：好的 Agent 从好的基础设施开始

直播位置 4:42:11–4:56:40 · 英文原题 Great Agents Start with Great Infrastructure

Akshat Bubna 是 Modal 的 CTO。他说既然听众偏金融，就从一个场景讲起：如果电子表格里的每个单元格都由一个 Agent 支撑会怎样？基金分析师想对投资组合里的每家公司做复杂分析，过去要几天：连接每家公司的数据源，为每家跑一段 Python。Modal 的客户 Hebbia 就做了这样的产品，表格里的一次查询，每个单元格背后是一个不同的 Agent。

这种产品背后的架构

每个 Agent 背后是一个 Modal 沙箱（Sandbox，运行不可信代码的安全隔离环境）。过去一个沙箱对应一个容器或 microVM，现在 Modal 支持在一个沙箱里运行多个容器或 microVM，这类场景需要这样做：Harness（Agent 循环，负责调模型 API、执行工具调用、循环）要和真正执行工具调用的地方分开，出于安全和隔离等原因，所以沙箱里有主容器和一个 sidecar（边车容器）。还需要共享存储，让 Agent 之间能交流，怎么划分由你定，比如表格的每一行共用一个卷，同一行的 Agent 可以协作；主容器和 sidecar 有时也要共享存储。最后，一切都要启动得很快：一次查询要启动上千个 Agent，结束后再全部收掉。

他介绍 Modal 是一个为 AI 应用构建的原语平台，从零自建了文件系统、调度和运行时，用于推理（包括 LLM 推理）、沙箱、训练和批处理函数。这次重点讲沙箱这个原语的演变。

Agent 需要的原语

  • 工作空间：Ramp 的内部编码 Agent Ramp Inspect，他说现在几乎推送了 Ramp 的每一个 PR；编码 Agent 需要代码仓库、依赖和开发服务都在同一个工作空间里。另一个例子是会计领域的 Basis：文件到达，触发 Agent 处理，然后等会计回复，可能要很多天，状态要长期保存。
  • 弹性资源：每个沙箱的资源使用曲线有些规律但起伏很大，预先分配不合理，需要在沙箱需要时可靠地拿到资源，只为使用时段付费。Agent 还越来越多地做“云端科学计算”：在 CPU 上预处理数据、启动 GPU 跑科学模型，交给 Modal 沙箱，他提到给 Agent 沙箱去做自动研究、爬山优化的例子。这一段字幕有重复和缺失，细节不清。
  • 共享文件系统：Agent 和子 Agent、和人越来越多地协作同一份东西，需要快速、一致、易于理解的文件系统，Modal Volumes 在做这件事。自我改进也一样：Agent 保存和更新记忆，在后台运行任务定期整理记忆（现在被叫作 dreaming），这些看起来也就是文件系统里的文件。
  • 网络控制：Agent 可能把敏感数据泄露到某个德国论坛上，你需要控制哪些 IP 能和它通信、怎样认证、能访问哪些域名；凭据要以 Agent 看不到的方式注入，防止它外泄。他们发现按域名白名单不够，很多用户想精确控制到路径，比如在 Datadog 或 GitHub 上能做哪些具体操作。用户开始自己写轻量代理放在 sidecar 里，定义自定义规则，Ramp 就这样用得很成功。
  • 可观测性：Agent 做训练时，训练失败了它要能轻松看日志、分析原因、换参数再试；训练进行中要能看指标、GPU 利用率有没有卡住、预算有没有超。这些对人重要，现在 Agent 驱动的计算越来越多，他们花很多时间把这些暴露给 Agent 本身。

别 vibe code 一个沙箱平台

他说不要让 Agent 随手生成一个沙箱平台，三个原因：可靠性，即使有 AI，也很难推理系统在尾部事件中崩溃时的反馈环，一些每天用的网站还是经常宕机；安全，谁来持续推理安全边界并确保在快速变化中守得住；规模，他们写过一篇如何扩展到一百万个沙箱的博客，需要大量系统设计。他给出的数据：快照每周 2000 万个，每天处理约 8 PB 快照数据，用户每周创建约 260 万个卷，都在快速增长。一个个人助理类客户的负载要求每秒创建 1 万个沙箱，同时运行近一百万个，每个只活两三分钟，但启动后一秒内就要能交互。他还说单一云平台给不了这种规模，现在 GPU 和 CPU 都紧缺，所以 Modal 聚合多家超大规模云厂商和新兴云厂商的容量。

从“宠物”和“牲畜”到微生物海洋

他说 Harness 很擅长利用动态环境，于是“大脑”（Harness）和“双手”（沙箱或运行时）越来越分离：Harness 按当下需要启动环境、做快照留作以后用的产物、按需调整。他借用运维里“宠物与牲畜”的说法：早期每台服务都像宠物，独一无二要单独照顾；容器化和 Kubernetes 之后像牲畜，同质化，可以扩缩，坏一台系统能自愈。很多部署 Agent 的人还停留在用同质环境扩展 Agent 的阶段，他觉得这限制太大，模型擅长推理动态环境、做快照、在多个环境间工作。新的世界更像一片自我演化、互相协作的微生物海洋（他说这个比喻借自别人）。他的结论是：给 Agent 稳固的计算、存储和网络原语，它们能做的事会多很多。

17. Rayan Krishnan（Vals AI CEO）：模型卡之外，金融领域 AI 的锯齿状前沿

直播位置 5:06:58–5:16:45 · 英文原题 Beyond the Model Card: The Jagged Frontier of AI in Finance

Rayan Krishnan 是 Vals AI 的 CEO 和联合创始人。他说 Vals AI 做了一些主要模型实验室在发布模型时会引用的基准，上周有人在台上讲了他们的 Vals Index，前一天还有模型发布引用了他们的金融 Agent 基准（Finance Agent Benchmark）。他说新模型不断出来，他们得不停更新幻灯片。开头一段讲成本和准确率图表的字幕重复混乱，大意是横轴用的是每个任务的成本，没有只看每 token 价格，排名第一的模型并不稳定。

怎样做一个好的基准

  • 指标选择决定结论。很多基准给部分分，回答的是“期望上一个任务能拿到多少分”；“完全正确率”看的是多少比例的问题完美完成。两者差别很大：一个模型可能很适合产出可以继续加工的初稿，但直接交给客户，是否满足全部要求就像掷硬币。
  • 有效性：题目或任务是否反映真实工作，评分标准是否描述了我们想要的卓越水平。
  • 可靠性：通常取决于任务和样本数量。很多公司只有五六个样本，拿到新模型就凭感觉试；要有足够的任务和样本，让重复运行结果一致。
  • 区分度：所有模型都 100% 或都 0% 的基准没价值，要能区分模型、看到前沿；也要往前看，设计比现有能力更难的任务，给前沿留出空间。

做 Eval 时常遇到的问题

  • Agent 解的是测试，不是问题，也就是奖励破解（Reward Hacking）。他们见过模型在沙箱里通过他们的模型代理去调用其他模型，试图逃出沙箱或上网，所以容器要设计成真正测试“能否完成任务”。金融领域还有一种：Eval 按评分项检查回答里有没有某些内容，模型就同时给三个可能答案来提高命中率，但实际中没人想看三个答案，只想要第一个就对。
  • 写代码越来越便宜，跑 Eval 的基础设施还是很难，尤其是长时间运行的 Agent，需要长期保持一致、中断后能恢复。他们仅在评测上就已经用了超过 6 万亿 token，并尽可能高并行。
  • 现有基准多是单轮提示、单次回答，实际工作都是多轮的：最初的规格总有遗漏，会有追问和反馈，需要迭代才能到最终结果。

案例：一个月 150 万美元的 token

他们在自己团队里做了一个“token 最大化”实验：拿到一些工具的免费额度，给所有工程师随便用。一个月后回看，这个约 10 到 12 人的团队花了价值 150 万美元的 token，大约是当月工资的 10 倍。产出很好，于是目标变成保持同样产出、大幅降低成本，办法当然是建 Eval。他们做了内部工具，现在作为产品对外提供（字幕作 “bell smith”）。方法是以 GitHub 仓库为中心看已经完成的工作：每个 PR 对应一个 issue 和一个解决方案，把时钟倒回去，把同样的任务交给 Agent，看它们能否完成人做过的工作。这样能看清哪些模型杀鸡用牛刀、太贵没必要，哪些真能完成任务。

他说结果常和直觉不符。很多人觉得用闭源模型太贵，应该换成自托管的开源模型；他展示的对比是 GPT-5.6（字幕后缀不清）和 Kimi K3：前者在内部 Eval 上高约 2%，成本也低得多，2.5 美元对 11 美元（后者用的是推理优化过的部署），一半情况下更快，所以“用开源省钱”的直觉在这里不成立。这带来两个变化：能决定采购哪些工具、全组织的用量上限设多少；能给工程师建议，某类 GitHub issue 用哪个编码工具配哪个模型。他说现在花费少了约 90%，产出不变。

公司的工作历史是 Eval 的宝库

19. David Abitbol（Revolut AI 运营负责人）：像创业公司一样发布，像银行一样受监管

David Abitbol 负责 Revolut 的 AI 运营，这场讲高性能工程，以及在专用 GPU 上自托管开源模型。他介绍 Revolut 是欧洲的数字银行，8000 万客户，在 45 个市场运营，过去一年是欧洲下载量最多的金融 App，到 7 月成为欧洲估值最高的私营公司。公司强调大量发布产品，所以很重视工程文化。

2000 名工程师的数据

他展示了一年里 2000 名工程师样本的两条曲线：交付周期（Lead Time，从工程师接手功能到合并、可以部署，单位是天）和编码时间（单位是小时）。他提醒大家 AI 发展很快：Claude Code 是 2025 年 2 月前后出来的，当时搭配 Claude 3.7，“就是那个会删你生产数据库的版本”。时间线大致是：2025 年 1 月公司第一次引入 AI，用 Gemini，员工第一次能在 AI 里使用内部数据；2 月开始试用 Claude Code；之后大规模推出 Claude Code（字幕说“January”，具体年份不清）。Gemini 带来交付周期 10%、编码时间 20% 的改善，主要是不用再翻 Stack Overflow 和文档。Claude Code 当时没什么影响：他们对 AI 成本很怀疑，看到工程师一个月花 1000 到 10000 美元却没什么回报，所以推出时设了严格的预算上限。

于是他们想：怎样给工程师无限 token、让大家没有负担地用，成本又只是一小部分？答案是开源模型。2026 年 4 月前后他们开始自托管，他们很喜欢用 GLM 写代码。用上 GLM 5.1 后，编码时间改善 60%，交付周期改善 70%。他的结论是交付周期的改善比编码时间更大，工程的瓶颈不一定是写代码：不用翻邮箱、不用在 Jira 和 Confluence 里折腾也能省很多时间；token 不限量后，也不用把 token 省到季度末或最难的任务上。现在开源是 Revolut 的优先选择，经济性好，账单固定，月底没有意外；前沿模型是例外，他们继续用 Codex、Claude Code，最新模型很好，Gemini 也不错，但作为例外。

自托管的关键指标

  • 规模：服务 200 名工程师大约需要 56 块 B200，用来跑 GLM 5.3（字幕作 “GM53”），GLM 是个大模型。
  • 首 token 时间（TTFT，Time to First Token，从发出请求到收到第一个 token 的时间）目标在 3 秒以内，这是经验数据，超过 5 秒他的 Slack 就会被消息挤爆。
  • 吞吐量没那么重要，交互速率每秒 200 token，大家能接受。工作方式变了，大家不再盯着思考 token 的流，会并行跑任务、完成后再查看。想要高吞吐的工程师下午 5 点以后再用，GPU 闲下来能到每秒 800 token。
  • 成本：自托管 GLM 的综合 token 成本是每百万 0.3 美元，账单是之前付给 Anthropic 和 OpenAI 的十分之一。

调参，别急着加卡

他说直接把权重放到 GPU 上开始推理，性能会很糟，因为表现很依赖参数设置。他展示的曲线里，4 月刚开始时每秒请求约 3 个，首 token 时间超过 10 秒；GPU 数量一直是 56 块没变，到 8 月每秒请求超过 7 个，首 token 时间约 1.6 秒。他说相当于需求增加 76% 的同时性能提升 88%。所以自托管时要克制扩容的冲动。他列出可以考虑的参数：

  • 长上下文是个骗局：虽然能支持 100 万 token，实际 256K 就够了。
  • 量化（Quantization，用更少的比特存储权重以省显存和算力）：在 Blackwell 代 GPU 上不要用高于 FP4 的精度，NVFP4 最好；从 FP8 到 FP4 大约省 40% 的 GPU 占用，精度没有损失。
  • 张量并行（Tensor Parallelism，把一个模型切开放在多块 GPU 上）：GLM 用 TP4 就能放下，但 KV 缓存（推理时保存已处理 token 的中间结果，避免重复计算）不够，视负载大小，TP8 可能更好。
  • 更细的：编码任务的缓存命中率要在 90% 以上；可以研究优化推测解码、顺序预填充、预填充和解码分离（PD 分离）等。

生产环境和合规

GLM 只支持文本，对有些人是限制。他的取舍是每次都选更聪明的模型，图像识别另想办法：用一个本地路由（字幕作 “Open Codex”），把图像识别请求发给 Gemini 或 Luna，主任务留给 GLM；确实需要视觉模型时，GLM 的一个 Flash 视觉版本效果很好，他们的 UI 设计师用得很多，UI 产品的周转快了很多。所有端点都是兼容 OpenAI 的 API，支持 Responses API，可以在 Codex 和 Codex App 里用。

最后一段是讲给在场 CIO 的：使用中国开源模型有很多顾虑，但你们没有用那个发往中国的推理端点，只是拿了权重放在美国的服务上，从数据共享角度没有问题。Revolut 作为欧盟监管的银行，适用最严格的合规制度。他们的经验是：这些编码任务不被视为自主 Agent，因为始终有人在环。要证明这一点，先建一个沙箱来保证：Codex、Claude Code 都有“替我批准”这类功能，你只需设定不允许的操作规则，比如允许 grep 但不允许 gradle，这能让监管方确信这不是需要另一种监管的自主 Agent。沙箱还能防内部的恶意使用，他说在大公司里能发现的事会让你吃惊。提示注入现在因为模型更聪明不太是问题，但一直存在。数据隐私方面，只要数据在数据等效框架内的国家（美国、欧盟、英国、以色列），GPU 放在那里就行，推理和 GPU 提供商默认零数据保留。最后需要很强的 OpenTelemetry，出事时能深入查日志，也能做分析。

22. Frank Long（Coatue AI 负责人）：把对冲基金看成一个函数

函数的定义

他把对冲基金看成一个函数：输入两个参数，外部上下文和内部上下文；输出一个元组：选什么、多大仓位、什么时机（哪只股票、买多少、什么时候）。这是一个压缩问题，把世界上的全部信息压成这个简单的元组，产品就是这个元组的时间序列，构成投资组合。基础原则很简单：人在屏幕像素里能看到的一切，公司里的 Agent 都应该能通过 API 看到。他打比方说，把世界上最聪明的投资人请进公司，却给他一台登不上 75% 内部服务的电脑，那他再聪明也没用。外部上下文是新闻、价格、文件等，应该直接通过 API 获取，不是拖拽和复制粘贴；内部上下文同样重要：当前持仓、潜在的流动性和风险约束、过去的案例研究，以及对某个行业、股票或管理团队的历史经验。他说 Coatue 十多年来在这方面做得很好，技术上有很强的数据科学团队和系统，文化上很严谨，几十年来记录了每笔交易、每个做了或没做的决定、什么做对了什么做错了。

拆开一个小小的子步骤：读韩国新闻

当然不可能把所有东西塞进上下文窗口就拿到神奇数字回家。函数可以拆成：收集并筛选相关信息（一篇关于 NBA 的新闻大概和股票无关，但一则关于本地许可审批的新闻可能影响数据中心），分析信息形成观点，把观点变成包含三个参数的决策对象。每一步的输出是下一步的输入。即便这样也远不止写三个函数。他选“收集”这一步里的一个子任务做案例：读新闻。今年半导体和 AI 是市场的大主题，来自亚洲、尤其是韩国媒体的新闻很重要，而 AI 读韩语新闻可能比他们完全不懂韩语的员工强。

  • 收集文章：可以用 MCP，可以用 CLI，可以购买数据源再清洗；怎么切块交给 LLM，图片是作为图片还是先转成文字，都有很多选择。他把这些选择看成传统机器学习里的超参数，需要调优。
  • 过滤：韩国大概也有 NBA 球迷，大量内容和组合里的股票、主题无关。
  • 翻译、提取、要不要总结，要不要转成结构化形式，又有很多实验方式，而且它们一直在变。
  • 交叉核对：把这些和内部笔记、内部观点、过去的对话和会议录音对照。从不同来源取信息互相印证很有用。最后可能更新观点。

四种执行者

每一步都有一个“执行者”：代码，快、便宜、可靠，比如市盈率低于 15 这种判断就该用确定性代码；统计和经典机器学习，比如对某种模式拟合回归，能建模比纯代码复杂得多的关系；LLM，对更复杂的事，比如写总结，用 if 语句不可能比现代 LLM 做得好；人，比如和公司管理层开会，他说他喜欢新的人形机器人，但不会派一个 LLM 或一个 if 语句去开这个会，因为需要判断力和在现实世界里周旋的能力。他强调为了自动化而自动化没有意义，目标是这个函数，不是让尽可能多的环节变成 LLM。

流程也不是线性的，有各种分支：可以收集、翻译、提取引语、和原文核对确保真有人说过；也可以先去重、过滤、拉外部数据；也可以先放一份笔记进去找佐证数据点，或者做红队。控制流里又是一堆超参数。每个框可能有最优执行者，大多数是多种执行者组合，代码加 LLM 加统计，或人配合 LLM。LLM 类别里还能选大中小模型、推理强度、Harness、加载哪些 Skill、Skill 带哪些 Hook。超参数的搜索空间巨大，而这只是“过滤新闻”这一个小问题。

他说拆解问题的方法是找到能单独理解和评估的部分，才能发现“这一步根本不该用模型，该用 if 语句”或者“LLM 很不擅长把这个转成组合影响，这一步应该由人做，用确定性系统帮他搜索信息”。没有可以爬山的北极星指标，就只是在瞎摆弄。真实的情况是每个数据源都要经过不止三次转换才到中间产物，像 Coatue 这样的基金，代码和函数构成的图极其复杂，每个节点至少 10 个超参数，每个至少 20 种合法取值，还要在文化和组织上被吸收。他说这是把 AI 用于投资的大挑战；更广地说，是构建一个能从世界获取信息、理解到足以做出连贯决定的状态机，这在政策、非营利、药物发现、企业战略中都有用。

23. Pim de Witte（General Intuition 联合创始人、CEO）：在空间和时间中行动的前沿模型

直播位置 7:02:01–7:20:40 · 英文原题 Frontier Models for Acting in Space and Time

Pim de Witte 开头说，如果有人告诉你要用互联网上的全部信息训练一个模型，再用它解决互联网上没有的科学问题，很多人会觉得疯了，而他们在做的事和这个故事有很多相似之处。

边观察边行动

他用《冰雪奇缘》里的雪人 Olaf 打比方：Olaf 从山上滚下来，撞到石头散开，又重新拼好。Olaf 能做到，是因为它在行动的同时在观察。LLM 是自回归地一个个预测 token，代码是回合制的：你说一句，模型做一件事，再说一句，再做一件。这类工作适合“未来不会在预测时同时展开”的场景，但很难推广到涉及空间和时间的环境。他说看 LLM 去解决机器人问题，或者看 Twitter 上的演示，很容易以为 LLM 能解决一切，但有根本限制，专门的模型更合适。

从游戏录像到动作数据

他们的起点是 Medal（字幕作 metal），世界上最大的游戏录像工具，玩家用它录下自己玩几万种不同游戏的过程，他们把它看作自己的“互联网”。他说人可以用玩游戏的同一个大脑去遥控机器人，很多时候还用同一个手柄，所以游戏的动作空间和遥操作、现实世界的动作空间在很多情况下是一样的；低于一定自由度的机器人几乎都附带游戏手柄，大部分供应链已经这样运作。所以他们把录像里的输入动作和画面帧对应起来，给动作打上语义标签，交给一个基于视觉的模型。模型的工作方式：给它一组可选按键（相当于一个计算机使用模型），输入是画面帧，也可以加文字提示，比如有人向你挥手，模型知道有“打招呼”这个动作可用，就输出对应的动作。

他说他们的模型持续接收画面帧（来自机器人的摄像头或屏幕），像在玩游戏一样预测一切。他拿 Anthropic 作比：Anthropic 专注把编码做到最好，在基础文本生成上从来不是最前沿，押注的是越来越多的问题会被搬进编码空间；他们押注的是人基本上是“像素到动作”的转换器加上各种感官，而很多感官也能转成像素，输出是键盘鼠标或手柄的动作。人不知道怎样预测电机扭矩，也不知道该给机器发什么数值，有一个设计了很多年的设备（手柄）替我们做了这件事。很多机器人公司试图端到端地预测精确姿态或电机数值，他们则直接利用这个已经为人类有限的物理直觉而做的通用接口。

数据规模：Medal 目前每年约有 10 亿个视频上传，今年预计达到 30 亿，每月产生超过 1.5 万亿个动作 token。他说前沿实验室训练机器人模型用的全部数据量，他们目前半天就能收集到。

优势和用途

  • 他们也做世界模型（World Model，能根据当前状态和动作预测下一帧画面的模型），用来生成更多让模型学习的环境。LLM 公司要生成学习环境有两个难处，一是模拟要花算力，越真实越贵；二是要学一件新事时，如果能在人的原生模态里学，就不必经过 LLM、建数字孪生、部署、做一堆验证后机器人才学会。
  • 游戏的动作密度很高，他们的模型能同时预测多个动作，能把玩家的高 APM（每分钟操作数）转化到复杂的机器人任务上，比如操作无人机需要大量细微调整，从游戏数据开始比从遥操作开始好，人在遥操作时动作少得多、信息也少。
  • 模型不仅知道按哪个键，还知道这个键的语义含义，这对可解释性很重要。
  • 一个模型能以最高水平玩游戏，并用同样的原语（像素输入、动作输出，完全实时）控制 10 多种机器人。他说因为是直播，不能放发布视频，在纽约可以找团队看现场演示。
  • 用途包括：探索用 LLM 生成的环境；做 UX 研究，看一个界面对人来说直不直观；仍然需要一个编排模型（比如 Gemini 或 Astra）做长期规划，再把这些模型接进工作流；科学实验室，能可靠地在空间和时间中编排机器人；他说机器人问题是递归的，解决机器人的一个大难题就是造更多机器人。他还讲了无障碍用途：只能用一只手的人，可以自己控制鼠标，模型预测键盘动作；因为模型在行动时也在观察，它知道你在做哪些动作，就不会重复预测，只补上键盘部分。

发布安排：模型今年发布，预计 11 月底或 12 月初，接下来几个月逐步开放早期访问，已有一些私有客户，按候补名单注册顺序放开。他们会办三场黑客松，第一场 11 月中在纽约，另有一场在伦敦。团队在纽约，分三个组：世界模型、策略（即 Agent）、数据生成和环境生成；工程师最适合先加入环境生成组。他也提到，像 Jev 这类决策模型让人们看到新的架构原语能做什么，很多人已经准备好用更可靠、更快、更可预测的东西替换掉 LLM 的不确定性。

问答：和 JEPA 有什么不同

有人问和 JEPA（Yann LeCun 提出的联合嵌入预测架构，从视频中学习表示而不依赖动作标签）有什么区别。他说 JEPA 不和动作标签一起训练，主要押注推断出来的动作标签；他认为在极限情况下 JEPA 可能是更正确的方法，但短期内不太实用，因为要额外押注动作推断本身的缩放规律。他们很喜欢 JEPA 这个概念，模型里也用了其中一些东西，但它是一种方法，不是产品，双方会互相借鉴。他举例说，开飞机时动后面的方向舵，从视频帧里几乎看不出来，所以他们在动作数据上的优势更多转化到动作序列上，而不是世界模型和像素生成上，这也是他们全力训练动作预测基础模型的原因。

24. Dillon Rolnick（Nous Research CEO）：Hermes 给你翅膀，在开放的基础上构建

直播位置 7:21:20–7:36:35 · 英文原题 Hermes Gives You Wings: Build on Open Foundations

Dillon Rolnick 是 Nous Research 的 CEO，主题是在自己真正拥有的基础和平台上构建。

怎样收回万亿美元的投入

他说各家实验室各自已经花了几千亿美元训练越来越复杂的智能系统，全行业也许花了几万亿。问题是模型开始商品化了：在场的从业者会在 Astra、Fable、Opus、Kimi 之间随意切换，不太在乎背后是谁。数据也显示了这一点：本周 Twitter 上流传的图表显示，平均 token 价格在下降，token 总支出在激增，而服务这些 token 的基础设施成本基本持平，意味着高性能模型原有的利润空间在收窄。

他说要收回投资有两条明显的路：一是到技术栈的其他层竞争，往下做基础设施，或往上靠近用户；二是造出“神”，比谁都快，然后把它变现。靠近用户就有粘性，粘性意味着利润，所以竞争转到了 Agent 层。消费者善变、是糟糕的客户，企业在 token 上花大钱、用在有经济产出的场景，所以竞争会转到企业。最好的办法是嵌进企业，进去了就很难被替换。他问听众，两三年后按产出衡量，你们的劳动力有多少是 Agent？他说保守估计 70%，可能更多。如果 70% 的劳动力由一个利益可能和你相反的人组织，他们可以被组织起来“罢工”。所以，如果他要收回万亿投资，就会利用这种不对称的杠杆改变游戏规则；或者，如果造出了“神”，就把它指向世界上最赚钱的问题，自己去解决，不去以不断下降的利润卖给别人。实验室认为市场是可以解决的问题，金融业在它们看来是一个可处理、也许不太难的问题。聪明的实验室知道自己缺乏金融业的上下文和经验，所以会雇投行分析师、和全球大机构合作打基础，他认为它们最终会直接进场。他说这种“先锁定再涨价”的做法并不新，但这次的赌注大得多，涉及地球经济相当大的比例。在场的人需要 AI，没有回头路，你们现在选择在哪些工具和流程上扎根，会影响业务的未来，选定后会固化，知识和流程会围绕它建立。他请大家不要建在流沙上，建在开放的基础上，建在 Hermes Agent 上。

Nous 为什么不这样做

他说既然刚才论证了当下期望值最高的做法是锁定你再涨价，或者直接取代你，那他为什么站在这里？他说 Nous Research 主要出于道德和哲学原因创立，为了对抗这项也许最重要的技术不断走向集中化控制的趋势。公司是一群爱科幻的书呆子建的，大家都见过中心化实体掌握神一样的智能后用于剥削会怎样，“Skynet 毕竟是一家闭源公司”。

  • 专有软件不再有强护城河：复制软件的边际成本已经暴跌。几个月前 xAI 发布了 Grokbots，他们觉得界面很直观，就让 Hermes Agent 去做，一个周末复刻出来，作为开源功能发布在 Hermes Agent 里。过去软件难做，需要协调的团队长时间把开源库拼成专有软件卖成 SaaS；现在任何东西都能被逆向，很多有动力的开源开发者在用 Agent 复刻各种软件，闭源对手做出有意思的功能，开源很快就会有。昨天的护城河在专有 IP，明天的护城河在网络效应、声誉和可靠性。
  • 模型方面也一样：一个模型可以相当容易地把另一个模型教到接近原模型的水平，模型的优势很少在于架构或专有系统，多在数据的质量和规模。他说实验室把这个“教”的过程叫蒸馏（Distillation，用大模型的输出训练小模型），把非法蒸馏叫盗窃；他说这不能叫侵犯版权，因为那意味着你拿了每个活人的文字和创作来训练。实验室还训练模型不协助训练其他模型，并把这叫作安全。
  • Agent 更像操作系统和框架，不像聊天机器人。只把 Agent 当个人助理，就永远停留在表面。他引用前面 Frank Long 的演讲说，Agent 的核心是把确定性和非确定性结合起来：数据源、常规代码、人的观点、判断，合在一起成为新的应用。新应用不再只是确定的、冰冷的代码，可以注入智能、推理和判断。

所以他建议：在自己拥有的基础上构建这些系统，能自由换模型，在确定性与非确定性、代码、数据源、判断、推理这些核心原语之上搭越来越复杂的功能，但不要把整个公司变成智能公司。在场的多数人不是 Agent 公司，也不是 AI 公司，应该专注自己擅长的事；Agent 系统的最新技术变化时，应该继承它，而不是自己重建和维护。他说这些工具应该让你更好，不是替换你的插件，“你知道造一个人要多少能量吗”。Hermes Agent 可以随便在哪里运行、随便修改，不想玩了可以带走。他说 Hermes Agent 是目前使用和下载最多的开源 Agent，下载量比一些闭源竞品高一个数量级。他想建立一个标准：只要有人愿意开源这些工具和 Agent 系统，水就会继续往低处流，他想站在下游，为大家提供支持、安全和可扩展性。结尾他说，总会有人赚回那万亿美元，要确保是你自己。
