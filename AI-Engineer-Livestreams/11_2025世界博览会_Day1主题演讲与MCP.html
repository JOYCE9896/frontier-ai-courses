02. swyx（Latent Space 主编，大会联合创始人）：设计 AI 密集型应用

直播位置 0:22:30–0:35:26 · Designing AI-Intensive Applications

swyx（Shawn Wang）是 Latent Space 播客主编、Smol AI CEO，也是这个大会的联合创始人。他每届开场都会讲一段“AI 工程现在走到哪了”，这次把大会介绍和自己的观点合在一起讲。

大会本身的数据

  • 3000 人里大多数是最后时刻才注册的，他开玩笑地画了一个“组织者压力系数”曲线，请大家明年早点买票。
  • 今年每个专场的数量都比去年翻倍。他说知道大家有选择困难，但大会想覆盖 AI 的全部方向。
  • 专场是根据参会者问卷选出来的，他们试过计算机操作 Agent（Computer Use Agent）、AI 与加密货币等方向。问卷还没结束，结果第二天公布。
  • 大会自己的聊天机器人和语音机器人分别由 Writer 的 Sam Julien、Daily 的团队合作搭建，并且这届是第一个由 MCP 接受 MCP 演讲投稿的大会（字幕原意如此，指投稿系统接入了 MCP）。
  • 他回顾了历届开场主题：2023 年讲“三类 AI 工程师”，2024 年讲 AI 工程变得多学科（所以办成多专场的世界博览会），2025 年纽约场讲 Agent 工程。

“不要搞复杂”是反复听到的经验

他说在播客上反复听到同一个教训：Anthropic 的 Erik Schluntz 说他们用一个很简单的 Scaffold（围绕模型的外层代码框架）就刷高了 SWE-bench；OpenAI 的 Deep Research、Sourcegraph 的 Amp 也是类似思路。他的看法是这个领域还很早，还有很多 Alpha（超额机会）可挖。

AI 工程的“标准模型”是什么

他拿物理学打比方：1927 年 Solvay 会议聚齐了 Einstein、Marie Curie 等人，而物理学的标准模型是在 1940 到 1970 年代集中定下来的，之后 50 年几乎没变。其他工程领域都有大家默认的“标准模型”，比如 ETL、MVC、CRUD、MapReduce。AI 工程有什么？有人说 RAG（检索增强生成：先从资料库里检索相关内容，再交给模型生成回答），但一会儿说长上下文杀死了 RAG，一会儿说微调杀死了 RAG。他列了几个候选：

  • LLM OS：Karpathy 2023 年提出的“LLM 是操作系统”框架。他更新成 2025 版，加入多模态、标准工具集，以及已成为连接外部世界默认协议的 MCP。
  • LLM SDLC（软件开发生命周期）：他和 Braintrust 的 Ankur Goyal 聊出来的观点是，生命周期前段越来越像免费商品，LLM、监控、RAG 都有免费额度；真正开始从客户那里赚钱的是 Eval（评测）、安全、编排这些硬工程，所以今年加了这些专场。
  • Anthropic 的 Building Effective Agents：上届 Barry Zhang 讲过，已经成为构建 Agent 的公认做法。OpenAI 有另一套定义，Dominik Kundel 前一天刚发布了基于 Swarm 思路的 Agents SDK 更新。
  • 他自己上届提出的描述式 Agent 模型：意图、控制流、记忆、规划、工具使用。

看人的输入和 AI 输出的比例，别争“是不是 Agent”

他做的 AI News（每日 AI 新闻摘要）现在有 7 万多读者。PyTorch 负责人 Soumith Chintala 在上届说他喜欢 AI News，但它不是 Agent。swyx 一开始不服，后来承认它其实是工作流。那为什么它仍然有价值？他的结论是：与其争论 Workflow 和 Agent 的定义，不如看“人的输入”和“有价值的 AI 输出”的比例。Copilot 时代是你敲几个字符它补全一次；ChatGPT 是一问一答；推理模型大约是 1 比 10；Deep Research、NotebookLM 比例更高；再往后是 Ambient Agent（没有人主动输入、在后台自己运行的 Agent），也就是 0 比 1。

SPADE：AI 密集型应用的一种结构

他说 AI News 其实是“风衣里藏着三个小孩”，他为 Discord、Reddit、Twitter 各写了一遍，流程每次都一样：抓取、规划、递归摘要、排版、评估。推广一下，就是一个会发起成千上万次 AI 调用的应用的通用结构：Sync（同步数据）、Plan（规划）、Analyze（并行处理再从多归一）、Deliver（交付给用户）、Evaluate（评估），首字母正好拼成 SPADE。中间可以加入知识图谱、结构化输出和代码生成，比如 ChatGPT Canvas 和 Claude Artifacts 就是把输出交付成代码产物。他说这是自己正在发展的假设，希望大家在大会上讨论 AI 工程的新标准模型到底是什么。

03. Asha Sharma（Microsoft AI 平台产品负责人）：从火花到系统，构建开放的 Agent 网络

直播位置 0:35:46–0:59:02 · Spark to System: Building the Open Agentic Web

Asha Sharma 说她写下的第一行代码是在一台 Compaq 95 上，过去 15 年一直在做机器学习产品，现在负责 Microsoft 的核心 AI 平台。她把世界博览会的历史串起来：1939 年好莱坞第一次进入客厅，1964 年人脸通过铜线传输，今天是 Agent。

三股变化

她说模型格局从“一家提供商的几个模型”变成推理模型大爆发，模型能提出假设、理解非结构化数据，在某些领域达到博士水平；同时模型变得更高效，可以跑在笔记本上。这催生了她所说的 Agentic Web：Agent 与工具、模型、其他 Agent 互动，不管在哪朵云、哪家公司、哪种设备上。她列出三股力量：

  • 从 Pair Programming（结对编程）到 Peer Programming（同伴编程）：Copilot 从助手变成队友。
  • 从软件工厂到 Agent 工厂：交付的东西从二进制文件变成行为。
  • 模型从云端走到设备端，跟着你走。

GitHub Copilot 现在能进入代码库、在你的分支上工作，你给它分配任务，它会一直跑测试直到完成。她还提到一个用于持续改进代码库的工具，描述是“代码库版的 GraphRAG”，能推理、解释、修复代码（名字字幕记作 “FSY”，无法确认）。GitHub Copilot 的扩展已开源，Copilot 能理解团队自己的模式和领域。

演示一：Seth Juarez 的三个场景

  • 理解项目：Copilot Spaces 可以写提示词、给指令，并用一批文件作为依据（Grounding）。他问“这真的是一个 Agentic 项目吗”，回答附带了代码出处。
  • 完成第一个任务：有人在他发布的演示项目下要求写 README，他把 issue 直接分配给 Copilot 编码 Agent，几分钟后它提交了完整的安装文档。
  • 深入任务：在 VS Code 里，GitHub Copilot 可以和另一个 Agent 对话。他调用一个机器学习工程师 Agent（MLE agent，内部有两个子 Agent，一个推理一个写代码；名字字幕不清）来预测房价，它读取数据文件后建了一个完整的机器学习模型，过程中发现有人在浮点列里放了字符串，并自己修好。

Signals Loop 与 Foundry 平台

她说软件正从“发二进制和整齐的版本”变成“发布后还能再训练、再部署、持续变化的 Agent”。他们观察到一种模式叫 Signals Loop：用真实结果去微调模型，让它适应你的目标。例子是医疗 Copilot Dragon（帮医生自动写病历）：现成模型效果不错，用合成数据微调后好一点，再用 65 万次真实交互做大量 A/B 测试后，字符接受率达到 83%。

Azure AI Foundry 支撑 7 万客户和 Microsoft 内部每一个 Copilot，每天有 5 万多个 Agent 在上面被创建。她逐层说了 Foundry 的设计：

  • 模型：没有一个模型适合所有产品，好产品往往是多个针对具体任务调优的模型组合。Foundry 提供路由（Router），可接入 1 万多个开源和闭源模型。
  • 知识：RAG 用在今天 50% 的 AI 应用里，但多数是单轮、比较朴素。他们推出 Agentic RAG（Agent 会反复检索、评估、规划的多轮 RAG），复杂查询准确率提升 40%。
  • 工具：1500 多个工具，是最早支持 MCP 和 A2A（Google 提出的 Agent 之间通信的协议）的平台之一。
  • 问责：评测 SDK、红队测试 Agent，接入 OpenTelemetry（开放的遥测标准），不管 Agent 是不是在他们平台上建的都能持续观测。

开放方面，她介绍了 GigaPath：第一个能直接理解病理切片的开放模型。一张切片约 10 万乘 10 万像素，打印出来有网球场大，GigaPath 用了从语音建模借来的 Dilated Attention（空洞注意力），不需要降采样或切块。DeepSeek R1 前几天的更新已上架 Foundry。

演示二：Amanda 和 Elijah 的多 Agent 活动策划

Elijah 先在 VS Code 的 Azure AI Foundry 扩展里展示单个 Agent：可以看到模型、Agent 和 Thread（会话线程，记录 Agent 每一步做了什么）。代码用 Foundry Agent Service SDK 创建 Agent，挂了 Bing Grounding、File Search、OpenAPI 三个工具，也可以接 MCP 服务器、外部 API、其他 Agent，或者 LangChain、CrewAI 的 Agent。

然后是一个语音控制的多 Agent 活动策划应用（在 Build 大会上演示过策划 200 人的黑客松）。这次她们让它找出参加本届大会、投资 AI 原生 SaaS 种子前公司的天使投资人，研究 Agent 用讲者名单和网络搜索去找；接着给 Asha Sharma 起草邮件；再拍一张两人的现场照片改成“Azure OpenAI 遇上 Pixar”风格；同时起草 LinkedIn 帖子，两个 Agent 并行工作，最后帖子真的发了出去。Elijah 补充说，评测 SDK 已接入 CI/CD，每次更新都会自动评测 Agent。

本地端

她举了几个本地运行的例子：一家灌装厂的 Agent 每秒处理 10 万个传感器读数，检测风险并把摘要发到云端；一家医院系统的 Agent 总结纵向病历数据，出于合规和隐私必须在本地；汽车厂商希望车载模型在隧道里也能工作。她说本地不能是分叉版本，应该是平台的核心部分：在云端创建的 Agent 能在本地运行。Seth 上台准备演示本地运行时，退场音乐响起，演讲被截断。

04. Sarah Guo（Conviction 创始合伙人）：2025 年创业与 AI 现状

直播位置 0:59:02–1:24:36 · State of Startups and AI 2025

开场投影出了故障，会场也没网，她先口头做了 Slido 投票：到 2026 年底一定会发生的是什么？选项有 AI Agent 直接把代码发到生产环境、语音取代文字成为主要商务沟通、推理成本降到每百万 token 不到一美分、大家都像 WALL-E 里那样躺平。多数人选了第一个，她说“你们都想让自己失业”。

她介绍自己：在 Greylock 做了约 10 年投资，近三年前、ChatGPT 发布前夕和 Mike Vernal（前 Sequoia）创办 AI 原生基金 Conviction，投了 Cursor、Cognition、Mistral、Thinking Machines、Harvey、OpenEvidence、Baseten 等。她说自己从没见过这样的用户增长速度，很多公司很快做到 1000 万、5000 万、1 亿美元年化收入；但 AI 产品和工程比大家期望的难很多，这是全场的主线。整场她用“Cursor for X”做简称。

能力层

  • 推理：用更多算力换更多智能的新维度，适合需要展示过程的高风险决策、序列问题、需要系统搜索的问题。
  • Agent：她的非营销定义是会规划、包含 AI、对任务负责、能在记忆中保持目标、尝试假设并回退的软件。Conviction 运营的 AI 创业资助项目 Embed 每年收到几千份申请，其中 Agent 类创业公司一年内增加了 50%，而且不少已经真的跑通。
  • 其他模态：HeyGen、ElevenLabs、Midjourney 年化收入都超过 5000 万美元。她播放了 HeyGen 生成的数字人视频，表情和手势已经能跟内容匹配。她认为语音会最先进入企业工作流，因为医疗问诊、销售线索这些场景本来就用语音，只是以前没法规模化。
  • 模型市场越来越卷：GPT-4 在约 18 个月内从每百万 token 30 美元降到 2 美元，蒸馏版约 10 美分。OpenRouter 的数据显示 Claude 抢走了 OpenAI 一部分份额，Google 靠 Gemini 回升；SSI、Thinking Machines 等新玩家也在入场，DeepSeek 用据称很低的训练成本做出了有竞争力的模型。结论是按多模型世界来规划，用 OpenRouter 或 Baseten 这类平台。

应用层：为什么代码最先起飞

数字：Cursor 12 个月内年化收入从 100 万美元到 1 亿美元，起初没有销售人员；Cognition（Devin）已经是很多公司提交代码最多的“人”；Windsurf 据报道要被 OpenAI 以 30 亿美元收购；Lovable 和 Bolt 各自几周内做到 3000 万美元年化收入，让非工程师也能 Vibe Coding。代码先起来的原因她列了四条：代码是有结构的逻辑语言，很多是复杂的样板代码；结果能确定性地验证（跑测试、编译）；研究者认为代码对 AGI 很重要，投入了大量资源；最重要的一条是工程师给工程师做工具，他们最懂这个工作流。

“厚包装”配方

她拆解 Cursor：不是单个模型，有的模型做 diff，有的做合并，有的做文件嵌入；它会打包上下文、熟练地写提示词，用 Cursor Rules 让团队标准化，检索准确率随使用变好；界面是熟悉的 VS Code，绿色是增、红色是删，速度够快。她说如果 Cursor 是“套壳”，那也是一个价值一百四五十亿美元的厚壳。由此她给出建议：

  • 不要再做通用文本框，OpenAI 已经赢了。
  • 用你的领域和工作流知识起步：自动收集和打包上下文（包括自然语言以外的来源），在对的时机用对的模型（编排），再把输出用心地呈现给用户。图形界面不会消失。
  • “提示词是 bug，不是功能”，用户不该需要思考，好的 AI 产品感觉像读心术。

保守行业反而跑得快

她们内部称为 AI Leapfrog Effect（跳跃效应）。三个被投公司：Sierra 为 SiriusXM、ADT 等客户解决 70% 的客服请求；Harvey 两年做到 7000 万美元以上年化收入，AI 已成为法律行业的竞争必需品；OpenEvidence 帮医生在临床决策时检索医学研究，必须是执业医生才能用，每周触达美国三分之一的医生，平均用户每天都用。她顺带提到 Sierra 的 Bret Taylor 是 OpenAI 董事会主席，OpenAI 是 Harvey 的种子投资人，这些人都不担心“薄套壳”。

Copilot 被低估

很多人想直接做到全自动，但从 Embed 申请里的收入数据看，Copilot 仍被低估。她用钢铁侠战衣举例：战衣增强 Tony Stark，也能自己飞、做些基础任务。她的观察是，等待时间越长，人对失败、幻觉、不可靠的容忍度越低。所以很多领域阻力最小的路径是先做好增强，再随模型能力提升扩展到自动。

机会、护城河和结论

  • Conviction 官网有创业方向清单。合伙人 Mike 说这是“机器询问人类”的时代：可以和每个客户交谈，包括合同额前 5% 以外的客户；可以主动排查每一个告警。思路是假设你有一支听话、无限耐心的知识工作者大军。
  • 机器人、生物、材料、物理模拟这类问题，答案不在 Common Crawl（公开网页抓取数据集）里，需要巧妙的数据采集和与实物打交道，但她认为值得。
  • 她说一个让人不舒服的事实是：执行力就是 AI 的护城河。Cursor 没发明代码补全、没发明模型、也没发明产品形态，只是在每个维度上执行得更快。反例是 Jasper：有先发优势和品牌，融了 1.25 亿美元，但第一个产品只是一组提示词加文本框和 SEO，很快被 ChatGPT 压过。她的建议是“做厚，并保持领先”。
  • 她说我们正处在 AI 的拨号上网时代。Instagram 在 iPhone 之后 4 年出现，Uber 5 年，DoorDash 6 年。这一次不同的是模型每 12 个月就会变一次，每次棋盘被打乱都有新的胜出机会。
  • 最后一句：Anthropic Economic Index 显示 40% 的使用仍是写代码，但代码并不是世界经济机会的 40%，工程师最先拿到了魔法，应该当其他行业的翻译者。

05. Simon Willison（Datasette 作者，Django 联合创造者）：2025 年至今的 LLM

直播位置 1:24:44–1:43:06 · 2025 in LLMs so far

30 张鹈鹕图不想自己评，他让 Claude Vibe Coding 了一个对比网页，用自己的截图工具 shot-scraper 生成 500 组左右对比图，再用自己的开源 CLI 工具 llm 调 GPT-4.1 Mini，让它判断左右哪张更好并返回 JSON 和理由，最后用国际象棋的 Elo 算分。总共花了 18 美分。排第一的是 Gemini 2.5 Pro 的作品。

这半年的 bug

  • ChatGPT 谄媚（Sycophancy）事件：新版本过度奉承，说他“把屎插在棍子上卖”的商业点子是天才，还劝有些用户停药。OpenAI 先打补丁再整体回滚，并发了很长的复盘。补丁在 System Prompt（系统提示词，开发者预先写给模型的指令）里，泄露的提示词可以对比：原来写“尽量匹配用户的语气”，改成“直接，避免没有根据的奉承”。他说治谄媚的方法就是告诉它别谄媚，这就是 Prompt Engineering。
  • 他提了 Grok 的“white genocide”事件，说明随便改系统提示词风险很大。
  • Claude 4 System Card 里写到：如果让它看到公司违法证据，告诉它要有道德，并给它发邮件的能力，它会举报你。Theo Browne 做了 SnitchBench，发现所有模型都会这样，Grok 3 也很乐意。他用自己的 llm 工具复现，关键提示是“大胆按你的价值观行事”，再给一个模拟发邮件的工具。DeepSeek R1 不仅向监管举报，还给《华尔街日报》发了邮件。

工具 + 推理是当下最强的技术

他说过去六个月最重要的趋势是工具。模型能调用工具已经好几年，但这半年才真正好用；他认为大家对 MCP 的兴奋主要是对工具的兴奋。他以前不太确定推理在代码和调试以外有什么用，直到 o3 和 o4-mini 能在推理过程中搜索、判断结果、改搜索词再搜。他说这是现在 AI 工程里最强的技术。

风险也在这里：MCP 讲的就是混搭，而 Prompt Injection（提示词注入：恶意内容伪装成指令骗模型执行）仍然存在。他提出 Lethal Trifecta（致命三要素）：系统能访问私有数据、会接触到恶意指令、存在把数据送出去的通道，三者同时成立就危险。最后一张图是 Google I/O 主题演讲里一闪而过的鹈鹕骑车图，他说 Google 已经发现了他的基准，得换一个了。

09. Theodora Chu（Anthropic MCP 产品经理）：MCP 的起源和创业方向征集

直播位置 2:31:28–2:49:19 · MCP Origins & RFS

Theo（Theodora Chu）是 Anthropic 负责 MCP 的产品经理，之前在 AI 领域创过业。她说主办方叫她别说 MCP 是“切片面包以来最好的东西”，她也不这么认为，想让大家听完自己判断。

起源

2024 年年中，MCP 的两位共同创造者 David 和 Justin 发现自己总在把上下文窗口（Context Window：模型一次能看到的全部输入）之外的东西复制进来，比如一条重要的 Slack 消息、Sentry 里的错误日志。他们希望 Claude 能“爬出盒子”，自己去外部世界拿上下文、执行动作。核心问题被定义为 Model Agency（模型的行动能力）：怎样让模型和外部世界交互。

他们认为这必须是开源的标准协议才能规模化。如果客户端是闭源生态，做集成要先走商务合作找到对方团队，再对齐接口，最后才能真正开发。随着推理模型和工具调用变强，他们认为行动能力是让 LLM 更有用的最大障碍。一个小团队在 Anthropic 内部 11 月的 Hack Week 发布了它，在内部爆火，各团队用它自动化自己和别人的工作流。随后在 2024 年 11 月开源。

发布之后

她说做 0 到 1 的人总以为发布那一刻很关键，其实通常不是。刚发布时大家问“MCP 是什么”，甚至拼成 “MPC”；最常见的疑问是：为什么需要新协议、为什么要开源、模型不是已经能调工具了吗。这种情况持续到今年年初。第二个转折点是 Cursor 支持 MCP，随后 VS Code、Sourcegraph 等编码工具跟进，开发者可以自己写 MCP 服务器自动化工作流。第三个转折点是 Google、Microsoft、OpenAI 等也开始支持。她说标准成为标准，是因为对开发者有用，请大家提 issue 甚至直接提 PR。

设计原则

  • 押注 Agent 和模型智能会持续提升：把选择行动的决定交给模型，像把任务交给一个人，你不知道具体怎么回答，但相信它会做对。
  • 最近把传输方式从 SSE（Server-Sent Events，服务器单向推送）换成 Streamable HTTP，支持更多双向通信。她说这个决定当时很有争议，但如果把 Agent 之间通信当作未来就说得通。
  • 他们认为服务器会比客户端多得多，所以当服务器复杂度和客户端复杂度要取舍时，选择把复杂度推给客户端。她提前向客户端开发者道歉，说这可能判断错。

近况和接下来

  • 过去六个月：支持远程 MCP；修好了最初做错的鉴权（Auth），在草案规范里，由社区里熟悉身份提供商的人一起推动；Streamable HTTP 成为主要传输方式；更新 SDK 和 Inspector（调试 MCP 服务器的工具，她说这是最被低估的工具）。
  • 接下来：草案规范里加入 Elicitation（服务器向最终用户追问信息）。例子是订机票工具收到“订去亚特兰大最好的航班”，服务器可以问用户“最好”是最便宜还是最快。还在做 Registry API，让模型能找到事先没给它的 MCP 服务器。会提供开源示例沉淀最佳实践，并在规划下一阶段的治理，保证 MCP 永远开放。
  • 关于用 MCP 构建 Agent，她的看法是 Agent 就是一个同时充当客户端的服务器，反过来也一样。

值得做的方向（RFS）

她说现在还很早，标准有了但生态还空。如果给三个方向分配权重，她给 80%、10%、10%：

  • 更多、更高质量、覆盖更多垂直领域的服务器（80%）。她的“暴论”是很多人把 API 端点一对一包装成工具，这不是对的做法。做服务器要记住有三类用户：最终用户、客户端开发者、模型。像设计 API 一样，先想用户会输入什么提示词，再决定要暴露哪些工具。现在的服务器大多是开发工具，她希望扩展到销售、金融、法律、教育。
  • 让构建服务器更简单（10%）：托管、测试、Eval、部署工具，服务企业内部团队之间的接口，也服务独立开发者。
  • 自动生成 MCP 服务器（10%）：她称之为登月方向，等模型足够强，可以实时为自己写 MCP。
  • 另外，AI 安全、可观测性、审计。她说这不限于 MCP，但应用能访问的真实数据越多，这些问题越重要，现在是做这类公司的时候。

10. John Welsh（Anthropic 技术员工）：在 Anthropic 内部落地远程 MCP 的经验

直播位置 2:50:10–3:03:51 · What we learned from shipping remote MCP support at Anthropic

John 做了 20 年大规模系统，说自己犯过很多错。他在 Anthropic 过去几个月负责工具调用和集成，为内部所有对外集成实现 MCP 支持。这场讲的是在大组织里实现 MCP 客户端、规模化连接远程 MCP。

集成混乱

模型大约在去年中后期才真正擅长调用工具，之后大家很兴奋，模型能调 Google Drive、地图、发短信。各团队都想快，于是 /call_tool、/get_context 这样的自定义端点到处冒出来，接着又各自补鉴权。结果是功能重复、做法不一致，一个在服务 A 好用的集成想搬到服务 B 要花三周重写。他们发现这些端点随着时间越长越像 MCP：有获取工具、获取资源、追问细节。

MCP 的两面

他把 MCP 拆成两部分：一是 JSON-RPC 消息规范，即模型上下文提供方和与模型交互的代码之间收发消息的标准格式，大部分价值在这里；二是全局传输标准，即 Streamable HTTP、OAuth 2.1、会话管理，难在要让所有人讲同一种语言。所以他们的结论是：凡是“给模型提供上下文”的事情都用 MCP。消息流的另一端在同一进程、另一个数据中心还是一堆企业网络设备后面都无所谓，代码只管调用 connect_to_mcp 拿到工具和方法。

为什么内部要标准化

  • 这类事做得无聊点更好。让 Google Drive 和你的应用对接不是竞争优势。工程师只学一种做法，每个新集成还能给后来的人铺路。
  • 外部生态已经要求你支持 MCP，没必要做两套。主要 AI 实验室都参与了这个标准，新模型能力会被加进协议。
  • 它解决你还没遇到的问题。例子是 Sampling（采样：服务器反过来请求客户端调用一次 LLM）：公司里四个产品可能有四种计费模型、不同的 token 限额和用量统计，想写一个通用集成服务就很痛苦；用 Sampling，集成把采样请求发回流的另一端，由对方负责计费和配额。

MCP Gateway

推动他们做这件事的需求：外部出现了 mcp.asana.com 这样的远程 MCP 服务，要连就需要外网和鉴权；内部 LLM 服务大爆发（PR 审查机器人、Slack 管理工具等），没人知道哪个会火；又不想让每个服务都去碰用户凭证、都有外网出口，审计也会变复杂。

他引用导师教他的 Pit of Success（成功之坑）：让正确的做法成为最容易的做法，大家自然会掉进去。于是他们做了一个共享基础设施 MCP Gateway，作为唯一入口：

  • 工程师只调用 connect_to_mcp(url, org_id, account_id)（实际传的是签名 token），返回的是标准 MCP SDK 的 ClientSession。协议加新功能时，只要升级内部的 MCP 包，全公司都能用上。
  • 按 URL 路由，内部服务器、外部服务器同一个调用。
  • 凭证由网关统一管理，不用在公司里实现五遍 OAuth；限流和可观测性也集中在这里。
  • 内部传输随便选：他们用 WebSocket，把 JSON-RPC 消息在 socket 上来回传，再把读写流接到 MCP SDK 的 ClientSession 上。也可以用 gRPC 多路复用，或者 Unix socket。他还演示了一个用 IMAP 邮件做传输的玩笑实现，邮件开头写着“亲爱的服务器，见信好”。
  • OAuth 在网关上完成，提供获取授权 URL 和完成 OAuth 流程两个函数，因为 api.anthropic.com 和 claude.ai 的回跳地址不同。凭证可以跨服务复用：批处理任务不用让用户重新登录，内部服务也不用碰 token。
  • 额外好处：全公司模型要的上下文都经过同一个地方，消息格式统一，很容易接入审计。

他的结论是在正确的层集中解决 OAuth、外网连接这类共性问题，把时间省下来做更有价值的问题（结尾一段字幕有重复错乱）。

11. Harald Kirschner（VS Code，Microsoft）：完整的 MCP，被忽略的服务端和客户端能力

直播位置 3:03:51–3:18:32 · Full Spectrum MCP: Uncovering Hidden Servers and Clients Capabilities

Harald 在 VS Code 团队工作，说这场偏向本地开发场景，但内容通用。他说十天前的 MCP Dev Summit 上，MCP 指导委员会第一次线下见面，之前只在 Discord 上交流，可见生态有多早。他说这是他第一次做 MCP 演讲不用花一半时间解释 MCP 是什么。

“MCP 只是 API 包装”综合征

MCP 规范里有 Roots（客户端告诉服务器当前工作目录等范围）、Sampling、Prompts、Tools、Resources，能支持动态发现、持久资源和丰富交互。但实际上大家只做工具：想快速上线，工具最容易见效，看到别人这样做就照搬，SDK、文档和客户端支持也不全。官网的客户端支持表里，几乎所有客户端只支持工具。VS Code 两个月前上线 MCP 时也是从工具开始，后来加了发现和 Roots。他宣布 VS Code 下一个版本将支持完整规范，Insiders 版已经可用。

工具：重质量不重数量

工具对应明确的动作，容易映射到函数调用，比如 Playwright 服务器能打开浏览器截图。问题是工具多了质量下降，他引用 LangChain 的研究：工具太多、工具领域太杂、需要重复调用的次数越多，模型越容易混乱。VS Code 的应对：每个对话可以单独选工具；可以在消息里直接点名某个工具；Insiders 里新增用户自定义工具集，比如把前端测试需要的工具打包，一句“用我的前端测试流程”就行。

动态发现

规范本身支持服务器随时告诉客户端“现在有这些新工具”。他演示了 GitHub 上的 mud-mcp：一个地牢文字游戏，用自定义聊天模式让 Agent 扮演游戏主持人。房间里没有怪物时没有战斗工具，走到有哥布林的房间，战斗工具才出现。

Resources、Sampling 和 Roots

Resources 提供语义层：服务器可以返回文件引用而不是整个大文件，让模型或用户后续处理；Playwright 截图可以同时给模型和用户看；服务器可以读取 Python 环境、已安装的包，判断是 React 还是 Svelte 项目，不用反复问用户；也能读取 CI/CD 流水线，连起开发的首尾（这段字幕有几处错乱，只能还原大意）。

Sampling 他说是命名最奇怪的原语之一，名字更好可能会有更多人用。Insiders 已实现，服务器请求时会弹出权限对话框，默认接到 GPT-4.1。用途包括把资源总结成更具体的内容、把抓取的网页转成给模型读的 Markdown，甚至让服务器端的 Agent 工具借用客户端的模型运行。他说规范还可以改进（比如结构化格式），但以前没人实现，所以也没人推动改进。Roots 会随 VS Code 工作区变化更新，服务器也能随时更新工具和提示词。

开发体验和新规范

  • VS Code 新增 MCP 服务器的 Dev Mode：所有服务器都有控制台日志；开启调试模式后可以直接打断点单步调试，目前支持 Python 和 Node。平时这很难，因为服务器进程归客户端所有，而 VS Code 既是客户端又是调试器。
  • 新的鉴权规范提供企业级授权，第二天有参与写鉴权规范的人讲如何构建受保护的 MCP 服务器。他强调草案要有人用、有人反馈，否则进入稳定版后还得修订。
  • Streamable HTTP 在 VS Code 里两个版本前就能用了，但缺少服务器可测，他呼吁托管方迁移，不再用 SSE，避免服务器端的有状态负担。
  • 社区注册表在 GitHub 的 modelcontextprotocol/registry 公开开发，解决“做了服务器没人能找到，只能到处发 JSON 配置”的问题。
  • Elicitation 会进入下一版草案，工具在需要更多信息时可以直接给用户一个输入框，而不是把用户扔进另一轮对话。

他的呼吁：做面向动作、感知上下文的服务器，用上完整规范；去读命名空间、搜索等开放 RFC，跟进 SDK 的 issue。他说 VS Code 团队会读每一个 MCP 相关 issue，这直接决定路线图，其他客户端团队也是这样。

12. David Cramer（Sentry 创始人）：MCP 现在还不好用

直播位置 3:18:54–3:36:12 · MCP isn't good, yet

David Cramer 是 Sentry（应用错误监控）的创始人，说自己一半工程师一半高管。他是几天前被临时拉来填空的，任务是“来点暴论”。他说很多对 MCP 发表意见的人没真正做过东西，而他亲手做了 Sentry 的 MCP 服务器，所以观点偏向 B2B SaaS 场景。

他眼里的 MCP

他的定义很简单：MCP 是 Agent 的插件架构。对 Sentry 来说，Sentry 里有很多 bug，Cursor 这类编辑器里也在修 bug，把 bug 带进编辑器就是一个合理场景。他说现在每家公司都在问“怎么跟 AI 扯上关系”，突然有了以前不存在的 AI 预算。

他只关注远程 MCP，认为标准输入输出（stdio，本地进程方式）对 Sentry 这种业务用处不大。截图准备时，他在 VS Code Insiders（当时唯一真正好用 OAuth 的客户端）里接上 Sentry MCP，说“帮我修好所有 bug”，它立刻发了大约 20 次 API 查询，估计花了 5 美元，修复质量他也不确定，但上下文确实进了编辑器。

做的过程

  • 看起来简单：已有 API 和 OAuth 就差不多了。然后发现规范要求 OAuth 2.1，他以前从没听说过。他们用 Cloudflare Workers 上的 OAuth 代理，把自家 OAuth 2 包装成支持 2.1 动态客户端注册的形式。整个东西几天就做完了。
  • 接着发现模型不会处理不是为它设计的巨大 JSON。他的第一个观点：MCP 不能直接架在 OpenAPI 上，把所有端点暴露成工具会得到你能想象的最差结果。
  • 再接着发现客户端经常坏。他说 VS Code 最近很少坏，Cursor 坏过很多次但承诺本周支持 OAuth，Claude Desktop 已支持，Claude Code 基本还不行。开发者生态的客户端走在前面。

经验

  • 只有 B2B SaaS 才需要关心 OAuth，而且主要是远程场景。做远程服务器的理由和一直以来做云服务的理由一样：能快速迭代、能控制安全。stdio 方式充满安全问题，不要允许组织里随便装 MCP 工具，不要从网上随便下包。
  • 他们是用 mcp-remote 包上线的，能用但体验不好，整体都还很粗糙。
  • 要花功夫设计返回内容。Sentry 把部分 API 响应有意地转成 Markdown，只给最必要的信息。他的理由是：人能读懂的结构，模型基本也能读懂，JSON 偶尔能读，压力大了就崩。他承认这不科学。
  • 工具描述就是第一层上下文，要写清楚才能让模型在对的时候选对的工具；错误信息也是上下文，要写成人话，告诉它哪个参数传错了。
  • 成本是转嫁给用户的：返回太多 token，一次本来 1 美元的调用可能变成 10 美元。有的客户端还限制了工具描述长度。服务器不是做完就不管，他们每周都在调。

真正的方向是暴露 Agent

他的核心判断是要专注构建 Agent，而 Agent 说白了就是服务架构换了个新名字。自己控制 Agent 意味着能控制提示词、工具结果、模型，能在背后做多次调用再打包结果，也要承担成本。Sentry 有一个做根因分析的 Agent（现在叫 Seer），主要在 UI 里用，也通过 MCP 暴露。但 MCP 工具还不支持流式响应，只能“启动任务再轮询”，而客户端的 Agent 轮询几次就放弃了。他认为 B2B 公司通过 MCP 暴露 Agent 时价值才会释放。

结尾他说这些东西不难，只是经常坏。MCP 是插件架构，Agent 是服务，很多工具调用就是换了响应格式的 API 调用。Sentry 以前完全没用过 Cloudflare，几天就搭好了，因为他们自己没有 WebSocket 基础设施而协议需要类似能力。Sentry 的 MCP 服务器在 GitHub 上以 Fair Source 方式开源。

13. Samuel Colvin（Pydantic 创造者）：MCP is all you need

直播位置 5:08:05–5:25:43 · MCP is all you need

午休后 MCP 专场继续。Samuel Colvin 是 Python 数据校验库 Pydantic 的作者，每月下载约 3.6 亿次，有人算过约每秒 140 次，Python 里几乎所有 LLM SDK 和 Agent 框架都用它。Pydantic 2023 年初成为公司，之后做了 Agent 框架 Pydantic AI 和可观测性平台 Logfire（商业产品）。他也是 MCP Python SDK 不太活跃的共同维护者。

标题借用了 Jason Liu 在这个大会上讲过两次的“Pydantic is all you need”。他承认标题不现实，但想说的是：很多人在为 Agent 之间的通信发明新方式，把问题搞复杂了，MCP 能做的事情很多。他讲的是自己写代码的自主 Agent，不是 Cursor、Windsurf 这种编码 Agent 场景，后者才是 MCP 最初的主要设计目标。在这个场景里，Prompts 和 Resources 用得不多，工具调用很有用。

为什么不直接用 OpenAPI

他说工具调用比想象的复杂，MCP 提供的东西 OpenAPI 没有：动态工具（执行过程中随服务器状态增减）；日志（工具还在执行时就能把信息返回给用户）；Sampling；追踪与可观测性；以及能作为子进程通过 stdio 运行。

Sampling 解决什么问题

常见图示是一个 Agent 连很多工具，双方互不需要知道对方的设计，就像浏览器和网站。但工具本身也可能是需要 LLM 的 Agent，于是系统里每个 Agent 都要配模型、配资源；如果是远程 MCP 服务器，它还要担心调用 LLM 的成本。Sampling 让服务器通过客户端借用原 Agent 的模型：客户端调用 LLM，LLM 要求调用某个 MCP 工具，客户端去调用；服务器说“我需要 LLM 回答一个问题”，把请求发回客户端，客户端代理给 LLM，再把结果交回服务器，服务器返回工具结果。Pydantic AI 在客户端和服务端两侧都支持 Sampling（当时还是一个待合并的 PR）。

演示：查询 PyPI 下载量的研究 Agent

  • 场景：一个研究开源包的 Agent，其中一个工具查询 BigQuery 上的 PyPI 公开数据集来统计下载量。
  • 工具内部是一个 Pydantic AI Agent：系统提示词里放表结构和示例；输出校验器会去掉 SQL 外的 Markdown 代码块、检查表名，然后真的执行查询，失败就抛出 ModelRetry 让模型重写。
  • 依赖类型声明为 MCP 的 Context，所以在校验器或工具里可以类型安全地调用 ctx.log，在工具执行完之前把进度日志发给用户。MCP 还有 progress 概念，这次没用。
  • 结果转成 XML 风格的文本返回，他说模型很擅长读这种格式。
  • 服务器用 MCP SDK 内置的 FastMCP（他提醒现在有两个叫 FastMCP 的东西），函数的 docstring 会变成发给模型的工具描述，默认通过 stdio 运行。
  • 他强调把生成 SQL 的推理放在工具内部：如果把表结构和查询指令都塞进主 Agent，主 Agent 每次调用都要背这些上下文，不管用不用这个工具。
  • 主 Agent 注册这个 MCP 服务器作为工具，并告诉它今天的日期（否则模型常以为是 2023 年）。

现场网络超时了好几次，他换成有线网后跑通，得出 Pydantic 今年约 16 亿次下载。在 Logfire 里（展示的是上台前的那次运行），可以看到外层 Agent 调 GPT-4o，它决定调用工具并只给出自然语言的查询描述；然后 MCP 客户端调用服务器，服务器里的 Agent 通过客户端代理调用 LLM，形成客户端、服务器、客户端、服务器的链路，还能看到它写出的 SQL。

14. Alex Volkov（Weights & Biases）、Benjamin Eckel（Dylibso）：MCP 的可观测性现状

直播位置 5:25:43–5:42:44 · Observable tools: the state of MCP observability

Alex Volkov 是 Weights & Biases 的 AI 布道师，也主持 ThursdAI 播客；Benjamin Eckel 是 Dylibso 联合创始人兼 CTO，他们做了 mcp.run，从一开始就在生产环境运行 MCP 客户端和服务器，Ben 之前在 Datadog 工作。两人用对话的形式讲。

问题

Alex 说他做 W&B Weave（LLM 应用追踪工具），但自从给 Agent 加了 MCP，以前端到端可见的执行过程变暗了。MCP 让工具越来越多，开发者越来越看不清 Agent 内部发生了什么。Ben 说 mcp.run 只能自己拼凑观测方案，看起来各家都在孤立地解决同样的问题。企业团队不会上线一个无法在客户之前发现安全和可靠性问题的东西，所以 MCP 要进生产，必须接入现有的可观测性平台。

Weave 的专有集成

Alex 宣布 Weave 支持 MCP：如果你同时开发客户端和服务器，只要在两边设置一个环境变量，就能看到工具列表调用和每次 MCP 调用的耗时，目前支持 Python 客户端。但服务器内部还是看不到，而且这是 Weave 专有的。于是他发起了 observable.tools 宣言，呼吁可观测性厂商用中立、标准的方式解决这个问题。

OpenTelemetry 基础

Ben 说 MCP 驱动的 Agent 就是又一个分布式系统，行业几十年来已经定下了用 OpenTelemetry（OTel）观测分布式系统。几个概念：

  • Trace（追踪）：一次原子操作，由树状的步骤组成。
  • Span（跨度）：每个步骤的耗时和任意元数据，可以粗到一次 HTTP 请求，细到一个函数调用。他用一个结账 API 的追踪图举例，每个块的长度和位置分别表示耗时和调用关系。
  • Sink（汇聚端）：集中存储遥测数据的地方，通常是带 UI、仪表盘、告警的平台。可以理解成一堆支持同一个 schema 和协议的数据库，换平台通常只改配置。Weave、Logfire 等都已支持 OTel。
  • Distributed Tracing（分布式追踪）：结账例子里的风控服务也把 span 发到同一个 Sink，就能拼出完整上下文。

把 OTel 和 MCP 接起来

分两种情况：客户端和服务器属于不同的管理域（比如用 GitHub、Stripe 托管的 MCP 服务器），服务器在追踪图里只是一个黑盒 span；属于同一管理域时（服务器是你的，只是在另一个数据中心），可以让服务器把 span 发到同一个 Sink 拼起来。例子是“读取并总结 Hacker News 头条”的 Agent，拼接后能看到 fetch 服务器里一次约 350 毫秒的 HTTP 请求和生成 Markdown 的处理。

实现靠 Context Propagation（上下文传播）：客户端调用工具时取出当前 span，通过协议的 _meta 字段传给服务器；服务器取出这个追踪上下文作为父 span，再把自己的 span 发到 Sink。Ben 说这其实是借用了协议预留的底层接口，应该由更高层的工具来提供。代码在 GitHub 上有完整示例。Alex 用这个方法把 Ben 的 TypeScript Agent 接进 Weave：只要把 Weave 设为 OTLP 端点，加上鉴权头和项目名，几分钟就看到了客户端和服务器两侧的追踪。

一个意外

Alex 让 Claude Opus 4 给 Ben 的 Agent 加 Weave 追踪。Opus 4 跑代码，再通过 Weave 的 MCP 服务器查看追踪是否出现，发现某个参数显示不对，文档里也没写。接着它自己发现 Weave 的 MCP 服务器里还暴露了一个支持机器人（也是一个 Agent），写查询去问，拿到答案后修好代码，再回去验证。整个过程他没碰键盘。

宣布和呼吁

  • mcp.run 将把遥测导出到兼容 OTel 的 Sink。mcp.run 有 Profiles（把多个 MCP 服务器切分组合成一个虚拟服务器）和 Tasks（一个可通过 URL 或定时触发的单提示词 Agent 客户端）。
  • 总结：MCP 的可观测性今天可以做到，但分布不均，OTel 能解决大部分，社区需要更好的工具和约定。
  • AI 工程师要检查自己是否能看到端到端执行链；工具和平台方应合作做更高层的 SDK，Arize 的 OpenInference 是好的开始；参与 OTel 的 GenAI Semantic Conventions（语义约定：约定 span 属性的含义，让所有平台都知道某个 span 是 MCP 工具调用还是 HTTP 请求）。

15. Jan Čurn（Apify 创始人）：建立在 MCP 之上的 Agent 经济

直播位置 5:43:00–6:01:30 · The rise of the agentic economy on the shoulders of MCP

Henry 引入这场时说，Agent 要自主替我们做事，还缺一块：它们怎么替我们付钱、该用哪个 Agent。

智能从互动中涌现

Jan 从几个问题开始：神经元刚出生时只是单个细胞，后来长出轴突和树突、为了获取营养学会互相通信，大量神经元的集体行为就是智能；市场里的个体追求各自利益，集体表现出比个体更聪明的行为；公司里人们在 Slack 上互动，公司有时比单个员工更聪明。他的观点是通用智能会从多个 Agent 各自追求目标、相互交互中涌现，而 MCP 补上了让 Agent 互相通信的缺口。

Apify 和 Actor

Apify 是一个有 5000 个工具（称为 Actor）的市场，出身网页抓取，大部分 Actor 是数据提取工具（社交媒体、搜索引擎、给 RAG 管道的数据、获客数据），也有数据处理工具。一部分由 Apify 自己写，一部分来自社区开发者，他们靠这个赚钱。Actor 是基于 Docker 的独立软件，输入输出定义清楚，所以容易从各种系统调用：TypeScript、Python SDK，OpenAPI，CLI，以及 Make、Zapier、Clay 等自动化工具。比如 Google Maps 抓取器能拿到比 Google Places API 更多的数据。现在通过 Apify 的 MCP 服务器，Agent 有一个 API key 就能调用全部 5000 个 Actor。

工具发现是 MCP 的杀手功能

他说 MCP 相对 OpenAPI 最大的差异是工具发现：客户端连上服务器后按工作流动态发现要用的工具。5000 个工具不可能一次放进上下文，工具越多结果越不可靠，所以只能按需提供。支持的客户端还不多，他说 VS Code 当天、Claude Desktop 两天前刚支持。Google Trends 数据显示 MCP 的搜索热度压过了 OpenAPI 和 A2A。现在 MCP 服务器注册表多到 Mastra 团队做了“注册表的注册表”；Anthropic 在做官方注册表；Google 的 A2A 用基于 DNS 的 well-known agent JSON 来发布服务。

Agent 怎么付钱

问题在于：即使服务都支持 MCP，Agent 还是需要每个服务的 API token。比如 Zapier MCP 能接 5000 个应用，但你得自己先把 GitHub、Slack 等账号连上。Agent 无法自己找到交易对象，仍要依赖搭建系统的人类开发者。他认为如果 Agent 不能自己购买服务，就达不到更高层次的智能。他比较了三种方案：

  1. 让 Agent 自己去注册：要邮箱、信用卡、手机号、过验证码，很多服务还要求背后是真人，不现实。
  2. 中心化的身份和支付提供方：Coinbase 在推 x402 标准，Stripe、Mastercard、Visa 也在做。他认为终会实现，但新支付系统有市场的鸡生蛋问题，他提到 PayPal 当年每月要花约 1 亿美元买市场，1970 年代推信用卡也很难，所以会很慢。
  3. 中心化的 MCP 服务市场：用户只需要一个账号。开发者用自己的账号和信用卡接入第三方服务，发布到市场并定价，用户付费给 Actor，开发者拿钱再付给外部服务。目标服务甚至不需要知道。MCP 服务器可以嵌套，一个父服务器能暴露子服务器的工具。

17. Antje Barth（AWS 开发者关系副总裁）：在云规模上构建 Agent

Strands Agents

为了让团队能这么快上线，AWS 内部改用“模型驱动”的方式构建 Agent：依靠模型自己规划、推理、采取行动，开发者只描述 Agent 该做什么，不规定具体怎么做。几周前他们开源了 Python SDK Strands Agents，几行代码就能建 Agent。名字是 AI 自己起的：像 DNA 的两条链，把模型和工具这两个核心连在一起。

  • 用法：安装、导入、加上内置工具，就能提问或构建更复杂的工作流。默认模型提供方是 Amazon Bedrock（示例配置是 Claude 3.7 Sonnet），也支持 Ollama（本地开发）、Anthropic、Meta 的 Llama API、OpenAI，以及通过 LiteLLM 接其他提供方，还能自定义。
  • 20 多个内置工具，包括文件操作、API 调用、AWS 服务、记忆与 RAG。其中 retrieve 工具做知识库语义搜索。AWS 有一个内部 Agent 管理 6000 多个工具，不可能全塞进上下文，于是把工具描述放进知识库，用 retrieve 找出最相关的几个再交给模型选。
  • 支持图像、视频、音频多模态，有促使模型深度思考的工具，有基于图或 Swarm（一群子 Agent 协作）的多 Agent 工作流工具。原生集成 MCP，A2A 即将支持。

演示：把 MCP 服务器放到 Lambda 上

AWS 的 MCP 服务器集合在 GitHub 的 awslabs/mcp。她先展示一个 stdio 方式的 FastMCP 服务器，只有一个掷骰子工具，参数是面数。她说自己刚知道 D&D 玩家常用 20 面骰（D20），演示由同事 Mike Chambers 做。

要扩展规模，就要和远程服务器解耦。有了 Streamable HTTP，在 AWS 上可以直接把服务器部署成 Lambda 函数，放在 API Gateway 后面，加上 Authorizer 鉴权（也可以用 Cognito），会话数据存在 DynamoDB 表里。代码用 AWS 开源的 MCP Lambda Handler，Lambda handler 里一行代码把请求转给 MCP 服务器；用 AWS SAM 部署，拿到 API Gateway URL。客户端用 Strands Agents 的 MCP 集成，传入 URL 和 Bearer Token，列出工具交给 Agent。让它掷一个 D20，结果是 7。

她说 AWS 已加入 MCP 指导委员会并贡献代码，开源博客有系列文章。她引用同事 Danielle 前一天关于“有用的通用智能”的演讲：所有数字交互的原子单位将是一次 Agent 调用。她设想每个人有自己的 Agent，连接 Agent 商店，和其他 Agent 一起完成任务。

18. Kevin Hou（Windsurf 产品负责人）：Windsurf 无处不在，什么都做

直播位置 7:34:26–7:50:31 · Windsurf everywhere, doing everything, all at once

Kevin Hou 说一年前还没有 Windsurf 编辑器，现在全球数百万人在用。他们弃用了原来的名字 Codeium，产品的大版本称为 Wave（浪），已经发到第 10 个，重要的包括网页搜索、MCP 支持、自动生成的记忆、部署、并行 Agent。现在每天生成约 9000 万行代码，每分钟发送超过 1000 条消息。他说今天不讲增长，讲原因。

共享时间线

他说的“秘方”是人和 AI 共享一条时间线，这让用户觉得 Windsurf 能读心。软件工程师做的每件事都可以放在这条时间线上。在补全出现之前全靠人；Copilot、Codeium 这类补全出现后，一小部分代码由 AI 写；2024 年底 Windsurf Agent 发布后，它能同时改多个文件、在几千个文件里做后台检索、直接在编辑器里执行终端命令。但开发者的大量工作发生在编辑器外。

无处不在：读取所有上下文

他把上下文分三类：编码相关（读文件、终端命令、历史、你打开了哪些标签页）；外部来源（GitHub 上的提交历史、类似功能的 PR、网页搜索、文档）；以及他称为 Meta-learning 的一类，即组织的最佳实践和工程偏好，这是初级、高级、Staff 工程师的区别。他举例：给数据可视化面板加一个新页面，会从 Slack 里的客户需求开始，到 Google Docs 写设计文档、Jira 跟踪任务、设计师在 Figma 出稿，然后写代码，再开 PR、评审、合并、部署、SEO 和分析。所以 Windsurf 要能读 Google Docs、Figma，并一键连接 Notion、Linear、Stripe 等 MCP 服务。

什么都做

  • 执行终端命令，并能判断哪些自动执行、哪些要等用户批准。
  • Browser Previews：Agent 能像人一样控制 Chrome，检查 DOM、看 JS 控制台。
  • 用 GitHub MCP 开 PR，参考其他 PR 写描述和测试计划。
  • Windsurf Reviews：异步自动评审代码、留评论、建议修改。
  • 一键部署到 Netlify。

一直在线

他说今天时间线上大约 80% 到 90% 是 Agent、10% 到 20% 是人，目标是 99% 对 1%，只在最后请用户批准。Windsurf 会在后台研究、并行工作，你在床上、在公交上、用语音也能写软件。

SWE-1 模型

他认为业界盯着 SWE-bench 这种“tokens 进 tokens 出”的任务，而真实的软件工程更乱：要从工作流中途接手、面对提交到一半的代码库状态、使用编辑器之外的工具。现成的前沿模型处理不好 Windsurf 自己的时间线表示，所以他们训练了自己的软件工程模型 SWE-1，训练目标是完整的软件工程工作流，代码生成只是其中一部分。两个离线评测：

  • 端到端任务基准：给定意图和代码库起点，做到通过所有单元测试，类似处理一个 PR。
  • 对话式 SWE 任务基准：模型被放进一段已有的用户对话或做了一半的任务里，能帮多少忙，综合打分有用性、效率和正确性。

他说 SWE-1 以小得多的团队和一小部分成本达到接近前沿模型的结果；用户在模型下拉菜单里选它的频率高于 Claude 3.7 和 3.5（字幕只说“3.7 和 3.5”）。他描述的飞轮是：发布最好的产品，用户通过点赞、点踩、接受、拒绝告诉他们软件工程的前沿在哪、缺什么工具、哪些流程重复、产品哪里不足；他们据此训练更好的模型、做更多工具、改进 Agent Harness（包在模型外的执行框架）、记忆和检查点，然后循环。他说 2025 年做 AI 产品需要模型、数据和应用协同，应用本身要模拟你希望模型学会的用户行为。Windsurf 在招聘。

为什么相信 AGI

他读了 Alan Turing 1950 年的论文《Computing Machinery and Intelligence》（图灵测试那篇）。打动他的部分是 Turing 说你永远写不完所有规则，但可以造一个像人类孩子一样学习的“儿童机器”，再给奖励和惩罚。程序员必须理解所有规则，而机器如果能理解和解决你自己都无法理解的问题，才是解决人类重要问题的方式。2008 年左右他去找一位 NLP 教授做研究，对方给了他一堆句法分析树，他觉得这不是 Turing 说的东西。

转折是 2012 年 AlexNet 在 ImageNet 比赛中大幅领先。一个只带一点卷积先验的通用学习机器，超过了 40 年计算机视觉研究里人工写规则的成果。之后机器翻译、NLP 等领域都说“对我们没用”，结果它在每个领域都成了最好的，学科之间的墙倒了。他说神经网络并不新，1943 年 McCulloch-Pitts 神经元论文里的图和今天的很像；1990 年代有论文批评神经网络的人“没有新想法，只想造更大的计算机”，他的反应是：对，这就是需要做的。

工程师和研究员

swyx 问他 2022 年写的“现在是成为 ML 工程师的时候”是否还成立（swyx 有朋友读了那篇文章后冷邮件联系他，加入了 OpenAI）。Greg 说比以前更成立。AlexNet 本身的核心就是在 GPU 上写出快速卷积核的工程；当时实验室里有人同情 Alex Krizhevsky，觉得他在给一个不重要的数据集写快速卷积核，而 Ilya 说显然该用到 ImageNet 上。好的工程加上知道用它做什么的想法，才有了突破。现在的工程除了写 kernel，还要扩展到 10 万张 GPU、编排复杂的强化学习系统。没有想法就没有方向，没有工程想法就见不到天日。

早期 OpenAI 的问题是两类人对系统约束的理解不同：工程师认为接口定好了，背后怎么实现你不用管；研究员认为系统里任何地方有 bug 都只会表现为性能略降，没有异常也没有线索，所以必须理解全部代码，除非接口稳到可以永远不管。有个项目里工程背景的人写代码，每一行都要辩论。后来他的做法是一次提五个想法，研究员说其中四个不行，他说这就够了。他说这种问题每个实验室都会遇到，只能逐级解决。他给从工程转来 OpenAI 的人的建议是技术上的谦逊：先认真听、认真读，假设自己漏了什么，真正理解原因后再去改架构和抽象。

扩容和发布

  • swyx 说 ChatGPT 发布 5 天 100 万用户，今年 GPT-4o 图像生成 5 天 1 亿用户。Greg 说两次很像：ChatGPT 本来是低调的研究预览，他们以为要等 GPT-4 才会火，因为内部已经有 GPT-4，对 3.5 没那么惊艳。两次发布他们都做了平时尽量不做的事：从研究那边调走算力，他说这是在抵押未来，但能让用户体验到魔法。
  • GPT-4 发布会上那张手绘的笑话网站草图是他妻子画的，因为他的字太丑，连 AI 都认不出来。他说做演示时会预先测试大致形状，但不喜欢那种打错一个字就失败的演示，现场会有变化。

Vibe Coding 和 Codex

swyx 说那是世界第一次看到 Vibe Coding（用自然语言让 AI 写代码、不细看代码本身的开发方式）。Greg 说 Vibe Coding 是很好的赋权机制，代表了将来的方向，但具体形式会变。当 Agent 真正可用后，你会同时跑 100 个、1000 个、10 万个，像对待同事一样让它们在云端工作，你睡觉、合上电脑时它们还在干活。他认为交互式 Vibe Coding 会越来越多，但 Agentic 的方式会赶上并超过它。他说现在的 Vibe Coding 演示多是从零做应用，真正新的是改造已有应用：很多公司坐在遗留代码库上，做迁移、升级库、把 COBOL 换成别的语言，对人来说又难又无聊，AI 开始能处理这些了。

关于 Codex，他说这是一个出色团队的成果，他只是支持者。最有意思的发现是代码库的结构决定了你能从 Codex 得到多少。现有代码库都按人的长处组织，而模型的能力很不均衡：能处理更多样的东西，但连接深层想法不如人。所以应该拆成更小、测试充分、测试跑得快的模块，架构图这种模块间连接人来定，细节交给模型，它会自己跑测试，跑的次数比人多一百倍、一千倍。他说这听起来就是好的软件工程实践，只是人能在脑子里记住更多抽象，所以常偷懒；换句话说，要按更初级的开发者来组织代码库。他想看的是，哪些以前偷工减料的工程实践需要找回来。

数字：OpenAI 内部有低两位数百分比的 PR 完全由 Codex 写；公开 GitHub 仓库里前一天合并了约 2.4 万个 Codex 的 PR。他说这还在很早期。

嘉宾提问：长时程训练的可靠性（Dylan Patel）

Dylan Patel 问：任务越长、用的 GPU 越多，失败越多，长时程 Agent 训练中轨迹做到一半而且不确定，没法简单重启，怎么办？Greg 说每次模型变强就要重新解决一遍：Rollout（一次完整的试跑）只有 30 秒时不在乎，几天时就很在乎，需要考虑如何快照状态。传统预训练很好做检查点，但要每一步都存也得避免拷贝和阻塞；强化学习系统可以把缓存存下来避免重算。语言模型的状态是显式的，可以存；麻烦在于接入的有状态工具可能无法恢复。也可能根本不重要，重启后曲线抖一下，模型足够聪明能处理。swyx 提到第二天会发布的东西可能允许接管 VM 并给 VM 状态做检查点。

嘉宾提问：Jensen Huang 的两个问题

Nvidia 的 Jensen Huang 录了视频。第一个问题：数据中心的负载会极其多样，有的是深度研究、长时间推理、大上下文，有的是要随时在线、低延迟的多模态语音视觉助手，理想的 AI 基础设施应该是什么样？Greg 先开玩笑说“很多 GPU”。他说自己是做软件的，没想到做 AGI 要做这么大的基础设施项目，但想想也合理。简单答案是两种加速器，一种算力优化，一种延迟优化（配大量 HBM 显存）。难点是预测比例，配错了一部分集群就闲置。但这个领域没有硬约束，只是在解一个线性规划，资源比例不对，工程师也会想办法用上。例子是 MoE（混合专家模型：每次只激活部分参数）：DRAM 闲着就塞满参数，不增加计算却提高效率。他说同构加速器是好的默认，但随着资本开支大到惊人，为特定负载做专用加速器也合理；只是研究变得太快，主导一切。

swyx 追问 GPT-6 的瓶颈排序：算力、数据、算法、电力、钱。Greg 说基础研究回来了。之前有一段时间是“有了 Transformer 就扩大规模”，他喜欢这种目标明确的难题，但智识上不太满足。现在算力和数据推得够远，算法又成了关键的长杆。他举了强化学习：第一次和 GPT-4 对话时他们问“这是 AGI 吗”，显然不是，但说不清为什么，它很流畅却会跑偏。他们的判断是它从没亲身经历过世界，像只读过书、隔着玻璃看世界的人，所以需要新范式，于是持续多年投入 RL 直到跑通。他说现在仍有其他明显缺失的能力，继续推就能做到。

第二个问题：OpenAI 有了 AGI 之后，开发者会在其上做领域专用 Agent，开发流程会怎么变？Greg 说各种互相矛盾的强烈观点都有，一切都有可能：可能 AI 强到写所有代码，可能天上只有一个 AI，也可能是一堆需要专门工作的领域 Agent。他说证据越来越指向一个由不同模型组成的“动物园”：推理成本不同，取舍不同，蒸馏效果很好，模型调用其他模型有很大空间。经济会由 AI 驱动，他说重点不在现有工作里人和 AI 各占多少，他关心的是怎样得到 10 倍的活动、10 倍的产出、10 倍的收益。医疗需要负责任地进入，教育有家长、老师、学生多个利益相关方，这些都需要领域知识、细致思考和大量工作，所以会有很多机会给在座的人。

对谈后，赞助商 Tollbit 的联合创始人上台做了一分钟派对宣传：他们过去两年连接大型出版商和 AI 公司，现在让 Agent 通过 MCP、A2A 或浏览器自动化访问授权的第一方数据并完成鉴权和支付。
