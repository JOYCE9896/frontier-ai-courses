02. SallyAnn DeLucia（Arize AI 产品负责人）：做 Alyx 学到的四课

直播位置 0:08:36–0:24:10

讲者和 Alyx

SallyAnn 是 Arize 的产品负责人，数据科学出身，既是 Alyx 的产品经理，也是核心贡献者，所以说自己“亲身知道造 Agent 有多痛”。Arize 做三件事：可观测性（Observability，看清 Agent 内部每一步发生了什么，通常靠记录 Trace，即一次运行中每个模型调用和工具调用的完整记录）、评测（Eval，衡量 Agent 表现好不好）、再用这些数据帮用户改进。Alyx 横跨整个平台，她称之为“AI 工程 Agent Harness”：用户用自然语言让它分析数据、迭代提示词、对齐评测器。团队做了三年，从生成式 AI 刚起步做到现在带推理和规划的 Alyx 2.0。她这次讲四课：保持在任务上、上下文管理、把好的行为固化下来、调试真实的 Agent。

第一课：保持在任务上

每个做 Agent 的人都见过这种情况：让它做几件事，第一件做好了，后面两件忘了。她说这常被当成幻觉问题或能力问题，其实是注意力问题：后面的要求被淹没在大量数据里，Agent 想清楚下一步时已经忘了下一步是什么。她们的解法是规划，在动手拉数据之前先写出明确的待办清单。

  • 三个工具 todo_write、todo_update、todo_read，四个状态：pending、in progress、completed、blocked。她说这个思路借鉴了 Claude 这类工具。一开始只有 pending 和 completed，后来加上 in progress，让 Alyx 明确知道自己当前在做哪一项，完成率明显提高。
  • 计划放在对话历史之外。对话历史会被截断，计划不能被截掉，所以每次调用 LLM 时都把计划紧跟在系统指令后面注入，和对话数据分开。注入的内容里还带着明确的指导，比如“做完这项就调用 todo_update 把状态改成 completed”，相当于给它一个随时可见的少样本示例。
  • Finish gate：Alyx 如果在待办没做完时调用 finish 工具，会收到一条明确的结构化报错，要求回去把待办做完。她强调这是一个硬性的拦截，不是提示。唯一例外是 blocked 状态，用于需要人参与的环节，比如生成了提示词的 diff 等用户接受，或者需要人填写标注配置。

她总结的几条：用代码强制，不要只靠提示词；少样本示例好过抽象指令；只给一个 todo_write 不够，要有完整的函数并示范什么是好的规划。

第二课：上下文管理

Alyx 处理的是 AI 应用的可观测性数据，几乎全是文本，所以上下文管理是硬需求（她提到之前在伦敦专门讲过一场）。早期她们在系统提示词里写“一次比较的实验不要超过两个”，但 Arize 里一个实验可能有几百行，相当于十万 token，比一个实验就能把上下文窗口撑爆。于是她们做了几个抽象：

  • Large JSON：工具返回的数据大部分存在服务端内存里，只给 Agent 一个 ID，需要时再取。最初的做法是截取前 N 个 token 当预览，但 Agent 看不到数据结构，就不知道下一步该查什么。改进后的原则是“压缩值，不压缩结构”：保留所有字段和数组，只截断其中很长的字符串。
  • 小而可组合的工具：给 Alyx 两个工具，一个是命令行里常用的 jq，一个是能对序列化数据做正则搜索的 grep JSON。工具很小，但可以把一个的输出接到另一个的输入，完成切片、聚合等操作。她的比喻是工具像 Unix 小程序，Agent 像 shell 脚本。

经验：每个工具输出都设硬性 token 预算（她们统一是 1 万 token），这样不会溢出，只会多几轮；压缩值不压缩结构；不要用人为限制掩盖问题，要在反馈回路里给出好的异常信息；工具返回里可能有客户数据，要注意日志。

第三课：把好的行为固化下来

早期她用电子表格和 Google 文档手工测试，很快发现“凭感觉检查”（vibe check）没法扩展，每次改动都不知道会不会弄坏什么。她们后来把生产环境的 Trace 当作标准答案的来源，代替手写的黄金答案。测试分三层：

  • 决策点测试：单测一个组件，经过编排器后检查结果。不用精确匹配，用“包含任一”这类开放检查，比如时间戳可能写成 2000 毫秒、2 秒、2 s。
  • 轨迹测试：保存生产中的完整轨迹，逐行步进，用 LLM 当评审（LLM-as-judge，让另一个模型按评分标准判断输出好坏）评估每一步。她说评测提示词要能处理不确定的输出，并为每一步定义什么算成功。
  • CI 和提示词验证：所有测试都放在 Arize 里，既能临时跑，也在 CI（持续集成，每次提交代码自动跑测试）里跑，还能看随时间变化的可视化。她说这是在“吃自己的狗粮”。

经验：保存好的用户会话；匹配事实而不是匹配措辞；语义层面的评估用 LLM 评审；用真实 API 不用 mock，因为集成里的 bug 是真的。

第四课：调试真实的 Agent

她把谁在读遥测数据的变化分成三个阶段：最早是人直接看数据、回 IDE 改代码；然后是用 Agentic IDE，人还在环里但借 Agent 迭代；现在是第三阶段，Coding Agent 直接读 OpenTelemetry 数据并迭代。她们的做法是 Arize Skills（Skill 是写成 Markdown 的说明文件，教 Agent 完成某类任务），让 Cursor、Claude Code 直接和 Arize 交互：拉取 Trace 和完整会话、找出失败的节点，也能读 Datadog 的 APM Trace 和 Google Cloud 日志。她举了一个内存溢出的例子，从发现问题到定位根因很快。Agent 提出修复，她和工程师只做审查。

经验：Skill 只是 Markdown，成本低、价值高；安全必须靠包装层，不能靠提示词；调试 Agent 本身就是一个适合 Agent 做的问题；可观测性要在需要之前就建好，没有可观测性就没有评测。

03. Timothy Lin（Resaro）：给关键任务 AI 做场景化评测

直播位置 0:24:54–0:35:00

Resaro 和问题

Resaro 是一家测试评估公司，客户主要在医疗、国防、安全这类关键任务领域，帮他们测试自研或采购的 AI 系统，让他们有信心上线。Timothy 分享过去几年的体会：问题在哪、怎么克服、扩展用例专属评测还卡在哪里。

基准刷分和凭感觉测试之间

他用一张幻灯片开场：眼镜蛇、冲刺速度追踪和 AI 基准测试有什么共同点？都是反向激励。悬赏抓眼镜蛇，人们就去养眼镜蛇；经理要求提高故事点，数字上去了，实际产出没变；开源模型在基准上的分数和你自己的用户测试常常对不上，这就是现在越来越常说的 benchmaxxing（为了刷榜而针对基准优化）。另一头是 vibe testing：心里有几道刁钻题，比如 strawberry 里有几个 r、画一只骑自行车的鹈鹕。他说这些其实挺有用，能看出模型在某方面的表现，也鼓励探索。但“鹈鹕骑自行车”和“犀鸟坐嘟嘟车”测的是同一件事吗？是只测鸟和交通工具，还是测更高层的概念？他认为要明确每个测试用例到底在测哪些维度，这就是两者之间的中间地带。

ODD 和数据管线

他们借用了运行设计域（ODD，Operational Design Domain，原本来自自动驾驶，指系统被设计在哪些条件下运行）的概念：先定义问题的约束空间，决定哪些测试用例有意义；再定义系统的预期行为、要注意的边缘情况、以及完全超出系统范围不该使用的情况。然后把 ODD 转成测试用例，接上数据质量检查过滤不合格数据，找出覆盖缺口并补齐。越是关键任务，边缘情况的测试数据越少，这时就靠合成数据来补。他说这样一来，问题从“怎么评测”变成了“数据是瓶颈”：怎么生成能让人放心上线的测试用例。

坦克图片的例子

他举的例子是评估一个视觉模型在战场场景下的表现，原图里有一辆坦克。好的增强会按提示生成雨、雪、雾三种天气，主体保持完好，没有多余的伪影。差的增强里会凭空多出两个人，或者坦克被改成了普通车辆，雨丝也不真实。要从肉眼判断变成结构化地找出这些缺陷，他们尽量依赖更小的确定性模型：比较两张图主体的结构图是否有实质变化，检查生成图里有没有新冒出来的物体。用这些信号过滤数据，还可以用积累下来的反馈微调一个评估模型，把筛选自动化，甚至反过来改进生成模型。

最后他们组装出一整套针对不同用例的指标，成为可复用的工具箱。他把这和代码、数学推理领域类比：尽量把验证自动化，减少人工监督；人的反馈用来改进自动化模型。他还说每个用例里每个指标的阈值分布差别很大，所以校准是一个重要的统计问题。他的结论是，难点在于扩展合成数据生成，同时加上足够的质量检查。

04. Abhishek Kankani（Cloudflare 新兴技术与孵化团队负责人）：Code Mode

直播位置 0:35:50–0:48:10

标准工具调用的成本

Abhishek 带 Cloudflare 的新兴技术与孵化团队，同时负责印度办公室。他先确认台下都知道 MCP（Model Context Protocol，Anthropic 提出的让模型接入外部工具和数据的开放协议）和工具调用（Tool Call，模型输出一个结构化请求，由程序替它去调某个函数或 API）。标准流程是模型说要调某个工具，请求发到 MCP 服务器，拿到结果再还给模型。他举了一个生产场景：一个长期运行的 Agent 监控每次发布，按错误率决定是否回滚。这样会产生一串顺序执行的工具调用：列日志、取指标、做条件判断、决定下一步。每次调用都要把整段对话加上调用和结果再发一遍，上下文越来越大，既烧钱又增加往返延迟。

Code Mode 的思路

他的论点是模型更擅长写代码，因为训练数据里有大量真实代码，而工具调用的训练数据大多是合成的。Cloudflare 有一个叫 Code Mode 的库，把工具定义（名称、描述、参数、输出）转换成 TypeScript 类型：工具名变成函数声明，描述变成注释，参数和返回值变成类型。模型拿到的是一个叫 code mode 的单一工具，原来那一组工具都收在里面，里面是这些类型的字符串。模型写一段代码，就能完成原来五到八轮的调用。代码还能带逻辑：变量让后一个调用依赖前一个结果，可以分支（错误率高于阈值走一条路），可以循环（列出账户里所有 Worker 再逐个取指标，原来要几十次调用，现在一个 for 循环），也能把互不依赖的任务并行。现有工具不用换掉，整套包起来交给 code mode 就行。

他特意强调 Code Mode 不替代 MCP。MCP 是底层协议，最后一公里的 API 调用还是由 MCP 服务器完成；Code Mode 只是给模型一种更好的方式去发起调用。

2,500 个 API 压到 1,000 个 token

Cloudflare 有超过 2,500 个 API。直接做成 MCP 工具，光工具描述就有 170 万 token，大部分模型的上下文窗口都放不下；就算转成 TypeScript 类型也一样。他们的办法是只给两个工具：search 和 execute，两个工具里模型都可以写代码。完整的 API 描述放在一个全局变量里，不发给模型；模型写代码去过滤出要用的那个接口，再写代码执行。这样整套 Cloudflare API 只需要大约 1,000 个 token 就能让模型调用，他说是 99.9% 的压缩，自己从没见过这种幅度。

代码在哪里跑

他说放在 AI 之前，有人让你在自己机器上跑一段用户生成的代码，那就是一个远程代码执行漏洞；现在他却在鼓励大家让模型写不受信任的代码再去执行。所以需要一个高效、安全的沙箱（Sandbox，与主系统隔离的执行环境）。容器的问题是冷启动慢，内存和算力要提前规划，交接也麻烦。另一种是 V8 isolate（Chrome 的 JavaScript 引擎 V8 提供的轻量隔离单元）。Cloudflare Workers 就是基于 V8 isolate 的无服务器运行时。他说 dynamic workers 冷启动几乎为零，会在主应用所在的同一位置启动，每个 isolate 可以只服务一个请求就丢掉；创建时可以决定传给它什么权限和能力，不会泄露密钥，也不会把恶意代码带进主系统。因为运行时是 Cloudflare 自己的，信息交换做起来更容易也更安全。

05. Tejas Kumar（IBM AI 工程师）：从第一性原理讲 Agent Harness

直播位置 0:48:50–1:07:50

为什么需要 Harness

Tejas 住在柏林，前一天在罗马尼亚，飞了 16 小时过来。他现在是 IBM 的 AI 工程师，IBM 做基础模型和 Harness，他负责面向开发者社区教这些东西。开场他问谁有信心解释 Agent Harness，只有三个人举手，他说讲完再问一次。

他从“为什么”讲起。登山用安全带是为了能可靠地上下山，遛狗用牵引带是为了它不跑丢，Harness 的目的就是可靠性。做 AI 时我们大多在信任黑箱：除了少数在本地跑推理的人，大家都是把提示词发给某个厂商，然后祈祷结果。他说你以为在调 Claude 4.7 Opus，厂商出了事故可能给你换成 Sonnet，你根本无从得知，只会觉得“Opus 今天感觉不对”。Harness 让你多一些控制。机器学习里早有 eval harness，基本是给模型用的单元测试；Agent Harness 是更新的概念，他的定义是：Agent 周围的一切，包括工具链和执行环境，让 Agent 有最大机会成功、最可靠。

他列了常见 Harness 至少有的六个部件：

  • 工具注册表：比如 Claude Code、Codex 都有读写文件、搜网页的工具。
  • 语言模型。
  • 上下文管理原语：压缩或清空上下文，比如 Claude Code 的 /compact。
  • 护栏（Guardrails）：最常见的就是“额度用完了，充值之前我不回你”。
  • Agent 循环：做完一个任务后判断是真的做完了还是再跑一遍。
  • 验证步骤：比如做完后自动跑 npm run verify。

现场搭一个：在 Hacker News 上点赞

他说听腻了自己说话，于是现场写代码。任务是做一个浏览器 Agent，打开 Chromium，去 Hacker News 给第一篇还没点赞的文章点赞。他故意用很老很便宜的 GPT-3.5 Turbo 和一个写得很差的提示词，并且整个过程中模型和提示词都不改。他的观点是：Harness 让你用更少做更多，好的 Harness 能赢下 70% 的仗，不用拼命改提示词、加 Skill。

第一次运行：浏览器打开 Hacker News，点赞时跳到登录页然后崩了，但 Agent 回答“我已经给排名最高的文章点了赞”，他说这是彻头彻尾的谎话。代码结构很简单：用 Playwright 编程控制浏览器（不是 Playwright MCP），创建工具（一组带描述的 JSON 对象），创建上下文（只是系统提示词和用户提示词两条消息的数组），然后跑 Agent 循环，也就是 while (true) 一直推消息，直到模型说完成为止，途中把每次工具调用、每条消息都推进一个列表。

他接着分三步加 Harness：

  • 护栏：新建 guardrails.ts，设最大迭代次数和最大消息数，每轮检查，不通过就停下并说明原因；每条消息都调用 trimContext，只保留系统提示、用户提示和最近两条消息。他说这种裁剪方式很糟，实际别这么做，这里只为演示护栏。有了 Agent 加护栏，这就已经叫 Harness 了，于是他把代码挪进 harness.ts，入口改成 runHarness。
  • 让它说实话：浏览器会话归 Harness 控制，Agent 管不到，所以 Harness 可以检查事件列表来判断成败。加上一个 verifySuccessfulUpvote：如果事件里有点击了 up 箭头的元素，就判为成功；如果停在登录 URL 上又没有自动登录记录，就返回失败“停在登录页，没有完成点赞”。最多尝试三次。再跑一次，结果如实报告失败。
  • 修好它：新建一个 login handler。不在登录页时什么也不做；在登录页时，Harness 直接往输入框填用户名和密码，然后往消息链里注入一条名为 harness_auto_login 的消息，告诉 Agent 已经登录、回到首页。Agent 读到后继续工作。最后一次运行，点赞成功并经 Harness 确认。

他重申：没改提示词、没换模型，还是 GPT-3.5 Turbo，只是多了控制。他在 IBM 做的一个实际例子是 OpenRAG，一个开源的企业级 RAG Harness。RAG（检索增强生成）是先从文档库检索相关内容再交给模型回答；企业数据量大、分散，还分不清哪些是机密，风险高。讲完他再次请台下举手，几乎全场都举了。他最后提了一个展望：今天的 Harness 是手写的，未来 Agent 也许能动态生成自己的 Harness，他认为这可能是通往 AGI 的下一步。

06. JJ Geewax（Google DeepMind 应用 AI 工程总监）：用确定性包住不确定的模型

直播位置 1:32:42–1:52:45

团队做什么

JJ 是 DeepMind 的工程总监，在新加坡带应用 AI 团队，正在招人。团队负责把 DeepMind 的模型推过它们原本的设计边界：Gemini、开放权重的 Gemma，还有 Nano Banana（图像）、Veo（视频），以及更偏科学的 AlphaGenome 和预测天气、飓风的 WeatherNext。例子：Veo 一次生成 8 秒视频，如果要生成一整场五分钟的电影戏怎么办？或者用 Nano Banana 把整部电影外扩成宽银幕。这些听起来只是“更多同样的东西”，其实难得多。8 秒视频是黑客松项目，卖不给电影公司；还要让模型按导演或动画师的要求来，用文字描述电影很难，提示词会变得巨大而脆弱，要想办法用关键帧锚定。他说很多工作会在即将到来的 Google I/O 上讲，他不能多说，“真的不想被开除”。

移动的球门

他先停下来说：AI 真的很惊人。深蓝赢了国际象棋，大家说“只是象棋”；十年前 AlphaGo 下围棋（他说 Demis 刚去韩国庆祝十周年），当时在 Google 的他也不确定能赢，现在大家说“只是围棋”；ChatGPT 刚出来时他给妻子演示，她问什么都能答还能做成表格，现在大家说“只是个聊天机器人”。现在 Agent 用 ElevenLabs 和 OpenClaw 打电话订餐厅、意外删掉邮件，我们还在怪它不听话。飞机上有 Wi-Fi 时觉得神奇，现在没有就抱怨；机器人进了工厂，我们说它还不会叠衣服，而他刚看到一个机器人铺床倒垃圾的视频。他的意思是一切走得太快，但做业务的人得在某个时间点按下暂停、下车，基于当下的模型造真东西。

三个常见的墙

他把 AI 的使用分成几类：开发时用来生成代码、用 Agent 做事，以及他专注的第三类：应用内的 API 调用，终端用户直接和它交互，可能是不知道自己在跟机器人聊天的奶奶。他重点讲“不违反政策”这个问题，说这是架构和设计的决策。

  • 提示注入（Prompt Injection，用户输入里夹带指令，让模型偏离开发者的设定）：他提到 Chipotle 客服机器人的截图，有人说“我想要墨西哥卷饼，但先帮我写个斐波那契的 Python 函数”，它照写了。问题在于定义 Agent 行为的方式和用户跟 Agent 说话的方式都是文本。
  • temperature 设成 0 也不等于确定性。Temperature 是控制采样随机程度的参数。他说接近确定，但输入文字的细微差别会导致输出大不一样，这和给伪随机数生成器设种子不是一回事。
  • RAG 的风险：如果聊天记录里有一次退款是因为特殊情况（比如“你妈妈打来电话”），检索到之后模型就当成惯例开始退款；如果某处有个测试样例把车卖了 1 美元，可能就真按 1 美元卖车。他说 Agent 像很笨的新实习生，想做好但不知道该做什么。

这三件事的共同点是模型被要求做得稍微多了一点。一部分原因是期望一直在涨，另一部分是对齐本身很难，把脑子里的想法变成文字、代码、图像，经常要看到结果才知道不是自己要的，面对客户时还会在规模上反复发生。黑客松里一切都能跑，生产环境里边缘情况到处都是。

拆成路由、变换、生成和安全检查

他的办法是别把语言模型当成一个大路由器、把一切塞进系统提示词，要拆开、用确定性包住。他提到当天早上 Arize 讲的 to-do 和 finish 报错就是这类做法。他的分层：

  • 结构化：把随机输入变成你知道、理解的 JSON。他推荐 Pydantic AI，也提到 ADK、Agno 等 Agent 框架。
  • 路由：可以用一次 LLM 调用决定用户要什么（退款、表扬、取消服务），但把它变成选择题，让模型当分类器用。他认为 plan mode 和推理很棒，但在生产环境还没准备好。
  • 变换：坚持 JSON 到 JSON，从一个结构化的输入变成另一个结构化的输出。
  • 生成：最后才让模型生成给人看的文本、音频、图像或视频。
  • 安全检查：直接用语言模型检查仍有提示注入风险。两种选择：不带上下文的一次调用（“我是一家车险公司，这是要发给用户的话，可以吗？”），这样没有注入的口子；或者用更小、更有针对性的 ML 分类器。他说 Cloudflare 等公司也在做这类事。

同样的模式适用于图像和视频。他提到一个不能细讲的项目：处理手机摄像头的实时画面并给出语音反馈。手机上跑的是笨但快的小模型，每秒 50 帧、50 毫秒内响应，能判断深度、前方有凳子或障碍；Gemini 能精确理解画面但有网络延迟，首 token 时间远超 50 毫秒。他们把问题拆成两半：大模型处理关键帧做语义理解，小模型吃整个视频流做实时的安全和避障。

他的收尾：把语言模型用在难的部分，把确定性用在不能妥协的部分。“不能跟客户说别担心，我在提示词里加了‘不要违法’。”反过来，开发阶段可以让 Claude、Gemini 或 Codex 按这些思路去搭系统。他也提到没展开的两件事：微调（Fine-tuning）很好但要用在合适的地方，比如做安全分类或输出风格的小模型，不要拿烂数据去微调巨大的模型；评测如果先写就像 AI 版的测试驱动开发，但需要黄金数据集。最后一句：别等完美的模型，它不会很快到来，现在的模型已经够用了。

PI 是维也纳的 Mario 写的编程 Agent，看起来和 Codex、OpenClaw 差不多。大家最先注意到的是它没有的：没有 MCP、没有子 Agent、没有权限弹窗、没有 plan mode、没有内置 to-do、没有后台 bash。他说重点是你让它自己做。他前一天的例子：让 PI 写一个扩展，在推送到远程 main 分支时先问权限。PI 读了相关文档、写好扩展、加载（实际要 reload 一下），之后再推送时就会弹出确认。

  • 聊天：问一个问题，加一些总的指令。

OpenClaw 的结构大致是：消息从 WhatsApp、Telegram、Discord 进来，经过网关，右边是一堆工具和数据、记忆，核心的“大脑”就是 PI。他举了 Peter 的例子：Peter 发了一条语音，OpenClaw 回了文字。过程是读到一个文件，判断是语音，转成 wav，用 Whisper 转写；那次 Whisper 没返回结果，它就改调一个 API 把语音转成文字。他说我们看到的魔法，本质就是在循环里调用工具。

14. Pierre-Loic Doulcet（LlamaIndex 创始工程师）：LlamaParse 在规模上踩到的坑

直播位置 3:25:50–3:35:50

LlamaIndex 最早是开源框架，现在主攻文档 AI。过去两年他们在生产环境处理了超过十亿份文档，每份都有自己的 Agentic 循环。难点在于 PDF 里没有结构化内容，只有页面上单词的边界框，必须重建成可用的东西。从 2024 年初起，他们把 LLM、视觉语言模型（VLM，能同时看图和读文字的模型）、OCR（光学字符识别）等多种模型和技术组合进 Agentic 循环来做解析。这场讲的是生产里经常坏、但很少被讨论的几件事。

输出循环，尤其是空格循环

LLM 和 VLM 喜欢在输出上打转，大约 1% 或 0.5% 的请求会返回重复内容，直接搞坏工作流。最糟的是空格循环：模型无限输出空格，把 token 预算烧光。他说 Anthropic 的 Sonnet 系列对此特别敏感。因为分词器的原因，空格几乎是唯一不能设成停止序列（Stop Sequence，遇到就停止生成的字符串）的字符：大部分前沿模型和开放权重模型都有表示 1 个空格、2 个空格直到 128 个空格的 token，只放空格做停止序列，大多数 provider 或模型会拒绝请求。办法是始终用流式输出，对每个到来的数据块在中途跑启发式检测，发现重复就尽早掐断，不然可能为空格花掉 12 万 Opus token；然后换模型、换提示词或换 temperature 重试。思考过程里的循环更难，因为很多 provider 已经不再流式返回思考内容，只能靠 max tokens 限制，设低了拿不到想要的输出，设高了在思考循环上烧更多钱。

模型盲区

  • 如果内容或 RAG 的分块里同一个字符串出现两次，两处之间的内容有时会被模型完全忽略。他说所有模型都有这个问题，程度不同，盲区也不同，所以可以换模型。改提示词没用，他认为这是注意力结构导致的。
  • 色盲：很多视觉模型分不清某些颜色，尤其在红色区间，人很擅长区分不同的红；各模型的色盲谱不一样，要逐个测。检测办法是先对图片跑 OCR，看模型有没有读到 OCR 识别出的那些词，用多个信号融合。
  • 空内容：如果工具失败导致提示词模板里塞进了空内容，模型不会告诉你内容是空的，它会换成另一个任务并编造内容。他说某些模型总爱编同一类东西，比如 Anthropic 特别喜欢编特拉华州的公司注册文件。可以用启发式过滤，或者在调用前检查有没有发出空白图片、空模板。

基础设施和兜底

他说现在各家模型 provider 都在扩容上吃力，API 几乎每天都有宕机，所以系统要支持多个 provider、多个模型家族，每个家族的代码当作专门代码对待，Anthropic 挂了就切到 Gemini。还要有好的评测，因为大家越来越多地用 Coding Agent 写代码，评测是在规模上控制 Agent 行为的唯一办法；他们为文档解析开源了 ParseBench，在 Kaggle 和 Hugging Face 上有官方排行榜。Agentic 流程失败时还需要不依赖 LLM 的兜底，他们开源了 LiteParse，在 CPU 上每秒约 500 页。

15. Jun Yu Tan（Tusk 创始人）：Coding Agent 的执行边界

直播位置 3:38:09–3:48:05

从 SQL 注入说起

Jun 先放了一个经典的 SQL 注入：用户控制的字符串直接进了 SQL 解释器。他说当年没有靠训练开发者更认真地清洗输入，解决它的是预编译语句，把边界移到驱动层，让注入在结构上不可能。然后他放出 --dangerously-skip-permissions 这个参数。他翻了 Twitter：第一类人对每一小步都要批准感到疲劳；第二类人干脆关掉提示，还推荐别人也这么做；第三类人对 Agent 能做的事感到不安，或者已经被删过重要数据甚至整个系统。他管这叫 UX 失效模式：提示疲劳导致绕过，绕过导致越界。

他自己的数据和概率

他拉了自己过去六周 110 个 Cursor Agent 会话的记录：中位数每个会话 42 次工具调用，平均 120 次，最长的超过 1,000 次。每次都问人显然不可扩展。今年早些时候 Anthropic 给 Claude Code 推出了 auto mode，用一个分类器审每个工具调用，看起来合理的放行，可疑的拦截；Anthropic 自己也建议在隔离环境里用。他算了一笔账：分类器每次判断准确率 99%，一个 120 次调用的会话里全程不出错的概率是 0.99 的 120 次方，约 30%；超过 1,000 次的会话接近 0。他提醒错误并不独立，不要按字面理解这些百分比，他想说明的是逐次的概率检查有一个随会话长度下降的上限，确定性的边界在规模上不会退化。

把执行权限放到更底层

他回顾以前怎么处理“大体可信但无法完全验证的代码”：SQL 注入靠预编译语句和 ORM；内存安全靠内存安全的语言；网络窃听靠 TLS。模式是把强制执行放到出错的那一层之下。他把现在的问题叫 Agent 越界（agent overreach）：可能有攻击者，也可能没有，Agent 可能幻觉、被提示注入、绕圈子，最后决定把系统删了，原因无所谓。他的主张是别再要求执行者守规矩，改变执行者能做什么。

他们最早做这个是为了自家的 Tusk Drift：一个 API 测试回放系统，在 CI 里把几百上千条生产 Trace 对着你的应用重放，绝不能有副作用，比如一个实时调用打到生产数据库改了状态。为此他们做了一个确定性的、操作系统级别的执行边界，开销接近零，开源为 Fence。它管三样：文件系统（策略外的文件 Agent 碰不到）、网络（所有请求强制走本地过滤代理，只有允许的域名能访问）、命令（执行前检查，包括命令链和嵌套 shell）。策略就是一个文件，写清可见路径、可访问域名、永远禁止的命令，没有守护进程、镜像或容器运行时。

演示里，策略屏蔽了仓库里某个目录和 home 目录下的一个目录，也没有允许任何域名。在 Fence 外运行时，读这些文件的脚本和向外发请求的脚本都能成功；在 Fence 下都失败。让 Agent 更新 README 里的日期，它能改文件，但提交后 git push 被拒，因为策略里把 git push 列为禁止命令。

瑞士奶酪模型

他把安全执行分三层，每层都有洞，叠起来让洞对不上，这就是纵深防御：第一层是分类，比如 auto mode，问“这个动作合理吗”，概率性的但懂语境；第二层是策略和强制执行，Fence 在这里，问“这个动作被允许吗”，第一层漏掉的只要被策略禁止就会被拦；第三层是隔离，容器和 microVM，问“出事时这个进程能碰到什么”，适合敌意代码或多租户负载。他说多数团队已经有一层，用 Claude Code 的大概开着 auto mode，重视安全的会把 Agent 放进容器或云沙箱，他希望更多人考虑中间这层：在操作系统层定义规则并强制执行，然后让 Agent 放手去跑。

17. Vincent Wu（MiniMax API 平台产品工程师）：自己调度算力的 Agent

直播位置 5:17:28–5:27:45

算力用得不好

Vincent 说算力是下个世纪最大的商品之一，但现在用得并不高效。他举的现象是有些推理提供商封禁第三方 Harness 使用它们的推理，他认为部分是竞争，主要原因是不同类型的请求对算力的压力不同。尤其是请求的 token 画像（token profile），即缓存的输入 token、未缓存的输入 token、输出 token 各有多少，对提供商能多好地利用算力影响很大。他引用了 Dwarkesh 对 Reiner Pope 的一期播客，那期讲了推理负载怎样依赖 token 画像。所以如果提供商能事先知道一个会话的 token 画像，就能更好地服务，最大化整个集群的利用率。

为什么交给 Agent

让人在每次会话前报告负载类型、时长和 token 分布太过分，他说自己根本不关心自己的 token 分布，但让自主 Agent 做是合理的。Agent 已经在接管越来越多的 Harness，从上下文管理到工具使用，以前都是工程师写死的；它们还没接管的是自己的算力和智能。以前和人结对编程时没什么可调度的，就是贪心地马上要结果；Agent 在后台做长任务时就有了调度空间。例子：给 Agent 一个周末前完成的目标和预算，它可以先选一个擅长规划但不擅长实现的模型，在午夜推理最便宜、成功率高的时候做规划；到项目后期做 QA 时，换一个很强的能看 GUI 的视觉模型做低延迟的实时测试。不同阶段的 token 画像差别很大，适合不同的集群。

答案推理和 Agentic 推理

他引用 Ben Thompson 在 Stratechery 上的文章，把推理分成答案推理（answer inference）和 Agentic 推理。前者是你和 Coding Agent 结对时要的低延迟输出；后者延迟没那么重要，你交出目标和预算，Agent 围绕资源去优化。他补充说答案推理其实是 Agentic 推理的一部分，比如后台任务最后的 GUI 审查，没人看着也需要实时延迟。

他预期最终会出现推理交易所：后台 Agent 在跑负载之前把会话信息提交给交易所，最重要的是用哪个模型和 token 画像，交易所把会话匹配到最适合的批次和节点。好处是把闲置算力变成用户和提供商双方的盈余：匹配得好，每块 GPU 的 MFU（模型浮点利用率，实际算力占理论峰值的比例）都能拉满；时间上也能削峰填谷，现在提供商下午过载、半夜 GPU 闲着。对提供商是更高吞吐、更多收入；对用户是更少被限流，还可能在非高峰时段更便宜，他说现在已经有低延迟、高延迟、批处理等不同价格档。最后他介绍了 MiniMax 的 MMX CLI，这是给 Agent 用的，不是给人用的，让 Agent 自主调用 MiniMax 的语音、图像、视频生成和 LLM 接口，以后会朝 Agent 端到端管理自己算力的方向扩展，比如在一天不同时段跑视频任务来省钱。

18. Daniel 与 Siddharth Krishnan（The Robot Company）：部署遥操作机器人

直播位置 5:29:44–5:40:20

为什么还要遥操作

Daniel 和 Sid 的口号是“今天部署遥操作机器人，为明天的自主性”。遥操作（Teleoperation）是人远程实时控制机器人。开场视频是他们部署在英国剑桥一家昆虫养殖场的机器人，处理喂壁虎和爬行动物的黑蟋蟀，他说没多少人愿意在这种环境工作。Daniel 过去一年在英国部署机器人，除了昆虫养殖场还有洗衣厂、食品加工和酒店。他承认最近有知名研究者说遥操作作为数据采集手段已死，而且有道理：遥操作是一对一线性扩展的；操作员很难培训，他培训过约 100 人，只有三到四成通过；有硬件和延迟的限制；部署也很难，每个新环境的光线、桌子、尺寸、客户需求都不同，会有 bug，在昆虫养殖场里还有真正的虫子，硬件也会坏。

模型怎么扩展，数据从哪来

他简要回顾 LLM 的扩展路径：预训练（大量数据，广泛但粗糙）、监督微调（SFT，用标注好的示范数据让模型学会具体任务）、基于人类反馈的强化学习（RLHF，人提供偏好或标准答案来调整模型），底下都是高质量数据。机器人的数据分四类，可扩展性和数据质量、硬件对齐程度大致成反比：仿真数据最好扩展，但有 sim-to-real 差距（仿真里学到的东西到真实世界会失效）；第一人称视角数据，在眼睛高度放摄像头，较好扩展，但不直接对应机器人的执行器和舵机；可穿戴设备，比如 UMI（Universal Manipulation Interface），能拿到关节或末端执行器位置，再换算到机器人上，质量和扩展性都不错；遥操作质量最高，因为是真机器人在真实场景采集，但不好扩展。LLM 的部署大致就是一个 API 调用，机器人部署难得多。很多人用 LLM 的方式做机器人：数据加算力，预训练加 SFT，在实验室里效果很好，往往依赖仿真数据、第一人称数据和世界模型。问题是怎么在真实世界里补上自主性的差距。

三步

  • 第一步：把遥操作机器人放进真实的商业场景，既给客户干了活，又采集到最高质量的具身数据。Sid 原本安排现场一位同事递给他一瓶水，没成功，他说“部署就是难”。他引用从 LLM 和自动驾驶学到的：最有价值的数据集是做真实有用工作的副产品。在此之上叠加 Pi 0.5、GR00T 这类预训练模型，形态、环境和任务都对得上，形成很好的基础数据集。
  • 第二步：用遥操作数据做监督微调，大约能达到 80% 的自主。他说网上那种炫酷视频就是 80%，但生产里 80% 意味着客户现场每五件衣服就有一件掉在地上，这个差距叫自主性差距。他提到 Figure 最近直播机器人分拣包裹八个小时，很厉害，但也遇到了问题。
  • 第三步：遥操作加人工实时干预，叫遥监督（tele-supervision）：机器人出错时人介入做细微修正，然后放手，不断迭代。要突破遥操作的上限，就从一对一变成一对多，自动驾驶领域早在做，他提到 Waymo；另一面是远程遥操作，他们的系统能跨境低延迟操作，演示过从新加坡到伦敦，他说新加坡到美国、印度到新加坡、中国到新加坡都能在 100 毫秒以内。

他们的结论是企业不能像研究实验室那样思考，要从遥操作开始，作为部署层，加上那些枯燥、不舒服的苦活，再采集丰富数据，再部署商业上可行的模型和机器人。

部署差距和“空热量”数据

Aravind 说网上能看到机器人在春节晚会跳舞、后空翻，也能看到机器人撞镜子、到处出乱子。这就是机器人开发差距：实验室表现很好，部署到真实世界后性能大幅下降。他画了一张图：横轴是各种场景，训练集、测试集和部署时遇到的分布只有部分重叠；实验室里干净有序，真实世界有人走进画面、镜子反光、镜头眩光，这些分布外（out of distribution）的场景就是机器人失败的地方。很多人会说多给数据，但机器人采集的大量数据是“空热量”，重复同一种场景，没有新信号。他举自动驾驶的例子：不需要更多高速公路场景，需要的是奶牛穿过复杂路口、倒车时塑料袋正好挡在后视镜前这类边缘情况。

可靠性怎么扩展

现在进入通用策略（generalist policy）的时代，机器人号称从装洗碗机到叠衣服到医疗科研什么都能做，验证就更难。可靠性大致等于成功率（做 100 次成功几次）乘以要覆盖的所有场景，要覆盖 1,000 个场景就得做 1,000 乘 1,000 次，增长很快。各家都在争谁更快达到可靠性，找可靠性的扩展规律。

  • 人工布置场景实时测试：被人、机器人和时间卡住，线性扩展。
  • 抽样一些测试用例：好一些，但仍是人工，分布有限。
  • 把人移出评测循环：比如用 Gemini Robotics 看画面给出定性反馈（任务完成了吗，离目标多远），再用另一个视觉语言模型或视觉动作模型自动复位场景。人没了，但仍受机器人数量和时间限制，还是线性的，只是稍快。
  • 仿真：像造桥前先做力学仿真。问题是 sim-to-real 差距。他说过去一年有了很多新办法，他们在做的是用真实世界数据生成仿真器本身：输入真实数据，为你的特定领域生成整个世界，比如在加州沙漠跑越野的自动驾驶车，可以很快生成那个世界并在里面训练。这样能复制测试集的分布，做闭环测试。

他展示了一个场景：一艘船驶进拥挤的码头，镜头有眩光，很混乱。再往前一步，在仿真器里对各种运行条件做参数扫描，像同时看到一千种现实，用它们测试模型，在发布前就看到模型会在哪里失败。思路是在仿真里快速失败，再把这些失败点作为真实世界测试的重点，省钱也更高效。他说这比真实数据能覆盖的范围宽得多，业内叫领域随机化（domain randomization）。他还说“数据飞轮”已经成了梗，飞轮没抓住最重要的东西：数据要被提炼，找出最有价值的部分，并反过来指导该在真实世界采集什么。Bifrost 把这些做成在浏览器里仿真世界、在里面“弄坏”你的 AI 模型。

第一人称数据为什么有用

开讲前投影坏了几分钟，主持人临场聊了聊。Julia 讲日常的人类经验怎样变成下一代人形机器人的训练数据。她说过去一年业内出现一件奇怪的事：几百家公司开始大规模采集人的行为数据，比如工厂工人帽子上戴摄像头，人们拍第一人称视角的日常任务还拿报酬。原因是有了它有效的证据：她引用 NVIDIA 最近的 EgoScale 研究，用第一人称视频做预训练，再用人机对齐数据和少量机器人遥操作数据微调，机器人能一次性迁移完成叠衣服这类任务，而且像语言模型一样表现出显著的扩展规律。她认为第一人称视频有两个根本优势：一是我们在造和人一样形态、自由度相近的人形机器人，人和机器人的形态差距在快速缩小，人的行为可以直接迁移，是最直接的监督信号；二是它在真实世界采集，连续、动态、物理上真实，信息量很高。

机器人是工具，还是和我们一起生活

够不够，取决于你在造哪种未来：一种是机器人当工具，在仓库和工厂干活，不和人共享空间；另一种是和我们一起生活，在家叠衣服、陪伴父母、递一杯水。后者需要物理智能，要像我们一样学习世界。婴儿通过抓、按、扔、摸、拉，还经常放进嘴里尝，来学习世界，这叫感觉运动学习（sensorimotor learning）：通过动作和反馈，观察世界对我的动作怎样回应。婴儿同时产生视觉、触觉、本体感觉（proprioception，身体对自身姿态和运动的感知）、声音、动作和反馈回路。如果能采集所有这些，就能让机器人像我们一样学。

缺的是触觉

她说今天大部分模态已经可测：视觉来自第一人称摄像头；运动可以从视频重建；三维手部姿态、手腕姿态、轨迹、身体动作这些本体信息也能从视频重建；声音摄像头自然就录了。只剩触觉基本缺失，而物理交互里触觉可能是最重要的信号。触觉数据少的一个原因是其他信号都能从第一人称视觉推出来；她说视觉能扩展，要感谢几十年的摄像头硬件进步和统一在 RGB 像素上的生态，触觉还没有这样的时刻。触觉也需要统一的硬件栈和统一格式的数据基础设施。OpenGraph Labs 要做触觉的标准，分两层：可大规模部署、从指尖采集高保真接触信号的硬件；以及建立在硬件之上的触觉编码器，把信号变成有意义的表示。她说他们刚开始搭一条完整的人类感觉运动回路采集管线，目标是几千人、几百万次交互。

22. Suveen Ellawela（Cortex AI 创始工程师）：机器人是数据和运营问题

直播位置 6:19:44–6:29:30

学习系统和栈

Cortex AI 主要做双臂（bimanual）机器人的操作任务，也有在便利店这类真实环境里干活的移动机器人。片子里机器人能把最后一滴牛奶倒进杯子。Suveen 解释这些学习系统就是像素进、动作出：通常一个顶部摄像头和腕部摄像头，加上机器人的关节数据和一句语言指令，模型预测动作，机器人执行，进入下一个状态，循环往复。他把机器人学习栈分成：数据（摄像头画面和关节）、软件（采集、训练、推理）、硬件（机械臂和摄像头）、模型（策略）、评测，以及让这一切反复运转的运营层。他说机器人常被看成硬件或模型问题，其实也是很大的数据和运营问题。

数据采集

他们最近和艾伦人工智能研究所（Ai2）合作 MolmoAct 2 论文，采集了超过 700 小时的双臂 YAM 机械臂数据，他说这是目前最大的开放双臂数据集。数据来自遥操作：同事操作主臂（leader arm），从臂（follower arm）复制动作。看着好玩其实很难，因为人的直觉不能很好迁移到新的身体上，用手拿杯子容易，通过机械臂就难，但这是可以学会的。采集前还有很多事：就算是叠毛巾，叠两折还是三折要先定策略，再练动作，还要保证不同回合、不同操作员之间一致。规模到几百小时后，小的流程改动会累积：一开始每个回合要等两三分钟编码；挪到会话结束统一编码后，要等三四十分钟才能开下一场；他们改了一点代码，断开所有硬件连接后，上一场还在编码时就能开新一场，最后采集、编码、上传完全解耦。

跨层的视野

他说问题空间和解法空间往往不在同一层。例子一：机器人抓罐子时夹爪断了飞出去，他以为是模型学错了或该在代码里降低夹持力，同事说干脆自己设计夹爪，他们用的是第三方硬件但仍可以在上面改，这是用硬件解决他以为的软件问题。例子二：摄像头经常断线，拔插几次又好了；有次操作员不小心碰歪了顶部摄像头，那天所有数据视角不对只能扔掉。他们一边想办法让支架更牢，他一边写了一个检查顶部视角是否正确的脚本，每次开工前花两三分钟检查，这是用软件解决硬件问题。

评测和安全

仿真里的评测可以并行，真实世界很乱：光线会变、有干扰物、执行器和摄像头有噪声。做 MolmoAct 2 时他们在五个策略上跑了几千次真实世界评测。每次跑完要手动复位环境，弄乱了要人去收拾，他做过几百次，“保证不好玩”，很贵，但这仍是金标准。机器人失败时也很难定位原因：可能是数据（不同操作员策略不同，一个叠两折一个叠三折）；训练设置（比如 LoRA 还是全量微调，LoRA 是只训练少量附加参数的高效微调方法）；加载模型时部分权重被随机初始化导致它乱动；action chunk（一次预测的连续动作段）大小和训练时不一致；或者评测设置本身错了，以为在测分布内，物体位置却偏了。

安全方面，他放了一段自己偶然录到的视频：一个关节不到半秒转了 90 度，如果有人的手在那里就受伤了。他说大家常讨论部署后的安全，开发时的风险也很多：采集时主臂突然断电，整个重量可能压在操作员身上；评测涉及试管的任务时机器人打碎了试管，玻璃碎片乱飞；过期的动作队列可能导致机械臂突然移动。AI 写的代码跑在机器人上也要小心。他们很喜欢 Hugging Face 的 LeRobot，把它适配到自己的机械臂时有大量脚手架和接口代码，用 AI 写来提速。但上机前要做常规的软件检查和 PR 审查，在仿真里测，再看日志（把动作发给机器人但不执行，先看日志），真上机时一次只动一个关节、把速度调慢。他最后说不用每层都是专家，但懂得越多层，解决问题越快。

25. Alex Lee（Magic Patterns 创始工程师）：AI 时代更需要设计系统

直播位置 7:09:54–7:18:40

13 岁的联合主持人 Usman 介绍他时说，AI Studio 这类工具做出来的设计很难看，大家要的是符合自己品牌的设计。Magic Patterns 是一个 AI 设计工具，号称几分钟从想法到生产，被 2,000 多个产品团队使用，他提到 KPMG、Ramp。Alex 主要负责设计系统。他说 AI 让加新功能变得容易，难的是一致性。

设计系统的来龙去脉

早期网页像 MySpace 主页，每页都不同，设计师和工程师各自重做，没有共享体系。设计系统（Design System）是产品团队共用的语言：设计令牌（tokens，颜色、字体、间距等基础变量），加上 Brad Frost 的原子设计给出的组件层级，原子（按钮、标签、输入框）、分子（表单模块、搜索栏）、有机体和模板（侧边栏、仪表盘布局）。承诺是一致、速度和规模。但后来太一致了，加一个按钮要走流程，大家想的变成了怎么用工具箱里现有的组件，很少再从第一性原理想怎么解决用户问题。业界退了一步，把设计系统当成一个框架来用：有创造空间，也有护栏。

AI 又把混乱带回来了

他说过去六个月自己的工作流完全变了，已经不写代码，让 Agent 写。实现成本几乎为零（尤其公司在付 Opus 4.7 的 token 费），问题从“能不能做、要多久”变成“要不要做、要不要维护、用的是不是我设计系统里的组件、符不符合品牌”。没有上下文的 AI 会幻觉出组件、用不在品牌规范里的颜色。光有 Figma 稿、Storybook 甚至一个 design.md 都不够。

他们的方案叫 AI 原生设计系统，靠两根支柱：文档和代码。文档包括系统级规则（令牌）和组件级规则；组件必须有代码支撑，越贴近代码越接近用户真正看到的东西，Agent 也能理解组件的 props 和变体。案例是心理健康平台 Headway：他们本来有设计系统，Magic Patterns 把 Storybook 作为文档来源，生成系统级和组件级规则，再通过 npm 包或 GitHub 同步导入代码里的令牌和组件。同样一句“给我做一个仪表盘”，没有设计系统时得到的是一个通用的 SaaS 仪表盘；带上设计系统后，logo、组件、颜色、字体都和 Headway 的品牌对得上。

为什么做图层

现在的图像和视频生成输出的是 MP4、PNG 这类冻结的文件格式，图层不暴露，每次提示设计状态都被重置；文字也不是好的输入方式，很多人说不清自己要什么，翻译中损失很多；所以今天没有人和 AI 一起协作的体验。图层级可编辑除了方便人挪东西，还能把不同图层交给不同的专用模型：文字生成、SVG 生成、照片生成，不必一个大模型做所有事。

为什么创业公司来做，大实验室没做？她说老实的答案是没有数据。代码有大量 GitHub 仓库，平面设计只有三家大公司，Figma、Canva、Adobe 都是围墙花园，握有几十亿条编辑轨迹，实验室和社区都拿不到。所以他们收集了超过 150 万个分图层的平面设计作品，部分已开源，有一个浏览器可以看，覆盖 Instagram、商务演示、海报等 50 多个类别。每个数据点有丰富标注：画面内容、裁切、位置、语义和逻辑分组，可以教模型怎样重排内容、改宽高比时怎样规划布局，她说这些都是前沿模型现在做得很差的。配置文件也能当 Skill 给 Claude Agent 用，效果会好很多，也能拿来训练模型或做评测。

品味是成千上万个小决定

她说人们说“AI 没有品味”，意思是设计师执着于细节：矩形的圆角多大、用哪种裁切、文本框离边距多远，成千上万这样的小决定让设计变好，模型不懂，每一处小失误都让结果显得空洞。企业里不会有无限 token，比如电商要为东南亚多种语言、多个国家生成符合品牌规范的横幅，只想改文字或某个图形，其余保持不变；或者把相机拍的图、人写的文案和 AI 生成的像素组合起来；还要能组合一组模型，随着新模型出来把设计的不同部分交给不同模型。她说一次生成所有东西是工程师对创意模型的想象，而创作本来就是渐进、反复的，往后退几步、往旁边走，可能推倒重来。

他们还做了一个多信号奖励的学习系统：只用人类偏好容易被钻空子，尤其不同品牌品味不同，所以把人类偏好和客观奖励（输出是否有效、是否符合设计原则）结合。有两个模型：一个 AI 评审不断更新评分标准，越来越会分辨好坏；再用更新后的评审去重训生成器，因为设计有保质期，要持续喂好例子。也要超越文字提示，把更多交互形式纳入训练循环。最后她说她的幻灯片前后不一致，这就是今天模型的样子，不管 Twitter 和 LinkedIn 怎么吹，模型在布局规划、规模化视觉一致性和图层级可编辑上都很差。数据集在 Hugging Face 和 GitHub 上，他们还发布了一个平面设计基准（GraphicDesignBench）。

28. Conor Brennan-Burke（Hyperspell）：怎样给公司造一个大脑

直播位置 7:44:55–7:55:45

聪明但对公司一无所知

Usman 介绍他 12 岁从高中辍学，住过黑客屋的壁橱，Hyperspell 融资超过 670 万美元。Conor 说 Agent 是“一无所知的天才”：聪明的博士级实习生，对你的公司一无所知，每天都像上班第一天，读到什么就信什么，所以需要人看着。他认为通往 AGI 的关键是给对上下文，模型已经很聪明了。

最常见的做法是连接器，把 Slack、Drive、Notion 接给 OpenClaw，或用 Anthropic、ChatGPT 的连接器。问题是 Agent 会把读到的当真，而文档本身常常不真：找到一份文档却漏了更正；找到过时的版本；两个来源冲突时先找到哪个就信哪个；同一个人在 Slack、Gmail、Notion 里出现，它以为是五个不同的 Lisa；没有时效概念。他说连接器给的是访问，不是理解。他问台下：入职后照着文档去做，结果别人说那个过时了、去问 Bob，谁遇到过？几乎所有人。所谓的“事实来源”很少是真的，信息一产生就开始过时，文档是滞后指标，组织调整、客户例外、新部署都让现实远离文档。人知道去问在公司待了五年的人，Agent 不知道。

公司大脑是什么

每个组织需要一个给 Agent 的单一事实来源。它和连接器、跨来源的 RAG 都不一样：它知道某份文档是谁写的，把邮件、Slack、Notion、会议的线索串起来，暴露冲突并决定怎么取舍，给每条信息一个置信度。他说很多企业 AI 部署失败，就是因为 Agent 直接去读文档，没有公司大脑可依。他还强调上下文不再只是人产生的：你给 Agent 的提示词、OpenClaw 的记忆、Agent 的 Trace 和推理过程、和 Claude Code 来回得到最终产出的过程，都是上下文，不放进大脑就丢了一大块。他预计几年内组织里大部分上下文会由 Agent 产生。

大脑里要放四类知识，各自存法不同：

  • 稳定事实：法律实体、组织架构、品牌色。
  • 流程知识：怎么入职、怎么评审交易、怎么响应事故。
  • 隐性经验：只在人脑子里的东西，比如怎么拿下这个客户、哪个测试不稳定、哪个集成不好用，很少写下来。
  • 状态性的现实：进行中的交易、正在发生的事故、今天的阻塞。

怎么造

他们和从小创业公司到财富 500 强的客户合作后的做法：先摄入所有数据，Slack、Gmail、Notion、GitHub、会议录音，还有 Agent 的 Trace；他说 Meta 已经开始这么做，甚至记录键盘输入，也有人录屏。然后建上下文图谱（context graph）：一个图结构，找出组织里每条事实，知道它什么时候为真、谁写的、多可信。但图数据库对 Agent 不友好，模型没在这上面做过后训练，所以最适合 Agent 的表示是文件系统：公司层面有人员、潜在客户、客户、决策、事件，往下是每个团队，再往下是每个人。文件系统是通用的，Claude Code、Cursor、OpenClaw、NanoClaw、内部 Agent 都能用。

构建流程分四步：采集上下文，既要导入历史数据也要实时接入，Slack 这类实时信息漏掉了 Agent 就不是最新的；规范化，认出邮件里的 Lisa 和 Slack 里的 Lisa 是同一个人，去重、结构化；综合，数据冲突时交给人决定取舍；最后服务给 Agent，在对的时候给对的上下文。他说难点在综合，不在搜索。他问谁知道 Karpathy 的“第二大脑”想法、谁用 Obsidian 做个人知识库，说这就是给整个公司、每个人、每个 Agent 用的版本。最终公司会从自身学习：人和 Agent 干活产生新上下文，综合进大脑，下次执行更好；一个销售学到更好的卖法，马上全员共享。以前人走了上下文就跟着走了，现在组织可以递归地自我改进，而且不用多开一个会。

问题：大模型在确定性任务上仍会幻觉

Interfaze 自称是在重新发明 Transformer 的研究实验室。Harsha 说 2010 年代初，一家银行要做 OCR，得买大数据集、请团队训练、部署和维护，可能花几十万到几百万美元；有了 LLM，用提示词就能做。但当输入数据很多、又要求确定性的结果时，模型会因为上下文漂移而产生幻觉，即使 GPT、Gemini 已经是大规模多模态模型。他们的思路是把机器学习模型的严格和 LLM 的灵活结合：用专门训练的模型做特定任务的强编码器，用 LLM 做解码。

三个演示

  • 一份真实证件：要提取文字、检测照片上的人脸、算出年龄来核验。Interfaze 给出了文字和文字在图上的像素坐标，两张脸都检测对了，年龄也算对了。对比的 OCR 服务 Reducto 文字提取对了，但没有给出位置，也没算年龄。
  • 抓取一个 LinkedIn 页面（他开玩笑说 Garry 还没关注他）：LinkedIn 有反爬和机器人检测，要抓“展开”按钮后面的经历。Interfaze 一直抓到了对方的实习经历，靠的是他们自己的抓取模型。
  • 一篇很密的研究论文 PDF：全文提取、翻译成印地语、统计字符数。结果全文提取并翻译了，地址和作者名这些不该翻的保持原样，字符数也对。他们拿 Claude 4.7 Opus 试了三次，三次都因超时失败；他说即使不超时，长任务里多语言尤其是南亚语言也是问题。

底下是怎么做的

  • OCR：他说在 MOCR bench（考复杂文档、手写和多语言 OCR）上排第一，超过 Chandra OCR 这类专用模型和 Reducto。图像先进一个他们训练的 CNN（卷积神经网络）编码器栈，找出文字区域，按区域裁切再交给解码器生成，所以有置信度、边界框和元数据；再把这些交给一个条件化过的大解码器得到结构化输出，年龄就是这样算出来的。
  • 自然语言目标检测：YOLO 这类模型只能检测训练过的类别，他们能根据提示词检测，比如“找出所有穿黑 T 恤的人”。文本编码器理解用户要什么，图像编码器给出带位置的表示，再做对比式分割，把相近的像素拉到一起；进一步用掩码解码器给每个像素分类，就能做分割。
  • 语音识别（ASR）：他说他们是最快的之一，词错误率最低。长音频先做语音活动检测，把有人说话的片段切出来，提取声学特征做嵌入，再聚类，得到说话人分离（diarization，分辨每段话是谁说的）；文字部分把音频转成频谱图（spectrogram，声音的可视化表示），逐帧分类成文字。

视觉、音频、文本三个编码器各配一个适配器，接到同一个解码器上，所以既有准确的数据，又知道数据来自哪里。他展示了和常用生产模型在确定性任务上的对比，强调是只有一个正确答案的任务，“图上我的名字不会变”。他和团队做任务专用模型大约一年，用过小语言模型、花钱买大数据集，一直卡在确定性上，最后得出结论：瓶颈在架构，不在数据。

32. Hrishi Olickel（Southbridge）：在旧系统里造可靠的 Agent

直播位置 8:31:07–8:41:10

立场

Hrishi 在新加坡。他的壁纸是一张改过的 Windows XP “Bliss”，来自他在非正式会议上讲过的“怎样离开绿地”（Greenfield 指从零开始的新项目）。这场的暂定标题是“老代码无处容身”，讲的是在已有的大系统里造 Agent，面对旧代码、旧组织和旧数据：修复优先于重建，更新优先于新建。他说从这些前提出发会自然得出一组原语：用更简单、可复用的工作单元，别想着一次塞满上下文窗口；从上下文里删东西而不是加东西；把控制流和提示词分开、提示词和代码分开；按行为校准，而不是按单步成败；成本感知，分开构建期和运行期以便分配资源。做到这些，就能交付结果，做一次就保持做完，修一次就保持修好，想 vibe 的时候也能 vibe。

Southbridge 和数据的难度

他之前在电子和软件行业待了几年，瓶颈一直是数据，要把数据整理成能支撑决策的样子。琢磨了十年后，他带着一个信念创办 Southbridge：GPT-3.5 Turbo 是缺的最后那一块通用智能，剩下的可以自己造。之后他们做了能自我修复、自动重新生成的数据连接器，为医疗、金融、能源做了 ETL（抽取、转换、加载数据的流程）系统，在解决数据“摄入”这个横向问题，不管是新客户、新数据集还是用户上传的数据，都是数据的“第一公里”。他说从数据起步难度一上来就是 11 级：从第一天起就在关键路径上，任务从第一天就是长时程的，可靠是底线。即使 1 GB 的小数据，校验格式、验证、实体解析都要几百万次操作，错误会累积。上下文窗口还倒退过（他提到 Gemini 从 200 万降到 100 万），就算扩大 100 倍，一天的数据也处理不完。最大的杀手是多样性：人会把一切变成画布，文档、Excel、PDF，他们内部开玩笑说 Excel 的合并单元格按钮是反人类罪；每家公司都是独一无二的雪花，同一个 Postgres 透过不同的内网和权限看起来像完全不同的系统。

两个判断

  • 在线和离线：有人在前面等的是在线系统，没人等的是离线系统。他说大多数真实系统的离线部分远大于在线部分。只有每次都从头构建时才需要一个对延迟敏感的人在环；如果能造出会随时间固化、记住你偏好的可靠系统，大部分工作可以挪到夜里离线跑，用本地模型更便宜，Agent 就像家电，可以重复做上千次，像睡前装好的洗碗机。
  • Coding Agent 会成为 Agentic 工作的基础层。他认为写代码很快会饱和，所以原因在别处：Coding Agent 循环拥有最多的资源、最多的强化学习、最大的部署压力，还有通用的原语：读、写、编辑、shell。就像 V8 和浏览器成了大量不是网站的软件的底座。

学到的几件事

  • 别再追求一次成功。复杂指令、长计划、巨大的 Skill 在搭东西时追一次成功很好玩，但可重复的工作要先拆成小的原子单元。在他们用了很久、最近开源的运行时 Hankweave 里，这些小单元叫 codon，串起来得到想要的行为，可复用、可组合。这样更容易推理长时间运行，他说人能否推理第 20、25 小时发生了什么，会成为构建复杂软件的瓶颈。
  • 从上下文里删东西。他惊讶于很少有 Harness 或框架提供删除上下文的方式。他们的默认做法是设边界，删掉不需要的上下文并归档，防止他们内部叫“世界线腐烂”的问题。他引用 Ted Lasso 的“做条金鱼”。
  • 按类型分开组件。他说业界一直在重学这件事：冯·诺依曼和哈佛架构区分代码和数据；PHP、CGI 之后又花了几年才学会分开模型、视图、控制器。Agent 也一样，数据、提示词、控制流等要尽量分开。他们读过几百万字 AI 生成的输出，十次有九次出问题，是因为你和 Agent 之间共享了错误的抽象，或者上下文里留了不该留的东西。
  • 最好的零件是没有零件。简单工具按顺序干活，只有绝对需要才加东西。他说他们从来没需要过并行 Agent，单一主 Agent 线程对可靠性的好处太多，就像很多编程语言的单线程事件循环。
  • Sentinel：最初为监控长时间运行设计，现在是他们最强的原语。它是在主循环的某些事件组合上触发的 LLM 调用，触发后套模板组织上下文，把结果写进文件。比如每 50 次工具调用醒来一次总结发生了什么，再睡回去。它能抓住偷懒、乱 mock、数据卫生差、文件写入、shell 报错这类行为，又不会复杂到你得去排查评测系统本身；定义好模式，在主线程里修。他说比 hook 好得多。
  • 预算：长时程系统要在每个重要维度上都有成本意识。做到前面那些，就能做声明式预算，像 SQL 一样声明你有什么，系统去填中间的差距。在模型、Harness、实现细节一直变化的领域，声明式能让你不必一直重写。维度有钱、token、时间，甚至在什么时候能访问什么数据；构建期声明怎么分配，运行期知道实际有多少资源。

最后他说，做到这些，交付的就是结果，不再只是工具。大多数人不关心洗碗机怎么工作、车怎么喷油，只要干净的碗、到达目的地，所以他们的北极星是交付结果：尽快让客户上线、验证研究假设、缩短集成时间。为此 Agent 要变成基础设施，无聊、可重复、可预测，目标是造出能成为“遗留系统”的东西，他说只有在代码里“遗留”才是贬义词。

33. Henry Mao（Smithery 联合创始人）：MCP 和 CLI，Harness 时代的 Agent 能动性

直播位置 8:44:30–8:55:00

从复制粘贴地狱开始

Henry 上一家创业公司 Jenni AI 做学术研究的 AI 助手。他观察用户时很烦的一点是：大家开着好几个窗口，在各个应用和 ChatGPT 之间来回复制粘贴。这影响所有知识工作者，人在充当 AI 的适配层，每次读写不同服务都要人来提示模型。他说提示就是模型无法安全访问你的数据或替你行动时交的税，而且很贵。大约一年前他创办 Smithery，当时 MCP 刚出现，他看作连接 Agent 和服务的桥梁。Smithery 起步是开放的 MCP 注册表，有几千名开发者发布 MCP 服务器；后来做了网关，聚合服务、统一认证，让 Agent 把所有 API 当成一个工具箱来用，现在每天处理约 10 万次工具调用。

MCP 为什么被说“死了”

他说 MCP 发布后热度很高，问题也很多：协议野心大，在 Agent 还没学会好好调用工具时就想定标准，2025 年初规格变动很快；客户端和服务器实现质量差，用户很沮丧；到 2025 年底很多人宣布 MCP 已死，这次大会上至少五个人问过他。他承认很多批评成立。最主要的原因是 2025 年大部分 Harness 的做法很粗糙，把所有工具一股脑塞进模型上下文。他打比方说像 Chrome 不渲染 HTML，直接把 HTML 和 CSS 丢给你让你找该点哪里。这浪费 token、造成上下文腐烂（context rot，上下文越长越杂，模型表现越差），明显拉低性能。很多 2025 年做的 MCP 服务器也很差，是官方 API 的缩水版，没有好好做认证，开发者还在工具描述里手写提示去“注入”较弱的模型，把本该属于 Skill 的任务行为写进了工具描述。

于是大家找替代：Coding Agent 已经很会用 bash，为什么不用 CLI？CLI 自带渐进式披露（progressive disclosure，先看到概要，需要时再查细节，比如 --help 和子命令），有管道可以组合子命令，建立在成熟的 Unix 栈上。但他说这里有一个类别错误：MCP 是 Model Context Protocol，是协议，和 REST、GraphQL 同类，规定怎么通信；CLI 是界面。拿两者比是拿苹果比橘子。缺的是一个能把 MCP 好好呈现给 Agent 的 Harness，他称为原生 MCP 渲染（native MCP rendering）。他说到 2026 年初，Claude 和 Codex 这些主要 Harness 终于做好了 MCP 的呈现。

他们的实验

Smithery 测了现代 Harness 用原生 MCP 和用 bash 调 CLI 的差别。选了三个 API：GitHub、Linear 和新加坡公交 API，风格不同，训练数据里的污染程度也不同；三个模型（名字在幻灯片上，字幕没有念出）；唯一的变量是给 Agent 的接口，要么装成 MCP 服务器，要么给 bash 一个 CLI。测准确率和 token 效率。现场投票，认为 CLI 更好的人最多。结果出乎他们意料：原生 MCP 在准确率和 token 效率上都赢了，他说这主要是因为 Harness 自己更新、变高效了。

他更关心的是哪些 Agent 体验的设计原则起作用，于是做了消融实验，改造 CLI 看能否追平。最重要的两点：一是自我文档化，工具可发现、描述清楚，Agent 表现更好；二是搜索，让 Agent 能搜索 CLI 子命令或 MCP 工具，减少找到合适工具的步数。给 CLI 加上这两点，差距基本能补上。完整实验细节在他们的博客上。

MCP 的长处

他说如果你是在本地跑东西的工程师，大概就该用 CLI，他也声明自己没收 MCP 的赞助，这个基准是在 Smithery 推出 CLI 产品之后做的，两种他们都支持。但 MCP 有几点要给它记上：可移植性，CLI 要配沙箱，好的 Harness 下 MCP 开箱即用，适合不需要沙箱、更轻、延迟更低、与写代码无关的云端 Agent；上下文工程的责任在 Harness 上，Claude Code 改进了 Harness，你的工具也跟着变好；更微妙的一点是权限。CLI 是给开发者做的，范围通常太宽，攻击面很大，等于交出整个王国的钥匙。后台长任务里跑 CLI Agent 只有两个糟糕的选择：每步请求批准（不可扩展），或者像台下很多人那样直接 dangerously skip permissions。MCP 定义了一个有主见的小接口，形成一个可以施加策略和护栏的咽喉点，比如 Smithery 网关提供策略 DSL（为特定用途设计的小语言），细粒度地规定 Agent 能做什么不能做什么。

他的回答：MCP 没死，但这也不是这场的重点，MCP 和 CLI 各有用处，留下来的是 Agent 体验、安全和认证背后的原则。MCP 可能不再是热点，他觉得这很好，协议最好的结局是像 HTTP 一样无聊，这样大家可以去解决更有野心的问题，让 Agent 由结果驱动而不是由提示驱动，从聊天机器人变成同事，人从“在每个循环里”变成“在循环之上”。

34. Rach Pradhan（独立开发者）：自我进化的 Harness

直播位置 8:56:30–9:06:30

介绍他的 Ivan 说，Rach 在一次黑客松里做了一个让 Agent 协作的工具，周末又为下一场 Mistral 黑客松先做了一个帮自己做参赛作品的工具，赢过一场 Gemini 黑客松，还自己对 Kimi 2.5 Thinking 做了后训练，超过原模型，当作自己的主力 Agent。

从开放式学习到“太阳”

他最初和朋友写一篇论文，从零训练一个医学扩散模型（扩散模型是通过逐步去噪生成图像的模型），发现数据很少。读论文时碰到一篇讲模型有“人类的有趣感”的文章（整理者注：应是 OMNI 这一工作），用语言模型当评审来生成开放式的强化学习课程，由此接触到开放性（open-endedness，让系统无限产生新东西）这一方向。他自然想到：如果说 Agent 可以开放地、永远产生新东西，在我们的生物学里这是什么样？他的答案是太阳：太阳的高能粒子到达地球，再以更高熵的光子辐射回太空，生命就是利用这个梯度、制造更多熵的东西，而且是花了几十亿年才演化出来的特定的熵。他做了一个映射：太阳是算力，DNA 是把单细胞生物演化成会写代码的我们的那条轨迹，选择压力就是 Harness，Harness 随着模型演化。

论文线索

他提到 OMNI-EPIC：单个 Agent 在不同环境里，起初只擅长一个环境，随时间变得越来越通用，出现涌现行为。同一作者的另一篇工作把被进化的对象换成代码本身（整理者注：应是 Darwin Gödel Machine），在 SWE-bench 上从大约 20% 提到大约 50%。他由此意识到环境和工具都是可以拉的杠杆。他说现在模型比 Harness 强得多，每家公司都在造自定义 Harness，他认为这不是正确的方向，应该让 Harness 自我进化，相关的有 Meta-Harness 和 RLM 等文献（字幕写作 ROMs）。再下一步是 Agent 本身：把记忆状态放在别处、让 Agent 进化；再往后是在代码环境里的世界模型（不是物理世界模型），他的一位做世界模型论文的朋友说，更有意思的是看在这些世界模型里 Agent 的架构会长什么样，可能不是人手工设计的。他说以前要很久才把 MMLU 等基准刷饱和，现在每隔几周就有新的最强模型，原因是训练循环更快了，模型在一定程度上自己闭合了循环。他认为扩展规律仍然成立，只要人类比 Agent 和 Harness 更有趣。

他学到的和造的工具

  • 真正提升模型表现的是轨迹，权重的作用小得多，就像 DNA 不变、表现方式在变。值得研究的是路径和推理轨迹、模型为什么这样做，最终状态没那么值得看。
  • 迭代循环很重要：最成功的生命形式适应得快、死得也快。编程语言就是一个例子，他现在多用 Zig 和 Rust，他发现编译时间更短的语言能造出更好的工具和测试，即使不是内存安全的。他预计今年或明年几乎每家公司都会写某种自己的“元 Agent 语言”，不一定是人能读的。
  • 一个比 ripgrep 更快的搜索工具（名字字幕不清），让 Agent 拿到精确的代码行。
  • Code DB：完全开源的三元组（trigram）搜索，让 Agent 只拿到需要改的那几行，减少上下文腐烂。
  • nanobrew：把 Agent 放进沙箱后，要么快照环境，要么一遍遍 apt-get 拉依赖，他做了一个比 apt-get 和 Homebrew 快得多的包管理工具。
  • 一个类似 agent-browser 的浏览器工具，用 Chrome DevTools Protocol 暴露的无障碍（a11y）树来减少 token，提升 Agent 大规模浏览网页的能力。
  • Dev Swarm：编排一组可以变形的模型，比如几个 Opus 上下文窗口加几个 ChatGPT 窗口组成多 Agent 框架，以 Terminal-Bench 这类更刚性的基准为事实来源；用的人多了，他拿到了哪些有效哪些无效的遥测数据。这些最后都汇入某种适应度函数，在 Coding Agent 里由 Harness 每次重写。

他的 Harness 叫 CodeGraph，曾在 Terminal-Bench 上是最好成绩，现在已经不是了。它是自我进化的 Harness，随着模型更替越来越好，还会自己造工具。代码和轨迹都开源了，但还没大规模发布，仍在开发中。他说他最后只造了一个 Harness，但一路上造的工具对他自己也是一个进化循环，这五样东西都让 Harness 变得更好。

怎么来的

主持人介绍 Agrim 是新加坡赢黑客松最多的人，在这个生态里成长起来。他说故事要回到 2025 年 7 月 16 日，他和 Rachel、Sherry 吃午饭，对新加坡 AI 活动的状态很不满：说得多，对建造者不友好。那时他们还没办过活动，但觉得最后一定会办一场大会。他当时发消息说：“我们会 yolo 着办成城里最大的会。”他没想到真成了。

但不能光靠 yolo，要先试探受众：是生态没反应，还是活动没服务好他们？那条消息一周后他们给 Cursor 办了一场聚会，以为来一两百人，结果 900 人报名，放进来 500 人。几个月后办了一场 24 小时黑客松，1,200 人报名，放进 500 人，有人从荷兰和周边各地飞来。这让他们相信大家需要一个空间。90 天前他们见到 swyx，说要办 AIE Singapore，他说 swyx 大概想笑：你们办过会吗？会有人付钱吗？他能帮的有限。他们的回答基本是“我们会想办法”，这成了整场活动的座右铭，他也为不完善的地方道歉。

高意愿和本地化

一切围绕“高意愿”：他们想做最适合建造者的活动；希望在场的人是真的想来，票不便宜，没有发免费票；讲者是真的想来，所以给他们出机票；赞助商也是。他说房间一整天都是满的，到晚上 6 点还有人，每位讲者都说台下反应很好，尽管不确定新加坡观众是不是和旧金山、伦敦一样。

他说不能把海外大会照搬过来：研究太重会走掉一半人，太浅又不像 AI Engineer。Sherry 排了大约 21 版讲者阵容，把相关话题放在一起，比如几场 OpenClaw 的演讲连着听，Magic Path 和 Magic Patterns 前后相接，名字和领域相近，产品思路很不同，让观众自己形成判断。他们加了自己的东西：每张票都包含工作坊，这在其他 AIE 不是默认的，他说这是给建造者的活动，没打算办成思想领袖的炉边对谈；加了减压环节，因为 AI 焦虑、token 焦虑现在很普遍；前一晚办了大派对，他和 Geoff Huntley 先 DJ，然后是压轴 DJ。他说最重要的是走廊里的碰撞：赞助商的核心团队都来了，讲者随处可遇，这在新加坡很少见，一般会议上你只会见到交换名片的市场人员。

奖学金和致谢

他们想让读书的年轻人也能来。原本有一家大组织要赞助奖学金，在公布前两天撤了，Agrim、Sherry 和 Rachel 决定自掏腰包，之后很多建造者以个人身份加入，一共资助了 20 名学生，他请了其中几位上台，说这些学生每场活动都到，在 Twitter 上写回顾。他点名感谢了 Arize 的 Patrick Kelly（Arize 是赞助商，他又个人出钱）、Neil Chang、Ivan、Leo、Casper、Iterative 的 Suken、Zayn 等人和很多匿名的人。

他说常听到“新加坡没有圈子，要飞去旧金山参加会议”，他希望大家觉得自己就是这个圈子：每场演讲、每个工作坊、所有周边活动都超额报名，下着雨早上 8 点半、9 点也到场。他希望大家继续去黑客松、一起做东西、不等许可就分享，让人知道新加坡在亚洲乃至全世界都是值得重视的城市。他感谢了讲者，钻石和白金赞助商 OpenAI、Z.ai、Google DeepMind、Cursor、Arize，几夜没睡的志愿者和团队，请团队上台。最后他宣布 AI Engineer 会再回来，有意向登记表，会先给登记的人发早鸟票和信息。他还请 swyx 上台，说 swyx 是 AI Engineer 全球的负责人，也是新加坡人，是他的同意让这场会得以发生。
