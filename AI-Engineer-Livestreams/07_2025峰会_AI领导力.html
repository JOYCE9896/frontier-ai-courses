02. Grace Isford（Lux Capital）：2025 年 AI 前沿，Agent 为什么还没真正起作用

直播位置 0:17:20–0:34:32 · Beyond the Consensus: Navigating AI's Frontier in 2025

讲者和背景

Grace Isford 是风投机构 Lux Capital 的合伙人。她介绍 Lux 投前沿科技，早期投过 Hugging Face（她称之为“机器学习界的 GitHub”）、Together AI（开源 AI 云）、Physical Intelligence（机器人软件大脑）和东京的研究实验室 Sakana AI，后者在演讲前一晚刚发布了 AI CUDA Engineer。Lux 创立于纽约，2013 年在纽约做了第一笔 AI 投资，现在多数 AI 被投公司以纽约为总部或主要据点。

2025 年开局

她从 2022 年 8 月的 Stable Diffusion 讲起，说过去两年半的进展越来越快，而且发模型的公司越来越多，不只 OpenAI 和 Anthropic，还有 xAI（上周刚发 Grok 3）、Mistral、DeepSeek。2025 年开局的事件她列了：5000 亿美元的 Stargate 项目；OpenAI 的 o3 在 ARC-AGI 上超过人类水平；DeepSeek R1 发布后英伟达股价下跌、DeepSeek 冲到 App Store 第一；上周的巴黎 AI 峰会上马克龙宣布新的 AI 计划。

她说很多人觉得 2025 是 Agent 的“完美风暴”：o1、o3、R1、Grok 的推理模型在一些任务上超过人类；测试时计算（Test-time Compute，即在推理阶段多花算力让模型多想一会儿）在提升效果；推理和硬件越来越便宜；开源和闭源的差距在缩小；数据中心投资巨大。但她的判断是“雷声很大，闪电还没劈下来”。她给 Agent 的定义是：由 LLM 自己决定行动的全自主系统。

一个订机票的例子

她让 OpenAI 的 Operator（能自己操作浏览器的 Agent）订周一从纽约飞旧金山的机票，条件写得很细：周一下午三点以后出发但要避开晚高峰；只要 United、JetBlue 或 American，方便升舱；500 美元以内，符合公司报销政策；靠走道的座位但别离厕所太近；午夜前到达。第一次它去了 Kayak，没找到航班，似乎也没去查 United 或 American。第二次去了 Skyscanner，找到了一班，但是下午 5:30 从 JFK 起飞，正好是纽约最堵的时间，而且没法选座。

五类累积错误

她说大家常谈幻觉，却很少谈这些一点点累加的小错误。她分了几类：

  • 决策错误：选错了事实，比如订到秘鲁的 San Isidro 而不是加州的旧金山；或者想太多、夸大。
  • 执行错误：接入或权限出问题。她在 Skyscanner 上碰到验证码，流程就断了；也可能被锁在关键数据库外面。
  • 启发式错误：判断标准不对。模型没有考虑去 JFK 要留足时间，也没问她从曼哈顿还是布鲁克林出发。
  • 品味错误：不懂个人偏好。她说自己怕坐飞机，不坐 Boeing 737 MAX，提示词里没写，但如果真订到了她不会上飞机。
  • “完美悖论”：AI 已经能做很神奇的事，我们却因为 o1 想太久、Operator 只有人的速度而失望；就算一次做对，不稳定也让人失望。

她用一张图说明错误会复合：一个每步准确率 99% 的 Agent 和一个 95% 的 Agent，连续做 50 步后差距拉开到约 50 个百分点，而 99% 的那个也只剩约 60%。多 Agent、多步骤系统里放大得更厉害。

五条缓解办法

  • 数据整理（Data Curation）：数据分散、杂乱、模态多样，包括 Agent 自己实时产生的数据。要从第一天设计“数据飞轮”，让每次使用都让产品变好。例子是整理一份她的出行偏好，包括不坐 737 MAX。
  • 评测：数学、科学这类能验证对错的领域好办，她举了 Grok 3 发布时用的都是可验证基准；难的是“Grace 会不会喜欢这个座位”这种没有标准答案的问题。她提到 OpenAI、Perplexity、Gemini 都有 Deep Research，哪个更好取决于用途。她说有时候最好的评测就是自己去用、看感觉（Vibes）。
  • 脚手架（Scaffolding）：防止一个错误连锁扩散。她举 Lux 的被投公司 Ramp，新 AI 功能出错时有基础设施逻辑挡住，不会波及整个生产系统；必要时让人回到环节里（Human in the Loop）。对推理模型，要让 Agent 能发现自己错了并自我纠正，或者在不确定时中断执行。订机票的例子里，可以加一个核查交通的检查点。
  • 用户体验是护城河：大家用的是同一批基础模型，她说基础模型是“折旧最快的资产”。她举的例子有 Deep Research 先问澄清问题，Codeium 的 Windsurf 预测开发者下一步，法律 AI 公司 Harvey 和老系统深度集成。Lux 看好有专有数据、懂用户工作流的领域，比如机器人、硬件、国防和制造、生命科学。
  • 多模态：她说自己受够了聊天框界面。语音进步很快；Lux 投了数字化嗅觉的 Osmo；还有触觉和机器人的具身感、记忆。她展示了被投公司 tldraw 的 tldraw computer，用画笔在画布上把多个 AI 模型串起来，用户甚至感觉不到背后是大语言模型。

03. Hamel Husain（Parlance Labs）、Greg Ceccarelli（SpecStory）：怎样制定一个注定失败的 AI 战略

直播位置 0:35:11–0:51:32 · How To Build an AI Strategy That Fails

Greg Ceccarelli 是 SpecStory 联合创始人，之前做过 Pluralsight 的首席产品官，他说自己多年在高管层看着清晰的战略机会被做成灾难。Hamel Husain 是机器学习工程师和独立顾问，给很多公司做过 AI 项目。整场借用 Charlie Munger 的“反过来想”（Invert, always invert），全程讲“最坏实践”，每一条反过来就是建议。

第一步：在公司内部制造分裂

Greg 拿商学院的“价值杆”（Value Stick，由客户支付意愿、价格、成本、供应商出售意愿组成）开玩笑，改成“反价值杆”：WTP 是“一厢情愿的承诺”，告诉客户 AI 能写邮件、治气候、带来世界和平；价格是“到处都是离谱的基础设施成本”，买最贵的 GPU、不做成本收益分析；成本是一连串技术债，系统复杂到连你自己都看不懂，这样它坏了只有你能修；WTS 变成“为什么用这个系统”，答案永远是“因为 AI”。还有一条：参加所有行业会议，但回去不跟团队分享，制造信息孤岛。

第二步：定战略、发布战略

诊断造假：拿去年年报随便划几段你最看不懂的，宣布“这个要修”，不和干活的人聊。指导方针要含糊，比如“在一切领域成为全球 AI 领导者”，但不定义“一切”。行动计划是给卖花园地精的公司做保证 Google 排名第一的 AI SEO 工具、给 CEO 的猫生成 NFT。没有时间表，永远 Beta。Hamel 补充：写一份 4000 页的文档贴到所有 Slack 频道，消磨大家的耐心。

然后是用行话把人挡在外面。Hamel 讲了一个真实案例：他有一个心理健康领域的客户，本来要说“我们需要写个提示词”，团队却说“我们在构建 Agent”，结果心理健康专家觉得自己插不上话，没有进会议室。Greg 接着说，不要说“让 AI 拿到正确的上下文”，要说 RAG；不要说“用户可能骗 AI 做坏事”，要说提示词注入（Prompt Injection）。他们的反话是：让工程师来写提示词，别让最懂客户的人写。他们还做了一份“日常英语到行话”的对照指南。

第三步：动员和执行

把 AI 任务随机分给毫无相关经验的人，把数据审核外包给不了解业务的离岸团队；跳过测试，把没测过的聊天机器人直接上线给客户；把最好的工程师从赚钱的产品上抽走。

第四步：只上工具，不看流程

RAG 检索不准就换一个更贵的向量数据库；用所有现成评测指标，从不按业务定制；Agent 不好用就换框架、换供应商；不测量就做微调。Hamel 说这是“打地鼠”：每个问题都用一个工具去砸。要把评测当成“供应商的问题”，做一个塞满现成指标的仪表盘，没人分得清 3.5 分和 4.5 分有什么区别，一直攒指标，直到有一个往上走就宣布成功。Hamel 说他“最喜欢优化余弦相似度、BLEU 和 ROUGE，完全不管用户体验”，也从不跟领域专家核对。

最强的一招：不看数据

他们说这是工具箱里最有效的技巧：随身带眼罩，免得不小心看到数据。看数据是工程的事，领导要去开“关于会议的会议”；让客户当你的 QA；相信直觉。光自己不看还不够，要确保别人也看不到：把数据放进只有工程师能用的复杂系统，不给领域专家用电子表格或 Airtable，坚持买一套要一队博士才能操作、加载要六个月的定制平台。

最后他们说，这场是反着讲的，但经历是真的。他们的网站是 ai-execs，同样内容的 O'Reilly 书 2 月 27 日出版。

04. Don Bosco Durai（Privacera）：Agent 的安全与合规

直播位置 0:52:05–1:09:31 · Balancing Innovation with Security & Safety

讲者

Don Bosco Durai 是 Privacera 联合创始人兼 CTO，也是开源项目 Apache Ranger 的创建者和 PMC 成员。Ranger 做大数据的数据治理，AWS、GCP、Azure 都在用。Privacera 最近开源了一套生成式 AI 和 Agent 的安全方案（字幕里听起来叫 PAIG）。

先统一术语和风险

他的定义：Agent 是自主系统，自己推理、自己定工作流，通过任务（Task）执行动作；任务可以调用 LLM、RAG 或工具（Tool）；工具是函数，能上网、查数据库、调服务 API；记忆（Memory）是 Agent、任务和工具之间共享的上下文。

他指出一个安全问题：多数 Agent 框架把 Agent、任务和工具跑在同一个进程里。工具要访问数据库就得有凭证，调 API 就得有令牌，这些通常是权限很大的服务账号；同一进程里的其他工具、甚至任何第三方库都可能读到这些凭证和提示词，等于没有零信任（Zero Trust）。再加上 Agent 是自主的，会自己编排工作流，安全上属于“未知的未知”，攻击面比传统软件大得多。后果包括越权访问、敏感数据泄露、提示词被篡改导致错误结果，以及合规治理缺位。

他讲了一个客户：美国三大征信机构之一，做了很多 Agent，但卡在上生产。他们把 Agent 当成和人类员工一样的“用户”：人类入职要培训、要遵守法规，比如加州居民数据在没有同意时不能用于营销，欧洲数据谁能访问有规定；Agent 也得走同样的流程，否则不能上线。

三层防护

  • 上线前评测：除了评答案质量，还要做安全和合规方向的评测，最后得出一个风险分数，决定能否推上生产，第三方 Agent 也一样。他类比传统软件的上线门槛：测试覆盖率、容器漏洞扫描、第三方库 CVE 扫描、渗透测试。对应到 Agent：准备基准真值（Ground Truth），换提示词、框架或 LLM 时确认基线没变；检查第三方模型有没有被投毒；测提示词注入；测数据泄露（他举的例子是 HR Agent，员工只能查自己的薪资福利，HR 管理员可以查别人，Agent 不能让恶意用户钻空子）；测越权动作；测失控的 Agent，比如陷入死循环。
  • 执行层强制（Enforcement）：评测分数取决于执行做得多好。重点是身份认证和授权。用户的身份必须从入口一路传到任务、工具，直到最后真正访问数据或调 API 的地方，在那里按这个用户的权限执行访问控制。审批可以交给另一个专门检查结果的 Agent，设定自动批准的阈值，超过就自动拉人进来。
  • 可观测（Observability）：模型更新快，框架和第三方库在变，用户输入千差万别，测试时多是“晴天场景”。要持续监控输入变化、监控有多少个人信息（PII）被发出去。请求量大时不可能逐条看，要定失败率阈值，超过就告警；失败可能来自 Agent 本身出错，也可能是恶意用户。他说 Agent 的异常检测还很早期，未来会像传统安全里的用户行为分析一样，最后汇总成一个近实时的安全态势分数。

他说安全合规领域太大，一家公司做不完，在找设计合作伙伴和贡献者。

05. Colin Flaherty（Augment Code）：一个帮忙写出自己的编程 Agent

直播位置 1:10:07–1:27:24 · Building Self-Coding Agents

讲者和核心数字

Colin Flaherty 是 Augment Code 的创始研究员。他把 AI 开发工具分三个阶段：2023 年是自动补全（以 GitHub Copilot 为代表），2024 年聊天模型进入开发团队，2025 年是 Agent。几个月前 Augment 开始做自己的 Agent，代码库大约 2 万行，其中 90% 以上是 Agent 在人类监督下写的。

Agent 怎样写自己

  • 第三方集成：Agent 要像工程师一样用 Slack、Linear、Jira、Notion、Google 搜索。团队自己写了前几个以后，对 Agent 说“加一个 Google 搜索集成”，它能找到正确的文件和接口去加。加 Linear 集成时，底层模型没记住 Linear 的 API 文档，它就用自己之前写的 Google 搜索集成去查文档。
  • 写测试：给它一些进程管理工具（启动子进程、交互、测试死循环时不卡住、读输出）以后，它能给 Google 搜索集成写单元测试。
  • 性能优化：他说网上演示多是写功能、写测试，很少见 Agent 做优化。他们发现 Agent 很慢，就让它给自己做性能分析。它在自己代码里加打印语句，跑自己的子副本，读输出，发现有一段代码在同步加载并哈希用户仓库里的所有文件，于是加了进程池，还写了压力测试确认。

演示

他问 Agent“你能搜 Google 吗”，它找到 Google Search 工具，发了一个测试查询，回答能看到前 10 条结果。工具调用（Tool Call）的意思是：一个总控 Agent 负责规划，手里有一组可以调用的工具来和环境交互。

更复杂的一次：让它“给 Agent 的 Google 搜索工具加日志，然后生成一个示例”。它先用检索工具在本地代码库里找到目录层级很深的 Google 搜索集成文件（字幕里路径大致是 services、integrations、third_party 下的 google_search 文件），用文件编辑工具加打印语句，再想跑一个子副本看输出，结果发现没有 Google 凭证。它调用“澄清”工具问用户：要加一个 Google API 的桩（Stub），还是带你配凭证？Colin 告诉它凭证其实就在 augment 目录下的 google_api.json。Agent 接着调用记忆工具，记下凭证位置，留着以后用。最后输出了搜索“Python programming language”的日志，返回 python.org 和 wikipedia.org 等结果。

为什么几个月就能做出来

Augment 一直在做补全和聊天，重点放在可扩展、企业级的上下文引擎（Context Engine）和人机交互设计上。他说三样东西最重要：能接入代码库、Slack 等多种来源的上下文引擎；一流基础模型的推理能力；能在客户环境里安全执行命令的代码执行环境。

常见误解

  • “Agent 已经是资深工程师水平”：推特演示常是从零写一个网站，真实工程很少从零开始，环境也乱得多。
  • “按任务类别分 Agent”：有人想先做后端 Agent、再做前端 Agent、再做测试 Agent。他说这项技术是通用的，更好的思路是按复杂度分级，它在前端、后端、安全上的能力是一起提升的。
  • 拟人化：有人把弱工程师的特点套到弱 Agent 上。Agent 的长短板和人不同，可能不会算数，却能比任何人更快写完一个前端功能。

经验

知识库。他让 Agent 用 Graphite（一个基于 Git、能把 PR 叠成栈方便评审的工具）建两个叠起来的 PR。模型不知道 Graphite，就改用 git checkout。没法让 OpenAI 或 Anthropic 一夜之间重训模型，他们就做了一个知识库：一组 Markdown 文件，写 Graphite 的常用命令（比如 gt create）和禁忌，还有技术栈细节、怎么跑测试、代码风格。Agent 遇到不懂的会去搜知识库，之后就能正确运行 gt create。他说给 Agent 做入职（Onboarding）和给新员工做入职一样重要，不会让新人盯着代码库看三天。

产品管理在变。做第三方集成时不知道先做哪个，平时要猜几个先做，有 Agent 就可以一次全做出来。代码便宜以后，瓶颈变成产品洞察和设计。

上下文是相乘的。Agent 能读最近的 PR、生成一篇公告发到 Slack；演讲开头那张“代码行数随日期变化”的图也是 Agent 画的。代码库加 Slack 的价值大于两者之和。

测试决定能放多少权。他展示了一个 Agent 写的 bug：多个 Agent 并行写同一个缓存，它在 JSON 写入外面加了锁，所以不会显式报错，但写之前没有先读，会互相覆盖。这种并行加缓存的场景难测，团队没写测试，Agent 就出错了。他们的内部修 bug 基准上，把底层模型升级到新半年的版本只提升了 4%；让 Agent 能跑测试、看结果、再改，最多循环四次，提升了 20%。

他的结论：代码不会消失，因为代码是系统的规格说明，但人和代码的关系在变；测试框架（Test Harness）变得更重要，要特别注意测试薄弱的部分；代码便宜以后，重心移到产品工作和快速收集用户反馈。

06. Stephen Chin（Neo4j）、Jonathan Lowe（Pfizer）：用知识图谱支撑企业生成式 AI

直播位置 2:07:32–2:28:25 · Anchoring Enterprise GenAI with Knowledge Graphs

上午休息后，主持人回来开场。Stephen Chin 是图数据库公司 Neo4j 的开发者关系 VP，Jonathan Lowe 是 Pfizer 运营与洞察的高级总监。

失败率和业务场景

Stephen 引 Gartner 去年的预测：到 2025 年底 30% 的生成式 AI 项目会被放弃。他现场问谁参与过失败的项目，有人举手；再问谁还没上生产，剩下的人都举了手。他说 Gartner 报告里最大的失败原因是没有能解决真问题、能变现的业务场景。

Jonathan 自称“扫兴的 Debbie Downer”。他的场景是生物制药里的技术转移（Technology Transfer）：把实验室烧杯规模的工艺放大到全球多个工厂、每天生产一百万剂。建厂和建设备的人要翻几十万份科研阶段的文档、笔记和测试结果，要花好几年。他引一项研究：2019 年制造业员工平均在公司工作约 20 年，现在约 3 年，大量经验随婴儿潮一代退休而流失，所以需要把文档里、甚至人脑子里的知识交给新人。

他们把几百万份文档切块后放进图里，并且把块的结构也建进图：文档、区块、段落、行。这样做相似度搜索时，能分析哪种粒度的块返回的结果最好，逐渐改进切块（Chunking）方式。

大公司里怎样推项目

Jonathan 讲了在 5 万到 10 万人公司里推一个 AI 搜索工具要过的关卡。他的习惯是先找最底层的用户：工具要替他们去掉无聊的活，结果要准，速度要快。他说这部分现在反而最容易。

难的是上面。他讲了个故事：两周前他在总部七楼进电梯，CEO 就在里面，他像电影 Dirty Dancing 里见到 Johnny 只说出“我搬了个西瓜”的 Baby 一样，紧张到说不出话，CEO 出电梯时他只憋出一句“我在做 LLM”。他的建议是了解每一层想要什么：CEO 会有一句全公司都能记住的愿景，比如“每年改变十亿人的生活”；下一层的首席数字官、首席科学官、首席供应官各自翻译成自己的版本；再往下的二三级领导要的是降本、规避成本、更早实现收入、更均衡的人员配置，所以给他们的幻灯片里必须有数字和时间。

还有其他关卡：负责对接业务的客户伙伴（Client Partner），有的会说“研发已经有五到十个搜索引擎了，为什么再做一个”，有的会说“好主意，把它塞进供应部门的每个工具里”，范围要么变成零要么变成全部；供应商会来问“为什么不买我们的”；最后是同事的“友军火力”，“AI 搜索是我的地盘”或者“请和我做的东西集成”。他的建议是了解受众，按每一层定制说法。

为什么用图

Stephen 说 LLM 的幻觉一直是做企业 RAG 的障碍。RAG（检索增强生成）是先从企业数据里检索相关内容，再交给模型生成答案。Jonathan 说 Pfizer 有很多天然是图的数据：家谱式的序列、配方、社交网络、层级、时间序列。他还发现，数据越多地汇总进图，数据科学家和工程师理解数据全貌越快，一个新项目原来要三个月整合清理，现在三周或更短。

Stephen 提到 Microsoft 关于 GraphRAG 的论文：用 LLM 把文档切块建成图，效果更好。他把方法排成一条光谱：直接用 LLM 缺企业知识；向量数据库加基础 RAG 能带进组织知识，但答案偏泛、仍有幻觉；GraphRAG 从知识图谱拿答案，更精确。Jonathan 补充，关系数据库里很多关联因为没人建固定连接而看不到，图里关系一开始就在，搜到一个节点，周围相关的内容都能一起交给 LLM。

架构上，应用同时查向量索引和知识图谱：向量找答案，图拿到关系上相近的节点作为补充上下文，一起交给 LLM。好处还有治理（在图节点上加权限属性，控制谁能看到什么）和可解释性（能直接看节点和边来推理，不用面对向量空间里的概率）。

07. Beyang Liu（Sourcegraph）、Bruno Passos（Booking.com）：在企业软件开发流程里做出真实 ROI 的 Agent

直播位置 2:28:27–2:49:28 · Building AI Agents with Real ROI in the Enterprise SDLC

问题：几十年的实验旗标

Beyang Liu 是 Sourcegraph 的 CTO 和联合创始人，Sourcegraph 做面向大型复杂代码库的开发工具。Bruno Passos 负责 Booking.com 开发者体验的产品侧，过去一年也负责生成式 AI 创新。Beyang 开场说常见的剧本是：CEO 说要用 AI，大家因为怕落后买了 Copilot 之类的工具，半年后 CFO 问 ROI 在哪，没人答得上来。

Bruno 介绍 Booking 有 3000 多名开发者，每年跑 250 万个 CI 任务（合并请求的数量字幕不清）。Booking 靠 A/B 测试驱动，实验旗标（Feature Flag）和死代码不断留在代码库里，几十年下来代码库越来越臃肿，周期变长，开发者大部分时间在做杂活（Toil）。他说他孩子看他改幻灯片时，把留在代码里的旗标叫“代码屁”。Beyang 改写了金斯堡的诗：“我看见我这一代最好的头脑，被长达十年的死旗标迁移毁掉。”

Sourcegraph 的产品

代码搜索（像代码版的 Google）；大规模重构和迁移工具；AI 编程助手 Cody，带有代码库上下文，适合大而乱的代码库；以及这场要讲的、把杂活从开发流程里自动化掉的 Agent。他的说法是：在内循环（写代码）里增强人的创造力，在外循环里尽量自动化掉无聊的部分。

Booking 一年的时间线

  • 两年多前开始用 Sourcegraph 代码搜索，在臃肿代码库里找上下文很好用。
  • 去年 1 月：给 3000 名开发者都开了 Cody。有人用了觉得没价值就不用了。当时全公司只能用一个 LLM，还有 token 上限，他们和 Sourcegraph 一起去掉了这些限制，让每个开发者能选多个模型。他说不同 LLM 有不同专长，挖老代码和写新服务适合的模型不一样。
  • 7 月：开始培训开发者。之前觉得没用的人培训后开始天天用，变成“日活用户”。
  • 指标：1 月时主要看“节省小时数”，他认为样本太少、统计上站不住，并把市面上“节省了几万小时”的说法叫“半个胡扯”。10 月定了新的 KPI。
  • 11 月：看到每天用 Cody 的开发者快 30% 以上。他们还和 Sourcegraph 一起在 Cody 前面做了一层 API，可以接 Slack、Jira 等工具，不必只在 IDE 里用。

KPI 有四类，分短期、中期和一年的长期：变更前置时间（Lead Time for Change）、质量、代码库洞察、现代化。短期看到的是评审时间：日活用户提交的合并请求多 30%，而且每个合并请求更小，他说还不知道该怎么解读这一点。质量方面想做的是根据历史漏洞和代码库上下文预测新漏洞，以及给老代码补测试，重写时能用这些测试验收。代码洞察是找出没人用的代码、残留的旗标和性能差的代码。最终目标是把重写平台的时间从几年缩到几个月。

联合黑客松做出的三个 Agent

Beyang 说工程师用助手时自然会去调底层 API，自定义提示词，再把调用串成更长的自动化，这就是 Agent。早期很多坑，比如大家不清楚 LLM 能做什么不能做什么，于是双方飞到阿姆斯特丹办了一周黑客松。

  • GraphQL 生成：Booking 的 GraphQL schema 超过一百万 token，放不进任何模型的上下文窗口（Context Window，模型一次能读的文本上限），硬塞进去也会大量幻觉。他们做了一个系统：先在 schema 里搜到相关节点，由 Agent 判断哪些相关，再沿树往上取父节点，最后生成回答。直接做的话界面看起来一样，但输出是垃圾。
  • 自动代码迁移：老代码里有超过一万行的函数。用代码搜索、结构化的元提示词，加上分而治之。开发者之前花了几个月还没弄清问题规模，黑客松两天里就搞清了调用点从哪来、问题有多大，然后先摘容易的果子。Bruno 说开发者之前觉得没用，主要是因为不知道怎么给提示词和上下文，请专家来现场带效果很明显。
  • 代码评审：起初他们觉得这个方向没意思，已经有两打创业公司在做。但和 Booking 等企业聊下来，评审规则高度依赖组织，有一长串规则和规范，现成工具不好定制。他们做的方法是：在一个简单的平面文件里写规则，Agent 只对改动文件套用相关规则，有选择地发评论，追求精确率（Precision）高于召回率（Recall），尽量少噪音。

下一步：声明式规则

Bruno 想把 CI 里报的错提前到 IDE 里，以“这里有错、这是修法”的形式出现，最终让服务能自我修复；开发者在提示词库里攒的提示词也可以自动拿去问代码库。Beyang 补充，他提到《人月神话》：成功的软件会被自己的成功拖累，需求和 bug 越来越多，为了竞争不断欠技术债，贡献者越来越多，统一的愿景和标准就散了。用声明式的方式，让资深工程师和架构师定义代码库必须满足的约束，在评审时和编辑器里同时执行，不管代码是人写的还是 AI 写的。Bruno 说合规规则也适合这样声明。

Bruno 最后强调：这一年最重要的是教育。带着整个业务部门做两天工作坊和黑客松，人出来以后就变成热情的日活用户。

08. Waseem Alshikh（Writer）：在金融场景里评测领域模型

直播位置 2:49:31–3:01:00 · Building Trust in Enterprise AI: Evaluating Domain-Specific LLMs for Real-World Financial Scenarios

要回答的问题

Waseem Alshikh 是 Writer 的联合创始人兼 CTO。他说 Writer 的故事就是 Transformer 的故事，从早期的编码器、解码器模型做起，现在发布了大约 16 个模型，还有 20 个在路上，分两类：通用模型（字幕里是 Palmyra X 系列的几个版本）和领域模型（创意、金融、医疗等）。2024 年初他们注意到，通用模型在基准上的准确率普遍到了 80% 到接近 90%。公司内部于是有了一个问题：还值得继续做领域模型吗？还是只做通用模型、微调一下、或者走推理模型路线就够了？

评测怎么设计

他们做了一个模拟真实场景的金融评测集（字幕只听到 “fail”；Writer 公开发布的这个基准名为 FailSafeQA），数据、白皮书和排行榜都已在 GitHub 和 Hugging Face 开源。故障分两类，每类三种：

  • 查询故障：拼写错误、语法错误等错拼查询；缺关键词的不完整查询；领域外查询（非专业人士提问，或复制粘贴了一段泛泛的内容）。
  • 上下文故障：缺失上下文（问题问的内容在给的文档里根本没有）；OCR 错误（纸质文件转文字时字符出错、词粘在一起）；无关上下文（上传了完全不相干的文档）。

评价看两件事：模型能不能给出正确答案，以及能不能遵循给定的上下文（Context Grounding）。参评的有普通聊天模型和多个“思考”模型。

结果

他说思考类模型很少拒答，乍一看是好事。但给错上下文、错数据时，它们不会指出问题，照样给出答案，幻觉率高得多。在查询故障上，几乎所有模型都能答，推理模型分数还略高，错拼、不完整、领域外都处理得不错。到了上下文遵循，尤其是文本生成和问答任务，表现就差了。他点出 o1、o3 这类更大的思考模型在上下文遵循上反而最差，比其他模型差 50% 到 60%，答案常常出自给定上下文之外；较小的模型反而做得更好。他据此质疑这到底是“思考”还是只是思维链（Chain of Thought）。

即使最好的模型，在稳健性和上下文遵循上也没超过 81%。他说这听着不错，但意味着每 100 个请求有将近 20 个完全错。他的结论：以今天的模型，需要一整套系统，包括 RAG、上下文遵循机制和护栏（Guardrails，挡住不安全或不可靠输出的机制）；而开头的问题，答案是还要继续做领域模型，因为准确率虽然在涨，上下文遵循还远远落后。

09. Toki Sherbakov、Prashant Mital（OpenAI）：OpenAI 怎样和企业合作，以及构建 Agent 的四条经验

直播位置 3:01:34–3:18:07（Prashant 的 Agent 部分从 3:09:47 开始）· OpenAI for VPs of AI

Toki：企业的 AI 之路

Toki Sherbakov 是 OpenAI 解决方案架构负责人，Prashant Mital 是技术人员。Toki 先讲 OpenAI 的组织：研究团队约 1200 名研究员做基础模型；应用团队把模型做成 ChatGPT 和 API；他们所在的市场团队把产品交到企业手里，再把一线反馈带回产品和研究。

企业通常经历三个阶段，不一定按顺序：让员工具备 AI 能力（通常从 ChatGPT 开始）；自动化内部运营（简单的用 ChatGPT，复杂或需定制的用 API）；把 AI 放进面向终端用户的产品（主要用 API）。战略上，他说要先问的是公司整体业务战略是什么，再看技术和它在哪里交汇；然后挑一两个高影响的用例做出来；再通过培训推广、卓越中心、共享技术平台把能力铺到全公司。

一个用例的典型三个月：先构思、定范围、做架构评审、定成功指标和 KPI；大部分时间花在开发迭代上（调提示词、加 RAG 等），OpenAI 会通过工作坊、答疑、结对编程参与；然后用事先定好的评测做 A/B 测试和小范围上线；最后上生产、做规模优化，之后持续维护。OpenAI 会提供新模型和功能的抢先使用。他说自己看不到 18 个月的路线图，大概能说出接下来两个季度会发生什么，这种前瞻对客户提前布局很重要。

案例是纽约的 Morgan Stanley：给财富顾问做内部知识助手，查研究报告、实时行情等。一开始准确率只有 40% 到 45%。他们逐步加方法：HyDE 检索（先让模型生成一个假设答案，再用它去检索）、微调的 Embedding、不同的切块策略；再加重排序（Reranking）和分类步骤，到了 85%；目标是 90%，最后通过提示词工程和查询扩展做到 98%。

Prashant：构建 Agent 的四条经验

Prashant 说 OpenAI 既和做前沿 Agent 的客户一起工作，内部也在做 Deep Research 和 Operator。他的 Agent 定义：一个模型，有指令（通常是提示词），能用工具检索信息、和外部系统交互，整体包在一个执行循环里，何时结束由模型自己决定。每一轮里，Agent 接到自然语言指令，决定要不要调工具，执行工具，用返回值合成回答，判断目标是否已达成。

  • 先用原语，少用抽象。用框架起步很诱人，他自己也是这样开始的，很快就能出概念验证。问题是你不知道系统实际怎么运行、用了哪些原语，在理解约束之前就把设计决策推迟了，也就没法优化。更好的做法是先用原始 API 调用、自己记录结果和失败，弄清任务怎么拆、哪里出错；当发现自己在重复造轮子（比如又写一遍 Embedding 策略或模型打分器）时，再引入抽象。他说很多团队花大量时间挑框架，其实关键的是理解数据、失败点和约束。
  • 从单个 Agent 开始。很多团队一上来就做多 Agent 系统，Agent 调 Agent、动态协调，听起来强大，但太早做会带来很多未知。建议先做一个专门处理一个任务的 Agent，给少量用户上线，观察真实瓶颈：长对话里的幻觉、延迟高导致没人用、检索差导致不准。复杂度应该随着发现更多失败情形和约束逐步增加。
  • 复杂任务用 Agent 网络和交接（Handoff）。Agent 网络是多个专门 Agent 各管一段子流程；交接是一个 Agent 把对话控制权转给另一个，像电话转接，但完整对话历史保留，新 Agent 什么都知道。示例是全自动客服：用 GPT-4o mini 做分诊，GPT-4o 的争议处理 Agent 和用户对话，用 o3-mini 推理模型做判断客户是否有资格退款这类要求准确的任务。他说保留历史、同时替换模型、提示词和工具定义，灵活度足够覆盖很多场景。
  • 护栏并行跑。主提示词保持简单、只管目标任务的“顺利路径”，护栏不放进主提示词，单独并行运行；GPT-4o mini 这类又快又便宜的模型让这更可行。高风险的工具调用或回复（比如发退款、展示用户账户信息）要等所有护栏返回后再执行。示例里有一个防提示词注入的输入护栏和几个检查回复的输出护栏。

一路走来

Shirsha Chaudhuri 从班加罗尔来，在 Thomson Reuters 把 AI 带进团队和业务流程。她说要讲的故事在公司内部有，在各种开发者聚会上也反复听到。她开场说想用 AI 找个笑话暖场，结果 AI 讲的笑话都不好笑。

两个工作流的例子

一个是客服：客户打电话报账单、发票或功能问题，客服可能用 RAG 回答，或查内部工单；找不到就提交给 IT 运维做二线支持；还不行就到工程团队做三、四线支持，用观测工具定位，跑脚本出新版本，跑回归和集成测试，最后修复、更新工单、满足 SLA。另一个是内容生产：作者或内容专家看到某个触发事件，获批后做研究、写稿，编辑和审稿人审几轮，交给出版团队排版发布。她说这两个流程里很多环节都能交给 Agent，人留在审批环节，但问题是要不要沿用原来的流程设计。

缺的拼图

  • 连接器（Connector）：她在展区和厂商聊，大家都说做 Agent 方案总需要一层连接现有 IT 系统。她的数据是 71% 的财富 500 强公司还在用大型机，全球 68% 的 IT 生产负载跑在大型机上，很多信用卡交易也在大型机上完成。从大型机到 Agent 工作流，中间隔得很远。
  • 可靠性和 ROI：业务方看的是 0 或 1：付钱给 Agent 以后，还要不要继续付人工工时？
  • 能一起重新想象流程的人：AI 从业者只能想到一定程度，需要领域专家一起设计。
  • 标准化：Agent 怎么构建、怎么打包、怎么部署，还没有成熟的规范。
  • 数据和系统：Agent 要的上下文分散在各种 IT 和业务系统、日志、聊天记录、工单里，找出哪个系统有什么、怎样把同一笔交易在多个系统里关联起来，常常是卡点。
  • 协作式 UX：她最看重这一条。Agent 是助手，人的角色是什么、人和 Agent 怎样互相支持，她说还在等新的想法。
  • AI 治理：已有的伦理和负责任 AI 规范，要怎样落到 Agent 架构的各层。
  • 控制权：哪些步骤要确定性执行，哪些让 Agent 自己决定，人在什么时候介入。
  • Agent 的生命周期：技术变得这么快，怎样把最新能力更新到已经部署的 Agent 里。

12. Aparna Dhinakaran（Arize）：怎样评测 Agent

直播位置 5:06:07–5:27:47 · Ensure AI Agents Work: Evaluation Frameworks for Scaling Success

为什么领导层也要懂

Aparna Dhinakaran 是 AI 评测和可观测公司 Arize 的联合创始人兼 CPO，她说 Arize 当天刚宣布 C 轮融资。她提醒这场会比较技术，但领导层也需要理解怎样确认上线的东西真的有效。她先说语音 Agent：全球呼叫中心每年有超过 10 亿通电话，语音 API 已经在改造呼叫中心。她举了 Priceline 的语音助手 Penny，能不打字、全程语音订完一次度假。多模态 Agent 需要额外的评测。

Agent 的三个组件

  • 路由器（Router）：像老板，决定下一步做什么。以电商 Agent 为例，用户说“我要退货”“推荐点东西”“有没有折扣”，路由器决定调客服技能、折扣技能还是商品搜索技能。
  • 技能（Skill）：真正干活的逻辑链，里面可能是 LLM 调用，也可能只是 API 调用。
  • 记忆（Memory）：存多轮对话的状态，免得 Agent 忘了你之前说过什么。

她说不管用 LangGraph、CrewAI、LlamaIndex Workflows 还是不用框架，都能看到这三种模式。她用一个开源项目展示了一个 Agent 的 Trace（追踪记录，把 Agent 每一步调用记录下来，工程师靠它排查问题）：用户问“我的 Trace 延迟有什么趋势”，路由器先调一个技能跑 SQL 查询收集所有 Trace，回到路由器，再调数据分析技能。路由器可以被调用多次，记忆贯穿全程。

每个组件怎么评

  • 路由器：有没有调对技能（问紧身裤却被送去客服或折扣），以及参数有没有传对（材质、价格区间等）。她现场问有多少人在评测 Agent、多少人在评测路由器层，举手的人不少，她说这一屋子很厉害。
  • 技能：以 RAG 技能为例，评检索块的相关性和生成答案的正确性。可以用 LLM-as-a-Judge（让另一个模型按标准打分），也可以用代码写的评测。
  • 路径（她称为收敛 Convergence）：她说这是团队最难评的。同一个技能跑几百次，理想情况是总在五六步左右完成。她说同一个技能用 OpenAI 和 Anthropic 分别实现，步数有时差别很大。目标是步数精简而且稳定。

语音的额外评测

她引电影 Her 里 Samantha 同时和 8000 多人聊天的桥段，说语音应用是最复杂的一类。除了转写文本，还要单独评音频片段：语音转文字准不准，用户意图，语音质量，语气是否前后一致。很多语音 API 是先发音频、后生成转写，所以只看文字是不够的。

Arize 自己的 Copilot

Arize 产品里有一个 Copilot，帮用户调试、总结、用自然语言搜索。他们用自己的工具评测它：最上层评整体回答（这次搜索结果对不对），然后评是否选对了路由、传对了参数，最后评技能是否正确完成。她说要在整个 Trace 的每一层都有评测，出错时才能定位是路由器、技能还是别处的问题。

问答

  • 怎么测收敛：用同样的输入反复调同一个技能，一次到一百次，记录每次步数；有的团队会稍微改写输入，看会不会多走几步。
  • 护栏：她说这算更主动的评测，会拦截或改动输出，但会增加延迟，主要适合对外应用和高风险场景，要确定真的需要。
  • 多模态：语音比视频、图片常见得多。一个客户的语音 Agent 开头语气温和、后来变得生硬，只评转写发现不了。图片和视频常见做法是先总结画面内容再评，加上画质评测。
  • 数据安全：可观测平台一般可以部署在客户自己的 VPC 里。
  • 长语音对话的上下文：上下文窗口装不下来回的音频和转写，常见做法是总结历史状态、总结音频片段，并假设越近的内容越重要。

13. Diamond Bishop（Datadog）：从不睡觉的 DevOps 工程师

AI 值班工程师

目前私测中的 Agent 之一。告警一来它就主动启动：先读 Runbook（运维手册）、拿告警上下文，然后像人一样去查日志、指标和 Trace，循环推进。人还没打开电脑，它已经整理好摘要。它会提出多个假设，用工具去跑查询，逐个验证或推翻。找到根因后可以建议补救，比如把另一个团队拉进来，或者扩缩容；如果你在 Datadog 里已经配了工作流，它能理解并调用。事故结束后它还会写复盘报告（Postmortem），包括它做了什么、人做了什么。

他们做了一个人机协作页面：能看到每个假设为什么提出、Agent 找到了什么、执行了 Runbook 的哪些步骤，还能像问初级工程师一样追问它为什么这么做。他说这样可以逐步建立信任。

AI 软件工程师

另一个 Agent 更主动，盯着错误追踪：自动分析错误、找原因、给出代码修复，目标是从源头减少值班事故。演示里它发现了一个递归问题，给出修复，还写了一个递归测试防止复发，可以直接在 GitHub 开 PR 或在 VS Code 里打开 diff。

四条经验

  • 界定任务以便评测：先从人的角度定义“要完成的工作”（Jobs to be Done），一步步写清楚，想好另一个人会怎样检查。所以他们做垂直的、针对具体任务的 Agent，不做通用 Agent。每一步尽量可测量、可验证。他说这是他们最大的痛点：演示很快能做，验证和持续改进很难。领域专家要当设计伙伴或任务验证者，不要让他们去写规则代码，因为随机性模型和专家的思维方式差别很大。评测要先想，“因为没先想评测犯过的错多到让人沮丧”；要有离线、在线和不断更新的评测集，有端到端的度量，并做好埋点收集用户反馈。
  • 组队：不需要一堆机器学习专家，市面上也没那么多。用一两个专家打底，配上一群乐观、会写代码、愿意快速尝试的通才。他作为后端工程师也承认，前端和 UX 比他希望的更重要。队员最好自己就每天用 AI。
  • UX 在变：老的交互模式在变化，要适应。他偏向让 Agent 越来越像人类队友，少加新页面和按钮。
  • 可观测不能事后补：Agent 是复杂的多步工作流。Datadog 有 LLM Observability，把自托管模型和 API 模型的调用放在同一个界面里看。但 Agent 的调用可能有几百次、来回循环，平铺的列表看不出问题，所以他们做了“Agent 图”视图，出错的节点标红，放大就能看到错误在哪。

应用层的“苦涩教训”和未来

他借用“苦涩教训”（The Bitter Lesson，Rich Sutton 的观点：能利用更多算力的通用方法最终胜出）说应用层也一样：你花大力气针对某个任务微调，新模型一出就把它解决了。所以系统要能随时换模型，不要绑死在一个模型上。

他还认为五年左右 Agent 会超过人类成为 SaaS 产品的主要用户（他说有人说一年，有人说十年，他取中间）。所以产品也要为外部 Agent 设计，他自己用 MCP 很快就让 Claude 直接用上了 Datadog。MCP（Model Context Protocol）是 Anthropic 推出的开放协议，让模型以统一方式连接外部数据和工具。他预计很快能提供一整队“DevSecOps Agent”供雇用，小公司可以用 Cursor、Devin 这类自动开发者写产品，用 Datadog 这类 Agent 管运维和安全。

14. Paul Gilbert（Arista Networks）：2025 年怎样自建 AI 数据中心网络

直播位置 5:44:41–6:07:23 · How to Build Your Own AI Data Center in 2025

讲者和训练与推理的差别

Paul Gilbert 是 Arista Networks 的技术负责人，常驻纽约，设计企业网络，他自称“管道工”。这场讲的是训练和推理背后的网络基础设施。他展示了一张给企业客户讲 GPU 规模的图：一个模型训练用了 2048 块 GPU、跑一到两个月，微调和对齐之后推理只要 4 块 H100。他说有了思维链和推理模型，推理的负载变大了很多，以后会怎样他也不确定。

两张网

后端网络连 GPU，完全隔离，不接任何其他东西，因为 GPU 贵、耗电、难买。每台服务器 8 块 GPU，接到 Leaf 交换机，再到 Spine 交换机（两层的叶脊架构）。前端网络连存储，GPU 同步计算后再要更多数据，就是这样循环。后端 GPU 会以 400 Gbps 线速工作，他说做了这么多大数据中心也没见过这种流量。协议上尽量简单，用 iBGP 或 eBGP。

他展示 H100 服务器背板：8 个 400G 的 GPU 端口，加 4 个 400G 以太网端口，一台服务器就能往网络上打 4.8 Tbps。Blackwell 一代（他说大约三月发布）是 800G，每台最高 9.6 Tbps；他说企业里习惯的服务器带宽通常只有一到四个 100G 端口。他说 Nvidia 的“纵向扩展”（Scale Up）他在企业里很少见，买来的 DGX 或第三方 HGX 服务器不往里加东西；网络做的是“横向扩展”（Scale Out），从小规模加到几千甚至云厂商的几十万块 GPU。

和传统数据中心有什么不同

  • 软件：他们要理解 NCCL（Nvidia 的多 GPU 集合通信库），因为它的集合通信方式决定流量怎样打到网络上。
  • 故障模式：传统 Web 应用、数据库挂一台有负载均衡切换；AI 集群里 GPU 互相通信，一块失败整个任务可能失败或要从检查点恢复。光模块、线缆的问题在几千块 GPU 规模下会频繁出现。
  • 突发流量：几千块 GPU 会同时以 400G 爆发。
  • 无超订：传统数据中心以前 1:10，后来降到约 1:3，AI 后端网络必须 1:1，带宽全给满。
  • 负载均衡：传统做法按五元组哈希（他称为熵），但 GPU 流量常常只有一个 IP，可能全挤到一条上行链路，造成大量丢包。Arista 改为按上行链路带宽占用率分配，能做到约 93% 的利用率；还有按集合通信做的“集群负载均衡”。
  • 电力：普通机柜 7 到 15 kW，一台 8 卡服务器就要 10.2 kW，一个机柜只能放一台。企业开始建 100 到 200 kW 的液冷机柜，风冷不可能。
  • 流量方向：GPU 之间是东西向流量，最猛；向存储要数据是南北向，存储目前大多只能到 100 到 200G。
  • 拥塞控制：用 RoCEv2（在以太网上跑 RDMA 的协议；RDMA 是内存直接到内存的读写，绕过 CPU）。里面有两部分：ECN 是端到端的“请慢一点”，拥塞时标记数据包，接收方通知发送方降速，一段时间没有标记再提速；PFC 是“缓冲满了，停”，相当于急刹车。一个端口、一块 GPU 慢下来，同步的所有 GPU 都会被拖慢。
  • 网络很简单：没有 DMZ、防火墙、四到七层服务，后端完全隔离。

Arista 的功能

  • 按模型收发的包大小调交换机缓冲区，缓冲是交换机里昂贵的资源。
  • RDMA 有十几种错误码，拥塞丢包时会把包或包头拷贝出来，告诉你为什么丢。
  • 装在 Nvidia GPU 服务器上的一个 Agent（一段 API 和代码），和交换机互相核对 PFC、ECN 配置，并上报收发包和 RDMA 错误统计，这样能分清是 GPU 的问题还是网络的问题。
  • 智能系统升级：升级交换机软件（加功能或修安全漏洞）时不必下线，比如 1024 块 GPU、64 台交换机的网络，升级时 GPU 照常工作。
  • 其他建议：点对点地址用 /30、/31，地址不够可用 IPv6；路由用 BGP；多业务线共用时用 EVPN/VXLAN 做多租户；一定要部署 RoCE，否则网络会“熔化”而你不知道原因；监控和遥测要让运维中心比开发者先发现问题。

他展示了几种规模的拓扑，包括一个 4000 卡的集群，以及 7800 系列 16 槽机箱，一台能接 576 个 800G 或 1152 个 400G 端口。他还提到 Ultra Ethernet Consortium：以太网三十年没怎么变，这个联盟在拥塞控制、包喷洒（Packet Spraying）、网卡之间协作上做改进，1.0 版预计 2025 年第一季度批准，产品可能三、四季度出现，云厂商很感兴趣，因为它把更多工作放到网卡里。他说 800G 已经用了一年，1.6T 可能年底到。最后他说，对他们来说最重要的指标是任务完成时间（Job Completion Time）：如果昨天一个任务一小时，今天要四天，多半是网络的问题。

15. Alexander Bricken、Joe Bailey（Anthropic）：给 AI 负责人的 Anthropic 实践建议

直播位置 6:07:38–6:28:16 · Anthropic for VPs of AI

讲者和 Anthropic 介绍

Alexander Bricken 在 Anthropic 的应用 AI 团队，和客户一起做技术落地，再把经验带回产品和研究。Joe Bailey 在市场团队（GTM），加入一年多，见证了模型从 Claude 2.1 到现在。他们说内容来自和很多同事聊过的几百次客户合作。

Alexander 介绍最新模型是去年 10 月下旬的 Claude 3.5 Sonnet（新版），在编程上领先，在 SWE-bench（一个 Agent 编程评测）上仍居榜首。Anthropic 的研究方向在模型能力、产品研究和安全之间有交叉，他说最有区别的是可解释性（Interpretability），即逆向分析模型怎么“想”，进而引导它。他们把可解释性分成几个逐层递进的阶段：理解、检测（识别具体行为并打标签）、引导（Steering）、可解释，最后一步才能带来业务价值，他说现在大概只走到前四分之一到一半。他推荐了 Towards Monosemanticity 和 Scaling Monosemanticity 两篇论文。

他举的例子是：问模型今天 NBA 比分，它答“Steph Curry 得了 30 分”，会激活某个“著名 NBA 球员”特征（他用编号 304 举例），这个特征是一组神经元，在所有提到著名篮球运动员的地方都会以可识别的模式激活。Golden Gate Claude 是引导的例子：把“金门大桥”方向的激活调高，问它卧室刷什么颜色，它会说刷成金门大桥那样的红色。

先回到核心问题

Joe 说他们常劝客户回到基本问题：你的产品要解决的核心问题是什么，AI 能怎样帮它，不要停在聊天机器人和摘要上。他举了一个员工入职和技能提升平台：简单做法是总结课程、做问答机器人；更大的想法是按每个员工的情况超个性化课程，学得快的自动提高难度，是视觉型学习者就自动生成视觉内容。他还提到报税、法律、项目管理领域的客户，他们用 AI 改善核心体验，而且报税这种场景不能有幻觉。

产品方面：API 用来把 AI 嵌进自家产品，Claude for Work 给整个组织日常用；模型也可以通过 AWS Bedrock 和 Google Cloud Vertex AI 使用，部署在现有环境里，不用管新基础设施。他说不管第一方还是第三方接入，Anthropic 的支持都一样。

应用 AI 团队怎样介入

Alexander 的团队帮客户设计架构、做评测、调 Claude 的提示词，再把一线经验带回公司。他提到同事 Barry 发表的 Building Effective Agents（Barry 第二天会讲），以及 Anthropic 推出的 MCP，Mahesh 周六会带 MCP 工作坊。他们主要深度介入用 Claude 用得多、在具体领域遇到难题的客户：启动一个冲刺（Sprint），处理 LLMOps、架构或评测问题，帮客户定义重要指标，把迭代结果放进 A/B 测试环境，再上生产。

Intercom 的案例由 Joe 讲。Intercom 是 AI 客服平台，有 AI Agent Fin。双方先做了两周冲刺：拿 Fin 最难的提示词，和 Anthropic 帮忙用 Claude 调出来的版本对比，效果很好；接着做了大约两个月，优化所有提示词。最后 Intercom 的基准显示 Anthropic 优于他们原来用的 LLM，于是改用并推出 Fin 2。Intercom 按“解决”计费，所以大家都有动力让模型真正解决问题，不做“推诿机器”。他给的数字是 Fin 2 最高能解决 86% 的客服量，开箱即 51%。Anthropic 自己的支持团队比较多个方案后也用了 Fin，看到相近的解决率。他说 Claude 还让语气、回答长度更容易调，对退款政策这类规定的理解也更好。

常见错误和最佳实践

  • 评测要先行。常见错误是先花大量时间搭好工作流，再回头做评测。Alexander 说评测才是把你引向好结果的东西。数据有问题时可以用 Claude 清洗和对账。也不要只凭感觉，跑几条看着不错就上线，样本要有代表性、有统计意义。他把用例想成一个隐空间（Latent Space），调提示词、用提示词缓存等手段，就是在这个空间里移动、在几个“吸引子状态”之间找最优点；改一条指令，Transformer 的注意力机制会带来什么结果，事先不知道，只能靠评测实证。他对客户说“评测就是你的知识产权”，谁更快找到最优点谁有竞争力。要提前建遥测做回测，要设计有代表性的测试用例，包括离谱的问题，比如一个孩子跑到你的客服 Agent 上问“Minecraft 里怎么杀僵尸”。
  • 先定指标的取舍。智能、成本、延迟三者一般只能顾到一两个，要提前定好。客服场景要在 10 秒内回复，否则用户会离开；金融研究分析 Agent 花 10 分钟也没关系，因为后面是资本配置决策。UX 也能缓解，比如加一个跳动的“思考中”框，或者让用户先看点别的。
  • 微调不是银弹。很多客户一上来就说要微调，他说“又来了”。微调像对模型做脑外科手术，可能削弱它在其他领域的推理；很多人连评测集都没有就想微调。应该先试别的方法，有清晰的成功标准，只有在特定领域达不到时再微调，并且能证明成本和投入值得。不要让“等微调”拖慢项目，先推进，需要时再把微调模型换进来。
  • 别的方法很多：基础的提示词工程之外，提示词缓存（Prompt Caching，复用重复的长前缀）能降低 90% 成本、提速 50%，这样不必为了提速删指令；Contextual Retrieval 能显著改善检索；还有开箱即用的 Citations（引用）功能，以及 Agent 架构。

16. Heath Black（SignalFire）：用数据招 AI 人才

讲者和数据来源

下午休息后的最后一段。Heath Black 是风投 SignalFire 的产品董事总经理。他本科后读的是爱尔兰文学硕士，两个儿子都以爱尔兰作家命名。2009 年进创业公司，在 Chirpify 做出最早的对话式聊天机器人之一；之后在 Reddit 做实验性业务线和信任与安全工具；在 Meta 做了 Messenger 里的第一个助手 M，又当了 Ray-Ban 眼镜 AI 助手的第一位产品经理。他说 SignalFire 是“像科技公司一样建的风投”：访谈了 500 位创始人，围绕他们的痛点建 AI 工具和投后团队。数据来自 SignalFire 的平台 Beacon，追踪 6.5 亿名员工、8000 万家公司、2 亿个开源项目。他从四个方面讲：筛选、地点、时机、叙事。

  • AI 创业公司招的工程师里，来自顶尖学校的比例从 2015 年的 27% 降到 2023 年的 15%，有博士学位的从 16% 降到 7%，都降了约一半。

17. Xiaofeng Wang（LinkedIn）：搭建 LinkedIn 生成式 AI 平台的经验

直播位置 7:26:07–7:43:10 · Lessons from Building LinkedIn's GenAI Platform

平台是怎样一步步长出来的

Xiaofeng Wang 是 LinkedIn 生成式 AI 基础团队的工程经理。他按产品的三代来讲平台：

  • 2023 年：第一个正式的生成式 AI 功能是 Collaborative Articles，用 GPT-4 生成长文章，再邀请会员评论，属于“提示词进、字符串出”的简单应用。团队做了统一访问模型的网关、做提示词工程的 Python Notebook。当时线上用 Java、后端用 Python，两套技术栈，还谈不上平台。问题是没法把 LinkedIn 自己的丰富数据放进产品体验。
  • 2023 年中：第二代，内部叫 Copilot 或 Coach。例子是根据你的档案和职位描述，用 RAG 告诉你是否适合这个职位。平台开始成形：在 LangChain 之上做 Python SDK 编排 LLM 调用，并接入 LinkedIn 的大规模基础设施；统一技术栈，因为把 Python 提示词搬到 Java 里成本高、还容易出错；开始做提示词管理（他叫“提示词的唯一事实来源” Prompt Source of Truth），给提示词做版本和元提示词结构；最重要的是对话记忆，记录 LLM 交互和检索内容并注入最终产品，用来做对话式机器人。
  • 去年：第一个真正的多 Agent 系统 LinkedIn Hiring Assistant，帮招聘者自动做发职位、评估几百个候选人、联系候选人等繁琐的活。平台跟着变成 Agent 平台：把 Python SDK 扩展为大规模分布式 Agent 编排层，处理分布式执行、重试、流量切换；做技能注册中心（Skill Registry），开发者把 API 发布进去，解决技能发现和调用；记忆从对话记忆扩展到“经验记忆”，从 Agent 和用户的交互中提取、推断上下文知识，并分成工作记忆、长期记忆、集体记忆几层；还在 OpenTelemetry 之上自建可观测，记录细粒度的遥测数据，可以回放 Agent 调用，并加一层分析指导优化。

他把平台分成四层：编排、提示词工程工具、技能调用、内容与记忆管理。旁边还有兄弟团队负责微调开源模型的建模层、确保 Agent 符合政策的负责任 AI 层，以及托管模型的机器学习基础设施。平台的价值是给这个复杂生态提供统一接口，比如在 SDK 里改一个参数就能从 OpenAI 模型换到自家模型（提示词工程还得重做，但省掉了基础设施集成的麻烦）；而且集中式平台方便落实最佳实践和治理。

为什么要建这个平台

他的回答是要建。传统 AI 系统里，模型优化和模型服务界限清楚，AI 工程师和产品工程师可以用两套技术栈、不碰同一个代码库；生成式 AI 系统里这条线消失了，每个人都在优化整体系统表现。他借用 Berkeley AI Research 的“复合 AI 系统”（Compound AI System）定义：用多个相互作用的组件完成 AI 任务的系统，组件包括多次模型调用、检索器、外部工具。这需要跨越 AI 工程和产品工程两种技能，平台就是用来弥合这个差距的。

怎样招人

他从团队顶尖工程师身上总结出理想画像：能做基础设施集成的强软件工程师，有设计接口的开发者产品思维，有 AI 和数据科学背景，能跟上新技术又亲自动手。他说这种人比独角兽还难找，所以实际上要取舍：

  • 核心技能上，把强软件工程能力排在 AI 专长前面，他承认这可能有争议。
  • 招潜力，不招经验或学历，因为领域变得太快，经验很快过时。
  • 组一个多样化的团队：全栈工程师、数据科学家、AI 工程师、数据工程师、顶尖研究型大学的应届生、非典型背景的人，放进同一个项目，强工程师会在协作中补齐技能，逐渐长成理想画像。
  • 批判性思维：他们开会常说，现在做的东西一年甚至半年内就会过时，所以要持续评估开源包、和供应商聊，并主动废弃自己的方案。

要点

  • 技术栈尽量选 Python。他们从 Java 加 Python 起步，内部争论过，最后选 Python，因为研究和开源多在这里，经验上也能扩展。
  • 关键组件：提示词的唯一事实来源，像管理模型参数一样做版本控制，避免误改生产提示词；记忆，用来把丰富数据注入 Agent 体验；把 API 升级成 Agent 能方便调用的技能。

18. Douwe Kiela（Contextual AI）：企业 RAG Agent 的十条经验

直播位置 7:43:51–8:00:16 · Specialized RAG Agents（章节名：10 Lessons Learned from the Frontier of AI）

上下文悖论

Douwe Kiela 是 Contextual AI 的 CEO 和联合创始人，研究背景出身，他说 RAG 最初就是他在 Facebook AI Research 时和团队提出的。他先给出反差：McKinsey 估计生成式 AI 能给全球经济增加 4.4 万亿美元，但 Forbes 的研究说只有四分之一的企业真的从 AI 拿到价值，很多 AI 负责人正被问 ROI 在哪。

他用机器人领域的莫拉维克悖论（Moravec's Paradox）解释：下棋赢人类比让机器人吸尘、自动驾驶容易得多，看着难的反而容易，看着容易的反而难。企业 AI 里类似的是“上下文悖论”：模型写代码、解数学题比大多数人强，但把信息放进正确的上下文，这件人类专家毫不费力的事，模型仍然不擅长。他画了一张图：现在大多数应用在左下角，是通用助手带来的便利；企业想要的是右上角的差异化价值和业务转型，而越往上走，对处理企业内部上下文的要求越高。他说这就是他两年前创办 Contextual AI 的原因。

十条经验

  1. 看系统，不看模型。在企业部署里，语言模型通常只占整个系统的 20%，企业部署通常就是 RAG 系统。新模型一出大家都盯着模型，很少想周围的系统。一个普通模型加一套很好的 RAG 管线，比一个很强的模型加一套糟糕的管线好得多。
  2. 专业知识是燃料，专门化优先于 AGI。公司里有大量机构知识，通用助手很难达到你公司专家的水平。他们公司的说法是“Specialization over AGI”，在你理解的具体问题上做专门化能走得更远。
  3. 规模化的数据是护城河。人会流动，长期来看公司就是它拥有的数据。很多企业以为得先把数据清洗干净才能用 AI，他说要做的是让 AI 能在大规模的嘈杂数据上工作，这很难，但做成了就是差异化。
  4. 试点容易，生产难。现在用框架放几份文档就能做出 RAG 演示，给 10 个用户用都说好，CEO 看了就说三个月内裁掉一半客服换成 AI，你就被套住了。几万到几百万份文档、几千个用户、企业里可能两万个用例、安全合规要求，现有开源工具都扛不住。所以从第一天就为生产设计，不为试点设计。
  5. 速度比完美重要。尽早交给真实用户（不是友好的测试者），哪怕只是勉强能用，然后靠反馈逐步爬坡（Hill Climb）。等太久想做到完美，就很难从试点跨到生产。
  6. 别让工程师做无聊的事。比如每个用例、每个框架都要琢磨最优切块策略、基础提示词。这些可以交给现在的平台抽象掉，工程师应该想怎样交付业务价值、怎样比竞争对手强。
  7. 让 AI 容易被用上。他常问已经上了生产的公司有多少人在用，答案经常是几乎为零：要么过模型风险评审时被削得没什么用，要么大家不知道怎么用。越贴近企业已有的工作流，真实使用就越多。
  8. 尽快让用户“哇”一下。他举 Qualcomm：Contextual AI 在 Qualcomm 全球上线，几千名客户工程师在用。有一位工程师找到一份藏了七年、自己都不知道存在的文档，多年的问题一下有了答案。他说这种小胜利对推广很重要，可以围绕它设计新用户上手流程。
  9. 准确率只是门槛，要管的是不准确的那部分。100% 很难甚至不可能，到 90% 或 95% 也许可以，企业更关心剩下的 5% 到 10% 出错时怎么办。办法是可观测：认真评测，在受监管行业要有审计记录（Audit Trail），说明“这个答案是因为在这份文档里找到的”；RAG 里的归因（Attribution）因此很要紧；还可以对系统生成的论断做后处理核查，确保每条都有出处。
  10. 要有野心。他说很多项目失败是因为目标定得太低：上线了生成式 AI，结果只是回答“我们的 401k 供应商是谁”“我有几天年假”，这不是 AI 的 ROI 所在。他把现在比作登月的年代，建议别只摘低处的果子。
