02. swyx（Latent Space / AI Engineer）：为什么是 Agent 工程

直播位置 0:15:36–0:27:10 · Why Agent Engineering

swyx 是 Latent Space 的编辑、smol.ai 的创始人，也是这个大会的联合创办人。他说每次大会他都会用开场演讲给“行业现状”打个标记：第一届讲 AI 工程师的崛起和三种 AI 工程师，去年的 World's Fair 讲这个学科在成熟、在向不同方向扩散。

AI 工程现在的位置

他先列了几个信号：有了一本 O'Reilly 的书（作者 Chip Huyen 是他的朋友，第二天会做工作坊主题演讲）；Gartner 认为这个领域已经到了炒作曲线的顶点，他开玩笑说“从这里开始只能往下走了”。他现在遇到两边的阻力：机器学习工程师 MLE 觉得 AI 工程师就是 MLE 加几句提示词，软件工程师觉得这就是软件工程加几个 LLM API 调用。他自己仍然会说 AI 工程是“90% 软件工程，10% AI”，但他认为 AI 那一部分会随时间变大，最终成为独立学科，今年会开始分化。

他把自己的观察称为“人类学”：看人们怎么描述自己、怎么形成群体和行业。语言会暴露背景，比如 MLE 说 test-time compute（测试时计算），因为对他们来说跑推理只是为了测试；AI 工程师可能说 inference-time compute（推理时计算），因为他们真正关心推理；软件工程师可能直接说 reasoning（推理能力）。

为什么把峰会改成 Agent 工程

这次峰会对 RAG（检索增强生成，先检索资料再让模型据此回答）、开放模型、GPU 这些主题都说了不，只讲 Agent。他回看去年 YouTube 上表现最好的演讲，观众最想看的是 Agent 相关内容。问题在于这样征稿，来的多半是做 Agent 框架的公司，而大家真正想问的是“到底谁把它放进了生产”。于是今年定了规则：不要厂商推销。他说这让策展难了很多，因为接下来这些讲者没有什么动机上台分享。他还观察到“任何东西加上 Agent 都成立”：Agent 加 RAG、Agent 加搜索都行，他说这差不多是 2025 年赚钱的简单公式。

对“2025 是 Agent 之年”这个说法，他坦白自己和搭档 Alessio 也怀疑过。前一天大会和观众玩 Family Feud，“Agent”是大家最听腻的流行词第二名。2024 年 3 月他们和前 OpenAI 工程副总裁 David Luan 的访谈里还说过，劝创业公司把 Agent 从品牌里拿掉；现在他们又劝大家把它加回去。

Agent 的定义

他用一页幻灯片给出不同人群的定义：机器学习背景的人会讲强化学习环境、动作和目标；软件工程师比较简化，觉得就是一个 for 循环。Simon Willison 众包收集了大约 300 个定义，swyx 归纳成六类：围绕目标、围绕工具、围绕控制流、长时间运行的进程、被委托的权限、多步任务完成。还有一种思路是先找一批大家公认属于 Agent 的东西，检查你的定义能不能覆盖它们。他也提到 OpenAI 前一天在直播里发布了自己的一版 Agent 定义，后面的产品会建立在它上面。

为什么是现在

大家常说的原因是推理更强、工具调用 Tool Call 更强、工具更多，其中包括 MCP（Model Context Protocol，Anthropic 提出的让模型接入外部工具和数据的开放协议，第二天有工作坊）。他补充了几条不太被注意的原因：

  • 模型多样性：OpenAI 的市场份额从两年前大约 95% 降到 50%，就在这一周又出现了两个可能挑战 OpenAI 的前沿实验室。
  • 智能的成本在快速下降：GPT-4 级别智能的价格在 18 个月里降了 1,000 倍，o1 级别的智能也开始走同样的曲线。
  • 出现了 RL 微调的选项，他自己没经验，下午有讲者会讲。
  • 还有按结果收费（他引用和 Bret Taylor 的对话）、多智能体、更好的硬件带来的更快推理等。

用例和反用例

他认同 Barry Zhang 的说法：编程 Agent 和客服 Agent 已经找到产品市场契合 PMF，他认为现在 Deep Research 也有了。他提出的反用例是订机票：“请别再演示订机票的 Agent 了，我想自己订机票”，自己下 Instacart 订单也一样。

最后是一组数字。OpenAI 刚公布 4 亿用户，三个月增长 33%。他用 Deep Research 画出了 ChatGPT 两年半从 0 到 4 亿的曲线，指出 ChatGPT 曾经有一年几乎没增长，他认为原因是那段时间没发布 Agent 类的模型。把周活跃用户曲线拉长看，o1 系列模型让 ChatGPT 的使用量翻了一倍；按这个趋势，ChatGPT 年底会到 10 亿用户，大约是去年 9 月的五倍、世界人口的八分之一。他的结论是 AI 产品的增长会和推理能力、能交付给用户的 Agent 数量紧紧绑在一起，而 AI 工程师的工作正在转向构建 Agent，就像 MLE 构建模型、软件工程师构建软件。后面几页他因为超时跳过了。

03. Sayash Kapoor（Princeton，《AI Snake Oil》作者）：构建和评测 AI Agent

直播位置 0:27:23–0:46:35 · AI Snake Oil: Building and evaluating AI Agents

Sayash Kapoor 是《AI Snake Oil》的作者之一，在 Princeton 做研究。他开场就说，今天的主题是 Agent 在工作，而他接下来 18 分钟要讲的是 Agent 现在为什么不太好用，以及怎么做得更好。

他先承认 Agent 已经在被广泛使用：按 swyx 收集的定义之一，“语言模型控制系统的流程”，那么 ChatGPT 和 Claude 这些产品本身就是初级的 Agent，有输入输出过滤、能调用工具。OpenAI Operator 能在网上执行开放式任务，Deep Research 能用 30 分钟写一份任意主题的报告。但更宏大的设想离实现还很远。他把电影《Her》里的场景和一些失败的产品放在一起，说他放这页幻灯片无意批评某个产品，想让观众正视“做出真正能用的 Agent”这件事。他讲了三个原因。

原因一：评测 Agent 真的很难

  • DoNotPay 是一家美国创业公司，宣称能自动化律师的全部工作，联合创始人还悬赏 100 万美元，找愿意戴着耳机用 DoNotPay 在美国最高法院辩护的律师。最近美国联邦贸易委员会 FTC 罚了它几十万美元，原因是它的性能宣传完全不实。
  • LexisNexis 和 Westlaw 是美国头部法律科技公司。LexisNexis 曾宣称自己的产品生成法律报告“无幻觉”。Stanford 的研究者评测后发现，这些产品在至少六分之一、最多三分之一的情况下有幻觉，有的把原始法律文本的意思完全说反，有的段落是编出来的，研究里列了大约 200 个这样的错误。
  • Sakana AI 宣称做出了能完全自动化开放式科学研究的“AI 科学家”。他们团队为了检验，做了一个基准 CORE-Bench：任务比真实科研简单得多，只要求复现论文结果，还给 Agent 提供了代码和数据。结果是当前最好的 Agent 能复现的论文不到 40%。他说 40% 已经能帮研究者省很多时间，但据此说 AI 很快能自动化全部科学还太早。别人细看 Sakana 的 AI 科学家后发现，它只在玩具问题上运行，用 LLM 当评审（LLM-as-a-judge）而没有人类同行评审，产出更像本科生研究项目，是在已有论文上做小改动。
  • 他准备幻灯片的那几天，Sakana 又宣称做了一个优化 CUDA kernel 的 Agent，比 PyTorch 自带的 kernel 快 150 倍。再往下分析一层就会发现，这意味着超过 H100 理论峰值 30 倍，显然不可能。原因是 Agent 在钻奖励函数的空子（reward hacking），并没有真的改进 kernel。

他说他无意点名哪家公司，想说明的是评测要成为 AI 工程工具箱里的一等公民。

原因二：静态基准会误导

给 LLM 做评测，通常只需要一个输入字符串和一个输出字符串。Agent 要在环境里采取行动，所以评测要搭建它能操作的虚拟环境，难得多。LLM 的评测成本受上下文窗口 Context Window 长度限制，有一个上限；Agent 可以调用子 Agent、可以递归、可以在 for 循环里不停调 LLM，成本没有上限，所以成本必须和准确率一起作为评测的坐标轴。另外 Agent 往往是专用的，编程 Agent 不能拿网页 Agent 的基准来测，这就需要多维度的指标，不能只靠单一基准。

他们在 Princeton 做了一个 Agent 排行榜，在 CORE-Bench 上同时显示成本和准确率，画出帕累托前沿 Pareto Frontier（在给定成本下准确率最好的那条边界）。Claude 3.5 的得分和 OpenAI o1 差不多，但跑一遍只要 57 美元，o1 要 664 美元。他说即使 o1 高出几个百分点（这里其实没有），大多数 AI 工程师也会选便宜 10 倍、表现相近的那个。

常有人问他：LLM 不是越来越便宜了吗，为什么还要关心成本？他承认成本降了很多，2022 年的 text-davinci-003 到今天的 GPT-4o mini，后者大多数情况下更好，成本降了两个数量级以上。但他给了三个理由：规模化的应用仍然很贵；做原型需要公开迭代，不算成本的话原型很快就要花掉几千美元；还有杰文斯悖论 Jevons Paradox，19 世纪一位英国经济学家发现煤炭开采成本降低后，各行业的煤炭总用量反而上升。ATM 也一样，大家以为会让银行柜员失业，结果因为 ATM 好装，银行网点大量增加，柜员人数反而增加。他预期 LLM 越便宜，跑 Agent 的总成本反而会上升。

他们把这些做成了 HAL（Holistic Agent Leaderboard，整体 Agent 排行榜），已经能在 11 个基准上自动跑 Agent 评测，还在加。但还有一个问题：基准成了风投决定投资的依据。Cosine 靠 SWE-bench 成绩拿到种子轮；Cognition 以 20 亿美元估值融了 1.75 亿美元，主要也是因为 Devin 在 SWE-bench 上表现好。可是 Answer.AI 的团队把 Devin 放进真实工作里试了一个月，20 个任务只成功了 3 个。他推荐 Berkeley 的论文《Who Validates the Validators?》：传统流水线是单次 LLM 调用对照静态指标；他们提议让领域专家参与进来，主动修改 LLM 评测所依据的标准，这样评测结果会好很多。

原因三：把能力当成了可靠性

能力 capability 指模型在某些时候能做到什么，技术上对应 K 很大时的 pass@k，也就是 K 次输出里至少一次正确。可靠性 reliability 是每次都答对。Agent 用在后果重大的决策上时，要看的是可靠性。他说让模型达到 90% 的训练方法，用 swyx 的话说是 MLE 的工作，不一定能带你到 99.999%，也就是“五个九”；填上 90% 到五个九之间的差距是 AI 工程师的工作。他认为 Humane AI Pin 和 Rabbit R1 的失败就在这里。一个个人助理如果只有 80% 的时候能正确帮你点 DoorDash 外卖，从产品角度就是灾难性失败。

有人提议用验证器 Verifier（类似单元测试）来提高可靠性，靠推理时扩展（多试几次、用验证器挑）得到可靠的结果。他们发现验证器本身也不完美：两个主流编程基准 HumanEval 和 MBPP 的单元测试都有假阳性，错误的代码也能通过测试。把假阳性算进去后，推理扩展曲线会往下弯，试得越多越可能拿到错误答案。

结论：AI 工程是可靠性工程

他认为 AI 工程师要解决的是：面对 LLM 这种本质随机的组件，需要什么样的软件优化和抽象。这是系统设计问题，不能只当建模问题。他的标题页用的是 1946 年的 ENIAC：它用了超过 17,000 个真空管（字幕作 177,000，按史实应为约 17,000），早期真空管坏得太频繁，计算机有一半时间不可用。那批工程师头两年的主要工作是修可靠性问题，直到它能被用户正常使用。他说这就是 AI 工程师真正的工作，需要在思维上转向可靠性，把自己看作保证下一波计算对用户足够可靠的人。

04. Aarush Selvan 与 Mukund Sridhar（Google）：Gemini Deep Research 是怎么做的

直播位置 0:47:17–1:01:54 · Going deep on Gemini Deep Research

Aarush 是 Gemini 的产品经理，Mukund 是 Google 的 staff 机器学习软件工程师，做 Deep Research。Aarush 开玩笑说，要用 Deep Research，得在 Gemini Advanced 的模型菜单里滑过 2.0 Flash、2.0 Flash Thinking Experimental、带应用的 2.0 Flash Thinking Experimental、2.0 Pro Experimental，最后才找到“1.5 Pro with Deep Research”，付 20 美元就能用。它是一个会替你浏览网页、写报告的个人研究 Agent。

为什么做它

目标是“帮人快速变聪明”。研究和学习类问题是 Gemini 的头部用例之一，但遇到难题时，聊天机器人常常给你一个答案的蓝图。他们内部常用的例子是“怎么拿到铅球项目的体育奖学金”：一般回答是去联系教练、了解要扔多远、保持好成绩，但用户真正想知道的是成绩线是多少、要扔多远。于是他们设想：去掉推理时的算力和延迟约束，让 Gemini 想浏览多久就浏览多久，换一个全面得多的答案。但必须在五分钟内完成，“再长我们就没有那么多芯片了”。

产品上的三个难题和对应设计

  • Gemini 是同步的聊天产品，要在里面做异步体验。
  • 要管理用户预期：很多问题是“天气怎么样”“讲个笑话”，等五分钟毫无意义。
  • 答案可能有几千字，要让用户在聊天界面里方便地读和追问。

他用一个例子走了一遍界面：假设你是风投，想了解小型核反应堆的最新技术突破和供应链里值得关注的公司。第一步，Gemini 先生成一份研究计划，放在卡片里。这告诉用户“接下来和普通聊天不一样”，也让用户可以编辑计划、调整方向，就像一个好分析师会先说明打算怎么做。点开始后，界面实时显示 Gemini 正在浏览的网站，用户可以点进去看。这个功能比 thinking 模型出现得早。他们意外发现有人想刷高这个网站数量，把它推到上千个。最后生成的报告有几千字。他们受 Anthropic Artifacts 的启发，把报告固定在侧边，用户边读边提问，不用来回滚动，也可以改风格、加减章节、追问。最后是信任和对出版方负责：界面列出所有读过的来源和报告里用到的来源（没用到的来源仍留在上下文里供追问），导出到 Google Docs 时保留为引用。

技术上的四个难题（Mukund）

第一是长时间运行。一个任务跑几分钟，要调用很多次 LLM 和各种服务，中间必然有失败；以后可能跑几个小时。所以需要好的状态管理，能从错误中恢复，不能因为一次失败丢掉整个任务。这套设计也让功能可以跨平台：用户提交任务后离开，完成时收到通知，换一台设备接着读。

第二是迭代规划。以铅球奖学金为例，模型要先判断哪些子问题可以并行、哪些必须按顺序。它总会处在“信息不全”的状态，所以每一步都要看已找到的全部信息再决定下一步。例如它已经找到 D1 级别的达标线，就知道还得去找 D2、D3 的对应标准。搜“适合孩子的过山车”时，搜到的是“十大过山车”的页面，没提适不适合孩子，规划器要意识到这一点并在后续步骤里消除歧义。考潜水证的例子里，课程结构在一个来源，某个潜水中心的价格在另一个来源，模型要把两者拼起来。还有经典的实体消解 Entity Resolution 问题：不同来源提到的是不是同一个实体，要靠线索推断或进一步查证。

第三是网页本身很嘈杂。他展示了两个都在讲葡萄牙今年音乐节的网站，一个布局清楚、一次拿到大部分信息，另一个布局完全不同，所以浏览机制要足够稳健。

第四是上下文管理。规划过程中信息流不断涌入，上下文增长很快；用户还会追问，或者让它对另一个主题再做一遍，进一步挤压上下文。Gemini 有长上下文模型，但仍要设计管理方式，每种方式都有取舍。他展示的一种做法带“近期偏好”：当前任务和上一个任务保留更多信息，更早的任务则挑出所谓“研究笔记”放进 RAG，模型仍能访问，但是有选择的。

接下来

Aarush 说 12 月上线时他们不确定有没有人愿意等五分钟，结果反响出乎意料地好，他形容为“做出了一个可能和分析师差不多的东西，20 美元送出去”。目前它只从开放网络检索，是文本进文本出的系统。他看到的方向有三个：一是专业深度，从麦肯锡分析师走到麦肯锡合伙人、高盛合伙人、律所合伙人，能想清楚“所以呢”，给出含义和洞见；科学领域也一样，读很多论文、找规律、提出新假设。二是个性化：同样是对一家公司做尽调，给他看要讲清公司是什么、战略位置如何，给高盛银行家看则要有财务数据和 DCF 模型，这会影响怎么浏览、怎么组织答案、追问哪些问题。三是跨能力组合：把网页研究和编程、数据科学甚至视频生成结合，比如做尽调时自己跑统计分析、建财务模型（他补充说 Google 不提供投资建议）。最后他说，还好上线前没把它叫做 Gemini Deep Dive，那是他们之前最好的候选名。

05. Barry Zhang（Anthropic）：我们怎样构建有效的 Agent

直播位置 1:02:23–1:17:00 · How We Build Effective Agents

Barry Zhang 是 Anthropic 的技术人员。大约两个月前，他和 Erik 写了博客《Building Effective Agents》，给出了关于 Agent 是什么、不是什么的一些有立场的看法。这次他在博客的基础上深入三点：不要什么都做成 Agent；保持简单；像你的 Agent 一样思考。

从单次调用到工作流再到 Agent

大多数人从很简单的功能开始，摘要、分类、抽取，两三年前像魔法，现在已经是标配。产品成熟后，一次模型调用不够，就开始在预先定义好的控制流里编排多次调用，用成本和延迟换更好的效果，他们称之为工作流 Workflow，认为这是 Agent 系统的开端。现在模型更强，生产里出现了越来越多的领域 Agent：和工作流不同，Agent 能自己决定轨迹，根据环境反馈几乎独立地运作。下一阶段是什么还说不准，可能是更通用的单个 Agent，也可能是多智能体的协作与委派。大趋势是给系统越多自主权，它越有用，但成本、延迟和出错的后果也越大。

一、不要什么都做成 Agent

他把 Agent 看作扩展复杂、高价值任务的方式，它不该是每个用例的直接升级。他们的检查清单：

  • 任务复杂度：Agent 适合模糊的问题空间。如果能轻松画出整棵决策树，就直接显式地做出来，再逐个节点优化，更省钱也更可控。
  • 任务价值：探索会花大量 Token，任务价值要撑得起成本。如果每个任务预算大约 10 美分，比如高并发客服系统，那只够 3 万到 5 万个 Token，这时用工作流解决最常见的场景就能拿到大部分价值。他开玩笑说，如果你的第一反应是“我不在乎花多少 Token，只要把事做成”，会后来找他，Anthropic 的销售团队很想和你聊。
  • 关键能力去风险：确保 Agent 的轨迹上没有明显瓶颈。做编程 Agent 就要确认它能写好代码、能调试、能从错误中恢复。有瓶颈通常不致命，但会成倍增加成本和延迟，这时他们会缩小范围、简化任务再试。
  • 出错的代价和发现错误的难度：如果错误代价高又难发现，就很难信任 Agent 替你行动。可以限制范围，比如只读权限、更多人在环 Human-in-the-loop，但这也限制了扩展。

用这张清单看编程：从设计文档到 PR 是模糊又复杂的任务；好代码价值高；很多人已经在用 Claude 写代码，知道它擅长编程流程的很多环节；而且编程的输出很容易通过单元测试和 CI 验证。他认为这就是现在有这么多成功编程 Agent 的原因。

二、保持简单

在他们眼里，Agent 就是“模型在循环里使用工具”。三个组成部分：环境，Agent 所处的系统；工具，Agent 采取行动、获得反馈的接口；系统提示词 System Prompt，规定目标、约束和理想行为。然后在循环里调用模型，就是 Agent。他们吃过亏才学到：前期加的任何复杂度都会拖慢迭代速度，只在这三个组件上迭代，投入产出比最高，优化放到后面。

他展示了三个他们为自己或客户做的 Agent，产品形态、范围、能力都不一样，但骨架几乎相同，代码也几乎一样。环境基本由用例决定，所以真正的设计决策只有两个：给 Agent 哪些工具，用什么提示词。他顺带推荐同事 Mahesh 第二天上午的 MCP 工作坊。行为稳定之后再做优化：编程和 Computer Use 可以缓存轨迹降成本；工具调用很多的场景可以并行调用降延迟；几乎所有场景都要把 Agent 的进展展示出来，赢得用户信任。

三、像你的 Agent 一样思考

他说很多 Builder，包括他自己，都是从自己的视角开发 Agent，Agent 犯错时就想不通。所以他们建议把自己放进 Agent 的上下文窗口里。Agent 的行为看起来再复杂，每一步模型做的只是在一小段上下文上跑推理，它对世界当前状态的全部了解就在那 1 万到 2 万个 Token 里。

他让观众想象自己是一个 Computer Use Agent（操作电脑界面的 Agent）：你只拿到一张静态截图和一段写得很烂的描述（他说这段是他本人写的）。你可以随便思考，但只有工具调用会真正作用于环境。你尝试点一下，在推理和工具执行的那 3 到 5 秒里，相当于闭着眼用电脑；睁开眼看到新截图，刚才的操作可能成功了，也可能把电脑关了。他建议大家真的从 Agent 的视角完整做一遍任务，说这是“有意思、只是稍微有点难受”的体验。做完就会清楚 Agent 需要什么：要知道屏幕分辨率才能点准，最好有推荐操作和限制，避免不必要的探索。

既然模型懂我们的语言，也可以直接问 Claude：把系统提示词丢给它，问有没有歧义、能不能照做；把工具描述丢给它，看它会不会用、想要更多还是更少参数。他们常做的一件事是把 Agent 的整条轨迹交给 Claude，问“你觉得我们在这里为什么做了这个决定，我们能做什么帮你做出更好的决定”。他说这不能代替你自己的理解，但能让你更接近 Agent 看到的世界。

他个人关心的三个开放问题

  • 让 Agent 有预算意识。工作流的成本和延迟可控，Agent 不太可控。怎样按时间、金钱、Token 定义和执行预算，还没有好办法。
  • 自我进化的工具。他们已经用模型帮忙迭代工具描述，这应该能推广成一个元工具，让 Agent 自己设计和改进工具的易用性。
  • 多智能体协作。他说这已经不算激进观点：到今年年底生产中会有更多多智能体协作，它们容易并行、职责清楚，子 Agent 还能保护主 Agent 的上下文窗口。开放问题是 Agent 之间怎么通信：现在的系统基本围绕同步的 user/assistant 轮次设计，怎样扩展到异步通信、让 Agent 互相识别，还没解决。

最后他讲了一个小故事：2023 年他在 Meta 做 AI 产品，那里可以把自己的职位名称改成任何东西。读了 swyx 那篇博客之后，他把自己的职位改成了“第一个 AI 工程师”。

06. Zack Reneau-Wedeen（Sierra）：Agent 开发生命周期

直播位置 1:17:30–1:35:40 · The Agent Development Life Cycle

Zack 是 Sierra 的 AI 产品经理。Sierra 是面向企业的对话式 AI 平台，客户包括 Sonos、ADT、SiriusXM。大家多半把 Sierra 和聊天、客服联系在一起，他说业务正在扩展：到今年年底，大部分交互可能会通过电话进行，也有客户用它做销售、订阅管理和商品推荐。

从 2016 年的 Google Lens 讲起

他调侃前一天的讲者回顾“AI 古代史”最远只到 2019、2020 年，他要回到 2016 年。当时他在 Google 和一群计算机视觉工程师做第一版 Google Lens，难题是区分吉娃娃和蓝莓松饼、狗和百吉饼、狗和炸鸡。他住在纽约东村，走路 30 分钟上班，路上用 Lens 识别植物，这是当时视觉模型少数几个真正有用的消费场景，还会走进花店去测。结果有时准，有时“不算错但也不贴切”，像老虎机。他说做 AI 的人都懂这种感觉：连续成功五次，第六次为什么失败。如今的 Lens 能搜你看到的、买你看到的、翻译非拉丁字符（比如看懂东京 Airbnb 里的洗衣机）、解数学作业，也还能识别花。他认为这是十年持续逐步迭代的结果，背后需要一个“变好的同时不变差”的流程，也就是软件开发生命周期 SDLC。

Chubbies 和 Agent Duncan Smothers

他又回到 2012 年：Google Brain 在 YouTube 上识别猫，模型大约 10 亿参数，是今天前沿模型（约 1 万亿参数）的千分之一；Marc Andreessen 发表《软件正在吞噬世界》；Stanford 草坪上有一批创业公司。他让观众猜是哪家，答案是男士短裤品牌 Chubbies。Chubbies 的商务 SVP Kit Garton 认为，就像 1995 年企业需要网站、后来需要社交账号和移动应用，2025 年企业需要一个 AI Agent 来代表自己。Sierra 为他们做的 Agent 叫 Duncan Smothers，“能力强，也总愿意开玩笑”。他经许可展示了几段真实对话：询问尺码时 Duncan 会问腰围并推荐商品；查询库存；查询包裹时告诉客户一个订单有多个追踪号；直接办理退款。他说这就是“会采取行动的自主 Agent”，Chubbies 因此能更快地服务更多客户，满意度也更高。

Sierra 的理念是“每个 Agent 都是一个产品”，不能靠拖拽几个框搭出来，需要完整的开发平台和客户体验运营平台。他们还设有专门的 Agent 工程和 Agent 产品经理岗位，类似前置部署，每天和客户团队一起工作。中间他插了一段：去年 World's Fair 上他坐在 Deepgram 的工作坊里，旁边的人叫 Sean，两人聊怎么用 Mac 的 say 命令加 Loopback 软件把语音直接接进浏览器，加快语音 Agent 的开发循环，不用戴着耳机在办公室对着电脑说话。几个月后 Sean 加入了 Sierra，所以公司让他这次再“找几个 Sean”。

Agent 开发生命周期

他说 LLM 像是建在果冻地基上：传统软件确定、快、便宜、死板、由 if 语句控制；LLM 不确定、慢、贵，但灵活、有创造力、能推理。Sierra 想要一套既利用 LLM 长处、又在合适的地方调用传统软件的方法论，这就是 Agent 开发生命周期 ADLC。看起来和 SDLC 很像，他说细节决定一切：每个环节都要和客户在生产中反复打磨。

以质量保证为例：客户公司的人可以在 Sierra 的 Experience Manager 里查看每一段对话、看实时的整体报告，并提交反馈。比如 Duncan 报错库存，可能是只调了一个仓库的 API，没调全，或者某个调用超时了。反馈会生成 issue，issue 会生成测试，测试通过后发新版本。一个 Sierra Agent 上线时只有几个测试，之后会增长到几百、几千个。有时 Agent 并没犯错，只是可以做得更好：Chubbies 给每个 Agent 一笔“取悦客户”的预算，网上缺货时 Duncan 可以用 DoorDash 从门店送短裤过去。

一年前这些都是人工做的，现在他们在生命周期的每个环节都加了 AI。客户越大，这套流程越有价值：Duncan 处理几十万次请求，而有的客户是几千万次。变化也来自外部：模型升级、推理模型这类新范式、多模态。他说推理模型对每一步都是倍增器，用 AI 做开发、测试、QA 都更有效了。

语音

他大约一年前开始做语音，Sierra 在 10 月正式推出语音功能。大客户 SiriusXM 在美国有几千万客户，现在每次来电都能立刻接起。他们对语音的思路类似网页的响应式设计：十几年前很多网站有单独的 m. 移动版，后来统一成响应式；Sierra 的 Agent 也是同一套平台、同一份代码，自动适应用户来的渠道和模态，同时仍可定制措辞、并行请求以降低延迟。

结尾他说，LLM 让人想到自己：难以预测、慢、数学不太好。这让设计者可以对机器产生共情，站在它的角度想体验。关于语音，他一直在问自己：如果有人只把对方说的话转成文字、延迟几百毫秒递给你，让你当场回应，你能做得多好？他说 Sierra 的结果显示，让 LLM 拥有和人一样的输入会更好，他胸牌上写的兴趣是 voice-to-voice（语音到语音）模型。

07. Will Brown（Morgan Stanley）：强化学习对 Agent 意味着什么

直播位置 1:36:07–1:53:37 · What RL Means for Agents

Will Brown 是 Morgan Stanley 的机器学习研究员。他在 Columbia 读研时主要做多智能体强化学习的理论，过去几年在 Morgan Stanley 做各种 LLM 项目。他说这场和其他演讲不同：不讲已经上线、确定可行的东西，讲的是研究社区的一些趋势可能指向哪里，带一些推测，也讲讲他自己最近的开源工作。

我们在哪里

他用 OpenAI 的五级框架：聊天机器人做得不错，推理者 Reasoner（o1、o3、R1、Grok 3、Gemini 等）也做得不错，现在大家在想怎么做到第三级 Agent，也就是能采取行动、做更长更复杂事情的系统。目前的做法是把多次聊天模型或推理模型的调用串起来，加上提示工程、工具调用、评测、人在环。他沿用 Barry 的说法，把自主度低、需要大量工程去确定决策树和提示词的系统叫流水线 Pipeline（即 Barry 说的工作流）。很多成功的 Agent 类应用反馈回路都很短：Cursor、Windsurf、Replit 这类 IDE，带搜索的问答工具。能自己跑 10 分钟以上的 Agent 不多，他想到的只有 Devin、Operator 和 OpenAI Deep Research。

传统的答案是等更好的模型。但他提醒，强化学习里 Agent 的原始定义是：和环境交互、有目标、通过反复交互学会更好地达成目标。很多人现在是手工在做这件事：提示词调到 70%，想到 90%，模型就是做不到，下一步怎么办？

模型趋势和 DeepSeek R1

预训练对资本的回报在递减；RLHF（基于人类反馈的强化学习）适合做友好的聊天机器人，但看起来不能持续推高智能前沿；合成数据适合把大模型蒸馏到小模型，单靠它不是能力的突破口，除非加上验证或拒绝采样。这就到了强化学习：它看起来是 o1 和 R1 解锁测试时扩展的关键，不受人工标注数据限制，而且真的有效。

大约一个月前 DeepSeek 发布 R1 模型和论文，第一次把怎么做出 o1 这类模型讲清楚：给模型一些问题，衡量它答没答对，不断给反馈，让它多做有效的、少做无效的。o1、R1 的长思维链 Chain of Thought 是这个过程的副产品，没有人喂给它上万 Token 的推理示例，是模型自己学会的，因为这是好策略。他说强化学习的核心就是找到解决问题的好策略。开源模型也重新热起来，大家在复现 o1，或把 o1 的数据蒸馏到小模型里。

RL 的核心是探索与利用：尝试，看什么有效，多做有效的。他展示了一个例子：模型写代码通过测试用例，奖励来自格式、用对语言、最终测试是否通过。这是一个数值信号，模型自己做合成的 rollout（一次完整的生成尝试），把得分反馈回模型。DeepSeek 用的 GRPO 算法，他认为技术上不算重大突破，但概念简单：对同一个提示采样 N 个回答，全部打分，告诉模型“更像高分的那些”。

到 Agent 还有多远

上面这些仍是单轮推理模型的世界。OpenAI Deep Research 很多细节不公开，但 OpenAI 说过它是端到端强化学习训练的，可能调用上百次浏览和查询工具来合成答案。大多数人的直观感受是很厉害，但它不是 AGI：没法让它在代码库里干活或解决难的软件工程任务，有人发现它遇到分布外任务会吃力，比如让它填一张需要上百次手工计算的表。所以 RL 一方面解锁了新技能和更高的自主度，另一方面还没给出什么都能做的 Agent；它是让模型学会特定技能的路径，尤其配合环境、工具和验证。

现有基础设施大多是 RLHF 风格的单轮交互，奖励来自由人类数据训练出的奖励模型。也许大实验室会提供好用的 API 让大家在 GPT 或 Claude 上做 RL 微调，但现在还没有：OpenAI 预告了强化微调 Reinforcement Fine-tuning，但还不支持多步工具调用。未知的问题很多：花多少钱、模型能多小、能否跨任务泛化、怎么设计好的奖励和环境。这里有开源基础设施和公司的机会。他也提到不训练权重、在提示词层面做的自动化，比如 DSPy，它也是有一个信号，再据此提升下游分数，和 RL 是相邻的思路。

一个 Python 文件的故事

R1 发布后的那个周末，还没到 Nvidia 股价大跌，他用 Hugging Face 的一个带 GRPO 的 trainer，让很小的 Llama 1B 模型在数学题上先推理再作答，用了很简单的系统提示词和手写的奖励函数，然后发到了推特上。图里能看到模型似乎在自我纠错，准确率上升；回答长度先下降（学会格式），再上升（学会用更长的思维链推理）。他说这算不上真正的复现，也不是最复杂的，但接下来两周它自己火了：很多人 fork、修改、改成 Jupyter Notebook、写博客。他认为吸引人的地方是只有一个文件、很简单、很容易改。

他把这种修改称为“评分规则工程”Rubric Engineering。最简单的奖励是答对没答对，但可以做更多：遵守某种 XML 结构就加一分；答案虽然错了但是整数格式，也给一点分。这些规则除了给人当下游评测看，也让模型自己知道做得好不好，并据此继续训练。可探索的方向包括用 LLM 设计评分规则、自动调规则、用 DSPy 之类框架自动调提示词、把 LLM 评审纳入打分。他特别提醒奖励投机 Reward Hacking：要确保奖励真的反映目标，没有让模型钻空子拿高分而学不会任务的后门。

之后他在做一个更稳健、能用于真实项目的框架（字幕里没有报名字），用来在多步环境里做 RL。思路是很多人已经为 API 模型写好了 Agent 框架和环境，希望能直接复用：你只需写一个交互协议，不用管权重和 Token，把环境交给训练器，模型就会在反复交互中变好。他强调这是很新的研究代码，不是让大家明天就拿去用。

RL 时代的 AI 工程

现成的 API 模型能不能解决你的任务，还不知道。他认为它们可能不是全部答案的一个原因是：技能很难写进提示词。知识可以放进提示词，但人做一件事往往第一次做不好，要靠试错，模型也一样，靠试错才真正掌握技能，这是目前解锁 Deep Research 这类高自主 Agent 最有希望的路径。微调可能仍然重要：以前很多人放弃微调，因为开放模型离前沿太远，提示一个前沿 API 就能赢过微调的小模型；现在开源闭源差距缩小了，很多平台在用托管的开源模型；而 DeepSeek 对 R1、OpenAI 对 Deep Research 做的那种 RL 本身就需要训练。他说过去几年积累的技能可以直接迁移：搭环境和评分规则，和搭评测、写提示词差别不大；仍然需要好的监控工具，需要支持这些 Agent 的公司和产品生态。

08. John Crepezzi（Jane Street）：在 Jane Street 构建 AI 开发者工具

直播位置 2:53:39–3:10:27 · Building AI-Powered Developer Tools at Jane Street

John 在 Jane Street 的 AI Assistant 团队，这个团队的目标是让公司从 LLM 里拿到尽可能多的价值。他整个职业生涯都在做开发者工具，之前在 GitHub 工作了很久。

为什么现成工具不好用

Jane Street 几乎所有东西都用 OCaml 写。OCaml 是一种强大的函数式语言，但很冷门，起源于法国，常见用途是定理证明、形式化验证和编写编程语言。他们写网页应用也写 OCaml，用 js_of_ocaml 把 OCaml 字节码转成 JavaScript；写 Vim 插件用 Vcaml 转成 Vimscript；写 FPGA 代码也不用 Verilog，用 OCaml 库 Hardcaml。现成工具不适合他们，原因有三：

  • 模型本身不擅长 OCaml。这不怪 AI 实验室，是训练数据量的问题：Jane Street 内部的 OCaml 代码很可能比外面全世界的加起来还多。
  • 他们给自己设置了很多难度：自建构建系统、自建分布式构建环境、自建代码评审系统 Iron；整个公司在一个巨大的 monorepo 里开发，而且存在 Mercurial 而不是 Git 里；上次统计，公司 67% 的人用 Emacs，VS Code 也有人用，但 Emacs 最多。
  • 他们想把 LLM 用到开发流程的各个环节，比如解决合并冲突、写更好的功能描述、推荐评审人，不想被不同系统的边界限制。

训练自己的模型

训练模型很贵、很慢、出错的方式很多。让他们下决心的是 Meta 的论文 CodeCompose：Meta 为 Hack 语言微调了模型。Hack 和 OCaml 的相似之处在于基本只在一家公司内部使用（他还提到一个巧合：Hack 是用 OCaml 实现的）。他们一开始很天真，以为拿现成模型给它看一堆自己的代码，就能得到懂自家库和习惯用法的模型。事实是要得到好效果，模型必须看到大量和你想问的问题同形状的示例。

所以先定目标：用户在编辑器里写一段描述，模型给出可能跨多个文件的 diff，比如同时改测试文件、.ml 文件和 .mli（类似头文件）；diff 要能干净地应用，应用后大概率能通过类型检查；目标范围是 100 行以内，他们认为这是 LLM 能力合适的区间。训练数据的形状是“上下文、提示、diff”三元组。

数据从哪来？Iron 里的 feature（相当于 PR）有人写的描述和对应的代码，但 PR 描述的写法和人在编辑器里说的话很不一样，编辑器里你只会说“修一下现在这个报错”；而且 feature 常常有 500 到 1,000 行，需要自动拆成小块。commit 更小，但 Jane Street 的 commit 主要当检查点用，没有描述，也不是独立的改动。最后他们用的是工作区快照：在工作日里大约每 20 秒给开发者的工作区拍一次快照，同时记录构建状态。构建从绿到红再到绿，通常对应一次独立的改动；从红到绿是开发者遇到类型错误或编译错误并修好了。在红的时刻记下构建错误，再取红到绿之间的 diff，就能训练模型从错误中恢复。描述则让 LLM 先写一份尽量详细的说明，再逐步压缩，直到接近人会写的长度。

有了监督训练数据，第二步是强化学习，让模型和“人认为的好代码”对齐。在 OCaml 里，好代码首先要能通过解析器；因为 OCaml 是静态类型语言，还要能通过类型检查；最高标准是能编译并通过测试。他们做了一个代码评测服务 CES（Code Evaluation Service），类似构建服务，但做了加速：先让构建停在一个已经是绿色的版本上预热好，一批 worker 整天从模型那里拿 diff、应用、看构建变红还是变绿，再把结果报回去。持续用了几个月，模型写出能编译、能过测试的代码的能力明显提升。同一套设置也可以直接做评测，只要留出一部分 RL 数据不用于训练。

训练也会出好笑的事故。他们训练过一个单独的代码评审模型，花了几个月，第一次提交代码让它评审，它想了一会儿回复了类似“我明天再看”。因为训练数据是人写的评审，人就常这么写。他说这说明有意义的评测是防止模型跑偏、浪费时间和钱的基石。

编辑器集成：AIDE

做集成时有三个原则：他们支持 Neovim、VS Code 和 Emacs 三个编辑器，不想把上下文构建和提示策略写三遍；要保持灵活，当时用的还不是微调模型，但他们确信以后会换，所以要能换模型、换提示策略；要能收集指标，开发者在编辑器里在乎延迟和 diff 能不能应用。于是有了 AIDE（AI Development Environment）：一边是 LLM，AIDE 负责构建提示词和上下文、查看构建状态，每个编辑器上只写很薄的一层。AIDE 作为 sidecar 运行在开发者机器上，要更新时不用改编辑器、不用等大家重启编辑器，在所有机器上重启 AIDE 服务就行。

在 VS Code 里它是一个侧边栏，类似 Copilot，但能要求并得到跨文件 diff。在 Emacs 里，开发者习惯在文本 buffer 里工作，所以他们把 AIDE 做成一个 Markdown buffer：用户在里面移动、提问，按快捷键会把新内容追加到 buffer 末尾。AIDE 的架构可以插拔：换模型、改上下文构建、加新编辑器（他说正在加），公司不同部门还能提供领域专用工具，自动出现在所有编辑器里。还能做 A/B 测试，比如一半人用一个模型、一半人用另一个，看哪个接受率高。他说每次 LLM 有变化，只要在编辑器下游的这一处改，所有地方就都有了。他们还在做编辑器里的 RAG、大规模多智能体工作流、推理模型，思路都一样：保持可插拔，打好基础，让公司其他人能在上面加领域工具。

09. Anju Kambadur（Bloomberg）：为生成式 AI 产品扩展 Agent 的挑战

直播位置 3:10:51–3:29:59 · Challenges to Scaling Agents for Generative AI Products

Anju Kambadur 是 Bloomberg 的 AI 工程负责人。他说这次的题目很大程度上受主办方影响，因为 Agent 领域值得讲的事情太多。

背景

2021 年底 LLM 开始引起关注。Bloomberg 投入 AI 已经大约 15、16 年，决定自己训练大模型，2022 年全年在做，2023 年发了论文（整理者注：即 BloombergGPT），学到了很多关于数据集、评测和性能调优的东西。然后 ChatGPT 出现，开放权重和开源社区发展得很好，于是他们在战略上转向“在现有模型之上构建”，同时继续做类似的研究工作。他的团队向全球工程负责人汇报，和数据、产品、CTO 团队跨部门合作，大约 400 人、50 个团队，分布在伦敦、纽约、Princeton 和多伦多。他们用生成式 AI 做产品大约 12 到 16 个月了，从工具类走向更 Agent 化。

他列了一长串今天要解决的挑战，然后说这次一个都不讲，其他讲者会讲。他强调这是现实，谈不上悲观：他要用今天能拿到的东西、今天就交付产品。关于术语，内部大家对“Agent”和“工具”各有说法，他采用论文 CoALA（Cognitive Architectures for Language Agents）里的光谱：左边是工具，右边是更自主、有记忆、能进化的 Agent。

Bloomberg 是金融科技公司，客户包括金融业的很多种角色。它既生产也汇集大量结构化和非结构化数据：新闻、研究、文档、幻灯片、参考数据、市场数据。规模是每天 4,000 亿条结构化行情 tick、超过 10 亿条非结构化消息、几百万篇写作质量高的文档（包括新闻），历史超过 40 年。这次他以研究分析师为例：分析师通常专精一个领域，比如 AI、半导体或电动车，每天要做搜索、发现和摘要（非结构化数据），数据和分析（结构化数据），和同事交流收集信息，有的人还要规范化数据、写程序、建模型。金融业有些产品要求不能妥协：精确、全面、速度、吞吐、可用性，保护贡献者和客户数据，全程透明。不管用不用 AI 都一样。

第一个产品：财报电话会摘要

2023 年他们认真起步。上市公司每季度开财报电话会，管理层演讲，然后问答。财报季一天会有很多场，分析师要跟上。Bloomberg 本来就用 AI 生成通话转录稿，他们发现：对某个行业的公司，分析师关心哪些问题是可知的，可以提前回答好，帮分析师决定要不要深入。看起来简单，但当时开箱即用的效果不好，精确度、准确性、事实性都不够。他们做了很多 MLOps 工作：补救工作流、熔断机制 Circuit Breaker。因为这些摘要是公开发布的，所有人看到的都一样，任何错误影响都很大，所以持续监控、补救，摘要才越来越准，背后有大量监控和 CI/CD。

今天的产品架构他称为“半 Agent 化”：他们还不完全相信一切都能自主，有些部分自主，有些不是。护栏 Guardrails 就是典型：Bloomberg 不提供投资建议，用户问“我该不该投某某”就要拦住；事实性也是护栏。这些对任何 Agent 都不是可选项，是写死必须执行的检查。

扩展的第一点：别指望上游准确，自己做检查

他读研时经常用矩阵乘法，展示了通用矩阵乘 GEMM 的 API 文档：每个输入、每个错误码、运行时间都写清楚，就是能用。建在这种软件上的产品也很稳健。20 年前开始用机器学习做产品时，下游调用者面对的 API 背后是模型，有一定随机性，但还能用。到了 LLM 和 Agent（由多个 LLM 组合而成），错误会成倍放大，带来脆弱性。

2009 年他们做过新闻情绪产品，判断一条新闻对某公司是利好还是利空。输入分布清楚（监控哪些通讯社、什么语言，通讯社还有编辑规范），输出就是 -1 到 +1，训练数据是自己从零做的，有按时间和空间切分的测试集，能评估部署风险、能监控。即便这样，他们还要和下游做大量带外沟通，比如提前通知“模型版本要变了，你的下游应用请测一下”。

Agent 架构下情况变了：你想每天改进 Agent，不想要靠批量回归测试的发版周期，因为下游有很多也在独立改进的消费者。他举了一个例子：用户问“美国过去五个季度的 CPI”，一个 Agent 理解问题、分派到对应领域，再调用工具取数。结果数据错了，因为漏了一个字符，取到的是月度数据。好分析师看表格能发现，但如果下游工作流不展示表格，只给一个“答案大概是 42”，这种叠加的错误就很难发现。所以与其指望上游准确，不如假定上游会脆弱、会变化，自己做安全检查。即使在他自己的组织里，数据和分析 API 工具每个版本都在变好，但“更好”是平均意义上的，不代表对你这个下游更好。他认为加这些护栏反而让你走得更快：每个 Agent 都能独立演进，不需要每个下游都签字才能把新 Agent 推到 beta 或生产。

扩展的第二点：组织结构

他说自己现在是管理者，所以讲讲组织结构。传统机器学习有一套软件拆分方式，组织结构也跟着它（他提到“反向康威定律”）。做新产品时要重新想：要建多少个 Agent，每个做什么，功能能不能重叠。直接沿用现有的软件栈或组织结构很诱人。他们的经验是：一开始不清楚产品形态、要快速迭代，就把组织和软件栈压扁，成立垂直团队去做，共享代码、数据和模型。等你对单个产品或 Agent 理解透了，知道它擅长什么不擅长什么，并且建了很多个这样的 Agent，再回到好软件和好组织的基本功：优化性能、降成本、更可测试、更透明，这时开始建横向团队。护栏在他们那里就是横向的，不希望 50 个团队各自去琢磨怎么拒绝“变相的投资建议”。每个组织要自己判断什么时候开始做横向能力、拆分单体 Agent。

以研究分析师 Agent 为例，现在的结构是：理解用户问题和会话上下文、判断需要什么信息，单独做成一个 Agent，在组织上也对应一个团队；答案生成单独拆出来，对“什么是格式良好的答案”有严格要求；护栏不可选，必须在多个环节调用，没有自主性，所以叫半 Agent 化；底层是多年积累的传统和现代数据处理，比如稀疏索引已经变成了稠密和混合索引。

10. Mike Conover（Brightwave）：面向金融工作流的知识 Agent

直播位置 3:30:29–3:51:05 · Knowledge Agents for Finance Workflows

Mike Conover 是 Brightwave 的创始人兼 CEO。之前他在 Databricks 做了语言模型 Dolly，是较早证明指令微调 Instruction Tuning 能让开源模型学会遵循指令的模型之一。Brightwave 做的是能消化金融领域超大量内容的研究 Agent。

用户和问题

他举了几个场景：竞争性交易里还没签条款清单，你进了一个有几千页材料的数据室，要比其他团队更快形成判断，找出会削弱资产表现的关键风险；共同基金分析师在财报季覆盖 80 到 120 家公司，有电话会、转录稿、监管文件；确认性尽调时手上有 800 份供应商合同，要找出提前终止条款，看整个投资组合在合同谈判上的整体情况。他说这超出了人的能力，初级分析师在很紧的期限里被要求做不可能的事。

他拿早期电子表格类比：1978 年问会计“你的工作是什么”，答案是“算数字”，那些人把数字手写在很宽的纸上，那种纸就叫 spreadsheet。工作费脑、重要、耗时。现在没人想要那份工作了。财务分析仍然有人做，只是工具让人能把更高水平的思考用到问题上。他们从客户那里听到，这类知识 Agent 能把效率和见效时间提高几个数量级。要解决的设计问题是：一个看过一万页内容的系统，它的思考过程怎么以有用、可读的方式呈现给人。他说这在三年前并不存在，最终形态还没定，大家都盯着 Chat，那大概不够。

技术观察

非推理模型做的是贪心的局部搜索。他接着 Bloomberg 讲的保真度问题举例：把一篇 Reuters 文章给 GPT-4o，让它抽出所有组织，它很可能会把产品也给你。如果错误率是 5% 到 10%，链式调用会让出错概率呈指数增长。他认为胜出的系统会在工具调用上做端到端 RL，把 API 调用结果也纳入 RL 的决策序列，这样可以在局部做次优选择以换取全局最优，但这仍是开放的研究问题。

现实是你今天就得交付产品。人们会说 Bitter Lesson，更多数据、更多算力、更好的模型压倒一切，没人想要专家系统，没人想用 spaCy 做命名实体识别。他的看法是：限定 Agent 的行为范围，就像机器学习里的正则化参数，约束复杂度，降低系统彻底跑偏、产出退化内容的可能。他说和语言模型最有意思的对话都在对话树很深的地方，每一步你都在选怎么回应、在引导它，这是一种技能，而有全职工作的人不一定会花时间练。他把多轮对话看作在推动模型的激活值：你说“不是这样，更像这样”，就是把激活值推到能解决问题的位置，他认为思维链做的也是这件事。人们不会想成为提示词专家，那要上千小时，所以垂直化的产品工作流会长期存在，因为它们替用户明确了意图。

设计模式

  • 模仿人的决策过程来分解任务。比如想了解一家聚丙烯树脂制造商怎么管理成本，会去找上市可比公司，查 SEC 文件和电话会转录稿，可能还会查私募投资人自己过往交易构建的知识图谱、新闻语料，判断哪些文档相关，从中提炼支持或否定假设的发现，再充实和纠错。
  • 中间笔记：他提到 Deep Research 团队讲过的做法，在第一轮过完数据后写下“根据目前找到的事实，我们相信什么”，他认为很有用。
  • 对单条发现做充实很有效；自我纠错也有效，比如问模型“这是否被这篇文档在事实上蕴含”“这真的是一个组织吗”。他们发现放在同一次调用的 JSON 里当思维链来做也行，但单独再发一次调用效果更好，因为模型在同一轮里倾向于轻信自己刚说的话。
  • 最后通过综合，把很多文档里的事实串成连贯的叙述。
  • 人的监督很重要：分析师掌握未数字化的信息，比如和管理层的谈话、投资经理认为某类生物科技公司不靠谱。他认为最强的产品会倾向于发挥这种品味判断。
  • 反对把节点拟人化。很多人还在做“投资经理 Agent”“事实核查 Agent”，他认为这会在计算图需要变化时限制灵活性。他引用 Unix 哲学：简单的工具只做一件事，彼此配合好，文本是通用接口。

他引用 Latent Space 画的价格性能帕累托前沿：这个前沿会不断外推，但会一直存在，所以每个计算图节点都要选用哪个模型。他提出“延迟陷阱”：很容易想象系统会检查、纠错，25 分钟后给出精彩结果，但即使像 OpenAI Deep Research 这样的好产品，你也不确定输出质量。而且从用户练习的角度，用户对报告的预期和实际报告之间的差距就像损失函数，用户在学习“我的提示会引出什么行为”；如果反馈回路是 8 分钟、20 分钟，一天练不了几次，用户对系统的掌握就会很低。

综合是最难的部分

他问在场有没有人从任何模型拿到过 5 万 Token 的回答，没人。o1 号称输出上下文 10 万 Token，他存疑，因为后训练用的示例（人写或合成）有典型的输出长度，人很难写出 5 万字连贯的新内容；o1 的输出也只比 GPT-4o 长两三千 Token 左右。所以这是一个压缩问题：输入上下文很大，要压缩到有限的输出 Token。他让模型写全球金融危机分析，结果“影子银行体系的兴起”只写了三句话。把研究指令拆成多个子主题，更细、更具体，能得到信息密度更高的输出。另一个限制是后训练语料里缺少“重组式推理”的示例：给《了不起的盖茨比》写个新结尾很容易，读一遍就能写五个；综合是把多篇文档的不同事实编织在一起，比如生物医学文献综述，这类高质量示例很难得到。时间性也难：并购之后的备考财务报表和之前不同，合同有补充条款，所以要带着证据段落传递元数据，说明为什么关心这条、怎样和上下文里其他证据一起看。

产品演示

他认为呈现方式更像一个“表面”。他类比 Facebook 和 LinkedIn 的“你可能认识的人”：算法一般，但人的视觉皮层有专门识别面孔的区域，在 6×6 的头像里一眼就能认出熟人，所以即使精度不高，你也会注意到重要的东西。关键是按需给细节。演示里，点击 Brightwave 报告的引用，会看到额外的上下文：来自哪篇文档、该怎么理解、模型当时怎么想的；有结构化的交互输出，可以“追问资本开支上升”；可以高亮任何一段文字问“告诉我更多、这意味着什么”（他说 OpenAI Canvas 也在往这个方向走）。他把模型读完文档形成的东西看作一个高维数据结构，报告只是其中一个视角；金融用户要看“收据”，也就是审计线索：融资时间线、正在进行的诉讼，点进去看细节。比如看到一条专利诉讼，或者墨西哥一家关键单一来源供应商的工厂失火，就能立刻深挖。他承认这类产品的最终形态还没出现。最后是招聘广告，提到 1 万美元推荐奖金，并按 DARPA 红气球挑战的方式沿推荐链分配。

11. Kevin Hou（Windsurf / Codeium）：Agent 成败在边缘，从 90 分到 100 分

直播位置 5:07:34–5:27:56 · Agents are built at the fringe: getting from 90 to 100

午餐后第一场。Kevin Hou 领导 Windsurf 的产品工程团队，团队在旧金山，他说这是 Windsurf 第一次公开演讲。Windsurf 是 Codeium 做的 Agent 编辑器。

来历和数字

2022 年 Copilot 刚出 beta，大家第一次看到灰色的补全文字。Codeium 是最早推出自动补全产品的公司之一，在 VS Code、JetBrains、Vim、Emacs 插件上积累了几百万用户。他们一直相信模型会变强，所以那时就开始研究 Agent，但当时能做的最好产品是聊天加补全。他们知道从 ChatGPT 复制粘贴会成为过去，以后按 Tab 也会变少。他说 2025 年大家终于都认识到 Agent 在软件开发里的力量。

演示：在侧边栏的 Agent 里让它写一个 Python 网页爬虫并统计网站信息，它在你自己用的终端里用 pip 装依赖、建虚拟环境、给出修改建议，用户逐条接受或拒绝。还有默认开启的网页搜索、在代码库里 grep、生成 commit 信息、拖入图片等。团队的使命是“让你保持心流”：把查堆栈、改源码、找对版本文档这些杂活交给 Agent，让用户用最少的显式输入得到最正确、可以上生产的代码，减少人在环。

Windsurf 在 11 月 13 日上线，三个月里生成了 45 亿行代码。过去 90 天里有 16 个晚上，团队半夜被 PagerDuty 叫醒，因为容量超了，他们已经是 Anthropic 和 OpenAI 最大的客户之一。

原则一：轨迹 Trajectory

他说和 Cursor 这类编辑器（他称之为“房间里的大象”）不同，Windsurf 的 Agent 深度集成在编辑器里：一方面要理解你在做什么，另一方面要能替你执行。功能例子有“continue my work”（继续我的工作）：Agent 一直在理解你写代码、跑终端命令的过程，你只要说这一句，它就接着做，甚至给出完整的 PR 或 commit。还有终端执行模式：由 LLM 判断命令是否安全，git 这类直接跑，有 rm -rf 就提示用户确认。

背后是一条“统一时间线”：Agent 在后台理解用户隐式的操作，查看文件、在代码库里跳转、编辑、搜索、grep、提交，用户和 Agent 的动作都写进同一条时间线。这样就不会出现 Agent 撤销你刚做的修改，或者对文件状态有过时认识。演示中用户加了一个新函数，然后说 continue my work，Agent 推断表单处理函数应该用这个新函数，改了相关文件，最后在后台终端里跑了 npm run dev。另一个例子是你在终端里 npm install 或 pip install 一个包，Agent 会知道并接着把它用进项目。他们相信“不再复制粘贴”，也认为未来不会是纯终端。命令在尽量接近用户自己环境的沙盒里跑，pip install 装进的是同一个环境。他说以后 Agent 会往前看 10、20、30 步：你还没写完函数，它已经在写单元测试；你改一个变量名，它就做全代码库的重构。

原则二：元学习 Meta-learning

前沿 LLM 是很强的工程师，但它不知道你个人或你公司怎么写代码，而资深工程师会慢慢积累这些。Windsurf 的做法：

  • 自动生成的记忆：说一次“记住我用 Tailwind v4”“记住我用 React 19 不是 18”，就会一直记住。演示里用户只是问“这个项目是做什么的”，Agent 通过几次工具调用看了文件和路由，就把项目结构和可用端点存进记忆，下次对话可以一次做对。
  • 支持自定义 MCP 服务器，接入自己喜欢的工具。
  • 命令白名单和黑名单，比如“没有我批准不要运行 rm”。
  • 文档自动学习：根据 package.json 知道你用的包和版本，自动上网找对应版本的文档。

他说公司里有句话叫“想法很便宜”。他们允许用户写规则文件，但认为规则文件是拐杖：到 2025 年底，你放进规则文件的东西 99% 会从代码库或使用过程中推断出来，每个用户的 Windsurf 都会针对他个性化。

原则三：随智能一起扩展

2021、2022 年模型不够聪明，大家（包括他们）建了很多基础设施：向量索引、检索启发式、输出校验系统，在边际上有帮助，但都基于“智能水平固定”的假设。Windsurf 希望产品随模型一起变好。例子是他们删掉了 Chat：他到纽约后发了条推特说 Cascade 里删掉了聊天，很多人注意到了。现在 Windsurf 里只有 Agent，叫 Cascade，聊天被视为旧范式，用户可能都没察觉，只感到质量更高。

另一个例子是 @ 提及。以前上下文检索不好，才需要 @file、@web、@docs；现在 Windsurf 能动态推断代码和文档之间的关系，90% 的情况下不用 @，让检索系统和 Agent 自己规划、重建上下文。演示里以前要在 Next.js 应用里接 Supabase，得 @docs、@codebase，现在只说“加上 Supabase”，它会自己决定搜网页。内置网页搜索按人读网页的方式工作：本来可以做嵌入索引，但他们认为结果质量会很低，所以让模型自己决定读哪些搜索结果、读页面哪部分，再给答案。

他给的数字是：Windsurf 用户写的代码里 90% 由 Cascade 生成，而自动补全时代是 20% 到 30%。最后他推了下载链接和免费档，还开玩笑说“像纽约所有好东西一样，我期待 25% 的小费”。

12. Mustafa Ali（Method）与 Kyle Corbitt（OpenPipe）：两个工程师在生产中跑 5 亿个 Agent

直播位置 5:28:06–5:46:27 · How we scaled 500m AI agents in production with 2 engineers

Mustafa Ali 是 Method Financial 的高级软件工程师，Kyle Corbitt 是 OpenPipe 的创始人兼 CEO。Method 从几百个数据源汇集并整理负债数据：接入征信局、Visa 和 MasterCard 这样的卡组织、直连金融机构和其他第三方，再提供给金融科技公司、银行和放贷机构，用于再融资、贷款整合、还款和个人理财。OpenPipe 帮客户训练和部署开源模型，并用生产中的用户和环境信号持续改进模型。

问题和最初方案（Mustafa）

客户希望除了余额和还款信息，还能拿到具体负债的数据点，比如车贷的提前还清金额、房贷的托管账户余额。他们问数据伙伴，发现没有集中的 API；直接和银行合作至少要几年，作为早期公司等不起。再去问客户现在怎么做，答案是雇海外外包团队，替公司和终端用户给银行打电话、验证身份、收集信息，再有人校对，然后录入金融平台。这个流程贵（一人同时只能做一件事，扩展只能加人）、慢（同步）、人为错误多（还要专门的校对团队），最糟的情况是给用户展示了错误的金融信息。

他们把问题拆下来，发现核心是理解非结构化数据，而且整体像一个 API：有请求、认证、响应校验。恰好 OpenAI 发布了 GPT-4，他们很快用 GPT-4 搭了一个 Agent 工作流，效果很好，还尽量在一次调用里抽更多字段。流量一上来，第一个月账单是 7 万美元，管理层很不高兴，但因为价值很大，仍然让它在生产里跑了几个月。除了成本，提示工程也撞墙了：GPT 很聪明但不是金融专家，需要很详细的指令和示例，提示词越来越长、难以泛化，修好一个场景就弄坏另一个，也没有提示词版本管理。总结下来，GPT 方案有和人工方案一样的扩展问题：贵（提示词常改、响应多变，没法利用缓存）、慢（基础延迟高，没法高并发）、有错误（幻觉，难以发现）。

他们估算的目标规模：每天至少 1,600 万次请求，至少 10 万并发，延迟要低于 200 毫秒。于是开始想要不要买 GPU、自己托管模型。

先测量，再定目标（Kyle）

大约一年前 OpenPipe 开始和 Method 合作。Kyle 说质量、成本、延迟这三个问题几乎是他们每个客户都关心的。第一步是测错误率：概率系统做不到 0%。在 Method 的任务上，GPT-4o 错误率约 11%，o3-mini 约 4%。Method 的任务比较好测，因为 Agent 最终是要抽出余额之类的信息，可以让人走一遍流程得到真实值，再和 Agent 的最终输出比对。延迟上 GPT-4o 约 1 秒，o3-mini 约 5 秒。测量时要用真实生产条件：真实的任务分布、和生产相当的并发。成本上，o3-mini 的单价虽然比 GPT-4o 低，但在这个任务上反而略贵，因为它生成大量推理 Token。他建议有了能用的原型之后，写几个简单的 Python 脚本对不同模型做这类测量，新模型出来时就能很快知道表现如何。

然后确定需要达到的线。Method 在模型之后还有额外检查（数字是否合理、是否和以往一致等），所以不需要 0% 错误，但检查也会漏，大约 9% 的错误率能满足需要。延迟有硬上限，因为是实时系统。他说客户之间差异很大：有的后台批处理几天内出结果就行，有的做实时语音，超过 500 毫秒就不行。Method 量大，成本很重要。对照下来，两个模型都不能同时满足三项：GPT-4o 错误率和成本不达标，o3-mini 成本尤其是延迟不行。

微调

OpenPipe 做的是微调 Fine-tuning，为具体用例定制模型。他说微调是“电动工具”，比提示需要更多时间和工程投入，所以应该先拿生产模型做好基准测试，确认提示做不到再上。微调可以大幅改变价格性能曲线：错误率显著好于 GPT-4o，也好于 Method 的门槛。以前这需要大量人工标注，现在容易多了：拿生产中的真实输入，用 o3-mini 这样的模型生成输出，再拿来训练。通常达不到老师模型 o3-mini 的水平，但能很接近，而且比稍差但大得多的模型好。最后部署的是 80 亿参数的 Llama 3.1，他说大多数客户用这个大小或更小的模型就够。模型小，顺序计算的层数少，延迟低得多；还可以部署在自己的基础设施里，和应用代码放在一起，完全消除网络延迟（Method 没有这样做）。成本也大幅下降，远远超过 Method 的成本目标，单位经济不再是问题。

Mustafa 总结：标题里写两个工程师，是因为这事没那么复杂。选定具体用例，用 GPT 在生产中已经积累了数据，不用另外找数据，用最便宜、最快的模型，也不需要买 GPU。另外，把 AI Agent 推上生产需要工程团队和管理层的开放和耐心：传统代码写完就能用，Agent 需要一段时间才能达到生产可用。他最后开玩笑：“如果你还在做传统软件工程，转 AI 工程吧。”

13. Nick（SuperDial）：语音 AI，你的 Bot 并不特别

直播位置 5:46:59–6:05:46 · Voice AI: Your Bot Isn't Special

讲者是 SuperDial 的 staff 软件工程师 Nick（字幕里姓氏识别不清，故只写名）。他说这是当天少数几场语音 AI 演讲之一。

2025 年的语音 AI

现在有又聪明、又快、又便宜的 LLM，能支持复杂的对话用例，但把聊天 Agent 变成语音 Agent 还要一些技巧。文本转语音 TTS 模型延迟低、很逼真，但有时会出现音频幻觉，还要处理发音和拼读。语音 AI 的基础设施、工具和评测系统数量激增，问题变成哪些值得自己掌握。大家最关心的是新的语音到语音（voice-to-voice）模型，他们的看法是对很多生产应用还没准备好，因为会输出不像正常说话、不利于构建可靠对话的东西，刚出来时还会模仿人的声音。所以他们从一开始就选择可靠性优先于逼真度。

SuperDial 做什么

他们做的是最烦人的那种电话：打给保险公司。客户是中大型医疗行政机构。客户设计通话脚本和要问的问题，通过 CSV、API 或 EHR（电子病历系统）集成把要打的电话发过来，几小时到一天内拿到结构化结果。这形成了一种“Agent 合同”：客户为结果付费，告诉他们打给谁、问什么，SuperDial 给出答案。内部有一个 Agent 循环：等对方办公时间、呼叫中心开门再打；先用语音 bot 打，如果需要人接手，或者尝试若干次仍完不成，就交给后备人工团队。他们对客户透明，客户也乐意，因为医疗电话有时必然需要人，而无论如何电话都会打完、答案都会以结构化格式拿到。每通电话后都会学习，更新这个号码的办公时间、记录电话按键菜单的走法；因为是敏感电话，还会随机抽查审计。

他播放了一段事前授权 Prior Authorization 电话的录音，已经走完按键菜单、在和真人对话：报会员 ID、CPT 编码 81243，对方查到该编码的案例正在审核，还没收到临床资料，最后要了对方姓名和通话参考号。他说如果你觉得这通电话很无聊，那就对了，对他们来说无聊的电话就是好电话，很多工作本来就无聊。这个系统已经节省了超过 10 万小时的人工通话时间，2025 年有望节省数百万小时，而团队只有 4 个工程师，从全栈网页应用、EHR 集成到 bot 都是他们做的。

语音 AI 工程师

他在 swyx 最初那张图的基础上说，语音 AI 工程师要处理多模态数据（MP3、音频字节和转录稿），要用转写、语音、语音到语音模型；应用是实时的，延迟突然重要得多，会写比想象中多得多的 Python async；产品约束几乎总是一场语音对话，人们对对话的期望很高，他们是嵌入已有的业务交互里。SuperDial 内部有两句话：“在对的时间说对的话”和“边飞边造飞机”。最难的是给每个客户定制脚本和用例，其他问题依靠横向的语音 AI 技术栈。他的核心观点是：现在做语音 MVP 很容易，你的 bot 的独特之处不在声音、打断处理、逼真程度或轮流说话，而在对话内容和设计，以及围绕它的垂直集成。

他也提到伦理：语音应用可能对某些口音或方言有偏见，也可能听起来很真却说出奇怪的话。美国 AI 监管少，责任落在工程师和管理者身上。他建议选择工具和基础设施时，让各种背景的利益相关方从一开始就能参与。

最后一公里的问题

一开始他们拼了一条转写模型加 LLM 加 TTS 的流水线，很快遇到很多问题，而很多经验并不新：语音 UI 早就有了。他和家里的朋友 Cathy Pearl 聊过，她做对话设计大约 20 年，在做 Gemini 的用户体验。语音 UI 从电话按键菜单设计，到 Alexa、Siri，再到现在，很多原则没变，最大的变化是从“规定式”变成“描述式”开发：不再画出对话的每个分支，只描述想要什么，然后祈祷它发生。比如提问时该开放还是给选项？因为是已有的对话，他们发现问得宽泛、让客服多说信息、再适应对方的回答，效果比防止对方说错话更好。Cathy 的建议是请对话设计师；如果只是工程师，可以做“剧本朗读”：一人扮 bot、一人扮用户，大声读出来，手写稿里的空白和别扭会立刻暴露。

技术栈方面：

  • 编排用 Pipecat，Daily 团队维护的开源框架，容易扩展和修改，方便他们做电话转接；他们的电话可能长达一个半小时，能自托管、按需部署扩展是选它的重要原因。
  • 自己维护一个兼容 OpenAI 接口的端点，和各种新语音工具对接更方便，背后可以路由到不同模型，比如对延迟更敏感的模型。
  • 所有生成请求经过 TensorZero，一个较新的开源工具，提供结构化、带类型的 LLM 端点，可以在生产中做实验。
  • 日志和可观测性自托管 Langfuse，因为医疗电话要符合 HIPAA，自托管更容易；在上面做异常检测、评测和数据集。

TTS 是另一个难点。这类电话的“密码”是姓名、出生日期和会员 ID，会员 ID 可能是 12 位字符，要在电话里说清楚。LLM 的输出不一定适合直接送进 TTS，两者也不一定和录音一致。他举了自己的姓：大多数人和模型都念错。Rime 这家公司的语法可以写出精确发音；拼读长串字符时可以用一个“拼读”函数控制停顿。因为输出是音频，他们除了检查转录稿也会回听录音。用语音到语音模型的话，这些基于规则的处理会更复杂。

他的几条小经验：

  • 早定人设：公司原名 SuperBill，bot 叫 Billy，结果电话里人们总是听错名字，反复纠正，很糟糕。
  • 刚起步别从零造，Pipecat 这类工具能让你快速起步。
  • 到处追踪延迟，每个处理环节的首字节时间是最重要的新指标。
  • 想好升级路径：转写用 Deepgram，需要更高准确率时可以和他们合作微调。
  • 准备好后备：OpenAI 宕机一会儿，所有并发通话就全断了。TensorZero 之类工具容易配置后备。
  • 端到端测试：大家逐渐用电话线路作为测试边界。最简单的是建一个只播放 MP3 的假号码，bot 连 MP3 都应付不了就有大问题；然后用按键菜单工具模拟一棵电话树让 bot 走；还有 Coval 等服务让你的 bot 和另一个 bot 对话。

他的结论：慎选技术栈，把精力放在对话体验真正独特的部分；专注最后一公里；跟上新模型，但要能安全地用。

14. Rahul Sengottuvelu（Ramp）：AI Agent 与 Bitter Lesson

直播位置 6:06:12–6:22:54 · AI Agents: the Bitter Lesson

Rahul 是 Ramp 的应用 AI 负责人。他开场让大家找幻灯片上的错误：标题配图是柠檬，“苦涩的教训”配了酸的柠檬，他自己十分钟前才发现。他做 LLM 四年了，ChatGPT 出来之前就在做后来会被叫做 AI Agent 的公司，那时是客服，用 GPT-2 和 BERT，模型笨、上下文窗口小，只能围着模型写大量代码让它勉强可靠；模型变聪明后，又一点点删掉这些代码，从中看出了哪些代码会被删、怎样建 Agent 能随智能扩展。他还写过结构化抽取库 JSONformer，他说可能是第一个，时间上早于其他主流库，那也是在模型不会输出 JSON 时“求它、逼它”的脚手架。

Bitter Lesson

他转述 Rich Sutton 的 Bitter Lesson：随算力扩展的系统会打败不随算力扩展的系统。后者往往是死板、固定、确定性的。他进一步解释原因：指数增长很少见，大多数东西不是指数的，碰到了就应该搭上车，不必太用力。国际象棋、围棋、计算机视觉、Atari 游戏都是例子：人们花很多周末写聪明、抽象良好的代码，把人类思考过程合成为特征。固定算力时这种做法会赢，但一旦扩大搜索规模，通用方法总是胜出。

Ramp 的一个生产 Agent：切换报告

Ramp 是帮企业管理费用、付款、采购、差旅和记账的金融平台，产品里有大量 AI，处理财务团队和员工的杂事，比如提交报销、订机票酒店，很多工作是和其他遗留系统打交道。他讲的是“切换报告”Switching Report：新客户上 Ramp 时，Ramp 想给他们一份清单，列出他们在其他卡平台上的交易，帮他们迁过来。难点是读入任意格式的 CSV，各平台的 schema 千奇百怪。三种做法：

  1. 为最常见的 50 家第三方卡厂商手写解析代码。能用，工作量不大，但要去 50 个平台下载 CSV 看格式；对方改格式就会坏，坏了你会被叫醒去修。
  2. 在确定性流程里加一点 LLM：对每一列调 OpenAI 或嵌入模型做语义相似度，分类是日期、交易金额、商户名还是持卡人，再映射到目标 schema。大部分计算仍在传统代码里。
  3. 把 CSV 直接交给 LLM，给它代码解释器，可以用 pandas 或基于 Rust 的更快的库，能看头尾任意行，要求它输出指定格式的 CSV，并提供一个单元测试作为验证器。他说只跑一次时这招不灵；并行跑 50 次，就很可能成功，而且能泛化到很多格式。

第三种的算力大约是第一种的一万倍，但真正稀缺的是工程师的时间。即使多用一万倍算力，成本可能不到 1 美元，而每一笔迁移失败的交易、每一个解析失败的 CSV 给 Ramp 带来的损失都远大于此。

他把三种做法画成图：黑色箭头是传统计算，蓝色箭头是“模糊”的 LLM 计算。第一种全是传统代码；第二种由传统代码在需要时调用 LLM；第三种反过来，LLM 决定什么时候写 Python 代码进入传统计算，大部分计算是模糊的。后端说到底都是请求-响应，人类至今建的系统大多像第一种；用 OpenAI 的系统大多像第二种；Ramp 代码库里越来越多部分在转向第三种，因为效果好，而且就算全公司放假一年，大实验室还在花几十亿美元改进模型，蓝色箭头会自己变好，你代码里蓝色箭头越多，公司越受益。

演示：LLM 就是后端

他再往前推一步。传统网页应用如 Gmail：静态服务器发来 JavaScript、HTML、CSS，浏览器渲染，点开邮件时前端请求后端，后端查数据库返回。哪怕用了各种代码生成工具，LLM 也只在工程师写代码时参与，上线后就是传统计算。他提议的模型是：后端就是 LLM，由它直接执行请求，不让它去生成代码。LLM 能用代码解释器、发网络请求、访问数据库。

他现场演示了按这个原则做的邮件客户端，并公布测试邮箱让观众发邮件。还是有一些普通 JavaScript 把 LLM 接到浏览器上。登录时，他的 Gmail token 直接发给一个 LLM 会话，提示词大意是：“你在模拟一个 Gmail 客户端，你能访问所有邮件、Rahul 的 Gmail token 和代码解释器，按你认为合理的方式渲染首页。”它把邮件列表渲染成 Markdown（他说其实是提示里要求的）。他点开一封“hello from California”，没有调用任何后端接口，只是告诉 LLM 用户点了这段文字和对应 ID，LLM 去取邮件正文、重新渲染页面，还自己加了“标为未读”“删除”等功能。他试着删除邮件，没成功，整个过程很慢。他说这种软件今天勉强能用，但不代表将来不行，在指数趋势下它可能会起飞，他想推大家往这个方向想。

15. Karina Nguyen（OpenAI）：创造能共同创作的 Agent

直播位置 7:06:33–7:30:30 · Creating Agents that Co-Create

最后一段开场时 Ksenia 说日程有一处调整：第二场换成了教育主题。Karina Nguyen 是 OpenAI 的 AI 研究员，之前在 Anthropic 做了大约两年 Claude。她要讲过去两到四年 AI 研究里的两种扩展范式，它们怎样打开新的产品研究，开发 Claude 和 ChatGPT 时的设计挑战，以及 Agent 怎样从协作者走向共同创新者。

两种扩展范式

第一种是下一个 Token 预测，也就是预训练。她说它是一台“构建世界的机器”：模型通过预测下一个词来理解世界，因为序列是由前面的动作引起的、不可逆，模型就学到一些世界的规律。Token 可以是字符串、词、像素。下一个 Token 预测相当于大规模多任务学习：有的任务好学，比如翻译、“法国首都是巴黎”这类在网上大量出现的知识；有的任务很难，比如物理、问题求解、逻辑表达、空间推理（还不完美）。数学这类任务在单次 Token 预测里需要的计算量太大，所以需要思维链，花更多算力在推理上。

她特别讲了创意写作。模型可以很好地预测风格，但创意写作主要是构建世界、讲故事、设计情节，预测下一个 Token 时很容易犯一个错，就让情节连贯性崩掉。它也很难衡量什么是好的创意写作。她认为让模型写出长篇连贯的小说、甚至发明新的写作形式，是当下最难的 AI 研究问题之一。

2020 到 2021 年 Anthropic 和 OpenAI 都在大规模扩展预训练。早期产品之一是 GitHub Copilot：模型从 GitHub 开源项目的数十亿代码 Token 学了很多，研究者再用 RLHF 和 RLAIF（基于 AI 反馈的强化学习）约束它，让补全更有用，后训练时代就此开始：教模型补全函数体、理解 docstring、生成多行补全、预测和应用下一个 diff。她认为后训练还有很多可探索的空间。

第二种范式是去年 OpenAI 用 o1 发布的：在思维链上扩展强化学习。模型在训练中学会怎么思考，并从好的 RL 信号中学习。她对比了原版 GPT-4 的输出和 o1 的完整思维链。任务越难，比如从翻译走到解决医学问题，模型越需要长时间思考，需要更复杂的、带工具的环境来思考和验证输出。思维链本身还有很多科学问题：忠实度怎么衡量，模型走错方向能不能自己回退。她在 OpenAI 做的第一个项目和交互范式有关：模型遇到难题会想很久，怎么让人不用干等 15 秒或 30 分钟？一个简单做法是把思考的摘要流式展示给用户。她说随着能力和交互范式变化，总会有新的设计挑战。

从 Agent 到共同创新者

她说今年 OpenAI 把它看作 Agent 之年：经过 RL 和思维链训练的复杂推理者，在长时间、长上下文里使用浏览、搜索、Computer Use 等真实工具。她认为下一阶段是共同创新者 Co-innovator：在推理、工具使用、长上下文之上再加创造力，而创造力只能通过人与 AI 的协作实现，所以要为人与 AI 的协作创造新的交互方式。

她说产品研究的节奏也变了，现在的情况比“拿到 API 再集成进产品”快得多：可以用强推理模型蒸馏出更快的小模型，用它们合成新数据，构建新的后训练数据集和 RL 环境。比如想做多人与 AI 的协作，可以合成以不同用户为条件的数据集来训练。RL 环境会越来越复杂，让模型在 RL 中使用搜索、浏览、Canvas 这样的协作工具，从而学会协作；也可以利用上下文学习 In-context Learning，做个新工具，给几个示例模型就会用；还可以设计新的模型行为和交互来利用用户反馈。

几个产品故事

  • Claude 的 100K 上下文：把陌生能力放进熟悉的形式。当时也可以做成一个无限长的聊天，但他们选了文件上传，因为大家天天和文档打交道。
  • ChatGPT Tasks（她在 OpenAI 的第二个项目）：提醒和定时任务是熟悉的东西，但它能随模型能力扩展，比如让模型每天给你续写一个故事、每隔一天搜索你感兴趣的内容，或者每天生成交互式可视化帮你学外语。她的心得是产品功能应该支持模块化组合，模型变强时能自然扩展。
  • 实时交互与异步任务之间的衔接：让模型去研究或写代码 10 个小时再回来，瓶颈是信任。她认为要给人新的协作方式去核验、编辑模型输出，并实时给模型反馈，让模型自我改进。
  • Claude in Slack：Anthropic 最早的产品之一，第一次尝试把虚拟队友放进组织。Slack 自带工具、图片上传、多人协作，她认为还有很多经验可以带到下一代产品。Tasks 也受了它启发，那时 Claude 能每周五汇总公司各个 Slack 频道。
  • Canvas（她在 OpenAI 的第一个项目）：界面很灵活，模型可以是共同创作者和编辑，做细粒度修改，可以搜索后写报告，你可以要求它核实某段输出。这种界面可以扩展到多人，甚至多 Agent（比如加一个批评者或编辑模型），同时多人又多 Agent 是新的设计挑战。Canvas 同时被训练成能协作写作和写代码，能搜 API 文档，上传 CSV 后还能做实时数据分析。她前一天在飞机上用 Canvas 给自己做了一个游戏。

她还想要个性化的导师：视觉型学习者和听觉型学习者得到不同的教法。研究方面，她演示了让模型复现她参与发表的一篇论文：人和模型一起共写一份文档，模型利用自身知识，双方一起提出研究假设、验证方向，也可以把任务委派给 AI 助手。

她对未来的设想

她预测会有一层“看不见的软件创作”，人们在手机上就能做自己的工具；点网页链接会越来越少，人们会通过模型这层透镜访问互联网，更干净、更个性化。比如说“我想了解太阳系”，得到的应该是一个可交互的 3D 可视化。她把通往 AGI 的界面想象成一块会按你的意图变形的空白画布：你今天要写代码，它就变成 IDE；你要写小说，它就为你临时造出头脑风暴、编辑、人物情节可视化的工具。最后她说，共同创新会通过和强推理 Agent 系统的创意共同指导来实现，去创造小说、电影、游戏，以及新的科学和知识。

16. Stefania Druga（Google）：下一代 AI 工程师

直播位置 7:30:48–7:51:42 · The Next AI Engineers

Stefania Druga 是 Google 的研究科学家。她问现场有多少人第一次来 AI 工程大会、多少人来自美国以外，然后进入主题：怎样把这些知识开放给更年轻的下一代 AI 工程师。她给的理由是 70% 的 AI 用户是 Z 世代，学生已经在用生成式 AI 写作业，很多时候他们更喜欢 AI 而不是人类辅导老师。她希望孩子们也成为设计这些工具的工程师。

Cognimates：在 Scratch 里学 AI

Scratch 是 MIT 开发的免费开源少儿可视化编程平台，全球有超过 1 亿孩子在用，积木块像乐高一样拼成程序。她在 MIT 读硕士时就在那个实验室，2015 年开始做 Cognimates，扩展 Scratch，让孩子通过做游戏、训练自己的 AI 模型、编程硬件来学习 AI。

她展示了 9 岁的 Tiana 第一次写的程序：机器人检测到人数大于零就说“我看到你了”，是捉迷藏游戏，Tiana 玩了半小时。她问观众程序有什么问题，有人答出来：缺一个循环，否则只能玩一次。她说 Scratch 从开始到能玩的时间很短，所以选了它。视频里孩子们训练模型玩石头剪刀布，有孩子说“电脑玩着玩着变好了，就像我们一样，一开始不会，多试就会”；家长说自己父亲年轻时会把车拆开看它怎么工作，孩子也应该这样了解大人编程的东西。

2015、2016 年这些孩子训练的是图像和文本的基础分类模型，也能用现成的情感分析、图像分类扩展，给语音助手编程让它记住自己的偏好（因为他们发现语音助手很有限），编程 micro:bit 和机器人。训练页面上可以拖入示例图片：一个孩子做“独角兽对独角鲸”的游戏，把画对着摄像头，看模型的预测和置信度。置信度很低时孩子会想到，自己的训练图大多是卡通，要补一些手绘的图。她说这就是 AI 素养和数据素养，能消除“AI 是邪恶终结者”之类的误解。孩子们做了把摄像头变成显微镜看食物的项目、石头剪刀布游戏、分析说话风格像哪位作家的文学程序。

她在公立、私立学校和社区中心测试，发现孩子像小科学家：给对工具，他们会提出关于模型怎么工作的假设、测试、修正理解。所以工具要让孩子尽快进入这个科学过程，还要好玩、让人想一直用。她在孩子编程和训练模型前后，都问了他们对语音助手、智能玩具和机器人的看法（聪不聪明、信不信任、友不友好），发现经历训练和编程之后，孩子对这些技术的智能归因有显著变化。平台已被翻译成 50 种语言。

家庭和 AI 结对编程伙伴

疫情时很多孩子困在家里，她开始研究家庭可以一起用的工具。一个早期原型是会参与编程过程的机器人，会说“我想知道你的名字，我们写个程序让我学会它吧”，并提示孩子去找“询问”积木。不是每家都买得起机器人，所以她想在浏览器里做一个类似的结对编程伙伴。她在美国 10 个州、背景和族裔差异很大的家庭里做设计研究。造系统前先做了“绿野仙踪”式研究：没有可用的助手，她本人扮演 AI，孩子们通过聊天和“它”互动，事后才被告知是真人。

发现是：孩子不想让 AI 替他们做完一切，最想要的是一起想点子，比如“我想做个关于熊的游戏”“我喜欢足球，给我点主意”。一个 12 岁的参与者说，用 AI 朋友写程序的好处是项目里最难的就是开头，你会卡住、没主意。它还帮孩子展开想法，比如做 Pong 游戏时问“球怎么动、怎么动得更快”。它也支持孩子的创作者身份：一个孩子说写代码会烦躁，终于成功时有人说“干得好”感觉很好。参与研究的孩子编程时间是平时的两倍。也有失败的时候：太分散注意力，没法协调兄弟姐妹轮流，解释不了 Scratch 里 clone（同一对象的多个实例）和 broadcast 这类较复杂的概念，这时需要家长参与。

之后她做了一个评测基准，100 多个 Scratch 程序案例，在不同前沿模型上测它们解释 Scratch 代码、配合学习练习解释、调试和产生创意的能力，结果很有希望。然后才真正做出 Cognimates Copilot。她说这次是第一次公开刚跑完的研究结果：18 个来自 11 个国家的年轻人，用不同语言测试。系统很简单，代码编辑器加一个 AI 聊天，消息发到 Web 服务器再返回，她在评测包括一个用 Scratch 项目微调的模型在内的多个模型，还能生成游戏用的图片素材。分析 18 个孩子的会话发现，Copilot 提供了概念支持、设计支持、正面鼓励、平台导航等帮助，也有失败的情况，也有很多孩子拒绝它的建议。一个来自牙买加、从没写过 Scratch 的学生，在 Copilot 帮助下从零做出了完整可运行的程序，它还告诉他循环积木在哪、怎么建变量。高级用户喜欢它生成的素材和改进代码、加关卡的建议。孩子还拿它想角色名字和情节。有个孩子贴了代码截图要建议，不喜欢答案，说“我不想要这种移动方式”，Copilot 回答“没关系，这是你的游戏，玩得开心”。

经验

  • 把用户的自主权放在首位，平衡支持和挑战：默认不直接给答案，先提问；学生同一个问题问了三次还卡住，才给提示。
  • 把 Agent 当作激励者和起点，解决空白页问题，Scratch 里叫“冷启动”。
  • 允许灵活和定制：有的孩子想用语音，有的只想打字；有的想每次要三个点子，有的只要一个。
  • 在情境中支持创造：孩子希望 Agent 能和他们一起拖积木，想看五个 Agent 怎么协作做一个小行星游戏，希望生成的素材直接出现在舞台上。下一版原型打算把 Agent 接进 UI 的各个环节，支持声音生成、对摄像头画面做反应等多模态能力。
  • 做不到时要说明原因，比如“我的训练数据里没有这类图片”“我的提示词规定只回答 Scratch 相关问题”，以设定正确的预期。

她现场演示了原型：打招呼后它问今天想在 Scratch 里做什么，她说赛车游戏，它给出加速道具等点子。它能导入 Scratch 社区的项目，她加载了一个别人用 Scratch 写的手写数字 OCR 程序，画了一个数字，程序识别为 2 和 8；她本想截图让 Copilot 解释这段复杂代码，因为双屏没截成。项目免费开源。她最后说，AI 素养已经写进法律：本月早些时候生效的欧盟 AI 法案条款要求 AI 系统的提供者和部署者尽力确保员工和用户具备足够的 AI 素养，所以要从小开始。

17. Soumith Chintala（Meta，PyTorch 联合创始人）：做一个个人、本地、私有的 AI Agent 需要什么

直播位置 7:52:26–8:12:12 · What does it take to build a personal, local, private AI Agent that augments you deeply?

Soumith Chintala 联合创办了 PyTorch，这个项目主要由他所在的 Meta 资助。他说很多人现在只用高层 API，不知道底下是什么，但 PyTorch 很可能就在支撑你用的 AI API。他也参与一点 Llama 的工作，但不负责 Llama，不会透露下一个 Llama 什么时候发布。

为什么想做个人 Agent

他说每天最节省他时间的 AI 应用是 swyx 的 AI News：跟进 AI 进展是他的工作，以前每天要花三到五小时看各种来源，它帮你汇总。这让他开始想把 AI 更深地融入日常。但 AI News 不算 Agent，是聚合器。另一个原因是他做机器人，目标是做家用机器人，不用自己跑腿，而机器人本身就是 Agent。他的核心观点是：个人 Agent 有很大的行动能力，又掌握你大量的生活上下文，所以最好让它本地、私有。他说自己也没有完整方案。

他的 Agent 定义是：能在世界上采取行动的才是 Agent，只能获取上下文、做事却不能行动的就不算。他认为一个高度智能但缺乏正确上下文的 Agent“跟一袋石头一样没用”。例子：个人 Agent 能读他的 Gmail、WhatsApp 和日历，他问“处方续上了吗”，它说还没有。其实 CVS 的短信发到了 iMessage，它看不到，只能凭手头信息尽力回答。钱打进了 Venmo 但 Agent 只接了一个银行账户，也会“撒谎”。缺上下文的个人 Agent 会很烦人，你不知道它什么时候可靠，每次都得自己去查，所以达到一定的可靠性和可预测性之前，它就没用。

上下文从哪来，Agent 跑在哪

  • 可穿戴设备：AI 看你所看、听你所听，是提供上下文的最好方式，但现在没有设备的电池撑得住。
  • 手机：在后台一直看你的屏幕。但 Apple 不让你在手机上随便异步跑东西，就算能也有很多限制，他自己用 Apple，所以这条也不通。
  • Mac Mini：他觉得目前可行。如果你日常用 Apple 生态，买一台 Mac Mini 放在家里联网，异步跑 Agent，没有电池问题，可以登录你所有的服务，也能接 Android 生态，因为 Android 是开放的。他说他不在这两家公司工作，所以可以直说。

为什么要本地和私有

第一是可控。你信任免费的云邮箱，把税务和私事都放进去，是因为它的心智模型很简单：邮件进来，回复出去，不会背着你做不可预测的事。信任和你是否理解它的行为相关。如果有一天邮箱服务说“对有把握的邮件，我会替你自动回复”，你会想最坏情况是什么，比如给老板回了句难听的话。行动空间一旦足够强大又不可预测，你就会对一个不由你完全控制的服务感到不安。更糟的是公司要变现，可能让 Agent 购物时只买给它回扣的商品。

第二是去中心化。各家生态是互相打架、互不兼容的围墙花园，地图、邮件这类单一功能还行，但一个能在生活里替你做各种事的 Agent，绑在一个生态上合适吗？他认为世界应该把本地个性化 Agent 当作常态。

第三他称为“思想罪”：你有个不好的念头，通常不该因此受罚。一个深度增强你的个人 Agent，你会问它一些你从不会说出口的东西。即使是企业级的云 API 合同，也有法律要求的日志和安全检查，他不想冒被追诉或迫害的风险，所以最私密的增强要放在本地。

技术挑战和开放问题

本地推理有很好的开源项目，比如 vLLM 和 SGLang，都建在 PyTorch 上。他讲了个插曲：有一次他们在 PyTorch 里写了个 bug，团队里好几个人开 Tesla，而 Tesla 用 PyTorch，大家紧张“是不是给自己埋了雷”，结果 bug 没那么严重。目前本地推理仍然慢且有限，花钱买强机器也比不上云服务；用 200 亿参数左右或蒸馏模型在本地挺快，但想跑完整未量化的 R1 就慢得多。他认为这会自己解决，只是你大概跑不了最新最强的模型。

他认为更大的缺口在研究和产品上，留给在场的 AI 工程师：

  • 开放的多模态模型不错但不够好。Computer Use 连付费的闭源模型都经常出错。
  • 让模型帮忙购物，衣服、鞋、家具，它只会给最普通的东西。你说得越具体越不行：要一张橡木腿的红色天鹅绒沙发，它给你一张绿色天鹅绒沙发，腿也不是橡木。他认为模型不擅长从视觉上识别你要什么，主要靠文本匹配。
  • 没有好的“灾难性动作分类器”。Agent 的很多动作可逆或无害，点错一个维基百科链接回退就是；但有些动作是灾难性的，比如让它补货洗衣凝珠，它买了一辆 Tesla。如何让 Agent 在执行前识别这类动作、改为通知用户，有一些研究但不够。无论个人还是云端 Agent，要信任它都得在这上面做得更好。
  • 开源的语音模式还很初级，而个人 Agent 他一定想要语音。

他仍然看好，是因为他观察到按投入的资源算，开放模型的智能积累比闭源快：OpenAI 和 Anthropic 只改进自己的模型，开放模型在全行业协同改进。大家一直不信，直到 Llama 出来，直到 Mistral 出来，直到 Qwen 出来，直到 DeepSeek 出来。他一辈子做开源，认为开源一开始有协调问题，没有足够的关键规模；一旦有了，就会以前所未有的方式胜出，Linux 就是例子。所以他看好开放模型按每美元投入会比闭源模型更好。

最后是几条推荐：朋友 Ross Taylor 的 General Reasoning（gr.inc）。Ross 在 Meta 做过开放科学模型 Galactica，那时 ChatGPT 还没发布，Galactica 发布后受到很多批评，被撤下，他也不再公开做很多事；现在他在做缩小开放模型和闭源模型推理差距的工作，发布了一批开放推理数据。PyTorch 在为本地 Agent 解决他讲的那些技术挑战，正在招既是 AI 工程师又懂系统的人。他还邀请大家参加 4 月 29 日的 LlamaCon。
