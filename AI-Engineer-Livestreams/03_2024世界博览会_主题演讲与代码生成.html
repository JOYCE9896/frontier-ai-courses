02. Simon Willison（独立开发者，Datasette、LLM 作者）：GPT-4 壁垒被打破之后

直播位置 0:32:49–0:51:36

Simon Willison 开场说，这个时段原本属于 OpenAI，他是前一天临时被请来替补的，所以准备材料时用了很多 LLM 辅助。整场讲了五件事：GPT-4 壁垒、这些工具其实很难用、AI 信任危机、提示注入、Slop。

GPT-4 壁垒已经没有了

GPT-4 在 2023 年 3 月发布。他提到人们第一次接触它其实更早：一个月前 Microsoft Bing 偷偷跑着 GPT-4 预览版，试图拆散一位《纽约时报》记者的婚姻，上了头版。之后整整 12 个月，GPT-4 没有对手。他说这让他有点沮丧，因为行业需要健康的竞争。

最近几个月情况变了。他喜欢一张 Karina Nguyen 做的图：横轴是每 Token 价格，纵轴是 MMLU 分数（MMLU 是一个覆盖几十个学科的多选题基准）。那张图是 3 月的，已经过时，于是他把图贴给 GPT-4 的 Code Interpreter，给它新数据，让它照着画了一张新的。新图里有三个簇：

  • 最强的一簇：Gemini 1.5 Pro、GPT-4o、刚发布的 Claude 3.5 Sonnet，他都归为 GPT-4 级，价格也合理。
  • 便宜的一簇：Claude 3 Haiku、Gemini 1.5 Flash，没到 GPT-4 级，但便宜得多，能做很多事。他说做 LLM 应用的人应该关注这几款。
  • GPT-3.5 Turbo：不算便宜，现在看效果很差，“如果你还在用它，赶紧换”。

他接着说 MMLU 测的基本是酒吧问答式的冷知识，他举了题库里的一道题：Ia 型超新星有什么特点。他做的事从来用不到这种知识。AI 工程师真正看的是“Vibes”，而 Vibes 也有排行榜：LMSYS Chatbot Arena，用户给两个匿名模型同一个提示，选更好的那个，用国际象棋那样的 Elo 分排名。前一天的截图里 GPT-4o 仍在榜首，Claude 3.5 Sonnet 紧挨着；往下翻，开放许可的模型出现了：Llama 3 70B 已经进入 GPT-4 级，还有 NVIDIA 的新模型、Cohere 的 Command R+、来自中国的阿里巴巴和 DeepSeek。GPT-3.5 Turbo 排在第 66 位。

Peter Gostev 做过一个 Arena 排名随时间变化的动画。Simon 截了两张动画截图给 Claude 3.5 Sonnet，花了大约 20 分钟，让它做出了一个类似的动画，数据一直到前一天。他的结论是：OpenAI 不再有护城河，四家机构在这个级别竞争；GPT-4 级模型正在变成商品，会越来越快、越来越便宜，Llama 3 70B 能装在硬盘上、在他的 Mac 上运行。

免费用户终于能用到好模型，但工具很难用

他引用 Ethan Mollick 的话：OpenAI 让免费用户用“差的 AI”（GPT-3.5），导致多数人看不出少数用高级系统的人为什么觉得 AI 是大事。而最近几周 GPT-4o 和 Claude 3.5 Sonnet 对消费者基本免费了，很多人会经历一年前我们第一次用 GPT-4 时的震动。

问题是这东西很难用。他问：什么情况下把 PDF 上传给 ChatGPT 是有效的？他用了这么久也答不上来，查了一番：PDF 必须是可搜索的，扫描件不行；短 PDF 会被直接塞进提示，长 PDF 会做某种搜索（不知道是全文检索还是向量）；表格和图表几乎一定处理错，但截图贴进去就很好，因为 GPT 的视觉能力很强；有时它会调用 Code Interpreter，用 fpdf、pdf2image、PyPDF 之类的库。他知道这些，是因为他用 GitHub Actions 定期抓取 Code Interpreter 里可用的包和版本号，OpenAI 自己不公布。他的结论是 ChatGPT 是奖励高级用户的工具，和 Excel 一样，谁都能打开，但想精通要多年经验。

AI 信任危机

Dropbox 在 12 月上线 AI 功能，因为默认勾选，网上一片恐慌，大家认为它在用私人数据训练模型；几个月前 Slack 遇到一模一样的事，起因是服务条款里的几句话和一个默认开启的勾选框。他说两家公司其实都没用客户数据训练模型，只是把部分数据发给 OpenAI，并签了 OpenAI 不拿来训练的协议。这是文案和用户体验设计的问题，但你很难说服一个已经认定你在用他数据训练的人。

他表扬了 Anthropic：Claude 3.5 Sonnet 发布时写明，迄今没有用任何客户或用户提交的数据训练生成模型。他原以为 OpenAI 有 ChatGPT 用户数据这个不可能追上的优势，结果最好的模型不需要这些数据。不过他也说，这些公司都犯过“原罪”：用未经授权抓取的整个网络训练。所以你说“我们不用你的数据训练”，对方会回“你们不是已经抓了我网站上的东西吗”，而这是事实。

提示注入：Markdown 图片外泄漏洞

提示注入（Prompt Injection）指攻击者把指令藏进模型会读到的内容里，让模型执行这些指令。他说如果你还不知道这个词，“你就是问题的一部分”，所以他不定义，只举一个例子：Markdown 图片外泄（exfiltration）漏洞。条件是聊天机器人能渲染 Markdown 图片，又能访问私密数据。Johann Rehberger 最近在 GitHub Copilot Chat 里发现：在文档里写一段指令，让模型输出一个指向攻击者服务器、URL 参数里带着私密数据的 Markdown 图片链接，图片一渲染，数据就发出去了，图片还可以是隐形的。解决办法就是别这样渲染图片。可这个漏洞先后出现在 ChatGPT、Google Bard、Writer.com、Amazon Q、Google NotebookLM 和 GitHub Copilot Chat，六个很强的团队犯了同一个错。

提示注入有时只是好笑。有人拿他项目的文档做了个 RAG 应用，问“生命的意义是什么”，它回答“亲爱的人类……作为一只机智的沙鼠……”。原因是他的发布说明里有个示例让模型“假装是一只机智的沙鼠”，语义搜索时这段成了最接近的匹配。后来还有人画了“Willison 的沙鼠”同人图。他的总结是：LLM 很好骗，它相信你告诉它的一切，也相信别人告诉它的一切。

Slop 与问责

Slop 这个词正在被主流接受。他的定义是：既没人要、也没人审过的 AI 生成内容。你向 Claude 要信息不算 slop；你用 LLM 帮忙写、但自己核实过再发表，也不算。把提示丢进模型、出来什么就发什么，才是 slop。他在 The Guardian 的报道里被引用过：他喜欢这个词，因为它像“spam”，有了名字之后大家才明白发垃圾营销信息是坏行为。他说核心是问责：人发布内容时押上了自己的声誉，ChatGPT 做不到这一点。英语是第二语言的人用模型润色没问题，前提是自己审过。

结尾他说，GPT-4 级模型现在人人可用（个别国家除外），在场的人是最有资格做两件事的人：先摸清怎样负责任地使用这些工具，什么好用、什么有害；然后帮其他人跟上。

03. Stephen Hood、Justine Tunney（Mozilla）：llamafile 与 CPU 推理加速

直播位置 0:52:25–1:09:29

llamafile 是什么（Stephen Hood）

Stephen Hood 负责 Mozilla 的开源 AI，Justine Tunney 是 llamafile 的主开发者。llamafile 是 Mozilla 的开源项目，目标是让更多人用得上 AI。它最初的“魔术”是 Justine 想出来的：把模型权重变成程序。一个 llamafile 是单个可执行文件，不用安装，几乎能在所有操作系统、CPU 架构和 GPU 架构上运行，而且是同一个文件，不是 Windows、Linux、Mac 各一份。完全本地运行，不联网，没有监控和统计，“拿剪刀剪断网线也能用”。Hugging Face 已经把 llamafile 作为文件类型支持，可以按它筛选；Mozilla 发布了一批现成的 llamafile，一条命令也能自己做一个。

这次演讲的主题是 CPU 推理速度。他先向 NVIDIA 的 Jensen 开了个玩笑，然后说整个行业过度依赖 GPU：贵、难买、耗电；而全世界有海量便宜好用的 CPU，不该在 AI 时代被扔掉。llamafile 建立在 llama.cpp 之上（llama.cpp 是一个用 C/C++ 写的本地推理项目），他们的性能改进也贡献回 llama.cpp，很多已被合并。他们的数据是：根据 CPU、模型和权重格式不同，llamafile 比原来快 30% 到 500%，而且远没有到头。

为什么是 Mozilla？他问在场有多少人用过 Netscape Navigator，很多人举手。他说大家记得 90 年代 Web 差点被一家公司、一个产品控制，现在 AI 可能重演，几家大科技公司有机会控制机器智能的未来，这对公平、隐私、安全和用户的自主权都不好。Mozilla 的答案一直是开源，所以要让 AI 有可行的开源替代。

可移植性与 tinyBLAS（Justine Tunney）

Justine 先讲跨平台：她的 Cosmopolitan 项目让一个文件能在六种操作系统上运行，技巧是把一个 Unix 第六版的 shell 脚本放进 Windows 可执行文件（PE）的 MS-DOS 头里，于是同一个文件能在 Mac、Windows、BSD、Linux 上跑。GPU 的问题是分发：很多项目要附带 500MB 的 cuBLAS 二进制，她问“如果软件大部分时间都花在一个专有二进制块里，还能叫开源吗”。他们的办法是发布一个叫 tinyBLAS 的库，让 LLM 在 Windows 等平台上只需要显卡驱动、不依赖 SDK 就能用 GPU。

矩阵乘法：展开外层循环

LLM 大部分时间在做矩阵乘法。为了让提示处理（prompt processing，即模型读入输入的阶段）更快，她用了一个所有程序员都能用的简单技巧：展开外层循环。不要展开内层循环（她拿 Gentoo 社区的 funroll-loops 开玩笑），编译器自己会做；展开外层循环后，矩阵乘法能“像花一样展开”，专心做浮点运算，接近 BLAS 内核的效果，大部分收益就来自这里。BLAS 是一套标准的线性代数运算库接口。

效果覆盖从 Raspberry Pi 到大型工作站。用 Intel 游戏电脑的人会看到更好的 Token 生成速度；Alder Lake 上提示处理快了约 4 倍；Threadripper 收益最大，因为 AVX-512（一种一次处理 512 位数据的 CPU 向量指令集）第一次普及到消费级，“几乎像 GPU”。她希望大家把 llamafile 看成“处理文字的机器”，她自己常用它做摘要。

把 CPU 当 GPU 用

她说 NVIDIA 成功的一部分原因是 CUDA 框架改变了开发者写程序的方式。她学 CUDA 时发现最重要的函数之一是 syncthreads，并在 CPU 上用大约 10 行代码实现了它。用 lockstep（锁步）编程模型，把 CPU 当 GPU 来用，就能得到很好的性能。演示是对一篇 Dijkstra 的文章（字幕作 dexra）做摘要，左边旧版本还在慢慢读，右边新版本已经开始输出摘要。

社区贡献与大内存

量化（quantization，用更少位数存储权重以减小体积、加快速度）格式 K-quants 的发明者 Iwan Kawrakow 也参与了 llamafile，把这些格式在 x86 和 ARM 上提速 2 到 4 倍。有用户反馈在一颗 350 美元的 CPU 上跑起了 Mixtral 8x22B。她说性能不是最终目的，智能才是：CPU 的内存便宜，她花一块显卡的钱给工作站装了 512GB 内存，能跑所有新出的前沿开放模型，只是要多等一会儿。

Mozilla Builders

Stephen 回来宣布 Mozilla Builders 计划：赞助或共同开发有影响力的开源 AI 项目，llamafile 是第一个。当天宣布第二个：Alex Garcia 的 sqlite-vec，给 SQLite 加向量搜索。他设想在 Raspberry Pi 5 上，本地开放 LLM 离线连着你的私人数据做 RAG。他们还启动了 Mozilla Builders Accelerator，给推动本地 AI（在用户设备上运行的 AI 应用）的开源项目提供 10 万美元非稀释资金，不一定要成立公司才能申请，网址是 future.mozilla.org/builders。

04. Jamie Turner（Convex）：我们无意中做成了一个 AI 平台

直播位置 1:09:29–1:15:58

Jamie Turner 是 Convex 的 CEO。原题叫“确定性工作流与 AI”，他说真正想用的题目是“我们无意中做成了一个 AI 平台，接下来怎么办”。Convex 的使命是取代传统后端工程：把东西粘在一起、给各种系统做配置、反复转换数据格式，很多团队一半时间耗在这些上，用户并不受益。他们想用一个像 Firebase、Parse 那样贴近应用的高层函数式接口替代这些。

怎么做一个邮件机器人

  • 选一个可编程邮件服务，他用 Postmark：配几条 DNS 记录，把收件指向 Postmark，Postmark 会向你的应用发 HTTP 请求，邮件数据是 JSON。他用 FastAPI 接收。
  • 用 Celery 这类后台任务做生成，因为生成需要时间。邮件是异步的，用户不期待秒回，所以适合更偏 Agent 的流程，也可以用批处理（batch）省钱，甚至加人工审核。回复属于事务性邮件，送达率比群发邮件高。
  • 系统消息里告诉模型这是一段邮件对话，让它回纯文本；需要 HTML 格式时再单独跑一次生成。用户消息里用 JSON 传入邮件信息，一定要带上主题，很多用户把关键内容甚至整封信写在主题里。
  • 线程：回复时保持主题不变，并设置 References 头指向原始 Message-ID，Gmail 等客户端会把它们归到同一线程。
  • 多轮对话用 mailbox hash：邮箱地址的加号后面放一个唯一 ID，收到邮件时检查有没有，没有就是新对话，有就取出历史消息。
  • 最快的原型方式是 OpenAI Assistants API，把它给的 thread ID 当 mailbox hash，还能在它的界面里改系统提示快速迭代。他觉得这不适合大规模生产，但适合快速拿到用户反馈。

13. Avthar Sewrathan（Timescale，闪电演讲）：pgvectorscale，让 Postgres 撑得住向量负载

直播位置 2:06:04–2:10:54 · 预录视频

Avthar 是 Timescale（一家 Postgres 云数据库公司）的 AI 产品负责人。他说 Postgres 是 2023 年 Stack Overflow 开发者调查里最受欢迎的数据库，靠 pgvector 扩展（在 Postgres 里存储和搜索向量）成了 RAG 应用最常用的向量数据库之一。向量数据库是专门存储 Embedding 并按相似度查找的数据库。一直有人质疑：专用向量数据库有专门的数据结构和算法，性能更好。他的回答是 Postgres 可以扩展，答案是 pgvectorscale。

pgvectorscale 是开源的 Postgres 扩展，用 PostgreSQL 许可证，建立在 pgvector 的数据类型和距离函数之上，和 pgvector 互补。他们做它有三个原因：让 Postgres 更适合 AI；挑战“Postgres 做向量不行”的看法；让开发者继续用 pgvector 而没有性能瓶颈。基准测试：5,000 万条 768 维 Embedding，对比 Pinecone。结果是 P95 延迟（95% 的请求都快于这个值）比 Pinecone 的存储优化索引低 28 倍，比性能优化索引低 1.4 倍；自托管的月成本是对方的 25%（字幕原话是“at 75% the monthly cost”，意思应为便宜 75%）。

两项技术：

  • StreamingDiskANN 索引：受 Microsoft 十亿级向量搜索研究（DiskANN）启发，由 Timescale 研究者改进。它把部分索引放在磁盘上，克服 HNSW（分层可导航小世界图，一种常见的全内存近似最近邻索引）必须全部放内存的限制。SSD 比内存便宜得多，所以规模越大越省钱。
  • Statistical Binary Quantization（SBQ）：Timescale 研究者提出的量化方法，在标准二值量化的基础上提高精度，用来压缩向量存储空间。

GitHub Next 是什么

Rahul Pandita 是 GitHub Next 的研究员。GitHub Next 大约 20 人，是资深开发者、研究者和工具制作者，独立于常规产品线，直接向 CEO 汇报，任务是探索软件工程的未来，再把经验交给产品团队。他借用 Andrew Ng 的“AI 是新电力”：电气化之前，工厂中央是一台巨大的蒸汽机，通过主轴、副轴和皮带带动各个工位，整个厂房围着发动机设计，是人在迁就技术。1880 年代出现电动机，小型化后效率不降，可以重新设计工厂；但直到 1920 年代才成为主流，中间 40 年都在探索和试验。

GitHub Next 的流程：先做可运行原型，在团队内部重度使用（dogfooding）；挺过去再到公司内部用；再作为技术预览给早期用户；还活着才可能成为产品，任何阶段都可以砍掉。Copilot 就是从 Next 实验开始的，之后还有 Copilot for CLI、Copilot Voice、GitHub Blocks、SpecLang 等，有的成了产品，有的并入现有产品，相当一部分被搁置了。

Next Edit Suggestions

Copilot 的 ghost text（幽灵文本，编辑器里光标后面灰色的补全建议）擅长写新代码，可我们大部分时间在改旧代码，要在多处增删改。Next Edit Suggestions 不只在光标处给建议，还提示程序里还有哪里需要改。演示里他给一个 Python 函数调用加了参数，它提示更新函数定义；改完定义，提示补上参数；再提示文档字符串和代码不一致并更新；再加一个参数，过程重复。他们还在研究：ghost text 是否是合适的呈现方式；下一处要改的地方不在当前视野、甚至在没打开的文件里怎么办；以及专门为此微调模型。预计几个月内作为独立技术预览或并入某个 Next 产品出现在 IDE 里。

Copilot Workspace：从代码补全到任务补全

他说软件开发有一个内循环（inner loop）：先弄清任务是什么；再弄清现状（框架、语言、已有代码），这形成规格（specification）；再决定最终状态和要改哪些文件，这形成计划（plan）；最后实现。他们希望 AI 在每一步都帮上忙。Copilot Workspace 来自几个并行的探索：SpecLang（用自然语言当程序的功能规格），以及把运行时信息放进提示来改进补全。用户访谈得出几点：最难的是开始一个任务；不信任 AI 的输出；希望保留解决问题的部分，让 AI 当思考伙伴；开发者要掌控。于是 Workspace 提供一键生成方案、内置运行时用于验证、随时可以修改的迭代环境，以及可以作为 PR 或共享工作区分享给同事。

演示用的是 GitHub 发布的 Monaspace 等宽字体网站，它的语法高亮演示区缺 Rust 示例。他从一个“给字体 playground 加 Rust 示例”的 issue 点进 Workspace。为了控制时间，他用了缓存结果，但说真实情况是几分钟，不是几小时。Workspace 先写出当前规格（网站有没有 Rust 包：没有）和目标规格（会有对应的语法高亮包，package.json 会更新），然后生成计划，列出要改的三个文件，再实现。用户随时可以在计划里加“把 Rust 加进语言映射”“加代码文档”等，也可以用聊天修改具体位置。验证时他在集成终端里用自然语言输入“安装并运行这个仓库”，第一次给的命令不对，他手动改后运行，代码能编译，实时预览里出现了 Rust 示例。用自然语言写终端命令，是为了在手机上用 Workspace 时不用敲符号。他说 Next 还在探索 AI 时代开发者怎么学习、大部分代码由 AI 写之后代码会怎样变化，希望不要像电气化那样等 40 年。

15. Kevin Hou（Codeium）：Embedding 正在拖住 AI Agent

直播位置 2:50:03–3:09:22

Brittany 介绍说，Codeium 前身是 Exafunction，是近一年半 AI 领域最惊人的转型故事之一，在 Stack Overflow 调查里被开发者评为满意度最高的代码助手，上个月 VS Code 下载量破百万。Kevin Hou 是 Codeium 产品工程负责人。他说 Codeium 下载超过 150 万次，免费提供不限量的自动补全、聊天和搜索，支持 70 种语言、40 种 IDE，受 Fortune 500 企业信任。用户选择它的原因，他的回答是上下文感知（context awareness）。

三种获取上下文的办法

他用 RAG 举例：在一个中等规模的代码库里做 React 联系表单，ChatGPT 给的通用代码不够用，你需要的是符合自家设计系统组件（按钮、输入框）、仿照库里已有表单、遵守样式规范（比如 Tailwind）、参考内外部文档的代码。问题是怎样收集和排序这些东西，又快又准。

  • 长上下文（Long Context）：把更多内容塞进提示，代价是延迟和费用。他的数据是 Gemini 读入 32.5 万 Token 要 36 秒；一个中小型仓库轻松超过 100 万 Token（约 10 万行代码），多数企业有超过 10 亿 Token 的代码，不可能全塞进去。
  • 微调（Fine-tuning）：调整模型权重去贴合客户数据。需要持续更新，计算昂贵，每个客户一个模型，对多数应用成本过高。
  • Embedding：把对象（函数、文档块）转成固定维度的数值向量，再按向量距离搜索。成熟、便宜，但难以同时推理多个条目，维度空间也低。

基准测的是错的东西

他展示了一个主流 Embedding 基准，历年各家模型的分数挤在正负 5 分以内，像是碰到天花板。Codeium 认为原因在于没法把所有可能问题的维度压进 Embedding 的维度空间。而且这类基准偏向“大海捞针”（needle in a haystack），只找一根针；写代码需要很多根针。于是他们用 Recall@50：真实相关集合中有多少比例出现在检索结果前 50 条里。为了贴近真实使用，他们自己构建数据集：从 PR 里拆出 commit，把 commit 信息和被修改的文件对应起来，得到“一段英文描述 → 一组相关文件”的映射。他称之为产品主导的基准（product-led benchmarks）。公开模型在这个基准上表现下降，既不擅长推理代码，也不擅长理解真实 commit 里的英文。

M-Query：用 LLM 逐条判断相关性

他们的答案是投入更多算力，而且不能让成本失控。Codeium 是垂直整合的：自己训练模型；自己做到硬件层的基础设施（Exafunction 原来做的就是 ML 基础设施）；以产品为导向，看真实用户结果而不是本地基准。M-Query 的做法是：对代码库里的 N 个条目，并行调用 LLM 逐条推理是否相关，相当于让 ChatGPT 对每个条目回答是或否，不看向量。他说这给出最高质量的判断，再结合当前打开的文件、相邻目录、最近的 commit、正在处理的工单，选出前 N 个文档。因为不用外部 API，他们的计算成本是竞争对手的百分之一，所以用户能得到 100 倍的算力。M-Query 并行运行上千个 LLM，代码在几秒内开始流式输出。

他们把 M-Query 推给一小部分用户（以百万下载计，小比例也是很多人），结果是聊天的点赞变多、补全接受率上升、替用户写的代码变多。演示 GIF 里，他询问 alert dialog 的用法，系统从仓库里找出了他改过的一个 shadcn 组件源码。未来这套上下文引擎还会用于生成文档、commit 信息、代码审查、代码扫描，以及把 Figma 画板转成用自家组件写的 UI。他们的迭代循环是：从产品数据和评测出发，用大量算力服务用户，连夜推给用户，看点赞点踩，再回到起点。

自动驾驶的类比

他以前在自动驾驶行业工作。2015 年 TechCrunch 预言那是自动驾驶之年，事后看并没有实现：当时在做传感器融合、降低轮询频率、跑车外模型，都是用启发式规则弥补算力不足。如今车上算力多了 100 倍，可以在旧金山坐 Waymo，2024 年 TechCrunch 又问今年会不会是自动驾驶之年；性能提升来自更大的模型和更多数据。他说基于 Embedding 的检索是一种启发式方法，应该为 AI 优先的产品做规划，直接把大模型用在问题上。

16. Michael Truell、Sualeh Asif（Cursor）：AI 时代的编程长什么样

直播位置 3:10:10–3:28:40 · 含问答

Brittany 介绍 Michael Truell 时提到，他在 Two Sigma 实习时创办了 AI 编程挑战赛 Halite，至今仍在公司内部延续；Cursor 的用户包括 Shopify、Samsung、OpenAI、Ramp、Replicate。Michael 和联合创始人 Sualeh Asif 一起上台。

他们想解决的问题

从机器码开始，人类花了几十年发明高级语言、语法高亮、代码导航、lint 等工具，开发效率大幅提升。他们认为未来 5 到 10 年，类似量级的提升会在更短时间里发生好几次，他们想知道 AI 时代的“高级语言”和配套工具是什么。他把现有看法分两类：一类是 Agent 路线，认为编程作为职业会消失，人人通过 PRD（产品需求文档）或聊天生成代码库；另一类是给现有编辑器做插件，在边缘改进 ghost text。Cursor 的看法是：5 年后编程仍是职业，程序员仍然收入很高，仍是技术活，但会大变，需要一个全新的软件工程工具，而不是插件。重点是尽量提高工具能承担的工作量，同时让程序员坐在驾驶座上。

Copilot++ 与 Command K

Cursor 是为 AI 编程打造的代码编辑器，目标是成为专业程序员用 AI 的最佳工具，目前集中在写代码和问答。两个代表功能：

  • Copilot++：预测程序员的下一步。程序员不总是在光标后打字，有时跳到别处，有时删行、在多处插入，他们训练模型预测下一处编辑和下一个跳转位置。Sualeh 补充：最初的愿景第一句话就是“Copilot 应该做你的下一个编辑”，但几个月里原型要么用删除线、要么老是挪动光标，很烦人，模型也不够准。去年 10 到 11 月有了突破：学会利用程序员的编辑轨迹（从一个文件到另一个文件）和 commit 历史里一连串连贯的 diff 来训练模型，并设计了并排显示编辑的界面，易于解析，打字时也不打扰。
  • Command K：从指令到代码。选中一段代码，说要怎么改，再和 AI 来回迭代。难点是既要低摩擦（敲几个字就行），又要从整个仓库和最近的文件里拉上下文避免出错。

Sualeh 说他们每隔几周就有模型或上下文更新，六个月前用过的人值得再试一次。

两个未来方向

  • 让编程更像读写伪代码。写的一侧已经发生：用户在编辑器里敲的东西越来越简略，被 diff 式补全展开成代码，或写成高层指令由 Command K 变成改动。读的一侧他们在试：有时能否用形式严谨换简洁，给程序员一个滑块控制看到的抽象层级，看类似伪代码的东西，用它导航，也直接改它，再由 AI 改到底层源码。这比站远了写一份和代码脱节的 PRD 更能保留控制。
  • 让 AI 在后台做受约束的任务。他认为端到端自动化 PR 对专业程序员来说还需要技术进步。在此之前的用法是收窄范围：比如你写好方法或类的接口，让 AI 去实现，给它 5 分钟的延迟预算（在环内协作时只能等 10 到 15 秒）。他说这两个方向的内部实验都很有希望。

背后的技术

  • 下一步动作预测模型：先试现成模型，不够准、贵、慢；于是用小规模精选数据集做参数高效微调（PEFT，只训练一小部分参数的微调方法），再进一步让开源模型擅长这个目标，现在有很小但很强的下一步编辑预测模型。
  • 推理优化：重写代码时大量时间浪费在没变的部分上，推理环境里可以跳过这些不变的片段。
  • Embedding 文件同步：多数工具打开大仓库建 Embedding 很慢，像 LLVM 要上传好几个小时。他们做了高性能的同步引擎，一般几分钟同步一千个文件，像 Instacart 那样有几十万文件的也只要几十分钟；编辑后 Embedding 很快更新，上下文基本是实时的。
  • 缓存技巧，以及利用跳转到定义（go to definition）等语言语义链接来构建上下文。
  • 编辑器本身的性能：他们在远程性能分析上下了功夫，要让发给几十万人的编辑器跑得快。

Michael 最后说，他们相信 5 年内可以做出一个工具，自动化今天软件工程的几乎全部内容，让单个工程师造出比今天整个团队更复杂的系统。招聘邮箱是 hiring@anysphere.inc（Cursor 的母公司 Anysphere）。

问答

  • 有什么进阶用法？Michael 说很多功能藏得深：聊天里模型常输出带省略号的简写代码块，他们有专门的模型把这些代码块应用到代码库里；很多人还不知道 Command K，行内编辑比在聊天和代码之间来回切换顺手；终端里出现堆栈跟踪时有专门的调试循环；遇到棘手的 lint 错误，悬停可以找到修复入口。目前最有用的三个功能是 Copilot++、Command K 写代码、聊天问答。
  • 有没有个性化模型？Michael 说没有为每个用户改权重，靠的是上下文构建和模型的上下文学习能力：比如重构到一半时，模型从你最近改的 200 行里挑出最能说明意图的 15 行。Sualeh 说他们感兴趣的两个问题是：能否在你提问时在后台跑一个 Agent 循环为你构建上下文；能否让模型直接学会你的代码库，因为仓库很大时检索会变得不准。

17. Quinn Slack（Sourcegraph）：为什么大多数开发者还不用代码 AI

直播位置 5:13:08–5:31:44 · Brittany Walker 的下午场开场在 5:12:20

下午场仍由 Brittany Walker 主持，讲者是 Quinn Slack、Morgante Pell 和 Gunjan Patel。她介绍说 Quinn 2013 年起做 Sourcegraph，之前联合创办了 Blend，还是 Bleacher Report 的第一位员工。Quinn 的题目原文是“the AI emperor has no DAUs”（AI 皇帝没有日活）。DAU 是日活跃用户数。他说自己仍天天写代码，当天上午合并了四个 PR。三个论点：大多数开发者不用代码 AI，他想吓一吓大家；Sourcegraph 犯过的错；做 Cody 的经验。

真实使用率有多低

  • GitHub 的调查说 92% 的开发者在工作中用代码 AI 工具，但样本是 500 名美国开发者，对“使用”的定义很宽。另一张信息图说 70% 的开发者看到了好处，看到好处不等于在用。
  • Microsoft 2024 年 1 月报告 GitHub Copilot 有 130 万付费订阅。付费不等于在用，而且和全世界写代码的人比也不多。GitHub 发布的一项研究细则里写，某时间段内有 93.5 万开发者“收到过一次建议”，没说接受，而且是年活跃用户，月活和日活肯定更低。
  • 全球专业开发者约 2,600 万（他说这是 Google 各种统计的大致数，可能低估），广义上碰代码的人他估计有 1 亿到 1.5 亿。他的最佳估计是约 5% 的专业开发者在用代码 AI，20 人的屋子里 19 个不用。
  • 用的人里绝大多数只用自动补全（ghost text），写整个文件、回答问题、修 bug 这些能力几乎没人用。他说“我们这屋子人都是怪人”。

Cody 内部统计的不用原因，按频率排：没理由，就是还没用（有开发者甚至没听说过 ChatGPT）；不完美，试过一次给了错误答案；觉得不需要、帮助不大；公司没采购、太贵；安全和隐私顾虑，这一条已经少多了，他开玩笑说用的人多到如果违法大家就“相互确保毁灭”了。

钱从哪里来

他画了一个金字塔：最上面是 OpenAI、Anthropic 这样的基础模型公司，下面是 AI 基础设施公司，再下面是应用。尝鲜式的使用会带来尝鲜式的收入，制造“这东西很火”的感觉；真正的软件收入来自企业的持续使用，比如 JP Morgan 第一年付 100 万美元、第二年续约 200 万。他说所有人工资里的钱最终都来自这里，而这样的收入现在很少。他根据内部信息和 GitHub 在本次大会公开的信息估计，代码 AI 的年度经常性收入（ARR）总共约 3 亿美元。Sourcegraph 花在 AI 推理上的钱不到收入的 10%，按这个比例只有约 3,000 万美元流回模型和基础设施公司。Salesforce 年收入 360 亿美元，代码 AI 全行业只是它的 1/120。他说要么使用量大幅增长，要么悲观派说对了，这是一个会破的泡沫；他每天都用代码 AI，认为它是真的，只是太早。

Sourcegraph 的教训

Sourcegraph 做了 10 年代码搜索，发现手上的全公司代码是做代码 AI 的好上下文，于是做了 Cody：补全、行内编辑、生成单元测试、聊天，聊天最能发挥上下文优势。客户包括美国最大五家银行中的四家和多数 FAANG 公司，他说按收入 Cody 排第二，仅次于 GitHub Copilot。

  • 炒作会骗所有人，包括你和客户。如果做产品的团队自己不每天用，产品就没希望。
  • 客户不知道自己要什么。一年里每个客户都说要微调模型，销售天天催，竞品都把它列成“即将推出”；其实客户要的只是好用，这些词是从会议上听来的。如果不用“AI”这个词就说不清产品为什么好，大概活不下去。
  • 一个存在性问题：如果产品让开发者效率提高 20% 到 30%，为什么不直接买一家软件外包公司，自己把价值赚回来？他说一年前就该这样做，现在正在考虑；如果你没信心拿几百万美元押这件事，说明产品还没准备好。
  • 推特上的热度不等于 DAU，不必为此沮丧。

功能四象限与“先手动、后魔法”

他用一个四象限看功能：横轴是使用频率，纵轴是验证结果对不对有多容易。自动补全落在最好的右上角，每次按键都触发，一百毫秒就能看出对不对，是“百年一遇”的功能，代码 AI 的第一个功能恰好就在那里，让大家被惯坏了。聊天用得少、长回答难验证；行内编辑类似；Agent 是未来，但还没到，他问现场上周有谁让代码 Agent 合并过 PR，只有少数人举手。他们在找下一个像补全那样的形态，对 Next Edit、Copilot++ 这类思路他持怀疑态度；他提到 Sourcegraph 的 Steve Yegge 写的“聊天导向编程”（CHOP）：很多开发者整天开着一个持续的聊天会话写代码，有意思的是用这种方式的多是 Z 世代和 50 岁的老程序员。

18. Morgante Pell（Grit）：大规模代码生成与维护，CPU 依然重要

直播位置 5:32:32–5:51:44

Brittany 介绍说 Grit 在 3 月开源了 GritQL，采用很快。Morgante Pell 是 Grit 创始人兼 CEO，之前在 Google Cloud 做了五年 DevOps 层的开发者工具（Kubernetes 编排、Kustomize、Terraform 模板）。他说 Grit 可能是世界上合并 PR 最多的 AI 公司，原因是任务收得很窄，并在模型层之上做了大量工作。

为什么做 Grit

在 Google Cloud 时，很少有客户要新应用，90% 的客户说的是“我有一个年收入 1 亿美元的业务系统，怎么跑在 Kubernetes 上”。推特上的演示总是一句提示生成一个新应用，可开发者的日常是改庞大的老应用。他把 AI 开发工具分三类：IDE 助手，产品市场契合度最高；降低门槛（lower the floor）的 Agent，让产品经理等非技术人员也能做应用，他对这条路持怀疑态度，因为好软件需要工程师受过的那种思考训练；Grit 选择提高上限（raise the ceiling），让最顶尖的 1% 工程师（比如首席工程师）同时出现在十个地方。这也绕开了“95% 开发者不用 AI”的问题：他们的客户里 95% 的工程师不碰 Grit，团队 100 人里只有一个深度使用，靠 Agent 生成几百个 PR。

他说 IDE 是手术刀，编辑单行代码很好用，但不适合同时改几百个仓库、几千个文件，Grit 想做代码的推土机。他们的客户看到团队产出的代码多了 20% 到 30%，当使用 AI 的人从 5% 变成 50%，世界上会有多得多的代码需要管理。

案例：迁移到 OpenTelemetry

一个有几千个仓库、几千名开发者的客户想把日志改成 OpenTelemetry（一套开源的可观测性标准，统一采集日志、指标和链路追踪）。传统做法要协调几百个团队，教育、改代码、换日志库，是人和流程的问题，通常由项目经理拿一张巨大的 Excel 表推进，他说 Grit 的真正竞争对手是 Excel。这类改动要几万个开发者工时，很多公司干脆不做，所以还有几百万行 COBOL。用 Grit，一个工程师指挥 AI Agent，不到 100 个开发者工时加几千个计算小时；这个推迟了多年的项目一周完成，开了约一千个 PR，迭代后合并。

三步：规划、执行、提交审查

  • 规划：索引整个代码库，既做语义索引（Embedding，理解每个文件的意图），也做传统静态分析索引（代码结构、导入关系、依赖图）。
  • 执行：LLM 把改动分派给子 Agent，每个子 Agent 改一个文件，用 GritQL 和语言模型生成的 diff。GritQL 是他们自研的查询引擎，能索引数百万行代码，找到要改的位置。
  • 提交审查：首席工程师主导并审查 PR；各团队开发者只是看到自己仓库里来了一个 PR，可能留一行评论让 Grit 学习，基本不打开 Grit 界面。

找代码：GritQL 把静态分析和 AI 结合

目标是找出所有错误日志。朴素做法是把代码切块放进 RAG，他说这对这个问题完全不行：会找到很多看起来像日志的无关代码，LLM 分不清 UI 上给用户看的提示和真正该进 OpenTelemetry 的日志；阈值也不可预测，有时要找 10 处，有时要找 1 万处，开发者自己往往也不知道改动有多大。GritQL 查询可以这样写：先用语法模式匹配所有 logger 函数调用；再用一个“像”的关键字，给出“an error occurred”这类示例，转成语义表示，按余弦相似度超过阈值筛选；最后用内置的依赖图确认它是从 log4j 导入的。

改代码：编译器是 Agent 的一半

他当天用 Claude 3.5 Sonnet 做了个试验：把约 10 万 Token 的上下文放进窗口，包括 Grit VS Code 扩展的代码和 lint 输出，让它写一个把 linter JSON 输出转成 VS Code 诊断信息的函数，所需信息全在上下文里。生成的代码看起来没问题，他自己也看不出错，但放进扩展就坏了。问 Claude 为什么坏，它只是给出无关的猜测，因为它没有依据真实错误。用 TypeScript 编译器 TSC 一跑，就知道 Grit 的 position/range 和 LSP 的 range 类型签名不一样；把这个错误喂回 LLM，它立刻改对，用上了上下文里本来就有的转换函数。

他说“提示、生成、构建、类型检查、根据输出修复”这个循环大概是做好 Agent 的一半。问题是企业代码库编译很慢：一个客户的应用从零构建要 10 分钟，只是类型检查，而一次长提示的推理才 30 秒，10 分钟的构建会毁掉整个 Agent 流程，循环几次就要一天。IDE 里每次按键不用等 10 分钟，是因为有语言服务器（LSP，Language Server Protocol，让编辑器实时获得补全和报错的协议）：预先在内存里建好索引，只重新检查改过的部分。用 TS Server，流程变成 30 秒生成、1 秒检查、30 秒修复。所以 Agent 应该用人类在 IDE 里用的那套语言服务器，CLI 工具往往没有这些优化。

回滚到已知良好状态，并行分叉

现实中 Agent 会遇到修不好的错误，陷入循环，换五种方法，上下文窗口被错误信息污染。他说 Agent 不好用，一半原因是错误层层累积；他们发现连续超过 10 次提示后，PR 成功率急剧下降。对策是保存原始状态，走错了就回到已知良好的检查点（checkpoint）重来。为了不每次重算 10 分钟，他们用 Firecracker（一种轻量虚拟机管理器）给内存状态（包括建好的 TS Server 索引）拍快照，再分叉成 10 个隔离环境，各试一种改法。常见做法是 6 到 10 个 Agent 并行，从同一个已知良好状态出发，完成后用 LLM 评测和启发式指标（代码库里还剩多少错误、多少单元测试通过）评估，选出多数一致的状态（quorum）作为新的良好状态继续分叉。他说这更像一个分布式数据库选主节点。一个 PR 可能做了 30 到 40 次生成，但最终链条里只有 4 次。

编辑格式

40 次编辑、大文件，推理费很贵。最简单的做法是让模型重写整个文件，可以先这样做，但会遇到“偷懒”：Sonnet 会写“函数开头保持不变”这样的注释，不输出代码。原因是输出 Token 更贵（GPT-4 输入输出价格比是 5 比 15，Claude 3.5 Sonnet 是 3 比 15），而且输出上限没有随上下文增长，上下文到了 150 万、200 万 Token，单次输出还是 4,000 Token 左右。其他格式各有问题：unified diff 需要行号，LLM 不擅长算行号，训练数据里 diff 也少；用函数调用做搜索替换，底层是 JSON，代码转义浪费大量 Token。Grit 用的是 GritQL 宽松搜索替换：模型像教程那样给出“把这段换成那段”，可以省略无关细节，GritQL 做模糊匹配找到最相似的代码再替换。

他最后展示了现在的界面，看起来还像 CI；他希望未来像《模拟城市》那样，可以缩放到不同粒度管理整个代码库。

19. Gunjan Patel（Palo Alto Networks）：在 CI 里自我演进的代码

从心流说起

他引用《心流》：技能和挑战难度匹配时人处于心流区。现实中写代码时，遇到难题会焦虑，写单元测试、写文档又无聊。写代码只是开发的一小部分，还有 Kubernetes manifest、Dockerfile、部署、测试。Copilot 能帮你越过技术障碍，他想做的是把无聊的事外包给 CI（持续集成，代码提交后自动跑构建和测试的流程）。他提出“Ghost Pilot”和 Copilot 对比：Copilot（Sourcegraph Cody、GitHub Copilot）服务于即时决策，开发者没耐心，响应要以秒计；代码审查需要深思，要反思答案、看全局上下文、迭代。他借用《思考，快与慢》：Copilot 是快系统，Ghost Pilot 是慢系统。

四步架构

开发者用 IDE 助手写代码，提交 PR 后，CI 里依次做：

  • 改进注释和变量名。他引用前一天一位讲者的话“LLM 是一种文化技术”：LLM 学了世界上各个领域的知识，编程只是其中之一。比如金融公司的变量叫 rev，改成 annual_revenue 后，后续步骤里的模型会调用它在金融领域的知识，可能发现原本发现不了的边界情况。注释容易过时，改进注释是让 LLM 明白代码本来想做什么，“没有人想写 bug”。他的例子把 port 改成 port_number，因为也可能是端口名。
  • 添加并循环运行单元测试。目的是建立行为基线：给定输入，预期输出是什么。只说“给这段代码写单元测试”效果不好。他们先让 LLM 根据注释、README、PRD 推断代码的预期行为；再加入对抗视角，用同一个或另一个模型去找边界情况；再从 Jira 里的历史 bug 获取上下文。CI 不像 IDE 那样急，可以多轮迭代。
  • 结合环境上下文找安全问题。上下文包括云厂商、服务、部署位置、内部工具还是面向客户、有没有个人身份信息（PII）、前端还是后端、网络、PRD、Jira 项目、Slack 频道、公司安全策略；还有一部分由 AI 推断，比如语言、是基础设施即代码还是后端代码、历史 bug 指向的重点（SQL 注入、超时、并发）。他还没实现的一点是像 Perplexity Pro 那样缺上下文时反问用户。他提到 Quinn 的 OpenCtx 可能是一个集成点。这一步和静态扫描（SAST）不同，找的是没遵守的安全最佳实践和逻辑问题，并且要排优先级，因为让 AI 找问题，它总会找出点什么。
  • 提出修复建议并重跑单元测试，由人来决定修哪些。

三个虚拟员工辩论

找安全问题时，他模拟了三个 AI 员工：红队工程师（拿到安全策略和被审查代码）、Python 开发者（扮演写代码的人，拿到 PRD）、工程经理（拿到业务背景、Zoom 会议记录、Slack 讨论和 PRD）。他们多轮辩论每个安全问题的风险、是否需要修、工作量多大，最后再自我反思一次，检查是否符合原意，这一步可以换一个模型。他还提了一个好玩的方向：播客里听到的“奥德赛计划”，设想三条路径再回来和过去的自己对话，他说有研究表明这类做法比直接用 LLM 更有效。

他的例子是一个 Kubernetes 的严重级别漏洞，特意选在 GPT-3.5 训练截止日期之后。这是一个逻辑问题，一个 if 语句的位置要挪，SAST 工具查不出来，而他的流程找到了。每个修复建议附上优先级理由、三位虚拟员工讨论的三点摘要和安全策略引用，人审之前先跑单元测试，免得浪费审查者时间。示例 PR 评论是一个硬编码的 API key，给出风险分、工作量分、建议和代码片段。直播到这里被切走。

22. Cheng Lou（Midjourney）：AI 的二阶效应与怎样预测它们

直播位置 7:22:21–7:44:16

Cheng Lou 是 Midjourney 的技术人员。开场的动画是一个矩阵乘法可视化，整个画面是一个片段着色器（fragment shader）在 GPU 上实时绘制，没有导入素材、没有三角网格，只有几百行 GLSL。他说 GPU 本来不是这么用的，可机器学习就是靠这种“误用”复兴的。这场讲的是二阶效应：意外的后果怎样发生，以及如何更可靠地预测。他引用一句科幻作家的话：好的科幻预言汽车，伟大的科幻预言堵车。

涌现行为难以从底层预测

1996 年 Deep Blue 击败 Kasparov，2016 年 AlphaGo 击败李世石（字幕作 2015）。悲观者说国际象棋和围棋完了，可他展示的职业棋手决策质量随时间变化的图，在 AlphaGo 之后明显上升。另一个例子是 Conway 的生命游戏：黑白格子和几条规则，组合出复杂图案，甚至能在生命游戏里实现生命游戏，图灵完备。数量和质量提升一个数量级会产生涌现行为，要理解它得退后一层，用新的规则和启发式去看，这些人工作起来更像生物学家，不像数学家或物理学家。下面是他自己用来预测二阶效应的三种思路。

思路一：谁在学习

国际象棋没死，反而更好了：随时都有免费老师，不用去村里找那位会下棋的人，人人都懂棋，懂棋的观众多了，职业棋就养得起。说到底是你自己想学，机器去健身房你也不会变强。画画也一样：他设想一个“笔触自动补全”的滑块，一端什么都不发生，另一端整幅画替你画好，中间可以调。你画一把椅子，系统看出弧度猜你要维多利亚风格；你用某种蓝，它提示脸上的海水反光因为有沙子应该偏绿一点。学上色的反馈循环本来很长，现在可以即时得到；而讽刺的是，随着时间推移，滑块会被调到最左，你不再用 AI，因为技能已经内化了。音乐里多数乐器是直接操作，按琴键就出声；特雷门琴已经有一点间接操作；他设想用手指操作声谱图，手指不够精细，但 AI 有足够的世界知识帮你“超采样”，可能出现像操纵木偶一样演奏的新乐器。他的结论是：直接操作的用户界面主要是为了自己学习，当点这点那的功能性界面被自动化之后，剩下的是生活方式型的界面，人用它是为了自我实现，于是可能出现更多手工感、小众、古怪的界面。

思路二：拓宽信息带宽

他看 Anthropic 稀疏自编码器研究里的一张聚类可视化，想到 Villeneuve 的电影《降临》：人类学会外星语言后解锁潜能。他的推论是每人一种语言。人类语言是标准化、带宽很窄、有损的接口；AI 基本解决了翻译，那就再进一步，把一种英语翻译成另一种英语。比如吵架时他说“I feel blue”，对某个听者也许该译成“I'm feeling purple”；如果足够快，每句话都能按对方的审美偏好变成动态的 4D 作品，在 AR 里递给对方，信息密度远高于表情符号。也许 50 年后口角几秒就能化解。

iPad 上的例子：笔尖接触屏幕通常是画线，但又被重载成选择、移动、缩放。现实中的信息带宽高得多：用户可能刚说完“这块为什么是红的”再点几下，或者画完一笔说“这个应该放那边”。传统设计要靠当前工具状态、笔下的对象、一秒前的动作这一堆隐式规则来判断，还要撤销误画的笔画。他认为这一笔应该以整个世界为条件来理解，点击和笔画的判断应尽量交给机器学习，人类旁观者一秒就能纠正的误触，机器也该能在本地纠正。

思路三：把某个量推到极端

Smalltalk 是 70 年代的编程环境，面向对象编程的鼻祖，启发了 Objective-C 等语言，核心是消息传递，消息可以发给网络上另一台机器的对象。Alan Kay 说灵感来自细胞，每个对象都是一台完整的计算机；他还说发消息容易，找到接收者难。每个 Smalltalk 对象理论上可以像一个自主的智能 Agent 去网上办事。问题是对象越聪明，消耗的资源越多，你只能有一两位数的数量，于是错过了来自数量和协作的涌现。多层感知机正好相反：节点尽可能笨，权重是学出来的，全连接也就解决了“找接收者”的问题，节点简单就能有几百万个，聚合起来产生新东西。他借此评论当天很多 Agent 的话题：Agent 越多，你越关心整体而不是个体。在另一个现实里，我们派几个 Agent 去读 Wikipedia 带回片段；在这个现实里，我们让几十亿个笨节点读了 Wikipedia，聚合起来放进手机，由一个顶层过程协调。

最后的例子是 Apple TV 的 Mac 应用：点剧集简介的“更多”按钮，弹出的是一个很不像 Apple 的大文本框，甚至能选中文字。原因是它是 Catalyst 应用，直接从 iOS 移植，在 iOS 上这样很自然。他说这可以看成缺少设计和工艺，但他想换个角度：这是缺少“更多的 UI”。如果 UI 多两个数量级会怎样？在设计阶段，用 AI 在 12 列网格里为剧集信息生成成千上万种布局（AI 能理解标题和方框大小、位置之间的语义关系，传统生成算法做不到给每个框贴对标签），再用传统或 AI 的审美评分淘汰差的，设计师在离线阶段慢慢筛选，甚至用 ControlNet 之类的扩散模型生成粗略效果图给老板看。运行时，他不主张让 LLM 现场生成界面（Web 的瓶颈在前端，AGI 也不能让 JavaScript 比 C++ 快），他的做法是用一个快速决策树选出合适的布局。现在 Web 只有媒体查询（media query）按窗口宽度显示或隐藏元素这一条规则；新手引导、高级用户、不同国家、年龄、搜索词都可以对应不同布局。Uber、Facebook 在印度和中国的界面差别很大，但那要上千名工程师。比如用户问“Villeneuve 拍了哪些电影”和“Villeneuve 和谁合作拍了哪些电影”，应该展示不同的精选布局。他估算真正需要的布局在千这个量级，AI 帮忙仍可人工挑选，所以这是一个分类问题，不是自回归或扩散问题。最后一句是“预测未来最好的方法是创造它”。

23. Ishan Anand（Edgio）：Spreadsheets Are All You Need，在 Excel 里给 GPT-2 做“脑外科手术”

直播位置 7:44:16–8:01:12

Ishan Anand 是 Edgio 产品副总裁，穿着手术服上台。他说这是给没有机器学习学位的 AI 工程师的速成课。他用一个 Excel 表完整实现了 GPT-2 small，全是 Excel 函数，不调 API、不用 Python，150 多个工作表、超过 1.24 亿个单元格，对应全部参数。三部分：解剖、做“MRI”看它怎么想、做“脑外科手术”改它的想法。

解剖：前向传播

LLM 被训练来补全句子，比如“Mike is quick. He moves”，人会猜 quickly。计算机擅长算术，所以要把文字题变成数学题：把句子切成子词单位 Token，把每个 Token 映射成一串数字 Embedding；中间的运算换成了多头注意力和多层感知机（MLP，就是神经网络）；最后得到的是下一个 Token 的概率分布，没有唯一的标准答案。表格里提示输入后，大约 30 秒输出 quickly，他说“别在生产环境用”。

  • 分词：他用 reinjury（真词）和 funology（假词）演示。funology 被切成 fun 和 ology，符合词素；reinjury 却被切成 rein 和 jury，因为算法只挑最常见的子词，不符合直觉，机器学习界认为分词是“必要之恶”。
  • Embedding：每个 Token 一行，GPT-2 small 每个 Embedding 有 768 个数，从第 3 列一直到第 770 列。
  • 12 个层（block 0 到 block 11），每层一个工作表。注意力阶段 Token 看周围的 Token 理解语境：he 看向 Mike 找代词的先行词；moves 看向 quick，因为 quick 有多种意思（快速、聪明、指甲下的嫩肉、莎士比亚英语里的“活着的”），看到 moves 才知道说的是物理移动。在一个注意力头的表里，右上角全是 0，因为 Token 只能往前看不能往后看；Mike 100% 看自己，he 有 0.48 的注意力放在 Mike 上。MLP 部分就是 Excel 的 MMULT 矩阵乘法加激活函数。
  • 语言头：把最后一个 Token 的结果做 Layer Norm，乘以反嵌入矩阵得到 logits（每个候选 Token 的原始分数），解释为概率分布。表格用 temperature 0，直接取最大值；他说 temperature 更高时按某种算法采样，并举了 beam search。

MRI：残差流与 Logit Lens

每层里都有加法，即残差连接，模型可以借此让信息绕过注意力或 MLP。所以可以把模型看成一条通信总线，残差流（residual stream）就是每个 Token 位置上的“信息高速公路”车道：注意力在车道之间搬运信息，MLP 在每条车道上推测下一个 Token。Logit Lens 是把语言头插到每一层之间，看模型在那一层“想”的是什么。提示“If today is Tuesday, tomorrow is”，GPT-2 对一周七天都答对。表格显示：block 0 时 Wednesday 出现在 Tuesday 那一列的底部，随后消失；中间层的最高预测是 not、still、just 这类错词；到最后几层出现 tomorrow、forever、Tuesday、Friday，模型知道在说时间和星期，Wednesday 先排第三，最后升到第一并锁定。他引用的研究发现，七天都答对只需要四个组件：第 0 层的 MLP、第 9 层注意力（其实只要一个头）、第 9 层的 MLP 和第 10 层注意力，研究者称之为电路（circuit）。

手术：用稀疏自编码器特征做 Steering

他提到 Anthropic 的 Scaling Monosemanticity 研究和 Golden Gate Claude（一个痴迷金门大桥、有人觉得它以为自己就是金门大桥的 Claude）。原理是用稀疏自编码器（sparse autoencoder，把残差流拆成可解释特征的另一个模型）找出特征，再把某个特征调大或调小注入残差流。Joseph Bloom、Neel Nanda 等人在为 GPT-2 small 等开源模型做 SAE 特征。他取了第 2 层的特征 7650（所有和 Jedi 有关的东西），把它的解码向量乘一个系数，直接加到 block 2 起始处的残差流里。原本“Mike pulls out his”接 phone，打开 Jedi 向量后接的是 lightsaber。他说 Anthropic 的做法略有不同但思路相似，另外还有表示工程（representation engineering，用主成分分析 PCA 推出 steering 向量）和激活 steering（分别跑 Jedi 和 phone，取“Jedi 减 phone”的向量注入）。

他说了解黑箱的好处：更清楚工具的行为和局限；跟得上快速发展的研究；和非技术人员沟通时能消除“魔法”误解。例子是 RWKV（另一种模型架构）的提示模板建议把指令和上下文的顺序反过来，因为它的类注意力机制不能像 Transformer 那样回看，架构一直影响到提示怎么写。表格可以在 spreadsheets-are-all-you-need.ai 下载，他当天还在 Maven 上线了一门逐步讲解的课。

24. Jerry Liu（LlamaIndex）：知识助手的未来与 llama-agents

直播位置 8:01:12–8:18:12

LlamaIndex 联合创始人兼 CEO Jerry Liu 说，企业里最常见的 LLM 用例是文档处理、打标签和抽取，知识搜索和问答（他们的推特过去一年 75% 在讲 RAG），扩展到带对话历史的会话 Agent，以及今年很热的能执行操作的 Agent 工作流。他关心的是知识助手：任何任务进去（简单问题、复杂问题、模糊的研究任务），出来短答案、研究报告或结构化输出。他说去年就讲过 RAG 只是一个 hack。朴素 RAG 的问题：数据处理粗糙（基础解析、按句切块、top-k 检索），10 分钟搭好但上不了生产；不理解复杂、宽泛的查询，没有规划；不能和其他服务交互；无状态、没有记忆。他说只是这样的话 RAG 很无聊，就是套在几十年老检索方法上的搜索。路线分三步。

第一步：数据与检索质量

垃圾进垃圾出。数据处理的主要环节是解析、切块、索引。你首先需要一个好的 PDF 或 PowerPoint 解析器，把复杂文档提取成结构良好的表示；用 PyPDF 处理财报里的表格，会把数字和文字搅在一起，导致幻觉。他说单是好的解析就能提高效果。例子是 Caltrain 周末时刻表：用 LlamaParse 解析成保留空间布局的文本，LLM 能读懂，问某列车次的时间答得对；用 PyPDF 就一堆幻觉。LlamaParse 几个月前开放，有几万用户、处理了几千万页。

第二步：单 Agent 的高级查询流程

他和 Andrew Ng 在 DeepLearning.AI 做过一门课。在基础 RAG 之上可以叠加 Agent 组件，左边是成本和延迟低的简单组件，右边是完整的 Agent 系统，甚至能和其他 Agent 协作。核心组件：函数调用（Function Calling）与工具使用、查询规划（顺序的或 DAG 形式的）、对话记忆。他们提出 Agentic RAG：LLM 除了最后合成答案，还在查询理解和处理阶段大量参与，说到底是 LLM 把各种数据服务当作工具来用。推理循环里最稳定的是基于函数调用的 while 循环或 ReAct（让模型交替“思考”和“调用工具”的提示框架），也有 DAG 规划、树搜索规划的论文。这样能处理跨文档比较、记住用户状态、同时查结构化和非结构化数据。剩下的问题：一个 Agent 解决不了无限多的任务，给它一千个工具会失败，专精的 Agent 更好；Agent 越来越多地和其他 Agent 打交道。

第三步：多 Agent 任务求解与 llama-agents

多 Agent 的好处：每个 Agent 专注一组任务更可靠，能拼起来解决大任务；同一个 Agent 可以多副本并行，更快；每个 Agent 只管 5 到 10 个工具，可以用更弱、更快的模型，省成本和延迟。难点是在放任 Agent 自由协作和加约束之间取舍，以及生产化：现在多数 Agent 是 Jupyter Notebook 里的函数，需要合适的服务架构。

当天他发布了 alpha 版 llama-agents，把每个 Agent 当作微服务：Agent 可以用 LlamaIndex 或其他框架写，部署成独立服务，通过消息队列（message queue）通信，由一个控制平面（control plane）编排，灵感来自 Kubernetes 这类资源调度器。编排可以是显式的（你定义服务间流程），也可以是隐式的（由 LLM 编排器决定把任务交给谁）。演示是一个简单的 RAG 管线拆成服务：查询改写 Agent 接收查询并改写，第二个 Agent 做检索并输出答案，还可以加反思、通用工具服务等，能同时处理多个客户端请求。逻辑本身很简单，重点是展示怎样变成可部署的服务。发布时有十几个教程，路线图公开在 GitHub Discussions，他想听社区对通用通信协议的意见。另外 LlamaCloud 开放 waitlist，面向“有一桶带图表、表格、图片的 PDF”的企业开发者，处理解析、切块、索引。

他查了软件工程的定义（IEEE、Google 开发者文档：软件的设计、实现、测试、文档、生命周期管理），再看真正工程的定义（IEEE 和美国国家工程院都提到应用自然科学、造福人类），发现软件工程的定义里缺了理解自然规律和造福人类这两部分。他的提议是 AI 工程介于两者之间，比典型软件工程师遇到更多现实世界的约束。他提出几类规律供讨论：

他说 AI 工程在 EA（有效利他）和 e/acc（有效加速）之间，既在乎安全又想加速，一个维度不够，要加第二个维度：效用，AI 工程师首先是效用最大化者，看到有什么就想用它造福人类。他的寄语是“少尊重一点边界”：避免自己的教条、他人的懒惰共识和被动反应，多和自己的结论、彼此、现状唱反调。最后一个比喻：AI 工程师看到哥斯拉，想的是把它变成大众捷运。他鼓励大家跨专场、跨圈子、跨学科和模态交流。
