这一场的内容

这条直播录的是 2025 年 6 月在旧金山举办的 AI Engineer World's Fair 最后一天，检索与搜索（Retrieval + Search）分会场一整天的内容。上午四场演讲，讲者来自 LlamaIndex、LanceDB 和 Harvey、Quotient AI 和 Tavily、Voyage AI（已被 MongoDB 收购）。午饭时间同一个房间被创业孵化器 HF0 借去办了一场“下一批 AI 独角兽”路演，十位创始人各讲两三分钟。下午由 Arize AI 的 Dat 主持，11x、Exa 和 Pi Labs 三家各讲一场。

先解释一个贯穿全天的词。检索增强生成 RAG（Retrieval-Augmented Generation）指的是：模型回答之前，先从外部资料里找出相关的几段内容，再把这几段塞进提示词里让模型据此作答。这一天反复出现的话题有三个：复杂文档（PDF、表格、Excel、视频）先要被正确解析成文本，后面的检索才有意义；评测 Eval 比算法本身更花时间，好几位讲者都说团队把大部分精力花在验证上；单纯的语义相似度不够用，真实的检索系统还需要关键词匹配、领域信号、用户行为信号和查询改写。午休和场间等待（约 1:27 到 2:20）在本文中略过；直播开头约 6 分钟没有字幕，第一位讲者的开场部分因此缺失。

01. Jerry Liu（LlamaIndex 联合创始人兼 CEO）：给 Agent 用的文档工具箱，以及 Excel Agent

直播位置 0:11:56–0:23:59（字幕从这里才开始，演讲前半段没有字幕）

文档工具箱和复杂文档

字幕接上时，他正在讲“文档工具箱”的最后一类操作：在抽取出来的结构化数据上做结构化查询，拿到汇总性的结论。他说做这类工具箱最先要面对的是复杂文档。大量人类知识存在复杂 PDF 和其他格式里，里面有嵌入的表格、图表、图片、不规则版式、页眉页脚。这些文件是给人看的，不是给机器读的。文档处理错了，LLM 再强也会失败。

他说 LlamaIndex 是最早意识到 LLM 和视觉语言模型（他称为 LVM）可以用来做文档理解的团队之一。传统做法是为某一类文档手工调一个专用的机器学习模型；LLM 的准确率更通用。最简单的基线是把 PDF 截图丢给 ChatGPT 或 Claude，准确率不算好，但是个起点。他们的做法是把 LLM、LVM 和传统解析技术交错使用，再加上测试时的额外 token，也就是让 Agent 做校验和推理，把准确率往上推。他们的云端文档解析服务适配了 Claude Sonnet 3.5 和 4（字幕不清）、Gemini 2.5 Pro、OpenAI 的 GPT-4.1 等模型，他说在现有解析基准上超过了开源和商业的所有工具。他提到很多人知道 LlamaIndex 是一个 RAG 框架，现在他们还有一个托管平台，提供解析、抽取、建索引等文档操作。

新发布：Excel Agent

当天几小时前他们在博客里宣布了 Excel 能力。他说大量知识工作发生在 Excel、Google Sheets 这类表格里，但 LLM 一直没解决好。他展示的表格不是规整的二维表，行和列中间有很多空隙，RAG 和“转成 CSV”两种办法都不管用。他们做了一个 Excel Agent，能把不规整的表格转成规整的二维格式，并且能在原表和规整后的表上做 Agent 式问答。演示视频里，他们上传一个合成数据集，转成二维表，然后对它提问。

  • 他说最好的基线是让 LLM 带上代码解释器（Code Interpreter）写代码，在他们的私有合成 Excel 数据集上能到 70% 到 75% 的准确率。
  • 他们的 Agent 做到了 95%，超过人手工做同样数据转换的 90% 基线。
  • 原理：先做结构理解，用了一点强化学习 RL，按每份表格的具体格式动态适配，学出这张表的“语义地图”；再把语义地图转成一组专用工具交给 Agent。他说随着 LLM 变强，直接从零写代码会成为越来越强的基线，眼下他们用专用工具帮 Agent 一把。

两类 Agent 架构

他说 Agent 编排从受约束到不受约束是一条光谱。受约束的架构由开发者明确写死控制流程；不受约束的就是 ReAct 循环（让模型在“思考、调用工具、看结果”之间反复循环）、函数调用、CodeAct 之类，给一组工具让它自己跑，Deep Research 也属于这一类。他们观察到两类主要的用户体验：

  • 助手型：通常是聊天界面，输入是自然语言，架构更不受约束，基本是一个 ReAct 循环，人在环中（Human-in-the-loop）的程度更高，靠人一步步引导 Agent 完成任务。可以看作 RAG 聊天机器人的推广。
  • 自动化型：端到端处理例行的多步骤任务，输入是一批数据，可以后台运行或由人临时触发。架构更受约束，因为要端到端跑就不能跑偏；每一步的人工介入更少，通常最后做一次批量审核，输出结构化结果，对接 API，批准后自动流向下游系统。用例有财务数据规范化、数据手册抽取、发票对账、合同审查。他提到社区里有一个开源的发票对账器（invoice reconciler）。

他总结的模式是：自动化 Agent 常常充当后端，在后台做数据 ETL 和结构化处理；助手 Agent 面向前端。自动化 Agent 把数据处理好，并为助手 Agent 提供合适的工具接口。

真实用例

  • 财务尽调：一家客户（字幕记作 Carl，名字不清）做了一个端到端的杠杆收购 Agent。先用自动化界面吞下大量公开和私有财务数据（Excel、PDF、PPT），经过定制抽取算法和人工审核；数据结构化之后，再给分析师团队一个 Copilot 界面，用来获取洞察和生成报告。
  • 企业搜索：属于助手型。客户（字幕记作 SEMX）为不同数据源定义不同集合，提供面向具体任务的 Agentic RAG 聊天机器人，也就是在 RAG 上加一层推理，拆解用户问题、做研究、再回答。
  • 纯自动化：一家全球电子公司有大量技术数据手册需要处理和审核，过去靠大量人工。端到端的自动化 Agent 把业务规则编码进去：解析文档、抽取信息、对照规则、把结构化数据写进 SQL，中间有人工审核。他说这把技术写作人员几周的工作变成了自动抽取。

最后他说 LlamaIndex 的使命这几年有变化，过去是一个以 RAG 为主的通用框架，现在定位成用 Agentic AI 自动化文档工作流的平台。

02. Chang She（LanceDB 联合创始人兼 CEO）、Calvin Qi（Harvey）：在法律领域扩展企业级 RAG

直播位置 0:25:13–0:41:24 · 英文原题 Scaling Enterprise-grade RAG Systems: Lessons from the Legal Frontier

两位讲者

Chang She 说自己做机器学习和数据科学的数据工具大约 20 年，是 pandas 库的共同作者之一，现在做 LanceDB，处理那些装不进 pandas DataFrame 的数据。Calvin 在 Harvey 带一个团队，处理跨海量复杂法律文档的 RAG 难题。

Harvey 的三种数据规模

Harvey 是卖给律所的法律 AI 助手，帮律师起草、分析文档、走法律工作流。Calvin 说数据处理是其中一大块，分三个量级：

  • Assistant：按需上传，像任何 AI 助手一样，规模在 1 到 50 份文档。
  • Vault：更大的项目上下文，比如律所正在做的一笔大交易，或者一个数据室，把所有合同、诉讼文件、邮件放在一起。
  • 数据语料库：全世界的知识库，比如某个国家的立法、判例法、税法和监管规定。一个语料库可以有几千万份文档，单份文档往往也很长。

挑战：查询有多复杂

挑战包括规模、稀疏与稠密表示的选择（稀疏指关键词式表示，稠密指向量表示）、查询复杂度、领域专业性、数据安全隐私（保密交易、IPO、财务申报）、以及评测。他读了一条“中等复杂度”的真实查询：在欧盟指令 EU 2019/2162 和 CRR 第 129 条下，2022 年 7 月 9 日之前发行的担保债券适用什么监管制度。他拆开讲里面有几层：语义部分；隐含的日期过滤；指向一个专门数据集（欧盟法律和指令）；对具体法规编号的关键词精确匹配；同时问两部法规，属于多部分问题；还有领域缩写（他说当天早上查过，记不清全称了）。系统要能拆解这样的查询，对不同部分用不同技术。

评测上花的时间最多

Calvin 说常有人问怎么评测，他们在这上面花的时间最多，比花在算法和花哨的 Agent 技巧上的时间更多。尤其当工程师本身不懂这个领域时，投资评测开发是做好系统的关键。他说没有万能的评测，他们按“保真度高但贵”到“自动化、迭代快”排成一个范围：

  • 最高保真：请领域专家直接审阅输出，分析并写报告。最贵，质量最高。
  • 中间：专家标注一套评判标准，再用合成或自动方式去评。整理起来贵，运行也有点贵，但更可控。
  • 最快迭代：自动化的量化指标，比如检索的精确率和召回率，以及确定性的检查：是不是从正确的文件夹取的文档、是不是正确的章节、有没有包含正确的关键词。

数据侧，他们接入很多国家的数据集，每个都有复杂的过滤、组织和分类，他们和领域专家合作，再尽可能用专家给出的启发式规则或 LLM 处理来自动分类。性能要求分在线（查询延迟）和离线（摄入、重新摄入、跑各种机器学习实验）。基础设施需求包括可靠可用、平滑扩展（让机器学习和数据团队专注业务逻辑和质量，不用手动调数据库和扩容）、数据隐私和保留策略（有的存储要按客户隔离，有的文档因法律原因只能存一定时间）、遥测，以及同时支持精确匹配、语义匹配、过滤、Agent 式动态导航的查询灵活性。

LanceDB：AI 原生的多模态湖仓

Chang She 接着说，LanceDB 想做的超出向量数据库，他们称之为 AI 原生的多模态湖仓（Lakehouse）。湖仓指把所有数据放在对象存储上，在同一份数据上跑检索、分析、训练和预处理。他说传统湖仓适合大批量离线任务，但不适合在线服务，LanceDB 的分布式架构两种都能做：

  • 直接从云端对象存储大规模服务，计算、内存、存储分离，成本只是一小部分。
  • 一个简单的 API 做复杂检索：组合多个向量列、向量加全文检索、再加重排序（Reranking）。Python 和 TypeScript 都有，用户说用起来像 pandas 或 Polars。
  • 大表支持 GPU 建索引。他说记录是单表三四十亿个向量，两三个小时内建完索引。
  • 他说这是唯一能把图片、视频、音频和向量、文本、表格数据、时间序列放进同一张表的数据库，作为搜索、分析、训练、特征工程的唯一数据源。

这一切的基础是他们从零写的开源 Lance 格式。他说如果用 WebDataset 或 Iceberg/Parquet 存多模态数据，会缺随机访问、不支持大的二进制数据（blob）、模式演进（Schema Evolution）效率低。很多 AI 团队因此把数据的不同部分存在不同地方，花大量精力让它们保持同步。他把 Lance 格式概括为“Parquet 加 Iceberg 加二级索引，面向 AI 数据”：随机访问快，适合搜索和打乱（shuffle）；扫描快，适合分析和训练时加载数据；能存大 blob 和小标量数据的混合。它用 Apache Arrow 作接口，所以能用 Spark、Ray 分布式写入，用 PyTorch 加载训练，用 pandas、Polars 查询。

三条结论

  • 领域难题需要创造性的方案：理解数据结构、用例、显式和隐式的查询模式，和领域专家合作，尽量沉浸进去。
  • 为迭代速度和灵活性而建。新工具、新范式、新的上下文窗口长度不断出现，好的评测集和评测流程是快速迭代的基础。
  • 新的数据基础设施要面对多模态、以向量和嵌入为主、工作负载多样、规模越来越大的现实。

03. Julia Neagu、Deanna Emery（Quotient AI）与 Tavily：怎样评测 AI 搜索

直播位置 0:45:51–1:06:16 · 英文题目大意：Evaluating AI Search: A Practical Framework for Augmented AI Systems

三位讲者：Julia Neagu 是 Quotient AI 的 CEO 兼联合创始人，Deanna Emery 是 Quotient AI 的创始 AI 研究员，第三位来自实时搜索 API 公司 Tavily（主持人介绍时的名字字幕记作 Mar Asher，她自我介绍时字幕把名字吞了）。

问题从哪里来

Julia 说传统监控方式跟不上现代 AI 系统：Agent 在不断变化的环境里运行，根据变化的网页内容、用户交互和复杂工具链实时做决定；而且多种失败会同时发生，幻觉、检索失败、推理错误互相牵连。Quotient 做的是监控线上运行的 AI Agent，他们的“专家评估器”不依赖标准答案、人工反馈或基准，就能识别客观的系统故障。

一年前 Tavily 的创始人兼 CEO 给他们出了一道题：搜索 Agent 面对两个无法提前控制的不确定性，怎么做到生产可用？第一，Tavily 的 Agent 靠搜网页获取上下文，网页不是静态的，传统基准假设标准答案稳定，而实时信息的标准答案本身在移动。第二，用户不按测试用例提问，会问奇怪、格式错乱的问题，还有没说出口的隐含上下文。Tavily 在生产中为 Agent 处理数亿次搜索请求。

Tavily 的两条评测原则和动态数据集

Tavily 的讲者说他们在做“Agent 大规模交互的基础设施层”，给语言模型提供来自全网的实时数据。客户例子：一家合同生命周期管理（CLM）公司做了法律助手，一家体育新闻媒体做了混合 RAG 聊天 Agent 播报比分和新闻，一家信用卡公司用实时搜索定位商户位置来反欺诈。两条原则：网页一直在变，评测方法要跟上；真相常常是主观和依赖上下文的，评测方法要尽量无偏、公平。

静态数据集是好的起点。她介绍了 OpenAI 的 SimpleQA（单一事实答案的短问题，很多 AI 搜索厂商用它自报成绩）和 HotpotQA（需要跨多篇文档推理的多跳问题）。但静态数据集不能检验系统是否跟上快速变化的信息，也处理不了没有唯一答案的问题。于是他们做了一个开源 Agent，专门为基于网页的 RAG 系统生成动态评测集。这个项目由 Tavily 的数据负责人发起，用 LangGraph 搭建，步骤是：

  1. 为目标领域生成宽泛的网页搜索查询，所以可以为任意领域造评测集。
  2. 从多家实时 AI 搜索服务聚合“依据文档”。她说不能只用 Tavily 自己搜、再用这些结果出题、再评自己，所以用多家服务来扩大覆盖、减少偏差。
  3. 生成有证据支撑的问答对，这是最关键的一步。Agent 必须同时生成答案所依据的上下文，可以回查每对问答用了哪些来源、哪些证据，减少幻觉。
  4. 用 LangSmith 追踪实验，查看不同时间点的表现。

下一步计划：支持简单事实题和类 HotpotQA 的多跳题；主动处理偏差，覆盖每个主题的多种视角；加一个协调用的监督节点（Supervisor Node）。她说只测准确率不够，要有整体评测框架，比如来源多样性、来源相关性、幻觉率；还要用不需要标注数据的无监督方法来扩大规模、应对主观性。

实验：六家 AI 搜索服务，静态对比动态

Deanna 讲了一个两部分的实验。第一部分比较六家 AI 搜索服务在静态基准 SimpleQA 和一个约 1000 行的 Tavily 动态基准上的准确率，两个数据集的话题分布大致相同。评分用 SimpleQA 自带的正确性指标，这是一个 LLM 评委（LLM-as-a-judge，用一个模型来给另一个模型的回答打分），把回答和标准答案比，判为正确、错误或未作答。厂商名字做了匿名。

  • SimpleQA 的分数都是厂商自报的，不一定有清楚的计算说明。
  • 动态基准上的正确率明显更低，相对排名也变化很大。图最右边那家在 SimpleQA 上最差，在动态基准上最好。
  • 她展示了 LLM 评委的误判：有些回答文本里明明包含标准答案，却被判为错误；有些被判正确的回答虽然包含正确答案，其余文字里可能有幻觉，评委没管这些。

不需要标准答案的指标

线上和生产环境里大多没有标准答案，AI 搜索尤其如此。第二部分用 Quotient 的三个无参考（Reference-free）指标评动态基准上的回答：

  • 答案完整性：问题的每个部分是否都回答了，分为完全回答、未回答、未知（模型说“我不知道”）。它的排名和动态基准正确率排名很接近，平均分相关系数 0.94。她提醒完整不等于正确。
  • 文档相关性：检索到的文档里有多少比例真正和问题相关。六家里只有三家会返回生成答案所用的检索文档，大多数只给引用链接，她说这在规模化时没什么用，也让调试缺乏透明度。文档相关性和“未知”回答数量强负相关，符合直觉：没有相关依据时模型应该说不知道。
  • 幻觉检测：回答里有没有任何检索文档中都不存在的事实。意外的是幻觉率和文档相关性同向：X 家文档相关性最高，幻觉率也最高。她的解释是 X 家答案完整性高、“未知”最少、在基准上正确率也最高，回答可能更详细、加入了更多推理和解读，于是幻觉的机会也更多。

她说这些指标测的是回答质量的不同维度，常常此消彼长，比如完整性和幻觉之间有取舍。三个指标合起来能帮你判断问题出在哪：例如回答不完整、但文档相关、没有幻觉，多半是信息不够，多检索一些文档就能解决。评测应该指出问题类型和修复策略，光给排名不够。

Julia 收尾时说，他们的方向是让 AI 系统能持续自我改进：Agent 从模式中学到哪些信息过时、哪些来源不可靠、用户需要什么，甚至在对话中途发现幻觉并自行纠正。动态数据集、整体评测和无参考指标是通往那里的组件。

04. Tengyu Ma（Voyage AI 联合创始人兼 CEO，现属 MongoDB；斯坦福教师）：2025 年的 RAG，变了什么，往哪里走

直播位置 1:07:54–1:27:15 · 英文题目大意：RAG in 2025: State of the Art and the Road Forward

为什么选 RAG，不选微调或长上下文

Tengyu Ma 说 Voyage AI 刚被 MongoDB 收购，他同时在斯坦福任教。Voyage 专注让检索更好。出发点是：现成的 LLM 和基于 LLM 的 Agent 不可能知道企业的私有信息，否则就意味着数据泄露了，所以要用到企业里就得把私有数据“喂”进去。办法有三种：

  • 长上下文（Long Context）：把所有文档直接塞进上下文窗口，可能是一百万 token，也可能是十亿 token，再提问。
  • 微调 Fine-tuning：先用文档更新模型参数，之后回答时不再看文档。
  • RAG：提问时用检索方法临时找出一小部分相关文档，交给 LLM 生成回答。

他说他们当初就相信 RAG，部分想法受斯坦福研究启发。他不相信微调能行，也不认为长上下文长期来看在成本上划算。他用人如何使用外部资料来类比：长上下文像每回答一个问题都把整座图书馆扫一遍；微调像提前把图书馆背下来、重新连接大脑里的突触，难度大也没必要，而且该背哪些、怎样干净地忘掉某些知识、谁能访问哪些书（数据治理）都很麻烦；RAG 简单、模块化、可靠、快且便宜，像人去图书馆找最相关的章节，是一种分层存储信息的方式。

检索的组成和两年的进步

检索部分有两到三个组件：嵌入模型（Embedding Model，把文档和查询转成向量，向量表示内容的含义）；向量数据库（存向量，并做 k 近邻搜索）；进阶的话还有重排序器。之后 LLM 生成答案。

  • 他说 Voyage 创立时 OpenAI 的 v3 嵌入模型还没发布（v3 是约一年半前发布的）。这一年半 Voyage 和 Cohere 都进步明显，新模型准确率更高、成本更低，规模定律（Scaling Law）也更好：同样参数质量更高，或同样质量参数更少。进步来自优化整条研究和调优链路：数据整理、数据选择、架构、损失函数、评测。
  • 他的图是在约 100 个数据集上平均，准确率约 80%，所以还有约 20% 的空间。但他强调不是每个数据集都 80%：大约一半能到 90% 甚至 95%，有的只有 60%，有的 20%、30%。常见任务的检索准确率已经很高。
  • Matryoshka 表示学习（字幕记作 matasha learning）：保证一个高维嵌入的前若干维本身也是合理的嵌入。比如 2048 维的向量，前 256 维也能用，只损失 1% 到 2%。量化（Quantization）是降低向量精度、性能基本不变。两者都用来降存储成本。他说至少能省 10 倍不怎么掉点；省 100 倍会掉 5% 到 10%，但 Voyage 省 100 倍仍好过 OpenAI，因为帕累托前沿不同。

让 RAG 更好的技巧

他只剩九分钟，快速过了一遍。最简单的是换更好的嵌入模型，其次：

  • 混合检索加重排序：用词法检索等多种检索，再用重排序器合并。Voyage 也提供重排序器。
  • 查询分解和文档增强：用 LLM 把查询改写得更长，或拆成多个子查询分别检索；给文档补元信息（标题、页眉、类别、作者、日期）。切块之后某块里可能已经没有这些信息，所以要把全局信息加到每一块里。他提到 Anthropic 写过一篇博客（即 Contextual Retrieval），用 LLM 为每块生成额外上下文，效果不错。
  • 领域专用嵌入：Voyage/MongoDB 为代码等领域定制嵌入，效果更好，压缩时掉得也更少。他给的数字是压缩约 100 倍只掉约 5%，通用模型要掉 10% 到 15%。
  • 用自己的数据微调嵌入模型。
  • 在嵌入之上的其他“技巧”：图、迭代检索等，都是基于嵌入的额外一层。

他对未来的判断

他认为 RAG 会一直存在，理由同前：只用一小部分数据，很高效。他类比 AI 整体的演变：七年前他刚开始在斯坦福和 Chris Ré 一起教机器学习课，有一页讲企业构建机器学习系统的七个步骤（收集数据、划分训练测试集、定义损失函数、建模、迭代……），这页现在还在讲义里，只是加了很多星号。到了 LLM 时代，企业直接拿现成模型部署，多数情况下已经比过去在企业内部走完所有步骤更好。训练这些步骤仍然有人做，只是改由 OpenAI、Anthropic、Voyage/MongoDB 这些模型提供方来做。

他认为 RAG 也会这样演变。现在有算力层（GPU，或 CPU 上的 KNN），模型层（嵌入、重排序器、LLM），以及上面一层他称为“技巧”的东西：各种解析和切块策略、递归检索、上下文化切块、GraphRAG 等。技巧现在有必要，因为模型都还不完美。将来模型层会变厚、技巧会变少。他说两年前在 GPT-3 上要做很多事才能让应用跑起来，现在开箱即用就能达到当年加满技巧的效果。仍然需要的技巧是那些通用模型不具备的信息，比如应该在提示词里定制“相似度”的定义。

  • 多模态嵌入：直接吃截图。过去 PDF 要先抽取成图片和文本再分别嵌入，视频要先转成文字稿；现在 PDF、PPT、表格都可以截图后直接嵌入，视频可以截取关键帧来嵌入。他展示的评测覆盖文档截图、表格、图表和纯文本，各项都有提升。
  • 即将发布的“上下文感知自动切块嵌入”：现在长文档必须由用户自己切块，一是嵌入模型的上下文长度有限（他说 Voyage 是最长的，也只有 32k），二是即使能整篇嵌入，检索出一篇 100k token 的文档再交给 LLM 也太贵，而且模型会漏掉中间的内容。他们的接口是：用户交一篇长文档，Voyage 负责切块，返回每块和每块的向量，每个向量既代表本块细节，也带有其他块的全局信息。
  • 之后还会有微调 API，让用户用自己的数据微调。

06. Sherwood Callaway、Satwik（11x）：构建 Alice 的大脑，一个像人一样学习的 AI 销售

直播位置 2:54:43–3:16:33 · 英文原题 Building Alice's Brain: How We Built an AI Sales Rep that Learns Like a Human

背景：Alice 和旧的“资料库”

Sherwood 是 11x 的技术负责人之一，负责 Alice 产品的工程；同台的是同事 Satwik（字幕名字拼写不一）。11x 为市场销售团队做“数字员工”，目前有 AI SDR Alice 和语音 Agent Julian。SDR（销售开发代表）是入门级销售岗位，主要做三件事：找潜在客户、跨渠道联系他们、约会议，核心指标是正面回复数和约到的会议数。大部分工作是写邮件。Alice 每天发约 5 万封邮件，人类 SDR 每天 20 到 50 封；Alice 在为约 300 家企业跑营销活动。

他们定义了两个词：seller 指通过 Alice 卖东西的公司（11x 的客户），lead 指被推销的人。Alice 要成功必须了解 seller（产品、服务、案例、痛点、价值主张、理想客户画像 ICP）和 lead。这次讲的是了解 seller。旧版产品里 seller 要在一个叫“Library”的界面手工录入每个产品和服务、痛点、方案、价值主张的详细描述，这些描述会进入 Alice 写邮件时的上下文；建活动时再手动选哪些产品给 Alice。问题有三个：录入繁琐；没填完资料库就不能跑活动，入门门槛高；邮件质量不好，选少了会出现不相关的产品，选多了上下文窗口塞满，Alice 写得更差。

新思路是反过来：让 Alice 主动把 seller 的所有资料拉进系统，写邮件时用最相关的部分。这就是知识库（Knowledge Base）。Satwik 说这更接近培训一个人类 SDR：丢一堆文档给他，几周到几个月慢慢上手。SDR 关心的资料有营销材料、案例、销售通话录音、新闻稿等，他们分成文档和图片、网站、音视频几类。

架构

用户在客户端上传资源，存到 S3，发给后端；后端在数据库里建记录，按资源类型和所选供应商启动任务；供应商异步解析，完成后发 Webhook（一种由对方服务器主动回调通知你的机制）回来；他们接收后把解析结果存进数据库，同时嵌入并写入 Pinecone；界面更新；Agent 之后查询 Pinecone。管线分五步：解析、切块、存储、检索、可视化。

解析：交给供应商

解析是把非文本资源转成文本，因为语言模型读的是文本。他们统一输出 Markdown，因为 Markdown 带有有意义的结构信息。多模态模型是一个办法，但有很多限制，所以解析仍然需要。他们没有自己做：资源类型和文件格式太多、想快速上市、也没信心做得比专门做这件事的公司好。选供应商的三个要求是支持所需资源类型、输出 Markdown、支持 Webhook。他坦白一开始没考虑准确性和完整性，假设头部供应商都在合理范围内；也没考虑成本，因为还没上线、不知道用量，打算有了真实数据再优化。

  • 文档和图片选 LlamaParse（LlamaIndex 的产品）：支持的文件类型最多，支持响应快，Jerry Liu 团队在初步评估后几小时内就拉了 Slack 频道。
  • 网站选 Firecrawl：之前项目用过；另一个候选 Tavily 的 crawl 接口当时还在开发中。
  • 音视频选较新的 Cloudglue：同时支持音频和视频，而且除了转写音轨，还能从画面本身抽信息。

切块、存储、检索

切块（Chunking）是把长文档切成可以嵌入和检索的语义单元，同时保留 Markdown 结构，因为标题和段落本身有含义。可选策略有按 token、按句子、按 Markdown 标题、让 LLM 来切，或组合。Satwik 建议问自己：想保留哪些逻辑单元、检索时想拿到什么、不同资源类型要不要不同策略、预期什么样的查询。他们用瀑布式组合：先按 Markdown 标题切，再按句子，最后按 token，让每条记录控制在目标 token 数内。这对各种文档都有效，切出来的块能在界面上干净展示，也避免了超长块稀释含义。

存储上 Sherwood 提醒，RAG 只要求从外部来源检索，图数据库、Elasticsearch、文件系统里的文件都算，文档数据库、关系数据库、键值存储、S3 对象存储都可以用。他们要做相似度搜索，所以用向量数据库，选了 Pinecone：知名、市场领导者、云托管不用自己运维、上手容易、自带嵌入模型（不用另找嵌入服务或自己部署）、客户支持好，帮他们分析过各种向量库，也讨论过图数据库和 GraphRAG 是否合适。

检索上 Satwik 讲了过去一年的演变：传统 RAG（取信息、补进系统提示词再调 LLM）；Agentic RAG（把检索做成工具，挂到 Agent 流程里让它自己调用）；最近几个月出现的 Deep Research RAG（研究型 Agent 先做计划，计划里有一步或多步检索，可宽可深，并自行判断要不要继续检索）。他们做了一个深度研究 Agent，用的是云端 Agent 服务商 Letta：传入 lead 信息，Agent 做计划、调用检索工具、总结结果，以问答形式输出。

可视化：让用户看看 Alice 的大脑

客户要信任 Alice 代表自己的公司，要确认她懂产品、不会编造案例或痛点。他们的办法是一个交互式 3D 可视化：把 Pinecone 里的所有向量投影到三维，渲染成节点，点任意节点能看到对应的文本块。销售和支持团队会用它向客户展示 Alice 知道什么。界面上，用户在弹窗里拖入网址、文档、视频，点 “Learn”；可以向 Alice 提问她对知识库了解什么（也是用 Letta 做的 Agent）；建活动时左侧以问答形式显示知识库内容，点开能看到检索出的、用于写这封邮件的文本块。

经验和计划

  • RAG 很复杂，比想象的难很多，有大量细小决策和要评估的技术。
  • 先上线，再做基准，再改进。先做出满足产品需求的东西，再建立真实的基准来迭代。
  • 依靠供应商。他们在争取你的生意，让他们教你各家方案的区别。
  • 后续计划：追踪和减少邮件里的幻觉；按准确性和完整性评估解析供应商；试验混合 RAG，在向量库旁加图数据库；降低整条管线的成本。

07. Will Bryk（Exa 联合创始人兼 CEO）：为 AI 而建的网页搜索

直播位置 3:19:51–3:38:11

从 1998 年讲起

他说本来要现场写代码，但先讲一个“为 AI 而建的网页搜索”的故事，结尾是一页幻灯片：一个 API 获取网上的任何信息。1998 年的最先进信息检索是 Google：输入 Australia，返回所有包含这个词的网页，按 PageRank（根据网页之间的链接结构判断权威性）排序。他说那时他两岁。2021 年 GPT-3 出来，可以输入一整段话描述需求，模型能理解语言里的细微差别；同时在 Google 搜 “shirts without stripes”（没有条纹的衬衫）却会返回有条纹的衬衫，因为关键词比较不理解 “without”。他决定至少用十年时间，做一个用 GPT-3 那类技术、真正理解查询和网页内容的搜索引擎。

用嵌入重做搜索

2021 年夏天他们进了 YC，融了几百万美元。他开玩笑说他们干了每个 YC 公司都该干的事，把一半钱花在 GPU 集群上；还按“YC 的建议”一年半不跟用户说话只做研究。随后他说这两件事你们都不该学，只是他们在从零重做搜索这个难题上有理由这么做。他展示了一次 Weights & Biases 训练曲线，紫色那条是一个突破。

他解释思路：传统搜索引擎为网页建倒排索引（Inverted Index，从每个词映射到包含它的所有文档），查询时做复杂的关键词比较。他们的想法是用 Transformer 把每个文档变成嵌入，嵌入可以表示词语之外的含义、观点、以及网上别人怎么提到这篇文档，而且可以任意变大，极限情况下一定胜过关键词。他称之为“苦涩的教训”（The Bitter Lesson）式的思路：数据越多越好，就能做出真正理解你的搜索。查询时把 “shirts without stripes” 嵌入后和万亿文档的嵌入比较。一年半后他们在 Exa 上搜这个词，结果真的没有条纹，也能处理一整段话的查询。2022 年 11 月发布时在 Twitter 上很受关注，两周后 ChatGPT 发布了。

LLM 为什么永远需要搜索

他们一度怀疑搜索还有没有位置，很快确认有。他用信息论论证：问 GPT-4 “找一些旧金山工程师的个人网站”，它的权重里没有这些。GPT-4 据说有几万亿参数，可以算作不到 10 TB；互联网光文档就超过一百万 TB，加上图片视频更多，他在推文里估算网页总量在 EB（exabyte）量级，公司名 Exa 就是这么来的。而且网页一直在更新。所以 LLM 必须搜索，LLM 加搜索引擎才能回答这类问题。

传统搜索是给人用的，AI 要的不一样

他说的“秘密”是：Google、Bing 这些搜索引擎是为人设计的，人慢、懒、打几个关键词、只想看几个链接、在乎页面 UI。AI 能飞快吞下大量信息，想用复杂查询拿到尽可能多的知识。为人优化的算法不可能同时对 AI 最优，所以他认为很多工具把传统搜索和 AI 拼在一起并不对路。他举了三个区别：

  • AI 要精确可控的结果。一个 VC 让 AI 找“像 Bell Labs 的下一个大事”，Google 返回人爱点的东西，信息密度低，也不符合要求；AI 想要的是一份创业公司名单。未来的 Agent 会做大量搜索，需要一个“说什么就返回什么”的 API。
  • AI 想带着大量上下文搜索。一个整天陪你的 AI 助手知道你的偏好，应该能用好几段文字去搜餐厅或公寓。他说 Google 的查询有几十个关键词的上限，Exa 能处理好几段文字。
  • AI 要全面的知识。给人一万个链接没用，AI 并行处理几秒钟就看完。比如要找所有 YC 投资的 AI 公司，就该拿到全部，Google 做不到返回一千、一万条。

他画了一个“所有可能查询的空间”：2022 年前大家只在关键词查询那一角（Stripe 定价、某人的 GitHub、Taylor Swift 男友）；2022 年后多了不需要搜索的查询（像给五岁小孩解释概念、帮我调试代码）；Exa 引入了语义查询（旧金山懂汇编的人）；还有极复杂的查询（找出所有论证 X 而不是 Y、作者像 Z 的文章），Exa 的 Websets 产品开始能处理，这相当于把网页变成可以随意过滤的数据库；还有大家没想到的查询类型。目标是一个 API 覆盖所有查询。

演示

  • 搜索控制台：一个查询返回结果和对应代码，可以调结果数量（10、100、1000）、日期范围、限定域名、神经检索或关键词检索。他说开关多是好事，因为调用它的是 AI，需要完全的控制权。
  • 他写了一个叫 Mark 的 Agent（agent.py），什么都转成 Markdown。用神经检索搜“喜欢信息检索的旧金山工程师的个人网站”，Mark 把结果整理成 Markdown。
  • “我的 GitHub”这类适合关键词检索的查询，换成 keyword 模式，拿到他自己 GitHub 的信息。
  • 他说用 o3 一次写成的 GitHub Agent 组合两种检索：先神经检索拿一批人名，再对每个名字做关键词检索找 GitHub。演示只取 10 条，企业版可以 100 或 1000 条。
  • 他说当天刚发布了 research 接口，在后台做大量搜索和 LLM 调用，产出报告或结构化输出，相当于一个深度研究 API，他称之为业界最好。

08. David Karam（Pi Labs 联合创始人，前 Google 搜索团队）：从 BM25 到最复杂的 RAG，一层层加技术

直播位置 3:39:17–3:59:07（屏幕上把公司写成了 Google，主持人更正为 Pi Labs）

先看结果，再选技术

他说他和联合创始人以及很多同事之前在 Google 搜索工作，后来出来做 Pi Labs。他想用“白话”搭一个框架：要提升系统质量该怎么做，平时听到的各种技术放在哪里。他在 Google 和 Pi Labs 的习惯都是看具体案例、具体查询，看什么有效什么无效，他说这就是 Google 过去所说的“质量工程”。他给自己定了 19 分钟讲 50 页幻灯片的挑战。

他的框架：从结果出发，你在解决一个产品问题，有一条质量线要达到，比如上线一个 CRM Agent 的上线标准。你自己的基准分成简单、中等、困难几组查询集。质量工程循环是：建立基线，做损失分析（看哪里坏了），再做质量工程，技术只出现在最后这一步。他说最大的问题是有人从技术开始问“我要不要 BM25、要不要向量检索”，他会反问你想做什么、查询集是什么、哪里在失败。他的原则叫“按复杂度调整后的影响”，或者“保持懒惰”：没坏就别修。他列了一张技术目录，最重要的两列是难度和影响，简单的就试。

技术清单，按失败一步步往上加

  • 内存内检索：把所有文档塞给 LLM。他说上下文窗口用起来最容易，应该先从这里开始，例子是 NotebookLM，放五份文档直接提问，不需要 RAG。它坏在文档放不下，或上下文太长模型注意不到。
  • BM25：一种经典的关键词排序算法。他说它大致看四样东西：查询词、词频、文档长度、词的稀有程度。容易试，效果不错，但查询没有关键词性质时就不行。
  • 相关性嵌入（向量检索）：向量空间能处理比关键词多得多的细微差别，但在需要关键词精确匹配时会失败。他让 ChatGPT 列了两类查询：“iPhone battery life” 不需要向量检索；“iPhone 充一次电能用多久才要再充” 就需要。做损失分析时看你的查询长什么样，再决定投入。
  • 重排序器：BM25 和向量检索合起来的候选集需要排序，通常指交叉编码器（Cross-encoder）。嵌入是查询一个向量、文档一个向量再算距离；交叉编码器同时读查询和文档再给分，更强也更贵，不能对全部文档用，所以要先多取、再对小集合重排。
  • 自定义语义：标准嵌入和重排序器只衡量语义相似度，而相关性只是代理指标，相关不等于排名。他说 Google 搜索的魔力来自看相关性以外的很多信号。他引用上午 Harvey 那条法律查询，“regime”“material” 在法律里有特定含义，法律法规需要专门检索，这时要做自定义嵌入，把领域建模进自己的向量空间。他又让 ChatGPT 列出法律领域标准检索会出错的词，比如 moot、material。
  • 排序也需要领域信号：他当天在 Perplexity 上试，问给儿子的便宜礼物，追问“预算 50 美元或以上”，结果仍给出 15 美元和 40 美元的东西。价格是一个信号，没被识别、没进查询也没进排序。其他信号有商家信号、播客收听次数、受欢迎程度。PageRank 衡量的是显著性，和相关性无关，是关于语料结构的信号。他把这叫“横向语义”和“纵向语义”：垂直领域里，相关性只占语义世界很小一部分。
  • 用户偏好：即使懂了购物领域，用户会点你没想到的东西，不点你以为会点的东西。这时要引入点击、点赞点踩信号，比如做一个点击率预测信号，再和其他信号合成排序分数：相关性加半结构化的价格信号与查询理解，加用户偏好。
  • 查询改写和扇出（Fan-out）：Agent 自己发查询时，搜索引擎期望的查询和 LLM 发出的查询之间有“阻抗失配”，你没法把搜索引擎的全部特性描述给 LLM。很多公司（包括 Google）会自己掌控编排，把一个大查询拆成 N 个小查询。他展示了 Google AI Mode 的截图，动画里一闪而过地显示在发 15 个、20 个查询。他说他喜欢 MCP（模型上下文协议，让模型以统一方式调用外部工具），但不相信只靠提示词能让 LLM 知道后端搜索能做什么，边界在哪里还不清楚，现在质量不够时需要控制权。例子：“David 在做这个吗”应该变成“Jira 里的 David”“Slack 线程里的 David”。
  • 补充检索：查询对了，后端对不对？他说客户常常搜得不够，想要高召回就多搜。他讲了 Google 搜索时的例子：一个中东菜名的查询（字幕不清），难倒了一个 6000 人的组织，因为意图模糊，可能想找餐厅，也可能想看图片，最后 Google 去调所有后端再全部放进来。除非成本扛不住，不要省。
  • 蒸馏（Distillation）：规模大了 GPU 会“融化”，他提到 Sam Altman 一直抱怨 GPU 在融化。蒸馏是在保持质量不变的前提下把模型变小，需要会微调。他的理由是大模型对你的单一任务大多是“资历过剩”。他说 Perplexity 很快，因为专门训练了一个只做问答的模型。这很难，只在延迟对用户很要紧时做，比如 10 秒会流失用户、2 秒不会。

全都做了还失败怎么办

他开玩笑说怪产品经理，随后认真讲：质量工程永远到不了 100%，这些是随机系统，要把问题往上交给产品设计。产品界面能承受多少“魔法”，决定了能显得多神奇。复杂的例子是客服里的人在环中，简单的例子是 Google 购物：理解度高时展示“高承诺 UI”，有可点击的商品、评论、筛选；理解度低（只把网页当作词袋）时退化成一列 10 个结果让你自己选。理解多就优雅地升级，理解少就优雅地降级，而且降级后仍然可用。

最后他重复框架：一切都是经验性的，不要陷入上下文窗口对 RAG、Agent 对工作流之类的理论争论。建立基线、分析损失、看工具箱里有没有简单的事可做，没有就做中等的，再不行再考虑招人做很难的事。他提醒做得太超前会白费时间。他在 19 分钟内讲完了，还剩 30 秒。
