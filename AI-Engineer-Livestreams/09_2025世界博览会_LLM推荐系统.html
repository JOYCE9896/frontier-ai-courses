01. Eugene Yan（RecSys 专场主持）：语言模型怎样进入推荐系统

直播位置 0:02:37–0:24:22

Eugene Yan 开场说，他妻子嫌他的幻灯片太素，所以每页都配了他家两只狗 Latte 和 Mochi 的照片。这一讲是整个专场的导读，他把后面几位讲者的工作提前串了一遍。

语言模型技术在推荐里早就有了

他先回顾历史：2013 年起，人们就从用户交互序列的共现关系里学物品嵌入（Embedding，把物品表示成一串数字向量）；后来用 GRU4Rec 这类循环神经网络，根据短序列预测下一个物品；再后来 Transformer 和注意力机制出现，长距离依赖处理得更好，大家开始把用户几百到两千个物品 ID 的完整序列都喂进去。他想在这个专场讨论三个方向：语义 ID、数据增强、统一模型。

一、语义 ID：快手的可训练多模态语义 ID

传统推荐系统给每个物品分配一个哈希 ID，这个 ID 本身不包含物品内容。于是每来一个新物品都要从零学起，这就是冷启动（Cold Start）问题；长尾物品只有一两次到十来次交互，数据稀疏，学不出来。结果是推荐系统偏向热门内容。语义 ID（Semantic ID）的思路是让 ID 本身编码内容信息，甚至是多模态内容。

他的例子是快手（字幕作 "Quao"，他介绍为中国第二大短视频平台，也是可灵 Kling 的出品方）。快手每天有数以亿计的短视频上传。模型是标准的双塔网络（Two-Tower）：左边是用户塔，输入用户 ID 和历史 ID 序列；右边是物品塔。新东西在于加入了内容输入：画面用 ResNet 编码，视频描述用 BERT，音频用 VGGish。

难点是这些编码器很难一起反向传播更新。快手的做法是把各模态的内容嵌入直接拼接起来，再在约 1 亿条短视频上用 k-means 聚出 1000 个聚类 ID。编码器上方是不可训练的内容嵌入，下方是可训练的聚类 ID，每个聚类 ID 对应自己的嵌入表。训练过程中，模型学会通过聚类 ID 把内容空间映射到用户行为空间。

结果：语义 ID 在点击和点赞上都优于哈希 ID；冷启动覆盖率（推出的 100 个视频里有多少是新视频）提高 3.6%；冷启动速度（多少新视频达到某个播放门槛，论文没公布门槛）也有提升。他预告后面 YouTube 的分享会展示语言模型和语义 ID 结合后，能用人话解释为什么推荐某个视频。

二、数据增强：Indeed 和 Spotify

他说机器学习靠的是大规模高质量数据，搜索比推荐更依赖元数据：查询扩展、同义词、拼写纠错等。过去靠人工标注，现在 LLM 很擅长做这件事。

Indeed 的问题：通过邮件给用户推送职位，其中一部分不合适，用户失去信任后直接退订，而退订的用户几乎不可能再拉回来。显式反馈（点赞、点踩）太稀疏；隐式反馈不准确，用户没点一个职位，可能是不喜欢，也可能是时机不对，或者"你妻子在那家公司上班，你不想和她同一个单位"。他们的方案是一个过滤坏推荐的轻量分类器。他喜欢这篇论文，因为它把一路的弯路都写了出来：

  • 先请专家给"职位 + 用户（简历和行为数据）"配对打标签。
  • 用开放模型 Mistral 和 Llama 2 做提示，效果很差，模型抓不住简历和职位描述里的内容，输出很空泛，尽管上下文长度够用。
  • GPT-4 效果很好，精确率和召回率约 90%，但太贵太慢，一次要 22 秒。
  • GPT-3.5 精确率很差：它判为坏推荐的里面只有 63% 真的是坏的，相当于要扔掉三分之一本来是好的推荐。
  • 微调 GPT-3.5 后达到了想要的精确率，成本和延迟是 GPT-4 的四分之一，但仍要 6.7 秒，做不了在线过滤。
  • 最后用微调模型的标签蒸馏出一个轻量分类器，AUC-ROC 0.86，延迟足够实时过滤（他估计在 200 毫秒以内，论文没给具体数字）。

上线结果：坏推荐减少约 20%。他们原以为推荐变少会让申请率下降，实际申请率上升 4%，退订率下降 5%。他的结论是推荐的数量不等于一切，质量能带来实打实的提升。

Spotify 的问题：用户习惯搜歌和歌手，平台加入播客和有声书后，不仅是单个物品冷启动，还是整个品类的冷启动。他们做了查询推荐系统。新查询的来源大多是传统办法：从目录标题、歌单标题、搜索日志里抽取，或者在歌手名后面加上 "cover"。LLM 只用来生成自然语言查询。他强调，先用好已有的常规技术，需要时再用 LLM 补充，别一上来什么都交给 LLM。最终搜索结果页顶部展示推荐的查询，下方仍是直接结果，这样不用打横幅也能告诉用户"我们有有声书和播客了"。探索型查询增加 9%，他换算为每天十分之一的用户在探索新品类。

三、统一模型：Netflix 和 Etsy

一般公司里广告、推荐、搜索是各自独立的系统；推荐内部，首页、物品详情页、加购、感谢页又可能各有一个模型。模型越来越多，但人手不变，流水线重复，维护成本高，而且改进一个模型不会自动惠及其他模型。他提到 Stripe 发过一条推文，说他们做了一个基于 Transformer 的支付欺诈基础模型，说明连支付序列都能这样做。

Netflix 的 UniCoRn（Unified Contextual Ranker，统一上下文排序器）：原来搜索、相似视频推荐、搜索前推荐（用户还没输入查询时）各有专门模型。新模型底部是用户基础模型，输入观看历史，另有上下文和相关性模型。核心做法是统一输入格式：用户 ID、物品 ID、搜索查询（如果有）、国家、任务类型，类似多任务学习。缺失字段用插补：做物品到物品推荐时没有搜索查询，就用当前物品的标题代替。结果是统一模型在多个任务上追平或超过专用模型。他说"追平"听起来不起眼，但消除了技术债，后续迭代会更快。

Etsy 的统一嵌入：Etsy 的库存一直在变，"母亲节礼物"这种宽泛查询几乎匹配不到描述里含这几个字的商品，而基于词面的检索也不考虑用户偏好。他们同样用双塔：商品塔用 T5 编码文本描述，并用"查询-商品"日志（用户搜了什么、最后点击或购买了什么）；查询塔和商品塔共享文本 token、商品类目、用户位置的编码器，所以嵌入可以把用户和商品所在地匹配起来；用户偏好（过去的查询、购买）也编码进去做个性化。系统层面，他们给商品向量拼接一个质量向量（评分、新鲜度、转化率），为了维度一致，查询向量那边拼一个常数向量，然后就能照常做点积。结果：全站转化率提升 2.6%，搜索购买提升 5% 以上。

他也提醒统一模型有"对齐税"：把十几个用例压进一个模型，可能某个任务变好会让另一个变差，最后可能要拆成两三个统一模型。三条带走的建议：语义 ID、数据增强、统一模型。

问答

  • 有人问他写的那篇推荐系统长综述为什么没提 Meta 的生成式推荐（HSTU）工作。他说不是有意遗漏，论文太多，他给自己限定两周写完，时间到了就发布。
  • 有人问 Google 搜索质量下降是否和放弃可审计的显式排序因子、转向黑盒模型有关。他说没有内部信息，自己也没感觉到质量下降，建议去问在场的 Google 员工。

02. Han 等（Pinterest 搜索相关性团队）：把 LLM 用在 Pinterest 搜索相关性上

直播位置 0:27:34–0:33:22（录像在第二条经验中途被切断）

讲者自我介绍叫 Han，和一位同事（字幕里名字没录清）都是 Pinterest 搜索相关性团队的机器学习工程师。Eugene 介绍时说，他们会讲怎样把搜索查询和多模态上下文（视觉模型生成的描述、链接文本、用户整理的看板）结合起来做相关性打分。

Pinterest 搜索的规模和结构

Pinterest 是视觉发现平台，有三个主要入口：首页信息流、相关 Pin 和搜索。搜索每月处理超过 60 亿次查询，候选 Pin 有数十亿个，支持 45 种以上语言，覆盖 100 多个国家。后端和业界多数推荐系统类似：查询理解、召回、重排、混排，最后生成搜索结果流。这次讲的是重排阶段的语义相关性模型。

相关性模型本质是分类模型：给定查询和一个 Pin，预测两者相关程度，用五级量表，从"最相关"到"最不相关"。他们总结了四条经验，录像只保留了前两条。

经验一：LLM 擅长做相关性预测

模型结构是交叉编码器（Cross-Encoder）：把查询和 Pin 的文本拼在一起送进 LLM 得到嵌入，这样能更好地捕捉两者之间的交互；再把嵌入送进 MLP 层，输出对应五个相关性等级的五维向量。训练时用 Pinterest 内部数据微调开源 LLM。

基线是 Pinterest 自研的查询和内容嵌入 SearchSage。结果是 LLM 明显提升了相关性预测，模型越先进、越大，效果越好。例如 8B 的 Llama 3 比多语言 BERT-base 提升 12%，比 SearchSage 嵌入提升 20%。

经验二：视觉语言模型生成的描述和用户行为是有用的内容标注

要让 LLM 判断相关性，需要给每个 Pin 一个文本表示。讲者列举了几类特征，包括 Pin 被保存到的用户看板标题、把用户带到这个 Pin 的历史查询等。讲到这里录像中断。

03. LinkedIn 讲者：推荐大模型的蒸馏、剪枝、量化和稀疏化

直播位置 0:33:22–0:43:47（只有后半段和问答）

录像从这里直接跳进另一场演讲的中段。Eugene 开场时预告上午最后一场是 LinkedIn，加上内容里提到 1500 亿参数的模型、用户求职记录和职位帖子，可以判断这是 LinkedIn 关于推荐基础模型的分享。字幕里讲者称搭档为 "Maz"，姓名未完整出现，这里不写具体人名。

先做大，再变小

他说在线推荐要求延迟最好在 400 到 500 毫秒以内，有三个手段提高吞吐、降低延迟：换更小的模型（蒸馏）、剪枝、量化，外加稀疏化。小模型吞吐更高，但他们的经验是先用大模型：小模型一开始容量和推理能力都不够，解决不了复杂任务。所以他们从一个 1500 亿参数的模型出发往下蒸馏。

蒸馏要分步做：比如先蒸到 8B，再到 3B，再到 1B，每一步都从上一步的模型蒸馏。这比从 150B 直接蒸到 1B 效果好得多。

渐进剪枝

剪枝（Pruning）是一个数学优化问题：减少 Transformer 的注意力头数、MLP 数量，或者降低部分激活和参数的精度。他说 Transformer 在信息保留上冗余很大，可以剪。但一开始剪得太狠，效果会明显下降。做法同样是渐进的：剪一点，蒸馏一次，再剪，再蒸。他们的图显示渐进剪枝几乎没有信息损失，一次性大幅剪枝会让模型质量下降最多约 1%。

混合精度量化

量化（Quantization）是把参数和激活换成更低精度的数值格式。他们对激活和参数用 FP8，但所有层都用 FP8 会让质量明显下降，所以用混合精度。对排序和推荐任务，模型输出的概率要足够精确，所以最后的 LM head 必须保持 FP32。用 FP16、BF16 或 FP8 的话数值会塌缩，概率校准变差，分不清不同候选物品的高低。

注意力稀疏化

Transformer 最贵的是注意力分数。知道任务是推荐后，可以让历史里的物品不必两两互相注意。打分时也一样：一次给 50 个、500 个候选物品打分，但候选之间不能互相注意，所以对输出部分的注意力也做稀疏化。

综合下来，经过四五个版本的迭代，延迟降低到 1/7，单张 GPU 的吞吐提高 30 倍。他们也发表了几篇技术报告和论文分享过程。

问答

  • 怎么确认微调后没有丢掉泛化能力？他们有 50 到 60 个基准测试，有内部的也有外部的，例如用 IFEval 检查指令遵循；还有一些任务从没出现在训练数据里，用来衡量对新领域的泛化。
  • 小型房产列表网站有没有开箱即用的推荐模型？他说希望有，这也是他们做基础模型的原因之一；提问者提到微软刚发布的 NLWeb，讲者说没听说过，建议对方去看看。
  • 一次给多个物品打分是不是要多步解码？不是。他们不想引入投机解码这类复杂度，全部放在预填充（Prefill）阶段：把所有候选物品排成一个序列，用他们称为 4D 注意力掩码的方式让候选之间互不注意，只注意用户历史和画像。为此他们在 SGLang 和 vLLM 里写了专门的 kernel，一次最多 500 个候选。
  • 用户历史太长怎么办？他们试过用检索挑出和当前查询最相近的历史，也试过按时间排序加衰减权重。结果多数应用里按时间顺序就够了，因为推荐系统很看重新鲜度。更难的是在上下文里平衡正负样本的比例。另一位讲者补充，服务时还不能破坏 KV 缓存（KV Cache，推理时缓存已计算的注意力键值以加速），所以比简单的时间排序更聪明的做法会很麻烦。
  • 怎样支撑这么多实验？靠高度自动化：实验结果自动写进 Excel 表，想换量化参数只要改参数，其余端到端自动跑。大部分自建，同时用了 Lightning、vLLM 等开源工具，并把它们整合好。

04. Yesu Feng（Netflix 资深研究科学家）：用一个基础模型覆盖所有推荐场景

直播位置 2:22:45–2:44:46

Eugene 介绍他是 Netflix 的 staff research scientist（字幕里名字只听出 "Yu"，后面 Instacart 讲者称他 "Yazu"）。他讲的是 Netflix 在个性化上的一个大赌注：用一个基础模型覆盖全部推荐用例。

问题：推荐需求太多样，专用模型越来越多

Netflix 首页是行和物品组成的二维布局，多样性至少有三层：行的种类（喜剧、动作片、新上线、Netflix 独家等）；物品的种类（除了电影和剧集，现在有游戏、直播，以后还会更多）；页面的种类（首页、搜索页、儿童首页、移动端信息流是线性页面，没有二维布局）。

多年下来形成了很多专用模型：有的排视频，有的排行，有的专注用户没看过的剧，有的专注用户正在追的剧。它们独立开发，目标不同但大量重叠，标签工程和特征工程重复。以特征为例，同一份用户交互历史被衍生出各种计数、不同时间窗口内的计数、历史剧集和目标剧集的相似度、去重的剧集 ID 序列等，各模型版本略有不同，很难维护。继续按用例开新模型显然无法扩展，也拖慢创新速度。这是大约四年前、疫情期间的状况。

两个假设

他们问：能不能把用户表示的学习集中到一处？于是提出两个假设。第一，通过扩大规模的半监督学习可以改进个性化，缩放定律（Scaling Law）对推荐系统也适用。第二，把基础模型接入所有系统，可以产生高杠杆，同时改进所有下游模型。

数据和 tokenization

他说自回归 Transformer 推荐模型和 LLM 有很多相似处，也有不同。最底层是数据清洗和 tokenization（把输入切成模型处理的基本单位），做过 LLM 的人都知道这里的决定会影响到上面每一层。不同之处在于：LLM 的一个 token 就是一个 ID，而推荐里一个 token 是用户的一次交互事件，事件带有很多字段。怎样切分、粒度多细、和上下文窗口长度怎么权衡，都要仔细考虑。经过多轮迭代，他们做出了可调整 tokenization 的抽象和接口，比如预训练用一种 tokenization，针对具体应用微调时用稍有不同的另一种。

模型各层

  • 事件表示层：按"何时、何地、何事"拆。何时是时间编码；何地包括国家、设备、在哪个页面哪一行发生；何事是目标剧集、交互类型、持续多久。这里要决定保留哪些信息、丢掉哪些。
  • 嵌入层：推荐必须把从零学的 ID 嵌入和语义内容信息结合起来。只有 ID 嵌入的话，训练时没见过的剧集在推理时就无从处理，这是 LLM 没有、推荐系统常见的冷启动问题。
  • Transformer 层：架构本身不多讲。他强调用这一层的隐藏状态输出作为用户表示，学好长期用户表示是基础模型的主要目标之一。要考虑用户历史不断变化时表示是否稳定，如何沿时间维度或跨层聚合，以及是否要针对下游目标显式适配。
  • 目标层：比 LLM 丰富得多。输出可以是多个序列：一个是实体 ID 序列，类似下一个 token 预测的 softmax 或采样 softmax；事件的其他字段也能当目标，比如动作类型、实体元数据（类型、类别、语言）、观看时长、设备、下一次播放的时间。可以把问题建成多任务、多头或分层预测，也可以把这些字段当作损失函数的权重、奖励或掩码，让模型专注学习某类用户行为。

缩放定律成立吗

他的回答是成立。大约两年到两年半里，他们一直在放大规模并持续看到收益，模型从千万级规模涨到约 10 亿参数，数据相应扩大。他说收益并没有到头，停在这里是因为推荐系统的延迟和成本要求严格，继续放大就必须再蒸馏回来。

他列出三项从 LLM 借来的做法：

  • 多 token 预测（他提到 DeepSeek 论文里也有）：让模型不那么短视，对训练和服务之间的时间差更稳健，关注长期用户满意度，不只盯着下一个动作。他说这带来了明显的指标提升。
  • 多层表示：借鉴逐层监督、自蒸馏、多层输出聚合，让用户表示更好更稳定。
  • 长上下文处理：从截断滑动窗口、稀疏注意力，到逐步加长训练序列，再到各种并行策略。

上线和应用

以前的架构是许多数据、特征、模型各自独立。有了基础模型后，数据层和表示层（尤其是用户表示和内容表示）基本统一了，各应用模型建在基础模型之上，变成一层薄薄的适配。下游有三种用法：

  • 把基础模型作为子图嵌进下游神经网络，直接替换原来的序列 Transformer 塔；内容嵌入也可以作为嵌入查找层接入。
  • 推送嵌入：内容嵌入和会员嵌入推到中心化的嵌入存储。要考虑会员嵌入多久刷新一次、怎样保证稳定。这也让数据科学家等非个性化团队能直接取用。
  • 把模型拿出来针对具体应用微调，或者蒸馏以满足严格的在线延迟要求。

他展示了过去一年半的成绩图：蓝柱是接入基础模型的应用数量，绿柱是 A/B 测试胜出次数。他认为两个假设都得到了验证：可扩展（模型越大质量越好，基础设施统一，新应用接入更容易），高杠杆（集中学习），创新更快（很多新应用直接微调基础模型做首个版本）。

当前方向：一是面向异构实体的通用表示，也就是语义 ID 一类，因为 Netflix 的内容类型越来越杂；二是做合集推荐的生成式检索，推理时多步解码，业务规则和多样性可以在解码过程中自然处理；三是借鉴 LLM 的提示调优（Prompt Tuning），训练一些软 token，推理时换入换出，让基础模型表现出不同行为。

问答

  • 既然学到了用户偏好，能不能预测别的事，比如选举？他说他们在扩展到更多实体类型，并尝试捕捉用户在平台内外的品味，这是总体趋势。
  • 图模型和强化学习？他说有专门的子团队做图模型，围绕覆盖平台内外整个娱乐生态的知识图谱，图模型产出的嵌入用于冷启动，就是前面提到的语义嵌入的来源。强化学习也在用，特别是用稀疏的用户行为奖励来引导整个合集的生成。
  • 嵌入是否用到视频帧或片段级信息？还没有。组织里别的内容团队有这类嵌入，但尚未接入，他认为趋势会走到那一步。

05. Vinesh Gudla、Tejaswi Tenneti（Instacart）：用 LLM 改造搜索和发现

直播位置 2:45:35–3:06:42

Eugene 介绍两人分别是 Instacart 的机器学习总监和 staff 机器学习工程师（字幕里名字被听成 "Jastri"、"Mesh"、"Vines"、"TSV"）。两人都在搜索与发现 ML 团队。Instacart 是北美最大的在线生鲜杂货平台。前半段由 Vinesh 讲查询理解，后半段由 Tejaswi 讲发现型内容。

生鲜电商里搜索的位置

用户带着长长的购物清单来，一次要找几十样东西，多数是回购，少数是第一次尝试，而大部分购买来自搜索。所以搜索既要让人快速找到要买的东西，也要支持新品发现。新品发现对广告主（展示新品）和平台（更大的购物篮）都有好处。

两类查询最难。一是过于宽泛的查询，比如 "snacks"，对应商品太多，而模型靠互动数据训练，没曝光的商品收集不到数据，排不上去，这是另一种冷启动。二是很具体的查询，比如 "unsweetened plant-based yogurt"（无糖植物基酸奶），出现频率低，互动数据不够。他们以前做了不少工作，召回提高了，但精确率始终是难题。另外，用户反馈搜到想要的商品后就"走到死胡同"，想找相关商品（比如买意面时顺便看看意面酱）得再搜好几次。

查询理解：类目分类器

查询理解（Query Understanding）是搜索栈最上游的模块，包含查询归一化、查询标注、查询分类、类目分类等多个模型。第一个例子是把查询映射到商品类目的分类器，比如 "watermelon" 映射到水果、有机水果等。类目体系约 1 万个标签，其中约 6000 个常用；一个查询可以对应多个类目，是多标签问题。

旧方案是一个基于 FastText 的神经网络建模查询和类目的语义关系，再加一个 NPMI 统计共现模型兜底。头部和腰部查询效果不错，长尾查询覆盖很低。他们也试过 BERT 类模型，有些提升，但抵不过增加的延迟。

第一次尝试 LLM：把查询和整个类目体系喂给 LLM，让它预测最相关的类目。输出看上去很合理，但线上 A/B 测试效果不好。典型例子是 "protein"：Instacart 用户搜它是要蛋白粉、蛋白棒等补剂，LLM 却理解成鸡肉、豆腐等富含蛋白质的食物。问题出在 LLM 不了解 Instacart 用户的行为。

改进办法是把每个查询转化率最高的前 K 个类目作为额外上下文给 LLM，再经过排序和下游校验（他说实际流程比这复杂）。例子：查询 "Werner soda"，旧模型识别为水果味汽水品牌，不算错但不精确；LLM 识别为一个姜汁汽水品牌，下游召回和排序随之改善。长尾查询上精确率提升 18 个百分点，召回提升 70 个百分点。他展示的提示词很简单：传入高转化类目作为上下文，加上一些输出准则。

查询改写

不同零售商的商品目录大小差别很大，同一个查询在小目录里可能没有结果，这时改写很有用，比如把 "1% milk" 改写成 "milk"。旧模型基于互动数据训练，长尾效果差。用 LLM 后能生成很精确的改写，分三类：替代（avocado oil 改成 olive oil）、更宽泛（healthy cooking oil）、同义（avocado extract）。根据人工评测数据，换用更好的第三方 LLM 效果就能明显提高；线上无结果查询的数量大幅下降。

上线方式：头部预计算，长尾兜底

Instacart 的查询分布是头部和腰部很厚，尾部很长。他们离线批量为头部和腰部查询预计算 LLM 输出并缓存，线上直接查缓存，几乎不影响延迟；长尾查询退回旧模型。现在正尝试用一个蒸馏过的 Llama 模型替换长尾的旧模型。

他还提到：查询理解现在由一堆模型组成，正如 Netflix 讲者说的，管理这么多模型很复杂，合并成一个小模型或大模型会让结果更一致。例子是查询 "hum"：品牌标注模型正确识别为一个康普茶品牌，拼写纠正模型却把它改成 "hummus"（鹰嘴豆泥），结果让用户困惑；统一模型就没有这个问题。另外，用 LLM 做查询理解可以传入更多上下文，理解用户这次购物的目的，比如是不是在为某个菜谱买食材。

发现型内容

Tejaswi 接着讲搜索结果页上的发现型内容。效果是：搜 "swordfish"（剑鱼）没有完全匹配的商品时，展示罗非鱼等其他肉质鱼类作为替代；搜 "sushi" 这种结果很多的查询时，在结果页底部展示亚洲烹饪食材、日本饮料等。两类内容都提高了互动和每次搜索的收入。

要求有两条：内容要是现有结果之外的增量，不能重复；内容要符合 Instacart 的领域知识，比如 "dishes" 指的是餐具，不是菜，"Thanksgiving dishes" 则是菜。

第一版很朴素：告诉 LLM "你是 AI 助手，为给定查询生成两份清单，一份互补商品，一份替代商品"。结果看着不错，PM 也逐条审过，但上线后用户互动不如预期。原因还是 LLM 给的是常识答案，和用户真实需求不符，"protein" 的例子再次出现。于是他们在提示里加入 Instacart 的领域知识：一种是附上该查询的高转化类目以及查询理解模型的标注（品牌、饮食属性等）；另一种是附上用户搜完这个查询后接着搜了什么。加入这些后效果好了很多，互动和收入都大幅提升。

服务方式和查询理解类似：实时调 LLM 在延迟和成本上都不现实，所以用历史搜索日志批量调用 LLM，把查询、内容元数据乃至可能出现在轮播里的商品都存进特征存储，线上只做快速查找。

他说概念简单，但解决了三个难题：让生成内容和收入等业务指标对齐（反复调整提示和喂给 LLM 的元数据）；内容排序（传统的 pCTR、pCVR 模型不管用，改用基于多样性的重排等策略）；内容评估（既要检查没有幻觉，也要检查符合产品需求）。

三条经验

  • LLM 的世界知识对改进查询理解，尤其是长尾查询，帮助很大。
  • 真正带来顶线收益的是把 Instacart 的领域知识和 LLM 结合起来。
  • 评估内容和查询理解结果比预想的重要得多，也难得多。他们用 LLM-as-a-judge（让一个 LLM 给另一个模型的输出打分）来做，并坦言意识到这一点有点晚。

问答

有人问是否支持像 ChatGPT 那样的长自然语言查询。他们说之前上线过 Ask Instacart，能把"适合三岁孩子的健康食品"这类问题映射成具体的搜索意图（水果片等，"还有三岁孩子能不能吃爆米花"），再交给常规召回和排序。经验是：要往模型里注入大量 Instacart 上下文；要有健壮的自动化评估流水线；要把上下文传给下游，比如母亲节查询拆出的意图是香水时，下游要知道是女士香水，否则什么香水都会出来。

06. Devansh Tandon（YouTube 产品经理）：把 Gemini 改造成 YouTube 推荐模型

直播位置 3:06:42–3:31:50

Devansh 是 YouTube 的产品经理，在 Google 做推荐系统多年，和 DeepMind 一起搭建了一套用 Gemini 推荐 YouTube 视频的新系统。Eugene 介绍时提到，这一讲会讲他们怎样把多模态特征压成 token 做成语义 ID。

为什么推荐比搜索更值得关注

他说大家都在关注 LLM 怎样改变搜索：Google 搜索在变，ChatGPT 有聊天界面，很多人用 Perplexity。但推荐对用户是隐形的，所以被低估，而他认为 LLM 在推荐上的应用会是比搜索更大的消费级应用。YouTube 是全球最大的消费应用之一，大部分观看时长由推荐系统驱动，覆盖首页、观看下一个、Shorts，连很多搜索结果也有个性化。任何有十亿级日活的消费应用都是如此。

他把推荐问题描述为一个函数：输入用户和上下文，输出一组推荐。YouTube 拥有的用户信息包括人口属性（年龄、性别、地点）、最近 100 个看过的视频、互动深度、评论、订阅等。他们试过多头排序器、嵌入模型、序列到序列 Transformer 等很多方法。大约两年前，他们开始考虑在 Gemini 之上重建推荐系统，做出了 LRM（Large Recommender Model，大型推荐模型）。

流程是：从 Gemini 基础检查点出发，教它大量 YouTube 知识，得到 YouTube 专用的统一检查点 LRM；再针对检索、排序等任务对齐，为每个主要推荐场景做一个小的定制版本。LRM 已经在 YouTube 检索系统里上线一段时间，排序方面还在大量实验。

第一步：给视频做 tokenization，即语义 ID

理想产品是输入一串视频 token，输出一串视频 token 作为推荐。即使有百万 token 的上下文，要对很多视频做推理，也必须压缩视频的表示。在定下这个方案之前，他们试过先预测搜索查询再用查询检索视频，也试过直接推荐视频，都不够好。

语义 ID 的做法（他们去年发过论文，在 RecSys 会议上发表）：从视频中提取标题、描述、字幕文本，甚至音频和画面帧级数据，合成一个多维嵌入，再用 RQ-VAE（残差量化变分自编码器，把连续向量逐层量化成一串离散码）量化，给每个视频一串 token。他的说法是为 YouTube 视频这门新语言造原子单位。数十亿视频会围绕这些有语义的 token 组织起来：第一个 token 可能代表音乐、游戏、体育这样的大类，往下是具体运动，再到排球；两个排球视频共享前缀 token，最后有各自的唯一标识。这本身就是从哈希 ID 走向有语义的 ID 的一个里程碑，已在 YouTube 生产中使用。

第二步：继续预训练，让模型同时懂英语和"YouTube 语"

分两步。第一步把文本和语义 ID 联系起来：比如给出一个网球集锦视频的语义 ID，提示"这个视频的标题是……"，让模型学会输出标题；同理可以训练创作者、主题等。第二步让模型理解观看序列：用 YouTube 全部的用户观看路径数据，提示"用户看了视频 A、B、C、D"，遮住其中一些让模型预测，模型就学到哪些视频常被一起看。

得到的模型可以跨英语和视频做推理。他的例子：提示"视频 1 网球迷会感兴趣，因为讲温布尔登；视频 2 F1 迷会感兴趣，因为讲西班牙大奖赛；视频 3 数学迷会感兴趣，因为讲圆周率；视频 4 会让……感兴趣"，模型能补全"科技迷，因为讲 AI"，而它对视频 4 的了解只有语义 ID。

第三步：生成式检索

为每个用户构造一个提示，让模型解码出推荐视频的语义 ID。例子：一位在美国用 Android 的 24 岁女性，正在看奥运会集锦，有 50 条观看历史及互动情况。上线前的生产系统会推荐其他男子田径比赛；LRM 能把用户的人口属性和观看历史联系起来，推荐相关的女子比赛，这是以前推不出来的。对系统了解较少的用户，这种方式能给出独特的推荐。

主要发现：LRM 很强，学得快，训练数据效率高，能处理最难的推荐任务；最大的限制是服务成本太高，YouTube 有数十亿用户。第一批实验跑通后，他们花了大量时间压低 TPU 服务成本，降了 95% 以上才得以上线。

另一个办法是把问题变成离线的：用同样的提示和模型，只去掉个性化部分，生成一张离线推荐表，"如果你在看视频 A，接下来适合看这些"。一般来说非个性化推荐比不上个性化推荐，但因为 LRM 来自一个很大的检查点，它给出的推荐有差异化价值。他们对承载大部分观看时长的头部视频做离线推理，线上简单查表即可，完全绕开了服务成本问题。

为什么比训练 LLM 更难

  • 词表和语料规模：英语 LLM 的词表大约是牛津词典的 10 万词，每年新增约一千个；YouTube 有 200 亿个视频，每天新增数百万。
  • 新鲜度：模型不知道 2023 年度词 "rizz"，99% 的问题照样能答；但 Taylor Swift 发了新 MV，几分钟到几小时内就必须能推荐，否则大量用户会不满。所以 LRM 要以天甚至小时为单位持续预训练，而 Gemini 这样的经典 LLM 预训练大概三到六个月一次。
  • 规模：Gemini Pro 很强，但不可能服务数十亿日活用户，所以他们用 Flash 乃至更小的检查点，才能满足延迟和规模要求。

LLM 做推荐的三步配方

  1. 为内容做 tokenization：用丰富的特征建嵌入，再量化成 token，得到你自己的领域语言。
  2. 适配 LLM：设计训练任务，把英语和领域 token 联系起来，得到一个既懂自然语言又懂领域语言的"双语"LLM。
  3. 用用户信息构造个性化提示，训练面向具体任务或场景的模型，得到一个建在 LLM 之上的生成式推荐系统。

他说这是大约两年工作的"推文长度总结"。

未来方向

他认为现在的阶段是 LLM 在增强推荐，用户的信息流变好了，却不知道背后有没有发生 Gemini 推理。接下来，有了懂英语和推荐的双语模型，用户可以用自然语言和推荐系统对话，按自己的目标引导推荐，推荐系统也能解释为什么推荐某个视频，搜索和推荐的界限会变模糊。更远一步，推荐会和生成内容结合：推荐某个内容的个性化版本，甚至直接为用户生成只给一个人看的内容。他说这还有些距离，但会比大家预期的来得快。

问答

  • 怎样平衡学习语义 ID 和保留语言能力？他说这方面他们很挣扎。早期只关心推荐质量，过度训练语义 ID 语料后模型会"忘了说英语"，也许它在中间层推理，最后输出语义 ID。他们在尝试用混合专家（MoE），让一部分专家保留文本能力，另一部分专注语义 ID。随着要做用户输入文本的交互体验，他们会更偏向保留文本能力。
  • 冷启动嵌入有什么经验？语义 ID 的训练是完全无监督的，模型自己对视频库做量化，抽样看时会发现它学到了体育、影视娱乐这类概念，但没人教过它。因为有语义 ID，新视频可以热启动到有语义的空间里，过去一天或一周上传的视频推荐效果明显变好。
  • 画面帧怎么取？规模太大不能多取，他们尝试从关键时刻取帧，用的是播放器里显示的观众最集中的片段数据。能否识别画面里的小物体？很难说，所有视频信息最后压缩成 8 个 token，具体学到什么不清楚。
  • 预训练是否用到搜索查询，用户是否也有语义 ID？目前只给视频做了 tokenization，重点在观看序列，不在"搜索到观看"的路径。给用户做 token（比如代表最近 500 次观看）有过实验，进展较少，但他觉得是有意思的研究方向。预训练确实是在已有的 Gemini 检查点上做的。
  • 和传统推荐系统比提升多少？他说除了代码和指标什么都能讲，只能说这是他们近几年推荐质量上最大的一次提升。
