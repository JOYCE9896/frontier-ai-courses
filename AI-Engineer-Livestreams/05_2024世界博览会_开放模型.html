01. Mistral AI（讲者姓名未录到）：LLM 训练的三个阶段和 Codestral

直播位置 0:00:00–0:10:37（视频从演讲中途开始）

录像开始时讲者正在说：Mistral 的模型不是开箱就能做所有事，但社区会围绕他们的模型做各种定制和部署，他们也从社区学到模型能怎样用。接着讲者概述开源模型是怎样训练出来的。

预训练（Pre-training）

把文本一个 token 一个 token 地喂给模型，让它预测下一个 token。一个 token 大约是 0.75 个单词，词表规模是几万到几十万个 token，每个 token 用一个整数表示，并对应一个嵌入向量（embedding）。概念简单，实际很难：

  • 数据集是万亿 token 量级，构建要花大量功夫。很多人以为数据越多越好，但数据里的噪声会损害性能。
  • 模型有几百亿、几千亿甚至上万亿参数，每次训练花费数千万到数亿美元。你没有多次机会：训练出了问题，很难再拿到预算重来。
  • 小模型上最好的超参数不一定适合大模型。讲者展示了 Llama 1 系列的超参数表，问为什么 Llama 65B 是 80 层而不是 82 层，答案是“我们不知道”。很多决定靠直觉，不是精确的科学，最佳架构、最佳数据配比都还不成熟。

讲者用一个例子说明预训练模型的局限：让它“写一个判断质数的 Python 函数”，它会续写文本，举个例子、描述思路，但不直接给代码；如果输入改成一个 Python 函数定义加文档字符串，它就会写出代码。这说明模型其实知道答案，只是没有和人类偏好对齐。

指令微调和人类反馈学习

  • 指令微调（Instruction Tuning）：数据变成“提示词-回答”对，例如提示“写个 Python 函数”，回答直接是代码。训练目标仍是预测下一个 token，只是把提示词部分屏蔽掉，只对回答部分计算损失。通常用十万到几十万条指令。
  • 人类反馈学习：给一个提示词和两个回答，让人判断哪个更好，比让人从头写一个回答便宜得多，所以数据能扩得更快。两种主要技术是基于人类反馈的强化学习（RLHF）和直接偏好优化（DPO，直接用“更好/更差”的成对数据调整模型，不单独训练奖励模型）。

讲者说他们所有的开源模型都用了这些技术，没讲架构细节，只放了一张性能/成本图：横轴是激活参数量（和运行成本成正比），纵轴是性能，Mistral 的目标是在给定尺寸下拿到最好的性能。

Codestral 22B

  • 专门为代码训练的稠密 Transformer 模型，22B 参数，覆盖 80 多种编程语言。
  • 同时有指令（instruct）模式和中间填充（Fill-in-the-Middle，根据光标前后的代码补出中间部分）模式，所以既能像 GitHub Copilot 那样在编辑器里补全，也能像在 ChatGPT 里那样问 bug 和报错。
  • 讲者说它超过了 CodeLlama 70B、DeepSeek Coder 33B 和 Llama 3 70B，上下文窗口也比其他开源代码模型长，在多种语言上表现都更好。
  • 可以在 chat.mistral.ai 免费用，API 在 Mistral 的 La Plateforme 上，讲者记得免费到 7 月底；有 VS Code 和 JetBrains 插件可以当代码助手。

什么时候用开源模型

用闭源商业模型时，可以做提示工程、少样本提示（few-shot）、思维链（Chain of Thought）和 RAG，但通常不能微调；开放模型还可以微调。权衡在性能和成本之间：商业模型通用性能更高、上手容易；一旦进入生产或调用量大，经过微调的开放模型能在特定任务上胜过商业模型。讲者说常见路径是先用最强的模型做原型，确定要解决的任务后，再拿 Mistral 7B 或 8x7B 这样的开源模型微调。最后说 Mistral 在招人。

主持人随后提到，这和上午主题演讲里 llamafile 在本地硬件上运行模型的演示呼应，并感谢 Mistral 团队把这些昂贵的成果开源。

02. Rémi Louf（.txt）：用 Outlines 做结构化生成

直播位置 0:12:51–0:28:27

Rémi 是开源库 Outlines 的共同作者和共同维护者，也是 .txt（读作 dottxt 或 text）的 CEO 和联合创始人。他说自己的团队是比较传统的机器学习背景，出发点是一个简单的观察：大语言模型有根本缺陷。

问题：输出不可信

例子：从一堆邮件里抽取航班信息（出发地、目的地等）。你去用 OpenAI，把提示词写到极致、威胁模型、用函数调用，有时得到的仍然是 JSON 解码错误。他说这有根本意义：计算建立在接口之上，我们能搭出复杂的模块化系统，是因为能信任各段代码的 API；而 LLM 不能保证输出格式一致。结构化生成（Structured Generation，在生成时就强制输出符合指定格式）解决这个问题。

Outlines 怎么用

  • 它是一个 Python 库，可以直接嵌入现有工作流，不是框架。他说如果你在别的一些库里用函数调用，底层可能就是 Outlines。当时有 87 位贡献者，可能已经 88 位。他说一年前大家觉得他们谈结构化生成很疯狂，现在大家都跟上了。
  • 只专注开源模型，集成了六种模型后端，包括 Transformers、llama.cpp，以及最近加的 MLX；也接了 OpenAI，但主要用来和开放模型对比结果。
  • 第一步选模型并实例化；第二步用 generate.text 生成文本，可以设置遇到句号就停。
  • 正则表达式：问“Google 公共 DNS 服务器的 IP 地址是什么”，不加约束时模型会啰嗦几百个 token，答案埋在中间，你再用正则表达式去抽。Outlines 的做法是把这个正则直接拿来引导生成，模型只能输出符合格式的内容。他用 Mistral 7B 演示得到了正确答案。
  • JSON：可以用 JSON Schema 或 Pydantic 模型定义结构。回到航班例子，出发地和目的地可以进一步限定为三个大写字母的机场代码，结构能定义多细就定义多细。
  • 视觉模型：最近合并了对视觉模型的支持，他们用 Wikipedia 上一张菜品照片，让模型输出指定结构的 JSON。

原理

模型接收提示词（token ID），输出的是 logits，也就是下一个 token 的概率分布。生成时先经过一个 logits 处理器去调整它，平时用的温度（temperature）、top-k、top-p 采样其实都是在调整 logits；然后用采样算法选出 token。结构化生成就是在这里加一步：如果把某个 token 加到当前生成内容后会违反结构，就把它屏蔽掉。思路简单，难的是高效实现，这是 .txt 和 Guidance 等其他库的区别。

为什么没有理由不用

  • 大多数任务本来就是结构化的。他举 GSM8K（小学数学应用题基准）为例：格式总是“Q. 问题文本？”，答案里的算式可以用上下文无关文法描述，最后输出答案 6。
  • 保证格式有效。他放了一个梗图，讽刺大家为了拿到合法 JSON 写的各种疯狂代码，而且还不保证成功。一个实验（字幕里实验者名字不清）用 Mistral 7B v0.1 输出 JSON，只有 17% 是合法的；加上结构化生成后是 99.9%，而且提示词还没优化过。
  • 几乎没有额外开销。他对比了 Guidance 做结构化生成时的开销随生成 token 数的变化，Outlines 的开销接近零，代价是有一段编译时间，但推理过程中不会变慢。
  • 反而更快。JSON 的括号和字段名是事先知道的，不用让模型生成，他的简单例子里 10 个 token 只需生成 5 个。还有一种更隐蔽的加速：同一个 DNS 问题，ChatGPT 用了 50 个 token，结构化生成只要 8 个。
  • 提升效果，这是他说最让他们震惊的结果：在 GSM8K 上用 Mistral 7B v0.1 比较不同示例数（shot）。不加结构时，1-shot 比 8-shot 差，这符合预期；加了结构后，1-shot 的准确率和 8-shot 一样。他的解读是示例的作用可能主要是教模型问题的结构，而不是教任务本身，但还需要更多研究确认。
  • 提升开放模型的表现：在 Berkeley 函数调用排行榜（BFCL）的一个简单函数调用基准上，Microsoft 的 Phi-3 medium 不加结构是 86%，加了结构化生成是 96.5%，而最好的 GPT-4 版本是 93.5%。他说这说明开放模型今天就能超过更大的模型，社区还能从开放模型里挖出很多。

之后的方向

上面是他们大约一年前的工作。之后他们从正则表达式推广到上下文无关文法（Context-Free Grammar，可以描述代码、蛋白质结构或上面 GSM8K 那类格式），同样做到无额外开销。他们也在加语义约束，例如 Text-to-SQL：多数模型 SQL 语法没问题，错在编造表名和列名，内部已经能做到“完美”的 Text-to-SQL，他说不能保证查询结果是你想要的，但能保证查询能运行。他们还在把计算前移到模型结构里：既然要屏蔽 logits，模型为那些被屏蔽的 token 做的计算就白费了，可以提前省掉。这些会在接下来几周的博客里发布。

他的结论是：只要你做的不是聊天机器人，迟早会用上结构化生成。

03. Sandra Kublik（Cohere）：Command R 系列、RAG 和多步工具调用

直播位置 0:29:24–0:49:43

主持人介绍 Sandra 在 YouTube 上有一档播客。她从波兰华沙飞来，第一次来 AI Engineer，说从机场过来一路看到很多提到 AI 的广告牌，像回到家一样。她的开场问题是：如果给你一个擅长结构化高级 RAG 和顺序推理、能在本地运行、能和 GPT-4 Turbo 和 Claude Opus 竞争而且小得多的模型，会怎样。

时间线和社区反响

  • 3 月 11 日发布 Command R 并开放权重，它为检索增强生成（RAG，先检索相关资料再交给模型回答）优化，体量小，便于规模化。
  • 随后发布 Command R+，为工具使用（Tool Use）和高级 RAG 优化，发布几天内就登上 LMSYS 竞技场前列。
  • 两周内在 OpenRouter 上走红，在 Hugging Face 上下载 5 万次。Hugging Face 团队喜欢它的工具使用能力，用它做了 HuggingChat 的基础模型，里面有文档解析器、图像编辑器，还有计算器（她开玩笑说比 iPad 还早有计算器）。
  • 她说现在有将近 50 万开发者和研究者在用 R 系列。她点名的社区作品有 Daniel S 做的代码助手、一个叫 Complexity 的生成式搜索演示，以及支撑 Cohere Discord 社区的两个机器人，一个用来玩、展示能力，一个基于文档、专注 API 问题。

做 RAG 为什么难

  • 模型对提示词高度敏感。用于 RAG 时，模型既要知道去找信息、去哪找，还要分清和用户的对话历史与检索来的信息。
  • 模型天然偏向关注文档开头。她说多个 RAG 基准和“大海捞针”（needle in a haystack）测试都显示，模型会偷懒，关注开头而不是最准确的信息。
  • 预训练知识和提示词内容之间的拉锯。RAG 场景里要让模型调用参数里没有的知识，时效信息是典型例子，比如问现任美国总统是谁。

他们通过后训练优化模型行为：先判断是否需要外部信息（有时预训练知识就够了），然后顺利地操作检索系统、运行搜索查询、取回尽量准确的信息，再把它作为对话的依据。重点在引用（citations）：她说他们很看重引用，让用户能核实信息来源，所以花了额外时间把引用做得很细粒度，从而降低幻觉、可靠地使用上下文。在 KILT 等标准 RAG 数据集上，Command R 和 R+ 表现同级最佳，她说要达到这个水平，通常要串起一整条 LLM 流水线。

开源 Toolkit

用户反馈说为 RAG 和工具使用做 UI 很痛苦，他们自己也在这上面花了很多时间。4 月 24 日他们开源了这套界面，叫 Toolkit。她说很多人不知道。

  • 即插即用的组件，以及用 Next.js 写的界面应用源码，带一个保存对话历史的小 SQL 数据库。
  • 模型组件：可以通过云服务商、Cohere 平台、本地或 Hugging Face 访问 Command R 模型。
  • 检索组件：可自定义工具和数据源，内置一个基于 LangChain 的示例检索器，支持文档上传和网页搜索。
  • 功能包括对话历史、细粒度引用、文档上传、接入各种工具。

工具使用：单步和多步

她说企业场景下的工具使用是他们的主战场。这是 RAG 的延伸：先训练模型用好向量数据库和检索系统，再扩展到更广的工具使用，理想状态是零样本（zero-shot）使用任何工具。

  • 单步：适合只做一个动作或一组互相独立的动作，比如搜一份文档或发一封邮件。
  • 多步：一连串动作，每一步建立在前一步上，例如搜文档、和另一份文档比较、生成比较摘要、再用邮件发出。系统要能反思并纠错，模型要从不同数据源多次检索，形成一个循环。她说大家说“Agent”时，多数指的就是这个。

上周他们发布了多步 API。用户只需描述有哪些工具、做什么、有什么参数；用户发出请求后，模型制定计划，调用每个工具后反思结果，必要时调整计划，比如 API 返回错误就自动重试或重新规划。这些行为写在一个很长的多步 Preamble（预置提示词）里，放在 Hugging Face 上。她强调透明性：Command R 和 R+ 被训练成生成可通过引用核实的论断，能说明每个回答用了哪个工具。她说 Command R+ 的表现和 Claude Opus、GPT-4 Turbo 有竞争力，价格便宜 3 到 5 倍；在标准复杂推理基准上接近或持平 GPT-4 Turbo。

现场演示

  • Complexity（cplx.ai）：问“怎样提高演讲能力”，返回基于多个来源的答案，可以点开某条信息来自哪个网站去核实。
  • 内部 RAG 演示：给它一个难任务，“全球市值最大的三家公司是哪些、各有多少员工、画个图、起草一条推文”。界面里能逐步看到模型行为：先搜公司，再搜员工数，然后运行 Python 画图并加上引用。推文那一步当场没出来，她说之前跑通过。
  • Discord 机器人：问“AI Engineer 大会现在在进行吗”，它没找到这个会，找到了别的会议；换个问法还是不行。她说它支持多轮对话、记得上下文、会多种语言，包括她的母语波兰语。最后一次终于回答成功。

主持人随后宣布上午场结束，下午有 Liquid AI、Unsloth 等。

04. Leo Pekelis（Gradient）：构建金融专家模型：领域模型和长上下文

直播位置 2:36:37–2:53:45

下午场的第一位。Leo 是 Gradient 的首席科学家，题目是怎样训练成为“金融专家”的大语言模型。

两个观察

一是基础模型数量呈指数增长，不光 AI 公司，数据公司和通用科技公司都有自己的语言模型。二是上下文长度一年里大幅增长，一年前约 10 万 token，最近几个月发布的模型已经到更高的量级（字幕数字不清）。两者都说明大语言模型不是一个尺寸适合所有人，尤其是复杂用例，通用模型直接拿来用是不够的。

Gradient 的 AI Foundry

他们的 AI Foundry 是一组定制语言模型加一组工作流原语，组合起来为客户做定制方案。在金融领域，最有用的两个组件是金融领域语言模型和上下文长度扩展。他们曾写下金融应用对语言模型的六条要求，通用模型往往在这些方面不足，这场只讲其中两条，正好对应这两个组件。

为什么要领域模型

GPT 这类通用模型的训练数据广而不深，在技术性的金融信息上尤其明显。他引用一篇论文的图：即使是 1760 亿参数的模型，也要在预训练里见过上千篇相关文档，回答相关问题的准确率才能超过 50%。也就是说，问到训练数据长尾里的内容，模型会答得很差。自然的修法是给它补金融知识，但金融数据多到无法人工审阅，所以要做自动化数据流水线。

数据流水线和训练

  • 自动数据筛选是最有意思的一环，借用了成员推断（membership inference，判断某段数据是否在模型训练集中出现过）文献里的方法。先收集大量语料，然后对每篇文档估计它已经在基础模型（比如一个 Llama 基础模型）训练数据里的概率，过滤掉模型已经见过的部分。
  • 剩下的数据量小得多，可以人工审阅。
  • 再做合成数据增强，既用来上采样，也用来覆盖数据表示和格式上的变化。
  • 训练流程他说已经比较标准：先在 Llama 等基础模型上做持续预训练（继续做下一个 token 预测），再做对齐，包括监督微调和偏好优化。他的说法是，预训练像让模型读完一堆教科书，对齐像考试或做项目，教它怎样用这些知识。

长上下文和幻觉

幻觉（Hallucination）指模型生成与输入无关、编造或不一致的内容。很多研究把原因归到训练数据：数据过时；自动采集数据时的不一致和 bug 造成“来源与参考不一致”（source-reference divergence）等。这些会在模型的记忆里编码进不准确的信息。对齐和继续训练可以缓解，但 Gradient 发现最直接、最省样本的方法是上下文学习（In-context Learning，把信息直接放进提示词让模型当场使用），用少量信息就能在推理时补上训练数据的缺陷。

问题是用多了就会撞上上下文长度这个瓶颈：放少样本示例时，提示词空间比示例先用完，只能花大量时间挑示例或做有损的摘要；复杂问题需要脆弱的预处理流水线，每一步都可能出错；RAG 这类外部记忆在检索的块之间互相关联时效果很差，比如一个块需要引用前一个块才知道要不要查。所以最自然的办法是直接扩展上下文长度。

百万 token 上下文能做什么

  • 在提示词里直接放上千个示例，相当于在推理时现场做领域学习，能随问题灵活调整。他说很多任务要到上千个示例才能达到生产级的准确率。
  • 利用 Transformer 能关注提示词里每一个 token 的特点，让模型在各层注意力里隐式完成相当复杂的推理。他们做了一个实验：拿 Mark Twain 的书，删掉所有能识别作者的信息，放进上下文，让模型按同样风格写新故事。放到五本书作为参考后，生成的短篇能让另一个评判模型相信它们出自同一作者，相似之处除了文风和用词，还有主题、人物和场景。

他的结论是长上下文让系统更有依据、更稳健，组件更少，更多东西装在模型里，从而减少幻觉。

开源模型

他说 Gradient 重视透明、可验证的基准，也想回馈开源社区，所以两个方案都在 Hugging Face 上开源了模型：

  • Albatross（字幕作 “v-alpha-tross”）：在 Llama 2 基础模型上做金融领域训练的结果。在 Open LLM 通用基准上和同级模型有竞争力，在金融基准上更好。
  • 基于 Llama 3 的 100 万 token 上下文扩展版：在超过 100 万 token 的长度上“大海捞针”测试得分 100%；在 Nvidia 推出的长上下文基准 RULER 上比基础模型有明显提升，他说这让它进入 Gemini 1.5 Pro、GPT-4、Command R+ 等旗舰长上下文模型的行列。

05. Daniel Han（Unsloth）：修复开放模型里的 bug

直播位置 2:56:39–3:13:43

主持人开玩笑说 Unsloth 名字里有树懒，却让 LLM 跑得很快。开讲前有几分钟投影故障。Daniel 前一天做过一场三小时的工作坊，幻灯片在 tinyurl.com/unsloth，这场的幻灯片在 tinyurl.com/unsloth2。他说大家可能是因为 Gemma 的 bug 修复认识他们的：Gemma 是 Google 的开源模型，他们发现并修了其中几个 bug，比如激活函数应该用近似 GELU 而不是精确 GELU，还有分词方面的问题。Gemma 和 Phi-3 的修复都有博客和 Colab notebook。

Phi-3 的例子他简单带过：滑动窗口应该是 2048 而不是 2047；要把融合在一起的 QKV 矩阵拆开，否则 LoRA 微调效果不好。这场主要讲 Llama 3，他说一共有八个 bug，有些还没公开发布，这次算是预发布。

Llama 3 的问题

  • 不能有两个 BOS token。BOS（Beginning of Sequence）是加在序列开头的特殊 token。很多人微调 Llama 3 时不知道自己加了两个，训练时有两个、推理时只有一个，模板就对不上，推理准确率下降。Mistral 和 Gemma 也有同类问题。检查方法：用 Hugging Face 的 apply_chat_template 时，如果聊天模板里已经有 BOS，就不要再手动加一个。Unsloth 会自动检测并删掉多余的 BOS。
  • Llama 3 基础模型里有未训练的 token。保留的特殊 token（0 到 250 号）、轮次结束 token、header 开始和结束 token 在基础模型里没训练，在 Instruct 模型里训练过。他展示了各 token 嵌入均值的图，其中一些是零，他说 Llama 3 团队是有意把不用的 token 置零的。如果用 Llama 3 Instruct 的聊天模板去微调基础模型，这些 token 会让梯度出现 NaN，整个微调就坏了。修法是把它们设成已训练 token 的均值，但算均值时要先把未训练的 token 排除，否则比如有 1 万个未训练 token 混在分母里，均值就不对。另一种修法是训练 lm_head 和 embed_tokens。Unsloth 会自动处理。
  • PAD token 和 EOS token 不能相同。计算交叉熵损失时 PAD 会被屏蔽，如果两者相同，结束符也被屏蔽，模型就学不会停下来，会无限生成。他说 Phi-3 的这两个 token 就是相同的。Unsloth 会挑一个未训练的保留 token 当 PAD，没有的话就新增一个，并且确保新 token 和现有词表不重复（在名字里加额外的 # 号）。
  • 导出到 Ollama 时，Ollama 的聊天模板必须和微调时完全一致，以前很难做对，现在 Unsloth 会在微调时自动生成 Ollama 的 Modelfile。有两个 Colab：一个用 Alpaca 数据集，一个可以上传 CSV 文件。

社区贡献的发现

  • 转成 GGUF 给 llama.cpp 用时要用 CPU 转换，不要用 GPU。他认为原因是 CPU 和 GPU 做 float16 转换的精度不同。
  • llama.cpp 现在会对双 BOS 给出警告，请重视。
  • 加系统提示词可能让微调效果更好。有些人推理 Llama 3 Instruct 时根本没加系统提示词，可以试试带上。

Unsloth 的其他功能

  • GitHub 仓库里的“免费开始微调”按钮会跳到已经包含全部 Llama 3 修复的 Colab。
  • 持续预训练：可以训练 lm_head 和 embed_tokens，但这两部分的学习率要比其他部分低 5 到 10 倍。
  • 支持 4 倍长的上下文，只慢 1% 到 2%。用的是“卸载式梯度检查点”（offloaded gradient checkpointing），把梯度卸载到系统内存。他说有的系统卸载到硬盘，会很慢，应该先卸到内存；卸载调用必须是非阻塞的，否则也会变慢。

Colab 实操讲解

  • max_seq_length 决定能做多长的上下文微调，可以随意设，但应和数据集匹配，数据没那么长就别设太大。
  • load_in_4bit 做 4 比特训练，显存降到约四分之一。在免费 Colab 的 Tesla T4 上设成 False，显存会冲到 16GB，别这么做，除非 GPU 更强。
  • 模型名可以填任何 Hugging Face 模型名，不限于列出来的 Llama、Mistral、Gemma、Phi-3，他说很多人不知道这一点。
  • LoRA 的秩 r：默认 16，可以任意，一般建议 2 的幂，常用 16、32、64、128。秩越大学得越多，但可能过拟合、显存上涨，最大不要超过模型的隐藏维度（例如 4096）。
  • 目标模块必须包含所有线性层：q、k、v、o 以及 gate、up、down，少了效果就不是最优。
  • lora_alpha 设成等于或大于秩，他们发现设成秩的两倍效果更好；也可以开 rsLoRA 自动设置。
  • 梯度检查点设成 "unsloth" 就是上面说的长上下文方法，设成 True 也行但显存更高。
  • 数据准备用 Titanic 的 CSV 演示（根据年龄、票价、登船港口等预测乘客是否生还）。导出到 Ollama 或 GGUF 时只能有指令和输出两列，所以新 notebook 支持把多列合并成一列。
  • 可自定义聊天模板，必须包含输入和输出，并且要把模板重复写两遍，因为会有多出来的换行，重复两次是他们找到的解决办法，不这样做会报错。也给了 Llama 3 模板的写法。
  • 训练参数：建议 batch size 2、梯度累积 4，有效 batch size 是两者相乘，等于 8。显存只和 batch size 有关，想要大批次就加梯度累积步数。学习率 2e-4 或更小，比如 2e-5。
  • 推理用 apply_chat_template，注意双 BOS（Unsloth 已修）。保存到 Ollama 前要先装 Ollama，现在可以一次导出多种 GGUF 格式，以前每多一种要多等 10 分钟。自动生成的 Modelfile 可以直接复制到自定义 Ollama 里。

06. Maxime Labonne（Liquid AI）：微调 LLM 和模型合并

直播位置 3:14:33–3:33:26

Maxime Labonne 是 Liquid AI 的资深机器学习科学家（Staff ML Scientist），也是 Google Developer Expert。他写这些主题的博客，创建了在 GitHub 上很受欢迎的 LLM Course，向开源社区贡献过模型和工具，著有 Packt 出版的《Hands-On Graph Neural Networks Using Python》。他说上一场已经讲了不少微调，尽量不重复。

LLM 训练的生命周期

三个阶段：预训练用大量原始文本做下一个 token 预测，得到基础模型（base model），你问它问题它会接着补全问题而不是回答；监督微调（SFT）用问答对训练，训练目标类似，但结束后能回答问题、遵循指令；偏好对齐用人类偏好让模型按我们希望的方式表现，结果通常叫聊天模型（chat model）。

什么时候微调

他画了一张流程图：先尽量用提示工程，同时建立稳健的评测（Eval）体系，指标可以是准确率（必要时为小众用例做自定义基准，或复用开源基准）、成本、延迟。如果提示工程就够好，不需要微调。否则问能不能做出指令数据集，即问答对；做不出来，往往说明项目需要重新界定范围；做得出来，微调就是一个选项，并且可以复用之前的评测框架。非技术的答案来自 a16z 的一份报告：企业关心开源的两大原因是控制权和可定制性，可定制性主要就是微调。

微调库

除了 Unsloth，还有 Hugging Face 的 TRL（建在 Transformers 之上，易用）、Axolotl（很灵活，用大量 YAML 配置文件）、LLaMA-Factory（自带好用的图形界面）。

SFT 和偏好对齐

  • SFT 样本包括指令（系统提示词加用户提示词）和回答。例子：系统提示词“像对五岁小孩那样回答”，用户任务“删掉下面句子里的空格”。通常只在回答部分训练，其余部分屏蔽掉作为上下文。他说大多数 SFT 数据集用的是前沿模型生成的合成数据，这完全没问题，是构建高质量数据集的好办法。
  • 偏好对齐方法有 DPO、KTO、IPO 等，实践中直接偏好优化（DPO）最流行。数据格式是指令加一个被选中的回答和一个被拒绝的回答，目标是让正在训练的模型给被选回答的概率高于未训练的原模型。可以用来做审查（问怎么造炸弹，选中的回答是“作为 AI 助手我不能告诉你”），也可以用来整体提升表现。

怎样做 SFT 数据集

什么是好样本？他说人工评审在这件事上表现很差。他定义了三个特征：准确（事实正确，最好没有错别字，不要用错误信息损害模型知识）；多样（尽量覆盖多的话题和写作风格，取决于用例，做摘要就不需要那么通用）；复杂（这一点不那么显然，用需要推理的任务迫使模型推理，比如输出里带思维链，或者“像给五岁小孩解释”这类任务，难度高于能在 Wikipedia 上查到答案的问答）。

他的流程：先尽量从开源数据集开始并组合；然后去重，可以精确去重也可以模糊去重；再做质量过滤，可以基于规则（比如删掉所有含 “as an AI assistant I cannot” 的行，因为大家讨厌这种话），也可以用奖励模型或 LLM-as-a-judge（让一个 LLM 当评委给样本打分）筛掉差样本；再用 Nomic Atlas、text-clustering 这类工具做主题聚类、可视化数据集，找改进思路，回到数据生成，循环往复。

三种 SFT 技术

  • 全量微调：最基础，在指令数据集上训练整个基础模型，效果最好，但很低效。
  • LoRA（低秩适配）：冻结所有预训练权重，在每个目标层加上 A、B 两个小矩阵作为适配器，只训练这部分参数，快很多，但仍要把整个模型以 16 位精度载入。
  • QLoRA：把预训练模型量化到 4 位再套 LoRA，显存更省，但性能会下降，是一种权衡。

超参数

Daniel 已讲过很多，他只简要说。最重要的是学习率，和模型有关，要做几次实验；他建议尽量往高调，直到损失爆炸（他放了一张损失爆炸的图），再往回降。epoch 数取决于数据集大小。序列长度和 batch size 要权衡，上下文越长显存越大，但不需要用到预训练模型那么长。batch size 尽量大以充分利用 GPU。LoRA 的秩比较容易调。

模型合并

模型合并（Model Merging）是把多个微调模型的权重组合在一起，可以直接利用 Hugging Face Hub 上社区已有的成果。它不需要 GPU，效率很高，效果也很好。他说 Open LLM Leaderboard 当天早上刚更新到第二版，他还来不及换图，第一版上 7B 模型前八到前十名全是合并模型。合并模型之间还会再合并，形成巨大的家族树，他放的那张已经算小的。

  • SLERP（球面线性插值）：对两个模型的权重做球面插值，一次只能合并两个，但可以给不同层设不同的插值系数。他展示了一个自己用这种方法做的模型（字幕里名字不清）。
  • DARE：通过剪枝减少参数冗余，选出最重要的参数，并对源模型的权重重新缩放。优点是能一次合并多个模型，他推荐用七八个模型来合，效果很好。
  • Passthrough：把不同 LLM 的层拼接起来，也可以是同一个模型自己拼，叫自合并（self-merge）。他的例子是 Meta-Llama-3-120B-Instruct：把 Llama 3 70B Instruct 的若干层重复了几遍。他说照理这根本不该成功，模型完全没训练过，确实荒唐，但 Twitter 和 Reddit 上大家很喜欢，它特别擅长创意写作，也相当放飞，现在仍有很多人在用。这说明这些合并技术还有很多反直觉的东西可挖。
  • 混合专家（MoE）合并：传统 MoE 是从头预训练一个带路由器（router）和多组前馈网络层的模型。合并的做法是把不同微调模型的前馈层抽出来组合，再加一个路由器，称为 FrankenMoE。他的 Beyonder 模型用了四个源模型，分别是聊天、代码、角色扮演和数学模型。路由器本应为每个 token 每层选择用哪个前馈层，不想训练它的话，可以用“正向提示词”（positive prompts）算出嵌入，用这些嵌入初始化路由器，效果很好。他还做过 Phixtral，为此修改了代码以兼容 Phi-2，表现超过基础模型。但他说如果只是想提升性能，SLERP 和 DARE 比 MoE 合并更好，后者更实验性。Beyonder 在很多基准上超过了它的各个源模型。

他的 LLM Course 在 GitHub 上，所有 notebook 都能直接跑。

问答

一位听众提到他写过的 NeuralDaredevil 博客和其中用到的 abliteration（一种找到模型里与“拒绝回答”相关的方向并把它去掉的技术），说这也可以看作另一种无需训练的方法。Maxime 说 abliteration 可以叠加在上面所有技术之上，只是时间不够没放进幻灯片，现在把机制可解释性（mechanistic interpretability）技术用到这里也很有意思。主持人随后结束了开放模型专场。
