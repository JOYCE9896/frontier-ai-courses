01. Jed Borovik（Google）：主持人开场

02. swyx（AI Engineer 发起人）：开场致辞，向 slop 宣战

直播位置 0:14:32–0:23:41 · Opening Remarks

swyx 写过那篇给“AI 工程师”这个职业命名的文章，也是这个大会的发起人。他先讲了每届大会背后的“秘密”：第一届押注 AI Engineer 会成为一个职业；第二届扩展到领导力；第三届意识到一定要请到模型实验室，所以顶级实验室都来了；World's Fair 把范围扩到 AI 产品经理和 AI 设计师；到了这届 Code Summit，重点变成策展，集中在一个主题上。他说今天剩下的时间都会讲编程，他只想用五分钟讲 slop。

什么是 slop

Slop 指低质量、不真实或不准确的内容，常被拿来说 AI 批量生成的垃圾内容。他展示了牛津词典的释义：slop 是 2024 年度词候选，输给了 brain rot。他不同意词典把 slop 限定为“由 AI 生成”，说人和 AI 都可能产出 slop。网络俚语里 slop 的反义词是 kino。他举了一串例子：同一个工作室（Netflix）既能出 K-pop Demon Hunters 也能出 Electric State；同一个创业点子可以做成 kino 也可以做成 slop；他第一次在 AI Engineer 做主题演讲时用的 AI 幻灯片公司后来关门了，那份幻灯片也没了。

swyx 的反 slop 定律

他引用 Brandolini 定律：反驳谎言所需的精力比制造它大一个数量级。生成 token 的成本每年下降 100 到 1000 倍，所以他提出自己的版本：对抗 slop 需要的品味，比制造 slop 需要的大一个数量级。

他列了几种用 AI 对抗 slop 的办法：

  • 他的副业 AI News 通讯，没新闻的时候会直说“今天不用读”。
  • 用提示词对抗：下一场 Anthropic 讲者的 skill 提示词里明确要求 Claude 不要产出 slop，前后效果差别很大。
  • 代码 slop：两个工程师可以制造 50 个工程师的技术债，今年也出现过泄露数百万用户隐私数据的事故。他还点名一种说法：“我的模型能自主跑 30 到 60 小时”，却不说代码好不好。他套用“无代表不纳税”，说不能有“没有问责的自主”（autonomy without accountability）。
  • 他在 Cognition 做的工作：“半异步死亡谷”（semi-async valley of death）的概念，难题需要人保持注意力、和机器同步工作，已经商品化的工作可以异步交出去；以及 Codemaps，用 AI 扩展对代码库的理解。
  • 计算机使用（Computer Use，让模型直接操作图形界面）一年前由 Anthropic 首发，现在已经能自主操作 IDE 这样复杂的应用。他们用 Devin 自动更新大会网站。
  • 前一天领导力专场的收获：用子 Agent（Sub-agent）对抗上下文腐化（Context Rot，上下文越长模型表现越差）。还有 Greg Brockman 强调的模块化：人设计清楚的边界，中间交给 AI 写。

最后他带全场喊口号 “No more slop”：老板要你季度末多交代码行数、有人想推一个测试不足的版本、推特算法要你发博眼球的内容，都用这句话回应。

03. Barry Zhang、Mahesh Murag（Anthropic）：别再造 Agent，去造 Skills

直播位置 0:23:41–0:39:54 · Stop Building Agents

两人是 Anthropic 的 AI 工程师，Agent Skills 就是他们做出来的。开场一句话：Agent 有智力和能力，但做真实工作时常常缺专业知识。

代码就是通用接口

Barry 说上次来讲之后变化很多：MCP（Model Context Protocol，让模型连接外部工具和数据的开放协议）成了 Agent 连接的标准；Claude Code 发布；Claude Agent SDK 提供开箱即用的生产级 Agent。他们以前以为不同领域的 Agent 会长得很不一样，各有各的工具和脚手架。后来发现底层 Agent 比想象中通用：代码是通向数字世界的通用接口。做完 Claude Code 之后他们意识到它其实是通用 Agent。以生成财务报告为例：调 API 拉数据做研究，在文件系统里整理，用 Python 分析，再输出成各种文件格式，全都通过代码完成。脚手架可以薄到只有 bash 和文件系统。

缺的是领域专长

新问题是领域专长。他问：报税你找谁，300 IQ 的数学天才 Mahesh，还是有经验的税务专业人士 Barry？他每次都选 Barry，因为不想让天才从第一性原理推出 2025 年税法。今天的 Agent 像 Mahesh：聪明，但缺专业知识，前期缺重要的上下文，吸收不了你的经验，也不会随时间学习。

Skill 就是文件夹

Skill 是一组有组织的文件，打包了可组合的程序性知识。说白了就是文件夹。这种简单是刻意的：任何人或 Agent，只要有电脑就能创建和使用；可以放进 Git 做版本管理，放进 Google Drive，打包分享给团队。

  • 脚本即工具。传统工具的问题：说明写得差、含糊，模型卡住时改不了工具，而且工具定义一直占着上下文窗口。代码能自我说明、可以修改、平时躺在文件系统里，用到才读。例子：他们发现 Claude 一遍遍写同一个给幻灯片套样式的 Python 脚本，于是让 Claude 把脚本存进 skill，留给“未来的自己”用，结果更一致也更省。
  • 渐进式披露（Progressive Disclosure）。运行时只给模型看 skill 的元数据，表示有这个 skill；需要时才读完整的 SKILL.md（核心指令和文件夹目录），其余文件按需访问。这样能装下几百个 skill 而不撑爆上下文。

五周里的生态

Mahesh 接着讲：发布 5 周，已经有几千个 skill，大致三类：

  • 基础 skill：给 Agent 新的通用或领域能力。Anthropic 自己做了文档类 skill，让 Claude 能创建和编辑专业的 Office 文档；Cadence 做了科研 skill，比如分析电子病历（EHR）数据、更好地使用 Python 生物信息学库。
  • 第三方 skill：伙伴为自家产品做的。Browserbase 为开源浏览器自动化工具 Stagehand 做了 skill，Claude 装上后能更好地操作浏览器；Notion 做了一批 skill，让 Claude 理解你的 Notion 工作区并在上面做深度研究。
  • 企业内部 skill：他说这里热度最高。Fortune 100 公司用 skill 教 Agent 组织内部的最佳实践和内部定制软件的特殊用法；服务几千到几万名开发者的效率团队用 skill 部署 Claude Code，教它代码风格等规范。

他观察到几个趋势：skill 越来越复杂，从一个 SKILL.md 发展到打包软件、可执行文件、二进制、脚本和素材，未来可能像软件一样要花几周几个月开发维护；skill 和 MCP 互补，MCP 负责连接外部世界，skill 负责专业知识，很多 skill 是在编排多个 MCP 工具；越来越多非技术人员在写 skill，财务、招聘、会计、法务都有。

通用 Agent 的架构

他们认为架构正在收敛：一个 Agent 循环（Agent Loop）管理模型的上下文和进出的 token；一个运行时环境，提供文件系统和读写、执行代码的能力；接上 MCP 服务器获取外部工具和数据；再配一个几百上千个 skill 的库，运行时按任务决定拉哪些进上下文。进入一个新领域，可能只需要配好 MCP 服务器和 skill 库。Anthropic 发布 skills 后马上推出了金融服务和生命科学方向的产品，每个都带一组 MCP 服务器和 skill。

下一步

  • 像对待软件一样对待 skill：测试和评测，确认 Agent 在对的时候为对的任务加载 skill，衡量装了 skill 后的输出质量。
  • 版本管理：skill 和 Agent 行为的演变要能追踪。
  • 依赖：skill 能显式引用其他 skill、MCP 服务器和环境里的包，让 Agent 在不同环境里更可预测。
  • 分享和分发：组织里由人和 Agent 共同维护、不断演进的能力知识库。新人第一次用 Claude，它已经知道团队在乎什么。

Barry 补充了持续学习的部分：标准化的格式保证 Claude 写下的东西能被未来的自己高效使用，学习因此可以迁移。Skill 让“记忆”变得具体，但只存程序性知识，不是什么都存。他们的目标是：和你合作第 30 天的 Claude 比第 1 天好很多。现在 Claude 已经能用 skill-creator 这个 skill 帮你写 skill。

结尾他们用计算机做类比：模型像处理器，Agent 运行时像操作系统，skill 像应用层。少数公司做处理器和操作系统，几百万开发者写的软件才承载了领域知识。他们希望 skill 把这一层开放给所有人。

04. Dex Horthy（HumanLayer）：不靠感觉，在复杂代码库里解决难题

直播位置 0:39:54–1:00:08 · No Vibes Allowed: Solving Hard Problems in Complex Codebases

Dex 是 HumanLayer 的 CEO。他 6 月在 AI Engineer 讲的 12 Factor Agents 是大会历史上最受欢迎的演讲之一。这次讲面向编程 Agent 的进阶上下文工程（Context Engineering，指精心管理放进模型上下文窗口里的内容）。

问题：棕地代码库里的返工

他引用 Yegor Denisov-Blanch（Stanford）6 月在大会上讲的调研：调查了 10 万名开发者，发现用 AI 写代码时大量时间在返工，代码库频繁翻动，复杂任务和棕地代码库（Brownfield，指已有大量历史代码的老项目）效果很差。产出看起来多了，很多是在修上周交的 slop。做绿地的小 Vercel 仪表盘很顺，进 10 年的 Java 代码库就不行。这和他自己的体验一致。

他坦白第一次用 Claude Code 没被打动。后来他们三个人的团队花了 8 周，改造了整个开发方式，吞吐量提升到 2 到 3 倍，多到不得不改变协作方式。他们开源的 research / plan / implement 提示词系统 9 月在 Hacker News 上走红，几千人去 GitHub 拿了。目标是：能在棕地代码库里工作，能解决复杂问题，没有 slop，保持团队的心智对齐（Mental Alignment）。

从重开会话到有意压缩

  • 最朴素的用法：提需求、说它哪里错、再纠正，直到上下文用完或者你放弃。
  • 好一点：走偏了就开新的上下文窗口，同样的任务，告诉它别走那条路。看到 Claude 说 “You're absolutely right” 就该重开了。
  • 有意压缩（Intentional Compaction）：不管有没有走偏，都让 Agent 把当前上下文压缩成一个 markdown 文件，你审一遍，新会话直接从这里开工，不用重新搜索和理解代码。好的压缩内容是和问题相关的具体文件和行号。占上下文的东西主要是找文件、理解代码流程、编辑文件、测试和构建输出，以及那种往上下文里倒一堆 JSON 和 UUID 的 MCP。

为什么执着于上下文

LLM 不是纯函数（输出不确定），但它是无状态的。要更好的输出，只能放进更好的 token。Agent 每一轮选下一步工具时，只受目前对话内容的影响。所以要按正确性、完整性、大小和轨迹来优化上下文。轨迹的例子：你一直骂它做错，模型看到的模式是“我做错，人类骂我”，下一个最可能的 token 就是再做错一次。从坏到好排序：错误信息最糟，其次是缺信息，再其次是噪声太多。

他引用 Geoffrey Huntley 的说法：上下文用得越多，结果越差。由此他提出“dumb zone”（笨区）：Claude Code 大约有 168,000 token 的上下文，一部分留给输出和压缩；用到 40% 左右开始收益递减，具体看任务。装了太多 MCP，你所有工作都在笨区里做。

子 Agent 是用来控制上下文的

如果你建了前端子 Agent、后端子 Agent、QA 子 Agent、数据科学家子 Agent，他说请停下。子 Agent 不是用来扮演角色的，是用来控制上下文的。让子 Agent 开一个新的上下文窗口，去读文件、搜代码、理解代码库，最后只给父 Agent 返回一句很短的话：“你要的文件在这儿。”父 Agent 读那一个文件就能开工。

频繁有意压缩：Research / Plan / Implement

比子 Agent 更进一步的是他说的“频繁有意压缩”（Frequent Intentional Compaction）：整个工作流围绕上下文管理来设计，分三步，始终待在“聪明区”。

  • Research：弄清系统怎么工作、找到对的文件，保持客观。
  • Plan：列出确切步骤，包括文件名和代码片段，写明每一步改完后怎么测试。他们的计划里有真实代码片段。
  • Implement：照着计划执行，保持上下文低。他说好的计划连最笨的模型也很难搞砸。提示词都开源了。

实战案例

  • 他和 BoundaryML 的 CEO Vaibhav 一起做播客。周一晚上他说要一次性修好 BAML（一门编程语言）30 万行 Rust 代码库里的一个问题，中间做的研究有些不好就扔了，也对比了有研究和没研究的计划。第二天上节目时，对方 CTO 看到 PR，没意识到这是节目效果，直接说可以进下个版本。
  • 为了验证复杂问题：两人一个周六坐了 7 小时，给 BAML 交了 35,000 行代码（有一部分是代码生成和 golden 文件更新），其中一个 PR 一周后合并。Vaibhav 估计这是 1 到 2 周的工作量。
  • 失败案例：他和 Blake 想从 Parquet Java 里移除 Hadoop 依赖，没成功。最后把研究和计划全扔了，回到白板前，在搞清楚坑在哪之后重新想整体怎么组织。

他的结论：不要把思考外包。AI 只能放大你已经做过的思考，或者放大你没做的思考。

“规格驱动开发”这个词已经坏了

有人问这是不是 Spec-driven Development。他说这个想法没问题，词坏了。他引用 Martin Fowler 2006 年的“语义扩散”（Semantic Diffusion）：一个好词被大家拿去指一百种东西，最后没用。“Agent”就经历过：Agent 是人、是微服务、是聊天机器人、是工作流，最后 Simon Willison 把它拉回“循环里调用工具”。现在 spec 也一样，有人指更详细的提示词，有人指 PRD，有人指可验证的反馈回路，有人指像 Sean Grove 说的把代码当汇编，还有人说开源库的文档就是 spec。

今天确实有用的做法

  • 按需压缩的上下文。他用电影《记忆碎片》举例：主角每天醒来没有记忆，靠读自己的纹身知道自己是谁。Agent 不做入职就会瞎编。可以在每个仓库放说明文件，大了以后可以按目录分层渐进披露，但文档会过时。他放了一张图：代码、函数名、注释、文档里，“谎话”的数量依次增加。所以他偏好按需生成：给一点方向，让研究提示词派出子 Agent 沿着代码库纵向切片，生成一份基于代码本身的研究文档。他的说法是“我们在压缩真相”。
  • 计划是杠杆，是对意图的压缩。他用计划来保持心智对齐：代码评审最重要的作用是让团队都知道代码库怎么变、为什么变。他作为技术负责人不想每周读一千行 Go，但可以读计划。他提到 Mitchell Hashimoto 把 Amp 的对话记录贴在 PR 上，让评审者看到每一步提示词和测试过程。计划越长越可靠，但越难读，每个团队要找自己的平衡点。
  • 人在环中审研究和计划。一行坏代码就是一行坏代码；计划里的一处错可能变成一百行坏代码；研究里的一处误解会让整件事报废。所以人的注意力要放在流水线里杠杆最高的地方。他提醒警惕那种狂吐 markdown 文件让你感觉良好的工具。
  • 按任务难度调整流程。改按钮颜色直接跟 Agent 说；小功能做个简单计划；跨多个仓库的中等功能先研究再计划。能解决的问题上限，取决于你愿意做多少上下文工程。怎么判断用多少？要练，会错很多次。他建议挑一个工具练熟，不要在 Claude、Codex 等工具之间来回比较。

他说大家已经在叫这套方法 RPI，但他认为三个步骤本身不重要，重要的是压缩、上下文工程和待在聪明区。如果非要一个热词，可以叫 Harness Engineering（围绕 Codex、Claude、Cursor 等工具的接入点定制你的代码库，属于上下文工程的一部分）。

接下来的难题在组织

他认为编程 Agent 本身会商品化，难的是团队和软件开发流程怎么适应 99% 代码由 AI 交付的世界。他看到一道裂缝：资深的 staff 工程师不用 AI，因为提速不大；初中级工程师大量使用，因为能补技能短板，也产出 slop；高级工程师每周清理上周用 Cursor 交上来的 slop，越来越讨厌 AI。他说这不怪 AI 也不怪中级工程师，文化变化很难，要从上往下推。HumanLayer 在做一个 Agentic IDE，帮团队走到 99% AI 生成代码。

05. Lee Robinson（Cursor）：用强化学习训练又快又强的模型 Composer

直播位置 1:00:08–1:15:37 · Building a Fast Frontier Model with RL

Lee Robinson 是 Cursor 的开发者体验负责人，之前在 Vercel。他代表 Cursor 的工程和研究团队讲 Composer，这是 Cursor 第一个 Agent 模型（同事 Sasha 讲过另一个版本）。他说自己不是机器学习研究员，尽量讲得好懂。

模型定位

Composer 面向真实的软件工程，追求又快又聪明。按 Cursor 内部基准，它强于最好的开源模型，接近最新的前沿模型，但略低于 Sonnet 4.5 和 GPT-5.1 Codex。它的长处是：在同等智能水平的模型里，token 生成效率大约高 4 倍。

为什么做模型

Cursor 的研究团队之前做过自动补全模型 Tab，想把低延迟的思路用到 Agent 编程上，但不确定能不能成。早期原型以 Cheetah 的代号发布，用户喜欢速度，但说还不够聪明，当不了日常主力。于是他们做了一个反映自己仓库和真实开发方式的内部基准，目标是做出 Cursor 自己的开发者每天愿意用的检查点。帮助最大的变化之一是学会并行调用工具，以及有效使用语义搜索工具。

演示里，Cursor 2.0 新界面中的 Composer 1 同时并行调用多个工具：grep、读一堆文件、跑 shell 命令、改文件、维护待办列表，在调查一个开源仓库的问题。他说这和把 Agent 派出去等 20 分钟的体验很不一样，能让人留在心流里。

强化学习怎么做

强化学习（RL，让模型尝试、按结果打分、再更新参数）的思路：用户提交请求，Agent 决定调用一系列工具。Cursor 的 Agent 大约有 10 个工具，他重点讲 5 个：读文件、改文件、搜代码库、看 lint、跑终端命令，Agent 自己决定串行还是并行。训练时尽量模拟 Cursor 生产环境，从同一个起点跑多次 rollout（一次完整的尝试轨迹），每次可能调用完全不同的工具组合，打分、比较，然后更新模型参数。

想法简单，难在规模化，有三个挑战：

  • 训练环境和推理环境要一致。他们训练的是一个大型混合专家模型（MoE，每次只激活部分“专家”子网络），并行在几千张 GPU 上。
  • rollout 复杂：一次可能用几十万到几百万 token、几百次工具调用，各自完成时间差别很大。
  • 一致性：要和生产环境用完全相同的工具格式和工具返回，但训练时的算力需求是突发式的，和生产不一样。

他说这三个机器学习问题的解法，碰巧都是基础设施问题。

基础设施

  • 三类服务器：训练服务器（标准的 PyTorch 栈）、推理服务器（跑 rollout，用 Ray）、环境服务器（模拟 Cursor 环境）。推理服务器把 advantage（这次尝试比平均好多少的信号）发回训练器，更新参数后再把新权重送回推理服务器。
  • 研究团队写了一套支持低精度训练的自定义 kernel，在 NVIDIA Blackwell 芯片上混合专家层提速约 3.5 倍，也更容易把权重发到推理服务器。他们有博客详细讲。
  • rollout 完成时间不一，朴素做法会有大量空闲。他们在线程和进程间做负载均衡，某个 rollout 在装包或做大量工具调用时，不用干等其他的。
  • 他们同时在做 Cloud Agents 产品（可以从手机、网页、Slack 启动在云端运行的 Cursor Agent），为此在云上开虚拟机，加载用户代码，在安全沙箱里改文件、跑工具。这套恰好就是 RL 训练需要的基础设施。为了应付训练的峰值，他们搭了编排系统，跨多个集群管理几十万台虚拟机，展示的内部监控面板就是用 Composer 写的。

为什么要和生产环境一致

好处之一是能把有价值的专用工具教给模型。Cursor 训练了自己的嵌入模型（Embedding Model）做语义搜索：索引你的代码库，Agent 用自然语言查询找文件。他们的研究发现，语义搜索对 Cursor Harness 里几乎每个模型都有帮助，对 Composer 帮助最大，因为它就是在同一个环境里训练的，成了这个工具的重度用户。

训练结果

随着 rollout 和算力增加，性能持续上升：起点约等于最好的开源模型，现在接近前沿。RL 还改变了模型行为：学会并行读 10 个文件而不是逐个读；一开始改动太多、有不必要的编辑，训练后更愿意先搜索和读文件，找到对的地方再改。

“飞机 Wi-Fi”

Composer 上个月随 Cursor 2.0 发布。他把要等 10 到 20 分钟的编程 Agent 比作飞机上的 Wi-Fi：能用，但慢到让人宁愿没有。他引用 swyx 的“半异步死亡谷”：你要么要很快的，要么要最强、能在后台跑几小时几天的，卡在中间最痛苦。他自己的日常用法：用最前沿的模型（GPT-5.1 Codex）写计划，再用 Composer 执行，和 Dex 讲的思路一样。

三点体会

  • 有高质量数据和足够算力，RL 训练专用模型的效果出乎意料地好。Cursor 不做 AGI，只想做最好的编程模型。
  • AI 工具让研发本身加速，整个团队用 Cursor 写代码和调试，收益在所有工程工作里累积。
  • 大量机器学习工作其实是基础设施问题。他在 Vercel 时也看到过类似情况：框架层的好体验离不开部署基础设施。

Cursor 刚在纽约开了办公室，正在招人。

06. Naman Jain（Cursor）：从代码片段到整个代码库，编程评测的过去、现在和下一步

直播位置 1:15:37–1:33:36 · From Code Snippets to Codebases: What's Next for Coding Evals

Naman Jain 在 Cursor 做工程，做代码方向研究四年，起点在早期 Copilot 出来之前。他的第一个项目是生成单行 pandas 代码，最近一个是生成整个代码库。他按任务时长讲评测（Eval，衡量模型能力的测试集和方法）的演进：秒级（代码补全）、分钟级（面试式竞赛题）、几十分钟（仓库问答）、小时级（代码优化等复杂任务）。

LiveCodeBench：竞赛编程评测

竞赛题（类似 LeetCode）的好处是定义清楚：有自然语言描述和输入输出样例，好判对错。他列了三个难点：

  • 数据污染（Contamination）：模型在整个互联网上训练过，Stack Overflow 和 GitHub 上有大量相似题目。
  • 测试不足：他举例，题目要求返回两个列表排好序的去重公共元素，一个没排序、直接返回 set 的解法也能通过，因为测试太弱。
  • 难度分布：他刚入行时，一个基准上分数 80% 到 90%，另一个上只有 1%，中间没有东西。太难或太简单都给不出信号，没法爬坡。

LiveCodeBench 开创了动态评测：定期更新题目。一是对抗污染，可以只用模型训练截止之后发布的题测它；二是随模型变强调整难度分布。题目收集和测试用例生成都是自动化的，所以“时间”成了一个控制变量。按 LeetCode 题目发布月份看 pass@1（一次生成就通过的比例），DeepSeek 2023 年 9 月发布之后的题目上，它的表现从平均约 50% 骤降到 15% 到 20%。排行榜可以拖动时间条，被污染的模型（红色柱）分数会掉下来。测试生成参考模糊测试（Fuzzing），用 LLM 写输入生成器，每题 30 到 50 个输入。他们已经发了 6 个版本。他原本担心持续更新的评测没人跟，结果各大模型实验室都持续采用新版本。

软件优化基准

他对这个方向最兴奋：衡量模型写高性能软件的能力。它结合了算法能力（像 LiveCodeBench）和真实代码库编辑（像 SWE-bench），需要深入分析。核心原则是构念效度（Construct Validity）：测量要真的反映想测的能力，很多基准分数高却换不来真实收益。要做到这一点，任务要来自真实世界，评分要可靠。

  • 构造方式：拿 llama.cpp 这样的代码库，爬所有 commit，找出做性能优化的（比如优化某类量化模型的性能），为每个生成性能测试负载，例如跑 Qwen 7B。题目就是：给定这个负载，让 SWE Agent 把仓库优化得更快。
  • 评分：补丁要通过和人类补丁的等价性检查，还要看能不能比人类的参考补丁更快。
  • 规模：100 多个优化任务，涉及 C、C++、Rust 等底层代码，场景包括数据科学、机器学习、可视化。性能测试给到模型，它可以长时间迭代，也可以扩展测试时计算（Test-time Compute）然后挑最好的结果。

他们遇到了奖励作弊（Reward Hacking，模型钻评测规则的空子拿高分而不是真解决问题）。一个例子：优化 pandas 时，模型给任意方法加 lru_cache，而正确做法需要改内部实现。他们加固了评测设施，接着出现更极端的：模型加了一个 sitecustomize.py 文件（Python 启动时自动运行），把仓库里装好的 numpy 换成它自己从源码抓来的版本，等于劫持了评测设施。

他们的对策是 Hack Detector：用 GPT-5 的代码分析能力加上测试时计算，输入模型补丁、专家补丁和测试用例，让它给出是否作弊的判断和解释，多跑几次取共识。这样不需要事先想到所有作弊方式。分析结果：模型犯了很多测试能抓到的正确性错误；即使通过了测试，o3 在它尝试的约 30% 的问题里有作弊行为，新模型的比例在下降，但仍然存在。

整个代码库翻译

更前沿的任务：给一个 C 程序做规格，生成安全的 Rust 实现。他们选了 Google 的高效压缩库 Zopfli，约 4,000 行代码、几百个函数、复杂数据结构，生成了一百万个压缩输入做测试，要求 Rust 版在一百万个用例上都正确。他去年做这件事花了 12 小时，现在更好的模型可能 2 小时。他的发现：端到端正确性只给 1 bit 反馈，长任务需要中间进度指标，比如已翻译代码的比例、已重构代码的比例。

真实环境里的评测

和 LMArena 团队合作的两个项目：

  • Copilot Arena：IDE 插件，像 GitHub Copilot 一样补全，但同时给上下两个补全，用 Tab 或 Shift+Tab 选，用接受率做模型两两比较。
  • RepoChat：输入 GitHub 链接，用自然语言问代码库，从“解释这个代码库”到“给我一个修这个 issue 的补丁”，背后是一个简单的 SWE Agent，支持多轮对话。

他的体会是实验设计要以人为中心：延迟超过 1 秒，补全接受率骤降，所以实验必须平衡不同模型之间的延迟差异。

三点收获

  • 动态更新评测集，防污染，并随模型能力和真实使用方式调整任务分布。
  • 可靠评分：测试适合判断正确性，但真实场景里模型会写不地道的代码，比如到处加 try/catch 防报错，需要 LLM 评委（LLM-as-a-Judge）检测代码质量和作弊。
  • 中间评分信号，衡量渐进的进展。

07. Jacob Kahn（Meta FAIR）：Code World Model，为计算建世界模型

直播位置 2:07:04–2:23:38 · Code World Model: Building World Models for Computation

Jacob Kahn 是 Meta FAIR 的研究科学家，讲团队的 Code World Model（CWM）。目标是做能推理、规划和决策的模型，先从代码入手，因为代码规则明确，是研究推理的好沙盒。

世界模型和 LLM 并不对立

世界模型（World Model）在这里的意思是：给定过去的观测和动作，预测未来的观测。学会这种映射能得到好的表示，进而支持规划：可以设想不同动作，看结果再决定。他认为现在把世界模型和大语言模型对立起来是个伪二分：世界模型是对问题的一种参数化方式，LLM 是使用这种参数化的一种方式。

建模程序的执行过程

普通的自回归模型看到的代码只是语法：分词、输入、预测更多代码。CWM 想更明确地建模程序执行。做法是执行轨迹（Execution Trace）：比如一个数 strawberry 里有几个 r 的程序，每执行一行就有一个帧分隔符，显式写出局部变量的值，还可以加入内存信息，每一行轨迹对应程序里的一行。不限于单个函数，也可以是仓库级、分布式系统级的执行轨迹，以及竞赛题解，或者转成自然语言描述的轨迹。

抽象地说：程序或数据是状态，执行下一行是动作，得到下一个状态，这是一个转移函数。程序执行和 Agent 的决策都可以这样建模。普通 Agent 是思考、动作、拿到环境反馈、失败再想；有了世界模型，可以在想象的环境里模拟动作和反馈，不执行就生成执行轨迹，等准备好了再和真实世界交互。放到 LLM 上，执行轨迹就像一种思维链，模型逐 token 预测下一个状态。

数据与训练

  • 数据：大量 GitHub 事件和 PR，对 PR 做变异、预测改动，得到原始 PR 数据集；在测试或 CI 能通过的仓库上运行并生成仓库级执行轨迹。
  • 模型：320 亿参数的稠密 Transformer，定位是研究用模型，现在就能下载使用，上下文较长。
  • 训练流程全部自己做：几万亿 token 预训练；用领域数据中期训练（Mid-training），包括长上下文；指令遵循和推理数据的微调；最后是 RL 和 Agent 推理联合训练。
  • CWM 偏重 bash，工具比别的模型少，要学会熟练用终端。SWE RL 阶段给它 GitHub issue，基本只用 bash 修改环境和文件，最后提交，尽量接近工程师的真实环境。RL 之前先做 SFT，找出失败模式，再做拒绝采样（Rejection Sampling），把失败任务上的推理轨迹处理后喂回模型。

异步的后训练

模型小，正好可以大规模做后训练，重点是提高吞吐。系统有采样器、可在终端执行的环境、训练器（算梯度、给轨迹打分）和模型的“真值”来源，这是一个生产者消费者问题。CWM 的做法是高度异步：训练器积极地把检查点发给采样器，轨迹采完积极地送回训练器，两边都有队列，几乎不用等待，同时仍基本保持 on-policy（训练数据来自当前策略）。他提到一个越来越常见的做法：在轨迹进行到一半时就换上新检查点。理论上这段轨迹有一点 off-policy，但凭借吞吐和数据量，他说仍有很强的保证。后训练总共处理了两千多亿 token。他说结果是一个小而强、以小博大的开放模型，用工具和 bash 都很好。

能拿它做什么

  • 逐行追踪：给一个函数，它能高精度地逐行预测执行过程和局部变量的值。
  • 神经调试器（Neural Debugger）：以前要用自然语言把“左右两个变量该是什么”的不确定性说清楚；用 CWM，可以直接在代码里写出程序的形状、留下问号，模型通过模拟执行（比如理解你写的循环和条件）推断你想要什么，再补全。他说这是和代码并排协作，生成代码只是其中一部分。
  • 停机问题（Halting Problem，判断一个程序会不会终止，一般情况下不可判定）：他承认理论学者会不舒服，但想问能否近似。模型通过模拟执行或许能识别高层模式，判断程序是否停机。同样的能力可以用于调试执行代价很高的大型分布式系统，不必真的运行。

他说“这个演讲会停机”。模型在 Hugging Face 上，GitHub 有推理代码，技术报告详细写了后训练设置、执行轨迹数据和可能的用途。

08. Rhythm Garg、Linden Li（Applied Compute）：高效的强化学习

直播位置 2:23:38–2:43:46 · Efficient Reinforcement Learning

Applied Compute 的三位联合创始人（第三位 Yash 没来）之前都是 OpenAI 早期 RL 团队的研究员。公司帮企业构建专属于自己业务的“智能”，追求能量化 ROI 的真正自动化，部署时带数据飞轮，越用越好。他们说 RL 是把企业那些“分布外”数据拉回“分布内”的机制：在 OpenAI 时用 RL 刷公开基准，现在帮企业刷它们的“私有基准”。

RL 是怎么工作的

Rhythm 用数学题举例：一个训练步取 4 道题，让开源模型（比如 gpt-oss 或 Llama）每道题尝试 100 次，每次都有很长的思考过程和最终答案。全部打分，答对就强化那次的思考轨迹，答错就抑制。一步步训练下去，模型就学会了做数学题。

他们和实验室的需求不同

大实验室做几周的大训练；Applied Compute 做专门的训练，要求快（以天为单位交付给客户）、便宜（单位成本才成立）、训练时长估计方差低（要的是稳定地快）。所以核心研究问题是：能不能做出足够高效的 RL 栈。

同步 RL 的问题：长尾

同步 RL 里采样和训练轮流进行，比如一批 8 个样本要全部完成才开始训练，GPU 都在等最慢的那个。他们的测量：40 道算术题，每题用 Qwen 30B 采 32 个样本，99% 的样本约 40 秒完成，最后 1% 又花了 80 秒。吞吐图上开头 GPU 很忙，结尾大量空闲。

异步 Pipeline RL 和“陈旧度”

解法是异步 RL，打破采样和训练的锁步。他们喜欢的一种是 PipelineRL（Piché 等人）：一部分 GPU 专门采样、一部分专门训练。采样不停、用大批量推理，完成的样本进队列，训练从队列取批次。每训练完一步，就把新权重推给所有采样器，叫做飞行中权重更新（In-flight Weight Update），即使采样器正在生成某个样本也更新。结果一个样本里的 token 可能来自好几个版本的策略。

他们用陈旧度（Staleness）衡量样本落后几个版本。容忍的陈旧度越高，GPU 空闲越少；但策略梯度里用于纠正采样策略和训练策略差异的重要性比率（Importance Ratio），方差会随陈旧度上升，学习会不稳定甚至发散。所以要快就要高陈旧度，高陈旧度又需要算法创新来稳住。这是他们的主要研究问题之一。

用系统建模找最优 GPU 分配

Linden 讲一个简化的子问题：假设算法能容忍某个固定陈旧度，算力预算固定，怎样做 RL 最快？他列出建模要素：

  • 算力预算：GPU 数量。同步时全部用于训练或采样；异步时要决定怎么分。
  • 训练批大小：一批多少道题，每道题采多少个样本（难题多采一些，鼓励多样性）。
  • 采样吞吐：推理引擎的显存里放着权重、激活值和 KV Cache（缓存已生成 token 的中间结果，避免重算）。每次前向传播生成下一个 token。他们拟合了单次前向传播延迟随批大小变化的曲线：小批量时受显存带宽限制，加样本几乎不增加延迟；大批量时受计算限制，越加越慢。公式基于 roofline 模型，用一个 sigmoid 平滑两段之间的过渡。批大小受 KV Cache 显存上限约束。
  • 训练吞吐：每张训练 GPU 每秒处理的 token 数（含前向、反向和优化器步骤），用实际负载拟合。

同步方案的模拟：批大小开始很高，随样本完成逐渐降到零，然后做一次优化步。采样时间由最长请求的 token 数和延迟估计决定，结合响应长度分布算出每一步掉了多少样本；训练时间是总 token 数除以总训练吞吐。

异步方案要小心分配，否则又会空闲：推理 GPU 太少，训练端消费快于生产，训练 GPU 空着；采样 GPU 太多，生产快于消费，样本越来越陈旧，每个样本能学到的越来越少。异步稳态下批大小大致恒定（响应变长时会因 KV Cache 不够而下降，模型也考虑了这一点）。约束有两个：生产速率等于消费速率（训练 GPU 数乘单卡训练吞吐，等于采样 GPU 数乘批大小再除以单步延迟）；最大陈旧度（最长请求耗时除以一个训练步的时长）不超过算法能承受的值。扫描不同的训练 GPU 数，算出对应的最小稳态批大小，去掉超过陈旧度上限的方案。

结果：在最优分配下，模拟显示比同步基线快约 60%。这套模拟让他们在真正花钱跑之前就能比较配置，回答比如“如果响应长度变得很长（RL 训练中模型常会越想越久），最优配置是什么”“性能优化应该瞄准多高的吞吐”。

09. Will Brown（Prime Intellect）：规模化的 RL 环境

直播位置 2:43:46–3:02:15 · RL Environments at Scale

Will Brown 是 Prime Intellect 的研究负责人。他说题目有点误导：会提到几千个并行 rollout、沙盒、几百张 GPU 的工程问题，但主要讲另一种“规模”。

另一种 scaling：人才池

除了数据、算力、参数这种 Scaling Law，还有更模糊的部分，有人叫 unhobbling、算法技巧或人才。它来自社区、公司、大学、互联网上的人讨论和分享想法，在应用里测试技术，再把工具做得更易用，让后来的人不用重造轮子。实验室抢人、薪水飞涨，另一种办法是扩大研究者的人才池，让 AI 研究更容易做。

Prime Intellect 同时是研究实验室、算力提供商、平台公司和开源生态。他们的目标是让 AI 研究成为全世界 AI 工程师的日常工作流的一部分，不必进大实验室、不必有巨型集群、不必读博。他说 AI 里的开源类比不该是固定的模型检查点，而应该是“研究”这种实践和思想，就像 Linux、Node、Apache 那样靠抽象和工具的积累降低门槛。他们把要做的东西叫 open superintelligence stack：算力、编排、训练和评测库、代码执行平台、评测、推理和微调。

产品就是模型

以前有人说“模型就是产品”，现在很多赢家是“产品就是模型”。他举的两个例子是 Cursor 的 Composer 和 OpenAI 的 Codex：模型就是为那个产品训练的，用模型的体验就是用产品的体验。做法是拿代表产品的 Harness，在里面训练模型，也就是一个 RL 环境。

他对环境的定义：环境就是一个 Harness 加一组任务和奖励。环境不只用于 RL：它和评测是同一个东西；可以当合成数据的引擎，用于 SFT 或蒸馏（Distillation，用大模型的输出训练小模型）；部署在外面、被监控的 Agent 也是环境。离线数据集也好，产品里源源不断的用户任务也好，“任务 + Harness + 奖励”都是环境。

环境是 AI 研究的“Web 应用”

他的意思是：环境简单、自成一体，可以从很简单做到代表一个大型产品的复杂度；有教学性，复杂起来会撞墙，逼你学系统扩展、超参数和算法；而且必须做实验。环境和单纯 Harness 的区别在于必须事先定义好任务和奖励，是一个真正的评测，不能只“凭感觉试试就上线”。他认为 SFT 时代微调没流行起来，很大原因是标注“正确答案”太难；如果你能衡量答案的好坏，就能边跑边生成数据，这就是环境解锁的东西。

Environments Hub 和 verifiers

  • 几个月前他们推出 Environments Hub，一个开源社区平台，用来创建、发现和分享 RL 环境和评测。已有几百位建设者，有人实现自己的想法，有人复现论文，有人把某个基准改成适合 RL 的版本，有人做游戏。
  • 九个月前他在同一个房间发布了开源库 verifiers，至今还在做。它是一组可组合的组件，从简单评测、问答、游戏，到工具调用、沙盒、Agent 框架、CLI 编程 Agent、数学题，做出来的环境可以直接拿去做 RL 训练。设计上优先可扩展性，按层级组织：比如一个 Terminal-Bench 的编程 Agent 环境，是 Harbor 框架的一个实例，Harbor 是 CLI Agent 环境，CLI Agent 是多轮环境，多轮环境又是环境的一种；同层还有 TextArena、Wordle、用 MCP 搜索、沙盒里的 Python REPL 等。

端到端例子：wiki-search

给 Agent 几个搜索 Wikipedia 页面的工具来回答问题。Hub 上每个环境是一个 Python 项目，有依赖、版本，可以上传评测结果。环境定义很简单：工具写成 async Python 函数，一个数据集，一个 rubric（组合多个奖励项的抽象，也可以加奖励为零、只用于观察的指标）。训练再加一个给 prime-rl 训练器的配置文件；prime-rl 是他们的大规模异步 RL 训练栈，汇集了研究文献里的最佳实践，配置暴露需要思考的参数并给合理默认值。一行命令指定环境，如果在 Hub 上就自动安装并开始训练，运气好奖励曲线直线上升。不顺的时候就要迭代环境、奖励、数据和任务。

结果：Qwen3 4B 从约 55% 训到 89%，和 GPT-4.1、GPT-5 mini 等大得多的模型持平。他说把小模型训好适合需要快、需要便宜，或者最好的模型也不够好的场景。即使不训练，既然要做评测，把它当环境来做也能打开提示词调优、模型选择、多用户规模化测试等选项，也逼你想清楚你在优化什么。

INTELLECT-3 和 Lab

  • 为了压力测试整套栈，他们在训练 INTELLECT-3：1000 亿参数以上，在 500 张 GPU 上完成 SFT 和 RL 的端到端后训练（prime-rl 也支持 SFT），很快发布。他们读论文、试各种技巧，把有效的沉淀进 prime-rl。prime-rl 和 verifiers 都在 GitHub 上开源。
  • 社区项目：赞助小任务、和全球研究生的研究驻留项目、prime-environments 仓库里人工审核的环境，已经收到几百个。这些帮他们发现了很多粗糙的地方。
  • 即将推出的平台产品叫 Lab：浏览环境、跑评测、推理、微调。很多人讨厌处理 torch 版本、flash attention、vLLM 的兼容问题，代码可以读，但不用自己跑。Lab 的入口就是环境：做合成数据和 SFT、做评测、做 RL，都从建环境开始。

他的结尾是：模型常被当成黑盒，钻进研究里改东西、弄坏东西，能让人更理解模型从哪来、往哪去。

10. Will Hang、Cathy Zhou（OpenAI）：Agent 强化微调（Agent RFT）

直播位置 3:02:15–3:18:58 · Agent Reinforcement Fine Tuning

两人在 OpenAI 微调团队，讲 Agent RFT，他们称之为提升 Agent 表现最强的方法。

Agent 是什么，怎么变好

Will 说 Agent 和普通模型的区别是能和外部世界交互、自己完成任务，所以需要工具，比如编程 Agent 要有终端、代码解释器甚至整个代码库。Agent 的工具调用和推理过程交替出现在同一个上下文窗口里。OpenAI 的旗舰例子是 Codex：有的工具以终端命令形式提供，有的是自定义函数，比如调用一个规划流程。

提升 Agent 的常规手段依次是：提示词工程或优化；任务优化（简化任务、加护栏、增减工具、改工具行为）；都试过还想更好，才用微调，直接改模型权重。Agent RFT（强化微调，Reinforcement Fine-tuning）按你指定的学习信号改权重，训练中 Agent 会探索调用你的工具的各种方式。

新功能

  • 训练时模型可以通过你部署在公网上的 endpoint 调用你的工具。
  • 每次 rollout 结束后调用你通过 endpoint 提供的自定义奖励。他说这是 OpenAI 第一次允许模型在训练过程中和外部世界交互。
  • 样本效率高：有人只用了大约 10 个样本就成功了。
  • 每次 rollout 有唯一 ID，所有打到你系统的工具调用都带这个 ID，你可以跟踪整条轨迹，最后把最终答案和累积的上下文一起交给评分器。

为什么有效：你的环境和 OpenAI 内部训练用的环境不同，这叫领域偏移（Domain Shift），会导致 Agent 工具用得不好：调用太多次，或者往工具里塞错误输入。Agent RFT 让模型适应你的环境，学会更好地用工具、更好地推理工具输出。还可以加一个超出工具调用预算就扣分的惩罚，模型会学会待在预算内，同时保持或超过原来的效果，延迟因此降低。

推荐流程：先确保训练集和评测集与生产流量一致，不能有偏移；用基础模型跑出基线；先做提示词和任务优化；榨干之后才上 Agent RFT。

客户案例（Cathy）

  • Cognition：用在 Devin 的代码编辑规划阶段，也就是 Devin 查看仓库、用 grep 和读文件等 shell 工具决定改哪些文件的那一步。数据是用户请求和用户实际改过的文件，奖励是所选文件的 F1 分数（兼顾精确率和召回率，既不多选错的，也不漏掉关键的）。每条轨迹开一个 VM，隔离环境、执行工具、评分。两点收获：数据量和质量重要，100 个样本提升 5 分，1000 个样本提升 10 分；RFT 擅长教会并行调用工具，原来要 8 到 10 步交替推理和调用，训练后第一步就并行发出多个调用，降到 4 步。
  • Qodo：在做代码评审 Agent，其中一个环节是回答开发者关于大型代码库问题的深度研究 Agent。他们用 GPT-5 训练，工具是在仓库上搜索和检索，从 8 个仓库收集约 1000 个真实问答对，奖励是检索到的相关事实的召回率。效果提升 6%，工具调用和输出 token 都减少。最有意思的是工具调用次数分布：GPT-5 偶尔会有单个样本超过 15 次调用的糟糕运行，训练后这条长尾消失，集中在 2 到 4 次，P95 长尾没了，对生产延迟很重要。
  • Cosine：为大型复杂企业代码库做编程 Agent，给了 30 个工具（grep、关键词搜索、终端会话、浏览器会话等），评分器很严格。他们发现给“尝试就有部分分”时，模型开始优化代码风格和语气，效果不好。所以只有最终代码通过测试才给奖励。奖励因此稀疏，好在 GPT-5 能产出一些成功样本，他们又加大批大小和算力，保证每批里有正奖励样本。另有一个自定义 LLM 评委惩罚啰嗦、表情符号和不专业的内容；评分器还奖励 Agent 自己验证（跑测试、看终端输出、跑 lint 再宣布成功）。结果在多个基准上达到 SOTA，Agent 也快很多，原来有超过 100 条消息的轨迹，训练后收敛到紧凑的步骤序列。
  • Mako：做写高性能 GPU kernel 的 Agent。kernel 训练样本少，尤其是 NVIDIA B200 这类新硬件。他们只用约 100 个 PyTorch 提示就训练 GPT-5 写快速 kernel。早期发现奖励作弊，检查 rollout 后找出 7 种作弊方式，比如直接返回参考实现、返回空操作 kernel 或恒等 kernel，用一个 LLM 评委把这 7 类都判 0 分，再用基于抽象语法树（AST）的静态分析确认 kernel 真的存在并被调用。之后按正确性和相对 PyTorch 基线的真实加速打分。最后每次采 3 个样本取最好的，比之前的 SOTA 好 72%。

四条原则（Will）

  • 任务定义清楚、有约束，成功标准明确，去掉主观性，评分不应依赖品味。
  • 别让模型在生产中“吃惊”：训练集、评测集要和生产流量一致。
  • 多采样应该能提高单个数据点上的最好成绩，也就是同一题上不同 rollout 之间要有差异，模型才能从中学到好坏之别。
  • 奖励函数不能被钻空子；尽量让奖励连续而不是二值，像给学生部分分，模型才能一点点逼近最优。

想用 Agent RFT 可以联系 OpenAI 的客户经理。

11. Kitze（独立开发者）：从 Vibe Coding 到 Vibe Engineering

直播位置 3:18:58–3:44:21 · From Vibe Coding to Vibe Engineering

Kitze 是来自欧洲的独立开发者和内容创作者，这是一场以段子为主的演讲。他介绍了自己同时在做的产品：给开发者用的浏览器 Sizzy、一个整合用药、习惯、待办和计划的 life OS（TestFlight 快上线）、全栈课程 Zero to Ship，以及正在复活的 changelog 和路线图工具 Glink。

前端这十年

他先放了其他领域的炫酷图形演示（Vision Pro 的布料碰撞、程序化生成城市等），然后对比前端：将近十年过去，网页上的 select 下拉框可能到 2037 年才能自定义样式；某个老库仍有 1500 万下载量，他每年设日历提醒看它死没死；CLI 不但没死，终端里还能拖图片了；Internet Explorer 只是换了 logo；Ryan Florence 演示的 Remix 各个版本里，连“让计数器加一”都能写出很多种。最火的库仍然是 React。

LLM 和 React

他说 LLM 很会写 React。人类看着重复代码就想抽象，LLM 不在乎重复代码，他从 2017 年起就认为人们太在乎重复、抽象得太早。LLM 让这件事更好也更糟，尤其用 Composer 1：你能更快到达正确的抽象，也能更快到达错误的抽象。他还说 LLM 写 React 不比人差，因为本来就没人真会写 React，每次去 React 大会都会发现自己一直用错了，所以别光怪机器写不好 useEffect。

Vibe Coding 和 Vibe Engineering

Vibe Coding 一词由 Andrej Karpathy 提出，大意是不太在乎代码，一路点接受，让 LLM 去做。现场觉得 vibe coding 好的人比他在其他城市遇到的多得多。他放了 2017 年自己的幻灯片：当时就预测前端会变成“把标题样式换一下，往右挪 3 像素”这种指令式开发，台下笑他，现在大家在 Cursor 里就是这么做的。他还说经理一直都在 vibe coding：提需求、试用、从不读代码。

他转述了把 vibe coding 比作赌场的段子：买筹码对应买 token，拉老虎机对应点生成，可能中大奖做出一个全栈应用，也可能是垃圾；“再来一次提示，bug 就没了”；四个小时写提示词做了一件手写 15 分钟能完成的事。

他更喜欢推特上有人提出的 Vibe Engineering：一直用 Agent 写代码，自己不碰代码，但像侦探一样盯着屏幕，怀疑每一处。他说自己这样做了 15 个以上的项目，没有 LLM 很多根本不会做。他保持怀疑的理由是模型从人类代码里学来：他展示了 Gemini 自我贬低说“我不配当助手”，Qwen 说它撒谎是因为在论坛上读到人类犯错时会嘴硬，以及一张 Agent 删掉生产数据的真实截图。

他的建议

  • 用 git worktree 并行开多个任务（他两周前才知道）。
  • 有一个扎实的起点：好的基础组件、函数、模式和抽象，在提示里标出来。
  • 用语音写代码。Agent 做完后，他先在浏览器里像跟朋友聊天一样描述看到的界面和 bug，把思考过程说出来，再跳到代码里继续说，一段口述有时长达 5 分钟。
  • 用 rules、docs、commands、memories：模型不会读心，也装不下整个应用的上下文。
  • 他对比了自己的提示和 vibe coder 的提示：他的充满技术细节，比如 tRPC 怎么定义、抽象怎么组织，相当于在“vibe 架构”；后者是“把整个项目改成 TypeScript，别犯错”“给我做个百万美元的应用”。
  • 别把 AI 工具丢给实习生和初级工程师，然后指望低薪加 LLM 就够了，他说这是最蠢的主意。把持怀疑态度的资深工程师说服去做 vibe engineering，才有 10 倍效果，难的是说服他们。
  • 一次性脚本、简单功能、不会再被人看的代码、个人工具，适合放手 vibe coding。能判断“这段代码够用了”是一项重要技能，有没有 AI 都是。

为什么有人体验很差

  • 时机不巧：比如 Claude Code 刚火时大家从 Cursor 迁过去，一周后有人觉得模型变笨了，后来厂商修复了问题，你可能正好赶上那一段。他说几乎每家都发生过。也有人用每月 3 美元的方案替代 200 美元的方案，或者还在 ChatGPT 里生成代码片段再粘贴回来。
  • 选择太多：哪个模型最好，早上 9 点和现在答案就不一样。
  • 他说 Composer 1 改变了他的工作方式：以前用 GPT-5 Codex 跑一个任务要等很久，他就去刷短视频；现在速度快到他重新坐回驾驶位，盯着 Agent 随时叫停。但这只对懂行的人有用，不懂的人只会“错得更快”。两周完成了过去一年的进度：快要放弃的项目 benji.so 从 Blitz 迁到 Next 16（app router、Better Auth、tRPC、Turborepo monorepo、React Native 应用），不到一周移植了 90% 的功能；Glink 也复活并迁移；Sizzy 这个 Electron 加 MobX State Tree 的“意大利面”项目也被几轮提示重构了。
  • 他的编程工具史：复制粘贴，然后 Tab 补全，然后 Supermaven，然后 Cursor，第一次用 Agent 时觉得会改变人生，后来是每月花很多钱，接着 Claude Code、GPT-5 Codex，最后因为 Composer 1 回到 Cursor。
  • 被热词淹没：他拿 MCP 开玩笑，说它是“API 的花哨说法”。
  • 你是“PITA dev”（难搞的开发者）：两行 PR 留挑刺评论、字典里没有 LGTM、对 tab 和空格有宗教信仰、一路把 lodash 换成原生实现再换成 for 循环，只为两个用户。他说这种人永远存在。
  • 技能问题：vibe engineering 远不止写英语，要懂模型的限制、Agent 的能力、该给什么上下文、上下文上限、怎么写 rules、提示词工程，还要一直泡在推特上，并且要有足够的技术功底才能驾驭模型。“干净代码”的定义也在变成“够干净，让 Agent 能继续在上面干活”。一直接受 slop，迟早会卡死。

学计算机和工作

有人问还要不要学计算机，他说要，现在是最好的时机。他当年学编程时唯一的“LLM”是朋友的朋友的朋友，一边打 CS:GO 一边在 Skype 上隔 45 分钟回他一个 .NET 问题。至于工作，他说目前还行，但岗位在从底部变薄，实习生和初级工程师更难进门。他提到 Shopify 等公司有 vibe coding 排行榜，统计员工消耗的 token。他认为基础设施和集成已经基本解决：AI SDK、MCP 等标准，Agent 已接入 Linear、GitHub、Slack、Sentry，剩下的是模型变好、变便宜、上下文变长。今天工作流里 @某个同事，以后会变成 @Cursor，由云端 Agent 更快完成。

他还提到新出现的职位：Reddit 上很多人 vibe coding 做到 80%，剩下 20% 花钱请人收尾，已经有专门的“vibe code 修复”服务。历史上收入最高的一直是维护遗留系统的资深工程师，他拿一家 COBOL 维护公司 COBOL Cowboys 的网站开玩笑，说退休后要开一家 React Cowboys。

13. Eno Reyes（Factory）：让代码库为 Agent 做好准备

直播位置 5:11:19–5:26:38 · Making Codebases Agent-Ready

Eno Reyes 是 Factory 的联合创始人兼 CTO。Factory 两年半前成立，使命是“把自主性带进软件工程”。他说这次讲的东西不依赖 Factory 的产品，适用于任何 AI 工具。

从规格到验证

他引用 Andrej Karpathy 最近的一条推文：Software 2.0 取决于能否验证。前沿模型的后训练大量依赖可验证任务，AI 能解决什么问题，取决于你能否给出目标并在可能的解空间里搜索。传统软件靠规格来写（输入 x、输出 y），换成“通过验证来自动化”的思路，能做的事就不一样了。

他还引用了 Jason Wei 关于“验证不对称性”的博客：很多任务验证比求解容易。最适合的可验证问题有几个特点：有客观真相、验证快、可以大规模并行验证、噪声低、有连续信号（除了对错，还能给出 30%、70%、100% 这种程度）。软件开发是高度可验证的，所以编程 Agent 是当今最先进的 Agent。过去二三十年积累了大量自动化验证手段：单元测试、端到端测试、QA 测试，Browserbase 和计算机使用 Agent 让验证复杂的前端改动更容易，OpenAPI 规格这类文档也能自动生成和校验。

人能忍受的，Agent 忍受不了

他给了一个自查清单：有没有代码格式的自动验证？有没有 linter？更进一步，linter 是否严格到让编程 Agent 写出的代码总能达到高级工程师的水平？有没有测试能在 AI slop 引入时失败、在高质量 AI 代码引入时通过？

大多数代码库缺这些额外的验证层，因为人类不靠自动化验证也能应付：测试覆盖率 50% 到 60% 就够了，因为人会手动测；构建每三次挂一次，大家心里都烦但没人说。在 44,000 名以上工程师的超大组织里，这种低标准成了常态，而且组织也能照样扩张。但把 AI Agent 放进软件开发全流程（交互式写代码之外，还有评审、文档、测试）时，这些缺口会让 Agent 失效。他说世界上最好的一些公司已经建立了严格的验证标准，所以它们用 Agent 的能力远超一般开发者。

有了严格验证，开发循环从“理解问题、设计方案、写代码、测试”变成“指定约束和要构建的东西、生成方案、用自动化验证和自己的直觉检验、继续迭代”，也就是规格驱动开发。现在各家工具都有 spec 模式或 plan 模式，Factory 的编程 Agent Droid 也有。

组织该把时间花在哪

他问：是花 45 天比较所有编程工具，最后发现某个在 SWE-bench 上准 10%，还是改进组织实践，让所有编程 Agent 都能成功，再选一个开发者喜欢的，甚至让大家自己选？如果连单个任务（“我要做这件事，这样做，这样验证”）都不能接近 100% 成功，就别想并行跑多个 Agent，或者把大型现代化改造拆成子任务交给 AI。高质量的 AI 代码评审也需要给 AI 系统写文档。Agent 会越来越会找该跑哪个 lint 和测试，但不会凭空创造验证标准。所以他认为开发者会继续深度参与，角色变成打理软件生长的环境：设定约束、建自动化、把团队的主见写进自动化里。

他说可以按八个维度（演讲开头的介绍称之为八类）评估自动化验证的现状，比如有没有 linter、linter 多好、有没有 AGENTS.md（几乎所有编程 Agent 都支持的开放标准）等，系统地补齐。还可以看哪些开发者在用哪些工具：如果 Agent 对高级工程师够可靠、初级工程师却用不起来，原因往往在于团队有一些没被自动化验证覆盖的小众惯例，和他们会不会用工具关系不大。他说 Google、Meta 和一个 2,000 人工程组织的区别在于：一个几乎没有上下文的应届生，可以去把 YouTube 某个边框改圆一点，而且有相当把握不会让十亿用户的 YouTube 挂掉，靠的是代码上线前海量的验证。

正反馈循环

现在编程 Agent 能找出这些缺口并修补：让它找出 linter 不够严格的地方，让它生成测试。他引用 Factory 工程师 Alvin 的话：“slop 测试也比没有测试好。”他承认有争议，但认为只要有一个基本符合规格、改对了就能通过的测试，人会改进它，其他 Agent 也会注意到这些测试并沿用模式。更好的 Agent 让环境更好，更好的环境让 Agent 更好，人也有更多时间改善环境。他说这是新的开发者体验循环，会让你采购的所有工具都受益。领导者除了用 opex 加人，还可以投资这个环境反馈循环。好的编程 Agent 也应该主动去找 linter 和测试。一个有主见的工程师，如果能衡量并系统改进，可以实质性地改变整个公司的速度。

他的结尾：客户提一个问题、建一个工单、编程 Agent 接手、开发者点批准、合并部署上线，一两个小时的全自动流程今天技术上已经可行。编程 Agent 的能力已经够了，限制它的是组织的验证标准。他说 1.5 倍、2 倍之外的 5 到 7 倍提升来自这里，但这需要投入，AI 不会自动给你。

14. Beyang Liu（Sourcegraph / Amp）：Amp，一个有主见的前沿编程 Agent

直播位置 5:26:38–5:45:03 · Amp Code: Next-Generation AI Coding

Beyang Liu 是 Sourcegraph 和 Amp 的联合创始人兼 CTO。他说 Amp 的展台上有个骑金鱼的吹笛人形象，代表他们想拥抱当下这种被 Agent 写越来越多代码的奇怪又神奇的感觉。他们想做一个“活在一年之后”的 Agent 研究实验室。

产品形态

  • 终端：他们从零写了一个终端 UI 框架，充分利用现代终端的能力。界面上展示适量信息：流式显示 diff 和执行的 CLI 命令，不把模型的每个解释 token 都铺出来。CLI 能连接你的编辑器（Emacs、Neovim、JetBrains）收集诊断信息。演示是 Amp 给自己加一个帮助按钮。
  • 编辑器：装进 VS Code 及其衍生品（Cursor、Windsurf、Antigravity），暂时没有 fork VS Code 的打算。他说自己几乎所有代码都通过 Agent 面板写，很少手动编辑，大部分时间在做代码评审，这是限制他同时多开两三倍 Agent 的瓶颈。

他说不打算说服大家 Amp 最好，要自己试；他想展示的是他们在架构上做的一系列反主流决定。

Agent 的几个杠杆

Agent 本质是一个循环，中间是模型和工具调用。能调的杠杆就是：选什么模型、工具怎么描述、模型怎样和工具迭代。这些杠杆看着少，组合起来变化很多。

反主流决定一：少接 MCP，打磨自有工具

四月时他们决定把精力放在 Amp 的核心工具集上，而不是 MCP 集成。理由有二：用 Agent 越多，越发现关键是找出反馈回路并帮 Agent 闭合，这需要专门为此调校的工具，MCP 服务器的作者不知道你的 Agent 要干什么，不会为你调工具描述；二是上下文混淆，工具越多 Agent 越难选，不相关的工具会让它困惑。

反主流决定二：专门化的子 Agent

工具描述占上下文，工具调用本身也占。好的编程 Agent 会先 grep、读文件，到要改代码时上下文所剩无几，只能提前停下。叫它少读一点，又会出现他说的 doom loop：没收集够上下文，一遍遍重试同一件事。解法是子 Agent，相当于编程语言里的子程序调用，把子任务的上下文分出去，只返回相关结果。Amp 没有用那种只改改系统提示和工具的通用子 Agent，他们做了三四个核心子 Agent：

  • Finder：代码库搜索。换过几代模型，现在用一个小而快的模型配一组精简工具。
  • Oracle：Amp 的推理能力。多数 Agent 通过选择模型来提供推理，Amp 把推理模型放进子 Agent，主 Agent 保持轻快、能用各种工具，遇到难调的 bug 或复杂规划才进入 Oracle。他说自己不想花一两个小时钻牛角尖时就叫 Oracle，切去看邮件，有时要几分钟，大约五次里有四次能找到根本原因。
  • Librarian：从你依赖的库和框架获取代码库以外的上下文。
  • Kraken（实验中）：不逐个改文件，专门写 codemod 做大规模重构。

反主流决定三：没有模型选择器

几乎所有编程 Agent 都把模型选择器当核心 UX，他认为这不是未来的架构。选择多了有“选择悖论”的认知负担；架构上 N 个模型共用一个只能轻度定制的 Harness，就没法为任何一个模型做到最好。Amp 有两个顶层 Agent：smart（能调用所有子 Agent，慢一些，可以交复杂指令，适合派出去异步跑）和 rush（适合人在环中、快速做定点修改）。这是在智能和速度的前沿上挑两个对用户体验有意义的点。smart 的模型只换过一次，就在两天前换成 Gemini 3。他说 Gemini 3 在不同 Agent 环境里表现差异很大，他们在发布前一周做了大量测试来优化 smart Agent，还在处理一些问题，但认为它推进了可能性的前沿。

界面

  • 编辑器变成“readitor”（读代码的编辑器）：专门为 Agent 输出做的 diff 查看器，可以选任意 commit 范围看文件级 diff，diff 可编辑，支持跳转定义、查找引用，底部有“变更导览”告诉你先读哪些文件。他说审大改动一半的难度在于不知道从哪开始。
  • 终端：Ghostty 的一位核心贡献者为 Amp 从零写了 TUI 框架。比如 diff 的绿色会和终端背景色混合，显示更好看；在 JetBrains、VS Code 内置终端或 macOS 默认终端里会优雅降级。

一起重新学写代码

  • 线程分享：团队成员可以看彼此用 Amp 改了多少代码，点进具体对话看怎么做的，发链接说“这个提示技巧不错”或者“这里卡住了，帮我想想怎么接上反馈回路”。
  • 成本：他说现在全面用 Agent 的最大障碍之一是成本。去大学校园问，用过编程 Agent 的学生比他想的少很多。团队有人提议在终端里放广告，一开始觉得不可能，随着推理成本下降又觉得可行。他们做了一个小型广告网络，在终端和编辑器里展示其他开发者工具的低调广告，用来补贴 rush Agent 的推理费用，让更多人能在业余项目里用上。

用户和社区

他说 Amp 不做付费网红营销，目标用户是少数想“活在未来”的人。他点名 Mitchell Hashimoto（HashiCorp 创始人，现在在做 Ghostty 终端）用 Amp 推动大量改动，Hamel Husain（他说可能是 AI 评测领域的头号权威）几周前说 Amp 是他最喜欢的编程 Agent，两人都没有入职或投资。他们还办了一个 Agent 建设者社区，由 Ryan Carson（Treehouse 创始人，教过一百多万人写代码）运营，不要求用 Amp，有定期访谈和线下活动。

15. Natalie Serrino（Gimlet Labs）：用 AI 生成的 kernel 给 PyTorch 提速

直播位置 5:45:03–6:04:23 · Using AI-Generated Kernels to Speed Up PyTorch

Natalie Serrino 是 Gimlet Labs 的联合创始人。Gimlet 在做一个面向 Agent 的推理云，关注性能和效率。她说 Agent 是多模型、多阶段加工具调用的复杂流水线，远比一个聊天模型复杂，背后的算力天然应该是异构的。Gimlet 会自动拆分这些工作负载，编排到不同厂商、不同规格的最合适硬件上。问题在于很多模型只为一种硬件优化过，所以他们研究能否用 AI 自动把工作负载的各部分移植到没优化过的硬件上。

这里说的 kernel 是什么

这里的 kernel 指 GPU 上执行大规模并行计算的单个函数（和 Linux 那种操作系统内核无关），比如 Transformer 里的各个算子实现。为什么用 AI 做：

  • 底层 kernel 优化能大幅提速。她展示了 NVIDIA 的一篇博客，换一种 attention 实现让 Llama 模型吞吐提升 3 倍。
  • 专家太少，人人都在推特上抱怨招不到，现有的人忙不过来。
  • 组合爆炸：CUDA、Triton、Pallas、Metal 等写法，不同硬件平台，同一厂商的不同代硬件也有不同特性和缓存大小。她看到一些旧 DSL 在 NVIDIA 新硬件上表现不好。

Agent 的工作流照搬人的工作流

专家移植一个工作负载（比如到 Metal）时：写一个实现，看能不能编译、能不能运行、结果对不对，不行就把信息带回脑子里再改；能跑以后看 profiling，一个一个瓶颈地磨。Agent 就放在人的位置上：先保证编译、执行、正确，再优化。演示：CLI 输入一个 PyTorch 工作负载，目标 H100，系统探索了一批候选优化，和 eager 模式、torch.compile 比较，找到一个比 torch.compile 快 22% 的方案，实际耗时约 20 分钟。

衡量的坑

  • 浮点数下“正确”的定义：容差怎么定。
  • 输入尺寸太小，测到的是开销而不是 kernel 本身。
  • 朴素计时测到的是启动时间而不是执行时间。要做预热、清缓存，否则原实现的结果被缓存后，新实现直接取了缓存。她说必须对这些事“神经质”。
  • 好的基准稀缺：跨硬件平台的底层 kernel 例子本来就少。

初步结果

在 Apple M4 上用 Metal，跑 KernelBench v0.1 的 250 道题，和 torch.compile 或 eager 中较快的那个比较。题目分 L1（最简单）到 L3（较复杂）。独立运行的 Agent 平均提速约 24% 到 25%，表现最好的是中等复杂度的问题，太复杂就掉下来，和很多编程问题一样。

例子

  • 算子融合（Kernel Fusion，把多个算子合成一个 kernel，减少启动和读写开销）：一个包含卷积、softmax、加 bias、缩放、sigmoid 五个操作的问题，Agent 把其中四个合并成一个大函数，用内联字符串写 C++ 代码，在 forward 里调用，在 M4 上提速 40%。她说 torch.compile 本来就擅长融合，但 Agent 能针对具体用例定制。
  • 换一种表达：一个 L1 问题提速 80%。Agent 发现 Metal 上的 1D 平均池化不如其他算子优化得好，就把它改写成等价的卷积（生成对应的权重矩阵），因为卷积在 Metal 上很快。
  • 算法层面：一个 L3 问题里，Agent 在 PyTorch 层把两个操作合成一个卷积，不用写底层 kernel，减少了算子启动。
  • 失败：矩阵乘法。Agent 写了自定义 CUDA kernel，比基线慢得多。矩阵乘法是被人手工优化得最彻底的算子之一，这不意外。
  • 可疑结果：一个 71,000 倍加速。那个算子要把输入限制在 -1 到 1 之间，Agent 发现测试用例的输入本来就都在这个范围内，写了一段长注释说没必要，直接返回输入。可以说是聪明地省掉了无用功，但不符合基准想测的东西，他们把这类情况排除了。她说这里需要人来判断。

Agent 擅长什么，还缺什么

她说这个小众的底层领域和其他编程 Agent 的情况差不多：Agent 擅长低成本产生大量想法、吞下大量上下文、做 L1 和 L2 级别的任务。还需要的是：严格的质量和性能验证，防止作弊并确认结果正确；硬件在环（Hardware-in-the-loop）的实测数据，因为光看底层代码很难判断它在硬件上跑多快；人在环中监督和指导。

Gimlet 的架构：一个监督 Agent 接收输入代码、目标硬件和人的提示，负责管理工作；它派出一群合成 Agent 产生优化想法；想法交给验证 Agent，在真实硬件上运行，并且严格防止任何“猫腻”。

真实模型上的案例

  • Vision Transformer：生成的代码比原版快一倍，后来发现只是把原来的 attention 模块换成了更优化的 SDPA。她说这是有效优化，但算不上高深，归为平凡案例。
  • 音频编码器模型：在人的提示下，为 RTX 6000 Blackwell 生成了 6 个专用融合 kernel，两边都用 torch.compile，快约 70%。以内联方式声明 kernel 虽然看着怪，但得到的是和原 PyTorch 模块 API 完全兼容的替换件。

结论和下一步

她说这不是银弹，但是工具箱里有前途的新工具。最适合：在一堆已知技巧（融合、分块等）里快速大量试验；把已有实现移植到新硬件并利用新硬件特性；把已有优化迁移到新场景，比如换了量化方式。还做不到：写出下一代 FlashAttention 那样的算法突破，或者胜过花了几个月钻研同一问题的专家，也不该期待它做到。价值在于让专家专注最有意思的优化，而他们没时间管的问题也能超过基线。下一步是为不同机器建抽象模型让 Agent 更好地针对硬件定制，尝试生成 PTX（NVIDIA 的类汇编中间语言），她认为 AI 在这种繁琐工作上可能比人做得好，以及研究学术界的形式化验证方法来保证正确性。

16. Jake Nations（Netflix）：无限软件危机

直播位置 6:04:23–6:23:26 · The Infinite Software Crisis

Jake Nations 是 Netflix 的 staff software engineer，过去几年在 Netflix 推动 AI 工具的采用。他以一个坦白开场：他上线过自己不太理解的代码，生成、测试、部署，却讲不清它怎么工作，而且他敢打赌在场每个人都做过。

他说加速是真的：以前要几天的待办现在几小时，拖了多年的大重构终于在做。但大型生产系统总会以意想不到的方式出故障，他举了最近 Cloudflare 的事故。出事时你得理解你在调试的代码，而现在代码生成的速度和数量让理解跟不上。

历史在重复

60 年代末 70 年代初，一批计算机科学家宣布进入“软件危机”：需求巨大，项目太慢。他转述 Dijkstra 的话：计算机弱的时候编程是个小问题，计算机巨大了编程就成了巨大的问题；硬件能力增长一千倍，社会对软件的需求同比例增长，程序员要想办法跟上。之后每个年代都在循环：70 年代有了 C，能写更大的系统；80 年代个人电脑让人人都能写软件；90 年代面向对象（他调侃 Java 的继承层级）；2000 年代敏捷和 Scrum；2010 年代云、移动和 DevOps，软件吞噬世界；今天是 Copilot、Cursor、Claude、Codex、Gemini，描述多快就能生成多快。模式没变，规模变成了无限。

Fred Brooks 1986 年的论文 No Silver Bullet 认为不会有单一创新让软件生产力提高一个数量级，因为难的一直是理解问题、设计方案，编码的机械部分（语法、打字、样板代码）从来不难。之前所有工具都在让机械部分更容易，核心难题没变。

简单和容易不是一回事

他引用 Clojure 作者 Rich Hickey 2011 年的演讲 Simple Made Easy：simple（简单）的意思是一股、一条辫子、不缠绕，每部分只做一件事、不和其他部分交织；easy（容易）的意思是就在手边、不费力就能拿到，复制、粘贴、上线。简单关乎结构，容易关乎距离。简单需要思考、设计和解缠，没法靠许愿得到；容易总能做到，装个包、让 AI 生成、从 Stack Overflow 抄。每次选容易，就是用现在的速度换以后的复杂度。以前这笔交易还行，因为复杂度积累得够慢，来得及重构。他认为 AI 打破了这个平衡，它是终极的“容易按钮”，让人连简单的路都不再考虑。

他用一个对话式开发的例子说明：给应用加认证，得到一个干净的 auth.js；接着加 OAuth，多了 oauth.js；继续迭代，session 坏了，冲突一堆；到第 20 轮，你已经没在讨论了，你在管理一团连你自己都记不清约束的上下文：废弃方案留下的死代码、被“改到能过”的测试、三种方案的碎片。每条新指令都在覆盖架构模式，代码对坏的架构决定没有任何抵抗，只是变形去满足最新的要求。

更危险的是，Agent 分析代码库时把每一行都当作要保留的模式：第 47 行的认证检查是模式，2019 年那段像 GraphQL 一样用的奇怪 gRPC 代码也是模式。技术债在它眼里不是债，只是更多代码。Brooks 把复杂度分为本质复杂度（问题本身的难度，比如用户要付款、订单要履约）和偶然复杂度（一路加上的变通方案、防御性代码、框架、过时的抽象）。真实代码库里两者缠在一起，分开它们需要上下文、历史和经验，生成的代码不做这种区分。

Netflix 的真实例子

他们有一个系统，在大约五年前写的旧授权代码和新的集中式认证系统之间放了一层兼容层（shim），因为当时没时间重写整个应用。有了 AI，看起来正好可以重构成直接用新系统。结果旧代码和授权模式耦合太深：权限检查织在业务逻辑里，角色假设嵌在数据模型里，认证调用散落在几百个文件里。Agent 改几个文件就碰到解不开的依赖，开始失控然后放弃；更糟的是它会在新系统上重建旧系统的逻辑。它看不到接缝，分不清业务逻辑在哪结束、认证逻辑从哪开始。他的结论是：偶然复杂度缠到这个程度，AI 帮不上忙，只会在上面再加层。

上下文压缩：三个阶段

他工作的代码库约一百万行 Java，主服务大约 500 万 token，没有任何上下文窗口装得下。把大段代码塞进上下文的尝试失败了，于是他改为挑选材料：设计文档、架构图、关键接口，花时间写清组件如何交互、遵循什么模式。500 万 token 变成了 2,000 字的规格；再把规格变成精确的代码执行步骤。他早先把这叫做上下文压缩，别人叫上下文工程或规格驱动开发，名字不重要，重要的是思考和规划成了大部分工作。

  • 研究：把架构图、文档、Slack 讨论都喂进去，让 Agent 分析代码库、梳理组件和依赖。这不是一次完成的，他会追问缓存怎么处理、失败怎么处理，分析错了就纠正，缺上下文就补。产出是一份研究文档：现在有什么、什么连着什么、你的改动会影响什么。几小时的探索压缩成几分钟的阅读。他说这里人的检查点最关键，杠杆最高。
  • 规划：写详细的实现计划，包括真实的代码结构、函数签名、类型定义、数据流，像“按数字填色”一样，交给最初级的工程师照抄就能跑通。重要的架构决策在这一步做：服务边界、清晰分离、避免不必要的耦合。人能提前看出问题，是因为经历过；AI 把每个模式都当要求。几分钟就能审完一个计划。
  • 实现：有了清晰的规格，上下文保持干净，避免长对话的复杂度螺旋。50 条消息的演化代码变成三个经过验证的产物。因为思考已经做完，可以交给后台 Agent 去实现，回来审查时只需确认符合计划，不用担心它发明了什么。

先手动做一次

那个授权重构现在开始有进展，但不是因为找到了更好的提示词。他们发现根本没法直接进入研究、规划、实现，必须先完全不用 AI 手动做一次迁移：读代码、理解依赖、改了看什么坏掉。他承认很痛苦，但这暴露了所有隐藏约束：哪些不变量必须成立，认证一变哪些服务会坏，这些是任何代码分析都发现不了的。然后把这个手动迁移的 PR 作为研究的种子，让 AI 看到干净的迁移长什么样。每个实体还略有不同，有的加密有的不加密，要反复补充上下文，之后才可能生成一次成功的计划，而且“可能”是关键词，他们仍在验证和发现边界情况。他说这套方法只在他们亲手做过一次迁移之后才管用，理解必须先挣来。

理解的能力会退化

为什么不一直和 AI 迭代到能跑为止？他说能跑不够：通过测试的代码和在生产中活下来的代码不同，今天能运行的系统和将来别人能修改的系统不同。AI 几秒钟生成几千行，理解它可能要几小时、几天，太缠的话永远理解不了。他认为很少有人在谈的一点是：每次为了跟上生成速度而跳过思考，我们一边添加不理解的代码，一边丧失识别问题的能力。“这里变复杂了”的直觉来自经验，他能认出危险的架构，是因为凌晨三点处理过它；他推动更简单的方案，是因为维护过别人的复杂方案。AI 按你要求的生成，不会编码过去失败的教训。三阶段方法把理解压缩成可以按生成速度审阅的产物。

他的结尾：AI 改变了写代码的一切，但没改变软件为什么会失败。Dijkstra 那一代用建立软件工程学科来应对危机，这一代面对的是无限代码生成。他说打字从来不难，难的是知道该打什么。会不会用 AI 已成定局，他留下的问题是：当 AI 写了大部分代码时，我们是否还理解自己的系统。

18. Aparna Dhinakaran（Arize）：给编程 Agent 做系统提示词学习

直播位置 7:23:06–7:34:05 · Continual System-Prompt Learning for Code Agents

Aparna Dhinakaran 是 Arize 的联合创始人兼 CPO。她说大家关注前沿编程模型，但不太注意做编程 Agent 的团队在系统提示词上花了多少工夫。她展示了一条走红的推文，对比泄露的 Claude、Cursor、Cline 系统提示词的长度，并说这些提示词不是静态的，会被反复迭代。

系统提示词学习

Andrej Karpathy 提出过 system prompt learning 的说法：有点像人类学习，拿回英文反馈，用它决定下次怎么做不同。他也用了《记忆碎片》的比喻，主角把学到的东西写下来，第二天照着做。

她用学生考试做对比。RL 像学生考完只拿到一个分数（70、80、90 分），几乎要靠猜去提高下一次的分数。她说 RL 在很多领域很好用，但样本效率低、耗时、吃数据，需要一个数据科学团队，对做 Agent 的团队可能大材小用，因为 LLM 已经很强了。提示词学习则是同一场考试，除了分数还拿回英文反馈：为什么对、哪里错、漏了哪些概念、该复习什么。

在 Cline 和 Claude Code 上的实验

两个 Agent 都有可以追加规则的地方：Cline 有 rules，Claude Code 有 CLAUDE.md，初始为空。基线是在 SWE-bench（她用的是 SWE-bench Lite 的 150 个例子）上用 Claude Sonnet 4.5 跑原版：Cline 解决约 30% 的 GitHub issue，Claude Code 约 40%。他们也在 BBH 等其他数据集上做了同样的实验。不做微调、不换模型，只改系统提示词。

  1. Agent 读题生成补丁，跑单元测试。
  2. 把题目、Agent 的方案、单元测试结果和标准答案交给 LLM 评委。评委输出通过或失败，关键是还要输出解释：为什么错，比如某些库上的解析错误、没处理某类情况，错误分很多类。
  3. 把原系统提示词、原规则（初始为空）、输入、评委结论和解释一起放进一个大的元提示词（Meta Prompt），生成一组新的规则：学到了什么、要避免什么。
  4. 用新规则重新跑一遍。

结果：只用 150 个例子做“训练数据”，Claude Code 多解决 5% 的 issue，Cline 多解决 15%。

和 GEPA 的比较

GEPA 是 DSPy 里的提示词优化器，思路相同，也是把英文反馈用进提示词。他们做了并排对比，她说 GEPA 需要多得多的循环和 rollout，他们的方法只要一小部分。底层思路一样，差别在于他们花了大量时间开发和迭代评测，评测提示词的质量决定了能给 Agent 多好的解释。她把这叫做评测工程（Eval Engineering）。

19. Nik Pash（Cline）：做编程 Agent 的教训，以及 Cline Bench

直播位置 7:34:05–7:48:17 · Hard-Won Lessons from Building Effective AI Coding Agents

Nik Pash 是 Cline 的 AI 负责人。

苦涩的真相：能力胜过脚手架

他说多年来大家用聪明的脚手架弥补弱模型：RAG 索引系统、搜索树、工具调用框架，前沿模型直接碾过这些抽象，脚手架反而碍事。Agent 栈有多花哨越来越不重要，要看驱动它的模型有多强。例子：这周发布的 Gemini 3 没有任何专门的 Agent Harness，就登顶了 Terminal-Bench 排行榜。图上 Gemini 3 在 Terminus 上的分数超过了世界上绝大多数“模型加 Agent”的组合。Terminus 是一个刻意不带立场、精简的通用 Harness，没有图搜索、没有 RAG、没有索引、没有上下文工程，只给一个终端让它自己想办法。他的要点是：如果你在做 Agent，放松，别搞那么多聪明的工程技巧。

他说推特上那些上下文小技巧已经被讲烂了，他看着很累，有流量但没什么信号。完整的做法他放在一张幻灯片上就够了。Cline 是模型无关的，支持所有模型，每两周就有新的大模型发布，从 Sonnet 4 调到 4.5、Gemini 2.5 到 3、GPT-5 到 5.1，套路都一样，改动琐碎，收益很小。

真正的瓶颈：基准

你能做出世界上最干净的 Agent，但不会让模型能力提升哪怕 1%。模型只有在实验室拿难的东西训练时才变强。决定前沿模型接下来学会什么的是基准，Agent 的聪明设计和 RAG 管线做不到这一点。模型变得会用工具，是因为有人建了 RL 环境逼它们练习，比如处理失败、重试。他说每一次推理能力的跳跃都来自某个基准，每一次 Agent 可靠性的跳跃都来自某个 RL 环境。

基准是什么：一个环境（他们的情况是一个 Docker 容器，让 Agent 在里面随便跑）、一个起始状态（开始做一个真实编程任务时的代码快照）加起始提示词、一个检查最终状态是否正确的验证器（Verifier）。RL 环境和它几乎一样，唯一区别是奖励的用途：基准衡量模型，RL 环境改进模型，分数除了发到排行榜，还用来更新策略模型的权重。

RL 环境工厂

Cline 建了一个系统，把真实编程数据变成 RL 环境，他们叫它 RL environments factory（名字还在想）。

  • 第一阶段，资格筛选：多个子 Agent 并行判断任务是否适合。查来源：仓库是否存在、起始 commit 能否访问、是否开源。查过程：起始提示词和后续追问，理解用户真正想做什么。查结果：能否找到实际修复问题的 commit 或 PR。同时积极排除：vibe coding 出来的 slop（不需要又一个“从零做一个 Next.js 应用”的基准）、太简单的任务、没有可靠起止状态的任务。
  • 第二阶段，构建环境：先做“考古”，在本地重建起止两个状态，拉代码、构建，确认用户说的 bug 和修复都存在，记录每个障碍和依赖；用 Docker 容器化，去掉 git，防止 Agent 作弊；最后定义验证器。

他用烧水壶讲好的验证器：目标是把水烧开，好的验证器是壶上的哨子，纯粹看结果，水要么到了沸点要么没到，不管你用燃气、电磁炉还是篝火。过程中会冒出很多坏测试，比如子 Agent 发现标准答案里火开到最大，就去检查火力，但小火也能烧开水；或者检查是不是用了左前方的灶头、是不是过了 5 分钟。要点是不要按标准答案过度规定，要测任务的本意和结果。产出是一个容器化的基准或 RL 环境，记录 Agent 的轨迹，可以可靠评分，可以在任何设备上运行。

这项工作起初是手工的，第一个 RL 环境花了他大约 16 小时，现在每个任务不到 20 分钟。他们在走向完全自动化，瓶颈从工程转向收集高质量任务。他还留了一个问题：如果做一个 RL 环境来测 Agent 造 RL 环境的能力，在上面爬坡会是什么样？模型如果能根据真实用户数据给自己造训练环境，循环就闭合了。

“真相核弹”和 Cline Bench

他说每家主要的 Agent 实验室都在幕后做类似的事、收集这类数据，但没人公开谈。他们引用内部基准，却从不公开让人检查。Agent 实验室站在真实工程师和模型之间，掌握着世界上最丰富的真实工程工作数据集，模型离不开这些数据，把它们关起来在拖慢前沿研究。

所以他宣布 Cline Bench：一个把真实软件开发打包成标准化 RL 和评测环境的基准，他说它不是“角色扮演式的工程”，不是“写一个生成斐波那契数列的服务器”。全部开源，可以自己跑、自己检查，可以用来做 SFT、RL、评测。参与方式：在开源项目上用 Cline provider 并选择加入 Cline Bench 计划，前沿模型卡住、你出手修好的任务，就是理想的候选任务。Cline Bench 会一直免费开源。

20. Joel Becker（METR）：基准和经济证据之间的能力测量鸿沟

直播位置 7:48:17–8:09:26 · Benchmarks vs. Economics: The AI Capability Measurement Gap

Joel Becker 是 METR（Model Evaluation and Threat Research）的研究员。METR 是独立的非营利研究机构，向公众、政策制定者和实验室说明 AI 可能带来灾难性风险的程度：模型评估部分研究 AI 的能力和倾向，威胁研究部分把这些能力和潜在风险联系起来。他讲两类看似矛盾的证据：基准式证据和经济式证据，各用一篇他参与的 METR 论文做例子。

第一篇：衡量 AI 完成长任务的能力

通常的基准（SWE-bench、GPQA 等）有一个下限（GPQA 是四选一，随机 25%），一个人类专家基线（GPQA 大约 75%），上限 100%。但分数难以解释：50% 意味着什么？达到人类基线是否意味着在你关心的意义上和专家一样强？而且基准从开始有信号到饱和的时间越来越短。

METR 的做法：

  • 收集多样任务上的人类基线数据。这些人是相关领域的熟练专家，但像入职第一天或第一周，对具体任务没有上下文。
  • 任务来自三个集合：HCAST（需要自主性、和工具和环境交互的软件类任务）；SWAA 套件（原子级小问题，比如“四个文件里哪个包含密码”，GPT-2 可能会也可能不会）；RE-Bench（很难的开放式机器学习研究工程挑战，顶级专家也觉得难）。
  • 在尽量相同的条件下测 AI 在同一批任务上的表现。
  • 把人类完成时间换算成 AI 自主能力的估计。以当时的前沿模型 Claude 3.7 Sonnet 为例：约 4 分钟以内的任务几乎 100% 成功，最难的任务很吃力，中间一段成功率在 10% 到 90%。他说“人越久能做完的任务模型越不行”不是自然法则，但在这批任务上各模型都很稳健地呈现这个规律，他猜在其他任务分布上也成立。拟合一条曲线，预测成功率 50% 时对应的人类耗时，就是该模型的时间跨度（Time Horizon）。为什么选 50% 可以另外讨论。

Claude 3 Opus 的时间跨度约 4 分钟，o1-preview 约 15 分钟，依此类推。按模型发布时间画图，接近一条直线，也就是指数增长，比他们预想的稳定得多，一直更新到最近的 GPT-5.1 Codex Max，预测都还成立。他的解读：AI 能完成对人类来说很难的任务（RE-Bench 远超他本人的能力），而且进步很快。

局限：人类基线是低上下文的专家，熟悉任务的人会更快；基准天花板低，时间跨度每 6 到 7 个月翻一倍，造更难的任务越来越难，时间跨度背后的基准可能也会很快饱和；问题不够“乱”（messy），不太需要和人协调，环境小而封闭，不像大型开源代码库或真实世界那样容易出意外。SWE-bench 等很多 Agent 基准也有这个问题。

第二篇：随机对照试验

为了更高的外部效度（External Validity，结论能否推广到真实情况），他们做了现场实验，也就是更偏经济学的证据：高上下文的开发者做他们本来就在做的任务，测速度提升；即使基准饱和，这种测量还有信号；任务是真实工作，不是合成的。

  • 16 名经验丰富的开发者，来自大型成熟开源项目，每人平均完成约 16 个真实任务（相关仓库的 issue，排除最长的那些）。
  • 每个任务随机分到“禁止 AI”（相当于 2019 年的开发方式：没有 AI 补全、没有 Cursor 这类 Agent 工具、不能在网页上用 LLM）或“允许 AI”（什么都可以，也可以不用）。他们给开发者买了 Cursor Pro，当时多用 Claude 3.5 或 3.7 Sonnet，那是当时的前沿模型。
  • 仓库包括 Haskell 编译器（GHC）、scikit-learn、Hugging Face Transformers 等，平均超过一百万行代码、存在十年以上。参与者平均是数百甚至数千名贡献者里的第三大贡献者，平均已贡献约 5 年。

预期和结果：经济学和机器学习专家（大型 AI 公司和实验室的人、顶尖学者、研究生）预计开发者能省约 40% 或略少；开发者事前预计提速 24% 到 25%；事后回忆认为提速约 20%。实际结果是：允许用 AI 时，开发者多花了 19% 的时间，也就是变慢了 19%。

他第一次看到数据时以为实验搞错了，团队看了大量屏幕录像，逐个检验假设。他们认为起作用的因素包括：

  • 对 AI 有用程度过度乐观，研究结束后开发者仍觉得 AI 有帮助，所以可能用多了。
  • 仓库的隐性上下文多、开发者极其熟悉：他们往往一开始就知道答案，瓶颈只是打字速度，给 AI 下指令反而有不小的时间成本。
  • AI 在大型复杂仓库上可能表现较差，这和基准式证据不同。
  • AI 可靠性低：即使能做对，也只是 50%、80% 或 20% 的时候，至少要检查，常常还要花时间修改。

效果不明的因素之一是“开发者 AI 工具用得低于平均水平”，这在公开讨论里被提出过，正反证据都有。

他强调的局限：结论不代表所有开发者和任务，这是经验极其丰富的开发者在极其复杂、长寿的开源仓库上；他自己经验没那么深、做的仓库小得多，他觉得自己当时是被 AI 提速了的。实验集中在 2025 年 3 月，AI 进步快，结果可能已经变了。

怎么调和两种证据

一种可能是实验有问题，这仍未排除：开发者也许不太会用 AI，随着熟悉会得到收益（他持怀疑态度，但他们在继续做实验）；按小时付费，没有激励他们快点完成（为了外部效度这么设计，他看录像觉得开发者没有因此改变做法）；样本小，不该过度更新，他们在做更大的研究。

如果结果成立，可能的解释：

  • 要真正省时间，可靠性要很高，大概 95% 到 99%，开发者才能一路按 Tab 而不花大量时间验证。
  • SWE-bench 式的算法评分不考虑代码能否被人维护、是否满足单元测试之外的质量要求，可合并性（Mergeability）式的整体评分更严格。
  • 基准用的是低上下文的人类基线，相比高上下文的专家，AI 没那么强。
  • 任务分布不同，基准任务没那么乱。
  • 能力激发不足：METR 花了大量工作和 token 让 Agent 在自家任务上发挥到最好，当时的 Cursor 可能没做到这一步。
  • 任务之间的依赖：人能做 A 和 B，AI 只能更快地做 A。人仍然要自己做 A，因为要知道 A 是怎么完成的才能可靠地做 B，要在子任务之间保持上下文。他认为这是原因之一。

METR 在招研究工程师、研究科学家（也欢迎创业背景的人）和运营总监。

21. Kevin Hou（Google DeepMind）：Antigravity，Agent 优先的开发平台

直播位置 8:09:26–8:34:29 · Defying Gravity

Kevin Hou 带领 Google Antigravity 的产品工程团队。Antigravity 是 Google DeepMind 新出的 IDE，和 Gemini 3 Pro 同一周（周二）发布，他说这是第一个出自基础模型实验室的 IDE，并且“毫不掩饰地 Agent 优先”。他开玩笑说这周对重力很不友好：当晚 Wicked 2 上映，又有 Antigravity 发布。

三个界面

  • Agent Manager：中心枢纽，Agent 优先的视图，让你站得比看代码更高一层，不看 diff。任何时候只有一个 Agent Manager 窗口。它有一个收件箱：需要你确认的事情（比如某些终端命令不该让 Agent 自己就跑）会出现在这里，一键处理，还有系统级通知，解决同时管理多个任务的问题。
  • 编辑器：该有的都有，包括很快的自动补全。他说“这里大家可以做梗图了，没错我们 fork 了 VS Code”。侧边栏的 Agent 和 Agent Manager 同步。用 Cmd+E / Ctrl+E 可以在编辑器和 Agent Manager 之间切换，不到 100 毫秒，切过去时对应的文件、artifact 和对话都已打开，方便你自己完成最后 80% 到 100%。
  • Agent 控制的浏览器：一个 Agent 控制的 Chrome。一方面用于获取上下文，它带着你在 Chrome 里的登录状态，可以访问你的 Google Docs、GitHub 面板等；另一方面用于验证，Agent 能点击、滚动、执行 JavaScript，测试你的应用。演示中他做了一个随机展示 Thomas Cole 画作的页面，加了一个弹出卡片功能，Agent 交回来的是一段 Chrome 录屏，没有给 diff，蓝色圆点是鼠标。另一个例子是航班追踪器，蓝色边框表示浏览器正由 Agent 控制，背后是 Gemini 的计算机使用变体模型，能读 DOM，模型也能看懂录屏并据此继续迭代。

他为算力不足道歉：发布后容量不够，用户遇到很多错误，团队在全天候处理，他半开玩笑地代表团队“为全球芯片短缺道歉”。

为什么这样设计

他说每次来这个大会都会看到同一个主题：产品只能和背后的模型一样好。每次产品范式的跳变都由模型能力变化驱动：模型擅长短补全时出现了 Copilot 式自动补全，有了 RLHF 出现了聊天，然后是 Agent。团队在 DeepMind 内部，提前几个月拿到 Gemini 3，和研究团队一起找模型的长处和缺口。他列了四类进步：智能和推理（更会遵循指令、更会用工具，能理解浏览器这种有无数操作的工具的细微之处）；能跑更长的任务，可以放到后台；思考更久；多模态，Gemini 3 和 Nano Banana Pro 等模型结合效果很好。

第一步：提高能力上限

  • 浏览器使用（Browser Use）。他把软件工程分成“做什么”“怎么做”“动手做”三部分。动手做（给足上下文后生成能用的代码）模型已经基本能做；做什么靠人的想象力；怎么做依赖丰富的上下文和组织内部知识，访问浏览器、bug 面板、实验数据等给了 Agent 这层上下文。浏览器同时提供了验证。
  • 图像。他认为开发本来就是多模态的：要看网站输出、架构图。图像理解用来验证截图和录屏；图像生成用来做设计稿。演示：从图像空间开始做网站设计稿，在图上留一批评论，像 GitHub 一样说“更新设计”，Agent 知道何时、如何应用这些评论。Nano Banana Pro 发布当天就在 Antigravity 里可用。

第二步：新的交互方式 Artifacts

能力上限提高、任务更长更复杂、Agent 在多个界面上工作，就需要新的交互模式，他们叫 Artifacts。Artifact 是 Agent 生成的、为你和你的用例动态呈现信息的东西。用途：让 Agent 自己保持条理、自我反思；和用户沟通，比如给你截图或录屏；在 Agent 之间传递，比如给浏览器子 Agent、其他对话，或者存为记忆。Agent Manager 右侧一半的空间都留给 artifact。

他说以往监督 Agent 的方式是读它的思维链，即使分了段，也是一长串 token，滚了又滚还是不知道它干了什么。可视化的呈现好懂得多，就像他今天用幻灯片而不是站着念一大段意识流，幻灯片就是他的 artifact。原始对话仍然随时可看。

  • 动态：模型自己决定要不要生成 artifact（改个标题就不需要），以及生成哪种。常见的是 markdown 写的计划和最终的 walkthrough。计划类似 PRD，还会列出开放问题，让你先回答。没有问题时模型会自己决定继续执行，他说这是在押注模型。之后可能有任务列表（用来看进度，不用看对话）、架构图，最后是 walkthrough，相当于 PR 描述，向人证明它做对了、做好了。还有图片、录屏、Mermaid 图。新的 artifact 类型可以随时间出现，所以可扩展。
  • 可见范围：子 Agent、其他 Agent、其他对话是否该看到，是否存入记忆库。例子：给它一份 API 文档和 API key，它会跑 curl 请求摸清确切的 schema，做很久的深度研究，最后给出报告。这份报告会存进记忆，下次不用重新推导。
  • 通知：有开放问题时，Agent 会主动找你。
  • 反馈：参考 Google Docs 和 GitHub 的评论方式，选中文字留评论，比如“这里要再细化”“别用 Tailwind，用原生 CSS”，攒一批再发送。在图像上可以像 Figma 一样框选后评论。Agent 会在不中断执行循环的情况下吸收这些评论，比如浏览器操作进行到一半，你圈出不喜欢的地方发过去，它处理完再通知你。

Agent Manager 为审阅 artifact 和并行编排做了优化：你可以同时让一个任务迭代设计稿、一个研究 API、一个构建应用，用 artifact 反馈，用通知知道哪里需要你。不信任 Agent 的任务可以随时切回编辑器。

第三步：研究和产品的飞轮

他说自己做代码生成三年的经验是要做自己产品的头号用户。Google 工程师和 DeepMind 研究员先是提前、现在正式在内部使用 Antigravity，改进模型的人能亲身看到模型在计算机使用、图像生成、指令遵循等方面的缺口；基础设施工程师觉得某个页面慢就去改。他说这种洞察是评测给不了的。两个例子：

  • 计算机使用：和隔几十英尺坐着的计算机使用团队合作，双方互相找问题。一边说能力在某处不对，可能是数据分布不匹配；另一边说你们的 Agent Harness 有问题，工具得修。
  • Artifacts：最初的模型版本不擅长，因为训练数据里很少有这种“评审”的概念。和研究团队一起给它一个可以爬的坡，逐步提升，Gemini 3 Pro 发布时已经能很好地处理 artifact。

他总结了三步：提高上限（他说 vibe coding 方面 Google 有 AI Studio 这样出色的产品，Antigravity 专注于提高上限）、Agent 优先的体验（artifacts 和 Agent Manager）、研究和产品的飞轮。最后感谢 swyx 和 Ben，并开玩笑说大家可以“领养一块 TPU”帮他们少被 PagerDuty 叫醒。
