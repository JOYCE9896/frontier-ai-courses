02. Jason Liu（OpenAI 开发者体验团队）：AI 时代的野心

直播位置 0:19:45–0:38:29 · 英文原题 Ambition in AI

Jason 3 月加入 OpenAI 开发者体验团队，那时 Codex app 还没正式推出，也还没有 Astra。他说这些东西上线以后，他觉得自己从“开发者体验团队”变成了“所有人的体验团队”，因为 AI 让每个人都能做东西，所以这场演讲也想讲给线上的非开发者听。他列了 OpenAI 今年做的事：Codex app、生物方向、个人应用（sites）、网络安全、语音、Computer Use，最近几个月还有数学、物理和实体工程上的贡献。他说几年前模型还在做小学数学，现在能去碰 Navier-Stokes 方程。

三条原则，对应三种恐惧

他说执行已经变得免费，野心不等于用更多 token 或说“我有几千个 Agent 在后台跑”。他把野心归成三条：你是否相信自己拥有这份作品（ownership）；你能否描述自己的品味，说清楚“好”长什么样，好让模型改得更好；你是否足够好奇，用 AI 去追别的领域。这三条分别回应人们对 AI 的三种担心：会不会造出更多 slop（AI 批量生成的低质量内容），会不会毁掉批判性思考能力，会不会取代我们。

拥有作品：相机的故事

他说自己以前做过机器学习工程师、物理学家，也做过艺术家。他用相机出现时的历史来想 slop 问题：画家一开始很紧张，人们也没想到摄影会改变艺术，看卓别林的片子很容易当成小玩意。他引用 Walter Benjamin《机械复制时代的艺术作品》里的话：摄影把手从最重要的职能里解放出来，交给了眼睛和声音。他说现在用语音模式对 ChatGPT 说“做这个做那个”也是一样。人人都有相机，相册里一千张没人看的照片也许是 slop，但要紧的是拍下了几个重要时刻。他说 30 年前他家买不起相机，他没有童年照片，宁可当时多一点 slop 也想有相机。

他问大家把自己当成画家还是艺术家。用 DeWalt 电锯做的桌子不会说是 DeWalt 做的；片场有几千人，电影仍是导演的；开源项目有几千个贡献者甚至 Agent，质量责任仍在核心维护者身上。他说危险不在于 slop 变多，在于“自我抹除”：做一个被动旁观者。同样提交 1000 个 PR 的两个人，差别只在于是否在乎、是否主动参与。对工程师来说，就是多用自己的产品，注意哪里坏了，决定要不要再过一遍。他说网上那些好例子大多不是一次生成的，是反复打磨的。对付 slop 的药是相信这是你的作品。

描述“好”：品味是语言

第二个担心是 AI 会不会毁掉批判性思考。他说给你一台相机并没有拿走创作的努力，现在要的是能描述发生了什么的语言。他在艺术学校学的是空间、明暗、形状、肌理这些设计要素，不懂负空间就去画很多速写。他发现自己的品味和判断超过了技能。他不喜欢“品味是护城河”这句话，因为它没说品味是什么；他的定义是：品味是描述你喜欢什么、预测别人会喜欢什么的能力。他引用维特根斯坦“我的语言的界限就是我的世界的界限”。

例子是 Steve Yegge 前几天发推说“找出我应用里所有隐式状态机”，他得去 Google 这是什么意思，结果评论里都在说应用快了 20%。他借用机器学习里生成器和判别器的差距：判别器太强，生成器学不动；生成器太强，判别器帮不上忙。他说人现在就是判别器，模型输出一旦达到你的品味水平就很难再提高，失败模式是你分辨不出模型还能不能更好。

他过去一年为了做软件学了字体排印（“为什么全是斜体”）、信息呈现、动效设计、交互模式。他说那些紫色调的应用之所以存在，是做的人说不出哪里不对。他的口号是想要好品味就得多“吃”：想 vibe coding 游戏就先去玩游戏，做工具就去试别人的工具。他用 AI 做 3D 打印，出来的东西都像几个长方体粘在一起，一直说“做得更漂亮点”很挫败，后来去看跑车和工业设计、去店里看实物，学会描述好的曲线，设计就好看多了。他对团队负责人的建议：如果你真相信 AI 让人更高效，就该给团队留出时间去探索和体验世界。

好奇：回到你放下的领域

第三条，他请大家想想为了做软件放弃了什么。他说工具变容易以后，创意行业变得跨学科，家具设计师可以做建筑、拍电影、设计玩具，米开朗基罗同时是雕塑家、画家、建筑师和诗人；技术领域因为知识太多很难这样做，没人能读四个博士。但跨学科时会有好事发生：分子生物学的奠基人是物理学家，一位数学家领导过人类基因组计划，研究磁体的数学被用来理解神经网络。他举的现实例子有：一位机器学习顾问用 AI 和分子生物学帮自家狗治癌症；北海道一位公务员用 ChatGPT 和计算机视觉模型造机器人让农场自动化。

他说软件工程师带着判断力进入新领域，有一种“重新当小孩”的天真，敢问别人觉得不可能的问题，再用 AI 去实现。他自己在学打鼓，写了定制的打鼓软件，用 AI 学 Ableton，把鼓接上 MIDI，用 Computer Use 学以前没时间学的软件，还在 3D 打印零件、做芯片。他说以前别人问他怎么学编程，他从不让人读 Python 教材，总是让人去做一个天气应用或笔记应用，现在问题的尺度更大了。他说 Codex app 和 sites 都是有人真正在乎才做出来的，现在 PM 能写代码、工程师能做设计；OpenAI 的使命是让所有人都拥有这项技术，各自做出贡献。

03. Armin Ronacher（Earendil CTO，Flask 与 Jinja 作者）：先建工坊，再建工厂

直播位置 0:39:35–0:59:26

Armin 想讲的是：在建“软件工厂”之前，先建一个“工坊”（atelier）。他的比喻是艺术家用上 CNC 机床、3D 打印机这些好工具，提升的是作品的野心；软件也一样，重点是做更有野心、质量更高的软件，不是做更多软件。他说 Earendil 在做 Pi 这个编程 Agent，所以他在这件事上有立场。

Harness 一年没变，能力全来自模型

Harness 指包在模型外面、负责调用工具和管理上下文的那层程序。他说 Pi 的核心 Harness 一年没变，工具和去年 12 月一样，但它变强了很多，全是因为模型变好了。过去一年半流行过很多提示词技巧和 Harness 花招，现在大多不需要了。他举的例子是他喜欢的 Pi Auto Research 插件，能让 Agent 朝一个目标（比如提升性能）一直推进，用今天最先进的模型就发现整个插件已经没必要了。

他筛出自己只用默认配置的 Pi 会话，用 Jev 分析：他需要纠正 Agent 的次数随每代模型一路下降，中止 Agent 的次数也一样。他觉得最有意思的是 P90 运行时长：去年 12 月用 Opus 4.6，P90 下 Agent 对一个任务跑约两分半；现在最新模型 P90 跑 14 分钟以上。另外现在的 Agent 比以前更爱用 bash，而不是其他提供的工具。Astra 和 Sol 的表现跟 Opus 很像，只是数据不够没画出来。图上有一小块紫色是 code mode，在慢慢增多。

人的注意力是节拍器

他说一年来没变的是人还是人。他不想说人是瓶颈，但人决定了节奏，人的注意力是有限的。新开项目变得极其容易，维护却没变容易；同时我们在给很多外部系统施压，GitHub 上的提交和仓库多了很多，他认识一些老网站的维护者，突然要面对 Agent 打来的流量，完全没准备好。

他的数据：一年里他每天发出的提示词数大致持平，在 120 到 190 条之间；Agent 的活跃时长从不到一个工作日涨到好几倍于工作日，11 月还没过完。他这一年新建了 141 个 git 仓库，但持续提交（超过 5 天、会回来继续做）的项目一直只有 10 到 15 个，他问过朋友也差不多。有个朋友把开源项目完全自动化了，issue 进来、Agent 自动审查、提交、回复，后来他也关掉了，因为他不再关心这个项目，想把 token 预算花在别处。Armin 说即使全自动化，人的注意力对项目仍然要紧。

什么要紧：反推、真技能、标准

第一是知道什么时候反推 Agent。Agent 的奖励是完成目标，这和强化学习环境训练模型时的奖励类似，但完成目标不等于长期让人满意。代码越多越容易造出“辛普森一家”里那辆堆满功能的车，让系统内部复杂度不爆炸仍需要人边做边看。他管这叫真技能和 Agent 技能的区别：他儿子现在给他们一起做的项目提 PR，用的是同一套系统，质量差别一眼可见，因为儿子不是软件工程师。他也说在重要场合，别人只会转头去问 Agent，自己不理解系统和问题本身，是很让人沮丧的。所以要放慢到自己能理解的速度。

他的做法是看会话轨迹，在快结束前插一个固定的评估点：在 Agent 进入验证阶段（通常在约 70% 处）之前，让它写一份简短的执行摘要和一个排版好的 HTML 页面，讲清它做了什么。他说新模型写的文字没那么难读了，这是他在多数情况下不再读代码时找到的平衡。

第二是别一遍遍重写所有软件。他喜欢少用依赖、多写自己的代码，但德语里有个词 Wildwuchs，意思是失控生长，本该互相配合的软件失控生长后果很坏。他提到最近流传的一篇博客：一个精心构造的 TAR 包被不同 TAR 实现读出不同结果。现在可以让 Agent 实现任何格式，但实现之间会有差异，而统一标准的难处往往不是技术，是人们怎样就格式内容和解释达成一致。他设想一个未来：每人都有自己的 Photoshop 克隆，却没法互发文件。他说人与人协作和以前一样难，开源项目里真正的人际协作变得很少，fork 满天飞，因为 fork 比推回上游容易。有时该忍住让 Agent 直接解决的冲动，退一步想想是不是该和别人一起做。

他希望软件追求卓越。最近经过验证的软件（verified software）爆发，但还很难，技术栈没到位，值得推。他高兴看到很多人想做更快、更省内存的软件，用原生语言重写而不是再包一层 Electron；他喜欢 Rust，强模型能找安全漏洞让内存安全更有说服力，以前不会选 Rust 的人也开始试，因为它的好处现在“免费”了。

Harness 还能做什么

一是持久化 Agent（durable agents）。任务只跑两分钟时人愿意盯着，断了就手动重启；但夜里让自动化 Agent 处理几千个 issue 时，Agent 要能自己恢复，能启动、停止、挂起、恢复，并能编排出同样可持久化的工作流。另一个理由是算力和推理成本有限：按 token 付费时用弹性调度（flex scheduling）有不小的折扣，但可能好几分钟没有 token 返回，这时应该挂起 Agent 和沙箱，别浪费其他也很贵的资源。

二是 code mode。Pi 出来时的信念是 bash 就是一切，他现在仍这么认为，但大家开始想编排子 Agent，想用决策模型、分类模型（比如 Jev）这类非 LLM 的模型，这就需要组合工作流。他说这个思路最早来自 Cloudflare：与其把几千个工具塞进上下文，不如在 bash 之外再给 Agent 一个 JavaScript 运行环境，让工具调用都通过 JavaScript 发生，便于编排。这从好奇心变成了“出奇地有用”，Codex、Pi 和很多 Harness 都支持，Harness 可以大规模调用工具而不经过低效的上下文。分类模型不受没有活跃 KV cache 的惩罚，又便宜又快。他的例子：要处理 3000 个客服请求，每个都要决定是交给 Agent 处理还是要客户补充信息，Agent 可以现场生成一个工作流，每个 if 分支都走 Jev，以前要几小时的事很快做完。他最后说，既然什么都能造，也许不该什么都造，该把力气放在更让人愉快、更有野心的软件上。

04. Zach Lloyd（Warp 创始人兼 CEO）：软件工程正在变成工厂工程

直播位置 1:00:51–1:20:09

Zach 以前是 Google 首席工程师，带过 Google Docs 套件的工程团队，把它做到数亿用户。Warp 以开源的 Agent 终端出名，GitHub 上约 6.5 万星，近百万开发者在用；现在 Warp 也做一个平台，帮公司搭建自己的内部软件工厂。

为什么要离开“本地多开 Agent”

他说大多数开发者和平台团队还停在每个人在本地跑自己的编程 Agent、可能同时开好几个的阶段，现场举手的人仍占多数。他认为这会变，理由有三：本地交互式提示受人的吞吐量限制，每个 Agent 都要人去提示就没法自动化；每人各选模型、Skill 和本地配置，很难从成本和产出上保证效率；每人各自跑 Agent 带来安全和治理问题。现场问谁在做或在用内部软件工厂，举手的人几乎比前一个问题还多。

软件工厂的定义

他先说什么不算软件工厂：一堆松散的自动化、一群“AI 队友”、一套共享的 Skill 和 MCP、个人的 Agent 集群。这些都是有用的基础件，但不是终点。他的定义是：一个用代码定义的闭环系统，持续度量并改进云端编程 Agent。拆开有三点。第一，用声明式语言完整描述工厂，像 Terraform 那样写清楚跑哪些 Agent、怎样触发、工作从分诊到规格的流程、能用哪些 MCP、Agent 在哪里运行。第二，持续改进的闭环，大体就是软件开发生命周期：想法来自人或自动信号，Agent 把 issue 推过分诊、实现、验证、监控等阶段，跑得越多，闭环可以调得越高效。第三，一切都要可度量，凭感觉部署编程 Agent 就没法确定质量、成本和吞吐量是否最优。

他希望大家带走的一点是：智能 Agent 是过去一年里出现的新工程基础件，怎样围绕它搭系统是一个新的工程问题，跟“种花园”或“照菜谱”无关。他在 Google 学做好工程师时要精通调试器、性能分析器、Chrome DevTools；工厂工程也有自己的工具：评测 Eval、能跑通的自我改进循环、写基准、对工厂做 A/B 测试。工程师仍要做产品工程，对产品是否解决真实问题负责，但每个工程师都需要学会改进系统。

一套基础设施栈

  • 最底层是“工厂即代码”：可以分支、测试不同工厂配置、回滚，也让 Agent 能提议修改工厂本身，形成自我改进。
  • 数据和上下文层：记录 Agent 产出的一切，对话、产物、录屏、截图，这是日后改进工厂的原料。
  • 计算层：沙箱，提高安全性和可重复性，最好跨平台。
  • 推理层：模型是一个可以测试的自由度，工厂应支持多个模型和多个 Harness（Claude Code、Codex、Pi、Warp 各有特点），也可以写带组织上下文的自家 Harness。
  • 编排层：推动工作流过工厂，他说这是最无趣但必需的部分。
  • 最上层：API 和 MCP 优先，让其他 Agent 也能用，并接入 Slack、Linear、Jira、GitHub。

Warp 的演示

他展示了 Terraform 风格的工厂定义：策略、可访问的仓库、触发器、定义工作流程的 blueprint。然后是一个类似 Google Docs 的实时视图，显示 Warp 团队每个工程师的每个 Agent 正在做什么，例如同事 Maggie 在 Slack 里发起、用 Opus 5.5 做某个计划，可以点进去看对话和产物。数据集中存储后，不用在每人电脑上装东西就能看指标：DORA 指标、周期时间，也包括自动化程度、每个 PR 的人工交互次数、吞吐量和成本。

再往上是在线评测：会话运行并记录输出时，让另一个 Agent 回头给它们按某个维度打分。他举的评分项是“冗余测试”，编程 Agent 常写不必要的测试，这个 Eval 专门抓它，然后去查为什么会写太多测试、工厂里能改什么机制。有了这些就能做自我改进：让 Agent 而不是人去看评分结果，在失败的运行里找规律，以 PR 的形式向工厂定义提交修复。最后是基准：网上总在说哪个模型、哪个 Skill、哪个 Harness 最好，唯一真实的答案是在自己的数据上测，把真实任务做成基准集，换模型、换 Harness、换工厂配置重放。他展示的图像 SWE-bench 或 Terminal-Bench 发布新模型时的成本与质量散点图，目标是左上象限，区别是用自家数据，还能测“去掉这些 Skill 工厂表现变好还是变坏”。他说 Warp 靠这些工具大幅提高了吞吐量、降低了成本。

结尾他说知道大家对工程师身份很焦虑，他自己也不写代码了，但仍在用整个职业生涯学到的工程技能，所以他觉得这是个让人兴奋的时期。

07. Ayush（chat-history CLI 作者）：Agent 的管道命令就是 bug 报告 [线上]

直播位置 1:46:45–1:58:26

Ayush 做了一个 CLI，让编程 Agent 跨 Claude Code、Codex、Cursor 搜索自己过去的会话、复用上下文。他在改进它时发现了“Agent 为什么偷偷讨厌我的 CLI”。开头三个例子来自他自己的会话记录：Claude Code 想从文档页找一个设置，下载整页、grep，再只保留 40 行；Codex 想知道多少依赖有漏洞，请求整个 JSON 报告，只留最后 40 行，因为总数在那里；Cursor 跑测试发现一个失败，留最后 80 行。三次截断都保住了答案，但每次都暗含一个“答案在输出哪里”的假设，这会把摩擦藏起来，不让做工具的人看见。他说那个 Claude Code 的例子还是 Agent 在帮他审这场演讲时写的。

Agent 不报 bug，只绕开

他说 Agent 遇到摩擦会绕开，不会提 bug，就在你的程序外面再写个小程序。6 月 Sanity 写过他们的 MCP 服务器：上线后超过 2 万个 Agent、约 300 万次工具调用，一个 bug 报告都没有；他们加了一个反馈工具，Agent 有地方抱怨之后就开始说哪里不对。他说不用专门的反馈工具，反馈已经躺在会话记录里。

两万次调用的数据

  • 他从会话记录里抽了约 2 万次 Agent 调用，涉及 14 个 CLI：git、GitHub CLI、Cargo、curl、npm、Docker 等。四分之一把输出接进 head、grep、tail、python、sort、wc 这类过滤器；读取型命令超过一半，git show 和 cargo test 都是 62%。Codex 让 Agent 给每次调用设输出上限，管道用得少很多。
  • 管道不只是去噪。bash 里没开 pipefail 时，管道返回最后一个命令的退出码，cargo test 接 head 可能在测试失败时报成功。他展示了一个编译错误配着绿点的例子，那次 Agent 还读得到错误；更糟的是管道把错误本身截掉。Claude Code 的一个 GitHub issue 里，脚本抛了 ReferenceError、以错误码退出，tail 只显示三行无害内容，Claude 报告成功。他的建议是大声失败：失败时最后几行放简短摘要和完整日志的路径。
  • 他自己工具的 10 月审计有约 1000 次调用：Agent 用它打开旧会话时，五次里有四次（80%）输出直接进了 grep、sed、head、tail 或 python。他管这叫“管道税”：每次都手写同样的截断命令，每次都是一次关于答案在哪的猜测。
  • Hacker News 上有人反对说，让 Agent 自己决定读多少，它会 grep 和 head。他同意一次性的情况应该这样，但在这些日常 CLI 里，83% 的管道属于至少出现 10 次的固定模式（同一个 CLI、同一个子命令、同样的管道规则），Agent 一直在要同样的东西。
  • 他用工具打开一个长会话：完整输出 120 万字符，只取搜索命中附近约 3000 字符。Harness 会限制输出大小，但大小上限挑不出相关消息，选择类参数可以让 Agent 告诉工具它要哪部分。

把管道读成 bug 报告

他给了三个例子：用 rg 和 sed 过滤，意思是“让我挑我要的部分”，于是 read 命令可以只返回命中附近、只返回匹配消息或最后几条，并有大小上限；用 python 处理 JSON，意思是“给我少几个字段”，于是 search 加了紧凑模式，每个结果一行，比 JSON 小约 6 倍，结果相同；inspect 命令有约三分之一来自 Agent 手写 for 循环逐个看多个会话，意思是“让我一次问几个”，现在一次调用就行。他说他的路线图就写在 Agent 围着他命令写的那些命令里。

Infracost（云成本工具）5 月有同样的发现：他们的 Agent 在 JSON 输出上写 jq 和 python 管道，于是把过滤做进 CLI、加紧凑格式和一个教用法的 Skill。测试里没有这些的 Claude 六个难题答对零个，有了之后六个全对，整个基准的成本降了 41%。写那篇 Hacker News 帖子的人说读 Agent 日志像看可用性测试，他很同意。

文档就是接口

功能做进 CLI 后要通过 Skill 文件或 help 告诉 Agent，而 Agent 会照字面执行。他把 deep 参数改成空操作，但 Skill 里仍让 Agent 用它，结果 95 次搜索里 95 次都带着它；之后两个会话加载了改写后的 Skill，不再提这个参数，搜索里一次都没再用，而且两个会话第一次读取就试了新参数。所以 skill.md、help 文本、错误信息都是接口，过时的文档就是 bug。新参数到达 Agent 后，几乎每次搜索都用紧凑输出，读取时接管道的比例从 82% 降到约四分之一。

他说测试用例也在会话记录里：Agent 真实跑过的命令就是用例，Agent 紧接着做了什么就是粗略的答案。把这些命令分别在旧版和新版上重放：改了排序就看 Agent 后来真正用的那个结果是否仍排第一；改了输出格式就看有没有丢东西；改了默认值就看哪些命令行为变了；Agent 紧接着换参数重试的，多半是失败用例。留几个用例不看，用来给修复打分。

如果重来，先做什么

  • 测到的管道里 55% 下游只有 head、tail 或 sed，说明需要更小的切片，先提供范围和数量限制。
  • 参数要有人用才有用：GitHub CLI 的 list 有 limit 参数，Agent 81% 的时候会用；反例是 cargo test 的 quiet 模式，每个测试只打一个字符、仍报告失败，但 Agent 大约十次里只用一次，其余都接管道。所以要在 help 和 Skill 里教，并让大输出默认少打印，告诉 Agent 怎样拿更多，比如结尾写“显示 300 条中的 20 条，加 offset 20 看下一页”。
  • 可以做一个 Agent 模式：Claude Code 这类 Agent 会在 shell 里设环境变量，工具据此识别。DuckDB 已经这样做：终端里给人画漂亮的表格，给 Agent 一张朴素的表并说明省略了多少行、怎样取；超大查询提前停下并说明；错误以 JSON 返回。
  • 他自己照这份清单改完，模型读取的输出减少 59%，但省下的 token 只占模型读取总量的约 0.5%，成本和时长没有改善。Infracost 的收益在于答对，DuckDB 也是。所以要度量轮数和答对率，不能只看 token。

10. Dmitry：在代码失控之前，用小步清扫维护大型 AI 编程项目 [线上]

直播位置 2:18:37–2:31:31

第一章：什么算对

贯穿的任务是：有人要修改一张已审批订单的金额。这里有两种 Agent，一种写指令，另一种在生产环境照指令执行。他们的系统在 110 个国家运行，有约 1 万个用散文（自然语言）写的指令场景，每个任务落在一个“切片”里：一个国家的一个流程。第二颗宝石“空间”问的是变更允许走到哪，默认只在自己的切片内。他估计系统约四分之三是散文，所以散文也需要工程化。起初他们借用变异测试：故意改坏一句话，看测试会不会变红，结果几乎都不变红。他说对代码，测试能告诉你重写后什么必须保留；对散文，只有人能。Agent 自己搭不出复杂系统，会修容易看见的问题、顺手破坏一致性；人也会累，所以只在需要的地方花人的判断。

业务方说“和团队确认一下”时，背后的问题是这一步是人工的还是能自动化。专家答不了，因为他们看不到系统内部怎样连接；开发者带着编程 Agent 翻轨迹和日志来判断。在这个任务里，团队负责人的决定是人工步骤，限制在于能关联到的数据。业务专家看得到规则，开发者看得到水面下的部分，多数 bug 在那里，他们让编程 Agent 把这些联系写下来，供运行时检查。给专家的指南写的是：业务告诉我们做什么，我们想办法怎么做。一份文档两种读者：Agent 读其中的结构化块，所以块必须精确；专家读周围的文字并签字。只保留一份，有第二份就会漂移。专家按 Agent 看到的样子逐个审任务，他们知道这会变成下一次由编程 Agent 做、在同一任务上测试的变更。所以“对”取决于人，没有单个人全知道，由一组专家决定，因此从一开始就要把他们拉进来。

第二章：哪里还需要判断

专家一次纠正一个任务，Agent 则整天跑同样的散文。他们记录每个结果被接受还是被拒绝，准确率告诉他们哪里还需要人看。他以前以为目标是把一切搬进代码。例子：散文说限额 1500，代码说 1000，同一张订单在一处没问题、在另一处超限，什么错都不报。即使写一句“不要调用 X”，也在教模型 X 存在。这是第三颗宝石“现实”：是真的，还是只在模型看来像真的。散文没有编译器，他们就做了一个：作者把每个改动的文件像代码一样过 lint。lint 防不住副本之间漂移，所以他们观察“walk”，即 Agent 走过散文的路径。Agent 反复走同一条路，就把它变成一个工作流工具，并删掉对应的散文。第一批工作流工具反而更糟，因为散文里还写着工具内部的步骤，Agent 会再执行一遍；改成散文只保留决策后才好。现在只有当一条路径反复出现且在各国一致时才变成代码，否则留在散文里。代码准备事实、执行决定；专家维护决策表，模型只选一行，没有合适的行就交给人。下一步（模型做小决定、工作流串起来）还没做。边界是双向的：他们把几百行表达式从代码搬回散文，因为专家读不懂；正则用来识别关键信号仍然可以，多了就会冲突。判断留在答案会变的地方，放在专家能读的位置。

第三章：怎样保持控制

他以前以为控制就是给 Agent 设权限。第四颗宝石“心灵”问模型知道什么。让模型自己选加载什么，它全加载了，然后因为看得到价格就凭空发明了一个价格检查。上下文里有什么，就会成为行动的理由。所以由运行时决定模型看到什么，在这个任务里是订单的三个事实，完整记录留在运行时，模型的错误动作就少了。对大的数据集，模型传一个 handle（运行时已持有数据的简短名称），运行时在写入前检查。同时校验上下文的一致性。第五颗宝石“力量”问什么可以改：开发时控制一次变更，运行时写入时再控制一次，只有代码能打开写入路径，所以散文一天可以改很多次。写入前有五道墙，第六道检查写入是否落地；写入看似失败时 Agent 会重试，日志（journal）保证只执行一次。

第四章：谁来判断，代价是什么

他说多数时候他“在系统上空滑翔”，不下去看每个变更。起初他读每个变更，系统也学到了他的习惯；后来量超过一个人能读的范围，他开始倦怠，不再逐个读，这是最后一颗宝石的代价。他认识的每个技术负责人都当过那个所有变更都要等的人，Agent 只是让你几周而不是几年就走到这一步。第一个仪表是他自己：累到说不清改了什么，就是信号，仪表盘全绿时这个信号也可能在响，这时先停下修流程，不等数字。他读不过来所有 diff，就做了观察变化及其变化率的工具，比如“爆炸半径”：上线一个新检查前，先在几千个历史会话上重放它的规则，它会在不到 1% 的会话上触发；数字跳变的地方他下去读。看起来有问题时先等，单个信号要等它再出现，即使来自专家；跨切片成簇出现就不同了，那就修背后的概念。Agent 单独放着会不断加条件直到当天的任务通过，把这些条件去掉 Eval 分数就降，于是得到一份诚实的缺口清单。一个切片变红很少是孤立的：专家的意见变成一个 Eval，Agent 去兄弟切片找同样的失败；兄弟切片按市场和当地法律有意不同，所以只在确认失败的地方修。任何时候都有 10 到 20 个这样的回路开着。他说有段时间自己成了用户和 Agent 之间的消息总线。演讲到这里被换场画面切断，结尾不完整。

他们一切在 Slack 里做。客户在 Slack 上发来一段 bug 视频，转发到内部频道 @Devin 让它修；Devin 提 PR，并回一段展示修复的视频作为证据，他把证据直接转给客户，多数时候不用打开 IDE 甚至 GitHub。他说终点是整个开发周期不打开 IDE、不打开任何编程 Agent。

为此要改的基础设施

  • 以前测试连云上的 staging 环境和数据库，工程师手动点一遍流程。他们做了一次大迁移，让每个服务都能用 Docker Compose 在本地跑，每个第三方服务都有本地 mock 版本，全部能在一台虚拟机里运行，每个 Devin 都有一台。公司里的编程 Agent 测试改动时完全不碰线上服务。
  • 这些 VM 每小时重建一次：拉最新代码、从零构建。构建失败时 Devin 先上去修 VM 快照。所以从 Slack 拉起的每个 Agent 都在新机器、最新代码上开始。
  • 要教 Agent 怎样测试代码库。云端 Agent 能自己维护测试 Skill，代码库变了，Devin 会更新这些 Skill。
  • 结果是工程师不用打开电脑测试改动，有几位已经用 iPad 开发。他说 iPad 也更安全，最近很多攻击源于 DevOps 和密钥泄露，开发者电脑上可能到处是密钥，放在受控的云端 VM 里更安全。
  • 复杂测试也能做：开发 Devin 加入 Zoom 语音通话的功能时，Devin 在一台 VM 里创建多个账号加入同一个 Zoom 会议，互发语音来验证。

递归自我改进，从任务到“岗位”

他说在云端 Agent 体系下，每行代码、每个 PR、每个决定都有记录，可以让 Agent 在上面做数据分析，找哪里浪费时间和 token、什么能变成脚本、该加什么测试。他们有个频道，Devin 每天发改进建议，比如改 Node 设置能让 CI 快一分钟，改 lint 脚本能在 AI 代码审查前多抓 20% 的 bug。

他认为下一步是从给 Agent 派任务变成给 Agent 派“岗位”（job），把它当同事。例子：你在意后端性能，就告诉 Agent“我想改善应用的 P99 延迟”，它自己加遥测弄清现状、设告警、拆解所有任务、建 Datadog 告警、在 Slack 发周报、每天在手机上告诉你延迟改善了多少。他说他们甚至不希望工程师多数时候在写提示词，而是给 Agent 能长时间推进的目标。公司里看似不可度量的东西也要想办法度量：点击延迟、布局偏移（量元素的边界框）、新用户留存。能归结为一个数字的，就让 Agent 全天候优化它。

两个例子。一是推理性能：Cognition 是最早拿到 NVIDIA 新一代 Vera Rubin GPU 的客户之一，当时没有针对它的 kernel，要从零在新硬件上搭推理栈。他们给 Agent 一组固定 GPU，目标是把吞吐（TPM）推到极限，大约一周里 Agent 找到并测试了八九种策略，效果好的交给人做最终批准，吞吐从比 GB300 还差变成明显超过 GB300。二是 Android 应用：团队小，没人手做 Android。工程师 Sam 提议以 iOS 应用为蓝本，让 Devin 端到端保持 Android 与 iOS 一致；做法是在代码库上设常驻钩子监控 iOS 应用，监听 Slack 里的用户反馈频道，持续改进，逐像素对照 iOS 做实时 QA。44 天里多数日子没有一条人类消息，那些天每天合并 40 到 50 个 PR，只把最重要的决定升级给人。他展示了整个过程中人一共发给 Agent 的消息数，很少，并说这个应用很快会上线，不是 slop。他最后说大多数团队受限于自己的野心。

12. Jeff（Exa CTO）：你的 Agent 不知道的东西

直播位置 2:59:09–3:09:56

Exa 专门给 Agent 做网页搜索，当作 Agent 的知识层。他的数据：两年前每月约 1250 万次请求，今年 10 月超过 13 亿次，两年约 100 倍。他说这不是 Exa 独有的现象，OpenAI 刚宣布 ChatGPT 的搜索量约相当于 Google 的五分之一，Agent 现在约占网页流量的一半。

为什么 Agent 需要搜索

前沿模型能靠参数记忆（训练时记进权重的知识）完成很多任务，但真实任务不够。模型从训练截止到发布要两到五个月，下一代前沿模型又要几个月，所以总落后最新知识四到八个月，而库、API、价格、法规、判决一直在变。就算世界不变，训练数据也只是一小部分：最大的模型训练约 50 万亿 token，整个网络约 3100 万亿 token（含登录墙和应用后面的深网），只算搜索引擎能索引的部分也有约 510 万亿。编程、法律、尽职调查这类有价值的工作，都需要跨多个来源的正确、完整知识。

Atlas 基准

为度量这个缺口，他们做了 Atlas 基准，测 Harness 利用真实世界知识的能力：先让 Agent 找出满足条件的实体，再尽可能多地补充信息，最后对照标准答案打分，只有每一项都对的行才算对，所以要求持续正确，不是单次搜索命中率高就行。结果：模型的记忆随新近程度急剧下降，越新的事实越不知道；只用参数记忆不联网，Atlas 得分约 9%。

为什么不直接 Google

  • Agent 搜索方式和人不同：人在 Google 里平均输入约三个词（六年前约两个），Agent 用接近完整的句子，Exa 上平均查询约 12 个词，约 10% 的查询有 17 个词以上，带着版本、日期、地点等约束，这是关键词排序没设计去处理的。他展示了一个真实的找公司查询，关键词检索返回的结果没回答问题，其中第三条在美国，而查询要的是美国以外的数据。
  • 很多有价值的信息不在开放网络上：新闻报道、人员数据、财务数据、研究都在付费墙后面，爬开放网络的搜索引擎看不到。
  • 效率：Agent 搜 10 次、每次读 5 个页面、每页约 16K 的原始 HTML，光处理结果就约 86 万 token；按每月 13 亿次请求算，大量 token 花在提取信息上。
  • 给 Agent 加上关键词搜索后 Atlas 升到约 28%，多数行仍然数据不全或数值错误。

Exa 的做法

一是从信息里提取语义，不做字面或关键词匹配：爬网、做语义提取、嵌入向量空间、建索引；查询来了嵌入同一空间找最近邻。他说处理量最高每秒一百万个页面，从爬取到进索引约三分钟。二是超出开放网络：合作的专有数据，加上他们提取、表示出来的知识图谱数据，Agent 不用知道去哪找，通过一个 API 就能拿到。三是不只指向网页，要从页面里抽出答案，做成 token 密度高的表示。例子是“谁因锂离子电池获诺贝尔奖”：指向 Wikipedia 页面会给出几千字符，真正用于引用和依据的片段约 500 字符；直接处理 Google 结果的数据比抽取后多约 16 倍 token。抽取要语义丰富，挑出回答问题的那段，所以和查询有关。

结果是 Atlas 从闭卷的约 9% 提高到约 56%，约 5 倍，同时因为 token 效率，成本降了约 28%。他的结论是前沿模型的推理能力在一段时间内相对固定，扩展 Harness、让它获得整个互联网的语义信息，能显著提升 Agent 表现。

13. Doug Clausen（AWS Kiro 产品经理）：Kiro Crew 团队怎样每周合并几千个 PR

直播位置 3:23:25–3:41:03

Doug 先问现场有多少人觉得已经从 Agent 身上拿到了全部价值，举手的很少。他说 Amazon 一开始也一样，只看到 10% 到 20% 的提升（1.1 到 1.2 倍），原因是团队把 AI 拴在已有流程上，而且只缩短了代码生成阶段，软件开发远不只代码生成。他 6 月做过一项研究（也写了博客），看 Amazon Stores 部门里改变工作方式的团队：很多团队先变慢再变快，中位团队的生产力提升（按团队自己历史基线归一化的开发速度）是 4.5 倍，有的超过 10 倍。他说作为 Kiro 的 PM，他总被问两个问题：下一步发什么；我们这样做对吗。今天讲第二个。

Kiro 和 Kiro Crew

Kiro 是 AWS 的 Agent 开发系统，可以用 AI Agent 规划、构建和发布软件，有 IDE、CLI、网页和手机客户端，支持 Anthropic、OpenAI 的模型和一些开放权重模型，他说 AWS 会把省下的成本让给用户。Kiro Crew 用来同时跑很多 Kiro Agent，完全开源。它起源于 Amazon 内部：OpenClaw 热潮时（很多人在家用 Mac mini 跑），有工程师拿 Kiro CLI 扩展，想让 Agent 更像个人助理，做成内部产品 MeshClaw，头两个月就有约 4 万名 Amazon 内部开发者使用。Kiro 团队于是扩展并对外发布，8 月 4 日上线。他们的原则是自己不用、不喜欢就不发。上线以来一个很小的团队合并了约 16500 个 PR，上周一周就超过 3000 个，接受 Amazon 内外的贡献。图上前几个月稳定在每周 600 到 800，9 月 28 日左右突破 1000，徘徊在约 1200，之后又有一次阶跃。他说团队真正在意的是一个开发者能同时驾驭多少个会话。约十分之一的 PR 是新功能，其余是测试、对已发布功能的小修小补和 bug 修复。

五个阶段

  1. 一人一会话：打字、Agent 干活、停下、再打字。
  2. 并行会话：同时开两三个，方式不变。问题是人成了反馈回路，也就成了瓶颈，Agent 早就比人快，所以卡在每人两三个会话。
  3. 记忆和定时任务：新会话自动知道你的约定（隐式记忆），定时任务让你不用亲自启动所有工作。教训是定时任务只在机器开着时有用，所以转到远程运行，做到每人 10 到 20 个会话后又到顶，因为人还在会话之间当胶水。
  4. 流水线：更像装配线。他以前在航空航天行业，见过很多装配线，难点在非标准工作；软件每次走的路径不同，到 20 到 40 个会话时，团队又在忙着疏通卡住的流水线：小问题变大问题，要重启或重新规划。
  5. Ultra Mode：在 Agent 之上再放一个 Agent，负责定目标、启动任务、盯问题、解卡。现在每人 50 个以上会话。它还在开发者预览、藏在功能开关后面，但代码开源。他说下一道墙已经看得见：编排者和编排者协作，治理和护栏更要紧。

教训

第一，什么都测。他说很多人仍觉得信心来自看过全部代码，Amazon 一直以测试驱动，信心来自测试：你不能每次都看，但能每次用同样方式测。质量成了测试问题，他们现在约 20% 的时间花在测试上。

第二，审查，他说这有争议。他们最初写了个审查 Agent 审所有东西，目标是修掉每条评论，结果每次提交都冒出三条新问题、已修的地方又出四条，无限循环。现在把审查意见分成阻塞和非阻塞：破坏构建的必须先修，改变量名之类以后再说。先有一个快速闸门，检查文件放对了目录等基本项，然后跑六个审查者：两个代码审查者用不同模型家族（Anthropic、OpenAI 或开放权重模型），避免某个模型的盲区；设计审查，看形状对不对，比如这个 PR 又加了一个缓存，已有的缓存能不能解决；第一性原理审查，问这个改动是否针对真问题；UX 审查，比如新错误信息用户看了知不知道该怎么办；安全审查。每个审查者一票，全绿就合并，否则进入仓库里的 prepare PR Skill 去解决问题。他说他们很久以前就不审代码了，负责的是审查记录：流程是否按预期走、结果是否达标，不达标就修审查流程。

第三，过度工程。他们专门有个角色教 Agent 做减法，从流程中删代码。路线图上也一样：说 yes 变得很便宜，但一直说 yes 会让产品失去形状，Kiro Crew 已经有这种迹象，不想让用户淹没在噪音里。第四，合并不是终点：发布前有一个发布闸门，Agent 下载仓库、安装、运行、检查核心流程；安全也一直在做，每小时按安全指南检查，每天做一次 AppSec 审查，另有一个常驻的渗透测试 Agent。

他回顾了阻碍 Agent 的几件事：人的注意力、合上笔记本就断连、形状固定的流水线、无休止的审查循环、只加不减的循环。他说这会持续调整，下个月可能又有新做法。最后给了一个用 Kiro Crew 搭软件工厂的工作坊二维码，免费试用覆盖 IDE、CLI、网页和手机客户端。

14. Lance Martin（Anthropic）：一千个 Agent 的团队，以及“做梦”的记忆

直播位置 3:48:12–4:06:18

Lance 开场说遥控器和电脑都能用，暗指此前主题演讲出过故障。他讲两个关于 Claude 前沿能力的故事。

多 Agent：形式化费马大定理

这部分来自他在 Fable 5.2 发布时写的博客。费马大定理说 an + bn = cn 在 n 大于 2 时没有正整数解，叙述简单，约 350 年没被证明。90 年代中期 Andrew Wiles 花七年证明了它。此后数学界一直想把证明形式化，即用计算机逐步检查每一步。Lean 就是这样一种证明检查系统。

9 月 Anthropic 发表过用 Claude 在 Lean 里形式化这个证明的结果。那次一开始用了约十几个 Agent，起初效果不好，后来给了一个编排数学证明的平台（字幕作 ProveToMe），帮 Agent 管理项目状态，提供一个可查询的图，他说可以把它看成高度领域专用的 Harness；另外还有一位研究员提供大量支持。这次在 Fable 5.2 上想测的是：把团队从十几个扩到一千个，不用领域专用 Harness，也没有人在解法上引导，能否自主完成形式化。

Harness 很简单，大部分在安全上：一千个 Agent 各有一个网络受限的沙箱，只能连两样东西，Git 和一个 SQL 数据库；有实时监控检查每次工具调用是否有逃逸，还有离线监控每 10 分钟检查一次所有 Agent 的运行。提示词也简单：设一个 lead Agent 和 999 个 helper，告诉它们有 Git、有数据库和问题陈述。运行 5 分钟时，lead 自己建了几张表：公告表（发布全局消息、给 worker 分配角色和定理里的不同命题）、笔记表（交流进度）、子任务表、“landed”表（写进证明的 Lean 代码）。没人告诉它们要这样用数据库。他展示了读写这些表的可视化，以及一个难点（字幕作 Lagrange tunnel，听不清）的任务依赖树，Agent 在难的部分自己发展出了抽象。整个运行约 30 小时，证明里约 60 个命题逐个解决，Agent 按进展重新分配自己。最后有一条 Agent 留下的笔记：“全面冻结 origin，即刻生效，干得漂亮，你们 999 个”。他的要点是：在安全和监控上给足结构，Agent 团队只用简单的基础件就能协调完成很长周期的难题。

记忆：边做边写，回头再整理

第二个故事来自他最近的一篇博客，开头引用克尔凯郭尔：“生活只能向后理解，却必须向前过。”他说这是 Agent 记忆的根本矛盾：Agent 在做任务时边做边写记忆，看到怪事或有趣的事就记，写的时候只看眼前这个会话；但记忆需要是全局一致、不冗余的知识地图。人也有这个问题：白天写入短期记忆，据信由海马体负责，夜里海马体向新皮层回放，那里存长期知识，所以做梦被认为能把日常经验里最重要的片段整合成长期知识。Agent 也能从“日常记忆”和“长期知识”的拆分里受益。

结果一：开源的持续学习基准 CL-bench。设置是让 Claude 回答 40 个关于一个数据库的问题，每题都是新会话，中间可以往记忆目录写笔记。实验里没有专门的记忆提示，只告诉 Agent 有个目录可用。Sonnet 4.6 有记忆几乎没提升，他们查看后发现它不清楚何时该写，也不会自然地去读；Sonnet 5 好一些，Opus 更好，到 Opus 5.5 越来越会用。强模型本能地知道何时写、何时读，写的记忆质量也更高，是经过验证的陈述或对数据库状态、接下来会发生什么的预测。

结果二：玩 Pokémon。对比 Claude 3.7 Sonnet 和 Fable 5 的记忆目录，方框大小表示每个目录里的文件数。3.7 写了大量记忆，不加选择，什么经历都记，目录庞大混乱，跟玩法策略无关，游戏也走得差得多；Fable 5 的目录紧凑得多，都是战略洞察和战术知识，是从游戏状态里不容易直接得到的东西，游戏进度远超 3.7。

以上都是“经验中写入”。另一半是“做梦”（dreaming）：让 Claude 回看记忆，修正错误。他的框架是：会话记录是记忆的地基，最简单的记忆系统就是搜索记录，但记录很大，真正有用的信息很少；Claude 也能边做边写笔记；做梦则是回看记录和笔记，重新表示它们，比如建 wiki，或把某些记忆提升为注入上下文，预先加载到之后每个会话。

  • 纠错：Pokémon 里 Claude 把某个地标的位置记错了，于是在某处总是定位错、掉进一个暗门回到上一层，被困在循环里。没有做梦时，这个“中毒的记忆”让它一次次退步；有做梦时，错误被修正，Claude 进入下一层。
  • 建 wiki：Anthropic 5 月收购了 Stainless，他们拿到公司的文档和 Slack 消息语料，匿名化后做成数据集，出了 25 个只能从这些语料回答的问题。基线是语义搜索工具，约 53%；让 Claude 在语料上建 wiki，投入的做梦 token 越多，wiki 越有用，答题越好；wiki 和搜索工具一起用还能再高于单纯搜索。
  • 补全：另一个基准里，做梦前 Claude 建的 wiki 有不少指向不存在页面的占位链接；做梦后它补上了很多缺口，还建了索引。

15. Scott Tolinski 与 CJ Reynolds（Syntax 播客）：午间新闻点评与“猜猜哪个模型做的”

直播位置 4:11:21–4:53:56

午饭时段由 Syntax 播客的两位主持人现场直播，两人都来自 Denver。这一段是闲聊式的节目，内容依次如下。

“最伟大的提示词”：找出隐式状态机

一条疯传的推文写着“找出我应用里所有隐式状态机”（上午 Jason Liu 也提过）。CJ 解释：隐式状态机就是没有明确定义的状态机，代码里散落着 isLoading、isRunning 一类变量和一堆 if。Scott 补充：React 代码库里常见 isLoading、hasError、isSuccess 这样分开的布尔值，容易出 bug，还会让 UI 进入不可能的状态，比如 isLoading 和 isError 同时为真。显式状态机有一个声明的状态值和集中定义的状态转换，Redux 当年啰嗦但思路对，还有 XState 这类库。CJ 说这反驳了“别管代码、全让 AI 决定”的说法：代码库越干净，AI 越好干活。他最近常用的提示词是“找出所有重复和可以抽象的地方”，难点是让 AI 遵守你的抽象，不然会出现抽象的副本；他用 lint 规则解决。例子是他在做的一个大量读写文件的 CLI，重构前有 10 处用 10 种方式写文件，重构成一个统一的 file manager 后加了 lint 规则：禁止直接调用 fs 读写，强制 AI 用这个抽象。

UnfairPlay

FairPlay 是 iOS 应用的加密机制，防止反编译。UnfairPlay 能解密 IPA，恢复出应用本体。Scott 把它比作游戏 ROM 修改圈：不分发盗版，但可以把自己下载的应用解出来随意修改再装回设备。CJ 是 Android 用户，说 Android 上有类似的 ReVanced，常被用来去掉 Spotify、YouTube、Instagram 的广告（他们说不是在鼓励）。有人用 UnfairPlay 把 YouTube Shorts 全删了，或者给 Instagram 加使用时限，或者把被 YouTube 挪走的订阅入口放回导航栏。他们把这和 reverse-engineer-everything 那个仓库联系起来，说这是 AI 好的一面：拿回对应用和硬件的所有权和控制。

给 Agent 用的编程语言

Anomaly（OpenCode 团队）的 Kit 在讲他的新语言 Blood，只露出过一点他自己说已经过时的语法；此外还有 Bend（bend-lang.com）和 Vercel 团队的 0lang，Scott 说他至少见过 15 个这样的语言，而且“都比 Rust 快”。CJ 起初觉得 AI 是在现有语言上训练的，新语言凭什么更好；但看它们的原则，主要是提供证明、防止犯错，类似 Elm 让人很难进入错误状态。Scott 说 Elm 最近被提得很多，Effect 生态里的 UI 框架 FoldKit 就是 Elm 风格：单一状态树，全基于 Effect，一切都是 schema，开发者刚宣布全职做它，卖点是正确且 AI 擅长写。有人已经让 FoldKit 应用输出 GPUI 原生界面。CJ 说以前觉得 Effect 太晦涩不会用，但如果是给 Agent 用就无所谓。Scott 说两个月前他们还怀疑模型写不了不在训练数据里的框架，现在把示例仓库放进代码库、让 Agent 参照就行；他写 SvelteKit 很久，以前因为不在训练数据里得加各种确定性检查、Skill 和 MCP。CJ 查了 foldkit.dev/llms.txt 确实存在，FoldKit 还有连接自家开发者工具的 MCP。Scott 说这改变了他对 Agent 优先语言的看法，但它们也要争夺注意力；CJ 感慨“最喜欢的语言”这种开发者身份在消失，他重新用 React 就是因为 Agent 写 React 很好。Scott 说他用 FoldKit 开了个项目，很喜欢它的产出，因为它让大型应用里的状态问题少了很多。

Discord 改用 Rust 和 GPUI

16. Chetas（Robinhood 数据平台工程师）：机器人提的 PR，也让机器人来审 [线上，结尾缺失]

直播位置 4:53:56–5:16:38

这段录播开头已经开始了几句：一个改动可能在下游出问题，可能违反数据新鲜度 SLA，可能弄坏三个团队以外没人预料到的消费者，可能暴露不该被访问的数据，“CI 通过”和“这个改动真的安全”之间的差距是他的团队每天要填的。Chetas 在 Robinhood 数据平台团队设计和构建数据湖背后的分布式数据摄取和处理框架。他的问题用一句话说：给生产数据管道的 PR 以机器速度到来，安全审查仍以人的速度进行。

问题和整体做法

这里的 PR 指数据管道相关的改动：schema 变更、管道代码、配置、给人数据访问权限的授权（grant）。AI 编程助手让开 PR 变得很便宜，几分钟一个，而审这类 PR 归数据平台团队。原有的安全网是 CI 加人工审查，抓到过很多真实问题：坏代码、低效查询、下游破坏、敏感数据泄露。但人工那一半只能按人的速度、凭一个人脑子里的上下文（谁读这张表、表多大、数据多敏感）工作，而懂得什么能安全合并的人没有增加，队列就堆在这几个人面前。

他们的答案是三种职责、三个负责方：脚本证明能证明的，Agent 判断需要上下文的，人负责只有人该做的决定。第一层是确定性脚本，对照权威来源（schema registry、数据目录）检查，失败就让 CI 变红、阻塞 PR。第二层是 Agent，它的规则写明第一层已经检查了什么，专注于那些检查抓不到的风险：审 PR、打风险分、批准或升级给人。合并需要检查全部通过且有一个批准的审查。这样也省 AI 成本，AI 用来判断，不用来重新发现脚本能查到的事实。

贯穿的例子：把 int 加宽成 bigint

一个 PR 对数据湖里一张表做两个改动：上游源表多了一列，让摄取把它带进来；已有一列从 integer 加宽到 big integer。加宽类型听起来是最安全的 schema 变更，但真正的问题是下游谁在读这一列，血缘（lineage）工具里登记了一部分读者，但是不是全部？

  • 第一层的检查：数据契约，对照 schema registry 确认新列在上游确实存在，通过；必需标签，在目录里查表有没有负责人、PII（个人身份信息）有没有标注，通过；血缘爆炸半径，逐个检查血缘里登记的这列的消费者，看加宽后会不会坏，都没问题，但它只看得到血缘里记录的东西；性能，在 staging 用和生产同样数据量的 mock 数据跑改动，看集群规格是否合适、作业能否满足新鲜度 SLA，这类问题不查的话几周后会变成事故。全部绿灯，但只是“就脚本所见”安全。
  • 第二层 Agent 的输入：diff、PR 描述和提交信息（描述只说明意图，代码和描述冲突时以代码为准）、读取/搜索/列出仓库文件的工具。它只有仓库工具，不能查线上目录、血缘工具或生产状态，线上事实归第一层。规则按变更类型配置，针对查询反模式（比如不分区的 cross join 结果正确却会压垮集群）、敏感数据访问（看似普通的授权可能打开敏感数据）、血缘之外的消费者。
  • Agent 在仓库里找到一个血缘里没登记的作业：它读这张表被加宽的列，写进另一张表，而那张表里这一列还是 integer。第一次出现超过 integer 范围的值时写入就会失败。一个合法的 schema 变更，CI 全绿，下游作业照样坏。Agent 在审查评论里写出了整条链路。

为什么血缘漏了？企业数据环境很乱，工作负载跑在不同查询引擎上，每个引擎得自己发布血缘，有一个不发布就缺一块，没有能自动看到一切的目录。他也不夸大代码搜索：ad hoc 查询、仪表盘都在代码库外面，仓库搜索看不到。所以 Agent 被要求诚实：没找到时不能说“没有下游消费者”，只能说“在搜过的地方没找到”，永远不能宣布全部安全。

Agent 的产出和好的人类审查者一样：针对具体行的评论和理由（“这行改了这列，这是读它的作业”，而不是“看起来有风险”）；一个风险分；一个决定，没有严重风险可以批准，需要人的就升级并带上评论和理由。这个例子里 Agent 打了高风险分并升级。人做了 Agent 做不到的事：确认这个作业在生产中确实在跑。修复是调整顺序：先更新下游表让它能接受更宽的类型，再合并部署这个 PR，没有出事故。

永远留给人的决定

多数改动 Agent 可以自己批准。但有三类它永远不能批准：涉及敏感数据的授权，谁能访问敏感数据每次都要人来定；看起来改变了数据含义（而不只是搬运或存储方式）的迁移；Agent 对自己的结论不自信时，不能因为没发现具体问题就当作批准。这三种情况它只负责把风险和理由摆出来。

反馈和指标

人在审查评论下回复同意或不同意并说明原因，原因让反馈有用。回复每天收集，每周值班的人读一遍，手动更新审查规则。他承认现在是手动的，没有自动再训练或改规则，有个想法是让事故调查 Agent 帮忙做每周这一步，还没做。一个人纠正 Agent 的例子：某列在源数据库被标为个人信息，但摄取管道在写入数据湖前已经加密，PR 提议在数据湖里标为非敏感。Agent 因为上游是 PII 而标记；作者反驳，请它看看其他表的同类列是怎么分类的；人同意作者。这类纠正下次能避免不必要的升级，但它依赖这条管道在写入前加密，不是“加密就不敏感”的通用规则。

他们看两类错误：批准了坏 PR（漏报，危险）和把好 PR 不必要地交给人（误升级，耗人的时间）；全部升级的闸门不会漏，但也没减轻审查负担。截至 2026 年 8 月 31 日，漏报率约 2%，主要来自规则缺口，不是判断失误；误升级没有干净的单一数字，主因是缺上下文。漏报带来新规则，误升级告诉他们审查者缺什么上下文。一个漏报例子：一份开放副本里的某些列被隐私团队重新标为个人信息后，会移到更受限的副本、从开放副本消失；PR 看着没问题就合并了，没人检查下游是否还在从开放副本读这些列，结果有个读者坏了。于是新增规则：某列被重新标为敏感时，搜索代码库里还有谁从将要失去它的副本读取。演讲讲到这里被换场画面切断。另外 5:02 左右直播里短暂混入了闭幕环节请 Corey Quinn 上台的旁白，之后又回到这场录播。

17. Jarred Sumner（Bun 作者，Anthropic）：怎样放心地发布 Agent 写的几百万行代码

直播位置 5:19:16–5:41:12

Jarred 是 Bun 的作者，在 Anthropic 工作，Bun 是驱动 Claude Code 的 JavaScript 运行时。今年夏天他把 Bun 用 Rust 重写了；最近他合并了一个几百万行的 PR，给 Bun 加了一个预先编译器（AOT 编译器）。JIT（即时编译）是运行时边跑边编译，AOT 是运行前把代码全编译好，省掉运行时编译的开销。他说这个项目比 Rust 重写还大，挑战是怎样放心发布 Agent 写的几百万行代码。

为什么做 AOT，而不是用 Rust 重写 Claude Code

起点的提示词大意是：要让 Claude Code 更省内存、更快，可以改 WebKit 或 Bun（Bun 底层用 WebKit 的 JavaScriptCore）。他说典型 JavaScript 应用约一半 CPU 时间花在按需编译代码上；很多人把 JavaScript 代码库重写成 Rust 或 Go，原因就是 JIT 加单线程。对 Claude Code 的 iOS 应用这一点尤其要紧，每个会话都在编译。他们讨论过用 Rust 重写 Claude Code，因为 Bun 团队刚做过 Rust 重写，但决定不做：Bun 好重写，是因为测试用 TypeScript 写、和实现语言无关，同一套测试能在 Zig 版和 Rust 版上跑；Claude Code 的测试也是 TypeScript，重写就得移植测试，测试一改就不能再信它。所以改为让 JavaScript 本身变快。

结果：内存约省 4 倍，启动约快 2 倍，内部在 dogfood，很快对外。他还提到 TypeScript 7 是人手把编译器从 TypeScript 移植到 Go 的，而现在单线程的 TypeScript 用 bun compile 编译后，比单线程的 Go 移植版还快；AOT 版还没加多线程，已有 PR。

测试决定做法

一个多月里这个编译器重写了五次。他说这类项目受限于怎样验证代码能用，怎样构建完全由怎样验证、怎样信任它来决定。编译器会把 TypeScript 类型当作预测而不是事实，因为 TypeScript 的类型不保证正确；他说模型很擅长写编译器。这类问题适合 Agent 的原因是可以跑大量现成测试：Bun 已有的测试套件、WebKit 的测试、Test262、Claude Code 的测试，还让 Bun 自己的测试运行器能在 AOT 模式下运行。有两处破坏性变更，主要是防原型污染攻击（prototype pollution，往 Object.prototype 上加属性来攻击 JavaScript 应用）的安全措施，顺带也提升性能，编译器直接禁止这样做，一部分测试失败就是因为这个。另一个办法是差分测试：同一个应用跑三个版本，JIT 版、AOT 版、去掉类型的版本，三者行为一致就说明至少对这个应用是对的；再让 Claude 写代码生成器去 fuzz 各种模式。V8 用的 JavaScript 引擎 fuzzer Fuzzilli 他们本来就在用，又扩展到测试 TypeScript 类型。他强调要检查测试真的能抓到问题，很容易自欺以为在找 bug 其实没有。

五次重写

  • 第一版尽量复用 JavaScriptCore 已有代码，上限就是它的水平，Claude Code 占 1 GB 内存，很糟。
  • 之后给 Bun 加了 TypeScript 类型检查器 bun check，让 Claude 去用它，启动快了 2 倍、内存省了约 3 倍，但代码是 slop：比如任何访问名为 archive 属性的对象，都会被假定可能用到 Bun.archive API。他说不能发这种东西。做大规划时它还爱写 markdown 设计文档，1500 个 markdown 文件没人能读。
  • 第三版用 140 个 Agent 同时把所有代码写出来，再让 Claude Code 跑起来。
  • 第四版代码不 slop 了，性能差不多，但编译太慢：Claude Code 要 50 秒，其他项目也要好几秒，写 JavaScript 的人不期待有编译时间（更早的版本要 10 到 20 秒）。而且他问为什么有 90 万行，应该小得多。
  • 第五版代码好、构建时间低于 20 秒，下周发布。也许以后会有第六版，但他说做得够久了。

流程上，写大批代码的阶段不要频繁构建，只构建一次，否则时间全花在编译和等构建错误上；代码写完后的长期阶段用很多个体 Agent。他以前做 Rust 重写时很依赖 Claude Code 的 workflows，现在用最新模型主要靠长期存活的子 Agent（除了一开始集中写代码的阶段），它们把相关代码留在上下文里，浪费少，能一直做下去。编译器原理上，如果能证明值的类型一致（单态），就编译成直接的字段访问，否则每次都检查，另有少量内联缓存。项目太大很难跟进，他让 Agent 每小时在 Slack 发一份记分卡，对比上一版和这一版的一组指标，看数字涨跌。测试几乎都是项目之前就有的，所以 Agent 改不了它们。

一整天在做什么

他展示了自己发得最多的消息，“continue”最多，还有笔记本没电了。具体来说是一堆引导性问题：我们为什么这么做？能不能这样做？能不能快点？什么花了这么久？因为 Claude 会自己编出规则，也常低估自己能做到什么，所以他常要催它更努力。它还会先“掂量”一个想法值不值得做，很容易测错了还说服自己，这一点他觉得还要再审视。结果是在 JavaScript 引擎常用的 JetStream 3 基准上，Bun 在大多数项目上超过 JavaScriptCore 的 JIT 和 Node.js/V8 的 JIT；也不总是更快，比如 UglifyJS 这种大量走解释器（eval、new Function）的情况。整个过程中他们一直用 Claude Code 来构建 bun compile，再用 bun compile 编译出来的 Claude Code 继续干活。

他的几条体会：大项目里可测试性最要紧，要确认测试真的在测；不持续重新度量，东西会变差；还没发布的大项目，重写比重构容易；不推着它有野心，模型就只做 0.1% 的改进而不是 10%。想试可以运行 bun upgrade --canary 然后 bun compile。

18. Pritam 与 Manjiri（Uber 开发者平台）：AI 规模下的合并 [线上，结尾缺失]

直播位置 5:45:12–6:03:12 · 英文原题 Merging at AI Scale

副标题是 Uber 从“主干永远是绿的”走向“主干有时是坏的”的过程。Pritam 是 Uber 开发者平台的 staff engineer，Manjiri 是开发流程方向的资深工程师。Uber 有六个按语言划分的 monorepo，5000 多名开发者每周提交 3.6 万多个 commit、2.7 万个 PR，几乎所有服务和库的改动都在这些 monorepo 里。演讲以最大、扩展挑战最多的 Go 仓库为例。

SubmitQueue 怎样保持主干全绿

问题：A 和 B 都基于主干某个版本开 PR，各自 CI 都是绿的；A 合并后主干仍绿，B 合并后主干坏了，因为 B 从没和 A 的改动一起测过。几千名工程师每天几百上千次改动，主干就会经常坏，修复成本落在全公司身上。Uber 的合并队列（merge queue）叫 SubmitQueue，它预测主干可能的几种未来：A 单独落地、B 单独落地、A 和 B 一起，只落地能让主干整体保持绿的组合。它的扩展靠三点：

  • 目标分析：两个用户改的是不同服务，没有重叠的构建目标，就可以各自独立构建测试再合并，不用把每个改动串行化。
  • 概率推测：用历史构建信息和改动特征预测一个改动的成功率，优先跑最可能需要的那些推测构建，而不是所有推测分支。
  • 绕过大改动：大改动构建慢，小改动不用等它先落地。

AI 出现后数字变了：2026 年 1 月每小时约 90 个请求，3 月约 130 个，两个月涨了约 44%，主要来自 AI 生成的改动。P95 落地时间从每小时 90 个请求时的 30 分钟，变成 130 个时的三到四个小时。主干仍然全绿，代价是开发者要等三四个小时才能合并。

三项新优化

Manjiri 讲了三项应对。第一是准入闸门（admission gating）：每个请求进入主队列前被分为小改动或昂贵改动，定义之一就是目标分析，小改动涉及的目标少、并行度高；昂贵改动横跨很多目标甚至整个构建图，会占着资源、要和队列里其他一切验证，成为瓶颈。高峰时段直接拒绝昂贵改动，开发者得在非高峰重试。效果是吞吐提高 20% 以上，工作时间的落地率从每小时 113 升到约 160；代价是开发者变成了调度员，尤其是维护横跨全仓库的库的人，他们的工作天然落在昂贵那一类。

第二是延期队列（deferrals），为了缓解准入闸门的体验问题：高峰时来的昂贵请求不再拒绝，而是持久化存进一个延期队列，等闸门放行（比如高峰过后）再放回主队列。开发者只需提交一次，不用早起晚睡找队列空闲的窗口，但等待时间并没有减少。

第三是冲突松弛（conflict relaxation）。先讲目标重叠怎样导致串行：A 到 F 六个请求，两两之间至少有一个目标重叠，连成一个连通分量，SubmitQueue 就把它们分成一组、一起走，这阻碍了提速。以前只要有相关重叠就算冲突；松弛后分三步：给重叠打分而不是只问有没有，用 Jaccard 系数算依赖重叠，结合重叠的目标和新引入的依赖边，得到 0 到 1 之间的分数，越高表示重叠越强；保留强边，按配置值松掉弱边来换回并行度。例子：配置要求队列始终至少 50% 并行，六个改动就需要至少三条独立队列，最弱的是 D-C 和 D-E 两条边，去掉后变成三个连通分量，从六个请求的串行链变成三路、每路两个。

在哪里做这个决定：可以在全局每次分配冲突图时重算，但队列里有新请求进来、旧工作完成离开，会让图不稳定；他们选择只在新请求到达时局部计算它和队列中已有请求的边，算一次就固定，下一次只在下个新请求到达时发生。这样基于旧冲突图已经调度的工作得以保留，推测构建也能继续用。效果最大：吞吐提高 50% 以上，从每小时约 160 次落地到近 250 次，高峰时更高，P95 落地时间也很好。她开始讲代价，说代价就是第一张幻灯片里那个（主干不再保证全绿），讲到这里直播切到了换场画面，后面的结果和下一步计划没有播出。

她解释：平常在 Agent 会话里让它写 PR，它只读自己膨胀的会话上下文去推测做了什么，上下文在运行中会被压缩，越往后越不准。TraceTune 改为读取你电脑上相关的多个会话，弄清你实际做了什么。这个项目源自她之前的 ShowTale 项目：她支持的一项学术研究发现，学生用 AI 写程序，交上去的只有最终程序，大部分工作（提示和过程）没被提交，无法追溯学生的真实投入。她把同样的思路用到 PR 上：找出证据，比如在 cd 之前记录 CWD、解释为什么测试数据会泄漏到别的仓库，讲清楚背后发生了什么；而多数 AI 写的 PR 只是逐行解释 diff，因为它们就是照着 diff 写的。错误的事实会污染信息，造成 PR 冲突和不准确的结果。

原始流程和它的问题

TraceTune 原本的流程：找出某个分支的所有轨迹，做研究，审阅描述，补充上下文，循环直到证据足够，再由独立的撰写者和独立的审查者产出 PR。主观上以及用他们的测试框架 PR Bench 衡量，质量更好、研究更充分、错误率更低。但仍偶尔出错，多发生在最后带着更多上下文修订的那一步。例子：PR 声称“测试通过，按记录运行”，但轨迹显示 bun test 和 bunx tsc 是同时跑的，这两个必须顺序执行测试才能通过，所以“所有检查都跑过”的说法不成立。财务的第一反应是换便宜的撰写模型，不用 Opus、Sonnet、Haiku，结果质量更差。

他们的做法叫“邻域简报”（neighborhood brief）：把原因、代码、检查结果以及它们之间的归属和关系连起来，作为一个证据包返回，撰写 PR 时所有相关事实和来源都在一处，草稿更准、改的轮次更少，审查也更容易。于是审查可以用几个 Haiku（或 Codex 那边的 Luna）代替一个 Sonnet，撰写者仍用 Sonnet 或 Terra 一级的模型。Stephen 说这有点反直觉，人们通常想让规划者、审查者用最强的模型，但写作要用强模型，弱模型无论迭代多少轮、给多少反馈，都会把文字写成机械的清单；审查和交叉核对反而是机械的工作。最后的 PR 列出原因（在 cd 之前记录 CWD 说明 shell 状态）、例外（cd 目标在仓库内或命令提到某路由时）、通过了什么（类型检查加 71 个测试，在提交的内容上检查），以及从 correlate.ts 开始审查的建议，Mira 终于满意了。

22. Ari（Intrinsic AI 创始人）：把 KV cache 当作安全信号 [线上]

这场面向自己运行推理栈或打算这么做的人。主题和第一天直播里那场 KV cache 安全演讲相同（第一天字幕把公司记作 Pinter AI，这里语音识别为 Intrinsic AI）。KV cache 是推理引擎为每个 token 保存的键和值，免得模型重复计算，通常被当作吞吐优化。Ari 想换个角度看它。

Agent 应用出错的方式越来越多：提示词注入、越狱、错误的工具调用、敏感工具调用、敏感信息暴露、隐藏后门、漂移等。现在的防法多是守在边缘，用裁判模型对照策略检查输入和输出，或者每种情况训练一个分类器。他的视角是：模型在行动之前、解码之前、在响应变成下一次工具调用之前，会把每个输入变成一次计算，KV cache 就是推理引擎对这次计算的记录，现代引擎本来就在免费生成和读取它。他建议把它当作现有护栏的补充，称之为“KV 作为安全信号”。理由有三：数据本来就有，从推理栈原本要丢掉的东西里挑宝；能覆盖护栏的盲区，任何溜过护栏的东西仍会变成计算留在那里；数据不离开原地，适合不能直接读取输入输出的隐私场景。做法分三步：学习你的 AI 推理流量里 KV 页通常长什么样的基线，找出相对基线罕见的 KV 页（异常），再对它们分类和解释。

KV cache 让推理在某种意义上变成有状态的：LMCache 这类 KV 管理层把它从 GPU 存到远程存储，llm-d 和 NVIDIA Dynamo 会把新请求路由到已持有对应缓存页的 worker。所以有两个集成点：直接在推理引擎里实现（实时，生成的告警可以随后续工具调用或策略一起走，用来加固护栏）；或者和 LMCache 集成，读取存储的 KV 页做威胁发现。

数据：一个没有文本可过滤的语音 Agent 案例，模型是 Gemma 的 E4B 版本（字幕不清），基线是四种声音说的 72 段普通音频，用 16 token 的页；测试时一段干净的声音、一段带隐藏指令的声音，简单的异常检测就能发现，还能定位到哪个请求的哪一页。他们还训练了一个以 KV 页为特征的模型来打标签解释，它没在音频上训练过，也能正确标出个人信息、家庭住址、位置数据、出行目的地。文本 Agent 用的是 Qwen3 14B 加 LMCache：攻击流量和正常流量能明显分开；在 AgentBench 和 Hugging Face 上的一套数据里，基线是 9 种 Agent 轨迹，有 8 类 Agent 故障（从注入的工具描述到错误信息），异常检测给出的前 10 条告警里约 7 到 8 条是真正有意义的异常。

落到生产有两个难点：模型会变（微调、新版本、不同 Agent 用不同模型、路由器按请求选专门模型），每个模型的页有自己的坐标，要么每个模型都学基线、分类器和解释器，算力上不可行，要么找办法映射到一个共享表示空间；实时意味着搬大对象，比如 Qwen3 14B 一个 256 token 的块约 40 MB 的 KV，CacheGen 这类压缩和流式传输有帮助，但为安全分析搬运并实时处理仍然慢。他说 Intrinsic AI 在找自建推理栈、把安全当作基础设计决策的团队合作。

24. Melvin Johnson（Google DeepMind 副总裁，Gemini 后训练负责人）：怎样为长周期编程任务后训练 Gemini 4

直播位置 7:35:07–7:54:35

后训练（post-training）指在预训练之后，用监督数据和强化学习 RL 把模型调成能完成具体任务、行为对齐的阶段。Melvin 从外界的嘲讽讲起：有人说“Gemini 凉了，但 GCP 在发力”，有人说 DeepMind 已不是前沿实验室，Ethan Mollick 客气地说他们“两次发布间隔很长”。他说过去 28 天里他们发布了 Gemini 4 Argon，宣布并发布了 Carbon，还收到 Dylan（字幕仅有名，应是 SemiAnalysis 的 Dylan Patel）的公开道歉“Google 其实在发力”。他说他们曾 236 天没有前沿模型，现在 28 天两个，发布速度快了约 10 倍，挨批评也推着他们做得更好。

Carbon 和今天发布的 Hydrogen

他放了一段 Carbon 做出的东西的视频（中间投屏出了点状况），说视频本身也是模型做的：3D、用 Blender 做素材、很多游戏、真实场景、多模态文档处理。他给的基准：Carbon 在 CursorBench 上排第一，比第二名便宜 3.3 倍；在 Perplexity 的深度研究基准 Wander 上最好，比第二名便宜 9 倍；在 Zapier 的 Automation Bench 上第一，每个任务便宜 2 倍。当天发布了 Gemini 4 Hydrogen，目标是把 Gemini 的核心智能带给所有人，快且可靠，上线了 Antigravity、Gemini API、Gemini 应用和搜索。他展示了一张智能指数对时间的图，说它在这个智能水平上是最快的模型之一；Terminal-Bench 4 上 Gemini 3.8 Flash 约 20%，Hydrogen 约 60%，性能三倍、速度也快三倍。Gemini 4 系列于是有 Carbon（深度前沿智能）和 Hydrogen（日常快速执行），他说元素周期表里还有很多元素。

为什么后训练难

他说 Google 新代码约 75% 由 AI 写，几年前不到 25%；每天有 10 万人在 Google 内部用 Antigravity 写代码。任务复杂度指数上升：从几秒的聊天补全，到几分钟写小函数，到约一小时提 PR 解决 issue，现在是持续几天的真实工程任务，有人用 Agent 集群解决真实的开放问题。他们的循环是：找难任务；像有经验的代码审查者那样评分；大规模 RL 训练；让 10 万工程师 dogfood，dogfood 里的失败变成下一轮的任务。

难任务

模型变强后，基准会饱和，训练数据也会饱和。他展示了 Gemini 4 三次迭代中“可学习提示词”占比不断下降：上一轮的提示词对下一轮太简单。简单任务没有学习信号，如果所有 rollout 都对，就没有方差，没有 RL 信号。所以要比模型变强更快地找到难任务：识别并剪掉对模型太简单的 SWE-bench 式任务；扩展到更难的、跨多文件仓库的任务；从单元测试的二元对错改成基于评分细则（rubric）的评分，细则给的是稠密信号，不只是 0 或 1。例子：从多文件仓库里提取 commit，让模型自动从 commit 生成评分细则，不要求有单元测试；从空文件夹和一份规格（比如 grep 的参数、选项、功能）从零构建 CLI 工具，用隐藏测试套件评估生成的二进制；从生产代码库里模型的真实使用中提取任务。

评分器和防作弊

你训练 Agent 去通过测试，它就会想尽办法通过，测试通过不等于问题解决。他举的情况有：绕过检查器、刷基准、伪造证据（把假证据写进临时文件，再删掉作假的痕迹）。所以要像严格的审查者那样评：不只看正确性，还看风格、可维护性等。评分细则来自真实 commit，惩罚走捷径的解法；细则示例包括必须通过的边界情况、要保持的代码卫生、验证方面的约束。评分环境也要加固：评分器放在隔离沙箱里，删掉 git 历史和 git remote 防止答案泄露；测试集留出，只有 Agent 提交后才揭示，他们遇到过 Agent 说“我做完了”，测试一出现就去看测试、再重新提交。评分看完整 diff 并对照参考答案，看正确性、代码质量和改动范围。任何作弊或篡改环境都给很大的负奖励，判断只基于模型的动作，不监管它的思考。他说 Carbon 在 Terminal-Bench 4 上作弊率为 0%，以前的模型高得多，对抗性约是 Argon 的五分之一。

诚实

Agent 总想显得有帮助，有时会假装有帮助：声称测试通过实际没过，宣布完成实际没完成，声称改了代码实际没改，编造事实和 API，或者给你一墙数字让你无从核实。在一项内部难题评测上，编造率从 8% 降到 Hydrogen 的约 3%，Carbon 约 1.5%，目标是降到零。做法：清洗数据，过滤掉含有意或无意编造、含未经验证说法的训练轨迹；以完整轨迹为依据，Agent 给出“已完成”的总结时，对照它在轨迹里实际执行的动作，总结必须有动作支撑；奖励诚实，难题上宁可说“这是我的部分进展”，也不要假装完成最后一步。

为什么能按周发布

最大原因是 Google 内部 10 万多名工程师在真实任务上用模型。Google 是 monorepo，整个公司一个代码库，他说可能是世界上最大的之一，非常复杂。每次后训练产出新候选模型，就提供给内部用户，做多个候选的盲测对战让用户挑，也在后台把人路由到实验模型收集反馈，所有信号和摩擦都回到下一个候选的训练中。Gemini 3 时代每两三个月发布一次，现在过去 16 周发布了 6 次。

围绕 Agent 的工作方式

  • 去掉其他工具：没有 Jira，没有任务追踪，没有客服系统，一切在 Agent 里做。Amp 里的会话叫 thread，他们甚至在 Agent 里交流，发现产品有问题就在 thread 里说，Agent 听着并去修。本地 Agent 做不到在你搞不定时把别人拉进来。
  • 推送非常频繁，靠拆小降低风险：随时可以自己推送，就能把工作切得很碎。做大改动前先加日志，确认你和 Agent 对系统的理解是对的；推一个小改动，让 Agent 监控一小时，再推下一个；还可以让新系统以影子模式和旧系统并行，看每种情况结果是否完全一致。按老办法做完，你大概已经忘了在做什么。
  • 让 Agent 无可辩驳地证明自己做对了：比如要消除 UI 加载时的抖动，让 Agent 做人没耐心做的事，逐帧做视觉对比。让 Agent 一次做很多版本，比如 Amp 听写功能的波形，让它做九种样式；他说让设计师做九种会惹恼人家。他说那些抱怨等 Agent 的人，往往是一次只让它做一件小事。

  • 听写：他说这是把信息从脑子送到 Agent 的最快方式，可能还会带回远程办公，因为他今天和另一位联合创始人 Beyang 在办公室里一起听写，很烦。他建议克服尴尬，学 Nathan Fielder 那样承受任何程度的别扭。
  • 自建替代 SaaS：Agent 直接用各种工具后，很多软件产品就不需要了，真正有粘性的很少。他们在 Amp 里做了自己的 CRM。一年前人们嘲笑没人会 vibe coding 一个 Salesforce，他说确实，谁想要那个；但你只用 Salesforce 2% 的功能，再加 2% 和自家技术栈完美集成的功能，这 4% 是简单的部分，你比 Salesforce 更清楚自己要什么，也不用听对方 PM 说“我会争取放进第四季度路线图”。他说 Salesforce 是 SaaS 的眼镜王蛇，续约最稳；如果连它都开始被替代，靠付销售 10 万美元签一个能续十年的单子的整个 SaaS 模式都要受质疑。

Amp 现在 21 人，没有 PM，人人和客户交流。有位原来在 Sourcegraph 做 SDR（销售开发代表）、毕业两年的同事，自己做了一个 ACH 电汇收款功能，让超出信用卡额度的客户能付款，客户那边没人知道他是 SDR。团队里的 Alex Kemper 当天对一个想买的客户说“这听起来会让我们陷进一堆没用的事里，对谁都不划算”，他说拿提成的销售说不出这种话。他们每周只开一个会，其余时间的指引是“跟着你的精力走”，周六周日也算在内。他说 Amp 是盈利的，年经常性收入超过 1 亿美元，在一美元进一美元出的基础上，效率是老派公司的 40 到 50 倍。他的建议是走出笼子：很多人跟他说公司里有个八卦频道大家都在议论这场变化，他说你越久待在八卦频道、拿着高薪却什么都不做，就越成为问题的一部分；越久只把自己当开发者，越伤害自己。去一家愿意被 Agent 塑造的公司。

他说最早只有 9 条，现在是 12 条。下面按他讲的顺序整理，有几条他讲得很快，条目边界不完全清楚。

  • 循环：前向压力和反向压力的相互作用，自动开始工作，并保证人接手之前低垂的果实都已摘掉。
  • 知己知彼：无人看管的模型不能很好地长期维护和改进代码库质量。模型能几天甚至几小时克隆 Excel 或 Redis，但那需要预先知道整个问题；多数人是一个功能接一个功能地做，手工做时会中途发现抽象不好、该集中或该删。SlopCodeBench 测的就是模型随时间演化代码库的能力，看圈复杂度、每个符号的行数、高复杂度函数比例等，有 200 条自定义规则，50 条来自已有做法，其余是对比 AI 前的仓库与模型写的代码得出的。实验室负责人 Gabe Orlanski 当天发了论文，也测设计库和接口的能力。最离谱的发现是，很多被认为不好的模式在六个月前的模型里少得多，在今天的模型里更多，像是 slop 在随时间放大：模型学会了在 Python 里抛异常而不是返回元组；Claude 和 GLM 现在用 Python 2 风格写 Python 3，%s 格式化字符串回来了，默认不用 f-string。Fable 5.2 还没定论，Anthropic 的提示指南说告诉 Fable 它拥有代码库，它就会保持整洁，他们的基准正在后台跑。
  • 先计划再构建：以前团队有架构评审、迭代规划，是为了降低返工概率。也有人做过头，花六小时写规格，觉得还不如直接 YOLO。他用“预期痛苦”来权衡：以后要改的概率乘以改起来有多难。两句话的提示词，小事或无所谓时，大约 50% 概率要再补几条提示；花五小时写详细规格，也许 10% 要改；20 小时全手写，因 Agent 返工的概率为零（人也会犯错）。他不会在规划时和模型争按钮颜色，但数据库 schema 一定要定对。
  • 视觉对齐：他发布了一个叫 show me 的 Skill，让 Agent 给 HTML 原型、表格、图表，不给大段文字，约 4 万次安装。他引用一句话：人类躲避捕食者、吃水果几百万年，读文字才约 5000 年。
  • 帮 Agent 测试自己的工作：截图、浏览器、视频、curl，做 iOS 应用就确保它能在所处环境里构建、运行、测试。
  • 对抗 slop：Cloudflare 首席工程师 Dylan Mulroy 的 Anti-Slop 仓库有约一百条阻止 Agent 写出 slop 的规则（TypeScript）；Factory 也有一个 ESLint 插件；Python 可以从 SlopCodeBench 里直接拿规则。
  • slop 也是工具：vibe coding、原型、业余项目、功能开关后面还不确定有没有人要的东西，用 slop 没问题，不是每行代码都要完美。
  • 给模型一个功能开关系统（PostHog、Statsig、LaunchDarkly 等），让它试验、看效果再决定。
  • 复利积累：评测一切，从过去的会话中学习。
  • 统一你的 forge：以前在邮件列表里传 git 补丁（Linux 社区还这样），后来代码集中到 GitHub；现在大家还在 Slack 里互相粘贴 Claude 的回答，复制、转给同事、粘进他的 Agent、再传回来。应该把 Notion、Google Docs 等处的设计和决策尽量和代码放在一起，不只知道代码是什么，还知道背后的决定。
  • 不是什么都能买到：VM 可以买也可以自备；开发环境对每个团队都很个人化；Harness 可以用前沿的，也可以用 OpenCode 或 Pi 这类精简的再大改；还有控制平面，涉及会话和计划协作、自动化和调度、事件响应、治理。他说加入 Factory 让他兴奋的原因之一是 Factory 对这张图看得更全、解决得更多。但最上面那层，代码验证，没人能卖给你，只有你知道几百个工程师、几百个仓库要怎样测。

他说软件工厂是一种思考工作方式的方法，有些构件是同质化的，可以买。

反 slop 宣言

他宣布了 Anti-Slop Manifesto（slopmanifesto.com），和很多与会者、讲者一起写的，特别感谢了 swyx 和 Philip，签名者来自 ZoomInfo，他说好像还有 xAI 和 OpenAI 的人。价值观是：结果优先于产出，理解优先于速度，自己的思考优先于模型的初稿，更好的工作优先于更省事的工作，改进系统优先于修补产出。他们相信：AI 是多数人用过的最有用的工具，但一群 Agent 一天产出的东西，一个人一辈子都审不完。slop 的定义是：我们为产出某样东西投入的精力，少于我们要求接收方为理解它投入的精力。用 AI 不一定就是 slop，把 AI 的产出转手而不对质量和读者体验负责时才是。AI 不能替代人的判断，只能放大判断，或者放大判断的缺失。slop 是不对称的：生成一千行 PR 或十页文档的成本趋近于零，审查的成本却基本不变。slop 在我们反复绕开问题而不正确解决时扩散，来自只爱加不爱减的工具，也来自压力，公司在逼员工重新定义人力所能及的极限。slop 会复利，知识库、聊天、代码里的 slop 越多，下一个 Agent 读到并照抄的就越多，团队里 slop 越多，大家越没意志去对抗它。

（讲到这里他说有点热，脱掉了外套。）签署者承诺：珍惜人的时间和注意力；为高效引出人的意图、高效让人理解来优化系统、工具和产品；与模型合作时自己思考，先探索资料、代码、已有方案，理解问题再动手；不论 AI 帮了多少，都要拥有所交付东西的意图、品味和后果；发给别人的东西若是 Agent 写的要说明，并在发到 Slack 或邮件前确认它够好；收到 slop 时要友善、有同理心地反馈，请对方先自己审一遍，他说他两边都当过。他相信审查永远有超额收益：模型变好后我们也许不再读大部分代码，但仍会审计划、设计或结果；什么都不审、什么思考都不带，就只能得到和别人一样的 AI 产出。Agent 审查者、linter、验证器有用但不够。审哪些取决于利害；交付了什么、谁在用、怎样帮到他们，比代码行数、合并的 PR 数，更别说并行跑多少 Agent，重要得多。未经审查的产出不一定坏，一次性提示、vibe coding 放在合适的地方都是高杠杆，slop 只有在破坏你的目标时才是坏的。最后他说没人完全想清楚，每个人都在重新学习自己能接受什么。

27. Thariq Shihipar（独立工程师，前 Anthropic）：苦涩教训的甜的一面

直播位置 8:36:55–8:56:40

Thariq 离开 Anthropic 后反思了这一年，结论叫“苦涩教训的甜的一面”，以及自己哪里错了。苦涩教训（The Bitter Lesson）是 Rich Sutton 的说法：长期看，利用算力的通用方法总会胜过人为设计的巧思。他说自己说对了几件事：模型能编辑和生成视频（他去年 6 月左右就在讲）；模型能用 HTML 来帮助理解自己的工作；模型能帮你搞清楚自己的未知、帮你规划和学习。

他错在哪

  • “Bash 就是你需要的一切”：Claude Code 围绕 Bash 工具构建，大家以为一切都会变成 CLI。实际并非如此，他现在更喜欢 MCP 而不是 CLI，还有 code mode、Skill、渐进式披露，Agent 作用于世界的方式很多，用 Bash 只是早期训练方式留下的痕迹。
  • “React 就是你需要的一切”：一度看起来模型特别会写 React，做 AI 应用就该用 React、React Native、全放到网页上。现在模型写 HTML、React、Swift、Figma 的私有 JSON 格式，效果差不多；他曾担心 React 会成为最后一种语言，现在很多人在写自己的语言。
  • “扩散模型会吃掉艺术”：他担心我们对这些模型及其作品毫无控制，结果并非如此，LLM 能通过代码、控制电脑用 Blender、Photoshop、Figma 来创作。

他说这些担心都来自对苦涩教训的一种恐惧：模型是外星智能，像修格斯（shoggoth），有自己怪异的做事方式，我们只能接受、服从。他认为事情不是这样发展的。他关心的问题是：怎样既相信 AGI 又以人为中心。软件工程师是 AI 采用的最前沿，软件上发生的事会发生在知识工作和其他经济领域。

工业革命与文艺复兴

他说 AI 同时是一场工业革命和一场文艺复兴。今年主要是工业革命，大家常说软件工厂，把不可靠、难执行的手艺变成不再是瓶颈的东西。同时人们想要质量越来越高的软件，每一点创造力、实用性、灵魂都有用、有经济价值，这两件事很难同时放在脑子里，但都在发生。

人们谈能力时常说“锯齿状前沿”（jagged frontier）：两年前让 AI 写函数，后来做功能、做待办应用、克隆 Slack，现在从零做 Mario Kart 再移植到 Wii，评测和基准看到的是这种参差的前沿。他更想讲“平滑内部”：前沿之下，模型能做的事并不参差，写 React、写 Figma、写 JSON 都行，覆盖面很广。他说他已经不在乎模型能不能从零做 Mario Kart，在乎的是做出来的软件质量高不高，配不配得上文艺复兴。做原型时可以要 HTML、React、Figma 文件，或者让它用 After Effects 做视频。他说推到极限，所有 Harness、软件工厂和脚手架，甚至“人的工作是 QA 模型或审代码”，都会被平滑内部吸收，完美的模型不需要验证自己的工作或扫描安全漏洞，写完说“我做完了”，你一查确实按规格做对了。

他展示了一个可视化（他说好像是 Karpathy 发的）：给模型一个经纬度，问是陆地还是水，据此画出世界地图。Opus 4.6 画得比较模糊，Opus 5.5 几乎完美。他说这比基准更能说明模型的一般知识，也说明我们可以用智能来理解和塑造我们怎样使用智能，他认为这会是明年的主题。

他的游戏和“给人读的代码”

他在做一个 2D 等距视角的格斗游戏，灵感来自《降世神通》和任天堂大乱斗，常在 Twitter 上发。他想当个出色的 vibe coder，但很挫败：他说“让这个角色扔石头”，模型就替他做了一堆选择，这个角色还能召唤墙，那石头穿不穿墙、速度多少、大小、蓄力怎样；他试玩后完全不知道角色到底做了什么。他容易分心，发出提示后去做别的事，回来时不在状态，进展反而更少。他一度以为和 AI 合作就是这样，后来觉得不对：AI 可以按我们想要的方式工作，这样做不出伟大的软件。他引用 Dex 的话，好作品来自一个你不确切知道自己要什么的混乱过程，更多在于你做了哪些选择、没放进什么；要做出好东西就得是行家，得真懂。

他的做法（他说还在早期）：代码库分两部分，一部分是引擎代码，相机等他不懂的东西都在这里；另一个文件夹（叫 spec 或 human 之类）是他会读的代码，有 lint 和给 Claude 的规则，要求读起来像英语、像规格，密度刚好让他一读就懂、能改，是游戏的事实依据。他现场演示：每个角色的招式写在这里，比如扔石头的招式有一堆可调参数，注释清楚，用“米”这样的单位而不是 0.5 这种数字，能看出这个角色扔石头有三种方式：从地上拿、从墙上拿等。他说这等于给游戏做了一种自定义脚本语言。他把石头尺寸改成 1.5，进游戏蓄力、变大、扔出。他还开始更多用 Cursor 和它的 Tab 补全模型，比如写“如果中间召唤了墙，就把它排进动作队列”，Cursor 帮着补全。他说这有点像规格驱动开发，只不过规格是这种脚本语言。复杂的事还是要让 Claude 做，让 Claude 造基础件，但他很容易看懂发生了什么，感觉更有掌控，Claude 工作时他也能边审边配合。

他的结论是：现在要想的是怎样最好地交付高质量软件，不再受模型能力或模型偏好的语言限制。他列了很多可做的方向：新语言（既要 Rust 那样高效，也可能要模块化、可热重载、可读）、新基础件（新型数据库、服务器、操作系统交互，他 vibe coding 了很多改动操作系统行为的个人软件）、新交互范式（很多老的人机交互研究值得重新看）、新美学。模型不是要强迫我们按某种方式工作的外星智能，它们几乎什么都能做，我们的工作是决定工作的未来和理想体验的样子，带来文艺复兴。
