01. Santosh（Agnostiq，开源项目 Covalent）：用纯 Python 批量微调和部署模型

直播位置 0:23:54–0:30:20

主持人介绍他来自 Agnostiq，题目是怎样加速训练，特别是 Llama 的微调。他自己说这场只有五分钟，重点是“直接从 Python 把事情跑起来”，不需要 Kubernetes、Docker 之类的基础设施知识。演讲材料和代码放在一个二维码里。

Covalent 是什么

Covalent 是一个开源核心（open core）的产品。思路是：你在本地写 Python，把代码发送到任何需要的计算后端去执行。比如本地 Jupyter notebook 里有一个函数，在上面加一个装饰器（decorator，Python 里写在函数定义上方、用来给函数附加行为的 @ 语法），声明“我要在 H100 上跑，36GB 内存，最多两天”，按 Shift+Enter，代码就被送到 GPU 后端执行，结果再传回本地。

  • 开源版本把任务发到你自己接入的计算集群；云版本发到他们的 GPU 集群，按实际运行时间收费，跑 5 分钟付 5 分钟，跑 10 秒付 10 秒。
  • 也可以把自己的云或本地机房接进来，由他们负责编排。
  • 推理部署同样是 Python 写法：定义一个初始化函数和一个 /generate 端点，调用 cc.deploy，就得到一个能缩到零、也能随请求扩容的 API 端点。自动扩缩容规则可以自定义，例如每天 9 点扩到 10 张 GPU、GPU 利用率超过 80% 时扩容、请求数到一千时扩容，还可以配鉴权。

演示：批量微调、选最优、再部署

他展示的代码分几步。先在本地包里写好普通的训练和评测函数；然后定义一个微调任务，指定 24 核 CPU、1 张 48GB 的 H100、最长 18 小时；评测任务接收微调后的模型并算准确率；排序任务只用 CPU，因为排序不值得占 GPU；最后把表现最好的模型部署成 /generate 端点。一个工作流函数把这些串起来：循环遍历一批模型，逐个微调、评测，把结果排序，部署最好的那个。

提交之后，前端界面里出现一个新任务，每个函数在各自声明的硬件上运行。他点开其中一次评测：在一台 L40 上跑了 6 分钟，花了 87 美分；另一个在 V100 上跑了 6 分钟，花了 11 美分（字幕原文如此）。整个微调到部署的流程都只用了 Python。

02. Dylan Patel（SemiAnalysis）：怎样跑 Llama 3 405B 级别的模型，以及十万卡集群

直播位置 0:30:20–0:49:57

主持人介绍 Dylan 时提到他在 SemiAnalysis 写的 GPU、TPU 供应链分析。他这场分两半：前一半是现在就能用上的推理技术，后一半他自己称作“脑袋在云里”的内容，讲正在建的超大集群。

为什么大家觉得模型“停滞”了

他说很多人在谈模型能力停滞，原因是最近没有出现大的能力跃升。今天用的模型和 2022 年训练出来的模型大体是同一代：GPT-4、GPT-4 Turbo、GPT-4o 都是更小、训练更久的模型，质量相近。Claude 3.5 Sonnet 比 Opus 小，但训练得更久，所以反而更好。更大的模型还没出来，但很快会出来。

他给出的 GPT-4 规模是约 1.8 万亿参数，每个 token 激活约 2000 亿参数，每个 token 需要将近 600 GFLOPs 的计算。他说一年后这会被当成上一代模型。

推理的两个阶段：Prefill 和 Decode

大模型推理（Inference）分两步。预填充（Prefill）是处理输入提示词，一次性把整个 prompt 过一遍模型；解码（Decode）是逐个生成 token，每生成一个就喂回模型继续生成。

  • Prefill 是计算密集型。他说对 GPT-4 这个规模，一个 2000 token 的提示词就要 1 PFLOP 的计算，32000 token 的提示词要 20 PFLOPs。
  • Decode 是内存带宽密集型。每生成一个 token 都要把模型权重从显存读进计算单元。在合理的批大小下，MoE 模型的所有专家都会被激活，等于每步都要读全部 1.8 万亿参数。
  • 他的算法：如果每个用户要 30 token/秒（他认为这是多数人的最低要求，很多人想要几百），同时服务 64 个用户，就需要约 60 TB/s 的内存带宽，而一张 H100 只有约 3 TB/s。
  • Decode 吃带宽但计算很便宜，这就是 OpenAI 和 Anthropic 的定价里输入和输出差 3 到 4 倍的原因。他举的价格是每百万 token 输入 5 美元、输出 15 美元。

跑 405B 开放模型必须有的几项技术

他说对在座的人来说，真正能摸到的是即将发布的 Llama 3 405B，这会是开源市场的一次能力解锁。但不能指望用 llama.cpp 去跑它。可选的推理库有只支持 Nvidia 的闭源 TensorRT-LLM，以及开源、支持 AMD 和 Intel 的 vLLM。

  • 连续批处理（Continuous Batching）：在云上以批大小 1 跑推理，成本会高 10 倍，甚至 10 到 100 倍。要用大批次，但用户请求到达时间不同，第一个人的请求还没结束，第二个人已经来了，所以要能在每一步迭代时把新用户加进批次。他说 llama.cpp 这类软件当时还不支持，要么自己做，要么去给开源项目贡献。
  • 分离式预填充（Disaggregated Prefill）：既然 prefill 吃算力、decode 吃带宽，量大以后就用一组加速器专门做 prefill，再把结果交给另一组做 decode。他说 Google 公开说过在这样做，他相信 OpenAI 和 Anthropic 也在做，Together 和 Fireworks 也暗示过。主要原因是“吵闹的邻居”（noisy neighbors）：用特定方式发请求就能明显拖慢大多数推理服务，首 token 延迟（time to first token）变长用户就会走，每秒 token 数忽高忽低也很烦人。例如有人一次提交一万行数据库记录让模型逐行处理，会拖垮其他所有人。他认为用速率限制去挡是最糟糕的办法。
  • 上下文缓存（Context Caching）：Google 刚为 Gemini 1.5 Pro 推出，上下文可到 200 万 token。他的看法是，最好的模型很难或根本没法微调（Claude 3.5 Sonnet 不能微调，微调 405B 要几十张 GPU），与其微调，不如把自己的数据填进长上下文。问题是像法律合同审阅这类企业场景，输入一大份文档、输出很短，成本几乎全在 prefill 上。缓存的做法是不再每次重算 KV Cache（模型处理过的 token 留下的中间结果，下次生成时直接复用），但它占用大量内存，所以放在 CPU 内存或存储里而不是显存。他说 vLLM 正在做这个功能，欢迎贡献。

正在建的十万卡集群

  • GPT-4 训练用了约 2 万张芯片、90 到 100 天、约 38 GWh 电力，训练量约 2e25 FLOPs。OpenAI、xAI、Anthropic 等现在在建 10 万卡集群，同样的训练三天就能完成。新集群能做 1e26 到 1e27 FLOPs 的训练，模型可能有几十万亿参数，跑它需要几百 TB/s 的内存带宽。
  • 他放了微软在亚利桑那州数据中心的照片，说那里在训练 GPT-5，约 10 万张 GPU、150 MW，相当于几万到几十万户家庭的用电。
  • Elon Musk 说过下一代集群要 30 万张 GPU，光电费一年约 5 亿美元，集群本身造价超过 100 亿美元。
  • 今天训练讲的是全互联集群，每张 GPU 都以某种速度连到其他每张 GPU。到这个规模已经做不到，10 万卡集群跨好几栋楼，明年还要建多个，需要复杂的跨数据中心网络。
  • 光模块和光收发器很不可靠，平均大约 5 年坏一次。到 50 万卡的规模，大约每 5 分钟就会有东西坏掉。
  • “硅彩票”（silicon lottery）：同一型号的芯片速度并不完全一样。训练是同步负载，一张卡慢 10%，整体就慢 10%。他引用 ByteDance 的论文：在 2 万卡集群上，一张按 Nvidia 标准“正常”的 GPU 让整体速度下降了 25%，拔掉后性能明显回升。

他最后说，今天大家给 LLM 搭的很多脚手架是在对付幻觉之类的问题，而做 AGI 的人希望把算力放大 100 倍后，这些问题会被新模型解决。实验室已经不在为 405B 级别的模型操心了。

03. Sunny Madra（Groq）：推理速度和 AI 带来的软件工业化

直播位置 0:50:08–1:10:17

Sunny Madra 在 Groq 工作，此前创办的 Definitive Intelligence 被 Groq 收购，更早在福特（收购 Autonomic 之后）待过。他说这是一场全新的演讲，可能有点粗糙。

从 1 GHz 说起

25 年前的 1999 年，Intel 的微处理器突破了 1 GHz。他原以为更早，查了几遍才确认，并放了当年的新闻稿。他提这件事有两个原因：那是一个标志性的数字；之后 Intel 开始改变处理器的思路，转向多核。微处理器用了大约 20 年把速度提升了三个数量级，而他说包括 Jensen Huang 在内的很多人认为 LLM 的进步已经超过摩尔定律的曲线。

他的例子：Groq 在今年 4 月到 6 月之间把 Llama 3 8B 的速度提高了 50% 以上。现在已有模型能以每秒约 1 万个输入 token 的速度处理输入，处理一大段输入只要三分之一秒左右，在整合和分析信息的速度上远超人类。

例子：globe.engineer

他推荐了一个叫 globe.engineer 的服务。他让它规划一次去纽约吃最好披萨的旅行，它联网实时拆出所有要素：航班、打车、酒店、餐厅、行程，大约五秒内完成。他说自己规划旅行会开几十甚至上百个浏览器标签页，每个标签页是一条调研线，现在都收进了一个界面。这依赖于模型读输入和写输出都足够快。

软件的工业化

他用工业革命做对照：食物、汽车、衣服在工业革命之前都是手工定制，工业革命后能按国家规模生产。技术领域还没有过这种工业化。他引用 Paul Maritz（长期在微软，后来在 VMware、Pivotal，他们在 Pivotal 认识）的框架：第一个时代是把纸面流程数字化，所以操作系统里有文件、文件夹、收件箱、发件箱；第二个时代是联网，也就是互联网；最近 15 年是形态变化，上云和上手机。AI 带来的是技术的工业化。他的例子是 18 到 24 个月前，要一张演示用的 Photoshop 图得找设计师，一天出一两张；现在用 Midjourney 一分钟能出一千张。

如果单次决策能压到 0.1 毫秒，一秒就能做 1 万个复杂决策，那么把 LLM 当作计算的核心就变得可行。他引用了 Karpathy 画的 LLM 操作系统示意图：LLM 居中，连着音视频、浏览器、其他 LLM、代码解释器和文件系统。

速度起来以后能做的事

他列了一串他们准备演讲时想到的方向：

  • 即时响应和决策：像 globe 那样，把一个下午或几个晚上的任务压到几秒。
  • 个性化：他提到 Bill Gurley 和 Brad Gerstner 在他们的播客里认为个性化是下一个大方向，个性化和速度要一起才行。
  • 通用的自然语言交互和多模态混合交互，他们称之为 xRx（任意输入、推理、任意输出）。例子：订理发时用语音问有哪些时间，但答案“9 点、11 点、3 点半、5 点半”用语音听很难记，最好用文字显示出来。
  • 复杂任务的高级助手：今天评测 LLM 通常看单次（single shot）结果，但多次尝试、多个 Agent 协作，小模型也能和大模型竞争。他提到 Apple Intelligence 里端侧和云端协作的早期实现。
  • 预测性分析：算力接近免费时，可以有一直在后台运行的 Agent。
  • 创作工具：他喜欢让 LLM 用当下的新闻写一集 Seinfeld，模型很会判断哪个角色会遇到好笑的事。
  • 复杂决策：Definitive Intelligence 做过 Text-to-SQL，同事 Rick（在现场）做过一个叫 Pioneer 的自动数据科学 Agent，可以几乎无限期地盯着一个业务的 KPI 和新数据持续提问分析。他们让 Pioneer 分析一份员工绩效数据，它发现某个年龄段拿到某类绩效评价后生产率会下滑（他说细节可能要 Rick 纠正）。
  • 动态优化：他们在福特时看到汽车生产和运输的供应链软件仍然不够高效。
  • 边缘和去中心化 AI：他提到 hyperspace.ai，类似 SETI@home，让人把闲置 GPU 贡献出来，适合不要求实时的任务。
  • 安全和隐私：一位同事接到一个电话诈骗，对方掌握大量信息、叙事很完整。他认为以后要有跑得很快的 AI 站在用户这边做防护。
  • 教育：他引用 Sal Khan 的 TED 演讲，一对一辅导可以让学生成绩提高两个标准差。他见过一个家庭教育 AI 服务，孩子喜欢独角兽和小马，就用它们来讲加减乘除。
  • 互操作性：企业软件的大部分钱花在部署、维护和系统互联上，快而便宜的 AI 能减轻这部分负担。

04. Crusoe 网络产品经理：轨道优化的 GPU 集群网络和 MoE 训练加速

直播位置 1:11:06–1:28:24

讲者是 Crusoe 负责 GPU 网络基础设施的产品经理（字幕里的姓名不清，这里不写）。主持人介绍的题目是加速混合专家模型（Mixture of Experts，MoE，模型里有多组“专家”子网络，每个 token 只走其中几组）。

Crusoe 是什么

Crusoe 是一家 AI 云平台，使命是“让计算的未来和气候的未来对齐”。GPU 很耗电，数据中心投资给电网带来压力，他们用被浪费的、困在当地送不出去的能源（stranded energy）和可再生能源给数据中心供电，目标是 100% 用这类能源、做到净零新增排放。平台有三个支柱：高性能（基础设施的任何延迟、故障或性能不佳都直接增加客户的训练时间和成本）、易用（区别于什么场景都支持的超大规模云，专注 AI 工程师的体验，把底层复杂度藏起来）、气候友好。

  • 数据中心：美国本土三个，靠近能源所在地，包括德州一个、中北部一个、东部一个；正在冰岛建一个用地热供电的大数据中心，也方便欧洲（EMEA）客户的延迟和连接。
  • 产品：带 GPU 的虚拟机，可以把多台连成一个训练集群；用于数据预处理的 CPU 实例；本地 NVMe 的临时盘和持久盘、持久块存储，托管网络文件系统在做；前端 VPC 网络、防火墙，负载均衡器即将推出；以及接下来重点讲的轨道优化 InfiniBand 集群网络。
  • 用户体验：CLI、API、图形界面，全部可以自动化。
  • 客户：他说在展台区看到很多客户。Together AI 用他们做训练、微调，有时做推理；Codeium 等用他们训练基础模型。

分布式训练里网络占多少时间

分布式训练每完成一步，所有 GPU 都要交换各自算出来的数据，通常通过 all-reduce、all-gather 这类集合通信完成。他说在没有优化时，网络通信占训练时间的 25% 到 30%，这段时间 GPU 只能闲着等。把计算和通信重叠（一边算一边开始传数据）能减少约 10%，但和客户合作时看到仍有大约 25% 的时间花在网络上。作为产品经理，他经常被问怎么缩小这段差距。

拓扑：从胖树到轨道优化，再到 PXN

  • 传统做法是胖树（fat tree）拓扑，可扩展、可以做到无阻塞，但如果服务器都接到同一台叶交换机（leaf），那台交换机就是单一瓶颈和单一故障域，坏了就丢掉所有连着的 GPU。
  • 轨道优化（rail-optimized）的做法：同一台服务器内的 GPU 用 NVLink 和 NVSwitch 直接通信；不同服务器上编号相同的 GPU 接在同一台叶交换机上，称为同一条“轨道”，互通只要一跳。
  • 问题是跨轨道通信要一路走到脊交换机（spine），多一跳，还可能带宽饱和，增加延迟，影响 all-reduce。
  • Nvidia 在新版 NCCL（Nvidia 的 GPU 集合通信库）里加了 PXN 功能：跨轨道时先在主机内部经 NVSwitch 把数据转到对应轨道的 GPU 上，再发到那条轨道的叶交换机，这样跨轨道也只要一跳。例如一台主机的 GPU 0 要和另一台主机的 GPU 8 通信，就先在本机内部转一次。

结果

NCCL 测试里，小消息和大消息都看到约 50% 的提升；小消息主要看延迟，大消息主要看带宽。他说这些合成数字大家都爱看，但客户真正关心的是训练某个模型要多久。所以他们用开源的稀疏 MoE 模型 Mixtral（8 个前馈块，8×7B）在 240 张 H100 上做微调，MoE 的专家之间会产生大量 GPU 间流量。开启 PXN 后训练时间改善了 14%，可以直接换算成训练时间和成本，客户对这个数字更有感。

05. Kathleen Kenealy（Google DeepMind）：Gemma 模型家族和 Gemma 2 发布

直播位置 3:09:07–3:27:51

午休和调音之后的第一场。讲者是 Google DeepMind 的研究工程师、Gemma 的技术负责人（自我介绍处字幕被音乐盖住，姓名据后一位讲者的提及和会议资料补全）。这天正好是 Gemma 2 发布日。她说做 Gemma 时的北极星是赋予开发者能力、加速开源社区，自 2 月发布第一批模型以来，社区在 Gemma 上做出的项目让她很惊讶。

Google 和开放研究

她先回顾 Google 过去十年发表的关键研究，比如 Transformer、SentencePiece、BERT，以及从 TPU 硬件到 TensorFlow、JAX 框架对整个技术栈的支持。Gemma 是这条线上最新的投入：Google DeepMind 的开放、轻量、最先进的模型家族，用的是和 Gemini 相同的研究和技术。（演讲中她的手机在包里响了，她让旁边的人帮忙翻出来关掉。）

Gemma 的几个特点

  • 负责任的设计：从第一天起安全就是首要事项。人工检查数据集，既要高质量也要安全；从最早的实验和消融（ablation，逐个去掉某个设计看效果变化的实验）就评估安全，选择能产出更安全模型的训练方法；最终模型和 Gemini 用同一套严格的安全评测。
  • 同尺寸下的性能突破，能超过明显更大的模型。
  • 可扩展：针对 TPU、GPU 和本地设备都做了优化，支持 TensorFlow、JAX、Keras、PyTorch、Ollama、Transformers 等框架，几乎能找到开放模型的地方都有 Gemma。
  • 开放访问和开放许可。

家族成员

  • Gemma 1.0：基础 LLM。后来更新为 Gemma 1.1，指令遵循和对话更好。
  • CodeGemma：在 Gemma 1.0 上为代码生成和代码评估微调，后续也更新过。
  • RecurrentGemma：她特别喜欢的一个，新架构，她称之为一种状态空间模型（State Space Model，一类不用标准注意力、靠递推状态处理序列的结构），为更快、更省的推理设计，长上下文时尤其明显。现在有 2B 和 9B 两个尺寸。
  • PaliGemma：社区从第一天起呼声最高的功能就是多模态。PaliGemma 把 SigLIP 视觉编码器和 Gemma 1.0 文本解码器组合起来，可以做图像问答、图像和视频描述、目标检测、目标分割。目前只有一个尺寸（字幕作 2B）。有可继续微调的预训练权重、面向检测和分割的微调版本，以及针对若干学术基准的迁移检查点。

Gemma 2

  • 两个尺寸：9B 和 27B。她说两者都是同尺寸中性能最好的，并且能超过大两到三倍的模型。
  • 和 Gemma 1 用同一套工具和框架，已经在用 Gemma 1 的人改几行代码就能切换。
  • 文档大幅改进，从第一天起就有推理和高效微调的指南、教程。
  • 团队专门研究了核心建模决策如何影响下游微调，她认为这批模型会很容易微调。
  • 27B 已经上线 Google AI Studio，打开主页选 Gemma 2 就能直接试提示词。

性能数字

她说 27B 的学术基准表现和 Llama 3 70B 在同一水平，在很多基准上明显超过 Grok。但学术基准只是一部分，他们也做了大量人工评测，Gemma 模型一直比其他开放模型（包括更大的）更受偏好。在 LMSYS 竞技场上，27B 是同尺寸排名第一的开放模型，排名高于 Llama 3 70B、Nemotron 340B、Grok、Claude 3 等；任何尺寸的开放模型中只有 Yi-Large 排在它前面。相比 1.0 和 1.1，Gemma 2 指令遵循更好、更有创造力、事实性更好。

怎样上手

  • GitHub 上的 Gemma Cookbook：20 个从简单到高级的示例，接受 pull request，欢迎把自己做的东西提交进去。
  • 可以申请 GCP 额度做基于 Gemma 2 的研究，她鼓励不管项目大小都去申请。
  • 各框架的指南、教程和 Colab，覆盖推理、微调和评测。
  • 她说自己在这个项目上做了快两年。当初加入，是因为她在学术界做研究时，看到开放的基础 LLM 远远落后于闭源模型的进步速度，这是她当年希望拥有的东西。

问答

主持人问她最想看到大家用 Gemma 做什么。她说安全和责任方面的研究还远远不够，开源社区里做更私密、更安全模型的工作会很有意思；她也期待像 RecurrentGemma 那样把 Gemma 改造成新架构的工作；最期待的是她完全不了解的研究方向。

问到 Gemma 1 发布后最让她惊讶的用法：Gemma 和 Gemini 用同一个分词器（tokenizer），虽然 Gemma 主要用英文数据训练，但很容易适配其他语言。印度的一个研究团队把 Gemma 微调到在 200 多种印度语言变体上达到最先进水平，这个项目在 Google I/O 上也展示过。另一个是一家小企业，收到的订单邮件格式五花八门，他们微调 Gemma 把这些邮件整理成按优先级排列的待办订单，这个例子会进入 Cookbook。

06. Dmytro Dzhulgakov（Fireworks AI）：把开放模型推上生产

直播位置 3:27:51–3:47:47

主持人说 Fireworks 的 CEO 因个人紧急情况来不了，由 CTO Dmytro 代讲。他自我介绍：Fireworks 的创始团队来自 Meta 的 PyTorch 负责人和几位 Google AI 的老员工，合计有大约十年在大公司把 AI 推上生产的经验，他本人做了五年 PyTorch 核心维护者。他们相信开放模型也是生成式 AI 应用的未来。他现场问了一下，用 GPT 做生产的人和用开放模型做生产的人都不少，他说开放模型的份额在这个听众群里已经相当大了。

为什么选小模型

目前大部分生产推理仍然跑在闭源模型上。这些模型很好，往往在很多领域是前沿，但它是一个什么都会的模型，而且不管用途都用同一种方式提供服务。你的客服机器人不需要认识 150 种宝可梦，也不需要会写诗，但你要为这些能力付钱。由此带来几个问题：

  • 延迟：大模型响应慢，对语音助手这类实时场景、以及需要多次调用模型的 Agent 类应用很要命。在窄领域里，选 Llama 或 Gemma 这样的小模型可以做到同等或更好的质量，速度快到 10 倍。他举 Berkeley 函数调用基准：微调过的 Llama 3 能以约 10 倍速度达到相近表现。
  • 成本：他举了一个例子，5000 token 的提示词、1 万个用户、每人每天调用 20 次，用 GPT-4o 也是每天上万美元的量级，他接着说一年约 3000 万美元（字幕里的几个数字前后对不上，这里照录他的说法）。换小模型可以大幅削减。
  • 领域适配：开放权重意味着可以针对自己的场景微调。Hugging Face 上有上万个模型变体，有专门做代码、做医学的，前一位讲者提到的印度语言版 Gemma 也是例子。

用开放模型的三个难点

一是部署和维护复杂：要找 GPU、选框架、下模型、调性能，每次模型更新都要从头再来一遍。二是优化：延迟优先还是吞吐优先，提示词长还是短，全栈的设置都依赖具体用例，选得好能有数倍的差距。三是生产就绪：公有云上的 GPU 不总是可靠，企业级还需要可扩展性、遥测、可观测性。

Fireworks 怎么做

  • 自研推理栈，从手写 CUDA kernel 到服务层的部署编排都自己做，并且按客户的负载、成本和延迟要求定制。
  • 例子：很多用例用 RAG（检索增强生成，先检索相关资料再放进提示词让模型回答），提示词很长且经常重复，可以在运行时和部署层面针对长提示词调优，比如用缓存、在维持延迟的同时提高吞吐。他说在 Artificial Analysis 上选长提示词场景，Fireworks 是最快的。
  • 多模态：SDXL 图像生成他们最快；他们是唯一提供 SD3 的服务商，因为 Stability 自己的 API 也路由到他们的服务器。
  • 他推荐的性能思路是“在给定延迟约束下最小化成本”。客户常说“我的交互应用要在两秒内生成这么多 token”，在这个约束下跨栈调参，可以把吞吐提高数倍，吞吐高就是 GPU 少、成本低。
  • 模型支持：Gemma、Llama、语音识别和语音合成模型；也和模型开发者合作，例如上周上线的 Yi-Large 在美国就由 Fireworks 提供服务。
  • LoRA 多模型服务：LoRA（低秩适配，只训练插在原模型上的一小组参数）微调出来的模型，可以成千上万个部署在同一张 GPU 上，所以即使有上千个变体，也能按 token 计费的无服务器方式使用，不用付固定成本。

复合 AI 系统和函数调用

他说越来越多的应用里，模型本身不是产品。模型会幻觉，需要用 RAG 接外部知识；还没有通吃所有模态的模型，要串起多种模型；还要调用外部工具和执行动作。他喜欢 Databricks 推广的说法“复合 AI 系统”（Compound AI System）。他认为这个架构的核心是一个负责函数调用的 Agent 模型，连着各个领域专用模型和外部工具（代码解释器、外部 API 等）。函数调用（Function Calling，模型输出结构化的调用请求，由程序去执行外部函数）是 OpenAI 最先推广的。

他们专门微调了函数调用模型系列，最新的 FireFunction v2 两周前发布。演示应用把通用聊天和函数调用结合，接了股票报价、画图、图像生成等工具：

  • 问它能做什么，它会自我描述。
  • 让它“画出三大云厂商股价的柱状图”，它要先理解三大云厂商是 AWS、GCP、Azure，知道 Azure 属于 Microsoft，然后分别调用股价接口，再把结果交给画图 API。
  • 再说“把 Oracle 加上”，它要记得上文并重新生成图。
  • 换一个话题（比如要一张猫的图片）时，它要知道丢掉之前的上下文，猫图里不会出现 Oracle。

这个演示应用开源在他们的 GitHub 上，模型本身也开源在 Hugging Face，可以本地运行。它用了平台上的结构化生成功能（JSON 模式、语法模式），他说和前一天 Outlines 团队讲的内容类似。

产品形态和客户

  • 无服务器（serverless）推理：按 token 付费，体验和 OpenAI playground 差不多，也能部署自己的 LoRA 微调。
  • 按需（on-demand）专用硬件：可配置，可以上传自己从零训练的模型。
  • 企业级：长期合约折扣，并帮客户做前面提到的性能定制。
  • 他说上次查看时每天处理约 1500 亿 token。客户有做 Poe 的 Quora、Sourcegraph、Cursor（代码助手里对延迟很敏感的功能），以及 Upstage、Liner 等做助手和 Agent 的公司。
  • 他引用去年 LangChain 的 State of AI 数据：在开发者拉取模型的平台里，他们仅次于 Hugging Face。
  • API 兼容 OpenAI，可以继续用原来的客户端或 LangChain、LlamaIndex 等框架。

07. Scott Wu（Cognition）：Devin 的早期构建和软件工程的未来

直播位置 3:47:47–4:07:04

主持人问现场谁听说过 Devin，大部分人举手。Scott Wu 是 Cognition 的联合创始人，他说他们还在很早期，这场讲 Devin 的早期构建、这个领域的现状和接下来会发生什么。

现场演示：记名字小游戏

他当天早上让 Devin 做了一个适配手机的网站来玩“记名字”游戏，因为他很难记住人脸和名字。他给了一个 TSV 文件，里面是这届大会全部讲者的名字和照片（大约 170 位），要求每次显示两张随机的脸和其中一人的名字，让他猜是哪一个。

  • 他说 Devin 是“完全自主的软件工程师”，能用人类工程师会用的所有工具。
  • Devin 先做计划，计划会随着新信息和反馈不断更新；然后像人一样新建目录、创建 React 应用、读 TSV 文件、写代码，几分钟后部署了第一版。
  • 第一版接近但不完全对：名字一开始就显示出来了，他说可能是自己没交代清楚。他用普通英语继续反馈：点答案之前隐藏两个名字、重新设计“再玩一次”按钮、加连胜计数器、答错归零。
  • 最终版本现场可玩，他故意答错一次，连胜清零。他说自己真用这个游戏记住了所有人的名字，网站附带的二维码页面也是 Devin 做的。

在自家生产代码库里用 Devin

Devin 的会话列表里有一个跨会话的搜索栏，是 Devin 在 Devin 自己的仓库里做的。团队成员 Bryce 让 Devin 在会话列表里加搜索组件。针对生产代码库的几个特点：Devin 从一个机器快照启动，仓库已经克隆好；有一份 Playbook，记录了仓库的很多细节；能在 git 环境里工作并提 PR。对话过程像和另一位工程师合作：Bryce 说开头不错，再加个放大镜图标，用 Phosphor 图标库写得地道些；又说不用测试了，相信你；Devin 回报登录流程有点问题。这个 PR 最终合并了。他说 Devin 的很多 API 集成、内部仪表盘和指标追踪也是 Devin 写的。

公司历程

他们 11 月开始，至今约七个月。起步于 Burlingame 的一个黑客屋，很多人之前就一起住过，各自都有 AI 方面的经历，想一起做和代码有关的 Agent。之后在纽约和湾区之间来回搬，每次换一个稍大的 Airbnb，因为团队在变大，现在准备在湾区定下来。

为什么做 Agent，为什么是代码

他说生成式 AI 的第一波是文本补全类产品：语言模型的接口本来就是给前缀、补后缀，ChatGPT、问答产品、写营销文案、客服，甚至 GitHub Copilot 和 Cursor 都属于这一类。新一波开始引入自主决策，也就是 Agent。它要求高得多的一致性，但能解锁新的东西；这既是核心能力问题，也是一个很新的产品设计问题。

代码特别适合 Agent 的原因：

  • 软件工程远不止打字写代码：查 bug、翻代码库里的不同文件、跑命令、查文档、自己启动前端复现问题、改一处再试。这本身就是一个 Agent 式的工作流。
  • 可以用代码反馈来迭代：面对几千个文件、几十万行代码的生产代码库，直接找 bug 对人和 AI 都难。实际做法是加 print、看日志、看监控、在文件间跳转，每次决策后都运行真实代码看结果，这给了一条更清楚的解题路径。
  • 模型的 Agent 能力进步很快。两年前，连这个记名字游戏都几乎不可想象。

Agent 的产品体验问题

他说大家刚开始做 Agent 时，会自然地去类比现有软件和人与人之间的交流，Devin 的不少功能就像“从实习生肩膀后面看他干活”，能看到它的电脑和它在跑的命令。但 Agent 和这两者都不同，在并行工作、信息收集、上下文管理等方面有很多细节。他列了他们做的部分功能：用 shell、改代码、浏览网页、分叉和回滚会话、Slack 和 GitHub 集成、Playbook、机器快照、密钥管理、用合适的工具做验证。新功能是可以通过 VS Code Live Share 进入 Devin 的机器，直接在里面改几行代码，同时和 Devin 对话。

它怎样改变了他们自己的工作方式

他们现在用更异步的方式处理任务：一个工程师当天有四个任务，就分给四个 Devin 并行跑，他说这把每个工程师都变成了工程经理。他形容 Devin 是热情的实习生：很努力，不是什么都懂，会犯小错，会问很多问题。当天的例子是讨论某个功能时，在 Slack 里 @Devin 改个颜色，它提 PR，人点合并。他们常常在健身房或车上这样“写代码”：描述清楚要什么，之后再审代码。

软件工程师会怎样

他说 Devin 不决定做什么。软件工程师其实同时在做两份工作：一是用代码解决问题，拆解方案、定架构、想清楚流程和边界情况；二是实现，包括调试、写函数、写单元测试等。他估计今天普通工程师花 10% 到 20% 的时间在前者，80% 到 90% 在后者。Devin 把人从实现中解放出来，不用自己去搭 Kubernetes、调坏掉的 API、处理版本升级和迁移，工程师更像技术架构师和产品经理的混合。

他认为工程师会比以往更多。编程曾经意味着打孔卡，后来是汇编，再后来是 C，今天很少有人用打孔卡，但程序员多了很多。他说软件是过去四五十年推动世界进步的头号力量，但社会对软件的需求可能是当前产出的 10 倍以上，所以会有更多人能用上软件工程，每个工程师效率提高 5 到 10 倍，总的软件工程量也会大得多。

问答

  • 什么时候能用上：每周都在放开更多人，也在和企业客户扩大规模，等候名单很长，会尽快。
  • Devin 怎样复现问题：在他们的代码库里，Devin 有一台配置好的机器，能跑开发环境、服务端和前端，让它调试某个问题时它会自己启动、复现、修改、再试。
  • 简单任务被自动化后，初级工程师和实习生怎么学：他认为需求会随供给一起上升，培养方式会变，但基本功不变。说一个人是好工程师，通常指他理解问题、熟悉各种架构、不漏边界情况，打字快不快在其次。初级工程师会更早接触到这些基本功。
  • 实现愿景的最大挑战：几乎所有方面，速度、一致性、访问、集成、产品体验都是。他说好的一面是整个技术栈都在涨：每次新硬件、每个新基础模型、每项新的 Agent 研究都会让这条路更顺。
