01. David House（G2i 软件工程经理）：改变编程心态，Agentic Coding 落地的几个案例

直播位置 0:04:45–0:25:27 · 英文原题 Transforming Programming Mindsets: Case Studies in Agentic Coding Adoption

讲者和问题

David House 是 G2i 的软件工程经理，但他的本行是心理健康咨询。这是他第一次在大会上演讲。他听到很多人在用 Coding Agent（能自己读代码、改代码、跑命令的 AI 编程助手），也听到很多焦虑和恐惧，于是在团队里做了一轮访谈，问大家怎么开始用这些工具、经历了什么、感受如何，从中总结出一个“成功采用”的模式。

他说网上讨论 AI 编程时容易分成两极：一边说 AI 是“slop cannon”（垃圾代码大炮），一边说用不好是“skill issue”（你自己水平不行）。他认为两种说法都对，中间有一段可以学的东西。他花了很久琢磨的一张幻灯片写的是：对新手来说，Agentic 框架应该约束他的输入，因为新手不知道自己会在哪里犯错；对熟手来说，框架应该放大他的输入。框架既要改善 Agent 的输出，也要塑造人的输入。他的判断是这些技能对任何工程师都不直观，学校里没教过。

G2i 用的框架

案例都来自 G2i 的同一个项目。所有人都用同一套依赖文档和分阶段交接的流程：

  • /brief Skill：Agent 扮演产品经理，采访用户，产出产品简报。
  • /spec Skill：Agent 扮演技术架构师，再采访一次，产出技术规格。
  • /code 或 /tdd：两份文档作为带着工程师判断的提示词，交给 Agent 写代码。TDD 是测试驱动开发，先写测试再写实现。
  • /review 检查实现是否覆盖了文档里的所有内容，最后用一个起草 PR 的 Skill 省点时间。

他强调别被框架本身分散注意力，大部分框架做的是同一件事：把 Agent 编程里隐藏的做法摆出来；让 Agent 的推理和产出可以被审查；训练工程师学会有效地委派任务。新手可能一句话让 Agent 把整个代码库重写成 Rust，有经验的人会一步一步来。

四个案例

  • Ava：最早用 ChatGPT 帮家里想活动点子，这些只需要她自己认可。工作上她标准完全不同，不复制粘贴、不信任输出，很在意名声，不想交出烂代码。到了 G2i，项目从一开始就要求用 Agent。几个月后她把流程内化了，自己做了一个专门处理某种测试模式的子 Agent。
  • Lucy（四年经验）：在上一份工作里让 Agent 写过一个迁移脚本（从 Vite 和 barrel files 相关的结构迁移，他说懂的人都知道有多难），很成功。于是她在一个复杂的个人项目里一开始就全交给 Agent，结果代码重复、看不懂、审不过来，用的还是她不熟的技术，很受打击。G2i 的框架告诉她一件事后看来很明显的事：你得告诉 Agent 去写测试、跑测试、确认通过。她学到 Agent 编程就是把你作为工程师的判断写进提示词和审查机制。现在她不用框架了，改成和 Agent 长时间来回“面谈”，靠面谈把判断注入进去，面谈也帮她想起自己忘了说的事。
  • Antoine（15 年经验、创业公司创始人）：在 G2i 以“什么都能搞定”出名。早期用 Agent 很失望，审代码时发现必须处处小心，于是变得过度警惕，反而拿不到 Agent 的价值。G2i 的 TDD Skill 明显改善了产出，信任提高，就敢让 Agent 做更多，结果更好，信任再提高。他仍然怀疑，但怀疑变得更看场景。他说不清现在和以前有什么不同，只说有“一百个细节”是长期审 Agent 输出练出来的。
  • Dale（四年经验）：几年前和 David 一起在 PHP 代码库里工作，两人都不太会 PHP。David 建议他用 ChatGPT 解释 Laravel 和 collections，他只拿来理解代码，不让它写。他担心名声，也知道 ChatGPT 读不到整个代码库，所以总不确定输出是否和上下文对得上。到 G2i 后他早期有些成功，然后让 Agent 一口气做完整个 epic，得到一个一万行的 PR，很快学会缩小委派范围。现在他离开了框架，但做法和框架很像：他自己花 20 分钟写完整的文档式提示词，把框架默认带的护栏和判断都写进去，按下回车就走开，回来像审同事的 PR 一样审 Agent 的 PR。

他的结论是：成功的采用来自把这些做法内化。工程师刚开始用 Agent 时说的是无力感，是被动应对；学会之后，他们坐上了驾驶座。

初级工程师

谈到初级工程师，他常听到两种说法：要么找到一个已经会 AI 的初级工程师，要么初级工程师就完了。他举了 Andy 的例子。Andy 刚毕业，大学老师一直告诉他别用 AI，辅导员劝他把 AI 当家教用，但他交的每一行作业代码都是自己写的。到 G2i 是一次文化冲击。他看到资深工程师用 Agent 很成功，但不信任自己能当 Agent 的向导。让他成功的做法是：在写任何代码之前，先把 brief 和 spec 文档单独提 PR，请资深同事审。资深工程师借此把判断写进文档，实现更顺利，这也成了带新人的机会。Andy 是团队里唯一的初级工程师，三个月成了稳定的贡献者。一位同事说没想到这是他的第一份工作，他和十年经验的人一起干活毫不违和。

他最后说，很多人认定软件工程要完了，也许是，也许预测未来的人都错了。他不想放弃那些犹豫和矛盾的人。可以试他们的框架，也可以试 BMAD、RPI，或者前一天有人讲的那个比 RPI 字母更多的缩写（现场有人喊出 CRISPY）。挑一个能让你慢下来、审得了输出的框架。

02. Sarah Chieng（Cerebras 开发者体验负责人）：我们欠下了很深的“延迟债”

直播位置 0:26:34–0:42:50 · 英文原题 Help! We're DEEP in (latency) Debt

开场：等待 Claude Code 的时间

她开玩笑说最近学了很多新单词，比如 reticulating、schlepping，因为每次用 Claude Code 都要看着这些“思考中”的动词跳 35 分钟。慢速代码生成的体验是：写巨大的提示词，提交巨大的 diff，或者按下回车去吃午饭，回来祈祷它做完了。她是 Cerebras 的开发者体验负责人，Cerebras 在做世界上最大、最快的 AI 处理器，她的工作是带开发者第一次体验快速编程。她也在 YouTube、TikTok 和 Twitter 上做内容。

模型变大，速度没变

她先讲好消息：几年里模型从 3 亿参数涨到超过 1 万亿参数，很多是开源的；上下文窗口（模型一次能读进的最大 token 数）也大到可以塞几百万 token。她引用了 OpenRouter 和 a16z 的一项研究，OpenRouter 是一个统一接入各家 LLM 的 API 层，研究抽样了 100 万亿个真实 token：过去一年输入 token 长度变成原来的 4 倍，每次请求的输出 token 涨了 3 倍。输出变长一部分是因为推理 token，也就是模型给出最终答案前一步步思考时生成的中间 token，这和推理模型的兴起对得上。

然后她现场放了 Opus 4.5 写一个 HTML 小游戏的录屏，一直在转，台下等得很尴尬。她管这个副作用叫延迟债（latency debt）：模型优化得比基础设施快，积累下一笔隐藏成本。她的图显示过去两年 Gemini 系列、Claude 系列（Sonnet 等）的输出速度一直停在每秒 50 到 150 个 token。速度不变而输入输出都变多，单次请求的总时间就变长，开发体验就变差。

Codex Spark

她说大约一个月前，Cerebras 和 OpenAI 合作发布了 Codex Spark，按她的说法是第一个每秒能生成 1,200 个 token 的顶尖编程模型，比图上其他模型快 20 倍，图的纵轴都得重新调。她认为这会改变开发者和模型的交互方式：不用按下回车就走开，可以坐下来把它当结对程序员，边看边纠正，不再生成机器量级、来不及审的代码，也就不会积累技术债。她说这进入了“快速推理”的阶段，模型写代码比人跟得上的速度还快，瓶颈变成了人。

为什么现在能快：整个推理栈同时在优化

  • 硬件和“内存墙”：推理时权重、KV cache（缓存下来的注意力中间结果，避免每个新 token 都重算）要在内存和芯片之间搬来搬去。GPU 的显存在芯片外，她说这种搬运占到推理总延迟的 50% 到 80%。Cerebras 的做法是把权重、激活和 KV cache 都放在芯片上的分布式 SRAM 里，每个计算核心直接拿到需要的数据。
  • 分离式推理（Disaggregated Inference）：推理分两步。预填充（Prefill）并行处理所有输入 token、写进 KV cache，是计算受限的；解码（Decode）一个一个生成输出 token，是顺序的、内存受限的。两步需求完全不同，过去却跑在同一种硬件上。现在开始把 decode 放到内存优化的硬件上，prefill 放到计算优化的硬件上。她说这就是 NVIDIA 几个月前以 200 亿美元买下 Groq 的原因，也是 Cerebras 和 AWS 合作把 Cerebras 晶圆级引擎和 AWS Trainium 放在一起服务的原因。
  • 模型结构：混合专家模型（MoE）每个 token 只激活一小部分“专家”子网络，用小模型的计算成本得到大模型的能力。更新的做法如 REAP（Router-weighted Expert Activation Pruning）：针对某个具体用途，看哪些专家被激活，把用不上的剪掉。
  • 推理优化：Baseten、Modal、Together、Fireworks 这类公司在做这一层（她提到前一天 Baseten 的 Philip 讲过）。最重要的一项是 KV cache 复用，存下算过的 token 表示，不用每次对整个序列重算注意力。

接着她放了同一个小游戏在 Cerebras 第三代晶圆级引擎（WSE-3）上、Codex 里用 Codex Spark 生成的录屏，几乎瞬间完成。

跟着钱看

她列了过去半年的几笔大投入：Google 推出比 NVIDIA GPU 快四倍的 TPU，而 Google 是 NVIDIA 最大的客户之一；Anthropic 买了价值数百亿美元的 TPU；NVIDIA 以 200 亿美元收购 Groq，她说这是 NVIDIA 史上最大的收购，Groq 做的是自己的快速推理芯片 LPU；还有 OpenAI 采购 Cerebras 的硬件，Codex Spark 是这次合作的第一个模型。她的意思是大公司不只看见了延迟债，也在往里投钱，现在开始见效。

最后她回顾历史：1985 年左右从定制硬件转到 CPU，因为工作负载从科学计算变成了需要高度可编程的软件应用；2003 年左右从 CPU 转到 GPU，因为机器学习和图形处理需要大规模并行。2026 年工作负载又变了：多 Agent 系统、500 个以上 Agent 的集群、人在环的 Agentic 流程，基础设施也得跟着变。她说重点在开发者和模型交互方式的改变。她的网名是 Milks and Matcha，需要额度可以找她。

03. Lech Kalinowski（Callstack 研发中心，物理学背景）：在手机 NPU 上离线跑潜在扩散模型，用环境光当提示词

直播位置 0:44:29–0:59:40 · 英文原题 Ambient Generative AI: Deploying Latent Diffusion Models on Mobile NPUs

从随机性讲起

Lech Kalinowski 是物理学家，在波兰公司 Callstack 的研发中心工作，这次讲的是他关于“超级用户体验”（hyper user experiences）项目里的一项原创研究。他从随机性讲起：蒙特卡洛方法可以用随机采样算圆面积、模拟核物理里的链式反应。他说现在大实验室也在用随机性让 LLM 更快更便宜，举了 Google 的 TurboQuant 为例，说它的核心有随机性。他还提到某个模型每百万 token 要 120 美元（模型名字幕不清），用来说明为什么要从基本规律里找更省的做法。

思路：去掉文本，直接用传感器数值

扩散模型生成图片通常要大 GPU、耗时长，手机上还要考虑发热。他的想法是把扩散模型直接部署到手机的 NPU（神经网络处理单元，现代手机里专门跑神经网络的芯片）上。更进一步，他把“文本提示词 → 嵌入向量”这整段管线拿掉，直接用环境光传感器的数值做条件输入。他说换成加速度计等其他传感器也可以。整个流程零云端 API 调用，还配了完整的测量系统来证明手机本地跑扩散模型可行。

他顺带解释了扩散模型：训练时往数据（比如一堆狗的照片）里一层层加噪声，模型学习去掉噪声；推理时从潜在空间（Latent Space，模型内部压缩后的表示空间）里的一团噪声出发，迭代去噪，所以计算量大。

管线结构

  • 输入和编码层：读取环境光传感器，做直方图和统计特征，归一化后构造潜在向量。这一步把原始传感器数据映射到潜在空间并不简单。
  • 潜在更新函数里加了随机扰动项（stochastic perturbation scale），随机性在这里引入。
  • 安全回退：内存不够或温度过高时直接切断应用，他说不想把手机烧坏。
  • 通过 Android 原生桥接把模型部署到 NPU，用 ONNX Runtime（一个跨平台的模型推理引擎）运行。
  • 扩散部分：Android 原生会话管理器、VAE 编码、UNet 去噪循环（8、16、24 步），再解码成张量和 RGB 图片。
  • 最后收集图片、产物和元数据，做成图库和完整遥测。

演示和结果

他先在电脑上演示模拟：拖动模拟光照，设备上立刻出推理结果，同时显示环境光、平滑后的光照、稳定性、温度等元数据。然后在他自己的三星手机上演示（他说不是赞助），先打开飞行模式证明不是假的。随着现场光照的 lux 值变化，屏幕上实时出现扩散模型生成的图像。他承认图像不是逐像素的精细画面，因为为了效率砍掉了文本嵌入那部分，但速度快、稳定。单次实验的稳定延迟大约 600 毫秒，不会把手机拖垮，可以拿来做别的应用，甚至做动画。

他不想以奇怪的 RGB 色块收尾，会前又加了一些几何约束，逼模型生成了一个心形。他的建议是：现代手机都有 NPU，但很少有开发者用，可以拿它来加速应用、做一些不常见的用途。Callstack 的孵化器和研发中心开源了不少 AI 项目，比如 React Native 应用的评测基准。

04. Tejas Bhakta（Morph 创始人）：一切都是模型，“软件 3.5”和专用子 Agent 模型

直播位置 1:51:37–2:03:12 · 英文原题 Everything is Models

讲者

主持人介绍说 Tejas 以前在 Tesla Autopilot 工作，现在创办了 Morph，专注推理优化和代码生成。他上台时投影出了问题，调了一会儿才开始。

从软件 3.0 到 3.5

他从 Trump 在白宫看 Model S 时说的 "Everything is computer" 说起，然后引用 Andrej Karpathy 的划分：软件 1.0 是人写代码编程计算机；软件 2.0 是权重编程神经网络，比如识别红绿灯；软件 3.0 是人用提示词编程 LLM。他说现在出现了新的基本单元，举了 Claude Code 的子任务、Cursor 的 Composer 做后台搜索、Cognition 的 SWE 系列模型等例子（这句字幕有些含糊）。他把下一步称为软件 3.5：人在最上面给主 Agent 下指令，Agent 再给其他 Agent 下指令。有人叫它 agent swarm，他嫌这个词太“vibe”。

子 Agent（Sub-agent）最简单的定义就是：为一个任务开一个独立的上下文窗口。他说这已被证明能提升 Coding Agent 的表现，是继系统提示词和工具之后的第三个基本组件。子 Agent 该用专用模型还是通用模型？他说看情况，这场讲专用模型的情况。

为什么要专用模型

前沿模型擅长编程和推理，但很耗算力、很贵。宏观上现在算力紧缺，GCP 和 AWS 上都找不到 H200、B200 的容量，他说自己后台就有 Agent 在找算力。这种压力推动大家用专用模型，以更少的算力完成同等准确率的任务。Morph 的分工是：代码搜索、上下文压缩这类任务交给专用模型；编程、规划、推理这类需要前沿算力的留给前沿模型。

专用化可以做通用模型不愿做的取舍。他举例说前沿实验室一般不会在“并行工具调用”的 Harness（包在模型外面、负责调用工具和管理循环的程序框架）上做强化学习（RL），因为会出现灾难性遗忘，顺序工具调用能力会退化。Morph 的模型可以做这个取舍：

  • 代码搜索模型：每轮最多并行 12 个 grep、读文件、列目录，最多 6 轮。跑在他们自己为这种负载设计的推理引擎上，负载是重预填充的，输入可达 8 万 token，输出约 200 token。
  • 上下文压缩（Compaction）模型：每秒 33,000 token 的速度压缩上下文。
  • Fast Apply：把模型给出的修改应用到文件上的模型。

他说 Coding Agent 大部分时间都花在这些不需要前沿算力、却要做几千次的事情上。对他们来说，F1 分数高还不够，模型要训练成好用的子 Agent。比如 Opus 在上面调用他们的搜索模型时，可能高估它的能力或误解它的工作方式，所以 RL 时要专门减少这种不确定性。

怎么做快

  • 推测解码（Speculative Decoding）：GPU 是大规模并行的机器，LLM 却是一个 token 一个 token 顺序生成的。推测解码先用某种方法猜出比如 6 个 token，再让大模型一次并行验证，验证 6 个和生成 1 个耗时差不多。传统做法用一个很小的模型（比如 0.7B）来猜，让大模型验证，但也可以用启发式规则来猜。
  • 分离式预填充：首 token 之前的都是 prefill，之后是 decode，现在开始放到不同芯片上。他说 NVIDIA 正在让 Groq 做 prefill、NVIDIA GPU 做 decode，全用 NVIDIA 也行，因为 NVLink 够好。
  • 写 Kernel：最难的一项，领域变化快，今天 CuTe DSL，明天 Mojo，后天又换别的。

他预测会进一步拆分，把注意力计算单独放到一类机器上，可能有三四种芯片各管 prefill、decode、attention。他说 Jim Keller 这类从第一性原理出发的人大概会讨厌这个方向，因为直觉上一块板子就该搞定，但现实和理论不一样。

和 40 多家客户合作的经验

  • 大家都在做差不多的东西（Cursor 的多 Agent 和 Composer、Devin 的并行会话、Claude Code、Codex、Windsurf），更快更便宜是一种差异化。能多跑 10 倍 token，会长出很多功能。
  • “什么都变成 Coding Agent”：他说一个月前这还是热观点，现在已经温吞了。客服 Agent 写 SQL，营销 Agent 调 Apollo API 发邮件。他们最早的客户是 Vercel v0、Lovable 这类编程产品，后来扩展到 Zo Computer 这种会写代码的个人助理。代码是“能构建所有功能的那个功能”，很多工具可以删掉，瓶颈只剩基础模型写代码的能力。
  • 几乎所有客户都一样：速度翻倍，转化率大致翻倍，前提是准确率不降。只看没有遇到报错的用户群，转化率会翻倍。
  • 搜索子 Agent：输入用自然语言（比如“认证逻辑在哪里”），输出只给文件路径和行号范围，让输出 token 尽量少，这样就快。他们的搜索子 Agent 在 SWE-bench Pro 上大约提升 3%，换成 Claude Code 自己的搜索子 Agent 也有类似提升。
  • 任务型子 Agent 仍应用前沿模型，并共享前缀缓存（Prefix Cache）：主模型一次派出三个任务 Agent 时，让它们共享同样的前缀以命中缓存。
  • 他提到泄露出来的 Claude Code 代码里有一个叫 TeamCreate 的机制：主 Agent 建一个带 slug 的文件夹，每个 Agent 一个 JSON 文件，写文件就是发消息，各任务 Agent 不断轮询自己的 JSON 拿更新，实现主 Agent 和子 Agent 的双向通信。没有正式协议，比较 hacky。他也提到有人在推 ACP 来规范这类 RPC 格式，但他更关心双向通信本身。

05. Rick Blalock（Agentuity 创始人）：Coding Agent 吃掉了世界

论点

Rick Blalock 是佛罗里达人，Agentuity 的创始人。他要讲的是过去两年 AI Agent 的演变，以及为什么在 2026 年 4 月，Coding Agent 在写世界上的新软件，同时也在慢慢变成软件本身，是一种新的基础组件。他说从一个人怎么描述 Agent 就能看出他走到了哪一步：“不就是个工作流吗”“不就是高级 RPA 吗”“不就是几次 LLM 调用的循环吗”“不就是更好的聊天机器人吗”“Coding Agent 会犯错，还不能用来开发”。

回顾：想要自主性，却造了一堆控制

  • 两三年前大家说想要 Agent 有自主性，做出来的却多是漂亮一点的工作流或“聊天机器人++”。人总把过去的经验套到新东西上，几十年用计算机解决问题的方式让人很难从第一性原理出发。

  • 他读了 Anthropic 2024 年 12 月的建议：找最简单的方案，可能意味着根本不做 Agentic 系统。他说这些“编排表演”在最近六到九个月被大量移除。Cursor 加了子 Agent，Claude 用不好又删了，Claude 变好了又加回来。

他说非工程师可能比一些工程师更快理解这件事。工程师忙着挑 Coding Agent 的错，非工程师已经在用它经营生意。他举了几个认识的人：

06. Nyah Macklin（Neo4j）：有效的上下文工程技巧，用上下文图谱记录 Agent 的决策

直播位置 2:27:02–2:57:00 · 英文原题 Effective Context Engineering Techniques for AI

一个会出事的场景

Nyah Macklin 来自 Neo4j，以前当过老师，说自己习惯用多种方式让从首席安全官到实习生都能听懂。她先问多少人把 Agent 上了生产，又有多少人的 Agent 在生产里干过让你怀疑职业选择的事。然后给了一个场景：合规团队跑一个 Agent 管线，检索到三段互相独立的文本：Jessica 在 Apex Global 工作；Apex 在制裁观察名单上；Jessica 申请 25,000 美元的信用额度提升。三段都在上下文窗口里，Jessica 信用分 850，Agent 批准了。她称之为 “vibe banking”。

她说问题出在这几个事实之间的联系从来没有在向量空间里表示出来，模型只能猜，猜错了。直到官司来了，上级问你为什么 Agent 这么回答，你答不上来。

两个维度：文本相似和结构相似

向量搜索找的是含义相近的文档，这是文本相似；结构相似找的是连接方式相近的实体。她说现在的检索管线，无论朴素 RAG（检索增强生成，先从资料库里检索相关片段再交给模型回答）、混合搜索还是重排，都只在文本相似这一个维度上工作，能走到 70% 到 80%。“公司客户的信用额度提升”和“雇主上了联邦制裁名单”含义并不相近，向量搜索不会把它们联系起来，但 Jessica、她的雇主和制裁之间的关系是一个连接问题。

她引了几组数字：MIT NANDA 项目 2025 年的 GenAI Divide 报告说 95% 的 AI 试点没有可衡量的损益影响；Gartner 预测到 2027 年 40% 的 Agentic AI 项目会被取消。她让台下跟她重复一句：更好的模型修不好破碎的上下文。

她用苹果做例子：右边是向量表示，一串人读不懂的浮点数；中间是人眼看到的苹果，大脑隐式处理了所有关系；左边是知识图谱（Knowledge Graph，用“节点 + 关系”显式存储实体之间联系的数据结构），苹果连到树，有果实、有茎，每个属性是节点，每个关系都是显式的，人和机器都能读、能查、能审计。

让她相信这套思路站得住的数据：一篇 2026 年 3 月发表的论文（第一作者字幕作 Jang，期刊名字幕不清）做了一个电信领域的基础模型，在 3GPP 问答上做了消融实验。基础模型准确率 37%，用领域数据微调到 54%，再加上知识图谱和 RAG 到了 91%。她强调单靠 RAG 补不上这段差距，图谱是 demo 和生产系统的区别。

上下文工程的常见手法

她对上下文工程（Context Engineering）的定义是：系统性地在正确的时间、以正确的格式，给模型提供完成某个任务所需的全部相关信息、工具和指令。她感谢了前一天讲过、推广这个词的 Dex。它和提示词工程的区别在于，它关注的是为每次 LLM 调用动态组装完整、结构化上下文的系统。常见手法：

  • RAG 和混合搜索：用向量库做相似度搜索。
  • 记忆管理：长会话和跨会话积累大量信息，用滑动窗口、按新近程度丢弃历史（她用 Dory 来比喻“管理要忘掉什么”）。
  • 上下文的结构和顺序：她说 Anthropic 对长提示词的指南建议把最关键的内容放前面。
  • 工具和函数调用：与其把一整张大表塞进上下文，不如给模型一个数据库查询工具。
  • 知识图谱增强上下文：把结构化的关系知识放进上下文，Agent 可以从一个节点跳到下一个，追踪路径，解释答案。用关系表就得做大量复杂 join，拖慢性能。

架构上，她把知识层放在 Snowflake、Databricks 等现有数据平台之上，连接结构化和非结构化数据，上面再接 LangChain、Semantic Kernel 等编排层和 Agent 框架。她说知识图谱已经存在很多年，不是 Neo4j 发明的。

上下文图谱（Context Graph）

她问台下有没有人读过去年 12 月那篇《AI's trillion-dollar opportunity: Context graphs》，只有一两个人举手。她说讨论已经从朴素 RAG、Graph RAG、知识图谱增强上下文，走到了上下文图谱。现在 Agent 要决定谁能贷款、能不能买房、医疗上的判断，所以必须能审计每一个决策。缺的是“为什么”：没有记忆，没有审计轨迹，多个 Agent 之间也无法共享学到的东西。

上下文图谱是一种专门记录决策轨迹（Decision Trace）的知识图谱：每个重要决策背后的完整上下文、推理和因果关系。它和审计日志的区别在于，审计日志只有逐条交易记录，上下文图谱还能装进没写下来的东西，比如资深架构师脑子里的权衡、Slack 消息、邮件线程、Zoom 会议。这些因果链可以被查询和遍历。

现场演示

她的金融数据模型分三类：实体（人、地点、东西），事件（发生了什么），以及上下文和原因（决策、政策等）。演示里，她问一个金融服务 AI 助手是否应批准 Jessica Norris 的 25,000 美元额度提升，图谱实时构建：一个人就某笔交易提交了工单，交易触发警报、标记账户，警报进入系统上下文，基于政策形成决策轨迹，再反馈给账户所有人。她展示了 Agent 定义的工具和系统提示词，工具负责去图谱里取做推荐所需的上下文。

Agent 的结论是拒绝，理由包括：4 月 9 日已有一次类似请求被拒；去年账户有欺诈历史，符合已知欺诈类型，29 分钟内 14 笔交易的速度异常；IP 地理位置和账户地址不符；还有多项合规违规。右侧显示完整决策轨迹和置信度。她说如果 Jessica 能解释这些情况，图谱会随新决策更新。演示地址是 context-graph-demo.vercel.app，完全开源。

背后的检索流程：先找客户和客户周边的上下文，再用结合向量和图的混合搜索。Neo4j 的 Graph Data Science 可以跑中心性、PageRank 等图算法，还能生成图嵌入，比如 FastRP。向量相似度用来找语义相近的政策和决策；图嵌入刻画账户和交易、其他账户、欺诈模式之间的结构关系，再用熟悉的向量搜索去找最相关的数据。工具通过 MCP 接入。她给了一个研究资料汇总页 graphrag.com/appendices/research。

为什么做一个夸人的机器人

Lena Hall 以前在 AWS 和 Microsoft，现在是 Akamai 负责开发者关系和 AI 的高级总监（主持人说当天最期待这场）。她说模型在商品化，工程出正确行为的能力没有。AI 离开聊天窗口进入 Agent、语音和实体界面后，产品的重心从模型转到整个系统怎么和世界互动。给语言模型一个身体，架构里每个隐藏假设都会变成物理上的副作用。

她自嘲说“像任何负责任的成年人一样”做了一个多模态吹捧机器人，真正的题目是“给 4o 一个身体会怎样”。她想要一个最小的任务，逼出现代 AI 的所有难题：看向某人、看到真实的东西、说出有依据的话，顺便用点 Gen Alpha 俚语。一个夸人需求就牵出感知、时序、工具调用、事实依据、语音、动作、打断处理和响应协调。硬件是 Pollen Robotics 的 Reachy Mini（也被称为 Hugging Face 的机器人），有摄像头、麦克风，头部六个自由度。她选它是因为整套系统一路都能看到底，开放的系统让你能检查、打补丁、替换，看清行为在哪里坏掉。

现场演示

她启动应用和 Reachy 对话。问它在哪，它说传感器没有 GPS，但你在哪都是主角；让它描述周围，它说空间不错但真正的焦点是你；问观众，它说观众爆满，顶灯让一切像电影画面。她还问了个现场梗：前一天 Dex 说六个月前他建议别读代码，现在又说要读代码，该信哪个？机器人说读代码那个。问它最好的 JavaScript 框架，它先躲，被追问后选了 React。最后让它睡觉，它也以一句夸奖收尾。她说有意思的不是机器人的技术回答，是要让一次互动感觉连贯，背后要做多少事。

五层架构

  1. 实体机器人。
  2. 本地媒体层：负责音频和摄像头输入输出，长期运行的音频管线和单独的摄像头 worker。
  3. 实时编排层：与 OpenAI Realtime 的会话，管理事件循环，如开始说话、停止说话、部分转写、响应生命周期、工具调用事件。是否用服务端 VAD（语音活动检测，判断用户何时开始和停止说话）、怎么处理打断都在这层决定。
  4. 工具和动作层：把模型意图转成物理动作，有工具分发器、动作管理器、摄像头 worker、视觉管理器、头部摆动器。工具作为后台任务，共享一个工具依赖对象，避免变成“每个组件都认识每个组件”的硬编码引用图。
  5. 配置和人格层：配置、白名单、指令加载，同时决定模型说什么和能做什么。

整体图上，左边是机器人，上面是实时推理和工具，右边是 ElevenLabs 文本转语音，下面是可选的工具后端。决定产品体验的工程都在中间那层本地运行时，她称之为行为运行时（Behavior Runtime）。她说今天大多数 AI 产品里，模型远比包着它的运行时先进，中间有一道“运行时缺口”。

几条原则

  • 模型选意图，运行时选动作：模型不直接控制硬件。它想让机器人动，就发起工具调用表达意图，由运行时决定是否以及怎么转成舵机指令。感知方向也一样：模型调用摄像头工具，运行时抓最新一帧、编码成 JPEG 注入对话。模型一旦直接操作运行状态，安全、监督、日志、可观测性、可移植性就没有地方放了。“模型可以有观点，但不能直接碰电机。”
  • 响应要串行化：Realtime 一次只允许一个活跃响应，但用户会打断、工具会返回、摄像头会回图、后台进程会有新信息，人人都想发言。放任的话机器人会在打断眼前用户的同时，回应五秒前的现实。她用一个专门的响应 worker，同时只有一个活跃响应，其余排队。用户打断时不只停止排队，还清空音频队列、重置动作状态、积极取消。只要 Agent 有多个触发源（用户输入、定时任务、webhook、回调、工具完成），都会遇到这个问题。
  • 延迟就是交互设计：聊天里短暂的延迟像在等；在机器人身上同样的延迟像犹豫、困惑、出了问题。她给了实际日志：音频上线 400 毫秒；Realtime 会话就绪 2.3 秒；用户转写完成后模型决定调用摄像头工具约 274 毫秒（字幕作 "to 74"）；摄像头抓图和注入 30 毫秒；但图像进入最终回答花了 4 秒以上。传感器、工具分发、调用决策都快，慢在工具返回之后。只优化一个端到端数字会优化错地方，要问的是循环里哪一段让互动感觉不对。
  • 人格就是策略：人格会从提示词渗进声音、工具权限、会话设置、打断行为、工具调用后的追加指令。每个人格配置声明了模型可用的工具。她遇到过主提示词很好、机器人说话很接地气，可一调完工具回来就变成“法务审过版本”的通用 AI 助手。修法是在运行时策略里，把当前人格的语气注入到工具调用后的追加指令中。
  • 空闲也是行为：屏幕上的 Agent 空闲就是什么都不做，机器人等待时仍然在场。它没事做时是平静、活跃还是尴尬，都得设计。
  • 基础设施 bug 表现为行为问题：项目里遇到过媒体 bug、依赖版本不匹配、重采样器的流式 PCM 边界情况、工具调用溢出。它们出现时都不像基础设施 bug，而像机器人“死了”“不靠谱”“抽风”。工具调用溢出那次，机器人突然开始说西班牙语，指令里根本没有。用户不会报“重采样器边界情况”，只会说“这东西怪怪的”。所以系统感觉坏了时，先给协调层加监测，再考虑换模型。

她的结论是行为运行时就是产品：换掉底层模型产品还在，运行时做错产品立刻失败。编排、工具边界、会话契约、延迟预算、打断纪律、人格策略和可观测性都是产品本身。她给了三条建议：AI 产品感觉不对时先调试运行时再怪模型；把编排、会话管理和工具边界当产品工作排优先级；如果你是做系统出身、这几年在 AI 讨论里觉得格格不入，她认为市场会修正这一点。最后她用自己写的 Reachy Mini Codex Skill，在 Codex 里让机器人摆了六下左天线。

10. Alvin Pane（OutRival 创始工程师）：干掉你的检索管线，Agentic Memory 是新的最佳水平

背景

Alvin Pane 来自多伦多，在 AMD 做过研究，一年前搬到迈阿密加入 OutRival。OutRival 的目标是让企业为 AGI 做好准备，做的是“数字员工”，代表机构和联系人打交道，要决定联系谁、何时、怎么联系、每次互动存什么，常常覆盖一个联系人的完整生命周期。他说规模上可能是每月数百万次互动、6,000 小时的上下文，所以记忆是产品核心。他开场问大家有没有遇到过：一个 Agent 会话很顺，突然它变笨了十倍。这就是记忆问题。业界多年来的做法是往 Agent 上外挂更多基础设施，RAG 管线就是这样来的，他要论证反方向。

DMD：五天做出的记忆系统

二月初他发了一篇博客《How I built the most accurate memory system in the world in 5 days》，介绍 DMD（Dynamic Memory Discovery），用来解 LongMemEval，这是对话 AI 记忆的行业标准基准。他说这个成绩后来被超过了，现在已有 100% 的结果，但更重要的是他从中得到的思考框架。当时主流方案是向量库、重排器、知识图谱全套，他想问：全拿掉会怎样？

思考框架：奥卡姆剃刀、赌注、苦涩的教训

  • 奥卡姆剃刀常被概括为“最简单的答案通常是对的”，他更喜欢另一种说法：每多一个假设，就多一块可能出错的面积。
  • 轮盘有 38 个格，却按 36 个格的赔率付钱，每一转期望值都是负的，下注越多越确定会输。搭 Agent 时也在下注：加嵌入模型，是赌语义相似度正好是 Agent 需要的；做分块（Chunking），是赌在问题出现之前就把上下文切对了；加重排器，是赌你的相关性排序比 Agent 自己的好。
  • 苦涩的教训（The Bitter Lesson）：利用大规模计算的通用方法，最终会胜过基于人类领域知识的方法。国际象棋和围棋里，几十年都在把人类策略编码进程序，直到转向大规模搜索和强化学习才超越人类。他说记忆领域也在发生，DMD 之后在 LongMemEval 上拿到 100% 的方案，都建立在让模型做更多工作、真正 Agentic 的记忆上。

架构

DMD 很简单：没有向量存储，只有一个文件系统，里面放原始 JSON 会话；一个编排 Agent，拿到几个基本能力：文件系统工具、可以递归调用其他 Agent 或 LLM，以及一个计划文件，用来记录找到了什么、哪些还不确定、还在找什么。他说这个简单方法胜过了多年的管线研究。

记忆没解决：三个组成部分和三个难题

他说 LongMemEval 100% 不代表记忆解决了，生产里仍然难，这个基准也没覆盖好记忆的所有部分。他列的三个组成部分：

  • 状态（State）：LLM 本身无状态，要知道任何事都得有个放上下文的地方。
  • 筛选（Curation）：在正确的时间把状态里正确的东西放进上下文窗口。
  • 生命周期（Lifecycle）：Agent 在真实世界里行动，世界在变，什么保留、什么更新、何时忘掉什么。LongMemEval 没有评测这一项。

生产还有约束，不能无限推理、无限等待。所以记忆是一条光谱：一端是“原始记忆”，文件系统加一个 Agent 去推理，DMD 属于这一端，在基准上表现更好；另一端是“派生记忆”，预先加工出更多结构。成本和延迟的约束可能让你往派生那边买一些结构，关键是挑你的赌注。即使 LongMemEval 拿满分，仍有三个常见失败：时间推理（什么时候什么是真的，中间变了什么）；实体消歧（一个会话说 “Alvin loves Miami”，另一个说“最帅的工程师爱迈阿密”，怎么知道是同一个人）；有原则的遗忘（何时该忘、上下文何时过期）。

他的结论是：做 Agent 就是在做记忆。最后引用 Karpathy 的说法：今天的 LLM 已经能解决大多数任务，问题在于是否在正确的时间把正确的东西放进正确的窗口，他称之为 skill issue。OutRival 在迈阿密 Wynwood 招人。

他说曾经好奇 Anthropic 为什么不做 LLM 以外的模型，后来想通了：只要是一个很好的 Agentic 模型，别人做的模型它都能调用。

做 Skill 的方法

  • 结构可以很简单：模型是基本单元，文件是载体，提示词是意图，工具和 Skill 是会被调用的东西，然后循环。别过早优化。
  • 如果一次就能做对，那不算 Skill，它已经在模型或 Harness 里了，你只是在给潜在空间里已有的东西写文档。一个 Skill 写一次就永远好用，可能根本不需要，它的前置元数据还会占上下文 token。
  • 做 Skill 时用同系列里较弱的模型，或者等更好的模型。他的 DAW Skill 最初用 Opus 4.6 做，很多挫折；4.7 一出来就直接做成了，没掉进同样的坑。弱模型提供约束，逼你把失败模式写具体，这种具体性能扛过模型和 Harness 的更新。
  • 从一个让你烦的小问题开始，然后注意观察，和模型一起排查，别自以为是地指挥它，然后把结论写下来。
  • 两种失败：过度泛化（只写“写好听的音乐”）；在失败模式上过度规定，比如模型说“我再也不碰那整个领域”。要弄清到底为什么失败再写下来。他用 Claude 的 skill-creator 写音乐 Skill 时，它一开始就限定了 10 种曲风，这扼杀了表达力，降低了上限。
  • 贴近一线做元工作：别急着让后台 Agent 在你睡觉时跑，先熬夜把 Skill 迭代到位，然后再睡、再回顾。永远有循环：每次运行后，让它把这次学到的东西反思并写回 Skill。迭代在钱和 token 上很便宜，但要花功夫。他自造了一个词 GOFE，good old-fashioned engineering。

关于持续学习

他问台下谁认为持续学习已经解决、谁认为需要解决。他说很多演讲声称没解决持续学习就没有超级智能，又说不清持续学习是什么，他认为是胡扯：你可以把东西写下来，写进 Skill 就是记忆，放进未来的上下文就是记忆，运行时学到再存起来就是记忆。

展望上，他几个月前给 NVIDIA 的 Nemotron 模型做过一个很简单的终端编程 Harness，让它能访问自己的代码库、自己写评测并在自身循环外运行。他提到 skill-creator 这类帮 Agent 给自己写 Skill 的 Skill，以及刻意极简但可扩展的 Pi agent，称之为自修改的 Agent Harness，前提是你盯着。他认为今天靠 Skill 和 Harness 能做到、模型自己做不到的事，将来训练会把它们放进权重，Skill 是介于 ML 研究和提示词工程之间的一种手段。

最后他说要多犯错，犯得越多越能推进；要培养“模型同理心”，多玩多看它在哪失败、什么帮它成功；他的经验是有些模型需要一点心理安全感才能发挥最好。他放了 Claude 在 DAW 里写的金属乐，完整的六个版本在 hyperoperator.vercel.app。结果永远不会是 100%，模型是概率，但可以接近到能上生产。放到商业里，你解决的每个错误都是差异化，能让你比只用模型的人走得更远。

14. Laurie Voss（Arize AI 开发者关系负责人，npm 联合创始人）：MCP 对命令行，Agent 工具接入方式的正面评测

直播位置 7:08:44–7:35:40 · 英文原题 MCP vs. Command Line: A Head-to-Head Evaluation of Agent Tool Integration Patterns

争论和他的做法

Laurie Voss 做开发者 30 多年，“有些博客文章比在座有些人年纪还大”，曾联合创办 npm，现在在 Arize AI 想怎么用评测（Eval）让 AI 应用变好。这场比较给 Agent 接工具的两种主流方式，他想拿数据说话，不凭热观点。

  • MCP：带内置发现机制的远程工具协议。SDK 每月下载近 1 亿次，已知 MCP 服务器超过 17,000 个。
  • Skill：就是一个 Markdown 文件，告诉模型怎么做某件事，常常是怎么用某个命令行工具，也可以是怎么调某个 REST API 或遵守团队的编码规范。没有正式协议，靠自然语言。他说它和 MCP 做的是同一件事，也是带发现机制的远程工具调用方式，发现机制就是“去 skills 目录里找”。skills.sh 列了 9 万多个 Skill，有的被装了几百万次，但很多是自动生成的，很多也不涉及远程工具。

半年前 MCP 是新热点，后来 Anthropic（也是 MCP 的发明者）推出 Skill，引发争论。Simon Willison 去年 10 月说 Claude Skills 很棒，可能比 MCP 还重要，他说这对一向不爱发辣评的 Simon 来说很辣了。今年 2 月一篇《MCP is dead. Long live the CLI》在 Hacker News 置顶两天，论点是 LLM 本来就会用 CLI，给它 shell 和文档就够了。3 月 Pieter Levels 说 MCP 和 llms.txt 一样没用。他说这是一场很“在线”的争论，全是推文和感觉，没有数据。他从几周前开始做评测，一直写到演讲前的周日晚上。他现场让大家举手投票：偏好 MCP 的、偏好 Skill 的，以及猜谁赢。

实验设计

  • 模型固定为 Claude Opus 4.6（“因为我不付 token 钱”），用 Claude Agent SDK，也就是驱动 Claude Code 的同一个 SDK。
  • 任务对象是 GitHub：大家都用；有成熟的官方 MCP 服务器；也有能力很强的命令行客户端 gh。他说很难找到另一个 MCP 和 CLI 都这么好的热门服务，双方都能拿出最好状态。
  • 建了一个假仓库 acme-sdk-python，代码是不能跑的假代码，但填满了逼真的 issue、评论、PR、里程碑、指派人。一开始设成公开，马上有人的 bot 发现 “good first issue” 标签，拼命想修他的假代码，开 PR、改状态，把实验搞乱了。他说这至少证明仓库够逼真。
  • 25 个任务分四级：一级是一条命令就能完成的简单读取；二级是要多次读取的读任务；三级是写操作，结果最棘手；四级是复杂任务，多次读取加分析，比如“每个里程碑报告完成百分比”“找出带多个标签的 issue 中最常见的标签组合”。
  • 三个实验组（A/B 测试里叫 arm）：MCP 组，用 GitHub 官方 MCP 服务器，被明确要求只用它；LobeHub 组，用从 LobeHub 拿来的 GitHub Skill，2,187 行 Markdown，像 man page 一样列出 gh 的所有子命令和参数；Vault 组，用 Claude Skills Vault 里的 Skill，短六倍、有主见，把命令分成安全的和危险的、读的和写的，更像操作手册。他加第二个 Skill 是怕选到差的 Skill 不公平。
  • 三组用同一个 Agent、同一个基础提示词、同样 25 轮上限、同一个模型，只改工具。

他解释了评测：确定性代码可以写 2+2=4 这种测试；LLM Agent 的输出不确定，“总结这段文字”可能有一百万种答案，一半是对的，你不知道是哪一半，没法字符串匹配。人能判断但不可扩展、进不了 CI。解法是用另一个 LLM 来评判，即 LLM-as-a-Judge。Arize 提供采集日志的 Trace、查看 Trace 的界面、在开发、CI 和生产数据上跑评测，也能把一部分 Trace 做成数据集，一次只改一个变量反复跑实验。

五个指标：正确性（LLM 评判，对照他写下的标准答案）；输出质量（LLM 评判，格式是否好）；延迟（墙钟时间）；成本；工具忠实度（每组有工具白名单，调用中有多少比例在白名单内，因为 Agent 把规则当建议）。每个任务每组跑五遍，共 500 次测试，每次要好几分钟，Claude 宕机或仓库没重置好时整批作废，前后花了几周。

结果

  • 正确性：三组差不多，都在 80 多分。一二级读任务都是 100%，到写操作和复杂分析才开始掉。无论用 MCP 还是命令行，最终都能做对。
  • 延迟和成本：差别很大。MCP 慢得多，四级任务平均约 12 次调用，命令行约 5 次。轮数多还会复利地烧钱，因为每轮都要把之前的对话重新塞进上下文窗口。
  • MCP 吃亏的原因之一是 GitHub MCP 服务器不如 gh 背后的 API 灵活，比如拿一个里程碑的所有 issue，gh 一次搞定，MCP 要分开拿 open 和 closed 两次。另一个是结构性的：MCP 返回大量冗长的 JSON，撑爆了上下文，Agent 只好再调一次，把 JSON 写到磁盘，再用 bash 和 grep 去读，他说这算作弊。
  • LLM 评判的好处是每个结果都附带解释，他靠读这些解释看清发生了什么。早期解释多是在指出他测试写错了，后来才变成对 Agent 行为的解释。
  • 第 22 题“找出在同一里程碑内开启并关闭的 issue，计算平均开启时长”：Vault 平均 7 次调用、不到一分钟、19 美分；MCP 最差的一次用了 71 次调用，其中只有 3 次是 MCP 调用，其余都在用 bash 和 grep 解析下载的 JSON，违反了他的指令。
  • 工具忠实度上 MCP 组整体不好，复杂任务更糟。他说从实用角度看用 bash 也无所谓，但说明有问题：GitHub MCP 是固定的 API 面，有正好合适的调用时一次搞定，没有就要多次调用或者干脆不会。bash 是图灵完备的，什么都能做，所以三组遇到难题都会转向 bash。
  • 反例是第 13 题“建分支并开 PR”：MCP 正好有两个对应调用，两次搞定；LobeHub 组用了 22 次调用、近一分半、约 50 美分。

为什么结论没那么简单

看起来命令行赢了，但他说事情更复杂。GitHub 和 gh 太有名了，博客、Stack Overflow、Reddit 里到处都是。于是他又补跑了第四组：不给 Skill 也不给 MCP，让 Agent 自己想办法。结果 Claude 自己用 gh 就很好，正确性甚至比有 Skill 的略高。他读解释发现，Skill 文件提醒“做危险操作要小心”，而裸 Claude 直接一把梭，反而少几轮。延迟上两个 Skill 组都比裸 Claude 好，因为 Skill 让它少犯错；成本上 LobeHub 因为文件太大而更贵，短而精的 Vault 比裸 Claude 略便宜。所以 Skill 有用，好 Skill 更有用。

MCP 的成本高一部分是因为它带着大量“怎么用这个工具”的上下文，而对 GitHub 来说模型大多不需要。但你的 CLI 没有 GitHub 那么有名、文档那么多，没有 MCP 提供的额外上下文，Agent 可能根本搞不定。此外，MCP 不应只是 REST API 的薄包装，它有 tools、resources、prompts 等丰富能力，服务器背后还可以放一个 Agent：你的 Agent 用自然语言说“给我所有符合这些条件的 issue 并按那些条件过滤”，对方的 Agent 做完再返回，一次就好。GitHub MCP 不是这样做的，但没有理由不能。

还有认证这个大问题。CLI 天生是开发者工具，GitHub 用户生成 API key 不难，但 LLM 的用户是全世界，让普通用户生成 API key 已经勉强，再让他们打开终端写配置文件更不可能。CLI 的访问控制也和企业管理员期望的差得远。MCP 用 OAuth（让用户在浏览器里授权第三方访问账号的标准协议），还为了 MCP 扩展了 OAuth：把 MCP 服务器网址贴进 Agent，它自己发现能力，弹出一个友好的授权窗口，然后就能用。这让 MCP 从开发者工具变成了普通人能用的消费级工具，管理员也终于能控制谁在何时访问什么。

结论

他的窄结论是：开发者用开发者工具，尤其是广为人知的服务，Skill 通常是对的选择。但绝大多数 Agent 用户不是开发者，对他们来说 MCP 是最好的选项，很多时候也是唯一的选项。所以“MCP 还是命令行”是个错误的问题，应该是两者都用，Claude Code 和 Cursor 都是根据情况两者并用。本地工作、工具有几十年训练数据、认证已配好、需要管道组合时用 CLI，这是自动化自己工作流的场景；工具在远程、是专有的不在训练数据里、需要 OAuth 和按用户授权、跨步骤有真实状态要管、尤其想在 API 后面放一个 Agent 时用 MCP，这是要交付产品的场景。

他的核心数据：MCP 在开放式分析上崩溃，最难任务上成本 6 倍、延迟 5 倍；Skill 有一点帮助，短而有主见的 Skill 最有用；对 gh 这样的热门 CLI，大部分功劳在训练数据。他说测试做了测试该做的事，显示了原问题的边界。代码和数据都开源在 GitHub 上，可以复核。

15. David Gomes（Cursor 软件工程师）：IDE 已死，IDE 万岁

直播位置 7:37:12–7:54:00 · 英文原题 IDEs are dead. Long live IDEs

一个 IDE 迷的经历

David Gomes 住在马德里，中学和大学时打过竞赛编程，自称 IDE 迷。他的第一个编程项目就是一个 IDE，叫 Crockett，2011 年给一门现在已不存在的语言 Axe 做的。那时身边的人不是用 Emacs 就是用 Vim，像《哈利·波特》里被分院，他选了 Emacs，理由只是 Emacs 有界面、Vim 在终端里看着吓人。他也用过 Geany 和 Eclipse。后来转到 VS Code（他说 2014 年左右出来，2017 年变得很好用），因为在 Emacs 里每试一门新语言都要花一周配置，VS Code 没这个问题。他的 VS Code 配置超过 500 行，快捷键配置又是 500 多行，改得已经不像 VS Code。很多人劝他试 Cursor，他一直抗拒，直到坐在一个用 Cursor 的人旁边看了一次。

吸引他的是 Tab 补全，这是让大家爱上 AI 编程的第一个功能。他去年 9 月加入 Cursor，他的 Tab 使用记录是：9 月 1,400 次，12 月 9 次，而他 12 月没休假。他说如果图延续到 2026 年，现在大概是零。

旧 IDE 的很多东西不需要了

多年来大家花大量时间配置编辑器：括号要不要自动闭合，哪些引号和括号自动闭合，光标要不要闪、间隔多少毫秒，滚动要不要吸附、吸附几行，一行 80 还是 200 个字符。他说这些大多已经不重要，而且会损害 IDE：设置越多，组合复杂度接近阶乘级，越难测试、越不稳定。VS Code 光小地图（minimap）就有十多个设置。这让 Cursor 和 Microsoft 的 VS Code 团队都把大量时间花在修 bug、测各种配置上，很难创新。

他说现在 Agent 写了他们 99% 的代码（后面他自己又说是 97% 到 98%），所以必须从第一性原理重想 IDE，问还需要什么。一个想法是什么都去掉，只留一个聊天框，这就是 Cursor CLI、Claude Code CLI、Codex CLI。他每天都用 Cursor CLI，这次的幻灯片就是用它做的，但这只占他 Agent 使用的 5%。他需要的东西 CLI 渲染不了：

  • 视频播放：他现在大部分工作是看 Agent 录的视频来确认它做对了。
  • 图片渲染，以及在图片和视频上做标注。
  • 富界面：Mermaid 图、知识图谱、图表，用于测试和数据分析。
  • 浏览器，更重要的是 Chrome DevTools 和调试器。
  • 移动开发需要 iOS 和 Android 模拟器。
  • Agent 完成时的系统原生通知。
  • 还剩那 2% 到 3% 自己写的代码，需要一个够用的编辑器，有跳转到定义、LSP（语言服务器协议，编辑器获取补全、跳转等语言功能的标准接口）等。

他展示了自己从去年 11 月起每天启动的 Agent 数量，云端 Agent 的比例越来越高，他的电脑越来越不是性能瓶颈。他在 IDE 里做的事主要是看视频确认 Agent 的工作、用浏览器验证、看图表。他常用 Cursor 的 Canvas 功能做数据分析：Agent 临时生成一个单一用途的界面，用完就扔。

从 Cursor 2.0 到 3.0

他加入 Cursor 第一周，经理就说要做一个面向 Agent 的新界面，这就是 Cursor 2.0。他当时既兴奋，也怀疑自己会不会真的那么放手不碰代码，几个月后发现自己几乎不打字了。2.0 在去年 10 月底发布，有 worktree、并行 Agent，也首次推出了 Cursor 自己的模型，但没得到他们期望的用户喜爱。后来又加了复杂的平铺布局，可以把终端、文件、聊天排成很多格的 Agent 网格，仍然觉得不够灵活。

两周前发布的 Cursor 3.0 是从零重做的界面。从零开始一是为了摆脱 VS Code 的布局系统和架构包袱，要一块白画布按第一性原理重建；二是作为一个新窗口，用户可以渐进采用：VS Code 式的传统界面和新的 Agent 窗口可以同时开、来回切，不强迫任何人。接下来他们想做的：

  • 更好的交接：Agent 在手机上开始，进到云端，拉到电脑上，可能进 worktree，再回云端，最后在手机上收尾，要无缝。
  • 更多编排工具：越往高层走，读的代码越少，需要看板式、DAG 式的界面来制定计划、分给多个 Agent。
  • 更好的移动开发支持：现在很多人要同时开 Xcode 和 Cursor 来回切，不该这样。
  • 本地的 Computer Use：云端 Agent 已经能操作电脑，Cursor 浏览器里也能，但桌面应用还不行。
  • 更好的代码审查：他说这是公司现在的 P0 之一，大家不写代码了，但还在读大量代码，他估计多数人仍在读 90% 以上的代码，审查界面也得重想。

他反复请大家去试新界面、给反馈，说前一天他还坐在一个没试过的人旁边，求对方点一下那个按钮。
