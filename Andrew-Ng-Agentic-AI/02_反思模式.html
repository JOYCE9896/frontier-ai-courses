模块 2：反思设计模式

让 LLM 先交一版初稿，再回头检查、改出第二版；能拿到外部反馈时效果更好

主讲：吴恩达（Andrew Ng）· 出品：DeepLearning.AI · 本模块 5 节视频，约 26 分钟 · 整理：Joyce（@JOYCE9896）

这一模块讲什么

模块 1 介绍了 Agentic 工作流（Agentic Workflow，把一个任务拆成多步、让 LLM 分步完成的做法）和几种常用设计模式。模块 2 专讲第一种：反思（Reflection）。做法是先让 LLM 生成一版输出，再把这版输出交给同一个或另一个 LLM，让它按给定标准检查并改写。吴恩达说这是他在很多应用里用过、实现起来又出奇简单的模式。

五节视频依次讲：反思是什么；为什么不直接一次生成；一个图表生成的完整例子（也是本模块实验的内容）；怎样用评测（Eval）确认反思到底有没有用；以及怎样引入外部反馈让反思更强。最后一节结尾预告了模块 3 的工具使用（Tool Use）。

09. 用反思改进任务输出

英文原题 Reflection to improve outputs of a task · 课程页 · 3:56

从人改邮件说起

吴恩达先拿人自己举例。他打字快的时候，邮件初稿可能写得不好：约 Tommy 吃饭只写了“下个月”，没说具体哪几天；有个错别字；还忘了署名。自己读一遍就能发现这些问题，于是改成更具体的版本，比如问 Tommy 5 号到 7 号有没有空。

LLM（大语言模型，Large Language Model）也能走类似的流程。先用一个提示词（Prompt）让它写出邮件初稿 email v1，再把 v1 交给同一个模型，换一个提示词，让它反思并写出改进后的第二稿 email v2，作为最终输出。他说这里是把“先生成一次、再反思改进一次”这个流程直接写死在程序里的。

写代码也一样，可以换模型来反思

同样的流程可以用在代码上：让 LLM 写出 v1 代码，再交给同一个或另一个 LLM，让它检查 bug、写出改进后的第二版。吴恩达说不同的 LLM 各有所长，所以他有时会给“写初稿”和“反思改进”选不同的模型。

他举的例子是推理模型（reasoning model，也叫 thinking model，回答前会先生成一段思考过程的模型）。他发现这类模型找 bug 挺在行，所以有时他会用直接生成的方式写出代码初稿，再用推理模型来查 bug。

外部反馈让反思更有力

外部反馈（external feedback）指的是来自 LLM 之外的新信息。吴恩达说，如果能拿到外部反馈，反思会强得多。以代码为例，最直接的办法就是把代码跑一遍，看它输出什么。代码的输出，包括报错信息，对 LLM 反思和改进代码都很有用。

他的例子里，LLM 写出的初稿一运行就报了语法错误（syntax error）。把代码输出和错误日志一起交回给 LLM，让它针对这些反馈反思并写新稿，它能拿到的信息多了很多，写出的 v2 也好得多。

他的提醒

  • 反思不是魔法，不会让 LLM 每次都百分之百做对，通常带来的是一个幅度不大的性能提升。
  • 设计时要记住一点：反思过程中如果能吸收额外的外部信息，效果会强很多。能运行代码、把输出或错误信息作为反思步骤的额外输入，LLM 就能更深入地找出哪里可能出了问题，改出的第二版也比没有这些信息时好得多。

下一节他要把反思和直接生成做一次更系统的比较，后者有时也叫零样本提示（zero-shot prompting）。

10. 为什么不直接一次生成？

英文原题 Why not just direct generation? · 课程页 · 5:11

直接生成与零样本提示

直接生成（direct generation）就是给 LLM 一条指令，让它一次性给出答案就结束。比如让它写一篇关于黑洞的文章，或者写一个计算复利的 Python 函数，它直接输出文字或代码。

吴恩达顺带解释了几个术语。在提示词里放进一个“期望的输入和输出”示例，叫单样本提示（one-shot prompting）；放两个叫 two-shot，放好几个叫少样本提示（few-shot prompting）。一个示例都不放，就是零样本提示（zero-shot prompting）。他说不熟悉这些词也没关系，这里的重点是“让 LLM 一步到位直接生成答案”，因为提示词里没有示例，他也把这种做法叫零样本提示。

研究结果：反思普遍优于直接生成

他说多项研究表明，在各种任务上反思都比直接生成表现更好。他展示的图改编自 Madaan 等人 2023 年的论文“Self-refine: Iterative refinement with self-feedback”，比较了不同模型在不同任务上加不加反思的表现。

读图方法：看每一对相邻的浅色柱和深色柱，浅色是零样本提示，深色是同一个模型加上反思。蓝、绿、红三种颜色代表不同模型（图例里是 GPT-3.5、ChatGPT、GPT-4）。他说在很多应用上，深色柱都明显高过浅色柱，但具体到你自己的应用，效果可能不一样。

幻灯片上的七类任务和柱子上标的提升值（单位是百分点）如下：

  • Sentiment reversal（情感反转）：GPT-3.5 +21.6，ChatGPT +31.8，GPT-4 +32.4
  • Dialogue response（对话回复）：+27.2，+19.8，+49.2
  • Code optimization（代码优化）：+8.2，+3.6，+8.7
  • Code readability（代码可读性）：+13.9，+35.4，+28.8
  • Math reasoning（数学推理）：+0.0，+0.2，+0.2
  • Acronym generation（缩写生成）：+14.8，+10.0，+25.6
  • Constrained generation（受约束生成）：+9.0，+23.0，+30.0

幻灯片左侧的结论是：在各种任务上，反思稳定地胜过直接生成。数学推理这一组几乎没有提升，吴恩达在讲解中没有单独评论这一点。

哪些场景适合加反思

  • 结构化数据。比如生成 HTML 表格时，输出格式有时会出错，加一个校验 HTML 代码的反思提示词可能有帮助。如果只是基础的 HTML，帮助可能不大，因为 LLM 写基础 HTML 已经挺好了。但像嵌套很深的 JSON 数据结构这类更复杂的结构化输出，反思更可能发现 bug。
  • 步骤说明。比如让 LLM 写“怎样泡出一杯完美的茶”的操作步骤，它有时会漏步骤。让反思提示词检查说明是否连贯、完整，可能帮忙发现错误。
  • 起域名。这是吴恩达自己做过的事：用 LLM 生成域名，但生成的名字有时带有意料之外的含义，或者很难念。他用反思提示词再检查一遍有没有不好的含义、好不好念。他说他在 AI Fund 的团队用这个方法给正在筹建的创业公司想域名。

两个反思提示词示例

幻灯片上给了两段反思提示词，原文如下：

Brainstorming domain names:

Review the domain names you suggested.
Check if each name is easy to pronounce and thus easy to spread via word of mouth.
Consider whether each name might mean something negative in other languages.
Then output a shortlist of only the names that meet these criteria.
Improving email:

Review the email first draft.
Check that the tone is professional and look for phrases that could be considered rude or insensitive.
Verify all facts, dates, and promises are accurate.
Then write the next draft of the email.

关于邮件这一段，他补充说“核对事实”的前提是：写初稿时已经把相关事实、日期等信息喂给了 LLM，这些都在 LLM 的上下文（Context，模型这次调用能看到的全部输入）里。

写反思提示词的建议

  • 明确告诉模型，你要它审阅或反思的是初稿。
  • 尽量给出一组清晰的标准，比如域名好不好念、有没有负面含义，邮件的语气、事实是否准确。标准越清楚，LLM 越能按你最在意的方面去反思和批评。
  • 他自己学写提示词的一个办法是多读别人写的提示词。有时他会下载开源软件，找到他觉得做得特别好的那些，专门去读作者写的提示词。

下一节他要讲一个多模态（multimodal，模型能同时处理文字和图像等多种输入输出）的例子：让算法对生成的图表做反思。

11. 图表生成工作流

英文原题 Chart generation workflow · 课程页 · 3:53

任务：比较两年第一季度的咖啡销量

这是本模块编程实验里要做的工作流：用一个 Agent 生成好看的图表。吴恩达说反思能明显提升这类输出的质量。

数据来自一台咖啡机，记录了每种饮品（拿铁、热巧克力、卡布奇诺等）什么时候卖出、卖了多少钱。目标是让 Agent 画一张图，比较 2024 年和 2025 年第一季度（Q1）的咖啡销量。数据存在一个 CSV 文件（comma-separated values，用逗号分隔字段的表格文件）里。

工作流一步步走

  1. 提示词交给 LLM，让它写 Python 代码。幻灯片上的提示词是：Create a plot comparing Q1 coffee sales in 2024 and 2025 using coffee_sales.csv.
  2. LLM 输出 v1 代码。幻灯片上露出的开头是这样的： 
    import matplotlib.pyplot as plt
import pandas as pd

# Filter for Q1 sales
q1_sales = df[df['quarter'] == 1]
....
  3. 执行 v1 代码，得到 plot.png。吴恩达说他第一次运行时真的就得到了这张图：一张堆叠柱状图（stacked bar plot），2024 和 2025 各一根柱子，每种饮品叠成一段。他认为这种图不太容易看，整体也不算好看。
  4. 把 v1 代码和它画出的 plot.png 一起交给一个多模态 LLM（能接受图像输入的 LLM），让它检查这张图、提出批评、想出更好的可视化方式，并更新代码。多模态 LLM 能做视觉推理，能真的“看”这张图来找改进点。
  5. 执行 v2 代码，得到 plot_v2.png。这次是一张普通的分组柱状图，把两年的各类饮品分开排列。他觉得更清楚，也更好看。

他鼓励大家在实验里多折腾，看能不能画出更好看的图。

生成和反思用不同的 LLM

因为不同 LLM 各有长短，他有时会给初次生成和反思分配不同的模型。比如用 OpenAI 的 GPT-4o 或 GPT-5 这类模型写初始代码。幻灯片“Reflection with a different LLM”上的两段提示词是： 

LLM (code generation):
Write python code to generate a visualization
that answers the user's question

{user prompt}

LLM 2 (reflection):
You are an expert data analyst who provides
constructive feedback on visualizations.

{V1 code} {plot.png} {conversation history}

Step 1: Critique the attached chart for readability, clarity,
and completeness.

Step 2: Write new code to implement your improvements.

反思提示词让模型扮演一位提供建设性反馈的数据分析专家，给它 v1 代码、生成的图，可能还有生成代码时的对话历史，再让它按具体标准批评。吴恩达再次强调，给出可读性、清晰度、完整性这类具体标准，LLM 更清楚该怎么做。最后让它写新代码实现改进。

他还提到，用推理模型做反思，有时比用非推理模型效果好。初次生成和反思各用哪个模型，是可以切换、组合着试的不同配置。

反思对你的应用到底有没有用

做应用时会碰到一个问题：反思在我这个具体应用上真能提升性能吗？吴恩达说，从各种研究看，反思在有些应用上提升一点，在有些上提升很多，在另一些上几乎没有提升。所以需要了解它对你的应用的影响，这也能指导你去调初次生成或反思的提示词。下一节讲怎样为反思工作流做评测。

12. 评估反思带来的效果

英文原题 Evaluating the impact of reflection · 课程页 · 8:16

吴恩达说反思通常能提升系统性能，但在决定保留它之前，他一般会先确认它到底提升了多少，因为多一个步骤会让系统变慢一点。这一节讲反思工作流的评测（Eval，用一组测试样例系统地衡量系统表现）。

例子：用反思改进 SQL 查询

假设你经营一家零售店，会被问到“哪种颜色的商品总销售额最高？”这类问题。要回答它，可以让 LLM 生成一条数据库查询，比如用 SQL（一种查询数据库的语言）写。他说不熟悉 SQL 也不要紧。幻灯片上的流程是：

  1. LLM 根据问题生成 SQL 查询（v1）。
  2. 同一个或另一个 LLM 反思 v1 SQL，写出 v2 查询。幻灯片上这一步用红色虚线框圈出来，是要评估的部分。
  3. 执行 v2 SQL，拿到查询结果。
  4. 再由 LLM 根据查询结果回答问题。

要回答的问题是：用第二个 LLM 反思并改进 SQL 查询，最终输出真的变好了吗？

客观评测：准备带标准答案的数据集

做法是收集一组问题（提示词），并为每个问题写下标准答案（ground truth，人工确认过的正确答案）。他说大概写 10 到 15 条就行。幻灯片上的表格是这样的：

PromptsGround truth answerNo reflectionWith reflection
Number of items sold in May 2025?12019801201
Most expensive item?Airflow sneakerAirflow sneakerAirflow sneaker
How many styles carried?141414
87% correct95% correct

“不加反思”指直接用第一个 LLM 生成的 SQL 去查，看得到什么答案；“加反思”指用第二个 LLM 反思后的 SQL 去查。然后分别统计答对的比例。这个例子里，不加反思答对 87%，加反思答对 95%。他说这说明反思确实明显提高了 SQL 查询的质量，能更多地查出正确答案。（口播里他把 5 月销量说成 1,301，幻灯片上写的是 1201。）

有了评测，就能放心改提示词

开发者经常会改写反思提示词。比如要不要在反思提示词里加一句，让查询跑得更快或写得更清楚？或者你对初次生成提示词、反思提示词各有不同改法。评测搭好之后，就能快速试各种提示词，看系统答对的比例怎么变，判断哪种提示词最适合你的应用。他的建议是：如果要试很多提示词，搭评测很重要，它让你有一套系统的方法在候选提示词之间做选择。

这个例子可以用客观评测，因为有唯一正确答案：卖了多少件，答案要么对要么错。

主观评测：两张图哪张更好

上一节的图表例子里，不加反思得到堆叠柱状图，加反思得到分组柱状图。吴恩达说他更喜欢后者，但图表会在很多维度上不同，怎么判断哪张更好？这更像一个主观标准，很难像对错题那样黑白分明。

对这类主观标准，可以用 LLM-as-a-judge（让一个 LLM 充当评委，给其他模型的输出打分或排序）。最基础的做法是把两张图都喂给一个能同时接受两张图片的多模态 LLM，直接问哪张更好，也可以再给它清晰度、美观程度之类的标准。但他说这样做效果不太好，用 LLM 比较两个输入、判断哪个更好有一些已知问题：

  • 给出的答案往往不太好。
  • 对评委提示词的具体措辞很敏感。
  • 排出的顺序有时和人类专家的判断对不太上。
  • 位置偏差（position bias）：很多 LLM 更常选第一个选项。他说他用过很多 LLM，给两个选项时，不管哪个放在前面，它都说第一个更好。也许有些 LLM 偏向第二个，但他认为大多数偏向第一个。

更好的办法：按评分细则逐项打分

与其让 LLM 比较一对输入，不如每次只给它一张图，按评分细则（rubric）打分，结果会更一致。幻灯片上的评分提示词是： 

Assess the attached image against this quality rubric.
Each item should receive a score for 1 (true) or 0 (false).
Return the scores for each item as a json object

1. Has clear title
2. Axis labels present
3. Appropriate chart type
4. Axes use appropriate numerical range
5. ...

他特别指出，与其让 LLM 在 1 到 5 分的量表上打分（LLM 在这种量表上往往校准得不好），不如给它比如 5 条二元标准，每条只打 0 或 1，再把分数加起来，得到 0 到 5 的总分；有 10 条标准就是 0 到 10。这样结果更一致。

具体做法是：收集 10 到 15 条用户可能提出的、针对咖啡机销售数据的不同可视化请求，分别用不加反思和加反思的流程生成图片，再用这套细则给每张图打分，检查加反思生成的图是否真的更好。评测搭好之后，以后改初次生成提示词或反思提示词，都可以重跑一遍，看改动后的系统生成的图能不能在细则上拿到更多分。这也是持续调优提示词的方法。

两类评测的对比

  • 有客观标准时，基于代码的评测（code-based evaluation）通常更好管理。SQL 的例子里，就是建一个标准答案的数据集，写代码统计系统答对的比例，是一个客观的评测指标。
  • 主观任务可以用 LLM-as-a-judge，但通常要多花些功夫调，比如想清楚用什么评分细则，才能让评委校准得好、给出可靠的评测结果。

吴恩达说会做评测对高效构建 Agentic 工作流很重要，后面的视频还会讲更多。下一节深入讲反思的一个方面：从外部获取额外信息。

13. 使用外部反馈

英文原题 Using external feedback · 课程页 · 4:49

吴恩达开头就说：如果能拿到外部反馈，带外部反馈的反思比只靠 LLM 自己当反馈来源的反思强得多。

提示词工程的投入回报曲线

幻灯片标题是“Return on investment on prompt engineering”，横轴是花在提示词工程（prompt engineering，反复修改提示词来提升效果）上的时间，纵轴是性能，有三条曲线：

  • 红线 No reflection：只做直接生成（零样本提示）时，一开始调提示词性能会涨一阵，之后逐渐走平，再怎么改提示词也很难更好。
  • 蓝线 With reflection：与其把时间都耗在调提示词上，有时更好的做法是早一点加入反思，性能会跳一下，跳多跳少不一定，但系统也更复杂了。在曲线中段加入反思后再调反思提示词，性能会走到更高的水平。
  • 黄线 Reflection with external feedback：如果除了 LLM 对原有信息的再思考，还能拿到来自外部的新信息，继续调提示词和外部反馈，有时能达到更高的性能。

他的建议：如果你在做提示词工程，感觉投入回报在递减，改了很多提示词也不见明显提升，可以考虑加反思，最好是找找有没有可以接入的外部反馈，把性能曲线从走平的红线拉到更高的轨迹上。

外部反馈的几个例子

他先回顾了前面讲过的代码例子：执行代码，把输出或错误信息交回给 LLM，让它带着这些新信息反思并写出新版本。接着又举了三个用软件代码或工具产生新信息、辅助反思的例子：

  • 正则匹配查竞品名。LLM 写邮件时有时会提到竞争对手的名字。可以写一段代码或做个工具做模式匹配，比如用正则表达式（regular expression，按规则匹配文本的写法）在输出里搜竞品名。一旦找到，就把它作为批评或输入交回给 LLM，让它重写、不提竞品。
  • 用网页搜索核对事实。比如一个研究 Agent 写了“泰姬陵建于 1648 年”。实际上泰姬陵是 1631 年下令修建、1648 年完工，所以这句话不算完全错，但也没有准确反映历史。如果做一次网页搜索，取回一段准确说明建造时期的片段，作为额外输入交给反思 Agent，它就可能写出关于泰姬陵历史更好的版本。
  • 字数统计工具。让 LLM 写博客文案或论文摘要时，它有时会超出字数限制，吴恩达说 LLM 现在仍不太擅长精确遵守字数。可以写代码精确统计字数，超了就把字数反馈给 LLM 让它重写，这样能更准确地写到想要的长度。

这三个例子的共同点是：写一段代码查出关于初始输出的额外事实（发现了竞品名、搜到的信息、准确的字数），再把这些事实交给负责反思的 LLM，帮它更好地思考怎么改进输出。
