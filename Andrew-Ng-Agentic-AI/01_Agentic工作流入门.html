01. 欢迎

英文原题 Welcome! · 课程页 · 1:57

“agentic”这个词和它的热度

吴恩达说，“agentic”这个词是他提出来的，用来描述他看到的一种快速增长的趋势：人们开始用新的方式在大语言模型（LLM，Large Language Model，用海量文本训练、能根据提示生成文字的模型）之上搭应用。他没料到的是，营销人员拿到这个词以后，把它当贴纸贴在几乎所有东西上，于是 Agentic AI 的炒作一路飙升。

好消息是，撇开炒作不谈，真正有价值的 Agentic AI 应用也在快速增长，只是速度比不上炒作。这门课要讲的是搭建这类应用的最佳实践。

现在用它做什么

  • 客服 Agent；
  • 深度研究（deep research），帮人写有洞见的研究报告；
  • 处理复杂的法律文件；
  • 读病人的输入，给出可能的医学诊断建议。

他说自己很多团队做的项目，没有 Agentic 工作流根本做不出来，所以会搭这类应用是当今 AI 里最重要、最有价值的技能之一。

会做和不太会做的人差在哪

他观察到，真正擅长搭 Agentic 工作流的人和效率不高的人，最大的差别之一是能不能推动一套有纪律的开发流程，具体来说是围绕评测（Eval）和错误分析（Error Analysis）的流程。评测就是用一组样例系统地衡量系统表现好不好；错误分析是逐个查看出错的地方，找出该改哪一块。课程里会讲这两件事具体指什么。

02. 什么是 Agentic AI

英文原题 What is agentic AI? · 课程页 · 5:12

一口气写完 vs. 分步迭代

很多人今天用 LLM 的方式是直接给一个提示词（Prompt），比如“帮我写一篇关于主题 X 的文章”。吴恩达把这比作让一个人（这里是 AI）从第一个字写到最后一个字，一气呵成，而且不许按退格键。人用这种完全线性的方式写不出最好的文章，AI 也一样。他说，尽管有这么大的限制，LLM 的表现已经出乎意料地好。

换成 Agentic 工作流，过程可能是这样：

  1. 先写一个文章大纲；
  2. 判断需不需要上网查资料；
  3. 做网页搜索，下载一些网页；
  4. 写初稿；
  5. 读初稿，看哪些部分需要修改或补充研究；
  6. 修改初稿，如此往复。

这个过程更像人的做法：想一想、查一查、改一改，再想一想。这样迭代下来，Agentic 工作流花的时间更长，但交出来的东西好得多。

定义

吴恩达给的定义是：Agentic AI 工作流是一个基于 LLM 的应用执行多个步骤来完成一项任务的过程。

拿写文章的例子来对应：

  • 用一个 LLM 写大纲；
  • 用一个 LLM 决定往搜索引擎里输入什么搜索词，准确说是用什么搜索词去调用网页搜索 API（API 是程序之间互相调用的接口）；
  • 把下载的网页喂给 LLM，让它写初稿；
  • 再用另一个 LLM 做反思，判断哪里需要改；
  • 根据设计，还可以加一个人在回路（human in the loop）的步骤：LLM 可以选择请人审核一些关键事实；
  • 然后再修改初稿。

这门课的核心技能：任务拆解

课程要教的一项关键技能，是把写文章这样的复杂任务拆成更小的步骤，让 Agentic 工作流一步一步执行。知道怎么拆、怎么把每一步的组件做好，他说这不容易，但决定了你能为多大范围的应用搭出 Agentic 工作流。

贯穿全课的例子：研究 Agent

他演示了一个研究 Agent。输入的研究题目是“我该怎么建一家新的火箭公司来和 SpaceX 竞争”。他说自己并不想和 SpaceX 竞争，但如果你想，可以让研究 Agent 帮你做背景调研。这个 Agent 的流程是：

  1. 规划要做哪些研究，包括调用网页搜索引擎下载网页；
  2. 综合并排序找到的信息；
  3. 起草大纲；
  4. 让一个编辑 Agent 审查连贯性；
  5. 最后生成一份完整的 Markdown 报告，包含引言、背景、发现等部分。

他说报告恰当地指出了这会是一家很难做的创业公司。因为它找了多个来源并下载下来认真思考，最后的报告比直接让 LLM 写一篇文章要周到得多。

他对这个例子感兴趣的一个原因是，他自己的工作里搭过不少专门的研究 Agent，比如做法律合规文件的、某些医疗领域的、商业产品研究的。他希望学员通过这个例子学会给别的应用搭 Agentic 工作流，同时以后真需要定制研究 Agent 时，这里的一些思路也能直接用上。

刚才演示的是一个相对复杂、高度自主的工作流，但也有很多简单的工作流同样有价值。下一节讲自主程度。

03. 自主程度

英文原题 Degrees of autonomy · 课程页 · 5:03

为什么用形容词“agentic”

几年前，AI 社区里有一场越来越有争议的讨论：什么才算 Agent。有人发论文说“我做了一个 Agent”，另一些人反驳“那不是真正的 Agent”。吴恩达觉得这种争论没必要，于是开始用“agentic”这个词。把它当形容词用，不做“是 Agent / 不是 Agent”的二分，就等于承认系统可以有不同程度的 agentic。那就都叫 agentic，然后去做真正的搭建工作，不必纠结够不够自主。

他回忆，准备一场关于 agentic reasoning 的演讲时，有个团队成员找他说：“Andrew，我们不需要再多一个词了，已经有 agent 了，你为什么还要造一个 agentic？”他还是用了。后来他在自己的 newsletter《The Batch》上写了一篇文章，也发在社交媒体上，主张别再争哪些算真正的 Agent，承认系统可以有不同程度的 agentic。他认为这帮大家绕过了“什么是真正的 Agent”的争论，把注意力放到搭建上。

自主程度较低的 Agent

例子是写一篇关于黑洞的文章。一个比较简单的 Agent 可以先让 LLM 想几个网页搜索词，然后在代码里写死：调用网页搜索引擎、抓取一些网页、再用这些内容写文章。这是一个步骤完全确定的序列，效果还可以。

图示约定

整门课的图里，他用颜色区分三类框：

  • 红色：用户输入，比如用户的问题，或者后面例子里输入工作流的文档；
  • 灰色：对 LLM 的调用；
  • 绿色：用其他软件执行动作的步骤，比如网页搜索 API 调用（web search），或者执行代码抓取网站内容（web fetch）。

自主程度更高的 Agent

同样是写黑洞文章，可以让 LLM 自己决定：是做网页搜索，还是搜最近的新闻，还是去 arXiv 网站搜最新论文。在他的例子里，做出选择的是 LLM，它选了调用网页搜索引擎，工程师没有事先指定。接着还可以让 LLM 决定要抓取几个网页；如果抓到的是 PDF，要不要调用一个函数，也就是一个工具，把 PDF 转成文本。它可能抓取前几个网页，写出文章，再决定要不要反思改进，甚至回头再抓更多网页，最后输出。

一条光谱

  • 自主程度低：所有步骤都由程序员事先定好；调用的函数，比如网页搜索，由工程师写死。这叫工具使用（Tool Use），模块 3 会讲。大部分自主性只体现在 LLM 生成什么文本上。
  • 高度自主：Agent 自己做很多决定，包括决定写文章要执行哪些步骤、按什么顺序。有些高度自主的 Agent 甚至能写新函数，或者自己造出新工具再去执行。
  • 半自主：介于两者之间，能做一些决定、挑选工具，但工具通常是预先定义好的。

课程里会教怎么搭这条光谱上任何位置的应用。吴恩达说，光谱低自主的一端有大量很有价值的应用，正在为很多企业搭建；高度自主的一端也有人在做，但通常更难控制、更难预测，而且还有很多研究在探索怎么搭这类 Agent。

04. Agentic AI 的好处

英文原题 Benefits of agentic AI · 课程页 · 4:47

吴恩达认为最大的好处是：很多以前做不到的任务，现在能有效完成。另外两个好处是并行，让某些事做得很快；以及模块化，让你可以从不同地方挑最好的组件拼成工作流。

好处一：效果更好（HumanEval 数据）

他的团队收集了一组编程基准测试的数据。基准测试（benchmark）是一套固定的题目，用来比较不同模型的能力；这里用的是 HumanEval，测 LLM 写代码完成特定任务的能力，指标是 pass@k。

  • GPT-3.5（第一个公开版 ChatGPT 所基于的模型）直接写代码，口述里说的是答对 40%，幻灯片上标注的是 48%；
  • GPT-4 好得多，同样用非 agentic 方式直接写，跳到 67%。

从 GPT-3.5 到 GPT-4 的提升已经很大，但把 GPT-3.5 包进 Agentic 工作流带来的提升更大。用课程后面会讲的技术，比如让 GPT-3.5 写代码，再反思代码看能不能改进，GPT-3.5 能达到高得多的水平。GPT-4 放进 Agentic 工作流里也好得多。

幻灯片上把各种 agentic 方法标在 40% 到 100% 的横轴上，按设计模式着色（Reflection、Tool Use、Planning、Multiagent）：

  • GPT-3.5 这一行：Intervenor、ANPL 在 75% 左右，Language Agent Tree Search 在 80% 出头，LDB+Reflexion 在 95% 左右；
  • GPT-4 这一行：CodeT、MetaGPT、ANPL 在 80% 出头，Reflexion 约 90%，Language Agent Tree Search 和 AgentCoder 在 90% 以上。

他的结论是：即使用当下最好的 LLM，Agentic 工作流也能让表现好得多。一代模型到下一代的提升虽然巨大，仍比不上在上一代模型上实现 Agentic 工作流带来的差距。

好处二：并行，速度快

还是写黑洞文章。可以让三个 LLM 并行，各自想网页搜索词去搜；每次搜索取前 3 个结果去抓取，于是一共 9 个网页。人做这项研究得一个一个读这 9 个网页，Agentic 工作流可以把 9 个网页的下载全部并行，最后统一交给一个 LLM 写文章。

他承认，Agentic 工作流比直接生成（只提示一次）要慢。但和人做同样的事相比，能并行下载大量网页，反而比一个人顺序处理快得多。

好处三：模块化，可以替换组件

他搭 Agentic 工作流时经常做的一件事，是检查各个组件，然后增加或替换：

  • 换网页搜索引擎。可选的有很多是专门给 LLM 用的：Google、Bing、DuckDuckGo、Tavily、You.com 等；
  • 把三次网页搜索中的某一步换成新闻搜索引擎，找黑洞科学的最新突破；
  • 每个步骤不一定用同一个 LLM，他常常试不同的模型、不同的 LLM 提供商，看哪个在哪一步效果最好。

他总结说，自己用 Agentic 工作流的主要原因就是在很多应用上效果好得多；另外它能把人只能顺序做的事并行化；模块化的设计让人可以增减或更新工具，有时还可以换模型。

05. Agentic AI 的应用

英文原题 Agentic AI applications · 课程页 · 7:39

这一节由易到难举了四个例子。

例一：发票处理

很多企业都要处理发票。给定一张发票，要提取最重要的字段：开票方（例子里是 Tech Flow Solutions）、开票方地址、应付金额（3,000 美元）、到期日（2025 年 8 月 20 日）。很多财务部门是由人来看发票，找出要付给谁、什么时候付，记进数据库，确保按时付款。

用 Agentic 工作流实现：

  1. 输入一张发票；
  2. 调用 PDF 转文本的 API，把 PDF 转成带格式的文本，比如 Markdown，供 LLM 读取；
  3. LLM 判断这是不是发票，不是就忽略；
  4. 如果是，提取所需字段；
  5. 用一个 API 或工具更新数据库，把这些字段存进记录。

这个工作流的特点是有清晰的流程：找出字段，记进数据库。吴恩达说，流程清晰的任务往往更容易交给 Agentic 工作流，因为可以一步一步可靠地执行。

例二：回复客户的订单咨询

稍难一点。步骤是：提取关键信息（客户订了什么、叫什么名字），查相关客户记录，最后起草回复，交给人审核后再发出。实现上：

  1. 把邮件交给 LLM，核对或提取订单细节；
  2. 如果邮件确实是关于订单的，LLM 可以选择调用订单数据库调出信息；
  3. 信息回到 LLM，起草回复邮件；
  4. LLM 可以选择调用一个“请求审核”（request review）工具，把草稿放进队列，人审核通过后再发给客户。

他说这种客户订单咨询 Agent 已经在很多企业搭建和上线了。

例三：通用客服 Agent

更难的情况是，客服 Agent 要回答客户可能问的任何问题，不只是订单。比如客户问“你们有黑色或蓝色牛仔裤吗？”要回答这个问题，可能要多次调用数据库 API：先查黑色牛仔裤库存，再查蓝色牛仔裤库存，然后回复。系统得自己规划出要查哪些数据库、按什么顺序查。

又比如客户说“我想退掉买的沙滩浴巾”。可能需要：核实客户确实买过沙滩浴巾；查退货政策，比如只能在购买后 30 天内退、浴巾必须没用过；如果可以退，让 Agent 开具退货单（return packing slip），并把数据库记录设为“退货待处理”（return pending）。

如果处理请求需要哪些步骤事先不知道，就更难，基于 LLM 的应用得自己判断要走哪三步。课程后面会讲这类问题的最新做法。

例四：电脑操作 Agent

特别难的一类是电脑操作（computer use）：Agent 用网页浏览器、读网页，自己想办法完成复杂任务。吴恩达让一个 Agent 查两个特定的美联航航班是否有座，从旧金山飞华盛顿 DCA 机场。视频里它自己在 United 网站上导航，点击页面元素、填写文本框。它边做边对页面内容推理，判断下一步做什么。

它在 United 网站上查航班遇到了麻烦，于是转到 Google Flights 去搜。在 Google Flights 上它找到几个符合要求的航班，选了一个，被带回 United 网站，这次似乎到了正确的页面，于是确认那两个航班有座。

他说电脑操作是当前很前沿、令人兴奋的研究方向，很多公司都想让它跑起来。这个例子里 Agent 最后找到了答案，但他常看到 Agent 用不好浏览器：网页加载慢时，Agent 可能搞不清状况；很多网页它还解析不了或读不准。他的判断是，电脑操作 Agent 目前还不够可靠，不能用在关键业务上，但这是未来重要的发展方向。

怎样判断难易

吴恩达考虑做一个 Agentic 工作流时的经验：

  • 较容易：有清晰的分步流程，或者企业已经有标准操作流程（SOP）可循。把这个流程编码进 Agent 可能要不少工作量，但实现起来往往更容易；
  • 较容易：只处理文本。LLM 本来就是在文本上成长起来的，处理其他输入模态也能做，但会难一些；
  • 较难：完成任务需要哪些步骤事先不知道，比如上面的通用客服 Agent，Agent 需要边做边规划，结果更难预测、更不可靠；
  • 较难：需要接收丰富的多模态输入，比如声音、视觉、音频，往往不如纯文本可靠。

06. 任务拆解：找出工作流里的步骤

英文原题 Task decomposition: Identifying the steps in a workflow · 课程页 · 8:36

人和企业要做很多事。这一节讲怎样把这些事拆成离散的步骤，交给 Agentic 工作流去执行。

例一：研究 Agent，拆了两轮

如果直接提示 LLM 写一篇关于主题 X 的文章，对需要深入研究的主题，输出可能只停在表面，或者只讲显而易见的事实。这时可以想想你作为人会怎么写：是坐下来就写，还是分几步？比如：

  1. 写文章大纲；
  2. 上网搜索；
  3. 根据搜索结果写文章。

拆步骤时，他一直在问自己一个问题：每一步能不能由一个 LLM、一小段代码、一次函数调用或一个工具完成？LLM 对他想思考的很多主题能写出像样的大纲，第一步可行；他知道怎么用 LLM 生成搜索词，第二步也可行；LLM 读搜索结果写文章，第三步也行。这就是一个比直接生成更深入的合理初版。

但实现以后看结果，可能还是不够好，不够有深度，文章读起来有点散。他说这事真发生过：他用这个工作流做过一个研究 Agent，读输出时觉得有点脱节，开头和中间不太一致，中间和结尾也不太一致。

这时再想想，如果你作为人发现文章有点散，会怎么改流程。一种做法是把第三步“写文章”再拆开：

  1. 写初稿；
  2. 判断哪些部分需要修改（读一遍初稿，这也是 LLM 做得不错的一件事）；
  3. 修改初稿。

回顾一下：从一步的直接生成开始，觉得不够好，拆成三步；还是不够好，再把其中一步拆成三步，得到一个更丰富的写作流程。根据对结果满意的程度，还可以继续改。

例二：客户订单咨询

  1. 提取关键信息：邮件是谁发的，订了什么，订单号是多少。LLM 能做。
  2. 找到相关客户记录：写出并生成合适的数据库查询，调出客户订了什么、什么时候发货等。一个能调用函数查询订单数据库的 LLM 应该能做。
  3. 写好回复并发给客户：有了调出的信息，如果给 LLM 调用发邮件 API 的能力，这一步也能做。

例三：发票处理

PDF 发票转成文本以后，第一步提取所需信息：开票方名称、地址、到期日、应付金额等，LLM 能做。第二步如果要确认信息已提取、存成数据库里的新记录，LLM 可以帮忙调用一个函数更新数据库。所以实现上基本就是这两步。

手里的积木

吴恩达把搭 Agentic 工作流看成用一批积木（building blocks）来拼：

  • AI 模型：大语言模型，或者要处理图像、音频时用大型多模态模型（LMM）。LLM 擅长生成文本、决定调用什么、提取信息。一些专门任务还会用别的 AI 模型，比如 PDF 转文本、文本转语音、图像分析。
  • 软件工具：各种可调用的 API，比如语音搜索、获取实时天气、发邮件、查日历等。
  • 信息检索工具：从数据库里调数据，或者做 RAG（Retrieval Augmented Generation，检索增强生成，先从一个大文本库里找出最相关的段落，再交给 LLM 生成回答）。
  • 代码执行工具：让 LLM 写代码并在你的电脑上运行，能做的事很多。

他说如果这些工具看起来有点陌生，不用担心，后面的模块会详细讲最重要的几种。他很多时候的工作就是看一个人或一家企业在做的事，然后想怎么把这些积木排成序列来完成任务。所以对有哪些积木可用了解得越清楚，越能想象出可以搭什么样的工作流。

他的方法

  • 看一个人在做的一堆事，找出可以实现的离散步骤；
  • 对每一步问：能不能用一个 LLM，或者手上的某个工具（API、函数调用）实现？
  • 如果不能，就问：我作为人会怎么做这一步？能不能再拆成更小的步骤，让它更适合用 LLM 或某个软件工具实现？

他说如果还没完全掌握也没关系，课程里会有很多例子。实际做的时候，通常先有一个初始的任务拆解和初始工作流，然后反复迭代改进很多次，直到达到想要的效果。推动这个改进过程的一项关键技能，是知道怎么评测你的工作流。

07. 评测 Agentic AI

英文原题 Evaluating agentic AI (evals) · 课程页 · 5:38

吴恩达和很多团队合作搭过 Agentic 工作流。他发现，最能预测一个人做得好不好的因素之一，是能不能推动一个有纪律的评测流程。这一节是概览，模块 4 会深入讲。

先做出来，再看输出

以客户订单咨询的工作流为例。搭好以后，很难事先知道哪里会出问题。所以他不建议提前设计评测。他的建议是先看输出，手动找你希望它做得更好的地方。

比如读了大量输出后，你发现它提到竞争对手的次数比应该的多。很多企业不希望 Agent 提竞争对手，因为场面会很尴尬。输出里可能有这样的句子：“很高兴你在我们这里购物，我们比竞争对手 ComproCo 好多了”，或者“没问题，和 RivalCo 不同，我们退货很方便”。这种问题在搭工作流之前很难预料。

所以最佳实践是先搭出来，检查哪里还不令人满意，再想办法评测和改进，消除这些不满意的地方。

客观标准：写代码检查

如果你的业务认为这样提竞争对手是错误，那么在消除这个问题的过程中，可以加一个评测来追踪这个错误出现的频率。手上有一份竞争对手名单（ComproCo、RivalCo、TheOtherCo），就可以写代码在输出里搜索这些名字，算出误提竞争对手的回复占全部回复的比例。

提竞争对手是一个客观指标：要么提了，要么没提。对于客观标准，可以写代码检查这个错误出现得多频繁。

主观标准：LLM 当评委

LLM 输出的是自由文本，有些评价标准更主观，很难写代码打出非黑即白的分数。这时常用的技术是 LLM 当评委（LLM-as-a-judge）：用另一个 LLM，给它一个提示词，让它给输出打分。比如研究 Agent 写的文章，可以这样提示（下面的英文按他的口述整理，不是幻灯片原文）： 

Assign the following essay a quality score between 1 and 5,
where 1 is the worst and 5 is the best.
{generated_essay}

他说这里的 Python 写法表示把生成的文章粘贴进去。然后让研究 Agent 就不同题目写多篇报告，比如黑洞科学的最新进展、用机器人采摘水果。评委 LLM 可能给黑洞那篇 3 分、机器人采摘那篇 4 分。随着你改进研究 Agent，希望看到这些分数逐渐上升。

他顺带提醒：LLM 其实不太擅长这种 1 到 5 分的打分。可以试试，但他自己不太用这种方法。后面的模块会讲让 LLM 输出更准确分数的更好技术，尽管也有人把 1 到 5 分的打分当作 LLM-as-a-judge 评测的初版。

后面会讲的两类评测

  • 端到端评测（end-to-end）：衡量整个 Agent 最终输出的质量；
  • 组件级评测（component level）：衡量工作流中某一个步骤输出的质量。

他说这两类评测在开发过程中各有用处。

看 trace，做错误分析

他自己还经常做的一件事，是检查中间输出，也叫 LLM 的轨迹（trace，记录工作流每一步输入和输出的日志），去理解它在哪里没达到预期。这就叫错误分析：把每一步的中间输出都读一遍，找改进的机会。他说会做评测和错误分析是一项关键技能，模块 4 会讲得更多。

08. Agentic 设计模式

英文原题 Agentic design patterns · 课程页 · 7:03

Agentic 工作流是把积木组合成复杂流程得到的。设计模式就是思考怎样组合这些积木的几种套路。吴恩达认为关键的设计模式有四个：反思（Reflection）、工具使用（Tool Use）、规划（Planning）、多 Agent 协作（Multi-agent Collaboration）。这一节逐个简单介绍，后面的模块会深入其中大部分。

一、反思

让一个 LLM Agent 写代码，它生成了一段代码，定义了一个完成某任务的 Python 函数。然后可以构造这样一个提示词，把它刚输出的代码粘贴回去： 

Here's code intended for a task:
{code}
Check the code carefully for correctness, style, and efficiency,
and give constructive criticism.

同一个模型这样被提示后，可能指出代码里的一些问题。再把这些批评反馈给模型：“看起来这里有个 bug，能改一下吗？”它可能就给出更好的版本。提前透露一下工具使用：如果能运行代码、看到哪里报错，把这个信息反馈给 LLM，它还能再迭代出更好的第 3 版。

所以反思这种设计模式，是让 LLM 检查自己的输出，或者引入外部信息，比如运行代码看有没有报错信息，以此为反馈再迭代出更好的输出。他说这不是魔法，不会让一切 100% 成功，但有时能给系统性能带来不错的提升。

他画的是同一个 LLM 被反复提示，但这也预示了多 Agent 工作流：可以不让同一个模型自我批评，另设一个批评 Agent。它也只是一个 LLM，提示词是“你的角色是批评代码，这是为某任务写的代码，仔细检查……”。这个批评 Agent 可以指出错误，或者运行单元测试。两个模拟的 Agent，每个都只是被提示扮演某个角色的 LLM，来回迭代，得到更好的输出。

二、工具使用

现在可以给 LLM 工具，也就是它可以调用来完成工作的函数。例子：

  • 问 LLM“评测者认为最好的咖啡机是哪个”，给它网页搜索工具，它就能上网搜，给出好得多的答案；
  • 问数学问题，比如“如果我以复利投资 100 美元，最后会有多少”，给它代码执行工具，它可以写代码并运行来算出答案。

开发者已经给 LLM 配了各种工具：数学和数据分析；从网页或各种数据库收集信息；对接邮件、日历等办公应用；处理图像等等。LLM 能自己决定用什么工具，也就是调用哪个函数，这让模型能完成多得多的事。

三、规划

例子来自一篇叫 HuggingGPT 的论文。请求是：生成一张女孩在读书的图，女孩的姿势和图中男孩一样，然后用语音描述这张新图。模型可以自动决定，要完成这个任务：

  1. 先找一个姿势识别模型，判断男孩的姿势；
  2. 再用一个根据姿势生成图像的模型，生成女孩的图；
  3. 再把图像转成文字描述；
  4. 最后文本转语音。

在规划模式里，LLM 决定要执行的动作序列，这个例子里是一串 API 调用，按正确顺序执行。步骤由 LLM 自己决定，开发者不用事先写死。吴恩达说，会规划的 Agent 目前更难控制，也更偏实验性，但有时能给出很让人惊喜的结果。

四、多 Agent 协作

人类经理会雇几个人一起做复杂项目；有时你也可以“雇”一组 Agent，每个专精一个角色，一起完成复杂任务。

他展示的图来自 ChatDev，一个由 Chen Qian 及合作者开发的软件框架。在 ChatDev 里，多个不同角色的 Agent，比如 CEO、程序员、测试员、设计师等，像一家虚拟软件公司那样协作，能完成一系列软件开发任务。

另一个例子：写一份营销宣传册，你可能会想雇三个人：一个研究员做网上调研，一个营销人员写营销文案，一个编辑润色。类似地，可以搭一个多 Agent 工作流，包含模拟的研究 Agent、营销 Agent 和编辑 Agent，一起完成这件事。

多 Agent 工作流更难控制，因为你并不总能事先知道各个 Agent 会做什么。但他说研究表明，它们在很多复杂任务上能带来更好的结果，比如写传记、决定下棋的走法。

吴恩达希望学员现在对 Agentic 工作流能做什么有了概念，也知道主要的难点：找到积木，再通过这些设计模式把它们拼起来，同时做好评测，看清系统表现、持续改进。下一个模块深入第一个设计模式：反思。他说它实现起来可能简单得出人意料，有时能让系统性能有不错的提升。
