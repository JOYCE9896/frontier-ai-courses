二、Lab 1：MapReduce

实现一个 MapReduce 系统，和第 1 讲的 MapReduce 论文类似（实验里用 "coordinator" 代替论文的 "master"）。一个 coordinator 进程负责分配任务、应对失败的 worker；一个或多个 worker 进程并行执行，调用应用的 Map 和 Reduce 函数，负责读写文件。真实系统里 worker 在不同机器上，本实验都跑在一台机器上，通过 RPC 和 coordinator 通信。

起步

$ git clone git://g.csail.mit.edu/6.5840-golabs-2026 6.5840
$ cd 6.5840/src/main
$ go build -buildmode=plugin ../mrapps/wc.go
$ rm mr-out*
$ go run mrsequential.go wc.so pg*.txt
$ sort mr-out-0
A 509
ABOUT 2
ACT 8
ACTRESS 1
...

src/main/mrsequential.go 是一个顺序版的 MapReduce，在一个进程里一次跑一个 map、一个 reduce，可以从中借代码。mrapps/wc.go 是词频统计，mrapps/indexer.go 是文本索引器，应用的 Map 和 Reduce 函数通过 Go 的 plugin 包在运行时从 .so 文件加载。实现写在 mr/coordinator.go、mr/worker.go、mr/rpc.go 三个文件里，main/mrcoordinator.go 和 main/mrworker.go 不要改。

分布式版本这样运行：

$ go run mrcoordinator.go sock123 pg-*.txt     # one window
$ go run mrworker.go wc.so sock123             # one or more other windows
$ cat mr-out-* | sort | more                   # should match sequential output

sock123 是 coordinator 接收 RPC 的 socket；每个 pg-*.txt 是一个 "split"，即一个 Map 任务的输入。

你的任务

每个 worker 在循环里：向 coordinator 要一个任务；从一个或多个文件读任务输入；执行任务；把输出写到一个或多个文件；再要新任务。coordinator 要注意到某个 worker 在合理时间内（本实验用十秒）没完成任务，把同一个任务交给另一个 worker。

测试（mr/mr_test.go）检查：wc 和 indexer 的输出正确；Map 和 Reduce 任务并行执行；worker 在运行任务时崩溃后能恢复。完成后应看到：

=== RUN   TestWc            --- PASS
=== RUN   TestIndexer       --- PASS
=== RUN   TestMapParallel   --- PASS
=== RUN   TestReduceParallel --- PASS
=== RUN   TestJobCount      --- PASS
=== RUN   TestEarlyExit     --- PASS
=== RUN   TestCrashWorker   --- PASS
PASS

（worker 在 coordinator 退出后连不上它时，打印少量 "connection refused" 是正常的。）

规则

  • map 阶段把中间键分到 nReduce 个桶里，nReduce 是 reduce 任务数（main/mrcoordinator.go 传给 MakeCoordinator() 的参数）；每个 mapper 为 reduce 任务创建 nReduce 个中间文件。
  • 第 X 个 reduce 任务的输出放在文件 mr-out-X 里，每行一个 Reduce 输出，用 Go 的 "%v %v" 格式打印键和值（见 mrsequential.go 里注释为 "this is the correct format" 的那行），格式偏差太大测试会失败。
  • worker 把 Map 的中间输出放在当前目录的文件里，之后作为 Reduce 的输入读回。
  • mr/coordinator.go 要实现 Done()，整个作业结束时返回 true，mrcoordinator.go 随之退出。
  • 作业结束时 worker 进程也要退出。简单的做法是看 call() 的返回值：联系不上 coordinator，就认为它已经因作业完成而退出了；也可以设计一个 "请退出" 的伪任务。

三、Lab 2：键值服务器

为单台机器构建一个键值服务器，保证尽管网络会出故障，每个 Put 最多执行一次（at-most-once），并且操作是线性一致的。然后用它实现一把锁。后面的实验会复制这样一台服务器来应对服务器崩溃。

接口

客户端通过 Clerk（一组发 RPC 的库函数）和服务器交互。两种 RPC：Put(key, value, version) 和 Get(key)。服务器在内存里维护一个 map，为每个键记录 (value, version)，键和值都是字符串，版本号记录这个键被写过几次。

  • Put(key, value, version)：只有 Put 的版本号和服务器上这个键的版本号一致时，才安装或替换值，同时把版本号加一。不一致就返回 rpc.ErrVersion。用版本号 0 的 Put 创建新键（服务器存下的版本是 1）。版本号大于 0 而键不存在，返回 rpc.ErrNoKey。
  • Get(key)：取回当前值和版本号；键不存在返回 rpc.ErrNoKey。

每个键维护版本号，对用 Put 实现锁、以及在网络不可靠、客户端重传时保证 Put 最多执行一次都有用。完成后，从调用 Clerk.Get 和 Clerk.Put 的客户端看，你有了一个线性一致的键值服务：非并发的操作，每个都能看到前面操作序列造成的修改；并发的操作，返回值和最终状态就像它们按某种顺序一次执行一个；一个操作必须看到在它开始前已经完成的所有操作的效果（见第八讲线性一致性）。单台服务器提供线性一致性相对容易。

代码在 src/kvsrv1：client.go 是 Clerk，server.go 是 Put 和 Get 的处理函数，RPC 请求、回复和错误值定义在 kvsrv1/rpc/rpc.go。

任务一：可靠网络下的键值服务器

先实现没有消息丢失时能工作的版本：在 client.go 的 Put/Get 里加发 RPC 的代码，在 server.go 里实现处理函数。通过 Reliable 测试（TestReliablePut、TestPutConcurrentReliable、TestMemPutManyClientsReliable）即完成。

任务二：用键值 Clerk 实现锁

很多分布式应用里，不同机器上的客户端用一个键值服务器协调活动，比如 ZooKeeper 和 Etcd 允许客户端用分布式锁协调，就像 Go 程序里的线程用 sync.Mutex 协调；ZooKeeper 和 Etcd 用条件 put 实现这种锁。你的任务是在 src/kvsrv1/lock/lock.go 里实现锁：可以有多把独立的锁，各有名字（传给 MakeLock）；支持 Acquire 和 Release；规范是同一时间只有一个客户端能成功获得某把锁，其他客户端要等它 Release。锁的状态通过 lk.ck.Put() 和 lk.ck.Get() 存在键值服务器里。

如果客户端持锁时崩溃，锁永远不会被释放。更复杂的设计会给锁加一个租约，租约到期时锁服务器替客户端释放锁；本实验里客户端不会崩溃，可以忽略这个问题。这个练习代码不多，但比上一个需要更多独立思考。每个锁客户端需要一个唯一标识，用 kvtest.RandValue(8) 生成随机字符串。

任务三：会丢消息的网络

网络可能重排、延迟或丢弃 RPC 请求和/或回复。为了从丢弃中恢复，Clerk 要不断重试每个 RPC，直到收到回复。ck.clnt.Call() 返回 true 表示收到了回复；返回 false 表示在超时时间内没收到。重试前稍等一下，比如 time.Sleep(100 * time.Millisecond)。服务器不需要改。

  • 如果丢的是请求，重发就解决了，服务器只收到并执行重发的那个。
  • 如果丢的是回复，客户端不知道丢的是哪个，只知道没收到回复。重发后服务器会收到两份请求。对 Get 没关系，它不改状态。对 Put，用同样的版本号重发是安全的，因为服务器按版本号有条件地执行：如果已经执行过，对重发的那份会回 rpc.ErrVersion，不会执行第二次。
  • 棘手的情况：对一个重试过的 RPC，服务器回复 rpc.ErrVersion。这时 Clerk 无法知道自己的 Put 有没有被执行：可能第一次执行了、成功回复被网络丢了，服务器只对重发的那次回了 ErrVersion；也可能另一个 Clerk 在第一次 RPC 到达前就更新了这个键，服务器两次都没执行。所以 Clerk 对重发的 Put 收到 rpc.ErrVersion 时，Clerk.Put 必须向应用返回 rpc.ErrMaybe，由应用处理。对首次（不是重发的）Put 收到 rpc.ErrVersion，就返回 rpc.ErrVersion，因为它肯定没执行。

如果 Put 是恰好一次（没有 ErrMaybe）对应用开发者会更方便，但不在服务器上为每个 Clerk 维护状态很难保证这一点。（2020 年版的 Lab 2 要求的就是恰好一次，Lab 5D 的扩展建议之一就是把它实现回来。）通过所有 kvsrv1 测试（多了 TestUnreliableNet）即完成。

四、Lab 3：Raft

这是构建容错键值存储系统系列实验的第一个：本实验实现 Raft，一个复制状态机协议；下一个在 Raft 之上构建键值服务；再下一个把服务"分片"到多个复制状态机上以提高性能。

复制的服务把状态（数据）的完整拷贝存在多台副本服务器上来实现容错，即使部分服务器出故障（崩溃，或网络断开、不稳定）也能继续运行。难点在于故障可能让副本持有不同的数据拷贝。Raft 把客户端请求组织成一个序列，即日志，并保证所有副本看到同样的日志；每个副本按日志顺序执行请求，应用到本地的服务状态上。所有活着的副本看到同样的日志内容，就以同样的顺序执行同样的请求，状态保持一致。服务器故障后恢复，Raft 负责把它的日志补齐。只要多数服务器活着并能互相通信，Raft 就能继续运行；没有这样的多数，Raft 不前进，但一旦多数又能通信，就从中断处继续。

按 Raft 扩展版论文实现，特别注意图 2。要实现论文的大部分内容，包括保存持久状态、节点故障重启后读回；不实现集群成员变更（第 6 节）。分四个部分，各有截止日期。代码写在 raft1/raft.go，测试在 raft1/raft_test.go。Raft 实例之间只能通过 RPC 交互（用 labrpc 包，测试器可以让它延迟、重排、丢弃 RPC 来模拟网络故障），不能通过共享的 Go 变量或文件通信。后面的实验都建立在这个实验上，留足时间写出可靠的代码。

接口

// create a new Raft server instance:
rf := Make(peers, me, persister, applyCh)

// start agreement on a new log entry:
rf.Start(command interface{}) (index, term, isleader)

// ask a Raft for its current term, and whether it thinks it is leader
rf.GetState() (term, isLeader)

// each time a new entry is committed to the log, each Raft peer
// should send an ApplyMsg to the service (or tester).
type ApplyMsg

peers 是所有 Raft 节点（包括自己）的网络标识数组，me 是自己在数组里的下标。Start(command) 让 Raft 开始把命令追加到复制日志，要立即返回，不等追加完成。每个新提交的日志条目，都要发一个 ApplyMsg 到 applyCh。

3D：日志压缩

目前重启的服务器要重放完整的 Raft 日志来恢复状态，但长期运行的服务不可能永远记住完整日志。要修改 Raft，配合那些不时持久保存自己状态"快照"的服务：快照之后，Raft 丢弃快照之前的日志条目。结果是持久数据更少、重启更快。但现在跟随者可能落后太多，领导者已经丢弃了它追上所需的日志条目；这时领导者要发快照，加上快照之后的日志。扩展版论文第 7 节概述了方案，细节要你自己设计。

五、Lab 4：容错键值服务

4A：复制状态机（rsm）

在常见的用 Raft 做复制的客户端/服务器服务里，服务和 Raft 有两种交互：服务的领导者调 raft.Start() 提交客户端操作；所有服务副本通过 Raft 的 applyCh 收到已提交的操作并执行。在领导者上这两件事相互作用：任何时刻都有一些服务器 goroutine 在处理客户端请求，已经调了 raft.Start()，各自在等自己的操作提交、等着知道执行结果；而已提交的操作出现在 applyCh 上时，要由服务执行，结果要交给当初调 raft.Start() 的那个 goroutine，让它回复客户端。

rsm 包封装了这种交互，它是服务（比如键值数据库）和 Raft 之间的一层。在 rsm/rsm.go 里要实现一个读 applyCh 的"reader" goroutine，和一个 rsm.Submit() 函数：为客户端操作调 raft.Start()，然后等 reader goroutine 把执行结果交给它。服务对 rsm 的 reader 来说是一个提供 DoOp() 方法的 StateMachine 对象，reader 把每个已提交的操作交给 DoOp()，DoOp() 的返回值交给对应的 Submit() 调用返回。Submit() 要把每个客户端操作和一个唯一标识一起包在 Op 结构体里，帮助 reader 把 applyCh 消息和等待中的 Submit() 调用对上。raft.Start() 表明当前节点不是领导者时，Submit() 返回 rpc.ErrWrongLeader。

一切顺利时，一个客户端请求的事件序列：

  1. 客户端把请求发给服务的领导者；
  2. 服务的领导者用这个请求调 rsm.Submit()；
  3. rsm.Submit() 用这个请求调 raft.Start()，然后等；
  4. Raft 提交请求，在所有节点的 applyCh 上发出；
  5. 每个节点上的 rsm reader goroutine 从 applyCh 读到请求，交给服务的 DoOp()；
  6. 在领导者上，rsm reader 把 DoOp() 的返回值交给最初提交请求的 Submit() goroutine，Submit() 返回这个值。

Submit() 要检测并处理这种情况：刚调完 raft.Start() 领导权就变了，操作丢失（永远不会提交）。一种做法是让 rsm 察觉到自己失去了领导权：Raft 的 term 变了，或者 Start() 返回的下标处出现了另一个请求，这时从 Submit() 返回 rpc.ErrWrongLeader。如果前领导者被单独分区，它不会知道新领导者；但同一分区里的客户端也联系不上新领导者，所以这时服务器无限期地等到分区愈合也可以。4A 里 rsm 测试器充当服务，提交的操作被解释为对单个整数状态的加一。不需要给 ApplyMsg 或 AppendEntries 等 Raft RPC 加字段，但允许加。

测试：RSM basic、concurrent submit、Leader Failure、Leader Partition、Restart、Shutdown、Restart and submit。

4B：不带快照的键值服务

用 rsm 复制一个键值服务器。每个 kvserver 有一个关联的 rsm/Raft 节点。Clerk 把 Put() 和 Get() RPC 发给关联 Raft 是领导者的那个 kvserver；kvserver 把操作提交给 rsm，rsm 用 Raft 复制它，并在每个节点上调用你的服务器的 DoOp，把操作应用到该节点的键值数据库上，目的是让各服务器维护相同的数据库副本。

  • Clerk 有时不知道哪个 kvserver 是领导者。RPC 发错了服务器，或者联系不上，就换一个 kvserver 重试。操作提交到 Raft 日志（因而应用到状态机）后，领导者通过回复 RPC 把结果告诉 Clerk；没能提交（比如领导者被替换了），服务器报错，Clerk 换服务器重试。
  • 先做没有消息丢失、没有服务器故障时能工作的版本，可以把 Lab 2 的 client.go 拷过来，加上决定把 RPC 发给哪个 kvserver 的逻辑。通过 TestBasic4B 即完成第一步。
  • kvserver 如果不在多数派里，就不应完成 Get() RPC（以免返回过时数据）。简单的办法是把每个 Get()（和每个 Put() 一样）都通过 Submit() 写进 Raft 日志。不必实现第 8 节描述的只读操作优化。
  • 一开始就加锁，因为避免死锁的需要有时会影响整体代码设计。
  • 然后处理网络和服务器故障。Clerk 可能要把一个 RPC 发多次，才找到一个肯定答复的 kvserver。如果领导者刚把条目提交到 Raft 日志就失败了，Clerk 可能收不到回复，于是把请求重发给另一个领导者。对一个特定的版本号，每次 Clerk.Put() 调用只应导致一次执行。Clerk 可以用和 Lab 2 类似的重试方案，包括重试的 Put RPC 的回复丢失时返回 ErrMaybe。
  • rsm 领导者可能失去领导权、从 Submit() 返回 rpc.ErrWrongLeader，这时让 Clerk 把请求发给其他服务器，直到找到新领导者。
  • 你大概要让 Clerk 记住上一次 RPC 时谁是领导者，下次先发给它，免得每次 RPC 都去找领导者，这可能帮你足够快地通过某些测试。

4C：带快照的键值服务

六、Lab 5：分片键值服务

可以做自己设计的期末项目，也可以做这个实验。构建一个把键"分片"（分区）到一组 Raft 复制的键值服务器组（shardgrp）上的存储系统。一个分片是键值对的一个子集，比如所有以 "a" 开头的键是一个分片，以 "b" 开头的是另一个。分片是为了性能：每个 shardgrp 只处理少数几个分片的 put 和 get，各 shardgrp 并行运行，所以系统总吞吐和 shardgrp 的数量成正比。

组成

  • shardgrp：存储分片，每个都是一组用 Raft 复制的服务器；
  • clerk：客户端通过它和分片键值服务交互，实现 Get 和 Put。为了找到一个键所在的 shardgrp，clerk 从 kvsrv（你在 Lab 2 实现的）读取配置；配置描述分片到 shardgrp 的映射（比如分片 1 由 shardgrp 3 服务）；
  • controller（控制器）：管理员（即测试器）用它增删 shardgrp、更新哪个 shardgrp 服务哪个分片。它的主要方法是 ChangeConfigTo，把系统从当前配置改到新配置：把分片移到新加入的 shardgrp，从要离开的 shardgrp 移走分片。为此控制器 1）向 shardgrp 发 RPC（FreezeShard、InstallShard、DeleteShard），2）更新 kvsrv 里存的配置。

需要控制器，是因为分片存储系统必须能在 shardgrp 之间挪分片：有的 shardgrp 负载更重，要移分片来平衡；shardgrp 会加入和离开，新加的提高容量，已有的下线维修或退役。

主要挑战：在 1）分片到 shardgrp 的分配变化、2）控制器在 ChangeConfigTo 中途失败或被分区的情况下，保证 Get/Put 的线性一致性。ChangeConfigTo 把分片从一个 shardgrp 移到另一个，风险是有的客户端用旧 shardgrp、有的用新 shardgrp，可能破坏线性一致性，所以任何时刻每个分片最多只能由一个 shardgrp 服务请求。如果 ChangeConfigTo 在重新配置时失败，那些开始移动但没移完的分片可能无法访问；为了继续前进，测试器会启动一个新控制器，你要保证新控制器完成旧控制器开始的重新配置。

本实验的"配置"指分片到 shardgrp 的分配，和 Raft 集群成员变更不是一回事，不用实现 Raft 成员变更。一个 shardgrp 服务器只属于一个 shardgrp，一个 shardgrp 的服务器集合永远不变。只能用 RPC 交互。这个设计和 Flat Datacenter Storage、BigTable、Spanner、FAWN、Apache HBase、Rosebud、Spinnaker 等很多系统的总体设计相同，它们在很多细节上不同，也更复杂、更强大，比如本实验不改变每个 Raft 组的节点集合，数据和查询模型都很简单。Lab 5 要用 Lab 2 的 kvsrv、Lab 4 的 rsm 和 Raft，并且 Lab 5 和 Lab 4 必须用同一份 rsm 和 Raft。Part A 可以用迟交时间，B–D 不行。

代码在 src/shardkv1：client.go 是 shardkv 的 clerk；shardcfg 包计算分片配置；shardgrp 包是 shardgrp 的 clerk 和服务器；shardctrler 包里的 shardctrler.go 有控制器改配置（ChangeConfigTo）和查配置（Query）的方法。

先在没有故障时实现 shardgrp 和 InitConfig、Query、ChangeConfigTo。shardkv1/shardcfg 里已经给了描述配置的代码：每个 shardcfg.ShardConfig 有一个唯一编号、分片号到组号的映射、组号到复制该组的服务器列表的映射。分片通常比组多（每个组服务不止一个分片），以便以相当细的粒度转移负载。

  1. 在 shardctrler/shardctrler.go 里实现 InitConfig 和 Query：InitConfig 收到测试器传来的第一个配置，把它存进一个 Lab 2 kvsrv 实例；Query 从 kvsrv 读出当前配置。用 ShardCtrler.IKVClerk 的 Get/Put 和 kvsrv 通信，用 ShardConfig 的 String 方法把配置转成字符串传给 Put，用 shardcfg.FromString() 转回来。通过 TestInitQuery5A 即完成，这一步不需要任何 shardgrp。
  2. 从 Lab 4 kvraft 拷代码，实现 shardgrp 的初版服务器（shardgrp/server.go）和 clerk（shardgrp/client.go）；实现 shardkv1/client.go 的 clerk：用 Query 找到键所在的 shardgrp，再和它通信。用 shardcfg.Key2Shard() 找键的分片号；测试器把一个 ShardCtrler 对象传给 MakeClerk；用 shardgrp.MakeClerk 为 shardgrp 创建 clerk，传入配置里找到的服务器和 shardkv clerk 的 ck.clnt；用 ShardConfig 的 GidServers() 找分片对应的组。shardkv1/client.go 的 Put 在回复可能丢失时必须返回 ErrMaybe，而它是调 shardgrp 的 Put 和某个 shardgrp 通信的，内层 Put 可以用一个错误表示这种情况。第一个 shardgrp（shardcfg.Gid1）创建时要初始化为拥有所有分片。通过 Static 测试即完成。
  3. 实现 ChangeConfigTo，支持分片在组间移动。新配置可能包含旧配置里没有的 shardgrp，也可能不包含旧配置里有的。控制器要移动分片（键值数据），让每个 shardgrp 存的分片集合和新配置相符。

建议的移动一个分片的做法：

1. FreezeShard at the source shardgrp   (source rejects Puts for keys in the shard)
2. InstallShard at the destination shardgrp (copy the shard)
3. DeleteShard at the source             (delete the frozen shard)
4. post the new configuration            (clients can now find the moved shard)

这种做法的好处是 shardgrp 之间没有任何直接交互，并且不受这次配置变更影响的分片可以照常服务。为了给配置变更排序，每个配置有唯一的编号 Num；Part A 里测试器顺序调用 ChangeConfigTo，每次传入的配置 Num 比上一个大一，所以 Num 越大越新。网络可能延迟 RPC，RPC 可能乱序到达 shardgrp；为了拒绝旧的 FreezeShard、InstallShard、DeleteShard，这些 RPC 要带上 Num（见 shardgrp/shardrpc/shardrpc.go），shardgrp 要记住每个分片见过的最大 Num。

  • shardgrp 对不归它负责的键（键的分片没分配给它）的 Put/Get 回复 ErrWrongGroup，shardkv1/client.go 要重读配置再重试。
  • FreezeShard、InstallShard、DeleteShard 也要像 Put 和 Get 一样通过 rsm 执行。
  • 可以在 RPC 请求或回复里直接发整个 map 作为状态，让分片转移的代码保持简单。
  • 如果 RPC 处理函数在回复里放了一个属于服务器状态的 map（比如键值 map），可能因竞争出 bug：RPC 系统要读这个 map 才能发给调用者，但它没持有保护这个 map 的锁，而你的服务器可能同时在改它。解决办法是在回复里放这个 map 的拷贝。

先通过 JoinBasic 和 DeleteBasic（关注 shardgrp 加入）；再扩展 ChangeConfigTo 处理 shardgrp 离开，通过 TestJoinLeaveBasic5A；最后通过所有 Part A 测试：很多组加入和离开、shardgrp 从快照重启、部分分片离线或在配置变更中时处理 Get、测试器并发调 ChangeConfigTo 重新平衡时很多客户端交互下的线性一致性。必须继续服务不受进行中的配置变更影响的分片。

5B：处理失败的控制器

控制器是一个短命的命令，由管理员调用：移动分片，然后退出。但它可能在移动分片时失败或断网。这部分的主要任务是从没能完成 ChangeConfigTo 的控制器中恢复。测试器把第一个控制器分区后，启动一个新控制器并调它的 ChangeConfigTo，你要让新控制器完成重新配置。测试器启动控制器时调 InitController，可以在这个函数里检查是否有被打断的配置变更要完成。

好的做法是保存两个配置：当前配置和下一个配置，都存在控制器的 kvsrv 里。控制器开始重新配置时，先存下一个配置；完成后，把下一个配置变成当前配置。InitController 先检查是否存有编号比当前配置更高的下一个配置，有的话就完成重新配置到它所需的分片移动。接手失败控制器工作的控制器可能重复 FreezeShard、InstallShard 和 Delete RPC，shardgrp 用 Num 检测重复并拒绝。

5C：并发的配置变更

控制器崩溃或被分区时，测试器启动新控制器，它要完成旧控制器可能在做的工作（像 5B 那样完成分片移动），这意味着可能有几个控制器同时运行，向 shardgrp 和存配置的 kvsrv 发 RPC。主要挑战是保证这些控制器互不干扰。Part A 里所有 shardgrp RPC 都已经用 Num 隔离（fence），旧 RPC 会被拒绝；即使几个控制器同时接手旧控制器的工作，一个成功、其他的重复所有 RPC，shardgrp 也会忽略它们。

剩下的难点是保证只有一个控制器更新"下一个配置"，避免两个控制器（比如一个被分区的和一个新的）往里放不同的配置。为了制造这种场景，测试器并发运行几个控制器，每个读当前配置、为一个离开或加入的 shardgrp 更新它，再调 ChangeConfigTo，所以多个控制器可能用同一个 Num 的不同配置调 ChangeConfigTo。可以用键的版本号和带版本的 Put，保证只有一个控制器更新下一个配置，其他调用什么都不做就返回（这就是 Lab 2 版本号的用处）。通过 TestConcurrentReliable5C 和 TestAcquireLockConcurrentUnreliable5C 即完成（测试器怎样并发运行控制器见 test.go 里的 concurCtrler）。

然后把旧控制器的恢复和新控制器结合起来：新控制器要执行 5B 的恢复；如果旧控制器在 ChangeConfigTo 中途被分区，要保证它不干扰新控制器。如果控制器的所有更新都已经像 5B 那样用 Num 检查隔离好了，就不用写额外的代码。通过 Partition 测试即完成。至此你实现了一个高可用的分片键值服务：多个分片组带来可扩展性，重新配置应对负载变化，控制器也是容错的。重跑所有测试，确认最近对控制器的修改没有破坏之前的测试。Gradescope 除了 5C 测试，还会重跑 Lab 3A 到 3D 和 Lab 4A 到 4C 的测试： 

$ make raft1
$ make kvraft1
$ make shardkv

  • 让 kvsrv 支持 Range 函数，返回从低键到高键范围内的所有键。偷懒的实现是遍历服务器维护的键值 map；更好的是用支持范围查找的数据结构（比如 B 树）。附一个让偷懒方案失败、让更好方案通过的测试。

  • 在 kvraft 里支持事务，让开发者能原子地执行多个 Put 和 Get。有了事务就不再需要带版本的 Put，事务涵盖了它。可以参考 etcd 的事务接口。
  • 让 shardkv 支持跨分片的事务，这需要实现两阶段提交和两阶段锁（见第十一讲）。
