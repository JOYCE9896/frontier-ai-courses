第十四讲：FaRM 与乐观并发控制

为什么读 FaRM，它和 Spanner 针对的瓶颈不同；整体设置：一个数据中心、ZooKeeper 配置管理、分片的主/备、f+1 个副本容忍 f 次故障；高性能的几个来源；用电池实现"非易失内存"；为什么网络常常是瓶颈：传统 RPC 栈的 CPU 开销；内核旁路和 RDMA，单边 RDMA；RDMA 和事务、复制怎样结合；乐观并发控制；事务 API、对象 ID、服务器内存布局；图 4 的提交协议：执行、LOCK、COMMIT-PRIMARY，三种交错下两个事务给 x 加一；VALIDATE 优化和经典的 x/y 例子；纯只读事务；容错：COMMIT-BACKUP 和为什么要等一个 COMMIT-PRIMARY；局限；FaRM 对 Spanner

主讲：Frans Kaashoek（2026 年春季讲义）；录像为 2020 年春季 Robert Morris 讲的同一篇论文
资料来源：2026 讲义、FaRM FAQ、2020 课堂录像、论文 No compromises: distributed transactions with consistency, availability, and performance（SOSP 2015）

一、为什么读 FaRM

  • 事务 + 复制 + 分片的另一种做法，这仍是一个开放的研究领域！人们对性能和一致性之间可选的取舍远不满意，还在努力做得更好。
  • 乐观并发控制。
  • 利用 RDMA 网卡巨大的性能潜力。

Morris 在录像里先对比 Spanner：两者都复制，都用两阶段提交做事务。Spanner 是部署多年的系统，主要关注地理复制，在东西海岸不同的数据中心放副本，最有新意的是用同步时间为只读事务开辟优化路径，读写事务要 10 到 100 毫秒。FaRM 是研究原型，探索新的 RDMA 高速网络硬件的潜力；假设所有副本在同一个数据中心，放在不同数据中心就完全没意义了，它的容错是针对单台崩溃，或者整个数据中心断电后恢复；RDMA 严重限制了设计选择，迫使它使用乐观并发控制；但性能远高于 Spanner，一个简单事务 58 微秒（6.3 节，图 7），比 Spanner 快约 100 倍。换个角度说，两者针对不同的瓶颈：Spanner 担心数据中心之间的光速和网络延迟，FaRM 担心服务器上的 CPU 时间，它把副本都放在同一个数据中心，就把光速和网络延迟"许愿"掉了。

二、整体设置

  • 全在一个数据中心里；
  • 配置管理器，用 ZooKeeper，选择主和备份；
  • 分片，每个分片主/备复制：P1 B1、P2 B2……只要每个分片至少剩一个副本就能恢复，即 f+1 个副本容忍 f 次故障。这些副本不用 Paxos 之类维护，每次修改都要更新所有副本，读总是读主；
  • 事务客户端（他们在服务器上运行）；
  • 事务代码充当两阶段提交的事务协调者（TC）。

FAQ：为什么有三种角色？数据分片在很多主/备集合上，备份存一份分片的数据和日志以防主坏掉；主执行对分片数据的所有读写，备份只执行写，以保持副本和主一致；只有一个配置管理器，跟踪哪些主和备份活着，以及数据怎样分片。高层上和 GFS 类似。

目标

每秒几百万个分布式事务，所以时间预算是几十微秒。很有挑战！

怎样获得高性能

  • 在很多服务器上分片（评估里 90 台），只要不同分片上的操作大致独立，就自动得到 90 倍的加速；
  • 数据必须放得进总内存（所以不读盘）；
  • 非易失内存（所以不写盘）；
  • 单边 RDMA（跨网络快速访问内存）；
  • 用户态直接快速访问网卡（内核旁路）；
  • 利用单边 RDMA 的事务加复制协议。

三、NVRAM（非易失内存）

FaRM 的写写到内存而不是磁盘，消除了一个巨大的瓶颈。写内存要 200 ns，写硬盘要 10 ms，写 SSD 要 100 us（ns 是纳秒，ms 是毫秒，us 是微秒）。和你们的 Raft 实现花大量时间持久化到磁盘相比，FaRM 里根本没有持久化写盘这件事。但内存断电就丢内容！它本身不是持久的。

为什么不直接写到 f+1 台机器的内存里来容忍 f 次故障？如果故障总是独立的，也许就够了，但停电不是独立的，可能一次击中 100% 的机器！所以：

  • 每个机柜装电池，能让机器运行几分钟；
  • 主电源断了，电源硬件通知软件；
  • 软件停止所有事务处理；
  • 软件把 FaRM 的内存写到 SSD，可能要几分钟；
  • 然后机器关机；
  • 重启时，FaRM 从 SSD 读回保存的内存镜像；
  • 这就是"非易失内存"。

如果崩溃让软件来不及写 SSD 呢？比如 FaRM 或内核的 bug，或者 CPU、内存、硬件错误。FaRM 用复制来应对单台机器的崩溃，（停电以外的）崩溃必须是独立的！总结：NVRAM 消除了持久化写的瓶颈，剩下网络和 CPU 是瓶颈。

有同学问数据中心断电、全部写到 SSD 后，能不能把数据搬到另一个数据中心继续运行：原则上可以，但旧数据中心没电，要把硬盘（甚至计算机）物理搬过去，恢复供电肯定更容易，FaRM 的设计者假设的是电会恢复。FAQ：这个想法很老，比如 90 年代初的 Harp 复制文件服务；很多存储系统以类似方式用电池（比如 RAID 控制器）来持久地写而不等磁盘。但 FaRM 这种电池配置不常见，通用软件不能依赖它；如果你自己的硬件配了电池，就该改改你的 Raft 来利用它。没有电池支撑的内存，FaRM 还有意义吗？大概没有，图 4 里 COMMIT-BACKUP 这类单边日志写就不能挺过断电了；可以改成所有日志更新都先写 SSD 再返回，但性能会低得多，SSD 写约 100 微秒，FaRM 对非易失内存的单边 RDMA 写只要几微秒。断电时用机械硬盘代替 SSD 也行，设计不用改，但写盘和读回都要慢约 10 倍，需要更大的电池和更多耐心。

四、网络：内核旁路与 RDMA

为什么网络常常是性能瓶颈

FaRM 假设单个数据中心，所以光速延迟小。但处理网络数据的 CPU 开销常常很大！局域网上 RPC over TCP 的通常结构： 

app                       app
---                       ---
socket buffers            buffers
TCP                       TCP
NIC driver                driver
NIC  -------------------- NIC

很多昂贵的 CPU 操作：系统调用，拷贝消息，中断，上下文切换。所以慢：很难造出每秒能送几十万个以上 RPC 的系统；对短 RPC，线路带宽（比如 10 Gbit/s）很少是限制；对小消息，限制性能的传统上是每个包的 CPU 开销。Morris：每秒几十万听起来很多，但对 FaRM 的目标差了几个数量级，远低于网线和网卡本身能做到的，数据库常用的小消息，10 Gbit/s 意味着每秒几百万甚至几千万条消息。FAQ 详细解释了传统 RPC 的路径：应用对本地内核做系统调用，内核让网卡发包；接收方网卡把包写进内存里的队列并中断内核，内核把包拷到用户空间并切换到接收应用；回复时反过来再走一遍，每个 RPC 要执行大量代码。

内核旁路（kernel bypass）

[FaRM user program] -- CPU cores -- [DMA queues in user RAM] -- [NIC]

应用直接和网卡交互，没有系统调用，不经内核；网卡直接 DMA 进出用户内存；FaRM 软件轮询 DMA 区域，检查是否有新消息到来；网卡轮询 DMA 区域，检查是否有要发出的消息。Morris：内核配置好保护机制，允许应用直接碰网卡的寄存器、告诉它做什么，内核就完全不参与网络了。代价是 TCP 原来做的事（校验和、重传等）要应用自己负责。可以用网上的 DPDK 工具包自己做内核旁路，相对容易用。这需要内核支持把硬件访问委托给应用（Linux 已经支持），也需要足够聪明的网卡，能为多个应用各自维护独立的队列。FAQ：FaRM 还专门拿出 CPU 核（论文叫硬件线程）来轮询进来的消息，消除了中断、系统调用、用户态和内核态之间的数据拷贝、上下文切换的开销。

RDMA（远程直接内存访问）

[src host] -- [NIC] -- [switch] -- [NIC] -- [target memory]   (target CPU not involved)
  • 远端网卡直接读写内存：发送方提供内存地址；远端 CPU 不参与！这就是"单边 RDMA"（one-sided RDMA）；原子地读一整条缓存行。
  • RDMA 网卡之间用可靠的协议，带确认（像 TCP 但不是 TCP），请求丢了会一直重传，最终告诉发起方成没成功。
  • 一台服务器的吞吐：每秒一千万次以上（图 2）。
  • 延迟：5 微秒（来自他们 NSDI 2014 的论文）。FAQ：一次单边 RDMA 读写最快只要 1/18 微秒（图 2），传统 RPC 可能要 10 微秒。

这还不是普遍使用的硬件，可以买到，但不是默认配置，而且只在局域网里工作，跨远距离的数据中心大概不行。FaRM 有时直接用单边读，但写的时候总是用 RDMA 把一条消息追加到目标机器内存里的消息队列或日志上，目标机器的软件轮询这些队列发现新消息，相当于一种类 RPC 的方案（FAQ：FaRM 的 LOCK 阶段就是这样用的；VALIDATE 阶段只用单边读）。这样的 RDMA 消息仍比传统 RPC 快得多。

如果客户端能通过单边 RDMA 直接访问服务器上的数据库记录，性能会惊人！那怎样把单边 RDMA 和复制、事务结合起来？我们到目前为止看到的协议都需要服务器主动参与，比如检查和设置锁、检查租约、指出什么时候已安全持久化。这和单边 RDMA 不能直接兼容。Morris 提出一个值得想的问题：能不能只用单边 RDMA 实现事务，从不发需要服务器软件解释的消息？FaRM 的回答实际上是"不能"。他推测将来网卡支持原子 test-and-set 之类更多操作时，也许能用纯单边 RDMA 做加锁方案，但 FaRM 没这么做。

五、乐观并发控制

事务的两类并发控制：

  • 悲观（两阶段锁）：第一次使用对象时等它的锁，持有到提交/中止；冲突导致延迟。
  • 乐观：不加锁地读对象；提交前不装入写（在客户端本地缓冲）；提交时"验证"有没有其他事务冲突；有效，提交写；无效，中止。叫乐观并发控制（OCC）。冲突时事务已经用了不该读的数据，计算已经"中毒"，没法像加锁那样阻塞等待，只能中止，也许重试。

FaRM 用 OCC。原因：OCC 让 FaRM 能用单边 RDMA 读，服务器不必主动参与读。这个设计实际上是被 RDMA 逼出来的。FaRM 的 OCC 怎样验证？下面看图 4。

FaRM 的事务 API（简化）

txCreate()
o = txRead(oid)   // RDMA
o.f += 1
txWrite(oid, o)   // purely local
ok = txCommit()   // Figure 4

（在作者 2014 年的论文里描述。）它是研究原型，不支持 SQL，没有 join 之类的花哨查询，只是很底层的读写接口加事务支持，可以看作一种带事务的 NoSQL 数据库。有同学问 OCC 冲突时中止，重试有没有指数退避：Morris 不记得论文提过，但在重试之间延迟、并逐渐加大延迟很有道理，就像 Raft 的随机选举计时器。

对象 ID 是什么

<region #, address>。region 编号索引到一张映射：[primary, backup1, ...]，配置管理器跟踪哪些服务器复制哪个 region；目标 RDMA 网卡直接用地址读内存。

服务器内存布局

  • 若干 region，每个是一个对象数组；
  • 对象布局：头部有版本号，锁标志在版本号的最高位。每个对象同一时刻只有一个版本，每次修改版本号加一；
  • 对每台其他服务器：一个进来的日志，一个进来的消息队列（发送方通过 RDMA 写，本地 FaRM 轮询读）。所以总共有 n 平方个这样的队列；
  • 所有这些都在非易失内存里（即断电时写到 SSD）。

六、图 4：事务执行和提交协议

一步一步看图 4，先关注并发控制（不考虑容错）。

执行阶段

  • TC（客户端）从服务器读它需要的对象，包括它将要写的记录（要先读才能拿到初始版本号）；用单边 RDMA 读；不加锁。这就是乐观并发控制里的"乐观"。每次 5 微秒左右，极快。
  • TC 记住版本号。
  • TC 在本地缓冲写。

现在 TC 提交，两大目标：原子的分布式提交，要么所有写都做、要么都不做；可串行化，仿佛完全在其他每个事务之前或之后执行。

LOCK（提交协议的第一条消息）

  • TC 发给每个被写对象的主；
  • TC 用 RDMA 往每个主上自己的日志里追加；
  • LOCK 记录包含 oid、事务读到的版本号、新值；
  • LOCK 现在记在主的 NVRAM 里，能挺过断电；
  • LOCK 消息既是一条预写日志条目，也是对主的一个 RPC 请求。

主收到 LOCK 后做什么？

  • FaRM 软件轮询内存里进来的日志，看到我们的 LOCK；
  • 如果对象已被锁，或者版本号不等于事务读到的版本，给 TC 发 "no"；
  • 否则设置对象的锁标志，回复 "yes"，但还不修改数据！
  • 检查锁、检查版本、设置锁这三步是原子的，用原子的比较并交换（compare-and-swap）指令。"locked" 标志是对象版本号的最高位，这样一条指令就能同时检查和设置两者；这是为了应对另一个 CPU 也在处理一个 LOCK（主是多线程的，可能有多个核同时读不同客户端的日志），或者有客户端正在用 RDMA 读。
  • 注意：如果对象已被锁，没有阻塞，不等锁释放，直接回 no。

TC 等所有 LOCK 的回复消息：只要有一个 "no" 就中止，往各个主的日志里追加 ABORT 让它们释放锁，txCommit() 返回 "no"。

先忽略 VALIDATE 和 COMMIT-BACKUP。这时主需要知道 TC 的决定：

COMMIT-PRIMARY

  • TC 往各个主的日志里追加 COMMIT-PRIMARY；
  • TC 只等 RDMA 硬件确认（ack），不等主处理这条日志，硬件确认意味着它已安全地在主的 NVRAM 里；
  • TC 从 txCommit() 返回 "yes"。Morris：只要收到任何一个主的确认就可以返回。

主处理日志里的 COMMIT-PRIMARY 时：把新值拷到对象的内存；版本号加一；清除对象的锁标志。所以一旦主处理了 COMMIT-PRIMARY，新数据就可能暴露给其他事务。

提交点是第一条 COMMIT-PRIMARY 被写入的时候，因为从那时起事务的结果就可以被暴露。等 TC 知道每个主都知道了它的决定，再通知它们丢掉这个事务的日志条目（FAQ：TC 看到所有主和备份的日志里都有 COMMIT-PRIMARY 或 COMMIT-BACKUP 后，告诉它们删除这个事务的日志条目；为了恢复时仍知道事务已完成，主在截断后仍记住已完成的事务 ID；截断意味着截断点之前的所有日志条目都被删，这行得通是因为每个主/备对每个 TC 有一份单独的日志）。

例子：T1 和 T2 都想给 x 加一

x = x + 1。可串行化允许哪些结果？即一个一个执行可能有哪些结果？

  • x = 2，两个客户端都被告知"成功"；
  • x = 1，一个被告知"成功"，另一个"中止"；
  • x = 0，两个都被告知"中止"。

如果 T1 和 T2 完全同步？

T1: Rx0  Lx  Cx
T2: Rx0  Lx  Cx

两个都能读，单边读不可能失败。两个给 x 的主发了相同的 LOCK（同样的版本号，同样的新值 1）。主可能在不同核上并行处理这两条 LOCK，但关键是原子的比较并交换：先执行的那个设置锁位、发现之前没被锁，回 yes；后执行的发现锁位已设，回 no。假设 T2 收到 no，中止；T1 提交，主装入新对象（1），清锁位，版本加一。结果 x = 1，一个 true 一个 false，合法。

或者：

T1:    Rx0 Lx Cx
T2: Rx0          Lx  Cx

T1 的 LOCK 成功，COMMIT-PRIMARY 清掉了锁位，所以 T2 的 LOCK 到来时锁位没设；但 COMMIT-PRIMARY 把版本号加了一，T2 的 LOCK 带的是它当初读到的旧版本号，主发现版本不对，回 no，T2 中止。结果仍是 x = 1，一真一假，合法。

或者：

T1: Rx0  Lx  Cx
T2:             Rx0  Lx  Cx

（讲义写成 Rx0，实际上 T2 这时读到的是 T1 写的 1。）第一个事务没有竞争，顺利提交。第二个事务读 x 时看到了新的版本号和新的值 1，锁位没设；它的 LOCK 到来时没被锁、版本也是最新的，允许提交。结果 x = 2，两个都返回 true。

为什么 FaRM 的 OCC 能提供可串行化，即检查了"执行是否和一个一个执行相同"的直觉：如果没有冲突的事务，版本号不会变；如果有冲突的事务，某一方会看到锁或者变了的版本号。比较开始读对象时和最终提交时的版本号与锁位，就能知道有没有别的提交插了进来。而这一切让我们能在读的时候根本不检查锁，从而使用极快的单边 RDMA 读。

图 4 里的 VALIDATE

它是对只被事务读、不被写的对象的一种优化。VALIDATE = 单边 RDMA 读，重新取回对象的版本号和锁标志；如果锁已设、或者自读取后版本号变了，TC 中止。它不设置锁，所以比 LOCK 加 COMMIT 快：一次单边读，而不是往日志追加、等主看到并处理。

VALIDATE 的例子：x 和 y 初始为零。

T1:
  if x == 0:
    y = 1
T2:
  if y == 0:
    x = 1

（这是事务的一个经典测试例子，也是强一致性的经典测试。）T1、T2 的顺序得到 y=1、x=0；T2、T1 得到 x=1、y=0；中止可能留下 x=0、y=0；但可串行化禁止 x=1、y=1。

假设同时执行：

T1:  Rx  Ly  Vx  Cy
T2:  Ry  Lx  Vy  Cx

会怎样？两个 LOCK 都会成功！两个 VALIDATE 都会失败，因为锁位都已被设置（被对方的 LOCK 设的）。所以两个都中止，这是可以的。

再看：

T1:  Rx  Ly  Vx      Cy
T2:  Ry          Lx  Vy  Cx

T1 提交：它验证 x 时还没人动过 x。T2 中止：T2 的 Vy 要么看到 T1 设的锁（T1 还没提交），要么看到更高的版本号（T1 已经提交）。但不可能两个 V 都在对方的 L 之前。所以在这个例子里 VALIDATE 看起来是正确的，而且快：一次单边 VALIDATE 读，而不是 LOCK 加 COMMIT 两次写。

纯只读事务

一个纯只读的 FaRM 事务只用单边 RDMA 读：读用单边读，验证也用单边读；没有写，没有日志记录，不加锁，服务器根本不需要参与。很快！

FAQ：怎样保证事务的读是一致的？有两个危险。一是大对象可能前一半在并发事务写之前读、后一半在写之后读，可能让读的程序崩溃；FAQ 作者根据 2014 年的论文理解，每个对象的每条缓存行都有版本号，单条缓存行的 RDMA 读写是原子的，FaRM 库取回对象的所有缓存行后检查版本号是否都相同，相同才交给应用，否则重读。二是读事务和并发写事务可能不可串行化，由第 4 节的验证解决。第 3 节说一个事务的读可能看到不一致的数据，这怎么可串行化？FaRM 只保证提交了的事务可串行化，看到这种不一致的事务会被中止；应用必须能容忍这种不一致而不崩溃，这样才能走到请求提交那一步，让 FaRM 中止它。

七、容错

假设一些计算机崩溃且不重启。最有意思的是 TC 和一些主都崩溃了，但我们假设每个分片至少有一个备份幸存。关键问题：如果一个事务被故障打断，而客户端可能已被告知事务提交了，或者一个已提交的值可能已被另一个事务读到，那么这个事务必须在恢复时被保留并完成。

看图 4。第一条 COMMIT-PRIMARY 一发出，已提交的写就可能被暴露（因为主会写入并解锁）。所以到那时，事务的所有写必须已经在所有相关分片的全部 f+1 个副本上。好消息：LOCK 和 COMMIT-BACKUP 做到了这一点。LOCK 把新值告诉所有主；COMMIT-BACKUP 把新值告诉所有备份；TC 在所有 LOCK 和 COMMIT-BACKUP 完成之前不发 COMMIT-PRIMARY。备份也许还没处理 COMMIT-BACKUP，但它们已在 NVRAM 日志里。

同样，TC 在至少一条 COMMIT-PRIMARY 安全地进入主的日志之前，不回复客户端。如果没有 COMMIT-PRIMARY，有风险的情形是：TC 在 COMMIT-BACKUP 之后（COMMIT-PRIMARY 之前）就回复应用"yes"；然后 TC 和所有备份都失败了；现在剩下的证据只有 LOCK 记录；但即使一整套 LOCK 记录也说明不了 TC 是否提交了，也许 TC 因为 VALIDATE 失败而中止了！写入 COMMIT-PRIMARY 处理了这个风险，因为 TC 的决定能挺过任何分片的 f 次故障：有一个分片拥有完整的一套 COMMIT-BACKUP 和 COMMIT-PRIMARY，其中任何一条都是"决定提交"的证据。

FAQ：COMMIT-BACKUP 期间可能因为硬件故障而中止吗？FAQ 作者认为可能：一个备份没回应，TC 又崩溃了，事务可能在恢复时被中止。论文里每个事务的消息数 Pw(f + 3) 中的 3 从哪来（Pw 是被写对象所在的主的数量）？f 为 1 且只涉及一个主 P 时，4 条消息是：发给 P 的 LOCK 请求、P 的 LOCK 回复（图 4 里画成单边 RDMA 写）、COMMIT-BACKUP、COMMIT-PRIMARY。"vertical Paxos"：一种由外部 master 做重新配置、Paxos 组在重新配置期间仍能继续执行操作的 Paxos 风格；FaRM 论文宽泛地用这个词，指配置管理由外部服务（ZooKeeper 和 CM）做，事务的写用标准的主/备协议处理。

八、评价

FaRM 很了不起，它离完美还差在哪

  • 因为用 OCC，冲突少时效果最好。FAQ：很多事务同时修改同一个对象时，有些会在 LOCK 阶段看到锁已被持有，读者可能在 VALIDATE 阶段看到变了的版本或锁标志，每个这样的事务都要中止、从头重来，频繁发生时性能确实会受损；作者测的应用大概冲突的事务比较少。
  • 数据必须放得进总内存。
  • 只在一个数据中心内复制（没有地理分布）。
  • 数据模型很底层，需要比如 SQL 库。
  • 需要有些不寻常的 RDMA 和 NVRAM 硬件。

FAQ 还列了：事务 API 看起来用起来别扭，回复通过回调返回；应用代码要和轮询 RDMA 网卡队列、日志紧密交织；应用在执行最终会中止的事务时可能看到不一致；FaRM 把线程钉在核上并占满所有核，应用可能没法随意用线程。它是探索新想法的研究原型，不是面向通用的成品。论文说 FaRM 宣告了分布式系统里一致性/可用性折中的终结吗？FAQ 说这部分更像广告而不是科学，历史表明没有哪种性能高到没人想要更多，那些人很可能愿意在别的方面妥协来换取所需的性能。图 7 里每微秒操作数超过 120 后延迟显著上升，FAQ 作者猜是服务器总共只能处理每秒约 1.4 亿次操作，客户端发得更快时一部分要等待。FaRM 在小规模下有意义吗？只有需要每秒极多事务时才有意思，每秒几千个用成熟的 MySQL 就行；最小也要分片加复制，至少四台数据服务器（两个分片、每片两台），加几台跑 ZooKeeper 的机器（大概也能跑在那四台上），成本大约一万美元量级，每秒能执行几百万个简单事务，相当不错。

FaRM 和 Spanner 有什么不同

两者都分片、复制，并用两阶段提交（2PC）做事务。

  • Spanner：专注于应对地理复制带来的网络延迟；Paxos 能容忍延迟；TrueTime 让它们能从本地副本读；性能：读写事务 10 到 100 ms（表 3 和表 6）。
  • FaRM：专注于降低 CPU 开销；RDMA、直接访问网卡、用 NVRAM 避免写盘；RDMA 把它们引向乐观并发控制（OCC）；性能：简单事务 58 微秒（6.3 节，图 7），即比 Spanner 快 100 倍。

总结

超高速的分布式事务。硬件很特殊（NVRAM 和 RDMA），但可能很快就会普及。用 OCC 获得速度，并允许快速的单边 RDMA 读。FAQ：硬件已经存在很多年了，但之前没人想出怎样把各部分组合起来、真正发挥硬件的潜力；FaRM 的一个原因在于他们同时在网络、持久存储和 CPU 使用上下了大功夫，以往很多系统只优化其中一个；一个具体的设计点是很多交互用快速的单边 RDMA 而不是更慢的完整 RPC。FaRM 是 Fast Remote Memory 的缩写。目前看是研究系统，没有在生产中使用。
