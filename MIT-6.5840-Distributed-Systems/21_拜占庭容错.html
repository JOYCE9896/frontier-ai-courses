第二十一讲：拜占庭容错（PBFT）

从比特币的局限说起：能不能在有恶意副本的情况下做复制状态机；什么是拜占庭故障，攻击者的能力和不可能发生的事；成绩文件的例子；一步步设计：要全部同意，2f+1 台等 f+1 个回复为什么不对，3f+1 台等 2f+1 个；多数派的安全性和活性；加一个主，故障主能做什么；PRE-PREPARE 和 PREPARE；三种情形的分析；视图变更、轮换主；为什么要第三阶段 COMMIT；新主怎样知道已执行的操作；扩展成完整的复制状态机和优化；FAQ：为什么是三分之一，FLP，视图变更不是选举，f 怎么定，N 版本编程

主讲：Derek Leung（2026 年春季）；本讲没有公开录像，内容根据讲义（2024 年版）、他的课件和 FAQ 整理
资料来源：讲义、课件、BFT FAQ、论文 Practical Byzantine Fault Tolerance（Castro 和 Liskov，OSDI 1999）

一、为什么读这篇论文

课件从上周讲起：第 19 讲 fork 一致性（SUNDR），第 20 讲去中心化支付（比特币）。比特币回答了"能不能在开放系统里复制状态"，解决了一个被认为不可能的问题！但有局限：吞吐每分钟约一千笔支付，延迟约一小时（6 个区块的深度），而且没有线性一致性保证。那复制状态机（Raft）呢？Raft 有线性一致性保证，网络有问题时就等它恢复。能不能实现一个副本可能是恶意的复制状态机？这叫"拜占庭"问题（Lamport、Shostak、Pease 1982）；Practical Byzantine Fault Tolerance（Castro 和 Liskov 1999）给出了实用的解法。课件说它曾是一个"学术问题"，如今是很多加密货币协议的祖先。

讲者介绍了自己：课程项目是实现 PBFT（6.5840 的期末项目）；工作是在 Algorand 公司实现 BFT 协议；博士项目是无 bug 地实现 PBFT（形式化验证，参见 IronFleet 和 6.5120，和 Frans Kaashoek、Nickolai Zeldovich 合作）。

讲义列出的理由：

  • 令人印象深刻的结果：解决了一个比 Raft 严格更难的问题，即存在恶意副本时的状态机复制；
  • 有很多后续论文；
  • BFT 今天并没有广泛使用，人们依靠预防和检测被攻破的节点；
  • BFT 在类比特币系统里正在回归：比特币解决了有恶意参与者的共识，但用的是工作量证明，解决分叉要很长时间；Stellar 把 PBFT 推广到联邦式部署；IBM 的 Hyperledger 用 PBFT。

课件的对照：PBFT 和 Raft 思路相似，都是复制状态机，但副本可能是恶意的。领导者 ≈ 主（primary），任期 ≈ 视图（view），都有超时。额外需要的成分：1. 消息的真实性；2. 更多的诚实节点；3. 领导权的"公平性"。

二、拜占庭故障和假设

我们看过很多容错协议，一直假设"故障即停"，比如断电，即服务器都遵守协议。这已经够难了：崩溃和网络断开的区分，网络分区。能不能处理更大一类故障？有 bug 的服务器，算错了而不是停下来；不遵守协议的服务器；被攻击者改过的服务器。这些通常叫"拜占庭"故障。FAQ：任何被攻破的计算机都会变成拜占庭的，因为它在攻击者的控制下。

论文的方法：复制状态机；假设 3f+1 台里有 2f+1 台不出故障；用投票选出正确的结果。这没听起来那么容易。

假设最坏的情况

一个攻击者控制着 f 个出故障的副本，并且主动地试图破坏系统。如果能应对这种情况，也就能应对 f 个副本里的 bug。

攻击者的能力：

  • 提供出故障副本运行的代码；
  • 知道非故障副本运行的代码；
  • 知道出故障副本的密钥；
  • 能读网络消息；
  • 能通过拒绝服务（DoS）暂时迫使消息被延迟；课件还加了：能重排消息。

什么故障不会发生：

  • 3f+1 个副本里出故障的不超过 f 个；
  • 没有客户端故障，客户端从不做坏事（课件："细节：论文里客户端是诚实的"）；
  • 不会猜中密钥或破解密码学：密码学保护诚实机器的消息。

课件讲了数字签名的接口：KeyGen(随机数) → (公钥, 私钥)；Sign(私钥, 消息) → 签名；Verify(公钥, 消息, 签名) → 是否通过。性质：正确性，非故障节点的签名一定能通过验证；安全性，验证通过就意味着签名来自那个（非故障）节点。课件在假设旁标了"现实吗？"

使用场景的例子

RM:
  echo A > grade
  echo B > grade
  tell FK "the grade file is ready"
FK:
  cat grade

一个出故障的系统可能：完全编造文件内容；执行 write("A") 却忽略 write("B")；给 RM 看 "B"、给 FK 看 "A"；只在部分副本上执行 write("B")。

三、一步步设计拜占庭容错的复制状态机

从简单（而错误）的开始，逐步走向论文的设计。

设计 1

  • n 台服务器，它们没有相同的漏洞：不同的操作系统、不同的服务实现等；
  • 客户端和服务器都有公钥对，每条消息都由发送者签名，接收者验证消息的来源；
  • 客户端把请求发给所有服务器，等所有 n 个回复，验证回复；只有 n 个全部一致才继续。

问题：一台服务器可能已被攻破，它只要不同意就能阻止系统前进。

设计 2：投票

2f+1 台服务器，假设不超过 f 台出故障。客户端等 f+1 个一致的回复：如果只有 f 台出故障，网络最终能工作，就一定能等到。

问题：f+1 个一致的回复可能是 f 个坏节点加 1 个好节点，所以也许只有一个好节点拿到了这个操作！下一个操作也等 f+1 个，可能不包括看到第一个操作的那个好节点。例子：f g1 g2（f 是坏的）： 

   Put k=A       Put k=B     Get k   ->   A   (f lies, sending A too)
C --------------------------------------------------
       ^ ^ ^      \   ^  ^    \   ^     ^
    \ / / /        \/  /       \ /     /
f --------------------------------------------------
     \/  /           \/         \    /
g1 --------------------------------------------------
       \/                         \/
g2 --------------------------------------------------
        A

所有人都听到并回复了 write("A")；f 和 g1 回复了 write("B")，g2 错过了，客户端不能等 g2，因为它可能就是那台坏服务器；f 和 g2 回复了 read()，g1 错过了；所以 read() 得到 "A"。结果：客户端被骗接受了一个基于过时状态的回复，比如助教读成绩文件读到 A 而不是 B。这破坏了正确性，它应该提供线性一致性（返回 B）。所以需要保证回复包含好节点的多数，这样之后至少有一个会返回 B。

设计 3：3f+1 台，等 2f+1 个

3f+1 台服务器，最多 f 台出故障。客户端等 2f+1 个一致的回复，相当于 f 个坏节点加上好节点的多数，所以任意两个 2f+1 的集合至少有一个好节点重叠。例子：f g1 g2 g3： 

   Put k=A        Put k=B       Get k: A  B    B  A
C --------------------------------------------------
       ^ ^ ^  ^     \  ^  ^ ^     \   ^  ^    ^ ^
    \ / / /  /       \/  / /       \ /   /   / /
f --------------------------------------------------
     \/  /  /         \/  /          \ /   / /
g1 --------------------------------------------------
       \/  /           \/              \/  /
g2 --------------------------------------------------
        \/                              \/
g3 --------------------------------------------------

所有人都听到了 write("A")；f、g1、g2 处理了 write("B")，g3 错过了；然后 read()，客户端等 3 个一致的回复：f 和 g3 回复 "A"，g1 和 g2 回复 "B"。客户端不知道该信哪个（都不到 2f+1），但保证能看出有问题。所以客户端能检测到有好节点错过了一个操作，稍后会看到怎样修复。

课件的总结：单客户端协议不能容忍 N/3 及以上的故障（即 N >= 3f+1）。多数派（quorum）：任何 |Q| >= 2f+1 的集合 Q。安全性：每个 Q 都有诚实的多数（因此是唯一的）。活性：|Q| <= N - f（不依赖出故障的副本）。（受 Baudet、Danezis、Sonnino 2020 启发。）FAQ：如果超过 1/3 的节点是恶意的，就不可能有协议，论文第 3 页第二段有一个 3f+1 是所需最少副本数的简短证明；使用 PBFT 类协议的开放账本系统有类似的界限（比如 Algorand 继承了 PBFT 的界限）；愿意接受 fork 一致性的话可以做得更好，见 NSDI 2007 的 Beyond One-third Faulty Replicas。

四、多个客户端：加一个主

多个客户端呢？非故障副本必须以同样的顺序处理操作！让一个主（primary）为并发的客户端请求选顺序。但我们要担心主出故障。

故障主能做什么？

  1. 忽略客户端的操作；
  2. 给不同副本不同的操作；
  3. 给客户端发错误的结果。

应对故障主的总体方法：

  1. 客户端除了通知主，也把每个操作通知各副本；
  2. 副本之间交换主发来的操作的信息；
  3. 副本直接把结果发给客户端；
  4. 每个副本盯着每个操作的进展，没有进展就强制换主。

副本第一次从主那里收到一个操作就能执行它吗？不能：也许主给不同副本发了不同的操作，没确定就执行，会毁了副本的状态。需要第二轮消息，确保所有好副本拿到的是同一个操作。

设计 4（带主）

  • 3f+1 台服务器，一台是主，f 台出故障，主也可能出故障；
  • 客户端把请求发给主，也发给每个副本；
  • 主选定下一个操作和操作编号，发 PRE-PREPARE(op, n) 给各副本；
  • 每个副本发 PREPARE(op, n) 给所有副本；
  • 如果副本从 2f+1 个副本（包括自己）收到一致的 PREPARE(op, n)，并且 n 是下一个操作编号，就执行这个操作（可能修改状态），给客户端发回复；否则继续等；
  • 客户端收到 f+1 个一致的回复就满意了。
op                                                       f+1 matching replies
C ------------------------------------------------------------------------
                                                    ^      ^
    \ pre-P (op,n)   PREPARE   2f+1 matching -> reply /      /
p ------------------------------------------------------------------------
     \       \   ^ ^   \  ^ ^   / \                   /
g1 -----------------------------------------------------------------------
       \       \ / /    \ / /   \  /
g2 -----------------------------------------------------------------------
        \       \/       \/      \/
g3 -----------------------------------------------------------------------

记住我们的策略：主遵守协议，就有进展；没有进展，副本就检测到并强制换主。

如果主没出故障，出故障的副本能阻止正确的进展吗

  • 它们不能伪造主的消息；
  • 它们能延迟消息，但不能永远延迟；
  • 它们可以什么都不做：但凑齐 2f+1 个一致的 PREPARE 并不需要它们；
  • 它们可以发正确的 PREPARE，同时对 f 个好副本做 DoS，让它们听不到操作；但那些副本最终会从主那里听到。

最坏的结果：延迟。

如果主出故障，副本能检测到问题吗，还是主能造成检测不到的问题

主不能伪造客户端的操作，它们是签名的；不能忽略客户端的操作，客户端会发给所有副本；它可以试着以不同顺序发给不同副本，或者试图骗副本以为一个操作已被处理、其实没有。副本能检测到这种攻击吗？主给不同副本发不同操作的后果：

  • 情形 1：所有好节点都收到 2f+1 个一致的 PREPARE。它们拿到的是同一个操作吗？是：任何收到 2f+1 个一致 PREPARE 的节点拿到的必定是同一个操作，因为任意两个 2f+1 的集合至少共享一个好服务器。结果：所有好节点都执行这个操作，客户端满意。
  • 情形 2：>= f+1 个好节点收到 2f+1 个一致的 PREPARE。同样不可能有分歧。结果：f+1 个好节点执行这个操作，客户端满意。但最多 f 个好节点没执行，它们能被用来实际上回滚这个操作吗？比如把 write("B") 发给 f+1 个，把 read() 发给剩下的 f 个？不能：凑不出 2f+1 个持有旧状态的副本，所以 PREPARE 不够。
  • 情形 3：< f+1 个好节点收到 2f+1 个一致的 PREPARE。结果：客户端永远收不到回复；系统会停下，因为 f+1 个副本卡在等这个操作。

五、视图变更

故障主之后怎样恢复运行？需要一次视图变更（view change）来选新主（这里的视图变更只选主，没有"活着的服务器集合"这种概念）。

  • 副本什么时候请求视图变更？如果它看到了一个客户端操作，但在一段超时时间内没看到 2f+1 个一致的 PREPARE。
  • 只要一个副本请求就触发视图变更可以吗？不行：出故障的副本可能不断引发视图变更。需要多少副本请求，先放一放。
  • 下一个主是谁？要确保出故障的副本不能总把自己变成下一个主。视图号 v，主是 v mod n，所以主在服务器之间轮换，最多连续 f 个故障主。课件称之为"任期限制"：轮换的主；超时，视图变更也必须是所有对所有的（超时指数增长）。课件还指出：和 Raft 一样，需要视图足够新的主（NULL 相当于视图 0）；和 Raft 不同（为了活性），不能随便选任何一个有资格的候选人。FAQ：视图变更像 Raft 换领导者，但没有选举，下一个视图的主是预先确定的。

视图变更设计 1（不正确）

  • 副本把 VIEW-CHANGE 请求发给新主；
  • 新主等足够多的视图变更请求；
  • 新主用 NEW-VIEW 宣布视图变更，里面包含那些 VIEW-CHANGE 请求，作为足够多副本想换视图的证据；
  • 新主从它看到的最后一个 n 加 1 开始给操作编号。

所有非故障副本会对跨视图变更的操作编号达成一致吗？问题：我看到了操作 n 的 2f+1 个 PREPARE，于是执行了它；新主没看到，没执行；所以新主可能从 n 开始编号，产生两个不同的第 n 号操作。新主能不能问所有副本它们执行过哪些操作？不行：新主只能等 2f+1 个回复，出故障的副本可能回复了，所以新主可能不等我。

解法：第三阶段 COMMIT

在确定新主会听说一个操作之前，不执行它。加第三个阶段：PRE-PREPARE、PREPARE，然后 COMMIT，只在提交后执行。 

operation protocol:
  client sends op to primary
  primary sends PRE-PREPARE(op, n) to all
  all send PREPARE(op, n) to all
  after a replica receives 2f+1 matching PREPARE(op, n):
    send COMMIT(op, n) to all
  after receiving 2f+1 matching COMMIT(op, n):
    execute op

view change:
  each replica sends the new primary 2f+1 PREPAREs for recent ops
  new primary waits for 2f+1 VIEW-CHANGE requests
    new primary fixes up the log based on info in the view-change requests
  new primary sends NEW-VIEW msg to all replicas with
    complete set of VIEW-CHANGE msgs
    list of every op for which some VIEW-CHANGE contained 2f+1 PREPAREs
      if an op doesn't have 2f+1 PREPAREs, make it a no-op
    i.e. list of final ops from the last view

课件的说法：故障主对设计提出要求，加一个新的所有对所有的 prepare 轮；恢复消息必须有凭据，即"签名装订"（把签名的证据附在消息里）；提交也是所有对所有的。

如果一个副本执行了一个操作，新主一定会知道吗

副本只在收到 2f+1 个 COMMIT 后才执行。也许其中 f 个是谎言，来自出故障的副本，它们不会告诉新主；但有 f+1 个 COMMIT 来自收到了 2f+1 个一致 PREPARE 的副本。新主等 2f+1 个副本的视图变更请求，可以不管那 f 个故障节点；f+1 个发了 COMMIT，f+1 个发了 VIEW-CHANGE，在 3f+1 台里必然重叠。新主能省略某些报上来的近期操作吗？不能，NEW-VIEW 必须包含签名的 VIEW-CHANGE 消息，别人能检查。

FAQ：同一个请求怎么会在两个不同视图里以同一个序号提交？新主可能不知道上一个视图里提交过的某条消息（它错过了），但正常操作协议保证新主会在视图变更时得知，因为 2f+1 个好副本在上一个视图里承诺了它；新主从最近的稳定检查点开始修补日志，为消息插入稳定性的证明，然后切换到新视图。为什么有些序号会在视图变更中变成空请求？新主在修补日志时决定上一个视图里所有序号的结果，如果某个序号在上一个视图里没有足够多的 prepare，就把它变成空请求。序号永远不会跳过吗？FAQ 作者认为是这样，只是视图变更时有些序号会变成空操作。副本可能先收到 prepare、后收到 pre-prepare 吗？可能（乱序或丢包），它会注意到还没看到这个序号的 pre-prepare，FAQ 作者不知道协议具体怎么做，多半是等 pre-prepare，因为它包含日志条目本身，prepare 只包含条目的摘要（digest，即对消息做的抗碰撞密码学哈希，比如 SHA256）。

六、从单个操作到完整的复制状态机

课件：

  • （和 Raft 一样）主把很多客户端请求流水线化；
  • 低水位线和高水位线防止序号耗尽；
  • 每个视图是一个新的"日志"；
  • 检查点允许日志压缩（参见 Raft）；
  • 提交也是所有对所有的；
  • 客户端收到 f+1 个回复，这就够了：其中至少有一个诚实副本。

论文还讨论了：帮助好节点恢复的检查点和日志；各种密码学优化；减少常见情况下消息数的优化；快速的只读操作。课件列的优化：值的哈希（参见比特币）；试探性的回复；只读操作；用 MAC 代替签名；网络 NACK。

FAQ：PBFT 怎样为 MAC 做密钥管理？每个客户端和每个副本共享一个秘密会话密钥，另有一些协议机制让副本能验证其他副本的 2f+1 个响应的真实性，这利用了主的存在，细节在博士论文第 3 章。消息数似乎是 O(n²)，有没有文献证明处理拜占庭故障需要 O(n²) 条消息？BFT 文献很多，FAQ 作者知道的最高效之一是 Zyzzyva，它推测每个节点都诚实，这时只发 2n 条消息；消息数只是一个因素，往往不是最重要的，很多协议并行发消息或用多播，其他指标有关键路径上的服务器数、每秒消息数（可以用批处理提高，代价是延迟）等。丢失或乱序的消息怎么办？消息里有足够的信息让接收者发现自己漏了消息或消息乱序（见 6.1 节第 4 段）。

七、讨论和 FAQ

讲义留了几个问题：

  • 如果出故障的服务器超过 f 台会怎样？系统能恢复吗？
  • 如果客户端是恶意的呢？
  • 假设攻击者能攻破其中一台服务器（利用一个 bug、偷到密码、能物理接触等），为什么它不能把所有服务器都攻破？（因为设计要求各副本没有相同的漏洞，见下面 N 版本编程。）

FAQ 选摘

  • 今天有系统在用 BFT 协议吗？在论文针对的场景里，开发者倾向于预防和检测被攻破的节点，而不是运行一个能处理被攻破节点的类 BFT 协议（那很贵）。在没有中心权威来清理坏节点的开放系统（比如公共账本）里，BFT 协议回来了。FAQ 作者猜 Google 等公司也是靠预防和检测。
  • 能用 BFT 实现一个成员固定的"许可制"比特币吗？有一个有趣的联系：比特币解决了有恶意节点的共识问题，但可能有很长的分叉，可以看看基于或受 PBFT 启发的账本系统 Stellar 和 Hyperledger。
  • 拜占庭容错严格比解决网络分区更难吗？论文处理的问题和 Raft 相同（包括处理网络分区），只是存在恶意副本，所以 PBFT 解决的问题更难。
  • 为什么在不依赖同步来保证安全性时，却要依赖同步来保证活性？有一个不可能性结果：在异步分布式系统里（消息延迟没有上界），只要有一个故障节点，就不能在有限时间内达成共识，这叫 FLP 结果。PBFT 的作者只是指出他们没有绕过这个结果，而是假设一种弱同步（delay(t) 不会无限期地比 t 增长得更快）。
  • BFT 是强领导者设计吗？和 Raft 一样，每个视图有指定的领导者决定消息顺序；领导者失败或不守协议就换视图和领导者。FAQ 作者知道的高性能后续工作都有指定的领导者，比如 Zyzzyva。
  • 出故障的节点集合是固定的吗？f 怎么定？论文描述的系统在整个生命周期里最多只能有 f 个坏节点。这是 PBFT 的阿喀琉斯之踵。博士论文和后续工作加了主动恢复（proactive recovery），只要在一个小的脆弱窗口内少于 1/3 的副本出故障，就能在整个生命周期内容忍任意多次故障。
  • 每个节点都要运行不同的服务实现才能独立地出故障，这现实吗？确实棘手，不同副本不能有相同的 bug，所以实现必须不同。论文提到 N 版本编程；作者后来的 BASE 用抽象来提高屏蔽软件错误的能力、复用现成的服务实现：它用正确副本存储的状态的一个抽象视图定期修复每个副本，每个副本可以运行不同的或非确定性的实现，降低共模故障的概率。
  • 副本怎样确定性地判断一个值是否正确？一般情况要在协议里加一个阶段，收集 2f+1 个值，用确定性的计算得出要用的值（比如取中位数）。作者指出常见情况可以避免这个额外阶段，因为副本能检查值是否正确，比如时间戳可以由主选，副本检查它是否在自己本地时钟附近的一个窗口内。
  • 读了 Mickens 的 "The Saddest Moment"，BFT 的实际应用是什么？似乎要么环境受控、BFT 没必要，要么环境不受控、BFT 无法处理。FAQ 作者也不知道是什么，读它一是因为这是一个令人印象深刻的结果，二是它很可能会回来，比如比特币解决的是类似的问题却有长分叉，也许将来会有结合 BFT 和比特币思想的系统。

课件的结语

  • PBFT：安全的复制状态机；
  • 为了冗余，对冗余状态做冗余复制；
  • 永远不丢失提交的证据；
  • 密码学限制攻击者的影响（在一些假设下！）；
  • 设计限制任何单个节点的影响，这对稳健的系统是个好想法，不管是不是数字系统。

课前问题

假设我们从 Practical BFT 协议里去掉 pre-prepare 阶段：主直接把 PREPARE,v,n,m 消息多播给各副本，副本像以前一样多播 COMMIT 并回复客户端。会出什么问题？给一个简短的例子，比如"主发送 foo，副本 1 和 2 回复 bar……"。（可以对照第四、五节里每一轮消息各自的作用来想：哪一轮让好副本确认彼此拿到的是同一个 (n, m)，哪一轮保证视图变更后新主一定能知道已执行的操作。）
