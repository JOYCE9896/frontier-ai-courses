主讲：Robert Morris（2026 年春季讲义；录像为 2020 年春季）
资料来源：2026 讲义、2020 课堂录像、论文 MapReduce（OSDI 2004）

一、什么是分布式系统

讲义的定义很短：一组相互协作、共同提供某种服务的计算机。例子有热门应用的后端（比如消息服务）、大型网站、云服务商。这门课关注的是分布式基础设施：存储、事务系统、"大数据"处理框架。

Morris 在录像开头先提醒：如果一个问题能在一台计算机上解决，就在一台上解决。很多工作一台机器就能做完，而且总是更简单。建分布式系统之前，应该先把别的办法都试过，因为分布式系统不会更简单。

为什么要建

  • 用并行处理提高容量：很多 CPU、很多内存、很多磁盘一起工作。
  • 用复制容忍故障：两台机器做同样的事，一台坏了换另一台。
  • 匹配物理设备的分布：比如传感器；录像里的例子是银行间转账，A 银行的计算机在纽约，B 银行的在伦敦，它们天然就要通信协作。
  • 用隔离提高安全性：不信任的代码，或者可能有恶意、可能有 bug 的对方，放在另一台计算机上，双方只通过一个定义得很窄的网络协议交互。

这门课大部分时间讲性能和容错，后两者在案例里常常作为限制条件出现。

为什么难

  • 并发：很多部分同时执行，有并行编程的所有问题：复杂的交互、奇怪的时序依赖。
  • 复杂的交互。
  • 性能瓶颈：建分布式系统常常是为了拿到一千台机器的性能，但用一千台机器真的得到一千倍的加速很难，路上有很多障碍，要仔细设计。
  • 部分故障：一台计算机通常要么在工作要么坏了。很多台计算机加一个网络，就会出现一部分坏了、其他还在工作；或者计算机都好着，但网络某一段坏了或者不可靠。

为什么上这门课

有意思：问题难，解法强大。需求大：大网站的兴起推动了它。Morris 说他刚开始教这门课时，分布式系统多少是学术上的好奇，大家觉得小规模用一用、也许将来重要；过去二十年随着巨型网站、海量数据和整栋楼的计算机出现，它成了计算基础设施里极重要的一部分。研究活跃：还有很多重要问题没解决。有挑战：实验。

三、主要主题

这是一门关于基础设施的课：存储、通信、计算。Morris 说存储讲得最多，因为它是一个清楚、有用、通常容易理解的抽象；通信主要作为构建分布式系统的工具，网络本身是另一门课（6.829）的内容。一个大目标：把分布的复杂性对应用隐藏起来。梦想是给应用一个看起来像非分布式系统（比如普通文件系统）的接口，背后是巨大、高效、容错的分布式实现。Morris 说这个梦想很少完全实现，大家在这方面越做越好，课上会学这些方法。

实现

RPC、线程、并发控制。RPC 的目的是隐藏"我们在不可靠的网络上通信"这一事实；线程既能用上多核，更重要的是能让程序员更简单地组织并发操作；用了线程就要花时间想并发控制，比如锁。这些在很多论文里都会碰到，而完整地碰到它们是在实验里。

性能

一个常见目标：可扩展的吞吐量。N 倍的服务器通过并行的 CPU、内存、磁盘、网络得到 N 倍的总吞吐。这很有吸引力，因为计算机用钱就能买到；另一条路是付钱让程序员重写软件、换更好的算法，那贵得多。但 N 越大越难扩展，比如负载不均。

Morris 的例子：一个网站，用户的浏览器访问运行 Python 或 PHP 的 web 服务器，web 服务器访问一个数据库。一两个用户时一台机器就够；突然有一亿人注册，就多买 web 服务器，把用户分到不同服务器上。如果像 Reddit 那样所有用户要看同样的数据，所有 web 服务器最终访问同一个数据库，web 服务器可以加很久。但到了 10 台、20 台、100 台 web 服务器时，数据库成了瓶颈，再加 web 服务器也没用。这时几乎一定要做设计工作，把一个数据库里的数据重新分到多个数据库，这很费劲，但很多人不得不做。课上会看到很多例子，分布式系统就是一个存储系统，起因是作者经营的大网站把单个数据库或存储服务器用到了头。

容错

成千上万台服务器加一个大网络，故障就成了常态。Morris 说他办公室里有服务器连续运行多年没出问题，单台计算机相当可靠；但即使每台机器平均一年坏一次，一千台机器每天就要坏大约三台。规模把罕见的故障变成了持续不断的麻烦：总有一台机器坏了、莫名其妙地慢或者出错，总有一根被人踩过的网线、一根松了的网线、一台风扇坏了过热宕机的交换机。所以应对故障必须设计进系统里，我们希望把这些故障对应用隐藏起来。

  • 高可用（availability）：在某些类型的故障下（不是所有故障），服务继续运行。比如两份副本的服务，坏一台另一台继续，两台都坏就无法保证。
  • 可恢复（recoverability）：出问题时服务可能停下来，等人修好，修好后能像什么都没发生一样继续正确运行。这比可用性弱，但也是重要的要求，通常要把数据存到磁盘上，来电后能恢复。好的可用系统通常也是可恢复的：故障太多时停止响应，修好足够多的部件后继续正确运行。

两件最重要的工具：

  • 非易失存储：硬盘、闪存、SSD，存检查点或者状态日志，断电恢复后从磁盘读出最后的状态继续。难点是写非易失存储很慢（以前要移动磁头、等盘片转过来，对 3 GHz 的处理器来说慢得痛苦；闪存好很多，但仍要仔细设计），所以高性能容错系统的很多巧妙之处在于避免频繁写盘。
  • 复制：一台服务器崩溃，可以用其他的继续。复制系统里永远潜伏着同一个关键问题：两份本该相同的副本不小心不同步了，不再是副本。Lab 2 到 Lab 4 都在处理这件事。

一致性

通用的基础设施需要有明确定义的行为，例如"read(x) 返回最近一次 write(x) 的值"。保证规定好的行为很难，比如很难让"副本"服务器保持一样。

Morris 的例子：一个只支持 put(key, value) 和 get(key) 的键值服务，两台副本服务器上键 1 的值都是 20。一个客户端要把它改成 21，给第一台发了 put，正要给第二台发时崩溃了（断电或者操作系统出错）。现在一台是 21，一台还是 20。之后有人 get 键 1，会得到 21 还是 20，取决于问的是哪台。即使规则是"先问上面那台，它坏了再问下面那台"，迟早也可能在某次 get 里读到过时的数据，甚至一周后突然读到一周前的值。

  • 强一致：一次读返回最近一次成功写入的值（细节很多要推敲）。
  • 弱一致：不保证读到最近写入的值，可能在不确定的时间里一直看到旧值。人们对它感兴趣，是因为强一致要大量通信，代价很高。最简单的强一致做法是读者读所有副本、取最新的值，但为了读一个值聊这么多太贵了。

通信的代价还被容错放大了：为了让副本的故障尽量独立（不相关），人们希望把副本放远。两份副本放在同一个机房同一个机柜里是坏主意，有人碰掉那个机柜的电源线，两份数据一起没了；所以放到不同城市，甚至大陆两端，一场地震毁掉一个数据中心，不太可能也毁掉另一个。但光速决定了和大陆另一端通信要几毫秒到几十毫秒，对每秒执行约十亿条指令的机器来说，每次读写等 10 到 30 毫秒代价巨大。所以人们常常建弱得多的系统，只更新或只访问最近的副本，并且在弱一致之上加一些语义，让它对应用更有用。

取舍

容错、一致性和性能互相为敌。容错和一致性都需要通信（把数据发给备份服务器；检查缓存的数据是不是最新），而通信常常慢且难以扩展。很多设计牺牲一致性来换速度，read(x) 可能读不到最新的 write(x)，这让应用程序员（或者用户）很痛苦。课上会看到很多一致性和性能之间的设计点。

四、案例：MapReduce

MapReduce 是 6.5840 各个主题的好例子，影响巨大，也是 Lab 1 的内容。

背景

Google 要在几个 TB 的数据集上做几个小时的计算：建搜索索引、排序、分析网页的链接结构（找出最重要、最权威的网页）。录像里 Morris 说当时整个 web 就有几十 TB，给 web 建索引基本上等价于排序，在一台计算机上可能要几周、几个月甚至几年，只有用几千台计算机才现实。在 MapReduce 之前，Google 的工程师每遇到一个问题就手写一次性的分布式程序：怎样把工作分到很多机器上、怎样组织计算、怎样把数据取回来、怎样应对故障。如果只雇分布式专家也许还行，但那也浪费工程师的精力，而且 Google 想雇擅长别的事情的人。

一个大目标：让非专家程序员也能轻松使用。程序员只定义 Map 和 Reduce 两个函数，通常是简单的串行代码；MR 管理并隐藏分布的所有方面。MR 是一个框架或库，"应用"就是 Map() 和 Reduce()。

抽象视图：词频统计

Input1 -> Map -> a,1 b,1
Input2 -> Map ->     b,1
Input3 -> Map -> a,1     c,1
                  |   |   |
                  |   |   -> Reduce -> c,1
                  |   -----> Reduce -> b,2
                  ---------> Reduce -> a,2
  1. 输入（已经）被分成 M 份。
  2. MR 对每一份输入调用 Map()，产生一个 k,v 对的列表，叫"中间"数据。每次 Map() 调用是一个"任务"（task），整个计算叫一个"作业"（job）。
  3. 所有 Map 结束后，MR 把每个 k 的所有中间 v 收集到一起，把每个键和它的值交给一次 Reduce 调用。
  4. 最终输出是所有 Reduce() 产生的 <k,v> 对的集合。
Map(d)
  chop d into words
  for each word w
    emit(w, "1")

Reduce(k, v[])
  emit(len(v[]))

Map 的参数实际上是文件名（通常忽略）和文件内容。emit 是框架提供的函数。Map 函数完全不知道分布、不知道有多少台计算机、不知道数据要过网络；Reduce 也只是数一数传进来多少个值，不用知道容错。

它扩展得好，也隐藏了很多复杂性

N 台"worker"计算机（可能）带来 N 倍吞吐：Map() 之间不交互，可以并行；Reduce() 也一样。更多计算机就有更多吞吐。MapReduce 隐藏了：把 map 和 reduce 的代码发到服务器上；跟踪哪些任务完成了；把中间数据从 Map "洗牌"（shuffle）到 Reduce；在服务器之间平衡负载；从崩溃的服务器恢复。

代价是对应用的限制：只有一种模式（Map -> shuffle -> Reduce）；除了中间输出，没有交互和状态；只能批处理，不能实时或流式处理。

录像里有同学问能不能把 reduce 的输出再交给下一轮。Morris 说实际中很常见：复杂的多步分析或者 PageRank 这样逐步收敛的迭代算法，要跑很多轮 MapReduce 作业，每轮的输出是下一轮的输入，写 reduce 时要让输出格式适合下一轮。这也暴露了 MapReduce 的一个小缺点：算法能表达成 map、按键排序、reduce 时它很好，但很多人想跑长得多、包含很多种处理的流水线，用 MapReduce 只能拼成好几个作业；后面课上会讲更先进的系统（Spark），能描述整条计算流水线并自己做优化。另一位同学问为什么 reduce 不做成流式的，不用等所有 map 完成：Morris 说可以想象那样的定义，但它的首要目标是让不懂系统的人好写程序；很多取代 MapReduce 的现代系统确实处理数据流，而 MapReduce 是批处理，要先有有限的输入。

一些细节（论文图 1）

实际系统里有一大批服务器，叫 worker，还有一个协调整个计算的主节点（论文叫 master，讲义叫 Coordinator）。

  • 输入和输出存在 GFS 集群文件系统上。MR 需要巨大的并行输入输出吞吐。GFS 把文件按 64 MB 的块分到很多服务器、很多磁盘上，Map 并行读，Reduce 并行写；GFS 把数据复制到 2 或 3 台服务器上来容错。GFS 对 MapReduce 是一大利好：如果把十 TB 爬下来的网页写进 GFS，哪怕写成一个大文件，它也自动切成 64 MB 的块均匀地分到所有服务器上，一千个 map worker 就能从一千台 GFS 服务器并行读，拿到一千台服务器的总读带宽。
  • MR 把 Map() 的输出写到本地磁盘。按 hash(key) mod R 分成 R 个文件，每个"哈希桶"包含多个键，所有 map worker 用同样的方式哈希。
  • shuffle：每个 Reduce 任务处理一个哈希桶。MR 从每个 Map worker 取来这个 Reduce 任务的桶，合并、按键排序，对每个键调用 Reduce()。每个 Reduce 任务在 GFS 上写一个单独的输出文件。Morris 把 shuffle 描述成一次"行转列"：数据原来按行存在执行 map 的机器上，需要按列存到负责 reduce 的机器上，每一份数据都要从产生它的 map 穿过网络到需要它的 reduce。
  • Coordinator 管理作业的所有步骤：跟踪每个任务的状态，把任务分给 worker 机器。

什么会限制性能

要关心这个，因为限制在哪里，就该优化哪里。CPU？内存？磁盘？网络？2004 年作者受限于网络速度。MR 通过网络发送：Map 从 GFS 读输入；Reduce 取 Map 的中间输出，常常和输入一样大，比如排序；Reduce 把输出文件写到 GFS（GFS 要存两三份副本，所以至少有一份要过网络）。

论文的网络有多快？第 5.1 节：1800 台机器，两级交换网络（一个根交换机，第二层若干交换机，下面是机器）。每台交换机大约 42 个端口（1800 的平方根）。MR 的 shuffle 要求每个 worker 从其他每个 worker 取数据，只有 1/42 的数据留在本地交换机里，所以 shuffle 的大部分数据都穿过根交换机。论文的根交换机总带宽 100 到 200 Gbit/s，分给 1800 台机器，约每台 55 Mbit/s。55 很小，比磁盘或内存的速度都低。

MR 怎样减少网络使用

  • Coordinator 尽量把每个 Map 任务放在存有它输入的 GFS 服务器上运行。所有计算机同时运行 GFS 和 MR worker，所以 Map 的输入通常从本地磁盘的 GFS 数据读，不过网络。（会因为崩溃、负载等原因做不到，但几乎所有 map 都在存有数据的机器上执行。）
  • 中间数据只过一次网络：Map worker 写本地磁盘，Reduce worker 通过网络从 Map worker 的磁盘读。（如果存到 GFS 里，至少要过两次网络。）

录像里 Morris 补充：如今数据中心网络的核心带宽高得多，常见的结构有多个根交换机，每个机柜交换机连到每个根交换机，流量分摊在它们之间。后来 MapReduce 不再费力把 map 放到数据所在的机器上，因为大家认为网络已经很快了。

MR 怎样获得好的负载均衡

为什么在乎：如果一台服务器的活比别人多，或者它更慢，其他服务器到最后就会闲着等它，白白浪费。理想情况是 MR 分配工作，让所有 worker 同时结束。但任务大小不一，计算机快慢也不一。解法：任务数比 worker 机器多得多。Coordinator 把新任务交给做完上一个任务的 worker，快的服务器做更多任务，慢的服务器少分一些，减小它对总时间的影响。

容错

如果一台 worker 计算机崩溃了怎么办？我们希望 MR 框架隐藏故障。MR 要从头重跑整个作业吗？不用，Coordinator 只重跑失败的 Map() 和 Reduce()。

假设 MR 把一个 Map 任务跑了两次，一个 Reduce 看到第一次的输出，另一个 Reduce 看到第二次的输出？两次 Map 执行最好产生完全相同的中间输出！所以 Map 和 Reduce 应该是纯粹的确定性函数：只允许看自己的参数和输入；没有状态、没有文件 I/O、没有交互、没有外部通信、没有随机数。保证确定性是程序员的责任。

其他故障和问题：

  • 如果 Coordinator 把同一个 Map() 任务交给了两个 worker？也许它误以为一个 worker 死了。它只会把其中一个告诉 Reduce worker。
  • 如果把同一个 Reduce() 任务交给了两个 worker？它们都会试着在 GFS 上写同一个输出文件！GFS 的原子重命名防止内容混在一起，最终可见的是一个完整的文件。
  • 如果某个 worker 特别慢，是个"拖后腿的"（straggler）？也许是硬件不稳定。Coordinator 为最后几个任务启动第二份副本。
  • 如果某个 worker 因为硬件或软件坏了，算出错误的输出？那就没办法了！MR 假设 CPU 和软件是"故障即停"（fail-stop）的。
  • 如果 Coordinator 崩溃了？（讲义留作问题。论文里的做法是整个作业失败，由用户重新提交。）

性能：论文图 2

横轴是时间，纵轴是一个"grep"类作业读取输入的总速率。输入是 1 TB（1000 GB），1764 个 worker。峰值 30000 MB/s（30 GB/s），很大。为什么能到 30000 MB/s？每台 worker 机器 17 MB/s，即 140 Mbit/s，比我们估算的 55 Mbit/s 网络带宽还多；所以输入多半是直接从两块本地 GFS 磁盘读的，每块磁盘大约每秒读 9 MB。讲义还留了两个思考题：为什么主要的活动期大约 30 秒？为什么吞吐要用 50 秒才达到最大？

现状

影响巨大（Hadoop、Spark、Lab 1 等等）。在 Google 内部可能已经不用了，被 Flume / FlumeJava 取代（见 Chambers 等人的论文）；GFS 被 Colossus（没有很好的公开描述）和 BigTable 取代。
