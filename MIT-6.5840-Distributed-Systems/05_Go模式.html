第五讲：Go 并发的模式与提示（客座讲座）

Go 项目负责人之一 Russ Cox 的讲座：并发不是并行；序章：用 goroutine 保存状态，把数据状态变成代码状态，引号字符串解析器的逐步改写；调试 goroutine：Ctrl-\ 和 /debug/pprof/goroutine；模式一：发布/订阅服务器，从互斥锁版本到 goroutine 加 select 的版本，慢订阅者和带队列的辅助 goroutine；模式二：工作调度器的七次改写，关闭 channel 表示不再发送，重试失败任务时的死锁；模式三：复制服务的客户端，超时和偏好的服务器；模式四：协议多路复用器；全部提示汇总

主讲：Russ Cox（Google，Go 项目负责人之一）；本讲没有公开录像，内容根据他的课件整理
资料来源：课件 Patterns and Hints for Concurrency in Go、FAQ、阅读材料 The Go Programming Language and Environment（CACM 2022）

一、并发不是并行

  • 并发（concurrency）：把各自独立执行的过程组合起来。
  • 并行（parallelism）：同时执行（可能相关的）计算。

并发是关于同时应对很多事情；并行是关于同时做很多事情。这场讲座讲的是前者：怎样用 goroutine、channel 和互斥锁把程序组织清楚。

二、序章：用 goroutine 保存状态

例子：判断输入是不是一个带引号的字符串，即匹配正则表达式 /"([^"\\]|\\.)*"/：以双引号开始，中间是除引号和反斜杠以外的字符，或者反斜杠加任意一个字符（转义），以双引号结束。

状态机写法

state := 0
for {
    c := read()
    switch state {
    case 0:
        if c != '"' {
            return false
        }
        state = 1
    case 1:
        if c == '"' {
            return true
        }
        if c == '\\' {
            state = 2
        } else {
            state = 1
        }
    case 2:
        state = 1
    }
}

课件一步步改写它：先把 read() 挪进每个 case；再把 switch 换成 goto 标签（state0、state1、state2）；state0 只走一次，可以去掉跳转；state2 只是读一个字符再回到 state1，可以内联；两个分支都 goto state1，可以合并；最后 goto 变成循环： 

func parse(read func() rune) bool {
    if read() != '"' {
        return false
    }
    var c rune
    for c != '"' {
        c = read()
        if c == '\\' {
            read()
        }
    }
    return true
}

原来的 state==0、1、2 分别对应程序里的不同位置：第一次 read 之前、循环里、读完反斜杠之后。也可以写一个带 inEscape 布尔变量的版本（inEscape==false 对应状态 1，true 对应状态 2），但不如上面清楚。

提示：在能让程序更清楚时，把数据状态变成代码状态。

当调用方要一个字符一个字符地喂数据时

如果接口必须是"每来一个字符调用一次 Write(c)，返回需要更多输入 / 成功 / 输入错误"，就只能回到状态机： 

type quoter struct {
    state int
}

func (q *quoter) Init() {
    q.state = 0
}

func (q *quoter) Write(c rune) Status {
    switch q.state {
    case 0:
        if c != '"' {
            return BadInput
        }
        q.state = 1
    case 1:
        if c == '"' {
            return Success
        }
        if c == '\\' {
            q.state = 2
        } else {
            q.state = 1
        }
    case 2:
        q.state = 1
    }
    return NeedMoreInput
}

（课件 Init 里写成了 r.state，是笔误。）另一种办法：开一个 goroutine 运行清楚的 parse，用两个 channel 在 Write 和它之间来回传字符和状态：

type quoter struct {
    char   chan rune
    status chan Status
}

func (q *quoter) Init() {
    q.char = make(chan rune)
    q.status = make(chan Status)
    go q.parse()
    <-q.status // always NeedMoreInput
}

func (q *quoter) Write(c rune) Status {
    q.char <- c
    return <-q.status
}

func (q *quoter) parse() {
    if q.read() != '"' {
        q.status <- SyntaxError
        return
    }
    var c rune
    for c != '"' {
        c = q.read()
        if c == '\\' {
            q.read()
        }
    }
    q.status <- Done
}

func (q *quoter) read() rune {
    q.status <- NeedMoreInput
    return <-q.char
}

parse 还是那段顺序代码，"现在走到哪一步"保存在这个 goroutine 的程序计数器和栈里，不需要 state 变量。（课件里 parse 的接收者写成了 quoteReader、read 的返回类型写成了 int，这里按上下文改成了一致的写法。）

提示：用额外的 goroutine 保存额外的代码状态。

知道每个 goroutine 为什么、什么时候退出

package main

import (
    "net/http"
    _ "net/http/pprof"
)

var c = make(chan int)

func main() {
    for i := range 100 {
        go f(0x10*i)
    }
    http.ListenAndServe("localhost:8080", nil)
}

func f(x int) { g(x+1) }
func g(x int) { h(x+1) }
func h(x int) {
    c <- 1
    f(x+1)
}

这 100 个 goroutine 都卡在 h 里向一个没人接收的 channel 发送，永远不会退出，这就是 goroutine 泄漏。上面 parse 的例子里，如果调用方喂到一半就不喂了，那个 goroutine 也会一直等着。

提示：知道每个 goroutine 为什么、什么时候退出。

怎样找出它们卡在哪：在终端里按 Ctrl-\（发送 SIGQUIT），程序退出并打印所有 goroutine 的栈，例如 "goroutine 18 [chan send]: main.h(0x12) ... main.g(0x11) ... main.f(0x10) ... created by main.main"。程序还在跑时，导入 net/http/pprof 后访问 HTTP 服务器的 /debug/pprof/goroutine，能看到按栈归类的所有活着的 goroutine，例如 "goroutine profile: total 106"，其中 "100 @ ..." 都卡在 main.h。

提示：按 Ctrl-\ 杀掉程序并转储所有 goroutine 的栈。用 HTTP 服务器的 /debug/pprof/goroutine 查看活着的 goroutine 的栈。

三、模式一：发布/订阅服务器

type PubSub interface {
    // Publish publishes the event e to
    // all current subscriptions.
    Publish(e Event)

    // Subscribe registers c to receive future events.
    // All subscribers receive events in the same order,
    // and that order respects program order:
    // if Publish(e1) happens before Publish(e2),
    // subscribers receive e1 before e2.
    Subscribe(c chan<- Event)

    // Cancel cancels the prior subscription of channel c.
    // After any pending already-published events
    // have been sent on c, the server will signal that the
    // subscription is cancelled by closing c.
    Cancel(c chan<- Event)
}

互斥锁版本

type Server struct {
    mu  sync.Mutex
    sub map[chan<- Event]bool
}

func (s *Server) Init() {
    s.sub = make(map[chan<- Event]bool)
}

func (s *Server) Publish(e Event) {
    s.mu.Lock()
    defer s.mu.Unlock()
    for c := range s.sub {
        c <- e
    }
}

func (s *Server) Subscribe(c chan<- Event) {
    s.mu.Lock()
    defer s.mu.Unlock()
    if s.sub[c] {
        panic("pubsub: already subscribed")
    }
    s.sub[c] = true
}

func (s *Server) Cancel(c chan<- Event) {
    s.mu.Lock()
    defer s.mu.Unlock()
    if !s.sub[c] {
        panic("pubsub: not subscribed")
    }
    close(c)
    delete(s.sub, c)
}

慢的 goroutine 怎么办

Publish 在锁里依次往每个订阅者的 channel 发送，一个订阅者接收得慢，所有人都被拖住。选项：

  • 减慢事件的产生（上面的代码就是这样，Publish 会阻塞）；
  • 丢弃事件，例子：os/signal、runtime/pprof；
  • 把任意多个事件排进队列。

提示：引入无界队列之前要仔细想清楚。

goroutine 加 select 的版本

type Server struct {
    publish   chan Event
    subscribe chan subReq
    cancel    chan subReq
}

type subReq struct {
    c  chan<- Event
    ok chan bool
}

func (s *Server) Init() {
    s.publish = make(chan Event)
    s.subscribe = make(chan subReq)
    s.cancel = make(chan subReq)
    go s.loop()
}

func (s *Server) Publish(e Event) {
    s.publish <- e
}

func (s *Server) Subscribe(c chan<- Event) {
    r := subReq{c: c, ok: make(chan bool)}
    s.subscribe <- r
    if !<-r.ok {
        panic("pubsub: already subscribed")
    }
}

func (s *Server) Cancel(c chan<- Event) {
    r := subReq{c: c, ok: make(chan bool)}
    s.cancel <- r
    if !<-r.ok {
        panic("pubsub: not subscribed")
    }
}

func (s *Server) loop() {
    sub := make(map[chan<- Event]bool)
    for {
        select {
        case e := <-s.publish:
            for c := range sub {
                c <- e
            }
        case r := <-s.subscribe:
            if sub[r.c] {
                r.ok <- false
                break
            }
            sub[r.c] = true
            r.ok <- true
        case r := <-s.cancel:
            if !sub[r.c] {
                r.ok <- false
                break
            }
            close(r.c)
            delete(sub, r.c)
            r.ok <- true
        }
    }
}

订阅表 sub 现在是 loop 这个 goroutine 的局部变量，不再需要锁：只有它能碰这张表，所有操作通过 channel 排队交给它。（课件里 cancel 分支写成了 case c := <-s.cancel，下面又用 r，是笔误，这里写成 r。）

提示：在能让程序更清楚时，把互斥锁变成 goroutine。

给慢订阅者加一个带队列的辅助 goroutine

func helper(in <-chan Event,
            out chan<- Event) {
    var q []Event
    for in != nil || len(q) > 0 {
        // Decide whether and what to send.
        var sendOut chan<- Event
        var next Event
        if len(q) > 0 {
            sendOut = out
            next = q[0]
        }
        select {
        case e, ok := <-in:
            if !ok {
                in = nil // stop receiving from in
                break
            }
            q = append(q, e)
        case sendOut <- next:
            q = q[1:]
        }
    }
    close(out)
}

课件的推进过程：最初的写法是 select 里直接 case out <- q[0]，q 为空时会越界。改成：只有队列非空时才把 sendOut 设成 out，否则 sendOut 是 nil，对 nil channel 的发送永远不会就绪，select 自然跳过这个分支。再处理关闭：in 被关闭时把 in 设成 nil，不再接收，等队列发完后关闭 out，这样 Cancel 的语义（先送完已发布的事件，再关闭 channel）也保住了。这样就可以给每个订阅者配一个 helper：loop 往 helper 的 in 发，helper 按订阅者自己的节奏往 out 发，loop 不会被慢订阅者拖住。

四、模式二：工作调度器

这和 Lab 1 的 coordinator 有关：

func Schedule(servers []string, numTask int,
              call func(srv string, task int))

第一版：空闲服务器放进带缓冲的 channel

func Schedule(servers []string, numTask int,
              call func(srv string, task int)) {
    idle := make(chan string, len(servers))
    for _, srv := range servers {
        idle <- srv
    }
    for task := range numTask {
        go func() {
            srv := <-idle
            call(srv, task)
            idle <- srv
        }()
    }
}

提示：用带缓冲的 channel 作为并发的阻塞队列。用 goroutine 让各自独立的事情独立运行。

问题一：每个任务一开始就开一个 goroutine，任务有一百万个就是一百万个 goroutine 排队等服务器，又是无界队列。问题二：Schedule 不等任务完成就返回了。

第二版：先拿到空闲服务器再开 goroutine，最后等所有服务器归还

    for task := range numTask {
        srv := <-idle
        go func() {
            call(srv, task)
            idle <- srv
        }()
    }
    for range servers {
        <-idle
    }

第三版：每台服务器一个 goroutine，从 work channel 取任务

func Schedule(servers []string, numTask int,
              call func(srv string, task int)) {
    work := make(chan int)
    done := make(chan bool)
    runTasks := func(srv string) {
        for task := range work {
            call(srv, task)
        }
        done <- true
    }
    for _, srv := range servers {
        go runTasks(srv)
    }
    for task := range numTask {
        work <- task
    }
    close(work)
    for range servers {
        <-done
    }
}

课件先给的是用共享计数器 done++ 加 runtime.Gosched() 忙等的版本，那有竞态，也浪费 CPU；改成每个 runTasks 结束时往 done channel 发一个值，主线程收够服务器数量个。close(work) 让每个 runTasks 的 for range 在取完任务后结束。

提示：关闭一个 channel 来表示不会再发送值。不要通过共享内存来通信，要通过通信来共享内存。

第四版：服务器会动态加入

servers 改成 chan string，新服务器随时会从这里冒出来，所以单开一个 goroutine 不停地接收新服务器、为每台启动 runTasks。这时就不知道总共有几台服务器了，不能再"等每台服务器结束一次"，改成每完成一个任务发一次 done，主线程收够 numTask 个： 

    runTasks := func(srv string) {
        for task := range work {
            call(srv, task)
            done <- true
        }
    }
    go func() {
        for srv := range servers {
            go runTasks(srv)
        }
    }()
    for task := range numTask {
        work <- task
    }
    close(work)
    for range numTask {
        <-done
    }

但这里有死锁：主线程卡在 work <- task 上发任务，而 runTasks 做完一个任务后卡在 done <- true 上，主线程要等发完所有任务才开始收 done。课件给了三种解法：用 select 在发任务的同时也收 done（带标签的 continue WorkLoop）；或者把"发任务"放进一个单独的 goroutine（"让各自独立的事情独立运行"）；或者把 work 改成容量为 numTask 的带缓冲 channel，发送不会阻塞。

提示：引入无界队列之前要仔细想清楚。（这里队列的大小是 numTask，是有界的。）

第五版：call 可能失败，失败的任务要重做

func Schedule(servers chan string, numTask int,
              call func(srv string, task int) bool) {
    work := make(chan int, numTask)
    done := make(chan bool)
    runTasks := func(srv string) {
        for task := range work {
            if call(srv, task) {
                done <- true
            } else {
                work <- task
            }
        }
    }
    go func() {
        for srv := range servers {
            go runTasks(srv)
        }
    }()
    for task := range numTask {
        work <- task
    }
    for range numTask {
        <-done
    }
    close(work)
}

失败的任务重新放回 work。注意 close(work) 必须挪到收完所有 done 之后：如果像前面那样发完任务就关闭，之后某个失败的任务要放回 work 时，会向已关闭的 channel 发送而 panic。因为 work 的容量是 numTask，同时在途的任务不会超过 numTask 个，放回去也不会阻塞。（课件里有一版 for 循环写成 for _, srv := range servers，servers 已经是 channel，应为 for srv := range servers。）

提示：知道每次通信为什么、什么时候能进行。

五、模式三：复制服务的客户端

type ReplicatedClient interface {
    // Init initializes the client to use the given servers.
    // To make a particular request later,
    // the client can use callOne(srv, args), where srv
    // is one of the servers from the list.
    Init(servers []string, callOne func(string, Args) Reply)

    // Call makes a request on any available server.
    // Multiple goroutines may call Call concurrently.
    Call(args Args) Reply
}
type Client struct {
    servers []string
    callOne func(string, Args) Reply

    mu     sync.Mutex
    prefer int
}

提示：如果互斥锁是最清楚的写法，就用互斥锁。（prefer 只是一个小小的共享变量，用锁保护最简单。）

先试一台，超时就换下一台

func (c *Client) Call(args Args) Reply {
    type result struct {
        serverID int
        reply    Reply
    }

    const timeout = 1 * time.Second
    t := time.NewTimer(timeout)
    defer t.Stop()

    done := make(chan result, len(c.servers))

    c.mu.Lock()
    prefer := c.prefer
    c.mu.Unlock()

    var r result
    for off := range c.servers {
        id := (prefer + off) % len(c.servers)
        go func() {
            done <- result{id, c.callOne(c.servers[id], args)}
        }()
        select {
        case r = <-done:
            goto Done
        case <-t.C:
            // timeout
            t.Reset(timeout)
        }
    }
    r = <-done

Done:
    c.mu.Lock()
    c.prefer = r.serverID
    c.mu.Unlock()
    return r.reply
}
  • 每个请求在单独的 goroutine 里调用 callOne，主流程用 select 等结果或超时。超时了不取消前一个请求，而是再向下一台服务器发一个，谁先回来用谁；所有服务器都试过还没回复，就一直等第一个回来的。
  • done 的缓冲区大小是服务器数：Call 返回以后，那些迟到的 goroutine 发送结果时不会阻塞，能正常退出。如果是无缓冲 channel，它们会永远卡住，就是泄漏。
  • 记住上次回复的服务器（prefer），下次先试它（上次能及时回复的服务器，下次多半也能）。
  • defer t.Stop()：不需要的计时器要停掉。课件注明这一条在 Go 1.23 里已经修复（在那之前，没停止也没触发的计时器不会被垃圾回收）。

提示：停掉不需要的计时器。知道每个 goroutine 为什么、什么时候退出。知道每次通信为什么、什么时候能进行。如果 goto 是最清楚的写法，就用 goto。

六、模式四：协议多路复用器

很多并发请求共用一条连接：每个请求带一个标签（tag），回复带回同样的标签，多路复用器根据标签把回复交给对应的调用者。 

type ProtocolMux interface {
    // Init initializes the mux to manage messages to the given service.
    Init(Service)
    // Call makes a request with the given message and returns the reply.
    // Multiple goroutines may call Call concurrently.
    Call(Msg) Msg
}

type Service interface {
    // ReadTag returns the muxing identifier in the request or reply message.
    // Multiple goroutines may call ReadTag concurrently.
    ReadTag(Msg) int64
    // Send sends a request message to the remote service.
    // Send must not be called concurrently with itself.
    Send(Msg)
    // Recv waits for and returns a reply message from the remote service.
    // Recv must not be called concurrently with itself.
    Recv() Msg
}
type Mux struct {
    srv  Service
    send chan Msg

    mu      sync.Mutex
    pending map[int64]chan<- Msg
}

func (m *Mux) Init(srv Service) {
    m.srv = srv
    m.send = make(chan Msg)
    m.pending = make(map[int64]chan<- Msg)
    go m.sendLoop()
    go m.recvLoop()
}

func (m *Mux) sendLoop() {
    for args := range m.send {
        m.srv.Send(args)
    }
}

func (m *Mux) recvLoop() {
    for {
        reply := m.srv.Recv()
        tag := m.srv.ReadTag(reply)
        m.mu.Lock()
        done := m.pending[tag]
        delete(m.pending, tag)
        m.mu.Unlock()
        if done == nil {
            panic("unexpected reply")
        }
        done <- reply
    }
}

func (m *Mux) Call(args Msg) (reply Msg) {
    tag := m.srv.ReadTag(args)
    done := make(chan Msg, 1)
    m.mu.Lock()
    if m.pending[tag] != nil {
        m.mu.Unlock()
        panic("mux: duplicate call tag")
    }
    m.pending[tag] = done
    m.mu.Unlock()
    m.send <- args
    return <-done
}
  • Send 不能并发调用，所以只让 sendLoop 这一个 goroutine 调用它，其他人通过 m.send channel 把请求交给它。
  • Recv 也不能并发调用，所以只有 recvLoop 调用它。
  • "标签 → 等待回复的 channel" 这张表被 Call 和 recvLoop 共享，用互斥锁保护最简单。
  • 每个 Call 的 done 有 1 个缓冲，recvLoop 交付回复时不会被某个调用者拖住。

（课件 Init 里没有创建 m.send，pending 的类型写成了 map[int64]chan Msg，和结构体里的 chan<- Msg 不一致，另一版 recvLoop 里写成了 m.srv.Tag，这里按接口统一改正。）

提示：如果 goroutine、channel 和互斥锁一起用是最清楚的写法，就一起用。

  • 考虑慢 goroutine 的影响。
  • 知道每次通信为什么、什么时候能进行。
  • 知道每个 goroutine 为什么、什么时候退出。
  • 按 Ctrl-\ 杀掉程序并转储所有 goroutine 的栈。
  • 用 HTTP 服务器的 /debug/pprof/goroutine 查看活着的 goroutine 的栈。
  • 用带缓冲的 channel 作为并发的阻塞队列。
  • 引入无界队列之前要仔细想清楚。
  • 关闭一个 channel 来表示不会再发送值。
  • 如果互斥锁是最清楚的写法，就用互斥锁。
  • 解锁互斥锁时优先用 defer。
  • 如果 goto 是最清楚的写法，就用 goto。
  • 如果 goroutine、channel 和互斥锁一起用是最清楚的写法，就一起用。

八、FAQ 里 Russ Cox 的几个回答

  • defer 是别的语言里就有的吗？defer 是 Go 新加的，最初是为了从 panic 中恢复（见语言规范里的 recover），结果对 "defer mu.Unlock()" 这样的惯用法也很有用。后来 Swift 也加了 defer，显然受 Go 启发。
  • 为什么不像 C++、Java 那样用类和面向对象？Go 的面向对象方式更接近 Smalltalk 而不是 Java/C++/Simula，更轻量，更容易改造大型程序。
  • 为什么 while 循环也叫 for？C 里 while(cond) {} 和 for(;cond;) {} 是一回事，Go 不需要两个关键字做同一件事。
  • 多行的 struct 定义为什么要求末尾逗号？Go 发布后不久把分号变成了可选的，规则很简单：每行末尾隐式加分号，除非最后一个记号不可能结束一个语句（比如加号或逗号）。不写末尾逗号，那一行就会被加上分号，解析不了。
  • 为什么这么重视并发和 goroutine？以往的经验表明，用 channel 和轻量进程提供好的并发支持，会让 Google 要建的那类系统容易写得多。
  • Go 传参是传值还是传引用？大多数类型（数字、结构体）传值的拷贝；字符串内容不能修改，相当于传值；channel、map、slice 实际上像传引用，调用者和被调用者都能看到对数据结构的修改；带指针接收者的方法调用会传对象的指针，虽然调用处没有 &。这种不统一可能让人困惑，比如把 sync.WaitGroup 传给函数大概要传 &wg，而 channel 不用 &。
  • 从 Rust、D、Swift、Nim 这些新语言学到了什么？希望有一天 Go 编译器能更好地推断所有权规则，甚至在类型系统里有轻量的所有权表达，Javari、Midori、Pony 和 Rust 是灵感来源。
