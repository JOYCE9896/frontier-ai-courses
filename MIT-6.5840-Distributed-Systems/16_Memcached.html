第十六讲：Facebook 怎样扩展 Memcache

为什么读一篇经验论文；网站架构的四个演进阶段；Facebook 的整体结构：区域、MySQL 分片、memcached 层、无状态 web 服务器；memcached 是什么，旁路缓存的读写流程，为什么由客户端而不是缓存去读数据库；命中率和数据库负载；分片还是复制；为什么要多个区域、区域内为什么要多个集群，入播拥塞，区域池；冷集群预热；惊群和租约；memcached 服务器故障与 Gutter；一致性：写走主区域的数据库，读允许略旧但要能读到自己的写；为什么写时删除而不是更新；"过时的 set"竞态和租约；冷集群的不一致；教训

主讲：Robert Morris（2026 年春季讲义；录像为 2020 年春季，同一篇论文）
资料来源：2026 讲义、FAQ、2020 课堂录像、论文 Scaling Memcache at Facebook（NSDI 2013）

一、为什么读这篇论文

这是一篇经验论文：作者是怎样把一个大系统扩展上去的？遇到了哪些问题？怎样解决？它是一扇看向真实世界的窗口，展示了性能、一致性和实用性之间的取舍。Morris 说里面其实没有新概念、新技术，有几种读法：一个关于"不从一开始认真对待一致性会出什么问题"的警示故事；一个主要用现成软件获得极高容量的了不起的故事；很多系统都面临的根本矛盾的例子，高性能靠复制，而复制正是一致性的敌人。你可以争论设计是否优雅，但不能否认他们的成功。他说自己多年前第一次读后经常回想这篇论文。

网站架构的演进（录像）

  1. 一台机器：用户少时没必要更复杂。Apache web 服务器，PHP 或 Python 之类易写的脚本语言生成网页（Facebook 用 PHP），下载一个标准数据库（Facebook 用 MySQL，有 SQL 和 ACID 事务、持久存储）。这能走很远。
  2. 多台前端服务器加一台数据库：用户多了，第一个瓶颈几乎总是 PHP 脚本占满 CPU，于是多加前端服务器；它们要看到同样的后端数据，能用一台数据库就用一台，一旦用两台，就要操心分布式事务、PHP 脚本该找哪台数据库。
  3. 数据库分片：数据库服务器终于扛不住了，把数据分片到一整柜 MySQL 上（比如 a 到 g 一台，g 到 q 一台）。PHP 代码要知道分片方式，改分片就要改前端软件；跨服务器的事务要两阶段提交，痛苦又慢。MySQL 每秒大概几十万次读，写少得多，网站以读为主，读先撑不住；分片越切越细有两个问题：热门的键只在一台服务器上，分片多细都没用；而且加 MySQL 服务器很贵。同样的硬件跑 memcached，读快得多。
  4. 加缓存层：前端和数据库之间放一层 memcached 服务器，这就开始像 Facebook 了。

二、Facebook 的整体结构

  • 大量数据：好友列表、状态、帖子、点赞、照片；
  • 新鲜/一致的数据不是关键，人能容忍；
  • 读多写少（有帮助）；
  • 局部性很少（没帮助）；
  • 高负载：每秒几十亿次存储操作，远高于单台存储服务器能处理的：MySQL 每秒约 10 万次简单查询，memcached 每秒约 100 万次 get/put；
  • 多个数据中心（至少西海岸和东海岸）。
region (data center):
  "real" data sharded over MySQL DBs   -- ACID, but slow
  memcached layer (mc)                 -- in RAM: fast but limited size
  web servers (clients of mc and DB)   -- "stateless"

每个数据中心的数据库都包含完整的副本。西海岸是主，其他区域通过 MySQL 的异步日志复制成为副本。

先谈性能。论文大部分是在讲怎样避免缓存里的过时数据，但过时问题正是由提高性能的努力引起的。Morris 说他们被极高的负载逼着拼命追性能，一致性则在后面勉强跟上，所以他先讲性能架构。

三、memcached 和旁路缓存

memcached 是一个简单的键值服务器：put(k,v)、get(k)、delete(k)。在内存里：快，不持久，不复制。内存有限，所以按 LRU 淘汰。客户端让它存什么它就存什么。通常部署很多台 memcached 服务器，由客户端决定什么存在哪里。Morris：它比你们的 Lab 3 简单得多，就是内存里一张大哈希表。（FAQ：memcached 指那个软件；论文里的 memcache 指 Facebook 那一整套运行 memcached 的服务器。）

Facebook 的应用怎样用 mc（图 1）

把 mc 当作"旁路"（look-aside）缓存：真正的数据在数据库里；应用分别和 mc、（缺失或写时）数据库通信；mc 对数据库一无所知。 

read(k):
  h = hash(k) % n      // hash chooses which memcache server to talk to
  v = mc[h].get(k)
  if v is nil:
    v = fetch from DB
    mc[h].put(k, v)

write(k, v):
  send k,v to DB
  h = hash(k) % n
  mc[h].delete(k)

memcached 非常流行！旁路方式让它很容易加到现有的 web 应用里；可以缓存任何东西，从数据库的行到算好的整个 HTML 页面；灵活、简单、快。

有同学问为什么缓存不能在缺失时自己去读数据库、存下结果再回复（"直通"缓存，look-through）。Morris：memcached 是完全独立的软件，对数据库一无所知，甚至不一定和数据库一起用；更深的原因是前端存进 memcache 的往往不是一条条数据库记录，而是查了数据库、做了一些处理（转成 HTML 片段，或者把多次查询多行的结果拼起来）之后的半成品，省得下一个读者再处理一遍。怎样从数据库推导出缓存内容，这个知识只在前端的 PHP 代码里。虽然直接整合会让缓存一致性简单得多，但做不到。

用 mc 的好处

它只对读有帮助，但读是绝大多数操作。高命中率减轻数据库服务器的负载：表 2 说命中率约 99%，即数据库读负载降低 100 倍。了不起；但要小心：命中率下降 1%，数据库负载就翻倍。这种缓存不是为了减少用户可见的延迟，而是为了保护数据库服务器免于被巨大负载压垮。Morris：缓存层让系统承受的负载比数据库能处理的高好几个数量级，一旦缓存出问题（比如某台 memcached 坏了，前端只好直接找数据库），数据库看到的读可能从几个百分点跳到一半，所以必须采取认真的措施，确保数据库永远看不到接近全部的负载。

分片还是复制

需要很多台 mc 服务器来处理总负载：CPU 和网络的并行，总内存。怎样在 mc 服务器之间分配负载？客户端的哈希函数决定键分到哪台 mc 服务器：可以分片（分区），可以复制，也可以组合。所有 web 服务器用同样的 hash(k)，所以 C1 缓存了 k，C2 也能看到！中央配置管理器告诉客户端怎样哈希。

分片还是复制能带来最高的 mc 吞吐？这是很多设计的核心问题。

  • 分片：把键分给 mc 服务器。
    • + 省内存（每个键值对只存一份）；
    • - 少数键特别热门时没用；
    • - 每台 web 服务器要和很多 mc 服务器通信（包的开销高）；
    • - 有"入播拥塞"（incast congestion）的风险。
  • 复制：把客户端分给 mc 服务器。
    • + 少数键的读特别热门时有用；
    • + 每个包能装很多请求/回复（开销低）；
    • + 需要联系的服务器少，减少每个包的开销；
    • + 配套的网络更容易设计（两张 1 倍容量的网比一张 2 倍容量的网好建）；
    • - 用更多内存，所以能缓存的不同数据项更少（Morris：10 台各 1 GB 内存的机器分片能缓存 10 GB 不同的数据，复制则每台存的差不多是同一个 1 GB）；
    • - 写更贵。

四、多区域的性能（第 5 节）

west (primary):  DB primary shards,   mc servers, clients
east (replica):  DB secondary shards, mc servers, clients
                 <-- feed from DB primaries to secondaries

问：区域（多个完整副本）的意义是什么？

  • 到用户的往返时间更短（东海岸、西海岸）。Morris：跨大陆大约 50 毫秒，等上好几个就会被察觉；
  • 从本地 mc 和数据库快速读。前端生成一个网页常常要读几十到几百个数据项，所以只读本地很重要；
  • （不过写很贵：必须发到主区域）；
  • 主站点出故障时有一个热副本（Morris 说论文没明说，他不知道他们是否有这个打算）。

问：为什么不按区域划分用户？即东海岸用户的数据放东海岸区域，等等。那样就不用复制，硬件成本也许能减半！但社交网络局部性很差：我的好友有的在东海岸、有的在西海岸，前端就要发很多 50 毫秒的跨数据中心请求。这对比如电子邮件可能很好用。

问：写都发到主区域，为什么性能还可以？写比读少得多；用户不等写完成。

五、区域内的性能（第 4 节）

region:
  DB shards
  cluster 1: mc servers + web servers
  cluster 2: mc servers + web servers
  ...

每个区域内部有多个 mc 集群。集群 = 一整套 mc 缓存服务器加 web 服务器。每台 web 服务器只在自己集群的 mc 服务器之间哈希键。数据库层在区域内只分片、不复制；mc 层在区域内既分片又复制。

为什么每个区域要多个集群

为什么不在每个区域建一个大集群、把负载分给很多台并行的 mc 服务器？

  1. 更多 mc 服务器对热门键没用；复制（每个集群一份）有用。
  2. 集群里 mc 越多，分片越细，每次网页浏览就要（向更多 mc 服务器）发更多包，回复也带来更多入播拥塞。客户端请求一次要取 20 到 500 个键！分布在很多 mc 服务器上，必须并行请求（串行的话总延迟太大），但所有回复会同时回来，网络交换机和网卡的缓冲区耗尽。Morris 补充：用 TCP 时连接数随前端和 mc 的数量相乘增长，每个连接都有开销。（FAQ：入播拥塞就是一台计算机同时收到来自不同来源的太多包，来不及处理，最坏情况下超出缓冲而丢包，交换机里也可能拥塞丢包；论文 3.1 节的窗口机制就是为了限制并行请求数。）
  3. 单个大集群的网络很难建：任意客户端到任意服务器的访问，所以对分带宽必须很大，很贵；两个集群只需一半的对分带宽。

但对不那么热门的项，复制是浪费内存。所以有一个所有集群共享的"区域池"（regional pool），放冷门的对象（不需要很多份），由应用软件决定哪些键放进区域池，这样 mc 服务器能腾出来复制更多热门对象。（FAQ：一个区域有 N 个集群，数据项可能有 N 份缓存拷贝；放在区域池里的项每个区域只缓存一次；代价是 N 份时潜在的服务能力是 N 倍。）

启动一个新的 mc 集群是个性能问题

新集群的命中率是 0%，它的客户端可能给数据库带来巨大的负载尖峰。Morris 的假想例子：原来数据库只看到 1% 的读，新集群接过一半流量后整体缺失率变成 50%，数据库负载涨 50 倍，那就是世界末日。所以新集群的客户端先从已有集群 get()（4.3 节），再 put() 进新集群，基本上是把已有集群惰性地拷到新集群。论文说这样运行几个小时，新集群有了热门数据后再关掉这个模式。

另一个过载问题：惊群（thundering herd）

一个客户端更新数据库并 delete() 一个键；很多客户端 get() 但缺失；它们都去数据库取同样的数据。不好：没必要的数据库负载。解法：mc 只给第一个缺失的客户端一个"租约"（lease）。租约 = 从数据库刷新的许可；mc 记住有效租约的集合；mc 告诉其他人"过几毫秒再试 get()"。效果：只有一个客户端读数据库并 put()，其他人稍后重试 get()，希望能命中。Morris 补充：如果拿到租约的前端在尴尬的时刻失败、没去读数据库也没装入，memcached 最终会让租约超时，下一个来的会拿到新租约。

如果一台 mc 服务器坏了（3.3 节）

不能让数据库处理这些缺失，负载太大；也不能把负载转给另一台 mc 服务器，负载太大。Gutter：一池空闲的 mc 服务器，客户端只在某台 mc 服务器坏了以后才用它，每个集群一个单独的 Gutter 池。过一阵坏掉的 mc 服务器会被替换（Facebook 有自动化机制，但要一段时间）。只要同一时刻只有少数几台 mc 服务器宕机，一个小的 Gutter 池就能当一大批 mc 服务器的备份。前端收到"联系不上"的错误，就把同样的请求发给某台 Gutter 服务器（Morris 猜也是对键哈希来选），没有就读数据库再装进 Gutter。FAQ：Gutter 空闲时是不是浪费？普通 mc 服务器常常接近满负荷，没多少余量，坏了一台，接替者必须本来就差不多是空闲的。

课前问题

为什么失效消息（delete）不发给 Gutter 服务器（无论来自 web 服务器还是 MySQL/McSqueal）？讲义作者的猜测：Gutter 可能存任何键，所以所有失效消息都得发给 Gutter，这至少让删除流量翻倍，而且可能给少量 Gutter 服务器带来很重的负载。Morris 在录像里也是这样解释的，他补充说作为替代，他们让 Gutter 服务器很快地删掉键，而不是一直留着直到被显式删除。

六、一致性

论文的一致性方案是什么

写直接到主数据库，带事务，所以数据库保持一致，比如给"点赞"计数加一是正确的。读呢？读不保证看到最近的写；不同客户端不保证看到同样的值；但不会太旧！只有几秒，即最终一致性；并且能"读到自己的写"。

这是一个常见的模式：更新是 ACID 的，而且慢；读不太一致，但是快。FAQ：如果客户端读到过时数据、基于它算出结果再写回数据库呢？Facebook 的应用程序员不这样写代码，而是给数据库发一个事务，读和写都在事务里，所以更新是强一致的，不涉及过时数据。

为什么读到过时数据也可以

数据是新闻推送条目、帖子、点赞等等。用户看到的网页内容可能稍稍落后于数据库，只要只差一点点，很少有人会注意或在乎，下次再看时 mc 多半已经追上了数据库。FAQ：要避免的大危险是长期缓存过时数据，过时几秒可以，过时几小时不行；没有论文里的机制，丢失的删除或乱序的更新会造成无限期的过时。

论文说的"一致性"是什么意思

它指一次读可能多过时。"更一致"意味着读不会落后最近的写太多。读可能过时是前提，只是想限制过时的程度。这是一种从用户体验出发看待一致性的视角，不是关于正确性或保证的性质。Morris：他们不在乎秒级的一致性，但很在乎不能把一天前、一周前甚至一小时前的数据展示给用户；另一个必须提供一致性的情形是用户更新了自己的数据再读，人知道自己刚改过，看到旧数据会非常困惑。

数据库副本怎样跨区域保持同步

一个区域是主；所有客户端只把更新发给主区域的数据库服务器；主数据库把更新日志分发给次区域的数据库；次数据库应用它们；次数据库是完整的副本（不是缓存）。数据库复制的延迟可能相当长（好几秒）。问：为什么客户端只把更新发给主区域的数据库？为什么不发给本地区域的？（讲义留作问题。）FAQ：FB 把基于日志的复制作为一个发布/订阅系统的组件，见 Wormhole 论文，核心是从 MySQL 的事务日志读出更新、发给备份应用。

写数据库时，对现在已过时的缓存数据怎么办

一个区域里一个数据项可能有很多缓存拷贝，每个集群一份。

  1. 数据库给区域里相关的 mc 服务器发失效消息（delete()），即图 6 里的 McSqueal；
  2. 写的客户端也让本地集群的 mc 失效，这是为了读到自己的写。Morris：数据库发失效可能要一阵，所以前端自己也删；
  3. 次数据库收到更新后，也发出失效消息。

有同学问为什么不先删再写数据库：先删的话，别的客户端在这期间读，缺失后从数据库读到旧值装进缓存，然后才更新数据库，缓存里就留着旧值，写的客户端再读可能看到旧值，违反了读到自己的写。后删也有一小段时间别人能读到旧值，但他们主要担心的是读到自己的写，而数据库最终也会发删除。FAQ：论文的设计并没有消除过时数据的可能，比如客户端写了数据库后，McSqueal 把失效消息发到区域里所有集群的所有相关 mc 服务器之前有一段延迟，这期间的读可能读到旧缓存。

他们遇到了很多数据库和 mc 之间的一致性问题，原因是并发更新以不同顺序影响了不同的缓存拷贝。如果会导致永久过时的缓存数据，就很危险。

竞态例子 1（第 2 节，图 1）：为什么写时删除而不是更新

假设客户端的 write(k,v) 是这样的（这是错的）：

send k,v to DB
put(k,v) in mc    -- rather than delete(k)

两个客户端同时写同一个键怎么办？更新可能以一种顺序到达数据库，却以另一种顺序到达 mc 服务器！导致可能永久缓存不正确的数据。Morris 的例子：C1 把 x 从 0 加到 1、C2 加到 2，数据库最终是 2，但两个 set 到达 memcached 的顺序反了，缓存里留着 1。解法：他们 delete(k)，而不是更新；删除以任何顺序执行都是正确的（论文说删除是幂等的）。Morris 说更新方案不是不能做，但需要仔细的设计。

竞态例子 2（3.2.1 节）："过时的 set"

k not in cache
C1 get(k), misses
C1 v1 = read k from DB
    C2 writes k = v2 in DB
    C2 delete(k)
C1 put(k, v1)

现在 mc 里是过时数据，delete(k) 已经发生过了，它会无限期地一直过时，直到 k 下次被写。用租约解决：mc 在"缺失"时给 C1 一个对 k 的租约，即写 k 的许可；C2 的 delete(k) 让 C1 的租约失效；所以 mc 忽略 C1 的 put(k)；键仍然缺失，下一个读者会从数据库刷新它。Morris 也检查了另一种顺序：如果删除在 set 之后才到，租约还有效，set 被接受，缓存里暂时是旧值；但删除随后到达，会把旧值清掉，过时只是多持续一会儿，不会无限期。

FAQ 给出了更完整的版本：

  1. C1 向 memcache 要 k，memcache 说 k 不存在，返回租约 L1 并记住它；
  2. C1 向 MySQL 要 k，MySQL 回复值 1，C1 这时因为某种原因很慢……
  3. 有人把 MySQL 里 k 的值更新为 2；
  4. MySQL/mcsqueal/mcrouter 给 memcache 发 k 的失效消息，memcache 本来没缓存 k，没什么可删的，但它让 C1 的租约 L1 失效（从有效租约集合里删掉）；
  5. C2 向 memcache 要 k，memcache 说 k 不存在，返回租约 L2（因为 k 当前没有租约）；
  6. C2 向 MySQL 要 k，得到 2；
  7. C2 带着有效的 L2 把 k=2 装进 memcache；
  8. C1 带着无效的 L1 想装入 k=1，memcache 忽略。

现在 memcache 缓存着正确的 k=2。没有租约的话，第 7、8 步之后 memcache 会留着过时的 k=1，可能永远不更新。

冷集群预热的不一致（4.3 节，FAQ）

0. key k starts out with value v1
1. client C1 updates k to v2 in the DB
2. C1 and the DB send delete(k) to the cold cluster,
   but the DB is slow at sending delete(k) to the warm cluster
3. C2 sends get(k) to the cold cluster, which says "miss"
4. C2 sends get(k) to the warm cluster, receives v1
5. C2 set(k, v1) into the cold cluster
6. the DB's delete(k) finally reaches the warm cluster

现在冷集群里是过时的 v1，而删除已经发生过了，所以会一直过时，直到这个键下次被写。论文用两秒的阻止期解决：C1 调用 delete(k) 之后，冷集群的 memcached 在两秒内忽略对 k 的任何 set，到那时数据库对暖集群的 delete(k) 应该已经到了。

一致性问题不正是因为客户端把数据库数据拷进 mc 引起的吗

为什么不只让数据库往 mc 里装值、客户端从不装？那样就没有客户端之间的竞态了，只有有序的写。原则上对，但是：

  1. 数据库一般不知道怎样为 mc 计算值：通常是客户端的应用代码根据数据库结果算出缓存项，mc 的内容往往不是一条字面的数据库记录；
  2. 数据库不知道缓存了什么，最终会为很多没被缓存的键发送大量的值。

FAQ：为什么不干脆在 MySQL 里加个缓存、更好地整合以提供好的一致性？要是有人能给 MySQL 加一个透明缓存、让它像一群 memcached 那么快就太好了，但没人做到，也许不可能。MySQL 本身也缓存，仍然慢得多，大概很大程度上是因为 MySQL 提供的接口强大复杂得多，SQL 大概比 memcached 的 put/get/delete 复杂 1000 倍。FAQ 还提到，图 11 显示 Memcache 可能提供甚至一天前的数据，虽然概率很低，这确实是 FB 一直头疼的问题，让写应用更难，后续有两篇论文讨论，结论大体不变：不一致的概率低到他们愿意接受，即使少数用户原则上可能注意到，多半也意识不到或不在乎（他们的目标应用不是银行）。

七、教训

FB/mc 对存储系统设计者的教训：

  • 缓存对挺过高负载至关重要，不只是为了降低延迟；
  • 需要灵活的工具来控制分片还是复制；
  • 线性一致性太多了；最终一致性又常常不够。

Morris 的总结：可以说这个系统的很多复杂性来自它是用彼此不了解的部件拼起来的，比如 memcached 要是了解数据库、两者配合一个一致性方案就好了；如果 Facebook 一开始就能预见会出什么问题、又有足够的工程师，本可以从头建一个同时满足高性能、多数据中心复制、分片的系统。有公司这样做过，和本文最直接可比的是 Yahoo 的 PNUTS，从头设计，提供多站点复制、有用的一致性（不是线性一致）和好的性能。所以可以做得更好，但问题都是一样的。FAQ：一个毫不妥协的设计要每秒处理几十亿请求、对程序员好用、对全世界的用户都好用、强一致、还不太贵，这是一组很难的目标，FAQ 作者不知道有令人满意的答案；也许用 FaRM 这样更快的数据库就不再需要缓存，也就没有缓存一致性问题；也许让缓存和数据库更紧密地合作，让缓存（而不是应用）处理缺失、让数据库独自负责更新或失效缓存数据。

FAQ 的其他问答：McRouter 是什么？它把很多客户端的 memcached RPC 聚合起来，成批发给 memcached 服务器：每台 memcached 只需要和每个 mcrouter 保持 TCP 连接，而不是和每个客户端；mcrouter 也能把很多客户端请求装进一个 TCP 包，减少每个包的头部和中断开销。用户数据的隐私怎样保护？论文没谈，只能猜：只有 Facebook 自己的计算机能和 memcached、MySQL 服务器通信，大概有防火墙挡住外界；更高一层，web 服务器的代码决定把什么数据给谁看，你把敏感信息交给 Facebook，就得相信他们代码里"谁能看"的观念和你的相同，还要考虑权限代码的 bug、外部黑客、腐败恶意或粗心的员工，这需要内部控制来限制数据即使在 Facebook 内部的使用。
