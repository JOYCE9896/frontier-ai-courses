第十九讲：不可信服务器上的可信存储：SUNDR 与 fork 一致性

为什么要关心不可信的存储服务器；目标是完整性而不是保密；密码学哈希和内容寻址存储，哈希树；数字签名让存储可变，但服务器仍能返回旧的已签名值；x.c 和 NEWS 的例子；SUNDR 的稻草人设计：签名覆盖整个日志；服务器能伪造吗，能隐藏吗；被分叉的日志为什么永远合不回去；fork 一致性；为什么要把 fetch 也记进日志；串行化 SUNDR：每个用户一棵哈希树、签名的句柄和版本向量；隐藏更新后为什么再也无法揭示

主讲：Robert Morris（2026 年春季讲义）；本讲没有公开录像（2020 年这一讲读的是证书透明，录像整理在补充部分），内容根据讲义和 FAQ 整理
资料来源：2026 讲义、SUNDR FAQ、论文 Secure Untrusted Data Repository (SUNDR)（OSDI 2004）（只读到 3.3.2 节末尾）

一、为什么读这篇论文

到目前为止我们基本忽略了安全。安全是个大话题，MIT 有好几门课专门讲；接下来几讲讨论它和一致性、复制的交叉。

我们经常信任存储服务：GitHub、Gmail、AFS、Dropbox。Google 等公司也许是好意，但：也许服务器的软件或硬件有 bug，甚至可被利用；也许攻击者猜到了服务器管理员的密码，改了软件；也许云服务商的某个员工腐败或者马虎。这个问题是真实的！论文引用了对开源代码仓库的成功攻击。令人不安的是，攻击者随后可以修改源代码，也许不会被发现。FAQ：你不会把数据放在一台已知被攻破的服务器上，但你信任的服务器可能后来被攻破了，攻击者改了文件，从这种攻击中恢复很难；如果服务器存的是像 Debian Linux 源代码这样被广泛依赖的东西，问题就很严重，Canonical 在 2019 年就被攻破过。

能不能用不可信的服务器获得可信的存储？

[clients] <--> [untrusted server]

我们想要"完整性"

  • 读者能检查自己取回的数据是正确的；
  • 服务器不能伪造或隐藏更新，也不能改变更新的顺序，比如不能藏起一个关键的安全补丁。

SUNDR 的目标是完整性，不是保密，它用密码学只是为了验证数据是正确的（FAQ：用户可以自己加密文件内容来保密）。用的工具：密码学哈希；数字签名。

二、密码学哈希和内容寻址存储

密码学哈希，比如 SHA-1：h = hash(data)。h 很小，data 可以很大，SHA-1 的 h 是 160 位。"安全"是指实际上找不到两个哈希相同的不同输入。用来给数据命名，和/或验证完整性。

用密码学哈希做安全存储

假设你在用一个云服务商的键值服务器，想检测服务器是否损坏了你的数据。一种办法：

client write(v):
  k = hash(v)
  put(k, v)        // RPC to server
  return k

client read(k):
  v = get(k)       // RPC to server
  if hash(v) != k: reject!
  return v

注意 k 有两种用途：作为名字，也作为验证用的哈希。读的客户端从哪里得到键？不能自己选键，键必须是 hash(v)，所以读者预测不了键，必须有人告诉它，比如发布在安全的网页上，常用于安全的软件分发。

这就是不可信服务器上的安全存储：服务器损坏了数据，客户端的检查会失败。叫"内容哈希存储"（content-hash storage）。

可以用内容哈希存储构建安全的列表和树形结构：文件……被目录引用，目录被根键引用。即使块存在不可信的服务器上，根键也能让客户端取回并检查整个结构，论文称之为"哈希树"。但内容哈希存储不足以构成一个可读写的文件系统：一个键的值不能改变，因为键 = hash(v)，是"不可变"的。

三、数字签名让存储可变

数字签名（比如 RSA）：每个用户有一对公钥/私钥。sig = sign(data, k_priv)；ok = verify(data, sig, k_pub)。 

client write(k, v) OR update(k, v):
  put(k, v + sign(v, k_priv))

client read(k):
  v + sig = get(k)
  if verify(v, sig, k_pub) != true: reject!
  return v

注意 k 和 k_priv 完全无关，值可以修改而不改变 k。任何知道 k 和 k_pub 的人都能取回值，检查它是 k_priv 的持有者签的（不过这并不完全等于"v 是 k 的正确值"！）。

只有数字签名够吗

服务器不能伪造签名，所以不能凭空造出假值。但服务器可以返回一个旧的、签名正确的值：所以它能隐藏一次更新；或者给不同的读者看不同的已签名版本；或者对有些键给旧版本、对另一些键给新版本。这些都是严重的安全问题。而且我们想要的是一个文件系统，不只是单独的数据项：文件名、目录、多个用户、权限等等。

过时值造成问题的例子

开源项目有两个文件：x.c、NEWS。存储服务器归别人所有。

X: x.c  -- v1
A: x.c  -- v2 fixes a bug
B: NEWS -- announce "bug fixed!"
C: read NEWS
C: read x.c

服务器可以给 C 新的 NEWS，却给旧的 x.c！签名都是正确的！但 x.c 是错的版本。SUNDR 能防止这种情况。

SUNDR 的一个想法：每次更新都带一个覆盖整个文件系统的数字签名。所以 B 对 NEWS 的更新里，签名反映了 A 更新过的 x.c；如果 C 看到了 B 更新的 NEWS，只有在 C 也看到 A 的新 x.c 时签名才能通过检查。

四、稻草人设计（第 3.1 节）

  • 服务器存储文件系统修改的完整日志：create、write、rename、delete、mkdir 等；
  • 客户端请服务器追加新操作；
  • 客户端通过取回并重放整个日志来重建文件系统内容；
  • 客户端也请服务器追加"fetch"（读取）日志条目。

细节

日志条目：fetch 或 modify，用户，签名。签名覆盖到这一条为止的整个日志。客户端的一步：

  1. 取回整个日志（其他客户端此时要等）；
  2. 检查日志：每个条目的签名正确，覆盖了之前的日志；每个操作都被权限允许；这个客户端自己的最后一个日志条目在里面（所以客户端必须记住它！）；
  3. 从头重放日志里的操作，构建文件系统状态；
  4. 追加这个客户端的操作，带上对整个结果日志的签名；
  5. 上传日志（然后其他客户端可以继续）；
  6. 客户端（在本地磁盘上）记住它签过名的新条目。

低效，但推理起来简单。稻草人日志的例子：

mod(x.c), X, sig    -- X creates x.c
mod(x.c), A, sig    -- A applies a crucial security patch
mod(NEWS), B, sig   -- B announces the patch

服务器能伪造日志条目吗

不能：它需要知道某个被授权用户的私钥。客户端怎样知道被授权用户的公钥？1. 所有客户端都必须被告知根目录所有者的公钥；2. 文件系统本身存储每个用户的公钥。

服务器能对 C 隐藏一个条目吗

能。隐藏和展示，是 SUNDR 服务器唯一能做的坏事。

如果服务器对 C 隐藏了 A 和 B 的更新

C 读的时候只看到 X 的 mod(x.c)，请求追加一个带签名的 fetch，签名覆盖它看到的内容：fetch(), C, sig，并记住它的最后一个操作 (fetch(), C, sig)。这就是一个分叉日志的开端。服务器可以继续让 C 延长这个"分叉的"日志（这里假设服务器是恶意的，被改造成欺骗 C）。

假设之后服务器想把 B 更新的 NEWS 给 C 看

给 C 看"真实的"日志行不通：

mod(x.c), X, sig
mod(x.c), A, sig
mod(NEWS), B, sig

因为 C 要求它的最后一个操作（它的 fetch）在日志里。把 NEWS 插到 C 的 fetch 之前也不行：

mod(x.c), X, sig
mod(NEWS), B, sig
fetch(), C, sig

因为 C 的 fetch 签名里不包括 A 的 mod(x.c)（也不包括 B 的 mod(NEWS)），签名对不上。把 NEWS 放在 C 的 fetch 之后也不行：

mod(x.c), X, sig
fetch(), C, sig
mod(NEWS), B, sig

因为 B 的 mod() 的签名不包括 C 的 fetch。

所以服务器永远不能再给 C 看 B 的 mod(NEWS)。也不能看 B 未来的任何操作，因为 B 以后生成的签名都包含它的 mod(NEWS)。服务器也不能给 B 看 C 未来的任何操作：它不能给 B 看 C 的 fetch()，因为那和 B 的 mod(NEWS) 不相容；而 C 未来的任何操作的签名都覆盖了 C 的 fetch。但服务器可以继续给 C 一个单独的文件系统视图，只包含 C 未来的操作，不包含 B 的操作。

这就是 SUNDR 的"fork 一致性"

服务器可以永久地把用户分叉开，对彼此隐藏对方的更新。但服务器不能愈合一个分叉，一旦分叉就永远分叉。FAQ 的定义：fork 是恶意服务器给不同用户展示不同文件系统内容的攻击，在 SUNDR 里是可能的，比如 X 更新了 F，之后 Y 读 F，服务器给 Y 看 X 更新之前的旧内容；fork 一致性是指，如果服务器曾经对用户 Y 隐藏了用户 X 的任何操作，就不能再给 X 和 Y 看对方之后的任何操作，一旦隐藏，就必须呈现两个不同版本的文件系统，一个只反映 X 的操作，一个只反映 Y 的。服务器行为正确时得到的是 fetch-modify 一致性：每个用户都看到其他每个用户操作的效果。

fork 一致性是好结果吗

  • SUNDR 允许 fork 攻击，这不理想。
  • 但分叉会造成很大干扰，因为隐藏一次更新就要隐藏那个用户之后的所有更新，所以过一阵很可能被发现。
  • 用户如果能在 SUNDR 之外通信，就能发现，比如发邮件问"你觉得我上次的更新怎么样？"FAQ：如果用户 A 告诉 B 去看文件 x，而 B 看不到 x，他们就知道服务器分叉了文件系统（或者 A 在撒谎）。作者还建议用一个时间戳盒子；比特币有另一种解决分叉的办法，下一讲讲。
  • 在这些假设下，这似乎已经是能做到的最好结果。

FAQ：为什么 fork 一致性是好的？分叉确实不可取，但在通常的假设下，似乎不可能阻止恶意服务器分叉它的客户端。SUNDR 做的是限制服务器挑选隐藏和揭示哪些操作的自由：服务器只能分叉，不能合并。它可以在分叉点之前把 X 的所有更新都给 Y 看，之后对 Y 隐藏 X 的所有更新，但不能隐藏 X 的一次更新而揭示 X 之后的更新。更大的一点是，分叉的后果很可能相当明显（合作的用户不再看到彼此的更新），人们会比较快地意识到被分叉了，然后不再信任这个存储服务，换一个更可信的。论文说"fork 一致性是没有在线可信方时可能达到的最强完整性"，为什么？如果客户端常常离线、彼此不能直接通信，只能和 SUNDR 服务器通信，客户端似乎没什么办法发现服务器在隐藏其他客户端最近的更新；如果客户端一直在线、能直接通过互联网通信，可以互相告知最近的更新、哈希、日志条目甚至文件本身，似乎就能消除成功的 fork 攻击，但那样互联网或客户端本身就充当了在线可信方，这个论断在技术上仍然成立。论文更大的一点是：一旦有了 fork 一致性，再加一些外部措施就比较容易获得接近线性一致的东西，这就是 3.2 节讲的。

发现了 fork 攻击该怎么办（FAQ）？没有很好的答案。当然要换一个存储服务商；要检查各个分叉，合并（或者审慎地丢弃）相互冲突的写，这取决于应用和文件格式，没有通用的技术。最麻烦的是要考虑分叉（以及隐藏用户更新）可能已经对外部世界造成的坏影响，比如用户根据被分叉的（不正确的）数据做出的决定。

课前问题

为什么要把 fetch() 也放进日志？更具体地说（课前问题页的版本）：在简单的稻草人设计里，fetch 和 modify 操作都放进日志并签名。假设另一种设计只签名并记录 modify 操作，这会让恶意服务器能够破坏 fetch-modify 一致性或 fork 一致性吗？为什么？（提示：上面的推理里，C 之所以被困在分叉里，就是因为它的 fetch 条目和签名在日志里，签名记录了它看到过什么。如果只读不写的用户不留下 fetch，服务器之后就可以把 B 的更新再展示给 C，而 C 无法证明自己之前看到的是一个缺了 A 和 B 更新的视图，也就是服务器能先隐藏、后揭示。）

稻草人不实用：日志一直在增长！

五、串行化 SUNDR（第 3.3 节的简化概述）

想法：存储当前的文件系统状态，而不是操作日志（图 2）。用一棵模仿文件系统目录/文件树的哈希树：文件、目录，加一个带签名根哈希的句柄。哈希树不能直接更新，但可以有一个签名的"句柄"（handle）对象，存放当前的根哈希，放在一个已知的、不变的键下。更新时：创建一棵新的哈希树，签名根哈希并更新句柄，删除旧树。FAQ：计算 SHA-1 很快（每字节约 10 个周期），改一个块只需要重算那个块的哈希，再沿路径往上把块哈希到根；签名才是昂贵的部分。不过 SHA 的开销也不能忽略，论文提出让 i-handle 存放哈希和一小段对 i-table 的修改日志，以便把重算哈希树的开销分摊到多个操作上；这也加快了检查过较新版本的客户端的检查，它们只需应用那几个操作。

但是：有多个用户，每人有自己的公钥/私钥；用户之间可能不完全信任；所以一个所有人都能写的根太脆弱。想法：每个用户一棵树（和一个签名的句柄），文件系统是这些树的并集。每个用户的树只存这个用户的文件；读的时候取回所有树，合并成一个文件系统。FAQ：SUNDR 的目标之一是强制用户权限，一个用户的工作站不能修改文件系统的任意部分，用户只能改自己的文件；即使服务器是恶意的、和一个恶意用户勾结，也要做到这一点。这排除了用单个带签名根哈希的数据结构（比如单个 i-table），因为那样所有用户大概都得有更新根哈希所需的私钥。所以每个用户有自己的文件系统树，根哈希由所有者的私钥签名，客户端在查看时把各用户的树合并起来。看起来每个文件属于某个特定用户，只有它的所有者能写。

但是：我们需要强制 fork 一致性，即检测服务器是否在试图愈合一个分叉，也就是检测客户端是否看到了不同的更新序列。用户 X 的树需要声明，X 最近一次更新或读取文件系统时看到了其他哪些树，这样客户端就能检查不同用户的树构成一个线性序列（就像稻草人里对整个日志的签名）。

版本向量

每个用户的树经历一系列编号的版本。用户 X 签名的句柄包含（论文的版本结构，图 3）：

  • X 的根哈希；
  • X 的版本号；
  • 一个"版本向量"（version vector），每个其他用户一个数：X 最近一次读时，看到的每个其他用户的树的版本；
  • 签名（只对句柄块签名）。

然后就能比较 X 和 Y 版本向量里的数，判断：树的更新是否构成一个序列，每次更新都看到了之前的？服务器是否在试图揭示一棵之前被隐藏的树？

例子（服务器行为良好时）

"A1" 是一棵新的签名树，"1 0 0" 是 A1 里的版本向量，时间向下流动。

    A  B  C
    -------
A1  1  0  0
B1  1  1  0
C1  1  1  1
B2  1  2  1

版本向量每次前进一个位置（一个用户）。B 最新的向量是 "1 2 1"，说明 B 看到了 A 的版本 1 和 C 的版本 1。任何看到 B 最新更新的人，就知道要求 A 和 C 的树至少是这些版本。服务器不能伪造版本向量，因为一切都是签过名的；但它能隐藏最新的树：提供旧的签名句柄。

注意例子里的版本向量是可以排序的（服务器行为良好时）：每个在所有位置上都大于等于前一个。这意味着更新按顺序发生，每次都看到了之前的更新。客户端检查版本向量是否可排序。

如果服务器隐藏了一次树更新

假设它对 C 隐藏了 B1（它能做到）：

    A  B  C
    -------
A1  1  0  0
B1  1  1  0      C1  1  0  1

服务器之后就不能把 C 的更新揭示给 B：那会把 C 的版本向量暴露给 B，B 会发现自己和 C 的向量无法排序。B1 然后 C1 不对，因为那样 B1 就被藏起来没让 C 看到（C1 的向量里 B 是 0）；C1 然后 B1 也不对，因为那样 C1 就被藏起来没让 B 看到（B1 的向量里 C 是 0）。SUNDR 的版本向量方案确实强制了 fork 一致性，而且比稻草人对整个日志签名便宜得多。

六、要带走的想法

  • 用不可信的服务器提供可信服务的梦想；
  • fork 攻击；
  • 哈希树；
  • 版本向量。
