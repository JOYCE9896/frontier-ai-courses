补充三：Frangipani：缓存一致性、分布式事务与分布式崩溃恢复

2020 年第 11 讲。整体设计：工作站上的 Frangipani 加共享的块存储 Petal；预期用途和为什么设计适合它；三个挑战：一致性、原子性、崩溃恢复；锁服务器和缓存一致性协议，busy 和 idle，request/grant/revoke/release；用同一把锁做原子的文件系统操作；每个工作站一份放在 Petal 上的预写日志；撤销锁时先写日志再写数据；别人怎样替崩溃的工作站恢复；为什么只重放一份日志也安全：版本号；日志不含文件内容的后果；租约和网络分区；隐藏的 Paxos；性能；Petal 的细节；局限

主讲：Robert Morris（2020 年春季 6.824 第 11 讲）
资料来源：2020 讲义、FAQ、课堂录像、论文 Frangipani: A Scalable Distributed File System（Thekkath、Mann、Lee，SOSP 1997）

一、为什么读这篇论文

缓存一致性；分布式事务；分布式崩溃恢复；以及这三者之间的相互作用。FAQ：主要是作为缓存一致性的例子；此外每个客户端有自己的日志、放在公共的地方让任何人都能用它恢复，这很巧妙；而且这些日志以不寻常的方式交织，对同一个对象的更新可能分散在很多份日志里，所以重放单份日志很微妙（因此需要版本号）；用简单的共享存储（Petal）加聪明但去中心化的参与者构建系统，尤其是从一个参与者崩溃中恢复，也很有意思。

整体设计

[users]
[workstation + Frangipani]  [workstation + Frangipani]  ...
            \                        /
                   network
                     |
                  [Petal]        replicated, striped + sharded block storage
            [lock server]
  • 一个网络文件系统，对现有应用（文本编辑器等）透明，很像 Athena 的 AFS；
  • Petal：块存储服务，有复制，为了性能做了条带化和分片；
  • Frangipani 在 Petal 里存什么？目录、i-node、文件内容块、空闲位图，就像普通硬盘上的文件系统一样；
  • Frangipani：去中心化的文件服务，为了性能做缓存。

预期用途

环境：一个由合作的工程师组成的实验室，即作者自己的研究实验室（在 DEC，FAQ：Digital Equipment Corporation，卖计算机和系统软件的公司，Unix 最初是在 DEC 的硬件上开发的，虽然是在贝尔实验室）；编程、文本处理、电子邮件等；办公室里的工作站。大多数文件访问是访问用户自己的文件；但要能在任何工作站之间共享任何文件：用户之间的合作；一个用户登录多台工作站。所以：常见情况是独占访问，希望它快；但文件有时需要共享，希望那时是正确的。论文写作时这是一个常见场景。

为什么 Frangipani 的设计适合这种用途

  • 强一致性，人们对文件系统就是这样期待的；
  • 每个工作站里做缓存，写回式：所有更新起初只应用在工作站的缓存里，很快，包括创建文件、创建目录、重命名等；如果一切都已缓存，更新完全不需要 RPC；所以文件系统代码必须在工作站里，而不是在服务器里；
  • 大部分复杂性在客户端，不在共享的 Petal 服务器上：客户端越多，CPU 能力越多；在以前的系统（比如 NFS、AFS）里，复杂的服务器是严重的瓶颈。

FAQ：和 GFS 有什么不同？一个大的架构区别是 GFS 的大部分文件系统逻辑在服务器里，而 Frangipani 把逻辑分布在运行它的工作站上，它其实没有 GFS 那种文件服务器的概念，只有文件客户端，这是为了让客户端能纯粹在本地缓存里执行文件系统操作；所以它有大量机制保证工作站的缓存一致，既让一台工作站上的写立刻被另一台的读看到，又让复杂操作（比如创建文件）在其他工作站同时查看相关文件或目录时仍是原子的，而没有指定的文件服务器执行对某个文件或目录的所有操作，这就很棘手。GFS 则完全没有缓存，它关注的是大到放不进任何缓存的巨型文件的顺序读写，靠把每个文件条带化到很多服务器上获得高性能，所以没有缓存一致性协议，客户端相对简单，只有服务器需要加锁和操心崩溃恢复。Frangipani 表现为一个真正的文件系统，任何现有程序都能用；GFS 不是，应用要通过库调用显式地使用它。

工作站缓存里有什么

如果 WS1 想创建并写 /grades：把 / 的信息从 Petal 读进 WS1 的缓存；只在缓存里加一条 "grades" 的目录项；不要马上写回 Petal！以防 WS1 还要做更多修改。

挑战

  • WS2 运行 "ls /" 或 "cat /grades"，它会看到 WS1 的写吗？缓存是写回的，所以工作站的写不在 Petal 里，缓存让读到过时数据成为严重的威胁。这是"一致性"（coherence）。
  • WS1 和 WS2 同时试图在同一个目录里创建 /a 和 /b，它们会覆盖彼此对 / 的修改吗？没有中央文件服务器来理清这件事！这是"原子性"。
  • WS1 在创建文件时崩溃：有很多步，分配 i-node、初始化 i-node、更新目录，没做完会留下一团乱麻。怎样保证其他工作站看不到这团乱麻？怎样清理？这是"崩溃恢复"。

二、缓存一致性

"缓存一致性"解决"读能看到写"的问题，目标是线性一致并且有缓存。很多系统都用"缓存一致性协议"：多核处理器、文件服务器、分布式共享内存。

Frangipani 的一致性协议（简化）

lock server (LS), one lock per file/directory:
  file  owner
  -----------
  x     WS1
  y     WS1

workstation (WS) Frangipani cache:
  file/dir  lock  content
  -----------------------
  x         busy  ...
  y         idle  ...
  • 如果工作站持有锁：busy，正在使用这些数据；idle，持有锁，但此刻没在使用缓存的数据。
  • 工作站的规则：不持有锁就不缓存；先拿锁，再从 Petal 读；先写到 Petal，再释放锁。
  • 一致性协议的消息：request（WS → LS），grant（LS → WS），revoke（LS → WS），release（WS → LS）。

锁以文件/目录命名（实际上是 i-number），但锁服务器其实对文件系统和 Petal 一无所知。

例子：WS1 修改文件 z，然后 WS2 读 z

WS1                      LS            WS2
read z
  --request(z)-->
                         owner(z)=WS1
  <--grant(z)---
(read+cache z data from Petal)
(modify z locally)
(when done, cached lock in idle state)
                                       read z
                          <--request(z)--
   <--revoke(z)--
(write modified z to Petal)
   --release(z)-->
                         owner(z)=WS2
                           --grant(z)-->
                                       (read z from Petal)

要点：锁和规则迫使读看到最后一次写；锁保证"最后一次写"是有明确定义的。注意：工作站释放一个文件的锁之前，必须把修改过的文件内容和元数据都写到 Petal，所以文件内容和元数据都得到了一致性，即读文件能看到最近的内容。

一致性的优化："idle" 状态本身就是一种优化，工作站用完数据后不立刻释放锁，自己再用时不必重新请求。Frangipani 也有共享的读锁，以及排他的写锁。FAQ：如果每个文件的每个块一把锁，性能能提高多少？大概反而更差：读一个文件就要为每个块拿一把锁，工作站和锁服务器的工作都多得多；而且实际中很少有应用在文件块的粒度上做读写共享，更常见的是整个文件粒度的共享，比如编辑器写出整个文件，然后编译器读整个文件。FAQ 也解释了论文里的"伪共享"：系统以 512 字节的块为单位读写 Petal，如果不相关的 X 和 Y 放在同一个块里，一台工作站要改 X、另一台要改 Y，就得让这个块在两者之间来回传，因为没法让 Petal 一次写少于 512 字节；说它是"共享"，因为两台都在用同一个块；说它"伪"，因为它们本质上并不需要共享。

三、原子性

如果两台工作站同时试图创建同一个文件呢？多次写组成的操作做到一半时，部分结果可见吗？比如创建文件要初始化 i-node、加目录项；比如重命名（两个名字都可见？都不可见？）。

Frangipani 实现了事务性的文件系统操作：

  • 一个操作对应一个系统调用（创建文件、删除文件、重命名等）；
  • 工作站获取它要修改的所有文件系统数据的锁；
  • 持有所有锁执行操作；
  • 只在完成后释放，只在整个操作完成后才响应 revoke；
  • 所以其他工作站看不到完成了一部分的操作，也不能同时执行冲突的更新。

注意 Frangipani 的锁在做两件不同的事：缓存一致性（揭示写）；原子事务（隐藏写）。

四、崩溃恢复

如果一台 Frangipani 工作站在持有锁时死了怎么办？其他工作站想继续运行……能直接撤销死掉的工作站的锁吗？如果它在缓存里修改过数据呢？如果它已经开始把修改的数据写回 Petal 呢？比如它已经把新的目录项写进 Petal，却还没写初始化好的 i-node，这是麻烦的情形。等崩溃的工作站重启可以吗？（讲义留作问题。）

Frangipani 用预写日志做崩溃恢复

在把一个操作的任何缓存块写到 Petal 之前，先把日志写到 Petal。这样如果崩溃的工作站为一个操作做了部分 Petal 写，就能根据 Petal 里的日志把它补完。很传统，但是：

  1. Frangipani 为每个工作站单独一份日志：这避免了日志成为瓶颈，便于去中心化，但对某个文件的更新会分散在很多份日志里。
  2. Frangipani 的日志在共享的 Petal 存储里，不在本地磁盘上：WS2 能读 WS1 的日志来从 WS1 的崩溃中恢复。

分开的日志是一种有趣而不寻常的安排。

日志里有什么

（这部分有些是推测，论文没说得很明确。）日志条目：

  • 日志序号；
  • 更新数组：块号、新版本号、地址、新字节；
  • 只包含元数据的更新，不包含文件内容的更新。

例子：创建文件 d/f 产生一个日志条目，它有一个两项的更新数组：在 d 的内容块里加一条 "f" 目录项，带新的 i-number；初始化 f 的 i-node。起初日志条目在工作站的本地内存里（还没到 Petal）。

工作站收到锁服务器对一个被修改过的目录的撤销时

  1. 把它的整个日志强制写到 Petal；
  2. 然后把缓存里更新过的块发给 Petal；
  3. 然后把锁释放给锁服务器。

为什么工作站必须先把日志写到 Petal，再在 Petal 里更新 i-node 和目录等？为什么要等到锁服务器撤销锁时才写日志？（讲义留作问题。前者是预写日志的要求：只写了一部分块就崩溃时，要靠日志补完；后者是为了性能，没人要这把锁时什么都不写，更新都留在缓存里。）FAQ：论文 9.2 节说"文件创建花的时间更长……"是因为日志，所有元数据修改都要写到 Petal 两次，一次写日志，一次写文件系统结构，之后那部分日志才能删掉；日志满了，Frangipani 就得停下来，把对应那部分日志的修改块发给 Petal，才能释放那部分日志继续处理新操作。为什么加大日志能提高性能？FAQ 作者猜测基准测试大概反复往同一个目录里加新文件，每释放一部分日志，这个目录的块就得写一次 Petal，日志越长，整个测试里这个目录要写 Petal 的次数越少，这叫"写吸收"（write absorption）。

WS1 在持有锁时崩溃会怎样

起初没什么，直到 WS2 请求一把 WS1 持有的锁。锁服务器给 WS1 发 revoke，得不到回应；锁服务器超时，让 WS2 根据 Petal 里 WS1 的日志恢复 WS1。WS2 怎样根据 WS1 的日志恢复？从 Petal 读 WS1 的日志；执行日志里描述的 Petal 写；告诉锁服务器完成了，锁服务器就可以释放 WS1 的锁。注意，每个工作站的日志都在 Petal 里、任何工作站都能读来做恢复，这一点至关重要。

如果 WS1 在把最近的日志写到 Petal 之前就崩溃了呢？WS1 最近的操作可能完全丢失，但 Petal 里的文件系统在内部是一致的。FAQ：比如应用创建了文件 x 并打印"我创建了文件 x"，然后工作站在把信息写到 Petal 之前崩溃，可能打印了但文件 x 并不存在，这对 Linux 这样的本地磁盘文件系统也相当常见，需要确保数据永久保存的应用可以调用 fsync()。

为什么只重放一份日志也是安全的

尽管其他工作站对同样的文件做了交错的操作。例子：

WS1: delete(d/f)               crash
WS2:               create(d/f)
WS3:                                  recover WS1

WS3 在恢复 WS1 的日志，但它不看 WS2 的日志。恢复会重放那个 delete 吗？（这就是 2020 年的课前问题。）不会，"版本号"机制阻止了这一点：Petal 里每个元数据块（i-node）都有版本号；每个日志操作里的版本号是块的版本加一；恢复只在操作的版本 > 块的版本时才重放，即只在这个块还没被这个操作更新过时才重放。

WS3 需要获取 d 或 d/f 的锁吗？不需要：如果版本号和操作之前相同，说明 WS1 没做这次写，所以它不可能释放过这把锁，所以没有别人能拿到这把锁，所以 WS3 在 Petal 里更新它是安全的。FAQ 用 WS1 create(xxx) delete(xxx)、WS2 之后 create(xxx) 的例子说明了同一件事：恢复时看到 delete(xxx) 的日志条目版本号 <= 元数据块的版本号，就知道这个块已经被更新过，忽略这个条目。

日志不包含文件内容，后果是什么

工作站发给 Petal 的内容写，顺序可能和应用调用 write 的顺序不同。没有崩溃时，锁把这一点隐藏了，所以无所谓；崩溃了，Petal 里可能留下最近写的一个随机子集。对很多应用这无所谓，崩溃本来就不太可能让程序的输出处于有用的状态；谨慎的程序（比如文本编辑器、数据库）会用 fsync()。这种行为模仿的是比如 Linux 用本地磁盘的情形。FAQ：文件系统小心地维护自己内部的不变式（元数据），否则崩溃后文件系统可能根本没法用；但把维护文件内容的不变式留给应用，因为只有应用知道哪些数据必须小心地（也就是昂贵地）马上写盘。

网络分区

如果 WS1 持有一把锁，网络分区，WS2 认定 WS1 死了，恢复它，释放了 WS1 的锁。如果 WS1 其实还活着，它之后会试图写这把锁保护的数据吗？锁有租约！锁的持有者在租约期过后不能再用这把锁；锁服务器在租约过期之后才开始恢复。

这里藏着 Paxos 或 Raft 吗

有，锁服务器和 Petal 服务器都有基于 Paxos 的配置管理器：保证即使有分区也只有一个锁服务器；保证每个 Petal 分片只有一个主。

FAQ：Frangipani 和两阶段提交都提供分布式事务，等价吗？有相似之处：要执行一个操作，都要获取所有相关的锁、收集所有相关的数据、把一切记进日志，然后才能释放锁。最大的区别在这些事情发生的地方：在 Frangipani 里，锁和数据是可移动的，被收集到执行操作的那台 Frangipani 服务器上；在两阶段提交里，数据（连同锁和日志）分片在各台服务器上，所以工作也得按同样的方式切分。另一个重要区别是 Frangipani 有服务器在持锁时崩溃后怎样继续的办法，每台服务器的日志在 Petal 里，别的服务器能替它恢复；经典两阶段提交把服务器的日志放在本地磁盘上，服务器崩溃就访问不到，在它复活之前无法前进、锁也不能释放。另一种办法是用比如 Paxos 复制每个参与两阶段提交的服务器（包括锁、日志和数据），实际上消除了服务器崩溃的问题，Spanner 就是这样做的。

五、性能

很难评判 1997 年的数字。它们达到硬件极限了吗（磁盘带宽、网络带宽）？硬件越多，总吞吐增加吗？每加一台 Frangipani 工作站，带来的容量和负载哪个更多？我们关心哪些场景？读写很多小文件（比如读我的邮件）；读写巨大的文件。

  • 小文件性能（图 5）：横轴是活跃工作站数，每台跑一个文件密集的基准测试，用不同的文件和目录；纵轴是单台工作站的完成时间。平的说明扩展性好，没有显著的共享瓶颈；大概每台工作站只用自己的缓存，Petal 的众多磁盘可能也带来了并行性能。

六、Petal 的细节

Petal 为 Frangipani 提供容错的存储，值得讨论。

  • 块读写接口，和现有文件系统兼容；
  • 看起来像一块巨大的磁盘，但由很多服务器、很多磁盘组成，大而且高性能，按 64 KB 的块条带化（FAQ：条带化和分片类似，具体是把一个文件的各块分布在多台服务器上，块 0 在服务器 0、块 1 在服务器 1、块 2 在服务器 0……一来读单个大文件时不同部分可以从不同服务器读，二来负载均衡）；
  • 虚拟的：64 位稀疏地址空间，写时分配，有地址翻译映射；
  • 主/备（一台备份服务器）：主把每个写发给备份；用 Paxos 为每个虚拟地址范围就主达成一致；
  • 崩溃后怎样恢复？假设一对是 S1 和 S2，S1 坏了，S2 现在是唯一的服务器；S1 重启，但错过了很多更新；S2 记得一份它写过的每个块的列表！所以 S1 只需要读那些块，不用读整块磁盘；
  • 日志：虚拟到物理的映射，以及错过的写的信息。

FAQ：Frangipani 工作站的日志和 Petal 的日志有什么区别？Petal 论文几乎没提它的日志，FAQ 作者猜 Petal 记录的是逻辑块号到物理块号映射的变化、物理块空闲列表的变化，以及表明另一个副本可能缺了哪些块更新的 "busy" 位，即底层块操作的信息；Frangipani 记录的是文件系统操作的信息，往往涉及更新 Petal 里多处文件系统状态，比如删除文件的日志条目可能说这个操作改了某个块和 i-node 空闲位图的某些位，擦掉了某个目录项。两份日志都存在 Petal 的磁盘上，在 Petal 看来 Frangipani 的日志只是存在 Petal 块里的数据。Petal 怎样高效地给它表示的大虚拟磁盘做快照？映射实际上是按（虚拟块号，epoch 号）这一对索引的，还有一个当前 epoch 号；写一个虚拟块时，如果当前映射的 epoch 小于当前 epoch，就新建一个映射（分配一个新物理块），epoch 为当前值；读一个虚拟块用 epoch 最高的映射；做快照只需把当前 epoch 加一；读快照时指定快照的 epoch，每次读用 epoch <= 快照 epoch 的最高映射（见 Petal 论文 2.2 节）。为什么 Petal 用块接口，而不是像 AFS 那样懂目录和文件的文件服务器？一个原因是作者先开发了 Petal，它已经解决了很多容错和扩展问题，用它简化了 Frangipani 的一些设计；而且这种安排把工作从中心化的服务器挪到客户端工作站，帮助 Frangipani 在工作站增加时扩展得好。但这种划分让维护文件系统层面结构的不变式更难，没有哪一个实体负责，所以 Frangipani 用锁服务和自己的日志构建了自己的事务系统，才能对 Petal 里的文件系统做复杂的原子更新。

七、局限和要记住的想法

  • 最适合比如程序员工作站，其他场合用处不大：文件系统对很多应用（比如网站）来说并不是好的 API；
  • Frangipani 负责强制权限，所以工作站必须可信，因此 Athena 不能在 Athena 工作站上运行 Frangipani。FAQ：用户可以改本地的 Frangipani 软件，读写别的用户在 Petal 里的数据；在小组织里，或者让 Frangipani 跑在专门的服务器上、用 NFS 之类的协议和用户工作站通信，也许仍有意义；
  • Frangipani 和 Petal 的划分有点别扭：两层都记日志；Petal 可能接受来自已被判定"宕机"的 Frangipani 工作站的更新；比简单的文件服务器 RPC 消息更多。

要记住的想法：共享简单存储的复杂客户端，也许可扩展；缓存一致性；分布式事务；分布式崩溃恢复；以及它们之间的相互作用。

FAQ：二十多年后分布式文件系统的现状？有些组织仍把用户和项目文件放在分布式文件系统上，但随着笔记本（必须自成一体）和商业云服务的兴起，它们的重要性下降了；SMB、NFS、AFS 等现有协议仍有很多用户，还有 xtreemfs、Ceph、Lustre、Dropbox 等较新的系统；NetApp 和 EMC 卖大量网络存储。网站、大数据和云计算的兴起转移了存储系统开发的重心：网站适合数据库类的服务器，包括键值存储，文件服务器不太合适；大数据处理系统常用文件系统，比如 MapReduce 用 GFS，但重点是对巨大文件的高并行吞吐，用不上 Frangipani 的缓存、一致性和加锁。
