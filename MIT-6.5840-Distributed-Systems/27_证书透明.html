补充六：证书透明（Certificate Transparency）与二义性

2020 年第 18 讲，和第十九讲 SUNDR 同属"fork 一致性"这条线。为什么看 CT：开放系统里互不信任的参与者；证书之前的中间人攻击；证书和 CA 的方案，为什么并不完美；为什么不建一个有效证书的在线数据库；CT 是一个审计系统：CA、日志服务器、浏览器、监视者；难点是让所有人看到同一份日志：不能删除，不能二义；Merkle 树，签名的树头；包含证明；分叉攻击；一致性证明和 gossip；浏览器用一致性证明防止切换分叉，fork 一致性；发现问题时怎么办；CT 的可攻击之处；要带走的东西

主讲：Robert Morris（2020 年春季 6.824 第 18 讲 Fork Consistency, Certificate Transparency）
资料来源：2020 讲义、FAQ、课堂录像、阅读：Certificate Transparency 的介绍材料和 RFC 6962

一、为什么看证书透明

  • 到目前为止我们都假设系统是封闭的，所有参与者都可信，比如 Raft 的节点；
  • 如果系统是开放的，任何人都能用呢？如果没有一个人人信任的权威来运行系统呢？那就要用互相猜疑的部件构建有用的系统，信任和安全成了分布式系统的头等问题；
  • 最基本的问题是"我在和正确的计算机通信吗？"这是一个（几乎无解的）问题，CT 有助于应对它；
  • 这部分内容往回连到一致性：CT 的全部要义就是确保所有各方看到同样的信息；
  • 往后连到区块链和比特币：CT 是一种类区块链设计在加密货币之外的用途，已经部署，用得很多。

二、证书和 CA

证书出现之前（1995 年以前）

中间人（MITM）攻击是 web 上的一个担忧：浏览器经互联网连 gmail.com，攻击者让它连到一台假服务器，偷走密码。重定向流量不太难：DNS 不太安全，可以给浏览器伪造 gmail.com 的 DNS 信息；网络路由器、路由系统、WiFi 也不总是很安全。FAQ 更具体：攻击者可以在本地 WiFi 或 MIT 校园网上窥探 Ben 的 DNS 请求并给出错误回复，让浏览器连到攻击者的服务器；如果攻击者有一张看起来正确的、由合法 CA 签名的 gmail.com 证书，浏览器就会接受，攻击者的服务器给出一个和 gmail.com 登录页一模一样的页面，Ben 就输入了密码。

基本的证书和 CA 方案

把 DNS 名字映射到公钥。假设用户知道自己想通信的对象的 DNS 名字。

[Google] --requests cert--> [CA]
[gmail.com server] <--https connection--> [browser]

一张证书包含：DNS 名字（比如 "gmail.com"）；那台服务器的公钥；CA 的身份；用 CA 的私钥做的签名。

  • 浏览器里有一份所有可接受 CA 的公钥列表；
  • 浏览器用 https 连接时：服务器发来证书；浏览器（用可接受 CA 公钥的列表）检查 CA 的签名；浏览器挑战服务器，让它证明自己有私钥；
  • 现在中间人攻击更难了：假设用户点了 https://gmail.com，攻击者的假 gmail.com 服务器必须有一张 gmail.com 的证书。

为什么证书并不完美

  • 不清楚怎样判断谁拥有一个 DNS 名字：我向 CA 申请 "x.com" 的证书，CA 怎么判断？结果很难，即使是 microsoft.com 这样的知名名字。
  • 更糟的是：浏览器列表里有 100 多个 CA，不是都管理得好，不是都只雇可信的员工，不是都能顶住本国政府的要求。
  • 而且：任何 CA 都能为任何名字颁发证书，所以整体安全受限于最不安全的那个 CA。
  • 结果：多次出现"伪造"证书的事件，比如一张颁给别人的 gmail.com 证书；很难防止；甚至很难发现外面有一张伪造证书！

为什么不建一个有效证书的在线数据库

数据库服务能发现并拒绝伪造的证书，浏览器使用任何证书前都先查数据库。但是：

  • 怎样判断谁拥有一个 DNS 名字？判断不了，就没法拒绝伪造证书；
  • 必须允许人们换 CA、续期、丢了私钥等等，这些看起来都像是已有名字的第二张证书！
  • 谁来运行它？世界上没有一个人人信任的权威。

三、CT 怎样应对：一个审计系统

它其实是一个审计系统，不直接禁止任何东西，这很合理，因为名字所有权的规则本身就没有明确定义。它的主要效果是保证所有证书的存在都是公开的。 

[gmail.com] [CA] [CT log server] [browser] [gmail's monitor]
  1. gmail.com 向 CA 申请证书；
  2. CA 给 gmail.com 颁发证书；
  3. CA 把证书登记到 CT 日志服务器（通常不止一个）；
  4. 日志服务器把证书加进日志；
  5. 浏览器连 gmail.com；
  6. gmail.com 把证书给浏览器；
  7. 浏览器问 CT 日志服务器这张证书在不在日志里；
  8. 与此同时：gmail.com 的监视者（Monitor）定期取回整个 CT 日志，扫描所有写着 "gmail.com" 的证书，如果有它不知道的就报警，因为那些一定是伪造的。

所以：如果浏览器和监视者看到同一份日志，监视者在日志里发现伪造证书时报警，浏览器要求它用的每张证书都在日志里，那么浏览器就可以放心地使用日志里的任何证书。

FAQ：监视者（Monitor）和审计者（Auditor）有什么区别？每个浏览器里跑一个审计者：浏览器访问 https 网站、收到证书后，向相关的日志服务器要证书在日志里的证明；它还持久地保存见过的最新的 STH（签名的树头），并要求日志服务器证明最新的 STH 描述的日志是它上次那份日志的扩展。监视者检查它知道的那些名字在日志里只有正确的证书，比如 MIT 可以跑一个监视者，定期在 CT 日志里找所有 *.mit.edu 的证书，和它知道的有效证书列表比对；也可以由每个 CA 跑监视者，检查它颁过证书的名字没有突然出现别的 CA 颁的证书。监视者取回整个日志，并检查日志服务器给的 STH 和日志内容是否匹配；审计者只有一些 STH、一些包含证明、一些一致性证明。Google、Facebook 等公司跑自己的监视者，也有监视服务。监视者怎么知道哪些证书合法？它必须对它负责检查的那些名字有特殊的了解：所有者给它合法证书的列表，或者被授权为所有者颁证书的 CA 列表。

难点：怎样保证所有人看到同一份日志

当日志运营者可能是恶意的，并且和（其他）恶意 CA 合谋时。

  • 关键：不能删除（即使是恶意的日志运营者）。否则日志可以给浏览器看一张伪造证书，声称它在日志里，等浏览器用过后再删掉，监视者就注意不到了。（准确说是"不能有不被发现的删除"。）FAQ 描述了完整的攻击：恶意 CA 造一张 gmail.com 的伪造证书，搭一个看起来像 gmail.com 的网站，骗你的浏览器去那里，和一个腐败的 CT 日志运营者合谋让浏览器相信证书在日志里，你的浏览器接受了，网站捕获你的密码，以你的身份登录真的 gmail，取走并记录你的邮件，再给你看你的收件箱，仿佛一切正常；事后要掩盖痕迹，就得让这张证书悄悄从日志里消失。
  • 关键：不能二义（equivocation，即每个人看到同样的内容）。否则日志服务器可以给浏览器看一份含伪造证书的日志，给监视者看一份不含它的日志。（准确说是"不能有不被发现的二义"。）

这样一来：如果 CA 颁了伪造证书，必须把它加进中心日志客户端才会接受；但之后就不能删掉；所以名字所有者的监视者最终会看到它。怎样在不可信的服务器上建一个不可变的、只能追加的、无分叉的日志？

四、Merkle 树

              root = H(H(H(a),H(b)), H(H(c),H(d)))
               /                         \
       H(H(a),H(b))                 H(H(c),H(d))
        /       \                     /       \
     H(a)      H(b)                H(c)      H(d)
      a         b                   c         d      <- logged certs
  • 日志服务器维护一份证书日志；为简单起见，假设日志条目数总是 2 的幂；
  • H(a,b) 表示 a+b 的密码学哈希，关键性质：找不到产生同样哈希的两个不同输入；
  • 在日志条目之上建一棵哈希的二叉树，即 Merkle 树；每个哈希值只对应一种可能的日志条目序列，以任何方式改动日志，根哈希都会变；
  • STH 是签名的树头（Signed Tree Head），由日志服务器签名，所以它之后无法否认自己发布过这个根哈希；
  • 日志服务器一旦把一个 STH 给我看，就承诺了特定的日志内容。

日志服务器怎样往 Merkle 树日志里追加记录：假设日志里已有 N 个条目，根哈希为 H1；日志服务器等 N 个新条目到达，把它们哈希成 H2；创建新的根 H3 = H(H1, H2)。

包含证明

日志服务器怎样证明一张证书在某个 STH 下的日志里？叫"包含证明"（proof of inclusion，或 RecordProof()，或 Merkle Audit Proof）。浏览器不想用不在日志里的证书，因为那样监视者看不到它，就没有任何针对伪造证书的保护。这个证明表明：对一个 STH、一张证书和一个日志位置，那张证书必定在那个位置。浏览器向日志服务器要当前的 STH（日志服务器可能在 STH 上撒谎，后面再考虑）。

考虑只有两条记录 a 和 b 的日志：STH = H(H(a), H(b))。起初浏览器知道 STH，但不知道 a 或 b。浏览器问"a 在日志里吗？"，服务器回复"位置 0"和 z = H(b)，这就是证明；浏览器检查 H(H(a), z) = STH。浏览器问"x 在日志里吗？"，但我们知道在这个 STH 下 x 不在日志里，日志服务器想撒谎说在，以便骗浏览器使用伪造证书 x 而不让监视者在日志里看到 x。浏览器知道 STH，所以日志服务器需要找到一个 y，使得 H(H(x), H(y)) = STH = H(H(a), H(b))，而 x != a。但密码学哈希保证：实际上不可能造出两个不同的消息 M1 ≠ M2，使 H(M1) = H(M2)。

推广到更大的树：提供一路到根的"另一侧"哈希。证明很小，N 个元素的日志只要 log(N) 个哈希，这很重要，我们不希望浏览器下载整个日志，外面有几百万张证书。FAQ：浏览器不提供证书在日志里的下标，而是提供证书的哈希，日志服务器回复包含证明（加上证书的下标），所以日志服务器要有一张从证书哈希到日志位置的大表（RFC 6962 第 4.5 节）。

五、分叉攻击、一致性证明和 gossip

如果日志服务器为浏览器编造一份不同的日志，里面含伪造证书，只把那份日志的 STH 发给浏览器（不发给任何监视者）呢？即日志服务器在当前 STH 上撒谎。日志服务器能向浏览器证明伪造证书在那份日志里。这是一种分叉攻击，或者说二义。在 CT 里分叉是可能的，但故事没有结束。

怎样发现分叉/二义

浏览器和监视者应该比较 STH，确保看到的是同一份日志，这叫"gossip"（闲聊）。怎样判断一对 STH 是否构成分叉的证据？它们可能合法地不同，如果一个来自比另一个更晚的日志版本！

Merkle 一致性证明（TreeProof()）

给定两个 STH H1 和 H2，H1 下的日志是 H2 下日志的前缀吗？客户端请日志服务器给出证明：证明成立，日志服务器就没有分叉它们；给不出证明，日志服务器可能分叉了它们，给它们看了不同的日志。证明：在树从 H1 长到 H2 的过程中，对每个根哈希 Hz = H(Hx, Hy)，给出右边的哈希 Hy。客户端计算 H(H(H1, Hy1), Hy2)……检查是否等于 H2。

为什么一致性证明意味着客户端看到的是同一份日志？如果 H2 是由 H1 覆盖的那段区域里不同的日志条目推导出来的，即日志服务器分叉了两个客户端。假设 H2 是比 H1 大的下一个 2 的幂大小的日志：两个都知道 H1 和 H2 的客户端期待的证明是一个 x，使 H2 = H(H1, x)。因为日志服务器分叉了它们，我们知道 H2 = H(Hz, y)，其中 Hz != H1。所以作弊的日志服务器要找到 x 使 H(H1, x) = H2 = H(Hz, y)，而 H1 != Hz，密码学哈希保证这不太可能。所以一致性证明是令人信服的证据，说明 H1 是 H2 的前缀，日志服务器没有分叉两个客户端。

所以如果浏览器和监视者做足够多的 gossip，并要求一致性证明，就能相当确定它们看到的是同一份日志，因而监视者检查的证书集合就是浏览器看到的那些。

最后一个证明问题：防止切换分叉

如果浏览器遇到伪造证书 C1，从日志服务器拿到了有效的包含证明，但那是在一个专为骗它而设的分叉日志里呢？浏览器会照常使用伪造的 C1。但下次浏览器和日志服务器通信时，日志服务器又给它看主分叉和它的 STH，现在浏览器和监视者比较 STH，看起来什么坏事都没发生。

浏览器用日志一致性证明来防止切换分叉：浏览器（持久地）记住它从日志服务器拿到的最后一个 STH；每次和日志服务器通信都拿到一个新的 STH；浏览器要求证明旧 STH 表示的日志是新 STH 的前缀。所以一旦日志服务器把一张证书展示给浏览器，它以后给浏览器看的 STH 也必须反映这张证书。所以如果日志服务器分叉了一个浏览器，它就不能再切换分叉了，这叫"fork 一致性"，一旦分叉，永远分叉。所以下次浏览器和监视者 gossip 时，分叉会暴露出来；所以日志服务器有动力不去分叉。

FAQ：gossip 好像没有定义也没有实现，没有 gossip CT 还安全吗？没有 gossip，合谋的 CA 和 CT 日志可以分叉一个浏览器、骗它使用伪造证书（有 gossip 也可能发生），而且也许永远不被发现（gossip 本可以防止）。但因为 CT 是 fork 一致的，恶意的 CA/CT 必须永远维护并扩展给受害者看的那份日志，把受害者期待的所有证书都放进去，那必须是专为这个受害者准备的一份特殊日志；不这样做，受害者会发现很多别人能用的证书在他这里不能用，也许就意识到出了问题。这个故事有点弱，但利用缺少 gossip 确实别扭而且有风险。日志服务器能分叉吗？FAQ：确实可能，至少暂时可能；CT 的设计目标是改进现有的 CA 体系、同时实际可部署，而不是追求完美（没人真知道怎样做到完美）；在 CT 之前基本没有办法发现伪造证书，被发现的都是偶然；有了 CT，不能立刻发现，所以伪造证书仍能被使用，但监视者最终（也许一天之内）会意识到日志里有伪造证书，或者某个日志运营者分叉了它的日志。

六、发现问题时怎么办，CT 的可攻击之处

  • 给不出日志一致性证明：即分叉攻击的证据，说明日志服务是腐败的或者管理很差，调查之后这个日志服务器多半会被移出浏览器的认可列表。
  • 明明有签名的 SCT（Signed Certificate Timestamp，日志服务器承诺收录这张证书的签名凭据），却给不出包含证明：这可能是攻击的证据，即给受害浏览器看了一张证书，却在监视者能看到的日志里略去了它；也可能只是日志服务器往日志里加证书比较慢。
  • CT 日志里有伪造证书，比如一张 mit.edu 的证书，而 MIT 没申请过：需要人去和负责的 CA 弄清原委，常常只是一个错误，就把证书加进吊销列表；如果频繁发生或者显然是恶意的，浏览器厂商可能把这个 CA 从认可列表里删掉。FAQ：大多数情况大概是良性的（比如有人合法地给网站换了新证书），即使是错误颁发的证书也可能只是一次意外。Morris 在录像里补充：已有一个早就存在的吊销服务，浏览器会检查它，监视者发现伪造证书就能把它放上去让它失效，这不是 CT 的一部分。

CT 能被怎样攻击？

  • 浏览器使用一张证书和监视者检查日志之间有时间窗口；
  • 没有人监视某个名字；
  • 出了问题时不总是清楚该怎么办：谁拥有一个名字？也许伪造证书只是个意外？
  • 当前的 CT 设计和实现缺少 gossip；
  • 隐私和追踪：浏览器向日志服务器要证明，会暴露它访问了哪些网站。

FAQ：不同的 CT 日志应该相同吗？不同的日志多半不同，CT 只需要一张证书在一个表现良好的日志里就能达到目标，证书（实际是 SCT）里有它所在日志的 ID，浏览器知道该找哪个日志服务；浏览器要求证书在日志里，监视者检查所有日志，所以即使只在一个日志里的伪造证书也很可能很快被发现。因为任何一个日志服务都可能失败或变得恶意，有一定数量（几十个）的独立日志服务，CA 通常把每张新证书放进多个日志（比如五个）。还需要 CA 吗，日志本身不就能当权威？这是个诱人的想法，一个担心是没有 CA 过滤，CT 系统可能被垃圾证书淹没；另一个是 CA 确实对证书请求做了一些验证；而且浏览器和 web 服务器已经在用现在的证书，换一套方案是个巨大的麻烦。FAQ 作者猜，就像 CA 方案最终的问题比 90 年代刚引入时大多数人想象的严重，如果完全依赖 CT，它也会这样。检查 CT 日志会不会成为性能瓶颈？FAQ 作者不知道问题有多大，一个日志的副本可以由很多服务器提供以提高吞吐；浏览器对一个 https 网站的证书拿到一次包含证明后，可以永远缓存它。CT 真的抓到过伪造证书吗？有成功的案例（Google 安全博客 2015 年 9 月）。可以在 transparencyreport.google.com 查一个网站的证书是否在 CT 日志里。

七、要带走的东西

  • 关键性质：尽管有恶意，每个人都看到同一份日志，浏览器和 DNS 名字所有者都是；如果浏览器看到了一张伪造证书，DNS 名字所有者也会看到。这是一种一致性性质！
  • 无法预防时，审计值得考虑：能事后发现坏事，往往就够了，而且常常比预防容易得多。
  • 二义（equivocation）：恶意服务器给一部分人一个视图、给另一部分人另一个视图，这是一种重要的攻击。
  • fork 一致性：担心分叉时，构建一个系统，迫使恶意服务器一旦分叉了某人就得一直把他留在那个分叉上，从而无法通过抹掉分叉来消灭证据。
  • 用 gossip 发现分叉：如果参与者彼此不通信，通常无法注意到发生了分叉，所以想发现分叉，就必须有某种 gossip，让各方能互相对照。
