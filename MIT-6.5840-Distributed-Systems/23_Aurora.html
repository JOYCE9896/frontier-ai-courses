补充二：数据库日志、多数派与 Amazon Aurora

2020 年第 10 讲。为什么读 Aurora；从 EC2、EBS 到 Multi-AZ RDS 的演进，各自的问题；事务数据库怎样使用存储：缓存的数据页、预写日志、提交、恢复；Aurora 的两个大想法：多数派写入，存储服务器懂得应用数据库日志；容错目标 AZ+1；多数派读写的原理和好处，和 Raft 的比较；N=6、W=4、R=3；Aurora 的写其实是日志条目，读其实不是多数派读；崩溃恢复时才用读多数派：VCL 和 VDL；保护组和快速重新复制；只读副本；教训

主讲：Robert Morris（2020 年春季 6.824 第 10 讲）
资料来源：2020 讲义、FAQ、课堂录像、论文 Amazon Aurora: Design Considerations for High Throughput Cloud-Native Relational Databases（Verbitski 等，SIGMOD 2017）

一、为什么读这篇论文

  • 成功的近期云服务，为客户解决了严重的问题；
  • 好的设计带来巨大回报（表 1）；
  • 展示了通用存储抽象的局限；
  • 有很多关于真实云基础设施里什么重要的细节。

二、引出 Aurora 的故事（讲义作者的理解）

Amazon EC2

面向网站的云计算：可以租虚拟机（"实例"），运行在 Amazon 数据中心的物理机上，虚拟的本地磁盘存在直接连接的物理磁盘上；客户在 EC2 上跑 web 服务器和数据库。EC2 很适合 web 服务器：负载大了就多租实例；崩溃了无所谓，它们无状态，数据在数据库里。EC2 不太适合数据库（比如 MySQL）：扩展选项有限，只能加只读的数据库副本；容错有限，物理机坏了，磁盘跟着坏；只能定期把数据库备份到 Amazon 的大容量存储服务 S3。

Amazon EBS（Elastic Block Store）

  • 即使 EC2 实例崩溃也仍然可用的块存储；对 EC2 实例来说看起来就是一块磁盘，可以在 EBS 卷上挂载比如 Linux ext4。
  • 实现为成对的带磁盘的服务器，用链式复制，配置管理器基于 Paxos。
  • 两个副本在同一个"可用区"（AZ，机房或数据中心）里，为了速度，因为客户端的每个写都要等两台 EBS 服务器。
  • 对 EC2 上的数据库，容错比本地存储好得多！数据库的 EC2 实例崩溃了，就在另一个实例上重启它，挂上同一个 EBS 卷。
  • 注意：同一时间只有一个 EC2 实例能用一个 EBS 卷，EBS 不是共享存储。

数据库放在 EBS 上的缺点

  • 通过网络发送大量数据：日志和脏数据页都要发，即使只改了几个字节，数据页也很大；
  • 容错不够：两个副本不够，但更长的链又太慢！而且两个副本在同一个 AZ，容易受火灾、水灾、停电、互联网连接中断的影响。

三、事务数据库怎样使用存储

论文假设你知道数据库怎样工作、怎样使用存储。这里是一个通用事务数据库的概述，单台机器。

例子：银行转账，从 x 的账户转 10 美元给 y 的账户：

x = x + 10
y = y - 10
  • 锁住 x 和 y，提交完成后释放；
  • 数据在磁盘上的 B 树里；缓存的数据页；
  • 事务运行时，数据库服务器只修改缓存的数据页，并把更新信息追加到预写日志（WAL，Write-Ahead Log），论文的 "redo log" 就是 MySQL InnoDB 的事务日志。
LSID  TID  key  old  new
101     7    x  500  510     (generated by x = x + 10)
102     7    y  750  740     (generated by y = y - 10)
103     7  commit            (transaction finished)
  • WAL 安全落盘后提交：释放 x 和 y 的锁，回复客户端；
  • 之后再把修改过的数据页从缓存写到磁盘，以释放日志空间、允许缓存淘汰。延迟写对性能至关重要，可以"吸收"多次写，因为页很大；
  • 崩溃恢复：对日志里所有已提交的事务重放"新"值（redo）；对日志里未提交的事务重放"旧"值（undo）。

FAQ：为什么 MySQL 这类传统数据库每个事务要产生很多磁盘 I/O？它们要更新磁盘上存放表和索引的 B 树等数据结构，还要往磁盘日志追加条目；而且数据库和磁盘之间通常还有一个文件系统，它也要写自己的 i-node、空闲块位图、自己的日志。数据库在事务的所有日志条目安全落盘之前不能回复客户端，它会把几个并发事务的日志写合在一起以减少磁盘操作（叫组提交，group commit）；对数据本身（B 树等）的写可以晚些做，通常也是这样，希望把多个事务对同一部分的写合成一次磁盘写。

下一个想法：图 2，Amazon 的 Multi-AZ RDS

数据库即服务，而不是客户自己在 EC2 上跑。目标：通过跨 AZ 复制获得更好的容错。对数据库的 EBS 卷做 EBS 层面的镜像：数据库服务器的每次 EBS 写，都发给本地 EBS，也发给由另一个 EC2 实例驱动的镜像 EBS；镜像日志和所有脏数据页。数据库的写要等全部四个 EBS 副本回复：延迟长，数据多；但因为有第二个 AZ，容错更好。

四、Aurora 全景

DB clients (e.g. web servers)
     |
[one database server, in an EC2 instance, dedicated to one customer]
     |
[6 storage servers holding 6 replicas of a volume; volume private to this DB server]

Aurora 用两个大想法：

  • 多数派写入：容错更好，又不用等太久；
  • 存储服务器懂得怎样把数据库日志应用到数据页上：所以只需要发（小的）日志条目，不用发（大的）脏页；发给很多副本，但数据量不大。

表 1 总结了结果：吞吐提高 35 倍！很难判断硬件资源是否相当；很难说多少收益来自多数派写入、多少来自只发日志；也许主要是因为发送的数据少得多。显然网络容量是主要的限制因素，因为这个设计减少了网络使用，却增加了 CPU 和存储的使用。FAQ：主要原因是镜像 MySQL 通过网络发送的字节多得多。普通 MySQL 以为自己在写本地磁盘，每个事务要做一堆大的 B 树页写，即使只改了几个字节，写出去的也是整个文件系统块，比如 8192 字节，镜像要把这些块发给四台 EBS 服务器并等它们写盘；Aurora 只发小的日志记录，不比真正修改的字节大多少。缺点是复杂和不通用：存储服务器很了解数据库，能把日志记录应用到存储的数据上，实际上把数据库的一大块功能挪进了存储系统，Aurora 的存储系统大概除了 Aurora 什么都干不了。

Aurora 存储的容错目标

  • 即使一整个 AZ 死了也能写；
  • 即使一个 AZ 死了、再加一台存储服务器死了也能读：这时不能写，但仍能服务只读请求，并创建更多副本；这叫 "AZ+1"；
  • 平滑地容忍暂时变慢的副本（这很重要）；
  • 很快地修复死掉的副本（以防再有故障！）。

数据库服务器的故障是另一个问题：在新的 EC2 实例上启动新的数据库服务器。谁来决定什么时候这么做？怎样避免数据库服务器脑裂？论文对此没说多少。新数据库服务器从存储服务器上的日志和数据恢复。

五、多数派读写

这是一个古老而被广泛使用的想法（Gifford，SOSP 1979）。目标：容错的存储，即使有一些故障也能读到最新的数据。通常用于简单的读写（put/get）存储。

  • N 个副本；
  • 写到任意 W 个副本；
  • 从任意 R 个副本读；
  • R + W = N + 1。

最简单的情况：N=3、W=2、R=2。重叠保证读多数派至少包含上一个写多数派里的一台服务器。怎样判断哪个是最新的拷贝？不能对内容投票！读多数派里可能只有一台服务器是最新的。写者给它的写分配递增的版本号，存储服务器必须记住每个数据项的版本，读者取收到的 R 份拷贝里版本号最大的。如果读或写凑不齐多数派呢？继续试。

多数派读写存储系统的好处

（和比如链式复制相比。）

  • 平滑地处理死掉的、慢的或被分区的存储服务器：不必等，不必检测故障，没有超时；这对 Amazon 的远程 AZ 和暂时变慢的服务器很重要；存储服务器之间没有脑裂的风险。
  • 可以调整 R 和 W，让读或写更快（但不能两者都快）。

但是：

  • 不在写多数派里的服务器必须追上（比如 Aurora 的 gossip）；
  • 只能容忍 min(N-W, N-R) 次故障；
  • 需要版本号，所以最适合单写者。

注意：Raft 也用多数派

领导者只有在多数节点收到后才能提交；读写重叠保证新的 Raft 领导者能看到每个已提交的写。Raft 更强：它能处理复杂的操作，因为它给操作排序；它能自动换领导者而不脑裂。

Aurora 需要怎样的 N、W、R

N=3、W=2、R=2，每个副本在不同的 AZ？不满足 AZ+1 的目标，那样只剩一个副本。Aurora 用 N=6、W=4、R=3：三个 AZ 各两个副本。一个 AZ 故障，剩下的仍构成写多数派（4）；再坏一台，剩下的仍构成读多数派（3）。

六、Aurora 的写和读

Aurora 的多数派写长什么样

不是经典的多数派写：数据库服务器对存储服务器的写不修改已有的数据项！一次写是一个新的日志条目，属于一个正在进行的事务，或者是一条提交记录。Aurora 把每条日志记录发给全部六台存储服务器。事务提交要等这个事务的所有日志记录都到了一个多数派上，表述为 VDL >= 事务的最后一条记录，这样崩溃后直到这个事务的每个事务都能恢复。提交，然后释放锁，回复客户端。

存储服务器怎样处理进来的日志条目（"写"）

起初只是存下来，为每个数据页维护一个相关的待处理日志条目列表。所以存储服务器的状态是：每个数据页的一个（旧）版本，加上把这一页更新到最新所需的日志记录列表。存储服务器在后台应用日志记录，或者在读需要时应用。FAQ：这就是 3.2 节说的把 redo"卸载"给存储：大多数数据库服务器读出旧数据页、修改、写回整页，即使只改了几个字节也要搬很多数据；Aurora 只发日志记录，由存储服务器解释日志条目、修改存储的数据页。

普通的 Aurora 读长什么样

不是多数派读！Aurora 数据库服务器因为缓存缺失需要一个数据页（写是日志条目，读得到的是数据页）。它要找到一台拥有所有相关日志条目的存储服务器。数据库服务器跟踪每台存储服务器的 SCL（Segment Complete LSN）：每台存储服务器拥有所有 <= 它 SCL 的日志条目，并报告给数据库服务器。数据库服务器从任何 SCL >= 最高已提交 LSN 的存储服务器读，那台存储服务器可能要先把一些日志记录应用到数据页上。（这就是因为只有一个写者，数据库服务器自己知道哪些写到了哪里，所以不需要多数派读。2026 年课前问题页里保留着 Aurora 的问题：第 4.1 节第二段说"数据库维护的运行时状态让我们可以用单段读而不是多数派读"，数据库需要维护什么运行时状态才能避免多数派读？答案就是上面每台存储服务器的 SCL。）

Aurora 什么时候用读多数派

只在崩溃恢复时。崩溃是指数据库服务器崩溃、在另一个 EC2 实例上重启，新数据库服务器使用原来的六台存储服务器。恢复要做什么？对已提交的事务没什么要做的，它们已经在写多数派上。被崩溃打断的事务呢？没法完成，数据库服务器丢了它们的执行状态。

  • 数据库找出最高的日志记录，使得日志到那一点为止是完整的。一条日志记录只要在任何一台能联系上的存储服务器上就算存在。这就是 4.1 节的 VCL（Volume Complete LSN）。
  • 数据库让存储服务器删除 VCL 之后的所有日志条目。
  • 对于在 VCL 之前开始但没有提交的事务，数据库发出补偿性的 "undo" 日志条目。

FAQ：VCL 是怎么回事？日志末尾附近可能有空洞，旧数据库服务器没来得及把它们复制到存储服务器上。恢复软件扫描日志（也许用多数派读），找出每条日志都存在于某台存储服务器上的最高 LSN，就是 VCL，删除之后的条目；这保证不会删掉任何已提交事务的日志，因为没有事务在它所有日志条目都进入写多数派之前提交（回复客户端）。VCL 之前的日志可能包含崩溃前没提交的事务的条目，数据库服务器发出新的日志条目撤销它们的修改。为什么还要 VDL？存储服务器上的数据页其实是某种复杂索引结构（比如 B 树）的一部分，更新 B 树可能很复杂、要多次写不同部分（比如平衡、腾出空间），一次复杂的修改有时跨越多条日志条目，在这些条目之间看这个数据结构是不一致的；CPL 标出日志里可以安全读取数据结构的点，VDL 是 VCL 之前最后一个这样的点。只读副本只能看对应 CPL 边界（比如 VDL）的数据页版本。FAQ 作者说不完全明白 VDL 对崩溃恢复为什么重要，也许是要先让存储的数据结构处于内部一致的状态，然后才能前滚（重做已提交的事务）和回滚（撤销被崩溃打断的事务）。更清楚的解释见 SIGMOD 2018 的后续论文 Amazon Aurora: On Avoiding Distributed Consensus for I/Os, Commits, and Membership Changes。

七、保护组、修复和只读副本

数据库太大、一台存储服务器放不下一个副本怎么办

数据页被分片成 10 GB 的保护组（PG，Protection Group），每个 PG 单独复制成六个"段"（在六个副本上）。不同的 PG 很可能在不同的六台存储服务器上。日志怎样按 PG 存？数据库服务器只把和某个 PG 的数据页相关的日志记录发给那个 PG。

一台存储服务器永久死掉后怎样恢复复制

要很快，以减少暴露在下一次故障之下的时间。死掉的存储服务器可能存着大约 1000 个 PG 的副本（10 TB），从一台服务器拷 10 TB 到另一台要 10000 秒！但对各个 PG 来说，它们的其他副本很可能在不同的存储服务器上，新建的副本也可以放在不同的存储服务器上。所以每个 PG 可以完全并行地重新复制，各自从不同的源服务器发到不同的目的服务器，并行度最多到存储服务器的数量。存储服务器很多的话，整个工作只要 10 秒。（这和链式复制论文 5.4 节的 rndpar 是同一个思路。）

图 3 里的只读副本（Replica Instance）

  • 客户端可以把只读请求发给它们，减轻主数据库服务器的负载，它很可能是瓶颈。结果可能不反映最近提交的更新！
  • 只读副本从存储服务器读数据页（但不写），并缓存这些数据页。
  • 主数据库服务器把日志发给副本，副本用日志让缓存的页保持最新。
  • 问题：只读副本不知道事务锁住了什么。解法：副本忽略或撤销未提交事务的写，它们能从日志流里的提交标记看出来。
  • 问题：要防止副本看到处于中间状态的 B 树等。解法：大事务里的原子迷你事务。

FAQ：Aurora 和 Spanner 比较

实际上的主要区别是 Aurora 只有一台读写数据库服务器，读写事务多到一台处理不了时，单靠 Aurora 不够；Spanner 不仅分片数据，还能完全独立地运行影响不同分片的事务，有很自然的扩展方式。三个共同的态度：都认为在多个独立的数据中心放副本很重要，保证整个数据中心离线时也可用；都用多数派写来平滑地容忍少数不可达或慢的副本；都支持高读吞吐（Spanner 用基于时间的一致读，Aurora 用只读数据库副本）。一个巨大的区别是 Aurora 是单写者系统，只有一台机器上的一个数据库在写，这带来很多简化，比如日志序号只有一个来源；Spanner 支持多个写者（事务来源），有分布式事务和加锁系统（涉及两阶段提交）。Aurora 一个模糊的地方是怎样处理主数据库服务器的故障或分区，系统要切换到另一台服务器，同时排除脑裂，论文没说怎么做；Spanner 用 Paxos、避免了任何类似单个数据库服务器的东西，更清楚地能在自动恢复故障的同时避免脑裂。

Aurora 怎样在 50/50 的网络分区里避免脑裂？一半或另一半会包含数据库服务器（图 3 的 Primary Instance），只有那一半能工作，因为只有数据库服务器服务客户端请求；它联系不上写多数派（4 of 6，超过 50%），所以不能写；能联系上读多数派，所以能读。FAQ 作者认为唯一可能脑裂的情形是出现两台数据库服务器，比如以为数据库服务器坏了、启动了替代者，而旧的其实还在运行；这大概是个真实的问题，Amazon 大概有解法，但论文没解释。

八、教训

  • 预写日志怎样和存储系统相互作用；
  • 用多数派平滑地处理慢的或坏掉的副本；
  • 跨层优化，数据库和存储服务器一起：带来巨大的性能提升，但存储不再通用；
  • 云基础设施主要关心的一些细节：AZ 故障，因此需要跨 AZ 复制；单个副本暂时变慢；网络是比 CPU 或存储更严重的约束。
