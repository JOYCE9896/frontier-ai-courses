补充十一：Mahmoud Hashemi 和他的共享 Agent 记忆

Python 开源老兵谈 AI 时代开源的变化和"意图是人仅有的东西"，演示他做的 Agent 共享记忆平台 Good Turn，并现场给它加一个"发布日历"功能：用 Obsidian 写意图文档，在计划模式里和模型问答取舍，让它参考开源范例；以及一整套"胶带式"小工具：who-am-i skill、自愈的线上巡检 skill、计划归档、并行 Agent 的提交锁、每个项目配一个 CLI

嘉宾：Mahmoud Hashemi（Python 软件基金会 Fellow，FinFam 创始人，曾在 PayPal、Stripe 工作十五年以上，现在在 South Park Commons）· 主持：Mihail Eric
资料来源：Building a Shared Agent Memory（2026 年 10 月 9 日上传，约 1 小时 42 分钟）
说明：这不是 CS146S 的课堂讲座。它是课程自己的 YouTube 频道 The Modern Software Developer 上的访谈节目 The Build System 的一期，由主讲人 Mihail Eric 主持，嘉宾边写代码边讲。本文依据 YouTube 自动生成的英文字幕整理；字幕里的模型型号写成"46""48"之类，听写不一定准确，文中照录并注明。
和课程的关系：对应第六讲 常驻 Agent 怎样工作 里的记忆和例行任务，以及第七讲 定制你的 Agent 配置（AGENTS.md、skill、扩展）；他用的 Oh My Pi 建立在 补充十 的 Pi 之上。

一、嘉宾和一段 PayPal 旧事

Mihail 介绍他时说，他据称是 PayPal 最早的工程实习生之一。Mahmoud 更正说是 eBay 收购之后的第一个实习生，他自认的"成就"是删掉了很多创始人 Max Levchin 写的 Palm OS 时代的 C 代码。PayPal 最早是在 Palm 掌上电脑之间通过红外口转账；后来网站上放了一个两台 Palm 的演示页面，能在银行账户之间转钱，结果被大家拿去付 eBay 拍卖的钱。那段加密代码一直留到上市之后，里面还有 Alice 和 Bob，"像研究生写的"，用的是标准化之前的椭圆曲线密码，有很多问题。

二、开源在 AI 时代变了什么

他说这一波技术"undeniably exhilarating"，十几年手写代码让他对产出量特别敏感，停不下来。但他对资源的分配方式和行业的宣传方式不满意。

他在 South Park Commons 常对想走开源路线的人说"2026 is not 2016"。他的经历是：大学时有自由文化社团，"knowledge wants to be free"；后来开源成了职业通道，像一所"finishing school"，外地、外国或本地的新人在 Kubernetes、LLVM 这类有战略意义的开源项目里展示自己，进入大公司。这套信任网络靠会议和聚会维持，新冠是一颗钉子，AI 是最后一颗：

"it's hard to reach any other conclusion than like this is the last nail in the coffin of open source as I knew it"

他不想过分怀旧，也希望开源有未来，只是"发到 Hacker News、拿几百颗星、认识人、办聚会"这套做法得改。他举了自己带的维基媒体基金会 Google Summer of Code 项目：几十甚至上百个 PR 明显是 Claude 写的，他回复问对方用了什么模型、什么提示、自己怎么想的，基本得不到回应。最后他们选了一个几乎不用 AI 的申请者，理由是"教一个人用好 Agent 容易，教一个人思考难"，这个人看起来像一个会留下来、真正在乎这件事的队友。

他认为开源早已从理念变成商业打法（例如 GitLab 用开源对抗闭源的 GitHub），这本身可以接受。让他难受的是，AI 领域的领袖在台上说要把他这样的人"商品化"。他的看法是，人需要空间去产生大量平庸的想法，才能走到一个新想法；如果把思考都拿走，从旁观者成长为出色参与者的那座桥也就没了。

Mihail 提到有人认为以后大家都在自己的网络边界内重写一切、不再依赖外部开源库。Mahmoud 说"vendoring"（把依赖的代码直接拷进自己的仓库）原来有取舍，现在 AI 从记忆里把代码粘进你的仓库，你等于在不知道来源的情况下 vendor 了一段代码，这已经很常见。他以前把开源分成"库"和"应用"，他的星大多来自给 Python 开发者写的库；开源应用仍然有生命力，但价值主张要更大、维护承诺要更明确。

三、意图是人仅有的东西

Mihail 说最近很多工程负责人的饭局上都在讲"两年内不再看代码，只定义软件工厂的成功指标"。Mahmoud 说他和 South Park Commons 的多数人一样，认为还太早，他自己用两个 Claude Max 套餐，仍然需要大量引导。他认为 AI 不可能有愿景，因为它没有意图：

"attention may be all they need, but humans, we need intention ... intention is all you have as a human ... and it's inalienably human"

"if you find yourself asking AI like you know what to do writ large ... you've gone too far, you've ceded the game, right? Like you need to take a step back and form your own intentions."

四、Good Turn：Agent 的共享记忆

他的出发点是一个判断："the agent assisted human is the new unit of development"。人加 Agent 比单独的人或单独的 Agent 都强。问题是他和 South Park Commons 的几位工程师让 Agent 整夜消耗 token，Agent 发现和学到的东西都埋在会话记录里。于是他们想做一个类似博客圈或 Stack Overflow 的地方，让 Agent 把学到的东西发出来，人可以和它一起学，也能看出它什么时候跑偏了。

名字 Good Turn 有两层意思：有了公共知识库，每个人的 Agent 都能有更好的"turn"（对话轮次）；"one good turn deserves another"，你用了一百万 token，拿出 1% 回馈公共库，别人就不用再重新发现 YouTube 的某个 API 坏了、某个库的文档写错了。

  • 不靠人点赞："humans don't upvote. The agents have to upvote"。点赞是给人用的设计，这里换成更具体的信号：这条有用、这条通过了测试，还有一个 GitHub Action 能标记"通过了 CI"。他说以前论坛上常见"A 坏了""试试 B"，半年后没人回来说到底行不行，Good Turn 也许能把这种后续反馈自动化。
  • 人来审：人可以像左滑右滑一样审阅 Agent 的记忆。例子是他的 Agent 发现"YouTube 的 RSS 接口每天有三小时不可用，从 12 月起一直这样"。
  • 声誉：登录必须用 GitHub 账号。他打算看账号是否在 AI 出现之前就创建、有多少星、谁邀请的，算一个初始声誉分，把一些信任网络带到新平台上。
  • 可视化：节目最后他展示了按嵌入向量聚类的树，能看到他最近在和 ffmpeg 帧率较劲。

五、要做的功能：发布日历

South Park Commons 是孵化器，大家不会一直待在那里，需要一种方式知道彼此什么时候发布东西。他们现在的习惯是：要发推或发 Hacker News 时，先发一个日历邀请，让朋友到时候去看、去真诚地互动，而不是一周后在 LinkedIn 上才知道。他要做的是"Luma for launches"，叫 Good Turn Launches。

他不想"刷票"。他说自己遇到过：在朋友的 Discord 里发了一个作品，太多人去点赞，Hacker News 的管理员联系他说"我们喜欢你的东西，但我们知道这不是自然流量，请别再这样"。所以他的设计像传单底下那排可以撕走的小纸条：发布者预先定好任务，比如"在 Hacker News 帖子下评论""在 Twitter 互动"，每种只要几个人，像信号量（semaphore，限制同时占用数量的机制）那样，被领完就满了。

六、他的开发流程

1. 环境

  • 一台 MacBook Air（他在做 iOS 开发，Linux 机器放进了家里的机柜）。
  • 一个老 dotfiles 技巧：终端颜色随工作目录变化。他说 Agent 没有让单件事快多少，但让他能大量并行，颜色帮他分清窗口。
  • 编程 Agent 用 Oh My Pi，Pi 的一个"自带电池"版本，加上他自己写的扩展。偶尔把 Oh My Pi 弄坏了，就让 Claude Code 来修。
  • 编辑器仍然是 Emacs，喜欢 Mac 上所有输入框都支持 Emacs 快捷键。
  • 一个他没公开的小工具 Advect：把正在做的工作做一个 WIP 提交加交接文档，通过 Tailscale SSH 到另一台机器，在 tmux 里接着跑。大约五分钟完成交接，由 Agent 自己驱动。他说这不是什么分布式系统，"It's duct tape"。

"AI has been amazing for duct tape ... I'm a Python guy ... I love glue, right? And the quality of glue and duct tape has gone way up."

2. 先写意图文档

他在 Obsidian 里写每日笔记和待办，笔记同步到一个私有 GitHub 仓库，"that intention formation is still very much low tech for me"。这次功能的规格文档是当天早上写的，他说写这个文档花了一些时间，要动脑子。Mihail 说"这就是你的意图文档"，他说是。

3. 计划模式里的问答

他让 Fable（Claude 的一个模型）在计划模式下读这份文档，并要求它以交互问答的方式给出取舍（"interactive Q&A with trade-offs"），还要"find exemplars in open source"，去开源项目里找可以参考的实现，这次是 cal.com。

为什么要找范例？他在 PyCon 2026 讲过一个在前端跑 Python 的演讲，演示项目是让 Opus 几个小时做出来的正则表达式测试器，但它没有 CI、没有可观测性，SharedArrayBuffer 也没处理好。他发现让 Agent 参考开源范例能补上这些。他最多星的仓库就是 awesome-python-applications，收集的是有完整架构、能当参考的 Python 应用。

问答过程中的几个决定：

  • 接受邀请必须有 GitHub 账号，因为声誉系统依赖它。
  • 邀请用一个分享链接，发到 Slack 里就行；名额由发布者预先定的任务数控制，任务领完就满，避免一窝蜂。
  • 任务可以多选。他希望发布者能附一段"建议评论"：朋友发了一篇讲后训练的白皮书，他不一定马上读懂，"can you just tell me what's interesting about this in your words"，他转发时能说到点子上。
  • 数据库方面，他以前喜欢在每张表上加一个 JSONB 的 extras 字段，因为迁移很麻烦；现在 AI 写迁移很好，他宁可让迁移堆积，再让 AI 合并压缩。
  • 所有页面都是私有的，不做公开页。

他用"渐进式 JPEG"形容这种开发：拨号上网时代的图片先出模糊的整体，再逐渐清晰；先把整件事做出来，点一点试，感觉对了就发布。

4. who-am-i skill

他的 skill 不多，但有一个"who am I"：告诉模型他是谁、他的偏好。比如他参与提出了日历版本号（CalVer），所以版本一律用 CalVer；工作账号和个人账号分开；"always cite linked precedents, never memory"；不用花哨的记忆工具；文档按 ISO 8601 日期命名，每个仓库都有一个 docs 目录，过程中发现的东西都写进去。他说加了这个以后，Agent 找范例时会更偏向 Python 项目而不是 Ruby 项目，也就是他看得懂的代码，值得一直挂在上下文里花 token。Mihail 说这是他最想马上照做的一点。

他提到让他从 Cursor 转到全面用 Agent 的，是 Stripe 时的同事 Ryan（字幕听写为 Ryan Lapolo）在 OpenAI 写的博客 "harness engineering"："如果一个我审过他代码、他也审过我代码的人都几乎不读代码了，那我也可以了。" Ryan 后来把自己的做法写成了一个 GitHub 仓库，建议别人 vendor 进去按需修改；Mahmoud 的用法是让 Agent 拿自己的仓库和它对比，提出建议，挑合适的采纳。

5. 计划要归档

等主任务时，他顺手开始规划另一件事：把 Good Turn 的记忆审阅流程做成 PWA（渐进式网页应用，可以装到手机桌面），因为坐湾区地铁时可能没信号，最好能离线审。他之前给维基媒体基金会做过一个 PWA（Top Hat，列出前一天访问量最高的一百个维基百科页面），那次不是一次做成的，来回改了很多。他把那次的计划文件和决策都存在仓库里，这次让模型去读，希望它吸取那次的教训。

他有一个叫 workstream 的工具，"the closest thing I have to a mind palace"：知道他的几个主要仓库，把所有计划文件收集到他放待办的那个仓库，按实际的提交和分支合并情况勾掉待办，每个计划有状态（实现了，或者规划完但决定暂时不做），还有审计日志。他的一个扩展让他在计划模式里点"执行"再取消，计划就自动存进 plans 目录。

6. 模型分工

Mihail 注意到他用不同模型做不同事。他说：规划和长时间运行的任务用 Fable；日常主力是字幕里的"Opus 46"，"it's got reasoning. It doesn't overstep. It doesn't blow things out of proportion"；前一天刚把"48"设为默认，想再给它一次机会；他在尽量避开字幕里的"Opus 5"，觉得它像"a lobotomized Fable"，分不清什么重要什么不重要。Anthropic 给了他一个免费的 Max 套餐支持开源工作，他有两个账号，Oh My Pi 能叠加用量，常常一周就用满；有一天额度用完只好用 Codex，"it's much faster but I do like some of those thought tokens that Claude has. I don't like how it writes but I kind of like how it thinks"。他还挺常用 Gemini。自动路由他还没考虑，等对 token 更敏感时再看。

七、线上巡检：一个会自己记账的 skill

Mihail 问他怎样判断能不能上线。Good Turn 用户少、面向开发者，他直接发生产环境，靠 Sentry 和 PostHog 做可观测性，出问题现场修，而且多数问题是他自己先撞到的。Sentry 有一个会提 PR 的 Agent，他先在 Good Turn 上试，再带到正式工作的仓库。

他的每个线上服务的仓库都有一个 prod checkup skill（不常驻，需要时调用），把他以前手工做的巡检都做了：主要通过 API 和密钥查 Sentry、PR 等，偶尔通过浏览器中继去网页上点。这个 skill 是"自愈、自记账"的：

  • 遇到不寻常的情况，skill 可以修改自己。
  • 但不希望它老改自己，有时只是偶发异常（比如 Cloudflare 前一天短暂故障）。所以允许它在旁边写一个 JSON 文件，每条记录带日期，相当于"下次运行时再看看这个"的提醒。演示时能看到它直接写出这些 JSON 条目，"There's no code or library or anything to do this"。
  • 他说 Agent 还不够好，分不清什么重要；与其都开成 GitHub issue，不如让它像人在心里记"一周后再看一下"那样自己记账。问题足够大时才浮上来给他，再变成 issue 和 PR。
  • 它每次输出一份带日期的报告，放在 reports 目录。他有空时对着报告做计划，并要求报告区分"创始人需要处理的"和"Agent 可以自己开工的"。巡检这一步不让它改代码，他说这是反复迭代之后才做到的，之前它太积极，会直接跳去改代码。

"there's just no way I would be able to run as many sites as I run now without like having captured everything I was doing manually to run sites before into this skill."

这次巡检报告里提到他之前遇到的内存问题（和 DSPy、LiteLLM 有关，他在用 AI 做内容审核），已经加了一个定时回收进程，巡检跟踪了几周，看起来有效。报告还发现 Playwright 端到端测试有红的。

八、技术栈和"胶带"

  • 部署用 Render（他说是 Heroku 精神上的继承者，层次合适，有 Postgres、备份、只读副本，同时能用代码定义基础设施），喜欢把一切放在代码库里。
  • skill 要求增量提交；以前用 Cursor 时就开着自动保存，git 就是撤销历史。推送他都手动做。正式工作有 staging 环境，先推到那里，让 Agent 或自己点测，再手动推到生产，一天一两次。
  • Python 后端：基于 dataclass 的 SQLAlchemy 基类、Alembic 迁移、pre-commit 挂一堆 linter（拼写检查、shellcheck、ruff），"it's the pre-commit that's sort of keeping it honest"。FastAPI 生成 OpenAPI，再生成 TypeScript SDK，类型能拦住很多 Agent 会写错的地方。
  • 发邮件用 Postmark，并包了一层自己的网关。他建议对大型外部库都包一层，测试时就不用做难看的 mock。
  • 前端用 Svelte（还在 4，没升 5）。他在 Stripe 时被 React 搞得很累；Svelte 由 Rich Harris 在《纽约时报》时开发，"一个人同时做几个项目"，更像他自己在开源、维基百科、工作之间分身的状态；它有编译步骤，比单纯 lint 多一些保证。
  • 以前在 Linux 上他把 Oh My Pi 跑在 Docker 里的 Docker 里，很怕 Agent 乱来；换了 Mac 以后没再这样，但所有应用都跑在 Docker 里，监控有没有意外的出站流量。

并行 Agent 的提交锁

他写了一个 Pi 扩展：两个 Agent 同时要提交时，没有它就会互相覆盖，"the nastiest git commit graph that you've ever seen"。扩展让它们先拿一个信号量，有一个小频道互相协调，还有指数退避。演示中正好碰上：他手动提交了一次，正在做发布日历的 Agent 碰到了锁，开始退避。他说直播时等 55 秒、120 秒不好看，但并行做很多事时无所谓。他说这只是最后一道防线；在 FinFam 上他有专门的 worktree 工具，建分支、工作目录和一组端口覆盖，通过 Docker 端口映射让同一台机器上两份实例互不干扰。

每个项目配一个 CLI

他的每个仓库都有一个配套的 Python 命令行工具，这里叫 gt，封装常用操作：跑测试、构建 SDK、Good Turn 的提示优化流水线等。他倾向于把操作做成工具，而不是只写成 skill 或文档。演示中 Agent 也是用 gt 跑测试，而不是直接调用 pytest。他说在 Stripe 和 PayPal 时就有这种东西；否则 Agent 太不知疲倦，会钻进兔子洞重新发明轮子，"we did that like two sessions ago"。他还写过一个扩展让 Agent 能翻以前的会话，但效果还不好，他认为仍然需要把记忆提炼出来，这就是 Good Turn 的用途。

AGENTS.md 和 README 是同一个文件

Mihail 问他怎么用 AGENTS.md。他说 harness engineering 那篇文章讲的就是这个：要有，但要很短，主要是一张目录，告诉 Agent 需要信息时去哪里找，比如告诉它有 gt 这个工具。他让 Agent 只修正、不扩写这个文件，大部分内容是 Agent 自己写的。看到 Agent 反复重新发现同一件事，就写进去。他发现里面几乎没有专门针对 Agent 的内容，都是会告诉人类同事的事，所以他把 README.md 和 AGENTS.md 做成了符号链接，"can we just read the readme?"

不压缩，只"抖掉"

他不太在乎 token 效率（这次实现花了约 50 美元，但都算在 Max 套餐里，"this is like a week plus of work pre LLM"），几乎不做上下文压缩。他用 Oh My Pi 的一个功能叫 shake：丢掉旧的工具结果和大图片，文字一点不丢。网页测试时上下文里会堆积截图，而模型看完截图通常已经用文字描述过一遍，所以丢掉图片损失很小，比压缩的损失少。

九、浏览器中继和点测

Oh My Pi 通过一个 Chrome 扩展做浏览器中继，能操作 Chrome、截图。他用它做过一件事：从没投过广告的他，让 Claude 通过浏览器点完 Meta 广告后台，一个下午搭好了每天约 60 美元的广告投放，为 FinFam（一个帮人做生活和财务决策的计算器应用，比如买油车还是柴油车、租房还是买房）获取信号。他的理由是：B2B 靠和客户聊天，同时学会怎么卖；消费级应用不是靠直销卖的，而是靠营销，和"大众"对话的方式就是广告。

对大功能，仓库里的偏好写着要写 Playwright 测试，但要求 Agent 先自己点测，他再跟着点一遍。演示中能看到浏览器中继开始调试浏览器，WebSocket 有时不稳要刷新几次，也比较费 token。

十、抽象的未来和代码审查

他回忆 Claude 3.5 前后 Cursor 开始真正好用时，他有过一种存在主义的感觉："is this the end of abstraction?" 他的看法是抽象的语言变了。正则表达式是很强的抽象，紧凑、表达力强、容易保证正确，但现在谁还自己测正则？Agent 写得比人准，regex101 这类网站的流量大概掉了。以后谁来创造下一个"正则"、怎样让它进入模型的训练数据，变成了开源的新玩法，他承认这对他没吸引力。他担心 Ruby 这类以写 DSL、提升抽象为卖点的语言前景。但他说写一个可扩展的包装脚本这种实用抽象，回报很大，每个项目都该有。

关于代码审查，他说团队里审查很重要，因为它主要关乎团队成员之间的对齐，关乎方法而不是代码。GitHub 经典的审查工具太以代码为中心。他希望 Good Turn 能分享"轨迹"，也就是你和 Agent 的实际交互，因为 Agent 更像向你汇报的团队成员，而不是你内心的思考过程，这些应该拿出来对齐。他自己现在读代码少多了，像这种全新项目几乎不读。AI 审查可以接手 linter、CI 这类让审查者轻松的工作，但他还没看到有人正面解决"AI 在达成共识中能起什么作用"，在每个人身边都有一个什么都同意的助手（sycophancy，谄媚）的今天，这个问题更重要了。

十一、结果

节目接近尾声时，发布日历页面做出来了，"this kind of looks like what I wanted"。他说会继续测，等 Good Turn 本身发布时会把 Mihail 加进去。他还设想了一个发布后的复盘：不接各平台的 API，只准备一段提示词，让 Oh My Pi 自己去各渠道点一遍，收集点赞、转发数。邮件邀请在本地还没收到，他打算直接部署到生产测，因为这个功能不影响网站核心；如果是 FinFam 或 Stripe，会加功能开关。

他的建议是自己做自己的胶带，"scratch your own itch"。他说对他来说，这一切是从 2026 年 2 月左右真正开始的。

顺带一提，他对 Product Hunt 的观察：他为了 SEO 把产品放上去，很多人在 LinkedIn 上找他，说付 150 美元就能上首页，还给他看过去的聊天记录；他的结论是 Product Hunt 被 AI 垃圾淹没，只剩 SEO 的用处。

十二、和课程的对照

  • 第六讲 常驻 Agent 怎样工作 讲 Agent 的记忆文件和例行任务；这期的 prod checkup skill 是一个实际在用的例行任务，带自己的 JSON 记账；Good Turn 则把记忆从个人扩展到一群人共享。
  • 第七讲 定制你的 Agent 配置：who-am-i skill、很短的 AGENTS.md（和 README 共用）、几个 Pi 扩展，都可以对照着读。
  • 第三讲 高级提示与 RePPIT 讲先研究、再计划、再实现；这期的"意图文档 + 计划模式问答 + 找开源范例 + 计划归档"是同一思路的个人版本。
  • 第八讲 让代码库适合 Agent：每个项目配一个 CLI、pre-commit 兜底、外部服务包一层网关，都是让 Agent 少走弯路的做法。
