第十一讲：后台 Agent

从同步地一次做一件事，到异步地同时派出很多任务；告别本地开发环境，自己搭一个"接任务、起环境、交 PR"的后台 Agent 平台，沙盒服务商，一个 Slack 机器人的架构，子 Agent 和 Agent 团队，生成-验证和"主模型加聪明朋友"两种多 Agent 模式，以及管理多个 Agent 需要的能力

主讲：Mihail Eric
资料来源：课件（2026 年 11 月 10 日，共 16 页；这一讲没有公开转录，本文依据课件整理，包括课件里的图片页。课件文字很少，讲者口头展开的内容这里没有）
课程推荐阅读：From Migration Scripts to Agent Fleets（Spotify）、From Slack Message to Review-Ready PR（Stripe）、Giving Agents the Tools to Prove Their Work（Ramp）、Inside an Open-Source Software Factory（LangChain Open SWE）

二、为什么要后台 Agent

课件先回顾了编程 Agent 能力的三个阶段，以及每个阶段大致带来的效率提升：

阶段形式效率提升
2021Tab 补全：编辑器里补全下一行约 15%
2024同步完成单个任务：开发者盯着一个 Agent 做完一件事约 25% 到 35%
2026 年以后后台完成多个任务2 倍以上

第三阶段的变化在于"异步"和"并发"：开发者把多个任务同时派出去，Agent 在后台各自做，开发者不用守着。能同时跑的任务越多，并行度越高。课件提到，第十讲的 Agent 代码审查已经是这种用法：PR 一提交，几个审查 Agent 在后台同时开始工作。

三、告别本地开发环境

后台 Agent 不在开发者自己的电脑上跑，而是在云端的独立环境里跑。课件把这叫做 "End of Localhost"，列了四点好处：

  • 不用再处理依赖安装的麻烦，没有"在我电脑上能跑"的问题。
  • 环境可以复现、可以控制，每次都从同一个状态开始。
  • 测试在专门的机器上跑，不占开发者的电脑。
  • 想开多少个就开多少个，并行度几乎没有上限（课件给"无限"加了引号）。

四、自己搭一个后台 Agent 平台

课件说，很多公司在自己搭后台 Agent 平台，有的每周完全自主地交出 1000 个以上的 PR。推荐阅读里的 Spotify、Stripe、Ramp 都写过自己的做法。这类平台做的事情可以用一句话说清：接一个任务，起一个接近生产环境的开发环境，把整个流程从头跑到尾，最后交回一个 PR。

它由三部分组成：

  1. 临时的、可复现的开发环境：每个任务一个，用完就销毁。
  2. 完整的访问权限：整个代码库、相关服务、构建系统、文档、代码搜索、日志、监控指标，常常还有从生产环境导出的只读数据。
  3. 默认处理的工程步骤：构建、lint、跑测试、推送改动，平台自动完成，不用 Agent 每次自己想起来去做。

课件的结论是：这样的平台是大规模并行使用 Agent 的关键。

一个开源的例子：Open SWE

课件放了一张架构图，来自推荐阅读里 LangChain 的开源项目 Open SWE。从左到右是：

  • 触发方式：Slack、Linear、GitHub 上 @ 机器人、网页仪表盘、命令行或桌面端（图上标注这一种不在沙盒里运行）、定时任务。
  • 运行时：托管的 Deep Agents 运行时，带对话线程和检查点、一个收件箱（运行中途可以追加指示）、模型循环。上面跑三种任务：agent（实现、测试、开 PR）、reviewer（只读的 GitHub 审查）、review-scout（写一份给人看的改动导读）。
  • 沙盒：LangSmith 沙盒，每个线程一台 Linux（4 核 CPU、16 GB 内存），通过 GitHub 凭证代理访问仓库（Agent 拿不到真正的令牌），持久保存，空闲 2 小时休眠、7 天删除，不会在不告知的情况下被替换。
  • 上下文：AGENTS.md、Skill、记忆和整理器、缓存的系统提示词。
  • 护栏：改 CI 工作流文件需要人批准；只能开 PR（open_pull_request），不能直接推主分支；PR 先以草稿形式提交，满足条件才转为可审查；外部不可信的内容（比如 issue 正文）单独隔开，防提示词注入。
  • 输出：GitHub PR，接着自动跑一次审查，再到 Slack 里请人审，另外有一个 /baby-sit CI 命令盯着 CI 跑完。

这里面很多部分前面几讲都讲过：AGENTS.md 和 Skill（第五、七讲）、审查 Agent（第十讲）、凭证代理和不可信内容隔离对应第七周的安全主题。后台平台把它们装进了同一个系统。

沙盒服务商

不想自己管机器，可以用现成的沙盒服务。课件列了 Coder、Vercel Sandbox、Daytona，以及 E2B、Modal 等。

五、一个 Slack 机器人的架构

课件还放了一张公司内部 Slack 机器人的架构图（名叫 HAL）。它的结构是：

  • 入口：Slack 里的 @提及、私信和线程回复，每条消息开始一轮处理。
  • 运行时：OpenClaw，跑在 AWS EC2 上，模型是通过 Amazon Bedrock 调用的 Claude。中间是 Agent 循环（推理、用工具、观察、重复），上面加载上下文和 Skill（线程历史、指令、操作流程）。
  • 工作区和记忆：克隆的代码仓库，每个线程一个 Git 工作树；持久记忆用 OpenViking 存取。会话、文件和记忆都存在 EFS 上，机器重启也不丢。
  • 连接的系统：工具层用 MCP 和命令行，连到 GitHub、Linear、Notion（知识和工作），Datadog、Postgres、Judgment、PostHog（生产环境的数据，只读），结果再发回 Slack，附报告和分支链接。
  • 边界：凭证按需限定范围；代码改动在隔离的工作树里做；代码改动必须经过人审查。

图下面的一句话概括了这种设计：持久的运行时，加上持久的上下文，再加上工具，Agent 就能做超出一轮对话的工作。

六、多 Agent 的几种模式

1. 子 Agent 和 Agent 团队

课件用一张图对比两种结构：

子 AgentAgent 团队
谁分配工作主 Agent 派生每个子 Agent主 Agent（组长）建团队，把任务放进共享任务列表
成员之间互不通信，各做各的成员互相沟通，自己从列表里认领任务
结果怎样回来每个子 Agent 把结果报告给主 Agent通过共享任务列表和互相沟通汇总

课件给了 Agent 团队的两个用法，原文是给 Agent 的指令：

Users report the app exits after one message instead of staying connected. Spawn 5 agent teammates to investigate different hypotheses. Have them talk to each other to try to disprove each other's theories, like a scientific debate. Update the findings doc with whatever consensus emerges.

Create an agent team to review PR #142. Spawn three reviewers: 1) One focused on security implications 2) One checking performance impact 3) One validating test coverage. Have them each review and report findings.

第一个是排查 bug：五个成员各自验证一种假设，再互相反驳，最后把共识写进文档。第二个是审查 PR：三个成员分别看安全、性能、测试覆盖。两者都需要成员之间交流，所以用团队而不是互不相通的子 Agent。

2. 生成-验证

这一页和下一页的图引自 Cognition 的 Walden Yan（原帖）。生成-验证（generator-verifier）的图里，左边是一个 Agent 的上下文从上往下变长：计划、写代码、报错、测试、创建 PR。旁边标着"上下文腐化"（context rot）：上下文越长，模型越容易忽略或混淆前面的信息。PR 提到 GitHub 后，由另一个 Agent 只看代码去找 bug。它的上下文是干净的，没有被前面的计划和试错过程影响。找到的 bug 再交回原来的 Agent，讨论哪些是真问题。

3. 主模型加聪明朋友

另一种模式里，主模型持有完整上下文，自己干活；遇到难题时去问一个更强的模型（"聪明朋友"）。聪明朋友一开始没有上下文（图上画成虚线框），所以第一次常常回一句"需要更多上下文"。主模型就去读文件、grep，把相关内容补齐再问一次，拿到答案后继续工作。这样大部分 token 花在便宜的主模型上，贵的模型只在需要时被问几次。

七、管理多个 Agent 需要的能力

最后一页讲开发者自己要练的"元技能"：

  • 委派和多线程：同时管几件事。
  • 计划、界定范围、设计结构：对每个任务保持掌控和上下文；动手之前花时间判断任务有多复杂；把窗口分成做计划的和处理快速任务的两类。
  • 读代码和读计划：代码审查是新的瓶颈（第十讲的结论）。
  • 逐步增加 Agent 数量：先用好一个，再慢慢加到多个。
