作业：第 1 到第 4 周

拆解一次真实的 Claude Code 会话，为一个第三方 API 写 MCP 服务器，写一个 Skill，给一个陌生仓库写 AGENTS.md：每份作业要做什么、怎样评分、要注意什么

资料来源：课程作业仓库（截至 2026 年 10 月 23 日公开了第 1 到第 4 周；课程共 6 次作业，后两次发布后再补）
对应讲次：第 1 周对应第二讲，第 2 周对应第四讲，第 3 周对应第五讲，第 4 周对应第七讲

一、通用说明

作业都在同一个 GitHub 仓库里，每周一个目录（week1/ 到 week4/），里面有 assignment.md（题目）和 writeup.md（要填的报告模板，所有 TODO 都要填掉）。环境是 Python 3.12，用 conda 建环境、用 Poetry 装依赖。提交方式：把自己的作业仓库推到远程，加三位老师和助教（mihail911、isaackann、vdaita）为协作者，再在 Gradescope 提交。作业占总成绩的 15%。

四份作业有一个共同点：评分看的不是"做出来没有"，而是你对 Agent 怎样看待你写的东西想得多清楚。Agent 只能看到 schema、说明文字和配置文件，看不到你脑子里的意图，所以每份作业都在练"写给 Agent 看的东西"。

二、第 1 周：拆解一次真实的 Claude Code 会话

用代理把一次真实的 Claude Code 会话截下来，读它实际发出的 HTTP 请求。不用造任何新东西，是在"读别人的生产系统"，读到能看出设计决定的细致程度。学习目标：追踪一次生产级编程 Agent 的会话，理解调用结构；看清提示词、工具 schema 和模型回复在一个不平凡的编程任务中怎样相互作用；想清楚哪些做法你会照搬到自己的 Agent 里，哪些会改。

准备工作

要先有 Claude Code（斯坦福学生用 SUNet 账号申请），记下 claude --version。然后装 mitmproxy（macOS 上 brew install --cask mitmproxy，或 pip install mitmproxy），以反向代理模式启动： 

mitmweb --listen-host 127.0.0.1 --listen-port 58888 \
        --web-open-browser --mode reverse:https://api.anthropic.com \
        -w session.flows

发到本地 58888 端口的流量会被转发到真实的 API，检查界面在 http://localhost:8081。用反向模式是因为可以让 Claude Code 指向一个普通 HTTP 本地地址，不用装 CA 证书。-w session.flows 把所有流量存盘；要在任何 git 仓库之外的目录运行，免得不小心提交。

再在要用的仓库里建一个项目级的 .claude/settings.json： 

{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:58888",
    "ENABLE_TOOL_SEARCH": "true"
  }
}

题目特别警告：不要写进用户级的 ~/.claude/settings.json，否则你机器上所有 Claude Code 会话都会被截进来，而且关掉代理后它们都会连不上。开一个会话，确认 mitmweb 里出现了 POST /v1/messages。做完后删掉这个配置，停掉代理。

五个部分

  • 第一部分：截一次会话（15 分）。会话要同时满足四条：改动至少两个文件；至少失败一次，要有一段错误恢复的过程（故意弄坏一个测试是最可靠的办法）；长到需要计划，Agent 要明确做计划（任务清单、计划模式或计划文件），而不是一次工具调用了事；用你自己的仓库。题目给的点子：删掉一个被其他模块引用的函数，让 Claude 恢复功能并让测试通过；给一个小 Web 应用加接口和测试，再要求它在一个你没装的依赖版本上让测试通过；重命名一个模块，让它更新所有 import，再跑 lint 和测试；要一个需要陌生库的功能，逼 Agent 先去查 API。把请求体存成 JSON 留在本地，不提交，但后面每一部分都要从里面找证据。
  • 第二部分：注释系统提示词（25 分）。把 system 块和所有 system 角色的消息拆成段，每段回答"这段在换取什么行为？在防哪种失败？"是注释不是摘要。至少覆盖：结构（主要段落、顺序、为什么这样排）；语气和篇幅（控制回复长短和格式的具体措辞，为什么值得花这些 token）；什么时候不行动（破坏性操作的关卡、范围限制、拒绝条件）；环境上下文（Agent 被告知了机器、仓库、会话的哪些信息，放在请求的哪里）。还要专门分析 <system-reminder>：出现在哪（system 块、消息里，还是都有，举例）；能找到证据的两种不同用途；为什么在对话中途注入，而不是开头说一次。
  • 第三部分：注释工具设计（25 分）。先给数字：一共多少个工具，内置、MCP 提供、延迟加载可搜索的各多少；工具集在请求之间有没有变，什么触发的。题目举的合格答案是"第一个请求有 117 个工具：35 个内置，82 个来自三个 MCP 服务器"，不合格的是"有很多工具"。然后挑两个工具当作接口设计来分析：摘出 schema 的相关部分；为什么是这组参数，哪些必填、哪些可选、哪些故意不暴露；描述在防什么，题目说成熟 Agent 的工具描述大多是"累积的伤疤"，要找出一句只因为模型老是做错某件事才存在的话，并说出那件错事；它故意不做什么，这说明周围的系统是怎样的。两个工具要不同类，两个文件操作工具是弱选择，一个文件工具配一个编排工具，或一个有特殊失败约定的工具，是强选择。
  • 第四部分：有证据的行为分析（25 分）。每个回答都要引证据（哪个请求、第几条消息、哪次工具调用），并标注 [OBSERVED]（能在记录里指出来）或 [INFERRED]（根据定义推理，没亲眼看到）。两种都可以，标错不行，不标没分。问题有：错误恢复，从头到尾走一遍一次失败，Agent 看到了什么、接着试了什么、几轮恢复，要逐字引用；计划是来自工具、提示词指令、自发行为还是组合，什么证据能区分；计划和任务状态怎样创建和推进，模型每轮看到的任务状态是什么、放在请求哪里；子 Agent 什么时候委派、子 Agent 被告知了什么、返回了什么（会话里没触发的话，诚实标 [INFERRED] 即可）；上下文管理，会话变长时载荷有什么变化、早先的轮次后来怎样表示。
  • 第五部分：反思（10 分）。最多一页：两个你会照搬的设计决定及各自解决的问题；一个你会换种做法的，并认真想想它为什么存在；一件这次记录改变了你日常驾驭编程 Agent 方式的事。

安全提醒

截到的内容里有你自己的源码、文件路径和凭证。不要贴原始流量或 HTTP 头（x-api-key、authorization 在那里）；请求体也可能有秘密，Agent 读过的 .env、配置文件、命令输出都会在 messages 里重放，引用前要检查；session.flows 不进任何 git 仓库；引用里的私密内容用看得见的标记涂掉（比如 [REDACTED: internal hostname]），不要悄悄删除；实在无法脱敏，就在一个丢弃用的仓库上重截。评分会因引用里有未脱敏的凭证、或把记录不支持的推测说成观察而扣分。

三、第 2 周：为第三方 API 写一个 MCP 服务器

写一个把第三方 API 暴露给编程 Agent 的 MCP 服务器。调 API 是容易的部分，评分看的是"Agent 人体工学"：模型能不能挑对工具、调用正确、出错后恢复；外加一个能用的 OAuth 流程，因为值得封装的 API 大多不收静态密钥。学习目标：为一个只看得到 schema 和描述的使用者设计工具接口；在长期运行的服务器里实现 OAuth 令牌的获取、缓存和刷新；观察设计选择怎样改变 Agent 的实际行为。用 FastMCP 写。

  • 第一部分：服务器（25 分）。选一个用 OAuth 2.0 的 API（GitHub、Google 的 Gmail/日历/Drive、Notion、Linear、Slack、Spotify、Strava 都行），挑你自己真用的，你才判断得了工具该做什么。至少 3 个工具，而且要能串起来，一个的输出喂给另一个（比如 search_x 返回的 ID 能给 get_x(id)）；至少一个会改变真实状态的写工具；代码在 week2/，通过 stdio 运行，一条写在文档里的命令就能启动。
  • 第二部分：Agent 人体工学（30 分）。这是作业的核心。约束写进 schema 而不是正文：sort: Literal["stars", "forks"] 胜过 sort: str 加一句说明，schema 和说明一旦矛盾，Agent 会遇到它解释不了的校验失败。整理输出：不要原样透传 API 的 JSON，挑出 Agent 需要的字段，原始载荷费 token，还把你的接口和别人的 API 绑死。错误是数据不是堆栈：返回结构化、可操作的错误，让 Agent 分得清"别重试"（ID 错）和"可以重试"（限流、网络抖动）；一段堆栈会结束 Agent 这一轮，{"error": "rate limited, retry after 42s"} 不会。说明文字就是契约：写清 ID 从哪来（"来自 list_templates 的数字 ID"），工具才能串起来；跨工具的流程指导用 FastMCP(instructions=...)。写工具要有刹车：读工具标 readOnlyHint，不可逆的工具要么有 dry_run 参数，要么拆成"预览"和"提交"两步。
  • 第三部分：OAuth（25 分）。真正的 OAuth 流程，不是贴一个现成的令牌。完整的授权码交换，令牌缓存，过期时静默刷新；最小权限范围，只读就只要只读，每个范围都要在报告里说明理由；仓库里没有秘密，从第一次提交起就从环境变量读，提交 .mcp.json.example，真正的配置文件加进 gitignore；令牌在会话中途失效时，长期运行的服务器不能在工具调用中弹出浏览器，而要返回一个可操作的错误。
  • 第四部分：集成与演示（20 分）。把服务器注册到 Claude Code 或 Cursor，提交配置示例；展示一次端到端记录，Agent 串用至少两个你的工具回答一个真实提示（提示、调了哪些工具、参数、结果）；展示一次失败以及你的错误设计怎样处理（必要时故意制造，比如错 ID、吊销令牌）；至少一个通过 MCP 协议本身测试服务器的测试，而不只是直接调你的 Python 函数。

扣分项：提交了秘密；工具说明和 schema 互相矛盾。报告里还要写一件"看到 Agent 误用某个工具后你改了什么"。做完后建议把服务器从 Agent 配置里删掉、删掉缓存的令牌、在服务商那里吊销 OAuth 应用的权限。

四、第 3 周：写一个 Skill

Skill 是放可重复流程的地方：那份你本来每次都要贴进聊天的清单。这周写一个，用在一个真实的开源仓库上，看它该触发时会不会触发、运行时撑不撑得住。学习目标：找出一个值得写下来而不是每次重新解释的工作流；写一个描述能可靠触发、正文写进判断而不只是步骤的 Skill；验证它。参考材料是开放标准 agentskills.io、Claude Code 的 Skill 文档和 Matt Pocock 的 Skill 集。可选的目标仓库有 htmx、dayjs、slidev、pixijs、yt-dlp、stable-diffusion-webui、TheAlgorithms/Python、vue、react，也可以用自己的。

  • 第一部分：选工作流（15 分）。选一个你会不止做一次、里面至少有一个真正决策点的事。一条固定命令是 shell 别名，不是 Skill。题目给的点子：从 issue 到实现计划；按固定标准审 PR，引用确切的文件和行，把阻塞问题和建议分开；复现 bug（先做最小复现、提出假设、跑针对性测试，然后才提修复）；写测试；带新人上手仓库；代码库迁移（比如 Pydantic v1 到 v2 的检测规则和安全变换步骤）；依赖升级；按截图用仓库现有组件实现界面并目视验证；性能调查（先建基线、先剖析再改、只做一处有针对性的修复、对比）；安全审查（只看一个类别，要证据，不要猜测性的警告）。要先手动做一遍，没亲手做过的流程写不出来。
  • 第二部分：写 Skill（60 分）。按 Agent Skills 标准写 SKILL.md，放在你的 Agent 会发现 Skill 的目录里。得分点：能触发的描述，要说清它做什么以及什么时候用，用的是别人真会打出来的措辞，大多数 Skill 失败在从来不触发；写进判断而不只是步骤，情况模糊时怎么决定、什么不要做，复述工具文档什么也教不了；确定性的部分给出确切命令；正文要精简，Skill 一触发正文就进上下文，长的参考资料放进目录里的辅助文件再引用。
  • 第三部分：测试（25 分）。触发测试：三个应该触发的提示，一个不该触发的"擦边"提示，报告实际结果，擦边的也触发了就说明描述太宽；运行测试：在你选的仓库上端到端用一遍，展示结果。

报告里还要写：手动做的时候学到了什么没想到的；描述为什么这样措辞；正文里写进了哪些判断；哪些内容放进了辅助文件、为什么不放正文。

五、第 4 周：让一个乱糟糟的仓库适合 Agent

挑一个陌生的开源仓库，写它缺的那份 Agent 配置文件（AGENTS.md 或 CLAUDE.md，二选一）。要练的是好配置文件的结构和内容：什么该放、什么不该放、要具体到什么程度才真有用。学习目标：在陌生代码库里定位到能准确描述它的程度；把这些知识写成持久、可执行的仓库上下文；判断哪些属于配置文件、哪些是噪音。可选仓库和第 3 周相同，也可以用别人写的其他仓库。

  • 第一部分：探索仓库（20 分）。fork 下来，弄清它实际怎样工作：怎样构建、测试、lint、运行，要拿到确切命令；主要目录和入口；代码遵循哪些没人明说的惯例；哪些是生成的、vendored 的或者不该手改的。题目说用 Agent 帮忙探索最快。
  • 第二部分：写文件（55 分）。放在 fork 的根目录，至少覆盖：项目是什么（几句话，让 Agent 知道领域）；架构（关键目录、入口、各部分关系）；命令（构建、测试、lint、运行，确切、可直接复制，比如 pixi run pytest tests/，而不是"跑测试"）；惯例（仓库实际用的测试写法、风格规则、命名模式）；护栏（什么不要碰，以及值得警告的"看起来对其实错"的命令或目录）。质量标准是每一行都只适用于这个仓库：能干的模型本来就会遵守的通用建议是凑数，复述 README 也是。这个文件会进每一次上下文，长度就是成本，大约一页。
  • 第三部分：试用（25 分）。带着你的文件在仓库上跑两个小任务，比如跑测试和做一个小改动，如实报告 Agent 有没有用你的命令、遵守你的惯例，并根据观察说出一处你会改的地方。

报告里还要写：故意没放进去的东西和原因；在放什么上最难的一个决定。
