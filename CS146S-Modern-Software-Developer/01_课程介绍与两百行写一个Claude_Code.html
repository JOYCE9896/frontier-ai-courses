第一讲：课程介绍，用两百行代码写一个 Claude Code

2026 年软件开发的处境，这门课讲原则而不讲工具，课程安排与评分，然后从零写一个最小的编程 Agent：读用户输入、告诉模型有哪些工具、解析工具调用、在本地执行、把结果送回去

主讲：Mihail Eric
资料来源：课件和课上写完的代码（2026 年 9 月 22 日；这一讲没有公开转录，本文依据课件和代码整理）
课程推荐阅读：Building a Coding Agent、Lessons from Building Claude Code、Dive into Claude Code

一、2026 年的处境

课件第二页贴了几条 2026 年的新闻标题：Anthropic 和 OpenAI 的顶尖工程师说 AI 现在写了他们 100% 的代码；Business Insider 报道 Meta 在推员工用 AI，并有内部文件说明推到什么程度；OpenAI 和 Hugging Face 联手处理一次模型评测期间的安全事件。

Eric 从这里引出对学生的意思：

  • 整个行业都在用 AI，公司需要你，变成"AI 原生"（AI-native）已经是新的目标。
  • 但门槛也抬高了。软件开发者的生产力是历史上最高的，对开发者的期望也跟着涨了。
  • 要把注意力放在整体的系统层面：架构和抽象。这种能力再配上 AI 优先的开发方式，就很难被替代。

二、这门课讲原则，不讲工具

课程叫 The Modern Software Developer（现代软件开发者）。课件专门用一页写了一句话："这门课讲原则，不讲工具。"工具每个月都在换，课上用 Claude Code、Cursor 做演示，但要学的是背后不变的做法。

课件的"要点"一页把整门课浓缩成三条：

  • 人和 Agent 一起做工程。专注于 AI 系统还替代不了的技能：理解业务和产品；当技术架构师，培养对软件系统的品味；沟通很重要。
  • LLM 的上限是你。好的上下文带来好的代码。你自己看不懂自己的代码库，LLM 也看不懂。要防止"AI 垃圾"（AI slop），即看着像样、其实没人审过的生成代码。
  • 大胆试。

三、课程安排

主讲人 Mihail Eric 在斯坦福读的本科和研究生，现在是旧金山一家做销售方向的创业公司 Monaco 的 AI 负责人，给几十家公司（从种子轮创业公司到上市企业）做 AI 顾问。他在 Amazon Alexa 做过最早的一批 LLM，创办并卖掉过一家机器学习教育公司，还创办过一家 YC 投资的 AI 编程公司。助教是 Isaac Kan 和 Vijay Daita。

  • 上课时间：周二、周四下午 5:30 到 6:20。
  • 6 次作业，每周一次，练习当周讲的内容，放在 GitHub 作业仓库。
  • 给开源项目贡献 3 到 4 次代码。
  • 一个开放式的期末项目，用上课程讲的 AI 编程原则。
  • 评分：期末项目 50%，作业 15%，开源贡献 30%，课堂参与 5%。

开源合作伙伴有 15 个当下很热门的 AI 原生开源项目，包括 Vercel、Warp、Marimo、Milvus、Pi、CrewAI、Browserbase、HeyGen、CopilotKit、Semgrep、OpenHands、cmux、Arize、Unsloth、Anyscale（后来公布的正式名单略有出入，见第三讲）。客座讲座请的是正在带领顶尖 AI 开发工具团队的创始人和工程负责人，比如 Claude Code、Devin、Replit、Factory 的创造者。

四、用两百行代码写一个 Claude Code

后半节课是现场写代码。课件上的结构图很简单：左边是用户，中间是 Agent 外壳（图标是 Claude、Cursor、Windsurf），右边是 LLM，上面是一组工具。用户和外壳来回说话，外壳和 LLM 来回说话，外壳在需要时调用工具。标题写着："就这么简单。"

课件列的步骤：

  1. 从终端读用户输入，不断追加到对话记录里。
  2. 告诉 LLM 有哪些工具可用。它会在合适的时候请求使用某个工具；你在本地执行这个工具，再把结果交回给它。
  3. 工具只有三个：读文件（read_file）、列目录（list_files）、改文件（edit_file）。

下面按课上写完的代码（Python，调用 OpenAI 的 Responses 接口）一块块看。

1. 三个工具就是三个普通函数

工具没有任何特别之处，就是 Python 函数，每个都写了说明文字（docstring）和参数类型。之所以要认真写说明，是因为后面会把它们原样拼进提示词，模型完全靠这些文字知道工具干什么。

  • read_file_tool(filename)：把相对路径换成绝对路径，读出整个文件，返回路径和内容。
  • list_files_tool(path)：列出目录下每一项，标明是文件还是目录。
  • edit_file_tool(path, old_str, new_str)：在文件里把第一次出现的 old_str 换成 new_str；如果 old_str 是空的，就直接新建或覆盖文件。找不到 old_str 时不抛异常，而是返回 "old_str not found"，让模型自己知道改失败了。

三个函数登记在一个字典里： 

TOOL_REGISTRY = {
    "read_file": read_file_tool,
    "list_files": list_files_tool,
    "edit_file": edit_file_tool
}

2. 把工具写进系统提示词

系统提示词告诉模型三件事：你是编程助手；你能用下面这些工具；想用工具时，只回一行 tool: 工具名({JSON 参数})，别的什么都不写。

工具列表是自动生成的：对字典里的每个函数，用 Python 的 inspect.signature 取出函数签名，加上函数名和 docstring，拼成一段文字填进系统提示词。所以改一下函数的说明，模型看到的工具描述就跟着变了。

3. 解析工具调用

模型的回复是纯文本。extract_tool_invocations 逐行扫描，找以 tool: 开头的行，按第一个左括号切开，前面是工具名，后面用 JSON 解析器读出参数。格式不对的行直接跳过。这是最原始的做法，今天的商用接口有专门的结构化工具调用字段，原理是一样的。

4. Agent 循环

核心是两层循环。外层每次读一句用户输入；内层反复调用模型，直到它不再请求工具为止： 

conversation = [{"role": "developer", "content": create_full_system_prompt()}]
while True:                                  # outer loop: one user turn
    user_msg = input("You: ")
    conversation.append({"role": "user", "content": user_msg})
    while True:                              # inner loop: until no tool call
        reply = execute_llm_call(conversation)
        calls = extract_tool_invocations(reply)
        conversation.append({"role": "assistant", "content": reply})
        if not calls:
            print(reply)
            break
        for name, args in calls:
            result = TOOL_REGISTRY[name](**args)
            conversation.append({"role": "user",
                                 "content": f"tool_result({json.dumps(result)})"})

（上面是按原代码简化的示意，原代码对每个工具分别取参数并给默认值。）要注意几点：

  • 整个对话就是一个不断变长的列表，每次调用模型都把全部历史发过去。模型没有记忆，"记忆"就是这个列表。
  • 工具结果是以 user 角色塞回对话的，前面加上 tool_result(...) 标记，模型读到后接着干活。
  • 模型可以连续调好几次工具（先列目录，再读文件，再改文件），每次结果都回到列表里，直到它觉得做完了，用普通文字回答。

这样不到两百行，就有了一个能看懂代码、能改文件的编程 Agent。第二讲会在这个骨架上，看真正的 Claude Code 多了哪些东西。
