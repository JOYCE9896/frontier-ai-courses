第七讲：定制你的 Agent 配置

MCP 的额外好处，四种定制手段（AGENTS.md / CLAUDE.md、Hook、Skill、子 Agent），怎样写一份好的 AGENTS.md，Hook 能在哪些事件上运行、用来做什么，子 Agent 适合哪些支线任务，常用的 MCP 服务器，以及上下文是怎样一层层叠起来的

主讲：Mihail Eric
资料来源：课件（2026 年 10 月 13 日；这一讲没有公开转录，本文依据课件整理）
课程推荐阅读：I Still Prefer MCP Over Skills、AGENTS.md（Factory 文档）、Steering Claude Code: Skills, Hooks, Rules, Subagents, and More、Writing a Good CLAUDE.md

一、开场事务

  • 期末项目的技术规格周四截止。
  • 第一次开源贡献周日截止。
  • 从这周起，所有周四的课（客座讲座）改在 STLC 111。周四的嘉宾是 Claude Code 的创造者 Boris Cherny（那一讲没有公开课件和转录）。

二、补充：MCP 的额外好处

开头再放了一次 API、MCP、Skill 的对比表（见第四讲），然后补了几条 MCP 相对于直接调 API 或写 Skill 的好处。推荐阅读里那篇《I Still Prefer MCP Over Skills》也站在这一边。

  • 认证顺畅：OAuth 这类流程由协议和客户端处理，不用每次自己写。
  • 版本管理和更新容易：服务器一更新，所有客户端都用上新版本。
  • 能在不同客户端之间移植：同一个服务器，Claude Code、Cursor、Codex 都能接。
  • 远程 MCP 天然有沙箱：能力跑在别人的服务器上，和你的本地环境隔开。

三、为什么要定制

要用编程 Agent 达到最高效率，就得掌控自己的工具栈，而可用来定制的机制有很多。课件列了四种：

  1. Agent 行为文件（CLAUDE.md / AGENTS.md）
  2. Hook
  3. Skill
  4. 子 Agent

这四样在第二讲拆 Claude Code 时都见过，这一讲讲怎样用好它们。

四、怎样写一份好的 AGENTS.md

把它看作"写给 Agent 的 README"。建议的结构：

  • 项目概览：代码库的地图。
  • 构建和测试命令，要具体到"用 maven 而不是 gradle"这种程度。
  • 代码风格规范。
  • 测试说明。
  • 安全注意事项。
  • 语言或技术栈特有的坑，比如"React 18 加 TypeScript，用 Vite，不是 React 脚手架"。

写法上的几条原则：

  • 指令尽量写成普遍适用的。这个文件会出现在每一次请求里，只对某个任务有用的话会在其他任务里变成噪音。
  • 不要放代码片段，它们很快就会过时。第二讲也说过，最多放一两条确切的命令。
  • 注意长度，控制在 300 行以内。
  • 大仓库用嵌套的配置文件，根目录的 AGENTS.md 当路由器用，比如写一句"API 网关设计的细节见 docs/API-GATEWAY.md"，Agent 需要时再去读。这和 Skill 的渐进式披露是同一个思路。

作业 4（见作业页）就是给一个陌生的开源仓库写这样一份文件，要求每一行都只适用于这个仓库，大约一页长。

五、Hook

Hook 是在预定义的事件上运行的确定性脚本。和提示词不同，它一定会执行，不依赖模型自己记得去做。常见的事件类型：

  • PreToolUse：工具调用之前。
  • PostToolUse：工具调用之后。
  • UserPromptSubmit：用户提交提示词时。
  • PreCompact：上下文压缩之前。
  • 还有更多。

用途：

  • 清理用户的提示词。
  • 拦住敏感操作。
  • 对生成的代码跑 linter 和格式化工具。
  • 任务完成后跑测试。

六、Skill 和子 Agent

Skill（详见第五讲）：把常用的提示词做成文件，让 Agent 可以执行。用途包括跑测试、做计划、做研究、审查代码、验证输出。

子 Agent 是运行时的委派。它的作用是：

  • 把不同工作流的上下文干净地分开。
  • 只把最后一条消息返回给主 Agent。
  • 名字、描述和工具列表在会话开始时就加载。
  • 可以隐式调用（主 Agent 判断该用），也可以显式调用。
  • 把最常做的工作流自动化。

典型用途：探索、理解代码库；改完代码后做简化；端到端测试应用。总之最适合做支线任务，主线的上下文不被它们的细节填满。

七、常用的 MCP 服务器

类别例子用来做什么
产品管理Jira、Linear创建和更新 issue；拉取 issue 信息，据此启动任务
文档Notion、Confluence根据功能规格创建 issue
可观测性Datadog、Sentry实时调试生产环境
数据库Redshift调试数据问题，弄清数据是怎样组织的
技术文档Context7永远不用过时的库定义，减少幻觉
实验追踪Arize拿一次测试运行的输出，建议新的实验

八、上下文是怎样叠起来的

课件最后一页画了一摞方块，从上到下是一次请求里上下文的组成：

  1. 系统提示词
  2. Memory.md（记忆）
  3. 环境信息
  4. MCP 工具
  5. Skill
  6. AGENTS.md（全局）
  7. AGENTS.md（本地）

这些都在你打第一个字之前就占进了上下文。结合第三讲的"聪明 token"和"笨区"：前面这些层越臃肿，留给任务本身的好用空间就越少。所以定制的目标是放进对的东西，而不是放进更多东西。
