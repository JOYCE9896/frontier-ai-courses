第八讲：让代码库适合 Agent

上下文的层次回顾，为什么大多数代码库还没准备好让 Agent 干活，人能绕过去而 Agent 绕不过去的缺口，一份“Agent 就绪”检查清单和 Factory 的就绪度报告，以及后台编程 Agent 需要什么：工作树隔离、多 Agent 编排器和云端 Agent

主讲：Mihail Eric
资料来源：课件（2026 年 10 月 20 日；这一讲没有公开转录，本文依据课件整理）
课程推荐阅读：Making Codebases Agent Ready（视频）、Making Ergonomic Repositories

一、开场事务

  • 第 4 周作业周日截止。
  • 问大家第一次开源贡献做得怎么样，并发了期中课程问卷。
  • 周四的客座讲座在 STLC 111，嘉宾是 Factory 的 CTO Eno Reyes（笔记见第九讲）。

二、回顾：上下文是怎样叠起来的

开头一页“上下文的故事”把第七讲结尾的内容再列了一遍。编程 Agent 每次调用模型时，送进去的上下文（Context，模型这一轮能看到的全部文字）从上到下由这几层组成：

  1. 系统提示词（System Prompt）
  2. Memory.md（Agent 自己记下的长期记忆）
  3. 环境信息（操作系统、当前目录、日期等）
  4. MCP 工具
  5. Skill
  6. 全局 AGENTS.md
  7. 本地（仓库里的）AGENTS.md

这一讲接着往下走：上下文写得再好，如果代码库本身乱，Agent 照样会出错。

三、为什么要做“Agent 就绪”的仓库

课件的判断是，今天大多数代码库都没有为 Agent 的成功做好准备。LLM 的很多困惑，来自它要在一个杂乱或不完整的开发环境里完成任务。所以要优化代码库和开发环境，目标是让一个人和一个 Agent 都能看懂这里发生了什么。

人能绕过去的问题

课件逐条列了人类工程师平时怎样应付这些缺口：

  • 测试覆盖不够：手动测一下。
  • 文档过时：去问同事。
  • 没有 linter（自动检查代码格式和常见错误的工具）：自己看看分号写没写。
  • 构建不稳定（flaky build，同样的代码有时成功有时失败）：重试。
  • 环境搭建和上手复杂：去问同事。
  • 可观测性（Observability，能看到系统运行时发生了什么）差或没有：去翻日志。
  • 没有安全扫描：先不管。
  • 写法不统一：靠团队里没写下来的经验（tribal knowledge）。

同样的问题怎样卡住 Agent

  • 没有测试，Agent 没法验证改得对不对。
  • 没有文档和规范，Agent 没法保证写法一致。
  • 构建不可靠，Agent 没法验证自己的改动。
  • 没有可观测性，Agent 没法调试。
  • 环境搭建复杂，Agent 没法复现环境。
  • 没有安全检查，Agent 会引入漏洞。

课件备注补了一句：杂乱的仓库可以很简单，比如访问数据库有几种不同写法、变量命名不统一、好几个函数做同一件事。

四、Agent 就绪环境检查清单

  • 足够的测试覆盖
  • 封闭构建（Hermetic build）：构建只依赖仓库里声明的东西，在哪台机器上跑结果都一样
  • 文档清楚、前后一致的设计模式
  • 没有过时的 README
  • 可以验证的检查（Agent 能自己跑、能得到明确通过或失败的检查）
  • 一份专门给 Agent 的操作手册：AGENTS.md 等

做到之后能干什么

  • 完成大任务，比如代码迁移。
  • 团队里多个人各自跑多个 Agent 任务。
  • 自动代码审查（见第十讲）。
  • 结果可以验证的长时间 Agent 任务。
  • 在老代码库（brownfield，已有大量历史代码的项目）上跑 Agent。

五、演示：Agent 就绪度报告

课上演示了 Factory 的 Agent 就绪度（Agent Readiness）框架，现场给几个开源仓库打分。课件给的链接：

  • Factory 介绍这个框架的文章和公开报告页
  • 现场看的例子是 vercel/next.js 的就绪度报告
  • 一条相关推文（alvinsng）和一个开源的同类工具 kodustech/agent-readiness

框架的具体内容（支柱和五个等级）在第二天 Eno Reyes 的客座讲座里讲得更细，见第九讲。第 5 周作业就是用这个报告给三个开源仓库打分，见作业。

六、后台编程 Agent 的工作流

后半节换到后台 Agent（Background Agent）：你把任务交出去，Agent 在别处自己跑，你不用盯着，可以同时开好几个。

为什么要往这里走

课件列了编程 Agent 能力的三个阶段和对应的效率提升：

阶段时间效率提升
Tab 补全2021约 15%
同步完成单个任务2024约 25% 到 35%
后台同时完成多个任务2026 年以后2 倍以上

后台 Agent 需要什么

要求是：隔离的开发环境，加上第四节那份清单上的全部内容（测试覆盖、封闭构建、一致的设计模式、没有过时 README、可验证的检查、AGENTS.md）。课件备注自己点破了：这和前面“Agent 优先的开发环境”那页基本是同一页。也就是说，仓库做到 Agent 就绪，后台 Agent 就跑得起来。

隔离：Git 工作树

多个 Agent 同时改同一个仓库，最简单的隔离办法是 Git 工作树（worktree）：同一个仓库检出到多个目录，每个目录在自己的分支上，互不干扰。 

git worktree add -b my-new-branch ../my-new-branch

多 Agent 编排器

选项有 Conductor、Cursor 的并行 Agent、Claude Code Swarms，或者自己写。好处是把建工作树这类底层操作包起来。缺点是界面有时比较死板；共享资源（数据库、端口）并没有完全隔离。课件备注还提到，这些编排器会让你很难在终端、IDE、云端之间来回切换。

云端 Agent

云端 Agent 把开 Agent、配环境这些复杂的事全包了，而且可以从不同的入口启动：

  • 浏览器：Codex、Claude Code、Devin
  • 代码审查：Graphite、Claude、Devin Review
  • 聊天工具：Slack 里的 Claude Code 和 Codex
  • 手机：原生 App，或者通过 Slack 这类第三方 App
  • 任务跟踪软件：比如一个 Linear issue
