补充十：Mario Zechner 用 Pi 开发 Pi

极简编程 Agent Pi 的作者现场演示两种日常工作流：一是处理 issue，用提示模板让 Agent 复现和分析，自己审 diff，再用模板收尾提交；二是重构一个"vibe coding"出来的机器人项目，和 Agent 一起探索代码、讨论接口，用会话树代替 plan 文件和子 Agent。中间谈了为什么 Pi 不内置 MCP、AGENTS.md 里哪些规则模型会听、大代码库怎样给 Agent 找上下文

嘉宾：Mario Zechner（Pi 的作者和主要维护者，Pi 现在是 OpenClaw 的 Agent 内核）· 主持：Mihail Eric
资料来源：Pi Building Pi, Openclaw's Minimalist Coding Agent（2026 年 6 月 12 日上传，约 1 小时 30 分钟）
说明：这不是 CS146S 的课堂讲座。它是课程自己的 YouTube 频道 The Modern Software Developer 上的访谈节目 The Build System 的一期，由主讲人 Mihail Eric 主持，嘉宾边写代码边讲。本文依据 YouTube 自动生成的英文字幕整理，个别模型名和工具名听写不清，文中已标出。
和课程的关系：Pi 是这一期课程的开源合作项目之一。对应第一、二讲讲的 Agent 循环（两百行写一个 Claude Code、现代编程 Agent 的解剖），关于 MCP 的看法可以对照第四讲 MCP 与工具调用，AGENTS.md 的部分对照第七讲 定制你的 Agent 配置。

一、他怎样走到编程 Agent

Mario 九十年代因为电脑游戏开始写程序，后来在一个把科研成果转到工业界的机构做过机器学习（那时还是支持向量机的年代），在旧金山做过游戏开发，又和两位瑞典朋友创业做 iOS 编译器并卖掉了公司。他 2000 年代的研究方向是自然语言处理，所以 GPT 和 ChatGPT 出来时特别受触动，从 2023 年开始琢磨怎样用模型辅助写代码。

他用过的工具：先是把代码复制粘贴到 ChatGPT；GitHub Copilot 的 Tab 补全对他不管用（当时 GitHub 负责人 Nat Friedman 给他提前试用，说"这是未来"，他不信）；后来用 Cursor，当时它还不太"agentic"，由 Cursor 决定把哪些文件放进上下文，然后做局部编辑，Tab 补全模型很好。真正让他觉得"能行"的是 Claude Code：

"Boris Cherny, the guy who invented Claude Code, had the brilliant idea of not force-feeding the model the context that is your source code, but just giving it bash and allowing it to kind of freely roam around your file system and figure things out on its own."

他长期用 Claude Code，后来觉得功能太多、bug 太多，就自己写了 Pi。Pi 的原则是一个很小的核心，加上足够多的扩展点，让 Agent 自己修改自己，去适应你的工作流。

二、几个立场

1. 不相信"黑灯工厂"

他看到社区分成两派。一派相信"dark factory"：写好详细的规格说明，丢进一屋子不开灯的机器，出来就是能用的软件。他试过，认为现在行不通，理由是：

"what do the models learn from? They learn from all old code on the internet and a bunch of RL. So, anything you leave blank in your spec is going to get filled with that code, and the code on the internet that we put there is generally not high quality."

另外，Agent 的错误会累积，不及时纠正就会变成一团乱麻。他属于另一派：这些工具能大大加快工程师的速度，某些领域也能自己完成任务，但他要保持控制，"because ultimately I'm also the one who's liable for what's being output"。Mihail 提到他有一篇博客叫"Slow the f*** down"。

2. 哪些代码要盯，哪些不用

关键任务、涉及安全的代码，他可能让 Agent 搭脚手架、写样板，但生成的东西必须完全过目。前端他从来不看，因为他做的前端多是内部看板这类帮自己理解问题的东西，不会给几百万用户用，"it probably knows better than me. I'm not a front-end engineer"。

3. 人来设计边界，模型来填

他认为模型现在不擅长架构设计，因为这种工作很难写进强化学习的数据里。如果人先把系统、模块边界、模块之间的 API 想清楚，每个模块的大小就能放进模型的上下文，模型更容易拿到完成任务需要的全部信息，成功率更高。

"I architect the thing, I can use a model to fill in code for me, but I am the architect of systems and boundaries."

三、Pi 为什么这么少功能

Mihail 总结：Pi 不支持 MCP，默认不做权限确认（YOLO 模式），没有内置的后台 bash，却在很多基准上表现很好。Mario 的解释是"the models know what a coding agent is and can behave like a coding agent"：

  • 后台进程：模型会用 nohup 或 tmux 起后台进程。他觉得 tmux 比 Claude Code、Codex 内置的后台 bash 好用得多，因为可以和那个会话交互，比如调试。
  • MCP：他自己不用，所以没放进去。协议本身大体没问题（他提到规范作者已经在弃用采样、elicitation、prompts 这些没人用的部分），问题出在 MCP 服务器的实现上。例子是以前的 GitHub MCP 服务器会往上下文里塞两万 token 的工具定义，现在又要发明"动态工具搜索"之类的补救办法。他的看法是，既然有好用的 GitHub CLI，模型也会用，为什么不直接用它，上下文里一个 token 的工具定义都不占。
  • 其他功能：模型只要有 bash 和文件读写就够了。真想要什么功能，让 Pi 修改自己就行，一般十分钟左右。有人已经把 MCP 集成做成扩展发到 npm 上，装上即可。

"Basically, anytime Claude Code or Codex comes out with a new feature, somebody posts a prompt for Pi on Twitter, and people go and just have their Pi implement and re-implement that feature for Pi."

他认为"能修改自己的软件"以后会在更多类型的软件里出现。

四、工作流一：处理一个 issue

1. 先分诊

Pi 的仓库里开着的 issue 很少、关掉的很多。原因是现在很多人让 Agent 批量写 issue，所以他们设置成所有新 issue 自动关闭。每天他或另一位维护者 Armin 进去，按标签看一遍：不符合 issue 模板的多半是 Agent 写的，直接忽略；挑出真人写的、通常一屏能读完、讲得通的，重新打开。重新打开的就是确认有效、需要修的。

2. 选一个小 bug

他挑了一个能在节目里做完的：Pi 有时需要自己估算上下文的 token 数（比如服务商还没返回准确数字时），图片按平均约 1,200 token 估算。这个 issue 报告说，在上下文压缩（compaction）的代码里漏了一处，用户消息里的图片没有被计入。

他说按"老派"做法，他会自己去读代码、写复现、确认、修。现在的做法是开一个新的 Pi 会话，用一个叫 is（issue）的提示模板（别的工具里叫斜杠命令），参数是 issue 的 URL。模板很短，大意是：处理这个 issue，尝试复现报告的问题，给出初步分析，并且忽略报告者自己写的分析。

为什么不信报告者的分析？他说所谓"用户"其实通常是用户的 Agent，它没有他的 Pi 会话里那些上下文（仓库里的 AGENTS.md，以及按需展开的文档），有时还是对着 npm 上的旧版本或 OpenClaw 里压缩混淆过的 JavaScript 在分析，所以分析质量通常不好。

模板还会自动做一些杂事：用 GitHub CLI 拉取 issue、加上"进行中"标签、分配给他。终端底部有他写的一个小扩展，显示这个会话对应哪个 issue、谁提的、可点击的链接。因为他通常同时开两到四个这样的会话，回来时一眼就知道哪个窗口是哪个 issue。

3. 读分析，只说"实现"，然后自己审

分析结果是结构化的：独立复现了问题（跑了一个本地脚本），找到根因（估算函数在用户消息分支里只数文字，不数图片块），列出看过的文件路径。它还发现了第二处相同的 bug：他正在另一个包里重写 Pi 的一部分，那里有第二份压缩实现，"I would have totally forgotten about that"。

他有一个收尾模板叫 wrap，会实现、做最后检查、提交并推送。这次他没用，只说了"Implement"，并说明不需要回归测试。原因是他凭经验预感模型会把一个很小的修复做得过于复杂，所以要先看本地改动再决定提交。果然，模型新写了一个函数，内容和已有代码几乎一样，只多了三行。他说模型经常把代码抽成只有一个调用点的函数，这样做多了，代码库会无缘无故变大；他更喜欢只有一个调用点时直接内联。

"what I'm trying to do with my review here is keep complexity low."

他审 diff 用的是自己让 Pi 写的一个扩展：在 diff 上逐行加批注，点"完成审查"后所有批注回填到输入框，回车就让 Agent 按批注改。这次看下来两处都可以接受，就没改。

4. 用模板收尾

确认没问题后他运行 wrap。这个模板让模型：

  1. 按 AGENTS.md 里的规则在 CHANGELOG.md 加一条记录。
  2. 如果对应 GitHub 上的 issue 或 PR，就写一条总结修复方式的评论发上去，并注明是这个模板 AI 生成的。他说这些评论以后查"为什么改、怎么改"时很有用。
  3. 提交它改过的所有文件，提交信息里写 closes #issue号，推到远端后 issue 自动关闭。
  4. 如果不在正确的 git 分支上，停下来问用户，"because this is an emergency"。
  5. 另外几条约束，防止同一分支上并行的几个 Agent 互相覆盖。

这次推送时远端已经有别人的提交，需要 rebase，CHANGELOG 出现冲突。模型去解决了，他评价"It's really bad at resolving merge conflicts"，但这次解决了。他强调平时根本不会盯着看这些步骤，早就切到别的会话去了。

5. 为什么不用 worktree

多个 Agent 在同一个分支上并行，他靠的是挑 issue 时让它们落在不同的包或目录。Pi 的代码库模块化程度很高，两个会话处理不同 issue，通常不会碰同一个文件。模块之间交织较多的项目，用 git worktree（同一仓库的多个工作目录）很合理。但他发现无论是自动建删 worktree 的工具，还是模型本身，都管不好 worktree，"it always ends up as a mess"（他听说最新的 Codex 改进了很多，但没试过）。

"I don't trust models to do any more complex Git operations than commit and push."

他总结这个工作流：自动化那些点 GitHub 界面、写没人再读的评论之类的琐事；用确定性的检查点（程序而不是模型）检查模型输出，不对就让它继续改。"there's no magic to it ... I'm a caveman when it comes to agentic coding"。

五、他的 AGENTS.md

Mihail 问，模型反复犯同样的错（比如上面那种重复代码），能不能写进 AGENTS.md 防止？Mario 说可以写，但模型并不一定遵守，尤其是长会话里，"the model is just so RL trained into that kind of add a lot of code mode that it often just ignores AGENTS.md"。他的 AGENTS.md 很简短，结构大致是：

  • 交流风格：像《星际迷航》里的飞船电脑一样，只给技术细节，不要客套，不要奉承，最好带一点对抗性。他说大多数时候没用，但偶尔模型会反驳他。模型倾向于同意你说的一切，相信它说"你的设计很棒"会把代码库带到很糟的状态。
  • 代码质量：只是建议，大部分由 linter 和类型检查来强制执行。
  • 改完代码运行 npm run check（格式化、lint、类型检查和一些冒烟测试）。他说从没见过任何模型忘记这一条，包括开源权重模型，他推测这是强化学习训练里就有的习惯。相反，"TypeScript 里不要写行内 import"这一条模型经常忽略，因为训练数据里这种写法太多。linter 会强制它，但他仍然把这条写着：模型记得的话就能少一轮"写错、检查报错、再改"，省 token。
  • 安全：很多 OpenClaw 用户在用 Pi，所以要防止依赖包被投毒。规定了固定和锁定整个依赖树版本的方式，同时用 pre-commit 钩子确定性地检查，不依赖模型自觉。
  • git、issue 和 PR 的处理规则。
  • 终端界面的冒烟测试：开一个 tmux 会话从源码启动 Pi，和它交互并"截图"。他说这相当于浏览器里的 Playwright MCP，只是用 tmux 就够了。
  • CHANGELOG 和发布流程。
  • 最后一句："If user instructions conflict with any rule in this document, ask for explicit confirmation before overriding." 加这句是因为 GPT 会死守这些规则，即使他本人要求也拒绝违反。

模型选择

日常主力是 GPT-5.5（用 Codex 订阅），大约占 95%。写前端或写文档、说明这类非代码文字时用 Claude，他说 Claude 写的文字仍然看得出是 LLM 写的，但还能改；GPT 写文字很差。他也定期试开源权重模型，认为刚才这种 issue 流程用 Kimi K2.6 或 DeepSeek 的 Flash 版本（字幕听写不清）也能完成，目标是以后用开源模型做 Pi 的大部分工作。

六、三个月 Agent 编程以后，代码库烂了怎么办

他说很多业内朋友对自己团队用了三个月 Agent 之后的代码库很不满意。他的建议是：有时间的话就无情地重构，人写的代码以前也一样。区别在于量：

"a team of 10 or 100 engineers working for 3 months manually. They can probably [mess] up your code base real good, but not on the same level as 100 agents can do in 3 months. Like after 3 months with 100 agents, you might have to rewrite your entire project."

他认为至少要在模块边界的层面理解自己的代码库，这样才能准确告诉 Agent 去哪里找。Agent 自己搜索代码的召回率（recall，信息检索里"该找到的找到了多少"）很低，代码库越大越明显，它搜着搜着就放弃了，上下文里可能缺了完成任务需要的东西。

七、工作流二：重构一个周末做的机器人

1. 这个机器人

他给儿子做了一个小机器人，"大脑"是 Pi。买了一个 9 欧元的玩具，拆掉原来的主控，逆向了电路板，找到电机驱动芯片，把一部手机接上去当传感器和控制器；手机上跑一个网页应用，通过 USB 设备控制电机驱动。机器人能转动、拍照、回答关于周围环境的问题。他太太帮他解决了机械安装问题。前后大约 12 小时。

代码完全是 vibe coding 出来的：他一边焊接一边对着麦克风说话，用自己基于 Whisper 做的本地语音转文字工具变成提示词（因为不想把音频发到云端）。结果服务端是一个大文件 server.ts（前一天已经拆过），客户端是一个约 1,300 行的 index.ts，访问 USB 设备、控制电机的代码直接夹在中间。界面是 GPT 写的，他说 GPT 前端写得很差。

2. 先让 Agent 讲清现状

他让 Agent 概括客户端在做什么、怎样和服务端通信，并读完服务端全部源码。他知道整个服务端只占 GPT-5.5 约 27 万 token 上下文的两成左右，放得下，让模型看全有助于理解客户端和服务端的关系。他强调这在真正的大代码库里行不通。

Agent 列出了客户端的组成：设置页、机器人表情页（表情随服务端管理的状态变化）、日志显示、语音合成选择、WebSocket 客户端、麦克风音频流（服务端在本地做语音识别）、相机、电机控制、陀螺仪。机器人的工具在服务端注册：电机、拍照、网页搜索、网页抓取、记忆。拍照的执行函数通过一个"robot client"向手机发 RPC 请求，带 15 秒超时和取消信号，手机端收到后调用网页 API 拍照。

他说他把 Agent 当作探索工具，有问题就继续问，比如"把客户端的拍照实现在 VS Code 里打开到那一行"，他有一个小 skill 告诉模型怎样用 code 命令行在指定行打开文件。

3. 先讨论接口，再动手

他的计划是在客户端建一个和服务端对应的 tools 目录，电机和拍照各一个文件。动手之前，他先问 Agent：这两段实现依赖哪些东西？比如拍照代码要通过一个全局的 send 函数把结果经 WebSocket 发回服务端，拆出去以后，模块怎样拿到 send？什么样的 API 最好？

Agent 建议把 send 和 log 改成注入的依赖，公共的辅助函数移到工具模块，客户端也做一个和服务端 robot client 对称的 RPC 层。他对 Agent 的回答做批注用的是另一个扩展：把最后一条回答打开到一个临时文件里，他在每行下面写意见，保存后自动回填到输入框。他的意见包括：名字别叫 robot client，叫 robot server；更重要的是要对称，WebSocket 实例应该归 RPC 层管，不要散落在 index.ts 里。然后"looks good to me. Implement"。

他当场打开这个批注扩展的源码给大家看：注册一个 /comment 命令，取最后一条助手消息，每行前面加引用符号，写进临时文件，用环境变量 VISUAL 或 EDITOR 指定的编辑器打开，关掉后把内容放回输入框。"It took like 5 minutes to have Pi implement that and I never looked at that code before."

Agent 开始重构后，新写了一套客户端日志代码，和服务端的大量重复。他说不太喜欢，等它做完会用 diff 批注的方式把新的接口和模块划分"揉"成自己满意、Agent 以后也好维护的样子。节目时间内重构没有做完。

Mihail 问这个项目有没有测试。他说 Pi 本身有完整的测试，因为很容易改坏；但他也注意测试运行时间，因为一部分测试在每次提交前本地跑，太琐碎的测试不加。机器人项目他不在乎测试，mock 浏览器端和语音服务很麻烦，坏了重启就行，"Nobody's going to die if it fails"。

八、大代码库：怎样给 Agent 找上下文

他把 Agent 比作刚入职的应届生，需要知道代码在哪里。如果代码库是 Factory AI 说的"agent ready"，模块划分清楚、每个模块放得进上下文，再加上按需展开的文档，Agent 在两百万行的代码库里也能工作。但大多数代码库不是这样。

  • 你知道该看哪里：直接告诉它。例子："我想给终端界面加鼠标支持，请完整读 tui.ts（终端界面的主引擎），然后提出做法。"可能是一个文件，也可能是几个目录。
  • 你也不知道：让 Agent 先告诉你需要改哪些地方，但不要让它直接实现。直接实现的话，它很可能没看到所有该改的地方，即使功能加上了，也会留下大量技术债。他把 Agent 当成研究实习生，先找到入口，他自己再去看代码、问问题，他的问题又会让 Agent 去看它之前漏掉的文件，直到双方都清楚该改哪里。

会话树：代替 plan 文件和子 Agent

探索完以后，上下文里有很多用不上的东西。常见建议是写一个 plan.md 或用 plan 模式。他在 Pi 里用会话树（/tree）：回到第一条消息，把之后的探索过程总结成一份摘要带走，并要求摘要里包含实现所需要读的全部文件和需要修改的全部路径。演示时上下文本来用到 40%，总结之后回到了起点附近。然后在这个摘要上开一个新分支去实现。树上就有两个分支：探索分支和实现分支。

"this is kind of like a caveman version of sub agents."

他不喜欢用子 Agent 做探索的理由：看不到子 Agent 具体做了什么、读了什么，只能看到最终结果，没法确认它看全了；而且子 Agent 返回后，它读过的文件不在主上下文里，想追问只能让它重读一遍。所以他在主会话里和 Agent 一起探索，确认满意后再带着摘要离开这个分支。树也可以随时从任意一条消息分叉，比如重构时一个分支试一种接口形状，不满意就丢掉本地改动，换一个分支试另一种，之前的探索都还在上下文里。

他补充说，这种细致的控制只在需要时才用。像前面那个 issue，他已经知道怎么修，也有把握 Agent 能做好，就完全放手，等最后的 diff。重构这类探索性工作，他不想让 Agent 自己跑一大圈回来给出他不喜欢的东西，那是浪费 token 和钱；他也想自己理解代码库，因为"agents tend to overcomplicate things. They kind of replicate the patterns they learned from the internet and the patterns on the internet are bad"，他想把自己的设计品味注入进去。

九、对"不懂的那部分烂了"的回答

Mihail 追问：你说前端完全交给 Agent，如果有一天前端烂到没法维护怎么办？Mario 说要看你的业务和用户能忍多少。有些代码烂了也可以一直不碰。否则就是自己去学、去重构或重写，或者请公司里的前端专家帮忙。

他观察到，原本负责某个模块、在 Agent 出现之前就积累了系统知识的工程师，用 Agent 时不太会把自己困住，因为他们会守住软件里的不变量和设计品味。问题多出在外行进来的时候，比如产品经理觉得往代码库里提交前端代码很好。他的结论是不要让它发生：至少在设计 API 和模块时人要在场。只要边界划好了，就算某个模块是垃圾，它也被隔离着，重写或重构都容易。如果已经困在角落里，可以让 Agent 协助，但不能指望再派一百个 Agent 来修，"chances are they will come up with even more garbage"。

节目最后他说，他也不知道什么是最好的做法，这只是对他有效的方式；以技术人的角度看，现在是很好的时代，"Experiment, throw [stuff] at the wall and see what sticks"。

十、和课程的对照

  • 第一讲用两百行代码写一个 Agent 循环；Pi 是这种"小核心"思路做成的完整产品，作者的论点是模型已经知道怎样当编程 Agent，给 bash 和文件读写就够了。
  • 第四讲 MCP 与工具调用 讲 MCP 的用法；这期给出一个反方观点：工具定义占上下文，能用 CLI 就用 CLI。
  • 第七讲 定制你的 Agent 配置 讲 AGENTS.md、提示模板和扩展；这期是一份实际在用的 AGENTS.md，以及"模型不一定听，要靠 linter 和钩子兜底"的经验。
  • 第八讲 让代码库适合 Agent 和这期第八节讲的是同一件事：模块边界清楚，Agent 才找得到上下文。
