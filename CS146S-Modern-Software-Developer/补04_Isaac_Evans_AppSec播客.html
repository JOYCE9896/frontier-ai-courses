补充四：Isaac Evans 谈 AI 时代的应用安全

CI 不再是安全的中心关口：一头是用大模型连续跑几天的后台漏洞挖掘，一头是嵌进编程 Agent 循环里的快速确定性检查；用规则和指导去"影响模型的想法"，安全工程师变成管理一批安全 Agent 的人，以及模型本身为什么难以信任

讲者：Isaac Evans（Semgrep 联合创始人兼 CEO）；主持：Chris Romeo（The Application Security Podcast）
这一篇不是课堂讲座。Isaac Evans 11 月 5 日（第 7 周，安全）在 CS146S 做过客座讲座，但那一讲没有公开课件和录像。这里整理的是他上过的一期公开播客：Isaac Evans - AppSec in the Age of AI（The Application Security Podcast 频道，2026 年 7 月 28 日上传，49 分 09 秒）。本文依据 YouTube 自动生成的英文字幕整理；字幕把 Semgrep 写成 "SEGRP""Samrup""Sim Gre" 等，已按上下文更正。字幕没有标出说话人，归属按内容判断。
和课程的关系：第 7 周讲安全，包括静态分析、依赖漏洞和密钥泄露、提示词注入，以及用 Agent 辅助分诊和修复。Semgrep 是这门课的开源合作伙伴之一。

一、他怎样走进安全领域

他最早的兴趣是密码学（"back when crypto meant cryptography and not something else"），写的第一批程序是密码分析和凯撒密码。另一个兴趣是机器人。在 MIT 读本科三年级时，日本海啸摧毁了福岛核电站，电站里需要有人去关阀门、搬管道，市场上找不到能在高辐射环境下做这些事的机器人，最后是退休的电站工人自愿进去。这件事促成了 DARPA 的机器人挑战赛（DRC），要求造能做救灾任务的机器人。

他是 MIT 参赛队里仅有的三名本科生之一。机器人由 Boston Dynamics 制造，比赛成绩不好。他印象最深的是队里的博士生"almost like they had negative security knowledge"：他们懂的安全知识刚好够绕过安全控制，好把代码更快装上机器人、早点毕业。一台精密的机器人跑着很不安全的代码，这是他后来创办 Semgrep 的原因之一。Semgrep 2017 年创立，做应用安全平台。

二、CI 不再是安全的中心关口

主持人问 AI 会怎样在未来三到五年改变应用安全（AppSec）。他说可能不用五年，"just in the past six months"，从 Opus 4.6 开始，安全从业者的工作方式已经被明显改变。

过去把 CI（持续集成，代码合并前自动跑的检查流程）当作控制点：开发者怎么写不管，到了 CI 有代码审查、有安全检查。这比更早的做法（上线前扫描、要跑几天几周的后台扫描）快。现在 CI 正在失去中心位置，取代它的是两样东西。

1. 往右：用大模型连续跑几天的后台挖掘

Semgrep 提前拿到过 Anthropic 的 Mythos 模型，帮着改进过它，也有客户把它和 Semgrep 一起用。他的结论是："you're going to want to spend days of compute if not weeks you know just hunting for interesting vulnerabilities"。

他还提到一个角度：攻击者今天用不到 Mythos，而 DeepSeek 之类模型找到的漏洞和 Mythos 找到的并不完全重合。所以也可以问"现在的攻击者用的是什么模型"，用那个模型去扫自己的应用，尽量覆盖攻击者会看到的东西。

但他提醒，靠一个个删 bug 得不到安全，"Like fundamentally like a whack-a-mole game"。

2. 往左：嵌进编程 Agent 的循环里

九个月前他还认为代码是人写的还是 Agent 写的都无所谓，一样扫描。后来 Semgrep 做了一个给 Cursor、Claude Code、Codex 用的插件，成了公司增长最快的产品。好处在于：

"the advantage of being in the loop of the coding agent is that you can sit there and force the coding agent to try again and again and again until it gets it right."

这要求检查足够快。扫一段代码不能花两分钟，Semgrep 不到一秒就能扫完，然后告诉 Agent "this does not have the security properties we want, regenerate it"。模型能写出很多功能相同的版本，只有其中一部分满足你要的安全性质。

主持人问要重写多少次。他说一般一到两次就过了，不需要上千次。这些检查相当于放在代码生成循环里的快速安全测试。另外，"the models do better with more constraints"，例如有类型检查时模型写的代码 bug 更少，安全也是同样的道理。

3. 两头连起来

有人说模型是概率性的，不能信它有安全性质。他的回应是"humans are also probabilistic security reviewers"。他看到的做法是：后台用 Mythos 找到问题后，分析根因，写几条简单的 Semgrep 规则，放进代码生成插件里，"we just never want to see you generate code that looks like this"。这些规则不一定针对漏洞，也可以是安全弱点。

Semgrep 内部也这样用：CI 里 LLM 给出代码审查意见时，同时让它生成一条能检测这类问题的 Semgrep 规则；工程师看了觉得"I never want to see that again"，就提议把规则推广到全组织的代码生成循环里。

四、确定性检查和"影响模型的想法"

除了代码漏洞，插件里还可以放：检查依赖包有没有已知的 CVE（公开登记的漏洞编号），因为模型有训练截止日期，不知道昨天刚公布的漏洞；或者"我们组织的令牌长这样，绝不要提交这样的字符串"。模型也许知道，但用确定性的工具检查更快更便宜。"we're not ideological but in the coding agent case the determinism ends up being pretty valuable."

他认为应用安全里最大的机会是更一般地引导模型。例如给 Claude Code 写一份关于依赖的指导："We don't want you to introduce a dependency if it was published yesterday and it has three stars on GitHub." 以前很难让开发者遵守这种指导，他们会按自己的想法做，问题拖到 CI 再处理；模型则会说"whatever you say boss"，自己把代码写出来，不引入那个依赖。

过去影响开发者的办法只有安全培训，"which I've been through it is not the most exciting thing in the world and has limited knowledge retention"。现在可以直接影响模型的安全取舍，所以安全团队的工作变成"teach this model what the business case for security tradeoffs in our organization looks like"。主持人指出这意味着规则按组织定制，和过去所有客户共用一套规则的静态分析（SAST）不同，他表示同意。

五、安全工程师会做什么

他说要先回答软件工程师现在是什么。他讲了 Anderson Cooper 采访一位音乐制作人的故事：对方没有任何技术能力，Cooper 问他靠什么拿钱，对方说"For the confidence that I have in my taste"。他觉得软件工程师现在离这个不远：靠品味和判断，能预见"这样建系统"以后是否站得住。工程师变成了一群初级工程师的管理者，也要有产品经理式的思考。

安全工程师也一样：管理一批虚拟安全 Agent，让它们做大部分琐碎工作，自己只看 Agent 处理不了的异常情况；把精力放在跳出"打地鼠"，能证明业务处在可接受的风险水平，以及发现新的威胁。他认为安全的需求会更多，因为 LLM "don't find the simplest solution to a problem. they find like the fastest solution"，代码可能比人写的复杂得多，"complexity as we know is the enemy of security"。

给做了十年应用安全的人的建议：安全知识本来就过期很快，要保持敏捷；多参加会议、和社区交流，了解哪些团队已经用好了虚拟 Agent；亲自上手用这些技术，"there's never been a better time to be an IC"（IC 指不带团队的个人贡献者）。

六、模型公司会不会吃掉安全公司

他说危险是有的，但不一定来自模型公司直接竞争：很多应用安全产品在新环境下本身就过时了，"all these companies that had product market fit in the old world do not have it in the new world"，Semgrep 也一样，所以才做面向编程 Agent 的新产品。SAST 和 SCA（软件成分分析，检查依赖）这些整个品类都会变样。

他拿云计算类比：当年也有人问 AWS 会不会把云安全全包了，结果云安全里有大量问题要解决。所以独立安全厂商仍有空间，只是做的事可能和今天不同。他也承认，如果模型继续指数级进步、走向 AGI，模型公司之外的所有公司会怎样，他不确定。

七、信任：模型是最难逆向的二进制

主持人说自己做安全快 30 年，什么都不信。他接着说，自己做过逆向工程工具：

"the models are the most inscrutable binaries we've ever seen ... Even the the most obfuscated binary is more tractable to predict the behavior of than a model."

他引用 Anthropic 几个月前发表的研究：如果想在训练数据里投毒，让某个特定触发条件引出模型的异常行为，需要多少样本？答案和模型参数量关系不大，大约 250 个样本就够。相比之下，Ken Thompson 的经典论文 Reflections on Trusting Trust 里在编译器中藏后门的攻击"child's play"：训练语料太大，不可能完全理解，就很难推断模型的安全性。

他更信 Agent 写的代码，而不是 Agent 直接执行的动作

问他多信任 Agent 写的代码。他说代码可以被机械地解释、是确定的、能推理它的结构，所以比"让 Agent 直接去执行一个动作"更可信。有明确的判定标准时，Agent 表现最好，例如 Mythos 给 Firefox 写利用代码："model don't stop until you have control of the instruction pointer"，能不能控制指令指针是一个可以直接验证的条件。他认为模型写代码会比人好，多数情况下已经比人好。

但他也说，最近几个月 Semgrep 发现的漏洞，多数是 Claude Code 写的代码里的，这也是他们做插件的原因。

多加审查不等于安全

主持人提到有人用 Claude Code 写、用 Codex 审。他说多加 Agent 审代码"fundamentally kind of like a token slot machine"：不停往里投 token，也许能找到好漏洞，但靠这样得不到可信和安全。所以他更看好生成那一端：插件相当于额外的安全测试，能得到"模型没有生成任何可能 SQL 注入的代码"这类性质。

更根本的办法是用更安全的语言重写软件，例如用 Rust 代替 C，消除整类缺陷。但不会消除全部漏洞：coreutils 的 Rust 移植版刚公布了约 15 个 CVE。他猜以后会发明新的编程语言，安全性质更强，更适合 LLM 时代。

八、业务逻辑漏洞和跨仓库推理

主持人认为 SQL 注入模式固定、容易找，业务逻辑漏洞（不违反语法规则、但违反业务意图的漏洞）会重新变多。他说 LLM 在找业务逻辑漏洞上很强，但"找到漏洞"和"写出没有漏洞的代码"是两类问题。

他最佩服的是 LLM 能跨模块、跨仓库推理业务逻辑漏洞。Semgrep 在做跨组织缓存和管理上下文的工具：有一百个仓库，要推理它们之间的交互，怎样把上下文正确地交给 LLM。他说在用 Mythos 的客户里，直接把仓库丢进去说"find vulnerabilities"的团队，和用工具引导上下文（"go look at this now go look at this and with this context"）的团队，最后得到的 CVE 数量差了 10 倍，"not an exaggeration"。是模型还是 Harness 的功劳？两者都有。

九、氛围编程的人越来越多

主持人说有企业一次把 200 个市场部的人加进 GitHub。他说客户也问"Wait, where'd these new developers come from?" 对这些人说"你有 SQL 注入"没有意义。他认为模型公司在想办法，以后模型大概不会再写出 SQL 注入，但"Today they're actually worse than the average developer"。

他类比汇编程序员看到别人开始用 C 这样的高级语言：不懂寄存器，但生产力的提升值得。他自己的体会是 LLM 有好的测试套件时表现很好，而设计测试套件需要氛围编程者通常没有的专业知识。所以写代码之外的那些工作（安全、性能、测试保障）会更重要，更需要专业人士。

他还提到开源社区里的反应：HashiCorp 联合创始人 Mitchell Hashimoto 发起了 Vouch 项目，只和自己网络里有人担保、质量标准相近的人合作；有人发氛围编程的项目，评论说"I would just vibe code my own garbage but then it's my AI slop rather than your AI slop"。以前 MIT 的邮件列表里常有哈佛学生说"我有绝妙的点子，只缺一个技术合伙人"，"now I think a lot of people are like, 'Oh, Claude is my technical co-founder.'"

十、给安全从业者的话

最后的建议是把模型看作机会。模型会毁掉一些产品品类，也会带来新的安全问题，但"you're going to be able to influence the models in a way that you could never influence developers"。可以把模型当作一批要管理的虚拟安全 Agent，也可以参与搭建公司里自动生产软件的"工厂"，让它从一开始就符合业务的风险要求。

他也承认会有一团乱：LLM 到处发现零日漏洞，今年要打大量补丁；会有更多安全状况很差的氛围编程应用上线，安全人员要收拾。他举了一个例子：Mythos 在 FreeBSD 或 OpenBSD 里找到的一个代表性漏洞，后来发现和七年前另一个项目里的一个补丁一模一样，也就是在训练数据里。他认为这仍然是好事，因为安全人员一直在重复修别家早已修过的同类问题，系统化地利用这些知识就是机会。

他欣赏的客户团队没有想拦住 AI，他们对开发团队说"we want to help you build that factory"、从一开始就把安全要求放进去的。
