第三讲：复杂代码库的高级提示与上下文工程

开源合作伙伴计划，从 vibe coding 到有方法地写生产代码，规格驱动开发的 RePPIT 框架（研究、提议、计划、实现、测试），用它给一个 Mint 克隆加功能的完整演示，"聪明 token"与"笨区"，什么时候清空和压缩上下文，任务委派的分级，以及 Superpowers、OpenSpec 等框架

主讲：Mihail Eric
资料来源：课件、课堂转录（2026 年 9 月 29 日；本文依据课件和转录整理）
课程推荐阅读：The Context Tax: When to Compact、OpenSpec、Superpowers

一、开场事务

申请进课的截止日期已过，没收到通知的同学大概进不了学分名额，但欢迎旁听。

额度合作方之一 Factory（估值约 50 亿美元的编程 Agent 创业公司）的 Ashley 周四课后会办一个 20 到 25 分钟的工作坊，介绍 Factory 平台并给大家开通账号，自愿参加。Factory 的 CTO Eno 几周后会来做客座讲座。

这一讲正式公布开源合作伙伴计划，筹备了几个月，Eric 认为这是这一期课最让人兴奋的部分：

  • 每位同学填一份志愿表（邮箱、Discord 和 Slack 信息，各合作方用不同渠道和社区交流），课程用类似稳定匹配的方法分配，让每个合作方都有学生，每个学生尽量排到靠前的志愿。
  • 学期中途会换一次，所以至少跟两个合作方合作，也可以更多。要练的就是"上手几个大型陌生代码库"这件事。目标是至少四次贡献，每次的截止日期写在课表里。
  • 每个合作方至少有一位专门的维护者对接，主要负责审 PR、把代码合进去。有些还会办双周答疑，有些会亲自来见大家，比如 cmux 的人下周会来，他会演示怎样同时并行驱动几十个 Agent。相当于有一条直通项目负责人的"快速通道"。

二、这一讲要解决的问题

课程的目标之一，是让理论功底扎实的好开发者具备在工业界成功的工具，这一讲讲的大多是业界工作里真会用到的东西。

最需要学会的一件事，是在远超几个本地文件的规模上驱动编程 Agent：几百上千个文件、几百万行代码，像 Google 那种规模。到了这个规模，就会撞上上下文窗口的固有限制。有的 Agent 号称有一百万 token，但 token 并不都一样好用，真正能用来做有效工作、性能还没下滑的，远少于一百万。所以在大型复杂软件上工作时要更有章法。大家都会 vibe coding 和普通提示，但只能走到一定程度，这是 Eric 的主要论点。

课件上的目标：从临时起意的提示，走向稳健可靠的同步 AI 开发流程；用 AI 快速上手陌生代码库，系统地完成复杂的编码任务。具体学三件事：怎样快速上手大型陌生代码库；用 RePPIT 框架做规格驱动开发；了解其他规格驱动的 AI 开发框架。Eric 说规格驱动开发（spec-driven development）大概是业界解决较难任务的标准做法了。

三、从 vibe coding 说起

"vibe coding"这个词是 Andrej Karpathy 在 2025 年 2 月的一条推文里提出的（他是斯坦福校友，出自李飞飞的实验室）。按他自己的说法，那是洗澡时冒出的念头：完全顺着感觉走，忘了代码的存在，全部接受，报错就贴回去。Eric 说这是条很火的推文，还因此有了维基百科词条；但要在困难的代码库里解决难题，就得超越 vibe coding。有人管这门课叫"vibe coding 课"，他不希望这样，这门课讲的是使用编程 Agent 的系统化原则。课件把这一点写成一句话："vibe coding 搅乱了预期"。

思考题：你会怎样做一个 Mint 的克隆？Mint 是早年的个人记账应用，可以输入预算、绑定信用卡、追踪开销、看各类花费，后来被 Intuit 收购，现在也有 Monarch 等同类产品。再进一步：假设已经有一个功能完整的 Mint 克隆，要给它加功能。要在生产规模上做到，就必须有方法地使用编程 Agent。

课件列出写生产级 AI 代码的原则：

  1. 理解陌生的代码库，尤其是你没贡献过、不是你写的代码，要熟悉到足以指挥 Agent。
  2. 提出几种解决方案。
  3. 挑出最有希望的一种，做计划。
  4. 实现。
  5. 测试。

有人会说："我们做测试驱动开发，先写测试再倒推实现。"也行，Eric 不规定顺序，核心部件一样，只是排列不同。这就是他日常工作里常用的框架，他认识的人也用类似原则，只是叫法不同。

四、RePPIT 框架与演示

RePPIT 是五个步骤的首字母：Research（研究）、Propose（提议）、Plan（计划）、Implement（实现）、Test（测试）。演示的任务是给一个极简的 Mint 克隆加一个功能：显示各类别花费随时间变化的趋势线。Eric 坦白这个应用本身就是 vibe code 出来的，他不是前端开发者，"懂得足够闯祸，但不够有用"，连它用的是不是 Vue 都不确定。应用现在能上传 CSV、检测异常（比如一笔"异常大额消费"，数据是编的）、画基本图表、设预算上限、按类别查看明细，但还没有趋势线。他每一步都用一个自己写的 Skill，在 Cursor 里演示。

1. 研究（Research）

这一步是用代码库的有用信息给 Agent 的上下文"播种"，但不把原始代码全塞进去，而是把代码库提炼成一个精简的表示，让 Agent 有足够的了解，能开始提方案。

"research codebase"这个 Skill 的提示词写得很明确：研究阶段只负责记录代码库里已经存在的东西，不负责实现，不提方案，它的任务是写清楚今天存在的"行为契约"；只记录现状，不建议改进。它可能会读提到的文件，把请求拆成几个研究方向，按清单逐项做。重要的是最后的产物：一份结构化的研究文档，描述它对各组件、各部分的了解，可以附上代码引用。提示词也规定了输出格式。

有同学问这个提示词是不是做过 A/B 测试。Eric 说"A/B 测试"说重了，但确实测过：他在大约一年到一年半的实际开发中迭代写成，从一个文档开始一行行加，看到研究阶段有不满意的地方就改。它也提交在团队共享的仓库里，其他开发者也在用、在测，有人会说"这里退化了，改一下"，这是他们代码库里被审视得最多的代码之一。提示词里提到的 Context7 是一个获取第三方最新文档的 MCP 服务器，只关心本地代码可以删掉那一行。如果 Skill 已经提交在仓库里，克隆仓库时就自动有了；也可以把 Skill 打包成插件，在整个组织里分发。

研究生成了相当详细的文档，它有两个用途：一是给 Agent 播种，后续步骤都建立在它之上；二是帮助他自己理解。他想知道得足够多，能分辨好坏，不需要每个细节，但要有心智模型，比如知道有前端和后端、用了 Vue、后端模型是什么形态，必要时能自己去看代码。Eric 坚持认为，到这一步人仍然需要对代码的现状有心智模型。

有同学问：如果项目里已经有很多描述结构的 Markdown 文档，是跳过研究、让 Agent 读文档，还是重做一遍？Eric 说完全取决于文档质量。维护得好、准确反映代码，就复用它，把 Skill 改成以它为起点；但文档常常维护得不好，在烂文档和从头开始之间，他选从头开始，让 Agent 自己建立理解，别被过时的信息带偏。最佳做法是让过时文档要么不存在，要么被更新，现在可以让编程 Agent 定期跑一跑来保持文档最新。

2. 提议（Propose）

到这里只有一份描述代码库现状的通用文档，和要做的功能无关。现在要变得有立场了：把功能需求交给"make proposals"这个 Skill，它的意思很简单：基于代码库的精简表示，为这个功能提出两种截然不同的方案。可以要三四个，但他发现超过两个收益递减。有同学问为什么是两个：基本是经验法则。他打了个比方，熟悉机器学习里 PCA 的话，他想要的是两个互相正交的主成分方向，逼 Agent 找到解空间里两块不同的区域，通常足以覆盖解空间，又给他自己的判断留了余地；代码库更大时可能要重新考虑。

每个方案包括：背景、方案概述、关键改动、取舍、验证方式、未决问题。不一定要写成文件。这一步和下一步是用户作为专家最应该参与的地方。演示里两个方案一个是服务端改动（上传接口返回多序列数据），一个是在客户端基于已上传的交易计算，纯前端改动，更轻量。现场演示能少碰后端就少碰，他选了第二个。平时他会仔细看取舍，作为懂产品需求、系统需求和系统限制的技术人员做选择。

要不要再写一个 Skill 让 Agent 自己选方案？也许可以，那样选择就被包进 Agent 自己的决策里了。但 Eric 认为，在编程越来越强的今天，人最有用的地方主要有两处：意图与架构，以及代码审查。人应该作为懂产品需求、系统需求和约束的专家插进来，在早期就决定 Agent 怎样运作和实现，把规格、研究和计划把好关，这是今天人力杠杆最高的地方之一。两年后还是这样吗？难说，他认为即使编程变得无比强，早期阶段可能仍需要人。"我们在录像，两年后你们可以来核对。"

也有同学问：外壳越来越强，内置的计划能力已经很好，还需要自己的流程吗？Eric 说 Claude 和 Codex 的内置计划确实很好，他也不总用自己的计划提示词；但他仍然觉得引导 Agent 的行为、把产物和输出标准化有价值。他会公开这些提示词，鼓励大家拆开改，删掉不喜欢的行。以前教这门课时，有个做医疗的学生按自己的需要扩展了 RePPIT，这不是定死的流程，而是拆解复杂问题的起点。

3. 计划（Plan）

选定方案后做计划。他的 Skill 基本就是：这里有一份设计文档模板，根据选定的方案填好它（课程第一版时的设计文档模板也公开过）。为什么是这个格式？因为他喜欢、容易读，里面有他做判断需要的信息，是长期打磨出来用来评估 Agent 即将实现的方案质量的。设计文档包括：代码库现状、功能需求和非功能需求、设计决策与取舍、技术设计（带一些代码级细节，他想看到哪些文件要改，几乎像一个 diff；模板里那句要求标出行号的大写字母一看就是人写的，是他几个月前加的，为了让计划落到代码层面）、测试和要跑哪些测试、可观测性、未来考虑、安全、发布等。

其中最有价值的一项，是明确写出不在本次实现范围内的东西。他把这些放在"未来考虑"里，并写明"别碰这些，只实现范围内的工作，其他一律推迟"。这能防止 Agent 跑偏去做无关的事。这一步他会很投入地审读。

有同学问研究的输出要怎么验证。Eric 说他现在对研究阶段的验证比以前少了，因为 Agent 读代码、提炼成精简表示的能力已经很强，研究其实是信息压缩，Agent 很擅长；他更担心的是实现。验证也发生在后面，尤其是测试。

4. 实现与 5. 测试

实现的提示词"极其复杂"，Eric 开玩笑说它几乎不需要是个提示词，但缩写里需要一个 I，所以就有了它，基本就是让 Agent 执行计划。

有意思的是，Cursor 在实现时会自己打开浏览器操作应用，造一份合成数据，通过 CSV 界面上传，把实现和测试合在一步里做了。六个月前还做不到，现在模型已经好到会在实现后想"我应该自己测一下"。Cursor 等很多 Agent 内置了这个能力，没有的话可以加 Playwright MCP 之类让外壳能操作浏览器的 MCP 服务器。这种浏览器操作就是在检查行为契约：上传 CSV，应该看到新功能。

单元测试、集成测试、冒烟测试是验证方案最有价值的手段。如果相信编程会越来越强、实现细节越来越不重要，那么我们关心的是输入和输出，必须严格检查输出。现代开发者的大量时间会花在给输出定要求上：它该怎样工作、该有哪些行为。

行为契约之外，还有性能、质量、可读性等问题，归代码审查管。他演示了一个简单的代码审查 Skill（不一定推荐，只是激发好奇），检查 diff，输出"必须改""建议改""可以考虑"三档，像红黄绿灯，一个 Skill 里同时管安全、性能、风格、一致性和边界情况。实际中人们常用四五个 Agent 各管一块，在 GitHub 上开 PR 时由 Action 运行它们，再由一个协调 Agent 汇总成一份报告。

五、课程公开的 RePPIT Skill 文件

课程把演示用的 Skill 放在了共享文件夹里，共六个，每个是一个目录，里面有 SKILL.md。它们的头部元数据都写了 disable-model-invocation: true，意思是模型不会自己调用，只在用户输入 /research-codebase 这类命令时才运行，因为每一步之间都要人来把关。各自的要点：

  • research-codebase：照现状记录代码库，不做任何建议或评价。行为契约三条：只记录今天存在的东西，不提改进、根因分析或后续工作；结论要给出具体文件路径和行号；先完整读完用户提到的文件再拆分工作。步骤：读提到的文件；把问题拆成几个研究方向，列内部清单；方向互相独立时并行探索相关目录，必要时看 git 历史，涉及第三方 API 就用 Context7 查最新文档；全部探索完再综合，实际代码优先于历史文档；把研究文档放在顶层 research/ 目录。输出格式：三到六句的总体摘要，按组件分组的详细发现，引用写成 path/to/file.py:123-145。
  • make-proposals：基于研究文档提出最多两个方案，没有研究文档就不做。步骤：记下用户请求；完整读研究文档，提取约束、相关模块、依赖、数据流和以往决策；推出候选方案，每个写明主要改动、受影响的代码路径、需要的迁移或配置更新、发布考虑，按与约束的契合程度排序；规划验证手段（测试、实验、可观测性），列出关键未知和需要先补的研究。输出模板就是课上看到的：背景（请求、所用研究的来源），然后每个方案的概述、关键改动、取舍、验证、未决问题。研究没覆盖到请求时，要指出缺口，建议先补研究再提方案。
  • plan：用设计文档模板在 plans/ 下写一份计划，不动代码。先澄清改动范围、约束和时间；照模板结构写；测试、可观测性、发布、安全几节只在和这次改动有关时才写，无关就空着；不要实现任何改动；只做被明确要求的改动，方案保持简单。模板（design_doc_template.md）的章节是：现状、功能和非功能需求、设计决策（选什么、为什么、考虑过的取舍和替代）、技术设计（核心组件和数据模型的带类型接口、集成点、改动文件）、分阶段的实现计划、测试策略、可观测性（日志、指标）、未来考虑（可能的增强、已知限制）、依赖、安全、发布策略、参考资料。"改动文件"一节要求列出的必须是这次改动唯一涉及的文件，并且全大写地强调"必须写出要改文件的行号"。测试策略一节有一条提醒：不是每个改动都要写测试，要想清楚测试什么时候真有用，别让生成的测试过度 mock 代码库。
  • implement：只有一句话：实现某个计划文件里描述的计划。
  • review：审查所有未提交的改动（暂存和未暂存的）。先收集上下文：git status --porcelain、git diff、git diff --cached、git diff HEAD、git log --oneline -n 5；再从安全、性能、风格、一致性、遗漏的边界情况、依赖影响、集成风险几方面分析；输出一句话摘要和一份按优先级排列的行动清单，用红、黄、绿三档标出必须改、建议改、可以考虑，每条带文件和行号。
  • explore：探索代码库里一块陌生的区域并向用户汇报：这块功能的简介和用途，关键入口函数及其路径，调用关系和依赖（包括外部库和服务），文件和目录结构，数据流和状态（重要模型、输入输出、副作用）。做法是先读主入口文件，顺着 import 画出依赖，浏览测试和示例看预期行为；记下运行需要的准备步骤，但没被要求就不执行代码。

六、上下文：清空、压缩与"笨区"

有同学问了一串好问题：每一步都写文档、开新会话吗？什么时候清空上下文重来？某些步骤需要更强的模型吗？Eric 说这些多少是艺术而不是科学，但已经有人在研究。

  • 压缩。他推荐了一篇研究压缩的博客（The Context Tax），研究什么时候压缩、对成本有什么影响、积累多少 token 后该压缩。一个结论是，视模型不同，大约在 25 万到 45 万 token 之间。他们还研究了 Agent 实际用到更多上下文的频率，结果并不常。所以虽然号称有一百万 token，真正有用的可能接近一半。实际结论：常压缩。
  • 清空。演示里他做了一件不推荐的事：选定方案后没有清空上下文，于是两个方案都还留在里面，尽管已经说了用方案二，上下文里仍有另一个没选方案的 token，可能让 Agent 搞混。一般他倾向于清空：看到几十万 token 时，就把相关信息写进文件，在新的上下文里读入这个压缩后的表示再继续。
  • 模型强弱。前几个阶段用很强的模型，研究、提议、计划是大部分思考发生的地方；实现乃至测试可以用轻一些的模型。

课件第 13 页画了一个上下文窗口：从上往下是系统提示词、AGENTS.md/CLAUDE.md、任务相关上下文，它们占据上下文窗口里前二分之一到四分之三的"聪明 token"；再往下，虚线以下是"笨区"。这个比例更多是人们注意到什么时候开始出问题的直觉。

课件总结的最佳实践：

  • 仔细地审查你的规格，尤其积极参与研究、提议和计划三步。
  • 很大的功能拆成任务清单。
  • 每完成一项，把 Agent 的工作记录在一份书面产物里，它就成为继续下一项的上下文。
  • 时刻注意上下文窗口，只有二分之一到四分之三是"聪明 token"。

七、什么时候用更重的流程

刚才走完五步、做计划、审查、实现了一个功能，可什么时候用普通提示就够，什么时候换更重的做法？课件列出四档：直接提示（"上帝来掌舵"）；做一个计划（直接进 Claude 的计划模式）；先研究再计划（在计划前多花时间建立上下文）；研究加计划重复多轮。

课件第 16 页引用了一张图：横轴是压缩和上下文工程的投入，从"直接和 Claude 聊"到"做个简单计划再执行"，到"做一次研究、做计划、分阶段实现"，再到"多轮研究、拆成多个计划、很多次实现会话"；纵轴是能解决的最难问题，从改文案、小修复，到跨三五个文件的小功能，到中等复杂度的新应用和跨项目跨仓库的中等功能，再到大重构和全新的大功能。坐标轴会随模型质量移动，但方向上是对的。

Eric 承认今天演示的做法很重：花了 45 分钟讲提示词，只为给一个 Web 应用加一个看板功能。改个文案、小修小补，直接和 Claude 或 Codex 说就行。跨多个文件的小功能，开始考虑做计划：你对所有文件都熟吗？也许不，那就保险起见做个计划。中等功能，尤其是大重构或迁移，就要多轮研究、提议和计划，用不同会话和子 Agent。他日常工作里的大项目会拆成多个 issue，每个 issue 一个 Agent，把 issue 叠起来，让后面的 Agent 在前面的工作上继续，这时他会很用心写 issue 描述。

八、其他框架与规格放在哪

  • Superpowers：有立场的端到端引导式流程，用来解决复杂任务，以测试驱动开发为基础，是一组用于创建规格和计划、实现、测试的 Agent Skill，内置并行。Eric 说它基本就是今天讲的框架"打了激素"，在 GitHub 上有约 30 万星。打开仓库看，它的核心就是一组 Skill：头脑风暴、写计划、执行计划、代码审查等，全是今天讲的东西。
  • OpenSpec：一个轻量的流程，用来写规格、实现计划等；它有一套很好的方法来追踪作为"唯一事实来源"的规格的变化，并在 diff 产生后把它们合并。

规格放在哪？可以放在 Linear 里，也可以像 OpenSpec 那样放在本地或 Git 里；代码库各部分的设计取舍和决策点可以放在一个 .notes/ 目录里。
