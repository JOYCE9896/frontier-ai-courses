补充六：Eno Reyes 现场演示 Factory 的 Missions

让 Droid 连续工作几小时到几天：先把需求变成功能清单和验证合同，再由编排者带着一群工人按里程碑一项项做完；为什么能跑这么久全靠验证，Skill 怎样在任务中自我修正，什么时候不该用，以及"产品工程系统"的设想

嘉宾：Eno Reyes（Factory 联合创始人、CTO）· 主持：Mihail Eric（本课程讲师）
资料来源：The Build System: Mission Impossible with Eno Reyes, CTO Factory AI（2026 年 3 月 13 日，1 小时 23 分；本文依据 YouTube 自动生成的英文字幕整理）
说明：这不是一次课堂讲座。The Build System 是本课程 YouTube 频道 The Modern Software Developer 上的访谈节目，由讲师主持，嘉宾现场用自己的工具做一个真实项目。Eno Reyes 在 2026 年 10 月 22 日给本课上过客座讲座，见第九讲：能验证，Agent 就能解决；第九讲讲的是验证的道理，这一期是半年多以前录的现场演示，可以当作第九讲的实操版来读。

一、嘉宾和 Factory

Eno Reyes 最早做认知科学和神经科学，用深度学习处理 fMRI 和 EEG 数据，后来去了 Microsoft 和 Hugging Face，在 Hugging Face 帮很多公司做代码模型，当时大家要的都是自动补全。他认为 Copilot 掀起了 AI 编程这一波，但补全式的产品不足以撑起"真正自主的软件组织"。Factory 大约三年前成立，使命是"bring autonomy to software engineering"（给软件工程带来自主性）。

他现在把 Factory 看作"一个做企业产品的 Agent 研究实验室"：一边做前沿研究，一边靠企业客户提供经济来源和真实反馈。他要的是"people who will not buy your thing if it doesn't work"（东西不好用就不买的客户），所以核心客户是大型企业。平台有三部分：Agent（叫 Droid）；Agent 就绪度工具，帮组织判断 Agent 能做什么；Agent 效果度量，衡量影响和投入回报。

主持人补充：大多数软件不在新项目（green field）里，而在大企业的旧代码库（brownfield）里，Factory 一开始就面向后者。Eno 说另一面是做企业的"trusted adviser"（可信赖的顾问），和客户一起摸索这种变化对人、对组织、对软件意味着什么。

二、今天要做什么：一个内部用的项目管理系统

演示的是 Missions，当时刚推出、内部已经大量使用的功能。普通用法是在终端里和 Droid 对话；进入 Mission 模式后，Droid 会先建好一大批功能和验证标准，然后连续工作几小时甚至几天。Eno 说内部最长的一个 Mission 连续跑了 16 天。

操作过程：

  1. 在 projects 目录下新建一个项目，起名 arrow，输入 droid 打开界面。他开着最高自主级别（auto high），因为是在沙盒里，比较安全。
  2. 换模型。Droid 不绑定模型，可以选 Opus、Sonnet、GPT-5.3 Codex，或者 Factory 在美国托管的开源模型（他说 Kimi 很好）。他开了 fast 模式。
  3. 输入 /enter-mission 进入 Mission 模式。在这里可以给不同角色分别选模型：编排者（orchestrator，和人对话、管全局的那个）用了 Opus 4.6 fast，"会有点贵"。
  4. 用很口语的方式描述需求。

他给的需求大意是：做一个受 Linear 启发、专门给 Factory 用的项目管理系统；可以调用公司的 product management skill 了解 Factory；最想要的新东西是"归因"（attribution）。他解释，现在工单、PR、触发它们的信号（Sentry 报警、客户反馈）之间明明有关联，数据模型里却没有，想回答"我们为什么做了这个功能""这个功能坏了哪些客户会不高兴"就得靠外部系统拼起来。其余部分照常见项目管理系统的习惯做，方便迁移。最重要的一条：

"I'd like to see an MVP of this before we add any heavy features so I can tweak the design system before we implement all the nice to haves."

技术栈他说无所谓，但公司是 Next.js 加 Vercel，沿用也可以。

这里用到的 product management skill 是 Factory 自己写的，它引用公司 Notion 里的产品资料：使命、价值观、产品定位、研究方向。他更愿意用 Notion 当"source of truth"（唯一可信的来源），因为全公司都能改，比写进 AGENTS.md 再等人或代码去更新要及时。

Droid 先问问题

Droid 先调用了两个内置 Skill（mission planning 和 defining mission skills），再调用 product management skill，检查了电脑配置（什么机器、多少内存），然后开始提问：给谁用？（内部用，不是产品。）归因要追踪哪些信号？Droid 自己列出 Sentry、客户反馈、GitHub、内部事故、指标回退，Eno 说"you're reading my mind"。要不要先做一个灵活的信号抽象？（要，先做最简单的。）Docker 没开，存储用 SQLite 行不行？（行。）Droid 还从 Skill 里知道 Factory 按"pod"组织团队，问要不要按 pod 建团队。Eno 选了每个团队一个平铺的列表，把项目当作父子工单处理；字段用标准的就行；部署这一环先不做。

Eno 的解释是，他给的需求一个资深工程师看了也会问"spec 呢"，Mission 的提问阶段就是把这些补出来。

三、Mission 和普通的计划模式有什么不同

Droid 接着提出里程碑：先搭一个能跑通的骨架（walking skeleton），然后是工单管理、归因、团队视图。里程碑是检查点：每个功能做完都会单独验证，到了里程碑再做一次更重的验证。如果里程碑验证不过，说明某个功能虽然单独验证通过了，要么实现得不对，要么把别的东西弄坏了。

主持人问：Claude Code 之类的工具都有 /plan，Mission 像是"加强版计划模式"，区别在哪？Eno 先说明 Droid 也有类似的 spec mode。他们不叫 plan mode，理由是：

"What you should create is not how the agent should do something but what it should build. So that's more spec than plan."

Mission 的区别在复杂程度和深度。按 Ctrl+O 能看到发给每个工人（worker，也就是子 Agent）的完整提示。第一个工人的任务是"validation dry run"：检查需要的工具是否装好、哪些端口可用、数据库在不在，甚至检查能不能用浏览器做 QA。Eno 说这相当于在开工之前先做一个微型 MVP，确认项目的骨架做得出来。

规划阶段会产出这些东西：

  • 验证合同（validation contract）：一长串验证标准。
  • features.json：结构化的功能清单，每项有描述、验证标准、前置条件、所属里程碑。
  • Mission proposal：很详细的 spec。
  • 工人用的 Skill：Droid 判断执行时需要哪些可复用的工作流程，写成 Skill。
  • AGENTS.md：说明这个项目怎样运作（已有的话不会重建）。
  • services.yaml 和 init 脚本：环境弄脏了可以反复重新初始化；services.yaml 写明怎样跑测试、lint、类型检查。

Eno 的概括："a heavy-duty map for an agent to be able to QA and validate every aspect of work that it's going to do"（一张让 Agent 能对每项工作做 QA 和验证的详细地图）。普通 spec mode 用户期待三到五分钟得到结果，Mission 则愿意做很久。演示里它接着上网查了 Drizzle、Next.js App Router、Tailwind、shadcn 的文档，确认用的是最新版本，然后才提出 Mission。整个前期工作在节目里花了二三十分钟。

四、Skill：他自己用哪些，Mission 怎样让 Skill 自我修正

等 Droid 干活的时候，主持人请他讲 Skill。他日常用的 Skill 有：写 Factory 博客（带样式图表）；视觉设计（含 Nano Banana CLI 等生成图片的工具）；human writing（让文字读起来更像人写的）；machine control（他用一个 Mission 做的 CLI，能控制 Mac、点击、读 iMessage，他平时尽量不用）；浏览器导航；创建 Skill 的 Skill；产品管理；前端设计。

他的建议：

  • 有固定流程的工作，适合写成 Skill，让 Agent 照着走。
  • 他最常留着的是"有好例子"的 Skill。前端设计那个 Skill 里装的就是好例子，这样能指着说"质量就是这样"。
  • 用户量大的 Skill Factory 会直接做成内置功能，例如浏览器操作。

Mission 里的 Skill 有两种用途：参考资料，或者让 Agent 不偏离路线的工作流程。Mission 会生成"怎样做一个前端功能""怎样做一个后端功能"这类 Skill，工人领到任务就照着做。关键在这里：如果工人碰到问题，比如"后端要先开 Docker 才能跑"，它会自己去改那个 Skill，加一条警告。

"For a mission, you might be working 30, 40, 50 tasks continuously. And so if that compounds over every single issue, it's just sort of devastating for the mission."

人在旁边盯着的时候，这类小坑无所谓，烦的人多了自然有人写进 AGENTS.md；但 Mission 要连续做几十个任务，同一个坑每次都踩会毁掉整个 Mission。所以 Mission 必须有某种持续学习：把坑和规律写回 Skill。改 Skill 的主要是工人自己，编排者看全局结果。这些 Skill 放在项目的 .factory 目录里，提交到仓库后，以后在这个代码库上跑的所有 Agent 都能用上。在一个代码库上跑的 Mission 越多，这些工作流程就越贴合这家公司。

五、验证合同长什么样，为什么能跑这么久

Eno 打开了验证文档。第一条是"应用能成功加载"：在 localhost 启动、渲染主布局、没有报错，页面上要显示哪些东西；怎样证明——查控制台、查网络请求、截图。后面还有浅色和深色模式各截一张图并检查控制台，再往后是用户旅程（user journeys）和关键路径上的工作流。这些标准和功能一一对应，形成"合同"：工人知道"我在做这个功能，如果我做对了，这些必须成立"。

"Fundamentally this is why we're able to run for so long is the it's sort of a binary yes no. You're either done or you're not. And how do you know you're done? The validation criteria has been satisfied."

他接着说，几乎所有 Agent 在训练时都是以"是否正确"作为奖励信号，所以只要能把任意任务表述成一个奖励信号，就能把 Agent 推到能力的边缘。

Droid 审查验证合同时，同时派了两个独立的审查者，找出了漏掉的东西：用户身份、深链接、编辑、看板上的拖拽。

串行为主，局部并行

Eno 说 Mission 整体是一个串行流程，只在中间需要时并行跑子任务。很多工具一上来就做"多 Agent 蜂群"，一次派十个 Agent 各做一个功能；他们更喜欢"controlled chaos"：让编排者一路推进，必要时再把子任务并行出去。他引用 Google 的研究：可以事先根据任务判断该不该并行。只读的任务（比如深度研究）尽量并行；任务越复杂越不该并行，因为几条分支的上下文都要知道，没法拆出去。

主持人问有没有用 DAG（有向无环图）表示依赖，并提到 Steve Yegge 的 beads。Eno 说功能和验证都带依赖列表，但模型通常会判断同一里程碑里的功能基本是串行的，所以"DAG 在实践中往往就是一条线"；验证一般可以并行，也由模型决定，比如后端都没跑通，前端测试就先别做。演示里 Droid 判断这个项目不复杂，只建了一个"全栈工人"Skill。

六、Mission Control：什么时候可以走开

因为开着最高自主级别，人唯一要做的确认就是接受 Mission proposal。接受之后就可以走开，终端窗口会自动阻止电脑休眠。演示中有一处例外：Droid 检测到 rm -rf，即使在高自主级别也强制要人批准。Eno 说这是个小的体验问题，但比反过来好。这次 Mission 共 17 个功能。

Mission Control 是终端里的一个视图：左边是正在做的功能（这时在搭脚手架：空目录、能跑起来、深浅色模式、shadcn、脚本），上面是高层进度日志，下面是正在工作的工人。可以在待做的功能之间切换（脚手架、数据库、种子数据、MVP），也可以进入某个工人的实时视图，停止或打断它，或者直接和编排者说话，比如"第二个里程碑改成这样"。

一个意外的现象：如果在 Mission 后期大幅改方向，Droid 会照做，但语气里带着情绪。

"We've noticed it can be quite passive aggressive with you if you make a huge change."

他的解释是，他们花了很多功夫向模型讲清 Mission 是什么，模型知道这是要长时间运行的大工作，看得到自己做了多少，所以被推翻时会问"怎样避免再发生"。他也提到，把这种系统用简洁清楚的语言讲给系统本身听，比想象中难得多。

界面方面，这个功能他们先做了桌面版（还在功能开关后面没发布），后来做终端版时发现终端的限制逼着他们想清楚：一个要跑几小时的东西，到底该给人看哪些高层信息。Factory 本身是多端的：桌面、网页、终端、Linear、GitHub。

七、人该把时间花在哪

Eno 说演示里跳过的才是最费人力的一步：认真读 features.json 和验证标准，确认要做的东西是自己想要的。他们的经验是，只要两件事成立，结果就有很高把握：

  1. 开头那一步，Droid 确认它能验证你要它做的东西；
  2. 功能清单和验证标准都列出来了，人也审过。

Droid 对自己也诚实：如果没法在生产环境测数据库、没法起带测试数据的 Docker 容器，它会写明某些东西"只能看一眼来验证"，而这些地方它就会出错。这也是 Factory 做 Agent 就绪度工具的原因。

他估计以后的工作方式是：前两个小时确认一切正确，然后放它跑八到十个小时。"耐心地花一个半小时读一份 200 项的文档"和亲手写代码是很不一样的技能，人要适应，工具也要让这种事前审查更容易。事后审查是另一个问题：几万行你从没看过的代码。

验证用的是什么工具

主持人问工人做测试时用的是 MCP 还是 CLI。Eno 说他们没有额外做任何连接器。Droid 预装了 agent browser，可以操作 Chrome；其余都写在 mission planning Skill 里，大意是"想想所有需要验证的东西"：桌面应用要电脑控制，网页应用要浏览器，API 要发 HTTP 请求，处理音频的要生成音频再过一遍 FFmpeg。每类软件只写了两句"作为 Agent 你可以怎样验证"。Droid 据此在规划时摸清能怎样验证，写成验证标准，再在工人 Skill 里写下针对这个代码库的具体做法。如果你有查错误日志、查 Datadog 的 CLI，还可以加一个"部署和监控"里程碑：等一小时，查 Datadog，再等一小时，再查。这需要云沙盒，Factory 平台里有。

八、从 Ralph 循环到旧代码库

主持人提到 Ralph Wiggum 循环（让 Agent 在一个 while 循环里一直跑下去的流行做法），问 Missions 怎样做到在旧代码库里也可靠。Eno 讲了这个功能的来历：内部先有类似 Ralph 循环的实验，但他们关注的是验证，目标是让 Droid 在一个会话里几乎百分之百确认活干对了。轻量版先给客户用于较小的任务，再配上 spec mode，一些企业客户拿它做遗留系统现代化和迁移，于是收到大量"在旧代码库里怎样验证"的反馈。

"Being able to be very prescriptive about what success looks like is what makes brownfield work really well."

旧代码库做好了，新项目就简单了：新项目可以事先选一个特别容易验证的技术栈。旧代码库的第二个难点是分清哪些地方需要人参与。那里总有乱七八糟的事，比如"登录要走 OAuth，OAuth 还有机器人检测，agent browser 进不去"。

这时演示里的网页已经有了侧边栏和待办项的雏形。Eno 发现 Droid 生成的假数据里用了联合创始人 Matan 的名字，姓是编的，他也不知道是从哪份文档里来的还是巧合。

九、什么时候适合用 Mission，上限在哪

Eno 的判断标准只有一条：能拿到多少验证。

  • 16 天那次是一个迁移，时间长主要是因为反复启动、关闭开发数据库。
  • 一个两小时的小例子：Droid 编辑自己的终端界面，以前大约 85% 能做对，15% 到 20% 做不对。他们给它做了一个终端控制和渲染的工具（类似终端版的 Playwright，还能抓闪烁），之后只要心里清楚要什么，"几乎是有保证的"。他们现在甚至先在一个 HTML 文件里摆弄终端文字，满意了截图丢给 Droid，它会反复对比直到做出来。
  • 反过来，如果代码库里有东西就是没法验证，他不推荐用 Mission：它会跑几个小时、花很多 token，最后给你一个"大概 85% 对"的东西，返工可能比自己做还累。

上限他们还不知道。他们在做一个内部叫 SaaSBench 的基准：用 Mission 从零构建常见的生产力工具和开发工具，分五档，第五档是一百多个功能的复杂 SaaS。最高档运行时间很长，结果有好有坏，失败原因都和部署、基础设施有关：要不要给 Droid 一个 AWS 账号？做一个 Zapier 克隆，不用 Firecracker 虚拟机跑小函数，就没法知道它在生产环境能不能用。

"We've hit the bounds of what's easily evaluatable and testable and now the evaluation harness itself needs to look more like real life."

主持人担心"几个 Mission 就能复刻上市 SaaS 公司"会被媒体写成头条。Eno 承认很多软件已经能用这种方式做到相当准确，但同样多的软件远远做不到；从零复刻核心十个功能容易，难的是后面上百层东西。他引用 Rippling 的说法：95% 的软件都差不多，治理、数据、权限这一层要花 60% 的时间。

主持人总结：秘诀不在提示词、工具或者装了几个 MCP 服务器，在于验证定义得多清楚、给 Agent 多少手段检验自己。Eno 同意，并说这一点不用 Droid 也成立，用任何 Agent 都会因为验证而明显变好。

十、"产品工程系统"和工程师的未来

Eno 描述的未来：现在大多数人直接做产品，组织里只有 5% 到 10% 的人在做"构建产品的那套系统"（工程领导、开发平台团队、产品人员）；一两年内可能所有人都转去做这套产品工程系统。具体说，不再是开会争论按钮放右上角还是右下角再让 Droid 去改；而是 Droid 自动吸收客户反馈、自动实现，人发现它总把按钮放右上角，就去改 Droid 的产品设计原则文档。

"We are sort of like constitutional lawyers. We need to debug the constitution that Droid has... We are mechanics on like this software factory."

这套系统包括：产品原则、可以接受哪些取舍、听谁的不听谁的，以及从外部进来的信号。他说没人能直接买到它，Factory 想卖的是搭这套系统用的零件。

主持人追问：这样产品经理、销售、客户成功也能做，工程师还剩什么？Eno 认为总得有人做架构；一个不断累积微小改动的系统会变得极其复杂，涌现出意想不到的性质，这有点像控制论。软件治理该集中还是去中心化，会成为一个独立的领域：开源项目也许适合去中心化，企业卖的产品可能仍需要集中协调。要把这些设计好，得懂数据库、懂基础设施、懂产品。

"In five years we're going to say, 'Oh yeah, we really thought that that stuff was going to put us out of a job.' Instead, it just made the job 10 times harder."

最后一个问题：Mission 做完能直接上线吗？他的回答是不能。他从没有在 Mission 结束后直接说"好了"。他会自己 QA、亲手用一遍；这次的功能清单人工 QA 一遍大概要一小时，肯定有地方不对，尤其是设计，他说 LLM 在设计上还不够好。Mission 结束后编排者还在，可以直接告诉它"这里设计我不喜欢、这几个函数坏了"，它会把修复追加成新功能派给工人，做完再回来汇报。

十一、和课程的关系

  • 第九讲：Eno 在课上讲的"可验证性和粒度"、Agent 就绪度，在这一期里都有对应的实操：验证合同、dry run、只能"看一眼"验证的地方会出错。
  • 第三讲：先写 spec 再实现。这一期的说法是 spec 写"做什么"，plan 写"怎样做"。
  • 第五讲：Skill。这一期多了一个用法：工人在执行中改写 Skill，把踩过的坑留给后面的任务。
  • 第十一讲：长时间运行、人只在前后介入的工作方式。
