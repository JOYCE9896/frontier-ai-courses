二、为什么讲代码审查

代码审查（Code Review）是指代码合进主分支之前，由别人（现在也可以是 Agent）读一遍改动、提意见。课件开头的判断：代码审查是想成为更好的工程师、提高团队整体代码质量时，杠杆最高的事情之一。它有两个作用：发现并修掉 bug；让团队对系统形成共同的理解（shared mental model）。

审查能抓到什么

  • 逻辑和正确性错误
  • 可读性和可维护性
  • 性能
  • 安全
  • 最佳实践，也就是团队里没写下来的经验

审查需求的层次

课件引用了 Blake Smith 的“代码审查需求层次”金字塔，从最重要到最不重要：

  1. Mental Alignment：大家对系统的理解保持一致（最重要，在金字塔底部）
  2. Correct Solution：改动确实正确地解决了问题
  3. Design Discussion：对设计的优缺点展开讨论
  4. Find Bugs：在上线前抓到 bug
  5. Style：代码风格和组织保持一致（最不重要，在顶端）

按这个排法，找 bug 和统一风格反而排在后面，最重要的是让团队成员随着系统的变化更新自己对它的理解。

三、AI 原生的代码审查

现在的问题是，代码生成的速度上去了，审查没跟上，成了新的瓶颈。课件给了一个成熟度阶梯：

阶段做法评价
0人审查一切不可能规模化
1单个 Agent 审查好一些，配上自动修复循环更好，但还有收益没拿到
2多 Agent、按风险分级、自带自我改进的审查；工程规范存在 Skill 知识库里很多公司正在收敛到的最佳实践

分层检查，不靠一道关

第一张图来自 Addy Osmani 的推文（Layers, not one gate）：六层检查叠在一起，下面还有一层快速回滚。问题从上面掉进来，每一层都会漏掉一些，但每一层抓的不一样。六层从上到下是：

  1. verification（验证）
  2. required CI（必须通过的 CI）
  3. AI review（AI 审查）
  4. security review（安全审查）
  5. human approval（人工批准）
  6. merge queue + flags（合并队列和功能开关）

全部漏过去的问题，由最底下的 fast rollback（快速回滚）兜住。

按风险分流

第二张图来自 Augment Code 介绍 Cosmos 的文章，是一条按风险分流的审查流水线：

  1. PR Author：PR 作者负责这个 PR 的整个生命周期，一轮轮修改，直到意见处理完、合并进去。
  2. PR Risk Analyzer：给每个 PR 评估风险，决定走哪条路。
  3. 低风险的走 Auto-Approve，自动批准；其余的走 Deep Code Review，逐行分析代码正确性。
  4. Review Outcome：发评论、批准，或要求修改。
  5. Code Review Memory：组织级的记忆，存 Agent Skill 和开发者的最佳实践，反过来供作者和审查环节使用。

四、多 Agent 审查架构

课件引用了 Cloudflare 的文章（internal AI engineering stack）：一个 PR 进来，分给几个各管一方面的审查 Agent，最后由一个汇总的评判 Agent 合并结论。

                 Aggregate Judge

安全审查 Agent 的规则

课件截了这样一个 Agent 的指令片段，规定该标什么、不该标什么：

## What to Flag
- Injection vulnerabilities (SQL, XSS, command, path traversal)
- Authentication/authorisation bypasses in changed code
- Hardcoded secrets, credentials, or API keys
- Insecure cryptographic usage
- Missing input validation on untrusted data at trust boundaries

## What NOT to Flag
- Theoretical risks that require unlikely preconditions
- Defense-in-depth suggestions when primary defenses are adequate
- Issues in unchanged code that this MR doesn't affect
- "Consider using library X" style suggestions

一次实际的审查输出

课件还放了一张 OpenCode Code Review 的截图：一个合并请求的审查结果按领域分块，Security、AGENTS.md、Code Quality、Performance 各自给出 LGTM（Looks Good To Me，审查通过）和理由，比如令牌只传给创建客户端的函数、没有被记日志，路径做了前缀校验，远程内容用 Zod schema 校验；Code Quality 一栏逐条确认上一轮指出的三个问题都已解决。

五、怎样设计一个审查 Agent

这部分对应推荐阅读里 Greptile 的文章。

审查和生成用不同的模型

写代码用一个模型，审查换另一个。课件在这一条下面写了一个词 Model inverter，没有展开解释（没有转录，具体指什么这里不确定）。

精心准备上下文

审查 Agent 只看 diff 不够。课件的图：文档和工单（Jira、Linear、文档）经过一个 MCP 网关进来，代码库经过一个代码库索引器进来，两路都汇到审查 Agent。

实际运行来验证

起一个开发容器（dev container），把不同的代码路径真正跑一遍。

按任务难度选模型，控制成本

  • 收集代码上下文：便宜、快的模型。
  • 浏览器操作：小到中等的模型，推理力度调高。
  • 深度 bug 分析：前沿模型。

评测

评测（Eval）审查 Agent 的数据从哪来：有已知 bug 的历史 PR；以及后来出了事故、被回滚（revert）的改动。拿这些看审查 Agent 当时能不能抓出来。
