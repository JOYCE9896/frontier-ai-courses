第六讲：常驻 Agent 怎样工作

客座讲座。从第一周那个终端里的 Agent 出发，讲一个一直在线、有自己的电脑和记忆的 Agent 怎样搭：模型的六项新能力，知识存在文件里，触发器与睡眠唤醒，每个用户一台虚拟机，把一切存在服务器上，持久化工作流，只用一个工具和用户说话，便宜的手段先试，安全措施，保持提示词前缀稳定以命中缓存，记忆分层，以及还没解决的问题

主讲：Lee Robinson（SpaceX，Model Behavior）
资料来源：讲者课件 + 课堂录像（2026 年 10 月 8 日；Lee Robinson 在 YouTube 公开，45 分钟，本文依据课件和录像字幕整理）
录像只有讲座部分，开头说的课后问答没有放出来。YouTube 的英文字幕是自动生成的，个别产品名靠上下文判断。

一、从第一周的 Agent 说起

Lee Robinson 开头放的就是大家第一周写的那个循环：消息列表里放系统提示词和用户消息，循环调用模型；模型不再请求工具就打印回复、结束，否则执行工具，把结果追加进去。他说，这个 Agent 在你关掉终端时就停了。今天讲怎样做一个一直跑着的 Agent，以及为什么这让它变成另一种产品。课件开头有一份免责声明：内容可能涉及公司未来产品的计划，以实际发布为准。他们把这种常驻 Agent 的实现叫做 Bot（录像里具体说的是他们在 SpaceX 做的 Grok Bot）。

录像里他对常驻 Agent 的描述更像一个同事：它有自己的一台云端 Linux 电脑，有桌面、文件和浏览器；你合上笔记本、它重启、它崩溃，都不影响它继续干活；它不会对你的每句话马上回一条，而是"knows when it's best to remain silent"，在后台做事，有重要进展才来找你；叫醒它的也不只是你在终端里打的字，可能是一条 Slack 消息、一封邮件或别的事件。他们希望这样的 Agent 能连续工作的时间不止几小时、几天，而是几周甚至几个月，这需要另一种架构，也就是本讲的主体。

第一周的 Agent常驻 Agent
跑在你的终端里跑在服务器上，挺得过崩溃、发版和合上的笔记本
用你的笔记本电脑有自己的云端电脑：一台带桌面、浏览器和文件的小虚拟机
只记得消息列表保存自己的状态、记忆和 Skill，旧消息会被总结
打印模型的每一句回复只有调用"发送"工具时才给你发消息，所以可以保持安静
你打字时才开始由事件启动：你的消息、定时任务、Slack、电话、完成的后台工作
做完一个任务就退出用同一份记忆工作好几个月，跨越很多次对话

二、怎么走到这一步

开发者和 AI 协作的方式大致经历了四个阶段，AI 做的事越来越多：

  1. 2022 到 2023 年，复制粘贴：在浏览器标签页里聊天，手动把代码贴进去、把答案抄回来。
  2. 2024 到 2025 年，终端里的 Agent：Agent 在循环里改文件、跑命令，你批准每一步。
  3. 2025 到 2026 年，为 Agent 设计的应用：很多 Agent 在后台或云端并行跑，你审查做完的改动。
  4. 现在，常驻 Agent：你给一个有自己电脑、工具和记忆的 Agent 发消息，你离开后它还在继续工作。

人的角色也从"批准每一步"变成"掌舵"。以前：提示，Agent 干活，等你批准，再干活，再等批准，最后你审查。现在：Agent 一直干活，你中途改方向，比如"也看一下那个 Slack 线程""其实改成周四吧""准备好了就发邀请"；它可以连续工作几个小时，把任务交给帮手 Agent；有风险的动作由自动审查放行，比如"发日历邀请"被一个安全检查自动批准了，就不必等你。

录像里补充了两点。第三个阶段，你仍然是瓶颈：你要盯着每一条 shell 命令，确认它没问题再放行。现在可以在 Agent 干活的中途插话，例如先说"看一下这个线程"，紧接着又说"对了，改成周四"。上一代模型被打断后容易糊涂，现在的模型能明白这几句话说的是同一件事，就像和朋友聊天一样。自动审查（auto-verification）是一个单独的 AI 模型，检查每一条要执行的命令。他说，这样反而比让人去批准几百条 shell 命令更安全，他们的结论是："if you were to do a blind test of what the AI model checks and what a human checks, most of the time the model does better."

他的一句总结：模型越强，界面越简单。为什么界面变成了"发消息"？他的解释是，每个人都会发短信、都会用手机，和 Agent 协作变得像给朋友发消息，只是对方能真的帮你干活，交给它的是可以交给同事的长任务，而不只是一问一答。

三、模型的六项新能力

  1. 能连续工作几个小时，整个过程中一直遵循复杂的指令。
  2. 能交给帮手。主 Agent 把任务交给帮手 Agent，每个帮手有新的上下文，总工作量不受单个上下文窗口的限制。他在录像里说，模型的工作记忆有限，迟早会填满；帮手带着新的上下文去做耗 token、耗工具调用的活，做完只把结果报告回来，这样主 Agent 看起来就像有无限的上下文。前提是对话压缩做得好（见第六节）。
  3. 能用真正的工具。shell、文件、浏览器，通过 MCP 使用应用的 API，和你在自己电脑上用的工具一样。他提到，几年前模型还几乎不会用工具、经常编造，现在已经很少听人讨论幻觉了；现在可以像给新同事开权限一样，给它一台完整的 Linux 电脑。
  4. 能用电脑。能看屏幕、能点击，所以没有 API、也没有 MCP 服务器的 SaaS 产品和网站也能用。
  5. 把知识存在文件里。Skill 和记忆都是纯文本文件，Agent 自己读、自己更新。
  6. 看一遍就能学会。在它的电脑上演示一遍你怎么做某件事，它把步骤存成一个可以复用的 Skill。

Agent 知道的东西都在文件里

一个简化的例子： 

memory/
  profile.md           always in the prompt
  log/2026-10.md       dated facts, one per line
skills/
  linkedin-sourcing/
    SKILL.md           "Use this when..."
  weekly-metrics/
    SKILL.md
routines/
  morning-brief        prompt + weekdays 8:00
  • 模型极其擅长使用 Linux、执行 shell 命令。
  • 纯文本，你和 Agent 都能读、能搜、能改。
  • Agent 自己维护它：你说一次偏好，它就存进记忆。
  • Skill 只在需要时加载，所以有很多个也不贵。

他在录像里逐个解释了这几个目录。profile 是对用户的了解，每次请求都会带上，例如"这个用户喜欢全用小写字母发消息"，那每条回复都该是小写。log 像同事每天写的工作日志，你问"我上周做了什么"，它去翻日志就行，模型很会用 grep 这类 Linux 命令在文件里搜。Skill 是把你做某件事的具体流程和成败要点写进一个 markdown 文件；现在已经有很多公司和开发者在写 Skill，比如怎样写一封好邮件、怎样设计好的 API。Grok Bot 还有一个插件系统，几乎每个想用的工具都有插件，插件里装的就是 Skill 或服务器。routines 类似 cron 任务，按时间表运行一个固定的请求。

课件把这概括为"一切皆电脑"（Everything is computer）。

四、它怎样"一直在线"

关键是：没事的时候什么都不跑。系统分四块：触发器负责唤醒它；Agent 进程跑完一轮就停；Agent 的电脑空闲时睡眠；保存的状态始终在服务器上（数据库和存储里有对话、记忆、定时任务、Skill）。比如你发来一条消息：载入状态，干活，每一步都保存。早上 8 点的定时任务触发：任务运行，空闲两分钟后停止；电脑一直睡着，存在磁盘上，只有某个工具需要它时才恢复，这个任务用不到它，就一直睡着。因为所有重要的东西都存下来了，任何触发器都能把它叫回来。

为什么要让电脑睡眠？他的回答很直接：让每个人的电脑一直开着太贵，而且"there aren't enough computers in the world"，服务器资源也撑不住。

什么会唤醒它

  • 你，在任何一个应用里。
  • 一个定时任务：按时间表，或者 webhook。
  • Slack 里的 @、私信或线程。
  • 一通电话或一场会议。
  • 另一个 Agent。
  • 后台工作完成。
  • 计划好的例行检查。

他举了一个例子：在 SpaceX，越来越多的 Bot 替不能到场的员工去开会，记笔记，会后把报告带回来。

这些都先进一个路由器，它去掉重复的、选好属于哪个对话；然后进对话队列，一次只跑一轮。跑完后判断"有没有值得说的"：有就把消息发到对的地方，没有就保持安静。每次唤醒都记录来源，所以 Agent 分得清是你问的、定时任务跑的，还是外部服务发来的。

"要不要打扰用户"这一步，他的类比是同事：如果同事每有一点进展就跑过来拉你看，会很烦；多数任务一天给一次进度就够了，具体看任务。

Agent 的电脑

每个用户一台 Firecracker 虚拟机，空闲时存到磁盘。里面是一个 Linux（Debian）容器，由一个守护进程保持运行，包括：文件服务器（文件、应用连接、实时桌面画面）；命令执行器（shell 命令、文件、截图、点击）；屏幕 1，一个带自己 Chrome 的虚拟显示器；每多一个活跃的 Agent，就多一块屏幕。文件、装好的工具和浏览器登录状态在会话之间都保留。

选 Firecracker 的原因是给机器状态拍快照、关机、再启动都很容易。你也可以连上这台机器看实时画面，甚至自己接手操作。有些 shell 命令你不想在自己笔记本上跑，放在这个隔离的环境里跑更放心。同时跑五个、十个 Bot 时，每个都需要自己的浏览器，就给它们各开一块虚拟屏幕。

  • 入睡：最后一次活动后几分钟，绝不在一轮的中途。先把文件同步到云存储，再把内存和磁盘存成快照，然后关机。
  • 唤醒：在下一次工具调用时。原地恢复快照，登录状态和装好的工具都还在，对话状态从服务器取回。

三部分

应用和渠道（桌面应用、手机和网页、Slack、邮件、webhook、定时任务、电话和会议）；服务器负责运行 Agent（入口检查和路由输入，每个对话一个队列，模型，Agent 循环和工具，保存状态的数据库和存储）；Agent 的电脑负责运行工具（文件和连接器服务器，命令执行器，每个 Agent 一个桌面和 Chrome）。Agent 跑在服务器上，在自己的电脑上用工具，每个应用显示同一段对话。

为什么 Agent 跑在服务器上：

  • 瘦客户端，厚服务器。
  • 合上笔记本，工作照样继续；在电脑和手机之间随意切换。
  • 发布代码不用等应用商店审核。
  • 重活交给服务器。
  • Agent 循环和应用代码完全解耦。
  • 高速增长时更容易扩展。
  • 能工作几个月的 Agent 不可能放在设备上。

原则只有一句："把一切存在服务器上。"这样虚拟机随时都能重建。录像里的解释：如果把 Agent 循环放在虚拟机里，就没法单独关掉虚拟机而不停掉 Agent。他举的例子是 Linux 出了一个严重的零日漏洞，要给虚拟机打补丁，这时希望直接重建虚拟机，不影响 Agent 循环、也不让应用停机。发版不用等应用商店审核，转写、生成图片这类重计算在服务器上也比在设备上快。

按下发送之后

  1. 发送。应用立刻显示这条消息，在本地存下来并给它一个唯一 ID；服务器丢掉已经见过的 ID。唯一 ID 让重试变得安全。
  2. 这一轮。消息进入对话的队列，Agent 跑一轮：模型、工具、重复。每一步都存进数据库。每个对话一次只跑一轮。
  3. 观察。服务器发出一个很小的"有东西变了"信号，每个打开的应用都收到，各自去取新消息。信号本身不带数据，所以丢一个也无妨。
  4. 排序。每次更新都有序号，应用按 41、42、43 的顺序应用；缺了一个就从数据库重新加载。每个应用最后显示的都一样。

要点是：通知只说"有东西变了"，真正的数据永远在数据库里。

持久化工作流和任务队列

服务器在一轮中途崩溃会怎样？用普通任务队列，第 3 步崩了就从头重来，第 1、2 步白做一遍。用持久化工作流（durable workflow），每一步都有记录，新的服务器从最后一步接着做，不重复做完的工作。配套的要求是"安全重试"：每一步都写成跑两次也无害，这叫幂等（idempotent）。Temporal 这类开源引擎自带定时器、取消和健康检查。他们自己用的就是 Temporal，这在分布式系统里算是已经解决的问题，不必从零造；不过 Temporal 本身的基础设施还是要自己维护。他也提到，按下发送后的这套流程涉及强一致和最终一致，想深入可以去学分布式系统。

新消息怎么排队

Agent 一次处理一批消息。在一对一聊天里，你的消息会插队，可以打断或停止正在跑的一轮，比如"其实改成周四吧"。其他来源（群聊、Slack 线程、定时任务、帮手）排在后面；短时间内连着来的几条（"要加 Maya 吗？""还有 Jordan""谢谢！"）会合并成一轮处理；每周报告这类定时任务排在队尾。录像里他说，你说"把这个活动的日期改一下"时，就希望 Agent 循环停下来，先处理你这条；具体用什么规则排队，可以按需要自己定。

五、外壳

只用一个工具和你说话

干活的工具有很多：shell、文件、浏览器、桌面、记忆、Skill、帮手 Agent、云端 Agent、应用连接器、网页搜索、图片生成、录屏。但和你说话只有一个工具：SendToUser。你的消息可能出现在桌面、网页、手机、Slack、邮件或语音里。他说这是 Grok Bot 的外壳和市面上同类工具最大的不同，也是"瘦客户端、厚服务器"的体现：客户端只往服务器发文字，重活都在服务器上；不管新开的是手机应用、桌面应用、邮件还是 Slack，客户端和服务器之间都只靠这一个工具通信。这样设计有几个好处：

  • 思考保持私密：模型的普通文字输出从不直接展示给你。
  • 允许安静：没有新东西，就不给你发消息。
  • 富消息：可以发文字、文件、选择题，以及安全的密码输入框。
  • 少一步：最后一条消息可以直接结束这一轮，不必再调用一次模型。

工具配上合适的界面

外壳有几十个工具。需要你看一眼或批准时，工具会显示专门做的控件：登录表单只在当前打开的网站上填你的登录信息，密码不经过模型；付款审批要等你点"允许"或"拒绝"；邮件草稿让你看到整封邮件，选"发送"或"丢弃"；有时一个表情回应就是最合适的回复。录像里提到的具体服务：登录可以接 1Password，付款可以接 Stripe Link 或 X Money。客户端收到的只是同一个工具的结果，自己决定用什么交互形式展示。

工具详情按需加载

课件画了两个上下文窗口的方格图：一种是所有工具的详情一开始就全部装进去，紫色方块占了大半；另一种是先只放工具名字，需要时再载入详情，大部分空间都空着。这和第二讲说的工具膨胀、第五讲的渐进式披露是同一个道理。

先试最便宜的办法

顺序是：①它已经知道的；②应用的 API（连接器）；③网页搜索；④它自己已登录的浏览器；⑤完整的桌面；⑥问你。越往后越慢、越贵、风险越高。如果某个连接器坏了，Agent 不该用浏览器去绕过它，而应该告诉你、问你。

录像里的例子：银行信息可以通过 Plaid 这样的 API 拿；昨天小熊队（Cubs）比赛的比分要上网搜；都不行再开浏览器，再不行就用整个桌面跑脚本、跑命令；只有这些都失败了，才去"harass the user"。他说这样用起来才像和同事合作，同事不会什么小事都来问你，会先自己把这些办法试一遍。

三种用电脑的方式

  • 读页面结构：读出页面上按钮、链接和输入框的列表，直接点击。比截图更快、更可靠。录像里说的是读页面的 HTML 或无障碍树（accessibility tree），后者能大幅减少 token。
  • 按像素点击：在 1280 × 800 的屏幕上用鼠标和键盘，用于桌面应用、系统对话框和其他一切。有些网站会弹出必须点掉的模态窗口，所以这个能力少不了。
  • 找人：遇到登录、验证码、人机验证或付款时，它停下来，说明自己在哪一步，把屏幕交给你，比如请你提供两步验证码。

点击由一个单独的帮手 Agent 来做，截图就不会塞满主 Agent 的上下文。

一个主 Agent，很多帮手

主 Agent 自己回答简单问题，把大任务交给帮手，好继续和你对话。帮手有：通用帮手（shell、网页、应用连接器、云端 Agent）；用电脑的帮手（浏览器和桌面，一次一个任务）；视频帮手（看和审查视频文件）；云端编程 Agent（在自己的虚拟机里改代码）。主 Agent 交出去的是完整的任务描述，拿回来的是简短报告。有一张待办清单追踪每个请求，可以查看某个帮手的进度、给它发消息、或者停掉所有帮手。

录像里补充：主 Agent 的对话要尽量简洁，帮手跑了一大堆 shell 命令或昂贵的工具调用，最后只带回结果，不占主 Agent 的上下文。每个帮手都是一个独立的持久化工作流，比如视频帮手内存用多了崩掉，可以重启后接着做，不丢进度。他说这套设计参照的是"怎样扩大一支工程师团队去解决一个很复杂的问题"。当然真正无限的上下文并不存在，训练模型时也有一些办法，让它在上下文接近上限时质量不明显下降。

设计 Agent 工具的建议

  • 不要在两轮之间增减工具。某个工具暂时不能用，就让它返回一个清楚的错误。
  • 每个工具的描述加 schema 控制在 4000 个字符以内。
  • 保存状态用专门的工具，而不是 shell 命令，这样审查的人能看清改了什么。录像里他的说法是：有人说只要一个工具就够了，就是跑 shell 命令，这确实能模拟很多事；但如果某类任务 90% 的时间都在用 shell 做同一件事，就值得为它单独做一个工具，测试产品的人也看得更明白。
  • 错误信息要说明下一步怎么做，比如"电脑在睡眠中。先用 Shell 或 Read 唤醒它，再重试。"他说给人写错误信息要清楚，这条对 Agent 同样有用，算是 Agent 的"开发者体验"。

安全措施

  • 自动审查。一个单独的模型在有风险的动作执行前检查它；被拦下就给你发审批请求，15 秒内没回应就算拒绝。
  • 追踪来源。来自邮件和 webhook 的文字标记为不可信，比如一封钓鱼邮件，不能被当成用户指令交给模型；记忆被当作信息，而不是指令。他在录像里承认，防提示词注入还有很多工作要做。
  • 先问。你没要求，它就不会给别人发邮件或消息；新建定时任务需要你同意。
  • 藏好秘密。密码放进环境变量，永远不给模型；在你自己笔记本上的操作需要你批准。

六、上下文工程

保持提示词开头不变

模型服务商对"开头和最近一次请求相同"的提示词收费更低、响应更快（前缀缓存）。所以稳定的内容放前面，新内容放最后。从上到下是：

  1. 工具定义；系统提示词，包括记忆和定时任务的一份快照；第一条消息，写环境信息和工具名单。这几部分在下一次总结之前保持不变，每次调用都一模一样，服务商可以复用缓存。
  2. 对话历史：新消息只往后追加，于是它成为下一次调用可复用的开头的一部分。
  3. 最新一条消息：当前时间、对变化之处的简短说明，然后是你的消息。只有这一部分每次都是新的。

录像里的解释：和 Agent 对话时，每加一条消息都要把整段对话重发一遍，所以理想情况下用掉的 token 大部分应该是缓存命中的 token，而模型的价目表上缓存 token 有很大折扣。他也说上下文工程和"外壳工程"基本是一回事，只是叫法随时间变了。

保持主上下文小

主 Agent 的上下文保持小，每次调用就又快又便宜。重的东西放在主对话之外，只带回一个指针或一份摘要：

  • 长输出写进文件，上下文只留文件路径。
  • 截图交给帮手，上下文只拿到它发现了什么。
  • 工具密集的活交给帮手，上下文只拿到简短报告。
  • 旧消息被总结，上下文只留一段简短摘要。
  • 旧记忆可以搜索，提示词里只放最重要的事实。
  • 指令变成 Skill，提示词里只留一行指引。

把缓存未命中当成 bug

  • 在下一次总结之前，工具、系统提示词和第一条消息必须保持完全相同。
  • 如果一次发版改了某个工具的描述，正在进行的对话收到的是一条说明，而不是新文本。
  • 所有内容按固定顺序拼装并排序，调用之间什么都不会挪位置。
  • 工具永远不会只为某一轮增减，不可用的工具返回错误。
  • 每一段单独做哈希，能准确看出是哪一段变了。
  • 你打开聊天或开始打字时，服务器提前准备提示词，预热缓存。

录像里的背景：今年 1 月 OpenClaw 流行起来时，很多人通过订阅在用，这是模型服务商没见过的用法，当时的基础设施没有为这种一直在跑的 Agent 优化，缓存未命中很多，花了不少调整才稳定下来。每一段单独哈希、固定顺序，好处之一是做 A/B 测试时往提示词里加一段新内容，不会打乱别人那部分的顺序、把缓存清掉。预热缓存他比作网页上鼠标悬停在链接上时预先加载下一页。

趁你不在时做总结

一大轮结束，提示词超过 10 万 token；过了大约 10 分钟，服务商的缓存还是热的；这时写一份总结，用的是同样的提示词开头，所以能复用缓存；你下一条消息就从这份简短总结开始。如果后台工作马上要唤醒 Agent，就跳过这一步。Agent 最后发给你的几条消息逐字保留。如果某一轮太长，也可以在中途总结。

录像里他说得更具体：上下文窗口如果是 20 万 token，迟早要总结，而任何压缩都会丢信息，怎样压缩才不丢重要细节"very, very difficult to do right"。服务商的缓存保温时间可能是 10 分钟，也可能是 60 分钟；对话已经超过 10 万 token、你被别的事叫走时，趁缓存还热马上做总结要便宜得多，等你 30 分钟后回来，就从这份总结开始，之后追加消息也更便宜。总结算法的质量还有很多工作要做。

Agent 怎样记事

  • 档案（profile）：关于你的核心事实，始终在提示词里，最多 100 条、4000 个字符。
  • 日志（log）：带日期的事件，最相关的 30 条近期事件放进提示词。
  • 笔记（notes）：很快就会过时的短期细节。
  • 其他一切：需要时用记忆搜索工具找。

重要的事实排得更靠前，老的事实慢慢往后排；每一轮结束后有一遍处理，加入新事实、替换旧事实，它只能删除自己看过的事实；关于你的事实由你的所有 Agent 共享，每个 Agent 写自己的文件；模型被告知记忆是信息，不是指令。

录像里他用人脑作比较：哪些事实现在重要、和今天的对话有关，就留在眼前；你此刻多半没在想足球赛。记忆系统需要类似"垃圾回收"的机制决定保留哪些事实。"全用小写"这种偏好应该每次都在提示词里，否则某条回复突然有了大写字母会很奇怪。

七、往哪里走

为产品训练模型

  • 预训练：从海量文本学语言、代码和常识。
  • 监督微调：从示例里学这个外壳：工具和它们的格式，什么时候快速回一句，理想的回复长什么样。
  • 强化学习：练习真实的 Agent 任务，做得好就给奖励：遵循长指令、使用 Skill 和记忆、点中正确的位置（定位）、和其他 Bot 协作。

主 Agent 追求快速回复，推理和外壳都调成几秒内回答；帮手追求长任务，调成能可靠完成几小时的工作、快速操作电脑。录像里的说法是，交给帮手的长任务，10 分钟还是 12 分钟做完已经无所谓，所以两边可以分别优化。监督微调阶段让模型见过这个环境、懂这些工具；强化学习阶段练习遵循指令，在有几百个 Skill 时选对那一个，以及在浏览器里点对位置。

产品和模型一起改进

内循环，每天：一个 Bot 做错了事，把它变成一条评测（eval），修外壳、提示词或推理，检查评测，发布修复。外循环，每几个月：用外壳和评测训练下一个模型，换进产品，人们以新的方式使用它（比如满是 Bot 的群聊），出现新的行为需要评测和训练。每一个表现不好的 Bot 都变成一条评测，评测今天改进产品，明天改进下一个模型。

录像里的例子：模型在不该调用某个工具时调用了，就写成一条评测，然后在后端修外壳、修提示词或推理，确认评测通过再上线，做这类产品的团队每天都在这样做。群聊是新领域，用来训练 Bot 在群聊里表现的数据还很少；他提到 Moltbook 和 Hugging Face 事件这类出过问题的案例，说明在多个 Bot 互相交流的系统里，教会模型正确行事很重要（Hugging Face 事件见 CMU 11-768 第十八讲）。

他的一条原则写成一页："删掉产品。"假设模型会变得强得多，在它周围尽量少造东西，并把它不再需要的部分删掉。这和第二讲说的"外壳越来越简单"是一个方向。录像里他说这是他在 Cursor 时就有、到 SpaceX 也沿用的原则，出发点是"today's models are the worst they will ever be"，6 个月后你可能要把界面整个重做；今天讲的很多做法，和他 6 个月或一年前会采用的做法相比已经变了很多。所以要按下一代模型来设计，尽量少造东西。

未来 6 到 12 个月的预期

  • 更长的项目：Agent 在一个项目上工作几个月，而不是一个任务几分钟。
  • 更好的记忆：记住你和团队怎样工作，并且越做越好。
  • 更强的工具：电脑上能做的任何事，都做得更快更可靠。
  • 更简单的界面：今天是发消息，下一步也许只用语音，怎么方便怎么来。他在录像里说，也许会有一个 Jony Ive 风格的设备，让你整天对着它说话。
  • 没被训练过的技能：Bot 能在工作中学习，靠更好的记忆、对 Skill 和指令的遵循，加上原始的智力。
  • 知识被写下来：人和公司会把自己知道的东西写下来，供 Agent 使用。

可以去做的开放问题

  • 测试长时间运行的 Agent：一个工作几周的 Agent 怎么打分？现有方法都很吃力。录像里他把问题说得更尖锐：新模型每个月都在发布，一个要工作一个月的 Agent 怎么评测？要么想出更好的评测办法，要么放慢发布新模型的速度，他认为这是行业在未来 6 个月要面对的问题。
  • 正确的记忆：替换过时的事实，被要求时忘掉，绝不编造。
  • 提示词注入：读邮件和网页的 Agent 会看到专门写来骗它的文字，防御还很初级。
  • 什么时候说话：消息太多是噪音，太少你又不知道它在干什么。他举的例子是 Agent 主动说"我看到你昨天缺了一节课，我有录音、记了笔记"，这可能有用，也可能有点烦，平衡还没找好。
  • 协作：很多 Agent 共用一台电脑和一份记忆，会遇到分布式系统的经典问题。
  • 成本：只有空闲的 Agent 几乎免费、活跃的 Agent 也便宜，常驻才行得通。他在录像里预计，到明年这个时候世界上流转的 token 会多得多，所以优化推理、模型和环境、减少 token 用量会越来越重要。

新的基础构件

以前每个 Web 应用都有：服务器、数据库、缓存、增删改查界面。以后每个 Agent 产品都会有：持久化工作流、会用电脑、记忆和 Skill、触发器和定时任务、连接器和认证、文字和语音渠道、支付和身份、评测和可观测性。很多产品看起来会很像，但这些构件的做法会很不一样，每一块都会出现一长串专门做到最好的版本。

录像里他引用了 OpenRouter 的 Alex 在 X 上的一段回应：有人抱怨现在的应用都长一个样，侧边栏、一个 Agent、一个聊天框；Alex 回答说这就像 2005 年，那时大家也都在做一样的东西，一个服务器、一个数据库、一个增删改查界面。Lee 的看法是，这是新的常态，每个新产品都要有 Agent 的部分，要么集成在里面，要么做成别的 Agent 可以调用的无界面数据服务。他说上面每一格都可能是十亿美元级的投资方向，每一格都有二十家创业公司在做。

带走什么

代码越来越容易写，懂得各部分怎样拼在一起就越重要。

  • 架构会复利：代码便宜的时候，对的架构让你一直比别人快。他在录像里说自己仍然审查自己写的代码，有人已经不看代码了，但他觉得审查对理解自己发布的架构很有用。
  • 自己做一个：从第一周的 Agent 出发，加上服务器、电脑和记忆。开源的常驻 Agent 是很好的学习材料。他说 GitHub 上应该有人 fork 了 Grok Bot 的代码做了开源版本，可以给它配上图形界面、沙盒和虚拟机来学习各部分怎样工作。
  • 学好基础：懂 LLM 的工作原理，能帮你判断什么可行，就像懂数据库能帮你做网站。
