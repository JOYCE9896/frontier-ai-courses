第二讲：现代编程 Agent 的解剖

用抓包的方式拆开一次真实的 Claude Code 会话：Agent 循环之外的"外壳"有哪些部件，约 40 个内置工具和 MCP 工具，系统提示词，CLAUDE.md / AGENTS.md，计划模式，Skill，子 Agent，Hook，上下文压缩，以及好外壳的原则：简单

主讲：Mihail Eric
资料来源：课件、课堂转录、课上用到的提示词（2026 年 9 月 24 日；本文依据课件和转录整理）

一、开场事务

  • 期末项目说明已经发布。整个学期大约有四个里程碑，包括开题和几个中期检查，免得大家都拖到最后一周疯狂"vibe coding"。
  • 项目可以再找一个人类队友，外加任意多个编程 Agent。一个人做也完全可以，Eric 说以现在 Agent 的能力，一个人做也许更合适。
  • 课程拿到了几家编程 Agent 公司的额度：Claude Code、Factory、xAI、Devin（Devin 和 Windsurf 同属 Cognition）。
  • 开源合作伙伴的具体安排下周讲，有几家会亲自来课上介绍项目，有的还会办线上或线下答疑。
  • 想从候补名单进课的申请截止到 9 月 27 日（周日）。

二、从骨架到外壳

上一讲证明了一件事：150 到 200 行代码就能搭出编程 Agent 的骨架，它能理解请求、读写文件，从 hello world 做到稍复杂一点的东西。这一讲要把它拉到今天的水平，解剖一个最先进的编程 Agent 的内部。

能看到的是除了模型以外的一切。模型是"智能层"，是一大组参数，跑在分布在世界各地的服务器上，看不见；但包在模型外面的那一层看得见，这一层叫外壳（harness）。核心循环和上一讲一样：用户通过外壳的界面说话，外壳和 LLM 来回交流，LLM 再和一组工具来回交流，工具让模型"落地"，能搜网页、能动文件系统。外壳就是围在这个循环周围的所有附加机制。

为了讲最新的东西，Eric 选的是 Claude Code 配 Opus 5.5，这个模型两天前刚发布（他提到 OpenAI 几乎同一天也发了新模型，两家常常把发布安排在同一天）。课件贴了 Anthropic 公布的基准测试表，Opus 5.5 在多数编程 Agent 基准上排第一。

Eric 强调的一个结论：外壳设计可能是编程 Agent（乃至所有 Agent）里最难也最重要的问题之一。这里讲的是编程，但很多原则同样适用于销售、法律、客服等其他领域。如今比较标准的外壳部件有：

  • 系统提示词（system prompt）
  • 自定义配置文件（AGENTS.md、CLAUDE.md 等）
  • 工具列表
  • 计划模式（plan mode）
  • 子 Agent（subagent）
  • Skill
  • Hook
  • 上下文压缩（compaction）

课件第 7 页把它们画成一张图：中间是 Agent 循环（上下文窗口，即所有 token；模型选下一步动作；外壳执行工具调用），左边是送进上下文的输入（系统提示词规定身份、规则、环境；AGENTS.md 是项目记忆文件；工具列表；按需加载的 Skill），右边是外壳机制（压缩会缩短历史；计划模式只给只读工具；子 Agent 有隔离的上下文）。

三、演示方法：抓包看请求

这一讲是边讲原则边看真实数据。Eric 用一个代理工具拦截 Claude Code 发出的请求和收到的响应，把它们存成 JSON 文件。上过 CS144 的同学可以把它想成 Wireshark：抓网络包，在协议层面看发生了什么；也可以想成浏览器的调试控制台。第一次作业就是让每个人自己做一遍这件事。

演示用的项目是他"vibe code"出来的一个命令行待办工具，能添加任务、列出任务、标记完成、加子任务。他凌晨四点和 Claude Code 聊了一阵，把所有请求都记了下来。打开记录：

  • 有一个 model 字段，然后是一个 messages 列表。这就是上一讲那个不断追加的对话列表。
  • 每条消息有角色：user（他打的字，也包括工具结果）、assistant（Claude 的回复，比如发起工具调用），还有外壳在背后注入的系统信息。
  • 很多消息被"加料"了：外壳塞进了平时看不见、但能帮 Claude 干活的信息。这就是要拦截请求才能看到的东西。

四、工具列表

工具是 LLM 在静态参数和训练之外接触真实世界的方式，可以是本地文件系统、电脑上的东西，也可以是网上的东西。Claude Code 下载下来大约自带 40 个内置工具，这是 Anthropic 团队认定编程 Agent 应该具备的能力；Eric 进一步说，模型本身经过后训练（post-training），已经针对这些工具优化过。除了内置工具，还有 MCP 工具，MCP 是把外部工具和资源接入外壳的方式（第四讲细讲）。

要记住的一点：工具可以看成一个函数，它定义里的一切，包括描述、注释、名字、完整签名，都会变成提示词的一部分，被注入上下文。所以给 Agent 写工具时，docstring 写得清楚一致、参数类型写得明确，很要紧，这是模型判断"做什么、什么时候用这个工具"的全部依据。

在抓到的请求里，messages 下面有一个 tools 块，是一个列表，每个元素是一个字典。比如 Agent 工具：它能启动一个新的 Agent 处理复杂的多步任务，描述里写明了那个 Agent 的能力；还有一个 schema，相当于这个工具的函数签名，列出可以指定的属性。Eric 把内置工具和 MCP 工具分开列，约 40 个内置工具涵盖：访问文件、通过 Bash 操作 shell、类似 cron 的监控、网页搜索、用 LSP（语言服务器协议）检索代码、Agent 相关工具、计划和隔离工具、定时任务工具、创建 artifact 和列出 MCP 资源的工具、与用户交互、调用 Skill、提问、推送通知、发送反馈等。MCP 工具的名字以 mcp__ 开头，表示来自外部服务器，比如文档托管服务 Mintlify，或者 Notion、Slack。

有同学问：这些全都在同一个请求体里吗？是的。每接一个 MCP 服务器，它的所有工具都会出现在这个块里，每次请求都带上。这也是后来引入 Skill 的原因之一：渐进式披露。Skill 一开始只放一小段描述它做什么的元数据，等到和任务相关时才把完整内容拉进来。

所以要小心接入哪些 MCP 服务器，它们会把上下文撑爆。无关的东西放得越多，Agent 越容易把任务做砸；已经有研究在测，上下文里有多少 token 时性能开始下滑。

课堂问答里的几个点：

  • 为什么 Agent 之间用自然语言而不是向量传递信息？Eric 说不清内部细节，但训练数据大多是自然语言，人工标注的数据也是文字，人很难用向量和系统交流。
  • 看到的这个 JSON 是请求的原始形态，真正喂给模型前很可能还有压缩、精简之类的处理，那部分可能是各家的独门手艺，看不到。
  • 元数据里有校验和、哈希、UID 等，缺了这些可能造成安全漏洞。
  • MCP 工具和 Skill 的区别：MCP 工具是最小的原语，有点像一次 API 调用，一进一出；Skill 是把工具、函数、脚本和其他资源包成多步操作的流程。两种粒度都有用。

历史：从工具膨胀到少而强

Claude Code 大约在去年 12 月走红，原因之一是它的外壳很简约：很长一段时间里只有一小组工具，却几乎什么都能做，40 个在这个意义上也不算多。强大的工具比如 Bash 和 SQL：给 LLM 文件系统和命令行，就能做复杂操作，Bash 本身就是一门完整的语言。

2024 年底 MCP 刚出来时，GitHub 的 MCP 服务器一上来就有大约 110 个工具：列 issue、建 issue、评论 issue……这些有用，但加了大量上下文，上下文越臃肿，LLM 越差。Claude 在精简这件事上迈了一大步：从三到五个能干很多事的工具起步，再慢慢加。整个行业的趋势是降低复杂度，用更少的工具做更多的事，大家都在找"瑞士军刀"式的工具，SQL 和 Bash 就是例子。

五、系统提示词

系统提示词是 LLM 行为的蓝图：一段定义外壳及其行为、护栏和环境信息的文字。它由外壳设定，你说什么都不影响它，你也不控制它，但每次 Claude 发请求都带着它。

在抓到的请求里，有一个就叫 system 的块，里面有两段相关内容。第一段是"You are Claude Code, Anthropic's official CLI for Claude"，外壳用自然语言告诉模型它是什么系统。第二段是主要的指令，也就是 Opus 5.5 的系统提示词，大约 50 到 80 行，比以前的版本短了不少。里面写了：你是帮用户做软件工程任务的交互式 Agent；需要注意的事，包括安全相关的指令；外壳是什么、怎样和它交互；会话的信息；一大段关于记忆的说明；环境信息，包括有哪些 Claude 模型可用；一点上下文管理的说明。

记忆是 Anthropic 和 Claude Code 比较新的功能：一种从你的行为中学习的隐式记忆机制。Eric 说这本来就应该有，只是之前各家公司做得都不太好，现在重新做了。记忆存放在文件系统的某个位置，提示词规定了 LLM 决定写记忆时用什么格式，打开那个位置能看到 Claude 提取出的记忆的元数据块。有同学问记忆是每次运行独立的还是怎样：从路径看是项目级的，每个项目各有一份。它会被追加进系统提示词吗？Eric 说更准确的理解是：它们是分开的几个块，拼接在一起放进请求，属于提示词的一部分，但最好看作和系统提示词本身不同的对象。另一个同学问检索记忆是否该用 RAG 或 GraphRAG：这些设计决定是由基准测试驱动的，结果发现更复杂的检索系统并不总比让模型直接读平铺的文本强，要看任务。Eric 自己公司做的销售 Agent，记忆也用的是平铺文件。

系统提示词变短这件事值得一提：直到一两个月前，它还有 200 到 250 行，其中很多在教模型怎么用 Git、怎么开任务，那时觉得这些必须明说，现在好像没那么必要了。Eric 猜训练过程已经把这些信息学进了参数里。这和精简 MCP 工具是同一个道理：要减少超长系统提示词带来的臃肿。他记得大约一个月前系统提示词又缩短了约 8%。这些文字不是你写的，你看不到，可每次请求都在你的上下文里，第一次请求时可能已经有几万个 token 被你控制不了的东西占掉了，结果效果不好时你还一头雾水。

有同学问：既然能看到系统提示词，这算不算攻击面？Eric 认为没有想象中严重。一是抓这些请求并不难，有开源工具；二是 Claude Code 的整个系统大约半年前泄露过，泄露时大家惊呼"终于知道 Claude 怎么工作了"，可其实早就知道了，用 Wireshark 式的检查就能看到，他在泄露之前就这么做过。Codex 的外壳更是直接放在 GitHub 上。至于用提示词注入去攻破它，他相信人们早就在试，最简单的手法应该都已经被处理，而且有专门的团队负责防范。

六、CLAUDE.md 与 AGENTS.md

这两个是 Agent 配置文件。CLAUDE.md 是 Claude 专用的，AGENTS.md 是更通用的标准。本来好像所有人都认了 AGENTS.md，只有 Anthropic 想与众不同，几周前它也开始支持了；可以把 CLAUDE.md 用软链接指向 AGENTS.md。两者功能完全一样，只是名字不同，在 Codex 和 Claude 之间切换时有点烦，Eric 说这是"很弱的围墙花园"。

它是系统提示词在用户这一侧的对应物：系统提示词是静态的、外壳设定、背后注入；CLAUDE.md 也被注入，但由你控制，而且优先级高于其他指令。演示项目里的 CLAUDE.md 是他和 Claude 一起写的，核心内容是项目里什么东西在哪。

回到请求的开头：他打的第一句话是"这个待办应用的核心组件是什么？"但在这句话所在的 user 块里，上面还有一大段他没打过的东西，比如 system reminder，是外壳在背后加的。其中就有 CLAUDE.md 的内容，最上面写着：这些指令覆盖默认行为，必须严格照做，后面跟着文件路径。

怎样写好这个文件后面有一整讲（第七讲）。目前的共识是：放一些运行代码的指引，比如怎么跑测试、怎么启动服务，但不要太多，这是一条细线。放得太多会过度约束系统，你以为给的信息越多越好，结果模型几乎"过拟合"到你的指令上。一般不放整段代码，最多一两条命令，比如跑单元测试的确切命令、启动服务的命令。

七、计划模式

计划模式是专门用来设计规格（spec）、处理较难任务的模式。大约九个月前，多数编程 Agent 外壳都加上了它：和用户来回沟通，澄清需求和架构，最后写出规格。课件上的定义是：一个明确的工具，提示 Agent 为某个改动制定规格，并可以继续向用户提问来澄清需求。

它其实就是一段文字。在 Claude 里有一个进入计划模式的工具，外壳随即注入一大段说明，做完后有另一个工具退出计划模式。Codex 等其他外壳基本也是这样。Claude 的计划提示词描述了一套流程：第一阶段理解用户需求，其中甚至会派出 Agent 去探索代码库；第二阶段设计；然后是复查阶段、最终计划，做完就退出计划模式。最重要的是最后生成的产物：计划文件。演示里他想给待办应用加周期性提醒（比如"每周浇花"），进入计划模式、来回讨论，最后得到一份计划。

八、Skill、子 Agent、Hook 与压缩

Skill

Skill 的核心是一段书面的操作流程，可以包含多次工具调用和本地脚本，用提示词串起来，完成更复杂的任务。它可以由 Agent 根据上下文主动调用，也可以由用户明确调用，比如你让它审查代码，或者它发现任务做完了，自己调用代码审查的 Skill。后面有一整讲讲怎样设计好 Skill（第五讲）。

Eric 为这门课写了一个叫"check code quality"的 Skill，做法是写一个 SKILL.md 文件，描述要做什么、什么样的代码算好、什么样算差。会话中他特意说"用这个 Skill 检查我的代码质量"，好让它出现在记录里。在请求里看到：外壳注入了一段带"check code quality"命令的文本，告诉 LLM 该检查代码质量了，然后外壳找到 Skill 文件，把内容插进上下文。

子 Agent

子 Agent 让你把任务的一部分委派出去。有一个主控 Agent，即 Claude Code 的主循环，它可以调用带着全新上下文窗口的帮手；这样能并行，也能给不同任务定制行为（并行会增加 token 花费）。帮手做完把结果交回主 Agent。好处是每个子 Agent 从空白上下文开始，不继承父 Agent 的全部上下文，它的探索发生在主流程之外，只把结果带回来，是更好地管理上下文的办法。在记录里，子 Agent 是通过一次工具调用产生的，做完工作，返回结果。

Hook

Hook 是在外壳生命周期的不同节点插入的提示词或代码片段，需要做某些预处理或后处理时尤其有用。这一讲只简单提到，最佳实践在第七讲。

压缩

上下文越来越长时，压缩是把它整合、总结，减少臃肿的办法。和计划模式一样，有一个压缩模式。触发方式有两种：快要超过上下文窗口（比如接近一百万 token）时自动触发，或者你手动调用。有一整段提示词规定怎样写摘要，摘要会替换掉它所总结的那部分上下文，比如把 50 万 token 压成 15 万，之后模型看到的就是这份摘要。压缩会丢信息，所以你可能想定制自己的压缩方式。什么时候该主动压缩，后面会讲。

九、好外壳的原则：简单

核心循环外面有很多附加机制，但趋势是越来越简单：

  • 更少、更强的工具（SQL、Bash 等）。Claude 现在的约 40 个原生工具，比过去的版本少。外壳设计者越来越依赖底层模型的能力，而不是让外壳承担难题。
  • 注意上下文窗口，避开"笨区"（dumb zone），所以要小心工具膨胀。"笨区"不是正式术语，是大家对 LLM 开始变迟钝的那段上下文的俗称，第三讲会讲怎样避开。
  • 提示词的内容和长度会变，要让它们容易调整。现在的倾向是更短，既为了避免臃肿，也更容易针对任务修改。

Eric 还提了一个 Agent 设计里反复摇摆的大问题：该把力气花在模型上，还是外壳上？有时人们说价值和护城河在外壳；接着又有人指出训练 LLM 花了几十亿美元，应该投资模型。行业一直在两头来回。现在的共识是外壳尽量简洁，仍然可以做有意思的事，只是要小心别把上下文撑爆。
