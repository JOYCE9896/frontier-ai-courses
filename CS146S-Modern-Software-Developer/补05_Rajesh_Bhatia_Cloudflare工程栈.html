补充五：Rajesh Bhatia 谈 Cloudflare 的 AI 工程栈

一家大公司怎样在一年里让 93% 的研发人员用上 AI 工具：AI 网关、身份、Backstage 和 AGENTS.md 提供的上下文、可机读的工程规范，自建的多 Agent 代码审查器，怎样衡量投入产出，以及从"辅助"走向"委派"的后台 Agent

讲者：Rajesh Bhatia（Cloudflare，负责内部开发者效率平台）；主持：Ona 的产品设计与工程负责人 Matt
这一篇不是课堂讲座。Rajesh Bhatia 11 月 12 日（第 8 周）在 CS146S 做过客座讲座，但那一讲没有公开课件和录像。这里整理的是他在 Ona 活动上的一场公开访谈：Cloudflare's AI Engineering Stack: Assisted to Delegated（Ona 频道，2026 年 5 月 6 日上传，37 分 56 秒）。本文依据 YouTube 自动生成的英文字幕整理。访谈多次提到 Cloudflare 博客上的一篇长文（讲他们怎样用自家产品搭内部 AI 工程栈），本文只整理访谈里说到的内容。
和课程的关系：第 8 周讲后台 Agent，第 9 周讲打造 AI 原生团队（MCP 门户、LLM 网关、模型路由、全组织推广）。这场访谈讲的是一家大公司全组织推广的实际过程，最后一部分谈到后台 Agent，可以和第十一讲对照。

一、背景和数字

Rajesh 在 Cloudflare 工作了 8 年，主要负责内部的效率平台团队，"the remit is to help our engineers life be very efficient internally"。主持人提到那篇博客里的数字：近 4,000 人在用，占研发的 93%，覆盖 295 个团队。

二、搭了一个什么样的平台

他说目标是在 AI 工具周围建一个平台层，"not just coding assistance, but the stack that makes the tools useful and safe inside a real engineering organization"。

起点是大约一年前，CEO Matthew Prince 在一次财报电话会上说 MCP 会改变每个人的工作方式，团队把这句话当真了。内部成立了一个叫 iMARS 的小组（internal MCP agents and server rollout squad），召集感兴趣的工程师搭内部 MCP 服务器和 Agent 基础设施。之后扩展成由效率平台团队牵头、覆盖整个软件开发生命周期（SDLC）的工作，并把为客户做的产品用到内部：

  • AI Gateway：做模型路由、设置控制、提供可见性。LLM 网关是所有模型请求都经过的一层代理。
  • Access：Cloudflare 的身份认证产品，用来管理各种 AI 工具的身份和权限。
  • 上下文：已有的 Backstage（内部开发者门户）和各仓库的 AGENTS.md。
  • AI 代码审查器和 engineering codex：codex 是一套机器可读的工程规范。

最初的问题很简单："People could see the promise of AI coding tools, but without context, trust, and controls, it didn't feel like we were going to be there."

三、怎样做到 93% 的采用率

一开始采用得很慢：搭 MCP 服务器的时候模型还不够好，用不到工程师真正想用的工作流上。拐点出现在模型变强以后，而他们之前已经把上下文和 MCP 基础设施准备好了，所以工具一下子能帮上实际工作。另外几件起作用的事：一条命令就能装好、共享配置、上下文，这些让工具产出更好的结果，采用率也跟着上去。非工程岗位的使用也越来越多。

拐点具体是什么时候？2025 年六七月他们已经引入 Windsurf IDE，也在试 Claude Code 等工具，但到 11 月左右才明显看到收益，"I think Opus 4.5 maybe was the inflection point"。主持人也说，圣诞假期后大家回来，怀疑的态度好像都消失了。

他用两个词描述这一年的变化：去年流行的是 vibe coding（氛围编程），它降低了门槛，让更多人能参与写代码；现在是 agentic engineering，重点变成保证质量，让产出符合真正的软件工程标准。

剩下的 7%

他观察到很多人先用 IDE 里的工具，而越来越流行的 CLI 工具安装配置更麻烦，有工程背景的人容易上手，非工程背景的人就难。所以他们在做一键安装依赖和配置。另外公司层面也在推广（比如在 Google Workspace 里用 Gemini）、做培训、分享成功案例，"by educating it by having some mandates even together along with that"。对仍有疑虑的人，他们收集反馈并调整工具。

四、人人都能写代码，谁来把关

代码变便宜了，但不是每个人写的都该上线。他们的办法是一层"执行层"（enforcement layer）：把工程规范写成机器可读的 engineering codex，用 AI 代码审查器按规范自动审查所有提交，任何改动至少先过一层审查和质量护栏，然后再由人审。

他们没有限制谁能提交，"the more people contribute, the more we are able to try to review automatically"。既然有统一的关口，"it really doesn't at that point matter the role that submitted the initial change"。最终由负责在生产环境运维这个系统的团队决定改动能否上线，这个环节会有瓶颈。

五、Backstage 和 AGENTS.md：减少模型的猜测

主持人说很多公司已经不太坚持做内部开发者门户（IDP），问 Backstage 在 AI 里起什么作用。他的解释：

"the code tells the model what's in front of it, but it does not tell the model who owns the service, what the dependencies are, where the boundaries matter, what databases are being talked to, what conventions are that the teams consider non-negotiable."

Backstage 给出整个系统的地图，AGENTS.md 给出仓库的地图，两者"reduce the amount of guessing the models have to do"。他们吃过亏才学到："even with the decent context file, it is better than having none. And when the model stops guessing, the quality goes up everywhere else." 他建议各公司都投资某种服务目录。

Backstage 覆盖了 4,000 多个仓库。数据怎样保持不过时？一部分靠自动化，一部分仍要人来核对。另外他们做了很多依赖 Backstage 数据的使用统计工具，团队想用这些统计，就有动力回去把数据改对。主持人总结为一个正向循环：Backstage 对 Agent 工作流越重要，大家越愿意维护它。

六、怎样衡量值不值

主持人提到 AI 的投入产出很难衡量，又很贵（他举了"Uber 的 CTO 到 4 月 1 日就花光了全年 token 预算"这个流传的说法）。Rajesh 的看法：

  • 请求数和 token 数反映用量；合并请求数和流水线次数反映平台活动；这些都不等于价值。
  • PR 数量"is easy to count, of course, but it is also very easy to over interpret"。
  • 更有意义的长期问题是功能交付速度，以及能不能更顺畅、更安全地把改动发出去。

AI Gateway 和 Workers AI 提供了"operational truth"：能看到用了哪些模型、成本曲线、缓存命中情况，以及哪些开源模型在某些场景已经够用，例如他们据此调整代码审查器里开源模型的用法。但这回答不了所有效率问题，"It just keeps us honest about what's actually happening"。他的建议是在开始之前就把可见性、成本归属和指标建好。

七、自建的多 Agent 代码审查器

先 AI 批准，再人批准

审查器接在 CI 里，必须先由 AI 审查器批准，才能请人批准 PR。它是多 Agent 的：有安全审查、代码质量审查、文档审查等，可以分别调整用哪个模型、花多少钱。评估方式包括一套针对审查提示词的评测、上线后的反馈，以及一些指标：开发者有多少次按审查器的意见改了代码，有多少次用了"break glass"（紧急绕过）功能；每次审查还收集反馈，据此换模型或加新规则。主持人认为审查正在成为新的瓶颈，一天能生成 50 个 PR，先让 AI 过一遍再交给人很合理。

从主观意见到对照规范

早期的做法只是把 diff 交给模型、让它给意见，效果不好："engineers don't trust AI opinions. They just trust clear findings tied to standards that we have agreed upon." 意见听起来很主观，常被忽略。引入 engineering codex 后，输出变成结构化的，能校准严重程度，并对应到具体的 codex 条款，"it stopped sounding more like maybe this is a problem and started sounding more like this violates a standard that we actually care about"。信任因此建立起来，采用也快了。推更多强制规则时要慢慢来、收集反馈，平衡开发者体验和规范，就像平衡开发者体验和安全一样。

为什么自建

大约一年前他们也看过第三方代码审查工具，最后决定自建，他认为很值：能按自己的工程规范定制，能做成多 Agent（例如专门的安全 Agent 按安全最佳实践审查），这些用第三方工具很难做到。

关于"自建还是购买"，他说 Cloudflare 本来就在做开发者平台和各种底层组件，所以自建对他们来说更容易，不一定适用于每家公司。他们也用一些第三方工具；如果某个供应商愿意配合定制，也可能买。"it's in your journey you need to decide what is right for the company where you are at right now."

八、下一步：从辅助到委派

他把后台 Agent 看作"a movement from assisted work to delegated work"。Cloudflare 刚办过的 Agents Week 发布了沙盒、Agent SDK 等组件，内部和客户都会用。Agent 能在云端按计划运行、用同样的工具和护栏之后，更长的工作流就自然了：迁移、跨整个仓库的改动、生成测试、写文档，各种运维性的任务。

但信任边界也随之改变："Once the agent is off the box, you still need to be able to have the right identity, the execution isolation and the governance. They will continue to matter more not less."

九、给刚起步的公司的建议

如果明天开始，先建三样东西：身份方案；上下文层（知识层）；安全执行的环境。"don't start with some flashy demo, start with parts that make the system trustworthy." 主持人总结为：要像给新员工入职一样给 AI"入职"，给它和工程师一样的上下文和信任。

他最后说，从 CEO 的一句号召开始，花了 11 个月重新思考代码怎样写、怎样审、规范怎样执行、改动怎样跨仓库发布，每一层都跑在客户用的同一套产品上；现在做的只是第一版，"there's more ahead of us"。
