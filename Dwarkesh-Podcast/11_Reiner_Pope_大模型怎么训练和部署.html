01. 批大小怎样决定 token 的成本和速度

节目位置 0:00:00–0:31:59 · How batch size affects token cost and speed

开场的三个问题

Dwarkesh 说，这一期想讲清楚训练和推理在集群上怎么跑。他的理由是：搞懂了这个，很多事情就说得通了，比如 AI 为什么是现在这个样子、模型架构为什么这样设计、API 价格为什么这样定、AI 进展为什么是这个节奏。

他先抛出 Fast Mode 的例子：几家公司都提供 6 倍价格、2.5 倍速度的选项。他问了三件事：机制是什么；能不能继续往上加钱换更快；能不能反过来，愿意等几分钟的用户换更低的价格。

Reiner 直接给结论：最大的因素是批大小。另一个因素是投机解码（speculative decoding）或多 token 预测（multi-token prediction），他说可以以后再谈，这期没有展开。

分析方法：roofline 加两个模型因素

他用两个原则来分析。一是 roofline 分析：看一个 Transformer 在一组芯片上跑的时候，内存带宽和算力分别卡在哪里。（roofline 分析是一种估算方法，把一段计算需要的时间分别按“搬数据”和“做乘法”算出来，取两者中较大的一个作为下限。）他拿 Blackwell NVL72 做例子，也就是一个装 72 块 GPU 的机柜。二是只看模型的两个因素：处理权重要花的时间，处理上下文（KV cache）要花的时间。

他强调这里算的都是下界：真实时间大于等于这个数，因为有些项被忽略了。但他说这个简单模型的预测能力很强。

  • 计算时间：批大小 × 激活参数量 ÷ 芯片的 FLOPs。这一项覆盖所有权重矩阵乘法。注意力本身的计算量他说相对很小，先忽略。
  • 内存时间：两部分。一是取权重：要取全部参数，不只是激活参数。二是取 KV cache：批里每个序列都要取一整段上下文，所以是 批大小 × 上下文长度 × 每 token 字节数。两部分加起来除以内存带宽（字节/秒）。

Dwarkesh 帮观众补充：推理时服务器不是一次只服务一个用户，batch 指同时服务的一批用户。Reiner 预告了后面的结论：如果不把很多用户凑成一批，成本和经济性可能差到 1000 倍。

关于激活参数，他举 DeepSeek V3：激活参数约 370 亿，总参数约 7000 亿。（MoE，混合专家模型，每个 token 只经过一小部分“专家”子网络，所以每个 token 实际用到的参数远少于总参数。）

KV cache 是什么

Dwarkesh 请他先解释 KV cache。Reiner 画了自回归解码（decode）的过程：每生成一个新 token，要把它过一遍整个模型的所有权重矩阵；同时注意力机制让这个新 token 去“看”所有之前的 token。它看的是模型给之前每个 token 算出的内部表示，这些表示存起来就叫 KV cache。他说这一步主要受内存读取限制，不受矩阵乘法限制。

时延和批大小的关系

他先画“批大小对时间”的图。计算时间对批大小是一条过原点的直线。内存时间里，取权重是一个与批大小无关的常数，取 KV 随批大小线性增长；两者相加是一条带截距的斜线。总时间取两条线中较大的那条。

结论一：时延有下界。批再小，也得把全部参数从内存读进芯片一次，用满内存带宽也不可能更快。这部分回答了“能不能花更多钱换更快”：在给定硬件配置下，存在一个时延下限。

Dwarkesh 问，图上 KV 的斜率比计算的斜率小，是不是意味着批足够大时计算总占主导、内存永远不是问题？Reiner 说这对上下文长度很敏感。上下文越长，取 KV 的时间越长，系统会从受算力限制变成受内存限制。两条斜率刚好相等时，说明内存和算力同时用满，这是理想位置。

Dwarkesh 接着问：如果最优上下文是 100K，跑到 200K，MFU（模型 FLOPs 利用率，芯片算力实际用上的比例）会不会掉到 50%？Reiner 说按这个模型确实如此，但前提是内存读取量和上下文长度成正比。这对所有用稠密注意力（dense attention）的架构成立，稀疏注意力（sparse attention）的扩展性好得多。被问到实验室是不是都用稀疏注意力，他说不知道实验室用什么，他本人看好稀疏注意力；DeepSeek 发表过一种稀疏注意力机制，在那几篇论文里，这一项变成了平方根关系。

成本和批大小的关系

时延图上看不出成本。他的算法是：跑一次推理要占用 GPU 若干毫秒，按每块 GPU 每小时 2 美元左右付租金；这次推理处理的 token 数就是批大小。所以每 token 成本 = 时间 ÷ 批大小。

把三条线都除以 B：计算时间变成常数，取 KV 的时间也变成常数，取权重的时间变成随 B 下降的曲线。批大小为 1 时成本接近无穷大，因为权重读取没有被分摊；批越大，权重读取摊得越薄，最后计算成本决定一切。所以成本也有下界。

这回答了“Slow Mode”：Claude Code Slow 或 Codex Slow 就会落在这条下界线上，帮不了多少。原因是 KV 读取和计算都是每个序列各自独有的，没法在更大的批里分摊。

实际需要多大的批

Dwarkesh 问：到不再受内存带宽限制的那个点，实际需要多大的批？Reiner 说可以直接解出来，而且对模型架构不太敏感。为了得到干净的答案，他先忽略 KV 读取，只让“取权重时间”等于“权重计算时间”：

总参数 ÷ 内存带宽 = 批大小 × 激活参数 ÷ FLOPs。整理成 FLOPs ÷ 内存带宽 = 批大小 × 激活参数 ÷ 总参数。左边全是硬件参数，右边全是模型参数。左边如果按 FP4 来算（每个 FP4 数占半个字节），可以变成一个无量纲常数，大多数 GPU 上大约是 300。

Dwarkesh 问这个比值有没有随硬件代际变化。Reiner 说从 A100 到 H100 到 B100，FLOPs 和内存带宽都涨了很多，这个比值保持得比较稳定。

于是批大小要大于约 300 × 稀疏度（总参数 ÷ 激活参数）。DeepSeek 在 256 个专家里激活 32 个，稀疏度是 8，算出来约 2400。他说这个数和实际情况惊人地接近，实践中会再放大一些，因为真实效率达不到 roofline 的理想值，通常乘 2 到 3。Dwarkesh 据此说是两三千 token 一批。如果把 KV 读取算进去，KV 占掉一部分内存带宽，留给权重的更少，批还要更大。

Dwarkesh 觉得这个数太小，连一个序列都不到。Reiner 解释：这里的 token 数是“这一步要各自再生成一个 token 的序列数”，所以实际上是约 2000 个不同的序列，每个序列在这一次前向计算里各前进一个 token。

“发车时刻表”：凑批要不要等

Dwarkesh 问：凑满一批会不会带来额外等待？Reiner 用发车时刻表来讲（这是他自己的说法）：选定批大小后，假设一步要 20 毫秒，这是常见的落点，GPU 每 20 毫秒发一班车，到点就走。乘客赶上了就上车，满了就等下一班，没满也照样发车。最坏情况是请求刚好在发车后到达，等 20 毫秒上下一班，再花 20 毫秒跑完，最坏排队时延 40 毫秒。

20 毫秒从哪来？他说这是经验值，来源和内存容量有关：一次前向计算里，希望把全部内存容量（存权重或 KV）都读进芯片一遍，所需时间是 容量 ÷ 带宽。这个值在很多代 HBM 上都在 20 毫秒左右。（HBM 是高带宽内存，堆叠在 GPU 旁边的显存。）比如 Rubin 一代大约是 288 GB ÷ 20 TB/s，约 15 毫秒。

为什么不选比 15 毫秒更长的时间？他说那意味着有时间把 HBM 读两遍，但没有意义，权重和 KV 都不需要读两遍。他补充，HBM 访问几乎全是读：权重矩阵只读，KV cache 的访问也绝大多数是读。

规模经济有多大：至少要有 Gemini 的千分之一

Dwarkesh 总结说，最优批大小大约 2000，只取决于稀疏度，和模型规模无关（Reiner 补一句：稀疏度会体现在模型规模里，除此之外与规模无关）。他问这对推理的集中化有多大推动，2000 个并发用户看起来不算多。

Reiner 说更有用的视角是每秒 token 数：每 15 到 20 毫秒跑一批，每秒约 64 批，所以吞吐约 64 × B，约 2000 × 64 = 128,000 token/秒。他记得 Gemini 去年的某些公告提到全球流量在每秒数亿 token。128K 只有那个量的千分之一。他的说法是：Gemini 很大，Gemini 的千分之一也很多，要在规模上有竞争力，至少得能服务 Gemini 的千分之一。

稀疏度能推多远：Unified Scaling Laws 论文

Dwarkesh 接着问：稀疏度越高，需要的算力越少，但模型质量会不会下降得比省下的算力更快？Reiner 说这没法解析推导，只能看实验，于是调出了论文 “Unified Scaling Laws for Routed Language Models”。他说这篇比较老，结论对 MoE 的具体做法很敏感；MoE 早在 2017 年左右就有了，GShard、Switch Transformer 是更早的方法，DeepSeek 的 MoE 又改动很大。

论文里用的是较老的技术。固定激活参数，增加专家数，质量持续上升。在 1.3B 稠密模型那条水平线上，64 个专家、激活 3.7 亿参数的模型和 1.3B 稠密模型一样好。Dwarkesh 算了一下：总参数涨 64 倍，换来相当于 4 倍激活参数的效果，回报并不惊人。

Reiner 的看法是，从这节课的分析框架看，这仍是净收益：多出来的那部分内存读取可以靠批大小摊掉，只要一直加大批，直到用户不够为止。用户越多，可以用越稀疏的模型。另一项代价是内存容量。Dwarkesh 复述：想少花计算时间就提高稀疏度，要让它划算就需要更大的批，也就需要更多内存容量。

02. MoE 模型怎样摆在 GPU 机柜上

节目位置 0:31:59–0:47:02 · How MoE models are laid out across GPU racks

一层 MoE 的结构

Reiner 画了一层 MoE：token 进来先过路由层（router），路由决定送到哪几个专家，通常只占很小一部分，比如 1/32。每个专家就是一个普通 MLP：上投影、非线性、下投影。之后把各专家的输出收回来相加，再加上残差连接。

专家并行和 all-to-all 通信

他说标准做法也是最好的做法是专家并行（expert parallelism）：不同专家放在不同 GPU 上。以 DeepSeek 的 256 个专家放进 72 块 GPU 的 Blackwell 机柜为例，256 不能被 72 整除，简化成只用 64 块，另外 8 块不管，每块 GPU 放 4 个专家（为了画图他改成每块 2 个）。

token 送出去要付一次通信成本，收回来再付一次。通信模式是任意 GPU 对任意 GPU，取决于模型的路由决定，叫 all-to-all。Dwarkesh 问路由是不是只在一块 GPU 上。Reiner 说实际上路由有很多份，和 GPU 一样多；图上左右两排 64 块 GPU 其实是同一批，只是承担不同用途分开画。

他说 Blackwell 机柜的连接方式和 MoE 需要的 all-to-all 模式完美契合。但如果一个机柜太慢，想用两个机柜，两个机柜之间就没有 all-to-all 互联了，机柜间通信会成为大瓶颈。所以一个机柜限定了一层专家能做多大。他说这也是推动互联域越做越大的原因之一。

机柜是什么，柜内和柜外差多少

Dwarkesh 请他解释什么是机柜。Reiner 说这里 Nvidia、Google 和其他公司（包括 MatX）差别很大。一般而言，机柜是几米高、一两米宽的物理结构，装大约 64 块 GPU 或 XPU。限制它大小的是供电、重量和散热能力。一个数据中心可能有几千个这样的机柜并排放。

Nvidia 的做法是把 GPU 放在机柜外侧，NVSwitch 交换机放在中间，每块 GPU 都有线缆连到中间的交换机。任意两块 GPU 之间只要两跳：到交换机，再到另一块 GPU。这套就是 NVLink，更通用的叫法是 scale-up 网络（纵向扩展网络）。要出机柜就走另一条路：每块 GPU 还连着 scale-out 网络（横向扩展网络），接到数据中心交换机，带宽通常慢约 8 倍。

如果一层 MoE 横跨两个机柜，平均一半 token 留在柜内走快网，另一半要出柜走慢网，慢网就成了 all-to-all 的瓶颈。

为什么不做一个更大的 scale-up

Dwarkesh 问：为什么不把一百万块或一千块芯片都放进 scale-up？Nvidia 从 Hopper 的 8 块到 Blackwell 的 72 块，再到 Rubin 的五百多块，靠的是什么？

Reiner 说，用层级交换机而不用一个大交换机，是为了控制线缆拥堵。Hopper 到 Blackwell 主要是产品决策：把形态从托盘（tray）换成整机柜，没有大的技术障碍。从 64 到五百多，他说里面有一点“Jensen 算术”，但至少有真实的 4 倍提升，来自复杂得多、难得多的机柜设计，是能走更多线缆的新物理设计。

他重画了一张图说明线缆密度：机柜里 GPU 数翻倍，竖着走的线缆密度也要翻倍。Dwarkesh 说数据中心里机柜看上去空间很大。Reiner 说机柜外有空间，柜内越优化越紧：托盘到机柜背板的连接器密度、背板本身的密度都很高，还有线缆弯曲半径的限制，弯太狠会折断。他说机柜设计不是他的专长，但听做这个的人讲，约束是多方面的：空间、重量（机柜很重，要足够的金属防止下垂，金属多了又更重）、供电和散热，现代机柜在这些方面都推到了物理极限。

为什么 GPT-4 之后参数量好几年没涨

Dwarkesh 问 GPT-4 是哪年发布的，Reiner 说 2023 年。Dwarkesh 说 GPT-4 传闻超过一万亿参数，直到最近六个月才有参数明显更多的模型发布，而按理说这三年应该一直在扩大。原因是不是一直在等内存够大的机柜，能装下一个 5 万亿参数的模型和足够多序列的 KV cache？做 RL 时也一样，要放下一批题目的 KV cache。

Reiner 说 Hopper 是 8 块一组，2022 年大约 640 GB。到 Blackwell（Dwarkesh 说大概去年部署），scale-up 域终于到了 10 到 20 TB 量级，足够放 5T 模型加 KV cache。他说部署更大的 scale-up 域是一个大突破。Google 的部署很早就有很大的 scale-up 域。

Dwarkesh 说这也解释了为什么 Gemini 似乎领先，Gemini 成功的预训练比别的实验室持续得更久。Reiner 说自己当时不在那里，不确定有多少来自更高稀疏度的成功部署，也可能来自很多建模上的东西，比如 MoE 的具体做法。DeepSeek 的 MoE 激活更多但更细粒度的专家，是一个大创新；模型架构和训练数据上肯定还有很多别的创新，很难拆开。他能确定的是：激活参数受计算成本限制，总参数受 scale-up 规模限制。

03. 流水线并行怎样把模型层分到多个机柜

节目位置 0:47:02–1:03:27 · How pipeline parallelism spreads model layers across racks

几种并行方式

Dwarkesh 问：待在单个 scale-up 域内，这个要求是针对前向还是反向、prefill 还是 decode？还是不管预训练、RL 生成、用户推理都最好待在一个 scale-up 里？

Reiner 说要回答这个得看通信模式。专家并行的 all-to-all 强烈偏好全连接，也就是一个机柜内部。文献里还有张量并行（tensor parallelism，把一个矩阵切开分到多块芯片），但随着专家越来越小，它已经不太相关，可以忽略。剩下的是数据并行（data parallelism，每组芯片各算一部分数据）和流水线并行（pipeline parallelism，把不同的层放在不同的芯片组上），这两种更适合跨机柜。

换机柜会不会成为通信瓶颈

他画了一摞 MoE 层，上面还有上百层，在某一层换到另一个机柜，再过若干层又换一次。判断换柜处会不会卡住，方法是比较 scale-out 带宽需求和 scale-up 带宽需求。他给的提示是：柜内要发很多份，换柜处只发一份。

Dwarkesh 试着推：进机柜的是批大小那么多，柜内是批大小 × GPU 数？Reiner 纠正为“激活的 GPU 数”，没被路由到的 GPU 根本不用发，这是很大的节省。

他写出比值：scale-up 时间 ÷ scale-out 时间。scale-up 快约 8 倍，所以基线是 1/8；然后乘上数据放大倍数：一个 token 进来会被路由到若干专家（DeepSeek 的情况可能是 32 或 16 个），即激活专家数；每个流水线阶段有多层，所以再乘每阶段层数；Dwarkesh 指出 all-to-all 有发出和收回两次，要再乘 2，Reiner 同意。希望这个比值大于等于 1，因为 scale-up 才是更宝贵的资源。

他说这不难：只要激活专家数 × 每阶段层数 × 2 大于 8 就行。激活专家数本身就可能是 8，再加大每阶段层数就能满足。结果就是一整条机柜流水线：一个机柜做一层，交给下一个机柜做下一层。

Dwarkesh 说他觉得有意思的是，实际最好的并行策略和模型架构在物理上一一对应：有专家就把专家放不同 GPU，有不同层就把层放不同机柜，没有什么花哨的东西。Reiner 换了个角度说：模型在几个维度上扩大，层数、模型维度、DFF 维度（MLP 中间层宽度）、专家数，每个维度都可以选择沿着切。数字足够大时沿那个维度切就有利可图。按现在模型通常的尺寸，选了两个维度，另外两个不划算。

流水线的麻烦和好处

Dwarkesh 提到 Ilya 的一次演讲说“今天我们知道不要做流水线并行”。他还说 Horace He 给他和朋友讲过一课：流水线并行的问题除了气泡，还会带来架构上的约束，比如 Kimi 有一种残差，让注意力看前面几层，用流水线就很难实现。

Reiner 承认这些复杂性是真实的，流水线是个大麻烦，但它也有好处，值不值得要自己权衡；推理里有一些好处，训练里可能更大。推理中它并不省内存时间或计算时间，只是把内存时间从一个芯片挪到另一个芯片、从一个机柜挪到另一个机柜，运行时间没有收益。它省的是内存容量：如果机柜内存是瓶颈，流水线能大幅缓解。

Dwarkesh 转述 Jane Street 的 GPU 性能工程师 Axel 的说法：做流水线必须用微批（micro-batch），用了微批就没法把权重读取摊到所有用户上。好处是用的内存少，坏处是摊不薄权重读取。

推理中的流水线气泡

Reiner 先画推理的情况。横轴时间，纵轴机柜编号，假设 4 个机柜。推理 0 以某个批大小依次走过 4 个阶段。如果等推理 0 全部跑完才开始推理 1，每个机柜四分之三时间空闲，这段空闲叫流水线气泡（pipeline bubble）。推理中自然的做法是推理 0 一离开第一个机柜，就让推理 1 进去，依次填满。所以在只有前向的推理里，气泡很容易避免。

Dwarkesh 说推理里微批和批的区别无所谓，叫什么都行，只在训练里才有意义，因为训练有最优批大小。Reiner 同意：做一次完整的反向更新之前，要把这一批的所有序列都累积完。

训练中的流水线

训练时先做若干个微批的前向，然后所有人一起切换到反向，中间有一个硬停顿。Dwarkesh 补充：之所以有硬停顿，是因为反向更新要一次处理整批，而批有最优大小。

Reiner 说，从机器学习收敛速度看，批越小越好，因为每次梯度下降都拿到最新的信息；从系统和总训练时间看，批越小越差。最优点是两者折中。选定批大小后，先做一段前向，再做一段反向。

这里的空闲就是训练中的气泡，文献里有很多办法去掉它，比如 zero bubble、one-forward-one-backward（1F1B），把前向和反向复杂地交错排布。Dwarkesh 开玩笑说可以在气泡里挖比特币。Reiner 说更有用的是在里面做权重梯度那一步，挖比特币也行。

他总结推理中的流水线：对批大小、时延这些指标是中性的，不变好也不变差。全放一个机柜时，把各段方块往下挪成一排，时延一样。它只是让每个机柜需要的内存容量变少，原来要存整个模型，现在只存四分之一。

Dwarkesh 说那推理中用流水线是理所当然的。Reiner 说其实推理中用得并不多。它减少内存容量需求，但容量本来就有大量富余：一个 Blackwell 机柜有几十 TB，一万亿参数的模型只要 1 TB 就放下了，把一个本来就小的数再减小，好处不大。理论上这说明内存可能放多了：如果权重可以分到 8 个机柜，就可以设计每块 GPU 配更少 HBM 的硬件。

04. 为什么 Ilya 说“现在我们知道，流水线并行不明智”

节目位置 1:03:27–1:18:49 · Why Ilya said, “As we now know, pipelining is not wise.”

内存墙和“内存太多”的矛盾

Dwarkesh 说现在人人都在谈内存墙：内存越来越贵，不够用，智能手机出货量会因为内存不够下降 30%。他引用 Dylan 的说法：超大云厂商今年 50% 的资本开支花在内存上。Reiner 说这可信。Dwarkesh 估算超大云厂商的资本开支在几千亿高位、可能上万亿美元，一半花在内存上，这是很大的约束，也是今年买不到新笔记本和手机的原因。那为什么又说内存太多？Jensen 为什么往机柜里塞这么多内存？

每块 GPU 的内存需求公式

Reiner 开始算内存容量。总需求 = 总参数 + KV，KV = 批大小 × 上下文长度 × 每 token 字节数。设 E 为专家并行的规模（比如 64 块 GPU），P 为流水线的规模，也就是机柜数（比如 4）。每块 GPU 的内存需求就是把总需求除以 E × P：参数在柜内各 GPU 之间均分，层在各机柜之间均分；上下文他假设也能同样均分（具体怎么做他没展开）。

流水线省了权重，省不了 KV

接下来要搞清楚 B 是多少。他回到流水线图：decode 时一个批其实在循环，生成一个 token、写入 KV cache、再前向生成下一个。所以批 0 跑完一圈又回到第一个机柜。

全局批大小 B = 微批数 × 每个微批的大小。每个微批的大小就是前面那个“300 × 稀疏度”，也就是每 20 毫秒发的那班车，由硬件参数决定（Dwarkesh 先说成 2000 左右，又自己改口）。微批数要尽量少，但又要能绕回来不留空闲，从图上可以直接看出它等于流水线阶段数，这里是 4。

Dwarkesh 问：前沿模型今天推理时真的用流水线吗？Reiner 说大规模训练里肯定用，推理里可以用，但他正要说明为什么它不太有吸引力：对权重有用，对 KV 没用。

把 B = P × b 代回公式，拆成两项：权重项仍然除以 E × P；KV 项除以 E × P，但分子里多了一个 P，P 抵消了。结论是：流水线阶段越多，每块 GPU 上权重占的内存一路下降，但 KV 占的内存保持不变。流水线做到一定程度（他说不用多，两级往往就够），权重项变得很小，KV cache 成为主导。

Dwarkesh 说他知道自己错了，但想弄明白错在哪：各层的 KV 不共享，流水线分到不同层，每个机柜只需存自己那几层的 KV，为什么不省？Reiner 说从这个角度确实省了，但同时要让所有机柜都有活干，同时在飞的序列数变多了，两者正好抵消，每块 GPU 没有节省。他回到根本：KV cache 既不能在批里分摊，也不能在流水线阶段间分摊，两个角度都吃亏。

那推理实际怎么做

Reiner 说 DeepSeek 论文报告过他们的做法：大量用专家并行。一般而言，应该把专家并行做到 scale-up 域的大小，然后几乎不用流水线，也许完全不用，也许两级，刚好让权重存储不成问题。只有这两种并行真正有意义。以前的张量并行是在一个专家内部切，但现在专家太小，不划算。

Dwarkesh 问前沿实验室推理时是不是都只在一个 scale-up 域内。Reiner 说是，但取决于模型大小：如果模型超过一个机柜的内存，比如极其稀疏，就应该做一点流水线。

回到 AI 进展：scale-up 规模为什么重要

Dwarkesh 想确认这里的论点。Reiner 说：流水线对上下文长度没帮助，对模型大小完全有帮助。有了流水线，机柜至少不该是放下模型参数的约束。所以更大的 scale-up 域有用，原因不在内存容量（至少就模型大小而言已有解法），另一个原因是时延。

Dwarkesh 问机柜间每一跳的时延是多少。Reiner 说这很依赖硬件，他说不准，大概是几毫秒量级，但可能差一个数量级。4 级流水线是现实的数字，阶段少时时延影响不大。Dwarkesh 算了一下大概每 token 多 10 毫秒，从 20 毫秒变成 30 毫秒左右，他觉得 10 毫秒不少。Reiner 描述了路径：GPU 或 TPU 到网卡，到柜顶交换机（top-of-rack switch），跳到另一个机柜再反过来走一遍，也可能上到数据中心交换机再下来，取决于部署方式。Dwarkesh 补充：因为 decode 是串行的，各阶段的时延会叠加，不能同时进行。Reiner 同意。

更大的因素是内存时间。取权重的时间 = 总参数 ÷ 内存带宽，这里的带宽是能并行用来读权重的所有 GPU 的带宽总和。不同流水线阶段不同时运行，不能并行用；但 scale-up 域内的所有 GPU 可以并行读。所以带宽 = scale-up 规模 × 每块 GPU 的带宽。每块 GPU 的带宽每代大概只涨 1.5 到 2 倍，scale-up 规模从 Hopper 起涨了 8 倍。

结论是：更大的 scale-up 重要，原因在内存带宽，不在整个 scale-up 的内存容量。流水线能解决容量问题，scale-up 规模解决带宽问题。带宽能支持更长上下文，模型越来越 agentic，这一点越重要；首先它能让模型以更低时延运行。如果在一台小小的 H100 机器上跑一个很稀疏的模型，时延会很高。

05. 因为 RL，模型可能比 Chinchilla 最优多训练了 100 倍

节目位置 1:18:49–1:32:52 · Because of RL, models may be 100x over-trained beyond Chinchilla-optimal

问题：过度训练了多少

Dwarkesh 先铺背景。Chinchilla 缩放定律（scaling law，描述模型效果怎样随参数量、数据量、算力增长的经验规律）告诉你，给定训练数据量，模型该多大。（Chinchilla 是 DeepMind 2022 年的一项研究，结论常被概括为每个参数大约配 20 个训练 token。）但现在要优化的是训练加推理的总算力能换来的用户效果，光看训练算力已经不够。所以有一个问题：为了让训练和推理的总算力最小，应该“过度训练”多少？过度训练的意思是：只看训练算力，更大的模型训练更短时间更高效；但你选一个更小的模型，多花算力训练它，换来给用户用时更便宜。

有了 RL（强化学习，让模型自己生成答案、按结果好坏更新）以后又多了一层：预训练的模型既要用于 RL 生成，又要用于最终用户推理。他的具体问题是：模型比 Chinchilla 最优多训练了多少，这个倍数有没有因为 RL 生成而变化？

启发式：总成本在两项相等处最小

Reiner 说这里得靠猜，因为最新的缩放定律和模型流量都没有公开。他先提一个启发式说法：总成本 = A + B（比如训练成本加推理成本），对很多曲线来说，最小值出现在两项相等的地方。1/x 加 x 是这样，e^x 加 e^-x 也是。一条下降、一条上升，最小值往往在交点。他说要证明这对这里的情况成立，得去拟合缩放定律里那些奇怪的指数，但服从幂律的东西往往有这个性质，他就先这么断言。

三项成本

  • 预训练：6 × 激活参数 × 预训练数据量，就是常说的 6ND 公式。
  • RL：激活参数相同，数据换成 RL 数据，系数在 2 到 6 之间。Dwarkesh 说一部分原因是不会在所有 rollout 上训练；Reiner 说另一个可能更大的低效来自 RL 里有大量 decode，decode 的 MFU 通常低于训练。
  • 推理：2 × 激活参数 × 推理数据量。

Dwarkesh 替观众整理：每个参数前向加反向是 6 次运算，只有前向是 2 次。RL 里所有轨迹都要生成，但不一定都训练，所以是 2 到 6。

Reiner 说三项各占三分之一是个不错的大致估计。实验室知道多做 RL 和多做预训练哪个更有效，他不知道。Dwarkesh 问为什么不是 RL 加预训练占 50%、推理占 50%。Reiner 说那也是合理答案，这是启发式，没法争哪个对，33% 和 25% 差得不多，他选全部相等。

推导过程（含当场纠错）

激活参数在等式里直接消掉。他写成：预训练数据 + α × RL 数据 = β × 推理数据。α 包括 2 到 6 除以 6 的系数，再乘一个他估计约 30% 的效率，得出约 1/10；β 也是三分之一乘 30%，约 1/10。Dwarkesh 指出如果两者都是 1/10，等于假设 RL 从不做反向。于是把一项改成 2/10。

推理 token 数就是每秒几亿 token × 模型部署两个月（之后被下一版替换）。预训练和 RL 之间，他先写预训练数据 = 2/10 RL 数据，又改成 1/10，然后发现方向弄反了：低效时付出的成本更多，所以那一项要反过来。Dwarkesh 开玩笑说“几十亿美元的算力刚刚流向了反方向”，Reiner 说用电子表格建模的话，钱往下水道流的时候你可能会注意到。他又说 30% 可能给得太宽松，最后各项大约是 1.5 和 1。

结论：推理 token 数应该和预训练 token 数差不多，也和 RL token 数差不多，在他推理不了的那些系数范围内。Dwarkesh 问 RL token 应该比预训练少吧？Reiner 说一般是这样：RL 在机器时间上更低效，要让两者花的时间相等，RL token 就该更少。他说起点是让成本相等，按这样建模成本，结果接近让数据量相等。

Dwarkesh 的说法是：照这个推理，要让 GPT 训练得最优，所有 GPT-5 用户流出的 token 总量应该等于进入预训练的 token 总量，而预训练是全人类知识的总和，所以每个模型应该在输出端生成相当于它输入端的全人类知识。Reiner 同意。

Dwarkesh 问人们会往哪边偏。Reiner 说预测能力不完美，而且有风险做出来的模型不是前沿模型、只能扔掉，这会改变成本权衡：推理那一项要乘一个概率，应该把推理 token 打个折扣。

代入真实数字：约 100 倍

  • 推理流量：Reiner 说几亿 token/秒，“也许现在是五亿，我不太确定”。五亿 token/秒 × 两个月，Dwarkesh 用电脑算出 2.6 × 1015。
  • Reiner 说这个数可能太大，因为是一个模型家族里的多个模型，缩小 5 到 10 倍，按每个具体模型约五千万 token/秒、上线两个月，得出约 200 万亿 token。
  • Dwarkesh 说有人告诉他前沿模型在 150 万亿 token 上训练（他先口误说成激活参数，随即改正）。Reiner 说这和推算出的数很接近。他也说这个来源不可靠，但可以用。
  • 激活参数：Reiner 说前沿模型可能在 1000 亿左右，也许更大一点。乘 20 得到 Chinchilla 推荐的 token 数，约 2 万亿。
  • 200 万亿（或 100 万亿）÷ 2 万亿，约 100 倍过度训练。

Dwarkesh 说，只要大致在这个范围，靠“让各项算力相等”这一个想法，再加上 OpenAI 每秒服务多少 token，就能推出 GPT-5 预训练用了多少数据，即使差 50% 也很惊人。Reiner 说正因为误差很大，所以到处都该做近似，但“令 A 等于 B 然后算出来”这件事让人很有掌控感。

06. 从 API 价格倒推长上下文的内存成本

节目位置 1:32:52–2:03:52 · Deducing long context memory costs from API pricing

Gemini 3.1 超过 200K 贵 50%

Dwarkesh 说 API 价格是公开的，也许能从中推出东西。Gemini 3.1 在超过 200K token 时比 200K 以下贵 50%，为什么是 50%？

Reiner 重新写出之前的公式，这次画“成本对上下文长度”的图。计算成本和上下文长度无关（实际有一点依赖，但很弱，忽略），是一条水平线。内存读取从权重那个较大的数起步，随上下文长度缓慢上升。取较大者，有一个拐点。定价时要保证无论上下文多长都盈利，于是用两档价格。他说拐点在 200K，大概说明价格分档和这个交叉点大致对齐，未必完全对齐。

反推每 token 的 KV 字节数

他接着算：假设内存时间和计算时间在 200K 处相等，并假设批足够大，权重的内存时间可以忽略，只看 KV。等式是 批大小 × 上下文长度 × 每 token 字节数 ÷ 内存带宽 = 批大小 × 激活参数 ÷ FLOPs，批大小抵消。代入 FLOPs 与带宽之比的倒数 1/300（他说在很多硬件平台上都比较稳定）、激活参数 1000 亿（前面猜的）、上下文 200K。中间他把上下文长度写到了分子上，自己发现后改到分母。结果是 1667 字节，约 2 KB。

他说这个数是合理的，并做了合理性检查。用很少的字节存每个 token 的注意力有两种机制：

  • 稠密注意力加大量跨层复用。Character AI 有篇博客讲过，交替使用长上下文和短上下文的层；这种做法也出现在 Gemma 模型里，全局上下文在所有层之间共享。每 token 字节数通常 = 注意力层数（这里指有独立上下文的层数）× 2 × d_head × KV 头数。Character AI 式模型里层数这一项是 1，d_head 典型值 128。KV 头数通常在 1 到 8 之间，取 8 个 KV 头、d_head 128，正好得到这个数；或者 KV 头更少、层更多。
  • 稀疏注意力：上面这些数都可以更大，再乘一个 1/稀疏度。

Dwarkesh 问 head 和 KV head 的区别。Reiner 说 KV 头存在内存里，保存之前 token 的内容；Q 头是检索用的，只临时用于当前正在关注别人的那个新 token。d_head 是向量维度。他觉得 2 KB 合理，可能稍小。

Dwarkesh 说他们居然通过 API 定价泄露这么多信息。Reiner 说定价有动力贴近成本，否则别人就会抢走你的生意。

输出比输入贵：decode 受内存带宽限制

Dwarkesh 想从输入和输出的价格差推 decode 和 prefill 的情况，他记得输出贵 50% 左右，但不确定。Reiner 说他以前看到的是贵 3 到 5 倍，两人按 5 倍算。（prefill 是一次性并行处理输入提示里的所有 token；decode 是一个一个生成输出 token。）

Reiner 先画了 prefill 在会话中的位置：先 decode 一段，用户再说一句话就 prefill 一段，读文件、工具调用返回、任何非 AI 生成的内容都是 prefill。prefill 时之前的 KV 已经算好；本次 prefill 这些 token 之间的注意力用 flash attention 做，是临时的，不进主存，可以忽略。所以内存时间根本不用调整。

中间两人对坐标和变量有一段来回（字幕里有些地方说得比较乱）。最后的做法是：横轴是“这一次计算处理的 token 数”（len-pass），等于 1 是 decode，大于 1 是 prefill；纵轴是每 token 时间，即 t ÷ len-pass。每 token 的计算时间是一条水平线；内存时间除以 len-pass，随 len-pass 增大下降。Dwarkesh 据此推出：既然 prefill 比 decode 便宜 5 倍，说明他们 decode 时受内存带宽限制很严重，在 len-pass = 1 处内存线比计算线高出约 5 倍。Reiner 确认，并说真实的图两条线仍会相交。Reiner 原本要引出的结论就是：prefill 受算力限制，decode 受内存带宽限制。

缓存命中为什么便宜 10 倍

Dwarkesh 说按各家定价，写缓存更贵，但命中缓存便宜约 10 倍。他猜是因为要把东西留在 HBM 里而不是清掉。Reiner 说一个 token 的 KV cache 有两种来源：从 token ID（很小）从头重算，或者之前算好存在某处内存里。价格比反映的就是这两种方式的成本比。缓存未命中意味着所有内存里都删掉了，只能从 token 重新算。

再往下想就是存在哪一层内存。HBM 之外还有更慢、更便宜的，比如主机上的 DDR、闪存。可以计算每层内存在什么情况下划算，这和要存多久有关。

为什么没有人做超过一百万 token 的上下文

算重建（rematerialization，删掉后再重新生成 KV）成本时，Dwarkesh 问为什么没有二次项。Reiner 说有，在计算里，他为了近似删掉了。每 token 的 FLOPs 里，权重乘法是平的，注意力部分随上下文线性增长，但斜率很低，画出来几乎是平线，要到几百万 token 才明显。

Dwarkesh 追问：那为什么没有公司做超过一百万 token 的上下文？Reiner 说长上下文有两种成本，内存带宽和计算；计算的斜率由基本原理决定，几乎总比内存带宽小得多。限制超长上下文的主要是内存带宽和内存容量。

Dwarkesh 提到 Dario 在播客上说过、别人也说过的观点：AGI 不需要持续学习，上下文内学习就够了。（持续学习指模型部署后还能不断从新经验中学习、更新自己。）他说如果信这个，就得认为要到一亿 token 的上下文，才能相当于一个和你共事了一个月的员工；也许稀疏注意力能改变这一点，但否则 ML 基础设施得有变化才能支撑。

Reiner 说稀疏注意力肯定是一条出路，有平方根，改进很大。但看历史，从 GPT-3 到 GPT-4（他不记得确切何时），上下文从约 8K 涨到 100K 到 200K，然后最近一两年一直在这附近徘徊。他认为这说明这是比较平衡的成本点，再大幅往上会贵得无法承受，原因是内存带宽成本，不是计算成本。他说自己看不到很好的解决路径，HBM 就那样，不会大幅变好。

Dwarkesh 问为什么稀疏注意力解决不了。Reiner 说它是很大的改进，也许已经算进现在的价格里了。但它不是无限的：太稀疏就只看一小部分 token，质量会下降。实证结果是上下文长度没怎么增长，他认为是因为这里的内存墙没有解法。

三种保存 KV 的方式，各自的成本

他列了一张表，按“取回成本”（一次性的）和“保存成本”（每秒的）两列：

  • 重建：取回成本是重跑一遍前向的计算时间 × GPU 每秒的钱；保存成本为零，因为已经删了。
  • 存在 HBM：保存成本是 每 token 字节数 ÷ HBM 容量 × GPU 每秒的钱，也就是按占用 HBM 的比例计价，因为 HBM 被不用的 KV 塞满，这块 GPU 就没法用了。取回成本按他的定义为零。
  • 存在 DDR：保存成本是 每 token 字节数 ÷ DDR 容量 × DDR 每秒成本；取回成本比 HBM 高，因为要拷回 HBM，是 每 token 字节数 ÷ DDR 带宽，同时也占一部分 DDR。闪存同理。

Dwarkesh 问每个 scale-up 都配 DDR 和闪存吗？Reiner 说这是部署选择，Nvidia 的部署两者都有。Dwarkesh 又问为什么 HBM 的取回成本不是字节数 ÷ 内存带宽。Reiner 说取决于怎么定义“取回”，他定义为放进 HBM、可以开始推理；已经在 HBM 里的话，从 HBM 读到 SRAM 可以和计算同时进行。他说自己表里的行排错了顺序，一般规律是：在内存层级里平衡两种成本时，一种成本上升，另一种就下降。存得时间很短的话，保存成本都乘以存放时间。

五分钟和一小时两档缓存对应哪层存储

Dwarkesh 说 API 里写缓存有五分钟和一小时两档价格，暗示五分钟是 HBM、一小时是 DDR。Reiner 说这是不错的假设，但看数字也可能低一层，是 DDR 对闪存。Dwarkesh 查了价格：基础输入 5 美元/百万 token，“基础”就是重建，也就是“取回”成本 5 美元；写入五分钟缓存是 6.25 美元。

Reiner 说可以靠时长判断是哪层内存，时长可能就是那层内存的“排空时间”：如果要存五分钟，就选一种每五分钟大致能把整个内存读一遍的存储，即 容量 ÷ 带宽 ≈ 五分钟。

  • HBM：前面算过，约 20 毫秒，太小。
  • DDR：可能差一到两个数量级，大约秒级，1 到 10 秒。
  • 闪存：大约一分钟量级。
  • 机械硬盘（spinning disk）：差别很大，大约一小时量级。

他说这些数没有背下来，只是大致量级。照这样看，两档可能对应闪存和机械硬盘。

Dwarkesh 问为什么是这么算。Reiner 说选哪层存储是为了让成本最小：你用设备的一部分来保存，一部分来取回；两部分比例相等，说明选对了。要让两种成本相等，取回时间应该等于 保存时间 × 占用容量的比例。Dwarkesh 换了个说法：存放的时长应该等于把所有东西放进去再取出来的时间。Reiner 说大致如此。

Reiner 说这很可能说明两档是闪存和机械硬盘。Dwarkesh 对机械硬盘还在用感到吃惊，说它慢到要一小时才能把整个容量读一遍。Reiner 说这是很不吸引人的技术，但在某些地方有用。

07. 神经网络和密码学的趋同演化

节目位置 2:03:52–2:13:40 · Convergent evolution between neural nets and cryptography

同样的机制，相反的目标

两人坐下来聊不需要黑板的问题。Dwarkesh 提到 Reiner 的一篇博客：密码学协议的架构在高层上很像神经网络。两者都要把信息在所有输入之间搅匀：密码学是为了让每个新输入都彻底打乱哈希函数的结果；神经网络是为了考虑这一条信息怎样改变对另一条信息的理解。但他觉得两者目标相反：密码学把有结构的信息变得和随机无法区分；神经网络从看起来随机的东西（蛋白质序列、DNA、乱码文本）里提取高层结构。

Reiner 说他也找过其他出现“混合和打乱”的例子。物理上有一个：做蛋糕搅面糊，先这样搅再那样搅，不算坏办法。回到数字世界，Dwarkesh 指出的区别很实在。如果随机初始化一个神经网络，它可能也是个还行的密码，因为随机初始化会把东西复杂地搅乱。

可微性：梯度下降和差分密码分析

他说让神经网络可以理解的是梯度下降：神经网络可以求导，得到有意义的导数。人们花很多功夫不让导数变复杂，残差连接让它保持简单可控，LayerNorm 也是。

对密码最强的攻击之一也是对密码求导。密码在另一个数域上运算，是只有两个元素的域，也就是二进制；神经网络理论上在实数域上运算。对二进制求导是可以做的，这叫差分密码分析（differential cryptanalysis）：输入有一个小差异时，很难让输出的差异也小，设计良好的密码就是要让输出差异很大。区别在于密码的优化目标是变复杂，没有残差连接、LayerNorm 那样的东西。

两者交汇的地方：后门和对抗攻击

Dwarkesh 说两者交汇的一个地方是后门：在 LLM 里藏后门，藏进去的东西属于反向传播的输入，前向计算里看不到。Reiner 说对抗场景里会出现密码那种“雪崩效应”（avalanche property，输入微小变化导致输出大变）的地方。图像分类的对抗攻击就是找一个很小的扰动，彻底改变分类结果。在密码里这是常态，在神经网络里是不想要的情况。

神经网络能当密码用吗

Dwarkesh 问用神经网络做密码这个方向有没有成功。Reiner 说创造任何新密码，如果没经过 10 年审视，大概率已经被破解；99% 的新密码都被破解了，所以这是个危险的起点。（这段两人先坐着说了一遍，又站回黑板前重讲了一遍。）

反过来：Feistel 网络和 RevNets

反方向至少有一个明确成功的例子：Feistel 密码（Feistel network），从密码学引入了神经网络。思路是：有一个本身不可逆的函数 f，但你喜欢它，因为它做有用的事，比如一个 MLP，或者能有趣地搅乱数据，你想用它造一个可逆的东西。

做法是用两个输入 x 和 y：输出是 (x, y + f(x))。要还原的话，x 直接读出来；y = z − f(x)，因为 x 已经知道了。所以这个结构可逆。他说这在密码里用得很多，现在还在用，是构造密码的主要机制之一；密码的各层通常希望可逆，这样密码学性质更好。

神经网络里对应的是 RevNets（可逆网络）论文（坐着时他说是 2018 或 2019 年，站在黑板前说是 2017 年）。它让整个网络可逆，可以套在任何网络上，比如 Transformer：x 过函数 f（一个 Transformer 层），加到 y 上，成为新的 x；原来的 x 成为新的 y。他说这相当于前面 Dwarkesh 提到的从两层之前接过来的残差连接。

为什么要可逆？主要用在训练。普通训练的前向要把所有激活值写进 HBM，占用随层数线性增长，这可能是训练中最大的内存占用；反向时再倒着读出来。RevNets 因为可逆，不需要存这些：反向传播时一边算反向，一边同步把前向一步步撤销回去，重建出需要的激活值，省内存。

Dwarkesh 说这是多花计算省内存，和 KV cache 正好相反，KV cache 是多花内存省计算。Reiner 说按现在硬件的情况，多花内存省计算通常是划算的。

结尾 Dwarkesh 说这一期证明了新演播室和黑板形式的设想。
