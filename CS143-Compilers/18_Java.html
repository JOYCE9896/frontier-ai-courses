一、Java 的来历

最后几段录像用课上学的东西分析 Java 的若干特性，一来看看一门真实语言是怎样设计的，二来讲一些 Cool 里没有、课程项目里因为太费时间或太复杂而没加进去的重要语言结构。从这门课的角度看，Java 是"打了激素的 Cool"，是 Cool 加上很多很多特性。核心上两者很像：都是有类型的、面向对象的、有垃圾回收的语言，都设计于 1990 年代初，共享当时流行的那些想法。

Java 起源于 Sun 的一个叫 Oak 的项目，最初面向机顶盒：放在电视机上面的小盒子，连到某种网络，控制有线电视节目，让电视更有交互性，那时电视本身还不是一台计算机。Oak 大约从 1991 年做到 1994 年，但据 Aiken 所知，机顶盒市场一直没起来，消费者不买账，Oak 的前景很有限。然后互联网来了。1993、1994 年前后，显然需要专门针对互联网问题的编程语言，人们尤其担心安全：不想下载一堆 C 写的二进制程序到处传，因为不能保证它们会按预期工作而不搞垮你的机器。要从不完全信任的人那里分享代码，就需要比 C、C++ 安全的语言，这给了新语言机会。候选的不只 Java，Tcl 和 Python 也是认真的竞争者，最终 Sun 的支持帮 Java 在互联网上站稳了。

Aiken 说这个故事的要点是：每门新语言都需要一个杀手级应用，每门编程语言都是骑在某个应用的背上进入世界的，必须有一种人们想写、现有语言又服务得不好的新应用，才值得人们学一门新语言。Java 很安全，有垃圾回收和类型系统，正适合当时新兴的互联网编程需求，Aiken 认为这是它流行的主要原因。这就是第二讲"编程语言的经济学"里讲的道理。

新语言大量借鉴前辈很正常，往往主要是把以前的想法重新组合成新设计，再加一点创新。据 Aiken 所知，Java 的影响来源：

  • 对类型的坚持大概可以追溯到 Modula-3，那里人们试图造一门能真实地扩展到大型系统、又是强类型的语言。
  • 面向对象来自 Objective-C、C++，还有 Eiffel，Eiffel 也有接口的概念，接口是 Java 的一个显著特性。
  • Java 相当动态，很多事不在静态时做而在运行时做，比如反射，这和 Lisp 有共同的文化，Lisp 是函数式家族的语言，但也很动态。

要意识到 Java 是一门大语言，不简单，语言手册有好几百页。它有很多特性，更重要的是有很多特性之间的交互，设计语言最难的就是把所有交互、所有组合都弄对，确保它们之间没有出人意料的相互作用。

二、数组

设 B 是 A 的子类： 

B[] b = new B[10];
A[] a = b;
a[0] = new A();
b[0].methodNotDeclaredInA();

分配一个装 B 的数组，b 指向它；a 的类型是 A 的数组，也指向同一个数组。往 a[0] 里放一个新的 A 对象，看起来没问题，a 是装 A 的数组嘛。然后访问 b[0]，因为 a 和 b 指着同一个数组，它就是 a[0]，调用一个只在 B 里声明、A 里没有的方法。B 是 A 的子类型，有 A 的所有方法，还可能更多；b 是装 B 的数组，按理说可以调用 B 的所有方法。可这里会出运行时错误，因为数组第一个位置上实际是一个 A 对象。

看 Java 的子类型规则：B 继承 A 则 B ≤ A，和 Cool 以及大多数面向对象语言一样；子类型可传递，也很标准。但还有一条不标准的规则：如果 B ≤ A，那么 B[] ≤ A[]，元素类型有子类型关系，数组类型就有子类型关系。Cool 没有数组，没机会有这种规则；别的有对象和子类型的语言也不这样做。

换个角度说。问题的本质不在于是数组，而在于有一块可更新的内存（哪怕只是一个单元），有两个指针 a、b 指向它，都能读写。两个程序名字指向同一块内存，叫别名（aliasing）。别名在真实程序里很常见，本身不坏。问题在于 a 和 b 的类型不同。一般地：对可更新位置的多个别名，如果它们的类型不同，类型系统就不可靠。这里能通过 A 类型的指针往那个位置写一个 A 对象，再通过 B 类型的指针把它当 B 读出来，可它没有 B 的全部方法和字段，对它做 B 的操作就可能未定义。交换 A 和 B 的子类型关系也没用，别名是对称的，只要换成从 b 写、从 a 读，问题一模一样。

这个问题在很多语言里都出现过，不只 Java，它是类型系统里相当微妙的一点，很多语言想让子类型穿过数组起作用，结果给静态类型系统制造了麻烦。编程语言研究界最广泛接受的解决办法是给数组一条不同的子类型规则：只有当 B = A 时才有 B[] ≤ A[]。这样两个引用的类型存在子类型关系时，元素类型一定相同，就不可能对一个可更新位置造出类型不同的两个引用，类型系统就是可靠的。

Java 的补救方式不同：不在静态时检查数组访问，而在运行时检查。new B[10] 时，数组里记住"这是装 B 的数组"，以后每次往数组里赋值，都检查赋进去的东西是不是 B 或 B 的子类型。这显然给数组计算增加了开销，每次往数组赋值都有一次运行时类型检查。好在最常见的数组是基本类型的数组，特别是 int 和浮点数的数组，它们不受影响：基本类型不是类，没有子类型，不可能造出这种问题。但对象数组的每次赋值都有额外的运行时开销。

三、异常

典型场景：你深入一段相当复杂的代码，到了一个可能出现意外错误的地方，比如可能内存不够，或者某个数据结构不满足不变量（一个本该有序的列表没有序）。怎样优雅地处理，又不把程序弄得很难看？很多语言（包括 Java）的流行做法是：给语言增加一种新的值，叫异常，再加两个处理它的控制结构：

  • throw e：在此处造出一个异常。它会从程序里往外传播，停下当前的执行，外层的结构也一层层抛出它，直到遇到 try-catch。
  • try { e1 } catch (Exception x) { e2 }：执行 e1；如果 e1 内部某处抛出异常，就捕获它，像 let 一样把异常值绑定到名字 x，然后执行清理代码 e2。

这样设计的想法是：检测到异常的地方可能深埋在代码里，不是处理它的好地方。应该先离开那部分代码，回到某个更高层的地方，清理、处理异常，也许再重试一个更大的代码块。 

class Foo {
    public static void main(String[] args) {
        try { X(); } catch (Exception e) {
            System.out.println("Error!");
        }
    }

    public void X() throws MyException {
        throw new MyException();
    }
}

main 调 X，X 分配一个异常对象（它只是一个值，和别的类一样，特殊之处在于可以被抛出）并抛出，X 异常终止，回到 main 的 catch 块，打印一条错误信息。这里没做什么聪明的事，但至少捕获了异常，打印了错误，而不是直接终止。

操作语义

非形式的描述不太清楚，好在学过操作语义，可以简洁地说清 try-catch 怎样工作。要区分异常对象的两种状态：new 一个异常类的对象时，它只是普通的值 v，行为和别的对象一样；被抛出后，它成了一种特殊的值，记作 T(v)，是一个活跃的异常。

  • 如果 e1 求值得到普通值 v（没有抛异常），try-catch 的结果就是 v。
  • 如果 e1 求值得到被抛出的异常 T(v)，就把里面的值 v 拆出来，绑定到 catch 里命名的局部名字上，在这个绑定下求清理代码 e2，e2 的结果就是整个 try-catch 的结果。
  • throw e：求 e 得到值 v，然后把它标记为被抛出的异常，结果是 T(v)。
  • 其他所有结构都让被抛出的异常直接传播出去。以 e1 + e2 为例：先求 e1，如果得到 T(v)，加法立刻停下，连 e2 都不求（规则横线上方根本没出现 e2），整个加法的结果就是那个异常。其他结构同理，只要有一个子表达式得到异常，就停止求值，把异常往上传。只有被某个 try-catch 捕获，异常才不会一路传到整个程序的结果。

实现

实现方法很多，一种简单的：遇到 try 时，在栈上做个标记，记下遇到 try 的位置，然后继续执行 try 里面的东西，栈可能继续增长。抛出异常时，展开栈：把一切弹掉，一直弹回最近的 try 标记，再执行对应的 catch（通过标记找到对应的 catch 块代码，从那里开始求值）。这种设计的缺点是 try 本身有代价：就算不抛异常，执行 try-catch 也要付出点什么，至少要在栈上做标记，离开 try 块时记得去掉标记。更复杂的技术会降低 try 和 throw 的代价，并在两者之间取舍。异常在大多数程序里大概比较少见，所以通常希望 try 尽量便宜，即使代价是 throw 稍贵一点。

一个冷知识：终结方法里的异常

对象被垃圾回收时，可以先在它身上运行一个方法做清理，再真正释放，这叫终结方法（finalization），由垃圾回收器调用。为什么需要？比如一个对象持有一个打开的文件句柄，它变得不可达、被回收时，如果不关掉文件，大量无人使用的打开文件就会挂在那里，操作系统给的文件句柄数通常是固定的，可能用完。正确的做法是回收时先关文件，再释放对象。问题是：如果终结方法抛出异常，谁来捕获？它是垃圾回收器调用的，什么时候调用不可预测，也说不清该在哪里处理。答案是没人处理：终结方法里没在方法内部处理掉的异常，直接被丢掉。

受检异常

Java 的一个不错的创新是：异常是方法接口的一部分，由编译器检查。上面例子里 X 的声明写了 throws MyException，这是 X 受检接口的一部分。为什么要在编译时检查？最初的 Java 项目观察到，Java 程序可能抛出很多异常，人们很容易搞不清可能抛出哪些、必须处理哪些。加了这个特性、让编译器强制每个方法声明它可能抛出的每个异常之后，他们在 Java 编译器自身里发现了很多抛出了却没有被正确处理的异常，Java 编译器的错误处理因此变好了。Aiken 认为人们普遍同意这是个好主意，程序员能清楚看到要处理哪些异常，有助于写出更健壮的代码。

也有例外：有些运行时错误很难静态地证明一个方法永远不会引发，比如解引用 null、整数溢出，就不必声明在接口里。还有一些平常的类型规则，比如 throw 只能作用于异常类型的对象。总的来说 Java 的异常做得相当好，声明方法可能抛出的异常类型是 Java 的新想法。

四、接口

接口在不使用继承的情况下规定类之间的关系： 

interface PointInterface {
    void move(int dx, int dy);
}

class Point implements PointInterface {
    void move(int dx, int dy) { x += dx; y += dy; }
}

接口里主要是方法签名（也可以有别的东西）。任何实现 PointInterface 的类都必须提供签名相同的 move 方法；接口有别的方法，类也必须一一实现。

Java 语言手册说，Java 程序可以用接口使相关的类不必共享一个公共的抽象超类，或不必往 Object 里加方法。翻译过来就是：接口起的作用和 C++ 的多重继承相同。一个类可以实现多个接口，如果类 X 实现了接口 A、B、C，X 对象就能在相应的上下文里被当作 A、B 或 C 对象，几乎就像 X 有三个超类。两者有一些重要区别，但效果如此。

例子：斯坦福或别的大学的研究生。研究生是学生，上课、拿学位、有成绩；也常常为大学工作，当助教或研究助理，是大学雇员。如果在大学人事管理软件里花大力气实现了处理学生的功能和处理雇员的功能，写研究生时自然想利用它们。有了雇员接口和学生接口，研究生类可以两个都实现。只有单继承就很难：让研究生继承雇员类，学生的功能从哪来？继承学生类，雇员的功能从哪来？单继承逼你只选一个类，接口让你表达和多种东西的功能关系。

为什么接口不如继承高效

既然如此，为什么两样都要有？因为接口没法实现得像继承一样高效，能用继承时宁可用继承。主要原因是：实现接口的类里，接口的方法不一定在固定偏移处，一般来说无法把接口里的方法分配到类的实现或对象实现里的固定偏移。

比如 Point 实现了 PointInterface 和 move；另一个类 Point2 也实现了它，但还实现了别的不属于接口的方法。按 coolc 那样把方法按声明顺序排，move 不会在两个类的同一个位置。可以想象加一遍编译，把方法排序，让 PointInterface 的方法在所有实现它的类里都出现在同样的位置、同样的顺序。可一旦一个类实现多个接口，这就不行了：如果 Point2 还实现了接口 A，已经决定 PointInterface 的 move 要放第一个，A 接口也做了类似的决定，要求它的某个方法总是放第一个，就冲突了。一般来说，不事先知道所有声明的类和接口，就没法给所有接口的所有方法排一个能在所有实现类中保持的全序；而强迫人们一次声明完所有类和接口、以后不能扩展，很不像 Java。结论是：接口里的方法在类里不在固定偏移。

所以当 e 的类型是某个接口、调用它的方法 f 时，分派要多做些工作。一种方法（相当低效，但能看出它行得通，还有更高效的方法）：每个实现了接口的类都有一张查找表，把方法名（字符串）映射到方法本身；可以对方法名做哈希以加快查找，而且哈希在编译时就能算好。比如分派表的末尾放一个指针，指向这张"名字到代码"的表，每个类的每个对象都能通过它找到实现接口方法的实际代码。

五、强制转换

很多语言的类型系统都有强制转换（coercion）这个特性。Java 允许在某些上下文里把基本类型从一种类型转成另一种。比如 1 + 2.0：1 是整数，2.0 是浮点数，整数和浮点数没法直接相加，要么把整数转成浮点再做浮点加法，要么把浮点转成整数再做整数加法，总之得先转成共同的表示，通常的做法（也是 Java 的做法）是把整数转成浮点数 1.0。

最好把强制转换理解为编译器替你插入的基本函数：好像你漏写了一个函数调用，编译器发现后补上。这里就是一个把整数按显而易见的方式转成浮点数的基本函数，表达式实际上变成 int_to_float(1) + 2.0。所以强制转换是给程序员的方便，让你在类型转换显而易见的地方省掉一些函数调用。大多数语言，各种风格的语言，都有大量的强制转换，数值类型之间尤其常见。

Java 区分两种强制转换和类型转换（cast）：

  • 加宽：总是成功，编译器和运行时系统都不会抱怨。int 到 float 就是加宽。
  • 收窄：如果数据转不成想要的类型就可能失败。float 到 int，2.0 能显然地转成 2，但 2.5 没有整数表示，该截断还是进位？对这种没有清楚映射的收窄，Java 会抱怨，不让你隐式地做。更好的例子是向下转换：B 是 A 的子类型，x 的类型是 A，写 (B) x，编译器会放行（因为 B 是 A 的子类型），但运行时会检查 x 是否真的是 B 对象，不是就抛异常。

Java 的规则是：收窄必须显式写出，你得自己写上类型转换，表明你确实要这样做；加宽和强制转换可以隐式进行，往超类型提升，或者在一种类型明显嵌入另一种的整数类型之间转换，编译器可以替你补上。

Java 冷知识：Java 里有一种类型完全没有定义到任何其他类型的强制转换或类型转换，隐式和显式的都没有。答案是 boolean。

反面例子：PL/I

Aiken 说他本人不太喜欢强制转换。它显然方便程序员，隐式转换无处不在，被广泛认为是编程语言必需的东西，但他认为它往往让程序的行为和程序员预期的不同。PL/I 有很广泛的类型转换和强制转换，会导致令人吃惊的行为： 

DECLARE (A, B, C) CHAR(3);
B = '123';
C = '456';
A = B + C;

A、B、C 是长度为 3 的字符串，长度是类型的一部分。A 是多少？加号被解释为整数加法，B 和 C 先转成整数 123 和 456，相加得 579。但 A 是三个字符的字符串，所以结果还要转回字符串，分两步：先转成默认长度的字符串，默认长度恰好是 6，于是是三个空格加上 579；再把这个六字符的串转成三字符的串，取前三个字符。结果 A 里存的是三个空格，这大概不是任何人期望的。

六、线程

Java 通过线程内置了并发。线程像一个独立的程序，有自己的程序计数器（正在执行的指令）和自己的局部变量、活动记录；一个程序可以同时有多个线程，它们可以引用堆里共同的数据。概念上（实际实现通常不完全如此）有一个调度器，每一步挑一个线程执行它的一条语句，然后重复。哪一步执行哪个线程、执行它多少条指令是不确定的，于是各线程的指令可以以相当任意的顺序交错。

Java 的线程对象都属于 Thread 类，要成为线程必须继承它，得到开始和结束线程的 start、stop 方法等。线程可以通过 synchronized 结构在对象上同步：synchronized (x) { e } 表示执行 e 之前获得 x 上的锁，过程是锁 x、求 e、解锁 x。这是一种结构化的同步结构，也是 Java 里在线程之间同步几乎唯一的方法：一个线程执行这段代码、持有 x 的锁时，别的线程不能同时执行这段代码并持有同一个对象的锁。两个线程可以执行同一段语法结构，只要它们的 x 指向不同对象，但如果锁的是同一个 x，就保证不会交错。更常用的简写是把 synchronized 加在方法上：synchronized void f() {...}，调用这个方法时锁住 this 对象。

例子

class Simple {
    int a = 1, b = 2;
    void to() { a = 3; b = 4; }
    void fro() { System.out.println("a=" + a + ", b=" + b); }
}

线程一调用 to，线程二调用 fro。如果 to 全部跑完 fro 才开始，打印 a=3, b=4；如果 fro 先全部跑完，打印 a=1, b=2，之后 to 再把 a、b 设成 3、4。这两种都没问题。但可能有奇怪的交错：to 执行了 a = 3，fro 执行打印的前半部分读到 a 是 3，接着 fro 继续读 b，读到 2，然后 to 才执行 b = 4。打印出 a=3, b=2，看到了线程一只执行了一部分的中间状态，一个变量更新了另一个没有。

想用同步防止这个，先看一个错误的尝试，它根本没解决问题，但它展示了 Java 程序员最常犯的线程错误，很多人包括职业程序员都犯，很多生产 Java 程序里都有这个错误：只给 to 加 synchronized。设整个堆里只有一个 Simple 对象 S。线程一先走，因为是同步方法，先锁住 this，只能是 S；执行 a = 3；这时被打断，线程二运行。线程二不检查锁，fro 没有 synchronized，有人持有 S 的锁并不阻止另一个不检查锁的方法访问这个对象的字段，于是它一路跑完，打印 a=3, b=2。然后线程一跑完，最后解锁。这个修补毫无作用，没有同步时的所有交错都还在。

这个错误常见，是因为人们常想：读没关系，并行读不会出问题，因为不改数据，要同步的是写。要点是：只同步对共享数据的两种访问中的一半是没用的，同步只有在所有人都检查锁时才有效，读者和写者都要检查锁，才能限制两个方法的交错。正确的做法是两个方法都加 synchronized，这样只可能打印 a=1, b=2（fro 整个在 to 之前）或 a=3, b=4（to 整个在 fro 之前）。

凭空出现的值

希望有这样的性质：即使没有同步，一个变量也只会持有某个线程实际写过的值。线程一 a = 3.14，线程二 a = 2.78，两个赋值以某种顺序执行完，a 应该是 3.14 或 2.78。不希望 a 变成比如 3.78，这个值哪个线程都没写过，是被"制造"出来的：如果两个线程写的数的各部分以奇怪的方式拼在一起，就会得到这样的值。

Java 保证基本类型的写入是原子的，给一个基本类型赋值不会被对同一内存位置的另一个赋值干扰，唯独浮点 double 例外。double 占两个字，大多数机器没有一次写两个字的基本指令，写一个 double 要两条机器指令，先写高半部分，再写低半部分。两个线程的这两对写入可能交错，结果高半部分是线程一写的、低半部分是线程二写的，造出一个两者都没写过的、"凭空出现"（out of thin air）的值。凭空出现的值显然是坏事，但出于性能原因，手册说这是"对当前硬件的让步"，不要求 double 的写入是原子的，除非程序员把类型声明为 volatile。所以写并发读写 double 的 Java 线程程序时，要把这些 double 声明为 volatile（Aiken 说这在将来可能会改，他相信设计者也想改）。

更一般地，Java 的并发语义细节相当难懂，凭空值只是其中一个方面。这不能怪 Java：并发语义本身就难，这还是研究前沿，我们并不完全清楚在并发环境下语言的行为应该怎样规定才对。不是说什么都不懂，有些语言的并发语义完全没问题，但在 Java 这样特性丰富的语言里，有些东西在某些机器上该怎样实现并不完全清楚。为此专门针对 Java 做了大量工作。Java 是第一个有一等线程、并试图把线程和所有其他现代语言特性整合起来的主流语言，遇到些麻烦并不意外。Aiken 认为这是 Java 仍有争议的领域：用线程做比较直接的事，一切都没问题；但有些语言部分和线程一起用，可能会惹上麻烦。写重要的并发 Java 程序，值得花功夫理解 Java 的并发和线程。

七、类加载和初始化

与 Java 的动态性一致，Java 允许在运行时加载类，可以在程序运行时加载新类来增加功能。这带来类型安全和安全性的隐患，因为编译时和加载时有了区别：源代码的类型检查在编译时进行（就是前面讲的那种）；但加载类时加载的是字节码，不是源代码，不会再做类型检查，而这些字节码可能来源不可信，可能不是一个做过类型检查的编译器的输出，未必满足 Java 实现的类型假设。所以必须再检查一遍字节码：加载类时进行字节码验证，说到底就是对字节码做类型检查，只是代码低层得多，算法看起来有些不同。

加载策略由类加载器（一个特殊的 Java 类）处理，它决定哪些类可以加载。Java 早期发现过一批安全问题：攻击者能控制类加载器，装上自己的、比标准类加载器宽松得多的加载器，从而破坏系统。这些问题很早以前就修好了。类还可以卸载，Aiken 上次查看时，语言定义对此规定得不太清楚，卸载一个类时这个类的现有对象会怎样，并不明确。

类初始化

Java 的初始化相当复杂，这不奇怪：Cool 的初始化就已经挺复杂了，而 Java 是 Cool 的超集，有 Cool 的所有初始化问题，还多得多。主要的复杂来源是并发，但别的语言特性也增加了复杂性。Aiken 说，想理解一门新的面向对象语言，研究它的对象初始化和类初始化是个不错的办法，因为初始化时语言的所有特性都会相互作用，要有一个定义良好的初始化过程，就得说清这些交互是怎样理顺的。这里只讲类初始化，即类第一次被引入程序时，代表这个类的对象怎样被初始化。

类在其中某个符号第一次被使用时初始化，而不是在类加载时。这样做是为了让类初始化里的错误发生在可预测的地方：程序跑五次，错误大概每次都在同一个地方，可重复、可预测。如果在加载时初始化，类可能在很多不同的时刻被加载，初始化错误就变得不确定。

Java 有而 Cool 没有的一个概念是类对象：它不是类的实例，它代表这个类本身，包含关于这个类的所有信息，类型、字段等等。它用于内省或反射，因为有动态加载这样的特性：动态加载了一个类之后要使用它，就得能查询它有哪些方法之类，这就是类对象的用途。每个类有一个类对象。初始化类对象的大致过程（Aiken 说略去了一些东西，有所简化）：

  1. 锁住这个类的类对象。如果已被别的线程锁住，就等在锁上，直到有人通知可以继续。
  2. 拿到锁后，如果发现就是本线程在初始化这个类，就释放锁并返回。这可能发生，因为类可以有同类型的字段，比如类 X 有一个 X 类型的字段，初始化类时要递归地确保所有字段的类都已初始化，于是会递归地尝试初始化同一个类。
  3. 如果类已经初始化好了（别的线程抢先完成了），什么都不用做，正常返回。
  4. 否则，标记"本线程正在初始化这个类"，然后解锁。
  5. 初始化超类，然后按文本顺序初始化各字段，但 static final 字段最先初始化。当然，和 Cool 一样，初始化前先给每个字段默认值。这一步和 Cool 里发生的很像。
  6. 如果初始化过程中出错，抛出了异常，就把类标记为错误的，表示这个类不能用了，只能放弃它，这是能做的最好的处理。
  7. 如果没有错误，再锁住类，标记为已初始化，通知所有等在这个类对象上的线程，然后解锁。

这个过程展示了语言的各种特性怎样必须相互作用：并发、异常、static 和 final 字段、继承，都要在一个类初始化算法的设计里一起处理。

特性交互

退一步看，Java 类初始化的讨论说明了设计复杂系统的一个普遍道理。任何系统都有一定数量的特性，记为 n，因为要提供功能。但特性一多，特性之间的潜在交互也多：只算两两交互，就有大约 n² 个，数量随特性数超线性增长；加一个新特性，要考虑它和所有已有特性的关系，所以给功能很多的系统扩展或构建都很难。如果还要考虑特性的各种子集怎样相互作用，潜在交互的数量就是指数增长的。结论是：特性多的大系统很难理解。这是计算机科学乃至任何设计复杂系统的学科的普遍教训，适用于编程语言，也适用于你想构建的任何软件系统。但它在编程语言里格外有分量，因为语言特性之间的交互发生在很细的粒度上，而且可以任意组合，语言设计必须把所有交互都弄清楚，程序员才能理解、才能高效地用这门语言。Aiken 说这是整门课讲过的重要思想之一，希望大家带走。

八、总结

  • 按产品级标准，Java 是一门做得很好的语言，极其出色，是今天在用的设计和规范得最好的语言之一。
  • 它把几个重要想法带进了主流。这些想法存在已久，但还没进入一门被广泛使用的产品级语言：Java 是第一个在商业环境中被很广泛使用、有真正提供保证的强静态类型、同时又是有垃圾回收的托管语言。
  • 但它并不完美。它包含一些设计时人们还没有完全理解的特性，那是 Java 设计里仍然有些粗糙的地方，比如并发下的内存语义，大多数人大概会同意它还有一些问题和灰色地带，程序员最好避开。
  • Java 特性太多，特性多交互就更多，带来难以管理的复杂性。
