第十七讲：自动内存管理

手工管理内存的 bug 为什么难找，类型安全为什么离不开自动内存管理；可达性和根，可达性只是对"不再使用"的近似，coolc 从累加器和栈开始追踪；三种技术：标记清除（标记位、工作表、指针反转、空闲链表和碎片），停止复制（新旧两个空间、转发指针、scan 和 alloc 指针、为什么最快），引用计数（每次赋值的代价、收不了环）；保守回收；垃圾回收的利弊和更先进的回收器

主讲：Fredrik Kjolstad（2026 年春季）；录像主讲：Alex Aiken
资料来源：课件（2026 年 5 月 28 日）、录像第 17 周（17-01 Automatic Memory Management 到 17-05 Reference Counting，按小节转载的播放列表）

一、为什么要自动内存管理

在现代编程里，存储管理仍然是个难题。手工管理内存，也就是所有分配和释放都自己显式去做，是一种很难的编程方式，会带来一些极难消除的 bug。今天主要见于 C 和 C++ 程序，它们是主流语言里仍然手工管理内存的。常见的存储 bug：

  • 忘了释放不再用的内存，即内存泄漏；
  • 解引用悬空指针；
  • 不小心覆盖了数据结构的一部分；
  • 还有别的。

这些 bug 极难发现，常常是复杂系统里最后才被找到的那批，经常带进生产环境，有时在投入使用后很久还在。原因是它们的效果在时间和程序文本上都离源头很远。比如一个对象有几个字段，程序里某处有指向它的指针；手工释放了它，却忘了那个指针还在；之后再分配别的东西，可能恰好分到这块内存，可能是完全不同类型的对象。那个指针以为自己指着原来那种对象，往里写的东西就是一堆无意义的位；程序另一处、可能很远的地方再按新对象去读，读到的就是乱七八糟的东西，多半导致崩溃。

类型能不能防止手工分配和释放内存的程序出错？有一些花哨的类型系统（线性类型）就是为此设计的，但会让编程复杂很多。目前，如果想要类型安全，就必须用自动内存管理。

这是一个很老的问题，自 1950 年代起就为 LISP 研究过，有成熟的完全自动的内存管理技术。它直到 1990 年代随着 Java 流行才成为主流，在那之前，主流语言里没有一门用自动内存管理。

二、基本思路和可达性

创建对象时，运行时系统自动给它分配未用的空间，在 Cool 里就是 new X。这样一直分配下去，过一阵就没有未用空间了，这时必须回收一些空间才能继续分配。垃圾回收依赖的观察是：有些空间被将来永远不会再用的对象占着，找出它们就能释放空间、留给以后用。

怎样知道一个对象"永远不会再用"？一般来说这无法判断，只能用启发式。今天大多数垃圾回收技术依赖的观察是：程序只能使用它能找到的对象。 

let x : A <- new A in { x <- y; ... }

新分配的 A 对象只有一个指针 x 指向它，紧接着 x 被赋成 y 指的对象，唯一指向 A 的指针丢了，程序里没有任何变量或数据结构指向它，以后再也不可能访问到它，它的空间可以回收。

更一般的定义：对象 x 是可达的，当且仅当

  • 某个寄存器里有指向 x 的指针，或者
  • 另一个可达对象 y 里有指向 x 的指针。

寄存器里放着局部变量、中间表达式这些程序能直接访问的值。从寄存器出发，沿所有指针走，能到达的就是全部可达对象（有些对象可能有多条路径到达）。实现只能通过寄存器访问东西，再从能到达的对象里取出指针找到更多东西，所以不可达的对象永远不会被使用，它们就是垃圾。

可达性只是近似

Aiken 的例子：x 指向一个新的 A，y 指向一个新的 B，然后 x ← y，第一个 A 不可达了。接着一个条件总是为真、只会走 true 分支，而 true 分支立刻覆盖 x。假设在进入条件之前做垃圾回收：B 是可达的（通过 x，也通过 y），不会被回收。可是编译器不知道这个分支总为真，不知道 x 此刻的值以后不会再用；如果 y 在这里也已经死了，那 B 实际上永远不会再被用到，尽管它可达。

课件的例子更简单： 

main() {
    x <- new A;
    foo()
}

调用 foo 时 A 对象已经死了，再也不会被用，但直到程序结束它都不会被回收。

所以可达性是一种近似：我们真正想回收的是将来执行中永远不会再用的对象。不可达的对象一定不会再用；可达的对象却不保证会再用。

coolc 里追踪可达对象

coolc 里的寄存器只有累加器和栈指针。累加器指向一个对象，这个对象可能指向别的对象，依此类推。栈指针更复杂：每个栈帧里有指针（比如方法参数），也有非指针（比如返回地址）。只要知道帧的布局，就能找到其中的指针。编译器决定了布局，自然知道：它要为每种方法的活动记录记下哪些槽是对象指针，比如方法 foo 的活动记录有四个槽，第二和第四个总是对象指针，其余两个不是，运行时垃圾回收器看到 foo 的活动记录，就知道要跟着哪些指针走。

在 coolc 里从累加器和栈开始追踪，它们叫根（roots），垃圾回收的术语里，根是开始追踪可达对象的那些寄存器。课件的例子：累加器指向 A，A 指向 C，C 指向 E；栈上第一个帧没有指针，第二个帧指向 E（已经标过了，再标一次也无妨）。没被碰到的 B 和 D 不可达，它们的空间可以重用。注意 D 其实有指针指向它，但仍不可达，因为指向它的只有别的不可达对象。不是每个不可达对象都没有指针指向，有些不可达对象有指针指向，但只来自其他不可达对象。

垃圾回收的步骤

  1. 需要时为新对象分配空间，只要有空间就一直分配。
  2. 空间用完时：(a) 算出哪些对象可能还会再用，一般是追踪从一组"根"寄存器可达的对象；(b) 释放 (a) 中没找到的那些对象的空间。

有些策略在空间真正用完之前就做垃圾回收，后面会讲到一种。

三、标记清除

内存用完时，垃圾回收分两个阶段：标记阶段追踪可达对象，清除阶段回收垃圾对象。每个对象有一个额外的位，叫标记位，专留给内存管理，别的东西不用它。开始时所有对象的标记位都是 0，标记阶段把可达对象的标记位设为 1。

标记阶段

let todo = { all roots }
while todo != {} do
    pick v in todo
    todo <- todo - { v }
    if mark(v) = 0 then          (* v is unmarked yet *)
        mark(v) <- 1
        let v1, ..., vn be the pointers contained in v
        todo <- todo U { v1, ..., vn }
    fi
od

这是一个基于工作表的算法，初始工作表是所有根。核心是：如果 v 还没标记，就标记它，并把它指向的所有东西加进工作表；如果已经标记，说明处理过了，它指向的东西也已经加过，什么都不做，直接把它从工作表扔掉。

清除阶段

扫描整个堆，找标记位为 0 的对象：它们在标记阶段没被访问到，是垃圾，加入空闲链表。标记位为 1 的对象把标记位重置为 0，为下一次回收做好准备。 

(* sizeof(p) is the size of block starting at p *)
p <- bottom of heap
while p < top of heap do
    if mark(p) = 1 then
        mark(p) <- 0
    else
        add block p...(p+sizeof(p)-1) to freelist
    fi
    p <- p + sizeof(p)
od

从堆底开始，p 总是指向一个对象的开头。sizeof(p) 是从 p 开始的那个对象的大小，这就是 Cool 对象头部要存大小字段的原因：回收器走过内存时要知道对象多大，才能找到下一个对象。

例子：堆里有 A 到 F，只有一个根，指向 A；初始所有标记位为 0，空闲链表上已经有一小块内存。标记之后 A、C、E 的标记位是 1（从 A 出发，跟着指针到 C，再到 E），其他都是 0。清除时所有标记位重置为 0，不可达的 B、D 被加入空闲链表。最后空闲链表是一串可供今后分配的内存块。

细节

概念上很简单，但有一些棘手的细节，这在垃圾回收算法里很典型。标记阶段有个严重问题：它是在空间用完时才被调用的，可它又需要空间来存 todo 表，而 todo 表的大小没有上界，可能相当大，没法事先给它预留固定的空间。

有一个技巧可以把这些辅助数据存在对象本身里：指针反转。沿一个指针走过去时，把它反过来指向父对象。这实际上是在为图的深度优先搜索维护那个栈：要覆盖所有可达节点就得能回溯，反转的指针让你能沿原路走回去，回去时再把指针恢复原样。还有一个小问题是"差一位"：指针的空间在出发的那个对象里，被指向的对象里不一定有地方放反向指针。办法是用一个寄存器记住上一个访问的对象，往下走到下一个对象时，用当前对象里正在走的那个指针的位置，指回上一个对象的父对象。只需要一个寄存器，就能把指针一路反转回父对象和祖父对象。

空闲链表也存在空闲对象自身里：比如每个空闲块的第一个字存块的大小，第二个字指向链表的下一块。

评价

  • 新对象的空间从空闲链表分配：挑一个足够大的块，从中分出需要的大小，剩下的放回空闲链表。比如链表上有一个 100 字节的块，要分配 50 字节的对象，就用前一半，后一半放回去。
  • 所以标记清除会让内存碎片化：可能留下很多小碎块，散在各处，小到装不下任何对象。因此要尽量合并相邻的空闲块：清除阶段整理空闲链表时，发现两块在内存中紧挨着，就合成一块大的，只占链表一项，以抵消碎片。
  • 最大的优点：回收时对象不移动，不需要更新指向对象的指针。所以它能用于 C、C++ 这样的语言。在那里指针暴露给程序员，可以被操作和比较，指针地址是对象语义的一部分，不能移动对象；人们确实为 C 和 C++ 做过保守的标记清除变体。

四、停止复制

内存分成两个区域：旧空间用于分配，程序当前用的所有数据都在这里；新空间作为垃圾回收的预备区，程序不用。所以第一个决定是程序只能用一半的空间。有更先进的停止复制技术能让程序用到一半以上，所以没听起来那么糟，但终归有相当大一部分空间要留给回收器。

旧空间里有一个堆指针，指向下一个空闲的字，它左边的都在用。分配新对象就直接在堆指针处分配，堆指针往前挪一块。分配只是推进堆指针，又简单又快，这是停止复制的优点之一。

反复分配，旧空间终会填满，这时开始回收：把所有可达对象从旧空间复制到新空间。妙处在于，复制可达对象时，垃圾就被留在了后面：把用到的数据全捡起来搬过去，不要的都扔在旧空间。复制之后，新空间用的空间比回收前的旧空间少，有了可以分配新对象的余量。然后交换两个空间的角色，旧的变成新的，新的变成旧的，程序继续运行。

例子：旧空间里有 A 到 F，根指向 A；A 指向 C，C 指向 F，F 指回 A。复制这三个可达对象时连同指针一起复制，并且调整指针：新的 A 指向新的 C，新的 C 指向新的 F，新的 F 指回新的 A。整个对象图被复制到了新空间，后面留出空闲区，堆指针指向它的开头。

转发指针

和标记清除一样，要找出所有可达对象。不同的是要复制它们，于是必须找到并修正所有指向被复制对象的指针。这并不显然：找到一个对象时，你看不到所有指向它的指针。办法是：复制一个对象时，在旧副本里存一个指向新副本的转发指针，并以某种方式标记它已被复制（转发指针放在对象里一个固定的位置，课件写的是第一个字，Aiken 说重点不在第一个字，而在于总用同一个字）。就像知道一个人的住址，去了发现搬家了，可以问到新地址：之后在回收过程中（可能很久以后）遇到一个指针指向已移走的对象，就能通过转发指针找到新对象，把这个指针改过去。

不用额外空间的遍历

和标记清除一样，还要在不用额外空间的情况下遍历对象图。这些算法只在内存紧张时运行，回收器必须在常数空间里工作。技巧是把新空间分成三段连续的区域，用 scan 和 alloc 两个指针划分：

  • start 到 scan：已复制、已扫描的对象，复制过来并且处理过里面的所有指针。
  • scan 到 alloc：已复制、未扫描的对象，复制过来了，但还没看里面的指针，可能还指向没复制的对象。这一段就是工作表。
  • alloc 之后：空的，往里放新复制过来的对象。

演示

  1. 把根直接指向的 A 复制到新空间（逐位复制，不检查内部），alloc 移到 A 之后；在旧 A 里设转发指针。逐位复制意味着新 A 里的指针还指向旧空间的 C。
  2. scan 和 alloc 不相等，说明中间至少有一个对象，有活要干。扫描 A：它指向的 C 还没移走，复制 C，把 A 里的指针改为指向新 C，在旧 C 里设转发指针。scan 移过 A，alloc 移过 C。新 C 也是逐位复制，它还指向旧空间的 F。
  3. 扫描 C：F 还没移走，复制 F，改 C 里的指针，scan 移过 C。
  4. 扫描 F：它指向 A，而 A 已被标记为移走、有转发指针，于是不再复制，直接把 F 里的指针设成转发指针指向的位置，也就是新 A。没有分配新对象，alloc 不动。
  5. scan 追上 alloc，工作表为空，完成。新空间里是从根可达的对象图的完整副本。交换两个空间的角色，程序继续运行，在 alloc 之后分配，直到填满现在的旧空间，那时另一半就是下一次回收的新空间。
while scan != alloc do
    let O be the object at scan pointer
    for each pointer p contained in O do
        find O' that p points to
        if O' is without a forwarding pointer
            copy O' to new space (update alloc pointer)
            set 1st word of old O' to point to the new copy
            change p to point to the new copy of O'
        else
            set p in O equal to the forwarding pointer
        fi
    end for
    increment scan pointer to the next object
od

细节

  • 和标记清除一样，扫描一个对象时要知道它多大（才能把 scan 移到下一个对象的开头），还要知道里面哪些是指针，不能把看起来像指针的其他字段（比如整数的位模式）弄混。这不难，编译器决定了堆里对象的布局，可以把每种类型的指针位置等信息存下来交给回收器。
  • 还必须复制栈指向的所有对象，并更新栈里的指针。每次回收都得走遍整个栈，这可能是一个代价不小的操作。

评价

  • 停止复制一般被认为是最快的垃圾回收技术，Aiken 说他相信停止复制的各种变体是已知最高效的自动内存管理方法。
  • 分配很便宜，只是递增堆指针，没有复杂的空闲链表要遍历，也不用决定对象放哪。
  • 回收也相对便宜，垃圾越多越便宜：它只碰可达对象，完全不碰垃圾，一次回收的代价与存活对象的大小成正比。标记清除则与用到的全部内存成正比，因为清除阶段要碰每个对象，不管死活。存活对象少、垃圾多时，停止复制比标记清除快得多。
  • 缺点是要移动对象，而有些语言不允许复制，比如 C、C++，对象所在的地址在程序里可见、是对象语义的一部分，只能用标记清除。

五、保守回收

录像里有一小段讲 C、C++ 能怎样做垃圾回收。自动内存管理要能找到所有可达对象，还要能找到对象里所有的指针。C、C++ 的难处在于很难甚至不可能百分之百可靠地识别内存里对象的内容：看到两个字，可能是一个链表单元（一个数据字段、一个 next 指针），也可能是二叉树节点（两个都是指针），由于 C、C++ 类型系统的弱点，没法保证知道指针在哪里。

基本思路是：保守总是可以的。拿不准某样东西将来会不会用，就留着它；图的可达性本来就是一种保守的近似。所以诀窍是：看起来像指针的，就当作指针。怎样判断一个字像不像指针？

  • 它是对齐的，末尾有若干个 0，说明如果是指针，指向的是字边界；
  • 把它解释成地址，是一个有效的地址，指向数据段。

这两条能排除内存里大量的数据，比如任何小整数大概都不会被解释成数据段里的有效地址，所以被当成指针的绝大多数确实是指针。跟着它走，会高估可达对象的集合，留下一些其实不可达的东西，但留得比需要的多总是没问题的。仍然不能移动对象：不能确定一个东西是指针，就绝不能改它。比如把一个账号误当成指针，移动对象时更新了它，程序的行为就全变了。所以保守回收只适用于标记清除。

六、引用计数

与其等内存耗尽，不如在一个对象再没有指针指向它时就回收它：丢掉指向对象的最后一个指针、它变得不可达的那一刻就回收。做法是在每个对象里存指向它的指针数，这就是引用计数；如果这个数降到 0，就没人指着它，可以释放。为了维持准确的计数，每次赋值都要操作引用计数。

  • new 返回的对象引用计数为 1，返回的那个指针是它唯一的引用。
  • 记 rc(o) 为对象 o 的引用计数。设 x、y 分别指向对象 o、p。
  • 每个赋值 x ← y 都要改成：
rc(p) <- rc(p) + 1
rc(o) <- rc(o) - 1
if (rc(o) == 0) then mark o as free
x <- y

x 原来指的 o 少了一个引用，y 指的 p 多了一个；减了 o 的计数，就要检查它是否变成 0，是的话释放 o；最后真正做赋值。程序里每一个赋值都变成这四步。

优点

  • 容易实现。基本的实现很直接，可以想象代码生成器给赋值操作生成不同的代码就行了，对编译器的改动并不大。
  • 增量地回收垃圾，执行中没有长时间的停顿。对实时或交互式应用很有帮助，它把最长可能的停顿压到最小，程序不会因为跑去回收垃圾而看起来停住一阵。

缺点

  • 每次赋值都操作引用计数，很慢：两次计数更新、一次判零测试，再加赋值本身，每个赋值的代价至少翻四五倍，对很多程序的性能有明显影响。可以优化，比如在一个基本块甚至一个控制流图内对同一个对象的两次更新，聪明的优化编译器常常能合并成一次，更多次的更新也可能在某段程序内合并。但要做对很棘手：简单实现很慢但容易对，高度优化的实现快不少（对所有对象做引用计数时仍有可见的性能影响），却很难做对。
  • 不能直接回收环状结构。x 指向一个对象，它指向第二个对象，第二个又指回第一个，一个长度为 2 的循环链表：第二个对象计数为 1，第一个计数为 2（x 一个，另一个对象一个）。执行 x ← null 后，第一个对象计数变成 1。现在两个对象都不可达，但计数都不是 0，回收不了；引用计数看不出指向它们的引用只来自其他不可达对象。

对付环只有两个办法：程序员记住，每当环状结构要变得不可达时，先打破环，比如在丢掉 x 之前把环里的一个指针设为 null，这样计数就能正确地降到 0；或者用别的能回收环的垃圾回收技术给引用计数兜底，有的系统大部分回收靠引用计数，隔很久才跑一次标记清除，清掉那些环状但不可达的数据结构。

七、垃圾回收的评价

  • 自动内存管理防止了严重的存储 bug，那是编程中最难的一类 bug。用有垃圾回收的语言，整整一类问题都不用操心，编程效率更高。Aiken 说，如果你的程序很适合自动内存管理，不用支持它的系统就太傻了。
  • 但它减少了程序员的控制：控制不了数据在内存里的布局，也控制不了内存什么时候释放，对程序用多少内存只有很有限的控制。如果应用不是极度数据密集、不在乎精确的内存布局和驻留数据量，垃圾回收大概会很好用；但高端数据处理和科学计算这类要用大量数据、要很高效地利用内存的应用，垃圾回收效率太低，这些领域的人仍然手工管理内存。
  • 停顿对实时应用是问题。必须保证截止时间的程序，比如很多与外界交互、控制危险机械的嵌入式系统，要保证响应时间；可能停顿任意长时间的自动内存管理让这种保证很难做到。不过近些年实时垃圾回收器进步很大。
  • 内存泄漏仍然可能，甚至很可能。自动内存管理防止你破坏内存，却不能防止你抓着太多数据不放，从而大大拖累性能。正因为不必那么在意内存怎样被使用，反而更容易泄漏。Java 程序里典型的泄漏：某个变量 x 指向一个巨大的数据结构，比如编译器里的 AST；转成中间语言之后，后续编译只处理中间表示，再也不回头看 AST，但回收器不知道你以后不用它了，只要有变量指着，它就一直占着内存。正确的做法是在不再需要它的地方把 x 设为 null，丢掉这个指针，不管用哪种回收器，都能看出它不可达并回收。生产环境的 Java 程序里，这种忘了的、指向不再使用的数据的指针造成的泄漏很常见。

垃圾回收很重要，每个程序员都应该了解它的好处和代价，它也是语言实现里很有意思的部分。研究者在做更先进的算法，主要方向：

  • 并发：回收进行时程序可以继续运行，回收器在后台工作。
  • 分代：不在每次回收时都扫描长寿对象。生产回收器里很常见。回收很频繁，有些对象（比如程序大部分时间都在的大数据结构）活得很久，经过几次回收还在，大概还会再活几次。分代回收器把老对象放在单独的区域，回收得不那么频繁，让回收器集中处理最可能是垃圾的新分配对象。
  • 实时：限制最长停顿，即对程序的最长打断。
  • 并行：几个回收器同时工作并协调动作。
