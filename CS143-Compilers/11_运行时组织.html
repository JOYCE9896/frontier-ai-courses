第十一讲：运行时组织

从前端到后端，静态结构和动态结构的区分；程序启动时的内存布局；两条执行假设，活动和生命周期，活动树，用栈跟踪活动；活动记录（栈帧）里放什么，一个具体的设计和两次调用后的栈；全局变量和静态区，堆，栈和堆相向增长；字长、字节和对齐；栈机器，累加器，以及求值时保持栈不变的不变量

主讲：Fredrik Kjolstad（2026 年春季）；录像主讲：Alex Aiken
资料来源：课件（2026 年 5 月 7 日）、录像第 11 周（11-01 Runtime Organization 到 11-06 Stack Machines，按小节转载的播放列表）

一、从前端到后端

前端的三个阶段（词法分析、语法分析、语义分析）已经讲完。它们合起来的工作是强制执行语言的定义：如果三个阶段都没有报错，程序就是这门语言里的合法程序。前端还建好了代码生成需要的数据结构。从这里开始，编译器不再找程序里的错误，而是要生成代码，这是后端的工作。后端有两大块：代码生成和程序优化。先讲代码生成。

但在讲怎样生成代码之前，要先知道要生成的东西是什么样子：翻译后的程序是怎样组织的。这是一个很成熟的领域，有一些被广泛使用的标准技术，课程讲的就是这些，也鼓励大家在项目里用。

这一组内容的重点是运行时资源的管理，特别是静态结构（编译时存在的东西）和动态结构（运行时存在或发生的东西）之间的对应和区别。Aiken 说，要真正理解编译器怎样工作，这大概是最重要的一个区分：脑子里要清楚，什么是编译器做的，什么是推迟到生成的程序真正运行时才做的。

二、内存布局

程序的执行一开始由操作系统控制。用户要运行一个程序时：操作系统给程序分配空间；把代码载入这块空间的一部分；跳到入口点（比如 main），程序开始运行。

画内存图的惯例：低地址在上，高地址在下，用横线划分存放不同种类数据的区域。这只是惯例，反过来画也一样。这些图是简化：比如在虚拟内存系统里，内存不一定连续，但简单的图有助于理解有哪些种类的数据、编译器要怎样处理它们。

代码通常放在分配给程序的空间的一端，剩下的"其他空间"就是数据空间，放程序的所有数据。代码生成棘手的地方在于：编译器不但负责生成代码，还负责安排数据区的使用。它要决定数据的布局，再生成正确操作这些数据的代码。代码里当然有对数据的引用，所以代码和数据布局必须一起设计。

两个目标

代码生成有两个目标：正确和快。单独解决任何一个都很容易：只求正确，生成又简单又慢的代码不难；只求快不管对错就更容易了，Aiken 说他能为你说出的任何问题生成飞快但答案错误的程序。代码生成的所有复杂之处都来自同时追求两者。为此逐渐形成了一套相当精细的框架，规定代码生成器和对应的运行时结构应该怎样做。

三、活动

对要生成代码的语言做两条假设：

  1. 执行是顺序的：控制按明确定义的顺序从程序的一处移到另一处，执行完一条语句，下一条是哪条很容易预测。
  2. 调用一个过程时，控制最终会回到紧跟在调用之后的那一点。

这些假设总成立吗？不。违反第一条的最重要的一类是有并发的语言：执行了一条语句，下一条可能在完全不同的线程里。违反第二条的是一些高级控制结构，比如异常和 call/cc：Java、C++ 里抛出的异常可能逃出好几层过程才被捕获，调用一个可能抛异常的过程，控制未必会回到调用之后。课程剩下的部分保持这两条假设；这里讲的内容是所有实现的基础，有并发和异常的语言也建立在这些想法之上。

定义：调用一次过程 P，叫 P 的一次活动（activation）。P 的一次活动的生命周期是执行 P 的所有步骤，包括 P 调用的那些过程的所有步骤，也就是从 P 被调用那一刻到 P 返回那一刻之间执行的一切。

变量 x 的生命周期是执行中 x 有定义的那一部分，从 x 被创建到被销毁或释放。生命周期是动态（运行时）的概念；作用域是静态的概念，指程序文本中变量可见的那部分。这又是一次运行时和编译时的区分。

活动树

由第二条假设：P 调用 Q 时，Q 在 P 之前返回。所以过程活动的生命周期是正确嵌套的，可以画成一棵树。 

class Main {
    g() : Int { 1 };
    f() : Int { g() };
    main() : Int {{ g(); f(); }};
};

根是 main；main 调 g，g 成为 main 的孩子，表示 main 调了 g，而且 g 的生命周期包含在 main 之内；g 返回后 main 调 f，f 也是 main 的孩子；f 又调 g，又一次 g 的活动，成为 f 的孩子。这棵树表达了生命周期的包含关系，也表达了别的关系：g 的第一次活动和 f 是兄弟，生命周期完全不重叠。同一个方法在树里可以出现多次，每次调用都是一次单独的活动。 

class Main {
    g() : Int { 1 };
    f(x : Int) : Int { if x = 0 then g() else f(x - 1) fi };
    main() : Int { f(3) };
};

课件留作练习。答案：main 调 f(3)，3 不是 0，调 f(2)，再调 f(1)、f(0)，f(0) 调 g。活动树是一条链 main → f(3) → f(2) → f(1) → f(0) → g。递归过程会让同一个函数的活动嵌套在自己里面。

  • 活动树取决于运行时行为，具体调用哪些过程取决于运行时的值。
  • 不同输入的活动树可能不同。上面的程序不接受输入，所以每次运行都一样。
  • 从实现角度最重要的一点：活动是正确嵌套的，所以可以用栈跟踪当前活跃的过程。

栈只记录当前正在运行的活动，不记录整棵树。第一个例子：main 开始，栈是 [main]；调 g，压入 g；g 返回，弹出；调 f，压入 f；f 调 g，栈是 [main, f, g]；然后依次弹出 g、f、main。调用过程时压入一个活动，返回时弹出，因为生命周期正确嵌套，这样做是对的。

于是内存布局里，代码之后是栈，栈朝内存的另一端增长；过程调用时变大，返回时缩小。

四、活动记录

管理一次过程活动需要的信息叫活动记录（AR），也叫栈帧（frame），两个名字指同一样东西。有个有意思的事实：F 调用 G 时，G 的活动记录里常常混有 F 和 G 两方的信息。

为什么要保存活动的信息？F 调 G 时，F 被挂起，G 运行时占用处理器和机器的所有资源；G 完成后，F 要恢复执行。在 G 运行期间，必须把 F 的状态存在某处，才能正确地恢复它。所以 G 的活动记录里有完成 G 需要的信息，也有恢复 F 需要的信息。G 的活动记录还可能包括：G 的返回值（F 要用）；G 的实参（F 提供）；G 的局部变量的空间。

一个典型的 G 的活动记录包括：

  • G 的返回值的空间。
  • 实参。
  • 指向前一个活动记录的指针，叫控制链（control link），指向 G 的调用者的活动记录。
  • 调用 G 之前的机器状态：寄存器的内容和程序计数器。
  • 局部变量。
  • 其他临时值。

一个具体的例子

回到递归的例子，给 f 设计一个四格的活动记录：结果、参数、控制链、返回地址。f 在两处被调用，记 main 里调用 f(3) 之后的位置为 (*)，f 里 else 分支调用 f(x-1) 之后的位置为 (**)。

  • main 调 f：压入一个 f 的活动记录。结果格先空着，f 返回时才填；参数是 3；控制链指回 main 的活动记录；返回地址是 (*)。
  • f(3) 调 f(2)：再压一个。结果空；参数 2；控制链指向前一个 f 的活动；返回地址是 (**)。

返回地址并不简单：f 从不同的地方被调用，完成后要回到不同的地方。从 main 调用时，回去要做的只是结束整个程序；从 f 内部调用时，回去要做的是 if 表达式剩下的部分，然后从 f 返回。(*) 和 (**) 都是真实的内存地址，是调用 f 之后那条指令的地址。

Aiken 提醒，这个活动记录的栈没有数据结构课上讲的栈那么抽象。栈上确实有一个个不同的活动记录，运行时系统也这样对待它们，但它也是一个巨大的数组：所有数据都放在连续的内存里，一个活动记录紧接着上一个。编译器作者常常利用这一点耍些花招，下面就有一个。

第二次 f 调用返回后，调用者重新成为当前活动，它是新的栈顶。但被调用者的那个活动记录的数据还在内存里，可以去读，而且按这个设计必须去读：被调用者的返回值就存在那个活动记录的第一个字里。调用者的代码知道自己的活动记录有四个字，所以能在固定的偏移处（自己的帧之后第五个字）找到被调用者的返回值。只要在返回后立即读，在下一次过程调用覆盖它之前，数据都在。这就是把返回值放在帧的第一个位置的好处：调用者能在相对自己帧的固定偏移处找到它。

几点说明：

  • main 没有参数和局部变量，它的结果也从不被使用，它的活动记录没什么意思，这里不关心。
  • 这只是许多种可能的活动记录设计中的一种，它也适用于 C、Pascal、FORTRAN 等语言。可以重新排列帧里各项的顺序，可以换一种方式划分调用者和被调用者的职责。很多编译器不用控制链，因为不需要显式的链接也能找到调用者的活动记录，课程项目的 Cool 编译器就不用；大多数活动记录也不放返回值，因为用寄存器返回更高效方便。唯一的标准是：一种组织更好，如果它让代码更快或者让代码生成器更简单。
  • 真正的编译器会把帧里尽可能多的内容放在寄存器里，特别是方法的结果和参数，因为它们访问得最频繁。

要点：编译器必须在编译时（静态地）确定活动记录的布局，并生成正确访问活动记录里各个位置的代码。所以活动记录布局和代码生成器必须一起设计，不能先设计一个再回头定另一个，两者互相依赖。

五、全局变量和堆

全局变量的基本性质是所有引用都指向同一个对象。它不能放在活动记录里，因为活动结束时活动记录会被释放。所以每个全局变量被分配一个固定地址，一次定好。有固定地址的变量叫静态分配的，相当于在编译时分配：编译器决定它住在哪里，在程序的每次执行中它都住在那里。取决于语言，可能还有别的静态分配的值，后面会见到，它们的行为和全局变量一样。内存布局变成：代码，紧接着是静态数据，然后是栈。

比创建它的过程活得更久的值，也不能放在活动记录里： 

method foo() { new Bar }

Bar 对象是 foo 的结果，foo 返回后它的调用者还要能访问，可 foo 的活动记录已经被释放了。所以所有动态分配的数据都要放在活动记录以外的地方，有动态分配数据的语言用堆来存放。

总结各种数据：

  • 代码区：目标代码。对很多语言来说大小固定、只读，编译器生成所有要用的代码，一次分配好。也有很多语言可以在运行时动态生成代码。
  • 静态区：有固定地址的数据（不是代码），比如全局数据。大小固定，可读，可能可写（代码一般不希望可写）。
  • 栈：每个当前活跃的过程一个活动记录。每个活动记录通常大小固定，包含局部变量和执行这次活动需要的临时值。
  • 堆：其他所有数据，包括所有动态分配的数据。C 里由程序员用 malloc 和 free 管理；Java 用 new 分配，垃圾回收负责回收不再使用的数据。

堆和栈都会增长，要小心别让它们互相侵入对方的数据。一个简单漂亮的办法：让堆和栈从内存的两端开始，相向增长。代码、静态数据之后是栈，朝高地址增长（过程返回时也会缩小）；堆从另一端开始，朝低地址增长。有一个栈分配指针（下一个栈帧放在哪里）和一个堆分配指针（下一个对象放在哪里），只要两者不相遇，程序就还有内存加栈帧或分配对象。如果相遇，程序就真的没有内存了，运行时系统会终止程序，或者向操作系统要更多内存，或者采取别的办法。这个设计让堆和栈按程序最合适的方式共享数据区，不用做任何修改，就同样适用于需要很多堆、很少栈的程序，需要很多栈、很少堆的程序，以及两者大致平衡的程序，只要总量不超过分配给程序的内存。

六、对齐

机器体系结构的底层细节对数据布局的正确性和性能都很重要，其中最主要的是对齐。每个编译器作者都要了解它。

  • 今天大多数机器是 32 位或 64 位的，即一个字（word）32 或 64 位。
  • 一个字节 8 位，一个字 4 或 8 个字节。
  • 机器是按字节寻址或按字寻址的：机器码里只能指定整个字，或者能以单个字节为粒度引用内存。
  • 数据从字边界开始，就说它是字对齐的。

大多数机器有对齐限制，有两种形式：有的机器上，访问没有按要求对齐的数据，指令根本无法执行，程序甚至机器会挂起，总之不能正确执行；有的机器允许数据放在任何位置，但代价很大，访问未对齐的数据很容易慢十倍。

最常遇到对齐问题的情况之一是分配字符串。在 32 位机器上把 "Hello" 从一个字边界开始放：H、E、L、L、O 占五个字节，如果字符串以 \0 结尾就是六个字节。下一个数据放在哪？紧接着放最省内存，但它就不是字对齐的了。简单的办法是跳到下一个字边界再放下一个数据。中间跳过的字节就是垃圾，从不被引用，值是什么无所谓，只是没用的内存。它们不属于字符串。没有结尾的 \0 时，"Hello" 后面要补 3 个填充字节。

一般策略：数据从要求的边界（通常是字边界）开始；如果数据长度不是边界的整数倍，就跳过中间的字节，让下一个数据落在正确的边界上。

七、栈机器

现在开始讲代码生成，先讲最简单的模型：栈机器。它是表达式的一种简单求值模型：没有变量和寄存器，只有一个存放中间结果的值栈。每条指令：从栈顶取操作数，把它们移出栈，对它们做所需的运算，把结果压回栈。

加法：栈顶是 5、7、9……，add 弹出 5 和 7，算出 12，压回去，栈变成 12、9……。一条重要的性质：求值 7 + 5 之后结果在栈顶，而原来在参数下面的那些东西（9 及以下）完全没被改动，经过所有操作都保持原样。一般地，求值一个表达式后，它的结果在栈顶，求值开始前栈里的内容保持不变。

一门只有两条指令的语言：push i 把整数 i 压栈；add 弹出两个元素相加，把结果压回。计算 7 + 5 的程序： 

push 7
push 5
add

为什么用栈机器

  • 每个操作都从同一个地方取操作数、把结果放到同一个地方，所以编译方案是统一的，编译器也就更简单。
  • 操作数的位置是隐含的，总在栈顶，不用在指令里写出操作数和结果的位置。寄存器机器的 add 通常要写三个寄存器（两个参数一个目的地），栈机器只写一个 add。指令编码更小，程序更紧凑。这是 Java 字节码和 WebAssembly 采用栈求值模型的原因之一。Aiken 补充说，在 Java 早期，通过互联网下载程序很贵，代码紧凑是个优点。

那为什么还要寄存器机器？寄存器机器的代码一般更快，可以把数据正好放在想放的地方，中间操作更少，不用为了取到数据而反复压栈弹栈。

累加器

在纯栈机器和纯寄存器机器之间有一个中间点：n 寄存器栈机器，把栈顶的 n 个位置放在寄存器里。特别有意思的是单寄存器栈机器，只用一个寄存器存栈顶，收益就很大。这个寄存器叫累加器（accumulator），直观上它累积运算的结果，其余的数据都在栈上。

纯栈机器的 add 要做三次内存操作：读两个参数，写一个结果。栈顶被访问得非常频繁。把栈顶放进累加器，寄存器访问更快，add 变成 

acc <- acc + top_of_stack

只有一次内存操作，去取存在内存里的那部分栈上的第二个参数。

求值表达式的不变量

现在不只是字节码层面的指令序列，而是完整的 Cool 表达式，里面可以嵌套别的复杂表达式。对有 n 个参数的 op(e1, …, en)：

  • 依次求值 e1 到 e(n-1)，每求完一个，结果在累加器里，把它压到内存里的栈上。
  • 求值 en，结果留在累加器里，不压栈。
  • 求值 op：从栈上弹出 n-1 个值，和累加器里的值一起算出 op，结果存回累加器。

不变量：表达式的结果在累加器里，求值一个表达式保持栈不变。也就是说，求值 e 之后，内存里那部分栈和求值开始前一模一样。这是非常非常重要的性质。

用累加器算 7 + 5：acc ← 7；push acc；acc ← 5；acc ← acc + top_of_stack，得 12；pop。

更大的例子 3 + (7 + 5)，这次外层加法的一个参数本身是复合表达式，要递归求值：

代码累加器栈
acc ← 33<init>
push acc33, <init>
acc ← 773, <init>
push acc77, 3, <init>
acc ← 557, 3, <init>
acc ← acc + top_of_stack127, 3, <init>
pop123, <init>
acc ← acc + top_of_stack153, <init>
pop15<init>

整个表达式求值完，结果 15 在累加器里，栈和开始时一样。看子表达式 7 + 5 也一样：它从第三行开始、到第七行结束，开始前栈是 3, <init>，结束后还是 3, <init>，结果 12 在累加器里。外层加法的第一个操作数 3 一直在栈顶，等着最后的加法用。
