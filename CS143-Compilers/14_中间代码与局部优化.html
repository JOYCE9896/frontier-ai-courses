第十四讲：中间代码与局部优化

为什么要中间表示，三地址码和 igen；课程用的中间语言；基本块和控制流图；优化的目标、三种粒度和代价；局部优化：代数化简、常量折叠（以及交叉编译时折叠浮点数的危险）、删除不可达基本块、单赋值形式、公共子表达式消除、复制传播、死代码消除，以及它们怎样互相促成；窥孔优化；为什么"优化"其实应该叫"改进"

主讲：Fredrik Kjolstad（2026 年春季）；录像主讲：Alex Aiken
资料来源：课件（2026 年 5 月 19 日）、录像第 14 周（14-01 Intermediate Code 到 14-04 Peephole Optimization，按小节转载的播放列表）

一、中间表示

到目前为止讲了运行时组织、简单的栈机器代码生成和对它的改进。我们的编译器把 AST 直接映射到汇编，不做优化。优化是最后一个要讲的阶段，在流程上它位于语义分析和代码生成之间，因为要在把程序落实为机器码之前改进它。现代编译器的大部分复杂性在优化器里，它也是代码量最大的阶段。先要讲中间表示。

中间语言介于源语言和目标语言之间。用中间语言的编译器先把源程序翻译成中间语言，再把中间语言翻译成目标语言。为什么要分两步？因为中间这一层提供了一个中间的抽象层次：

  • 它比源语言有更多细节。比如要优化寄存器的使用，Cool 源代码里根本没有寄存器的概念，连想做的优化都没法表达；中间语言里有寄存器，就能写改进寄存器使用的算法。
  • 它比目标语言细节更少。它可以稍高于某台具体机器的指令集，没有那些琐碎的机器细节，更容易换到很多不同的机器上。

经验表明这是个好主意，几乎所有编译器的实现里都有中间语言，有的还有不止一个，要经过一系列中间语言才到达目标语言。

在哪一层做优化

层次优点缺点
AST与机器无关太高层，很多优化依赖机器的低层细节，在 AST 上连表达都表达不出来
汇编暴露所有机器细节和优化机会，原则上任何优化都能表达与机器相关；换目标体系结构时要重新实现优化
中间语言设计得好的话，与机器无关（能代表一大类机器），又暴露足够的优化机会

三地址码

课程只用一种中间语言：高级汇编。

  • 用寄存器名，但数量不限，不受 32 或 64 个的约束。
  • 控制结构和汇编一样，有显式的跳转和指令标号。
  • 有操作码，大多数直接对应汇编操作码，但有些更高层，比如 push 会翻译成目标机器上的好几条汇编指令。

每条指令的形式是 x := y op z 或 x := op z，y 和 z 是寄存器或常量。这种中间代码用得很广，有自己的名字：三地址码，每条指令至多三个地址，两个参数一个目的地。

它确实是低层的：含多个运算的高层表达式要翻译成一串每次只做一个运算的指令。x + y * z 要写成 

t1 := y * z
t2 := x + t1

每次只做一个基本运算、结果存进一个寄存器，效果是给每个子表达式都起了名字。在原表达式里 y * z 是匿名的，改写后这个中间结果有了名字 t1。

生成中间代码

和生成汇编很像，主要区别是可以用任意多个寄存器存中间结果。写一个函数 igen(e, t)，生成计算 e 并把值放进寄存器 t 的代码： 

igen(e1 + e2, t) =
    igen(e1, t1)      # t1 is a fresh register
    igen(e2, t2)      # t2 is a fresh register
    t := t1 + t2

寄存器不限量，代码生成就很简单，甚至比栈机器还简单：栈机器要把 e1 的结果压栈，要好几条指令；这里存进一个寄存器，后面直接用它的名字。课程只要求能在讲课的层次上使用中间代码，能写简单的中间代码程序和在中间代码上工作的算法，不要求会生成中间代码，因为不会再细讲，坦白说它也没有新想法，只是已经细讲过的代码生成的一个变体。

课程用的中间语言

P -> S P | ε
S -> id := id op id
   | id := op id
   | id := id
   | push id
   | id := pop
   | if id relop id goto L
   | L:
   | jump L

id 是寄存器名，也可以用常量代替；常见运算符有 +、-、* 等。语句有赋值（复制、一元或二元运算）、压栈弹栈、比较后条件跳转、无条件跳转和标号。

二、基本块和控制流图

优化通常作用在一组语句上，最重要的分组之一是基本块：一个极大的指令序列，满足

  • 除了第一条指令，没有标号；
  • 除了最后一条指令，没有跳转。

于是不能跳进基本块的中间（只能从开头进），也不能从中间跳出（只能从末尾出）。基本块是单入口、单出口的直线代码段：一旦从第一条开始执行，就一定执行完所有语句才到最后一条，控制流完全可预测。 

L:
    t := 2 * x
    w := t + x
    if w > 0 goto L'

第三条总是在第二条之后执行，所以可以把它改成 w := 3 * x，这个优化之所以正确，是因为第二条保证在第三条前执行。还能删掉第二条吗？如果 t 只是为了算 w 而存在的临时值，就可以；但这取决于程序的其他部分，要知道 t 在别处有没有用，只看这个基本块看不出来。

第二个重要的分组是控制流图（CFG）：一个以基本块为节点的有向图，如果执行能从块 A 的最后一条指令走到块 B 的第一条指令，就有一条从 A 到 B 的边，比如 A 的最后一条是 jump LB，或者执行从 A 顺序落到 B。块内没有值得关心的控制流，所以控制流图概括了一段代码里真正做控制流决定的地方。 

x := 1
i := 1

L:
    x := x * x
    i := i + 1
    if i < 10 goto L

两个基本块：循环外的初始化，和循环体。循环体末尾是一个测试分支，要么退出去别处，要么回到循环体再执行一遍。方法（过程）的主体总可以表示成控制流图，约定有一个起始节点（通常就是列在最上面的那个），所有"返回"节点都是终止节点，没有出边。

三、优化概述

优化的目的是改进程序对资源的使用。课程里说优化，一般指执行时间，让程序跑得更快，这也是人们最关心的。但也可以优化别的资源，Aiken 说你能想到的任何资源，大概都有某个领域的编译器在为它花力气：代码大小、发出的网络消息数、内存使用、磁盘访问（比如数据库尽量减少访问磁盘的次数）、电池供电设备的功耗。重要的是，优化不能改变程序算出的东西，答案必须一样。

三种粒度

对 C、Cool 这类语言，优化有三种粒度：

  1. 局部优化：单独作用于一个基本块。
  2. 全局优化：单独作用于一个控制流图（一个方法体）。这个名字起得不好，它指的是跨一个函数的所有基本块，并不跨整个程序。
  3. 过程间优化：跨方法边界，把多个函数作为一个整体来优化。

几乎所有编译器都做 (1)，很多做 (2)，很少做 (3)。粒度越大做的编译器越少，部分因为更难实现，也因为很多收益来自更局部的优化。

课件列出的主要优化：基本块优化，数据流优化，循环优化，指令选择和窥孔优化，寄存器分配；面向对象语言的内联、计算方法调用的目标、拆箱；函数式语言的尾递归消除、deforestation（消除中间数据结构）。

优化的代价

实践中，人们常常有意不去实现已知的最花哨的优化。Aiken 说，作为一个很喜欢编译器、花了大量时间思考优化的人，他觉得这有点遗憾，对职业编译器研究者来说也许不太好接受，但值得明白为什么，归根到底是软件工程问题：

  • 有些优化很难实现。
  • 有些优化编译时间开销很大。虽然编译是离线的、不属于程序运行，但程序员还得等着，要是优化一个程序要几个小时甚至几天，并不好。
  • 有些优化收益很低，总能改进程序，但改进得很少。
  • 研究文献里很多最花哨的优化三样全占：复杂、慢、收效甚微。

所以真正的目标是以最小的代价换最大的收益，讲的是性价比：优化在编译器复杂度和程序员等待时间上要付出代价，它对程序的改进必须足以抵消这些代价。

四、局部优化

最简单的一种优化，只看一个基本块，不需要分析整个过程体，不用操心复杂的控制流。以下例子都假设 x 是 Int。

代数化简

有些语句可以删掉：x := x + 0、x := x * 1，0 是加法单位元，1 是乘法单位元，赋给 x 它现有的值，没用。这是很好的优化，省掉了整条指令。

有些语句可以化简：

  • x := x * 0 ⇒ x := 0。在很多机器上两者一样快，但把常量赋给变量能促成别的优化，所以仍然很值得做。
  • y := y ** 2 ⇒ y := y * y。乘方几乎肯定不是机器指令，生成代码里多半是调用数学库，有函数调用开销，里面还有一个按指数做乘法的通用循环。指数是 2 时直接乘一次高效得多。
  • x := x * 8 ⇒ x := x << 3，乘以 2 的幂相当于把二进制左移。
  • x := x * 15 ⇒ t := x << 4; x := t - x，不是 2 的幂也能用移位和减法的组合代替。

后两条在某些机器上 << 比 * 快，但不是所有机器：在现代机器上整数乘法和任何其他单条指令一样快，一般不会有加速；在历史上的机器上这些是很重要的优化。这些都叫代数化简，利用数学运算的性质，把复杂的指令或运算换成简单的。

常量折叠

最重要、最有用的局部优化之一：如果参数在编译时已知，就在编译时而不是运行时算出结果。对 x := y op z，如果 y 和 z 都是常量（指令里的立即数），就在编译时算出 y op z。

  • x := 2 + 2 ⇒ x := 4。
  • if 2 < 0 jump L 可以删掉：条件只含立即数，编译时就能决定，2 < 0 为假，不会跳转。如果条件保证为真，就把它换成无条件跳转。

课件问：常量折叠什么时候可能有危险？Aiken 讲了一个不常见但很有启发的情形，它揭示了程序优化和语言语义的一些微妙之处。设编译器运行在机器 X 上，生成的代码运行在机器 Y 上，这叫交叉编译。常见的原因是 Y 很弱：很慢、内存很少、功耗受限，在强大的工作站上开发和编译更划算，很多嵌入式代码就是这样开发的。如果 X 和 Y 是不同的体系结构，考虑 a := 1.5 + 3.7，想折叠成 a := 5.2。可如果在 X 上直接按浮点运算算，X 的舍入和浮点语义可能和 Y 略有不同，在 Y 上算可能得到 5.19 之类。有些算法很依赖浮点数被一致地处理，同一个运算每次都要按同样的方式舍入。把计算从运行时（在 Y 上）挪到编译器里（在 X 上），就可能改变程序的结果。讲究的交叉编译器会在编译器内部把浮点数表示成字符串，在字符串上做全精度的长式加减乘除，在生成代码里写入全精度的字面量，让 Y 自己决定怎样舍入。

删除不可达基本块

不可达的基本块是不作为任何跳转目标、也不会从别的块顺序落入的块，它永远不会执行，可以删掉。它本来不增加执行的指令数，但删掉它让程序变小，有时也变快：指令和数据一样要放进内存，程序小了更容易装下，一起用的指令也可能靠得更近，空间局部性更好，缓存效果更好。

为什么程序里会有不执行的代码？其实很常见，所以这个优化相当重要：

  • 代码按情况参数化，有些部分只在特定条件下编译和使用。C 里常见 #define DEBUG 0 和 if (DEBUG) { ... }，不带调试编译时，这等于 if (0)，常量折叠后 then 分支成为不可达块，被删掉。优化器就这样剥掉了所有用不到的调试代码。要调试时把 DEBUG 改成非零。
  • 库：程序常常用一个通用的库，库提供一百个方法覆盖各种需求，你的程序也许只用了三个，其余的可以从最终的二进制里去掉。
  • 其他优化的结果：优化常常引出更多优化，经过别的重排，某个基本块可能变成多余的。

单赋值形式

有些优化在每个寄存器最多在赋值左边出现一次时更容易表述。于是把中间代码改写成单赋值形式：如果一个寄存器被重复赋值，就给其中一次赋值换一个新寄存器名，并替换它的使用： 

x := z + y          b := z + y
a := x       =>     a := b
x := 2 * x          x := 2 * b

b 是新寄存器。有循环时一般情况更复杂（这就是静态单赋值形式 SSA）。另外还要求块里对一个寄存器的定义是它在块里的第一次使用，排除"先读 x、后面再定义 x"的情况，那样的话后面的定义也要换名。

公共子表达式消除

如果基本块是单赋值形式，并且定义 x := 是 x 在块里的第一次使用，那么两个右边相同的赋值计算出同样的值： 

x := y + z          x := y + z
...          =>     ...
w := y + z          w := x

块里只能有一次对 x 的赋值，中间省略的指令不能给 x 赋值，也不能改 y 和 z（它们已经有自己的定义了），所以 x 和 w 算的是同一个值，第二次计算可以直接用已有的名字 x，省得重算。这也是更重要的编译器优化之一，出现得出奇地频繁，能省不少工作。

复制传播

如果块里有 w := x，就把之后对 w 的使用替换为对 x 的使用（同样假设单赋值形式）： 

b := z + y          b := z + y
a := b       =>     a := b
x := 2 * a          x := 2 * b

它本身对代码毫无改进，只在和别的优化结合时才有用，用来促成常量折叠和死代码消除。传播的值是常量而不是寄存器名时，叫常量传播，本质一样。 

a := 5              a := 5
x := 2 * a   =>     x := 10
y := x + 6          y := 16
t := x * y          t := 160

把 5 传播给 a 的使用，2 * 5 折叠成 10；10 是常量赋值，又能传播给 x 的使用，10 + 6 折叠成 16；再传播，10 * 16 折叠成 160。一步引出下一步。

死代码消除

如果基本块里有 w := rhs，而 w 在程序里别的任何地方都没有出现（不只是这个块，整个过程里都没有），那这条语句就是死的，可以删掉。"死"的意思是对程序的结果没有贡献：写进 w 的值从来没被引用，算它纯属浪费。设 a 在别处都不用： 

b := z + y          b := z + y          b := z + y
a := b       =>     a := b       =>     x := 2 * b
x := 2 * a          x := 2 * b

先转成单赋值形式，再复制传播，a := b 之后不再被用，删掉。

优化的相互作用

每个局部优化单独做的事都很少，有些上面讲的变换本身既不让程序变快也不变慢。但优化之间会相互作用，做一个会促成另一个。Aiken 说，可以把优化编译器想成有一大袋技巧，知道很多单独的程序变换；面对一个程序，它在袋子里翻找能用于某部分代码的优化，找到就做，然后回头再看程序，看还有没有能用的，一直重复，直到它知道的优化一个都用不上为止。优化器也可以随时停下来，以限制编译时间。

一个专门构造来展示这些优化的例子： 

a := x ** 2
b := 3
c := x
d := c * c
e := b * 2
f := a + d
g := e * f
  1. 代数化简：a := x * x，e := b << 1。
  2. 复制传播：b 是常量赋值，c 是复制，传播到它们的使用：d := x * x，e := 3 << 1。
  3. 常量折叠：e := 6。
  4. 公共子表达式消除：a 和 d 都是 x * x，d := a。
  5. 复制传播：d 和 e 传播下去，f := a + a，g := 6 * f。
  6. 死代码消除：假设 b、c、d、e 在程序别处都不用，四条全删。这一步才真正省下了整条指令，是最好的那种节省。
a := x * x
f := a + a
g := 6 * f

这是最终形式。其实还不是最快的：还可以注意到 f 等于 2 * a，再重排一下得出 g = 12 * a，然后 f 的赋值也可能成为死代码。Aiken 说有些编译器能找到这一步，但他相信很多当前最先进的编译器也发现不了这最后的重排。

五、窥孔优化

前面的优化作用在中间代码上，与目标无关，但也可以直接用在汇编上。窥孔优化是改进汇编代码的一种有效手段。"窥孔"是一小段（通常连续的）指令：把程序看作一长串指令，透过一个小孔看，比如孔的大小是 4，就只能看到连续的四条指令。优化器盯着这一小段，如果知道一个等价但更快的序列，就替换掉；然后把孔挪到别处，或者在同一处继续应用别的变换。

窥孔优化写成替换规则 i1, ..., in → j1, ..., jm，右边是左边的改进版：

  • move $a $b, move $b $a → move $a $b：第二条把值搬回去，没用。前提是 move $b $a 不是任何跳转的目标。
  • addiu $a $a i, addiu $a $a j → addiu $a $a i+j：把两次加法合成一次，这是常量折叠。

很多（但不是全部）基本块优化都可以写成窥孔优化：

  • addiu $a $b 0 → move $a $b。
  • move $a $a →（空），自己赋给自己，删掉。
  • 两条合起来就消掉了 addiu $a $a 0：先变成 move $a $a，再被删掉。和局部优化一样，窥孔优化也要反复应用才能达到最大效果。

六、小结

  • 中间代码对很多优化有帮助。
  • 很多简单的优化仍然可以直接用在汇编上，优化中间代码并没有什么神奇之处。用任何语言写的程序，源语言、中间语言或汇编，都可以谈怎样变换它来改进行为。
  • "程序优化"这个名字有点名不副实。"优化器"产生的代码在任何合理的意义上都不是最优的，编译器要是碰巧生成了一个程序的最好代码，那纯属偶然。编译器做的是：它知道一堆能改进程序行为的变换，就尽量改进。所以更恰当的叫法是"程序改进"，让程序变得更好，但不保证达到最好。
