第十六讲：寄存器分配

存储层次和谁负责在各层之间搬数据；寄存器分配问题：让很多临时变量共用少数寄存器；两个临时变量能共用寄存器的条件，用活跃性信息构造寄存器冲突图；图着色、NP 难和那个简单有效的启发式（删度数小于 k 的节点入栈，再逆序着色），完整演示；启发式卡住时的溢出、乐观着色、改写代码和重算活跃性，选哪个变量溢出；CISC 机器；编译器不擅长管理缓存，循环交换

主讲：Fredrik Kjolstad（2026 年春季）；录像主讲：Alex Aiken
资料来源：课件（2026 年 5 月 26 日）、录像第 16 周（16-01 Register Allocation 到 16-04 Managing Caches，按小节转载的播放列表）

一、存储层次

层次访问时间容量（课件给的数字）
寄存器1 个周期256 到 8000 字节
缓存3 个周期256 KB 到 40 MB
主存20 到 100 个周期4 GB 到 32 GB 以上
磁盘50 万到 500 万个周期1 到 10 TB

寄存器能以时钟频率在一个周期内访问，但造这么快的存储很贵，所以很少；现代处理器芯片面积的很大一部分给了缓存，比寄存器稍慢，但多得多；主存（DRAM）远离处理器，访问代价高得多，Aiken 说如今更接近 100 个周期那一端；磁盘最远，要几十万到几百万个周期，但容量巨大。

大多数程序写得好像只有两种存储：主存和磁盘。各层之间搬数据的责任是这样分的：

  • 程序员负责在磁盘和内存之间搬数据（文件 I/O）。
  • 硬件负责在内存和缓存之间搬数据。
  • 编译器负责在内存和寄存器之间搬数据。

趋势：功耗限制了寄存器和缓存的大小与速度，也限制了处理器的速度。但缓存未命中的代价很高，从缓存取只要几个周期，不在缓存里就要从主存取，慢两个数量级。所以要在处理器和主存之间放缓存来掩盖主存的延迟，通常需要两到三级缓存才能把快速的处理器和大容量的主存衔接好。因此管好寄存器、管好缓存都很重要。编译器很擅长管理寄存器。

二、寄存器分配问题

寄存器分配是编译器为了性能所做的最精巧的事情之一，也用到了全局流分析里的很多概念。中间代码可以用无限多个临时变量，这简化了代码生成和优化（不用操心保留正确数量的寄存器），却让最终翻译成汇编变复杂了：典型的中间代码用的临时变量太多，比目标机器的寄存器还多，这在实践中很常见。

问题：改写中间代码，使它用的临时变量不超过机器寄存器的数目。方法：把多个临时变量分配给同一个寄存器，即从临时变量到寄存器的多对一映射，同时不改变程序的行为。很多临时变量显然不能都塞进一个寄存器，需要某种诀窍；有时还会失败，需要后备方案。

诀窍是：一个寄存器可以装多个值，只要同一时刻只装一个。 

a := c + d
e := a + b
f := e - 1

假设 a 和 e 用过之后就死了，在别处都不用。a 在第一条写、第二条读，读完 a 就用完了，第二条之后可以"重用"a 的寄存器；e 在第二条写、第三条读，之后也可以重用。a、e、f 从未同时存在，所以可以都放进同一个寄存器 r1，c、d、b 各占一个： 

r1 := r2 + r3
r1 := r1 + r4
r1 := r1 - 1

这只是把原代码按多对一映射换成了寄存器名。死的临时变量不再需要，它的寄存器可以重用。

历史

寄存器分配和编译器一样古老，1950 年代最初的 FORTRAN 编译器就做了，但算法很粗糙。人们很快发现它是代码生成质量的瓶颈，寄存器分配做不好，对编译器能产生的代码质量影响很大。大约三十年后的 1980 年，IBM 的一个研究小组取得突破，发现了基于图着色的寄存器分配方案。它相对简单，容易解释；是全局的，同时利用整个控制流图的信息；在实践中效果很好。

基本原则

如果在程序的任何一点，临时变量 t1 和 t2 至多有一个是活跃的，它们就可以共用同一个寄存器。反过来说：如果 t1 和 t2 在某一点同时活跃，它们就不能共用寄存器，同一时刻需要两个值，就得放在两个寄存器里。

三、寄存器冲突图

第一步：算出每个程序点上的活跃变量。课件的例子是一个带循环的控制流图： 

   +-------------------------------+
   v                               |
a := b + c                         |
d := -a                            |
e := d + f                         |
   |                               |
   +--> f := 2 * e                 |
   |    b := f + c   (b live on exit)
   |                               |
   +--> b := d + e                 |
        e := e - 1  ---------------+

（这是根据课件的控制流图和活跃集合整理的示意：第一个块之后分两路，一路算 f 再算 b 后退出，另一路算 b、e 后回到开头。）假设出口处只有 b 活跃。活跃性是后向分析，从出口往回推：b := f + c 写 b、读 f 和 c，所以它之前 {c, f} 活跃；f := 2 * e 读 e、写 f，之前 {c, e}；另一边 e := e - 1 之后回到开头，开头的 a := b + c 读 b 和 c，再往下 e := d + f 读 f，所以这里是 {b, c, f}（只要在某条将来的路上会被用到就算活跃）；之前加上 e 是 {b, c, e, f}；b := d + e 写 b、读 d，之前是 {c, d, e, f}；如此等等。课件给出的各点活跃集合有 {a, c, f}、{c, d, f}、{c, d, e, f}、{b, c, e, f}、{b, c, f}、{c, e}、{c, f}、{b}。

构造一个无向图：

  • 每个临时变量一个节点；
  • 如果 t1 和 t2 在程序某点同时活跃，就在它们之间连一条边。

这就是寄存器冲突图（register interference graph，RIG）。两个临时变量之间没有边，就可以分配到同一个寄存器。

从上面的活跃集合读出边：ac、af、cf（来自 {a,c,f}），cd、df（{c,d,f}），ce、de、ef（{c,d,e,f}），bc、be、bf（{b,c,e,f}）。比如 b 和 c 之间有边，不能在同一个寄存器；b 和 d 之间没有边，它们的活跃区间不重叠，可以在同一个寄存器。

RIG 的好处：

  • 它恰好提取了刻画合法寄存器分配所需的信息，表示了所有可能的合法分配。
  • 它给出寄存器需求的全局图景，跨整个控制流图，有助于在全局上决定哪些值最值得放进寄存器。
  • 建好 RIG 之后，寄存器分配算法与体系结构无关，唯一需要知道的机器属性是寄存器的数目。

四、图着色

图的一个着色是给节点分配颜色，使有边相连的节点颜色不同。如果一个图有一个用 k 种（或更少）颜色的着色，就说它是 k 可着色的。比如三个两两相连的节点，可以涂成蓝、绿、黑。

在我们的问题里，颜色就是寄存器：要给图的节点（临时变量）分配颜色（寄存器），令 k 为机器寄存器的数目。如果 RIG 是 k 可着色的，就存在一个用不超过 k 个寄存器的分配。

例子的 RIG 没有少于 4 种颜色的着色，但有 4 着色，比如 f = r1，e = r2，b = r3，c = r4，d = r3，a = r2。节点远多于四个，但只用了四种颜色，d 和 b 同色，e 和 a 同色。把临时变量换成对应的寄存器名： 

r2 := r3 + r4      # a := b + c
r3 := -r2          # d := -a
r2 := r3 + r1      # e := d + f
r3 := r3 + r2      # b := d + e
r2 := r2 - 1       # e := e - 1
r3 := r1 + r4      # b := f + c
r1 := 2 * r2       # f := 2 * e

离可以输出、在目标机器上运行的代码已经很近了。

怎样算出着色

不容易：

  1. 这个问题很难，是 NP 难的，不知道有高效算法。解决办法：用启发式，也就是不能完全解决问题的近似技术，所有编译器都这样做。
  2. 对给定的寄存器数，着色可能根本不存在：机器只有 8 个寄存器，图却至少需要 9 或 10 种颜色。解决办法后面讲。

启发式

观察：挑一个在 RIG 中邻居少于 k 个的节点 t，把 t 和它的边从 RIG 中删掉。如果剩下的图是 k 可着色的，原图也是。为什么？设缩小的图里 t 的 n 个邻居被涂了颜色，因为 n < k，它们用不完 k 种颜色，总能给 t 挑一种和所有邻居都不同的颜色。这是一种分而治之：删一个节点，给剩下少一个节点的小问题着色，再把它加回来。

实践中效果很好的做法：

  • 第一阶段：挑一个邻居少于 k 个的节点 t，把 t 压栈，从 RIG 中删除。重复直到图为空（课件写的是直到只剩一个节点）。
  • 第二阶段：给栈里的节点着色，从最后压入的节点开始。每次弹出一个节点，连同它在原图里的边加回图中，挑一种和已着色的邻居都不同的颜色。它被删掉时邻居少于 k 个，加回来时也少于 k 个，所以总有颜色可用。

演示（k = 4）

  1. 开始时栈为空。a 只有两个邻居（c、f），删掉 a，栈 {a}。
  2. 剩下的图里只能挑 b 或 d，c、e、f 都有四个邻居。任意选 d，栈 {d, a}。
  3. 现在所有节点的邻居都少于 4 个。这时着色保证会成功，因为每删一个节点，其他节点的邻居数只会减少。Aiken 指出这是这个启发式的一个好性质：一个节点哪怕一开始邻居远多于 k，删掉足够多的节点后，它的邻居数也可能降到可用颜色数以下，于是就能着色了。在上一步它们不能被选，因为它们的邻居可能用光所有颜色。删 c，栈 {c, d, a}。
  4. 删 b，栈 {b, c, d, a}。
  5. 删 e，栈 {e, b, c, d, a}。
  6. 删 f，栈 {f, e, b, c, d, a}，图空了。

第一阶段的真正目的，就是给节点排一个着色的顺序。第二阶段从栈顶开始，每次挑一个邻居没用过的、编号最小的寄存器：

  • f 独自在图里，给 r1。
  • e 必须和 f 不同，给 r2。
  • b 和 f、e 都相邻，给 r3。
  • c 和 f、e、b 都相邻，前三个寄存器都被占了，给 r4。四个寄存器全用上了，但因为第一阶段按正确的顺序删了节点，剩下的节点不会同时和这四个都相邻。
  • d 的邻居是 f、e、c，唯一没被用的是 r3，和 b 同一个寄存器。
  • a 的邻居用了 r1 和 r4，可以用 r2 或 r3，按编号最小的规则给 r2。

得到的就是上面那个完整的着色。

五、溢出

启发式不一定能给任意图着色，可能卡住。这时只能得出结论：想放进寄存器的值装不下，临时值比寄存器多。它们总得有地方住，只能住在内存里，这叫溢出（spilling）。Aiken 的比喻是一个桶，只能装固定的量，装太满就有东西溢到别处去。

启发式什么时候卡住？只有当所有节点都有 k 个或更多邻居时。还是那个 RIG，但假设机器只有三个寄存器，要找 3 着色：删掉 a 之后就卡住了，剩下的每个节点都至少有三个邻居，没有哪个删掉后能保证用这个启发式给它着色。

办法：挑一个节点作为溢出候选，被溢出的临时变量"住"在内存里。假设挑了 f（怎样挑稍后讲，对这个例子无所谓）。把 f 删掉，继续化简，这回成功了：b、d 都只有两个邻居，删掉它们后 e、c 各只剩一个邻居。成功的一种顺序是 b、d、e、c。

乐观着色

最终总得给 f 分配颜色。也许运气好：f 被删时虽然有三个或更多邻居，但子图着色后，这些邻居可能并没用光所有寄存器，比如它们都被分到了同一个寄存器，那 f 就有寄存器可用，可以照常继续着色，好像什么都没发生。我们希望 f 的四个邻居用了少于 3 种颜色，这叫乐观着色。

这个例子里，把 f 加回去，它的邻居分别用了 r1、r2、r3，乐观着色失败，f 必须真的溢出，存在内存里。

改写代码

为 f 分配一个内存位置，通常在当前栈帧里，记其地址为 fa。然后修改正在编译的代码：

  • 在每个读 f 的操作之前插入 f := load fa：值在内存里，要用就得先从内存装进寄存器。
  • 在每个写 f 的操作之后插入 store f, fa：把当前值存回它在内存里的位置。

这样改写的代码重用了寄存器名 f，正确但不够好。应该尽可能用不同的寄存器名，让不同的使用可以有不同的颜色： 

a := b + c
d := -a
f1 := load fa
e := d + f1
f2 := 2 * e
store f2, fa
f3 := load fa
b := f3 + c
b := d + e
e := e - 1

（代码按课件的列法排列，实际分布在原来的几个基本块里。）原来 f 有两处读、一处写，现在每处各有自己的名字 f1、f2、f3。

重算活跃性和 RIG

决定溢出就意味着改了程序，加了 load 和 store，寄存器分配问题也变了，要重算活跃性、重建 RIG、再试着着色。新的活跃性信息几乎和以前一样：f 以外的临时变量基本不受影响，只是多了几个可能活跃的新程序点，以前活跃的地方现在仍活跃。f 本身变化很大：旧名字 f 不再使用，它的活跃信息消失；f 被分成三个临时变量，每个只在很小的范围内活跃，新增的活跃集合是 {c, d, f1}、{c, f2}、{c, f3}。

  • load 装进的 fi 只在 load 和下一条使用它的指令之间活跃。
  • store 存的 fi 只在 store 和前一条产生它的指令之间活跃。

溢出大大缩短了被溢出变量的活跃区间，从而减少了它的冲突，在重建的 RIG 里它的邻居更少。把名字分开，也避免了不同版本之间共享活跃区间。新 RIG 里 f 的各个版本只和 c、d 冲突（原来 f 还有好几个别的邻居），新图是 3 可着色的。

选谁溢出

找到着色之前可能还要溢出更多变量。难的是决定溢出哪个，这是寄存器分配中最难的决定。但任何选择都是正确的，区别只在性能，有的选择生成的代码更好。几种常用的启发式：

  • 溢出冲突最多的临时变量。把它移到内存里，对图中冲突数影响最大，也许溢出这一个就能去掉足够多的边，让图可以着色。
  • 溢出定义和使用很少的临时变量。用得少，要加的 load 和 store 就少，额外执行的指令代价相对小。
  • 避免在内层循环里溢出。Aiken 认为所有编译器都实现了这一条：在内层循环里用的变量和在别处用的变量之间，宁可溢出后者，因为不想往内层循环里加额外的指令。

小结

寄存器分配是编译器最重要的工作之一，如今任何像样的产品级编译器都必须有它：中间代码通常用了太多临时变量（正因为有好的寄存器分配算法，中间代码才可以写得随意一点），而寄存器是很重要的资源，用好它，代码效率会高得多。这里讲的算法主要针对 RISC 机器，在很多 RISC 机器上几乎拿来就能用。CISC（复杂指令集）机器上寄存器分配更复杂：常有寄存器使用的限制，某些操作只能用某些寄存器，寄存器可能大小不同、只能装某些值。人们的做法是改造这里讲的图着色过程，基本思路完全一样，只是多了一些步骤，在这些地方遵守具体的寄存器约束。

六、缓存

编译器很擅长管理寄存器，比程序员能做到的好得多，今天大多数人都同意，几乎所有程序都应该把寄存器分配交给编译器。但编译器不擅长管理缓存，这个问题仍然留给程序员：想要好的缓存性能，程序员得了解机器缓存的行为、自己程序的行为、编译器能做什么，然后把程序写成对缓存友好的样子。编译器到底能为缓存性能做多少，仍然是个开放问题。编译器能做、也有少数编译器确实在做一些缓存优化。 

for (j := 1; j < 10; j++)
    for (i := 1; i < 1000000; i++)
        a[i] *= b[i]

这个程序的缓存性能极差。为什么？第一次迭代读 b[1]、写 a[1]，它们被装进缓存；第二次是 a[2]、b[2]……每次迭代都访问新的元素，不是上一次的那些，所以每次访问都未命中。（先忽略一个缓存行里有多个元素的事实：取数据时会取一整行，可能顺带取到几个相邻元素；但如果数据项大到占满一行，每次迭代两个元素都未命中，完全得不到缓存的好处，循环以主存而不是缓存的速度运行。）而且循环上界选得很大，比缓存大得多：快到内层循环末尾时，缓存已被 a、b 的值填满，开始覆盖已有的值。如果数组是缓存的两倍大，内层循环跑完一遍时，缓存里是数组的后半段；外层循环下一次迭代重新从 a[1]、b[1] 开始，缓存里却是高编号的元素，又全部未命中。 

for (i := 1; i < 1000000; i++)
    for (j := 1; j < 10; j++)
        a[i] *= b[i]

交换内外层循环后，计算的东西完全一样：读 b[i]、写 a[i]，在同样的数据上重复 10 次。第一次访问未命中，后面九次数据都在缓存里；把对这对 a、b 值的计算全做完，再去下一对。好处是把数据装进缓存后尽可能多地用它，而不是对每个数据做一点，扫一遍，再回来扫一遍又做一点。它的缓存行为好得多，很可能快 10 倍以上。

编译器能做这个优化，叫循环交换（loop interchange）。在这个例子里很容易看出交换是合法的，编译器也能判断出来。但实现它的编译器不多，因为一般来说判断能否交换循环的顺序并不容易，通常要程序员自己意识到需要这样做来提高性能。

七、结论

  • 寄存器分配是编译器的"必备"功能：中间代码用了太多临时变量，而且它对性能影响很大。
  • 对 CISC 机器，寄存器分配更复杂。
