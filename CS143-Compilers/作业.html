作业与考试

课程项目：用 C++ 分四步写一个把 Cool 编译成 MIPS 汇编的完整编译器（flex 词法分析器、bison 语法分析器、语义分析器、代码生成器），外加一个做优化的加分作业；四次书面作业分别练正则与自动机、文法与语法分析、类型规则与代码生成、操作语义与 SSA；期中和期末考试

一、总体安排

成绩：四次书面作业共 10%（各 2.5%），四次编程作业共 50%（PA1、PA2 各 10%，PA3、PA4 各 15%），期中 15%，期末 25%。书面作业在 Gradescope 上交 PDF，课程提供 LaTeX 模板；编程作业在斯坦福的 myth 机器上做，用课程提供的 pa_fetch 取起始代码、make submit 提交，整个学季共有三天迟交额度。

编程作业可以一个人做也可以两人一组。各阶段是"即插即用"的：每个阶段都有参考实现（lexer、parser、semant、coolc），做某一阶段时，项目目录里其余阶段默认是指向参考实现的符号链接，可以拿自己的替换。评分时用参考实现的前面各阶段来测你这一阶段，所以就算前面做得不好，也不耽误后面。学术诚信方面，课件第一讲说可以用大模型帮自己读懂作业给的代码，但交上来的代码必须自己写。

二、PA1：词法分析器

用词法分析器生成器 flex 写 Cool 的扫描器：用合适的格式描述 Cool 的 token 集合，由 flex 生成识别 token 的代码。对应第三讲和第四讲。

flex 的规则文件

%{
Declarations
%}
Definitions
%%
Rules
%%
User subroutines
  • 声明和用户子程序两段是可选的，用来写 C 的声明和辅助函数。
  • 定义段给正则表达式起名字，比如 DIGIT [0-9]。
  • 最重要的是规则段：每条规则以一个正则表达式或定义开头，后面是输入匹配时要执行的 C 代码，比如把词素记进全局变量 cool_yylval、返回 token 编码。
  • flex 的消歧规则就是第四讲讲的那两条：多条规则都匹配时选匹配字符最多的（最长匹配），一样长时选文件里写在前面的。说明里的例子：规则 [0-9]+ 和 [0-9a-z]+，输入 2a 会走第二条。
  • 要根据之前遇到过的 token 做不同动作时（比如处理注释的结束符，要知道之前是否遇到过注释开头），可以用起始条件：%Start COMMENT 声明状态，BEGIN(COMMENT) 进入，<COMMENT> 开头的规则只在这个状态下生效；默认状态叫 INITIAL。

要做什么

  • 改 cool.flex：按 Cool 手册第 10 节和图 1，为 cool-parse.h 里定义的每种 token 写规则，返回正确的 token 类型，在需要时记录词素的值（比如 BOOL_CONST 要记是真是假，TYPEID 要记类型名；关键字只返回类型就够了）。
  • 改 test.cl：写能充分测试扫描器的输入。说明特别强调不要轻视这一点，好的测试输入很难造，忘了测某样东西是丢分最常见的原因，评分会看测试文件的覆盖程度。
  • 扫描器要健壮，对任何可以想象的输入都能工作，比如字符串或注释中间遇到 EOF、字符串常量过长；致命错误也要得体地结束，不能有核心转储或未捕获的异常。评分时输出要和参考扫描器完全一致。

错误处理

所有错误都交给语法分析器，词法分析器自己不打印任何东西：返回特殊的错误 token ERROR，错误信息放在 cool_yylval.error_msg 里（小写的 error 是 PA2 里语法分析器用的，这里不管）。具体要求：

  • 遇到不能开始任何 token 的非法字符，返回只含这个字符的错误串，从下一个字符继续。
  • 多行字符串报告行号时用最后一行，一般地行号取 token 结束的那一行，这样实现简单。
  • 字符串太长报 "String constant too long"；含有空字符报 "String contains null character"；含有未转义的换行报 "Unterminated string constant"。只报一个字符串里最先出现的错误，然后从字符串末尾之后继续：有未转义换行时，末尾是下一行的开头；否则是结束的引号之后。
  • 文件结束时注释还没关，报 "EOF in comment"，不要因为缺了结束符就把注释内容当 token 扫；字符串同理，报 "EOF in string constant"。
  • 在注释外看到 *)，报 "Unmatched *)"，而不是扫成 * 和 )。
  • 这个阶段只捕捉很有限的一类错误，不要检查不属于词法的错误，比如变量是否先声明后使用。

其他要点

  • 字符串表：程序里同一个词素常出现很多次，为了省时间和空间，编译器通常把词素存在字符串表里，课程提供了实现。Object、Int、Bool、String、SELF_TYPE、self 这些特殊标识符在扫描器里和普通标识符一样处理，它们的问题要到后面的阶段才出现。整数字面量不检查是否超出表示范围，直接把整个文本存成一个 Symbol。
  • 字符串里的转义要转换成实际的值，比如输入的八个字符 "ab\ncd" 返回的是五个字符，中间是真正的换行符。字符串里出现字面的空字符要报错，但两个字符 \0 是允许的，转换成数字字符 0。
  • 维护变量 curr_lineno，记录当前扫描的行号，方便语法分析器打印有用的错误信息。
  • 词法规格必须完整，每一种可能的输入都要有正则表达式匹配，否则 flex 生成的扫描器会做出不希望的事。
  • 测试：make lexer 后运行 ./lexer test.cl，它打印识别出的每个 token 的行号和词素，和参考扫描器的输出比较；觉得没问题了，用 mycoolc 把你的扫描器和课程提供的其余阶段接起来，就是一个完整的 Cool 编译器。

三、PA2：语法分析器

用语法分析器生成器 bison 和一个操作树的包，写 Cool 的语法分析器，输出抽象语法树（AST），AST 用 bison 的语义动作构造。对应第五讲到第八讲，尤其是第六讲的语义动作和第八讲的 LALR 与冲突。

  • 改 cool.y：声明段基本已写好，但要给新引入的非终结符加类型声明，可能还要加优先级声明；规则段很不完整，给出的部分规则也别假设是完整的。
  • 改 good.cl 和 bad.cl：good.cl 要覆盖文法的每一种合法结构，bad.cl 要在一个文件里覆盖尽量多种语法错误。
  • 用 myparser 运行，它把语法分析器和扫描器接起来，-p 选项打印分析器的大量调试信息。bison 会把 LALR(1) 分析表以人能读的形式输出到 cool.output，调试时有时很有用。默认用参考扫描器，评分也用参考扫描器；别假设扫描器（无论谁的）没有 bug，潜伏的扫描器 bug 会让分析器出现莫名其妙的问题。
  • 对能成功分析的程序，输出 AST 的列表，AST 的根（也只有根）的类型是 program；有错误的程序输出错误信息，用课程提供的报错例程，不要修改，也不要在语义动作里直接调用，bison 发现问题时会自动调用。多行结构的行号可以取其中任一行。

错误恢复

用 error 伪非终结符给分析器加错误恢复能力（第六讲的恐慌模式）。它不是万灵药，分析器还是可能完全糊涂。要拿满分，至少要能在这些情况下恢复：一个类定义里有错，但类正确地结束了、下一个类语法正确，分析器要能从下一个类定义重新开始；同样，要能从特征（feature）里的错误恢复，继续下一个特征；从 let 绑定里的错误恢复，继续下一个变量；从 {...} 块里某个表达式的错误恢复。

提示

  • 可以用优先级声明，但只能用于表达式。不要盲目使用，不要一遇到移进归约冲突就加优先级规则直到冲突消失（第八讲说过，这些声明其实是冲突消解，未必等于你想要的优先级）。
  • Cool 的 let 结构给语言带来了二义性，手册的规定是 let 表达式尽可能向右延伸。取决于文法的写法，这可能表现为涉及 let 产生式的移进归约冲突，可以用 bison 给产生式（而不只是运算符）设定优先级的功能解决。
  • mycoolc 用管道在各阶段之间传数据，分析器多打印一点东西都可能让语义分析器读不懂你输出的 AST，提交前一定要删掉所有打印。
  • 要给有属性的终结符和非终结符声明 bison"类型"，比如 %type <program> program。"类型"这个词有误导性，它其实是说这个非终结符的属性存在 union 的哪个成员里。声明错了几乎保证分析器不能工作。g++ 和 bison 的类型警告都要重视，忽略了程序可能会崩溃。

四、PA3：语义分析

实现 Cool 的静态语义：用 PA2 建的 AST 检查程序是否符合 Cool 规范，拒绝错误的程序；对正确的程序，收集代码生成需要的信息，输出带类型标注的 AST。对应第九讲和第十讲。这次作业的设计空间比前两次大得多，没有唯一正确的做法，但有错误的做法。

高层上要做的事：

  1. 看所有类，建立继承图。
  2. 检查继承图是否良构。
  3. 对每个类：遍历 AST，把所有可见的声明收集进符号表；检查每个表达式的类型是否正确；给 AST 标上类型。

要改的文件：cool-tree.h（给 AST 节点加声明，不改已有的）、semant.cc（主要实现，入口是 program_class 的 semant() 方法，里面有一个 ClassTable 的起头，用不用随意）、semant.h，以及 good.cl、bad.cl（这次不评分，但建议多写测试文件）。

要点

  • 遍历：AST 节点上的 dump_with_types 方法演示了怎样遍历 AST 并从中收集信息。对复杂树结构的递归遍历很重要，是组织 AST 上很多计算的自然方式。一次遍历叫一"遍"，大概至少需要两遍才能检查完。
  • 继承：继承图必须无环，一个简单办法是建出类型图再查环。Cool 对继承基本类有限制；继承一个没定义的类也是错误。起始代码里有所有基本类的定义，要把它们加进继承层次。建议分两步：先检查继承图良构（不良构可以打印错误后中止编译），再检查其他所有语义条件，知道继承图合法后，第二步容易得多。
  • 命名和作用域：语义检查器的一大块工作是管理名字，判断每次使用标识符时哪个声明有效。可以用课程提供的符号表。除了每个类里隐式绑定的 self，引入对象名的方式有四种：属性定义、方法形参、let 表达式、case 分支。还有方法名和类名。用了没有对应声明的名字是错误，但发现这种错误后不应中止编译。记住类、方法、属性都不必先声明后使用，想想这对分析有什么影响（第九讲的多遍）。
  • 类型检查：检查需要声明类型的地方声明了合法的类型（比如方法必须声明返回类型），并按类型规则验证每个表达式。表达式没有合法类型时，先打印带行号的、说明哪里错了的错误信息，语义分析阶段的错误一般很明显，要求给出有信息量的错误；然后尝试恢复、继续检查。要求能恢复，但不要求避免连锁错误，简单的办法是给不能定类型的表达式定为 Object（第十讲的方案一）。
  • 和代码生成器的接口：每个表达式节点的 type 字段必须设成类型检查器推出的类型的 Symbol，必须是 idtable 的 add_string 的结果；特殊表达式 no_expr 的类型设为预定义的 No_type。
  • 输出：错误程序输出错误信息，除了不良构的类层次，所有错误都要能恢复；继承层次良构时，要捕捉并报告程序里所有语义错误。错误信息不必和参考实现一字不差、顺序一样。正确的程序输出带类型的 AST，评分看类型标注是否正确、能否和参考代码生成器一起工作。用 mysemant 运行，-s 打开调试变量。

说明里说参考解大约是 1300 行文档完善的 C++，是到目前为止最大的组件。动手前花点时间设计会容易很多，对 Cool 的每个方面问自己：要检查哪些要求？什么时候检查？检查需要的信息什么时候产生？信息在哪里？

五、PA4：代码生成

实现 Cool 的代码生成器，做完就有一个完整可用的 Cool 编译器了。代码生成器用 PA2 建的 AST 和 PA3 的语义分析结果，生成忠实实现任何正确 Cool 程序的 MIPS 汇编。代码生成阶段没有错误恢复，错误的程序都已被前端发现。对应第十一讲到第十三讲。说明提醒：代码量大约是上一次作业的两倍，早点开始。

写出正确的代码生成器，关键是彻底理解两样东西：Cool 结构的预期行为，由 Cool 手册第 13 节的操作语义规定（它只规定语言结构的意义，不规定怎样实现）；运行时系统和生成代码之间的接口，见 Cool 运行时手册。还要读 SPIM 手册了解要输出的代码格式。

要做的事

  1. 确定并输出全局常量，比如原型对象（prototype objects）。
  2. 确定并输出全局表，比如 class_nameTab、class_objTab 和分派表。
  3. 确定并输出每个类的初始化方法的代码。
  4. 确定并输出每个方法定义的代码。

一种合理的策略是分两遍：第一遍决定每个类的对象布局，特别是每个属性在对象里的偏移；第二遍递归地遍历每个特征，为每个表达式生成栈机器代码（第十二讲）。主要文件是 cgen.cc（入口是 program_class::cgen(ostream&)，提供了输出 MIPS 指令的函数、字符串整数布尔常量的骨架和一个类表 CgenClassTable 的骨架）、cgen.h、emit.h（输出 MIPS 指令的宏）、cgen_supp.cc。

  • 生成的代码必须和 Cool 运行时系统正确配合，运行时手册第 5 节有调用约定的重要信息。
  • 要清楚 Cool 程序的运行时语义。
  • 要了解 MIPS 指令集。
  • 要决定生成的代码遵守和依赖哪些不变量：哪些寄存器会被保存，哪些可能被覆盖，等等。
  • 不必生成和 coolc 一样的代码。coolc 有一个很简单的寄存器分配器和一些小改动，作业不要求，唯一的要求是生成的代码和运行时系统一起能正确运行。

运行时错误和垃圾回收

  • Cool 手册末尾列了六种会终止程序的错误。生成的代码要捕捉前三种：对 void 分派、对 void 做 case、case 没有匹配的分支，打印合适的错误信息后中止。除以零可以让 SPIM 去捕捉。子串越界和堆溢出由运行时系统的 trap.handler 负责。
  • 要拿满分，代码生成器必须和运行时系统里的分代垃圾回收器（第十七讲）正确配合。命令行选项 -g 打开回收（默认关闭），打开后回收器不只回收内存，还检查堆里所有对象之间都用 -1 隔开，以此发现程序（或回收器）是否意外写过了对象的末尾；-t 让回收器很频繁地回收（每次分配都回收）；-T 回收器不直接用，可以自由使用。最简单的开始方式是先不用回收器，决定用时仔细读运行时手册里的回收器接口，保证在所有情况下都和回收器正确配合并不容易。

调试

  • 用 mycoolc 运行，对 file.cl 生成 file.s；-c 打开调试变量。可以先用参考的前面几个阶段生成中间结果 ./lexer file.cl | ./parser | ./semant > file.semant，再在 gdb 里 run < file.semant 调试自己的 cgen。
  • SPIM 是汇编代码的解释器，不是真正的汇编器，这让调试变难：代码或数据定义引用了未定义的标号，只有执行到引用它的代码时才会报错，而且只报代码段里的未定义标号；常量数据定义里引用了未定义标号，SPIM 什么也不说，直接把它当 0。

六、PA5：优化（加分）

学季末一个有趣的开放项目：给编译器加优化。期末的分数曲线在计入加分之前确定，不做加分作业不会吃亏。做多少随意，按结果给分，只尝试而没完成优化阶段，可能一分都拿不到。coolc 没有优化阶段，所以没有骨架代码，建议先找助教谈谈，而且代码生成器做完之前绝对不要碰优化。不接受迟交。

  • 两个关键因素：正确性（优化不能让程序出错），以及相对 coolc 的加速比，用一组助教选的基准程序在 SPIM 上执行的指令数加权求和来衡量（用 spim 的 -keepstats 选项看执行了多少条指令）。
  • 如果初始代码生成器像 coolc 那样直接，两个可能收效显著的方向是：改进寄存器的使用（第十六讲），以及专门化基本类 Int 和 String 的实现。
  • -O 选项控制全局变量 cgen_optimize，评分时总是带 -O 运行。
  • 加分总共不超过课程总成绩的 6%，大约相当于两次大编程作业之一的一半。在 README 里简要描述你做的优化。

七、书面作业

书面作业可以和同学讨论、一起做，但答案要自己独立写，并注明和谁合作。下面只概括题目考什么，官方解答在课程网站上。

WA1：正则语言、有限自动机、词法分析

  • 对字母表 {0, 1}，为四种语言各写正则表达式和不超过 4 个状态的 DFA：以 110 结尾的串；0 少于三个的串；没有两个或更多连续 0 的串；作为二进制数是 3 的倍数的串（空串算 0）。最后一题提示先画 DFA，再看到达接受状态有哪些路径来构造正则表达式。
  • 对字母表 {a, b, c} 写 NFA：存在 i < j 使 w[i] = a、w[j] = b 的串（不超过 3 个状态）；某个字符出现奇数次的串（不超过 8 个状态）。
  • 用课上的方法（子集构造）把三个给定的 NFA 转成 DFA，并给出每个 DFA 状态对应的 NFA 状态集合。要注意 DFA 对每个状态和符号都必须有转移，NFA 不必，提示想想当前状态集没有显式转移时会转到哪个子集。
  • 给一个 flex 规格（三条规则分别打印 a、b、c），构造一个输入，使输出的词素序列恰好是 aacbbca。
  • 最长匹配的局限：构造不超过两条正则表达式和一个输入串，使这个串可以切分成每段都匹配某条规则的形式，但每步取最长匹配的常规算法却切不开，并解释原因。挑战：只用一条正则表达式。

WA2：上下文无关文法和语法分析

  • 为四种语言写 CFG：由 2、-、+ 组成、每个整数都是一位数且值非负的算术表达式；0 比 1 恰好多一个的 0、1 串；先 i 个 0、再 j 个 1、再 k 个 0，且 j = i + k 的串；由花括号、方括号、逗号定义的"集合"和"数组"互相嵌套的语言。
  • 判断一个只涉及变量 x 的 if-then-else 文法是否二义，是就画出两棵语法分析树，不是就解释原因（第五讲的悬空 else）。
  • 对一个文法提取左因子；对另一个文法消除左递归（第六、七讲）。
  • 对一个给定文法，算 First 集、Follow 集，构造 LL(1) 分析表，并给出分析串 "#a?ca?" 时栈、输入和动作的完整序列（第七讲）。
  • 对一个含 A → Ac | ε 和 B → Bc | ε 的文法：构造 LR(0) 自动机的第一个状态，算 A 和 B 的 Follow 集，指出使它不是 SLR(1) 的冲突；再修改这两条产生式，使文法成为 SLR(1) 而语言不变，并解释直觉（第八讲）。

WA3：语义分析、类型系统、代码生成

  • 补全 Cool 程序：一个被"撕坏"的程序有四处空白，每处只能填一个表达式（不能用块），使程序打印 "Cool compilers are Cool"，考的是动态分派和继承；另一个程序里有嵌套的 let 和 while，要在一处填一个表达式，让它打印给定的五行图案，或者说明为什么做不到，考的是 Cool 的作用域。
  • 类型推导：给出方法 test 开始时的环境 O 和 M（含 SELF_TYPE），对三个表达式各给出推出的类型和推导树。
  • 对同一个 Main，分析四个版本的类 A、B：能否通过类型检查？如果能，运行时会不会出错？要说明不满足的是哪条规则的哪个假设。四个版本的差别在 SELF_TYPE 用在属性、返回类型、new 的哪里，以及 set 方法最后有没有返回 self（第十讲）。
  • 扩展 Cool：为元组（固定长度、元素类型可以不同，元组类型之间按分量定义子类型）的创建和下标访问写类型规则；把"子类覆盖方法时参数和返回类型必须完全相同"的规则放宽，写出保证类型安全的新假设（提示：考虑参数和返回类型的方向）。
  • 在一个只有两个寄存器、指令带栈偏移的虚构栈机器上，写一段永不终止的代码，依次打印 1, 2, 6, 24, … 这些阶乘，不能硬编码常数（第十一、十二讲）。

WA4：代码生成、操作语义、优化

  • 在一个虚构体系结构上写汇编：两个 64 位寄存器 x、y，一个栈，指令有 push、pop、swap、加减乘除、按栈顶是否为零做相对跳转的 jz、print、halt。程序开始时 x 里是 1 到 19 之间的 n，要打印 1! 到 n!。课程在 myth 上提供了模拟器，可以加 --trace 打印每步的机器状态，通过助教的测试会打印一个秘密字符串，要写进答案里。
  • 一大题静态单赋值（SSA）形式，它是今天几乎所有产品级编译器（LLVM、GCC、V8、HotSpot 等）用的中间表示，比第十四讲讲的单赋值形式更进一步：每个变量在整个 IR 里只赋值一次，每次使用在静态上都在定义之后。题目一步步引导：先给没有汇合点的控制流图改名转成 SSA；判断给定 IR 里哪些使用违反"先定义后使用"；引入 φ 节点（控制从第 i 个前驱进入时取第 i 个参数）处理汇合点，判断哪些 φ 节点不合法；照一个简单但浪费的算法（新加入口块把所有变量设为 UNDEFINED，每个块开头给每个变量插 φ 节点，块内改名，最后填 φ 的参数）把一个带循环的 IR 转成 SSA；论证这个算法总能产生合法的 SSA；在 SSA 上做死代码消除；去掉不必要的 φ 节点，最后应剩四个。结尾提到实际编译器用的是 Cytron 等人 1989 年的快速 SSA 构造算法，快得多，插入的 φ 节点也少得多。
