第九讲：语义分析与类型检查（上）

主讲：Fredrik Kjolstad（2026 年春季）；录像主讲：Alex Aiken
资料来源：课件（2026 年 4 月 28 日）、录像第 9 周（09-01 Introduction to Semantic Analysis 到 09-09 Implementing Type Checking）

一、语义分析做什么

这一讲之后的周四是期中考试，范围到第八讲，可以带笔记，但不能用计算设备。

从"程序合不合法"的角度回顾一下：词法分析发现含有非法 token 的输入；语法分析发现语法树不合法的输入；语义分析是最后一个"前端"阶段，负责抓住其余所有错误。可以把这三个阶段看作三层过滤器，一层层拒掉更多的输入串，三层都过了，剩下的才是可以编译的合法程序。

为什么要单独的语义分析？有些错误语法分析抓不住，有些语言结构不是上下文无关的。这和从词法分析过渡到语法分析时很像：有限自动机做不了的事需要上下文无关文法，而上下文无关文法本身也不够。

coolc 做的检查包括：

  1. 所有标识符都已声明（并遵守作用域限制）。
  2. 类型。这是语义分析器的主要工作。
  3. 继承关系合理。
  4. 每个类只定义一次。
  5. 一个类里的方法只定义一次。
  6. 保留标识符没有被误用。

还有别的。具体要求取决于语言，coolc 做的这些是静态类型面向对象语言的典型检查，别的语言家族会有不同的检查。

二、作用域

作用域要解决的问题是把标识符的声明和使用对应起来：如果变量 x 在程序里可能有不止一个定义，说 x 时指的是哪一个？这是大多数语言里一个重要的静态分析步骤，Cool 也是。 

let y : String <- "abc" in y + 3

y 的这次使用对应到声明为 String 的那个 y，于是编译器会报错：把字符串和数相加。 

let y : Int in x + 3

声明了 y 却没用，这本身不是错误（可以给一个警告）。问题是用了 x，而这里看不到 x 的定义；如果外面也没有，就会报"未声明的变量"。课件注明：这是一个不是上下文无关的性质的例子。

标识符的作用域是程序中能访问这个标识符的那部分。同一个标识符在程序不同部分可以指不同的东西，但同一名字的不同作用域不重叠，在程序的任一处，x 只能指一样东西。标识符的作用域可以是受限的。

静态作用域和动态作用域

今天的大多数语言是静态作用域的，Cool 也是：作用域只取决于程序文本，和运行时行为无关。也有少数语言是动态作用域的，作用域取决于程序的执行。历史上 Lisp 是动态作用域的，很早以前改成了以静态作用域为主；SNOBOL 也是，现在基本只有历史意义。Aiken 说两者孰优孰劣争论过很久，今天看来静态作用域一方已经赢了。 

let x : Int <- 0 in
{
    x;
    let x : Int <- 1 in
        x;
    x;
}

按最近嵌套规则，变量绑定到包围它的、同名的最近的定义：第一个和第三个 x 在内层 let 外面，指外层定义，值是 0；中间那个 x 指内层定义，值是 1。

动态作用域下，变量指的是程序执行中最近的那次绑定： 

g(y) = let a <- 4 in f(3);
f(x) = a;

f 可以写在代码里完全不同的地方，和 g 不在同一个语法作用域里。按动态作用域，f 里的 a 指的是 g 里定义的 a，f(3) 返回 4。具体怎样实现，要等讲了语言实现的细节之后再说。

Cool 的作用域规则

Cool 里引入标识符绑定的地方：

  • 类声明（引入类名）。
  • 方法定义（引入方法名）。
  • let 表达式、形式参数、属性定义、case 表达式的分支（都引入对象标识符）。

不是所有标识符都遵守最近嵌套规则。一个大例外是类定义：不能嵌套，在整个程序里全局可见，只要在任何地方定义了，在所有地方都能用，所以类名可以先用后定义： 

class Foo {
    ... let y : Bar in ...
};

class Bar {
    ...
};

属性名在定义它的类里是全局的，也可以先用后定义： 

class Foo {
    f() : Int { a };
    a : Int <- 0;
};

通常属性写在方法前面，但这不是必需的，类里的属性和方法可以按任意顺序写。方法名的规则更复杂：方法不一定定义在使用它的类里，可以定义在某个父类里；方法还可以被重新定义（覆盖）。这些规则要等后面有了合适的语言才能说清楚。

三、符号表

在 AST 上递归处理

Aiken 先介绍一个通用算法，课程剩下的部分会反复见到它的各种实例：很多语义分析和代码生成都可以表达为对 AST 的递归下降遍历。每到一个节点 n：

  • 之前：处理节点 n。
  • 递归：处理 n 的孩子。
  • 之后：完成对 n 的处理。

有的算法只在处理孩子前做事，有的只在之后做事，有的两样都做。对 AST 的一部分做语义分析时，需要知道哪些标识符已经定义。

例子：let x : Int <- 0 in e，let 绑定的作用域是 AST 的一棵子树，x 在子树 e 里有定义。从父节点来到 let 节点时，有一组当前可见的符号放在旁边的数据结构里，那就是符号表。先处理初始化表达式（把符号表传下去）；处理 e 之前，把 x 的定义加进当前定义，覆盖外面任何别的 x 的定义；递归处理 e；处理完 e 回来后，删掉 x 的定义，恢复原来的 x。离开这棵子树后，可见的符号和进来之前完全一样。

符号表就是记录标识符当前绑定的数据结构。

用栈实现

最简单的符号表就是一个栈，三个操作：

  • add_symbol(x)：把 x（以及它的类型等信息）压栈。
  • find_symbol(x)：从栈顶往下找第一个 x。这自动处理了遮蔽：栈里有 x、y、z，进入一个引入新 y 的作用域，把 y 压在顶上，再找 y 就先找到新的这个。
  • remove_symbol()：离开作用域时弹栈，恢复进入前的状态，再找 y 就找到外层的那个。

这对 let 很合适，因为符号一次加一个，而且声明是完美嵌套的，这就是能用栈的全部理由：三层嵌套的 let，从根往下走时按 x、y、z 的顺序压栈，处理完往回走时正好按相反的顺序遇到这些作用域，弹栈的顺序恰好是要删除的顺序。

但对另一些结构就不够好。比如一个方法有两个都叫 x 的参数，这是非法的，因为两者在同一个作用域里定义。方法一次往同一个作用域里引入多个名字，只能一次加一个名字的栈不好表达"同时定义"。

作用域的栈

稍微复杂一点的符号表就能解决：结构是作用域（映射）的栈，每个作用域里是在同一层定义的所有变量。五个操作：

  • enter_scope()：开始一个新的嵌套作用域。
  • find_symbol(x)：找到当前的 x，没有就返回 null。
  • add_symbol(x)：把 x 加到当前作用域（栈顶的那个）。
  • check_scope(x)：x 恰好在栈顶的作用域里定义过时返回 true。用来检查重复定义：加第二个 x 之前问一下，返回 true 就报"x 重复定义"。
  • exit_scope()：退出当前作用域。

课程项目会提供一个实现了这个接口的符号表管理器，不想自己写可以直接用。

类名需要多遍

类名可以先用后定义，所以不能用符号表、甚至不能在一遍里检查类名：不读到程序末尾，就不知道是否已经看到了所有类定义。办法是分两遍：第一遍收集所有类名，第二遍检查类的主体只用了定义过的类。

要点是语义分析需要多遍，很可能不止两遍。Aiken 建议，在组织编译器时不要怕加很多简单的遍，如果这让事情更容易的话。把一件事拆成三四个简单的遍，比一个所有代码纠缠在一起的复杂的遍好得多，调试起来容易得多。

四、类型

类型是什么？这个概念因语言而异。大致的共识是：一个值的集合，以及（也许更重要的）在这些值上定义的一组操作。整数可以加减、比较大小；字符串可以连接、判断是否为空。这些操作不同，不应该混用，对整数做字符串操作只会得到无意义的结果。

类是现代"类型"概念的一种具体形式。在 Cool 里，类名就是类型，只有一个例外 SELF_TYPE。Aiken 提醒，类和类型其实是两回事，只是很多面向对象语言恰好把它们等同起来；有的设计里类不是唯一的类型，有的语言根本没有类的概念。

为什么需要类型系统

add $r1, $r2, $r3

这条汇编把 r2 和 r3 的内容相加放进 r1。$r1、$r2、$r3 是什么类型？这是个刁钻的问题：在汇编层面看不出来，它们只是一些装着 0 和 1 的寄存器，可以代表任意类型，add 照样把它们加起来，即使毫无意义。

两个整数相加有意义，得到表示它们之和的位模式；在 C 里把函数指针和整数相加没有意义，也能得到一串新的位，但没有任何有用的解释。问题是这两种操作的汇编实现完全一样，在汇编层面无法区分。

语言的类型系统规定哪些操作对哪些类型合法。类型检查的目的是保证操作只用在正确的类型上，以此强制值按照预期的方式被解释，因为再没有别的东西会检查了：到了机器码层面，一切都是 0 和 1，机器乐意对它们做任何你让它做的操作。

三类语言

  • 静态类型：所有或几乎所有类型检查在编译时完成，如 C、Java、Cool。
  • 动态类型：几乎所有类型检查在程序运行时完成，如 Scheme、Lisp，录像里还提到 Python、Perl。
  • 无类型：完全不做类型检查，如机器码，它没有类型概念，执行时不强制任何抽象边界。

类型之争

关于静态和动态类型孰优孰劣，争论了几十年。Aiken 不站队，只列出双方的说法：

  • 静态类型的支持者：静态检查在编译时就抓住很多编程错误，证明某些错误永远不会发生；避免了运行时类型检查的开销，因为一次性在编译时检查过了，运行时做操作前不用再查参数类型。这两点都确实成立。
  • 动态类型的支持者：静态类型系统有限制性，它要证明程序类型正确，靠的是限制你能写的程序，有些程序编译器很难证明正确，在静态类型语言里就很难写；在静态类型系统里很难快速做原型，探索想法时你可能还不知道所有类型是什么，却被要求写出对所有情况都类型正确的程序，这会拖慢工作。

实际情况：静态类型语言里写的代码很多，而实用的静态类型语言总有某种逃生机制，比如 C、C++、Java 的不安全转换。C 里不安全转换可能导致运行时崩溃，Java 里失败的向下转换会在运行时抛出未捕获的异常，效果都是可能因为类型原因出现运行时错误。另一边，动态类型语言流行到一定程度，就有人想给它写优化编译器，而优化编译器首先想要的就是类型信息，因为它有助于生成好得多的代码，于是人们回头想办法从这些语言里得到尽可能多的类型，有的语言还支持"pragma"或"advice"这样的类型声明。Aiken 说，这两种妥协到底是两全其美还是两头吃亏，很有争议，但这就是今天的现状。课件问了一句：为什么没有人人都喜欢的静态类型系统？

Cool 的类型

Cool 是静态类型的，类型是类名和 SELF_TYPE（下一讲专门讲）。用户给标识符声明类型，编译器推导表达式的类型，而且给程序里每个表达式都推出一个类型：它遍历整棵 AST，用标识符的声明类型算出每个表达式和子表达式的类型。

两个术语：类型检查是验证一个已经完全标好类型的程序，AST 每个节点都有类型，只需看每个节点和邻居，确认类型正确；类型推导是填补缺失的类型信息，AST 上没有类型或者只在声明处有几个，要把缺的填上。两者不同，在很多语言里差别很大，但人们常常混用，Aiken 说他在录像里也不会特别区分。

五、推理规则

已经见过两种用来规定编译器部分功能的形式记号：词法分析用正则表达式，语法分析用上下文无关文法。类型检查合适的形式是逻辑推理规则，形式是"如果假设为真，则结论为真"。类型检查的典型推理就是："如果 E1 和 E2 有某种类型，那么 E3 有某种类型。"推理规则是写这类"如果……那么……"陈述的紧凑记号。没见过的话一开始会觉得陌生，练一练就很好读。

构件：$\wedge$ 表示"并且"，$\Rightarrow$ 表示"如果……那么……"，$x : T$ 表示"x 的类型是 T"。

"如果 e1 的类型是 Int 并且 e2 的类型是 Int，那么 e1 + e2 的类型是 Int"一步步变成：

$$(e_1 : \text{Int} \wedge e_2 : \text{Int}) \Rightarrow e_1 + e_2 : \text{Int}$$

这是 $\text{Hypothesis}_1 \wedge \cdots \wedge \text{Hypothesis}_n \Rightarrow \text{Conclusion}$ 的特例，就是一条推理规则。现代的写法是把假设写在横线上面，结论写在下面：

$$\frac{\vdash \text{Hypothesis} \quad \cdots \quad \vdash \text{Hypothesis}}{\vdash \text{Conclusion}}$$

$\vdash$ 读作"可以证明"：如果能证明所有假设成立，就能证明结论成立。Cool 的类型规则的假设和结论都是 $\vdash e : T$ 的形式。

头两条规则

$$\frac{i \text{ 是整数字面量}}{\vdash i : \text{Int}}\ [\text{Int}] \qquad \frac{\vdash e_1 : \text{Int} \quad \vdash e_2 : \text{Int}}{\vdash e_1 + e_2 : \text{Int}}\ [\text{Add}]$$

这些规则是模板：Int 规则用一个泛指的整数 i，不是每个整数一条规则；Add 规则对任意满足假设的 e1、e2 都适用。往模板里填，就能得出具体表达式的完整类型推导。比如 1 + 2：1 是整数字面量，所以 $\vdash 1 : \text{Int}$；2 同理；两个假设都有了，所以 $\vdash 1 + 2 : \text{Int}$。

可靠性

如果每当 $\vdash e : T$ 时，e 求值得到的都是 T 类型的值，就说类型系统是可靠（sound）的：类型系统给出的类型反映了实际运行程序时得到的值的种类。我们只要可靠的规则，但有些可靠的规则比别的好。比如

$$\frac{i \text{ 是整数字面量}}{\vdash i : \text{Object}}$$

也是可靠的，Cool 里每个整数也都是对象，但这没什么用，你没法再对它做整数操作。对一种表达式往往有很多条可靠的规则，我们要的是最具体的那条。

类型检查证明的形状

类型检查证明的是 $e : T$ 这样的事实。证明建立在 AST 的结构上，形状和 AST 一样，每个 AST 节点用一条类型规则。节点 e 用的那条规则里，假设是 e 的子表达式的类型证明，结论是 e 的类型。证明树的根画在最下面，AST 的根通常画在最上面，但两者是一一对应的。所以类型是在 AST 上自底向上一遍算出来的：先给叶子定类型，再一层层往根走。

更多规则

$$\frac{}{\vdash \texttt{false} : \text{Bool}}\ [\text{False}] \qquad \frac{s \text{ 是字符串字面量}}{\vdash s : \text{String}}\ [\text{String}] \qquad \frac{}{\vdash \texttt{new}\ T : T}\ [\text{New}]$$

new T 产生一个 T 类型的对象（暂时忽略 SELF_TYPE）。

$$\frac{\vdash e : \text{Bool}}{\vdash \texttt{not}\ e : \text{Bool}}\ [\text{Not}] \qquad \frac{\vdash e_1 : \text{Bool} \quad \vdash e_2 : T}{\vdash \texttt{while}\ e_1\ \texttt{loop}\ e_2\ \texttt{pool} : \text{Object}}\ [\text{Loop}]$$

while 循环：条件 e1 必须是 Bool，循环体 e2 可以是任意类型（但必须能定出某个类型），整个表达式的类型是 Object。Aiken 解释这是一个设计决定：本可以让 while 的类型是 T、值是最后一次执行循环体的值，但如果第一次进循环时条件就是假，循环体一次也不执行，就没有值，得到 void，有人去解引用就会出运行时错误。为了不让程序员依赖循环产生有意义的值，就把它定为 Object。

六、类型环境

问题来了：一个变量引用 x 的类型是什么？

$$\frac{x \text{ 是变量}}{\vdash x : ?}\ [\text{Var}]$$

只看 x 本身，这条局部的、结构性的规则没有足够信息给 x 定类型。推理规则要求所有信息都是局部的，执行规则需要的一切都必须编码在规则里，没有外部数据结构。解决办法是往规则里放更多信息。

类型环境给自由变量提供类型。一个变量在一个表达式里是自由的，如果它不是在这个表达式内部定义的：x 在表达式 x 里是自由的；x 和 y 在 x + y 里都是自由的；在 let y ... in x + y 里，y 由表达式内部的声明约束，是约束变量，只有 x 是自由的。要我类型检查一个有自由变量的表达式，你就得告诉我这些变量的类型。

类型环境是从对象标识符到类型的函数。设 O 是一个类型环境，

$$O \vdash e : T$$

读作：在 e 的自由变量具有 O 给出的类型的假设下，可以证明 e 的类型是 T。这个记号把假设（转门左边，是输入）和要证明的东西（右边）清楚地分开了。

所有规则都要加上环境。整数字面量的规则里，O 不影响结果；加法规则里，e1 和 e2 可能含有自由变量，要用同一个 O 去查：

$$\frac{i \text{ 是整数字面量}}{O \vdash i : \text{Int}}\ [\text{Int}] \qquad \frac{O \vdash e_1 : \text{Int} \quad O \vdash e_2 : \text{Int}}{O \vdash e_1 + e_2 : \text{Int}}\ [\text{Add}]$$

变量的问题现在很简单，到 O 里查：

$$\frac{O(x) = T}{O \vdash x : T}\ [\text{Var}]$$

let

$$\frac{O[T_0/x] \vdash e_1 : T_1}{O \vdash \texttt{let}\ x : T_0\ \texttt{in}\ e_1 : T_1}\ [\text{Let-No-Init}]$$

$O[T/y]$ 表示把 O 在点 y 上修改为返回 T 的函数，记法是"在 O 里，T 是 y 的类型"：对 y 返回 T，对其他变量返回 O 原来给的类型。这条规则说：在 O 的基础上把 x 的类型改成 T0，在这个环境里检查 e1，得到的类型就是整个 let 的类型。注意 let 规则强制了变量的作用域：检查 e1 之前要往假设里加上 x，检查完 e1 离开时要去掉这个新假设，因为 let 外面只有原来的 O。这听起来很熟悉，类型环境实际上就是用符号表实现的，规则里的类型环境承载的就是编译器里通常存在符号表里的信息。

  • 类型环境给出当前作用域里自由标识符的类型。不知道自由标识符的类型，谈表达式的类型检查都没有意义。
  • 类型环境沿 AST 从根往叶子传，经过 let 这样的定义时会被扩展。
  • 类型沿 AST 从叶子往根算。叶子大多很简单，常量有明显的类型，变量到环境里查。

七、子类型

带初始化的 let：

$$\frac{O \vdash e_0 : T_0 \quad O[T_0/x] \vdash e_1 : T_1}{O \vdash \texttt{let}\ x : T_0 \leftarrow e_0\ \texttt{in}\ e_1 : T_1}\ [\text{Let-Init}]$$

顺带注意：e0 是在 O 里检查的，新的 x 在 e0 里不可见，如果 e0 用了 x，那是 let 外面定义的另一个 x。课件问：这条规则为什么弱？它要求 e0 的类型和 x 完全一样，可是 e0 的类型是 T0 的子类型也完全没问题，T0 类型的变量能装下 T0 任何子类型的值。

在类上定义关系 $\le$：

  • $X \le X$（自反）。
  • 如果 X 继承自 Y（代码里写了 X inherits Y），则 $X \le Y$。
  • 如果 $X \le Y$ 且 $Y \le Z$，则 $X \le Z$（传递）。

改进后的规则：

$$\frac{O \vdash e_0 : T_0 \quad O[T/x] \vdash e_1 : T_1 \quad T_0 \le T}{O \vdash \texttt{let}\ x : T \leftarrow e_0\ \texttt{in}\ e_1 : T_1}\ [\text{Let-Init}]$$

T 是 x 声明的类型，e0 的类型只需是它的子类型。两条规则都是可靠的，用第一条能编译通过的程序都能正确运行，但用第二条能通过类型检查的程序更多，它更宽松而仍然正确。

赋值和属性初始化

$$\frac{O(x) = T_0 \quad O \vdash e_1 : T_1 \quad T_1 \le T_0}{O \vdash x \leftarrow e_1 : T_1}\ [\text{Assign}]$$

左边是变量，右边是表达式，求出右边的值赋给左边。先在环境里查 x 的类型 T0，在同一环境里检查 e1 得到 T1（变量集合不变），要求 x 能装下 T1 类型的值，即 $T_1 \le T_0$。

属性初始化除了名字的作用域，和赋值很像。设对类 C 中声明的所有属性 x : T，都有 $O_C(x) = T$：

$$\frac{O(x) = T_0 \quad O_C \vdash e_1 : T_1 \quad T_1 \le T_0}{O \vdash x : T_0 \leftarrow e_1;}\ [\text{Attr-Init}]$$

初始化表达式在特殊环境 $O_C$ 里检查，它只含类 C 里声明的所有属性的类型，因为属性的初始化表达式可以引用这个类的任何属性。所以要先扫一遍类定义，取出所有属性名和类型，建好环境，再检查初始化表达式。

if-then-else 和最小上界

if e0 then e1 else e2 fi 的结果可能是 e1 也可能是 e2。类型检查时不知道会走哪个分支，而且这个表达式在一次运行中可能执行很多次，有时走 e1，有时走 e2。所以它的类型是 e1 的类型或 e2 的类型，编译时不知道是哪个，最好的办法是取比两者都大的最小的超类型。

最小上界 $\text{lub}(X, Y) = Z$，如果

  • $X \le Z \wedge Y \le Z$：Z 是一个上界；
  • $\forall Z'.\ X \le Z' \wedge Y \le Z' \Rightarrow Z \le Z'$：Z 是所有上界里最小的。

在 Cool 和大多数面向对象语言里，两个类型的最小上界就是它们在继承树里的最近公共祖先。继承树以 Object 或类似的类为根，要找两个类型的 lub，就沿树往回走，直到找到它们的最近公共祖先。

$$\frac{O \vdash e_0 : \text{Bool} \quad O \vdash e_1 : T_1 \quad O \vdash e_2 : T_2}{O \vdash \texttt{if}\ e_0\ \texttt{then}\ e_1\ \texttt{else}\ e_2\ \texttt{fi} : \text{lub}(T_1, T_2)}\ [\text{If-Then-Else}]$$

if 不引入也不移除变量，所有子表达式都在同一环境里检查。条件必须是 Bool；两个分支必须能通过类型检查，但类型可以是任何类型；整体的类型是两者的 lub，这是在 true 分支可能返回 T1、false 分支可能返回 T2 时能给出的最好估计。

case

$$\frac{O \vdash e_0 : T_0 \quad O[T_1/x_1] \vdash e_1 : T_1' \quad \cdots \quad O[T_n/x_n] \vdash e_n : T_n'}{O \vdash \texttt{case}\ e_0\ \texttt{of}\ x_1 : T_1 \Rightarrow e_1; \ldots; x_n : T_n \Rightarrow e_n;\ \texttt{esac} : \text{lub}(T_1', \ldots, T_n')}\ [\text{Case}]$$

case 是加强版的 if-then-else。它先求 e0，看 e0 的运行时类型（动态类），在所有分支里挑声明类型是这个运行时类型的超类型、而且是其中最小的那个分支，把 x 绑定到 e0 的值、类型当作该分支声明的类型，执行那个分支。类型检查时：检查 e0；每个分支在把 $x_i$ 扩展为类型 $T_i$ 的环境里检查，得到 $T_i'$；不知道运行时哪个分支会匹配，所以整体类型是所有分支类型的 lub（把二元的 lub 推广到 n 元）。

八、方法

方法调用 $e_0.f(e_1, \ldots, e_n)$ 的类型检查有一个问题：检查 e0 和所有实参都能得到类型，但返回类型是什么？和变量引用一样，只有名字 f，不知道 f 的任何信息，就说不出它返回什么类型的值。

Cool 里方法标识符和对象标识符在不同的名字空间里：同一作用域里可以同时有方法 foo 和对象 foo，它们的用法差别足够大，不会混淆。所以实际上 Cool 有两个环境。类型规则里用一个单独的映射 M 记录方法的签名（输入和输出类型）：

$$M(C, f) = (T_1, \ldots, T_n, T_{n+1})$$

表示类 C 里有方法 $f(x_1 : T_1, \ldots, x_n : T_n) : T_{n+1}$，前 n 个是参数类型，最后一个是返回类型。

分派规则

$$\frac{O, M \vdash e_0 : T_0 \quad O, M \vdash e_1 : T_1 \quad \cdots \quad O, M \vdash e_n : T_n \quad M(T_0, f) = (T_1', \ldots, T_n', T_{n+1}) \quad T_i \le T_i' \ (1 \le i \le n)}{O, M \vdash e_0.f(e_1, \ldots, e_n) : T_{n+1}}\ [\text{Dispatch}]$$

检查 e0 和所有实参；到类 $T_0$（e0 的类）里查 f，必须有参数个数对的签名；每个实参的类型必须是对应形参类型的子类型；都满足的话，整个调用的类型是方法的返回类型 $T_{n+1}$。

静态分派

静态分派是普通分派的变体：语法上程序员写出类名 e0@T.f(...)，运行的是 e0 的类的某个祖先类 T 里的 f，不是 e0 所属类里的 f。推出的 e0 的类型必须符合指定的类型：

$$\frac{O, M \vdash e_0 : T_0 \quad \cdots \quad O, M \vdash e_n : T_n \quad T_0 \le T \quad M(T, f) = (T_1', \ldots, T_n', T_{n+1}) \quad T_i \le T_i'}{O, M \vdash e_0@T.f(e_1, \ldots, e_n) : T_{n+1}}\ [\text{StaticDispatch}]$$

完整的环境

方法环境要加到所有规则里。这很容易，因为只有分派规则真正用到 M，其余规则只是把它原样从根往叶子传下去：

$$\frac{O, M \vdash e_1 : \text{Int} \quad O, M \vdash e_2 : \text{Int}}{O, M \vdash e_1 + e_2 : \text{Int}}\ [\text{Add}]$$

涉及 SELF_TYPE 的一些情况还需要知道表达式所在的类。所以 Cool 完整的类型环境是三样：给对象标识符类型的映射 O，给方法类型的映射 M，当前类 C。句子的形式是

$$O, M, C \vdash e : T$$

读作：在对象标识符具有 O 给出的类型、方法具有 M 给出的签名、表达式位于类 C 中的假设下，可以证明 e 的类型是 T。

这一讲的规则是 Cool 特有的，别的语言规则可能很不一样，但有几个共同的主题：类型规则定义在表达式的结构上，通常是归纳式的，表达式的类型取决于子表达式的类型；变量以及更一般的自由名字（比如方法名）的类型由环境建模。还有一点：类型规则很紧凑，记号不复杂，但信息量很大，要花时间仔细读才能真正明白它在说什么。

九、实现类型检查

Cool 的类型检查可以在对 AST 的一次遍历中实现，分两个方向：类型环境从父节点传给子节点（自顶向下），类型从子节点传回父节点（自底向上）。从根带着初始环境出发，递归地传到叶子，再从叶子开始用环境算出每个子表达式的类型，一路回到根。

加法规则怎样实现：写一个递归函数 TypeCheck，参数是一个环境（一个包含 O、M、C 三部分的记录）和一个表达式。几乎可以照着规则直接翻译成代码，这就是类型系统记号的好处之一，它很清楚地告诉你实现该怎么写： 

TypeCheck(Environment, e1 + e2) = {
    T1 = TypeCheck(Environment, e1);
    T2 = TypeCheck(Environment, e2);
    Check T1 == T2 == Int;
    return Int;
}

e1 在和 e1 + e2 相同的环境里检查，所以把环境原样传给递归调用，得到 T1，这时还不知道 T1 是不是 Int，先记下来；同样检查 e2；然后确认两者都是 Int（也可以检查完 e1 立刻查 T1，这里为了省篇幅写在一行）。检查失败时这里应该打印错误信息；成功就返回 Int。

带初始化的 let： 

TypeCheck(Environment, let x : T <- e0 in e1) = {
    T0 = TypeCheck(Environment, e0);
    T1 = TypeCheck(Environment.add(x : T), e1);
    Check subtype(T0, T);
    return T1;
}

e0 在原环境里检查；e1 在扩展了"x 的类型是 T"的环境里检查；检查 T0 是 T 的子类型，这要调用一个实现子类型关系的函数；通过就返回 T1，作为整个 let 表达式的类型。
