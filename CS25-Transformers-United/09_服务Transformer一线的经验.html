第九讲：服务 Transformer：一线的经验

推理为什么重要；三类应用与怎样定义工作负载和服务目标；效率受限与能力受限两种模型选择；vLLM、SGLang、TensorRT-LLM 等推理引擎；硬件与云端部署；可观测性与调试；推测解码、量化等性能优化，以及接下来会发生什么

主讲：Charles Frye（Modal）
资料来源：课堂录像（Stanford Online 公开，2026 年春季，本文依据录像字幕整理）

一、为什么关心推理

Charles Frye 在 Modal 工作，教人构建 AI 应用。他发表过精神药理学和神经生物学的研究，在 UC Berkeley 读博（他开玩笑说"别因此对我有成见"），论文研究神经网络优化；在 Weights & Biases、Full Stack Deep Learning 和 Modal，向数千人讲授 AI 应用开发的整个技术栈，从线性代数、GPU 的各种冷门细节到建立有护城河的业务。

他看了前面几讲（超大规模训练、状态空间模型），很多是关于能力和模型的生产，这很重要，是起点；但模型最终要被人使用，这是他这几年的工作。如果你一心想做训练，也许能了解训练中的选择对推理有什么后果；他也想说服大家推理同样有意思。他引了 swyx（Shawn Wang）最近的推文：做 AI 基础设施的人终于都发大财了，他还补充说不是性感的 AI 研究，就是无聊的基础设施；那是在 Modal 和另外几家公司宣布融资之后。推理有点像训练的弟弟。他给出的理由：

  • 对企业来说训练是成本中心而不是收入中心：投钱进去，出来一个模型，但没有好办法直接把权重变成钱，就像软件很难只卖一张装着软件的光盘，要围绕它构建系统，才能产生收入去继续做模型。即使只靠风投，投资人也想看到收入。这也意味着它会长期吸引大量资源，工程师有更多资源去解决问题。
  • 训练（尤其预训练）目前只有少数机构在做，有点像只有少数机构造芯片，大多数人在其上构建；推理则无处不在，做推理的人越来越多。
  • 现在做训练也要让模型生成输出、与世界交互，再用强化学习反馈回权重，这已经是训练栈的重要部分，可能比预训练用的 FLOP 还多（他说也许大家还没意识到），这需要高效推理，所以训练的人也必须关心这些。
  • 推理横跨整个技术栈：要想应用拿它做什么，要想线性代数、CuTe 的布局代数，还要想电子、热量和冷却，对真正的全栈工程师来说很好玩。
  • 一大波推理需求正在到来，既有对闭源厂商模型的需求，也有各种其他需求，工程师有很大机会高效地满足它。

他在 Modal 做推理基础设施约两年，之前在 Full Stack Deep Learning 讲怎样训练和部署模型，再之前做训练；最近在 Modal 内部关注 GPU 的指标、剖析和性能，也就是推理中真正见真章的地方。他既为自己的项目跑小语言模型服务，也和一批领先团队合作，在几百、几千块 GPU 的规模上部署和优化推理。他说和这个领域的一些人不同，他不想藏着这些知识，希望大家都知道，希望世界上有更多推理。这一讲是快速的全景之旅：应用（人们想做什么，分解为工作负载和服务目标）；组件（产生推理的模型和编排推理的引擎）；硬件（在这一代软件中比很多年代都更重要）；部署（目前主要在云和数据中心）；调试和可观测性；性能优化；以及他认为接下来会发生什么。

二、应用与工作负载

三类应用

他从基础设施的角度把 LLM 应用分成三类，主要是为了弄清服务它们的工程约束：

  • Chatbot plus：大家最熟悉的，目前两个杀手级应用 ChatGPT 和 Claude Code 都属于这类。另一端有人，有人的反应时间、人的延迟容忍度。叫 plus 是因为它不只是聊天，还用文本输出代表用户与其他计算机系统交互。
  • 后台 Agent：比如编程 Agent Devin、Ramp 的 Inspect（以及开源的 Open-Inspect）、OpenClaw。有人参与，可能写了提示中很多或最重要的 token，但不一定在等结果，比如开会时有人要求实现某个功能，就在聊天里标记 Devin 去实现并开 PR。没有交互式的人类延迟约束，只有几秒、几分钟乃至几小时量级的约束。
  • 数据处理器：原型是 Reducto 这类处理平台，比如为 Jmail 项目索引了 Jeffrey Epstein 的邮件，做成邮件界面。场景是处理 PDF、文档等非结构化数据，从中提取结构，下游是之后会被查询的存储系统（文件系统、数据库）。量大，延迟容忍度高，但和很多数据库和存储系统一样，写入很不均匀，稀疏期和高峰期交替。

定义工作负载

做产品的人和应用工程师这样想问题；做推理系统的人要在更低的层次思考，交接点是对工作负载的定义：会提交什么样的工作，应用对服务这些工作有什么约束。常说的 SLA（服务等级协议）、SLO（服务等级目标）描述了失败率、性能（速度）、成本等方面的约束和期望。他们和很多想构建 LLM 推理系统的客户合作，发现很难从客户那里问出工作负载的信息，于是在《LLM Engineer's Almanac》里做了一个类似填词游戏的小工具，让你选择要服务的模型、延迟和吞吐量方面的约束等，这大大缩短了很多原本困难的对话。关键是用一组指标定义工作负载：

  • 每秒查询数（QPS）：由用户决定，往往难以预测，做了东西不知道大家想不想用；还有很大的波动和季节性，很多人不考虑。平均流量与峰值流量之比越高，服务越难，要尽早弄清。
  • 每个查询的 token 数：预填充阶段的输入 token 数，解码阶段的输出 token 数。输出长度很烦人，不仅由用户决定，也由模型决定，因为模型决定什么时候输出结束 token，即使同样输入同样随机种子能做到确定，也很难推断，因为它来自统计模型。和数据库有点像，数据变了查询性能就变，很多时候只能靠经验测量，但这比估计 QPS 容易（QPS 取决于你有没有上 Hacker News 首页、有没有被网红转发）。
  • 前缀复用：进来的 token 序列有多少是之前见过的。这很重要，因为可以缓存之前的计算，大家在这上面做得很精细，尤其在交互性较低的场景，相当于把 GPU 计算变成从存储加载，对成本很有利，往往以延迟为代价。他主要在用户延迟容忍度较高时做激进的 KV 缓存。它主要由用户决定，但用户写的提示只有几十个 token，模型看到的提示有几千个，所以实际上由框架之类的软件系统决定，你可能有一定控制权，可以做得聪明或做得笨；他还开玩笑说，可以封禁那些用"疯狂的龙虾主题软件"把缓存搞爆的人。
  • 延迟预算：主要有两个，首 token 时间（TTFT，第一个 token 或第一个字节返回给用户要多久），以及每个输出 token 的时间（TPOT，或叫 token 间延迟）。末 token 时间也重要，但它很直接地依赖输出长度，通常把 TPOT 和输出长度分开推理，需要时再合起来。一旦有工具调用就全乱了，又要回到用实时数据凭经验测。延迟预算由应用决定，是区分三类应用的主要因素之一。除了批量数据处理，TPOT 等要按单个用户、单个请求来想，因为它由用户体验定义，要关心的是用户的体验而不是机器的体验。

还要按单个副本推理。整个系统有某个 QPS，比如有人会说"我预计有 1000 个并发用户，每几秒发一个查询"，推出总 QPS，这能告诉你总需求；但你大概会用多个副本（多台运行推理引擎的机器）来服务，每个副本在满足延迟预算、考虑前缀复用的前提下能承受一定数量的查询，然后增加副本直到满足总负载。这和数据库不同，数据库会尽量在 IPO 之前避免多副本，而推理各引擎之间基本独立，除了前缀缓存。

三类应用各自关心的指标：chatbot plus 关心交互性，即每个用户每秒的输出 token 数；后台 Agent 关心末 token 时间，因为那时才产出人在等的结果（PR、设计文档、生成的图像）；数据处理器关心处理速度，比如每美元多少百万 token，取决于按输入输出适当加权的总吞吐量。

怎样对单个副本做基准测试？最小延迟：一次一个地跑 $n$ 个查询，记录平均延迟的倒数，相当于每个用户独占一个副本时最快能多快；最大吞吐量：一次扔进 $n$ 个查询，记录 $n$ 除以总耗时，相当于所有请求同时到达，给引擎和硬件暴露最大并行度。最大吞吐量下总体完成更快，但每个请求耗时更长。中间的行为通过扫描不同的发送速率来测量。他说对系统或电子工程背景的人，可以把这看成测量系统的冲激响应。他还做了一个模拟 token 生成节奏的小工具，展示为什么关心 P95、P99 这类尾部延迟：保持中位数不变，只加大尾部，你可能觉得只有 1/20 或 1/100 的用户受影响，但这些指标通常是在单个序列、单个 token 的粒度上测的，所以即使中位数的 token 1 毫秒就出来，整体看起来还是一卡一卡的；用过很多推理服务商的人大概都见过这种难以控制的长尾。

三、模型与引擎

两类约束

他认为模型某种程度上也是工作负载的一部分，最好由应用开发者在 Jupyter 里跑 Transformers 版本的模型，决定应用需要什么样的模型质量。但选用什么模型是最重要的决定之一。他观察到两类约束，导致很不同的模型选择：

  • 效率受限：智能已经够用，模型训练者不难做出能解决这个任务的模型，之后成本就是主要驱动因素。这个领域开源模型通常占主导，闭源厂商并不追求这些工作负载。
  • 能力受限：现有最高的智能还不够，某种程度上也许永远不够。

他的类比：效率受限像显示器刷新率，到 60Hz 已经不错，100Hz 很棒，很少有人要 1000Hz；能力受限像内存，笔记本已经 64GB，Claude Code 和 Chrome 还在要更多。这是计算机系统不同部分出现的两类不同约束，认为只有一类重要是愚蠢的，虽然一些闭源实验室的人这么说。闭源模型主导能力受限的领域，很多人想加入那些实验室做推理；但他说开源模型的微调版本正在追上：前沿能力够用但不够理想时，对 DeepSeek V4 这样的模型做 RL，能力就上去了，也许效率也提高了，这只在最近三到六个月才真正成立。

效率受限时目标是性价比：高性能低成本，或以最低成本达到足够性能。现在通常每个副本一块 GPU，不错的模型在一百亿、几百亿参数量级，能放进常见加速器的显存；延迟预算很紧时才换成多块 GPU，多块 GPU 能把工作分到多条内存通道上，去掉一些延迟瓶颈。但这比较少见，因为这类工作负载多是数据处理器、后台 Agent 的子 Agent，很少是对人类交互延迟要求极高的 chatbot plus。例外也许是语音 Agent：打电话的人不需要和超级智能说话，但要在 100 毫秒内得到回答，这是效率受限场景中开始出现多 GPU 的情况。这类模型常是多模态输入、结构化输出：增加模态让模型获得更多信息，但如果要最高的智能，现在（至少开源模型）还是纯语言模型更好；目标通常是把非结构化信息变成结构化信息，这不需要拿 IMO 奖牌的智能。好消息是选择很多：Qwen、Nemotron、gpt-oss、Gemma、阶跃星辰的 Step、Mistral 等，每个都是模型家族，数据配比不同（偏编程或偏文本），大小不同，支持的模态不同，选择多到让人宠坏了。

能力受限时，模型质量很难达到，目前唯一的办法是把模型做得很大，有几个后果：基本总是每个副本多块 GPU，没人能用一块芯片的 HBM 装下万亿参数（他说 Cerebras 的芯片很大，不记得它的内存有多少）；还常常多节点，多个操作系统在不同机器上互相通信，延迟预算较高时更常见，预算越紧越希望计算和存储挨得近。这类场景常是 chatbot plus（ChatGPT、Claude 等）或后台 Agent 的编排者：用户输入一个提示，后台发生一连串事情，比如一个生成 PR 或做代码审查的 Agent，往往是多 Agent 系统，各有不同的技能和权限边界，最上面通常有一个负责一切的编排 Agent，它需要最高的能力，下面的可以用更快、能力较弱的模型做相似的任务；他说这和人类组织的相似之处留给读者自己体会。它们工具调用很多，因为智能不就是用来与世界交互的嘛，比较一下 Mycroft Holmes 和 Sherlock Holmes 就知道。它们不只是发出指令，还要执行、观察结果、继续交互，这意味着前缀命中率很高、很有用；工具调用的延迟（从毫秒到小时）也成为系统运行的重要组成部分。他的经验是，做这类应用的人通常先用闭源 API 开发，之后想更多地掌控推理，这时选择较少，大概是 DeepSeek、Kimi、GLM、MiniMax 各自最大、最新的那个；一旦开始微调，换模型就更受限，因为训练软件还不像推理引擎那样可移植。

他推荐 Artificial Analysis 来把握这个快速变化的领域：它的智能指数（智能当然很难定义，但它给出一个数字，和他的直觉判断相关，他就把它当作自己直觉的度量）对每百万 token 服务价格的图，他经常回来看。这个价格基于闭源推理服务商，他的经验是：只要有足够的负载填满硬件，达到这个价格中等难度，超过它难但不是不可能。现在做性能优化比一两年前容易，一个关键原因是有了极高质量的开源推理引擎。

推理引擎

推理引擎有几个组件：一个与外界通信的服务器进程，通常负责分词和反分词；分词很耗 CPU，在 Python 世界里通常用多个进程，反分词处理的是生成出来的 token，来得没那么快，所以通常只有一个或比分词器少得多的反分词进程。中间是 CPU 上的调度器进程，编排 GPU 上的所有工作。所有组件都重要，但瓶颈和关键是调度器：GPU 是协处理器，你给它工作，它稍后返回结果，要保证它一直有活干。他说这就是 PyTorch 的"道"：PyTorch 的 eager 模式之所以可行，是因为 GPU 在做一个 petaflop 的运算时，Python 慢悠悠地花一秒决定下一个跑哪个内核也没关系，只要在 GPU 做完之前决定好。CPU 和 GPU 之间的通用接口，对这些引擎来说就是 PyTorch。几个主要的开源选择：

  • TensorRT-LLM（NVIDIA，基于 TensorRT 运行时）：编译成 C++ 运行时，部署后基本都在 C++ 里，避免了 CPU 瓶颈，不需要那种"聪明"，因为代码本身就快（他说对 C++ 的朋友没有恶意）。小模型、小批量时仍是最好的选择，但通常不是首选。NVIDIA 是唯一的开发者，仍会在里面发布一些新技术，但对它的投入似乎在减少，转而支持开放的库。他认为这是 NVIDIA 的一贯做法：做软件来示范怎样用它的硬件，有人接手之后，它就回去卖芯片赚钱。
  • vLLM：采用最广，可以说是最早上市的、真正开放治理的开源项目，现在有点企业风格。它是 Linux 基金会下的开放治理项目，类似 Postgres 或 PyTorch，这影响你怎样参与以及它可能怎样发展。
  • SGLang：稍晚但也相当成熟，很有"要快"的气质，采用和支持者更偏创业公司。现在是开源但封闭治理，由一个非营利组织（由维护者组成）持有，创始团队中很多人分拆出了 RadixArk 创业公司。他觉得 SGLang 的工程文化极度注重性能，有无数个版本的 Docker 镜像和分支，各带一点小优化；vLLM 更多地把东西合进主线，没那么多疯狂的 hack。他还没发现强烈偏好其中一个的理由，两者都做得很好，作为使用者，多几个追求者是好事。

做服务不一定要自己写引擎，但要了解它们：mini-SGLang 和 nano-vLLM 有简单的实现，有助于学习架构；Aleksa Gordić 写过一篇很好的 vLLM 详解，他把它做成了 Modal 上的笔记本，可以在多块 GPU 上运行，看预填充与解码分离怎样工作；Cognition 的 DeepWiki 把软件仓库建了索引，可以提问，不需要把代码下载到运行 Agent 的地方，在手机上就能问"SGLang 的 Radix 缓存怎样支持混合模型"（他认为不支持，但 DeepWiki 会告诉你），有图、有组织、可查询；当然也很值得把代码拿下来和 Agent 一起探索，用自己的"思考 token"，不只是用付费的那些。

四、硬件

从硬件角度看有两个子工作负载：预填充，输入 token 很多（现在几乎所有工作负载都是几百、几千、几万甚至几十万），处理它们要把几 GB 的权重（所有激活参数）从加速器的高带宽内存搬到寄存器里计算；解码阶段，每生成一个 token 也要把所有权重从内存搬到寄存器，粗略的经验是每个批元素（每个 token、每个请求）对每个字节只做两三次浮点运算（乘一下再累加）。所以解码时每加载一个字节只做几次运算。坏消息是 GPU 等硬件的趋势是"屋脊点"的算术强度越来越高（用满全部算术带宽、算力成为性能上限的那个点），而内存带宽低得多，所以用不满算术带宽。最近几代 NVIDIA GPU 张量核的屋脊点在每字节几百到上千次运算，解码时每字节只有几次，很难充分利用加速器，但你付的钱一样多。所以预填充和解码要分开优化，这也是它们已经出现在应用和工作负载定义中的原因。

他的经验是目前要做好，基本只有最新的数据中心级、带张量核的 SXM 规格 NVIDIA GPU。这些是营销术语，他解释了一下：

  • 数据中心级：NVIDIA 用来指 GPU 的互联、封装等。照片中蓝色的块是高带宽内存（HBM），在基板上但不在芯片上，焊死的，不像家里的内存条能插拔；它的超低延迟和超高带宽对解码阶段很关键，这是不用 GDDR 显存 GPU 的原因之一，容量通常也更大（他认为这只是部署方式的产物，不是做不出带巨大 GDDR 的芯片，只是 NVIDIA 没提供）。
  • SXM：一种安装规格，取代 PCIe（你见过的 GPU 底部那排像牙刷的金手指）。它供电更好，能跑满 GPU 的功率。内存带宽和算术带宽的限制根本上来自芯片的供电和散热能力，SXM 供电更好、更适合装进数据中心，最快的芯片型号里都有它。还有连接 GPU 的 NVLink 和连接节点的 InfiniBand，这次不多讲。
  • 张量核：基本上是 NVIDIA 在 Google 做出 TPU 之后"钉"到 GPU 里的矩阵乘法单元（他说这句话会引起争吵），是一个独立的、单独编程的硬件单元，现在硬件 99% 的 FLOP 在这里，而它只能做矩阵乘矩阵。所以他的建议是：想设计奇怪的模型架构，要确保它能利用矩阵乘矩阵，别犯 Transformer 推理时像矩阵乘向量的错误。

他推荐自己写的 GPU Glossary（从 warp 调度器到编译器标志都汇集在一起，还有屋脊点图等性能优化内容），这是"书本知识"；想要"街头知识"，可以用朋友做的 Tensara，类似 GPU 编程的 LeetCode（也跑在 Modal 上）。其他选择：

  • CPU：目前一般达不到人们想跑的模型的可接受延迟。真的需要 HBM，而多数 CPU 的内存和处理器是分开部署的；也有带 HBM 的 CPU，但 Intel 的 HBM 和 CPU 在速度上难以匹配。一个大问题是 GPU 让程序员控制 L1 缓存（SM 共享内存），这对利用很高的算术带宽很重要。很多人在做出色的工作，他预期会变：模型变小、CPU 变大，会出现交叉点，之后会有大量很棒的 CPU 推理，但不是今天。
  • AMD GPU：他用得不多，听说编程有挑战、很难达到满速，但他们也在做很好的工作，值得关注。
  • TPU：他有点担心从头到尾只有一个供应商。你可以买到 Coral 这种小 TPU，但他说自己枕头下放着一块 2070，觉得了解那台机器，而不了解 TPU；更严肃的是经济上的顾虑：从一个高度垂直整合的垄断者那里买，和从 NVIDIA 这种松散整合的垄断者那里买不一样。
  • 其他推理芯片：通常更难，也普遍有单一供应商的问题，很多已经收回"买芯片装进你自己的机架"的做法，一般不通过超大规模云厂商部署，而是像 TPU 那样自己建、通过自己的云用，这让它们能走得更快，没有贬义；但这也让它们更难编程、装机量更小，没有一群 13 岁的地下室黑客去逆向它们的指令集（NVIDIA GPU 就有），他有点担心这一点，但那里显然有很多事在发生。

五、部署

部署选择受硬件限制。GPU 和 HBM 稀缺，大概会一直稀缺，所以现在推理主要不在本地，大多数推理应用会在数据中心代表客户端运行。他预期这会变：对比数据库，SQLite 数据库和 Postgres 数据库各有多少？有人算过 SQLite 有上万亿个，最终推理也会大量走向边缘，但现在是云端部署。超低延迟预算会被网络吃掉：区域部署损失几十毫秒，全球部署损失几百毫秒，这推动更复杂的区域部署或（数据中心意义上的）边缘部署。因为稀缺、需求大，GPU 很贵，所以要最大化硬件的产出，这也是整场讨论一直关注性能的隐含原因：一台 8 卡 B200 机器的运行成本和一名员工的成本相当，所以大家在乎性能。

另一个问题是 GPU 经常坏，H100 的平均故障时间以周甚至天计，而不是年，有点像老工程师讲的旋转硬盘时代的故事，必须假设会坏，做冗余，让硬件故障不变成系统失效。好消息是推理比训练容易：训练要求所有 GPU 一直在线，否则全停；推理的副本彼此独立，路由到别的副本继续就行。但可靠性和性价比仍是问题。Modal 写过一篇博客，讲在几千到一两万块 GPU 规模上观察到的情况，比如不同云厂商的故障率差别很大，有些部署比别的好，也有办法应对。

推理服务更大的挑战是流量波动。他们平台上推理应用每分钟的请求数波动很大，有季节性，也有很大的需求起伏，他认为部分是因为历史上增长最快的公司正在出现，社交媒体能极快地传播产品。和训练不同，推理的这些情况不是你能规划的，它们会自己发生。默认做法是买 GPU、提前上架，猜峰值有多大，非峰值时仍为硬件付钱（直接付云租金或间接摊销），很低效，网上很多人报告利用率只有 30%、40%。解决办法是按需获取 GPU，难点是让推理服务器的新副本启动得很快；做不好就既有用不上的 GPU 挂着，又错过高峰。目标是快速、自动地分配，既有最高利用率又有好的服务质量。Modal 有一篇很详细的博客讲内部做法，希望别人借鉴，大意是：

  • 不要因为来了一个用户请求就从零启动一台机器，维护一个空闲机器的缓冲池，随时接新流量；多个应用在同一个池子上扩缩容时尤其重要，你不知道下一个要扩的是哪个。Modal 是大规模多租户系统，用经典的运筹学线性规划方法管理缓冲池的大小，并考虑价格。
  • 创建和销毁副本（容器、虚拟机等）时，要从云存储把运行所需的文件拿过来。做法是不让加载整个文件系统挡住容器启动：文件系统懒加载，但对最先需要的东西（PyTorch、Python、核心操作系统库）在容器启动时并发地急切加载，并存进多层云缓存，从副本上的 Linux 页缓存一直到对象存储，中间还有各种层，更快地交付。即使单租户部署甚至单一工作负载，大概也会用到同样的基本技术。
  • 启动应用本身对 SGLang、vLLM 这类引擎要几分钟：即时编译、CUDA Graph 捕获、torch.compile 都很花时间，看起来只能等。但每个进程最终只是一个数据结构，Linux 进程的表示、GPU 上的部分内容，最终都是数据（TCP 套接字等是例外，需要一些手术），知道怎样创建，就可以存下来，从存储恢复比重新创建快。可以用 CRIU 和 cuda-checkpoint 这类检查点恢复技术；NVIDIA 前一天也发了博客介绍他们的 GPU 内存服务等系统，会进入即将发布的 Dynamo 版本。

六、可观测性与调试

部署之后怎样知道坏了、坏了怎样修？三类 bug：应用层 bug、模型质量 bug、性能 bug（或者说没达到 SLO）。应用层 bug 是你和应用开发者、相关方共同的责任，很棘手，有些横跨机器学习、正确性、用户体验；他做基础设施，在自己的应用上可以不想这些。推理工程师更有控制权或更该负责的是：

  • 模型质量 bug：部署时看起来不错，在生产中表现变差。可能只是生产环境不同，学术上叫训练与服务的偏差；他经验中最常见的是分词器 bug。正如 Albert 在他那讲说的，token 是被诅咒的，我们希望没有它，但至少现在还有。分词器和聊天模板（用特殊字符串或特殊 token 增强用户或框架的输入）越来越复杂，开源模型刚发布时几乎肯定有 bug，之后慢慢被修掉。如果想做开源贡献，能跑模型、发现这些分词器 bug，就可以报告，最好在引擎或模型定义里修好，这是很有价值的贡献；所谓"眼睛足够多，所有 bug 都很浅"，分词器 bug 也是。
  • 性能 bug：随时间退化，以及（尤其在异构计算环境中）副本之间令人意外的差别。

可观测性根本上指能否只靠日志来调试。Charity Majors 说可观测性与可控性是对偶的，这来自线性系统分析。理想是：看记录下的东西，找出问题，改代码，上线，当然也要跑测试，但不用做最小复现或用别的办法调试一个复杂的、往往是分布式的系统。

  • 应用层：通常要定制，可以用 OpenTelemetry 一类的工具自己搭（Datadog 等通用的东西也挺好用），但应用层更"模糊"、更像机器学习，也有专门工具，比如 LangSmith 和 Braintrust，他用得不多，听说用它们或自己搭都不错，看个人选择。
  • 模型质量：部署前跑评估，有基线可比；然后大量记录轨迹和用户反馈。对分词器，他"恳求"大家在日志里记录 token ID，而不只是字符串，事后很难重建 token ID，用 Unicode 表达的 bug 很隐蔽，用 token ID 表达就很明显："这个数字是哪来的？"
  • 性能：记录比需要的更多的指标，记得越多，越可能刚好记下了那个指向真正问题的"冒烟的枪"，先记下所有可能想要的，再筛选。

评估在应用层是为 LLM 应用建立可观测性的方式，很像测试：吃力不讨好、写起来烦、束手束脚、难做又耗时，是被看低的劳动，但对做成应用至关重要。可以从一个 Jupyter 笔记本或一张 Excel 表开始，放一些提示，在建好整个系统之前就能带来价值，也有助于调试部署、知道该期望什么性能。如果评估与模型无关，还能用来做更偏应用和产品层面的决定：用哪个模型、在什么上面跑、模型能量化到什么程度。模型和部署往往是临时的，换来换去；评估某种意义上是永久的，至少要活得比模型长，才能比较两个模型。也可以用来对各种改进推理部署的工作做质量保证，比如微调和蒸馏、基准测试、激进的有损优化、推测模型等。

要记录的指标：TTFT、TPOT（token 间延迟）、末 token 时间、每秒请求数或查询数（请求是用户层面的，查询是语言模型层面的，从系统外部按用户来想，系统内部有工具调用返回等时按查询来想）；排队，从 GPU 和它的 SM 一直到 Kubernetes 的入口，到处都有队列，它们是尾部延迟的主要来源，TTFT 或末 token 时间飙升时，多半是某处有队列；预填充和解码各自什么时候在跑、量有多大；缓存预填充，即实际多常命中见过的前缀，更进一步可以把所有前缀永久记下，离线算出假如缓存无限大、检测完美时的最优前缀命中率来对比，他说有一个永远达不到的目标挺好，够你忙一辈子；这些指标既要每个副本的，也要汇总的，汇总的给出整体分布，可以和当前状态而不只是离线测量的结果比较；要中位数和尾部，也要平均值，平均值帮助计算吞吐量和确定规模，分位数反映用户体验，正如前面的模拟所示，5% 这样看似小的数字其实大部分时间都在发生。硬件层面：温度、功率很重要，不是每个部署都做对了，有的散热不好；还有显存容量利用率、CUDA 流和内核利用率（GPU 上有多少时间在跑工作）。这些可以异步测、几乎没有开销；更底层的性能计数器目前会带来通常无法接受的性能损失。

他展示了 Modal 内部 alpha 版的看板，是最近一个多模态模型的部署：P50 看起来很好，P95 和 P99 有很多尖峰；token 间延迟和排队在时间上相关，说明很长的 token 间延迟其实是请求生成了一阵后被踢出去让别的请求生成，再轮回来，推理引擎会这样做，以便把 token 吞吐量公平地分给各请求。这不好，可能说明单个副本上请求太多，要减少；也可能是副本里有什么在变慢。他没有完全调试，因为对那个场景（一个艺术展）性能已经可以接受。

七、性能优化

和别处一样，先做收益大的：推测解码和量化，它们是低垂的果实，但往往依赖具体应用，不能像其他地方那样直接站在巨人肩上；然后是一系列中等收益的主机端（而非 GPU 端）工程；最后才考虑 GPU 端的工作，比如内核优化，只能带来几个百分点的提升，在很大规模上很重要，但要先把大的做完。

推测解码

解码时每字节的运算太少（从算法角度看，注意力里只有一个或很少的查询向量，MLP 里只有一个 token），没用满 FLOP，但用满了内存带宽。那就给多余的 FLOP 找点事做，即使不总是有用：猜接下来是什么，比如"Modal 是一家无服务器计算公司"，把猜的（草稿）token 放进去，用想要的目标模型对它们跑一遍，再用类似 Metropolis-Hastings 的拒绝采样算法，保证得到的 token 和原分布完全一样；贪心解码（温度为 0）时就是接受前缀中一致的 token，第一个不一致的位置用目标模型的 token。受内存限制时（延迟预算很紧、小模型跑在大 GPU 上），这几乎是不用想就该做的。他说"推测就是你需要的一切"，因为它带来整数倍的加速，大家说 2 倍、4 倍、8 倍；他的同事 David Wang 说这也是一个疯狂的"苦涩的教训"：生成草稿 token 需要另一个模型，它要训练，和基座模型一样随数据和计算变好；用特定应用的数据，能把推测解码的加速从 2 倍提到 6 倍，相当于又快了 3 倍，这可能决定应用能不能用。最简单的数学模型给出随接受长度指数增长的加速，生产中确实观察到这种现象，更细的模型有收益递减，但定制的推测模型确实带来很大加速。除了 SGLang、vLLM 的出色工程，很好的推测模型的出现是人们现在能自己跑推理而一两年前不行的另一个原因。

推测方法有很多：简单的 n-gram（数学或统计课上学过的语言模型），重复提示中出现过的 token 序列，看到前 $n-1$ 个就猜第 $n$ 个，效果还行；现在很多模型发布时内置多 token 预测（MTP），最后几个头不只产生一个 token 而是几个，训练和推理时都有好处（他说这两拨工程师通常互相讨厌），几乎成了标准，但 MTP 有时不好训练，推理时还能做得更好：人们发现基于模型的隐藏状态（甚至较早层的）训练草稿模型效果好。一个有趣的现象是随深度增加，层越来越专门化于预测下一个 token，较早的层在跨 token 做有意思的推理组合，可能还不知道下一个 token 是什么，但知道下一个或几个"想法"，越深越清晰（可以看层跳过等模型手术的论文）。所以想用较早的层，这用 MTP 很难做，离线训练草稿模型就容易。EAGLE 是最早这样做的之一，和模型一起训练；Modal 很看好 DFlash，它像 EAGLE，但是去噪的扩散语言模型。扩散语言模型通常难以达到最高能力，但扩散更适合硬件，算术强度更高，没有预填充与解码之分，他们和作者合作改进它，并把它好好地集成进 SGLang。

量化

量化是另一个最大的杠杆：从 FP8 到 FP4 大约快 2 倍，对内存受限和计算受限都是：内存受限时字节少了，内存带宽需求减半；张量核等浮点运算的标称每秒运算数随字节数线性变化，实际上有一个"每秒字节运算"的带宽，所以同样适用。但这需要全栈协调：在 NVIDIA 的栈中要用硬件加速的 FP4 需要 Blackwell GPU；量化会改变模型行为，要在应用层考虑，应用层和硬件层之间的交接点是评估、直觉检查或生产测试，要确保足够好才能放心上线。关于行为变化：长序列上通常更差，精度低、长序列累加更多，误差积累更多，不管是输入还是输出序列；所以短序列上可以更有把握。FP8 很标准，Hopper 及以上支持；FP4 比较前沿，通常只用在 MLP 或 MoE 层，不用在注意力层，注意力累加多得多，更棘手，但矩阵乘法通常（或更常）是瓶颈，所以仍有大致线性的加速。也可以量化或压缩 KV 缓存，但很难，他认为一般应该在训练时做，像 DeepSeek V4 那样，比权重量化难做对。他强调这些都是当前的状态，也许他漏了最近的论文。

主机端与 GPU 端

下一层是别让 CPU 挡住 GPU：不断给 GPU 提交工作，保证它总有活干。关键技术是 CUDA Graph 捕获，把许多 CUDA 内核启动变成一次，要在推理引擎里打开。发现主机开销的关键工具是看 GPU 功耗或温度是否没到应有的水平：他展示了两个副本，一个比另一个慢，慢的只用了 2 千瓦，而本该能用满 3 千瓦以上；用 torch profiler 或 Nsight Systems（两者都基于 NVIDIA 的 CUDA 剖析工具接口）看，发现原因之一是参与集合通信的一个 worker 落后于其他 worker，他还没完全查清（这是本周的问题），怀疑是 NUMA 亲和性问题，在异构硬件上很难追踪，但看温度或功耗很容易而且免费，先看它再深入。也不必那么高级，用 py-spy 看主机上在发生什么，找瓶颈就行：Modal 有一篇博客，在 SGLang 中用一个很简单的纯 Python 办法，把多模态推理加速了 10% 以上，就是把一个指针缓存在 Python 字典里，而不是每个请求都为每个张量重新创建，没用 CUDA，没用 Nsight，只用了 py-spy。

最后才考虑 GPU 优化。现有内核已经很好，通常很接近"光速"，很多人在做，复用性强，有很多好库，所以大多只能再挤出几个百分点，只有在几个百分点重要时才去做。主要工具是 Nsight Compute，能测最底层的硬件利用率，比如用了多少算术带宽和内存带宽，把性能直接映射到汇编上，找流水线停顿、记分板停顿等。他也提醒，在拿出高级工具之前，Tri Dao 写快内核用的是白板：先想瓶颈是什么、最重要的优化是什么、能达到什么速度，从这里推理，再用实证手段。

  • 有损的怪异优化：跳层、量化、剪枝、有损推测解码。
  • mega kernel：已经有用于推测解码和草稿模型、用于特定层的，将来会有用于整个模型的。
  • 硬件：他说 NVIDIA GPU 是唯一选择，但只是现在。NVIDIA 下一代会发布包含 Groq LPU 的混合机架，严格说还没有对应预填充与解码的分工，但他认为那只是历史原因，如果需求持续，将来预填充和解码会由不同的加速器完成。
  • Agent：他答应过推特上的人要讲这一点。他讲的多半是假设你自己写代码，但未来很多软件工程会把 Agent 的 LLM 推理作为工程本身的一部分。不能提示一下就走开，你的工作变成构建衡量 Agent 是否正确的系统，让它们去做基准测试、配置、监控；你要知道该给它们接哪些工具和 MCP、需要哪些指标；要过很久人们才会放心把 AWS 根账号交给模型去配置监控之类，所以理解并搭建这些是你的工作。vLLM、SGLang、TensorRT-LLM 是很棒的软件，但它们建立在"写这种软件很贵"的假设上；如果每个部署都能很便宜地写一个定制引擎，也许那是更好的策略，可以看 Song Han 实验室最近的 VibeServe 论文，有一些朝这个方向的尝试。Modal 很喜欢工程化的系统，不喜欢手敲、为每个人定制白手套式的部署，希望这件事可扩展，他认为 Agent 会是其中的一部分。
