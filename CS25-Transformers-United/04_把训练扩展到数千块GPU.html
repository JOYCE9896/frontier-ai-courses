第四讲：把训练扩展到数千块 GPU

依据 Hugging Face《The Ultra-Scale Playbook》讲五种并行：数据并行与 ZeRO 1、2、3（FSDP），张量并行与序列并行，流水线并行与调度器，上下文并行（环形注意力），专家并行，以及它们怎样正交组合

主讲：Nouamane Tazi（Hugging Face，《The Ultra-Scale Playbook》主要作者，Nanotron 核心开发者）
资料来源：课堂录像（Stanford Online 公开，2026 年春季，本文依据录像字幕整理）

一、为什么要扩展

讲者在 Hugging Face 工作了 4 年，是《The Ultra-Scale Playbook》的主要作者、Hugging Face 开源分布式训练库 Nanotron 的核心开发者，参与过 StarCoder 2、SmolLM 3 和 MoE 扩展等项目。这一讲主要依据那本书（在线免费，也有纸质版），书是一年前写的，他补充了 MoE 扩展等新内容。

看最新发布的 LLM，趋势仍是越训越大，因为规模和智能似乎相关，模型越大越聪明，比如本周发布的 Kimi K2.6 也是万亿参数模型。现在的模型有 1 万亿甚至更多参数，在 15 万亿 token 上训练，上下文长达 100 万。从基础设施角度看：要从存储中持续加载约 15 万亿 token 的数据；即使是万亿参数的模型，每个训练迭代也要在 1 秒左右完成；受限于每块 GPU 或 TPU 的显存；还要不时把检查点存回存储。这一讲主要讲训练迭代本身。

单卡时：前向、反向、算梯度、优化器更新。但全局批大小通常是 100 万到 1000 万甚至 1500 万 token，一次迭代放不下，常用梯度累积：把批切成小批，多次前向反向，顺序累积梯度。问题是它假设模型能放进显存，而现在的模型太大；顺序训练也要等很久。更多的 GPU 怎样解决这两个问题？有多种并行，各有适用场景，他希望大家至少形成直觉，知道什么场景用什么并行。他重点讲前两种（数据并行和张量并行），因为能讲清思路，后三种快速带过，思路可以推广。

几点说明：这些方法适用于任何加速器（GPU、CPU 等，幻灯片里用 GPU）；适用于预训练、后训练、蒸馏训练、推理等任何工作负载；不需要上千块 GPU，至少有两块就能受益。理想情况下，我们想把模型横向或纵向切分，梯度和优化器状态也随之切分；数据也要切分，免得顺序训练等太久。

二、数据并行与 ZeRO

数据并行（DP）是大家最常用的基本形式：不再顺序训练多个批，而是每块 GPU 一个不同的批，所以叫数据并行。每块 GPU 数据不同，算出的梯度也不同，为了让各卡上的模型保持一致，要同步梯度，就像分布式的梯度累积，用 all-reduce 集合通信（多块 GPU 上的分布式求和），得到相同的梯度，各卡做相同的优化器更新。代码上用 PyTorch 的 DDP 类包住模型，反向时自动处理 all-reduce。

all-reduce 时 GPU 是不是闲着？可以用 torch profiler 可视化 CPU 和 GPU 的时间线：CPU 流有前向和反向，GPU 有计算流和通信流。朴素的 DDP 实现里有三个问题：最重要的是不希望 GPU 闲着，GPU 计算流要一直是满的，这里不是；CPU 要一直领先于 GPU，才能提前调度内核；all-reduce 没有和计算重叠。重叠的办法：一个"桶"的梯度算好就开始 all-reduce。反向从最后几层开始，不必等整个模型的反向完成，最后一层的梯度算好就能开始 all-reduce，同时继续反向。PyTorch 里可以用 bucket_cap_mb 参数控制桶的大小，让通信和计算更好地重叠。每个想扩展模型的工程师都要经历这个：GPU 多了，一定要让计算和通信高效重叠，避免 GPU 计算出现空闲，用好 GPU 的张量核。这也是这一讲的最终目标。

DP 小结：容易实现，重叠效率高，与模型无关，包住任何模型就能自动在反向时归约梯度。问题：一是优化器更新在各卡重复，是重复劳动；二是 GPU 越多需要的批越多，全局批大小随之增长，不能无限增长，受限于几千万 token，比如有 100 万块 GPU 就不能全用 DP；三是最大的瓶颈：DP 假设一个训练步能放进显存，而这常常不成立，需要别的方法省内存。

  • ZeRO-1：解决优化器更新的重复。不让每块卡都存全部优化器状态，而是切分到各卡；反向时不做 all-reduce，只做 reduce-scatter，每块卡只对自己那片做优化器更新，没有重复劳动；得到更新后的参数片后，在下一步之前 all-gather。一个很重要的直觉：原来 DP 反向时有一次 all-reduce，ZeRO-1 把它换成 reduce-scatter 加 all-gather，而 all-reduce 本来就等于 reduce-scatter 加 all-gather，所以没有增加通信，只是先 reduce-scatter 得到梯度，做完优化器更新再 all-gather 参数。后面还会反复用这个技巧。
  • ZeRO-2：reduce-scatter 后只用到自己负责的那部分梯度，其余可以丢掉，进一步省内存，这就是和 ZeRO-1 的小区别。说起来容易，实现时丢东西挺麻烦，所以大家通常只用 ZeRO-1，保留梯度。另外，现在有了 Muon 优化器，它需要完整的梯度张量。以前大家把所有参数展平，不保留张量的概念，再按 GPU 数切分；但 Muon 要对完整的张量做 Newton-Schulz 迭代，不能随便切开张量，所以切分时要保证每块卡上的张量是完整的，比如前 5 个完整张量给第一块卡，接下来 5 个给第二块。其他一些优化器也有这个要求。
  • ZeRO-3：连参数的内存也要省，这最"疯狂"，前向和反向都需要参数，怎么能切开？ZeRO-3 的技巧：优化器更新后不马上 all-gather，每块卡只保留自己那片参数；做某一层的前向时，再向其他卡要这一层的其他片，算完前向就释放，下一层同理，反向也一样：all-gather 权重，算反向，释放。看起来很慢，每层都要向其他卡要参数，但实际效果很好，因为在计算当前层时预取下一层：原来优化器更新后的一次大 all-gather 被拆成多层的小 all-gather，算第一层前向时已经在 all-gather 下一层。所以内存里同一时间最多只有两个所谓的 FSDP 模块，一个释放、一个收集。这是最好的 DP 形式：优化器状态、梯度、模型都省了内存，预取让一切重叠得很好；和 DDP 的桶大小类似，可以控制 FSDP 模块的大小。

ZeRO-3 也叫 FSDP（全分片数据并行）。PyTorch 有两个版本：FSDP1 是一个 FSDP 类，包住模型，定义 wrap policy（类似桶大小）；FSDP2 是 fully_shard 函数，对模型调用就能把模块变成 FSDP 模块。区别：FSDP1 把所有参数展平，前面说过 Muon 等优化器需要完整张量，这不好；FSDP2 能让每块卡保留完整张量；FSDP2 基于 PyTorch 新的 DTensor，便于和其他并行组合。

ZeRO-3 的优缺点：用通信换内存。朴素 DP 完全不省内存，假设模型放得下；需要省内存时才用 ZeRO-1、2 或 3。他提醒，很多人给所有模型都套上 FSDP2，这不好：如果 ZeRO-1 就能放下，就不需要 ZeRO-3，它只会增加通信、拖慢训练，没有别的好处。所以用刚好够省内存的那一级。通信和计算重叠得很好；与模型无关，实现不头疼，不管是什么 PyTorch 模块（状态空间模型也好）都能直接包上 FSDP。缺点：规模很大时每个 FSDP 模块都要 all-gather 参数，即使重叠了，网络很慢时也藏不住通信。解决办法是混合分片（HSDP）：小圈子里用 FSDP，大圈子里用普通 DP。另外 ZeRO-3 仍是数据并行，仍随批扩展，每块卡一个不同的批，不能无限扩展：比如有 1 万块 GPU，在 1000 块时就已经用满了全局批大小，就需要另一种并行。

三、张量并行与序列并行

张量并行（TP）的动机：同一个批（同样的输入、同样的数据），把模型切开，做和单卡完全相同的计算，只是用两块卡代替一块，模型、梯度、优化器状态的内存都按 GPU 数切分。面试常问的一个问题：张量并行中保留的激活是完整的还是一半？后面回答。

从矩阵乘法开始：$Y = XW$，要在两块卡上并行，可以把 $W$ 按列切开，再 all-gather 输出。两次矩阵乘法 $Y_1 = XW_1$、$Y_2 = Y_1W_2$：第一个权重按列切，第二个按行切，各卡做两次乘法，最后做一次 all-reduce，结果和单卡相同。这就是张量并行的直觉：原来单卡用完整矩阵做两次乘法，现在分到两块卡，每块卡只有一半的权重、做一半的计算，代价是要做一次分布式通信 all-reduce 来保证正确。反向也一样：假设上游梯度 $dY_1$、$dY_2$ 在各卡相同（这是个大麻烦，后面讲），计算输入梯度 $dX$ 时乘以 $W_2$ 和 $W_1$ 的转置，还是两次乘法、各一半权重、一次 all-reduce。所以把两次矩阵乘法高效分到多块卡上，前向一次 all-reduce、反向一次 all-reduce，前提是各卡的输入相同、上游梯度相同。

用到 MLP 上：比如 $\text{act}(XA)$ 再乘另一个矩阵，总有两次矩阵乘法，第一个用列并行线性层，第二个用行并行线性层，加一次 all-reduce 保证数学正确。大前提是：在 Transformer 中各卡总有相同的激活、输入，要得到相同的输出，之后有相同的上游梯度，所以 $Z$ 之后的运算在两块卡上必须相同。计算减半，$A_1$、$A_2$ 是 $A$ 的两半，隐藏维度被切分了。

注意力也有两次矩阵乘法：QKV 投影和输出投影。应该沿头维度切，还是沿头的数量切，还是都切？要问的通用问题（实现张量并行或检查实现是否正确时都适用）是：各卡算出的激活是否和不用 TP 时相同？如果沿头维度切，算 $QK^\top$ 时隐藏维度变小，影响 softmax，结果和 TP=1 不同；如果沿头的数量切，各头相互独立，激活和不用 TP 时相同。所以为保证注意力正确，按头切分，同样需要相同的输入和上游梯度。

TP 小结：优点是把模型和计算都分到各卡，既省内存又不消耗样本，参数、梯度、优化器状态都切开了，各卡用的是同一个样本，不需要多个批；也不需要对梯度做 all-reduce，因为各卡在做同一件事，就像一块大 GPU 被分成了几块小 GPU。缺点：通信很重，每个注意力块、每个 MLP 块前向和反向都要 all-reduce；TP 区域（隐藏维度被切分的区域）之外的参数必须保持同步，否则输入和上游梯度就不同了，矩阵乘法就不对了，实践中要对它们的梯度做 all-reduce，这常常把训练搞坏，理论上不需要，但由于数值精度，它们会逐渐漂移；实现复杂，换架构（比如用 MLA 或别的花哨注意力）时实现 TP 很头疼。

序列并行（SP）是 TP 的一种变体。在 TP 中，注意力和 MLP 是 TP 区域，形状是（序列，批，切分后的隐藏维度），第二个矩阵后恢复原来的隐藏维度，之后的部分（层归一化等）在各卡重复，保持同步很麻烦，要对层归一化做 all-reduce，其他运算也要保证复制一致。能不能也分出去？还是用那个技巧：把 all-reduce 换成 reduce-scatter，把恒等换成 all-gather。在 TP 区域沿隐藏维度切分激活，然后沿序列维度 reduce-scatter，SP 区域中序列被按 TP 大小切分，再 all-gather 回来，在隐藏维度和序列维度的切分之间来回切换。好处：原来要存很大的 $S\times B\times H$ 激活，有了序列并行，大小总是除以 TP；通信量相同，因为 all-reduce 就是 reduce-scatter 加 all-gather。

那还需要同步层归一化的梯度吗？不需要。reduce-scatter 和 all-gather 互为逆运算，reduce-scatter 的反向是 all-gather，all-gather 的反向是 reduce-scatter（可以自己验证）。反向时，层归一化之前有一个 reduce-scatter，它负责同步梯度。他说这样恰好成立很漂亮：各卡做的不再是完全相同的事、看到的是不同的序列片段，反向时有了 reduce-scatter，不再假设理想的恒等、层归一化永远同步，由 all-gather 和 reduce-scatter 负责同步梯度。

TP 加 SP 的优点：模型和计算分到各卡，省内存、尤其不消耗样本（这是 DP 做不到的）；不需要对梯度做 all-reduce；有了 SP，也不需要对层归一化做 all-reduce。缺点仍是通信重、实现复杂。因为通信重，各分布式训练库都建议 TP 在单个节点内使用，比如一个节点 8 块 GPU，TP 不超过 8，让 TP 的通信留在节点内，前向反向不会卡在等 all-reduce 或 reduce-scatter、all-gather 上。

组合两种并行

前面讲的几种并行彼此正交：比如 DP 大小为 3，TP 把模型切成两份；批沿数据轴切分，沿模型轴复制；模型沿 TP 轴切分，沿数据轴复制。于是可以把所有并行组成一个网格，现在是两种，后面有五种甚至六七种。看 TorchTitan、Megatron 或 Nanotron 的代码，开始时初始化进程组，比如 6 块 GPU，创建 TP 组和 DP 组，之后可以选择在哪个轴上通信，比如沿 TP 组 all-reduce。这就是这些并行的好处：保证它们彼此正交。

四、流水线并行

流水线并行（PP）比 TP 容易得多：不横向切层，而是纵向切，一些层放在第一块卡，一些层放在第二块。问题是第二块卡一开始没有激活，只能等第一块卡；第一块卡算完前四层，又要等第二块卡。解决办法是 PP 调度器，它规定各卡怎样加载数据、怎样和其他 rank 交换激活和梯度。简单起见假设每块卡一层：

  • 全前向全反向（all-forward all-backward）：第一个批从第一块卡开始，激活传给第二、第三、第四块卡；为了不让卡等着，调度 8 个批，都做完前向再做反向，每块卡做完反向把梯度传给前一层，重复。空闲时间就是流水线的"气泡"，是流水线并行最大的问题。
  • 一前向一反向（1F1B）：优先反向而不是前向，中间某段就会前向反向交替。但气泡仍没解决，这只是对内存稍有帮助。
  • 最好的办法是从另一端也开始前向，这就是 DeepSeek 的 DualPipe：有 8 个设备，按轮转方式分配层，第一层同时放在第一个和最后一个设备上，两端都能开始处理数据，一个前向从左往右、一个从右往左，反向也是两个方向，在中间管理重叠。说起来容易，实现很复杂，要跟踪各批的前向和反向，才能发送正确的激活和梯度。

PP 的优点：通信便宜，没有 all-reduce，只交换激活和梯度；切分很高效，每块卡只管模型的一片；与模型无关，只要有层，能传激活和梯度就行。缺点：要为多个微批保存激活，比如有 8 个反向时调度 20 个微批，就要存 20 份激活。所以 PP 和 FSDP 这类大量依赖激活的方法，通常会卸载激活：用激活检查点，或者现在还有 CPU 卸载，GPU 好的话把激活卸载到 CPU，需要时再加载。要藏住气泡需要 DualPipe 这样的高级调度器，实现复杂，很难加进库里。还要多个微批来藏住气泡，在某种意义上和 DP 的问题一样：全局批大小要随 PP 大小增长。

五、上下文并行与专家并行

最后两种针对特定场景。上下文并行（CP）解决长序列：序列变长后激活会爆炸，即使用了 TP 和 PP，长上下文训练时怎样分摊内存？DP 是沿批维度切，现在沿序列维度切，类似数据并行。但每块卡只有序列的一部分，怎样对整个序列算注意力？这就是环形注意力，思路类似 FlashAttention 中的在线 softmax：softmax 不必一次算完，可以在线计算，每块卡先在本地算 softmax，再和其他卡交换 K 和 V，更新 softmax，依此类推。小问题是每个注意力块内部都要传 K 和 V，和 TP 类似，通信很重，可以用 send/receive 或 all-gather。优点：它是唯一能高效切分长序列内存的并行，其他并行并不真正切分序列。缺点：通信重；和 DP 一样各卡数据不同，要对梯度做 all-reduce；对短序列帮助不大，真正只在长上下文训练时用。

专家并行（EP）用于 MoE：有路由器把 token 路由到不同的专家，可以把专家分到各卡上，那么路由需要什么通信？路由有 Switch Transformer 的方式和更通用的 top-k 方式，讲 top-k。all-to-all 是交换消息最通用的方式：比如 4 个进程各有 4 条不同的消息，每个进程把消息发给其他所有进程，也从其他所有进程接收，是 $N^2$ 量级、最复杂的通信。用到 MoE 上：每块卡有不同的专家，路由时每块卡都有一些 token 要发给第一块卡（上面有第一批专家），第一块卡要从其他卡收到属于它的 token。具体做法：只把专家切分到各卡，EP 只用于 MoE，不碰注意力；为避免注意力中的重复劳动，也要把数据切分到各卡，所以 EP 在这个意义上和 DP 不正交，数据也沿专家并行轴切分；用 all-to-all 把 token 路由到对应的专家（叫 dispatch），专家之后再合并（combine）恢复原来的序列。

扩展 MoE 时最大的问题：怎样知道 all-to-all dispatch 要发多少？要知道 token 怎样路由，路由器得先算出分数，CPU 必须等 GPU 算完路由（叫 dispatch 预处理），GPU 要告诉 CPU 缓冲区大小和每个专家的 token 数。解决方案有 DeepSeek 的 DeepEP 和 NVIDIA 的 HybridEP，目前唯一的办法是用支持 IBGDA 和 RDMA 的新硬件：预先分配特定的 SM 和内存，一旦知道哪些 token 要发给哪块卡，内存已经准备好了。如果是 H100 或没有 InfiniBand 网络，就卡在 CPU-GPU 同步上，所以很多做 MoE 训练的实验室训练很慢就是因为硬件；DeepSeek 开源的 DeepEP 只能在 InfiniBand 上工作，其他实验室很难跟上。

EP 小结：它是高效分布式训练 MoE 的唯一方式；通信重，每个 MoE 块都要 all-to-all；数据不同，要对梯度 all-reduce；启动 dispatch 需要 CPU-GPU 同步，严重拖慢训练。只在 MoE 训练中使用。实践中的做法是和 PP 结合：dispatch 和 combine 很慢，而 1F1B 中前向和反向可以重叠，有两个批（蓝和绿），对蓝色批做 dispatch 的同时，对另一个批做反向；MLP 不需要 dispatch，可以在那时做另一个批的 dispatch。Megatron 等库已经实现，有两个对应的参数可以打开。

总之，五种并行可以组合，训练的不同步骤有不同的通信；EP 只作用于 MoE 部分，CP 只作用于自注意力；所有并行彼此正交，五种可以全部组合。《The Ultra-Scale Playbook》里有一张速查表，根据你有多少 GPU 帮你做决定；对基础设施感兴趣，可以看《Smol Training Playbook》的基础设施部分，有很多关于基础设施怎样承受这类负载的基准测试；还可以参考 JAX 的 scaling book，了解 TPU 的视角。欢迎为 Nanotron、TorchTitan、Megatron-LM 等库贡献代码。最后他提醒，扩展到上千块 GPU 时，要注意能耗，负责任地使用它们。

六、问答

  • 专家并行要求 token 在各卡间分布均匀，如果所有 token 都路由到一块卡，其他卡就闲着，实践中怎么办？这是负载均衡要解决的。DeepSeek 最早引入负载均衡损失，在损失中加一项惩罚 token 分布不均；还有无辅助损失的方法，计算路由时加一个偏置项，自动调整分布，使各卡均匀。
  • 不同的并行策略会影响扩展效率、模型表现或收敛吗，还是只是让你能达到更大规模？各种并行不改变前向和反向，实现正确的话，效果应该和单卡一样，缩放规律相同，从计算的角度看用 PP 还是 EP 不应该有差别。
  • RL 训练中，CPU 端的检查点或环境数据处理变成串行瓶颈时，怎样减少 GPU 空闲？至少对文本，可以事先分配很多 worker，PyTorch 的数据加载器可以指定 worker 数量，在训练之前预处理数据，缓解预处理的瓶颈。
  • 有自动决定最佳并行的方法吗？有一些论文，JAX 的书里也做过，让 TPU 决定最佳并行。但这很依赖具体情况：模型大小、数据量、全局批大小、网络。扩展时最大的因素是网络瓶颈，比如 GPU 的 NVLink 域通常是 4 或 8，最新的有 32 甚至 72，据此可以用通信更重或更轻的并行；TPU 以 32 个为一组，所以大家会在 32 个上用张量并行。所以很依赖硬件和全局批大小。
