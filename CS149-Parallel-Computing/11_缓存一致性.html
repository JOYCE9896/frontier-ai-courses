一、补完 Spark

Kunle 说本来以为作业 3、4 需要先懂 GPU 上的 DNN 优化，所以上周四换成了 Kayvon 讲；后来作业推迟了，讲课顺序就不那么顺了，大家切换一下上下文。Spark 的完整内容见第九讲，这里记下课上补充的部分。

回顾：MapReduce 怎样做到容错？中间数据放在哪？放在分布式文件系统 HDFS 上，它是复制过的所以容错，但很慢，比内存慢约 100 倍。对大量使用中间数据的应用（迭代算法、对同一份数据反复做即席查询），MapReduce 很低效。Spark 的 RDD 是只读的有序记录集合；并行性能来自大量并行加上局部性优化。上一讲 Kayvon 讲的 FlashAttention，本质上就是融合加分块的组合。这些变换一般要理解应用、可能要全局重构；Spark 的好处是 RDD 上的变换都是批量操作，运行时能看出发生了什么并做优化。

  • 窄依赖可以融合：lower 的分区 0 只依赖 lines 的分区 0，mobileViews 的分区 0 只依赖 lower 的分区 0。运行时能把这些变换融合，只从文件系统一次取一行，其余都在内存里一行一行做，没有额外的外部访存，集群节点之间也没有通信。
  • 宽依赖：比如 groupByKey，算 RDD_B 的分区 0 要从其他所有节点取分区 1、2、3 的数据，没法在单个节点内融合，通信很多。
  • join 什么时候不用通信？同学答：如果某个键只出现在 RDD_A 的分区 0 和 RDD_B 的分区 0，不在其他分区。也就是 RDD_A 和 RDD_B 用同一个哈希分区器分区，共同的键只在同一编号的分区里。代码里显式定义 partitioner，用它分别给 mobileViews 和 clientInfo 分区，运行时检测到两边用的是同一个分区器，就判断只有窄依赖，可以融合。有同学指出一边某些键的条目可能特别多，负载不均。Kunle 说一阶上，负载均衡的问题比通信小。

容错：血缘是从分布式文件系统装数据开始、施加的那串变换，是可以用来重建任何 RDD 的变换日志。RDD 只读、变换是函数式的不修改输入，所以总能从永远不会丢的持久数据（它在各节点间复制）重建。有同学问：既然只存日志，为什么还要物化数据？Kunle 反问：用户想要什么？timestamps。用户关心中间数据吗？所以尽量融合，不保留用户没要的中间数据；用户要了就得给。唯一的问题是在得到用户要的最终结果之前丢了中间数据怎么办。计算 timestamps 中途节点 1 崩溃，丢了 timestamps 和 mobileViews 的分区 2、3：重放日志。假设数据在 HDFS 其他地方有副本，日志粒度很粗，要记的东西不多，从 lines 到 mobileViews、Chrome views，重新得到 timestamps。血缘由主节点记录，假设主节点不太会坏，或者它也有副本。如果想用完全自定义的函数呢？必须待在 Spark 的世界里，对 RDD 做函数式的变换；一旦修改输入，就破坏了 Spark 的抽象，你就得自己负责了。

性能：Spark 论文（2012 年左右）和 Hadoop 比，Hadoop 一直是个好欺负的对象，因为太慢了。逻辑回归（很简单的机器学习操作）：Hadoop 第一轮 80 秒，之后几轮也快不了多少，每轮都要读写 HDFS；HadoopBinMem 在内存里存二进制副本而不是文本，第二轮稍快，但仍要访问磁盘；Spark 只做一次 HDFS 读，之后直接用内存，后续几轮快得多，快一到两个数量级，和存储系统与 DRAM 之间的带宽差距一致。K-Means（作业里玩过的）也一样。Spark 生态：Spark SQL 做数据库处理，MLlib 机器学习库，GraphX 图操作。以前几届课的作业里有广度优先搜索这类图分析，今年没有。

横向扩展不是全部：横向扩展的发明，是因为人们想分析放不进单台服务器内存的数据。大服务器能放多少内存？同学说 TB 级，大约 0.5 到 2 TB。很多展示 Spark 的研究用的数据其实不够大：Twitter 图 5.7 GB，合成图 14.72 GB。数据放得进内存就不该用分布式系统，开销太大：这两个图上跑 20 轮 PageRank，Spark 用 128 个核仍比单线程慢两倍。Frank McSherry 抨击分布式系统研究者，说大数据系统的论文把可扩展性奉为一切，制造了一堆开销再想办法减少自己制造的开销，主张以性能为指标。几百 TB 数据只能用分布式系统；不到 1 TB，单机会高效得多。有同学问什么是横向扩展：用网络连接独立的服务器叫横向扩展（scale out）；在共享内存系统里连接多个核叫纵向扩展（scale up）。在 Spark 之前，课上讲的都是纵向扩展。

二、缓存复习

现在进入今天的主题。缓存一致性既影响性能，也影响正确性，软件开发者写程序时要考虑它。现代处理器芯片很大一部分面积是缓存，Intel Core i7 约 30% 的芯片面积是缓存。要到芯片外取数据，现代芯片上要一百甚至几百个周期，CPU 在这期间停顿就浪费很多时间。

缓存例子（回到第一、二讲）

假设：总容量 8 字节，缓存行 4 字节（所以能放 2 行），LRU（最近最少使用）替换策略，内存里是 16 字节的数组。

  • 例子 1：访问 0x0，"冷缺失"，装入行 0x0；访问 0x1、0x2、0x3、0x2、0x1，都命中；访问 0x4，冷缺失，装入 0x4；再访问 0x1，命中。这个序列里有两种"数据局部性"：空间局部性，装入一个缓存行就"预装"了之后访问同一行里其他地址需要的数据，带来命中；时间局部性，反复访问同一地址带来命中。
  • 例子 2：顺序访问 0x0 到 0xF，再访问 0x0。每到新的一行就冷缺失，装入 0x8 时逐出 0x0，装入 0xC 时逐出 0x4；最后访问 0x0 时是"容量缺失"，装入 0x0 逐出 0x8。（Kunle 说之前课件把它错标成冲突缺失，其实是容量缺失：缓存更大就能放下三四行。）

为什么要有缓存行？一是利用空间局部性；二是让缓存一致性的实现更高效，并且充分利用存储系统内的数据通路，整行地批量搬运比一个个搬更高效。冷缺失：第一次访问某地址，它不可能在缓存里，对这个地址来说缓存是"冷"的。什么程序行为带来空间局部性？顺序访问数据；另一处是指令访问流。时间局部性：反复访问的计数器变量，递归函数里的栈访问。

Intel Skylake CPU（2015）的缓存层次

  • L1（每核私有）：32 KB，8 路组相联，写回；每周期 2 × 32 B 读加 1 × 32 B 写；4 周期延迟。
  • L2（每核私有）：256 KB，4 路组相联，写回；每周期 64 B，12 周期延迟。
  • L3（每芯片）：8 MB，包含式（inclusive），16 路组相联；每个存储体每周期 32 B；42 周期延迟。每个核一个存储体，通过环形互连相连。
  • 缓存行大小 64 字节。支持 72 个未完成的 load、56 个未完成的 store。
  • 来源：Intel 64 and IA-32 Architectures Optimization Reference Manual（2016 年 6 月）。

缓存利用局部性。Mark Hill 提出的 3C 缺失模型：冷缺失（cold）、容量缺失（capacity）、冲突缺失（conflict）。

冲突缺失：为了简化在缓存里查找，限制每行能放的位置数，这叫相联度。Skylake 的 L1 是 8 路组相联，任何一行只要在 8 个位置里找。缓存算术：64 字节一行，32 KB 的缓存有几行？512 行。完全通用的查找要同时找 512 个位置，很贵，所以限制成 8 个；但只能放 8 个位置会比随便放带来更多缺失，这些额外的缺失就是冲突缺失。能放在缓存任何位置的叫全相联。相联度越高，冲突缺失率越低，但查找越难。Kunle 说一般会预期越大的缓存相联度越高，这里却是 8、4、16，有点奇怪，不知道设计者为什么这样做。

缓存设计

一个缓存行：数据（现代 Intel 处理器上 64 字节）和元数据。元数据里有标签（tag），即这一行数据的地址（准确说是缓存行的地址，去掉低位，这样落在这一行里的每个地址都由这个标签代表）；脏位，表示缓存里的数据是否被修改过；还有一致性协议用的行状态。缓存可以看作按内容寻址的数组：拿处理器产生的地址和所有标签比较，有一个匹配就命中，缓存里的位置本身不重要。

假设代码执行 int x = 1;，x 对应内存地址 0x12345604（简化起见不在寄存器里）。

  • 写回和写直达有什么区别？写直达：写缓存的同时也写主存。写回：只写缓存，之后替换这一行时才写到主存，需要脏位；写直达不需要脏位，因为主存总是最新的。
  • 写分配和写不分配呢？写缓存时那一行不在缓存里，是把这一行取进来再写，还是直接写主存？

写分配、写回缓存在写缺失时的行为（单处理器）：

  1. 处理器写一个在缓存里"缺失"的地址；
  2. 缓存选一个位置放这一行，如果这个位置当前有一个脏行，先把脏行写回内存。脏位表示这份数据和内存里的不同，可能是存储系统里唯一的一份，不能丢；
  3. 缓存从内存装入这一行（"在缓存中分配这一行"）；
  4. 取来整个缓存行，更新其中的 32 位。处理器只写 32 位，这一行其他字节也得有效，所以要像读缺失一样取来整行；
  5. 把缓存行标记为脏。

三、缓存一致性问题

回顾：共享地址空间模型

  • 线程读写共享变量：线程间通信隐含在内存操作里。线程 1 存 X，之后线程 2 读 X（看到线程 1 更新的值）。
  • 操作同步原语，比如用锁保证互斥。
  • 这是顺序编程的自然延伸。

共享内存多处理器：处理器读写共享变量，更准确地说是发出 load 和 store 指令。对内存合理的期望：读地址 X 应该返回任何处理器最后写到 X 的值。

问题出现

现代处理器在本地缓存里复制内存的内容。问题：不同处理器可能对同一内存位置看到不同的值。四个处理器各有私有缓存，通过互连连到主存。变量 int foo; 存在地址 X，初值 0，假设写回缓存。

（初始）0
P1 load X（缺失）00
P2 load X（缺失）000
P1 store X100
P3 load X（缺失）1000
P3 store X1020
P2 load X（命中）1020
P1 load Y（假设导致 X 被逐出）021

最后内存里 X 是 1，P3 的缓存里是 2，P2 的缓存里是 0，P1 没有 X。这看起来是一场灾难，这样的内存系统没法用。这是互斥问题吗？能靠在程序里加锁修好吗？不能！这个问题是把地址 X 的数据复制到各个本地缓存造成的，系统里有多处保存着对应内存的地址，多个处理器在改自己的私有副本。怎么修？

内存一致性问题

  • 内存系统的直观行为：读地址 X 返回任何处理器最后写到 X 的值。
  • 问题之所以存在，是因为实现单一共享地址空间这个抽象的，既有全局存储（主存），又有每处理器的本地存储（处理器缓存）。
  • 单处理器上提供这种行为相当简单，因为写一般只有一个来源：处理器。例外：通过直接内存访问（DMA）的设备 I/O。

单 CPU 系统里也有一致性问题

考虑 I/O 设备做 DMA 数据传输：

  • 情况 1：处理器写主存里的缓冲区，告诉网卡异步发送缓冲区。问题：如果处理器的写（反映在缓存副本里）没刷到内存，网卡可能传过时的数据。
  • 情况 2：网卡收到消息，用 DMA 把消息拷进主存的缓冲区，通知 CPU 消息已收到、缓冲区可读。问题：如果网卡更新的地址恰好在缓存里，CPU 可能读到过时的数据。

常见解法：CPU 用不经缓存的 store 写共享缓冲区（比如驱动代码）；操作系统支持：把含共享缓冲区的虚拟内存页标为不可缓存，I/O 完成时显式把页从缓存刷出。实际中 DMA 传输比 CPU 的 load/store 少得多，所以这些重量级的软件方案可以接受。但如果多个处理器在频繁共享内存，软件方案就不行了。

直觉的问题

  • "最后"是什么意思？两个处理器同时写呢？P1 写之后紧接着 P2 读，近到根本来不及把写的发生告诉 P2 呢？
  • 在顺序程序里，"最后"由程序顺序决定（而不是时间），在并行程序的一个线程内也成立。
  • 但需要一种有意义的方式来描述跨线程的顺序。

定义：一致性（coherence）

一个内存系统是一致的，如果：并行程序执行的结果使得，对每个内存位置，存在一个所有处理器对该位置的所有程序操作的假想串行顺序，和执行结果相符，并且：

  1. 任何一个处理器发出的内存操作，按它发出的顺序发生；
  2. 读返回的值，是这个串行顺序里对该位置最后一次写的值。

例子：对地址 X 的操作时间线：P0 写 5，P1 读（5），P2 读（5），P0 读（5），P1 写 25，P0 读（25）。一致性只谈单个内存位置（或单个缓存行）。

实现：缓存一致性不变式

对任何内存地址 x，在任一时间段（epoch）：

  • 单写者多读者（SWMR）不变式：读写时段，只有一个处理器可以写 x（也可以读它）；只读时段，若干个处理器只能读 x。
  • 数据值不变式（写串行化）：一个时段开始时内存地址的值，和它上一个读写时段结束时的值相同。

例子：地址 x 先是 P0 的读写时段，然后 P0、P1、P2 的只读时段（看到 P0 写的值），然后 P1 的读写时段，然后 P0、P1 的只读时段（看到 P1 最后写的值）。

有同学说多个处理器写同一个地址，本来就该加锁，为什么这还是问题？Kunle：可以规定你写、他写、她写，不同时写，但你写自己的缓存，他写他的缓存，她写她的缓存，系统照样不一致，虽然同步过了。两个问题相互独立，一致性问题来自数据可以存在多个地方，这是缓存共享数据的多处理器系统固有的。可以设计一个不缓存共享数据的系统，就没有一致性问题，但会有性能问题，每次共享内存访问都要去内存，没什么用。

实现一致性的方式

  • 基于软件的方案（粗粒度：虚拟内存页）：操作系统用缺页机制传播写；可用来在工作站集群上实现内存一致性；这里不讨论；大的性能问题：伪共享（后面讲）。
  • 基于硬件的方案（细粒度：缓存行）："监听"（snooping）式一致性实现（今天）；基于目录的一致性实现（简要）。如今大多数系统用的是目录式，但先讲监听，它更有意思也更好懂。

共享缓存：一致性变简单

  • 所有处理器共享一个缓存，消除了在多个缓存里复制状态的问题。
  • 明显的扩展性问题（缓存的意义就在于本地、快速）：大家都打同一个缓存，带宽有限，几个处理器还行，多了就带宽不够或者缓存极贵；很多客户端造成的干扰（冲突缺失）和争用（破坏性的），一个处理器不共享的数据也可能因为别的处理器产生容量缺失。
  • 但共享缓存也有好处：便于细粒度共享（工作集重叠）；一个处理器的 load/store 可能为另一个处理器预取行（建设性的）。例子 forall (i = 0; i < N; i++) x[i] = y[i] + y[i+1] + y[i+2];，迭代交错分给各处理器，迭代 i 会取到后面迭代要的数据（假设缓存行很小，比如一个字）。

共享缓存不太适合 L1，可以用于 L2。Kunle 多年前设计的 Sun Niagara 2（UltraSPARC T2）就有共享的二级缓存，用交叉开关提供足够带宽：全对全的网络，带宽很高，但占芯片不少面积（和一个核差不多），而且不能扩展，这里到 8 个核为止，交叉开关的连线数是二次的。

四、监听式缓存一致性

  • 主要思想：所有与一致性相关的活动都广播给系统里所有处理器（更具体地说，广播给各处理器的缓存控制器）。
  • 缓存控制器监视（"监听"）内存操作，按缓存一致性协议行事来维护内存一致性。
  • 注意现在缓存控制器要响应"两端"的动作：来自本地处理器的 LD/ST 请求；通过芯片互连广播的一致性相关活动。缓存把处理器和互连解耦开，它一直看着互连："互连上有失效消息吗？有的话查我的缓存，有这个地址就失效，没有就忽略。"

非常简单的一致性实现

假设：写直达缓存；一致性的粒度是缓存行。协议：写的时候，缓存控制器广播失效消息；于是其他处理器下一次读会缓存缺失（因为写直达，处理器从内存取到更新后的值）。

P1 load XX 缓存缺失000
P0 写 100 到 XX 失效100100
P1 load XX 缓存缺失100100100

两个处理器同时广播同一地址的失效？总得有一个赢，假设互连一次只允许一条消息。

写直达策略很低效：每次写都要去内存，带宽需求很高，会耗尽带宽。写回缓存把大部分写流量作为缓存命中吸收掉，大大降低带宽需求；但这时怎样维护一致性不变式？需要更复杂的一致性协议。

写回缓存的一致性

把互连换成总线。总线有两个很好的性质，是什么？有同学说很宽、带宽大。从一致性角度看：总线一次只能有一个事务（环、任意网络都不是这样），一次一个意味着串行化，总线是一个串行化点；另一个是像教室里的空气，广播介质，一个处理器说话，其他人都听得到。

  • 缓存行的脏状态现在表示独占所有权（读写时段）。
  • Modified（已修改）：这个缓存是唯一有该行有效副本的缓存（可以安全地写它）。
  • Owner（所有者）：其他处理器试图从内存装入它时，这个缓存负责把信息传过去（否则别的处理器从内存读会拿到过时数据）。

要保证系统里任何时候只有一个缓存的脏位被置上，否则违反"读写时段只有一个处理器"的不变式。维护缓存一致性不变式的算法就是缓存一致性协议。下面描述的逻辑由每个处理器的缓存控制器执行，响应本地处理器的 load/store 和总线上其他缓存的消息。如果所有缓存控制器都按协议运行，一致性就得以维护，各缓存"合作"保证一致性。

基于失效的写回协议

  • 处于"modified"状态的行可以修改，不必通知其他缓存。
  • 处理器只能写处于 modified 状态的行。需要一种方式告诉其他缓存"处理器想独占这一行"：给所有其他缓存发消息。
  • 缓存控制器看到对自己持有的某一行的 modified 访问请求时，必须让自己缓存里的这一行失效。

MSI 写回失效协议

  • 协议的主要任务：保证处理器为写获得独占访问；缓存缺失时找到该缓存行数据的最新副本。
  • 三种缓存行状态：
    • Invalid（I，无效）：和单处理器缓存里无效的意思一样，这一行不在。
    • Shared（S，共享）：这一行在一个或多个缓存里有效，内存是最新的。只读。
    • Modified（M，已修改）：这一行只在恰好一个缓存里有效（也叫"脏"或"独占"状态）。
  • 两种处理器操作（本地 CPU 触发）：PrRd（读）、PrWr（写）。
  • 三种一致性相关的总线事务（来自远程缓存）：
    • BusRd：取得行的副本，不打算修改；
    • BusRdX：取得行的副本，打算修改（写之前也要先有整行）；
    • BusWB：把脏行写回内存。

MSI 状态图

每条边标着 A / B：缓存控制器观察到动作 A，就采取动作 B。处理器发起的（课件绿色）和总线发起的（红色）：

  • I --PrRd / BusRd--> S：无效状态下处理器读，是缺失，发 BusRd，"给我这一行，我要读"。可以把任何引起总线事务的处理器动作都想成缺失。
  • I --PrWr / BusRdX--> M：无效状态下处理器写，直接到 modified。
  • S --PrRd / --：共享状态下读，命中，没有总线事务。
  • S --PrWr / BusRdX--> M：共享状态下写，发 BusRdX 把行从共享移到已修改，叫"升级"（upgrade）。
  • M --PrRd / --、M --PrWr / --：已修改状态下读写都命中，随便做，没有总线事务。
  • S --BusRd / --：共享状态下看到别人的 BusRd，什么都不用做。所有持有这一行的缓存都是共享状态，不可能有谁是已修改。
  • S --BusRdX / --> I：看到别人的 BusRdX（别的处理器要写），变为无效。
  • M --BusRd / BusWB--> S：自己是唯一有效副本，看到别人的 BusRd，必须提供数据：把数据给请求者，同时写回内存（共享状态下内存总是最新的），然后转为共享，因为只要有别的缓存持有这一行，就不可能是已修改。
  • M --BusRdX / BusWB--> I：看到别人的 BusRdX，提供最新副本（BusWB），然后变为无效。

有同学问争用时怎样避免状态来回颠簸？Kunle 笑着说：那正是会发生的，你会整天这样，性能会差很多，缓存缺失很多，后面马上会看到例子。

MSI 失效协议要点：读得到的块处于"共享"，即使是唯一的缓存副本；写之前获得独占所有权，BusRdX 让其他缓存失效，如果在另一个缓存里是 M 会引起写回；即使在 S 里命中也要发 BusRdX，升级到 M。记住，所有缓存都独立地执行这套逻辑来维护一致性。

一个缓存一致性的例子

处理器动作P1 状态P2 状态P3 状态总线动作数据来自
1. P1 读 xS----BusRd内存
2. P3 读 xS--SBusRd内存
3. P3 写 xI--MBusRdX内存
4. P1 读 xS--SBusRdP3 的缓存
5. P2 读 xSSSBusRd内存
6. P2 写 xIMIBusRdX内存

课上的讨论：共享状态下数据总是来自内存（为了简单；也可以设想别的方案，但那就要决定两个缓存都有时从谁那里取）。第 4 步数据来自 P3 的缓存，内存怎么知道不用响应这个读？持有这一行的处理器告诉内存先别响应。课上还加了一步：P1 再读 x，是命中，没有总线事务。如果第 4 步 P1 是写呢？BusRdX，数据还是来自 P3，P1 变 M、P3 变 I。"--" 和 I 有功能上的区别吗？"--" 表示从没见过（会是冷缺失），I 是被失效了；对处理器访问这一行而言是一样的。

这是单写者多读者协议。为什么需要从 Modified 到 Shared 的转换？要维护"单写者多读者"这个不变式，必须记录这次转换，同时数据写回了内存。通信增加了访存延迟：因为 P3 写了 x，缓存里有 x 的 P1 现在要做一次总线事务，比缓存命中慢得多；中间插入的写引起额外的缓存缺失，性能就下降了。

MSI 怎样满足缓存一致性？

  1. 单写者多读者不变式：只有一个缓存能处于 M 状态，其他缓存都收到失效消息；多个缓存可以处于只读的 S 状态。
  2. 数据值不变式（写串行化）：BusRd 和 BusRdX 时，数据由处于 M 状态的缓存提供（通过 BusWB，每当离开 M 状态，必须提供这一行的数据）；总线把所有事务串行化。

有同学问一个处理器写到一半时别人也要写怎么办？它会完成自己的写。总线串行化所有动作，拿到这一行的处理器完成写、修改自己的缓存行，然后写回给下一个要写的处理器。这一行可能在所有处理器之间绕一圈，但每次拿到独占访问都能做一次写。这些逻辑在缓存控制器的硬件里实现，每个处理器有自己的缓存控制器连在总线上，另有一些访问控制逻辑决定谁下一个用总线。

MSI 小结

  • M 状态的行可以修改，不必通知其他缓存：其他缓存都没有这一行，其他处理器读不到这些值（除非产生一次内存读事务）。
  • 处理器只能写 M 状态的行：如果写一个在缓存里不是独占的行，缓存控制器必须先广播读独占事务，把行转到那个状态。读独占告诉其他缓存即将有写（"你不能再读了，因为我要写"）。即使这一行在本地缓存里有效（但不独占，处于 S 状态），也需要读独占事务（为什么？）。脏状态意味着独占。
  • 缓存控制器监听到它持有的某一行的"读独占"时：必须让自己缓存里的这一行失效，否则多个缓存会有这一行（另一个缓存里就不是独占的了！）。

MESI 失效协议

  • MSI 在"先读一个地址再写它"这种常见情况下需要两次互连事务：事务 1，BusRd 从 I 到 S；事务 2，BusRdX 从 S 到 M。
  • 即使应用完全没有共享，这个低效也存在。
  • 解法：加一个状态 E（"独占干净"，exclusive clean）。这一行没有被修改过，但只有这个缓存有副本。把独占和行的所有权解耦（行不脏，所以内存里的副本是有效的）。从 E 升级到 M 不需要总线事务，是命中而不是缺失。
  • 是 MESI，不是 Messi！（不是那位阿根廷足球巨星。）

MESI 状态转换：I 上 PrRd / BusRd，如果没有其他缓存声明共享，进入 E；如果另一个缓存声明共享，进入 S。E 上 PrRd 不变，PrWr / -- 直接到 M（无总线事务）；E 上看到 BusRd 转 S，看到 BusRdX 转 I。其余和 MSI 一样：S 上 PrWr / BusRdX 到 M；M 上 BusRd / BusWB 到 S，BusRdX / BusWB 到 I；I 上 PrWr / BusRdX 到 M。Kunle 让大家自己把其余转换补全。

五、基于目录的可扩展缓存一致性

总线的问题是不能扩展：所有人共享一组线，每个缓存行的每个事务都被所有处理器看到，包括没有这一行的处理器；所有处理器共享缓存和内存之间的接口，带宽会不够；而且总线把对所有缓存行的事务都串行化了，其实只需要串行化对同一个缓存行的操作。

  • 监听方案广播一致性消息来确定行在其他缓存里的状态：不可扩展。
  • 另一个想法：把行的状态信息存在一个地方，避免广播，这个地方叫"目录"。一个缓存行的目录项包含它在所有缓存里的状态信息；缓存按需从目录查信息；缓存一致性靠缓存之间按"需要知道"原则的点对点消息维护，而不是靠广播。可以用更可扩展的互连，网络、环，不需要广播和串行化所有事务的能力。
  • 仍然要维护不变式：SWMR、写串行化。

Intel Core i7 CPU 里的目录一致性

  • L3 作为 L3 缓存里所有行的集中目录，是串行化点。因为 L3 是包含式缓存，L2 里的任何行都保证也在 L3 里（这个性质叫包含性，inclusion）。
  • 目录维护持有该行的 L2 缓存的列表。
  • 不把一致性流量广播给所有 L2，只发给持有该行的 L2。Core i7 的互连是环，不是总线，监听在这里行不通。
  • 目录的维度：P = 4，M = L3 缓存行数。可以想成每行 5 位：处理器 0 到 3 各一位，加一个脏位。共享状态时多位为 1，比如处理器 0、1、2 都有这一行，来了一个写就知道给谁发失效；已修改状态时脏位为 1，只有一个处理器的位（比如处理器 3）为 1。

目录更可扩展，但需要在存储系统某处保存额外信息，处理器越多目录项越大，有各种更高效实现目录的方案。用目录式一致性可以扩展到几十甚至上百个处理器。有同学问 MSI、MESI 是不是只用于没有目录的缓存？目录机制和具体协议基本是正交的，仍然有 modified、exclusive、shared 这些状态；区别在于怎样让处理器注意一个事务，是用大家都在监听的总线，还是用点对点消息、更可扩展的目录。

六、缓存一致性对程序员的影响

通信开销

  • 通信时间是一个主要的并行开销。在多处理器里表现为访存时间增加：UMA 系统里多出主存访问，要看缓存缺失率相对单处理器增加了多少；NUMA 系统里有些访问延迟更高；哪怕只有百分之零点几这样的访问也可能很显著！
  • 单处理器：寄存器、L1、L2、主存，图里宽度表示访问频率。多处理器：寄存器（寄存器分配变少）、L1（缺失率更高）、L2（缺失率更高）、主存（NUMA 里可能"缺失"）、远程（极长的延迟）。
  • 平均访存时间 AMAT = Σ 访问频率 × 访问延迟。AMAT多处理器 > AMAT单处理器：从单处理器应用到并行应用，访问的分布向延迟更长的存储层次移动。

NUMA：比如两个插槽的 CPU 1、CPU 2，各有自己的 DRAM，之间有互连，每个 CPU 里有多个核，CPU 1 访问本地 DRAM 的带宽比远程 DRAM 高。作为应用程序员一阶上可以不管，但想要最高性能，可能要让操作系统把数据分配在最常访问它的处理器的本地。

Core i7 Xeon 5500 系列的数据来源延迟（约）
L1 命中~4 周期
L2 命中~10 周期
L3 命中，行未共享~40 周期
L3 命中，行在另一个核里共享~65 周期

Kunle 课上强调 L3 命中的三个数：未共享 40 周期，共享 65 周期，在另一个核里被修改时 75 周期，几乎翻倍。可以用 Intel VTune 了解存储系统性能，它查询处理器的性能计数硬件，告诉你缓存缺失和一定程度上的通信；Apple M1 笔记本上可以用 Xcode Instruments 得到类似信息，看哪些数据结构引起缓存缺失，再根据对应用的了解改善局部性。

伪共享带来的意外通信

// allocate per-thread variable for local per-thread accumulation
int myPerThreadCounter[NUM_THREADS];
// allocate per thread variable for local accumulation
struct PerThreadState {
    int myPerThreadCounter;
    char padding[CACHE_LINE_SIZE - sizeof(int)];
};
PerThreadState myPerThreadCounter[NUM_THREADS];

第一段代码有什么潜在的性能问题？为什么第二段可能更快？同学们答：第一种情况下多个计数器可能落在同一个缓存行里；第二种保证每个计数器独占一行，没有争用。缓存一致性以缓存行为单位通信。如果能按字、按字节做一致性，粒度很细，对应用程序员很好，对硬件设计者是噩梦。用缓存行的结果就是"伪共享"：意想不到的共享。

演示：伪共享

void* worker(void* arg) {
    volatile int* counter = (int*)arg;
    for (int i = 0; i < MANY_ITERATIONS; i++)
        (*counter)++;
    return NULL;
}

struct padded_t {
    int  counter;
    char padding[CACHE_LINE_SIZE - sizeof(int)];
};

void test1(int num_threads) {
    pthread_t threads[MAX_THREADS];
    int       counter[MAX_THREADS];

    for (int i = 0; i < num_threads; i++)
        pthread_create(&threads[i], NULL, &worker, &counter[i]);
    for (int i = 0; i < num_threads; i++)
        pthread_join(threads[i], NULL);
}

void test2(int num_threads) {
    pthread_t threads[MAX_THREADS];
    padded_t  counter[MAX_THREADS];

    for (int i = 0; i < num_threads; i++)
        pthread_create(&threads[i], NULL, &worker, &(counter[i].counter));
    for (int i = 0; i < num_threads; i++)
        pthread_join(threads[i], NULL);
}

线程多次更新各自的计数器。4 核系统上 num_threads = 8：test1 用 14.2 秒，test2 用 4.7 秒。这当然是刻意构造的情况，但伪共享经常发生时会严重影响性能。数据其实完全独立，只因为多个线程的局部变量落在同一个缓存行上，就产生了意外的通信。数值应用里也会发生：网格应用里有缓存行跨越分给不同处理器的网格边界。

伪共享

  • 两个处理器写不同的地址，但这些地址映射到同一个缓存行。
  • 缓存行在写的处理器的缓存之间"乒乓"，因一致性协议产生大量通信。
  • 没有固有通信，完全是人为通信（缓存行大于 4 字节）。
  • 为缓存一致的架构编程时，伪共享可能是一个因素。

缓存行大小对缺失率的影响

1 MB 缓存的模拟结果，四个应用（Barnes-Hut、Radiosity、Ocean Sim、Radix Sort，大约 30 年前斯坦福写的基准，至今仍在用），缓存行从 8 到 256 字节，缺失分为冷缺失、容量/冲突、真共享、伪共享、升级（图出自 Culler、Singh、Gupta，因纵轴范围不同分成两张图）。

  • 真正共享的数据有相当的空间局部性：缓存行变大，真共享缺失减少。
  • Radiosity 的伪共享缺失随缓存行变大而增加，如果只是真共享，行变大应该让它下降，但伪共享让它上升。
  • 极端情况是 Radix Sort，因为应用的写法，伪共享随行变大急剧增加。缺失率先下降后上升：利用空间局部性带来的改善，最终被伪共享的害处盖过。
  • 行越长，伪共享越糟。如果用虚拟内存页大小当一致性粒度（前面说的操作系统软件方案），不说软件开销，伪共享就会非常可怕。

能在程序里保证不产生伪共享吗？总可以把数据隔开，但可能浪费空间；而且应用可能有多个阶段，有时要换一种组织方式，不一定方便按最小化伪共享来组织。但要意识到它。缓存行一般是 64 或 128 字节，而且越来越长。

小结：缓存一致性

  • 缓存一致性问题之所以存在，是因为单一共享地址空间这个抽象不是由单个存储单元实现的：存储分布在主存和处理器的本地缓存里；为了性能，数据在本地缓存里复制。
  • 监听式缓存一致性的主要思想：每当发生可能影响一致性的缓存操作，缓存控制器就向系统里所有其他缓存控制器广播通知。硬件架构师的挑战：降低一致性实现的开销。软件开发者的挑战：警惕一致性协议带来的人为通信（比如伪共享）。
  • 监听式实现的扩展性受限于向所有缓存广播一致性消息的能力！用基于目录的方法扩展缓存一致性。
