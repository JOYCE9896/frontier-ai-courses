第十六讲：事务内存（一）

把同步的抽象层次再提高：锁让人在并发度和正确性之间两难；atomic 块是声明式的；事务的语义：原子性、隔离性、可串行化，对应的一致性模型；动机：Java HashMap、树的并发更新、双向链表、失败原子性、可组合性（转账死锁）；atomic 不等于 lock + unlock：用 atomic 替换 synchronized 会死循环、原子性违例；实现的两个维度：数据版本管理（急切的撤销日志、懒惰的写缓冲）和冲突检测（悲观、乐观），四种情形逐个推演

主讲：Kunle Olukotun
资料来源：课堂录像（Stanford Online，2023 年秋季）、课件（课件标号为 Lecture 15）；冲突检测的权衡、实现空间和软件事务内存在下一讲讲，见第十七讲；树更新的例子课件致谢 Austen McDonald

一、提高同步的抽象层次

  • 上一个主题：机器级的原子操作，fetch-and-op、test-and-set、compare-and-swap、load-linked/store-conditional。实现同步原语的关键硬件机制就是原子的 load 加 store；现代系统把它拆成 LL 和 SC 两个内存操作，由一致性系统把它们连起来、变成原子的。
  • 然后用这些原子操作在软件里构造更高层的同步原语：锁、屏障；无锁数据结构。我们已经看到，用这些原语写出正确的程序可能很难：很容易写出违反原子性、造成死锁等的 bug；同步顺序做错就死锁。
  • 今天：把同步的抽象层次提得更高。思路：事务内存。能不能让程序员更容易同时得到正确的程序和高性能的程序？

应该掌握的内容

  • 事务是什么；
  • atomic 代码块和 lock/unlock 原语在语义上的区别；
  • 事务内存实现的基本设计空间：数据版本管理策略、冲突检测策略、检测的粒度；
  • 事务内存软件实现的基础；
  • 事务内存硬件实现的基础（想想它和之前讲的缓存一致性协议实现的关系）。

检测的粒度会让人想起缓存一致性：讲一致性时说过两种粒度，主要讲了缓存行级别，那有什么问题？伪共享，期中又考到了。如果在操作系统页级别做检测，伪共享会糟得多。粒度的问题在事务这里会再次出现。

进退两难（Between a Lock and a Hard Place）

  • 锁迫使程序员在两者间权衡：并发度，关系到性能；出现竞争、死锁的可能，关系到正确性。上这门课就是为了写高性能程序，两者都想要。
  • 粗粒度加锁：并发度低，正确的可能性高。比如整个数据结构一把锁，甚至整个共享内存一把锁，每次碰共享内存都要拿锁，一次只能有一个线程碰共享内存。
  • 细粒度加锁：并发度高，正确的可能性低。比如手递手加锁。
  • 有更好的同步抽象吗？

复习：用锁保证原子性

void deposit(Acct account, int amount)
{
    lock(account.lock);
    int tmp = bank.get(account);
    tmp += amount;
    bank.put(account, tmp);
    unlock(account.lock);
}

存款是一次读改写操作：先取账户余额，加上存款额，再放回账户。希望"存款"相对这个账户上的其他银行操作是原子的。如果在 get 的中途有别人也要给你打钱，没有同步就会得到错误的数额，你会很恼火。锁是同步线程、保证更新原子性的一种机制（通过在账户上保证互斥）。

用事务编程

void deposit(Acct account, int amount)
{
    atomic {
        int tmp = bank.get(account);
        tmp += amount;
        bank.put(account, tmp);
    }
}
  • atomic 结构是声明式的：程序员说明要做什么（保持这段代码的原子性），而不是怎样做；没有显式使用或管理锁。
  • 系统按需实现同步来保证原子性：系统可以用锁实现 atomic { }（后面会看到），但程序员看不到锁，接口就是这个 atomic 声明；今天讨论的实现采用乐观并发：只在真正争用的情况下（读写或写写冲突）才保持串行化。

声明式与命令式的抽象

  • 声明式：程序员定义该做什么。"执行这 1000 个独立的任务。""以原子方式执行这组操作。"
  • 命令式：程序员说明该怎样做。"创建 N 个 worker 线程，从共享任务队列里取工作分给线程。""获取一把锁，执行操作，释放锁。"

课上问：这门课讲过的声明式抽象有哪些？同学答：ISPC 的 foreach。对，和它相对的是显式地创建线程、用共享任务队列分工作。命令式是"怎样"，声明式是"什么"。

二、事务内存的语义

内存事务：一个原子的、隔离的内存访问序列，受数据库事务启发。学过数据库课的人知道 ACID 性质，事务内存有类似的语义：

  • 原子性（全有或全无）：事务提交时，事务里所有内存写同时生效；事务中止时，没有任何写看起来生效（就像事务从没发生）。
  • 隔离性：事务提交前，其他处理器观察不到它的写。
  • 可串行化：事务看起来按某个单一的串行顺序提交，但事务的语义不保证提交的确切顺序，由系统决定。

没有 D（持久性），因为内存会坏。

换句话说：在一致的内存系统里我们为单个地址保持的很多性质，现在想为一个事务里的一组读写保持。事务：读 X、Y、Z，写 A、X。这些内存操作要么全部被其他处理器观察到，要么全都观察不到（实际上它们同时发生）。可以把一个事务里的操作看作缓存一致性里的单个操作，每个事务是一个可以被系统串行化的原子内存操作。

事务内存的一致性模型是什么？同学答：顺序一致性。基本上就是顺序一致：想象那个随机从一个线程指向另一个线程的开关，只是每次指向某个线程，就取一整个事务的内存访问。有人叫它"事务一致性"，以区别于每次只取一个内存访问。有同学问一个事务里能不能读写同一个变量：事务里随便做什么都行，它是隔离的；但要符合程序顺序里的依赖，没有依赖才可以重排。

三、为什么要事务内存

例子：Java HashMap

// Map: Key -> Value, implemented as a hash table with linked list per bucket
public Object get(Object key) {
    int idx = hash(key);            // compute hash
    HashEntry e = buckets[idx];     // find bucket
    while (e != null) {             // find element in bucket
        if (equals(key, e.key))
            return e.value;
        e = e.next;
    }
    return null;
}
  • 坏：不线程安全（需要同步时）。
  • 好：不需要同步时没有锁的开销。

怎样让 Java 的 HashMap 线程安全？

同步的 HashMap

public Object get(Object key) {
    synchronized (myHashMap) {    // per-hashmap lock guards all
                                  // accesses to hashMap
        return myHashMap.get(key);
    }
}
  • Java 1.4 的方案：同步层，把任何 map 转成线程安全的版本；用程序员指定的显式、粗粒度的互斥锁。synchronized 指定使用这个方法前要拿锁，但不用显式释放，系统替你获取和释放。
  • 好：线程安全，容易编程。坏：限制并发，扩展性差。

一个方案：用更细粒度的同步，比如每个桶一把锁（同学也这样提议）。现在线程安全了，但即使不需要同步也有锁的开销；而且实现复杂得多，不能只在整个方法外套个 synchronized，要深入 HashMap 的实现细节。

复习：细粒度加锁的性能。执行时间（越低越好）对处理器数 1 到 16：

  • 哈希表：粗锁几乎不随并行改进，因为没有足够的并发；细锁随处理器数增加而改进。减少争用带来更好的性能。
  • 平衡树：细锁在一个处理器时比粗锁慢得多。同学说：树上手递手加锁，每做一点工作要拿很多锁，开销相对工作很大。要四个处理器的能力才能抵消细锁的开销。它确实能扩展，但开销要克服。

细粒度加锁总是赢吗？不一定。

事务的 HashMap

public Object get(Object key) {
    atomic {                // system guarantees atomicity
        return m.get(key);
    }
}
  • 直接把所有操作放进 atomic 块。atomic 块的语义：系统保证块里逻辑的原子性。
  • 好：线程安全，容易编程，和用 synchronized 锁住整个方法一样简单。
  • 性能和扩展性呢？取决于工作负载和 atomic 的实现（后面讨论）。

另一个例子：两个线程更新树

树：根 1，下面 2，2 下面是 3 和 4。目标：以线程安全的方式修改节点 3 和 4。

  • 细粒度加锁（手递手）：锁住通往节点 3 的路径（红色），另一个线程锁住从根到节点 4 的路径（黄色）。两条路径都经过 1 和 2，所以更新节点 3 时对 1、2 的锁可能延迟对 4 的更新。加锁可能阻碍并发。可 3 和 4 是独立的，本应能同时更新。
  • 事务：事务 A 读 1、2、3，写 3；事务 B 读 1、2、4，写 4。两个事务冲突，当且仅当一个的写集和另一个的读集或写集有交集。这里没有读写或写写冲突！（没有哪个事务写了别的事务访问的数据。）可以并发执行。
  • 例子 2：事务 A 读 1、2、3，写 3；事务 B 读 1、2、3，写 3。有冲突，事务必须串行化（两个事务都修改节点 3）。

有同学问两个都写 3 时会怎样。Kunle 反问，同学说给其中一个优先；对，必须串行化，至于具体怎样管理事务的执行后面讲，从抽象来看它们会被串行化。另一个同学问由谁确定读集和写集，Kunle 笑说：这只是抽象，细节一定会讲，别急。

性能：锁和事务对比。平衡树和 HashMap 上，粗锁、细锁和 TCC（一个用硬件实现的事务内存系统）的执行时间。有正确的硬件支持，事务能得到和细粒度锁一样好的性能；在细锁表现不好的情况下（平衡树），事务也表现很好。这就是动机：易用的编程模型加上细粒度并发的性能，只有冲突时事务才被串行化。

atomic 和双向链表

void PushLeft(DQueue *q, int val) {
    QNode *qn = malloc(sizeof(QNode));
    qn->val = val;
    QNode *leftSentinel = q->left;
    QNode *oldLeftNode = leftSentinel->right;
    qn->left = leftSentinel;
    qn->right = oldLeftNode;
    leftSentinel->right = qn;
    oldLeftNode->left = qn;
}

用 atomic() 让双向链表的 PushLeft 方法线程安全。Kunle 给了几分钟和邻座讨论。同学答：qn->val = val 之后的所有行都放进 atomic： 

void PushLeft(DQueue *q, int val) {
    QNode *qn = malloc(sizeof(QNode));
    qn->val = val;
    atomic {
        QNode *leftSentinel = q->left;
        QNode *oldLeftNode = leftSentinel->right;
        qn->left = leftSentinel;
        qn->right = oldLeftNode;
        leftSentinel->right = qn;
        oldLeftNode->left = qn;
    }
}

把对双向链表相关变量的所有操作都变成原子的，不用手递手加锁、不用想清楚谁是谁，只说"这些都要原子，系统照办"。

另一个动机：失败原子性

void transfer(A, B, amount) {
    synchronized(bank)
    {
        try {
            withdraw(A, amount);
            deposit(B, amount);
        }
        catch(exception1) { /* undo code 1 */ }
        catch(exception2) { /* undo code 2 */ }
        ...
    }
}
  • 手动捕获异常很复杂：程序员要逐个情况提供"撤销"代码；要记住撤销什么、怎样撤销，在异常处理里释放拿到的锁，把内存和系统状态恢复到方法执行前；有些副作用可能已经对其他线程可见；比如一个没捕获的情况就可能让系统死锁……
void transfer(A, B, amount)
{
    atomic {
        withdraw(A, amount);
        deposit(B, amount);
    }
}
  • 系统现在负责处理异常：所有异常（除了程序员显式管理的），事务中止，内存更新被撤销。
  • 回忆：事务要么提交、要么不提交，没有部分更新对其他线程可见。
  • 比如失败的线程不会持有锁……中止事务就像一次大撤销，系统状态回到事务开始前，不用操心恢复什么状态、释放哪些锁，是很干净的异常恢复方式。

另一个动机：可组合性

软件开发里很重要的思想是把小模块组合成更大更复杂的系统，但用锁时可组合性就崩了。 

void transfer(A, B, amount)
{
    synchronized(A) {
        synchronized(B) {
            withdraw(A, amount);
            deposit(B, amount);
        }
    }
}

// Thread 0: transfer(A, B, 100)
// Thread 1: transfer(B, A, 200)
// DEADLOCK!

嵌套的 synchronized：先锁账户 A，再锁账户 B。线程 0 调 transfer(A, B)，线程 1 调 transfer(B, A)：一个先拿到 A 的锁，另一个先拿到 B 的锁，死锁，"致命的拥抱"。课件还有一个版本：transfer 先锁 A 再锁 B，另一个函数 transfer2(B, A, amount) 先锁 B 再锁 A，同样死锁。

怎样修？同学说用事务内存，那只给你锁呢？同学说总按同样顺序加锁：按某个全局顺序获取锁，比如总先锁编号小的。但这个全局机制破坏了可组合性：要组合这些简单部件，得知道全局该怎么做。

  • 组合基于锁的代码可能很棘手：需要全系统范围的策略才能做对；全系统范围的策略会破坏软件的模块化。
  • 程序员进退两难：粗粒度锁，性能低；细粒度加锁，性能好，但一出错就可能死锁。
void transfer(A, B, amount) {
    atomic {
        withdraw(A, amount);
        deposit(B, amount);
    }
}
  • 事务能优雅地组合（理论上）：程序员声明全局意图（transfer 要原子执行）；不需要知道全局的实现策略；transfer 里的事务包含了 withdraw 和 deposit 里定义的事务；最外层的事务定义原子性边界。同学说得对：外层 atomic 优先，假定外层 atomic 里的一切都是原子的。
  • 系统尽可能好地管理并发：transfer(A, B, 100) 和 transfer(B, A, 200) 串行化；transfer(A, B, 100) 和 transfer(C, D, 200) 并发。

有同学以为第二个例子不该放进 atomic，否则一次只能做一件事。Kunle 让他回想树的例子：这两个事务有冲突吗？没有，所以它们应该能并发运行。两个事务同时执行，有冲突就串行化，没有就并发，一定要明白这一点。

事务内存的优势（承诺）

  • 易用的同步结构：程序员很难把同步做对；程序员声明需要原子性，系统把它实现好；声称事务和粗粒度锁一样容易用。
  • 往往和细粒度锁表现一样好：自动提供读读并发和细粒度并发；性能可移植性：适合 4 个 CPU 的加锁方案对 64 个 CPU 可能不是最好的；事务内存的生产力论据：系统对事务的支持能获得专家用细粒度锁编程的大部分好处，开发时间少得多。
  • 失败原子性和恢复：线程失败时不会丢锁；失败恢复 = 事务中止 + 重启。
  • 可组合性：安全、可扩展地组合软件模块。

为什么只能得到"大部分"好处，不是最优的吗？有时你知道数据结构的一些东西：只看读写集会认为它们冲突，但你知道其实不冲突、可以并发。通常是你带进实现的额外知识让你能做得更好。细粒度锁在有些情况下可能比事务更细，也可能更好。

四、自测：atomic { } ≠ lock() + unlock()

  • 区别：atomic 是原子性的高层声明，不规定原子性的实现；锁是底层的阻塞原语，它本身不提供原子性或隔离性。
  • 记住：锁可以用来实现 atomic 块，但锁还能用于原子性以外的目的，不能把锁的所有用法都换成原子区域；atomic 消除了很多数据竞争，但用 atomic 块编程仍可能出现原子性违例，比如程序员错误地把本该原子的一段拆成两个 atomic 块。
  • 一定要弄明白语义上的这个区别！

在这个例子里把 synchronized 换成 atomic 会怎样？

// Thread 1
synchronized(lock1)
{
    ...
    flagA = true;
    while (flagB == 0);
    ...
}

// Thread 2
synchronized(lock2)
{
    ...
    flagB = true;
    while (flagA == 0);
    ...
}

用两把不同的锁，两个线程能互相看到对方设的标志。换成 atomic：同学说两个块要以可串行化的方式调度，而这段代码依赖于一个线程设标志发生在另一线程设标志和 while 循环之间。会发生什么？atomic 的第二个性质是隔离性：事务提交前观察不到它的写。所以谁也看不到对方的标志，两个都永远在 while 里转，没有进展，是死循环。这里把 synchronized 换成 atomic 行不通。

程序员错误造成的原子性违例

// Thread 1
atomic
{
    ...
    ptr = A;
    ...
}

atomic
{
    B = ptr->field;
}

// Thread 2
atomic
{
    ...
    ptr = NULL;
}

程序员的错误：线程 1 里逻辑上原子的代码序列被错误地拆成两个 atomic 块，另一个线程可以在中间把指针设成 NULL。同学答：不知道三个 atomic 的执行顺序，如果在 ptr = A 之后 ptr 被设为空，最后那个 atomic 会解引用空指针。修法：合成一个 atomic。这叫原子性违例：把 atomic 套在了错误的代码范围上。

五、实现事务内存

回忆事务的语义：原子性（全有或全无：提交时所有内存写同时生效，中止时没有写看起来生效）；隔离性（提交前其他代码观察不到写）；可串行化（事务看起来按单一串行顺序提交，但确切顺序不保证）。

实现的基础

  • 事务内存系统必须提供原子性和隔离性，同时保持尽可能多的并发。
  • 两个关键的实现问题：
    • 数据版本管理策略：系统怎样为并发的事务管理未提交（新）和之前已提交（旧）的数据版本？
    • 冲突检测策略：系统怎样、何时判断两个并发事务冲突？

数据版本管理

为并发的事务管理未提交（新）和之前已提交（旧）的数据版本：1. 急切版本管理（基于撤销日志）；2. 懒惰版本管理（基于写缓冲）。

急切版本管理：立即更新内存，维护"撤销日志"以备中止。之所以叫急切，是尽早更新内存（这里的内存也可以是缓存）。

  • 开始事务：内存里 X = 10，撤销日志为空。
  • 写 x ← 15：把 x 的旧值 10 放进撤销日志，直接更新内存为 15。内存是最新的，这总是好事。
  • 提交事务：清掉撤销日志就完了，事务已提交，内存是最新的。
  • 中止事务：应用撤销日志，把内存恢复成 10。

课上问答：缓存怎么办，日志放在哪？会影响实现，后面讲软硬件两种管理方式；可以有专门的日志缓存，也可以放在普通内存里，这最可扩展，靠缓存利用局部性。中止只是因为错误吗？可以随时拉"中止绳"跳出事务，知道内存状态没被改变；另一个原因是检测到冲突，通常就重启事务再试。撤销日志只存事务开始前的值，也就是每个位置第一次写时的旧值，之后的更新不用再记。撤销日志本身坏了呢？那系统就坏了，需要别的机制处理内存容错，这里假设系统是健壮的。

懒惰版本管理：把内存更新记在事务的写缓冲里，提交时冲刷缓冲。大家都喜欢偷懒。

  • 开始事务：内存 X = 10，写缓冲为空。
  • 写 x ← 15：不直接更新内存，写进写缓冲，X: 15。
  • 提交事务：用写缓冲更新内存（X = 15），清空写缓冲。
  • 中止事务：直接扔掉写缓冲，内存没改过，还是 10。

这样事务里后面对 x 的读会复杂一点：值该从哪来？不是内存，要从写缓冲来，写缓冲里有被写过的变量的最新值。所以可能要查两个地方，取决于实现。撤销日志则从来不用查，只在修复中止的事务时用。

数据版本管理的权衡

  • 目标：为并发事务管理未提交（新）和已提交（旧）的数据版本。
  • 急切版本管理（基于撤销日志）：写时直接更新内存位置；在日志里维护撤销信息（每次 store 都有开销）。好：提交更快（数据已经在内存里），只需查一个地方。坏：中止更慢，容错有问题（想想在事务中途崩溃）。
  • 懒惰版本管理（基于写缓冲）：在写缓冲里缓存数据直到提交；提交时更新真实的内存位置。好：中止更快（清掉日志就行），没有容错问题。坏：提交更慢，要把写缓冲的内容应用到内存；可能要查多个地方。
  • 急切的哲学：立即写内存，希望事务不会中止（必须时再处理中止）。懒惰的哲学：只在必须时才写内存。

有同学问急切版本管理是否让隔离更难：另一个线程也在做事务，可能读到主存里早早写进去的值。Kunle 说是的，取决于冲突检测怎么做，马上讲。另一个同学问急切方式访存更频繁、冲突更多，选择时要考虑吗？选哪种版本管理，关键在于和冲突检测的搭配，两者是一起决定的。

冲突检测

  • 必须检测和处理事务之间的冲突：
    • 读写冲突：事务 A 读地址 X，而 X 被一个未决（还没提交）的事务 B 写过；
    • 写写冲突：事务 A 和 B 都未决，都写地址 X。
  • 系统必须跟踪事务的读集和写集：读集是事务中读过的地址；写集是事务中写过的地址。

悲观检测

  • 在 load 或 store 时（立即）检查冲突。哲学："我怀疑可能有冲突，所以每次内存操作后都查一下有没有发生……如果得回滚，不如现在就做，免得白干。"也叫遇到即检测（encounter detection）。
  • 检测到冲突时，由"争用管理器"决定停顿还是中止事务。有各种策略，让常见情况快。

下面的图假设一个"激进"的写争用管理器：写者赢，其他事务中止。每次访问都要检查冲突。

  • 情形 1，成功：T0 读 A，检查：T0 读集是 A，T1 写集为空，无冲突。T1 写 B，检查：T1 写集是 B，T0 读集是 A，无冲突。T0 写 C，检查：T0 读集 A、写集 C，T1 写集 B，无冲突。两个事务都提交。
  • 情形 2，提前检测（并停顿）：T0 写 A，检查。T1 读 A：T0 写集是 A，T1 读集也是 A，冲突。选择？可以中止 T1 重启；也可以假设 T0 某时会完成，让 T1 停顿。停顿比中止好在哪？同学答：T1 到目前为止做的工作不用扔掉，保持 T1 的状态，等 T0 提交后继续 T1，重新读 A（必须重读，才拿到正确的值）。如果 T1 之前读过 B，而 T0 后来又写了 B 呢？每次访问都在检查，T0 后面写 B 时会导致 T1 中止，停顿变成中止；状态一直在，检查一直在做。
  • 情形 3，中止：T0 读 A，检查：T0 读集 A，T1 读写集为空，通过。T1 写 A：写者赢，T0 中止、重启，重新读 A……T0 再读 A 时 T1 还没提交，停顿，T1 提交后继续。规则：读写冲突时写者赢；如果另一个事务已经写了而你要读，你停顿（你还没读，正在考虑这次读会不会冲突）；如果你已经读了、并基于它做了计算，然后来了一个写，你就得中止；看到写读冲突就立即中止重启。
  • 情形 4，没有进展：T0 写 A，检查通过。T1 写 A，检查不通过，写者赢，T0 中止重启。T0 又写 A，T1 中止重启……这个方案下不会有进展，系统必须检测到这种情况、让其中一个事务完成。这是活锁（问题：怎样避免活锁？）。

有同学问会不会有系统让读优先、让写的那个事务中止：Kunle 没见过这样的系统，想不出为什么要这样。也可以先来先服务，让已经在运行的事务赢、中止写的那个；争用管理有很多选项，不同系统根据应用场景实现了不同的策略。

乐观检测

  • 在事务试图提交时检测冲突。直觉："往好处想，只在事务提交时才把所有冲突理清。"
  • 冲突时优先保证正在提交的事务：其他事务可能随后中止。好处是总能让正在提交的事务优先。

规则：拿正在提交的事务的写集，和所有其他事务的读集比较。

  • 情形 1，成功：T0 读 A、写 C，T1 写 B，期间不检查。T1 提交：它的写集 B 对比 T0 的读集 A（T0 写集是 C），无冲突，提交。T0 提交，同样无冲突。
  • 情形 2，中止：T0 写 A，T1 读 A。T0 提交：写集 A，T1 读集 A，冲突，T1 中止重启。这里不能停顿，没法提前发现。这种事务有时叫"注定失败的事务"：其实已经知道它不会成功，因为系统里已经有一个会冲突的写，它做的工作都会浪费。
  • 情形 3，成功：T0 读 A（这次读可以发生在事务里任何时候，可能在 T1 写 A 之后），T1 写 A。T0 先提交：它的写集为空，对比 T1 的读集，没问题。然后 T1 提交。串行化后，读 A 在写 A 之前，T0 本就不该看到 T1 的更新。（课上 Kunle 说出题时会明确说明，也可以检查现有事务的写集是否冲突，但其实无所谓，提交的事务会更新内存状态，不会有冲突。）
  • 情形 4，有进展：T0 和 T1 都读 A、写 A。T1 先提交：读写集都有 A，和 T0 冲突，T0 重启，然后 T0 提交。悲观检测在这里没有进展，乐观检测有。

课上问答：情形 4 里 T1 在 T0 写 A 之后读 A，T1 写的值可能依赖 T0 写的 A，T1 都提交了才中止 T0，不会有问题吗？记住一切都是隔离的，提交前事务之间不传递任何值，T0、T1 读到的值要么在事务开始前就存在，要么是自己在事务里产生的。急切版本管理直接写内存，配合乐观检测怎么办？Kunle 笑说：急切版本管理和乐观检测配合得不好。为什么情形 3 不重启、情形 4 重启？提交事务的写集对比其他事务的读集：情形 3 里提交的 T0 写集为空，没有冲突；只单向比较，不反过来比。
