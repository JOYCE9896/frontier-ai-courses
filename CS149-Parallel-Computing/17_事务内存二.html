第十七讲：事务内存（二）软件与硬件实现

冲突检测的权衡和实现空间；软件事务内存：软件屏障、函数克隆、事务描述符和事务记录、数据到记录的映射和检测粒度；Intel McRT 算法：全局和局部时间戳、乐观读、悲观写、读集验证、提交，foo/bar 的例子；编译器优化把开销降到 30% 到 40%；为什么需要硬件：STM 慢 2 到 8 倍；硬件事务内存：在缓存里做版本管理、在一致性协议上做冲突检测、R/W 位、懒惰乐观的例子，TCC 和 Intel Haswell 的 RTM；最后开个头：异构并行

一、回顾和冲突检测的权衡

上一讲讲了事务内存要保持的性质、它的优势，以及设计时要考虑的两方面：用什么数据版本管理策略来跟踪已提交的旧数据和事务执行中产生的新数据（急切或懒惰）；怎样检测事务之间的冲突（悲观：在内存访问发生时检测；乐观：假设没有冲突，在事务提交时检测）。悲观检测的例子里出现过活锁，事务内存系统必须检测并从活锁中恢复，保证应用能前进；乐观检测里没有活锁，因为提交的事务总是赢：拿提交事务的写集和所有仍在执行的事务的读集比较，有冲突的那些中止，提交的事务完成提交。

课件复习时把生产力论据说得更具体：系统对事务的支持能用 10% 的开发时间，得到专家用细粒度锁编程 90% 的好处。

冲突检测的权衡

  • 悲观冲突检测（也叫"急切"）：
    • 好：尽早检测冲突（撤销的工作少，把一些中止变成停顿）；
    • 坏：没有前进保证，有些情况下中止更多；
    • 坏：细粒度通信（每次 load/store 都检查）；
    • 坏：检测在关键路径上。
  • 乐观冲突检测（也叫"懒惰"或"提交时"）：
    • 好：有前进保证；
    • 好：批量通信和冲突检测；
    • 坏：冲突检测得晚，仍可能有公平性问题。

事务内存的实现空间（例子）

  • 软件 TM 系统：
    • 懒惰 + 乐观（读写都乐观）：Sun TL2；
    • 懒惰 + 乐观读 / 悲观写：MS OSTM；
    • 急切 + 乐观读 / 悲观写：Intel STM；
    • 急切 + 悲观（读写都悲观）：Intel STM。
  • 硬件 TM 系统：
    • 懒惰 + 乐观：Stanford TCC；
    • 懒惰 + 悲观：MIT LTM、Intel VTM；
    • 急切 + 悲观：Wisconsin LogTM（和传统缓存一致性配合最容易）；
    • 急切 + 乐观：不实用。检测到冲突时，可能已经以难以恢复的方式改了内存。
  • 最优设计仍是开放问题，对硬件、软件和混合系统可能不同。

今天看的软件系统其实是一种混合：急切的，读乐观、写悲观，通过区别对待读和写同时做到两者。然后看硬件系统：先说明为什么需要硬件（想提高性能永远需要硬件），软件系统的性能开销可以用硬件缓解；也可以软硬件混合，针对软件系统里开销最大的部分谨慎地用硬件去削减。

二、软件事务内存（STM）

// what the programmer writes:
atomic {
    a.x = t1
    a.y = t2
    if (a.z == 0) {
        a.x = 0
        a.z = t3
    }
}

// what the STM system turns it into:
tmTxnBegin()
tmWr(&a.x, t1)
tmWr(&a.y, t2)
if (tmRd(&a.z) != 0) {   // slide's translation; the original tests a.z == 0
    tmWr(&a.x, 0);
    tmWr(&a.z, t3)
}
tmTxnCommit()
  • 为 TM 簿记插入软件屏障（STM 函数调用）：版本管理、读写集跟踪、提交……用锁、时间戳、数据拷贝等实现。这里的"屏障"不是同步用的屏障，只是调用事务内存系统的 tmRd、tmWr 函数，告诉系统要做什么簿记。每个写变成 TM 写，每个读变成 TM 读，要改写程序员给的代码。
  • 需要函数克隆或动态翻译：一个函数既在事务内又在事务外使用时，要两份，一份不带插桩、一份带。在 Java、C# 这类有虚拟机的环境里，可以自动做函数克隆，加上合适的软件屏障。

这是用软件实现事务的经典方式，用在事务内存上；也可以想象用类似的东西在别处保持数据一致。很多 TM 调用是冗余的，可以优化掉，后面会看到。

STM 运行时的数据结构

  • 事务描述符（每线程一个，或者说每事务一个）：用于冲突检测、提交、中止……包括读集、写集、撤销日志或写缓冲。
  • 事务记录（每份数据一个）：一个指针大小的记录，守护共享数据；跟踪数据的事务状态：
    • 共享：被多个读者访问，用版本号或共享的读者锁；
    • 独占：被一个写者访问，用指向拥有者的写者锁；
    • 顺便说一句：硬件缓存一致性就是这样工作的。和缓存一致性直接类比：缓存状态告诉你数据被多个 CPU（这里是多个事务）共享，还是被一个独占。

把数据映射到事务记录

每个数据项都有一个关联的事务记录。

  • Java/C#：嵌入在每个对象里（对象有 vtbl、事务记录 TxR、字段 x、y）；或者把字段、数组元素哈希到全局表 f(obj.hash, field.index)。
  • C/C++：基于地址哈希到全局表，以缓存行或字为粒度。

权衡是什么？同学说：对象粒度下认为所有字段一起处理，其实它们可能独立，比如 x 和 y；不独立时会有不必要的中止和重启。Kunle：对，冲突比实际需要的多。

冲突检测的粒度

  • 对象粒度：映射操作开销低；暴露优化机会（反复用同一对象时，可以分摊管理它的数据记录的开销）；会有伪冲突（比如例子里的 Txn 1 和 Txn 2）。
  • 元素/字段粒度（字）：减少伪冲突；提高并发（比如 Txn 1 和 Txn 2）；开销增加（时间和空间）。
  • 缓存行粒度（多个字）：和硬件 TM 一致；减少事务记录的存储开销；程序员和编译器难以分析，和程序员写的东西没有直接对应。
  • 按类型混搭：比如数组用元素级、非数组用对象级，这是相当好的折中。

例子：Txn 1 写 a.x 和 a.y，Txn 2 读 a.z。按对象粒度，两个事务冲突；按字段粒度，没有冲突。

三、一个 STM 算法的例子

  • 基于 Intel 的 McRT STM [PPoPP'06、PLDI'06、CGO'07]：急切版本管理，乐观读，悲观写（写时拿锁）。
  • 基于时间戳做版本跟踪：
    • 全局时间戳：写事务提交时递增；
    • 每个事务的局部时间戳：事务上次验证时的全局时间戳值（事务开始时打上）。
  • 事务记录（32 位）：
    • 最低位：0 表示被写者锁住，1 表示未锁；
    • 高位：未锁时是上次提交的时间戳（版本号）；锁住时是指向拥有者事务的指针。

类比缓存一致性：最低位是 1 时，数据是什么状态？同学答：共享。是 0 时是独占，正被指针指向的那个事务写。

STM 操作

  • STM 读（乐观）：
    • 直接读内存位置（急切）；
    • 验证读到的数据：检查是否未锁，且数据版本 ≤ 局部时间戳；
    • 如果不是，验证读集里所有数据的一致性；
    • 插入读集；
    • 返回值。
  • STM 写（悲观）：
    • 验证数据：检查是否未锁，且数据版本 ≤ 局部时间戳；
    • 获取锁；
    • 插入写集；
    • 创建撤销日志项；
    • 就地写数据（急切）。

课上讨论读：假设先检查再读。如果数据被锁住，说明什么？有一个事务正在写它，该不该读？大概不该，争用管理器可能说等着，那个事务完成后再读。如果没锁、但检查没通过（数据版本大于局部时间戳）呢？说明本事务开始后，有别的事务修改过它。这不意味着本事务读错了，数据已经更新，拿到的是最新副本；但要确保其余数据都还好，于是重新验证整个读集。之所以说读是乐观的：验证通过后就放心了，直到有别的事务要提交；写时拿锁所以写是悲观的；但写的时候并不检查有没有读者读过这个数据，读者可以照常进行，冲突可能在这个事务后来提交时才被检测到。

STM 操作（续）

  • 读集验证：
    • 取得全局时间戳；
    • 对读集里的每一项：如果被别人锁住，或数据版本 > 局部时间戳，中止；
    • 把局部时间戳设为第一步取得的全局时间戳。读集全部验证通过，就好像本事务是在此刻开始执行的。
  • STM 提交：
    • 原子地把全局时间戳加 2（最低位用作写锁标记，所以每次加 2）；
    • 如果加之前的（旧）全局时间戳 > 局部时间戳，验证读集，检查有没有最近提交的事务会导致本事务中止；
    • 对写集里的每一项：释放锁，把版本号设为全局时间戳。

有同学问被锁住和版本号更新有什么区别，不都是同一件事吗？另一个同学答：锁住表示另一个事务正在写，写正在进行；版本号变大表示写已经发生了。有同学问是先原子地递增全局时间戳、再用旧值验证读集吗？是的。

STM 的例子

// X1: copies object foo into object bar
atomic {
    t = foo.x;
    bar.x = t;
    t = foo.y;
    bar.y = t;
}

// X2: should read bar as [0,0] or [9,7]
atomic {
    t1 = bar.x;
    t2 = bar.y;
}

初始 foo = {x = 9, y = 7}，时间戳 3；bar = {x = 0, y = 0}，时间戳 5。X1 把 foo 拷到 bar；X2 原子地读 bar，应该读到 [0,0] 或 [9,7]，不能看到部分更新。这个例子是上面算法的一个小变体：没有局部或全局时间戳，每个对象有一个时间戳。

  1. X1 读 foo.x，读集加入 <foo, 3>。
  2. X2 读 bar.x，读集加入 <bar, 5>。
  3. X1 写 bar.x = 9：拿写锁（bar 的记录指向 X1），写集加入 <bar, 5>，因为是急切模式，把 bar.x 的旧值 0 放进撤销日志 <bar.x, 0>。
  4. X2 要读 bar.y：同学说对象粒度下应该判为无效。验证时看到 bar 被锁住，假设它等待，X2 停顿。
  5. X1 读 foo.y（读集里仍是 foo，时间戳 3），写 bar.y = 7，撤销日志加入 <bar.y, 0>。
  6. X1 提交：先验证读集，foo 的时间戳两次都还是 3，通过；提交，把 bar 的时间戳加 2，从 5 变成 7（<bar, 7>）。
  7. 解除 X2 的停顿，X2 读 bar.y，拿到新的时间戳。X2 到提交点，先验证读集：第一次读的 <bar, 5> 已经不对了，验证失败，中止；重新执行，得到 bar 的正确值。

有同学指出：读了两次 foo 有两项，写了两次 bar 写集里却只有一项。Kunle 说按对象粒度，这里又是悲观检测加撤销日志，写集具体有什么不太重要，但严格说应该为第二次写 bar 再加一项。

TM 实现小结 1

  • TM 实现：数据版本管理，急切或懒惰；冲突检测，乐观或悲观；粒度：对象、字、缓存行……
  • 软件 TM 系统：编译器（或虚拟机）加入版本管理和冲突检测的代码；注意 STM 屏障 = 插桩代码；基本数据结构：每线程的事务描述符（状态、读写集……），每份数据的事务记录（锁住/版本）。

STM 系统的挑战

  • 软件屏障的开销；
  • 函数克隆；
  • 健壮的争用管理；
  • 内存模型（强原子性与弱原子性）。

优化软件事务

整块的屏障把冗余的日志和加锁藏起来，编译器看不到： 

tmTxnBegin()
tmWr(&a.x, t1)
tmWr(&a.y, t2)
if (tmRd(&a.z) != 0) {
    tmWr(&a.x, 0);
    tmWr(&a.z, t3)
}
tmTxnCommit()

把屏障分解开，冗余就暴露了： 

txnOpenForWrite(a)
txnLogObjectInt(&a.x, a)
a.x = t1
txnOpenForWrite(a)
txnLogObjectInt(&a.y, a)
a.y = t2
txnOpenForRead(a)
if (a.z != 0) {
    txnOpenForWrite(a)
    txnLogObjectInt(&a.x, a)
    a.x = 0
    txnOpenForWrite(a)
    txnLogObjectInt(&a.z, a)
    a.z = t3
}

编译器就能优化 STM 代码，产生更少、更便宜的 STM 操作： 

txnOpenForWrite(a)
txnLogObjectInt(&a.x, a)
a.x = t1
txnLogObjectInt(&a.y, a)
a.y = t2
if (a.z != 0) {
    a.x = 0
    txnLogObjectInt(&a.z, a)
    a.z = t3
}

对象 a 只需要打开一次写；a.x 已经记过撤销日志，第二次写不用再记。

编译器优化的效果

McRT 论文的数据：HashMap（大约 80% get、20% put）和 TreeMap，单线程相对于线程不安全基线的开销。0% 是不线程安全的代码；蓝条是在整个方法外套一把粗锁；未经编译器优化的 STM 在单处理器上有 70% 到 80% 的开销；加上编译器优化后大幅下降：比没有并发控制多不到 40%，比基于锁的同步多不到 30%。

有同学说粗锁只多 10%，快得多。Kunle：单处理器上是这样，但它不能扩展，前面看过了。要扩展就得用细粒度锁（这里没画）或事务。没有任何同步的代码根本不线程安全，不能并行地正确运行，所以要和同步的开销比；用事务内存加编译器优化，得到既能扩展、开销又合理的东西。

STM 练习

给定一个乐观读、悲观写、急切版本管理的 STM，实现下面的原子区域需要哪些步骤？ 

atomic {
    obj.f1 = 42;
}

// answer:
tx = GetTxDescriptor();            // assume a way to get transaction descriptor
OpenForWriteTx(tx, obj);
LogForUndoIntTx(tx, obj, offset);  // record old value in the undo log
obj.f1 = 42;

同学答：如果未锁就验证，拿锁、加入写集、记入撤销日志，然后写数据。OpenForWrite 做检查和加锁，记日志，因为是急切的，直接写。

四、为什么需要硬件支持

  • STM 的减速：由于屏障，每线程 2 到 8 倍的开销（这是未像 McRT 那样经过编译器优化的 STM）。短期问题：打击人们写并行程序的积极性；长期问题：浪费能量。
  • 缺乏强原子性：纯靠软件提供代价太高。
  • 课件的图：三层服务器应用（Vacation）的加速比，STM 远低于理想线。

STM 为什么慢？

  • 实测单线程 STM 性能，比顺序执行慢 1.8 到 5.6 倍。
  • 大部分时间花在读屏障和提交上：大多数应用读的数据比写的多。kmeans 和 vacation 的执行时间分解：STM 写、STM 读、STM 提交、忙于有用工作。

有了硬件事务内存，就不需要显式屏障，不用告诉系统"我在读""我在写"，只做普通的 load 和 store，让硬件做正确的事。

硬件支持的类型

  • 硬件加速的 STM 系统（HASTM、SigTM、USTM……）：从一个 STM 系统出发，找出关键瓶颈；提供（简单的）硬件原语来加速，但保留软件屏障。写版本管理在软件，冲突检测在硬件。
  • 基于硬件的 TM 系统（TCC、LTM、VTM、LogTM……）：版本管理和冲突检测直接在硬件里；没有软件屏障。
  • 混合 TM 系统（Sun Rock……）：结合 HTM 和 STM，需要时切换模式，依据事务特征、可用资源等。写版本管理和冲突检测都在软件里（硬件模式时由硬件做）。

硬件事务内存（HTM）

  • 数据版本管理在缓存里实现：缓存写缓冲或撤销日志；增加新的缓存行元数据，跟踪事务的读集和写集。
  • 通过缓存一致性协议做冲突检测：一致性查找检测事务之间的冲突；可配合监听和目录式一致性。
  • 注意：事务开始时还必须为寄存器状态做检查点（中止时恢复执行上下文状态），很多处理器都支持。

现代处理器里已经有实现事务内存的机制：已经有一致的共享内存，已经有缓存，在缓存里做版本管理，在一致性之上做冲突检测。

HTM 设计

  • 缓存行加注释，跟踪读集和写集：R 位表示数据被事务读过（load 时置位）；W 位表示数据被事务写过（store 时置位）；R/W 位可以是字粒度或缓存行粒度；事务提交或中止时成组清零（gang-clear）；急切版本管理还需要为撤销日志再写一次缓存。
  • 一致性请求检查 R/W 位来检测冲突：
    • 观察到对 W 字的共享请求，是读写冲突（我已经写了这一行，别的处理器想读）；
    • 观察到对 R 字的独占（打算写）请求，是写读冲突（我已经读了，别的处理器想写）；
    • 观察到对 W 字的独占（打算写）请求，是写写冲突。
  • 缓存行：MESI 状态位（比如 M 状态）、标签、R、W 位（跟踪这一行是否在未决事务的读写集里）、行数据（比如 64 字节）。这里的图以缓存行粒度跟踪读写集。

Xcommit
  1. 事务开始：初始化 CPU 和缓存状态，为寄存器做检查点。缓存里原有 C = 9（有效，R、W 为 0）。
  2. load A：必要时处理缓存缺失；把数据标为读集的一部分（A 的 R 位置 1）。为简单起见假设缓存行只有一个字。
  3. load B：同样，B 的 R 位置 1。
  4. store C ⇐ 5：必要时处理缓存缺失；把数据标为写集的一部分（C 的 W 位置 1，值为 5）。注意：这不是以独占状态装入。为什么？因为事务是隔离的，在到达提交点之前不参与一致性，别的事务和线程还不知道。
  5. 提交，快速两阶段提交：验证，对写集的行请求 RdX 访问（如果需要），也就是向所有人发出升级 C 的请求，C 现在是脏（独占）状态；提交，成组清零 R 和 W 位，把写集数据变成有效的（脏）数据。

快速冲突检测和中止：检查，在读集和写集里查找外来的独占请求；中止，让写集失效，成组清零 R、W 位，恢复到寄存器检查点。假设远处的处理器提交了一个写 A 和 D 的事务：看到对 A 的升级请求，冲突，因为 A 在缓存里而且 R 位置位（注意，A 可能在事务开始前就在缓存里但没有 R 位，仅仅在缓存里不代表冲突）；远程核写 A 和本地读 A 冲突，触发本地未决事务中止。看到对 D 的升级呢？什么都不做，D 不在缓存里，不可能冲突。

这个硬件系统的策略是什么？同学先说急切，Kunle 反问：升级到底什么时候发生？在提交时，听起来是乐观的；数据版本管理呢？懒惰的，缓存就是写缓冲，提交时说"这些是我写过的，现在公布给全世界"，和所有人的读集比较，靠发出这些升级请求来比。所以是懒惰乐观。有同学问读集里的行要做什么：就做一次普通的读，从内存或从之前以已修改状态持有它的缓存取得，处于共享状态。

HTM 性能的例子

  • 比 STM 性能高 2 到 7 倍；
  • 单线程时在顺序执行的 10% 以内；
  • 随处理器数高效扩展（Vacation 的加速比图上，HTM 接近理想线，STM 远低于它）。

回顾：事务内存

  • atomic 结构：声明系统必须保持原子行为。动机：在不（显著）牺牲性能的前提下让同步更简单。
  • 事务内存实现：提出了很多变体，软件、硬件、软件加硬件；区别在于数据版本管理策略（急切或懒惰）、冲突检测策略（悲观或乐观）、检测粒度（对象、字、缓存行）。
  • 软件 TM（STM）：编译器加入版本管理和冲突检测的代码；STM 屏障 = 插桩代码（比如 StmRead、StmWrite）；每线程的事务描述符（状态、读写集……），每份数据的事务记录（锁住/版本）。
  • 硬件事务内存（HTM）：版本化的数据保存在缓存里；冲突检测机制扩展了一致性协议。

五、HTM 的例子：事务一致性与一致性（TCC）

  • 把 TM 当作一致性机制：一直都是事务，所有时候都是事务。
  • 成功的事务提交会更新内存和系统里所有缓存。到提交点时把修改过的状态全发出去，更新所有人，这是典型的懒惰乐观；除此之外没有别的状态。
  • 假设：懒惰和乐观；所有处理器每个执行步只有一次"提交"（像基于总线的方案，一次只有一个事务在提交并更新所有人）；一个事务导致另一个事务中止并重新执行时，假设前者的"提交"可以和重新执行的事务的"开始"重叠；尽量减少执行步数。

练习：三个处理器上四个事务，填出每一步每个处理器的动作、读集和写集。 

// P1
Begin T1
Read A
Write A, 1
Write C, 2
Read D
Commit T1

// P2
Begin T2
Read A
Write E, 3
Commit T2
Begin T3
Write C, 4
Read A
Write E, 5
Commit T3

// P3
Begin T4
Read E
Write B, 6
Write C, 7
Read F
Commit T4

要点：

  • 懒惰乐观的规则：拿提交事务的写集，和其他事务的读集比较。
  • T2 在 P2 上先提交（写集 E），P3 上的 T4 读过 E（读集有 E:0），冲突，T4 必须重启；T2 的提交和 T4 的重新开始可以重叠。
  • T1 在 P1 上提交，写集是 A、C；当时其他事务的读集里如果有 A 就要中止。
  • 有同学问：T1 的写集有 C，T4 的写集也有 C，两个都写，不冲突吗？只有读集要紧，这只是覆盖，谁先到不影响数据一致性，T4 从没读过 C，只是写了它，结果仍然正确。

（课件上这张推演表在提取时错位较多，同学还在课上指出表里有一处和代码不符，Kunle 笑着承认"不保证没有 bug，应该修一下"。考试时要能按给定的规则推演这类序列。）

有同学问实现上是不是假设所有处理器同时看到：假设提交发生时，提交事务的写集是全局可知的。有总线时一次只能有一个事务在总线上，这让事情简单了，串行化好推理，总线提供了串行化点；没有总线的系统里问题会难得多。有同学问是不是有专门的指令：是的，会有显式的硬件指令。还有人问加几条总线行不行：有了多条总线就失去了串行化的好处，得想别的方案。总线不能扩展，课上讲总线只是因为好讲；最早的多核处理器确实是基于总线的，因为最容易实现、而造硬件很贵，但今天没有人用总线造任何东西，性能不好。

Intel Haswell 架构里的硬件事务内存支持

  • 新的"受限事务内存"（RTM，restricted transactional memory）指令：xbegin，接受一个中止时的"回退地址"，比如回退到使用自旋锁的代码路径；xend；xabort。实现：在 L1 缓存里跟踪读集和写集。
  • 处理器保证所有内存操作原子地提交，但处理器可能因为很多原因自动中止事务（比如读集或写集里的行被逐出就会中止）；实现不保证进展（见回退地址）；Intel 优化指南（第 12 章）给出了提高事务不中止概率的建议。

Kunle 说 Intel 架构里实现过硬件事务内存支持，但因为各种原因效果不太好：使用它的软件没像人们希望的那样发展起来；能力有限，事务几乎可以因任何原因中止，中止往往多于必要；最后给它钉上棺材钉的是它打开了被人利用的安全漏洞。Intel 的路线图里仍计划加入事务内存，ISA 手册里也有支持它的指令定义，但最新的实现里没有。IBM 实现过，Sun 在被 Oracle 收购前也实现过。

商业上用得更多的是软件，而且是把事务内存局部地用在很难用锁实现的地方：某些数据库系统在数据库管理系统的核心用事务内存的思想来实现部分功能。人们设计为事务内存优化的数据结构，系统的一部分用事务内存实现，而不是整个并行系统都用。为什么用得少？要有软件实现的事务内存系统，想要好性能还得有编译器支持，而且不完全通用，要克隆代码，整个系统没那么健壮。几乎所有商用的都是软件方案，"几乎没人用硬件，因为硬件坏了"。有同学问硬件将来会不会真的好用，Kunle 说这是好问题，是开放问题。有同学问能不能用单独的缓存避免"行被逐出就中止"：你永远不想专门化，专门化后不用事务内存的程序就用不上那些资源，想复用同样的资源。事务内存大约十年前是产出了海量研究的领域，用 Google 搜就会看到无数想法和论文。

总结：事务内存

  • atomic 结构：声明系统必须保持原子行为。动机：在不（显著）牺牲性能的前提下让同步更简单。
  • 事务内存实现：很多变体，软件、硬件、软件加硬件；版本管理策略（急切或懒惰）、冲突检测策略（悲观或乐观）、检测粒度（对象、字、缓存行）。
  • 软件 TM 系统：编译器加入版本管理和冲突检测的代码；STM 屏障 = 插桩代码；每线程的事务描述符，每份数据的事务记录。
  • 硬件事务内存：版本化的数据保存在缓存里；冲突检测机制建立在一致性协议之上。理解了缓存一致性，理解事务内存系统怎样实现只差一小步。

六、开个头：异构并行

最后几分钟 Kunle 引入下一个主题。到目前为止讲的是用多核、GPU、SIMD 来利用并行，重点是通用计算、写相当通用的并行程序。但想更高效地使用硬件，可能需要更专门的东西：给定现代 CPU 或 GPU 的资源，怎样用好它们是一回事；更进一步：如果有个算法想跑得非常高效，怎样让它能效高得多？

观察：大多数真实应用的工作负载特征很复杂：有些部分能大规模并行，有些很难并行；有些适合宽 SIMD 执行，有些不适合（控制流发散）；有些部分的数据访问可以预测（可以预取），有些不可预测但可能缓存得很好。想法：最高效的处理器是各种资源的异构混合（"用最高效的工具做每件事"）。

现代处理器其实都是异构的。比如 Intel Skylake（2015，第六代 Core i7 架构，myth 机器里的芯片）：4 个 CPU 核加图形核加媒体加速器；集成的 Gen9 GPU（图形加媒体）占芯片相当大的面积；CPU 核和图形核共享同一个内存系统和 LLC（L3 缓存），让 CPU 和集成 GPU 之间能低延迟、高带宽地通信；图形核和 CPU 核是缓存一致的。异构意味着硅片资源和能量的使用效率更高，但编程模式更难：CPU 核要多线程，GPU 要 CUDA 之类的数据并行编程模型，媒体部件可能要另一种编程模型。下次接着讲现代计算格局里的各种异构，以及怎样应对编程问题，尤其是作业里这类机器学习应用。
