第十四讲：期中复习课

这一讲没有课件，是答疑式的复习：前半学期的主题地图；compare-and-swap 和"不互斥却得到互斥的效果"的无锁思维；CAS 在一致性协议里的代价；重讲 MapReduce，以及"横向扩展"和局部性；两位同学上台扮演缓存，现场走一遍 MSI；MESI 与第五个状态；地址之间的独立性；放松一致性和程序顺序；分段扫描该掌握到什么程度；CUDA 线程块调度和 warp

主讲：Kayvon Fatahalian
资料来源：课堂录像（Stanford Online，2023 年秋季）；本讲没有课件，内容根据录像整理

一、前半学期的主题地图

Kayvon 先列出前半学期的几条主线，说明期中考什么、考到什么深度：

  • 多核架构（第一到三讲）：多核、SIMD、多线程、超标量，你懂不懂？肯定会考。
  • 优化并行程序的一般策略：大多是在编程作业里自己摸索出来的，办公时间里考前一般不花太多时间。比如给你一个负载不均的程序，能认出来；一个缓存性能很差的程序，能不能改改循环顺序来改善。
  • GPU 架构：就是前三讲的东西再来一遍，GPU 以同样的方式工作，不奇怪。要懂 CUDA 编程模型的基础：线程块组织、块里的线程，写完作业 3 应该很熟悉了。
  • 深度神经网络那一讲：任何特定网络的细节都不重要。两三个主要概念：缓存局部性很重要，所以讲了分块；其他的是专用硬件之类，后面还会细讲，更像期末的内容。
  • 数据并行思维：可能出一道数据并行思维的练习，检验你是自己做了 find repeats，还是交给队友了，那现在就露馅了。
  • 细粒度加锁：讲了 compare-and-swap，实现锁，以及和缓存一致性的有趣关系；用锁、细粒度加锁，给了练习题。期中水平的细粒度加锁题会比练习题简单，大概不超过链表这种程度；练习题里有哈希表、图、树等，想给大家更多时间琢磨，再出难题。
  • Kunle 讲的：MSI 协议、缓存一致性的含义和主要思想；放松的内存一致性：一个线程写 X 再读 Y，其他处理器可能以不同的顺序看到这些写和读，有些有意思的含义。

然后就按同学们举手提的主题来讲。

二、compare-and-swap 和无锁思维

有同学想再过一遍上次简要讲到的无锁编程。Kayvon 说课上没强调的东西不会拿来考。

到目前为止同步基本有两种方式。一是锁：互斥是什么意思？同学答：一段代码一次只有一个线程运行。这个细节很重要：只允许一个执行者在某段代码里，我在里面，你们都被挡着。二是原子操作，也是这种心态，通常用于读改写：我在读、改这个变量时，别人不能读改它。compare-and-swap 是原子操作的一种，读、比较、写：读变量的值，如果等于参数 compare，就把新值写进去；否则相当于把旧值写回去，不变。无论在什么硬件平台上调用，它保证原子执行，这可以当作前提。

怎样用原子 CAS 实现 atomic min？一种想法是硬件直接给一个原子 min 原语。但我们不是这样设计系统的，不会为每件想做的事造一个新原语，而是要一个坚如磐石、也许很快的原语，用在各种场合。min 要求：从内存读值，检查新值是否更小，更小就更新，整个过程原子。先确认：如果有锁，拿锁、读值、比较、可能更新、放锁，绝对正确，保证互斥，一次只有一个线程在做原子 min。

CAS 版的代码在做什么？它没有对整个 min 操作保证互斥，不同线程可以同时读到这个值、同时比较。同学说得很好：它保证得出 min 结论所依据的前提，在写入结论时仍然成立。读值，做该做的工作（这里是取 min，也可以是更贵的运算），最后回头看：内存里的值还是我开始时的那个吗？是的话，就可以确定没人来过，或者来过但没更新最小值。CAS 就做这件事：地址上的值还等于 old，就更新成 new；它返回内存里的值，等于 old 就说明成功了。

如果我做 atomic min 时，你作为另一个线程来了，读了值，发现你的值太大不用更新，我的 CAS 会成功吗？会。这里没有互斥，我们俩同时在所谓的关键区域里，但除非双方的动作真的需要同步，否则都能继续。也就是在投机：希望不冲突，先往前做，最后写之前检查假设是否成立，成立的话做过的工作都有效；不成立的代价是什么？重做，在旧值上做的工作可能都白费了。如果这个函数不是 min，而是很贵的运算，比如对值算某个指数再存回去，每次绕一圈 while 循环都要扔掉做过的工作重来。无锁思维是：要给出和互斥相同结果的表象，但实际上并不强制互斥。这是最大的思维差别。

感恩节后 Kunle 会讲几讲，其中两讲是事务内存，把这个想法扩展到任意函数、写很多变量：你只管写函数，它可能读写一堆变量，系统判断这些读写是否和其他处理器冲突，冲突就中止、让其中一个处理器回退。期中对无锁的掌握到这个程度就够了。课件里有无锁栈等的实现；无锁链表在有些并行课里会讲，正确实现插入和删除要一整节课，非常难写对，Kayvon 说他自己在考场上大概也写不出来，所以不会考。

有同学问无锁编程是否更容易饥饿。饥饿是系统在进展、某个线程却一直不成功。这个实现里没有保证线程间公平的机制；但上次讲的原子加锁解锁（除了票号锁）也没有。无锁还是互斥，和公平性是正交的。可以在失败几次后睡一会，做指数退避，锁里也可以这样做。

CAS 的开销

没有缓存一致性的话怎样实现原子 CAS？不只是读，还有写，得在系统里有专门的机制说"这是对这个地址的当前原子操作，其他核都不能访问它"，相当于为单个地址做了个简单版的缓存一致性。有缓存一致性时，CAS 的代价是什么？是一次 BusRdX，是写，即使失败也必须是写，这很贵。而且不只是 BusRdX：读到值以后，在比较和可能的写完成之前，一致性协议不能让这一行被别的处理器抢走。就像发 BusRdX 拿到行后，一般假设处理器在行被抢走前会执行它的写，否则两个处理器可能不停地 BusRdX、BusRdX，行总在写之前被抢走，活锁在同一条指令上。所以拿到可写状态的行后要先完成比较和写，缓存逻辑要稍复杂一点。

后面有同学追问：默认的 MSI 不是要先 BusRd、再 BusRdX 两步吗？CAS 也是两步？Kayvon 说不对。地址不在缓存里就是无效状态（缓存不会为所有可能的地址存一位"无效"，不在缓存里就是无效）。普通的读会进入共享，再写才升级，那是两步。但如果 CAS 不是原子地实现，处理器升到共享后，别的处理器可以随意产生总线流量、写这个值、读这个值，等我写时状态可能已经变了，原子性就没了。所以 CAS、test-and-set 这类原子操作，在一致性协议看来都是写，不管变量最后有没有被更新，从 I 一步到 M；否则需要额外的逻辑来保证原子性。

三、重讲 MapReduce

有同学想回顾分布式数据并行里的 MapReduce。任何编程系统，第一件事都是想清楚 API 是什么、API 函数的含义是什么。MapReduce 只有两个。历史：MapReduce 是 Google 出的一篇很简单的论文，大约 2000 年代初，早于 Spark。Google 有很多作业要处理海量数据，比如整个网页索引，为此已经建了 Bigtable、共享文件系统，世界上所有数据都在这个分布在大量计算机上的文件系统里；还有很多做数据挖掘的应用。典型例子是挖掘 Web 日志：一个几 TB 的巨大文本文件，每行是一条 Apache 日志，文件的不同部分散在不同机器上。以前 Google 的程序员得自己把数据从各机器取来再处理，很复杂。

  • map：受数据并行的 map 启发，但和数据并行思维那讲的定义不太一样。对文件的每一行（每样东西）运行函数 f。MapReduce 里 map 的输出不是任意类型，而是键值对：输入是一行字符串，输出比如键是用户代理（浏览器），值是 1；也可以是浏览器和错误信息之类。map 可以在所有机器上跑，文件分布在一千台机器上，就在已经存着那部分文件的机器上对那些行运行 map，数据不动。
  • 按键分组：然后是"魔法"，MapReduce 的高明在于这么简单的东西能管用这么多场合（也很笨拙、写死了）：系统把所有键相同的元组组织到一个文件里，每个键一个文件，文件里是匹配这个键的所有值的列表。这就是数据到处搬的地方，像一次大的重新排序，在 Spark 里叫 group by key 或 shuffle。因为已经有共享文件系统，就把这些信息存在文件里，并行文件系统就是数据洗牌的传输机制。
  • reduce：参数是一个键和一列值，产生一个结果。reduce 函数被映射到所有唯一的键上，拿到这个键的值列表（实际上就是一个文件的内容），做它想做的，比如统计这个键的行数。所以 reduce 这个名字不是并行归约，实际上是 map、按键分组、再 map：把每个键对应的列表映射成一个值。

你会觉得很怪：数据分布在所有计算机上，通信方式却是写进文件系统，再从另一个节点读回来。Spark 就说这很蠢，应该全在内存里做，并且用一套正经的数据并行算子，而不只是 map、reduce 和按键分组。有同学说 MapReduce 当初这样设计也许因为商用硬件便宜、数据量没现在大，不太在乎延迟，最初甚至没有主服务器的复制，是单点故障。Kayvon 说他当时不在场，不能权威地说动机，但借此强调：担心去磁盘，是因为延迟吗？不是。这是大规模并行，文件里有几十亿行，写出一个键值对后可以去做别的；reduce 阶段处理一个键时可以开始装下一个键的数据。有大量并行时延迟可以掩盖，你在乎的是带宽和吞吐。真正的问题是各阶段之间，整个 TB 级数据集都要从磁盘读出、写回、再读入，即使按键分组其实没做什么（全是窄依赖）。

当心对并行的迷恋

当时人们觉得十行代码就能用一千台机器，有容错、有并行，太棒了。后来有篇论文（在 Kunle 的课件里）指出：你们用 5000 个节点的 Spark 或 MapReduce 集群处理 500 GB 左右的数据集，这放得进笔记本的内存里（Kayvon 印象中实验是把数据从磁盘流式读入，留一块在内存里做几轮迭代，不每次都回磁盘），一台笔记本的一个核就能跑过 5000 个节点的 Spark 集群，因为人们迷上了并行，忘了局部性和带宽。2023 年，每小时 3 美元就能在 AWS 上租一台 512 GB 内存的机器。我们大多数时候处理的问题，都没超过几分钱能买到的规模。所以更合理的是重视局部性，也许扩展到 4 TB 内存的机器，而不是让代码能容忍一万个节点的故障。

Kayvon 还提到 Amazon Prime Video 团队大约一年半前的博文。AWS Lambda：你给一个函数，需要时帮你运行，不用管服务器，适合一秒以内的计算；没人访问时一分钱不花，访问突增时并行执行所有请求，不用操心扩展，虽然每次调用的代价不低。Prime Video 把整个系统建在这些微服务和 Lambda 上（一小段视频交给一个 Lambda 处理），而 Amazon 自己在卖 Lambda 服务。博文说：整个系统建在大规模横向扩展的 Lambda 上，现在又收回到少数几台服务器，因为局部性等原因；少量大服务器比几千台小服务器成本效率高 10 倍。性能一样，成本低 10 倍。任何系统里通信都会一次次咬你。如果你相信要处理的数据集大到永远没希望放进内存，比如几 TB 又几 TB 的数据库，那从第一天起就该按横向扩展设计，这才是这些系统真正有价值的地方。

四、上台扮演缓存：走一遍 MSI

考试开卷，而且只要考 MSI 都会给出状态图，所以不必背；但不把它完全装进脑子里，很难答题。用上一讲开头那个序列，请两位同学上台分别当缓存 0 和缓存 1，在黑板上写自己那一行的状态（Kayvon 开玩笑说当缓存要身高一米八以上，所以他不报名），Kayvon 当"不到一米八的内存系统"。

  1. P0 LD X：缓存 0 先喊"我要读"，等确认；确认后知道没人在写，以 S 状态装入 X。
  2. P0 LD X：什么都不做，连消息都不用发。缓存 0 处于共享状态，就保证了别人最多也是共享，不可能是已修改，继续读没问题。
  3. P0 ST X ← 1：缓存 0 喊"我要写"；缓存 1 耸耸肩，它根本没有这一行，"你随便"。缓存 0 从 S 转到 M，现在保证没有别的缓存有这个值，可以写，X 在 M 状态，值为 1。内存里的 X 还是 0。
  4. P0 ST X ← 2：又写，不需要任何一致性流量，保证缓存 1 没有这份数据，没必要告诉别人他们不需要知道的事。值为 2。
  5. P1 ST X ← 3：缓存 1 说"我要写，要以独占方式拿到"。缓存 0 的反应："我写过它"，于是冲刷：把值写回内存（内存更新为 2），自己的行转为无效。缓存 1 从内存读到这一行（值 2），更新为 3。
  6. P1 LD X：缓存 1 读，命中，什么都不做。
  7. P0 LD X：缓存 0 说要读；缓存 1 说"等一下，得冲刷"，冲刷 3 到内存。这时同学说"我转为无效，把标记给你"。Kayvon 停下来：这不是 MSI 协议，但它是正确的缓存一致性吗？完全正确，只是低效。按 MSI 应该留在共享状态，没理由丢掉，以后可能再读，再读时不用去内存取。现在两边都是共享。
  8. P0 ST X ← 4：缓存 0 看自己的数据结构，只能看自己的（不知道别的缓存的状态），是共享，所以不保证别人没有。要写就得先通知所有人：如果缓存 0 先改了值和状态再通知，缓存 1 可能还在继续读，读到过时的值。所以要拿独占访问：喊"我要写"，其他缓存都把副本丢掉，然后才写。写完要不要写回内存？MSI 不写，因为将来读的时候总能拿到最新值：
  9. P1 LD X：缓存 1 是无效的，内存里还是 3（已过时）。缓存 1 声明要读，缓存 0 冲刷 4 到内存（M 状态意味着是脏的），缓存 1 拿到 4。
  10. P0 LD Y：第一次是 Y 而不是 X，两边的 X 都是 S。缓存 0 说要读 Y，缓存 1 耸耸肩，它没有 Y。状态图是针对同一个地址保持一致的，每个地址都有一份这样的状态机在跑，缓存里可以同时有 X 是 S、Y 是 S。
  11. 之后对 Y 的写（P0 ST Y ← 1、P1 ST Y ← 2）：缓存 1 要修改 Y 时，没有 Y 的一方照样耸肩；一旦一方持有 Y 而另一方要写，就是失效、冲刷，和 X 上的过程一样。

要点：本地缓存的任何状态变化都要向所有其他缓存喊出来，因为其他缓存的数据结构里的状态让它们决定能做什么、不能做什么。至于怎样"告诉"所有人，这门课不讲，课上说成广播，底层一般是点对点消息，那是别的课的内容。

为什么要先写回内存再给对方？

为什么不直接把缓存行从一个缓存传给另一个？任何现代系统都这样做。Intel、AMD 的现代缓存一致性是五状态的，第五个状态是一种特殊的共享状态，意思是"别人需要这一行、而我有，我直接提供，不用他去内存取"。这是大家都想到的明显优化，但 MSI 里没有（这种协议叫 MOESI、MESIF 之类）。如果我以共享状态持有你要读的行，就直接给你，大家都是共享；如果我以已修改状态持有、你要读，我给你并冲刷到内存，大家都共享；如果我已修改、你也要修改，我可以不冲刷直接给你，你变为已修改，由你负责以后冲刷。

但要记住：说 load X，其实是包含 X 的那个缓存行，演示里假设一行只有一个值。往 X 写 4 时，这一行其余的数据没动，之所以要把整行写回内存，是因为不知道这一行里哪些是脏的。更高级的协议里传的也是整行；除非缓存在位或字节级别跟踪脏的程度。

MESI 和更好的协议

第四个状态 E 有什么好处？想想先读一个值、之后再写它这种计算机里很常见的情况。MSI 下读进来是共享，只知道可能有别的处理器也有；要写时还得出声说"我要写了"。MESI 下装入时看别人的反应：如果有人说"我以共享状态持有"，那我也该是共享；如果大家都说"关我什么事"，我就以"不脏、但保证别人没有"的状态装入，之后想写就直接从 E 翻到 M，不用告诉任何人。处于 E 时看到别人的读，什么都不做，降为 S。

有同学问：缓存行变成共享后，能不能再回到 E？状态图里没有这条转换。要怎么设计更好的协议？要从 S 升到 E，得让其他所有处理器都失效；或者每次写都问一遍别人"你还有吗"，那就失去了共享状态的意义。可以这样：任何处理器转为无效时（通常是因为别人的动作，但也可能是被自己的缓存逐出），告诉大家"我要转为无效了"，触发所有缓存报告自己是否以共享状态持有；如果只剩一个缓存持有，它就知道可以升到 E。这就是更高级的缓存一致性协议了。

不同地址之间互不影响

有同学问：装入 Y 时，如果 X 在已修改状态，要先把 X 冲刷吗？Kayvon 说这个问题很好，要确保大家都懂：不会。一致性是系统里每个地址一台状态机，不同地址不相互作用。唯一的交集与并行无关：把 Y 装进缓存可能逐出 X，X 因此要冲刷并转为无效，但那是普通的缓存行为，和一致性讨论无关。缓存永远是满的，读一个新值就要按某种策略踢掉一个已有的值；如果它是脏的（即处于已修改状态），就冲刷并转为无效，然后对新地址发 BusRd。从这张一致性图的角度，就是在为 X 腾出空间之前不发对 X 的总线事务；另有一张针对 Y 的图从已修改或共享转为无效。状态是按缓存行维护的。

五、放松一致性和程序顺序

有同学问内存一致性题怎么做，有什么诀窍。Kayvon 说没有秘诀，最好自己练习。这门课很重要的一项技能，是想清楚机器上什么时候在运行什么操作，也就是调度：这个线程在这个核上执行这条指令时，那个线程在那个核上执行哪条。比如本周的练习题：线程 T0 执行指令 1、2、3，线程 T1 执行 4、5、6。唯一的要求是 T0 观察到 1、2、3 的顺序，T1（可能在另一个处理器，或同一个核的另一个线程）观察到 4、5、6 的顺序；放到时间线上，1 在 4 前、4 在 2 后、3 插在中间，都没人阻止。要能想清楚所有可能性和观察到的结果。这其实假设了顺序一致性，存在某个全序。放松一致性就是：可能找不到办法把六个操作排在一条时间线上，使程序的效果和这个顺序相符。比如 1 和 2 都是写，这个处理器显然先做 1 再做 2，但这些更新在别人看来可能是另一个顺序。和一致性（coherence）不同，这里谈的是对不同地址的操作的效果顺序，coherence 只谈同一地址，两者完全正交。

有同学追问：放松一致性下也不总是按指令顺序，可以重排读写吧？Kayvon 很严肃地澄清：只有一个控制线程时，如果你得到和程序顺序不一致的结果，编译器或硬件就是坏的，放松一致性在单线程下不可能被看到。就像超标量执行，处理器乱序或并行执行指令，如果结果不同就是坏了。第一天就说过线程内指令会被重排，超标量就这样做，但你永远观察不到，仍然完全是程序顺序。放松一致性说的是：T0 认为自己先写了 X 再写了 Y；如果放松了写写顺序，T1 读 X 和 Y 时可能先看到 Y 更新、后看到 X 更新。这只关乎观察别的处理器的写。如果我自己的写都不符合 C 的语义，那就把计算机和编译器扔了。

有同学想过一遍所有可能的重排。Kayvon 笑说最后 12 分钟里范围扩大得太多了。出题时，比写写重排更复杂的题都极难出，所以写写重排是重点；或者想想有一个写，把别的读写移到它上面或下面意味着什么。也可能题目说"一切都放松，除了程序顺序没有任何保证"。最容易出的是写写重排。

六、分段扫描要掌握到什么程度

分段扫描只需要懂定义。它就是扫描：一个序列的序列，比如第一个子序列三个元素、第二个五个元素。对第一个做 exclusive 求和扫描，得到 0、1、3（1+2）、6（3+3）……再对第二个做，得到 0、4、8、15、22、30（课上举的数）。就是两次扫描，懂扫描就知道分段扫描的正确答案。课件上的分段扫描算法是用 O(n) 并行度算出这两次扫描的方法（n 是所有子序列的总长度），放进课件是觉得大家会觉得很酷。考试要求：给出定义（课件那页的下半部分），让你在更高层的算法设计里使用分段扫描，这是可以考的；不会让你实现数据并行的扫描，就算要实现，也会是有很多引导、真正考点在别处的题。

七、CUDA：线程块调度和 warp

回忆作业 2：有一个任务系统，应用发来命令"把这个任务运行 n 次"；还可以发多条命令，"这是新任务，运行 n 次，但要等之前所有的批量启动都完成"。CUDA 也是批量启动系统，和你的任务 API 很像，只是有两个数：运行 n 个线程块，每个线程块有 T 个线程。线程块和你的任务、ISPC 的任务有对应关系，在任务内部用 T 个线程做并行工作。1D、2D、3D 不重要，就是创建这么多线程块，每个需要这么多资源：多少共享内存、多少线程。

第七讲的例子：每块 128 个线程，需要 520 字节存储。如果 GPU 每个 SM 有 384 个线程的执行上下文，按线程能放几个块？三个。如果每个块需要略多于三分之一的共享内存，按存储能放几个？两个。所以这里一次能放到处理器上的块数受共享内存限制；如果不用共享内存，就能放三个。NVIDIA 的调度器（他们版本的作业 2）拿到"运行 1000 个线程块"，就开始把工作交给各核上的 worker 执行上下文：先把第一个块放到核 0，给它 128 个线程的执行上下文和 520 字节存储；机器还有很多能力，下一个块放到核 1。

好的考题：为什么这个调度器（实现细节）把块 0 放核 0、块 1 放核 1 是合理的？如果块 0 和块 1 都放在核 0 上呢？每块 128 个线程，一个核在这个例子里是 32 宽的能力。同学答：会让那个核内部变得串行。这些线程是交错在同一份处理资源上的，让所有人共享同一份资源，而另一个核闲着。这块芯片同时能放四个线程块，资源用完就放不下了。一个线程块完成时，就像作业里一个任务完成，就能放下一个；所有块需要的资源一样多，填空很方便，否则就有分配问题。

warp 的调度

有同学问单个核上一个时钟能跑几个 warp。Kayvon 先声明：这段在录像，不想因为说错现代 NVIDIA GPU 的事被人扒，但对大多数 NVIDIA GPU，这样想完全没问题：芯片有一组 ALU（他虚构的代理 GPU 有 32 个 ALU），它拿 32 个 CUDA 线程（一个 warp），为这 32 个线程各执行一条指令，在 warp 上推进一步；下一个时钟可能选另一个 warp。一个 warp 的执行就是 32 个 CUDA 线程同时做同一件事。

总是从同一个线程块里取线程组成 warp 吗？NVIDIA 官方对实现什么都不说，所以不能确定地讲；历史上答案是肯定的：同时运行的是线程 ID 0、1、2、3 直到 31。NVIDIA 有完全的灵活性：你写的是线程，如果他们想改 SIMD 宽度、把 ALU 砍一半，你永远不会知道，因为你只创建了 128 个线程，从没想过 warp。编译线程块代码时，它只是普通的顺序标量线程，按你要的数量并发运行。这和机器上 SIMD 指令的实现细节不同：如果明年 Intel 出了 64 宽 SIMD 的处理器，你要回到 ISPC，把 gang 大小改成 64，重新编译，得到一个用 64 宽向量指令的线程。这就是 GPU SIMD 和 CPU SIMD 的区别：CPU SIMD 里，生成机器架构暴露的指令是编译器的责任；GPU 汇编里编译器做得少得多，只生成顺序的东西，然后说"我们同时跑几千个，按块大小（这里是 128）分组"，怎样运行由 NVIDIA 决定。历史上是把块里的线程按连续的 32 个一组切开并行运行；如今他们确实有能力在有发散和 if 语句时重排线程，以发现更好的 SIMD 一致性，能做到什么程度是完全的商业秘密，没有很好的文档。
