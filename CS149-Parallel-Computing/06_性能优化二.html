第六讲：性能优化（二）局部性、通信与争用

共享地址空间的实现很复杂：环形互连、交叉开关、NUMA；消息传递模型，用消息写网格求解器，幽灵行，阻塞收发造成的死锁和修法，异步收发；把并行系统看成扩展的存储层次；算术强度；固有通信与人为通信，一维分块、交错和二维分块的比较；缓存分块和循环融合；争用；性能分析：高水位线、Roofline 模型、性能计数器；问题规模对加速比的影响

主讲：Kayvon Fatahalian
资料来源：课堂录像（Stanford Online，2023 年秋季）、课件；课件最后的问题规模部分是附加材料，课上没讲

一、这一讲讲什么

这是第 6 讲。下周讲 GPU 和 GPU 编程，第 8 讲讲数据并行编程和数据并行思维。之后课程有个转换：前八讲 Kayvon 讲软件性能优化，然后 Kunle 来讲硬件。上一讲是调度：有一批线程或处理器和一堆工作，怎样把工作均匀分给所有 worker，又不在分配上花太多开销。这一讲在负载均衡之外加上另一件事：减少通信和同步开销。内容是：

  • 降低通信代价的技术，包括处理器之间的通信，以及处理器和内存之间的通信；
  • 一般的程序优化建议。

二、共享地址空间的实现并不简单

到目前为止，课程和几乎所有作业都假设所有处理器连接到一个内存系统，它提供单一共享地址空间的抽象：所有线程都能读写这个地址空间里的变量。概念上简单，但这个抽象的实现可能很复杂。

现代计算机上线性内存地址空间的实现：8 个核，每核有 32 KB 的 L1 和 256 KB 的 L2，共享 20 MB 的 L3，后面是 32 GB 的 DRAM。"把地址 X 的值装入寄存器 R0" 这条指令，可能涉及多级数据缓存和 DRAM 访问的一串复杂操作。数据都在 DRAM 里，但各个缓存里存着很多副本。下周末 Kunle 要讲的第一件事就是：这个核拷了一份某地址的数据，那个核也拷了一份同一地址的数据，两个都写了，怎么办？系统里不同的参与者写同一地址，副本的值可能不同，很快就乱成一团。到时会讲现代系统怎样保持一致。

共享地址空间的硬件结构

任何处理器都能直接访问任何内存位置。例子：Intel Core i7（Kaby Lake）四核处理器，同一块芯片上还有集成 GPU，片上网络把各核连起来，再接到同一个内存控制器，互连是一个环。

Intel 的环形互连（从 Sandy Bridge 微架构开始）：

  • 四个环，分别传不同类型的消息：请求、监听（snoop）、确认、数据（32 字节）；
  • 六个互连节点：四个 L3 "切片"（每片 2 MB）、系统代理、图形；
  • 每个 L3 存储体两次接到环形总线上；
  • 3.4 GHz 下从核到 L3 的理论峰值带宽约 435 GB/s（每个核都访问自己本地切片时）。

我们只想着 load X、store X，但处理器发出的 load 实际上是往环上发一个请求，最终路由到内存；如果缓存命中，可能是到环上某处的某一片缓存里取数据。为什么每个节点接到环上两次？有同学说为了降低延迟。对：一方面消息总按顺时针方向发，死锁之类的问题就不大；另一方面有两个接入点，要去左右邻居时能更快到达。这也意味着，L3 命中的代价因地址而异，取决于地址在 L3 的哪一片上。L3 是按地址分片的。

Sun Niagara 2（UltraSPARC T2）：交叉开关互连。Kunle 是这项技术最初设计的重要参与者；Sun 后来被 Oracle 收购。这是最早的主流多线程芯片之一，8 个核，每核很多线程，所有核通过交叉开关（CCX）连到主存。交叉开关就是每个核都直接连到其他所有核，N 个核要约 N² 条连线。芯片图上交叉开关的面积和一个核差不多。在所有处理器之间提供高带宽连接的网络又贵又复杂。

非一致内存访问（NUMA）

例子：现代的多插槽配置。买一块双插槽主板，插两颗四核 CPU，每颗芯片上有连接各核的环，两颗芯片之间通过主板上的走线相连，各自有内存控制器和内存。不管缓存怎样，核 1 访问地址 X 可能比核 8 访问 X 快不少。

  • 系统中不同的处理核访问同一内存位置的延迟可能不同；
  • 从某一位置到不同 CPU 核的带宽也可能不同；
  • 实际上单插槽系统里也能看到 NUMA 行为：不同的缓存切片到各个核的距离不同。

现代大型 GPU 更是如此。离得多近，不只是"在内存里还是在缓存里"这么简单。编程时一般不去想，否则脑子会炸；但真想优化，你会知道数据放在哪里。高手会问"这个地址在这台机器的哪儿？"并根据代价做不同的事。

共享地址空间模型小结

  • 通信抽象：线程读写共享地址空间里的变量；线程操作同步原语（锁、原子操作等）；是单处理器编程的逻辑延伸。但 NUMA 实现要求为了性能优化去考虑局部性。
  • 需要硬件支持才能高效实现：任何处理器能从任何地址 load 和 store；扩展到大量处理器代价可能很高，这也是高核数处理器很贵的原因之一。

三、消息传递

在共享地址空间模型里，线程通过读写共享变量通信。换一个让处理器间通信更显式的抽象，更容易推理通信。写过 Web 上的分布式程序的人都熟悉：互联网上不会说"我要这个内存地址的数据"，而所有计算机共享一个统一的地址空间；分布式系统里靠发消息通信，比如 HTTP GET、POST 和响应。

消息传递模型（抽象）

  • 线程在各自私有的地址空间里运行。线程 1 地址空间里的地址 X 和线程 2 地址空间里的地址 X 不是同一个地址。
  • 线程通过发送和接收消息通信：
    • send：指定接收者、要传输的缓冲区，以及可选的消息标识（"tag"）；
    • receive：指定发送者、存放数据的缓冲区，以及可选的消息标识；
    • 发消息是线程 1 和线程 2 之间交换数据的唯一途径。
send(X, 2, my_msg_id)   // send contents of local variable X as message to thread 2,
                        // tag message with the id "my_msg_id"
recv(Y, 1, my_msg_id)   // receive message with id "my_msg_id" from thread 1,
                        // store contents in local variable Y

常用比喻：如果共享内存是谁都能不打招呼就贴、谁都能看的公告板，消息传递就像寄信：把数据装进信封，写上地址，有人负责送到那里。有同学问这是不是像互联网那样，带源地址和目的地址的数据包在网线上传。是的，任何消息传递系统都有某种寻址机制。不同之处在于规模，互联网、单台计算机里的线程、小集群还是大机架，识别接收者的机制、数据移动的方式（TCP/IP 还是 UDP）都可能不同。概念上的区别是：共享地址空间里大家谈的是同一批地址，都能直接读写；消息传递里各自在自己的地址空间，发消息说"这是一些数据，拷一份放到你的地址空间里"。

消息传递的实现

硬件不需要为所有处理器实现单一共享地址空间，只要提供在节点之间传递消息的机制。可以把普通的商用系统连起来组成大型并行机器，消息传递是集群和超级计算机的编程模型。课件的图是用 InfiniBand 网络连接的工作站集群。

用消息写网格求解器

回忆网格求解器：并行更新所有红格，红格更新完再并行更新所有黑格（遵守对红格的依赖），重复直到收敛。一种可能的消息传递机器：两台计算机组成的集群，每台有处理器、本地缓存和自己的内存（实现自己的地址空间），通过网络相连，以太网、互联网甚至信鸽都行。只有 send 和 receive 两种操作。为什么发消息是交换数据的唯一途径？就像你宿舍的电脑不能对我办公室的电脑发 load/store。

首先要把网格数据划分到各处理器。以前（比如作业 1）只有一个大数组，程序告诉线程 0、1 碰这些地址，线程 2 碰那些地址；现在没有共享地址空间，图上换成四台机器，网格数据分成四份分配，各在一个线程的地址空间里，四个线程各有一个私有数组。线程 3 没办法直接 load 别人那里的值。

要算块边上的元素，需要左右邻居和下方邻居，这些线程 3 都有；但还需要上方那一行，它在一个访问不了的地址空间里。几乎所有消息传递系统的做法是：既然要访问又访问不了，就复制一份放在自己的地址空间里。所以每个节点多分配两行，自己那一块的上面一行和下面一行，请邻居通过消息把这两行的值发过来。这时需要数据复制才能正确执行程序。从远程地址空间复制来的格子叫"幽灵格"（ghost cells，幽灵行、幽灵值），常说幽灵格里的信息由其他线程"拥有"。科学计算里很常见。例子：红格处理完后，线程 1 和线程 3 各给线程 2 发一行数据，线程 2 下一阶段更新黑格需要最新的红格信息。 

// thread 2 logic:
float* local_data = allocate(N+2, rows_per_thread+2);
int tid = get_thread_id();
int bytes = sizeof(float) * (N+2);
// receive ghost row cells (white dots)
recv(&local_data[0], bytes, tid-1);
recv(&local_data[rows_per_thread+1], bytes, tid+1);
// thread 2 now has data necessary to perform
// its future computation

求解器一轮迭代的完整消息传递实现（伪代码出自 Culler、Singh、Gupta）： 

int N;
int tid = get_thread_id();
int rows_per_thread = N / get_num_threads();
float* localA = allocate(rows_per_thread+2, N+2);
// assume localA is initialized with starting values
// assume MSG_ID_ROW, MSG_ID_DONE, MSG_ID_DIFF are constants used as msg ids

void solve() {
    bool done = false;
    while (!done) {
        float my_diff = 0.0f;

        // send and receive ghost rows to "neighbor threads"
        if (tid != 0)
            send(&localA[1,0], sizeof(float)*(N+2), tid-1, MSG_ID_ROW);
        if (tid != get_num_threads()-1)
            send(&localA[rows_per_thread,0], sizeof(float)*(N+2), tid+1, MSG_ID_ROW);
        if (tid != 0)
            recv(&localA[0,0], sizeof(float)*(N+2), tid-1, MSG_ID_ROW);
        if (tid != get_num_threads()-1)
            recv(&localA[rows_per_thread+1,0], sizeof(float)*(N+2), tid+1, MSG_ID_ROW);

        // perform computation (just like in shared address space version of solver)
        for (int i = 1; i < rows_per_thread+1; i++) {
            for (int j = 1; j < N+1; j++) {
                float prev = localA[i,j];
                localA[i,j] = 0.2 * (localA[i-1,j] + localA[i,j] + localA[i+1,j] +
                                     localA[i,j-1] + localA[i,j+1]);
                my_diff += fabs(localA[i,j] - prev);
            }
        }

        // all threads send local my_diff to thread 0;
        // thread 0 computes global diff, evaluates termination
        // predicate and sends result back to all other threads
        if (tid != 0) {
            send(&my_diff, sizeof(float), 0, MSG_ID_DIFF);
            recv(&done, sizeof(bool), 0, MSG_ID_DONE);
        } else {
            float remote_diff;
            for (int i = 1; i < get_num_threads(); i++) {
                recv(&remote_diff, sizeof(float), i, MSG_ID_DIFF);
                my_diff += remote_diff;
            }
            if (my_diff/(N*N) < TOLERANCE)
                done = true;
            for (int i = 1; i < get_num_threads(); i++)
                send(&done, sizeof(bool), i, MSG_ID_DONE);
        }
    }
}

（课件代码里 mydiff/my_diff、MSD_ID_DONE 等拼写不一，循环上界写成了 get_num_threads()-1，会漏掉最后一个线程，这里已改正。）每个线程按 SPMD 方式执行这段代码，各自的工作由线程 ID tid 决定。流程分几个阶段：发送和接收数据；做自己的工作；判断是否结束、要不要再来一轮。

课上的讨论：

  • 调用 receive 的线程要等别的线程 send 了才返回，返回时数据已经在自己的地址空间里。如果没人发，就永远等着。
  • localA 分配了 rows_per_thread + 2 行。send/receive 的数据直接放进本地数组的第一行或最后一行，这样后面遍历时不用区分哪行是幽灵行，代码简单。if 语句是边界情况：第一个线程上面没有邻居，就不用收发。最后一个线程下面没有幽灵行，那块内存分配了但从不写入，只是为了不在分配外面加条件。有同学指出边界线程读到未赋值的那一行，Kayvon 承认没有处理好，"我写得有点马虎，但希望你明白要点"。
  • 怎样判断是否继续？除线程 0 外的每个线程把本地 diff 发给线程 0；线程 0 收齐所有线程的值，算出是否结束，再把布尔值 done 发给其他所有线程。也可以把总和发回去，让各线程自己判断，这只是一种写法。
  • 为什么没有锁？因为没有任何共享的东西，没有需要互斥保护的对象。消息传递代码里永远不会有锁。同步只能通过消息：大家把部分和发给一个线程，它做完计算再把结果发回给所有人。
  • 为什么没有屏障？屏障隐含在这个通信模式里。每个线程有自己的 done 变量，不用担心有人进入下一轮时覆盖了别人刚收到的值。

这个例子的要点：

  • 计算：数组下标相对于本地地址空间。所有线程在自己那块局部数组里遍历同样的下标；共享地址空间版本里要做些数学保证各线程遍历不同的下标。
  • 通信：通过发送和接收消息完成；批量传输，一次发一整行，为了效率一次发很多元素，而不是很多次小的发送。
  • 同步：通过发送和接收消息完成，不用锁和屏障，同步体现在消息的组织方式上。想想怎样用消息实现互斥、屏障、标志位。

同步（阻塞）的 send 和 recv

  • send()：发送者收到确认、确定消息数据已经在接收者的地址空间里，调用才返回。
  • recv()：收到的消息数据已经拷进接收者的地址空间、并且向发送者发回确认后，调用才返回。

过程：发送者调用 SEND(foo)，把发送者地址空间里缓冲区 foo 的数据拷到网络缓冲区，发出消息；接收者调用 RECV(bar)，收到消息，把数据拷进接收者地址空间的缓冲区 bar，发回确认，RECV() 返回；发送者收到确认，SEND() 返回。

有同学问数据始终没到怎么办，比如网络故障。按这个简化定义，接收者永远不返回，发送者收不到确认也永远不返回。在分布式编程环境里故障会发生，要对它健壮。但如果你买了一台 16 核计算机，一个核的消息到不了 L3，那就把机器扔了。片上网络的所有故障重传都在硬件层面处理。或者可以认为这个 API 下面有系统软件负责重试，直到成功。也可以设计能失败、返回错误码的 API，但写这类代码的人不会去检查"内存不工作了"这种错误码。

致命 bug：死锁

前面那段代码如果用同步的 send/recv，有个大问题。为什么？有同学看出来了：所有线程都先阻塞在 send 上。把每个处理器想成教室里的一排人：每个人第一件事是往后面那排发送，发送要等后面的人确认、做了匹配的接收才完成，可后面的人也在往后发送，永远轮不到接收。有人以为第一排不往后发、应该能行，其实第一排会往前发，所以每个人在第一次接收之前都要做一次发送，任何情况下都会死锁。这是一种死锁：你在等别人，而那个人也没法前进。

怎样在只用阻塞收发的前提下修好？按行号奇偶配对：偶数号线程先发后收，奇数号线程先收后发。 

void solve() {
    bool done = false;
    while (!done) {
        float my_diff = 0.0f;
        if (tid % 2 == 0) {
            sendDown(); recvDown();
            sendUp();   recvUp();
        } else {
            recvUp();   sendUp();
            recvDown(); sendDown();
        }
        // ... computation and convergence check as before ...
    }
}

有同学说感觉很糟，一个小错误就能让程序锁死。确实如此。

非阻塞的异步 send/recv

另一个方向是异步通信。上一讲 Cilk 里有异步函数调用，可以和调用者并发执行；消息也可以想成一种异步调用。

  • send()：调用立即返回。提供给 send() 的缓冲区，调用线程不能修改，因为消息处理和线程执行是并发的。调用线程等消息发送时可以做别的工作。
  • recv()：登记"将来要接收"的意图，立即返回。用 checksend()、checkrecv() 确认发送、接收的实际状态。调用线程等消息到达时可以做别的工作。

过程：发送者调用 SEND(foo) 返回句柄 h1，之后消息库在某个时刻把 foo 拷进网络缓冲区并发出；接收者调用 RECV(bar) 返回句柄 h2，消息库收到消息后把数据拷进 bar。发送者调用 CHECKSEND(h1)，如果消息已发出，现在可以安全地修改 foo；接收者调用 CHECKRECV(h2)，如果已收到，现在可以安全地访问 bar。句柄就像快递单号。

在确认之前改 foo，就无法保证消息库已经取走了数据，就像把包裹放在门廊上叫 UPS 来取，UPS 到之前又改了里面的东西，发出去的是改过的；或者把包裹拿走了，UPS 来了发现什么都没有。接收方在确认前读 bar，不知道会读到什么。

课上的问答：

  • 编译器会不会把指令重排到这些调用的另一边？如果你是 send/recv 库的实现者，一定会在里面放内存栅栏之类的东西，防止编译器重排。后面讲同步实现时会谈。
  • 确认怎么工作？那是底层通信传输机制的细节，故意没画在图上。从线程的角度，你发起一次发送，拿到一个单号，以后凭单号查是否完成（或者失败）。网络层怎样实现可靠传输不在本课范围。
  • 连续两次异步 send 同一个变量 foo，会发生什么就很不确定了。即便发的是不同变量，除非库声明了保证（比如设了某个标志就保证顺序），两条消息没有根本理由按同样顺序到达。
  • 怎么等？可以忙等；有的库让你注册回调，像异步 JavaScript 发 AJAX 请求，完成时被调用。
  • 消息 ID：可以指定"接收这个 ID 的消息"，也可以只登记接收，收到后查看 ID，ID 是 43 就做这个，42 就做那个。等任意消息、等某个发送者的消息、等某个 ID 的消息，都是消息传递 API 的参数和细节。
  • 只有一台机器（不是集群）时，有理由用消息传递吗？有。消息传递迫使你考虑所有通信。很多人在多核共享内存系统上也用消息传递的模型写程序，因为锁很难；把东西扔进消息队列让另一边去取，可能更容易推理并发。比如很多多进程系统里，给另一个进程发消息，而不是把地址空间映射到两个进程里。消息传递是高度结构化的通信，要花功夫写对，但写对之后通信很显式，你知道可能在哪里停顿，调试和调优更容易。共享内存不强迫你有任何纪律，第一个程序可能更容易跑起来，比如套一个大的全局锁，但调优时得到的结构和帮助就少了。
  • 消息传递多了一次拷贝，能避免吗？办法很多。现代数据中心里，比如跨很多机器的键值存储，人们很关心降低发消息的延迟和代价。send foo 时可能只把指针交给网卡，网卡自己从内存读数据推到线上，不做多余的拷贝。但即使这样，在数据真正被拷进网络之前，调用线程修改 foo 都可能改变要发的内容，你以为发的是调用时 foo 的内容，实际发的是后来的，这就是 bug。同步时从不用考虑调用者和消息传输之间的并发；异步也许让某些事更容易，也可能更难，因为程序里多了并发，问题可能更多。
  • 消息传递和上一讲的工作队列是什么关系？消息传递只是线程间交换数据的一种方式，另一种是大家读写共享地址空间。在没有共享地址空间的集群上，也可以用消息实现共享工作队列、动态窃取，只是窃取变成给另一台计算机发消息、拿回工作，而不是直接访问它的数据结构。共享地址空间程序里的通信隐含在 load/store 里，那个 load/store 实际上是向内存发请求、拿回数据。讲消息传递，是因为在这种模型里能在程序中直接看到通信在哪。

四、通信的一般观点

说通信，不只是数据中心里机器之间的消息。还有：芯片上核与核之间的通信；核与它的缓存之间的通信；核与内存之间的通信。概念上没有区别，抽象地看，任何东西之间都可以发消息。

把并行系统看成扩展的存储层次

从一个处理器看出去：寄存器、本地 L1、本地 L2、L3、另一个核的 L2、本地内存、远程内存（一次网络跳转）、远程内存（N 次网络跳转）。越往上延迟越低、带宽越高、容量越小；越往下延迟越高、带宽越低、容量越大。在本地内存里满足不了的访问，会和下一层产生通信。所以在所有层次上管理局部性、减少通信量都很重要。

一个例子：CPU 和内存之间的通信

处理器发出 load 指令；查 L1；查 L2；向内存发请求；内存通过内存总线传缓存行；把值传到处理器寄存器。整个过程是访存的总延迟，其中有一段是在内存总线上传缓存行的时间。这下大概能感觉到访存延迟从哪里来：L1 查找、L2 查找，也许操作系统那边还有一次 TLB 未命中，请求要发到内存说"我要这个地址的数据"，然后内存开始送回数据，带宽 B 比特每秒，就以 B 比特每秒送回来。

回忆受带宽限制的执行（第三讲）：处理器每装一个缓存行执行 2 条指令，"数学、数学、读"。只要处理器有能力掩盖延迟（多线程之类），我们不太在乎延迟，最在乎的是蓝条（传输一个缓存行）的长度。内存 100% 的时间都在传数据，没法更快；处理器在等下一条指令的数据时停顿（红色区域）。指令速率由内存提供数据的速率决定。稳态下核的利用不足只取决于指令吞吐和内存吞吐，与访存延迟、未完成的请求数无关。

课件留的好问题，Kayvon 请大家课下能回答：

  • 怎样从图上看出内存总线被完全利用了？
  • 怎样表示更高的访存延迟（访存请求是流水的，总线带宽不变）？答：只要能掩盖，利用率和效率都不变。
  • 内存总线带宽提高，图会怎样变？蓝条变短，红色停顿区变少。
  • 数学指令和 load 指令之比大幅提高，处理器还会停顿吗？为什么？利用率会上升。

算术强度

算术强度 = 计算量（比如指令数）÷ 通信量（比如字节数）

  • 如果分子换成计算的执行时间，这个比值给出代码平均的带宽需求。
  • 1 / 算术强度 = 通信计算比。有人喜欢用通信计算比，Kayvon 觉得算术强度更直观，因为越高越好；"而且听起来更酷"。也有人叫它 operational intensity。
  • 要高效利用现代并行处理器，需要高算术强度（低通信计算比），因为计算能力和可用带宽之比很高（回忆第三讲的逐元素向量乘法）。

如果能掩盖延迟，不管是靠多线程、预取还是别的，游戏最终取决于每读一个单位的数据做多少数学运算。

五、固有通信和人为通信

把通信分成两类有帮助：一类是算法本身决定必须发生的；一类是由机器实际的工作方式产生的。

固有通信

并行算法里必须发生的通信，对算法来说是根本的。开头的消息传递例子里，发送幽灵行就是固有通信：不把这份数据送到这个线程，就得不到正确答案，这个代价总得付。

好的分配决定能减少固有通信（提高算术强度）。N×N 网格，P 个处理器（这一讲里处理器和线程是一回事）：

  • 一维分块：每个处理器计算约 N²/P 个元素，通信约 2N 个元素（块的上下两条边，各宽 N），去掉常数，算术强度正比于 N/P。
  • 一维交错：计算仍是 N²/P，但每算一行，要传两行，算术强度变成 1/2。

假设 N 比 P 大不少，左边每通信 P 个元素做 N 次运算，右边每通信 2 个元素做 1 次运算，右边受带宽限制的可能性大得多。

能比一维分块更好吗？同学说分块，分成方块。这里的算术强度就是区域面积和周长之比，面积周长比最高的形状是正方形（同学问圆形不是更好吗？Kayvon 说你去试，圆里面那些区域怎么办，可能要浪费太多计算去搞清楚在做什么，未必更快）。

  • 二维分块：为了让图更直观用 9 个处理器。每个处理器计算 N²/P；一行有 √P 个处理器，每条边长 N/√P，通信约 4N/√P，算术强度正比于 N/√P。

渐近意义上比一维分块的通信扩展性好，通信代价随 P 亚线性增长，这个分配抓住了算法的二维局部性。在核数多的机器上这很重要：16 核机器上 √P 和 P 差 4 倍，用这个方案，带宽少 4 倍也能维持峰值利用率。

人为通信

  • 固有通信：给定分配方案，为了执行算法，处理器之间根本上必须移动的信息（假设缓存容量无限、传输粒度最小等）。
  • 人为通信（artifactual communication）：其余所有通信，来自系统实现的实际细节。

例子：

  • 系统有最小的数据传输粒度，要传的数据比应用需要的多：程序装一个 4 字节 float，但整个 64 字节缓存行都要从内存传过来，多了 16 倍。我们从不在计算机里移动单个数据，总是移动一个缓存行；网络里最小包可能是 1 KB，或者要在 16 的边界上传输。
  • 系统的工作方式可能导致不必要的通信：程序存 16 个连续的 4 字节 float，结果整个 64 字节缓存行先从内存读进来，被完全覆盖，再存回内存。2 倍开销，因为整行都被覆盖了，那次读没有必要。
  • 有限的复制容量：缓存太小，两次访问之间留不住数据，同一份数据多次传给处理器（容量未命中）。

缓存行为产生的人为通信

这里的通信在内存和处理器之间。这就是这门课讲缓存的原因。网格求解器按行主序遍历，假设网格按行主序存放，缓存行是 4 个格子，缓存容量 24 个格子（6 行）。

  • 更新一个红点要读上下左右四个邻居，会装入几个缓存行（图上蓝色）。
  • 水平右移一格，没有未命中，全是命中。一直往右走到行尾，缓存里是最近这几行。
  • 回到下一行开头处理红点时：不久之前缓存里有需要的大部分数据（只差红点下面那一行），可现在 (0,1)、(1,1)、(2,1)、(0,2)、(2,2) 这些之前访问过的元素都已不在缓存里，又全部未命中。
  • 结果，这个程序每输出 4 个元素要装 3 个缓存行。

理论上这些数据已经装过了，有个神奇缓存就不用再传给处理器；但看实际程序，每次碰数据都未命中。注意这里没有并行，假设全在一个线程里，是一个 worker 内部、处理器和自己的内存之间的通信。

六、减少通信的技术

改变遍历顺序提高时间局部性："分块"

怎样改程序提高算术强度？有同学说走到行尾后下移一行再从右往左，蛇形走。目标是：回到左边时要足够快，数据还没被挤出缓存。改变遍历数组的顺序，算出的答案一样，只是顺序不同；这与并行无关，只关乎通信。"分块"的迭代顺序：在一个窄块里一行行地处理，回来时已经访问过的数据还在缓存里，只需装下面的一行。课件的图显示做完第一块第一行后缓存的状态：现在每输出 6 个元素装 2 个缓存行，原来是 4 个元素 3 行，算术强度提高了不少。

这叫缓存分块（cache blocking），Kayvon 说这大概是任何涉及张量和矩阵的代码里最重要的技术。现代矩阵乘法、现代张量运算之所以快，就因为选了很好的数据遍历顺序。

有同学问反向遍历行（走到底再走回来）行不行：在这张小图上看起来不错，两端有复用；但 N 很宽，比如 1000，中间又回到原来的失败模式。缓存只有 16 KB 或 32 KB 左右，2K×2K 的矩阵就能撑爆 L3。能不能用工具搞清楚？性能剖析工具能告诉你算术强度是多少、是否受带宽限制，但不会告诉你怎么修。

循环融合提高时间局部性

void add(int n, float* A, float* B, float* C) {
    for (int i = 0; i < n; i++)
        C[i] = A[i] + B[i];
}

void mul(int n, float* A, float* B, float* C) {
    for (int i = 0; i < n; i++)
        C[i] = A[i] * B[i];
}

float *A, *B, *C, *D, *E, *tmp1, *tmp2;
// assume arrays are allocated here

// compute E = D + ((A + B) * C)
add(n, A, B, tmp1);
mul(n, tmp1, C, tmp2);
add(n, tmp2, D, E);

这很像 NumPy 里的代码：有一组对数组做乘法、加法的库函数（很像作业 1 的 saxpy），用它们组合出更复杂的表达式。每个库函数每次数学运算要两次 load 一次 store，算术强度 1/3；由它们组合起来的程序，整体算术强度也是 1/3。写起来很方便，但状态很糟。 

void fused(int n, float* A, float* B, float* C, float* D, float* E) {
    for (int i = 0; i < n; i++)
        E[i] = D[i] + (A[i] + B[i]) * C[i];
}

// compute E = D + (A + B) * C
fused(n, A, B, C, D, E);

为什么下面的好得多？同学说遍历 4 个数组而不是 6 个。读 A、B、C、D 的值，中间结果都放在寄存器或缓存里，全部算完再把结果写出去。每 3 次数学运算 4 次 load 1 次 store，算术强度从 1/3 提高到 3/5。已知它受带宽限制，加速比就是算术强度提高的倍数。上面的代码更模块化，下面的性能好得多。很多深度学习编译器开始替你做这种优化：你想用加法、乘法这些向量张量操作写代码，但绝不想它在底层真的那样跑。TensorFlow、PyTorch 的 JIT 做的就是：拿到看起来是向量运算的张量程序，用融合后的方式执行。

通过共享数据提高算术强度

  • 利用共享：把操作相同数据的任务放在一起。在同一时刻、同一处理器上调度处理同一数据结构的线程，减少固有通信。（课上没展开。）

七、争用

Kayvon 说这部分和这一讲的主线不完全一致，只给两分钟，其余请课下读。他想强调的是：归根结底一切都是"通信的字节数与工作量之比"；这部分只是指出，通信或工作什么时候发生也很重要。

例子：下午 3:00 到 3:20 的办公时间，不预约。要做的操作：Kayvon 教授回答一个学生的问题；执行资源：Kayvon 教授。步骤：学生从 Bytes Cafe 走到办公室（5 分钟）；必要时排队；问题得到有见地的回答（5 分钟）。

  • 第一个学生到了立刻开始，5 分钟走路加 5 分钟答疑，学生花了 10 分钟。
  • 五个学生差不多同时出发，后到的要排在别人后面等，最后一个学生花了 23 分钟。
  • 问题：对共享资源的争用让整体操作时间变长（学生的代价可能更高）。
  • 如果两个学生分别预约 3 点和 4 点半，每人都只花 10 分钟。这就是 Kayvon 喜欢预约制办公时间的原因，对学生更高效。

这和前面讲的带宽不是一回事：每个请求的工作量和路上时间都一样，只是有人排在队尾。

  • 一个资源能以给定的吞吐量（单位时间的事务数）执行操作：内存、通信链路、服务器、办公时间的助教等。
  • 在很短的时间窗口内对一个资源发出很多请求，就发生争用（这个资源是"热点"）。
  • 例子：更新共享变量。扁平的通信：可能有高争用（没有争用时延迟低）。树形的通信：减少争用（但没有争用时延迟更高）。
  • 例子：分布式工作队列减少争用（访问单一共享工作队列时有争用）。worker 线程从自己的队列取、往自己的队列推，所有处理器都有工作时没有争用；本地队列空了，从随机的工作队列窃取，这时同步没关系，因为线程本来也会闲着。

上一讲为避免争用常常复制东西，比如共享的 myDiff、共享的队列。访存通信里争的是内存：所有处理器同时向内存要数据，前面那些漂亮的流水线图在实际中可能就不成立了。很多系统里争用不多，我们按平均来想，比如每次操作读多少字节；但如果这些读恰好同时发生，内存看起来会比实际慢很多。所以有时随机化反而好，比如大家在随机的时间出门上高速，公路更可能达到峰值带宽。

小结：降低通信代价

  • 减少发送方/接收方的通信开销：发更少的消息、让消息更大（分摊开销）；把很多小消息合并成大消息。
  • 降低通信延迟：应用开发者重组代码以利用局部性；硬件实现者改进通信架构。
  • 减少争用：复制被争用的资源（本地副本、细粒度锁）；错开对争用资源的访问。
  • 增加通信和计算的重叠：应用开发者用异步通信（比如异步消息）；硬件实现者用流水线、多线程、预取、乱序执行。这要求应用有额外的并发（并发度多于执行单元数）。

Kayvon 的总结：讲了把工作重新分配给 worker 以减少固有通信；改变单个 worker 做事的顺序以减少人为通信，尤其是缓存局部性。

八、理解并行软件性能的技巧

记住：永远、永远、永远先试最简单的并行方案，然后测量性能，看自己处在什么位置。有时最笨的、不做任何优化的静态方案比复杂方案还快。行得通就继续，去做别的课。

一种有用的性能分析策略：

  • 判断性能是受计算、内存带宽（或访存延迟）还是同步的限制？
  • 设法确立"高水位线"：实践中最好能做到多少？你的实现离最好情况有多近？

作业 1 里大家做了很多测量，看负载是否均衡，不均衡就再努力一点。那怎么测是不是受带宽限制？可以用 VTune 之类的性能剖析工具，它可能直接告诉你。也可以这样想：如果我知道程序每秒执行多少指令、多少 MFLOPS，又知道这台计算机的峰值 MFLOPS，就能算出自己拿到了峰值的多少，判断要不要继续努力。

Roofline 模型

图出自 Williams 等人 2009 年的论文。X 轴是算术强度（单位是每字节的浮点运算数，flops/byte），X 轴上不同的点对应不同算术强度的程序，越往右每从内存读一个字节做的运算越多。Y 轴是给定算术强度的程序能达到的最大指令吞吐量（GFLOPS）。图形像屋顶，所以叫 roofline。

  • 水平区域：受计算限制的执行。看蓝线，算术强度 1 以上的所有程序在这台计算机上性能都一样。程序访存越来越少，性能却不变，因为每读一个字节做的运算太多，性能受限于算术单元的产出能力，一直顶在那里。比如 1 GHz、16 核，程序受计算限制，做得好就是 16 GFLOPS，这已是最好。
  • 斜线区域：受内存带宽限制的执行。过了那个拐点，数据送不过来，没法执行这些运算；算术强度降低一半，每次运算要的字节翻倍，受带宽限制时运行时间翻倍，性能减半。对数坐标下这段斜线的位置由带宽决定。
  • 如果你看代码的主循环知道自己的算术强度，比如 4，实测性能却在曲线下方很远：这时不应受内存限制，而离峰值又差一截，说明有别的问题，也许负载不均，也许有争用。这张图告诉你自己处在什么位置。
  • 绿线是另一个处理器（x2、x4 是营销名称），总计算能力是蓝线的 4 倍，峰值性能约高 4 倍；内存系统相同，所以需要约 4 倍的算术强度才能保持受计算限制。买一台塞满并行能力的计算机，只有应用里有足够的数学去用它，才能跑到峰值。

让程序在图上往右走的办法就是课上讲的那些：融合循环、分块、重排以减少通信。几乎所有工作都是在把程序往右推，让性能沿曲线往上爬，直到碰到平顶。

有同学问有没有想往左走的时候。看墙钟时间：工作量乘以速率。如果改算法让你往左移、但仍在屋顶线上，而且工作量减少了，那就很好，同样的峰值吞吐、更少的工作。如果改进让工作少了 10 倍、仍然高吞吐，那很好；但如果工作少了 2 倍，算术强度却降到让效率也减半的位置，可能就白忙了。这张图讲的是效率和吞吐量。

Roofline 的优化区域：在基准测试里使用不同层次的优化（比如用和不用 SIMD 指令时的最佳性能），画出不同高度的"屋顶"。

确立高水位线

  • 加"数学"（非访存指令）：执行时间是否随运算数线性增加？如果是，说明代码受指令速率限制。
  • 把所有数组访问改成 A[0]：代码快了多少？这给出改善数据访问局部性的收益上限。
  • 去掉所有原子操作或锁：代码快了多少（前提是工作量大致不变）？这给出减少同步开销的收益上限。
  • 去掉几乎所有数学，但装入同样的数据：执行时间减少多少？如果减少不多，可以怀疑是内存瓶颈。

计算、访存和同步几乎从不完美重叠，所以总体性能很少完全由计算、带宽或同步之一决定。尽管如此，性能对上述程序改动的敏感程度，能很好地指示主要代价在哪里。

九、附加材料：问题规模

理解问题规模的影响，对评估程序性能很有帮助。（课件附加页，课上未讲。）

你被某芯片公司录用，第一天老板说："所有高级架构师都决定休假一年，你来领导下一代并行处理器的设计。"你会问什么？老板挑出公司最看重的应用："我要你在这个应用上展示好的性能。"怎样算好的设计？

  • 绝对性能？通常用墙钟时间衡量，或者每秒操作数。
  • 加速比，即并行带来的性能提升？顺序程序的执行时间 ÷ P 个处理器上的执行时间；或者 P 个处理器的每秒操作数 ÷ 顺序程序的每秒操作数。
  • 效率？单位资源的性能，比如每单位芯片面积、每美元、每瓦的每秒操作数。

测量扩展性

网格求解器为了并行改了算法，新算法可能收敛更慢，需要更多迭代。加速比该和并行版程序在一个处理器上的性能比，还是和最好的顺序程序比？常见陷阱：拿并行程序的加速比和并行算法在一个核上的运行比较，这样更容易让自己显得好看。

课件引用 Culler、Singh、Gupta 的数据：258×258 网格的求解器在 32 处理器 SGI Origin 2000 上的加速比曲线。回忆二维分块：小 N（或大 P）会让算术强度很低。

  • 固定问题规模的陷阱一：258×258 网格在 32 个处理器上，每个处理器约 310 个格子；1K×1K 在 32 个处理器上约 32K 个。小网格从某个处理器数开始毫无收益（还略有变慢），问题规模对这台机器太小了，通信计算比太大。而且小问题的扩展性也许本来就不重要，单核上可能已经够快。
  • 陷阱二：超线性加速！处理器足够多时，分给每个处理器的那块网格开始能放进缓存（关键工作集放进了每个处理器的缓存）。另一个例子：问题对单台机器太大，工作集放不进内存，导致频繁换页到磁盘，这会让更大、内存更多的并行机器上的加速比看起来惊人。

理解扩展

  • 要解决的问题规模和并行计算机的规模之间可能有复杂的相互作用：会影响负载均衡、开销、算术强度、数据访问的局部性；效果可能很显著，并且依赖应用。
  • 用固定问题规模评估机器可能有问题。
    • 问题太小：并行开销盖过并行收益（甚至变慢）；问题规模可能适合小机器，不适合大机器（不反映大机器的实际用法）。
    • 问题太大（为大机器选的规模）：关键工作集可能放不进小机器（频繁换页到磁盘、关键工作集超过缓存容量，或者根本跑不了）；工作集放得进大机器却放不进小机器时，可能出现超线性加速。
  • 随着机器规模增长扩大问题规模可能是可取的：买更大的机器是为了算更多，而不只是把同样的问题算得更快。

建议汇总

  • 测量，测量，再测量……
  • 为程序确立高水位线：你受计算、同步还是带宽限制？
  • 注意扩展性问题：问题和机器匹配吗？
