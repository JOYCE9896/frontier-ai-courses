第五讲：性能优化（一）工作分配与调度

先做最简单的方案再测量；负载均衡；静态分配、半静态分配、动态分配；共享工作队列、任务粒度、先调度长任务、分布式队列和工作窃取、带依赖的任务；fork-join 并行和 Cilk Plus：cilk_spawn / cilk_sync 的语义，线程池实现，先跑子任务还是先跑后续部分，双端队列、从顶部窃取、随机选受害者，sync 的实现和贪心 join

主讲：Kayvon Fatahalian
资料来源：课堂录像（Stanford Online，2023 年秋季）、课件（副标题是 "how to be l33t"）

一、补上一讲的题：一个屏障

上一讲最后问为什么求解器要三个屏障、能不能只用一个。总要等来等去，是因为有一个变量大家反复检查：diff，它保存每轮迭代的变化量，而同一个变量在每轮都被重复使用。所以所有线程都要离开第 i 轮，才能有人在第 i+1 轮用 diff 做任何事。这是程序里人为制造出来的依赖：一个变量被拿来做了好几件事。

解法：把 diff 变成数组。概念上可以开"迭代次数"那么大，但其实三份就够了：上一轮、这一轮、下一轮。所有线程在任意时刻只可能处在这三轮之一，要么在收尾上一轮，要么在做这一轮，要么在往下一轮走。这和用本地 myDiff 累加部分和是同一个技巧：大家在一个变量上同步，就让每人写不同的副本，最后再汇合。

这一周的安排：今天讲分配，即哪个 worker 做哪份工作，以及调度，基本不考虑内存，只考虑让一群 worker 同步、负载均衡；周四讲怎样调度才能减少通信开销、减少因内存产生的停顿。

二、高性能编程的总体目标

优化并行程序的性能，是一个反复改进分解、分配、编排选择的迭代过程。几个主要目标彼此冲突：

  • 把工作负载均衡地分到可用的执行资源上；
  • 减少通信（避免停顿）；
  • 减少为了增加并行、管理分配、减少通信等而做的额外工作（开销）。

提示 1：永远先实现最简单的方案，然后测量性能，再决定是否需要做得更好。Kayvon 说这一点怎么强调都不为过，作业 3 尤其如此。每年约 10% 的学生读完讲义和课件，在白板上设计出一套相当复杂的方案，花好几天；离截止只剩三四天才开始写代码，以为一跑通就万事大吉，结果复杂方案常常比简单方案还慢。正确做法：最简单的方式让程序跑通，最简单的方式并行化，然后像作业 1 要求的那样加计时器，看哪个线程干活最多，只有性能不好时才做更复杂的事。用测量数据决定下一步。

三、负载均衡

理想情况：程序执行期间所有处理器一直在计算，同时开始、同时完成自己那份。少量的负载不均就能严重限制最大加速比。课件的例子：4 个处理器，P4 的工作是别人的两倍，P4 用两倍时间完成，于是并行程序运行时间的 50% 是串行的。（这段串行部分里做的工作约占整个程序工作的 1/5，所以 Amdahl 定律里 S = 0.2。）大段时间里只有一个 worker 在干活，等于以串行程序的方式在跑。

静态分配

工作到线程的分配不依赖程序运行时的动态行为。注意"静态"不一定是编译时确定：只要分配在工作量和 worker 数量已知时就确定下来，就叫静态，它可以依赖运行时参数，比如输入数据大小、线程数等。所以不要以为静态分配就是写程序时就知道的。

回忆作业 1 程序 1（Mandelbrot 分形）：给每个线程分相等数量的格子（像素），同学们尝试了不同的静态分配。最初的做法是每个线程分一块连续的行。这里每个像素的工作量怎么看？图里像素的亮度大致就是计算它的代价，暗的区域工作少，亮的区域工作多，所以连续分块造成了严重的负载不均。有人改成按行交错分配，为什么效果不错？每行工作量当然不同，但相邻的行工作量差不多（图像有连续性），每一小片局部区域被拆成几行分给不同线程，平均下来每个线程的工作量就差不多。换一种工作负载，这种策略可能很糟：比如上方全白、往下渐渐变暗，上半部分是个三角形，线程 1 总比线程 2 多一点，线程 2 又比线程 3 多一点。

静态分配的好处：简单，执行分配的运行时开销几乎为零（这个例子里只是一点下标计算）。更重要的是，告诉 P1 负责第一个四分之一、P2 负责第二个之后，线程之间不用同步，也没有通信，每个线程不需知道别人在做什么就能算出自己该做什么，通信降到最少。

什么时候适用静态分配？

  • 工作的代价（执行时间）和工作量可预测，程序员能提前想好一个好的分配。最简单的情况：事先知道所有工作代价相同。12 个任务、代价相同、4 个处理器，每个处理器静态分 3 个。
  • 工作可预测但代价不同：代价不等但已知。
  • 执行时间的统计特性可预测，比如平均代价相同。不知道任何一份工作的确切代价，但有方差也没关系：给每个 worker 分足够多的工作，把深蓝色条叠起来，每个线程的总量差不多。分形就是这样的例子。

半静态分配

工作的代价在短期内可预测，思路是最近的过去能很好地预测不久的将来。应用定期剖析自己的执行情况，重新调整分配；两次调整之间，分配是"静态"的。

  • 自适应网格：图里白色是机翼剖面，从机翼边缘看向机身，网格把机翼周围的流场离散化。压强大的区域分辨率极高。颜色表示网格的哪些单元由哪个线程处理，各线程占据的空间大小相差很大，但数一数单元数大概差不多。网格随物体移动或流动变化而改变，但变化很慢。比如模拟起飞降落时，可以先静态分配，跑一两分钟，压强变了、单元数变了，再重新分一次。
  • 粒子模拟：粒子在模拟过程中移动，把粒子重新分给 worker；运动慢的话，不需要经常重新分配。
  • Kayvon 补充：长时间运行的机器学习计算也类似，训练一段时间，找出负载不均，调整，再跑一小时，如此反复。

动态分配

程序在运行时动态决定分配，以保证负载分布良好。适用于任务的执行时间或任务总数未知、不可预测的情况。例子：判断数组里每个数是不是素数，这很难预测代价。 

// Sequential program (independent loop iterations)
int N = 1024;
int* x = new int[N];
bool* prime = new bool[N];
// assume elements of x initialized here
for (int i = 0; i < N; i++)
{
    // unknown execution time
    is_prime[i] = test_primality(x[i]);
}
// Parallel program (SPMD execution by multiple threads)
int N = 1024;
// assume allocations are only executed by 1 thread
int* x = new int[N];
bool* is_prime = new bool[N];
// assume elements of x are initialized here
LOCK counter_lock;
int counter = 0;  // shared variable

while (1) {
    int i;
    lock(counter_lock);
    i = counter++;        // could also be: atomic_incr(counter);
    unlock(counter_lock);
    if (i >= N)
        break;
    is_prime[i] = test_primality(x[i]);
}

所有线程都运行这段代码。检查一下：所有 N 个元素都会被处理吗？会。两个线程会做同一份工作吗？不会，锁保证我递增计数器时没人在读它，我拿到当前的号，就像熟食店柜台的排号票，后来的人拿到更大的号，每人的号都不同，所以所有工作都会做完。会终止吗？会，拿不到号的线程就退出，所有线程退出后结束。

用高层的话说这是什么分配策略？整份工作是判断所有这些数的素性，一份工作是判断一个数。程序用数组下标划分工作，大家不断去拿下一个还没人做的下标，直到全部做完。虽然看不到队列数据结构，实际上相当于把所有要做的事扔进一个大队列，队列用一个数组加一个计数器实现，"弹出下一个"只要一次原子递增。概念上这就是一个共享工作队列：worker 线程从共享工作队列取数据，产生新工作时也推回队列（暂时假设每份工作相互独立）。典型的动态分配就是：把能并行做的工作都暴露出来，由底层系统根据谁空闲来动态地把工作分给 worker。

作业 1 程序 3：为什么把问题拆成很多个 ISPC 任务能提升性能？很多人问"机器有 8 个线程，不就该创建 8 个任务吗？"假设 4 个核，切成 4 个任务，不就回到了刚才那种连续分块吗？很不均衡。切成很多小块扔进工作队列，各块代价不同，但只要块够多、每块相对短，所有线程不断拿下一块，直到全部做完，就会得到好的均衡。代价是什么？程序 1 不用做的事：同步。问题在于好的负载均衡带来的收益，能否盖过同步的开销。这个例子里确实盖过了。

四、什么算一份工作？

上面的程序里，调度（分配）的单位是一个数：细粒度划分，1 个"任务" = 1 个元素。可能有很好的负载均衡（很多小任务），但同步代价可能很高（在临界区串行化）。时间线上，蓝条是做任务的时间，白条是拿锁、递增计数器、放锁的时间。临界区里的时间是串行程序没有的开销，而且是串行执行的（回忆 Amdahl 定律）。

那么这是个问题吗？Kayvon 带大家走了一遍排查过程：

  1. 先给整个程序加计时器，比如总共 5.9 秒。
  2. 再把计时器放在 test_primality 周围，把所有调用的时间加起来。总时间减去有用工作时间就是开销。也可以反过来计时锁。
  3. 也可以先实现静态版本作对比，比如 8 秒，那 5.9 秒已经更好了。问题是还能不能比 5.9 秒更好。
  4. 如果所有 test_primality 调用总共 5.75 秒：做不了更好了，最多省 0.1 秒左右。高频交易员也许要赢这场比赛，做作业的话就去上下一门课吧。
  5. 如果只有 2.5 秒：一半以上的时间花在别处，这个程序这么简单，肯定是在锁上。

超过 50% 的时间耗在锁上怎么办？一个可行的方向是退回静态分配，去掉动态机制。但还有更简单、不用全部重写的办法。当初把工作切成最小的块，是为了块越多越容易找到人人工作量差不多的划分。8 个线程把工作分成 8 块再动态调度，没什么用。但块越小，开销可能越大。如果 N 是一百万、只有 8 个线程，块的大小翻倍仍有足够的工作。怎样一次从队列拿两份？计数器一次加 2，白色的区段就减半。 

const int N = 1024;
const int GRANULARITY = 10;
// assume allocations are only executed by 1 thread
float* x = new float[N];
bool* prime = new bool[N];
// assume elements of x are initialized here
LOCK counter_lock;
int counter = 0;

while (1) {
    int i;
    lock(counter_lock);
    i = counter;
    counter += GRANULARITY;
    unlock(counter_lock);
    if (i >= N)
        break;
    int end = min(i + GRANULARITY, N);
    for (int j = i; j < end; j++)
        is_prime[j] = test_primality(x[j]);  // slide writes [i] here; [j] is intended
}

粗粒度划分：1 个"任务" = 10 个元素，进入临界区的次数少了 10 倍，同步代价降低。Kayvon 把它参数化成 GRANULARITY，"因为我是个好的软件工程师，截止前可以调这个参数拿最好的性能"。在很多现代系统上这一小次递增并不贵，稍微把粒度调大一点，大概就能把很多动态情况下的开销冲掉。

选择任务大小

  • 任务数远多于处理器数是有好处的（很多小任务让动态分配能做好负载均衡），这要求小粒度。（这里"任务"泛指一份工作，不特指 ISPC 任务。）
  • 但任务越少越好，以减少管理分配的开销，这要求大粒度。
  • 理想粒度取决于很多因素。这门课反复出现的主题：必须了解你的工作负载和你的机器。

有人在作业 1 里试过每行一个任务、创建一千个任务吗？到某个点加速曲线可能开始下降；如果一个像素一个任务，几乎肯定会下降。

更聪明的任务调度

16 个任务，故意让最后一个比其他的长得多。用共享工作队列动态调度，系统按从左到右的顺序把任务分给 worker 会怎样？即使是动态分配，运气不好，队列末尾恰好是最长的那个，最后分出去的是运行最长的工作，结尾仍拖出一条长尾，负载不均。

  • 一种办法：把工作分成更多更小的任务。希望"长杆"相对总执行时间变短；可能增加同步开销；也可能做不到，长任务也许本质上就是串行的。
  • 另一种办法：更聪明的调度，先调度长任务，减少计算末尾的"零头"。执行长任务的线程总共做的任务少，但工作量和其他线程差不多。例子里 P4 一开始就拿到大任务，只做了两个任务，大家几乎同时完成。这需要对工作负载有一定了解（代价有一定可预测性）。你对任务了解越多，调度就能做得越好。

分布式队列减少同步开销

共享工作队列例子里共享的是什么？锁和计数器。在有 128 个线程的大机器上，尤其工作很小时，对这个计数器的争用可能不小。和把一个 diff 变量复制成本地 myDiff 一样，可以给每个线程复制一个工作队列，避免所有 worker 在一个队列上同步：

  • worker 线程从自己的工作队列取数据；
  • 新产生的工作推到自己的队列；
  • 本地队列空了，就从另一个工作队列窃取工作。

一般每个 worker 线程一个队列。作业里不要求做这个，只是让大家了解。

队列里的工作不必相互独立

目前为止扔进队列的工作都是独立的，按任何顺序处理都行。很多系统里常见的是：很多工作可以并行，但彼此之间有依赖。 

foo_handle = enqueue_task(foo);              // enqueue task foo (independent of all prior tasks)
bar_handle = enqueue_task(bar, foo_handle);  // enqueue task bar, cannot run until foo is complete

这样就建出一张依赖图，限制什么时候能运行什么。任务管理系统的调度器管理任务间的依赖：一个任务的所有依赖都满足之前，不能分给 worker 线程；worker 可以向任务系统提交新任务（可选地带显式依赖）。作业 2 的最后一部分就是这个：给你一批带依赖的任务，实现一个能运行它们并遵守所有依赖的工作队列。有点棘手：一个任务完成，可能意味着一大批之前已经提交、但还不能开始的任务现在可以跑了。很多系统里都有这个调度问题。

小结

  • 挑战：实现好的负载均衡。希望所有处理器一直在工作，否则资源闲置；但又希望实现均衡的代价低：减少计算开销（调度和分配逻辑），减少同步代价。
  • 静态分配和动态分配不是二选一，是一个连续的选择谱系。尽可能利用对工作负载的预先了解，减少负载不均和任务管理、同步的代价。极限情况下系统什么都知道，就用完全静态的分配。

五、常见的并行编程模式

目前课上几乎所有程序的并行都来自对一个集合里不同的数据做差不多的事，比如 Mandelbrot 算每个像素的颜色，作业 1 里其他例子算每个数的正弦。

数据并行：对很多数据元素执行同样的操作序列。 

// openMP parallel for
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    B[i] = foo(A[i]);
}

// ISPC foreach
foreach (i = 0 ... N) {
    B[i] = foo(A[i]);
}

// ISPC bulk task launch
launch[numTasks] myFooTask(A, B);

// using higher-order function 'map'
map(foo, A, B);

// bulk CUDA thread launch (GPU programming, in a future lecture)
foo<<<numBlocks, threadsPerBlock>>>(A, B);

OpenMP 是一个小小的 C 扩展：在 for 循环前加 pragma，告诉编译器"这是普通 C 循环，但我保证迭代相互独立"，底层就启动真正的线程并行执行迭代。在 C 里获得并行最简单的办法就是用 OpenMP。map 是后面会讲的函数式抽象，更像 PyTorch 的思路；CUDA 也一样，"把函数 foo 在这些数组上运行这么多次"。

用线程显式管理并行：每个执行单元（或者每份期望的并发）创建一个线程。这时想的是"这是我的线程，它们该做什么"，而不是"对这些数据可以独立做这件事"。 

float* A;
float* B;
// initialize arrays A and B here

void myFunction(float* A, float* B) { ... }

std::thread thread[NUM_HW_EXEC_CONTEXTS];
for (int i = 0; i < NUM_HW_EXEC_CONTEXTS; i++) {
    thread[i] = std::thread(myFunction, A, B);
}
for (int i = 0; i < NUM_HW_EXEC_CONTEXTS; i++) {
    thread[i].join();
}

六、分治算法与 fork-join

还有一类算法（CS161 里学过）用分治的方式思考，典型例子是快速排序：选一个元素作为划分键（它的选法影响渐近复杂度，这里随便选一个或者就选第一个），把小于它的移到数组一边，大于它的移到另一边，然后对两边递归。 

// sort elements from 'begin' up to (but not including) 'end'
void quick_sort(int* begin, int* end) {
    if (begin >= end - 1)
        return;
    else {
        // choose partition key and partition elements
        // by key, return position of key as `middle`
        int* middle = partition(begin, end);
        quick_sort(begin, middle);
        quick_sort(middle + 1, end);  // slide writes `last` here
    }
}

第一步永远是找潜在的并行。把 partition 当作串行的黑盒，并行在哪里？两次递归调用：左边和右边可以并行排序。数据并行的思路是"一千万个元素都能并行"，这里是"从功能上看有两件事能并行"。只靠这一次不够填满大机器，但每次调用又产生两次调用，如此下去形成一棵潜在并行的树，递归到某一层就有很多并行的事可做。这是一个逐步揭示并行的递归算法，和"这里有一百万件事"的数据并行不同。

Cilk Plus

fork-join 模式是表达分治算法固有的独立工作的自然方式。这一讲的代码用 Cilk Plus：一个 C++ 语言扩展，最初由 MIT 开发，现在是开放标准（GCC、Intel ICC 都支持），myth 机器上也能写。原则上只对 C 加了两样东西：

  • cilk_spawn foo(args);：调用 foo，但和普通函数调用不同，调用者可以和 foo 的执行异步地继续执行。这是 "fork"，创建新的逻辑控制线程。
  • cilk_sync;：当前函数 spawn 出去的所有调用都完成后才返回（和 spawn 出去的调用"同步"）。这是 "join"。可以把它看作针对所有 spawn 出去的函数的屏障。
  • 每个包含 cilk_spawn 的函数结尾都有一个隐含的 cilk_sync。也就是说，一个 Cilk 函数返回时，和它相关的所有工作都已完成。

Kayvon 强调：先把编程模型的语义在脑子里弄清楚，独立于它可能怎样实现。普通 C 的函数调用：控制转移到被调用函数（线程执行函数的指令），函数返回时控制回到调用者（线程继续执行调用者的指令）。图示是 my_func 的 part A，然后 foo，然后 bar，然后 part B，一条直线下来。

cilk_spawn 看起来很像 fork 一个线程，cilk_sync 很像 join。但创建线程和 spawn 工作不同：spawn 是说"有一份工作要做，就是在这些参数上执行 foo，将来什么时候做都行"；创建线程是说"这是一个控制线程，它现在就在运行，需要执行上下文，处理器在跑它"。 

// foo() and bar() may run in parallel
cilk_spawn foo();
bar();
cilk_sync;

// foo() and bar() may run in parallel
cilk_spawn foo();
cilk_spawn bar();
cilk_sync;

// foo, bar, fizz, buzz, may run in parallel
cilk_spawn foo();
cilk_spawn bar();
cilk_spawn fizz();
buzz();
cilk_sync;
  • 第一个：foo 被 spawn 到一边，bar 由调用者作为普通 C 函数执行（所以图上是竖直往下），sync 表示调用者要等 foo 完成才继续。
  • 第二个：和第一个的独立工作量相同，但运行时开销可能更高（两次 spawn 而不是一次）。最初的逻辑线程什么都不做，只是等 foo 和 bar 完成。
  • 第三个：buzz 是普通的 C 函数调用，在主线程上执行，然后 sync 保证所有异步的东西做完。

有同学问参数会不会被拷贝：暂时就当完全共享的地址空间。还有人问第三个例子里能不能按 fizz、bar、foo 的顺序执行：可以。foo、bar、fizz 都和主线程异步，彼此之间也没有任何依赖，可以按任何顺序调度。不要把它想成命令缓冲区，往里推命令。唯一的保证是 sync 返回时它们都已完成。区别在于 foo、bar 可以是递归函数，自己再发起并行工作。

抽象和实现

cilk_spawn 这个抽象没有规定 spawn 出去的调用怎样、何时被调度执行，只规定它们可以和调用者（以及调用者 spawn 的所有其他调用）并发运行。问题：如果 Cilk 的实现把 cilk_spawn foo() 实现成和普通调用 foo() 一样，正确吗？正确。也就是说，在源码里搜索 cilk_spawn 删掉，搜索 cilk_sync 删掉，当普通 C 程序编译，是正确的实现，语言是有意这样设计的。另一个也正确的实现：每遇到一个 spawn 就开一个 C++ 线程跑它，cilk_sync 就是把它们都 join。可以顺序跑 foo、bar、fizz，可以放在不同线程，也可以 foo 和 bar 在一个线程、fizz 在另一个，都能得到相同的答案。但 cilk_sync 确实是对调度的约束：所有 spawn 出去的调用必须在 cilk_sync 返回前完成。

Cilk Plus 写的并行快速排序

void quick_sort(int* begin, int* end) {
    if (begin >= end - PARALLEL_CUTOFF)
        std::sort(begin, end);
    else {
        int* middle = partition(begin, end);
        cilk_spawn quick_sort(begin, middle);
        quick_sort(middle + 1, end);  // slide writes `last` here
    }
}

基本只加了一个 spawn；函数结尾有隐含的 sync，所以没写。问题规模足够小时就顺序排序，因为此时 spawn 的开销盖过了潜在并行的收益。这个基本情况不是正确性所需的。追踪一遍：主线程运行 partition（普通函数），spawn 一份并行工作（图上向右的分支），然后在当前控制线程上递归调用 quick_sort（也可以两边都 spawn，效果基本一样），递归下去，叶子是 std::sort。

写 fork-join 程序

  • 主要思路：用 cilk_spawn 把独立工作（潜在并行）暴露给系统。程序员只负责揭示工作，可以递归地揭示；调度这些程序是 Cilk 的责任。如果你没有创建足够多的并行任务，谁也没办法。
  • 回忆并行编程的经验规则：工作量至少要和并行执行能力相当（程序 spawn 的工作至少要能填满机器所有处理资源）；独立工作最好多于执行能力，以便把所有工作均衡地分到各核上。
  • "并行余量"（parallel slack）= 独立工作量与机器并行执行能力之比，实践中约 8 是个不错的比例。
  • 但独立工作也不能太多，否则粒度太细，余量太多会带来管理细粒度工作的开销。

七、调度 fork-join 程序：Cilk 的实现

现在开始谈 Cilk 的实现。考虑一个非常简单的调度器：每个 cilk_spawn 用 pthread_create 开一个 pthread，cilk_sync 翻译成相应的 pthread_join。可能的性能问题：

  • spawn 操作很重量级；
  • 并发运行的线程远多于核数；
  • 上下文切换开销；
  • 工作集比需要的大，缓存局部性差。

上一讲的演示里线程池比每任务一个线程快 300 倍。所以和大家一样，用线程池：Cilk Plus 运行时维护一个 worker 线程池，可以认为所有线程在应用启动时创建（实际上运行时一般比较"懒"，在第一次 cilk_spawn 时才初始化 worker 线程，ISPC 运行任务的 worker 线程也这样），worker 线程数恰好等于机器的执行上下文数。比如带超线程的四核笔记本，8 个 worker 线程。每个线程运行： 

while (work_exists()) {
    work = get_new_work();
    work.run();
}

所有 spawn 调用实际上是往待办列表里加工作，需要一个让每个线程运行的算法，既能做好负载均衡，又能把同步代价降到最低。

子任务和后续部分

考虑 cilk_spawn foo(); bar(); cilk_sync;，从 spawn foo 那一刻起。起个名字：spawn 出去的 foo 叫子任务（child），调用函数剩下的部分（bar 和之后）叫后续部分（continuation）。分配问题：foo 和 bar 该由哪个线程执行？

先看串行实现：线程 0 通过普通函数调用先跑子任务，跑 foo，从 foo 返回，再跑 bar。后续部分隐含在线程的调用栈里（栈表明从 foo 返回后接着跑 bar）。普通 C 程序先跑子任务，因为会进入函数调用。可是线程 0 执行 foo 时，如果线程 1 闲着，它本可以在这时执行 bar！

解决办法：每个线程有一个工作队列，存放"要做的工作"。原本栈放在堆里、别的线程看不懂；现在 spawn foo 时会建一个数据记录，表明有 foo、还有后续部分 bar，都在工作队列里。

  1. 线程 0 到达 cilk_spawn foo() 时，把后续部分放进自己的工作队列，开始执行 foo()。
  2. 线程 1 闲着（自己的队列里没有工作），就去忙碌线程 0 的队列里找工作。
  3. 线程 1 把工作从线程 0 的队列移到自己的队列。
  4. 线程 1 开始执行 bar()。

spawn 时，调用线程先跑子任务还是后续部分？

  • 先跑子任务：把后续部分放进队列，留待以后执行，后续部分可以被其他线程偷走，叫"后续窃取"（continuation stealing）。这和串行程序的顺序相同。
  • 先跑后续部分：把子任务放进队列，留待以后执行，子任务可以被其他线程偷走，叫"子任务窃取"（child stealing）。这是完全不同的顺序。

选哪个？看一个例子： 

for (int i = 0; i < N; i++) {
    cilk_spawn foo(i);
}
cilk_sync;
  • 先跑后续部分（子任务窃取）：调用线程在执行任何一次迭代之前，先把所有迭代的工作都 spawn 出来，foo(0)、foo(1)、foo(2)…… 一个个加进自己的队列，自己一直在跑那个 for 循环（那就是后续部分），队列越塞越满。可以想成调用图的广度优先遍历，spawn 出的工作要 O(N) 空间（最大空间）。如果没有窃取发生，执行顺序和删掉 cilk_spawn 的程序很不一样。
  • 先跑子任务（后续窃取）：调用线程只产生一个可偷的东西，即代表剩余所有迭代的后续部分。线程 0 在做 foo(0)，队列里是"从 i=1 开始的后续部分"。如果没有窃取，线程不断从队列弹出后续部分，再推入一个新的后续部分（i 更新了），执行顺序和删掉 spawn 的程序相同，可以想成调用图的深度优先遍历。如果后续部分被偷走，偷的线程 spawn 并执行下一次迭代（foo(1)），队列里变成"从 i=2 开始"；线程 0 做完了又把后续部分偷回来，执行 foo(2)，放入 i=3 的后续部分。这样后续部分在线程之间来回弹。可以证明，T 个线程的系统里，工作队列的存储不超过单线程执行时栈存储的 T 倍。

Kayvon 说到这里你可能感觉不太好，工作到处乱弹。但看看递归算法的情况。

调度快速排序：200 个元素

先跑子任务的方案下：先递归排 0 到 100，把"排 101 到 200"推进队列；再排 0 到 50，推入"51 到 100"；再排 0 到 25，推入"26 到 50"……递归调用不断堆积，每次放进去的工作都比上一次小，队列顶部是大任务，底部是小任务。由于程序的递归性质，任务大小各不相同。

现在闲着的线程 1、2 要去偷。三份工作，线程 1 该偷哪份？从顶部还是底部？同学们说偷顶部：一个理由是之前讲过把大工作留到最后会让一个线程在末尾独自干活；另一个更直接的理由：顶部是排 100 个元素的大任务，底部是排 25 个元素的小任务，既然要花窃取的开销，就偷最大的，偷过去它还会再分成小块供别人偷。

每个 worker 一个双端队列：

  • 本地线程从"尾部"（底部）推入和弹出，这和串行程序的顺序在某种意义上相同，也有好的数据局部性；
  • 远程线程从"头部"（顶部）窃取。

线程 2 偷走最大的那份（101 到 200），线程 1 偷走中等的（51 到 100），大家各自处理自己的工作，而这些工作又在递归调用、往各自的队列里塞东西。所有线程独立地处理子任务，完全不通信，边做边揭示更多的并行工作。在某个线程闲下来之前，不再有任何同步。对比单一共享工作队列：每做完一份都要去拿那个共享变量；现在只看自己的本地队列，就像自己的 myDiff。

选择受害者：闲着的线程随机选一个线程尝试窃取。有同学说应该偷工作最多的那个。理论上已经证明，随机选一个队列去偷，渐近意义上在最优的常数倍以内，改进也只能改进常数。而且如果大家都决定偷同一个线程，那次窃取会因为争用变贵；等别的线程也作出同样决定时，那份工作可能已经没了，你可能在偷一个只剩很少工作的线程。所以最简单的做法是随机挑一个有工作的队列。

从双端队列顶部窃取的好处：

  • 偷到的工作量最大，减少窃取次数，偷到大量工作就很久不用再同步；
  • 每个线程所做的工作局部性最好（配合先跑子任务的方案）；
  • 窃取线程和本地线程不争用双端队列的同一批元素，存在高效的无锁双端队列实现，同步少得多。

先跑子任务的工作窃取调度器适合分治

void recursive_for(int start, int end) {
    while (start <= end - GRANULARITY) {
        int mid = (end - start) / 2;
        cilk_spawn recursive_for(start, mid);
        start = mid;
    }
    for (int i = start; i < end; i++)
        foo(i);
}

recursive_for(0, N);

（课件这里的 mid 应理解为区间中点 start + (end - start)/2。）回到 for 循环 spawn foo(i) 的例子：那段代码是串行地揭示并行工作的，要么主线程串行地 spawn 所有东西，要么后续部分不断被偷、来回弹，Kayvon 请大家课下自己确认。这不好，我们有这么多线程，希望很快揭示出所有工作。更好的写法是上面这种分治的循环：前一半、后一半递归，再四分之一……一半的数组可以被偷走，然后像快速排序一样分裂下去，独立工作的产生本身也是并行的，所以能更快填满并行机器。Cilk 有 cilk_for 结构，写 cilk_for (i = 0; i < N; i++)，底层就是这样实现的。

八、实现 sync

最后一块：sync 意味着要检查所有 spawn 出去、可能被其他线程偷走的工作是否完成，需要更多簿记。例子： 

for (int i = 0; i < 10; i++) {
    cilk_spawn foo(i);
}
cilk_sync;
bar();

把 sync 之前的这段叫块 A，cilk_sync 同步块 A 内 spawn 的所有调用。循环快结束时的状态：线程 0 在做 foo(9)，队列里是"i=10 的后续部分"；线程 1、2、3 在做 foo(7)、foo(8)、foo(6)。下一个做完的线程会闲下来，去偷线程 0 的后续部分，那个后续部分说循环已结束，接下来要和所有其他工作 join。

没有窃取的情况：线程 0 在做 foo(9)（id=A），队列里是后续部分（id=A）。如果没有工作被别的线程偷走，sync 点什么都不用做，cilk_sync 是空操作。

有窃取的情况：

  1. 线程 0 在做 foo(0)，队列里是 i=0 之后的后续部分。空闲的线程 1 从线程 0 偷走它。这时创建块 A 的描述符，记录这个块未完成的 spawn 数和其中已完成的数：spawn: 1, done: 0。这 1 个 spawn 对应线程 0 正在跑的 foo(0)，因为偷完之后后续部分归线程 1 了。线程 0 的队列里留下 "STOLEN (id=A)" 的标记。
  2. 线程 1 开始跑 foo(1)，spawn 计数变成 2。
  3. 线程 2 偷走后续部分，跑 foo(2)，spawn 计数 3。
  4. 线程 0 完成 foo(0)，块 A 已被偷过，所以完成时要更新 done 计数：spawn: 3, done: 1。线程 0 闲了，去偷更多工作，跑 foo(3)，spawn: 4。
  5. 计算接近尾声：spawn: 10, done: 9，只剩 foo(9)，线程 0、1 都闲着。
  6. 最后一个 spawn 完成：spawn: 10, done: 10。
  7. 线程 2 接着执行后续部分，运行 bar()。块 A 的描述符释放。

这里没讲怎样给这些共享数据结构加锁解锁。要点：sync 要记录与这个块相关的所有 spawn；完成某个被偷过的块的工作时，更新引用计数；完成最后一份工作的那个线程，直接接着执行后续部分。

贪心 join 调度

  • 所有线程无事可做时总是尝试窃取（所以叫贪心）；
  • 只有系统里没有可偷的工作时，线程才闲下来；
  • 发起 spawn 的 worker 线程不一定是执行 cilk_sync 之后逻辑的那个线程。例子里 spawn 由线程 0 开始，由线程 2 收尾，因为它是最后一个做相关工作的。

记住：只有发生窃取时，才有记录窃取和管理 sync 点的开销；如果偷走的是大块工作，窃取就不常发生；大多数时候线程只是在自己的本地双端队列上推入和弹出本地工作。

Cilk 小结

  • fork-join 并行是表达分治算法的自然方式。这里讲的是 Cilk Plus，很多其他系统也有 fork/join 原语（比如 OpenMP）。
  • Cilk Plus 运行时用一个注重局部性的工作窃取调度器实现 spawn/sync 抽象：总是先跑 spawn 出去的子任务（后续窃取）；join 时是贪心的（线程不在 join 处等待，立即去找别的工作偷）。

Kayvon 说 Cilk 很优雅，玩起来很有意思。它的调度算法有扎实的理论保证，随机地做一些事就能保证在最优调度的常数倍以内；它让你写分治程序几乎和不考虑并行时一样容易；底层的调度策略最大化局部性，最小化线程间的通信，同时仍能做到相当好的负载均衡。这比作业 2 要求实现的东西高级得多，只是大家通常喜欢了解；这类技术在分布式系统等地方也很常见。
