第十八讲：硬件专用化与面向算法的编程

能量受限的计算：Dennard 缩放终结后，性能只能靠降低每次操作的能耗；通用处理器为什么低效：执行一条指令的能量大多不花在运算上；SIMD 的分摊和它的上限；FFT 上 ASIC 对 CPU 的千倍面积效率、百倍能效；DSP、Anton、TPU、FPGA；可编程性与能效的光谱；用 Spatial 设计加速器：存储模板、控制模板、设计参数，内积的逐步优化（分块、并行、流水）；流式执行模型让注意力"免费融合"，与 FlashAttention 的关系

主讲：Kunle Olukotun
资料来源：课堂录像（Stanford Online，2023 年秋季）、课件（课件标号为 Lecture 17）；第十七讲课件末尾的异构处理器例子一并整理在这里；课件最后的 DRAM 部分课上没讲，放在第十九讲

一、能量受限的计算

上一讲末尾讲了异构：不同的程序特征可以被更专门的架构利用，目前主要讲的是能被 GPU 这类架构利用的数据并行计算，得到高性能，更重要的是能效。专用化和面向算法的编程是异构计算环境的下一步：为某个特定应用非常专门化的环境。

为什么受能量约束？因为底层半导体技术的状况。曾经每一代新工艺都给你更多晶体管，而这些晶体管功耗更低，同样的功率能得到更高的性能，这叫 Dennard 缩放。它大约十年前就结束了，现在晶体管多了，功耗就增加，于是被功率和能量约束住了。

  • 能量 = 功率 × 时间；功率 = 每秒操作数 × 每次操作的焦耳数。
  • 能散发的功率是固定的，想要更高的性能，就必须降低每次操作的能耗，提高能效。
  • 提高能效的关键手段是专用化（固定功能），去掉那些不推动计算前进的多余功耗。专用化能带来多大的改进？

整个计算领域都受能量约束：

  • 超级计算机：机器规模庞大，几千甚至几十万个核，运行的总成本（机器本身的电力和冷却）很高。
  • 数据中心（Google、Facebook 这类大网站背后）：降低冷却成本，减少物理空间需求。在计算资源三年左右的生命期里，供电和冷却的成本可能超过购买计算资源本身。
  • 移动设备：电池寿命有限；散热，手机里没有风扇，只能被动散热。

专用化的效率收益

经验规则，和 CPU 上高质量的 C 代码相比 [Chung 等 2010，Dally 08]：

  • 吞吐量最大化的处理器架构，比如 GPU 核：每瓦性能约高 10 倍，前提是代码能很好地映射到宽数据并行执行，并且受计算限制。
  • 固定功能 ASIC（专用集成电路）：每瓦性能可接近高 100 到 1000 倍或更多，前提是代码受计算限制，而且不是浮点运算。

等一下……这一整门课都在讲怎样高效使用多核 CPU 和 GPU，现在又说这些平台"低效"？

二、通用处理器为什么这么低效

想想在现代处理器上执行一条指令有多复杂：

  • 读指令（地址转换、和指令缓存通信、访问指令缓存等）；
  • 译码指令（把操作翻译成微操作、访问微操作缓存等）；
  • 检查依赖和流水线冒险；
  • 找可用的执行资源；
  • 用译码出的操作数控制寄存器文件 SRAM（取数据）；
  • 把数据从寄存器文件移到选中的执行资源；
  • 执行算术运算；
  • 把数据从执行资源移回寄存器文件；
  • 用译码出的操作数控制对寄存器文件 SRAM 的写。

Kunle 说，看一条乘加指令的能耗分解，大部分能量并不用于实际计算，计算只占约 6%（课件图出自 Eric Chung），其余花在处理指令、弄清它要做什么、取数据和搬数据，以及控制电路、分发时钟这些开销上。对比真正做运算所需的电路：比如 8 位逻辑或，就是 8 个或门。

复习题：SIMD 执行怎样降低某些计算的开销？这些计算必须有什么性质？同学答：只推一条指令就做多个算术运算，把那些非绿色的部分分摊到更多的绿色（运算）上，SIMD 宽度决定你可能有多高效。那为什么不做 16、32、64 宽？同学答：宽 SIMD 很难用满。对，峰值很好看，平均会差得多，因为可能填不满所有 SIMD 槽，看不到那么多 SIMD 数据并行。

SIMD 改善了吗？斯坦福几年前的研究 [Hameed 等，ISCA 2010]：H.264 视频编码（相当数据并行、对 SIMD 友好的应用）在支持 SIMD 的 CPU 上的能耗分解，即使用 SIMD 指令实现了编码，功能单元消耗的能量比例仍然很小。各部分：FU 功能单元，RF 寄存器读取，Ctrl 其他流水线控制，Pip 流水级间寄存器，IF 取指加指令缓存，D-$ 数据缓存；阶段包括整数运动估计、分数（亚像素）运动估计、帧内预测、DCT 和量化、算术编码。想做得更好，就得实现更专门的部件。

快速傅里叶变换（FFT）：专用化的吞吐量和能量收益

[Chung 等，MICRO 2010] FFT 是很多信号处理应用的核心、研究得很透的算法，有人称之为有史以来最重要的算法。横轴是 lg2(N)（数据集大小），比较 CPU（Core i7）、GPU、FPGA、ASIC 的每平方毫米 GFLOPS 和能效。这是很老的 40 纳米工艺的研究：

  • ASIC 达到一个 CPU 核同样的性能，只需约 1/1000 的芯片面积；
  • GPU 核的面积效率比 CPU 核高约 5 到 7 倍；
  • ASIC 达到一个 CPU 核同样的性能，只用约 1/100 的功率。

ASIC 的坏处？同学答：只能用于那一个算法。而且要去设计它：有了新想法，要等 18 个月设计 ASIC 吗？它最好是 FFT 那样重要的算法，才值得做 ASIC。

移动设备：提高效率的好处

  • 在固定时间内跑得更快：更高的时钟，用更多的核（降低关键任务的延迟）；同时做更多事。
  • 在固定性能下跑得更久：比如视频播放、健康应用；实现以前不可能的"常开"功能。例子：Amazon Echo / Google Home 一直在听；iPhone 的 Siri 要按按钮或把手机举到耳边才激活；Google Glass 每次充电约 40 分钟录像（离"常开"差得远）。

三、异构的例子

观察：大多数真实应用的工作负载特征很复杂，有能大规模并行的部分，也有难以并行的；有适合宽 SIMD 的，也有不适合的（控制流发散）；有数据访问可预测的，也有不可预测但可能缓存得很好的。想法：最高效的处理器是各种资源的异构混合（"用最高效的工具做每件事"）。

  • Intel Skylake（2015，第六代 Core i7）：4 个 CPU 核加图形核加媒体加速器；CPU 核和图形核共享内存系统，也共享 LLC（L3），让 CPU 和集成 GPU 之间低延迟、高带宽通信；图形核和 CPU 核缓存一致。
  • 再加一块独立 GPU：高端独立 GPU（AMD 或 NVIDIA）通过 PCIe x16 总线连接，有自己的 DDR5 显存。除非是图形密集的应用，否则让耗电的独立 GPU 休息；基本的图形、窗口管理、UI 用集成的低功耗图形。
  • 移动异构处理器：Apple A11 Bionic（TechInsights 的估计，非 Apple 官方资料），两个"高性能"64 位 ARM CPU 核，四个"低性能"ARM CPU 核，三"核"Apple 自研 GPU，图像处理器，用于 DNN 加速的神经网络引擎，运动协处理器。NVIDIA Tegra X1，四个 ARM Cortex A57 CPU 核跑应用，四个低功耗的 ARM A53 核，一个 Maxwell SMM（256 个"CUDA"核）。
  • GPU 加速的超级计算：橡树岭国家实验室的 Frontier（2022 年秋世界第一），9,472 颗 AMD 64 核 2 GHz CPU（606,208 个核），37,888 块 Radeon Instinct MI250X GPU，10 PB DRAM，功率 21 MW，造价 6 亿美元。
  • GPU 本身就是异构多核处理器：你在 CUDA 作业里用的计算资源（一堆带缓存的 SIMD 执行单元），加上图形专用的固定功能计算资源：纹理、裁剪/剔除、光栅化、细分、Z 缓冲/混合、调度器/工作分发器。固定功能硬件做的图形任务例子：光栅化（确定三角形覆盖哪些像素）、纹理映射（变形、过滤图像，把细节贴到表面上）、几何细分（从粗糙几何算出细尺度几何）。

异构让硅片资源和能量的使用更高效，但编程更难：CPU 核要多线程，GPU 要 CUDA 这类数据并行模型，媒体部件可能还要别的编程模型。

四、比 CPU 更专门的计算

数字信号处理器（DSP）

  • 可编程处理器，但指令流控制通路更简单。
  • 复杂指令（比如 SIMD、VLIW）：每条指令做很多操作，分摊控制的代价。
  • VLIW："超长指令字"，一条指令规定同时做多个不同的操作（和 SIMD 不同）。
  • 例子：Qualcomm Hexagon DSP，用于 Qualcomm Snapdragon SoC 上的调制解调器、音频，以及越来越多的图像处理；Google Pixel 手机里就有。课件给出 FFT 最内层循环，Hexagon 每周期做 29 个"RISC"操作。

DSP 专做 FFT、滤波这类信号处理算法，通用计算机的指令和寻址方式在这里可以改进：有正好满足特定算法需求的复杂指令，有复杂的寻址方式，比如 FFT 需要的位反转寻址。给你这么复杂的指令集，能写出编译器吗？大概不能。所以这些复杂指令总伴随着底层编程，实现各种算法要手写。比做 ASIC 容易得多，但比给通用 CPU 编程难得多。效率和可编程性之间有了权衡。

Anton：分子动力学超级计算机

  • 模拟蛋白质随时间的演化；
  • 计算粒子间相互作用的 ASIC（机器里有 512 个）；
  • 面向吞吐量的子系统，高效做快速傅里叶变换；
  • 定制的低延迟通信网络，针对 N 体模拟的通信模式设计；
  • 由 D. E. Shaw Research 开发。

Kunle 说 D. E. Shaw 在金融领域赚了很多钱，决定花一部分做对人类有益的事，其中之一是分子动力学加速器。理解蛋白质怎样折叠，归结为算分子之间的相互作用，这是化学里重要的领域，有人因此得过诺贝尔奖。通过把算法和硬件一起精心设计，他们比 CPU 和 GPU 快得多，目前大概有三代 Anton，一代比一代好。顺便提一句，也可以用统计方法解决这个问题，做加速器的人和做大规模统计方法的人之间曾经有张力。

深度网络的专用处理器

例子：Google 的 Tensor Processing Unit（TPU），加速深度学习运算；Intel Lake Crest 机器学习加速器（原 Nervana）。顶级计算机体系结构会议上有数不清的关于深度学习 ASIC 或加速器的论文。Kunle 说 TPU 掀起了为机器学习开发新架构的热潮，可以把它理解为让大的稠密矩阵乘法跑得很快：最初是 256×256 的整数矩阵乘法，后来的版本改成 128×128，但做 16 位浮点乘法。这些架构大多其实有一定可编程性，因为要适应机器学习算法的变化，但根本上聚焦于这些算法的核心计算内核：矩阵乘法，大多是稠密的，也有有意思的稀疏版本。

Google 的 Pixel Visual Core：可编程的"图像处理单元"（IPU），每个核是 16×16 的 16 位乘加 ALU 网格，Google 在 HotChips '18 上称其在图像处理任务上比 GPU 高效约 10 到 20 倍。

打开一部现代智能手机（Google Pixel 2：Qualcomm Snapdragon 835 SoC 加 Google Visual Pixel Core）：多核 GPU（3D 图形，OpenCL 数据并行计算）；显示引擎（压缩像素，传到高分辨率屏幕）；图像信号处理器（处理相机传感器像素的 ASIC）；多核 ARM CPU（4 个大核加 4 个小核）；视频编解码 ASIC；"Hexagon"可编程 DSP（数据并行的多媒体处理）；Visual Pixel Core（可编程图像处理器和 DNN 加速器）。

FPGA（现场可编程门阵列）

  • ASIC 和处理器之间的折中。是否有一种能有点可编程性的硬件？这就是 FPGA 的动机，有人在数字设计课上玩过。
  • FPGA 芯片提供一组逻辑块，由互连连接。可配置逻辑块基本是布尔代数的查找表（LUT），比如能算任意四输入布尔函数，再配一个触发器（寄存器）提供存储。
  • 程序员定义的逻辑直接由 FPGA 实现。
  • 用 LUT 描述组合逻辑：比如 Xilinx Virtex-7 FPGA 里的 6 输入 1 输出 LUT，可以把 LUT6 想成一张 64 项的表；例子：6 输入与门；40 输入与门由 8 个 LUT6 的输出级联构成（延迟为 3）。
  • 现代 FPGA：很多面积给了硬门电路，存储块（SRAM）、DSP 块（乘法器）。全用可配置逻辑块搭一切最灵活，但开销很大：连接这些块的开销，用 CLB 实现计算单元的开销。想更紧凑高效地用硅片，就要这些硬宏块。
  • Microsoft Research 的 Project Catapult：研究用 FPGA 加速数据中心工作负载，演示了把 Bing 搜索的部分文档排序逻辑卸载到 FPGA 上；1U 服务器，双路 CPU 加通过 PCIe 总线连接的 FPGA [Putnam 等，ISCA 2014]。
  • Amazon EC2 F1：云上提供 FPGA，相当先进，有连到 DDR4 内存、通过 PCIe 连到 CPU、连到其他 FPGA 的链路，还有一整套软件开发环境用来给它编程。Kunle 说也可以去他的实验室看看怎样用。

为任务选择正确的工具

Pat Hanrahan 设计的这张光谱图，从左到右：能耗优化的 CPU；面向吞吐量的处理器（GPU），约高效 10 倍；可编程 DSP；FPGA / 可重构逻辑，约 100 倍？（尚无定论）；领域专用的（有限领域的可编程性，比如 Google TPU）；ASIC，约高效 100 到 1000 倍，用于视频编解码、音频播放、相机 RAW 处理、神经网络（未来？）。左边最容易编程；右边难以编程（让它变容易是活跃的研究领域）；ASIC 不可编程，而且设计、验证、制造要花几千万到几亿美元。

Kunle 的解读：作为系统设计者，要根据约束挑：需要多高的能效，应用要多快能用起来，愿意花多少功夫。CPU 能满足性能就用高级语言写；要更多性能就往右走，GPU 可能要写 CUDA；DSP 可能要写汇编；领域专用计算，如果领域是机器学习之类、能用 PyTorch 或 TensorFlow 编程，可能效果不错；FPGA 基本上要成为硬件设计者；ASIC 则肯定是硬件设计者。越往右能效越高，ASIC 高得惊人，但要更费力、花更多钱。

有同学问：TPU 的 1000 倍很诱人，但中间那段，为什么不干脆买两块 GPU，可能便宜得多？Kunle 说还没有定论；GPU 显然在借鉴 TPU，原来是通用的线程，现在加了 Tensor Core 单元，更专门了；但作为 CUDA 程序员去给 Tensor Core 编程其实很有挑战（这门课没做）。这个领域在变化，被机器学习这个高价值应用驱动，大家都在把架构往这个方向倾斜。为什么 DSP 比 GPU 效率高？它更专注于 DSP，有很多专门的寻址机制和计算，做数字信号处理时会更高效；做机器学习大概就不是了。

异构的挑战

  • 异构系统：每项任务有首选的处理器。
  • 对软件开发者的挑战：怎样把应用映射到一组异构资源上？"为任务选对工具"：设计能分解成多个部分、每部分都能很好地映射到机器不同处理部件的算法；异构系统上的调度问题更复杂。
  • 对硬件设计者的挑战：资源的正确配比是什么？面向吞吐量的资源太少（并行工作负载的峰值吞吐量低）；顺序处理资源太少（受工作负载里顺序部分的限制）；芯片面积该给特定功能（比如视频）分多少？

五、为算法设计加速器：Spatial

这门课大部分时间在想怎样给现有架构里固定的那组资源编程，通用处理器或 GPU。现在想想：如果要描述或编写一个加速器，能控制通用环境里控制不了的东西，需要什么？特别是能有定制的存储系统，很多性能提升来自按应用的局部性和访问特征来组织存储；以及匹配应用需求的专门计算。

课件的对比图：通用处理器是双核、多线程（每核 4 线程）、双发射超标量（每核每周期最多从任意线程发两条独立指令，一条标量一条向量，16 宽向量 ALU），有共享数据缓存和 DRAM；专用处理器（加速器）有定制的控制、定制的寄存器、定制的存储（SRAM）和大量 ALU。

想为你的算法设计一个加速器

  • 传统上要花好几年成为 VHDL 或 Verilog、Chisel 的专家，在寄存器传输级（硬件描述级）思考。（很多同学写过 Verilog，知道其中的痛苦。）
  • 高层次综合（HLS）：Vivado HLS、Intel OpenCL、Xilinx SDAccel。受限的 C 加上 pragma。这些工具牺牲性能，而且难用。Kunle 指出两个问题：C 程序本来不是为描述硬件而设计的，要从为通用处理器写的程序推断硬件该做什么；为弥补 C 的不足加了 pragma，而要把 pragma 放对，你得懂很多硬件，于是升到 C 层面的初衷就落空了，想得到像样的性能，还得借 pragma 下降到硬件层面。
  • Spatial 是一门设计硬件加速器的高级语言，让面向性能的程序员能够描述：并行，即专门的计算；局部性，即专门的存储和数据移动。这门课的同学现在都算面向性能的程序员。网站 spatial-lang.org。

Spatial：加速器设计的 DSL

  • 简化可配置加速器的设计。表达以下内容的结构：
    • 把并行模式（map、zip、reduce 这类对集合的数据并行模式）表达为并行和流水的数据通路；
    • 独立的并行：用独立的计算单元执行 map；
    • 依赖的并行：并行的单元相互依赖。怎样执行各部分相互依赖的计算？同学答：像 CPU 的指令流水线那样。对，指令执行流水线的各部件都相互依赖，但有一串独立的指令，就像工厂造汽车的装配线，每个工位独立工作，靠流水线各段之间得到并行；
    • 层次化的控制（并行模式可以嵌套）；
    • 显式的存储层次。
  • 显式的参数：所有参数都暴露给编译器，编译器可以替你探索设计空间。
  • 管理 CPU 和加速器之间通信的简单 API。
  • 让程序员专注于"有意思的东西"：为面向性能的程序员（并行和局部性）设计；比 CUDA 更直观，是数据流而不是线程。

Spatial 语言：存储模板

val image  = DRAM[UInt8](H,W)     // off-chip memory
val buffer = SRAM[UInt8](C)       // on-chip memory
val accum  = Reg[Double]          // registers
val fifo   = FIFO[Float](D)
val lbuf   = LineBuffer[Int](R,C)
val pixels = ShiftReg[UInt8](R,C)

val videoIn  = StreamIn[RGB]      // streaming abstractions
val videoOut = StreamOut[RGB]

buffer load image(i, j::j+C)      // dense transfer
buffer gather image(a, 10)        // sparse transfer
  • 显式的存储层次：片上的 SRAM、片外的 DRAM，指定数据类型（这里是无符号 8 位）和元素数；各种寄存器、累加器；FIFO 就是队列，后面会大量用到；图像处理里的行缓冲（可以按行移动的二维数组）；移位寄存器（和行缓冲精神类似）。
  • 类型化的存储模板。
  • 跨存储层次的显式传输。CPU 上程序员只看得到主存地址空间，可以写对缓存友好的代码，但控制不了数据在主存和缓存之间怎样移动，那由底层硬件控制器自动处理；Spatial 里不是这样，程序员必须显式地在存储层次之间搬数据。这里用 load 把数据从 DRAM 里的 image 搬到 buffer，是稠密的数据移动。
  • 稠密和稀疏的访问：gather 怎样工作？从 image 取 10 个元素，位置由某个数组 a 给出，把稀疏数据变成 buffer 里稠密的。相应地还有 store 和 scatter。
  • 流的抽象：可以把数据流进流出，流是获得效率的关键。

Spatial 语言：控制模板

Accel { ... }       // blocking interaction with CPU
Accel(*) { ... }    // non-blocking: runs continuously

FSM[Int]{s => s != DONE }{
    case STATE0 =>
        Foreach(C by 1){j => ... }
    case STATE1 => ...
        Reduce(0)(C by 1){i => ... }
}{s => nextState(s) }
  • 和 CPU 的阻塞或非阻塞交互：Accel 块把程序分成加速的部分和只在 CPU 上跑的部分；Accel 只运行一次，Accel(*) 持续运行。
  • 任意的状态机和循环嵌套，控制信号是隐含的。有限状态机这里不讲，重点是做并行模式的关键机制：Foreach，本质上是 map；Reduce，就是 reduce。"对 C 里的所有元素，步长 1，执行花括号里的代码。"

Spatial 嵌在 Scala 里，有历史原因。Scala 很灵活，很适合嵌入 DSL，第九讲讲 Spark 时见过；它曾经作为宿主语言很流行，但因为基于 JVM 有些缺陷，限制了普及。

Spatial 语言：设计参数

val B = 64 (64 -> 1024)          // explicit size parameters for stride and buffer sizes
val buffer = SRAM[Float](B)
Foreach(N by B){i =>
    ...
}

val P = 16 (1 -> 32)             // explicit parallelization factors
Reduce(0)(N by 1 par P){i =>
    data(i)
}{(a,b) => a + b}

Stream.Foreach(0 until N){i =>   // implicit/explicit control schemes
    ...
}

Foreach(64 par 16){i =>
    buffer(i)                     // parallel read: implicit memory banking
}
  • 显式的并行化因子：某个 Foreach、Reduce 并行多少。
  • 显式的步长和缓冲大小参数：比如缓冲大小默认 64，但希望在 64 到 1024 之间，编译器可以探索。
  • 隐式或显式的控制方案：指定怎样调度，流水还是流式。
  • 为并行访问隐式地做存储分体（banking）和缓冲：如果并行化意味着对同一个存储单元有多次访问，编译器负责复制存储或恰当地分体，保证能达到这个并行度，你不用操心。

例子：内积

用 Spatial 造一个加速器，看看它怎样工作。先看 C： 

// set up accumulator and memory pointers
int output = 0;
int* vec1 = (int*)malloc(N * sizeof(int));
int* vec2 = (int*)malloc(N * sizeof(int));

// iterate through data and accumulate
for (int i = 0; i < N; i++) {
    output = output + (vec1[i] * vec2[i]);  // slide writes vec1(i) * vec2(i)
}

Spatial 版本，逐步构建。开头像 C：vec1、vec2 是 DRAM 里的整数数组；Accel 在硬件里实例化这个"for"循环。假设有直接内存访问（DMA）这种在主存和加速器之间高效搬数据的方式。 

// set up host and memory pointers
val output = ArgOut[Int]
val vec1 = DRAM[Int](N)
val vec2 = DRAM[Int](N)

// create accelerator (instantiate hardware)
Accel {
    // allocate on-chip memories
    val tile1 = SRAM[Int](tileSize)
    val tile2 = SRAM[Int](tileSize)

    // specify outer loop
    Reduce(output)(N by tileSize){ t =>
        // prefetch data
        tile1 load vec1(t :: t + tileSize)
        tile2 load vec2(t :: t + tileSize)

        // multiply-accumulate data
        val accum = Reg[Int](0)
        Reduce(accum)(tileSize by 1 par 1){ i =>
            tile1(i) * tile2(i)
        }{a, b => a + b}
    }{a, b => a + b}
}
  • 要把数据从 DRAM 搬进加速器，就得在加速器里给数据一个落脚的地方：两块 SRAM，tile1 和 tile2，大小为 tileSize。
  • 要分块，所以需要双重嵌套循环。为什么从 DRAM 取一块而不是单个元素？同学答：缓存更好。Kunle 说：能更好地利用 DRAM 和加速器之间的接口，就像去超市，从来不会只买一样东西，跑一趟就买一堆放进冰箱和储藏室，不用每次想吃东西都跑超市。去 DRAM 代价很高，要取一块大小的数据。在 CPU 上这就是通用缓存，数据移动由缓存算法控制；这里你显式地编排数据移动。
  • Spatial 生成多步的控制器（外层 Reduce 控制器的最后一步负责累加）；Spatial 管理和 DRAM 的通信。完整的应用生成三步控制：装入 → 块内累加 → 整体累加。

并行在哪里？

  • 同学说：三个步骤可以在数据的不同部分上同时做。那是流水，先放一放。
  • 同学说：并行化第 2 步（块内的归约）。最有效的方式是什么？从口袋里掏出你很熟的东西：一直在做同一条指令，所以 SIMD。并行化这个 reduce 需要并行的乘法加一棵归约树。Spatial 有归约和归约树的概念，可以 par 2，这时没什么树，只是两个乘法；也可以更宽。更宽的坏处？归约树更大，硬件更多，用更多资源。没有免费的午餐，但你能根据想要的性能提升控制用多少资源。
Reduce(accum)(tileSize by 1 par 2){ i =>
    tile1(i) * tile2(i)
}{ _ + _ }
  • Spatial 帮你表达硬件数据通路。
  • 也可以控制块大小，决定每次去内存取多少数据：比如 val bigTileSize = 2*tileSize，外层按 bigTileSize 步进、装入 bigTileSize 个元素。Spatial 让分块变得容易。
  • 最后，用流水调度让外层 Reduce 的各步重叠：Pipeline.Reduce(output)(N by tileSize){ ... }。有了注解，各步（各级）以流水方式执行，存储的"缓冲"由编译器推断。Spatial 让分块和流式处理变得容易，让用户管理调度。

流水要成立，关键需要什么？同学先说冒险，Kunle 说已知没有冒险；额外需要什么资源？双缓冲：第 1 级在从内存填数据时，第 2 级要能处理上一次第 1 级产生的数据。流水几乎是硬件里最接近免费午餐的东西，但不完全免费，因为要加存储。最好情况是 3 级流水，性能提升 3 倍（当然不总是这样），开销是每个级间接口要额外的块存储，保证流水时数据不被覆盖。三种优化：并行化、数据局部性的处理、流水。

Spatial 问题：谁负责什么

  • Spatial 程序员的责任：把算法表达为控制器的层次（用 Foreach、Reduce 结构）；描述算法的存储层次（数据该住在你定义的哪块存储里）；显式的数据移动；选择分块因子、并行度和调度。
  • Spatial 编译器的责任：存储的分体和缓冲，最大化性能、最小化资源；为目标平台（FPGA、CGRA、ASIC）生成硬件；性能调试反馈，告诉你代码在各目标上能达到什么性能、要用多少资源。

从 TensorFlow 到 FPGA

Spatial 被用来把机器学习算法的 TensorFlow 表示转换成硬件。流程：高层应用（领域专用算子的数据流图，比如输入数据、卷积、权重、求和池化、归一化）→ IR 翻译 → 并行模式 IR（并行模式的层次化数据流图，Map、Reduce）→ 模式编译器 → Spatial IR（分块流水线的层次化数据流图，存储层次：DRAM、移位寄存器、行缓冲、寄存器文件、SRAM）→ Spatial 编译器 → Chisel/Verilog（存储和计算单元、控制信息）→ FPGA 工具 → FPGA 配置。

六、流式执行模型：注意力的"免费融合"

回顾：FlashAttention 为什么强大？同学答：不用物化注意力矩阵。把东西分块，一次算一块，把注意力算法的各部分融合在一起，减少内存带宽，带来性能和内存大小上的收益。用 Spatial 这种流式编程模型，用更简单的编程模型就能得到很多同样的好处，不必写显式的融合内核。用流式执行，这些好处是免费的（免费融合！）。

  • 基于内核的执行模型：FlashAttention 避免物化 N×N 矩阵，但它要修改算法，还要额外计算（为了处理 softmax 需要整行才能算的问题）。
  • 流式执行模型：避免物化 N×N 矩阵，不用改算法，也没有额外计算，代价是可能多用一点存储。

预备：softmax

softmax 其实是三步操作：Pij = eSij / Σj eSij。① 指数：S' = Exp(S)，N×N；② 归约（按行）：r = RowSum(S')；③ 除法：P = S' / r。

注意力：S = QKT（N×N），S' = Exp(S)（N×N），r = RowSum(S')，P = S'/r（N×N），O = PV。

基于内核的执行模型

不做 FlashAttention 那样的优化，每一步是一个内核，每步之间都要物化整个 N×N 矩阵：物化 N×N 矩阵，内存占用上升；读写 N×N 矩阵，内存带宽上升。课件的总览图显示所有必须物化、并在加速器（上方）和 GPU 显存（下方）之间搬运的数据，所有穿过那条线的数据都是计算注意力要用的内存带宽。

流式执行模型

用流式执行模型，得到免费的融合：避免物化 N×N 矩阵，内存占用下降；避免读写中间的 N×N 矩阵，内存带宽下降。

例子程序，计算指数和行求和 Exp(S)、RowSum(S')：输入输出在片外存储，装入片上存储，逐片计算。用 Spatial 写：第一个 Foreach（一个 map）算指数，但不把输出放进另一个矩阵，而是放进一个 FIFO 排队；Spatial 的语义是这个 Foreach 和下一个 Foreach 同时执行。第一个 Foreach 是生产者，第二个消费它的输出：从 FIFO 出队一个元素，持续累加，做完后输出也放进 FIFO（这里是单个元素）。两个 Foreach 构成流水线，中间是 FIFO。

没有流式时要物化整个 N×N 矩阵；有了流式，数据只是流过去，这里只要两个元素的 FIFO，相当于第一个例子里的双缓冲，只是变成了显式的 FIFO，所需存储大幅减少。但要让它成立，编程模型要能想象这两个内核同时运行、由 FIFO 相连，这是很自然的硬件思路，却不是自然的软件思路。Spatial 让你按高效硬件实现所需的方式思考流水并行，而这和通常写软件的方式不同。

对整个注意力：一个内核把数据放进 FIFO，下一个内核取出来计算，永远不必物化整个矩阵。课件逐帧演示 Q1 和 KT 的块依次产生 S1、S2、S3、S4，经过指数、行求和、除法得到 P1 到 P4，再和 V 的块相乘累加出输出块 O1，同时开始下一个输出块的计算。限制是：按行做的操作需要累积一整行数据，所以 FIFO 要有矩阵一行那么长，这可能成为限制。

能用 FlashAttention 做得更好吗？

  • 能！像 FlashAttention 那样多付一点计算代价，就能去掉中间那个 FIFO。
  • 需要这个序列长度（N）大小的 FIFO，是为了缓冲 S' = Exp(S) 的输出：softmax 里要等按行的归约（行和）算完，才能用它去除 S' 的输出。
  • FlashAttention 打破这个依赖：重排操作；用运行和加重新缩放代替朴素的归约（行和）。序列很长时连一行都太多，想限制 FIFO 大小，就可以把 FlashAttention 用到流式的优化上，大幅减少 FIFO 里一行数据的需求。

内核执行与流式执行

  • 更多并行：基于内核执行的 FlashAttention 不能重叠不同输出块的计算；流式执行模型把每个计算在空间上映射成带流水通信的单元，能重叠（流水）不同输出块的计算，多了一个维度的并行和性能。
  • 不必手工写融合内核：基于内核执行的 FlashAttention 要在 CUDA 里手写融合内核，由于每个 SM 寄存器数的限制，往往很难融合得很深；流式执行模型里，用 FIFO 写程序，操作就自动融合；即使用缓冲写，也能用双缓冲技术；编译器可以自动生成融合的执行。

有同学问流式执行模型是否独立于加速器设计、能在现有架构上跑。可以设想，但在 CUDA 里写流式程序很难，根本没法让内核的不同部分独立运行，通常只能写融合内核；Kunle 认为开发 CUDA 的人在努力支持这种执行方式，但目前还不知道怎么做到，不是说永远不行。FIFO 太深怎么办？可以改用 SRAM 而不是寄存器做缓冲，应用写法可能要稍改；或者用 FlashAttention 这类从根本上缩小 FIFO 的技术。简单粗暴地用 FIFO 就能得到好处，不用太费劲；FIFO 太大了，再更费力地变换应用。Spatial 能面向很多目标，它本来是硬件模型，非常适合他们定义的一种新型架构"可重构数据流"，和 GPU 不太匹配，当然也能在 CPU 上跑。

加速器设计小结

  • 专用加速器带来显著的能效提升（100 到 1000 倍）。
  • 设计加速器是在性能和资源利用之间权衡：并行；局部性。
  • 需要程序员洞察应用：瓶颈在哪里？实现受计算还是受内存限制？算法和实现变化时它怎样变？
  • Spatial 帮你理解性能和资源利用之间的权衡：允许快速探索你的算法；支持高层次的加速器设计。

Kunle 说这是比这门课所做的再往前一小步：你懂应用，懂并行和不同类型的并行；如果硬件也由你定义，你会怎么做？在加速器设计里，你显式定义用什么资源来利用并行、怎样设计存储层次来获得最大局部性，定义大小，定义数据何时从存储层次的一部分移到另一部分。

七、降低能耗的第二个思路：少搬数据

降低能耗的思路 1：用专门的处理（为任务选对处理器）。思路 2：少移动数据。（课件这部分在本讲课上没时间讲，Kunle 说存储设计也许由 Kayvon 周四讲；DRAM 的细节见下一讲。）

  • 移动系统设计的经验规则：总要设法减少从内存传输的数据量。前面为了减少停顿（性能差）而减少通信，现在是为了减少能耗而减少通信。
  • "大致"数字：整数运算约 1 pJ；浮点运算约 20 pJ（只算执行逻辑运算本身，不含指令译码、从寄存器装数据等开销）；从很近的小块本地 SRAM（芯片上 1 毫米外）读 64 位约 26 pJ；从低功耗移动 DRAM（LPDDR）读 64 位约 1200 pJ [来源：Bill Dally（NVIDIA）、Tom Olson（ARM）]。
  • 含义：从内存每秒读 10 GB 约 1.6 瓦；移动 GPU 的整个功率预算约 1 瓦（别忘了手机还在跑 CPU、显示、无线电等）；iPhone 6 电池约 7 瓦时（作为对比，课件作者的 MacBook Pro 电池 99 瓦时）。利用局部性很重要！！！
  • 这说明：为能效优化代码时，重新计算值，而不是存起来再读回，是更好的选择！

移动数据代价很高！数据移动限制性能：处理单元很多，意味着整体内存请求速率更高，需要更多内存带宽（结果是受带宽限制的执行）。数据移动能耗很高（[Han，ICLR 2016]，45 纳米 CMOS 假设）：32 位浮点运算约 0.9 pJ；本地 SRAM（片上）数据访问约 5 pJ；从 LPDDR 内存装 32 位约 640 pJ。
