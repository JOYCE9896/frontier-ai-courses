第二讲：现代多核处理器

从软件工程师的角度看计算机体系结构：缓存怎样工作（缓存行、冷未命中、容量未命中、LRU），用 sin(x) 的泰勒展开做贯穿例子，三个想法：多核（把晶体管拿去复制简单的核）、SIMD（让一个指令流驱动多个 ALU，条件分支怎样造成发散）、硬件多线程（交错执行多个线程来掩盖访存延迟）；吞吐量计算的取舍，执行上下文的存储有限，需要几个线程才能把核用满；Kaby Lake 和 V100 的实例

主讲：Kayvon Fatahalian
资料来源：课堂录像（Stanford Online，2023 年秋季）、课件

一、回顾：抽象和实现

上一讲问了几个看似简单的问题。程序是什么？一串指令，告诉机器做这个做那个。处理器做什么？执行这些指令，效果是修改状态，状态有两种：寄存器和主存。处理器示意图里，取指译码（橙色）负责控制，决定下一步做什么、遇到分支跳到哪里；执行单元（黄色）真正干活；执行上下文（蓝色）是寄存器状态，还有图上没画的内存。

Kayvon 反复强调一个区分：一样东西的含义（语义）和它的实现。程序的含义是"按这个顺序对这些状态做这些操作，最后得到这个答案"；现代处理器的实现可以换个顺序做，你永远看不出来，只觉得程序快了一点，这就是超标量。"超标量"这个怪词拆开看：标量执行是一次做一件事，超标量是说其实做了多一点，但程序看起来仍然一次做一件。内存也一样：含义是一个字节数组，读地址 42 就给你那里的值，写就把值放进去；DRAM 芯片是这个抽象的一种实现，缓存是另一种实现的一部分。

有同学问 DRAM 是什么：Dynamic RAM，动态是指断电数据就没了（和 SSD 这类持久存储相对），而且读一个值会破坏它，读完要写回去。课程最后会花半小时讲 DRAM，现在就把它想成很远的车库，缓存是手边的桌子。

二、缓存的两个细节

第一，虽然内存的语义是"给地址给值"，但几乎所有现代系统的实现都以更大的粒度，即缓存行，在内存和缓存之间搬数据。示意图里缓存能放两行，每行 4 字节，共能复制 8 字节；Intel 芯片上缓存行是 64 字节。要地址 5，缓存向内存要的是从地址 4 开始的那一整行。缓存行和地址的对应是固定的，按缓存行大小取模划分，这是硬件，不想搞动态分配。

处理器说"load 地址 5"时，概念上是问内存要值，实际上先问缓存有没有；有就直接给，没有缓存再去问内存要包含 5 的那一行。

第二，缓存满了要替换。课程假设最简单的 LRU 策略：最久没碰过的那一行，被假设最不可能再被访问，把它赶出去。

顺序读一个 16 字节的数组：0 冷未命中，1、2、3 命中；4 冷未命中；8 冷未命中，缓存满了，赶出最久没用的 0 那一行；C 冷未命中，赶出 4 那一行。这些都叫冷未命中，因为是第一次碰这些数据，缓存无限大也会未命中，未命中的名字是相对于被访问的数据说的。再回头读 0：如果缓存无限大，或者能放 16 字节，这里本该命中，它未命中只是因为缓存容量有限，这叫容量未命中（Kayvon 当场把名字说混了，被同学纠正）。还有一种冲突未命中：缓存本来够大，但它的组织方式规定某块数据只能放在某些位置，这门课不讲。

未命中的原因对处理器来说无所谓，反正都是没有数据要去取、要启动替换策略；知道原因的好处是你也许能改改程序避开它。被赶出的行如果被写过，要先写回内存；只读过的直接扔掉。如果访问 0、1、2、3、5、6、7、8、10 这样跳着读，就降低了访问的空间局部性：装进来的行里有的值从没用过，产生了不需要的内存流量，但底层实现就是这样工作的。

缓存同时解决了两个问题：已经碰过的数据再访问更快（时间局部性，就像正在批改的作业放在桌上，不用每次去车库拿）；按行批量搬运数据效率高，而且常见的程序访问了地址 0 就会接着访问 1、2、3（顺着数组往下走），行起到了预取的作用。另外常见的模式是读一个值、做点逻辑、再更新它，本身就是两次访存。

最重要的是：缓存是实现细节，把缓存拿掉程序结果完全一样，只是可能更慢。缓存存在是为了降低访存延迟，让处理器不用干等。就像家里有桌面、文件柜、走廊壁橱、车库，按常用程度放东西，大多数现代计算机有一层层缓存。粗略的规律是：存储越大，离得越远，访问延迟越高（以后还会讲访问能耗也越高）。L1 在一个 4 周期左右，DRAM 约 250 周期。一个"load、算一下、load、算一下"的程序，大家担心用四个核能不能得到 4 倍加速，而访存搞错了可能差 250 倍，数据移动的影响就有这么大。

有同学问能不能把数据直接从 DRAM 装进 L1 绕过其他层。有些指令可以让读取绕过所有缓存，但 Kayvon 认为那与其说是为了降低延迟，不如说是为了不污染缓存。

三、贯穿例子：sin(x)

今天从软件工程师的角度讲计算机体系结构，讲现代并行处理器怎样获得高吞吐量的三个关键概念：两个关于并行执行（多核、SIMD），一个关于应对访存延迟（多线程）。懂了这些，能理解和优化并行程序的性能，也能对"什么样的工作负载能从快速并行机器上受益"有直觉。 

void sinx(int N, int terms, float* x, float* y)
{
    for (int i = 0; i < N; i++)
    {
        float value = x[i];
        float numer = x[i] * x[i] * x[i];
        int denom = 6;   // 3!
        int sign = -1;
        for (int j = 1; j <= terms; j++)
        {
            value += sign * numer / denom;
            numer *= x[i] * x[i];
            denom *= (2*j+2) * (2*j+3);
            sign *= -1;
        }
        y[i] = value;
    }
}

用泰勒展开 sin(x) = x − x³/3! + x⁵/5! − x⁷/7! + … 对 N 个浮点数的数组逐个求正弦。怎样求的不重要，只需看出：外层循环对每个输入 x[i] 算出一个值存进 y[i]，内层循环只是求 sin 的迭代算法，可以把整个循环体看作输入 x[i]、输出 sin(x[i]) 的函数。

编译后，循环体是一串标量指令：load x[i]，一堆乘法，最后 store 到 y[i]。处理器如果聪明，会发现分子和分母的计算是独立的，有一点指令级并行。但 Kayvon 选的那段区域里指令全是相互依赖的，没有 ILP，双发射的超标量处理器也只用得上一个执行单元。

可这个程序里并行多得是：数组的每个元素都能完全独立地处理。只是处理器只看局部的指令序列，看到的都是相互依赖的指令；要它看一个巨大的窗口，看出"虽然这是个 C 的 for 循环，因为有 i++ 技术上每次迭代都相互依赖，但它们读的都是不同的输入"，这种分析远超硬件在一个时钟周期里能做的。于是硬件架构师说：干脆假设程序员告诉我们并行在哪里，我们就不用费这么大劲找了。

四、想法一：多核

多核之前的处理器，芯片上大部分晶体管用来让单个指令流跑得快：乱序控制逻辑、高级的分支预测器、内存预取器、很大的数据缓存。晶体管越多，缓存越大、乱序逻辑越聪明、分支预测越准。

想法一：与其用增加的晶体管去提高加速单个指令流的处理器逻辑的复杂度（乱序、推测执行等），不如用它们在处理器上加更多的核。把那些花哨的东西拿掉一些，缓存小一点、乱序执行少一点，剩下的基本处理器需要的晶体管少得多，再把它复制很多份。"核"这个词业界没有精确定义，这里指把运行一个指令流所需的一切都复制一遍，包括寄存器。

两个核同时算两个元素：每个简单的核跑单个指令流可能比原来那个花哨的核慢，比如慢 25%（缓存小了未命中多，或者分支预测错了），但现在有两个：2 × 0.75 = 1.5，有加速的潜力。有同学问：这和造一个双发射超标量处理器有什么区别？两者都有两套取指译码和两个执行单元，组织方式不同：多核复制了执行上下文，去掉了找 ILP 的逻辑；如果你给它两个指令流，它保证两个都跑、得到两倍性能。

但我们的程序没有表达任何并行。这段 C 代码编译成一个指令流，在一个核上作为一个线程运行；如果每个简单的核比原来那个复杂的核慢 25%，程序现在反而慢了 25%。有同学说编译器不能看出外层循环是并行的吗？现代的高级编译器在这个例子上大概能，但只要程序稍加变化，编译器就会说"我推理不了了"。

用线程表达并行

typedef struct {
    int N;
    int terms;
    float* x;
    float* y;
} my_args;

void my_thread_func(my_args* args)
{
    sinx(args->N, args->terms, args->x, args->y);  // do work
}

void parallel_sinx(int N, int terms, float* x, float* y)
{
    std::thread my_thread;
    my_args args;
    args.N = N/2;
    args.terms = terms;
    args.x = x;
    args.y = y;
    my_thread = std::thread(my_thread_func, &args);    // launch thread
    sinx(N - args.N, terms, x + args.N, y + args.N);   // do work on main thread
    my_thread.join();                                  // wait for thread to complete
}

新起的线程处理前一半，主线程处理后一半。哪个线程做哪半不重要，重要的是程序员创建了两个线程，从机器的角度就是两个指令流。操作系统（这门课不讲）把它们交给处理器，处理器把一个放在核 0、一个放在核 1 上跑。没有程序员或某个神奇的编译器显式地创建并行，处理器就拿不到两个指令流。

数据并行的写法

void sinx(int N, int terms, float* x, float* y)
{
    // declares that loop iterations are independent
    forall (int i from 0 to N)
    {
        float value = x[i];
        ...
        y[i] = value;
    }
}

用线程写很别扭，Kayvon 都要让大家花时间读代码。更直观的是有一种办法直接说"外层循环的迭代是独立的，你想怎么分给线程都行"。这里用的是 Kayvon 编的 forall 语法，不是合法的 C：有 N 次迭代，用 i 标识当前迭代，我保证所有迭代都可以并行做，结果一样。几乎所有带并行结构的现代语言（包括 PyTorch）都有这样的写法。在这个抽象层次写代码，你很容易想出怎样把它变成线程代码：在两核机器上开两个线程各跑一半。更好的是，用 pthread 写死两个线程的代码，在四核机器上只用得到两个核；而用 forall，运行时在四核机器上可以开四个线程，在 16 核上开 16 个，程序员不需要知道，只需说"相信我，这些迭代是独立的"。

去掉超标量执行、换成小缓存，能在芯片上放很多核。芯片照片上能看出各个核的晶体管在哪里：10 核的 Intel CPU；RTX 4090 上复制的单元大约有 144 个，NVIDIA 叫它们 SM（streaming multiprocessor）；Apple A15 的 6 个 CPU 核甚至不是同一个设计，2 个大核有大缓存和乱序执行，用来跑单线程，4 个小核去掉了更多超标量之类的东西，用来跑并行度更高的工作。

五、想法二：SIMD

forall 写法还有一个好性质：并行的是循环的各次迭代，而所有迭代执行的是完全相同的指令序列（循环体），只是输入数据 x[i] 不同。机器学习、图形、数值计算、数据科学里的代码常常是这样：一个大数组或张量，对每个元素做同样的事。

想法二：把管理一个指令流的成本和复杂度分摊到很多 ALU 上。这就是 SIMD（Single Instruction, Multiple Data，单指令多数据）：同一条指令广播给所有 ALU，在所有 ALU 上并行执行。示意图上取指译码（橙色）完全不变，每周期仍只取一条指令、做一份控制，但 ALU 复制成了 8 个，下一条指令是加法时，不是在一个值上做一次加法，而是在八个不同的值上做八次。可以理解为所有寄存器都变成了 8 宽的向量寄存器。

用 AVX 内建函数写向量程序

#include <immintrin.h>
void sinx(int N, int terms, float* x, float* y)
{
    float three_fact = 6;  // 3!
    for (int i = 0; i < N; i += 8)
    {
        __m256 origx = _mm256_load_ps(&x[i]);
        __m256 value = origx;
        __m256 numer = _mm256_mul_ps(origx, _mm256_mul_ps(origx, origx));
        __m256 denom = _mm256_broadcast_ss(&three_fact);
        int sign = -1;
        for (int j = 1; j <= terms; j++)
        {
            // value += sign * numer / denom
            __m256 tmp = _mm256_div_ps(_mm256_mul_ps(_mm256_set1ps(sign), numer), denom);
            value = _mm256_add_ps(value, tmp);
            numer = _mm256_mul_ps(numer, _mm256_mul_ps(origx, origx));
            denom = _mm256_mul_ps(denom, _mm256_broadcast_ss((2*j+2) * (2*j+3)));
            sign *= -1;
        }
        _mm256_store_ps(&y[i], value);
    }
}

把每个 int 或 float 变量换成 8 个 32 位浮点数组成的 256 位向量类型（这些内建数据类型和函数是给 C 程序员用的），外层循环变成每次前进 8。每次循环做的是同样的逻辑，只是同时做 8 份，代价是代码几乎没法读了。编译出来的指令操作的是 256 位向量寄存器（vloadps、vmulps 之类），一个指令流同时处理八个数组元素。

两个想法可以组合：16 个核，每核 8 宽 SIMD，就是 16 个指令流、128 个 ALU，同时处理 128 个数据，相比原来单核单 ALU 的处理器，理想情况下快 128 倍。如果你知道一个循环是 forall，你可以自己当个小编译器，把它变成 16 个线程，线程里用向量指令，外层循环每次前进 8。作业 1 就要做这件事。价值在于有人告诉你哪些东西是独立的，机械地变换成向量指令或线程并不难。

有同学问：为什么不干脆做八倍多的核？因为向量化把处理一个指令流的大量成本分摊给了八个执行单元，示意图上还是只有一个取指译码单元。Kayvon 说，你会惊讶于造一个算术单元需要的资源相比其余部分是多么少，尤其是不需要高精度浮点的时候，所以只要代码能用上，就可以在芯片上塞满它们。至于数据怎样及时送到这么多 ALU，暂且不管，本讲最后回来谈。

条件执行

forall (int i from 0 to N) {
    float t = x[i];
    // unconditional code
    if (t > 0.0) {
        t = t * t;
        t = t * 50.0;
        t = t + 100.0;
    } else {
        t = t + 30.0;
        t = t / 10.0;
    }
    // resume unconditional code
    y[i] = t;
}

每个元素都能独立处理，但有的迭代要走 if 分支，有的要走 else。可我刚造的处理器每个核有 8 个执行单元，必须同时做同一件事。开始的部分没问题：8 个 ALU 一起用一条向量操作装入 x[i]，一起算 t > 0，得到一个真假组成的布尔向量，比如 T、T、T、F、F、F、F、F。接下来呢？规则是一次只能做 8 件事而且必须是同一条指令，所以先执行 if 分支的指令，同时把不需要它的那些 ALU 的结果屏蔽（丢弃）掉；然后翻转掩码执行 else 分支。分支结束后恢复全速。

结果不是所有 ALU 都在做有用的工作。最坏情况是峰值性能的 1/8。课上讨论：能不能只用一个 if 语句写出平均利用率是 1/8 的代码？

  • 有同学提议把分支改成"两边都算，用 0 和 1 乘以条件来选结果"。这其实是一种很好的把 if 语句降级的编译方法，叫谓词化（predication），但它执行的指令和代价跟原来完全一样。
  • 让每次迭代依赖上一次：这样确实最慢，但整个程序就不并行了。
  • 按 i 的奇偶分：两边各一半，利用率 50%。
  • x[i] 等于 x[0]：要么全真要么全假，另一个分支可以整个跳过，利用率反而是 100%（如果没有任何迭代需要某个分支，硬件可以聪明地跳过它）。
  • 每八个元素有一个走 if：if 时 1/8 在干活，else 时 7/8 在干活，如果两边代价相同，平均仍是 50%。
  • 答案：让每八个里只有一个走 if，并且 if 分支极其昂贵（比如十亿条指令）、else 分支很便宜。这样几乎所有时间都花在只有 1/8 的 ALU 在干活的 if 分支上。

这确实可能是个问题：现代 Intel 和 AMD 硬件的向量宽度是 8，GPU 上可能高达 32，代码写错了就只跑到峰值的 1/32。

术语

  • 指令流一致性（"一致执行"，coherent execution）：同一个指令序列适用于很多数据元素。要高效使用 SIMD 资源，一致执行是必需的；但要在不同核之间高效并行，它不是必需的，因为每个核都能从自己线程的指令流里取不同的指令。读 GPU 编程资料时常听到"一定要一致执行"。
  • 发散执行（divergent）：缺乏指令流一致性，不同元素需要不同的控制路径。发散的代码在 SIMD 架构上跑不好。

现代 CPU 和 GPU 上的 SIMD

  • Intel AVX2：256 位操作，8 个 32 位或 4 个 64 位（8 宽浮点向量）。AVX512：512 位，16 个 32 位。ARM Neon：128 位，4 个 32 位。手机芯片上常见 4 宽，高端 GPU 上约 32 宽。x86 上最早是 SSE 指令，大约 2000 年代初，4 宽，用于 RGBA 这样的简单图形运算。
  • SIMD 指令由编译器生成：程序员用内建函数显式要求；或者用并行语言的语义表达（比如 forall）；或者"自动向量化"的编译器通过循环的依赖分析推断出来。
  • 显式 SIMD：SIMD 并行化在编译时完成，看程序的二进制就能看到 vstoreps、vmulps 这样的 SIMD 指令。
  • 很多现代 GPU 上是隐式 SIMD：编译器生成的二进制里是标量指令，但程序的 N 个实例总是一起在处理器上运行，由硬件（而不是编译器）负责在 SIMD ALU 上同时执行多个程序实例的同一条指令、作用于不同数据。GPU 的 SIMD 宽度大多在 8 到 32 之间，发散执行可能是大问题，写得不好的代码可能只跑到机器峰值能力的 1/32。Kayvon 另录了一段补充视频讲 GPU 和 CPU 实现这个概念的细微差别。

六、三种并行执行形式

三个相互正交的想法，可以混合搭配：

  • 超标量：利用一个指令流内部的 ILP，在一个核内并行处理同一指令流的不同指令。并行由硬件在执行时自动发现，程序完全不用改。
  • SIMD：多个 ALU 受同一条指令控制（在一个核内）。对数据并行的工作负载很高效，把控制成本分摊到很多 ALU 上。向量化由编译器完成（显式 SIMD）或由硬件在运行时完成（隐式 SIMD）。
  • 多核：用多个处理核，提供线程级并行，每个核同时执行一个完全不同的指令流。软件创建线程（比如通过线程 API）把并行暴露给硬件。

示例：单核双发射超标量处理器，每周期最多执行同一指令流里两条独立指令；双核处理器，每个核每周期执行自己指令流的一条指令；SIMD 四核处理器，每个核每周期执行自己指令流的一条 8 宽 SIMD 指令。

真实的例子：四核 Intel i7-7700K（Kaby Lake），每核三个 8 宽 SIMD ALU（AVX2 指令），4 核 × 8 宽 × 3 × 4.2 GHz ≈ 400 GFLOPs（图上只画了 AVX 数学单元和对应的取指译码，另外还有整数运算能力）。Kayvon 在课上把 myth 机器画成：四核，每核三路超标量，每条指令可以是 8 宽向量指令，所以一个核每周期峰值 24 个操作，整个芯片 96 个。NVIDIA V100：80 个 "SM" 核，每个 SM 128 个 SIMD ALU（实际组织成 32 宽的 SIMD 指令），1.6 GHz，约 16 TFLOPs，约 250 W。都是同样的想法，只是规模不同。

有同学问向量指令到底是什么：就像一条 add 指令把一个标量寄存器加到另一个，42 加 10 得 52；一条 SIMD 向量指令是"把这个 8 宽向量和那个 8 宽向量逐元素相加"，一条指令做八个标量操作。就像在 NumPy 或 PyTorch 里对两个 8 元素张量用加号，那就是一条机器指令。

七、想法三：硬件多线程

现在回到访存。缓存能降低访存延迟。另外，很多现代 CPU 有预取逻辑，像找独立指令一样分析程序的访存模式，猜测将来会访问哪些数据并提前装进缓存，这样访问时就命中了，减少了停顿。预取猜错了也可能降低性能：消耗带宽，污染缓存。顺序扫描数组这样可预测的模式，前面例子里最后那次读 0 可能就被预取到了。

但如果数据最近没读过、不在缓存里，下一个要读的数据又不容易预测呢？比如遍历链表，或者刚算出一个值，再用它去查数组（int x = some_function(); int y = A[x];），"给一个下标数组，去查每个下标处的数据"是很常见的操作。而且为了腾地方放这么多核，可能已经去掉了预取逻辑、缩小了缓存，更容易未命中；同时又塞满了 ALU，要更多、更快的访存才能让它们都忙起来。我们给自己制造了一个问题：处理器能力惊人，却在等内存。

Kayvon 说他有个博士生刚毕业，今晚请他和女朋友来家里吃火锅，要做很多准备。洗衣服时，有谁把衣服放进洗衣机就坐在那等？烧水时，有谁站在那等水开再下菜？你们会去做别的事，比如写 CS149 的作业。要点是：如果你知道某件事要过一阵才能完成，就去做别的，前提是你有别的事可做。

想法三：在同一个核上交错处理多个线程，来掩盖停顿。当前线程没法前进，就去做另一个。

取指译码和 ALU 完全不变，把执行上下文（寄存器以及相关的地址空间）复制几份。执行上下文代表一个指令流的状态，也就是一个线程的状态。这样一个核能同时保存四个指令流（四个线程）的状态。比如线程 1 处理元素 0 到 7，线程 2 处理 8 到 15，线程 3 处理 16 到 23，线程 4 处理 24 到 31。核跑线程 1，执行一些 SIMD 指令，遇到一次 load 缓存未命中，要等很久（比如 250 个周期）才能继续。核不会闲着，硬件立刻开始执行下一个线程的指令，没有任何延迟；它也停顿了就换下一个；等第四个也停顿时，第一个的数据早就回来了，它又可以继续跑，直到完成。

这个核的利用率是 100%。但完成任何一个线程的时间变长了：线程 1 的数据回来后本可以立刻继续，却要等别的线程停顿才轮到它。

吞吐量计算的取舍

面向吞吐量的系统的关键想法：可能增加完成任何单个线程工作的时间，以换取运行多个线程时整个系统更高的吞吐量。一个线程在"可运行"但没被执行的那段时间里，核在执行别的线程的指令。

天下没有免费的午餐：执行上下文要存在片上，这是有限的资源。同样大小的上下文存储（也可以当 L1 缓存用），可以切成 16 个小上下文（16 个硬件线程，每个线程能放的工作集小，掩盖延迟的能力强），也可以切成 4 个大上下文（4 个硬件线程，每个线程能放的工作集大，掩盖延迟的能力弱）。

练习：要几个线程才能把核用满

一个简单的双线程核：单核，每周期能从某个硬件线程执行一条标量指令。程序里每个线程做三条算术指令，然后一次 load，延迟 12 个周期。

  • 一个线程：每 15 个周期只有 3 个周期在干活，利用率 3/15 = 20%。
  • 两个线程：6/15 = 40%。
  • 五个线程才能达到 100%：一个线程等 12 个周期，正好够另外四个线程各做 3 条指令。
  • 再多线程没有好处，已经是 100%。
  • 如果每个线程做六条算术指令再 load（延迟仍是 12），只需要三个线程就能用满。

两个要点：

  1. 有多个硬件线程的处理器，能在一个线程必须等待长延迟操作完成时执行别的线程的指令，从而避免停顿。注意多线程并没有改变访存的延迟，只是延迟不再造成处理器利用率降低。
  2. 多线程处理器靠执行其他线程的算术来掩盖访存延迟。每次访存配的算术越多的程序，需要越少的线程来掩盖访存停顿。

硬件支持的多线程

  • 核管理多个线程的执行上下文。核的 ALU 资源数量不变，多线程只是在面对访存这样的长延迟操作时更高效地用它们。处理器每个周期决定跑哪个线程。
  • 交错多线程（也叫时间多线程）：前面讲的那种，每个周期核选一个线程，在核的 ALU 上运行它的一条指令。
  • 同时多线程（SMT）：每个周期核从多个线程中选指令在 ALU 上运行。例子是 Intel 的超线程（每核 2 个线程）。

Kayvon 虚构的多核芯片：16 个核，每核 8 个 SIMD ALU（共 128 个），每核 4 个线程。16 个同时执行的指令流，64 个并发指令流，要让芯片以最大的延迟掩盖能力运行，需要 512 份独立的工作。

Intel Skylake/Kaby Lake 的核：双路多线程（2 个线程），每核每周期最多运行四条独立的标量指令和最多三条 8 宽向量指令（最多两条向量乘或三条向量加），图上没画 load/store 单元。

GPU：极端面向吞吐量的处理器

一个 NVIDIA V100 的 SM（streaming multi-processor）单元：

  • 每个子核 64 KB 寄存器，每个 SM 共 256 KB 寄存器，最多分给 64 个 "warp"。warp 就是 GPU 的执行上下文，每个 SM 有 64 个 warp 执行上下文。
  • 宽 SIMD：16 宽的 SIMD ALU，分两个周期执行一条 32 宽的 SIMD 指令。每个 SM 并发处理最多 64 × 32 = 2048 个数据项。
  • 另有 fp64 单元、整数单元、load/store 单元、Tensor Core，以及 128 KB 的"共享"内存加 L1 缓存。
  • V100 有 80 个 SM：要最大限度地掩盖延迟，需要同时处理 163840 份数据。6 MB L2 缓存，16 GB HBM 显存，900 GB/s（4096 位接口）。

八、到目前为止

要高效利用现代并行处理器，应用必须：

  1. 有足够的并行工作，用上所有可用的执行单元（跨很多核，每核又有很多执行单元）；
  2. 成组的并行工作项需要相同的指令序列（才能用上 SIMD 执行）；
  3. 暴露比处理器 ALU 更多的并行工作，才能交错执行来掩盖访存停顿。

思考题：两个向量 A、B 逐元素相乘，向量有几百万个元素，每个元素 load A[i]、load B[i]、算 A[i] × B[i]、store 进 C[i]。这是在现代面向吞吐量的并行处理器上跑的好应用吗？要回答这个问题，先得理解延迟和带宽的区别，下一讲从那里开始。

课件建议大家掌握这些术语：指令流、多核处理器、SIMD 执行、一致的控制流、硬件多线程（交错多线程、同时多线程）。

附：把所有想法放在一起

课件的附加页把各种组合逐一画出来，Kayvon 说看懂这串图就懂了这一讲：

  • 简单处理器：单核单线程，每周期一条标量指令。
  • 超标量核：单线程，双路超标量，每周期最多两条来自同一指令流的独立标量指令。
  • SIMD 能力：单线程，每周期一条 8 宽 SIMD 向量指令。
  • 异构超标量（标量 + SIMD）：每周期最多两条独立指令，一条标量、一条向量。
  • 多线程核：两个执行上下文，每周期从其中一个硬件线程运行一条标量指令。线程可以运行完全不同的指令流、处在各自流的不同位置，硬件线程的执行在时间上交错。
  • 多线程超标量核：可以每周期从一个线程取一标量一向量两条指令，也可以设计成从不同线程各取一条，这是指令选择的实现细节；四线程时，硬件线程的执行可能交错，也可能同时（不同线程的指令同时运行）。
  • 多核，每核多线程、超标量：双核，每核 4 个线程，每核每周期最多两条独立指令（一标量一向量），核之间共享数据缓存。
  • GPU 的 SIMT（单指令多线程）：很多现代 GPU 执行的硬件线程只包含标量指令，GPU 核检测到不同硬件线程在执行同一条指令时，用 SIMD ALU 同时执行最多 SIMD 宽度个线程。如果线程 6 执行的指令和其他线程不同，ALU 6 就被屏蔽，这就是发散执行。

最后一个思考：你写的 C 程序创建两个线程，跑在一个双核、每核两个执行上下文、每周期最多两条指令（其中一条是 8 宽 SIMD）的处理器上。谁负责把应用的线程映射到处理器的线程执行上下文？操作系统。如果你来实现操作系统，怎样把两个线程分给四个执行上下文？如果程序创建了五个线程呢？
