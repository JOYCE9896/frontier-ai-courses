一、开场：概念单独看不难，难在组合

作业 1 进行中，办公时间里有很多概念性问题。Kayvon 的建议：到目前为止讲了四个概念，多核、SIMD、多线程，还有一点超标量。第一步是把每个概念单独理解透，书面作业就是"拿课件上的概念直接应用"，应该都能答。编程作业跑在真实硬件上，真实硬件是四个概念同时组合在一起的，有点乱。如果按课上的第一性原理推出应该看到 A，实际看到的是 B，不用怀疑自己对基本原理的理解，多半是两个你都懂的效应混在一起互相作用了，多想一想就能解释。

他讲了一个很早以前的期末项目：一个学生说，这门课大家学得很辛苦，但教的东西其实人人每天都在做，忙了就去做别的，十件事三个人就分着做。于是他在街上拿期中考试题问路人，只是把题目换成生活中的说法，看普通人能考多少分，结果分数还不错。这些东西难在组合，按第一性原理其实很简单。

二、再复习 ISPC：先问含义，再问实现

上一讲第一次要求大家把"并行程序应该算出什么"和"它在计算机上怎么运行"分开想。这个习惯对写程序和设计任何系统都很有帮助。

调用普通 C 函数，控制流跳到函数开头，顺序执行指令，再回到调用者。调用 ISPC 函数的意思是：把这段逻辑运行 gang 大小那么多次。gang 大小为 8，就运行 8 遍，每遍只有一个细节不同：programIndex 的值，也就是"这是 8 份中的第几份"。每一份本身都是顺序程序，因为逻辑依赖 programIndex，每份做的事略有不同。调用处创建 8 份，返回处 8 份都已完成。到这里没说任何并行或实现，但说的都是对的。

  • gang 大小怎么定？编译时通过参数指定，可以是 4、8、16。设成 64 也是有效的程序（只要程序能处理这个倍数），就是创建 64 份、每份做自己那块。
  • gang 里所有实例同时运行吗？这是在问实现。语义只规定：64 份都要运行，每份 programIndex 不同。把它们一份接一份顺序跑完也能得到正确答案（手册第 42 页左右有些小细节其实不允许 ISPC 顺序执行，先不管）。也就是说，在调用外面套一个 for 循环，依次设 programIndex 再调用，是完全有效的实现。ISPC 不会这么做，否则就没人用它了。

实际的实现：ISPC 编译器在底层做的，就是作业 1 第二部分你手工做的程序变换，把一段顺序 C 代码改写成向量指令，让向量的每个通道同时做循环的一部分。把 gang 大小设成机器的 SIMD 宽度，是因为既然要跑 8 份，不如让 8 份同时在向量的不同通道里跑。编译结果就是一串（比如 70 条）向量指令，为所有 8 个实例一起执行这段逻辑。它们在一个线程里同时运行，这个线程发出向量指令。追踪执行过程会看到：一个线程跑标量指令，普通的函数调用，同一个线程开始跑向量指令，从 ispc_sinx 返回后继续跑标量指令。

用表格看分配

画一张表很有帮助：行是循环的迭代（i = 0, 8, 16, …），列是程序实例，格子里是该实例在该迭代访问的 idx。交错版本里，同一行（同一时刻）8 个实例访问的是连续的 8 个下标；分块版本里，每个实例沿时间方向一个接一个，而同一时刻的 8 个实例相隔很远。

哪个更高效？有同学选交错版：同一时刻向内存要的连续下标正好落在一个缓存行里。完全正确。分块版里一条向量 load 的每个通道地址相隔很远，programCount 够大时每个通道要一个不同的缓存行，这条 load 可能要 8 个缓存行；如果隔得更远，可能有的已经被换出到磁盘，引起 8 次 TLB 未命中、8 次缺页，代价很高。

gang 大小是 16、向量宽度只有 8 会怎样？ISPC 在这些代码里从不创建线程。编译器会背靠背发两条 8 宽指令。在你的机器上把 gang 大小从 8 改成 16 往往会更快：做 16 宽操作的两条向量指令相互独立，指令流里的 ILP 多了，在流水线上调度得更好。

foreach 是"每个 gang"的概念

Kayvon 承认 foreach 有点怪、有点丑，课上别的东西里都不会再见到。它是针对整个 gang 的：所有实例一起要跑 N 次迭代，每次 i 取不同的值，怎样把迭代映射到 8 个实例上由 ISPC 编译器决定，程序员不想交错还是分块。所以编译器可以把它变换成上一讲的四种实现中的任何一种。实际上它会采用交错的方式，原因就是刚才说的内存利用率好。

看到这样的结构，你不知道哪个 worker 在做哪块工作，也不关心，只是说"系统，把工作分好，让我得到好的并行，我相信你会做出好的决定"。也许我自己手写的分配在未来某个系统上是个坏主意，用 foreach 写，未来的 ISPC 编译器可能做得更好。

让系统来决定有代价吗？有，系统有自己的策略，也许不如熟悉自己程序的你。ISPC 的设计很聪明：给你低层机制精确指定想要的东西，也给你一个高层机制，它到低层有明显的翻译。能用高层就用高层，大多数时候效果不错；不满意时可以往下挖，自己做。Kayvon 说这种"洋葱的层次"在好的编程系统设计、特别是系统编程设计里非常重要。

所以看到一个 foreach，大多数时候根本不再去想程序实例，只想"我有 N 件事要做，ISPC 请用好的 SIMD 实现它"。

三个小程序

  • absolute_repeat：对每个元素取绝对值，在输出里存两次。输入大小 N，输出得是 2N。按"我要处理 N 个元素"去理解就行，ISPC 按什么顺序做都可以。
  • shift_negative：不是第一个元素、值为负时往前挪一格。大家摇头，这不是有效的程序。顺序执行时答案很明确：往 i-1 写了，下一次迭代可能覆盖也可能不覆盖。可你已经告诉系统这些迭代相互独立、可以按任意顺序在实例上执行，输出就依赖于 ISPC 的执行顺序，是未定义的。ISPC 编译器出了新版本，你的程序可能得到不同的答案，而它完全有权这样做，因为 foreach 的约定就是这样。编译器能抓到这种错误吗？现在的 ISPC 不做任何尝试，而且一般也抓不到：把 x[i] 换成 x[a[i]]，a 是任意的数据相关数组，就没法分析了。这就是一种竞争条件。
  • 求和：第一个错误版本里 sum 是每实例一份的变量，8 个实例都返回 sum 没有意义，调用者只期待一个返回值；ISPC 里只能返回 uniform 值，所以过不了类型检查。概念上也有问题：最后 8 份 sum 各是分给该实例的那些迭代的和。把 sum 改成 uniform 就能返回了，但又有了竞争条件：一个 sum，很多实例同时往里 +=。正确写法是每个实例累加私有的 partial，最后用 ISPC 提供的跨实例库函数 reduce_add 安全地加到一个 uniform 值里返回。

有同学问 ISPC 能不能自定义归约用的 lambda：目前不能，概念上很容易做。现在的 ISPC 编译器把正确的求和程序编译成：i 从 0 到 N 步长 8，向量 load、向量 add；循环结束时得到一个向量，每个通道是一部分元素的部分和；最后顺序地把这个向量的 8 个通道加起来。这是 reduce_add 的朴素实现。

要点：先问这门语言的含义是什么、做什么，再谈怎么实现。今天说的一切都只会在一个核、一个核上的一个线程里运行，还没讲怎样创建更多线程。

三、ISPC 任务和线程池

任务（task）把上面的一切复制出去。创建一个任务，就是说"这里有一份工作，我想让一个 gang 的程序实例来做"。可以创建十万个任务。foreach 说"这里有无数次迭代，ISPC 你决定怎样分给程序实例"；任务说"这里有无数个 gang 的工作，你决定怎样分给机器上的线程"。在有 8 个超线程的 myth 机器上创建一百万个任务，ISPC 在底层会创建 8 个线程，然后"你做下一个任务"，如此循环。

ISPC 任务不等于线程，线程是实现细节。创建 8 个任务，底层开 8 个线程分别跑是聪明的做法；创建 10 万个任务还开 10 万个线程就很蠢。为什么？一台机器上同时有约 700 个内核线程，只有 8 个执行上下文，靠操作系统的上下文切换：不时把 8 个线程放到处理器上，定时器到期后把它们换下来，换另外 8 个上去。这可能很慢。

线程创建的演示

Kayvon 现场跑了一个 C 程序，里面有一个什么都不做的函数 dowork（加了不让编译器内联和优化的标注），代表世界上最便宜的任务。三个测试：

  • 测试 0：顺序地调用这个函数 N 次。
  • 测试 1：每个任务创建一个 C++ 线程运行它，再 join 回收。
  • 测试 2：创建 8 个 worker 线程（他机器上写死为 8），每个线程不断取下一个可用的任务，调用 dowork，计数，总数达到 N 就退出。

同学们大多投测试 2。结果：顺序的测试 0 用了 1.6 毫秒，比线程池（测试 2）快 23 倍，因为根本没有工作，调用函数只是压栈出栈那几条指令；线程池比"每个任务一个线程"快 300 倍。这是任务极小、任何开销都暴露出来的极端情况，但"每个任务一个线程、让操作系统去处理"和"只创建机器能用的线程数、自己用高效的取下一个任务来分发"相差 300 倍。ISPC 创建任务时在底层做的就是后者：建一个大小合适的线程池来分。

如果函数很长呢？那线程池肯定比顺序快，所有工作都并行了；至于和"每任务一个线程"比，函数长到一定程度，创建线程的开销就无关紧要了。可以在任务里加循环让它做越来越多的工作，找出分界点。另一端也有分界点：任务小到一定程度，干脆不要并行。

操作系统的上下文切换和这门课讲的硬件多线程不要混淆。这门课几乎不考虑操作系统上下文切换，通常假设我们是机器上唯一的应用，创建比执行上下文更多的线程没有意义，只会迫使操作系统把它们换上换下。你的任务是每个执行上下文创建一个线程，然后自己负责把工作分给这些 worker 线程。操作系统上下文切换要几十万个周期，硬件执行上下文切换一个周期。如果用操作系统上下文切换来掩盖访存延迟，内存几百个周期就回来了，你却要花十万个周期换线程，毫无意义。想法相同，数量级差得很远。

四、写并行程序的四步

接下来第一次真正开始优化程序，目标暂时就是最大化加速比。对一个固定的计算：

加速比（P 个处理器）= 时间（1 个处理器）÷ 时间（P 个处理器）

其他目标还有：高效率（成本、面积、功耗等），或者处理一台机器放不下的更大问题。思考过程：

  1. 找出能并行执行的工作；
  2. 划分工作（以及与之相关的数据）；
  3. 管理数据访问、通信和同步。

课件用 Culler、Singh、Gupta 的框架：待解决的问题 →（分解）→ 子问题，也叫"任务""要做的工作" →（分配）→ 并行线程，即 "worker"（Kayvon 说总得挑个词）→（编排）→ 并行程序，相互通信的线程 →（映射）→ 在并行机器上执行。这些职责可能由程序员承担，也可能由系统（编译器、运行时、硬件）承担，或者两者都有。

分解

把问题拆成能并行执行的任务。一般来说，至少要创建足够多的任务，让机器上所有执行单元都忙起来。分解的主要挑战是找出依赖（或者说，找出没有依赖的地方）。

谁负责分解？大多数情况下是程序员。自动分解顺序程序仍是很难的研究问题，一般情况下非常困难：编译器要分析程序、找出依赖；依赖如果是数据相关的，编译时不知道怎么办？研究者在简单的循环嵌套上取得了一些成功，但针对复杂通用代码的"魔法并行化编译器"还没有实现。这门课里分解几乎总是你的事，别指望魔法；除非用很专门的计算语言。

Amdahl 定律

运行你喜欢的顺序程序，设 S 是顺序执行中本质上必须顺序的那部分所占的比例（依赖阻止了并行执行）。那么并行执行带来的最大加速比 ≤ 1/S。即使其余部分用无穷多个处理器完美并行化，运行时间至少还有 S 那部分。

例子：N×N 的图像分两步处理，第一步把所有像素亮度乘 2（每个像素独立），第二步计算所有像素的平均值。相机经常做这类操作。两步各要约 N² 时间，顺序实现共约 2N²，并行度为 1。

  • 第一次尝试：第一步在 P 个处理器上并行，时间 N²/P；第二步顺序执行，时间 N²。加速比 = 2N² ÷ (N²/P + N²)，N 再大也 ≤ 2。一半程序仍是顺序的，用一百万个处理器也被 2 卡住。
  • 并行化第二步：每个处理器算一部分像素的部分和，最后顺序地把 P 个部分和加起来。第二步时间 N²/P + P。总加速比 = 2N² ÷ (2N²/P + P)，N 远大于 P 时趋近 P。合并部分和是并行算法的额外开销：P 相对 N 很小时效果很好，P 相对 N 不小时仍有问题。

更一般地，设 S 是总工作中本质顺序的比例，P 个处理器上的最大加速比为 1 ÷ (S + (1-S)/P)。课件画了 64 个处理器以内 S = 0.01、0.05、0.1 三条曲线：

  • 只有 1% 是顺序的，另外 99% 能完美并行，在 64 核机器上最多约 40 倍（按公式约 39 倍）。那 1% 已经开始咬人了。
  • 10% 不能并行，在 64 核机器上最好约 8 倍（按公式约 8.8 倍）。

小的顺序区域能限制大并行机器上的加速比。Summit 超级计算机：27,648 块 GPU × 每块 5,376 个 ALU = 148,635,648 个 ALU，能同时做约 1.48 亿个单精度运算。如果 0.1% 的程序是顺序的，最大加速比是多少？1/0.001 = 1000 倍，远远用不上这台机器。在约 1.5 亿个并行单元的机器上，顺序部分得压到极小的比例，否则不如不用。幸好我们跑的大多数代码相当容易并行。

分配

把任务分给 worker。任务是要做的事；worker 可能是线程、程序实例、向量通道等。目标是负载均衡和减少通信开销。可以静态地分（程序运行前），也可以在程序执行时动态地分。程序员通常负责分解，但很多语言和运行时会负责分配。

  • ISPC 交错版 sinx：按循环迭代分解，程序员管理的静态分配，把迭代以交错方式分给程序实例。
  • ISPC foreach 版：按循环迭代分解，foreach 把独立工作暴露给系统，由系统管理迭代到程序实例的分配。这个抽象给动态分配留了空间，但目前的 ISPC 实现是静态的。
  • C++11 线程（第一讲的例子）：程序员管理的静态分配，按分块方式分配，前一半数组给新开的线程，后一半给主线程。
void my_thread_start(int N, int terms, float* x, float* result) {
    sinx(N, terms, x, result);  // do work
}

void parallel_sinx(int N, int terms, float* x, float* result) {
    int half = N / 2;
    // launch thread to do work on first half of array
    std::thread t1(my_thread_start, half, terms, x, result);
    // do work on second half of array in main thread
    sinx(N - half, terms, x + half, result + half);
    t1.join();
}
  • ISPC 任务做动态分配：
void foo(uniform float* input,
         uniform float* output,
         uniform int N)
{
    // create a bunch of tasks
    launch[100] my_ispc_task(input, output, N);
}

ISPC 运行时（对程序员不可见）把任务分给线程池里的 worker 线程：有一个任务列表（task 0 到 task 99）和一个"下一个任务"指针，worker 完成当前任务后查看列表，把下一个未完成的任务分给自己。底层可能就是你在 CS111 里实现过的那种线程池："有空闲线程吗？请做任务 0。你刚做完？下一个可用的是任务 42，去做吧。"大多数时候我们宁可让系统做分配，假设它比我们做得好；而且不同计算机可能需要不同的分配策略，除非特别在乎性能，不想为某台特定计算机写程序。

编排

包括：组织通信；必要时加同步来保持依赖；组织数据在内存中的结构；调度任务。目标是减少通信和同步的开销、保持数据访问的局部性、减少额外开销等。机器的细节会影响很多决定，比如同步很贵，程序员可能就少用。今天见到的例子：reduce_add 等跨实例调用；线程池里 worker 要同步，保证每个任务只给一个 worker、每个 worker 拿到下一个任务。演示里线程池仍比顺序版慢，就是因为线程在取下一个任务时要同步。

映射到硬件

把"线程"（worker）映射到硬件执行单元：

  • 操作系统映射：比如把一个线程映射到 CPU 核上的硬件执行上下文。
  • 编译器映射：把 ISPC 程序实例映射到向量指令通道。
  • 硬件映射：把 CUDA 线程块映射到 GPU 核（以后的课讲）。

有很多有趣的映射决定：把相关的线程（协作的线程）放在同一个核上，最大化局部性和数据共享，减少通信和同步的开销；把不相关的线程放在同一个核上（一个可能受带宽限制，另一个受计算限制），更高效地利用机器。比如你是操作系统，程序在 myth 上创建两个线程，放在同一个核的两个执行上下文，还是两个不同的核？这是策略决定，各有利弊。

五、案例：二维网格求解器

问题：在 (N+2)×(N+2) 的网格上求解偏微分方程。方法是迭代算法：在网格上做 Gauss-Seidel 扫描直到收敛。Kayvon 说这类似流体求解器，网格每个点上有压强之类的量，计算上就是把网格"模糊"：一个点的新值是它和周围四个点的平均（各乘 0.2）。迭代直到收敛：改变一个点的值，会引起它周围的值更新。 

A[i,j] = 0.2 * (A[i,j] + A[i,j-1] + A[i-1,j]
                       + A[i,j+1] + A[i+1,j]);

顺序算法的伪代码： 

const int n;
float* A;  // assume allocated for grid of N+2 x N+2 elements

void solve(float* A) {
    float diff, prev;
    bool done = false;
    while (!done) {                          // outermost loop: iterations
        diff = 0.f;
        for (int i = 1; i < n; i++) {        // iterate over non-border points of grid
            for (int j = 1; j < n; j++) {
                prev = A[i,j];
                A[i,j] = 0.2f * (A[i,j] + A[i,j-1] + A[i-1,j] +
                                 A[i,j+1] + A[i+1,j]);
                diff += fabs(A[i,j] - prev);  // compute amount of change
            }
        }
        if (diff/(n*n) < TOLERANCE)          // quit if converged
            done = true;
    }
}

每次扫描累计所有点的变化量，整个网格的平均变化小于容差就认为收敛，停止。

第一步：找依赖（分解阶段）

在求解器的一次迭代（"while not done" 的一轮）里：每行的元素依赖它左边的元素，每行依赖上一行。A[i,j] 依赖邻居，而邻居刚在 j 循环的上一次迭代里更新过，所以最内层循环的下一次迭代要等上一次完成。

课上同学们出了几个主意：

  • "分成互不接触的块"：先顺序做左上块，能同时做什么？右上块不行，它的值要等信息从左边传过来，可能得到错误答案。
  • "每轮写到一个新的结果数组"：那算的就不是同一个东西了，这次迭代的值依赖同一轮里之前的计算结果。
  • "沿对角线分"：对角线上的工作是独立的，确实有并行。可能的实现：把一条对角线上的格子分成任务，并行更新，完成后移到下一条对角线。坏处：独立的工作很难利用，计算开始和结束时并行度很小；每条对角线完成后都要同步，同步很频繁。Kayvon 还补充：沿对角线走，访问在地址空间里到处跳，就算有点并行也未必划算。他说自己都不想写那段代码，Amdahl 定律会找上门来。

换个算法：红黑着色

思路：把算法换成更适合并行的，以此提高性能。改变格子的更新顺序，新算法迭代到（近似）同一个解，只是收敛的方式不同。算出的浮点值不一样，但解仍收敛到误差阈值以内。是的，要知道这种改动可以接受，需要对 Gauss-Seidel 方法有领域知识，但这是并行编程里常见的手法。Kayvon 说作业 4 写迷你 Transformer 时也会这样：有时看着一个程序觉得不值得硬并行，就用领域知识换一个能算出近似相同答案、对并行更友好的算法。你得去找领域专家，或者自己就是机器学习、图形学的专家。

红黑着色：像棋盘一样把格子染成红黑两色。并行更新所有红格（红格只依赖黑格）；红格全部更新完，再并行更新所有黑格（遵守对红格的依赖）；重复直到收敛。新算法收敛可能要多迭代几轮，多做一点工作，希望能用大规模并行来弥补。

有同学问能不能用专用硬件，比如脉动阵列，来处理原来的算法。可以，但这里的并行度有限，而且你提议为一个两周的作业设计一个一亿美元的加速器，太贵了。

分配：分块还是交错？

把网格分给处理器有两种方式：按连续的行分块，或者按行交错。哪个更好？有关系吗？答案：取决于程序运行在什么系统上。

看程序里的依赖，它是分阶段的：

  1. 并行做红格更新；
  2. 等所有处理器完成更新；
  3. 把更新过的红格传给其他处理器；
  4. 并行做黑格更新；
  5. 等所有处理器完成更新；
  6. 把更新过的黑格传给其他处理器；
  7. 重复。

分块分配要在处理器之间传的数据更少：每一轮只有块边界上那一两行要发给相邻的处理器（比如 P2），块内部的值自己就有，更新黑格需要的信息已经在手里了。交错分配时，算出的每个值将来都要传给邻居。所以就这个程序而言，大概会用分块分配。可上一讲讲 SIMD 硬件上的 ISPC 时，结论是交错更好。要知道自己跑在什么上，才能做判断。

六、两种写法

同一个求解器用两种思路写：数据并行的思路，以及 SPMD / 共享地址空间的思路。

数据并行的写法

不想线程，也不想并行，只想并行的工作，很像 foreach 的思路。这是伪代码，不想 SIMD，只做抽象的思考；为简化只写了红格的更新： 

const int n;
float* A = allocate(n+2, n+2);  // allocate grid

void solve(float* A) {
    bool done = false;
    float diff = 0.f;
    while (!done) {
        for_all (red cells (i,j)) {
            float prev = A[i,j];
            A[i,j] = 0.2f * (A[i-1,j] + A[i,j-1] + A[i,j] +
                             A[i+1,j] + A[i,j+1]);
            reduceAdd(diff, abs(A[i,j] - prev));
        }
        if (diff/(n*n) < TOLERANCE)
            done = true;
    }
}
  • 分解：处理单个格点就是独立的工作。
  • 分配：？？？（交给系统）
  • 编排：由系统处理，内置通信原语 reduceAdd；for_all 块的结尾隐含地等待所有 worker 完成，再回到顺序控制。

逻辑上程序是顺序运行的，只是把普通 for 循环写成"对所有红格独立地做更新"，再用一个辅助函数把这一轮的变化量累加进全局变量 diff。我们完成了分解，把分配交给并行系统，只告诉编译器"相信我，这些迭代可以并行，只要这里小心一点"。Kayvon 更愿意这样写，因为它基本就是顺序代码。

共享地址空间的写法（SPMD 线程）

往下一层，看看用更低层的抽象怎么自己写；也可以把它理解成：如果你是编译器或运行时，怎么实现上面那段代码？总有人要决定谁做什么。现在有一组线程在共享地址空间里运行，都能访问共享变量，需要用锁和屏障之类的结构同步。程序员负责同步。常见的同步原语：

  • 锁（提供互斥）：一次只有一个线程在临界区里。
  • 屏障：等所有线程到达这一点。
int     n;              // grid size
bool    done = false;
float   diff = 0.0;
LOCK    myLock;
BARRIER myBarrier;

// allocate grid
float* A = allocate(n+2, n+2);

void solve(float* A) {
    float myDiff;
    int threadId = getThreadId();
    int myMin = 1 + (threadId * n / NUM_PROCESSORS);
    int myMax = myMin + (n / NUM_PROCESSORS);
    while (!done) {
        float myDiff = 0.f;
        diff = 0.f;
        barrier(myBarrier, NUM_PROCESSORS);
        for (j = myMin to myMax) {
            for (i = red cells in this row) {
                float prev = A[i,j];
                A[i,j] = 0.2f * (A[i-1,j] + A[i,j-1] + A[i,j] +
                                 A[i+1,j] + A[i,j+1]);
                myDiff += abs(A[i,j] - prev);
            }
        }
        lock(myLock);
        diff += myDiff;
        unlock(myLock);
        barrier(myBarrier, NUM_PROCESSORS);
        if (diff/(n*n) < TOLERANCE)  // check convergence, all threads get same answer
            done = true;
        barrier(myBarrier, NUM_PROCESSORS);
    }
}

（课件代码里有个逗号写成了加号的笔误和少了的括号，这里已改正。）n、done、diff、锁和屏障都是全局变量，所有线程可访问。假设 solve() 由所有线程执行（SPMD 风格）。每个 SPMD 实例的 threadId 不同，用它算出自己负责的网格区域：myMin 到 myMax 是连续的一块行，也就是分块分配。和 ISPC 里取 programIndex 一样，任何线程系统都能拿到当前线程 ID，知道"我是谁"，再据此决定自己负责哪部分工作。

七、共享地址空间里的同步

共享地址空间模型

线程 1 做了些工作后写 x = 1；线程 2 循环读 x，直到非零就打印。线程启动时 x = 0。我们期望打印 1。线程通过读写共享地址空间里的位置（共享变量）来通信，图上 store 和 load 就是通信操作。这就是你一直默认的计算机概念：有一个地址空间，地址 x 处有个值，所有线程都能读写它。常用的比喻是公告板，谁都能读、能写，同时读写同一处就可能出问题。

为什么需要互斥

// shared (among all threads) variables:
int x = 0;
Lock my_lock;

// thread 1 and thread 2 both run:
my_lock.lock();
x++;
my_lock.unlock();
print(x);

x++ 一行代码其实是三个操作：把 x 从内存装进寄存器 r1；把 r2 加到 r1；把 r1 存回 x 的地址。设 x 初值 0，r2 = 1，一种可能的交错：

  • T1 读到 0；
  • T2 读到 0（在 T1 写回之前）；
  • T1 把自己的 r1 设为 1；
  • T2 把自己的 r1 设为 1；
  • T1 把 1 存到 x；
  • T2 把 1 存到 x。

丢了一次更新。这三条指令必须是"原子"的。这是竞争条件，因为没有互斥，没有规定一次只能有一个线程写共享值。锁提供互斥：一次只有一个线程能持有锁，也就只有一个线程能写。

保持原子性的机制举例：

  • 在临界区前后加锁/解锁互斥量：mylock.lock(); /* critical section */ mylock.unlock();
  • 硬件支持的原子读改写操作的内建函数：atomicAdd(x, 10);
  • 有的语言对原子代码块有一等支持：atomic { /* critical section */ }

课程后面会讲不用锁也能保证互斥的原语。回到求解器，如果没有那把锁会怎样？总的 diff 可能比应有的小，有些线程会误以为已经收敛而终止。

共享地址空间模型小结

  • 线程通过两种方式通信：读写共享地址空间里的共享变量，线程间的通信隐含在内存的 load/store 里；操作同步原语，比如用锁保证互斥。
  • 这是顺序编程的自然延伸。事实上到目前为止课上所有讨论都默认了共享地址空间。

一个性能问题

Kayvon 本想问"你看出这个实现的性能问题了吗"，结果发现前一晚复制粘贴时已经把改好的版本放上去了。原来的版本没有 myDiff，在最内层循环里每次都加锁去更新全局 diff，同步发生在最内层循环。改进办法：每个 worker 先把变化量累加到本地的部分和 myDiff 里，不用锁，到这一轮结束时再做一次全局归约。这样每个线程每轮只加一次锁，而不是每个 (i,j) 迭代一次。

屏障

barrier(num_threads)：锁是互斥，一次只有一个线程持有；屏障是很粗粒度的同步，把计算分成阶段。调用者在所有线程都到达这一点之前不会越过屏障。屏障之前所有线程的所有计算，都在屏障之后任何线程的任何计算开始之前完成。换句话说，假定屏障之后的所有计算依赖屏障之前的所有计算。屏障是一种保守的表达依赖的方式。

为什么要三个屏障？

直觉上应该只要一个：做完工作，等大家都累加完，检查，继续。但这段代码是对的，有三个屏障。课上留了几分钟讨论：

  • 第二个（加完 diff 之后）最明显：任何线程检查是否收敛之前，必须确保所有线程都完成了更新，看到的 diff 值才正确。
  • 第三个（检查之后）：如果没有它，判定要继续的线程 0 立刻回到循环开头，把全局 diff 清零，开始下一轮；其他线程这时才去检查，看到 0，就以为收敛了，停下。不能让人在别人看之前把值清掉。
  • 第一个（清零之后）：如果没有它，某个线程可能在下一轮里飞快地做完工作，把自己的 myDiff 加进 diff，而另一个线程这时才执行 diff = 0.f，把它清掉；或者在别的线程检查上一轮的值之前就改了 diff。diff 可能偏大也可能偏小，总之是错的。

只用一个屏障

Kayvon 留的挑战：能不能只用一个屏障正确地写出来？提示：前面为了去掉对一个全局 diff 的争用，给每个线程复制了一份本地 myDiff。这里大家争的是什么？是 diff，问题在于不同迭代重复使用同一个 diff 变量。能不能复制点什么来去掉这个依赖？课件给出了答案： 

int     n;              // grid size
bool    done = false;
LOCK    myLock;
BARRIER myBarrier;
float   diff[3];        // global diff, but now 3 copies

float* A = allocate(n+2, n+2);

void solve(float* A) {
    float myDiff;       // thread local variable
    int index = 0;      // thread local variable

    diff[0] = 0.0f;
    barrier(myBarrier, NUM_PROCESSORS);  // one-time only: just for init

    while (!done) {
        myDiff = 0.0f;
        //
        // perform computation (accumulate locally into myDiff)
        //
        lock(myLock);
        diff[index] += myDiff;        // atomically update global diff
        unlock(myLock);
        diff[(index+1) % 3] = 0.0f;
        barrier(myBarrier, NUM_PROCESSORS);
        if (diff[index]/(n*n) < TOLERANCE)
            break;
        index = (index + 1) % 3;
    }
}

思路：相邻的循环迭代使用不同的 diff 变量，以此去掉依赖。用三份轮流：这一轮累加到 diff[index]，同时把下一轮要用的 diff[index+1] 清零；屏障之后大家检查 diff[index]。慢的线程还在读这一轮的 diff[index] 时，快的线程已经在往下一轮的那份里加，互不干扰；而再下一份的清零发生在这一轮的屏障之前，不会碰到别人正在读的值。（初始化时还需要一次性的屏障。）用更多内存占用换取去掉依赖，是常见的并行编程技巧。

八、两种编程模型对比与小结

  • 数据并行编程模型
    • 同步：单个逻辑控制线程，但 forall 循环的迭代可以由系统并行化（forall 循环体结尾有隐含的屏障）。
    • 通信：隐含在 load 和 store 里（和共享地址空间一样）；更复杂的通信模式有专门的内置原语，比如 reduce。
  • 共享地址空间
    • 同步：共享变量需要互斥（比如用锁）；用屏障表达计算阶段之间的依赖。
    • 通信：隐含在对共享变量的 load/store 里。

小结：

  • Amdahl 定律：并行带来的总最大加速比受程序中顺序执行部分的限制。
  • 写并行程序的几个方面：分解出独立的工作，把工作分配给 worker，编排（协调 worker 处理工作），映射到硬件。接下来几讲会大量讨论怎样在每个阶段做出好的决定。
  • 今天的重点：找出依赖。
  • 接下来的重点：找出局部性，减少同步。
