第六讲：内核、Triton 与性能剖析

GPU 编程模型（线程、线程块、网格）和它与硬件的碰撞：warp、占用率、存储体冲突、合并访问、块占用；怎样做基准测试和剖析；用 Triton 写 GELU、softmax、行求和与分块矩阵乘法内核，以及编译出的 PTX 是什么样

主讲：Percy Liang
资料来源：课堂录像（Stanford Online 公开，2026 年春季，本文依据录像字幕整理）

一、回顾硬件

这一讲接着上一讲，深入代码：写 Triton 内核，做基准测试和剖析。NVIDIA 的 GPU 从 A100 到 H100 到 B200，每代的 SM 数大约在 100 到 200 之间，变化不大；每个 SM 有一组寄存器（B200 每个 SM 约 6.5 万个寄存器，共 256 KB），这也没怎么变；每个 SM 有 L1 缓存和共享内存（两者是同一块存储，共享内存可控，L1 不可控）；整块芯片共享 L2 缓存，大一些；最后是高带宽内存 HBM，容量增长很快。带宽大致与大小成反比：寄存器最快，L1 其次，L2 再次，HBM 最慢，不过 8 TB/s 也不算慢。要记住的层级：大内存又远又慢，快内存（寄存器、L1）在 SM 上，局部、快但小。

二、编程模型与硬件的碰撞

编程模型：每个线程对一小部分数据执行一段代码；线程组织成线程块（也叫协作线程阵列 CTA）；线程块组成网格。启动一个内核，就是启动一个由线程块和线程构成的网格并行计算。（H100、B200 还有线程块簇，可以分布式共享内存；B200 还有给张量核心用的张量内存，介于寄存器和共享内存之间，这里不讲。）

为什么要有线程块？逐元素运算（比如 GELU）每个线程处理一个元素就行；但 softmax、矩阵乘法需要线程之间通信，如果愿意付读写 HBM 的代价，也可以让每个线程独立去读写 HBM，但 HBM 很慢。所以要用 SM 本地的共享内存，线程块就是一组会访问同一块共享内存的线程：一个线程块被调度到一个 SM 上，从 HBM 读一批数据，线程之间可能通过共享内存通信、处理，再写回。这是后面分块的关键。Triton 天然以线程块为单位思考，他说习惯之后会觉得轻松很多。

编程模型很优雅，只关心正确性的话，知道这些就够了，写起来像写 Python；但性能对硬件非常敏感，要深入理解硬件。几个例子：

  • warp：线程块里的线程按 32 个一组成为 warp，同一 warp 的线程每个周期必须执行同一条指令。如果有分支，只能先执行 A 分支的线程，再执行 B 分支的，变成串行，这是控制发散，所以要尽量避免分支。SM 上同时驻留多个 warp，warp 调度器可以零成本地在它们之间切换，这是为了隐藏延迟：一个 warp 在从 HBM 读数据（可能要上百个周期）时，立刻切换到另一个可以做张量核心运算的 warp。
  • 占用率：每个线程最多用 255 个寄存器，SM 的寄存器总数固定，每个线程用得越多，能同时运行的线程就越少，占用率降低。但这不一定坏，线程少而每个线程做更多工作也可以很好，比如"线程粗化"：逐元素运算中让每个线程处理 8 个元素而不是 1 个，调度更容易。算一个例子：每块 128 个线程、每个线程 160 个寄存器，B200 每个 SM 最多约 6.5 万个寄存器、最多同时运行 64 个 warp；每块用约 2 万个寄存器，所以一个 SM 最多同时跑 3 个块，即 12 个 warp，占用率约 18%，是寄存器限制了计算。
  • 存储体冲突：共享内存分成 32 个存储体，每个 4 字节宽，每个周期每个存储体最多被一个线程访问（访问同一地址除外）。多个线程访问同一存储体就要排队。最坏情况是矩阵按某种方式排布，32 个线程都去读第一列，就是 32 路冲突。矩阵乘法时一个矩阵按行读、另一个按列读，还有转置，没法总选对顺序，解决办法之一是"swizzling"，重新排布共享内存避开冲突。
  • 内存合并访问：一个 warp 的 32 个线程访问 HBM 时，访问会合并成 32 到 128 字节的事务（缓存行）一次取回。最好的情况是所有线程访问同一个缓存行；如果沿列访问，会取回大量用不上的数据。这和存储体冲突感觉相似，但一个是共享内存的约束，一个是 HBM 的约束。
  • 块占用：线程块被调度到 SM 上，逻辑上可以定义任意多块，物理上只有比如 148 个 SM。启动 160 个块，先跑 148 个，再跑剩下 12 个，这时大部分 SM 闲着。最好让块数能整除 SM 数。学生问一个块能否分摊到多个 SM，他说块必须在一起，解决办法是改变块的大小和数量，避免这条"尾巴"。

小结：HBM 对所有人全局可见，共享内存属于一个线程块，寄存器属于一个线程；warp、存储体冲突、合并访问、占用率这些硬件细节决定了性能，而且很多细节难以知晓，调度器的行为你也控制不了，比编程模型乱得多。

三、基准测试与剖析

他强调的理念是：先测量，找到瓶颈，再写内核。成功的配方是：基准测试和剖析，修改，再基准测试和剖析。基准测试给出端到端时间，不告诉你时间花在哪，但这是你最终关心的，而且是一个数，可以看它随维度怎样变化。几个要点：一定要预热，因为有些东西是延迟编译的，初始开销不该算进去；要多次计时，因为有波动；正确的计时方式是用 CUDA 事件记录开始和结束，并调用同步，因为 GPU 上的一切是异步的；可以取平均，讲究的话看整个分布或 P95。把矩阵放大，矩阵乘法时间按立方增长，但在约 2000 维之前时间基本不变，因为 GPU 是为大矩阵乘法设计的，2×2 的矩阵效率很低。

剖析告诉你时间实际花在哪里，即使不关心时间，也能看清高级语言底下到底发生了什么。PyTorch 有内置剖析器，作业里用更详细的 Nsight Systems。剖析 a + b，会看到一个名字很长的内核，是做张量加法的；剖析 a @ b，看到一个名字很长的矩阵乘法内核，名字里有 CUTLASS（NVIDIA 的 CUDA 线性代数库）、SM100（对应 Blackwell 架构）、F32、以及 64×64×16 这样的分块形状；把矩阵改成 128×128，调用的就变成了另一个分块形状为 32×32×16 的内核。所以看起来只是一个运算，底下根据张量形状会调用不同的内核。

以 GELU 为例（常用 tanh 近似，计算更友好），有三种实现：照公式用 PyTorch 写的朴素版本；内置的 F.gelu；对朴素版本调用 torch.compile。三者结果相同，性能差别很大：朴素版本约 3.75（课上单位），内置快得多，编译版也快得多，但比内置略慢。剖析显示：朴素版本调用了一串内核（乘法、加法、tanh 等），因为 PyTorch 计算图中每个原语都对应一次内核启动，每个内核都要从 HBM 读、算、写回，下一个内核再读，来回读写很多次；内置版本是一个专门写好的 GELU CUDA 内核，因为大家常用 GELU，有人把它写进了标准库；编译版本也只有一个内核，编译器看了计算图，用 Triton 写出了一个融合内核，每个元素只读写 HBM 一次。学生问为什么 Triton 内核更快，他说这里 Triton 版其实略慢于内置，去年测时更接近，和硬件很有关系，这些都没怎么优化，只是说明思路。

四、用 Triton 写内核

CUDA 由 NVIDIA 开发，多年来是写内核的标准，思路是"每个线程做什么"：写一段代码，用 ID 区分线程。好处是贴近底层、控制精细；缺点是线程块里的线程常常要通信，得自己做同步和记账。逐元素运算用 CUDA 没问题，运算复杂了 Triton 的抽象就有价值。Triton 由 OpenAI 开发，现在相当标准，思路是"每个线程块做什么"：把数据载入共享内存、处理、写回全局内存。对这门课和入门来说足够强大，要榨取最新硬件的每个特性可能不够灵活。它介于 PyTorch（把大矩阵相乘作为原子操作）和单个元素之间。

ReLU：最简单的内核

准备一个 8000 维的向量，先在 PyTorch 里分配输出张量，因为 Triton 不再是函数式的，要显式读写。向量太大放不进一个 SM，切成块：块大小 1024，共 8 块。用 kernel[(num_blocks,)](x, y, num_elements, BLOCK_SIZE) 这样的语法启动，方括号里是网格形状。内核里：

  1. 参数 x_ptr、y_ptr 是指针，即内存地址（整数），要习惯这一点。
  2. 块醒来先问"我是谁"：pid = tl.program_id(0)。
  3. 算出起点 start = pid * BLOCK_SIZE，偏移 offsets = start + tl.arange(0, BLOCK_SIZE)。
  4. 元素数不一定被块大小整除，所以有掩码 mask = offsets < num_elements，最后一块超出部分为假。
  5. x = tl.load(x_ptr + offsets, mask=mask)，这是指针运算；之后就可以把 x 当向量做普通计算。
  6. tl.store(y_ptr + offsets, y, mask=mask) 写回。

所有内核基本都是这个形式：输入输出，醒来，算出要看的索引，读，算，写回 HBM。学生问这和 CUDA 有什么区别，他说逐元素时几乎一样，CUDA 甚至更简单；运算超出逐元素后，CUDA 会麻烦得多。张量核心怎样用？由硬件决定，你控制不了。有学生问执行时数据从 HBM 到共享内存到寄存器的具体过程，他说 Triton 代码某种意义上是"谎言"，GPU 并不真的调用 Triton 库执行这段代码，它是给人看的计算规格，编译器会把它编译成 PTX；概念上 load 是根据 HBM 中的地址取数据，得到的局部变量一般放在寄存器或共享内存里，由 Triton 决定。

PTX

Triton 编译生成 PTX，这是 NVIDIA GPU 的一种中间汇编语言。PTX 描述的是一个线程实际做什么（线程块的抽象已经编译掉了）：ld.global 从 HBM 加载到寄存器（%r 是整数寄存器，%f 是浮点寄存器）；mov、mul 等指令；最后 st.global 写回 HBM。代码里有多段重复的块，这就是线程粗化：编译器觉得这个线程太轻，让它处理 8 个元素。同一段代码所有线程都运行，靠 %ctaid.x（块索引）和 %tid.x（线程索引）区分自己。有人会手写 PTX，如果觉得自己比编译器强；NVIDIA 的编译器很成熟，一般不需要，但一些不太成熟的加速器有时要手动干预。PTX 里仍没有指定用哪个 SM、warp 怎样调度，这些由硬件控制。学生说到 tl.load 时这个 warp 会等很多周期，SM 会切换到别的 warp，数据到了再调度回来，他说对。

softmax：一行放得进一个块

softmax 对每行取指数再归一化。朴素实现：每行求最大值（数值稳定）、减去、取指数、求和、相除，在普通 PyTorch 里每一步都是独立的内核，各自读写 HBM，共约 $5MN$ 次读、$3MN$ 次写，原则上应该少得多。Triton 版本让每一行成为一个块：softmax 不是逐元素的，而是逐行的，各块之间不需要交互（块之间也没有共享内存）。块大小取列数向上取到 2 的幂，块数等于行数；内核按行跨度（stride）算出这一行的地址，加载，掩码之外的位置填 $-\infty$（对 softmax 相当于 0），然后和朴素版本一样求最大值、减去、取指数、求和、相除，写回。他说只要数据放得进一个块，Triton 写起来几乎就是普通 PyTorch。学生问按列做 softmax，他说改一下步长就可以。

行求和：一行放不进一个块

如果一行有 4000 列而块大小只有 1024，就把这一行切成多个分块（tile），每个线程依次遍历各个分块，累加到自己的累加器里，最后把所有线程的累加器加起来。为了简单，从 softmax 换成行求和。仍然是每个块负责一行；块在这一行上循环，每次加载一个分块、加到累加器上；遍历完后把累加器求和得到一个标量写出。累加器放在寄存器还是共享内存由 Triton 编译器决定，块很大时只能放在共享内存。他特别区分：GELU 里把一行切成的若干段是不同的块，各自独立处理；这里切出的是分块，属于同一个块，一个块要处理完所有分块，这时就不再像 PyTorch 了，因为数据放不进共享内存。

矩阵乘法

矩阵乘法是深度学习的基本运算，已经被优化到极致。这里做矩阵乘法后接 ReLU，这在线性层加激活中很常见。$A$ 是 $M\times K$，$B$ 是 $K\times N$，$C$ 是 $M\times N$。

  • 朴素做法：固定 $C$ 的一个元素，沿 $K$ 遍历，每次从 HBM 读 $A$ 和 $B$ 的元素、相乘、累加，最后写出。正确，但读取次数是 $MKN$ 量级，运算次数也是 $MKN$，算术强度是常数，很差。而且有大量重复读取：算 $C$ 的相邻元素要重复读同一行 $A$。
  • 理想做法：把 $A$ 和 $B$ 全部载入共享内存再算，读取只有平方级，算术强度是 $O(N)$。但 $A$、$B$ 通常太大，放不进共享内存。
  • 分块：整体上像朴素做法，局部上像理想做法。把 $C$ 切成分块，每个分块由一个线程块负责，不同分块完全独立地计算。一个线程块沿 $A$ 的行分块和 $B$ 的列分块同步扫描，每次把对应的 $A$ 分块和 $B$ 分块载入共享内存，相乘，把部分和累加到共享内存中的累加器里；扫完后把输出分块写回 HBM。算术强度提高到分块大小的量级，达不到 $O(N)$，但分块大时很不错。既然在写这个内核，写出之前顺手做逐元素激活也很容易，这就是内核融合。

步长（stride）：张量在内存中是线性排列的，步长告诉你怎样从多维索引映射到线性索引，地址等于行号乘行步长加列号乘列步长。比如行步长 4、列步长 1，转置就反过来。内核里：醒来，知道自己负责 $C$ 的第 $(m, n)$ 个分块；做一些索引计算，得到要看的 $A$ 的哪些行、$B$ 的哪些列、以及 $1$ 到 $K$；得到 $A$、$B$ 在分块位置的指针；在共享内存中建一个 $M\times N$ 的累加器；循环中加载 $A$ 的小分块和 $B$ 的小分块，执行 tl.dot（数据在共享内存里时，写起来就像 PyTorch），推进到下一个分块；循环结束后可以施加逐元素非线性，最后写出。

五、小结

程序员能控制的是编程模型，PyTorch、Triton 甚至 PTX（可以任意定制），但代码要在硬件上运行，SM 数、存储体、内存和寄存器大小都是有限的，大矩阵和 Transformer 要适应这些约束，所以基准测试和剖析很重要，能看清硬件的"乱"怎样转化为性能。Triton 是思考线程块的好语言，以块思考比以单个线程思考容易，因为不用显式同步线程、管理共享内存：把计算拆成线程块，从共享内存读、处理、写回 HBM。例子由易到难：逐元素最简单，然后是行内归约，行放不下时引入初步的分块，最后矩阵乘法是分块的经典例子。下一讲讲多 GPU 编程。

学生问 Triton 之外还有什么选择，能多接近最优性能。他说每种语言都有自己的归纳偏置，让某些事容易、某些事难；Triton 是训练 Transformer 的人做的，处理 Transformer 相关的东西比较容易；极端情况可以写 PTX，但不建议作为第一步；还有 ThunderKittens、CuTe 等各种领域专用语言，它们不一定在技术栈上更高或更低，只是特性不同。
