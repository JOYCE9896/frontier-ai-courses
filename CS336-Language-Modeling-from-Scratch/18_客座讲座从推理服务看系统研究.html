客座讲座：从推理服务看系统研究（Dan Fu）

一个 token 在推理服务中的一生：工作负载、预填充与解码分离、KV 缓存分层、大规模部署中的罕见 bug；用 mega kernel 加速解码；以及稳定化的循环 Transformer Parcae 和它的缩放规律

主讲：Dan Fu（UCSD，Together AI）
资料来源：课堂录像（Stanford Online 公开，2026 年春季，本文依据录像字幕整理）

一、动机

这门课主要讲怎样训练语言模型，Dan Fu 讲的是另一面：模型有了之后，怎样服务它，怎样把电变成 token、变成智能，以及从这个角度能做哪些有意思的研究。

他说我们正在经历一场新的工业革命。这些幻灯片是两年前求职时做的，例子有点旧了：人类水平的文本和代码生成（Cursor、Claude Code、GPT-5.5），生成和理解图像视频，开始理解新模态，在生物、健康、DNA 模型等科学领域出现应用。他的研究一直关注是什么推动了这些进步、下一代怎样改进。一个显著的驱动力是规模：2018 年他读博刚开始（他开玩笑说那是上古时代），最大的模型约 1 亿参数，大家已经觉得很疯狂；2019 年 GPT-2 被认为太危险不能发布，这门课里你们努力一下就能训练出 GPT-2 水平的模型；现在开源模型有万亿参数以上，前沿大概在 5 到 10 万亿。

转变比想象中快。他用了一个类比：1902 年曼哈顿有 13 万匹干活的马，每匹每天产生几磅粪便，粪便成了大问题，甚至有专门讨论马粪的学术会议，1898 年纽约开过一次，结论是什么也做不了，只能捏着鼻子忍着。10 年后的 1912 年，曼哈顿的汽车数量已经超过了马。他认为对语言模型来说，1912 年那一刻大概是去年：至少从去年起，他大部分代码是用语言模型写的，团队里多数人也是，他让学生都这么做（做作业时除外）。

规模很大程度上由 GPU 驱动，某种意义上 GPU 是新的石油，有几千亿美元乃至更多的投资，整个国家和主权财富基金都把它当作重点。推理是把电变成智能的引擎：石油只有在发动机把它转成动能时才有用，推理引擎和 GPU 内核就是把 GPU 从（Percy 说的）沙子变成可用之物的东西。机器学习模型只是运算组成的有向无环图，是存在于"以太"中的数学对象，推理引擎和 GPU 内核是实际要编程、把它们映射到硬件上的部分。课上你们实现过一些训练侧的东西，比如 FlashAttention，但推理一侧有另一个复杂的世界。他希望大家记住一点：理解推理、推理引擎和底层 GPU 内核，就能实现机器学习算法的全栈创新。

他代表两个机构：UCSD 的小实验室，以及 Together AI（一家 AI 云，提供 GPU、推理、微调等，研究背景很强，Percy 也在其中）。讲座分三部分：一个 token 的一生，然后两个研究项目。

二、一个 token 的一生

这部分幻灯片改编自他的学生 Austin 根据在 Together 的经验做的报告，图全部由 Nano Banana Pro 生成，他说大体正确，细看文字会发现很多错。

请求进来后：先被调度到某些 GPU，预填充和解码可能分在不同机器上；查 KV 缓存，看以前是否见过这个请求或类似请求，能不能省掉一些计算；然后执行核心的机器学习代码，可以把计算分到不同机器、节点间并行、节点内多 GPU 并行，取决于模型大小和切分方式，随着硬件发展选择会越来越多；最后得到 token 输出，比如"Percy 说的线性回归是什么意思？我那天翘课了"，形成完整的端到端体验。

工作负载

生产流量和训练时看到的 token 很不一样，也不像你凭空想象的流量。不同工作负载有不同的输入输出 token 分布：

  • 编程（比如 Cursor，Agent 能访问整个代码库）：输入很长，几万个 token；输出取决于模型怎么训练的，可能有一些思考 token，也可能很短。
  • 长篇摘要：把整本书贴进聊天窗口来回讨论，和普通聊天（"给我讲讲一阶微积分"）形状完全不同。
  • 现在用语言模型的方式是多轮、Agent 式的：编程时你和 Agent 来回沟通（"做这个。不对，我是说那个。"），Agent 自己也会多次调用模型，调用工具，比如在代码库里 grep、上网搜索，再把结果喂回模型。
  • 时间间隔各不相同：快速交互的聊天，或者手机上和 ChatGPT 语音对话，要求快速回应；让 Agent 自己去迭代，节奏就不同；Agent 卡住求助而你没注意到，轮次之间又会有间隔。他自己有一个和 ChatGPT 讨论每周健身计划的对话，大约两周才互动一次，流量模式又完全不同。

这些决定了工作负载的样子：每次来多少新 token，要生成多少，会话多长（来回很多轮的"黏性"用户，还是问一个问题就走、第二天再来），轮次间隔多久。不同应用有不同目标：交互应用可能要求不到一秒拿到首个 token，让 Agent 先说"我在想……"；或者知道要生成 500 个 token，要求整段在一定时间内返回，让用户读得够快。

请求进来后先分词，然后进入相当复杂的调度：这些 token 见过吗？能否从缓存里查到激活？然后是两个主要部分：

  • 预填充：比如 10000 个没见过的 token 进来，计算激活和 logits，10000 个 token 进，1 个 token 出，严重受计算限制，和训练很像，只是不做反向传播。
  • 解码：一次生成一个 token（推测解码好用的话一次三四个），每生成一个都要再跑一遍模型，算下来 FLOP 不多，但严重受内存带宽限制，为了一个 token 要把整个模型加载一遍。

模型前向的最后得到一个代表 token 的数字，转成字符串，再做一些处理：查停止符，可能做安全检查（用户是不是在恶意攻击系统）等，最后输出。推理引擎就在这个"调度、执行、采样"的循环中等待请求。

连续批处理与 KV 缓存

系统同时处理很多请求时用连续批处理。示意图中时间向下流动：一个长请求（分析长文档）在生成很多 token；另一个请求进来，占用一些资源（同时跑多个请求的计算资源，以及填充 KV 缓存的内存资源）；短请求完成后新请求进来；又来一个很长的请求，但 GPU 内存不够（KV 缓存要放在 GPU 上，可能已经满了），只能排队，等长请求完成再开始。多请求共存时复杂性已经显现。

KV 缓存很重要：很多用户都说"Hi ChatGPT"或"Hi Claude"，理论上不必为每个用户重算激活；用户传入一本长书，预填充一次，下一轮对话追加内容时也不必全部重算。KV 缓存用前缀共享，用基数树这类传统数据结构查哪些 token 见过、哪些是新的，再查对应的激活。

并行与预填充解码分离

万亿参数模型跑在 80 GB 的 GPU 上，单卡放不下，要切分：每个张量切到 4 块 GPU（张量并行）；现在最好的模型多是 MoE，可以把专家分到不同 GPU 上。这些选择决定了瓶颈在哪、需要多少 GPU、能同时服务多少会话。

一个大趋势是把预填充和解码放到不同的机器上，因为计算特性完全不同：预填充很像训练，FLOP 密集，能把 GPU 用满；解码受内存带宽限制，计算不多，但要加载所有权重。耗时也不同：一次预填充比一步解码长得多，但每个提示只预填充一次，每生成一个 token 就解码一次，解码步数多得多。所以基本的优化（大家基本都采用了）是预填充一组机器、解码另一组机器，各自专门优化。这种分离带来了很多创新空间：NVIDIA 收购 Groq（一种推理芯片），原因之一就是解码工作负载和预填充差别太大，可以用完全不同的芯片，下一代硬件中 NVIDIA 计划用 GPU 做预填充、用 Groq 的 LPU 做解码；OpenAI 和 Cerebras 有算力合作，Cerebras 的芯片更擅长解码；SambaNova 等公司也在这一空间的不同位置下注。

大规模部署中的罕见 bug

每天服务万亿级 token 时，会遇到很棘手的 bug。他列了一组，大多发生在去年末的一些开源推理引擎中。大规模系统的特点是：小规模运行良好的东西，到了大规模必然出问题，涉及 0.001% 甚至更低概率的事件。

  • NaN：某个内核有极轻微的错误，触发条件很罕见，计算到一半 logits 变成 NaN。之后模型开始重复同一个 token，比如一直输出 "hi hi hi" 或感叹号，陷入循环。
  • 工具调用：有人改了处理工具调用的方式。正常情况下模型说"去做一次网络搜索"，外部框架用普通代码执行搜索后返回；某个引擎里工具调用不再被正确处理，症状是生成长度暴涨：模型反复说"去搜索""去搜索""怎么没有搜索结果"，陷入几万 token 的死循环。
  • 突然输出中文：一个影响了好几家推理提供商的 bug，一开始被归咎于量化，实际更隐蔽：模型会毫无理由地突然输出中文字符。有人猜测这些模型一定是在中文模型上微调过；实际是某个内核里的差一错误，偶尔读入一些未初始化的 GPU 内存，经过注意力，最后冒出一个随机中文字符，模型会想"我怎么开始用中文想了，用户一定是在用中文问我"，然后就转向中文。有时模型确实被训练成用中文思考，有时只是某人代码里的差一错误。

KV 缓存分层

生产系统希望 KV 缓存尽可能大，能缓存很多用户、同一用户很多会话的请求，同时运行尽可能多的会话。先放 GPU 上，很快 GPU 内存就不够，于是放到 CPU 的 DRAM。他说如果关注黄仁勋的主题演讲，会发现他最近很在意 CPU 性能，原因之一是上一代 CPU 其实很慢，拖累了一批很重要的工作负载：你的 5 亿美元机器被上面那几千美元的 CPU 卡住，处境就很糟，其中一个原因就是 KV 缓存放在 CPU 内存里，读回的速度很关键。再往下可以放到磁盘，于是开始关心 SSD 空间，你可能听说过 OpenAI 买光了世界上的 SSD 和 DRAM，部分原因就是这个。构建引擎时有一套复杂的流程：一段时间没见的 token 就驱逐，送到 CPU、磁盘或全局存储；新请求来了，要去取回、加载。

学生问是否某类特定工作负载才卸载。他说这就到了经典的调度问题，建议大家去上操作系统课：除了右边的 GPU，这张图和七八十年代的操作系统图一模一样，那时开太多程序，CPU 内存不够，就把程序放到磁盘上，是完全相同的工作负载。图左边 Nano Banana 恰好"幻觉"出了 LRU（最近最少使用）驱逐，这其实是不错的启发式，大概有篇操作系统论文证明 LRU 在最优的 2 倍以内。最好当然是能预测未来，知道某类请求要来，提前预取；也许真能预测，比如你在聊天应用里打开一个月前的旧对话，很可能要接着问，可以提前加载到 GPU。预测不了就用启发式。他说没见过谁想让 GPU 上的流量少一点，在满足服务等级要求的前提下，希望服务尽可能多的流量。

新硬件带来的问题

上一代 Blackwell 中 NVIDIA 推出了 GB200 NVL72，72 块 GPU 用很快的互联连在一起。于是有新问题：怎样把万亿参数模型分到 72 块 GPU 上？这有意义吗？能带来什么？怎样考虑容错？它们会因各种原因出故障，比如连接器是塑料的不是金属的，插得太用力，线缆会把东西掰弯一点，NVLink 就变得很不稳定。（他指出 AI 生成的图在芯片里画了个风扇，说不太合理。）模型分到 64 块 GPU 上，为数百万用户服务万亿 token，一块 GPU 挂了怎么办？能否做到容错？还有上下文已达百万甚至更长，要不要把上下文分到多块 GPU 上？

一个系统层面优化的例子是 Together 几个月前发布的"缓存感知的预填充解码分离"，在路由层只改两行代码，效果却不小。大多数请求是对话中途的轮次；假设平均对话 10 轮，那 10% 的请求是全新的，有几千个新 token，计算更贵。你不希望有人贴了一本书说"聊聊这本书"，和对话中途的短问答（"为什么 1+1=2？""因为数字……""我没懂"）在同一批 GPU 上同时跑。于是做一个简单的路由器：缓存命中率很低的新请求发到一组 GPU，其他"热"请求发到另一组预填充节点。结果服务速度最多快 40%。他说这类研究还非常早期，10 到 20 年后回头看，大家会想"这不是很显然吗？"，但这正是因为我们第一次以新的方式在生产中看到这些流量。

三、Mega kernel：让解码接近硬件极限

第一个研究项目来自服务中的观察，是 Stanford 和 Together 的合作，主题是用 mega kernel 让解码快得多。

解码的根本挑战是要跑完整个模型才能生成一个 token，把一个大规模并行的系统变成了一个"高级内存加载器"。更麻烦的是，我们通常一次为一个运算写一个内核：内核很难写（你们写 FlashAttention 时应该深有体会），所以通常给模型里的每种运算各写一个内核，归一化、矩阵乘法、注意力各一个，好写，但给系统带来了大量空闲。他展示了一张示意图（取自一个注意力推理内核）：横轴是时间，纵轴是 GPU 上的流式多处理器（H100 有 132 个，B200 大约 148 个），条形是有效工作，空白是在等别的操作完成。不管内核写得多好，总有空闲：内核启动和销毁的间隙；尾部效应，和短提示与长提示一起处理同理，一直到注意力运算本身，一批输入中有短有长，就要等最长的完成；跨多个内核时，内核之间的间隙会累加。

mega kernel 的思路是不再每个运算一个内核，而是用一个内核覆盖多个运算，类似 FlashAttention 中的融合，但更激进、覆盖更多运算。它把 GPU 从"一次执行一个运算的设备"变成一个大规模分布式系统：有一堆工作要做，有些依赖于别的工作，怎样调度分配才能最大化利用率？只对注意力推理内核这样做，就快了 30% 到 70%；还可以对整个模型做，比如把 Llama 1B 的一整层放进一个内核，各种条形以奇怪的方式重叠：比如在注意力进行时就加载下一层的权重，在注意力结束前就开始部分归约。两个具体例子：

  • 注意力层先做 QKV 投影加 RoPE，然后是注意力。可以在 QKV 完成前就开始加载 KV 缓存，尤其在解码时；QKV 完成后有了新的查询，再做剩下的注意力。
  • 注意力之后是输出投影（O projection），可以在注意力结束前就开始加载它的权重。

有了这种细粒度控制，就能在一些运算结束前开始另一些。实现上是一个相当复杂的 CUDA 框架，基于指令的抽象：每个子内核在自己的文件里实现，用一个大的虚拟化共享内存系统协调运行。为此他们做了 ThunderKittens，一个写内核的库，可以看作像 Triton，但更底层，控制更细。结果是接近"光速"的解码：mega kernel 比其他一些最先进的引擎快得多（现在的数字更好），在 H100 上达到 72% 的带宽利用率，也就是说，抛开所有复杂性，只问 GPU 物理上做这个操作能多快，已经达到了那个"光速"的 72%。要点：对内核有深入控制、理解硬件，能催生很不一样的计算范式，这些只有深入推理才能看到。

四、Parcae：稳定的循环 Transformer

第二个项目进入新架构领域，是他 UCSD 实验室的工作，由 Hayden 领导，与 Zachary 和 Taylor 合作。开头说新能力来自参数和数据的扩展，Parcae 想问：这是唯一的扩展方式吗？它是对"循环 Transformer"的探索：让 Transformer 的某几个块循环运行，token 不是一层一层地只过一遍，而是在某处被送回去再过几遍。两部分内容：用状态空间模型（SSM）的理论稳定这个过程，朴素训练会发散；一些有意思的缩放规律，显示随数据增加应该增加循环次数，要充分利用参数，就要一定程度地复用它们。

为什么循环有意思：激活经过模型的一部分后进入循环块，同一个激活在同一块里跑若干次，最后输出。好处是参数不变，但多了一个增加 FLOP 的旋钮，如果相信更多 FLOP 带来更高质量，这就是不增加参数成本就能提升质量的办法；几年前的工作还表明循环模型表达能力更强，有些东西同样参数量的普通模型表达不了。他们的驱动问题是：每个参数（或每个参数加每份数据）能得到的最好质量、最好智能是多少？Tom Goldstein 在马里兰的组有初步结果显示它可能比 Transformer 好，比如在 ARC 任务上。他还提到 Parcae 发布前大约一周，据他说是一位 OpenAI 的人在推特上声称 Claude Mythos 是循环语言模型，引发了大量猜测，最后那人写博客承认是自己编的；他说他们在那之前就在做这项工作了，但这说明这个方向确实引人关注。

问题是这些循环模型很不稳定：训练算法稍有改动，比如学习率改一点，就会发散。做一次学习率扫描，十次里九次不收敛，出现 NaN 和大的损失尖峰。以前的应对是一些 hack：每层加归一化，或者只用 $2\times10^{-4}$ 这个学习率、别的都不用。他说训练放大时如果看到大的损失尖峰，说明训练过程出了大问题，应该深入看看发生了什么。

他们用类似状态空间模型的数学来处理稳定性。直接分析循环块很复杂：参数众多，有各种非线性、softmax、RoPE。他们的切入点是只看残差，激活在块与块之间怎样变化。第一个经验观察是变化不大，每个残差块只轻微改变向量。于是在残差上写下一个动态系统：把注意力、激活函数、大的前馈网络这些非线性部分装进一个盒子，叫 $R$，放到一边；剩下矩阵 $B$（对进入循环前的初始向量的变换，每次注入）和矩阵 $A$（每次循环对残差的变换）：

$$h_{t+1} = A\,h_t + B\,e + R(h_t, e)$$

去掉复杂性后，可以用这个简单形式看待以前所有的循环 Transformer：有的把 $A$ 当作恒等（直接相加），有的让它完全可学习。他们经验上观察到 $A$ 和 $B$ 主导了这个式子的量级，那么去掉复杂的非线性部分会怎样？得到一个用高中微积分就能解的简单系统，有闭式解，给定初始激活和注入，可以算出第 $t+1$ 步的激活，它由 $A$ 的高次幂主导。关键量是 $A$ 的谱半径（可以看作某种范数）：把矩阵自乘很多次，如果它像标量 2，循环 16 次就把激活放大到 $2^{16}$，这就解释了那些大的损失尖峰。以前论文对 $A$、$B$ 的选择要么是"临界稳定"，要么是不稳定。

Parcae 的做法：约束 $A$ 和 $B$，让数学上不会发散。$A$ 实际上被参数化为负对角矩阵，自乘多次后趋于 0，不会爆炸；$B$ 只作用一次，不太会爆炸，加一个简单的归一化即可。这样谱半径小于 1，成为稳定系统。训练时损失曲线稳定了，即使用对其他模型很糟的 $6\times10^{-4}$ 学习率，也能得到稳定的模型；状态（激活）的范数也自然受到约束。对比：完全不加约束的基线发散到 $10^{19}$；每层加归一化的模型，激活范数看起来很好，但模型其实想把激活扩大（空间更大，可以把不同概念放得更开），归一化又把它压回 1，两股力量互相较劲，表现为损失尖峰。这个简单的重参数化稳定了训练，也得到更高质量的模型：与之前的循环模型（recurrent depth 模型）比，Parcae 在多种任务上更好，也胜过一个很强的 Transformer 基线（nanochat 那种大家都在努力加速学习的模型）；把同样的 Transformer 架构拿来循环并加以稳定，困惑度和端到端质量都更好。

循环的缩放规律

这很巧，但真的应该更激进地循环吗？他回顾了缩放规律：几年前大家问应该加大模型还是加数据，得到很多漂亮的幂律曲线。看曲线的走向：向右下，说明数据和参数应该同时扩大；竖直向下，说明只加数据；水平向右，说明只加参数。实际是向右下，所以要同时扩大，于是有了在 35 万亿 token 上训练的万亿参数模型。

循环在其中处于什么位置？可能是永远不该循环，可能是大量循环，也可能只循环一些。他们的初步缩放规律中，每条曲线都是等参数、等 FLOP 的：左右两图参数量相同，颜色变化表示通过增加数据增加训练 FLOP，同时改变循环次数。两个模型都出现了向右下的趋势：固定参数量时，随着数据增加，也应该增加循环次数。循环次数遵循相当经典的幂律，可以用缩放规律在循环次数和 token 数联合扩展时预测质量。学生问能否和参数一起联合扩展，他说他们有一张很复杂的三维图，也指向"右下"，如果相信那张图，三者应该一起扩展，只是图太难看懂。有意思的是，据他所知，现在所有模型都没有循环，都在这些曲线的最左边，而且都用了大量数据，这暗示也许有稍好一点的训练方式。另一个角度的实验：固定模型大小，橙色是普通固定深度的 Transformer，蓝色是循环模型，两者训练 FLOP 相同，但数据量不同；通过增加循环次数（而不只是数据）达到同样 FLOP，验证损失更低。这再次暗示，也许所有大规模预训练都该做循环。

五、总结与问答

理解模型的推理、GPU 内核和其中的各个部分，就能实现机器学习算法的全栈创新：可以是让你服务更多流量的新路由算法，可以是让系统某部分快得多的新内核，也可以是新架构，比如参数少得多，能放进更少的 GPU、减少通信。他希望至少启发在座的一位深入研究这些。

  • Parcae 是从头训练的吗？能用于预训练模型吗？是从头训练的。几个月前有一篇很"整活"的博客，作者没训练任何东西就在某个排行榜上胜出：他把 Qwen 模型里的两三层循环运行，在一些数学题上质量提升了。他们有一些相关工作可能很快发布：对预训练模型做一点循环也许就能提升质量。他说这很怪，让他不安，不知道为什么会这样，希望能说服 Hayden 去盯着激活和权重研究循环为什么会变好。
  • 循环模型对推理的意义？他个人对循环很兴奋的原因之一是，高效服务推理的一大瓶颈是 GPU 内存。参数少，就能放更多 KV 缓存，或者模型切到更少的 GPU 上，减少通信，小模型带来很多灵活性。他还有个梦想：如果循环块足够小，可以写一个很快的小 mega kernel 来跑循环，目前还没做到那么小。下一代和 NVIDIA 产品结合的 Groq LPU 内存大约只有 250 MB，能放进去的东西非常小；如果能设计出放得进去的模型，权重可以一直留在片上，只让激活尽快流过。跨过某些门槛可能带来非线性的收益。
  • mega kernel 的代价？代价是人的血汗泪。它们极其费人力：给你一点概念，一位全职的天才内核工程师一年大概能为一种硬件、两三个模型、批大小 1 到 16 写出 mega kernel；批大小变成 17，就得重来。Together 在做能自动化部分过程的编译器，但很难。mega kernel 这个想法在 GPU 编程中几十年来起起落落。做得出来就会快到不能再快，但需要大量精力。
  • （Percy 问）如果知道模型将部署在 Groq、Cerebras 这类推理硬件上，架构该怎么改？首先受内存约束：要部署在某种 Cerebras 芯片上，就去看晶圆上有多少内存，按留出足够 KV 缓存的余量来定模型大小。仔细看最近的中国模型，会发现一些有意思的选择，暗示他们可能在考虑即将推出的华为芯片。还有量化格式：打算在 NVIDIA GPU 上服务的模型，比如 NVIDIA 发布的 Nemotron，会用 NVFP4 训练，这是 NVIDIA 芯片专有的 FP4 格式；不在 NVIDIA 芯片上跑（比如 AMD），就用另一种格式 MXFP4，各有利弊。这些细微选择都取决于硬件。
  • 如果只关心计算最优训练，循环是否比加参数更优，还是只是降推理成本的技巧？计算最优总是"给定 FLOP 预算选什么"，某种意义上有点刻意：想要更高质量就加 FLOP 预算；定了模型大小就训练更久；受限于模型大小就循环更多；数据用完了，就选你认为能训练得最充分的模型大小。这些选择还要考虑会不会被采用、怎样服务、开源的话大家在笔记本上能跑多大的模型。模型更大、数据更多总会更好，取决于这些设计点。
  • （Percy 问）不同用途（Agent 编程与批量数据处理）的最优架构差别最大在哪？Agent 式循环工作流中，很重要的是让 KV 缓存尽量保持"热"；批量处理每个文档只看一次，比如翻译，KV 缓存就没那么重要。DeepSeek 的 MLA 是对 KV 缓存的激进压缩，能用 FP8 或 FP4 处理 KV 缓存的模型也是很大的变化，对 Agent 工作流敏感就要关注这些。最大的差别是因果注意力还是非因果注意力：做批量处理，Google 很长时间都在用 BERT 模型，他认为搜索可能仍在用，因为不需要在另一端生成大量 token，做一次双向注意力得到向量，存进数据库即可；聊天工作流总有解码部分。T5 这样先双向处理再生成的中间方案也曾被采用。
  • 多 GPU 通信在循环里时 mega kernel 怎么办？他们有很早期的工作：设置正确的话可以把 NCCL 调用也融合进 mega kernel，但还没找到很好的杀手级用例，有时瓶颈就是 NCCL 调用本身的延迟。DeepSeek V4 发布时，DeepSeek 开源了一个用于 MoE 推理层的 mega kernel，确实融合了部分通信。他认为接下来会看到更多为模型某一部分计算写的小 mega kernel，而不一定是整个模型的 mega kernel，除非你付出血汗泪的代价把整个东西做出来。
