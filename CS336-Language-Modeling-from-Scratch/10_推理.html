第十讲：推理

推理为什么受内存限制，KV 缓存和预填充与生成两阶段的算术强度，延迟与吞吐量的取舍，缩小 KV 缓存的各种方法（GQA、MLA、跨层注意力、滑动窗口），量化和剪枝，推测解码，以及连续批处理和 PagedAttention

主讲：Percy Liang
资料来源：课堂录像（Stanford Online 公开，2026 年春季，本文依据录像字幕整理）

一、推理为什么重要

推理的问题很简单：模型训练好了，给一个提示，尽可能准确、尽可能快地生成回答。推理只有一讲，但重要性在增长，它出现在很多地方：和聊天助手对话、代码补全、Agent、批量数据处理、需要生成的评估，还有训练内部，做强化学习时要用模型生成 rollout、打分、更新权重。

训练是一次性成本，很贵，但做完就完了；推理是每天都在发生的重复成本。据估计 OpenAI 每天生成 8.6 万亿 token；作为对比，今年早些时候发布的一个模型（字幕里模型名识别不清）用 32 万亿 token 训练，也就是说不到 4 天生成的 token 就超过了这个训练量。过去一年推理更重要了：以前把语言模型主要看作聊天助手，输入提示、得到回答、人去读；现在进入 Agent 时代，一个请求进去，Agent 会思考、推理、调用工具、反思，最后才给人一个输出，大部分 token 不是给人读的。生成的 token 数就是花掉的算力，而且没有上限：问题够难，就需要很多 token。聊天场景下推理快到一定程度就够了，因为人读得没那么快；Agent 场景下，推理能榨出多少就有多少价值。

做推理的人很多：闭源 API 提供商要服务自己的模型，也有很多提供商服务开源权重模型。开源软件包里，vLLM 很流行，是首选之一；SGLang 特别适合 Agent 工作负载，但还没那么流行；NVIDIA 的 TensorRT 很快但比较窄；llama.cpp 适合在 CPU 上做推理。把推理提速两倍甚至 10%，都是大事。

"快"有几种度量：

  • 首 token 时间（TTFT）：用户在任何生成出现之前要等多久。对交互应用很重要，干等的时间越长体验越差；token 开始出来之后就不必那么快，反正人读不了那么快。
  • 延迟：对单个用户，一个请求的 token 出现得多快，也对交互应用重要。
  • 吞吐量：对很多请求，每秒总共出多少 token。适合批处理：你有一 PB 数据要用语言模型处理，只想把活干完，不在乎哪个请求先完成。延迟和吞吐量相关，很多改进会同时改善两者，但后面会看到它们之间也有取舍。

这一讲最该记住的一点：训练时能同时看到所有 token，可以在序列维度上并行，序列只是张量的一个维度；推理时由于自回归，只能一个一个地生成 token，无法在序列维度上并行。这是推理和训练工作负载根本不同的原因，也让推理更难有高算术强度、更难用满算力。

这一讲先用数学分析 Transformer 的算术强度、吞吐量和延迟，然后讲降低成本的方法（缩小 KV 缓存、量化、剪枝），再讲推测解码和一些实际问题。内容很多基于 Google 的 scaling book 中关于 Transformer 推理的章节，他推荐大家去读，一些图也取自那里。

二、算术强度分析

记号：$B$ 是批维度（序列数），$T$ 是序列维度（token 数），$D$ 是模型维度，$H$ 是头维度，$N$ 是查询头数，$K$ 是键值头数，$F$ 是 MLP 的升维维度（约定 $F = 4D$），$D = N\times H$。$S$ 表示作为条件的输入 token 数，$T$ 表示要输出 logits 的 token 数：训练时两者相同，推理生成时 $T = 1$。张量运算图里，红色维度是被收缩的维度（出现在两个操作数中，结果里消失），蓝色是批处理维度（出现在两个操作数中，保留在结果里）。他说这种类似电路图的 Transformer 块描述是他见过最清楚的定义，精确给出了每个张量的形状和依赖。

先复习矩阵乘法 $X$（$B\times D$）乘 $W$（$D\times F$）。推理时用 BF16：读 $X$ 是 $2BD$ 字节，读 $W$ 是 $2DF$ 字节，计算 $2BDF$ FLOP，写回 $2BF$ 字节。读写量是二次的，矩阵乘法是三次的，这就是高算术强度的来源。假设 $B$ 远小于 $D$ 和 $F$，算术强度简化为约 $B$。H100 的加速器强度（每秒 FLOP 除以内存带宽）对应这个运算的临界点是 $B > 295$ 才受计算限制。极端情况 $B = 1$ 时算术强度为 1，严重受内存限制：读了整个 $D\times F$ 矩阵，只做了 $2DF$ 次运算。推理的工作负载就是这样，不是满满的矩阵，而是很"瘦"的张量。

KV 缓存

最朴素的生成：把提示 "Never gonna give you" 送入 Transformer，得到下一个 token 的分布，采样一个 token，拼到提示后面，再整体跑一遍。每生成一个 token 要 $O(T^2)$，生成 $T$ 个 token 就是 $O(T^3)$，很糟。但大量工作可以在前缀之间共享：因为是因果 Transformer，前面 token 的激活不会因为后面追加 token 而改变（如果是双向的，加一个 token 一切都变）。所以把键和值存进 HBM，生成下一个 token 时直接复用，这就是 KV 缓存：对每个序列（$B$ 个）、每个 token（$S$ 个）、每层、每个头，存一个 $H$ 维向量。

推理分两个阶段：预填充，拿到提示，计算并填好 KV 缓存，和训练一样可以并行，因为整个提示都看得到；生成，一个一个地产生新 token，但不用再为已经看过的 token 计算 KV。

MLP 和注意力的算术强度

只看矩阵乘法，其他运算 FLOP 不多，也可以融合进矩阵乘法。

  • MLP：假设 $BT$ 远小于 $D$ 和 $F$，算术强度约为 $BT$，和单个矩阵乘法类似。这说得通：MLP 其实就是大矩阵乘法，批和序列各位置互相独立。预填充时批大、序列长就没问题。生成时 $T = 1$，强度约为 $B$，而 $B$ 是并发请求数：批处理时可以控制；服务聊天机器人时取决于同时在线的用户，难以预测、随时间变化（后面的连续批处理会处理这个问题）。总的来说只要批足够大就还好。
  • 注意力：FLOP 约为 $BSTD$，算术强度约为 $\frac{ST}{S+T}$。预填充时 $T = S$，强度为 $S/2$，序列够长就能保持高强度，注意这里不含批维度。生成时 $T = 1$，强度为 $\frac{S}{S+1}$，小于 1。而 H100 要约 295 才能用满算力，这就是瓶颈。

为什么注意力是瓶颈？MLP 中，每个序列用的是同一组权重，与 $B$ 无关，大 $B$ 能让权重加载一次、用于所有序列；注意力中，每个序列有自己的 KV 缓存，都依赖 $B$，增大 $B$ 没有帮助，相当于每个序列各做各的矩阵乘法，其实和点积一样，算术强度很差。张量图里那个蓝色的 $B$ 就是原因。

小结：预填充受计算限制，生成受内存限制。预填充的 MLP 强度是 $BS$，很好；预填充的注意力是 $S/2$，可以接受；生成的 MLP 是 $B$，需要很多并发请求，也可以接受；生成的注意力强度约为 1，是根本瓶颈，只要还用 Transformer，就没法改善。以后听人说"推理受内存限制"，就知道原因了。

三、延迟与吞吐量

推理受内存限制，某种意义上让事情变简单了：假设通信和计算重叠，耗时只取决于要搬多少内存；但也让人沮丧，加速器在那儿闲着。

以 Llama 2 13B 在 H100 上为例（没有 GQA，$N = K$）：

  • 参数量算出来约 130 亿，和宣称一致；BF16 下参数占 2 倍参数量的字节。
  • KV 缓存每个序列为：序列长度 × 键值头数 × 头维度 × 层数 × 2（键和值）× 2（BF16 字节）。
  • 总内存 = $B$ × 每序列 KV 缓存 + 参数字节，是 $B$ 的线性函数。
  • 延迟由内存读写决定：总内存除以内存带宽，同样是 $B$ 的线性函数，因为 KV 缓存要来回搬。
  • 吞吐量 = $B$ / 延迟，形如 $\frac{B}{aB + b}$，随 $B$ 增大而提升，但有上限。

代入数字：批大小 1 时，延迟约 0.008 秒/token，吞吐量约 124 token/秒。增大批，延迟变差，吞吐量变好；再增大，延迟更差，吞吐量更好，但最后 KV 缓存超过 H100 的显存，放不下。换 B200 能开得更大，但终究有极限，永远到不了渐近线，增益也在递减。

所以"快"有两种含义，取决于你关心哪个，调批大小的方向完全相反：小批延迟好、吞吐量差；大批吞吐量好、延迟差。大批时单个请求要等所有人一起完成，像坐公交车，等车的人延迟高，但公交车的吞吐量好。吞吐量随批增大而提升，是因为参数共享，加载一次就能处理很多序列。并行这一讲不多讲（可以看 scaling book 的推理章节），最简单的例子：启动 $M$ 个模型副本，延迟不变，吞吐量乘 $M$。首 token 时间基本就是预填充的时间，想要 TTFT 小就用小批。

四、缩小 KV 缓存

加快推理的手段很多样，从改模型架构到系统优化都有。最直接的一条：内存是瓶颈，KV 缓存占大量内存，批大时甚至超过参数，那就缩小 KV 缓存，同时注意不要损失太多准确率。

  • 分组查询注意力（GQA）：查询头数不变，键值只按组计算，$K$ 是组数。多头注意力 $K = N$，不缩减；多查询注意力 $K = 1$，效果很差没人用；中间找平衡。2023 年的 GQA 论文显示，MHA 每样本耗时高，$K = 1$ 快很多，$K$ 增大到 8 左右仍然很快。KV 缓存缩小 $N/K$ 倍，由于受内存限制，延迟和吞吐量都改善。回到 Llama 例子，批 64 时用 1:5 的 GQA，延迟和吞吐量都变好：两者并不总是对立，减少内存能同时改善两者，真正造成取舍的是批维度。原来批 256 放不下，现在放得下，延迟略差，吞吐量成比例上升，可以联合调这些参数。有损的改动都要检查准确率：GQA 论文说在一系列评估上效果不错，但他提醒对非纯数学的结论都要存疑，后来 DeepSeek 的论文显示 GQA 其实有损失。
  • 多头潜在注意力（MLA，DeepSeek）：键值数量不减，而是压缩：把激活投影到 $C$ 维（DeepSeek V2 从约 16000 维降到 512 维，很激进），只缓存这个压缩表示，需要时再算出 K 和 V。MLA 和 RoPE 不兼容（RoPE 直接作用于键），所以额外加了一些维度处理 RoPE，但总体缩减仍然很大。延迟和吞吐量按简单的数学改善，在一定范围内近似线性。DeepSeek 的结果显示 GQA 比 MHA 差，MLA 和 MHA 差不多，甚至略好。学生问这和直接减小模型维度比如何，他说这些消融没比较，猜测直接减小模型维度是无差别地削减，会更差；诀窍是找到模型里可以挤压的地方，这事先不知道，只能大量实验。
  • 跨层注意力（CLA）：只为部分层计算 KV，其他层复用前一层的 KV 缓存。GQA 在头之间共享 KV，CLA 在层之间共享。论文显示它改善了帕累托前沿：通过调 $K$ 和头维度可以扫出不同 KV 缓存大小，加上 CLA 更好。
  • 局部注意力（滑动窗口）：生成时只看最近 $K$ 个 token，KV 缓存与序列长度无关，对长上下文特别好；由于层层传递，有效上下文比窗口长。也可以间隔选取，或"全局加滑动窗口"。问题是仍然损害准确率，降低了表达能力，没有免费午餐。解决办法是混合：部分层全注意力，部分层局部注意力，在准确率和速度之间平衡。
  • 线性注意力（学生问到）：不存 KV 缓存，而是维护历史的压缩表示。最朴素的是把 KV 加成一个向量，与序列长度无关；Gated DeltaNet、Mamba 等能压缩而少遗忘。它们也被用来代替滑动窗口，效果不错，也可以三者组合：要局部高分辨率信息，滑动窗口更好；要对过去的大致概括，线性注意力可能更好。学生问长上下文是否线性注意力更好，他说没有免费午餐，比如大海捞针，把全部历史压缩进小状态就会丢信息、取不回来。他认为 Mamba、DeltaNet 比滑动窗口更强，至少有更大的空间，因为它们能表示滑动窗口的某些方面，而滑动窗口就到头了。
  • DeepSeek 还在不断发明新的注意力：压缩稀疏注意力、DeepSeek 稀疏注意力、高度压缩注意力（他说自己也记不住这些缩写）。大意是：把每 $M$ 个 token 压缩成一个；用轻量的查询和键做一个小注意力得到索引分数，快速选出要保留的 token 子集，再进一步压缩。

这一节的目标是缩小 KV 缓存，直接转化为吞吐量和延迟的改善，关键是不伤准确率。可以在头之间、层之间、头维度上降维，用局部注意力或线性注意力，还有很多别的办法，比如扩散模型这种非自回归的生成方式，可能快得多。

五、量化与剪枝

量化更偏系统视角：降低数值精度，内存少了，延迟和吞吐量就好，同样要担心准确率。精度可以从 BF16 一路降到 INT4。

  • 量化感知训练：训练时前向中先量化再反量化，模拟量化误差，权重会适应量化，效果更好；缺点是需要昂贵的大规模训练。
  • 训练后量化：更常见，便宜得多。朴素做法是每层或每个张量确定缩放和零点，分别量化，效果一般。GPTQ 利用 Hessian 信息逐层量化，把误差传播到还没量化的权重上来修正。激活感知量化（AWQ）更精细：有些激活通道很大，和它们相乘的权重更重要，就给这些权重更高精度，比如大部分量化到 INT3，少数重要通道保留 FP16。

剪枝：拿一个大模型，挖掉一些部分，再修补，很粗暴但有效。NVIDIA 的一篇论文：先估计模型各部分的重要性，去掉不重要的隐藏单元甚至整层，得到的模型不太好，再在关心的数据或任务上继续训练来"治愈"它。他说这相当于用一个好模型的一部分做初始化来训练更小的模型。他们把 15B 模型压到 8B，准确率损失不大，所需训练量也少得多。学生问怎么判断哪些重要：用一个校准集过模型，看激活大小，接近 0 的（比如死单元）可以去掉，大的保留；这依赖于"有些通道远大于其他通道"的经验观察，这在训练出来的模型中恰好成立。学生问如果某个神经元总是 100 呢？他说那也不能直接去掉，否则全坏了；但如果均值高、方差低，也许可以把它并进偏置。

小结：要在不伤准确率的情况下降低推理复杂度，主要是减少参数或 KV 缓存。可以定义更快的架构从头训练；也可以定义更快的架构，用原模型（可能是不同架构）的权重初始化，拼成一个"弗兰肯斯坦"，再用蒸馏修复。

六、推测解码

前面的方法都是有损的。推测解码（推测采样）是无损的，很优雅。预填充可以并行处理所有 token，同时得到概率，快且受计算限制；生成一次一个。所以检查比生成快：给你一个序列，评判它比逐个生成快得多。利用这种不对称：用一个便宜的草稿模型 $p$ 猜几个 token（比如 4 个），再用真正关心的目标模型 $q$ 并行地审查，决定接受与否。草稿模型小，逐个生成也不算贵；目标模型大，但并行处理一批 token，也不算贵。效果是一阵一阵地冒出 token。

算法：从草稿模型采样 $K$ 个 token；用 $q$ 并行计算它们的 logits；对每个 token 以概率 $\min\left(1, \frac{q(x)}{p(x)}\right)$ 接受；被拒绝时从残差分布 $\max(q - p, 0)$（归一化后）采样一个 token 并结束。和拒绝采样类似，但拒绝采样被拒时什么都得不到，这里总能得到一个样本，而且保证恰好服从目标模型的分布（证明和拒绝采样的论证相同，课上略过）。草稿 token 太少，没有利用目标模型并行处理的优势；太多，被拒的概率变大，原论文中最佳点在 3 到 4 个。草稿模型要比目标模型小得多，又要尽量接近目标，所以常用蒸馏，前面缩小 KV 缓存的那些办法也都适用：得到的小模型如果你满意，就直接服务它；不满意，至少可以当草稿模型，让主模型修正。现在有大量改进推测解码的文献，课上略过。

七、动态工作负载

实际服务网站时，用户请求在不同时间到达，有不同的共享前缀，长度各异，远比训练时整齐的块要乱。

  • 连续批处理（很早的 Orca 系统提出）：每一步为批中所有序列各解码一个 token；某个序列结束就移出，新请求到达就加入，批是动态更新的。问题是长度各不相同，批处理要求维度一致。选择性批处理：注意力依赖各自的序列长度（3×3 和 9×9 的计算无法共用张量），只能分开算；而占大量 FLOP 的 MLP 等非注意力层，可以把所有序列拼成一个超长序列一起处理。
  • PagedAttention（vLLM 论文提出，vLLM 现在有很多其他功能，但这是当时的核心想法）：KV 缓存存在内存里会产生碎片，就像以前硬盘要整理碎片。内部碎片：不知道什么时候停，只能按最大 token 数（比如 1024）预留，没用上的都浪费了；外部碎片：请求之间的空隙太小用不上。做系统的人懂操作系统，就借用分页的思路：把一个序列的 KV 缓存分成不连续的块，比如 "Four score and seven years ago our fathers brought forth" 按 4 个 token 一块，块放在哪里无所谓，记录好索引即可。块对齐带来一致性，不同请求可以共享块：很多人用同一个系统提示时，系统提示的 KV 缓存只算一次；同一提示要生成多个回答时，也共享提示部分。多个样本在同一块中采样到相同 token 就继续共享，采样不同时再复制拆分，这是写时复制。还有内核等其他优化，课上没时间讲。

八、小结

推理很重要。模型和训练时是同一个，但要它做的事很不一样，最终严重受内存限制，在线聊天场景下还是动态的。改进推理的方法很多：量化、新架构、剪枝和蒸馏、推测采样，背后是同一个原则：缩小 KV 缓存，又不太伤准确率。分页、推测执行等系统思想也可以用于实际的推理服务器。

课上没来得及展开的一点：他认为新架构的潜力很大，比如状态空间模型、线性注意力、扩散模型。KV 缓存和注意力的结构从根本上让 Transformer 对推理不友好；如果能设计出为推理而生的架构（Transformer 并不是），也许能解锁很多东西。下一讲 Tatsu 回来讲缩放规律第二部分。
