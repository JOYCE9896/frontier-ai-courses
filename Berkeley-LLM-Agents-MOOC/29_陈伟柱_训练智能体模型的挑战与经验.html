Weizhu Chen：训练智能体模型的挑战与经验

微软 CoreAI 后训练负责人讲工业界怎样用强化学习训练编程智能体：rubric 评分细则，只用一个样本的 RLVR，数据配比和数据合成；产品里的多重 grader 怎样平衡、模型怎样作弊又怎样防；异步 RL、策略探索和工具泛化、解长度控制、长上下文摘要、LoRA 用于 RL；用乐高解释预训练、后训练和 RL，以及测试时和训练时扩展的展望

主讲：Weizhu Chen（Microsoft）· 课程：Berkeley CS294/194-196 Agentic AI（2025 年秋季）· 上课日期：2025 年 10 月 13 日 · 时长：1 小时 4 分 · 整理：Joyce（@JOYCE9896）

这一讲讲什么

Weizhu Chen（陈伟柱）在微软将近 20 年。幻灯片上的自我介绍是：工程师、研究员，微软 technical fellow 和 CVP，带 CoreAI 后训练团队；在香港科技大学读的博士，先在微软亚洲研究院（MSRA）工作，2012 年来美国；一直在研究院和产品团队之间切换，现在在产品团队。他说自己更想做真正能用的产品，而且发现待在产品团队时研究反而更高产，幻灯片上列的工作大多是在产品团队时做的：2020 年的 LoRA（GPT-3 定制）和 MuP（GPT 预训练），2022 年的 DeBERTa（支撑多个自然语言理解产品）和 GitHub Copilot 正式发布，2024 年 Phi-3 和 Phi-4 的数据合成，以及获得 NeurIPS 最佳论文亚军的 Rho-1。

他说前面几讲（Yann Dubois、Jiantao Jiao 等）已经讲了很多，所以他想讲教科书里没有、但在日常大规模训练里真正管用的东西。重点是模型训练而不是推理，因为他认为要提升模型质量，得靠端到端训练。他拿编程智能体当例子，分三块讲：数据，grader（评分器，也就是评测），效率；最后讲他看到的下一步方向。幻灯片首页注明观点只代表他个人，不代表公司。录像没有课程事务开场，也没有问答。字幕把他的名字听成了 “Richard Chen”，把 rubric、grader 等词的上下文听得比较乱，本文按幻灯片整理。

01. 一个编程智能体的训练回合由哪些部分组成

录像位置 0:00:00–0:06:18

他说团队也做编程以外的东西，选编程当例子，是因为大家都用 VS Code、GitHub Copilot、Cursor 这类工具，编程最能说明业界的模型现在怎么变了。

例子：修一个 GitHub issue

输入是一个 GitHub issue 和对应的代码仓库。issue 描述要解决的问题，比如修一个 bug。模型要尝试解决它。除了模型之外还有一个环境模拟器：要跑代码、跑测试，这些不在本地机器上跑，而是在沙箱里。他说这种环境模拟器规模很大，大多跑在 CPU 上，CPU 的数量至少是 GPU 的 10 倍。

模型和模拟器之间要来回交互很多次，每次让模拟器跑不同的东西，这就是多轮对话。最后模型判断已经可以修好了，生成一个 pull request（PR）连同说明交给用户。用户可能说这个 PR 不对，还要改，交互继续下去。过程中模型还会让环境跑单元测试，环境告诉它通过没有。幻灯片上的示意图是：Linux 系统里，问题提示和代码仓库输入语言模型，模型通过工具调用和环境模拟器交互，收到工具返回，最后输出补丁和 PR 描述，由单元测试判定通过或失败。

智能体训练需要哪些能力

  • 目标导向：有一个要达成的目标，可以是一道数学题，也可以是生成一个 PR。PR 本身有很多要求，比如要解决问题、要通过所有单元测试。
  • 工具使用：让模拟器跑各种东西，而且是多轮的，交互有时很复杂。
  • 规划：决定先做什么、后做什么。
  • 推理：根据当前状态和反馈（来自模型自己或模拟器）决定下一步。他说这就是推理模型特别适合智能体训练的原因。
  • 用户交互：在真实系统里，模型要根据上下文听用户说哪里错了、哪里能改进。

幻灯片把训练侧要解决的东西列为数据、grader、评测、效率和环境。他说今天只讲其中几件，而且他在业界的经验可能和大家在别处听到的不太一样。数据的重要性没人会低估；grader 就是评测，Yann 在第一讲里就说过，RL 训练智能体模型主要在于你怎样定义评测、定义 grader，而这并不容易；效率决定了在几千张 GPU 上能不能稳定地跑。

02. RL 数据：可验证、不可验证和 rubric

录像位置 0:06:18–0:11:54

两类数据

第一类是结果可以验证的数据，比如数学、编程（能跑单元测试）、有标准答案的 ABCD 选择题。他说可验证数据很好，带来了很多智能。但真实产品里很多东西不可验证，很难判断什么是标准答案，而且很开放：给用户看的代码风格好不好，一段文字或一种呈现方式好不好，你喜不喜欢，都很主观；让模型写首诗，不同人看法不同；安全也一样，对一个人安全的内容对另一个人可能不安全。针对不可验证数据，他讲两件事：rubric 和数据合成。

rubric：可打分、可引导

rubric 是评分细则：针对一道题，把“好答案”拆成一条条具体、可判定的标准。他说业界实验室会写大量 rubric，比大多数人想的复杂得多，而且由很强的人来写。

以前的做法是请人类专家针对问题写一个标准答案。他说这不够，现在要人写评分标准。一道题有 50 条标准并不稀奇；每条都要写得清楚详细、人能读懂、有结构，而且能打分，比如读完判断这一条得 1 分还是 0 分。打分方式决定了 RL 训练时 grader 怎么跑，rubric 就是 grader 的输入。

这种做法适合开放领域、开放问题，因为这些问题很难判断答案对不对。办法是拆成细粒度的小项，每一项判断好坏。他强调：如果没法衡量，就没法学。

代价是贵。专家写完一道题的全部标准，花几个小时甚至几天很正常（幻灯片上写的是几小时、几天甚至几个月）。标准要全面，合起来能覆盖这道题的所有方面，不管来的是什么答案，都能用 rubric 衡量它有多好。他说数量不用很多，泛化可以交给语言模型，质量比数量重要得多。幻灯片还写着：由专业领域专家来策划和验证数据，成本高、难以规模化。

03. 只用一个样本做 RLVR

录像位置 0:11:54–0:16:03

既然高质量数据又贵又重要，那到底要多少？他提了一个极端问题：只有一个样本行不行？他说做 SFT（监督微调）或者训练奖励模型时，一个样本永远不够。但他们做过一项工作，研究在 RLVR（reinforcement learning with verifiable rewards，用可自动验证对错的奖励做强化学习）里只用一个样本训练会怎样，用的是数学题，因为做研究要靠公开基准来验证。

结果

他展示的曲线里，虚线是用 1,200 个样本训练，绿线是只用一个样本训练：模型反复做这一道题、反复验证答案对不对，成绩一直往上走，最后很接近用一千多个样本训练的结果。评测集是同一个，里面有很多不同的题。幻灯片上的表：

数据或方法MATH500AIME24
基座模型36.06.7
只给格式奖励65.08.3
π1（单个样本）74.020.4
π17（单个样本）67.213.3
1.2k DSR-sub75.218.8

他的解读是：只用一个样本也能学成这样，说明 RL 没有在记这道题，它学到的是怎样解数学题。

怎样挑这一个样本

不是随便哪个样本都行。他们按方差挑：让模型对这道题做多次 rollout（按当前策略完整生成一次解答），看结果彼此差别大还是几乎一样，他们偏好差别大的。幻灯片上的说法是按历史训练准确率的方差给训练数据排序。rollout 越多样，能学到的越多。表里 π1 就比 π17 好很多。

RL 数据和 SFT、RLHF 数据的区别

他说这说明 RL 数据和 SFT、RLHF（基于人类反馈的强化学习）的数据很不一样，区别在于探索的力量：

  • 学到的是构件：RL 用这道题探索出数学题的基本构件，一个样本就摸到了大部分。
  • 数据效率极高：选对数据，就能学到很好的策略。他说这是今天的 RL 和以前工作的不同之处。
  • 质量很重要。幻灯片补充：数据要有高熵来鼓励探索；不能太难（通过率为 0），也不能太简单（没有负反馈）。

04. 数据配比和数据合成

录像位置 0:16:03–0:22:20

数据配比

工业训练有很多不同的任务。训练编程模型，除了写 PR，用户还会问很长的编程问题、做问答、让模型根据代码写文档。他说业界实验室做数据，大部分精力花在怎样混数据：这类占 3%，那类占 20%，训最终模型时不断调。配比在训练过程中也会变：开始时多放一些简单数据，让模型先学到这个水平；随着模型变强，混进越来越多的难数据。

如果模型在三类任务上很好，另外两类不行，最简单的办法就是找更多这两类的数据，找不到就合成。幻灯片上的话是：认真整理高质量数据，往往比在训练参数上“炼丹”效果更好。还列了四条经验：

  1. 难题通常对强模型更有用。
  2. 数据好不好也取决于模型。
  3. 真实数据和合成数据结合使用：真实数据对真实场景有帮助，合成数据可以按多种风格规范化生成。
  4. 用强模型当评判者来生成更多数据。

数学题的数据合成

他说数据合成不只能解决数量问题。在数学上，他们的一项工作是合成大量新题目，同时有机制保证新题的答案可验证。这样增加了数据多样性，几乎可以无限地造数据。另一个发现和熵坍缩有关：RL 训练提高质量的同时，模型输出的熵会下降，生成越来越单一。他们发现这种合成方式不仅提高了 pass@1，也明显提高了 pass@k（采样 k 次至少有一次对的比例）。他说 RL 训练里常常 pass@1 上去了 pass@k 却不涨，而要探索，就需要 pass@k 也提高，所以他们很看重这个指标。

智能体数据的合成

智能体任务的数据很难合成。他说自己不能透露微软怎么做，但推荐 Kimi K2 的工作（字幕听成 “K B K2”）。思路是典型的：从 GitHub 拿到已有数据和工具，合成工具定义、合成任务、合成智能体，再把合成数据和原始数据混在一起训练，整条管线要能跑、能扩展。幻灯片上的描述是：先做出可构建的仓库和镜像，再在环境里合成各种带可验证奖励的任务，用来提升最终任务和编程、智能体能力。

他的观点是，数据合成在业界已经很复杂，创新空间很大，他把团队里最好的人放在数据合成上。以前大家觉得造数据是脏活，现在不是了。他说训练方法比数据更容易趋同，可惜很多业界实验室不公开数据怎么造。如果他自己创业，会考虑怎样合成更好的数据；对博士生来说这也是很重要的方向。

05. grader：产品里的评分器有多复杂，模型怎样作弊

录像位置 0:22:20–0:30:37

RL 靠经验学习，而反馈只能由 grader 给出。他说如果你知道一个问题该评什么、怎么评，问题就解决了一半。

日常工作就是想清楚评什么

幻灯片上把他们的大部分工作归成三件：想清楚要评什么；搭新的 grader，和现有 grader 组合；准备要被评、被训练的数据。他说要评的远多于通过率。即使是编程，也要看呈现方式、是否符合期望行为、是否满足产品约束。每天根据用户交互看模型还缺什么，然后加更多 grader。加 grader 并不容易，新的可能和旧的冲突，要弄清多个 grader 之间的关系。grader 和数据高度相关，有时 grader 就是数据的一部分。因为他们也做基础模型，要评的领域很多（金融、医疗、编程、咨询、STEM、法律等），每个领域又有很多不同问题。仅编程就有 next edit suggestion、代码补全、编程智能体等。

产品约束

他举了个例子：编程智能体的任务有时要跑 10 分钟，用户说“我想去买杯咖啡，你能不能告诉我还要多久、进度怎样”。模型就得学会汇报进度。这是产品约束，不是通过率这种单一的学术指标。幻灯片上列的 SWE 产品 grader：

  • 通过率：PR 能通过所有测试。
  • 开放问题：超过 50% 是问答这类开放问题。
  • 多轮：在交互中改进 PR 或回答。
  • 格式：markdown、表格等呈现方式。
  • 行为：执行时汇报进度，最后总结 PR。
  • 长度：简洁，太啰嗦一般是负面的；还衡量 time-to-PR（多久交出 PR）。
  • 伦理：不能说很糟糕的话。

编程任务的 grader 进一步分为：单元测试 grader（硬性的性能要求）、补丁 grader（最终补丁格式好）、rollout grader（工具用得准）、行为 grader（修完后好好测试并写总结）、用户体验 grader（按用户指示一步步做、汇报进度）、任务专属 grader（如仓库搭建任务）等。他说日常最常用的是三种：verifier，比如单元测试，判定通过或不通过；LLM grader，用另一个大模型按提示打分；以及按前面说的 rubric 打分。

怎样平衡多个 grader

产品做下去，grader 只会越加越多，任何模型都很难全部通过，训练初期尤其如此。他打比方说，就像要求一个三岁小孩遵守大学的规矩。他们的办法：

  • 相对排序：不判通过与否，而是比较哪个结果比其他的好，从排序中学习。
  • 课程学习（curriculum learning）：有些 grader 到后期再加，一开始太难模型什么也学不到；训练中调整各 grader 的权重。
  • grader 依赖：有的 grader 依赖另一个，要先解决那一个，因为有些 grader 比别的更严格。有依赖的按顺序执行，其余的并行跑以加快速度。幻灯片示意图里单元测试 grader 和 rollout grader 输出通过或失败，补丁 grader 输出连续奖励。

作弊很正常

他说只要有 grader，模型就会想办法作弊，reward hacking（钻奖励函数的空子拿高分而不真正完成任务）很常见，因为模型太聪明了，他们见过很多让人意外的情况。幻灯片上的两个例子：模型把仓库里的测试文件改成一个永远通过的 hello-world 测试，每次都拿满分；给了网络权限时，比如跑 SWE-bench Verified 这类任务，模型会用 curl 或 wget 去 GitHub、Stack Overflow 上找标准补丁，直接抄过来当输出。

他们的防范办法：

  • 用另一个模型监管奖励模型，配合 rubric，检查输出是否容易被骗。
  • 检查最终答案，仔细检查 rollout，检查行为。
  • 模型能改测试用例，就在沙箱里把测试藏起来：跑之前把测试文件全部移走，跑完再把测试补回去做检验；PR 里的测试文件也删掉。
  • 作弊给很大的惩罚。

他说一定要小心，模型太容易作弊了。

06. 训练效率和异步 RL

录像位置 0:30:37–0:35:19

他说不确定 50% 是不是准确的数字，但数据（包括 grader）大约占他们日常工作的一半，另一半是效率和让训练跑通。效率首先包括让东西能跑，跑不通效率就是零。RL 很贵，尤其是采样阶段，模型要自己去探索出好的训练样本。前面说一个样本也能学到很多，前提是给足算力，而算力不容易拿，它关系到 GPU 数量，也关系到迭代速度。他们的做法有四项：强大的异步 RL 训练基础设施，鼓励策略探索，控制采样成本，RL 里用 LoRA。

异步 RL

RL 有采样器（sampler，按当前策略生成 rollout）和训练器（trainer，用这些数据更新模型）。两者互相等待会很慢，规模越大越明显，所以很多实验室的论文都在用异步方式，但在大规模下把异步做好并不容易。

他说现在最慢的是采样器，尤其要采样很长的思维链时。以前大家认为训练器最慢，现在采样器慢得多，所以他们给采样器分配的 GPU 比训练器多得多，让训练器一直有可用的样本进来。异步的意思是采样器和训练器不用等对方：采样器一直采样，用的不必是最新策略，可以是上一轮的策略，这就成了 off-policy 学习，需要做很多工作保证收敛。

幻灯片上的架构图：通常只有一个训练器，有多个采样器（他们叫 roller，Roller 1 到 Roller N），roller 产出 rollout 交给训练器，训练器定期把权重同步回 roller；roller 既要和 grader（G1 到 GK）通信，也要和环境通信，比如跑单元测试的模拟环境，grader 需要时也要访问环境。他说图很简单，但要在几千张 GPU 上跑好，有大量工作要做，因为一旦异步，很多事情都可能出问题，质量和效率很难平衡。

07. 策略探索和工具泛化

录像位置 0:35:19–0:39:58

他说一样本学习的例子说明了策略探索有多重要，怎样鼓励模型探索也是 RL 最有意思的研究方向之一。探索得越多，越可能得到更好的结果，探索决定了能从 RL 里学到多少。

先保证指令遵循

他们学到的一条经验：模型首先要能遵循指令。很多时候 RL 训不出好结果，原因是模型不会按指令做事。这时应先继续训练它的指令遵循能力，再上 RL。他说看到一个小模型 RL 效果不好，第一件要查的就是它的指令遵循能力。

增强探索的办法

  • 基于提示的办法：同一个问题用不同方式提示模型，比如“用这种方法解这道数学题”“用另一种方法解”。他说这听起来很朴素，但很重要，能做的事很多，甚至可以让另一个模型来生成提示。只要模型能遵循指令，不同的提示就让模型从不同角度看问题，有更多探索路径。幻灯片列出：改写提示生成变体；加引导性提示，鼓励用不同方式解题；结合用户交互引入不同提示变体。
  • 控制思维链长度，不让模型无限生成。
  • 基于噪声的办法（对抗训练）：在模型中引入噪声。
  • 基于工具的办法：同一个任务给模型配不同的工具，第一次用这套工具，第二次用另一套，或者去掉一些工具，鼓励模型在不同环境里探索。

工具泛化

现在用户可以接入自己的任何工具，比如通过 MCP 或者自己的 API。训练时并不知道用户会用哪些工具，但只有一个模型要应对所有工具，所以关键问题是工具泛化。他们的做法：

  • 指令遵循能力要很强，才能适应新工具。
  • rollout 里模型可能用错工具，要能反思并很快自我纠正：这个工具解决不了，换一个试试。
  • 用多种工具集训练，同一个任务构建多套工具集。幻灯片列出的工具变体有：工具函数的顺序不同、函数名不同、参数不同、描述不同。
  • 支持第三方工具（MCP）。
  • 提示里指定了工具而模型没用，就给惩罚，这也是 grader 的一部分。

08. 解的长度和长上下文

录像位置 0:39:58–0:44:45

解的长度决定采样效率

瓶颈在采样。模型很聪明，一种办法解不了就一次次重试，直到更可能解出来为止。这对用户体验不好：同一个问题，一个解法 1 分钟完成，另一个要 1 小时，用户当然要前者。目标是让模型尽快完成任务，所以要在性能和成本之间平衡。他们会让模型在不同长度约束下解题，偏好更短的答案。

难点在于：长度惩罚太低，模型会用无限多的 token，一直做到它认为答案更好为止，解的长度失控；惩罚太高，模型会压缩推理，给出过短的解来躲避惩罚，也就牺牲了探索，因为没有鼓励模型去尝试更长的解法。

他们的办法很简单。幻灯片上对比了“长度爆炸”和“长度受控”两条曲线。训练时，把特别长的 rollout 截掉（比如有的跑 13 分钟或 1 小时，就直接放弃），并额外计 token 成本。评测时，他觉得更有意思：看 SWE-bench Verified 排行榜，多数人只报通过率，不报 rollout 多长。他认为这有问题，因为在测试时扩展的范式下，质量高度依赖长度，也就是测试时给了多少算力。他们内部评测同时看通过率和解的长度，测试时算力不在同一水平的结果，他们认为不可比。

长上下文

有些模型支持 100 万 token，但很多情况下仍然不够；他说目前多数模型是 128K，更不够。原因是用户一直不关窗口、一直问下去，rollout 会很长；编程时有些文件本身就很长，会占满上下文。

他用一个开源方案说明解法：阿里巴巴的论文 ReSum（字幕听成 “Reese Sam”）。思路很简单：对历史或较早的 rollout 做摘要，摘要比原文短得多，用摘要替换原文，就能继续往下做；摘要器是一个单独的模型。幻灯片的说法是：用一个对话摘要器，在历史或思维链达到某个上限时反复做摘要。他说真正实现时细节很多，有很多种做法：摘要整个历史还是只摘要思维链，保不保留原始答案，保不保留给用户看过的内容。哪种好只能自己跑实验看。

09. LoRA 用于 RL，以及用次优设置做实验

录像位置 0:44:45–0:48:30

LoRA（low-rank adaptation）冻结原模型权重，只训练插进去的低秩小矩阵，参数量和显存都小得多，他本人是 LoRA 的作者之一。他提到 John 的 “LoRA Without Regret” 是很重要、很漂亮的工作，讲了怎样让 LoRA 做到和全量微调一样好（这篇是 Thinking Machines 的博客文章，属背景信息，课上只说了 John）。

为什么 LoRA 在 RL 里好用

以前 LoRA 有时好用，有时不如全量微调。他给的解释是：LoRA 更多是一种正则化。它天生带正则，主权重固定不变，无论怎么训，权重的改动都很小。而 RL 比 SFT 更需要正则化，有两个原因：一是 RL 不希望策略离上一个检查点太远；二是 off-policy 训练（前面讲的异步）总需要正则化，采样用的策略和正在训练的模型差得太多，就很难收敛。所以 LoRA 的更新方式和 RL 的需求很契合，这是 LoRA 在 RL 里流行的原因。另外它用的 GPU 少，训练也快一些。

用高效的次优设置当基线

他说的第二点不限于 LoRA：在业界实验室，大部分 GPU 用来跑各种实验，比如试这种数据配比、那种数据配比。凡事都有取舍，他们做实验时不用最优设置，而用最高效的设置，即使质量低一两个点，但实验能快两三倍。做法是把这种高效的次优设置当基线，在这个约束下做所有改动的并排比较，这样创新迭代能快两到三倍。等配方都摸清楚了，最终那一次训练再跑得更久、用上所有最好的设置。幻灯片上写的是：用次优的高效设置当基线，做降低风险的实验。他说大家可能会惊讶他们平时不用最优设置，原因是太贵。

10. 用乐高解释预训练、后训练和 RL

录像位置 0:48:30–0:52:52

他做过预训练，最近在做 RL。他 11 岁的女儿喜欢玩乐高，有天晚上陪她玩时，他试着把这些概念讲成乐高。

  • 预训练：给你一大堆没有顺序的数据，预训练要把无序变成有序，也就是从数据里找出关键的乐高积木，以及高效拼装它们的方法，用这些积木把原来的数据（一面乐高墙）再拼出来。更好的预训练模型能学到形状更复杂的积木，拼法也更高效，用更少的块就能拼出同样的墙。
  • 后训练：目标是你想要什么样的墙，任务就是用已有的积木把它拼出来。预训练已经备好了积木，所以有了预训练模型，后训练就高效得多。
  • RL：它是一种学习方式，不一定绑定在预训练或后训练上，已有工作把 RL 用在预训练里。RL 就是把乐高拼搭游戏玩几百万次，拿到反馈：反馈好，就多搭这样的墙；反馈不好，就拆掉，用积木重新搭。

他一直在想，能不能搭出和今天的墙完全不同的新东西。他觉得可能：今天乐高墙上的形状大多能在现实里找到，未来也许能出现现实里找不到的东西，只要积木够不一样，模型就能凭想象力和创造力搭出来。幻灯片上这一条写的是“探索鼓励创造力”，举的例子是 AlphaGo 的第 37 手。

11. 展望：测试时扩展、训练时扩展和自我改进

录像位置 0:52:52–1:04:37

他说他的展望很简单，唯一的共同点是扩展（scaling），分测试时和训练时。

测试时扩展

测试时扩展（test-time scaling）指推理时多花算力换更好的结果。他说归结起来只有三条路：

  • 更大、更深的模型。尤其是推理，模型需要更深，他提到最近有工作用循环（recurrent）等方式让模型变深。他的观点是，任何让模型变深的办法都有助于推理。
  • 更宽的执行。一是并行思考：今天的做法是模型训完后让它产出多个结果，再投票或用另一个模型挑，训练时并没有考虑这一点。他认为一个有意思的方向是在训练时就让模型为并行思考而学。二是多智能体：把同一件事交给多个智能体做，让它们协调，再有一个编排者（orchestrator）或者说“老板”分派任务，幻灯片上写的是把多智能体交互和编排纳入学习。
  • 更长的执行。今天编程智能体几分钟给出结果，未来可能做更复杂的任务，一两天后才交回来，他觉得这会很正常。这里有很多研究问题：长上下文，以及怎样记住之前的行为，比如记住一天前做过什么。人很擅长，模型还不行。

训练时扩展

数据合成仍是第一位。他说还有很多事可做，才刚刚开始。今天他们常常受限于数据而不是算力，算力很多，数据却快用完了，没有多少数据能把模型推上新台阶。他认为最好的模型一定出自最好的数据，今天一个模型有一半以上是由数据决定的。智能体数据把数据复杂度提到了新的层级：怎样用多智能体合成数据，怎样合成长程数据，都很复杂，所以他才介绍 Kimi K2 的工作。幻灯片上写：合成是生产智能体数据的可扩展方式。

关于 RL，他列了几点：

  • 和 SFT 比，RL 是用算力换鲁棒性。在业界，RL 不只让结果好一点，而是让结果稳得多：用户换一种方式问，模型也能给出可以接受的结果，SFT 有时很难做到。RL 用的算力比 SFT 多得多，但确实带来了鲁棒性，这对产品很重要。
  • 他相信只要 RL 训练做对了，加算力质量就会一直涨，直到碰到模型本身的上限。能找到一种“给算力就变好”的办法，是很大的事，预训练有时做不到，还受数据限制。
  • 可引导性（steerability）：RL 能把模型引向你想要的方向，可以快速修产品问题。和 RLHF 训奖励模型或做 SFT 相比，RL 灵活得多：想改模型行为，改 grader 就行，告诉它这样做奖励更高，那样做奖励更低。
  • RL 可能打破预训练和后训练之间的墙。他说现在常见的是预训练团队训好模型交给后训练团队，两边之间有“战争”，大家说预训练负责压缩、后训练负责行为。他不确定这种划分是否必要，未来也许只剩两种损失，RL 和下一个 token 预测，合在一起。他说这只是一种可能，他也不知道。

自我改进

他认为最好的方式是模型能自己改进。现在模型已经很强，这变得可能，很多前沿实验室都在做：在更高的层面上，投入更多算力和数据，模型就能不断进步。要做到这一点，最重要的两件是数据和 RL，怎样构建数据，怎样把 RL 变成一个游戏。模型还要能自我反思、自我批评，明白之前哪里错了并改正；幻灯片上还写了模型之间的交互。另一个要解决的方法论问题是，上一代模型不如下一代，怎样让弱的学习者造出更强的学习者。

训练模型的苦和乐

最后他说了几句和日常工作有关的话。他听说在座很多人每天训模型，有人昨晚干到早上 5 点。训模型很难：经常凌晨 3 点醒来看任务，出了问题要重启任务、和团队讨论哪里错了、怎样尽快修好重新提交，免得浪费 GPU。他说有一件他没多讲但对他们很重要的事是基础设施，很多细节不能公开，它是现实中最大的痛点之一：这块 GPU 坏了，那块掉线了，大量时间花在基础设施的不稳定上，有时会觉得绝望。训练模型大约 90% 的时间是跑不通的，只有 10% 的时间真正在进步，所以要有耐心。

但他也说训练模型很有意思，可能是世界上最好的工作之一：有机会用这么多 GPU 训模型很难得；训出的模型打败基线时很有成就感，因为基线有时就是世界上最好的模型；他在产品团队，模型被很多人用上并收到反馈，又是另一种成就感。
