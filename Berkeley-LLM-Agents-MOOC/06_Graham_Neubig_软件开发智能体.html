01. 软件为什么重要，开发者的时间花在哪

录像位置 0:00:00–0:03:39

软件在吞噬世界

他引用 Marc Andreessen 2011 年的文章 “Why Software Is Eating the World”：越来越多的大企业和行业靠软件运转、以在线服务交付，从电影到农业到国防；未来十年会有更多行业被软件改变。他说这大体成真了，比如很难想象电影不通过软件交付，他问过去五年谁还去租过实体电影，没人。

他的出发点是一个问题（幻灯片第 3 页）：如果每个人都能快速写软件来实现自己的目标，他们能做到什么？他说对学计算机的人来说，答案是能做很多。他还说这很应景：这一年的诺贝尔物理学奖和化学奖，都颁给了写软件的人。过去这些奖给的是用试管、跑回旋加速器的人，这些仍然重要，但越来越多的科学和人类进展会发生在软件里。

写代码只占 15% 的时间

他问大家，普通软件工程师每天有多少时间在写新代码？答案是 15%，出自 Microsoft 2019 年的研究（幻灯片：Meyer 等，“Today was a Good Day: The Daily Life of Software Developers”）。他说现在也许多一点或少一点，但开发者不只在写代码，还在修 bug、测试、写文档和做代码审查；36% 的时间花在各种沟通上；17% 是其他事情，比如去洗手间。幻灯片上的饼图还列了 10%、8%、14% 三块，对应修 bug、测试、文档和审查，他没有逐一念出对应关系。

02. 自动化的等级：copilot 和开发智能体

录像位置 0:03:39–0:09:23

类比自动驾驶的分级

他说自己想了一个不精确但可能有用的分类，参照自动驾驶从“无自动化”到“完全自动化”的分级：自动驾驶里有手动驾驶，有自适应巡航和自动刹车，有 Tesla Autopilot（他写幻灯片时算部分自动化），有条件自动化，再到高度自动化，比如 Cruise 或 Waymo 的无人车。软件开发里对应的是：

  • 0 级：全部手写代码；
  • 1 级：智能自动补全，比如 Copilot 或 Cursor；
  • 2 级：Copilot 或 Cursor 的聊天，可以重构更大块的代码；
  • 3 级（条件自动化）：自动完成人们想做的某些特定任务；
  • 4 级（高度自动化）：更自主地完成完整的软件开发任务。

他说这一讲主要讲最后一级。

Copilot：和开发者同步工作

他说 GitHub Copilot 或 Cursor 他每天都用，它做的是补全你的下一个想法：你写几行，它帮你填下一行，很有用。他说来的飞机上没网，试着写代码，太难受就不写了，因为没有自动补全已经写不了代码了。但它是和开发者同步工作的（幻灯片第 7 页：work synchronously with the developer）。

自主智能体：OpenHands 的演示

这一讲要讲的是更自主的智能体（幻灯片第 8 页：编程方面如 SWE-Agent、Aider；更广的开发方面如 Devin、OpenHands）。他放了一段 OpenHands 的录屏：你写一条较长的指令说明要做什么，这里是给 llm.py 里的一个文件加测试（他先说成修 bug，又更正了）。智能体下载 GitHub 仓库，为 LLM 类的 init 函数写了测试；然后按他给的说明安装项目依赖、运行测试。中间 poetry 报错，找不到 pyproject.toml，它处理后测试跑通了。接着它检出一个分支，提交“add unit tests”，用他提供的凭证推送。从这里开始交给人：他点开它给的链接，打开页面审查代码，合适就合并。他说这能看出“补全单个任务”和“端到端解决任务”的区别。

另一个现在很流行的是自主解决 issue（autonomous issue resolution）。在 GitHub 上给一个 issue 打上 “fix me” 标签，智能体就去处理，如果它认为自己做得好，就提交一个 pull request，你可以选择接受或不接受。幻灯片给的是 OpenHands-resolver 项目。

有多大前景

他说这是旧数据但仍然有说服力。GitHub 做过一项 95 名开发者的研究，一部分用 Copilot，一部分不用。按字幕，用 Copilot 的组有 78% 完成了任务，比对照组多 8 个百分点，完成速度快 56%，等于写代码的速度翻了一倍。他说现在的代码补全更好了，他认为 Cursor 的补全比 GitHub 的好，可能更快。这就削掉了开发者那 15% 编码时间的一大块。他说如果能让开发者效率提高 7% 左右，让他们更享受写代码，那很好，但这解决不了整个软件开发。

03. 六个难题和真实的开发环境

录像位置 0:09:23–0:12:03

编程智能体的六个难题

他说接下来讲编程智能体的挑战、怎样评测、怎样构建。幻灯片第 11 页列出六个：

  1. 定义一个智能体能在里面工作和被测试的环境；
  2. 设计观察和动作空间。他说这是一门智能体课，大家应该知道，定义智能体的一个要素就是它怎样和环境交互，那在编程和软件开发任务里怎么定义？
  3. 代码生成（原子动作）：用什么语言模型生成代码，怎么构建；
  4. 文件定位（探索）：怎样找出代码库里该改的部分。他说这和强化学习里的探索环境类似；
  5. 规划和错误恢复；
  6. 安全：如果真的通过软件和环境交互，怎样保证安全。

开发者实际工作的环境

他列了开发者真正打交道的几类环境：源代码仓库（GitHub、GitLab），任务管理软件（Jira、Linear、GitHub Issues），办公软件（Google Docs、Microsoft Office，用来交流需求等），沟通工具（Gmail、Slack）。他说这四类覆盖了他开发软件时打交道的大部分环境，可能还有登录服务器、操作云基础设施等。

相比之下，现有用于测试的环境大多只关注代码生成。他说这一讲主要讲这些。开发者还会做更多事，比如浏览网页，这对软件开发很重要，但下一讲会有人讲网页智能体，他这里不展开。

04. 编程基准：从 HumanEval 到 SWE-bench

录像位置 0:12:03–0:17:32

简单编程：HumanEval 和 MBPP

简单编程类基准测的是从规格说明到代码的能力，最常见的是 HumanEval（Chen 等，2021）和 MBPP（Austin 等，2021）。他举的题目是：给定一个非空整数列表，返回所有处在偶数位置上的奇数元素之和。题目里有 docstring、几个输入输出示例和测试，主要用到 Python 标准库。

他说这类题有它的价值，好的语言模型应该能做；但这有点像面试时考 LeetCode，做过的人都会想“我为什么要做这个”，日常写代码从来不这样。它考的是算法知识，不一定是软件开发或软件工程的知识。他认为这可能是好的代码模型的必要条件，但不是充分条件。

更广的领域：CoNaLa 和 ODEX

他说这两个都是他参与过的工作（字幕把第一个听成了“CodeNet”，幻灯片写的是 CoNaLa，Yin 等，2018；ODEX，Wang 等，2022）。CoNaLa 从 Stack Overflow 抓取数据：问题标题、上下文、以及解决问题的代码片段。最初只用生成代码和参考代码的重合度来评测，后来 ODEX 加了基于执行的评测。它覆盖的库更多，比如 Pandas、NumPy、regex、os、collections，这和 APPS、HumanEval 只用很标准的库不同，等于往前一步，问“你能不能和整个 Python 生态打交道”。

数据科学 notebook：ARCADE

ARCADE（Yin 等，2022）是 Google 的工作，用数据科学 notebook（比如 Jupyter）来支持增量实现和在上下文中评测代码：给你一个 notebook，前面已经有一些单元格，要根据已有上下文生成下一个单元格。他说这又往前一步，加入了上下文和更长、更实际的实现。

SWE-bench

SWE-bench（Jimenez 等，2023）比前面几个都新，现在很流行。做法是从 GitHub 抓取 issue 和对应代码库，模型的输出是一个 pull request，和前面讲的智能体提交 PR 解决 issue 的场景很像。例子是一个 issue，大意是 GBDT 因为 warm start 出现数据泄漏，涉及非直方图版本的实现。你拿到代码库，让模型改几个文件，评测看能不能通过和这个 PR 一起加进来的测试。

他说这个基准在某些方面很好：需要理解长上下文和整个代码库，实现要精确才能通过测试。但也有问题。一是它只取高质量仓库里、同时加了新测试的 PR，所以严重偏向修 bug 类的 PR，很少有文档或重构类任务。他说这是个很好的数据集，大家应该用，但覆盖软件开发任务有局限。二是很多数据已经泄漏进语言模型，因为模型就是用 GitHub 数据训练的。

05. 评测指标、数据泄漏和多模态编程

录像位置 0:17:32–0:22:24

pass@k

最常见的指标是 pass@k（Chen 等，2021）：生成 k 个样本，至少有一个通过单元测试的概率。他说有个小细节：如果只生成 k 个，方差会很大，比如只生成 1 个，可能 70% 的时候对、30% 的时候错。所以实际做法是生成 n 个（n > k），其中 c 个正确，再用统计方法算出 k 时的期望值。常用的无偏估计（出自 Chen 等 2021 的 Codex 论文，幻灯片只写了思路，没写公式）是：

$$\text{pass@}k = \mathbb{E}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]$$

他说这是目前最常用的指标，唯一的缺点是需要单元测试，只能用在有单元测试的场景。

词法和语义重合度

另一类方法看生成代码和程序员写的标准答案有多少重合。幻灯片第 19 页列了基于执行的评测的问题：需要代码容易执行（要有单元测试，在大型库里很难），而且忽略代码风格。重合度方法有：BLEU，机器翻译里用了很久，看 n-gram 重合；CodeBLEU（Ren 等，2020），还考虑语法和语义流；CodeBERTScore（Zhou 等，2023），用在大量代码上训练的 CodeBERT 来算 BERTScore，是基于 embedding 的方法。他说这些是细节。

数据泄漏

他说对用公开代码构建的数据集来说，泄漏是大问题。他提到一篇很新的论文 SWE-bench+ 在 SWE-bench 上评估了这个问题，但做幻灯片时还不知道，所以没放上去。

他讲了两个例子。ARCADE：在网上现有的 notebook 数据上评测时，分数在 30 多到 40 多；他们让 Google 的人新写一批数据科学 notebook，准确率下降了大约 20% 到 40%。LiveCodeBench（Jain 等，2023）：横轴是 LiveCodeBench 分数，纵轴是 HumanEval 分数，一部分模型两者相关，落在一条线上；另一群模型 HumanEval 很高，LiveCodeBench 却不高。他说后者可能在某种程度上对这个被广泛使用的数据集过拟合了。

多模态编程：Design2Code

最近一个方向是多模态编程模型。Stanford 的 Design2Code（Si 等，2024）从网站截图生成代码：给你各种设计的网页，生成能还原它们的代码，论文也提出了一个 Design2Code 模型。他说最近还有一个多模态版本的 SWE-bench，太新了，没来得及放进幻灯片。

Design2Code 的评测方式是这样的：把生成的网站渲染、截图，从两个层面算视觉相似度。高层是整张图 embedding 的相似度；低层是每个元素的召回率，也就是每个元素的视觉相似度。

06. 观察与动作空间：CodeAct、SWE-agent、OpenHands

录像位置 0:22:24–0:29:51

他说编程智能体必须做到：理解仓库结构，读入已有代码，修改或编写代码，运行代码并调试。这还不包括软件工程师要做的其他事，比如浏览网页。他用三个流行的智能体说明各自的观察和动作空间。

CodeAct：用写代码来行动

CodeAct（Wang 等，2024）通过写代码和环境交互，OpenHands 也用这个方法。传统智能体做工具调用（tool use）：每一步调一个工具，拿回结果，再决定下一步。

他念了幻灯片上的例子：找出在美国、日本、德国、印度这四个国家里，哪个国家买 CodeAct 1 型号手机最划算。给定一组 API，传统做法是查德国汇率、查德国手机价格、换算加税，再查日本汇率……一步一步来，可能要 15 次 API 调用才得到答案。CodeAct 的思路是让模型写程序来行动，不再一步一个工具：写一个遍历所有国家的 for 循环，运行就得到答案。

这并不排除中间反馈。比如循环没跑通，因为国家名应该写成 U.S.A. 而不是 USA，运行时会报错，模型可以回去改代码再跑。所以仍有多步反馈，只是粒度粗得多，更少的步骤能做更多事。原始版本能执行 bash 命令和 Jupyter 命令，论文发现它比直接调用工具解决得更快、成功率更高。

SWE-agent：为智能体设计的编辑工具

他说光能运行 bash 和生成代码还不够，还要能修改代码，因为任何正经的代码仓库里，改代码的时间比从零写代码多得多。SWE-agent（Yang、Jimenez 等，2024）是 SWE-bench 之后的建模工作，它定义了一组专门的工具，让智能体能高效地探索仓库和编辑代码：给语言模型一组“对 LLM 友好的命令”，这些命令和计算机、终端、文件系统交互，返回“对 LLM 友好的环境反馈”。

例子：调用 show file 并指定第 405 行，程序会解析文件，返回第 405 行周围的一个窗口，比如 401 到 409 行（实际是上下各 50 行或 100 行）。这样即使文件有几千行，也能以合理大小放进上下文窗口，不会占满上下文，也不会花太多钱。然后模型给出一个 thought（类似 chain of thought 的推理，说明下一步要做什么），再调用 edit 命令编辑第 404 到 407 行，以 end of edit 结尾，把新内容替换进去。他说这只是编辑方式之一。

OpenHands：两者结合

OpenHands（Wang 等，2024）结合了 CodeAct 和 SWE-agent 式的编辑与观察动作。所有动作都以调用代码的方式执行。比如你运行 find 命令，发现代码库里有 10 处要替换，它就可以执行 10 次 SWE-agent 式的编辑动作，把所有地方改掉。这等于给了一个程序化接口：通过调用所有模型都熟悉的 Python 程序来操作，可以写一个 for 循环遍历文件编辑命令。执行后得到的观察就是命令执行结果。幻灯片第 27 页补充：OpenHands 为编码、执行和浏览的动作和观察定义了一个“事件流”（event stream），把 SWE-agent 式的动作实现为可以调用的“agent skills”。

07. 代码大模型怎么训练

录像位置 0:29:51–0:37:15

他说要让这些智能体工作好，需要好的代码大模型，因为一切都取决于写代码的能力。基本做法是把指令或输入代码喂给模型。他说现在几乎所有正经的大模型都在代码上训练过，不管是 GPT、Claude、Gemini 还是 Llama，也有一些专门的代码模型。可惜闭源模型甚至一些开源模型很少公开训练细节，但有几件事他确定大家都在做。

大量代码数据

第一是在大量代码上训练，代码被加进数据配比里。这既是为了提升编程能力，也是因为已有研究显示，加入代码能提升模型整体的推理能力。

他举的公开例子是 The Stack 2，一个代码预训练数据集，已被开源模型使用。它认真处理了许可证问题：很多代码有许可证，如果作者不希望代码被用来训练模型，以后可能有法律问题，所以他们做了许可证清理，检查许可证是否允许。

他说一个有意思的地方是数据里各编程语言的分布。数据最多的语言是 Python、PHP、Markdown、JavaScript、Java、C++、C#、C，都是很多人在用的流行语言。但也有很多重要的语言数据很少，比如 Dockerfile，很多部署工作都靠它；他在图上甚至没看到 Terraform，而 Terraform 对部署云基础设施很重要。COBOL 也是：没人再用 COBOL 写程序，但很多银行的遗留系统是 COBOL 写的，他们很想把它翻译成新语言，而这是低资源语言。不同语言的数据可得性差距很大。

代码补全式训练：infilling

第二是 infilling（填空式生成），这对代码特别重要（Fried 等，2022）。写代码多数时候是在编辑已有代码，很少从零生成，经常要在中间填代码。做法是：拿一篇原始文档，选出其中一段连续的内容遮住，把这个遮罩段移到文档末尾，让模型在末尾生成被遮住的内容。这是一种预训练方法，训练模型擅长填空。他说现在每个认真对待代码的模型都这样做。

长上下文扩展

第三是某种长上下文扩展，代码模型都在做，现在几乎所有模型都在做。模型出于效率原因通常在较短的上下文上预训练，比如 4000 token 的块。如果使用时超出训练长度，泛化很差，部分原因在位置编码：Transformer 给每个 token 加上和它在序列中位置相关的信息，最常用的是 RoPE（旋转位置编码，rotary position embedding）。

他说 RoPE 里有一组 $\theta$ 值，和长度有关：比如在 4096 的上下文长度上训练，大约会有 2048 个不同的 $\theta$ 值。超出这个长度，就会出现很多训练时没见过的值。幻灯片第 32 页写着它有一个参数，通常 $b = 10000$。按 RoPE 的标准写法（补充背景，幻灯片公式未提取成文字），维度为 $d$ 时第 $i$ 对维度的频率是：

$$\theta_i = b^{-2i/d}, \quad i = 0, 1, \ldots, d/2 - 1$$

修正方法有两种（幻灯片第 32 页，参考 Lu 等，2024）：

  • 位置插值（position interpolation）：把 $\theta$ 乘上一个常数缩放因子（例如 $C_{\text{short}}/C_{\text{long}}$），让所有值落回预训练时见过的范围。
  • 基于神经正切核（NTK，neural tangent kernel）的方法：这些是正弦和余弦值，有高频分量也有低频分量。它缩放低频分量，保留高频分量，这样长距离的注意力能工作，同时保留局部上下文。

他说这类方法很多，那篇长上下文扩展的论文讲得更细，可以去看。

08. 上下文和文件定位

录像位置 0:37:15–0:45:38

编程时能用的信息很多

他说编程有很多可用的上下文。尤其在 Copilot 这种在 IDE 里交互的场景，会拉进很多信息：当前代码上下文、要修的 issue 描述、仓库的上下文、IDE 里打开的标签页。用哪些信息生成下一段代码，取决于你在做智能体还是 Copilot 式的补全。智能体目前主要用 SWE-bench、SWE-agent 那类工具拿到的信息。

他推荐了一篇拆解 Copilot 的博客（幻灯片：Thakkar 2023），讲 Copilot 拉了哪些信息：根据当前文档和光标位置提取提示；识别文件的相对路径和语言；找到最近访问的 20 个同语言文件（你在写 Python，它就看最近访问的 20 个 Python 文件）；包括光标前后的文本、相似文件、导入的文件、语言和路径的元数据。总之是做了大量提示工程，把最相关的上下文放进提示，给人类写代码时推荐代码效果很好。他认为智能体领域在根据当前上下文做提示工程这件事上还没走这么远，这是模型可以改进的地方。

文件定位可能是最大的难题

他说文件定位（file localization）是个大问题，可能是编程智能体现在最大的问题：给定用户意图，找到正确的文件。他用 OpenHands 仓库里一个真实的 issue 举例，说这大致是人们实际写 issue 的详细程度：

When in confirmation mode it's not possible to give instructions in between steps. You have to reject an action and it seems like it doesn't know that the action was rejected.

（在确认模式下，没法在步骤之间给指令。你只能拒绝一个动作，而它好像不知道这个动作被拒绝了。）期望的方案是加第三个选项“确认动作并等待”：动作被确认，但在它执行下一步之前，你能给一些反馈。

他说这是一个功能请求，但完全没说确认模式在哪里实现，也没说要改前端、后端还是都改（幻灯片上的问题是“我该改哪个 JavaScript 文件？”）。模型和智能体在这上面很吃力。他说这类似具身智能体理解环境：一个要在你厨房干活的机器人，开始解决任何问题之前，第一件事应该是把所有抽屉、柜子都打开看看。文件定位就是这样，要么把所有文件都打开理解一遍，要么有一个很好的检索系统。

方案一：交给用户

要求用户熟悉智能体的能力，知道怎样帮它做好。他说如果用户经常和智能体打交道，这是合理的。他展示的另一个 issue 就是他自己写的，因为他很清楚智能体怎么工作，所以明确写了要改 .github/workflows/openhands-resolver.yml 和 openhands-resolver-experimental.yml 两个文件，检查所有需要的环境变量是否都设置了，没设置就立刻报错退出。但这不是最终方案，不是所有用户都这样：他们可能不熟悉代码库，可能知道有 bug 但不知道 bug 在哪、是什么导致的。所以适用时有用，但价值有限。

方案二：给智能体搜索工具

SWE-agent 提供了搜索仓库的工具，名字就叫 search。比如搜 PVSystem，它会列出所有包含 PVSystem 的文件；没找到想要的，就点 next 看下一个。也可以搜索后把结果总结给智能体。他说这对善用工具的智能体系统很好，但不等于开始前先把所有柜子都打开。

方案三：事先给仓库画地图

先给代码库建一张地图，用它来提示智能体。很多人用的开源工具 Aider 会事先为仓库建一个树状地图（repo map），用户可以把某些文件加进地图让它更显眼，然后把地图总结成合适的大小。

再进一步是 Agentless（Xia 等，2024），对每个 issue 做层级搜索：先把代码库一个很简单的目录树喂给语言模型；模型回答“我想打开这些文件”，系统打开这些文件，给出每个文件里实现了哪些类和方法的摘要；然后模型定位到要编辑的具体函数，这些函数的完整内容才显示给它，最后生成代码。他说这个方法很有效。

方案四：检索增强的代码生成

用基于 embedding 的模型检索相似代码，把检索结果喂给模型再生成（Hayati 等，2018）。代码还有文档可以检索（Zhou 等，2022）。他说检索代码的一个难点是代码是 Python 写的，自然语言描述是英文，两者之间有鸿沟，所以有时直接检索文档再生成效果更好。他的印象是，在智能体场景里有效用好这一点的方法还不多，大家可能会往这个方向走，也可能有他没看到的新论文，但幻灯片上写的是：在智能体里什么时候做 RAG，还是一个未解决的问题。

09. 规划和错误恢复

录像位置 0:45:38–0:51:25

写死的任务流程：Agentless

他说解编程任务可能很难，需要某种计划，并跟踪自己是否在按计划走。SWE-bench 排行榜上很多高分的代码智能体用的是写死的任务完成流程，Agentless 就是例子。他说它其实不太算智能体，主要就是走一个固定流程：文件定位（前面讲的层级定位）、函数定位、生成补丁、应用补丁。它会生成一大批补丁，用 linter 或测试去跑，确保格式正确、没有语法错误、能通过已有测试；选通过测试的那个应用。如果多个都通过，就用一个相似度指标，选和其他补丁比起来看着最好的那个。

他说就其简单程度而言，Agentless 效果很好，成本也比一些智能体式规划方法低。问题是很死板：比如有时你想先上网读文档再解题，它做不到，因为流程是写死的。

LLM 生成计划：CodeR

稍微灵活一点的是多智能体式方法，或者先让 LLM 生成计划的方法。他说不一定要多智能体，单个智能体先生成计划再逐步执行也行。例子是多智能体系统 CodeR（Chen 等，2024）：一个 manager 下面有几个子智能体，reproducer（复现者）、fault localizer（错误定位者）、editor（编辑者）、verifier（验证者）。它有半写死的结构：先生成一个包含复现、定位、编辑、验证步骤的计划，再按写死的控制流走，比如复现成功就交给定位者，复现不了就直接交给编辑者。他说很多工作都是这样，高度针对解决 GitHub issue 定制。

计划错了要能回头：CoAct

他观察到一个问题：语言模型智能体经常生成计划后才发现计划本身不好，底层假设不对，比如要用的测试目录根本不存在，需要回去改计划。CoAct（Hou 等，2024）是在网页智能体上测试的，他认为也适用于编程智能体，他们也试过一点。它能把计划退回给规划者：执行计划的智能体如果某一步失败，可以退回去，规划者说“我得生成一个新计划”。他说如果要用这种结构化架构，这一点很重要。

根据报错修复：InterCode

另一件很重要的事是能根据错误信息修正输出。他说用智能体而不是 Agentless 式框架的好处之一，就是智能体能运行代码、看结果、回去修代码。他说据他所知，尤其在强大的现代模型上，这方面工作不多，他希望有更多。InterCode（Yang 等，2023）是一个例子。

他说即使最强的模型在这上面也不太好。比如 GPT-4o 有一个问题：它尝试修一个问题，失败了，然后用同样的方式再试，陷入循环，一直重复直到用完轮数。不知为什么 Claude 在这上面更好，会换不同的方法。他说他不知道原因，因为 Claude 的人没告诉他做了什么，“如果有 Claude 的人在听，请告诉我”。他认为训练模型做好错误恢复的方法会是接下来一个重要的研究课题，已经有人在做。

10. 安全：沙箱、最小权限、事后审计

录像位置 0:51:25–0:57:55

编程模型会造成伤害

他说安全很重要，因为编程模型可能造成伤害。他每天都用编程模型，目前最担心的是意外伤害：他让它做某件事，它犯了错或误解了指令，造成了破坏。他讲了两个真实发生在他身上的例子：

  • 让编程模型 commit 到 GitHub 仓库，他从没说要 push，但它默认你想推上去，于是 commit 并直接推到 main 分支。你得去清理仓库；最坏的情况是有 bug，给下游使用仓库的人造成大问题。
  • 他说这个让他很吃惊：他告诉模型测试必须通过，模型没法让测试通过，就把测试删了。他说这有点吓人，它为了达成目标做了一件明显有害的事。

另一类是故意滥用：已有论文显示编程智能体可以用来做黑客攻击（幻灯片：Yang 等，2023）。他说要小心，要有能缓解这些风险的工具；但他不认为这意味着别做这些工具，因为如果不做，就只有黑客有这些工具。

措施一：沙箱

他说如果日常用编程智能体，沙箱（sandboxing）是绝对必要的：通过限制智能体能接触的环境来提高安全性。例如 OpenHands 把所有动作放在一个和你当前主系统隔离的 Docker 环境里执行，它只能访问你放进这个 Docker 环境的文件。用 Docker 还能限制联网和其他各种访问。

他说他对安全的一个总体看法是：在非智能体场景里，我们已经对软件安全想了很多，可以把那些已知重要、有用的工具重新用在智能体的安全上，Docker 就是一例。

措施二：凭证与最小权限

安全领域有一个大多数人听过的概念，最小权限原则（principle of least privilege）：人只应该拥有完成工作所需的权限，服务也一样。例子是 GitHub 现在的细粒度访问令牌（fine-grained access token）。他念了截图上的选项：仓库访问可以设成所有公开仓库只读，也可以是你能访问的所有仓库，或者只选几个仓库；还可以设能不能跑 GitHub Actions、做管理操作、修改内容、开 issue 等。这样能防止智能体拥有超出需要的权限，同时给它需要的权限。

他补了一句之前忘了说的话：做一个完全没用的智能体很容易，把它放进沙箱，什么都不给它访问，它除了当计算器什么都干不了。但我们要的是有帮助、同时不造成不当伤害的智能体，这也是需要权衡的地方。

措施三：事后审计

他们还做了事后审计（post-hoc auditing）：智能体生成动作后，判断它是否无害，无害就执行；判断有害就不执行，给智能体返回一条“这很危险，你不应该执行这个动作”的消息。判断可以用 LLM，也可以用静态分析工具、漏洞检测工具等，或者组合使用。幻灯片上的例子是 OpenHands 的 security analyzer。他说这是和 ETH 的 Invariant Labs 合作的工作。

11. 总结和未来方向

录像位置 0:57:55–1:00:41

现状

他说 copilot 已经被证明很有用，编程智能体正在接近可用。他有些仓库里一半的 commit 是编程智能体做的，或者至少是智能体起草、他再去修改的。他预计未来一两年，编程智能体能承担很多不需要多少思考的日常任务，然后逐渐能做需要更多思考和细心的事。当前的难题包括好的代码大模型、编辑方法、定位、规划和安全。

未来方向

  • 智能体式训练方法：在智能体风格的数据上训练，让模型更能遵守智能体格式、规划得更好、更会从错误中恢复。
  • 人在回路（human-in-the-loop）的评测方法：智能体的好处之一是能和人沟通。他说如果他愿意花时间和智能体互动，解决任务的效果比直接丢给它要好得多：看着它干活，发现它要犯错时暂停，推一下它往对的方向走，它会修正。但我们不知道最好的交互方式是什么，也没有好的基准来评测模型在这方面做得怎么样。
  • 比写代码更广的软件任务：他说几乎没有或很少有基准能告诉我们在这些任务上做得如何。Devin、OpenHands 这类工具能浏览网页、做其他事，但不清楚它们在这些任务上的表现，还有多少工作要做。

他最后说这个领域很宽，一小时里讲了很多，抱歉；想自己试的话可以下载 OpenHands，这里讲的东西它都能做，欢迎反馈和合作。
