第一部分：Chi Wang，智能体框架与 AutoGen

他的议程分两块：智能体式 AI 框架的一般问题，然后深入 AutoGen。贯穿两块的两个问题是：未来的 AI 应用是什么样的？怎样让每个开发者都能做出来？

01. 未来的 AI 应用是智能体式的

录像位置 0:00:00–0:07:02

从生成到执行

他说大约从 2022 年开始，人们看到了语言模型和其他生成模型的能力，生成文本和图像的质量比他读博时研究的主题模型等老一代生成技术好得多，已经过了一道门槛，可以考虑更有创造性的应用和更高层次的 AI 能力。从去年年初开始，他们思考怎样最好地利用生成式 AI，下了不少技术赌注，最重要的一个是：未来的 AI 应用会是智能体式的（agentic）。智能体会成为人和数字世界交互的新方式，代表人去执行越来越复杂的任务。幻灯片上的对比是：生成式（generative）是生成文本和图像这类内容；智能体式（agentic）是代表人执行复杂任务。

他说当时很多人怀疑智能体式 AI 是否可行，但证据越来越多，比如今年早些时候 Berkeley 参与发表的文章（Zaharia et al. 2024, The Shift from Models to Compound AI Systems）指出，越来越多的 AI 成果从使用单个语言模型转向构建复合 AI 系统（compound AI systems，由多个模型调用、检索器、工具等组件组合而成的系统），这和他们的判断类似。

智能体的概念不新，个人助理、自主机器人、游戏智能体早就有。新的是：有了生成式 AI，这些老应用更容易做，也做得更强；同时出现了以前想象不到的新应用，比如能自动做科学发现的科学智能体、自动浏览网页的网页智能体、能从零开发软件的软件智能体。

一个演示

他播放了当天早上从一家创业公司拿到的演示视频（公司名字幕不清）：让 AI 做一个网站，从 Hugging Face 抓取模型并自动下载。收到请求后，AI 自动分析任务、查找信息、安装依赖。它用了多智能体框架，不同角色的智能体分工完成多步任务，智能体之间的推理和对话都是自动的，用的是语言模型加工具。最后它编译出了网站，列出很多模型，用户可以搜索、导出模型数据、下载。

然后他们故意删掉生成文件里一行关键代码，让 AI 再跑一次同样的任务。这次出现了报错，提示缺少脚本。几步之内，AI 就修正了错误，补上了刚删掉的那一行，完成任务。他说这显示了智能体自我修复、自我恢复的能力，将来我们可能会以完全不同的方式开发软件。

三个好处

  • 更自然的界面：用自然语言告诉 AI 你要什么，比如要一个满足某些要求的网站，再用自然语言迭代。
  • 更强的能力：给智能体更多能力，它就能在很少人工监督的情况下完成更复杂的任务，这对自动化价值很大。
  • 一种有用的软件架构：他说这一点讨论得少，但他特别强调。多个智能体互相协作，可以用递归的方式完成更多任务，从而用完全不同的方式构建软件。幻灯片上写的是“直观的编程范式”。

02. 例子：三个智能体做供应链优化问答

录像位置 0:07:02–0:12:10

他用一个例子说明这些好处：一个云上的供应链优化应用，由他以前在 Microsoft Research 的同事开发。用户比如咖啡店老板，可以问“如果改变运输约束，我的运营成本会怎样变化？”这类问题。ChatGPT 答不了，因为 AI 需要理解用户特定的数据、约束，甚至要用优化工具。

他们用 AutoGen 搭了三个智能体：Commander（指挥）、Writer（写代码）、Safeguard（安全检查）。流程是：

  1. 用户提问：“如果禁止从供应商 1 运货到烘焙厂 2，会怎样？”
  2. Commander 收到问题，先挂起当前对话，发起一个它和 Writer 之间的嵌套对话。Writer 以语言模型为后端，理解问题，写出能回答它的代码，这里是一段往优化问题里加一条约束的 Python 代码，返回给 Commander。
  3. Commander 看到代码，再挂起和 Writer 的对话，发起它和 Safeguard 之间的对话。Safeguard 也用语言模型，检查代码是否安全。这里结论是安全。
  4. Commander 结束和 Safeguard 的对话，执行代码：用更新后的约束跑优化程序，得到新结果。
  5. Commander 回到和 Writer 的对话，把执行结果发给 Writer，Writer 据此写出最终答案。

这是最顺利的一条路径。一般情况下可能出各种问题：代码不安全，Commander 就不执行；执行报错，Commander 把错误信息发回 Writer，Writer 重写代码。复杂任务可能要来回多轮，幻灯片上写的是“重复，直到回答了用户问题或超时”。终端用户看到的仍然很简单，不知道后台有多个智能体在跑，也不需要懂编程或优化，提一个问题，得到自然语言的回答。

程序怎么写

从编程角度看，这种程序的写法也和传统程序不同。第一步，创建几个智能体，每个一行：

writer = Writer("writer", llm_config=llm_config)
safeguard = autogen.AssistantAgent("safeguard", llm_config=llm_config)
commander = Commander("commander", llm_config=llm_config)
user = autogen.UserProxyAgent("user")

第二步，定义智能体之间的交互模式。这里给 Commander 注册两个嵌套对话：每个嵌套对话要定义参与的智能体、谁发谁收、对话结束后怎样做总结（summary_method）；被 user 触发时找 writer，被 writer 触发时找 safeguard，safeguard 那段只对话一轮（max_turns 为 1）：

writer_chat_queue = [{"recipient": writer, "message": writer_init_messsage, "summary_method": writer_success_summary}]
safeguard_chat_queue = [{"recipient": safeguard, "message": safeguard_init_message, "max_turns": 1, "summary_method": safeguard_summary}]
commander.register_nested_chats(safeguard_chat_queue, trigger="writer")
commander.register_nested_chats(writer_chat_queue, trigger="user")

第三步，由用户代理智能体向 Commander 发起对话，发出初始任务，之后的步骤都自动进行，框架负责所有步骤和嵌套对话，最后返回结果：

chat_res = user.initiate_chat(commander, message="What if we prohibit shipping from supplier 1 to roastery 2?")

03. 智能体编程的好处

录像位置 0:12:10–0:14:57

处理更复杂的任务，提高回答质量

  • 多个智能体互相对话，是在交互中逐步改进的自然方式。
  • 分而治之：把复杂任务拆成小任务，每一步的质量更高。
  • 可以定义不依赖模型的专用智能体，用模型以外的知识做 grounding 或验证，弥补模型本身的弱点。

幻灯片右边是一组实验：把任务拆成 Writer 和 Safeguard 两个智能体，对比把所有交互放进单个智能体，看安全检查这一项的表现。图上的数字：

设置F1Recall（召回率）
多智能体 GPT-496%98%
单智能体 GPT-488%78%
多智能体 GPT-3.583%72%
单智能体 GPT-3.548%32%

他说 GPT-4 上多智能体设置的召回率比单智能体高 20%，GPT-3.5 上差距更大。这说明在某些场景下，拆分任务、让每个智能体做相对简单的事，比让一个智能体一次做太多事更好。这取决于任务复杂度和模型能力：任务越复杂、模型越弱，越需要多智能体工作流。

更容易理解、维护和扩展

  • 模块化组合：比如其他智能体都不变，只想改 Safeguard 的行为，从用语言模型改成用工具或改成人来检查，模块化设计下很容易。
  • 人可以自然地参与：人可以接管系统里任何一个智能体，通过自然对话和其他智能体交互，不需要改变交互方式。
  • 这些好处加在一起，使智能体编程有潜力支持快速、有创意的实验，做出新颖的应用。

04. 一个智能体框架要满足什么

录像位置 0:14:57–0:20:39

他说要设计一个兑现这些承诺的框架并不容易，幻灯片上列了四条要求：直观、统一的智能体抽象；灵活的多智能体编排；有效实现各种智能体设计模式；支持多样的应用需求。

统一的抽象

构建复合 AI 系统需要各种实体：不同角色的人、工具、不同厂商的语言模型。如果能用一个概念统一思考它们，推理整个系统就容易得多。一个直接的好处是可以用多智能体编排来构建任意复杂的复合 AI 系统。

编排里的取舍

不同应用对智能体交互模式的需求不同，有很多取舍：

  • 静态还是动态：有时开发者想要静态工作流，明确规定每一步和智能体的顺序；有时很难预知智能体要处理的所有情况，就要给智能体更多自主权，让它们动态生成工作流。
  • 自然语言还是编程语言：有时想用自然语言告诉智能体做什么，有时要用编程语言做更精确的控制。这是灵活性和可控性之间的取舍。
  • 上下文共享还是隔离：什么时候让智能体共享上下文，什么时候隔离开，比如分层结构。
  • 合作还是竞争：什么时候让智能体合作，什么时候让它们竞争以更好地完成任务。
  • 集中还是分散，自动化还是人工干预。

设计模式

随着大家做的智能体越来越多，涌现出很多好的设计模式，框架要能支持：对话；提示和推理技巧，比如 ReAct、Reflection、Chain-of-Thought、Tree of Thoughts，以及更新的基于蒙特卡洛树搜索的方法；工具使用；规划；整合多个模型、多种模态和记忆。

从对话出发

要求这么多，很难一开始就全部考虑到。但从第一性原理想，能不能从一个设计点出发，推导出其他所有模式？他问全场，在这些设计模式里，能不能只用其中一个来容纳所有其他的？他说不同的人会选不同的起点，他个人的选择是对话。他读大学时体会到，对话是学习和证明定理时取得进展的好办法（字幕不清，大意如此）；看到 ChatGPT 的能力后，他马上联想到这段经历，决定试试把多智能体对话作为核心机制，看能走多远。结果是能走得很远。

几个框架的对比

  • AutoGen：基于多智能体对话编程，全面、灵活，能整合上面说的各种设计模式，也能和其他框架集成（幻灯片列了 OpenAI Assistant、LlamaIndex、LangChain）。
  • 基于 LangChain 的框架：LangGraph 侧重提供基于图的控制流；CrewAI 侧重提供高层、静态的智能体任务工作流。
  • LlamaIndex 由后半段的 Jerry Liu 介绍。

05. AutoGen：定义智能体，让它们对话

录像位置 0:20:39–0:28:22

简史

AutoGen 是一个智能体式 AI 的编程框架。它最初在开源项目 FLAML 里开发（2022 年 11 月），FLAML 是做自动机器学习和超参数调优的。2023 年 3 月做出最初原型，那时只是一个灵活的多智能体对话框架，带代码和函数执行能力；2023 年 8 月发表第一版研究论文；2023 年 10 月拆成独立的 GitHub 仓库，当月登上 GitHub 趋势榜榜首；2024 年 8 月成立独立的 GitHub 组织 AutoGen-AI，采用开放治理结构，欢迎所有人参与贡献。他还提到，论文获得 ICLR 2024 LLM Agents workshop 的最佳论文，他们在 DeepLearning.AI 上开了一门用 AutoGen 讲智能体设计模式的课。幻灯片上的社区数字：每月 20 万次下载，3 万 GitHub star，Discord 2 万人，4 千 fork，2023 年 12 月入选 The Sequence 的“5 篇最喜欢的 AI 论文”，Forbes、The Economist、WIRED 等有报道。

两个核心概念

AutoGen 功能很多，但他只讲最核心的概念，说这是理解其他所有模式的关键。目标是让开发者用两步来理解一个复杂工作流：第一步定义智能体，第二步让它们对话。对应两个概念：

  • 可对话智能体（conversable agent）：AutoGen 的智能体概念很通用，可以抽象各种实体。后端可以是语言模型、工具或人的输入，也可以混合多种。用多智能体对话模式，还可以让一个智能体内部包含其他智能体，进行内部对话，再包装成一个接口和外面的智能体对话。这样可以把多个对话嵌套在一个智能体里，递归地构建越来越复杂的智能体。
  • 对话编程（conversation programming）：对话模式包括顺序对话（sequential chats）、嵌套对话（nested chat）和群聊（group chat）等。

两个智能体的反思

最简单的是两个智能体对话。即使这么简单，也能实现反思（reflection）这类高级推理：比如一个 Writer 写博客文章，另一个 Critic 智能体提修改建议，两者反复迭代，提高文章质量。

嵌套对话：更高级的反思

如果觉得不够好，可以用嵌套对话加入更高级的推理。比如 Critic 不再是单个语言模型，而是一个嵌套对话，里面是多步的顺序对话：先把文章发给 SEO 审稿人，再发给法律审稿人、伦理审稿人等，最后一个元审稿人（meta reviewer）汇总各方面的意见，给出最终评论。从 Writer 的角度看，它还是在和一个 Critic 对话，但 Critic 底下用了好几个智能体。他说这说明可以用嵌套对话、通过对话来扩展智能体的能力。

用对话实现工具使用：对话式国际象棋

例子是让两个 AI 一边下国际象棋一边聊天、互相调侃。如果直接让两个语言模型智能体下棋，它们经常出错，走出不合法的棋步，棋局根本没法看。解决办法是加第三个智能体：棋盘智能体。它是基于工具的智能体，用一个 Python 国际象棋库管理棋盘，并把工具提供给语言模型智能体。这样语言模型只能走合法的棋步，否则要反复修改直到合法，棋局就能顺利进行。这里也是用嵌套对话：以语言模型为后端的“工具提议”智能体，和以工具为后端的“执行”智能体对话，完成工具调用。

群聊：复杂任务的规划和求解

更动态的方式是群聊。用户只需要定义不同角色的智能体，把它们放进一个群聊，它们会根据任务进展自动决定下一个由谁发言。有一个群聊管理者（group chat manager）监控进度、选择发言人。还可以加约束或有限状态机式的转移逻辑来规定发言顺序，不必定得很死，比如“A 发言后只能 B 或 C 发言，其他人不行”。这样仍有一部分决定由语言模型做出，保留了自主性，但选择被限定在一定范围内。还可以加转移逻辑告诉智能体：遇到某种情况走这条路，否则走那条路。这些都可以用自然语言或编程语言来写。

他说还有很多其他对话模式和应用，网站上的 notebook 示例都打了标签，可以搜索，比如搜“怎样把 AutoGen 和 LlamaIndex 集成”就能找到相应示例。论文里只展示了几个用简单对话模式的例子，但他看到开发者用这些积木搭出了各种复杂任务。

06. 社区用例和研究方向：AutoBuild

录像位置 0:28:22–0:36:35

社区里的应用领域

他展示了社区用例的分类：排在前两位的是软件开发和智能体平台，然后是研究、数据处理、游戏，以及长尾的网页浏览、金融、医疗、教育，还有图上没列的区块链。

  • 科学与工程：MIT 的 Markus Buehler 教授在蛋白质设计、材料设计等多个科学领域用 AutoGen 搭建智能体团队，模拟科学或工程团队的工作，从收集数据、生成假设到做实验、验证假设。他们最近还做了一个用知识图谱对任意科学领域做推理的工作（字幕里听起来是 SciAgents），智能体团队有多种角色，从理解本体（ontology）开始，经过多个“科学家”和“评论者”角色，生成各种概念和可能的假设，再选出最好的。他认为将来可能加速科学发现，很快也许会有 AI 设计的药物、建筑或新合金、新材料。
  • 网页智能体：创业公司 Emergence AI 用 AutoGen 做了 Agent E，一个分层的智能体团队，能在网页上做复杂任务，比如自动订机票、自动替医疗诊所填表。它有规划智能体和网页浏览智能体，对 HTML DOM 有更深的理解。它没用任何多模态模型，只用 HTML 内容、不用图像和视觉模型，就在 WebVoyager 基准上达到了当时最好的成绩，超过了之前用多模态模型的方法。他说总体成功率只有 73%，还有很大提升空间，结合多模态模型和更多智能体式工作流可能做得更高，但这项工作里有一些很好的基础设计原则可以学习。
  • 建筑：一家做建筑的公司（幻灯片上是 Terrascape AI 的联合创始人兼 CEO Medo Eldin）用 AutoGen 帮助没有专业知识的用户完成建筑项目。幻灯片上引用他们的话：AutoGen 让他们能快速探索多种智能体配置，大规模做实验。

他说几乎每个垂直行业都有企业客户感兴趣（幻灯片上列了会计、航空、生物技术、咨询、建筑、能源、金融、政府、医疗、制造、零售、电信等），使用者和贡献者来自世界各地的大学、机构和公司，也包括 Berkeley 学生做的 MemGPT（字幕记作 MGBT），它也和 AutoGen 做了集成。

正在进行的方向

幻灯片把进展分成三类：

  • 评估：做基于智能体的评估工具（例子：AgentEval、AutoDefense、可观测性），帮助开发者了解应用和智能体效果如何。这很难，因为生成的文本太多，很难弄清到底发生了什么。用智能体可以根据应用和任务自动提出成功标准，再给每个维度打分。
  • 学习、教学、优化：把评估的思路延伸，把反馈交给智能体本身，做基于智能体的优化、学习或教学（例子：AgentOptimizer、EcoAssistant、Learn to Cooperate）。
  • 接口：继续改进编程接口，降低编程门槛（例子：AutoBuild、Composable Actor Platform）。

AutoBuild

他特别讲了让他兴奋的一项研究 AutoBuild。很多开发者的一个疑问是：我该用什么样的多智能体工作流最有效？该为任务创建哪些智能体？AutoBuild 是初步尝试：

  1. 用户给出一个描述高层需求的任务，系统自动建议不同角色的智能体。
  2. 把这些智能体放进群聊来解决任务。
  3. 遇到新的、更具体的任务，可以复用已经创建的智能体团队，用户不必指定用哪些智能体。

他们还从静态团队扩展到自适应团队，这个技术叫 Adaptive Build：先把复杂任务分解成小步骤，为每一步提出一个专门的智能体团队，可以从已有的智能体库里选，也可以新建以前没有的智能体；完成一步后，再看下一步需要什么新智能体，所以智能体是动态选择的。新建的智能体会加回智能体库，让整个系统随时间改进。他们在数学、编程、数据分析等多个基准上做了实验，结果很有希望，超过了同类的已有技术。

开放问题

他说还有很多难题需要社区一起解决：

  • 最大的问题是怎样为任意应用设计最优的多智能体拓扑，要同时考虑质量、金钱成本、延迟和人工投入。
  • 怎样做出能力很强的智能体：推理、规划、多模态、学习。
  • 怎样实现规模化、安全和人的主导权：幻灯片上列了并行化、韧性、意图、教学。

最后他感谢开源贡献者，介绍了 Discord 社区和新的 GitHub 组织。幻灯片上致谢了 Qingyun Wu、Markus Buehler、Tamer Abuelsaad 和 Khoi Nguyen 帮忙准备课程材料。

第二部分：Jerry Liu，搭建多模态知识助手

07. 知识助手的目标和基本 RAG 的局限

录像位置 0:36:35–0:42:35

LlamaIndex 做什么

他介绍，LlamaIndex 是一家帮助开发者构建“上下文增强”的 LLM 应用、从原型走到生产的公司。开源工具包是一个在自己的数据上构建智能体和各类 LLM 应用的开发者工具包。他们一开始帮人搭 RAG 系统，现在进入更高级的领域，用 LLM 做多步推理，不再只做一次性的总结生成。另有一个企业产品 LlamaCloud，是托管服务，帮你承担数据索引和 RAG 这些事，这一讲不多讲。他会讲其中一块：文档解析，他认为这是任何上下文增强流水线里很重要的一环。

知识助手要做什么

他先问谁知道 RAG，然后简单解释：RAG 的一部分是有一个知识库，先从里面检索出一些文本；准备阶段要把文本切块（chunk）、做嵌入（embedding，把文本变成向量），放进比如向量数据库。

很多公司有大量数据，比如上百万个 PDF、一堆 PowerPoint、Excel 文件，想要一个界面：输入一个任务，返回一个输出。聊天机器人就是这样。输入可以是简单问题、复杂问题、研究任务；输出可以是简短回答、结构化输出、研究报告，也可以替你采取行动，比如发邮件、安排日历会议、写代码。

基本 RAG

按照“RAG 入门”教程做出来的，他们称为基本 RAG：拿到非结构化数据，用一个标准的文档解析器加载，每一千个 token 左右切一块，把每块送进嵌入模型（比如 OpenAI embeddings），存进向量库；检索时做语义搜索或向量搜索，取回最相关的条目（幻灯片上是 Top-K = 5），塞进 LLM 的提示窗口，用简单的问答提示生成回答。这条流水线能回答一些基本问题，但有四个局限：

  • 数据处理层很原始：切块时没考虑数据里的不同元素，有没有表格、图片、奇怪的章节，也没有把语义上该放在一起的内容保留在一起。检索接口也很原始。
  • 查询理解和规划很差：只用 LLM 做总结合成，没用它做任何推理或规划。他说前面讲的智能体协作那些东西，基本 RAG 一样都没用上，对 o1、Claude 3.5 这些能力强得多的模型是浪费。
  • 没有函数调用和工具使用。
  • 无状态，没有记忆：标准 RAG 一般是一次性的，不个性化，问完就忘，每次交互都是无状态的。这有好处，但要做个性化的知识助手，最好加一层记忆。

很多问题和任务基本 RAG 回答不了，会导致幻觉；一个 80% 的问题都答不上的聊天机器人价值有限，节省的时间和对决策的帮助都有限。问题是怎样构建一个更通用、生产级的知识助手，能处理任意复杂度的问题和任意规模的数据。

08. 多模态 RAG：解析、索引、检索

录像位置 0:42:35–0:50:52

更好的知识助手的四个组成

他说这一讲关注的是多模态：不只对普通文本文件做推理，还要能处理一整份带很多图表、图片的研究报告，处理互联网上的各种视觉数据。四个组成：

  1. 高质量的多模态检索流水线。
  2. 更复杂的输出：生成研究报告、做数据分析、采取行动，超出普通的聊天回复。
  3. 对复杂输入做智能体式推理：不只把用户问题拿去做总结，而是用 Chain-of-Thought、工具使用、反思等方法分解问题、做规划、一步步完成目标。幻灯片上列了工具使用、查询规划、记忆、反思。
  4. 部署：走向可扩展的全栈应用。

他说打算再讲 15 到 20 分钟，只讲高层要点，具体例子在幻灯片里有链接。

垃圾进，垃圾出

大家熟悉文本上的 RAG，他们关心的是能处理视觉数据的 RAG。视觉数据不限于 JPEG 文件，一份 PowerPoint 或一篇 arXiv 论文里也有图表、示意图、奇怪的版式。很多标准 RAG 流水线提取这些信息做得很糟。他说任何 LLM、RAG 或智能体应用的上限都取决于数据处理流水线。传统机器学习里“垃圾进、垃圾出”的原则在 LLM 应用开发里同样成立，数据质量好是生产级 LLM 应用的必要条件。这一层“面向 LLM 的 ETL”（ETL 指抽取、转换、加载，数据工程里把原始数据处理成可用格式的流程）包括解析文档、找到聪明的切块方式、再用聪明的方式建索引并放进提示窗口。

复杂文档

他们在很多公司看到一种常见的数据：复杂文档。里面有嵌入的表格、图表、图片，不规则的版式，页眉页脚。用现成组件解析，结果往往格式错乱，LLM 就会产生幻觉。用户对这些数据想问的问题也多种多样：简单的定点问题、多文档比较、更长的研究任务，比如给定 10 篇关于 LLM 量化的 arXiv 论文，生成一份浓缩的总结或综述。这比单纯的搜索检索层次更高。

为 LLM 设计的文档解析器

他说不需要懂解析的内部细节，但你需要一个好的 PDF 解析器。解析器不好，加载 PowerPoint 或 PDF 时提取不出正确的文字，把解析器“幻觉”出来的文字喂给 LLM，再好的 LLM 也很难理解。幻灯片上列的要求和非要求：

  • 要求：把表格准确解析成文本和半结构化表示；把正文解析成语义连贯的块；把视觉元素（图片、示意图、图表）提取成结构化格式，并返回图像块；自动提取元数据。
  • 不要求：为每个元素提取详细的 JSON；提取边界框。

他们做的 LlamaParse 是一个用生成式 AI 驱动的 PDF 解析器。他口头说用户已经超过 3 万，每人每天有 1000 页的免费额度；幻灯片上写的是 2 万多独立用户、处理了 2500 万页以上，并引了 Carlyle 应用 AI 负责人 Dean Barr 的评价，说它是他见过解析复杂文档结构最好的技术，能保留嵌套表格、提取复杂的空间版式和图片。幻灯片上的用例包括多模态 RAG、年报（表格）、Excel 表、表单。

高级解析加高级索引

把 PDF 解析成文本块、表格、示意图这些组成元素后，就可以用层级索引和检索（hierarchical indexing and retrieval）做比标准 RAG 更高级的事。标准 RAG 会直接对每个块做嵌入。他们发现更好的办法是：为每个元素提取多种指向源元素的表示。

  • 表格：提取几种不同的摘要，指向这张表。
  • 图片：没法直接送进文本嵌入模型，可以用模型提取几种文字摘要，指向这张图。
  • 大文本块：可以提取几个小文本块，指向大块。

这些表示他们称为节点（node），是实际被向量数据库（比如 Pinecone）嵌入和索引的东西，它们是和源元素相关联的元数据，不是源元素本身。检索时，根据用户问题先检索到节点；节点带有指向源文档的引用，于是可以“解引用”，把对应的源元素送进模型。幻灯片上把这叫递归检索（recursive retrieval）。

多模态 RAG 流水线

他说现在多数模型都是多模态的，o1、GPT-4o、Claude 3.5 Sonnet、Google 最新的 Gemini 都能同时接收文本和图像。所以可以继续用文本嵌入模型来表示元素，但真正送进 LLM 时，可以同时给文本和图像。幻灯片上的流水线：

  • 索引：用 LlamaParse 把文档解析成文本块和图像块；通过元数据把每个文本块链接到图像块；对文本块做嵌入并建索引。
  • 检索：用文本嵌入检索文本块；合成回答时，把文本和图像一起送进多模态 LLM。

给图像块建索引，也可以用 CLIP 嵌入，或者像上面说的用模型提取文字表示再链接到图像块。真正的多模态 RAG 流水线会同时存文本块和图像块，检索时两者都返回，一起送给多模态模型。幻灯片上有一个在复杂幻灯片文件上做多模态 RAG 的 notebook 示例，他跳过了。他提醒，到这里还没讲到智能体，这只是搭好多模态 RAG 的基础，还没用上 Chain-of-Thought、推理或工具使用，只是能就研究报告、幻灯片这类数据里的视觉元素提问并得到回答。

09. 报告生成和智能体式 RAG

录像位置 0:50:52–0:59:59

复杂输出：报告生成

他说智能体的很多前景在于，它除了给你一条聊天回复，还能生成整件产出：自己做一份 PowerPoint 或 PDF，或替你采取行动。他问有多少人用 Claude：你让它帮你写一篇申请 Berkeley 的文书，它会在旁边生成一整篇东西，这就是报告生成的例子，你可以直接复制粘贴再改。企业里这也很常见，很多咨询顾问和知识工作者希望拿到可以直接用的东西，代码也好，报告也好，而不是一段没有格式的回复。幻灯片上写，行动和产出生成在节省时间和提升能力上可能带来大得多的回报，解决方法是结构化输出和函数调用。他这里跳过了具体架构。幻灯片上的输出结构定义如下，报告由文本块和图像块交错组成：

class TextBlock(BaseModel):
    text: str

class ImageBlock(BaseModel):
    file_path: str

class ReportOutput(BaseModel):
    blocks: List[TextBlock | ImageBlock]

基本 RAG 在复杂问题上会失败

基本 RAG 对定点问题效果好，对复杂任务会失败，原因还是前面说的：只检索固定数量的块，也没用 LLM 先分解问题。幻灯片上列了四类复杂问题：

  • 总结类：“给我整份某公司 10-K 年报的总结”，需要整份文档，不是几个块。
  • 比较类：“比较候选人 A 和候选人 B 的开源贡献”，要查两份或更多文档。
  • 多部分问题：“讲讲文章 A 里支持 X 的论点和文章 B 里支持 Y 的论点，按我们的内部格式做一张表，再根据这些事实给出你自己的结论。”
  • 研究任务：“我想写一篇关于当前监督微调技术的综述，你能帮忙吗？”

从简单到高级的智能体组件

他说前一位讲者讲了多智能体怎样协作做很高级的事，他们的看法是智能体组件有简单到高级的一条谱系。简单的一端成本低、延迟低，包括工具使用、路由、一次性查询规划；高级的一端成本高、延迟高，包括 ReAct、对话记忆、动态规划加执行。

  • 高级的一端是完整的通用智能体架构。比如 ReAct（推理加行动的循环），差不多两年前提出，是现在最常见的智能体架构之一，用 Chain-of-Thought 加工具使用组成通用架构，可以接入任何工具，它会对工具做推理来完成任务。还有 LLM Compiler（他说是 Sehoon 的论文，字幕记作 seun），比 ReAct 更进一步做预先规划：它不再一次只规划下一步，会先规划出一个 DAG（有向无环图），优化、执行，并定期重新规划。
  • 他说他们实际看到的是：有人用 ReAct，它很容易上手；但也有很多人拿现有组件搭更受约束的架构，部分原因是想要可靠性。虽然表达能力弱一些、做不了所有事，但很多人还在建立对 AI 的信任，先解决一个具体用例，用更具体的组件、以更受约束的方式来做。这包括工具使用、记忆模块、函数调用；很多地方的人对结构化输出、调用已有 API 很感兴趣，还有基本的查询分解，比如 Chain-of-Thought，或者把一个问题并行拆成多个子问题。

智能体式 RAG

这一整套他们称为智能体式 RAG（agentic RAG），就是在 RAG 之上加一层智能体。把 RAG、检索或从向量数据库检索看作一种工具，智能体就在这些工具之上运作。查询不再直接送进向量数据库，而是先经过一个通用的智能体推理层，由它决定对查询做哪些处理、调用哪些工具来给出正确回答。幻灯片上的说法：每个数据接口都是一个工具；用智能体推理循环（顺序、DAG、树）处理复杂任务；结果是能处理复杂问题的个性化问答系统。

受约束和不受约束的流程

  • 更受约束的流程：比如有一个任务，用一个简单的路由提示（router prompt，从 N 个选项里选一个的 LLM 提示），根据它的决定把任务交给下游某个工具（RAG 工具或 SQL 工具），再经过一个反思层验证是否正确，然后给出回答。整个编排里没有循环。他说这更受约束，因为大部分控制流是人定义的，不是智能体定义的；更受约束的程序看起来就是你自己写的 if-else 和 while 循环。幻灯片上的评语：更可靠，表达能力更弱。
  • 不受约束的流程：用 ReAct、LLM Compiler、Tree of Thoughts 这类通用架构，等于说“我不知道要智能体按什么计划走，给它一堆工具让它自己想办法”（幻灯片上是一个智能体编排器连着 RAG、SQL、网页工具）。表达能力更强，理论上能解决更多种任务，但更不可靠：可能跑偏，调用你根本不想让它调的工具；可能卡在无限循环里永远不收敛；还更贵，这类架构提示更大，一次塞进更多工具，每次的 token 成本高得多。所以他们看到的很宽、不受约束的架构少一些。

他给的经验法则：如果用 ReAct 之类，以当前模型的能力，塞四五个工具，尽量控制在 10 个以内。

LlamaIndex Workflows

他说这些他们都叫 workflow，都在某种程度上是智能体式的。他给了一个很粗的智能体定义，承认每个人定义不同：一个包含非零次 LLM 调用的计算机程序。他们帮人写这类程序，不管是你自己写 if-else 条件的受约束程序，还是交给智能体处理的程序。核心是一个事件驱动的编排系统：每一步可以监听消息、把消息传给下游步骤，两步之间也可以来回传消息；每一步可以是普通 Python 代码、LLM 调用或任何东西；到某个时刻程序停止，返回结果。他们做这种底层编排，是因为认为智能体行为天然带有事件驱动的性质，这也方便把程序部署成 Python 服务。

幻灯片上列了他们认为编排框架应有的性质：事件驱动（每一步监听输入事件、发出输出事件）；可组合（把细粒度工作流拼成更高层的工作流）；灵活（逻辑可以用 LLM 调用写，也可以用纯 Python 写）；代码优先（编排逻辑用代码表达，易读易扩展）；可调试、可观测（能单步执行、观察状态）；容易部署到生产（把 notebook 代码变成生产服务）。

幻灯片还和基于图的方法做了对比，比如他们已弃用的 Query Pipelines：编排逻辑写在边里，代码更多、可读性差，运行时按条件动态生成工作流很麻烦。Workflows 的写法是用 @step 装饰器定义 retrieve、rerank、generate_response 等异步步骤，更易读，也更容易维护和扩展。这部分课上他跳过了。幻灯片上的另一页“收益和风险”写着：行动和产出生成可能带来更大回报；但 LLM 需要更高的可靠性，采取行动需要充分的人在回路才能建立信任。

录像位置 0:59:59–1:04:48

报告生成的架构

他们很关注报告生成这个用例，在很多公司都看到：给定一批数据，产出一份成品。一种架构是研究员加写作者，也许再加一个审稿人，可以看成多智能体系统，取决于你怎么定义。研究员做一点 RAG，从数据库检索相关的块和文档，或者上网抓取资料存进笔记，放进一个数据缓存，里面是生成报告所需的全部信息。写作者用这个数据缓存调用 LLM，生成文本、图片、表格交错的序列，给出完整产出。他们也有示例仓库能生成整套幻灯片，不限于报告。

客服

另一个幻灯片上没有的用例是客服。他说从实际企业用例看，面向外部的客服可能是智能体的头号用例：决策流程里有大量可以自动化的部分，可以提高分流率（deflection rate，不需要转人工就解决的比例），让用户体验比那种自动电话菜单好得多。

在生产里跑智能体

开始搭这些组件时，你多半在 Jupyter notebook 里做，这完全没问题，做原型时就应该本地、范围窄，看它在测试数据上是否有效。一个有意思的设计练习是：复杂的多智能体架构在生产里是什么样，怎样用现有的生产基础设施组件来实现。每个智能体负责一部分任务，它们之间能以某种方式通信，所以理想情况下：

  • 把每个智能体的行为封装在一个 API 接口后面，可以复用。
  • 通过一个核心消息层，标准化智能体之间以及和客户端之间的通信方式。
  • 能方便地增加智能体的数量，也能承载大量不同会话的客户请求。
  • 为终端用户提供人在回路；为开发者提供调试和可观测工具。

他们在做的 llama-deploy（还在进行中，但过去几个月进展很多）就是把智能体工作流部署成微服务：每个智能体工作流是一个服务 API；可以在本地启动，也可以部署到 Kubernetes（幻灯片上还有 docker-compose）；所有智能体通信都经过一个中央消息队列；工具执行是分布式的；人在回路也作为一个服务，比如某个智能体需要你的输入，它会给你发消息、等你回复，拿到输入后再继续执行。幻灯片上的架构图里，还有一个控制平面和编排器决定下一步发生什么。

他问有多少人看过 Cognition Labs 的 Devin 演示，大约一半人知道。这个编程智能体会为你生成整个代码仓库，但有时会停下来说：“我不够清楚该怎么做，你能告诉我下一步吗？”这就是人在回路的例子：一种有意思的客户端和服务器之间的来回通信，服务器在等客户端发来人的反馈。他说这些组件都是一步步走向在自己数据上搭建生产级多模态知识助手的过程。
