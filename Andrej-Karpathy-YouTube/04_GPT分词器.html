从零实现 GPT 分词器

BPE、Unicode、正则预切分、特殊 token 与为什么 tokenization 会塑造模型能力

演讲：Andrej Karpathy · 发布：2024 年 2 月 20 日 · 时长：2 小时 13 分
资料来源：Let's build the GPT Tokenizer（依据公开视频章节与英文自动字幕整理）

一、分词器是模型外的一道独立工序

Transformer 只接收整数 ID；把字符串编码为 ID、再把 ID 解码为字符串，是 tokenizer 的职责。它不随模型反向传播学习，却决定序列长度、词表大小、不同语言的压缩率、特殊标记怎样进入上下文，以及模型会在哪些字符边界上犯错。

实现前要先分清 Python 字符串、Unicode code point 和 UTF-8 字节。GPT-2 系的 byte-level tokenizer 能表示任意文本：先转 UTF-8 bytes，再把 bytes 当作初始符号，因此不会有传统词表的未知字问题。

二、BPE 如何从字节长出子词

Byte Pair Encoding 从单字节 token 开始，反复统计训练文本中相邻 token 对的频率，把最常见的一对合并成新 token，直到达到词表上限。训练产物是 merge 表；编码新文本时按同样的 merge 优先级不断合并，解码则把 token 字节拼回 UTF-8。

BPE 的目标是压缩，不是发现“真正的词”。常见片段会成为一个 token，罕见词则由多个片段组成；这使高频文本更短，但也造成数字、拼写、空格、非英语文本与安全过滤上的怪异行为。比较模型时，应先问 tokenizer 是什么，而不是只看参数量。

三、GPT 的工程细节

GPT-2 并非直接在整段原始 bytes 上运行：先用正则表达式把文本粗分为字母、数字、标点和空白等类别，再在每段内 BPE。这样可避免跨越不合理边界的 merge。GPT-4 系 tokenizer 的正则、词表和 special tokens 又与 GPT-2 不同，因此不能把同一字符串的 token 数跨模型直接比较。

特殊 token 代表消息边界、文档边界或控制信号。它们必须显式处理：允许用户输入把保留标记当普通文本编码，可能改变下游协议；禁止得太死，又会妨碍实际聊天模板。视频的练习是自己实现一个接近 GPT-4 的 tokenizer，并用 round-trip、压缩率和与参考实现的一致性测试它。

四、从文本走向多模态

图像、音频和视频也需先变成模型可消费的表示。文本通常离散化为 BPE token；图像和音频常先编码为连续向量或经向量量化为离散 code，再交给 Transformer。输入模态不同，但“有限上下文预算中的一串表示”这个问题相同。

最后的建议很实际：遇到 token 计费、上下文溢出、模型拼写异常或多语言性能差时，先观察 tokenizer；不要把它误当成一个无关紧要的预处理脚本。
